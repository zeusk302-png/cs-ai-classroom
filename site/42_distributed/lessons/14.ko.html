소단원 14.1

RPC 키값 서버·Raft 연결

서버 세 대에 같은 요청을 보냈다는 사실만으로 세 대의 결과가 같아질까?

준비 개념과 학습 목표

준비 개념

  • RPC 요청과 응답

  • 결정적 상태기계

  • Raft 로그·term·commit

  • 선형화 가능성

학습 목표

  • 요청 접수와 로그 커밋·상태 적용을 구분한다.

  • 요청 식별자와 결과 대기자의 연결을 설계한다.

  • 읽기를 오래된 복제본에서 즉시 반환할 수 없는 이유를 설명한다.

서비스 명세와 상태기계를 먼저 정한다

학습용 서비스의 상태는 문자열 키에서 정수 값으로 가는 표다. Put(k,v)는 값을 덮어쓰고 Get(k)는 값 또는 명시적인 NotFound를 반환한다. 값 0과 부재를 구별한다. 연습용 Add(k,delta)는 기존 값을 증가시키며 중복 처리의 필요를 보여 주는 별도 연산이다. 모든 정상 명령은 같은 이전 상태에서 같은 다음 상태와 결과를 만든다. 현재 시각이나 임의 수를 각 복제본에서 따로 고르면 이 조건이 깨진다.

Raft 모듈은 명령을 합의된 로그 순서로 전달하고 서비스는 적용한 결과를 만든다. RPC handler가 요청을 받았다는 사실, 리더가 로그에 추가한 사실, 커밋된 사실, 서비스가 적용한 사실은 서로 다르다. 성공 응답은 명세에 맞게 커밋과 적용 결과를 확인한 뒤 보내도록 설계한다. 원격 호출 실패는 요청이 실행되지 않았다는 증명이 아니다.

제안과 적용 결과를 같은 요청으로 연결한다

서버는 (클라이언트 ID, 요청 번호) 같은 식별자를 명령에 담아 제안한다. 적용 경로는 커밋된 명령을 순서대로 읽고 상태기계에 전달한 뒤 해당 식별자의 대기자에게 결과를 전달한다. 로그 index만으로 기다리면 리더 교체 뒤 그 index에 다른 명령이 들어간 경우를 혼동할 수 있다. index와 term 및 요청 식별자를 대조하고 일치하지 않는 결과로 성공 응답을 만들지 않는다.

제안 직후 리더가 바뀌거나 결과가 대기자 등록보다 먼저 도착할 수 있다. 구현 계약은 등록과 결과 전달의 경쟁을 잠금 또는 완료 결과 보관으로 해결한다. 서비스가 잠금을 잡은 채 무기한 네트워크 응답을 기다리면 적용 경로가 멈출 수 있으므로 잠금 범위도 분리한다. 이 단원에서는 실제 goroutine 프로그램 대신 요청→제안→커밋→적용→응답이라는 종이 시간선을 그린다.

읽기 역시 최신성의 근거가 필요하다

세 노드 A,B,C에서 이전 리더 A가 혼자 떨어지고 B,C가 새 리더를 세웠다고 하자. A는 아직 자신이 리더라고 생각해도 새 커밋을 모른다. A의 메모리 표를 즉시 읽어 반환하면 이미 성공한 Put 이전 값이 나올 수 있다. 단순 학습 설계는 Get도 로그 명령으로 제안하여 최신 합의된 적용 순서에서 읽는다.

더 효율적인 읽기는 별도의 리더 확인·읽기 장벽·안전한 lease 조건을 요구한다. 이를 구현하지 않은 상태에서 메모리 Get을 최적화라고 바꾸지 않는다. 다수에 복제되었다는 사실도 과거 term의 항목에 언제나 직접 커밋 규칙을 적용할 수 있다는 뜻은 아니다. 아래 계산은 현재 term에서 리더가 제안한 명령에 한정하고, 정확한 Raft 규칙은 앞 단원의 조건을 유지한다.

중간 과정을 따라가는 예제

고정 세 노드 A,B,C의 현재 term 리더는 A다. 초기 x=2다. 현재 term의 index 7에 Put(x,5)를 넣었다. A와 B의 영속 로그에 들어갔고 C는 늦다. 이후 커밋·적용·읽기 경로를 추적하라.

  1. 세 노드의 다수는 2다. 리더 자신 A와 B를 합친 2개가 현재 term 항목을 영속 보관했으므로 이 조건에서 index 7을 커밋할 수 있다. C의 응답을 반드시 기다릴 필요는 없다.

  2. A의 적용 경로가 index 7을 순서대로 적용하여 x=5와 Put 결과를 만든다. 요청 식별자가 대기자와 일치하면 성공 응답을 반환한다. 복제만 되고 아직 적용되지 않았으면 서비스 결과는 아직 준비되지 않았다.

  3. Get(x)를 다음 로그 index 8에 넣고 커밋·적용한다. 적용 시 x=5이므로 5를 반환한다.

  4. C는 커밋 위치를 전달받고 따라 적용하여 x=5가 된다. 그 전의 C는 x=2일 수 있으므로 아무 확인 없이 C에서 읽은 값은 이 성공한 Put 뒤 읽기의 근거가 되지 않는다.

이 예제처럼 Put 성공 뒤 호출되어 다음 로그에서 적용되는 Get은 5다. 모든 노드가 매 순간 동시에 같은 메모리 상태여야 한다는 조건과 합의된 적용 순서의 안전성을 혼동하지 않는다. 호출이 앞서 Put과 겹친 Get은 별도의 허용 순서를 검토해야 한다.

종이와 본문으로 직접 해보기

로그 index 9의 요청 R을 기다리던 이전 리더에서 새 term의 index 9 명령 S가 적용되었다. 대기자는 index가 같다는 이유로 S의 성공 결과를 R에게 돌려줘도 되는가?

힌트 보기

위치는 같지만 명령의 정체성과 term이 다르다.

풀이 보기

안 된다. 식별자가 일치하지 않으므로 R의 성공 증거가 아니다. 리더 변경/재시도 가능한 오류 또는 결과 불명 상태를 명세대로 반환하고 같은 요청 식별자로 재시도하게 한다.

오해와 반례

리더가 요청을 로그에 추가했으면 클라이언트에게 바로 성공이라고 해도 된다.

미커밋 항목은 리더 교체 뒤 사라질 수 있다. 커밋·순서 적용·해당 요청 결과를 확인하기 전의 접수는 성공 보장이 아니다.

자기점검

세 노드 중 두 노드의 로그에 있는 현재 term 명령은 언제 서비스 결과를 반환하는가?

답과 이유 보기

로그 복제와 상태기계 실행은 다른 단계다.

겹친 Get이 Put 이전 값 0을 반환하면 반드시 선형화 위반인가?

소단원 14.2

재시작·스냅샷·중복 처리

결과를 보낸 서버가 죽어 같은 요청이 다시 와도 한 번만 더한 것으로 만들 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 요청 ID와 at-most-once 효과

  • 로그 재생

  • 스냅샷의 적용 경계

  • 영속 상태의 원자적 조합

학습 목표

  • 중복 검사 위치를 상태 적용 경로로 정한다.

  • 키값과 중복 결과를 함께 스냅샷에 넣는다.

  • 이미 스냅샷에 포함한 로그를 재적용하지 않는 이유를 설명한다.

재시도는 같은 요청의 다른 전달이다

RPC 응답이 없어도 서버가 명령을 실행했을 수 있다. 새 요청 번호로 Add를 재시도하면 별도의 증가로 해석되어 두 번 더할 수 있다. 같은 논리 요청은 같은 ID를 유지한다. 학습용 모형은 모든 완료 요청의 ID, 요청 내용과 결과를 표에 보관한다. 같은 ID와 내용이 다시 적용되면 표의 결과를 반환하고 상태 효과는 반복하지 않는다.

중복 검사를 RPC 접수 순간에만 하면 동시에 들어온 두 복사본이 모두 미완료로 보이거나 서로 다른 리더에 들어갈 수 있다. 각 복제본이 합의된 적용 경로에서 검사해야 같은 상태를 만든다. 같은 ID를 다른 내용에 재사용하면 잘못된 클라이언트 요청으로 거부한다. 모든 ID를 무한 보관하는 것은 실제 서비스의 해결책이 아니므로 만료와 클라이언트 재시작 정책을 설계할 때 보장 범위를 함께 정한다.

사진에는 재시도에 필요한 기억도 담는다

스냅샷은 특정 적용 index까지의 서비스 상태를 저장한 것이다. 키값 표뿐 아니라 중복 요청의 결과 표, 마지막 적용 위치와 해당 Raft 경계 정보가 필요하다. 이미 효과를 반영한 요청을 기억하지 못하면 재시작 후 같은 요청이 다시 실행된다. snapshot의 마지막 index와 term은 이후 로그가 어떤 경계부터 이어지는지 확인하는 근거다.

종이 모형은 index s까지 적용한 상태 사진을 원자적으로 보관하고, 그 뒤의 커밋된 로그만 순서대로 재생한다. 적용 중 상태와 별개 시점의 요청 표를 섞어 찍으면 같은 경계를 나타내지 않는다. 실제 구현에서는 Raft 영속 상태와 대응 snapshot을 일관되게 저장하는 API, 오래된 snapshot 거부, 남겨야 할 로그 suffix의 조건을 검증해야 한다. 사진을 만들기 전에 필요한 로그를 지우면 장애 뒤 복구할 정보가 사라진다.

로그의 위치와 논리 요청의 중복은 다른 문제다

snapshot 이전 index를 다시 적용하지 않는 것은 로그 경계 검사이고, snapshot 이후에 같은 클라이언트 요청이 다른 index에 다시 들어오는 것을 막는 것은 요청 중복 검사다. 하나가 다른 하나를 대신하지 않는다. 동일 항목 전달이 반복되거나 복구가 다시 시작되는 경우에도 마지막 적용 위치와 중복 결과를 일관되게 유지한다.

값 덮어쓰기 Put은 우연히 같은 최종 값을 만들 수 있어 중복 결함을 감춘다. Add처럼 효과가 반복되면 달라지는 자체 연산으로 검증하면 문제를 드러낼 수 있다. 이것은 네트워크 메시지가 한 번만 전달된다는 주장이 아니다. 여러 전달과 로그 항목이 있어도 명세에서 정한 논리 요청의 상태 효과를 한 번으로 제한하는 설계다.

중간 과정을 따라가는 예제

초기 x=4이다. 요청 R=(c,7,Add(x,3))가 index 10에서 적용되어 결과 7을 만들었으나 응답이 유실되었다. index 10까지 snapshot을 찍고 재시작한다. R의 재시도가 index 11에 들어오고 S=(c,8,Add(x,2))가 index 12에 들어오면 최종 상태와 응답은 무엇인가?

  1. index 10 적용 후 x=7이고 중복 표에는 R의 내용과 결과 7을 보관한다. snapshot에 이 표와 x=7, 경계 index 10을 함께 담는다.

  2. 재시작은 snapshot을 복원하고 index 10을 다시 적용하지 않는다. index 11의 R을 적용 경로에서 발견하면 동일 ID와 내용이 이미 있으므로 x를 바꾸지 않고 보관 결과 7을 반환한다.

  3. index 12의 S는 새 ID다. x=7+2=9로 만들고 S 결과 9를 보관한다.

  4. 반례로 요청 표를 빼고 x=7만 복원하면 R 재시도가 3을 다시 더해 10을 만들고 S 뒤 12가 된다. 이는 요구한 9와 다르다.

올바른 최종 x는 9, R의 재시도 결과는 7, S의 결과는 9다. 재시도 결과는 현재 값이 아니라 원래 요청의 완료 결과일 수 있다.

종이와 본문으로 직접 해보기

snapshot index 10 뒤의 로그에 index 9, 11, 12가 전달되었다. 어느 항목을 경계 검사에서 건너뛰는가? index 11이 R의 복사본이면 상태 효과는 있는가?

힌트 보기

snapshot 경계와 요청 표를 각각 확인한다.

풀이 보기

index 9는 이미 snapshot에 포함된 경계 이전이므로 재적용하지 않는다. 11과 12는 그 뒤 순서로 처리한다. 11의 R은 요청 표에 있어 효과 없이 원래 결과를 반환한다. 경계 검사만으로 11의 중복을 알 수는 없다.

오해와 반례

키값 표만 snapshot에 넣으면 서버를 완전히 복원한다.

요청 중복 상태가 빠지면 응답 유실 뒤 재시도를 새 효과로 처리할 수 있다. 위 반례는 최종 12를 만들어 원래 명세의 9를 위반한다. 복구에 필요한 서비스 상태 전체와 경계를 저장해야 한다.

자기점검

같은 R을 새 요청 번호 8로 재시도하면 중복으로 인식되는가?

답과 이유 보기

일반적으로 아니다.

그 번호는 새로운 논리 요청을 뜻한다. 재시도 때 ID를 유지해야 한다.

중복 R의 응답이 현재 x=9 대신 7인 이유는?

답과 이유 보기

원래 R이 완료되었을 때의 결과를 반환하기 때문이다.

후속 S가 만든 값을 R의 결과로 바꾸면 동일 요청의 결과 계약이 달라진다.

snapshot의 키값만 보관하고 요청 R의 결과 표를 버리면 재시도 안전한가?

답과 이유 보기

아니다. 이미 적용한 R을 다시 실행할 수 있다.

적용 상태와 중복 요청 식별자·원래 결과를 함께 복구하는 계약이 필요하다.

한 단계 더

요청 표가 커질 때 클라이언트가 이전 결과를 더는 요구하지 않는다는 확인, 세션 만료, 여러 미완료 요청 허용 여부를 설계해 보자. 최고 번호 한 개만 기억하는 단순 방식은 동시 요청과 순서가 뒤바뀐 재시도에서 추가 조건이 필요하다.

소단원 14.3

안전성·활성·성능 검증

응답이 빠른 서버가 틀린 값을 돌려주면 좋은 복제 서비스라고 할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 안전성과 활성의 구분

  • 선형화 가능 이력

  • 분할과 다수

  • 완료 요청과 시도 횟수

학습 목표

  • 허용되지 않는 이력과 단순 지연을 구분한다.

  • 분할 중 다수/소수의 진행 조건을 설명한다.

  • 재시도를 논리 작업 수와 분리해 처리량을 계산한다.

어떤 잘못도 일어나지 않았는가

안전성 검사는 서로 다른 복제본이 같은 적용 위치에 다른 명령을 적용하지 않는지, 성공 응답한 쓰기가 복구 뒤 사라지지 않는지, 완료된 요청들의 읽기 결과가 서비스 명세와 실시간 선후관계에 맞는지 확인한다. 선형화 가능성은 각 논리 작업을 호출과 반환 사이 한 순간에 실행된 것처럼 배열할 수 있다는 조건이다. 물리 시계가 다른 서버의 timestamp만으로 이 순서를 정하면 안 된다.

작은 이력은 종이에 직접 순서를 시도할 수 있다. 여러 가능한 배열을 탐색하는 검사기가 시간 제한을 넘기면 통과가 아니라 결론 미정으로 남긴다. 안전성 실패 하나는 반례지만 유한 번 통과는 모든 실행의 증명이 아니다. 이력의 요청 ID, 호출/반환, 결과, 타임아웃과 재시도를 함께 보관해야 검사 의미가 유지된다.

언제까지 기다리는가

활성은 계속 요청이 끝나지 않는 문제와 관계한다. 고정 5노드의 다수는 3이다. {A,B}와 {C,D,E}로 분할되면 소수 쪽은 최신 선형화 읽기·새 커밋을 성공시키면 안 된다. 다수 쪽도 리더 선출과 영속 저장, 노드 간 및 클라이언트 통신이 안정되어야 진행할 수 있다. 다수가 있다는 수량만으로 즉시 응답을 보장하지 않는다.

분할이 회복되면 재시도 중인 클라이언트가 올바른 리더를 찾고 로그와 snapshot이 따라잡는지 확인한다. 무한 네트워크 지연을 허용한 채 고정 시간 내 모든 요청 완료를 요구하지 않는다. 테스트 시간 제한은 실험의 판정 기준이며 합의 알고리즘의 보편적인 시간 보장이 아니다. 이전 리더가 자신의 상태만 보고 성공한 읽기를 제공하는 결함을 별도로 시험한다.

정확한 완료 수로 속도를 기록한다

성능표의 작업은 명세상 완료된 논리 요청이다. RPC 재시도 150회가 논리 요청 완료 100개를 뜻할 수도 있다. 처리량은 지정한 측정 구간의 완료 수/구간 길이이고 실패·타임아웃은 별도 열에 남긴다. 재시도 증폭은 RPC 시도 수/논리 완료 수처럼 분모를 정의해야 한다. 응답을 못 받은 요청도 실제 커밋되었을 수 있으므로 서버 효과 수와 클라이언트 완료 수를 별도 비교한다.

같은 초기 데이터, 노드 수, 요청 비율과 부하 방식을 사용하고 정상·분할·재시작 조건을 나누어 기록한다. 중앙값과 꼬리 지연에는 사용한 표본과 실패 처리법을 적는다. 빨라 보이는 변화가 중복 처리나 최신 읽기 장벽을 제거한 것이라면 정확성 계약을 바꾼 것이므로 동일 서비스의 개선으로 계산하지 않는다. 여기의 숫자는 자체 가상 자료이며 실제 클러스터 측정값이 아니다.

중간 과정을 따라가는 예제

초기 x=0이다. Put(x,1)이 시간 0에 호출되고 2에 성공 반환한다. Get(x)는 3에 호출되고 4에 값 0을 반환했다. 별도 가상 성능 실험에서 10초 동안 RPC 시도 150회, 논리 완료 100개를 기록했다. 판정과 계수를 구하라.

  1. Put은 Get 호출 전에 완료되었다. 따라서 선형화 순서는 Put 앞, Get 뒤여야 한다.

  2. 다른 쓰기가 없는 명세에서 Get은 1을 반환해야 한다. 0을 반환한 이력은 오래된 읽기 반례이며 단순 느림 문제가 아니다.

  3. 가상 처리량은 논리 완료 100/10=10개/초다. RPC 시도는 150/10=15회/초지만 이를 처리량 15작업/초라고 부르면 중복 시도를 작업으로 센다.

  4. 완료당 RPC 시도는 150/100=1.5다. 시도마다 응답 시간을 모두 넣으면 같은 논리 요청의 여러 시도가 중복 표본이 되므로 지연의 표본 규약도 따로 정한다.

이력은 안전성 위반이다. 별도 가상 계수의 논리 처리량은 10개/초, 시도율 15회/초, 완료당 시도 1.5회다. 정확성 위반 이력의 빠른 응답을 좋은 성능으로 인정하지 않는다.

종이와 본문으로 직접 해보기

Get 호출을 시간 1로 바꾸어 Put과 겹치게 하면 Get=0은 언제 가능한가? 5노드 중 2노드와 3노드로 분할했을 때 어느 쪽이 안정된 리더와 통신 조건 아래 새 작업을 커밋할 수 있는가?

힌트 보기

겹치는 작업의 순서는 실시간 조건으로 하나만 강제되지 않는다.

풀이 보기

겹친 Get을 Put보다 먼저 선형화할 수 있는 이력이면 초기 값 0이 가능하다. 다수가 3이므로 3노드 쪽은 조건이 충족될 때 진행할 수 있고 2노드 쪽은 새 작업을 커밋할 수 없다. 이는 즉시 완료를 보장한다는 뜻은 아니다.

오해와 반례

테스트 제한 시간 동안 오류가 없으면 안전성과 활성이 모두 증명되었다.

미완료 요청, 검사기 시간 초과와 실험 범위를 확인해야 한다. 테스트는 주어진 실행에 대한 근거이고 모든 가능한 지연·장애 실행의 보편적 증명은 아니다.

자기점검

150번 RPC를 보내 100개의 요청을 완료했다면 요청이 150개 처리된 것인가?

답과 이유 보기

아니다. 논리 완료는 100개다.

재시도 전달과 논리 작업을 분리해야 처리량과 중복 효과를 올바르게 해석한다.

소수 이전 리더가 응답을 보류하는 것은 바로 안전성 실패인가?

답과 이유 보기

아니다.

진행이 제한될 수 있지만 근거 없는 최신 결과를 반환하지 않는 것은 안전성 보존과 일치한다.

100개 완료와 150개 시도의 10초 기록에서 시도 처리율을 완료 처리율로 쓰는가?

답과 이유 보기

아니다. 완료는 10개/초, 시도는 15개/초다.

분자가 다르고 재시도·미완료가 포함되므로 같은 지표로 보고하지 않는다.
