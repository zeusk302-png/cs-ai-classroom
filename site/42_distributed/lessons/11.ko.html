최종 일관성

저장 성공 표시 뒤 다른 서버에서 옛 이름을 읽었다면 저장이 반드시 사라진 것일까?

학습 목표

  • 전파와 충돌 해결의 조건을 적는다.

  • 수렴 시한과 쓰기 내구성을 별도로 판단한다.

모든 복제본이 같은 값이면 현실에서 마지막으로 쓴 값일까요?

자체 LWW register에서 한 쓰기는 값과 불변 순서 키 (시계 숫자,작성자 ID)를 함께 갖는다. 작성자 ID는 A<B의 순서로 비교하고 시계 숫자를 먼저 비교한다. 이 예제에서는 작성자별 쓰기가 하나씩이라 두 키가 고유하다. 각 복제본은 받은 쓰기 중 가장 큰 키의 값만 보존한다. 현실 시각 10에 A가 red를 쓰며 시계 숫자 110을 붙였다. 현실 시각 12에 B가 blue를 쓰며 시계 숫자 12를 붙였다. 두 쓰기는 상대의 쓰기를 보지 않고 만들었다. 시계 숫자는 현실 시각과 일치한다는 가정이 없다.

모든 쓰기를 받아 적용한 복제본은 (110,A)의 red를 고른다. A의 쓰기를 먼저 받든 B의 쓰기를 먼저 받든 결과는 같다. 현실에서는 B의 blue가 나중 쓰기지만 키 비교는 red를 고른다. 수렴은 두 값을 모두 보존하거나 현실의 가장 나중 의도를 보존한다는 뜻이 아니다. 이 계약은 정해진 순서 키의 최댓값으로 충돌을 해소한다. 인과 순서를 시계 숫자로 자동 보장한다고도 주장하지 않는다.

시계 숫자만 비교하고 같은 숫자는 현재 값을 그대로 유지하는 다른 규칙을 생각하자. A와 B가 각각 숫자 100을 붙이면 A를 먼저 받은 복제본은 red를, B를 먼저 받은 복제본은 blue를 유지할 수 있다. 도착 순서에 의존하는 동률 해소는 같은 쓰기를 받은 뒤에도 수렴하지 않는다. 작성자 ID까지 고유한 전체 순서로 비교하면 B의 blue로 합쳐진다. 실제 여러 쓰기를 허용할 때는 동일 작성자와 같은 시계 숫자도 구별할 추가 순번 등 고유 키 계약이 필요하다.

복제본의 현재 상태가 잠시 다를 수 있다

복제본은 같은 논리 데이터를 여러 곳에 저장한 사본이다. 비동기 복제에서는 한곳이 쓰기를 받아 응답한 뒤 다른 곳이 메시지를 늦게 받을 수 있다. 읽기 요청이 아직 갱신되지 않은 곳으로 이동하면 옛 값을 볼 수 있다. 이는 해당 이력만으로 원래 저장이 영구히 사라졌다는 뜻은 아니다.

최종 일관성은 새 갱신이 멈추고 필요한 갱신이 결국 전달·반영되는 조건에서 복제본이 정해진 상태로 수렴하는 보장이다. 수렴 뒤 같은 상태를 읽는 것과 매 순간 가장 최근 쓰기를 읽는 것은 다르다. 동시에 발생한 쓰기에는 어떤 상태로 합칠지 정책도 필요하다.

전파 조건과 충돌 정책을 따로 정한다

연결이 영구히 끊겨 메시지가 전달되지 않으면 수렴을 기대할 근거가 없다. 재전송·동기화·적용 규칙이 필요하며 지연되거나 중복된 메시지가 상태를 잘못 되돌리지 않게 버전도 관리한다. 단순히 일정 시간이 흘렀다고 내용이 자동으로 맞아지는 것은 아니다.

두 곳이 서로의 변경을 보지 못하고 같은 값을 바꾸면 충돌할 수 있다. 마지막 쓰기 우선, 여러 버전 보존, 자료형별 병합 등은 서로 다른 결과를 만든다. 모든 갱신의 사용자 의도가 그대로 보존되는지를 수렴 여부만으로 판단할 수 없다.

시한과 장애 손실은 다른 보장이다

일반적인 최종 수렴 조건만으로 정확히 2초 뒤 일치한다는 시간 상한이 나오지 않는다. 전달 지연·장애 복구·처리량·서비스 계약을 추가로 알아야 한다. 실제 제품의 읽기 모드는 공식 문서와 설정으로 확인하며 과거 논문의 방식을 현재 모든 클라우드에 적용하지 않는다.

내구성은 응답한 쓰기가 장애 뒤에도 보존되는지의 문제다. 유일하게 새 값을 가진 복제본이 영구 손실되었다면 옛 값들이 서로 같아진다고 쓰기가 보존된 것이 아니다. 최종 일관성과 내구성·트랜잭션 무결성은 구별해 설계한다.

현실 시각과 시계 숫자는 서로 다른 열의 정보다. 복제본이 같다는 결론은 동일 쓰기 집합을 받았다는 전제에서 낸다. 수렴 시점의 상한과 저장 장애 뒤 보존은 이 표에서 주지 않았다.

중간 과정을 따라가는 예제

처음 A/B/C가 (v0, 옛 이름)이다. 단일 작성자가 A에 (v1, 새 이름)을 쓰고 성공 응답을 받는다. A는 B/C에 메시지를 보내고 버전이 큰 상태만 적용한다. t1의 B 읽기, t2의 B 전달, t3의 C 읽기, t4의 C 전달 순서라면?

  1. 쓰기 직후 상태는 A v1, B v0, C v0다. t1의 B 읽기는 옛 이름이다.

  2. t2 이후 B도 v1이다. t3의 C는 아직 v0이므로 옛 이름을 읽는다.

  3. t4 이후 세 곳 모두 v1·새 이름이다. 이후 새 쓰기가 없고 상태가 보존되면 수렴했다.

  4. C에 늦게 v0 메시지가 와도 큰 버전만 적용하는 규칙으로 v1을 유지한다.

  5. t1이 쓰기 성공 뒤라도 옛 값을 반환하므로 이 이력은 즉시 최신 읽기를 보장하지 않는다. 숫자 t는 순서를 나타내며 초 단위 지연 측정이 아니다.

쓰기 완료 뒤에도 B/C에서 옛 값을 읽다가 메시지 적용 후 같은 새 상태로 수렴한다.

조건을 바꾸어 비교하기

순서가 다른 전달의 같은 최댓값

R은 A 뒤 B, S는 B 뒤 A를 받는다. 원래 두 쓰기의 최종 값과 현실에서 나중 쓰기를 비교하라.

  1. R은 먼저 red를 보존하고 작은 키의 blue를 받아도 red를 유지한다.

  2. S는 먼저 blue를 보존하지만 큰 키의 red를 받으면 red로 바뀐다. 현실에서 나중 쓰기는 B의 blue다.

두 복제본은 red로 수렴하지만 현실에서 나중 쓰기는 blue다.

동률 때 현재 값을 유지하는 실패

별도 쓰기 A와 B의 시계 숫자가 모두 100이다. 같은 숫자에서 현재 값을 유지하는 규칙과 작성자 ID까지 비교하는 규칙을 대조하라.

  1. 현재 값을 유지하면 A를 먼저 받은 R은 red, B를 먼저 받은 S는 blue를 보존한다.

  2. 키 (100,A)와 (100,B)를 전체 순서로 비교하면 두 곳 모두 B의 blue를 고른다.

숫자만의 동률 유지 규칙은 도착 순서에 따라 갈리고 고유 전체 순서는 blue로 수렴한다.

비교할 점

동일 숫자라는 사실만으로 동일 쓰기라고 판정하지 않는다.

삭제한 항목이 concurrent add 때문에 남는 이유는 무엇일까요?

자체 observed-remove set은 추가 태그 집합 A와 제거 태그 집합 R을 보존한다. 태그는 작성자와 순번으로 고유하며 항목 p의 태그 p1과 p2는 서로 다른 추가다. 보이는 p는 A 안의 p 태그 중 R에 없는 태그가 하나라도 있을 때 존재한다. 병합은 A끼리 합집합, R끼리 합집합이다. 제거 연산은 그 복제본이 현재 관측한 p의 추가 태그를 R에 넣는다. 태그를 과거와 독립된 새 추가에 재사용하지 않는다.

처음 두 복제본은 A={p1}, R=∅다. 분리된 동안 X는 p를 새 태그 p2로 추가한다. X의 상태는 A={p1,p2}, R=∅다. Y는 자신이 본 p를 제거하여 A={p1}, R={p1}이 된다. 병합하면 A={p1,p2}, R={p1}이고 살아 있는 태그는 p2다. 따라서 p는 남는다. 이는 Y가 아직 보지 못한 추가 p2를 제거하지 않았다는 observed-remove 규칙이며 삭제 실패나 무조건 최근 시간 선택이 아니다.

병합 뒤 Y가 p2까지 관측하고 p를 다시 제거하면 R={p1,p2}가 되어 p는 보이지 않는다. 그 뒤 옛 추가 p1이 다시 전달돼도 제거 태그 p1이 남아 있으므로 부활하지 않는다. 제거 흔적을 지우면 이 방어가 사라진다. 여기서는 설명을 위해 추가와 제거 태그를 모두 보존하는 합집합 상태를 쓴다. 실제 Akka의 압축 상태나 delta 전송 구현을 실행하거나 같은 자료구조라고 주장하지 않는다. 안전한 흔적 정리에는 더 이상 관련 옛 상태가 도착하지 않는다는 별도 증거가 필요하다.

벽시계와 인과 버전은 다른 정보를 준다

두 작성자 A/B의 버전 벡터를 (A 수, B 수)로 나타내자. 각 작성자는 본 변경을 반영한 후 자기 성분을 증가시킨다. 모든 성분에서 v ≤ w이고 적어도 하나가 작으면 v가 w보다 이전이라는 관계를 기록한다. 어느 쪽도 상대를 지배하지 않으면 동시 갱신으로 본다.

(2,0)과 (1,1)은 A 성분과 B 성분의 크기 방향이 달라 비교할 수 없다. (2,1)은 둘의 이력을 모두 포함할 수 있다. 벡터를 병합해도 실제 문서 내용이 자동으로 의미 있게 합쳐지는 것은 아니다. 벽시계 기반 우선순위는 시계 차이 때문에 실제 작성 시각의 선후와 다를 수 있다.

정해진 결과가 모든 의도를 보존하지는 않는다

마지막 쓰기 우선 정책은 시간표식과 동점 해소 규칙으로 한 값을 고르면 수렴할 수 있지만 다른 수정은 버린다. 여러 동시 버전을 보존하고 사용자나 프로그램이 내용에 맞게 합치는 방법도 있다. 글의 두 문장을 합치는 정책과 수량을 더하는 정책은 같지 않다.

CRDT는 연산과 병합 규칙을 자료형에 맞게 설계해 필요한 전달 조건에서 수렴하도록 하는 자료형이다. 상태 기반과 연산 기반의 전제가 다르며, 연산 중복 전달을 그냥 두 번 증가시키는 방식은 안전하지 않다. 모든 임의 문서나 업무 제약이 자동으로 해결되는 것은 아니다.

증가 전용 카운터는 작성자별 기여를 보존한다

여기서는 고정된 두 작성자 A/B가 각각 자기 성분만 증가시키는 상태 기반 GCounter를 쓴다. 상태는 음이 아닌 정수쌍이며 읽기는 두 성분의 합이다. 병합은 성분별 최대값이다. 같은 작성자 신원을 서로 독립적으로 재사용하거나 성분을 줄이는 행동은 이 모형 밖이다.

max는 입력 순서를 바꿔도 같고, 묶는 순서를 바꿔도 같으며, 같은 상태를 다시 병합해도 같다. 각각 교환·결합·멱등 성질이다. 로컬 갱신은 상태를 줄이지 않고 필요한 상태가 결국 전파되면 이미 전달된 기여를 중복해서 더하지 않으며 수렴한다. 감소나 재고 하한 제약에는 별도 설계가 필요하다.

A와 R은 값의 개수가 아니라 고유 추가 태그의 집합이다. 제거는 항목 이름 p만 적는 것이 아니라 관측한 태그를 적는다. 이 표의 두 연산은 서로를 관측하지 않은 concurrent 연산이다.

중간 과정을 따라가는 예제

A/B의 초기 GCounter는 (0,0)이다. A는 3번, B는 2번 독립 증가한다. 상태 교환·중복 전달·추가 증가를 계산하라.

  1. 교환 전 A의 상태 (3,0)의 읽기는 3, B의 상태 (0,2)의 읽기는 2다.

  2. 성분별 최대 병합은 (3,2)이며 합은 5다. 단순 총값 최대 max(3,2) = 3은 증가 2개를 잃는다.

  3. B의 옛 상태 (0,2)를 한 번 더 병합해도 (3,2)로 값은 5다. 상태 합산 (3,2) + (0,2) = (3,4)는 중복을 잘못 센다.

  4. 병합 뒤 A가 한 번 더 증가하면 (4,2)로 값은 6이다. B가 이 상태를 받으면 (4,2)로 맞춘다.

  5. 옛 A의 상태 (3,0)를 다시 받아도 최대 병합으로 (4,2)를 유지한다.

독립 증가 5개를 보존하고 중복 전달에 5가 7로 부풀지 않는다. 추가 A 증가 뒤 최종 값은 6이다.

버전 숫자의 합이 크면 세션에 충분히 새로울까요?

자체 두 작성자 모형에서 frontier (a,b)는 A의 앞 a개 사건과 B의 앞 b개 사건을 모두 알고 있다는 뜻이다. 사건은 작성자별 고정 순서이며 좌표는 알려진 연속 접두 길이다. 세션 토큰 c는 세션이 이미 관측한 사건과 자신이 수행한 쓰기를 포함한다. 응답 복제본의 frontier v가 c를 좌표별로 지배해야 토큰에 든 사건을 빠뜨리지 않는 읽기를 허용한다. 새 응답을 읽으면 토큰을 좌표별 최댓값으로 갱신한다. 이 토큰은 지식 범위를 나타내며 충돌을 해소한 업무 값 자체가 아니다.

세션 토큰 c=(2,1)에서 X의 frontier는 (3,0), Y는 (2,1), Z는 (1,4)다. 좌표 합은 각각 3, 3, 5지만 X는 B의 첫 사건을 모르고 Z는 A의 둘째 사건을 모른다. Y만 토큰을 지배한다. 큰 총합만으로 세션에 필요한 사건 포함을 판정할 수 없다. Y를 읽은 뒤 W=(2,3)을 읽으면 토큰은 (2,3)이 된다. 그 뒤 Y=(2,1)로 돌아가는 읽기는 B의 두 사건을 빠뜨려 허용하지 않는다.

자기 쓰기를 토큰에 넣는 것은 read-your-writes를, 이미 본 사건을 유지하는 것은 monotonic reads를 위한 이 모형의 별도 검사다. 자신이 쓰지 않은 사건을 이미 읽은 경우에도 monotonic 조건이 필요하다. 새 프로세스나 세션에 토큰을 넘기지 않으면 이전 세션의 관측 보장을 자동으로 이어받는다고 주장할 수 없다. 여러 키 사이 인과 의존도 별도로 기록한다. 게시물 사건 A2를 본 뒤 댓글 사건 B1을 만들었다면 댓글을 표시하는 응답에 A2의 게시물 자료가 없다는 상황은 숫자가 더 크다는 말만으로 해결되지 않는다.

내 쓰기와 내 이전 읽기를 지킨다

자기쓰기읽기는 같은 과정 또는 정해진 세션의 쓰기 뒤 읽기가 그 쓰기 효과를 반영하도록 하는 보장이다. 다른 사용자의 읽기까지 즉시 바꾸는 조건이 아니다. 동시 변경이 있는 경우 항상 내 값만 영원히 보인다는 뜻으로 확대하지 않는다.

단조읽기는 내가 이미 관찰한 변경보다 이전 상태로 다음 읽기가 되돌아가지 않는 보장이다. 직접 쓰지 않았어도 적용된다. 여기서는 하나의 단일 작성자 객체에 증가하는 버전을 사용하므로 이전보다 작은 버전이 되돌아감이라는 단순 기준을 쓸 수 있다. 복잡한 동시 버전에서는 인과 관계를 비교한다.

세션 상태를 서버 선택과 함께 전달한다

클라이언트가 마지막 관찰 버전과 자기 쓰기 버전을 기억하고 요청에 필요한 최소 버전을 전달할 수 있다. 서버가 그 수준을 아직 모르면 기다리거나 적절한 곳으로 보내거나 실패를 알리는 정책이 필요하다. 옛 값을 그대로 성공 결과로 보여 주면 요청한 보장을 지키지 못한다.

같은 서버에 머무르는 방법도 그 서버가 상태를 보존하고 이력 조건을 지킨다는 전제가 있다. 장애로 다른 서버나 새 세션으로 옮길 때 보장이 어디까지 이어지는지 정해야 한다. 클라이언트 기억 없이 임의 서버로 이동하면 최종 수렴만으로 세션 보장을 복원할 수 없다.

의존 관계와 화면 상태를 맞춘다

인과 보장은 원인인 글을 관찰해 작성한 댓글처럼 의존하는 변경을 원인과 맞게 볼 수 있도록 다룬다. 두 키를 따로 복제하고 자기쓰기읽기만 제공하면 다른 사용자가 댓글을 먼저 보고 원글을 못 보는 상황을 자동으로 막지는 않는다. 여러 객체에 걸친 보장을 별도로 확인한다.

화면에서는 로컬 임시 반영, 서버 접수, 다른 복제본 전파, 충돌 해결 상태를 구별할 수 있다. 실제 프로토콜 증거가 없는데 모든 장치에 동기화 완료라고 표시하지 않는다. 중요한 전역 유일성이나 재고 예약에는 단순 최종 수렴 이상의 조건이 필요하다.

풀이와 답 확인

  2. 기존 관측 토큰 (2,3)의 B 좌표를 유지하지 못하므로 monotonic reads 조건에 어긋난다.

  2. 부족하면 충분한 복제본을 찾거나 자료 전달을 기다리거나 실패를 보고한다. 부족한 응답을 성공 읽기로 간주하지 않는다.

충돌 선택·관측 제거·세션 포함의 공동 감사

서로를 보지 않은 A와 B의 register 쓰기는 현실 시각 10의 red와 시각 12의 blue다. 불변 고유 키는 각각 (110,A), (12,B)이며 큰 키를 보존한다. 두 전달 순서의 최종 값과 현실의 나중 쓰기를 비교하라. 별도 observed-remove set은 처음 A={p1}, R=∅다. X는 새 p2를 추가하고 Y는 관측한 p1을 제거한다. 병합 상태와 보이는 항목을 구하고, 병합 뒤 모든 살아 있는 태그를 제거한 다음 옛 p1 추가 상태를 다시 병합한 결과를 구하라. 별도 세션의 토큰 c=(2,1)에 복제본 X=(3,0), Y=(2,1), Z=(1,4)가 응답한다. 허용 복제본을 고른 뒤 W=(2,3)을 읽으면 새 토큰과 Y 재읽기의 허용 여부를 적어라. 실제 분산 저장소는 실행하지 않는다.

힌트 1

register는 불변 고유 키의 최대 선택이다. 태그 집합의 추가와 제거는 각각 합집합으로 병합한다.

힌트 2

frontier는 같은 작성자의 사건 포함을 좌표별로 비교한다. 총합과 현실 시각을 별도 정보로 둔다.

풀이와 답 확인

  1. 두 전달 순서 모두 키 (110,A)의 red로 수렴한다. 현실에서 나중 쓰기는 시각 12의 blue이므로 수렴이 그 의도의 보존을 뜻하지 않는다.

  2. 첫 태그 병합은 추가 A={p1,p2}, 제거 R={p1}이다. 살아 있는 태그 p2로 p가 보인다.

  3. 후속 제거 뒤 R={p1,p2}가 된다. 옛 p1 추가를 합집합으로 받아도 제거 태그가 남아 p는 보이지 않는다.

  4. 세션에서는 Y만 (2,1)을 지배한다. W를 읽은 뒤 토큰은 (2,3)이고 Y의 B 좌표 1이 부족하여 Y 재읽기를 거절한다.

register는 red로 수렴하지만 현실의 나중 쓰기는 blue다. 첫 집합 병합에서는 p2 때문에 p가 보이고 후속 제거 및 옛 추가 재전송 뒤에는 보이지 않는다. 세션의 첫 허용 응답은 Y뿐이며 W 관측 뒤 토큰은 (2,3)이고 옛 Y 응답은 거절한다.

해결한 뒤 점검할 것

  • 고유 키의 수렴과 현실 시간·의도 보존을 구별한다.

  • 추가 태그와 제거 태그를 모두 보존하여 concurrent 추가와 옛 재전송을 판정한다.

  • 벡터 총합 대신 각 좌표 포함과 관측 뒤 토큰 갱신을 검사한다.

  • 교육용 상태·토큰 계약과 실제 제품 구현·내구성·시간 상한·학생 실행을 구별한다.

보강 자료의 출처와 확인 범위
  • Werner Vogels: Eventually Consistent (2008)

    실제 본문 37–48행의 최종 일관성, causal consistency, read-your-writes, session consistency와 monotonic reads 정의 및 68–70행의 sticky session·클라이언트 버전 문맥을 읽었다. 2008년 설명이며 현재 AWS 전체 서비스의 계약을 일반화하지 않는다. 특정 수렴 시간 상한과 장애 후 내구성을 정의만으로 얻지 않았다.

  • Preguiça: Conflict-free Replicated Data Types

    실제 HTML 43–90행에서 동일 업데이트 후 수렴, add-wins/remove-wins set, timestamp와 작성자에 의한 전체 순서, multi-value/LWW register와 PN-counter를 읽었다. 94–126행에서 state-based join·inflation 및 operation-based 전달 가정과 객체 수준의 성질을 시스템 보장으로 확대할 수 없는 조건을 읽었다. 두 태그 합집합과 고정 작성자 PN-counter는 자체 명시 모형이며 논문 전체 읽기나 실행 검증을 주장하지 않는다.

  • Akka Distributed Data

    공식 실제 본문 592–753행 중 counter의 625–654행과 ORSet의 696–717행을 포함해 읽었다. 노드별 성분의 최대값과 총합, PN-counter의 두 G-counter, 고유 노드 정보, observed-remove set의 추가·제거와 delta 전달 조건을 확인했다. 자체 두 태그 집합 모형을 Akka의 실제 압축 상태·구현 또는 실행으로 주장하지 않는다.

  • Amazon Dynamo, SOSP 2007 §4.4

    실제 PDF 물리 6–7쪽의 §4.4 버전 관리 본문에 해당하는 추출 613–727행을 읽었다. 벡터 시계로 인과 관계를 비교하고 concurrent 판본에 semantic reconciliation이 필요하며 벡터 절단이 정확한 조상 판정에 영향을 줄 수 있음을 확인했다. 2007 Dynamo 논문을 현재 DynamoDB 전체 서비스 계약으로 쓰지 않았다.

  • Jepsen: Read Your Writes

    짧은 실제 전체 본문 0–17행을 읽고 5–11행에서 같은 process의 쓰기가 후속 읽기에 보이는 조건과 다른 process의 범위를 구별했다. 세션 이동의 자동 보장을 추가하지 않았다.

  • Jepsen: Monotonic Reads

    짧은 실제 전체 본문 0–18행을 읽고 5–12행에서 같은 process의 앞 읽기에 보인 자료가 후속 읽기에서도 보이는 포함 조건을 확인했다. 자체 frontier는 작성자별 연속 접두 지식의 두 좌표이며 숫자 합이나 업무 값 증가를 보장으로 바꾸지 않았다.

새 계산과 논증은 모두 손유도다. 현실 시각 10의 A 키 (110,A)와 시각 12의 B 키 (12,B)는 두 전달 순서에서 red로 수렴하며 현실의 나중 쓰기는 blue다. 동일 숫자 100의 현재 값 유지 규칙은 red와 blue로 갈릴 수 있고 작성자 전체 순서를 더하면 blue로 수렴한다. 태그 첫 병합은 추가 {p1,p2}, 제거 {p1}, 살아 있는 태그 {p2}다. 후속 제거 뒤 제거 집합은 {p1,p2}이고 옛 p1 전달로 부활하지 않는다. 두 집합을 모두 지운 별도 잘못된 정리에서는 옛 p1이 부활한다. PN-counter의 P=(4,2), N=(1,3) 값은 2이고 A의 감소 2 뒤 N=(3,3)의 값은 0이다. 토큰 (2,1)은 X=(3,0)과 Z=(1,4)에서는 충족되지 않고 Y=(2,1)에서만 충족된다. W=(2,3)을 관측한 뒤 새 토큰은 (2,3)이며 Y 재읽기는 거절한다. V=(4,3)을 이후 읽으면 토큰은 (4,3)으로 갱신된다. 자기 쓰기 없는 관측의 퇴행과 여러 키의 게시물·댓글 의존 조건을 별도로 손검토했다.
