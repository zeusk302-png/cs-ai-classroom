소단원 4.1

선형화가능성·순차·인과 일관성

같은 기록을 읽었는데 서로 다른 순서로 보아도 될까?

준비 개념과 학습 목표

준비 개념

  • 읽기와 쓰기

  • 한 사용자의 프로그램 순서

학습 목표

  • 실시간 순서와 프로그램 순서를 구별한다

  • 인과 관계와 동시 관계를 판별한다

객체마다 가능한 순서를 합치면 전체 순서도 가능할까?

초기 x=y=0인 두 register를 둔다. A는 Wx(1) 뒤 Ry()=0을 실행하고 B는 Wy(1) 뒤 Rx()=0을 실행한다. 다른 쓰기는 없다. 각 프로세스의 두 연산은 겹치지 않으며 실제 서버 실행 자료가 아닌 완결된 종이 기록이다. 객체 x만 보면 Rx(0),Wx(1) 순서가 가능하고 y만 보면 Ry(0),Wy(1) 순서가 가능하다.

전체 순차 일관성은 두 객체 연산과 각 프로세스 순서를 동시에 만족해야 한다. A의 순서, y의 초기값 읽기 조건, B의 순서, x의 초기값 읽기 조건을 잇으면 Wx<Ry<Wy<Rx<Wx라는 순환이다. 객체별 순차 일관성에서 시스템 전체의 순차 일관성이 자동으로 나오지 않는다. 이와 달리 선형화가능성은 객체별 성질이 합성되는 성질이다.

두 독립 쓰기에는 서로 인과 관계가 없다. A의 관찰 순서에는 Wx,Ry,Wy를, B에는 Wy,Rx,Wx를 놓을 수 있다. 서로 다른 관찰자의 합법 순서가 하나의 공통 순서여야 하는 것은 아니다. 인과 일관성 자체와 이후 복제본 수렴을 추가한 causal+를 구별한다.

한 순간에 일어난 것처럼

초기값 0인 register는 write(v)로 값을 바꾸고 read()로 값을 받는 객체다. 선형화가능성은 각 연산을 호출과 응답 사이의 한 순간에 일어난 것처럼 놓아 합법적인 순차 기록을 만들 수 있다는 조건이다. 응답이 끝난 뒤 시작된 다른 연산은 그 뒤에 놓여야 한다.

서로 겹치는 연산은 실제 시간만으로 한 순서가 강제되지 않는다. Write 1과 read가 겹치면 초기 0 또는 1을 반환하는 순서를 만들 수 있지만, write 1이 완료된 후 시작한 read가 0을 받으면 최신 완료 쓰기 이후라는 조건을 어긴다. 이 예에는 다른 쓰기가 없다.

프로그램 순서를 지키는 전체 순서

순차 일관성도 전체 연산을 합법적인 한 순서에 놓되 각 프로세스의 프로그램 순서를 지킨다. 서로 다른 프로세스의 응답/호출 사이 실시간 선후를 모두 지킬 필요는 없다. 따라서 같은 프로세스 안의 순서와 프로세스 사이 시간을 따로 적어야 한다.

서로 다른 사용자 A의 write 1 뒤에 실제로 B가 read 0을 했더라도 B의 read를 전체 순서의 앞에 놓을 수 있다면 순차 일관성 예가 될 수 있다. A가 직접 write 1 뒤 read 0을 했다면 프로그램 순서 때문에 그 재배치는 불가능하다.

원인과 결과를 함께 보기

인과 순서는 한 프로세스의 순서, 어떤 쓰기 값을 읽어 얻은 의존 관계, 그 관계의 이어짐으로 만들어진다. 인과 일관성은 원인 쓰기보다 결과 쓰기를 먼저 보게 하는 식의 역전을 허용하지 않는다. 인과 관계가 없는 동시 쓰기는 관찰자마다 다른 순서로 볼 수 있다.

초기 x=y=0이고 A가 x=1을 쓰고 그 뒤 y=1을 썼다면 x쓰기에서 y쓰기로 의존이 생긴다. B가 y=1을 읽고 이어 x=0을 읽는 관찰은 이 단순 register 모형에서 인과 관계에 맞지 않는다. 이후 x를 덮는 다른 쓰기는 없다고 명시해야 반례가 분명하다.

독립 쓰기의 순서 차이 허용

각 부등호의 근거를 프로그램 순서 또는 초기값 읽기로 이름 붙인다. 객체별 검사에서 사라지는 다른 객체의 프로그램 순서를 복원한다.

중간 과정을 따라가는 예제

x 초기 0. A의 write 1은 시간 1 호출/2 응답. B의 read 0은3 호출/4 응답. 각 프로세스의 연산은 이 한 개뿐이다. 선형화가능성과 순차 일관성을 판정하라.

  1. 시간 2<3이므로 선형화에서는 A의 write를 B의 read 앞에 놓아야 한다.

  2. 그러면 마지막 쓰기는 1이며 read 0은 합법적인 register 결과가 아니다. 선형화가능성은 실패다.

  3. 순차 일관성에서는 두 프로세스 사이 실시간 선후를 반드시 유지하지 않는다.

  4. B의 read 0→A의 write 1 순서를 택하면 초기값을 읽고 바꾸는 합법적 기록이며 각 프로세스 내부 순서도 지킨다.

선형화가능하지 않지만 순차 일관적이다. 이 판정은 이 완결된 기록과 초기값·연산 조건에 대한 것이다.

조건을 바꾸어 비교하기

두 개의 통과 기록이 전체 통과가 아닌 경우

앞의 두 객체 기록이 순차 일관적인지 판정하라.

  1. A는 Wx<Ry를 요구한다. Ry=0이므로 다른 쓰기 없는 y에서 Ry<Wy다.

  2. B는 Wy<Rx를 요구한다. Rx=0이므로 Rx<Wx다.

  3. 네 관계를 잇으면 자기 자신보다 앞서야 하는 순환이 생긴다.

객체별 순차 검사는 통과하지만 전체 순차 일관성은 실패한다.

비교할 점

단일 객체 성질과 전체 합성을 비교한다.

긴 쓰기의 선형화 위치

별도 초기 x=0이다. 서로 다른 주체의 w1=write(1)는 시간 [0,10], w2=write(2)는 [3,4], r2=read()→2는 [5,6], r1=read()→1은 [11,12]다. 추가 연산은 없다.

  1. w2의 선형화 시각을 3.5, r2를 5.5, w1을 9, r1을 11.5로 잡는다.

  2. 모든 시각은 각 호출/응답 구간 안이며 순서는 w2,r2,w1,r1이다.

  3. w1은 늦게 시작한 w2와 겹치므로 호출 시각만으로 먼저 놓을 필요가 없다.

이 기록은 선형화가능하다. 쓰기 호출 순서와 선택된 선형화 순서는 다를 수 있다.

비교할 점

완료된 쓰기만 단순 호출 정렬하는 방법의 한계를 확인한다.

종이와 본문으로 직접 해보기

초기 x=y=0. A가 write(x,1) 뒤 write(y,1); B가 read(y)=1 뒤 read(x)=0이다. 다른 쓰기는 없다. 인과 의존 화살표를 그리고 모순을 설명하라.

힌트 보기

A의 순서와 y 읽기의 의존, B의 순서를 이어라.

풀이 보기

Wx1→Wy1→Ry1→Rx0이다. B의 합법적인 인과 관찰 순서에서 Wx1은 Rx0 앞에 와야 하며 다른 x 쓰기 없으므로 Rx0와 모순이다.

오해와 반례

순차 일관성은 모든 사용자의 실제 시간을 보존한다.

앞 예의 read 0를 write 1 앞에 놓는 순차 기록이 반례다. 선형화가능성이 실시간 조건을 추가한다.

자기점검

겹치는 write 1/read가 0을 반환하면 반드시 선형화 위반인가?

답과 이유 보기

아니다.

read를 write보다 먼저 선형화할 수 있다.

같은 프로세스write 1 뒤read 0는 순차 일관적인가?

답과 이유 보기

다른 쓰기가 없으면 아니다.

프로그램 순서와 register 의미가 충돌한다.

인과 관계 없는 동시 쓰기는 모두 같은 순서로 보여야 하는가?

답과 이유 보기

인과 일관성만으로는 아니다.

그 조건은 의존 순서를 보존하며 모든 동시 연산의 공통 전체 순서를 강제하지 않는다.

스스로 풀어보기

먼저 답과 이유를 적고, 필요한 만큼 힌트를 한 단계씩 열어 보세요.

연습 1 · 값과 상태 예측

긴 쓰기 예제에서 w1의 응답 시각만 2로 바꾸고 나머지 기록을 유지하면 최종 r1=1은 가능한가?

힌트 1

w1 응답 2는 w2 호출 3보다 이르다.

힌트 2

r1보다 마지막으로 끝난 다른 쓰기를 확인한다.

풀이와 답 확인

  1. w1<w2<r2<r1이라는 실시간 순서가 강제된다.

  2. r1 앞의 마지막 쓰기는 2인데 1을 반환했다.

이 수정 기록은 선형화가능하지 않다.

흔한 오답에서 다시 생각하기

더 먼저 응답했으므로 1이 더 최신이다.

최신성은 숫자 크기가 아니라 강제된 연산 순서와 register 의미로 정한다.

연습 2 · 오류 찾아 고치기

객체별 순차 검사가 성공했으므로 앞의 x/y 전체도 순차 일관적이라고 했다. 빠진 관계를 표시하라.

힌트 1

같은 주체가 두 객체에 걸쳐 수행한 순서를 넣는다.

힌트 2

초기 0 읽기는 유일한 쓰기보다 앞에 둔다.

풀이와 답 확인

  1. 객체별 순서에 A의 Wx<Ry와 B의 Wy<Rx를 더한다.

  2. 네 관계가 순환하므로 공통 전체 순서는 존재하지 않는다.

각 객체의 대체 순서가 서로 양립하는지 확인해야 한다.

흔한 오답에서 다시 생각하기

객체별 순차 일관성이 선형화가능성과 같은 합성 법칙을 가진다.

두 성질의 합성 보장은 다르며 이 기록이 반례다.

연습 3 · 직접 만들어 보기

앞의 x/y 기록에서 B의 Rx 반환값만 1로 바꿔 합법적인 전체 순차 순서를 구성하라.

힌트 1

Ry=0은 Wy보다 앞이다.

힌트 2

Rx=1은 Wx보다 뒤다.

풀이와 답 확인

  1. Wx,Ry,Wy,Rx 순서를 택한다.

  2. A와 B의 각 프로그램 순서 및 두 읽기의 반환값을 모두 만족한다.

반환값 한 개의 변경으로 순환이 풀리고 전체 순차 순서가 존재한다. 실제 시간 기록이 없으므로 선형화 여부까지 단정하지 않는다.

흔한 오답에서 다시 생각하기

합법 순차 순서를 찾으면 모든 실제 시간 구간도 자동으로 만족한다.

구간 사이 실시간 조건은 별도 자료와 검사다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

A가 Wx(1) 뒤 Wy(1)을 쓰고 B가 Ry=1 뒤 Rx=0을 읽는다. 다른 쓰기가 없을 때 인과 일관성의 모순을 보이라.

힌트 1

A의 쓰기 순서를 잇는다.

힌트 2

Ry가 읽은 쓰기를 통해 B의 다음 읽기로 의존을 이어라.

풀이와 답 확인

  1. Wx→Wy→Ry→Rx의 인과 사슬이다.

  2. B 관찰의 합법 순서에서 Wx는 Rx 앞이어야 하지만 Rx=0은 Wx 앞을 요구한다.

이 기록은 인과 일관성도 만족하지 않는다.

흔한 오답에서 다시 생각하기

언젠가 x=1을 보게 하면 현재 인과 역전도 고쳐진다.

이후 수렴과 지금의 의존 순서 보존은 다른 조건이다.

겹친 쓰기의 호출 순서가 최종 순서를 정하는가?

설명 기준 확인

아니다. 호출/응답 사이 위치와 모든 읽기 결과를 함께 검사한다.

한 단계 더

A:Wx1,Ry0와 B:Wy1,Rx0의 기록에서 순차 전체 순서를 만들려고 해 보자. 각 프로세스 순서와 0을 읽기 위한 조건이 Wx1<Ry0<Wy1<Rx0<Wx1이라는 순환을 만든다. 인과 관찰에서는 서로의 독립 쓰기를 아직 못 볼 수 있으므로 더 약한 조건과 차이가 드러난다.

primary-backup·quorum

복사본이 여러 개면 어느 답을 믿을까?

준비 개념과 학습 목표

준비 개념

  • 집합의 교집합

  • 버전 번호

학습 목표

  • primary의 순서 결정과 교체 조건을 설명한다

  • 정족수 교집합의 보장 범위를 구별한다

확인은 정확히 같은 값을 저장했다는 뜻이어야 할까?

A,B,C,D,E의 고정 membership에서 다수는 3개다. timestamp는 (번호,작성자 ID)로 비교하고 같은 번호에서는 A<B다. 값 7의 태그 (6,A)와 값 9의 태그 (6,B)는 다른 쓰기다. 서버는 받은 태그가 현재보다 클 때만 갱신하며, 작은 태그를 받더라도 처리 확인을 돌려준다.

한 읽기의 질의 응답이 A:(6,A,7), C:(6,B,9), D:(5,A,4)이면 선택은 (6,B,9)다. 읽기는 이를 다수에 write-back하고 확인 뒤 반환한다. 확인 서버가 이미 (7,A,11)을 가지고 있으면 작은 태그로 되돌리지 않는다. 확인이 보장해야 하는 것은 선택 태그 이상의 보존이며 모든 복제본 값이 정확히 9로 같다는 뜻이 아니다.

집합 크기 식은 같은 membership에 적용한다. 옛 구성 {A,B,C,D,E}의 쓰기 집합 {A,B,C}와 새 구성 {C,D,E,F,G}의 읽기 집합 {E,F,G}는 각각 3개지만 서로 안 겹친다. 구성 변경에 버전 번호만 붙여도 교차 보장이 생기는 것은 아니다. 이전 완료 기록의 이전·새 구성 승인·옛 primary 차단을 별도 규칙으로 확보해야 한다.

    단조 태그와 읽기 write-back의 결합 조건을 사용한다.

순서를 정하는 primary

Primary-backup은 주 복제본이 요청의 순서를 정하고 backup들이 같은 순서를 반영하는 방식이다. 응답 전에 어느 복제본의 확인을 기다리는지는 프로토콜마다 다르다. 전부 기다리는 단순 방식과 다수 로그 확인을 사용하는 viewstamped replication을 같은 규칙이라고 말하지 않는다.

Primary가 실패하면 새로운 view에서 역할을 바꿀 수 있다. 이미 실행한 요청이 새 view에서도 남고 같은 순서를 유지해야 한다. 느린 old primary를 단순히 없다고 가정한 채 다른 primary를 추가하면 두 순서가 갈라질 수 있으므로 view에 맞지 않는 요청을 처리하지 않게 하는 규칙이 필요하다.

교차하는 정족수

복제본 N개에서 쓰기 완료에 필요한 집합 크기를 W, 읽기 응답 집합 크기를 R이라 하자. R+W>N이면 임의의 두 집합은 겹친다. 안 겹친다면 합집합 크기가 R+W로 N보다 커져 모순이라는 비둘기집 직관이다.

같은 membership의 집합 크기에 대한 사실이지, 그 자체가 완전한 일관성 프로토콜은 아니다. 버전의 순서, 동시 쓰기, 확인 전후 시점, 오래된 복제본 복구, 읽기 결과 선택 규칙을 따로 정한다. 2W>N이면 두 쓰기 집합도 겹치지만 그것만으로 모든 읽기 기록이 선형화되는 것은 아니다.

원자 register의 두 단계

Cornell의 ABD 계열 register 설명에서는 다수에게 버전과 값을 질의하고 최대 논리 timestamp를 택한다. 쓰기는 관찰 최대보다 큰 고유 timestamp를 만들어 다수에 저장하고 확인을 기다린다. 서버는 더 오래된 버전으로 되돌리지 않는다.

읽기도 최대 버전과 값을 다수에 다시 쓰고 확인을 기다린 뒤 반환한다. 이 write-back은 한 읽기가 본 진행 중 쓰기 값을 후속 읽기가 놓치는 역전을 막는 핵심이다. 숫자 교집합과 이 상태/메시지 규칙을 합쳐 보아야 보장 근거를 설명할 수 있다.

중간 과정을 따라가는 예제

복제본 A,B,C,D,E 다섯 개, R=W=3이다. 완료 쓰기 버전 7이 {A,B,C}에 저장되었고 읽기 응답은 {C,D,E}다. 이후 다른 쓰기 없고 서버는 버전을 되돌리지 않는다. C는 7, D/E는 6이다.

  1. R+W=6>5이므로 두 정족수는 반드시 겹친다.

  2. 실제 교집합은 {C}다. 일반 최소 교집합 크기는 R+W−N=1이다.

  3. 최대 버전을 고르는 규칙으로 응답 7,6,6 중 7을 선택한다.

  4. 원자 register 읽기 규칙을 끝내려면 버전 7과 값을 다수에 write-back하고 확인을 받은 뒤 반환한다. 조회만 마친 상태와 구별한다.

최대 버전 7을 선택하고 다수 write-back까지 완료한다. 단일 오래된 복제본 읽기와 다르다.

  1. E는 (7,A)>(6,B)이므로 기존 11을 유지한다.

  2. 확인된 B,C,E는 모두 선택 태그 (6,B) 이상을 보존한다.

소단원 4.3

읽기·쓰기 경로와 장애

응답이 사라졌다면 쓰기도 없었던 것일까?

준비 개념과 학습 목표

준비 개념

  • 요청과 응답

  • timeout은 관찰한 대기 시간

학습 목표

  • 완료와 불확실 상태를 나눈다

  • 장애 중 안전성과 진행성을 따로 설명한다

재시도 결과가 현재 값과 달라도 올바를 수 있을까?

자체 counter 서비스의 초기 값은 20이다. 요청 u는 +3, 요청 v는 +2다. 유효한 요청 ID에는 고정된 payload가 대응한다. counter 변경과 ID별 원래 결과 저장이 하나의 원자·내구성 경계 안에서 완료된다는 별도 모형을 먼저 둔다. 외부 결제나 분산 트랜잭션의 구현 증거는 아니다.

u 완료 뒤 상태 23과 결과 장부 u→23을 보존했으나 응답이 유실된다. 이후 v 완료로 상태는 25이고 장부 v→25가 추가된다. 같은 u를 재전송하면 counter를 다시 바꾸지 않고 u의 원래 결과 23을 반환한다. 현재 상태 25를 과거 u의 결과로 덮어 쓰는 규칙과 구별한다.

이 모형의 보장은 두 저장을 같은 복구 경계로 보존한다는 가정에 달린다. counter만 23으로 남고 u 장부가 빠진 복구라면 재시도 u가 다시 +3을 적용하여 26이 된다. 동일 ID로 다른 payload +8을 보내는 요청은 충돌로 거절해야 한다. ID 문자열 하나가 상태 저장과 복구의 계약을 대신하지 않는다.

  • 단조 저장과 다수 확인

응답까지의 길

쓰기 경로에는 요청 전송, 복제 저장, 확인 수집, 클라이언트 응답이 있다. 저장 이후 응답 메시지만 유실되면 서버 쪽에는 값이 남지만 클라이언트는 완료 여부를 모른다. Timeout만으로 저장 실패를 결론 내릴 수 없다.

재시도는 같은 요청 ID와 중복 처리 규칙을 함께 설계한다. 특히 증가나 결제 같은 연산을 새 요청으로 반복하면 두 번 처리될 수 있다. 이 단원의 ID 표는 종이 설계 예이며 실제 결제 서비스나 완전한 exactly-once 보장 구현이 아니다.

읽기도 값을 퍼뜨리는 경로

다수 질의에서 읽은 최대값을 반환하기 전에 write-back하는 단계는 후속 읽기와의 순서 보존에 기여한다. 진행 중 쓰기는 전부 완료되지 않아도 한 읽기의 결과로 관찰될 수 있다. 후속 읽기가 더 오래된 값을 반환하지 않게 하려면 그 관찰을 다수에 보존한다.

서버는 버전을 단조롭게 유지하고 요청 ID·단계별 응답을 구별해야 한다. 다른 단계의 응답을 같은 다수 확인으로 세거나 한 서버의 중복 응답을 여러 복제본으로 세면 숫자가 맞아 보여도 근거가 무너진다.

네트워크가 갈라질 때

다섯 복제본이3/2로 갈라지고 다수 3이 필요하면3쪽은 필요한 응답을 얻을 수 있지만2쪽은 완료할 수 없다. 여기서 진행은 올바른 참여자와 필요한 메시지가 도착한다는 전제를 둔다. 장애 때 멈추는 선택은 잘못된 결과를 만들지 않는 안전성 요구와 구별된다.

Timeout은 상대가 죽었는지 늦었는지 알려 주는 완벽한 증거가 아니다. Primary 교체는 view 전환과 과거 상태 보존 조건을 만족해야 한다. 이 설명은 실패·복구 원리를 배우는 것이며 실제 네트워크 장애 주입 결과를 주장하지 않는다.

중간 과정을 따라가는 예제

A,B,C 세 복제본의 초기 버전 0/값 0. 진행 중 쓰기 버전 1/값 9가 A에만 저장됐다. 첫 읽기 r1은 A,B에서1/0을 받고 최대 1을 B,C에 write-back하여 두 확인 후 끝난다. 이어 r2가 B,C를 질의한다.

  1. r1의 첫 단계 최대는 버전 1/값 9다. 진행 중 쓰기의 값을 관찰할 수 있다.

  2. B와C가 write-back을 받아 버전 1/값 9로 올라가고 각각 확인한다.

  3. r1이 다수 확인 후 완료하므로 이어 시작한 r2의 질의 B,C는 모두 버전 1이다.

  4. r2는 9를 선택한다. 단조 버전과 다수 단계가 유지된다는 가정에서 옛 0으로 돌아가지 않는다.

r2는 9를 반환한다. r1이 새 값을 다수에 보존한 뒤 종료한 것이 차이를 만든다.

조건을 바꾸어 비교하기

오래된 결과를 반환하는 정상 재시도

위 모형에서 u 응답만 유실된 뒤 v는 완료했다. 다시 온 u의 처리와 현재 counter를 구하라.

  1. 내구성 장부에서 같은 ID·같은 payload의 결과 23을 찾는다.

  2. u를 다시 적용하지 않으므로 현재 counter는 25다.

  3. 재시도 응답은 원래 u의 결과 23이다.

현재 값 25와 재시도 반환 23은 서로 다른 대상이며 모순이 아니다.

비교할 점

조회 결과와 요청별 원래 결과를 구별한다.

중간 저장 복구가 보존 경계를 깨는 경우

별도 구현은 counter를 23으로 먼저 저장하고 장부 저장 전 중단된다. 복구 뒤 u를 처음 보는 ID처럼 처리한다.

  1. 복구 상태에는 counter 23과 빈 장부가 있다.

  2. u의 +3을 다시 적용해 counter가 26이 된다.

  3. 요청 ID가 같아도 이전 결과를 찾을 수 없으므로 첫 모형의 보존 전제가 성립하지 않는다.

ID 중복 검사는 효과와 결과 기록을 함께 복구할 때의 범위를 갖는다.

비교할 점

종이 원자 경계와 두 번의 독립 저장을 같은 구현으로 취급하지 않는다.

종이와 본문으로 직접 해보기

같은 초기 상태에서 r1이 write-back 없이 9를 반환한다면 r2가 B,C에서 받을 값은? 또한 다섯 복제본의3/2분할에서 다수 3을 얻을 수 있는 쪽을 표시하라.

힌트 보기

풀이 보기

B,C는 버전 0/값 0이어서 r2는 0을 반환할 수 있다. 서로 다른 클라이언트라도 r1 종료 뒤 r2 시작이라는 실시간 순서에서 새 값→옛 값 역전이다. 3/2 분할의 3쪽만 다수 3을 모을 수 있으며 2쪽은 기다려야 한다.

오해와 반례

Timeout이 났으면 같은 증가 요청을 새 ID로 반복해도 안전하다.

증가가 저장된 뒤 응답만 사라졌다면 새 ID의 재시도로 두 번 증가할 수 있다. 같은 ID의 중복 처리도 상태 보존·복구 조건을 따로 검증해야 하므로 ID 한 개만으로 만능 보장을 주장하지 않는다.

다른 문제에 적용하기

전체 순서와 보존 경계의 종합 감사

초기 x=y=0에서 A:Wx(1),Ry=0과 B:Wy(1),Rx=0의 순차 일관성을 판정한다. 별도 고정 다섯 서버에서 읽기가 태그 (8,A),값 4를 다수 ABC에 write-back 확인한 뒤 끝났다. 후속 질의는 CDE이고 D는 태그 (9,B),값 −2다. 서버는 태그를 낮추지 않는다. 후속 선택값의 숫자와 태그 하한을 구별한다. 별도 counter는 처음 30이고 요청 p의 +4 후 응답 유실,다음 q의 +1 완료다. 효과와 원래 결과 장부는 함께 내구성 있게 보존된다. 재시도 p의 현재 상태·반환값과 p 장부만 유실된 별도 복구에서 34에 재시도하는 결과를 구하라.

힌트 1

두 프로그램 순서와 초기값 읽기 조건을 잇는다. C의 태그 하한과 질의 최댓값을 따로 본다.

힌트 2

재시도는 현재 조회가 아니라 원래 결과 반환 계약이다. 장부 유실 사례는 다른 복구 전제다.

풀이와 답 확인

  1. 전체 기록은 Wx<Ry<Wy<Rx<Wx라는 순환이므로 순차 일관성이 없다. 객체별 검사가 가능하다고 전체 검사도 가능한 것은 아니다.

  2. C의 응답 태그는 (8,A) 이상이고 D의 응답 태그는 (9,B)다. 따라서 세 응답의 최댓값은 적어도 (9,B)다. C와 E가 모두 (9,B)보다 높은 태그를 갖지 않을 때 선택은 (9,B),값 −2다. 두 서버의 정확한 후속 태그는 미정이므로 일반적으로 정확한 선택값까지 정해지지는 않는다.

  3. p의 원래 결과는 34이고 q 후 현재 counter는 35다. 장부가 보존된 p 재시도는 34를 반환하고 현재 35를 바꾸지 않는다.

  4. 별도 복구가 counter 34만 남기고 p 기록을 잃었다면 새 적용처럼 +4를 더하여 38이 될 수 있다.

전체 순차 순서는 존재하지 않는다. 후속 최대 태그는 적어도 (9,B)이고 숫자 값의 하한은 주어지지 않는다. C와 E가 모두 더 높은 태그를 갖지 않을 때 선택값은 −2다. 보존된 p의 재시도는 현재 counter 35를 유지하면서 원래 결과 34를 반환한다. p 기록만 잃은 별도 34 복구에서는 재적용으로 38이 될 수 있다.

해결한 뒤 점검할 것

  • 객체별 순서와 전체 순환을 구별한다.

  • 교집합 서버의 태그 하한과 질의 최대 및 미지의 C/E 후속 상태를 구별한다.

  • 태그의 단조성과 값의 수치 대소를 혼동하지 않는다.

  • 현재 상태·원래 반환값·복구 보존 경계와 실제 서비스 미수행을 구별한다.
