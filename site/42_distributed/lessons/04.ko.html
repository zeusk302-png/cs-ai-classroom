소단원 4.1

선형화가능성·순차·인과 일관성

같은 기록을 읽었는데 서로 다른 순서로 보아도 될까?

준비 개념과 학습 목표

준비 개념

  • 읽기와 쓰기

  • 한 사용자의 프로그램 순서

학습 목표

  • 실시간 순서와 프로그램 순서를 구별한다

  • 인과 관계와 동시 관계를 판별한다

한 순간에 일어난 것처럼

초기값 0인 register는 write(v)로 값을 바꾸고 read()로 값을 받는 객체다. 선형화가능성은 각 연산을 호출과 응답 사이의 한 순간에 일어난 것처럼 놓아 합법적인 순차 기록을 만들 수 있다는 조건이다. 응답이 끝난 뒤 시작된 다른 연산은 그 뒤에 놓여야 한다.

서로 겹치는 연산은 실제 시간만으로 한 순서가 강제되지 않는다. Write 1과 read가 겹치면 초기 0 또는 1을 반환하는 순서를 만들 수 있지만, write 1이 완료된 후 시작한 read가 0을 받으면 최신 완료 쓰기 이후라는 조건을 어긴다. 이 예에는 다른 쓰기가 없다.

프로그램 순서를 지키는 전체 순서

순차 일관성도 전체 연산을 합법적인 한 순서에 놓되 각 프로세스의 프로그램 순서를 지킨다. 서로 다른 프로세스의 응답/호출 사이 실시간 선후를 모두 지킬 필요는 없다. 따라서 같은 프로세스 안의 순서와 프로세스 사이 시간을 따로 적어야 한다.

서로 다른 사용자 A의 write 1 뒤에 실제로 B가 read 0을 했더라도 B의 read를 전체 순서의 앞에 놓을 수 있다면 순차 일관성 예가 될 수 있다. A가 직접 write 1 뒤 read 0을 했다면 프로그램 순서 때문에 그 재배치는 불가능하다.

원인과 결과를 함께 보기

인과 순서는 한 프로세스의 순서, 어떤 쓰기 값을 읽어 얻은 의존 관계, 그 관계의 이어짐으로 만들어진다. 인과 일관성은 원인 쓰기보다 결과 쓰기를 먼저 보게 하는 식의 역전을 허용하지 않는다. 인과 관계가 없는 동시 쓰기는 관찰자마다 다른 순서로 볼 수 있다.

초기 x=y=0이고 A가 x=1을 쓰고 그 뒤 y=1을 썼다면 x쓰기에서 y쓰기로 의존이 생긴다. B가 y=1을 읽고 이어 x=0을 읽는 관찰은 이 단순 register 모형에서 인과 관계에 맞지 않는다. 이후 x를 덮는 다른 쓰기는 없다고 명시해야 반례가 분명하다.

중간 과정을 따라가는 예제

x 초기 0. A의 write 1은 시간 1 호출/2 응답. B의 read 0은3 호출/4 응답. 각 프로세스의 연산은 이 한 개뿐이다. 선형화가능성과 순차 일관성을 판정하라.

  1. 시간 2<3이므로 선형화에서는 A의 write를 B의 read 앞에 놓아야 한다.

  2. 그러면 마지막 쓰기는 1이며 read 0은 합법적인 register 결과가 아니다. 선형화가능성은 실패다.

  3. 순차 일관성에서는 두 프로세스 사이 실시간 선후를 반드시 유지하지 않는다.

  4. B의 read 0→A의 write 1 순서를 택하면 초기값을 읽고 바꾸는 합법적 기록이며 각 프로세스 내부 순서도 지킨다.

선형화가능하지 않지만 순차 일관적이다. 이 판정은 이 완결된 기록과 초기값·연산 조건에 대한 것이다.

종이와 본문으로 직접 해보기

초기 x=y=0. A가 write(x,1) 뒤 write(y,1); B가 read(y)=1 뒤 read(x)=0이다. 다른 쓰기는 없다. 인과 의존 화살표를 그리고 모순을 설명하라.

힌트 보기

A의 순서와 y 읽기의 의존, B의 순서를 이어라.

풀이 보기

Wx1→Wy1→Ry1→Rx0이다. B의 합법적인 인과 관찰 순서에서 Wx1은 Rx0 앞에 와야 하며 다른 x 쓰기 없으므로 Rx0와 모순이다.

오해와 반례

순차 일관성은 모든 사용자의 실제 시간을 보존한다.

앞 예의 read 0를 write 1 앞에 놓는 순차 기록이 반례다. 선형화가능성이 실시간 조건을 추가한다.

자기점검

겹치는 write 1/read가 0을 반환하면 반드시 선형화 위반인가?

답과 이유 보기

아니다.

read를 write보다 먼저 선형화할 수 있다.

같은 프로세스write 1 뒤read 0는 순차 일관적인가?

답과 이유 보기

다른 쓰기가 없으면 아니다.

프로그램 순서와 register 의미가 충돌한다.

인과 관계 없는 동시 쓰기는 모두 같은 순서로 보여야 하는가?

답과 이유 보기

인과 일관성만으로는 아니다.

그 조건은 의존 순서를 보존하며 모든 동시 연산의 공통 전체 순서를 강제하지 않는다.

한 단계 더

A:Wx1,Ry0와 B:Wy1,Rx0의 기록에서 순차 전체 순서를 만들려고 해 보자. 각 프로세스 순서와 0을 읽기 위한 조건이 Wx1<Ry0<Wy1<Rx0<Wx1이라는 순환을 만든다. 인과 관찰에서는 서로의 독립 쓰기를 아직 못 볼 수 있으므로 더 약한 조건과 차이가 드러난다.

소단원 4.2

primary-backup·quorum

복사본이 여러 개면 어느 답을 믿을까?

준비 개념과 학습 목표

준비 개념

  • 집합의 교집합

  • 버전 번호

학습 목표

  • primary의 순서 결정과 교체 조건을 설명한다

  • 정족수 교집합의 보장 범위를 구별한다

순서를 정하는 primary

Primary-backup은 주 복제본이 요청의 순서를 정하고 backup들이 같은 순서를 반영하는 방식이다. 응답 전에 어느 복제본의 확인을 기다리는지는 프로토콜마다 다르다. 전부 기다리는 단순 방식과 다수 로그 확인을 사용하는 viewstamped replication을 같은 규칙이라고 말하지 않는다.

Primary가 실패하면 새로운 view에서 역할을 바꿀 수 있다. 이미 실행한 요청이 새 view에서도 남고 같은 순서를 유지해야 한다. 느린 old primary를 단순히 없다고 가정한 채 다른 primary를 추가하면 두 순서가 갈라질 수 있으므로 view에 맞지 않는 요청을 처리하지 않게 하는 규칙이 필요하다.

교차하는 정족수

복제본 N개에서 쓰기 완료에 필요한 집합 크기를 W, 읽기 응답 집합 크기를 R이라 하자. R+W>N이면 임의의 두 집합은 겹친다. 안 겹친다면 합집합 크기가 R+W로 N보다 커져 모순이라는 비둘기집 직관이다.

같은 membership의 집합 크기에 대한 사실이지, 그 자체가 완전한 일관성 프로토콜은 아니다. 버전의 순서, 동시 쓰기, 확인 전후 시점, 오래된 복제본 복구, 읽기 결과 선택 규칙을 따로 정한다. 2W>N이면 두 쓰기 집합도 겹치지만 그것만으로 모든 읽기 기록이 선형화되는 것은 아니다.

원자 register의 두 단계

Cornell의 ABD 계열 register 설명에서는 다수에게 버전과 값을 질의하고 최대 논리 timestamp를 택한다. 쓰기는 관찰 최대보다 큰 고유 timestamp를 만들어 다수에 저장하고 확인을 기다린다. 서버는 더 오래된 버전으로 되돌리지 않는다.

읽기도 최대 버전과 값을 다수에 다시 쓰고 확인을 기다린 뒤 반환한다. 이 write-back은 한 읽기가 본 진행 중 쓰기 값을 후속 읽기가 놓치는 역전을 막는 핵심이다. 숫자 교집합과 이 상태/메시지 규칙을 합쳐 보아야 보장 근거를 설명할 수 있다.

중간 과정을 따라가는 예제

복제본 A,B,C,D,E 다섯 개, R=W=3이다. 완료 쓰기 버전 7이 {A,B,C}에 저장되었고 읽기 응답은 {C,D,E}다. 이후 다른 쓰기 없고 서버는 버전을 되돌리지 않는다. C는 7, D/E는 6이다.

  1. R+W=6>5이므로 두 정족수는 반드시 겹친다.

  2. 실제 교집합은 {C}다. 일반 최소 교집합 크기는 R+W−N=1이다.

  3. 최대 버전을 고르는 규칙으로 응답 7,6,6 중 7을 선택한다.

  4. 원자 register 읽기 규칙을 끝내려면 버전 7과 값을 다수에 write-back하고 확인을 받은 뒤 반환한다. 조회만 마친 상태와 구별한다.

최대 버전 7을 선택하고 다수 write-back까지 완료한다. 단일 오래된 복제본 읽기와 다르다.

종이와 본문으로 직접 해보기

N=5, R=2, W=3에서 서로 안 겹치는 읽기/쓰기 집합을 골라라. 그 뒤 N=5, W=3의 두 쓰기 집합이 반드시 겹치는 이유를 말하라.

힌트 보기

2+3은5와 같고3+3은5보다 크다.

풀이 보기

쓰기 {A,B,C},읽기 {D,E}는 안 겹친다. 이 읽기는 완료 쓰기를 놓칠 수 있다. 크기3인 쓰기 두 집합은 합이6이어서 적어도 하나 겹친다. 그러나 동시 버전 처리 규칙은 여전히 필요하다.

오해와 반례

R+W>N이면 어떤 구현도 선형화가능하다.

진행 중 쓰기가 A에만 새 값을 남긴 상태에서 조회만 하는 첫 읽기는 A/B를 통해 새 값을, 그 뒤 읽기는 B/C를 통해 옛 값을 받을 수 있다. N=3,R=W=2여도 읽기 write-back 등 추가 규칙 없이 새 값에서 옛 값으로 역전하는 문제가 생긴다.

소단원 4.3

읽기·쓰기 경로와 장애

응답이 사라졌다면 쓰기도 없었던 것일까?

준비 개념과 학습 목표

준비 개념

  • 요청과 응답

  • timeout은 관찰한 대기 시간

학습 목표

  • 완료와 불확실 상태를 나눈다

  • 장애 중 안전성과 진행성을 따로 설명한다

응답까지의 길

쓰기 경로에는 요청 전송, 복제 저장, 확인 수집, 클라이언트 응답이 있다. 저장 이후 응답 메시지만 유실되면 서버 쪽에는 값이 남지만 클라이언트는 완료 여부를 모른다. Timeout만으로 저장 실패를 결론 내릴 수 없다.

재시도는 같은 요청 ID와 중복 처리 규칙을 함께 설계한다. 특히 증가나 결제 같은 연산을 새 요청으로 반복하면 두 번 처리될 수 있다. 이 단원의 ID 표는 종이 설계 예이며 실제 결제 서비스나 완전한 exactly-once 보장 구현이 아니다.

읽기도 값을 퍼뜨리는 경로

다수 질의에서 읽은 최대값을 반환하기 전에 write-back하는 단계는 후속 읽기와의 순서 보존에 기여한다. 진행 중 쓰기는 전부 완료되지 않아도 한 읽기의 결과로 관찰될 수 있다. 후속 읽기가 더 오래된 값을 반환하지 않게 하려면 그 관찰을 다수에 보존한다.

서버는 버전을 단조롭게 유지하고 요청 ID·단계별 응답을 구별해야 한다. 다른 단계의 응답을 같은 다수 확인으로 세거나 한 서버의 중복 응답을 여러 복제본으로 세면 숫자가 맞아 보여도 근거가 무너진다.

네트워크가 갈라질 때

다섯 복제본이3/2로 갈라지고 다수 3이 필요하면3쪽은 필요한 응답을 얻을 수 있지만2쪽은 완료할 수 없다. 여기서 진행은 올바른 참여자와 필요한 메시지가 도착한다는 전제를 둔다. 장애 때 멈추는 선택은 잘못된 결과를 만들지 않는 안전성 요구와 구별된다.

Timeout은 상대가 죽었는지 늦었는지 알려 주는 완벽한 증거가 아니다. Primary 교체는 view 전환과 과거 상태 보존 조건을 만족해야 한다. 이 설명은 실패·복구 원리를 배우는 것이며 실제 네트워크 장애 주입 결과를 주장하지 않는다.

중간 과정을 따라가는 예제

A,B,C 세 복제본의 초기 버전 0/값 0. 진행 중 쓰기 버전 1/값 9가 A에만 저장됐다. 첫 읽기 r1은 A,B에서1/0을 받고 최대 1을 B,C에 write-back하여 두 확인 후 끝난다. 이어 r2가 B,C를 질의한다.

  1. r1의 첫 단계 최대는 버전 1/값 9다. 진행 중 쓰기의 값을 관찰할 수 있다.

  2. B와C가 write-back을 받아 버전 1/값 9로 올라가고 각각 확인한다.

  3. r1이 다수 확인 후 완료하므로 이어 시작한 r2의 질의 B,C는 모두 버전 1이다.

  4. r2는 9를 선택한다. 단조 버전과 다수 단계가 유지된다는 가정에서 옛 0으로 돌아가지 않는다.

r2는 9를 반환한다. r1이 새 값을 다수에 보존한 뒤 종료한 것이 차이를 만든다.

종이와 본문으로 직접 해보기

같은 초기 상태에서 r1이 write-back 없이 9를 반환한다면 r2가 B,C에서 받을 값은? 또한 다섯 복제본의3/2분할에서 다수 3을 얻을 수 있는 쪽을 표시하라.

힌트 보기

r1이 읽기만 했다면 B,C는 바뀌지 않는다.

풀이 보기

B,C는 버전 0/값 0이어서 r2는 0을 반환할 수 있다. 서로 다른 클라이언트라도 r1 종료 뒤 r2 시작이라는 실시간 순서에서 새 값→옛 값 역전이다. 3/2 분할의 3쪽만 다수 3을 모을 수 있으며 2쪽은 기다려야 한다.

오해와 반례

Timeout이 났으면 같은 증가 요청을 새 ID로 반복해도 안전하다.

증가가 저장된 뒤 응답만 사라졌다면 새 ID의 재시도로 두 번 증가할 수 있다. 같은 ID의 중복 처리도 상태 보존·복구 조건을 따로 검증해야 하므로 ID 한 개만으로 만능 보장을 주장하지 않는다.

한 단계 더

요청 u의 증가를 처리한 뒤 결과를 ID표에 저장하는 종이 서비스와 ID표를 저장하지 않는 서비스를 비교하자. 재전송 u에서 저장된 결과를 반환하는 조건, ID표가 유실된 복구의 한계, 메모리와 영속 저장의 차이를 표로 적는다. 실제 분산 트랜잭션 보장과는 별도로 검토해야 한다.
