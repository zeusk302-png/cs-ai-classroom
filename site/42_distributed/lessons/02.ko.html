소단원 2.1

직렬화·요청·응답

함수 인자에 메모리 주소를 적어 보내면 다른 컴퓨터도 같은 객체를 읽을까?

준비 개념과 학습 목표

준비 개념

  • 바이트는 8비트이고 이 단원의 바이트 값은 0~255이다. 16진 표기 01 00은 두 바이트를 나열한 것이다.

  • 직렬화는 값을 전송 가능한 기호열로 표현하는 일이며 역직렬화는 합의한 형식으로 값을 복원하는 일이다.

  • RPC는 원격 절차 호출이다. 요청은 수행할 연산과 인자, 응답은 그 요청의 결과 또는 오류 정보를 전달한다.

학습 목표

  • 메모리 참조와 전송 값을 구분한다.

  • 형식·범위·요청 ID를 가진 자체 메시지를 종이로 인코딩한다.

두 요청이 세 조각으로 도착하고 응답 순서가 뒤집히면?

기본의 7바이트 ADD 요청을 그대로 쓰되 자체 외부 프레임을 추가한다. 길이 접두사는 unsigned 16비트 big-endian 두 바이트이며 payload 길이만 센다. 이 버전은 길이가 정확히 7이어야 한다. 따라서 한 요청 프레임은 9바이트다. 접두사 한 바이트만 도착하면 길이를 판정하지 않으며 두 바이트에서 길이가 7이 아니면 handler를 호출하지 않고 거절한다.

새 요청 A는 id=513, a=250, b=10이고 B는 id=514, a=1, b=2다. A의 payload는 01 01 02 01 FA 0A 00, B는 01 01 02 02 01 02 00이다. 스트림 전체 18바이트를 길이 1, 4, 13인 조각으로 받는다. 두 번째 조각 뒤에는 접두사와 A의 첫 3바이트만 있어 아직 요청을 호출할 수 없다. 마지막 조각은 A의 나머지 4바이트와 B의 전체 9바이트를 포함한다.

성공 응답의 새 자체 payload는 id 두 바이트, status 한 바이트 0, 합계 두 바이트 big-endian의 총 5바이트로 정한다. 오류 응답은 이 성공 형식으로 해석하지 않는 별도 계약이다. B 응답이 먼저 와도 id=514에 연결하고 A에는 id=513의 합계 260을 쓴다. 이 포맷은 실제 protobuf나 gRPC wire 형식이 아니다. 공식 proto3의 optional은 명시한 0과 미제공을 구분할 수 있지만 implicit scalar의 기본값은 그 구분을 보존하지 못한다. 값 복원 외에 필드 존재와 버전 의미도 계약에 필요하다.

먼저 확인할 개념
  • 고정 7바이트와 외부 프레이밍

    기본 요청을 유지하고 조각마다 접두사와 payload의 수신량을 따로 센다.

  • 호출자 관측과 서버 효과

    응답 수신 순서와 handler 실행 여부가 서로 다른 사건임을 사용한다.

같은 함수 모양, 다른 경계

RPC의 client stub은 인자를 메시지로 만들고 서버의 수신 절차는 이를 해석해 handler를 부른다. 네트워크 전송·프로세스·언어를 건너므로 로컬 포인터의 숫자는 상대 메모리 객체의 이름이 아니다. 원격 자원을 참조하려면 상대가 해석할 수 있는 객체 식별자와 그 사용 권한을 계약에 넣는다.

이 단원은 요청 하나에 응답 하나인 unary 모형을 사용한다. 요청 ID는 응답을 어느 호출에 대응시킬지 구분하며 인증이나 중복 방지를 자동으로 제공하지 않는다. 요청이 도착했는지, handler가 효과를 만들었는지, 응답을 클라이언트가 관측했는지는 서로 다른 사건이다.

명세가 있어야 바이트가 값이 된다

자체 형식은 요청을 7바이트로 정의한다: version 1바이트, method 1바이트, id 2바이트, a 1바이트, b 1바이트, reserved 1바이트이다. version=1, method=1은 ADD이며 id는 unsigned 16비트 big-endian, a,b는 0~255, reserved=0을 요구한다. 응답은 id와 성공/오류 및 합계를 별도 형식으로 전달한다고 정하고 합계는 0~510 범위 정수이다.

디코더는 총 길이 7, 버전·method·reserved 및 인자 범위를 검사한 뒤에만 handler를 호출한다. id의 상위 바이트 h, 하위 바이트 l은 256h+l로 복원한다. 이 형식은 protobuf의 실제 wire 형식이 아니다. 표준 도구를 쓰더라도 필드 번호·타입·누락의 의미와 버전 변경 계약을 보존해야 한다.

프레이밍과 오류의 구분

여기서는 메시지 길이를 외부 프레임으로 알려 주는 추상 전송을 가정한다. 바이트 스트림에서는 한 번 read한 조각이 요청 하나와 일치한다고 가정할 수 없으며 길이 접두사나 다른 프레이밍과 최대 길이 검사가 필요하다. 형식 오류는 합계를 계산한 뒤 발견하는 문제가 아니라 해석 경계의 거절이다.

인코더 E와 디코더 D의 목표는 허용 값 x에 D(E(x))=x이다. 이를 위한 범위와 바이트 순서의 합의가 없으면 같은 바이트를 다른 값으로 읽는다. 그렇다고 직렬화가 신뢰성이나 기밀성까지 보장하지는 않는다. 메시지 보호와 호출 권한은 추가 경계이다.

조각은 read 결과의 자체 배치이며 메시지 개수가 아니다. 응답 표는 성공 payload만 보여 준다. 합계와 id의 두 바이트를 각각 복원하며 대기 중인 요청 ID에 맞춘다.

중간 과정을 따라가는 예제

ADD 요청 version=1, method=1, id=258, a=7, b=9, reserved=0을 위 7바이트 형식으로 표현하고 응답의 합계를 구하라.

  1. id=258=256·1+2이므로 big-endian 두 바이트는 01 02이다.

  2. 전체 요청은 16진수 01 01 01 02 07 09 00이며 길이는 1+1+2+1+1+1=7바이트이다.

  3. 서버는 외부 프레임 길이와 version/method/reserved를 검사하고 id=258, a=7, b=9를 복원한다.

  4. ADD는 7+9=16을 계산한다. 응답은 id=258과 합계 16을 연결해야 하며 다른 id의 응답을 이 요청의 결과로 쓰지 않는다.

요청은 7바이트이고 성공 값은 16이다. 실제 패킷이나 protobuf 출력이 아니라 가상 형식의 종이 계산이다.

조건을 바꾸어 비교하기

완성 전 호출과 조각별 호출의 두 실패

1/4/13바이트 조각마다 ADD를 한 번씩 호출하는 구현과 완성 프레임만 호출하는 구현을 비교하라.

  1. 첫 두 조각은 A의 고정 필드를 모두 담지 않으며 마지막 조각은 요청 두 개의 경계를 포함한다. 조각별 호출 수 3은 요청 수 2와 다르다.

  2. 버퍼에서 접두사 두 바이트를 확인하고 payload 7바이트가 모일 때만 한 프레임을 제거한다. 마지막 수신 뒤 이 절차를 두 번 수행하면 A와 B를 분리한다.

정상 호출 수는 2이며 앞선 두 수신 직후는 각각 0이다.

비교할 점

기본의 단일 요청 길이 검사를 조각 누적과 여러 프레임 소비로 확장한다.

0은 기본값인가, 명시된 관측인가?

설정 메시지의 threshold를 미제공하면 기존 9를 유지하고 명시한 0이면 0으로 바꾸려 한다. implicit scalar 값만 읽는 정책과 존재 비트도 읽는 정책을 비교하라.

  1. implicit 값 0만으로는 미제공과 명시된 0을 구별할 수 없다. 둘에 서로 다른 효과를 요구하는 계약을 그 값 하나로 구현하지 못한다.

  2. 존재 여부와 값을 함께 보존하면 미제공은 9 유지, 존재하며 값 0이면 0 설정으로 나뉜다. 실제 serializer를 실행한 결과는 아니다.

요구가 존재 여부에 의존하므로 그 정보를 보존하는 표현이 필요하다.

연습 1 · 값과 상태 예측

A 성공 payload 02 01 00 01 04의 id와 합계를 복원하고 두 바이트 합계를 한 바이트로 잘라 읽으면 무엇이 되는지 구하라.

힌트 1

256h+l을 두 필드에 각각 쓴다.

힌트 2

마지막 바이트만 읽는 잘못된 정책을 따로 적용한다.

풀이와 답 확인

  1. id는 256·2+1=513이다. 합계는 256·1+4=260이다.

  2. 마지막 바이트만 읽으면 4여서 250+10의 결과와 다르다.

올바른 값은 id 513과 합계 260이며 잘못 잘라 읽은 합계는 4다.

합계 바이트 01은 id의 일부이므로 버려도 된다.

필드 경계는 계약이 정하며 id 뒤 status를 지난 두 바이트가 합계다.

접두사 00 06 뒤 payload 6바이트가 왔다. 마지막 reserved를 0으로 추정해 ADD를 호출하는 디코더를 고쳐라.

힌트 1

이 버전이 허용하는 길이를 먼저 확인한다.

힌트 2

불완전 요청의 값을 임의로 채우지 않는다.

풀이와 답 확인

  1. 접두사가 6을 선언한 순간 이 버전의 길이 7 계약과 불일치하므로 거절한다.

  2. reserved뿐 아니라 모든 필드의 존재·값 검사 완료 전에는 handler를 호출하지 않는다.

추정 보충 대신 형식 오류로 거절하며 효과는 만들지 않는다.

0으로 채우면 원래 인코더와 항상 같은 요청이다.

누락의 원인은 알 수 없고 허용 문자열 집합 밖의 입력을 자의적으로 합법화한다.

연습 3 · 직접 만들어 보기

A와 B의 두 프레임을 기다리는 버퍼 규칙을 구성하라. 완성된 A 뒤 B의 payload가 4바이트만 온 채 EOF라면 호출 수와 남은 처리 상태는?

힌트 1

A 전체 9바이트를 먼저 소비한다.

힌트 2

B의 접두사와 payload 부족을 EOF까지 구별한다.

풀이와 답 확인

  1. A의 길이·필드를 검사해 한 번 호출하고 9바이트를 소비한다. B는 접두사 2와 payload 4로 3바이트가 부족하다.

  2. EOF에서 B를 잘린 프레임으로 거절한다. A의 이미 완료한 효과를 자동 취소한다고 주장하지 않는다.

호출 수는 1이며 B는 미호출 형식 오류다.

스트림 EOF이면 A도 실행하지 않았다고 볼 수 있다.

재시도·중복·멱등성

서버가 처리했는데 응답이 사라지면 다시 보내도 한 번만 처리될까?

준비 개념과 학습 목표

준비 개념

  • 상태 전이 f는 상태 S를 다음 상태 f(S)로 바꾼다. 멱등성은 모든 허용 상태에서 f(f(S))=f(S)인 성질이다.

  • 재시도는 응답을 얻지 못한 호출을 다시 보내는 일이다. 한 논리 요청과 여러 전송 시도를 구분한다.

  • 원자 처리는 여러 상태 변경이 다른 처리와 중간에 섞이지 않는 추상 한 단계이고, 내구성은 성공한 기록이 장애 후에도 남는다는 별도 성질이다.

학습 목표

  • 증분과 설정의 멱등성을 구분한다.

  • 요청 ID·고정 인자·결과표의 조건 아래 중복 효과 방지를 증명한다.

현재 잔액이 달라도 같은 재시도의 결과는 같아야 할까?

기본의 정수 잔액·원자 결과표 모형을 그대로 사용한다. 초기 x=20에서 인증 주체 u의 id=513, p=2가 커밋되면 x=22와 D[(u,513)]=(2,22)가 함께 저장된다. 그 뒤 같은 주체의 새 id=514, p=5가 커밋되어 x=27이 된다. 이제 첫 요청을 재전송하면 현재 잔액 27 대신 저장 결과 22를 반환하며 x는 27에 남는다. 응답 재현성과 현재 상태 조회는 서로 다른 연산이다.

같은 id라도 인증 주체 v의 요청은 키가 다르므로 새 효과를 만들 수 있다. ID만 키로 쓰면 v의 요청을 u의 결과로 오인할 수 있다. 반대로 같은 주체·ID에 p=9를 붙이면 입력 충돌로 거절해야 한다. 여기서 인증 확인의 실제 구현을 검증한 것은 아니며 주체가 이미 확인되었다는 모형 전제다.

두 서버가 각자 빈 결과표를 보고 공통 잔액에 같은 p=2 효과를 차례로 저장하면 x=20에서 22를 거쳐 24가 될 수 있다. 첫 서버의 결과표는 둘째 서버에 보이지 않는다. 각각의 로컬 저장이 원자적이라는 사실만으로 공통 키의 최대 한 번 효과를 증명하지 못한다. 단일 일관된 원자 상태라는 기본 가정이 왜 필요한지 보여 주는 반례다.

  • 시간 초과 후 효과 조회

응답 없음은 실행 없음이 아니다

클라이언트가 응답을 못 본 실행에는 요청 유실, 서버 처리 전 장애, 효과 완료 후 응답 유실 등이 모두 가능하다. 같은 관측으로 어느 경우인지 결정할 수 없다. 재시도를 하면 도달 가능성은 높일 수 있지만 비멱등 효과가 중복될 위험도 생긴다.

증분 f(x)=x+3은 f(f(x))=x+6으로 멱등이 아니다. 설정 g(x)=10은 g(g(x))=10으로 멱등이다. 그러나 설정 요청도 다른 요청과 섞이면 과거 값 재설정이 새 값을 덮을 수 있다. 단일 전이의 멱등성과 여러 사용자의 의도 보존은 다른 명세이다.

고정 요청과 중복 결과표

가상 서비스의 상태는 수학적 정수 잔액 x와 결과표 D이다. 인자 p도 수학적 정수이며 이 모형은 고정폭 정수 overflow를 가정하지 않는다. 실제 구현에서는 저장 타입의 범위와 덧셈 전 검사를 추가해야 한다. 논리 키 k=(인증 주체,요청 ID)를 쓰며 인자 p도 저장한다. k가 없으면 x←x+p와 D[k]←(p,새 x)를 하나의 원자적이고 내구적인 전이로 커밋한다. 있으면 같은 p일 때 저장 결과를 반환하고 x를 바꾸지 않는다. 다른 p이면 ID_CONFLICT로 거절한다.

ID는 한 주체에서 재사용되지 않으며 결과표는 재시도 가능 기간 전체에 남는다고 가정한다. 인증 주체를 생략하거나 같은 ID의 인자를 바꾸면 엉뚱한 결과를 공유할 수 있다. 서로 다른 서버가 각자 결과표를 두면 중복 방지의 공통 경계가 깨질 수 있으므로 이 모형은 하나의 일관된 원자 상태를 전제로 한다.

최대 한 번 효과와 성공 관측

어떤 고정 키 k의 최초 커밋 뒤에는 D[k]가 있으므로 이후 동일 요청은 x를 바꾸지 않는다. 커밋 전에는 효과와 결과표가 함께 없고 커밋 후에는 함께 있으므로 장애 복구에서도 따로 사라지지 않는다는 가정 아래 최대 한 번의 상태 효과가 성립한다. 요청이 끝내 도착하지 않으면 효과는 0회일 수도 있다.

이 조건만으로 클라이언트가 반드시 응답을 받는 활성 성질은 보장되지 않는다. 무한 유실이나 영구 장애를 제외하고 재시도·처리·응답 전달의 진행 가정을 추가해야 한다. 외부 알림·결제 같은 별도 효과를 원자 상태 밖에서 수행하면 이 증명에 포함되지 않는다. 저장 결과를 돌려주는 것은 효과의 멱등성과 응답 재현성을 함께 설계하는 방법이다.

타임아웃과 취소

호출자가 기다리기를 그만두면 서버가 한 일도 사라질까?

준비 개념과 학습 목표

준비 개념

  • timeout은 기다리는 기간의 한도이고 deadline은 끝내야 할 시점이다. 여기서는 같은 단조 시간 축의 정수 ms를 사용한다.

  • 취소는 진행 중 작업을 중단하라는 요청 또는 상태이다. 원상복구는 이미 만든 효과를 되돌리는 별도의 연산이다.

  • 부분 실패는 클라이언트·서버·통신 중 일부만 실패하거나 관측이 다른 상황이다. 응답 없음만으로 서버 장애가 확정되지 않는다.

학습 목표

  • 잔여 시간 예산을 계산한다.

  • 취소 관측·커밋·응답 도착 순서에 따라 효과와 호출 결과를 따로 판정한다.

각 하위 호출에 같은 timeout을 새로 주면 전체 기한은?

새 시간 모형은 기본과 같은 단조 정수 ms 축을 사용하고 전체 deadline을 90 ms로 둔다. 유효 응답이 90 ms보다 먼저 도착해야 성공이며 등호도 시간 초과다. t=15 ms에 P를 시작하여 22 ms 걸리면 반환 시각은 37 ms다. 이때 하위 Q의 남은 전체 예산은 53 ms이지 90 ms가 아니다.

Q가 30 ms 뒤인 67 ms에 커밋·응답 생성하고 최종 전달이 25 ms 걸리면 고객 수신은 92 ms다. 서버 효과는 있을 수 있지만 고객은 시간 초과다. t=37 ms에 원래 timeout 90 ms를 다시 부여하면 잘못된 끝점 127 ms를 만들고 92 ms를 허용하는 오류가 생긴다. 실제 gRPC의 기간 전파와 시계 처리 설명을 참고했으나 이 절대 시간표는 자체 공통 축 모형이다.

취소 신호가 생성된 시각과 handler가 이를 관측한 시각을 따로 기록한다. 자체 polling 확인은 10, 30, 50 ms에만 실행된다고 하자. 취소가 11 ms에 생기고 30 ms에 관측되면 지연은 19 ms다. 관측 전에 25 ms에 원자 커밋하면 효과가 남고 30 ms 뒤 커밋 시도는 취소로 차단된다. 실제 handler의 확인 간격과 스케줄 상한을 측정한 것은 아니다.

먼저 확인할 개념
  • 남은 예산과 원자 취소 판정

    기본의 t<deadline 규칙을 여러 호출과 협력 확인 시점에 적용한다.

  • 응답 유실과 저장 결과

    효과 뒤 늦은 응답이 와도 같은 키 재시도가 중복 효과를 만들지 않는 조건을 사용한다.

시간의 계약

가상 호출자는 시작 t=0에서 deadline=100ms를 둔다. 유효 응답이 t<100에 도착하면 수신 성공으로 하고 t≥100에는 시간 초과로 끝낸다. 등호 처리 방식은 자체 정책이며 실제 API의 경쟁 사건 처리는 해당 구현 명세를 확인해야 한다. 시간 초과는 호출자 관측이며 서버가 작업을 하지 않았다는 증거가 아니다.

남은 예산은 max(0,deadline−현재 시각)이다. 같은 호출의 하위 작업을 시작할 때 초기 timeout을 다시 주면 전체 한도를 늘려 버릴 수 있다. 서로 다른 기계의 절대 시각을 그대로 빼려면 시계 관계가 필요하며, 실제 시스템은 경과 시간을 반영한 남은 기간 전파 같은 방법을 쓸 수 있다.

취소는 협력과 경계가 필요하다

클라이언트의 취소 메시지는 지연되거나 도달하지 않을 수 있다. handler가 오래 계산하는 동안 라이브러리가 이를 자동 중단하지 못할 수도 있어 안전한 확인 지점과 자원 정리가 필요하다. 하위 호출에도 취소를 전달할지 언어·구현·응용 계약에 따라 정한다.

가상 서버는 커밋 전 원자 단계에서 cancelled를 확인한다. 취소 관측이 커밋보다 먼저면 효과 없이 CANCELLED로 끝내고, 커밋이 먼저면 효과를 유지한다. 커밋 후 취소는 응답 대기를 끝낼 수 있어도 이미 만든 효과를 소거하지 않는다. 보상 연산이 필요하면 새 요청과 그 실패 가능성을 별도로 설계한다.

완료 결과를 두 축으로 읽기

서버의 효과 여부와 클라이언트의 성공 응답 여부를 표의 서로 다른 열로 둔다. 서버 커밋 뒤 응답이 deadline보다 늦으면 효과는 있지만 클라이언트는 실패를 관측할 수 있다. 이 상태에서 재시도하려면 요청 ID의 중복 처리 계약이나 상태 조회 계약을 이용한다.

시간 초과를 줄이는 목표, 효과 중복 방지, 취소 후 자원 회수는 다른 목표이다. 제한 시간이 있다는 사실만으로 처리 시간의 상계나 실시간성을 증명하지 못한다. 본문은 지연을 지정한 종이 사건표이며 실제 네트워크·OS 스케줄러·서버 지연을 측정한 자료가 아니다.
