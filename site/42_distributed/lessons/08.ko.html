소단원 8.1

분산 파일·키값 저장

한 파일과 사용자별 작은 값을 여러 컴퓨터에 나눠 담는 방식은 같은가?

준비 개념과 학습 목표

준비 개념

  • 파일은 이름과 바이트 내용으로 접근할 수 있다.

  • 키값 저장은 키로 값을 넣고 읽는 인터페이스다.

학습 목표

  • 논리 이름과 물리 저장 위치를 구분한다.

  • 분할·복제·메타데이터 역할을 비교한다.

복제본 세 개는 세 장애 영역을 뜻할까요?

새 파일의 논리 길이는 140 MiB다. 블록 최대 길이는 64 MiB이고 마지막 블록은 실제 길이만큼 저장한다. 각 블록을 서로 다른 세 DataNode에 복제하면 실제 내용의 합은 420 MiB다. 각 복제본마다 64 MiB 슬롯을 예약한다는 별도 할당 모형에서는 예약 용량이 576 MiB다. 실제 길이와 예약 슬롯을 같은 수치로 보고하지 않는다.

장애 배치의 별도 파일은 두 블록 u와 v다. rack A에는 A1·A2, rack B에는 B1·B2가 있다. u의 복제본은 A1·A2·B1에, v의 복제본은 A1·B1·B2에 둔다. 각 노드는 한 블록의 복제본을 하나만 가지지만 세 노드가 세 rack을 뜻하지 않는다. 파일 내용을 모두 얻으려면 모든 블록에 적어도 한 개의 살아 있는 복제본이 필요하다.

이 손모형은 내용 복제의 생존 조건만 계산한다. 새 클라이언트가 이름에서 블록 위치를 찾는 데 필요한 metadata 경로도 따로 확인한다. NameNode에 사용자 내용이 저장된다는 뜻은 아니다. metadata 접근 실패와 모든 내용 복제본의 소실은 서로 다른 실패다. 실제 HDFS의 구체 배치·고가용성 시험은 수행하지 않았다.

먼저 확인할 개념
  • metadata와 블록 내용

    이름·위치 관리 경로와 실제 사용자 내용 저장 위치를 분리한다.

  • 재배치의 운영 조건

    배치 변경 때 복사·갱신·접근 경로를 각각 확인하는 습관을 연결한다.

큰 파일을 블록으로 나누기

분산 파일 시스템은 한 논리 파일의 데이터를 여러 저장 노드에 둔다. 파일 경로·블록 순서·블록 위치 같은 메타데이터와 실제 바이트 데이터가 다른 역할을 한다. HDFS에서는 NameNode가 메타데이터를 관리하고 DataNode가 블록을 저장한다.

클라이언트는 위치 정보를 받아 실제 블록 데이터는 DataNode와 주고받는다. 파일 시스템에 큰 파일을 저장한다는 사실이 작은 부분 갱신이나 로컬 파일과 동일한 POSIX 동작을 모두 제공한다는 뜻은 아니다. 시스템의 접근 패턴과 일관성 규칙을 확인한다.

작은 값을 키로 찾기

키값 저장은 get(key),put(key,value) 같은 인터페이스로 논리 키를 실제 저장 노드에 대응시킨다. 값의 내부 형식을 저장소가 해석하지 않는 설계도 있다. 모든 키값 저장소가 관계형 질의·범위 검색·다중 키 트랜잭션을 똑같이 제공하는 것은 아니다.

키별로 저장 위치를 나누는 파티셔닝과 같은 값을 여러 위치에 유지하는 복제는 서로 다르다. 키가 다른 세 항목을 세 노드에 나누었다고 각 항목의 장애 대응 사본이 생긴 것은 아니다.

배치와 실패를 함께 설계하기

복제는 일부 노드 장애 때 다른 사본을 읽거나 복구하도록 돕지만 사본 위치·최신성·쓰기 성공 조건이 필요하다. 같은 랙에 모든 사본을 두면 랙 전체 장애에 함께 영향을 받을 수 있다. 사본 개수만으로 모든 종류 장애를 보장하지 않는다.

파일 위치 메타데이터도 잃으면 실제 블록이 남아 있어도 찾기 어려울 수 있다. 서비스별 메타데이터 보호와 데이터 보호를 함께 설계한다. 본문의 종이 예제는 실제 클러스터 가용성 시험이나 제품 구성 확인을 대신하지 않는다.

중간 과정을 따라가는 예제

교육 파일은250MiB이고 블록 최대100MiB다. 각 블록 실제 데이터는 마지막을 제외하고 가득 채우며 복제 인자는3이다. 패딩·메타데이터를 무시한 블록 수, 사본 수, 실제 내용 저장량을 계산하라.

  1. 블록은100,100,50MiB의3개다. ceil(250/100)=3으로 확인한다.

  2. 각 블록3사본이므로 블록 사본 수는9개다.

  3. 내용 저장량은3×(100+100+50)=750MiB다.

  4. 고정100MiB를 마지막에도 모두 예약하는 모형이면900MiB지만 이 문제는 실제 내용만 센다.

블록3개, 사본9개, 실제 내용750MiB다. 논리 크기250MiB와 물리 사본 내용량은 다르다.

조건을 바꾸어 비교하기

사용 내용 합과 예약 용량의 구별

140 MiB 파일을 세 번 복제할 때 블록 수, 실제 내용 합, 고정 슬롯 예약 용량을 계산하라.

  1. 블록은 64 MiB, 64 MiB, 12 MiB로 나뉜다.

  2. 세 블록마다 복제본 세 개이므로 복제본은 아홉 개다. 실제 내용은 140×3 MiB이고 예약은 64×9 MiB다.

블록 수는 3개, 실제 내용 합은 420 MiB, 예약 용량은 576 MiB다.

비교할 점

마지막 블록의 사용량 12 MiB를 예약 슬롯 64 MiB와 혼동하지 않는다.

복제 수가 같아도 파일 생존은 블록별로

두 블록 배치에서 A1과 B1이 동시에 중단했다. 전체 내용을 얻을 수 있는가?

  1. u는 A2에 남는다.

  2. v는 B2에 남는다. 두 블록의 살아 있는 노드가 서로 달라도 된다.

내용 복제본만 기준으로는 전체 파일이 생존한다. 실제 읽기 성공에는 metadata·통신 등도 필요하다.

비교할 점

한 노드가 파일의 모든 블록을 가지는 것을 필수 조건으로 추가하지 않는다.

primary가 그대로이면 복제 대상도 그대로일까요?

0부터 99까지의 원형 해시 공간을 시계 방향으로 걷는다. 토큰은 A10, B30, C50, A60, B80, C90 순서이며 문자는 물리 서버, 숫자는 토큰 위치다. 키 위치 이상인 첫 토큰을 primary로 택하고 끝을 넘으면 처음으로 돌아간다. 복제 목록은 그 지점부터 처음 만나는 서로 다른 물리 서버 세 곳으로 정한다. 같은 서버의 다른 토큰은 새 복제 대상이 아니다.

D70을 추가하면 primary가 바뀌는 구간은 (60,70]이다. 키 65는 B에서 D로 옮겨지지만 키 55의 primary는 A60을 유지한다. 그런데 키 55의 복제 목록은 이전 A·B·C에서 이후 A·D·B로 달라진다. primary 재배치 범위만 보아 전체 복제본 변경 범위를 결정하면 안 된다.

별도 요청 장부에서 키 55는 초당 100회, 키 65와 키 85는 각각 초당 1회 요청을 받는다. 여기서는 primary 처리 횟수만 센다. D를 넣어도 뜨거운 키 55의 primary A가 바뀌지 않아 A의 요청량은 그대로다. 해시 공간의 폭, 키 개수, 실제 요청 횟수는 각각 다른 부하 척도다.

어떤 기준으로 구역을 나눌까

범위 샤딩은 정렬 키의 연속 구간을 나누어 범위 조회에 유리하지만 최근 시각 등 한쪽 키에 쓰기가 몰리면 부하가 치우칠 수 있다. 해시 샤딩은 키의 해시를 이용해 위치를 분산시키지만 원래 키의 가까움이 저장 위치의 가까움과 같지 않다.

hash(key) mod N처럼 서버 수로 나눈 나머지는 쉽지만 N이 바뀌면 많은 키의 대응이 달라질 수 있다. 논리 파티션을 고정하고 물리 노드 매핑을 별도 표로 유지하는 설계도 가능하므로 모든 해시 시스템을 동일하게 보지 않는다.

원의 다음 위치로 대응하기

consistent hashing의 단순 모델은 해시 공간을 원으로 두고 노드 위치를 표시한다. 키 위치에서 시계 방향으로 처음 만나는 노드가 그 키의 담당이다. 이 본문은 동일 위치 키도 그 노드에 배정하는 경계 포함 규칙을 명시한다.

노드 하나가 추가되면 새 노드의 이전 노드부터 새 위치까지 구간만 새 담당으로 넘어간다. 모든 키가 그대로라는 뜻은 아니다. 정렬된 링의 마지막을 지나면 처음으로 돌아가는 구간도 처리해야 한다.

링 균형은 부하 균형과 다르다

물리 노드 하나에 여러 가상 위치를 배정하면 구간 길이 편차와 장비 용량 차이를 조절하기 쉽다. 가상노드는 서버 여러 대가 아니라 한 물리 서버가 담당하는 여러 논리 위치다. 복제 위치를 고를 때 같은 물리 서버의 위치를 독립 장애 사본으로 세지 않는다.

균일 키 분포를 기대할 수 있어도 특정 키에 요청이 몰리면 해당 소유 구간이 뜨거워질 수 있다. consistent라는 이름은 재배치 폭을 줄이는 성질이지 데이터 읽기의 강한 일관성 보증이 아니다.

준비 개념과 학습 목표

준비 개념

  • 처리량은 단위 시간의 요청 처리 수다.

  • 저장 바이트 균형과 요청 부하 균형은 다른 양이다.

학습 목표

  • 재배치 중 읽기·쓰기의 소유권을 설명한다.

  • 핫스폿을 진단하고 가정별 대응을 비교한다.

복사를 마치면 갱신과 소유권도 자동으로 따라올까요?

별도 재배치 계약을 명시한다. 옛 소유자 epoch 9의 snapshot 경계는 seq 40이며 값 x는 10이다. 이후 seq 41은 +3, seq 42는 ×2다. 먼저 공통 저장 경로에서 옛 epoch 9의 추가 쓰기 승인을 차단하고, 이미 승인한 마지막 경계가 42임을 확정한다. 새 소유자는 snapshot과 경계 42까지의 명령을 순서대로 적용한 뒤 새 소유권 epoch 10을 활성화한다. 차단 전 이미 승인된 43이 있다면 인계 경계도 43 이상으로 올려 재생해야 한다. 이 순서·원자성은 자체 계약이며 파일 복사만으로 자동 제공되지 않는다.

snapshot만 복사하면 새 값은 10으로 뒤처진다. 명령 42만 적용하면 20이 되고, 42 뒤 41을 적용하면 23이 된다. 올바른 순서는 10→13→26이다. 이전 epoch의 추가 쓰기 43을 그대로 승인하면 인계 뒤 갱신이 빠질 수 있다. 거절한 요청을 새 소유자에게 재시도할 때는 ID와 내용 확인으로 한 번만 적용한다.

전송 시간은 독립된 연속량 모형이다. 초기 미복사량 60 MiB, 새 갱신 유입량 초당 4 MiB, 복사율 초당 10 MiB이며 재복사·압축·처리 지연은 제외한다. 잔여량의 감소율은 초당 6 MiB여서 따라잡기 시간은 10초다. 서비스와 복사가 같은 초당 16 MiB 예산을 나누면 서비스 부하 변화가 복사율과 완료 시간에 영향을 준다.

이동은 복사 한 번으로 끝나지 않는다

샤드 이동은 새 위치에 데이터를 복사하면서 그 사이 생긴 갱신도 반영해야 한다. 오래된 스냅샷만 옮기고 즉시 원본을 삭제하면 이동 도중 쓰인 값이 사라질 수 있다. 시스템의 로그·버전·소유권 전환 절차를 따른다.

새 소유권을 클라이언트와 서버에 전달하고 요청을 라우팅하거나 이전 위치에서 새 위치로 안내한다. 재시도는 중복될 수 있어 작업의 멱등성이나 식별자 처리도 필요하다. 각 시스템의 구체 프로토콜 없이 이 순서만으로 원자적 이동을 보장했다고 말하지 않는다.

핫스폿의 원인을 분해하기

한 샤드의 큰 데이터, 작은 데이터에 높은 요청 수, 비싼 요청 하나는 서로 다른 병목이다. 요청/초·바이트/초·지연·CPU·저장소 부하를 함께 관찰한다. 항목 수가 똑같아도 인기 키가 한 서버에 집중할 수 있다.

읽기 핫키는 유효성 정책이 있는 캐시·읽기 사본으로 부하를 줄일 수 있다. 단일 키 쓰기는 단순히 샤드 수만 늘려 해결되지 않을 수 있다. 키를 여러 조각으로 나누면 합산·정렬·일관성 의미도 바뀌어 설계를 다시 확인한다.

복구와 이동 자체도 부하다

재배치의 네트워크/디스크 작업은 사용자 요청과 같은 자원을 쓴다. 속도를 제한하고 단계적으로 수행하면 서비스 지연을 보호할 수 있지만 이동 완료는 느려질 수 있다. 배경 작업이 공짜라고 가정하지 않는다.

균형 정책은 평균뿐 아니라 가장 바쁜 파티션과 짧은 버스트도 살핀다. 장비 하나의 여유가 다른 장비의 독점 키 처리 능력으로 저절로 바뀌지는 않는다. 본문 수치 계산은 운영 계측 결과가 아닌 가정 모델이다.

풀이와 답 확인

u의 내용이 소실되어 전체 파일은 불완전하다. 키 55의 primary는 A, 키 65는 D이고 키 55의 복제 대상은 A·D·B다. 정상 재생 후 값은 26이며 중복 제거된 r 처리 뒤 상태는 27, 두 승인 응답 결과도 27이다. 전송 모형의 따라잡기 시간은 10초다.

    공식 웹 본문의 관련 204–309행을 실제 읽었다. metadata와 사용자 내용의 경로, 마지막 부분 블록, 서로 다른 DataNode와 rack 배치, 실패·재복제·checksum 조건을 대조했다. 세 복제본을 세 rack으로 일반화하지 않았으며 고정 슬롯 예약과 두 블록 장애표는 자체 손모형이다.

  • DeCandia et al.: Dynamo, SOSP 2007

    원저자 공개 PDF를 내려받아 물리 5·6·12·13·14쪽 전체 텍스트를 실제 읽었다. §4.1–4.3의 ring·virtual node·서로 다른 물리 대상과 §6.2의 배치/분할 구별, §6.5의 foreground/background 자원 경쟁을 대조했다. 구체 링과 상태 인계 순서·epoch fencing·연속량 예산은 자체 명시 계약이며 Dynamo 구현 시험이 아니다.

  • AWS DynamoDB: Partition key design

    공식 본문 전체 5–13행을 실제 읽고 partition key별 요청 활동과 바이트에 따른 read/write 단위의 차이를 확인했다. 자체 요청 장부는 특정 서비스의 실측 처리량·가격·성능 보증으로 제시하지 않았다.

모든 새 학습 내용 계산은 손유도다. 파일의 세 블록은 64·64·12 MiB이고 실제 복제 내용 합은 420 MiB, 고정 슬롯 예약량은 576 MiB다. 별도 장애표에서 rack A와 B1 중단 시 u가 소실되고 v는 B2에 남는다. 링의 키 55 복제 목록은 A·B·C에서 A·D·B로 바뀌고 primary A는 유지된다. 키 65는 B에서 D로 바뀐다. 정상 상태 인계는 10에서 13을 거쳐 26이며 누락은 20, 역순은 23이다. 중복 제거된 +1은 상태 27을 유지한다. 일정한 전송 모형의 시간은 10초이고 서비스 증가 사례는 처음 4초와 나중 18초를 합한 22초다. 복사율과 유입률이 같으면 양의 잔여는 줄지 않는다.
