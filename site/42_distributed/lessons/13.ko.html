소단원 13.1

장애·분할·지연 주입

서버가 응답하지 않을 때 전원이 꺼진 것인지 메시지가 늦은 것인지 어떻게 구별할까?

준비 개념과 학습 목표

준비 개념

  • 노드와 메시지

  • 응답 제한 시간

  • 복제와 정족수

학습 목표

  • 중단·지연·분할의 장애 범위를 명시한다.

  • 시험 일정과 요구 조건을 별도로 적는다.

  • 관찰된 실패와 원인 추정을 구별한다.

무응답에는 여러 원인이 있다

프로세스 종료는 특정 프로그램의 실행을 멈춘다. 일시 정지는 다시 실행될 수 있다는 점에서 종료와 다르다. 메시지 지연은 처리나 전달을 늦추고, 네트워크 분할은 정한 노드 집합 사이의 통신을 차단한다. 한 방향만 차단되는 경우도 있으므로 양방향 차단 여부를 적는다.

응답 제한 시간 안에 답을 못 받았다는 사실만으로 서버가 종료되었다고 증명할 수 없다. 요청이 적용되었지만 답이 지연되었을 수도 있다. 시험에서는 관찰 결과와 주입한 원인을 각각 기록한다.

어떤 조건을 요구하는가

안전성은 잘못된 상태가 생기지 않는 조건이다. 진행성은 요청이 계속 완료되는 조건이다. 분할 중 일부 노드가 안전성을 지키려고 응답을 거부할 수 있다. 거부 하나를 바로 데이터 손상으로 분류하지 않는다.

자체 모형은 세 노드 A, B, C 중 두 노드의 확인을 받아야 새 값을 성공으로 응답한다. 각 집단 내부는 통신 가능하고 집단 사이는 차단한다고 정한다. 이 조건은 실제 제품 설정을 대신하지 않는다.

다시 실행할 수 있는 시험 명세

초기 데이터·노드 수·버전·주입 대상·시작과 종료 사건·요청 식별자·판정 조건을 함께 남긴다. 랜덤 선택을 썼다면 seed도 기록하지만 seed 하나가 스레드와 네트워크 일정을 모두 재현해 주지는 않는다.

Jepsen의 공개 과거 분석은 분할과 프로세스 중단 등 여러 장애를 결합하여 이력을 검사했다. 우리는 그 시험 설계를 읽었으며 서버나 도구를 실행하지 않았다. 실습은 아래 표를 손으로 비교하는 이론 활동이다.

중간 과정을 따라가는 예제

세 노드의 두 확인 모형에서 A | BC로 양방향 분할한다. 다른 경로는 없다. A 또는 B로 제출한 새 쓰기가 성공 확인을 받을 수 있는지 계산하라.

  1. A 쪽 집단에는 한 노드만 있어 필요한 두 확인보다 적다. 정한 계약을 지키면 새 성공을 응답하지 못한다.

  2. B 쪽은 B와 C 두 노드의 확인이 가능하다. 다른 오류가 없고 두 확인을 실제 받았다는 추가 조건에서 성공할 수 있다.

  3. 무응답 관찰은 적용 여부 미확정과 구별한다. A가 혼자 성공했다는 기록이 있다면 이 모형의 확인 계약부터 검사한다.

A 쪽 확인 수는 1, BC 쪽은 2다. 성공 가능성과 실제 성공 관찰은 다르며 분할 중 모든 노드의 성공을 요구하지 않는다.

종이와 본문으로 직접 해보기

힌트 보기

집단 크기와 제한 시간의 비교를 따로 계산한다.

풀이 보기

각 집단은 1로 두 확인 조건을 충족하지 못한다. 12 > 10이므로 응답이 늦지만 요청 적용이나 데이터 손실은 그 부등식만으로 확정하지 못한다.

오해와 반례

시간 초과가 나면 서버 종료와 쓰기 실패가 모두 확정된다.

느린 통신·정지·응답 유실도 가능하다. 응답 실패와 실제 적용 결과를 별도로 확인해야 한다.

소단원 13.2

이력과 일관성 검사

최종 값이 맞아도 중간에 완료된 읽기가 틀렸을 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 읽기와 쓰기

  • 호출과 응답

  • 사건의 앞뒤

학습 목표

  • 단일 레지스터의 순차 규약을 적는다.

  • 겹침과 실시간 앞뒤를 구별하여 이력을 검사한다.

  • 유한 이력 통과의 한계를 설명한다.

먼저 허용되는 순차 동작을 정한다

초기 값이 0인 레지스터 하나를 정한다. write(1)은 값을 1로 바꾸고, read는 그 순차 시점의 값을 반환한다. 선형화 가능성은 각 완료 연산을 호출과 응답 사이의 한 시점에서 일어난 것처럼 순서화할 수 있는지를 검사한다.

한 연산의 응답이 다른 연산의 호출보다 먼저라면 그 앞뒤는 지켜야 한다. 서로 겹친 두 연산은 호출 시각만으로 순서를 고정하지 않는다. 여기서는 하나의 객체만 다루며 여러 객체 트랜잭션의 보장과 혼동하지 않는다.

최종 상태만 검사하면 놓치는 것

write(1)이 성공한 뒤 시작한 read가 0을 반환했다면 이후 읽기가 1이어도 앞선 잘못된 관찰은 남는다. 검사에는 요청 ID·호출 사건·응답 사건·반환 값이 필요하다.

비교하는 사건의 앞뒤를 신뢰할 수 있어야 한다. 서로 다른 장비의 동기화되지 않은 시계 숫자만 정렬하여 실시간 순서를 확정하지 않는다. 아래 시간은 하나의 신뢰하는 관찰 시계에서 적은 자체 값이다.

미확정 연산과 검사의 범위

시간 초과로 응답을 받지 못한 쓰기는 적용되지 않았다고 자동 삭제하지 않는다. 가능한 완료나 미적용 경우를 규약에 맞게 검토해야 한다. 이 절의 첫 계산은 모든 연산이 완료된 작은 이력만 다룬다.

한 유한 이력이 통과했다는 말은 지정한 입력과 장애 및 관찰에서 반례를 찾지 못했다는 뜻이다. 모든 미래 실행을 증명했다는 뜻은 아니다. 잘못된 규약이나 누락된 이력으로 검사하면 판정 자체가 부정확해진다.

중간 과정을 따라가는 예제

초기 값 0에서 W=write(1)의 호출/성공 응답이 0/4, R=read의 호출/응답이 5/6이다. R은 0을 반환했다. 순차 규약으로 설명할 수 있는가?

  1. W의 응답 4가 R의 호출 5보다 앞이므로 W를 R보다 먼저 두어야 한다.

  2. 순서 W→R에서 마지막 쓰기는 1이다. R의 반환 값은 1이어야 한다.

  3. 관찰된 0과 충돌한다. R을 W 앞으로 옮기면 실시간 조건을 위반하므로 다른 순서로도 해결되지 않는다.

이 완료 이력은 레지스터의 선형화 가능성 조건에 실패한다. 최종 저장 값만 다시 1로 맞춰도 이 읽기 반례는 사라지지 않는다.

종이와 본문으로 직접 해보기

R의 호출/응답을 2/3으로 바꾸면 0과 1 중 어떤 반환이 가능한가? W의 응답을 시간 초과로 바꾼 별도 이력에서 R=1이면 W는 반드시 미적용인가?

힌트 보기

겹친 W와 R은 두 순서 후보를 고려한다.

풀이 보기

겹침에서는 R→W가 0, W→R이 1을 설명한다. 각각 연산 구간 안에 순차 시점을 놓을 수 있다. 시간 초과는 미적용 확정이 아니며 R=1은 W가 적용된 가능한 설명과 맞을 수 있다.

오해와 반례

호출 순서대로 정렬하거나 마지막 값만 맞추면 일관성이 검증된다.

겹침에는 다른 순서가 가능하고 완료 읽기마다 규약을 만족해야 한다. 호출·응답과 값 전체를 함께 검사한다.

자기점검

W 응답 4 뒤 R 호출 5면 순서는?

답과 이유 보기

W가 R보다 앞이다.

실시간 앞뒤를 보존한다.

겹친 연산은 호출 순서를 반드시 지켜야 하는가?

답과 이유 보기

아니다.

각 구간 안의 선형화 시점 순서를 찾는다.

소단원 13.3

로그·추적·재현

서로 다른 서버의 로그 시각을 정렬하면 요청이 지나간 순서가 정확히 나올까?

준비 개념과 학습 목표

준비 개념

  • 요청 식별자

  • 시계 오차

  • 로그와 사건

학습 목표

  • trace와 span의 역할을 구별한다.

  • 시계 정렬과 인과 관계를 구별한다.

  • 재시도와 재현 정보를 같은 사건 표에 기록한다.

같은 요청을 이어 주는 식별자

분산 추적의 trace는 요청이 여러 구성 요소를 지나는 작업을 연결한다. span은 개별 작업이며 자신의 span ID와 trace ID를 가진다. 자식 span에는 부모 span ID가 있고 root span에는 부모가 없다. 문맥 전달이 있어야 다른 프로세스에서 생성한 작업을 연결할 수 있다.

같은 trace ID라는 사실만으로 모든 작업의 실행 순서가 결정되지는 않는다. 부모·자식, 송신·수신, 작업 의존 관계를 함께 본다. 비동기 작업은 span link로 관련 작업을 연결할 수도 있다.

시계와 로그의 한계

기계마다 시계 오차가 있으면 실제 먼저 보낸 사건의 표시 시각이 나중에 받은 사건보다 클 수 있다. 메시지 송신이 그 메시지 수신보다 먼저라는 인과 관계와 숫자 시각 정렬을 구별한다.

누락·샘플링·수집 실패가 있으면 trace가 전체 이력을 담지 못할 수 있다. 기록이 없다는 사실만으로 작업이 실행되지 않았다고 결론 내리지 않는다. 일반 추적 화면과 일관성 검사에 필요한 완전한 연산 이력은 목적과 범위가 다르다.

다음 사람이 확인할 수 있는 기록

원 요청 식별자는 재시도에도 유지하고 각 시도의 번호는 따로 적는다. 서버의 적용 판정 및 응답 결과를 구별하면 한 요청의 두 시도를 서로 다른 업무로 잘못 세는 일을 줄일 수 있다. 식별자만 적었다고 자동으로 중복 적용이 막히는 것은 아니다.

재현 명세에는 입력·프로그램 버전·초기 상태·노드 구성·실패 일정·기대 조건·실제 관찰·누락 정보를 함께 둔다. 비밀 토큰이나 개인정보를 무작정 로그에 복제하지 않는다. 이 수업의 표는 가상이며 실제 서비스를 수집하지 않았다.

중간 과정을 따라가는 예제

같은 trace T의 부모 span P에서 서버 A가 메시지를 송신할 때 표시 시각은 105다. 자식 span Q에서 B가 그 메시지를 수신한 표시 시각은 101이다. 자체 시계 모형에서 A는 실제 시간보다 5만큼 빠르고 B는 2만큼 느리다. 실제 시간과 인과 순서를 계산하라.

  1. A 표시 = 실제 + 5이므로 송신 실제 시간은 105 − 5 = 100이다.

  2. B 표시 = 실제 − 2이므로 수신 실제 시간은 101 + 2 = 103이다. 실제 전달 간격은 3이다.

  3. 표시 숫자만 정렬하면 수신 101이 송신 105보다 먼저처럼 보인다. 보정 모형과 메시지 식별자의 인과 관계는 송신→수신을 지지한다.

  4. 실제 환경에서 오차 값을 모르면 이처럼 정확한 간격을 계산할 수 없다. 같은 trace와 부모 관계는 연결 근거이며 정확한 글로벌 시계의 보장이 아니다.

자체 오차 가정 아래 실제 송신/수신은 100/103이다. 인과 관계와 보정 없는 표시 시각 정렬을 분리해야 한다.

식별 기록과 실제 서버의 중복 판정 기능은 다르다.

풀이 보기

자동 중복 판정 계약과 적용 기록이 없으면 한 번 적용을 확정하지 못한다. 시도 두 개와 업무 적용 수는 다르다. Q 누락 역시 수집 누락일 수 있어 미실행 확정이 아니다.

오해와 반례

같은 trace ID와 정렬된 로그가 있으면 완전한 실행 증거다.

연결에는 문맥과 관계가 필요하고 누락이나 시계 차이가 남을 수 있다. 검사 목적에 충분한 기록인지 별도로 확인한다.
