소단원 12.1

GFS·Spanner·키값 저장 비교

큰 파일 분석·두 계정의 원자적 수정·장바구니 한 항목 저장에 같은 저장 규칙을 적용해야 할까?

준비 개념과 학습 목표

준비 개념

  • 복제와 분할

  • 파일·행·키값

  • 트랜잭션과 일관성

학습 목표

  • 세 논문의 자료 단위와 목표를 비교한다.

  • 동기 복제·충돌 해소·외부 일관성을 구별한다.

  • 과거 논문 설계와 현재 제품·자체 실험을 구별한다.

자료 단위가 출발점이다

2003 GFS는 큰 파일의 연속 읽기와 append가 많은 내부 분석 워크로드에서 출발했다. 파일을 chunk로 나누고 master가 이름·파일과 chunk 관계 등 메타데이터를 관리하며 실제 데이터는 chunkserver와 주고받는다. POSIX의 모든 의미를 구현한 파일시스템으로 일반화하지 않는다.

2012 Spanner 논문은 다중 버전의 행과 키를 여러 Paxos 그룹으로 복제하고 일반 목적 트랜잭션과 query 계층을 얹는다. 2007 Dynamo 논문은 한 키의 작은 객체 get/put과 높은 가용성을 우선하며 충돌 버전과 응용 해소를 노출한다. 모두 분산 저장이지만 같은 자료·질의·트랜잭션 단위를 제공하지 않는다.

이름이 비슷한 보장을 분리한다

GFS의 record append는 record 하나를 원자적으로 적어도 한 번 추가하는 의미다. 실패 후 재시도에 중복이 나타날 수 있어 exactly-once 전체 응용 처리라고 읽지 않는다. 일반 덮어쓰기와 append의 보장도 다르다.

Spanner의 외부 일관성은 한 트랜잭션이 커밋한 뒤 다른 트랜잭션이 시작하면 그 순서를 직렬화 순서에 반영하는 성질이다. TrueTime은 오차 없는 점시계가 아니라 참 시간을 포함하는 구간을 제공한다. 복제·잠금·커밋 프로토콜과 대기가 함께 필요하다. Dynamo는 장애 중의 쓰기와 이후 충돌 해소를 다루며 모든 업데이트가 즉시 하나의 최신값으로 보인다고 주장하지 않는다.

요구사항으로 설계를 평가한다

대용량 분석 결과 파일, 함께 갱신할 여러 행, 한 키 장바구니는 서로 다른 요구를 준다. 특정 논문의 설계가 요구를 설명하는 데 유용해도 오늘의 서비스를 비교 구매하는 권고나 모든 구현에 대한 성능 순위를 제공하지 않는다.

아래 예제는 요구와 논문의 보장 범위를 대조한 자체 시나리오다. 이름만 골랐다고 장애·중복·보안·복구가 구현된 것은 아니다. 키값 저장은 넓은 범주이며 모든 키값 시스템이 Dynamo와 같은 약한 보장을 갖는 것도 아니다.

중간 과정을 따라가는 예제

자체 요구 A는 큰 분석 파일에 record를 추가하되 재시도 중복을 식별해야 한다. B는 계정 두 행을 (10,20)에서 (7,23)으로 바꾸면서 읽는 쪽에 (7,20)이 보이지 않게 한다. C는 한 키의 장바구니가 분리된 두 곳에서 각각 {책}과 {연필}로 수정되어 합칠 정책을 요구한다. 세 논문에서 어떤 의미를 살펴야 하는가?

  1. A는 GFS record append의 적어도 한 번 보장을 읽고 자체 record ID·중복 판정 등의 응용 설계를 따로 붙여야 한다. 이를 정확히 한 번이라고 바꾸지 않는다.

  2. B는 합계 30을 보존하는 두 행 원자 수정과 읽기 의미가 필요하므로 Spanner의 분산 트랜잭션을 살펴볼 수 있다. 중간 (7,20)의 합은 27이라 요구를 어긴다. 단일 키 put 두 번으로 자동 해결되지는 않는다.

  3. C는 Dynamo의 여러 충돌 버전 반환과 응용 해소가 관련된다. 단순 집합 합치기는 {책,연필}이지만 삭제 의미를 표현하지 못할 수 있으므로 실제 정책의 정의가 필요하다.

자료 단위·원자 범위·재시도·충돌 정책을 각각 확인한다. 이 대응은 요구 비교이며 세 저장 시스템의 실행·운영 성공 결과가 아니다.

종이와 본문으로 직접 해보기

C에서 한 곳이 {책}에서 책을 삭제하고 다른 곳은 {책,연필}로 수정했다. 두 최종 집합을 단순 합치면 결과는? Spanner의 커밋 시간 s = 104에서 TrueTime의 earliest가 103, 104, 105인 세 상태에 대해 s가 확실히 지나갔는지 구별하라.

힌트 보기

집합 합집합은 삭제한 흔적을 모른다. 이 모형은 earliest > s일 때만 확실히 지난 것으로 본다.

풀이 보기

∅ ∪ {책,연필} = {책,연필}이라 삭제 의도를 자동 보존하지 못한다. 삭제를 어떻게 표현·충돌 해소할지 따로 정해야 한다. earliest 103과 104에서는 아직 통과하지 않고 105에서만 s < earliest가 된다. 이는 대기 조건의 종이 예제이지 실제 TrueTime 측정이 아니다.

오해와 반례

분산 복제가 있으므로 세 시스템은 모두 여러 키의 최신값을 즉시 원자적으로 제공한다.

논문의 자료·복제·트랜잭션 의미가 다르다. GFS append와 Spanner 트랜잭션, Dynamo의 한 키 충돌 해소를 같은 보장으로 합치지 않는다. 복제 개수만으로 원자 범위와 읽기 의미가 결정되지 않는다.

소단원 12.2

이름·메타데이터·배치

파일 이름을 알면 곧바로 저장 서버의 주소와 읽을 데이터도 알 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 논리 이름과 물리 위치

  • 분할 단위와 복제본

  • 정수 나눗셈·나머지

학습 목표

  • 이름 해석·메타데이터 경로·데이터 경로를 구별한다.

  • 범위·hash 배치가 locality와 변경에 미치는 영향을 설명한다.

  • chunk 번호와 내부 오프셋을 계산한다.

어디 있는지와 내용은 다른 메시지다

GFS 클라이언트는 파일 이름과 chunk index로 master에 위치 정보를 묻고, chunk handle과 복제 위치를 받은 다음 chunkserver에 byte 범위를 요청한다. master가 모든 파일 내용을 중계하는 구조가 아니다. 클라이언트의 메타데이터 캐시도 유효기간과 상태 변화를 다뤄야 한다.

GFS master의 이름과 파일→chunk 관계는 로그로 보존하지만 chunk 위치는 시작 시 chunkserver에게 재발견한다. 모든 메타데이터 항목의 영속 방식이 똑같지 않다. 아래 chunk 크기 10은 계산을 위한 자체 모형이며 논문의 실제 크기가 아니다.

배치 단위로 가까운 자료를 묶는다

Spanner 논문의 directory는 공통 키 접두어를 공유하는 자료의 배치 추상화다. 파일시스템의 디렉터리와 완전히 같은 뜻으로 사용하지 않는다. 관련 행을 함께 두면 통신을 줄일 수 있지만 한 묶음이 뜨거워지면 배치 조정이 필요하다.

논문에서는 설명을 단순화한 directory 단위 이동 뒤에, 큰 directory는 fragment로 나눌 수 있다고 명시한다. 전체 사용자 자료가 언제나 하나의 물리 서버에 고정되어 있다고 단정하지 않는다. 위치 이동 중에도 접근을 제공하려면 프로토콜과 메타데이터 갱신이 필요하다.

hash는 이름을 다른 위치 기준으로 바꾼다

Dynamo는 키를 hash ring 위치로 보내고 여러 물리 노드와 가상 노드를 이용해 배치와 복제를 다룬다. range 배치는 인접 키의 locality를 활용할 수 있고 hash 배치는 키 순서와 물리 순서를 다르게 만든다. 어느 쪽도 실제 요청이 자동 균등해지는 보장은 아니다.

아래 한 노드 한 토큰의 작은 ring은 clockwise 배치 직관만 보여 준다. 실제 Dynamo의 가상 노드·preference list·복제·장애 handoff를 구현한 것이 아니다. 하나의 인기 키에 요청이 집중되는 문제는 키의 개수를 고르게 나눴다는 사실만으로 사라지지 않는다.

중간 과정을 따라가는 예제

자체 파일은 25바이트이고 chunk 크기는 10바이트다. 파일 오프셋 23은 몇 번 chunk의 내부 몇 번인가? 또 ring [0,100)에서 토큰 A = 20, B = 60, C = 90이고 key hash는 10,35,70,95다. 첫 시계방향 토큰에 배치하라. 모든 hash는 토큰과 다르다.

  1. 0부터 세는 chunk는 [0,10), [10,20), [20,25) 세 개다. 23 // 10 = 2, 23 % 10 = 3이므로 chunk index 2의 내부 오프셋 3이다.

  2. 10은 A20, 35는 B60, 70은 C90으로 간다. 95는 ring 끝을 돌아 A20으로 간다.

  3. 자료가 실제로 읽히려면 해당 chunk handle과 접근 가능한 복제본 등의 정보를 알아야 한다. ring의 단순 결과는 1차 배치이며 복제 대상까지 구한 것은 아니다.

세 chunk이며 오프셋 23은 index 2·내부 3이다. 키 순서 10/35/70/95의 배치는 A/B/C/A다.

힌트 보기

35의 첫 시계방향 토큰만 바뀌는지 본다. 실제 파일은 필요한 내용 길이만 셌다고 가정한다.

풀이 보기

새 배치는 A/D/C/A이며 네 키 중 35만 B에서 D로 이동한다. 내용 25바이트를 세 번 저장하면 75바이트다. 디스크 block·메타데이터·로그·빈 공간은 제외했고 실제 GFS가 각 chunk를 무조건 10바이트로 채웠다는 가정도 하지 않는다.

오해와 반례

hash로 나눴으므로 한 키가 인기 있어도 모든 노드가 같은 요청 수를 처리한다.

같은 키의 hash는 같은 배치 기준을 만든다. 그 키 요청이 몰리면 담당 노드나 복제본에 집중될 수 있다. 요청 분산과 복제·캐시·읽기 정책을 따로 고려한다.

소단원 12.3

가용성·비용·복잡성

복제 수를 늘리면 저장량만 늘어날까, 아니면 응답과 복구 규칙도 달라질까?

준비 개념과 학습 목표

준비 개념

  • 복제와 장애 영역

  • 읽기·쓰기 정족수

  • 자료량과 전송량

학습 목표

  • 가용성·내구성·일관성·응답 지연을 분리한다.

  • 고정 복제 집합의 정족수 교집합 조건과 한계를 설명한다.

  • 용량·복구 전송·운영 복잡성의 단순 비용을 계산한다.

무엇이 실패해도 무엇을 지킬지 정한다

가용성은 요청에 응답할 수 있는 조건, 내구성은 저장한 내용의 손실을 견디는 성질, 일관성은 여러 관측을 어떤 순서와 값으로 설명할지를 다룬다. 응답 지연과 처리량도 별도 지표다. 복제는 도움이 되지만 같은 전원·랙·자격 증명·운영 오류의 공통 장애가 모든 복제본에 영향을 줄 수 있다.

일관된 쓰기에 정족수나 조정자가 필요하면 분할된 소수 측이 정상처럼 응답하지 못할 수 있다. 응답을 계속 주는 설계는 충돌 버전과 응용 해소 부담을 노출할 수 있다. 논문의 목표·실패 조건을 빼고 어느 시스템이 절대 가용하다고 말하지 않는다.

교집합의 산술과 프로토콜 보장은 다르다

고정된 N개 복제 집합에서 쓰기가 W개, 읽기가 R개 응답을 쓰고 R + W > N이면 두 집합은 반드시 겹친다. 겹침이 없다면 두 집합 원소 수 R + W가 N 이하이어야 하기 때문이다.

이 산술만으로 선형화 가능성이 증명되지는 않는다. 최신 버전 선택·동시 쓰기·장애·멤버십 변경·재시도와 프로토콜이 필요하다. Dynamo의 sloppy quorum은 장애 시 원래 상위 N개 밖의 건강한 노드도 사용하므로 고정 집합의 교집합 논증을 그대로 적용할 수 없다.

응답 비용과 복구 비용을 나눈다

복제는 내용 저장량·쓰기 전송·검증·재동기화와 모니터링을 늘린다. 빠른 읽기를 위해 가까운 복제본을 쓸 수 있어도 원하는 일관성·시점에 충분히 최신인지 확인해야 한다. 한 지역 장애를 견디려면 복제 배치와 경로도 중요하다.

아래 단순 비용 표는 압축·메타데이터·로그·읽기·요금·단계별 프로토콜을 제외한 계산이다. 실제 비용 예측이나 현재 클라우드 가격이 아니다. 오류 복구·출처 기록·보안·관측·충돌 해소 코드도 복잡성 비용이며 자료 바이트 합 하나로 비교가 끝나지 않는다.

중간 과정을 따라가는 예제

자체 고정 집합 {A,B,C}의 N = 3, R = W = 2를 둔다. 가능한 두 원소 집합은 AB,AC,BC다. 모든 읽기·쓰기 조합에서 겹침을 확인하라. 내용 40 GiB를 세 곳에 복제하고 모두 내용만 저장한다면 총 내용 용량은? 하루 새 내용 2 GiB를 1차에서 나머지 두 곳으로 각각 전송하는 단순 모형의 원격 전송량은?

  1. AB∩AC={A}, AB∩BC={B}, AC∩BC={C}이며 같은 집합끼리는 두 원소가 겹친다. 아홉 순서 조합 모두 적어도 하나가 겹치고 R + W = 4 > 3이다.

  2. 내용 용량은 40·3 = 120 GiB다. 원격 두 복제본에 2 GiB씩 보내면 4 GiB다. 처음 클라이언트 업로드는 이 원격 전송 합에 포함하지 않았다.

  3. 복제 하나를 잃고 남은 내용으로 같은 복제본을 다시 만들려면 이 단순 모형에서 40 GiB 복구 내용 전송이 필요하다. 실제 단계·압축·로그·retry는 다를 수 있다.

아홉 조합 모두 교집합이 있고 단순 용량 120 GiB·하루 원격 4 GiB·전체 복제 복구 40 GiB다. 강한 읽기·쓰기 의미나 장애 성공률을 이 숫자에서 추론하지 않는다.

종이와 본문으로 직접 해보기

N = 3에서 R = W = 1이면 겹치지 않는 응답 예를 만들라. 고정 3개가 2개 측과 1개 측으로 분리되고 두 응답이 필요한 쓰기라면, 각 측이 즉시 정족수를 구성할 수 있는가?

힌트 보기

읽기 A·쓰기 B를 선택한다. 도달 가능한 노드 수와 W = 2를 비교한다.

풀이 보기

읽기 {A}와 쓰기 {B}는 겹치지 않는다. 2개 측은 노드 수만 보면 정족수 후보가 있지만 리더·프로토콜·타이밍 조건이 별도로 필요하다. 1개 측은 고정 집합에서 두 응답을 모을 수 없어 성공을 보장하지 못한다. Dynamo의 대체 노드를 허용하는 경우는 이 고정 집합 모형과 다르다.

오해와 반례

R + W > N이면 모든 분할과 동시 쓰기에서도 최신값을 즉시 읽으며 서버 실패도 무제한 견딘다.

고정 집합의 교집합 산술과 전체 프로토콜 보장은 다르다. 응답 가능 수가 부족하거나 집합이 바뀌거나 여러 버전이 생기면 추가 처리가 필요하다. 실패 영역·읽기 정책·복구를 함께 정의해야 한다.
