소단원 2.1

주기·실행시간·마감

매 10밀리초에 한 번 하는 일이 2밀리초 걸린다면 항상 마감도 만족할까?

준비 개념과 학습 목표

준비 개념

  • 시각은 시간 축의 위치이고 기간은 두 시각의 차이다. ms는 밀리초로 1초=1000ms다. [a,b)는a를 포함하고b를 제외하는 실행 구간이다.

  • 태스크는 반복될 수 있는 일의 흐름, job은 그 흐름의 요청 한 건이다. CPU 실행시간은 실제로 CPU를 쓴 기간의 합이고 대기시간과 다르다.

  • 자가진단: 시각 4에 요청해 시각 9에 끝나면 응답시간 5ms다. 그 사이 CPU를 2ms만 썼을 수도 있다.

학습 목표

  • release·완료·상대/절대 마감과 실행시간을 구별한다.

  • 주기 태스크의 요청별 시간표를 계산한다.

  • CPU 마감과 외부 효과 마감의 범위를 명시한다.

마감이 주기보다 길면 자기 요청은 어떻게 겹치나요?

자체 단일 단위 속도 CPU를 FIFO로 사용한다. 다른 태스크·선점·전환 비용·입출력은 없고 각 job은 정확히 4 ms 실행한다. 첫 release φ=1 ms, 주기 T=3 ms, 상대 마감 D=7 ms다. 처음 네 요청의 release는 1, 4, 7, 10 ms이고 실행 구간은 [1,5), [5,9), [9,13), [13,17)이다. 한 태스크라도 앞 job이 끝나기 전에 다음 job이 release될 수 있다.

네 완료는 5, 9, 13, 17 ms이고 응답은 4, 5, 6, 7 ms다. 절대 마감은 8, 11, 14, 17 ms이므로 네 요청은 모두 통과한다. 그러나 다음 요청은 13 ms에 release되어 21 ms에 완료하고 응답 8 ms로 마감 20 ms를 놓친다. D>T인 정의 자체가 잘못된 것은 아니지만, 앞 job이 남지 않는다는 분석 가정을 사용할 수 없다.

0부터 세는 k번째 요청은 r_k=1+3k, f_k=5+4k이므로 R_k=4+k ms다. 이용률 4/3이 1보다 커 장기 누적 수요가 처리 능력을 넘는다. 반대로 별도 단독 태스크의 C=2,T=3,D=1 ms는 이용률 2/3이어도 첫 job부터 실패한다. 이용률과 상대 마감은 서로 다른 검사를 요구한다.

태스크 한 줄보다 요청별 시간을 적는다

주기 태스크의 release 시각을 rₖ=φ+kT, k=0,1,2,…로 정의한다. T>0은 주기이고 φ는 첫 release 시각이다. 각 job의 CPU 실행 요구 eₖ≤C, 상대 마감 D>0, 절대 마감 dₖ=rₖ+D다. 완료 fₖ의 응답시간은 Rₖ=fₖ−rₖ이며 마감 충족은 fₖ≤dₖ, 곧 Rₖ≤D다.

C는 일정한 실제 실행시간이라고 꼭 가정하지 않는다. 이 단원의 상계 모형에서 eₖ가 C 이내라는 계약이다. D=T는 implicit deadline, D≤T는 constrained deadline이다. D>T도 정의 가능하지만 요청이 겹칠 수 있어 분석 조건을 바꿔야 한다. 주기만 정했다고 상대 마감이 주기와 같아지는 것은 아니다.

CPU 시간과 응답시간을 구별한다

두 job이 한 CPU를 나눠 쓰면 실행하지 못하는 시간도 응답시간에는 들어간다. 예제는 독립 태스크 A:(C,T,D)=(2,5,5), B:(3,10,10)ms, φ=0이고 A가 높은 고정 우선순위다. 단일 단위 속도 CPU에서 즉시 선점·전환 비용 0·자원 대기 0·입출력 0·release jitter0을 가정한다.

0~2에는 A₀,2~5에는 B₀가 실행된다. B₀의 CPU 시간은 3ms이지만 release0부터 완료 5까지 응답시간은 5ms다. 시각 5의 A₁은 5~7, A₂는 10~12에 실행된다. 시간표 끝에서 완료와 새 release가 같은 시각이면 앞 job 완료를 먼저 확정해 경계를 일관되게 처리한다.

요구하는 완료 지점의 범위를 적는다

CPU 함수의 끝 f를 측정하는 계약은 센서 사건에서 모터 반응까지의 마감과 다르다. 사건 전달 지연·큐·CPU 작업·네트워크·장치 반응을 포함하려면 전체 경로를 정의하고 각 상계나 결합 모형을 확보해야 한다. 이 단원의 f는 CPU job 완료만이다.

평균 이용률 U=ΣCᵢ/Tᵢ는 장기 요구 비율의 한 지표다. 위 예제 U=2/5+3/10=0.7이지만 0.7이라는 숫자 하나가 모든 마감·정책의 충족을 보장하지 않는다. 동시 도착·짧은 D·블로킹·높은 우선순위 간섭을 확인해야 한다. 이 시간표는 특정 입력의 종이 계산이지 실제 장치의 실시간 인증이 아니다.

자체 조건시각 또는 수요판정

네 요청의 release는 1,4,7,10 ms다.

완료는 각각 5,9,13,17 ms이고 응답은 4,5,6,7 ms다.

이 네 요청은 끝점 포함 마감을 통과한다.

다섯째 요청의 release는 13 ms다.

완료는 21 ms, 절대 마감은 20 ms다.

첫 실패는 다섯째 요청이다.

별도 C=2,T=3,D=1 ms다.

이용률이 1보다 작아도 마감은 실패한다.

실행은 반열린 구간이며 같은 태스크의 job도 각 ID로 유지한다. 숫자 k는 0부터 세므로 다섯째 요청은 k=4다.

중간 과정을 따라가는 예제

위 A,B 가상 CPU에서 첫 B job과 0~10ms의 실행을 추적하고 CPU 시간·응답시간·마감을 구한다.

  1. 0에서 A₀/B₀가 준비되며 높은 A를 0~2 실행한다.

  2. B₀를 2~5 실행해 완료 5다. e_B=3 ms, R_B=5ms다.

  3. 5에서 A₁을 5~7 실행하고 7~10은 CPU가 빈다. B₀의 d_B=10이므로 5≤10이다.

  4. A₀/A₁ 응답은 각각 2ms이며 각 D=5 이내다. 첫 10 ms 사용량 7ms로 이용 비율 0.7이다.

B₀는 실행 3 ms·응답 5 ms·절대 마감 10ms이며 충족한다. 첫 10ms의 표만으로 모든 임의 태스크 모델을 보장하지 않는다.

조건을 바꾸어 비교하기

네 번 통과 뒤의 첫 실패

주어진 FIFO 태스크에서 처음 실패하는 요청 번호를 구하라.

  1. R_k=4+k≤7이면 k≤3이다.

  2. k=4의 release는 13 ms, 완료는 21 ms, 절대 마감은 20 ms다.

다섯째 요청이 1 ms 늦는다.

비교할 점

유한 앞부분 통과를 무한 실행의 보장으로 바꾸지 않는다.

시간 원점 이동과 고정 외부 마감

첫 release를 6 ms로 옮기고 모든 요청의 상대 마감은 유지한다. 네 응답은 변하는가? 별도 첫 요청의 고정 외부 마감이 10 ms이면 어떻게 되는가?

  1. 모든 release와 완료가 5 ms씩 이동해 첫 완료는 10 ms다. 응답은 그대로 4,5,6,7 ms다.

  2. 첫 요청은 고정 외부 마감 10 ms에도 등호로 통과한다. 별도로 첫 release를 7 ms로 바꾸면 첫 완료가 11 ms라 고정 외부 마감에는 실패한다.

상대 응답은 이동에 불변이며 고정 절대 마감은 별도다.

비교할 점

절대 시각과 기간을 혼합하지 않는다.

WCET가 마감보다 작으면 어떤 스케줄에서도 마감을 지킨다.

C≤D는 단독 CPU 실행 가능성의 필요 조건이 될 수 있지만 대기와 간섭이 남는다. 활동은 e=3≤D=5인데 R=6이라 실패한다.

연습 1 · 값과 상태 예측

힌트 2

한 단계 더

심화: 한 job의 release~완료 구간에서 실행 e, 다른 작업 간섭 I, 대기/블로킹 B가 서로 겹치지 않고 다른 비용을 전부 포함하면 R=e+I+B다. 간섭과 대기를 중복 계산하지 않도록 분류해야 한다. C,I_max,B_max가 실제 모든 허용 경로를 상계한다면 R≤C+I_max+B_max이고 그 합≤D는 충분조건이다. 관측된 최고값을 근거 없이 각 상계로 쓰면 이 증명의 전제가 성립하지 않는다.

준비 개념과 학습 목표

준비 개념

  • 간격은 연속 release의 시각 차이다. 최소 간격은 모든 그런 차이가 특정 T 이상이라는 조건이며 평균 간격과 다르다.

  • FIFO는 먼저 들어온 요청부터 처리하는 순서다. 큐는 대기 요청을 보관하고, service는 CPU 시간을 제공하는 일이다.

  • 자가진단:0,7,15 ms 사이 간격은 7,8이다. 최소 간격 6을 지키지만 일정한 주기는 아니다.

학습 목표

  • aperiodic의 미지정 수요와 서비스 계약을 설명한다.

  • 도착·큐·마감의 종이 사례와 과부하 반례를 만든다.

최소 사건 간격이 CPU release에도 그대로 남나요?

자체 사건 시각은 0,6,12 ms로 정확히 6 ms 간격이다. 각 사건에서 CPU release까지 각각 선택할 수 있는 지연 j_k는 0≤j_k≤4 ms다. 지연 [4,0,4] ms를 적용하면 실제 release는 [4,6,16] ms이고 연속 간격은 2 ms와 10 ms다. 사건의 최소 간격 6 ms를 실제 release의 최소 간격이라고 그대로 쓰면 틀린다.

일반 식 r_(k+1)−r_k=(a_(k+1)−a_k)+j_(k+1)−j_k를 쓴다. 사건 간격이 최소 T이고 지연 범위가 [0,J]이면 release 간격의 하한은 T−J다. J<T인 경우 순서를 뒤집지 않고 양의 하한을 준다. J≥T이면 이 식은 양의 최소 간격을 보장하지 않으며 동시 release도 가능하다. 지연의 개별 상계와 실제 서비스의 CPU 대기는 별도다.

고정 프레임 [5k,5k+5)마다 CPU 예산 최대 2 ms인 별도 모형을 생각한다. [3,5)와 [5,7)에 각각 2 ms 쓰면 각 프레임 예산은 지키지만 창 [3,8) 안의 사용량은 4 ms다. 프레임 예산, 모든 슬라이딩 창의 예산, Sporadic Server의 전체 replenishment 계약은 동일하지 않다.

불규칙함에도 서로 다른 모형이 있다

sporadic 태스크는 rₖ₊₁−rₖ≥T>0인 최소 release 간격, 실행 상계 C, 상대 마감 D를 갖는 모형이다. 일정 간격 T인 periodic 요청은 이 조건도 만족한다. 간격이 더 길어질 수 있으므로 다음 job이 정확히T 뒤에 반드시 오는 것은 아니다. 모든 허용 도착열에 대한 보장은 한 번 관측한 열의 보장보다 강하다.

이 단원에서 aperiodic은 고정 주기나 알려진 최소 간격 하계 계약을 기본으로 주지 않은 불규칙 요청을 뜻한다. 자료에 따라 용어 범위가 다를 수 있어 선언한 조건으로 구분한다. 불규칙이라는 말 자체가 soft deadline을 뜻하지 않는다. hard 마감이 있다면 추가 도착/수요 제한이나 admission 계약을 확보해야 한다.

도착을 제약하거나 서비스를 제약한다

sporadic 요청 C=2,T=6,D=4ms가 단독 단위 CPU에서 즉시 FIFO 실행된다고 하자.0,7,15 release는 간격 7/8로 합법이다. 각각 0~2,7~9,15~17 완료라 응답 2≤4다. 이전 job은 2 ms 내 완료하고 다음 release는 6 ms 이후여서 겹치지 않는다.

요청이 0,1,2에 각각 2 ms 필요하고 D=3이면 단독 FIFO라도 완료 2,4,6이라 응답 2,3,4다. 셋째는 실패한다. 이것은 T=6 sporadic 계약에 어긋난 도착열이며 그 계약의 보장이 실패했다는 반례가 아니다. 최소 간격 없는 aperiodic 수요를 제한 없이 높은 우선순위에 놓는 위험을 보여 준다.

예산은 도착 약속과 다르다

서버는 큐의 aperiodic 작업에 CPU 예산을 배정하고 다른 태스크에 주는 간섭을 제한할 수 있다. 하지만 도착량·요청 크기가 무제한이면 제한된 service로 모든 요청의 유한 응답 마감을 보장할 수 없다. 버퍼 용량·거절·지연 허용·우선순위·서비스 하계를 함께 정해야 한다.

예를 들어 고정 프레임 [5k,5k+5)마다 최대 2ms만 쓰는 가상 예산은 장기 비율 0.4를 제한한다. 프레임 말미와 다음 시작에 몰아 쓰면 짧은 경계 교차 창에서 4ms가 될 수 있으므로 모든 5 ms 슬라이딩 창의 2 ms 보장과 같지 않다. 이것을 완전한 Sporadic Server 알고리즘이라고 부르지 않는다. 실제 서버의 replenishment/overhead 규칙은 따로 확인한다.

같은 CPU 작업량도 조각 수에 따라 간섭이 달라지나요?

자체 비용 장부에서 높은 작업의 유효 CPU 요구 총합은 2 ms다. 각 조각이 낮은 작업을 한 번 선점하고 끝나면 낮은 작업으로 돌아온다고 정한다. 들어가는 전환과 돌아오는 전환의 비용은 각각 σ=0.1 ms다. 조각 하나면 전환 두 번으로 전체 간섭은 2.2 ms이며, 다섯 조각이면 전환 열 번으로 전체 간섭은 3 ms다. 총 유효 작업량만 같다고 간섭이 같지는 않다.

낮은 작업의 CPU 요구는 4 ms이고 마감은 release에서 6.5 ms라고 하자. 높은 조각과 전환을 낮은 작업의 완료 전에 모두 넣고 다른 비용은 없다고 정한다. 한 조각의 낮은 응답은 6.2 ms라 통과하고 다섯 조각의 응답은 7 ms라 실패한다. 두 장부는 명시적으로 달성되는 자체 이력이며 모든 실제 OS의 전환 비용 인증이 아니다.

상계 계약으로 최대 조각 수 q를 확보하면 간섭은 2+2qσ ms로 제한한다. 낮은 응답 상계는 6+0.2q ms이고 6.5 ms 이내 조건은 정수 q≤2다. 조각 수에 아무 상계도 없으면 σ>0일 때 유효 CPU 예산 2 ms만으로 전환 간섭의 유한 상계를 만들 수 없다. 실제 교재의 전환 비용·캐시 비용을 포함해야 한다는 설명을 이 작은 장부로 적용한다.

최악이라는 말의 집합을 먼저 정한다

WCET는 지정한 프로그램·입력/상태·플랫폼 조건의 실행 CPU 시간 상계다. 어떤 경로·메모리 대기·캐시·컴파일 옵션·클록·전력 상태를 허용하는지 없으면 숫자의 의미가 불명확하다. 측정 기반 추정과 증명된 상계는 구별하며 실제 측정 최대가 자동 WCET가 되지 않는다.

최악 응답시간은 여기에 release 배치·다른 태스크의 간섭·블로킹·스케줄러 비용·jitter를 포함한다. 한 job의 CPU 상계C만으로 전체 R을 결론내리지 않는다. 하드 마감 보장은 선언한 모든 허용 조건에 대해 필요하며 관측된 평균·백분위는 통계 목표의 근거가 될 수 있어도 같은 논리의 전칭 보장은 아니다.

자체 두 태스크 모형의 상계를 계산한다

예제는 단일 CPU·단위 속도·독립·즉시 선점·비용 0·jitter0·self-suspension0·블로킹 0, 더 높은 H:(C,T,D)=(1,4,4)ms, 낮은 L:(3,10,6)ms다. 동시에 0에 release하고 각각 실행 상계만큼 사용한다. H는 0~1, L은 1~4에 완료한다.4에서 도착한 다음 H는 L 완료 이후라 L에 간섭하지 않는다.

길이 R>0인 [0,R)에서 H의 최대 도착 수는 ceil(R/4)다. 앞선 미완료 L job이 없는 조건으로 첫 낮은 job의 busy window를 잡으면 반복 w₀=C_L, wₖ₊₁=C_L+ceil(wₖ/T_H)C_H가 대기 중 높은 작업량을 포함한다.3→4→4라 고정점 4이며 D_L=6 이내다. 이는 선언한 두 태스크 조건에서 사용하는 상계다. 다중 CPU·임의 jitter·D>T 겹친 자기 요청에 그대로 쓰지 않는다.

비용을 바꾸면 결론도 바뀐다

C_L을 5로 바꾸면 5→7→7이고 H0~1, L1~4, H4~5, L5~7이다. L의 CPU5ms와 응답 7ms를 구별하며 D_L=6을 놓친다. 그럼에도 U=1/4+5/10=0.75<1이다. 장기 이용률이 1보다 작다는 필요 검사는 짧은 마감의 충분 검사가 아니다.

실제 시스템에는 전환·인터럽트·비선점 구간·캐시 재충전 등의 추가 간섭이 있다. 안전 여유를 막연히 더하는 대신 각 비용의 발생 수와 상계, 중복 여부를 기록해야 한다. 자료에서 제시한 이론의 플랫폼 조건과 실제 실행 계약이 대응하지 않으면 수학적으로 맞는 표도 구현 보장으로 이전되지 않는다.

심화 논증: 함수 F(w)=C_L+ceil(w/T_H)C_H는 비감소다. w₀=C_L이고 C_H≥0이면 반복은 비감소한다. 고정점이 D_L 이내에 도달하고 위 조건에서 다른 비용/자기 carry-in이 없다면 높은 태스크가 만들 수 있는 요청량을 포함한 busy-window 상계로 사용한다. w가 D_L를 넘어도 시험의 실패와 모든 정책의 불가능성은 구별해야 한다. 본 활동은 명시된 정책에서 실제 허용 동시 release 시간표가 마감을 놓침을 따로 보여 실패를 확정한다. 종이 모형의 계산 정확성과 실제 입력·실행시간 상계의 확보는 별개의 검증이다.
