소단원 9.1

세마포어·mailbox·FIFO

신호가 세 번 왔다는 사실과 세 개의 측정값을 저장했다는 사실은 같을까?

준비 개념과 학습 목표

준비 개념

  • 생산자는 정보를 만들고 소비자는 처리한다.

  • 큐는 데이터와 그 순서를 유지한다.

학습 목표

  • 횟수 통지와 데이터 전달을 구별한다.

  • 자료 구조의 수명·호환성·대기 조건을 비교한다.

사건 개수를 보존하면 사건마다 다른 자료도 보존될까요?

기본의 공유 값 알림을 확장한 자체 모형에서 세마포어의 초기 count는 0이고 limit는 3입니다. 생산자는 공유 칸을 차례로 10,20,30으로 덮어 쓰며 매번 give합니다. 소비자가 아직 실행하지 않았다면 count는 3이지만 공유 칸은 하나이고 값은 30입니다. 소비자가 take를 세 번 성공한 뒤 매번 그 칸을 읽어도 결과는 30,30,30입니다. count가 보존한 것은 성공한 알림 횟수이며 과거의 값 10과 20은 저장하지 않았습니다.

Zephyr FIFO는 항목 순서를 보존하지만 항목 자체의 저장 수명과 중복 삽입 금지를 별도로 지켜야 합니다. 첫 포인터 크기 영역을 커널 연결에 예약하는 일반 put 항목과 alloc_put의 별도 연결 할당도 구별합니다. 다음 종이 모형은 서로 다른 항목 A와 B를 먼저 넣고 소비자가 없을 때는 A,B 순서로 꺼냅니다. 반면 두 소비자가 비어 있는 FIFO에서 기다리면 같은 항목을 두 소비자에게 복제하지 않습니다. 가장 높은 우선순위의 대기자가 먼저 받고 동률에서는 오래 기다린 대기자가 먼저 받습니다. 이는 항목의 FIFO 순서와 다른 선택 규칙입니다.

mailbox의 동기 send 타임아웃은 수신자가 메시지를 받기까지의 대기를 제한합니다. 수신자가 자료 복사를 뒤로 미루면 send는 자료 회수 완료까지 더 기다릴 수 있습니다. 자체 정확 시간표에서 송신 시작은 0 ms, 수신자의 메시지 접수는 4 ms, 자료 회수 완료는 9 ms이고 접수 타임아웃은 5 ms입니다. 접수는 제때지만 동기 송신의 완료는 9 ms입니다. 이를 전체 송신 완료가 5 ms 이하라는 보장으로 바꾸지 않습니다.

    기본의 limit와 공유 값 사례에서 count가 무엇을 보존하는지 먼저 확인합니다.

  • 전달 자료의 수명

    자료를 복사하는지 참조를 넘기는지에 따라 송신자가 저장 공간을 다시 써도 되는 시점이 달라집니다.

세마포어는 횟수와 허가

counting semaphore는 가능한 take 횟수를 count로 유지한다. count가 0이면 즉시 take를 할 수 없으며 thread는 대기 여부를 선택한다. give는 limit까지 count를 올린다. limit 1이면 여러 give가 처리 전에 합쳐질 수 있다.

세마포어 안에 측정값 자체가 자동 저장되는 것은 아니다. 값 10/20/30을 세 번 통지해도 단일 변수에 30만 남으면 이전 값은 복구할 수 없다. 값 보존이 필요하면 큐 등 별도 데이터 경로를 설계한다.

FIFO는 항목 순서와 수명

FIFO는 먼저 넣은 항목을 먼저 꺼내는 데이터 순서를 뜻한다. Zephyr FIFO는 연결된 item을 다루며 같은 item을 꺼내기 전에 다시 넣지 않는다. 항목의 메모리가 유효하고 사용 중 덮이지 않도록 해야 한다.

FIFO 데이터 순서와 대기 thread를 어느 우선순위로 깨우는지는 다른 질문이다. 이름만으로 모든 thread가 공정하게 같은 순서로 실행된다고 결론 내리지 않는다. fixed-size copy인 message queue와 item 수명 관리도 다르다.

mailbox의 만남 조건

Zephyr mailbox는 thread 사이에서 상대 조건을 맞추어 메시지를 전달한다. 수신자를 B로 지정한 A의 메시지를 C가 대신 받지 못한다. 이 API는 ISR용 일반 통신 수단이 아니다. mailbox란 말의 의미는 RTOS마다 다를 수 있다.

동기 전송에서는 데이터 회수가 끝날 때까지 기다리는 구간을 확인한다. 송신자가 지정한 timeout은 상대가 메시지를 받을 때까지의 대기만 제한하며 전체 전송 완료의 최대 시간을 보장하지 않을 수 있다. 실시간 설계에서는 API 이름뿐 아니라 완료 조건과 최악 지연을 읽어야 한다.

중간 과정을 따라가는 예제

소비자가 아직 실행되지 않았다. 초기 count 0/limit 1 세마포어에 give가 세 번 발생한다. 매번 공유 변수에 10,20,30을 순서대로 써 놓았다. 소비자가 그 뒤 nonblocking take를 두 번 시도하면 결과는? 별도 FIFO에 서로 다른 항목 10/20/30을 넣은 경우와 비교하라.

  1. 첫 give 후 count 1, 둘째·셋째는 limit 1을 넘지 않아 count 1이다. 공유 변수 최종값은 30이다.

  2. 첫 take 성공으로 count 0, 둘째 take는 즉시 실패한다. 값 10/20은 공유 변수에 남아 있지 않다.

  3. FIFO에 유효한 서로 다른 항목을 넣었다면 첫 세 get 결과는 10→20→30이다.

  4. 세마포어의 처리 가능한 통지 1개와 FIFO의 보존 데이터 3개는 같지 않다.

take 성공 1/실패 1, 단일 변수 30이다. 별도 FIFO는 항목 10/20/30을 순서대로 보존한다.

조건을 바꾸어 비교하기

count가 충분해도 과거 값은 사라진다

위 생산 뒤 소비자가 세 번 take하고 매번 공유 칸을 읽는다. 성공 횟수와 읽은 값의 합을 구하라.

  1. count는 3에서 시작해 2,1,0으로 감소하므로 세 번 성공한다.

  2. 생산자의 추가 변경이 없으므로 각 읽기는 값 30이다.

  3. 읽은 합은 30+30+30=90이며 생산 값의 합 60과 다르다.

성공은 세 번이고 읽은 합은 90이다. 알림 횟수의 보존은 자료의 보존이 아니다.

비교할 점

각 자료를 보존하려면 값별 저장 공간과 넘침 정책을 둔다.

접수와 송신 완료의 다른 시각

송신 시작은 0 ms이고 접수 타임아웃은 5 ms다. 접수는 4 ms, 자료 회수 완료는 9 ms이며 동기 송신의 전체 완료 목표도 시작 뒤 5 ms다. 접수 제한과 전체 완료 목표를 각각 판정하라.

  1. 4 ms 접수는 5 ms 접수 제한 안에 있다.

  2. 자료 회수를 미루는 동안 동기 send는 계속 기다린다.

  3. 완료 9 ms는 전체 완료 목표 5 ms보다 4 ms 늦다.

접수 타임아웃을 피했어도 전체 완료 목표는 지키지 못한다.

비교할 점

전체 완료 제한은 수신자 자료 회수와 스케줄링 계약까지 요구한다.

소단원 9.2

ISR와 태스크 통신

인터럽트가 측정값을 받았을 때 오래 걸리는 분석까지 그 자리에서 해도 될까?

준비 개념과 학습 목표

준비 개념

  • ISR은 하드웨어 사건에 반응한다.

  • 태스크는 스케줄러가 실행할 시간을 배정한다.

학습 목표

  • ISR의 짧은 처리와 태스크의 후속 처리를 구분한다.

  • 비대기 통신 실패와 데이터 수명을 처리한다.

ISR이 포인터를 넘긴 뒤 그 저장 공간을 다시 써도 될까요?

다음은 정적 버퍼 두 개 A와 B를 쓰는 자체 소유권 모형입니다. 각 버퍼의 상태는 free, queued, processing 중 정확히 하나입니다. ISR이 free 버퍼에 자료를 쓰고 포인터를 큐에 넣으면 queued가 됩니다. worker가 포인터를 꺼내면 processing이 되고 처리가 끝나야 free로 돌아갑니다. 꺼냈다는 사실만으로 버퍼를 생산자에게 돌려주면 worker가 읽는 동안 자료가 바뀔 수 있습니다. 큐가 복사한 것은 포인터 값이며 포인터가 가리키는 자료 전체가 아닙니다.

정확 사건 순서로 ISR은 A에 값 10을 써서 전달하고 worker는 A를 꺼내되 아직 읽지 않았습니다. ISR이 A를 free라고 잘못 판단해 값 20으로 덮으면 worker는 20을 읽습니다. 별도 고정 크기 값 큐가 정수 10 자체를 복사했다면 원래 칸의 값이 20으로 바뀌어도 받은 정수는 10입니다. 큰 자료를 복사하면 비용은 달라지고 Zephyr message queue의 복사 동안 인터럽트가 잠기는 구간도 고려해야 합니다.

단일 CPU의 별도 시간 모형에서 사건은 0 μs에 도착하고 ISR은 원인 확인 4 μs, 복사 3 μs, 종료 3 μs를 실행합니다. worker는 ISR 종료 뒤 20 μs 더 기다린 다음 CPU 50 μs를 씁니다. 완료는 80 μs입니다. 복사 비용을 8 μs로 늘리고 다른 조건을 유지하면 완료는 85 μs입니다. worker CPU가 같아도 복사 방식이 응답 시간의 일부를 바꿉니다. 일반 ISR에서 허용된 API의 비차단 사용과 zero-latency ISR의 커널 API 금지를 같은 규칙으로 합치지 않습니다.

먼저 확인할 개념
  • ISR의 짧은 실행과 후속 태스크

    기본의 원인 확인·전달·종료 및 worker 대기를 따로 더합니다.

  • 큐 실패와 저장 용량

    비차단 전달 실패를 성공한 자료나 처리 완료로 세지 않는 조건을 연결합니다.

빨리 끝내고 정보를 남기기

일반 ISR에서는 원인 확인·필요한 장치 처리·작은 정보 전달을 하고 시간이 많이 드는 분석은 태스크에 넘길 수 있다. ISR이 길어지면 다른 실행의 응답 지연에 영향을 준다.

thread 전용 API와 ISR에서도 가능한 API를 구분한다. 사용할 수 있는 통신 API라도 빈 큐나 가득 찬 큐를 ISR에서 기다리면 안 된다. zero-latency ISR 같은 특수 문맥은 일반 ISR과 달리 kernel API 사용 자체가 금지될 수 있다.

복사와 포인터 전달

고정 크기 message queue에 값을 복사하면 지역 변수에서 보낸 내용을 큐가 보존한다. 반대로 포인터만 전달하면 가리키는 객체가 소비 시점까지 살아 있어야 한다. ISR의 임시 stack 객체 주소를 남기고 돌아오는 계획은 위험하다.

큰 데이터는 미리 확보한 버퍼 pool에서 가져오고 소유권을 넘기는 방식을 생각한다. 소비 처리와 해제가 끝날 때까지 재사용하지 않는다. 작은 복사도 길이·큐 용량·실패 처리를 확인하며 복사 비용이 0이라고 가정하지 않는다.

통지 후 언제 실행되는가

ISR이 태스크를 준비 상태로 만들어도 그 태스크가 즉시 실행된다고 보장되지 않는다. 다른 우선순위 작업과 스케줄 규칙 때문에 늦게 시작할 수 있다. 사건→ISR→큐 등록→태스크 시작→처리 끝 시간선을 쓴다.

ISR의 nonblocking enqueue가 실패하면 자료를 저장하지 못했다는 사실을 남기고 손실·장치 억제 등 정책을 따른다. 성공처럼 통지하거나 실패 반복을 무한 루프로 만들면 시간 예산과 데이터 의미가 흐려진다.

중간 과정을 따라가는 예제

자체 단일 CPU 시간선에서 하드웨어 사건 t0에 ISR이 즉시 시작한다. 원인 확인 4μs, 작은 값 복사/큐 등록 3μs, 마무리 3μs다. 큐 등록은 성공하고 ISR 끝 뒤 태스크 대기 20μs, 처리 50μs다. 다른 비용 0이다. ISR 점유·태스크 시작·완료 시간을 구하라.

  1. ISR 점유는 4+3+3=10μs여서 t10에 끝난다.

  2. 태스크는 ISR 끝 뒤 20μs 대기하므로 t30에 시작한다.

  3. 처리에 50μs가 걸려 t80에 완료한다.

  4. 사건→처리 완료 지연은 80μs, 태스크 CPU 처리 시간은 50μs다. ISR 등록 완료가 처리 완료는 아니다.

ISR 10μs, 태스크 시작 30μs, 최종 완료 80μs다. 가상 시간이며 실측/마감 보장 아니다.

조건을 바꾸어 비교하기

포인터의 복사와 자료의 복사

worker가 A의 포인터를 꺼낸 뒤 읽기 전에 ISR이 A를 10에서 20으로 바꾼다. 포인터 큐와 정수 값 복사 큐의 결과를 비교하라.

  1. 포인터 큐는 같은 A를 계속 가리킨다.

  2. worker가 그 뒤 읽으면 현재 A의 값 20을 얻는다.

  3. 정수 값 복사 큐는 enqueue 때 저장한 10을 제공한다.

포인터 방식의 늦은 읽기는 20이고 값 복사 방식의 수신은 10이다.

복사 비용이 바꾸는 완료 시각

복사 비용이 3 μs 또는 8 μs다. 원인 확인과 종료 및 worker 조건은 위 모형대로 유지한다. 완료를 비교하라.

  1. 복사 3 μs의 ISR 합계는 10 μs다. worker 시작은 30 μs이고 완료는 80 μs다.

  2. 복사 8 μs의 ISR 합계는 15 μs다. worker 시작은 35 μs이고 완료는 85 μs다.

복사 증가 5 μs가 완료도 5 μs 늦춘다.

소단원 9.3

bounded buffer·backpressure

생산자가 계속 더 빠르면 큐를 크게 만드는 것만으로 해결될까?

준비 개념과 학습 목표

준비 개념

  • 유한 큐에는 최대 항목 수가 있다.

  • 생산과 소비 속도가 다르면 쌓이는 양이 변한다.

학습 목표

  • 고정 용량 큐의 순서와 가득 참을 추적한다.

  • 대기·거절·손실 및 생산 억제 정책을 구별한다.

생산을 멈추라고 보낸 뒤 들어오는 자료까지 용량에 넣었나요?

다음은 항목 용량 K=4인 자체 고정 슬롯 모형입니다. 슬롯은 free, reserved, queued, held 중 하나이며 이 네 개수의 합이 K입니다. 생산자는 먼저 빈 슬롯을 예약한 뒤 자료를 기록하고 enqueue합니다. 소비자는 dequeue해도 처리하는 동안 held 슬롯을 유지하고 완료 뒤 슬롯을 반환합니다. free 세마포어는 초기 4이며 예약 때 한 번 take하고 최종 반환 때 한 번 give합니다. 큐 길이만 보면 예약 중인 자료와 처리 중인 자료를 빠뜨립니다. 이 규칙은 실제 Zephyr FIFO가 자체 용량 4를 갖는다는 주장이 아닙니다.

초기 상태에서 생산자가 두 슬롯을 예약하면 free는 2이고 reserved는 2입니다. 하나를 enqueue하면 reserved는 1이고 queued는 1입니다. 소비자가 그 항목을 꺼내면 queued는 0이고 held는 1입니다. 다른 예약을 취소해 반환하면 free는 3이며 held 한 개가 남습니다. 소비자 처리까지 끝나야 free가 4입니다. 예약 취소 때 반환을 빠뜨리면 실제 자료는 없어도 permit가 한 개 줄어 실제 빈 슬롯이 남아도 이후 요청의 진행을 막을 수 있습니다.

별도 정수 사건 모형에서 용량은 K=5입니다. 생산을 멈추라는 신호를 보낸 뒤 이미 진행 중인 도착이 최대 3개 더 오고 그동안 소비는 없다고 가정합니다. 큐가 2개일 때 멈추면 마지막 점유는 5개여서 넘치지 않습니다. 큐가 3개일 때 멈추면 마지막 요청은 점유 6개를 요구해 하나를 버려야 합니다. 모형의 3개는 제어 지연 구간의 전체 도착 상계이며 단순한 장기 평균 도착률이 아닙니다.

저장 가능량에 경계 두기

bounded buffer는 담을 수 있는 항목 수에 상한을 둔다. 개수 q와 용량 K는 0≤q≤K를 유지한다. 빈 큐의 소비와 가득 찬 큐의 생산을 즉시 실패/대기/손실 정책 등으로 명확히 정한다.

Zephyr message queue는 최대 고정 크기 항목 수를 갖는다. Zephyr FIFO 그 자체를 고정 용량 ring이라고 혼동하지 않는다. FIFO를 제한하려면 응용의 유한 item pool 등 추가 조건을 정한다.

역압은 앞단의 생산을 조절

backpressure는 소비/저장 여유가 부족하다는 신호를 앞단으로 돌려 생산을 늦추는 것이다. thread는 상황에 따라 빈자리 대기를 선택할 수 있지만 ISR에서 block하면 안 된다. 입력 장치가 멈출 수 있는지도 확인한다.

가득 찰 때 새 항목을 버리거나 옛 항목을 버리는 정책은 정보 손실 정책이다. 손실이 허용되지 않는 업무라면 단순 삭제를 흐름 제어의 해결이라고 부를 수 없다. 번호·누락량·복구 규칙을 남긴다.

평균률과 급증량

생산률이 소비률보다 계속 높으면 유한 버퍼는 언젠가 찬다. 버퍼 증가는 가득 차는 시간을 늦추지만 지속 속도 차를 없애지 않는다. 반대로 평균 생산이 낮아도 한 번의 큰 burst로 가득 찰 수 있다.

실시간 평가에는 큐에 머무는 시간과 마감도 포함한다. 큐 크기와 성공한 전달 개수만 보면 오래된 값을 늦게 처리하는 문제를 놓칠 수 있다. 원고의 률 예제는 유체 근사이며 실제 정수 사건 일정은 별도로 작성한다.

중간 과정을 따라가는 예제

용량 3인 값 복사 FIFO 큐가 비어 있다. 즉시 연산을 순서대로 실행한다: put A, put B, put C, put D, get, put D, get, get, get. 가득 찬 put은 새 항목을 거절하고 기존 항목은 유지한다. 성공 get은 head를 제거한다. 각 큐 상태와 최종 get 순서를 구하라.

  1. put A/B/C 뒤 큐는 [A]→[A,B]→[A,B,C]이다. 첫 put D는 거절되어 [A,B,C] 그대로다.

  2. 첫 get은 A를 꺼내 [B,C]다. 다시 put D는 성공하여 [B,C,D]다.

  3. 이어 get은 B,C,D 순서다. 상태 [C,D]→[D]→[]다.

  4. D는 첫 시도 실패/두 번째 성공이다. 성공 put 4회/get 4회, 거절 1회이며 모든 성공 get 순서는 A,B,C,D다.

가득 찬 D 첫 시도만 거절된다. 출력 A/B/C/D, 마지막 큐 빈 상태다.

조건을 바꾸어 비교하기

자료가 없어도 사라질 수 있는 permit

위 표에서 남은 예약을 취소했지만 free give를 빠뜨린다. worker 처리 완료 뒤 실제 빈 슬롯 수와 세마포어 count를 비교하라.

  1. 취소한 슬롯은 실제 자료가 없지만 permit 한 개가 누락된다.

  2. worker의 슬롯은 정상 반환한다.

  3. 물리적으로는 네 슬롯이 모두 비고 count는 3이다.

실제 빈 슬롯은 4개인데 permit count는 3이다. 누락된 반환은 장부상 용량을 줄인다.

제어 지연까지 포함한 멈춤 문턱

  2. 문턱 3의 요구 점유는 3+3=6이다.

다른 문제에 적용하기

알림·버퍼 수명·제어 지연을 함께 확인하기

서로 독립된 세 모형을 푼다. ① count 초기 0, limit 3의 세마포어를 둔다. 생산자가 한 공유 칸에 10,20,30을 차례로 저장하며 매번 give하고, 그 뒤 소비자가 세 번 take하며 매번 그 칸을 읽는다. 성공 횟수와 읽은 값의 합을 구한다. ② 버퍼 A와 B 중 A는 processing, B는 queued이고 free 버퍼는 없다. ISR은 빈 버퍼가 없으면 새 사건을 버린다. 세 번째 사건의 결과를 판정한다. 별도 시간 모형의 ISR은 원인 확인 4 μs, 복사 8 μs, 종료 3 μs를 실행한다. worker 대기는 ISR 종료 뒤 20 μs이고 CPU 실행은 50 μs다. 사건 시점 0 μs부터 완료를 구한다. ③ 정수 큐의 K는 5개이고 stop 뒤 최대 3개가 더 오며 소비는 없다. 현재 점유 3개에서 stop을 보낸 경우 drop 없이 받기 위한 최소 용량과 현재 용량에서 버릴 개수를 구한다.

힌트 1

① count와 공유 칸은 별도 저장입니다. ② processing 버퍼를 free로 세지 않습니다.

힌트 2

② ISR 종료와 worker 완료를 구별합니다. ③ stop 효과 전에 들어오는 세 개를 기존 점유에 더합니다.

풀이와 답 확인

  1. ① count가 3이어서 take는 세 번 성공한다. 공유 칸은 계속 30이므로 읽은 값의 합은 90이다.

  2. ② 버퍼 A와 B는 모두 사용 중이므로 세 번째 사건을 하나 버린다. 별도 시간 모형의 ISR 종료는 15 μs, worker 시작은 35 μs, 완료는 85 μs다.

  3. ③ 요구 점유는 3+3=6개다. 최소 용량은 6개이고 K=5를 유지하면 마지막 한 개를 버려야 한다.

알림 세 번이 값 세 개를 저장하지 않으며, dequeue한 버퍼도 처리 중이면 재사용하지 않는다. 제어 지연 동안의 추가 도착까지 용량에 넣는다.

해결한 뒤 점검할 것

  • 성공한 take는 세 번이고 읽은 값의 합은 90이라고 구별했다.

  • processing 버퍼를 free로 세지 않고 새 사건 하나를 버린다고 판정했다.

  • ISR 종료 15 μs와 worker 완료 85 μs를 각각 명시했다.

  • 최소 용량 6개와 현재 용량에서 drop 1개를 제어 지연 조건으로 설명했다.
