총 빈 공간이 요청 크기보다 크면 풀 할당은 반드시 성공할까요?

기본의 고정 블록 풀을 확장한 자체 모형입니다. 작은 풀은 32바이트 블록 네 개, 큰 풀은 64바이트 블록 두 개이며 총 저장 공간은 256바이트입니다. 블록은 이미 올바르게 정렬되어 있고 별도 관리 구조의 바이트는 이 장부 밖입니다. 24바이트 요청 세 개는 작은 풀에, 48바이트 요청 두 개는 큰 풀에 넣습니다. 한 요청은 블록 하나에만 들어가며 풀 사이 이동이나 블록 결합은 하지 않습니다. 정적 저장 영역을 준비했다는 사실과 실행 중 블록을 빌리는 사건은 구별합니다.

이 상태에서 예약한 공간은 3×32+2×64=224바이트이고 실제 자료는 3×24+2×48=168바이트입니다. 예약 블록 안의 남는 공간은 56바이트이며 미사용 블록은 작은 풀의 32바이트 하나입니다. 새 48바이트 요청은 큰 풀의 빈 블록이 없어 실패합니다. 기존 24바이트 요청 하나를 반환해도 총 빈 공간 64바이트가 작은 블록 두 개로 나뉘므로 같은 요청은 여전히 실패합니다. 기다리는 할당을 사용한다면 실패 대신 대기가 생길 수 있으므로 대기 정책도 따로 지정해야 합니다.

교체 작업에는 최종 사용량보다 큰 순간 사용량이 필요할 수 있습니다. 별도 32바이트 풀에서 기존 객체 하나와 다른 객체 두 개가 살아 있다고 합시다. 기존 객체를 보존한 채 새 객체를 할당하고 복사를 마친 뒤 기존 객체를 반환하는 계약이라면 순간적으로 네 블록이 필요합니다. 세 블록 풀에서는 최종 객체 수가 세 개여도 교체가 시작되지 않습니다. 네 블록 풀의 128바이트는 이 교체 계약의 최소 저장 공간이며 자료 크기·정렬·다른 동시 요청이 달라지면 다시 계산해야 합니다.

할당을 언제 결정하는가

실시간 시스템은 결과의 정확성뿐 아니라 정해진 시간 안에 결과를 내는 조건을 다룬다. 실행 중 메모리를 구하는 작업이 실패하거나 오래 기다리면 계산 자체가 짧아도 마감을 놓칠 수 있다. 필요한 객체 수와 최대 버퍼 크기를 실행 전에 예산으로 적으면 이 위험을 줄일 수 있다.

정적 할당은 RTOS 객체의 저장 공간 등을 사용자가 미리 제공하는 방식이다. FreeRTOS는 이런 객체 생성 API와 동적 생성 API를 구별한다. 다만 정적 배열의 한계를 넘는 사용·스택 overflow·숨은 라이브러리 할당을 자동으로 막아 주는 것은 아니다. 정적 저장 영역을 기반으로 런타임에 블록을 빌리는 풀 역시 그 블록의 할당과 반환은 실행 중 일어난다.

고정 크기 풀은 횟수와 공간을 제한한다

고정 블록 풀은 같은 크기의 저장 칸을 미리 준비하고 비어 있는 칸을 빌려 준다. Zephyr의 slab이 이런 예다. 자유 목록으로 빈 칸을 관리하면 다양한 크기의 연속 빈 구간을 찾는 문제를 줄일 수 있다. 하지만 풀 내부 동기화와 빈 풀에서의 대기까지 모두 같은 시간이라고 증명되는 것은 아니다.

32바이트 블록에 20바이트 자료를 넣으면 남은 12바이트는 다른 요청에 줄 수 없는 내부 낭비다. 블록을 작게 하면 낭비가 줄지만 큰 요청을 담지 못한다. 블록 수를 정할 때 동시에 보유하는 생산자·소비자·큐와 오류 복구의 최대 수요를 포함한다. 고정 풀에도 고갈 시 즉시 실패·한정 대기·비필수 자료 삭제 같은 정책이 필요하다.

총 용량만 보면 외부 단편화를 놓친다

가변 크기 연속 할당에서는 빈 구간 사이에 사용 중인 블록이 끼어 있을 수 있다. 총 빈 바이트는 충분해도 요청 크기 이상의 연속 구간이 없으면 할당이 실패한다. 이것을 외부 단편화와 연결해 이해한다. 여기서 연속은 할당기가 관리하는 주소 영역 기준이며 물리 페이지 전체의 연속과 자동으로 같은 말은 아니다.

인접한 빈 블록을 합치는 allocator는 일부 단편화를 줄일 수 있지만 사용 중인 블록을 자동으로 옮길 수 없다면 모든 조각을 합치지는 못한다. 따라서 동적 할당은 항상 나쁘거나 모든 풀은 완벽하다는 규칙 대신 allocator·동기화·최대 수요·실패 경로를 분석한다.

중간 과정을 따라가는 예제

자체 모형의 고정 풀은 32바이트 블록 6개다. 자료 20바이트를 가진 작업 5개가 동시에 블록 하나씩 사용한다. 저장 영역·내부 낭비·남은 수용 수를 구하라. 관리 객체의 별도 공간은 계산에서 제외한다.

  1. 풀 저장 영역은 32×6=192바이트다.

  2. 5작업의 예약 블록은 160바이트이고 유효 자료는 20×5=100바이트다. 예약 블록 안 낭비는 60바이트다.

  3. 빈 블록은 1개, 32바이트다. 같은 크기 작업을 하나 더 수용할 수 있다.

  4. 여섯 블록이 모두 사용 중이면 일곱 번째 작업은 정책대로 실패하거나 기다린다. 총 블록 수가 제한돼 있으므로 무제한 자료 보관을 약속할 수 없다.

저장 영역 192바이트, 현재 내부 낭비 60바이트, 추가 작업 1개다.

조건을 바꾸어 비교하기

풀 종류에 따라 새 요청의 수용 여부가 달라진다

위 크기별 풀의 현재 상태와, 별도의 64바이트 공용 블록 여섯 개에 같은 다섯 요청을 저장한 상태를 비교하라. 관리 구조는 두 비교 모두 제외한다.

  1. 크기별 풀은 저장 256바이트, 예약 224바이트, 자료 168바이트이므로 내부 낭비는 56바이트다.

  2. 공용 풀은 저장 384바이트, 예약 320바이트, 자료 168바이트이므로 내부 낭비는 152바이트다.

  3. 공용 풀의 남은 한 블록은 64바이트여서 새 48바이트 요청을 수용하지만 크기별 풀의 남은 32바이트 블록은 수용하지 못한다.

공용 풀은 더 큰 저장 공간과 내부 낭비를 사용하지만 지정 상태의 새 48바이트 요청을 받을 수 있다.

비교할 점

낭비 최소화와 모든 요청의 수용 가능성은 같은 목표가 아니다.

최종 세 객체에도 교체 순간은 네 객체다

별도 풀에서 기존 객체와 다른 두 객체가 각 한 블록을 쓴다. 기존 객체를 보존하고 새 객체로 복사한 뒤 교체하려 한다. 블록 수 K=3과 K=4를 비교하라.

  1. 새 객체를 할당하는 순간에는 기존 세 객체와 새 객체가 함께 살아 있어 네 블록이 필요하다.

  2. K=3에서는 빈 블록이 없어 할당 단계에서 실패한다.

  3. K=4에서는 할당·복사를 마치고 기존 블록을 반환하여 최종 사용량 세 블록으로 돌아간다.

기존 객체 보존 계약에서는 K=4가 필요하며 블록당 32바이트라면 저장 공간은 128바이트다.

연습 1 · 값과 상태 예측

크기별 풀의 초기 상태에서 24바이트 요청 하나를 반환한다. 남은 자료·예약·내부 낭비·미사용 공간을 각각 구하고 새 48바이트 요청을 판정하라.

힌트 1

24바이트 자료와 32바이트 예약을 따로 뺍니다.

힌트 2

큰 풀의 빈 블록 수는 바뀌지 않습니다.

풀이와 답 확인

  1. 남은 자료는 168−24=144바이트이고 예약은 224−32=192바이트다.

  2. 내부 낭비는 192−144=48바이트, 미사용 공간은 256−192=64바이트다.

  3. 큰 풀은 여전히 가득 차 있어 새 48바이트 요청은 실패한다.

자료는 144바이트, 예약은 192바이트, 내부 낭비는 48바이트, 미사용 공간은 64바이트다. 새 요청은 수용하지 못한다.

흔한 오답에서 다시 생각하기

이 모형은 작은 두 블록을 결합하지 않으며 요청 종류에 맞는 빈 블록이 필요합니다.

연습 2 · 오류 찾아 고치기

계산을 락 밖으로 옮기면 복사본을 그대로 다시 써도 될까요?

기본의 짧은 임계 구역을 확장한 자체 잔액 모형입니다. 락 안에서 잔액 100과 버전 4를 복사하고 락을 풉니다. 락 밖에서는 30을 빼는 새 값 70을 계산합니다. 그 사이 다른 작업이 락 안에서 20을 입금해 잔액 120과 버전 5를 저장합니다. 처음 작업이 버전을 확인하지 않고 70을 다시 쓰면 입금 효과 20이 사라집니다. 복사본이 독립된 메모리에 있다는 사실은 복사한 내용이 아직 최신이라는 뜻이 아닙니다.

다시 락을 얻어 현재 버전이 복사 때의 4와 같은지 검사하면 충돌을 발견합니다. 충돌한 계산은 적용하지 않고 새 잔액 120과 버전 5로 재시도하면 결과는 잔액 90과 버전 6입니다. 모든 변경이 같은 락과 버전 규칙을 따르고 비교 동안 버전의 재사용이나 wraparound가 없다는 전제가 필요합니다. 계속 충돌하면 재시도는 끝나지 않을 수 있습니다. 시도 횟수를 두 번으로 제한하면 실패 반환의 종료는 제한할 수 있지만 성공을 보장하지는 못합니다.

우선순위 상속도 남은 임계 구역의 CPU 작업을 없애지는 않습니다. 별도 단일 CPU 모형에서 H>M>L이고 문맥 전환 비용과 다른 작업은 없습니다. L은 0 ms에 락을 잡고 CPU 작업 4 ms 뒤 풉니다. H는 1 ms에 도착해 같은 락을 얻은 뒤 CPU 작업 1 ms를 수행합니다. M은 1.5 ms에 도착해 CPU 작업 2 ms를 수행하고 락을 쓰지 않습니다. 상속이 없으면 M이 L을 중단하여 H는 7 ms에 끝납니다. 완전한 우선순위 상속이면 L이 H의 우선순위로 남은 작업을 진행해 H는 5 ms에 끝납니다. 이 단일 락 시간선은 실제 여러 락·ISR·우선순위 상한의 전체 지연 보장이 아닙니다.

먼저 확인할 개념
  • 락 대기와 임계 구역의 남은 작업

    기본의 높은 우선순위 작업 응답을 다시 읽고 중간 우선순위의 간섭과 상속을 분리합니다.

  • 복사본의 저장 수명

    락 밖의 독립 복사본은 별도 저장 공간을 사용합니다. 블록 확보와 원본의 버전 일치는 서로 다른 계약입니다.

보유 시간에 무엇을 포함하는가

mutex의 소유자가 공유 자료를 수정하는 동안 다른 작업은 그 자료에 접근하려면 기다린다. 락을 얻은 뒤부터 해제할 때까지의 범위를 표시하고 그 안에 계산·할당·I/O·추가 락·실패 재시도가 들어 있는지 읽는다. 락을 보유한 채 느린 저장이나 네트워크 응답을 기다리면 다른 작업의 대기도 늘어날 수 있다.

락 범위를 줄이는 것은 보호해야 할 자료의 일관성을 유지하면서 해야 한다. 공유 자료를 복사해 잠금을 풀고 외부 작업을 하는 설계라면 그 복사본을 사용할 동안 원본 변경을 허용하는지, 결과를 다시 적용할 때 버전 확인이 필요한지 정의한다. 단순히 unlock을 앞으로 옮겨 계산을 빠르게 하면 데이터 경쟁이 생길 수 있다.

우선순위 역전과 상속의 역할

낮은 우선순위 작업이 락을 가진 상태에서 높은 우선순위 작업이 기다리는 것은 우선순위 역전의 출발점이다. 중간 우선순위 작업이 낮은 작업을 계속 선점하면 락 해제가 더 늦어질 수 있다. priority inheritance는 기다리는 높은 작업의 우선순위를 소유자에게 임시로 전달해 이 간섭을 줄이는 기법이다.

상속이 있어도 소유자의 남은 임계 작업이 0이 되지는 않는다. 다른 락에 대기하는 소유권 사슬·설정 제한·I/O·교착 여부도 따로 분석한다. Zephyr 문서의 우선순위 상속 조건을 모든 RTOS의 동일한 규칙으로 일반화하지 않는다. timeout도 성공 보장이 아니라 실패로 돌아오는 경로를 포함한다.

단순 blocking 식에는 전제가 필요하다

한 CPU에서 다른 간섭·nested lock·I/O가 없고 낮은 작업이 한 락의 짧은 임계 구역을 마칠 수 있다고 가정하면 높은 작업의 락 대기는 소유자의 남은 임계 시간으로 계산할 수 있다. 이는 여기서 정한 교육 모형이지 모든 시스템의 blocking 상한 식이 아니다.

응답시간은 자기 계산·락 대기·더 높은 작업의 간섭·스케줄 overhead 등을 포함한다. 평균 lock 시간이 아니라 가능한 가장 긴 경로를 확인하고 무제한 반복이나 무제한 I/O가 있으면 유한 상한을 만들기 어렵다고 기록한다. 한정 timeout 뒤 무엇을 할지도 마감과 함께 설계한다.

상속은 중간 작업의 끼어듦을 줄인다

위 단일 CPU의 L/H/M 시간선에서 H의 완료 시각과 도착 뒤 응답 시간을 각각 구하라.

  1. 상속이 없으면 L은 0..1.5 ms 동안 CPU 1.5 ms를 쓰고 M이 1.5..3.5 ms 실행한다. L은 남은 2.5 ms를 3.5..6 ms 실행해 락을 푼다.

  2. H는 6..7 ms 실행하므로 완료 시각은 7 ms이고 응답 시간은 7−1=6 ms다.

  3. 상속이면 H가 기다리는 1 ms부터 L이 M보다 높은 우선순위로 실행해 4 ms에 락을 푼다. H는 4..5 ms 실행하므로 응답 시간은 5−1=4 ms다.

상속이 없을 때 H의 응답은 6 ms, 완전 상속 모형에서는 4 ms다. 상속 뒤에도 락의 남은 작업을 기다린다.

페이지 폴트 없는 실행 경로

RAM 용량이 충분해도 첫 접근 순간에 예상 밖의 지연이 생길 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 가상 메모리와 페이지

  • 스택·힙

  • 초기화와 반복 실행

학습 목표

  • 사전 준비와 시간 제한 실행 경로를 구별한다.

  • Linux memory lock·사전 접근의 조건과 보장 한계를 설명한다.

버퍼 시작부터 한 페이지씩 건너뛰면 모든 페이지를 미리 만졌을까요?

기본의 페이지 접근을 확장한 Linux 주소 공간의 자체 산술 모형입니다. 페이지 크기는 4,096바이트이고 페이지 번호는 0부터 셉니다. 양의 길이 버퍼 A는 시작 주소 4,095에서 길이 2바이트, 즉 반열린 구간 [4095,4097)을 차지합니다. 버퍼 B는 시작 주소 4,096에서 길이 2바이트, 즉 [4096,4098)을 차지합니다. A는 페이지 0과 1, B는 페이지 1을 사용하므로 두 버퍼의 페이지 합집합은 두 페이지이며 8,192바이트입니다. 이것은 현대 Linux의 페이지 단위 저장 장부이며 호출 성공·권한·실제 자원 여유는 별도 확인 대상입니다.

별도 버퍼 C의 시작 주소도 4,095이지만 길이는 4,098바이트입니다. 마지막 유효 주소는 8,192이고 페이지 0, 1, 2를 포함합니다. 시작부터 4,096바이트마다 접근하면 상대 오프셋 0과 4,096만 선택되어 절대 주소 4,095와 8,191을 만집니다. 페이지 2의 첫 주소 8,192는 놓칩니다. 첫 버퍼 바이트와 버퍼 안에 들어오는 모든 페이지 경계를 선택하면 상대 오프셋 0, 1, 4,097을 만집니다. 비정렬 시작에서는 페이지 크기만큼의 반복과 페이지 경계의 방문이 다릅니다.

mlock의 성공, ONFAULT 정책과 읽기·쓰기 준비도 구별합니다. ONFAULT는 비상주 페이지를 처음 fault 때 채워 잠그는 정책이므로 설정 성공 자체가 처음 접근의 fault 제거를 뜻하지 않습니다. 쓰는 경로에는 해당 페이지를 적절히 쓰는 준비, 충분한 스택 영역 확보 및 수명 관리가 필요하며 읽기만으로 private COW의 쓰기 경로를 인증하지 않습니다. 준비 뒤 fork는 COW 조건을 다시 만들 수 있고 자식은 메모리 잠금을 그대로 상속하지 않습니다. 여기서 손으로 세는 페이지 방문은 실제 fault 수 측정이 아닙니다. 페이지 관련 조건을 다뤘어도 캐시·락·인터럽트·I/O 전체 지연 보장은 남아 있습니다.

먼저 확인할 개념
  • 비정렬 시작과 페이지 수

    기본의 시작 주소·양의 길이·마지막 포함 주소를 다시 읽고 버퍼 합집합과 방문 경계를 계산합니다.

  • 페이지 준비와 전체 실행 지연

    페이지 fault를 줄이는 준비와 락 대기 상한을 다른 원인으로 기록해야 전체 실행 경로를 점검할 수 있습니다.

첫 사용에 숨은 준비 작업이 있다

가상 메모리 시스템에서 주소를 확보한 것과 그 주소의 페이지가 즉시 사용 가능한 것은 구별된다. 첫 접근의 매핑·초기화나 swap에서 가져오는 일, copy-on-write 처리 등이 page fault를 일으킬 수 있다. 디스크 접근이 없는 minor fault도 처리 시간이 들어가므로 page fault는 언제나 디스크 읽기라는 설명은 틀리다.

작은 MCU RTOS처럼 같은 가상 메모리·swap 모델이 없는 환경도 있다. 이 소단원의 memory lock API 설명은 Linux 프로세스에 한정한다. 어떤 플랫폼인지 먼저 확인하고 cache miss·인터럽트·버스 경쟁과 page fault를 서로 다른 지연 원인으로 분류한다.

준비 단계에서 필요한 페이지를 만든다

시간 제한 구간에 들어가기 전에 버퍼와 충분한 스택을 준비하고 필요한 경로를 사전 접근하는 방법을 생각할 수 있다. Linux man-pages는 실시간 경로에서 필요한 locked stack 페이지를 미리 확보하고 써 보는 조건을 설명한다. 필요한 데이터·코드·공유 라이브러리와 나중에 처음 실행되는 경로도 계획에 포함한다.

mlock 계열은 성공 조건 안에서 메모리를 RAM에 유지하는 API다. current mapping과 future mapping, ONFAULT 방식의 차이를 확인해야 한다. ONFAULT는 아직 없는 페이지를 즉시 모두 만들어 주는 방식이 아니다. 호출 실패·권한·잠금 용량 한도를 확인하지 않고 lock이 적용됐다고 주장하지 않는다.

폴트 회피가 마감 증명의 전부는 아니다

준비 후 새 할당·새 mapping·스택 증가·fork의 copy-on-write 같은 경로를 추가하면 준비했던 전제를 깨뜨릴 수 있다. 사전 읽기만으로 향후 쓰기의 COW 준비까지 끝났다고 단정하지 않는다. 시간 제한 구간의 호출 목록을 고정하고 라이브러리 내부 동작도 확인한다.

성공적인 memory lock은 모든 I/O 대기·캐시 미스·스케줄 지연을 없애거나 hard real-time을 보장하지 않는다. 페이지 폴트를 피하도록 설계한 경로와 실제로 폴트 수가 0이었다는 관찰, 최악 실행시간의 증명을 구별한다. 이 원고는 현재 Windows 환경에서 Linux API를 실행하지 않았으므로 코드 결과나 측정값을 제시하지 않는다.

중간 과정을 따라가는 예제

자체 페이지 모형은 한 페이지 4096바이트다. 정렬된 주소에서 시작하는 10000바이트 버퍼를 시간 제한 경로에서 사용한다. 준비 때 처음과 각 페이지 시작을 사전 접근하려면 몇 페이지인가? 시작이 정렬 경계보다 4000바이트 뒤인 경우도 비교하라.

  1. 정렬 시작은 바이트 offset 0..9999를 사용하여 페이지 번호 0,1,2에 걸친다. 페이지는 ceil(10000/4096)=3개다.

  2. offset 0,4096,8192의 세 위치를 접근하면 각 사용 페이지를 하나씩 만나는 모형이다. 실제 메모리 계약과 쓰기 준비는 별도로 확인한다.

  3. 4000바이트 밀린 시작은 바이트 4000..13999다. floor(4000/4096)=0부터 floor(13999/4096)=3까지 네 페이지다.

  4. 길이가 같아도 시작 위치가 달라 페이지 수는 달라진다. 이 계산은 페이지 수이며 폴트 발생 횟수나 처리 시간을 측정한 값이 아니다.

정렬 시작은 3페이지, 4000바이트 밀린 시작은 4페이지다.

  1. ① 반환 뒤 빈 공간은 작은 블록 두 개의 64바이트다. 큰 풀의 빈 블록은 없으며 결합을 허용하지 않으므로 새 48바이트 요청은 실패한다.

  2. ② 오래된 결과 70은 적용하지 않는다. 버전 5와 기준 버전 4의 충돌을 거절한 뒤 120에서 출금 30을 다시 계산하면 90이다. 다른 변경이 없고 검사·적용이 보호되면 버전 6으로 저장한다.

  3. ③ 마지막 유효 주소는 8,192다. 포함 페이지는 0, 1, 2이며 첫 바이트와 두 페이지 경계의 상대 오프셋 0, 1, 4,097을 방문하도록 준비한다. 실제 fault 수와 전체 지연은 아직 검증하지 않았다.

첫 모형은 빈 바이트가 충분해도 요청 종류별 블록이 없어 실패한다. 둘째 모형은 오래된 값을 거절하고 새 기준에서 계산해야 한다. 셋째 모형은 세 페이지의 방문 계획을 만들며 실제 fault 제거를 산술만으로 주장하지 않는다.

해결한 뒤 점검할 것

  • 빈 64바이트가 작은 블록 두 개임을 명시하고 큰 요청 실패를 설명했다.

  • 무검사 값 70과 정상 재시도 값 90의 차이 및 보호된 버전 비교·적용을 설명했다.

  • 포함 페이지 0, 1, 2와 상대 오프셋 0, 1, 4,097을 절대 주소로 확인했다.

  • 풀 수용·상태 유효성·페이지 준비 계획을 실제 RTOS/Linux/학생 실행 증거와 구별했다.

    실제 전체 0–114행을 읽었고 27–47/70–101행의 고정 블록·정렬·대기·반환·사용량 조건을 대조했다. 자체 32/64바이트 풀·교체 피크는 구현 실행 결과가 아니다. 미사용 블록 안의 연결 관리와 별도 자체 장부를 구별했다.

  • FreeRTOS task.h static task 계약

    실제 반환 본문 97–642행을 읽고 292–300/400–491행의 정적 TCB/스택 제공·태스크 수명·스택 깊이의 원소 단위와 포트 조건을 대조했다. 자체 원소4바이트/TCB80바이트는 보편 ABI가 아니다.

  • Linux mlock 현재 페이지의 확인 범위

기본 세 소단원 전체와 새 저장 보강의 모든 표·여섯 예제·12과제·힌트·답·오답·recap·전이를 손유도했다. 크기별 풀의 저장은 256바이트, 예약은 224바이트, 자료는 168바이트, 내부 낭비는 56바이트다. 작은 요청 반환 뒤 자료는 144바이트, 예약은 192바이트, 내부 낭비는 48바이트, 빈 작은 블록의 합은 64바이트다. 큰 요청 48바이트는 여전히 실패한다. 공용 풀은 저장 384바이트, 예약 320바이트, 내부 낭비 152바이트이며 빈 64바이트 블록이 새 요청을 받는다. 원본 보존 교체의 최대 공존은 네 객체, 최종은 세 객체이며 네 32바이트 블록의 저장은 128바이트다. 자체 정적 태스크는 스택 400바이트와 TCB 80바이트의 합 480바이트이고 세 태스크는 1,440바이트다. 잘못된 깊이 해석의 540바이트보다 900바이트 크다. 오래된 잔액 적용은 70이고 입금 뒤 성공 재시도의 잔액은 90이고 버전은 6이다. 한 시도 상한은 3.3 ms, 두 시도 반환 상한은 6.6 ms이며 성공 보장은 아니다. 상속이 없을 때 H의 완료 시각은 7 ms이고 응답 시간은 6 ms다. 완전 상속 자체 모형에서 H의 완료 시각은 5 ms이고 응답 시간은 4 ms다. 재진입 두 번 뒤 한 번 해제하면 잠금 한 번이 남는다.
