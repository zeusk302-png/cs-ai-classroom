소단원 10.1

주소와 패킷

긴 편지를 여러 봉투에 나누면 어느 봉투가 먼저 도착해도 원래 편지를 읽을 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 바이트는 데이터 크기의 단위

  • 나눗셈과 순서

학습 목표

  • 주소가 전달 목적지를 나타냄을 설명한다.

  • 패킷의 데이터와 제어 정보를 구별한다.

  • IP와 TCP의 전달 보장 차이를 설명한다.

송신 때 나눈 두 메시지가 수신 함수 두 번의 결과와 꼭 맞아야 할까?

TCP의 순서 있는 바이트 스트림과 애플리케이션 메시지 경계는 다른 계약이다. 이번 자체 모형은 길이 한 바이트 뒤 그 길이의 내용 바이트를 붙인다. 길이는 0..9로 제한하고 0은 빈 메시지, 그 밖의 값은 형식 오류다. 이는 실제 HTTP나 TCP 헤더 형식이 아니다.

수신 결과를 누적 버퍼에 붙인 뒤 첫 길이를 읽고 내용이 모두 모였을 때만 메시지를 꺼낸다. 모자라면 보존하고 다음 바이트를 기다린다. 이번에는 스트림이 정확히 종료되는 입력을 별도로 검사하며, 중간 수신 함수가 반환한 빈 값이나 실제 소켓의 상태는 실험하지 않는다.

먼저 확인할 개념
  • 바이트 표현

    길이 바이트의 숫자와 내용의 글자를 구별한다.

  • 버퍼와 논리 항목

    아직 완성되지 않은 바이트를 유효 메시지로 꺼내지 않는다.

목적지를 적고 중간 길을 고른다

인터넷에서는 서로 연결된 여러 네트워크를 거쳐 데이터를 보낸다. IP 주소는 이 전달 과정에서 출발지와 목적지를 나타내는 데 사용된다. 라우터는 목적지와 자신의 전달 정보를 보고 다음 경로를 고른다. 주소를 사람의 이름이나 기기의 영구 신분증과 같다고 생각하면 안 된다. 연결 환경에 따라 주소가 달라질 수 있다.

사람이 읽기 쉬운 도메인 이름과 IP 주소도 구별한다. 이름을 이용하는 프로그램은 필요한 주소 정보를 얻어 통신에 사용한다. 도메인 하나가 반드시 기기 한 대나 주소 하나만 뜻하는 것은 아니다. 인터넷은 연결 기반 구조이며, 웹은 그 위에서 이용하는 서비스 중 하나다.

큰 내용을 작은 전달 단위에 담는다

패킷은 네트워크에서 전달하는 데이터 단위다. 실제 네트워크에는 계층마다 프레임·IP 데이터그램·TCP 세그먼트 같은 이름이 있다. 처음에는 내용과 전달용 정보를 함께 담은 봉투라고 이해하되, 이 이름들을 모두 같은 규격으로 취급하지 않는다. 헤더에는 계층에 따라 주소나 길이 등 처리에 필요한 정보가 들어간다.

아래 계산은 자체 교육 모형이다. 내용 한 봉투에 최대 1000바이트, 봉투마다 제어 정보 40바이트를 붙인다고 정한다. 이것은 실제 IP 단편화 규칙이나 TCP 헤더 크기를 측정한 결과가 아니다. 데이터 크기와 추가 비용을 따로 세는 연습이며 실제 경로에서는 여러 계층의 비용과 재전송도 고려한다.

도착 순서와 완전성은 별도의 문제다

IP는 데이터그램들을 독립적으로 처리하며 자체적으로 도착이나 순서를 보장하지 않는다. 네트워크가 연결되어 있어도 손실과 순서 변경을 생각해야 한다. 봉투를 나눴다는 사실만으로 원문이 자동 복원되지는 않는다. 구분 번호와 누락 확인 같은 규칙이 추가로 필요하다.

TCP는 애플리케이션에 신뢰할 수 있는 순서 있는 바이트 스트림을 제공하도록 동작한다. 수신 확인과 손실에 대한 재전송 등이 이 역할을 돕는다. 그러나 연결 실패까지 없애는 마법은 아니며, 프로그램은 오류를 처리해야 한다. TCP는 바이트의 순서를 제공하지만 애플리케이션 메시지 경계를 그대로 보존하는 서비스는 아니다.

길이 2의 AB와 길이 1의 C가 다른 조각으로 도착
도착 조각누적 바이트꺼낸 메시지남은 버퍼

숫자 2, A

[2,A]

없음

[2,A]

B, 숫자 1, C

[2,A,B,1,C]

AB 뒤 C

[]

숫자 2와 1은 각각 한 바이트 길이 표식이다. 표는 순서대로 전달된 바이트의 자체 프레이밍 추적이며 네트워크 세그먼트나 실제 recv 반환을 측정한 것이 아니다.

중간 과정을 따라가는 예제

2500바이트 내용을 위 교육 봉투에 나눈다. 손실과 재전송 없이 한 번씩 보낼 때 봉투 수와 제어 정보를 포함한 총 크기는?

  1. 1000+1000+500으로 나누므로 봉투는 3개다.

  2. 제어 정보는 3×40=120바이트다.

  3. 총 크기는 2500+120=2620바이트다.

봉투 3개, 총 2620바이트다. 내용 크기 2500바이트와 전송 모형의 총 크기를 구별한다.

조건을 바꾸어 비교하기

완료 메시지와 미완료 꼬리

[2,A,B,3,X]가 도착한 뒤 스트림이 종료되었다. 해석 결과를 구하라.

  1. 첫 길이 2와 내용 A/B는 완성되어 AB를 꺼낸다.

  2. 남은 [3,X]는 내용 3개 중 1개뿐이다.

  3. 종료 시 미완료 꼬리를 형식 불완전 오류로 보고한다. X를 완성 메시지로 반환하지 않는다.

완성 AB 하나와 미완료 꼬리 오류다. 종료 전이라면 아직 오류로 확정하지 않고 대기한다.

비교할 점

기본 신뢰 스트림 설명에 애플리케이션 완전성 검사를 추가한다.

봉투 수와 크기의 경계

기본 봉투 내용 상한 1000바이트/제어 40바이트에서 내용 2001바이트를 최대한 채워 나누는 경우와 501/500/500/500으로 나누는 경우를 비교하라.

  1. 최대 채우기는 1000/1000/1의 3봉투라 총 2001+120=2121이다.

  2. 네 작은 봉투도 상한은 지키지만 총 2001+160=2161이다.

  3. 빈 내용은 이번 계산 계약상 봉투 0개라고 따로 정한다.

같은 내용에서 제어 비용이 40바이트 더 든다. 실제 TCP 분할 정책의 주장으로 확대하지 않는다.

비교할 점

기본 최소 봉투 계산과 임의 유효 분할의 비용을 비교한다.

종이와 본문으로 직접 해보기

내용 1800바이트를 같은 모형으로 나눈다. 2번 봉투가 먼저 오고 1번 봉투가 다음에 오면 원문 순서는? 2번이 한 번 손실되어 그것만 다시 보내면 보낸 봉투 수와 총 크기는?

힌트 보기

1번 내용은 1000바이트, 2번 내용은 800바이트다. 재전송에도 제어 정보를 붙인다.

풀이 보기

복원 순서는 1번 다음 2번이다. 처음 2개와 재전송 1개로 총 3개를 보낸다. 처음 크기 1800+80=1880에 재전송 800+40=840을 더해 2720바이트다. 자체 번호·재전송 모형이며 실제 TCP의 세그먼트 구성이 항상 같다는 주장은 아니다.

오해와 반례

IP 주소를 알면 데이터가 반드시 순서대로 전부 도착한다.

주소는 목적지 선택에 쓰이지만 IP 자체는 도착·순서·신뢰성을 보장하지 않는다. 두 봉투 중 하나가 손실되면 주소가 정확해도 원문이 부족하다. 신뢰성과 실패 처리는 다른 계층과 프로그램의 책임까지 살펴야 한다.

그렇게 보장하지 않는다.

TCP는 순서 있는 바이트 스트림이다. 메시지 경계는 애플리케이션이 별도 규칙으로 정한다.

스스로 풀어보기

먼저 답과 이유를 적고, 필요한 만큼 힌트를 한 단계씩 열어 보세요.

연습 1 · 값과 상태 예측

[0,1,Z]를 한 번에 받으면 메시지와 남은 버퍼는?

힌트 1

0은 이번 규약의 빈 메시지다.

힌트 2

꺼낸 뒤 다음 길이를 반복해서 읽는다.

풀이와 답 확인

  1. 첫 길이 0의 내용은 빈 바이트열이다.

  2. 다음 길이 1 뒤 Z가 있어 두 번째는 Z다.

  3. 남은 버퍼는 없다.

빈 메시지 뒤 Z의 두 메시지다.

흔한 오답에서 다시 생각하기

0이니 스트림 전체가 끝났다.

길이 0의 애플리케이션 메시지와 실제 스트림 종료 표시는 다른 계약이다.

연습 2 · 오류 찾아 고치기

첫 조각 [2,A]를 그대로 한 메시지로 표시했다. 이를 고쳐라.

힌트 1

길이 2에 필요한 내용 개수를 센다.

힌트 2

길이 바이트 자체는 내용이 아니다.

풀이와 답 확인

  1. 현재 내용은 A 한 바이트뿐이다.

  2. [2,A]를 보존하고 추가 바이트를 기다린다.

  3. B가 추가되면 AB를 반환한다.

수신 조각과 메시지 경계를 동일시하지 않는다.

흔한 오답에서 다시 생각하기

한 recv가 한 메시지다.

TCP 서비스는 바이트 스트림이다. 애플리케이션의 경계 규칙을 따로 적용한다.

연습 3 · 직접 만들어 보기

빈 메시지와 HI를 순서대로 보내는 자체 프레임 바이트열을 구성하라.

힌트 1

각 메시지 앞에 길이를 붙인다.

힌트 2

H/I는 이 모형에서 각각 한 바이트다.

풀이와 답 확인

  1. 빈 메시지는 [0]이다.

  2. HI는 [2,H,I]다.

  3. 전체 [0,2,H,I]이며 도착 조각이 어떻게 나뉘어도 누적 규칙이 같은 순서로 복원한다.

총 4바이트다. 길이 규약이 모호하지 않음을 확인한다.

흔한 오답에서 다시 생각하기

HI 두 글자만 붙이면 된다.

그러면 경계와 빈 메시지의 존재 정보를 잃는다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

여러 수신 조각의 경계가 달라도 같은 정상 바이트열을 모두 받은 뒤 복원 메시지가 같은 이유를 설명하라.

힌트 1

누적된 바이트 순서는 동일하다.

힌트 2

첫 길이가 정하는 접두 프레임은 하나다.

풀이와 답 확인

  1. 첫 표식이 길이 ℓ이면 다음 ℓ개가 첫 내용으로 유일하게 정해진다.

  2. 1+ℓ개를 제거한 동일한 꼬리에 규칙을 반복한다.

  3. 유한 정상 프레임열에 반복하여 같은 메시지열을 얻는다. 순서 변경·누락·오류 길이는 이 전제 밖이다.

조각 경계 독립이지 어떤 손상된 입력도 복구한다는 보장은 아니다.

흔한 오답에서 다시 생각하기

번호 없이 뒤집혀도 같은 결과다.

증명은 동일한 순서 있는 정상 바이트열이 누적된다는 전제를 쓴다.

클라이언트·서버

같은 컴퓨터가 누군가에게 자료를 주면서 다른 곳에서는 자료를 받을 수도 있을까?

준비 개념과 학습 목표

준비 개념

  • 프로그램은 입력을 받아 처리한다.

  • 요청과 답변

학습 목표

  • 통신에서 클라이언트와 서버 역할을 구별한다.

  • 기기와 프로그램 역할을 혼동하지 않는다.

  • 요청·응답의 크기와 처리 실패를 추적한다.

응답을 잃은 요청을 다시 보내면 서버의 상태가 몇 번 바뀔까?

응답이 안 왔다는 관찰과 요청 효과가 없었다는 주장은 다르다. 자체 서버의 작업은 카운터를 1 늘리는 요청이다. 초기 0에서 첫 요청을 처리해 1로 만들었지만 응답이 손실되었다고 하자. 같은 효과 요청을 새 작업처럼 다시 처리하면 2가 된다.

별도 중복 방지 모형은 요청 식별자 k와 요청 내용 및 결과를 기억한다. 같은 k와 같은 내용은 저장한 결과를 반환하며 다시 증가시키지 않고, 같은 k에 다른 내용은 거절한다. 효과와 이 기록이 원자적으로 저장되고 기록이 보존되는 순차 범위만 가정한다. 실제 HTTP가 이 기능을 자동 제공하는 것은 아니다.

먼저 확인할 개념
  • 완료와 관찰

    응답 관찰의 실패를 실제 처리 부재와 구별한다.

  • 원자성과 올바른 상태

    업무 효과와 중복 기록의 함께 저장 가정을 명시한다.

역할은 통신 관계에서 정해진다

클라이언트는 서비스를 이용하려고 요청을 보내는 역할이고 서버는 요청을 받아 서비스를 제공하는 역할이다. 웹에서는 브라우저가 페이지를 요청하고 웹 서버가 응답하는 장면이 익숙하다. 사람 자체가 패킷을 만드는 대신 프로그램들이 정한 규칙으로 메시지를 주고받는다.

이 이름은 기기의 크기나 가격을 뜻하지 않는다. 작은 컴퓨터에서도 서버 프로그램을 실행할 수 있고, 하나의 기기에서 여러 서버 프로그램이 동작할 수 있다. 역할은 누구와 어떤 통신을 하는지에 따라 판단한다. 실제 설치나 외부 접속 설정을 이 단원에서 요구하지 않는다.

요청을 보낸 뒤 결과를 확인한다

클라이언트는 원하는 자원과 작업을 표현해 요청하고 서버는 그 결과를 응답한다. 요청과 응답의 크기는 같을 필요가 없다. 짧은 페이지 요청에 큰 그림이 반환될 수 있고, 처리 결과가 작은 안내 문구일 수도 있다. 데이터를 보내는 방향과 총량을 따로 기록하면 구조가 보인다.

응답을 받지 못했다고 서버가 아무 처리도 하지 않았다고 단정할 수 없다. 요청이 도착하지 않았거나 응답이 돌아오지 않았거나 처리 중일 수 있다. 특히 결제 같은 동작은 확인 없이 무조건 반복하면 중복 효과가 생길 수 있다. 이 단계에서는 실패의 위치를 여러 경우로 나누는 것이 목표다.

서버도 다른 서비스의 클라이언트가 될 수 있다

한 웹 프로그램이 사용자의 요청을 받은 뒤 다른 서비스에 날씨 자료를 요청할 수 있다. 사용자와의 관계에서는 서버이고, 날씨 서비스와의 관계에서는 클라이언트다. 기기마다 한 역할만 영구히 붙어 있다는 그림보다 두 관계를 각각 그리는 편이 정확하다.

한 요청이 내부 데이터베이스나 다른 서버의 작업으로 이어져도 사용자는 하나의 응답만 볼 수 있다. 반대로 많은 사용자가 같은 서비스를 동시에 이용한다. 처리 용량과 기다림은 이후 운영체제·네트워크·분산시스템에서 다룬다. 여기서는 한 응답 뒤에 여러 프로그램의 협력이 있을 수 있음을 이해한다.

중간 과정을 따라가는 예제

서로 다른 클라이언트 3개가 각각 요청 100바이트를 보내고 응답 500바이트를 받는다. 모든 요청이 한 번 성공한다고 가정한다. 제어 정보·암호화·재전송을 제외한 두 방향 데이터량은?

  1. 서버로 들어가는 요청은 3×100=300바이트다.

  2. 서버가 보내는 응답은 3×500=1500바이트다.

  3. 두 방향 합계는 300+1500=1800바이트다.

요청 방향 300바이트, 응답 방향 1500바이트, 합계 1800바이트다. 실제 네트워크 측정값이 아니라 명시한 메시지 모형의 계산이다.

조건을 바꾸어 비교하기

요청이 도착하지 않은 다른 경로

초기 0에서 첫 요청이 서버에 도착하지 않았고 같은 R로 재시도한다. 두 모형의 효과는?

  1. 첫 효과도 R 기록도 없다.

  2. 재시도가 첫 처리라 두 모형 모두 카운터 1이 된다.

  3. 클라이언트의 처음 무응답만으로 이 경로와 앞의 응답 손실 경로를 구분하지 못한다.

무응답과 같은 관찰에 서로 다른 서버 이력이 가능하다.

비교할 점

기본 실패 가능성 나열을 상태가 다른 두 실행으로 비교한다.

역할마다 데이터량을 따로 센다

B→L 요청 80/응답 400바이트, L→S 요청 60/응답 200바이트가 한 번씩 오간다. B의 링크와 L의 전체 입출력을 나누어 계산하라.

  1. B의 두 방향 합은 480바이트다.

  2. L의 수신은 B의80+S의200=280, 송신은 S의60+B의400=460이다.

  3. 모든 메시지 각각 한 번의 합은 740이다. 양 끝에서 같은 메시지를 두 번 세어 1480을 전송량이라고 하지 않는다.

L은 B에 서버이면서 S에 클라이언트다. 관찰 위치별 분모가 다르다.

기본 전체 합과 특정 노드 방향별 집계를 비교한다.

종이와 본문으로 직접 해보기

브라우저 B가 강의 서버 L에 요청하고, L이 검색 서버 S에 질문한 뒤 B에 답한다. 각 관계의 클라이언트·서버를 표시하라. B→L 요청 80바이트와 응답 400바이트, L→S 요청 60바이트와 응답 200바이트가 한 번씩 오가면 전체 메시지량은?

힌트 보기

B↔L과 L↔S를 별도로 그린다. 네 메시지 크기를 모두 더한다.

풀이 보기

B는 L의 클라이언트, L은 B에 대한 서버다. L은 S의 클라이언트, S는 L에 대한 서버다. 합계 80+400+60+200=740바이트다. L의 두 역할은 모순이 아니다.

오해와 반례

서버라는 기기는 항상 응답만 보내며 요청은 보낼 수 없다.

서버는 통신 관계에서의 역할이다. 강의 서버가 검색 서버에 요청하면 그 관계에서는 클라이언트다. 하나의 기기나 프로그램에도 여러 역할이 가능하다.

자기점검

클라이언트 4개가 요청 50바이트·응답 150바이트를 각각 한 번 주고받으면 합계는?

그림 두 요청을 병렬로 바꾸면 요청 수와 전체 시간이 둘 다 줄까?

기본 네 자원은 HTML 12KiB, CSS 3KiB, 그림 두 개 각 5KiB다. 이번 비교는 HTML을 완전히 받은 뒤 나머지를 발견하고 즉시 요청하는 모형이다. 고정 요청별 지연 20ms와 각 요청의 독립 전송률 100KiB/s를 가정하여 HTML 140ms, CSS 50ms, 그림 각 70ms다.

이 독립 전송률은 동시에 세 전송을 지탱할 충분한 별도 용량을 준 가상 가정이다. 실제 공유 대역폭·HTML의 점진적 분석·캐시 재검증·연결 비용은 제외한다. 직렬과 이 가상 병렬은 같은 요청 수/본문량을 가져도 기다림이 겹치는 시간이 다르다. 실제 브라우저 성능을 측정하지 않는다.

주소가 가리키는 자원에 요청한다

HTTP는 웹 자원을 요청하고 응답하는 의미와 규칙을 정한 프로토콜이다. GET은 대상 자원의 현재 선택된 표현을 얻으려는 메서드다. 표현은 파일 내용일 수도, 프로그램이 데이터베이스에서 만든 결과일 수도 있다. 웹 주소의 경로를 서버 디스크의 파일 경로와 항상 같다고 해석하지 않는다.

예를 들어 강의 경로 /lessons/intro를 GET으로 요청하면 서버가 강의 HTML을 반환할 수 있다. 실제 메시지의 표현 방식은 HTTP 버전에 따라 달라지며, HTTP/1.1의 텍스트 예시를 모든 버전의 전송 형식이라고 생각하면 안 된다. 이 단원은 특정 연결 방식보다 요청과 응답의 의미에 집중한다.

상태와 내용은 함께 읽는다

200은 요청이 성공했음을 나타내며 GET의 200 응답 내용은 대상 자원의 표현이다. 404는 서버가 현재 표현을 찾지 못했거나 그 존재를 공개하지 않으려는 경우를 나타낸다. 404만으로 영구 삭제나 정확한 내부 원인을 확정할 수 없다.

404를 받았다는 것은 적어도 HTTP 응답이 돌아왔다는 뜻이다. 이름을 주소로 해석하지 못했거나 연결 자체가 실패한 상황과 구별한다. 또한 200을 받았다고 문서 안의 모든 그림까지 성공했다고 할 수 없다. 각 추가 자원 요청에도 별도의 결과가 있다.

문서가 다음 요청을 부른다

브라우저는 받은 HTML을 해석하고 필요한 스타일·그림·스크립트 등의 자원을 추가로 요청할 수 있다. 그러므로 주소 하나를 여는 동작이 요청 하나만을 뜻하지 않는다. 여러 자원을 합쳐 화면을 구성하며 일부 자원이 실패하면 글은 보이지만 그림은 없을 수도 있다.

캐시, 연결 재사용, 병렬 요청 등의 조건은 요청 수와 시간을 바꾼다. 아래 예제는 캐시가 비어 있고 네 자원을 각각 한 번 성공적으로 받으며, 한 요청씩 순서대로 처리하는 자체 모형이다. 실제 브라우저가 항상 직렬로 동작한다거나 전체 페이지 시간을 단순 합으로 측정할 수 있다는 주장은 아니다.

중간 과정을 따라가는 예제

캐시 없는 교육 모형에서 HTML 12KiB, CSS 3KiB, 그림 두 개가 각각 5KiB다. 자원마다 요청 한 번, 모든 요청 직렬, 각 요청의 고정 지연 20ms, 데이터 전송률 100KiB/s다. 헤더·이름 조회·연결·암호화 비용은 제외한다. 요청 수와 모형의 전체 시간은?

  1. HTML 1개, CSS 1개, 그림 2개로 요청은 4번이다.

  2. 본문 크기는 12+3+5+5=25KiB다. 1KiB는 1024바이트다.

  3. 전송 시간 25/100=0.25초=250ms에 고정 지연 4×20=80ms를 더한다.

4번 요청, 본문 25KiB, 전체 330ms다. 이 결과는 직렬·고정 지연 모형의 예상값이며 실제 브라우저 실험은 하지 않았다.

조건을 바꾸어 비교하기

요청 수가 그대로인 병렬

캐시 없이 네 자원의 직렬과 가상 병렬의 요청 수/본문량/시간을 비교하라.

  1. 두 경우 모두 4요청과 본문 25KiB다.

  2. 직렬은 140+50+70+70=330ms다.

  3. 병렬은 140+max(50,70,70)=210ms다.

시간은 120ms 줄어도 요청 수와 본문 총량은 줄지 않는다.

비교할 점

기본 직렬 시간을 명시적 의존성 및 용량 조건의 병렬과 비교한다.

캐시가 줄인 요청이 임계 경로를 줄이지 않을 수도 있다

그림 A만 유효 로컬 캐시로 요청 없이 준비된다. 남은 세 요청은 표의 가상 병렬 규칙을 유지한다. 그림 둘 모두 캐시인 경우도 비교하라.

  1. A만 캐시이면 요청 3개/본문 20KiB지만 남은 그림 B가 210ms에 끝나 전체 210ms다.

  2. 둘 모두 캐시면 요청 2개/본문 15KiB, 남은 CSS가 190ms에 끝난다.

  3. 캐시 재검증 요청과 사용 비용은 없다고 정한 모형이다.

요청 감소가 같은 비율의 시간 감소를 보장하지 않는다.

힌트 보기

풀이 보기

요청 3번, 전송 본문 20KiB다. 20/100초=200ms에 60ms를 더해 260ms다. CSS의 404는 그 자원의 결과이며 그림이나 HTML의 성공 여부를 직접 결정하지 않는다. 404 응답의 크기와 시간은 별도 실패 상황에서 주어지지 않았으므로 계산하지 않는다.

오해와 반례

다른 문제에 적용하기

가상 강의 페이지는 HTML 후 CSS와 두 그림을 발견한다. T3 표의 지속시간과 독립 용량을 사용해 직렬/병렬 시간을 비교하고, 그림 A만 유효 로컬 캐시일 때 요청 수·본문량·병렬 완료 시간을 구하라. 별도로 신청 카운터 0에서 k=R의 증가가 완료되었지만 응답을 잃었다. 같은 R 재시도 후 새 S를 증가시킨다. T2의 원자적 효과+기록 보존 모형에서 각 결과와 상태를 적어라. 반환 바이트는 T1 길이 규약으로 빈 메시지와 HI를 [0,2,H,I]로 만들며 두 조각 [0,2,H]와 [I]가 순서대로 도착한다. 꺼낸 메시지와 남은 버퍼도 추적하라. 실제 웹·소켓·신청·학생 시험은 하지 않는다.

HTML 의존성 뒤 가장 늦는 자원을 찾는다. R은 저장한 결과를 반환하고 S만 새 효과다.

힌트 2

길이 0도 메시지다. 첫 조각의 HI는 아직 한 바이트 부족하다.

풀이와 답 확인

  1. 직렬 완료 시간은 330 ms, 가상 병렬 완료 시간은 210 ms다. 그림 A가 캐시에 있으면 요청은 3개, 본문량은 20 KiB다. 그림 B가 남아 병렬 완료 시간은 여전히 210 ms다.

  2. 첫 R은 상태 1과 결과 1을 기록한다. 같은 R의 재시도는 결과 1을 반환하고 상태 1을 유지한다. 새 S는 결과 2를 반환하고 상태를 2로 바꾼다.

  3. 첫 조각 [0,2,H]에서는 빈 메시지를 꺼내고 [2,H]를 남긴다.

  4. I 도착 뒤 HI를 꺼내며 남은 버퍼는 없다. 두 수신 조각 자체가 두 메시지의 경계인 것은 아니다.

  5. 가상 효과/기록 원자성과 보존, 순서 있는 완전 바이트, 독립 용량의 전제를 모두 기록하며 실제 시험 미수행을 유지한다.

직렬 시간은 330 ms, 병렬 시간은 210 ms다. 그림 A 캐시 조건에서는 요청 3개, 본문량 20 KiB, 완료 시간 210 ms다. 최종 카운터는 2이며 R의 재반환 결과는 1, S의 결과는 2다. 메시지는 빈 내용 다음 HI다.

해결한 뒤 점검할 것

  • 작업 합계와 의존성 포함 전체 시간을 나눈다.

  • 요청 수·본문량·경과시간을 각각 보고한다.

  • 재시도의 응답 관찰과 새 효과 횟수를 구별한다.

  • 부분 버퍼를 보존하고 길이 0인 메시지와 종료를 구별한다.

  • 원자성·보존·전송순서·용량 가정과 실제 미수행을 명시한다.

보강 자료의 출처와 확인 범위
  • IETF RFC9293 TCP key concepts

    실제 RFC본문 §2.2의 순서있는 byte stream/재전송/양방향/포트 내용을 읽었다. 길이0..9는 자체 애플리케이션 규약이며 실제 TCP 헤더로 주장하지 않는다.

  • IETF RFC9110 HTTP semantics

    실제3443행 이하 §9.2.2의 의도된 효과/자동 재시도 범위와6761–6771행 §15.5.5의404 의미를 읽었다. HTML경로는 Internal Error여서 실제 읽은 txt를 근거로 사용했다. 자체 R/S중복모형이 HTTP자동기능이라는 주장은 없다.

  • MDN HTTP overview

    실제193–209행 역할/추가 자원·서버구성 및245–303행 요청/응답 흐름을 읽었다. 해당 페이지의 역사적 QUIC실험 문장은 현재판 설명으로 복제하지 않고 여기서는 버전 공통 의미만 사용한다.

길이 프레임과 미완료 꼬리, 봉투 경계, R/S의 효과와 기록, 방향별 집계, 직렬/병렬 의존성, 캐시 및 전이를 모두 손으로 추적했다. 지정 정수 assert로 2121, 2161, 280, 460, 330, 210, 190만 실제 재계산했다.

실제 소켓/네트워크/프레이밍 파서·HTTP·재시도 서비스·브라우저·캐시·시간측정 not_executed. 작성 helper 지정 정수 산술만 실제 실행했다.
