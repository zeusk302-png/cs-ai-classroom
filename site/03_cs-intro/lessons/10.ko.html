소단원 10.1

주소와 패킷

긴 편지를 여러 봉투에 나누면 어느 봉투가 먼저 도착해도 원래 편지를 읽을 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 바이트는 데이터 크기의 단위
  • 나눗셈과 순서

학습 목표

  • 주소가 전달 목적지를 나타냄을 설명한다.
  • 패킷의 데이터와 제어 정보를 구별한다.
  • IP와 TCP의 전달 보장 차이를 설명한다.

목적지를 적고 중간 길을 고른다

인터넷에서는 서로 연결된 여러 네트워크를 거쳐 데이터를 보낸다. IP 주소는 이 전달 과정에서 출발지와 목적지를 나타내는 데 사용된다. 라우터는 목적지와 자신의 전달 정보를 보고 다음 경로를 고른다. 주소를 사람의 이름이나 기기의 영구 신분증과 같다고 생각하면 안 된다. 연결 환경에 따라 주소가 달라질 수 있다.

사람이 읽기 쉬운 도메인 이름과 IP 주소도 구별한다. 이름을 이용하는 프로그램은 필요한 주소 정보를 얻어 통신에 사용한다. 도메인 하나가 반드시 기기 한 대나 주소 하나만 뜻하는 것은 아니다. 인터넷은 연결 기반 구조이며, 웹은 그 위에서 이용하는 서비스 중 하나다.

큰 내용을 작은 전달 단위에 담는다

패킷은 네트워크에서 전달하는 데이터 단위다. 실제 네트워크에는 계층마다 프레임·IP 데이터그램·TCP 세그먼트 같은 이름이 있다. 처음에는 내용과 전달용 정보를 함께 담은 봉투라고 이해하되, 이 이름들을 모두 같은 규격으로 취급하지 않는다. 헤더에는 계층에 따라 주소나 길이 등 처리에 필요한 정보가 들어간다.

아래 계산은 자체 교육 모형이다. 내용 한 봉투에 최대 1000바이트, 봉투마다 제어 정보 40바이트를 붙인다고 정한다. 이것은 실제 IP 단편화 규칙이나 TCP 헤더 크기를 측정한 결과가 아니다. 데이터 크기와 추가 비용을 따로 세는 연습이며 실제 경로에서는 여러 계층의 비용과 재전송도 고려한다.

도착 순서와 완전성은 별도의 문제다

IP는 데이터그램들을 독립적으로 처리하며 자체적으로 도착이나 순서를 보장하지 않는다. 네트워크가 연결되어 있어도 손실과 순서 변경을 생각해야 한다. 봉투를 나눴다는 사실만으로 원문이 자동 복원되지는 않는다. 구분 번호와 누락 확인 같은 규칙이 추가로 필요하다.

TCP는 애플리케이션에 신뢰할 수 있는 순서 있는 바이트 스트림을 제공하도록 동작한다. 수신 확인과 손실에 대한 재전송 등이 이 역할을 돕는다. 그러나 연결 실패까지 없애는 마법은 아니며, 프로그램은 오류를 처리해야 한다. TCP는 바이트의 순서를 제공하지만 애플리케이션 메시지 경계를 그대로 보존하는 서비스는 아니다.

중간 과정을 따라가는 예제

2500바이트 내용을 위 교육 봉투에 나눈다. 손실과 재전송 없이 한 번씩 보낼 때 봉투 수와 제어 정보를 포함한 총 크기는?

  1. 1000+1000+500으로 나누므로 봉투는 3개다.
  2. 제어 정보는 3×40=120바이트다.
  3. 총 크기는 2500+120=2620바이트다.

봉투 3개, 총 2620바이트다. 내용 크기 2500바이트와 전송 모형의 총 크기를 구별한다.

종이와 본문으로 직접 해보기

내용 1800바이트를 같은 모형으로 나눈다. 2번 봉투가 먼저 오고 1번 봉투가 다음에 오면 원문 순서는? 2번이 한 번 손실되어 그것만 다시 보내면 보낸 봉투 수와 총 크기는?

힌트 보기

1번 내용은 1000바이트, 2번 내용은 800바이트다. 재전송에도 제어 정보를 붙인다.

풀이 보기

복원 순서는 1번 다음 2번이다. 처음 2개와 재전송 1개로 총 3개를 보낸다. 처음 크기 1800+80=1880에 재전송 800+40=840을 더해 2720바이트다. 자체 번호·재전송 모형이며 실제 TCP의 세그먼트 구성이 항상 같다는 주장은 아니다.

오해와 반례

IP 주소를 알면 데이터가 반드시 순서대로 전부 도착한다.

주소는 목적지 선택에 쓰이지만 IP 자체는 도착·순서·신뢰성을 보장하지 않는다. 두 봉투 중 하나가 손실되면 주소가 정확해도 원문이 부족하다. 신뢰성과 실패 처리는 다른 계층과 프로그램의 책임까지 살펴야 한다.

자기점검

내용 2000바이트의 봉투 수와 총 크기는?

답과 이유 보기

2개, 2080바이트

정확히 1000씩 2개이며 헤더 비용은 80이다.

내용 2001바이트이면?

답과 이유 보기

3개, 2121바이트

나머지 1바이트도 새 봉투와 40바이트 제어 정보가 필요하다.

TCP에서 한 번 보낸 메시지는 한 번의 수신으로 그대로 나오나?

답과 이유 보기

그렇게 보장하지 않는다.

TCP는 순서 있는 바이트 스트림이다. 메시지 경계는 애플리케이션이 별도 규칙으로 정한다.

한 단계 더

헤더 비용을 교육 가정 20바이트로 바꾸고 2500바이트의 총 크기를 구해 보자. 2560바이트다. 실제 네트워크 성능은 이 비용 하나만으로 설명되지 않는다.

소단원 10.2

클라이언트·서버

같은 컴퓨터가 누군가에게 자료를 주면서 다른 곳에서는 자료를 받을 수도 있을까?

준비 개념과 학습 목표

준비 개념

  • 프로그램은 입력을 받아 처리한다.
  • 요청과 답변

학습 목표

  • 통신에서 클라이언트와 서버 역할을 구별한다.
  • 기기와 프로그램 역할을 혼동하지 않는다.
  • 요청·응답의 크기와 처리 실패를 추적한다.

역할은 통신 관계에서 정해진다

클라이언트는 서비스를 이용하려고 요청을 보내는 역할이고 서버는 요청을 받아 서비스를 제공하는 역할이다. 웹에서는 브라우저가 페이지를 요청하고 웹 서버가 응답하는 장면이 익숙하다. 사람 자체가 패킷을 만드는 대신 프로그램들이 정한 규칙으로 메시지를 주고받는다.

이 이름은 기기의 크기나 가격을 뜻하지 않는다. 작은 컴퓨터에서도 서버 프로그램을 실행할 수 있고, 하나의 기기에서 여러 서버 프로그램이 동작할 수 있다. 역할은 누구와 어떤 통신을 하는지에 따라 판단한다. 실제 설치나 외부 접속 설정을 이 단원에서 요구하지 않는다.

요청을 보낸 뒤 결과를 확인한다

클라이언트는 원하는 자원과 작업을 표현해 요청하고 서버는 그 결과를 응답한다. 요청과 응답의 크기는 같을 필요가 없다. 짧은 페이지 요청에 큰 그림이 반환될 수 있고, 처리 결과가 작은 안내 문구일 수도 있다. 데이터를 보내는 방향과 총량을 따로 기록하면 구조가 보인다.

응답을 받지 못했다고 서버가 아무 처리도 하지 않았다고 단정할 수 없다. 요청이 도착하지 않았거나 응답이 돌아오지 않았거나 처리 중일 수 있다. 특히 결제 같은 동작은 확인 없이 무조건 반복하면 중복 효과가 생길 수 있다. 이 단계에서는 실패의 위치를 여러 경우로 나누는 것이 목표다.

서버도 다른 서비스의 클라이언트가 될 수 있다

한 웹 프로그램이 사용자의 요청을 받은 뒤 다른 서비스에 날씨 자료를 요청할 수 있다. 사용자와의 관계에서는 서버이고, 날씨 서비스와의 관계에서는 클라이언트다. 기기마다 한 역할만 영구히 붙어 있다는 그림보다 두 관계를 각각 그리는 편이 정확하다.

한 요청이 내부 데이터베이스나 다른 서버의 작업으로 이어져도 사용자는 하나의 응답만 볼 수 있다. 반대로 많은 사용자가 같은 서비스를 동시에 이용한다. 처리 용량과 기다림은 이후 운영체제·네트워크·분산시스템에서 다룬다. 여기서는 한 응답 뒤에 여러 프로그램의 협력이 있을 수 있음을 이해한다.

중간 과정을 따라가는 예제

서로 다른 클라이언트 3개가 각각 요청 100바이트를 보내고 응답 500바이트를 받는다. 모든 요청이 한 번 성공한다고 가정한다. 제어 정보·암호화·재전송을 제외한 두 방향 데이터량은?

  1. 서버로 들어가는 요청은 3×100=300바이트다.
  2. 서버가 보내는 응답은 3×500=1500바이트다.
  3. 두 방향 합계는 300+1500=1800바이트다.

요청 방향 300바이트, 응답 방향 1500바이트, 합계 1800바이트다. 실제 네트워크 측정값이 아니라 명시한 메시지 모형의 계산이다.

종이와 본문으로 직접 해보기

브라우저 B가 강의 서버 L에 요청하고, L이 검색 서버 S에 질문한 뒤 B에 답한다. 각 관계의 클라이언트·서버를 표시하라. B→L 요청 80바이트와 응답 400바이트, L→S 요청 60바이트와 응답 200바이트가 한 번씩 오가면 전체 메시지량은?

힌트 보기

B↔L과 L↔S를 별도로 그린다. 네 메시지 크기를 모두 더한다.

풀이 보기

B는 L의 클라이언트, L은 B에 대한 서버다. L은 S의 클라이언트, S는 L에 대한 서버다. 합계 80+400+60+200=740바이트다. L의 두 역할은 모순이 아니다.

오해와 반례

서버라는 기기는 항상 응답만 보내며 요청은 보낼 수 없다.

서버는 통신 관계에서의 역할이다. 강의 서버가 검색 서버에 요청하면 그 관계에서는 클라이언트다. 하나의 기기나 프로그램에도 여러 역할이 가능하다.

자기점검

클라이언트 4개가 요청 50바이트·응답 150바이트를 각각 한 번 주고받으면 합계는?

답과 이유 보기

800바이트

4×(50+150)=800이다. 제어 정보 등은 제외한 가정이다.

응답을 받지 못하면 서버가 처리하지 않았음이 확실한가?

답과 이유 보기

아니다.

처리는 끝났지만 응답 전달이 실패했을 수도 있다.

서버 프로그램 2개를 한 기기에서 실행할 수 있나?

답과 이유 보기

가능하다.

서버 역할과 물리 기기 수는 일대일 관계가 아니다.

한 단계 더

B→L→S 그림에서 S가 늦어지는 경우를 표시하라. L이 기다리는 방식이라면 B의 응답도 늦어질 수 있다. 시간 제한이나 임시 응답 같은 설계 선택은 추가 조건이 필요하며 이 모형이 자동으로 정하지 않는다.

소단원 10.3

HTTP와 웹 요청 흐름

페이지 주소 하나를 열었는데 그림과 글꼴은 왜 따로 늦게 나타날까?

준비 개념과 학습 목표

준비 개념

  • 클라이언트와 서버
  • 문서와 이미지가 별도 데이터일 수 있다.

학습 목표

  • HTTP 요청·응답에서 자원·메서드·상태를 구별한다.
  • HTML 뒤의 추가 자원 요청을 추적한다.
  • 404 응답과 통신 실패를 구별한다.

주소가 가리키는 자원에 요청한다

HTTP는 웹 자원을 요청하고 응답하는 의미와 규칙을 정한 프로토콜이다. GET은 대상 자원의 현재 선택된 표현을 얻으려는 메서드다. 표현은 파일 내용일 수도, 프로그램이 데이터베이스에서 만든 결과일 수도 있다. 웹 주소의 경로를 서버 디스크의 파일 경로와 항상 같다고 해석하지 않는다.

예를 들어 강의 경로 /lessons/intro를 GET으로 요청하면 서버가 강의 HTML을 반환할 수 있다. 실제 메시지의 표현 방식은 HTTP 버전에 따라 달라지며, HTTP/1.1의 텍스트 예시를 모든 버전의 전송 형식이라고 생각하면 안 된다. 이 단원은 특정 연결 방식보다 요청과 응답의 의미에 집중한다.

상태와 내용은 함께 읽는다

200은 요청이 성공했음을 나타내며 GET의 200 응답 내용은 대상 자원의 표현이다. 404는 서버가 현재 표현을 찾지 못했거나 그 존재를 공개하지 않으려는 경우를 나타낸다. 404만으로 영구 삭제나 정확한 내부 원인을 확정할 수 없다.

404를 받았다는 것은 적어도 HTTP 응답이 돌아왔다는 뜻이다. 이름을 주소로 해석하지 못했거나 연결 자체가 실패한 상황과 구별한다. 또한 200을 받았다고 문서 안의 모든 그림까지 성공했다고 할 수 없다. 각 추가 자원 요청에도 별도의 결과가 있다.

문서가 다음 요청을 부른다

브라우저는 받은 HTML을 해석하고 필요한 스타일·그림·스크립트 등의 자원을 추가로 요청할 수 있다. 그러므로 주소 하나를 여는 동작이 요청 하나만을 뜻하지 않는다. 여러 자원을 합쳐 화면을 구성하며 일부 자원이 실패하면 글은 보이지만 그림은 없을 수도 있다.

캐시, 연결 재사용, 병렬 요청 등의 조건은 요청 수와 시간을 바꾼다. 아래 예제는 캐시가 비어 있고 네 자원을 각각 한 번 성공적으로 받으며, 한 요청씩 순서대로 처리하는 자체 모형이다. 실제 브라우저가 항상 직렬로 동작한다거나 전체 페이지 시간을 단순 합으로 측정할 수 있다는 주장은 아니다.

중간 과정을 따라가는 예제

캐시 없는 교육 모형에서 HTML 12KiB, CSS 3KiB, 그림 두 개가 각각 5KiB다. 자원마다 요청 한 번, 모든 요청 직렬, 각 요청의 고정 지연 20ms, 데이터 전송률 100KiB/s다. 헤더·이름 조회·연결·암호화 비용은 제외한다. 요청 수와 모형의 전체 시간은?

  1. HTML 1개, CSS 1개, 그림 2개로 요청은 4번이다.
  2. 본문 크기는 12+3+5+5=25KiB다. 1KiB는 1024바이트다.
  3. 전송 시간 25/100=0.25초=250ms에 고정 지연 4×20=80ms를 더한다.

4번 요청, 본문 25KiB, 전체 330ms다. 이 결과는 직렬·고정 지연 모형의 예상값이며 실제 브라우저 실험은 하지 않았다.

종이와 본문으로 직접 해보기

같은 모형에서 그림 하나가 처음부터 유효한 로컬 캐시에 있어 HTTP 요청 없이 사용된다. 다른 조건은 그대로라면 요청 수·전송 본문·시간은? 별도로 CSS 요청만 404이면 그림까지 모두 실패했다고 결론낼 수 있나?

힌트 보기

요청과 본문에서 그림 하나를 빼고 계산한다. 실제 캐시는 재검증 요청이 생길 수도 있지만 이 문제에서는 없다고 정했다.

풀이 보기

요청 3번, 전송 본문 20KiB다. 20/100초=200ms에 60ms를 더해 260ms다. CSS의 404는 그 자원의 결과이며 그림이나 HTML의 성공 여부를 직접 결정하지 않는다. 404 응답의 크기와 시간은 별도 실패 상황에서 주어지지 않았으므로 계산하지 않는다.

오해와 반례

웹 페이지가 200이면 페이지를 만드는 모든 자원이 성공했다.

HTML은 200이어도 그림 요청은 404일 수 있다. 한 페이지에는 여러 요청이 있을 수 있으므로 요청별 상태를 확인해야 한다. 화면의 빈 부분을 곧바로 인터넷 전체의 고장으로 해석하지 않는다.

한 단계 더

직렬 모형을 버리고 자원을 동시에 요청하면 왜 330ms 계산을 그대로 쓸 수 없는지 설명하라. 대기 시간이 겹칠 수 있지만 대역폭·자원 발견 순서·서버 처리 조건도 필요하다. 병렬이라는 말만으로 새 시간을 확정하지 않는다.
