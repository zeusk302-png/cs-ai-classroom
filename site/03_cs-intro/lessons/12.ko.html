테스트와 반례

프로그램이 한 번 맞는 답을 냈으면 다음에도 믿어도 될까?

준비 개념과 학습 목표

준비 개념

  • 조건문

  • 함수의 입력·출력

  • 정수 비교

학습 목표

  • 실행 전에 요구사항에서 기대 답을 만든다.

  • 대표·경계·실패 사례를 구별한다.

  • 반례를 작게 줄이고 수정 뒤 다시 점검한다.

항상 0을 반환하는 함수도 지불액이 구매액보다 작다는 검사를 통과하지 않을까?

단일 속성은 정답의 일부만 표현할 수 있다. base의 할인 규칙에서 음이 아닌 정수 a가 1000 이상이면 a−100, 그렇지 않으면 a다. 지불액≤a만 확인하면 항상 0인 잘못된 함수도 통과한다. 정확한 기대값과 관계 속성을 함께 쓰자.

새 비교는 요구사항에서 기대값을 먼저 만든다. 경계 양쪽뿐 아니라 할인 전후의 불연속도 본다. 이 함수는 999에서 999, 1000에서 900이므로 입력이 늘면 출력도 늘어난다는 일반 속성은 이 계약에 맞지 않는다. 테스트 설계 자체도 요구사항과 대조해야 한다.

  • 반례와 중간 상태

테스트는 약속과 실제를 비교한다

할인 규칙이 “구매액이 1,000원 이상이면 100원을 뺀다”라고 하자. 함수의 입력은 구매액, 출력은 지불액이다. 입력을 고르고 규칙으로 기대 답을 먼저 계산한 뒤 실제 출력과 비교한다. 프로그램이 만든 답을 그대로 기대 답에 복사하면 같은 실수를 검출하기 어렵다.

테스트 한 개가 통과했다는 것은 그 사례에서 약속과 일치했다는 뜻이다. 모든 입력에 대한 수학적 증명은 아니다. 정상 예제뿐 아니라 규칙이 바뀌는 경계와 잘못된 입력을 골라야 한다. 이 절의 함수는 음이 아닌 정수 구매액이 이미 검증됐다는 약속 아래 할인 계산만 다룬다.

경계의 양쪽을 직접 확인한다

1,000원보다 작은 999원, 경계 1,000원, 그보다 큰 1,001원을 선택해 보자. 기대 답은 각각 999, 900, 901이다. 코드가 >= 대신 >를 썼다면 1,000원에서만 할인을 놓친다. 2,000원 같은 멀리 떨어진 정상 예제는 이 오류를 드러내지 못한다.

작은 입력 0과 평범한 500도 정해진 입력 범위의 대표 사례다. 음수와 소수·문자 입력을 어떻게 처리할지는 별도 약속이 필요하다. 없던 요구사항을 테스트가 임의로 발명하지 않는다. 잘못된 입력에 거부를 기대한다면 입력 검증 기능과 예외 규칙을 구현하고 확인해야 한다.

def pay(amount):
    if amount >= 1000:
        return amount - 100
    return amount

반례를 줄이고 다시 실행한다

실패를 찾으면 입력, 기대 답, 실제 답과 실행 환경을 남긴다. 복잡한 장바구니 대신 할인 기준 하나인 1,000원이 실패한다면 더 작은 원인 설명을 얻는다. 코드에서 경계 비교를 고친 뒤 실패 사례와 기존 정상 사례를 모두 다시 실행해 다른 동작을 망가뜨리지 않았는지 본다.

unittest 같은 도구는 실제와 기대 값 비교 및 예상 예외를 모아 보고한다. 도구 자체가 기대 답을 대신 정하거나 프로그램의 모든 정확성을 보장하지는 않는다. 테스트 결과, 손 추적, 수학적 논증과 학습자 사용 검증은 서로 다른 근거다. 여기서는 설치 없이 표와 조건식만으로도 시작할 수 있다.

최종 열은 약한 속성 하나의 통과다. 정확 기대값 열과 동일한 의미가 아니다. 표는 가상 구현의 손추적이며 새 함수 테스트 실행 결과가 아니다.

중간 과정을 따라가는 예제

>=를 >로 잘못 쓴 함수와 본문의 수정 함수를 비교한다. 입력 0, 999, 1000, 1001, 2000의 기대 지불액을 먼저 적어라.

  1. 0과 999는 1,000 미만이므로 0과 999다. 1,000은 기준에 포함되므로 900이다. 1,001과 2,000은 100원을 빼 901과 1,900이다.

  2. 잘못된 > 함수는 1,000을 할인 조건에 넣지 않아 1,000을 반환한다. 이 사례의 기대 900과 실제 1,000이 다르다.

  3. 수정한 >= 함수는 0, 999, 900, 901, 1900을 반환한다. 저자는 이 다섯 입력을 실제 Python에서 대조했다.

  4. 통과한 것은 이 다섯 입력이다. 외부 입력의 형식 검증이나 실제 결제 서비스의 정확성까지 확인한 것은 아니다.

경계 1,000은 잘못된 > 조건의 반례다. 수정 함수의 실제 다섯 결과는 0, 999, 900, 901, 1900이다.

조건을 바꾸어 비교하기

잘못된 검사 조건을 고친다

검사자가 a가 증가하면 pay(a)도 감소하지 않아야 한다고 주장했다. 999와 1000으로 판정하라.

  1. 계약은 각각 999와 900이다.

  2. 출력은 99 감소하므로 단조 증가 속성은 계약 자체에 맞지 않는다.

  3. 조건이 바뀌지 않는 같은 구간에서 증가량을 비교하는 속성으로 범위를 제한한다.

각 구간 안에서 pay(a+1)−pay(a)=1이다. 999→1000에는 적용하지 않는다.

비교할 점

구현만 고치는 테스트와 검사 계약을 먼저 고치는 일을 구별한다.

작은 입력 공간에서 전수 검사한다

검사 대상 입력을 정수 0..1001로 제한하면 사례 수와 전수 통과의 결론 범위는?

  1. 양끝을 포함하여 1002개다.

  2. 독립 기대값과 이 1002개 결과가 모두 같으면 이 유한 입력 집합에서 일치를 확인한다.

  3. 1002 이상이나 잘못된 타입·서비스 상태는 확인하지 않았다.

전수 검사도 선언한 입력 공간에만 결론을 준다. 실제 전수 실행은 하지 않았다.

실패한 제출과 취소한 제출을 둘 다 성공 0개로 바꾸면 어떤 기록을 잃을까?

가상 수량 처리의 결과는 성공·거부·취소로 나눈다. 성공은 1..5의 수량을 갖고 거부는 형식 또는 범위 코드, 취소는 수량을 갖지 않는 상태다. 모든 경로를 수량 숫자 하나로만 나타내면 상태의 의미를 잃는다.

이 단원의 가상 이벤트 표에는 요청 별칭과 단계·결과만 남긴다. 비밀과 원문 입력은 넣지 않는다. 기록이 한 줄 구조를 유지하는지와 기록을 볼 권한은 별도다. 실제 로그 파일·서버·개인정보는 생성하거나 수집하지 않는다.

먼저 확인할 개념
  • 실패와 올바른 상태

    숫자값 하나와 업무 완료를 구별한다.

  • 오류 종류와 발생 위치

    거부 코드를 의미 있는 단계에 연결한다.

실패 종류를 먼저 구별한다

콜론이 빠진 if 문은 구문을 해석할 수 없는 문법 오류다. int("많이")는 구문이 올바르지만 정수 변환을 할 수 없어 실행 중 ValueError가 발생한다. 할인 기준을 >로 잘못 쓰는 코드는 실행돼도 요구사항을 어기는 논리 오류다. 각각 수정이나 처리가 다르다.

오류를 무조건 숨기면 잘못된 상태를 정상처럼 사용할 수 있다. 수량 변환 실패를 0으로 돌려준 뒤 주문 성공이라고 말하면 입력을 바로잡을 기회를 잃는다. 성공한 값과 실패한 결과를 구별하는 약속을 먼저 정한다.

예상한 예외를 필요한 범위에서 처리한다

본문 함수는 text가 문자열이라고 정하고 int 변환에서 ValueError만 처리한다. 변환 실패에는 안내용 오류를 다시 발생시키며, 변환이 성공해도 1..5 범위를 검사한다. 예외가 발생하면 try의 남은 문장은 실행되지 않는다. 오류를 호출자에게 보내는 함수와 다시 입력하도록 안내하는 화면은 역할이 다르다.

모든 예외를 한꺼번에 잡고 성공 값을 반환하면 프로그래밍 결함까지 숨길 수 있다. 예상 입력 오류는 사용자가 고치게 하고 예상하지 못한 오류는 조사할 근거를 남긴다. finally로 정리하는 작업도 성공 보장과는 다르다. 이 절은 실제 파일·네트워크 자원을 열지 않으므로 자원 정리 실험을 했다고 말하지 않는다.

def parse_quantity(text):
    try:
        quantity = int(text)
    except ValueError:
        raise ValueError("수량은 정수여야 합니다")
    if not 1 <= quantity <= 5:
        raise ValueError("수량은 1부터 5까지입니다")
    return quantity

사용자 안내와 운영 기록을 분리한다

이용자에게는 “수량은 1부터 5까지 입력하세요”처럼 고칠 방법을 설명한다. 조사 기록은 발생 시각·요청 식별·단계·오류 종류·결과를 목적에 맞게 남긴다. 잘못된 입력 전체, 비밀번호나 접근 토큰을 그대로 쓰지 않는다. 외부 입력의 줄바꿈이나 구분자가 로그 구조를 바꾸지 않도록 형식을 다룬다.

로그가 있다고 원인이 자동으로 밝혀지는 것도 아니다. 실패가 어디서 발생했는지 좁히는 단서이고 누락·변조·시간 차이도 고려한다. 반복 가능한 작은 입력과 프로그램 버전이 있으면 원인을 더 잘 찾는다. 이 단원은 가상 로그 설계이며 실제 서비스 사고를 조사한 결과가 아니다.

중간 과정을 따라가는 예제

본문 parse_quantity에 문자열 "3","많이","0","6"을 넣는다. 변환과 범위 검사 중 어디서 성공·실패하는지 순서를 설명하라.

  1. "3"은 정수 3으로 변환되고 1 ≤ 3 ≤ 5를 만족하므로 3을 반환한다.

  2. "많이"는 int에서 ValueError가 발생하여 변환 오류 안내를 raise한다. 범위 검사와 정상 반환에 도달하지 않는다.

  3. "0"과 "6"은 정수 변환 자체는 성공하지만 허용 범위 밖이라 별도 ValueError를 발생시킨다.

  4. 저자가 실제 호출해 확인한 결과는 3, 변환 오류, 범위 오류, 범위 오류다. 실패에 임의 0 반환을 섞지 않는다.

형식 변환 실패와 의미 범위 실패를 구별한다. 성공한 "3"만 정상 수량 3을 반환한다.

집계의 분모를 밝힌다

위 네 요청에서 전체 성공률과 취소를 뺀 제출 성공률을 구하라.

  1. 전체 요청은 4개라 성공 1/4다.

  2. 취소를 제외한 제출은 3개라 성공 1/3이다.

  3. 각 비율의 분모 정의를 함께 기록한다.

25%와 33⅓%는 서로 다른 집계를 답한다. 실제 운영률이 아니다.

로그 개수와 성공률의 분모를 혼동하지 않는다.

줄바꿈의 구조 영향을 다룬다

원문 문자열이 두 줄이면 한 줄 로그에 그대로 이어 붙일 때 두 사건으로 보일 수 있다. 기록 설계를 고쳐라.

  1. 원문 전체 대신 고정 오류 코드와 제한된 요청 별칭을 남긴다.

  2. 필요한 비신뢰 필드를 남긴다면 선택한 로그 형식에 맞게 인코딩한다.

  3. 사건 하나가 사건 하나로 해석되는지와 로그 접근 제한을 별도로 확인한다.

인코딩과 비밀 제외는 각각 필요한 설계다. 실제 주입 실험은 하지 않는다.

비교할 점

주입을 막는다고 비밀 전체를 기록해도 된다는 결론은 없다.

풀이 보기

R8, parse, invalid_integer, rejected는 필요한 메타데이터로 검토할 수 있다. password는 기록하지 않고 원문 input도 기본 로그에서 제외한다. 이용자에게는 “수량을 1부터 5까지의 정수로 다시 입력하세요”라고 안내한다. 실제로 secret 비밀번호를 수집·기록한 것은 아니다.

오해와 반례

except로 오류를 모두 잡고 0을 반환하면 프로그램이 안전해진다.

0이 유효한 결과와 혼동되거나 잘못된 주문이 정상 처리될 수 있다. 구체적인 예상 오류와 정상 반환을 구별하고, 예상 못한 결함을 숨기지 않아야 한다.

새 예약 입력의 자체 계약은 start와 end가 각각 길이 1..2의 ASCII 숫자 문자열이고 변환 값이 0..23이며 start<end인 것이다. 두 칸이 각각 형식과 범위를 만족해도 순서 조건이 남는다. 같은 시각 예약과 자정 넘김 예약은 이번 계약에서 허용하지 않는다.

검증이 끝난 정수 쌍을 이후 처리에도 그대로 사용한다. 별도로 요청자가 예약을 수정할 권한이 있는지 확인한다. 문맥에 맞는 안전한 출력과 매개변수화 쿼리도 검증과 다른 방어다. 이 자체 예약 정책은 실제 서비스의 시간대·날짜·재고·보안 검증을 대신하지 않는다.

  • 형식과 필드 간 의미

입력 규칙을 먼저 문장으로 정한다

수량 칸에서 길이 1..2의 ASCII 숫자 문자열만 받고 값은 1..5라고 정해 보자. "03"은 이 규칙에서 3으로 허용하고 "3.0", "-1", " 3 "은 문자 규칙을 어겨 거부한다. 선행 0과 공백을 허용할지 요구사항을 먼저 정해야 한다. 한국어 이름이나 자유 문장을 숫자 규칙으로 제한하는 것은 다른 입력의 의미를 망친다.

형식 검사는 문자열·숫자 표현을, 의미 검사는 해당 업무에 맞는 범위를 확인한다. 서버가 거대한 요청을 이미 읽은 뒤 길이 검사를 하면 읽기 단계의 자원 고갈을 막지 못한다. 실제 서비스는 요청을 받는 단계에서 크기 제한도 정해야 한다. 다음 함수의 len 검사는 이미 생성된 문자열의 검사이므로 그 상위 보호를 대신하지 않는다.

받은 값을 직접 평가하지 않는다

본문 함수는 문자열인지, 길이, 각 문자가 ASCII 0..9인지 검사한 뒤 int로 변환하고 범위를 확인한다. 입력을 Python 식으로 실행하는 eval 같은 방식은 사용하지 않는다. 보이는 숫자 한 칸을 처리하려고 입력에 프로그램 실행 권한을 줄 필요가 없다.

이 규칙은 교육용 수량 문자열 계약이다. 브라우저 버튼이나 입력 칸 제한은 사용자의 빠른 피드백에 도움을 주지만 우회해 직접 요청할 수 있으므로 서버에서도 필요한 검사를 수행한다. 내부 시스템에서 온 값도 그 시스템의 검사를 무조건 신뢰하지 않고 받은 쪽의 조건을 확인한다.

def valid_quantity(text):
    if not isinstance(text, str):
        return False
    if not 1 <= len(text) <= 2:
        return False
    if not all("0" <= ch <= "9" for ch in text):
        return False
    quantity = int(text)
    return 1 <= quantity <= 5

유효한 값과 허용된 행동은 다르다

사용자 ID가 올바른 숫자여도 다른 사용자의 정보를 볼 권한이 생기지 않는다. 검증은 값의 형식과 업무 조건, 권한은 요청자가 대상에 행동해도 되는지 판단한다. 데이터베이스에 값을 넣을 때는 매개변수화된 쿼리, 화면에 출력할 때는 문맥에 맞는 인코딩 같은 안전한 사용 규칙도 필요하다.

악성 문자열 목록을 계속 추가하는 방식은 우회와 정상 이름의 거부를 함께 만들 수 있다. 필드별 허용 규칙을 정하고 관련 방어를 별도로 적용한다. 이 작은 함수가 참을 반환했다고 애플리케이션 전체의 SQL·웹·권한 보안을 검증한 것은 아니다. 보안은 데이터가 들어와 사용되고 기록되는 경로를 함께 확인한다.

중간 과정을 따라가는 예제

본문 valid_quantity에 "3","03","0","6","3.0"," 3 ",정수3을 넣는다. 문자·길이·값 조건을 순서대로 추적하라.

  1. "3"은 문자열·길이 1·ASCII 숫자·값 3이므로 True다. "03"도 길이 2·ASCII 숫자·값 3이라 True다.

  2. "0"과 "6"은 형식은 통과하지만 값 범위 1..5를 벗어나 False다.

  3. "3.0"과 " 3 "은 길이 3으로 먼저 거부된다. 이 규칙에서는 공백을 자동 제거하거나 소수를 정수로 바꾸지 않는다.

  4. 정수 3은 문자열이 아니라 False다. 저자의 실제 Python 결과는 True, True, False, False, False, False, False다.

형식·범위·타입을 모두 만족한 "3"과 "03"만 허용된다. 숫자 값이 3이라는 이유만으로 다른 표현을 자동 허용하지 않는다.

  2. R2는 validation/order, R3는 validation/range, R4는 authorization/forbidden으로 rejected다. R5는 cancelled다.

  3. 각 거부에 요청 별칭과 고정 단계/코드를 기록한다. 비밀·원문 입력과 성공 수량 같은 오해할 필드는 넣지 않는다.

  4. 성공 1/전체 5=20%, 취소 제외 성공 1/제출 4=25%다. 이벤트 줄 수를 요청 수로 세지 않는다.

  5. start=00,end=00은 칸 조건을 통과하나 원래 0<0이 거짓이다. 잘못된 <=가 허용하므로 가장 작은 값의 관계 반례다.

성공은 1개, 거부는 3개, 취소는 1개다. 전체 성공률은 20%, 취소를 제외한 제출 성공률은 25%이며 최솟값 반례는 00/00이다. 각 거부 단계와 로그의 최소 맥락을 분리한다.

해결한 뒤 점검할 것

  • 필드 범위·관계·권한을 순서대로 분리한다.

  • 취소와 거부를 정상 성공으로 바꾸지 않는다.

  • 로그의 고정 코드와 비밀/원문 제외를 설명한다.

  • 비율마다 요청 분모와 취소 제외 정책을 기록한다.

  • 경계 비교 반례를 독립 요구사항으로 판정한다.
