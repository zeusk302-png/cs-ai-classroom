소단원 14.1

요구사항과 사용자

작은 도서 대출 프로그램에서 무엇을 성공이라고 부를까?

준비 개념과 학습 목표

준비 개념

  • 입력과 출력

  • 조건문

  • 사용자와 상태

학습 목표

  • 사용자 목적과 기능 아이디어를 구별한다.

  • 관찰 가능한 요구사항을 쓴다.

  • 범위·가정·실패 처리와 검증 기준을 연결한다.

누구의 어떤 일을 돕는지 먼저 적는다

이 단원은 한 권마다 고유한 도서 ID가 있는 작은 대출 기록 시스템을 설계한다. 학생은 빌릴 수 있는지 알고 싶고 담당자는 중복 대출과 잘못된 기록을 막고 싶다. 이름을 예쁘게 정하거나 화면을 먼저 그리는 것만으로 이 두 목적을 확인할 수는 없다.

사용자는 실제로 조작하는 사람이고 이해관계자는 결과의 영향을 받는 사람까지 포함한다. 서로의 요청이 다르면 우선순위와 범위를 정한다. 아래 모델은 한 번에 한 요청을 처리하는 단일 담당자 흐름이다. 여러 장치의 동시 대출·결제·추천·예약은 이번 범위에 넣지 않는다.

기능과 품질·제약을 구별한다

기능 요구사항은 도서의 존재 확인·대출·반납처럼 시스템이 해야 하는 행동이다. 품질 요구사항은 같은 과업을 얼마나 이해하기 쉽거나 빠르게 수행하는지 같은 성질이다. 제약은 사용 가능한 장치·저장 방식처럼 선택을 제한한다.

빠르고 편리하다는 표현만으로는 합격 여부를 정하기 어렵다. 과업·입력·예상 결과·관찰 방법을 적는다. 응답 시간 목표를 정한다면 장치와 자료 크기 및 측정 시작/끝을 함께 정해야 한다. 아직 측정하지 않은 목표를 달성 사실로 쓰지 않는다.

예외와 기준을 같이 남긴다

가상 요구 R1은 대출 가능한 존재 도서와 유효한 대출자 ID가 입력되면 성공하고 그 도서는 해당 대출자의 대출 중 상태가 된다는 것이다. R2는 이미 대출 중인 도서의 요청을 실패로 알리고 기존 기록을 바꾸지 않는 것이다. R3은 없는 도서를 요청하면 없음으로 알리고 기록을 추가하지 않는 것이다.

검증은 구현이 정한 요구를 충족하는지 확인하고, 사용자 목적 검증은 그 요구 자체가 실제 필요를 해결하는지 확인한다. 세 요구를 지키는 구현이라도 학생이 ID를 찾지 못한다면 사용 목적을 못 이룰 수 있다. 실제 사용자와 요구를 확인한 상태와 자체 설계 가정을 구별한다.

중간 과정을 따라가는 예제

도서 B1은 대출 가능, B2는 U7에게 대출 중이다. U3이 B1, B2, 없는 B9를 차례로 요청할 때 각 요구와 결과를 연결하라.

  1. B1 요청은 R1에 해당한다. 성공 뒤 B1의 대출자 ID는 U3이다.

  2. B2 요청은 R2다. 실패를 알리고 기존 U7을 보존한다. U3으로 덮어쓰면 R2 위반이다.

  3. B9 요청은 R3다. 없음으로 알리고 새 도서를 자동 추가하지 않는다. 도서 등록은 별도의 기능이다.

성공·대출 중·없음의 세 결과와 상태 변화 여부를 각각 기록한다.

풀이 보기

이번 모델은 이미 대출 중으로 실패하고 기록을 보존한다. 같은 요청의 재시도 성공을 원하면 요청 ID와 재시도 정책을 새 요구로 명시하고 관련 검증도 바꿔야 한다.

오해와 반례

작은 프로그램은 정상 입력만 정하면 요구사항이 충분하다.

중복·없는 도서·실패 뒤 상태처럼 실제 흐름을 결정하는 조건도 필요하다. 작다는 이유로 예외 동작을 임의로 추측하지 않는다.

소단원 14.2

모듈과 인터페이스

대출 화면이 바뀌어도 기록 규칙까지 다시 작성해야 할까?

준비 개념과 학습 목표

준비 개념

  • 함수와 반환값

  • 사전과 키

  • 성공과 오류

학습 목표

  • 모듈의 책임을 분리한다.

  • 입출력과 상태 보장을 계약으로 적는다.

  • 구현 세부와 인터페이스 약속을 구별한다.

책임과 변경 이유로 나눈다

화면 모듈은 입력을 받고 결과를 설명한다. 대출 규칙 모듈은 가능 여부와 상태 전이를 정한다. 저장 모듈은 기록을 조회·저장한다. 모듈은 단순히 파일을 많이 만드는 것이 아니라 책임과 의존 관계를 나누는 단위다.

화면이 저장 내부의 배열 위치를 직접 수정하면 저장 방식이 바뀔 때 화면도 함께 고쳐야 한다. 필요한 기능을 공개 인터페이스를 통해 호출하면 내부 구현을 숨길 수 있다. 다만 계약에 실제로 필요한 동작을 빠뜨리면 독립 변경의 근거가 부족하다.

함수 이름과 타입만으로는 부족하다

자체 대출 서비스 borrow(book_id,user_id)는 빈 문자열이 아닌 ID를 받고 success, already_borrowed, not_found, invalid_input 중 한 결과를 돌려준다. invalid_input을 먼저 검사하고 그다음 도서 존재·대출 중 상태를 확인한다. 결과와 상태 변화를 계약에 함께 적는다.

success이면 한 도서의 대출자를 바꾸고 다른 도서는 보존한다. 나머지 결과이면 모든 기록을 보존한다. 이번 종이 모델은 실패 없는 메모리 저장과 순차 호출을 가정한다. 실제 디스크 실패나 여러 요청의 경쟁 상태는 별도의 오류/동시성 계약이 필요하다.

약속을 통해 구현을 교체한다

클라이언트인 화면은 반환 결과와 공개 조회 기능을 사용하고 내부 사전 순서나 저장 파일 형식을 추측하지 않는다. 구현자는 사전을 파일 또는 데이터베이스로 바꾸더라도 동일한 계약을 유지해야 한다. 이 경계를 추상화 장벽이라 부른다.

자료 전달 때 ID의 문자열 규약·빈 값·결과 종류·기존 값 보존을 맞춘다. 입력을 잘못 받으면 아무 일도 안 한다는 보장이 필요한지, 사전조건만 두고 호출자 책임으로 할지도 명시한다. 여기서는 잘못된 입력을 실제 검사하고 결과로 알리는 계약을 택했다.

중간 과정을 따라가는 예제

초기 기록 {B1: available, B2: U7}에서 borrow(B1,U3), borrow(B1,U4), borrow(B9,U3), borrow(B2,빈 ID)의 결과와 상태를 추적하라.

  1. 첫 호출은 success이며 B1:U3, B2:U7이다.

  2. 둘째는 already_borrowed라 B1을 U4로 바꾸지 않는다. 셋째는 not_found라 B9를 만들지 않는다.

  3. 넷째는 invalid_input이다. 정한 검사 순서에서 빈 ID가 먼저 처리되며 B2:U7과 다른 기록을 보존한다.

최종 기록은 {B1:U3,B2:U7}이다. 네 결과는 success/already_borrowed/not_found/invalid_input이다.

종이와 본문으로 직접 해보기

화면이 not_found를 받으면 도서 등록을 직접 호출하여 대출을 재시도한다. 이 동작은 이번 공개 borrow 계약이 보장한 것인가?

힌트 보기

없는 도서 처리와 등록 기능의 책임 및 요구 R3를 비교한다.

풀이 보기

아니다. borrow는 등록하지 않고 상태를 보존한다. 화면이 자동 등록하면 별도의 정책이며 R3 의도와 충돌할 수 있어 요구와 인터페이스를 다시 합의해야 한다.

오해와 반례

함수 이름과 입력 타입이 같으면 두 구현은 언제나 교환 가능하다.

성공 조건·오류 우선순위·상태 변화·정렬이나 순서 보장까지 계약을 만족해야 한다. 타입만으로 의미를 모두 알 수 없다.

답과 이유 보기

invalid_input이다.

명시한 검사 우선순위가 먼저 적용된다.

저장 내부 사전의 순서를 화면이 이용해도 항상 안전한가?

답과 이유 보기

아니다.

공개 계약이 그 순서를 보장하지 않는다.

한 단계 더

프로토타입과 평가

확인할 질문에 맞는 작은 모형을 만든다

종이 화면은 ID 입력 위치와 오류 메시지 이해를 빠르게 살펴볼 수 있다. 와이어프레임은 배치를, 클릭 가능한 모형은 이동을, 동작 프로토타입은 실제 규칙과 상태 전이를 일부 확인한다. 각 모형의 구현 범위를 기록한다.

종이 그림에서 성공 화면을 넘긴 것은 저장 성공을 검증한 것이 아니다. 화면에서 만능 성공 결과를 보여주는 더미도 실제 대출 규칙의 완료가 아니다. 이번 활동은 종이 모형의 설계와 가상 기록 산술만 다루며 실제 구현이나 참여자 시험은 하지 않았다.

평가 계획은 실행 전에 적는다

과업은 가상 도서 B1의 가능 여부를 확인하고 U3에게 대출한 뒤 같은 도서 재요청의 실패를 알아보는 것으로 정한다. 완료는 마지막 실패 메시지의 의미를 참가자가 설명하고 기록 보존을 확인하는 것이다. 시간 제한은 90초, 도움 여부와 중단 이유도 기록하는 계획을 세운다.

기능 검증은 결과·상태·경계 입력을 요구별로 대조한다. 사용자 평가는 실제 대상자가 과업을 이해하는지 관찰한다. 평가자가 답을 대신 알려준 경우와 도움 없는 완료를 구별한다. 친숙한 개발자의 성공을 모든 초보자의 성공으로 확대하지 않는다.

분모와 미완료를 숨기지 않는다

가상 시험표에서 완료한 사람만의 평균 시간을 전체 성공률처럼 쓰면 실패를 숨긴다. 시도 수·완료 수·도움 조건·시간 초과·중단을 함께 기록한다. 시간 제한에 걸린 사람의 실제 완료 시간은 관측되지 않았다.

작은 표의 비율은 관측 범위 안의 설명이며 전 세계 초보자 성공률 추정이라고 단정할 수 없다. 프로토타입 수정 뒤 다른 과업·다른 사람·다른 도움 조건으로 얻은 표는 단순 시간 차이만으로 인과 효과를 선언하지 않는다. 반복 설계는 실패 원인을 기록하고 다음 확인 질문을 정한다.

중간 과정을 따라가는 예제

실제 실험이 아닌 가상 기록 A: 도움 없이 30초 완료, B: 도움 없이 50초 완료, C: 90초 제한까지 미완료에서 완료율과 완료자 평균을 계산하라.

  1. 시도 3, 제한 내 도움 없는 완료 2이므로 완료율은 2/3이다. C는 분모에서 빼지 않는다.

  2. 완료자 평균은 (30 + 50)/2 = 40초다. 이것은 전체 세 명의 완료 시간 평균이 아니다.

  3. C의 완료 시간은 관측하지 못했다. (30+50+90)/3을 전체 완료 평균으로 보고하면 제한 시점을 실제 완료로 바꾼다. 대신 시간 초과 1과 제한 90초를 함께 적는다.

가상 완료율 2/3, 완료자 평균 40초, 시간 초과 1이다. 실제 사용자 결과는 없다.

힌트 보기

같은 완료 정의에서 도움 허용 조건만 분리한다.

풀이 보기

도움 없는 완료는 2/4 = 1/2, 도움 포함 완료는 3/4다. D의 40초를 도움 없는 평균에 넣지 않는다. 실제 평가 자료가 아닌 계산 연습이다.

오해와 반례

프로토타입에서 세 번 성공 화면이 나오면 실제 서비스도 사용성·기능 검증 완료다.

화면 모형·실제 상태 변화·사용자 이해는 서로 다른 증거다. 수행하지 않은 검사와 사용자 평가는 미수행으로 남긴다.
