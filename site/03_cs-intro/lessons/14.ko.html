소단원 14.1

요구사항과 사용자

작은 도서 대출 프로그램에서 무엇을 성공이라고 부를까?

준비 개념과 학습 목표

준비 개념

  • 입력과 출력

  • 조건문

  • 사용자와 상태

학습 목표

  • 사용자 목적과 기능 아이디어를 구별한다.

  • 관찰 가능한 요구사항을 쓴다.

  • 범위·가정·실패 처리와 검증 기준을 연결한다.

같은 도서의 재요청을 성공으로 만들자는 요구가 기존 실패 규칙과 충돌하면 무엇을 고쳐야 할까?

base의 R2는 이미 대출 중인 모든 도서를 실패로 처리한다. 자체 변경안 R5는 같은 대출자가 같은 도서를 다시 요청하면 unchanged_success를 반환하고 기록을 보존한다. R2를 그대로 둔 채 R5를 추가하면 B1이 U3에게 대출 중이고 U3이 요청한 한 사례에 실패와 성공이 동시에 요구된다.

새 규칙을 늘리기 전에 적용 범위를 나눈다. R2를 다른 대출자가 재요청한 경우로 좁히고 R5를 같은 대출자의 경우로 정하면 서로 배타적이다. 새 반환값은 상태가 실제 바뀌는 success와 구별한다. 이 설계는 요청 ID를 저장해 결과를 재생하는 네트워크 재시도 계약과는 다르다.

요구는 관찰할 입력·반환값·직후 기록에 연결한다. 아래 표는 순차 호출과 실패 없는 메모리라는 범위에서의 설계 검산이다. 실제 사용자에게 이 정책이 필요한지 또는 이해하기 쉬운지는 아직 확인하지 않았다.

먼저 확인할 개념
  • 재시도와 효과

    같은 사용자 조건과 요청 ID 재생 조건을 혼동하지 않는다.

  • 검사와 기대값

    요구별 결과 및 상태 보존을 구체적으로 검증한다.

누구의 어떤 일을 돕는지 먼저 적는다

이 단원은 한 권마다 고유한 도서 ID가 있는 작은 대출 기록 시스템을 설계한다. 학생은 빌릴 수 있는지 알고 싶고 담당자는 중복 대출과 잘못된 기록을 막고 싶다. 이름을 예쁘게 정하거나 화면을 먼저 그리는 것만으로 이 두 목적을 확인할 수는 없다.

사용자는 실제로 조작하는 사람이고 이해관계자는 결과의 영향을 받는 사람까지 포함한다. 서로의 요청이 다르면 우선순위와 범위를 정한다. 아래 모델은 한 번에 한 요청을 처리하는 단일 담당자 흐름이다. 여러 장치의 동시 대출·결제·추천·예약은 이번 범위에 넣지 않는다.

기능과 품질·제약을 구별한다

기능 요구사항은 도서의 존재 확인·대출·반납처럼 시스템이 해야 하는 행동이다. 품질 요구사항은 같은 과업을 얼마나 이해하기 쉽거나 빠르게 수행하는지 같은 성질이다. 제약은 사용 가능한 장치·저장 방식처럼 선택을 제한한다.

빠르고 편리하다는 표현만으로는 합격 여부를 정하기 어렵다. 과업·입력·예상 결과·관찰 방법을 적는다. 응답 시간 목표를 정한다면 장치와 자료 크기 및 측정 시작/끝을 함께 정해야 한다. 아직 측정하지 않은 목표를 달성 사실로 쓰지 않는다.

예외와 기준을 같이 남긴다

가상 요구 R1은 대출 가능한 존재 도서와 유효한 대출자 ID가 입력되면 성공하고 그 도서는 해당 대출자의 대출 중 상태가 된다는 것이다. R2는 이미 대출 중인 도서의 요청을 실패로 알리고 기존 기록을 바꾸지 않는 것이다. R3은 없는 도서를 요청하면 없음으로 알리고 기록을 추가하지 않는 것이다.

검증은 구현이 정한 요구를 충족하는지 확인하고, 사용자 목적 검증은 그 요구 자체가 실제 필요를 해결하는지 확인한다. 세 요구를 지키는 구현이라도 학생이 ID를 찾지 못한다면 사용 목적을 못 이룰 수 있다. 실제 사용자와 요구를 확인한 상태와 자체 설계 가정을 구별한다.

입력 ID가 유효하다고 먼저 가정한 표다. 첫째와 둘째 행은 서로 다른 상태이며 마지막 두 행은 소유자 비교로 나뉜다. success 두 종류의 이름이 비슷해도 변경 여부는 다르다.

중간 과정을 따라가는 예제

도서 B1은 대출 가능, B2는 U7에게 대출 중이다. U3이 B1, B2, 없는 B9를 차례로 요청할 때 각 요구와 결과를 연결하라.

  1. B1 요청은 R1에 해당한다. 성공 뒤 B1의 대출자 ID는 U3이다.

  2. B2 요청은 R2다. 실패를 알리고 기존 U7을 보존한다. U3으로 덮어쓰면 R2 위반이다.

  3. B9 요청은 R3다. 없음으로 알리고 새 도서를 자동 추가하지 않는다. 도서 등록은 별도의 기능이다.

성공·대출 중·없음의 세 결과와 상태 변화 여부를 각각 기록한다.

조건을 바꾸어 비교하기

한 입력에 모순된 두 요구

B1:U3에서 U3의 재요청에 원래 R2와 새 R5를 그대로 적용하라.

  1. R2는 대출 중이므로 실패를 요구한다.

  2. R5는 같은 대출자이므로 unchanged_success를 요구한다.

  3. 한 반환이 두 요구를 동시에 충족하지 못한다. 수정 R2의 조건을 다른 사용자로 제한한다.

구현 순서를 바꾸기 전에 요구의 적용 범위를 수정해야 한다.

비교할 점

base의 미정 재시도를 구체적인 요구 충돌 사례로 바꾼다.

정상 상태와 미관측 목적

변경 정책에서 U3이 B1을 재요청하고 U4가 B1을 요청했다. 상태는 B1:U3이다. 두 결과와 사용자 목적 검증 상태는?

  1. U3은 unchanged_success, U4는 already_borrowed다.

  2. 두 호출 모두 기록을 보존한다.

  3. 사용자와 정책의 필요/이해를 확인하지 않았으므로 목적 검증 완료로 세지 않는다.

규칙의 종이 검산과 실제 요구 확인은 별도 결과다.

비교할 점

기능 결과를 목적 달성 증거로 확대하지 않는다.

힌트 보기

풀이 보기

이번 모델은 이미 대출 중으로 실패하고 기록을 보존한다. 같은 요청의 재시도 성공을 원하면 요청 ID와 재시도 정책을 새 요구로 명시하고 관련 검증도 바꿔야 한다.

오해와 반례

작은 프로그램은 정상 입력만 정하면 요구사항이 충분하다.

중복·없는 도서·실패 뒤 상태처럼 실제 흐름을 결정하는 조건도 필요하다. 작다는 이유로 예외 동작을 임의로 추측하지 않는다.

연습 1 · 값과 상태 예측

초기 {B1:available,B2:U7}에서 변경 정책으로 (B1,U3),(B1,U3),(B1,U4),(B9,U3)를 순차 처리하라.

힌트 1

첫 요청만 실제 대출 상태를 만든다.

힌트 2

같은 사용자와 다른 사용자의 재요청을 나눈다.

풀이와 답 확인

  1. 결과는 success, unchanged_success, already_borrowed, not_found다.

  2. 최종 상태는 {B1:U3,B2:U7}이다.

상태가 바뀌는 성공은 1회, 상태를 보존하는 성공은 1회다.

흔한 오답에서 다시 생각하기

두 성공이므로 도서가 두 권 더 생겼다.

반환 분류와 도서 수/갱신 수를 구별하라.

연습 2 · 오류 찾아 고치기

요구 문서에 R2는 모든 재요청 실패, R5는 같은 사용자 재요청 성공이라고 적었다. 충돌을 재현할 가장 작은 유효 사례를 적어라.

힌트 1

도서 하나와 사용자 하나면 된다.

힌트 2

이미 해당 사용자에게 대출 중인 초기 상태를 쓴다.

풀이와 답 확인

  1. 상태 {B1:U3}에 (B1,U3)를 입력한다.

  2. 실패와 unchanged_success가 동시에 요구되어 모순이다.

수정 R2를 다른 사용자로 한정하고 두 결과의 상태 보존을 남긴다.

흔한 오답에서 다시 생각하기

테스트 하나를 지우면 모순은 사라진다.

관찰 사례를 숨겨도 요구의 중첩은 남는다.

연습 3 · 직접 만들어 보기

없거나 이미 대출된 도서에서 기록이 보존됨을 관찰하는 검증 기준을 작성하라.

힌트 1

반환값만으로는 상태 보존을 확인하지 못한다.

힌트 2

호출 전후 전체 기록을 대조한다.

풀이와 답 확인

  1. B2:U7과 B1:available을 초기 상태로 정한다.

  2. (B2,U3)는 already_borrowed, (B9,U3)는 not_found다.

  3. 각 실패 직후 B2:U7/B1:available이고 B9는 존재하지 않아야 한다.

두 검사는 각각 독립 초기 상태에서 수행하도록 계획한다.

흔한 오답에서 다시 생각하기

실패 메시지가 맞으면 저장도 맞다.

반환 성공과 내부 상태 보존은 다른 관찰 대상이다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

반환 이름은 같지만 현재 소유자가 U3이면 성공으로 보는 정책이 원래 R 요청 ID의 재생을 보장하는가?

힌트 1

요청 ID와 사용자 ID는 다른 정보다.

힌트 2

도서가 반납 후 다시 대출 가능한 상황을 생각한다.

풀이와 답 확인

  1. 요청 ID나 과거 결과를 저장하지 않는다.

  2. 과거 요청이 성공한 뒤 반납되어 available이면 같은 사용자 요청도 새 대출 효과가 생긴다.

  3. 따라서 과거 응답 재생이나 중복 효과 방지의 전체 계약을 얻지 못한다.

현재 상태 기반 정책으로 범위를 제한한다.

같은 사용자이므로 모든 재시도는 같은 사건이다.

다른 시점의 새 의도와 과거 요청의 반복을 구별할 정보가 없다.

반납 기능에 사용자 ID를 추가하는 이유는 이름과 타입만으로 알 수 있을까?

새 return_book(book_id,user_id)는 입력 ID 검사→도서 존재→대출 상태→현재 소유자 비교 순서로 처리한다. 유효 ID는 빈 문자열이 아닌 문자열이며 인가된 호출 채널이라고 가정한다. user_id 비교 자체가 실제 로그인 신원을 인증한다는 뜻은 아니다.

결과는 invalid_input, not_found, not_borrowed, not_owner, returned다. returned에서 해당 도서만 available로 바꾸고 나머지는 보존한다. 그 밖의 결과에서는 전체 상태가 그대로다. 여전히 순차 메모리 모형이며 디스크 실패와 동시 실행은 계약 밖이다.

화면은 이 결과와 공개 조회에 의존한다. 저장 구현 A는 사전, B는 ID를 가진 행 목록이라고 해도 공개 결과가 같으면 이 계약에 대한 교체 후보가 될 수 있다. 내부 목록의 첫 행을 B1로 추측하는 화면은 목록 순서가 바뀌면 장벽을 넘은 의존성 때문에 실패한다.

책임과 변경 이유로 나눈다

화면 모듈은 입력을 받고 결과를 설명한다. 대출 규칙 모듈은 가능 여부와 상태 전이를 정한다. 저장 모듈은 기록을 조회·저장한다. 모듈은 단순히 파일을 많이 만드는 것이 아니라 책임과 의존 관계를 나누는 단위다.

화면이 저장 내부의 배열 위치를 직접 수정하면 저장 방식이 바뀔 때 화면도 함께 고쳐야 한다. 필요한 기능을 공개 인터페이스를 통해 호출하면 내부 구현을 숨길 수 있다. 다만 계약에 실제로 필요한 동작을 빠뜨리면 독립 변경의 근거가 부족하다.

함수 이름과 타입만으로는 부족하다

자체 대출 서비스 borrow(book_id,user_id)는 빈 문자열이 아닌 ID를 받고 success, already_borrowed, not_found, invalid_input 중 한 결과를 돌려준다. invalid_input을 먼저 검사하고 그다음 도서 존재·대출 중 상태를 확인한다. 결과와 상태 변화를 계약에 함께 적는다.

success이면 한 도서의 대출자를 바꾸고 다른 도서는 보존한다. 나머지 결과이면 모든 기록을 보존한다. 이번 종이 모델은 실패 없는 메모리 저장과 순차 호출을 가정한다. 실제 디스크 실패나 여러 요청의 경쟁 상태는 별도의 오류/동시성 계약이 필요하다.

약속을 통해 구현을 교체한다

클라이언트인 화면은 반환 결과와 공개 조회 기능을 사용하고 내부 사전 순서나 저장 파일 형식을 추측하지 않는다. 구현자는 사전을 파일 또는 데이터베이스로 바꾸더라도 동일한 계약을 유지해야 한다. 이 경계를 추상화 장벽이라 부른다.

자료 전달 때 ID의 문자열 규약·빈 값·결과 종류·기존 값 보존을 맞춘다. 입력을 잘못 받으면 아무 일도 안 한다는 보장이 필요한지, 사전조건만 두고 호출자 책임으로 할지도 명시한다. 여기서는 잘못된 입력을 실제 검사하고 결과로 알리는 계약을 택했다.

성공 화면을 본 사람과 실제 반납 기록을 이해한 사람을 같은 완료 수로 세면 어떤 결함을 놓칠까?

새 과업은 B1의 반납을 수행하고 그 뒤 available임을 설명하는 것이다. 가상 기록에서 화면 단계 도달, 실제 모형의 기록 상태, 참가자의 설명을 세 열로 나눈다. 화면은 안내를 보여 주어도 기록 갱신이 없을 수 있고, 기록이 맞아도 사용자가 다른 도서 상태로 오해할 수 있다.

계획상 60초 이내이며 도움 없이 올바른 최종 상태를 설명해야 완료다. 아래 다섯 행은 실제 사람이 아닌 계산용 합성 자료다. 60초 한계에 걸린 행의 진짜 완료 시각은 알 수 없으며, 기록된 종료까지 시간 평균과 완료자의 시간 평균을 구별한다.

더 빠른 후보가 완료율은 낮을 수 있다. 선택 목적이 도움 없는 완료를 우선한다면 성공자 평균만으로 후보를 고르지 않는다. 다른 사람의 기록을 비교해 화면 변경의 인과 효과를 확정하지 않고 다음 동일 조건 확인을 계획한다.

먼저 확인할 개념
  • 분모와 최종 상태

    어떤 사건을 성공으로 세는지 먼저 고정한다.

  • 목표 집단과 평가 기준

    작은 합성 비율을 전 세계 사용자 성능으로 확대하지 않는다.

확인할 질문에 맞는 작은 모형을 만든다

종이 화면은 ID 입력 위치와 오류 메시지 이해를 빠르게 살펴볼 수 있다. 와이어프레임은 배치를, 클릭 가능한 모형은 이동을, 동작 프로토타입은 실제 규칙과 상태 전이를 일부 확인한다. 각 모형의 구현 범위를 기록한다.

종이 그림에서 성공 화면을 넘긴 것은 저장 성공을 검증한 것이 아니다. 화면에서 만능 성공 결과를 보여주는 더미도 실제 대출 규칙의 완료가 아니다. 이번 활동은 종이 모형의 설계와 가상 기록 산술만 다루며 실제 구현이나 참여자 시험은 하지 않았다.

평가 계획은 실행 전에 적는다

과업은 가상 도서 B1의 가능 여부를 확인하고 U3에게 대출한 뒤 같은 도서 재요청의 실패를 알아보는 것으로 정한다. 완료는 마지막 실패 메시지의 의미를 참가자가 설명하고 기록 보존을 확인하는 것이다. 시간 제한은 90초, 도움 여부와 중단 이유도 기록하는 계획을 세운다.

기능 검증은 결과·상태·경계 입력을 요구별로 대조한다. 사용자 평가는 실제 대상자가 과업을 이해하는지 관찰한다. 평가자가 답을 대신 알려준 경우와 도움 없는 완료를 구별한다. 친숙한 개발자의 성공을 모든 초보자의 성공으로 확대하지 않는다.

분모와 미완료를 숨기지 않는다

가상 시험표에서 완료한 사람만의 평균 시간을 전체 성공률처럼 쓰면 실패를 숨긴다. 시도 수·완료 수·도움 조건·시간 초과·중단을 함께 기록한다. 시간 제한에 걸린 사람의 실제 완료 시간은 관측되지 않았다.

작은 표의 비율은 관측 범위 안의 설명이며 전 세계 초보자 성공률 추정이라고 단정할 수 없다. 프로토타입 수정 뒤 다른 과업·다른 사람·다른 도움 조건으로 얻은 표는 단순 시간 차이만으로 인과 효과를 선언하지 않는다. 반복 설계는 실패 원인을 기록하고 다음 확인 질문을 정한다.

중간 과정을 따라가는 예제

실제 실험이 아닌 가상 기록 A: 도움 없이 30초 완료, B: 도움 없이 50초 완료, C: 90초 제한까지 미완료에서 완료율과 완료자 평균을 계산하라.

  1. 시도 3, 제한 내 도움 없는 완료 2이므로 완료율은 2/3이다. C는 분모에서 빼지 않는다.

  2. 완료자 평균은 (30 + 50)/2 = 40초다. 이것은 전체 세 명의 완료 시간 평균이 아니다.

  3. C의 완료 시간은 관측하지 못했다. (30+50+90)/3을 전체 완료 평균으로 보고하면 제한 시점을 실제 완료로 바꾼다. 대신 시간 초과 1과 제한 90초를 함께 적는다.

가상 완료율 2/3, 완료자 평균 40초, 시간 초과 1이다. 실제 사용자 결과는 없다.

초기 {B1:U3,B2:U7}에서 T2 반납 계약으로 (B1,U4),(B1,U3),(B1,U3),(B9,빈 ID)를 순차 처리하라. 반환·전체 상태·실제 변경 수를 보고한다. 다른 저장 구현이 not_owner에서 B1을 available로 바꾸면 어떤 요구와 계약을 위반하는지 적어라. T3 합성 표의 화면 도달률·도움 없는 완료율·도움 포함 완료율·도움 포함 완료자 평균도 구하라. 이 계산으로 실제 사용자 필요나 저장 구현 완료를 주장할 수 있는가?

힌트 1

입력 검사가 존재 검사보다 앞서며 실패는 모든 기록을 보존한다.

힌트 2

합성 표에서는 A만 도움 없는 완료이고 D는 도움 포함 완료다. 종료 시각과 완료 시각을 구별한다.

풀이와 답 확인

  1. 반환은 not_owner, returned, not_borrowed, invalid_input이다. B1 상태는 U3, available, available, available 순서이며 B2는 계속 U7이다.

  2. 실제 기록 변경은 두 번째 호출의 1회다. 같은 도서의 여러 호출을 모두 변경 수로 세지 않는다.

  3. 오류에서 B1을 지운 구현은 not_owner 사후조건과 기존 기록 보존 요구를 위반한다. 동일 반환 타입만으로 교환 가능한 구현이 아니다.

  4. 화면 도달은 4/5, 도움 없는 완료는 1/5, 도움 포함 완료는 2/5다. 도움 포함 완료자 평균은 (20+40)/2=30초다.

  5. 순차 메모리 모형의 설계 검산과 합성 산술만 수행했다. 실제 프로그램·저장·사용자/학생 평가 및 정책 필요 확인은 미수행이다.

최종 {B1:available,B2:U7}, 변경 1회다. 반환 및 상태 보존을 함께 점검한다. 합성 지표는 80%/20%/40%, 도움 포함 완료자 평균 30초다. 실제 사용자/구현 완료 증거로 확대하지 않는다.

해결한 뒤 점검할 것

  • 검사 우선순위와 각 반환의 사후 상태를 연결한다.

  • 대상 도서만 바뀌고 다른 도서는 보존됨을 추적한다.

  • 동일 타입과 전체 의미 계약의 충족을 구별한다.

  • 화면/상태/설명/도움의 완료 기준과 분모를 분리한다.

  • 모형·합성 계산과 실제 요구 확인/구현/참여자 시험의 수행 상태를 구별한다.
