소단원 9.1

파일과 레코드

글자 한 줄을 저장하면 누구나 같은 세 개의 정보로 읽을 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 준비개념: 값 하나를 필드, 관련 필드의 묶음을 레코드라고 부른다.

  • 미니복습: 쉼표는 값의 일부일 수도, 필드를 나누는 기호일 수도 있다. 읽는 규칙이 필요하다.

  • 자가진단: 번호17,이름민지,점수82를 한 학생 레코드로 묶어 보자. 번호와 점수를 서로 바꾸면 다른 뜻이 된다.

학습 목표

  • 파일에 저장한 표현과 읽어 얻는 레코드를 구분한다.

  • 구분자·따옴표·필드 순서·값 변환 규칙을 명시한다.

  • 파싱 성공과 데이터 계약 충족을 따로 검사한다.

각 레코드는 올바른데 목록 전체를 저장하면 왜 거절될까?

기본 CSV 계약을 유지하고 여기서는 큰따옴표 안의 큰따옴표를 두 번 써서 한 글자로 읽는 규칙을 명시한다. 예를 들어 7,"나래 ""N""",90의 이름은 나래 "N"이다. 파싱 후 얻은 문자열과 원문 인용 기호를 구별한다. 문자를 단순히 쉼표에서 잘라 이 규칙을 구현했다고 하지 않는다.

각 레코드의 id 양수·이름 비어 있지 않음·점수 정수 0..100 조건을 통과해도, 전체 id가 유일하다는 조건은 목록을 함께 봐야 한다. 순차 가져오기는 이미 통과한 id를 seen에 기억하고 중복이면 그 레코드를 거절한다. 이 정책은 교육 모형이며 실제 파일 파서나 DB 동시 삽입을 실행하지 않는다.

먼저 확인할 개념
  • 타입과 값의 두 검사

    파싱 문자열의 정수 변환과 값 범위를 별도로 확인한다.

  • 키로 현재 값을 찾기

    seen에 이미 저장한 식별자인지 물어 전체 중복을 판정한다.

내용과 구조를 함께 정하기

파일은 저장한 데이터에 접근하는 단위이고 레코드는 이 수업에서 한 대상을 설명하는 필드 묶음이다. 레코드를 파일에 표현할 때는 필드 순서와 경계를 약속한다. 학생 레코드의 (id,name,score)와 (score,name,id)는 같은 숫자 세 개를 담아도 의미가 다르다. 파일 확장자만으로 실제 내용의 규칙이 정해졌다고 가정하지 않는다.

스키마라는 말은 필드 이름·종류와 제약 같은 구조의 약속을 가리킨다. 여기의 작은 스키마는 id가 양의 정수, name은 빈 문자열이 아닌 문자열, score는 0부터100까지 정수라고 정한다. 이 규칙은 우리가 만든 교육용 계약이며 모든 CSV 파일에 자동으로 적용되는 표준 규칙이 아니다.

쉼표와 따옴표가 맡는 일

CSV의 한 변형에서 쉼표는 필드 구분자이고 큰따옴표로 감싼 필드 안의 쉼표는 값의 일부다. 그래서 17,"민지, 김",82는 세 필드이며 이름은 민지, 김이다. 쉼표에서 무조건 잘라 버리면 이름을 둘로 나누어 잘못된 네 필드가 된다. 어떤 구분자와 인용 규칙을 사용하는지 먼저 고정한다.

Python csv 문서는 dialect에 따라 구분자와 인용 처리가 달라질 수 있음을 설명한다. 기본 reader의 반환 필드는 문자열이고 정수 변환은 별도 작업이다. 큰따옴표 안에 줄바꿈을 허용하는 형식에서는 레코드 하나가 여러 물리 줄에 걸칠 수도 있다. 따라서 줄 수와 레코드 수를 같은 지표로 쓰지 않는다.

읽히는 자료와 믿을 수 있는 자료

문법상 세 필드로 읽혔다고 내용이 올바른 것은 아니다. "eight"가 점수 필드에 들어오면 정수로 변환할 수 없고, "120"은 정수로 바꿀 수 있어도 점수 범위를 벗어난다. 필드 개수→종류 변환→값 조건→필요한 중복 확인을 순서대로 분리해 이유를 기록한다.

입력 오류를 조용히 0으로 바꾸면 실제 0점과 읽기 실패가 섞인다. 실패한 레코드의 원문 위치와 원인을 남기고, 전체 가져오기를 중단할지 그 레코드만 제외할지 정책을 정한다. 본문은 종이 레코드를 읽는 연습이며 실제 파일 인코딩·파일 권한·스트리밍 파서의 검증은 다음 실습에서 별도로 해야 한다.

중간 과정을 따라가는 예제

스키마(id,name,score)는 양의 정수 id / 빈값이 아닌 name / 0..100 범위의 정수 score이다. 쉼표 구분, 큰따옴표 인용, 인용 안의 쉼표는 내용이라는 규칙으로 17,"민지, 김",82와 18,도윤,120을 독립 판정한다.

  1. 첫 표현을 읽으면 문자열 필드 ["17","민지, 김","82"] 세 개다. 인용 기호 자체는 이름 값에 포함하지 않는다.

  2. id를 17, score를 82로 정수 변환한 뒤 17>0, 이름이 비어 있지 않음, 0≤82≤100을 확인하므로 첫 레코드는 통과한다.

  3. 둘째 표현도 문자열 필드 ["18","도윤","120"] 세 개로 읽힌다. 정수 변환도 가능하다.

  4. 하지만 120>100이어서 점수 조건을 실패한다. 문법 파싱 실패가 아니라 값 범위 실패라고 기록한다.

첫 레코드는 통과하고 둘째는 점수 범위 위반이다. 120을 임의로 100이나 0으로 고치는 규칙은 정의하지 않았다.

조건을 바꾸어 비교하기

따옴표도 값으로 복원한다

7,"나래 ""N""",90을 고정 규칙으로 읽고 이름 안의 두 큰따옴표가 어떻게 저장되는지 적어라.

  1. 세 문자열은 "7", 이름 나래 "N", "90"이다.

  2. 바깥 인용 기호는 필드 경계이며 내부의 "" 쌍은 큰따옴표 한 글자로 읽힌다.

  3. 정수 변환 후 id 7과 점수 90은 지역 조건을 통과한다.

큰따옴표는 이름 값에 두 글자 들어가지만 원문에는 내부 인용 쌍 네 글자가 있다.

비교할 점

기본 인용 쉼표에서 인용 기호 자체를 값에 포함하는 경우로 확장한다.

실패 레코드는 새 키를 차지하지 않는다

빈 seen에서 8,도윤,120 다음 8,도윤,80을 순서대로 검사하라. 지역 실패는 저장도 seen 갱신도 하지 않는다.

  1. 첫 레코드는 범위 실패라 seen은 빈 상태다.

  2. 둘째 레코드는 지역 조건을 통과하고 id 8도 아직 없다.

  3. 둘째만 반영하고 seen={8}로 만든다.

둘째는 중복 실패가 아니다. 실패 시 상태 보존의 정책을 지킨다.

비교할 점

단순 원문 id의 등장 여부와 성공 반영된 키를 구별한다.

종이와 본문으로 직접 해보기

같은 계약으로 19,서연,eight와 20,,0을 판단하자. 어떤 검사에서 처음 실패하는지 적고 정상 0점 레코드21,지우,0과 비교하자.

힌트 보기

빈 이름과 정수 0을 구별한다. 점수 문자열이 정수로 바뀔 수 있는지 먼저 확인한다.

풀이 보기

19,서연,eight는 세 필드로 읽혀도 점수 정수 변환 단계에서 실패한다. 20,,0은 id 20과 점수 0은 허용되지만 name이 빈 문자열이라 실패한다. 21,지우,0은 세 조건을 모두 통과한다. 오류를 0으로 대체하면 첫 실패를 정상 0과 구별하지 못한다.

오해와 반례

한 줄은 언제나 한 레코드이며 쉼표로 나누기만 하면 CSV를 제대로 읽는다.

인용된 "민지, 김" 안의 쉼표는 필드 구분이 아니다. 문서가 설명하는 인용된 줄바꿈도 물리 줄 수와 레코드 수가 다를 수 있는 반례다. 이 단원 예제는 줄바꿈 없는 고정 규칙의 일부이고 모든 CSV 변형을 구현하지 않는다.

소단원 9.2

관계형 데이터와 SQL 개관

표의 어디에 저장했는지 몰라도 조건에 맞는 행을 요청할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 준비개념: 열은 속성,행은 속성값의 묶음이다. 이 예제는(id,name,score)열을 쓴다.

  • 미니복습: 조건 score≥80은80을 포함하고79는 제외한다.

  • 자가진단: 같은 이름인 두 사람을 이름만으로 구분할 수 있는가? 고유id를 따로 적어 보자.

학습 목표

  • 행과 열,스키마와 실제 데이터를 구분한다.

  • SELECT/FROM/WHERE의 역할을 작은 표로 추적한다.

  • ORDER BY 없는 결과의 순서를 저장 순서와 동일시하지 않는다.

다른 학생을 조회했는데 이름만 보면 같은 행으로 보이는 이유는?

이번 students는 (id,name,score)이고 id가 고유하며 모든 값은 NOT NULL이다. 네 행 (1,가람,90),(2,가람,80),(3,나래,90),(4,다온,70)을 쓴다. id는 서로 다른 대상을 구별하지만 SELECT에서 그 열을 버리면 결과의 식별 정보가 줄어든다.

WHERE의 행 조건, SELECT의 출력 열, DISTINCT의 출력 중복 제거, ORDER BY의 순서 계약은 별개다. DISTINCT name은 같은 이름을 하나로 보일 뿐 실제 학생을 병합하거나 저장 행을 지우지 않는다. 여기의 순서 판단은 종이 조회 의미이며 SQL 실행 계획이나 성능 측정이 아니다.

먼저 확인할 개념
  • 정렬과 키의 의미

    값이 같은 출력의 동률과 원대상 식별을 구별한다.

  • 전체 유일 키

    입력의 id 유일성과 출력 열의 유일성을 혼합하지 않는다.

행의 의미와 식별자

관계형 모델은 이름 붙인 속성과 튜플의 관계를 중심으로 자료를 다룬다. 입문에서는 표의 열과 행으로 그 의미를 읽는다. SQL 표는 중복 행이나 NULL 같은 기능을 가질 수 있으므로 수학적 집합과 완전히 같은 규칙으로 처리한다고 단정하지 않는다. 고유한 행 식별이 필요하면 키 제약을 명시한다.

이 수업의 students에는 고유한 id, 이름 name, 정수 점수 score가 있다. 이름이 같은 두 학생도 id가 다르면 다른 행이다. 행의 물리적 위치를 바꾸어도 같은 id의 대상이 갑자기 다른 학생이 되어서는 안 된다. 정확히 한 행을 수정하려면 행 번호나 표시 순서보다 어떤 키로 대상을 찾는지 먼저 정한다.

무엇을 원하는지 적는 조회

SELECT는 반환할 열·식을,FROM은 읽을 표를,WHERE는 남길 행의 조건을 표현한다. SELECT id,name FROM students WHERE score>=80은 students에서 조건을 만족하는 행의 id와 name을 요청한다. 이 읽는 순서는 뜻을 이해하기 위한 논리 설명이며 실제 DBMS가 반드시 한 행씩 그 순서로 처리한다는 실행 계획은 아니다.

SQL은 요청 결과를 표현하고 DBMS가 적합한 처리 방법을 고를 수 있다. 같은 조회도 인덱스나 저장 상태에 따라 실행 경로가 달라질 수 있다. 여기서는 작은 표에서 결과를 종이로 계산할 뿐 인덱스가 어떤 속도를 냈는지 측정하지 않는다. 사용자 입력을 SQL문자열에 직접 붙이는 구현도 이 본문에서 만들지 않는다.

결과 순서는 별도의 요구

ORDER BY score DESC,id ASC는 점수가 큰 행을 앞에 두고 같은 점수이면 id가 작은 행을 앞에 둔다. 두 단계의 정렬 조건을 함께 읽는다. id가 고유하면 이 예제의 동률도 완전히 정해진다. 동률을 끝까지 구분하는 키가 없으면 같은 정렬값끼리의 순서를 별도로 보장했다고 말하지 않는다.

ORDER BY를 생략한 결과는 특정 순서를 기대하지 않는다. 어제 출력한 순서가 오늘도 같았다는 관찰은 앞으로도 같은 순서를 보장하는 계약이 아니다. 종이 예제의 표시 순서와 조회가 보장하는 순서를 분리해서 적는다. NULL 처리와 조인은 데이터베이스 과목에서 더 자세히 이어 공부할 수 있다.

정해진 세 행 순서

표의 쉼표 나열은 내용 설명이다. ORDER BY 없는 두 행의 실제 출력 순서를 지정하지 않았다. 마지막은 점수 동률 90에서 고유 id로 끝까지 구분한다.

중간 과정을 따라가는 예제

students의 행은(1,가람,90),(2,나래,70),(3,다온,90),(4,라온,80)이고 id는 고유하며 모든 값은 NOT NULL이다. SELECT id,name FROM students WHERE score>=80 ORDER BY score DESC,id ASC;의 예상 결과를 종이로 구하라.

  1. WHERE를 적용하면90≥80인id1과id3,80≥80인id4가 남고70점id2는 제외된다.

  2. 남은 행의 점수 내림차순은90,90,80이다. 90점 두 행은 id 오름차순으로 1 다음 3이다.

  3. SELECT에 지정한 열만 남겨(1,가람),(3,다온),(4,라온)을 적는다. 출력 열에 score가 없어도 이 예제에서는 score를 정렬 조건으로 사용할 수 있다.

  4. 결과는 세 행이며 순서는 정렬조건에 따른다. 이 SQL을 실제 DBMS에서 실행한 결과는 아니다.

예상 행은 순서대로(1,가람),(3,다온),(4,라온)이다. 가정의 표와 쿼리를 기준으로 한 종이 판정이다.

정렬 동률과 전순서

오해와 반례

SQL은 파일에 적은 순서대로 결과를 돌려주므로 ORDER BY는 꾸미기 기능이다.

공식 PostgreSQL 문서는 정렬을 명시하지 않은 결과 순서를 보장하지 않는다. 처리 계획이 달라져도 같은 행 내용의 조회가 가능하다. 순서가 요구사항인 화면이나 비교 문제에서는 ORDER BY와 필요한 동률 키를 계약에 넣는다.

준비 개념과 학습 목표

준비 개념

  • 미니복습: 100에서 30을 빼고 20에 30을 더하면 합계 120을 유지한다.

  • 자가진단: 점수가 정수라는 규칙만으로 0..100 범위와 id 중복 금지가 자동으로 따르는가?

합계가 맞는 저장 결과만으로 이체의 모든 계약을 확인할 수 있을까?

기본 순차 이체 (A−d,B+d)는 합계를 보존하지만 음수 금지까지 보존하려면 허용 d를 제한해야 한다. 예를 들어 A=10,B=20,d=15는 결과 (−5,35)로 합계 30은 같아도 A의 음수 조건을 깨뜨린다. 원자적으로 저장했다는 말과 허용 상태라는 말은 분리한다.

데이터 품질의 분모도 분리한다. 입력 4개 중 파싱 4개·지역 유효 3개·전체 유효 반영 2개라면 각 성공률이 다르다. 제약 통과 뒤에도 실세계 사실의 정확성은 원본 근거로 확인해야 한다. 실제 금융·학생 자료나 DBMS를 사용하지 않고 가상 모형만 분석한다.

먼저 확인할 개념
  • 타입과 업무 조건

    정수 합계와 허용 잔액 범위는 다른 조건이다.

  • 지역 검사와 전체 검사

    품질 지표의 단계와 각 분모를 명시한다.

허용 상태를 말로만 두지 않기

자료가 읽히는지, 값의 종류가 맞는지, 범위가 맞는지, 서로 참조하는 기록이 있는지 검사하는 조건은 다르다. 점수 INTEGER만으로 0..100이 보장되지 않고, 양의 id만으로 전체 중복 금지가 보장되지 않는다. 각 문제를 어느 제약으로 표현할지 분리해야 실패 이유를 알 수 있다.

PostgreSQL의 PRIMARY KEY는 식별값의 유일성과 NULL 금지를 함께 요구한다. NOT NULL은 값 없음 표시를 금지하고 CHECK는 값 조건을 표현한다. 단순 CHECK(score>=0 AND score<=100)는 NULL 값까지 금지하는 것으로 가정하지 않고 별도 NOT NULL을 함께 둔다. 이 차이는 해당 DBMS의 공식 규칙을 읽어 확인했다.

여러 변경을 한 묶음으로 보기

트랜잭션은 관련 DB 변경을 한 묶음으로 다루는 수단이다. 송신 기록에서 30을 빼고 수신 기록에 30을 더하는 두 변경의 한쪽만 영구 반영되면 총합이 달라진다. PostgreSQL 입문 문서는 BEGIN과 COMMIT으로 묶고 전체 ROLLBACK으로 그 묶음의 변경을 취소하는 경로를 설명한다.

원자성은 계약이 틀린 계산을 자동으로 고치는 기능이 아니다. 두 쪽에서 각각 30을 빼는 코드를 한 묶음으로 성공적으로 저장하면 묶음은 완료되어도 우리가 원한 총합은 깨진다. 실제 동시 거래의 경쟁과 장애 복구는 격리 수준·제약·구현을 추가로 분석해야 하며 종이의 두 숫자만으로 검증하지 않는다.

형식의 일관성과 사실의 정확성

한 학생의 점수를 두 파일에 복사하고 하나만 수정하면 어느 값이 기준인지 불명확해질 수 있다. 원본의 위치와 변경 이력, 기준 시점을 정하는 것이 도움이 된다. 조회 자료가 언제의 상태인지 설명하지 않으면 지난주와 오늘의 값 차이를 곧바로 오류라고 판정할 수도 없다.

모든 범위와 키 제약을 통과한 점수 82라도 원시험 점수가 28이었다면 실세계 사실을 잘못 기록한 것이다. DBMS는 대개 정한 제약과 저장 동작을 관리하며 실제로 시험지를 채점하지 않는다. 데이터 품질 검토에는 원본 근거·단위·입력 경로를 대조하는 일이 추가로 필요하다. 실제 학생 자료를 사용하지 않고 가상 데이터로 이 구분을 연습한다.

중간 과정을 따라가는 예제

가상 계정 A=100,B=20이고 음수 금지와 합계 120 유지가 계약이다. A에서 B로 30을 옮긴다. 모든 값은 정수이고 다른 동시 작업은 없다. 두 변경 모두 반영, 첫 변경만 반영, 첫 변경 후 전체 취소의 상태를 비교하라.

  1. 초기 상태 (100,20)의 합은 120이다. A에서 30을 빼면 임시 상태 (70,20)이고 합 90이다.

  2. B에 30을 더하는 두 번째 변경까지 반영하면 (70,50), 합 120이고 두 잔액 모두 음수가 아니다.

  3. 첫 변경만 영구 반영하면 (70,20), 합 90으로 계약을 깨뜨린다. 한 묶음으로 전체 또는 없음을 요구하는 이유다.

  4. 첫 변경 후 그 묶음을 전체 취소하면 초기 (100,20), 합 120으로 돌아간다. 이는 종이의 효과 모형이며 실제 DB 장애를 발생시켜 확인한 것이 아니다.

완료는 (70,50), 전체 취소는 (100,20)이다. 첫 변경만 남은 (70,20)은 허용하지 않는 중간 영구 상태다. 두 변경의 옳은 식을 먼저 작성해야 한다.

힌트 1

첫 id 2의 인용 이름을 복원하고 id 3의 범위를 확인한다. 마지막 id 2는 P의 앞 반영뿐 아니라 배치 전체 키에서도 중복이다.

힌트 2

Q에서 임시 검토한 행을 커밋된 저장 행으로 혼동하지 않는다. 조회는 최종 상태에서만 계산한다.

풀이와 답 확인

  1. 세 원문은 각 3필드다. 첫 이름은 가람 "G", 점수 80이다.

  2. 첫 레코드는 통과, 둘째는 점수 120 범위 실패, 셋째는 배치 중복 id 2다.

  3. P는 첫 레코드만 추가하므로 저장은 기존 id 1과 새 id 2다. QUERY 순서는 (1,가람),(2,가람 "G")다.

  4. Q는 배치 실패라 신규 반영 0개로 기존 id 1만 남으며 QUERY도 (1,가람) 한 행이다.

  5. P 전체 입력 반영률은 1/3이고 Q는 0/3이다. 정책을 밝히지 않고 하나의 정답 성공률을 주장하지 않는다.

P: id 1/2 두 행, 조회 순서 1→2. Q: id 1만 유지, 조회 1 한 행. 범위/전체 중복 실패와 정책별 반영 단위를 구별한다.
