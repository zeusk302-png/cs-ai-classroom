小節 1.1

入力・処理・出力

コンピュータに友達3人の最高点を求めてもらうとき、2人が同点だったら、誰の名前を表示するかも自動で決めてくれるでしょうか。

準備する概念と学習目標

準備する概念

  • 7 > 4 が成り立つか判断する。大小比較に慣れていなければ、数直線で右にある数ほど大きいことを確認しよう。
  • 規則を1行ずつ順番にたどり、その時点の値を紙に書く。変数は現在の値に結び付けた名前と考えてよい。

学習目標

  • 入力の型と許される値を定め、出力が何を意味するか説明する。
  • 3つの数から最大値を求める手順をたどり、同点と負数の反例を調べる。
  • 意図した目的と実際に定めた計算が異なる場合を説明する。

目的を明確な計算の約束にする

「一番よかった人を教えて」は、人にとっても曖昧です。「一番」は最高点なのか、最も努力した人なのか。同点ならどう表示するのか。この小節では入力を3つの整数 a、b、c に限り、出力をその最大整数 m とします。人の名前も返すなら、別の仕様が必要です。仕様は実装の前に、入力と結果が満たすべき関係を定めます。

数学的には入力の集合 D は Z³、つまり整数の順序付き3つ組 (a,b,c) の集合です。出力 m は a、b、c のいずれかであり、すべての入力値以上でなければなりません。整数が比較でき、許される値を十分に表現できる範囲があると仮定します。「missing」という文字列や値の欠落は D の外です。実際の製品では、これらを拒否するか、別の結果で扱うかも定める必要があります。

入力・処理・出力を区別する

入力は計算に渡すデータです。処理は規則に従ってデータと現在の状態を操作します。出力は利用者や別の計算に渡す結果です。最初から答えを与えても、最大値の求め方を説明したことにはなりません。手順を定めれば、同じ入力を紙でたどれます。ここでは m を a で初期化し、b の方が大きければ m を更新して、c についても同じように比較します。

値を返すことと表示することは異なります。最大値関数が 8 を返したのに呼び出し側が 6 を表示したなら、計算と表示を別々に調べられます。すべてのプログラムが1回の入力と出力で終わるわけではありません。ゲームやサーバーは入力イベントと状態変化に繰り返し応答するため、入力・処理・出力の図にも現在の状態と次の状態が必要です。

小さな不変条件で正しさを説明する

最初の比較の前は m=a で、これまで見た1つの数の最大値です。b を比較すると、2つの数の大きい方が m に残ります。c を比較した後は、3つの最大値が残ります。処理の中の特定の箇所で繰り返し成り立つ性質を不変条件と呼びます。「m はこれまで見た数の最大値」という性質は、初期化・更新・終了をつなぎます。いくつかの例に偶然成功するよりも強い根拠になります。

出力が値だけなら、厳密な大小比較 > で同点も正しく扱えます。ただし最大値の位置も返す場合、先の位置を保つか最後の位置に更新するかで同点の扱いが変わります。また、入力がすべて負数のとき m を 0 から始めるのは誤りです。入力にない 0 を返す可能性があります。実際の入力値から始めれば、この反例を避けられます。

m ← a
if b > m: m ← b
if c > m: m ← c
return m  // 擬似コード。実行結果ではない

途中の過程をたどる例題

3つの整数 (-4,-1,-1) から最大値だけを返す。同点の人の名前は返さない。

  1. m=-4 と初期化する。これまで見た値は [-4]。
  2. b=-1 と m=-4 を比較する。-1>-4 なので m=-1 に更新する。これは [-4,-1] の最大値。
  3. c=-1 と m=-1 を比較する。-1>-1 は偽なので m=-1 を保つ。
  4. m が入力値の1つであり、すべての入力値以上であることを確認する。

最大値は -1。2つの入力が同じ最大値でも、出力は1つの値です。比較は2回行いました。

紙と本文で試してみよう

カードに 8、8、3 と書き、同じ手順をたどろう。その後、最大値が最初に現れる位置も返すように規則を拡張しよう。位置は1から数え、同点なら先の位置を選ぶ。

ヒントを見る

m と一緒に位置 p も覚えておく。厳密に大きい値を見つけたときだけ m と p を両方更新する。

解答を見る

(m,p)=(8,1) から始めます。2つ目の 8 は大きくないので両方を保ち、3つ目の 3 でも変わりません。結果は (8,1)。> を >= に変えて毎回位置を更新すると、同点で p が 2 に変わり、仕様に反します。

よくある誤解と反例

「一番よいもの」を探すよう頼めば、コンピュータは目的を自動で理解する。

最高点と最大の努力は異なる関係です。入力に努力についての情報がなければ、比較する根拠はありません。同点から1人を選ぶ規則も人が決めます。学習を使うシステムにも入力・目的・評価基準が必要で、出力が仕様を満たすことは自動では保証されません。

理解を確かめる

点数 4、9、2 と「最大値は 9」という説明で、入力と出力は何か。

答えと理由を見る

入力は 4、9、2、出力は 9。

規則に3つの数を渡し、比較の結果を返すからです。

入力 -7、-2、-5 に対して m を 0 から始めると、何が起きるか。

答えと理由を見る

誤って 0 を返す。正しい結果は -2。

0 は入力値ではなく、初期化の時点で m が見た値の最大値になっていません。

値だけを返す仕様なら、6、6、6 は無効な入力か。

答えと理由を見る

無効ではない。出力は 6。

同点でも最大値は存在します。1人を選ぶ問題は別です。

もう一歩先へ

n 個の整数へ拡張しよう。n≥1 なら最初の要素で初期化し、残りを1回ずつ比較するので比較は n−1 回です。「k 個処理した後、m はその k 個の最大値」と帰納的に説明しよう。空のリストには最初の要素がなく、同じ初期化はできません。空入力を禁止するか、別の「結果なし」の値を導入する必要があります。

小節 1.2

問題分解と抽象化

クラスの図書貸出サービスを設計するとき、すべての本の表紙の色を記録する必要はあるでしょうか。

準備する概念と学習目標

準備する概念

  • 入力と結果を区別する。「本の識別子を渡して、貸出可能か答える」で両方を指摘する。
  • 規則を順番に適用し、ある段階の結果を次の段階の入力にできる。

学習目標

  • 分解と抽象化を区別し、簡単なモジュールの約束を書く。
  • 必要な情報を捨てると何が起きるか、反例で示す。
  • 部分ごとの仕様をつなげて全体の目的を達成するための条件を説明する。

分解で責任を分ける

貸出を1つの大きな仕事として扱うと、会員確認、本の検索、貸出可能かの判定、記録の保存が混ざります。問題分解では、責任の明確な小さな仕事に分けます。「会員確認」は会員識別子を受け取り有効か返し、「本の検索」は本の識別子を受け取り現在の状態を返します。入力・出力・失敗時の結果を書くと、変更する部分を見つけやすくなります。

細かくすれば必ずよくなるわけではありません。責任を分けた結果、複数の箇所で同じ状態を一緒に更新しなければならなくなると、接続の管理が難しくなります。この単元では1人が順番に処理し、同時の貸出要求はないと仮定します。実際に2人が同じ本を同時に借りようとするなら、貸出可能かの確認と記録更新の間の競合を防ぐ別の設計が必要です。

抽象化では目的に必要な情報を残す

抽象化とは、知りたいことに必要な区別を残し、他の細部を隠して状況をモデル化することです。貸出可能かを決めるには本の識別子と貸出中かが重要で、通常は表紙の色は不要です。色が違っても貸出状態が同じ本を同じように扱って、答えは変わりません。しかし表紙の色で探すサービスでは色を捨てられません。抽象化の適切さは目的に依存します。

より正確には、現実の状態 r のモデルを A(r) とします。A(r1)=A(r2) なのに必要な答えが違うなら、そのモデルだけを使う計算では常に正答できません。これは必要な区別が失われたことを示す反例です。現実の細部をすべて保存するのではなく、答えを変える違いを見つけて残すことが大切です。

小さな仕事をつなぐ約束を調べる

本例では会員が有効、本が存在し、貸出中ではない場合だけ承認します。memberOK、bookExists、loaned がすべて真偽値なら、承認条件は memberOK AND bookExists AND NOT loaned です。本がないと loaned を読めない実装なら、bookExists=false の経路ではその読み取りより先に終了しなければなりません。すべての論理入力が存在する仮定と、実際のデータ検索の順序を区別します。

仕事ごとに正しくても、約束が合わなければ全体は間違います。検索の「見つからない」を次の仕事が「空いているから借りられる」と解釈するかもしれません。インターフェースは単なる関数名ではなく、意味と許される状態の共通の約束です。後のデータ構造ではこの約束と内部表現を分け、ソフトウェア工学ではモジュール間の変更と検証を扱います。

途中の過程をたどる例題

会員 M は有効。本 B17 は存在し、loaned=true。要求は順番に処理し、予約や延滞の規則は対象外とする。貸出を許可できるか判断する。

  1. 会員確認モジュール：M→memberOK=true。
  2. 本の検索モジュール：B17→bookExists=true、loaned=true。
  3. 判定：true AND true AND NOT true = true AND true AND false = false。
  4. 拒否を返し、貸出記録は変更しない。

貸出は拒否。会員が有効なのは条件の1つで、それだけでは十分ではありません。

紙と本文で試してみよう

本 A は存在するが貸出中、本 Z は存在しない。モデルに「貸出不可」という状態1つだけを残したら、「貸出中」と「本が見つからない」という拒否理由を区別できるか。必要な情報を残すモデルを書こう。

ヒントを見る

同じモデル状態にまとめた現実の2つのケースで、必要な答えが違わないか調べる。

解答を見る

区別できません。現実の2状態をまとめたのに、必要な理由は異なります。NOT_FOUND、ON_LOAN、AVAILABLE の3状態なら区別を残せます。この拒否理由の判定には表紙の色は依然として不要です。

よくある誤解と反例

抽象化は細部を多く捨てるほどよい。

貸出中かを捨てると、存在するすべての本を誤って承認するかもしれません。判断基準は情報量の少なさではなく、目的に必要な区別が残ることです。分解と抽象化は関係しますが、仕事の責任を分けることと情報の区別を減らすことは異なります。

理解を確かめる

会員確認と本の検索を別の仕事にすることを何と呼ぶか。

答えと理由を見る

問題分解。

異なる責任の仕事を分けてつなぐからです。

本例の規則で、会員が有効、本が存在し、貸出中ではない場合はどうなるか。

答えと理由を見る

貸出を承認する。

必要な3条件をすべて満たします。除外した延滞や予約の規則を勝手に追加してはいけません。

表紙の色を捨てても常に安全か。

答えと理由を見る

安全とは限らない。色で検索するサービスには不適切。

答えを変える色の区別が失われます。

もう一歩先へ

会員1人につき3冊までの制限を加えよう。現在の貸出数をモデルに入れ、承認条件に count<3 を追加します。2つの同時要求が両方 count=2 を読めば、両方が承認されて4冊になる可能性があります。順番に処理するモデルの正しさが、同時処理へ自動では広がらない理由を説明しよう。オペレーティングシステムとデータベースの講義で並行処理の制御を扱います。

小節 1.3

コンピュータ科学の分野マップ

本の検索ボタンを押しても結果がなかなか出ない。1つのプログラミング言語を学ぶだけで、原因の説明と解決ができるでしょうか。

準備する概念と学習目標

準備する概念

  • 入力・処理・出力を理解し、例を「書名の入力→検索→結果一覧」と言い換える。
  • サービスには複数の責任があると理解し、画面と保存された記録を分けて考える。

学習目標

  • 問いと責任によってコンピュータ科学の主要分野を区別する。
  • 1つのサービスを複数の層に沿ってたどり、仮定を説明する。
  • 症状だけで原因を断定せず、調べる証拠を選ぶ。

言語は道具、分野は問いを整理する

C や Python は手順を表して実行する道具です。コンピュータ科学は言語科目の集まり以上のものです。アルゴリズム解析は手順の正しさと必要な仕事量を問い、データ構造はデータの整理と対応する操作を問い、コンピュータアーキテクチャはハードウェアによる命令実行を問います。コンピュータシステムではプログラマが実行を理解し、コストを減らす方法を学びます。1つの言語は多くの分野で使えます。

オペレーティングシステムはプログラム間での CPU 時間・メモリ・装置の共有を扱います。ネットワークはコンピュータ間の通信、データベースは保存データの問い合わせと整合性維持、ソフトウェア工学は要件・変更・テスト・協力を扱います。ヒューマンコンピュータインタラクションは人が目的を達成しやすい操作画面を研究します。境界は科目の重点を整理するもので、現実の問題は複数分野にまたがります。

1つのボタンを層に沿ってたどる

検索画面は書名の文字列を受け取り要求を作るかもしれません。ネットワークがサーバーに運び、サーバーが保存データを検索し、結果を返して画面が表示します。これは説明用のウェブ検索サービスのモデルです。すべてのプログラムにサーバーがあるわけではなく、オフラインの図書目録にネットワーク段階はありません。見慣れた層を自動で入れる前に、状況の構造を確認します。

遅い原因は複数考えられます。検索手順が多くの項目を比較しているかもしれず、通信待ち、ディスク読み込み、画面描画が時間を使うかもしれません。「Python は遅い」という推測だけで言語を変えるのは証拠不足です。各段階の時間を分けて観察すれば、次に調べる分野を絞れます。測定と見積もりは区別して表示します。

理論・実装・人の判断をつなぐ

理論分野では計算可能性・論理・正しさ・計算量を形式的に研究します。人工知能にはデータから規則や予測モデルを学ぶことが含まれ、性能評価には確率と統計も関わります。「好きそうな本」を薦めるモデルでも、同意・プライバシー・アクセシビリティを自動で解決するわけではありません。要件と評価基準は人が選びます。

この講義群では自分の準備に合う入口を選び、問いを簡単にするための仮定を見える形に保ちます。紙上の検索手順の比較はアルゴリズムの一部を調べることで、実サーバーの実行時間測定とは別の証拠です。小さなモデルで示した事実を、製品全体の性能や安全性の保証にしてはいけません。本単元は地図を示し、後の科目で定義・証明・実装を深めます。

途中の過程をたどる例題

説明用の順次検索サービスで、要求送信 20ms、サーバー検索 70ms、応答送信 20ms、表示 10ms とする。重なりと再試行はない。数値は仮想の観察値。

  1. 合計は 20+70+20+10=120ms。
  2. 検索を 70ms から 35ms に減らし、他の段階は変えないと仮定する。
  3. 新しい合計は 20+35+20+10=85ms。
  4. 検索段階は2倍速でも、全体の速度向上比は 120/85=24/17≈1.41。

合計は 35ms 減ります。ボトルネック候補の検索を改善しても、全体は2倍速にはなりません。数値は仮想データで、実サービスの測定値ではありません。

よくある誤解と反例

各分野は独立しているから、ウェブサービスにはウェブプログラミングだけあればよい。

検索のたどり方の誤りにはデータ構造とアルゴリズム、利用者記録の混同にはデータベースとセキュリティが関わります。一方、すべての小規模プロジェクトで全専門分野を深く実装する必要もありません。必要な機能と制約から深さを決めます。

理解を確かめる

115ms。

他の段階が同じで重ならないので、120−5=115ms。

もう一歩先へ

検索時間を 0ms にしても、このモデルでは 50ms が残ります。全体の速度向上比の上限は 120/50=2.4。複数の要求を同時処理するとき、1要求の遅延と1秒当たりの完了要求数は異なる指標です。コンピュータシステムのコスト分析とオペレーティングシステムの資源共有で、この違いを再び扱います。
