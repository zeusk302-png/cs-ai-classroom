小节 4.1

程序与进程

把同一个计算器应用打开两次，为什么两次执行中的计算值可以不同？

预备知识与学习目标

预备知识

  • 程序表示要执行的指令以及所需的数据。进程是该程序的一次执行实例，拥有随执行推进而变化的状态。
  • PC 表示下一条指令的位置；x 是本节虚构进程的私有整数变量。x←x+1 表示读取当前值，再把新值存回去。
  • 调度决定哪个已准备好的执行可以使用 CPU。切换保存的执行状态以恢复另一进程称为上下文切换；要把切换机制与选择策略区分开。

学习目标

  • 区分一个程序与多个进程各自的状态。
  • 用每个进程的 PC 和变量追踪单个 CPU 上的交替执行。
  • 说明 ready/running/blocked 以及 CPU 共享模型的适用边界。

保存的指令与正在推进的执行

能够读取程序指令并不意味着程序正在运行。操作系统准备执行所需的状态与资源，并管理执行。进程状态包括地址空间、寄存器、下一条指令位置以及输入输出相关信息。打开或复制可执行文件，并不等于执行其中的指令。

同一程序可以产生两个进程。即使代码的含义相同，输入、当前变量和执行位置仍可不同。实际系统可以共享只读代码或显式共享内存，所以并不要求每个字节都拥有独立的物理副本。以下规定可修改的私有变量互相独立，并且没有共享数据或线程。

一个 CPU 交替执行的完整规则

我们自定义程序 I：第0行 INC x，第1行 INC x，第2行 HALT。A 从 x=0 开始，B 从 x=10 开始，两者 PC=0。INC 使自己的 x 与 PC 各增加1。HALT 也使 PC 增加1，然后转为终止状态，不再执行指令。整数采用无大小限制的数学整数；实际机器指令、地址与溢出不在模型中。

一个 CPU 从 A 开始，每次一条指令，交替执行已就绪的 A/B。每条指令耗费虚构时间1，上下文切换与创建成本为0，没有外部输入或输入输出等待。两个进程的存活时间重叠，具有并发性，但模型的任一瞬间只执行一条指令。这不是实际多核并行执行，也不声称是某个操作系统的默认调度。

等待也是一种执行状态

running 是正在 CPU 上执行指令的状态；ready 是可以执行但尚未被选中的状态；blocked 是等待必要事件、目前尚未准备好执行的状态。简单输入输出模型中，running 发出请求后变为 blocked；完成事件使其回到 ready，调度器选中后才再次 running。完成并不意味着立即分配 CPU。

进程 ID 是在一个系统中区分执行的标识符，与程序名称不同。终止后的 ID 复用、权限与资源回收取决于系统规则。独立地址空间的抽象并不能单独解决共享文件冲突或隔离所有故障。后续操作系统与并发课程将更严格地讨论共享哪些状态以及需要哪些保证。

逐步推导的例题

按照上述规则，A(x=0) 与 B(x=10) 交替执行 I。求每条指令后两者的状态以及总虚构时间。

  1. 时间0→1，A 执行第0行：A=(PC1,x1)，B=(PC0,x10)。时间1→2，B 执行第0行，得到 B=(PC1,x11)。
  2. 时间2→3，A 执行第1行，得到 A=(PC2,x2)。时间3→4，B 执行第1行，得到 B=(PC2,x12)。
  3. 时间4→5，A 执行 HALT，得到 A=(PC3,x2,终止)。B 仍为 ready，保持 x12/PC2。
  4. 时间5→6，B 执行 HALT，得到 B=(PC3,x12,终止)。终止后不读取 I[3]。各执行3条，共6条指令。

A 的最终值为2，B 为12，总虚构时间为6。同一指令表可以对应不同私有状态。这不是实际 CPU 秒数或执行日志。

用纸笔和正文动手试一试

保持规则不变，将 A/B 的初始 x 分别改为5、5，最终值是什么？A 第一次 INC 后，B 的 x 也变为6吗？另问：B 因未完成的输入输出而 blocked 时，调度器能把它当作 ready 选中吗？

查看提示

INC 只作用于被选中进程的私有变量。分别使用 blocked 与 ready 的定义。

查看解答

两者各执行两次 INC，所以最终值都是7。A 第一次 INC 后是 A6/B5，B 不会自动变化。这个简单状态模型中的 B 在完成事件前尚未就绪，因此不能当作 ready 执行。

常见误解与反例

执行相同程序时，变量和执行位置总是相同。

例子中 I 相同，但初始值0/10与交替推进造成状态不同。显式共享内存可以使某些状态一起改变，因此应先规定私有状态与共享状态的契约。

检查理解

ready 进程现在正在使用 CPU 吗？

查看答案与理由

没有。

此刻执行指令的状态是 running。

输入输出完成使 blocked 变成 ready，就立即 running 吗？

查看答案与理由

不一定。

从 ready 转为 running 还需要调度器选择。

例子的总时间6能反映实际电脑的处理速度吗？

查看答案与理由

不能。

指令1/切换0/无输入输出是自定义假设，并没有测量实际时钟、切换和指令成本。

进一步探索

进阶：对只修改私有变量的 INC 建立保持另一进程状态的 frame 性质。A 的一步保留 B 的 x/PC，B 的一步保留 A 的 x/PC。对步骤数归纳可证明：某进程恰好执行 k 次 INC 后，x=初始值+k。因此，在无共享状态、输入输出、异常，且所有指令最终都会执行的条件下，改变交替顺序不改变最终变量值。如果缺少公平性，策略永远不选择某进程，就不能保证该进程终止。

小节 4.2

文件、权限与路径

即使拥有文件读取权限，如果无法通过到达它的路径，还能打开它吗？

预备知识与学习目标

预备知识

  • 文件内容是字节序列，路径是寻找内容时依次使用的名称。同名 notes.txt 位于不同目录时可以指向不同对象。
  • 本节采用 Unix 式分隔符 / 与根目录 / 的虚构树。相对路径从当前目录开始，绝对路径从 / 开始。不能直接套用 Windows 驱动器、路径或 ACL 规则。
  • r/w/x 对文件分别表示读/写/执行，对目录表示读取名称列表/修改名称条目/搜索与通过。限定模型不含链接、挂载、ACL、特权、sticky bit、只读文件系统或并发修改。

学习目标

  • 从当前目录依次跟随路径组成部分寻找目标。
  • 同时检查文件权限与途经目录的搜索权限。
  • 区分内容写入、名称删除与实际文件系统的附加条件。

沿名称寻找对象

目录条目把名称连接到文件或其他目录。绝对路径 /work/notes.txt 先在根目录找到 work，再在其中找到 notes.txt。如果当前目录是 /work/reports，../notes.txt 经父目录 /work 指向同一目标。. 是当前目录，.. 是父目录；本模型中根目录的父目录仍是根目录。

每个名称组成部分必须存在，作为途经目录使用的对象必须是目录，还需要前面目录的搜索权限。实际符号链接与挂载可以改变路径解析，因此不能把从字符串删除 a/.. 的规则推广为所有真实路径验证或安全检查。以下只使用依次跟随条目的纸上目录树。

权限不仅属于目标，也属于路径

基本权限分为所有者、组成员、其他用户三类。当前用户是所有者时，选择所有者权限；否则若属于文件的组，选择组权限；其余选择其他用户权限。适用类别的权限不足时，不能再加上其他类别的权限。实际访问使用的用户凭据与额外 ACL、特权规则不在这个限定模型内。

目录 x 允许搜索或通过已知名称，r 允许列出条目名称。目录有 x 而无 r 时，只要其他条件满足，就可以用已知文件名访问，但不能读目录列表。即使文件有 r，途经目录没有 x，也不能通过这条新路径打开文件。

改变内容与改变名称是不同请求

文件 w 允许写入该文件内容。创建或删除名称会改变父目录的条目，所以基本模型检查父目录 w 与 x。不能仅因文件不可写，就断定其名称也不可删除。实际还可能有 sticky bit、文件标志、只读挂载、错误等附加限制。

删除一个名称后，其他硬链接或已经打开的文件引用可能仍然存在。因此，这不保证全部字节立即消失或被安全擦除。文件描述符是进程对已打开文件的引用，与路径字符串不同。本节活动是纸上访问判断，不是修改实际账号权限或文件的操作练习。

逐步推导的例题

用户敏是 /work/notes.txt 的所有者。文件权限为所有者 r--/组 rw-/其他 ---。/、/work、/work/reports 都给予敏 x；/work 为 r-x。当前目录为 /work/reports。判断 ../notes.txt 的读取、内容写入和名称删除。

  1. 沿 .. 到 /work，再找到 notes.txt。给定条件满足根目录和途经目录 x，以及条目存在要求。目标绝对路径为 /work/notes.txt。
  2. 敏是所有者，选文件所有者 r--。有 r，允许读取；不把组 rw- 加进来。
  3. 选中的所有者权限类别没有 w，内容写入不允许。组 w 不补充所有者权限的不足。
  4. 名称删除需要父目录 /work 的 w+x。r-x 缺少 w，因此不允许。这与文件是否有 r 分别判断。

允许读取，不允许内容写入，不允许名称删除。这是同时检查路径和用户适用权限后的虚构结果。

用纸笔和正文动手试一试

在原条件下，只把敏在 /work 的权限改为 -wx。可以通过已知名称读取 notes.txt、读取 /work 的条目列表、删除 notes.txt 名称吗？文件内容写入权限保持不变。

查看提示

区分搜索 x 与列表 r。删除名称要检查父目录。

查看解答

已知路径读取可行，因为途经 x 和文件 r 都存在。/work 缺少 r，不能列出条目。父目录有 w+x，限定模型中可以删除名称。所有者仍缺少文件 w，内容写入仍不可行。没有执行实际删除或权限修改。

常见误解与反例

知道文件名后，只检查文件 r 就能读取。

通过新路径打开时，还需要途经目录搜索 x。/work 无 x，即使 notes.txt 的 r 仍存在，这次新访问也会拒绝。区分已打开描述符的后续使用与新的路径查找。

检查理解

目录 x 是读取文件内容的权限吗？

查看答案与理由

不是。

目录 x 负责搜索与通过；文件内容读取还需要文件 r 等条件。

文件所有者 r--/组 rw- 时，所有者能合并两类权限写入吗？

查看答案与理由

这个基本模型中不能。

优先选所有者权限类别，不把组权限相加。

删除一个文件名会立即安全擦除所有内容吗？

查看答案与理由

没有这种保证。

其他名称或打开引用可能仍存在；空间复用与字节安全擦除也是不同保证。

进一步探索

进阶：把路径存在 E、所有途经目录搜索允许 X、适用的文件读取 R 分开，则限定模型的新读取允许条件是 E∧X∧R。任何一个为假就拒绝。然而，真实执行中从检查到另一次调用打开文件之间，路径可能改变，这个静态论证并不足够。检查与使用的时间差、打开引用、链接处理与额外安全策略将在系统编程中讨论。

小节 4.3

终端与系统资源

画面没有输出，就能判定命令失败吗？

预备知识与学习目标

预备知识

  • 终端是以文字处理输入输出的连接环境，shell 是解释命令的程序。它们不等于操作系统内核或所有被执行命令本身。
  • stdin/stdout/stderr 分别是标准输入/标准输出/标准错误通道。通常通过描述符0/1/2连接，但目标可以改为终端、文件、管道等。
  • 经过时间从开始计到结束，CPU 时间累计实际使用 CPU 的时长。等待期间其他资源可以工作；解读数字前先检查单位和统计范围。

学习目标

  • 区分终端、shell 与被调用程序的职责。
  • 纸上追踪标准输入输出连接和退出状态。
  • 结合假设解释 CPU/经过时间及内存指标。

输入文字后，谁做什么

shell 解释命令文本，执行指定程序或内置功能。同一终端窗口中的语法与可用命令也会因 shell 而异。本节 >、>>、| 是参考 Unix 式 Bash 基本连接含义的纸上表示，不是要求在当前 Windows PowerShell 画面中原样运行。

命令有名称和参数。相对路径受执行的当前目录影响，名称查找与环境变量也影响执行条件。只看输入文本，不能证明选中了特定可执行文件或全部条件成功。学习记录应同时保存环境、参数、输入数据与实际结果，才能比较同样的执行。

把结果送往画面之外

stdout 连接文件后，正常结果可能不显示在画面。基本输出重定向 > 先把已有文件截为长度0，再写新输出；>> 在末尾追加。此处假定普通文件、权限成功、noclobber 关闭、无并发写入者、无记录失败。连接失败可能使程序执行也失败，结果0字节并不等于正常完成。

A | B 把 A 的 stdout 接到 B 的 stdin。仅有 | 不会自动合并 stderr。退出状态0是 shell 处理的成功标志，却不能保证内容符合用户意图。基本 Bash 关闭 pipefail 时，管道状态来自最后一个命令；前面的命令即使失败，整体仍可为0。应检查状态统计策略与程序契约。

先读资源指标的名称与范围

若经过时间10秒、用户 CPU2秒、内核 CPU1秒，则 CPU 累计3秒。假定单执行线程、单 CPU、统计区间互不重叠，使用比率为3/10=30%。其余7秒是简单模型的非 CPU 区间，但仅凭该数字不能推断是磁盘等待还是就绪等待。实际多线程累计 CPU 总和可以超过经过时间，所以不能断定比率总在100%以下。

内存指标包括当前值、最大值、虚拟地址空间、resident 驻留物理页等不同含义。把两个最大 resident 值相加会混合不同时间的峰值，可能高估同时占用，也可能重复计算共享页。文件字节数不等于内存占用。应说明单位、时刻、统计对象与共享条件，不能把不支持的指标解读为使用量0。

逐步推导的例题

虚构 emit 不使用 stdin，向 stdout 发送 A 和换行、向 stderr 发送 check 和换行，然后以状态0退出。out.txt 初始内容为 OLD 和换行。纸上追踪 emit > out.txt；另求虚构观测 real10秒/user2秒/sys1秒的 CPU 比率。

  1. 基本 > 连接成功时，先把 out.txt 现有内容截为长度0。这发生在 emit 输出之前。
  2. emit 的 stdout 中 A 和换行送入 out.txt。最终文件为 A 和换行，不保留 OLD。
  3. 假定 stderr 连接没有改变，check 和换行送到原错误通道，这里是终端。状态是程序契约中的0。画面没有正常输出 A 不意味着失败。
  4. 另一个资源表的 CPU=2+1=3秒，比率3/10=0.3=30%。这是解释给定的单线程纸上观测，不是测得实际 emit 的数据。

文件 A+换行，终端错误通道 check+换行，状态0。另一个虚构 CPU 比率30%；并未收集实际 shell 或时间工具的输出。

用纸笔和正文动手试一试

从独立的初始文件 OLD+换行开始，追踪 emit >> out.txt。另有虚构 A 不发送 stdout，状态1；B 处理其空 stdin，状态0。关闭 pipefail 的 A | B 状态是什么？

查看提示

区分追加与截断。基本管道状态取最后一个命令。

查看解答

追加后为 OLD+换行+A+换行，stderr 的 check 仍送到终端。另一个管道返回 B 的状态0，但 A 的失败1仍是事实，不能把它解释为所有数据处理成功。

常见误解与反例

程序存活了经过时间10秒，所以 CPU 也用了10秒。

虚构表的 CPU 合计3秒，非 CPU 区间7秒。可能包含就绪等待、输入输出等待等，识别原因需要额外状态追踪。多线程情形还要确认 CPU 时间统计范围。

检查理解

A | B 总把 A 的 stderr 也送给 B 吗？

查看答案与理由

不是。

基本 | 连接 stdout，合并 stderr 需要另外的连接。

状态0就保证写出的数据满足用户全部要求吗？

查看答案与理由

单凭它不能保证。

0是程序报告的成功，内容、质量、保存等要求需要另外的契约与检查。

单线程表 real8秒/user2秒/sys2秒的 CPU 比率是多少？

查看答案与理由

50%。

CPU 合计4秒除以经过时间8秒得0.5。不能自动推广到多线程或其他统计范围。

进一步探索

进阶：两个进程只计算各自独立的物理页。先假定所有时刻都满足 A≤8MiB、B≤8MiB。再假定 t1 的 resident 值为(A8MiB,B2MiB)，t2 为(A2MiB,B8MiB)，其他时刻之和不超过10MiB。所有时刻的个别上限是额外假设，不能只从其他时刻的合计≤10推出。各进程的8MiB上限分别在t1和t2达到，因此个别峰值之和为8+8=16MiB，但实际同时最大和为10MiB。即使没有共享页，个别最大之和也不等于同时最大。根据所有时刻 A≤8、B≤8 的假设，合计≤16仍是上界。要纳入实际共享页、页单位、其他进程与测量间隔，必须补充统计定义。
