소단원 8.1

컴파일과 인터프리트

번역기를 한 번 거친 프로그램도 실행할 때 또 해석될 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 미니복습: 원문은 사람이 쓴 기호열이고 실행 결과는 주어진 입력에서 일어난 동작이다. 둘은 같은 물건이 아니다.
  • 준비개념: 변수 대입, 두 수의 덧셈, 순서대로 실행되는 세 문장.
  • 자가진단: x=3 뒤 y=x+4라면 y는 7이다. 이 값을 얻는 경로와 값 자체를 구분해 보자.

학습 목표

  • 컴파일을 다른 표현으로의 변환, 인터프리트를 표현을 읽고 동작시키는 실행 방식으로 구분한다.
  • 원문·중간 표현·기계 코드·실행기를 서로 다른 단계로 그린다.
  • 컴파일 여부만으로 정확성·속도·타입 검사 여부를 단정하지 않는다.

표현을 바꾸는 단계와 동작하는 단계

컴파일은 프로그램을 다른 표현으로 바꾸는 작업이다. 원문을 기계 코드로 바꿀 수도 있고 다른 실행기가 읽을 중간 표현으로 바꿀 수도 있다. 변환 결과가 생겼다는 사실만으로 입력을 처리한 것은 아니다. 실행은 그 프로그램의 규칙을 실제 입력과 상태에 적용하는 과정이다.

인터프리트는 실행기가 어떤 표현을 읽으며 그 뜻에 맞는 동작을 수행하는 방식이다. 여기서 표현은 사람이 쓴 원문일 수도, 앞 단계에서 만든 중간 코드일 수도 있다. 책을 미리 번역하고 나중에 그 번역문을 읽을 수 있듯 두 단계는 한 파이프라인 안에 함께 있을 수 있다. 이 비유에서 번역 정확성을 보장하는 것은 언어의 구체적 규칙과 구현이다.

실제 구현의 경로를 이름 붙이기

CPython의 공식 용어집은 Python 원문이 바이트코드로 컴파일되고 가상기계가 그것을 실행하는 경로를 설명한다. 따라서 Python에는 컴파일 단계가 전혀 없다는 말은 맞지 않는다. 이 설명을 모든 Python 구현의 유일한 동작으로 확대하지 않는다. 내부 바이트코드는 구현과 버전을 가로지르는 공통 배포 형식이라고 가정할 수 없다.

Java의 javac는 .java 원문을 JVM용 .class 파일로 바꾼다. JVM 명세는 실행 방법을 단 하나로 고정하지 않는다. 바이트코드 해석이나 CPU 명령으로의 컴파일을 포함하는 구현이 가능하다. 실행 중 일부 코드를 컴파일하는 JIT도 이런 구분을 이해하는 한 경로이다. 모든 JVM이 같은 최적화나 속도를 보인다는 뜻은 아니다.

실패 지점도 구분하기

원문의 문법이 맞지 않아 변환이 실패하는 경우와, 변환된 프로그램이 특정 입력에서 실패하는 경우를 나눈다. 파이프라인의 어느 단계까지 도착했는지 기록하면 오류를 찾기 쉬워진다. 컴파일 성공은 모든 입력에서 원하는 답을 낸다는 증명이 아니다. 실제 오류 종류와 시점은 언어와 구현의 계약에 달려 있다.

이 단원의 작은 종이 기계는 명령별 정수 상태를 바꾼다. 가상기계라는 이름을 붙였다고 CPU나 JVM 전체를 재현하는 것은 아니다. 실제 처리 속도에는 입력, 최적화, 메모리, 입출력, 실행 환경이 함께 영향을 준다. 여기서는 시간 측정을 하지 않으므로 두 실행 방식의 우열도 판정하지 않는다.

중간 과정을 따라가는 예제

자체 종이 언어의 원문 x=3; y=x+4; emit y를 SET x 3 / ADD y x 4 / EMIT y로 변환한다. SET은 값을 저장하고 ADD는 현재 x와 정수 상수를 더해 y에 저장하며 EMIT은 현재 값을 출력 목록에 추가한다. 초기 변수·출력 목록은 비어 있다.

  1. 변환 결과를 종이에 적는다. SET x 3, ADD y x 4, EMIT y의 세 명령이며 이 시점에는 출력을 만들지 않았다.
  2. 종이 실행기가 SET을 읽으면 상태는 x=3, 출력=[]가 된다.
  3. ADD에서 현재 x=3을 읽고 3+4=7을 계산해 y=7을 저장한다.
  4. EMIT에서 y=7을 읽어 출력=[7]로 만든다. 두 단계가 함께 있어도 결과는 한 값 7이다.

컴파일 단계는 세 중간 명령을 만들고, 그 명령을 읽는 인터프리트 단계가 출력 [7]을 만든다. 실제 CPU·JVM 명령이나 관측한 실행 결과가 아니다.

종이와 본문으로 직접 해보기

같은 원문 형태에서 x=6, 더할 상수=2로 바꿔 변환 결과와 실행 후 상태를 적자. 그다음 중간 표현의 ADD를 의도적으로 SUB로 잘못 바꾸면 출력이 어떻게 달라지는지 비교하자. SUB는 첫 변수에서 상수를 뺀 값을 저장한다.

힌트 보기

먼저 변환된 글자만 적고 출력 칸을 비워 둔다. 실행 칸에서 6+2와 6−2를 따로 계산한다.

풀이 보기

올바른 변환은 SET x 6 / ADD y x 2 / EMIT y이고 출력 [8]이다. 잘못 바꾼 것은 SET x 6 / SUB y x 2 / EMIT y이며 출력 [4]이다. 실행기가 중간 명령을 정확히 읽어도 변환이 뜻을 보존하지 않으면 원문의 원하는 결과를 얻지 못한다.

오해와 반례

컴파일된 프로그램은 실행 때 해석될 수 없고, 컴파일 성공이면 답도 맞다.

원문→바이트코드 변환 후 바이트코드를 읽는 실행 경로가 반례이다. 또한 의도적으로 ADD를 SUB로 바꾼 종이 변환은 실행 가능하지만 원문의 뜻을 보존하지 않는다. 오류 없이 돌아가는 것과 요구한 결과를 내는 것은 다른 검사이다.

한 단계 더

심화: 이 종이 언어는 SET, ADD, EMIT만 허용하고 참조하는 변수는 앞에서 반드시 저장되었다고 가정한다. 원문 한 문장을 같은 의미의 한 중간 명령으로 바꾸면, 각 문장 뒤 변수값과 출력 목록이 같은지 문장 수에 대한 귀납으로 설명해 보자. 이 제한된 변환의 논증은 전체 Python·Java 컴파일러의 정확성 증명이 아니다.

소단원 8.2

정적·동적 타입

이름에 다른 종류의 값을 연결하면 객체의 종류 자체가 바뀐 것일까?

준비 개념과 학습 목표

준비 개념

  • 준비개념: 정수 4와 문자열 "4"는 겉모양이 비슷해도 서로 다른 값이다.
  • 미니복습: 타입은 허용되는 값·연산을 구별하는 규칙이다. 이름, 값, 객체를 구분한다.
  • 자가진단: 수의 덧셈 4+2와 문자 이어붙이기 "4"+"2"의 의도가 다른지 설명해 보자.

학습 목표

  • 정적 검사와 실행 중 검사를 검사 시점으로 구분한다.
  • Python 이름 재연결을 같은 객체의 타입 변화와 구분한다.
  • 타입 주석과 별도 검사 도구, 프로그램 요구사항 검사를 구분한다.

언제 어떤 정보를 검사하는가

정적 타입 검사는 프로그램을 실행하기 전에 표현의 타입 관계를 검사한다. Java 명세는 변수와 식에 컴파일 시점에 알려진 타입이 있다고 설명한다. 예를 들어 int 변수에 문자열 값을 그대로 넣는 것은 허용되는 정수 값의 범위를 벗어난다. 타입을 소스에 항상 직접 적어야만 정적 타입인 것은 아니다. 컴파일러가 식에서 타입을 알아내는 타입 추론도 가능하다.

동적 타입에서는 실행 중 현재 객체에 해당 연산을 적용할 수 있는지 판단하는 일이 중요하다. Python에서 이름 x를 정수에 연결했다가 문자열에 다시 연결할 수 있다. 원래 정수 객체가 문자열로 변신하는 것은 아니다. 객체의 타입과 현재 그 객체를 가리키는 이름의 연결을 따로 그려야 한다.

간단한 재연결의 효과

Python의 x=4 다음 x="four"는 x가 가리키는 대상을 바꾼다. 그 뒤 x+2를 평가하려면 문자열과 정수의 덧셈 규칙이 필요하지만 이 내장 조합은 지원되지 않아 TypeError가 예상된다. 반면 x+"!"는 두 문자열을 이어붙이는 연산이므로 "four!"가 예상된다. 이 예측은 문서와 종이 추적이며 실제 실행 결과로 표기하지 않는다.

타입을 검사한다고 데이터의 모든 조건이 검사되는 것은 아니다. 같은 정수형 80과 −5가 모두 허용되어도 나이 필드가 음수를 금지한다면 별도의 값 조건이 필요하다. 어떤 타입 체계는 더 자세한 조건을 표현할 수 있지만, 이 입문 예제의 단순 정수 타입에는 나이 제한을 넣지 않았다.

주석·도구·실행기의 역할

Python의 함수·변수 타입 주석은 예상 타입을 전달할 수 있으나 기본 실행기가 그 주석을 자동으로 강제하는 규칙은 아니다. 외부 정적 검사 도구를 사용하면 실행 전에 일부 불일치를 찾아낼 수 있다. 주석을 적는 것, 검사 도구를 실제 돌리는 것, 실행 중 입력 값을 검사하는 것은 세 가지 행동이다.

정적 타입 프로그램에도 0으로 나누기, 잘못된 배열 인덱스, 요구사항을 뒤집은 조건 같은 문제가 남을 수 있다. 동적 타입 프로그램에도 명확한 입력 계약과 검사·테스트를 작성할 수 있다. 여기서는 강한 타입과 약한 타입을 하나의 보편적 점수처럼 비교하지 않고 구체적으로 어떤 연산을 어느 단계에서 거절하는지 묻는다.

중간 과정을 따라가는 예제

코드는 실행하지 않고 각 문장을 독립적으로 판정한다. Java int count=4; 뒤 count="four";와, Python x=4 뒤 x="four" 뒤 x+2 및 x+"!"를 비교한다. 두 마지막 Python 식은 각각 같은 x="four" 상태에서 평가한다고 가정한다.

  1. Java count의 선언 타입은 int이고 초기 정수 4는 그 타입에 맞는다.
  2. Java의 문자열 "four"는 int 값으로 그대로 대입할 수 없으므로 두 번째 대입은 컴파일 시점 타입 오류로 판정한다. 실제 javac를 실행한 것은 아니다.
  3. Python의 두 대입은 이름 x를 정수 객체에서 문자열 객체로 재연결한다. 현재 x가 가리키는 것은 문자열이다.
  4. 같은 현재 상태에서 x+2는 지원되지 않는 타입 조합으로 TypeError가 예상되고 x+"!"는 문자열 "four!"가 예상된다. 앞 식 오류 뒤 프로그램이 자동으로 계속된다고 가정한 것이 아니다.

정적 예제는 대입의 타입 관계를 먼저 거절하며, 동적 예제는 현재 객체의 연산을 평가할 때 조합을 판정한다. 실제 컴파일·실행 관측은 없다.

종이로 Python def twice(x: int) -> int: return x + x를 읽자. x=5와 x="ha"를 각각 넣었을 때 본문 연산의 예상 결과와 주석이 기대한 타입을 적자. 함수 본문 외 별도 검사기·실행 검사는 없다고 가정한다.

Python 문자열과 정수의 +가 실패하는 예측이 첫 주장에 대한 반례이다. int 주석의 twice에 문자열을 주어 문자열 연산이 가능한 사례는 주석만으로 자동 검사된다는 주장에 대한 반례이다. 연산이 성공해도 함수가 정수 두 배라는 원래 계약을 충족한 것은 아니다.

소단원 8.3

언어별 사용 영역

어떤 언어가 가장 좋은지 묻기 전에 프로그램이 어디서 움직여야 하는지 정할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 준비개념: 실행 환경은 브라우저, 서버, 개인 컴퓨터처럼 프로그램이 움직일 조건이다.
  • 미니복습: 라이브러리는 이미 구현된 기능이고 API는 그 기능을 요청하는 약속이다. 언어 문법과 동일한 것은 아니다.
  • 자가진단: 버튼 클릭에 화면이 바뀌는 작업과 저장된 숫자들의 평균을 구하는 작업은 어떤 입력·출력을 갖는가?

학습 목표

  • 언어·구현·실행 환경·라이브러리를 구분해 설명한다.
  • 작업의 필수 조건으로 후보를 거르고 취향이나 익숙함을 다음 단계에서 비교한다.
  • 사용 사례를 독점 영역·성능 순위·유행 순위로 확대하지 않는다.

언어 이름보다 실행 조건부터

언어는 표현과 의미의 규칙이고, 실행 환경은 그 프로그램이 실제로 기능을 요청할 장소이다. 브라우저에서 버튼 클릭과 화면 갱신을 구현하는 일반적인 경로는 JavaScript와 DOM·이벤트 API를 함께 사용하는 것이다. MDN은 이런 API를 언어 핵심 기능과 구분한다. API 접근이 필요한 작업은 언어 문법만 외워서 완성되지 않는다.

Python 공식 사용 사례에는 과학계산과 웹 개발이 함께 있다. 같은 언어가 여러 영역에 쓰이고 같은 영역에도 여러 언어가 쓰인다. 서버가 만들어 보낸 결과를 브라우저가 보여 주는 것과 서버 원문을 브라우저에서 직접 실행하는 것은 다른 경로이다. 웹이라는 단어만으로 실행 장소를 확정하지 않는다.

배포 대상과 기능의 계약

Java용 class 파일을 다루는 경우 JVM 호환성과 의존성이 필요하다. CPU 이름이 같다고 실행 환경이 갖추어졌다고 판단하지 않는다. Python 분석 스크립트라면 필요한 Python 구현과 패키지의 조건을 조사한다. 실행기가 없다는 문제를 소스 파일 이름을 바꾸는 것으로 해결할 수는 없다.

새 작업의 필수 조건을 먼저 적는다. 예를 들어 계정 없이 브라우저에서 접근해야 하는가, 네트워크 없이 동작해야 하는가, 특정 장치 API가 필요한가를 묻는다. 실제 지원 여부는 해당 구현·도구의 공식 문서와 작은 실행 확인으로 검증해야 한다. 여기서는 후보의 실제 설치나 브라우저 실험까지 하지 않는다.

작은 후보표에서 합리적으로 고르기

필수 조건을 모두 만족하는 후보만 남긴 뒤 작성 경험, 유지보수 가능성, 사용 가능한 라이브러리를 비교한다. 어떤 조건을 필수로 놓았는지 공개하면 다른 사람이 같은 판단을 검토할 수 있다. 다수결로 조건을 지우거나 점수 합계로 필수 조건의 실패를 숨기지 않는다.

여기서 만드는 후보표는 연습을 위한 가정이다. 실제 언어의 속도·시장성·안전성을 조사한 측정표가 아니다. Python을 숫자 분석에 골랐다고 다른 언어로 분석할 수 없다는 뜻은 아니다. 브라우저 후보를 골랐다고 네트워크 장애나 개인정보 요구까지 검증된 것도 아니다. 선택 이유와 아직 확인할 항목을 함께 기록한다.

중간 과정을 따라가는 예제

자체 연습 작업 W는 설치 없이 제공된 브라우저에서 실행(B), 버튼으로 표 갱신(U)이 모두 필수이다. 후보 A는 주어진 환경에서 JavaScript+DOM으로 B=참,U=참, 친숙함2점; 후보 B는 로컬 Python 스크립트로 B=거짓,U=거짓, 친숙함5점; 후보 C는 제공된 브라우저 시각 도구로 B=참,U=참, 친숙함4점이라고 가정한다. 0~5점에서 큰 값이 더 친숙하다. A와 C는 수정·공개 권한도 같다고 가정한다.

  1. 필수 통과식은 B∧U이다. A:참∧참=참, B:거짓∧거짓=거짓, C:참∧참=참이다.
  2. B는 친숙함이 가장 높아도 필수 실행 조건을 만족하지 않아 이번 후보에서 제외한다.
  3. 통과 집합 {A,C} 안에서 친숙함만 비교하도록 정한 규칙을 적용하면 4>2여서 C를 고른다.
  4. 결론에 가정을 붙인다. C의 실제 실행·권한·표 갱신 지원을 확인한 결과가 아니라 주어진 표의 판단이다. 직접 코드 편집이 추가 필수라면 표에 새 열을 만들고 다시 걸러야 한다.

연습 표와 명시된 판단 규칙에서는 C를 선택한다. 언어 인기·성능 순위가 아니라 필수 조건 통과 후 친숙함 비교의 결과이다.

종이와 본문으로 직접 해보기

작업 W에 오프라인 실행(O)을 새 필수로 추가한다. 주어진 표에서 A는 O=참, B는 O=참, C는 O=거짓이라 가정하자. 기존 B·U 열은 바뀌지 않는다. 새 통과 집합과 선택을 구하고, 아무 후보도 통과하지 않는 경우 무엇을 기록해야 할지 적자.

힌트 보기

새 필수식은 B∧U∧O이다. 이전에 탈락한 B를 O 한 열만 보고 부활시키지 않는다.

풀이 보기

A만 참∧참∧참으로 통과한다. B는 B·U가 여전히 거짓이고 C는 O가 거짓이므로 탈락한다. 선택은 A이다. 통과 집합이 빈 경우에는 선택 없음과 충족하지 못한 조건을 기록하고 새 후보를 조사하거나 사용자와 요구사항을 다시 논의한다. 친숙함 점수만으로 실패를 통과로 바꾸지 않는다.
