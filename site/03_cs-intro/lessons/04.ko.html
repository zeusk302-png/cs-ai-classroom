소단원 4.1

프로그램과 프로세스

같은 계산기를 두 번 열면 계산값은 왜 서로 다를 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 프로그램은 수행할 명령과 필요한 자료를 표현한 것이다. 프로세스는 그 프로그램의 한 실행 인스턴스이며 실행이 진행되는 동안의 상태를 갖는다.

  • PC는 다음 명령 위치, x는 이 단원 가상 프로세스의 개인 정수 변수다. x←x+1은 현재 값을 읽어 새 값으로 바꾸는 대입이다.

  • 스케줄링은 준비된 실행 중 어느 것이 CPU를 사용할지 정하는 일이다. 저장된 실행 상태를 바꿔 이어 실행하는 문맥 교환과 선택 정책은 구별된다.

학습 목표

  • 프로그램 하나와 여러 프로세스의 상태를 구별한다.

  • 한 CPU의 교대 실행을 각 프로세스의 PC·변수로 추적한다.

  • ready/running/blocked 및 CPU 공유 모형의 적용 한계를 설명한다.

화면 두 개의 숫자는 다르지만 저장한 프로그램은 하나라면, 어느 상태를 따로 보관해야 할까?

메뉴얼 한 권을 두 사람이 읽으면 읽고 있는 페이지와 메모는 다를 수 있다. 프로세스도 명령의 의미뿐 아니라 지금 이어 실행할 위치와 개인 자료를 가진다. 아래에서는 코드 공유 여부와 관계없이 개인 변수와 PC를 따로 적는다. 실제 프로세스의 물리 메모리가 모두 복사된다고 가정하지 않는다.

기본 단원은 입출력 없는 교대 실행이었다. 이번에는 CPU를 쓰지 못하는 기다림을 넣고 준비된 다른 실행이 그 시간을 사용할 수 있는지 비교한다. 가상 시간은 초가 아니며 CPU 하나, 생성·교환 비용 0, 아래에 지정한 실행 순서만 사용한다. 완료 사건과 다시 CPU를 받는 사건도 따로 표시한다.

먼저 확인할 개념
  • 명령 위치와 개인 레지스터

    자체 명령을 하나씩 실행하며 PC와 값의 변화가 다른 사실임을 확인한다.

  • 필요한 상태를 보존하는 추상화

    실행 가능 여부를 버린 상태 요약으로는 올바른 선택을 할 수 없다는 관점을 연결한다.

저장된 명령과 진행 중인 실행

프로그램의 명령을 읽을 수 있다는 것과 그 프로그램이 실행 중이라는 것은 다르다. 운영체제는 실행에 필요한 상태와 자원을 준비하고 실행을 관리한다. 프로세스의 상태에는 주소 공간, 레지스터와 다음 명령 위치, 입출력과 관련된 정보 등이 포함된다. 실행파일을 열거나 복사하는 동작이 곧 그 명령을 실행하는 동작은 아니다.

같은 프로그램에서 두 프로세스를 만들 수 있다. 둘의 코드 의미가 같아도 입력, 현재 변수와 진행 위치는 다를 수 있다. 실제 시스템은 읽기 전용 코드나 명시한 공유 메모리 등을 공유할 수 있으므로 모든 바이트가 반드시 별도 물리 복사라는 뜻은 아니다. 아래에서는 변경 가능한 개인 변수만 서로 독립이며 공유 자료와 스레드가 없다고 정한다.

한 CPU를 번갈아 쓰는 완전한 규칙

자체 프로그램 I는 행0 INC x, 행1 INC x, 행2 HALT다. 프로세스 A는 x=0, B는 x=10, 둘 다 PC=0으로 시작한다. INC는 자기 x를 1 늘리고 자기 PC를 1 늘린다. HALT도 PC를 1 늘린 뒤 종료 상태로 바꾸며 그 뒤 명령을 실행하지 않는다. 정수는 크기 제한 없는 수학적 정수다. 실제 기계어·주소·overflow는 모형에 없다.

CPU 하나가 준비된 A/B를 A부터 한 명령씩 교대로 실행한다. 각 명령은 가상 시간 1, 문맥 교환과 생성 비용은 0, 외부 입력과 입출력 대기는 없다고 정한다. 두 프로세스가 겹치는 생존 기간을 갖는 동시성은 있지만 이 모형의 한 순간에는 명령 하나만 실행된다. 실제 다중 코어의 병렬 실행이나 어떤 OS의 기본 스케줄링이라고 주장하지 않는다.

기다릴 수 있다는 것도 실행 상태다

running은 CPU에서 명령을 수행하는 상태, ready는 실행할 수 있으나 아직 선택되지 않은 상태다. blocked는 필요한 사건을 기다려 지금 실행할 준비가 안 된 상태다. 단순 입출력 모형에서는 running이 요청을 내고 blocked가 되며, 완료 사건이 오면 ready로 돌아가고 스케줄러가 선택해야 다시 running이 된다. 완료가 곧 CPU를 즉시 배정받는다는 뜻은 아니다.

프로세스 ID는 한 시스템의 실행을 구별하는 식별자이며 프로그램 이름과 다르다. 종료 뒤 ID 재사용과 권한·자원 회수는 시스템 규칙에 의존한다. 독립 주소 공간이라는 추상화만으로 공유 파일의 충돌이나 모든 장애 격리가 해결되지는 않는다. 뒤의 운영체제·동시성 과목에서 어떤 상태를 공유하고 어떤 보장이 필요한지 더 엄밀하게 다룬다.

중간 과정을 따라가는 예제

정의한 I를 A(x=0),B(x=10)가 교대로 수행한다. 각 명령 뒤 두 상태와 총 가상 시간을 구하라.

  1. 시간0→1에서 A의 행0: A=(PC1,x1), B=(PC0,x10)이다. 시간1→2에서 B의 행0: B=(PC1,x11)이다.

  2. 시간2→3에서 A의 행1: A=(PC2,x2)다. 시간3→4에서 B의 행1: B=(PC2,x12)다.

  3. 시간4→5에서 A의 HALT: A=(PC3,x2,종료)다. B는 아직 ready이고 x12/PC2를 유지한다.

  4. 시간5→6에서 B의 HALT: B=(PC3,x12,종료)다. 종료 뒤 I[3]을 읽지 않는다. 각 3명령, 총6명령이다.

A 최종 2, B 최종 12, 총 가상 시간 6이다. 같은 명령표여도 개인 상태는 다르다. 이는 실제 CPU 초나 실행 로그가 아니다.

조건을 바꾸어 비교하기

같은 작업을 직렬로 기다리면

위 작업에서 B를 A가 종료한 뒤에만 실행한다면 두 작업의 종료 시각은 어떻게 달라지는가?

  1. A의 CPU는 0–2, 대기는 2–6, 마지막 CPU는 6–7이다.

  2. B는 7–11을 사용하므로 전체 종료는 11이다.

  3. B가 준비된 대기 구간을 쓰는 표에서는 종료가 7이다. 총 CPU 작업은 어느 쪽도 7이다.

경과시간은 11 대 7, 같은 CPU 작업 7을 기준으로 가상 완료 시간 비는 11/7이다. 실제 OS 속도 개선을 측정한 값이 아니다.

비교할 점

기본의 두 INC 교대와 달리 기다림을 겹쳐 쓰되 작업량을 줄이지 않는 경우다.

입출력 완료가 즉시 실행은 아니다

A의 입출력 대기만 2로 줄여 완료를 시각 4로 바꾼다. B는 중간 선점 없이 2–6을 계속 사용한다. A의 대기와 준비 대기를 구별하라.

  1. A는 2–4에서 blocked이고 완료 사건 때 ready가 된다.

  2. A는 4–6에서 ready지만 B가 CPU를 쓰므로 running이 아니다.

  3. A는 6–7에서 마지막 CPU 작업을 한다. blocked 2와 ready 대기 2를 더해도 원인을 하나로 합치지 않는다.

A 종료 시각은 여전히 7이다. 입출력이 2만큼 빨라졌어도 이 정책의 준비 대기가 그만큼 늘었다.

비교할 점

완료 여부와 선택 정책을 분리하면 최종 시간만으로 대기 원인을 추정할 수 없음을 볼 수 있다.

종이와 본문으로 직접 해보기

같은 규칙에서 A와 B의 초기 x를 각각 5,5로 바꾸면 최종 값은? A의 첫 INC 후 B의 x도 6이 되는가? 별도로 B가 입출력 때문에 blocked일 때 완료 사건 전 스케줄러가 ready처럼 선택해도 되는가?

힌트 보기

INC는 선택된 프로세스의 개인 변수에만 적용한다. blocked와 ready의 정의를 분리한다.

풀이 보기

둘 다 INC를 두 번 수행하므로 최종 7이다. A의 첫 INC 직후 A 6/B 5이고 B는 자동 변경되지 않는다. 이 단순 상태 모형의 blocked B는 사건 전 준비되지 않았으므로 ready처럼 실행하지 않는다.

오해와 반례

같은 프로그램을 실행하면 변수와 실행 위치도 항상 같다.

예제는 같은 I이지만 초기 변수0/10과 교대 진행으로 서로 다른 상태를 갖는다. 공유 메모리를 명시하면 일부 상태가 함께 바뀔 수 있으므로 개인/공유의 계약을 먼저 정해야 한다.

지금 명령을 실행하는 상태는 running이다.

연습 1 · 값과 상태 예측

표에서 A의 입출력 완료만 시각 8로 늦추면 CPU 유휴 구간과 전체 종료 시각은? B는 2–6을 사용한다.

힌트 1

B 종료 후 A가 준비되었는지 확인한다.

힌트 2

A가 마지막으로 쓰는 CPU 시간은 1이다.

풀이와 답 확인

  1. 6–8은 B 종료, A blocked여서 CPU 유휴다.

  2. A는 8–9를 쓰고 종료한다. CPU 작업 합은 7, 유휴 합은 2다.

전체 종료 9, CPU 유휴 [6,8)이다.

흔한 오답에서 다시 생각하기

대기가 길어졌으니 B도 시각 8까지 running이다.

실행 중인지와 다른 작업의 대기 길이는 독립이다. B의 계약은 CPU 4 뒤 종료다.

연습 2 · 오류 찾아 고치기

기록에 A가 blocked인 시각 3에 A의 다음 CPU 명령을 실행했다고 적었다. 위 표의 실행과 A의 PC 보존 규칙에 맞게 고쳐라.

힌트 1

blocked는 현재 실행할 준비가 없다는 뜻이다.

힌트 2

시각 3의 CPU는 누구에게 주어졌는지 본다.

풀이와 답 확인

  1. 시각 3은 B의 실행 구간이다.

  2. A의 다음 명령 위치는 입출력 뒤 마지막 CPU 작업을 가리킨 채 보존한다.

  3. A를 다시 선택하는 시각 6에 그 위치에서 이어간다.

시각 3의 실행 대상은 B이며 A의 PC는 CPU 명령 실행으로 증가하지 않는다.

흔한 오답에서 다시 생각하기

시간이 흐르면 모든 PC를 자동 증가시킨다.

PC는 해당 프로세스가 어떤 명령을 실행했는지를 추적한다. 외부 시간이 지났다는 사실과 다르다.

연습 3 · 직접 만들어 보기

코드 ADD 2, HALT를 두 프로세스 P(x=1)와 Q(x=10)가 공유한다. 개인 변수만 존재하며 명령 비용 1이다. P의 ADD, Q의 ADD, Q의 HALT, P의 HALT 순서로 PC와 x를 구성하라.

힌트 1

선택된 프로세스의 PC만 1 증가시킨다.

힌트 2

HALT 뒤 PC는 2이고 그 프로세스를 더 실행하지 않는다.

풀이와 답 확인

  1. 첫 단계 뒤 P=(PC=1, x=3), Q=(PC=0, x=10)이다.

  2. 두 번째 단계 뒤 Q=(PC=1, x=12)이고 P의 상태는 그대로다.

  3. 세 번째 단계 뒤 Q=(PC=2, x=12, 종료), 네 번째 단계 뒤 P=(PC=2, x=3, 종료)다.

최종 P 3, Q 12, 시간 4다. 코드 의미를 공유해도 개인 상태를 합치지 않는다.

흔한 오답에서 다시 생각하기

두 번 ADD이므로 둘의 변수도 함께 4 증가한다.

ADD의 대상은 선택된 프로세스의 개인 x다. 공유 변수를 추가하려면 새로운 계약이 필요하다.

소단원 4.2

파일·권한·경로

파일 자체를 읽을 권한이 있는데, 그 파일까지 가는 길을 통과할 수 없으면 열 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 파일 내용은 byte의 순서이고 경로는 그 내용을 찾아갈 이름의 순서다. 같은 이름 notes.txt도 다른 디렉터리에 있으면 다른 대상을 가리킬 수 있다.

  • 이 단원은 Unix식 / 구분자와 루트 /를 쓰는 가상 트리다. 현재 디렉터리에서 시작하는 상대 경로와 /에서 시작하는 절대 경로를 구별한다. Windows 드라이브/경로·ACL 규칙을 그대로 적용하지 않는다.

  • 권한 r/w/x는 파일에서는 읽기/쓰기/실행, 디렉터리에서는 이름목록 읽기/이름항목 변경/검색·통과라는 역할로 읽는다. 링크·마운트·ACL·특권·sticky bit·읽기전용 파일시스템과 동시 변경이 없는 제한 모형이다.

학습 목표

  • 현재 디렉터리와 경로의 구성요소를 따라 대상을 찾는다.

  • 파일 권한과 경유 디렉터리의 검색 권한을 함께 검사한다.

  • 내용 쓰기와 이름 제거 및 현실 파일시스템의 추가 조건을 구별한다.

파일 내용을 못 바꾸는 사람도 그 파일의 이름을 지울 수 있을까?

파일의 내용에 대한 요청과 디렉터리의 이름 대응에 대한 요청을 나눠 보자. 읽기와 쓰기는 대상 파일의 선택된 권한 묶음을 보지만 이름 제거는 부모 디렉터리를 바꾼다. 아래 표는 같은 사용자에게 허용되는 작업이 서로 다를 수 있다는 반례다.

Unix식 가상 트리 /lab와 그 파일 a.txt만 사용한다. 링크·마운트·ACL·특권·sticky bit·읽기전용·동시 변경·오류는 없고 루트 검색은 허용한다. 사용자는 파일 소유자이며 파일 권한 묶음은 소유자 r--, 그룹 rw-, 기타 ---다. 실제 계정이나 파일의 권한을 바꾸는 활동이 아니다.

  • 입력·출력 계약

    작업 이름과 요구한 성공 결과를 먼저 정하고 다른 작업의 허용을 대신 쓰지 않는다.

  • 필요한 판단을 남기는 추상화

    파일 내용과 이름 대응을 하나로 줄이면 삭제와 쓰기의 차이를 잃는다는 반례를 연결한다.

이름을 따라가며 대상을 찾기

디렉터리는 이름을 파일이나 다른 디렉터리에 연결하는 항목을 가진다. 절대 경로 /work/notes.txt는 루트의 work를 찾고 그 안의 notes.txt를 찾는다. 현재 디렉터리가 /work/reports이면 ../notes.txt는 부모 /work를 거쳐 같은 대상을 가리킨다. .은 현재, ..는 부모를 뜻한다. 루트의 부모는 이 모형에서 루트다.

이름 구성요소가 있어야 하고 경유 대상은 디렉터리여야 한다. 앞에 오는 디렉터리를 검색할 권한도 필요하다. 실제 심볼릭링크와 마운트는 경로 해석을 바꿀 수 있으므로 문자열에서 a/..만 지우는 규칙을 모든 실제 경로 확인이나 보안 검사로 일반화하지 않는다. 아래에서는 각 경유 항목을 실제로 따라가는 종이 트리만 사용한다.

권한은 대상뿐 아니라 경로에도 있다

예제의 기본 권한은 소유자/그룹/기타 세 묶음이다. 현재 사용자가 소유자이면 소유자 묶음, 그렇지 않고 파일 그룹의 구성원이면 그룹 묶음, 나머지는 기타 묶음을 선택한다. 자신이 해당하는 묶음이 부족하다고 다른 묶음의 권한을 더하지 않는다. 각 접근의 실제 사용자 자격과 추가 ACL·특권 규칙은 이 제한 모형 밖이다.

디렉터리 x는 이미 아는 이름을 검색·통과하는 권한이며 r은 항목 이름들을 열거하는 권한이다. 따라서 x는 있고 r은 없는 디렉터리에서 알고 있는 파일명으로 접근하는 것은 다른 조건까지 충족하면 가능하지만 목록을 읽는 것은 허용되지 않는다. 파일 r이 있어도 경유 디렉터리 x가 없으면 새 경로로 그 파일을 열 수 없다.

내용과 이름의 변경은 다른 요청이다

파일 w는 그 파일 내용에 쓰는 권한이다. 이름 생성이나 제거는 부모 디렉터리의 항목을 바꾸는 일이므로 기본 모형에서는 부모 w와 x를 검사한다. 파일에 쓰기권한이 없다는 사실만으로 해당 이름의 제거도 불가능하다고 결론내릴 수 없다. 현실에서는 sticky bit, 파일 플래그, 읽기전용 마운트와 오류 등 추가 제약이 있다.

이름 하나를 제거해도 다른 hard link나 이미 열린 파일 참조가 남을 수 있다. 따라서 이름 제거는 모든 byte가 즉시 소멸하거나 안전하게 지워졌다는 보장이 아니다. 파일 descriptor는 열린 파일에 대한 프로세스의 참조이며 경로 문자열과도 다르다. 이 단원의 활동은 종이 접근 판단이며 실제 계정 권한이나 파일을 바꾸는 실습은 아니다.

중간 과정을 따라가는 예제

사용자 민은 /work/notes.txt의 소유자다. 파일 권한은 소유자r--/그룹rw-/기타---다. /, /work, /work/reports 모두 민에게 x가 있고 /work는 r-x다. 현재 디렉터리는 /work/reports다. ../notes.txt의 읽기·쓰기·이름 제거를 판정하라.

  1. ..를 따라 /work로 가고 notes.txt를 찾는다. 루트/경유 디렉터리 x와 항목 존재가 주어진 조건에서 충족된다. 대상 절대 경로는 /work/notes.txt다.

  2. 민은 소유자이므로 파일 소유자r-- 묶음을 선택한다. 파일 읽기는 r이 있어 허용된다. 그룹rw-를 합산하지 않는다.

  3. 파일 쓰기는 선택된 소유자 묶음에 w가 없어 허용되지 않는다. 그룹의 w가 소유자의 부족을 보충하지 않는다.

  4. 이름 제거는 부모 /work의 w+x가 필요하다. /work r-x에는 w가 없어 허용되지 않는다. 파일의 r 여부와 별도 판정이다.

읽기 허용, 내용 쓰기 불허, 이름 제거 불허다. 경로와 사용자의 선택된 권한을 함께 확인한 가상 결과다.

소유자 우선과 이름 제거의 반례

부모 /lab가 -wx이고 파일은 위 권한이다. 사용자가 그룹 구성원이기도 하면 그룹 w를 써서 내용을 바꿀 수 있는가? 이름 제거는?

  1. 파일의 소유자이므로 소유자 r--를 선택하고 그룹 rw-를 더하지 않는다.

  2. 부모 x와 파일 r이 있어 알려진 이름으로 읽을 수 있다.

  3. 파일 내용 쓰기는 불허지만 부모 w+x가 있어 a.txt라는 이름의 제거는 허용한다.

내용 쓰기 불허와 이름 제거 허용이 함께 성립한다. 이 제한 모형의 권한 판단이며 실제 삭제를 하지 않는다.

  1. 첫 경로는 tmp의 부모 /lab에서 a.txt를 찾는다.

  2. 둘째는 tmp의 부모 /lab, 그 안의 archive, archive의 부모 /lab, a.txt 순이다.

이 가상 트리에서는 같은 대상을 가리킨다. 실제 링크가 있는 경로를 문자열만 줄여 보안 검증한 결과로 일반화하지 않는다.

소단원 4.3

터미널과 시스템 자원

화면에 출력이 없다는 이유만으로 명령이 실패했다고 판단해도 될까?

준비 개념과 학습 목표

준비 개념

  • 터미널은 글자로 입력과 출력을 다루는 연결 환경이고 shell은 명령을 해석하는 프로그램이다. 운영체제의 커널이나 모든 명령 자체와 동일하지 않다.

  • stdin/stdout/stderr는 표준 입력/표준 출력/표준 오류의 통로 이름이다. 보통 descriptor0/1/2로 연결하지만 대상은 터미널·파일·파이프 등으로 바꿀 수 있다.

  • 경과시간은 시작부터 끝까지의 시간, CPU시간은 실제 CPU를 사용한 누적 시간이다. 대기시간 동안 다른 자원은 일할 수 있으며 숫자의 단위와 집계 범위를 먼저 확인한다.

학습 목표

  • 터미널·shell·호출되는 프로그램의 역할을 구분한다.

  • 표준입출력 연결과 종료상태를 종이로 추적한다.

  • CPU시간/경과시간/메모리 지표와 가정으로 자원 사용을 해석한다.

두 출력 통로를 같은 파일로 보낸다는 표기는, 연결 순서를 바꿔도 같을까?

화면에 보이는 글자만 보면 파일로 보낸 출력과 실행되지 않은 명령을 구별하기 어렵다. 이번에는 각 통로가 어느 대상에 연결되었는지를 표로 적고, 연결을 복사한 시점이 중요함을 살펴본다. 아래 Bash식 표기는 읽고 추적하기 위한 것이며 Windows shell에 그대로 입력하는 실습이 아니다.

가상 emit은 stdout에 문자열 OK, stderr에 문자열 WARN을 보내고 상태 0으로 종료한다. 줄바꿈은 없고 터미널 두 통로는 같은 화면 T에 보인다고 가정한다. 파일 F의 초기 내용은 OLD다. 리다이렉션은 왼쪽부터 성공하고 noclobber는 꺼져 있으며 다른 작성자·쓰기 실패는 없다. 2>&1은 그 시점 stdout의 대상을 stderr에도 연결하며 이후 stdout 변경을 자동 따라가는 변수 참조가 아니다.

먼저 확인할 개념
  • 문자와 인코딩

    여기서 파일 결과는 ASCII 문자열의 정확한 순서이며 화면 존재 여부와 내용 계약을 구별한다.

  • 입출력 완료와 요청 상태

    통로 연결·프로그램 상태·사용자가 요구한 최종 결과를 서로 다른 단계로 기록한다.

문자를 입력하면 누가 무엇을 하는가

shell은 명령문을 해석하고 지정한 프로그램이나 내장 기능을 수행한다. 같은 terminal 창 안에서도 어떤 shell인지에 따라 문법과 제공 명령이 다르다. 이 단원의 >, >>, | 표기는 Unix식 Bash의 기본 연결 의미를 참고한 종이 표기이며 현재 Windows PowerShell 화면에서 똑같이 실행하라는 요구가 아니다.

명령에는 이름과 인수가 있다. 상대 경로 입력은 실행의 현재 디렉터리에 영향을 받고, 이름 검색이나 환경 변수도 실행 조건에 영향을 줄 수 있다. 입력문을 보았다는 사실만으로 특정 실행파일이 선택되거나 모든 조건이 성공했다는 것을 증명하지 않는다. 학습 기록에는 실행 환경, 인수, 입력 자료와 실제 결과를 함께 남겨야 같은 실행을 비교할 수 있다.

화면 대신 다른 통로로 보내기

stdout을 파일로 연결하면 정상 결과가 화면에 보이지 않을 수 있다. 기본 출력 리다이렉션 >는 기존 파일을 먼저 길이0으로 줄이고 새 출력을 쓰며, >>는 끝에 추가한다. 여기서는 일반 파일·권한성공·noclobber 꺼짐·동시작성자없음·기록실패없음을 가정한다. 연결에 실패하면 프로그램 실행도 실패할 수 있고 결과 0byte와 정상 완료는 동일한 사실이 아니다.

A | B는 A의stdout을 B의stdin에 연결한다. stderr는 |만으로 자동 합쳐지지 않는다. 명령의 종료상태 0은 shell이 취급하는 성공 표시지만 사람이 원한 자료의 정확성까지 보장하지 않는다. 기본 Bash에서 pipefail을 끄면 파이프라인 상태는 마지막 명령의 상태이므로 앞 명령이 실패해도 전체가 0일 수 있다. 조건을 바꾸려면 상태 집계 정책과 프로그램 계약을 확인한다.

자원 지표의 이름과 범위를 먼저 읽기

프로세스의 경과시간이 10초이고 사용자 CPU 2초/커널 CPU 1초라면 CPU 누적은3초다. 한 실행 스레드/한 CPU와 서로 겹치지 않는 집계 구간을 가정하면 사용 비율은3/10=30%다. 나머지 7초는 이 단순 모형의 비CPU 구간이지만 그 숫자만으로 디스크대기인지 준비대기인지 추론할 수 없다. 실제 다중스레드 집계 CPU 합은 경과시간을 넘을 수 있으므로 같은 공식으로 항상100% 이하라고 단정하지 않는다.

메모리 지표는 현재값, 최대값, 가상주소공간, resident 물리페이지 등 의미가 다르다. 최대resident값 두 개를 더하면 서로 다른 시점의 최대가 섞여 실제 동시 점유를 과대평가할 수 있고 공유페이지를 중복 계산할 수도 있다. 파일byte수와 메모리 점유도 같지 않다. 자료의 단위·시각·집계 대상과 공유 조건을 명시하고 실제 지원되지 않는 지표를0사용으로 해석하지 않는다.

표기첫 연결 뒤 stdout/stderr둘째 연결 뒤 stdout/stderr파일 F와 화면

F/T

첫 표기의 첫 단계는 F를 길이 0으로 줄인 뒤 stdout을 F로 연결한다. 프로그램은 항상 OK 뒤 WARN 순서로 내보낸다고 정했으므로 결합 파일은 OKWARN이다. 실제 두 작성자나 버퍼링 순서를 이 표에서 추정하지 않는다.

중간 과정을 따라가는 예제

가상 emit은 stdin을 사용하지 않고 stdout에 A와 줄바꿈, stderr에 check와 줄바꿈을 보내고 상태 0으로 종료한다. 파일 out.txt의 초기 내용은 OLD와 줄바꿈이다. emit > out.txt를 종이로 추적하라. 별도의 가상 관측 real=10초,user=2초,sys=1초의 CPU비율도 구하라.

  1. 기본 > 연결이 성공하면서 기존 out.txt 내용을 길이0으로 줄인다. 이 단계는 emit 출력 전에 일어난다.

  2. emit의 stdout A와 줄바꿈은 out.txt로 간다. 따라서 최종 파일은 A와 줄바꿈이고 OLD는 남지 않는다.

  3. stderr 연결은 바꾸지 않았다고 가정하므로 check와 줄바꿈은 원래 오류 통로, 여기서는 터미널로 간다. 상태는 프로그램 계약의 0이다. 화면에 정상 출력 A가 없어도 실패라는 뜻은 아니다.

  4. 별도 자원표는 CPU 2+1=3초, 비율3/10=0.3=30%다. 실제 emit의 측정값이라는 뜻은 아니며 주어진 한 스레드 종이관측을 해석한 것이다.

파일 A+줄바꿈, 터미널 오류통로 check+줄바꿈, 상태 0이다. 별도 가상 CPU비율30%이며 실제 shell·시간 도구의 출력은 수집하지 않았다.

복사한 연결은 나중 변화와 별개다

두 표기에서 실행 뒤 F와 화면 및 종료 상태를 비교하라.

  1. 첫 표기는 stdout을 F로 바꾼 뒤 그 연결을 stderr에 복제하므로 둘 다 F다.

  2. 둘째는 stdout이 T일 때 stderr를 T로 복제한 뒤 stdout만 F로 바꾼다.
