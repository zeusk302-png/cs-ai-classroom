소단원 11.1

편집기와 빌드

화면의 숫자를 바꿨는데 실행 결과가 예전과 같다면 무엇을 먼저 확인할까?

준비 개념과 학습 목표

준비 개념

  • 파일 이름과 폴더 위치로 저장한 내용을 구별한다.
  • 명령을 적은 코드와 그 명령을 실행하는 프로그램은 다르다.

학습 목표

  • 편집·저장·빌드·실행의 역할을 구별한다.
  • 실행하는 파일과 수정한 파일이 같은지 확인하는 순서를 적는다.

편집기는 글을 바꾸고 저장은 파일을 바꾼다

코드 편집기는 프로그램의 명령을 텍스트로 적는 도구다. 화면에 보이는 변경이 아직 파일에 저장되지 않았으면 다른 도구는 이전 파일을 읽을 수 있다. 우선 파일 이름·확장자·폴더 위치와 저장 상태를 확인하자. 다른 폴더의 같은 이름 파일을 수정하는 실수도 흔하다.

실습용 폴더 안에 한 파일을 두면 시작하기 쉽다. 아래 선택 실습은 Python이 이미 설치되어 있고 터미널에서 python 명령을 사용할 수 있을 때 main.py로 저장한 뒤 해당 폴더에서 python main.py를 실행하는 예다. 설치가 없거나 명령이 인식되지 않으면 종이 활동만으로도 이 단원의 목표를 학습할 수 있다. 명령 실패와 코드 오류를 먼저 구별한다.

빌드는 실행할 형태를 준비한다

C의 일반적인 빌드 흐름에서는 전처리·컴파일·어셈블·링크 단계가 소스 파일을 실행 파일로 바꾸는 데 참여한다. 링크는 여러 목적 파일과 필요한 정의를 연결하는 단계다. 하나의 버튼이 이 여러 일을 호출할 수 있어도 각 단계의 실패 원인은 다를 수 있다.

모든 언어가 같은 빌드 화면을 사용하는 것은 아니다. Python 예제는 해석기가 파일을 읽어 실행하는 경로로 소개하며, Python 내부에 컴파일 과정이 전혀 없다고 주장하지 않는다. 핵심은 실행 시 어떤 입력 파일과 도구를 쓰는지, 새로운 소스가 실행 대상에 반영되었는지를 확인하는 일이다.

실행 결과를 입력과 연결한다

빌드 성공은 실제 실행을 했다는 뜻도, 원하는 답을 얻었다는 뜻도 아니다. 소스에 2+3을 적고 출력 5를 기대하는 것과 실제 실행 화면에서 5를 관찰한 것은 구별해서 기록한다. 계산 조건이 바뀌면 기대값도 다시 계산한다.

수정 후 예전 결과가 나오면 저장 여부, 현재 폴더, 실행 파일 경로, 재빌드 성공 여부를 순서대로 확인한다. 오류가 났는데 이전 실행 파일만 다시 실행하면 수정이 적용된 것처럼 착각할 수 있다. 도구를 바꾸기 전에 어떤 단계의 입력과 출력이 오래된 것인지 찾는 편이 원인을 좁힌다.

중간 과정을 따라가는 예제

main.py에 print(2 + 3)을 적고 저장한다. Python이 준비된 같은 폴더에서 python main.py로 실행한다. 이어 코드의 3을 4로 바꾸고 저장한 뒤 같은 파일을 다시 실행한다. 두 결과를 예측하자.

  1. print는 괄호 안 계산값을 화면에 표시한다. 첫 값은 2+3=5다.
  2. 3을 4로 바꾸면 파일 내용은 print(2 + 4)다. 반드시 변경한 main.py를 저장한다.
  3. 같은 저장 파일을 다시 실행하면 2+4=6이다. 이 두 코드 조각은 집필 환경의 Python에서도 실행하여 5와 6을 확인했다.

첫 출력 5, 변경 후 출력 6이다. 집필 환경에서는 코드 조각 실행을 확인했지만 학습자의 파일 저장·터미널 실행 환경은 확인하지 않았다.

종이와 본문으로 직접 해보기

코드 print(7 + 2)를 종이에 적고 2를 5로 바꿔 보자. 수정 전후 기대 출력은? C 소스를 바꿨지만 재빌드가 실패했고 기존 실행 파일이 그대로 남아 있다고 하자. 그것을 실행한 결과는 새 소스 검증인가?

힌트 보기

계산값을 먼저 적는다. 실행 파일이 어느 소스 버전에서 만들어졌는지 구별한다.

풀이 보기

기대 출력은 9와 12다. 재빌드 실패 뒤의 기존 실행 파일은 이전 소스에서 만들어진 것이므로 새 소스의 실행 결과라고 보고할 수 없다. 빌드 로그에서 실패를 해결하고 새 실행 대상 생성과 실행을 확인해야 한다.

오해와 반례

편집기의 실행 버튼을 누르면 화면에 바꾼 모든 내용이 언제나 바로 실행된다.

도구의 저장·실행 설정과 실제 경로에 달린다. 저장하지 않은 변경이나 다른 파일 경로, 실패한 빌드 뒤의 이전 실행 파일 때문에 예전 코드가 실행될 수 있다. 화면 변경·저장 파일·실행 대상을 연결해 확인한다.

소단원 11.2

버전관리의 개념

어제 잘 되던 코드와 오늘 고친 코드를 이름만 다른 파일들 없이 비교할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 파일의 내용은 시간에 따라 바뀐다.
  • 변경 이유와 변경 결과를 기록할 수 있다.

학습 목표

  • 버전 기록의 목적과 변경 묶음의 의미를 설명한다.
  • 파일 저장·stage·commit·원격 공유를 구별한다.

변경 이력을 이름 대신 기록한다

버전관리는 파일이나 파일 묶음의 변화를 시간에 따라 기록하여 이전 상태를 비교하고 되찾도록 돕는다. 최종.py·진짜최종.py를 계속 복사하면 어떤 것이 어떤 변경인지 헷갈릴 수 있다. 기록에 변경 이유가 있으면 결과만 다른 두 버전의 관계를 설명하기 쉽다.

Git에서는 commit을 프로젝트 상태의 스냅샷 기록으로 이해할 수 있다. 번호 C1·C2는 아래 종이 예제의 별칭이며 실제 Git 식별자는 아니다. commit 메시지는 바꾼 이유와 행동을 적는다. 기록 자체가 코드의 정확성을 검사하지는 않으므로 실행·검토 결과는 별도로 연결한다.

작업 내용과 다음 기록의 내용을 나눈다

작업 트리는 현재 수정하는 파일들이 있는 공간, staging area는 다음 commit에 넣을 특정 내용을 준비하는 공간이다. 파일을 저장했다고 자동 commit되는 것은 아니며 stage한 내용이 다음 기록에 들어간다. 하나의 commit에는 관련된 변경을 묶는 편이 이유를 이해하기 쉽다.

파일을 stage한 뒤 다시 수정하면 작업 트리의 최신 내용과 stage 내용은 다를 수 있다. 같은 파일이 stage된 변경과 추가 미stage 변경을 동시에 가질 수 있는 이유다. 초보자는 commit 전에 어떤 내용이 기록될지 확인하는 습관으로 이 혼동을 줄일 수 있다.

기록과 협업을 구별한다

Git의 많은 작업은 로컬에서 가능하다. 로컬 commit과 다른 저장소에 변경을 보내는 원격 공유는 별도이며 commit했다는 사실만으로 웹에 공개되었다고 말하지 않는다. Git과 GitHub도 같은 도구가 아니다. 후자는 저장소 호스팅 등 기능을 제공하는 서비스다.

이력이 있어도 기록하지 않은 변경·외부 자료·필요한 설정이 모두 보호되는 것은 아니다. 다른 사람과 동시에 바꾸면 충돌을 조정해야 할 수도 있다. 버전관리는 변경을 추적하는 바탕이며 백업·검토·빌드 성공·배포 확인과 각각 역할이 다르다.

중간 과정을 따라가는 예제

종이 Git 모형에서 C1의 main.py 내용은 print(2 + 3)이다. 작업 파일을 print(2 + 4)로 저장하고 그 내용을 stage했다. 이후 작업 파일만 print(2 + 5)로 고친 뒤 추가 stage 없이 보통의 commit을 만든다. 새 C2에 어떤 내용이 들어갈까?

  1. C1은 2+3의 기록이다. 처음 저장한 작업 내용 2+4를 stage했으므로 다음 기록 준비 내용은 2+4다.
  2. 두 번째 수정 후 작업 트리는 2+5지만 준비한 stage 내용은 여전히 2+4다. 두 공간의 내용이 갈라진다.
  3. stage를 기반으로 commit하면 C2는 print(2 + 4)를 담는다. 작업 트리의 2+5는 C2와 다른 미기록 변경으로 남는다.

C2의 코드 기대 출력은 6이며 현재 작업 파일 기대 출력은 7이다. 이 모형은 기본 stage 기반 commit을 가정하며 Git 명령을 실제 실행한 기록은 아니다.

종이와 본문으로 직접 해보기

위 C2를 만든 뒤 작업 파일 2+5를 다시 stage하고 C3를 만들었다고 하자. C1·C2·C3의 기대 출력은? C3가 로컬에만 있고 원격 전송은 하지 않았다면 친구의 저장소에도 자동으로 C3가 있는가?

힌트 보기

각 스냅샷의 코드 내용을 따로 적는다. 로컬 기록과 공유는 다른 단계다.

풀이 보기

C1은 5, C2는 6, C3는 7이다. 원격 공유나 다른 전달을 하지 않았다면 친구에게 C3가 자동으로 생겼다고 볼 수 없다. 친구가 어떤 저장소의 어떤 상태를 받았는지도 확인해야 한다.

오해와 반례

파일 저장·commit·웹 배포는 모두 같은 저장 동작이다.

파일 저장은 작업 내용을 디스크에 반영하고 commit은 지정한 내용을 이력으로 기록하며 원격 공유·웹 배포는 별도 작업이다. 위 C3는 로컬에 존재해도 친구와 공개 사이트에는 아직 없을 수 있다.

자기점검

stage 후 추가로 고친 내용은 자동으로 그 stage에 들어가는가?

답과 이유 보기

일반적인 기본 흐름에서는 아니다.

stage한 시점의 내용과 이후 작업 트리 변경을 구별한다.

C2와 현재 작업 파일의 기대 출력 차이는?

답과 이유 보기

C2는 6, 작업 파일은 7이다.

기록된 2+4와 미기록 2+5가 다르다.

commit 성공은 코드 정답 검증인가?

답과 이유 보기

아니다.

내용 기록과 실행 정확성 검증은 역할이 다르다.

한 단계 더

문서 파일과 코드 파일을 함께 바꿀 때 변경 이유가 같은 부분과 별개인 부분을 표시하자. 문서가 설명하는 출력 6인데 코드가 7을 내도록 바뀌었다면 두 변경을 어떤 검토 가능한 기록으로 묶을지 이유를 써 보자. 명령 설치 없이 변경 묶음 설계를 연습한다.

오류 메시지와 디버깅

오류가 한 줄을 가리킨다면 그 줄만 바꾸면 될까, 실행은 되는데 답이 틀리면 어디서 찾을까?

준비 개념과 학습 목표

준비 개념

  • 코드는 순서대로 값과 상태를 바꾼다.
  • 문제의 기대 결과를 먼저 계산할 수 있다.

학습 목표

  • 구문 오류·실행 예외·논리 오류를 구별한다.
  • 재현 입력과 중간값을 사용해 원인을 좁힌다.

메시지에서 종류와 맥락을 읽는다

구문 오류는 코드를 문법에 따라 읽는 과정에서 발견한 문제다. 실행 예외는 문법상 읽을 수 있는 코드가 실행 중 금지된 연산 등을 만나 생길 수 있다. Python traceback의 마지막 줄에서는 예외 종류와 설명을 읽고 앞부분에서는 파일·줄·호출 맥락을 확인한다.

표시된 위치는 문제가 발견된 위치이지 항상 고쳐야 할 원인 위치와 같지는 않다. 괄호나 콜론을 앞에서 빠뜨리면 다음 토큰에서 읽기에 실패할 수 있다. 메시지를 지우려고 무작정 해당 줄을 삭제하지 말고 입력·명령·전체 메시지·관련 코드의 주변을 함께 기록한다.

재현을 작게 만들고 중간값을 추적한다

디버깅은 관찰된 문제의 원인을 찾아 수정하는 과정이다. 문제가 반복되는 가장 작은 입력을 만들고 기대값과 실제값을 나란히 쓴다. 한 번에 여러 부분을 바꾸면 어떤 수정이 효과를 냈는지 알기 어렵다. 가설을 하나 정하고 확인한 뒤 다음 가설로 넘어간다.

중단점은 실행을 특정 지점에서 멈춰 변수와 호출 흐름을 보는 도구다. step over는 현재 줄을 진행하되 함수 내부로 들어가지 않고, step into는 호출 내부를 따라간다. 실제 동작은 디버거에 따라 다를 수 있다. 설치 없는 활동에서는 줄별 변수 표가 같은 질문을 돕지만 실제 디버거 조작을 수행한 것과 같다고 보고하지 않는다.

예외가 없다고 논리가 맞는 것은 아니다

세 점수의 평균을 합계/2로 계산해도 숫자가 나와 실행이 끝날 수 있다. 그러나 분모가 점수 개수 3이어야 한다면 이것은 논리 오류다. 정상 종료와 정답은 서로 다른 기준이다. 손으로 계산한 기준 입력과 빈 입력·경계 입력도 확인할 이유가 있다.

수정 뒤에는 원래 재현 입력을 다시 확인하고 의미 있는 다른 입력에서도 기대값을 비교한다. 오류를 처리하는 except를 추가한다고 잘못된 평균식이 저절로 맞아지지 않는다. 원인 수정과 오류 발생 시 사용자에게 어떻게 안내할지도 구별해 설계한다.

중간 과정을 따라가는 예제

Python 코드 scores = [4, 6, 8] 다음 줄 print(sum(scores) / 2)가 평균을 표시하려 한다. 기대값과 출력, 수정할 부분을 추적하자.

  1. 점수는 3개이고 합계 4+6+8=18이다. 평균 기대값은 18/3=6이다.
  2. 기존 식은 18/2=9를 계산한다. 집필 환경에서 실행해 출력 9.0을 확인했다. 문법과 실행은 통과하지만 목적과 다르다.
  3. 분모를 len(scores)로 바꾸면 개수 3을 사용한다. 수정 코드를 집필 환경에서 실행해 6.0을 확인했다. 이 수정만으로 빈 리스트의 평균 문제까지 해결한 것은 아니다.

기존 출력 9.0은 논리 오류이며 수정 출력은 6.0이다. 합계와 개수의 중간값을 따로 확인하면 원인이 분모임을 찾을 수 있다.

종이와 본문으로 직접 해보기

total=6, count=0에서 print(total / count)는 어떤 종류의 문제인가? print(2 + )는? 별도로 [2,4]의 평균을 구할 때 합계와 개수·기대값을 적고, 빈 리스트 평균에는 어떤 처리가 필요한지 설명하자.

힌트 보기

문법을 읽을 수 있는지와 실행 중 연산이 가능한지를 나눈다. 빈 리스트는 개수가 0이다.

풀이 보기

첫 코드는 실행 중 ZeroDivisionError, 둘째는 구문 SyntaxError다. 집필 환경에서 두 예외 종류를 실제 확인했다. [2,4]는 합계 6·개수 2·평균 3이다. 빈 입력은 0으로 나눌 수 없어 평균을 정의하지 않거나 입력을 요청하는 등 문제 의미에 맞는 별도 처리가 필요하며 임의의 평균 0으로 단정하지 않는다.

오해와 반례

프로그램이 오류 메시지 없이 끝나면 답은 맞다.

기존 평균 코드처럼 9.0을 정상 출력하면서 요구한 평균 6과 다를 수 있다. 기대 결과·중간값·경계 입력을 확인해 논리 정확성을 검토한다. 메시지 처리만으로 계산 의미를 검증할 수 없다.
