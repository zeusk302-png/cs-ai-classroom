select·poll·epoll 비교

많은 연결 중 지금 처리할 수 있는 연결만 어떻게 찾을까?

준비 개념과 학습 목표

준비 개념

  • 파일 디스크립터

  • read/write와 대기

  • TCP byte stream

학습 목표

  • readiness와 요청 완료를 구별한다.

준비된 fd 하나가 두 개의 준비 건수로 세어질 수 있을까?

새 준비 모형은 fd 7 하나가 읽기와 쓰기 모두 준비되었다고 가정한다. select의 readfds와 writefds에 각각 비트 하나가 남으면 성공 반환 수는 두 집합 전체에 남은 비트 수 2다. 같은 fd를 poll 배열의 한 항목에 두고 revents에 읽기와 쓰기 표시가 함께 있으면 poll의 성공 반환 수는 revents가 비영인 항목 수 1이다. 반환 정수만으로 두 API가 다른 연결 수를 처리했다고 비교하면 집계 단위가 틀린다.

select의 nfds는 이 예에서 최대 fd에 1을 더한 8이고 poll의 nfds는 배열 항목 수 1이다. 읽기·쓰기 관심 원본을 별도로 보존하고 select가 반환 때 고친 집합을 다음 호출의 전체 관심으로 재사용하지 않는다. 이 값들은 새 입력의 산술이며 실제 kernel 통지 횟수나 성능 측정값이 아니다.

준비를 확인한 뒤 다른 소비자가 데이터를 먼저 읽었다면 논블로킹 읽기는 EAGAIN을 반환할 수 있다. 이는 앞의 준비 결과를 완성된 응용 메시지라고 읽을 수 없다는 반례다. POLLHUP과 POLLIN이 함께 왔을 때도 아직 남은 데이터를 읽고 EOF를 확인하는 경로가 필요하다. 남은 본문을 버리고 종료 성공으로 기록하는 것은 별도 프로토콜 검사를 생략한 것이다.

준비 결과를 모은 배열을 처리하는 동안 옛 연결 A의 fd 7을 닫고 새 연결 B가 같은 번호를 얻었다고 가정한다. 배열에 남은 A의 결과는 B의 메시지가 아니다. 이 자체 설계는 (fd, 연결 세대) 식별자를 두며 A의 세대 4와 B의 세대 5를 구별해 오래된 결과를 거절한다. epoll이 이 사용자 세대 번호를 자동 관리한다는 뜻이 아니다. 실제 등록 수명은 open file description과 중복 descriptor 참조까지 고려해야 한다.

준비되었다는 것은 완성이 아니다

I/O multiplexing은 여러 fd에서 읽기나 쓰기를 진행할 수 있는지 기다리는 방법이다. 읽기 준비에는 데이터와 EOF가 포함될 수 있고 쓰기 준비도 큰 버퍼 전체의 전송 보증은 아니다. 응용 메시지의 끝은 프로토콜이 정의해야 한다.

준비 통지 뒤 다른 코드가 데이터를 소비하거나 조건이 달라질 수 있다. 실제 syscall 결과를 확인하고 논블로킹 fd로 루프 전체가 멈추는 상황을 피한다. readiness를 완료 통지와 혼동하지 않는다.

관심 목록과 결과를 비교한다

select는 read/write 등의 fd_set과 가장 큰 fd+1을 받는다. 반환 때 set이 준비된 fd만 남도록 수정되므로 관심 집합을 보존하고 매 호출 전에 다시 만든다. glibc의 fd_set은 FD_SETSIZE 제한이 있으므로 범위 밖 fd를 FD_SET에 넣지 않는다.

poll은 fd와 요청 events 및 반환 revents를 담은 배열과 항목 수 nfds를 받는다. nfds는 최대 fd+1과 다르다. Linux epoll은 관심을 ctl로 등록하고 wait로 준비된 항목을 받는다. 등록/수정/해제 비용과 준비 항목 처리도 있으므로 모든 비용이 항상 O(1)이라고 단정하지 않는다.

통지 방식과 종료를 함께 처리한다

LT는 준비 상태가 남아 있으면 다시 알려 줄 수 있다. ET에서 일부 데이터만 읽고 새 통지를 기다리면 버퍼에 데이터가 남았는데도 진행하지 못할 수 있다. 논블로킹 읽기를 EAGAIN까지 진행하거나 애플리케이션 준비 큐에 남겨 계속 처리할 규약이 필요하다.

POLLHUP은 남은 데이터를 즉시 버리라는 뜻이 아니다. 데이터를 소비한 뒤 stream의 EOF를 확인한다. 오류·중단·timeout도 별도 처리하며 fd를 닫은 뒤 남은 통지가 다른 재사용 fd의 상태로 적용되지 않도록 연결 수명을 관리한다.

첫 두 행은 같은 가상 준비 조건의 서로 다른 API 집계다. 마지막 두 행은 독립 수명·경쟁 반례다. 반환 수, descriptor 번호, 연결 세대를 서로 더하거나 같은 단위로 비교하지 않는다.

중간 과정을 따라가는 예제

가상 관심 fd가 [3,7,12]이고 현재 읽기 준비는 [7]이다. select와 poll의 입력 크기 및 두 번째 select 호출을 설명하라.

  1. select의 nfds는 최대 fd 12에 1을 더한 13이다. 세 fd를 관심 read set에 넣는다.

  2. 성공 뒤 set에는 7만 남는다. 다음에도 3과 12를 감시하려면 원래 관심 집합에서 다시 set을 구성한다.

  3. poll의 배열 항목 수는 3이다. fd 값이 12라도 nfds를 13으로 두지 않는다. epoll은 세 관심을 먼저 등록하고 ready 목록으로 7을 받을 수 있다.

select는 최대 fd+1인 13, poll은 세 배열 항목인 3을 사용한다. 실제 호출 결과가 아닌 인터페이스 추적이다.

조건을 바꾸어 비교하기

한 fd의 두 준비 비트

fd 7이 읽기와 쓰기 모두 준비된 select와 poll 한 항목의 반환 수 및 nfds를 비교하라.

  1. select는 read/write 두 비트를 합해 2를 반환하고 최대 번호 7에 1을 더한 nfds=8을 받는다.

  2. poll은 비영 revents 항목 하나로 반환 수 1이고 배열 길이 nfds=1이다.

두 API의 반환 수는 2와 1이지만 이 모형의 고유 fd 수는 둘 다 1이다.

비교할 점

같은 정수 필드라도 개수의 단위가 다르다.

닫힌 연결의 남은 캐시 항목

이벤트 배열의 첫 항목 처리에서 A(fd 7, 세대 4)를 닫았다. B(fd 7, 세대 5)가 생성되고 뒤 항목에는 A의 옛 세대가 남았다.

  1. 캐시의 세대 4와 현재 연결 세대 5를 비교한다.

  2. 서로 다르므로 뒤 항목을 B의 작업으로 보내지 않고 폐기한다.

fd 숫자의 일치만으로 오래된 통지를 적용하지 않는다.

비교할 점

닫기와 번호 재사용은 연결의 업무 정체성을 보존하지 않는다.

연습 1 · 값과 상태 예측

select에 fd 3의 읽기 비트와 fd 9의 읽기·쓰기 비트가 남았다. 같은 고유 fd를 poll 두 항목에 두었다. 반환 수와 nfds를 구하라.

힌트 1

select의 서로 다른 집합에 남은 비트를 모두 센다.

힌트 2

poll은 revents 비영인 항목 수를 센다.

풀이와 답 확인

  1. select의 비트 수는 1+2=3이고 nfds는 10이다.

  2. poll의 두 항목이 모두 비영이므로 반환 수 2, nfds=2다.

select는 반환 3/nfds 10, poll은 반환 2/nfds 2다.

흔한 오답에서 다시 생각하기

select 반환 3은 연결이 3개라는 뜻이다.

같은 fd가 두 집합에 나타날 수 있어 비트 수와 고유 번호 수가 다르다.

연습 2 · 오류 찾아 고치기

select에 관심 fd 3과 9를 주었는데 첫 반환 집합에는 3만 남았다. 이 집합을 다시 전체 관심으로 쓴 오류를 고쳐라.

힌트 1

반환 때 집합이 수정된다.

힌트 2

관심 원본과 결과 집합을 나눈다.

풀이와 답 확인

  1. 원본 관심에는 여전히 3과 9를 보존한다.

  2. 다음 호출 전에 결과용 집합을 원본에서 다시 만든다.

첫 호출에서 준비되지 않은 9도 다음에 다시 기다린다.

흔한 오답에서 다시 생각하기

첫 호출의 준비되지 않은 fd는 앞으로도 준비되지 않는다.

준비 상태는 한 호출의 관찰이며 미래 관심을 삭제하는 정책이 아니다.

연습 3 · 직접 만들어 보기

준비 캐시의 (7,4), (8,2)에 대해 현재 연결은 (7,5), (8,2)다. 적용 또는 거절 표를 만들라.

힌트 1

번호와 세대를 함께 비교한다.

힌트 2

존재하는 현재 연결과 정확히 일치해야 한다.

풀이와 답 확인

  1. (7,4)는 현재 (7,5)와 달라 거절한다.

  2. (8,2)는 식별자 검사에 통과하고 실제 syscall 반환을 다음에 검사한다.

첫 항목은 거절, 둘째는 진행 후보다. 후보 통과는 메시지 성공 인증이 아니다.

흔한 오답에서 다시 생각하기

번호가 7이므로 첫 항목도 새 연결에 적용한다.

옛 연결 통지와 새 연결 자료를 혼합하면 다른 사용자 결과가 들어갈 수 있다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

POLLIN|POLLHUP이 왔고 읽기 반환은 2바이트, 이어서 0이다. 본문 길이 3의 요청에서 이미 1바이트를 받았었다. 상태를 판정하라.

힌트 1

HUP만 보고 대기를 버리지 않는다.

힌트 2

양수 크기 stream 읽기의 0을 EOF로 구별한다.

풀이와 답 확인

  1. 남은 2바이트를 더해 본문 3바이트가 완성된다.

  2. 다음 0은 EOF다. 본문 완성 검사 뒤 종료를 처리한다.

이 지정 입력의 본문은 완성된다. 실제 업무 검증은 별도다.

흔한 오답에서 다시 생각하기

HUP이 있으면 남은 2바이트를 버려야 한다.

종료 통지와 아직 읽을 수 있는 자료가 함께 존재할 수 있다.

ET의 한 번 통지 뒤 처리 예산이 끝나면 남은 자료는 어디에 보관할까?

새 종이 모형에는 준비 연결 A의 입력 7바이트와 B의 입력 2바이트가 있다. ET 통지를 한 번 받은 뒤 각 방문의 읽기 예산은 최대 3바이트다. 다른 자료는 도착하지 않고 지정 길이의 읽기는 성공한다고 가정한다. A에서 3바이트만 읽고 새 edge를 기다리면 아직 4바이트가 남아도 새 통지가 반드시 온다는 보장은 없다. 내부 준비 큐에 A를 다시 넣어 계속 진행할 계약이 필요하다.

큐는 A, B로 시작하고 예산이 끝나면 남은 A를 뒤로 보낸다. 방문 순서는 A, B, A, A가 되고 누적 읽기 길이는 각각 A=3, B=2, A=6, A=7이다. 각 연결을 실제로 EAGAIN까지 배수했다는 사실을 아직 확인하지 않은 동안 내부 작업으로 유지한다. 마지막 A에서 남은 1바이트를 읽은 뒤 다음 논블로킹 시도가 EAGAIN이라고 가정하면 그때 내부 준비를 해제한다. EOF·오류·취소는 다른 종료 경로다.

별도의 출력 모형에서 큐 길이 Q의 상한은 8바이트다. 높은 임계값 6 이상이면 읽기를 멈추고, 멈춘 동안 Q가 낮은 임계값 2 이하가 되어야 읽기를 다시 켠다. 시작 Q=5에서 응답 2바이트를 추가하면 Q=7이고 입력 읽기를 끈다. 송신 성공 3바이트 뒤 Q=4에서는 계속 끄고, 성공 2바이트 뒤 Q=2에서 다시 켠다. 두 임계값 사이에서 이전 상태를 보존하므로 작은 변동으로 켜짐·꺼짐을 반복하는 일을 줄인다.

읽기를 멈춘다고 이미 메모리에 있던 완성 요청이나 worker 결과가 사라지지는 않는다. 새 응답 3바이트를 Q=7에 더하려면 상한 8을 넘으므로 거절·지연·예약 같은 명시 정책이 필요하다. 출력 관심은 미송신 자료가 있을 때만 유지하며 EAGAIN에서는 offset을 그대로 둔다. 성공 send는 상대 업무 완료 증명이 아니다. 이 임계값과 큐는 자체 설계이지 kernel이 자동 제공한 상한이 아니다.

연결마다 진행 지점을 저장한다

이 단원은 TCP stream의 한 줄 요청에 한 줄 응답을 보낸 뒤 닫는 가상 프로토콜을 사용한다. LF byte가 끝 표시이며 완성된 줄 이전까지는 요청이 아니다. 입력은 byte 배열이고 길이 한도도 정한다. 문자열 인코딩과 응용 검증은 별도 단계다.

연결 상태에는 입력 버퍼, 출력 버퍼, 이미 보낸 offset, 읽기 종료 여부와 deadline을 둔다. WAIT_LINE에서 완전한 줄을 발견하면 응답을 만든 뒤 WRITE_REPLY로 이동한다. CLOSED에서는 fd와 관련 버퍼를 한 번만 해제한다.

syscall 반환에 따라 재개한다

양수 recv 반환량만 입력에 덧붙인다. EAGAIN/EWOULDBLOCK은 현재 진행할 데이터가 없다는 뜻으로 기존 버퍼를 보존한다. 양의 크기를 요청한 TCP recv의 0은 읽기 EOF다. 중간 요청 상태에서 EOF가 오면 잘린 요청을 오류로 처리한다.

send가 양수를 반환하면 그만큼 offset을 더하고 아직 안 보낸 부분만 다음 호출에 넘긴다. EAGAIN에서는 offset을 바꾸지 않는다. 성공한 send도 상대 응용의 처리 완료 증거는 아니다. EINTR와 치명 오류, 반환 0의 무진행에 대한 별도 규약을 두어 busy loop를 피한다.

무제한 버퍼와 굶주림을 피한다

느린 상대가 응답을 읽지 않으면 출력이 계속 쌓일 수 있다. 입력/출력 한도와 timeout을 두고 출력이 차면 읽기를 잠시 줄이는 backpressure를 설계한다. 무조건 데이터를 버리거나 무한히 버퍼를 늘리지 않는다.

한 연결의 처리량 예산은 다른 연결에 기회를 준다. 특히 ET에서 EAGAIN 전에 예산이 끝나면 새 edge를 기다리지 말고 내부 준비 큐에서 이어갈 일을 남겨야 한다. 대기 방식·읽기 관심·쓰기 관심·애플리케이션 준비 큐를 함께 관리한다.

worker가 먼저 끝낸 결과를 먼저 보내면 요청 순서도 유지될까?

새 혼합 모형은 한 I/O 루프와 worker 두 개를 쓴다. 같은 연결의 요청 R1과 R2는 순서 번호 1과 2를 갖는다. 시각 0에 둘 다 실행을 시작하고 계산 시간은 각각 4 ms와 1 ms다. 이 문제의 프로토콜은 응답을 요청 순서로 보내야 한다. R2가 1 ms에 끝났다고 바로 보내면 약속을 어긴다. 결과 2를 보관하고 R1이 4 ms에 끝난 뒤 결과 1, 결과 2 순서로 출력 큐에 넣는다.

두 worker의 결과에는 연결 세대와 요청 순서 번호를 넣는다. 연결 세대 10의 R1이 계산 중 종료되고 같은 fd 번호로 세대 11이 열렸다면 세대 10의 결과는 새 연결에 보낼 수 없다. 작업 취소를 시도했다는 사실만으로 이미 계산 중인 결과가 사라진다고 가정하지 않는다. 이 세대와 순서 정책은 애플리케이션의 추가 계약이다.

용량 표에서 worker 두 개는 실행 중 최대 2개, 대기 큐는 대기만 최대 3개로 정의한다. 실행 2개/대기 3개면 시스템이 수용한 작업은 5개다. 여섯째는 대기 상한으로 거절한다. 대기 3이라는 숫자를 실행 포함 전체 상한 3으로 읽으면 다른 정책이다. 작업별 결과와 응답 대기에도 상한이 필요하므로 완료 worker 수가 줄었다고 무조건 더 받아서는 안 된다.

별도의 처리율 산술 모형은 worker 한 작업이 항상 2 ms를 쓰고 두 worker가 병렬 실행하며 다른 비용이 없다고 가정한다. 이상적 계산 용량은 초당 1,000개 작업이다. I/O 출력 단계 용량이 초당 600개 응답이면 전체 장기 완료율은 그 단계를 넘을 수 없다. 지속 유입이 초당 800개 작업이라면 bounded 시스템은 모두를 무기한 수용할 수 없다. 이 모형의 최소 초과 유입은 초당 200개이며 거절·상류 감속 등 정책이 필요하다. 실제 CPU/runtime/lock/네트워크 성능은 측정하지 않았다.

프로세스는 소유 경계를 제공한다

프로세스별 서버는 각각의 주소공간에서 요청을 처리할 수 있다. 한 연결이 기다려도 다른 프로세스가 진행할 기회가 있지만 process 생성·관리·IPC 비용을 고려한다. private 전역변수와 명시적 공유 메모리는 다르다.

fork 뒤 descriptor 참조가 부모와 자식에 남을 수 있다. 실제 역할에 불필요한 참조를 닫고 자식을 회수하는 수명 규약이 필요하다. 프로세스라는 이름만으로 파일·socket·공유자원의 모든 오류가 격리된다고 단정하지 않는다.

스레드는 공유와 동기화가 함께 온다

스레드는 한 프로세스의 주소공간을 공유하고 각 실행 흐름의 stack과 register 상태를 갖는다. 각자 stack이 있다는 말은 다른 스레드의 접근이 메모리 보호로 차단된다는 뜻이 아니다. 연결별 buffer를 구별하고 공유 cache나 카운터에는 올바른 동기화를 적용한다. 여러 스레드가 있다는 사실만으로 항상 CPU 병렬성이 생기지는 않는다.

연결마다 무한히 스레드를 만들기보다 worker 수·대기 큐·메모리와 timeout 한도를 정한다. lock 대기, runtime 제약, 실제 CPU 수 및 작업 성격에 따라 성능이 달라진다. 한 모델을 모든 입력에서 최적이라고 부르지 않는다.

이벤트 루프와 worker를 조합한다

단일 이벤트 루프는 논블로킹 연결을 짧게 처리하며 상태를 직접 전환한다. I/O 대기를 겹칠 수 있어도 한 handler가 오래 계산하면 같은 루프의 다른 연결도 기다린다. CPU를 쓰는 작업을 여러 core에서 동시에 처리하려면 별도 worker나 여러 루프 등의 구조가 필요하다.

혼합 구조에서는 I/O 담당이 작업을 bounded queue로 worker에 넘기고 완료 통지를 받아 응답 상태를 갱신할 수 있다. 연결이 종료된 뒤 오래된 결과를 재사용된 fd에 적용하지 않도록 소유권과 요청 정체성을 관리한다. 큐 포화 때 backpressure와 거절 정책도 정한다.

다른 문제에 적용하기

하나의 새 설계를 세 독립 장부로 감사하라. ① fd 7의 read/write가 준비되었을 때 select와 poll 한 항목의 반환 수 및 nfds를 구하라. 준비 캐시에 (7,4)가 남고 현재 연결이 (7,5)라면 처리 여부도 적어라. ② ET 입력 큐 A,B는 7/2바이트를 갖고 방문 예산은 3이다. 마지막 양수 읽기 뒤 EAGAIN을 확인할 수 있으며 새 입력은 없다. 방문 순서와 길이를 구하라. 별도 출력 길이 5에 응답 2를 추가한 뒤 송신 3,2가 성공하면 높은 문턱 6/낮은 문턱 2 아래 읽기 상태를 추적하라. ③ 같은 세대의 요청 R1/R2가 0 ms에 시작해 4 ms/1 ms에 완료되고 요청 순서 출력 계약이 있다. 출력 허가 순서와 시각을 구하라. 별도 계산 용량 초당 1,000개·출력 초당 600개·유입 초당 800개의 장기 용량과 bounded 정책을 제안하라. 각 장부는 실제 OS나 서버 관찰이 아닌 지정 모형이다.

힌트 1

준비 비트·항목·고유 fd의 단위를 구별하고 ET에서 예산으로 멈춘 연결을 내부 큐 뒤에 남긴다.

힌트 2

출력 길이뿐 아니라 이전 읽기 상태를 보존한다. worker 결과는 연결 세대와 다음 요청 순서를 함께 확인하며 전체 처리율은 느린 단계로 제한한다.

풀이와 답 확인

  1. ① select는 반환 수 2/nfds 8, poll은 반환 수 1/nfds 1이다. 세대 4의 캐시와 현재 5가 다르므로 옛 결과를 거절한다.

  2. ② 방문은 A,B,A,A이고 읽기 길이는 3,2,3,1이다. 마지막 배수에서 EAGAIN 확인 후 내부 준비를 해제한다. 출력 길이는 7,4,2이며 읽기는 중지, 중지 유지, 재개 순서다.

  3. ③ R2가 시각 1 ms에 완료하면 결과를 보관한다. 시각 4 ms에 R1이 완료하면 R1의 결과 다음에 R2의 결과를 출력 허가한다. 송신 완료 시각은 별도이므로 주어진 자료만으로 정하지 않는다.

  4. 지정 용량 아래 완료율은 초당 600개를 넘지 못한다. 지속 유입 초과분 초당 200개는 상류 감속·거절 등으로 조정하고 입력·작업·결과·출력의 모든 대기를 제한한다.

준비 반환 수는 연결 수와 같은 단위가 아니다. ET의 남은 A 작업과 출력 읽기 상태를 보존하며 오래된 연결 결과를 거절한다. worker 결과는 4 ms부터 R1,R2 순서로 출력 허가하고 bounded 설계는 초당 200개의 지속 초과 유입을 무한 저장하지 않는다. 실제 syscall·서버·성능·학생 실행은 미수행이다.

해결한 뒤 점검할 것

  • select의 비트 수와 poll의 항목 수 및 서로 다른 nfds를 정확히 구하고 세대 불일치를 거절한다.

  • A,B,A,A의 내부 재개와 EAGAIN 확인을 설명한다.

  • 출력 길이 7/4/2에 따른 읽기 중지·유지·재개와 상한을 구별한다.

  • worker 도착/출력 허가/송신 완료를 나누고 초당 600개 및 초과 초당 200개를 가정과 함께 제시한다.

전체 원본 14의 세 소단원과 같은 단원 세 고유 선수 설명을 읽었다. select의 준비 비트 수는 각 사례에서 2와 3이며 nfds는 8과 10이다. poll의 준비 항목 수와 nfds는 각각 1과 2다. fd 세대 4와 5, 세대 10과 11의 불일치를 확인했다. HUP 상태에서 읽은 본문은 1바이트와 2바이트의 합인 3바이트다. ET 방문 A, B, A, A의 읽기 길이는 각각 3, 2, 3, 1바이트이며 A의 누적량은 7바이트, B의 누적량은 2바이트다. 출력 길이는 기존 5바이트에 2바이트를 추가해 7바이트가 된 뒤 송신에 따라 4바이트와 2바이트로 줄어든다. 별도 상한 사례에서는 7바이트에 3바이트를 더한 10바이트가 상한 8바이트를 넘는다. 송신 offset은 2바이트이며 남은 길이는 3바이트다. 두 문턱 사이에서는 이전 읽기 상태를 유지한다. R2의 완료 시각은 1 ms, R1의 완료 시각은 4 ms이며 요청 순서 출력 허가는 4 ms부터다. 실행 2개와 대기 3개의 총량은 5개이며 여섯째는 거절한다. 새 네 작업 중 두 개는 수용하고 두 개는 거절한다. 작업마다 2 ms를 쓰는 worker 두 개의 이상적 용량은 초당 1,000개다. 출력 용량은 초당 600개이며 초당 800개의 지속 유입 중 최소 200개를 조정해야 한다. 단일 루프 사례에서 B의 준비 시각은 1 ms이고 처리 시작은 5 ms보다 빠를 수 없어 최소 4 ms를 기다린다. 모든 예제·과제·힌트·오답·전이는 지정 종이 모형이며 새 산술 프로그램을 실행하지 않았다.
