소단원 14.1

select·poll·epoll 비교

많은 연결 중 지금 처리할 수 있는 연결만 어떻게 찾을까?

준비 개념과 학습 목표

준비 개념

  • 파일 디스크립터

  • read/write와 대기

  • TCP byte stream

학습 목표

  • readiness와 요청 완료를 구별한다.

  • 세 API의 관심 목록과 결과 표현을 비교한다.

  • 경계·EOF·LT/ET 조건을 설명한다.

준비되었다는 것은 완성이 아니다

I/O multiplexing은 여러 fd에서 읽기나 쓰기를 진행할 수 있는지 기다리는 방법이다. 읽기 준비에는 데이터와 EOF가 포함될 수 있고 쓰기 준비도 큰 버퍼 전체의 전송 보증은 아니다. 응용 메시지의 끝은 프로토콜이 정의해야 한다.

준비 통지 뒤 다른 코드가 데이터를 소비하거나 조건이 달라질 수 있다. 실제 syscall 결과를 확인하고 논블로킹 fd로 루프 전체가 멈추는 상황을 피한다. readiness를 완료 통지와 혼동하지 않는다.

관심 목록과 결과를 비교한다

select는 read/write 등의 fd_set과 가장 큰 fd+1을 받는다. 반환 때 set이 준비된 fd만 남도록 수정되므로 관심 집합을 보존하고 매 호출 전에 다시 만든다. glibc의 fd_set은 FD_SETSIZE 제한이 있으므로 범위 밖 fd를 FD_SET에 넣지 않는다.

poll은 fd와 요청 events 및 반환 revents를 담은 배열과 항목 수 nfds를 받는다. nfds는 최대 fd+1과 다르다. Linux epoll은 관심을 ctl로 등록하고 wait로 준비된 항목을 받는다. 등록/수정/해제 비용과 준비 항목 처리도 있으므로 모든 비용이 항상 O(1)이라고 단정하지 않는다.

통지 방식과 종료를 함께 처리한다

LT는 준비 상태가 남아 있으면 다시 알려 줄 수 있다. ET에서 일부 데이터만 읽고 새 통지를 기다리면 버퍼에 데이터가 남았는데도 진행하지 못할 수 있다. 논블로킹 읽기를 EAGAIN까지 진행하거나 애플리케이션 준비 큐에 남겨 계속 처리할 규약이 필요하다.

POLLHUP은 남은 데이터를 즉시 버리라는 뜻이 아니다. 데이터를 소비한 뒤 stream의 EOF를 확인한다. 오류·중단·timeout도 별도 처리하며 fd를 닫은 뒤 남은 통지가 다른 재사용 fd의 상태로 적용되지 않도록 연결 수명을 관리한다.

중간 과정을 따라가는 예제

가상 관심 fd가 [3,7,12]이고 현재 읽기 준비는 [7]이다. select와 poll의 입력 크기 및 두 번째 select 호출을 설명하라.

  1. select의 nfds는 최대 fd 12에 1을 더한 13이다. 세 fd를 관심 read set에 넣는다.

  2. 성공 뒤 set에는 7만 남는다. 다음에도 3과 12를 감시하려면 원래 관심 집합에서 다시 set을 구성한다.

  3. poll의 배열 항목 수는 3이다. fd 값이 12라도 nfds를 13으로 두지 않는다. epoll은 세 관심을 먼저 등록하고 ready 목록으로 7을 받을 수 있다.

select는 최대 fd+1인 13, poll은 세 배열 항목인 3을 사용한다. 실제 호출 결과가 아닌 인터페이스 추적이다.

소단원 14.2

논블로킹 상태기계

한 요청이 여러 번에 나누어 도착하면 함수가 끝난 뒤 무엇을 기억해야 할까?

준비 개념과 학습 목표

준비 개념

  • 상태와 전이

  • buffer와 offset

  • 부분 read/write

학습 목표

  • 연결별 입력과 출력 상태를 보존한다.

  • EAGAIN·EOF·오류의 의미를 구별한다.

  • 한도와 backpressure를 설계한다.

연결마다 진행 지점을 저장한다

이 단원은 TCP stream의 한 줄 요청에 한 줄 응답을 보낸 뒤 닫는 가상 프로토콜을 사용한다. LF byte가 끝 표시이며 완성된 줄 이전까지는 요청이 아니다. 입력은 byte 배열이고 길이 한도도 정한다. 문자열 인코딩과 응용 검증은 별도 단계다.

연결 상태에는 입력 버퍼, 출력 버퍼, 이미 보낸 offset, 읽기 종료 여부와 deadline을 둔다. WAIT_LINE에서 완전한 줄을 발견하면 응답을 만든 뒤 WRITE_REPLY로 이동한다. CLOSED에서는 fd와 관련 버퍼를 한 번만 해제한다.

syscall 반환에 따라 재개한다

양수 recv 반환량만 입력에 덧붙인다. EAGAIN/EWOULDBLOCK은 현재 진행할 데이터가 없다는 뜻으로 기존 버퍼를 보존한다. 양의 크기를 요청한 TCP recv의 0은 읽기 EOF다. 중간 요청 상태에서 EOF가 오면 잘린 요청을 오류로 처리한다.

send가 양수를 반환하면 그만큼 offset을 더하고 아직 안 보낸 부분만 다음 호출에 넘긴다. EAGAIN에서는 offset을 바꾸지 않는다. 성공한 send도 상대 응용의 처리 완료 증거는 아니다. EINTR와 치명 오류, 반환 0의 무진행에 대한 별도 규약을 두어 busy loop를 피한다.

무제한 버퍼와 굶주림을 피한다

느린 상대가 응답을 읽지 않으면 출력이 계속 쌓일 수 있다. 입력/출력 한도와 timeout을 두고 출력이 차면 읽기를 잠시 줄이는 backpressure를 설계한다. 무조건 데이터를 버리거나 무한히 버퍼를 늘리지 않는다.

한 연결의 처리량 예산은 다른 연결에 기회를 준다. 특히 ET에서 EAGAIN 전에 예산이 끝나면 새 edge를 기다리지 말고 내부 준비 큐에서 이어갈 일을 남겨야 한다. 대기 방식·읽기 관심·쓰기 관심·애플리케이션 준비 큐를 함께 관리한다.

중간 과정을 따라가는 예제

가상 요청 byte가 처음 b"HE", 다음 b"LLO "으로 도착한다. 응답 b"OK "을 send가 1 byte, EAGAIN, 2 byte로 처리할 때 상태를 추적하라.

  1. 첫 recv 뒤 입력 b"HE"에는 LF가 없으므로 WAIT_LINE이고 버퍼를 보존한다.

  2. 두 번째 뒤 b"HELLO "으로 한 줄이 완성된다. 요청을 검증하고 b"OK "을 만들면 WRITE_REPLY, offset=0이다.

  3. 첫 send의 1 byte로 offset=1이므로 남은 것은 b"K "이다. EAGAIN 뒤에도 1이고, 다음 2 byte를 보내면 offset=3이다. 응답이 다 보내졌으므로 이 한 요청 프로토콜에서는 연결을 닫는다.

분할 수신과 부분 전송 사이에 버퍼·상태·offset을 유지한다. 실제 socket 실행 기록은 아니다.

힌트 보기

오해와 반례

EAGAIN은 연결이 끊겼다는 뜻이므로 즉시 모든 상태를 지운다.

지금 진행할 데이터나 buffer 공간이 없다는 뜻이다. EOF와 치명 오류를 구별하고 부분 상태를 보존한다.

프로세스·스레드·이벤트 모델 비교

동시에 연결을 받는 것과 여러 CPU에서 동시에 계산하는 것은 같은가?

준비 개념과 학습 목표

준비 개념

  • 프로세스 주소공간

  • 스레드와 공유 상태

  • I/O 대기

학습 목표

  • 연결 동시성과 CPU 병렬성을 구별한다.

  • 모델별 상태 소유와 비용을 설명한다.

  • 혼합 구조의 한도와 공정성을 설계한다.

프로세스는 소유 경계를 제공한다

프로세스별 서버는 각각의 주소공간에서 요청을 처리할 수 있다. 한 연결이 기다려도 다른 프로세스가 진행할 기회가 있지만 process 생성·관리·IPC 비용을 고려한다. private 전역변수와 명시적 공유 메모리는 다르다.

fork 뒤 descriptor 참조가 부모와 자식에 남을 수 있다. 실제 역할에 불필요한 참조를 닫고 자식을 회수하는 수명 규약이 필요하다. 프로세스라는 이름만으로 파일·socket·공유자원의 모든 오류가 격리된다고 단정하지 않는다.

스레드는 공유와 동기화가 함께 온다

스레드는 한 프로세스의 주소공간을 공유하고 각 실행 흐름의 stack과 register 상태를 갖는다. 각자 stack이 있다는 말은 다른 스레드의 접근이 메모리 보호로 차단된다는 뜻이 아니다. 연결별 buffer를 구별하고 공유 cache나 카운터에는 올바른 동기화를 적용한다. 여러 스레드가 있다는 사실만으로 항상 CPU 병렬성이 생기지는 않는다.

연결마다 무한히 스레드를 만들기보다 worker 수·대기 큐·메모리와 timeout 한도를 정한다. lock 대기, runtime 제약, 실제 CPU 수 및 작업 성격에 따라 성능이 달라진다. 한 모델을 모든 입력에서 최적이라고 부르지 않는다.

이벤트 루프와 worker를 조합한다

단일 이벤트 루프는 논블로킹 연결을 짧게 처리하며 상태를 직접 전환한다. I/O 대기를 겹칠 수 있어도 한 handler가 오래 계산하면 같은 루프의 다른 연결도 기다린다. CPU를 쓰는 작업을 여러 core에서 동시에 처리하려면 별도 worker나 여러 루프 등의 구조가 필요하다.

혼합 구조에서는 I/O 담당이 작업을 bounded queue로 worker에 넘기고 완료 통지를 받아 응답 상태를 갱신할 수 있다. 연결이 종료된 뒤 오래된 결과를 재사용된 fd에 적용하지 않도록 소유권과 요청 정체성을 관리한다. 큐 포화 때 backpressure와 거절 정책도 정한다.

중간 과정을 따라가는 예제

가상 단일 CPU에서 A의 계산 handler는 20 ms, B는 2 ms이며 두 작업 모두 t=0에 준비되어 A부터 실행한다. 비선점 이벤트 handler와 1 ms 단위 번갈아 처리하는 가상 공정 scheduler를 비교하라.

  1. 비선점 이벤트에서는 A가 0–20 ms, B가 20–22 ms를 쓰므로 B는 22 ms에 완료된다.

  2. 가상 번갈아 처리에서는 A가 0–1, B가 1–2, A가 2–3, B가 3–4 ms를 쓴다. B는 계산 2 ms를 채워 4 ms에 완료된다.

  3. A는 이후 남은 18 ms를 써 22 ms에 완료된다. 총 CPU 작업량은 둘 다 22 ms다. switching 비용을 0으로 둔 가상 모델이고 실제 OS scheduler나 thread benchmark 결과가 아니다.

공정한 짧은 실행 조각은 B의 응답을 앞당길 수 있지만 이 단일 CPU 모델의 전체 계산량을 줄이지 않는다.

종이와 본문으로 직접 해보기

독립 두 CPU와 전용 worker가 A/B를 t=0부터 처리하며 다른 비용이 0이면 각 완료 시각과 전체 완료 시각은?

힌트 보기

각 작업을 서로 다른 CPU에 놓는다.

풀이 보기

A는 20 ms, B는 2 ms에 완료하고 전체 완료 시각은 20 ms다. 이는 실제 두 CPU 성능이나 linear speedup을 보장하는 측정이 아니다.

오해와 반례

연결 100개를 이벤트로 관리하면 CPU 계산도 자동으로 100개 병렬 실행된다.

연결 동시성과 계산 병렬성은 다르다. 단일 handler의 CPU 점유와 worker/core 수 및 작업 분할을 확인한다.

요청 도착률이 초당 50개이고 worker 하나가 초당 20개를 처리하는 가상 용량이라면 세 worker의 이상 총량은 초당 60개다. 그런데 단일 I/O 루프 한도가 초당 40개라면 전체 한도는 40개를 넘지 못한다. 병목·변동·안전 여유와 finite queue를 고려한 실제 측정 계획을 작성하라.
