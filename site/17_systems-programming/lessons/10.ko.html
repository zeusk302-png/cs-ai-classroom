pthread 생성·합류

작업자를 두 명 만들면 누가 먼저 끝나며, 결과는 언제 읽을 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 함수와 인자

  • 포인터가 가리키는 객체

  • 프로세스

학습 목표

  • 생성과 완료 대기를 구분한다.

  • 성공한 스레드만 합류하고 오류 반환값을 처리한다.

  • 결과 객체의 수명을 합류 시점과 연결한다.

두 작업이 모두 끝나는 시각과 첫 결과를 받는 시각은 같을까?

새 종이 일정에서 생성은 시각 0에 모두 성공하며 A는 시각 9 ms, B는 시각 4 ms에 종료한다. 두 작업은 독립된 안정된 결과 슬롯에 각각 19와 25를 기록한다. 합류와 결과 처리의 추가 시간은 0으로 두고, 부모는 합류 성공 뒤 해당 슬롯만 읽는다. 이는 지정한 일정의 계산이며 실제 스레드 성능 측정이 아니다.

부모가 A부터 합류하면 첫 결과 19는 9 ms에 회수되고 이미 종료한 B의 결과 25도 9 ms에 회수된다. B부터 합류하면 첫 결과 25를 4 ms에 회수하고 A의 결과 19를 9 ms에 회수한다. 전체 완료 시각은 둘 다 9 ms이지만 첫 결과의 지연은 다르다. 먼저 생성한 작업의 종료가 먼저라고 가정하지 않는다.

부분 생성 실패는 별도 장부로 관리한다. A와 C만 성공했고 B 생성이 오류 번호 E를 반환했다면 성공 목록은 A,C뿐이다. B의 출력 식별자를 합류 대상으로 사용하거나, 비어 있는 B 결과를 0으로 채워 전체 작업이 성공했다고 보고하지 않는다. 생성 성공과 작업 성공, 합류 성공은 서로 다른 확인이다.

한 joinable 대상의 합류 담당자는 하나로 정하고 성공 합류 뒤 목록에서 제거한다. 두 담당자가 동시에 합류하거나 이미 회수한 식별자를 다시 사용하지 않는다. detached는 종료 시 스레드 자원을 회수하는 정책이지, detach 호출 순간의 작업 종료나 공유 인자 객체의 사용 종료 확인이 아니다.

먼저 확인할 개념
  • 생성 성공과 특정 대상 합류

    성공 목록과 회수 목록을 분리하여 실패 식별자와 중복 합류를 피한다.

  • 결과 슬롯의 수명

    해당 작업의 합류 후 읽고 모든 사용자 종료 전 공유 인자를 해제하지 않는다.

시작 함수를 실행하는 새 흐름

pthread_create는 같은 프로세스 안에 새 실행 흐름을 만든다. 새 스레드는 start_routine에 arg를 인자로 전달해 실행한다. arg는 포인터 값이며, 인자가 가리키는 객체를 자동 복사하는 인터페이스가 아니다. 호출자와 작업자가 사용할 객체를 먼저 준비해야 한다.

생성 성공 뒤 호출자와 새 스레드 중 누가 다음 명령을 먼저 실행하는지는 일반적으로 정해져 있지 않다. A를 먼저 만들었다고 A가 먼저 완료되는 것은 아니다. 기본 속성으로 만든 스레드는 joinable이며, 종료 사실을 합류로 회수할 수 있다.

합류는 특정 작업자의 종료를 기다린다

pthread_join(A, ...)는 A가 종료될 때까지 기다린다. A가 이미 종료했다면 바로 종료 상태를 회수할 수 있다. B가 먼저 끝나도 A에 합류 중인 호출자가 곧바로 B의 결과를 회수하는 것은 아니다. 호출자가 지정한 대상이 중요하다.

성공한 합류 뒤에는 대상 스레드가 종료했으므로 그 작업에 쓰인 인자 객체를 정리할 수 있다. 다만 다른 작업자도 그 객체를 사용하면 모두의 완료가 필요하다. 같은 스레드에 여러 곳에서 동시에 합류하거나 이미 합류한 대상에 다시 합류하는 동작은 정의되지 않는다.

반환값과 정리 경로

pthread_create와 pthread_join은 성공하면 0, 실패하면 오류 번호를 직접 반환한다. 대부분의 pthread 함수는 errno를 설정하는 방식이 아니므로 반환값을 검사한다. 생성 실패 시 출력된 스레드 식별자를 유효한 대상으로 가정해서 합류하면 안 된다.

joinable 스레드는 종료 후에도 합류 전까지 일부 자원이 남는다. detached 스레드는 종료 시 해당 자원을 자동 회수하지만 합류할 수 없다. detach를 호출한 순간 작업까지 완료되었다는 뜻은 아니다. 또한 main에서 반환하거나 exit를 호출하면 다른 작업자가 남아 있어도 프로세스가 끝난다.

인자 해제의 완료 증거가 추가로 필요하다.

각 행은 서로 다른 정책을 같은 지정 일정에서 비교한다. 합류 순서가 작업의 실행 순서를 재배열했다거나 실제 처리율이 개선되었다고 주장하지 않는다.

중간 과정을 따라가는 예제

부모가 두 개의 별도 결과 슬롯을 준비했다. 생성과 합류는 모두 성공한다. A는 자신의 슬롯에 2+3을, B는 자신의 슬롯에 7+1을 기록한다. 부모는 A, B 순서로 합류한 뒤 합계를 구한다.

  1. A의 슬롯 값은 5, B의 슬롯 값은 8이다. 작업 중 부모는 이 슬롯을 읽지 않는다.

  2. B가 먼저 끝나는 일정도 가능하다. 부모의 첫 합류는 A를 기다리고, 둘째 합류는 이미 끝난 B의 상태를 회수할 수 있다.

  3. 두 합류 성공 후 부모가 슬롯을 읽어 5+8=13을 계산한다. 슬롯 저장 공간은 이때까지 유지한다.

합계는 13이다. 이 모형에서는 작업자가 별도 슬롯을 쓰고 부모가 두 작업의 완료 후 읽는다. 합류 순서가 작업 완료 순서를 지정하지 않는다.

조건을 바꾸어 비교하기

전체 합계는 같고 첫 응답은 다른 일정

위 A/B의 두 합류 순서에서 첫 결과 시각, 전체 완료 시각, 합계를 비교하라.

  1. A 우선은 9 ms까지 기다려 19를 받고 B도 그 시각에 회수한다.

  2. B 우선은 4 ms에 25를 받고 9 ms에 19를 받는다. 합계는 19 + 25 = 44다.

첫 결과 시각은 9 ms 대 4 ms이고 전체 완료는 모두 9 ms다.

비교할 점

첫 응답 지연과 전체 작업 완료 시간을 같은 수치로 취급하지 않는다.

성공 목록과 실패 결과

세 작업의 기대 결과는 A=19, B=22, C=25다. A/C 생성과 합류만 성공하고 B 생성은 E로 실패했다. 무엇을 보고하는가?

  1. 회수 가능한 결과는 A의 19와 C의 25이며 부분 합은 44다.

  2. 기대한 전체 합 66을 보고하지 않고 B 생성 실패 E와 미완료 과제를 함께 보고한다.

성공한 두 작업의 부분 합 44는 세 작업 완료의 증거가 아니다.

비교할 점

결측을 0으로 치환하면 합계 숫자만 남고 실패 원인이 사라진다.

종이와 본문으로 직접 해보기

A 생성은 성공, B 생성은 오류 번호 E를 반환했다. 합류 목록을 정하고, A가 결과 6을 기록하면 부모가 어떤 결과를 보고할 수 있는지 설명하라.

힌트 보기

유효한 식별자가 생긴 호출만 목록에 넣는다. 없는 결과를 0으로 임의 채우지 않는다.

풀이 보기

A에만 합류한다. B 식별자는 유효하다고 가정할 수 없다. A의 결과 6과 B 생성 실패 E를 함께 보고하며, 두 작업 합계가 완성되었다고 주장하지 않는다.

오해와 반례

먼저 생성한 스레드가 먼저 종료한다.

생성 순서는 실행 일정이나 완료 순서를 보장하지 않는다. B의 계산이 짧거나 먼저 실행되면 B가 먼저 끝난다. 정해진 순서가 필요하면 별도 동기화 규칙을 설계해야 한다.

자기점검

A 생성이 0을 반환했다. 이것만으로 A의 계산이 끝났는가?

답과 이유 보기

아니다.

0은 생성 성공이며 작업 완료는 합류 등으로 확인한다.

부모와 두 작업자가 동시에 살아 있을 때 실행 흐름은 몇 개인가?

답과 이유 보기

3개이다.

부모도 하나의 스레드다. 이미 작업자가 종료한 시점에는 이 수가 달라진다.

detached 대상에 합류해 결과를 회수할 수 있는가?

힌트 1

대상 종료 전에는 해당 합류가 끝나지 않는다.

힌트 2

이미 종료한 대상은 여기서 즉시 회수된다고 둔다.

연습 2 · 오류 찾아 고치기

세 생성 호출의 성공 여부와 무관하게 식별자 배열 세 칸 모두에 합류한다. B만 생성 실패했다면 무엇을 고치는가?

힌트 1

출력 식별자의 유효성은 성공 반환에 달려 있다.

힌트 2

작업 번호와 성공한 식별자를 별도 장부로 묶는다.

풀이와 답 확인

  1. 성공한 A/C만 등록하고 합류한다. B는 오류 번호를 기록한다.

  2. 합류 실패도 별도로 기록하고 성공 확인 없이 결과 슬롯을 읽지 않는다.

성공 생성 목록과 결과 완료 목록을 구별한다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

힌트 1

detach 시점과 종료 시점을 나눈다.

힌트 2

인자 객체의 마지막 사용자 완료를 확인한다.

  2. 다른 완료 통지·소유권 이전 등으로 마지막 사용을 확인한 후 정리한다.

자동 회수되는 스레드 자원과 애플리케이션 인자의 수명은 별도다.

detached로 바꾸면 A의 모든 접근이 즉시 끝난다.

회수 정책 설정을 실제 종료 사건으로 해석하지 않는다.

작업자는 계속 살아 있는데 요청이 끝나면 스레드별 자료도 없어질까?

새 작업자 풀에서 A는 요청 R과 S를 순서대로 처리하며 두 요청 사이에 종료하지 않는다. 유효한 키 K에 R의 문맥 pR을 연결했다. R 처리가 끝났다는 애플리케이션 사건만으로 스레드 종료 소멸자가 호출되지는 않는다. S가 같은 A에서 getspecific(K)를 호출하면 명시적 교체/정리 전에는 pR이 남아 있다.

요청마다 문맥을 따로 쓰려면 요청 종료 경로에서 소유한 pR을 정리하고 연결을 NULL로 바꾸거나, 다음 문맥을 적절히 교체한다. 성공한 setspecific(K,pS)는 포인터 연결을 바꾸며 기존 pR을 자동 해제하지 않는다. 재연결하지 않는 한 번 소멸자 모형에서 A의 최종 슬롯 pS는 종료 소멸자로 정리되지만, 잃어버린 pR은 따로 남는다.

다른 스레드의 슬롯은 분리되어도 같은 객체 주소를 넣으면 자료가 분리되지 않는다. A의 슬롯 K와 B의 슬롯 K가 모두 p를 가리키는 경우, 두 소멸자가 각각 free(p)를 호출하는 정책은 중복 해제를 일으킬 수 있다. 스레드별 조회와 실제 객체 소유권을 다른 표로 관리한다. 이 단원에서는 공유 객체의 동기화 없는 충돌을 실행하여 값을 추정하지 않는다.

키 삭제는 소멸자 호출을 하지 않는다. 또한 스레드 종료 소멸자는 호출 전 슬롯이 NULL로 바뀌고 소멸자가 다시 값을 연결하면 반복 규칙이 관련된다. 순서나 무한 반복 완료를 애플리케이션 계약으로 가정하지 않는다. 여기의 수치 예제는 재연결하지 않는 소멸자와 유효한 키, 성공한 API 호출이라는 조건을 둔다.

공통 키에 연결되는 개별 슬롯

pthread_key_create는 스레드별 데이터에 사용할 키를 만든다. 키 자체는 여러 스레드가 공통으로 사용하지만 그 키에 연결된 값은 각 스레드마다 따로 있다. 새 키의 연결 값은 모든 스레드에서 NULL로 시작한다. pthread_setspecific과 pthread_getspecific은 호출한 스레드의 연결을 설정하고 조회한다.

A가 키 K에 pA를 저장하고 B가 같은 K에 pB를 저장해도 A의 조회 결과가 pB로 바뀌지 않는다. 이 방식은 요청별 문맥이나 작업자별 상태에 유용하다. 키 생성의 성공과 키의 유효 기간은 별도로 관리해야 한다.

포인터의 분리와 객체의 분리는 다르다

스레드별 데이터 슬롯은 void* 값을 보관한다. 구조체 내용을 자동 복제하지 않는다. pA와 pB가 서로 다른 객체를 가리키면 작업자는 각자 객체를 사용할 수 있지만, 같은 객체 p를 저장하면 두 슬롯이 같은 대상을 가리킨다.

따라서 스레드별 슬롯이라는 이유만으로 공유 객체의 데이터 경쟁이 사라지지 않는다. 누가 객체를 만들고 언제 해제하는지 정해야 한다. 이 단원의 예제는 서로 다른 힙 객체를 사용하며 다른 작업자가 이를 읽거나 쓰지 않는다는 조건을 둔다.

종료 시 소멸자와 명시적 키 삭제

키를 만들 때 소멸자 함수를 등록할 수 있다. 스레드 종료 시 연결 값이 NULL이 아니면 해당 값을 인자로 소멸자를 호출한다. 여러 키의 소멸자 호출 순서는 정해져 있지 않다. 소멸자가 값을 다시 연결하면 반복 처리 규칙이 관련되므로 단순 한 번 호출 모형과 구별한다.

pthread_key_delete는 키를 삭제하지만 연결된 객체에 소멸자를 호출하지 않는다. 키를 먼저 삭제했다고 메모리가 자동 해제되었다고 생각하면 누수가 생길 수 있다. 객체를 별도로 정리하고 모든 사용자가 키 사용을 마쳤다는 사실을 확인한 뒤 삭제하는 정책이 필요하다.

작업 범위를 나누었으면 공유 주소의 위험도 사라졌을까?

새 배열의 인덱스는 0부터 5까지다. A가 [0,3), B가 [3,6)를 갱신하면 각각 0,1,2와 3,4,5를 쓰므로 서로 다른 요소다. 부모가 실행 중 배열을 접근하지 않고 안정된 저장 공간을 모든 사용 종료까지 유지한다는 조건도 둔다. 반면 B의 시작을 2로 잘못 정하면 인덱스 2가 겹친다. 범위 이름이 다르다는 사실보다 실제 접근 집합의 교집합을 검사한다.

그 겹친 요소가 보통 C 정수이고 동기화 없이 충돌하면 데이터 경쟁의 정의되지 않은 동작이다. 두 작업의 읽기/쓰기 종이 일정을 지정해 최종 값을 구하는 추상 모형은 문제의 직관을 보여줄 뿐, 실제 C 결과를 그 유한 값들로 제한하지 않는다. 서로 다른 요소 접근에서도 배열의 재할당이나 해제가 동시에 일어나면 객체 수명 문제가 추가된다.

부모가 안정된 records 배열에 인자를 보관해도 한 작업만 합류하고 배열을 해제하면 나머지 사용자에게 위험하다. 또 작업자가 자기 지역 변수의 주소를 반환하면 합류로 주소 숫자를 받아도 대상의 수명은 끝났다. 합류는 죽은 지역 객체를 되살리지 않는다. 부모 소유 결과 슬롯이나 명확한 힙 소유권 이전을 사용한다.

스택이 각자 있다는 설명은 주소를 전달해도 다른 스레드가 접근하지 못한다는 뜻이 아니다. 주소 공간을 공유하므로 유효한 지역 객체에 대한 접근은 가능하지만 그 객체를 만든 호출의 종료, 후속 수정과 동기화, 접근 종료를 함께 관리해야 한다. main 반환은 다른 작업자가 끝날 때까지 자동 기다리지 않는다.

자기 스택과 같은 주소 공간

스레드는 각각 스택을 갖지만 전역 데이터와 힙, 파일 서술자 등 많은 프로세스 자원을 공유한다. 자기 스택이 있다는 말은 다른 스레드가 포인터를 통해 그 스택의 객체에 접근할 수 없다는 뜻이 아니다. 유효한 객체 주소를 넘기면 다른 스레드도 접근할 수 있다.

문제는 접근이 가능한지와 객체가 살아 있는지가 별개라는 점이다. 생성 인자로 지역 변수 주소를 전달했다면 함수가 돌아가기 전에 작업자의 사용이 끝나는지 확인해야 한다. 반복문의 같은 변수 주소를 여러 번 넘기면 작업자마다 그 순간의 값이 따로 복사되지 않는다.

합류 이후에도 반환 주소가 유효한 것은 아니다

작업자가 자신의 지역 변수 주소를 반환하고 종료하면, 부모가 합류해 그 포인터 값을 얻어도 대상 객체의 수명은 끝났다. pthread_exit의 문서도 반환값이 호출 스레드의 스택 객체를 가리키지 않도록 요구한다. 합류는 죽은 지역 객체를 되살리지 않는다.

대신 부모가 유지하는 결과 슬롯에 기록하거나, 수명과 해제 권한을 정한 힙 객체를 반환할 수 있다. 부모의 결과 배열도 사용 중에 재할당하거나 해제하면 안 된다. detached 작업에서는 합류가 없으므로 다른 완료 확인 정책을 세워야 한다.

공유 값 변경에는 동기화가 필요하다

종이 위의 읽기·더하기·쓰기 모형에서 두 작업자가 모두 0을 읽고 각각 1을 쓰면 최종 값은 1이다. 이는 분리된 단계가 겹칠 때 갱신 하나가 사라지는 직관을 보여준다. 하지만 실제 C의 보통 정수에 동기화 없이 충돌하는 접근을 하면 데이터 경쟁이 되어 동작이 정의되지 않는다. 실제 C 결과가 항상 1 또는 2라고 단정해서는 안 된다.

C11의 조건은 다른 스레드의 충돌하는 두 동작 중 하나 이상이 원자적이지 않고 어느 쪽도 다른 쪽보다 happens-before 관계에 있지 않는 경우다. mutex로 전체 읽기·더하기·쓰기를 보호하거나 적합한 원자 연산을 쓰면 이를 피할 수 있다. 잠금 일부만 감싸거나 접근 하나만 보호하면 충분하지 않을 수 있다.

다른 문제에 적용하기

부모는 안정된 records에 A=9, B=12, C=15를 준비했다. 각 작업은 10을 더해 별도 결과를 쓴다. 시각 0에 A/C 생성은 성공하고 B는 E로 실패했다. A는 9 ms, C는 4 ms에 종료하며 합류 처리 시간은 0이다. 두 합류 순서의 첫 결과 시각과 회수 가능한 합계를 구하라. A는 24바이트 문맥 pR을 키 K에 연결하고 다음 요청에서 별도 24바이트 pS로 성공 교체했지만 pR을 정리하지 않았다. 소멸자는 재연결 없이 현재 포인터만 해제한다. A 종료 후 정리되지 않은 양을 구하라. 끝으로 부모가 A에만 합류한 뒤 C도 읽는 records를 해제하는 정책을 고쳐라.

힌트 1

B의 생성 실패와 A/C의 종료 시각을 각각 장부에 적는다.

힌트 2

키의 현재 연결과 두 객체의 정리 책임, records의 전체 사용자를 따로 센다.

풀이와 답 확인

  1. 성공 합류 목록은 A,C이며 A 우선의 첫 결과는 9 ms, C 우선의 첫 결과는 4 ms다. 전체 회수는 모두 9 ms다.

  2. 결과 A는 19, C는 25이며 부분 합은 44다. 기대한 B 결과 22까지 포함한 전체 66을 완료 결과로 보고하지 않는다.

  3. 두 문맥의 누적 할당은 48바이트다. A 종료 소멸자는 현재 pS의 24바이트만 정리하며 pR의 24바이트는 별도 소유 장부로 정리해야 한다.

  4. records는 A/C 모두 사용한다. C의 마지막 사용 종료까지 저장 공간을 유지하고 성공 합류/완료 증거 뒤 정리한다. 실제 C 충돌/죽은 객체 접근을 종이 일정의 값으로 인증하지 않는다.

첫 결과는 A 우선 9 ms, C 우선 4 ms이고 전체 회수는 9 ms다. 성공 부분 합은 44이며 B 실패 E를 함께 보고한다. 별도 정리되지 않은 pR은 24바이트다. 공유 records는 A/C 모두의 사용 종료 확인 뒤 해제한다.
