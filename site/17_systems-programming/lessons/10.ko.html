소단원 10.1

pthread 생성·합류

작업자를 두 명 만들면 누가 먼저 끝나며, 결과는 언제 읽을 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 함수와 인자

  • 포인터가 가리키는 객체

  • 프로세스

학습 목표

  • 생성과 완료 대기를 구분한다.

  • 성공한 스레드만 합류하고 오류 반환값을 처리한다.

  • 결과 객체의 수명을 합류 시점과 연결한다.

시작 함수를 실행하는 새 흐름

pthread_create는 같은 프로세스 안에 새 실행 흐름을 만든다. 새 스레드는 start_routine에 arg를 인자로 전달해 실행한다. arg는 포인터 값이며, 인자가 가리키는 객체를 자동 복사하는 인터페이스가 아니다. 호출자와 작업자가 사용할 객체를 먼저 준비해야 한다.

생성 성공 뒤 호출자와 새 스레드 중 누가 다음 명령을 먼저 실행하는지는 일반적으로 정해져 있지 않다. A를 먼저 만들었다고 A가 먼저 완료되는 것은 아니다. 기본 속성으로 만든 스레드는 joinable이며, 종료 사실을 합류로 회수할 수 있다.

합류는 특정 작업자의 종료를 기다린다

pthread_join(A, ...)는 A가 종료될 때까지 기다린다. A가 이미 종료했다면 바로 종료 상태를 회수할 수 있다. B가 먼저 끝나도 A에 합류 중인 호출자가 곧바로 B의 결과를 회수하는 것은 아니다. 호출자가 지정한 대상이 중요하다.

성공한 합류 뒤에는 대상 스레드가 종료했으므로 그 작업에 쓰인 인자 객체를 정리할 수 있다. 다만 다른 작업자도 그 객체를 사용하면 모두의 완료가 필요하다. 같은 스레드에 여러 곳에서 동시에 합류하거나 이미 합류한 대상에 다시 합류하는 동작은 정의되지 않는다.

반환값과 정리 경로

pthread_create와 pthread_join은 성공하면 0, 실패하면 오류 번호를 직접 반환한다. 대부분의 pthread 함수는 errno를 설정하는 방식이 아니므로 반환값을 검사한다. 생성 실패 시 출력된 스레드 식별자를 유효한 대상으로 가정해서 합류하면 안 된다.

joinable 스레드는 종료 후에도 합류 전까지 일부 자원이 남는다. detached 스레드는 종료 시 해당 자원을 자동 회수하지만 합류할 수 없다. detach를 호출한 순간 작업까지 완료되었다는 뜻은 아니다. 또한 main에서 반환하거나 exit를 호출하면 다른 작업자가 남아 있어도 프로세스가 끝난다.

중간 과정을 따라가는 예제

부모가 두 개의 별도 결과 슬롯을 준비했다. 생성과 합류는 모두 성공한다. A는 자신의 슬롯에 2+3을, B는 자신의 슬롯에 7+1을 기록한다. 부모는 A, B 순서로 합류한 뒤 합계를 구한다.

  1. A의 슬롯 값은 5, B의 슬롯 값은 8이다. 작업 중 부모는 이 슬롯을 읽지 않는다.

  2. B가 먼저 끝나는 일정도 가능하다. 부모의 첫 합류는 A를 기다리고, 둘째 합류는 이미 끝난 B의 상태를 회수할 수 있다.

  3. 두 합류 성공 후 부모가 슬롯을 읽어 5+8=13을 계산한다. 슬롯 저장 공간은 이때까지 유지한다.

합계는 13이다. 이 모형에서는 작업자가 별도 슬롯을 쓰고 부모가 두 작업의 완료 후 읽는다. 합류 순서가 작업 완료 순서를 지정하지 않는다.

종이와 본문으로 직접 해보기

A 생성은 성공, B 생성은 오류 번호 E를 반환했다. 합류 목록을 정하고, A가 결과 6을 기록하면 부모가 어떤 결과를 보고할 수 있는지 설명하라.

힌트 보기

유효한 식별자가 생긴 호출만 목록에 넣는다. 없는 결과를 0으로 임의 채우지 않는다.

풀이 보기

A에만 합류한다. B 식별자는 유효하다고 가정할 수 없다. A의 결과 6과 B 생성 실패 E를 함께 보고하며, 두 작업 합계가 완성되었다고 주장하지 않는다.

오해와 반례

먼저 생성한 스레드가 먼저 종료한다.

생성 순서는 실행 일정이나 완료 순서를 보장하지 않는다. B의 계산이 짧거나 먼저 실행되면 B가 먼저 끝난다. 정해진 순서가 필요하면 별도 동기화 규칙을 설계해야 한다.

자기점검

A 생성이 0을 반환했다. 이것만으로 A의 계산이 끝났는가?

답과 이유 보기

아니다.

0은 생성 성공이며 작업 완료는 합류 등으로 확인한다.

부모와 두 작업자가 동시에 살아 있을 때 실행 흐름은 몇 개인가?

답과 이유 보기

3개이다.

부모도 하나의 스레드다. 이미 작업자가 종료한 시점에는 이 수가 달라진다.

detached 대상에 합류해 결과를 회수할 수 있는가?

답과 이유 보기

그럴 수 없다.

detached 대상은 합류 대상이 아니므로 별도 완료 통지와 결과 수명 정책이 필요하다.

한 단계 더

A가 공유 객체 X를 쓰고 B도 X를 읽는 상황을 그려 보자. A에만 합류한 뒤 X를 해제해도 안전한지 확인하라. B가 아직 실행 중이면 안전하지 않다. 두 작업 모두 X의 사용을 끝냈다는 증거가 필요하다.

소단원 10.2

스레드별 데이터

같은 이름의 열쇠로 각 작업자가 서로 다른 값을 꺼낼 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 포인터와 힙 객체

  • 함수 호출

  • 스레드 생성

학습 목표

  • 키와 스레드별 포인터 값을 구별한다.

  • 스레드별 슬롯과 실제 객체의 공유 여부를 따로 판단한다.

  • 소멸자와 키 삭제의 차이를 설명한다.

공통 키에 연결되는 개별 슬롯

pthread_key_create는 스레드별 데이터에 사용할 키를 만든다. 키 자체는 여러 스레드가 공통으로 사용하지만 그 키에 연결된 값은 각 스레드마다 따로 있다. 새 키의 연결 값은 모든 스레드에서 NULL로 시작한다. pthread_setspecific과 pthread_getspecific은 호출한 스레드의 연결을 설정하고 조회한다.

A가 키 K에 pA를 저장하고 B가 같은 K에 pB를 저장해도 A의 조회 결과가 pB로 바뀌지 않는다. 이 방식은 요청별 문맥이나 작업자별 상태에 유용하다. 키 생성의 성공과 키의 유효 기간은 별도로 관리해야 한다.

포인터의 분리와 객체의 분리는 다르다

스레드별 데이터 슬롯은 void* 값을 보관한다. 구조체 내용을 자동 복제하지 않는다. pA와 pB가 서로 다른 객체를 가리키면 작업자는 각자 객체를 사용할 수 있지만, 같은 객체 p를 저장하면 두 슬롯이 같은 대상을 가리킨다.

따라서 스레드별 슬롯이라는 이유만으로 공유 객체의 데이터 경쟁이 사라지지 않는다. 누가 객체를 만들고 언제 해제하는지 정해야 한다. 이 단원의 예제는 서로 다른 힙 객체를 사용하며 다른 작업자가 이를 읽거나 쓰지 않는다는 조건을 둔다.

종료 시 소멸자와 명시적 키 삭제

키를 만들 때 소멸자 함수를 등록할 수 있다. 스레드 종료 시 연결 값이 NULL이 아니면 해당 값을 인자로 소멸자를 호출한다. 여러 키의 소멸자 호출 순서는 정해져 있지 않다. 소멸자가 값을 다시 연결하면 반복 처리 규칙이 관련되므로 단순 한 번 호출 모형과 구별한다.

pthread_key_delete는 키를 삭제하지만 연결된 객체에 소멸자를 호출하지 않는다. 키를 먼저 삭제했다고 메모리가 자동 해제되었다고 생각하면 누수가 생길 수 있다. 객체를 별도로 정리하고 모든 사용자가 키 사용을 마쳤다는 사실을 확인한 뒤 삭제하는 정책이 필요하다.

중간 과정을 따라가는 예제

유효한 키 K에 A는 값 2를 담은 객체 pA, B는 값 5를 담은 별도 객체 pB를 연결한다. A만 자신의 객체 값을 1 증가시킨다. 각 스레드는 종료 전까지 자신의 객체만 접근한다.

  1. A에서 getspecific(K)는 pA, B에서는 pB를 반환한다. 같은 키라도 조회하는 스레드가 다르다.

  2. A의 객체 값은 2+1=3이 되고 B의 객체 값은 5로 유지된다.

  3. 두 값이 모두 NULL이 아니고 소멸자가 재연결하지 않으며 각 객체를 한 번 해제한다면 두 스레드 종료 전체에서 소멸자 호출은 2번이다.

A의 값 3, B의 값 5이다. 결과 분리는 슬롯뿐 아니라 서로 다른 객체를 사용한다는 조건에 의존한다.

종이와 본문으로 직접 해보기

A와 B가 같은 키에 같은 객체 p를 연결했다. p의 최초 값은 4다. B가 접근하지 않는 동안 A가 1 증가시킨 뒤, 완료 통지와 적절한 동기화 후 B가 값을 읽는다. B는 어떤 값을 읽으며 소멸자 free를 둘 다 수행해도 될까?

힌트 보기

포인터가 같은지 확인하고 해제 권한을 하나로 정한다.

풀이 보기

B도 같은 객체를 보므로 5를 읽는다. 두 스레드에서 같은 p를 free하면 중복 해제 문제가 생긴다. 소유자를 한 곳으로 정하거나 참조 수명 정책을 사용해야 한다. 읽기 시점의 동기화 조건을 제거하면 값 5가 보장된다는 결론도 낼 수 없다.

오해와 반례

키를 삭제하면 연결된 모든 메모리도 해제된다.

key_delete는 소멸자를 호출하지 않는다. 각자 할당한 객체가 남아 있을 수 있다. 또한 동일 객체를 여러 슬롯에 연결했다면 각 슬롯에서 자동 해제하는 정책 자체가 위험하다.

자기점검

키를 새로 만들고 아직 값을 설정하지 않았다. 연결 값은?

답과 이유 보기

NULL이다.

새 키는 모든 스레드에서 NULL 연결로 초기화된다.

A와 B의 연결 값이 각각 pA와 NULL이고 재연결이 없다면 종료 소멸자는 몇 번인가?

답과 이유 보기

1번이다.

NULL이 아닌 A의 값에 대해서만 호출된다.

setspecific은 구조체의 모든 필드를 복사하는가?

답과 이유 보기

아니다. 포인터 값을 연결한다.

가리키는 객체의 수명과 공유는 호출자가 관리한다.

한 단계 더

세 스레드가 서로 다른 객체를 같은 키에 연결하고 모두 종료하기 전에 키를 삭제했다고 하자. key_delete 자체의 소멸자 호출은 0번이다. 객체 세 개를 잃지 않으려면 어떤 별도 정리 경로가 필요한지 그려 보라. 삭제된 키에 다시 접근하는 설계는 피해야 한다.

자기 스택과 같은 주소 공간

스레드는 각각 스택을 갖지만 전역 데이터와 힙, 파일 서술자 등 많은 프로세스 자원을 공유한다. 자기 스택이 있다는 말은 다른 스레드가 포인터를 통해 그 스택의 객체에 접근할 수 없다는 뜻이 아니다. 유효한 객체 주소를 넘기면 다른 스레드도 접근할 수 있다.

문제는 접근이 가능한지와 객체가 살아 있는지가 별개라는 점이다. 생성 인자로 지역 변수 주소를 전달했다면 함수가 돌아가기 전에 작업자의 사용이 끝나는지 확인해야 한다. 반복문의 같은 변수 주소를 여러 번 넘기면 작업자마다 그 순간의 값이 따로 복사되지 않는다.

합류 이후에도 반환 주소가 유효한 것은 아니다

작업자가 자신의 지역 변수 주소를 반환하고 종료하면, 부모가 합류해 그 포인터 값을 얻어도 대상 객체의 수명은 끝났다. pthread_exit의 문서도 반환값이 호출 스레드의 스택 객체를 가리키지 않도록 요구한다. 합류는 죽은 지역 객체를 되살리지 않는다.

대신 부모가 유지하는 결과 슬롯에 기록하거나, 수명과 해제 권한을 정한 힙 객체를 반환할 수 있다. 부모의 결과 배열도 사용 중에 재할당하거나 해제하면 안 된다. detached 작업에서는 합류가 없으므로 다른 완료 확인 정책을 세워야 한다.

공유 값 변경에는 동기화가 필요하다

종이 위의 읽기·더하기·쓰기 모형에서 두 작업자가 모두 0을 읽고 각각 1을 쓰면 최종 값은 1이다. 이는 분리된 단계가 겹칠 때 갱신 하나가 사라지는 직관을 보여준다. 하지만 실제 C의 보통 정수에 동기화 없이 충돌하는 접근을 하면 데이터 경쟁이 되어 동작이 정의되지 않는다. 실제 C 결과가 항상 1 또는 2라고 단정해서는 안 된다.

C11의 조건은 다른 스레드의 충돌하는 두 동작 중 하나 이상이 원자적이지 않고 어느 쪽도 다른 쪽보다 happens-before 관계에 있지 않는 경우다. mutex로 전체 읽기·더하기·쓰기를 보호하거나 적합한 원자 연산을 쓰면 이를 피할 수 있다. 잠금 일부만 감싸거나 접근 하나만 보호하면 충분하지 않을 수 있다.

중간 과정을 따라가는 예제

부모가 수명이 두 합류 이후까지 유지되는 records[0], records[1]에 각각 2와 3을 넣는다. A와 B는 각자 해당 레코드의 값에 10을 더해 별도 결과 슬롯에 저장한다. 모든 생성·합류는 성공하고 부모는 작업 중 레코드를 수정하지 않는다.

  1. A에게 records[0]의 주소, B에게 records[1]의 주소를 넘긴다. 서로 다른 안정된 객체 주소다.

  2. A는 2+10=12, B는 3+10=13을 자신의 슬롯에 기록한다.

  3. 부모는 두 합류 성공 후 12+13=25를 읽고 레코드 저장 공간을 정리할 수 있다.

결과는 12와 13, 합계25다. 같은 반복 변수 주소를 넘기는 방식과 달리 각 인자 객체가 따로 있고 사용이 끝날 때까지 살아 있다.

종이와 본문으로 직접 해보기

종이 모형의 공유 카운터는 0이다. A읽기, B읽기, A쓰기, B쓰기 순서에서 각각 1 증가를 시도한다. 이어 전체 증가를 하나의 mutex 임계 구역으로 보호한 순서와 비교하라. 실제 비원자 C 프로그램의 보장 여부도 말하라.

힌트 보기

종이 모형에서는 읽은 값을 각자 종이에 적는다. 실제 언어 의미는 별도로 판단한다.

풀이 보기

종이 모형에서 둘 다 0을 읽고 1을 쓰므로 최종1이다. 성공한 같은 mutex의 임계 구역 두 개가 직렬 실행되면 0→1→2다. 동기화 없는 실제 비원자 C 충돌은 정의되지 않은 동작이므로 종이 값1을 실제 실행 결과로 보장할 수 없다.

오해와 반례

작업자의 지역 변수 주소도 합류한 뒤에는 안전하게 읽는다.

그 객체는 작업자 종료와 함께 수명을 잃는다. 합류가 포인터를 전달해도 객체는 부활하지 않는다. 부모 소유 슬롯이나 수명 정책이 있는 힙 객체를 사용해야 한다.

한 단계 더

A는 mutex 안에서 공유 값을 쓰지만 B는 잠금 없이 읽는 설계를 검사하라. 같은 mutex를 획득하지 않는 B와 충돌하면 보호가 완성되지 않는다. 또 작업자의 반환 힙 객체를 부모가 한 번 해제하는 정책과 지역 주소 반환을 비교해 수명 표를 작성하라.
