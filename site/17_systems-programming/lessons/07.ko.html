소단원 7.1

sigaction과 마스크

시그널이 발생한 순간과 처리 함수가 실행된 순간이 꼭 같을까?

준비 개념과 학습 목표

준비 개념

  • signal은 특정 사건을 알리는 OS 통지이며 처리 정책을 disposition이라 한다.

  • mask는 해당 스레드에서 현재 전달을 막는 신호 집합이다.

학습 목표

  • 발생·pending·전달을 구별한다.

  • 처리 중 마스크 변화와 복원을 추적한다.

차단 집합과 pending 집합을 복사하면 자식에도 같은 통지가 남을까?

새 단일 스레드 Linux 종이 모형에서 마스크 M={USR1,ALRM}, pending 집합 P={USR1}이다. USR1과 USR2 모두 정상 반환하는 handler가 등록돼 있다. USR1 handler의 sa_mask={USR2}이고 SA_NODEFER는 없다. 발생은 통지의 생성, pending은 아직 전달되지 않은 종류, 마스크는 현재 전달을 막는 종류다. 집합의 같은 원소라도 세 장부의 의미는 다르다.

USR1을 마스크에서 제거하고 ALRM만 유지한 뒤 첫 USR1 handler에 진입하는 사건을 명시한다. pending USR1은 전달되며 제거되고 임시 마스크는 {ALRM,USR1,USR2}가 된다. 그 안에서 USR1 두 번과 USR2 한 번이 발생하면 pending 종류는 {USR1,USR2}다. handler 반환 뒤 마스크는 {ALRM}으로 복원된다. 두 종류는 전달 가능하지만 서로 다른 standard signal의 순서를 미리 정하지 않는다.

별도 fork 대안에서는 부모의 M={USR1,ALRM}, P={USR1}인 초기 상태에서 자식이 생긴다. 자식은 마스크와 disposition을 상속하지만 처음 pending은 빈 집합이다. 부모에 남은 신호를 자식이 자동 소비한다는 계획은 틀리다. 직접 exec 성공은 마스크와 pending을 보존하지만 잡던 handler 정책은 기본으로 바뀌며 무시 정책은 유지된다. 이 마지막 변화는 새 이미지의 신호 처리 안전성도 따로 검토하게 한다.

먼저 확인할 개념

  • 생성과 관리표 등록의 순서

정책과 전달 시점을 분리한다

sigaction은 특정 시그널을 기본 동작으로 처리할지, 무시할지, 사용자 handler로 받을지 설정한다. 정책을 등록하는 것과 시그널을 발생시키는 것은 다른 행위다. SIGKILL과 SIGSTOP은 사용자 handler로 잡거나 무시할 수 없다.

시그널이 발생했지만 마스크에 차단되어 있으면 전달될 때까지 pending으로 남을 수 있다. 차단은 삭제와 다르다. 프로그램의 정상 제어 흐름이 잠시 handler로 들어갔다가 복귀하는 비동기 사건을 생각하되, 모든 코드 지점에서 즉시 처리된다고 가정하지 않는다.

handler의 마스크는 임시로 늘어난다

특별한 SA_NODEFER가 없으면 처리 중인 시그널 자체가 handler 실행 동안 추가 차단된다. sa_mask에 지정한 시그널도 함께 차단된다. handler가 정상 반환하면 이전 마스크가 복원된다.

Linux의 disposition은 프로세스 수준이지만 마스크는 스레드별이다. process-directed signal은 차단하지 않은 스레드 중 하나에 전달될 수 있으므로 단일 스레드의 표를 다중 스레드 전체 정책처럼 확대하지 않는다. 이 단원 예제는 한 스레드만 가정한다.

일반 시그널을 횟수 기록으로 쓰지 않는다

같은 standard signal이 차단된 동안 여러 번 발생해도 pending은 같은 종류 하나로 병합될 수 있다. 따라서 handler 실행 횟수가 사건 발생 횟수와 같다고 보장되지 않는다. 서로 다른 종류의 pending 전달 순서도 임의로 정해 외우지 않는다.

real-time signal은 별도의 큐 규약을 가지지만 무한 큐라는 뜻은 아니다. 일반적인 제어 통지에는 알림을 보고 실제 상태를 조회하는 설계가 유용하다. 마스크 해제 후 처리할 일이 있다는 상태와 몇 개 발생했는지를 구별한다.

다음 전달 전의 경계 상태

마지막 행은 다음 전달을 아직 수행하지 않은 경계 상태다. 실제 handler 진입 시각이나 두 종류의 전달 순서를 관측한 표가 아니다. 마스크에 ALRM이 있다고 ALRM이 발생한 것은 아니다.

중간 과정을 따라가는 예제

단일 스레드에서 마스크는 {USR1}이고 USR1 handler의 sa_mask={USR2}, SA_NODEFER는 없다. 차단 중 USR1 세 번 발생한 뒤 마스크를 빈 집합으로 바꾸어 handler에 진입한다. 그 handler 중 USR2 한 번과 USR1 한 번이 발생한다. 각 시점의 차단 집합과 pending 종류를 구하라. 기본 종료 대신 두 신호 모두 handler가 등록됐다고 가정한다.

  1. 처음 USR1 세 번은 pending 종류{USR1}로 병합된다.

  2. 첫 USR1 전달 시 그 pending을 제거하고 handler 중 마스크{USR1,USR2}가 된다.

  3. handler 중 두 발생 뒤 pending{USR1,USR2}다.

  4. 정상 반환하면 빈 마스크가 복원되어 두 pending이 전달 가능하지만 두 종류의 순서는 지정하지 않는다.

첫 handler 동안 두 종류 모두 대기하고 반환 뒤 전달 가능하다. 처음3번이3회 handler를 보장하지 않는다.

조건을 바꾸어 비교하기

합집합과 복원의 서로 다른 집합

위 handler 중 마스크와 반환 뒤 마스크를 구하고 ALRM pending 여부를 판정하라.

  1. 처리 중은 기존 {ALRM}, 자동 차단 {USR1}, sa_mask {USR2}의 합집합이다.

  2. 반환하면 기존 {ALRM}만 복원된다. 이 이력에는 ALRM 발생이 없다.

처리 중 세 종류를 차단하고 반환 뒤 ALRM만 차단한다. ALRM은 pending이 아니다.

비교할 점

등록한 집합은 실제 사건 발생 목록이 아니다.

부모 pending을 자식에 복사한 오류

초기 마스크와 pending에서 fork 성공 뒤 부모와 자식의 두 집합을 비교하라.

  1. 부모는 기존 마스크와 pending을 유지한다.

  2. 자식의 마스크는 {USR1,ALRM}이지만 pending은 처음 ∅다.

같은 차단 정책과 같은 대기 통지는 서로 다른 상속 조건이다.

비교할 점

실제 process-directed 신호나 스레드별 다중 전달은 수행하지 않은 한 스레드 모형이다.

오해와 반례

차단은 신호를 버리고 마스크에 넣으면 해당 사건이 발생한다.

차단된 실제 발생은 pending으로 남을 수 있고, 발생하지 않은 USR2는 mask에 있어도 pending이 아니다. 무시 정책·차단·발생을 별도 열로 기록한다.

연습 1 · 값과 상태 예측

SA_NODEFER를 켜고 sa_mask={USR1,USR2}를 명시하면 기존 {ALRM}에서 USR1 handler 중 마스크는?

힌트 2

풀이와 답 확인

  1. SA_NODEFER가 자동 추가를 없애도 명시 집합의 USR1은 차단된다.

  2. 전체는 {ALRM,USR1,USR2}다.

NODEFER 하나로 같은 신호의 재진입이 항상 허용되는 것은 아니다.

  • 재진입 중 공유 상태 위험을 설명한다.

  • 짧은 handler와 정상 흐름의 후속 처리로 역할을 나눈다.

한 비트 알림을 안전하게 가져오는 것과 모든 사건을 세는 것은 같은가?

새 정상 흐름의 flag는 0이고 handler는 volatile sig_atomic_t flag에 1만 대입하는 작은 설계를 생각한다. 보조 안전 함수가 errno를 바꿀 수 있으면 handler는 진입 errno를 저장하고 반환 전에 복원한다. 초기 errno=22에서 보조 호출 뒤 11이 되어도 복원 뒤 정상 흐름은 22를 본다. 이는 일반 자료구조나 다중 스레드 통신의 임의 안전성을 증명하는 방식이 아니다.

main이 flag를 1로 읽은 뒤 처리 준비를 하다가 새 handler가 1을 쓰고 main이 0으로 지우면 새 알림을 덮어쓸 수 있다. 수정 계획은 해당 신호를 차단한 채 flag를 지역 장부에 복사하고 0으로 지운 뒤 기존 마스크를 복원하는 것이다. 차단 중 실제 새 신호는 pending으로 남고 이후 handler가 다시 1을 쓸 수 있다. 다만 이 비트는 아직 살필 상태가 있다는 뜻이고 정확한 발생 수가 아니다.

self-pipe의 한 바이트 통지도 큐 용량과 오류 정책을 가진다. 별도 가상 nonblocking pipe에 읽을 토큰이 이미 하나 있고 write가 EAGAIN으로 실패했을 때 기존 토큰을 깨우기 용도로 유지할 수 있다. 이 설명은 실제 업무 상태가 pipe 밖에서 신뢰할 수 있게 유지되고 단일 소비자가 상태를 다시 조회한다는 조건이다. 실패한 write를 새 토큰 저장 성공이나 사건 수 보존으로 표시하지 않는다.

먼저 확인할 개념

  • 차단과 pending

    임계 구간의 전달 차단이 실제 발생을 삭제하지 않음을 사용한다.

중단된 함수의 내부 상태를 다시 만진다

printf 같은 buffered stdio는 내부 버퍼와 인덱스를 갱신한다. main이 그 갱신 중 중단됐는데 handler도 printf를 호출하면 아직 일관되지 않은 공유 상태에 다시 들어간다. 실행이 한 스레드라는 사실만으로 이 위험이 사라지지 않는다.

일반 함수 호출에서는 앞 호출이 끝난 뒤 다음 호출을 한다. 비동기 handler는 앞 호출이 끝나기 전에 끼어든다. thread-safe라는 설명이나 자신의 테스트 한 번이 async-signal-safe 조건을 대신하지 않으므로 공식 목록과 함수의 규약을 확인한다.

handler는 할 일을 표시하고 돌아온다

교육용 handler는 volatile sig_atomic_t flag에 1을 대입하고 main이 정상 문맥에서 flag를 읽어 로그를 남기게 한다. flag를 정확 사건 수를 기록하는 counter로 쓰지 않는다. flag++는 읽기/연산/쓰기가 합쳐져 단순 대입과 같지 않으며 사건 통지도 병합될 수 있다.

flag는 시그널 문맥의 작은 통신을 위한 것이며 여러 스레드 사이의 임의 자료구조 동기화 수단이 아니다. main에서 확인하고0으로 지우는 사이 새 handler가1을 쓰면 새 알림을 덮어쓸 수 있으므로 처리/재설정 절차의 마스크 규약도 필요하다.

안전 함수라도 결과와 차단 가능성을 확인한다

POSIX의 async-signal-safe 목록에는 write 등이 있지만 호출이 항상 성공하거나 즉시 반환한다는 보장은 아니다. 예를 들어 꽉 찬 blocking pipe에 write하면 지연될 수 있다. 작은 알림을 쓰는 설계에도 nonblocking과 실패 대응 등의 별도 규약이 필요하다.

handler가 errno를 변경할 수 있는 함수를 부르면 진입 때 errno를 저장하고 반환 전에 복원해 중단된 main의 오류 해석을 보존한다. 목록에 있는 함수를 쓰는 것 외에도 공유 상태와 오류값을 안전하게 다뤄야 한다.

중간 과정을 따라가는 예제

main의 errno=5, flag=0이다. handler는 old=errno 저장, flag=1, 안전 함수 호출 후 errno=11이 된 뒤 errno=old로 복원하고 반환한다. main은 정상 문맥에서 flag를 확인해 로그를 남긴다. 이어 마스크 없이 main이 flag 1 확인→handler flag 1→main flag 0으로 지우는 사건을 추적하라.

  1. handler 진입 저장old5, flag 1이 된다.

  2. 호출 후errno 11이어도 복원하면 main 복귀errno 5다.

  3. 두 번째 사건열에서는 새 handler가 쓴1을 main의0이 덮어쓴다.

  4. flag는 최종0이며 새 통지를 별도 처리할 기회를 잃을 수 있다.

errno 복원은5를 지키지만 flag 소비/재설정 경쟁은 별도 차단 절차가 필요하다.

조건을 바꾸어 비교하기

errno 보존과 알림 소실의 다른 계약

진입 errno가 22이고 handler 보조 호출 후 11이 된다. 저장/복원 유무 및 main read 1→새 handler write 1→main reset 0의 알림을 비교하라.

  1. 저장·복원이 있으면 복귀 errno는 22이고 없으면 호출 뒤 11이 남을 수 있다.

  2. flag는 주어진 순서에서 마지막 0이라 새 알림을 덮어썼다. errno 복원만으로 이 순서 오류는 해결되지 않는다.

오류값 보존과 flag 소비 경쟁은 별도의 교정 항목이다.

안전 함수 목록 하나로 모든 공유 상태를 자동 보호하지 않는다.

이미 든 토큰과 실패한 새 write

pipe에는 알림 토큰이 하나 있고 새 한 바이트 write가 EAGAIN이다. 외부의 실제 상태를 단일 소비자가 다시 조회하는 조건에서 무엇을 보존할 수 있는가?

  1. 새 write는 실패했으므로 pipe에 토큰을 추가했다고 세지 않는다.

  2. 기존 토큰이 남아 읽을 준비 상태를 유지하며 소비자가 실제 상태를 조회할 기회를 제공할 수 있다.

깨우기 존재와 정확 사건 수를 구별한다. 외부 상태 보존·소비/reset 규약을 빼면 이 결론을 일반화하지 않는다.

소단원 7.3

자식 종료·타이머 처리

SIGCHLD 한 번이면 자식도 한 명만 끝났을까?

준비 개념과 학습 목표

준비 개념

  • waitpid는 자식 상태를 회수하며 종료 자식의 자원을 정리한다.

  • WNOHANG은 즉시 회수할 대상이 없을 때 대기하지 않는 옵션이다.

학습 목표

  • SIGCHLD 통지와 자식 상태 회수를 분리한다.

  • 타이머 예약/취소와 실제 전달 지연을 구별한다.

이미 발생한 알람을 예약 취소로 지우면 통지도 사라질까?

새 종료 전용 관리 모형의 등록 자식은 801, 802, 803이고 SIGCHLD handler는 등록돼 있으며 SIG_IGN·SA_NOCLDWAIT·ptrace·정지 옵션·다중 회수자는 없다. SIGCHLD가 차단된 동안 802와 801이 종료하여 통지 종류 하나가 pending이다. 해제 뒤 통지 한 번으로 정상 문맥에서 waitpid(-1,...,WNOHANG)를 반복하여 가상 반환 802, 801, 0을 얻는다고 정한다. 두 종료는 회수했고 803은 아직 살아 있다.

0은 현재 준비된 종료 상태가 없다는 결과이고 ECHILD와 다르다. 나중에 803도 종료하고 가상 반환 803, −1/ECHILD를 얻으면 전체 세 명을 회수한 것이다. 반환 순서는 이 사례가 준 사건이며 PID 정렬 보장이 아니다. 종료 수를 통지 실행 수로 세지 않고 실제 대기 상태를 반복 조회한다.

별도 타이머 모형에서 t=0에 alarm(3), t=1에 alarm(5)을 성공 호출한다. 이상화한 정수 시계에서 새 due는 t=6이고 이전 t=3은 취소된다. ALRM을 t=0부터 차단하여 t=6에 실제 신호가 발생하고 pending으로 남았다고 사건을 정한다. t=7의 alarm(0)은 미래 예약을 취소하지만 이미 발생한 pending 신호를 마스크에서 해제하지도, pending 집합에서 삭제하지도 않는다. t=8에 해제하면 전달 가능하며 실제 handler 시작을 정확히 t=8이라고 보장하지 않는다.

먼저 확인할 개념
  • 자식 상태 조회와 타이머 교체

    0·ECHILD 및 예약 시간/발생/전달을 분리한다.

  • 마스크·pending의 전달 조건

    예약 취소와 이미 생긴 통지를 구별한다.

알림을 받으면 모든 준비 상태를 조회한다

여러 자식이 연달아 끝나도 standard SIGCHLD는 병합될 수 있다. handler 실행 한 번에 waitpid 한 번만 호출하면 다른 종료 자식이 회수되지 않을 수 있다. 통지 횟수를 자식 종료 수로 생각하지 않고 회수 가능한 상태를 반복 조회한다.

waitpid(-1,...,WNOHANG)는 회수 대상 자식 PID, 아직 회수할 상태가 없으면0, 오류면−1을 반환한다. 종료 자식만 다루는 기본 옵션 모형에서 양수일 때 계속 회수하고0 또는 ECHILD면 멈춘다. EINTR 등 다른 오류는 따로 처리해야 한다.

등록과 기다림의 경계에서 사건을 놓치지 않는다

자식 관리표에 PID를 넣기 전에 자식이 종료하면 handler가 먼저 실행될 수 있다. 단일 스레드 설계에서 fork/관리표 등록 구간의 SIGCHLD를 차단하고 등록 후 해제하는 방식으로 순서를 보호할 수 있다. child가 상속한 마스크의 처리는 별도 확인한다.

main이 flag 0을 확인한 다음 pause를 호출하기 직전에 신호가 처리되면 이미 처리된 사건을 기다리며 잠들 수 있다. 검사 동안 차단하고 sigsuspend로 임시 마스크 교체와 기다림을 묶는 원리를 사용한다. 정확 구현과 오류처리를 하지 않은 종이 설명을 실제 안정 서비스로 주장하지 않는다.

예약 시간과 실행 시간을 구별한다

alarm(seconds)는 호출 프로세스에 SIGALRM을 예약하며 새 예약은 이전 예약을 취소한다. alarm(0)은 예약을 취소한다. 한 프로세스에 독립 타이머를 계속 추가하는 큐처럼 해석하면 안 된다.

정해진 시간이 지나도 차단 또는 스케줄링 상황에 따라 handler 실행은 늦을 수 있다. 일반 SIGALRM을 정확 주기 사건 횟수로 쓰지 않는다. 학습 모형에서는 예약 시각을 먼저 구하고 실제 전달 가능 시각/실행 시각을 별도 열로 둔다.

중간 과정을 따라가는 예제

단일 스레드이고 SIGCHLD handler가 있으며 명시 SIG_IGN/SA_NOCLDWAIT는 없다. 종료 자식101/102/103이 회수 대기 중이다. 한 통지 뒤 waitpid(-1,&status,WNOHANG)의 가상 반환이102,101,103,−1(ECHILD)라고 주어진다. 회수 수를 구하라. 별도로 정수시간 t0에서 alarm(5),t2에서 alarm(4),t3에서 alarm(0)을 호출하고 지연0의 예약표를 계산하라.

  1. 양수102/101/103을 각각 회수하므로3자식이다. 반환 순서는 가정이며 PID 정렬 보장이 아니다.

  2. −1/ECHILD는 현재 자식이 없다는 종료 조건이다.

  3. t0의 예약 5는t2에 취소되고 새 예약은6이다. t2 호출의 남은 초 반환은3이다.

  4. t3의0취소로6예약도 없어지며 반환 남은 초는3이다.

통지는1이어도3명 회수한다. 이 교육 예약표에서는 타이머가 모두 취소되어 ALRM이 예약상 발생하지 않는다.

단일 스레드의 M={USR1,ALRM}, pending={USR1}에서 USR1을 해제해 handler에 진입한다. sa_mask={USR2}, NODEFER 없음이며 handler 중 USR1 두 번/USR2 한 번이 발생한다. 처리 중과 반환 뒤 두 집합 및 별도 초기 상태 fork 뒤 자식 pending을 보고하라. flag 소비의 무차단 read 1→새 handler write 1→reset 0과 차단 복사/reset 계획을 비교하고 진입 errno 22/보조 호출 뒤 11의 복원을 설명하라. 등록 자식의 wait 반환 802,801,0과 이후 803,ECHILD에서 누적 회수 수를 구하라. 마지막으로 t=0 alarm(3), t=1 alarm(5), ALRM 차단 중 t=6 발생, t=7 alarm(0), t=8 해제의 미래 예약/pending을 보고하고 발생 전 t=4 취소 대안을 비교하라.

힌트 1

mask와 pending은 다른 집합이고 fork는 pending을 복사하지 않는다. flag 비트는 사건의 수가 아니라 조회할 상태의 존재다.

힌트 2

양수 wait 반환과 0/ECHILD를 구별하고 타이머 due와 이미 발생한 pending을 서로 다른 열에 적는다.

풀이와 답 확인

  1. 처리 중 M={ALRM,USR1,USR2}, 새 pending={USR1,USR2}다. 정상 반환 뒤 M={ALRM}이며 두 종류는 전달 가능하되 순서는 미지정이다. 초기 부모 상태에서 새 자식 pending은 ∅다.

  2. 무차단 소비는 새 1을 0으로 덮는다. 차단 중 복사/reset 뒤 마스크 복원은 새 pending 전달에 의한 다음 flag를 보존할 수 있지만 정확 발생 수는 복원하지 않는다. errno 저장/복원은 22를 지킨다.

  3. 첫 반복은 두 자식을 회수하고 0은 현재 종료 상태 없음이다. 이후 803 회수로 누적 세 명이며 주어진 조건의 ECHILD에서 끝낸다.

  4. 새 due는 6이고 t=6에 발생한 ALRM pending은 t=7 취소로 사라지지 않는다. t=8 뒤 전달 가능하다. 별도 t=4 취소는 due 6의 발생 전이며 이상화한 반환 남은 시간 2, 다른 발생 없는 조건에서 pending도 없다.

생성·pending·전달·flag 소비·회수·예약을 별도 장부에 기록한다. 모든 결과는 명시한 단일 스레드·성공/반환·이상화한 정수 시간의 자체 종이 모형이며 실제 신호/pipe/process/타이머/학생 실험은 미수행이다.

해결한 뒤 점검할 것

  • handler 임시 합집합/복원 및 부모·자식 pending 차이를 설명한다.

  • flag 소비 순서와 errno 보존을 별도 검토하고 사건 수를 가짜 복원하지 않는다.

  • wait의 양수/0/ECHILD 및 해당 종료 상태만 회수 장부에 반영한다.

  • 발생 전 취소와 발생 후 pending을 구별하고 실제 전달 시각을 측정처럼 주장하지 않는다.
