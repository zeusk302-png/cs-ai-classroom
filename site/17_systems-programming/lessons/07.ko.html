소단원 7.1

sigaction과 마스크

시그널이 발생한 순간과 처리 함수가 실행된 순간이 꼭 같을까?

준비 개념과 학습 목표

준비 개념

  • signal은 특정 사건을 알리는 OS 통지이며 처리 정책을 disposition이라 한다.
  • mask는 해당 스레드에서 현재 전달을 막는 신호 집합이다.

학습 목표

  • 발생·pending·전달을 구별한다.
  • 처리 중 마스크 변화와 복원을 추적한다.

정책과 전달 시점을 분리한다

sigaction은 특정 시그널을 기본 동작으로 처리할지, 무시할지, 사용자 handler로 받을지 설정한다. 정책을 등록하는 것과 시그널을 발생시키는 것은 다른 행위다. SIGKILL과 SIGSTOP은 사용자 handler로 잡거나 무시할 수 없다.

시그널이 발생했지만 마스크에 차단되어 있으면 전달될 때까지 pending으로 남을 수 있다. 차단은 삭제와 다르다. 프로그램의 정상 제어 흐름이 잠시 handler로 들어갔다가 복귀하는 비동기 사건을 생각하되, 모든 코드 지점에서 즉시 처리된다고 가정하지 않는다.

handler의 마스크는 임시로 늘어난다

특별한 SA_NODEFER가 없으면 처리 중인 시그널 자체가 handler 실행 동안 추가 차단된다. sa_mask에 지정한 시그널도 함께 차단된다. handler가 정상 반환하면 이전 마스크가 복원된다.

Linux의 disposition은 프로세스 수준이지만 마스크는 스레드별이다. process-directed signal은 차단하지 않은 스레드 중 하나에 전달될 수 있으므로 단일 스레드의 표를 다중 스레드 전체 정책처럼 확대하지 않는다. 이 단원 예제는 한 스레드만 가정한다.

일반 시그널을 횟수 기록으로 쓰지 않는다

같은 standard signal이 차단된 동안 여러 번 발생해도 pending은 같은 종류 하나로 병합될 수 있다. 따라서 handler 실행 횟수가 사건 발생 횟수와 같다고 보장되지 않는다. 서로 다른 종류의 pending 전달 순서도 임의로 정해 외우지 않는다.

real-time signal은 별도의 큐 규약을 가지지만 무한 큐라는 뜻은 아니다. 일반적인 제어 통지에는 알림을 보고 실제 상태를 조회하는 설계가 유용하다. 마스크 해제 후 처리할 일이 있다는 상태와 몇 개 발생했는지를 구별한다.

중간 과정을 따라가는 예제

단일 스레드에서 마스크는 {USR1}이고 USR1 handler의 sa_mask={USR2}, SA_NODEFER는 없다. 차단 중 USR1 세 번 발생한 뒤 마스크를 빈 집합으로 바꾸어 handler에 진입한다. 그 handler 중 USR2 한 번과 USR1 한 번이 발생한다. 각 시점의 차단 집합과 pending 종류를 구하라. 기본 종료 대신 두 신호 모두 handler가 등록됐다고 가정한다.

  1. 처음 USR1 세 번은 pending 종류{USR1}로 병합된다.
  2. 첫 USR1 전달 시 그 pending을 제거하고 handler 중 마스크{USR1,USR2}가 된다.
  3. handler 중 두 발생 뒤 pending{USR1,USR2}다.
  4. 정상 반환하면 빈 마스크가 복원되어 두 pending이 전달 가능하지만 두 종류의 순서는 지정하지 않는다.

첫 handler 동안 두 종류 모두 대기하고 반환 뒤 전달 가능하다. 처음3번이3회 handler를 보장하지 않는다.

한 단계 더

소단원 7.2

시그널 안전 함수

handler에서 printf 한 줄만 써도 왜 위험할까?

준비 개념과 학습 목표

준비 개념

  • async-signal-safe는 비동기 handler에서 호출이 안전하도록 규약이 정해진 함수다.
  • 전역 flag에는 단순 대입 가능한 volatile sig_atomic_t를 사용하는 작은 설계를 생각한다.

학습 목표

  • 재진입 중 공유 상태 위험을 설명한다.
  • 짧은 handler와 정상 흐름의 후속 처리로 역할을 나눈다.

중단된 함수의 내부 상태를 다시 만진다

printf 같은 buffered stdio는 내부 버퍼와 인덱스를 갱신한다. main이 그 갱신 중 중단됐는데 handler도 printf를 호출하면 아직 일관되지 않은 공유 상태에 다시 들어간다. 실행이 한 스레드라는 사실만으로 이 위험이 사라지지 않는다.

일반 함수 호출에서는 앞 호출이 끝난 뒤 다음 호출을 한다. 비동기 handler는 앞 호출이 끝나기 전에 끼어든다. thread-safe라는 설명이나 자신의 테스트 한 번이 async-signal-safe 조건을 대신하지 않으므로 공식 목록과 함수의 규약을 확인한다.

handler는 할 일을 표시하고 돌아온다

교육용 handler는 volatile sig_atomic_t flag에 1을 대입하고 main이 정상 문맥에서 flag를 읽어 로그를 남기게 한다. flag를 정확 사건 수를 기록하는 counter로 쓰지 않는다. flag++는 읽기/연산/쓰기가 합쳐져 단순 대입과 같지 않으며 사건 통지도 병합될 수 있다.

flag는 시그널 문맥의 작은 통신을 위한 것이며 여러 스레드 사이의 임의 자료구조 동기화 수단이 아니다. main에서 확인하고0으로 지우는 사이 새 handler가1을 쓰면 새 알림을 덮어쓸 수 있으므로 처리/재설정 절차의 마스크 규약도 필요하다.

안전 함수라도 결과와 차단 가능성을 확인한다

POSIX의 async-signal-safe 목록에는 write 등이 있지만 호출이 항상 성공하거나 즉시 반환한다는 보장은 아니다. 예를 들어 꽉 찬 blocking pipe에 write하면 지연될 수 있다. 작은 알림을 쓰는 설계에도 nonblocking과 실패 대응 등의 별도 규약이 필요하다.

handler가 errno를 변경할 수 있는 함수를 부르면 진입 때 errno를 저장하고 반환 전에 복원해 중단된 main의 오류 해석을 보존한다. 목록에 있는 함수를 쓰는 것 외에도 공유 상태와 오류값을 안전하게 다뤄야 한다.

중간 과정을 따라가는 예제

main의 errno=5, flag=0이다. handler는 old=errno 저장, flag=1, 안전 함수 호출 후 errno=11이 된 뒤 errno=old로 복원하고 반환한다. main은 정상 문맥에서 flag를 확인해 로그를 남긴다. 이어 마스크 없이 main이 flag 1 확인→handler flag 1→main flag 0으로 지우는 사건을 추적하라.

  1. handler 진입 저장old5, flag 1이 된다.
  2. 호출 후errno 11이어도 복원하면 main 복귀errno 5다.
  3. 두 번째 사건열에서는 새 handler가 쓴1을 main의0이 덮어쓴다.
  4. flag는 최종0이며 새 통지를 별도 처리할 기회를 잃을 수 있다.

errno 복원은5를 지키지만 flag 소비/재설정 경쟁은 별도 차단 절차가 필요하다.

오해와 반례

안전 함수는 실패도 차단도 없고 flag++도 원자적인 사건 계수다.

async-signal-safe는 재진입 규약이며 write의 실패/차단 가능성은 따로 있다. flag++는 여러 동작이고 일반 시그널도 병합되므로 발생 횟수와 같은 값을 보장하지 않는다.

소단원 7.3

자식 종료·타이머 처리

SIGCHLD 한 번이면 자식도 한 명만 끝났을까?

준비 개념과 학습 목표

준비 개념

  • waitpid는 자식 상태를 회수하며 종료 자식의 자원을 정리한다.
  • WNOHANG은 즉시 회수할 대상이 없을 때 대기하지 않는 옵션이다.

학습 목표

  • SIGCHLD 통지와 자식 상태 회수를 분리한다.
  • 타이머 예약/취소와 실제 전달 지연을 구별한다.

알림을 받으면 모든 준비 상태를 조회한다

여러 자식이 연달아 끝나도 standard SIGCHLD는 병합될 수 있다. handler 실행 한 번에 waitpid 한 번만 호출하면 다른 종료 자식이 회수되지 않을 수 있다. 통지 횟수를 자식 종료 수로 생각하지 않고 회수 가능한 상태를 반복 조회한다.

waitpid(-1,...,WNOHANG)는 회수 대상 자식 PID, 아직 회수할 상태가 없으면0, 오류면−1을 반환한다. 종료 자식만 다루는 기본 옵션 모형에서 양수일 때 계속 회수하고0 또는 ECHILD면 멈춘다. EINTR 등 다른 오류는 따로 처리해야 한다.

등록과 기다림의 경계에서 사건을 놓치지 않는다

자식 관리표에 PID를 넣기 전에 자식이 종료하면 handler가 먼저 실행될 수 있다. 단일 스레드 설계에서 fork/관리표 등록 구간의 SIGCHLD를 차단하고 등록 후 해제하는 방식으로 순서를 보호할 수 있다. child가 상속한 마스크의 처리는 별도 확인한다.

main이 flag 0을 확인한 다음 pause를 호출하기 직전에 신호가 처리되면 이미 처리된 사건을 기다리며 잠들 수 있다. 검사 동안 차단하고 sigsuspend로 임시 마스크 교체와 기다림을 묶는 원리를 사용한다. 정확 구현과 오류처리를 하지 않은 종이 설명을 실제 안정 서비스로 주장하지 않는다.

예약 시간과 실행 시간을 구별한다

alarm(seconds)는 호출 프로세스에 SIGALRM을 예약하며 새 예약은 이전 예약을 취소한다. alarm(0)은 예약을 취소한다. 한 프로세스에 독립 타이머를 계속 추가하는 큐처럼 해석하면 안 된다.

정해진 시간이 지나도 차단 또는 스케줄링 상황에 따라 handler 실행은 늦을 수 있다. 일반 SIGALRM을 정확 주기 사건 횟수로 쓰지 않는다. 학습 모형에서는 예약 시각을 먼저 구하고 실제 전달 가능 시각/실행 시각을 별도 열로 둔다.

중간 과정을 따라가는 예제

단일 스레드이고 SIGCHLD handler가 있으며 명시 SIG_IGN/SA_NOCLDWAIT는 없다. 종료 자식101/102/103이 회수 대기 중이다. 한 통지 뒤 waitpid(-1,&status,WNOHANG)의 가상 반환이102,101,103,−1(ECHILD)라고 주어진다. 회수 수를 구하라. 별도로 정수시간 t0에서 alarm(5),t2에서 alarm(4),t3에서 alarm(0)을 호출하고 지연0의 예약표를 계산하라.

  1. 양수102/101/103을 각각 회수하므로3자식이다. 반환 순서는 가정이며 PID 정렬 보장이 아니다.
  2. −1/ECHILD는 현재 자식이 없다는 종료 조건이다.
  3. t0의 예약 5는t2에 취소되고 새 예약은6이다. t2 호출의 남은 초 반환은3이다.
  4. t3의0취소로6예약도 없어지며 반환 남은 초는3이다.

통지는1이어도3명 회수한다. 이 교육 예약표에서는 타이머가 모두 취소되어 ALRM이 예약상 발생하지 않는다.

종이와 본문으로 직접 해보기

waitpid 반환이101,0이면 무엇을 알 수 있나? 다른 자식102가 살아 있다고 가정한다. 이어 t0 alarm2, ALRM 차단이 t0..5이면 t2에 handler가 실행되나?

힌트 보기

0은 ECHILD와 다르고 발생/전달도 다르다.

풀이 보기

101은 회수됐고0은 지금 회수할 변화가 없다는 뜻이며102가 아직 살아 있을 수 있다. ALRM은t2 발생해pending으로 남을 수 있고t5 해제 뒤 전달 가능하다. 정확 handler 시작 시각을t5로 보장하지 않는다.

오해와 반례

SIGCHLD 횟수로 종료 수를 세고 alarm을 여러 번 불러 타이머 여러 개를 만든다.

첫 예제는 통지 1과 회수 3이 다르다. 새 alarm은 이전 예약을 교체하므로t5와t6 두 타이머가 함께 남지 않는다. 통지와 실제 상태·예약 교체 규약을 분리한다.

한 단계 더

비차단 waitpid 반복을 handler에서 직접 하면 안전 목록과 errno 복원을 지켜야 한다. 더 복잡한 자료구조/로그는 정상 문맥으로 넘긴다. 시스템이 한 통지를 합쳐도 실제 종료 상태를 조회해 모두 회수하는 설계의 장점을 상태 그림으로 설명한다.
