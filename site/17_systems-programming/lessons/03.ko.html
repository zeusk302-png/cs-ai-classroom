소단원 3.1

open·read·write·close

파일 이름 대신 작은 정수를 전달해도 어떻게 같은 파일을 찾아갈까?

준비 개념과 학습 목표

준비 개념

  • 바이트는 이 단원에서 8 비트 자료 단위다. 문자 수와 바이트 수는 다를 수 있다. 예제 A,B,C는 각각 1 바이트인 ASCII로 고정한다.

  • 프로세스는 실행 중인 프로그램과 그 자원이다. 디스크립터 표는 각 프로세스가 가진 열린 대상의 번호표라고 생각하되 파일 자체의 이름표와 구분한다.

  • 배열의 유효 범위는 0 부터 길이-1 이다. read가 3 을 반환했다면 새 자료는 buf[0..2]에 있고 그 뒤를 새 자료로 읽지 않는다.

학습 목표

  • 열기·읽기·쓰기·닫기의 역할과 반환값을 구분한다.

  • 파일 위치의 이동을 실제 처리 바이트 수로 추적한다.

  • 실패와 자원 소유권을 고려해 닫기 계획을 세운다.

별도 번호를 얻으면 읽기 위치도 자동으로 독립일까?

새 ASCII 파일은 ABCDEFGH이고 fd a의 열린 파일 설명 D는 위치 0이다. dup(a)의 결과 b는 다른 번호지만 같은 D를 참조한다. a에서 2바이트를 성공 읽으면 AB이며 D의 위치는 2다. b에서 1바이트를 읽으면 C이며 위치는 3이다. 같은 경로를 별도 open한 c는 다른 설명 E의 위치 0에서 시작하여 A를 읽는다. 번호·설명·파일 내용의 세 층을 따로 그려야 한다.

위치 이동 가능한 같은 파일에 pread(a,2,offset=5)를 성공하여 2바이트 읽는다고 정하면 FG를 얻지만 D의 현재 위치 3은 바뀌지 않는다. 다음 보통 read(b,1)는 D 위치 3의 D 문자를 얻고 현재 위치는 4가 된다. 명시 위치 읽기는 현재 위치의 공유를 피하지만 파일 내용의 스냅샷이나 다른 쓰기의 부재까지 보장하지 않는다.

아래는 다른 호출이 끼어들지 않는 지정 파일·반환의 순차 모형이다. pread 대상은 seeking이 가능하고 양수 count이며 파일 내용도 이 사건열 동안 고정한다. 파이프에 같은 위치 접근을 옮기거나 같은 경로를 항상 같은 파일 정체성으로 취급하지 않는다. 실제 open/dup/pread/read는 실행하지 않았다.

먼저 확인할 개념
  • 번호와 열린 파일 설명

    독립 open과 dup의 위치 공유를 구별한다.

  • 요청량과 실제 반환량

    각 위치 변화는 실제 성공량만 반영한다.

번호표가 가리키는 대상

Linux/POSIX 계열에서 open은 경로와 접근 모드로 대상을 열고 성공하면 음이 아닌 정수 fd를 돌려준다. fd는 현재 프로세스의 표에서 항목을 찾는 번호다. 실패는 -1 이고 errno에 원인 정보가 있다. 0 도 성공 번호일 수 있으므로 if(fd<=0) 같은 검사는 잘못이다. 표준 입력·출력·오류에 흔히 0·1·2 를 사용하지만 이 번호가 항상 열린 채로 있다는 가정은 별도로 필요하다.

표 항목은 열린 파일 설명(open file description)을 참조하며 여기에는 현재 파일 위치와 상태 플래그가 있다. 파일 위치 offset은 다음 바이트를 읽거나 쓸 위치다. 같은 경로를 두 번 독립 open하면 별개의 위치 상태를 얻을 수 있다. 반대로 dup이나 fork로 같은 열린 파일 설명을 공유하면 위치도 공유할 수 있다. 이 단원 예제는 공유 없이 한 프로세스가 순차 호출한다. 번호표 비유는 위치가 어디에 저장되는지까지 설명하지 못한다.

접근 권한과 위치의 변화

O_RDONLY, O_WRONLY, O_RDWR은 읽기·쓰기 가능 방향을 정한다. O_CREAT는 없을 때 만들기를 요청하고 새 파일의 권한 인수 mode를 함께 제공해야 한다. O_TRUNC는 쓰기가 허용된 일반 파일의 길이를 0 으로 줄일 수 있어 단순 열기와 다르다. 이름이 같다고 원래 내용이 보존되는 것은 아니다. 이 자료에서는 실제 파일을 바꾸는 호출을 실행하지 않고 종이 위 가정을 명시한다.

위치 이동 가능한 일반 파일에서 read(fd,buf,k)는 최대 k바이트를 가져오며 양수 r을 반환하면 위치가 r만큼 증가한다. write(fd,buf,k)도 실제 쓴 양수 w만큼 증가한다. 둘 다 k를 전부 처리한다고 보장하지 않는다. O_APPEND의 쓰기는 끝으로 위치를 조정한 뒤 쓰지만 이를 모든 저장장치·네트워크 파일시스템에 대한 일반 동시성 보장으로 확대하지 않는다. 읽기·쓰기는 자료와 반환값을 함께 해석하는 작업이다.

닫기는 내용 삭제가 아니다

close(fd)가 성공하면 해당 프로세스의 번호는 더 이상 그 참조를 갖지 않으며 다른 open에 재사용될 수 있다. 따라서 닫은 번호 3 에 다시 write하면 원래 파일이 아니라 우연히 새로 열린 다른 파일을 건드릴 수도 있다. 자원 소유권은 누가 언제 한 번 닫는가를 정하는 규칙이다. 복사한 정수 변수 둘이 있다고 두 번 닫아야 하는 것이 아니다. 다른 참조가 있다면 그 참조는 별도로 남을 수 있다.

close의 성공은 자료가 물리 디스크에 영구 저장되었다는 보장이 아니다. 반환값 오류도 확인해야 하며 Linux에서는 실패 뒤 번호가 이미 반환되었을 수 있어 read처럼 무조건 재시도하면 새 참조를 닫는 위험이 있다. 이 주의는 Linux 맥락으로 한정하고 모든 OS의 close/EINTR 동작이 같다고 말하지 않는다. 내구성 요구는 쓰기·동기화·닫기와 저장 환경을 함께 설계하는 다음 단계다.

중간 과정을 따라가는 예제

단일 프로세스에서 일반 파일 내용은 ABCDEF이고 열린 번호는 0,1,2 뿐이다. 새로 O_RDWR로 열며 추가 플래그는 없다. 모든 호출은 오류 없이 성공한다. 이 종이 모형에서 write는 요청한 2 바이트를 처리하고 read는 요청량과 현재 위치 이후 남은 파일 길이 중 작은 만큼 읽는다고 가정한다. read 2, write XY 2, read 3, close 순서를 추적하라.

  1. 가장 작은 빈 번호 3 을 얻고 별개 열린 파일 설명의 초기 offset은 0 이다.

  2. read 2 는 AB를 반환하며 offset=2 다. 파일 내용은 아직 ABCDEF다.

  3. write XY 2 는 위치 2,3 의 C,D를 바꿔 ABXYEF가 되고 offset=4 다.

  4. read 3 요청은 끝까지 남은 EF 2 바이트만 반환하며 offset=6 이다. close 성공 뒤 fd 3 의 참조는 사라진다.

읽은 자료는 먼저 AB, 나중 EF다. 최종 파일은 ABXYEF이며 마지막 read는 요청 3 보다 작은 2 여도 성공이다.

조건을 바꾸어 비교하기

공유 위치에 직접 위치를 더하지 않기

표의 pread 뒤 D 위치가 7이라고 기록했다. 올바른 위치와 다음 보통 read 결과를 구하라.

  1. pread는 명시 위치 5에서 두 바이트 FG를 읽는다.

  2. 현재 위치는 3으로 유지되어 다음 read는 D 문자를 읽는다.

다음 성공 뒤 현재 위치는 4다. 5+2=7은 pread에서 읽은 범위의 끝이지 현재 위치 갱신값이 아니다.

비교할 점

명시 범위 끝과 공유 커서의 상태를 각각 이름 붙인다.

두 순차 read의 순서 바꾸기

같은 초기 위치 0에서 b가 1바이트를 읽은 뒤 a가 2바이트를 읽도록 순서를 바꾸어라.

  1. b는 문자 A를 읽고 공유 위치가 1이 된다.

  2. a는 자료 BC를 읽고 공유 위치가 3이 된다.

전체 연결 ABC는 같지만 호출별 자료는 A/BC로 바뀐다. 기존 AB/C와 호출별 결과를 같다고 하지 않는다.

비교할 점

총량이 같아도 각 작업자가 받은 자료 계약은 다를 수 있다.

종이와 본문으로 직접 해보기

종이 파일 KLMNO를 쓰기 없는 읽기 모드로 열었다. read 3 은 KLM, 다음 read 3 은 NO, 다음 read 3 은 0 을 반환한다고 주어졌다. 각 위치와 마지막 반환값 의미를 적어라. 또 fd=0 성공을 오류로 분류하는 조건식을 찾아 고쳐라.

힌트 보기

실제로 처리한 양만 더하고 성공 여부는 음수인가로 확인한다.

풀이 보기

위치는 0→3→5→5 다. count=3 의 마지막 0 은 이 일반 파일에서 EOF다. fd<=0 대신 fd<0 으로 오류를 검사하면 성공 번호 0 을 포함한다. read 위치는 요청량 3+3+3=9 로 계산하지 않는다.

오해와 반례

fd 정수는 파일의 영구 고유 번호라 닫은 뒤에도 같은 파일을 뜻한다.

fd는 프로세스 표의 재사용 가능한 번호다. 3 을 닫고 다른 파일을 열어 3 을 얻으면 새 대상이다. 경로, fd, 열린 파일 설명, 파일 내용은 서로 다른 층이다. 두 프로세스의 fd 3 도 서로 다른 파일을 가리킬 수 있다.

연습 3 · 직접 만들어 보기

두 작업자가 항상 offset 0부터 1까지와 offset 5부터 6까지를 각각 읽어야 한다. 공유 커서에 의존하지 않는 위치 요청을 구성하라.

힌트 1

목표 범위를 명시 offset으로 표현한다.

힌트 2

반환이 짧으면 해당 범위의 남은 부분만 처리한다.

풀이와 답 확인

  1. 첫 요청은 pread의 count를 2, offset을 0으로 지정한다. 둘째 요청은 count를 2, offset을 5로 지정한다.

이 방식은 현재 커서 변화와 분리되지만 동시 파일 수정·부분 실패·전체 범위의 원자성은 별도다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

소단원 3.2

부분 읽기·쓰기와 EOF

다섯 바이트를 보냈는데 한 번에 두 바이트만 처리되었다면 나머지는 어떻게 지킬까?

준비 개념과 학습 목표

준비 개념

  • 부호 있는 ssize_t는 양수 처리량, 0, -1 오류를 표현한다. 양수라는 것을 검사한 뒤에만 배열 위치나 size_t 누적값에 더한다.

  • EOF는 파일 끝 상태를 관찰한 반환 결과이지 모든 파일 뒤에 저장된 특별한 바이트가 아니다. 여기서는 read count가 양수일 때를 기본으로 한다.

  • done은 이미 처리된 양, remaining=N-done은 남은 양이다. 불변식 0<=done<=N을 유지하면 남은 부분을 정확히 고를 수 있다.

학습 목표

  • 짧은 성공·EOF·오류·일시적 준비 부족을 구분한다.

  • 반환량에 따라 버퍼 시작점과 남은 길이를 갱신한다.

  • 오류의 재시도 조건과 진행 없는 반복을 설명한다.

읽을 자료가 없다는 관찰은 누가 닫았는지까지 알려 줄까?

새 가상 파이프에는 쓰기 끝 fd 참조 W1과 W2가 있고 읽기 끝 R이 있다. 내용 XYZ 3바이트를 이미 넣었다고 정한다. W1만 닫고 W2를 남겨도 쓰기 끝 참조가 아직 있으므로 자료를 모두 읽은 뒤 빈 파이프의 양수 비차단 read는 지금 자료가 없음을 EAGAIN으로 알릴 수 있다. W1이 담당한 생산자가 종료했다는 사실만으로 전체 EOF를 선언하지 않는다.

이후 W2도 닫히고 버퍼가 비면 양수 count인 read의 반환값 0을 EOF로 읽는다. 닫기 전 남은 자료가 있으면 먼저 그 자료가 양수 길이로 반환될 수 있다. 따라서 판단 상태에는 미소진 바이트 수와 살아 있는 쓰기 참조 수가 모두 필요하다. 빈 상태와 생산 종료를 서로 다른 칸으로 기록한다.

파이프는 바이트 스트림으로 write의 메시지 경계를 보존하지 않는다. write 두 번으로 A와 BC를 넣어도 read가 AB 다음 C로 나누어 반환하는 경로는 가능하다. 아래 사건열의 반환 조각은 미리 지정한 허용 모형이지 실제 스케줄·파이프 용량·원자성 시험이 아니다. count가 0인 read의 반환값 0도 EOF 증거로 사용하지 않는다.

먼저 확인할 개념
  • 부분 읽기와 EOF의 참조 조건

    양수 count·버퍼 소진·쓰기 끝 참조를 함께 검사한다.

  • close와 다른 참조

    한 번호를 닫는 일이 다른 번호의 참조까지 자동 없애지는 않는다.

한 번의 호출과 하나의 요청은 다르다

read 또는 write가 양수로 k보다 적게 반환한 것은 부분 성공일 수 있다. 읽기는 지금 제공된 양이 적거나 끝에 가까울 수 있고 쓰기는 일부만 받아들여졌을 수 있다. 성공한 앞부분을 버리고 처음부터 다시 쓰면 자료를 중복시킬 수 있다. 호출 횟수와 논리적 메시지 수는 같지 않다. 스트림에서 두 write가 두 read로 그대로 경계를 보존한다는 보장도 없으므로 메시지 구분은 별도 형식이 필요하다.

read의 count>0 에서 0 은 EOF를 뜻한다. 일반 파일은 현재 위치에서 더 읽을 내용이 없음을 뜻하며 이후 다른 쓰기로 파일이 커질 수도 있다. 파이프는 쓰기 끝 참조가 모두 닫히고 버퍼 자료도 소진될 때 0 이 관찰된다. 하지만 read count=0 의 0 은 보통 무작업 결과여서 EOF 증거가 아니다. 비차단 read의 EAGAIN은 지금 읽으면 기다려야 함을 뜻하며 끝남과 다르다.

남은 부분만 다시 전달하기

N바이트 쓰기 완료를 목표로 하면 done=0 에서 시작한다. write(fd,buf+done,N-done)의 양수 r을 얻을 때 done+=r이다. done=N이면 끝나고 오류면 원인별로 대응한다. 버퍼 포인터를 움직이지 않고 길이만 줄이면 이미 쓴 앞부분을 다시 전송한다. 이 규칙은 유효한 버퍼, N이 허용 범위 안, 다른 호출이 순서를 섞지 않는다는 가정을 둔 순차 처리 논리다.

read도 목표 길이가 알려져 있을 때 같은 방식으로 누적할 수 있지만 N 이전에 EOF면 짧은 입력이라는 결과를 호출자에게 돌려야 한다. 예를 들어 4 바이트 헤더 중 2 바이트만 받고 EOF라면 완전한 헤더로 해석할 수 없다. 목표 길이가 없는 전체 파일 복사에서는 read의 양수 구간마다 실제 r바이트만 write 반복으로 넘기고 read가 0 이면 정상 입력 종료로 분류한다. 버퍼 전체 용량을 쓰면 오래된 뒤쪽 자료를 유출하거나 덧붙일 수 있다.

다시 시도와 기다림의 구분

read/write가 -1 이고 errno=EINTR이면 해당 호출은 자료를 처리하기 전에 신호로 중단된 경우이므로 같은 남은 구간을 다시 시도하는 기본 대응을 고려한다. 일부가 이미 처리되어 양수를 받았다면 그 반환량부터 반영한다. -1 을 unsigned로 먼저 바꾸면 거대한 양수처럼 보일 수 있다. 모든 오류를 재시도하지 않는다. 권한·잘못된 fd·용량 부족은 상황과 정책을 수정하지 않으면 같은 실패가 반복될 수 있다.

EAGAIN/EWOULDBLOCK에는 준비 알림을 기다리거나 상위 작업을 보류하는 처리가 필요하며 무한한 즉시 재시도는 CPU를 낭비한다. 양의 쓰기 길이 요청이 0 을 돌려준 사건을 방어적으로 만나면 done이 늘지 않으므로 완료로 보거나 끝없이 반복하지 말고 진행 없음 정책으로 종료·보고한다. 파이프 읽는 쪽이 없으면 SIGPIPE도 관련되어 write의 -1 만 검사해도 모든 상황을 포착한다고 말할 수 없다. 아래 사건열은 신호 처리와 실제 장치 동작을 구현한 코드가 아니다.

중간 과정을 따라가는 예제

buf는 HELLO 5 바이트다. blocking 출력에 남은 부분을 요청하며 반환 사건은 2, -1/EINTR, 1, 2 다. 성공한 수만큼 정확히 쓰였다고 가정하고 각 요청 구간·done·최종 출력의 연결을 추적하라.

  1. 처음 done=0, HELLO 길이 5 요청에 2 가 반환되어 HE가 처리되고 done=2 다.

  2. 다음 LLO 길이 3 요청이 EINTR로 실패한다. 이 호출의 처리량은 없으므로 done=2 를 유지한다.

  3. LLO 길이 3 을 다시 요청하여 1 을 받고 L이 처리되어 done=3 이다.

  4. LO 길이 2 요청에서 2 가 반환되면 done=5 다. 출력 연결은 HE+L+LO=HELLO이며 누적 양수 2+1+2=5 다.

네 번 호출했지만 완성 자료는 HELLO 한 번이다. EINTR는 처리량에 포함하지 않고 성공마다 시작점과 길이를 함께 바꾼다.

두 write를 한 read 계약으로 묶기

A와 BC를 두 write로 넣고 read 반환을 AB와 C로 정했다. 메시지 수와 read 횟수가 같다는 결론을 감사하라.

  1. 연결 자료는 A+BC=ABC다.

  2. read 연결도 AB+C=ABC지만 경계는 다르다.

바이트 순서는 보존해도 write별 경계는 read별 경계와 일치하지 않는다. 메시지는 길이/구분자 등의 별도 형식이 필요하다.

소단원 3.3

버퍼드 I/O와 비버퍼드 I/O

문자를 열 번 출력했는데 실제 운영체제 호출은 한 번일 수도 있을까?

준비 개념과 학습 목표

준비 개념

  • 사용자 공간은 프로그램과 라이브러리의 메모리, 커널 공간은 운영체제의 자원 관리 영역이다. 둘의 버퍼는 서로 다른 층이다.

  • FILE*는 C 표준 I/O의 스트림 객체 포인터이고 fd 정수와 타입·상태가 다르다. fopen/fread/fwrite/fclose와 open/read/write/close를 이름만으로 섞지 않는다.

  • 이 소단원의 버퍼 크기·flush 사건은 가상의 모형으로 주어진다. 실제 libc의 버퍼 크기나 syscall 횟수를 측정한 수치가 아니다.

학습 목표

  • stdio 버퍼와 커널 캐시를 구분한다.

  • 바이트와 fread/fwrite 항목 수 반환을 구별한다.

  • flush·오류 확인·영구 저장의 서로 다른 완료 단계를 설명한다.

같은 글자 수인데 flush 계기가 달라지면 전달 횟수도 같을까?

새 출력 모형은 용량 5바이트이며 ASCII A,B,줄바꿈,C,D,E,F를 순서대로 수락한다. 정책 F는 용량 도달과 마지막 flush만 사용한다. 정책 L은 추가로 줄바꿈 직후 현재 버퍼를 전달한다. 두 정책 모두 전달은 한 번에 성공하고 마지막 비어 있는 버퍼에는 새 전달을 세지 않는다. 이 규약을 준 뒤에만 횟수를 계산한다.

F는 AB\nCD의 5바이트와 EF의 2바이트를 두 번에 나누어 전달한다. L은 AB\n의 3바이트와 CDEF의 4바이트를 두 번에 나누어 전달한다. 횟수가 같아도 전달 시점과 각 덩어리가 다르다. 다른 입력 A, 줄바꿈, B, 줄바꿈, C, 줄바꿈, D, 줄바꿈에서는 F가 5바이트와 3바이트를 두 번에 나누어 전달하지만 L은 각 2바이트를 네 번 전달한다. 총 바이트만 아는 일반 식 ceil(m/B)에 줄바꿈 정책을 숨기지 않는다.

fflush 성공의 직접 범위는 사용자 공간 출력 버퍼 전달이다. kernel 캐시·장치 영속성·상대 소비까지 같은 단계로 표시하지 않는다. 여기서 줄바꿈 문자 \n은 실제 한 바이트이며 두 글자 역슬래시와 n이 아니다. stdio와 직접 fd 입력을 혼용하는 미리읽기 경고는 원본 선수 설명의 동기화 조건과 함께 읽는다. 실제 libc나 장치를 추적하지 않았다.

먼저 확인할 개념
  • 사용자 버퍼와 flush

    전달 계기를 지정한 모형으로 한정한다.

  • 논리 자료와 하위 호출

    전달 횟수·부분 성공·메시지 경계를 서로 분리한다.

사용자 공간에서 묶어 전달하기

버퍼드 I/O는 작은 요청을 사용자 공간의 메모리에 모아 더 큰 덩어리로 아래 계층에 전달할 수 있다. C stdio의 FILE 스트림은 위치·오류·EOF·버퍼 같은 상태를 관리하며 fgetc/fputc의 한 문자 작업이 매번 read/write 시스템 호출로 이어질 필요는 없다. 도서관에서 책 한 권마다 이동하기보다 수레에 모으는 비유는 이동 횟수 절약을 설명하지만 실제 전달 시점과 실패를 자동으로 보장하지 않는다.

여기서 비버퍼드 I/O는 주로 stdio의 사용자 공간 버퍼 없이 read/write 같은 인터페이스를 직접 사용하는 뜻이다. 그 호출도 프로그램 버퍼를 인수로 받고 일반 파일의 커널 페이지 캐시를 사용할 수 있다. 따라서 “비버퍼드이니 메모리를 전혀 쓰지 않는다”, “read는 무조건 디스크를 한 번 읽는다”는 결론은 틀리다. O_DIRECT나 동기 쓰기의 제약·내구성은 별개의 설정이고 사용자 버퍼를 없애는 말로 대체하지 않는다.

항목 수와 바이트 수

fread(ptr,size,n,fp)는 각각 size바이트인 항목 n개를 읽고 완전하게 처리한 항목 수를 반환한다. size=1 이면 반환값이 바이트 수와 같지만 size=4 이면 반환 2 는 완전 항목 2 개, 즉 8 바이트에 해당한다. short item count는 EOF 또는 오류일 수 있어 feof와 ferror로 구분해야 한다. 부분 항목의 뒤쪽 메모리를 완전한 자료로 해석하지 않는다. byte 단위로 직접 파싱하려면 size=1 의 반환량을 바탕으로 경계를 검사할 수 있다.

입력 버퍼는 미리 여러 바이트를 가져올 수 있다. 가상 모형에서 하위 read로 ABCDEFGH 8 바이트를 받아 FILE 내부에 저장한 뒤 fgetc가 A만 반환하면 앱은 1 바이트 소비했지만 아래 fd의 위치는 8 일 수 있다. 이 상태에서 같은 fd에 직접 read를 섞으면 B 대신 뒤쪽 자료를 읽어 순서를 깨뜨릴 수 있다. 두 인터페이스를 같은 열린 대상에 혼용하려면 동기화 규칙을 알아야 하므로 기본 경로에서는 한 스트림의 소유권과 API 층을 일관되게 유지한다.

flush와 저장 완료의 계단

완전 버퍼·행 버퍼·버퍼 없음은 사용자 공간에서 자료를 언제 넘기는가를 정한다. 출력 행 버퍼는 줄바꿈이 전달 계기가 될 수 있고 완전 버퍼는 공간이 차거나 명시적 flush가 계기가 된다. 이 단원은 실제 기본 설정을 추측하지 않고 문제에서 방식을 지정한다. 화면에 즉시 나타날 필요가 있는 안내문은 줄바꿈 유무와 flush를 검토해야 하지만 fflush 성공만으로 상대 앱이 처리했다는 뜻은 아니다.

fflush는 출력 스트림의 사용자 공간 대기 자료를 하위 쓰기 함수로 전달하고 실패할 수도 있다. 정상 종료의 출력 flush와 비정상 중단을 구분한다. fflush/fclose를 성공 처리했어도 커널 캐시와 실제 저장장치 내구성은 다른 단계이므로 fsync 같은 별도 인터페이스와 환경 조건을 검토한다. 프로그램 버퍼에서 빠져나옴, 커널이 받아들임, 물리 저장, 상대가 의미를 처리함을 모두 “저장됨” 하나로 표시하면 오류의 위치를 찾을 수 없다.

두 번째 입력은 8바이트다. ceil(8/5)=2를 L에도 적용한 보고를 교정하라.

  1. F는 5바이트와 3바이트를 두 번에 나누어 전달한다.

  2. L은 각 줄의 2바이트마다 flush하여 총 4회 전달한다.

줄바꿈 flush를 추가하면 단순 용량 식의 전제가 달라진다. 실제 libc 기본값을 추정한 것이 아니다.

비교할 점

같은 용량을 써도 별도 flush 계기가 횟수를 바꾼다.

종이와 본문으로 직접 해보기

버퍼 용량 3 의 같은 모형에서 WXYZ를 넣고 flush하라. 전달 덩어리·횟수를 적어라. 또 fread size=2,n=4 가 2 를 반환했다면 완전 항목 수와 완전 항목에 해당하는 바이트 수를 구하고 EOF인지 결정할 수 있는지 설명하라.

힌트 보기

버퍼가 찬 순간 먼저 비우고 항목 수에 size를 곱한다. EOF 여부는 반환 수만으로 결정하지 않는다.

풀이 보기

WXY가 차서 한 번 전달되고 Z는 마지막 flush로 전달되어 총 2 번이다. fread는 완전 항목 2 개이며 해당 길이는 4 바이트다. 요청 8 바이트 전체 완료는 아니고 feof/ferror 등 상태 검사 없이 EOF와 오류를 구분할 수 없다.

오해와 반례

fflush가 성공하면 자료가 디스크에 영구 저장되어 전원을 꺼도 안전하다.

힌트 1

명시 pread 위치는 공유 현재 위치를 바꾸지 않는다. 파이프 자료 수와 참조 수는 별도다.

힌트 2

줄바꿈은 한 바이트이고 L에서 추가 전달 계기다. 마지막 비어 있는 버퍼는 새 전달로 세지 않는다.

풀이와 답 확인

  1. ① 반환 자료는 차례로 AB, C, FG, D다. 각 사건 뒤 공유 현재 위치는 2, 3, 3, 4다. 명시 읽은 범위의 끝 위치 7을 현재 위치로 옮기지 않는다.

  2. ② 자료를 소진해도 W2가 남으면 EAGAIN은 준비 부족이며 전체 EOF가 아니다. W2도 닫힌 뒤 빈 버퍼에서 양수 count인 read의 반환값 0은 EOF다.

  3. ③ 총량은 8바이트다. F는 A\nB\nC의 5바이트와 \nD\n의 3바이트를 두 번 전달한다. L은 A\n, B\n, C\n, D\n을 각각 2바이트씩 네 번 전달한다.

  4. 모든 자료 전달 장부는 실제 API/커널/장치 실행이나 상대 소비·영속성 증거가 아니다.

공유 현재 위치의 최종값은 4이고 pread의 자료는 FG다. 파이프의 EAGAIN과 EOF는 남은 쓰기 참조와 버퍼 소진을 구별한다. 두 출력 정책 모두 8바이트를 전달하지만 F의 전달 횟수는 2회이고 L의 전달 횟수는 4회다. 실제 Linux/stdio·파일·파이프·학생 시험은 미수행이다.
