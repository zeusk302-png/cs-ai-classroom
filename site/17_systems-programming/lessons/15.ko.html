각 설정 값이 유효해도 설정 묶음이 유효하지 않을 수 있을까?

새 설정 모형은 전체 수용 한도 C와 대기 한도 W를 가진다. 둘은 양의 정수이고 W≤C여야 한다. 실행 중인 버전 4는 C=8, W=3이다. 후보 C=2, W=5는 각 값이 양수라는 검사를 통과하지만 묶음 조건을 위반한다. 새 설정은 임시 후보에서 구문·개별 범위·교차 조건·필요 자원 준비를 모두 검사한 뒤 한 번에 공개한다. 실패한 후보의 일부 값만 기존 설정에 섞지 않는다.

이 자체 설계에서 요청은 수용할 때 불변 설정 버전의 참조를 잡고 끝날 때 놓는다. 요청 R이 버전 4로 시작한 뒤 버전 5(C=10, W=4)가 공개되더라도 R의 두 검사 사이에 설정이 바뀌지 않는다. 공개 이후 새 요청 S는 버전 5를 잡는다. 옛 버전은 아직 사용하는 요청이 있으면 정리할 수 없다. 이 요청별 일관성은 systemd가 모든 애플리케이션에 자동 제공하는 기능이 아니다.

두 reload 후보를 병렬로 준비하는 경우에는 완료 순서와 요청 순서도 다를 수 있다. 요청 번호 6의 후보가 먼저 준비되어 공개되었는데 번호 5의 느린 후보를 나중에 무조건 공개하면 설정을 되돌린다. 이 문제는 더 큰 요청 번호만 공개하는 정책을 정한다. 번호 5를 폐기하고 사용자가 뒤늦게 성공했다고 오해하지 않도록 결과를 구별한다. 실제 구현에는 공개와 번호 비교를 함께 보호하는 동기화가 필요하다.

프로세스가 생성되었다는 관찰과 서비스를 이용할 준비가 되었다는 관찰도 분리한다. 실제 systemd 문서에서 simple은 fork 이후, exec는 실행 성공 이후, notify는 서비스 코드의 READY=1 통지 이후라는 경계가 다르다. 이 예의 가상 시각은 생성 0초, 실행 1초, 자원 준비 완료 4초다. 새 서버를 실행해 측정한 값은 아니다. 로그에도 준비 완료, 후보 거절, 공개 버전을 구별해서 남겨야 상태를 다시 설명할 수 있다.

설정은 읽은 뒤 검증하고 적용한다

서비스는 포트·대기열 한도·자료 경로 같은 설정으로 동작한다. 값을 읽는 일과 유효성을 확인하는 일, 실행 중 설정으로 채택하는 일은 다르다. 잘못된 새 설정을 중간까지 적용하면 기존 서비스가 불일치한 상태가 될 수 있다.

자체 설계에서는 새 설정 전체를 후보로 검증하고 성공할 때만 버전을 바꾼다. 실패하면 활성 설정을 보존하고 원인을 기록한다. 시작에 필수인 설정이 잘못되면 준비 상태로 가지 않고 오류 종료하는 계약을 정한다. 모든 서비스가 동일한 재설정 기능을 제공하는 것은 아니다.

로그는 사건을 연결하되 자료를 무조건 복사하지 않는다

로그에는 시각·프로세스/실행 식별자·사건·설정 버전·결과와 필요한 요청 식별자를 기록한다. 시작 요청, 준비 완료, 처리 실패, 종료 시작, 종료 완료를 구별하면 프로세스가 떴지만 준비되지 않은 상태도 살필 수 있다.

비밀번호·토큰·불필요한 개인정보나 요청 전체를 무조건 남기지 않는다. 로그 접근·보유·삭제·용량 제한을 정하고 로그 실패도 관찰한다. 로그 한 줄이 없다는 것만으로 사건이 없었다고 결론 내리면 기록 손실이나 다른 경로를 놓칠 수 있다.

오래 사는 서비스는 감독과 준비 상태가 필요하다

데몬은 지속적으로 서비스 일을 하는 프로세스다. Linux의 systemd 같은 관리자 아래에서는 전통적인 자체 분리/fork 절차를 무조건 반복하지 않고 관리자의 감독 방식에 맞춰 실행한다. 표준 출력/오류를 로그 경로로 연결하는 방식도 관리자 설정에 달려 있다.

자체 상태를 STARTING→READY→STOPPING→STOPPED로 나누고 실패는 별도 상태로 보고한다. 준비 통지는 포트나 자원 초기화가 끝난 뒤 보내도록 설계한다. 관리자에게 보이는 종료 코드와 실제 요청 성공은 서로 다른 정보다. 이 단원은 Linux/Unix 이론이며 현재 Windows 컴퓨터에서 데몬을 설치하지 않는다.

중간 과정을 따라가는 예제

자체 설정 v1은 port=9000,queue_limit=10이다. 검증 규칙은 port가 1024–65535인 정수, queue_limit가 1 이상 정수다. 새 후보 port=9001,queue_limit=−1과 다음 후보 port=9001,queue_limit=20을 순서대로 검사하라.

  1. 첫 후보의 port는 범위 안이지만 queue_limit는 규칙을 위반한다. 후보 전체를 거부하고 v1의 9000/10을 유지한다.

  2. 로그에는 설정 거부와 잘못된 항목·활성 버전 v1을 기록하며 비밀 자료를 함께 복사하지 않는다.

  3. 다음 후보는 두 항목 모두 유효하여 새 버전 v2의 9001/20을 채택한다. 적용은 검증 뒤 한 번의 상태 변경으로 설계한다.

첫 후보는 거부해 9000/10을 보존하고 두 번째 후보만 9001/20으로 적용한다. 이는 자체 규칙이며 모든 서비스의 실제 허용 포트 규칙이 아니다.

조건을 바꾸어 비교하기

묶음 검사를 생략한 부분 갱신

기존 C=8, W=3에서 후보 C=2, W=5를 필드별로 공개하려 한다.

  1. 양수 조건은 두 값 모두 만족한다.

  2. W≤C는 5≤2가 거짓이므로 전체 후보를 거절한다. 기존 값은 함께 유지한다.

실행 설정은 계속 C=8, W=3이다.

  1. R의 참조는 버전 4를 유지한다.

  2. S는 새 버전 5를 잡고 옛 버전의 정리는 R이 참조를 놓은 뒤 허용한다.

R과 S가 서로 다른 버전을 쓰는 것이 이 모형의 일관된 정책이다.

종료 단계가 의존하면 가장 긴 한 단계만 기다려도 될까?

새 종료 모형은 마지막 수용 시각을 10초로 정한다. 10초보다 먼저 수용한 요청만 배출하고 10초 또는 그 뒤의 새 요청은 거절한다. STOPPING 상태는 즉시 모든 자원이 사라졌다는 뜻이 아니다. 이미 수용한 요청이 아직 접근하는 저장소와 로그를 먼저 닫으면 정상 종료 계약을 깬다. 시각 경계는 이 문제의 반열린 수용 규칙이며 모든 서버의 공통 규칙은 아니다.

의존 그래프에서 A는 새 입력을 막고 2초 뒤 끝난다. A가 끝난 뒤에만 worker 배출 B(3초)와 상태 저장 C(5초)가 병렬로 시작한다. 둘 다 끝난 뒤 로그 정리 D가 1초 걸린다. 종료 시작을 상대 시각 0으로 놓으면 A는 2초, B는 5초, C는 7초, D는 8초에 끝난다. max(2,3,5,1)=5초는 독립 동시 시작을 잘못 가정한 값이다.

시간 초과 때문에 프로세스가 사라졌다는 관찰은 외부 효과가 없었다는 증거가 아니다. 요청 R의 원격 변경이 처리되었지만 응답 전에 종료되면 클라이언트는 미확인 상태에 놓인다. 다시 요청하려면 업무 식별자에 기반한 중복 정책이나 외부 상태 확인이 필요하다. 재시작이 메모리의 미확인 작업을 자동 복구한다고 가정하지 않는다.

signal handler가 종료 신호를 받아 복잡한 printf나 임의 자원 정리를 직접 수행하도록 만들면 안전성 문제가 생길 수 있다. 실제 signal-safety 문서는 비재진입 stdio의 중간 상태를 설명한다. 적절한 안전 통지 또는 안전하게 공유하는 플래그를 통해 주 처리 흐름에서 종료를 진행하도록 설계한다. 안전 여부는 선택한 실제 함수·동기화와 errno 보존까지 확인해야 한다. 이 보강은 실제 signal handler 코드를 실행하지 않았다.

실제 systemd TimeoutStopSec 문서는 종료 명령 대기와 서비스 종료 대기를 구별하고 기본 동작의 시간 초과 뒤 강제 종료를 설명한다. 아래의 7초/8초는 애플리케이션의 자체 전체 예산 모형이며 그 옵션 하나의 정확한 총 실행 시간이라고 주장하지 않는다. 확장 통지·설정·감독자 정책에 따라 실제 종료 경계가 달라질 수 있다.

정상 종료는 프로그램의 약속과 실행이다

Linux/Unix의 SIGTERM은 종료를 요청하는 신호다. 기본 동작이 종료일 수 있지만 프로그램은 적절한 처리 흐름을 설계할 수 있다. 종료 요청이 자동으로 모든 요청을 완료하거나 데이터를 영속 저장하는 것은 아니다.

자체 서비스는 새 요청 수락을 멈추고 진행 중 작업에 제한된 마무리 시간을 준 뒤 연결·파일 등 자원을 닫고 결과를 보고한다. 로그 기록과 응답 전송·실제 저장 완료의 의미를 따로 정한다. C의 신호 핸들러 안에서 printf 등 복잡한 작업을 무조건 수행하면 비동기 안전성 문제가 생길 수 있어 안전한 통지와 평상시 처리 흐름을 구별한다.

시간 제한을 넘으면 일부 완료를 보장할 수 없다

끝나지 않는 요청 때문에 종료가 무한히 미뤄지지 않도록 마감 시각을 정한다. 관리자가 중지 시간 제한 뒤 SIGKILL로 강제 종료하는 정책도 가능하다. SIGKILL은 프로그램이 잡거나 무시하여 자기 정리 코드를 수행할 수 있는 신호가 아니다.

자체 설계의 취소와 관리자 강제 종료를 구별한다. 마감에 요청을 취소했다는 보고가 실제 외부 효과의 원상복구까지 뜻하지 않는다. 완료/취소/결과 불명 상태를 분리하고 클라이언트가 재시도할 때 중복 효과를 어떻게 막을지 생각한다.

재시작은 잃은 의미를 저절로 복원하지 않는다

재시작 정책은 종료 코드·신호·시간 초과와 명시적인 중지인지에 따라 다르다. systemd의 Restart= 설정도 모든 상황의 자동 재시작을 의미하지 않으며 시작률 제한 등이 있다.

새 프로세스는 메모리만 있던 처리 기록을 잃을 수 있다. 처리 식별자·지속 기록·재시도 계약을 설계하지 않으면 “효과 적용 뒤 응답 전에 종료”된 작업이 재시도로 중복 적용될 수 있다. 재시작을 성공했다는 것만으로 요청이 정확히 한 번 처리됐다고 주장하지 않는다.

  2. t=3에 A가 완료된다. B는 7s가 필요하므로 t=5까지 미완료다.

  3. t=5에 B 취소를 시작하고 계약에 맞춰 자원을 닫고 종료 결과를 기록한다. 외부 효과 복구나 실제 프로세스 종료의 성공 여부는 별도 확인이 필요하다.

모든 도구의 종료 코드가 0이면 출력 내용도 맞을까?

새 파이프 모형에는 writer P와 복제 write descriptor를 가진 helper H가 있고 reader R이 있다. P가 자료를 쓰고 자기 write 참조를 닫아도 H의 참조가 남으면 R은 모든 자료를 소비한 뒤 EOF를 아직 볼 수 없다. 블로킹 R은 새 자료나 마지막 writer 종료를 기다릴 수 있고 논블로킹 R은 빈 상태에서 EAGAIN을 볼 수 있다. 마지막 write 참조가 닫히고 자료도 소진되어야 양수 길이 읽기의 반환 0을 EOF로 해석한다.

실제 pipe는 바이트 흐름이고 메시지 경계가 없다. 여기서는 writer 두 개가 각각 완전한 ASCII 줄 AA와 BB에 줄바꿈을 붙여 한 번의 blocking write로 보내며 각 길이는 3바이트로 PIPE_BUF 이하다. 두 write 각각의 바이트는 서로 끼어들지 않지만 어느 줄이 먼저인지는 별도 순서 계약이 없으면 정할 수 없다. read 한 번이 정확히 한 줄을 돌려준다는 보장도 없다. parser는 조각을 누적하고 줄 경계를 찾아야 한다.

Bash 동기 pipeline의 가상 각 단계 종료 코드를 왼쪽부터 (4,7,0)이라 놓는다. pipefail이 꺼져 있으면 전체 코드는 마지막 단계의 0이고 켜져 있으면 가장 오른쪽 비영 코드 7이다. 먼저 끝난 단계나 가장 큰 숫자를 고르는 규약이 아니다. 상태와 stderr 진단·내용 검사를 모두 보존해야 실패 위치를 설명할 수 있다. 아래는 실제 Bash나 파이프를 실행한 기록이 아니다.

다른 내용 검증 모형은 도구 세 단계가 모두 0으로 끝났지만 결과 ID가 [a,a,c]인 경우다. 계약은 [a,b,c]의 각 ID가 정확히 한 번이어야 한다. 길이는 둘 다 3이지만 b가 빠지고 a가 중복되어 내용 검사는 실패한다. 종료 코드 성공과 업무 출력 불변식 성공을 서로 다른 항목으로 기록한다. 실제 socket/tool 검증에서도 통신 성공이 응용 의미의 정확성을 대신하지 않는다.

연결과 한 번의 송수신은 메시지 성공이 아니다

TCP 스트림 소켓은 바이트 흐름이며 응용 메시지 경계를 대신 제공하지 않는다. send가 일부만 보내거나 recv가 요청한 최대량보다 적게 돌려줄 수 있다. 전송 반환량을 누적하고 응용 프로토콜 규칙으로 메시지를 조립한다.

자체 ASCII 프로토콜을 “십진 길이:본문”으로 정하자. 길이 접두부 자체도 여러 읽기에 나뉠 수 있고 한 읽기에 다음 메시지 일부가 붙을 수 있다. 허용 길이와 버퍼 한도·시간 제한을 검증한다. 이 단원은 TCP 같은 스트림에 한정하며 UDP의 빈 데이터그램과 연결 EOF를 혼동하지 않는다.

파이프는 descriptor와 종료 조건을 함께 확인한다

파이프는 프로세스 간 통신인 IPC의 한 방식이다. 읽기 끝과 쓰기 끝을 가지고 바이트를 전달하며 원래 메시지 경계는 없다. 쓰기 끝을 가진 복제 descriptor가 남아 있으면 생산자가 끝났어도 소비자가 EOF를 기다릴 수 있다.

불필요한 descriptor를 닫고 생산/소비의 종료와 오류를 각각 확인한다. 파이프가 가득 차면 쓰기 쪽이 대기할 수 있어 소비 흐름과 시간 제한을 살핀다. 도구가 화면에 문자열을 출력했다는 사실과 전체 데이터가 정확히 전달됐다는 사실은 다르다.

셸 전체 상태와 각 단계 상태를 나눈다

GNU Bash의 기본 파이프라인 종료 상태는 마지막 명령의 상태다. pipefail을 켜면 오른쪽에서 마지막으로 비정상 종료한 명령의 상태를 반환하고 모두 성공하면 0이다. 이는 Bash 계약이며 다른 셸이나 PowerShell에 그대로 적용하지 않는다.

검증 계획은 입력·예상 출력·각 단계 종료 코드·표준 오류·시간 초과·자원 정리·프로토콜 거부 결과를 기록한다. 원문 문서 확인, 종이 추적, 실제 도구 실행, 실제 서비스 요청 시험을 구별한다. 실제 실행하지 않은 명령의 출력은 관찰 결과로 쓰지 않는다.

다른 문제에 적용하기

가상 서비스의 공개 설정은 버전 4(C=8,W=3)다. reload 후보 5는 C=2,W=5이고 후보 6은 C=10,W=4로 모든 자원 준비까지 성공한다. 요청 R은 공개 전 버전 4를 잡았고 S는 후보 6 공개 후 시작한다. 종료 시작의 상대 시각 0에 입력을 막고 A 2초 뒤 B 3초/C 5초 병렬, 둘 뒤 D 1초를 수행한다. 전체 예산은 7초다. 출력 pipeline의 단계 코드는 (4,7,0)이고 출력 ID는 [a,a,c], 기대는 [a,b,c]다. 모든 상태와 최종 보고를 구성하라.

힌트 2

pipeline 기본/pipefail 코드와 ID별 빈도 검사 결과는 서로 다른 항목으로 기록한다.

풀이와 답 확인

  1. 후보 5는 5≤2가 거짓이어서 공개하지 않는다. 후보 6은 준비까지 성공해 공개한다. R은 버전 4, S는 버전 6을 보존하며 R이 끝나기 전 옛 자원을 해제하지 않는다.

  2. A는 2초에 끝나고 B/C는 각각 5초와 7초에 끝난다. D는 7초에 시작해 8초에 끝나므로 7초 전체 예산에는 정상 종료 완료가 아직 없다.

  3. pipeline 기본 코드는 0이고 pipefail 코드는 오른쪽 비영 값 7이다. 세 단계 상태를 별도 보존한다.

  4. 출력 빈도는 a가 2회, b가 0회, c가 1회다. 길이 3이 같아도 내용 검증은 실패다. 설정 공개·종료 기한·도구 반환·업무 내용의 결과를 개별 기록한다.

유효 공개는 후보 6이며 R/S는 각각 버전 4/6을 쓴다. 종료 모형의 정상 완료는 8초라서 예산 7초에 완료했다고 보고할 수 없다. pipeline은 기본 0/pipefail 7이지만 출력 ID 계약은 실패다. 실제 서비스·셸·pipe·signal·학생 실행을 수행한 결과가 아니다.
