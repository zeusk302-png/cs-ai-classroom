소단원 15.1

로그·설정·데몬 수명

서비스 프로세스가 살아 있다는 사실만으로 요청을 처리할 준비가 됐다고 알 수 있을까?

준비 개념과 학습 목표

  • 설정 값

설정은 읽은 뒤 검증하고 적용한다

서비스는 포트·대기열 한도·자료 경로 같은 설정으로 동작한다. 값을 읽는 일과 유효성을 확인하는 일, 실행 중 설정으로 채택하는 일은 다르다. 잘못된 새 설정을 중간까지 적용하면 기존 서비스가 불일치한 상태가 될 수 있다.

자체 설계에서는 새 설정 전체를 후보로 검증하고 성공할 때만 버전을 바꾼다. 실패하면 활성 설정을 보존하고 원인을 기록한다. 시작에 필수인 설정이 잘못되면 준비 상태로 가지 않고 오류 종료하는 계약을 정한다. 모든 서비스가 동일한 재설정 기능을 제공하는 것은 아니다.

로그는 사건을 연결하되 자료를 무조건 복사하지 않는다

로그에는 시각·프로세스/실행 식별자·사건·설정 버전·결과와 필요한 요청 식별자를 기록한다. 시작 요청, 준비 완료, 처리 실패, 종료 시작, 종료 완료를 구별하면 프로세스가 떴지만 준비되지 않은 상태도 살필 수 있다.

비밀번호·토큰·불필요한 개인정보나 요청 전체를 무조건 남기지 않는다. 로그 접근·보유·삭제·용량 제한을 정하고 로그 실패도 관찰한다. 로그 한 줄이 없다는 것만으로 사건이 없었다고 결론 내리면 기록 손실이나 다른 경로를 놓칠 수 있다.

오래 사는 서비스는 감독과 준비 상태가 필요하다

데몬은 지속적으로 서비스 일을 하는 프로세스다. Linux의 systemd 같은 관리자 아래에서는 전통적인 자체 분리/fork 절차를 무조건 반복하지 않고 관리자의 감독 방식에 맞춰 실행한다. 표준 출력/오류를 로그 경로로 연결하는 방식도 관리자 설정에 달려 있다.

자체 상태를 STARTING→READY→STOPPING→STOPPED로 나누고 실패는 별도 상태로 보고한다. 준비 통지는 포트나 자원 초기화가 끝난 뒤 보내도록 설계한다. 관리자에게 보이는 종료 코드와 실제 요청 성공은 서로 다른 정보다. 이 단원은 Linux/Unix 이론이며 현재 Windows 컴퓨터에서 데몬을 설치하지 않는다.

중간 과정을 따라가는 예제

자체 설정 v1은 port=9000,queue_limit=10이다. 검증 규칙은 port가 1024–65535인 정수, queue_limit가 1 이상 정수다. 새 후보 port=9001,queue_limit=−1과 다음 후보 port=9001,queue_limit=20을 순서대로 검사하라.

  1. 첫 후보의 port는 범위 안이지만 queue_limit는 규칙을 위반한다. 후보 전체를 거부하고 v1의 9000/10을 유지한다.

  2. 로그에는 설정 거부와 잘못된 항목·활성 버전 v1을 기록하며 비밀 자료를 함께 복사하지 않는다.

  3. 다음 후보는 두 항목 모두 유효하여 새 버전 v2의 9001/20을 채택한다. 적용은 검증 뒤 한 번의 상태 변경으로 설계한다.

첫 후보는 거부해 9000/10을 보존하고 두 번째 후보만 9001/20으로 적용한다. 이는 자체 규칙이며 모든 서비스의 실제 허용 포트 규칙이 아니다.

소단원 15.2

정상 종료와 재시작

종료 신호를 보내면 처리 중인 요청도 자동으로 안전하게 저장될까?

준비 개념과 학습 목표

준비 개념

  • 진행 중 작업

  • 시간 제한

  • 프로세스 재시작

학습 목표

  • 요청 중지·처리 마무리·자원 닫기 순서를 설계한다.

  • 종료 요청과 강제 종료의 차이를 설명한다.

  • 재시작 후 중복/상태 복구의 한계를 구별한다.

정상 종료는 프로그램의 약속과 실행이다

Linux/Unix의 SIGTERM은 종료를 요청하는 신호다. 기본 동작이 종료일 수 있지만 프로그램은 적절한 처리 흐름을 설계할 수 있다. 종료 요청이 자동으로 모든 요청을 완료하거나 데이터를 영속 저장하는 것은 아니다.

자체 서비스는 새 요청 수락을 멈추고 진행 중 작업에 제한된 마무리 시간을 준 뒤 연결·파일 등 자원을 닫고 결과를 보고한다. 로그 기록과 응답 전송·실제 저장 완료의 의미를 따로 정한다. C의 신호 핸들러 안에서 printf 등 복잡한 작업을 무조건 수행하면 비동기 안전성 문제가 생길 수 있어 안전한 통지와 평상시 처리 흐름을 구별한다.

시간 제한을 넘으면 일부 완료를 보장할 수 없다

끝나지 않는 요청 때문에 종료가 무한히 미뤄지지 않도록 마감 시각을 정한다. 관리자가 중지 시간 제한 뒤 SIGKILL로 강제 종료하는 정책도 가능하다. SIGKILL은 프로그램이 잡거나 무시하여 자기 정리 코드를 수행할 수 있는 신호가 아니다.

자체 설계의 취소와 관리자 강제 종료를 구별한다. 마감에 요청을 취소했다는 보고가 실제 외부 효과의 원상복구까지 뜻하지 않는다. 완료/취소/결과 불명 상태를 분리하고 클라이언트가 재시도할 때 중복 효과를 어떻게 막을지 생각한다.

재시작은 잃은 의미를 저절로 복원하지 않는다

재시작 정책은 종료 코드·신호·시간 초과와 명시적인 중지인지에 따라 다르다. systemd의 Restart= 설정도 모든 상황의 자동 재시작을 의미하지 않으며 시작률 제한 등이 있다.

새 프로세스는 메모리만 있던 처리 기록을 잃을 수 있다. 처리 식별자·지속 기록·재시도 계약을 설계하지 않으면 “효과 적용 뒤 응답 전에 종료”된 작업이 재시도로 중복 적용될 수 있다. 재시작을 성공했다는 것만으로 요청이 정확히 한 번 처리됐다고 주장하지 않는다.

중간 과정을 따라가는 예제

자체 서비스가 t=0에 종료 요청을 받는다. 새 요청을 거부하고 기존 A/B는 각각 남은 작업 3s/7s이며 독립적으로 동시에 진행한다. 자체 마감은 t=5이고 마감 때 미완료 작업을 취소한다고 정한다. 상태를 추적하라.

  1. t=0에 STOPPING으로 바뀌고 신규 요청은 거부한다. A/B의 기존 작업은 제한된 마무리 흐름으로 진행한다.

  2. t=3에 A가 완료된다. B는 7s가 필요하므로 t=5까지 미완료다.

  3. t=5에 B 취소를 시작하고 계약에 맞춰 자원을 닫고 종료 결과를 기록한다. 외부 효과 복구나 실제 프로세스 종료의 성공 여부는 별도 확인이 필요하다.

A는 마감 전에 완료하고 B는 마감 시 미완료로 취소 처리된다. 가상 병렬 시간선이며 실제 신호·관리자 동작을 관찰하지 않았다.

소단원 15.3

셸·IPC·소켓 도구 검증

소켓에서 한 번 읽은 데이터가 요청 한 개이고 파이프라인 종료 코드가 0이면 전체 도구가 성공한 것일까?

준비 개념과 학습 목표

준비 개념

  • 바이트와 길이

  • 프로세스 간 전달

  • 종료 코드

학습 목표

  • 스트림의 부분 읽기와 메시지 경계를 구별한다.

  • 파이프의 EOF와 descriptor 수명을 설명한다.

  • 셸 단계별 오류와 실제 검증 범위를 기록한다.

연결과 한 번의 송수신은 메시지 성공이 아니다

TCP 스트림 소켓은 바이트 흐름이며 응용 메시지 경계를 대신 제공하지 않는다. send가 일부만 보내거나 recv가 요청한 최대량보다 적게 돌려줄 수 있다. 전송 반환량을 누적하고 응용 프로토콜 규칙으로 메시지를 조립한다.

자체 ASCII 프로토콜을 “십진 길이:본문”으로 정하자. 길이 접두부 자체도 여러 읽기에 나뉠 수 있고 한 읽기에 다음 메시지 일부가 붙을 수 있다. 허용 길이와 버퍼 한도·시간 제한을 검증한다. 이 단원은 TCP 같은 스트림에 한정하며 UDP의 빈 데이터그램과 연결 EOF를 혼동하지 않는다.

파이프는 descriptor와 종료 조건을 함께 확인한다

파이프는 프로세스 간 통신인 IPC의 한 방식이다. 읽기 끝과 쓰기 끝을 가지고 바이트를 전달하며 원래 메시지 경계는 없다. 쓰기 끝을 가진 복제 descriptor가 남아 있으면 생산자가 끝났어도 소비자가 EOF를 기다릴 수 있다.

불필요한 descriptor를 닫고 생산/소비의 종료와 오류를 각각 확인한다. 파이프가 가득 차면 쓰기 쪽이 대기할 수 있어 소비 흐름과 시간 제한을 살핀다. 도구가 화면에 문자열을 출력했다는 사실과 전체 데이터가 정확히 전달됐다는 사실은 다르다.

셸 전체 상태와 각 단계 상태를 나눈다

GNU Bash의 기본 파이프라인 종료 상태는 마지막 명령의 상태다. pipefail을 켜면 오른쪽에서 마지막으로 비정상 종료한 명령의 상태를 반환하고 모두 성공하면 0이다. 이는 Bash 계약이며 다른 셸이나 PowerShell에 그대로 적용하지 않는다.

검증 계획은 입력·예상 출력·각 단계 종료 코드·표준 오류·시간 초과·자원 정리·프로토콜 거부 결과를 기록한다. 원문 문서 확인, 종이 추적, 실제 도구 실행, 실제 서비스 요청 시험을 구별한다. 실제 실행하지 않은 명령의 출력은 관찰 결과로 쓰지 않는다.

중간 과정을 따라가는 예제

자체 스트림은 “3:cat2:hi”이며 한 번씩 읽은 조각은 “3:c”, “at2:”, “hi”다. 허용 본문 길이는 최대 4바이트이고 모두 ASCII다. 메시지와 버퍼를 추적하라. 별도 Bash 가상 두 단계의 종료 코드는 2와 0이다.

  1. 첫 조각에서 길이 3을 읽지만 본문은 c 한 바이트만 있으므로 cat이 아직 완성되지 않았다.

  2. 두 번째 조각을 합치면 cat 세 바이트가 완성되어 첫 메시지를 꺼낸다. 남은 “2:”는 다음 길이 2이고 본문을 기다린다.

  3. 세 번째 hi로 둘째 메시지가 완성된다. 전체 스트림 9바이트에서 결과는 cat/hi다. 별도 Bash 기본 상태는 마지막 0, pipefail 활성 상태는 2다.

읽기 3번을 메시지 3개로 해석하지 않는다. 완성 메시지는 cat과 hi 두 개이며 가상 Bash 상태는 기본 0/pipefail 2다.

힌트 보기

길이 검증과 수신 완료를 나눈다.

풀이 보기

5는 한도 초과라 자체 프로토콜 오류로 거부한다. “3:ca”는 3바이트 중 2바이트만 있으므로 EOF 시 잘린 메시지 오류이며 완성 메시지로 처리하지 않는다.

오해와 반례

recv 한 번이 요청 한 개이며 파이프라인 0은 모든 단계 성공이다.

스트림 읽기와 메시지 경계는 다르다. Bash 기본 상태는 마지막 단계만 반영하여 앞 오류를 숨길 수 있다.

한 단계 더

9바이트 송신이 가상으로 2/4/3바이트씩 성공했다고 정하면 전송 위치는 2→6→9가 되고 남은 길이는 7→3→0이다. 실제 send의 0·오류·시간 초과는 무한 반복하지 않는 실패 계약으로 따로 시험한다. 한 번의 전송 성공도 상대 응용 처리 완료를 보장하지 않는다.
