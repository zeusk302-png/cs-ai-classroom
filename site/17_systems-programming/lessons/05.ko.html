소단원 5.1

fork와 주소공간 복제

한 프로그램이 둘이 되었을 때 변수와 열린 파일은 모두 두 벌일까요?

준비 개념과 학습 목표

준비 개념

  • 20_os: 프로세스는 PID와 주소공간을 가진 실행 단위이다.

  • 07_c: 지역 변수 값과 조건 분기를 구별한다.

학습 목표

  • fork 반환값 세 경우를 분리한다.

  • 일반 메모리의 분리와 열린 파일 위치의 공유를 구별한다.

복사된 장부와 공유된 커서가 함께 있으면 어떤 값을 어디에 적어야 할까?

한 스레드인 부모 P의 일반 변수 x=2, stdio의 아직 전달하지 않은 출력 버퍼 문자열 Q, 일반 파일 ABCDE의 열린 설명 O와 위치 0을 정한다. fork가 성공하여 자식 C가 생기면 x와 버퍼는 각 주소공간의 복사본이지만 fd가 참조하는 O는 공유된다. 공유 메모리·특수 매핑·동시 파일 변경은 이 모형에서 제외한다. 같은 숫자 주소나 fd를 보았다는 이유만으로 모든 상태를 하나로 합치지 않는다.

명시한 사건 순서는 P가 x에 3을 더하기, C가 x에 10을 곱하기, C의 read 2바이트 완료, P의 read 1바이트 완료다. 두 read는 정확한 길이로 성공한다. 그러면 x는 각각 5와 20, C는 AB, P는 C를 받으며 O의 위치는 3이다. 두 읽기 순서를 바꾸면 P가 A, C가 BC를 받아 위치만 3으로 같아진다. 최종 위치만으로 어느 쪽이 어느 바이트를 받았는지 복원할 수 없다.

버퍼 Q는 아직 커널로 쓰지 않은 사용자 공간 상태다. 모든 flush가 성공하며 각각 Q 전체를 한 번 전달한다는 별도 모형에서 두 프로세스가 모두 exit하면 Q가 두 번 전달될 수 있다. 자식이 _exit하고 부모만 exit하면 한 번이다. fork 전에 Q를 성공적으로 flush해 버퍼를 비우고 둘 다 exit해도 이전 Q의 총 전달은 한 번이다. 실제 출력 장치·버퍼링·프로세스 실행을 관측한 결과가 아니라 조건을 둔 장부다. 멀티스레드 fork 뒤 자식의 안전 함수 제한은 이 쉬운 모형으로 해결되지 않는다.

복제한 다음 지점에서 계속하기

fork는 호출 프로세스로부터 새 자식 프로세스를 만든다. 성공하면 부모에서는 자식 PID라는 양수, 자식에서는 0 을 반환하며 둘 다 fork 다음 지점에서 계속한다. 자식이 main 처음부터 다시 실행하는 것은 아니다. 실패하면 부모에 −1 을 반환하고 자식은 생성되지 않으므로 양수/0/−1 세 경우를 구별해야 한다.

자식은 자기 PID를 갖고 부모 PID를 연결 정보로 가진다. 부모와 자식 중 어느 쪽이 먼저 다음 명령을 실행하는지는 이 반환값 규칙만으로 결정되지 않는다. 출력 순서를 한 가지로 외우는 대신 명시한 동기화나 사건 순서가 무엇인지 확인한다. 본 단원은 스레드 하나인 프로세스의 정상 종이 사건 모형을 기본으로 한다.

같은 내용이지만 서로 다른 일반 메모리

fork 시점의 일반 변수 내용은 복제되어 부모와 자식이 같은 값을 볼 수 있지만 이후 서로의 일반 메모리 쓰기가 다른 쪽 값을 바꾸지는 않는다. 같은 가상 주소 숫자로 보이는 변수라도 각 주소공간의 객체이다. 공유 메모리 매핑처럼 별도 공유 장치가 있는 경우는 이 일반 변수 설명에서 제외한다.

Linux는 copy-on-write로 당장 모든 물리 페이지를 복사하기보다 필요한 쓰기 시점을 이용한다. 이는 관찰되는 일반 메모리 분리 의미를 효율적으로 구현하는 방법이지 이후 모든 변수 쓰기가 공유된다는 뜻이 아니다. 페이지 테이블과 자식 관리 구조 등 비용도 있으므로 fork를 비용 0 인 명령이라고 표현하지 않는다.

열린 파일은 다른 공유 관계를 가진다

자식의 fd 테이블 항목은 복제되지만 부모의 대응 fd와 같은 open file description을 참조한다. 따라서 파일 위치와 파일 상태 플래그가 공유될 수 있다. fd라는 작은 정수의 복사와 커널 객체를 별도로 새로 여는 일은 다르다. 일반 변수의 분리를 그대로 fd가 가리키는 모든 상태에 적용하면 틀린다.

멀티스레드 프로세스에서는 호출한 스레드만 자식에 남고 잠금 상태는 복제될 수 있으므로 복제 뒤 자식이 임의 라이브러리 함수를 호출하는 것이 안전하지 않다. 공식 규칙은 execve 전까지 async-signal-safe 함수만 안전하게 호출할 수 있다는 제한이다. 여기의 쉬운 단일 스레드 그림을 복잡한 서비스의 실행 안전 검증으로 확대하지 않는다.

중간 과정을 따라가는 예제

한 스레드 프로세스의 일반 변수 x=7, fd가 정상 일반 파일 ABC의 위치 0 을 가리킨다. fork 성공 뒤 부모는 x=9, 자식은 x=12 로 쓴다. 명시한 순서대로 부모 read1 바이트가 먼저 완료되고 자식 read1 바이트가 다음 완료된다. 두 읽기는 오류 없이 1 바이트를 처리한다. 최종 상태를 구하세요.

  1. fork는 부모에 자식 PID 양수, 자식에 0 을 반환한다. 두 일반 x 복사본은 초기 7 이다.

  2. 부모 x=9 와 자식 x=12 는 분리된 주소공간이므로 서로 덮지 않는다.

  3. 부모 read가 먼저 현재 위치 0 의 A를 읽고 공유 위치를 1 로 올린다.

  4. 자식 read는 같은 열린 파일 설명의 현재 위치 1 에서 B를 읽고 위치 2 로 올린다.

  5. 최종 부모 x9·읽은 A, 자식 x12·읽은 B, 공유 파일 위치 2 이다.

일반 변수는 9 와 12 로 분리되지만 파일 위치는 2 라는 공유 상태이다. A/B의 배정은 지정한 사건 순서 조건에 의존한다.

마지막 위치가 같은 두 이력

위 표의 read 순서를 바꿔 P의 1바이트 읽기를 먼저 완료시키면 어떻게 되는가?

  1. P는 위치 0의 A를 받고 위치를 1로 올린다.

  2. C는 위치 1에서 BC를 받고 위치를 3으로 올린다.

마지막 공유 커서만 같은 것은 전체 관찰 이력이 같다는 뜻이 아니다.

버퍼의 두 복사본과 한 번의 이전 flush

처음 Q는 미전달 상태다. 두 exit, 자식 _exit/부모 exit, fork 전 성공 flush 뒤 두 exit의 이전 Q 전달 수를 비교하라.

  1. 두 exit는 각 복사본의 Q를 flush하므로 두 번이다.

  2. _exit는 stdio를 flush하지 않아 부모 복사본만 전달한다. fork 전 flush는 원본에서 한 번 전달하고 빈 버퍼를 복제한다.

각각 2회, 1회, 1회다. 마지막 경우 fork 뒤 이전 Q의 추가 전달은 0회다.

비교할 점

fd를 닫는 것과 사용자 stdio 버퍼를 flush하는 것은 같은 사건이 아니다.

자식이 남긴 숫자 127만으로 exec 실패를 확정할 수 있을까?

부모 PID 900이 만든 자식 PID 901의 실패 처리 경로는 execve가 −1로 돌아오면 _exit(127)하는 것으로 정한다. 그러나 새 정상 바이너리 tool 자체도 정상 종료 상태 127을 선택할 수 있다. 부모가 wait로 정상 종료 127을 받았다는 한 관찰만으로 두 경로를 구별할 수 없다. exec 성공은 같은 자식 PID의 이미지 교체이고 이후 종료 상태의 의미는 새 프로그램의 계약이다.

성공 모형의 argv는 ["tool", "a b", "*", "", NULL], envp는 ["MODE=paper", NULL]이다. 문자열은 네 개이므로 argc는 4다. 공백 문자열, 별표 문자열, 빈 문자열은 각각 하나의 인자이고 끝 NULL은 세지 않는다. 직접 정상 바이너리를 실행하며 셸이나 스크립트는 사용하지 않는 조건이다. p 계열의 ENOEXEC 셸 fallback이나 명시적 셸 실행을 이 조건에 섞지 않는다.

fd 3과 dup으로 만든 fd 4는 열린 설명 O를 공유하지만 FD_CLOEXEC는 각각의 descriptor 플래그다. fd 3에만 표시하면 exec 성공에서 3만 닫히고 4는 유지된다. O의 공유 위치와 descriptor별 생존 조건을 구별한다. 반환한 exec 실패 경로에서는 성공 때의 close-on-exec 효과를 적용하지 않는다. 아주 드문 이미지 해체 뒤 치명적 실패는 옛 코드로 반환하는 모형 밖이므로 별도로 기록한다.

프로세스는 유지하고 프로그램 이미지를 교체하기

execve는 기존 프로세스의 프로그램 이미지를 지정한 새 프로그램으로 교체한다. 새 코드·초기 데이터·스택·힙을 준비하여 그 프로그램이 시작한다. 성공하면 기존 코드의 exec 다음 문장으로 돌아오지 않으며 PID를 새로 생성하는 동작이 아니다. fork 다음 자식에서 exec를 호출하는 조합이 새 프로세스로 다른 프로그램을 돌리는 흔한 구조이다.

실패하면 −1 을 반환하고 errno로 이유를 알려 주므로 기존 코드가 계속 실행될 수 있다. 파일 없음이나 권한 문제 등을 무시하면 자식이 부모용 흐름까지 실행하는 오류가 생긴다. 성공 비복귀와 실패 반환을 서로 다른 가지로 그려야 한다. 일반적인 반환형이 int라는 사실만으로 성공 때 0 을 받을 것이라고 생각하면 안 된다. 여기서 실패 후 흐름은 -1로 반환하는 오류 경로를 뜻한다. Linux에서는 드물게 자원 고갈 등으로 이전 이미지를 이미 해체한 뒤 새 이미지를 완성하지 못하면 반환하지 못하고 프로세스가 종료될 수 있다. 모든 실패가 반드시 옛 코드로 돌아온다고 일반화하지 않는다.

문자열들을 배열로 전달하기

argv는 문자열을 가리키는 포인터 배열이고 마지막 항목은 NULL이다. 통상 argv[0]은 프로그램 이름이며 argc는 이 끝 포인터를 제외한 문자열 수이다. envp도 KEY=VALUE 문자열 포인터 배열 끝에 NULL을 붙인다. 개별 문자열 끝의 NUL 문자와 배열 끝의 NULL 포인터를 같은 칸으로 세지 않는다.

직접 정상 바이너리에 전달하는 argv의 한 문자열 hello world는 공백을 포함해도 하나의 인자이다. 셸이 문자열을 파싱한 것이 아니므로 *, >, $ 같은 문자가 일반적으로 자동으로 확장/리다이렉션되지 않는다. 명시적으로 셸을 실행한 경우나 p 계열의 ENOEXEC 셸 fallback은 별도이며 모든 exec가 절대 셸을 쓰지 않는다고 일반화하지 않는다.

접미사와 남겨 둘 자원

l은 가변 인자 목록, v는 배열 vector, e는 명시한 환경 배열, p는 파일 이름에 슬래시가 없으면 PATH를 검색하는 계열이다. 예를 들어 execvp는 argv 배열과 PATH 검색을 사용하고, execv는 지정 경로와 argv 배열을 사용한다. p라도 이름에 슬래시가 있으면 PATH 검색을 하지 않는다. l 목록 끝은 가변 인자이므로 (char *)NULL로 명시한다.

exec 성공 뒤 기본적으로 열린 fd는 유지되지만 FD_CLOEXEC 표시가 있으면 닫힌다. 이전 일반 메모리 변수와 잡아 둔 신호 처리기·atexit 등록 등은 그대로 남는 것이 아니다. 새 이미지와 유지되는 프로세스 속성을 나누어 봐야 한다. 이 단원은 권한 상승 없는 정상 바이너리 예제로 제한한다.

wait·종료 상태·좀비

계산을 끝낸 자식은 왜 잠시 프로세스 목록에 남을 수 있을까요?

준비 개념과 학습 목표

준비 개념

  • 앞 소단원: 자식 PID와 _exit는 프로세스 종료를 구별한다.

  • 조건부 해석: 상태 종류를 확인한 뒤 그 값을 읽는다.

  • 시간선과 정수 나머지: 300 mod256=44.

학습 목표

  • 종료와 상태 회수의 두 사건을 구별한다.

  • waitpid 반환과 상태 매크로의 조건을 해석한다.

정지 통지 뒤 자식의 수명 장부를 지워도 될까?

가상 시간 단위에서 자식 A의 PID는 901, B는 902다. t=2에 A가 정상 _exit(513)으로 끝나고 t=4에 B가 신호 15로 종료된다. 기본 SIGCHLD 처리, 다른 회수자 없음, 자동 회수 옵션 없음, 부모 생존을 가정한다. 부모는 t=3에 B만 WNOHANG으로 조회하고 t=6에 B를 회수한 뒤 t=7에 A를 회수한다. B 조회의 0은 A가 종료하지 않았다는 말이 아니다.

A의 미회수 종료 구간은 [2,7), B의 것은 [4,6)다. 좀비 수는 [2,4)에서 1, [4,6)에서 2, [6,7)에서 1이므로 장부 면적은 2+4+1=7 process·시간 단위다. 이를 자식이 소비한 CPU 시간이나 메모리 전체로 해석하지 않는다. 회수 순서와 종료 순서가 다른 모형이다.

별도 단일 자식의 정지/재개 관찰 모형에서 WUNTRACED를 둔 조회가 WIFSTOPPED 참을 반환해도 자식은 종료한 것이 아니다. 이후 WCONTINUED 통지를 보고 마지막 정상 종료나 신호 종료를 회수해야 수명 장부에서 제거한다. 아래에서는 ptrace, 경쟁 회수자, 자동 회수와 고아 인계는 제외한다. waitid의 성공 0과 waitpid의 WNOHANG 0도 같은 인터페이스 결과로 섞지 않는다.

끝난 실행과 남겨 둔 영수증

자식이 종료하면 코드를 더 실행하지 않지만 부모가 결과를 회수할 수 있도록 PID·종료 상태·자원 사용 등 최소 관리 정보가 잠시 남을 수 있다. 이 상태가 좀비이다. 좀비는 CPU를 계속 쓰는 실행 루프도, 전체 작업 메모리를 그대로 가진 활성 프로그램도 아니다. 그러나 관리 슬롯을 차지하므로 대량 누적은 문제를 만든다.

이 단원의 좀비 시간선은 부모가 살아 있고 SIGCHLD를 명시적으로 SIG_IGN으로 설정하거나 SA_NOCLDWAIT를 쓰지 않는 기본 경우이다. 그런 설정은 자식을 자동 정리할 수 있어 설명이 달라진다. 부모 종료 시 자식의 인계와 subreaper도 별도이다. 한 시간선을 모든 종료 상황으로 일반화하지 않는다.

어느 자식을 기다릴지 정하기

waitpid(pid,&status,0)에서 양수 pid는 그 자식을 대상으로 하며, −1 은 임의 자식을 대상으로 한다. 이미 대상 자식이 종료해 회수 가능한 상태라면 바로 반환할 수 있다. 대상이 아직 실행 중이면 기본 호출은 기다릴 수 있으며 신호로 중단되어 EINTR가 되면 처리 방침에 따라 다시 시도해야 한다.

WNOHANG을 넣고 대상 자식이 존재하지만 아직 회수할 상태가 없으면 0 을 반환한다. 이는 종료 상태 0 이 아니다. 양수 반환일 때 반환 PID와 저장 status를 살펴보고, −1 이면 오류를 확인한다. 기본 options0 은 종료를 대상으로 하며 정지/재개 관찰은 추가 옵션과 상태 종류가 필요하다.

종료 상태의 종류를 먼저 확인하기

WIFEXITED(status)가 참일 때만 WEXITSTATUS(status)를 읽어 정상 종료의 하위 8 비트 상태를 얻는다. _exit(300)은 이 경로에서 44 를 남긴다. 정상 종료라는 말은 프로그램 목적이 성공했다는 뜻이 아니라 exit·_exit·main 반환 형태로 끝났다는 분류이다. 상태 0 성공 관례는 프로그램이 정한 의미와 함께 해석한다.

WIFSIGNALED(status)가 참이면 WTERMSIG(status)로 종료를 일으킨 신호를 읽는다. 신호 9 로 죽은 경우의 9 와 정상 _exit(9)의 9 는 숫자가 같아도 종류가 다르다. 셸이 보여 주는 128+신호 같은 표현을 raw wait status나 WEXITSTATUS로 바로 취급하지 않는다. 상태 int를 직접 비트 이동해 해석하기보다 제공된 매크로 조건을 지킨다.

정지 통지를 종료로 잘못 처리한 경우

별도 C는 t=1에 정지 통지, t=2에 재개 통지, t=5에 정상 종료 상태 0을 내고 즉시 회수된다. 장부를 언제 지우는가?

힌트 1

일반 메모리 복사본·stdio 복사본·열린 설명의 공유 커서·descriptor별 플래그를 네 종류로 나눈다.

힌트 2

종료 결과의 생성 경로와 wait의 종류/값을 구별하고, 미회수 수를 가상 시간 구간별로 센다.

풀이와 답 확인

  1. P의 x는 5, C의 x는 20이다. C는 AB를 받고 P는 C를 받아 O 위치는 3이다. C _exit는 stdio를 flush하지 않으므로 이전 Q는 부모가 한 번 전달한다.

  2. argc는 4이며 각 문자열은 배열의 한 항목이다. exec 성공은 같은 PID의 이미지 교체이고 fd 3만 닫혀 4는 유지된다.

  3. 정상 종료 127은 exec 반환 실패의 _exit(127)과 성공한 프로그램 자체의 exit(127)에서 모두 가능하여 원인이 미확정이다.

  4. A는 정상 1과 미회수 길이 5, B는 신호 15와 길이 2다. 구간별 수 1/2/1의 면적은 2+4+1=7 process·가상 시간 단위다.

  • 두 변수 복사본과 하나의 커서, 버퍼 flush와 fd close를 구별한다.
