소단원 2.1

라이브러리 함수와 시스템 호출

함수 호출 모양이 같으면 운영체제도 같은 일을 할까?

준비 개념과 학습 목표

준비 개념

  • 함수 계약: 입력과 전제조건, 반환값, 부작용을 함께 정한 약속이다. 반환값 0을 성공이라고 볼 수 있는지는 함수마다 다르다.
  • 사용자 공간과 커널: 응용 계산이 진행되는 영역과 운영체제가 보호된 자원을 관리하는 영역을 구별한다. 함수 이름만으로 경계 통과 횟수를 세지 않는다.
  • 바이트와 항목: 1바이트는 여기서 8비트다. 2바이트 항목 3개는 6바이트이며 항목 수 3과 바이트 수 6은 다른 단위다.

학습 목표

  • 함수/API와 실제 커널 진입을 구별한다.
  • 반환값 단위와 버퍼 조건을 명시한다.
  • 작은 자체 버퍼 모형의 호출·전송·지속성을 따로 추적한다.

인터페이스와 구현을 나누기

라이브러리는 프로그램이 호출할 함수와 자료 구조를 제공한다. 시스템 호출은 커널의 보호된 서비스에 진입하는 인터페이스다. Linux에서 보통 C 라이브러리 wrapper를 거쳐 호출하므로 C 함수 호출처럼 보여도 커널 진입이 포함될 수 있다. 반대로 순수 사용자 공간 계산만 하는 라이브러리 함수도 있다. API는 관찰할 의미의 계약이고 실제 ABI는 인자와 호출 번호를 전달하는 기계 수준 규칙이다.

응용이 라이브러리 함수를 한 번 불렀다고 커널 진입도 꼭 한 번이라는 등식은 성립하지 않는다. 구현은 데이터를 모으거나 여러 하위 호출을 수행할 수 있다. 성공·실패 값 역시 API 문서를 읽어야 한다. 이 단원은 C 라이브러리 인터페이스를 설명하며, 커널의 raw 반환값을 응용의 errno 규칙과 그대로 동일시하지 않는다.

자료의 단위와 상태를 정하기

fwrite(ptr,size,n,stream)은 size바이트 항목 n개를 쓰는 인터페이스이며 반환값은 완전한 항목의 수다. size=1일 때에만 그 수를 바이트 수로 곧바로 읽을 수 있다. 충분히 큰 유효 버퍼와 올바른 stream을 제공해야 하며 size×n이 실제 표현 범위를 넘지 않는지도 구현에서 확인한다. read/write 계열의 바이트 수 계약과 단위를 섞지 않는다.

비교를 위해 실제 stdio와 별개인 자체 B8 버퍼를 정의한다. 상태는 대기 바이트열 Q이며 처음 비어 있고 용량은 8바이트다. put2는 정확히 2바이트 항목 하나를 Q 뒤에 추가해 성공1을 반환한다. 이번 모형에서는 Q 길이가8이 되면 lower_write로 전부 전송한 뒤 Q를 비운다. flush는 남은 Q가 비어 있지 않을 때 전송하고 비운다. 모든 lower_write는 요청 전체를 수락하며 실패와 병렬 접근은 제외한다.

성공이라는 관찰의 범위

B8의 put2 성공은 항목이 라이브러리의 대기열에 수용됐다는 뜻이다. lower_write 성공은 이 모형의 하위 전송 계약이며 전원 장애 뒤의 지속성까지 정하지 않았다. 실제 프로그램도 라이브러리 버퍼, 커널 버퍼, 저장장치의 상태가 서로 다를 수 있다. 필요한 보장은 stream flush와 파일 동기화 등 각 층의 계약으로 따로 정한다.

실제 시스템 호출은 버퍼 권한과 파일 descriptor의 권한 등을 검사할 수 있지만, 잘못된 프로그램 메모리 접근의 모든 오류가 친절한 반환값으로 바뀐다고 기대하면 안 된다. 플랫폼마다 API/ABI와 처리 규칙이 다르다. 아래 계산은 B8 규칙의 추적이며 Windows에서 Linux 호출을 실행한 결과나 특정 libc의 버퍼 크기를 관측한 결과가 아니다.

중간 과정을 따라가는 예제

초기 Q가 빈 B8에서 2바이트 항목 [AB],[CD],[EF],[GH],[IJ]를 순서대로 put2하고 마지막에 flush한다. 각 항목은 문자 이름의 바이트 두 개라는 가상 표기이며 실제 문자 인코딩은 사용하지 않는다. put2 횟수, 하위 전송 횟수와 전송량을 구하라.

  1. 첫 세 put2 뒤 Q는 AB, ABCD, ABCDEF로 길이2,4,6이다. 세 호출 모두 항목 성공1이지만 lower_write는 아직0회다.
  2. 네 번째 put2는 Q=ABCDEFGH, 길이8을 만들고 이를 전송한다. lower_write1회/8바이트이며 이후 Q는 빈 열이다.
  3. 다섯 번째 put2 뒤 Q=IJ, 길이2다. 이 순간 항목 호출5회, 하위 전송1회, 전달8바이트/대기2바이트다.
  4. flush가 IJ를 전송하고 Q를 비운다. 하위 전송 총2회/10바이트다. 항목 성공 수는5이고 이를 바이트로 바꾸면5×2=10이다.

put2 5회, flush 1회, lower_write 2회, 전달10바이트다. 성공 수·함수 호출 수·하위 전송 수·지속 기록은 서로 다른 관찰이다.

종이와 본문으로 직접 해보기

같은 B8에서 항목3개만 넣고 flush 없이 중단하면 Q와 lower_write 횟수는? 실제 fwrite의 size=2,n=3에서 반환3은 무엇의 수인가?

힌트 보기

2바이트씩 쌓지만8에 도달했는지 먼저 확인한다. API의 반환 단위를 읽는다.

풀이 보기

Q는6바이트, lower_write0회다. 자체 모형의 put2 성공만으로 하위 전송을 주장할 수 없다. fwrite 반환3은 완전한 항목3개이며 요청 자료는6바이트다.

오해와 반례

라이브러리 함수가 성공하면 시스템 호출이 정확히 한 번 일어나고 자료는 영구 저장된다.

B8의 첫 put2는 성공1이지만 하위 전송은0회다. 다섯 항목도 전송2회다. 전원후 보존은 이 모형에서 정의하지 않았으므로 성공으로부터 유도할 수 없다.

한 단계 더

심화: B8의 모든 성공 경로에서 총 추가 바이트 A=하위에 전달한 바이트 L+현재 대기 길이 |Q|라는 보존식을 증명하자. 처음0=0+0이다. 추가는 A와 |Q|를2씩 늘리고, 전송은 L을 |Q|만큼 늘린 뒤 Q를0으로 만들어 등식을 유지한다. 실패·부분 전송을 추가한다면 실제로 전달된 수만 L에 더하고 잔여 열을 유지해야 한다. 이 불변식은 전송량의 증명이지 지속성·동시안전·실제 성능의 증명이 아니다.

소단원 2.2

errno와 재시도

오류 표시가 남아 있으면 방금 한 일도 실패한 것일까?

준비 개념과 학습 목표

준비 개념

  • 반환값: 함수가 호출자에게 돌려주는 값이다. read/write의 양수는 진행한 바이트 수, −1은 오류이며 일반 파일의 양수 길이 read에서0은 EOF를 뜻한다.
  • 진행량 p: 처음부터 확실히 전송한 접두부의 길이다. 전체 길이 N이라면 미전송 범위는[p,N)이고 남은 길이는 N−p다.
  • 재시도: 같은 목적을 다시 수행하는 정책이다. 이미 발생한 부작용과 미수행 부분을 구별해야 중복을 막는다.

학습 목표

  • 실패 반환과 errno를 함께 해석하고 즉시 보존한다.
  • EINTR와 양수 부분 I/O를 구분한다.
  • 완료·부분 실패·일시 대기 상태의 계약을 정한다.

먼저 반환값, 다음에 오류 정보

errno는 특정 함수가 실패한 이유를 전달하는 정수형 오류 표시이며 Linux/C 환경에서는 스레드별이다. 먼저 그 API의 실패 반환을 확인한 후 의미를 읽는다. 성공 호출 뒤 남은 errno는 그 호출의 실패 증거가 아니다. 예를 들어 이전 ENOENT가 남아 있어도 read가3을 반환하면 이 호출에서3바이트를 읽은 성공이다. 실제 코드에서는 오류 이름 EINTR처럼 심볼을 쓰고 고정 번호를 다른 플랫폼에 옮기지 않는다.

실패 직후 int saved=errno처럼 원인을 보존한 다음 로그나 해제를 수행한다. 다른 함수가 errno를 바꿀 수 있기 때문이다. 모든 함수가−1을 실패로 쓰는 것은 아니고 errno를 쓰지 않는 인터페이스도 있다. getpriority처럼−1도 성공 가능한 계약에서는 호출 전 errno=0 등 문서가 정한 추가 판별을 따른다. 보존한 원래 실패와 후속 정리 실패를 따로 보고할 수 있다.

부분 진행을 버리지 않는 반복

Linux read/write는 요청보다 작은 양수를 정상 반환할 수 있다. 신호가 자료를 옮기기 전에 중단하면−1/EINTR, 일부 전송한 뒤면 그 진행량을 반환하는 계약을 구별한다. 후자의 양수에 대해 p를 늘리고 잔여 부분만 요청해야 한다. 비차단 EAGAIN/EWOULDBLOCK은 준비 대기와 정책을 요구하며 CPU를 무한히 바쁘게 하는 즉시 반복의 면허가 아니다.

자체 전송 절차 W(N)를 완전히 정의하자. 유효 버퍼 길이 N≥0, p=0, 한 호출의 요청 길이는 N−p이고 자료는[p,N)이다. N>0이면 표현 가능하고 API 허용 크기 이하로 정하며 단일 호출자·일반적인 버퍼 I/O·버퍼 수명/내용 고정·연결 유효를 가정한다. 반환 r>0이면 r≤N−p를 확인하고 p←p+r다. −1/EINTR이면 오류를 보존한 후 p를 유지하고 재시도한다. 다른 오류면(p,원인)으로 실패, 남은 양수 요청에서 r=0이면 무진행 실패로 종료한다. p=N이면 완료다. N=0이면 호출 없이 완료한다. 이 종이 절차는 호출이 정상 반환하거나 오류 반환을 보고한다고 정한다. 실제 파이프·소켓 쓰기에서는 SIGPIPE의 기본 동작으로 프로세스가 종료될 수 있어, 신호를 처리·차단·무시하는 별도 정책 없이는 항상 반환값을 받는다는 가정을 쓸 수 없다.

모든 호출을 같은 방식으로 재시도하지 않기

W는 성공한 접두부를 취소하지 않는다. 일부 뒤 실패하면 p>0인 부분 실패이며 처음부터 전체 요청을 다시 보내면 중복할 수 있다. 실제 외부 서비스의 요청은 저장·결제 같은 부작용이나 결과 불확실성을 포함하므로 바이트 전송 정책만으로 전체 요청 재실행의 안전을 증명할 수 없다. 직접 I/O 등 오류여도 부분 효과가 가능한 별도 계약은 W의 가정 밖이다.

close 재시도는 read/write의 EINTR 처리와 별개다. Linux는 유효 descriptor를 닫는 과정에서 일찍 번호를 해제하므로 오류 뒤 같은 번호를 다시 close하면 재사용된 다른 자원을 닫을 수 있다. Linux의 close 실패는 진단하고 무조건 재호출하지 않는다. POSIX.1-2008의 EINTR 상태는 미지정이었고, 실제 읽은 Linux 문서는 POSIX.1-2024가 EINTR에서 열림을 유지하는 다른 계약을 표준화했다고 설명한다. 따라서 목표 플랫폼·버전의 계약을 정해야 한다. 재시도는 함수마다 판단한다.

중간 과정을 따라가는 예제

W(7)에 주어지는 반환 이력은3,−1/EINTR,2,2다. 이는 실제 호출 로그가 아니라 정의한 종이 입력이다. 진행량과 매번 요청할 자료 범위를 구하라.

  1. 처음 p=0, [0,7)을 요청한다. 반환3이면 p=3, 이미 전달한 범위는[0,3)이다.
  2. 다음 요청은[3,7), 길이4다. −1/EINTR의 원인을 즉시 saved에 보존하고 p=3을 유지한다. 전송 전 중단이라는 가정이다.
  3. 같은[3,7)을 다시 요청해2를 받으면 p=5다. 아직 필요한 것은[5,7), 길이2다.
  4. 마지막 반환2로 p=7=N이 되어 완료한다. 호출4회, 실제 진행3+0+2+2=7바이트다. errno의 옛 EINTR만 보고 마지막 성공을 실패라고 바꾸지 않는다.

요청 길이7,4,4,2와 진행량0→3→3→5→7이다. 최종 완료는 바이트 수 계약이며 지속 기록이나 원격 처리 성공은 증명하지 않는다.

한 단계 더

심화: W의 불변식은0≤p≤N이며 전달한 접두부가 원자료[0,p)라는 것이다. 양수 반환은 새 접두부를 정확히 연장하고 EINTR는 이를 보존한다. 모든 오류 없는 성공 호출이 적어도1바이트를 진행하고 EINTR 횟수가 유한하며 호출마다 반환한다면 양수 호출은 최대 N회이므로 종료한다. 이 충분조건은 장치가 반드시 응답하거나 실시간 마감을 지킨다는 보장이 아니다. 읽기의 정확한 N바이트 수집은 EOF를 별도 결과로 처리해야 하며, 일반 파일의 양수 요청 read0과 count0의 반환0을 혼동하지 않는다.

소단원 2.3

자원 획득·해제 규칙

번호를 복사하면 파일도 두 개 생기고 해제 책임도 두 개 생길까?

준비 개념과 학습 목표

준비 개념

  • 자원: 사용 중 관리가 필요한 파일 descriptor, 메모리, 잠금 등이다. 종류마다 획득과 해제의 짝이 다르다.
  • 소유권: 누가 해제할 책임과 권한을 갖는지 정하는 프로그램의 계약이다. 정수 값을 복사한 것만으로 책임을 새로 만들지 않는다.
  • 수명: 유효하게 사용할 수 있는 시간 구간이다. 빌린 자원은 소유자가 허용한 범위 안에서만 쓰며 그 안에 해제되어서는 안 된다.

학습 목표

  • 실패한 획득과 성공한 획득을 구분한다.
  • 별칭·실제 복제·소유권 이동의 책임을 명시한다.
  • 모든 종료 경로의 정리를 상태표로 검증한다.

성공한 획득부터 책임이 생긴다

open이 실패하면 descriptor를 얻지 못했고 close할 새 자원도 없다. 성공하면 반환된 비음수 번호를 얻는다. 성공 번호가0일 수도 있으므로 fd>0이 아니라 문서의 fd≥0 조건으로 확인한다. 이 단원은 한 스레드에서 소유자의 명시적 해제까지 descriptor가 유효하다고 가정한다. 파일 내용을 지우는 unlink와 열어 둔 descriptor를 해제하는 close도 같은 일이 아니다.

프로그램의 책임을 상태로 기록하자. absent는 획득한 자원이 없음, owned는 자신이 해제할 책임이 있음, moved는 다른 소유자에게 책임을 넘김, released는 종료한 책임이다. absent에서 획득 성공만 owned로 옮기고 실패면 absent를 유지한다. owned를 정리한 뒤 다시 해제하지 않으며 moved의 원 소유자도 해제하지 않는다. 이 이름은 자체 소유권 모형이지 운영체제의 실제 상태 enum이 아니다.

같은 번호의 별칭과 새로운 descriptor

fd=3의 정수값을 다른 변수에 복사해 g=3으로 만드는 것은 같은 descriptor의 별칭이다. close할 책임을 변수마다 하나씩 새로 만들면 이중 close가 된다. 반면 dup의 성공은 다른 descriptor를 만들고 두 descriptor가 같은 open-file description을 참조할 수 있다. 이때 각 descriptor의 해제 책임은 별개이며 공유된 파일 offset과 underlying 객체 수명은 다시 구분한다.

빌림은 소유권 이동이 아니다. 빌린 함수가 fd를 사용할 동안 소유자는 그 사용과 충돌하는 해제를 하지 않는다는 계약이 필요하고, 빌린 함수는 별도 허가 없이 close하지 않는다. 책임을 넘기는 move는 실제 언어 기능 없이 문서로도 정할 수 있지만, 성공/실패 때 누가 책임을 유지하는지 명시해야 한다. 다중 스레드에서 숫자 재사용은 더 복잡하므로 여기의 단순 상태 증명만으로 동시안전을 주장하지 않는다.

정리 경로와 오류의 분리

자원 F 다음 G를 획득하는 절차를 정의하자. F 실패면 곧바로 반환한다. F 성공/G 실패면 원래 실패 이유를 보존하고 F만 정리한다. 둘 다 성공하면 작업 뒤 G,F 순서로 각 책임을 정리한다. 여기서는 G가 F에 의존할 수 있으므로 역순을 택한다. 모든 종류의 자원이 항상 같은 순서를 요구하는 것은 아니며 잠금·메모리 등은 해당 API의 짝과 종속 관계를 확인한다.

Linux의 유효 owned descriptor 정리는 close 결과를 확인하고 자신의 번호 보관을 무효 상태로 바꾸며 실패 원인을 별도로 보고한다. close 실패했다고 owned를 그대로 두고 나중에 다시 close하는 전략은 Linux의 번호 재사용과 충돌한다. EBADF는 애초 유효성 불변식이 깨졌음을 뜻하는 경우이며 이를 정상 성공으로 덮지 않는다. 다른 플랫폼의 EINTR 계약은 따로 적용한다. 정리 호출 성공도 파일의 내구성·응용 작업 성공과 별개의 계약이다.

중간 과정을 따라가는 예제

초기 F/G absent다. acquire F가 번호0을 반환하고 acquire G가−1/EACCES를 반환한다. 이후 F의 Linux close는0을 반환한다. 단일 스레드이며 다른 사용자는 없고 이력을 그대로 가정한다. 소유 상태와 보고할 오류를 구하라.

  1. F의0 반환은 성공이다. F absent→owned(0)이며 close 책임은 하나다. G는 아직 absent다.
  2. G의 실패 뒤 EACCES를 saved에 즉시 보존한다. G는 absent이므로 G를 해제하지 않는다.
  3. F가 owned이므로 close(0)를 한 번 호출해 성공을 확인한다. F는 released로 바뀌고 번호 보관을 무효화한다.
  4. 정리가 끝났어도 G 획득 실패를 성공으로 바꾸지 않는다. 최종 F released/G absent, 주 결과 실패 EACCES, 새 자원 책임0개다.

F 번호0을 유효 성공으로 처리하고 F만1회 정리한다. 최종 실패 EACCES를 유지한다. 이력은 종이 입력이며 실제 표준입력 descriptor를 닫지 않았다.

오해와 반례

획득 성공은 양수로만 확인하고 번호를 복사한 변수마다 해제하면 된다.

한 단계 더

심화: 획득 성공 횟수를 A, 성공적으로 책임을 다른 소유자에게 넘긴 수를 M, 책임을 종료 처리한 수를 R이라 하면 이 절차의 현재 단독 소유 책임 O=A−M−R이다. 각 성공 획득은 O를1 늘리고 move와 정리는 각각1 줄인다. 이를 경로별로 증명하면 정상·오류 출구 O=0을 검사할 수 있다. 여기서 R은 소유권 계약상 종료 처리이며 저장 성공 수가 아니다. Linux close 실패의 진단도 책임 종료와 함께 기록한다. 메모리 free나 타 플랫폼 close에는 그 종류의 실패/해제 규칙을 다시 지정해야 한다.
