소단원 12.1

mmap과 파일 매핑

파일을 매핑하면 읽기 위치와 데이터의 수명을 어떻게 관리할까?

준비 개념과 학습 목표

준비 개념

  • 바이트와 파일 모드

  • with 문맥관리자

  • 파일 오프셋

학습 목표

  • 매핑 길이와 인덱스 범위를 확인한다.

  • 읽기 권한·정렬·플랫폼 조건을 기록한다.

  • 파일·매핑·임시 자료의 수명을 차례로 정리한다.

파일 바이트를 주소 범위로 연결한다

mmap은 파일의 일부 또는 전체를 메모리처럼 접근할 수 있는 객체로 연결한다. 매핑 내부 인덱스 i가 파일 offset+i에 해당한다. 생성자의 길이와 offset은 바이트 단위다. Python에서 length=0은 생성 시 파일 크기를 쓰는 방식이며, 빈 파일 등 플랫폼 조건을 확인해야 한다.

매핑 offset은 요구되는 ALLOCATIONGRANULARITY의 배수여야 한다. Unix에서는 이 값이 PAGESIZE와 같지만 Windows에서도 같다고 가정하지 않는다. 아래는 offset을 생략하여 0으로 두고, 먼저 여섯 바이트 파일을 만들어 환경별 빈 파일·부분 매핑 정렬 문제를 줄인다. 파일 생성과 매핑은 실제로 자원을 쓰므로 실패 예외도 생길 수 있다.

인덱스와 읽기 권한을 확인한다

Python mmap 객체의 한 바이트 인덱싱은 정수를 반환하고 슬라이스는 bytes를 반환한다. 여섯 바이트 ABCDEF의 인덱스 1은 B의 코드 66, 슬라이스 [1:4]는 BCD다. 슬라이스의 끝 4는 포함하지 않는다. 접근 단위가 문자열 글자가 아닌 바이트라는 점을 먼저 정한다.

ACCESS_READ에서는 바이트 쓰기가 TypeError다. 유효한 단독 인덱스는 0부터 5이며 mm[6]은 IndexError다. 모든 범위 밖 슬라이스가 같은 예외를 내는 것은 아니므로 인덱스와 슬라이스 규칙을 구별한다. 텍스트 파일의 UTF-8 한 글자는 여러 바이트일 수 있다.

import mmap
import tempfile
from pathlib import Path

with tempfile.TemporaryDirectory(prefix="map-lesson-") as folder:
    path = Path(folder) / "sample.bin"
    path.write_bytes(b"ABCDEF")
    with path.open("r+b") as f:
        with mmap.mmap(f.fileno(), 0, access=mmap.ACCESS_READ) as mm:
            print(mm[1], mm[1:4])
            try:
                mm[0] = ord("Z")
            except TypeError:
                print("read-only")
            try:
                print(mm[6])
            except IndexError:
                print("out-of-range")
    print(path.read_bytes())

매핑과 파일의 수명을 따로 끝낸다

안쪽 with가 매핑을 닫고 다음 with가 파일을 닫는다. mmap.close가 열어둔 파일까지 닫아 주는 것은 아니다. 임시 디렉터리 문맥이 마지막에 끝나며 이 실습에서 만든 파일도 제거한다. 실행 종료 뒤 남은 매핑 참조를 다시 사용하려 하지 않는다.

저장·실행을 해 보려면 코드를 map_read.py로 저장하고 터미널에서 python map_read.py를 실행한다. Python 3의 표준 라이브러리만 필요하며 웹 화면에서 종이로 출력을 예측해도 된다. 설치된 OS가 mmap을 지원해야 한다. 예상 출력과 저자가 실제 확인한 출력 범위를 아래에 구별해 기록한다.

중간 과정을 따라가는 예제

본문 코드를 따라 인덱스·슬라이스·두 예외와 마지막 파일 바이트를 적어라.

  1. mm[1]은 ASCII B의 정수 66, mm[1:4]는 b'BCD'이므로 첫 출력은 66 b'BCD'다.

  2. 읽기 전용에 Z를 쓰려 하면 TypeError를 받아 read-only를 출력한다. 파일과 매핑 내용은 여전히 ABCDEF다.

  3. mm[6]은 길이 6의 바로 다음 인덱스라 IndexError를 받아 out-of-range를 출력한다.

  4. 두 자원 문맥을 닫은 뒤 path.read_bytes()는 b'ABCDEF'다. 저자는 본문 코드를 실제 Python에서 실행해 이 네 줄을 확인했다.

실제 출력은 66 b'BCD', read-only, out-of-range, b'ABCDEF'의 네 줄이다. 이 작은 접근 확인은 속도·장애 상황 전체 검증이 아니다.

오해와 반례

소단원 12.2

공유·비공유 매핑

매핑에서 Z로 바꾼 값이 파일에도 남는지 무엇이 결정할까?

준비 개념과 학습 목표

준비 개념

  • mmap 접근 모드

  • 파일 바이트

  • 자원 문맥과 flush

학습 목표

  • READ/WRITE/COPY의 쓰기 약속을 비교한다.

  • private copy를 처음부터 전체 복사라는 뜻과 구별한다.

  • 파일 반영·동기화·지속성을 다른 질문으로 다룬다.

접근 모드가 변경의 대상을 정한다

ACCESS_COPY는 매핑의 사본에 쓰지만 underlying file은 갱신하지 않는다. ACCESS_WRITE는 변경을 파일에 반영하는 방식이다. READ는 쓰기를 거부한다. Unix에서 MAP_PRIVATE의 copy-on-write와 MAP_SHARED의 공유 연결을 이해할 수 있지만 Python의 이식 가능한 access 옵션과 Unix flags를 중복 지정하지 않는다.

private는 각 프로세스가 보는 변경을 별도로 만드는 정책이다. 항상 생성 순간 파일 전체를 독립 RAM에 복사한다는 뜻은 아니다. 변경하지 않은 페이지의 물리 공유와 변경 뒤 독립 페이지의 사용은 OS의 구현·정책에 따라 이뤄진다. 공유 매핑이라고 모든 사용자 코드의 읽기·쓰기 순서가 자동으로 안전해지는 것도 아니다.

같은 파일을 사본과 쓰기 방식으로 따로 다룬다

새 파일 ABCDEF에서 COPY 매핑의 인덱스 0을 Z로 바꾸면 매핑은 ZBCDEF지만 닫고 다시 읽은 파일은 ABCDEF다. 다음에 WRITE 매핑의 인덱스 1을 Y로 바꾸면 그 매핑과 파일은 AYCDEF다. 첫 COPY 변경 Z가 파일에 전달되지 않았으므로 두 번째 결과의 첫 글자는 A다.

본문은 두 문맥을 순서대로 실행한다. 동시 매핑이나 여러 프로세스의 중간 관측을 시험하는 코드는 아니다. 실제 실행하여 확인한 것은 이 임시 파일의 최종 바이트와 출력이다. 공유 경쟁·파일시스템 장애·전원 손실까지 확인했다고 확대하지 않는다.

import mmap
import tempfile
from pathlib import Path

with tempfile.TemporaryDirectory(prefix="map-modes-") as folder:
    path = Path(folder) / "sample.bin"
    path.write_bytes(b"ABCDEF")
    with path.open("r+b") as f:
        with mmap.mmap(f.fileno(), 0, access=mmap.ACCESS_COPY) as mm:
            mm[0] = ord("Z")
            print("copy", mm[:])
    print("file", path.read_bytes())
    with path.open("r+b") as f:
        with mmap.mmap(f.fileno(), 0, access=mmap.ACCESS_WRITE) as mm:
            mm[1] = ord("Y")
            mm.flush()
            print("write", mm[:])
    print("file", path.read_bytes())

반영과 서로 기다리는 절차는 별개다

WRITE 예제는 mm.flush()로 매핑 변경의 파일 반영을 요청한다. flush가 잠금이나 프로세스 사이 순서 제어를 대신하지 않는다. 파일의 최신 바이트를 보았다는 관찰을 전원 손실 뒤에도 같은 데이터가 남는다는 저장장치 지속성 검증으로 바꾸지 않는다.

여러 실행자가 같은 구조를 바꾸면 잠금·원자적 연산·프로토콜처럼 동기화 설계가 필요하다. 공유 여부는 누가 같은 데이터를 보게 될지 정하고 동기화는 어떤 순서로 안전하게 사용할지 정한다. 이 절의 설치 없는 활동은 각 모드의 결과를 종이에 구별하는 것이다.

중간 과정을 따라가는 예제

본문 COPY 후 WRITE 코드의 네 출력 줄과 마지막 파일을 구하라.

  1. COPY에서 mm[0]=Z 뒤 첫 출력은 copy b'ZBCDEF'다. 매핑을 닫고 파일을 읽으면 file b'ABCDEF'다.

  2. 그 파일로 새 WRITE를 만든다. 인덱스 1을 Y로 바꾸고 flush 뒤 write b'AYCDEF'를 출력한다.

  3. WRITE와 파일을 닫은 뒤 마지막 출력은 file b'AYCDEF'다. COPY의 Z는 이 파일에 저장되지 않았다.

  4. 저자는 이 순서를 실제 Python에서 실행하고 네 출력·마지막 파일과 임시 디렉터리 제거를 확인했다.

copy ZBCDEF / file ABCDEF / write AYCDEF / file AYCDEF의 네 bytes 출력이다. COPY 변경이 다음 WRITE 입력에 섞이지 않는다.

종이와 본문으로 직접 해보기

종이 변형으로 COPY에서는 인덱스 2를 X, WRITE에서는 인덱스 3을 W로 바꾼다. 각 매핑 결과와 마지막 파일을 적어라.

힌트 보기

WRITE는 COPY 사본이 아니라 변경되지 않은 파일을 다시 매핑한다.

풀이 보기

COPY 매핑은 ABXDEF지만 파일은 ABCDEF다. WRITE 매핑은 ABCWEF이고 마지막 파일도 ABCWEF다. 이 변형은 손 추적이며 실제 실행한 본문 사례와 구별한다.

오해와 반례

COPY 매핑에서 바뀐 사본을 flush하면 WRITE처럼 모든 변경이 원래 파일에 저장된다.

COPY의 약속은 underlying file을 갱신하지 않는 것이다. 이 모드를 선택한 뒤 flush를 파일 저장 방식 변경으로 해석하지 않는다. 파일에 새 결과를 저장하려면 별도의 허용된 쓰기 절차를 설계한다.

실제 확인한 AYCDEF가 전원 손실 지속성 테스트인가?

답과 이유 보기

자원 제한과 누수 진단

제한은 자원마다 다르다

Unix Python resource는 getrlimit으로 soft/hard 쌍을 읽는다. soft는 현재 한계이며 hard를 넘길 수 없다. hard를 올리는 데는 권한과 시스템 조건이 필요하다. RLIMIT_AS는 주소 공간 바이트, NOFILE은 파일 descriptor 관련 제한이다. CPU시간·파일 크기·스택 같은 자원도 따로다. 모든 시스템에 같은 기호·효과가 있는 것은 아니다.

이 모듈은 Unix 전용이므로 Windows에서 import resource가 된다고 가정하지 않는다. 여기서는 실제 제한을 낮추거나 한계를 고갈시키는 실험을 수행하지 않는다. 제한을 높이면 누수가 사라지는 것이 아니라 실패가 늦춰질 수 있다. 사용 중인 다른 프로세스의 한계를 바꾸지 않고 자기 시험 프로세스의 읽기부터 계획한다.

관측값의 의미와 반복 단위를 정한다

가상 크기·현재 RSS·최대 RSS는 서로 다른 값이다. Linux /proc의 maps는 매핑 범위·권한, smaps는 각 매핑의 RSS/PSS 등을 보여 준다. PSS는 공유 페이지를 비례 배분한다. fd 디렉터리는 열린 descriptor 목록이며 status의 FDSize는 할당된 slot 수라 현재 열린 개수와 같은 숫자라고 사용하지 않는다.

같은 요청을 여러 번 처리하고 요청 전·후·정리 후를 비교한다. 처음 한 번의 상승은 런타임 초기화나 cache일 수 있다. 반복마다 정리 후에도 동일 자원이 계속 남는지, 입력 크기와 작업 결과가 같은지 확인한다. RSS는 allocator가 OS에 바로 돌려주지 않으면 살아 있는 사용자 객체를 해제해도 즉시 떨어지지 않을 수 있어 숫자 하나만으로 소유자 누수를 증명하지 않는다.

소유자와 실패 경로를 추적한다

파일을 연 함수가 닫을 책임이 있는지, 호출자에게 소유권을 넘기는지 정한다. map·file·임시 자료도 각각 해제한다. 성공 경로만 닫고 예외 경로에 남기는 누수는 반복 실패에서 드러날 수 있다. 문맥관리자는 해제 시점을 표현하지만 모든 외부 자원과 살아 있는 참조를 자동으로 찾는 도구는 아니다.

Linux status의 RSS 회계는 비동기여서 정확하지 않을 수 있고 smaps 읽기는 더 자세하지만 비용·동시 갱신을 고려한다. 최대값은 현재값으로 떨어지는 지표가 아니다. 환경·PID·측정 시점·단위·시험 입력·자원 소유자를 함께 기록해야 실험을 재현한다. 아래 숫자는 가상 진단 표이며 실제 Linux나 Windows 측정이 아니다.

중간 과정을 따라가는 예제

가상 로그에서 시작할 때 열린 descriptor는 20개다. 요청마다 파일 2개를 열고 1개만 닫는다. 요청 5회 후와 남은 파일을 모두 정리한 뒤의 수를 구하라. 별도 현재 RSS가 100 → 108 → 108 MiB, 최대 RSS가 110 MiB인 기록은 어떻게 읽을까?

  1. 요청당 순변화는 +2 − 1 = +1이다. 5회 후에는 20 + 5 = 25개다. 남은 요청 파일 5개를 닫으면 시작할 때의 20개로 돌아간다. 파일의 소유자가 요청마다 하나씩 닫지 않았다는 가정의 누수다.

  2. 요청에서 연 파일 두 개를 모두 닫도록 고친 모델은 +2 − 2 = 0이므로 매번 정리 뒤 20개다. 예외 경로에도 같은 해제 규칙을 적용해야 한다.

  3. 현재 RSS가 100에서 108 MiB로 올라간 뒤 다음에도 108 MiB라는 사실만으로 요청당 8 MiB 누수라고 판단할 수 없다. cache, allocator, 다른 작업을 추가 조사한다.

  4. 최대 RSS 110 MiB는 이전 최고치다. 현재 108 MiB와 모순되지 않는다. 현재값을 최고치로 대신하지 않는다.

불완전한 정리 모델은 25개다. 남은 5개까지 정리하면 20개다. RSS를 해석하려면 반복 추세와 자원 소유자에 대한 근거가 필요하다.

종이와 본문으로 직접 해보기

요청당 순변화가 0이므로 12개다. soft 256은 hard 128을 넘어 유효한 제한 쌍이 아니다. 숫자는 Unix API 개념의 종이 모델이며 실제 setrlimit은 실행하지 않았다.

오해와 반례

RSS가 한 번 올랐으므로 누수이며 한계를 올리면 원인이 해결된다.

현재 RSS, 최고치, 공유, cache와 자원 소유자의 누수를 구별한다. 반복 정리 뒤에도 자원이 남는 흐름을 추적하고 소유와 해제를 고친다. 한계를 올리는 것은 해제 누락을 없애지 않는다.

한 단계 더

진단 계획에는 누적 요청 수, 입력 크기, fd·매핑·객체 소유자, 정리 후 현재값과 최고치를 분리해 적자. 실제 측정 전에는 가상 표의 숫자를 실험 결과로 보고하지 않는다. 다른 프로세스의 자원 한계, 파일, 매핑을 변경하는 단계는 이 활동에 포함하지 않는다.
