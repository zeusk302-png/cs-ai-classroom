소단원 6.1

환경변수와 작업 디렉터리

자식 프로그램이 폴더를 바꾸면 부모 shell의 폴더도 바뀔까?

준비 개념과 학습 목표

준비 개념

  • 환경 변수는 프로세스에 전달되는 이름 =문자열 값의 목록이다.

  • 작업 디렉터리 cwd는 상대 경로 해석의 기준이다.

  • 이 단원은 POSIX/GNU의 단일 스레드 프로세스 모형과 성공한 호출을 가정한다.

학습 목표

  • 부모· 자식·exec 뒤의 환경과 cwd를 따로 추적한다.

  • 없는 변수· 빈 문자열· 경로 오류를 구별한다.

프로그램의 PWD 표시와 실제 상대 경로가 충돌하면 어느 장부를 믿어야 할까?

링크 없는 가상 파일계에서 단일 스레드 부모 P의 PID는 700, cwd는 /work, 환경 MODE는 blue, PWD는 /work이고 EMPTY와 LOST는 없다. 성공한 fork로 자식 C의 PID가 701이 된다. 이후 C만 setenv(PWD,/else,1), chdir(/work/run), setenv(MODE,red,0), setenv(EMPTY,빈 문자열,1)을 성공시킨다. 이 모형은 경로의 존재와 각 변경의 성공을 별도로 가정하며 실제 호출은 하지 않는다.

PWD는 환경 문자열이므로 첫 변경만으로 cwd가 /else가 되지 않는다. chdir 성공 뒤 실제 상대 경로 기준은 /work/run이다. MODE는 이미 blue여서 replace=0인 변경은 red를 설치하지 않는다. EMPTY는 존재하는 길이 0의 문자열이고 LOST는 이름 자체가 없어 getenv의 NULL 결과다. 문자열 표시, 커널이 관리하는 cwd, 환경 이름의 존재, 값의 내용이라는 네 종류를 분리한다.

같은 C의 현재 상태에서 직접 정상 바이너리를 execv하면 현재 환경을 전달하지만 execve에 [MODE=green, NULL]을 주는 대안에서는 그 목록만 전달한다. 두 대안 모두 exec 성공 직후 PID 701과 cwd /work/run은 유지된다. 명시 환경에서 PWD가 없다고 cwd도 없어지는 것은 아니다. 새 프로그램의 이후 변경, 셸 확장, 동시 환경 변경 및 getenv 반환 포인터의 장기 유효성은 이 장부가 보장하지 않는다.

먼저 확인할 개념
  • 환경 존재·값·cwd의 별도 계약

    빈 값과 부재, PWD와 실제 경로 기준을 구별한다.

  • PID와 세션 멤버십

    이미지 교체와 프로세스 정체성을 따로 추적한다.

문자열 환경과 실행 인자

getenv는 이름의 값 문자열을 돌려주고 없으면 NULL을 돌려 준다. 값이 빈 문자열이면 포인터가 NULL인 것과 다르다. 반환 문자열을 직접 고치지 않고 환경 변경 함수의 계약을 사용한다.

setenv는 이름과 값을 복사한다. 이미 존재하는 이름에 replace =0이면 값을 유지하고 replace가 0이 아니면 바꾼다. 환경 문자열이 존재한다고 파일 접근 권한이나 특정 데이터 형식의 정확성이 보장되지 않는다.

fork 뒤 두 프로세스의 변화

일반 fork 뒤 자식은 부모의 환경과 cwd를 물려받지만 자식의 setenv와 chdir 성공이 부모를 자동 수정하지 않는다. 외부 프로그램의 cd가 shell의 cwd를 못 바꾸는 이유가 여기 있다. shell의 cd는 자기 프로세스에서 처리해야 한다.

exec는 현재 프로세스의 프로그램 이미지를 바꾼다. execv는 현재 environ을 사용하고 execve는 명시한 환경 목록을 사용한다. 성공한 exec 뒤 PID와 cwd는 유지되지만 새 프로그램이 이후 chdir를 하면 그때 바뀔 수 있다.

cwd와 PWD 문자열의 차이

상대 이름 data.txt는 현재 cwd를 기준으로 찾고 /lab/data.txt 같은 절대 이름은 자기 기준 경로를 갖는다. chdir는 실제 프로세스의 cwd를 바꾸며 실패하면 성공한 새 위치라고 기록하지 않는다.

환경의 PWD 문자열을 /other로 바꾸는 것만으로 cwd가 바뀌지 않는다. 심볼릭 링크를 포함한 shell 표시 경로와 getcwd가 얻는 경로가 다를 수 있다. 아래는 링크 없는 가상 파일계와 성공을 명시한 종이 활동이다.

중간 과정을 따라가는 예제

부모 PID100,cwd =/lab, 환경 COURSE =cs에서 자식 PID101을 fork한다. 자식만 chdir(/lab/run),setenv(COURSE,ai,1) 성공 뒤 execv(/bin/app)를 한다. 양쪽 상태는?

  1. fork 직후 자식 cwd =/lab,COURSE =cs다.

  2. 자식 chdir 성공으로 자식 cwd =/lab/run만 바뀐다.

  3. 자식 setenv 성공으로 자식 COURSE =ai만 바뀐다.

  4. execv 성공 뒤 새 이미지의 PID101,cwd =/lab/run,COURSE =ai다. 부모는 PID100,cwd =/lab,COURSE =cs를 유지한다.

부모 /lab·cs, 자식 새 이미지 /lab/run·ai다. exec 성공은 새 프로세스 번호를 만드는 일이 아니다.

조건을 바꾸어 비교하기

PWD를 고친 뒤에도 틀리는 상대 경로

C가 위 변경 뒤 data.bin을 상대 경로로 열려고 한다. P의 동일 이름과 PWD를 사용한 추측 경로를 비교하라.

  1. C의 실제 cwd를 사용한 기준 경로는 /work/run/data.bin이다.

  2. P의 기준은 /work/data.bin이고 C의 PWD만 이어 붙인 /else/data.bin은 이 모형의 실제 cwd 기준과 다르다.

세 경로의 문자열을 구별한다. 파일 존재·권한·열기 성공은 조사하지 않았다.

비교할 점

환경 표시값이 맞는지 확인하지 않고 권한이나 실제 열기 결과로 승격하지 않는다.

없는 이름과 빈 이름의 값을 하나로 합친 오류

C가 EMPTY를 빈 값으로 설치한 뒤 LOST와 둘 다 없다고 보고한다. execv와 명시 execve 대안도 비교하라.

  1. 현재 C의 EMPTY는 이름이 존재하여 getenv가 빈 문자열을 가리킨다. LOST는 NULL을 반환한다.

  2. execv 대안에서는 이 차이가 전달된다. [MODE=green, NULL]인 execve 대안은 둘 다 목록에서 빠져 새 이미지에 두 이름이 없다.

두 대안의 PID는 701, cwd는 /work/run이다. 환경 존재 여부의 결과만 달라진다.

비교할 점

같은 빈 표시를 출력하는 응용 코드도 NULL 검사를 지워서는 안 된다.

힌트 보기

풀이 보기

MISSING이 없으면 NULL이다. COURSE는 이미 ai라 replace0에서 ai 유지다. EMPTY는 존재하는 빈 문자열이므로 getenv 결과는 빈 문자열을 가리키며 NULL과 다르다.

오해와 반례

PWD 문자열을 바꾸거나 자식에서 cd하면 부모 cwd도 바뀐다.

자식 /lab/run인데 부모 /lab인 반례다. 환경 PWD는 문자열이고 chdir로 관리되는 실제 cwd와 별개다.

스스로 풀어보기

먼저 답과 이유를 적고, 필요한 만큼 힌트를 한 단계씩 열어 보세요.

연습 1 · 값과 상태 예측

C의 MODE가 blue인 상태에서 setenv(MODE,red,0), setenv(MODE,red,1)이 순서대로 성공한다. 각 완료 직후 값과 P의 값을 구하라.

힌트 1

replace가 0이면 기존 이름을 유지한다.

힌트 2

C의 변경은 일반 fork 뒤 P의 환경을 바꾸지 않는다.

풀이와 답 확인

  1. 첫 호출 뒤 C의 MODE는 blue다.

  2. 둘째 호출 뒤 C의 MODE는 red이고 P는 두 시점 모두 blue다.

실제 환경을 수정하지 않은 순서 추적이다.

흔한 오답에서 다시 생각하기

두 호출의 값 인자가 red이므로 둘 다 즉시 red다.

기존 이름과 replace 값을 함께 확인한다.

연습 2 · 오류 찾아 고치기

환경 PWD가 /else로 보이고 EMPTY 출력이 비어 있으므로 cwd=/else, EMPTY 없음이라고 썼다. 두 추론을 고쳐라.

힌트 1

cwd는 성공한 chdir 사건으로 추적한다.

힌트 2

NULL과 길이 0 문자열은 서로 다르다.

풀이와 답 확인

  1. 주어진 chdir 뒤 C의 cwd는 /work/run이다.

  2. EMPTY는 이름이 있으며 값이 빈 문자열이다. LOST만 이름이 없다.

표시 문자열만으로 커널 상태와 변수 존재를 합치지 않는다.

흔한 오답에서 다시 생각하기

PWD와 getenv 화면 출력만으로 모두 확정된다.

표시 방식은 서로 다른 상태를 같은 문자열로 보이게 할 수 있다.

연습 3 · 직접 만들어 보기

C를 cwd=/work/run에서 MODE=green만 가진 새 이미지로 바꾸고 부모 상태를 보존하는 종이 호출 계획을 만들라.

힌트 1

C에서만 cwd 변경을 수행한다.

힌트 2

명시 환경 목록은 NULL로 끝낸다.

풀이와 답 확인

  1. C에서 chdir 성공 여부를 확인한 뒤 직접 바이너리 execve에 [MODE=green, NULL]을 전달한다.

  2. 성공 뒤 C의 PID와 cwd는 유지되고 부모 P는 /work와 blue를 유지한다. 실패면 새 이미지가 실행됐다고 기록하지 않는다.

환경 문자열 배열의 계획이지 실제 파일계·권한·실행 검증은 아니다.

흔한 오답에서 다시 생각하기

환경에서 PWD를 삭제하면 cwd도 삭제돼 실패한다.

현재 작업 디렉터리는 환경 목록의 한 항목이 아니다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

setenv는 값을 복사하지만 putenv에 지역 배열 MODE=red의 주소를 주고 함수가 반환했다면 같은 수명 보장을 쓸 수 있는가?

힌트 1

GNU putenv는 제공한 문자열을 환경의 일부로 사용한다.

힌트 2

지역 배열의 저장 수명과 환경 사용 수명을 따로 본다.

풀이와 답 확인

  1. setenv와 달리 putenv의 해당 문자열은 복사본이라고 가정하면 안 된다.

  2. 자동 지역 배열의 수명이 끝난 뒤 그 주소를 계속 환경에서 사용하려는 계획은 유효한 장부가 아니다. 충분히 오래 유지되는 저장소나 복사 계약을 사용해야 한다.

실제 무효 포인터를 읽어 결과를 시험하지 않는다.

흔한 오답에서 다시 생각하기

두 함수의 이름이 비슷하므로 putenv도 지역 배열을 복사한다.

출처의 저장소 수명 계약을 읽고 입력 문자열 소유권을 구별한다.

세션·프로세스 그룹

파이프라인의 두 프로그램을 한 작업으로 중지하려면 무엇으로 묶을까?

준비 개념과 학습 목표

준비 개념

  • PID는 프로세스 번호, PGID는 프로세스 그룹 번호다.

  • session은 여러 프로세스 그룹을 포함할 수 있는 실행 맥락이다.

  • 본 POSIX 모형은 job control 지원· 유효한 자식· 허용된 호출 시점을 가정한다.

학습 목표

  • 프로세스· 그룹· 세션의 포함 관계를 그린다.

  • setpgid와 setsid의 효과 및 실패 조건을 구별한다.

같은 두 호출을 역순으로 하면 세션 장부도 같아질까?

새 가상 세션의 SID는 700이고 shell의 PID와 PGID는 700이다. fork로 생긴 C의 PID는 711이며 처음 SID 700, PGID 700이다. 자식 D의 PID 712도 같은 초기 멤버십을 갖는다. 모든 ID는 이 사례의 이름이며 실제 프로세스가 아니다. 같은 세션의 그룹 생성·이동을 허용하는 호출 시점과 권한을 명시한다.

C의 setsid를 먼저 성공시키는 A 계획에서는 SID와 PGID가 모두 711이 되고 제어 터미널이 없다. 반대로 C가 setpgid(0,0)를 먼저 성공시키는 B 계획에서는 SID는 700이지만 PGID가 711이 되어 그룹 leader가 된다. 그 상태의 setsid는 실패하여 새 세션이 생기지 않는다. 같은 이름의 두 동작을 나열해도 순서를 바꾸면 성공 조건 자체가 달라진다.

D가 SID 700에 남았을 때 A 계획의 PGID 711로 옮기려는 시도는 다른 세션의 그룹이므로 허용된 이동이 아니다. B 계획에서는 PGID 711이 같은 세션 안의 작업 그룹이라 exec 전의 허용 조건에서 D를 그 그룹에 넣을 수 있다. 부모가 이미 exec한 자식의 그룹을 뒤늦게 바꾸는 것은 EACCES 조건이고, 실행 뒤라도 자식 자신의 허용된 setpgid와 동일한 호출 주체로 합치면 안 된다.

먼저 확인할 개념
  • setpgid와 setsid의 성공 조건

    SID와 PGID를 별도 열로 두고 leader 조건을 먼저 검사한다.

  • 멤버십과 터미널 전경

    새 그룹 구성만으로 전경 그룹이 바뀌지 않음을 확인한다.

한 작업에 여러 프로세스

파이프라인 left |right는 보통 두 프로세스를 만든다. job control shell은 관련 프로세스를 같은 그룹으로 묶어 한 작업으로 다룬다. 부모-자식 관계와 그룹은 다르며 같은 그룹이 꼭 한 프로세스만 담는 것은 아니다.

fork한 자식은 처음 부모와 같은 PGID와 session을 상속한다. shell은 exec 전에 setpgid 등으로 별도 작업 그룹을 구성한다. 오류· 경쟁 조건을 확인해야 하며 단순 그림이 완전한 shell 구현은 아니다.

그룹을 바꾸는 조건

setpgid는 자기 프로세스나 허용된 자식을 같은 session의 그룹에 넣는다. 다른 session으로 이동시키는 함수가 아니며 session leader 이동과 exec한 자식의 변경에는 제한이 있다. PID와 PGID가 같으면 그룹 leader다.

세션의 그룹을 나누어도 현재 전경 터미널의 그룹이 자동 변경되지는 않는다. PGID와 터미널 전경 그룹은 별도 속성이며 같은 session이라는 조건 아래 tcsetpgrp 등으로 제어한다.

새 세션을 만드는 호출

setsid 성공 시 호출자는 새 session leader이면서 새 그룹 leader가 되고 sessionID/PGID가 자기 PID와 같아진다. 새 session에는 처음 자기만 있으며 제어 터미널이 없다. 기존 터미널 전경 작업과 동일하다고 취급하지 않는다.

이미 그룹 leader인 호출자는 setsid에서 실패한다. 새 프로그램을 exec 하는 것은 새 session을 만드는 것과 다르며 PID/PGID/session을 유지한다. 아래 그림은 성공 조건을 갖춘 가상 ID로만 추적한다.

  1. A의 그룹은 SID 711에 있으므로 D의 SID와 다르다. setpgid로 세션을 건너뛰게 만들 수 없다.

소단원 6.3

터미널과 작업 제어

Ctrl-C를 누르면 같은 shell의 모든 배경 작업도 함께 종료될까?

준비 개념과 학습 목표

준비 개념

  • 제어 터미널은 session의 상호 작용 입출력과 관련된 터미널이다.

  • 전경 그룹은 터미널이 현재 입력/ 키보드 신호를 보낼 작업 그룹이다.

  • 본예는 job control 지원· 비고아그룹· 신호 기본 처리· 성공한 전경 변경 조건이다.

학습 목표

  • 전경/ 배경 그룹별 신호·read·write 결과를 예측한다.

  • 중지· 재개· 터미널 소유권을 구별한다.

작업을 계속 실행시킨 사실과 터미널을 다시 준 사실은 어떻게 구별할까?

SID 700에 shell 그룹 700, 두 멤버 711과 712가 있는 작업 그룹 711, 배경 작업 그룹 721이 있다. 비고아 그룹·job control 지원·해당 신호 기본 처리 및 유효한 제어 터미널을 가정한다. 처음 전경 그룹은 711이다. Ctrl-Z가 SIGTSTP를 생성하면 대상은 그룹 711이며 종료가 아닌 정지 사건이다. 실제 신호나 터미널은 조작하지 않는다.

shell은 작업 멤버가 모두 정지하거나 종료한 조건을 확인한 뒤 성공한 전경 회수와 모드 처리를 거쳐 전경 그룹을 700으로 되돌린다. 그 뒤 그룹 711에 SIGCONT만 보내면 프로세스는 재개해도 전경은 700이다. 이 상태의 기본 처리 배경 작업이 제어 터미널을 read하면 SIGTTIN으로 다시 멈출 수 있다. 재개, 읽기 권한, 터미널 전경이라는 세 장부를 하나의 running 표시로 줄이지 않는다.

정상 fg 계획은 같은 세션의 제어 터미널에 그룹 711을 전경으로 성공 지정하고 필요한 모드를 복구한 뒤 SIGCONT로 재개한다. shell이 배경에서 tcsetpgrp를 호출할 때 SIGTTOU 처리 조건도 필요하다. 모든 호출 성공과 오류 검사를 이 계획의 조건으로 둔다. 배경 write는 TOSTOP가 꺼진 경우와 켜진 경우를 구별하며 해당 신호를 차단·무시한 예외도 별도로 본다.

키보드 신호의 대상

터미널의 현재 전경 PGID와 프로세스 PGID가 같은 그룹이 전경이다. Ctrl-C가 SIGINT를 발생시키는 설정에서 신호는 전경 그룹으로 전달된다. 기본 동작은 종료지만 프로그램이 처리하거나 무시할 수 있어 항상 종료라고 하지 않는다.

Ctrl-Z는 보통 SIGTSTP로 중지를 요청한다. 중지는 프로세스가 존재한 채 실행을 멈추는 것이고 종료와 다르다. SIGCONT를 보내 재개하는 것만으로 터미널 전경 그룹이 자동 변경되지는 않는다.

배경 입출력의 차이

제어 터미널을 배경 작업이 읽으려하면 보통 SIGTTIN으로 그룹이 중지된다. 이 신호를 차단하거나 무시하면 read가 EIO로 실패하는 경우도 있다. 실제 파일/ 파이프 read와 제어 터미널 read를 구별한다.

배경 쓰기는 TOSTOP 설정에 따라 달라진다. 꺼져 있으면 일반적으로 터미널 write가 허용되고 켜져 있으면 SIGTTOU로 중지될 수 있다. 차단/ 무시 및 예외 조건도 있으므로 배경이면 화면 출력이 언제나 금지라는 결론은 틀리다.

shell의 전경 회수

shell은 전경 작업을 시작할 때 tcsetpgrp로 터미널 전경 그룹을 작업에 넘기고 중지/ 종료를 기다린다. 작업이 멈추면 자기 그룹으로 전경을 회수하여 다음 명령을 읽는다. 터미널 모드 저장/ 복구도 필요할 수 있다.

중지 작업을 fg로 되살릴 때는 전경 그룹 전환과 재개 신호를 함께 처리한다. shell의 SIGTTOU 처리· 동일 session/ 터미널· 오류 검사는 실제 구현에서 필요하다. 아래 종이 모형에서는 적절한 shell 신호 처리로 해당 호출이 성공한다고 명시한다.

연습 1 · 값과 상태 예측

힌트 2

작업 실행 상태와 제어 터미널 전경을 나눈다. 기본 read의 SIGTTIN과 shell의 성공한 tcsetpgrp·mode 복구·CONT를 따로 기록한다.

풀이와 답 확인

  1. P는 PID 700, cwd /work, MODE=blue를 유지한다. C는 PID 711과 cwd /work/run을 유지하며 명시 execve 뒤 MODE=green이고 PWD는 전달 목록에 없다. C의 상대 이름 기준은 /work/run/data.bin이다. 파일 열기 성공은 미확인이다.

  2. A는 SID 711/PGID 711과 제어 터미널 없음이다. B는 첫 성공 뒤 SID 700/PGID 711이며 그룹 leader여서 이어 setsid는 실패한다.

  3. D의 SID가 700이면 A의 그룹 711로 이동은 세션 조건을 위반한다. B에서는 exec 전 부모의 유효한 자식 등 허용 조건에서 같은 작업 그룹으로 넣을 수 있다.

  4. CONT만 보낸 경우 실행은 재개해도 전경은 700이므로 기본 배경 터미널 read에 SIGTTIN 정지 조건이 남는다. 정상 fg 계획은 적절한 shell 신호 처리와 같은 세션 조건에서 전경을 711로 성공 지정하고 필요한 모드와 CONT를 처리한다.

환경 문자열의 교체, 세션/그룹 변경, 터미널 전경 이전은 서로 다른 계약이다. 같은 최종 PGID와 running 표시는 전체 상태를 복원하지 못한다. 모든 사건은 성공·실패 조건을 명시한 자체 종이 모형이며 실제 프로세스·셸·터미널·학생 실험은 미수행이다.

해결한 뒤 점검할 것

  • PWD 문자열·cwd·부재와 빈 값·명시 환경 및 PID 유지를 구별한다.

  • 두 순서의 SID/PGID/제어 터미널 차이와 실패 상태 보존을 설명한다.

  • 같은 세션·호출 주체·exec 시점 조건을 모두 확인한다.

  • CONT와 fg를 구별하고 멤버 전체 상태·터미널 소유권·I/O 예외 및 실제 실행 한계를 기록한다.

현재 base 전체와 세 고유 선수 설명을 읽고 새 장부를 손검산했다. P/C의 cwd와 환경 독립성, replace 0/1의 blue/red, 빈 값과 NULL, 명시 execve의 green 및 PID/cwd 보존을 확인했다. A의 SID/PGID 711과 B의 SID 700/PGID 711·setsid 실패, D의 같은 세션 조건 및 부모/자기 호출의 exec 시점 차이를 추적했다. 전경 711→700 회수와 CONT만 재개한 700 유지, 정상 fg에서 711 복구, 두 멤버 중 한 명 정지/한 명 실행의 전체 미완료, SIGTTIN 무시의 EIO, TOSTOP별 일반 write 및 SIGINT 대상/효과 분리를 손대조했다.
