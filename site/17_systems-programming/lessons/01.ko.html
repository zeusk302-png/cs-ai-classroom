셸·경로·환경변수

터미널에 명령 한 줄을 쓰면 누가 그 글을 해석하고 어떤 파일을 찾을까?

준비 개념과 학습 목표

준비 개념

  • 텍스트 파일은 문자 자료이고 실행 프로그램은 동작하는 절차라는 차이를 안다.

  • 폴더 안에 파일이나 하위 폴더가 있다는 나무 그림을 읽는다.

  • 이 활동은 Bash/Unix의 가상 환경을 종이에 따라간다. Windows의 PowerShell 문법과 같다고 가정하지 않으며 설치가 필요하지 않다.

학습 목표

  • 터미널·셸·프로세스·커널의 역할을 구별한다.

  • 현재 디렉터리에서 상대 경로와 절대 경로를 추적한다.

  • 인용·환경 전달·파이프의 입력 흐름을 설명한다.

자식에 넘긴 경로와 부모의 다음 경로가 왜 다를까?

아래는 Bash의 별도 실행 환경을 종이로 추적하는 사례다. 부모의 현재 디렉터리는 /lab이고 MODE=blue는 내보낸 셸 변수다. 외부 자식 도구 하나가 시작 때 /lab과 blue를 받고, 자기 안에서 디렉터리를 /archive로 바꾸고 MODE를 red로 바꾼 뒤 종료한다고 정한다. 부모는 여전히 /lab과 blue다. 다음 자식도 부모가 변경되지 않았으므로 /lab과 blue를 받는다. 같은 변수 이름이 있다는 사실은 같은 변경 가능한 저장소를 공유한다는 뜻이 아니다.

명령 앞의 MODE=green tool은 이 외부 도구 호출의 환경만 바꾸는 사례로 제한한다. 도구가 green을 읽어도 부모의 blue를 수정하지 않는다. 셸 함수나 특수 내장 명령의 다른 규약을 이 사례에 섞지 않는다. 인용은 또 다른 층이다. FILE 값이 team list.txt이면 "$FILE"은 한 인수이고, 기본 IFS의 공백 분할을 허용한 $FILE은 두 인수다. 이 사례에서는 경로명 확장을 유발하는 문자는 없다.

파이프의 자료 연결과 종료 상태도 구별한다. 가상 세 단계의 상태가 왼쪽부터 7,2,0이라면 기본 정책의 파이프 상태는 0이다. pipefail을 켜면 가장 오른쪽의 비영 상태인 2다. 첫 실패인 7을 반환하는 규약이 아니다. 실제 파이프를 실행하거나 상태를 관측한 것은 아니다.

먼저 확인할 개념
  • 환경 전달과 인용

    원본의 export·자식 환경·공백 인수를 별도 호출 경계로 적용한다.

  • 계약과 실행 관측

    화면 자료와 종료 상태가 각각 어느 범위의 증거인지 구별한다.

터미널과 셸은 다른 역할

터미널은 문자 입력과 출력을 주고받는 인터페이스다. 셸은 명령 언어를 해석하는 프로그램이며 Bash는 그 한 종류다. 셸은 문장을 분석하고 확장·리다이렉션 등을 처리한 뒤 내장 명령을 수행하거나 외부 프로그램을 실행한다. 외부 프로그램의 실행 중인 인스턴스가 프로세스다. 커널은 자원·보호·파일·프로세스 서비스를 제공한다. 터미널에 보이는 명령 텍스트가 커널 그 자체는 아니다.

내장 cd는 셸 자신의 현재 디렉터리를 바꾸어야 하므로 외부 프로그램 실행과 다른 책임을 갖는다. 자식 프로세스가 자기 현재 디렉터리를 바꿔도 부모 셸의 디렉터리가 자동으로 바뀌지 않는다. 명령이 성공했는지는 종료 상태와 프로그램의 약속으로 확인하며, 출력 문자가 없다는 사실만으로 성공·실패를 단정할 수 없다.

경로와 인용으로 파일을 정확히 지정하기

Unix의 절대 경로는 /에서 출발한다. 상대 경로는 현재 디렉터리에서 출발하며 . 은 현재, .. 은 부모를 뜻한다. 이 예는 심볼릭 링크가 없고 /home/learner/lab가 현재 디렉터리라는 가상 나무다. data/names.txt는 /home/learner/lab/data/names.txt를 가리킨다. 같은 문자열도 현재 디렉터리가 달라지면 다른 대상을 가리킬 수 있다.

공백이 있는 이름을 하나의 인수로 전달하려면 인용이 중요하다. Bash에서 cat "team list.txt"는 한 파일 이름을 전달한다. cat team list.txt는 보통 두 인수로 나뉜다. 작은따옴표는 내용을 문자 그대로 보호하고 큰따옴표 안에서도 변수 확장 등 일부 기능은 남는다. 이 예의 "$COURSE_DATA/names.txt"는 변수값과 나머지 경로를 합쳐 한 인수로 만든다. 인용은 권한이나 파일 존재를 만들어 주지는 않는다.

환경변수와 파이프는 전달의 약속

환경은 프로세스 시작 때 전달되는 이름=값 목록이다. Bash의 셸 변수와 자식에게 내보내는 환경은 구별되며 export한 값이 이후 실행된 자식의 환경에 포함된다. 자식이 자기 값을 바꾼다고 부모의 값을 자동으로 바꾸지 않는다. PATH는 실행 파일을 찾을 디렉터리 목록을 제공하지만 파일 자료의 경로와는 다른 검색 목적이다.

파이프 |는 앞 명령의 표준출력을 뒤 명령의 표준입력으로 연결한다. 기본적으로 표준오류까지 같은 파이프로 들어가지는 않는다. 두 프로그램은 자료가 흐르며 겹쳐 실행될 수 있으므로 ‘첫 프로그램이 종료한 뒤 두 번째를 시작한다’는 일반 규칙으로 이해하면 안 된다. 본문은 한 줄씩의 텍스트와 성공한 흐름만 종이로 추적하고 실제 프로세스 시각이나 오류 처리는 따로 표시한다.

# Bash/Unix 가상 사례: 이 환경에서 실행하지 않음
export COURSE_DATA=/home/learner/lab/data
cat "$COURSE_DATA/names.txt" | LC_ALL=C sort
# 파일에 b,a,b가 각각 한 줄이면 예상 출력은 a,b,b 각 한 줄

행은 부모와 외부 자식의 서로 다른 환경이다. 경로 변경은 가상 디렉터리가 존재하고 자식의 변경이 성공한다고 정한 모형이다. 실제 cd나 셸 실행은 하지 않았다.

중간 과정을 따라가는 예제

가상 현재 디렉터리는 /home/learner/lab이다. data/names.txt에는 ASCII 문자 b,a,b가 각각 줄바꿈으로 끝나는 세 줄이다. 도구는 Bash와 Unix cat/sort이며 LC_ALL=C로 정렬하고 모두 성공한다고 가정한다.

  1. COURSE_DATA 값을 /home/learner/lab/data로 내보낸다.

  2. 인용된 변수 확장으로 cat의 파일 인수는 /home/learner/lab/data/names.txt 하나다.

  3. cat의 표준출력 세 줄 b,a,b가 파이프를 통해 sort의 표준입력으로 간다.

  4. C 로케일의 이 ASCII 문자 정렬에서는 a,b,b 순서가 된다. 중복 제거 옵션은 주지 않았으므로 b가 두 번 남는다.

예상 텍스트는 a b b 이다. 실제 Unix 명령을 실행하거나 Windows에서 같은 출력을 관측한 기록은 아니다.

조건을 바꾸어 비교하기

같은 상대 이름의 다른 대상

심볼릭 링크가 없는 부모 /lab와 변경 후 자식 /archive에서 data/x.txt를 각각 해석하라. 부모에서 MODE=green tool을 추가 실행할 때 값도 적어라.

  1. 부모의 경로는 /lab/data/x.txt이고 자식의 경로는 /archive/data/x.txt다.

  2. 새 외부 tool은 green을 받지만 부모의 MODE는 blue로 남는다.

상대 이름이 같아도 시작 디렉터리가 달라 대상이 다르다. 환경 덮어쓰기의 범위는 해당 외부 호출이다. 파일 존재나 권한은 이 경로 계산만으로 보장되지 않는다.

비교할 점

문자열과 실제 대상, 전달값과 부모 저장 상태를 따로 표시한다.

파이프 성공의 두 정책

세 단계 상태 7,2,0과 별도 상태 0,0,0에서 기본 정책과 pipefail을 비교하라.

  1. 7,2,0의 마지막 상태는 0이므로 기본 정책은 0이다.

  2. 가장 오른쪽 비영 상태는 2이며 모두 0인 별도 흐름은 두 정책 모두 0이다.

첫 흐름은 기본 0·pipefail 2, 두 번째 흐름은 모두 0이다. 기본 0은 모든 단계가 성공했다는 증명이 아니다.

비교할 점

정렬된 출력이 보인다는 관찰만으로 앞 단계의 성공을 대체하지 않는다.

오해와 반례

터미널은 커널이고, 화면에 쓰인 경로는 어디서나 같은 파일을 뜻한다.

터미널은 인터페이스이고 셸은 해석 프로그램이다. 상대 경로 data/names.txt는 현재 디렉터리에 따라 대상이 달라진다. 또한 PowerShell에서 같은 모양의 텍스트를 넣었다고 Bash의 확장·파이프 계약이 그대로 적용되는 것은 아니다.

스스로 풀어보기

먼저 답과 이유를 적고, 필요한 만큼 힌트를 한 단계씩 열어 보세요.

연습 1 · 값과 상태 예측

FILE=team list.txt라는 값을 이미 저장했다. 기본 IFS이며 glob 문자가 없는 가상 Bash에서 tool "$FILE"과 tool $FILE의 파일 관련 인수 수를 예측하라.

힌트 1

큰따옴표 안에서는 값을 한 단어로 보존한다.

힌트 2

인용 없는 확장에는 공백 분할이 적용된다.

풀이와 답 확인

  1. 인용한 경우 team list.txt 한 인수다.

  2. 인용하지 않으면 team과 list.txt 두 인수다.

파일 관련 인수는 각각 1개와 2개다. 명령 이름 자체는 이 수에서 제외했다.

흔한 오답에서 다시 생각하기

작은따옴표를 쓰면 변수값을 같은 방식으로 확장한다.

작은따옴표의 $FILE은 변수값 대신 그 문자 그대로다.

연습 2 · 오류 찾아 고치기

부모의 exported MODE가 blue였다. 외부 자식이 red로 바꾸었으므로 부모의 다음 도구도 red라고 기록했다. 고쳐라.

힌트 1

부모를 수정한 명령이 있는지 찾는다.

힌트 2

외부 자식의 별도 환경에서 수정한 값은 부모에 자동 반영되지 않는다.

풀이와 답 확인

  1. 부모 MODE는 blue다.

  2. 부모의 다음 외부 도구에는 blue가 전달된다.

red는 이전 자식 내부의 값이다. 출력으로 red를 돌려받아 부모가 명시적으로 저장하는 별도 프로토콜은 이 사례에 없다.

흔한 오답에서 다시 생각하기

환경을 상속하면 이후 수정도 공유된다.

시작 때 값을 전달하는 것과 이후 변경을 공유하는 것은 다르다.

연습 3 · 직접 만들어 보기

세 단계 상태 0,5,0을 보았는데 파이프 기본 상태만 검사해 통과시켰다. 모든 단계 성공을 요구하는 감사 기준과 두 정책 결과를 적어라.

힌트 1

전체 단계 상태를 각각 확인하는 기준도 가능하다.

힌트 2

pipefail은 비영 상태의 유무를 전체 성공 판정에 반영한다.

풀이와 답 확인

  1. 기본 상태는 0, pipefail 상태는 5다.

  2. 세 단계가 모두 0일 때만 전체 성공으로 분류한다.

이 흐름은 전체 성공 기준을 만족하지 않는다. 정책 변경 또는 단계별 상태 확인과 자료의 의미 검사 범위를 명시한다.

흔한 오답에서 다시 생각하기

컴파일·Make·디버거

코드를 고친 뒤 실행 결과가 그대로라면 새 코드를 정말 빌드했는지 어디서 확인할까?

준비 개념과 학습 목표

준비 개념

  • 소스 파일과 실행 파일이 다른 산출물임을 안다.

  • 의존 관계를 화살표로 그린다. main.c가 바뀌면 그로부터 만든 main.o도 다시 만들 수 있다.

  • 변수·함수의 현재값과 다음 실행 위치라는 개념을 복습한다. 도구 설치 없이 가상 표를 읽는다.

학습 목표

  • 컴파일러·빌드 도구·디버거의 책임을 구별한다.

  • Make 규칙의 목표·의존 파일·조리법을 읽고 재빌드 대상을 찾는다.

  • 예상 디버그 상태와 실제 관측을 구별해 기록한다.

새 헤더가 두 갈래로 전파되면 링크는 몇 번 필요한가?

가상 빌드는 app가 a.o와 b.o에, a.o가 a.c와 common.h에, b.o가 b.c와 common.h에 일반 파일 의존을 갖는다. 현재 시각은 두 소스가 10, 헤더가 30, 두 오브젝트가 20, app가 25다. 시각은 동일한 신뢰 가능한 기준의 숫자다. 헤더가 두 오브젝트보다 새로워 둘을 다시 만들고, 새 오브젝트의 시각이 app보다 커지는 성공 조건에서는 마지막에 app를 링크한다. 헤더를 두 번 컴파일한다는 뜻이 아니라 헤더를 사용하는 두 번의 번역이 필요하다.

각 컴파일이 3초와 5초, 링크가 2초인 새 비용 모형을 붙이면 직렬 합은 10초다. 두 컴파일이 서로 독립이고 자원이 충분하며 병렬 비용이 없다고 제한하면 둘을 동시에 시작하여 5초에 모두 끝내고 2초 링크를 붙여 7초다. 실제 make의 소요 시간을 측정하지 않았다. 링크를 두 번 수행해야 한다는 의존은 없다.

최신 판정의 경계도 중요하다. a.o의 시각이 20이고 a.c의 내용만 바꾸되 시각도 20으로 유지하면 이 보통 규칙에는 더 새로운 의존이 없다. 의미 변화가 없는 것이 아니라 시각 기반 판정이 변화의 근거를 받지 못한 것이다. 빌드 옵션 변경도 파일 의존이나 생성 규약에 표현하지 않으면 자동으로 반영된다고 가정할 수 없다.

먼저 확인할 개념
  • Make 의존과 정지 위치

    원본의 목표 갱신·대입 전후를 다중 의존과 별도 상태 표에 적용한다.

  • 실행 파일의 경로와 환경

    만든 파일과 실제 호출할 대상의 경로 일치를 확인한다.

컴파일 성공은 실행 정답과 다르다

GCC의 전처리·컴파일·어셈블·링크를 거쳐 소스로부터 실행 파일을 준비할 수 있다. -c는 링크까지 진행하지 않고 오브젝트를 만들며, -o는 출력 이름을 지정한다. 이 예의 Unix 명령 gcc -g -O0 -Wall -Wextra main.c -o demo는 디버그 정보를 포함하고 최적화를 억제한 교육용 빌드 요청이다. 옵션을 적었다는 것이 실제 도구가 설치되어 있거나 빌드가 성공했다는 관측은 아니다.

문법·타입 관련 진단이 없더라도 알고리즘이 틀릴 수 있다. 링크 성공은 필요한 코드 참조가 연결되었다는 종류의 근거이며 입력 검증이나 정답을 증명하지 않는다. 실행 파일이 오래된 것인지 다른 경로의 파일을 실행했는지도 확인해야 한다. 경고를 켜면 실수 발견에 도움이 되지만 모든 오류가 경고로 나오는 것은 아니다.

Make는 의존 관계와 갱신 규칙을 실행한다

Make 규칙은 target: prerequisites와 그 아래 조리법(recipe)으로 구성된다. 일반 파일 목표에서는 목표가 없거나 일반 의존 파일이 목표보다 새로우면 재생성할 이유가 된다. Make는 소스 언어를 직접 컴파일하는 대신 조리법에 적힌 컴파일러 등을 실행한다. 시간 비교가 최신 소스와 실행 결과의 의미적 동일성을 증명하는 것은 아니다.

main.o가 main.c와 config.h에 의존하고 demo가 main.o에 의존하면 헤더 변경 때 main.o를 다시 만들고 이어 demo를 다시 링크해야 한다. config.h를 의존 목록에서 빼면 Make가 변경을 몰라 오래된 결과를 쓸 수 있다. 자동 의존 생성 같은 보완은 후속 실습에서 배우며, 첫 종이 활동에서는 의존을 명시한다. 기본 recipe의 앞에는 실제 탭 문자가 필요하다는 문법도 기록한다.

# GNU Make/Unix 가상 예제, 실행하지 않음
demo: main.o
	gcc main.o -o demo
main.o: main.c config.h
	gcc -g -O0 -Wall -Wextra -c main.c -o main.o

디버거는 실행 상태를 관찰하는 도구

GDB는 중단점에서 멈추고 다음 줄이나 명령으로 이동하며 변수·호출 흐름을 조사할 수 있다. break, run, next, print 같은 요청은 실행의 어느 지점인지와 함께 해석해야 한다. 소스 줄에 멈췄다는 표시가 그 줄의 대입을 이미 끝냈다는 뜻은 아니다. 실제 디버거 표시의 정지 위치를 확인해 예상과 비교한다.

디버그 정보가 있어야 소스 이름과 실행 상태를 연결하기 쉽다. 최적화된 코드는 변수의 저장이 사라지거나 소스 줄과 명령 대응이 복잡할 수 있다. -O0도 모든 환경에서 완벽한 관찰을 보장하는 마법은 아니다. 디버거가 관찰한 한 경로는 다른 모든 입력의 정답을 증명하지 않는다. 버전·빌드 옵션·입력·중단 위치를 기록하면 관측의 범위를 평가할 수 있다.

중간 과정을 따라가는 예제

가상 파일 시각: main.c=10:00,config.h=10:06,main.o=10:05,demo=10:05. 위 규칙이며 시각은 신뢰할 수 있고 두 조리법은 성공하고 재생성된 main.o의 시각은 기존 demo보다 새로워진다고 가정한다. make demo가 필요한 일을 추적한다.

  1. demo를 만들기 전에 일반 의존 main.o의 최신 여부를 확인한다.

  2. config.h(10:06)가 main.o(10:05)보다 새로우므로 main.o를 다시 만든다.

  3. 새 main.o가 demo보다 새로우므로 demo를 다시 링크한다.

  4. main.c가 안 바뀌었어도 헤더 의존 때문에 재컴파일한다.

main.o 재컴파일 뒤 demo 재링크가 예상된다. 실제 GNU Make 실행 로그가 아니라 가상 시각·성공 조건의 추적이다.

두 관찰이 한 최종값을 보장하지 않는다

별도 순차 프로그램은 x=1로 시작하고 x=2*x; 다음 x=x+3;를 수행한다. 두 문장의 실행 직전·직후를 표로 적어라.

  1. 첫 대입 직전은 1, 직후는 2다.

  2. 두 번째 직전은 2, 직후는 5다.

현재 줄이 둘째 대입을 아직 수행하지 않은 위치라면 x는 2다. 정지 위치를 실행 후로 바꾸면 5다. 실제 GDB 출력은 아니며 조건부 실행이나 최적화는 없는 종이 절차다.

매뉴얼과 시스템 호출 추적

라이브러리 함수 이름이 보이면 그 이름 그대로 커널에도 호출이 전달될까?

준비 개념과 학습 목표

준비 개념

  • 사용자 프로그램과 커널 서비스의 경계를 구별한다.

  • 반환값은 요청한 결과나 실패 상태를 알리는 값이라는 뜻을 복습한다.

  • 바이트 수를 셀 수 있다. 문자 인코딩에 따라 한 문자와 한 바이트가 항상 같지 않다.

학습 목표

  • 매뉴얼의 섹션·전제·반환값·오류를 읽는 순서를 설명한다.

  • 라이브러리 호출·시스템 호출·추적 도구 관찰을 구별한다.

  • 짧은 읽기와 EOF를 가상 추적에서 해석한다.

한 버퍼에 남은 옛 글자를 새 읽기 결과로 처리해도 될까?

가상 보통 파일은 ASCII ABCDE이고 변경이나 공유 위치 접근은 없다. 크기 4인 재사용 버퍼로 양수 count를 요청한다. 첫 성공은 ABC 세 바이트를 반환하며 버퍼의 마지막 칸에는 이전 X가 남아 있다고 정한다. 둘째 성공은 DE 두 바이트를 버퍼 앞에 덮고 이전 C와 X는 남는다. 유효한 자료는 반환 길이의 앞부분뿐이므로 두 호출을 합치면 ABCDE다. 버퍼 용량 4를 매번 처리하면 ABCXDECX라는 잘못된 8바이트가 생긴다.

정확히 N바이트가 필요한 절차에서는 total과 remaining=N−total을 기록한다. 양수 반환을 더하고, 목표에 도달했을 때 성공한다. 목표 전에 보통 파일의 0을 받으면 조기 EOF로 나누며 오류 −1은 실패 정책으로 분기한다. count=0으로 받은 0을 보통 파일 끝의 증거로 쓰지 않는다. 비블로킹 대기 오류나 인터럽트의 재시도 규약은 원문과 목적에 맞춰 별도로 정한다.

시스템 호출 추적에 읽기 2회가 보인다는 사실만으로 사용자 수준의 처리 함수도 2회라고 정할 수 없다. 처리 함수가 버퍼를 나눠 다섯 번 호출되거나 전체를 모아 한 번 호출되는 두 구현 모두 같은 읽기 장부와 양립할 수 있다. 새 표는 자체 설명 모형이며 실제 strace 기록이 아니다.

먼저 확인할 개념
  • 반환 길이·EOF·추적 범위

    원본의 짧은 성공 읽기와 사용자 계산의 보이지 않는 범위를 재사용 버퍼에 적용한다.

  • 현재 상태와 이미 실행한 상태

    버퍼의 옛 칸과 새로 유효한 칸을 시점에 맞추어 분리한다.

이름뿐 아니라 계약을 읽기

Unix 매뉴얼에는 보통 일반 명령 1, 시스템 호출 2, 라이브러리 함수 3 등의 섹션이 있다. 같은 이름이 여러 섹션에 존재할 수 있으므로 read(2)의 숫자는 호출 인수 개수가 아니라 분류다. 문서를 읽을 때 이름과 버전·플랫폼을 확인한 뒤 선언, 인수 전제, 반환값, 오류, 비고 순서로 실제 계약을 찾는다.

Linux read(2)는 파일 기술자에서 버퍼로 최대 count바이트를 읽는 인터페이스다. 성공한 실제 읽기 바이트 수를 반환하고 0은 요청 조건을 고려해 파일 끝 등으로 해석한다. count보다 적게 읽는 것이 반드시 오류는 아니다. 실패는-1과 errno로 설명하며, errno는 실패라는 반환을 확인한 뒤 의미 있게 해석한다. 여기서는 양수 count의 보통 파일 예제를 사용하므로 count=0의 특수 해석을 섞지 않는다.

추적 도구가 보는 경계

strace는 Linux에서 프로세스의 시스템 호출과 신호를 추적하는 도구다. 사용자 함수의 모든 대입·루프·라이브러리 내부 처리를 기록하는 도구가 아니다. 라이브러리 함수가 버퍼에 있는 자료만 사용하면 새로운 읽기 호출이 보이지 않을 수 있다. 반대로 단 한 줄의 출력 함수가 내부 준비 작업과 여러 커널 호출을 유발할 수도 있다.

따라서 printf를 한 번 호출했다고 write가 한 번 관찰된다고 고정하지 않는다. 호출 포장 방식·버퍼링·환경·버전에 따라 실제 시스템 호출 이름과 수가 달라질 수 있다. 추적은 실행 중 관찰이며 가상 로그는 설명용 데이터다. 이 자료의 짧은 read 표는 도구가 생성한 로그 모양을 그대로 복제한 실제 관측 기록이 아니다.

관찰을 안전한 근거로 해석하기

추적에서 요청 인수와 반환값을 함께 보아야 한다. read가 5를 요청하고 3을 반환하면 3바이트만 유효한 읽기 결과다. 나머지 2바이트가 있다고 가정해 읽으면 안 된다. 이어 나머지 자료가 있는지는 다음 요청과 파일 상태에 달려 있다. 일반적인 완전 읽기 처리에는 짧은 읽기, EOF, 인터럽트와 실패 등 정책을 정해야 한다.

추적 도구 자체가 실행 시간에 영향을 주므로 추적 중 걸린 시간을 그대로 원래 프로그램 성능이라고 보고할 수 없다. 한 실행에서 특정 오류가 없었다고 모든 입력·일정에서 없다는 증명도 아니다. 로그에는 경로·자료 같은 정보가 포함될 수 있어 공유 범위를 정하고 필요한 부분을 기록한다. 매뉴얼의 정적 계약과 추적의 특정 실행 증거를 함께 연결해야 원인을 좁힐 수 있다.

가상 보통 파일 내용은 ASCII ABCDE의 5바이트이고 위치는 시작이다. 양수 count=5로 반복 읽었을 때 반환[3,2,0]을 관찰했다고 가정한다. 각 호출은 성공했고 다른 프로세스의 파일 변경은 없다.

  1. 첫 호출은 3을 반환하므로 버퍼에서 ABC 세 바이트만 처리한다.

  2. 두 번째는 2를 반환해 DE 두 바이트를 처리한다. count5를 요청해도 5가 항상 반환되지 않는다.

  3. 세 번째는 0이며 이 보통 파일 모형에서 EOF다.

  2. 유효 접두부만 붙이면 ABC와 DE로 5바이트다.

같은 자료의 다른 완전 읽기 계약

N=6인 절차에서 요청은 남은 양이고 반환은 2,3,0이다. 파일은 총 5바이트라고 정한다. 각 remaining과 최종 분류를 구하라.

  1. 처음 remaining은 6, 첫 성공 뒤 4다.

  2. 둘째 성공 뒤 total=5, remaining=1이고 세 번째 양수 요청은 EOF다.

요청은 6,4,1이며 total은 2,5,5다. N=6을 채우지 못한 조기 EOF이므로 정확한 6바이트 성공이 아니다.

반환 성공 여부를 먼저 본다. strace가 보는 것은 커널 경계이지 모든 사용자 계산이 아니다.

풀이 보기

실패 반환-1이면 성공한 5바이트가 있다는 근거가 없으며 문서의 오류 정보와 정책을 확인한다. sum의 산술 대입은 그 자체가 시스템 호출이 아니므로 strace에 독립 호출로 보일 필요가 없다. 실제 실행에서 신호나 별도 I/O가 있는지는 추가 관찰 문제다.

오해와 반례

read가 요청량보다 적게 반환하면 항상 오류이고 strace는 소스의 모든 함수 호출을 보여 준다.

3/5바이트처럼 짧은 성공 읽기는 허용된다. strace의 경계는 시스템 호출·신호여서 사용자 함수의 모든 상태가 보이지 않는다. 명세와 관찰 범위를 구분해야 정상 동작을 결함으로 오인하거나 보이지 않는 결함을 없다고 단정하지 않는다.

연습 1 · 값과 상태 예측

N=5이고 반환이 2,3이다. 남은 양을 요청하는 절차의 두 요청과 완료 뒤 total을 구하라.

힌트 1

첫 요청은 목표 전체다.

힌트 2

둘째 요청은 첫 반환을 뺀 값이다.

풀이와 답 확인

  1. 요청은 5와 3이다.

  2. total은 2와 5로 변하고 목표에 도달한다.

두 번째 뒤 성공하며 종료한다. EOF를 증명하려는 계약은 아니므로 추가 읽기가 필수는 아니다.

흔한 오답에서 다시 생각하기

EOF를 아직 보지 않았으므로 N바이트 성공도 아니다.

길이 달성과 파일 끝 확인은 서로 다른 목표다.

연습 2 · 오류 찾아 고치기

양수 요청의 성공 반환 2 뒤 errno에 예전 오류 번호가 남았다. 오류라고 분류하고 성공한 두 바이트를 버렸다. 고쳐라.

힌트 1

반환값으로 성공과 오류를 먼저 나눈다.

힌트 2

errno는 실패 반환의 근거와 연결한다.

풀이와 답 확인

  1. 반환 2는 이 호출의 짧은 성공 읽기다.

  2. 이전 errno만으로 이번 호출의 성공을 실패로 바꾸지 않는다.

성공한 2바이트를 누적한다. 실제 errno를 관측한 기록은 아니며 실패 −1인 경우에는 해당 오류와 정책을 확인한다.

흔한 오답에서 다시 생각하기

errno가 비영이면 모든 호출은 실패다.

오류 번호가 과거 상태일 수 있으므로 반환 계약을 먼저 적용한다.

연습 3 · 직접 만들어 보기

N>0에 대해 성공한 호출마다 0<r≤N−total을 보장한다. total이 N을 넘지 않는 반복 불변식과 종료 분기를 적어라.

힌트 1

처음 total=0이다.

힌트 2

양수 r을 더한 뒤 상한을 대입한다.

풀이와 답 확인

  1. 0≤total≤N이고 total<N일 때만 양수 remaining을 요청한다.

  2. 양수 반환 뒤 total+r≤N이며 total=N이면 성공, 0이면 조기 EOF, −1이면 오류 정책으로 분류한다.

불변식은 유지되지만 오류 재시도나 대기 정책 전체의 종료를 자동 보장하지 않는다. 각 실패를 무조건 반복하는 구현은 별도 문제다.

흔한 오답에서 다시 생각하기

total이 증가한다는 사실만으로 모든 실행이 종료한다.

오류나 대기 분기에는 양수 증가가 없을 수 있다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

같은 N바이트를 오류 없이 양수 정수 반환만으로 완료하고 각 반환은 남은 양 이하다. 성공 읽기 횟수의 최솟값과 최댓값을 구하라.

힌트 1

한 번에 N바이트를 받을 수 있다.

힌트 2

매번 1바이트만 받을 수도 있다.

풀이와 답 확인

  1. 최소는 1회다.

  2. 양수 성공만 세면 매번 적어도 1 증가하므로 최대 N회다.

성공 읽기 횟수 범위는 1..N이다. EOF·오류·재시도 호출까지 포함한 전체 호출 수의 상한이라는 주장은 아니다.

흔한 오답에서 다시 생각하기

재시도를 포함해도 항상 N회 이하다.

total이 증가하지 않는 호출은 이 증명의 계수 범위 밖이다.

반환 0을 언제나 EOF라고 하는가?

설명 기준 확인

count=0 사례와 구별한다. 본문의 양수 count·보통 파일 계약에서 EOF로 분류했다.

같은 syscall 장부가 같은 사용자 함수 횟수를 정하는가?

설명 기준 확인

아니다. 사용자 처리 분할과 버퍼링의 다른 구현이 같은 장부와 양립할 수 있다.

한 단계 더

읽기 함수는 한 번으로 count를 모두 얻는다는 계약이 아니다. 누적 total이 목표 N보다 작은 동안 남은 양을 요청하되, 0이면 EOF, -1이면 오류 정책, 양수면 누적한다는 의사코드를 설계하라. EINTR 재시도와 비블로킹 EAGAIN 처리 등은 플랫폼 문서와 작업 목적에 맞춰 별도 분기로 정한다. 임의 오류를 무조건 재시도하는 루프는 종료하지 않을 수 있다.

MODE=green tool로 외부 도구를 실행하고 그 자식은 cwd=/tmp, MODE=red로 바꾼 뒤 종료한다. 부모가 ./app를 실행한다고 하자. app 의존은 두 오브젝트이고 공통 헤더가 둘보다 새롭다. 성공 재컴파일 비용은 4초와 6초, 마지막 링크 1초이며 자원이 충분한 이상적 병렬 모형이다. 실행된 app는 정확히 6바이트를 요구하고 반환 2,3,0을 받는다. ① 부모의 경로/값과 처음 자식의 시작값 ② 필요한 빌드 순서와 두 경과 ③ 읽기 요청/누적과 완전 성공 여부를 나누어 감사하라. 이 흐름은 실제 실행이 아니다.

힌트 1

자식의 마지막 값이 부모로 돌아오는 통로는 주지 않았다. 두 컴파일 뒤에 링크를 한 번 배치한다.

힌트 2

remaining은 6에서 양수 반환만큼 감소한다. 빌드 성공과 자료 길이 성공을 서로 대신하지 않는다.

풀이와 답 확인

  1. 처음 외부 자식의 시작은 /work와 green이고 부모는 /work와 blue로 남는다. 부모의 ./app는 심볼릭 링크가 없는 모형에서 /work/app다.

  2. 공통 헤더 변경으로 두 오브젝트를 만들고 둘 완료 뒤 링크한다. 직렬은 4+6+1=11초, 이상적 병렬은 max(4,6)+1=7초다.

  3. 읽기 요청은 6,4,1이며 total은 2,5,5다. 마지막은 목표 전에 양수 요청이 0을 받은 조기 EOF다.

  4. 성공한 빌드와 자식의 환경 전달이 올바르더라도 정확히 6바이트를 얻는 계약은 실패했다. 오류를 모르는 상태로 6바이트를 처리하지 않는다.

부모 /work·blue, 처음 자식 /work·green, 실행 대상 /work/app다. 빌드는 두 컴파일 뒤 한 링크이고 모형 경과는 11초와 7초다. 자료는 5바이트만 얻어 정확한 6바이트 성공이 아니다. 실제 셸/빌드/읽기나 학생 수행 증거로 보고하지 않는다.
