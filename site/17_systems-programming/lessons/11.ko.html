다른 크기를 기다리는 두 요청 중 누구를 깨워야 할까?

새 자원 장부는 free라는 정수의 가용 단위 수를 하나의 뮤텍스 m으로 보호한다. 요청 A는 9단위, B는 4단위를 요구한다. 초기 free=0이어서 두 작업자가 같은 조건변수 changed에서 기다린다. 각 작업자는 while free < need로 상태를 다시 검사하고 성공하면 잠금 아래에서 free를 need만큼 줄인다. 할당 객체나 실제 메모리 배치는 포함하지 않는 종이 모형이다.

조정자가 잠금 아래에서 6단위를 반환하고 signal을 보낸다. 선택된 작업자가 A라면 A는 m을 재획득해 6 < 9를 확인하고 다시 기다린다. B는 충분한 4단위를 사용할 수 있지만 통지를 받지 않아 계속 잠들 수 있다. 이후 사건과 허위 깨어남이 없는 지정 일정에서는 가용 자원이 남아도 진행하지 않는다. while은 잘못된 소비를 막는 안전 조건이지 올바른 대상을 반드시 선택하는 규칙은 아니다.

같은 상태 변경 뒤 broadcast를 보내면 현재 대기자 모두가 재검사할 기회를 얻는다. A는 기다리고 B는 4단위를 소비해 free=2가 된다. A가 먼저 잠금을 얻어도 검사 뒤 다시 기다리며 B를 위해 잠금을 놓는다. 이는 작업자가 결국 실행되는 지정 일정의 결론이며 특정 작업자의 공정한 실행이나 실제 시간 상한을 보장하지 않는다.

모든 성공 접근을 같은 m으로 보호하고 초기화·수명·실패 처리는 별도로 유지한다. 잠금과 조건변수의 API 성공, 취소가 비활성화되어 있거나 별도 안전하게 처리된 상태를 가정한다. 통지 수를 자원 수로 바꾸지 않으며 POSIX 전체 규약을 특정 구현의 과거 설명과 동일시하지 않는다.

문을 잠그는 도구와 기다리는 도구

뮤텍스는 한 번에 한 작업자가 공유 상태를 다루도록 정하는 잠금이다. 같은 상태를 읽거나 바꾸는 모든 경로가 같은 잠금 규칙을 지켜야 한다. 한쪽만 잠그면 다른 쪽의 접근과 겹칠 수 있다. 성공한 lock 뒤 소유자가 임계 구역을 처리하고 unlock한다.

조건변수는 상태 자체가 아니라 기다림과 깨우기를 연결한다. 큐에 물건이 있는지는 count>0 같은 조건식으로 판정한다. signal을 몇 번 보냈는지로 큐의 길이를 계산하지 않는다. 객체 초기화, 수명, 반환값 확인도 필요하다.

wait는 잠금을 쥔 채 잠드는 명령이 아니다

pthread_cond_wait는 호출자가 해당 뮤텍스를 소유한 상태에서 부른다. 함수가 잠금 해제와 조건변수 대기를 원자적으로 연결하므로, 상태를 바꾸는 작업자가 잠금을 얻고 통지하는 사이를 잘못 놓치는 문제를 막는다. 성공해서 반환할 때는 같은 뮤텍스를 다시 소유한다.

대기 중인 같은 조건변수에 서로 다른 뮤텍스를 연결하면 정의되지 않는 동작이 될 수 있다. 여기서는 처음부터 끝까지 하나의 뮤텍스 m을 사용한다. 아래는 흐름을 보여 주는 C 조각이며 전체 실행 프로그램이 아니다. 초기화와 오류 처리, 종료 규칙은 다음 절에서 별도로 다룬다.

pthread_mutex_lock(&m);
while (count == 0) {
    pthread_cond_wait(&not_empty, &m);
}
/* 잠금 아래에서 물건 하나를 꺼내고 count를 줄인다. */
pthread_mutex_unlock(&m);

깨우기는 재검사 기회다

signal 이후 기다리던 작업자가 즉시 다음 명령을 실행한다는 보장은 없다. 다른 소비자가 먼저 잠금을 얻고 마지막 물건을 가져갈 수 있다. 상태 변화 없이 깨어나는 경우도 있으므로, wait 뒤 count를 while로 재검사한다. if는 첫 판정만 하고 깨어난 뒤 다시 확인하지 않는다.

통지는 저장된 물건처럼 누적되지 않는다. 기다리는 사람이 없을 때 signal이 먼저 일어나도 count가 잠금 아래에서 이미 1로 바뀌었다면 나중의 소비자는 기다릴 필요가 없다. 이 단원은 상태 변경과 통지를 같은 잠금 아래에서 수행하는 간단한 규칙을 쓴다. POSIX가 모든 signal 호출의 잠금 소유를 무조건 요구한다고 확대하지 않는다.

통지가 자원처럼 쌓이는 것은 아니다.

두 통지 정책은 같은 초기 상태에서 별도로 비교한다. broadcast의 깨어남과 자원 소비는 다른 사건이며 소비는 m을 재획득한 뒤 조건이 참일 때만 한다.

중간 과정을 따라가는 예제

빈 큐에서 C1이 대기한다. P가 값 7을 넣어 count=1로 만들고 C1을 깨운다. C1이 잠금을 다시 얻기 전에 C2가 7을 꺼낸다. 모든 상태 접근은 m으로 보호된다.

  1. 처음 C1은 count=0을 확인하고 wait하면서 m을 놓는다.

  2. P가 m을 얻어 값 7과 count=1을 기록하고 signal 후 m을 놓는다.

  3. C2가 먼저 m을 얻어 7을 꺼내면 count=0이다. C1이 뒤늦게 m을 얻어 wait에서 돌아와도 count는 0이다.

  4. while은 C1을 다시 기다리게 한다. if만 사용하면 빈 큐에서 꺼내려는 논리 오류가 발생한다.

C1은 다시 기다린다. 깨우기와 물건을 실제 확보하는 시점은 다르다.

안전해도 진행이 멈출 수 있는 일정

6단위를 반환한 뒤 signal이 A만 깨우고 다른 사건이 없다고 정했다. A/B의 상태와 free를 구하라.

  1. A는 잠금을 다시 얻어 6 < 9를 확인하고 다시 대기한다.

  2. B는 6 ≥ 4지만 계속 대기한다. free는 소비되지 않아 6이다.

불변식은 유지되지만 가능한 B의 진행이 지연된다.

모두 깨워도 모두 소비하지는 않는다

같은 초기 상태에서 6 반환 뒤 broadcast하고 A가 먼저, B가 다음으로 잠금을 얻는다.

  1. A는 부족하므로 기다리면서 m을 놓는다.

  2. B는 4단위를 소비하여 free가 2가 된다.

생산자 하나가 끝나면 남은 생산자의 큐도 닫아도 될까?

새 큐의 용량은 3이며 head=tail=count=0으로 시작한다. 값 10, 20, 30을 넣고 10을 꺼낸 뒤 40을 넣는다. 최종 head=tail=1, count=3이고 논리 순서는 20, 30, 40이다. 같은 인덱스가 찬 큐를 뜻하는 경우를 실제 count로 구별한다. 모든 상태는 같은 m 아래에서 바뀐다.

여러 생산자를 위한 별도 상태 active=2를 둔다. 이 수는 더 이상 put을 하지 않겠다고 선언하지 않은 생산자의 수다. 각 생산자는 마지막 put을 끝낸 뒤 m을 얻어 자신을 정확히 한 번 완료 처리한다. active를 하나 줄이고 0이 된 작업자만 closed=true를 기록하며 not_empty와 not_full 양쪽에 broadcast한다. 이는 생성 성공한 두 생산자와 실패 없는 완료 경로를 가정하는 자체 협력 종료 규약이다.

P가 완료하면 active=1이라 큐는 아직 열려 있다. Q가 이후 작업을 넣을 수 있기 때문이다. 첫 생산자 완료 때 닫으면 Q의 예정 작업은 CLOSED로 거절되어 원래 전체 과제 계약이 깨진다. Q까지 완료한 뒤 닫힌 큐는 남은 값을 순서대로 제공하고 count=0일 때 END를 준다. 닫힘은 즉시 버퍼 해제나 값 삭제가 아니다.

사용자별 완료 처리의 중복·생성 실패·오류 이탈이 있으면 active 장부도 그 경로를 포함해야 한다. 이 예제는 취소가 없는 성공 경로로 한정한다. 잠금·조건변수·버퍼의 파괴는 큐의 closed 플래그 하나가 아니라 모든 마지막 사용자 종료 확인 이후에 수행한다. 실제 pthread 프로그램을 실행한 것이 아니다.

두 인덱스와 하나의 개수

cap은 양의 용량, tail은 다음 저장 위치, head는 다음 꺼내기 위치다. 처음 head=tail=count=0으로 둔다. 저장 후 tail=(tail+1)%cap, 꺼낸 뒤 head=(head+1)%cap으로 옮긴다. 사용 중인 항목 수 count는 항상 0≤count≤cap이다.

head==tail만으로 비었는지 찼는지 알 수 없다. 두 칸에 두 번 넣으면 tail이 0으로 돌아오기 때문이다. count가 0이면 빈 큐, cap이면 찬 큐다. 배열, 인덱스, count, closed를 모두 m 아래에서 읽고 바꾸어 여러 변수의 관계가 깨지지 않게 한다.

기다리는 이유마다 조건변수를 둔다

생산자는 count==cap일 때 not_full에서 기다리고, 소비자는 count==0일 때 not_empty에서 기다린다. 넣은 뒤 소비자를, 꺼낸 뒤 생산자를 깨운다. 같은 조건변수 하나에 서로 다른 이유의 대기를 섞고 signal만 보내면 진행할 수 없는 종류의 작업자를 깨울 수 있다.

아래 의사코드는 모든 동기화 연산 성공, 일반 비강건 뮤텍스, 취소가 비활성화되었거나 별도로 안전하게 처리된 작업자를 가정한다. wait는 앞 절의 원자적 해제·대기·재획득이다. 실제 구현에는 초기화와 실패 처리, 스레드 생성·합류, 자원 정리 코드가 추가되어야 하며 이 의사코드를 C 컴파일 입력으로 쓰면 안 된다.

# 흐름을 위한 의사코드: 실제 C 프로그램이 아니다.
# cap > 0, head = tail = count = 0, closed = false
put(value):
    lock(m)
    while count == cap and not closed:
        wait(not_full, m)
    if closed:
        unlock(m)
        return CLOSED
    buffer[tail] = value
    tail = (tail + 1) % cap
    count = count + 1
    signal(not_empty)
    unlock(m)
    return OK

get():
    lock(m)
    while count == 0 and not closed:
        wait(not_empty, m)
    if count == 0:  # 여기서는 closed도 참이다.
        unlock(m)
        return END
    value = buffer[head]
    head = (head + 1) % cap
    count = count - 1
    signal(not_full)
    unlock(m)
    return VALUE(value)

close_queue():
    lock(m)
    closed = true
    broadcast(not_empty)
    broadcast(not_full)
    unlock(m)

닫힘과 비어 있음은 다르다

close_queue는 앞으로 새 물건을 받지 않는다는 상태를 기록한다. 닫혀도 count>0이면 소비자는 남은 물건을 계속 꺼낸다. 닫혔고 count=0일 때 END를 반환한다. 생산자는 깨어났을 때 closed를 확인하고 물건을 넣지 않는다. close는 두 대기 집단에 broadcast를 보내 종료 판정을 할 기회를 준다.

종료 상태는 한 작업자가 먼저 끝났다는 이유로 설정하면 안 된다. 여러 생산자가 있다면 모든 생산자의 완료를 확인한 조정자가 닫거나, 잠금 아래에서 남은 생산자 수를 추적한다. 모든 큐 사용자가 합류한 뒤에만 뮤텍스·조건변수·버퍼를 파괴한다. 이 규칙은 데이터 순서의 안전성을 설명하지만 특정 작업자에 대한 공정한 실행까지 보장하지 않는다.

매 접근을 잠갔는데도 재고가 음수가 될 수 있을까?

새 재고 stock=1을 m으로 보호한다. A와 B가 각각 잠금을 얻어 stock>0을 확인한 뒤 잠금을 놓는다. 두 작업자는 가능하다는 결과를 지역 변수에 저장한다. A가 다음 잠금 구간에서 1을 차감하여 stock=0으로 만들고, B가 과거 검사 결과만 믿고 다음 잠금 구간에서 1을 차감하면 stock=−1이다. 모든 공유 접근을 잠갔으므로 이 모형의 오류는 동기화 없는 C 데이터 경쟁이 아니라 검사와 사용의 논리적 경쟁상태다.

재고 검사와 예약 차감을 하나의 임계 구역에 넣거나 실제 차감 구간에서 조건을 다시 검사한다. 지역에 저장한 참은 새 상태의 참을 보장하지 않는다. 반대로 보통 C의 비원자 stock을 한 경로라도 잠금 없이 충돌 접근하면 데이터 경쟁으로 UB가 될 수 있다. 이때 −1이 실제 C 출력이라고 예측하지 않는다.

잠금 A,B,C의 다른 예제는 T1이 A를 소유하고 B를 기다리고, T2가 B를 소유하고 C를 기다리며, T3가 C를 소유하고 A를 기다린다. 각 작업자는 두 번째 잠금 전 첫 잠금을 놓지 않고 외부 해제나 취소도 없다고 정한다. 전역 순서 A<B<C를 모든 경로에 적용하면 마지막 C→A 경로를 금지하여 이 종류의 순환을 제거한다. 대기 시간이 길다는 관찰만으로 이런 고리를 확정하지 않는다.

지연 취소 대기자의 정리는 별도 장부다. 대상은 m을 얻고, 자신만 쓰는 힙 문맥 p를 정리하는 handler를 먼저 등록하고 m을 푸는 handler를 그 다음 등록한 뒤 cond_wait로 들어간다고 정한다. 대기에서 취소가 처리되면 m을 재획득한 뒤 역순으로 unlock(m), free(p)의 정리를 수행한다. 이 설명은 적절히 초기화된 객체·정확한 handler 등록 범위·소유권을 가정하는 흐름이며 실제 C 코드가 아니다. 요청 성공만으로 대상 종료나 객체 파괴를 선언하지 않는다.

읽기와 쓰기 사이에 끼어드는 작업

공유 합계를 증가시키는 일을 읽기·계산·쓰기의 세 단계로 생각하면, 두 작업자가 같은 옛 값을 읽고 하나의 증가를 덮어쓸 수 있다. 이 단계 모형은 왜 전체 갱신을 하나의 임계 구역으로 묶는지 설명한다.

그러나 보통 C의 비원자적 객체에 두 스레드가 동기화 없이 접근하고 적어도 하나가 쓰면 데이터 경쟁으로 정의되지 않는 동작이 된다. 단순히 항상 1만 잃는다고 예상 출력처럼 말할 수 없다. volatile도 스레드 사이의 상호 배제나 동기화를 제공하지 않는다. 한편 각각의 접근은 안전해도 검사와 사용을 따로 잠그면 그 사이 상태가 변하는 논리적 경쟁상태가 남을 수 있다.

잠금 두 개가 만드는 순환

T1이 A를 가진 채 B를 기다리고 T2가 B를 가진 채 A를 기다리면 둘 다 다음 잠금을 얻지 못한다. 이것이 교착이다. 오래 기다린다는 관찰만으로 확정하지 말고 누가 무엇을 소유하며 무엇을 기다리는지 표를 그린다.

모든 경로가 A 먼저, B 나중이라는 동일한 전역 순서를 지키게 하면 이 두 잠금으로 생기는 순환을 제거할 수 있다. B를 이미 가진 채 A를 요청하는 경로가 하나라도 있으면 규칙이 깨진다. 잠금 순서가 starvation이나 모든 종류의 교착을 자동 해결하는 것은 아니다. 정상 비강건 NORMAL mutex를 자신이 다시 잠그는 경우도 교착이며, DEFAULT나 ERRORCHECK 등 다른 유형을 같은 동작으로 단정하면 안 된다.

취소는 요청이고 정리는 별도 책임이다

pthread_cancel의 성공은 요청이 전달되었다는 뜻이다. 기본 enabled·deferred 설정에서는 대상이 취소 지점에 도달할 때 처리될 수 있다. 취소 비활성 상태에서는 요청이 미뤄진다. join으로 종료를 확인한 뒤에야 대상이 사용하는 자원을 안전하게 정리할 수 있다. 임의의 명령에서 즉시 끊는 비동기 취소는 공유 상태를 중간에 남길 수 있어 초심자용 해법으로 삼지 않는다.

조건변수 wait에서 지연 취소가 처리되면 cleanup handler를 실행하기 전에 해당 뮤텍스를 다시 획득한다. 따라서 잠금 해제 같은 정리 경로가 필요하다. 단지 취소했으니 wait가 잠금을 자동으로 풀어 주겠다고 가정하면 다른 작업자를 막을 수 있다. 앞 절의 큐 닫힘처럼 협력적인 종료 상태를 통지하고 합류하는 방식은 많은 작업에서 종료 절차를 읽기 쉽게 만든다. 그래도 모든 자원과 모든 실패 경로를 검토해야 한다.

중간 과정을 따라가는 예제

A와 B는 서로 다른 초기화된 잠금이다. T1은 A 잠금 성공 뒤 B를 요청하고, T2는 B 잠금 성공 뒤 A를 요청한다. 두 작업자가 첫 잠금을 모두 얻은 일정에서 소유와 대기를 추적하라.

  1. T1 소유=A, 요청=B이다.

  2. T2 소유=B, 요청=A이다.

  3. A는 T1이 놓아야 T2가 얻고, B는 T2가 놓아야 T1이 얻는다. 각 작업자는 두 번째 잠금을 얻기 전 첫 잠금을 놓지 않는다고 가정한다.

  4. 소유·대기가 T1→B→T2→A→T1의 고리를 이루어 진행하지 못한다.

  5. T2도 A부터 요청하게 바꾸면 T1이 A를 가진 동안 T2는 B를 얻기 전에 기다린다. T1은 비어 있는 B를 얻고 일을 마친 뒤 풀 수 있다.

주어진 일정은 교착이다. 두 경로 모두 A→B 순서로 바꾸면 이 잠금 순환을 없앤다. 모든 경로가 같은 규칙을 따라야 한다.

다른 문제에 적용하기

서로 독립인 세 장부를 작성하라. ① 가용량 free가 0인 상태에서 요청 A는 9단위, B는 4단위를 기다린다. 6단위를 반환한 뒤 signal이 A만 선택하는 일정과 broadcast 뒤 A와 B가 재검사하는 일정을 비교한다. ② 용량 3인 큐에 값 10, 20, 30을 넣고 10을 꺼낸 뒤 40을 넣었다. 생산자 P와 Q 중 P만 완료했을 때 active와 닫힘을 판단한다. 이후 Q도 완료하여 닫힌 뒤 네 번 get의 결과를 구한다. ③ 재고 stock이 1인 상태에서 두 작업자가 각각 잠금 아래 가능 여부를 저장한 뒤 별도 잠금 구간에서 무조건 차감한다. 재고와 수정 규칙을 구한다. 지연 cond_wait 취소에서 free(p), unlock(m) 순으로 등록한 cleanup의 실행 순서와 공유 객체 파괴의 완료 조건도 적는다.

힌트 1

자원 충분성·큐 항목 수·미래 생산자 수를 다른 상태로 추적한다.

힌트 2

저장된 검사 결과는 다시 확인하고 wait 취소의 재획득 및 handler 역순을 적용한다.

풀이와 답 확인

  1. ① signal이 A를 선택하면 A는 자원이 부족하여 다시 기다리고 가용량 free는 6이다. 다른 사건이 없는 지정 일정에서는 B도 잠들어 있다. broadcast 일정에서는 B만 4단위를 소비하고 가용량 free가 2가 된다.

  2. ② 마지막 큐 상태는 head와 tail이 각각 1이고 count가 3이다. 남은 값은 순서대로 20, 30, 40이다. P만 완료하면 active는 1이고 큐는 열려 있다. Q까지 완료하면 active가 0이 되어 큐를 닫고 양쪽 대기자에게 broadcast한다.

  3. 닫힌 뒤 반환은 VALUE(20), VALUE(30), VALUE(40), END다. END 호출에서 count를 더 줄이지 않는다.

  4. ③ 오래된 두 검사에 따른 무조건 차감은 재고 stock을 1에서 0으로, 이어 −1로 만든다. 검사와 차감을 한 구간에 묶으면 하나만 성공하고 다른 작업은 거절되어 재고 stock은 0이다.

  5. 대기에서 취소 처리 시 m을 재획득하고 cleanup은 unlock(m), free(p) 순이다. 성공 join으로 대상 종료와 다른 사용자 부재를 확인한 뒤 공유 동기화 객체를 파괴한다.

통지는 자원 토큰이 아니며 재검사와 진행 기회가 다르다. 큐의 count와 active를 분리하고 닫힌 뒤 소진한다. 잠금 있는 접근이라도 오래된 검사로 재고를 차감하지 않는다. 취소 요청과 실제 cleanup/종료 확인을 구별한다. 모든 일정과 상태는 자체 종이 모형이며 실제 pthread/학생 시험은 미수행이다.
