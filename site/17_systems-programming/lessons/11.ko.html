소단원 11.1

뮤텍스·조건변수

벨이 울렸다면 기다리던 물건이 반드시 남아 있을까?

준비 개념과 학습 목표

준비 개념

  • 공유 변수
  • 임계 구역
  • pthread 생성과 합류

학습 목표

  • 잠금 소유권과 상태 판정을 연결한다.
  • wait의 잠금 해제와 재획득을 설명한다.
  • 깨어난 뒤 while로 조건을 다시 확인한다.

문을 잠그는 도구와 기다리는 도구

뮤텍스는 한 번에 한 작업자가 공유 상태를 다루도록 정하는 잠금이다. 같은 상태를 읽거나 바꾸는 모든 경로가 같은 잠금 규칙을 지켜야 한다. 한쪽만 잠그면 다른 쪽의 접근과 겹칠 수 있다. 성공한 lock 뒤 소유자가 임계 구역을 처리하고 unlock한다.

조건변수는 상태 자체가 아니라 기다림과 깨우기를 연결한다. 큐에 물건이 있는지는 count>0 같은 조건식으로 판정한다. signal을 몇 번 보냈는지로 큐의 길이를 계산하지 않는다. 객체 초기화, 수명, 반환값 확인도 필요하다.

wait는 잠금을 쥔 채 잠드는 명령이 아니다

pthread_cond_wait는 호출자가 해당 뮤텍스를 소유한 상태에서 부른다. 함수가 잠금 해제와 조건변수 대기를 원자적으로 연결하므로, 상태를 바꾸는 작업자가 잠금을 얻고 통지하는 사이를 잘못 놓치는 문제를 막는다. 성공해서 반환할 때는 같은 뮤텍스를 다시 소유한다.

대기 중인 같은 조건변수에 서로 다른 뮤텍스를 연결하면 정의되지 않는 동작이 될 수 있다. 여기서는 처음부터 끝까지 하나의 뮤텍스 m을 사용한다. 아래는 흐름을 보여 주는 C 조각이며 전체 실행 프로그램이 아니다. 초기화와 오류 처리, 종료 규칙은 다음 절에서 별도로 다룬다.

pthread_mutex_lock(&m);
while (count == 0) {
    pthread_cond_wait(&not_empty, &m);
}
/* 잠금 아래에서 물건 하나를 꺼내고 count를 줄인다. */
pthread_mutex_unlock(&m);

깨우기는 재검사 기회다

signal 이후 기다리던 작업자가 즉시 다음 명령을 실행한다는 보장은 없다. 다른 소비자가 먼저 잠금을 얻고 마지막 물건을 가져갈 수 있다. 상태 변화 없이 깨어나는 경우도 있으므로, wait 뒤 count를 while로 재검사한다. if는 첫 판정만 하고 깨어난 뒤 다시 확인하지 않는다.

통지는 저장된 물건처럼 누적되지 않는다. 기다리는 사람이 없을 때 signal이 먼저 일어나도 count가 잠금 아래에서 이미 1로 바뀌었다면 나중의 소비자는 기다릴 필요가 없다. 이 단원은 상태 변경과 통지를 같은 잠금 아래에서 수행하는 간단한 규칙을 쓴다. POSIX가 모든 signal 호출의 잠금 소유를 무조건 요구한다고 확대하지 않는다.

중간 과정을 따라가는 예제

빈 큐에서 C1이 대기한다. P가 값 7을 넣어 count=1로 만들고 C1을 깨운다. C1이 잠금을 다시 얻기 전에 C2가 7을 꺼낸다. 모든 상태 접근은 m으로 보호된다.

  1. 처음 C1은 count=0을 확인하고 wait하면서 m을 놓는다.
  2. P가 m을 얻어 값 7과 count=1을 기록하고 signal 후 m을 놓는다.
  3. C2가 먼저 m을 얻어 7을 꺼내면 count=0이다. C1이 뒤늦게 m을 얻어 wait에서 돌아와도 count는 0이다.
  4. while은 C1을 다시 기다리게 한다. if만 사용하면 빈 큐에서 꺼내려는 논리 오류가 발생한다.

C1은 다시 기다린다. 깨우기와 물건을 실제 확보하는 시점은 다르다.

종이와 본문으로 직접 해보기

소비자 시작 전에 생산자가 count를 0에서 1로 바꾸고 signal을 보냈다. 소비자가 뒤에 m을 얻으면 반드시 wait해야 하는가?

힌트 보기

통지를 들었는지가 아니라 잠금 아래에서 판정한 count를 본다.

풀이 보기

아니다. count=1이므로 while의 조건 count==0은 거짓이다. 소비자는 바로 물건을 꺼낸다. signal을 저장할 필요 없이 공유 상태가 진행 가능성을 나타낸다.

오해와 반례

signal을 받으면 기다린 조건이 참임이 보장된다.

다른 소비자가 먼저 물건을 꺼내거나 상태 변화 없이 깨어날 수 있다. 반환 시 잠금을 다시 소유한 뒤 조건식을 확인해야 한다. mutex 없이 count를 검사하고 나중에 wait를 호출하는 방식도 올바른 대기 규칙을 대신하지 못한다.

한 단계 더

count=0을 잠금 밖에서 읽고, 생산자가 count=1과 signal을 처리한 다음 소비자가 무조건 기다리는 순서를 그려 보자. 상태 판정과 대기를 하나의 잠금 규칙으로 연결하지 않으면 이미 가능한 작업을 두고 계속 잠들 수 있다.

소단원 11.2

생산자·소비자 구현

두 칸짜리 작업 바구니가 꽉 차면 생산자는 어떻게 기다릴까?

준비 개념과 학습 목표

준비 개념

  • 원형 큐
  • 나머지 연산
  • 뮤텍스와 조건변수

학습 목표

  • 원형 큐의 불변식을 유지한다.
  • 생산자와 소비자 대기 조건을 구별한다.
  • 닫힌 큐를 비운 뒤 종료하는 규칙을 설계한다.

두 인덱스와 하나의 개수

cap은 양의 용량, tail은 다음 저장 위치, head는 다음 꺼내기 위치다. 처음 head=tail=count=0으로 둔다. 저장 후 tail=(tail+1)%cap, 꺼낸 뒤 head=(head+1)%cap으로 옮긴다. 사용 중인 항목 수 count는 항상 0≤count≤cap이다.

head==tail만으로 비었는지 찼는지 알 수 없다. 두 칸에 두 번 넣으면 tail이 0으로 돌아오기 때문이다. count가 0이면 빈 큐, cap이면 찬 큐다. 배열, 인덱스, count, closed를 모두 m 아래에서 읽고 바꾸어 여러 변수의 관계가 깨지지 않게 한다.

기다리는 이유마다 조건변수를 둔다

생산자는 count==cap일 때 not_full에서 기다리고, 소비자는 count==0일 때 not_empty에서 기다린다. 넣은 뒤 소비자를, 꺼낸 뒤 생산자를 깨운다. 같은 조건변수 하나에 서로 다른 이유의 대기를 섞고 signal만 보내면 진행할 수 없는 종류의 작업자를 깨울 수 있다.

아래 의사코드는 모든 동기화 연산 성공, 일반 비강건 뮤텍스, 취소가 비활성화되었거나 별도로 안전하게 처리된 작업자를 가정한다. wait는 앞 절의 원자적 해제·대기·재획득이다. 실제 구현에는 초기화와 실패 처리, 스레드 생성·합류, 자원 정리 코드가 추가되어야 하며 이 의사코드를 C 컴파일 입력으로 쓰면 안 된다.

# 흐름을 위한 의사코드: 실제 C 프로그램이 아니다.
# cap > 0, head = tail = count = 0, closed = false
put(value):
    lock(m)
    while count == cap and not closed:
        wait(not_full, m)
    if closed:
        unlock(m)
        return CLOSED
    buffer[tail] = value
    tail = (tail + 1) % cap
    count = count + 1
    signal(not_empty)
    unlock(m)
    return OK

get():
    lock(m)
    while count == 0 and not closed:
        wait(not_empty, m)
    if count == 0:  # 여기서는 closed도 참이다.
        unlock(m)
        return END
    value = buffer[head]
    head = (head + 1) % cap
    count = count - 1
    signal(not_full)
    unlock(m)
    return VALUE(value)

close_queue():
    lock(m)
    closed = true
    broadcast(not_empty)
    broadcast(not_full)
    unlock(m)

닫힘과 비어 있음은 다르다

close_queue는 앞으로 새 물건을 받지 않는다는 상태를 기록한다. 닫혀도 count>0이면 소비자는 남은 물건을 계속 꺼낸다. 닫혔고 count=0일 때 END를 반환한다. 생산자는 깨어났을 때 closed를 확인하고 물건을 넣지 않는다. close는 두 대기 집단에 broadcast를 보내 종료 판정을 할 기회를 준다.

종료 상태는 한 작업자가 먼저 끝났다는 이유로 설정하면 안 된다. 여러 생산자가 있다면 모든 생산자의 완료를 확인한 조정자가 닫거나, 잠금 아래에서 남은 생산자 수를 추적한다. 모든 큐 사용자가 합류한 뒤에만 뮤텍스·조건변수·버퍼를 파괴한다. 이 규칙은 데이터 순서의 안전성을 설명하지만 특정 작업자에 대한 공정한 실행까지 보장하지 않는다.

중간 과정을 따라가는 예제

cap=2이고 빈 큐다. 생산자가 7, 9를 순서대로 넣고 11을 넣으려 한다. 이후 소비자가 한 번 꺼내고 생산자가 11을 넣는다. 다른 동작은 없다고 하자.

  1. 7을 넣으면 buffer[0]=7, tail=1, head=0, count=1이다.
  2. 9를 넣으면 buffer[1]=9, tail=0, head=0, count=2이다. head와 tail은 같지만 큐는 찼다.
  3. 11을 넣으려는 생산자는 count==cap이므로 기다리며 m을 놓는다.
  4. 소비자는 buffer[0]의 7을 꺼내 head=1, count=1로 바꾸고 not_full을 통지한다.
  5. 생산자가 재획득하고 count=1을 확인하면 buffer[0]=11, tail=1, count=2가 된다.

꺼낸 값은 7이다. 남은 논리적 순서는 9, 11이고 head=tail=1, count=2이다.

종이와 본문으로 직접 해보기

예제 끝에서 큐를 닫는다. 소비자가 세 번 get을 호출하면 결과는 무엇인가? 닫힌 뒤 put(13)은 어떻게 되는가?

힌트 보기

닫힌 상태에서도 count가 양수면 꺼내기가 허용된다.

풀이 보기

get은 VALUE(9), VALUE(11), END를 반환한다. 두 번 꺼내면서 count는 2→1→0이 된다. put(13)은 CLOSED를 반환하고 큐를 바꾸지 않는다. 닫힘은 남은 값을 즉시 지우는 동작이 아니다.

오해와 반례

head와 tail이 같으면 항상 비어 있다.

용량 2에 값 두 개를 넣으면 두 인덱스가 모두 0이어도 count=2다. 이 구현은 count를 사용해 비어 있음과 가득 참을 구별한다. 빈 칸 하나를 남기는 다른 큐 설계의 규칙과 섞으면 안 된다.

생산자가 기다리는 조건은?

답과 이유 보기

열려 있고 count==cap일 때이다.

닫혔다면 대기보다 CLOSED 반환이 필요하다.

소비자가 하나 꺼낸 뒤 통지하는 조건변수는?

답과 이유 보기

not_full이다.

빈 자리가 생겨 생산자가 진행할 수 있다.

닫힌 큐의 count=1이면 즉시 END인가?

답과 이유 보기

아니다. 남은 값을 꺼낸다.

END는 count=0이며 더 들어올 값도 없는 닫힘 상태에서 반환한다.

한 단계 더

cap=3에 2, 4, 6을 넣고 두 번 꺼낸 뒤 8을 넣어 보자. 꺼낸 값은 2, 4이며 head=2, tail=1, count=2, 남은 순서는 6, 8이다. 물리 배열의 왼쪽부터 읽는 것과 논리 FIFO 순서가 다름을 확인한다.

  • 취소 요청과 완료 확인, 정리 책임을 분리한다.

읽기와 쓰기 사이에 끼어드는 작업

공유 합계를 증가시키는 일을 읽기·계산·쓰기의 세 단계로 생각하면, 두 작업자가 같은 옛 값을 읽고 하나의 증가를 덮어쓸 수 있다. 이 단계 모형은 왜 전체 갱신을 하나의 임계 구역으로 묶는지 설명한다.

그러나 보통 C의 비원자적 객체에 두 스레드가 동기화 없이 접근하고 적어도 하나가 쓰면 데이터 경쟁으로 정의되지 않는 동작이 된다. 단순히 항상 1만 잃는다고 예상 출력처럼 말할 수 없다. volatile도 스레드 사이의 상호 배제나 동기화를 제공하지 않는다. 한편 각각의 접근은 안전해도 검사와 사용을 따로 잠그면 그 사이 상태가 변하는 논리적 경쟁상태가 남을 수 있다.

잠금 두 개가 만드는 순환

T1이 A를 가진 채 B를 기다리고 T2가 B를 가진 채 A를 기다리면 둘 다 다음 잠금을 얻지 못한다. 이것이 교착이다. 오래 기다린다는 관찰만으로 확정하지 말고 누가 무엇을 소유하며 무엇을 기다리는지 표를 그린다.

모든 경로가 A 먼저, B 나중이라는 동일한 전역 순서를 지키게 하면 이 두 잠금으로 생기는 순환을 제거할 수 있다. B를 이미 가진 채 A를 요청하는 경로가 하나라도 있으면 규칙이 깨진다. 잠금 순서가 starvation이나 모든 종류의 교착을 자동 해결하는 것은 아니다. 정상 비강건 NORMAL mutex를 자신이 다시 잠그는 경우도 교착이며, DEFAULT나 ERRORCHECK 등 다른 유형을 같은 동작으로 단정하면 안 된다.

취소는 요청이고 정리는 별도 책임이다

pthread_cancel의 성공은 요청이 전달되었다는 뜻이다. 기본 enabled·deferred 설정에서는 대상이 취소 지점에 도달할 때 처리될 수 있다. 취소 비활성 상태에서는 요청이 미뤄진다. join으로 종료를 확인한 뒤에야 대상이 사용하는 자원을 안전하게 정리할 수 있다. 임의의 명령에서 즉시 끊는 비동기 취소는 공유 상태를 중간에 남길 수 있어 초심자용 해법으로 삼지 않는다.

조건변수 wait에서 지연 취소가 처리되면 cleanup handler를 실행하기 전에 해당 뮤텍스를 다시 획득한다. 따라서 잠금 해제 같은 정리 경로가 필요하다. 단지 취소했으니 wait가 잠금을 자동으로 풀어 주겠다고 가정하면 다른 작업자를 막을 수 있다. 앞 절의 큐 닫힘처럼 협력적인 종료 상태를 통지하고 합류하는 방식은 많은 작업에서 종료 절차를 읽기 쉽게 만든다. 그래도 모든 자원과 모든 실패 경로를 검토해야 한다.

중간 과정을 따라가는 예제

A와 B는 서로 다른 초기화된 잠금이다. T1은 A 잠금 성공 뒤 B를 요청하고, T2는 B 잠금 성공 뒤 A를 요청한다. 두 작업자가 첫 잠금을 모두 얻은 일정에서 소유와 대기를 추적하라.

  1. T1 소유=A, 요청=B이다.
  2. T2 소유=B, 요청=A이다.
  3. A는 T1이 놓아야 T2가 얻고, B는 T2가 놓아야 T1이 얻는다. 각 작업자는 두 번째 잠금을 얻기 전 첫 잠금을 놓지 않는다고 가정한다.
  4. 소유·대기가 T1→B→T2→A→T1의 고리를 이루어 진행하지 못한다.
  5. T2도 A부터 요청하게 바꾸면 T1이 A를 가진 동안 T2는 B를 얻기 전에 기다린다. T1은 비어 있는 B를 얻고 일을 마친 뒤 풀 수 있다.

주어진 일정은 교착이다. 두 경로 모두 A→B 순서로 바꾸면 이 잠금 순환을 없앤다. 모든 경로가 같은 규칙을 따라야 한다.

종이와 본문으로 직접 해보기

지연 취소가 활성화된 작업자가 m을 가진 채 cond_wait에 들어가 대기 중이다. 취소 요청이 처리될 때 cleanup은 m을 소유한 상태인가? 요청 성공만 보고 다른 스레드가 m을 파괴해도 되는가?

힌트 보기

wait의 취소 규칙과 대상 종료 확인을 따로 생각한다.

풀이 보기

cleanup 실행 전에 m이 다시 획득되므로 잠금 해제 정리가 필요하다. 요청 성공만으로 파괴하면 안 된다. 합류로 종료를 확인하고 다른 사용자가 없는지도 확인한 뒤 자원을 파괴한다. 정리가 실제로 완료되었는지까지 이론만으로 실행 결과처럼 주장할 수는 없다.

오해와 반례

pthread_cancel이 0을 반환하면 대상이 끝났고 모든 잠금도 풀렸다.

0은 요청 성공이다. 취소가 비활성화되어 있으면 처리되지 않을 수 있고, 자원 정리도 프로그램의 책임이다. 조건 대기에서 취소 시 재획득되는 잠금은 올바른 cleanup 없이 남을 수 있다. 합류와 정리 규칙을 함께 확인해야 한다.

한 단계 더

초기 합계 0에서 A와 B가 모두 0을 읽고 각각 1을 계산해 두 번 1을 쓰는 추상 단계표를 그리면 최종값은 1이다. mutex로 각 읽기·계산·쓰기를 한 묶음으로 직렬화하면 0→1→2다. 첫 표는 위험의 설명 모형이며 C 데이터 경쟁 프로그램의 실제 실행 결과를 예측한 것이 아니다.
