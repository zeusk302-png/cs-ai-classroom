공유메모리와 메시지 큐

두 프로그램이 같은 자료를 사용하려면 하나의 주소를 서로 보내면 될까?

준비 개념과 학습 목표

준비 개념

  • 프로세스별 가상 주소공간

  • 배열의 크기와 바이트

  • 생산자와 소비자

학습 목표

  • 공유 영역과 메시지 전달의 차이를 설명한다.

  • 공유 자료의 상대 위치와 형식 약속을 계산한다.

  • POSIX 메시지 우선순위와 수신 순서를 구별한다.

공유 위치를 담은 메시지가 왔으면 그 자리의 자료도 그대로일까?

새 종이 프로토콜의 공유 객체 길이는 512바이트이고 헤더는 48바이트, 슬롯 하나는 20바이트다. 프로세스 A와 B의 매핑 시작은 각각 0x2000과 0x9000이다. 인덱스 7의 슬롯 시작은 48 + 7×20 = 188 = 0xBC이므로 주소는 각각 0x20BC와 0x90BC다. 한 프로세스의 주소 숫자 대신 객체 세대·슬롯 인덱스·슬롯 세대·실제 길이를 전달한다.

헤더 뒤의 464바이트에는 완전한 슬롯 23개가 들어가고 4바이트가 남는다. 마지막 인덱스 22의 시작은 488이며 끝은 508이다. 인덱스 23의 시작 508만 확인하면 그 주소가 객체 안에 있으므로 허용하기 쉽지만, 끝 528은 객체 밖이다. 정수 계산이 표현 범위를 넘지 않는 방법으로 인덱스와 길이 모두 검사하고, 실제 읽기에는 정렬·자료 형식·동기화 조건도 필요하다.

생산자는 슬롯 7의 세대 4에 자료 cat을 쓴 뒤 알림 N=(객체 X, 슬롯 7, 세대 4, 길이 3)을 큐에 넣는다. 소비자 확인 전에 같은 슬롯을 세대 5의 dog로 재사용하면 옛 알림은 여전히 세대 4를 가리키는데 현재 바이트는 dog다. 큐가 알림을 전달한다고 공유 자료의 수명까지 고정해 주지는 않는다. 이 프로토콜에서는 소비자가 읽고 확인을 반환할 때까지 생산자가 슬롯을 재사용하지 않는 소유권 규칙을 채택한다.

별도 POSIX 큐의 mq_msgsize는 16이다. 현재 메시지 길이가 3이어도 수신 버퍼 크기가 3이면 EMSGSIZE이며 최소 16을 제공해야 한다. 성공 반환 길이 3만큼만 실제 메시지로 해석한다. 높은 우선순위는 이미 대기 중인 메시지 사이의 선택 규칙이다. 먼저 꺼낸 낮은 우선순위 메시지를 미래의 높은 우선순위 메시지가 되돌려 바꾸지는 않는다. 실제 큐 실행이나 처리율 측정은 하지 않았다.

먼저 확인할 개념
  • 공유 객체의 상대 위치와 큐 경계

    서로 다른 매핑 주소에서 슬롯 전체 범위를 검사하고 알림과 자료 수명을 나눈다.

  • 세대와 객체의 수명

    객체 이름뿐 아니라 실제 객체와 슬롯 세대를 함께 확인한다.

같은 자료와 같은 주소는 다르다

프로세스는 각자의 가상 주소공간을 가진다. 두 프로세스가 같은 POSIX 공유메모리 객체를 MAP_SHARED로 매핑해도 시작 가상 주소는 다를 수 있다. 한쪽에서 유효한 포인터 숫자를 그대로 보내 다른 쪽에서 사용하면 안전하지 않다. 공유 객체 안의 상대 오프셋과 자료 형식을 약속하면 각자의 시작 주소에 오프셋을 더해 위치를 찾을 수 있다.

shm_open은 객체를 생성하거나 열고 파일 디스크립터를 돌려준다. 새 객체의 길이는 0이므로 생성 담당자가 ftruncate로 크기를 정한 다음 mmap으로 연결한다. 초기화 완료를 알리는 동기화도 필요하다. 공유 영역에 보인다는 것만으로 여러 필드의 일관된 읽기와 갱신 순서까지 자동 해결되지 않는다.

메시지는 경계를 가진 전달이다

POSIX 메시지 큐에서는 mq_send로 하나의 메시지를 넣고 mq_receive로 하나를 꺼낸다. 이는 임의 바이트 흐름을 읽는 것과 달리 메시지 경계를 보존하는 방식이다. 양쪽은 메시지 형식, 허용 크기, 길이의 해석을 함께 약속해야 한다. 수신 버퍼가 큐의 최대 메시지 크기보다 작으면 오류가 날 수 있다.

POSIX 큐는 높은 우선순위 메시지를 먼저 전달하고 같은 우선순위에서는 먼저 보낸 것을 먼저 받는다. 따라서 전역적인 발송 순서와 수신 순서는 항상 같지 않다. 큐가 가득 차면 설정에 따라 보내기가 기다리거나 실패할 수 있어 생산 속도와 소비 속도의 차이를 처리해야 한다.

자료 이동과 조율을 함께 설계한다

공유메모리는 큰 자료를 공동으로 접근하는 데 유용하지만 누가 언제 쓰고 읽는지, 부분 갱신을 어떻게 막을지 규칙을 별도로 정한다. 메시지 큐는 전달 경계와 순서를 운영체제에 맡기는 대신 큐 용량과 메시지 크기 제한을 고려한다. 어느 방식이 항상 빠르다는 결론은 실제 측정 없이 내리지 않는다.

이 단원의 주소와 크기는 종이 계산용 가정이다. 운영체제 인터페이스 설명은 Linux의 POSIX API를 기준으로 하며 Windows API나 System V IPC와 이름과 수명 규칙을 섞지 않는다.

중간 과정을 따라가는 예제

가상 공유 객체의 크기는 4096바이트이고 헤더는 32바이트, 레코드는 16바이트다. A의 매핑 시작은 0x100000, B는 0x700000이다. 0번부터 세는 레코드 3의 두 주소와 저장 가능한 레코드 수를 구하자.

  1. 레코드 3의 상대 오프셋은 32+3×16=80=0x50이다.

  2. A에서 주소는 0x100050, B에서는 0x700050이다. 객체 내 같은 레코드지만 숫자가 다르다.

  3. 헤더를 뺀 공간은 4096−32=4064바이트이고 4064/16=254다.

  4. 레코드 인덱스는 0~253이다. 마지막 레코드 시작은 32+253×16=4080이며 끝은 4096으로 객체 안에 맞는다.

각 주소는 0x100050과 0x700050이며 최대 254레코드다. 상대 오프셋 80은 양쪽에서 공유할 수 있는 위치 약속이다.

시작만 범위에 있는 마지막 후보

위 객체의 인덱스 23을 시작 주소만 보고 읽겠다고 했다. 최대 개수와 후보 범위를 구하라.

  1. (512 − 48)//20은 23이고 유효 인덱스는 0부터 22까지다.

  2. 인덱스 23의 범위는 [508,528)이며 객체 [0,512)에 포함되지 않는다. 마지막 정상 슬롯은 [488,508)이다.

완전한 슬롯은 23개이고 남는 공간은 4바이트다.

시작점 포함을 전체 범위 포함으로 확대하지 않는다.

우선순위의 현재 대기 집합

큐가 비어 있다. A의 우선순위 1 메시지를 넣고 즉시 성공 수신한다. 그 뒤 B와 C의 우선순위 5 메시지를 이 순서로 넣어 모두 수신한다. 순서는?

  1. 첫 수신 시 대기 메시지는 A뿐이므로 A다.

  2. 다음에는 같은 우선순위에서 먼저 들어온 B, 이어 C다.

전체 수신 순서는 A,B,C다. 모두 넣은 뒤 수신하는 별도 모형에서는 B,C,A다.

비교할 점

미래 도착이 과거 성공 수신을 선점하지 않는다.

오해와 반례

공유메모리에 포인터를 넣으면 모든 프로세스에서 바로 사용할 수 있다.

프로세스별 매핑 주소가 달라 포인터 숫자의 의미가 달라질 수 있다. 객체 기준 오프셋이나 식별자로 표현하고 범위를 확인해야 한다. 동일 가상 주소 매핑은 별도의 제약이며 여기서는 가정하지 않았다.

허가 두 개가 있어도 두 생산자가 서로 다른 칸에 쓸까?

새 두 칸 순환 버퍼에서 empty=2, full=0, write_index=0이다. 두 생산자 A/B가 각각 wait(empty)에 성공하면 empty는 0이 된다. 하지만 두 생산자가 일반 write_index를 동시에 읽어 모두 0을 선택하면 같은 칸을 덮어쓸 수 있다. 용량 허가는 쓰기 위치의 배정 자체를 서로 다른 칸으로 만들어 주지 않는다.

이 설계는 프로세스 공유 세마포어 mutex를 1로 시작하고, 생산자가 empty 허가를 얻은 뒤 mutex를 획득하여 슬롯 쓰기와 write_index 갱신을 함께 보호한다. 슬롯을 쓴 후 인덱스를 다음 칸으로 옮기고 mutex를 반환한 뒤 full을 알린다. 소비자도 full 허가를 얻고 같은 mutex로 읽기와 read_index 갱신을 보호한 후 empty를 반환한다. 여기서는 모든 자료 연산이 정해진 짧은 임계구역에서 완료되고 상대 순서가 잘못 섞이지 않는 추상 모형이다.

모든 참가자가 이 순서를 쓰는 이유가 있다. 소비자가 먼저 mutex를 얻고 full=0에서 기다리면 생산자는 full을 만들 자료를 쓰기 위해 mutex를 기다린다. 소비자는 자료를 기다리고 생산자는 소비자가 쥔 mutex를 기다리는 순환 대기가 가능하다. 용량/자료 허가를 먼저 확보하고 mutex 안에서는 비어 있음이나 채워짐을 기다리지 않는 순서를 지킨다.

sem_wait의 EINTR 실패에서는 허가 값이 바뀌지 않는다. 실패를 성공처럼 처리하여 자료를 쓰거나 허가를 반환하지 않는다. sem_timedwait는 절대 시각의 제한을 사용하고, 허가를 즉시 얻을 수 있다면 이미 지난 제한도 성공을 막지 않는다. 이미 초기화한 sem_t에 sem_init를 다시 호출하는 것은 정의되지 않은 동작이며 회복 기법으로 채택하지 않는다. 세마포어의 배치와 pshared 설정, 초기화 담당자와 준비 완료 확인도 필요하다.

먼저 확인할 개념
  • 용량 허가와 삽입 위치 보호

    여러 생산자가 같은 인덱스를 선택할 수 있어 허가 수와 상호배제를 분리한다.

  • 초기화 완료와 재초기화 위험

    정상 사용 중인 세마포어를 회복 명목으로 다시 초기화하지 않는다.

정수는 기다릴 수 있는 허가 수다

POSIX 세마포어의 값은 음수가 되지 않는 허가 수로 생각할 수 있다. sem_wait가 성공하면 하나를 줄이고 값이 0이면 허가를 얻을 때까지 기다린다. sem_post는 하나를 늘린다. 실제 구현에서 깨어난 대기자가 허가를 곧바로 소비할 수 있으므로 숫자 관찰만으로 모든 대기자의 상태를 판단하지 않는다.

동기화 연산은 일반 정수 변수의 읽기·쓰기와 다르다. 두 프로세스가 동시에 일반 변수의 값을 읽고 감소시키면 같은 허가를 중복 사용하기 쉽다. 라이브러리의 연산 성공 여부와 함께 동기화 규칙을 지켜야 한다.

한 칸을 비었음과 채워짐으로 나눈다

하나의 공유 칸에서 empty를 1, full을 0으로 시작한다. 생산자는 wait(empty)에 성공한 뒤 자료를 쓰고 post(full)을 한다. 소비자는 wait(full)에 성공한 뒤 자료를 읽고 post(empty)을 한다. 쓰기를 끝내기 전에 full을 알리면 소비자가 미완성 자료를 읽을 수 있다.

여기서는 생산자 하나와 소비자 하나, 전달 칸 하나를 가정한다. 여러 칸의 순환 버퍼와 여러 생산자라면 허가 개수만으로 삽입 위치의 갱신이 보호되지 않을 수 있어 별도의 상호배제와 위치 규칙이 필요하다. 일반 세마포어는 mutex의 소유자 규칙이나 소유자 사망 복구를 자동으로 제공하지 않는다.

세마포어 자체도 올바른 곳에 있어야 한다

이름 있는 세마포어는 두 프로세스가 같은 이름으로 열 수 있다. 이름 없는 프로세스 공유 세마포어는 공유메모리 안에 두고 sem_init의 pshared를 0이 아닌 값으로 설정한다. 각 프로세스의 별도 일반 변수에 같은 초기값을 넣는 것은 같은 세마포어를 공유하는 것이 아니다.

sem_wait는 신호 때문에 EINTR로 실패할 수 있다. 계속 기다릴 의도인지 종료할 의도인지 정책을 정하고 실패한 wait를 성공처럼 취급하지 않는다. 시간 제한은 무한 대기를 줄일 수 있지만 제한 만료가 상대 프로세스의 확정 사망 증거는 아니다. 실제 동시 실행 시험은 수행하지 않았다.

중간 과정을 따라가는 예제

한 칸 공유 버퍼에서 empty=1, full=0이다. 생산자와 소비자의 정상적인 한 번 전달을 상태와 값 42로 추적하자.

  1. 소비자가 먼저 wait(full)을 호출하면 full=0이라 기다린다. 이 대기만으로 음수 값이 되지는 않는다.

  2. 생산자의 wait(empty)가 성공해 empty=0이 되고 칸에 42를 쓴다.

  3. 생산자가 post(full)을 하면 소비자가 허가를 얻어 wait(full)을 끝낸다. 소비자가 허가를 소비한 뒤 full=0이다.

  4. 소비자가 42를 읽고 post(empty)을 하면 empty=1, full=0으로 돌아온다.

한 값 42가 전달되고 칸은 다시 비어 있다. post 직후의 순간 관찰값과 대기자가 허가를 소비한 뒤 값을 구별했다.

조건을 바꾸어 비교하기

허가 수는 맞고 위치는 틀린 실행

A/B가 empty를 얻고 둘 다 write_index=0을 읽었다. A가 10, B가 20을 칸 0에 쓰고 각자 full을 알렸으며 인덱스도 각각 1로 썼다. 무엇이 잘못인가?

  1. 최종 empty는 0, full은 2지만 칸 0은 20이고 칸 1은 미작성이다.

  2. full 두 개는 두 개의 독립된 유효 자료라는 계약을 만족하지 않는다. 슬롯 쓰기와 인덱스 갱신을 같은 mutex 임계구역으로 묶는다.

용량 허가 성공만으로 데이터 구조 불변식이 보존되지 않는다.

일반 인덱스 갱신이 우연히 같았다는 이유로 안전하다고 결론 내리지 않는다.

자료 허가를 mutex 안에서 기다린 오류

full=0에서 소비자가 mutex를 얻고 wait(full)을 호출했다. 생산자는 empty를 얻고 mutex를 기다린다. 두 대기를 추적하라.

  1. 소비자는 mutex를 보유한 채 full을 기다린다.

  2. 생산자가 full을 늘리려면 mutex를 얻고 자료를 써야 하지만 소비자가 반환하지 않는다.

이 이력은 순환 대기다. 소비자는 full을 먼저 얻고 그 다음 mutex를 얻도록 고친다.

이름이 같고 값도 같으면 재시도 대상까지 같을까?

새 참가자 A/B가 이름 /work로 객체 X를 매핑했고 헤더의 실행 세대는 7이다. 관리자가 이름을 지운 후 C가 같은 이름으로 객체 Y를 새로 만들고 실행 세대를 8로 초기화한다. A/B의 기존 매핑은 X, C의 매핑은 Y다. B가 X 매핑과 열린 참조를 정리하고 새 이름을 열어 Y로 이동해도 A는 자동으로 따라오지 않는다.

같은 문자열 /work는 이름 조회의 입력이다. 이미 받은 객체 연결은 별도로 존재한다. Y의 생성 직후 길이는 0이며 크기·헤더·세마포어를 성공적으로 준비한 뒤 동기화한 준비 완료를 공개한다. O_CREAT|O_EXCL의 원자적 생성자 선출과 전체 초기화 완료를 하나의 사건으로 섞지 않는다. 오류 원인이 권한인지, 부재인지, 일시적 허가 부족인지도 각각 처리한다.

X에서 잔액은 10이다. 요청 ID R과 내용 +4를 업무 상태와 완료 원장에 원자적으로 반영하여 잔액 14와 R의 결과 14를 확정했지만 응답 전에 처리자가 종료했다고 가정한다. 같은 R/+4의 재전송은 저장 결과 14를 반환하고 다시 더하지 않는다. 그런데 Y를 잔액 10과 빈 원장으로 만든 뒤 R을 처리하면 Y도 14가 된다. 두 잔액 숫자가 같다는 사실은 한 업무 권한 영역에서 단 한 번 효과가 있었다는 증거가 아니다. 객체 교체 시 상태/원장 이관·옛 처리자 격리·새 세대 합류를 조율해야 한다.

이 원자성은 큐 API가 제공하는 기능이 아니라 별도 업무 저장 설계의 명시적 가정이다. 원장을 먼저 쓰고 업무 반영 전 종료하면 R은 완료로 보이는데 잔액은 10이다. 업무를 먼저 +4하고 원장 전 종료하면 재시도에서 잔액이 18이 될 수 있다. 같은 ID에 다른 내용 +5가 오면 저장 +4와 충돌로 거부하여 옛 요청의 결과를 다른 업무에 재사용하지 않는다. 실제 저장소·장애 주입·복구 훈련은 수행하지 않았다.

  • 자료 확정과 허가 공개

이름과 객체는 수명이 다르다

POSIX 공유메모리의 close는 열린 파일 디스크립터를 닫는다. mmap 이후 디스크립터를 닫아도 매핑은 계속 유효하며 munmap은 그 매핑을 해제한다. shm_unlink는 이름을 제거한다. 이미 매핑한 프로세스는 이를 계속 사용할 수 있고, 같은 이름을 O_CREAT로 다시 만들면 기존과 구별되는 새 객체가 된다.

메시지 큐도 mq_close와 mq_unlink의 역할을 구별한다. 이름을 제거한 큐는 새로 같은 이름으로 열 수 없지만 이미 열린 디스크립터를 통한 사용은 가능하고 마지막 열린 참조를 닫으면 파괴된다. 시스템 종료까지 남을 수 있는 커널 객체를 평범한 지역 변수의 수명처럼 생각하지 않는다.

생성 경쟁과 초기화 경쟁은 다르다

O_CREAT와 O_EXCL을 함께 사용하면 이미 존재하는 이름에 EEXIST가 나므로 한 생성 담당자를 정하는 데 도움이 된다. 그러나 객체 생성 성공이 크기 설정·헤더 작성·세마포어 초기화 완료를 뜻하지는 않는다. 사용자는 준비 완료를 별도 프로토콜로 확인해야 한다.

헤더에 형식 버전, 전체 크기, 실행 세대 식별자와 상태를 넣으면 오래된 객체를 구별하는 데 도움이 된다. 이 필드를 읽고 쓰는 일 자체도 적절히 동기화한다. 다른 프로세스가 사용 중인 객체에 함부로 O_TRUNC를 쓰거나 세마포어를 다시 초기화하는 것은 복구가 아니라 자료 손상일 수 있다.

오류에 따라 다른 행동을 정한다

ENOENT는 이름이 없음을, EACCES는 권한 문제를 뜻한다. 둘을 같은 이유로 취급해 무조건 다시 생성하면 소유권이나 환경 문제를 숨길 수 있다. EINTR은 기다림이 신호에 끊긴 상황, 비차단 수신의 EAGAIN은 지금 메시지가 없다는 상황이다. 재시도 가능한 순간 상태와 설정 실패를 구별한다.

상대가 처리한 뒤 응답 전에 죽으면 보내는 쪽은 처리 여부를 모를 수 있다. 재전송 정책에는 요청 식별자와 중복 처리 방지, 결과 확인 규칙이 필요하다. 시간 제한이 생겼다고 이름을 지우고 새 객체를 만들면 기존 참가자와 새 참가자가 갈라질 수 있다. 아래 세대 예제는 설계 추적이며 실제 충돌 복구 실험은 아니다.

응답 제한이 끝났으니 X 이름을 지우고 Y를 만들면 모든 참가자가 복구된다는 정책을 고쳐라.

힌트 1

힌트 2

부재·느림·처리 완료 후 응답 유실을 구별한다.

  2. 새 Y의 상태/원장 이관과 준비 공개, 옛 참조 정리를 각각 확인한다.

연습 3 · 직접 만들어 보기

중단 위치가 원장 전/업무 전으로 나뉘는 비원자 설계를 감사하는 표를 만든다. 초기 10과 +4를 사용하라.

힌트 1

업무 먼저와 원장 먼저의 두 순서를 분리한다.

힌트 2

재시도의 누락 또는 추가 효과까지 계산한다.

풀이와 답 확인

  1. 업무 먼저 중단은 잔액 14/원장 없음이며 단순 재시도에서 18이 될 수 있다.

  2. 원장 먼저 중단은 잔액 10/완료 기록이며 건너뛰는 재시도 후에도 10이다. 원자 확정 가정에서는 14/완료가 함께 존재한다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

X에 R의 결과 14가 확정됐지만 Y는 잔액 10/빈 원장이다. Y가 R을 반영해 14를 만들었다. 잔액 일치만으로 세대 전환의 정확성을 증명할 수 있는가?

힌트 1

각 객체의 업무/원장 쌍을 따로 적는다.

힌트 2

풀이와 답 확인

  1. X와 Y의 숫자는 모두 14지만 별개의 객체와 원장이다.

  2. 상태/원장 이관의 일관성, 옛 권한 격리, 참가자 합류를 확인해야 한 업무 영역의 복구를 주장할 수 있다.

완료 숫자 하나는 X/Y의 분리와 후속 중복 가능성을 숨긴다.

한 단계 더

요청 17을 처리한 뒤 응답 전에 소비자가 종료되었다고 가정하자. 생산자가 요청 17을 다시 보내면 중복 효과가 생길 수 있다. 같은 요청 ID의 완료 결과를 기록하는 설계와 그냥 재전송하는 설계의 차이를 적어 보자. 기록을 어디에 두고 언제 확정할지도 별도 의무이며 큐 사용만으로 exactly-once 효과가 보장되지는 않는다.

A/B 매핑 주소와 슬롯 범위를 계산하고, 소비자 확인 전에 dog로 재사용하는 정책을 수정하라. 별도 두 칸 버퍼에서 A/B가 각각 empty 허가를 얻은 뒤 정상 mutex 순서로 10과 20을 공개한다. 소비자가 10만 읽고 빈 칸을 반환한 상태의 empty/full/P/C를 구하라. 끝으로 초기 잔액 10에서 R/+4를 업무와 원장에 원자 확정했으나 응답이 유실됐다. 같은 R 재전송과 새 S/+3의 결과를 구하고, X를 이름만 같은 Y로 바꾸는 정책에 필요한 추가 전환 조건을 적어라.

힌트 1

슬롯의 전체 범위와 소비자 확인까지의 소유권을 함께 검사한다.

힌트 2

예약을 포함한 허가 총수와 요청 ID/내용/객체 세대를 각각 추적한다.

풀이와 답 확인

  1. 슬롯 7은 [188,208)이며 A 주소는 0x20BC, B 주소는 0x90BC다. 전체 23개 슬롯과 잔여 4바이트다. 소비자 확인 전 세대 4를 재사용하지 않도록 하고 알림/현재 세대·길이·소유권을 대조한다.

  2. 두 생산자 공개 뒤 empty=0, full=2, P=0, C=0이다. 소비자 획득 중에는 full=1, C=1이며 반환 뒤 empty=1, full=1, P=0, C=0으로 총수 2를 유지한다.

  3. 원자 확정한 R의 재시도는 결과 14를 반환하고 다시 더하지 않는다. 새 S/+3의 결과와 잔액은 17이다. R과 다른 내용의 충돌도 검사한다.

  4. Y 생성은 기존 X 참가자의 자동 이주가 아니다. 상태와 원장의 일관된 이관, 옛 세대 권한 격리, 새 준비 완료와 참가자 합류, 마지막 참조 정리를 따로 확인한다.

주소 0x20BC/0x90BC, 슬롯 [188,208), 소비 완료 뒤 empty/full/P/C=1/1/0/0, R 결과 14와 S 결과 17이다. 이 값과 정책은 손으로 지정한 추상 모형이며 실제 IPC·장애·학생 실험이 아니다.
