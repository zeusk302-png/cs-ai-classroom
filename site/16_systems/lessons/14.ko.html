프로파일링과 반복 측정

한 번 빨랐다는 기록으로 다음에도 빠르다고 말할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 평균과 중앙값

  • 함수와 입력

  • 초와 밀리초

학습 목표

  • 측정 대상과 범위를 명시한다.

  • 반복 기록과 대표값을 함께 비교한다.

  • 프로파일 비율과 전체 개선을 구별한다.

같은 프로그램을 두 번 비교해도 측정 경계에 따라 결론이 바뀌는가?

측정값은 코드 이름뿐 아니라 경계·반복 수·입력·상태와 함께 기록한다. 아래 장부의 시간은 실제 실행 결과가 아닌 가상 값이다. 준비가 60 ms, 본문 한 번이 0.2 ms인 일을 100번 수행하면 본문만 20 ms, 준비까지 80 ms다. 두 합계 모두 계산상 맞지만 서로 다른 질문에 답한다. 매 호출에 준비를 다시 수행하는 계약에서는 총 6020 ms가 필요하므로 한 번 준비하는 배치와 비교할 때도 범위를 밝혀야 한다.

timeit의 setup과 본문 경계를 읽으면 준비를 제외한 수치와 실제 요청 지연을 구별할 수 있다. 반복 벡터의 최솟값이 어떤 조건에서 유용한지와 사용자의 평균 대기 질문은 별도다. 첫 실행의 상태를 그대로 다음 후보가 물려받으면 후보 순서 효과가 섞인다. 원문 예시 시간을 새 프로그램의 실제 기록으로 복사하지 않는다.

프로파일러의 포함 시간은 자식 호출을 포함할 수 있다. 한 부모 호출이 30 ms이고 그 안의 자식이 20 ms라면 부모 자체 시간은 10 ms다. 부모 포함 30과 자식 포함 20을 더한 50은 이 직렬 호출의 경과 30과 다르다. 호출 트리의 합산 규약을 먼저 정해야 병목의 비중도 정의할 수 있다.

    base의 wall/CPU 구별과 반복 통계를 새 배치 경계에 적용한다.

  • 측정 비중과 전체 병목

    부분 지표를 전체 경과 시간의 분모와 혼합하지 않는다.

먼저 같은 일을 비교한다

실행 시간은 입력 크기·내용, 출력의 정확성, 컴파일 옵션, 실행 환경과 측정 범위에 따라 달라진다. 파일 읽기·초기화·네트워크를 포함했는지, 이미 준비된 함수 호출만 재었는지 적는다. 같은 결과를 내는지 먼저 확인한다.

벽시계 시간은 기다림도 포함한 시작부터 끝까지의 시간이다. CPU 시간은 CPU에서 실행한 시간을 센다. 여러 스레드의 CPU 시간 합은 벽시계보다 클 수 있다. 두 숫자의 단위가 같아도 같은 질문에 답하는 것은 아니다.

반복과 준비 단계를 기록한다

캐시를 데운 뒤 처리하는 경우와 첫 실행은 다른 작업이다. 반복 횟수·순서·준비 단계·타이머·백그라운드 부하를 기록한다. 준비를 제외했으면 결과에도 제외 범위를 명시한다. 초기화가 서비스 실제 비용이라면 전체 비용을 별도로 측정한다.

작은 코드 구간에서는 타이머와 반복 루프의 overhead가 중요하다. Python timeit은 setup을 제외하고 기본적으로 GC를 끄므로 allocation을 포함한 실제 프로그램과 다른 조건일 수 있다. 공식 문서의 최소값 해석은 작은 snippet의 방해가 적은 비용을 살피는 규약이며 서비스 꼬리 지연을 대신하지 않는다.

프로파일은 개선 후보를 찾는다

프로파일링은 어느 함수나 명령에 시간이 귀속되는지 살피는 작업이다. 표본 비율은 실제 시간의 추정치일 수 있고 계측도 실행을 바꿀 수 있다. 호출자의 포함 시간과 함수 자체 시간을 중복 합산하지 않는다.

전체 시간의 비율 p인 부분만 s배 빠르게 하고 다른 비용이 그대로면 전체 speedup은 1/[(1−p)+p/s]다. 이 이상적인 비용 분해의 가정이 바뀌면 식도 다시 검토한다. hot 함수가 보였다는 이유만으로 전체 프로그램 개선을 확정하지 않는다.

모든 행은 준비 60 ms와 본문 0.2 ms를 가정한 합이다. 마지막 열은 서로 같은 측정 경계라는 뜻이 아니며 실제 timeit 실행은 하지 않았다.

중간 과정을 따라가는 예제

가상 반복 기록 A=[10,11,9,30,10] ms와 B=[8,9,8,9,8] ms의 중앙값과 평균을 비교하라. 이는 실제 측정 기록이 아니다.

  1. A를 정렬하면 [9,10,10,11,30]이므로 중앙값은 10 ms이고, 평균은 70/5=14 ms다.

  2. B를 정렬하면 [8,8,8,9,9]이므로 중앙값은 8 ms이고, 평균은 42/5=8.4 ms다.

  3. 중앙값 기준 시간 감소는 (10−8)/10=20%이고 speedup은 10/8=1.25다. 평균 기준 감소는 40%다. 대표값에 따라 해석이 달라지므로 다섯 원기록도 함께 둔다.

이 가상 배열에서는 B의 중앙값이 20% 작다. 실제 장비 성능이나 통계적 유의성을 검증한 결과가 아니다.

조건을 바꾸어 비교하기

작은 질의의 가중치가 뒤집힌 요약

두 고정 입력의 A 시간은 1과 100 ms, B 시간은 0.5와 90 ms다. 입력별 speedup 평균과 전체 시간을 합친 speedup을 계산하라.

  1. 입력별 비는 2와 10/9라 산술평균은 14/9다.

  2. 각 입력을 한 번씩 처리하면 A 합 101, B 합 90.5이고 전체 비는 202/181이다.

14/9와 202/181은 다르다. 전체 작업 비율은 입력별 비의 단순 평균이 아니라 B 시간으로 가중한 평균이다. 어느 쪽을 보고할지는 업무의 입력 비중과 질문에 따라 정한다.

비교할 점

같은 두 행이어도 평균하는 값과 가중치가 다르면 수치가 달라진다.

포함 시간의 중복을 제거한다

부모 포함 30 ms, 그 안의 자식 포함 20 ms를 합쳐 총 50 ms라고 했다. 호출이 한 번씩 직렬로 중첩될 때 고쳐라.

  1. 부모 자체 시간은 30−20=10 ms다.

  2. 자체 시간 10과 자식 20을 합하면 부모 전체 30 ms다.

두 포함 시간을 더하면 자식의 20 ms를 두 번 셌다. 이 장부의 전체 경과 시간은 30 ms다.

비교할 점

여러 스레드의 겹치는 경과 구간을 단순히 더하는 경우에는 다른 중복도 확인해야 한다.

종이와 본문으로 직접 해보기

전체 100 ms 중 한 함수가 40 ms를 사용한다는 가상 비중에서 그 함수만 두 배 빠르게 하면 전체 시간과 speedup은?

힌트 보기

나머지 60 ms를 그대로 둔다.

풀이 보기

40/2+60=80 ms이며 전체 speedup은 100/80=1.25다. 함수 두 배와 전체 두 배는 다르다.

오해와 반례

가장 느린 실행을 지우고 최솟값만 보이면 언제나 공정하다.

제외 사유를 정하지 않고 결과를 지우면 선택 편향이 생긴다. 작은 snippet의 최소 비용, 일반적 latency, 최악/꼬리 latency는 서로 다른 목적이다. 원자료와 선택 규약을 공개한다.

연습 1 · 값과 상태 예측

한 번 준비한 배치의 본문 반복 수를 200으로 늘리면 총 시간과 회당 배치 시간을 계산하라.

힌트 1

본문 시간은 200×0.2다.

힌트 2

준비 60은 한 번만 더한다.

풀이와 답 확인

  1. 본문 합은 40 ms다.

  2. 총 100 ms를 200으로 나누면 0.5 ms다.

총 100 ms, 회당 배치 시간 0.5 ms다. 본문 한 번의 가정 0.2 ms는 그대로다.

흔한 오답에서 다시 생각하기

회당 배치 값이 줄었으므로 본문 알고리즘도 빨라졌다.

준비 비용을 더 많은 호출로 나눈 효과일 수 있다.

연습 2 · 오류 찾아 고치기

A를 차가운 상태에서 12 ms, 뒤의 B를 따뜻한 상태에서 8 ms로 기록해 B가 1.5배 빠르다고 결론냈다. 어떤 추가 비교가 필요한가?

힌트 1

상태와 후보가 동시에 바뀌었다.

힌트 2

동일 상태의 A/B 또는 순서를 바꾼 반복을 설계한다.

풀이와 답 확인

  1. 입력·준비·캐시 조건을 맞춘 각 후보의 반복이 필요하다.

  2. B를 먼저 하는 블록과 A를 먼저 하는 블록을 함께 기록하되 상태 차이를 별도로 보고한다.

12/8은 이 두 가상 기록의 비지만 후보 자체의 인과 효과는 아직 식별하지 못했다.

흔한 오답에서 다시 생각하기

순서를 한 번 바꾸기만 하면 모든 잡음과 상태 효과가 제거된다.

순서 변경은 검사 설계의 일부이며 반복과 상태 계약까지 확인해야 한다.

연습 3 · 직접 만들어 보기

위 두 입력에서 B가 전체 업무를 처리하는 speedup을 입력별 비의 가중합으로 나타내라.

힌트 1

B 시간 비중은 0.5/90.5와 90/90.5다.

힌트 2

분수로 1/181과 180/181이다.

풀이와 답 확인

  1. 가중합은 (1/181)×2+(180/181)×(10/9)다.

  2. 결과는 202/181로 합계 시간의 비와 같다.

분모가 동일한 전체 업무의 B 시간 가중치를 쓰면 두 계산이 일치한다.

흔한 오답에서 다시 생각하기

A 시간 비중을 써도 같은 speedup 평균이다.

평균하는 비 A/B에는 B 시간 가중치가 필요하다. 다른 가중치는 다른 요약이다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

준비 60 ms와 본문 0.2 ms에서 한 번 준비한 배치의 회당 값이 0.3 ms 이하가 되는 최소 양의 정수 반복 수 n을 구하라.

힌트 1

회당 값은 60/n+0.2다.

힌트 2

60/n≤0.1을 푼다.

풀이와 답 확인

  1. n≥600이다.

  2. n=600이면 준비를 포함한 총 180 ms, 회당 0.3 ms다.

최소 n은 600이다. 실제 준비 시간이나 본문 시간이 반복 수와 함께 달라지면 이 고정 모형을 다시 검사한다.

흔한 오답에서 다시 생각하기

최솟값 0.2에 가까워지므로 모든 n에서 0.3 이하다.

극한과 유한 n의 부등식은 다르다.

한 단계 더

p=.4인 함수가 무한히 빨라져도 전체 시간은 60 ms이므로 최대 speedup은 5/3이다. 이 한계는 다른 비용이 불변이라는 모델의 결론이다. 실제 개선 전후의 출력·환경·단계별 비용을 다시 확인할 계획을 작성하라.

소단원 14.2

CPU·메모리 병목 구분

CPU가 바쁘다는 이유만으로 산술 연산이 병목인가?

준비 개념과 학습 목표

준비 개념

  • 명령과 메모리 읽기

  • 캐시와 miss

  • 단위와 비율

학습 목표

  • CPU 활동과 병목 원인을 구별한다.

  • miss 비율의 분모와 penalty를 해석한다.

  • 한 변수만 바꾼 비교로 가설을 점검한다.

miss rate와 CPI가 나빠졌는데 전체 시간이 줄 수 있을까?

지표의 분모가 바뀌면 비율의 방향과 절대 비용의 방향이 다를 수 있다. 같은 업무를 끝낸 가상 A는 load 100회·miss 10회·명령 200개·cycle 1000이고 B는 load 50회·miss 8회·명령 100개·cycle 800이다. load 기준 miss rate는 10%에서 16%로 증가하지만 miss 수는 줄고 cycle도 20% 줄었다. 명령 기준 CPI는 5에서 8로 늘어난다. 비율 하나만으로 전체 업무가 느려졌다고 결론내리지 않는다.

cycle 비를 경과 시간 비로 바꾸려면 동일한 주파수와 범위, 코어·대기 등의 조건을 추가해야 한다. 여기서는 cycle 장부만 비교한다. 실제 PMU의 이벤트 이름이 같은 모양이어도 대상과 제외 조건은 플랫폼에 따라 확인해야 한다. CPU 사용량과 유효 연산량도 동일하지 않다.

하드웨어 이벤트를 시간 일부에서만 세면 확대값은 추정이다. 별도 두 구간 각 5초 중 첫 구간에서만 실제 40개를 관찰하고 다음 구간을 관찰하지 않았다면 비례 확대는 80개다. 그러나 두 번째 구간 실제 수가 0인 모형의 전체는 40개이고, 80인 모형의 전체는 120개다. 관찰하지 않은 구간의 발생률 가정 없이 원래 총수를 유일하게 복구하지 못한다.

먼저 확인할 개념
  • CPU·메모리 지표의 분모

    base의 load miss와 LLC miss/전체 시간 구별을 명령 수까지 확장한다.

  • 동일 업무의 시간 비교

    후보별 요청·관찰 범위가 같아야 전체 업무의 비를 해석한다.

병목은 현재 작업과 자원의 관계다

CPU에서 실행 중인 코드는 산술 의존성, 명령 인출, 분기 예측, 캐시 miss로 인해 지연될 수 있다. CPU가 사용 중이라는 숫자만으로 계산 자원이 포화되었다고 판정하지 않는다. 메모리를 기다리는 실행도 CPU-bound 분석 안에 포함될 수 있다.

파일이나 네트워크 응답, 잠금, 스케줄링 대기는 또 다른 원인이다. wall과 CPU 시간 차이도 단서지만 여러 스레드와 계측 범위를 고려해야 한다. 한 카운터 값으로 모든 원인을 확정하지 않는다.

캐시 지표의 분모를 보존한다

miss rate는 정한 cache access 중 miss의 비율이다. load 명령 수, LLC access 수, 전체 명령 수는 다른 분모다. 하드웨어 event의 의미와 지원 여부를 확인하고 가상의 보편적인 event로 간주하지 않는다.

단순 직렬 모델에서 평균 접근 비용은 hit 비용+miss 비율×추가 miss penalty다. 실제 CPU는 여러 요청을 겹치고 prefetch하거나 캐시 계층을 거칠 수 있으므로 이 식을 전체 실행 시간과 동일시하지 않는다. 큰 대역폭 사용과 긴 접근 지연도 구별한다.

가설을 바꾸는 비교를 설계한다

같은 데이터와 출력에서 연속 접근과 큰 stride 접근, 작은 working set과 큰 working set을 비교하면 공간/시간 locality 가설을 조사할 수 있다. 반복 횟수·초기 cache 상태와 읽은 바이트를 통제해야 한다. 한 입력에 대한 개선을 모든 크기로 확대하지 않는다.

연산 의존성을 줄이는 변경과 데이터 배치를 바꾸는 변경을 동시에 하면 원인을 분리하기 어렵다. perf stat의 반복과 counters는 단서이며 동시측정 불가나 multiplexing은 비율 해석을 바꿀 수 있다. 결과가 예상과 다르면 가설을 고친다.

중간 과정을 따라가는 예제

가상 직렬 cache 모델의 hit 비용은 2 cycles이고 추가 miss penalty는 40 cycles다. 1000번의 접근 중 A는 100번 miss이고 B는 25번 miss일 때 평균 비용을 구하라.

  1. A의 miss 비율은 100/1000=.1이므로 2+.1×40=6 cycles/접근이다.

  2. B의 비율은 25/1000=.025이므로 2+.025×40=3 cycles/접근이다. miss 횟수는 네 배 줄었지만 접근 비용은 두 배다.

  3. 1000번 접근의 직렬 모델 비용은 각각 6000 cycles와 3000 cycles다. 실제 CPU 전체의 측정 시간이나 겹침 요청·다른 작업의 비용을 포함한 값은 아니다.

정한 직렬 모델에서는 평균 접근 비용이 6에서 3으로 줄었다. 전체 프로그램이 두 배 빨라짐을 보장하지 않는다.

조건을 바꾸어 비교하기

비율과 전체 cycle의 서로 다른 방향

A에서 B로 바뀐 miss 수·miss rate·cycle 및 IPC를 계산하라.

  1. miss 수는 10→8로 20% 감소하고 rate는 10%→16%로 6%p 증가한다.

  2. cycle은 1000→800으로 20% 감소한다. IPC는 200/1000=0.2에서 100/800=0.125다.

여러 비율은 악화돼도 전체 cycle은 감소한다. cycle 기준 speedup은 5/4다. 실제 경과 시간 speedup은 추가 주파수/범위 조건 없이는 확정하지 않는다.

비교할 점

분모가 다른 비율의 방향을 절대 업무량의 방향으로 바꾸지 않는다.

확대값은 누락 구간의 사실인가

10초 중 5초를 관찰해 40개를 셌다. 발생률이 동일하다는 가정으로 확대하고 두 가능한 실제 총수를 제시하라.

  1. 같은 발생률이면 40×10/5=80개를 추정한다.

  2. 미관찰 5초의 수가 0 또는 80이면 총수는 각각 40 또는 120개다.

관찰값 40과 추정값 80을 따로 기록한다. 실제 관찰하지 않은 5초가 균일했다고 확인한 것은 아니다.

캐시 충돌을 줄인 주소 변경이 전체 비용과 계약을 함께 개선하는가?

새 직접 사상 캐시는 block 16바이트·set 2개·set당 한 line이며 시작 상태는 비어 있다. 읽기 한 번은 1바이트이고 각 흐름은 따로 초기화한다. P의 주소는 0,32,0,32로 block 0과 2가 같은 set을 교체하므로 모두 miss다. Q는 0,48,0,48로 block 0과 3이 다른 set에 들어가 두 miss 뒤 두 hit다. 모형 주소를 바꾼 설명과 실제 배열의 논리 인덱스·범위 보존은 별도의 확인이다.

이 모형에서 hit 기본 비용 1, miss 추가 비용 9면 P의 접근 비용은 40, Q는 22다. 그런데 Q의 주소를 만드는 추가 작업 비용을 30으로 정하면 전체 Q는 52다. miss 감소라는 한 층의 개선이 전체 비용 개선을 보장하지 않는다. 추가 작업을 어느 범위에 포함했는지와 비용의 실제 측정 여부를 적는다.

기계어 명령 수가 줄었다는 관찰도 같은 경계를 요구한다. 실제 objdump는 대상 파일의 명령과 경우에 따라 소스 정보를 보여 주지만 그 출력만으로 각 입력의 실행 횟수·경과 시간·객체 안전성을 알지는 못한다. 아래에서는 파일을 역어셈블하지 않고 명시한 두 가상 흐름을 손추적한다.

실제 빌드의 명령을 읽는다

역어셈블은 실행 파일의 기계 명령을 사람이 읽을 수 있는 형태로 표시한다. 소스 줄의 개수와 실행 명령 수가 같지 않으며 최적화·inline·벡터화·debug 정보에 따라 대응이 달라진다. ISA와 compiler 옵션 및 분석할 함수 범위를 적는다.

objdump -d는 명령이 기대되는 section을 살피고 -D는 다른 section의 데이터도 명령처럼 해석할 수 있다. -S는 가능한 소스/명령 대응을 표시하지만 debug 자료가 필요할 수 있다. 여기서는 실제 executable을 만들거나 해체한 것이 아니라 도구의 해석 규약을 공부한다.

배치와 수명을 함께 본다

캐시의 블록 번호·set·tag로 주소 trace를 종이에 추적할 수 있다. 연속 요소를 재사용하면 같은 블록의 이익을 얻을 수 있지만 충돌이나 capacity 때문에 배치의 효과가 달라진다. 임의 주소 모델을 실제 malloc 주소로 오해하지 않는다.

할당기는 payload 이외에 header와 alignment padding을 사용한다. 요청 크기·동시 살아 있는 객체·전체 heap과 free 블록 분포를 구별한다. 큰 블록을 여러 요청에 재사용하면 호출 비용이 달라져도 수명·참조 공유·경계 안전성이 새로 필요하다.

가설과 검산을 연결한다

종이 cache trace가 좋아졌다는 결과는 locality 가설이다. 실제 miss counter·실행 시간과 대조해야 하며 명령이나 allocation 수가 동시에 바뀌면 효과를 따로 조사한다. 컴파일러는 alias와 부작용 때문에 겉보기 중복을 유지할 수 있다.

성능 비교 전에 같은 결과·정의된 산술·범위 안 접근·올바른 free를 확인한다. 프로그램에 오류가 있으면 빠른 결과도 의미가 없다. 실제 allocator policy, cache 구조, compiler 출력은 본문의 작은 모델과 구별한다.

중간 과정을 따라가는 예제

가상 cache는 블록 크기 B=16 byte, set 수 S=2, set당 line 수 E=1이며 처음 비어 있다. 한 byte씩 읽는 주소 [0,32,0,32]와 [0,16,0,16]을 비교하라.

  1. block=floor(address/16), set=block mod2, tag=floor(block/2)다. 첫 trace의 블록 번호는 [0,2,0,2]이고 둘 다 set 0에 들어가며 tag 0과 1이 번갈아 등장한다.

  2. 첫 trace는 매번 서로 퇴출하므로 miss가 4번이다. 둘째 trace의 블록 번호 [0,1,0,1]은 set 0과 1에 따로 남으므로 miss, miss, hit, hit 순서이며 miss가 2번이다.

  3. 각 접근은 한 byte로 정했다. 쓰기·prefetch·다층 cache·동시 접근은 모델에 없다. 실제 장비에서 이 비율을 측정한 결과가 아니다.

이 모델에서 주소 충돌을 줄이면 miss가 4번에서 2번으로 줄지만 실제 프로그램 속도는 별도 확인해야 한다.

조건을 바꾸어 비교하기

부분 개선과 전체 회귀

P에는 추가 작업이 없고 Q에는 추가 작업 30이 있다. 전체 비용을 비교하고 Q가 더 빠를 추가 작업 상한을 구하라.

  1. P 전체는 40이다. Q 전체는 22+30=52다.

  2. Q 추가 작업을 c≥0이라 두면 22+c<40은 c<18이다.

c=18이면 동률이고 c<18일 때만 이 고정 직렬 비용 모형에서 Q가 더 작다. 실제 CPU 시간은 미측정이다.

비교할 점

miss 수만 비교하면 빠진 주소 작업 때문에 최종 선택이 틀릴 수 있다.

동일 요청에서 다른 크기 올림

별도 가상 할당기는 헤더 8바이트이고 요청은 1과 9바이트다. 전체 크기를 각각 16 또는 8의 배수로 올리는 두 계약의 사용 크기와 요청 비율을 비교하라.

  1. 16의 배수 계약은 16과 32로 총 48이다.

  2. 8의 배수 계약은 16과 24로 총 40이다. 요청 합은 둘 다 10이다.

요청/사용 비율은 5/24와 1/4다. 첫 계약의 데이터 정렬 요구를 둘째가 만족하는지는 블록 시작/반환 위치를 따로 정해야 하며 이용률만으로 둘째를 합법한 대체 구현이라고 결론내리지 않는다.

비교할 점

크기를 줄이는 목적과 정렬·주소 계약을 만족하는 조건은 각각 검사한다.

종이와 본문으로 직접 해보기

가상 블록 규약 size=16×ceil((payload+8)/16)에서 payload가 12 byte와 20 byte인 동시 블록의 크기, 요청 payload 합/블록 합을 구하라.

힌트 보기

각 요청에 header 8 byte를 더한 뒤 16의 배수로 올린다.

풀이 보기

각 블록은 32 byte이므로 블록 합은 64 byte이고 요청 합은 32 byte다. 비율 1/2은 이 시점의 요청 payload/점유 블록 비율이다. free 공간이나 전체 heap 크기가 없으므로 실제 allocator의 peak utilization은 이 숫자만으로 정하지 않는다.

① 준비 60 ms와 본문 0.2 ms의 100회 배치 및 매 호출 준비 장부를 비교하라. ② A(시간 1,100)와 B(0.5,90)의 평균 비와 전체 비를 계산하라. ③ load/miss/명령/cycle 장부 A(100,10,200,1000), B(50,8,100,800)의 rate·CPI와 전체 cycle 변화를 비교하라. ④ 위 P/Q 캐시 흐름에서 Q의 추가 주소 작업 30을 포함한 최종 비용을 계산하고 채택 근거를 제한하라.

힌트 1

준비를 언제 반복하는지와 평균하는 비의 가중치를 먼저 적는다. 전체 speedup에는 B 시간 비중을 쓴다.

힌트 2

miss와 명령 수의 분모를 분리한다. 캐시 비용은 접근 수+9×miss이며 Q의 추가 30을 한 번 더한다.

풀이와 답 확인

  1. ① 한 번 준비한 배치는 80 ms이고 매 호출 준비는 6020 ms다. 회당 값은 0.8과 60.2 ms이며 본문만의 가정은 둘 다 0.2 ms다.

  2. ② 비의 단순 평균은 14/9다. 전체 합계 비는 202/181이며 B 시간 가중치 1/181과 180/181을 쓰면 같은 값이 나온다.

  3. ③ load miss rate는 10%에서 16%, CPI는 5에서 8이다. 반면 cycle은 1000에서 800으로 20% 감소하며 cycle 기준 비는 5/4다. 실제 wall time은 추가 조건 없이 확정하지 않는다.

  4. ④ P는 miss 네 번이라 40, Q는 miss 두 번과 hit 두 번으로 22다. 주소 작업을 더한 Q 전체는 52로 P보다 크다. 캐시 지표 하나만 근거로 Q를 채택하지 않는다.

측정 경계와 입력 가중치·사건 분모를 먼저 적고 전체 비용을 비교한다. 모든 수치는 자체 가상 장부의 손산술이며 실제 timeit/perf/CPU/역어셈블/캐시/할당기 성능·학생 실험은 미수행이다.

해결한 뒤 점검할 것

  • 배치 준비 경계와 본문 한 번의 시간을 섞지 않는다.

  • 입력별 비 평균과 합계 시간 비를 각각 계산하고 가중치의 근거를 설명한다.

  • rate/CPI 방향과 전체 cycle 방향을 구별하며 실제 시간으로 확대할 조건을 적는다.

  • 캐시 표 밖의 주소 비용까지 포함하여 P40/Q52를 검산한다.

보강 자료의 출처와 확인 범위
  • Python — timeit

    현재 Python 3.15 문서 실제 39–99/124–171행의 setup 제외·GC·반복 벡터·최소값 범위·wall/process·기본 오버헤드를 읽었다. 문서 예시 시간을 복제하지 않고 새 배치 경계와 입력 가중 장부를 손산술로 구성했다.

  • GNU Binutils — objdump

    실제 135–153/212–220/392–400행의 d/D·소스 혼합·대상 아키텍처·정적 정보 범위를 읽었다. 명령 목록과 동적 횟수·실제 시간·의미 보존을 구별하며 실제 도구를 실행하지 않았다.

  • CMU — Program Optimization

    실제 물리 1–8쪽의 측정·상수 비용·행동 보존·별칭·컴파일러 제약·코드 이동/강도 축소를 읽었다. 과거 GCC 범위·특정 CPU 비용을 현재 보편 보증으로 옮기지 않고 새 자체 비용 계약을 구성했다.

전체 base 세 소단원을 읽고 새 장부를 손검산했다. 100회 배치는 80 ms, 200회 배치는 100 ms, 매 호출 준비한 100회는 6020 ms다. 회당 배치 값이 0.3 ms 이하인 최소 반복 수 600, 비의 평균 14/9와 합계 비 202/181, 포함 시간 30/20에서 부모 자체 시간 10 ms를 확인했다. A/B의 load miss rate는 10%/16%, CPI는 5/8, IPC는 0.2/0.125이며 전체 cycle은 20% 감소한다. 미관찰 구간의 비례 확대 추정 80과 상한 조건의 실제 가능 범위 40–100을 구별했다. P/Q 및 변형 캐시 비용 40/22/31, 추가 30을 포함한 Q의 전체 비용 52와 개선 임계값 18을 계산했다. 할당 전체 크기 48/40, 요청 비율 5/24와 1/4, 올림 규칙 차이 0 또는 8을 손유도했다. 새 실행 계산은 없다.
