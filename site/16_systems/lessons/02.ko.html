소단원 2.1

2의 보수와 부호 확장

음수에 왼쪽 1을 더 붙였는데 어떻게 같은 값일까?

준비 개념과 학습 목표

준비 개념

  • w비트 패턴 b_(w−1)…b_0에서 unsigned 값은 U=Σb_i2^i다. 1110₂=14다.

  • 2의 보수 signed 값은 S=U−b_(w−1)2^w다. 4비트 1110의 값은 14−16=−2다.

  • 확장은 비트 수를 늘리는 일이다. 값 보존은 확장 전후 해석한 정수가 같은지를 말한다.

학습 목표

  • 부호 확장과 0 확장의 값을 계산한다.

  • 일반 폭에서 부호 확장의 값 보존을 증명한다.

  • 언어의 값 변환과 비트열의 재해석을 구분한다.

음수의 자리 가중치

w≥2일 때 2의 보수 해석은 최상위 자리만 −2^(w−1)의 가중치를 사용한다. 범위는 −2^(w−1)…2^(w−1)−1이다. 8비트 11111110은 −128+64+32+16+8+4+2=−2다. 모든 1인 패턴은 −1이지 가장 작은 음수가 아니다.

0은 모든 비트 0으로 하나만 표현된다. a의 반전 후 1 더하기를 낮은 w비트에 저장하면 −a의 모듈러 패턴을 만들지만, 최소값의 양수 상대는 같은 signed 폭에 들어가지 않는다. 따라서 패턴 조작과 표현 가능한 수학적 결과를 함께 확인한다.

부호 확장이 보존하는 것

W>w로 넓힐 때 unsigned는 앞에 0, 2의 보수 signed는 기존 부호 비트를 반복한다. 음수의 unsigned 값 U에 새로 추가된 1의 가중치 합 2^W−2^w를 더하면, 새 signed 값은 U+2^W−2^w−2^W=U−2^w다. 원래 signed 값과 같다.

4비트 1110을 8비트로 부호 확장하면 11111110=−2다. 0 확장 00001110=14는 unsigned 14를 보존하지만 signed −2를 보존하지 않는다. 새 폭은 기존 값 범위를 포함해야 하며 축소는 따로 다룬다.

값 변환과 저장 표현

C11에서 목적 정수 타입에 값이 표현 가능하면 변환은 값을 유지한다. 이 규칙 자체가 모든 구현의 signed 표현을 2의 보수로 지정하지는 않는다. 본문의 바이트 그림은 CHAR_BIT=8, signed char 8비트, int 32비트, 패딩 없는 2의 보수인 가정한 구현의 그림이다.

이 구현에서 signed char −2를 int로 바꾸면 값 −2이며 그림은 부호 확장과 같다. unsigned char 254를 int로 바꾸면 모든 값이 int에 들어가므로 +254다. 둘 다 원래 저장 그림이 11111110이어도 타입이 다르다. 캐스트는 값 변환이다. 임의 포인터로 다른 타입의 저장 공간을 읽는 동작까지 이 설명이 허용하는 것은 아니다.

중간 과정을 따라가는 예제

가정한 8비트 char/32비트 int 구현에서 signed char −2와 unsigned char 254를 int로 바꾸는 그림을 비교하라.

  1. 8비트 패턴은 두 경우 모두 11111110이다.

  2. signed 해석은 254−256=−2, unsigned 해석은 254다.

  3. −2는 int 범위 안이므로 signed 값 변환이 −2를 보존한다. 그림은 앞에 1을 24개 채운 0xFFFFFFFE다.

  4. 254도 int 범위 안이므로 unsigned char의 정수 승격은 +254다. 그림은 앞에 0을 24개 채운 0x000000FE다.

저장 패턴만 같다고 변환 결과 값이 같지는 않다. 출발 타입의 해석을 먼저 적용한다.

종이와 본문으로 직접 해보기

4비트 signed 1011을 8비트로 부호 확장하고, 0 확장한 결과도 계산하라. 원래 값을 되찾는 확장은 어느 것인가?

힌트 보기

원래 signed 값은 −8+2+1이다. 8비트 signed의 최상위 가중치는 −128이다.

풀이 보기

원래 −5다. 부호 확장 11111011은 −128+64+32+16+8+2+1=−5다. 0 확장 00001011은 11이므로 signed 값을 보존하지 않는다.

오해와 반례

음수는 모든 폭에서 왼쪽에 0을 채우면 된다.

4비트 1011=−5에 0을 채우면 +11이 된다. 2의 보수 signed 값 보존에는 부호 비트 반복이 필요하다. unsigned 값의 보존에는 0 확장이 맞다.

자기점검

8비트 10000000의 2의 보수 값은?

답과 이유 보기

−128

최상위 음수 가중치만 남았다. +128은 8비트 signed에 없다.

4비트 0110을 8비트로 부호 확장하면?

답과 이유 보기

00000110, 값 6

양수의 부호 비트는 0이라 부호 확장과 0 확장이 일치한다.

C11이 모든 signed 정수의 2의 보수 표현을 보장하는가?

답과 이유 보기

아니다. 이 본문은 2의 보수 구현을 별도로 가정한다.

값 변환의 표현 가능성 규칙과 저장 표현의 구현 선택은 별개의 조건이다.

한 단계 더

범위 안 값의 축소도 증명할 수 있다. 음수 x가 k비트 범위 안이면 넓은 패턴의 낮은 k비트 unsigned 값은 2^k+x이고 이를 k비트 signed로 해석하면 x다. 범위를 벗어난 값에서는 이 결론이 성립하지 않는다. 예컨대 +130의 낮은 8비트 10000010을 signed로 해석하면 −126이지만, C11의 표현 불가능한 signed 변환이 반드시 그 값을 주는 것은 아니다.

소단원 2.2

캐스팅과 오버플로

결과를 작은 상자에 넣는 것과 작은 상자 안에서 계산하는 것은 같을까?

준비 개념과 학습 목표

준비 개념

  • 캐스트 (T)x는 x의 값을 타입 T로 명시적으로 변환한다. 목적 타입의 범위가 중요하다.

  • 정수 승격은 작은 정수 타입을 계산 전에 int 또는 unsigned int로 바꾸는 규칙이다.

  • 정의되지 않은 동작은 명세가 그 실행 결과를 보장하지 않는 경우다. 구현 정의 결과는 구현이 선택하고 문서화해야 하는 경우이며 서로 다르다.

학습 목표

  • C11 정수 변환·승격·혼합 타입을 추적한다.

  • signed 산술 오류와 unsigned 나머지를 구별한다.

  • 계산 전 범위 검사를 설계한다.

목적 타입의 범위

이 절은 C11을 기준으로 CHAR_BIT=8, unsigned char 범위 0…255, 패딩 없는 32비트 int/unsigned int, signed는 2의 보수인 가상 구현을 가정한다. int 범위는 −2147483648…2147483647, unsigned int 범위는 0…4294967295다. 실제 구현이나 다른 언어 판본을 시험한 결과가 아니다.

정수에서 정수로 변환할 때 목적 범위 안이면 값 그대로다. 목적이 unsigned이고 범위 밖이면 최대값+1을 법으로 조정한다. (unsigned char)300은 44, (unsigned char)(−1)은 255다. 목적이 signed이고 표현 불가능하면 C11에서는 구현 정의 결과 또는 구현 정의 신호다. 낮은 비트를 잘라 signed로 읽는 종이 모형을 언어의 무조건적 보장으로 바꾸면 안 된다.

계산 전에 바뀌는 타입

unsigned char a=250,b=10이라도 a+b는 이 가정에서 int로 승격되어 260이다. 이를 unsigned char에 저장할 때 260 mod 256=4가 된다. 작은 타입의 원소들이 매 순간 8비트로 계산된다고 볼 수 없다. 반면 unsigned int의 UINT_MAX+1u는 해당 타입에서 0이 된다.

혼합 타입의 일반 산술 변환도 비교에 영향을 준다. 같은 rank의 int와 unsigned int에서 int가 unsigned의 모든 값을 담을 수 없으므로 unsigned로 맞춘다. 따라서 −1<1u에서 −1은 4294967295u로 바뀌고 비교는 거짓이다. 숫자 모양만으로 signed 비교라고 판단하면 오류가 난다.

사후 캐스트 대신 사전 조건

signed int 최대값+1의 산술은 C11에서 정의되지 않은 동작이다. (unsigned int)(a+b)처럼 결과 뒤의 캐스트는 a+b의 오류를 복구하지 않는다. unsigned 덧셈의 나머지가 유효한 언어 결과라도 배열 길이나 금액을 보존하는 요구에는 잘못된 값일 수 있다.

a,b가 음이 아닌 int라는 전제에서 정확한 합을 int에 담으려면 b≤INT_MAX−a를 먼저 검사한다. 전제 덕분에 INT_MAX−a 자체가 0…INT_MAX 안이고 안전하다. 실패하면 덧셈을 수행하지 않고 거절한다. 음수 입력을 허용하려면 별도의 상·하한 검사가 필요하다.

중간 과정을 따라가는 예제

가정한 구현에서 unsigned char a=250,b=10; unsigned char c=(unsigned char)(a+b);의 타입과 값을 추적하고 −1<1u도 판정하라.

  1. 250과 10은 모두 int에 들어가므로 a,b는 덧셈 전에 int로 승격된다.

  2. 중간 a+b는 int 값 260이다. int 범위 안이므로 signed 오버플로가 없다.

  3. unsigned char로 캐스트하면 260−256=4다. 저장된 c는 4다.

  4. −1<1u는 unsigned int 비교가 되어 4294967295<1이므로 거짓이다.

중간 값 260과 저장 값 4는 다른 단계의 결과다. 비교도 실제 변환된 타입에서 판정한다.

종이와 본문으로 직접 해보기

a,b≥0인 int에 대해 a=INT_MAX−2,b=3과 a=INT_MAX−2,b=2의 사전 검사를 종이로 수행하라. 거절 경로에서는 a+b를 계산하지 마라.

힌트 보기

두 경우 INT_MAX−a=2다. b가 이 한계를 넘는지 먼저 본다.

풀이 보기

b=3이면 3≤2가 거짓이라 거절하고 위험한 합을 수행하지 않는다. b=2이면 허용하며 정확한 합 INT_MAX다. 조건 a,b≥0 없이는 이 단일 검사만으로 모든 signed 합을 보호하지 못한다.

오해와 반례

unsigned를 쓰면 모든 범위 오류가 해결된다.

unsigned UINT_MAX+1u는 정의된 0이지만, 길이가 늘어나야 하는 요구에는 잘못된 값이다. 명세상 정의된 연산과 응용 의미상 올바른 결과는 다르다.

자기점검

(unsigned char)(−2)의 값은?

답과 이유 보기

254

−2에 법 256을 더해 범위 0…255에 맞춘다. 정수→unsigned 변환의 규칙이다.

이 구현의 a=250,b=10인 unsigned char에 대해 a+b 자체는 4인가?

답과 이유 보기

아니다. int 값 260이다.

정수 승격 뒤 계산하며 8비트로 변환하는 단계에서 4가 된다.

표현 불가능한 signed 변환과 signed 덧셈 오버플로가 C11에서 같은 규칙인가?

답과 이유 보기

아니다. 변환은 구현 정의 결과/신호, 덧셈은 정의되지 않은 동작이다.

6.3.1.3의 변환 규칙과 6.5의 표현 불가능한 산술 결과 규칙을 구분한다.

한 단계 더

음수도 허용하는 int 덧셈은 b>0이면 a≤INT_MAX−b, b<0이면 a≥INT_MIN−b를 검사한 뒤 수행할 수 있다. 두 경계식은 각각의 b 부호 조건 때문에 int 범위 안이다. b=0은 항상 안전하다. 이 논증은 a,b가 유효한 int이며 검사와 덧셈 사이에 값이 바뀌지 않는 순차 모형을 전제로 한다. 실수→정수 변환에는 이 unsigned 모듈러 규칙을 그대로 적용하지 않는다.

소단원 2.3

비트 마스크와 시프트

숫자 180 속의 네 개 깃발만 꺼내 읽으려면?

준비 개념과 학습 목표

준비 개념

  • 16진 한 자리는 4비트다. 0xB4=10110100₂=180이다.

  • 비트 마스크는 관심 자리만 1로 둔 패턴이다. AND는 선택, OR는 설정, XOR는 뒤집기에 쓸 수 있다.

  • 시프트는 자리를 이동한다. C 표현식에서는 이동 전 정수 승격과 결과 타입을 먼저 확인한다.

학습 목표

  • 마스크로 검사·설정·해제를 추적한다.

  • unsigned 시프트의 폭과 이동량 조건을 설명한다.

  • 가상 8비트 이동과 C11 승격 후 이동의 차이를 계산한다.

관심 자리만 선택하기

이 절은 unsigned int가 패딩 없는 32비트이고 CHAR_BIT=8,int도 32비트인 C11 구현을 가정한다. unsigned int x=0xB4u에서 x & 0x0Fu는 낮은 4비트 0100=4다. x | 0x02u는 비트 1을 설정하여 0xB6=182다. x & ~0x10u는 비트 4를 지워 0xA4=164다.

비트 번호는 오른쪽부터 0이다. 비트 k가 설정되었는지는 (x & (1u<<k))!=0으로 검사한다. 결과는 1 자체가 아니라 0 또는 2^k이므로 ==1로 비교하면 k>0에서 놓친다. ~0x10u는 32비트 전체를 반전하지만 x와 AND하면 지정 자리만 지우는 효과가 난다.

시프트의 정확한 계약

C11에서 <<와 >>는 각 피연산자를 정수 승격한 후 수행하며 결과 타입은 승격된 왼쪽 타입이다. 이동량은 0 이상이고 그 왼쪽 타입의 폭보다 작아야 한다. 이 32비트 모형에서 0…31은 허용되지만 −1이나 32는 정의되지 않은 동작이다.

unsigned x<<k는 x×2^k의 2^32 나머지이고 새 낮은 자리는 0이다. x>>k는 floor(x/2^k)다. signed 왼쪽 이동은 C11에서 입력이 음이 아니고 곱이 결과 타입에 표현될 때만 정의된다. 음수 signed 오른쪽 이동은 구현 정의다. 따라서 1u<<31은 정의된 2147483648u지만 32비트 int의 1<<31은 정의되지 않은 동작이다.

폭을 착각하는 반례

unsigned char v=0xB4라 해도 이 구현에서는 v가 int로 승격된다. v<<1은 int 값 360=0x168이며 8비트 0x68이 아니다. unsigned char로 다시 변환하면 360 mod 256=104=0x68이다. 이동량 한계도 저장 타입 8이 아니라 승격된 int 폭 32를 기준으로 한다.

부호 있는 음수의 >>를 나눗셈 대용으로 쓰려면 구현 정의와 반올림 방향을 확인해야 한다. C11 정수 나눗셈은 0 쪽으로 절단하지만, 산술 오른쪽 이동을 선택한 구현의 −3>>1은 −2일 수 있어 −3/2의 −1과 다르다. 마스크는 표현을 조작하는 도구이며 단위·범위·권한 같은 응용 조건을 대신 검증하지 않는다.

중간 과정을 따라가는 예제

unsigned int x=0xB4u인 32비트 모형에서 낮은 니블 추출, 비트 1 설정, 비트 4 해제, 네 자리 오른쪽 이동을 각각 원래 x에 적용하라.

  1. x=10110100₂이고 0x0F=00001111₂이므로 x&0x0F=00000100=4다.

  2. 비트 1 마스크 00000010과 OR하면 10110110=0xB6=182다.

  3. 비트 4를 제외한 마스크와 AND하면 10100100=0xA4=164다.

  4. x>>4는 00001011=11이다. 각 식은 원래 x를 읽으며 앞 계산 결과를 다음 입력으로 쓰지 않는다.

결과는 각각 4,182,164,11이다. 높은 24비트는 x에서 0이며 전체 타입 폭은 32다.

종이와 본문으로 직접 해보기

원래 x=0xB4u의 비트 2를 검사한 뒤 XOR로 한 번, 다시 한 번 뒤집어라. unsigned char v=0xB4의 v<<1과 변환 후 값도 비교하라.

힌트 보기

비트 2 마스크는 0x04u다. XOR를 두 번 같은 마스크로 수행하면 원래 패턴으로 돌아온다.

풀이 보기

x&0x04u=4이므로 설정되어 있다. 첫 뒤집기는 0xB0=176, 두 번째는 0xB4=180이다. v<<1은 승격 후 int 360이며 (unsigned char)(v<<1)은 104다. 그 변환을 생략하면 낮은 8비트만 남는다고 할 수 없다.

오해와 반례

시프트는 언제나 곱셈·나눗셈과 같고 이동량에는 제한이 없다.

32비트 unsigned 1u<<32는 C11에서 정의되지 않은 동작이다. 음수 signed 오른쪽 이동도 이식 가능한 나눗셈 대용이 아니다. unsigned의 범위 조건을 만족하는 오른쪽 이동은 양의 2의 거듭제곱으로 나눈 몫이며 왼쪽 이동은 모듈러 곱이다.

자기점검

x=0xB4u에서 (x&0x10u)==1로 비트 4를 검사하면?

답과 이유 보기

거짓이 되어 검사를 잘못한다.

실제 선택 값은 0x10=16이다. !=0을 써야 설정 여부를 얻는다.

32비트 unsigned int에서 1u<<31은?

답과 이유 보기

2147483648u, 정의된 연산

이동량31<32이고 unsigned 모듈러 규칙을 따른다.

이 구현에서 unsigned char v에 v>>8을 쓸 때 이동량8은 곧바로 불법인가?

답과 이유 보기

아니다. int로 승격되어 폭32를 기준으로 한다.

v의 값은 0…255라 결과는 0이다. 저장 타입 폭8만 보고 이동 한계를 판정하면 안 된다.

한 단계 더

폭32의 unsigned 필드에서 정수 폭 m과 정수 시작 위치 k가 1≤m≤31,0≤k, k+m≤32라면 마스크 ((1u<<m)−1u)<<k로 필드를 선택하고 (x>>k)&((1u<<m)−1u)로 값을 추출할 수 있다. m=32는 1u<<32가 불법이므로 전체 마스크를 따로 처리해야 한다. 전제 검사 없이 범용 공식을 그대로 사용하면 경계에서 실패한다. 통신 패킷에는 이 비트 계산 외에 바이트 순서와 입력 길이 검증도 필요하다.
