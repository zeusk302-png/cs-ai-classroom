ELF 섹션과 심볼

컴파일한 작은 조각에는 기계어 말고 어떤 연결 정보가 들어갈까?

학습 목표

  • 심볼 정의와 미정의 참조를 읽는다.

같은 파일의 두 관점

ELF는 재배치 가능한 파일, 실행 파일, 공유 오브젝트를 표현한다. 재배치 가능한 .o는 다른 조각과 연결할 코드·데이터·연결 정보를 담으며 곧바로 독립 실행 파일이라는 뜻은 아니다.

링킹 관점은 .text 같은 섹션, 실행 관점은 메모리에 올릴 segment와 program header를 본다. 섹션 하나와 segment 하나가 항상 일대일이라는 가정은 피한다.

저장 내용과 공간의 약속

.text는 실행 명령, .data는 초기화된 데이터의 대표 섹션이다. .bss는 시작할 때 영값으로 마련할 미초기화 데이터 공간이며 SHT_NOBITS라 그 크기만큼의 값 바이트를 파일에 저장하지 않는다.

실제 파일에는 헤더·정렬·심볼·재배치 정보도 있어 세 섹션 크기 합만으로 파일 길이를 계산할 수 없다. 영값 공간이 파일 바이트를 안 차지해도 실행 메모리는 필요하다.

이름과 정의 위치를 연결한다

심볼에는 이름, 바인딩, 종류, 관련 섹션과 값 등이 있다. 재배치 파일의 섹션 안 심볼 값은 보통 해당 섹션 기준 위치이며 최종 실행 주소와 바로 같지 않다.

local 심볼은 정의한 파일 범위에서 쓰고 global은 다른 파일 참조를 해결할 수 있다. SHN_UNDEF는 이 파일이 정의하지 않은 참조다. 같은 이름의 local끼리는 서로 충돌한다고 볼 수 없다.

중간 과정을 따라가는 예제

.o의 .text=24 바이트, .data=8 바이트, .bss=16 바이트다. helper는 .text offset8 의 global 함수, count는 .data offset 0, puts는 SHN_UNDEF다. 각 정보를 해석하자.

  1. 세 공간의 합은 24+8+16=48 바이트다. 실제 최종 로딩 공간은 정렬·다른 내용 때문에 이 합과 다를 수 있다.
  2. 이 세 섹션의 값 데이터로 파일에 저장할 부분은 24+8=32 바이트다. .bss는 크기 16 을 기록하되 16 개의 영 바이트를 섹션 내용으로 저장하지 않는다.
  3. helper offset8 은 최종 주소 8 이라는 뜻이 아니다. puts는 다른 오브젝트/라이브러리의 정의가 필요하며 이 파일만으로 연결 완료가 아니다.

내용 바이트 32 와 공간 크기 합 48 을 구별한다. 실제 파일 길이·프로세스 전체 메모리 크기는 별도다.

오해와 반례

.bss가 파일 내용을 차지하지 않으니 실행 때도 공간이 필요 없다.

재배치와 심볼 해석

아직 주소를 모르는 함수 호출 자리는 언제 채워질까?

준비 개념과 학습 목표

준비 개념

  • 심볼 정의/참조
  • 주소 덧셈과 차이

학습 목표

  • 이름 해석과 주소 보정을 구분한다.
  • 재배치 식의 대상과 범위를 검산한다.

먼저 참조가 어느 정의인지 정한다

심볼 해석은 참조 이름과 바인딩·가시성 규칙에 맞는 정의를 고르는 작업이다. 외부 함수 이름을 알았어도 어디에 배치될지 아직 모를 수 있다.

이 소단원의 단순 강한 global 모델은 중복 정의를 오류로 보고 정의 없는 참조도 해결해야 한다. weak/common·공유객체 interposition의 세부는 별도 규칙이므로 모든 이름을 무조건 같은 규칙으로 다루지 않는다.

기록된 위치에 규약의 식을 적용한다

재배치 정보는 바꿀 자리, 심볼, 종류와 addend를 연결한다. RELA는 addend를 별도 기록하고 REL은 수정 자리에서 암묵적으로 얻는 형식이다.

종류별 식과 비트 폭은 대상 ABI에 따른다. 아래 S는 해석된 심볼 주소, A는 addend, P는 수정 필드 주소인 가상 signed 16-bit PC-relative 식 S+A−P다. 실제 모든 ISA의 호출 인코딩으로 오해하지 않는다.

범위와 기준점까지 검사한다

정확한 수학적 차이를 구해도 필드의 signed 범위를 벗어나면 그대로 저장할 수 없다. 링크 단계 overflow 검사와 별도 long-call 변환 가능성은 도구 규약에 따른다.

어떤 ISA는 명령 다음 주소나 정렬된 PC를 기준으로 해석한다. 그 차이를 addend나 재배치 종류가 반영할 수 있으므로 P에 임의로 4 를 더하지 않는다.

중간 과정을 따라가는 예제

가상 재배치 S+A−P에서 함수 S=8192, 필드 P=4100, A=−4 다. signed 16-bit 범위는 −32768..32767 이다.

  1. 8192−4−4100=4088 이다. 이 종류는 P가 필드 주소라고 이미 정했다.
  2. 4088 은 signed 16-bit 범위 안이라 이 가상 필드에 표현할 수 있다.
  3. 파일 전체를 같은 256 만큼 이동해 S=8448,P=4356 이면 8448−4−4356=4088 로 상대 차이는 같다.

재배치 결과 4088 이며 공통 이동에는 상대값이 유지된다. 각 값은 바이트 주소인 자체 모형이다.

오해와 반례

심볼 이름만 찾으면 재배치 종류와 addend는 무시해도 된다.

같은 S도 절대 주소 저장과 상대 차이 저장은 다르다. A와 P 및 폭의 규약을 적용해야 올바른 필드 값이 된다.

소단원 8.3

정적·동적 라이브러리

같은 함수 코드를 프로그램마다 넣을까, 실행할 때 공유 조각을 찾을까?

준비 개념과 학습 목표

준비 개념

  • 오브젝트 연결
  • 미정의 심볼 집합

학습 목표

  • archive 탐색 순서를 추적한다.
  • 정적 코드 포함과 실행 시 공유객체 의존을 구별한다.

정적 archive는 필요한 멤버를 고른다

정적 라이브러리 .a는 여러 오브젝트 멤버를 모은 archive다. 보통 필요한 미정의 심볼을 해결하는 멤버를 꺼내 실행 파일 연결에 사용한다. archive 전체를 항상 모두 복사한다는 뜻은 아니다.

GNU ld의 일반 archive 탐색은 명령줄의 위치에서 현재 필요한 참조를 해결한다. 앞에서 한 번 지나간 다른 archive를 뒤 참조 때문에 자동 반복 탐색한다고 가정하면 안 된다.

공유객체는 실행 환경도 계약이다

동적 연결에서는 실행 파일이 필요한 공유객체와 심볼 정보를 남기고 loader가 실행 시 그 파일들을 찾아 로드·해석한다. 링크 성공만으로 다른 컴퓨터의 파일·ABI가 맞는다고 보장하지 않는다.

Linux의 검색은 dependency 경로, RPATH/RUNPATH, 환경·cache·기본 경로 등의 조건을 따른다. secure execution에서는 일부 환경변수를 무시한다. 이름 하나로 어느 파일이든 안전하다고 볼 수 없다.

순환 참조와 갱신을 관리한다

GNU ld archive group은 새로운 미정의 참조가 사라질 때까지 그룹을 반복 탐색할 수 있지만 비용이 있다. --whole-archive처럼 다른 포함 정책은 본문의 기본 모델과 구별한다.

동적 라이브러리를 바꾸면 여러 프로그램이 변경 영향을 받을 수 있다. ABI·버전·배포 일관성을 검증해야 하며 정적 연결도 취약점 수정 후 실행 파일 재빌드가 필요할 수 있다.

중간 과정을 따라가는 예제

main.o가 f를 요구한다. libA.a의 a.o는 f를 정의하고 g를 요구한다. libB.a의 b.o는 g를 정의한다. 다른 의존은 없고 GNU ld 기본 순차 archive 탐색을 가정한다.

  1. main.o 처리 후 미정의 집합은 {f}다.
  2. main.o libA.a libB.a 순서는 a.o를 꺼내 {g}, b.o를 꺼내 빈 집합이 된다.
  3. main.o libB.a libA.a 순서는 B 위치에서 g가 아직 필요하지 않아 멤버를 안 꺼낸다. 이후 A가 g를 요구하므로 기본 한 번 탐색에서는 g가 남는다.

A 뒤 B는 해결되고 B 뒤 A는 이 가정에서 g가 남는다. 순서는 단순 장식이 아니다.

힌트 보기

풀이 보기

반복 탐색으로 a.o 뒤 생긴 g를 b.o가 해결한다. 미정의 집합이 비며 그룹 반복 비용은 별도다.

오해와 반례

동적 링크가 성공하면 공유 라이브러리를 배포할 필요가 없다.

대상 환경에서 필요한 공유객체와 호환 ABI를 찾을 수 있어야 한다. 실행 파일의 존재만으로 의존 파일을 대신하지 못한다.
