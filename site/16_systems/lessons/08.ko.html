ELF 섹션과 심볼

  • 함수·전역 변수

학습 목표

파일에서 152번째 바이트는 메모리에서도 주소 152인가?

새 배치 모형의 .text 내용은 파일 오프셋 128에서 18바이트, .data 내용은 8바이트 정렬한 다음 위치에서 6바이트다. .text의 끝 다음 위치는 146이지만 .data는 152에서 시작한다. 이 두 내용 사이에는 6바이트의 빈 배치 공간이 있다. 섹션 내용의 합 24바이트를 파일 전체 길이라고 부르면 헤더와 이 간격, 다른 표를 놓친다.

링커가 배치한 가상 주소는 별도 장부다. .text의 가상 시작을 4096, .data의 가상 시작을 8192로 지정했다면 파일 오프셋 152의 데이터 첫 바이트는 가상 주소 8192에 해당한다. 이 숫자는 두 장부를 구별하는 배치 모형이며 유효한 실행 ELF 전체를 생성했다는 뜻은 아니다. 실제 적재 세그먼트의 정렬과 권한 등 추가 조건은 별도로 검사해야 한다.

같은 이름 helper라도 서로 다른 입력 파일의 local 심볼은 각 파일 문맥에서 선택한다. A의 .text 시작은 4096, B의 시작은 4128이고 각각 helper의 섹션 내 값이 4이면 주소는 4100과 4132다. 이름 문자열만 합쳐 하나로 만들지 않는다. 섹션은 링크 장부, 세그먼트는 실행 적재 장부라는 역할 차이도 유지한다.

    파일 위치와 섹션 내 값, 최종 가상 주소를 분리한다.

  • 정의 선택 뒤 재배치

    어느 파일의 정의를 선택했는지 확정한 뒤 주소 식을 계산한다.

같은 파일의 두 관점

ELF는 재배치 가능한 파일, 실행 파일, 공유 오브젝트를 표현한다. 재배치 가능한 .o는 다른 조각과 연결할 코드·데이터·연결 정보를 담으며 곧바로 독립 실행 파일이라는 뜻은 아니다.

링킹 관점은 .text 같은 섹션, 실행 관점은 메모리에 올릴 segment와 program header를 본다. 섹션 하나와 segment 하나가 항상 일대일이라는 가정은 피한다.

저장 내용과 공간의 약속

.text는 실행 명령, .data는 초기화된 데이터의 대표 섹션이다. .bss는 시작할 때 영값으로 마련할 미초기화 데이터 공간이며 SHT_NOBITS라 그 크기만큼의 값 바이트를 파일에 저장하지 않는다.

실제 파일에는 헤더·정렬·심볼·재배치 정보도 있어 세 섹션 크기 합만으로 파일 길이를 계산할 수 없다. 영값 공간이 파일 바이트를 안 차지해도 실행 메모리는 필요하다.

이름과 정의 위치를 연결한다

심볼에는 이름, 바인딩, 종류, 관련 섹션과 값 등이 있다. 재배치 파일의 섹션 안 심볼 값은 보통 해당 섹션 기준 위치이며 최종 실행 주소와 바로 같지 않다.

local 심볼은 정의한 파일 범위에서 쓰고 global은 다른 파일 참조를 해결할 수 있다. SHN_UNDEF는 이 파일이 정의하지 않은 참조다. 같은 이름의 local끼리는 서로 충돌한다고 볼 수 없다.

메모리 크기 20바이트

파일 내용 시작과 가상 시작은 서로 다른 열이다. .bss의 20바이트는 메모리 요구이며 내용 바이트 0과 충돌하지 않는다. 실제 섹션 헤더의 NOBITS 오프셋은 개념적인 위치를 가질 수 있으므로 여기서는 내용 없음으로 표시했다.

중간 과정을 따라가는 예제

.o의 .text=24 바이트, .data=8 바이트, .bss=16 바이트다. helper는 .text offset8 의 global 함수, count는 .data offset 0, puts는 SHN_UNDEF다. 각 정보를 해석하자.

  1. 세 공간의 합은 24+8+16=48 바이트다. 실제 최종 로딩 공간은 정렬·다른 내용 때문에 이 합과 다를 수 있다.

  2. 이 세 섹션의 값 데이터로 파일에 저장할 부분은 24+8=32 바이트다. .bss는 크기 16 을 기록하되 16 개의 영 바이트를 섹션 내용으로 저장하지 않는다.

  3. helper offset8 은 최종 주소 8 이라는 뜻이 아니다. puts는 다른 오브젝트/라이브러리의 정의가 필요하며 이 파일만으로 연결 완료가 아니다.

내용 바이트 32 와 공간 크기 합 48 을 구별한다. 실제 파일 길이·프로세스 전체 메모리 크기는 별도다.

조건을 바꾸어 비교하기

정렬된 내용 두 개

지정 .text/.data 배치에서 다음 위치와 내용 합을 구하라.

  1. 128+18=146이다. 8의 배수 중 146 이상 최소는 152다.

  2. 152+6=158이다. 내용 합은 18+6=24다.

데이터 시작 152, 두 내용의 마지막 다음 위치 158, 내용 합 24바이트다. 파일 전체 크기는 주어진 정보만으로 확정하지 않는다.

비교할 점

끝 위치와 내용 합, 파일 전체 길이를 세 장부로 나눈다.

같은 local 이름의 두 주소

A/B의 helper 오프셋이 모두 4일 때 정의별 주소를 구하라.

  1. A는 4096+4=4100이다.

  2. B는 4128+4=4132다.

각 문맥의 helper 주소는 4100과 4132다. 두 local 정의가 있다는 것만으로 strong global 중복 오류를 적용하지 않는다.

비교할 점

문자열 이름 같음과 같은 해석 범위의 정의 중복을 구별한다.

종이와 본문으로 직접 해보기

.text가 최종 가상주소 4096 부터 놓이면 helper 주소는? .bss를 32 바이트로 늘리면 공간 합은?

힌트 보기

섹션 기준 offset을 더하고 영값 공간의 증가를 센다.

풀이 보기

helper는 4096+8=4104 다. 세 공간 합은 24+8+32=64 바이트이며 .bss 내용 바이트 저장은 여전히 없다.

오해와 반례

.bss가 파일 내용을 차지하지 않으니 실행 때도 공간이 필요 없다.

16 바이트 영값 배열은 시작 메모리 이미지에 공간이 필요하다. 파일의 저장 생략과 메모리 할당은 다른 것이다.

연습 1 · 값과 상태 예측

.text 크기를 19바이트로 늘리고 나머지 파일 배치 규칙을 유지한다. .data 시작과 간격은?

힌트 1

끝 다음 위치는 147이다.

힌트 2

다음 8바이트 정렬 위치를 구한다.

풀이와 답 확인

  1. 152는 그대로 다음 정렬 위치다.

  2. 간격은 152−147=5바이트다.

데이터 시작은 152이며 간격은 5바이트다. 내용 합은 25바이트로 늘어난다.

흔한 오답에서 다시 생각하기

한 바이트 늘면 모든 뒤 위치도 한 바이트 증가한다.

정렬 올림은 계단 형태라 시작 위치가 그대로일 수 있다.

연습 2 · 오류 찾아 고치기

.bss 크기를 20에서 36바이트로 늘렸으니 파일 전체가 정확히 16바이트 늘었다고 했다. 무엇을 고쳐야 하는가?

힌트 1

NOBITS에는 그만큼의 초기 내용이 없다.

힌트 2

다른 헤더·배치 변경은 별도다.

풀이와 답 확인

  1. 메모리 요구가 16바이트 증가함을 기록한다.

  2. 해당 .bss 내용 증가분은 0바이트이며 파일 전체 변화는 추가 배치 정보 없이 확정하지 않는다.

메모리 증가 16바이트와 파일 내용 증가 0바이트를 구별한다. 실제 파일 측정은 아니다.

흔한 오답에서 다시 생각하기

메모리 크기와 파일 크기는 항상 같다.

0으로 초기화할 메모리 공간을 파일에 0바이트 배열로 모두 저장할 필요는 없다.

연습 3 · 직접 만들어 보기

하나의 별도 PT_LOAD 모형이 p_offset=0, p_vaddr=4096, p_align=4096, p_filesz=160, p_memsz=192라고 주어진다. 초기화 구간 두 개를 구성하라.

힌트 1

두 시작값은 정렬 기준으로 합동이다.

힌트 2

뒤의 32바이트는 파일 내용 뒤에 온다.

풀이와 답 확인

  1. 가상 [4096,4256)은 파일의 [0,160) 바이트를 받는다.

  2. 가상 [4256,4288)은 32바이트의 0 초기화 영역이다.

초기 파일 영역 160바이트와 뒤 0 영역 32바이트다. 앞의 섹션 배치와 독립인 모형이다.

흔한 오답에서 다시 생각하기

p_filesz=192로 읽어 파일도 192바이트 복사한다.

파일 바이트 수는 160이고 메모리 차이 32는 별도 초기화다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

A와 B의 local helper 값은 4로 같다. A의 .text만 16만큼 이동시키면 두 주소는 어떻게 되는가? 동일 이름만으로 하나의 global 정의처럼 결합할 수 있는가?

힌트 1

A의 시작은 4112가 된다.

힌트 2

B의 시작은 4128 그대로다.

풀이와 답 확인

  1. A의 주소는 4116으로 바뀐다.

  2. B의 주소는 4132로 유지된다.

4116과 4132다. local 해석 문맥을 지우지 않으며 실제 모든 ELF 심볼 정책으로 일반화하지 않는다.

흔한 오답에서 다시 생각하기

같은 이름이면 두 주소 중 작은 값만 남긴다.

local 이름에는 해당 입력 파일의 범위가 있고 임의 최솟값 선택 규칙은 없다.

내 말로 설명하기

.bss는 크기가 0인가?

설명 기준 확인

파일 내용은 차지하지 않지만 메모리 크기는 0이 아닐 수 있다.

섹션 위치만으로 실행 적재를 인증하는가?

설명 기준 확인

아니다. 세그먼트와 정렬·권한·대상 ABI 조건도 필요하다.

한 번 계산한 재배치 결과를 다음 addend로 써도 되는가?

새 종이 재배치 형식은 signed 8비트 필드에 S+A−P를 저장한다. S는 선택한 심볼의 가상 주소, P는 이 형식이 정한 필드 주소, A는 원래 addend다. S=1000,P=900,A=−4이면 96이므로 −128부터 127의 저장 범위 안이다. 실제 ISA의 next-instruction 주소나 명령어 인코딩 규칙이라고 주장하지 않는다.

S와 P를 둘 다 500만큼 이동하면 차이는 그대로 96이다. S만 32 증가하면 128이 되어 이 형식의 범위를 벗어난다. 하위 8비트만 저장하여 −128처럼 읽게 만드는 것은 이 모형이 요구한 범위 검사와 다르다. 주소를 모두 아는 것과 표현 가능한 재배치를 만들 수 있는 것은 다른 조건이다.

ELF RELA는 addend를 레코드에 명시하고 REL은 대상 위치에 담긴 addend를 사용한다. 아래 비교는 원래 −4를 보존해야 하는 자체 계산 감사다. 이미 저장된 결과 96을 다음 계산의 원래 A라고 오독하면 1000+96−900=196이 된다. 실제 링커가 이런 잘못된 재처리를 했다는 뜻도, 모든 재배치 형식이 재적용 가능하다는 뜻도 아니다.

    주소 선택·addend·저장 필드 폭을 먼저 확정한다.

  • 섹션 내 값과 최종 심볼 주소

먼저 참조가 어느 정의인지 정한다

심볼 해석은 참조 이름과 바인딩·가시성 규칙에 맞는 정의를 고르는 작업이다. 외부 함수 이름을 알았어도 어디에 배치될지 아직 모를 수 있다.

이 소단원의 단순 강한 global 모델은 중복 정의를 오류로 보고 정의 없는 참조도 해결해야 한다. weak/common·공유객체 interposition의 세부는 별도 규칙이므로 모든 이름을 무조건 같은 규칙으로 다루지 않는다.

기록된 위치에 규약의 식을 적용한다

재배치 정보는 바꿀 자리, 심볼, 종류와 addend를 연결한다. RELA는 addend를 별도 기록하고 REL은 수정 자리에서 암묵적으로 얻는 형식이다.

종류별 식과 비트 폭은 대상 ABI에 따른다. 아래 S는 해석된 심볼 주소, A는 addend, P는 수정 필드 주소인 가상 signed 16-bit PC-relative 식 S+A−P다. 실제 모든 ISA의 호출 인코딩으로 오해하지 않는다.

범위와 기준점까지 검사한다

정확한 수학적 차이를 구해도 필드의 signed 범위를 벗어나면 그대로 저장할 수 없다. 링크 단계 overflow 검사와 별도 long-call 변환 가능성은 도구 규약에 따른다.

어떤 ISA는 명령 다음 주소나 정렬된 PC를 기준으로 해석한다. 그 차이를 addend나 재배치 종류가 반영할 수 있으므로 P에 임의로 4 를 더하지 않는다.

학습 목표

필요한 이름이 아카이브 안에 있으면 순서와 무관하게 해결되는가?

새 아카이브 A에는 f를 정의하고 g를 요구하는 a_f와 h만 정의하는 a_h가 있다. B에는 g를 정의하고 h를 요구하는 b_g가 있다. main은 f를 요구한다. 일반적인 위치별 아카이브 검색 모형에서 main,A,B 순서라면 A의 a_f를 뽑아 g가 필요해지고 B의 b_g를 뽑아 h가 필요해진다. 이미 지나간 A를 자동으로 다시 검색하지 않는 모형에서는 h가 남는다.

main,A,B,A는 마지막 A에서 a_h를 뽑아 해결한다. A/B를 반복 검색 그룹으로 묶으면 새 요구가 생기는 동안 검색하여 같은 세 멤버를 찾을 수 있다. 반복은 정의를 창조하지 않으므로 어디에도 없는 이름은 해결하지 못한다. 실제 링크 실행·정적/동적 파일 생성·성능 측정은 수행하지 않는다.

이름이 필요할 때만 멤버를 뽑는 규칙과 모든 멤버를 강제로 넣는 규칙은 다르다. A에 unused를 정의하고 missing을 요구하는 a_u를 추가해도 main의 f 경로에서 a_u를 뽑지 않으면 missing 요구는 나타나지 않는다. 모든 멤버를 포함하면 missing이 새로 남는다. 그룹 반복과 전체 포함을 같은 수단으로 읽지 않는다.

먼저 확인할 개념
  • 아카이브 추출과 링크 순서

    미해결 이름 집합과 뽑힌 멤버를 단계별로 추적한다.

  • 정의가 없는 심볼의 판정

    모든 입력을 보아도 정의가 없으면 주소를 만들 수 없다.

정적 archive는 필요한 멤버를 고른다

정적 라이브러리 .a는 여러 오브젝트 멤버를 모은 archive다. 보통 필요한 미정의 심볼을 해결하는 멤버를 꺼내 실행 파일 연결에 사용한다. archive 전체를 항상 모두 복사한다는 뜻은 아니다.

GNU ld의 일반 archive 탐색은 명령줄의 위치에서 현재 필요한 참조를 해결한다. 앞에서 한 번 지나간 다른 archive를 뒤 참조 때문에 자동 반복 탐색한다고 가정하면 안 된다.

공유객체는 실행 환경도 계약이다

동적 연결에서는 실행 파일이 필요한 공유객체와 심볼 정보를 남기고 loader가 실행 시 그 파일들을 찾아 로드·해석한다. 링크 성공만으로 다른 컴퓨터의 파일·ABI가 맞는다고 보장하지 않는다.

Linux의 검색은 dependency 경로, RPATH/RUNPATH, 환경·cache·기본 경로 등의 조건을 따른다. secure execution에서는 일부 환경변수를 무시한다. 이름 하나로 어느 파일이든 안전하다고 볼 수 없다.

순환 참조와 갱신을 관리한다

GNU ld archive group은 새로운 미정의 참조가 사라질 때까지 그룹을 반복 탐색할 수 있지만 비용이 있다. --whole-archive처럼 다른 포함 정책은 본문의 기본 모델과 구별한다.

동적 라이브러리를 바꾸면 여러 프로그램이 변경 영향을 받을 수 있다. ABI·버전·배포 일관성을 검증해야 하며 정적 연결도 취약점 수정 후 실행 파일 재빌드가 필요할 수 있다.

빈 집합

a_h는 처음 A 검색 때 필요하지 않았고 B를 본 뒤 필요해진다. 각 멤버는 위의 정의/요구만 가지며 weak/common·공유 라이브러리·플러그인 같은 추가 정책은 없는 모형이다.

중간 과정을 따라가는 예제

main.o가 f를 요구한다. libA.a의 a.o는 f를 정의하고 g를 요구한다. libB.a의 b.o는 g를 정의한다. 다른 의존은 없고 GNU ld 기본 순차 archive 탐색을 가정한다.

  1. main.o 처리 후 미정의 집합은 {f}다.

  2. main.o libA.a libB.a 순서는 a.o를 꺼내 {g}, b.o를 꺼내 빈 집합이 된다.

  3. main.o libB.a libA.a 순서는 B 위치에서 g가 아직 필요하지 않아 멤버를 안 꺼낸다. 이후 A가 g를 요구하므로 기본 한 번 탐색에서는 g가 남는다.

A 뒤 B는 해결되고 B 뒤 A는 이 가정에서 g가 남는다. 순서는 단순 장식이 아니다.

조건을 바꾸어 비교하기

한 번씩 검색한 실패

main,A,B와 main,B,A를 비교하라.

  1. A,B는 f→g→h 순으로 요구가 생겨 h를 남긴다.

  2. B는 첫 방문에서 필요한 정의가 없어 아무 멤버도 뽑지 않는다. 뒤 A가 f를 정의하고 g를 남긴다.

앞 순서는 h 미해결, 뒤 순서는 g 미해결이다. 필요한 정의가 파일에 있다는 사실만으로 성공하지 않는다.

비교할 점

존재와 해당 검색 단계의 선택을 나눈다.

그룹과 전체 포함의 차이

a_u의 unused→missing 요구를 추가한 A/B에서 일반 그룹과 모든 멤버 포함을 비교하라.

  1. 그룹은 f/g/h의 요구 경로로 세 멤버만 뽑는다.

  2. 전체 포함은 a_u도 넣어 missing을 요구한다.

그룹의 지정 경로는 해결되지만 전체 포함에는 missing이 남는다. 추가 입력에 missing 정의가 없다는 조건이다.

비교할 점

더 많은 포함이 항상 성공을 늘리지는 않는다.

오해와 반례

동적 링크가 성공하면 공유 라이브러리를 배포할 필요가 없다.

대상 환경에서 필요한 공유객체와 호환 ABI를 찾을 수 있어야 한다. 실행 파일의 존재만으로 의존 파일을 대신하지 못한다.

스스로 풀어보기

먼저 답과 이유를 적고, 필요한 만큼 힌트를 한 단계씩 열어 보세요.

연습 1 · 값과 상태 예측

main의 요구를 f와 h 두 개로 바꾸고 A,B를 한 번씩 검색한다. 각 추출과 끝 집합은?

힌트 1

첫 A에서 a_f와 a_h가 필요하다.

힌트 2

a_f가 요구한 g는 B가 정의한다.

풀이와 답 확인

  1. A가 f/h를 정의하고 g를 남긴다.

  2. B가 g를 정의하며 요구한 h는 이미 해결되어 있다.

a_f,a_h,b_g가 선택되고 끝 집합은 비어 있다.

흔한 오답에서 다시 생각하기

B가 h를 요구하면 항상 A 재검색이 필요하다.

이미 선택된 h 정의가 있는지 먼저 확인한다.

연습 2 · 오류 찾아 고치기

그룹으로 여러 번 검색하면 어디에도 없는 missing도 해결된다고 했다. 종료/실패 장부를 고쳐라.

힌트 1

추가 추출로 새로운 정의가 생겨야 한다.

힌트 2

더 뽑을 멤버가 없으면 같은 집합이 반복된다.

풀이와 답 확인

  1. 모든 정의 집합에 missing이 없음을 확인한다.

  2. 더 이상 변경이 없는 반복을 끝내고 미해결로 기록한다.

반복은 기존 멤버 선택을 갱신할 뿐 없는 정의를 생성하지 않는다.

흔한 오답에서 다시 생각하기

계속 반복하면 결국 주소가 생긴다.

같은 유한 입력에 없는 정의는 검색 횟수로 만들어지지 않는다.

연습 3 · 직접 만들어 보기

원래 main 요구 f와 A/B로, 그룹 옵션 없이 세 멤버를 모두 필요한 순서에 선택하는 입력열을 구성하라.

힌트 1

처음 A 다음 B에서 h가 필요해진다.

힌트 2

A를 마지막에 한 번 더 둘 수 있다.

풀이와 답 확인

  1. main,A,B로 f/g를 고른다.

  2. 마지막 A에서 h를 고른다.

main,A,B,A가 된다. 아카이브 반복 지정의 실제 허용 여부는 사용하는 도구 조건도 확인한다.

흔한 오답에서 다시 생각하기

main,A,A,B면 항상 충분하다.

두 번째 A도 B보다 앞이면 아직 h가 필요하지 않아 같은 문제를 남긴다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

A에 a_u를 넣은 모형에서 기본 추출과 전체 포함의 선택 멤버 수, 끝 집합을 비교하라. 기본은 A/B 그룹으로 해결한다고 가정한다.

힌트 1

기본 요구 경로는 f→g→h다.

힌트 2

전체 포함에서는 unused도 정의하지만 missing이 요구된다.

풀이와 답 확인

  1. 기본은 세 멤버와 빈 미해결 집합이다.

  2. 전체 포함은 네 멤버와 {missing}이다.

선택 수 3/4, 미해결 빈 집합/{missing}이다. 멤버 수를 코드 바이트나 실제 링크 시간으로 바꾸지 않는다.

흔한 오답에서 다시 생각하기

멤버가 많으면 주소 해석은 항상 더 완전하다.

추가 멤버의 새로운 요구 때문에 미해결 집합이 늘 수 있다.

다른 문제에 적용하기

배치/주소/링크의 세 장부를 감사하라. .text는 파일 오프셋 128에서 19바이트, .data는 다음 8바이트 정렬 위치에서 6바이트이며 .bss 메모리 크기는 36바이트다. 파일 전체 크기는 주어지지 않았다. A의 local helper는 가상 .text 시작 4096과 오프셋 4, B는 시작 4128과 오프셋 4다. A helper를 S로 쓰는 종이 signed 8비트 재배치는 P=4000,A(addend)=−4다. A helper만 32만큼 이동했을 때까지 검사하라. 마지막으로 main의 요구 f를 A(a_f:f→g,a_h:h)와 B(b_g:g→h)로 해결할 입력열을 만들고, 모든 멤버 포함이면 unused→missing 멤버가 추가되는 차이를 설명하라.

힌트 1

파일 정렬과 가상 심볼 주소를 각각 계산한다. 36바이트 .bss를 파일 내용 합에 더하지 않는다.

힌트 2

재배치 결과의 상한은 127이다. 아카이브는 h가 필요해지는 시점 뒤에 A를 다시 검색한다.

풀이와 답 확인

  1. .text 끝 다음 위치는 147이고 .data 시작은 152, 정렬 간격은 5바이트다. 두 저장 내용의 합은 25바이트이며 .bss의 메모리 요구 36바이트는 파일 내용에 더하지 않는다. 파일 전체 길이는 확정할 수 없다.

  2. local helper는 A에서 4100, B에서 4132다. 선택한 A 정의의 원래 상대 값은 4100−4−4000=96이다.

  3. A helper만 32 이동하면 S=4132이고 결과 128이 되어 이 signed 8비트 형식에서 실패한다. B helper 주소가 우연히 같아져도 local 문맥을 하나로 합치지 않는다.

  4. main,A,B,A는 a_f,b_g,a_h를 선택하여 해결한다. A/B 그룹 반복도 지정 모형에서 해결한다. 전체 포함으로 a_u까지 넣으면 정의 없는 missing이 남는다.

파일 내용 합은 25바이트이고 전체 파일 길이는 미확정이다. 심볼 주소는 원래 4100/4132, 선택한 상대 재배치는 96에서 128로 바뀌어 실패한다. main,A,B,A로 세 필요한 멤버를 선택할 수 있지만 전체 포함은 missing 요구를 추가할 수 있다. 실제 ELF 생성·링크·적재·학생 실험 결과는 아니다.

해결한 뒤 점검할 것

  • 파일 오프셋·정렬 간격·메모리 요구를 분리한다.

  • local 이름의 입력 문맥을 보존한다.

  • 원래 addend와 필드 폭을 사용하여 128 범위 실패를 판정한다.

  • 새 요구 h가 생긴 뒤 A 재검색을 배치한다.

  • 그룹과 전체 포함 및 실제 실행 미수행을 구별한다.

보강 자료의 출처와 확인 범위
  • System V ABI sections

    실제 섹션 헤더 필드·정렬/NOBITS 및 특수 섹션 350–460행을 읽었다. 새 파일 배치 숫자는 자체 모형이며 실제 ELF 전체를 생성하지 않았다.

  • System V ABI symbol table

    공식 전체 본문을 HTML 텍스트로 읽어 local/global/weak와 relocatable 섹션 내 값/실행 파일 가상 주소의 차이를 확인했다. 자체 local 두 주소는 손계산했다.

  • System V ABI relocation

    공식 전체 본문을 읽어 REL/RELA addend·r_offset의 객체별 의미와 processor-specific 형식 조건을 확인했다. signed 8비트 형식은 자체 종이 모형이다.

  • System V ABI program header

    실제 0–177행의 파일/가상 시작·p_filesz/p_memsz·정렬 합동·PT_LOAD 0 초기화를 읽었다. 세그먼트 예제는 별도 가정이며 앞의 섹션 배치와 결합해 실행 가능하다고 주장하지 않는다.

  • GNU ld archive options

    실제 169–178행 위치별 아카이브 검색, 712–720행 그룹 반복, 1348–1352행 전체 포함을 읽었다. 새로운 멤버 요구 그래프만 손추적했고 GNU ld를 실행하지 않았다.

전체 base 세 소단원과 새 보강/전이를 읽고 손으로 정렬 146/147→152와 간격 6/5, 내용 24/25 및 local 4100/4132를 재계산했다. 별도 PT_LOAD의 160/32 구간, signed 8비트 96/128/−128·P 범위901–1156·두 레코드96/80을 검산했다. 새 아카이브 추출의 h/g 미해결과 A 재검색·세 대 네 멤버/없는 missing을 손추적했다. 새 계산 코드 실행은 하지 않았다.

not_executed — 실제 C/GCC/readelf/ld·ELF 생성·실행 적재·동적 라이브러리·파일 측정·ABI 적합성 시험은 미수행이다. 지정 배치/재배치/멤버 그래프의 손모형만 사용했다.

실제 같은 단원 세 고유 canonical 설명 전체를 읽고 여섯 HTML 선수 앵커의 파일/심볼·재배치·아카이브 의미를 대조했다.
