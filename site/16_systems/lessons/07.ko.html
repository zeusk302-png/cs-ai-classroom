소단원 7.1

최적화의 의미 보존

연산을 줄이면 언제나 같은 프로그램일까?

준비 개념과 학습 목표

준비 개념

  • 관찰 가능한 결과에는 출력·파일 효과·정의된 volatile 접근 등이 있다.

  • 정의되지 않은 동작은 언어가 결과를 보장하지 않는 입력/상태다.

학습 목표

  • 변환 전후 결과와 부작용을 비교한다.

  • 최적화가 적용되는 전제와 반례를 찾는다.

같은 반환값이 남으면 호출을 지워도 되는가?

자체 단일 스레드 모형의 mark()는 로그 끝에 문자 M을 붙인 뒤 항상 0을 반환한다. 별도 두 문장 a=mark(); b=mark(); 뒤 a+b를 반환하면 결과는 0이지만 로그는 MM이다. 한 번만 호출하고 같은 값을 두 번 더해도 결과는 0이며 로그는 M이다. 반환값 장부만 보았다면 이 차이를 놓친다.

관찰 계약이 반환값과 로그를 모두 요구하면 두 프로그램은 등가가 아니다. 호출이 순수하다는 증거, 로그가 계약에서 제외된다는 증거 없이 중복 호출을 제거하지 않는다. volatile도 일반 변수의 접근과 다르게 다뤄질 수 있으나 스레드 동기화나 장치 동작의 모든 조건을 대신하지 않는다.

산술 변환도 입력 영역을 먼저 적는다. 아래 십진 두 자리 모형은 매 연산 뒤 유효 숫자 두 자리로 가장 가까운 값에 반올림한다. 이 모형의 유한 연산은 정확한 실수 대수도 실제 C 컴파일 결과도 아니다. 잘못된 C signed overflow나 데이터 레이스는 실제로 실행하지 않는다.

먼저 확인할 개념
  • 결과와 부작용의 관찰 계약

    반환값과 로그를 각각 비교한다.

  • 옵션이 허용하는 의미 변경

    빠른 산술 옵션과 엄격한 결과 요구를 함께 확인한다.

결과를 지키며 구현을 바꾼다

컴파일러 최적화는 계산의 배치를 바꾸거나 중복 계산을 없애 비용을 줄이는 과정이다. 소스의 모든 중간 변수 값을 같은 기계 명령으로 유지할 필요는 없지만 언어가 요구하는 관찰 가능한 행동은 유지해야 한다. 여기서는 정수 범위 안의 순수 산술과 단일 스레드를 우선 다룬다.

예를 들어 x가 변하지 않으면 (x+3)+(x+3)을 두 번 계산하는 대신 임시값을 재사용할 수 있다. 그러나 읽기마다 달라질 수 있는 외부 상태나 부작용 함수 호출까지 같은 값이라고 가정하면 출력 횟수나 값이 달라질 수 있다.

대수 법칙에도 적용 조건이 있다

수학의 실수 덧셈 결합법칙과 유한 정밀도 부동소수점 계산은 구별한다. 예를 들어 큰 값에 작은 값을 더할 때 반올림이 일어나면 괄호를 옮긴 결과가 달라질 수 있다. 부동소수점 재결합을 허용하는 옵션의 의미를 확인해야 한다.

C의 signed 정수 overflow는 일반적인 순환 산술로 보장되지 않는다. 반면 unsigned의 모듈러 연산은 정의된다. 아래 예제는 값이 작아 overflow가 없다고 명시하며, 특정 언어의 정의되지 않은 동작에 대해 최적화 전후 출력을 비교하는 실험은 하지 않는다.

눈에 보이는 효과를 먼저 목록으로 만든다

변환 검토에서는 반환값만 보지 말고 함수 호출·쓰기·예외 또는 오류 발생 조건도 적는다. 원래 호출이 두 번이고 변환 뒤 한 번이라면 함수가 순수한지 증명하기 전에는 등가라고 확정할 수 없다. 관찰 대상이 무엇인지를 명시해야 한다.

volatile 접근은 컴파일러가 일반 변수와 다르게 취급하지만 여러 스레드의 동기화를 자동 보장하지 않는다. 최적화 문제를 해결하려고 모든 변수에 volatile을 붙이는 방식은 언어의 메모리 규약과 성능을 함께 오해할 수 있다.

중간 과정을 따라가는 예제

정수 x=4가 변하지 않는다. y=(x+3)+(x+3)을 임시값 u=x+3; y=u+u로 바꾼다. 이어 f()가 매번 전역 counter를 1 증가시켜 새 counter를 반환할 때, 순서가 명시된 a=f(); b=f(); y=a+b;를 u=f(); y=u+u;로 바꾸어 비교하라. counter 초기 0이며 두 호출은 별도 문장으로 순차 수행한다.

  1. 순수 식은7+7=14, 임시값도7을 두 번 더해14다.

  2. 원래 f 두 호출의 반환은1과2로 합 3, 최종 counter 2다.

  3. 한 번 호출은u1로 합 2, counter 1이다.

순수 식은 등가이나 f 변환은 반환값3→2와 부작용2→1을 모두 바꾸어 부적절하다.

조건을 바꾸어 비교하기

결과 검사가 놓친 로그

mark 모형의 두 계획을 반환값과 로그로 검사하라.

  1. 두 별도 호출은 0과 0을 돌려주고 MM을 남긴다.

  2. 한 호출 재사용은 0+0이지만 M만 남긴다.

반환값 0은 같고 로그 길이는 2와 1이다. 로그를 요구하면 부적절한 변환이다.

비교할 점

같은 반환값과 같은 관찰 전체를 구별한다.

두 자리 반올림의 괄호

모형 a=100,b=3,c=−100에서 (a+b)+c와 a+(b+c)를 매 단계 반올림한다.

  1. 103은 두 자리로 100이 되어 첫 식은 0이다.

  2. 3−100=−97은 두 자리로 표현되어 둘째 식은 100−97=3이다.

0과 3이다. 실제 CPU의 정밀도나 GCC가 한 변환을 했다고 주장하지 않는다.

비교할 점

매 연산의 반올림 위치가 관찰값을 바꾼다.

종이와 본문으로 직접 해보기

부동소수점 교육 모형에서 모든 연산을 유효 십진3자리로 반올림한다. a=1000,b=1,c=−1000일 때 (a+b)+c와 a+(b+c)를 계산하라.

힌트 보기

각 덧셈 직후에 세 자리로 반올림한다. 실제 CPU의 특정 정밀도를 주장하지 않는다.

풀이 보기

1001→1000이므로 앞 식은0이다. b+c=−999는 표현 가능하고 a−999=1이므로 뒤 식은1이다. 반올림 모형에서 괄호 이동은 결과를 바꾼다.

오해와 반례

반환값만 같으면 모든 최적화가 올바르다.

같은 반환값을 주어도 로그 기록 두 번을 한 번으로 줄이면 관찰 효과가 달라질 수 있다. 호출이 순수하거나 관찰 가능한 부작용이 없다는 조건을 확인한다.

루프 불변식과 의존성

루프 안에서 같은 곱셈을 네 번 하면 한 번으로 줄일 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 루프 불변 계산은 각 반복에서 같은 값을 계산한다.

  • 여기서 불변식은 계산 이동의 값 불변성을 뜻하며 논리적 반복 불변명제와 구별한다.

학습 목표

  • 루프 밖 이동의 조건을 판단한다.

  • 반복 간 의존성이 순서 변경을 막는 사례를 추적한다.

같은 주소를 네 번 읽으면 같은 값을 네 번 읽는가?

유효한 int 객체 x가 2이고 p와 q가 둘 다 그 객체를 가리킨다. 세 반복의 본문은 별도 순차 문장 y[i]=*p; *q=*q+1이다. 읽은 값은 2,3,4이고 x는 5가 된다. 첫 *p를 루프 밖에서 한 번 읽어 재사용하면 y는 2,2,2가 된다. 주소가 그대로여도 뒤 쓰기가 다음 값의 생산자다.

p가 가리킨 x와 q가 가리킨 z가 별도 객체이고 x가 어떤 호출/쓰기에도 바뀌지 않는다면 y는 모두 2다. x 읽기를 이동하려면 범위·수명·오류·volatile 여부도 확인한다. 본문의 *q 쓰기는 여전히 세 번 남겨 z의 마지막 값 5를 유지한다. 모든 읽기/쓰기를 지우는 변환과 구별한다.

값이 같아도 원래 0회 실행되던 식을 새로 평가하면 의미를 바꿀 수 있다. n=0,d=0에서 본문 안에만 있는 24/d는 원래 평가되지 않는다. n>0이고 d≠0인 정의된 입력에서만 계산 이동을 검토하고, n>0,d=0은 원래도 C에서 정의되지 않으므로 기대 출력을 만들지 않는다.

먼저 확인할 개념
  • 불변 읽기와 별칭 쓰기

    주소의 동일성과 값의 불변성을 나눈다.

  • 정의된 입력과 평가 효과

    원래 평가되지 않은 연산을 새로 만들지 않는다.

변하지 않는 값의 생산 비용을 줄인다

반복마다 k가 변하지 않고 곱셈이 부작용이나 오류 없이 정의되면 k*3 같은 값을 루프 앞에서 계산할 수 있다. 반복 인덱스 i가 식에 들어가면 일반적으로 같은 값이 아니므로 단순히 밖으로 꺼낼 수 없다. 코드가 짧다는 이유만으로 불변이라고 판단하지 않는다.

메모리에서 읽는 값도 주소가 같다는 사실만으로 불변은 아니다. 반복 안의 다른 포인터 쓰기나 함수 호출이 그 위치를 바꾸면 값이 변한다. 별칭 분석과 호출의 효과 분석이 계산 이동을 제한하는 이유다.

이전 반복의 결과를 기다린다

a[i]=a[i−1]+1처럼 앞 반복의 쓰기를 다음 반복이 읽으면 loop-carried dependency가 있다. 각 반복이 서로 다른 i를 사용해도 값의 연결 사슬이 생긴다. 독립 반복처럼 임의 병렬화하거나 역순으로 바꿀 수 없다.

의존성을 판정할 때 읽는 주소와 쓰는 주소, 두 반복의 인덱스 관계를 적는다. b[i]=a[i]+1에서 두 배열이 겹치지 않고 a를 수정하지 않는다는 전제가 있으면 각 반복은 독립일 수 있다. 배열 이름만 다르다고 실제 저장공간이 분리되는 것은 아니다.

원래 실행되지 않던 계산을 만들지 않는다

루프가 0회 실행되면 원래 본문 식은 계산되지 않는다. 루프 밖으로 이동해0으로 나누거나 잘못된 주소를 읽게 하면 원래 없던 오류가 생긴다. 값이 반복마다 같다는 조건 외에 이동 위치에서 안전하게 평가할 수 있다는 조건도 필요하다.

필요하면 반복이 실행되는 분기 안으로 계산을 옮긴다. 연산을 덜 하는 이득과 조건 검사의 비용은 실제 대상에서 측정해야 한다. 본문은 작은 표로 의미와 연산 횟수를 확인하며 실제 GCC가 반드시 해당 변환을 한다고 주장하지 않는다.

소단원 7.3

최적화 수준 비교

-O3를 붙이면 모든 프로그램이 가장 빨라질까?

준비 개념과 학습 목표

준비 개념

  • -O 옵션은 최적화 정책의 묶음이며 실제 활성 패스는 대상과 버전에 따라 다르다.

  • 측정 목적은 실행시간·크기·빌드시간·디버깅 등 여러 가지다.

학습 목표

  • 옵션의 목적을 구별한다.

  • 동일 조건의 가상 측정표를 해석한다.

가상 시간표에서 선택은 실행 횟수와 입력 비중에 따라 바뀌는가?

새 가상 표의 A는 빌드 1초·한 실행 80ms·코드 8KiB, B는 2초·30ms·10KiB, C는 4초·20ms·14KiB다. 이것은 실제 -O 옵션의 측정이 아니라 후보 세 개의 가정이다. 빌드 한 번 뒤 N번 실행한 총시간은 각각 1+0.08N, 2+0.03N, 4+0.02N초다.

한 실행 최단은 C지만 N=10의 총시간은 A 1.8초, B 2.3초, C 4.2초다. N=100이면 B 5초가 A 9초와 C 6초보다 작다. 최초 컴파일 비용과 반복 실행의 분모를 섞지 않는다. 코드 크기 10KiB 이하가 필수라면 C는 시간 우열을 따지기 전에 제외된다.

실행시간 요약도 입력 비중을 담는다. 다른 가상 X/Y의 작은 작업 시간은 1/2ms, 큰 작업 시간은 100/60ms다. 작은 작업 비중 p일 때 평균은 X=100−99p, Y=60−58p다. 어느 후보가 좋은지는 p와 목적에 따라 달라지며 세 반복의 중앙값 하나가 실제 배포 입력 비중을 증명하지 않는다. 정확성 통과는 시간 비교보다 먼저 필요한 독립 조건이다.

먼저 확인할 개념
  • 빌드·실행·크기와 비교 분모

    한 실행 시간과 전체 비용을 따로 읽는다.

  • 요구 관찰과 의미 옵션

    빠른 결과라도 의미 요구를 통과해야 후보가 된다.

수준은 목적에 맞게 읽는다

GCC -O0는 빠른 컴파일과 소스에 가까운 디버깅을 우선하며 대부분의 최적화 패스를 끈다. -O1/O2/O3는 서로 다른 패스 묶음을 추가한다. 숫자를 늘리면 가능한 변환이 늘지만 모든 입력에서 실행시간이 단조 감소한다는 보장은 없다.

-Os는 코드 크기를 고려하고 -Og는 최적화와 디버깅 경험의 균형을 목표로 한다. 정확한 활성 목록은 해당 compiler version/target의 문서를 확인한다. 서로 다른 컴파일러의 같은 숫자를 동일 기계 코드 정책으로 취급하지 않는다.

비교 실험의 분모를 맞춘다

동일 소스·입력·기계·컴파일러 버전·실행 환경에서 결과의 정확성을 먼저 확인하고 시간을 비교한다. 워밍업·캐시 상태·반복 측정의 변동도 기록한다. 한 번의 숫자만으로 아주 작은 차이를 확정하지 않는다.

빌드시간과 실행시간은 별도다. 여러 번 실행하는 서비스와 한 번 실행하는 작업에서는 컴파일 비용의 중요도가 다를 수 있다. 코드 크기가 늘면 instruction cache에 영향을 줄 수 있지만 아래 표만으로 그 원인을 실제 관측했다고 말할 수 없다.

언어 가정을 바꾸는 옵션은 따로 검토한다

-Ofast는 -O3의 다른 이름이 아니다. 문서는 엄격한 표준 준수를 무시할 수 있는 최적화와 fast-math 등을 포함한다고 설명한다. 입력에 NaN/무한대가 있는지, 반올림/괄호 의미가 중요한지 확인해야 한다.

최적화 이후 문제가 보이면 무조건 컴파일러 버그라고 결론 내리지 않는다. 소스의 overflow·범위 밖 접근·데이터 레이스·잘못된 alias 가정도 검토한다. 정의된 프로그램의 요구사항과 사용 옵션이 허용하는 의미를 먼저 맞춘다.

빌드는 한 번이고 모든 실행의 비용은 후보별 상수라는 가정이다. 캐시·입력 변화·네트워크·컴파일 실패 등 실제 원인은 포함하지 않는다. 크기 제한을 추가하면 마지막 열을 다시 판단한다.

중간 과정을 따라가는 예제

가상 동일조건 표: O0 실행100ms/크기10KiB/빌드1s, O2 40ms/12KiB/2s, O3 50ms/18KiB/3s, Os 45ms/9KiB/2s이다. 가장 빠른 실행, 가장 작은 코드와 O2의 O0 대비 speedup을 구하라.

  1. 실행 최소40ms이므로 O2다.

  2. 크기 최소9KiB이므로 Os다.

  3. speedup=100/40=2.5배, 실행시간 감소율(100−40)/100=.6이다.

  4. O3는 O2보다10ms 느리고6KiB 크다. 원인은 표에 없다.

가상 표에서는 속도 O2/크기 Os이며2.5배와60% 감소는 다른 표현이다.

조건을 바꾸어 비교하기

두 전환점의 전체 하한

자연수 N≥1에서 A/B/C 전체 최소를 구한다.

  1. A−B=−1+0.05N이므로 전환은 20이다.

  2. B−C=−2+0.01N이므로 전환은 200이다.

  3. A/C가 동률인 N=50에서는 B=3.5초가 둘보다 작다.

N<20은 A, 20은 A/B, 20<N<200은 B, 200은 B/C, N>200은 C다.

비교할 점

쌍별 동률이 전체 최적점인지는 제3 후보도 확인한다.

대표 표본이 바꾼 입력 비중

작은 작업 99개·큰 작업 1개와 작은 9개·큰 1개에서 X/Y 평균을 구한다.

  1. 99/1에서 합은 X 199ms, Y 258ms다.

  2. 9/1에서 합은 X 109ms, Y 78ms다.

첫 평균 X 1.99/Y 2.58ms, 둘째 X 10.9/Y 7.8ms다.

비교할 점

같은 두 작업별 시간에서도 배포 비중 변화가 전체 순위를 바꾼다.

종이와 본문으로 직접 해보기

동일 작업을1000회 실행한다고 가정한다. O0/O2의 컴파일1회+총 실행시간을 계산하고 어느 쪽이 더 작은지 비교하라.

힌트 보기

ms를s로 바꾸고 빌드시간을 한 번 더한다.

풀이 보기

O0는1+1000*.1=101s, O2는2+1000*.04=42s다. 실행1회이면 O0는1.1s/O2는2.04s이므로 총비용 선택이 바뀐다. 실제 측정값이 아닌 표의 계산이다.

오해와 반례

최적화 숫자가 크면 속도·크기·디버깅 모두 좋아진다.

가상 O3는 O2보다 느리고 크다. -Og의 목표도 디버깅 균형이며 모든 목표가 동시에 최적화되지는 않는다. 실제 프로그램에서는 의미 보존과 반복 측정이 선행된다.

스스로 풀어보기

먼저 답과 이유를 적고, 필요한 만큼 힌트를 한 단계씩 열어 보세요.

연습 1 · 값과 상태 예측

N=50에서 A/B/C 총시간과 코드≤10KiB 필수 조건의 선택을 구하라.

힌트 1

총시간은 빌드 한 번과 50 실행이다.

힌트 2

크기로 C를 먼저 제외한다.

풀이와 답 확인

  1. A=5초, B=3.5초, C=5초다.

  2. A/B가 크기 조건을 만족하고 B가 더 빠르다.

B를 선택한다. 모든 숫자는 가상 표의 산술이며 실제 최적화 효과 측정이 아니다.

흔한 오답에서 다시 생각하기

A와 C가 동률이면 둘이 최적이다.

전체 최소 B를 빠뜨렸다.

연습 2 · 오류 찾아 고치기

가상 반복 X=[1,1,100]ms, Y=[2,2,60]ms에서 중앙값 1<2이므로 X가 언제나 좋다고 했다. 어떤 목표를 누락했는가?

힌트 1

각 표본의 합도 계산한다.

힌트 2

중앙값과 평균의 목적이 다르다.

풀이와 답 확인

  1. 중앙값은 X 1/Y 2ms지만 합은 X 102/Y 64ms다.

  2. 같은 세 작업 전체 시간/평균을 목적에 넣으면 Y가 더 작다.

평균은 X 34ms, Y 64/3ms다. 중앙값만으로 총시간 우열이나 실제 배포 비중을 보장하지 않는다.

흔한 오답에서 다시 생각하기

중앙값이 낮으면 평균도 낮다.

큰 비용 표본의 크기와 빈도를 중앙값 하나가 보존하지 않는다.

연습 3 · 직접 만들어 보기

N=300에서 코드≤10KiB·총시간≤12초를 모두 만족하는 후보를 구성하라.

힌트 1

C는 코드가 14KiB다.

힌트 2

A/B 총시간은 25/11초다.

풀이와 답 확인

  1. A는 시간 제약에 실패한다.

  2. C는 크기 제약에 실패하고 B는 10KiB/11초다.

B만 가능하다. 더 빠른 C도 필수 크기 제약을 충족하지 않는다.

흔한 오답에서 다시 생각하기

제약을 평균 점수로 합치면 실패를 무시해도 된다.

필수 조건은 점수의 장점으로 상쇄하지 않는다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

X/Y의 작은 작업 비중 p∈[0,1]에서 X가 평균으로 엄격히 빠른 범위를 구하라.

힌트 1

100−99p<60−58p를 푼다.

힌트 2

두 시간은 같은 한 작업당 ms다.

풀이와 답 확인

  1. 40<41p이므로 p>40/41이다.

  2. p=40/41이면 동률이다.

X가 엄격히 빠른 범위는 (40/41,1]이다. Y는 p<40/41에서 빠르다.

흔한 오답에서 다시 생각하기

작은 작업이 절반 넘으면 X가 빠르다.

큰 작업의 차이 40ms와 작은 작업의 차이 1ms를 비중에 반영해야 한다.

설명 기준 확인

한 단계 더

크기≤10KiB와 실행≤50ms라는 두 제약을 동시에 적용하면 이 표에서는 Os가 가능하다. 비용을 하나의 점수로 합치기 전에 필수 제약과 선호 목적을 분리한다.

출처와 확인 범위
  • GCC: Optimize Options

    공식 옵션 본문 -O0/O1/O2/O3/Og/Os/Ofast와 대상별 옵션 차이, loop invariant motion 및 undefined behavior 가정 부분을 실제 읽었다. 아래 표는 실제 컴파일 측정이 아닌 가상 자료다.

다른 문제에 적용하기

동일한 세 반복 모형의 x는 2이고 p=q=&x다. 본문은 별도 문장 y[i]=*p; z=mark(); *q=*q+1이며 mark는 M을 로그에 붙이고 0을 반환한다. 요구는 y와 마지막 x 및 로그 모두다. 후보 V는 첫 *p를 앞에서 읽어 재사용하고 mark를 한 번만 호출한다. 먼저 원래/V 관찰을 비교한다. 읽기·호출을 모두 보존해 정확성을 만족하는 구현 후보 A/B/C는 위 가상 비용표를 가진다. N=100, 코드≤10KiB에서 최종 선택과 근거를 구성하라.

힌트 1

세 번의 읽기 직전 x와 M의 개수를 따로 기록한다. 마지막 x만 비교하지 않는다.

힌트 2

의미 실패 후보 V는 시간과 무관하게 거절한다. A/B/C의 크기와 100회 전체 시간을 계산한다.

풀이와 답 확인

  1. 원래 읽은 y는 [2,3,4]이고 세 증가 뒤 x는 5이며 로그는 MMM이다.

  2. V의 y는 [2,2,2]이고 증가 쓰기를 세 번 남겼다면 x는 5지만 로그는 M이다. 요구 두 항목이 달라 V를 거절한다.

  3. 정확성을 만족한 A/B/C에서 C는 크기 14KiB로 제외한다. A/B의 전체 시간은 9/5초다.

  4. B가 크기 10KiB와 전체 5초로 가능한 두 후보 중 작다. 가상 선택이며 실제 컴파일/장치 성능 인증은 아니다.

V는 의미 실패다. 지정 계약을 만족한 구현 중에는 B를 선택한다. 원래 관찰 y=[2,3,4], x=5, 로그 MMM을 그대로 요구하며 총시간 5초와 크기 10KiB는 가상 입력의 산술이다.

해결한 뒤 점검할 것

  • 순차 문장의 읽기/쓰기/로그 장부를 분리한다.

  • 최종 x가 같아도 y와 로그 차이로 V를 거절한다.

  • 읽기 재사용과 mark 호출 제거의 증명 책임을 각각 설명한다.

  • 빌드 한 번·100 실행 및 필수 크기를 적용해 B를 구한다.

  • 가상 모형과 실제 C/GCC/장치/학생 미수행을 구별한다.

보강 자료의 출처와 확인 범위
  • GCC optimization options

    실제 공식 본문 3–171행의 대상별 옵션·목적·Ofast와 1108–1146의 별칭 조건, 1440–1497의 재결합/유한값/반올림 조건을 읽었다. 자체 후보 A/B/C 비용은 문서의 실제 성능 결과가 아니다.

  • GCC volatile access

    실제 전체 3–35행의 sequence point 경계·일반 객체 순서 비보장·대입 뒤 재읽기·bit-field 주의를 읽었다. 본 단원의 로그 효과 모형은 직접 작성했고 장치 접근은 실행하지 않았다.

전체 base 세 소단원과 보강/전이를 읽고 손으로 0/로그2대1·두자리0대3과 네 b값, 별칭2/3/4→5와 짝홀 두 순서, 비용 전환20/200·N50/100/300·평균199/258 및109/78·경계40/41을 재계산했다. 새 산술 코드 실행은 하지 않았다.

not_executed — 실제 C/GCC/최적화 패스·UB·volatile/네트워크/스레드·시간 benchmark 실행은 미수행이다. 모두 지정 단일 스레드 종이 모형과 가상 비용 산술이다.

실제 base07의 세 고유 canonical 설명 전체와 여섯 HTML 앵커를 읽고 관찰 계약·평가 여부·별칭과 비용/옵션의 의미를 대조했다.
