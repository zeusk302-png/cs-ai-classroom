소단원 7.1

최적화의 의미 보존

연산을 줄이면 언제나 같은 프로그램일까?

준비 개념과 학습 목표

준비 개념

  • 관찰 가능한 결과에는 출력·파일 효과·정의된 volatile 접근 등이 있다.

  • 정의되지 않은 동작은 언어가 결과를 보장하지 않는 입력/상태다.

학습 목표

  • 변환 전후 결과와 부작용을 비교한다.

  • 최적화가 적용되는 전제와 반례를 찾는다.

결과를 지키며 구현을 바꾼다

컴파일러 최적화는 계산의 배치를 바꾸거나 중복 계산을 없애 비용을 줄이는 과정이다. 소스의 모든 중간 변수 값을 같은 기계 명령으로 유지할 필요는 없지만 언어가 요구하는 관찰 가능한 행동은 유지해야 한다. 여기서는 정수 범위 안의 순수 산술과 단일 스레드를 우선 다룬다.

예를 들어 x가 변하지 않으면 (x+3)+(x+3)을 두 번 계산하는 대신 임시값을 재사용할 수 있다. 그러나 읽기마다 달라질 수 있는 외부 상태나 부작용 함수 호출까지 같은 값이라고 가정하면 출력 횟수나 값이 달라질 수 있다.

대수 법칙에도 적용 조건이 있다

수학의 실수 덧셈 결합법칙과 유한 정밀도 부동소수점 계산은 구별한다. 예를 들어 큰 값에 작은 값을 더할 때 반올림이 일어나면 괄호를 옮긴 결과가 달라질 수 있다. 부동소수점 재결합을 허용하는 옵션의 의미를 확인해야 한다.

C의 signed 정수 overflow는 일반적인 순환 산술로 보장되지 않는다. 반면 unsigned의 모듈러 연산은 정의된다. 아래 예제는 값이 작아 overflow가 없다고 명시하며, 특정 언어의 정의되지 않은 동작에 대해 최적화 전후 출력을 비교하는 실험은 하지 않는다.

눈에 보이는 효과를 먼저 목록으로 만든다

변환 검토에서는 반환값만 보지 말고 함수 호출·쓰기·예외 또는 오류 발생 조건도 적는다. 원래 호출이 두 번이고 변환 뒤 한 번이라면 함수가 순수한지 증명하기 전에는 등가라고 확정할 수 없다. 관찰 대상이 무엇인지를 명시해야 한다.

volatile 접근은 컴파일러가 일반 변수와 다르게 취급하지만 여러 스레드의 동기화를 자동 보장하지 않는다. 최적화 문제를 해결하려고 모든 변수에 volatile을 붙이는 방식은 언어의 메모리 규약과 성능을 함께 오해할 수 있다.

중간 과정을 따라가는 예제

정수 x=4가 변하지 않는다. y=(x+3)+(x+3)을 임시값 u=x+3; y=u+u로 바꾼다. 이어 f()가 매번 전역 counter를 1 증가시켜 새 counter를 반환할 때, 순서가 명시된 a=f(); b=f(); y=a+b;를 u=f(); y=u+u;로 바꾸어 비교하라. counter 초기 0이며 두 호출은 별도 문장으로 순차 수행한다.

  1. 순수 식은7+7=14, 임시값도7을 두 번 더해14다.

  2. 원래 f 두 호출의 반환은1과2로 합 3, 최종 counter 2다.

  3. 한 번 호출은u1로 합 2, counter 1이다.

순수 식은 등가이나 f 변환은 반환값3→2와 부작용2→1을 모두 바꾸어 부적절하다.

종이와 본문으로 직접 해보기

부동소수점 교육 모형에서 모든 연산을 유효 십진3자리로 반올림한다. a=1000,b=1,c=−1000일 때 (a+b)+c와 a+(b+c)를 계산하라.

풀이 보기

반환값만 같으면 모든 최적화가 올바르다.

같은 반환값을 주어도 로그 기록 두 번을 한 번으로 줄이면 관찰 효과가 달라질 수 있다. 호출이 순수하거나 관찰 가능한 부작용이 없다는 조건을 확인한다.

소단원 7.2

루프 불변식과 의존성

루프 안에서 같은 곱셈을 네 번 하면 한 번으로 줄일 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 루프 불변 계산은 각 반복에서 같은 값을 계산한다.

  • 여기서 불변식은 계산 이동의 값 불변성을 뜻하며 논리적 반복 불변명제와 구별한다.

학습 목표

  • 루프 밖 이동의 조건을 판단한다.

  • 반복 간 의존성이 순서 변경을 막는 사례를 추적한다.

변하지 않는 값의 생산 비용을 줄인다

반복마다 k가 변하지 않고 곱셈이 부작용이나 오류 없이 정의되면 k*3 같은 값을 루프 앞에서 계산할 수 있다. 반복 인덱스 i가 식에 들어가면 일반적으로 같은 값이 아니므로 단순히 밖으로 꺼낼 수 없다. 코드가 짧다는 이유만으로 불변이라고 판단하지 않는다.

메모리에서 읽는 값도 주소가 같다는 사실만으로 불변은 아니다. 반복 안의 다른 포인터 쓰기나 함수 호출이 그 위치를 바꾸면 값이 변한다. 별칭 분석과 호출의 효과 분석이 계산 이동을 제한하는 이유다.

이전 반복의 결과를 기다린다

a[i]=a[i−1]+1처럼 앞 반복의 쓰기를 다음 반복이 읽으면 loop-carried dependency가 있다. 각 반복이 서로 다른 i를 사용해도 값의 연결 사슬이 생긴다. 독립 반복처럼 임의 병렬화하거나 역순으로 바꿀 수 없다.

의존성을 판정할 때 읽는 주소와 쓰는 주소, 두 반복의 인덱스 관계를 적는다. b[i]=a[i]+1에서 두 배열이 겹치지 않고 a를 수정하지 않는다는 전제가 있으면 각 반복은 독립일 수 있다. 배열 이름만 다르다고 실제 저장공간이 분리되는 것은 아니다.

원래 실행되지 않던 계산을 만들지 않는다

루프가 0회 실행되면 원래 본문 식은 계산되지 않는다. 루프 밖으로 이동해0으로 나누거나 잘못된 주소를 읽게 하면 원래 없던 오류가 생긴다. 값이 반복마다 같다는 조건 외에 이동 위치에서 안전하게 평가할 수 있다는 조건도 필요하다.

필요하면 반복이 실행되는 분기 안으로 계산을 옮긴다. 연산을 덜 하는 이득과 조건 검사의 비용은 실제 대상에서 측정해야 한다. 본문은 작은 표로 의미와 연산 횟수를 확인하며 실제 GCC가 반드시 해당 변환을 한다고 주장하지 않는다.

중간 과정을 따라가는 예제

k=2,n=4이고 k는 바뀌지 않는다. y[i]=i+k*3, i=0..3을 비교한다. 이어 a=[0,10,20,30]에 i=1..3 순서로 a[i]=a[i−1]+1을 수행하고 역순 수행과 비교하라.

  1. k*3=6이므로 y는6,7,8,9다. 곱셈은4회에서1회로 줄일 수 있다.

  2. 정순 a는 i1에서1, i2에서2, i3에서3으로 [0,1,2,3]이다.

  3. 역순은 a3=21,a2=11,a1=1로 [0,1,11,21]이다.

불변 계산 이동은 같은 y를 유지하지만 반복 순서 변경은 의존성 때문에 다른 a를 만든다.

종이와 본문으로 직접 해보기

n=0,k=0일 때 루프 본문에서만100/k를 계산한다. 식이 불변이라고 루프 앞에서 계산해도 되나? n>0인 경우만 계산하는 분기를 적어라.

힌트 보기

0회 반복일 때 평가되는 식을 표시한다.

풀이 보기

원래는 나눗셈이 없으므로 밖으로 꺼내면0 나누기가 생긴다. if(n>0) 내부에서 k!=0 등 원래 필요한 조건을 만족할 때 계산해야 하며, n>0/k0의 원래 프로그램도 정의되지 않음을 구별한다.

오해와 반례

같은 주소를 읽으면 값도 매번 같다.

포인터 p와 q가 같은 위치를 가리키고 반복 안에서 *q를 증가시키면 다음 *p 값은 변한다. 별칭이 가능한 쓰기를 배제하지 못하면 메모리 읽기의 불변성을 단정할 수 없다.

소단원 7.3

최적화 수준 비교

-O3를 붙이면 모든 프로그램이 가장 빨라질까?

준비 개념과 학습 목표

준비 개념

  • -O 옵션은 최적화 정책의 묶음이며 실제 활성 패스는 대상과 버전에 따라 다르다.

  • 측정 목적은 실행시간·크기·빌드시간·디버깅 등 여러 가지다.

학습 목표

  • 옵션의 목적을 구별한다.

  • 동일 조건의 가상 측정표를 해석한다.

수준은 목적에 맞게 읽는다

GCC -O0는 빠른 컴파일과 소스에 가까운 디버깅을 우선하며 대부분의 최적화 패스를 끈다. -O1/O2/O3는 서로 다른 패스 묶음을 추가한다. 숫자를 늘리면 가능한 변환이 늘지만 모든 입력에서 실행시간이 단조 감소한다는 보장은 없다.

-Os는 코드 크기를 고려하고 -Og는 최적화와 디버깅 경험의 균형을 목표로 한다. 정확한 활성 목록은 해당 compiler version/target의 문서를 확인한다. 서로 다른 컴파일러의 같은 숫자를 동일 기계 코드 정책으로 취급하지 않는다.

비교 실험의 분모를 맞춘다

동일 소스·입력·기계·컴파일러 버전·실행 환경에서 결과의 정확성을 먼저 확인하고 시간을 비교한다. 워밍업·캐시 상태·반복 측정의 변동도 기록한다. 한 번의 숫자만으로 아주 작은 차이를 확정하지 않는다.

빌드시간과 실행시간은 별도다. 여러 번 실행하는 서비스와 한 번 실행하는 작업에서는 컴파일 비용의 중요도가 다를 수 있다. 코드 크기가 늘면 instruction cache에 영향을 줄 수 있지만 아래 표만으로 그 원인을 실제 관측했다고 말할 수 없다.

언어 가정을 바꾸는 옵션은 따로 검토한다

-Ofast는 -O3의 다른 이름이 아니다. 문서는 엄격한 표준 준수를 무시할 수 있는 최적화와 fast-math 등을 포함한다고 설명한다. 입력에 NaN/무한대가 있는지, 반올림/괄호 의미가 중요한지 확인해야 한다.

최적화 이후 문제가 보이면 무조건 컴파일러 버그라고 결론 내리지 않는다. 소스의 overflow·범위 밖 접근·데이터 레이스·잘못된 alias 가정도 검토한다. 정의된 프로그램의 요구사항과 사용 옵션이 허용하는 의미를 먼저 맞춘다.

중간 과정을 따라가는 예제

가상 동일조건 표: O0 실행100ms/크기10KiB/빌드1s, O2 40ms/12KiB/2s, O3 50ms/18KiB/3s, Os 45ms/9KiB/2s이다. 가장 빠른 실행, 가장 작은 코드와 O2의 O0 대비 speedup을 구하라.

  1. 실행 최소40ms이므로 O2다.

  2. 크기 최소9KiB이므로 Os다.

  3. speedup=100/40=2.5배, 실행시간 감소율(100−40)/100=.6이다.

  4. O3는 O2보다10ms 느리고6KiB 크다. 원인은 표에 없다.

가상 표에서는 속도 O2/크기 Os이며2.5배와60% 감소는 다른 표현이다.

종이와 본문으로 직접 해보기

동일 작업을1000회 실행한다고 가정한다. O0/O2의 컴파일1회+총 실행시간을 계산하고 어느 쪽이 더 작은지 비교하라.

힌트 보기

ms를s로 바꾸고 빌드시간을 한 번 더한다.

풀이 보기

O0는1+1000*.1=101s, O2는2+1000*.04=42s다. 실행1회이면 O0는1.1s/O2는2.04s이므로 총비용 선택이 바뀐다. 실제 측정값이 아닌 표의 계산이다.

오해와 반례

최적화 숫자가 크면 속도·크기·디버깅 모두 좋아진다.

가상 O3는 O2보다 느리고 크다. -Og의 목표도 디버깅 균형이며 모든 목표가 동시에 최적화되지는 않는다. 실제 프로그램에서는 의미 보존과 반복 측정이 선행된다.

한 단계 더

크기≤10KiB와 실행≤50ms라는 두 제약을 동시에 적용하면 이 표에서는 Os가 가능하다. 비용을 하나의 점수로 합치기 전에 필수 제약과 선호 목적을 분리한다.
