소단원 1.1

소스에서 실행 파일까지

C 코드의 a와 b라는 이름은 CPU에도 그대로 들어 있을까?

준비 개념과 학습 목표

준비 개념

  • int a=2는 정수 객체에 초기값을 지정하는 선언임을 안다. 이름과 값을 구별해 보자.

  • 비트는 두 상태를 구별하는 정보 단위다. 메모리는 주소를 통해 자료에 접근하는 저장 공간이라는 큰 그림을 복습한다.

  • 2+3=5를 계산할 수 있다. 이 계산의 의미와 그 의미를 실현하는 명령을 구별한다.

학습 목표

  • 전처리·컴파일·어셈블·링크·적재의 역할을 구분한다.

  • 설명용 명령 추적을 실제 ISA의 실행 결과와 구별한다.

  • 최적화가 소스 변수의 저장 형태를 바꿀 수 있는 조건을 설명한다.

오브젝트 파일을 만들었으면 외부 함수도 이미 들어 있을까?

작은 모듈 A는 함수 twice의 선언을 보고 twice(6)을 호출한다. 모듈 B는 twice(x)가 표현 범위 안의 x에 대해 2*x를 반환하는 정의를 제공한다. 보통의 분리 번역 모형에서는 A만 오브젝트로 만드는 일과 A/B를 함께 연결하는 일이 다르다. 선언은 호출의 형태를 알려 주지만 정의의 기계 코드가 A에 자동으로 포함된다는 뜻은 아니다.

GCC의 -E는 전처리에서, -S는 컴파일 뒤 어셈블리에서, -c는 어셈블 뒤 오브젝트에서 멈추고 링크를 하지 않는다. 따라서 A에 외부 참조가 남은 오브젝트가 있어도 이 단계의 성공과 모순되지 않는다. 외부 정의를 어디에서 공급할지는 다음 연결 단계의 문제다. 아래 명령은 실제로 실행하지 않은 단계 선택 계획이며 파일이 생성되었다고 주장하지 않는다.

의미 검토에서는 A가 6을 인수로 넘기고 B의 계약으로 반환 12를 얻는다는 추론과 실제 산출물의 명령 수를 나눈다. 동적 라이브러리·링크 최적화·ABI·목표 ISA·런타임 입력은 추가 조건이다. 한 소스 문장이 오브젝트 명령 하나에 대응하거나 성공한 링크가 모든 실행의 정상 종료를 보장한다고 일반화하지 않는다.

사람이 읽는 소스와 실행 가능한 표현

소스 코드는 사람이 규칙을 표현한 텍스트다. CPU는 일반적으로 C 문장을 직접 해석하지 않고, 자신의 명령 집합 구조(ISA)에 정의된 기계 명령을 실행한다. 컴파일러는 소스의 의미를 목표 환경의 명령으로 바꾸는 번역 도구다. 이 단원은 보통의 네이티브 C 도구 흐름을 설명한다. 인터프리터·가상머신·JIT를 쓰는 실행 모델을 모두 같은 흐름으로 단정하지 않는다.

int a=2, b=3; int s=a+b;처럼 값이 알려져 있으면 번역 결과가 반드시 ‘a를 읽고 b를 읽고 더한다’일 필요는 없다. 외부에 보이는 결과가 5라면 컴파일러가 미리 계산해 상수 5만 남길 수 있다. 소스 객체의 의미는 언어 규칙에 있고, 물리적인 저장 위치는 구현이 선택한다. 디버그 정보가 이름을 보관할 수 있어도 CPU가 그 이름을 산술 명령의 피연산자로 사용한다는 뜻은 아니다.

번역의 단계와 각 단계의 산출물

전처리는 포함 파일·매크로 등 전처리 지시를 다루고, 컴파일은 언어 구문과 의미를 분석해 목표 코드 표현을 만든다. 어셈블러는 어셈블리 명령을 오브젝트 코드로 바꾸며, 링커는 오브젝트 파일과 필요한 라이브러리의 참조를 연결한다. GCC는 이 단계들을 한 명령으로 구동하거나 중간에서 멈출 수 있다. 도구 내부가 항상 별도 실행 파일 네 개로 분리된다는 주장도 아니다.

오브젝트 파일에는 코드뿐 아니라 아직 해결되지 않은 외부 참조와 재배치 정보 등이 있을 수 있다. 문법 검사를 통과했다고 외부 함수 정의가 존재하는 것은 아니다. 링크에 성공한 실행 파일도 실행할 때 환경·라이브러리·입력 조건이 맞아야 한다. 운영체제의 적재 과정은 실행 파일을 프로세스 주소공간에 준비하고 시작 지점으로 제어를 넘기는 일이며, 동적 링크 일부는 적재나 실행 시점에도 일어날 수 있다.

설명용 명령 모델의 범위

종이에 R1, R2, R3이라는 레지스터 칸과 이름 붙인 메모리 칸을 만들자. LOAD R1,[A]는 A 칸 값을 R1으로, ADD R3,R1,R2는 두 레지스터 합을 R3으로, STORE [S],R3는 R3을 S 칸으로 옮긴다고 약속한다. 이것은 이 본문이 정한 교육용 명령이다. 실제 x86-64나 ARM 명령 형식·주소 배치·ABI를 관찰한 결과가 아니다.

소스와 이 추적을 연결할 때는 값 2,3,5가 대응한다는 의미 수준의 설명만 주장한다. 실제 컴파일러는 레지스터 수·최적화·호출 규약에 따라 저장과 명령을 다르게 선택한다. 특히 C에서 정의되지 않은 동작을 일으킨 프로그램에는 우리가 기대한 수학 결과를 유지할 의무를 그대로 적용할 수 없다. 이 예의 작은 양수 합은 표현 범위 안에 있고 부작용이 없는 경우로 제한한다.

// 교육용 가상 ISA: 실제 CPU 코드가 아님
LOAD R1,[A]
LOAD R2,[B]
ADD R3,R1,R2
STORE [S],R3

모든 실행 입력의 정상 종료

각 행은 정상 입력과 적절한 도구 조건에서 요청하는 단계다. 실제 성공 로그가 아니다. .o 이름이나 파일 존재만으로 올바른 목표·현재 소스·연결 성공을 대신 확인하지 않는다.

중간 과정을 따라가는 예제

교육용 모델에서 메모리 A=2, B=3, S=미정이다. 레지스터는 처음 미정이며 ADD는 정확한 정수 덧셈을 한다. 위 네 명령을 차례로 추적한다.

  1. LOAD R1,[A] 뒤 R1=2, 메모리는 그대로다.

  2. LOAD R2,[B] 뒤 R2=3, R1=2.

  3. ADD 뒤 R3=2+3=5. 이 시점에서 S는 아직 미정이다.

  4. STORE 뒤 S=5. 레지스터를 갱신한 일과 메모리를 갱신한 일을 구별한다.

최종 S=5다. 이 모델에서는 명령 네 개를 수행했지만 실제 컴파일된 코드가 네 명령이라는 결론은 내릴 수 없다.

선언과 정의의 다른 역할

A만 gcc -c로 처리하는 계획에서 twice의 정의가 없으면 반드시 C 문법 오류인가?

  1. A에 호환되는 함수 선언이 있으면 호출 형태의 번역과 정의 공급은 다른 일이다.

  2. 일반적인 외부 참조는 연결 단계에서 해결하므로 오브젝트 생성 계획만으로 정의를 확인하지 못한다.

반드시 문법 오류라고 할 수 없다. 정의가 어디에서 연결되는지 별도로 검사한다.

언어 분석·오브젝트 생성·외부 참조 해결은 서로 다른 확인 범위다.

같은 반환값과 다른 표현

B가 2*x를 계산하는 대신 알려진 호출의 결과 12를 남긴다는 최적화 예상에서 무엇을 확인해야 할까?

  1. 호출 입력과 관찰 가능한 부작용이 고정인지, 해당 언어 동작이 정의되어 있는지 확인한다.

  2. 실제 명령을 말하려면 목표·옵션·빌드 결과를 관찰해야 한다.

의미 수준의 반환 12만 손으로 확인했다. 이 자료에서는 실제 최적화나 명령 삭제를 관찰하지 않았다.

오해와 반례

소스 변수마다 반드시 메모리 칸이 하나 생기고 CPU는 그 이름을 안다.

컴파일러가 상수 합을 접으면 a와 b의 별도 물리 저장이 사라질 수 있다. 다른 값이 레지스터를 재사용할 수도 있다. 언어에서 객체가 존재한다는 의미와 실제 저장 구현은 구별된다. 주소를 취하거나 volatile 접근 등 관찰 가능한 요구가 추가되면 구현이 지켜야 할 제약도 달라진다.

여섯 바이트를 요청했는데 두 바이트만 받으면 실패일까?

정상적으로 열린 순차 바이트 입력에서 정수 쌍을 ASCII 형식 "12,34\n"으로 받는 가상 사례를 정한다. 총 여섯 바이트이며 첫 읽기는 "12", 다음 읽기는 ",34\n"을 반환한다고 가정한다. 요청한 여섯보다 적은 두 바이트가 성공 반환될 수 있으므로 반환 수를 먼저 확인하고 실제 받은 부분만 누적해야 한다.

입력 프레임은 줄바꿈까지 완성되어야 파싱한다고 약속한다. "12"만 받은 시점에는 뒤 숫자나 종료 기호가 아직 없다. 여섯 바이트를 모두 받은 뒤에만 12와 34를 해석하고 합 46을 계산한다. 읽기 버퍼에 남아 있던 이전 값은 새로 수신한 내용의 증거가 아니다. 시스템 호출의 성공·프레임 완성·구문/의미 검사·산술은 차례로 다른 책임이다.

Linux read 계약에서 양수 count를 요청한 바이트 스트림의 0 반환은 끝을 뜻할 수 있지만 count=0의 호출도 0을 반환할 수 있으므로 이를 같은 관찰로 묶지 않는다. 음수 오류 반환을 길이로 사용해서도 안 된다. 여기서는 새 파일·소켓·시스템 호출을 열거나 실행하지 않았으며 손으로 정한 두 반환만 추적한다. 실제 객체별 오류·재시도·수명 조건은 별도 계약이다.

CPU와 OS의 역할을 나누어 보기

하드웨어는 명령 실행, 주소 변환, 보호 검사, 장치와의 상호작용을 위한 기구를 제공한다. 운영체제는 그 기구를 이용해 프로그램에 자원을 제공하고 접근을 관리한다. 일반적인 사용자 프로그램의 덧셈 명령은 사용자 모드에서 CPU가 바로 실행할 수 있다. 모든 산술 명령마다 OS에 허락을 묻는 것은 아니다. 다만 인터럽트·스케줄링 등 때문에 실행 중 OS가 제어를 얻을 수 있다.

사용자 모드와 커널 모드는 하드웨어가 강제하는 권한 수준의 구분이다. 커널 모드에서는 제한된 시스템 자원 관리 명령과 접근을 수행할 수 있지만, 사용자 프로그램은 보호된 자원을 임의로 건드릴 수 없다. 계정의 관리자 권한과 CPU의 커널 모드는 다른 개념이다. 관리자 계정으로 실행한 일반 응용프로그램도 보통 사용자 모드 코드로 시작한다. 세부 권한 수준과 예외는 ISA·OS에 따라 달라진다.

시스템 호출은 통제된 서비스 경계

파일의 자료를 읽는 일을 생각하자. 응용프로그램은 파일과 버퍼를 지정해 요청하고, 시스템 호출 경계를 통해 OS 서비스에 제어를 넘긴다. 커널은 사용자 입력과 권한을 확인하고 파일 시스템·장치 등의 처리를 수행한 뒤 결과나 오류를 돌려준다. 보통 라이브러리가 이 경계를 감싼다. 라이브러리 함수 호출이 전부 시스템 호출인 것은 아니며, 함수가 버퍼에 있는 자료만 처리할 수도 있다.

경계를 넘는다고 요청이 성공하는 것은 아니다. 파일 없음, 접근 거부, 자료 종료 등의 결과를 처리해야 한다. 읽기 요청한 양보다 적은 자료를 받을 수 있다는 점도 인터페이스의 계약에 따라 고려한다. 이 과목 첫 단원에서는 구체적인 Unix 함수 인수나 오류 번호보다 책임 분담을 배운다. API의 정밀 사용은 시스템프로그래밍에서 이어 다룬다.

주소와 파일은 관리되는 추상화

프로그램이 보는 가상 주소는 그 프로세스 주소공간 안의 위치다. 같은 숫자 주소를 서로 다른 프로세스가 사용해도 같은 물리 저장을 뜻하지 않을 수 있다. 하드웨어 주소 변환과 OS가 준비한 매핑·권한이 실제 접근을 결정한다. 가상 주소가 있다고 그곳에 접근할 권한이나 유효한 객체가 자동으로 존재하지는 않는다. 접근 불가 주소를 읽으면 보호 예외가 발생할 수 있다.

파일 이름 역시 디스크의 물리 블록 주소가 아니다. OS와 파일 시스템이 이름·디렉터리·접근 권한을 해석한다. 이 경계는 저장장치의 세부 구조가 달라도 비슷한 인터페이스를 제공한다. 그러나 추상화가 비용과 실패 가능성을 지우지는 않는다. 캐시를 통해 실제 장치 접근 없이 읽기가 끝날 수도 있고, 장치 오류로 실패할 수도 있다. 여기서는 메커니즘을 이해하고 커널 정책의 구현은 운영체제 과목에 남긴다.

오해와 반례

OS가 프로그램을 실행하므로 모든 명령은 OS가 대신 계산한다.

CPU의 덧셈을 두 배 빠르게 만들면 파일을 읽고 결과를 보여 주는 전체 프로그램도 두 배 빨라질까?

준비 개념과 학습 목표

두 작업의 단계 시간을 더하면 전체 경과시간일까?

가상 단일 CPU에서 작업 A는 CPU를 0–2 ms에 쓰고 2–8 ms에 기다린 뒤 8–10 ms에 CPU를 쓴다. 작업 B는 CPU를 2–5 ms에 쓰고 5–8 ms에 기다린 뒤 10–11 ms에 CPU를 쓴다. 두 작업의 대기 구간이 겹치고 B는 8 ms에 준비되어도 A가 10 ms까지 CPU를 사용하므로 기다린다. 각 구간은 설명용 스케줄로 직접 정했다.

A의 시작부터 완료까지 지연은 10 ms, B는 시작 2 ms부터 완료 11 ms까지 9 ms다. 전체 관찰 창은 0–11 ms로 11 ms이며 두 지연을 더한 19 ms가 아니다. A와 B의 CPU 시간은 각각 4 ms, 합도 8 ms다. 전체 창에서 CPU가 일하지 않는 5–8 ms는 3 ms다. 작업별 기다림 합과 전체 CPU 유휴 시간을 같은 지표로 보지 않는다.

Python의 perf_counter 차이는 수면을 포함하는 경과시간에, process_time 차이는 현재 프로세스의 사용자·시스템 CPU 시간 합에 관한 인터페이스다. 실제 여러 프로세스의 시간을 하나의 process_time 호출로 모두 얻는다고 주장하지 않는다. 표를 실제 타이머 출력이나 OS 스케줄 로그로 바꾸지 않으며, 어떤 대기가 I/O 때문인지도 숫자 차이만으로 단정하지 않는다.

빠르다는 말을 측정 가능한 지표로 바꾸기

지연시간은 특정 작업을 시작한 뒤 결과를 받을 때까지 걸린 시간이다. 처리량은 일정 시간 동안 끝낸 작업 수다. 한 작업이 오래 걸려도 여러 작업을 겹쳐 처리하면 처리량이 높을 수 있다. 단일 작업의 지연시간 감소가 서버의 처리량 증가와 같은 의미는 아니다. 무엇을 개선하려는지 먼저 정해야 측정이 답을 준다.

벽시계 시간은 관찰자가 본 경과 시간이고 CPU 시간은 CPU가 실행에 사용한 시간이다. I/O 대기나 다른 작업 때문에 실행을 못 한 시간이 경과 시간에 포함될 수 있다. 여러 코어·스레드의 CPU 시간을 합하면 경과 시간보다 클 수도 있다. 따라서 두 수치를 무조건 같은 값으로 취급하거나 빼서 하나의 원인을 확정하면 안 된다. 어떤 도구의 어떤 범위를 측정했는지도 적는다.

부분 비용의 합과 개선의 한계

서로 겹치지 않는 순차 단계라면 전체 시간 T를 각 단계 시간의 합으로 모델링할 수 있다. T>0, 0≤p≤1, s>0이라 하자. 총 시간 중 비율 p인 부분의 속도를 s배로 바꾸고 다른 부분이 그대로라면 새 시간은 T((1-p)+p/s), 전체 배속은 1/((1-p)+p/s)다. 이 식은 비용의 분할과 고정 조건에서 나온다. 병렬 중첩·입력 변화·새로운 오버헤드가 생기면 이 단순 합 모델을 다시 검토해야 한다.

빠른 CPU가 항상 전체 병목을 없애지 못하는 이유가 여기 있다. 기다림이나 메모리 접근이 큰 부분을 차지하면 산술 연산을 줄이는 효과는 작을 수 있다. 또 알고리즘의 연산 수와 실제 시간은 다른 층위다. 실제 시간에는 각 연산의 비용, 캐시, 컴파일된 명령, 입출력과 실행 환경이 관여한다. 연산 수 분석은 유용하지만 초 단위 성능의 직접 측정값은 아니다.

시간 밖의 비용과 신뢰할 수 있는 비교

프로그램은 메모리, 저장 공간, 네트워크 양, 에너지 같은 자원도 사용한다. 작은 연산을 미리 계산해 저장하면 시간은 줄고 메모리는 늘 수 있다. 자원 사이의 교환을 기록해야 ‘빠르다’는 한 숫자가 숨기는 비용을 볼 수 있다. 여기서는 배열 원소 개수로 논리적 저장량을 세며, 실제 객체의 패딩·할당기 오버헤드·페이지 사용량까지 같은 수치라고 주장하지 않는다.

비교할 때는 입력과 목표를 고정하고 버전·최적화·하드웨어·백그라운드 작업 등 조건을 기록한다. 한 번의 시간은 우연한 잡음일 수 있으므로 여러 번 측정해 대표값과 분포를 함께 본다. 첫 실행의 캐시 준비 비용을 포함할지 제외할지는 질문에 따라 정한다. 빨라 보이는 결과만 골라 내거나 가상 자료를 실제 실행 결과로 적으면 재현 가능한 근거가 아니다.

중간 과정을 따라가는 예제

설명용 순차 작업에서 계산 6ms, I/O 기다림 12ms, 표시 2ms라고 가정한다. 계산만 3배 빨라지고 다른 단계는 동일하다. 중첩은 없다.

  1. 기존 T=6+12+2=20ms.

  2. 계산의 새 시간=6/3=2ms.

  3. 새 T=2+12+2=16ms.

  4. 전체 배속=20/16=1.25. p=6/20=0.3을 식에 넣어도 1/(0.7+0.3/3)=1.25다.

  5. 계산을 0ms로 줄이는 한계에서도 전체는 14ms이고 배속은 20/14=10/7≈1.43이다.

계산은 3배 빠르지만 전체는 1.25배다. 이 수치는 자체 설정한 가상 시간의 검산이며 측정된 성능이 아니다.

종이에 A 방식의 시간 [10,11,9,30,10]ms와 B 방식 [12,12,11,13,12]ms를 적어 평균과 중앙값을 계산하라. 중앙값만으로 B가 항상 더 나쁘다고 말할 수 있는지도 적어라.

힌트 보기

평균은 합/5, 중앙값은 정렬 후 가운데 수다. 큰 지연이 사용자에게 중요한 경우도 생각한다.

풀이 보기

A 합70, 평균14, 정렬[9,10,10,11,30], 중앙값10. B 합60, 평균12, 정렬[11,12,12,12,13], 중앙값12. A는 중앙값이 낮지만 큰 지연30이 있다. 질문이 대표적인 응답인지 큰 지연 방지인지에 따라 평가가 달라진다. 5개 표본만으로 장기 분포를 확정할 수도 없다.

오해와 반례

연산 수를 절반으로 줄이면 실제 실행 시간도 반드시 절반이다.

20ms 중 계산 6ms를 3ms로 줄여도 전체는 17ms다. 남는 I/O·표시 비용 때문이다. 새 방식이 메모리 접근을 늘리면 계산 부분조차 기대만큼 줄지 않을 수 있다. 비용 모델은 전제 아래의 예측이며 실제 성능은 적절한 측정으로 확인해야 한다.

한 단계 더

가상 CPU 모델에서 명령 수 N, 명령당 평균 사이클 수 C, 초당 사이클 수 f를 쓰면 CPU 계산 시간은 N×C/f다. N=1000, C=2, f=10^6이면 0.002초=2ms다. C는 주어진 작업·기계의 평균이라는 가정이며, 벽시계의 대기 시간은 이 식에 들어 있지 않다. 실제 현대 CPU에서 고정 C 하나로 모든 실행을 정밀 예측하지는 못한다.
