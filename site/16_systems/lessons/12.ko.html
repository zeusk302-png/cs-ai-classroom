같은 숫자·다른 숫자의 가상 주소 중 어느 쪽이 같은 바이트인가?

새 종이 모형의 페이지 크기는 64바이트다. P의 VPN 1과 5는 모두 PFN 7로, VPN 2는 PFN 3으로 매핑한다. Q의 VPN 1은 PFN 9다. 여기서 주소는 실제 언어 포인터가 아니라 공간 이름과 함께 기록하는 비음수 바이트 번호다. P의 서로 다른 가상 주소가 같은 물리 바이트에 연결될 수 있고 P와 Q의 같은 숫자는 다른 바이트일 수 있다.

P의 주소 124에서 8바이트를 읽으면 첫 페이지의 offset 60–63 뒤 다음 페이지의 offset 0–3으로 넘어간다. 번역은 페이지별로 반복해야 한다. 첫 물리 주소에 0부터 7을 더하면 다른 프레임 배치를 지워 버린다. 권한·매핑 존재와 언어 객체의 유효성도 별도의 조건이다.

P에 512바이트의 가상 영역이 있다고 정해도 여덟 전용 물리 프레임이 설치된 것은 아니다. 이 모형에서는 그 영역의 VPN 1, 2, 5만 현재 resident이고 나머지는 미설치다. 설치된 가상 페이지는 세 개지만 서로 다른 물리 프레임은 두 개다. 이를 프로세스 전체 RSS나 실제 OS 과금 규칙과 동일시하지 않는다.

프로그램은 자기 주소 공간에서 계산한다

프로그램이 배열 요소를 가리키는 포인터는 보통 그 프로세스의 가상 주소다. OS와 하드웨어가 현재 매핑에 따라 물리 메모리를 연결한다. C 언어 포인터의 출력 숫자를 곧바로 RAM 칩의 위치라고 읽지 않는다. 동일 숫자가 다른 프로세스에서도 출력되어도 같은 데이터를 공유한다는 증거는 아니다.

이 절의 예제는 바이트 주소, 4바이트 정수, 256바이트 페이지를 사용한 작은 종이 모델이다. 실제 sizeof(int), 페이지 크기, 할당기와 언어의 배열 표현은 환경에 따라 확인한다. Python 정수 리스트는 원소의 정수 데이터가 4바이트씩 연속 배치된 C 배열과 같은 표현이 아니다.

가상 연속성은 매핑 뒤에도 같은 간격을 보장하지 않는다

배열의 첫 요소 주소를 base, 요소 크기를 w라 하면 a[i]의 첫 바이트는 base+i×w다. 이 계산은 배열 범위와 유효한 포인터라는 전제 아래 가상 주소를 계산한다. 페이지 경계를 넘으면 새 VPN을 매핑하므로 물리 주소 사이의 차이는 w가 아닐 수 있다.

기본 페이지에서는 VPN=VA//page_size, offset=VA%page_size다. 표가 VPN→PFN을 제공하면 PA=PFN×page_size+offset이다. 공유 프레임에 매핑하면 서로 다른 가상 주소도 같은 바이트를 볼 수 있다. 프로그램의 데이터 공유 여부는 포인터 숫자보다 매핑·권한·동기화 약속으로 판단한다.

예약한 영역과 실제 상주량은 다르다

프로세스가 큰 가상 영역을 확보해도 그 모든 바이트가 즉시 별도 물리 프레임으로 채워진다는 뜻은 아니다. 지연 할당, 파일 매핑, 공유 페이지나 아직 접근하지 않은 영역이 있을 수 있다. 반대로 페이지 표와 런타임·스택도 자원을 쓰므로 사용자가 요청한 배열 크기만으로 프로세스 전체 RAM을 계산하지 않는다.

Linux의 익명 매핑은 먼저 접근 가능한 영역을 정의하고 읽기에서 공유 zero page, 쓰기에서 실제 페이지를 만드는 경우가 있다. 이는 OS 정책의 사례이며 모든 플랫폼·상황에서 같은 순서로 할당된다는 보장은 아니다. 주소 공간이 크다는 사실은 메모리 부족이 불가능하다는 보장도 아니다.

중간 과정을 따라가는 예제

256바이트 페이지 모델에서 4바이트 정수 배열의 base=250이다. VPN0→PFN5, VPN1→PFN2다. a[0],a[1],a[2]의 첫 바이트 주소를 구하고 a[1]의 네 바이트가 어느 페이지에 있는지 확인하라.

  1. 첫 가상 주소는 250,254,258이다. 각각 (VPN,offset)은 (0,250),(0,254),(1,2)다.

  2. 첫 물리 주소는 5×256+250=1530, 5×256+254=1534, 2×256+2=514다. 가상 연속 정수 첫 주소가 물리적으로 같은 증가 간격을 유지하지 않는다.

  3. a[1]의 가상 바이트 254,255는 VPN0이라 물리 1534,1535이고 256,257은 VPN1이라 물리 512,513이다. 첫 바이트 번역만으로 나머지를 더하는 것은 틀리다.

  4. 이 모델은 경계·매핑을 분석하는 용도다. 실제 CPU가 비정렬 int 접근을 허용하는지, 몇 접근으로 나누는지와 예외는 별도 규칙이다.

첫 바이트 PA는 1530,1534,514다. a[1]의 네 바이트는 두 페이지에 걸쳐 물리 1534,1535,512,513으로 이어진다.

비교할 점

다른 주소의 공유와 같은 주소의 분리

P의 VA 124, P의 VA 380, Q의 VA 124가 같은 바이트를 가리키는지 판정하고 설치 공간을 구하라.

  1. P의 두 주소는 모두 PFN 7의 offset 60에 대응한다. Q의 주소는 PFN 9의 offset 60에 대응한다.

  2. P의 resident VPN은 세 개지만 서로 다른 PFN은 7과 3의 두 개다.

P 두 주소는 같은 모형 바이트이고 Q는 다르다. resident 가상 범위는 192바이트, 서로 다른 물리 데이터 프레임은 128바이트다.

비교할 점

페이지 표·런타임·OS 카운터 비용을 포함한 측정값은 아니다.

풀이 보기

연습 1 · 값과 상태 예측

P의 381과 Q의 125를 번역하라.

힌트 1

각 주소를 64로 나눈다.

힌트 2

P의 VPN 5와 Q의 VPN 1 매핑을 사용한다.

풀이와 답 확인

  1. P의 VA 381은 offset 61에 대응하므로 PA는 7×64+61=509다.

  2. Q의 VA 125도 offset 61에 대응하지만 PA는 9×64+61=637이다.

PA는 각각 509와 637이다.

흔한 오답에서 다시 생각하기

VA 차이가 작으면 공간과 상관없이 PA도 같다.

주소 공간의 페이지 표가 다르다.

연습 2 · 오류 찾아 고치기

P의 예약 512바이트가 즉시 전용 RAM 512바이트라고 보고했다. 고쳐라.

힌트 1

예약 페이지 수와 설치 VPN 수를 분리한다.

힌트 2

VPN 1과 5는 PFN 7을 공유한다.

풀이와 답 확인

  1. 예약 범위는 8페이지이고 설치된 VPN은 세 개다.

  2. 고유 데이터 PFN은 두 개다.

예약 범위는 512바이트, 설치된 가상 페이지 범위는 192바이트, 고유 물리 데이터는 128바이트로 각각 적는다. 실제 전체 RSS는 미측정이다.

흔한 오답에서 다시 생각하기

고유 PFN 수가 곧 OS의 모든 메모리 과금이다.

별도의 페이지 표와 공유 계상 정책이 남는다.

연습 3 · 직접 만들어 보기

P의 VA 124와 같은 바이트를 보는 다른 P의 주소를 만들고 양쪽 권한을 따로 검토하라.

힌트 1

VPN 5도 PFN 7에 대응한다.

힌트 2

같은 offset 60을 택한다.

풀이와 답 확인

  1. 5×64+60=380이다.

  2. 같은 PFN이어도 각 매핑의 쓰기 허용은 별도 설정일 수 있다.

P의 VA 380이 증인이다. 공유 주소가 있다고 두 매핑의 권한도 같다는 결론은 안 된다.

흔한 오답에서 다시 생각하기

같은 물리 바이트면 모든 가상 경로에서 쓰기 가능하다.

접근 권한은 해당 번역 경로에서 검사한다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

시작 s≥0·길이 n>0인 연속 범위가 만지는 64바이트 페이지 수를 식으로 쓰고 n=0을 구별하라.

힌트 1

마지막 포함 주소는 s+n−1이다.

힌트 2

첫·끝 페이지 번호 차이에 1을 더한다.

풀이와 답 확인

  1. 양의 n에서 floor((s+n−1)/64)−floor(s/64)+1이다.

  2. n=0은 읽는 바이트가 없어 0페이지로 별도 정의한다.

s=124, n=8이면 두 페이지다. 빈 범위에 마지막 포함 주소를 억지로 정의하지 않는다.

흔한 오답에서 다시 생각하기

언제나 ceil(n/64)만 쓰면 된다.

시작 offset 때문에 같은 길이도 경계를 더 넘을 수 있다.

  • TLB 미스 수를 측정 결과와 구별하여 추적한다.

TLB에서 주소 공간을 지우면 hit가 오히려 잘못된 번역인가?

새 두 항목 완전연관 LRU TLB는 (ASID, VPN)를 키로 한다. P와 Q의 ASID는 각각 1과 2이며 둘 다 VPN 1을 읽지만 PFN은 7과 9다. 처음 비어 있고 같은 공간의 매핑·권한은 추적 동안 바뀌지 않는다. P, Q, P, Q의 네 요청에서 두 번의 cold miss 뒤 두 hit가 가능하다.

VPN만 키로 남기고 P의 번역을 Q에 재사용하면 높은 hit 수가 올바른 실행을 의미하지 않는다. 주소 공간 구분을 지원하지 않는 별도 모형에서는 매 전환에 이전 항목을 invalid로 만들면 번역 오류를 막지만 네 번 모두 miss다. ASID의 실제 재사용·무효화 정책이나 현대 CPU 전체 동작을 이 네 사건으로 증명하지 않는다.

페이지 수에도 시작 정렬이 들어간다. 4바이트 원소 128개의 새 연속 모형은 512바이트다. 페이지 크기 256에서 시작 0이면 두 페이지지만 시작 252이면 마지막 포함 바이트 763이라 세 페이지다. 같은 원소 수와 같은 전체 길이가 동일한 번역 작업 집합을 보장하지 않는다.

많은 이웃 원소가 한 번역을 공유한다

페이지 크기 4096바이트, 원소 4바이트, 시작점이 페이지 경계에 맞는 배열이면 한 페이지에 1024개가 들어간다. 연속 요소는 같은 VPN 번역을 재사용할 수 있다. 첫 위치가 경계에 맞지 않거나 요소가 경계를 넘으면 페이지 수 계산이 달라진다. 언어의 객체가 실제로 연속인지도 확인한다.

TLB는 최근 가상 페이지의 번역을 담는다. 프로그램이 한동안 만지는 페이지 집합을 번역 working set 관점에서 볼 수 있다. 작은 범위를 반복하거나 근처 요소를 함께 쓰면 번역 지역성이 생긴다. 코드·스택·다른 자료의 접근도 실제 실행에서는 함께 TLB를 사용한다.

용량보다 많은 페이지를 돌면 교체가 반복될 수 있다

두 항목 완전 연관 LRU TLB에서 세 페이지 A,B,C를 반복하면 세 번째 페이지를 넣을 때 가장 오래된 것을 내보낸다. 다음 회전에서 필요한 항목이 다시 없어져 miss가 반복될 수 있다. 모든 TLB가 LRU이거나 같은 구조라는 주장은 아니며 교체 모델을 적어야 결과를 재현할 수 있다.

miss는 번역 캐시에 없음이다. 표가 유효하고 접근 가능한 페이지로 연결하면 추가 순회 뒤 성공한다. 데이터 캐시의 miss나 페이지 fault, 파일 I/O 횟수와 일대일 관계가 아니다. 실제 성능은 겹치는 순회·하드웨어 prefetch·큰 페이지·CPU 등의 영향도 받아 종이 카운트만으로 시간 배수를 주장하지 않는다.

큰 페이지도 조건과 비용이 있다

큰 페이지는 같은 번역 항목 하나가 더 넓은 범위를 덮도록 하여 TLB 압박을 줄일 수 있다. 그러나 사용하지 않는 공간의 낭비, 물리 메모리 확보·정렬과 OS 정책을 고려한다. Linux HugeTLB와 THP는 서로 다른 사용·관리 방법이다. 프로그램에서 배열이 크다는 사실만으로 큰 페이지가 반드시 적용되지는 않는다.

한 번역으로 덮는 바이트 수를 reach라고 할 때 단순 모델의 항목수×페이지크기는 최대 포괄 범위의 직관이다. 연관성 제한과 다른 주소 공간·페이지 크기의 혼합을 생략한 계산이다. 숫자만 보고 실제 프로그램의 모든 접근이 hit임을 보장하지 않는다.

중간 과정을 따라가는 예제

비어 있는 두 항목 완전 연관 LRU TLB와 성공하는 페이지 표에서 페이지열 A,B,C,A,B,C를 추적한다. 같은 여섯 접근을 A,A,B,B,C,C로 묶으면 어떠한가?

  1. 첫 열은 A,B miss로 채워지고 C가 A를 내보낸다. 다음 A가 B를, B가 C를, C가 A를 내보내므로 여섯 번 모두 miss다.

  2. 두 번째 열은 A miss/A hit, B miss/B hit, C miss/C hit로 세 miss와 세 hit다.

  3. 두 열의 서로 다른 페이지 수는 3으로 같다. 접근 순서와 재사용 시점이 hit 수를 바꾼다. 각 표의 매핑이 정상이라는 가정에서 두 열 모두 page fault 수는 0이다.

  4. 결과는 LRU 종이 모델이다. 두 번째 프로그램이 실제로 두 배 빠르다고 측정한 결과가 아니다.

ABCABC는 miss 6/hit 0, AABBCC는 miss 3/hit 3이다. 페이지 집합이 같아도 순서가 번역 재사용을 바꾼다.

같은 배열 길이의 다른 페이지 수

4바이트 원소 128개를 페이지 크기 256바이트에서 배치한다. 시작 주소가 0인 경우와 252인 경우를 비교하라.

  1. 시작 주소가 0이면 포함 주소는 0–511이고 VPN은 0과 1이다.

  2. 시작 주소가 252이면 포함 주소는 252–763이고 VPN은 0, 1, 2다.

각각 두 페이지와 세 페이지다. 뒤 배치의 원소 수는 페이지별로 1개, 64개, 63개다.

힌트 보기

정렬된 매핑 기준과 사용자가 원하는 파일 범위를 어떻게 연결하는가?

새 요청은 길이 5000바이트인 파일의 offset 4103부터 10바이트를 읽는 것이다. 매핑 offset의 정렬 단위를 가상 계약 G=4096으로 정하면 기준은 floor(4103/G)×G=4096이다. 원하는 첫 바이트까지 차이는 δ=7이므로 매핑 길이를 17바이트로 정하고 인덱스 7부터 16까지 읽는다. 전체 매핑 길이와 원하는 데이터 길이는 다르다.

가상 base를 0x60000으로 정하면 사용자의 i번째 바이트는 VA=base+7+i, 파일 offset=4096+7+i=4103+i다. 실제 Python mmap의 offset은 ALLOCATIONGRANULARITY의 배수여야 하며 Unix에서는 이 단위가 PAGESIZE와 같다. 여기의 4096이나 base는 실제 환경에서 조회하거나 호출한 값이 아니다.

파일 내용의 캐시 존재·PTE 설치·쓰기 권한·COW는 별도 상태다. 이미 캐시에 있는 파일 페이지를 새로 설치하는 fault는 새로운 디스크 읽기 없이 처리할 수 있다. READ의 쓰기 거절을 “아직 읽지 않아서 생긴 fault”처럼 기다리기만 하면 해결한다고 해석하지 않는다. COPY의 자기 변경은 underlying file을 갱신하지 않지만 모든 외부 변경에서 영원한 snapshot을 보장한다는 뜻도 아니다.

fault는 실패 알림이면서 복구의 출발점일 수 있다

page fault는 CPU가 정상 번역·권한 경로로 접근을 끝내지 못해 OS에 판단을 넘기는 사건이다. 아직 준비되지 않은 합법적 페이지나 COW 쓰기는 복구할 수 있고, 금지 영역 접근은 거부할 수 있다. 페이지가 backing storage에 있을 때는 읽기 I/O가 필요할 수 있지만 모든 fault가 디스크 대기는 아니다.

Linux의 익명 zero page나 이미 page cache에 있는 파일 내용으로 매핑을 준비하면 저장장치 읽기 없이도 처리할 수 있다. TLB miss는 번역 캐시의 miss로 더 좁은 사건이다. 운영체제의 minor/major 같은 카운터 정의도 따로 확인해야 하며 서로 다른 용어의 수치를 합쳐 하나의 “메모리 오류”로 보고하지 않는다.

파일의 범위에 프로그램의 주소 범위를 연결한다

파일 매핑은 파일의 특정 바이트 범위를 프로세스 가상 영역으로 연결한다. mmap 객체의 인덱스 0은 파일 시작 0이 아니라 매핑에 정한 파일 오프셋에 대응한다. 파일 오프셋이 8192이고 인덱스 123을 읽으면 파일 바이트 8315를 대상으로 한다. 매핑 생성 시 오프셋 정렬 제한과 파일·매핑 길이를 확인해야 한다.

Python 공식 mmap 문서는 Unix와 Windows 생성자 차이를 설명한다. Windows의 ALLOCATIONGRANULARITY와 페이지 크기를 같은 값이라고 가정하지 않는다. mmap의 offset = 8192는 아래 가상 모형의 4 KiB 정렬 약속에서는 맞지만 실제 플랫폼에서 무조건 유효한 호출이라는 뜻은 아니다. 범위 밖 접근·파일 축소·닫힌 매핑 등의 오류도 API 규칙으로 처리한다.

매핑 접근 권한과 파일 반영은 따로 약속한다

Python ACCESS_READ 매핑에는 쓰기를 허용하지 않는다. ACCESS_WRITE는 매핑을 통해 바꾼 내용을 underlying file에 반영하는 접근 방식이고 ACCESS_COPY는 그 변경을 파일에 쓰지 않는다. 일반적인 Unix shared/private 관계를 이해하되 플랫폼 API의 정확한 약속을 확인한다.

파일이 바뀌어 보인다는 사실과 충돌 없이 여러 실행자가 공유한다는 사실은 다르다. 공유 데이터에는 동기화가 필요하며, flush의 의미와 운영체제·장치의 지속성 조건도 따로 다룬다. mmap이 언제나 read보다 빠르거나 전체 파일을 즉시 전용 RAM에 복사한다는 보장은 없다. 객체와 파일을 각각 닫아 수명을 관리한다.

중간 과정을 따라가는 예제

종이 모형에서 4 KiB 페이지, 파일 오프셋 8192, 매핑 길이 8192, 가상 base 0x40000을 정한다. 매핑 인덱스 5000을 읽는 가상 주소·파일 위치·매핑 내부 페이지를 구하라. 매핑 내부 두 번째 페이지는 아직 설치되지 않았지만 파일 내용은 OS 캐시에 있다.

  1. 가상 주소는 262144 + 5000 = 267144 = 0x41388이다. 파일 바이트는 8192 + 5000 = 13192다.

  2. 5000 = 1 × 4096 + 904이므로 매핑 내부 페이지 1, 오프셋 904다. 전체 VA의 VPN은 65, 오프셋은 904이며 내부 페이지 번호 1과 구별한다.

  3. 아직 PTE가 준비되지 않아 fault를 받아 OS가 기존 캐시의 파일 페이지를 매핑할 수 있다. 이 가정에서는 새 저장장치 읽기를 요구하지 않는다.

  4. 추가로 ACCESS_COPY 방식의 가상 매핑에서 그 위치에 20을 썼다고 하면 매핑에서 보는 값은 바뀌어도 파일을 20으로 갱신하는 약속은 없다. 실제 mmap을 실행한 사례가 아니다.

VA 0x41388, 파일 바이트 13192, 매핑 내부 페이지 1과 오프셋 904다. 이 가정의 fault는 새 파일 I/O 없이도 복구할 수 있다.

조건을 바꾸어 비교하기

원하는 마지막 바이트를 복원하기

G=4096에서 요청 첫 바이트와 끝 바이트의 파일 위치 및 mmap 내부 인덱스를 구하라.

  1. 기준 4096에서 요청의 첫 위치 4103까지 차이는 δ=7이다.

  2. 마지막 파일 위치는 4103+9=4112이고 기준과의 차이는 16이다.

인덱스 7–16이 파일 위치 4103–4112에 해당한다. 인덱스 0–9를 읽으면 파일 위치 4096–4105를 읽으므로 요청과 다르다.

비교할 점

매핑 인덱스 0과 사용자가 요청한 첫 바이트를 구별한다.

캐시 설치와 사본 쓰기

값이 8인 파일 바이트가 캐시에 있고 P와 Q가 COPY로 같은 파일 범위를 본다. 추적 중 다른 파일 변경은 없고 P만 자기 사본에 20을 쓴다.

  1. PTE 미설치인 첫 합법 읽기는 기존 캐시를 연결해 복구할 수 있다.

  2. P의 자기 COPY 쓰기는 underlying file을 갱신하지 않는다.

이 고정 모형에서 P가 보는 값은 20이고 Q와 파일의 값은 8이다. 실제 동시 API·외부 파일 수정·snapshot 격리를 시험한 결과는 아니다.

P의 VA 124부터 8바이트 및 P의 VA 380과 Q의 VA 124를 번역하라. 정상 PTE와 두 항목 TLB에서 요청 P, Q, P, Q를 ASID 보존 방식과 전환 때 전부 무효화하는 방식으로 비교하라. 별도의 페이지 크기 256바이트 모형에서 4바이트 원소 128개인 배열의 시작 주소가 0인 경우와 252인 경우의 페이지 수를 구하라. 파일 offset 4103부터 10바이트를 읽는 요청을 G=4096, 가상 base=0x60000인 매핑으로 구성하고 마지막 바이트의 내부 인덱스·VA·파일 위치를 복원하라.

힌트 1

페이지 경계마다 매핑을 바꾸고 TLB 키에는 주소 공간 이름을 보존한다. 배열 마지막 포함 바이트는 시작+512−1이다.

힌트 2

파일 기준을 4096으로 내린 차이 7을 매핑 길이와 사용 인덱스 양쪽에 넣는다.

풀이와 답 확인

  1. P의 VA 124–131은 PA 508–511 다음 PA 192–195로 번역된다. P의 VA 380은 PA 508이고 Q의 VA 124는 PA 636이다.

  2. ASID 보존 방식은 miss 두 번과 hit 두 번이다. 전환 무효화 방식은 miss 네 번이다. 정상 PTE 가정에서 두 경우의 page fault는 모두 0이다.

  3. 배열의 시작 주소가 0이면 주소 0–511의 두 페이지다. 시작 주소가 252이면 주소 252–763의 세 페이지다.

  4. 파일 기준은 4096, 차이는 δ=7, 매핑 길이는 17바이트, 요청 인덱스는 7–16이다. 마지막 바이트의 VA는 0x60010이고 파일 위치는 4112다.

가상 연속성과 물리 연속성·올바른 hit와 공간을 잃은 hit·요청 길이와 매핑 길이를 분리한다. 모든 수치는 자체 고정 모형의 손계산이며 실제 포인터 접근·TLB/OS 측정·mmap 파일 변경·학생 실험은 미수행이다.

해결한 뒤 점검할 것

  • 경계 양쪽 번역과 별칭/공간 차이를 설명한다.

  • ASID와 valid 처리·TLB miss/page fault 분모를 나눈다.

  • 시작 offset을 포함한 페이지 범위를 계산한다.

  • 정렬 기준·δ·길이·파일 위치를 복원하고 실제 실행의 한계를 명시한다.

  • Python — mmap

    실제 현재 Python3.15 문서8–40행의 ACCESS/Windows·Unix offset/ALLOCATIONGRANULARITY와93–121행 close/flush를 읽었다. 새trackfd/flush변화를 실제 설치 버전으로 주장하지 않으며 자체 정렬 요청과COPY 사례는 API 미실행이다.

전체 base와 새 모형을 손검산했다. 페이지 크기 64바이트에서 네 PA는 순서대로 508, 192, 508, 636이다. P의 8바이트 범위는 PA 508–511 다음 PA 192–195에 대응한다. 예약 범위는 512바이트, resident 가상 범위는 192바이트, 고유 데이터는 128바이트다. 두 공간의 TLB에서 ASID 보존 방식의 miss 두 번과 hit 두 번, 전환 무효화 방식의 miss 네 번 및 정상 PTE에서 fault 0을 확인했다. 4바이트 원소 128개의 시작 주소가 0이면 두 페이지, 252이면 세 페이지다. 뒤 배치의 원소 수는 페이지별로 1개, 64개, 63개다. G=4096인 정렬에서 기준은 4096, 차이는 δ=7, 매핑 길이는 17바이트, 끝 인덱스는 16, 마지막 VA는 0x60010, 파일 위치는 4112다. 가상 G=65536이면 기준은 0, 차이는 δ=4103, 매핑 길이는 4113바이트다. COPY의 고정 모형에서 자기 변경 뒤 P의 값은 20이고 파일과 Q의 값은 8이다. 전체 전이의 조건을 손추적했다.
