소단원 12.1

가상·물리 주소 구분

프로그램의 배열이 연속이라면 실제 RAM도 같은 순서로 붙어 있을까?

준비 개념과 학습 목표

준비 개념

  • 배열의 바이트 주소

  • 페이지 번호

  • 몫과 나머지

학습 목표

  • 프로그램 포인터의 주소 공간을 명시한다.

  • 배열 주소를 페이지와 오프셋으로 나눈다.

  • 가상 영역의 크기와 상주 RAM 양을 구별한다.

프로그램은 자기 주소 공간에서 계산한다

프로그램이 배열 요소를 가리키는 포인터는 보통 그 프로세스의 가상 주소다. OS와 하드웨어가 현재 매핑에 따라 물리 메모리를 연결한다. C 언어 포인터의 출력 숫자를 곧바로 RAM 칩의 위치라고 읽지 않는다. 동일 숫자가 다른 프로세스에서도 출력되어도 같은 데이터를 공유한다는 증거는 아니다.

이 절의 예제는 바이트 주소, 4바이트 정수, 256바이트 페이지를 사용한 작은 종이 모델이다. 실제 sizeof(int), 페이지 크기, 할당기와 언어의 배열 표현은 환경에 따라 확인한다. Python 정수 리스트는 원소의 정수 데이터가 4바이트씩 연속 배치된 C 배열과 같은 표현이 아니다.

가상 연속성은 매핑 뒤에도 같은 간격을 보장하지 않는다

배열의 첫 요소 주소를 base, 요소 크기를 w라 하면 a[i]의 첫 바이트는 base+i×w다. 이 계산은 배열 범위와 유효한 포인터라는 전제 아래 가상 주소를 계산한다. 페이지 경계를 넘으면 새 VPN을 매핑하므로 물리 주소 사이의 차이는 w가 아닐 수 있다.

기본 페이지에서는 VPN=VA//page_size, offset=VA%page_size다. 표가 VPN→PFN을 제공하면 PA=PFN×page_size+offset이다. 공유 프레임에 매핑하면 서로 다른 가상 주소도 같은 바이트를 볼 수 있다. 프로그램의 데이터 공유 여부는 포인터 숫자보다 매핑·권한·동기화 약속으로 판단한다.

예약한 영역과 실제 상주량은 다르다

프로세스가 큰 가상 영역을 확보해도 그 모든 바이트가 즉시 별도 물리 프레임으로 채워진다는 뜻은 아니다. 지연 할당, 파일 매핑, 공유 페이지나 아직 접근하지 않은 영역이 있을 수 있다. 반대로 페이지 표와 런타임·스택도 자원을 쓰므로 사용자가 요청한 배열 크기만으로 프로세스 전체 RAM을 계산하지 않는다.

Linux의 익명 매핑은 먼저 접근 가능한 영역을 정의하고 읽기에서 공유 zero page, 쓰기에서 실제 페이지를 만드는 경우가 있다. 이는 OS 정책의 사례이며 모든 플랫폼·상황에서 같은 순서로 할당된다는 보장은 아니다. 주소 공간이 크다는 사실은 메모리 부족이 불가능하다는 보장도 아니다.

중간 과정을 따라가는 예제

256바이트 페이지 모델에서 4바이트 정수 배열의 base=250이다. VPN0→PFN5, VPN1→PFN2다. a[0],a[1],a[2]의 첫 바이트 주소를 구하고 a[1]의 네 바이트가 어느 페이지에 있는지 확인하라.

  1. 첫 가상 주소는 250,254,258이다. 각각 (VPN,offset)은 (0,250),(0,254),(1,2)다.

  2. 첫 물리 주소는 5×256+250=1530, 5×256+254=1534, 2×256+2=514다. 가상 연속 정수 첫 주소가 물리적으로 같은 증가 간격을 유지하지 않는다.

  3. a[1]의 가상 바이트 254,255는 VPN0이라 물리 1534,1535이고 256,257은 VPN1이라 물리 512,513이다. 첫 바이트 번역만으로 나머지를 더하는 것은 틀리다.

  4. 이 모델은 경계·매핑을 분석하는 용도다. 실제 CPU가 비정렬 int 접근을 허용하는지, 몇 접근으로 나누는지와 예외는 별도 규칙이다.

첫 바이트 PA는 1530,1534,514다. a[1]의 네 바이트는 두 페이지에 걸쳐 물리 1534,1535,512,513으로 이어진다.

종이와 본문으로 직접 해보기

같은 모델에서 다른 프로세스 Q의 VPN0→PFN8이라고 하자. 가상 250의 물리 주소는? P,Q의 같은 가상 주소가 곧 공유 증거인가?

힌트 보기

페이지 크기 256과 오프셋 250을 유지한다.

풀이 보기

Q의 PA는 8×256+250=2298이다. P의 1530과 다르므로 같은 가상 250만으로 공유를 결론낼 수 없다. 두 공간이 같은 프레임을 매핑했다는 정보가 필요하다.

오해와 반례

배열을 n바이트 요청하면 n바이트가 즉시 전용 RAM으로 상주한다.

가상 영역 확보·물리 할당·접근·상주·공유는 구별된다. 지연 익명 매핑이나 파일 매핑은 먼저 영역을 만들고 나중에 페이지를 준비할 수 있으며 부가 자원도 따로 쓴다.

자기점검

base = 250, w = 4에서 a[2]의 가상 주소는?

답과 이유 보기

258이다.

250 + 2 × 4로 계산한다.

가상 주소 258은 256바이트 페이지에서 오프셋 얼마인가?

답과 이유 보기

2다.

258 = 1 × 256 + 2다.

물리 1534에 네 바이트를 더해 a[1] 전체를 읽는 계산이 맞는가?

답과 이유 보기

현재 매핑에서는 틀리다.

두 번째 가상 페이지가 다른 PFN으로 매핑되어 물리 512로 옮겨간다.

한 단계 더

주소 접근 범위가 경계를 넘으면 양쪽 페이지의 존재와 권한을 확인하자. 배열 index와 포인터가 언어 규칙상 허용되지 않는 경우에는 MMU 변환을 계산할 수 있다는 사실로 프로그램의 정의된 동작을 보장하지 못한다.

소단원 12.2

페이지와 TLB

같은 원소 수를 읽어도 페이지마다 한 번씩 건너뛰면 번역 작업이 더 많아질까?

준비 개념과 학습 목표

준비 개념

  • 페이지 크기

  • 배열 주소 계산

  • 캐시와 LRU

학습 목표

  • 한 페이지가 담는 원소 수를 계산한다.

  • 접근 순서와 번역 working set을 구별한다.

  • TLB 미스 수를 측정 결과와 구별하여 추적한다.

많은 이웃 원소가 한 번역을 공유한다

페이지 크기 4096바이트, 원소 4바이트, 시작점이 페이지 경계에 맞는 배열이면 한 페이지에 1024개가 들어간다. 연속 요소는 같은 VPN 번역을 재사용할 수 있다. 첫 위치가 경계에 맞지 않거나 요소가 경계를 넘으면 페이지 수 계산이 달라진다. 언어의 객체가 실제로 연속인지도 확인한다.

TLB는 최근 가상 페이지의 번역을 담는다. 프로그램이 한동안 만지는 페이지 집합을 번역 working set 관점에서 볼 수 있다. 작은 범위를 반복하거나 근처 요소를 함께 쓰면 번역 지역성이 생긴다. 코드·스택·다른 자료의 접근도 실제 실행에서는 함께 TLB를 사용한다.

용량보다 많은 페이지를 돌면 교체가 반복될 수 있다

두 항목 완전 연관 LRU TLB에서 세 페이지 A,B,C를 반복하면 세 번째 페이지를 넣을 때 가장 오래된 것을 내보낸다. 다음 회전에서 필요한 항목이 다시 없어져 miss가 반복될 수 있다. 모든 TLB가 LRU이거나 같은 구조라는 주장은 아니며 교체 모델을 적어야 결과를 재현할 수 있다.

miss는 번역 캐시에 없음이다. 표가 유효하고 접근 가능한 페이지로 연결하면 추가 순회 뒤 성공한다. 데이터 캐시의 miss나 페이지 fault, 파일 I/O 횟수와 일대일 관계가 아니다. 실제 성능은 겹치는 순회·하드웨어 prefetch·큰 페이지·CPU 등의 영향도 받아 종이 카운트만으로 시간 배수를 주장하지 않는다.

큰 페이지도 조건과 비용이 있다

큰 페이지는 같은 번역 항목 하나가 더 넓은 범위를 덮도록 하여 TLB 압박을 줄일 수 있다. 그러나 사용하지 않는 공간의 낭비, 물리 메모리 확보·정렬과 OS 정책을 고려한다. Linux HugeTLB와 THP는 서로 다른 사용·관리 방법이다. 프로그램에서 배열이 크다는 사실만으로 큰 페이지가 반드시 적용되지는 않는다.

한 번역으로 덮는 바이트 수를 reach라고 할 때 단순 모델의 항목수×페이지크기는 최대 포괄 범위의 직관이다. 연관성 제한과 다른 주소 공간·페이지 크기의 혼합을 생략한 계산이다. 숫자만 보고 실제 프로그램의 모든 접근이 hit임을 보장하지 않는다.

중간 과정을 따라가는 예제

비어 있는 두 항목 완전 연관 LRU TLB와 성공하는 페이지 표에서 페이지열 A,B,C,A,B,C를 추적한다. 같은 여섯 접근을 A,A,B,B,C,C로 묶으면 어떠한가?

  1. 첫 열은 A,B miss로 채워지고 C가 A를 내보낸다. 다음 A가 B를, B가 C를, C가 A를 내보내므로 여섯 번 모두 miss다.

  2. 두 번째 열은 A miss/A hit, B miss/B hit, C miss/C hit로 세 miss와 세 hit다.

  3. 두 열의 서로 다른 페이지 수는 3으로 같다. 접근 순서와 재사용 시점이 hit 수를 바꾼다. 각 표의 매핑이 정상이라는 가정에서 두 열 모두 page fault 수는 0이다.

  4. 결과는 LRU 종이 모델이다. 두 번째 프로그램이 실제로 두 배 빠르다고 측정한 결과가 아니다.

ABCABC는 miss 6/hit 0, AABBCC는 miss 3/hit 3이다. 페이지 집합이 같아도 순서가 번역 재사용을 바꾼다.

종이와 본문으로 직접 해보기

시작점이 페이지 경계인 4바이트 배열의 원소 2048개가 차지하는 바이트와 4 KiB 페이지 수를 구하라. 같은 시작점에서 한 페이지 간격으로 인덱스 0과 1024를 읽으면 VPN이 같은가?

힌트 보기

2048 × 4를 계산하고 1024 × 4만큼의 주소 차이를 확인한다.

풀이 보기

총 8192바이트, 즉 8 KiB로 두 페이지다. 인덱스 0과 1024의 주소 차이는 4096바이트이므로 서로 이웃한 다른 VPN이다. 다음 원소를 읽는 연속 간격 4바이트와 구별한다.

오해와 반례

페이지 수가 같으면 접근 순서와 상관없이 TLB miss 수도 같다.

같은 세 페이지의 ABCABC와 AABBCC가 두 항목 LRU에서 각각 miss 여섯 번과 세 번을 만든다. 시간 지역성, 용량과 교체 규칙을 함께 봐야 한다.

자기점검

4096바이트에 4바이트 원소는 몇 개 들어가는가?

답과 이유 보기

경계 정렬·연속 모델에서 1024개다.

4096/4이며 시작점·표현 조건이 중요하다.

두 항목 LRU에서 A,B,A,C 다음 B는 hit인가?

답과 이유 보기

miss다.

C를 넣을 때 최근 다시 쓴 A가 아닌 B를 내보낸다.

TLB 64항목과 4 KiB 페이지의 단순 reach는?

답과 이유 보기

256 KiB다.

64 × 4096 = 262144바이트이며 실제 적중 보장은 아니다.

한 단계 더

행렬 순회에서 행 우선 저장과 열 우선 순회의 주소 간격을 계산해 보자. Python 중첩 리스트와 C의 고정 크기 연속 배열은 같은 메모리 모델이 아니므로 실제 표현과 페이지 크기를 먼저 고정한다. 직접 측정할 때는 TLB 카운터와 page fault 카운터를 별도로 기록한다.

페이지 폴트와 메모리 매핑

  • 읽기 전용·쓰기 반영·private copy의 약속을 구별한다.

fault는 실패 알림이면서 복구의 출발점일 수 있다

page fault는 CPU가 정상 번역·권한 경로로 접근을 끝내지 못해 OS에 판단을 넘기는 사건이다. 아직 준비되지 않은 합법적 페이지나 COW 쓰기는 복구할 수 있고, 금지 영역 접근은 거부할 수 있다. 페이지가 backing storage에 있을 때는 읽기 I/O가 필요할 수 있지만 모든 fault가 디스크 대기는 아니다.

Linux의 익명 zero page나 이미 page cache에 있는 파일 내용으로 매핑을 준비하면 저장장치 읽기 없이도 처리할 수 있다. TLB miss는 번역 캐시의 miss로 더 좁은 사건이다. 운영체제의 minor/major 같은 카운터 정의도 따로 확인해야 하며 서로 다른 용어의 수치를 합쳐 하나의 “메모리 오류”로 보고하지 않는다.

파일의 범위에 프로그램의 주소 범위를 연결한다

파일 매핑은 파일의 특정 바이트 범위를 프로세스 가상 영역으로 연결한다. mmap 객체의 인덱스 0은 파일 시작 0이 아니라 매핑에 정한 파일 오프셋에 대응한다. 파일 오프셋이 8192이고 인덱스 123을 읽으면 파일 바이트 8315를 대상으로 한다. 매핑 생성 시 오프셋 정렬 제한과 파일·매핑 길이를 확인해야 한다.

Python 공식 mmap 문서는 Unix와 Windows 생성자 차이를 설명한다. Windows의 ALLOCATIONGRANULARITY와 페이지 크기를 같은 값이라고 가정하지 않는다. mmap의 offset = 8192는 아래 가상 모형의 4 KiB 정렬 약속에서는 맞지만 실제 플랫폼에서 무조건 유효한 호출이라는 뜻은 아니다. 범위 밖 접근·파일 축소·닫힌 매핑 등의 오류도 API 규칙으로 처리한다.

매핑 접근 권한과 파일 반영은 따로 약속한다

Python ACCESS_READ 매핑에는 쓰기를 허용하지 않는다. ACCESS_WRITE는 매핑을 통해 바꾼 내용을 underlying file에 반영하는 접근 방식이고 ACCESS_COPY는 그 변경을 파일에 쓰지 않는다. 일반적인 Unix shared/private 관계를 이해하되 플랫폼 API의 정확한 약속을 확인한다.

파일이 바뀌어 보인다는 사실과 충돌 없이 여러 실행자가 공유한다는 사실은 다르다. 공유 데이터에는 동기화가 필요하며, flush의 의미와 운영체제·장치의 지속성 조건도 따로 다룬다. mmap이 언제나 read보다 빠르거나 전체 파일을 즉시 전용 RAM에 복사한다는 보장은 없다. 객체와 파일을 각각 닫아 수명을 관리한다.

중간 과정을 따라가는 예제

종이 모형에서 4 KiB 페이지, 파일 오프셋 8192, 매핑 길이 8192, 가상 base 0x40000을 정한다. 매핑 인덱스 5000을 읽는 가상 주소·파일 위치·매핑 내부 페이지를 구하라. 매핑 내부 두 번째 페이지는 아직 설치되지 않았지만 파일 내용은 OS 캐시에 있다.

  1. 가상 주소는 262144 + 5000 = 267144 = 0x41388이다. 파일 바이트는 8192 + 5000 = 13192다.

  2. 5000 = 1 × 4096 + 904이므로 매핑 내부 페이지 1, 오프셋 904다. 전체 VA의 VPN은 65, 오프셋은 904이며 내부 페이지 번호 1과 구별한다.

  3. 아직 PTE가 준비되지 않아 fault를 받아 OS가 기존 캐시의 파일 페이지를 매핑할 수 있다. 이 가정에서는 새 저장장치 읽기를 요구하지 않는다.

  4. 추가로 ACCESS_COPY 방식의 가상 매핑에서 그 위치에 20을 썼다고 하면 매핑에서 보는 값은 바뀌어도 파일을 20으로 갱신하는 약속은 없다. 실제 mmap을 실행한 사례가 아니다.

VA 0x41388, 파일 바이트 13192, 매핑 내부 페이지 1과 오프셋 904다. 이 가정의 fault는 새 파일 I/O 없이도 복구할 수 있다.

종이와 본문으로 직접 해보기

같은 매핑에서 인덱스 8191과 8192는 범위 안인가? 인덱스 0의 파일 위치는? READ와 COPY 매핑의 쓰기 차이를 적어라.

힌트 보기

길이 8192는 유효 인덱스 0부터 8191이다.

풀이 보기

8191은 안, 8192는 밖이다. 인덱스 0은 파일 8192에 대응한다. READ는 쓰기를 거부하며 COPY는 허용된 매핑의 사본을 바꾸되 underlying file을 갱신하지 않는다. 실제 API 예외와 정렬 조건은 환경에서 따로 확인한다.

오해와 반례

파일을 mmap하면 즉시 전체 파일이 전용 RAM에 복사되고 모든 변경이 파일에 저장된다.

매핑은 가상 영역과 파일 범위의 연결을 만든다. 페이지를 필요할 때 준비하거나 기존 캐시를 공유할 수 있으며 COPY와 READ 등 접근 방식에 따라 변경과 반영 규칙이 다르다.
