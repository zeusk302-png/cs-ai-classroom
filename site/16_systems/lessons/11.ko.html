소단원 11.1

블로킹과 배열 순회

같은 원소를 모두 읽는데 행을 따라 읽을 때와 열을 따라 읽을 때 왜 캐시 상태가 달라질까?

준비 개념과 학습 목표

준비 개념

  • 행 우선 배열의 주소를 계산한다.
  • 캐시 블록과 hit/miss를 구별한다.

학습 목표

  • 같은 결과를 만드는 다른 순회 주소열을 구성한다.
  • 타일이 응용 영역이며 캐시line과 다른 개념임을 설명한다.
  • 타일 경계와 결과 보존을 성능보다 먼저 확인한다.

먼저 원소의 주소를 적는다

행 우선 R×C 배열에서 원소 크기 e바이트, 시작 주소 base라면 원소 (i,j)의 시작 주소는 base+(iC+j)e다. 같은 행의 이웃은 e바이트 간격이지만 같은 열의 다음 행은 Ce바이트 간격이다. 추상적인 두 번째 첨자 이름보다 실제 배치를 먼저 알아야 지역성을 판단할 수 있다.

여기서는 시작 주소 0, 4×4 배열, 원소 1바이트의 읽기 주소만 추적한다. 캐시는 4바이트 블록·2set·1way, 초기 invalid, miss마다 블록 채움으로 고정한다. 합계 계산의 값·루프 변수·명령어·다른 배열 접근은 trace에서 제외한다. 실제 C코드의 전체 접근을 기록한 실험과 다른 간단한 모형이다.

작은 타일을 마치고 다음으로 이동한다

블로킹 또는 타일링은 응용의 일부 행·열 영역을 먼저 처리한 뒤 다음으로 이동하는 순서다. 2×2타일은4원소 영역이며 캐시가 가져오는4바이트 메모리블록과 같은 뜻이 아니다. 타일 안에서 필요한 데이터를 여러 번 쓰는 연산에서는 재사용 사이에 다른 데이터가 끼어드는 거리를 줄일 수 있다.

차원이 타일 크기의 배수가 아닐 때 끝쪽 타일에는 일부 원소만 있다. 루프 끝을 min(시작+타일크기,차원)으로 제한해야 밖을 읽거나 남은 원소를 빠뜨리지 않는다. 작은 단순 합계에서는 타일링이 행순서보다 더 좋을 필요가 없고 루프 제어 비용도 생긴다.

결과 보존과 접근 모형의 개선을 나눈다

모든 원소를 정확히 한 번 읽어 정수합을 구하는 목표라면 순회 집합과 중복 여부를 먼저 검사한다. 부동소수점 합은 덧셈 순서에 따라 반올림이 달라질 수 있고, 서로 의존하는 원소 갱신은 순서를 바꾸어도 의미가 같은지 확인해야 한다. 컴파일러가 원래 순서를 어떻게 바꾸는지도 실제 trace에서 별도 확인한다.

아래 자체 주소열에서는 행순서와2×2타일순서 모두4miss지만 열순서는16miss다. 이를 타일이 항상 가장 빠르다는 결론으로 바꾸지 않는다. 선택한 캐시의 모델과 읽기trace에서 얻은 횟수이며, 실행시간이나 실제 처리기의 하드웨어 카운터를 측정한 결과는 아니다.

중간 과정을 따라가는 예제

위 4×4 모형에서 행 순서 주소 0…15와 열 순서 0,4,8,12,1,5,9,13,…를 비교하자.

  1. 블록 번호는 주소//4다. 행 순서는 블록 0을 4번, 블록 1을 4번, 블록 2를 4번, 블록 3을 4번 방문한다.
  2. 각 블록 첫 접근만 miss라 MHHH가 4번이다. hit 12/miss 4, 2line이 차면 뒤 블록 채움 때 퇴출 2다.
  3. 열 순서는 블록 0,1,2,3을 반복한다. block mod2의 같은 set에서 0과 2, 1과 3이 서로 퇴출되어 16접근 모두 miss다.
  4. 자체 Python 모형을 실제로 실행해 행(12,4,2), 열(0,16,14)의 hit/miss/eviction을 확인했다.

이 모형에서 행 4miss/열 16miss다. 최종 배열값이나 실제 CPU 시간을 검사한 결과는 아니다.

종이와 본문으로 직접 해보기

2×2 타일 순서 주소 0,1,4,5,2,3,6,7,8,9,12,13,10,11,14,15를 블록 번호로 바꿔 miss를 추적하자. 3×5 배열에서 타일 2일 때 마지막 행과 마지막 열은 각각 어느 인덱스까지인가?

힌트 보기

블록 0/1을 타일 두 개 동안 보존한 뒤 2/3으로 이동한다. 0기준 행은 0…2, 열은 0…4다.

풀이 보기

타일 주소열 결과는 hit 12/miss 4/eviction 2로 행 순서와 같다. 3×5에서 마지막 행 타일은 행 2만, 마지막 열 타일은 열 4만 처리한다. 경계의 min을 생략하면 행 3이나 열 5를 잘못 읽을 수 있다.

오해와 반례

타일 크기를 캐시에 맞추면 모든 프로그램은 무조건 빨라진다.

자체 단순 순차 합에서는 행 순서와 타일 순서의 miss가 같다. 타일 제어 비용, 다른 배열과 충돌, 자료 배치, 연산 의존성도 영향을 준다. 정확성과 실제 측정을 함께 확인한다.

소단원 11.2

충돌 미스와 데이터 배치

배열 두 개를 조금 떨어뜨려 놓는 것만으로 번갈아 읽기의 miss가 줄어들 수 있을까?

준비 개념과 학습 목표

준비 개념

  • block/index/tag와 direct-mapped를 안다.
  • 배열 base와 stride를 구별한다.

학습 목표

  • 배치 주소로 set 충돌을 계산한다.
  • 패딩의 효과와 공간 비용을 분리한다.
  • 하나의 trace 개선을 전체 프로그램 개선으로 확대하지 않는다.

값이 아니라 주소 관계가 충돌을 만든다

블록 4B·4set·1way인 16B direct 캐시에서 주소 0은 block0/set0/tag0, 주소 16은 block4/set0/tag1이다. 두 주소의 값이 같든 다르든 같은 set의 하나뿐인 line을 사용하므로 번갈아 채우면 교체한다. 총 캐시가 16B라는 것과 두 블록을 동시에 둘 배치가 가능한 것은 다른 조건이다.

프로그램은 배열 시작 주소와 행 stride에 따라 반복적으로 같은 set을 방문할 수 있다. 이 예제의 단순 mod 배치는 설명용이며 실제 캐시의 물리 주소/해싱/페이지 관계와 정확한 index는 장치 조건을 확인해야 한다. 원소값의 변경만으로 주소 충돌을 해결한다고 생각하지 않는다.

패딩은 사용하지 않는 공간으로 주소 관계를 바꾼다

자체 B 시작을 16에서 20으로 옮기면 B는 block5/set1/tag1이 되어 A 주소 0의 set0과 다르다. 주소열 0,20,0,20은 첫 두 블록만 miss이고 뒤 둘은 hit다. 패딩은 필요한 논리 원소 사이에 추가 공간을 넣어 stride나 정렬 관계를 바꾸는 방법이다.

패딩으로 주소를 바꾸려면 새 배치에서도 논리 인덱스가 올바른 값을 가리키도록 코드를 맞춘다. 행마다 4B를 추가하면 많은 행에서 메모리 비용이 커지고 다른 계층의 용량/지역성/전송 효과가 변할 수 있다. 한 충돌을 없애는 작업이 새 충돌이나 더 큰 working set을 만들 가능성도 있다.

집합별 상태와 비교 기준을 보존한다

같은 주소열에서 way를 늘리는 대안도 생각할 수 있지만 총 데이터 용량과 set 수를 함께 맞춰야 한다. fully associative 동일 용량 기준에서 유지되는 블록이 direct에서 쫓겨나면 이 모형의 conflict miss다. 첫 접근 miss는 충돌되는 주소라도 compulsory로 따로 센다.

비교 표에는 원래/새 base, 블록 크기, set 수, way 수, 초기 상태, 방문 순서를 모두 적는다. 패딩 전후 프로그램이 같은 논리 원소를 읽는지도 검사한다. 실제 속도는 miss 외의 비용에도 달려 있으므로 모형의 횟수와 실제 시간을 분리한다.

중간 과정을 따라가는 예제

위 direct 캐시에서 논리 원소 A0/B0을 0,16,0,16주소로 읽다가 B base만 20으로 옮겨 0,20,0,20으로 읽는다. 각각 hit/miss/eviction을 추적하자.

  1. 원래 0/16은 set0 태그 0/1로 MMMM다. 최초 0은 빈 line 채움이라 퇴출 없고 나머지 3은 퇴출이다.
  2. 패딩 뒤 0/20은 set0/set1로 MMHH다. 각 set의 다른 빈 line에 들어가 퇴출 없다.
  3. 원래 hit0/miss4/eviction3, 새 hit2/miss2/eviction0이다.
  4. 자체 Python 모형으로 두 결과를 실제 확인했다. 새 주소 20은 논리 B0을 그곳에 놓는 가정이며 실제 malloc 배치를 바꾼 실험은 아니다.

지정한 trace에서 패딩 후 2miss가 줄었다. 첫 접근 miss 둘은 그대로이며 물리 컴퓨터의 시간 단축을 측정한 것은 아니다.

종이와 본문으로 직접 해보기

B base를 16 대신 32로 옮기면 4set/4B에서 충돌은 없어지는가? 24로 옮기면?

힌트 보기

byte 주소/4로 블록 번호를 구하고 mod4로 set을 구한다.

풀이 보기

32는 block8/set0이라 A0과 여전히 충돌한다. 24는 block6/set2라 A의 set0과 다르다. 단순히 더 멀리 놓는 것이 아니라 set 관계를 확인해야 한다.

오해와 반례

같은 set을 사용하는 첫 접근은 모두 conflict miss라고 부른다.

초기 빈 모형에서 각 블록의 최초 접근은 compulsory다. 뒤 재접근에서 동일 용량 fully 기준은 hit인데 direct는 miss일 때 conflict로 분류한다.

자기점검

주소 16과 0은 이 예제에서 같은 메모리 블록인가?

답과 이유 보기

아니다.

block4와 0이며 set만 같다.

패딩이 항상 무료인가?

답과 이유 보기

아니다.

추가 공간과 주소 계산/배치 변경 비용이 있다.

B base32는 A0과 set이 다른가?

답과 이유 보기

아니다.

32/4=8,8 mod4=0이다.

한 단계 더

4열·원소 4B인 행의 stride 16B는 4set/4B 모형에서 같은 열의 다음 행이 같은 set에 간다. 행 stride를 20B로 패딩하면 block 간격 5가 되어 set이 한 칸씩 옮겨진다. 시작 주소 0인 4행의 같은 첫 열 set이 0,1,2,3으로 바뀌는 대신 추가 공간이 행당 4B임을 계산하자.

소단원 11.3

캐시 시뮬레이션 실험

실험 결과의 miss 숫자가 나왔을 때 무엇을 실제로 검증했고 무엇은 아직 모를까?

준비 개념과 학습 목표

준비 개념

  • Python 함수·리스트·반복·조건을 안다.
  • set/way와 LRU 상태를 추적한다.

학습 목표

  • 작은 읽기 trace를 명시한 LRU 모형으로 실행한다.
  • hit/miss/eviction과 매 접근 상태를 손 표로 대조한다.
  • 소프트웨어 모형·실제 trace·실제 CPU 측정을 구별한다.

무엇을 모델링하는지 먼저 고정한다

아래 자체 함수는 비음수 정수 byte 주소열을 받는 읽기 전용 모형이다. block_bytes/sets/ways는 양의 정수여야 한다. 모든 접근은 1바이트 읽기 하나이며 큰 접근이 여러 블록을 넘는 경우는 입력에 없다. 최초 표는 비어 있고 miss마다 요청 블록을 채운다. 내용값·dirty·쓰기에 따른 트래픽·시간·prefetch는 저장하지 않는다.

각 set의 리스트에는 태그만 두고 맨 앞은 가장 오래 접근한 LRU, 맨 뒤는 최근 MRU다. hit면 태그를 제거한 뒤 끝에 추가해 최근성을 바꾼다. miss에서 set이 ways개로 가득 찼으면 맨 앞 태그를 퇴출한다. 공간이 있을 때 새로 채움은 miss지만 eviction은 아니다.

저장한 원고 코드를 실행하고 작은 표로 대조한다

Python 기초를 배웠다면 아래 코드를 새 파일 cache_demo.py에 붙여 넣고 저장한 뒤 Python 실행 환경에서 실행할 수 있다. 설치 없이도 출력 전 각 줄을 손으로 따라갈 수 있다. 여기 집필자는 같은 함수와 입력을 python -X utf8로 실제 실행해 (1,3,2,'MHMM')을 확인했다. 학습자가 직접 실행했는지는 별도 미수행이다.

결과 튜플은 hit 수, miss 수, eviction 수, 각 접근의 H/M열이다. 합 hit+miss는 입력 주소 수와 같아야 한다. eviction은 유효 line을 대체한 miss에서만 증가한다. 출력 숫자만 믿기보다 최소 입력·빈 표·동일 블록 재접근·서로 충돌·LRU hit 갱신을 손 표와 대조한다.

def simulate(addresses, block_bytes, sets, ways):
    lines = [[] for _ in range(sets)]
    hits = misses = evictions = 0
    events = []
    for address in addresses:
        block = address // block_bytes
        index = block % sets
        tag = block // sets
        group = lines[index]
        if tag in group:
            hits += 1
            group.remove(tag)
            event = "H"
        else:
            misses += 1
            event = "M"
            if len(group) == ways:
                group.pop(0)
                evictions += 1
        group.append(tag)
        events.append(event)
    return hits, misses, evictions, "".join(events)

print(simulate([0, 1, 8, 0], 4, 2, 1))

trace 수집과 모형 실행을 구별한다

실제 프로그램의 trace를 수집하는 도구와 그 trace를 재생하는 시뮬레이터는 다른 단계다. CMU 과제의 I/L/S/M에는 명령 읽기·데이터 읽기·저장·수정이 있고 M은 읽기 뒤 저장 두 접근으로 취급한다. 이 읽기 전용 함수에는 그 parser를 구현하지 않았으므로 원 과제 지원이라고 부르지 않는다.

시뮬레이터의 LRU와 cache 설정은 실제 CPU의 계층·근사 교체·가상/물리 주소·타이밍과 다를 수 있다. 원고 코드 검증은 그 지정 모형의 결과이며 실제 처리기 속도 증명은 아니다. 실제 실험을 보고할 때는 코드/입력/설정/출력/수행 범위를 보존하고 미수행 검사를 남긴다.

중간 과정을 따라가는 예제

simulate([0,1,8,0],4,2,1)의 매 접근과 실제 출력 (1,3,2,'MHMM')을 대조하자.

  1. 주소 0은 block0/set0/tag0, 빈칸이라 miss다.
  2. 주소 1은 같은 block0이라 hit다. offset이 달라도 같은 line이다.
  3. 주소 8은 block2/set0/tag1이라 miss이고 기존 tag0을 퇴출한다.
  4. 마지막 0은 tag0이 없어 miss이고 tag1을 퇴출한다. hit1/miss3/eviction2와 MHMM이다.

실제 자체 코드 출력과 손 추적이 일치했다. 주소값 내용이나 실제 캐시 시간을 측정한 결과는 아니다.

종이와 본문으로 직접 해보기

손으로 먼저 simulate([0,4,0,8,0],4,1,2)를 예측하자. block0/1 두 개를 넣은 뒤 0의 hit가 LRU를 어떻게 바꾸는가?

힌트 보기

set은 하나, way는 2다. hit 태그를 리스트 끝으로 옮긴다.

풀이 보기

블록 순서 0,1,0,2,0이며 상태 LRU→MRU는 [0],[0,1],[1,0],[0,2],[2,0]이다. 2 채움 때 1을 퇴출해서 마지막 0은 hit다. hit2/miss3/eviction1, MMHMH다. 집필자가 같은 모형으로 실제 실행해 대조했다.

오해와 반례

시뮬레이터에서 miss가 적으면 실제 프로그램은 그만큼 반드시 빨라진다.

이 모형은 시간·다른 접근·병렬 miss를 포함하지 않는다. 정확한 목표 결과와 실제 측정 조건을 별도로 확인해야 한다. 원고 코드 실행·trace 수집·CPU 측정·학습자 수행은 서로 다른 증거다.

한 단계 더

같은 tiny trace의 ways를 2로 바꾸고 sets2/block4는 유지하면 총 용량이 8B에서 16B로 늘어난다. 두 태그를 함께 유지해 MHMH, 즉 hit2/miss2/eviction0을 예측하자. way 효과만 비교하려면 총 용량도 같게 하는 설정이 필요함을 설명하고 이 확장 결과는 아직 실제 실행하지 않은 예측으로 표시하자.
