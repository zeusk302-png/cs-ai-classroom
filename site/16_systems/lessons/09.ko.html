주소공간은 영역들의 지도

프로세스는 자신의 가상 주소공간에서 코드·데이터·heap·stack·파일 mapping 등을 본다. 숫자로 가까운 주소가 물리RAM에서도 이웃이라는 뜻은 아니다. 빈 구간은 아직 매핑되지 않았거나 접근할 수 없는 곳일 수 있다. Linux의 /proc/pid/maps는 현재 매핑과 접근 권한을 보여 주며 열람 자체도 권한 검사 대상이다.

구간과 권한

maps의 주소 열은 시작-끝 형태이며 크기는 끝에서 시작을 뺀다. 이 단원은 시작 포함·끝 제외 구간으로 읽는다. r/w/x는 읽기/쓰기/실행, p는 private copy-on-write,s는 shared를 뜻한다. r-xp 코드 영역에 쓰는 것을 허용하는 표라고 해석하지 않는다. 파일 offset과 pathname은 어떤 파일 부분이 기반인지 보여 주지만 mapping 길이가 실제 물리 점유량과 같지는 않다.

스택과 힙 이름의 한계

[stack]은 주 스레드의 stack,[heap]은 heap으로 표시될 수 있다. 모든 동적 할당이 [heap] 하나에서만 나오지는 않으며 익명 mmap도 사용될 수 있다. 오래된 예시의 [stack:tid] 표시는 최근 Linux에서 제거되었으므로 현재 시스템에도 항상 나온다고 말하지 않는다. 주소의 배치와 growth 방향도 ABI와환경을 명시해야 한다.

중간 과정을 따라가는 예제

가상 지도에400000-402000 r-xp 코드와600000-603000 rw-p 데이터가 있다.16진수 주소이며 각 페이지4096B라고 가정한다. 크기와 페이지 수를 구하라.

  1. 코드 차이는0x2000=8192B=2페이지이다.

  2. 데이터 차이는0x3000=12288B=3페이지이다.

  3. 합매핑20480B=5페이지이나 이 표만으로 실제상주RAM5페이지를 확정할 수 없다.

코드8KiB·2페이지,데이터12KiB·3페이지,총20KiB 매핑이다.

오해와 반례

maps 길이를 더하면 프로세스의 실제 RAM 사용량이 된다.

가상 매핑은 아직 상주하지 않은 페이지와 공유 페이지를 포함할 수 있다. 상주량과 공유분 배분에는 별도 지표가 필요하다.

파일에서 실행 환경으로

ELF 동적 실행파일은 필요한 공유객체와 동적 loader 정보를 담는다. loader는 라이브러리를 찾아 매핑하고 기호와 재배치 등을 처리한 뒤 실행을 준비한다. 공유 라이브러리라는 말은 모든 가변 데이터가 모든 프로세스에 하나로 공유된다는 뜻은 아니다. 프로세스마다 주소와 private 데이터가 다를 수 있다.

검색 규칙과 조건

Linux ld.so는 의존 문자열에 slash가 있으면 그 경로를 사용한다. 없으면 조건에 따라 DT_RPATH, LD_LIBRARY_PATH, DT_RUNPATH, cache, default 경로를 검사한다. DT_RPATH는 RUNPATH가 없을 때 사용하고 secure-execution에서는 LD_LIBRARY_PATH를 무시한다. RUNPATH는 그 객체의 직접 DT_NEEDED 의존성에만 적용되고 자식의 의존성에는 자동 상속되지 않는다. 단순 목록만 외우지 말고 조건을 함께 읽자.

주소와 기호 호환

라이브러리 내 함수의 실행 주소는 단순 교육 모형에서 load base+상대 offset으로 계산한다. 실제 ELF에서는 segment layout과 relocation을 정확히 해석해야 하므로 파일 offset을 무조건 더하지 않는다. 이름이 같아도 ABI·기호 버전·calling convention이 달라질 수 있다. 잘못된 경로 설정은 예상치 못한 파일을 선택하게 하므로 어떤 파일을 적재했는지 확인해야 한다.

중간 과정을 따라가는 예제

가상 loader에서 slash 없는 libtoy.so를 요청한다. RPATH/RUNPATH는 없고 secure-execution도 아니다. LD_LIBRARY_PATH의 /a에는 파일이 없고 /b에는 있다. cache에는 /c의 파일이 있다. 어느 파일을 먼저 선택하나?

  1. 환경 경로를 지정 순서 /a, /b로 검사한다.

  2. /a에 없고 /b에 있으므로 /b/libtoy.so를 선택한다.

  3. cache의 /c는 앞 단계가 성공했으므로 이 선택에서 쓰지 않는다.

/b/libtoy.so. 존재하고 호환하여 로드 성공한다는 가상 조건이다.

오해와 반례

라이브러리 이름만 같으면 언제나 같은 파일·같은 함수 주소를 사용한다.

검색 경로·ABI·적재 base가 달라질 수 있다. 의존 이름·선택 파일·기호 호환·주소는 각각 확인해야 한다.

배치 바꾸기와 코드 대응

ASLR은 지원하는 환경에서 주소 배치를 무작위화해 주소 예측을 어렵게 한다. PIC는 특정 고정 주소에만 묶이지 않도록 생성한 코드이고 PIE는 위치독립 실행파일이다. PIC/PIE가 그 자체로 주소를 랜덤 선택하는 기능은 아니다. 가능한 재배치를 만드는 코드와 실제 배치를 정하는 운영 환경을 구별한다.

상대 관계의 보존

함수와 데이터가 이미지 내 상대 위치로 묶여 있다면 이미지 base가 바뀌어도 두 위치의 차이는 같다. 외부 기호는 GOT 등과 loader의 재배치로 처리할 수 있다. GCC는 공유 라이브러리용 -fpic/-fPIC와 실행파일용 -fpie/-fPIE를 구별하며 뒤 옵션은 보통 -pie 링크와 짝지어진다. 모든 target에서 동일한 구현이라고 단정하지 않는다.

무작위화의 범위와 한계

Linux randomize_va_space=0은 끄기, 1은 mmap base·stack·VDSO와 PIE code start의 무작위화, 2는 heap 무작위화를 추가한다. architecture와 kernel 설정 조건을 따른다. 이 단원은 값을 읽거나 변경하지 않았다. 무작위 배치가 매번 서로 다른 주소를 보장하지 않고 주소 유출이나 다른 오류가 있으면 보호 효과가 약해질 수 있다. 메모리 안전 버그를 수정하는 기능과는 별개다.

중간 과정을 따라가는 예제

가상 이미지에서 함수 F offset은 0x120, 데이터 D offset은 0x320이다. base가 0x400000인 실행과 0x800000인 실행에서 주소와 D-F를 구하라.

  1. 첫 실행 F=0x400120, D=0x400320이다.

  2. 둘째 실행 F=0x800120, D=0x800320이다.

  3. 두 실행 모두 차이는 0x200=512 B다. 실제 장치 측정이 아닌 주어진 배치 계산이다.

절대 주소는 달라도 상대 차이 512 B는 유지된다.

종이와 본문으로 직접 해보기

균일하고 독립적으로 4개 base 중 하나를 선택하는 장난감 모형에서 다음 실행 base가 직전과 같을 확률은?

힌트 보기

가능한 4개 중 같은 선택은 1개다.

풀이 보기

1/4이다. 실제 ASLR entropy를 측정한 값이 아니며 연속 실행 주소가 반드시 달라야 한다는 주장에 대한 단순 반례다.

오해와 반례

PIE를 컴파일하면 모든 메모리 버그가 사라지고 주소는 반드시 매번 다르다.

PIE는 배치를 옮길 수 있는 코드를 준비할 뿐 메모리 안전을 증명하지 않는다. 무작위 선택은 우연히 같을 수 있고 운영 환경이 ASLR을 적용해야 한다.
