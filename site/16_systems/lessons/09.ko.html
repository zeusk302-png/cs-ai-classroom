주소공간은 영역들의 지도

프로세스는 자신의 가상 주소공간에서 코드·데이터·heap·stack·파일 mapping 등을 본다. 숫자로 가까운 주소가 물리RAM에서도 이웃이라는 뜻은 아니다. 빈 구간은 아직 매핑되지 않았거나 접근할 수 없는 곳일 수 있다. Linux의 /proc/pid/maps는 현재 매핑과 접근 권한을 보여 주며 열람 자체도 권한 검사 대상이다.

구간과 권한

maps의 주소 열은 시작-끝 형태이며 크기는 끝에서 시작을 뺀다. 이 단원은 시작 포함·끝 제외 구간으로 읽는다. r/w/x는 읽기/쓰기/실행, p는 private copy-on-write,s는 shared를 뜻한다. r-xp 코드 영역에 쓰는 것을 허용하는 표라고 해석하지 않는다. 파일 offset과 pathname은 어떤 파일 부분이 기반인지 보여 주지만 mapping 길이가 실제 물리 점유량과 같지는 않다.

스택과 힙 이름의 한계

[stack]은 주 스레드의 stack,[heap]은 heap으로 표시될 수 있다. 모든 동적 할당이 [heap] 하나에서만 나오지는 않으며 익명 mmap도 사용될 수 있다. 오래된 예시의 [stack:tid] 표시는 최근 Linux에서 제거되었으므로 현재 시스템에도 항상 나온다고 말하지 않는다. 주소의 배치와 growth 방향도 ABI와환경을 명시해야 한다.

중간 과정을 따라가는 예제

가상 지도에400000-402000 r-xp 코드와600000-603000 rw-p 데이터가 있다.16진수 주소이며 각 페이지4096B라고 가정한다. 크기와 페이지 수를 구하라.

  1. 코드 차이는0x2000=8192B=2페이지이다.
  2. 데이터 차이는0x3000=12288B=3페이지이다.
  3. 합매핑20480B=5페이지이나 이 표만으로 실제상주RAM5페이지를 확정할 수 없다.

코드8KiB·2페이지,데이터12KiB·3페이지,총20KiB 매핑이다.

파일에서실행환경으로

ELF 동적 실행파일은 필요한 공유객체와 동적 loader정보를 담는다. loader는 라이브러리를찾아매핑하고기호와재배치등을처리한뒤실행을준비한다. 공유라이브러리라는말은모든가변데이터가모든프로세스에하나로공유된다는뜻은아니다.프로세스마다주소와private데이터가다를수있다.

검색규칙과조건

Linux ld.so는의존문자열에slash가있으면그경로를사용한다.없으면조건에따라 DT_RPATH,LD_LIBRARY_PATH,DT_RUNPATH,cache,default경로를검사한다. DT_RPATH는RUNPATH가없을때사용하고 secure-execution에서는환경변수를무시할수있다. RUNPATH는그객체의직접 DT_NEEDED 의존성에만적용되고자식의의존성에는자동상속되지않는다.단순목록만외우지말고조건을함께읽자.

주소와기호호환

라이브러리내함수의실행주소는단순교육모형에서load base+상대offset으로계산한다.실제 ELF에서는segment layout과relocation을정확히해석해야하므로파일offset을무조건더하지않는다. 이름이같아도ABI·기호버전·calling convention이달라질수있다.잘못된경로설정은예상치못한파일을선택하게하므로어떤파일을적재했는지확인해야한다.

중간 과정을 따라가는 예제

가상loader에서slash없는libtoy.so를요청한다. RPATH/RUNPATH는없고 secure-execution도아니다. LD_LIBRARY_PATH의/a에는파일이없고/b에는있다. cache에는/c의파일이있다. 어느파일을먼저선택하나?

  1. 환경경로를지정순서/a,/b로검사한다.
  2. /a에없고/b에있으므로/b/libtoy.so를선택한다.
  3. cache의/c는앞단계가성공했으므로이선택에서쓰지않는다.

/b/libtoy.so.존재·호환하여로드성공한다는가상조건이다.

힌트 보기

풀이 보기

오해와 반례

라이브러리이름만같으면언제나같은파일·같은함수주소를사용한다.

검색경로·ABI·적재base가달라질수있다.의존이름·선택파일·기호호환·주소는각각확인해야한다.

배치바꾸기와코드대응

ASLR은지원하는환경에서주소배치를무작위화해주소예측을어렵게한다. PIC는특정고정주소에만묶이지않도록생성한코드이고 PIE는위치독립실행파일이다. PIC/PIE가그자체로주소를랜덤선택하는기능은아니다.가능한재배치를만드는코드와실제배치를정하는운영환경을구별한다.

상대관계의보존

함수와데이터가이미지내상대위치로묶여있다면이미지base가바뀌어도두위치의차이는같다.외부기호는GOT등과loader의재배치로처리할수있다. GCC는공유라이브러리용-fpic/-fPIC와실행파일용-fpie/-fPIE를구별하며뒤옵션은보통-pie링크와짝지어진다.어느target이나동일한구현이라고단정하지않는다.

무작위화의범위와한계

Linux randomize_va_space=0은끄기,1은mmap base·stack·VDSO와PIE code start의무작위화,2는heap무작위화를추가한다. architecture와kernel설정조건을따른다.이단원은값을읽거나변경하지않았다.무작위배치가매번서로다른주소를보장하지않고,주소유출이나다른오류가있으면보호효과가약해질수있다. 메모리안전버그를수정하는기능과는별개다.

중간 과정을 따라가는 예제

가상이미지에서함수Foffset0x120,데이터Doffset0x320이다. base가0x400000인실행과0x800000인실행에서주소와D-F를구하라.

  1. 첫F0x400120,D0x400320이다.
  2. 둘째F0x800120,D0x800320이다.
  3. 둘다차0x200=512B로같다.실제장치측정이아닌주어진배치계산이다.

절대주소는달라도상대차512B는유지된다.

힌트 보기

풀이 보기

오해와 반례

PIE를컴파일하면모든메모리버그가사라지고주소는반드시매번다르다.

PIE는배치를옮길수있는코드를준비할뿐메모리안전을증명하지않는다.무작위선택은우연히같을수있고운영환경이ASLR을적용해야한다.
