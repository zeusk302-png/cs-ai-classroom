같은 파일의 두 지도 행에서 같은 바이트를 찾을 수 있는가?

새 종이 지도는 0x10000–0x12000 r-xp, 파일 오프셋 0x0000과 0x20000–0x21000 r--p, 파일 오프셋 0x3000을 같은 파일 X에 연결한다. 구간은 시작 포함·끝 제외다. 첫 행의 주소 0x10180은 시작에서 0x180 떨어져 파일 바이트 0x180에 해당한다. 둘째 행의 주소 0x20180은 파일 바이트 0x3180에 해당한다. 가상 주소의 낮은 자리만 같다고 같은 파일 바이트는 아니다.

첫 행은 두 페이지, 둘째 행은 한 페이지다. 페이지가 4096바이트라는 가정 아래 가상 매핑 크기의 합은 12KiB다. 이 합은 상주 물리 메모리의 합도 프로세스마다 고유한 물리 페이지의 합도 아니다. 서로 다른 프로세스의 같은 가상 주소 역시 각각의 지도와 변환을 따로 봐야 한다.

private는 쓰기 허가라는 뜻이 아니다. 첫 행의 r-xp에는 쓰기 권한이 표시되지 않고 둘째 행의 r--p에는 실행 권한도 없다. private/shared와 읽기/쓰기/실행은 별도 칸이다. 실제 Linux 지도 열람과 페이지 접근, 권한 변경은 수행하지 않는다.

주소공간은 영역들의 지도

프로세스는 자신의 가상 주소공간에서 코드·데이터·heap·stack·파일 mapping 등을 본다. 숫자로 가까운 주소가 물리RAM에서도 이웃이라는 뜻은 아니다. 빈 구간은 아직 매핑되지 않았거나 접근할 수 없는 곳일 수 있다. Linux의 /proc/pid/maps는 현재 매핑과 접근 권한을 보여 주며 열람 자체도 권한 검사 대상이다.

구간과 권한

maps의 주소 열은 시작-끝 형태이며 크기는 끝에서 시작을 뺀다. 이 단원은 시작 포함·끝 제외 구간으로 읽는다. r/w/x는 읽기/쓰기/실행, p는 private copy-on-write,s는 shared를 뜻한다. r-xp 코드 영역에 쓰는 것을 허용하는 표라고 해석하지 않는다. 파일 offset과 pathname은 어떤 파일 부분이 기반인지 보여 주지만 mapping 길이가 실제 물리 점유량과 같지는 않다.

스택과 힙 이름의 한계

[stack]은 주 스레드의 stack,[heap]은 heap으로 표시될 수 있다. 모든 동적 할당이 [heap] 하나에서만 나오지는 않으며 익명 mmap도 사용될 수 있다. 오래된 예시의 [stack:tid] 표시는 최근 Linux에서 제거되었으므로 현재 시스템에도 항상 나온다고 말하지 않는다. 주소의 배치와 growth 방향도 ABI와환경을 명시해야 한다.

직접 의존성을 찾은 경로가 그 자식에게도 전해지는가?

새 의존 그래프는 app→libA→libB다. app의 RUNPATH는 /pkg이고 libA에는 RUNPATH가 없다. 환경 경로·RPATH·cache는 없으며 기본 경로 /sys만 쓰는 단순 검색 모형이다. /pkg에 A와 B가 모두 있고 /sys에는 B가 없다. app은 직접 A를 /pkg에서 찾지만 libA가 B를 찾을 때 app의 RUNPATH를 자동 상속하지 않으므로 B를 못 찾는다.

libA 자체에 /pkg RUNPATH를 주면 그 직접 의존 B를 찾는다. 다른 별도 모형에서 의존 이름을 /pkg/libB로 지정하면 slash가 있는 경로로 해석하므로 일반 이름 검색 문제와 구별한다. 이 예제는 경로 선택 책임의 손추적이며 실제 바이너리나 loader를 실행하지 않는다.

경로에서 파일을 찾는 것과 그 파일이 필요한 심볼·버전·대상 ABI 계약을 만족하는 것은 별도다. 같은 이름의 파일이 여러 후보 경로에 있을 때 먼저 선택한 파일의 정체성과 호환성을 기록한다. 호환하지 않으면 무조건 다음 디렉터리로 재시도한다는 임의 규칙을 추가하지 않는다.

파일에서 실행 환경으로

ELF 동적 실행파일은 필요한 공유객체와 동적 loader 정보를 담는다. loader는 라이브러리를 찾아 매핑하고 기호와 재배치 등을 처리한 뒤 실행을 준비한다. 공유 라이브러리라는 말은 모든 가변 데이터가 모든 프로세스에 하나로 공유된다는 뜻은 아니다. 프로세스마다 주소와 private 데이터가 다를 수 있다.

검색 규칙과 조건

Linux ld.so는 의존 문자열에 slash가 있으면 그 경로를 사용한다. 없으면 조건에 따라 DT_RPATH, LD_LIBRARY_PATH, DT_RUNPATH, cache, default 경로를 검사한다. DT_RPATH는 RUNPATH가 없을 때 사용하고 secure-execution에서는 LD_LIBRARY_PATH를 무시한다. RUNPATH는 그 객체의 직접 DT_NEEDED 의존성에만 적용되고 자식의 의존성에는 자동 상속되지 않는다. 단순 목록만 외우지 말고 조건을 함께 읽자.

주소와 기호 호환

라이브러리 내 함수의 실행 주소는 단순 교육 모형에서 load base+상대 offset으로 계산한다. 실제 ELF에서는 segment layout과 relocation을 정확히 해석해야 하므로 파일 offset을 무조건 더하지 않는다. 이름이 같아도 ABI·기호 버전·calling convention이 달라질 수 있다. 잘못된 경로 설정은 예상치 못한 파일을 선택하게 하므로 어떤 파일을 적재했는지 확인해야 한다.

주소를 반복 관찰하면 이동 가능성과 무작위성을 증명하는가?

새 이미지 버전 V1의 F/G 상대 위치는 0x100/0x180이다. base가 0x40000이면 주소는 0x40100/0x40180, 0x90000이면 0x90100/0x90180이다. 같은 이미지의 상대 차 0x80은 유지된다. 절대 주소 0x40100을 다음 실행에 그대로 넣는 설계는 base 변경을 반영하지 못한다.

버전 V2에서는 F offset이 0x140으로 바뀌었다고 별도로 가정한다. V2의 base 0x90000에 V1의 offset 0x100을 더하면 0x90100이지만 F의 주소는 0x90140이다. 이미지 기준 offset은 base 이동을 처리할 수 있어도 버전 간 함수 위치 계약을 저절로 보존하지 않는다. 식별자·이미지 버전·선택된 정의를 함께 확인한다.

주소가 옮겨도 실행 가능한 코드의 준비와 운영 환경의 무작위 배치 선택은 다른 기능이다. 아래 후보 base 네 개의 확률은 자체 장난감 모형이다. 실제 Linux entropy·보호 효과·메모리 안전·PIE 빌드 성공을 측정한 것이 아니다. GCC/커널 문서의 옵션과 정책을 읽었지만 실제 설정을 변경하지 않는다.

배치 바꾸기와 코드 대응

ASLR은 지원하는 환경에서 주소 배치를 무작위화해 주소 예측을 어렵게 한다. PIC는 특정 고정 주소에만 묶이지 않도록 생성한 코드이고 PIE는 위치독립 실행파일이다. PIC/PIE가 그 자체로 주소를 랜덤 선택하는 기능은 아니다. 가능한 재배치를 만드는 코드와 실제 배치를 정하는 운영 환경을 구별한다.

상대 관계의 보존

함수와 데이터가 이미지 내 상대 위치로 묶여 있다면 이미지 base가 바뀌어도 두 위치의 차이는 같다. 외부 기호는 GOT 등과 loader의 재배치로 처리할 수 있다. GCC는 공유 라이브러리용 -fpic/-fPIC와 실행파일용 -fpie/-fPIE를 구별하며 뒤 옵션은 보통 -pie 링크와 짝지어진다. 모든 target에서 동일한 구현이라고 단정하지 않는다.

무작위화의 범위와 한계

Linux randomize_va_space=0은 끄기, 1은 mmap base·stack·VDSO와 PIE code start의 무작위화, 2는 heap 무작위화를 추가한다. architecture와 kernel 설정 조건을 따른다. 이 단원은 값을 읽거나 변경하지 않았다. 무작위 배치가 매번 서로 다른 주소를 보장하지 않고 주소 유출이나 다른 오류가 있으면 보호 효과가 약해질 수 있다. 메모리 안전 버그를 수정하는 기능과는 별개다.

이동과 버전 변경의 두 실패

첫 절대 주소와 첫 offset을 각각 언제 잘못 재사용하는지 계산하라.

  1. 같은 V1 base 변경에서 이전 절대 주소 0x40100은 새 0x90100과 다르다.

  2. V2에 옛 offset을 넣은 0x90100은 실제 지정 F 위치 0x90140보다 0x40 작다.

절대 주소는 base 변경, offset은 버전 변화에 각각 취약하다.

상대 기록의 장점과 유효 이미지 조건을 함께 적는다.

서로 다른 두 선택 규약

네 base를 균일 독립 선택하는 모형과 확률 (1/2,1/4,1/8,1/8)의 독립 선택 모형에서 두 연속 선택이 같은 확률을 구하라.

  1. 균일은 네 항의 합 4·(1/4)²=1/4다.

  2. 다른 규약은 1/4+1/16+1/64+1/64=11/32다.

1/4와 11/32다. 후보 개수만으로 반복 확률을 정할 수 없다.

1/4이다. 실제 ASLR entropy를 측정한 값이 아니며 연속 실행 주소가 반드시 달라야 한다는 주장에 대한 단순 반례다.

오해와 반례

PIE를 컴파일하면 모든 메모리 버그가 사라지고 주소는 반드시 매번 다르다.

PIE는 배치를 옮길 수 있는 코드를 준비할 뿐 메모리 안전을 증명하지 않는다. 무작위 선택은 우연히 같을 수 있고 운영 환경이 ASLR을 적용해야 한다.

연습 1 · 값과 상태 예측

V1 base=0xa0000에서 F/G의 주소와 차를 구하라.

힌트 1

같은 이미지 offset 0x100/0x180을 쓴다.

힌트 2

차에는 같은 base가 상쇄된다.

풀이와 답 확인

  1. F의 주소는 0xa0100이고 G의 주소는 0xa0180이다.

  2. G에서 F를 뺀 상대 차는 0x80, 즉 128바이트다.

F의 절대 주소는 0xa0100이고 G의 절대 주소는 0xa0180이다. 상대 차는 128바이트다.

흔한 오답에서 다시 생각하기

base 차이만큼 함수 사이 거리도 증가한다.

한 이미지의 두 주소에 같은 이동을 적용하면 차가 보존된다.

연습 2 · 오류 찾아 고치기

PIE 표시가 있으므로 주소가 매번 다르고 메모리 오류가 없다고 했다. 주장 범위를 고쳐라.

힌트 1

코드 이동 가능성과 실제 배치 선택을 분리한다.

힌트 2

같은 무작위 후보가 다시 나올 수 있다.

풀이와 답 확인

  1. 실제 운영 환경 정책과 배치 결과를 별도 확인한다.

  2. 메모리 안전은 해당 코드/수명/경계 책임을 따로 검토한다.

PIE 하나로 무작위 실행 기록이나 메모리 안전을 인증하지 않는다.

흔한 오답에서 다시 생각하기

주소 한 번 변경을 보았으면 모든 보안 요구가 끝난다.

단일 관찰은 전체 입력의 안전 증명도 무작위성 검증도 아니다.

연습 3 · 직접 만들어 보기

V1의 F 기록을 새 base에서 복구할 수 있게 필요한 메타데이터와 식을 구성하라.

힌트 1

이미지 정체성과 offset을 함께 보존한다.

힌트 2

실제 매핑의 기준을 다시 얻어야 한다.

풀이와 답 확인

  1. V1 식별자와 이미지 기준 F offset 0x100을 기록한다.

  2. 동일 V1 선택과 해당 base가 확인된 모형에서 base+0x100으로 복구한다.

V2이면 옛 offset을 자동 적용하지 않고 정의/버전을 다시 확인한다. 실제 심볼 조회 도구는 실행하지 않았다.

흔한 오답에서 다시 생각하기

offset 하나는 모든 버전과 모든 ABI에서 영구 주소다.

상대 위치는 특정 이미지 계약에 종속된다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

균일 독립 네 후보 모형에서 세 실행의 base가 모두 같은 확률은? 또한 비균일 모형에서 직전 base가 첫 후보였다고 조건화한 다음 일치 확률은?

힌트 1

세 실행 일치는 4·(1/4)³다.

힌트 2

조건부 다음 첫 후보의 확률은 1/2다.

풀이와 답 확인

  1. 세 실행 전체 일치 확률은 1/16이다.

  2. 비균일 조건부 일치 확률은 1/2다.

1/16과 1/2다. 비균일 무조건부 두 실행 일치 11/32와 조건화 범위가 다르다.

흔한 오답에서 다시 생각하기

후보 네 개면 모든 반복 확률은 1/4다.

실행 개수와 선택 확률·조건부 여부를 모두 명시해야 한다.

다른 문제에 적용하기

종이 배포 감사를 구성하라. 지도 X의 두 행과 V1의 F/G offset을 그대로 쓰되, 실제 프로세스 접근은 하지 않는다. 지도 주소 0x20180의 대응 파일 바이트와 두 행 가상 크기를 구한다. app→libA→libB에서 app RUNPATH=/pkg, libA RUNPATH 없음, 환경/RPATH/cache 없음, 기본 /sys에 B 없음이며 /pkg에는 A/B가 있다. 실패 원인과 객체 수준 수정 하나를 제시한다. V1 base=0x90000에서 F/G를 구하고 V2의 F offset 0x140에 옛 offset을 쓴 오류를 설명한다. 마지막으로 독립 후보 확률 (1/2,1/4,1/8,1/8)의 두 실행 일치 확률을 구하고 실제 적재/무작위화 인증과 구별하라.

힌트 1

파일 offset은 해당 지도 행의 값에 행 시작에서의 차를 더한다. B 요청의 RUNPATH는 libA 기준으로 검사한다.

힌트 2

주소 기록은 같은 이미지 버전인지 확인한다. 두 실행 일치에는 네 후보 각각의 확률 제곱을 더한다.

풀이와 답 확인

  1. 둘째 행의 파일 위치는 0x3000+0x180=0x3180이다. 가상 크기의 합은 0x2000+0x1000=12 KiB이며 실제 RAM의 고유 사용량은 미확정이다.

  2. A는 app의 /pkg에서 발견된다. B에는 app RUNPATH가 상속되지 않아 실패하며 libA RUNPATH=/pkg가 지정 모형의 해결 방법이다. 파일 발견 뒤 호환성 검증은 별도다.

  3. V1에서 F의 주소는 0x90100이고 G의 주소는 0x90180이므로 상대 차는 128바이트다. V2에서 지정한 F의 주소는 0x90140이다. 여기에 옛 offset을 적용하면 64바이트 작은 위치를 얻는다.

  4. 두 실행 일치 확률은 1/4+1/16+1/64+1/64=11/32다. 실제 loader/ASLR 상태·PIE 빌드·보호 효과를 인증한 값이 아니다.

대응 파일 바이트는 0x3180이고 가상 크기의 합은 12 KiB다. libA 자체에 RUNPATH를 추가해 직접 B 요청을 해결한다. V1에서 F의 주소는 0x90100이고 G의 주소는 0x90180이다. V2에서 옛 offset을 쓰면 주소가 64바이트 작아진다. 지정한 두 실행의 반복 확률은 11/32다. 실제 파일·프로세스·메모리·보안·학생 시험은 미수행이다.

해결한 뒤 점검할 것

  • 지도 파일 위치와 가상 크기를 분리하여 계산한다.

  • libA의 직접 요청을 기준으로 경로 수정 책임을 제시한다.

  • 발견과 ABI/심볼·실제 적재 성공을 분리한다.

  • base 이동과 이미지 버전 변경을 서로 다른 조건으로 다룬다.

  • 확률의 독립/분포 조건 및 실제 ASLR 미수행을 명시한다.

전체 base 세 소단원과 새 보강의 지도·권한, 여섯 예제, 열두 과제 및 전이를 손으로 검산했다. 파일 위치는 각각 0x180, 0x3180, 0x3fff이고 가상 크기는 3페이지다. 상주 페이지 중복에 따른 두 분모, A의 직접 발견과 B의 경로 실패를 확인했다. V1의 두 주소 사이 차이는 128바이트이며 V2의 옛 offset 오류는 64바이트다. 균일 선택의 두 실행 반복 확률은 1/4이고 세 실행은 1/16이다. 비균일 선택의 두 실행 반복 확률은 11/32이고 지정한 조건부 확률은 1/2다. 새로운 계산 코드 실행은 하지 않았다.
