소단원 13.1

블록 헤더와 자유 목록

free는 크기를 받지 않는데 어떤 블록을 되돌려야 하는지 어떻게 알까?

준비 개념과 학습 목표

준비 개념

  • 바이트 주소와 반열린 구간

  • C 포인터와 동적 수명

  • 배수로 올림

학습 목표

  • 요청 바이트와 전체 블록 크기를 구별한다.

  • 헤더와 자유 목록의 역할을 설명한다.

  • 명시된 정렬 모형에서 반환 주소를 계산한다.

블록 크기의 배수와 반환 데이터 주소의 정렬은 같은 검사인가?

새 종이 할당기는 헤더가 8바이트지만 반환 데이터는 16바이트 정렬을 요구한다. 힙의 첫 블록은 오프셋 8에서 시작하며 전체 크기는 16의 배수다. 블록 시작을 s라고 하면 반환 위치는 s+8이다. 따라서 s가 16의 배수라는 규칙을 쓰면 오히려 데이터가 8만큼 어긋난다. 시작의 나머지가 8이고 모든 전체 크기가 16의 배수일 때 그 다음 블록도 같은 나머지를 유지한다.

전체 필요 크기는 A(n)=16 ceil((n+8)/16)이다. 양의 요청만 다루며 관리 링크는 표 밖에 있어 자유 조각의 최소 전체 크기도 16바이트로 정한다. 이 규칙은 base의 8바이트 정렬 모형과 다른 비교 계약이다. 힙 [8,136)은 128바이트며 힙 앞의 [0,8)은 관리 대상이 아니다. 실제 malloc 헤더나 ABI를 읽거나 실행한 것은 아니다.

요청 바이트는 할당 세대와 함께 추적한다. 해제한 뒤 같은 숫자 위치가 다른 요청에 다시 반환돼도 이전 객체의 수명이 다시 시작한 것은 아니다. 아래 세대 번호는 종이 검사기의 정보이며 일반 C 포인터가 자동으로 이런 번호를 담는다는 뜻은 아니다.

먼저 확인할 개념
  • 헤더·전체 블록·반환 위치

    base의 크기 올림과 요청 구간을 읽은 뒤 새 정렬 계약과 비교한다.

  • 요청 범위와 할당 수명

    주소 숫자의 재사용이 원래 객체의 접근 권한을 복구하지 않음을 구별한다.

사용 공간 앞뒤에 관리 정보가 있다

동적 할당기는 실행 중 필요한 크기의 공간을 마련한다. 프로그램이 받는 포인터는 사용할 데이터 공간을 가리킨다. 관리용 헤더에는 블록 크기나 사용 여부를 저장할 수 있다. 구체 배치와 정렬은 구현마다 다르므로 특정 라이브러리의 내부 헤더를 임의로 읽는 C 코드는 이 이론 예제와 다르다.

아래 종이 모형은 오프셋 0부터 96바이트, 8바이트 정렬, 8바이트 헤더, 푸터 없음이다. 전체 블록 크기는 요청+8을 8의 배수로 올린다. 사용 블록의 요청 길이는 따로 표에 기록한다. 이 규칙은 실제 C ABI나 malloc 구현을 주장하지 않는다.

다음 블록과 자유 목록의 다음 노드는 다르다

전체 블록 크기를 알면 현재 시작 주소에 크기를 더해 물리적으로 이웃한 블록을 찾을 수 있다. 크기와 상태를 따라 모든 블록을 순회하는 방식과 자유 블록만 연결하는 방식은 탐색 대상이 다르다. 자유 목록은 사용 가능한 공간을 찾기 위한 관리 자료다.

자유 목록의 연결 순서는 주소 순서일 수도 있지만 반드시 그렇지는 않다. 연결상 이웃이라는 이유만으로 메모리에서 붙어 있다고 생각하지 않는다. 이 수업의 목록 노드는 블록 표 밖에 별도 저장한다고 가정해 최소 자유 블록 크기 8바이트를 허용한다. 실제 링크를 자유 블록 안에 넣으면 더 큰 최소 크기가 필요할 수 있다.

반환한 포인터와 수명 계약을 지킨다

free에 넘길 값은 해당 할당 방식의 계약에 맞는 원래 포인터다. 배열 중간 주소나 이미 되돌린 포인터를 다시 넘기는 것은 올바른 해제가 아니다. free(NULL)은 C에서 아무 동작도 하지 않는 경우로 구별한다. 해제 뒤 값에 접근할 권리가 사라지는 것이지 변수에 남은 숫자가 자동으로 지워지는 것은 아니다.

요청 실패를 확인하고 필요한 바이트 수 계산의 범위를 점검한다. 본 단원은 양수이고 작은 요청만 다루며 0바이트 요청의 반환 정책이나 큰 정수 곱셈을 실제 구현에 일반화하지 않는다. 메모리를 OS에 즉시 반환하는지도 할당기의 별도 정책이다.

첫 세 요청을 같은 힙에서 순서대로 할당한 표다. 시작은 모두 16으로 나눈 나머지가 8이고 반환은 모두 16의 배수다. 패딩과 헤더의 합을 패딩 하나로 보고하지 않는다.

중간 과정을 따라가는 예제

자체 96바이트 힙 모형에서 요청 A=13바이트, B=9바이트를 순서대로 앞쪽 자유 블록에서 할당한다. 8바이트 헤더·전체 크기 8의 배수·분할 가능 최소 8바이트다. 각 블록 구간과 반환 오프셋을 구하자.

  1. A는 13+8=21을 올림해 24바이트다. 블록 [0,24), 헤더 [0,8), 반환 주소 8, 요청 데이터 [8,21), 남는 패딩 [21,24)다.

  2. B는 9+8=17을 올림해 24바이트다. 블록 [24,48), 반환 주소 32, 요청 데이터 [32,41), 패딩 [41,48)다.

  3. 나머지 자유 블록은 [48,96)의 48바이트다. 전체 24+24+48=96이며 반환 주소 8/32 모두 8의 배수다.

A/B 반환 오프셋은 8/32, 전체 블록 크기는 24/24, 남는 자유 블록은 48바이트다. 실제 실행 주소가 아니다.

조건을 바꾸어 비교하기

한 바이트 증가로 두 배가 되는 전체 블록

요청 8과 9를 A(n)으로 비교하고 위 세 요청의 사용량을 구하라.

  1. 8+8=16이므로 전체 16이다. 9+8=17은 32로 올린다.

  2. 세 요청의 합은 41바이트, 헤더 합은 24바이트, 패딩 합은 15바이트다.

전체 사용은 80바이트이고 자유는 48바이트다. 41+24+15=80이며 세 반환 위치는 16,32,64다.

비교할 점

요청 증가 1바이트와 전체 증가 16바이트는 다른 양이다.

배수를 맞추었지만 반환은 틀린 배치

헤더 8·전체 32를 블록 시작 0에 놓고 16바이트 데이터 정렬을 주장했다. 수정하라.

  1. 반환은 0+8=8로 16의 배수가 아니다.

  2. 새 모형처럼 시작을 8로 두면 반환 16이고 다음 시작도 40으로 나머지 8이다.

전체 크기 검사와 반환 주소 검사를 함께 해야 한다. 여기의 오프셋 조정은 새 종이 배치이며 실제 할당기 구현을 고친 결과가 아니다.

비교할 점

크기의 정렬만으로 반환 주소의 정렬이 따라오지 않는다.

종이와 본문으로 직접 해보기

같은 초기 모형에서 첫 요청을 17바이트로 바꾸자. 그 뒤 9바이트 요청을 할당하면 두 반환 주소와 남는 자유 구간은 무엇인가?

힌트 보기

17+8을 먼저 올림한다. 두 번째 블록 시작은 첫 전체 블록 크기다.

풀이 보기

첫 전체 크기는 32, 반환 주소는 8이다. 둘째 전체 크기는 24, 시작 32·반환 40이다. 자유 블록 [56,96)은 40바이트이며 32+24+40=96이다.

오해와 반례

요청이 13바이트면 할당기에서 차지하는 전체 공간도 정확히 13바이트다.

자체 모형에서는 헤더와 정렬 패딩을 더해 24바이트다. 요청 데이터 크기·전체 블록·관리 자료의 범위를 따로 적는다.

스스로 풀어보기

먼저 답과 이유를 적고, 필요한 만큼 힌트를 한 단계씩 열어 보세요.

연습 1 · 값과 상태 예측

위 표의 요청 9만 10으로 바꾸면 전체 크기·반환 위치·패딩은 어떻게 되는가?

힌트 1

10+8을 16의 배수로 올린다.

힌트 2

블록 시작 24와 전체 크기가 그대로인지 비교한다.

풀이와 답 확인

  1. 전체 크기는 여전히 32바이트다.

  2. 반환 위치는 32이고 패딩은 32−8−10=14바이트다.

후속 요청 24의 시작 56과 반환 64 및 자유 48바이트는 같다.

흔한 오답에서 다시 생각하기

요청이 1 늘었으므로 모든 다음 주소도 1씩 늦춘다.

정렬된 전체 크기가 바뀐 경우에만 다음 시작이 이동한다.

연습 2 · 오류 찾아 고치기

세 요청의 비요청 공간 39바이트를 모두 정렬 패딩이라고 보고했다. 고쳐라.

힌트 1

전체 80에서 요청 41을 뺀다.

힌트 2

각 블록에 헤더 8바이트가 있다.

풀이와 답 확인

  1. 비요청 공간은 39바이트다.

  2. 그중 헤더 24와 패딩 15를 별도 열로 분리한다.

39=24+15이며 자유 48은 사용 블록 안의 낭비가 아니다.

흔한 오답에서 다시 생각하기

힙 전체 128에서 요청 41을 뺀 87이 패딩이다.

자유 공간 48과 사용 블록의 비요청 공간 39는 다른 상태다.

연습 3 · 직접 만들어 보기

위 첫 요청을 해제하고 같은 자리에 새 요청 8을 할당한 두 세대를 기록하라. 이전 별칭의 안전성을 판정하라.

힌트 1

옛 세대 A와 새 세대 D를 이름으로 구별한다.

힌트 2

두 반환 위치는 같아도 live 객체 이름이 바뀐다.

풀이와 답 확인

  1. A의 반환 16은 해제로 수명이 끝난다.

  2. 새 D도 반환 16이지만 검사기의 객체는 D다.

옛 A 별칭을 숫자만 보고 D의 유효 포인터로 되살리는 판단은 거절한다. 실제 C에서 해제된 포인터를 평가하거나 사용해 시험하지 않는다.

흔한 오답에서 다시 생각하기

같은 주소를 다시 받았으므로 모든 옛 별칭도 합법이다.

주소 숫자의 재사용과 할당 세대·수명은 별개다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

모든 양의 n에 대해 패딩 범위와 시작 나머지 불변식을 증명하라.

힌트 1

올림 전 n+8과 다음 16의 배수 차이를 센다.

힌트 2

s가 나머지 8이면 s+A(n)도 나머지 8이다.

풀이와 답 확인

  1. 0≤A(n)−(n+8)≤15다.

  2. s≡8 mod16과 A(n)≡0 mod16에서 다음 시작도 8이며 반환 s+8≡0이다.

패딩은 0–15바이트이고 데이터 정렬은 시작 불변식과 전체 크기 규칙을 함께 써서 증명한다.

흔한 오답에서 다시 생각하기

헤더 8바이트이므로 패딩도 항상 8 이하다.

패딩은 헤더 크기가 아니라 16바이트 올림의 나머지로 결정된다.

분할·병합·단편화

빈 바이트의 합은 충분한데 왜 큰 요청 하나를 못 받을까?

준비 개념과 학습 목표

준비 개념

  • 사용/자유 상태

학습 목표

  • 내부 공간 낭비와 외부 단편화를 구별한다.

  • 합계와 가장 큰 자유 블록을 함께 계산한다.

목록을 바꾸면 첫 맞춤의 성공과 병합 결과가 바뀌는가?

별도의 새 128바이트 힙은 [0,32) 자유, [32,48) 사용, [48,72) 자유, [72,88) 사용, [88,128) 자유다. 이번 모형은 헤더 8바이트·전체 크기 8의 배수·최소 자유 조각 16바이트이며 자유 링크는 표 밖이다. 요청 9는 전체 24가 필요하다. first fit의 선택은 명시한 자유 목록 순서에 따른다.

목록 [88,48,0]에서 first fit은 40바이트 블록을 고르고 잔여 16을 남긴다. 주소순 목록 [0,48,88]에서는 32바이트를 골라 잔여 8이 최소 16보다 작으므로 전체 32를 사용한다. best fit은 초기 24바이트 블록을 골라 잔여 0을 만든다. 한 흐름에서의 공간 결과를 모든 미래 요청에서 최적이라는 보증으로 일반화하지 않는다.

병합은 주소의 인접성으로 결정한다. 자유 목록에서 연속 등장한 88과 48은 중간 사용 [72,88)을 건너 합칠 수 없다. 즉시 병합 정책에서 이 사용 블록을 해제하면 양옆 자유 블록까지 함께 합칠 수 있다. 주소순은 이런 탐색을 돕지만 주소순으로 정렬한 것 자체가 해제를 수행하지는 않는다.

필요한 만큼 나누되 조각의 조건을 지킨다

분할은 큰 자유 블록을 사용 블록과 남는 자유 블록으로 나누는 작업이다. 남는 조각이 관리 가능한 최소 크기보다 작으면 전체 블록을 사용으로 잡는 정책을 둘 수 있다. 요청 크기만 빼면 헤더나 정렬을 놓치므로 전체 크기를 먼저 계산한다.

앞 절과 같은 자체 규칙을 쓴다. 필요한 크기 24를 자유 블록 32에서 받으면 8바이트 자유 조각을 남길 수 있다. 최소 크기를 별도로 16으로 바꾼 비교 모형에서는 남은 8이 너무 작아 전체 32를 사용한다. 한 예제의 최소 크기와 다른 예제의 규칙을 섞지 않는다.

붙어 있는 자유 블록을 다시 합친다

병합은 주소상 인접하고 둘 다 자유인 블록을 하나로 만드는 작업이다. 왼쪽 끝에 크기를 더한 값이 오른쪽 시작과 같아야 인접하다. 사용 블록을 가로질러 합치거나 살아 있는 데이터의 주소를 마음대로 옮기는 작업과 다르다.

분할과 병합을 각각 언제 할지도 정책이다. 아래 모형은 해제할 때 즉시 이웃 자유 블록을 병합한다. 양쪽이 자유면 세 블록을 합친다. 실제 구현의 경계 태그·검색 자료·잠금 비용을 이 작은 표만으로 측정했다고 말하지 않는다.

공간 낭비의 분모를 적는다

외부 단편화는 자유 공간이 떨어져 있어 한 연속 요청을 담지 못하는 문제다. 전체 자유량만으로 성공을 판정하지 않는다. 내부 공간 낭비는 할당된 블록 안에서 요청 외에 차지하는 공간이다. 자료마다 헤더를 포함하는 정의가 달라질 수 있어 본문은 헤더·패딩·전체 비요청 공간을 따로 표시한다.

배치 정책은 결과에 영향을 준다. first fit은 목록 순서에서 처음 맞는 블록을 고르므로 목록 순서를 적어야 재현할 수 있다. 특정 표에서 낭비가 적다고 모든 요청 흐름에서 항상 가장 좋은 정책이라고 일반화하지 않는다.

중간 과정을 따라가는 예제

앞 절의 A=[0,24), B=[24,48), 자유=[48,96)에서 A만 해제한다. 요청 C=49바이트가 성공하는가? 이어 B도 해제하고 즉시 인접 병합한 뒤 같은 요청을 비교하자. 힙 확장은 없다.

  1. A 해제 후 자유 크기는 24와 48, 합계 72바이트다. C는 49+8=57을 64로 올려야 한다. 가장 큰 자유 블록 48이 64보다 작아 실패한다.

  2. B도 해제하면 [0,24), [24,48), [48,96)이 모두 자유이며 인접하다. 즉시 병합하면 [0,96) 하나가 된다.

  3. C의 전체 64바이트를 [0,64)에 할당하고 [64,96)의 32바이트가 남는다. 반환 주소 8, 요청 공간 [8,57), 패딩 [57,64) 7바이트다.

A만 해제하면 총 자유 72에도 C는 실패한다. B 해제 후 병합하면 성공하고 자유 32가 남는다.

조건을 바꾸어 비교하기

합계는 줄어도 큰 요청이 되는 선택

세 정책 뒤 추가 요청 25의 성공 여부를 비교하라. 힙 확장은 없다.

  1. 추가 필요 크기는 25+8=33을 올린 40바이트다.

  2. 역순 first fit 뒤 최대 자유 32라 실패한다. 주소순 first fit과 best fit 뒤는 40이 남는다.

첫 정책은 자유 합 72에도 실패한다. 나머지 둘은 성공하며 40바이트 블록을 전부 쓴다. 주소순 첫 정책은 최초 요청에서 8바이트 더 사용했지만 이 추가 요청은 성공한다.

비교할 점

현재 내부 낭비 최소와 미래 큰 요청 성공은 같은 목표가 아니다.

목록 이웃이 아닌 실제 양옆을 병합하기

초기 상태에서 사용 [72,88)을 해제하고 즉시 병합하라.

  1. 왼쪽 자유 [48,72)와 새 자유 [72,88), 오른쪽 자유 [88,128)이 붙어 있다.

  2. 24+16+40=80으로 [48,128)을 만든다. [0,32)는 [32,48) 사용 때문에 떨어져 있다.

자유 블록은 [0,32)와 [48,128), 합 112·최대 80이다. 아직 살아 있는 중간 16바이트를 포함한 전체 병합은 불법이다.

합계·집합·도구 무경고 중 어느 검사가 놓치는 오류인가?

새 상태는 96바이트 힙을 [0,24) 사용·[24,48) 자유·[48,72) 사용·[72,96) 자유로 나눈다. 사용 요청은 각각 9바이트와 8바이트이고 반환 위치는 8과 56이다. 자유 목록의 정상 주소는 24와 72다. 블록 크기 합 96과 자유 노드 집합만 검사하면 중복·덮개 오류·정책 오류를 모두 잡는 것은 아니다.

불변식의 층을 나눈다. 구간의 정렬·양수 크기·끝점 연결·힙 덮개, 자유 목록의 시작/상태/정확히 한 번/비순환, 사용 객체의 요청 경계·초기화·세대·소유 추적을 별도로 검사한다. 구조 검사가 통과해도 요청 끝을 넘어 쓰는 응용 오류가 있을 수 있다. 반대로 아직 값을 쓰지 않은 바이트가 있다고 블록 목록의 구조가 깨진 것도 아니다.

Memcheck의 관찰은 실행된 접근과 값 사용을 중심으로 한다. 사용자 정의 할당기의 세부 요청을 도구가 모르면 큰 backing 공간 안의 경계를 도구가 자동으로 추론한다고 보장할 수 없다. 여기서는 모든 사건을 종이 객체 장부로 판정하며 실제 오류 로그를 생성하지 않는다. 유효 주소인지와 초기화된 값인지도 다른 검사다.

  • 반환 주소와 요청 데이터 구간

    전체 블록 안의 패딩을 요청 객체의 일부로 취급하지 않는다.

할당기 검사기는 구조의 약속을 확인한다

자체 검사기는 블록들이 힙 구간을 빠짐없이 겹치지 않게 덮는지, 크기가 양수이고 정렬 배수인지, 사용/자유 상태가 올바른지 확인한다. 즉시 병합 정책이라면 인접한 자유 블록이 남아 있지 않아야 한다. 정책을 먼저 적어야 지연 병합 구현을 잘못된 것으로 판정하지 않는다.

명시적 자유 목록의 각 노드가 실제 자유 블록 시작인지, 모든 자유 블록이 정확히 한 번 포함되는지, 순환이 없는지도 확인한다. 합계가 맞아도 중복 노드나 누락이 있을 수 있다. 이 목록 검사는 응용의 모든 포인터가 유효하다는 증명과는 다르다.

요청 경계와 할당기 경계는 같지 않다

A의 요청 데이터가 [8,21)이면 오프셋 21은 패딩 안이지만 요청한 13바이트 바깥이다. 전체 블록 안에 있다는 이유로 C 프로그램에 접근 권한이 생기지 않는다. 해제 뒤 원래 주소에 접근하는 use-after-free, 원래 포인터가 아닌 해제, 중복 해제를 구별한다.

초기화하지 않은 값을 계산 조건에 사용하는 문제와 반환할 수 있는 공간을 더 이상 추적하지 못하는 누수도 구별한다. 한 오류를 고쳤다고 다른 종류가 사라지지 않는다. 아래 기록은 실제 잘못된 C 코드를 실행하는 대신 수명과 요청 범위를 표로 판정한다.

도구 기록에는 실행 범위를 함께 적는다

Memcheck 같은 도구는 잘못된 접근·미초기화 사용·잘못된 해제 등을 실행 관찰로 찾는 데 도움을 준다. 관찰한 입력 경로 밖의 모든 동작까지 자동 증명하는 것은 아니다. 실제 실행하지 않은 로그를 출력 예시처럼 꾸미지 않는다.

직접 만든 할당기를 검사할 때는 요청별 상태·가장 이른 실패 단계·불변식·재현 입력을 기록한다. 이 단원은 종이 검사만 했으므로 실행 바이너리·도구 버전·실제 경고·성능 칸은 미수행이다. 선택 실습에서는 별도 안전한 작은 테스트 프로그램을 실제 실행한 뒤 결과를 구별해 기록한다.

중간 과정을 따라가는 예제

자체 블록 표는 [0,24) 자유, [24,48) 사용, [48,96) 자유다. 자유 목록 노드 시작을 L=[0,48,48]로 기록했다. 크기/덮개와 목록을 검사하자. 별도 손상 표에서는 마지막 크기를 40으로 잘못 기록했다.

무경고 기록의 해당 범위만 보고하며 전체 안전 증명으로 올리지 않는다. 여기서는 실제 도구 실행도 없으므로 경고 수를 결과로 기재하지 않는다.
