소단원 10.1

작업제약과 scheduling

업로드 예약을 했는데 왜 정확히 그 시각에 실행되지 않을까?

준비 개념과 학습 목표

준비 개념

  • 논리 AND

  • 앱과 운영체제

학습 목표

  • 실행 제약과 최소 지연을 시간선에서 판정한다.

  • 예약 가능 시점과 실제 실행 완료를 구별한다.

할 일과 조건을 함께 예약

앱 화면이 잠시 사라져도 나중에 수행할 지속 작업에는 운영체제가 관리하는 예약 방식을 사용한다. Android WorkManager는 제약·지연·재시도 같은 계약을 기록한다. 즉시 화면 응답, 정시 알람, 모든 종류의 긴 실행을 하나의 worker로 해결한다고 가정하지 않는다.

네트워크 종류, 충전 여부, 배터리·저장 공간 등의 제약을 함께 설정하면 모든 조건이 만족될 때 실행 대상이 된다. 조건은 곧 실행의 보장이 아니라 시작 가능 여부를 가르는 필터다. 시스템 최적화·다른 작업·기기 상태가 실제 시작 시간을 바꿀 수 있다.

지연과 중지의 의미

초기 지연은 그 시간이 지나기 전 시작하지 말라는 최소 대기다. 그 시각에 반드시 완료하라는 마감 시간이 아니다. 주기 작업의 간격도 정확한 벽시계 실행 시각과 다르므로 사용자가 반드시 정시에 알아야 할 알림과 구별한다.

실행 도중 제약이 사라지면 WorkManager는 worker를 중지하고 조건이 회복될 때 재시도할 수 있다. 작업이 일부 진행된 뒤 다시 시작되는 경우를 고려해 진행 기록과 서버의 중복 방지 계약을 설계한다. 중지 통보가 외부 서버 작업까지 되돌린다는 뜻은 아니다.

시간선으로 계약 읽기

다음 표의 C는 충전 중, N은 필요한 네트워크이며 AND를 쓴다. 지연 10분이 추가되면 t≥10도 함께 만족해야 한다. 실제 Android API를 호출하지 않고 각 관측 시점의 예약 조건만 판정한다.

기기별 정책과 OS 버전은 바뀔 수 있다. 이 본문은 확인한 WorkManager 문서의 조건을 사용하고 표의 관측값은 자체 교육 가정이다. 처음 가능했던 시점과 관측한 시작·완료 시각을 다른 칸에 적으면 지연의 원인을 구별하기 쉽다.

중간 과정을 따라가는 예제

t=0에 작업을 등록하고 최소 지연10분·충전C·네트워크N을 요구한다. t=5:(C1,N1), t=10:(C1,N0), t=12:(C1,N1). 관측점 중 처음 실행 대상이 되는 시점은?

  1. t5는 C/N이 참이어도 지연이 덜 지났다.

  2. t10은 지연은 지났지만 N이 거짓이다.

  3. t12에서 시간·C·N이 모두 참이다.

관측점 중 t12분이 최초 실행 가능이다. 실제 시작/완료 시각은 이 표로 보장하지 않는다.

종이와 본문으로 직접 해보기

힌트 보기

실행 중 제약이 깨지는 문서 계약을 적용한다.

풀이 보기

그렇게 가정하지 않는다. worker 중지와 조건 회복 후 재시도를 고려해야 하며 이미 수행한 외부 변경은 별도 확인한다.

오해와 반례

최소 지연10분을 넣으면 등록10분 뒤 반드시 끝난다.

10분은 가장 빠른 시작 제한이다. 실행 시간·제약·스케줄링이 추가된다.

소단원 10.2

배터리·백그라운드 제한

앱 하나의 깨우기가 작아 보여도 왜 휴대폰 전체에서 문제가 될까?

준비 개념과 학습 목표

준비 개념

  • 시간 간격과 횟수

  • CPU와 네트워크 사용

학습 목표

  • Doze와 App Standby를 구별한다.

  • 깨우기 횟수의 교육 예산과 실제 배터리 측정을 구별한다.

기기의 휴식을 공유하기

배경 앱마다 자주 CPU·네트워크를 깨우면 사용자가 보지 않는 동안에도 자원을 소비한다. Android의 Doze는 기기 미사용 중 배경 CPU와 네트워크 활동을 미루고 maintenance window에 일부 지연 작업을 진행하게 한다. 일반 job·동기화·알람의 실행에도 제한이 있다.

App Standby는 최근 사용자 활동이 적은 앱의 배경 네트워크 활동을 미루는 판단이다. 화면이 안 보이는 것, 프로세스가 종료된 것, Doze인 것은 같은 상태가 아니다. 배경에 있다고 모든 작업이 항상 금지되거나 항상 허용된다는 두 극단을 피한다.

작업을 묶는 이유와 대가

몇 개의 작은 요청을 한 번에 모으면 깨우기 고정비를 줄일 수 있다. 하지만 최신 자료를 보여 주는 시간이 늦어질 수 있으므로 횟수 절감과 사용자 대기 시간을 함께 적는다. 실제 무선 장치의 비용은 전송량·신호·상태 전환 등에 따라 달라진다.

foreground service는 사용자가 기대하는 즉시 또는 지속 작업을 위한 기능이다. 앱이 idle로 판단되지 않게 하려는 목적으로만 만들지 않는다. 중요한 알림 메시지도 적절한 플랫폼 경로와 정책을 적용해야 하며 이 수업은 제한 우회 코드를 작성하지 않는다.

예산 모형의 경계

아래는 1시간 동안 고정 주기를 완전히 따라간다고 가정한 종이 예산이다. 매 깨어남 비용2단위, 자료1건 처리비1단위이며 실제 Android가 그 주기를 보장한다는 뜻이 아니다. 비용 단위는 joule이나 배터리 퍼센트가 아니다.

Doze가 15분마다 창을 반드시 연다는 식의 숫자를 이 예산에서 추론하면 안 된다. 실제 성능 확인에는 버전·기기·절전 상태·실행 기록이 필요하다. 그런 장비 실험은 아직 수행하지 않고 횟수 모델만 계산한다.

중간 과정을 따라가는 예제

1시간에 자료12건이 생긴다. A는 매5분1건씩12번 깨어나고 B는 매15분3건씩4번 깨어난다고 가정한다. 고정비2/회, 처리비1/건이면 비용은?

  1. A의 고정비12×2=24, 처리비12×1=12다.

  2. B의 고정비4×2=8, 처리비12다.

  3. 자료 수는 같고 고정비만 달라진다.

A36단위, B20단위, 차이16단위. 실제 배터리 절감률은 아니다.

종이와 본문으로 직접 해보기

B의 묶음을30분6건씩2번으로 바꾸면? 자료가 묶음 직후 생기면 추가 대기는 어느 정도까지 가능하나?

힌트 보기

처리건수12는 유지하고 깨어남만 다시 센다.

풀이 보기

2×2+12=16단위다. 교육 정시 주기에서 자료는 다음 묶음까지 거의30분 기다릴 수 있다. 실제 스케줄 지연은 더해질 수 있다.

오해와 반례

백그라운드 예약 간격이15분이면 Doze에서도 매15분 실행된다.

주기와 OS의 maintenance window는 다르다. Doze 동안 WorkManager job도 미뤄질 수 있다.

소단원 10.3

알림과 사용자제어

알림을 보냈다는 로그가 있는데 사용자가 안 봤다면 무엇이 빠졌을까?

준비 개념과 학습 목표

준비 개념

  • 권한과 상태

  • AND 조건

학습 목표

  • 앱 권한과 채널·사용자 설정을 구별한다.

  • 알림의 요청·표시·열람을 별도 사건으로 기록한다.

보낼 수 있는가를 먼저 묻기

Android13 이상 새로 설치한 앱의 일반 알림은 런타임 권한을 받아야 한다. 사용자가 허용·거절·대화상자 닫기를 선택할 수 있으며 닫기는 기존 권한 상태를 바꾸지 않는다. 면제되는 알림 역할도 있으므로 이 단원은 일반 학습 알림만 다룬다.

학습자가 알림이 필요한 순간을 이해하도록 설명하고 거절해도 앱 안에서 자료를 찾아볼 수 있게 설계한다. 알림 권한은 자료 읽기 권한이나 서버 로그인 권한과 별개다. 허용 상태도 나중에 사용자가 바꿀 수 있다.

주제별 채널과 사용자 선택

Android8 이상 알림 채널은 주제별 시각·소리 동작을 구분하는 통로다. 학습 일정과 새 자료 소식을 다른 채널로 나누면 사용자가 원하지 않는 주제만 끌 수 있다. 채널 중요도를 생성한 뒤 앱이 마음대로 바꿔 사용자 선택을 덮어쓸 수 있다고 생각하지 않는다.

권한과 채널이 켜져 있어도 OS·방해금지·잠금 화면 등 다른 표시 조건이 존재한다. 민감한 내용을 알림 본문에 넣는 것은 잠금 화면에서 노출될 수 있다. 앱 내부 설정은 설명·선택을 돕고 시스템 설정과 실제 상태를 확인해야 한다.

성공을 여러 단계로 나누기

예약 완료, 서버 발송, 기기 수신, 표시, 사용자가 열람한 시점은 다르다. API 요청이 성공했다고 사람이 읽었다는 결론을 내리면 알림 기능의 성공률을 잘못 해석한다. 읽음 여부를 알 수 없다면 미확인으로 둔다.

아래 P는 일반 알림 권한, C는 채널 활성, U는 사용자의 앱 내부 알림 선택이다. 교육 모형의 발송 허용은 P AND C AND U이며 OS의 다른 조건은 만족했다고 가정한다. 실제 기기나 푸시 서비스에 메시지를 보내지 않는다.

중간 과정을 따라가는 예제

관측 상태 A:(P1,C1,U1), B:(P1,C0,U1), C:(P0,C1,U1)이다. 일반 학습 알림을 보내도록 허용할 상태는?

  1. A는 세 값 모두 참이다.

  2. B는 채널이 꺼져 있고 C는 권한이 없다.

  3. 이 표는 앱의 허용 판정이며 사람의 열람 증명은 아니다.

A만 허용하고 B/C는 차단한다. A도 실제 표시·열람은 별도 확인이다.

종이와 본문으로 직접 해보기

새 설치 권한P0에서 사용자가 권한창을 버튼 없이 닫았다. 채널C1, 내부U1이면 허용되나?

힌트 보기

닫기는 권한을 허용으로 바꾸지 않는다.

풀이 보기

P0 유지이므로0 AND1 AND1=0이다. 앱 내 자료 안내와 나중의 자발적 설정 변경 경로를 제공한다.

오해와 반례

알림 API 호출 성공이면 학생이 읽었다.

기기 수신·표시·사용자 열람은 서로 다른 관측이다. 확인하지 않은 읽음은 미확인이다.

자기점검

답과 이유 보기
