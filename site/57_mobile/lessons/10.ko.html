소단원 10.1

작업제약과 scheduling

업로드 예약을 했는데 왜 정확히 그 시각에 실행되지 않을까?

준비 개념과 학습 목표

준비 개념

  • 논리 AND

  • 앱과 운영체제

학습 목표

  • 실행 제약과 최소 지연을 시간선에서 판정한다.

  • 예약 가능 시점과 실제 실행 완료를 구별한다.

세 번의 관측이 같으면 실제 실행 가능 시간도 같을까?

자체 예약은 t=0분에 등록하며 최소 지연은 10분이다. 충전 C와 필요한 네트워크 N도 모두 참이어야 한다. t=5에서 C1,N1, t=10에서 C1,N0, t=12에서 C1,N1이라는 세 관측만으로는 관측 사이의 상태를 알 수 없다. t=12는 주어진 관측점 중 최초 가능점이며 실제로 처음 가능했던 시점과 반드시 같지는 않다.

구간까지 알려 주는 두 시간선을 비교한다. C는 내내 참이고 A의 N은 [0,10)에서 참, [10,12)에서 거짓, [12,20)에서 참이다. B의 N은 [0,9)에서 참, [9,9.5)에서 거짓, [9.5,10)에서 참, [10,10.5)에서 거짓, [10.5,20)에서 참이다. 두 시간선의 t=5,10,12 관측은 같지만 처음 가능했던 시점은 A에서 12분, B에서 10.5분이다. 구간의 왼쪽 끝은 포함하고 오른쪽 끝은 제외한다.

실행 가능과 실제 시작·완료도 나눈다. A에서 시작 13분, 중지 통보 14분, 서버 반영 13.8분, 다음 시도 시작 18분을 가상 사건으로 주었다고 하자. 중지 통보는 이미 생긴 서버 반영을 되돌리는 명령이 아니다. 다음 시도는 같은 작업 ID와 서버의 중복 방지 계약으로 결과를 확인해야 한다. 아래 시각은 자체 시간선이며 실제 WorkManager 측정값이나 실행 시각 보장이 아니다.

할 일과 조건을 함께 예약

앱 화면이 잠시 사라져도 나중에 수행할 지속 작업에는 운영체제가 관리하는 예약 방식을 사용한다. Android WorkManager는 제약·지연·재시도 같은 계약을 기록한다. 즉시 화면 응답, 정시 알람, 모든 종류의 긴 실행을 하나의 worker로 해결한다고 가정하지 않는다.

네트워크 종류, 충전 여부, 배터리·저장 공간 등의 제약을 함께 설정하면 모든 조건이 만족될 때 실행 대상이 된다. 조건은 곧 실행의 보장이 아니라 시작 가능 여부를 가르는 필터다. 시스템 최적화·다른 작업·기기 상태가 실제 시작 시간을 바꿀 수 있다.

지연과 중지의 의미

초기 지연은 그 시간이 지나기 전 시작하지 말라는 최소 대기다. 그 시각에 반드시 완료하라는 마감 시간이 아니다. 주기 작업의 간격도 정확한 벽시계 실행 시각과 다르므로 사용자가 반드시 정시에 알아야 할 알림과 구별한다.

실행 도중 제약이 사라지면 WorkManager는 worker를 중지하고 조건이 회복될 때 재시도할 수 있다. 작업이 일부 진행된 뒤 다시 시작되는 경우를 고려해 진행 기록과 서버의 중복 방지 계약을 설계한다. 중지 통보가 외부 서버 작업까지 되돌린다는 뜻은 아니다.

시간선으로 계약 읽기

다음 표의 C는 충전 중, N은 필요한 네트워크이며 AND를 쓴다. 지연 10분이 추가되면 t≥10도 함께 만족해야 한다. 실제 Android API를 호출하지 않고 각 관측 시점의 예약 조건만 판정한다.

기기별 정책과 OS 버전은 바뀔 수 있다. 이 본문은 확인한 WorkManager 문서의 조건을 사용하고 표의 관측값은 자체 교육 가정이다. 처음 가능했던 시점과 관측한 시작·완료 시각을 다른 칸에 적으면 지연의 원인을 구별하기 쉽다.

중간 과정을 따라가는 예제

t=0에 작업을 등록하고 최소 지연10분·충전C·네트워크N을 요구한다. t=5:(C1,N1), t=10:(C1,N0), t=12:(C1,N1). 관측점 중 처음 실행 대상이 되는 시점은?

  1. t5는 C/N이 참이어도 지연이 덜 지났다.

  2. t10은 지연은 지났지만 N이 거짓이다.

  3. t12에서 시간·C·N이 모두 참이다.

관측점 중 t12분이 최초 실행 가능이다. 실제 시작/완료 시각은 이 표로 보장하지 않는다.

조건을 바꾸어 비교하기

두 구간의 교집합

시간선 B에서 지연 조건과 N 조건을 동시에 만족하는 최초 시각은?

  1. t=9.5에서 N은 참이지만 지연 10분이 지나지 않았다.

  2. t=10에서 N은 거짓이다.

  3. t=10.5부터 N이 다시 참이며 C도 참이다.

최초 가능은 10.5분이다. 관측점만 보면 최초 가능 관측은 12분이다.

관측 간격에 숨은 상태 변화와 실제 실행 기록을 구별한다.

중지 뒤 외부 반영

가상 첫 시도의 서버 반영은 13.8분, worker 중지 통보는 14분이다. 다음 시도가 새 ID로 같은 변경을 보내면 왜 위험할까?

  1. 첫 서버 반영은 중지보다 앞서 있다.

  2. 중지 통보만으로 원격 반영이 취소됐다고 판단할 수 없다.

  3. 새 ID는 서버가 별도 작업으로 취급할 수 있다.

같은 업무 작업의 ID와 결과 확인 규칙을 유지하고 이미 반영됐는지 확인한다. 이 종이 사건표는 실제 서버의 멱등성을 증명하지 않는다.

연습 1 · 값과 상태 예측

A에서 최소 지연을 11분으로 바꿨다. C/N의 전체 구간은 그대로다. 최초 가능은 언제인가?

힌트 1

t≥11 구간과 N이 참인 구간을 겹친다.

힌트 2

11분에는 N이 거짓이다.

풀이와 답 확인

  1. 11분은 지연 조건만 만족한다.

  2. 12분부터 C와 N도 동시에 참이다.

12분이다. 실제 시작 시각은 이 교집합만으로 정해지지 않는다.

흔한 오답에서 다시 생각하기

지연이 11분이면 정확히 11분에 실행한다.

지연과 다른 제약을 모두 만족해야 하며 스케줄링도 별도다.

연습 2 · 오류 찾아 고치기

t=5,10,12의 세 관측만 저장하고 실제 최초 가능 시각을 12분이라고 확정했다.

힌트 1

관측하지 않은 구간은 미확인이다.

힌트 2

A와 B는 같은 관측을 만든다.

풀이와 답 확인

  1. 표현을 관측점 중 최초 가능으로 고친다.

  2. 더 정확한 구간 기록이 없으면 최초 실제 가능 시각은 미확인으로 둔다.

관측의 해상도를 결과 설명에 반영한다.

요청을 적게 묶는 정책이 자료 수와 기다림까지 같을까?

자체 한 시간 구간은 (0,60]분이고 자료는 1,6,11,…,56분에 한 건씩 생긴다. 각 묶음 시각에 그 시각까지 도착한 미처리 자료를 즉시 처리한다고 가정한다. 5분 묶음은 5,10,…,60분에, 15분 묶음은 15,30,45,60분에 실행한다. 깨우기 고정비는 2단위, 처리비는 건당 1단위다. 이 비용은 실제 에너지 단위가 아니다.

5분 정책은 12회에 12건을 처리하며 비용은 12×2+12=36단위다. 각 자료의 대기는 4분이다. 15분 정책은 4회에 12건을 처리하며 비용은 4×2+12=20단위다. 첫 묶음의 대기는 14,9,4분이고 이 패턴이 네 번 반복된다. 총 대기는 108분, 건당 평균은 9분이다. 비용은 줄었지만 자료를 오래 기다리는 경우가 늘었다.

같은 비교에서 자료가 끝까지 처리되었는지도 확인한다. 15분 정책에서 45분 묶음 하나만 생략되고 60분 묶음은 실행된다는 별도 시간선을 주면 처리량은 여전히 12건이다. 31,36,41분 자료가 추가로 15분씩 기다려 총 대기는 153분, 평균은 12.75분이다. 반면 마지막 60분 묶음이 생략되면 세 자료가 남는다. 이런 생략은 자체 가정이며 Doze 창이 15분마다 열린다는 플랫폼 규칙이 아니다.

기기의 휴식을 공유하기

배경 앱마다 자주 CPU·네트워크를 깨우면 사용자가 보지 않는 동안에도 자원을 소비한다. Android의 Doze는 기기 미사용 중 배경 CPU와 네트워크 활동을 미루고 maintenance window에 일부 지연 작업을 진행하게 한다. 일반 job·동기화·알람의 실행에도 제한이 있다.

App Standby는 최근 사용자 활동이 적은 앱의 배경 네트워크 활동을 미루는 판단이다. 화면이 안 보이는 것, 프로세스가 종료된 것, Doze인 것은 같은 상태가 아니다. 배경에 있다고 모든 작업이 항상 금지되거나 항상 허용된다는 두 극단을 피한다.

작업을 묶는 이유와 대가

몇 개의 작은 요청을 한 번에 모으면 깨우기 고정비를 줄일 수 있다. 하지만 최신 자료를 보여 주는 시간이 늦어질 수 있으므로 횟수 절감과 사용자 대기 시간을 함께 적는다. 실제 무선 장치의 비용은 전송량·신호·상태 전환 등에 따라 달라진다.

foreground service는 사용자가 기대하는 즉시 또는 지속 작업을 위한 기능이다. 앱이 idle로 판단되지 않게 하려는 목적으로만 만들지 않는다. 중요한 알림 메시지도 적절한 플랫폼 경로와 정책을 적용해야 하며 이 수업은 제한 우회 코드를 작성하지 않는다.

예산 모형의 경계

아래는 1시간 동안 고정 주기를 완전히 따라간다고 가정한 종이 예산이다. 매 깨어남 비용2단위, 자료1건 처리비1단위이며 실제 Android가 그 주기를 보장한다는 뜻이 아니다. 비용 단위는 joule이나 배터리 퍼센트가 아니다.

Doze가 15분마다 창을 반드시 연다는 식의 숫자를 이 예산에서 추론하면 안 된다. 실제 성능 확인에는 버전·기기·절전 상태·실행 기록이 필요하다. 그런 장비 실험은 아직 수행하지 않고 횟수 모델만 계산한다.

알림과 사용자제어

알림을 보냈다는 로그가 있는데 사용자가 안 봤다면 무엇이 빠졌을까?

준비 개념과 학습 목표

준비 개념

  • 권한과 상태

  • AND 조건

학습 목표

  • 앱 권한과 채널·사용자 설정을 구별한다.

  • 알림의 요청·표시·열람을 별도 사건으로 기록한다.

알림 표시 3건과 열람 확인 2건이면 실제 읽은 사람은 몇 명일까?

자체 장부는 서로 다른 일반 학습 알림 A,B,C,D 네 건을 다룬다. 모두 앱의 발송 허용 판정을 통과했다. 표시 사건은 A,B,C에만 관측됐고, 사용자 열람 사건은 A,B에만 관측됐으며 관측된 사건은 참이라고 가정한다. 누락된 열람 로그가 실제 미열람을 뜻한다는 조건은 주어지지 않았다.

확인된 표시 비율은 3/4이고 확인된 열람 비율은 2/4다. C는 표시됐지만 열람 여부는 미확인이다. D도 표시 로그가 없다는 이유만으로 미표시나 미열람을 확정할 수 없다. 서로 다른 네 알림의 실제 열람 건수는 주어진 증거에서 최소 2, 최대 4건이다. 이를 사람 수로 바꾸려면 알림과 사람의 대응 및 중복 수신 규칙이 추가로 필요하다.

사용자 제어도 별도로 확인한다. 새 설치의 일반 알림에서 권한 P0인 사용자가 권한창을 닫았으면 P는 그대로다. 채널이 켜져 있고 앱 내부 선택도 켜져 있어도 자체 P AND C AND U 판정은 거짓이다. 채널의 사용자 선택을 새 이름으로 덮는 흐름을 만들지 않는다. 아래 네 건의 로그와 비율은 실제 푸시·OS 표시·사람 열람 시험이 아니다.

  • 예약과 실제 완료

    예약 성공을 후속 알림 성공으로 확대하지 않는다.

보낼 수 있는가를 먼저 묻기

Android13 이상 새로 설치한 앱의 일반 알림은 런타임 권한을 받아야 한다. 사용자가 허용·거절·대화상자 닫기를 선택할 수 있으며 닫기는 기존 권한 상태를 바꾸지 않는다. 면제되는 알림 역할도 있으므로 이 단원은 일반 학습 알림만 다룬다.

학습자가 알림이 필요한 순간을 이해하도록 설명하고 거절해도 앱 안에서 자료를 찾아볼 수 있게 설계한다. 알림 권한은 자료 읽기 권한이나 서버 로그인 권한과 별개다. 허용 상태도 나중에 사용자가 바꿀 수 있다.

주제별 채널과 사용자 선택

Android8 이상 알림 채널은 주제별 시각·소리 동작을 구분하는 통로다. 학습 일정과 새 자료 소식을 다른 채널로 나누면 사용자가 원하지 않는 주제만 끌 수 있다. 채널 중요도를 생성한 뒤 앱이 마음대로 바꿔 사용자 선택을 덮어쓸 수 있다고 생각하지 않는다.

권한과 채널이 켜져 있어도 OS·방해금지·잠금 화면 등 다른 표시 조건이 존재한다. 민감한 내용을 알림 본문에 넣는 것은 잠금 화면에서 노출될 수 있다. 앱 내부 설정은 설명·선택을 돕고 시스템 설정과 실제 상태를 확인해야 한다.

성공을 여러 단계로 나누기

예약 완료, 서버 발송, 기기 수신, 표시, 사용자가 열람한 시점은 다르다. API 요청이 성공했다고 사람이 읽었다는 결론을 내리면 알림 기능의 성공률을 잘못 해석한다. 읽음 여부를 알 수 없다면 미확인으로 둔다.

아래 P는 일반 알림 권한, C는 채널 활성, U는 사용자의 앱 내부 알림 선택이다. 교육 모형의 발송 허용은 P AND C AND U이며 OS의 다른 조건은 만족했다고 가정한다. 실제 기기나 푸시 서비스에 메시지를 보내지 않는다.

예약·대기·열람 증거를 연결하기

힌트 1

관측점과 구간의 교집합을 나눈다.

  2. 세 묶음으로 12건을 처리하여 18단위다. 대기 합 108+3×15=153분, 평균 12.75분이다.
