소단원 4.1

생성·중지·재개

다른 화면에 잠깐 다녀오면 내 화면 객체가 반드시 새로 만들어질까?

준비 개념과 학습 목표

준비 개념

  • 객체는 메모리에 상태를 가진다.

  • 콜백은 시스템이 특정 시점에 호출하는 함수다.

  • 화면의 가시성과 사용자의 상호작용 가능성은 다르다.

학습 목표

  • Activity 인스턴스의 생성과 같은 인스턴스의 재개를 구별한다.

  • 정지 상태와 프로세스 종료를 별도 사건으로 추적한다.

  • 자원 사용 범위에 맞는 시작·해제 쌍을 정한다.

등록 수가 하나여도 과거 구독의 결과를 새 화면에 적용해도 될까?

자체 구독 모형에서 Resume 때 active가 false이면 등록 성공 후 true로 바꾸고 새로운 세대 번호를 부여한다. Pause 때 해제가 성공하면 false로 바꾼다. 모든 제어 사건과 callback 판정은 순차적이며 세대 번호는 이 유한 예제에서 재사용하지 않는다. 실제 센서·스레드·해제 API의 전달 보장을 모형에 추가하지 않는다.

첫 Resume의 등록은 세대 1이다. Pause에서 해제하고 다음 Resume에서 세대 2를 등록한다. 해제 전에 생성돼 대기하던 세대 1의 결과가 뒤늦게 도착할 수 있다고 자체 입력에 명시한다. active만 검사하면 현재 true라 옛 결과를 통과시킨다. active이고 결과 세대가 현재 세대와 같은지 함께 검사하면 세대 1은 버리고 세대 2만 적용한다.

구독의 수와 결과의 수명은 다른 조건이다. 등록 실패인데 true로 표시하면 실제 없는 구독을 있는 것처럼 적게 된다. 해제 실패의 상태·재시도 계약도 따로 정해야 한다. 아래 표는 등록과 해제가 성공하는 자체 종이 경로이며 registered − released가 0 또는 1이라는 수량 불변량만으로 옛 callback 처리가 올바르다고 증명하지 않는다.

화면 객체의 생애를 사건으로 읽기

Activity는 Android에서 사용자 화면을 담당하는 구성요소다. 한 앱에 여러 Activity가 있을 수 있으며 앱 전체와 하나의 화면 객체는 같은 대상이 아니다. onCreate는 특정 Activity 인스턴스의 초기 설정에 사용한다. 이후 onStart는 화면이 보이는 단계, onResume은 사용자와 상호작용하는 단계로의 진입을 알린다. 콜백 이름을 외우기 전에 어떤 객체의 상태가 바뀌는지 표시하자.

onPause를 받았다고 화면이 언제나 사라지는 것은 아니다. 다른 창과 함께 일부가 보일 수 있다. onStop은 화면이 더 이상 보이지 않는 상태로 이동했음을 알린다. 여러 창의 세부 실행 방식은 Android 버전과 환경에 따라 다르므로 이 단원은 모든 환경에 활동 중인 화면이 반드시 하나뿐이라고 가정하지 않는다.

같은 객체로 돌아오는 길

객체와 프로세스가 살아 있는 상태에서 잠깐 일시정지했다 돌아오면 onPause 다음 onResume으로 돌아갈 수 있다. 완전히 보이지 않는 정지 상태를 거친 뒤 같은 객체로 돌아오면 onRestart, onStart, onResume 순서로 진행한다. 이때 onCreate를 다시 호출해야 하는 것은 아니다. 메모리의 필드도 같은 객체에 남아 있다.

정지 상태는 메모리 유지의 영구 보증이 아니다. 시스템이 백그라운드 프로세스를 종료하면 그 프로세스의 Activity와 다른 객체도 함께 사라진다. 다음 화면 진입은 새로운 객체 생성과 복원이 필요하다. onDestroy가 항상 호출된 뒤 프로세스가 끝난다고 가정해서는 안 된다. 저장과 해제를 마지막 콜백 하나에 몰아 두면 이 차이를 놓친다.

필요한 동안만 자원을 쓰기

사용자 상호작용 중에만 필요한 가상의 센서 구독은 onResume에서 시작하고 onPause에서 끝내는 쌍으로 설계할 수 있다. 화면이 보이는 동안 필요한 작업은 onStart와 onStop 쌍을 검토한다. 실제 카메라나 위치 권한의 세부 규칙은 별도로 확인해야 하며 이 예는 자원 범위를 이해하기 위한 모델이다.

구독 여부를 active라는 상태로 기록하면 중복 등록을 피할 수 있다. 시작은 active가 false일 때 한 번 등록하고 true로 바꾸며, 종료는 true일 때 해제하고 false로 바꾼다. onPause는 짧게 끝내야 하므로 큰 데이터베이스 작업이나 네트워크 완료를 기다리는 장소로 삼지 않는다. 자원의 가시성 요구와 데이터의 보존 요구도 별도로 설계한다.

중간 과정을 따라가는 예제

프로세스가 끝나지 않고 구성변경도 없다. A의 콜백은 Create, Start, Resume, Pause, Resume, Pause, Stop, Restart, Start, Resume 순서다. Resume에서 구독하고 Pause에서 해제하는 가상 자원을 추적하라.

  1. Create에서 A를 한 번 초기화한다. 이 예에서 Create 횟수는 1이다.

  2. 첫 Resume에서 active를 false에서 true로 바꾸고 등록 횟수는 1이 된다. 첫 Pause에서 false로 돌아가며 해제 횟수는 1이다.

  3. 두 번째 Resume와 Pause를 거치면 등록 2회, 해제 2회이고 active는 false다. Stop 시점에도 false를 유지한다.

  4. Restart와 Start는 같은 A의 가시성 복귀 과정이다. 여기에서는 구독을 추가하지 않는다.

  5. 마지막 Resume에서 등록 3회, 해제 2회, active=true다. Start는 2회지만 Create는 1회다.

A는 한 번 생성되고 세 번 재개된다. 마지막에는 등록 3회·해제 2회이므로 살아 있는 구독은 하나다.

  1. 현재 active는 true다.

  2. 결과가 어느 등록의 자료인지 확인하지 않는다.

비교할 점

해제 직후의 결과

첫 Pause 뒤 Resume 전 세대 1 결과가 도착하면?

  1. active는 false다.

  2. 현재 사용 범위 밖이므로 결과를 반영하지 않는다.

거절한다. 세대가 같아도 active 조건을 함께 만족해야 한다.

비교할 점

세대 검사만으로 사용 가능 수명을 모두 표현하지 못한다.

종이와 본문으로 직접 해보기

마지막 Resume 뒤 Pause, Stop을 덧붙여 active와 등록·해제 횟수를 구하라. 이어 시스템이 프로세스를 종료한 경우 A의 필드가 남는지도 판단하라.

힌트 보기

해제 횟수는 실제 active=true인 구독을 끊을 때만 증가한다. 프로세스 종료 뒤에는 같은 객체라는 전제를 사용할 수 없다.

풀이 보기

추가 Pause에서 해제 3회가 되어 active=false다. Stop은 추가 해제가 없다. 등록 3회와 해제 3회가 같다. 이후 프로세스 종료 시 A와 필드가 소멸하며 새 객체가 필요한 상태다. 이 결론은 실제 센서 실험 결과가 아니라 주어진 콜백 모델의 종이 추적이다.

오해와 반례

onStop을 받으면 객체가 사라지고 돌아올 때 항상 onCreate가 실행된다.

프로세스가 살아 있는 정지 상태라면 객체는 메모리에 남을 수 있으며 같은 객체로 onRestart부터 복귀할 수 있다. 반대로 프로세스가 끝나면 새 객체가 필요하다. 두 사건을 같은 것으로 처리하면 초기화와 저장을 잘못 배치한다.

한 단계 더

심화: 자원마다 필요한 범위를 표로 써 보자. 화면이 보일 때의 애니메이션과 상호작용 중의 입력 추적은 요구가 다르다. 구독 수를 registered−released로 계산해 항상 0 또는 1이라는 불변식을 확인하되 실제 하드웨어 권한·스레드·오류 처리 검증은 별도 과제다.

소단원 4.2

구성변경

화면을 회전했을 뿐인데 입력 숫자가 0으로 바뀌는 이유는 무엇일까?

준비 개념과 학습 목표

준비 개념

  • Activity 필드는 해당 객체에 속한다.

  • 새 객체를 만들면 초기값부터 시작한다.

  • ViewModel은 특정 소유 범위에 연결된 상태 보관 객체다.

학습 목표

  • 기본 재생성이 일어나는 구성변경을 전제로 이전·새 Activity를 구분한다.

  • 같은 프로세스의 구성변경에서 ViewModel 보존 조건을 설명한다.

  • 새 구성의 자원 갱신과 사용자의 상태 보존을 함께 설계한다.

언어가 바뀌었을 때 선택한 항목과 표시 문자열 중 무엇을 유지할까?

자체 데이터 항목의 안정 ID는 42다. 한국어 자원에서 제목은 도서, 영어 자원에서 Books라고 정한다. 사용자 선택의 사실을 ID 42로 저장하고 현재 구성에서 제목을 계산하면 언어 변경 뒤 선택은 42이며 표시는 Books다. 번역 자체의 품질을 검증하는 예제가 아니라 식별과 표현을 분리하는 모형이다.

기본 재생성이 실제 발생하고 프로세스와 올바른 owner의 ViewModel M이 유지되는 구성변경을 전제한다. 이전 Activity A를 새 B로 바꾸며 M.selectedId는 42로 유지한다. M에 A의 화면 객체나 그 구성에서 계산한 제목만 저장해 재사용하면 수명이 끝난 대상이나 옛 표현을 사용할 수 있다. 영구 화면 종료와 프로세스 종료는 이 유지 전제 밖이다.

직접 특정 구성변경을 처리하는 별도 설계라면 Activity 재생성이 없을 수 있어도 구성에 맞는 자원과 포함된 View의 갱신 책임이 남는다. 실제 SDK·manifest·변경 종류의 조건을 확인한다. 아래 종이 사례는 모든 구성변경이 항상 재생성을 일으킨다고 일반화하지 않는다.

구성이 바뀌면 화면을 다시 구성하기

언어, 화면 크기, 방향, 글자 크기와 테마 등은 화면에 필요한 자원을 바꿀 수 있다. 해당 변경에서 기본 재생성이 적용되는 Activity라면 시스템은 기존 객체를 끝내고 새 구성을 사용하는 객체를 만든다. 이 단원의 회전 예는 재생성이 실제 발생하고 앱 프로세스는 유지되는 조건을 명시한다. 모든 변경과 모든 앱 설정에서 반드시 동일한 콜백 순서가 생긴다는 주장은 아니다.

새 Activity는 새 언어의 문자열이나 새 화면 크기에 맞는 배치를 사용할 수 있다. 사용자 선택은 그대로 두면서 표현을 갱신하는 것이다. 이전 Activity의 일반 필드에만 저장한 숫자는 새 객체에서 초기값으로 돌아갈 수 있다. 화면 표현을 새로 만든다는 사실과 사용자의 작업을 초기화해야 한다는 판단을 혼동하지 말자.

상태의 소유자와 수명

Activity 범위의 ViewModel을 권장 접근 방식으로 요청했다면 같은 프로세스에서 구성변경으로 재생성되는 Activity에 같은 ViewModel을 이어 줄 수 있다. 따라서 계산 결과나 화면의 데이터 상태가 유지된다. 매번 일반 생성자로 별도 객체를 만드는 것까지 시스템이 자동 보존해 준다는 뜻은 아니다. 소유 범위가 다르면 다른 ViewModel일 수 있다.

화면이 영구 종료되는 finish와 구성변경은 다르다. ViewModel은 일반 메모리 객체이므로 프로세스 종료를 넘어 혼자 살아남지 않는다. 작은 입력과 복원 식별자는 saved state를 활용하고 장기 데이터는 저장소를 활용하는 등 수명에 맞는 도구를 조합한다. 새 Activity를 필요로 하는 표시 작업은 그 Activity의 수명에 묶어 오래된 화면 객체로 결과를 보내지 않도록 한다.

재생성을 막는 설정만으로 해결되지 않기

특정 구성변경을 앱이 직접 처리하도록 설정하면 해당 경우 Activity 재생성을 제한할 수 있다. 그때도 언어, 크기나 자원 변경에 맞는 화면 갱신 책임이 남는다. Android 버전과 변경 종류에 따라 동작이 다르므로 manifest 옵션을 모든 문제의 해결책으로 소개하지 않는다.

화면 회전에서 유지되는지와 시스템의 프로세스 종료 후 복원되는지는 별도 확인 항목이다. 회전만 시험해서 저장 설계가 끝났다고 판단하면 메모리만 가진 ViewModel의 한계를 놓친다. 이 강의에서는 두 상황을 표와 종이 예로 구별하며 에뮬레이터나 기기의 회전·종료 실험을 수행했다고 기록하지 않는다.

중간 과정을 따라가는 예제

Activity A의 일반 필드 count=7, Activity 범위의 ViewModel M의 count=7이다. 새 Activity의 일반 필드 초기값은 0이다. 기본 재생성을 수행하는 회전이 일어나지만 프로세스는 살아 있다. 별도 saved state 복원은 하지 않는다. A와 새 Activity B의 상태를 구하라.

  1. 회전 전에는 A.count=7이고 M.count=7이다. 두 숫자는 값이 같아도 서로 다른 저장 위치다.

  2. 회전은 주어진 조건에서 A의 종료와 B의 생성을 일으킨다. B가 A 자체가 되는 것은 아니다.

  3. B의 일반 필드는 초기값 0으로 시작한다. A의 필드 7을 복사하는 절차는 주어지지 않았다.

  4. B는 같은 Activity 범위가 구성변경으로 이어지는 권장 ViewModel 접근을 통해 M을 받는다. M.count는 7이다.

  5. B가 M.count를 화면에 표시하면 7을 보여 준다. B.count를 잘못 표시하면 0이므로 표시의 진실 공급원을 명확히 해야 한다.

B의 일반 필드는 0, 이어진 ViewModel M의 값은 7이다. 표시를 M에서 가져오면 회전 뒤에도 7을 보여 준다.

소단원 4.3

프로세스 종료와 복원

메모리가 사라져도 검색어와 선택 항목을 다시 보여 주려면 무엇을 남겨야 할까?

준비 개념과 학습 목표

준비 개념

  • 프로세스 종료는 그 안의 메모리 객체를 없앤다.

  • 직렬화는 값을 저장 가능한 형태로 바꾸는 과정이다.

  • 영구 저장 완료와 저장 요청 시작은 다르다.

학습 목표

  • ViewModel·saved state·영구 저장소의 보존 범위를 비교한다.

  • 작은 복원 정보와 큰 데이터 본문을 분리한다.

  • 복원 시 기본값과 유효성 확인, 미완료 저장의 한계를 설명한다.

저장한 인덱스가 범위 안이어도 같은 항목을 가리킬까?

자체 목록은 ID [10,20,30]이고 선택 ID 20과 첫 가시 항목의 인덱스 1을 작은 복원 자료로 남겼다고 정한다. 이 예제의 위치는 항목 인덱스이며 본문의 scroll=120 같은 일반 위치 값을 임의로 같은 단위라고 바꾸지 않는다.

프로세스 후 목록을 다시 읽어 [5,10,20,30]이 되면 인덱스 1은 여전히 범위 안이지만 이제 ID 10이다. 선택 ID 20의 현재 위치는 2다. 위치의 범위 검사와 같은 의미의 항목을 찾는 검사는 다르다. 첫 가시 ID를 anchor로 남기는 대안은 현재 목록에서 그 ID를 다시 찾는 절차가 필요하다.

anchor 항목이 삭제됐거나 목록이 비어 있으면 복원 정책을 따로 정한다. 이 자체 정책은 anchor가 있으면 현재 인덱스를 사용하고, 없으면 비어 있지 않은 목록의 첫 항목, 빈 목록이면 위치 없음으로 둔다. 데이터의 현재 버전·접근 가능성을 확인하는 것과 과거 화면을 정확히 재현하는 것은 다른 요구다.

먼저 확인할 개념
  • 작은 ID와 복원 유효성

    복원 값의 현재 의미를 확인한다.

  • 화면 재생성과 현재 상태 소유자

    새 UI가 현재 데이터에서 표현을 만드는 경계를 확인한다.

세 보존 방식의 차이

ViewModel은 같은 프로세스에서 구성변경을 거칠 때 메모리 상태를 이어 주지만 시스템이 프로세스를 종료하면 함께 사라진다. saved state는 시스템이 유지하는 해당 화면·작업의 복원 정보로, 기록이 확보되고 시스템이 그 작업을 복원하는 조건에서 프로세스 종료 뒤에도 사용할 수 있다. 사용자 finish나 화면의 완전한 폐기는 같은 복원 상황이 아니다.

데이터베이스, 파일이나 서버에 성공적으로 기록한 영구 데이터는 화면과 프로세스의 수명 밖에서 읽을 수 있다. 다만 저장 호출만 한 경우, 쓰기 실패, 저장소 삭제, 계정 변경 등의 조건까지 무조건 보존한다고 말할 수 없다. ViewModel, saved state, 영구 저장소는 저장 위치와 보존 조건이 서로 달라 사용 목적에 맞게 조합한다.

큰 결과 대신 다시 찾을 실마리

검색 화면의 saved state에는 검색어, 선택 항목 ID와 스크롤 위치 같은 작고 단순한 값을 둔다. 큰 비트맵이나 결과 전체를 넣으면 직렬화 비용과 저장 크기 문제를 만들 수 있다. 항목 ID를 저장하고 데이터 본문은 저장소에서 다시 읽으면 복원 정보의 크기를 줄일 수 있다.

ID가 있다고 현재 항목이 반드시 존재하는 것은 아니다. 복원할 때 형식과 범위를 확인하고 저장소에서 찾지 못하면 선택을 해제하거나 안내를 표시한다. 기본값도 미리 정의한다. 예를 들어 검색어가 없으면 빈 문자열, 위치가 음수면 0으로 두되 오래된 결과에 대한 위치는 실제 목록 범위에 맞춘다.

언제 기록되었는지 따지기

saved state API의 화면 복원 기록은 Activity가 중지되는 시점과 연결된다. 메모리에서 새 값을 넣었다는 사실만으로 모든 순간의 최신 값이 시스템 복원 기록에 확정되었다고 가정하면 안 된다. 마지막으로 확보된 복원 기록을 기준으로 예를 풀어야 한다. 영구 저장 역시 마지막으로 성공한 버전을 기준으로 한다.

프로세스가 끝날 때 onDestroy에서 모든 입력을 저장하겠다는 계획은 보증되지 않는 콜백에 의존한다. 중요한 사용자 작업은 의미 있는 시점에 영구 저장하도록 설계하고 실패를 다룬다. 이후 새 Activity와 새 ViewModel은 복원 키로 데이터를 다시 구성한다. 이전 객체의 메모리 주소나 진행 중인 요청 자체를 복원했다고 설명하지 않는다.

중간 과정을 따라가는 예제

시스템이 백그라운드 프로세스를 종료한 뒤 기존 작업을 복원한다. 확보된 saved state는 query="graph", itemId=42, scroll=120이다. 성공한 영구 초안은 v5이며 메모리에만 있던 v6은 저장하지 않았다. 항목 42는 저장소에 존재하고 새 목록 길이는 위치 120을 허용한다.

  1. 종료 시 기존 Activity와 ViewModel을 포함한 프로세스 메모리는 사라진다. 메모리에만 있는 v6을 보존할 근거는 없다.

  2. 복원은 새 Activity와 새 ViewModel로 시작한다. 시스템이 해당 작업을 복원하며 확보된 saved state를 전달한다는 조건을 사용한다.

  3. query의 문자열과 itemId의 형식을 확인한다. itemId=42로 저장소를 조회해 항목 본문을 다시 읽는다.

  4. 복원된 목록의 범위를 확인한 뒤 scroll=120을 적용한다. 작은 위치 값 자체와 실제 화면 배치 완료 시점은 구별한다.

  5. 초안은 성공적으로 저장된 v5를 읽는다. v6을 읽을 수 없다는 사실과 복원된 검색 정보가 있다는 사실은 모순이 아니다.

검색어 graph, 항목 42, 위치 120은 주어진 복원 조건에서 재구성된다. 초안은 v5이며 저장하지 않은 v6은 잃는다.

오해와 반례

SavedStateHandle에 큰 결과를 넣으면 영구 저장소 없이 모든 종료에서 최신 상태가 보존된다.

작고 필요한 복원 정보에 적합한 도구이며 저장 크기·직렬화·중지 시 기록 조건과 작업 폐기 시 한계가 있다. 큰 결과는 별도 저장소에서 읽고 장기 데이터는 실제 성공한 영구 저장을 기준으로 다룬다.
