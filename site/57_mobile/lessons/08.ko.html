오프라인 편집은 저장했는데 보낼 작업이 사라진다면?

자체 지역 DB는 Note(id,value)와 Outbox(opId,noteId,payload)를 가진다. outbox는 나중에 서버로 보낼 보류 작업을 담는 지역 행이다. 초기 Note의 id7 값은 봄이고 Outbox는 비어 있다. 여름으로 수정한 행과 opA/7/여름을 같은 지역 거래에서 확정해야 한다는 자체 불변식을 정한다.

두 거래로 나누면 첫 거래의 Note=여름 확정 뒤, 둘째 Outbox 삽입 전에 앱이 종료되는 경로가 있다. 재시작하면 지역 수정은 있으나 보낼 작업은 없다. 한 거래로 묶어 전체 rollback하면 봄/빈큐이고 commit하면 여름/opA다. 실제 전원 장애·디스크 설정의 지속성 보장은 별도 시험이며 여기서는 정상 commit/명시 전체 rollback의 논리 모형이다.

지역 거래는 HTTP까지 원자적으로 확정하지 않는다. opA를 전송해 서버가 승인했으나 지역 완료 표시 전에 응답을 잃으면 Outbox에 opA가 남을 수 있다. 재전송과 서버의 중복 처리 계약이 필요하다. 또한 삽입 문장 하나 실패가 모든 DB에서 항상 전체 거래 rollback을 자동 유발한다고 일반화하지 않는다. 자체 정책은 실패 경로에서 전체 rollback을 명시한다.

목록을 지역 테이블로 옮긴다

SQLite 는 앱에서 사용할 수 있는 관계형 데이터베이스다. Room 은 Android 에서 SQLite 접근을 구조화하는 라이브러리이며 별도의 원격 서버가 아니다. 인터넷이 끊겨도 이미 지역에 저장한 행을 읽을 수 있지만 저장하지 않았던 서버 자료까지 새로 만들어 주지는 않는다.

Entity 는 테이블의 자료 구조, DAO 는 조회·삽입·갱신 등의 접근 함수, Database 는 연결과 DAO 의 진입점을 맡는다. id 가 기본키인 Task 의 title/done 열을 그려 화면 객체와 지역 행의 위치를 구별한다. 이 단원의 SQL 은 앱 구현을 생략한 종이 모형이다.

조회와 변경의 조건을 명시한다

done=false 인 행만 읽고 id 로 정렬하면 미완료 목록을 예측할 수 있다. Room 의 SQL 검증은 질의와 schema 가 맞는지를 일부 확인한다. 업무 규칙의 정확성·서버 권한·사용자가 실제로 학습했는지까지 증명하지 않는다.

여러 지역 변경을 하나의 DB transaction 으로 묶으면 일부만 확정되는 일을 피할 수 있다. 그러나 DB 거래 밖의 HTTP 요청과 파일 작업까지 자동 원자적으로 묶이는 것은 아니다. UI 스레드의 작업 배치와 오류 대응도 실제 앱에서 별도로 검증한다.

구조의 버전과 사용자 자료를 함께 보존한다

앱이 새 열을 요구하면 이미 설치된 옛 DB 를 다음 schema 로 옮길 경로가 필요하다. 빈 DB 를 새로 만드는 테스트만으로 기존 행을 가진 설치자의 이행을 확인하지 못한다. 옛 행과 새 구조를 함께 검토하는 migration 검증을 계획한다.

Room에서 migration 경로가 없으면 오류가 날 수 있다. androidx.room의 Room 2 계열 Builder에서 명시한 destructive fallback은 테이블을 다시 만들며 기존 자료를 잃을 수 있으므로 자료 보존 이행과 구별한다. 현재 가이드의 Room 3 API와 동일한 호출을 보장하는 설명은 아니다. 어떤 기기 파일도 삭제하거나 실제 이행하지 않았다.

SELECT id,title FROM Task WHERE done=0 ORDER BY id;

지역 보류 편집 확정

거래 내부 임시 값과 확정 값을 나눈다. 서버와 아직 통신하지 않았으므로 어느 행도 서버 승인 사실을 뜻하지 않는다.

중간 과정을 따라가는 예제

자체 Task 행은 (1, 읽기,0),(2, 쓰기,1),(3, 그리기,0)이다. 처음 미완료 목록을 구하고 한 거래에서 id1 done=1, id4(걷기,0)를 삽입한다. 두 변경 뒤 commit 하거나 삽입 실패로 전체 rollback 하는 결과를 각각 구하라.

  1. 처음 done0 인 id1/3 을 선택해 [1,3]이다.

  2. 거래 내부 변경 뒤 행 1 은 완료이고 새 4 가 미완료라 [3,4]이다.

  3. commit 성공이면 다음 거래의 목록도 [3,4]다.

  4. 전체 rollback 이면 행 1 은 미완료로 복원되고 4 는 없으므로 [1,3]이다.

확정 [3,4]와 전체 취소 [1,3]을 구별한다. 실제 기기 결과가 아닌 주어진 원자적 지역 거래의 예상이다.

조건을 바꾸어 비교하기

큐 삽입 실패의 명시 정책

한 거래에서 Note를 여름으로 바꾼 뒤 opA 삽입이 실패했다. 자체 정책대로 전체 rollback하면?

  1. 실패 뒤 전체 거래 rollback을 명시한다.

  2. 기존 Note와 빈큐로 돌아간다.

봄/빈큐다. 오류 하나의 자동 처리에 기대어 전체 rollback을 가정한 것이 아니다.

비교할 점

문장 오류 처리와 응용의 전체 취소 정책은 다르다.

서버 승인과 지역 큐 완료의 틈

서버가 opA를 승인한 뒤 응답 손실로 지역 완료 표시가 안 됐다. 재시작 시 무엇을 알까?

  1. 지역에는 opA가 남는다.

  2. 클라이언트는 승인 결과를 확정하지 못했다.

남은 큐만으로 서버 미적용이라고 단정할 수 없다. 같은 opId 재전달/상태 조회의 계약이 필요하다.

비교할 점

원격 효과와 지역 완료 표시는 같은 원자 거래가 아니다.

  • 작은 설정과 관계형 자료의 저장 요구를 비교한다.

  • 원자적 갱신과 오래된 읽기 기반 덮어쓰기를 구별한다.

원자적 설정 갱신 두 개는 순서를 바꾸어도 같을까?

본문의 증가 두 번은 성공·같은 저장소·overflow 없음 조건에서 어느 순서라도 2가 된다. 그러나 원자적 변환이 모두 교환 가능한 것은 아니다. 자체 counter 초기 3에서 I(c)=c+1과 D(c)=2c를 각각 한 번 성공 적용한다고 정한다.

I 다음 D는 3→4→8이고 D 다음 I는 3→6→7이다. 각 변환 안에서 최신 current를 받아도 결과가 다르다. 원자적 처리로 잃어버린 갱신을 피하는 것과 업무에서 어떤 순서를 채택할지 정하는 것은 별도다. 실제 동시 요청 중 어느 순서로 채택될지는 별도 보장 없으면 여기서 지정하지 않는다.

서로 일관되어야 하는 설정도 같은 범위에서 계산한다. 자체 두 값 min≤max에서 (2,5)를 (8,10)으로 바꾸려 한다. min=8을 먼저 독립 확정하면 (8,5)라는 중간 위반 상태가 있다. 두 값을 같은 객체 변환으로 한 번에 (8,10) 확정하면 그 중간 확정 상태를 만들지 않는다. 같은 파일의 단일 적절한 저장소와 불변 자료형 사용 조건을 확인한다.

먼저 확인할 개념
  • 최신 current 안에서 변환

    원자 read-modify-write와 밖에서 만든 값 쓰기를 구별한다.

  • 여러 행의 지역 확정 범위

    같은 객체/거래에 포함한 범위를 따져 본다.

작은 정책 값을 저장한다

언어·글자 크기·테마는 작은 설정의 예다. Preferences DataStore 는 키 기반 자료를 다루고, 사용자 정의 타입은 schema 와 Serializer 같은 변환 계약을 둔다. 서로 다른 방식의 타입 검사를 모두 같다고 부르지 않는다. 많은 행의 관계·부분 갱신에는 Room 같은 DB 를 검토한다.

설정 파일의 값, 읽기에서 값이 없을 때 선택한 기본값, 화면에 처음 표시한 임시값을 따로 적는다. 처음 light 를 표시했다고 파일에 light 를 쓰는 작업이 자동 수행된 것은 아니다. 비밀 토큰의 보호도 일반 설정 파일의 존재만으로 해결되지 않는다.

최신 상태 안에서 변경한다

counter 를 밖에서 읽어 old+1 을 저장하면 두 요청이 같은 old 를 읽을 수 있다. DataStore updateData 는 현재 상태를 받아 원자적인 read-modify-write 갱신을 제공한다. 증가 연산을 그 변환 안에서 최신 값에 적용해야 이전 증가를 이어갈 수 있다.

직렬화된 쓰기만 있어도 이미 밖에서 만든 두 값 1 을 연속 저장하면 1 다음 1 이 된다. 쓰기의 원자성과 증가의 논리를 구별한다. 여기서는 올바른 단일 저장소 사용·두 갱신 성공·overflow 없음·같은 counter 를 가정한다.

읽기와 수명·오류를 관리한다

Flow 는 시간이 지나며 바뀌는 설정을 관찰하는 통로다. UI 가 계속 직접 파일을 새로 여는 대신 데이터 계층에서 읽고 화면 상태로 전달한다. 실제 코루틴 취소·관찰자 수명과 다중 process 저장소 구성은 별도 규약을 따라야 한다.

파일 손상은 키가 없다는 정상 상태와 다르다. corruption handler 로 기본값 파일을 대체하면 옛 설정을 복구한 것이 아니라 대체한 것이다. 실패를 숨긴 성공 표시, 앱을 지웠는데 자료가 반드시 남는다는 보장도 이 단원의 범위를 벗어난다.

중간 과정을 따라가는 예제

자체 counter 초기 0 이다. A 와 B 가 모두 밖에서 0 을 읽고 각자 1 을 계산해 차례로 저장한다. 이어 초기 0 으로 되돌리고 두 updateData 변환 안에서 current+1 을 수행해 비교하라.

  1. 오래된 읽기 방식에서 A 가 1 을 쓴 뒤 B 도 미리 계산한 1 을 쓴다. 최종 1 이다.

  2. 원자 변환 방식에서 첫 변환은 current0→1 이다.

  3. 둘째 변환은 최신 current1→2 를 적용한다.

  4. 최종 2 이며 첫 실행순서가 A/B 인지와 관계없이 이 두 성공 증가 결과는 같다.

조건을 바꾸어 비교하기

밖에서 계산한 값은 다시 최신이 되지 않는다

I와 D가 모두 밖에서 old=3을 읽어 4와 6을 만들었다. I의 값 다음 D의 값을 저장하면?

  1. 첫 번째 저장으로 counter가 4가 된다.

  2. 두 번째 저장은 이전에 계산한 6을 그대로 기록한다. 첫 번째 저장으로 바뀐 값을 다시 읽어 계산하지 않는다.

최종 counter는 6이다. 최신 상태에 I를 적용한 뒤 D를 적용하면 8이 되므로, 미리 계산한 값을 차례로 저장하는 경로와 결과가 다르다.

비교할 점

쓰기 직렬화와 변환 안 최신 상태 사용을 구별한다.

두 설정의 중간 제약

초기 설정은 (min, max) = (2, 5)다. min을 8로 저장한 뒤 max를 10으로 별도로 저장하면, 각 저장 직후 확정된 설정과 제약 min ≤ max의 충족 여부는 어떻게 되는가?

  1. min을 먼저 저장하면 확정된 설정은 (min, max) = (8, 5)가 된다.

  2. max를 이어 저장하면 확정된 설정은 (8, 10)이 된다.

최종 설정은 min ≤ max를 만족하지만, 첫 번째 저장 직후의 (8, 5)는 이 제약을 위반한다. 두 값을 하나의 객체 변환으로 함께 확정하는 정책과 비교한다.

소단원 8.3

cache와 동기화충돌

인터넷 없이 고친 메모와 서버 메모가 다르면 어느 쪽을 살릴까?

준비 개념과 학습 목표

준비 개념

  • cache 는 재사용 복사본

  • revision 은 변경 버전

  • 요청 재시도

학습 목표

  • 오래된 복사본과 보류 쓰기를 분리한다.

  • 명시한 버전 충돌·중복 요청 정책을 추적한다.

중복 요청의 기억을 지운 뒤 재전달하면?

본문의 서버 계약은 기억한 opId와 동일한 payload인지 먼저 검사한 뒤 expectedRevision을 비교한다. 별도 예제 서버의 초기 상태는 revision 5이고 값은 봄이다. opA가 expectedRevision = 5와 값 여름을 요청하면 이를 승인해 revision 6, 값 여름으로 바꾼다. 이 예제는 현재 권한 확인을 통과한 뒤, 같은 작업의 재전달에는 기억한 과거 성공 결과를 반환한다는 조건을 추가한다.

이후 다른 작업 opB가 expectedRevision = 6과 값 가을을 요청하면 서버는 이를 승인해 revision 7, 값 가을로 바뀐다. opA의 기억이 남아 있을 때 원래 요청 사본을 재전달하면 revision 6의 성공 결과를 반환한다. 그러나 서버의 현재 자료는 여전히 revision 7, 값 가을이다. 과거 작업의 응답을 최신 조회 결과로 오인해 화면 전체에 덮어쓰면 새 자료를 지울 수 있다.

opA의 기억을 삭제한 뒤 원래 expectedRevision = 5인 요청이 다시 오면, 현재 revision 7과 맞지 않아 이 정책에서는 충돌한다. 원래 사본을 그대로 재전달하는 것과 expectedRevision을 7로 바꾸어 새 의도를 보내는 것은 다르다. 기억을 삭제했다면 opA를 expectedRevision = 7, 값 여름과 함께 재사용해도 이 비교만으로 과거 ID의 재사용을 알아낼 수 없다. 그 요청을 승인하면 revision 8, 값 여름으로 바뀐다. 따라서 ID를 기억할 기간, 재사용 금지와 새 의도를 식별하는 정책이 필요하다.

먼저 확인할 개념
  • opId 기억·버전 비교 순서

    기억 결과와 현재 자료를 구별한다.

  • 지역 보류 사본과 확정 범위

    재전달에서 사본을 임의 변경하지 않는 조건을 확인한다.

있음·최신·확정을 다른 상태로 둔다

지역 cache 가 있으면 오프라인 읽기를 제공할 수 있다. 하지만 파일이 존재한다는 사실은 서버의 현재 값과 같다는 뜻이 아니다. 마지막 동기화 시각·서버 revision·지역 편집 여부를 같이 보관해 화면에서 상태를 설명한다.

TTL 은 일정 나이가 넘은 복사본을 만료로 판단하는 자체 정책이다. TTL 안에 서버가 바뀌면 복사본은 이미 오래됐을 수 있다. stale 읽기를 허용할지, 재조회가 없으면 오류로 처리할지는 자료의 목적에 맞춰 정한다.

먼저 지역에 쓰고 보류 작업을 남긴다

오프라인 편집을 지역에 저장하고 서버로 보낼 큐에 작업을 남길 수 있다. 큐도 지속 저장하지 않으면 앱 종료에 보류 편집을 잃을 수 있다. 네트워크 복귀는 동기화 시작 조건이지 모든 요청의 성공 증거가 아니다.

응답 손실 뒤 같은 작업을 재시도하면 서버가 이미 처리했을 수 있다. 아래 자체 계약은 고유 opId 에 결과를 기억하고 동일 사용자/동일 payload 중복은 기억 결과를 반환한다. 다른 payload 로 opId 재사용은 거절하며 버전 비교와 중복 검사의 순서를 명시한다.

충돌을 발견하고 해결 선택을 남긴다

두 기기가 같은 revision 에서 각자 고치면 한 편집을 다른 편집으로 무조건 덮는 것은 자료를 잃을 수 있다. 자체 서버는 기억된 opId 중복을 먼저 처리한 뒤 expectedRevision 이 현재와 같을 때만 새 변경을 승인한다. 성공하면 revision 을 1 증가시키고 자료와 opId 결과를 원자적으로 저장한다.

충돌이면 지역 편집을 지우지 않고 서버 값과 함께 보여 수동 병합 또는 업무 규칙을 선택한다. 공식 자료의 last-write-wins 는 하나의 선택지이며 장치 시계 오차나 변경 유실을 저절로 해결하지 않는다. 이 단원의 정책은 Android 라이브러리가 자동 구현한 기능이 아니다.

다른 문제에 적용하기

지역 확정·업무 순서·과거 결과의 경계

Note의 id 7을 여름으로 수정하는 저장과 opA를 Outbox에 넣는 저장을 별도로 commit하는 설계를 사용한다고 하자. 두 저장 사이에 앱이 종료된 경우와, 두 변경을 한 거래로 묶은 뒤 전체 rollback한 경우의 확정 상태를 비교하라. 초기 counter가 3일 때 I 다음 D를 적용한 결과와 D 다음 I를 적용한 결과도 계산하라. 서버의 현재 상태가 revision 7, 값 가을일 때 기억한 opA의 원래 사본을 재전달하면 응답과 현재 서버의 revision은 각각 얼마인가? 기억을 삭제한 뒤 expectedRevision = 5인 원래 사본을 재전달한 결과도 구하라.

힌트 1

지역 행과 보류 사본의 확정 범위를 나눈다.

힌트 2

최신 상태에 변환을 차례 적용하고 과거 결과/현재 자료를 구별한다.

풀이와 답 확인

  1. 분리된 저장 사이에 종료하면 Note의 값은 여름이지만 Outbox는 비어 있다. 한 거래에서 전체 rollback하면 Note는 초기값 봄으로 돌아가고 Outbox는 비어 있다.

  2. 초기값 3에 I를 적용하면 4가 되고, 이어 D를 적용하면 8이 된다. 반대 순서로 D를 적용하면 6이 되고, 이어 I를 적용하면 7이 된다.

  3. opA의 기억이 남아 있으면 응답에는 과거 성공의 revision 6을 반환하며, 현재 서버는 revision 7과 값 가을을 유지한다. 기억이 없을 때 원래 expectedRevision = 5인 요청을 받으면 현재 revision 7과 맞지 않아 충돌한다.

원자 범위·변환 채택 순서·ID 보존·응답의 시점을 각각 명시한다. 실제 앱·저장·서버·복구·학생 실행은 미수행이다.
