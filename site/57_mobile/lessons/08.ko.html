소단원 8.1

SQLite·Room

화면을 닫아도 할 일 목록을 남기려면 어떤 상태를 저장해야 할까?

준비 개념과 학습 목표

준비 개념

  • 행과 기본키
  • 메모리와 저장 파일
  • 원자적인 변경 묶음

학습 목표

  • SQLite 와 Room 의 역할을 구별한다.
  • 지역 행 조회·transaction·migration 을 종이로 추적한다.

목록을 지역 테이블로 옮긴다

SQLite 는 앱에서 사용할 수 있는 관계형 데이터베이스다. Room 은 Android 에서 SQLite 접근을 구조화하는 라이브러리이며 별도의 원격 서버가 아니다. 인터넷이 끊겨도 이미 지역에 저장한 행을 읽을 수 있지만 저장하지 않았던 서버 자료까지 새로 만들어 주지는 않는다.

Entity 는 테이블의 자료 구조, DAO 는 조회·삽입·갱신 등의 접근 함수, Database 는 연결과 DAO 의 진입점을 맡는다. id 가 기본키인 Task 의 title/done 열을 그려 화면 객체와 지역 행의 위치를 구별한다. 이 단원의 SQL 은 앱 구현을 생략한 종이 모형이다.

조회와 변경의 조건을 명시한다

done=false 인 행만 읽고 id 로 정렬하면 미완료 목록을 예측할 수 있다. Room 의 SQL 검증은 질의와 schema 가 맞는지를 일부 확인한다. 업무 규칙의 정확성·서버 권한·사용자가 실제로 학습했는지까지 증명하지 않는다.

여러 지역 변경을 하나의 DB transaction 으로 묶으면 일부만 확정되는 일을 피할 수 있다. 그러나 DB 거래 밖의 HTTP 요청과 파일 작업까지 자동 원자적으로 묶이는 것은 아니다. UI 스레드의 작업 배치와 오류 대응도 실제 앱에서 별도로 검증한다.

구조의 버전과 사용자 자료를 함께 보존한다

앱이 새 열을 요구하면 이미 설치된 옛 DB 를 다음 schema 로 옮길 경로가 필요하다. 빈 DB 를 새로 만드는 테스트만으로 기존 행을 가진 설치자의 이행을 확인하지 못한다. 옛 행과 새 구조를 함께 검토하는 migration 검증을 계획한다.

Room에서 migration 경로가 없으면 오류가 날 수 있다. androidx.room의 Room 2 계열 Builder에서 명시한 destructive fallback은 테이블을 다시 만들며 기존 자료를 잃을 수 있으므로 자료 보존 이행과 구별한다. 현재 가이드의 Room 3 API와 동일한 호출을 보장하는 설명은 아니다. 어떤 기기 파일도 삭제하거나 실제 이행하지 않았다.

SELECT id,title FROM Task WHERE done=0 ORDER BY id;

중간 과정을 따라가는 예제

자체 Task 행은 (1, 읽기,0),(2, 쓰기,1),(3, 그리기,0)이다. 처음 미완료 목록을 구하고 한 거래에서 id1 done=1, id4(걷기,0)를 삽입한다. 두 변경 뒤 commit 하거나 삽입 실패로 전체 rollback 하는 결과를 각각 구하라.

  1. 처음 done0 인 id1/3 을 선택해 [1,3]이다.
  2. 거래 내부 변경 뒤 행 1 은 완료이고 새 4 가 미완료라 [3,4]이다.
  3. commit 성공이면 다음 거래의 목록도 [3,4]다.
  4. 전체 rollback 이면 행 1 은 미완료로 복원되고 4 는 없으므로 [1,3]이다.

확정 [3,4]와 전체 취소 [1,3]을 구별한다. 실제 기기 결과가 아닌 주어진 원자적 지역 거래의 예상이다.

소단원 8.2

설정저장

두 버튼이 동시에 숫자를 올리면 왜 한 번만 증가할까?

준비 개념과 학습 목표

준비 개념

  • 키와 값
  • 읽기→계산→쓰기
  • 기본값과 저장값

학습 목표

  • 작은 설정과 관계형 자료의 저장 요구를 비교한다.
  • 원자적 갱신과 오래된 읽기 기반 덮어쓰기를 구별한다.

작은 정책 값을 저장한다

언어·글자 크기·테마는 작은 설정의 예다. Preferences DataStore 는 키 기반 자료를 다루고, 사용자 정의 타입은 schema 와 Serializer 같은 변환 계약을 둔다. 서로 다른 방식의 타입 검사를 모두 같다고 부르지 않는다. 많은 행의 관계·부분 갱신에는 Room 같은 DB 를 검토한다.

설정 파일의 값, 읽기에서 값이 없을 때 선택한 기본값, 화면에 처음 표시한 임시값을 따로 적는다. 처음 light 를 표시했다고 파일에 light 를 쓰는 작업이 자동 수행된 것은 아니다. 비밀 토큰의 보호도 일반 설정 파일의 존재만으로 해결되지 않는다.

최신 상태 안에서 변경한다

counter 를 밖에서 읽어 old+1 을 저장하면 두 요청이 같은 old 를 읽을 수 있다. DataStore updateData 는 현재 상태를 받아 원자적인 read-modify-write 갱신을 제공한다. 증가 연산을 그 변환 안에서 최신 값에 적용해야 이전 증가를 이어갈 수 있다.

직렬화된 쓰기만 있어도 이미 밖에서 만든 두 값 1 을 연속 저장하면 1 다음 1 이 된다. 쓰기의 원자성과 증가의 논리를 구별한다. 여기서는 올바른 단일 저장소 사용·두 갱신 성공·overflow 없음·같은 counter 를 가정한다.

읽기와 수명·오류를 관리한다

Flow 는 시간이 지나며 바뀌는 설정을 관찰하는 통로다. UI 가 계속 직접 파일을 새로 여는 대신 데이터 계층에서 읽고 화면 상태로 전달한다. 실제 코루틴 취소·관찰자 수명과 다중 process 저장소 구성은 별도 규약을 따라야 한다.

파일 손상은 키가 없다는 정상 상태와 다르다. corruption handler 로 기본값 파일을 대체하면 옛 설정을 복구한 것이 아니라 대체한 것이다. 실패를 숨긴 성공 표시, 앱을 지웠는데 자료가 반드시 남는다는 보장도 이 단원의 범위를 벗어난다.

# 개념: updateData { current -> current.copy(counter=current.counter+1) }

중간 과정을 따라가는 예제

자체 counter 초기 0 이다. A 와 B 가 모두 밖에서 0 을 읽고 각자 1 을 계산해 차례로 저장한다. 이어 초기 0 으로 되돌리고 두 updateData 변환 안에서 current+1 을 수행해 비교하라.

  1. 오래된 읽기 방식에서 A 가 1 을 쓴 뒤 B 도 미리 계산한 1 을 쓴다. 최종 1 이다.
  2. 원자 변환 방식에서 첫 변환은 current0→1 이다.
  3. 둘째 변환은 최신 current1→2 를 적용한다.
  4. 최종 2 이며 첫 실행순서가 A/B 인지와 관계없이 이 두 성공 증가 결과는 같다.

밖에서 읽은 값 덮어쓰기 1, 최신 상태 안의 두 성공 증가 2 다. API 이름만 사용해도 밖의 old 가 최신으로 바뀌는 것은 아니다.

소단원 8.3

cache와 동기화충돌

인터넷 없이 고친 메모와 서버 메모가 다르면 어느 쪽을 살릴까?

준비 개념과 학습 목표

준비 개념

  • cache 는 재사용 복사본
  • revision 은 변경 버전
  • 요청 재시도

학습 목표

  • 오래된 복사본과 보류 쓰기를 분리한다.
  • 명시한 버전 충돌·중복 요청 정책을 추적한다.

있음·최신·확정을 다른 상태로 둔다

지역 cache 가 있으면 오프라인 읽기를 제공할 수 있다. 하지만 파일이 존재한다는 사실은 서버의 현재 값과 같다는 뜻이 아니다. 마지막 동기화 시각·서버 revision·지역 편집 여부를 같이 보관해 화면에서 상태를 설명한다.

TTL 은 일정 나이가 넘은 복사본을 만료로 판단하는 자체 정책이다. TTL 안에 서버가 바뀌면 복사본은 이미 오래됐을 수 있다. stale 읽기를 허용할지, 재조회가 없으면 오류로 처리할지는 자료의 목적에 맞춰 정한다.

먼저 지역에 쓰고 보류 작업을 남긴다

오프라인 편집을 지역에 저장하고 서버로 보낼 큐에 작업을 남길 수 있다. 큐도 지속 저장하지 않으면 앱 종료에 보류 편집을 잃을 수 있다. 네트워크 복귀는 동기화 시작 조건이지 모든 요청의 성공 증거가 아니다.

응답 손실 뒤 같은 작업을 재시도하면 서버가 이미 처리했을 수 있다. 아래 자체 계약은 고유 opId 에 결과를 기억하고 동일 사용자/동일 payload 중복은 기억 결과를 반환한다. 다른 payload 로 opId 재사용은 거절하며 버전 비교와 중복 검사의 순서를 명시한다.

충돌을 발견하고 해결 선택을 남긴다

두 기기가 같은 revision 에서 각자 고치면 한 편집을 다른 편집으로 무조건 덮는 것은 자료를 잃을 수 있다. 자체 서버는 기억된 opId 중복을 먼저 처리한 뒤 expectedRevision 이 현재와 같을 때만 새 변경을 승인한다. 성공하면 revision 을 1 증가시키고 자료와 opId 결과를 원자적으로 저장한다.

충돌이면 지역 편집을 지우지 않고 서버 값과 함께 보여 수동 병합 또는 업무 규칙을 선택한다. 공식 자료의 last-write-wins 는 하나의 선택지이며 장치 시계 오차나 변경 유실을 저절로 해결하지 않는다. 이 단원의 정책은 Android 라이브러리가 자동 구현한 기능이 아니다.

중간 과정을 따라가는 예제

자체 서버메모(rev5, 값봄)에서 A/B 가오프라인복사한다. A 는여름/opA/expected5, B 는가을/opB/expected5 다. A 성공 뒤응답손실로 opA 동일 payload 재시도, 그 뒤 B 요청을보낸다. 위 자체원자계약으로 추적하라.

  1. 처음 A 는 새 op 이고 expected5=현재 5 라승인한다. 서버값여름/rev6 과 opA 의 성공 결과를 기억한다.
  2. A 재시도는 기억 opA 와 같은 payload 라 기억 rev6 성공 결과를 반환한다. 새 rev7 로늘리지않는다.
  3. B 의 opB 는 새 op 이나 expected5≠현재 6 이라충돌이다. 가을로덮지않는다.
  4. 서버는여름/rev6 이고 B 지역에는가을의 보류 편집과충돌상태를 유지한다.

A 의 같은 재시도는 중복적용없고 B 는충돌한다. 지역 저장 성공과 서버승인은 다른상태다.

오해와 반례

마지막 시각이 큰 기기의 값이 언제나 실제 최신 편집이다.

A 의 느린 시계가 실제 나중 편집을 더 작은 시각으로 표시할 수 있다. revision 비교나 업무 충돌 정책이 없는 장치 시각 정렬만으로 편집의 의미를 보존한다고 단정하지 않는다.

한 단계 더

서버에서 rev8 삭제한 메모를 오래된 기기가 다시 보내는 사례를 그린다. 삭제 표식의 버전과 보관 기간이 없으면 부활 문제가 생길 수 있다. 모든 요청에 사용자 권한을 확인하고 opId 기억 범위/기간과 큐 실패 정책을 정의하되 실제 서버 시험으로 표시하지 않는다.
