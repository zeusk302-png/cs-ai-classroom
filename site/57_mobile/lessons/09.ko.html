최소권한과 요청시점

앱 첫 화면을 보는데 왜 아직 쓰지 않는 기능의 권한까지 물어야 할까?

준비 개념과 학습 목표

준비 개념

  • 앱 기능

  • 허용과 거절

학습 목표

  • 필요한 기능에 권한을 대응한다.

  • 사용 시점 확인과 대체 흐름을 설계한다.

권한 응답이 왔는데 사용자가 이미 기능을 취소했다면?

자체 지도 기능은 위치 요청 의도에 세대 번호 g를 붙인다. g1에서 권한 요청을 시작한 뒤 사용자가 기능을 취소하면 현재 의도는 비활성이 된다. 늦은 허용 응답은 기기의 현재 허용에 관한 사건일 수 있지만 취소한 기능을 다시 실행하라는 사용자 의도는 아니다.

기능 시작은 현재 의도 활성·응답 세대 일치·필요한 현재 권한을 모두 확인한 뒤 이 자체 직렬 사건 모형에서 수행한다. g1 취소 뒤 새 g2 의도가 생겼다면 g1 응답을 g2의 시작 근거로 쓰지 않는다. 새 g2는 필요한 접근 전에 현재 허용 상태를 확인할 수 있다. 기기 허용 사실과 어느 작업을 시작할지는 서로 다른 상태다.

허용 검사와 실제 API 사이에도 상태 변화나 접근 실패를 처리해야 한다. 검사를 했다는 기록을 영구 접근 보증으로 보관하지 않는다. 거절·취소 뒤에는 수동 도시 입력을 유지하며 대화상자가 다시 나타날지, 영구 거절인지 등은 실제 권한 종류·API·기기 조건에 맞춰 확인한다. 아래 g 규칙은 Android가 제공하는 자동 세대 관리 기능이 아니다.

먼저 확인할 개념
  • 현재 권한과 사용 맥락

    허용 검사·요청·기능 시작을 나눈다.

  • 취소와 결과의 수명

    옛 응답으로 취소한 의도를 되살리지 않는다.

기능과 접근 이유를 연결한다

권한은 사용자가 특정 기기 자원 접근을 허용하는 경계다. Android의 runtime permission 대상인지와 권한 없이 가능한 대안을 먼저 검토한다. 선언만으로 사용자 허용이 완료됐다는 뜻은 아니며 특수 권한에는 별도 절차가 있다.

사용자가 기능을 시작할 때 요청한다

위치 버튼처럼 접근이 필요한 맥락에 짧은 이유를 설명하고 현재 허용 상태를 확인한다. 필요한 동작마다 다시 확인해 과거 승인에만 의존하지 않는다. 묶음으로 모든 기능을 열려는 요청보다 이번 작업에 필요한 범위를 정한다.

거절은 정상적인 경로다

사용자가 설명이나 요청을 취소할 수 있고 기능을 쓰지 않아도 다른 화면은 계속 사용할 수 있게 한다. 거절되면 수동 입력 등 대안을 연결한다. Android 버전·권한 종류에 따라 대화상자와 재요청 정책은 달라 동일한 버튼 순서를 모든 기기에 약속하지 않는다.

중간 과정을 따라가는 예제

  1. 첫 화면 열기는 수동 도시 보기라 위치 요청 0 회다.

  2. 위치 버튼에서 미허용을 확인하고 이번 요청 1 회를 시작한다.

  3. 거절 뒤 위치 자동 찾기는 중단하고 수동 도시 보기는 유지한다.

이번 흐름은 요청 1 회, 자동 위치 없음, 수동 도시 보기 가능이다.

평균 벡터의 크기와 크기들의 평균은 같을까?

같은 좌표계·같은 단위·동일 가중치의 자체 두 샘플 a = (3,4,0), b = (−3,−4,0) m/s²를 비교한다. 각 샘플의 크기는 5 m/s²지만 두 벡터의 평균은 (0,0,0)이므로 평균 벡터의 크기는 0 m/s²다. 방향을 먼저 합치는 연산과 크기를 먼저 계산하는 연산의 순서가 다른 결과를 만든다.

두 샘플을 a=(3,4,0), c=(0,0,5)로 바꾸면 벡터 평균은 (1.5,2,2.5), 크기는 √12.5=5/√2≈3.54다. 크기 평균은 여전히 5다. 값이 0인 평균을 보고 센서 없음이나 움직임 없음이라고 단정하지 않는다. 실제 가속도에서 중력 성분·잡음·회전·측정 시간의 의미는 별도다.

좌표도 정의한다. 자체 평면 표시 변환 R(x,y,z)=(−y,x,z)는 90도 회전의 한 선택이다. (3,4,0)은 (−4,3,0)이 되고 크기는 5로 보존된다. 이는 실제 Android 화면 회전에 대응하는 확정 remap 공식이 아니다. 기기 자연 방향과 현재 화면 회전·축 정의를 읽고 실제 API 규칙을 확인해야 한다.

지원과 성공은 다르다

Android 센서 framework로 존재와 range·resolution 등을 확인한다. 센서가 없거나 반환이 지연되는 기기도 있어 빈 결과를 처리한다. 권한 허용은 장치 존재·서비스 동작·값 정확도의 증명과 다르다.

좌표·단위·시점을 읽는다

가속도와 위치와 사진은 자료 모양이 다르다. 축·단위·촬영 방향·시각을 연결해 해석하며 예전 위치를 지금의 위치라고 단정하지 않는다. 위치의 foreground/background와 approximate/precise 범위는 따로 정하고 사용자가 근사 위치만 허용한 경우를 지원한다.

사용 수명을 끝낸다

센서 listener는 필요한 화면 수명에 맞게 등록/해제해 불필요한 이벤트와 에너지 사용을 줄인다. 카메라 촬영은 시작·성공·취소·오류를 구별한다. 기기 API·버전별 절차를 확인하며 아래 숫자 벡터는 실제 센서의 좌표 보정이나 중력 제거 실험이 아니다.

사진 A의 업로드 승인으로 새 사진 B도 보내도 될까?

자체 업로드 확인은 자료 버전·목적·수신 대상에 묶인다. 사진 A/version1을 교실 서버 S에 과제 제출 목적으로 보내겠다는 승인 튜플 (A,1,과제,S)을 기록한다. 이 튜플은 법적 동의나 운영체제 권한 자료형의 구현이 아니라 학습용 업무 규칙이다.

사용자가 사진 B/version2로 교체하면 예전 A/1 승인은 현재 B/2의 전송 근거가 아니다. 동일 사진이라도 수신 대상을 T로 바꾸거나 목적을 공개 게시로 바꾸면 튜플이 다르다. 최종 전송 전 현재 자료와 명시한 승인 범위를 대조하고 바뀐 내용을 설명하여 새 선택을 받는 자체 흐름을 정한다.

사용자가 전송 전에 업로드를 취소하면 새 전송을 시작하지 않는다. 전송을 이미 시작한 후 취소나 기기 권한 철회가 있다면 원격 사본 삭제가 완료됐다는 뜻은 아니다. 로컬 사본·전송 작업·서버 사본·삭제 요청·삭제 확인을 나누어 표시한다. 여기서는 실제 서버 삭제나 나라별 법률 판단을 수행하지 않았다.

한 가지 실패값으로 뭉치지 않는다

권한 거절은 접근 불허, 촬영 취소는 사용자가 작업을 끝내지 않은 결과, 장치 오류는 실행 실패다. 성공 자료가 있는 경우에만 다음 처리를 시작한다. 실제 API의 결과·예외·수명 콜백을 한 교육용 상태표에 대응하고 구체 구현을 확인한다.

철회와 일회 권한을 고려한다

Android 11의 위치·마이크·카메라 일회 권한처럼 허용의 수명이 제한될 수 있다. 다음 사용에 현재 상태를 다시 검사하고 철회나 프로세스 종료를 정상적으로 복구한다. 이전 화면의 허용 사실을 영구 접근 계약으로 저장하지 않는다.

수집과 공유는 다른 결정이다

사진을 화면에 보여 줄 목적과 외부 서버 전송 목적을 구별한다. 필요한 자료만 보관하고 목적·수명·삭제 동작을 설명한다. 권한 승인은 모든 후속 사용에 대한 포괄 동의나 법적 의무 충족의 증명이 아니다. 이 단원은 UX·기술 계약이며 나라별 법률 판단은 수행하지 않는다.

중간 과정을 따라가는 예제

자체 사진 흐름은 권한 허용→촬영→결과 확인→사용자 업로드 확인→전송이다. 허용 뒤 촬영 취소, 촬영 성공 뒤 업로드 거절, 촬영 성공 뒤 업로드 허용의 세 경우를 각각 판단하라. 자동 전송은 없다.

  1. 촬영 취소는 성공 사진이 없어 전송 0 회다.

  2. 촬영 성공이어도 업로드 확인에서 거절하면 전송 0 회다.

  3. 성공 자료와 업로드 허용이 모두 있으면 전송 1 회를 시작한다. 전송 완료 여부는 별도 결과다.

세 경우의 전송 시작 횟수는 0/0/1이다. 시작 1 회를 성공 완료 1 회로 보고하지 않는다.
