소단원 5.1

navigation과 back stack

상세 화면에서 뒤로 가기를 누르면 왜 첫 화면 대신 방금 보던 목록으로 돌아갈까요?

준비 개념과 학습 목표

준비 개념

  • 스택은 마지막에 넣은 항목을 먼저 꺼내는 LIFO 자료구조다.

  • 화면의 종류와 같은 종류 화면의 개별 방문 항목은 다르다.

  • 예제는 탭·대화상자·중첩 그래프 없이 한 개의 navigation stack을 사용한다.

학습 목표

  • push·pop과 현재 화면을 종이로 추적한다.

  • 중복 방문 방지와 과거 항목 삭제를 구별한다.

  • Back·Up·로그인 후 이동 정책의 차이를 설명한다.

화면을 가리키는 항목의 목록

Navigation은 사용자를 목적 화면으로 이동시키고 돌아갈 맥락을 관리한다. 화면에는 목록·상세·편집처럼 종류가 있고, 상세(책 17)과 상세(책 28)처럼 각 방문의 인자도 있다. Back stack은 이런 방문 항목들의 순서를 기억하는 자료구조다. 여기서는 왼쪽을 바닥, 오른쪽을 꼭대기로 적고 꼭대기 항목이 현재 화면이라고 정한다.

자체 학습 모형은 [홈]에서 시작한다. 새 목록으로 이동하면 [홈,목록], 책 17 상세로 이동하면 [홈,목록,상세 17]이다. Back으로 pop하면 상세 17 을 제거하여 목록을 다시 보여 준다. 기존 항목을 복원한다고 모든 자료가 자동으로 최신이 되는 것은 아니다. 목록의 스크롤 위치·임시 편집·저장 자료는 별도 상태 관리 정책이 필요하다.

push·pop과 중복 이동

아래 표기는 Android API가 아닌 종이 연산이다. push(X)는 항목 X를 꼭대기에 추가하며 pop()은 꼭대기를 제거한다. 화면 종류가 같아도 기본 push를 반복하면 같은 목적의 방문이 여럿 쌓일 수 있다. 목록에서 상세 17 을 두 번 누른 것을 [홈,목록,상세 17,상세 17]로 기록하면 Back을 한 번 눌러도 겉으로 같은 상세 17 이 보일 수 있다.

Android Navigation의 launchSingleTop 같은 옵션은 꼭대기에 같은 목적 화면이 있을 때 중복 추가를 피하는 용도다. 스택 어디에 있든 해당 화면을 찾아 모든 중복을 지우는 일반 규칙으로 이해하지 않는다. 특정 항목 위를 삭제하는 popUpTo와 그 항목도 삭제하는 inclusive 조건은 별도의 동작이다. 아래 예제는 복잡한 API 동일성·인자 비교를 대신 주장하지 않는다.

종이 모형 — 실행 가능한 Kotlin/Java 코드가 아니다.
[홈]
push(목록)       -> [홈, 목록]
push(상세17)     -> [홈, 목록, 상세17]
push(편집17)     -> [홈, 목록, 상세17, 편집17]
pop()           -> [홈, 목록, 상세17]

뒤로 가기의 맥락을 설계한다

앱 내부의 단순한 이동에서는 Back과 앱 상단의 Up이 같은 이전 목적지로 갈 수 있다. 그러나 Back은 실제 사용 맥락의 역순 이동이고 Up은 앱 안의 상위 맥락으로 돌아가는 기능이다. 다른 앱에서 링크로 들어온 경우 Back이 이전 앱으로 갈 수 있으며 Up은 자기 앱 안의 계층을 만들 수 있다. 시작 화면에서 Up으로 앱 밖으로 나가는 정책을 일반화하지 않는다.

로그인 완료 후 로그인 화면이 Back으로 다시 나타나면 혼란스럽다. 자체 정책으로 [홈,로그인,인증]의 로그인 및 인증 항목을 제거하고 홈을 남긴 뒤 목록을 추가하면 [홈,목록]이다. 마지막 항목까지 제거한 빈 스택에서는 보여 줄 화면이 없으므로 종료 또는 새 시작점으로 이동하는 명시적인 처리가 필요하다. 실제 Navigation은 그래프 항목과 저장된 상태를 더 포함할 수 있다.

중간 과정을 따라가는 예제

단순 종이 모형 [홈]에서 목록, 상세 17, 편집 17 을 push하고 Back을 두 번 누른다. 각 단계의 스택과 최종 화면을 적어라. 홈 항목은 제거하지 않는다.

  1. 목록 이동은 [홈,목록]을 만든다.

  2. 상세 17 이동은 [홈,목록,상세 17]을 만든다.

  3. 편집 17 이동은 [홈,목록,상세 17,편집 17]이며 편집 17 이 현재다.

  4. 첫 Back은 편집 17 을 제거하여 [홈,목록,상세 17]이고 상세 17 이 현재다.

  5. 둘째 Back은 상세 17 을 제거하여 [홈,목록]이고 목록이 현재다.

최종 스택은 [홈,목록], 최종 화면은 목록이다. Back은 목록을 새로 push하는 연산이 아니다.

종이와 본문으로 직접 해보기

[홈,목록,상세 17,편집 17]에서 목록 위만 제거하는 정책 A와 목록까지 제거하는 정책 B를 비교한다. 그 뒤 두 정책 모두 새 검색 화면을 push한다. 최종 스택과 다음 Back의 목적지를 적어라.

힌트 보기

A에서는 목록을 남기고 B에서는 홈만 남긴다. 제거 후 새 검색 항목을 추가하라.

풀이 보기

A: [홈,목록]→[홈,목록,검색], 다음 Back은 목록. B: [홈]→[홈,검색], 다음 Back은 홈. 같은 검색 화면을 보여도 되돌아갈 맥락은 다르다. 정책 B가 홈까지 지우는 것으로 오해하지 않는다.

오해와 반례

뒤로 가기는 언제나 홈을 새로 여는 것이며 Up과도 항상 같다.

[홈,목록,상세 17]의 Back은 목록이 되는 반례다. 또한 다른 앱에서 deep link로 들어오면 Back과 Up의 맥락이 달라질 수 있다. 이동 이력과 앱 계층 및 task 조건을 구별해야 한다.

소단원 5.2

화면인자

책의 상세 화면을 열 때 책 전체를 보내야 할까요, 번호 하나면 될까요?

준비 개념과 학습 목표

준비 개념

  • 식별자는 자료를 찾는 키이고 제목은 바뀔 수 있는 속성이다.

  • 필수·선택 인자와 자료형은 화면의 입력 계약이다.

  • 네트워크나 저장소 조회는 실패하거나 자료가 사라질 수도 있다.

학습 목표

  • 화면이 요구하는 최소 입력 계약을 작성한다.

  • 문자열·자료형 검사와 존재·권한 검사를 분리한다.

  • ID 조회와 객체 사본 전달의 일관성 차이를 설명한다.

목적 화면의 입력 계약

화면인자는 목적 화면이 무엇을 보여 줄지 결정하는 입력이다. 자체 도서 앱의 상세 화면은 bookId라는 양의 정수 키 하나를 요구하고 mode는 선택 문자열로 기본 "read"를 쓴다고 정한다. 허용 mode는 "read"와 "edit"뿐이다. 이는 Android 전체의 기본 규칙이 아니라 이 앱의 명시적인 계약이다. 제목이나 표지 전체를 인자로 삼지 않아도 ID를 이용해 저장소에서 필요한 자료를 가져올 수 있다.

인자가 없을 때의 기본값과 인자가 잘못된 경우의 오류를 구별한다. mode가 빠지면 read를 적용하지만 "admin"을 넣었다고 조용히 edit로 바꾸지 않는다. bookId가 필수라면 누락을 임의의 책 1 로 대체하지 않는다. 잘못된 링크에서 사용자가 예상하지 않은 자료를 여는 대신 오류 안내나 안전한 목록으로 이동하는 정책을 정한다.

형식이 맞는 것과 접근할 수 있는 것은 다르다

인자를 타입이 있는 도구로 전달하면 내부 코드에서 문자열·정수 혼동을 줄일 수 있다. Android의 Safe Args 등은 내부 이동 인자의 자료형을 다루지만 외부 링크 값의 모든 사업 규칙·자료 존재·권한을 자동 보장하지 않는다. 문자열로 들어온 "17"은 정수 17 로 변환 가능해도 그 책이 존재하는지는 조회해야 한다.

이 단원의 종이 판정은 정수 변환 가능한 십진수 입력을 읽고 1≤bookId≤9999 를 요구한다. 단순히 변환에 성공했다는 이유로 -2 나 10000 을 받아들이지 않는다. ID17 이 존재해도 현재 사용자가 편집할 수 없다면 mode=edit 요청을 거부한다. ID를 추측하기 어렵게 만드는 것만으로 접근 권한 검사를 대신할 수 없다.

자체 입력 계약 — 실제 플랫폼 API나 실행 코드가 아니다.
bookId: 필수 정수, 1..9999
mode: 선택 문자열, {read, edit}, 누락 기본 read
판정 순서: 파싱 -> 범위/허용값 -> 자료 존재 -> 현재 사용자 권한
자료가 없음: 찾을 수 없음 안내
편집 권한 없음: 편집 거부

큰 사본보다 키를 전달하는 이유

목록이 가진 책 사본의 제목이 "초안"인데 저장소에서 "개정판"으로 바뀌었다고 하자. 제목 사본을 그대로 상세 화면에 전달하면 새 화면이 오래된 값을 믿기 쉽다. ID17 을 전달하여 현재 저장소를 조회하는 정책이라면 갱신된 제목을 얻을 수 있다. 물론 조회가 실패하거나 캐시가 오래되었다면 자동 최신 보장은 없다. 이 예제에서는 조회가 성공하고 현재 값을 준다는 가정을 분명히 한다.

큰 객체 전달은 저장 상태 크기 제한·직렬화·프로세스 재생성에도 영향을 준다. ID를 전달하면 입력을 작게 만들고 데이터 출처를 한 곳에 두기 쉽지만 조회 중 화면과 실패 처리는 여전히 필요하다. 저장하지 않은 편집 초안은 단순 ID 조회만으로 복원되지 않으므로 초안 저장소나 적절한 수명 범위의 상태를 별도로 선택한다. 민감한 비밀번호나 토큰을 화면 경로에 담지 않는다.

중간 과정을 따라가는 예제

자체 계약으로 A=(bookId="17",mode 누락), B=("-2","read"), C=("17","admin"), D=("17","edit")를 판정하라. 저장소에는 책 17 이 있고 현재 사용자는 읽기만 허용된다. 파싱에는 부호 있는 십진수 문자열을 허용한다.

  1. A는 문자열 17 을 정수 17 로 파싱하고 범위가 맞다. mode 누락은 read가 되어 존재와 읽기 권한을 통과한다.

  2. B는 정수-2 로 파싱되지만 양의 범위 1..9999 를 만족하지 않아 거부된다. 파싱 오류와 구별한다.

  3. C는 ID가 맞아도 mode가 허용 집합 밖이라 거부된다. admin을 edit로 바꾸지 않는다.

  4. D는 형식·범위·허용값·존재를 통과하지만 사용자의 편집 권한이 없어 편집을 거부한다.

A만 읽기 화면을 열고 B는 범위, C는 허용값, D는 권한에서 실패한다. 자료형 검사 하나로 네 경우를 해결할 수 없다.

종이와 본문으로 직접 해보기

목록의 책 17 사본 제목은 "초안", 현재 저장소 제목은 "개정판"이다. 정책 P는 사본 제목을 그대로 표시하고 Q는 ID17 로 현재 값을 성공적으로 조회한다. 두 화면의 제목과 Q의 조회 실패 때 필요한 처리를 적어라.

힌트 보기

정책 P에는 갱신 조회가 없다. Q의 성공과 실패를 따로 적고 실패를 존재하지 않음으로 곧바로 단정하지 말자.

풀이 보기

P는 초안, 가정한 성공 Q는 개정판을 표시한다. Q가 네트워크 오류로 실패했다면 읽기 실패 안내·재시도 등의 정책이 필요하다. 네트워크 실패는 책이 삭제되었다는 증거가 아니다. 이 모형은 캐시 신선도나 오프라인 복원을 실제로 검증하지 않았다.

오해와 반례

화면 인자를 타입 안전하게 만들면 그 화면은 어떤 사용자에게나 안전하다.

정수 17 과 문자열 edit라는 자료형이 모두 맞아도 읽기 전용 사용자가 편집을 요청할 수 있는 반례다. 타입 검사·자료 존재·사용자 권한은 각각 확인해야 한다. 화면 버튼을 숨기는 것만으로 서버 접근 제어를 대신하지 않는다.

자기점검

mode가 누락된 것과 admin인 것은 같은가?

답과 이유 보기

다르다.

누락은 명시한 기본 read를 쓰지만 admin은 허용값 밖이다.

정수-2 로 파싱 성공하면 허용 ID인가?

답과 이유 보기

아니다.

자체 범위가 1..9999 라 파싱 성공만으로 부족하다.

ID를 전달하면 저장 안 한 초안도 자동 복원되는가?

답과 이유 보기

아니다.

ID로 원본을 찾는 과정과 임시 편집 상태의 수명·저장은 별개다.

소단원 5.3

deep link

친구가 보낸 링크로 앱의 특정 강의를 바로 열면 뒤로 가기는 어디로 돌아갈까요?

준비 개념과 학습 목표

준비 개념

  • URI는 scheme·host·path·query 등의 구성 요소를 가진다.

  • 화면 이동 인자는 외부 입력으로부터도 올 수 있다.

  • 앞 소단원의 화면 이력과 입력 계약을 사용한다.

학습 목표

  • 링크에서 목적 화면과 인자를 추출하는 조건을 설명한다.

  • 도메인 연관 검증과 사용자 권한을 구별한다.

  • 외부 진입과 합성 이력의 Back/Up 정책을 분석한다.

앱 안의 목적지를 외부에 표현한다

Deep link는 앱의 특정 목적 화면으로 진입하는 링크다. 앱 첫 화면에서 목록을 거쳐 상세를 누르는 과정 대신 https://learn.example/books/17 처럼 목적지와 ID를 표현할 수 있다. learn.example은 교육용 가상 도메인이며 실제 서비스를 뜻하지 않는다. 링크를 지원하려면 OS가 어떤 앱에 전달할지와 앱이 어떤 목적지로 해석할지를 함께 설계한다.

Android Navigation에는 특정 목적지로 가는 explicit deep link와 URI·action·MIME 등을 맞추는 implicit deep link가 있다. 여기서는 외부 HTTPS URI의 개념을 다룬다. 링크 문자열을 만들었다는 사실만으로 OS 연결·manifest·navigation graph·앱 설치가 갖추어진 것은 아니다. 실제 플랫폼 설정과 도메인 등록은 수행하지 않았다.

링크 매칭 뒤에도 검증한다

자체 엄격한 링크 계약은 scheme=https, host=learn.example, path=/books/{bookId}, 선택 query mode=read 또는 edit만 허용한다고 정한다. 파싱 후 앞 소단원의 ID 범위·자료 존재·사용자 권한도 확인한다. host를 문자열 부분 포함으로 비교하지 않고 URI parser가 추출한 host를 정확히 비교해야 한다. learn.example.evil.test는 learn.example과 다른 host다.

Android의 일반 Navigation URI 매칭에는 기본값·nullable query나 추가 query가 허용되는 조건이 있다. 이 단원의 자체 엄격한 계약을 라이브러리의 기본 매칭과 혼동하지 않는다. App Links의 도메인 연관은 웹사이트의 Digital Asset Links와 앱의 설정을 통해 검증한다. autoVerify 설정만 적었다고 검증 성공을 선언하지 않는다. 도메인 연관이 확인되어도 로그인·자료 접근 권한 검사는 별도다.

새 진입에 어울리는 돌아갈 경로

외부에서 상세 17 로 바로 들어오면 사용자가 앱의 홈과 목록을 실제로 방문하지 않았을 수 있다. 자체 앱 task에 합성 이력 [홈,목록,상세 17]을 만드는 정책을 정하면 Back은 목록으로 간다. 이력은 실제로 눌렀던 모든 화면의 기록만이 아니라 진입 맥락에 맞춰 구성한 navigation state일 수 있다. 합성 이력의 계층과 중첩 그래프 조건을 명시해야 한다.

Android implicit link는 NEW_TASK 여부와 기존 task 맥락에 따라 동작이 달라진다. 다른 앱의 task에서 진입한 조건에서는 Back이 그 이전 앱으로 돌아갈 수 있고 Up은 자기 앱의 상위 맥락으로 갈 수 있다. 링크는 언제나 홈으로 돌아간다는 일반 규칙이 아니다. 로그인 필요 화면이면 링크 목적지를 보존한 채 인증으로 안내한 뒤 권한을 재검사하며 민감한 동작을 링크 열기만으로 실행하지 않는다.

중간 과정을 따라가는 예제

가상 링크 계약으로 A=https://learn.example/books/17?mode=read, B=https://learn.example.evil.test/books/17, C=https://learn.example/books/-2, D=https://learn.example/books/17?mode=edit를 판정하라. 책 17 은 존재하고 현재 사용자는 읽기만 가능하다. host는 정확 비교하며 인자 규칙은 앞 소단원과 같다.

  1. A는 scheme·host·path가 맞고 17 이 범위 안이며 read가 허용되어 읽기 화면으로 간다.

  2. B의 실제 host는 learn.example.evil.test다. 문자열에 learn.example이 포함되어도 정확 비교에 실패한다.

  3. C의 host와 경로 모양은 맞지만 ID-2 가 자체 범위 밖이어서 거부한다.

  4. D의 링크 형식은 맞지만 현재 사용자의 편집 권한이 없어 편집을 거부한다.

A만 읽기 허용. B는 host, C는 범위, D는 권한에서 거부된다. App Links 검증이나 OS 실행을 수행한 결과가 아니다.

종이와 본문으로 직접 해보기

정책 P는 자기 앱 task에 [홈,목록,상세 17]을 합성한다. 정책 Q는 다른 앱의 task에서 바로 상세 17 을 열고 NEW_TASK가 없는 Android implicit link 조건이다. 각 정책에서 Back과 Up의 맥락을 설명하라. P는 단순 계층을 사용한다.

힌트 보기

P의 꼭대기를 pop하면 목록이다. Q의 Back은 이전 앱이라는 외부 맥락을 보존한다.

풀이 보기

P에서 Back과 단순 계층의 Up은 목록으로 간다. Q에서 Back은 링크를 연 이전 앱으로 돌아갈 수 있고 Up은 자기 앱 task의 상위 목적지를 구성해 이동한다. Q의 상세 앞에 실제로 홈·목록을 방문했다고 가정하지 않는다. 구체적 stack 구성은 그래프와 설정에 따른다.

오해와 반례

우리 도메인의 검증된 App Link로 들어왔으면 ID와 사용자 권한은 검사할 필요가 없다.

공식 도메인 링크라도 다른 사람이 책 ID나 mode를 바꿔 읽기 전용 사용자의 편집을 요청할 수 있는 반례다. 도메인 연관 검증은 링크의 연결 대상에 관한 것이며 사용자 인증·자료 접근 권한을 보장하지 않는다.

아니다.

답과 이유 보기

아니다.
