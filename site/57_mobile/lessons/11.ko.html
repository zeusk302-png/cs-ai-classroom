소단원 11.1

ViewModel·UI 테스트

숫자 상태가 바뀌었는데 화면에는 옛 숫자가 남을 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 상태와 이벤트
  • 입력과 기대값

학습 목표

  • 상태 규칙과 화면 관측을 나눈다
  • 정상/경계/거절 상태를 추적한다
  • UI 동기화와 실제 수행을 구별한다

상태를 만드는 규칙

ViewModel은 화면에 필요한 상태와 처리 논리를 제공할 수 있다. 검사는 초기 상태와 이벤트 후 상태를 독립 기대값과 비교한다. 주변 저장소나 시각 같은 의존성을 대역으로 통제했다면 그 사실도 기록한다.

아래 자체 count 규칙은 정수0–3을 상태로 갖고 초기값0이다. Add는3미만이면1증가하고3에서는유지,Reset은0으로만든다. 반환상태가예상과같은지보는것은 ViewModel 단위의 질문이지 실제 버튼이 연결됐다는 증거가 아니다.

화면은 다른 연결을 포함한다

UI 검사는 의미가 부여된 화면 요소를 찾아 사용자 조작을 보내고 표시·활성 여부를 확인한다. Compose 테스트는 semantics와 테스트 API를 이용한다. 화면상태를 읽는 연결이나 버튼 이벤트가 빠지면 상태 규칙은 맞아도 사용자 흐름은 실패한다.

비동기 작업이나 UI 재구성이 끝나기 전에 비교하면 아직 갱신되지 않은 화면을 읽을 수 있다. 적절한 동기화와 대기 조건을 설계하고 무조건 긴 시간 잠드는 방법만으로 결과가 안정적이라고 단정하지 않는다. 이 단원은 실제 테스트 도구를 실행하지 않는다.

경계와 결과를 함께 적는다

count3에서Add의상태유지를확인하고 화면이 버튼을 비활성화하도록 설계했다면 그UI정책도 별도로 검사한다. 상태 규칙과 버튼 정책은 같아 보이지만 관측 지점이 다르다. Reset이 상태0으로돌아가는지와 화면숫자0을확인하는질문을나누면 실패위치가보인다.

초기상태·여러이벤트·한계도달·Reset뒤재시작을 종이표로 추적한다. 예상값/실제값칸을 나누어 아직 앱을 실행하지 않은 칸은 미관측으로 남긴다. 상태검사통과가 화면크기·접근성·프로세스복구까지 증명하지 않는다.

중간 과정을 따라가는 예제

자체 count 규칙에 Add,Add,Add,Add,Reset,Add를 차례로 보낸다. 초기0이며 상태변경 뒤 UI가 최신상태를 읽는다는 가정이다.

  1. 첫세Add뒤상태는1,2,3이다. 네번째는count3이므로3으로유지한다.
  2. Reset뒤0,마지막Add뒤1이다. 상태열은0→1→2→3→3→0→1이다.
  3. UI연결이최신값을읽는다는가정에서는각숫자를표시한다. 실제앱의낭독·표시·클릭성공은미확인이다.

소단원 11.2

회전·종료·네트워크 검사

화면을 돌린 것과 앱 프로세스가 사라진 것은 같은 사건일까?

준비 개념과 학습 목표

준비 개념

  • 메모리와저장소
  • 앱의상태

학습 목표

  • 구성변경과프로세스종료를구별한다
  • 복구값과영속데이터를분리한다
  • 네트워크실패와오래된결과를검사한다

사건을같은이름으로묶지않는다

Android의 구성변경으로 화면이 재생성될 때 적절히 scoped ViewModel의 메모리 상태는 유지될 수 있다. 시스템이 프로세스를 종료하면 그메모리는사라진다. 사용자에게완전히닫힌화면과 시스템복구도 같은조건이아니다.

saved state는작은검색어/선택ID같은복구정보를남기고 데이터는저장소에서다시읽는방식에적합하다.큰이미지나전체복잡한객체를모두넣지않는다. savedstate가저장되는수명주기시점과userdismissal시복구제한도있으므로모든종료에서자동복구한다고말하지않는다.

복구할것을각각정한다

교육검색앱은검색어를savedstate에,즐겨찾기3건을disk에,검색결과2건을ViewModel메모리에둔다. savedstate가이미정상확보된뒤systemprocessdeath가발생하고 복구가지원되는상황으로한정한다.

회전에서는살아있는같은scope의검색어/결과를쓸수있다. processdeath복구에서는검색어를복구해결과를다시요청하고disk즐겨찾기는다시읽는다. 네트워크가없으면재조회실패나offline표시를다루며 없는결과를있다고화면에내지않는다.

요청의시간순서도검사한다

네트워크검사에는성공뿐아니라실패·timeout·재시도·느린응답을포함한다. 아래자체정책은새검색에증가ID를붙여현재ID의응답만표시한다. 서버취소성공을가정하지않고오래된응답을화면갱신에서거르는규칙이다.

응답이없다고서버처리가없었다고단정할수없다. 쓰기작업재시도는중복효과를검토하고검색결과에는빈성공과실패를구별한다. 종이이벤트표로기대와원인을추적한뒤실제기기의회전/프로세스/네트워크실험은별도로수행한다.

중간 과정을 따라가는 예제

검색어graph/결과2건이메모리에있고검색어savedstate확보,disk즐겨찾기3건은저장완료다. 동일scope회전과시스템processdeath후지원된복구를비교하라.

  1. 회전은ViewModel생존조건에서결과2건과검색어를재사용한다. 즐겨찾기는저장소에도3건남아있다.
  2. processdeath는ViewModel메모리결과2건을잃는다. savedstate의graph를복구하고disk의3건을다시읽는다.
  3. 검색결과는재조회가필요하다. offline이면아직결과미확보/조회실패상태이며옛메모리2건이자동돌아온다고하지않는다.

회전의메모리보존과processdeath후최소값복구/재조회는서로다르다. 실제장비복구시험아니다.

오해와 반례

ViewModel이회전에살아남으므로프로세스종료와사용자완전닫기뒤에도모든상태가남는다.

한 단계 더

savedstate가확보된값은graph인데foreground에서검색어tree로바꾼후새저장시점전에processdeath가발생한교육상황을생각하라. 복구graph와사용자가마지막본tree가다를수있다. 이조건을유지한실험계획표를쓰고현실기기에서항상같은결과가난다고일반화하지않는다.

screen reader·터치목표

별모양만보이는버튼을소리로구별하고누를수있을까?

준비 개념과 학습 목표

준비 개념

  • 버튼의기능과상태
  • 길이와면적

학습 목표

  • 보이는모양과접근가능한의미를구분한다
  • 터치영역과그림크기를분리한다
  • 실제보조기기/사용자점검의범위를설계한다

기능이전달되는이름을준다

스크린리더는화면요소의이름·역할·상태같은의미정보로사용자의탐색을돕는다. 단순히검은별이라고부르기보다무엇을하는지알수있게설명한다. 읽혀야하는텍스트는이미Text자체로전달될수있어중복contentDescription을무조건붙이지않는다.

아이콘버튼의기능이저장이라면저장처럼목적을전하고버튼역할은Role등으로구별한다. 장식그림은다른요소의설명을반복하지않도록장식으로처리할수있다. 상태가저장됨/저장안됨처럼변하면실제낭독에서어떻게전달되는지도점검한다.

그림과손가락영역은다르다

Android문서는터치인터페이스의상호작용영역을최소48dp×48dp로권장한다. dp는밀도독립의레이아웃단위이며여기서실제화면픽셀이나센티미터로측정하지않는다. 그림이24dp여도주변여백을포함한터치영역은48dp일수있다.

사용자정의컨트롤에서는범위를명시하고이웃영역과불필요하게겹치지않도록설계한다. 영역을크게만들었다고이름·탐색순서·기능도올바른것은아니다. 마우스/트랙패드같은정밀입력권장과터치권장을같게일반화하지않는다.

실제흐름을확인한다

TalkBack에서는순서대로요소를탐색하거나화면의위치를탐색해목적을듣고현재요소를활성화할수있다. 이름이적절한지·핵심작업을끝낼수있는지·임시메시지가전달되는지확인한다. 설정이나제스처는보조기기환경에따라확인한다.

정적semantics/크기표·자동검사·실제보조기기조작·사용자피드백은각기근거를보탠다. 아래는설계표판정이며실제음성출력이나터치오작동을관측한것은아니다. 아직하지않은기기와학생검사는미수행으로남긴다.

중간 과정을 따라가는 예제

아이콘24dp×24dp를중앙에두고좌우상하12dp의터치여백을더한다. 이름은강의저장,역할버튼,상태저장안됨이라는설계표다. 영역과설명의의미를판정하라.

  1. 폭/높이는24+12+12=48dp라권장48×48목표를만족하는설계다.
  2. 그림면적24×24=576dp²,터치영역48×48=2304dp²로4배다. 실제픽셀측정아니다.
  3. 강의저장은목적을전하고역할/상태도별도표에있다. 실제로이이름/상태가낭독되거나활성화되는지는기기검사가필요하다.

터치영역48×48·그림의4배,목적있는설계표다. 실제접근성전체통과증거는아니다.
