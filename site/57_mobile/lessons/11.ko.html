소단원 11.1

ViewModel·UI 테스트

숫자 상태가 바뀌었는데 화면에는 옛 숫자가 남을 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 상태와 이벤트

  • 입력과 기대값

학습 목표

  • 상태 규칙과 화면 관측을 나눈다

  • 정상/경계/거절 상태를 추적한다

  • UI 동기화와 실제 수행을 구별한다

마지막 값이 1로 같으면 경계 버그도 없다고 할 수 있을까?

본문의 정상 count는 0에서 시작하며 Add가 3에서 더 늘리지 않고 Reset은 0으로 만든다. 자체 변이 M은 경계에서 잘못 늘려 4까지 허용하지만 Reset은 정상이다. 입력 Add 네 번, Reset, Add의 최종 값은 둘 다 1이다. 마지막 값만 확인하는 검사는 이 경계 오류를 구별하지 못한다.

상태열을 보면 정상은 0→1→2→3→3→0→1이고 M은 0→1→2→3→4→0→1이다. 네 번째 Add 직후의 기대 3과 실제 4가 판별 지점이다. 여기서 실제란 자체 변이 규칙에 따라 계산한 결과이며 실행한 앱 관측값이 아니다. 기대값은 검사 대상의 최종값을 복사하지 않고 먼저 정한 규칙에서 독립적으로 구한다.

동기화의 범위도 확인한다. Compose의 UI 동기화나 가상 시계가 모든 외부 네트워크 작업을 자동 완료시키는 것은 아니다. 자체 외부 작업이 벽시계 80 ms에 완료된다고 가정해도 가상 UI 시계 100 ms만 전진시켰다는 기록으로 완료를 확정하지 않는다. 실제 완료 조건, 적절한 대기 또는 동기화 자원, 제한 시간을 정의해야 한다.

먼저 확인할 개념
  • 초기·경계·Reset 기대값

    같은 최종값을 만드는 중간 경계 오류를 찾는다.

  • 비동기 결과와 현재 화면

    화면의 idle과 외부 작업의 완료 조건을 구별한다.

상태를 만드는 규칙

ViewModel은 화면에 필요한 상태와 처리 논리를 제공할 수 있다. 검사는 초기 상태와 이벤트 후 상태를 독립 기대값과 비교한다. 주변 저장소나 시각 같은 의존성을 대역으로 통제했다면 그 사실도 기록한다.

자체 count 규칙은 정수 0–3을 상태로 갖고 초기값은 0이다. Add는 3 미만이면 1 증가시키고 3에서는 유지하며, Reset은 0으로 만든다. 반환 상태를 예상값과 비교하는 것은 ViewModel 단위의 질문이며 실제 버튼 연결의 증거가 아니다.

화면은 다른 연결을 포함한다

UI 검사는 의미가 부여된 화면 요소를 찾아 사용자 조작을 보내고 표시·활성 여부를 확인한다. Compose 테스트는 semantics와 테스트 API를 이용한다. 화면상태를 읽는 연결이나 버튼 이벤트가 빠지면 상태 규칙은 맞아도 사용자 흐름은 실패한다.

비동기 작업이나 UI 재구성이 끝나기 전에 비교하면 아직 갱신되지 않은 화면을 읽을 수 있다. 적절한 동기화와 대기 조건을 설계하고 무조건 긴 시간 잠드는 방법만으로 결과가 안정적이라고 단정하지 않는다. 이 단원은 실제 테스트 도구를 실행하지 않는다.

경계와 결과를 함께 적는다

count 3에서 Add의 상태 유지를 확인하고, 화면이 버튼을 비활성화하도록 설계했다면 그 UI 정책도 별도로 검사한다. 상태 규칙과 버튼 정책은 관측 지점이 다르다. Reset 뒤 상태가 0으로 돌아가는지와 화면에 숫자 0이 표시되는지를 나누어 보면 실패 위치가 보인다.

초기 상태·여러 이벤트·한계 도달·Reset 뒤 재시작을 종이 표로 추적한다. 예상값과 실제값 칸을 나누어 앱을 아직 실행하지 않은 칸은 미관측으로 남긴다. 상태 검사 통과는 화면 크기·접근성·프로세스 복구까지 증명하지 않는다.

중간 과정을 따라가는 예제

자체 count 규칙에 Add, Add, Add, Add, Reset, Add를 차례로 보낸다. 초기값은 0이며 상태 변경 뒤 UI가 최신 상태를 읽는다고 가정한다.

  1. 첫 세 Add 뒤 상태는 1,2,3이다. 네 번째는 count가 3이므로 3으로 유지한다.

  2. Reset 뒤 0, 마지막 Add 뒤 1이다. 상태열은 0→1→2→3→3→0→1이다.

  3. UI가 최신 상태를 읽는다는 가정에서는 각 숫자를 표시한다. 실제 앱의 낭독·표시·클릭 성공은 미확인이다.

최종 count는 1이다. 단위 규칙의 예상과 가정한 UI 표시는 실제 관측이 아니다.

조건을 바꾸어 비교하기

끝값만 검사하는 약점

정상과 M의 최종 1만 검사하면 경계 오류를 찾을 수 있는가?

  1. Reset 이전의 3과 4가 Reset으로 모두 0이 된다.

  2. 마지막 Add는 두 경우 모두 1이다.

이 검사로는 구별하지 못한다. 네 번째 Add 직후 상태 3을 확인하는 기대를 추가한다.

비교할 점

나중의 재설정이 이전 오류의 흔적을 지울 수 있다.

가상 시간과 외부 완료

가상 UI 시계를 100 ms 전진시켰지만 외부 작업의 완료 관측은 없다. 벽시계 80 ms 완료 가정을 근거로 완료됐다고 할 수 있는가?

  1. 가상 시계와 벽시계는 서로 다른 시간 축이다.

  2. 외부 작업이 완료됐다는 조건은 관측하지 않았다.

확정할 수 없다. 외부 결과를 기다리는 조건과 제한 시간을 별도로 설계한다.

비교할 점

UI 시계의 전진량을 실제 네트워크 경과 시간으로 바꾸지 않는다.

종이와 본문으로 직접 해보기

UI 버튼에 Add가 연결되지 않아 눌러도 이벤트가 전달되지 않는다. 초기값 0에서 두 번 누르면? ViewModel에 직접 Add를 두 번 보낸 검사와 비교하라.

오해와 반례

ViewModel 기대값만 맞으면 버튼 표시와 조작도 확인됐다.

이벤트 연결이 없어도 직접 호출은 통과할 수 있다. 화면 노드·조작·표시 확인을 포함한 별도 검사가 필요하다.

회전·종료·네트워크 검사

화면을 돌린 것과 앱 프로세스가 사라진 것은 같은 사건일까?

준비 개념과 학습 목표

준비 개념

  • 메모리와 저장소

  • 앱의 상태

학습 목표

  • 구성 변경과 프로세스 종료를 구별한다

  • 복구값과 영속 데이터를 분리한다

  • 네트워크 실패와 오래된 결과를 검사한다

검색어가 A로 돌아왔으면 옛 A 응답을 다시 받아도 될까?

자체 검색은 같은 프로세스 세대 P에서 A를 요청 번호 1, B를 번호 2, 다시 A를 번호 3으로 요청한다. 현재는 (P,3,A)다. 오래된 첫 A 응답 (P,1,A)에 결과 5건, 새 A 응답 (P,3,A)에 결과 2건을 가정한다. 검색어 문자열만 비교하면 두 응답을 구별하지 못한다.

현재 작업의 정체성은 프로세스 세대와 요청 번호로 비교한다고 정한다. 새 A 결과 2건을 표시한 뒤 첫 A 결과 5건이 늦게 오면 (P,1)≠(P,3)이므로 거른다. 이는 오래된 결과의 화면 반영 정책이지 서버 처리 취소의 증거가 아니다. 같은 문자열의 반복 요청은 서로 다른 자료 시점이나 조건을 가질 수 있다.

세대도 필요한 범위를 명시한다. 시스템 process death 뒤 새 Q에서 요청 번호를 1부터 다시 시작했다면 옛 P의 응답이 새 Q로 자동 넘어온다고 주장하지 않는다. 다만 외부 대기열이나 대역이 옛 결과를 재전달하는 자체 시험 시나리오에서는 (P,1)과 (Q,1)을 구별해야 한다. saved state의 작은 검색어 복구, 메모리 결과 소실, 지속 자료 재조회는 이 요청 정체성과 별도의 저장 계약이다.

사건을 같은 이름으로 묶지 않는다

Android의 구성 변경으로 화면이 재생성될 때 적절히 scoped ViewModel의 메모리 상태는 유지될 수 있다. 시스템이 프로세스를 종료하면 그 메모리는 사라진다. 사용자가 화면을 완전히 닫은 사건과 시스템 복구도 같은 조건이 아니다.

saved state는 작은 검색어·선택 ID 같은 복구 정보를 남기고 데이터는 저장소에서 다시 읽는 방식에 적합하다. 큰 이미지나 전체 복잡한 객체를 모두 넣지 않는다. saved state의 수명주기 저장 시점과 사용자 dismissal 뒤 복구 제한도 있어 모든 종료에서 자동 복구한다고 말하지 않는다.

복구할 것을 각각 정한다

교육 검색 앱은 검색어를 saved state에, 즐겨찾기 3건을 disk에, 검색 결과 2건을 ViewModel 메모리에 둔다. saved state가 정상 확보된 뒤 시스템의 process death가 발생하고 복구가 지원되는 상황으로 한정한다.

회전에서는 살아 있는 같은 scope의 검색어와 결과를 쓸 수 있다. process death 복구에서는 검색어를 복구해 결과를 다시 요청하고 disk의 즐겨찾기를 다시 읽는다. 네트워크가 없으면 재조회 실패나 offline 표시를 다루며 확보하지 못한 결과를 있는 것처럼 표시하지 않는다.

요청의 시간 순서도 검사한다

네트워크 검사에는 성공뿐 아니라 실패·timeout·재시도·느린 응답을 포함한다. 자체 정책은 새 검색에 증가하는 ID를 붙여 현재 ID의 응답만 표시한다. 서버 취소 성공을 가정하지 않고 오래된 응답을 화면 갱신에서 거르는 규칙이다.

응답이 없다고 서버 처리가 없었다고 단정할 수 없다. 쓰기 작업의 재시도는 중복 효과를 검토하고, 검색 결과에는 빈 성공과 실패를 구별한다. 종이 이벤트 표로 기대와 원인을 추적하고 실제 기기의 회전·프로세스·네트워크 실험은 별도로 수행한다.

정사각형과 긴 직사각형의 면적이 같으면 터치 목표도 같은가?

자체 목표 A는 폭 48 dp, 높이 48 dp이며 B는 폭 24 dp, 높이 96 dp다. 둘 다 면적은 2304 dp²다. 그러나 최소 폭과 높이 각각 48 dp를 검사하는 이 설계 기준에서는 A가 맞고 B는 폭이 부족하다. 면적 하나만 비교하면 좁은 목표의 문제를 놓친다.

접근 가능한 의미와 그림의 개수도 나눈다. 자체 저장 버튼 안의 장식 별과 텍스트 강의 저장은 그림 두 요소지만 하나의 목적을 가진 버튼으로 표현할 수 있다. 테스트의 병합 semantics 트리와 비병합 트리는 다른 관측 방식이다. 테스트에서 노드 하나를 찾았다는 사실을 실제 TalkBack이 정확히 한 번 말하거나 사용자가 과제를 성공했다는 증거로 쓰지 않는다.

별개 삭제 버튼은 저장과 다른 기능이므로 목적과 조작을 구별해야 한다. 저장·삭제를 모두 하나의 이름 강의 버튼으로만 설명하면 어떤 행동을 선택하는지 사라질 수 있다. 동일 기능의 장식 요소를 묶는 것과 서로 다른 기능을 숨기는 것은 다른 설계다. 최종 점검에는 입력 방법별 탐색, 이름·역할·상태, 실제 조작과 과제 수행의 관측이 필요하다.

기능이 전달되는 이름을 준다

스크린리더는 요소의 이름·역할·상태 같은 의미 정보로 탐색을 돕는다. 단순히 검은 별이라고 부르기보다 무엇을 하는지 알 수 있게 설명한다. 읽혀야 하는 텍스트는 Text 자체로 전달될 수 있어 중복 contentDescription을 무조건 붙이지 않는다.

아이콘 버튼이 저장 기능이면 저장처럼 목적을 전하고 버튼 역할은 Role 등으로 구별한다. 장식 그림은 다른 요소의 설명을 반복하지 않도록 처리할 수 있다. 저장됨·저장 안 됨처럼 상태가 바뀌면 실제 낭독에서 어떻게 전달되는지도 점검한다.

그림과 손가락 영역은 다르다

Android 문서는 터치 인터페이스의 상호작용 영역을 최소 48dp×48dp로 권장한다. dp는 밀도 독립 레이아웃 단위이며 여기서 실제 화면 픽셀이나 센티미터로 측정하지 않는다. 그림이 24dp여도 여백을 포함한 터치 영역은 48dp일 수 있다.

사용자 정의 컨트롤에서는 범위를 명시하고 이웃 영역과 불필요하게 겹치지 않도록 설계한다. 영역을 크게 만들었다고 이름·탐색 순서·기능도 올바른 것은 아니다. 마우스·트랙패드 같은 정밀 입력 권장과 터치 권장을 같게 일반화하지 않는다.

실제 흐름을 확인한다

TalkBack에서는 요소를 순서대로 탐색하거나 화면 위치를 탐색해 목적을 듣고 현재 요소를 활성화할 수 있다. 이름이 적절한지, 핵심 작업을 끝낼 수 있는지, 임시 메시지가 전달되는지 확인한다. 설정과 제스처는 보조기기 환경에 따라 확인한다.

정적 semantics·크기 표·자동 검사·실제 보조기기 조작·사용자 피드백은 각각 근거를 보탠다. 아래는 설계표 판정이며 실제 음성 출력이나 터치 오작동을 관측한 것이 아니다. 하지 않은 기기와 학생 검사는 미수행으로 남긴다.
