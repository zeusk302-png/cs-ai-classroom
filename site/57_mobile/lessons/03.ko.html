소단원 3.1

입력이벤트

증가 버튼을 한 번 눌렀는데 같은 요청이 두 번 도착하면 숫자는 어떻게 되어야 할까?

준비 개념과 학습 목표

준비 개념

  • 상태는 현재 값을 담는 묶음이다. 여기서는 정수 count와 이미 처리한 ID 집합 seen을 함께 쓴다. 집합에는 같은 원소가 두 번 들어가지 않는다.

  • 이벤트는 입력 의도를 나타내는 자료다. (1, Inc)의 1은 사건 ID이고 Inc는 증가라는 종류이며 화면 평가 횟수가 아니다.

  • 함수 δ(S,e)는 이전 상태와 이벤트를 받아 다음 상태를 만든다. 순차 처리는 한 전이를 끝낸 뒤 다음 전이를 시작한다.

학습 목표

  • 이벤트·상태·UI 기술을 각각 구분한다.

  • 중복 ID와 순서가 상태에 미치는 영향을 추적한다.

  • 자체 전이 규칙의 불변량과 Android 전달 보장의 차이를 설명한다.

포화되어 숫자가 안 늘어난 사건도 처리 이력에 남겨야 할까?

본문의 순차 규칙 S = (count, seen)을 그대로 쓴다. 새 Inc는 min(3,count+1), 새 Reset은 0으로 바꾸고 두 사건 모두 ID를 seen에 추가한다. 같은 ID의 재전달은 같은 종류라는 계약이며, 이미 처리한 ID는 무시한다. 상태를 [count만]으로 줄이면 같은 표시 뒤에 숨은 다른 처리 이력을 잃는다.

자체 시작 상태는 count = 3, seen = {1,2,3}이다. 새 (4,Inc)를 받으면 숫자는 3에 머물지만 seen에는 4를 넣는다. 이어 새 (5,Reset)를 받으면 count = 0이고 seen은 {1,2,3,4,5}다. 마지막 (4,Inc)는 재전달이므로 0을 유지한다. 포화 당시 숫자를 바꾸지 않았다는 이유로 ID 4를 기록하지 않으면 마지막 재전달이 새 증가로 오인된다.

seen을 작게 만들려고 오래된 ID를 삭제하는 정책에는 재전달 가능 기간·ID 재사용·영속 상태의 원자 갱신 같은 별도 계약이 필요하다. 이 단원의 유한 추적은 그런 기간 보증 없이 이력을 지워도 안전하다고 증명하지 않는다. Android UDF는 상태와 사건의 흐름을 설명하며 이 자체 중복 ID 프로토콜을 제공한다는 뜻은 아니다.

먼저 확인할 개념
  • 중복 ID와 포화 전이

    포화에도 ID 기록이 필요한 이유를 확인한다.

  • 메모리와 복원 경계

    count만 남기고 seen을 잃는 상황을 구별한다.

사건에서 상태를 거쳐 표시로 간다

단방향 흐름은 UI가 사건을 소유자에게 올리고, 소유자가 상태를 갱신한 뒤 UI에 상태를 내려주는 구조다. UI는 현재 상태로 텍스트와 활성 여부를 기술한다. 예를 들어 count가 2이면 숫자 2와 증가 가능한 버튼을 설명한다. 다시 설명하는 일이 증가 입력은 아니다.

이벤트 콜백은 사용자의 의도를 전달하며 단순 표시 갱신과 구별된다. TextField의 변경 요청도 새 문자열을 소유자에게 전달하고, 소유자가 승인한 value를 다시 UI에 준다. 이 경계가 입력 검증과 상태 전이의 위치를 분명하게 한다.

중복 처리 정책을 명세한다

자체 모형의 S=(count,seen)은 0≤count≤3인 정수와 유한 ID 집합이다. 시작은 (0,∅)이다. ID는 비음수 정수이며 새 논리 의도마다 새 ID, 같은 ID의 재전달은 같은 종류라는 계약을 둔다. 종류는 Inc 또는 Reset뿐이다. seen에 있는 ID는 무시하고, 새 Inc는 min(3,count+1), 새 Reset은 0을 저장한 뒤 ID를 seen에 추가한다.

이 규칙은 중복 전달에 대한 정책이지 Android가 이벤트를 정확히 한 번 전달한다는 주장도, 클릭 중복이 모두 동일 ID라는 주장도 아니다. Reset도 seen을 비우지 않으므로 과거 ID는 계속 무시한다. 메모리는 처리한 ID 수에 따라 늘고, seen을 잃는 재시작에는 별도 저장 계약이 필요하다.

순차성·결정성과 화면 평가를 분리한다

유효한 유한 이벤트 열과 초기 상태가 같으면 순차 전이의 최종 상태가 같다. 그러나 순서를 바꾸면 결과가 달라질 수 있다. 0에서 새 Inc 뒤 새 Reset은 0, 역순은 1이다. 두 저장 갱신을 동시에 읽고 덮어쓰면 이러한 순차 추적과 달라질 수 있으므로 소유자는 전이를 직렬화하거나 적절한 원자 갱신을 보장해야 한다.

Compose는 관찰 가능한 상태를 읽은 부분의 재구성을 예약할 수 있다. 일부 실행은 건너뛰거나 취소될 수 있어 이벤트 수와 화면 본문 호출 수를 일대일 대응시키면 안 된다. 아래 Python은 실제 실행한 순차 상태 모형이고 Android 입력 전달·UI 스케줄링을 구현한 앱이 아니다.

from dataclasses import dataclass

@dataclass(frozen=True)
class State:
    count: int = 0
    seen: frozenset[int] = frozenset()

def reduce_event(state: State, event: tuple[int, str]) -> State:
    event_id, kind = event
    if type(event_id) is not int or event_id < 0 or kind not in ("Inc", "Reset"):
        raise ValueError("invalid event")
    if event_id in state.seen:
        return state
    count = min(3, state.count + 1) if kind == "Inc" else 0
    return State(count, state.seen | {event_id})

if __name__ == "__main__":
    state = State()
    for event in [(1, "Inc"), (1, "Inc"), (2, "Inc"), (3, "Reset"), (4, "Inc")]:
        state = reduce_event(state, event)
        print(state.count, len(state.seen))
    for events in [[(10, "Inc"), (11, "Reset")], [(11, "Reset"), (10, "Inc")]]:
        state = State()
        for event in events:
            state = reduce_event(state, event)
        print("order", state.count)

소단원 3.2

상태소유와 ViewModel

입력란과 미리보기의 검색어가 다르면 어느 쪽이 진짜 현재 값일까?

준비 개념과 학습 목표

준비 개념

  • 소유자는 상태의 변경 규칙과 현재 값을 관리하는 주체다. 읽는 곳이 여러 개여도 변경 권한과 기준 값을 하나로 정할 수 있다.

  • 트리의 공통 조상은 여러 자식에서 위로 올라가 만나는 노드다. 가장 낮은 공통 조상은 함께 필요한 값을 불필요하게 더 위로 올리지 않는 기준이다.

  • 범위(scope)는 여기서 상태 소유 객체를 공유하고 유지하는 경계다. 화면 A와 화면 B라는 이름만으로 동일한 객체 공유를 결정하지 않는다.

학습 목표

  • 공유 상태와 요소별 상태의 소유 위치를 정한다.

  • ViewModelStoreOwner와 키를 기준으로 공유 범위를 설명한다.

  • 구성 변경·owner 제거·프로세스 종료를 분리한다.

같은 클래스라도 owner와 키가 다르면 같은 상태일까?

자체 provider 장부는 각 owner의 store 안에서 키별로 ViewModel을 보관한다고 정한다. 처음 (owner A, key search)는 객체 M1, (owner A, key detail)은 M2, (owner B, key search)는 M3를 만든다. 같은 클래스 이름을 사용해도 owner·키의 조합이 다르면 이 모형의 객체는 다르다.

A/search의 query를 도서로 바꾸면 M1을 공유하는 두 소비자만 그 기준 값을 읽는다. A/detail의 query 과학과 B/search의 query 음악은 독립적이다. 같은 유지된 A/search를 다시 요청하면 M1이다. A owner가 영구 제거된 뒤 같은 화면 이름의 새 owner A′에서 search를 요청하면 M4를 초기화한다. 저장 복원·의존성 factory 변화는 이 비교에 없다.

소유권은 객체 공유뿐 아니라 변경 권한과 수명을 정한다. query를 함께 읽고 쓰는 입력·미리보기는 최소 공통 소유자에 둔다. 입력에만 필요한 일시적 펼침 상태는 가까이에 둘 수 있다. 공유 owner를 넓히면 서로 관련 없는 화면이 같은 값을 바꿀 수 있으므로 실제 요구를 먼저 정한다.

기준 값 하나와 읽기 경로를 정한다

검색 입력란과 결과 미리보기가 같은 query를 읽는다면 각각 독립 복사본을 진실의 원천으로 두지 않는다. 함께 읽고 쓰는 최소 공통 소유자에 query를 두고, 자식에게 현재 값과 변경 요청 콜백을 제공한다. 한 번 승인된 상태에서 두 표시를 계산하면 서로 다른 복사본 갱신 시점을 관리하는 부담이 줄어든다.

모든 상태를 앱 최상위로 올려야 한다는 뜻은 아니다. 입력란의 일시적인 펼침 여부처럼 다른 요소가 필요로 하지 않는 값은 가까이 둔다. 여러 요소가 함께 필요한 UI 논리에는 일반 상태 소유 클래스도 가능하다. 화면 데이터 준비와 비즈니스 논리에 접근하는 화면 수준 소유자에는 Android ViewModel을 사용할 수 있다.

ViewModel의 소유 범위는 명시한다

Android ViewModel은 ViewModelStoreOwner에 연결된 상태 소유 구현이다. 예를 들어 내비게이션 항목 A와 B에 서로 다른 owner를 두면 각 query는 독립적이다. 일반적인 store/provider 계약에서 같은 owner와 같은 키로 요청하면 같은 ViewModel을 얻는다. 클래스를 같은 이름으로 썼다는 이유만으로 모든 화면이 한 인스턴스를 공유하지 않는다.

두 목적지에서 의도적으로 공유할 값이면 공통 내비게이션 그래프 등 적절한 owner 범위를 선택한다. 넓은 범위는 더 오래 유지되고 더 많은 화면이 같은 변경을 보게 하므로 요구에 맞춰 결정한다. ViewModel을 모든 자식에게 통째로 넘기기보다 필요한 불변 상태와 이벤트만 내려주면 자식의 책임과 교체 가능한 경계가 드러난다.

메모리 유지와 영속 보장은 다르다

구성 변경으로 Activity와 UI가 재생성될 때 유지되는 owner store에 연결된 ViewModel은 살아 있고 새 UI가 그 상태를 읽을 수 있다. 그러나 owner가 영구 제거되는 내비게이션 pop이나 Activity 종료에는 정리 경계가 생긴다. 프로세스가 죽으면 ViewModel 인스턴스와 메모리 상태도 사라진다. 프로세스 후 최소 UI 상태 복원과 영속 데이터는 다음 소단원의 별도 책임이다.

ViewModel이라는 이름은 동시 갱신을 원자화하거나 데이터 저장을 자동 완료하지 않는다. 두 이벤트가 같은 낡은 값을 읽고 각각 덮어쓰는 반례를 막으려면 직렬 처리나 갱신 API의 계약이 필요하다. 이 단원의 사건표는 순차·외부 변경 없음·정의된 owner 유지 조건을 두며 실제 내비게이션이나 수명주기 관찰로 제시하지 않는다.

준비 개념과 학습 목표

준비 개념

  • 재구성은 변경된 관찰 상태를 바탕으로 UI의 필요한 부분을 다시 기술하는 일이다. 버튼 입력이나 Activity 재생성과 동일한 사건이 아니다.

  • 저장 스냅샷은 특정 시점 값의 사본이다. 스냅샷 후 바뀐 값이 자동으로 그 사본에 포함되지는 않는다.

  • 복원은 남아 있는 자료로 새 객체의 상태를 다시 구성하는 일이다. 기존 객체가 살아 있다는 것과 구별하며, ID는 큰 데이터를 다시 찾는 작은 식별 값이다.

학습 목표

  • remember·rememberSaveable·SavedStateHandle의 보존 범위를 구별한다.

  • 구성 변경·시스템 프로세스 종료·사용자 task 제거의 다른 결과를 추적한다.

  • 재구성 본문과 수명주기를 가진 효과를 분리한다.

저장 왕복이 맞아도 마지막 메모리 값의 복원이 보장될까?

자체 복원 자료 x = (query,selectedId)는 작은 문자열과 정수 ID다. encode가 두 값을 손실 없이 저장하고 decode가 같은 정책으로 읽으면 지원 값에 대해 decode(encode(x)) = x라는 왕복 계약을 만들 수 있다. 문자열의 바깥 공백을 지우는 encode는 query = 가와 query = 공백 가 공백을 같은 값으로 바꿔 원래 입력을 구별하지 못한다.

왕복 계약은 어느 시점의 x가 저장되었는지까지 결정하지 않는다. 자체 완료 스냅샷은 (가,9), 현재 메모리는 이후 (나,12)로 바뀌었다. 새 저장이 완료되지 않고 기존 스냅샷이 제공되면 복원은 (가,9)다. ID 9로 다시 읽은 큰 결과의 현재 내용이 과거와 같다는 보장도 없다.

SavedStateHandle의 저장 시점 조건과 task의 보존 범위를 확인한다. stopped 중 변경은 다시 onStart/onStop을 거치지 않으면 저장되지 않을 수 있다. LaunchedEffect의 로컬 작업 취소도 이미 완료한 외부 업무의 롤백이 아니다. 복원 자료의 왕복, 최신 시점, 데이터 재조회, 업무 중복 방지를 각각 요구로 적는다.

재평가되는 UI와 기억 위치

Compose는 관찰 상태 변화에 따라 필요한 부분을 재구성하며 일부 본문을 건너뛰거나 취소할 수 있다. 따라서 UI 기술은 빠르고 반복 평가해도 입력 의도를 몰래 실행하지 않도록 작성한다. 본문에서 전역 결제 횟수를 증가시키면 다시 기술하는 것만으로 결제가 추가되는 반례가 된다.

remember는 Composition의 해당 호출 위치에 값을 기억한다. 일반적인 같은 위치의 재구성에는 유지되지만 그 위치가 Composition에서 제거되거나 Activity 재생성으로 새 Composition이 만들어지면 자체적으로 복원하지 않는다. Composable은 remember·관찰 상태·주변 환경을 사용할 수 있으므로 모든 Composable을 수학적 순수함수나 같은 명시 인자만 보는 참조투명 함수라고 일반화하지 않는다.

무엇을 어디까지 복원할 것인가

rememberSaveable은 저장 가능한 작은 UI 상태를 저장 상태 경로에 연결한다. 기본 지원 자료형이나 알맞은 Saver 등의 변환이 필요하며 Bundle 크기 제한을 고려한다. SavedStateHandle은 ViewModel의 작은 복원 키/값을 다루는 경로다. ViewModel 자체는 구성 변경 동안 유지될 수 있지만 시스템 프로세스 종료 후에는 새 인스턴스가 만들어지고 저장된 최소 값으로 상태를 재구성한다.

프로세스 복원 예제는 시스템이 종료한 뒤 task가 남아 있고 유효한 저장 스냅샷이 제공되는 조건이다. 사용자 task 제거·finish·강제 종료·재부팅까지 saved state가 영속 기록처럼 보장한다고 하지 않는다. 공식 문서는 Activity가 stopped일 때 쓴 값이 다시 onStart와 onStop을 거치지 않으면 저장되지 않을 수 있음을 명시한다. 큰 검색 결과 전체 대신 작은 검색어/선택 ID를 저장하고 데이터 계층에서 새로 읽는다.

효과와 복원은 별도 계약이다

UI 관련 비동기 효과가 필요하면 LaunchedEffect 같은 정해진 효과 경계를 사용한다. 해당 Composition 진입 때 작업을 시작하고, 키가 바뀌면 기존 coroutine을 취소하고 새 작업을 시작하며, 이탈하면 취소한다. 상수 키는 그 인스턴스의 진입 기간을 기준으로 하므로 앱 전체에서 영원히 단 한 번 실행한다는 뜻이 아니다.

취소는 이미 외부에 커밋된 일을 되돌린다는 보장이 아니다. 복원으로 새 Composition이 진입하면 효과도 다시 시작할 수 있어 결제·주문 같은 업무의 중복 방지는 UI 평가 횟수가 아닌 업무 ID/서버 정책에 두어야 한다. 아래 표는 명시한 저장 조건의 종이 추론이며 coroutine 취소·원격 결과·실제 UI 또는 수명주기를 실행해서 검증한 결과가 아니다.

focus=True는 remember, draft=나 는 rememberSaveable, filter=active는 SavedStateHandle에 저장한다. ViewModel의 검색 결과 R은 재조회하는 큰 데이터다. 복원 가능한 저장 스냅샷은 완료되었으며 구성 변경의 owner store는 유지된다. 각 사건을 따로 초기 상황에서 비교하라.

  3. 시스템 프로세스 종료 후 task와 스냅샷을 이용해 재생성하면 새 ViewModel이 생긴다. focus=False, draft=나, filter=active를 복원하고 R은 재조회한다. 새 R이 과거 R과 같다고 보장하지 않는다.
