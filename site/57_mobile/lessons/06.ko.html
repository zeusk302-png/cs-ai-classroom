소단원 6.1

지연목록과 재사용

과목이 만 개이면 화면 밖의 카드도 모두 만들어야 할까?

준비 개념과 학습 목표

준비 개념

  • viewport는 현재 보이는 화면 영역이다.

  • 데이터 항목 ID와 화면의 순번은 다르다.

  • 재사용은 같은 표시 자원을 다른 항목에 연결하는 방식이다.

학습 목표

  • 지연 구성과 데이터 전체 보관을 구별한다.

  • 항목 정체성과 위치의 차이를 추적한다.

  • 재사용 시 남은 상태를 초기화할 조건을 설명한다.

400 px 창에는 80 px 행이 언제나 다섯 개만 보일까?

본문의 다섯 행 계산에는 정확히 행 경계에서 시작한다는 조건이 있었다. 자체 긴 균등 목록의 행 i는 [80i,80(i+1)) px이고 viewport는 [s,s+400) px다. 길이가 양수인 교집합이 있으면 보이는 행으로 센다. s = 800이면 행 10..14 다섯 개, s = 820이면 행 10..15 여섯 개가 일부 보인다.

s = 820의 첫 행 10은 60 px, 마지막 행 15는 20 px가 보인다. 중간 네 행은 각각 80 px라 60 + 320 + 20 = 400 px다. 양쪽 예비 행을 각각 한 개 둔 자체 정책은 중간 위치에서 다섯 가시 행이면 일곱, 여섯 가시 행이면 여덟 행을 구성한다. 실제 Compose의 예측·캐시·구성 개수를 측정한 것이 아니다.

행 높이가 다르면 같은 viewport 길이와 위치 변화만으로 보이는 개수가 바뀐다. 정체성의 키와 가시 위치도 별도다. 안정 키는 상태를 항목에 연결하는 기준이고 행의 실제 높이·자료 검색·정렬·통신 비용을 자동으로 상수로 만드는 도구가 아니다.

먼저 확인할 개념
  • viewport와 행 경계 조건

    보이는 행 수의 나눗셈이 사용하는 정렬 조건을 확인한다.

  • 이미지 치수와 행의 공간

    자료 도착 뒤 높이 변화가 배치에 영향을 줄 수 있음을 확인한다.

보이는 범위부터 구성하기

목록 데이터가 N개라고 모든 카드가 동시에 화면에 보이지는 않는다. 지연목록은 화면에 필요한 부분을 중심으로 구성한다. 데이터 검색·정렬 자체가 자동으로 무료가 되는 것은 아니며, 화면 구성 비용과 데이터 처리 비용을 따로 생각한다.

자체 종이 모형은 항목 높이 80px, 화면 높이 400px, 정확히 행 경계에서 시작하는 수직 목록이다. 보이는 행은 5개이고 위·아래 예비 행을 각 1개 두면 최대 7행이다. 실제 프레임워크의 예측 구성·측정·캐시 정책은 이 7이라는 숫자로 보장하지 않는다.

표시 위치 대신 안정적 ID로 식별하기

자체 목록 [A,B,C]에서 B의 체크 상태를 기억한다고 하자. 맨 앞에 X를 삽입하면 B는 순번 2에서 3으로 이동한다. 순번에 상태를 묶으면 예전 두 번째 자리에 온 A가 B의 체크를 잘못 받을 수 있다. 항목의 안정적인 고유 ID를 사용하면 B의 상태를 B에 연결할 수 있다.

키는 같은 목록에서 유일하고 같은 항목의 정체성을 유지해야 한다. 같은 제목이 두 과목에 있을 수 있으므로 제목을 무조건 키로 쓰지 않는다. Compose에서 저장 가능한 항목 상태를 복원하려면 키의 지원 타입 조건도 확인한다. 안정적 키가 영구 데이터 저장을 자동 구현하는 것은 아니다.

재연결할 때 화면 상태를 점검하기

전통적인 행 재사용 모형에서 슬롯이 A의 이미지·체크 표시를 담다가 B에 연결되면 B의 값을 모두 반영해야 한다. 값이 없는 B의 이미지를 생략하면 A의 이미지가 남는 오류가 가능하다. placeholder와 선택 상태를 새 항목 기준으로 설정하는 책임을 명시한다.

비동기 응답도 항목 ID나 요청 세대를 확인해야 한다. A 이미지 요청이 늦게 도착했는데 슬롯은 이미 B라면 A 결과를 붙이지 않는다. Compose 지연 구성의 내부를 모든 시스템에서 같은 가변 슬롯으로 구현한다고 주장하지 않고, 정체성·표시 분리 원칙을 익히는 자체 모형으로 한정한다.

행과 viewport는 반열린 구간이다. 경계 한 점만 닿는 행은 보이는 것으로 세지 않는다. ID는 이 기하 모형의 고정 행 번호이며 실제 데이터 ID와 순번의 일반 동일성을 주장하지 않는다.

중간 과정을 따라가는 예제

N=1000인 자체 목록에서 첫 5행이 보이고 아래 예비 1행만 가능하다. 중간으로 이동해 보이는 5행과 양쪽 예비 1행씩이 있으면 각각 구성 행 수는?

  1. 시작 위치에서는 위 예비 행이 없으므로 5+0+1=6행이다.

  2. 중간에서는 5+1+1=7행이다.

  3. N=1000은 데이터 수이며 이 모형에서 동시 구성 수 6/7과 다르다. 내부 프레임워크의 실제 측정 수로 해석하지 않는다.

시작 6행, 중간 7행이다. 목록 전체 데이터 1000개를 없애거나 7개로 바꾸는 계산이 아니다.

조건을 바꾸어 비교하기

부분 행 두 개의 공간

s = 820의 여섯 행이 480 px를 차지하므로 화면 밖이라고 했다.

  1. 전체 행의 높이와 보이는 조각의 높이를 나눈다.

  2. 첫 60 + 중간 4×80 + 마지막 20을 합한다.

보이는 조각은 400 px다. 구성된 행 전체 길이가 viewport와 같은 것은 아니다.

비교할 점

부분 교집합을 세는 가시 개수와 전체 높이 합은 다른 계산이다.

가변 높이 목록의 같은 길이 창

높이가 80,160,80,160,… px다. [0,400)과 [80,480)의 보이는 행은?

  1. 누적 경계는 0,80,240,320,480,…다.

  2. 첫 창은 행 0,1,2,3과 겹친다.

  3. 둘째 창은 행 1,2,3과 겹친다.

각각 네 행과 세 행이다.

비교할 점

같은 창 높이여도 항목 높이와 시작 위치가 결과를 바꾼다.

종이와 본문으로 직접 해보기

[A,B,C]의 B만 체크되어 있다. X를 앞에 넣으면 ID 방식에서 체크된 항목과 새 위치는? 예전 순번 2의 상태를 그대로 쓰면?

힌트 보기

새 순서는 [X,A,B,C]다. 정체성과 위치를 별도 열에 적는다.

풀이 보기

ID 방식은 B가 새 세 번째 위치에서도 체크된다. 예전 두 번째 위치의 상태를 그대로 사용한 단순 모형은 A를 잘못 체크한다.

오해와 반례

지연목록을 쓰면 데이터 정렬과 네트워크 처리도 항상 상수 시간이다.

화면 일부 구성은 전체 데이터 정렬·통신 비용을 없애지 않는다. 천 개 ID를 정렬해야 하는 요청은 별도 작업이며 화면 행 수와 작업량이 다르다.

이미지로딩

사진 파일은 작아도 표시할 때 메모리가 많이 필요한 이유는?

준비 개념과 학습 목표

준비 개념

  • 압축 파일 크기와 디코딩한 픽셀 메모리는 다르다.

  • RGBA 모형은 픽셀당 4바이트다.

  • 요청 시작과 응답 도착 순서는 다를 수 있다.

학습 목표

  • 픽셀 메모리를 계산한다.

  • 로딩·성공·실패 화면을 구별한다.

  • 재사용된 행에 옛 이미지가 붙는 조건을 찾아낸다.

정사각형을 채우는 이미지와 전체 사진을 보여 주는 이미지는 같은 크기일까?

자체 원본은 2000×1000 px다. 표시 사각형은 100×100 dp, 밀도 2 px/dp이므로 실제 목표는 200×200 px다. fit은 원본 전체가 사각형 안에 들어가도록 비율을 유지하고, cover는 사각형을 빈틈 없이 채운 뒤 넘는 부분을 자르는 자체 이상적 크기 규칙이다.

fit의 배율은 min(200/2000,200/1000) = 0.1이며 크기는 200×100 px다. cover의 배율은 max(0.1,0.2) = 0.2이며 크기는 400×200 px다. 이 이상적 크기를 RGBA 4바이트/픽셀로 보관하면 각각 80,000 B와 320,000 B다. 실제 decoder의 subsampling·stride·색상 설정·추가 buffer는 별도이고 이 정확한 크기를 보장하지 않는다.

행의 ID가 A로 같아도 요청한 URL·자료 버전·치수·변형이 바뀌면 옛 응답은 현재 결과가 아닐 수 있다. 자체 요청 세대 7은 fit, 8은 cover라고 정한다. 현재 A/8에서 A/7 성공이나 실패를 무시해야 한다. ID만 검사하는 것으로 새 요구의 정체성을 충분히 나타내지 못한다.

압축 자료와 픽셀 배열을 구분하기

자체 사진은 2000×1000픽셀이고 RGBA 4바이트를 쓴다. 디코딩 픽셀만 8,000,000바이트다. 다운로드 파일이 200KB라는 정보만으로 표시 메모리가 200KB라고 계산하면 안 된다. 행 메타데이터·복사본·GPU 저장은 이 단순 비용에서 제외한다.

목표 화면에서 200×100픽셀 정도만 필요하다면 그 크기에 맞는 자료·디코딩을 고려한다. 여기서 200×100은 가상의 실제 픽셀 치수이며 dp와 혼동하지 않는다. 화면 배율·회전·자르기 정책에 따라 필요한 치수를 다시 정한다.

기다림과 실패도 이미지의 일부로 설계하기

요청 중에는 정해 둔 자리와 대체 표시를 보여 주고 성공하면 해당 사진으로 바꾼다. 실패는 다른 항목 사진을 남겨 두는 대신 실패 표시와 재시도 선택을 준다. 그림이 내용을 전달하면 대체 설명도 그 내용을 알려야 하며 장식만 하는 그림은 정책에 따라 구별한다.

캐시가 있어도 새 URL·크기·변형 조건이 다르면 같은 결과를 재사용할 수 없을 수 있다. 메모리 캐시는 무제한이 아니므로 제거 정책이 필요하다. 이 절은 특정 이미지 라이브러리 기본값을 구현하거나 캐시 적중률을 측정한 결과가 아니다.

응답을 현재 항목과 대조하기

자체 행 슬롯은 현재ID와 요청번호를 보관한다. A를 연결할 때 번호1을 시작했다가 B로 재연결하며 번호2를 시작한다. 응답은 완료 시 현재ID와 요청번호가 모두 맞는 경우만 붙인다. 뒤늦은 A응답은 현재B 화면과 다르므로 버린다.

같은 ID라도 이미지 URL이 바뀌어 새 요청을 시작할 수 있어 요청 세대 비교가 도움된다. 취소는 불필요한 작업을 줄이는 선택이지만 취소 요청만으로 모든 늦은 완료 가능성이 사라졌다고 가정하지 않는다. 아래 계산은 응답 적용 조건의 종이 추적이다.

2000×1000과 200×100 RGBA 이미지의 픽셀 바이트 및 비율을 계산하라. 메타데이터·복사·압축 파일은 제외한다.

  1. 큰 이미지 픽셀 수는 2,000,000이며 ×4=8,000,000바이트다.

  2. 작은 이미지는 20,000픽셀이며 ×4=80,000바이트다.

  3. 비율은 8,000,000/80,000=100이다. 가로·세로 각각 10배 감소로 픽셀 수가 100배 줄었다.

8,000,000B와 80,000B, 큰 쪽이 100배다. 십진 바이트로 계산했으며 실제 전체 앱 메모리 측정은 아니다.

숫자 키보드가 뜨면 입력값 검사는 더 필요 없을까?

준비 개념과 학습 목표

준비 개념

  • 입력 문자열과 파싱한 숫자는 다르다.

  • 키보드 종류는 입력 편의를 위한 요청이다.

  • 서버가 받는 자료도 독립 검증해야 한다.

학습 목표

  • 입력·검증·제출 상태를 구분한다.

  • 키보드 옵션과 데이터 제약의 차이를 설명한다.

  • 오류 때 입력을 보존하고 고칠 위치를 안내한다.

제출한 뒤 입력을 고쳤다면 응답은 어느 입력에 대한 답일까?

자체 신청 폼은 본문의 이름 trim 뒤 비어 있지 않음, 학점 ASCII 정수 1..5라는 조건을 쓴다. 수정 상태의 버전을 r1, r2처럼 증가시키고 제출 시점의 입력 사본과 요청 ID를 별도로 기록한다. 업무 처리의 실제 서버 멱등 정책은 이 표가 구현하지 않는다.

r1의 이름 민·학점 3을 요청 Q1로 제출한 뒤 사용자가 영·4로 수정해 r2가 되었다. Q1 성공은 서버가 명시한 r1 사본을 접수했다는 자체 응답 계약이다. 현재 r2까지 저장됐다는 뜻이 아니다. Q1 응답을 받았다고 r2 입력을 무조건 비우면 사용자의 새 작업을 잃을 수 있다.

실패 응답의 항목 오류도 어느 사본을 검증했는지 표시한다. 현재 입력이 달라졌으면 옛 오류를 현재 입력의 검증 결과로 덮어쓰지 않는다. 초안 보존·접수한 사본·현재 미제출 수정·재시도 결과를 구별하고 키보드 옵션은 값 검증의 보증으로 사용하지 않는다.

문자열에서 업무 값으로 바꾸기

자체 과목 신청 폼은 이름과 학점이다. 이름은 앞뒤 공백을 제거한 뒤 비어 있지 않아야 한다. 학점 문자열은 ASCII 정수 표기를 파싱하고 값은 1~5여야 한다. 3은 통과하지만 3.5와 세는 이 모형의 정수 문법을 통과하지 않는다. 실제 국제 입력 처리 정책은 별도로 정해야 한다.

표시 중인 텍스트와 검증 완료 값을 구분하면 사용자가 수정하는 동안 중간 문자열도 보존할 수 있다. 제출할 때 검증 결과를 계산하고 오류 항목을 알려 준다. 입력하다가 잠시 빈 문자열이 되었다고 바로 자료를 삭제하거나 의미 없는 0으로 변환하지 않는다.

키보드는 편의이고 검증은 규칙이다

숫자 입력용 keyboardType과 다음·완료 같은 imeAction은 사용자 흐름을 돕는다. Compose 공식 문서는 소프트웨어 키보드가 옵션을 항상 따르지 않을 수 있다고 설명한다. 붙여넣기·하드웨어 키보드·다른 입력 경로도 있으므로 숫자 배치만으로 규칙을 강제했다고 말하지 않는다.

다음 동작은 원하는 다음 필드로 초점을 보내고 완료는 명시한 검증·제출 동작으로 연결할 수 있다. 실제 IME별 동작과 화면 가림은 장비에서 확인해야 한다. 종이 설계는 이름→학점→제출 순서를 정의하지만 모든 기기에서 그 흐름을 실험한 것은 아니다.

오류를 고치고 다시 시도할 경로 주기

이름=" "·학점="6"이면 이름 비어 있음과 범위 오류 두 개를 표시한다. 오류 이유를 항목 가까이 알려 주고 다른 입력을 보존한다. 서버가 거절했을 때도 무엇이 저장되었는지 알려야 하며 전송 시작만으로 신청 완료를 표시하지 않는다.

클라이언트는 사용자에게 빠른 피드백을 주고 서버는 권한과 값 조건을 다시 검사한다. 검사를 없앤 요청도 서버에 도착할 수 있기 때문이다. 제출중 상태에서 중복 누름을 줄일 수 있지만 전송 재시도와 업무 중복 적용은 서버의 별도 정책이 필요하다.

풀이와 답 확인
