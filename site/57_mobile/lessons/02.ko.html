소단원 2.1

layout과 component

버튼과 제목이 같은 화면에 있는데 왜 겹치거나 창 밖으로 나갈까?

준비 개념과 학습 목표

준비 개념

  • 구성요소는 텍스트·버튼처럼 역할과 입력/출력을 가진 UI 부분이다. 화면에 그려진 사각형만으로 클릭·이름·상태가 정의되지는 않는다.
  • 트리는 한 부모 아래 자식들이 놓이는 구조다. 부모의 내부 좌표와 전체 창 좌표를 구분해야 한다.
  • 제약은 허용 너비/높이 범위다. 이 예제의 dp는 논리 길이 단위이며 실제 픽셀 변환은 셋째 소단원에서 다룬다.

학습 목표

  • 구성요소 역할과 배치 규칙을 분리한다.
  • 부모 여백·간격·자식 크기로 좌표를 추적한다.
  • 배치 계산과 실제 입력/접근성 확인의 차이를 설명한다.

내용과 배치는 다른 계약이다

layout은 자식에게 사용할 공간을 정하고 위치를 배정하는 규칙이다. component는 예컨대 “대출 요청”이라는 행동이나 제목 표시 역할을 제공한다. 같은 버튼 역할을 세로 목록이나 가로 도구막대에 배치할 수 있으므로 역할과 위치는 동일 개념이 아니다. 본문은 Android14의 View 계열과 Jetpack Compose 개념을 비교하되 설치 없이 종이에 구조를 그린다.

View 계열에서는 ViewGroup이 자식을 포함하는 컨테이너다. Compose에서는 Column이 세로, Row가 가로, Box가 겹침을 표현하는 기본 배치 수단이다. 자식을 선언했다는 사실만으로 원하는 여백·정렬·줄바꿈이 결정되는 것은 아니다. 겹침은 배지처럼 의도할 수도 있으므로 무조건 오류가 아니라 목표에 따라 판정한다.

제약을 내려보내고 크기와 위치를 정한다

부모가 허용 공간을 자식에게 전달하고 자식의 측정값과 배치 규칙으로 결과를 정한다. 텍스트의 실제 크기는 문자열·글꼴·언어·글자 배율과 줄바꿈에 영향을 받는다. 여기서는 그 측정 문제를 생략하고 각 자식 높이를 이미 주어진 값으로 고정한다. 종이 모형 좌표는 왼쪽 위 원점, x 오른쪽, y 아래로 증가한다.

너비 W인 세로 컨테이너의 좌우 여백 p라면 내부 너비는 W−2p다. 이 값이 음수면 해당 고정 여백 계약을 만족할 공간이 없다. 자식 높이 h1..hn과 간격 g≥0에서 y1=p, yi=p+Σ(j<i)hj+(i−1)g다. 전체 필요 높이는 2p+Σhi+(n−1)g이다. 이 식은 자식의 추가 margin이나 겹침·스크롤을 넣지 않은 자체 모형의 식이다.

화면이 들어맞아도 조작 가능한지 확인한다

표시 영역과 입력 영역은 다를 수 있다. 이름이 없는 아이콘, 작은 표적, 다른 자식과 겹친 입력 영역은 좌표 식이 맞아도 사용을 방해할 수 있다. 표준 버튼의 의미 정보를 활용하고 아이콘의 역할 설명과 포커스 순서를 검토한다. 시각적으로 보인다는 확인과 보조기술이 의미를 읽는 확인은 별개다.

내용이 길어지면 고정 높이를 늘리거나 줄바꿈·스크롤 등 다른 계약을 선택해야 한다. 글자를 잘라 공간에 맞추는 것은 중요한 내용을 읽을 수 있다는 목표와 충돌할 수 있다. 이 단원의 설계 검토는 가능한 문제를 찾는 문서 작업이며 실제 사용자에게 편하다는 측정 근거는 아니다.

중간 과정을 따라가는 예제

자체 Column 모형 W=360dp, p=16dp, 간격 g=8dp, 자식 제목/설명/버튼 높이 24/40/48dp이다. 모든 자식은 내부 너비를 사용하며 margin·스크롤·추가 insets는 없다. 좌표와 필요 높이를 구하라.

  1. 내부 너비는 360−32=328dp, 각 자식의 x 시작은 16dp이다.
  2. 제목은 y16~40, 다음 시작은 40+8=48dp이다. 설명은 y48~88이다.
  3. 버튼 시작은 88+8=96, 끝은 144dp다. 아래 여백 16을 더한다.
  4. 필요 높이는 16+24+8+40+8+48+16=160dp이다. 자식은 서로 겹치지 않으며 끝점은 반열린 구간으로 읽는다.

세 자식 사각형은 x16~344에 놓이며 y16~40/48~88/96~144, 컨테이너 높이 160dp이다. 실제 Text/Button 측정값이 아닌 지정 모형의 결과다.

풀이 보기

오해와 반례

Row로 바꾸면 모든 창에서 같은 내용이 자동으로 잘 들어간다.

자식 너비를 200/200dp, 간격 8dp로 고정한 Row는 내부 328dp에 408dp를 요구해 넘친다. 방향 변경만으로 텍스트 크기·입력 영역·스크롤 문제가 사라지지 않는다.

소단원 2.2

View·Compose 비교

같은 숫자를 두 곳에 표시할 때 한 곳만 바뀌는 문제를 어떻게 막을까?

준비 개념과 학습 목표

준비 개념

  • 상태는 현재 UI를 정하는 값이다. 예제 count는 정수 0~2이며 사용자의 입력 이벤트로만 바뀐다.
  • 명령형 갱신은 특정 객체 속성을 바꾸는 일이고, 선언형 기술은 현재 입력에 해당하는 UI를 설명하는 일이다.
  • 콜백은 사건 때 호출하도록 전달하는 함수다. UI 기술 함수를 호출하는 것과 버튼 클릭은 다른 사건이다.

학습 목표

  • View의 속성 갱신과 Compose의 상태 기반 기술을 비교한다.
  • 한 상태에서 두 표시와 버튼 활성 여부를 계산한다.
  • 재구성을 상태 변경 사건이나 저장 보장으로 오해하지 않는다.

View와 Compose는 UI를 표현하는 방식이 다르다

View 계열은 자식 View 객체를 가진 계층에서 setText처럼 표시 속성을 갱신할 수 있다. XML은 초기 구조를 선언하는 수단이 될 수 있지만 이후 상태와 표시를 어떻게 일치시키는지는 별도 설계다. XML 사용 자체가 앱 전체를 선언형으로 만들거나, View가 항상 수동 갱신만 가능하다는 결론은 아니다.

Compose는 @Composable 함수에 현재 값을 전달해 UI를 기술한다. count=1이면 그 값에 해당하는 두 표시와 활성 여부를 함께 정한다. 여기서는 Android14/API34를 예시 환경으로 삼고 Compose의 상태 입력/이벤트 출력 개념만 사용한다. 두 방식의 성능 우열이나 특정 라이브러리 버전 호환성을 이 종이 예제로 증명하지 않는다.

상태의 주인을 하나 정하고 이벤트를 분리한다

자체 상태 전이는 Add 사건 때 count<2이면 count+1, 그렇지 않으면 그대로다. UI 함수 U(count)는 label1="선택: count", label2="합계: count", enabled=(count<2)를 산출한다고 정의한다. 이 입력을 주는 주인과 사건을 받는 콜백을 구분하면 표시 두 개가 각각 다른 count를 보관할 이유가 없다.

View에서도 render(count) 함수가 두 TextView와 Button.enabled를 모두 갱신하게 설계하면 같은 원칙을 적용할 수 있다. Compose에서는 count/onAdd를 받는 화면을 기술하고 사건 콜백으로 주인에게 변경을 요청한다. 실제 요청 접수·서버 성공·지속 저장은 이 카운터 전이의 보장이 아니다. 화면 상태와 업무 결과를 연결하려면 추가 계약이 필요하다.

재구성은 사용자의 클릭을 복제하지 않는다

Compose 재구성은 변경된 입력 등에 따라 UI 기술을 다시 평가하는 과정이다. 일부가 건너뛰어지거나 시작한 평가가 취소될 수 있어 호출 횟수나 순서에 부작용을 의존해서는 안 된다. 본문 함수를 평가할 때마다 count를 올리는 방식은 UI가 다시 그려질 때 클릭 없이 값을 변경하는 반례다.

동일 상태를 다시 표현하면 표시 결과도 같아야 하는 성질을 UI 모델의 기준으로 삼는다. 이것만으로 프로세스 종료 뒤 상태 복원이나 네트워크 재시도 안전성이 보장되지는 않는다. 이 단원은 의사 규칙을 추적하며 실제 Android 코드 컴파일·클릭·재구성 관찰을 하지 않았다. 다음 상태/수명주기 단원에서 소유와 복원을 더 다룬다.

중간 과정을 따라가는 예제

초기 count=0. U(count)는 두 label과 enabled를 위 규칙으로 정하고, 정상 Add 사건을 순서대로 세 번 적용한다. 세 번째는 버튼 비활성이라 UI에서 전달되지 않는다고 정하되, 전이 함수도 count=2를 유지하도록 방어한다.

  1. 초기는 선택 0/합계 0/enabled=true이다. UI 표시를 계산한다고 count를 바꾸지 않는다.
  2. 첫 Add는 0<2이므로 count=1. U(1)은 선택 1/합계 1/enabled=true다.
  3. 둘째 Add로 count=2. U(2)는 선택 2/합계 2/enabled=false다.
  4. 셋째 UI 클릭은 전달되지 않는다. 직접 전이에 Add를 주더라도 경계 검사로 count=2이며 두 표시 모두 2다.

최종 count=2와 두 표시 2, 버튼 비활성이다. 논리적 전이 추적이며 앱에서 관찰한 출력이 아니다.

종이와 본문으로 직접 해보기

count=1에서 UI 기술만 네 번 평가하고, 뒤에 Add 사건 한 번을 주라. count가 평가 때마다 증가하는 잘못된 모형과 비교하라.

힌트 보기

UI 평가와 상태 전이를 서로 다른 화살표로 그린다.

풀이 보기

올바른 모형은 네 평가 내내 count=1과 표시 1, Add 뒤 count=2/표시 2다. 매 평가 증가 모형은 사용자가 Add하지 않아도 상태를 바꾸므로 입력 계약을 위반한다. 잘못된 모형의 구체 출력은 임의 경계 규칙에 따라 달라진다.

오해와 반례

Compose이면 상태·저장·표시 일치 문제가 자동으로 모두 해결된다.

표시 기술 중 저장을 수행하거나 두 상태 저장소를 따로 유지하면 부작용·불일치가 남는다. 또한 UI 재구성은 프로세스 종료 후 복원을 약속하지 않는다. 도구 선택과 상태 계약의 정확성을 분리한다.

소단원 2.3

화면크기·밀도

픽셀 수가 많은 화면이면 항상 더 많은 버튼을 놓을 수 있을까?

준비 개념과 학습 목표

준비 개념

  • px는 화면 래스터의 픽셀 단위이고 dp는 Android의 밀도를 고려한 논리 길이 단위다. 두 값을 숫자가 같다고 동일시하지 않는다.
  • 이론 변환 모형은 밀도 비율ρ>0에서 px=dp×ρ다. 실제 앱은 플랫폼 밀도/변환 API를 사용한다.
  • 가용 창은 앱에 배정된 공간이며 전체 장치 화면과 다를 수 있다. 높이·insets·접힘과 글자 확대도 영향을 준다.

학습 목표

  • 고정 밀도 조건에서 px와 dp를 변환한다.
  • 화면 해상도 대신 현재 창 폭으로 배치 분기를 추적한다.
  • 문자 배율·터치·키보드 접근을 별도 요구로 명시한다.

밀도와 논리 공간을 구별한다

같은 48px도 밀도 비율 1과 3에서 논리 48dp와 16dp가 된다. Android dp는 기준 160dpi 부근의 픽셀을 기준으로 밀도 차이를 보정하는 단위이지 모든 기기에서 정확한 물리 mm를 보장하는 계측 단위는 아니다. 종이 모형에서만 ρ=dpi/160을 정확한 양수로 놓고 실수 길이를 계산하며 픽셀 반올림은 생략한다.

글자 크기는 사용자 선호를 반영하는 sp를 사용한다. 큰 글자 설정의 변환을 언제나 단순 dp×고정 배율로 일반화하지 않는다. 특히 최신 플랫폼의 글자 확대 정책을 실제 코드에 손으로 복제하지 않고 플랫폼 API에 맡긴다. 크기를 늘린 글자가 줄바꿈/배치 높이에 미치는 영향은 픽셀 밀도 문제와 별도로 점검한다.

창의 폭과 높이는 실행 중 바뀔 수 있다

공식 window size classes는 앱 가용 영역을 폭과 높이로 각각 분류한다. 예컨대 확인한 현행 문서에서 compact 폭은 600dp 미만, medium은 600dp 이상 840dp 미만이다. 이는 전화/태블릿이라는 기기 이름으로 고정한 분류가 아니다. 분할 화면과 창 변경은 같은 기기의 클래스를 바꿀 수 있다.

우리의 자체 규칙은 가용 콘텐츠 폭w<600dp이면 한 칸, w≥600dp이고 콘텐츠 높이h≥480dp이면 두 칸, 그 외에는 한 칸이다. 이것은 공식 클래스에서 아이디어를 얻은 예시 정책이지 Android 필수 배치 알고리즘이 아니다. 예제 w/h는 insets를 제외한 값으로 이미 주어졌고 공식 전체 창 클래스를 계산하는 API와 동일 입력이라고 주장하지 않는다.

적응형 UI의 성공 조건은 입력과 읽기를 포함한다

두 칸을 표시할 수 있어도 두 내용의 순서·현재 선택·포커스를 잃지 않아야 한다. 터치 표적은 확인한 Compose 접근성 안내의 최소 48dp 권고를 고려하고 이웃 영역의 겹침을 피한다. 마우스·키보드·보조기술 입력에서 역할과 이름, 포커스와 활성 상태도 확인한다. 48dp 식 하나가 모든 사용자에게 성공을 보장하지는 않는다.

실제 검증에는 경계 창 크기, 확대 글자, 회전/분할, 탐색 순서와 입력 방식의 관찰이 필요하다. 여기서는 규칙의 산술과 문서 조건만 확인한다. Android 에뮬레이터나 실기기를 설치할 필요 없이 종이로 분기를 계산할 수 있으며 실제 접근성·앱 동작 검증은 미수행 상태로 남긴다.

중간 과정을 따라가는 예제

가상 창 A는 콘텐츠 1080×1500px,ρ=3이고 B는 1200×1000px,ρ=2다. insets는 이미 제외했다. 위 자체 한/두 칸 규칙과 48dp 터치 영역의 픽셀 크기를 구하라.

  1. A의 논리 크기는 1080/3=360dp,1500/3=500dp다. 폭 600 미만이므로 한 칸이다.
  2. B는 600×500dp다. w≥600,h≥480이 모두 참이므로 두 칸이다.
  3. 48dp는 A에서 144px, B에서 96px다. 같은 px 수로 표적을 고정하지 않는다.
  4. B를 분할하여 콘텐츠 폭 800px,높이 1000px로 만들면 400×500dp이므로 한 칸으로 바뀐다. 밀도는 바뀌지 않았다.

A 한 칸/B 두 칸/B 분할 후 한 칸, 표적 144/96px이다. 가상 값의 산술이며 실제 기기나 앱 결과가 아니다.
