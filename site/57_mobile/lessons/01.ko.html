소단원 1.1

앱·프로세스·패키지

앱 아이콘이 남아 있는데 실행 중이던 변수는 사라질 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 상태는 현재 값들의 묶음이다. 이벤트는 상태를 바꿀 계기가 되는 입력이다. 프로그램 파일은 저장된 코드이고 프로세스는 그 코드를 실행하며 메모리 등 자원을 사용하는 실행 인스턴스다.

학습 목표

  • 설치된 앱과 실행 프로세스를 구분한다

  • APK/AAB와 실행 환경의 역할을 설명한다

  • 화면 재생성과 프로세스 종료에 맞게 상태 보존 범위를 정한다

같은 설치 앱의 두 프로세스가 메모리 변수도 함께 쓰는가?

자체 앱은 기본 UI 프로세스 P와 별도 프로세스 Q의 구성요소를 명시적으로 설정했다고 가정한다. 각 프로세스가 가진 메모리 카운터는 처음 0이다. Q의 자기 카운터만 7로 바꿔도 P의 카운터가 자동으로 7이 되지는 않는다. 같은 설치 묶음과 실행 메모리의 경계를 구별한다.

두 프로세스가 값을 교환하려면 명시한 IPC나 저장소 접근 계약이 필요하다. 여기서는 Q가 값 7을 영속 저장하고 완료를 확인한 뒤, P가 그 저장소에서 새 값을 읽어 자기 카운터를 갱신하는 자체 경로를 따로 정한다. 실제 Android DB·파일의 동시 접근 처방을 제시한 것은 아니다.

또 다른 자체 사건에서는 receiver가 자기 콜백 안에서 임의 스레드를 시작한 뒤 반환하고, 같은 프로세스의 다른 활성 구성요소가 없다. 스레드가 있다는 사실만으로 시스템이 그 작업의 수명을 보장하지 않는다. 사용자에게 중요한 작업은 작업 종류에 맞는 플랫폼 API와 완료·실패 계약을 확인해야 한다.

먼저 확인할 개념

    앱의 파일과 프로세스별 상태를 나눈다.

  • 실제 실행과 종이 예상

    프로세스 종료 가능성을 실제 관찰로 기록하지 않는다.

파일 묶음과 실행 인스턴스

이 단원은 Android14/API34의 보통 앱을 설명 모형으로 고정한다. APK는 설치에 쓰는 코드·자원·메타데이터 묶음이고 AAB는 배포용 묶음으로 필요한 APK를 생성하는 데 쓰인다. AAB 자체를 그대로 단말에 설치하는 APK와 혼동하지 않는다. 여기서 패키지는 앱 배포 묶음을 가리키며 Java 이름공간 package와 구별한다.

시스템은 기본적으로 앱에 고유 Linux 사용자 ID를 부여하고 보통 앱의 구성요소를 한 프로세스에서 실행한다. 필요할 때 프로세스가 시작되고 자원 상황에 따라 끝날 수 있다. 기본은 한 프로세스지만 앱이 다중프로세스를 설정할 수도 있으므로 앱=영구적인 프로세스 한 개라는 등식은 틀리다.

화면의 수명과 프로세스의 수명

Activity는 사용자와 상호작용하는 화면 구성요소다. 생성·시작·재개·일시정지·중지·파괴 등의 콜백은 시스템과 화면 상태 변화를 다루는 진입점이다. 기본 설정의 화면 회전처럼 구성 변경은 Activity를 재생성할 수 있다. 프로세스가 살아 있어도 화면 객체가 교체될 수 있다.

앱이 백그라운드에 있을 때 시스템은 메모리가 필요하면 프로세스를 종료할 수 있다. 다음 진입에서 새 프로세스와 객체가 생기면 예전 메모리 변수는 저절로 돌아오지 않는다. 종료 직전 onDestroy가 반드시 호출된다고 믿고 중요한 데이터를 그때만 저장하면 안 된다.

보존해야 할 의미에 맞게 저장한다

이름 입력 중의 짧은 UI 상태는 적절한 saved state로 복원하고, 화면 재생성 동안의 진행 상태는 ViewModel 같은 구조로 관리할 수 있다. 그러나 메모리에 있는 ViewModel 자체가 프로세스 종료 후에도 살아 있다는 보장은 없다. 데이터의 크기와 저장 기능의 계약에 맞는 선택이 필요하다.

작성 중 문서처럼 사용자가 보존을 기대하는 데이터는 영속 저장 계약으로 다루고 완료 여부를 확인한다. 화면 포커스 같은 임시 상태와 계좌 거래 같은 업무 사실을 같은 보존 범주에 넣지 않는다. saved state도 강제 중지·사용자 task 제거 등 모든 종료에서 복구되는 영구 저장으로 일반화하지 않는다.

각 행은 명시한 자체 사건이다. 같은 앱의 변수가 자동 공유된다거나 모든 저장소가 같은 동시 접근 계약이라는 의미가 아니다.

중간 과정을 따라가는 예제

Android14 기본 구성 변경을 가정한다. 화면의 임시 숫자=5, 메모리 ViewModel의 초안=문장A, 확인된 영속 저장 문서=문장B가 있다. 회전 후와 시스템 프로세스 종료 후에 자동 보존을 보장할 수 있는 범위를 추적하라.

  1. 회전으로 Activity 객체가 교체되면 그 객체의 숫자 필드만으로는 5가 복원된다고 보장할 수 없다.

  2. 적절히 범위를 정한 ViewModel은 구성 변경을 넘어 초안을 유지할 수 있다. 이것은 프로세스가 유지되는 조건이다.

  3. 시스템이 프로세스를 끝내면 숫자와 ViewModel은 메모리에서 사라진다.

  4. 문장B는 정상적으로 저장을 완료했고 저장소가 유지된다는 조건에서 다시 읽을 수 있다. saved state는 별도 계약이 있어야 문장A를 복원한다.

화면 객체, 프로세스 메모리, 영속 저장의 수명이 다르다. 아이콘과 설치된 APK가 남는 것은 메모리 값이 살아 있다는 증거가 아니다.

조건을 바꾸어 비교하기

같은 이름의 다른 상태

Q의 count가 7인데 P 화면이 자기 count를 읽으면?

  1. 두 변수를 서로 다른 메모리 상태로 둔다.

  2. 명시한 교환 경로가 아직 없다.

P의 값은 0이다.

비교할 점

동일 변수 이름과 같은 저장 위치를 구별한다.

작업 스레드를 시작했지만

receiver가 스레드를 시작하고 반환했다. 다른 활성 구성요소가 없으면 작업 완료가 보장되나?

  1. 콜백 반환 뒤 receiver는 더는 활성 상태가 아니다.

  2. 시스템이 프로세스를 종료하면 스레드도 종료된다.

보장되지 않는다. 필요한 작업의 플랫폼 수명 관리 계약을 확인한다.

비교할 점

스레드 생성과 시스템이 인지하는 작업 수명은 다르다.

종이와 본문으로 직접 해보기

계산기 선택 탭, 1MB 사진, 결제 완료 사실을 임시 UI/saved state 후보/영속 업무 사실로 나누고 이유를 적어라.

힌트 보기

크기와 사용자의 보존 기대를 함께 고려하라. 결제 사실은 화면 콜백이 만들 보증이 아니다.

풀이 보기

선택 탭은 작은 복원 가능한 UI 상태 후보다. 1MB 사진 본체는 작은 saved state 묶음에 넣기보다 파일 등 저장소와 참조를 설계한다. 결제 완료는 권위 있는 서버/업무 저장 계약으로 확인할 사실이며 화면 표시나 메모리 bool 하나로 확정하지 않는다.

오해와 반례

앱을 백그라운드로 보내면 항상 같은 객체가 기다린다.

메모리 부족으로 프로세스가 끝난 뒤 앱이 다시 생성되는 반례가 있다. 항상 종료된다는 주장도 틀리다. 실제 수명은 시스템 상태에 의존하므로 두 경우 모두 설계해야 한다.

연습 1 · 값과 상태 예측

P의 프로세스만 종료되고 새 P가 자기 count를 0으로 초기화했다. 저장소의 7을 아직 읽지 않았다면?

힌트 1

메모리 초기화와 복원을 나눈다.

힌트 2

저장된 값은 명시적으로 읽어야 한다.

풀이와 답 확인

  1. 새 P의 초기값을 적용한다.

화면이 자기 count만 읽으면 0이다. 저장소 값 7의 존재만으로 자동 복원이 되지 않는다.

흔한 오답에서 다시 생각하기

설치 앱이 같으니 새 프로세스 변수도 옛 값이다.

onDestroy에서만 중요 문서를 저장하므로 모든 종료에 안전하다고 했다.

힌트 1

풀이와 답 확인

onDestroy 호출을 모든 종료의 저장 보증으로 사용하지 않는다.

종료 전에 모든 콜백은 반드시 끝난다.

시스템 프로세스 종료에서 onDestroy는 보장되지 않는다.

한 단계 더

심화: 저장 완료 전후에 프로세스가 끝나는 두 경우를 상태 기계로 그려라. 완료 전 데이터를 잃을 수 있는 창을 명시하고, 업무 요청의 재시도에서는 중복 처리 여부와 서버 계약을 함께 다룬다. Android 수명 콜백만으로 분산 거래의 정확성을 증명할 수 없다.

소단원 1.2

에뮬레이터와 실기기

가상 휴대폰에서 잘 동작한 앱은 실제 휴대폰에서도 모든 특성이 같을까?

준비 개념과 학습 목표

준비 개념

  • 실행 환경은 운영체제 버전·하드웨어·설정의 묶음이다. 테스트는 특정 입력과 환경에서 결과를 관찰하는 일이며 다른 환경 전체에 대한 증명과 다르다.

학습 목표

  • AVD와 실기기의 비교 범위를 정한다

  • OS/API·화면·센서·네트워크 조건을 기록한다

  • 종이 상태 추적과 실제 장치 검증을 구별한다

두 조건씩 모두 시험하면 네 조건의 오류도 모두 찾을까?

자체 시험 축 A는 API 34/35, B는 작은/큰 화면, C는 권한 허용/거절, D는 온라인/오프라인이다. 각각 앞 조건을 0, 뒤 조건을 1로 표시한다. 전체 조합은 2^4 = 16개다. API 값은 비교용 고정 조건이며 현재 권장 버전 선언이 아니다.

아래 여덟 계획 행은 어떤 두 축을 선택해도 00·01·10·11을 모두 포함한다. 따라서 이 작은 목록은 두 조건의 조합을 빠뜨리지 않았다. 그러나 D를 A XOR B XOR C로 고른 행들이므로 네 조건의 가능한 16개 모두를 포함하지는 않는다.

오류가 오직 A=0,B=1,C=1,D=1일 때만 발생한다고 자체 정의하면 이 목록에는 해당 행이 없다. pairwise의 범위와 전체 조합의 범위를 구별한다. 시험을 실제로 수행한 횟수는 0이며 이 표는 실행 결과가 아닌 선택 계획이다.

먼저 확인할 개념
  • 실행 환경의 여러 축

    API·화면·권한·네트워크를 독립 조건으로 기록한다.

  • 상태와 실행 인스턴스

    초기 데이터가 다른 경우도 별도 입력으로 관리한다.

AVD는 환경의 명세와 저장소를 가진다

Android Emulator는 가상 장치를 실행한다. AVD는 그 장치의 Android 시스템 이미지와 화면·하드웨어 특징 등을 정하고 사용자 데이터 저장소도 가진다. 이 단원의 가상 시험 명세는 Android14/API34, 전화형 화면, portrait 시작으로 고정한다. 이것은 설치한 장치의 보고가 아니다.

에뮬레이터는 화면 전환·회전·다양한 OS 조합을 반복하는 데 유용하다. 그러나 호스트 컴퓨터 자원·가상화·가상 센서 등도 환경 일부다. 실기기와 CPU 시간·발열·배터리·카메라 동작이 자동으로 동일해지는 것은 아니다.

같은 앱에도 시험 조건이 여러 축이다

실기기는 실제 입력·무선 연결·센서·제조사 환경을 확인하는 데 필요하다. 버전만 맞춰도 화면 크기나 사용자 권한 설정, 네트워크 상태가 다르면 결과가 달라질 수 있다. 모든 축의 조합을 무한히 시험할 수 없으므로 요구사항에 중요한 조합을 선택한다.

화면 회전, 네트워크 응답 지연, 권한 거절을 서로 다른 입력으로 분리하면 실패 원인을 좁힐 수 있다. 회전은 기본 조건에서 Activity 재생성을 시험하는 계기가 될 수 있지만 프로세스 종료 시험 그 자체가 아니다. 두 수명 경계를 따로 관찰해야 한다.

기록은 실행 여부를 정직하게 담는다

설치 없이도 표를 만들어 이벤트 전후 상태를 예상할 수 있다. 예측은 검증할 질문을 만드는 도구이며 실제 장치 로그가 아니다. 이 단원은 에뮬레이터나 실기기를 실행하지 않았으므로 정상 동작 화면·배터리 성능·센서 정확도를 확인했다고 말하지 않는다.

선택 구현 때는 앱 빌드 식별자, OS/API, AVD 또는 기기 모델, 초기 저장 상태, 이벤트 순서, 예상/실제 결과를 나누어 기록한다. 에뮬레이터의 snapshot이나 기존 저장 데이터가 초기 상태를 바꿀 수 있으므로 새 설치와 기존 데이터 유지 시험도 구별한다.

  • 함수는 입력을 받아 규칙에 따라 결과를 만드는 코드다. 타입은 허용되는 값과 연산을 정한다. null은 참조할 대상이 없음을 나타내는 값이며 0이나 빈 문자열과 다르다.

null을 길이 0으로 바꾸면 빈 문자열과 구별할 수 있을까?

자체 Java 경계의 자료는 null, 문자열 AB, 빈 문자열이라는 세 경우다. 명시적인 nullable Kotlin 입력 s에 s?.length ?: 0을 적용하면 각각 0, 2, 0이다. 이 표현은 표시용 기본값을 고르지만 결측과 실제 빈 문자열이라는 원래 의미를 하나의 숫자로 합친다.

업무에서 두 상태를 구별해야 한다면 Missing과 Present(length)라는 자체 결과 장부로 바꾼다. null은 Missing, AB는 Present(2), 빈 문자열은 Present(0)으로 기록한다. 실제 앱의 결과 타입 구현을 실행한 것이 아닌 경계 계약의 설계다.

Java에서 넘어오는 목록 참조의 null 여부와 목록 안의 각 원소의 null 여부는 서로 다른 조건이다. 자체 non-null 목록 [AB,null,빈 문자열]에서 목록이 존재한다는 사실만으로 두 번째 원소의 안전한 문자열 사용을 보장하지 않는다. platform type과 generic 원소의 nullability 정보를 경계에서 확인한다.

언어와 런타임은 다른 층이다

Kotlin/JVM과 Java는 서로 호출 가능한 코드로 연결할 수 있다. 일반 JVM에서는 class 바이트코드를 사용하며 Android 빌드에서는 관련 바이트코드를 DEX로 변환해 ART가 실행하는 경로를 사용한다. 실제 최적화·네이티브 코드 생성 시점은 플랫폼과 빌드 설정에 따라 다르다.

빌드용 JDK, Java/Kotlin 언어 버전, Android compileSdk/minSdk, 실행 기기의 API 수준은 다른 설정이다. 최신 데스크톱 JDK에 있는 모든 API를 Android에서 사용할 수 있다는 결론은 틀리다. compileSdk가 제공하는 API와 최소 지원 기기 조건, 필요하면 지원되는 desugaring 범위를 따로 확인한다.

서로 호출하는 작은 계약

아래는 기본 package의 Java Helper.java와 Kotlin Main.kt를 같은 모듈에서 쓰는 종이 예제다. Java 메서드 add는 int 두 개를 받아 합을 반환한다. Kotlin에서 Helper.add(2,3)로 호출하고 JVM 상호운용 경계에서 int와 Kotlin Int의 대응을 이용한다. 입력을 2와 3으로 고정하여 오버플로 문제는 없다.

예제의 목표 언어 문법은 Java11과 Kotlin/JVM1.9 계열의 기본 문법이다. Android 앱 빌드 전체 설정 예제가 아니며 설치나 실제 Kotlin 컴파일을 수행하지 않았다. 예상 출력 5는 메서드 계약을 추적한 값이다.

// Helper.java
public final class Helper {
    public static int add(int a, int b) { return a + b; }
    public static String title() { return null; }
}

// Main.kt
fun main() {
    println(Helper.add(2, 3))
    val title: String? = Helper.title()
    println(title?.length ?: 0)
}

null 안전성은 경계를 살펴야 한다

Kotlin String은 null을 허용하지 않고 String?는 허용한다. ?.는 대상이 null이면 멤버 호출을 하지 않으며 ?:는 왼쪽이 null이면 오른쪽 값을 택한다. 위 예제는 title이 null이면 length 호출을 생략하고 0을 출력한다. 이것은 null을 빈 문자열로 바꾸는 연산이 아니다.

nullability 정보가 없는 Java 참조 타입은 Kotlin에서 platform type으로 취급될 수 있다. String! 같은 표기는 설명/도구 표기이며 소스에 쓰는 선언 타입이 아니다. Java 반환값을 무조건 non-null로 기대하면 실행 중 예외가 발생할 수 있다. 인정되는 annotation과 컴파일 설정에 따라 타입 정보가 더 정확해지지만 외부 경계의 계약을 검토해야 한다.

중간 과정을 따라가는 예제

위 Helper와 Main의 첫 두 출력 및 title을 String으로 강제 기대하는 변형을 추적하라. Java title은 반드시 null을 반환한다고 가정한다.

  1. add의 a=2,b=3이므로 합은 5다.

  2. title 변수는 명시한 String?라 null을 담는다.

  3. title?.length는 null이고 Elvis 연산 ?:가 0을 선택한다.

  4. val bad: String = Helper.title()로 선언하면 실제 null을 non-null로 기대하므로 안전한 정상 문자열 대입이 아니다. null 검사가 실행 중 실패할 수 있다.

원래 예제의 예상 출력은 5와 0이다. non-null 변형은 실패할 수 있으므로 예상 정상 출력으로 취급하지 않는다. 실제 Java/Kotlin 혼합 실행은 not_executed.
