소단원 7.1

coroutine과 취소

화면을 떠난 뒤에도 이전 작업이 결과를 화면에 써도 될까?

준비 개념과 학습 목표

준비 개념

  • 함수와 비동기 작업

  • 화면 수명

  • coroutine은 중단·재개 가능한 작업이며 Job은 작업의 수명과 취소 상태를 관리한다. dispatcher는 실행 배치, scope는 작업 수명의 경계다.

학습 목표

  • 일시 중단과 주스레드 안전성을 구별한다.

  • 취소 관측과 결과 반영의 경계를 추적한다.

취소 요청에서 실제 작업 종료까지 얼마나 기다릴까?

자체 작업은 항목 하나에 정확히 2 ms가 걸리고, 항목 처리 중에는 취소를 관측하지 않는다. 검사 비용은 0이며 묶음 시작 직전에 취소를 검사한다. 묶음 크기 10이면 첫 묶음은 0..20 ms, 크기 1이면 첫 검사 시각은 0,2,4,… ms다. 이는 실제 스케줄러나 입출력 시간을 측정한 것이 아니다.

취소 요청은 t = 7 ms에 발생한다. 묶음 10은 t = 20에 관측하므로 관측까지 13 ms, 묶음 1은 t = 8에 관측하므로 1 ms다. 취소 이후 이미 진행 중이던 항목이나 묶음은 이 자체 모형에서 마친다. 검사를 자주 한다는 설계와 실제 검사·작업 비용의 균형은 별도 측정이 필요하다.

소유 자원의 정리에 추가로 정확히 5 ms가 필요하고 정리가 끝나야 작업 종료라고 정한다. 종료 시각은 각각 25와 13 ms다. finally의 정리 완료는 앞서 처리한 항목의 효과가 원래대로 돌아갔다는 뜻이 아니다. 중단된 작업과 이미 완료된 외부 쓰기의 계약을 나눈다.

일시 중단은 스레드 차단과 다르다

coroutine은 실행을 일시 중단하고 나중에 이어 갈 수 있는 작업 흐름이다. Kotlin suspend 함수라는 이름만으로 모든 코드를 자동으로 다른 스레드에서 실행하지 않는다. 오래 걸리는 블로킹 입출력은 담당 계층이 적절한 dispatcher로 옮겨 주스레드 호출에 안전하게 만들어야 한다.

주스레드는 입력과 화면 갱신을 처리한다. 거기서 느린 네트워크 응답을 차단하며 기다리면 UI가 멈출 수 있다. 비동기 클라이언트의 중단과 블로킹 클라이언트를 IO dispatcher에서 사용하는 방법은 구별하고 라이브러리 계약을 읽는다.

작업의 소유 수명을 정한다

현재 화면에서만 의미 있는 요청은 호출자 scope의 수명을 따른다. ViewModel scope는 ViewModel이 clear될 때 취소되며 단순 회전과 모든 화면 이탈을 항상 같은 사건이라고 취급하지 않는다. 수명 관계를 실제 화면 구조에 맞춰 정한다.

화면을 떠나도 필요한 저장 작업은 더 오래 사는 외부 scope나 지속 작업 도구가 필요할 수 있다. GlobalScope를 임의로 쓰면 작업 소유자와 취소 경계가 흐려진다. 앱 프로세스가 죽어도 계속해야 하는 작업을 메모리의 coroutine 하나만으로 보장하지 않는다.

취소는 협력하여 확인한다

Job 취소 요청은 모든 CPU 작업을 즉시 강제 종료하지 않는다. 취소 가능한 중단이나 ensureActive 같은 검사 지점에서 관측한다. 긴 반복문이 검사 없이 실행되면 취소 반응이 늦을 수 있다.

CancellationException을 넓은 catch에서 삼켜 일반 실패 뒤 재시도로 바꾸면 취소 규율을 깨뜨릴 수 있다. 필요한 정리는 finally에서 수행하고 취소는 다시 던진다. 로컬 작업의 취소는 이미 서버에 도달한 쓰기가 되돌아갔다는 뜻도 아니다.

중간 과정을 따라가는 예제

파일A를 처리한 뒤 ensureActive를 거쳐 B,C를 처리하는 작업이다. A 뒤 취소 요청이 들어오고 다음 검사에서 관측한다. 무엇이 처리되는가?

  1. 시작 시 활성 상태에서 A를 처리했다고 정한다.

  2. A 뒤 Job 취소가 요청되며 다음 ensureActive에서 취소 예외를 관측한다.

  3. B,C 처리는 시작하지 않고 finally에서 소유한 자원을 정리한다.

A만 처리하고 B,C는 미처리다. 실제 파일 실행이 아닌 사건 모형이다.

조건을 바꾸어 비교하기

짧은 묶음에서도 즉시 종료는 아니다

크기 1에서 t = 7의 요청은 어느 항목 뒤 관측할까?

  1. 항목 네 번째가 6..8 ms에 실행된다.

  2. t = 8 검사에서 취소를 관측한다.

  3. 정리 5 ms를 더한다.

네 항목 완료, 관측 8 ms, 종료 13 ms다.

비교할 점

요청·관측·정리·종료의 시각을 각각 적는다.

시작 전 취소

  1. 첫 검사에서 취소를 관측한다.

  2. 항목 처리를 시작하지 않는다.

완료 항목 0개다. 앞 표의 5 ms 정리는 소유 자원을 이미 얻은 경로에 관한 조건이다.

정리 비용을 모든 경로에 무조건 붙이지 않는다.

오해와 반례

suspend이면 자동으로 백그라운드에서 실행하고 cancel은 서버 쓰기를 되돌린다.

suspend는 주스레드 차단 코드를 자동 이동시키지 않는다. 클라이언트 취소와 서버 이미 처리된 쓰기의 결과는 별도다.

준비 개념과 학습 목표

준비 개념

  • 요청과 응답

  • JSON 타입

  • repository는 데이터 접근을 모으는 객체, schema는 데이터 필드의 형태 계약이다. generation은 여기서 요청 의도를 구별하는 증가 번호다.

학습 목표

  • 전송·상태코드·파싱·내용검증을 나눈다.

  • 오래된 요청 결과가 최신 화면을 덮는 일을 막는다.

JSON의 숫자가 유효해도 식별자가 달라질 수 있을까?

본문의 정수 id 계약은 서버와 앱이 같은 값을 표현할 수 있어야 한다. JSON 문법은 숫자의 정밀한 내부 자료형을 하나로 강제하지 않는다. 여기서는 모든 JSON 숫자를 IEEE 754 binary64의 가장 가까운 값으로 반올림하고, 정확히 중간이면 짝수 유효 숫자를 선택하는 자체 수신 모형을 비교한다.

2^53은 9,007,199,254,740,992다. 이 부근 binary64의 표현 간격은 2이므로 바로 다음 정수 9,007,199,254,740,993은 이 반올림 조건에서 앞 값으로 바뀐다. 서로 다른 두 ID가 합쳐지는 문제다. 모든 JSON parser가 그러는 것은 아니다. 임의 정밀도 정수나 원문 토큰을 보존하는 다른 수신기는 구별할 수 있다.

큰 불투명 ID를 ASCII 숫자 문자열로 전달하는 새 API 계약을 비교하자. 이는 본문의 정수 필드를 그대로 통과시키는 해법이 아니라 양쪽 스키마를 바꾼 별도 계약이다. 문자열을 다시 부동소수점으로 바꾸면 이점도 사라진다. 이름이 중복된 JSON 객체는 RFC의 고유 이름 권고와 수신 정책을 구별하며 여기서는 중복을 거절하는 자체 정책을 정한다.

네트워크 계층과 데이터 계약

모바일 repository는 HTTP 메서드·URL·헤더와 응답 타입을 묶어 화면에 결과를 제공할 수 있다. HTTPS로 통신하고 제한 시간 및 응답 크기 정책을 둔다. 인증 정보는 필요한 헤더에 넣되 로그에 비밀을 노출하지 않는다.

연결 실패는 HTTP 응답 자체를 받지 못한 경우일 수 있다. 응답을 받았다면 상태코드에 따라 성공과 오류를 분류한다. 200의 JSON이라도 서버와 앱의 스키마가 다르면 데이터 처리 실패다. 204는 응답 내용이 없으므로 무조건 JSON 객체를 파싱하지 않는다.

파싱 뒤 타입과 필수값을 확인한다

이 자체 계약은 사용자 표현에 id는 정수, name은 빈 문자열이 아닌 문자열을 요구한다. {"id":7,"name":"가람"}은 통과하지만 {"id":"7","name":"가람"}은 문법상 JSON이어도 id 타입 실패다. 빠진 필드와 null과 빈 문자열도 계약에 맞춰 구별한다.

네트워크 응답을 화면의 Loading/Success/Error 상태로 연결한다. 예상 가능한 IO 실패와 파싱 실패를 구분하고 사용자에게 다시 시도할 수 있는 정보를 준다. JSON 오류를 감추고 빈 사용자로 성공 표시하면 서버 장애와 실제 빈 데이터를 구별하지 못한다.

응답 도착 순서와 요청 의도를 구별한다

사용자 7 조회가 느린 동안 사용자 8 조회를 새로 시작하면7의 응답이 나중에 올 수 있다. 여기서는 각 요청에 증가하는 generation을 붙이고 현재 generation과 일치하는 결과만 표시한다. 이전 작업 취소와 결과 검사를 함께 설계한다. 성공 데이터뿐 아니라 오류로 Error 상태를 표시할 때도 같은 검사를 적용하여 오래된 실패가 새 성공을 덮지 않게 한다.

generation을 확인하고 UI를 반영하는 단계는 이 예제에서 한 주스레드의 직렬 처리로 둔다. 검사와 반영 사이에 별도 동시 변경을 허용하면 추가 보호가 필요하다. 숫자 표식은 서버 권한이나 전송 암호화를 대신하지 않는다.

재시도 횟수가 남아도 전체 제한 시간이 끝나면?

자체 안전한 조회는 각 시도가 정확히 0.6초 뒤 실패한다. 실패가 확인된 뒤 1·2·4초를 기다리며 최초 시도에 최대 세 번 재시도한다. t = 0부터 전체 제한 시간 5초를 두고, 제한에 도달하면 추가 시도를 시작하지 않으며 진행 중 작업에도 중지를 요청한다고 정한다.

첫 번째 시도는 0초에 시작해 0.6초에 실패한다. 두 번째 시도는 1.6초에 시작해 2.2초에 실패하고, 세 번째 시도는 4.2초에 시작해 4.8초에 실패한다. 다음 계획 시작 시각은 8.8초이므로 전체 제한인 5초를 넘는다. 실제 시작한 시도는 세 번이며, 그중 재시도는 두 번이다. 본문의 즉시 실패 모형에서는 0초, 1초, 3초, 7초에 시작했지만, 이 사례에서는 대기 전에 각 시도에 걸린 시간도 누적된다.

전체 제한을 4.5초로 바꾸면 세 번째는 4.2초에 시작했으나 정상 실패 도착 예정 4.8초 전에 제한이 온다. 이 경우 클라이언트가 결과를 확인하지 못했다는 것과 서버가 처리하지 않았다는 것은 다르다. 쓰기였다면 중복 안전 계약 없이 다음 호출을 자동 전송하면 안 된다. 연결 관측도 특정 응답의 성공 증명을 대신하지 않는다.

연결 관측은 현재 요청의 성공 증명이 아니다

Android INTERNET capability는 인터넷 접근용으로 설정되었다는 뜻이며 captive portal처럼 실제 접근이 막힌 상태도 가능하다. VALIDATED는 시스템의 검사 시점에 공용 인터넷 접근을 확인한 상태지만 이후 연결 손실이나 특정 서버 차단까지 배제하지 않는다.

네트워크 callback으로 기본 연결과 capability 변화를 관측하되 실제 HTTP 요청의 실패도 처리한다. 연결 검사와 요청 사이에는 시간이 흐른다. Wi-Fi에서 이동통신으로 바뀔 때 오래된 연결이 끊어질 수 있으므로 같은 소켓이 영원히 유효하다고 가정하지 않는다.

오류 종류와 중복 효과를 먼저 판단한다

일시적인 읽기 실패는 최대 횟수와 대기 정책을 두고 재시도할 수 있다. 인증 실패는 같은 자격으로 무조건 반복하지 않고 유효 자격을 확보한다. 입력 범위 오류는 입력을 고치기 전 같은 요청을 반복해도 해결되지 않는다.

쓰기 응답을 놓쳤다면 서버가 처리했는지 모를 수 있다. POST 생성이나 결제에 안전한 중복키 계약이 없으면 반복으로 중복 효과가 생긴다. 연결이 복구되었다는 사실만으로 모든 대기 쓰기를 다시 전송하지 않는다. 큐·충돌·확인 정책을 함께 정한다.

backoff와 중지 조건

backoff는 실패 뒤 대기 간격을 늘리는 전략이다. 이 종이 모형은 즉시 실패하는 안전한 조회에 최초 시도와 최대3회 재시도, 대기1·2·4초를 둔다. 실제 앱은 지터라는 임의 분산과 최대 대기시간을 추가하여 많은 기기가 한꺼번에 다시 요청하는 일을 줄일 수 있다.

성공하면 중지하고 취소 요청을 관측하면 다음 재시도를 시작하지 않는다. 시간 제한을 각 요청에 둘지 전체 작업에 둘지도 명시한다. 지수 간격만으로 성공이나 배터리 비용이 보장되는 것은 아니다.
