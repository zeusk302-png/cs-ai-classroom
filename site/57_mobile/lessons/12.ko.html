평균 15 ms가 같은 두 흐름은 끊김도 같을까?

자체 순차 작업 표본 열 개를 비교한다. A는 10 ms 아홉 번과 60 ms 한 번이며 합이 150 ms, 평균이 15 ms다. B는 모두 15 ms여서 같은 합과 평균을 가진다. 이상적 60 Hz 주기 1000/60 ms와 각 작업 시간을 비교하면 A는 한 표본이 초과하고 B는 하나도 초과하지 않는다.

120 Hz의 이상 주기는 약 8.33 ms이므로 두 집합 모두 열 표본이 초과한다. 평균이 같다는 것, 각 주기 예산을 넘은 표본 수, 실제 기기의 끊김과 프레임 건너뜀은 다른 값이다. 아래 표는 단순 순차 작업의 비교이며 실제 렌더링 파이프라인이나 화면 FPS를 측정한 기록이 아니다.

메모리도 정상 보유와 교체 중 최대값을 나눈다. 자체 200×100×4 바이트 RGBA buffer 두 개를 보유하면 160000 B다. 새 buffer 한 개를 만든 뒤 옛 하나를 해제하는 정책은 잠시 240000 B를 보유한다. 실제 stride, 복사본, GPU와 다른 자원을 포함한 앱 프로파일 값은 별도로 확인해야 한다. 낮은 정상값 하나로 피크나 전력 감소를 증명하지 않는다.

먼저 확인할 개념
  • 프레임 주기와 자료 수명

    평균에서 표본별 예산 초과와 교체 피크를 구별한다.

  • 실행 환경과 증거 장부

    기기·빌드·주사율·열 상태에 맞는 실제 관측 계획을 세운다.

화면은 시간을 맞춰 바뀐다

jank는 화면 갱신이 제때 이루어지지 않아 끊겨 보이는 현상이다. 이상적 일정 갱신에서60Hz의 한 주기 길이는1000/60≈16.67ms이고120Hz면≈8.33ms다. 이는 단순 주기 예산이며 실제 렌더링 파이프라인의 모든 작업이 한 직렬 함수라는 뜻은 아니다. 평균 시간만 짧아도 드문 긴 프레임이 사용에 영향을 줄 수 있다.

UI thread의 긴 계산이나 디스크 읽기가 갱신을 방해하면 작업 위치와 필요한 결과 시점을 조사한다. 무작정 다른 thread로 옮겨도 동기화와 결과 적용 때문에 다시 멈출 수 있다. release에 가까운 빌드, 느린 기기, 동일 조작 흐름을 사용해 trace와 화면 관측을 연결한다.

파일 크기와 살아 있는 메모리는 다르다

압축 이미지 파일은 작아도 픽셀로 펼친 뒤 큰 메모리를 사용할 수 있다. 이 예제는 width×height×4바이트의 단순 RGBA buffer 모델을 쓴다. 실제 bitmap에는 stride·추가 객체·GPU 복사와 포맷 차이가 있으므로 이 숫자를 실제 프로파일 결과라고 부르지 않는다.

화면을 닫았는데 참조를 계속 보관하거나 필요 없는 cache가 커지면 메모리가 남을 수 있다. 한 번 증가한 수치만 보고 누수라고 단정하지 말고 반복 사용 뒤 살아 있는 객체와 수명 및 정상 cache를 구별한다. garbage collection이 모든 native 자원과 잘못된 참조를 자동 해결하는 것도 아니다.

전력은 사용 조건과 함께 본다

화면 밝기, CPU와 GPU 작업, 네트워크·위치 갱신, 장시간 깨어 있게 하는 wakelock 등이 전력에 영향을 준다. 같은 작업이라도 연결 품질과 화면 켜짐, 열 상태가 다르면 배터리 변화가 달라질 수 있다. 전력은 일하는 순간의 소비율이고 에너지는 시간 동안 소비한 총량이다.

동일 기기·밝기·네트워크·부하로 반복 비교하고 작업 및 전력 관련 기록을 함께 남긴다. Android 공식 문서는 Battery Historian이 더 이상 적극 유지보수되지 않는다고 알리고 trace·power metric 등 대안을 안내한다. 특정 도구 이름을 썼다는 사실만으로 실제 기기 전력 검증을 수행한 것은 아니다.

조건을 바꾸어 비교하기

같은 평균의 반례

A와 B의 평균과 60 Hz 예산 초과 표본 수를 계산하라.

  1. A의 합은 9×10+60=150 ms이며 평균은 15 ms다.

  2. B의 합은 10×15=150 ms다.

  3. 약 16.67 ms보다 큰 표본은 A의 60 ms 하나뿐이다.

같은 평균 15 ms여도 예산 초과는 A가 1개, B가 0개다.

비교할 점

평균 하나는 긴 표본의 위치와 크기를 보존하지 않는다.

buffer 교체의 피크

80000 B buffer 두 개를 보유하고 새 하나를 생성한 뒤 옛 하나를 해제한다. 정상과 순간 최대는?

  1. 정상은 2×80000=160000 B다.

  2. 해제 전에는 세 개이므로 240000 B다.

  3. 해제 후 다시 두 개가 된다.

정상 160000 B, 교체 중 최대 240000 B다. 추가 자원은 이 모형에 없다.

마지막 보유량과 교체 과정의 최대 보유량은 다르다.

코드 번호를 올려 옛 동작을 되살리면 데이터도 자동 호환될까?

자체 앱의 versionCode 21은 schema 1의 자료를 읽는다. 한 기록은 제목과 메모를 합친 문자열이라고 정한다. versionCode 22는 schema 2에서 두 필드를 분리하며 schema 1 자료를 읽어 올리는 변환을 제공한다. 이 저장 규약은 자체 사례이며 특정 Android 저장 API의 자동 변환 기능이 아니다.

22의 동작에 문제가 생겨 옛 동작 코드를 versionCode 23으로 다시 배포할 계획이라고 하자. 내부 번호는 23>22지만 schema 1만 읽는 옛 자료 처리 코드로는 schema 2 기록을 읽을 수 없다는 자체 규칙이다. 앱 번호 증가가 자료 호환성이나 복원 성공을 보장하지 않는다. schema 2를 읽는 호환 처리와 어떤 자료를 보존할지 따로 정해야 한다.

서명과 배포 근거도 구별한다. 업로드 키로 서명한 bundle의 제출과 사용자의 APK를 app signing key로 서명하는 단계는 다르다. 비밀키를 기록하지 않고 산출물 식별, 공개 인증서 정보, 실제 대상 track과 설치 결과를 연결한다. 같은 표시 이름이나 서명 사실만으로 시험한 bytes와 배포한 bytes의 기능 결과가 같다고 확정하지 않는다.

  • 업데이트 흐름의 실제 검사

서명은 출처와 갱신 신뢰의 일부다

Android APK는 설치 전에 디지털 서명이 필요하다. 서명은 해당 키의 산출물임을 검증하는 장치이며 앱에 버그가 없다는 보증은 아니다. debug 빌드는 개발용 인증서로 서명할 수 있고 공개 release는 배포 경로에 맞는 서명 구성이 필요하다. 비밀키와 password를 공개 저장소에 올리지 않는다.

Play App Signing에서는 업로드용 키와 사용자의 APK를 서명하는 app signing key를 구별한다. 업로드 키로 제출한 산출물과 실제 배포 APK의 서명 증거를 혼동하지 않는다. 공개 인증서와 비밀키는 다르며 갱신 신뢰와 키 교체 조건은 플랫폼 절차를 확인한다.

내부 번호와 표시 이름을 나눈다

versionCode는 Android의 내부 비교용 양의 정수이고 새 릴리스에서 증가시키는 번호다. versionName은 사용자에게 보이는 문자열이다.1.9와2.0 같은 이름만으로 내부 번호의 관계를 판단하면 안 된다. 기본 downgrade 방지와 플랫폼의 특별한 관리 절차를 구별한다.

예를 들어 code20/name1.9에서 code21/name1.9.1은 내부 번호가 증가한 갱신 후보지만 code19/name2.0은 이름이 커 보여도 내부 번호가 낮다. 설치 가능성은 번호 외에 앱 식별자·서명·기기 호환성도 필요하므로 숫자 비교만으로 실제 업데이트 성공을 기록하지 않는다.

릴리스 단계의 관측을 남긴다

빌드 완료, 서명 완료, 스토어 업로드, 검토 상태, 공개 배포와 실제 기기 설치는 각각 다른 단계다. 업로드가 성공했다고 사용자가 다운로드할 수 있다는 뜻은 아니다. 어떤 track과 대상 기기에 어떤 산출물이 노출되는지 확인한다.

릴리스 기록에는 원본 버전, build 설정, 내부 번호와 표시 이름, 산출물 식별, 서명 관련 공개 fingerprint, 검사 결과와 공개 상태를 적는다. 민감한 키값은 넣지 않는다. 문제 수정은 버전·데이터 호환성과 배포 상태를 고려해 준비하고 실제 설치 후 주요 흐름을 다시 확인한다.

준비 개념과 학습 목표

준비 개념

  • OS version

  • 화면과 입력

  • 테스트 사례

학습 목표

  • 기능 범위와 실행 위치를 구별한다.

  • 기기·상태 조합별 결과를 남긴다.

  • 사용자 신고와 재현 및 릴리스를 연결한다.

두 조건씩 모두 검사하면 세 조건이 겹친 오류도 잡힐까?

자체 지원 표는 화면 S/L, 연결 online/offline, 언어 ko/en의 이진 세 조건이다. 모든 세 조건 조합은 2×2×2=8개다. 네 선택은 (S,online,ko), (S,offline,en), (L,online,en), (L,offline,ko)로 정한다. 표의 실행 결과는 아직 없으며 조합 선택만 검토한다.

화면-연결, 화면-언어, 연결-언어의 각 두 조건 조합은 네 선택에서 네 가지를 모두 포함한다. 그러나 전체 세 조건 조합은 8개 중 4개만 선택했다. 오류가 정확히 (L,offline,en)에서만 발생하는 자체 함수 규칙이면 네 선택 모두 정상으로 예상하면서 해당 오류 조건은 빠진다.

위험 근거에 따라 (L,offline,en)을 추가하면 선택한 세 조건 조합은 5개이고 이 자체 오류를 찾는 기대가 추가된다. 그래도 나머지 세 조합이나 실제 기기·제조사·전력·사용자 행동을 전부 검증한 것은 아니다. 예상과 실제, 재현불가와 해결완료, 대역과 실기기의 범위를 분리해 기록한다.

먼저 확인할 개념
  • 위험별 대표 조합과 미검증

    두 조건 조합의 포함 범위와 세 조건의 빠진 범위를 계산한다.

  • 같은 산출물의 릴리스 근거

    조합표 결과가 어느 빌드의 어느 실제 시험인지 연결한다.

시험 크기와 실행 장소는 별개다

local 테스트는 개발 PC나 서버에서 실행하고 instrumented 테스트는 Android의 실제 또는 에뮬레이션 기기에서 실행한다. 작은 함수 검사와 전체 사용자 흐름은 범위 차이다. 작은 테스트도 기기 framework와의 통합을 위해 기기에서 실행할 수 있어 둘을 같은 분류로 읽지 않는다.

순수 계산 함수 통과는 카메라 권한이나 실제 화면 회전의 증거가 아니다. 기능·성능·접근성·호환성을 목표로 검사하고 어떤 버전과 환경에서 실행했는지를 남긴다. 에뮬레이터는 재현과 자동화에 유용하지만 열·전력·제조사 차이 모두를 대신하지 않는다.

상태와 조합을 선택한다

화면 크기,OS,언어·글자 크기,권한 거절,오프라인,백그라운드 복귀와 기존 데이터 업데이트 같은 상태가 주요 흐름을 바꾼다. 모든 조합을 무조건 나열하기보다 지원 범위와 위험을 근거로 대표 조합을 고르고 미검증 조합을 남긴다.

권한 거절 시 앱이 설명하고 다시 선택할 수 있는지, 회전 뒤 입력이 유지되는지, 오프라인 저장과 재연결이 중복 작업을 만들지 않는지 결과 상태를 확인한다. 버튼 탭 기록만으로 완료라고 하지 않는다. 점검표 성공 비율은 선택한 표의 범위이며 전세계 기기 성공 확률이 아니다.

신고를 재현 가능한 기록으로 바꾼다

운영 신고에는 앱 번호,기기와OS,입력 상태,재현 단계,예상과 실제 결과가 필요하다. 민감한 화면과 로그는 필요한 범위로 보호한다. 같은 오류라도 데이터 전제나 권한 상태가 다르면 재현 결과가 다를 수 있다.

수정 후에는 실패 사례와 관련 회귀 흐름을 같은 산출물에서 다시 검사한다. 재현불가를 해결완료와 혼동하지 않고 추가 정보와 남은 확인을 남긴다. 실제 학습자나 기기로 검사하지 않은 본문의 종이 표는 실행 증거가 아니다.
