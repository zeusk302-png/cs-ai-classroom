소단원 5.1

창작과 기여

같은 프로그램을 함께 만들었는데 발표자 한 명만 이름을 적어도 될까?

준비 개념과 학습 목표

준비 개념

  • 아이디어를 제안하는 일, 표현을 직접 작성하는 일, 검토하는 일은 서로 다른 기여다.

  • 버전 기록은 누가 언제 무엇을 바꾸었는지 남기는 기록이다.

  • 윤리적 크레딧과 법적 권리자의 판정은 다른 질문이다.

학습 목표

  • 여러 종류의 기여를 구체적 산출물에 연결한다.

  • 자기 창작과 타인의 표현·기여를 구별한다.

  • 확인되지 않은 소유권을 단정하지 않는 기록을 만든다.

커밋 열두 개와 해결이 확인된 보고 한 건을 어떻게 인정할까요?

앞 본문은 설계·표현 작성·검토·발표를 구체적인 산출물에 연결합니다. 새 가상 팀의 민은 자동 포맷 변경 커밋 12개를 남겼고, 별은 화면 문장 여섯 개를 한 커밋으로 작성했습니다. 준은 두 오류 보고 R1과 R2를 남겼습니다. R1은 변경 F1로 해결되어 연결이 확인되었고 R2는 아직 검토 중입니다. 발표는 별이 맡았습니다. 커밋 수의 합 13개와 오류 보고 수 두 개는 서로 다른 사건을 세므로 같은 생산성 척도로 합치지 않습니다.

자체 기록 기준은 기여의 대상·행위·확인 자료를 각각 적는 것입니다. 민의 포맷 작업도 실제 기여지만 화면 문장을 작성했다는 주장으로 넓히지 않습니다. 준의 두 보고는 보고 활동으로 모두 남기되 실제 오류 해결의 근거가 있는 보고는 R1 하나라고 구별합니다. 해결 연결 비율 1/2는 두 보고 중 연결이 확인된 비율이며 준의 가치나 법적 지분의 절반을 뜻하지 않습니다.

별도 이력 모형에서는 문장 d를 민이 v1에서 작성하고 별이 v2에서 교정했습니다. v3에서 그 문장을 제거하면 현재 사용 목록에서는 빠지지만 과거 기여 이력은 남깁니다. 실제 권리자·고용 관계·양도 조건은 이 입력에 없으므로 판단하지 않습니다. 자신의 기여를 설명하는 기록과 공개 이용 권한을 입증하는 기록은 따로 확인해야 합니다.

먼저 확인할 개념

  • 공개 자료의 출처 기록

완성품 뒤의 여러 손

학급에서 길 찾기 도구를 만든다고 하자. 민은 경로 비용을 설명하고, 별은 화면 문장을 쓰며, 준은 틀린 경로를 찾아 보고했다. 화면에 보이는 코드 줄 수만 세면 준의 검토는 사라진다. 어떤 문제를 발견했고 어떤 변경으로 이어졌는지를 함께 남기면 결과가 어떻게 만들어졌는지 이해할 수 있다. 이는 이 강의의 자체 가상 사례이며 세 역할의 우열을 정하는 공식 점수표가 아니다.

기여 기록은 사람을 칭찬하는 문장보다 대상·행위·확인 자료를 구체적으로 적는 데서 시작한다. 예를 들어 “도움 많이 줌”보다 “v2의 음수 비용 처리 오류를 보고하고 예제 두 개를 추가함”이 재검토하기 좋다. 실제로 하지 않은 테스트나 구현을 이름 아래 붙이지 않는다.

표현과 설명 가능한 아이디어

한 알고리즘의 아이디어를 배운 뒤 자기 예제와 자기 문장으로 설명하는 것과, 다른 사람이 그린 그림을 복사하는 것은 같은 행위가 아니다. 참고한 개념은 출처를 밝히고, 복사하려는 표현은 그 자료의 허락 범위를 별도로 확인한다. 출처를 적었다는 이유만으로 복제 허락이 생기지는 않는다.

법적 권리자는 창작자와 항상 일치한다고 단정할 수 없다. 고용 관계·양도·공동 창작 등의 조건과 적용 국가에 따라 확인할 사항이 달라진다. 여기서는 권리자 조사 절차를 배우며 특정 학생이나 팀의 법적 소유권을 판정하지 않는다.

함께 공개하기 전에 합의하기

누가 어떤 부분을 작성했는지, 공개해도 되는 자료인지, 어떤 조건으로 제공할지 팀에서 문서로 정한다. 제안만 한 사람을 코드 저자로 표시하거나 검토한 사람을 전혀 언급하지 않는 기록은 실제 작업을 왜곡한다. 기여 종류를 나누어 표현하면 모두를 같은 법적 저자로 단정하지 않고도 공정한 크레딧을 줄 수 있다.

변경 이력과 기여 표는 증거의 한 부분이다. 기록이 비었다고 기여가 없다는 결론도, 커밋이 많다고 모든 권리를 가진다는 결론도 나오지 않는다. 누락을 발견하면 당사자가 확인할 수 있는 근거를 모아 정정한다.

중간 과정을 따라가는 예제

가상 팀에서 민은 설계 메모, 별은 화면 문장 8개, 준은 오류 보고 2개를 남겼다. 발표자가 별이라면 기여 표에 무엇을 적고 법적 소유권은 어떻게 표시할까?

  1. 산출물 세 종류를 설계 메모·화면 문장·오류 보고로 나눈다.

  2. 민/별/준을 각각 실제 산출물에 연결한다. 발표 역할은 별에게 별도 표기한다.

  3. 오류 보고가 실제 수정으로 이어졌는지 변경 이력을 연결하고 미확인이라면 미확인으로 둔다.

  4. 법적 권리자·공개 동의는 이 입력만으로 정할 수 없으므로 팀 합의 및 관련 조건 확인 항목으로 남긴다.

기여 표는 민—설계, 별—문장 작성·발표, 준—오류 검토다. 발표자 한 명을 전체 창작자로 표시하지 않으며 법적 권리자 상태는 별도 확인한다.

보고와 해결 연결의 두 수

준의 R1과 R2 중 R1만 F1로 해결됨이 확인되었습니다. 보고 수·확인된 해결 연결 수와 그 비율을 쓰세요.

  1. 보고 활동은 R1과 R2 두 건입니다.

  2. 해결 변경과 연결된 것은 R1 한 건이며 R2의 결과는 아직 미확인입니다.

  3. 보고 두 건을 분모로 두면 확인된 연결 비율은 1/2입니다.

보고는 두 건이고 확인된 해결 연결은 한 건입니다. 연결 비율은 1/2이며 공로 지분은 정해지지 않았습니다.

제거된 표현의 현재 상태와 이력

문장 d를 민이 v1에서 작성하고 별이 v2에서 교정했으며 v3에서 제거했습니다. 현재 기여 설명과 이력을 구성하세요.

  1. 현재 v3의 사용 목록에서 문장 d를 사용 종료로 표시합니다.

준비 개념과 학습 목표

준비 개념

  • 열람은 화면에서 보는 행위이고 재배포는 다른 사람에게 사본을 제공하는 행위다.

  • 라이선스는 권한 있는 제공자가 정한 이용 허락과 조건이다.

  • 아래 사례는 권리자가 명시한 조건을 가정한 교육용 판정이다.

학습 목표

  • 무료 열람과 복제·수정 허락을 구분한다.

  • 명시된 라이선스의 범위·의무를 읽는다.

  • 출처가 다른 구성요소를 하나의 허락으로 덮지 않는다.

LICENSE 사본 한 개면 구성요소 네 개의 조건이 모두 충족되나요?

앞 본문은 직접 만든 자료와 Apache 코드·CC 그림의 조건을 각각 읽습니다. 새 종이 배포 묶음에는 자체 코드 A, 수정한 Apache 2.0 코드 B의 파일 b1과 b2, 색을 바꾼 CC BY 4.0 그림 C, 허락 근거가 없는 사진 D가 있습니다. A는 자기 권리가 확인되었다고 가정하고 B와 C는 권한 있는 제공자가 해당 자료에 명시한 조건이라고 가정합니다. 사진 D에는 별도 허락·적용 예외의 근거가 주어지지 않았습니다. 이것은 실제 특정 파일의 권리를 확인한 사례가 아닙니다.

B의 소스 배포에는 LICENSE 사본과 관련 기존 고지가 이미 준비되었지만 수정 고지는 b1에만 있고 b2에는 없습니다. 원래 NOTICE의 N1과 N2 중 N1은 현재 B의 부분에 관련되며 N2는 제거한 별도 부분에만 관련된다고 명시합니다. 새 묶음에는 N1의 읽을 수 있는 사본이 없으므로 추가합니다. 이 조건에서 b2의 수정 고지와 N1의 사본이 빠졌습니다. NOTICE 원본 파일 이름을 언제나 그대로 유지해야 한다는 규칙을 만들지 않으며 원문이 허용하는 문서 등 위치도 비교합니다.

C에는 제공자가 창작자·저작권·라이선스·면책 고지와 원본 링크를 함께 제공했다고 둡니다. 현재 크레딧은 창작자와 원본 링크만 적혀 있으므로 제공된 관련 고지, 라이선스 표시와 링크, 이번 색 변경 및 이전 변경 표시를 더 확인합니다. 원저자가 우리 강의를 승인한 것처럼 쓰지 않습니다. 대표 LICENSE가 있다는 사실은 C의 조건이나 D의 허락 근거를 만들지 않습니다. 실제 모든 의무의 완전성은 전문과 이용 조건을 함께 검토해야 하며 아래 수는 지정한 체크리스트만 셉니다.

가격 대신 이용 범위를 읽는다

다운로드 버튼이 있거나 비용이 없다는 사실만으로 수정·배포까지 허용되었다고 읽지 않는다. 코드·문장·사진마다 제공자가 정한 조건을 확인하고 그 자료가 허락 대상에 실제 포함되는지 본다. 같은 웹사이트에도 별도 저작권의 사진이 섞일 수 있다.

기본 절차는 자료 식별→권한 있는 제공자 확인→허락 조항 확인→하려는 이용과 비교→필요한 표시와 보존이다. 허락이 없거나 범위가 불분명하면 임의로 새 라이선스를 붙여 해결할 수 없다. 직접 만든 자료로 대체하거나 확인이 필요한 항목으로 남긴다.

두 라이선스를 서로 바꾸지 않는다

Apache 2.0 자료를 수정해 배포하는 가상 경우에는 라이선스 사본, 수정한 파일의 변경 고지, 관련 고지의 보존, 포함된 관련 NOTICE 처리 등을 원문에 맞게 준비한다. 상표의 일반적 사용 허락이나 품질 보증이 자동으로 생기는 것은 아니다. 조건의 전체 목록은 실제 원문으로 확인한다.

CC BY 4.0으로 명시된 가상 그림은 적절한 크레딧과 라이선스 링크, 변경 표시 등을 갖추어 활용하는 예를 생각할 수 있다. 그 그림을 코드 저장소에 넣었다고 그림의 원래 조건이 Apache로 바뀌지는 않는다. 사진 속 사람의 권리 같은 추가 조건은 저작권 라이선스만으로 모두 해결되지 않을 수 있다. 제공자가 함께 제시한 저작권·라이선스·면책 고지와 자료 링크 등도 해당 조건에 따라 보존한다. 크레딧 예시는 이 정보가 제공되었는지 확인하는 단계까지 포함한다.

아이디어와 사본을 구별한다

공식 자료를 읽고 자기 수치·자기 풀이로 새 예제를 만드는 활동은 원본 그림이나 문장을 통째로 복사하는 활동과 구분해 기록한다. 출처는 어느 설명을 참고했는지 연결하고 직접 복제한 부분은 더 명확하게 표시한다. 공개 강의의 목표가 좋다는 사실도 모든 외부 표현을 재배포할 허락은 아니다.

국가별 이용 예외는 서로 다를 수 있다. 이 단원은 특정 분량이 언제나 합법이라는 수치를 제시하지 않는다. 실제 이용에서는 적용 법과 정확한 라이선스 전문·권리 범위를 따로 확인한다.

소단원 5.3

공개 자료의 출처 기록

링크 하나를 적어 놓았는데 내년에는 어떤 그림을 썼는지 알 수 있을까?

준비 개념과 학습 목표

준비 개념

  • URL은 자료가 위치한 주소이며 파일이나 버전의 내용 자체는 아니다.

  • 출처 기록과 권리·라이선스 기록은 서로 연결되는 별도 정보다.

  • 가상 자료에 대한 예시는 실제 타인의 허락 확인 결과가 아니다.

학습 목표

  • 자료·버전·이용 위치·변경 범위를 연결한 기록을 만든다.

  • 확인 날짜와 라이선스 근거를 구별한다.

  • 후속 변경 때 원래 출처와 자기 기여를 보존한다.

URL이 같아도 같은 그림이라고 확인할 수 있나요?

앞 본문은 제목·제공자·버전·이용 위치·변경을 연결한 기록을 만듭니다. 새 가상 장부에서 외부 그림 K의 주소는 u이고 자료 식별자는 K1입니다. 강의 v1은 K1을 그대로 쓰고 v2는 K1을 자른 자체 수정본 K1c를 사용했습니다. v3에서는 K1c를 제거하고 자체 그림 J를 넣었습니다. u와 식별자는 모두 가상 입력이며 실제 URL 방문이나 파일 복제를 하지 않습니다. 장부에는 원자료 K1, 자기 수정 K1c와 사용 종료, 새 J를 구별합니다.

이후 주소 u의 내용이 K2로 바뀌었다고 알려져도 옛 강의에서 K2를 사용했다고 고치지 않습니다. 같은 주소는 과거 내용의 동일성을 보장하지 않습니다. K2의 크레딧이나 조건이 다르면 새 이용 때 새 범위를 확인합니다. 파일 지문은 비교 대상의 바이트 동일성을 점검하는 기술적 단서일 뿐 작성자·이용 허락·자료의 진실성을 입증하지 않습니다. 이 단원에서는 실제 지문을 계산하지 않고 동일/상이하다고 주어진 가상 관측만 사용합니다.

별도 자체 점검표에는 현재 사용 자료 E/F/G/H 네 행이 있습니다. E와 F는 원자료·조건·변경·현재 위치가 확인되었고 G는 주소만 있으며 H는 정확한 판본은 알지만 공개 이용 조건을 확인하지 못했습니다. 지정 점검 완료 비율은 2/4입니다. 과거에 사용 종료한 K1c를 분모에 섞지 않습니다. 완료 행의 수와 적법한 공개라는 판단, 실제 공개를 수행했다는 사실은 서로 다른 보고입니다.

먼저 확인할 개념
  • 공개 자료의 출처 기록

    같은 URL의 내용·버전·사용 위치·사용 종료를 별도로 추적하는 본문을 적용합니다.

  • 저작권·라이선스의 개념

    출처 식별과 정확한 허락 대상·이용 조건을 함께 확인하는 이유를 적용합니다.

남이 다시 확인할 수 있게 적는다

강의의 한 그림을 다음 사람이 수정하려면 어느 자료에서 왔고 어디까지 바꾸었는지 알 수 있어야 한다. 제목, 작성자나 제공자, 정확한 URL, 확인 날짜, 이용한 절·그림 번호, 허락 근거, 우리 문서의 사용 위치, 변경 내용을 함께 남기는 표를 설계해 보자. 이것은 이 강의의 권장 기록 양식이며 모든 라이선스가 같은 칸을 법적 의무로 요구한다는 뜻은 아니다.

“인터넷 참고”는 검색 경로일 뿐 자료 식별이 어렵다. “교재 2판, 3절 그림 4를 참고해 자체 그림 작성”처럼 입력과 자기 작업을 나누면 원본 사본을 썼는지도 확인하기 쉽다. 단순 참고인지 재사용인지도 표에 구분한다.

조건과 확인 범위

라이선스 이름만 적지 말고 원문 링크와 적용 대상도 적는다. 페이지의 본문 조건이 첨부 사진에도 적용되는지 확인하지 않았다면 그 범위를 미확인으로 남긴다. 날짜는 당시 확인한 시점을 나타내며 이후 조건이나 내용이 바뀌지 않았다는 보증이 아니다.

CC BY 가상 그림을 자르면 원본 제공자·자료 링크·라이선스 링크와 변경 표시를 연결한다. 원저자가 새 강의를 승인한 듯한 문구는 사용하지 않는다. Apache 가상 코드의 경우 기존 관련 고지와 배포 NOTICE를 보존하면서 자기 수정 내용을 덧붙인다. 크레딧과 허락 조건을 한 표에서 추적하되 서로 대체하지 않는다.

버전이 바뀔 때의 절차

강의 v1에서 v2로 수정할 때 외부 자료 행을 지우고 “전부 자체 작성”으로 바꾸지 않는다. 제거했다면 사용 종료를 기록하고, 새 자료로 교체했다면 새 출처와 새 조건을 확인한다. 접근할 수 없는 링크는 확인하지 못한 사실을 남기고 이전 내용이 계속 유효하다고 단정하지 않는다.

원문을 보관할 수 있는 범위도 허락에 따라 다르다. 주소·제목·버전·우리 이용 위치를 기록하는 것과 원본 파일 전체를 공개 저장소에 복제하는 것은 다른 작업이다. 재현성을 높이려는 목적만으로 원본 재배포 권한이 생기지는 않는다.
