dangling reference·view

문자열을 복사하지 않고 바라보는 작은 객체는 원본을 언제까지 지켜 줄까?

준비 개념

학습 목표

  • 반환값 소유와 사용 기간 계약을 설계한다.

컨테이너의 원소 주소와 그 원소가 소유한 객체 주소는 같이 움직일까?

vector<unique_ptr<int>> owners는 서로 별도로 정상 할당한 정수 객체 A=10, B=20을 소유한다. 첫 두 원소를 만든 뒤 slot=&owners[1]과 raw=owners[1].get()을 빌린다. 뒤 추가가 재할당하는 비교와 재할당하지 않는 비교를 명시적으로 나누며 모든 추가·이동은 정상 완료하고 기본 deleter는 비던짐이다. slot은 vector 안 관리 객체를, raw는 별도 정수 B를 가리킨다.

저장소 재할당은 unique_ptr 관리 객체의 위치를 바꾸지만 이동한 unique_ptr의 별도 정수 소유권은 유지한다. 따라서 이전 slot은 무효인 반면 raw는 B의 새 소유자가 살아 있는 동안 유효하다. 어느 주소가 안정적인지 대상 객체의 수명 장부로 읽어야 한다. 이후 해당 소유 원소를 erase하면 B가 삭제되어 raw도 끝난다. 재할당하지 않는다고 erase 위치 이후의 관리 객체 참조까지 보존되는 것은 아니다.

가리키는 객체가 살아 있어야 한다

참조는 별명을 붙이고 string_view는 문자열의 위치와 길이를 가진다. string_view 자체를 복사해도 문자 소유권이 생기지 않는다. 원본이 먼저 사라지면 길이가 남아 있다는 사실만으로 문자를 읽을 수 없다.

가상 함수 안의 std::string local = "cat"을 바라보는 view를 반환하면 local은 함수 종료 때 사라진다. view를 받는 호출자에게 실제 문자열 소유 값을 반환하거나, 호출자 소유 자료를 정해진 사용 기간 동안 빌려 보는 방식으로 계약을 고친다.

살아 있는 컨테이너도 저장소를 옮길 수 있다

vector 객체가 계속 살아 있어도 재할당이 일어나면 기존 요소 참조와 포인터는 무효가 된다. 따라서 컨테이너 수명뿐 아니라 저장소를 바꾸는 연산도 확인한다. reserve 호출 이전에 얻은 참조를 이후 재할당에도 재사용하면 안 된다.

재할당이 없어도 중간 insert와 erase는 삽입/제거 위치 이후의 참조 등에 영향을 준다. 인덱스도 요소 이동 뒤 같은 논리 대상이라는 보장이 없다. 수정 뒤에 필요하면 대상 식별자로 다시 찾고 새 참조를 얻는다.

빌려 주는 범위와 반환 값을 밝힌다

함수가 view를 잠깐 읽기만 하는지 보관하는지 구별한다. 호출자가 함수 반환 뒤 원본을 지워도 되는지는 보관 계약에 달려 있다. const로 읽기 전용임을 표현해도 원본 수명이 늘어나지는 않는다.

위험한 접근을 실행해 특정 문자열을 출력하는 활동은 하지 않는다. 종이에 생성·참조 획득·수정·파괴·사용의 순서를 그려 사용 시점에서 유효함을 따진다. 실제 검증 도구는 뒤 소단원에서 다룬다.

A만 삭제되고 B는 살아 있음

B 삭제 / raw 무효

이후 raw 역참조 결과를 예측하지 않음

erase 두 행은 독립 초기 A/B 상태에서 시작하며 셋째 행은 앞 A를, 넷째 행은 B를 지운다. raw가 살아 있다는 판단은 unique_ptr의 기본 소유권 규약과 정상 작업 전제를 사용하며 실제 주소 관측이 아니다.

중간 과정을 따라가는 예제

가상 수명표에서 t1에 local="cat" 생성, t2에 view 획득, t3에 함수 반환으로 local 파괴, t4에 호출자가 view 문자를 읽는다. 소유 std::string 결과를 값으로 반환하는 수정과 비교하라.

  1. t2에는 원본이 살아 있어 길이 3과 문자 범위가 유효하다.

  2. t3 이후 view에 위치·길이가 남아도 local의 수명은 끝났다. t4 문자 접근의 결과를 약속할 수 없다.

  3. 값으로 반환한 문자열은 호출자가 가진 결과 객체의 수명 안에서 문자를 소유한다. 반환 뒤 호출자의 결과 객체가 살아 있는 t4 읽기를 설계할 수 있다.

빌린 view의 t4 접근은 유효하지 않다. 소유 값 반환 또는 원본 수명 보존 계약으로 해결한다.

조건을 바꾸어 비교하기

재할당의 두 층을 그리기

A/B 초기 상태에서 C=30 소유자를 추가하며 vector 재할당이 일어난다고 정한다. slot과 raw의 읽기 허용성을 구하라.

  1. 이전 vector 원소의 주소 slot은 재할당으로 무효다.

  2. B의 정수 객체는 이동 생성으로 새로 만들어지는 것이 아니라 소유권이 옮겨진다.

slot 역참조는 허용되지 않고 raw는 B=20을 읽을 수 있다. 이후 B 소유자 파괴 시 raw도 끝난다.

비교할 점

base의 vector 참조 무효화에 관리 객체와 별도 자원의 두 수명을 더한다.

주소가 살아도 숫자 인덱스의 뜻은 바뀐다

A/B/C를 소유한 vector에서 rawB와 indexB=1을 기록한 뒤 첫 A를 정상 erase한다. rawB와 owners[indexB]의 뜻을 비교하라.

  1. A가 삭제되고 남은 순서는 B,C다.

  2. rawB는 살아 있는 B를 가리키지만 인덱스 1은 이제 C다.

rawB의 값은 20, owners[1]의 값은 30이다. 옛 slotB는 erase 규칙상 무효다.

비교할 점

인덱스가 범위 안이라는 조건만으로 원래 정체성을 보존하지 않는다.

할당을 줄이려는 매번 reserve가 오히려 이동을 늘릴 수 있을까?

자체 용량 모형을 두 개 정한다. L은 각 삽입 전에 reserve(size+1)를 호출하고 요청한 용량 그대로 새 저장소를 얻는다. G는 처음 1칸에서 용량 부족 때 2배로 성장한다. 둘 다 빈 상태에서 정수 6개를 추가하고 새 원소 생성은 별도 6회다. 실제 표준 vector의 reserve가 요청값과 정확히 같은 capacity를 주는 보장은 없으므로 이 표는 L/G라는 교육 정책의 비교다.

L은 용량 1,2,3,4,5,6을 지나 기존 원소 0+1+2+3+4+5=15개를 옮긴다. G는 1,2,4,8을 지나 0+1+2+4=7개를 옮긴다. 마지막 여유는 L의 0칸과 G의 2칸이다. 이동 누적, 마지막 여유, 새 저장소와 옛 저장소가 함께 있는 순간 피크는 서로 다른 지표다. 실제 원소가 소유한 문자열·정수 자원의 별도 할당도 vector 저장소 횟수와 합치지 않는다.

원소 수와 확보한 자리를 따로 센다

size는 현재 존재하는 원소 수이고 capacity는 재할당 없이 담을 수 있는 원소 수다. reserve는 용량을 확보하려는 요청이며 size를 늘리지 않는다. reserve(8) 뒤 size가 0이면 v[0]부터 v[7]을 유효 원소처럼 쓰면 안 된다.

resize는 필요한 원소를 생성하거나 제거한다. 빈 vector<int>에 resize(8)을 성공시키면 원소 8개가 생긴다. 용량과 원소 존재를 다른 표로 그려 범위 검사를 먼저 한다.

추가마다 같은 비용이 드는 것은 아니다

추가가 용량 안이면 새 원소를 만드는 일을 하고, 용량을 넘으면 새 저장소 확보와 기존 요소 이동 또는 복사 등의 작업이 필요할 수 있다. 요소 타입의 이동·복사·예외 조건에 따라 실제 비용이 달라진다.

아래 두 배 성장 모형은 설명용이다. 표준이 모든 구현에 정확한 두 배 성장이나 같은 주소를 약속한다는 뜻은 아니다. 실제 allocator 호출 수와 시간은 구현·컴파일 옵션·입력과 측정 조건을 기록해 확인한다.

필요량과 여유 자원의 균형을 본다

처음 필요한 개수를 알면 한 번 reserve해 재할당을 줄일 수 있다. 그러나 큰 추측 용량을 무조건 확보하면 메모리 부담이 늘고, 요소마다 reserve(size+1)를 하여 성장을 제한하는 방식도 비용을 키울 수 있다.

shrink_to_fit은 용량을 size로 줄이라는 강제 보장이 아닌 요청이다. 재할당이 일어나면 참조도 무효가 될 수 있다. 공간을 줄이려는 변경과 수명 계약을 함께 검토한다.

행별 할당은 컨테이너 원소 저장소만 센다. 원소 한 칸을 가상 4바이트로 잡으면 마지막 공간 L=24바이트, G=32바이트, 공존 피크는 44/48바이트다. allocator 메타데이터·정렬·별도 자원은 이 모형에 포함하지 않는다.

중간 과정을 따라가는 예제

빈 모형 컨테이너가 1,2,4,8 용량으로 정확히 성장한다고 가정한다. 원소 8개를 하나씩 넣을 때 저장소 확보 수와 옛 요소 이동 수를 계산하라. 처음 용량 8을 확보한 모형과 비교하라.

  1. 새 용량 1,2,4,8을 확보하는 네 번의 단계가 있다.

  2. 옛 요소 이동은 0 + 1 + 2 + 4 = 7개다. 새 원소 생성 8개와 구별한다.

  3. 처음 용량 8을 확보하면 저장소 확보는 1번, 기존 요소 이동은 0개다. 두 모형 모두 새 원소 8개를 만든다.

성장 모형은 확보 4번·이동 7개, 사전 확보 모형은 확보 1번·이동 0개다. 실제 vector 실행 측정은 아니다.

GoogleTest를 쓰는 이론 시험에서 void check(const vector<int>& v){ASSERT_FALSE(v.empty());}라는 도우미 뒤 호출자 TEST 본문이 check(v); EXPECT_EQ(v[0],7);을 수행한다고 정한다. 빈 입력에서 ASSERT 실패는 현재 도우미 함수에서 반환하지만 호출자 함수 전체를 자동 반환시키지는 않는다. 기록된 fatal failure와 제어 흐름을 같은 것으로 읽지 않는다.

고치는 한 방법은 도우미가 bool usable(const vector<int>& v){return !v.empty();}를 돌려주고 TEST 본문에 ASSERT_TRUE(usable(v)); 다음에 접근을 두는 것이다. 선행 검사는 접근하는 현재 함수에서 중단한다. 이것도 v의 수명이 이후까지 유효하고 다른 경로가 변경하지 않는다는 조건을 요구한다. 반환값 시험·수명 계약·sanitizer의 도달 경로 보고는 서로 보완하며 설치하지 않은 시험을 실제 통과라고 적지 않는다.

기대 결과를 계약에서 정한다

단위 시험은 작은 기능에 입력을 주고 기대 결과를 비교한다. 코드와 똑같은 계산식을 복제하기보다 계약의 경계·실패 조건에서 사례를 정한다. 각 시험은 다른 시험의 잔여 상태에 의존하지 않도록 자료를 준비한다.

GoogleTest의 EXPECT는 실패를 기록하고 현재 함수의 뒤 검사도 계속할 수 있으며 ASSERT는 실패 때 현재 함수를 끝낸다. 다음 접근의 선행 조건이 없으면 더 읽기 전에 중단하는 검사가 필요하다. 실제 설치나 실행을 하지 않은 시험 문장은 계획으로 기록한다.

메모리 오류는 별도 증거다

AddressSanitizer는 컴파일러 계측과 실행 런타임으로 실제 도달한 범위 밖 접근이나 수명 종료 후 사용 등을 찾는다. 검사된 출력이 맞아도 중간에 잘못된 접근이 있을 수 있어 결과 시험과 함께 사용한다.

도구가 모든 실행 경로나 업무 조건을 증명하지는 않는다. 옵션·플랫폼·계측 범위와 컨테이너 지원도 확인한다. 계측 없이 작성된 실행 파일을 한 번 돌렸다는 기록을 sanitizer 검사로 적지 않는다.

실패의 원인과 정상 동작을 함께 지킨다

오류 보고의 입력과 빌드를 보존하고 원인을 수정한 뒤 동일 입력과 정상 입력을 다시 검사한다. 모든 입력을 거절하여 크래시만 없애면 정상 계약을 깨뜨릴 수 있다. 실패 재현 시험과 회귀 시험을 함께 관리한다.

크래시가 없다는 사실, 기대값 일치, sanitizer 보고 없음, 모든 입력의 안전 논증은 서로 다른 근거다. 본문은 위험한 참조를 실제로 읽지 않으며 시험표의 기대만 손검토한다.

핵심 반복의 개선이 적은 호출에서도 전체 개선일까?

가상 대안 A는 준비 2ms와 요청당 8ms, B는 준비 14ms와 요청당 5ms가 든다. 준비는 세션당 한 번이며 요청 수 k는 음이 아닌 정수다. 같은 출력·입력·실패 계약을 만족한다고 가정하여 전체 시간 TA=2+8k, TB=14+5k로 비교한다. 이는 profiler·장치 관측값이 아닌 자체 모델이다.

TB<TA는 12<3k이므로 k>4일 때만 성립한다. k=4는 둘 다 34ms다. 준비를 제외한 요청당 비용만 보면 언제나 B를 고르지만 한 요청의 전체 시간은 A=10ms, B=19ms다. 실제 서비스의 호출 수 분포와 처음/반복 실행 목적을 먼저 정해야 한다. warmup 제외 반복, 사용자 전체 지연, 전체 CPU 소비는 같은 지표가 아니다.

프로파일링은 시간이 많이 쓰인 곳과 호출 빈도 등을 관찰해 개선 대상을 찾는 과정이다. 코드가 길거나 복잡해 보인다는 이유만으로 병목이라고 정하지 않는다. 입력·환경·빌드와 관찰 범위를 함께 남긴다.

아래 숫자는 실제 profiler 결과가 아닌 가상 시간표다. 구간 최적화의 기대 효과를 계산하는 연습에 쓴다. 실제 결과를 얻으려면 같은 업무와 입력에서 전체 시간을 비교하고 정확한 출력도 확인한다.

같은 조건의 비교를 설계한다

컴파일 최적화 옵션과 라이브러리, 장치, 입력 크기, 캐시 상태, 측정 구간을 맞춘다. 준비 작업까지 포함한 전체 시간과 핵심 반복만 측정한 시간은 별개다. warmup을 제외했다면 실제 첫 실행의 비용도 따로 고려한다.

Google Benchmark는 반복 결과의 통계를 제공하지만 도구 이름만으로 공정한 실험이 되지는 않는다. 출력이 사용되지 않아 계산이 제거될 수 있으며 DoNotOptimize도 식 내부의 모든 최적화를 금지하지 않는다. 측정할 일이 실제로 수행되는지 점검한다.

속도 배수와 시간 감소율을 구별한다

시간이 100ms에서 80ms로 줄면 속도 배수는 100/80 = 1.25배이고 시간 감소율은 20/100 = 20%다. 어느 표현을 쓰는지 분모를 표시한다. 더 많은 메모리 사용이나 유지 비용도 함께 평가한다.

반복 평균이나 중앙값만 좋은 경우 긴 지연이 남을 수 있다. 실제 사용자 흐름에 맞는 지표를 정하고 실패·변동과 정확성 검사를 함께 기록한다. 미측정 대안에는 예상이라는 상태를 붙인다.
