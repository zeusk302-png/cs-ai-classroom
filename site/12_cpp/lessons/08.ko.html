handler를 어디에 두느냐에 따라 자원 정리 시점도 달라질까?

새 사건 모형에서 바깥 자동 Guard A는 try에 들어가기 전에 생성 완료한다. try 안에서 자동 Guard B를 생성 완료한 뒤 예외가 발생하고 바로 그 try의 handler로 간다. B는 정리되지만 A는 여전히 바깥 스코프 안에 살아 있다. handler가 끝난 뒤 바깥 스코프 종료 때 A를 정리한다. 생성 완료 기록은 +이름, 정리는 -이름, handler 진입은 H다.

A/B가 모두 try 안에서 생성된 base 사례의 +A,+B,-B,-A,H와 비교한다. 같은 예외라도 어디부터 어디까지 수명이 종료되는지를 따라야 한다. 각 Guard 정리는 던지지 않으며 실제 파일·잠금은 사용하지 않는다. 살아 있는 Guard가 있다는 사실은 관찰 포인터의 범위나 동시 쓰기 안전성까지 증명하지 않는다.

정리 책임을 객체 수명에 붙이기

RAII 는 자원을 관리 객체가 보유하고 객체의 수명이 끝날 때 소멸자로 해제하는 방식이다. 메모리뿐 아니라 파일·잠금·연결처럼 사용 후 돌려줘야 할 것도 자원이다. 생성자는 유효 관리 상태를 만들고 소멸자는 약속한 해제 작업을 맡는다.

scope 는 코드의 이름 범위이며 자동 저장 객체의 수명 종료와 연결되는 기본 사례를 제공한다. 성공 경로의 마지막 줄에 close 를 적는 것만으로는 중간 return·예외 경로까지 보장하기 어렵다. RAII 는 각 종료 경로에 흩어진 해제를 객체 수명에 모은다.

완료된 생성의 역순으로 정리

A 를 성공 생성한 뒤 B 를 성공 생성하면 같은 블록을 나갈 때 B,A 순서로 소멸한다. 예외가 발생해 handler 까지 stack unwinding 을 할 때도 그 구간의 완료된 자동 객체는 역순으로 정리된다. 모든 종료 방식에 이 규칙을 적용하는 것은 아니다. 비정상 종료·프로세스 강제 중단은 다른 조건이다.

비위임 생성자 B 가 중간 실패하면 완성되지 않은 B 자체의 소멸자는 호출되지 않는다. 이미 완성된 B 의 하위 객체는 규칙에 따라 정리된다. 그러므로 생성 도중 얻은 자원도 먼저 RAII 멤버에 맡기면 정리 경로를 구성하기 쉽다.

소멸자 계약도 점검하기

소멸자에서 자원을 돌려주는 방법이 실패할 수 있다면 실패 기록 정책을 따로 설계한다. 예외 unwinding 중 또 예외를 던져 종료되는 문제를 피하도록 소멸자를 비던짐 정리로 설계하는 것이 일반적이다. noexcept 표기만으로 실패가 없어지는 것은 아니다.

  1. A 생성완료를+A 로적고 B 완료를+B 로적는다.

  2. 예외 발생위치에서 handler 로가는도중 B 가 먼저 파괴되어-B 다.

  3. A 가 다음 파괴되어-A,그후 handler 진입 H 다.

예상 사건 +A,+B,-B,-A,H 다. 실제 C++ 교육 코드는 실행하지 않았다.

조건을 바꾸어 비교하기

handler 밖에서 관리하는 자원

A는 try 바깥, B는 try 안에서 생성됐다. handler는 A를 이용해 실패 내용을 처리한 뒤 바깥 블록을 끝낸다.

  1. B를 정리한 뒤 handler에 들어간다.

  2. A는 handler 동안 살아 있고 바깥 블록 끝에서 정리된다.

+A,+B,-B,H,-A 순서다.

비교할 점

예외 발생만으로 모든 자동 객체를 한꺼번에 파괴하지 않는다.

관리 객체가 수명을 끝내지 않은 누수

new로 만든 Guard를 raw 포인터만 보관하고 포인터 변수 스코프가 끝났다. delete도 없고 소유 manager도 없다.

  1. raw 포인터 변수 종료는 동적 Guard의 delete가 아니다.

  2. Guard 자체의 소멸이 실행된 경로가 없다.

RAII 타입의 Guard라도 동적 관리 객체를 누수시키면 자원 자동 정리를 주장할 수 없다.

비교할 점

소유 관리 객체의 실제 수명 종료가 있어야 정리가 연결된다.

풀이 보기

RAII 이면 모든 종료에서 무조건 소멸자가 실행된다.

unique_ptr

한 자원에 해제 책임자가 하나라는 약속을 어떻게 표현할까?

준비 개념과 학습 목표

준비 개념

  • 소유권과 빌림

  • move

  • nullptr

학습 목표

  • move 와 get/release/reset 를구별한다.

  • 옛 소유자와 빌림 수명을 추적한다.

소유자를 바꾼 뒤 같은 raw 주소는 언제까지 유효할까?

새 p는 int 자원 R을, q는 다른 int 자원 S를 각각 unique_ptr로 소유한다. 기본 deleter와 할당 성공을 전제한다. int* borrowed=p.get(); 뒤 p.swap(q)를 하면 p는 S, q는 R을 소유한다. borrowed는 여전히 같은 R을 가리키며 q가 R을 유지하는 동안 유효하다. 포인터는 관리 객체 이름을 기억하는 표지가 아니다.

q.release()는 R을 삭제하지 않고 raw 주소를 반환하며 q를 비운다. 이 주소를 새 unique_ptr r에 즉시 맡기면 r이 다음 소유자다. p.reset()은 S를 삭제하고 r.reset()은 R을 삭제한다. release 주소를 방치하는 경로와 get 주소를 다른 독립 소유자에게 넘기는 경로는 각각 누수/중복 소유 문제다. swap의 deleter 교환 조건과 해제의 비던짐 조건도 확인한다.

먼저 확인할 개념
  • 주소 사본과 자원 수

    포인터 값 복사를 독립 자원 생성과 구별한다.

  • 빌림 대상의 수명

    관리 객체 이름 변경과 실제 대상 수명을 별도로 따라간다.

유일한 해제 책임

unique_ptr<T>는 하나의 포인터 소유권을 관리하는 표준 도구다. 일반 복사로 책임자를 둘로 늘리지 않고 이동으로 책임을 넘긴다. 두 개의 unique_ptr 를 같은 raw 주소에서 별도로 만들면 이 설계를 어기고 중복 해제 위험이 생긴다.

make_unique<int>(7)는 int7 을 만들고 관리 객체를 돌려준다. 아래 예제는 할당 성공과기본 deleter 를가정한다. 메모리주소 값은 숫자로 관측하지 않고 자원 R 이라고 부르므로 플랫폼의 주소 크기나 실행 결과를 꾸미지 않는다.

이동과 빌림을 구별하기

auto q=std::move(p)는 이동 생성으로 p 의자원을 q 에넘긴다. std::move 는 이동 가능한 표현으로 분류하는 변환이고 이 문맥의 이동 생성자가 실제 소유권을 넘긴다. unique_ptr 이동 뒤 p.get()==nullptr 라는 보장을 일반 모든 이동된 형식에 확장하면 안 된다.

get()은해제 책임을 넘기지 않고 raw 포인터를 관찰하거나 빌리는 통로다. p 에서 get 한주소는 q 로 이동한 뒤에도 같은 R 이 살아 있는 동안 사용 가능하지만 q 가 reset/파괴하면 그 빌림은 끝난다. 빈 p 를 역참조할 수 없다.

release 와 reset 은 정반대 책임 변화

release 는 옛 주소를 반환하고 관리 객체를 빈 상태로 만들며 자원을 삭제하지 않는다. 반환 주소를 새 소유자에 즉시 맡기거나 정해진 해제를 하지 않으면 누수될 수 있다. get 과달리해제 책임을 별도로 인계해야 한다.

reset()은 저장 포인터를 새 값으로 바꾼 다음 옛 자원에 deleter 를 호출한다. 기본 인자에서는 빈 상태가 된다. reset(p.get())처럼 자기 주소로 재설정하면 저장 포인터는 같은 주소인데 그 자원은 삭제되므로 유효한 소유 상태가 아니다. 이후 다시 삭제하는 위험도 생긴다. deleter 가 예외를 던지지 않는 계약을 확인한다.

auto p = std::make_unique<int>(7);
int *borrow = p.get();
auto q = std::move(p);
q.reset();
// 이후 borrow로 R을 읽으면 안 된다.

shared_ptr·weak_ptr

여러 곳에서 자원을 쓰되 언제 마지막 사용자가 끝나는지 어떻게 알까?

준비 개념과 학습 목표

준비 개념

  • 소유자 수

  • scope

  • 빈포인터

학습 목표

  • 강한 소유권과약한 관찰을 구별한다.

  • lock 이 만드는 임시 소유자를 센다.

shared_ptr가 가리키는 주소와 소유하는 객체가 다를 수도 있을까?

별도 선택 심화로 aliasing constructor를 사용한다. Box는 int value=7을 직접 멤버로 가진 살아 있는 객체다. owner는 make_shared<Box>()로 Box를 소유한다. shared_ptr<int> part(owner,&owner->value);는 Box의 소유 관리 관계를 공유하지만 저장 포인터는 내부 int를 가리킨다. owner.reset() 뒤에도 part가 Box를 살려 두므로 *part는 7이다.

다른 독립 사례에서 shared_ptr<int> marker(owner,nullptr);는 같은 Box 소유 관계를 공유하며 저장 포인터는 null이다. bool(marker)는 false여도 use_count는 0이 아닐 수 있다. weak_ptr<int> w=marker;의 expired는 강한 소유자 수로 판단하며 lock 성공 결과도 저장 포인터가 null일 수 있다. 이 특수 사례를 base의 비별칭 단일 객체 예제와 섞지 않고 관찰 주소와 소유 관계를 두 열로 설명한다.

먼저 확인할 개념
  • 강한 소유자와 약한 관찰

    weak expired와 lock을 관리 관계에서 판단한다.

  • 읽기 경로와 객체 자체

    조회 경로의 속성과 전체 소유 상태가 다른 개념임을 연결한다.

여러 소유자가 하나의 관리 관계를 공유하기

shared_ptr 를 복사하면 같은 관리 관계의강한 소유자가 늘어난다. 단순 raw 포인터 복사는 이 개수를 늘리지 않는다. 같은 raw 주소에서 shared_ptr 를 따로 두 번 생성하면 한 관리 관계를 공유한 복사가 아니라 독립 해제 책임 둘이 될 수 있어 위험하다.

마지막강한 소유자가 사라지면 관리 대상에 설정된 deleter 가호출된다. use_count 는그관리 관계를 공유하는 shared_ptr 개수다. 여기서는 비별칭 단일 객체·기본삭제·단일 스레드로 단순 추적하며 대상 데이터의 동시 변경 안전성을 증명하지 않는다.

weak 는 대상 수명을 연장하지 않기

weak_ptr 는관리 관계를 관찰하지만 강한 개수를늘리지 않는다. 강한 개수 0 이면 expired 가 참이며 대상 객체 수명이 끝난 상태다. weak 가 남아 관리 정보가 남을 수 있는 것과 대상 객체가 살아 있는 것은 다르다.

weak.lock()은 원자적으로 살아 있는 강한 소유자를 얻거나 빈 shared_ptr 를돌려준다. expired 검사 후 별도 역참조로 안전하다고 보장하지 말고 lock 결과를 가지고 작업한다. lock 이수명을 확보해도대상 데이터의 race 는별도 잠금 정책이 필요하다.

임시 소유자도 개수에 넣기

소유관계·순환참조·빌림

서로를 가리키는 두 객체는 바깥 변수를 없애도 왜 남을 수 있을까?

준비 개념과 학습 목표

준비 개념

  • shared/weak

  • 그래프 화살표

  • 빌림 수명

학습 목표

  • 강한 소유 그래프의 순환을 추적한다.

  • 약한 역방향과 빌림 계약을 설계한다.

강한 순환 하나를 끊으면 다른 순환도 사라질까?

새 세 객체 A/B/C는 각각 외부 a/b/c의 shared 소유자 하나를 가진다. 강한 멤버 선은 A→B, B→C, C→B이며 C→A는 weak다. 외부 소유자 모두 reset해도 B↔C 강한 순환이 남는다. A는 들어오는 강한 선이 없어 소멸하고 A→B도 사라지지만 B/C는 서로를 한 개씩 잡는다.

C→A의 weak는 A를 조회하는 연결이지 B/C의 소유 순환을 끊는 연결이 아니다. C→B도 weak로 바꾸면 강한 그래프는 A→B→C이고 외부 a만 남은 조건에서 a 종료가 연쇄 정리를 시작한다. 다만 성공 lock으로 C를 소유한 지역 hold가 남으면 C는 그 기간 유지된다. 대상의 수명 확보와 대상 데이터를 안전하게 동시에 바꾸는 것은 별도 계약이다.

먼저 확인할 개념
  • 강한 선만 보는 순환

    외부 이름 수가 아니라 내부 소유 그래프를 그린다.

  • 포인터 대상과 소유 책임

    찾아가는 선과 소유하는 선을 분리한다.

참조선과 소유선을 구별하기

A 가 B 를 읽는다는 뜻과 A 가 B 수명을 연장한다는 뜻은 다르다. 그림에서강한 shared 화살표는 소유자 수에더하고 weak/raw 빌림은 더하지 않는다. 역방향 연결을무조건 shared 로 표현하면 소유권이 필요 없는 관계까지 수명을 붙잡는다.

자체 Node 는 next 멤버가 상대 객체를 shared 소유한다. 외부 a 가 A,외부 b 가 B, A.next→B 와 B.next→A 가 있으면 각 객체 강한 개수 2 다. 외부 변수가 없어져도 내부 강한 선하나씩남아 0 이되지않는다. 이 명시 구조에서는 누수 순환이 생긴다.

약한 역방향이 순환을 끊는 조건

B 에서 A 로 돌아가는 선을 weak 로바꾸고 A 가 B 를 강하게 소유하면 외부 a 제거시 A 의강한 개수 0 이될수있다. A 소멸이 A.next 강한 선을제거하고 B 개수도줄인다. 다만다른 외부 shared 나임시 lock 이 남으면 그 수만큼 수명이 연장된다.

weak 하나를 아무 곳에 놓으면 모든 순환이 사라지는 것은 아니다. 강한 선만 그린 그래프에 다른 순환이 있다면 별도로 남는다. 누가 객체 집합을 소유하고 어느 연결은 찾아가기만 하는지 명확한 소유 계층을 설계한다.

빌림에는 살아 있는 소유자가 필요하기

T*나 T&는지침상 일반적으로 빌림을 표현하지만 C++언어가모든 raw 포인터의해제 책임을 자동 금지하는 것은 아니다. 실제함수 계약에대상 수명·NULL 허용·보관 가능 기간을 적는다. 부모가 소유한 자식을 빌린 포인터는 부모 소유 종료 뒤사용하면 안된다.

weak.lock 성공으로 얻은 지역 shared 를 보유하면 그동안 대상 수명을 확보할 수있다. 하지만 raw 를 돌려주고 지역 shared 를 즉시 버리면 호출자가 쓸 때 유일 소유자가 사라질 수 있다. raw 반환과 소유권 반환은 다른 계약이다.

// 약한선: B.back -weak-> A

조건을 바꾸어 비교하기

엉뚱한 weak 연결

C→A가 weak이므로 모든 순환이 제거됐다고 했다.

  1. 강한 선만 남겨 A→B,B→C,C→B를 그린다.

  2. B↔C는 여전히 닫힌 순환이다.

외부 종료 뒤 B/C 각각 강한 개수 1로 남는다.

비교할 점

조회용 weak 선의 존재와 모든 강한 순환 제거는 다르다.

임시 lock의 소유 기간

순환 없는 A→B→C와 weak 관찰 wC에서 외부 a만 있다. hold=wC.lock() 성공 뒤 a.reset()한다.

  1. hold가 C에 강한 소유자 하나를 추가한다.

  2. A 종료 뒤 B 종료와 B→C 제거가 이어진다.

A/B는 정리되지만 C는 hold 소유 1개로 남고 hold 종료 때 정리된다.

비교할 점

그래프 순환이 없어도 정상적인 임시 소유자가 수명을 연장한다.

종이와 본문으로 직접 해보기

B.back 을 weak 로 바꾸고 초기 외부 a/b 와 A.next 만강하다. a 를먼저 reset 하고 b 를 reset 하면? 반대로 b 먼저면? 별도 lock/외부 소유자는없다.

힌트 보기

A 소멸이멤버 A.next 의강한 소유자를 제거한다는 연쇄를 포함한다.

풀이 보기

처음 A1/B2. a 먼저→A0 소멸/A.next 제거로 B1,b 나중→B0 소멸. b 먼저→A1/B1,A 가 B 를유지; a 나중→A0 소멸→B0 소멸. 두순서모두 A/B 각 1 회삭제다.

오해와 반례

외부 shared 변수만지우면 모든 객체가 자동으로 없어진다.

A/B 내부 강한 순환만남아도 각개수 1 이다. 약한 선 설계와 독립 남은 소유자 검사가 필요하며 별도 순환은 따로 분석한다.

다른 문제에 적용하기

소유 이전과 내부 관찰·순환을 하나의 장부로

각 부분은 새 독립 상태다. 첫 부분은 p가 R, q가 S를 unique_ptr로 소유하고 borrowed=p.get()이다. swap 뒤 p.reset(); raw=q.release(); r(raw); r.reset();을 정상 수행한다. R/S 삭제 시점과 borrowed 사용 가능 기간을 적어라. 둘째 부분은 Box value=7의 shared owner와 alias part(owner,&owner->value), weak w=part다. owner.reset(); h=w.lock(); part.reset(); h.reset(); 뒤 다시 w.lock()한다. 각 강한 개수와 Box/value 수명을 적어라. 셋째 부분은 외부 a/b/c와 강한 A→B,B→C,C→B 및 weak C→A다. 외부 소유자를 모두 지운 결과와 C→B도 weak로 바꾼 별도 루트 설계를 비교하라. 기본 정상 해제·단일 스레드·추가 소유자 없음 전제이며 실제 C++/자원/학생 실행은 하지 않는다.

힌트 1

raw 주소는 처음 빌린 R을 계속 뜻한다. release는 삭제하지 않으며 인계 뒤 r이 R 정리를 맡는다.

힌트 2

alias의 저장 주소는 int지만 소유 관계는 Box다. 성공 lock도 강한 개수에 포함하고 그래프는 강한 선만 남겨 검사한다.

풀이와 답 확인

  1. swap 뒤 p는 S, q는 R이다. p.reset에서 S가 한 번 삭제되지만 borrowed의 R은 살아 있다. release는 삭제 0회이며 r(raw)로 인계한 뒤 r.reset에서 R이 한 번 삭제된다. borrowed는 그 뒤 읽지 않는다.

  2. owner/part 생성 뒤 count=2다. owner.reset 뒤 1, h의 lock 성공 뒤 2, part.reset 뒤 1, h.reset 뒤 0으로 Box와 value가 종료된다. 마지막 lock은 빈 결과다. value 주소로 별도 독립 shared 소유자를 만들지 않는다.

  3. 첫 그래프 외부 종료 뒤 A는 소멸하지만 B/C는 내부 순환으로 각각 강한 개수 1이다. C→B도 weak인 별도 A→B→C 루트는 다른 임시 소유자가 없다면 외부 a 종료로 A/B/C가 연쇄 정리된다.

  4. 각 단계의 예상 정리와 실제 OS·메모리 관측은 구별한다. 이번 모형은 동시 데이터 race 보호나 모든 강제 종료에서의 정리를 검증하지 않았다.

S는 p.reset, R은 r.reset에서 각각 한 번 정리된다. alias 소유 count는 2→1→2→1→0이며 마지막 lock은 빈 결과다. 첫 그래프의 B/C 강한 순환은 남지만 역방향도 weak인 별도 소유 계층은 조건 안에서 연쇄 정리된다.

해결한 뒤 점검할 것

  • 각 부분의 독립 초기 상태와 자원/관리 객체/저장 주소를 분리한다.

  • release의 무삭제와 get의 비소유 빌림을 추적한다.

  • alias와 lock을 같은 Box 소유 관계에서 센다.

  • 모든 강한 순환을 확인하고 임시 소유자와 동기화 범위를 구별한다.
