소단원 8.1

scope 기반 자원관리

중간에 함수가 실패해도 파일이나 잠금을 잊지 않고 돌려주려면?

준비 개념과 학습 목표

준비 개념

  • 지역 변수 수명

  • 생성자·소멸자

  • 예외

학습 목표

  • RAII 의획득/해제 짝을 설명한다.

  • 완료된 객체의 역순 파괴를 추적한다.

정리 책임을 객체 수명에 붙이기

RAII 는 자원을 관리 객체가 보유하고 객체의 수명이 끝날 때 소멸자로 해제하는 방식이다. 메모리뿐 아니라 파일·잠금·연결처럼 사용 후 돌려줘야 할 것도 자원이다. 생성자는 유효 관리 상태를 만들고 소멸자는 약속한 해제 작업을 맡는다.

scope 는 코드의 이름 범위이며 자동 저장 객체의 수명 종료와 연결되는 기본 사례를 제공한다. 성공 경로의 마지막 줄에 close 를 적는 것만으로는 중간 return·예외 경로까지 보장하기 어렵다. RAII 는 각 종료 경로에 흩어진 해제를 객체 수명에 모은다.

완료된 생성의 역순으로 정리

A 를 성공 생성한 뒤 B 를 성공 생성하면 같은 블록을 나갈 때 B,A 순서로 소멸한다. 예외가 발생해 handler 까지 stack unwinding 을 할 때도 그 구간의 완료된 자동 객체는 역순으로 정리된다. 모든 종료 방식에 이 규칙을 적용하는 것은 아니다. 비정상 종료·프로세스 강제 중단은 다른 조건이다.

비위임 생성자 B 가 중간 실패하면 완성되지 않은 B 자체의 소멸자는 호출되지 않는다. 이미 완성된 B 의 하위 객체는 규칙에 따라 정리된다. 그러므로 생성 도중 얻은 자원도 먼저 RAII 멤버에 맡기면 정리 경로를 구성하기 쉽다.

소멸자 계약도 점검하기

소멸자에서 자원을 돌려주는 방법이 실패할 수 있다면 실패 기록 정책을 따로 설계한다. 예외 unwinding 중 또 예외를 던져 종료되는 문제를 피하도록 소멸자를 비던짐 정리로 설계하는 것이 일반적이다. noexcept 표기만으로 실패가 없어지는 것은 아니다.

아래 Log 는 실제 파일 대신 생성/소멸 사건을 종이에 기록하는 자체 모형이다. unlock/close 성공이나 OS 결과를 관측한 것이 아니다. 자원 manager 복사 시 중복 소유가 생기지 않는지도 함께 설계해야 한다.

// 자체 사건 모형: 완료 생성은 +이름, 소멸은 -이름
// 같은 블록에서 A 완료, B 완료, 예외 -> handler

중간 과정을 따라가는 예제

A 완료 생성,B 완료 생성,예외가 handler 로 전파되는 사건을 추론하라. 소멸자는 던지지 않고 외부 강제 종료는없다.

  1. A 생성완료를+A 로적고 B 완료를+B 로적는다.

  2. 예외 발생위치에서 handler 로가는도중 B 가 먼저 파괴되어-B 다.

  3. A 가 다음 파괴되어-A,그후 handler 진입 H 다.

예상 사건 +A,+B,-B,-A,H 다. 실제 C++ 교육 코드는 실행하지 않았다.

종이와 본문으로 직접 해보기

B 비위임 생성자가자원 멤버 M 생성을 완료하고 나서 예외를 던지면? A 는이미완료 생성돼있다. B 자체소멸과 M 소멸을 구별하라.

힌트 보기

완성된 하위 객체와 완성되지 않은 바깥 객체를 분리한다.

풀이 보기

A 완료→M 완료→B 생성 실패→M 소멸→A 소멸→handler 다. B 자체 소멸자는 호출되지 않는다. 이조건에서 M 이 자원을 관리하면 실패 중에도 해제 경로가 있다.

오해와 반례

RAII 이면 모든 종료에서 무조건 소멸자가 실행된다.

정상 scope 종료와 handler 로가는예외 unwinding 이 기본 조건이다. 강제프로세스 종료나자원 관리 객체를 누수시킨 경우까지 자동 해제를 증명하지 않는다.

파일과 잠금을 각 manager 로 설계해 어느 순서로 얻고 역순으로 돌려주는지 그리자. 소멸자의실패 기록과실제 OS 확인은 별도 검증 항목이다.

소단원 8.2

unique_ptr

한 자원에 해제 책임자가 하나라는 약속을 어떻게 표현할까?

준비 개념과 학습 목표

준비 개념

  • 소유권과 빌림

  • move

  • nullptr

학습 목표

  • move 와 get/release/reset 를구별한다.

  • 옛 소유자와 빌림 수명을 추적한다.

유일한 해제 책임

unique_ptr<T>는 하나의 포인터 소유권을 관리하는 표준 도구다. 일반 복사로 책임자를 둘로 늘리지 않고 이동으로 책임을 넘긴다. 두 개의 unique_ptr 를 같은 raw 주소에서 별도로 만들면 이 설계를 어기고 중복 해제 위험이 생긴다.

make_unique<int>(7)는 int7 을 만들고 관리 객체를 돌려준다. 아래 예제는 할당 성공과기본 deleter 를가정한다. 메모리주소 값은 숫자로 관측하지 않고 자원 R 이라고 부르므로 플랫폼의 주소 크기나 실행 결과를 꾸미지 않는다.

이동과 빌림을 구별하기

auto q=std::move(p)는 이동 생성으로 p 의자원을 q 에넘긴다. std::move 는 이동 가능한 표현으로 분류하는 변환이고 이 문맥의 이동 생성자가 실제 소유권을 넘긴다. unique_ptr 이동 뒤 p.get()==nullptr 라는 보장을 일반 모든 이동된 형식에 확장하면 안 된다.

get()은해제 책임을 넘기지 않고 raw 포인터를 관찰하거나 빌리는 통로다. p 에서 get 한주소는 q 로 이동한 뒤에도 같은 R 이 살아 있는 동안 사용 가능하지만 q 가 reset/파괴하면 그 빌림은 끝난다. 빈 p 를 역참조할 수 없다.

release 와 reset 은 정반대 책임 변화

release 는 옛 주소를 반환하고 관리 객체를 빈 상태로 만들며 자원을 삭제하지 않는다. 반환 주소를 새 소유자에 즉시 맡기거나 정해진 해제를 하지 않으면 누수될 수 있다. get 과달리해제 책임을 별도로 인계해야 한다.

reset()은 저장 포인터를 새 값으로 바꾼 다음 옛 자원에 deleter 를 호출한다. 기본 인자에서는 빈 상태가 된다. reset(p.get())처럼 자기 주소로 재설정하면 저장 포인터는 같은 주소인데 그 자원은 삭제되므로 유효한 소유 상태가 아니다. 이후 다시 삭제하는 위험도 생긴다. deleter 가 예외를 던지지 않는 계약을 확인한다.

auto p = std::make_unique<int>(7);
int *borrow = p.get();
auto q = std::move(p);
q.reset();
// 이후 borrow로 R을 읽으면 안 된다.

중간 과정을 따라가는 예제

R 을소유한 p 에서 borrow=p.get(),q=move(p),q.reset() 순서다. 할당 성공·기본 deleter·단일 스레드다.

  1. 처음소유 p→R,borrow→R 이지만 borrow 는 소유자가 아니다.

  2. 이동 뒤 p 빈,q→R,borrow 는 R 이 살아 있어 유효한 읽기 빌림이다.

  3. reset 은 R 을 1 회삭제,q 빈,borrow 대상 수명 끝이다.

삭제 1 회이며빈 p 역참조와 reset 뒤 borrow 사용은금지다.

종이와 본문으로 직접 해보기

R 소유 q 에서 raw=q.release(),그다음 unique_ptr<int> r(raw)를 만들고 블록을 끝낸다. release 직후 R 삭제 횟수와 r 소멸 뒤는? 같은 raw 로또 s 를만들면?

힌트 보기

release 는 삭제가 아니라 책임 인계다. 동일 자원의독립 소유자 수를세라.

풀이 보기

release 직후 0 회/q 빈,raw 책임을 r 에넘긴뒤 r 소멸에서 1 회삭제다. raw 로 s 까지 독립 생성하면 같은 R 의중복 해제 위험이며 허용 설계가 아니다.

오해와 반례

get 과 release 는 모두주소 반환이라같다.

get 은소유권 유지,release 는 소유권 포기다. get 주소를 delete 하면 manager 가 나중에 다시 삭제할 수 있고 release 주소를 방치하면 누수할 수 있다.

한 단계 더

함수 인자를 T&/T*/unique_ptr<T>로받을때읽기 빌림·NULL 허용·소유권 인계를 각기 설계하자. 배열과 custom deleter 는 해제 방식 계약이 추가되는 확장이다.

소단원 8.3

shared_ptr·weak_ptr

여러 곳에서 자원을 쓰되 언제 마지막 사용자가 끝나는지 어떻게 알까?

준비 개념과 학습 목표

준비 개념

  • 소유자 수

  • scope

  • 빈포인터

학습 목표

  • 강한 소유권과약한 관찰을 구별한다.

  • lock 이 만드는 임시 소유자를 센다.

여러 소유자가 하나의 관리 관계를 공유하기

shared_ptr 를 복사하면 같은 관리 관계의강한 소유자가 늘어난다. 단순 raw 포인터 복사는 이 개수를 늘리지 않는다. 같은 raw 주소에서 shared_ptr 를 따로 두 번 생성하면 한 관리 관계를 공유한 복사가 아니라 독립 해제 책임 둘이 될 수 있어 위험하다.

마지막강한 소유자가 사라지면 관리 대상에 설정된 deleter 가호출된다. use_count 는그관리 관계를 공유하는 shared_ptr 개수다. 여기서는 비별칭 단일 객체·기본삭제·단일 스레드로 단순 추적하며 대상 데이터의 동시 변경 안전성을 증명하지 않는다.

weak 는 대상 수명을 연장하지 않기

weak_ptr 는관리 관계를 관찰하지만 강한 개수를늘리지 않는다. 강한 개수 0 이면 expired 가 참이며 대상 객체 수명이 끝난 상태다. weak 가 남아 관리 정보가 남을 수 있는 것과 대상 객체가 살아 있는 것은 다르다.

weak.lock()은 원자적으로 살아 있는 강한 소유자를 얻거나 빈 shared_ptr 를돌려준다. expired 검사 후 별도 역참조로 안전하다고 보장하지 말고 lock 결과를 가지고 작업한다. lock 이수명을 확보해도대상 데이터의 race 는별도 잠금 정책이 필요하다.

임시 소유자도 개수에 넣기

auto b=a 는강한 1 개추가,auto w=weak_ptr(a)는추가 0,auto c=w.lock()이 성공하면 강한 1 개추가다. c 가살아있으면 a,b 를 비워도 객체는 남는다. c.reset()까지 끝나야 마지막 해제를 예측할 수있다.

실제 동시 스레드에서는 use_count 숫자를 보고 나만 있다고 판단해 데이터를 무조건 바꾸면 안 된다. 현재 개수 관측과 미래 동작 보장은 다르다. 본 단원의 숫자는 명시한 단일 스레드 사건 순서에서만 정확한 상태표다.

auto a = std::make_shared<int>(5);
auto b = a;
std::weak_ptr<int> w = a;
auto c = w.lock();
a.reset(); b.reset();
c.reset();
auto d = w.lock();

중간 과정을 따라가는 예제

위코드의강한 개수와 R 삭제 시점을 종이로 추적한다. 할당 성공·단일 스레드다.

  1. a 생성 1,b 복사 2,w 생성여전히 2,c lock 성공 3.

  2. a reset 뒤 2,b reset 뒤 1,c 만 R 소유한다.

  3. c reset 뒤 0 으로 R 삭제 1 회. w.expired 참,d lock 빈/강한 0 이다.

강한 개수 1→2→2→3→2→1→0 이며 weak 는 R 을 살려 두지 않는다.

힌트 보기

오해와 반례

shared_ptr 를쓰면대상 데이터도 자동으로 동시 접근안전하다.

관리 관계와대상 수명에 관한 기능이지 int 내용 동시 쓰기까지 보호하는 잠금이 아니다. 데이터 race 정책은별도다.

소단원 8.4

소유관계·순환참조·빌림

서로를 가리키는 두 객체는 바깥 변수를 없애도 왜 남을 수 있을까?

준비 개념과 학습 목표

준비 개념

  • shared/weak

  • 그래프 화살표

  • 빌림 수명

학습 목표

  • 강한 소유 그래프의 순환을 추적한다.

  • 약한 역방향과 빌림 계약을 설계한다.

참조선과 소유선을 구별하기

A 가 B 를 읽는다는 뜻과 A 가 B 수명을 연장한다는 뜻은 다르다. 그림에서강한 shared 화살표는 소유자 수에더하고 weak/raw 빌림은 더하지 않는다. 역방향 연결을무조건 shared 로 표현하면 소유권이 필요 없는 관계까지 수명을 붙잡는다.

자체 Node 는 next 멤버가 상대 객체를 shared 소유한다. 외부 a 가 A,외부 b 가 B, A.next→B 와 B.next→A 가 있으면 각 객체 강한 개수 2 다. 외부 변수가 없어져도 내부 강한 선하나씩남아 0 이되지않는다. 이 명시 구조에서는 누수 순환이 생긴다.

약한 역방향이 순환을 끊는 조건

B 에서 A 로 돌아가는 선을 weak 로바꾸고 A 가 B 를 강하게 소유하면 외부 a 제거시 A 의강한 개수 0 이될수있다. A 소멸이 A.next 강한 선을제거하고 B 개수도줄인다. 다만다른 외부 shared 나임시 lock 이 남으면 그 수만큼 수명이 연장된다.

weak 하나를 아무 곳에 놓으면 모든 순환이 사라지는 것은 아니다. 강한 선만 그린 그래프에 다른 순환이 있다면 별도로 남는다. 누가 객체 집합을 소유하고 어느 연결은 찾아가기만 하는지 명확한 소유 계층을 설계한다.

빌림에는 살아 있는 소유자가 필요하기

T*나 T&는지침상 일반적으로 빌림을 표현하지만 C++언어가모든 raw 포인터의해제 책임을 자동 금지하는 것은 아니다. 실제함수 계약에대상 수명·NULL 허용·보관 가능 기간을 적는다. 부모가 소유한 자식을 빌린 포인터는 부모 소유 종료 뒤사용하면 안된다.

weak.lock 성공으로 얻은 지역 shared 를 보유하면 그동안 대상 수명을 확보할 수있다. 하지만 raw 를 돌려주고 지역 shared 를 즉시 버리면 호출자가 쓸 때 유일 소유자가 사라질 수 있다. raw 반환과 소유권 반환은 다른 계약이다.

// 강한선: a->A, b->B, A.next->B
// 약한선: B.back -weak-> A
// lock 성공 결과를 보유하는 동안만 관찰 대상 수명을 확보한다.

중간 과정을 따라가는 예제

외부 a→A,b→B 가있고 A.next→B/B.next→A 는 shared 다. 단일 스레드에서 a reset 뒤 b reset 한다. 각강한 개수는?

  1. 처음 A 는 a 와 B.next 로 2,B 는 b 와 A.next 로 2.

  2. a reset 이면 A1/B2. A 는아직 B.next 에 잡혀 소멸하지 않는다.

  3. b reset 이면 A1/B1. 내부 선이서로를 잡아 어느 소멸도 시작하지 않는다.

외부 소유자 0 이지만 A/B 강한 개수각 1,이 구조의대상 삭제 0 회다.

종이와 본문으로 직접 해보기

B.back 을 weak 로 바꾸고 초기 외부 a/b 와 A.next 만강하다. a 를먼저 reset 하고 b 를 reset 하면? 반대로 b 먼저면? 별도 lock/외부 소유자는없다.

힌트 보기

A 소멸이멤버 A.next 의강한 소유자를 제거한다는 연쇄를 포함한다.

풀이 보기

처음 A1/B2. a 먼저→A0 소멸/A.next 제거로 B1,b 나중→B0 소멸. b 먼저→A1/B1,A 가 B 를유지; a 나중→A0 소멸→B0 소멸. 두순서모두 A/B 각 1 회삭제다.

오해와 반례

외부 shared 변수만지우면 모든 객체가 자동으로 없어진다.

A/B 내부 강한 순환만남아도 각개수 1 이다. 약한 선 설계와 독립 남은 소유자 검사가 필요하며 별도 순환은 따로 분석한다.
