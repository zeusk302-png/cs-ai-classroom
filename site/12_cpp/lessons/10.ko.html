기본 인수와 실행할 함수는 같은 기준으로 결정될까?

새 모형 B는 virtual int f(int x=2) const이며 본문은 x+1을 반환한다. D는 B를 public으로 상속하고 int f(int x=5) const override에서 10*x를 반환한다. 각 예제는 생성이 끝난 D d와 그 객체를 가리키는 B& r=d에서 독립적으로 시작한다. 여기서는 작은 정수만 사용하여 산술 범위를 넘지 않는다.

인수를 생략하면 먼저 호출 표현식의 정적 형식에 연결된 선언에서 기본 인수를 가져온다. 실제 가상 함수 본문은 동적 객체를 따라 선택한다. 두 결정을 분리하면 B 참조로 호출해도 D의 기본 인수 5를 가져오는 것은 아니라는 사실이 보인다. 생성·소멸 중의 호출은 또 다른 경계가 있어, 아직 완성되지 않았거나 이미 정리 중인 더 파생된 부분을 일반 호출처럼 사용하지 않는다.

먼저 확인할 개념
  • namespace와 오버로드의 후보 선택

    호출 표현식에서 보이는 선언을 확인하는 단계와 실행 본문 선택을 나눈다.

  • const correctness

    const가 붙은 함수 서명을 같게 유지한 상태에서 기본 인수만 비교한다.

보이는 타입과 실제 타입

정적 타입은 변수·포인터·참조의 선언으로 정해지는 타입이다. 동적 타입은 현재 가리키는 실제 객체의 타입이다. Circle 객체를 Shape 참조로 가리킬 수 있어 두 타입이 다를 수 있다.

기반 함수가 virtual이면 보통 기반 참조를 통한 호출에서 실제 객체의 최종 재정의 함수를 선택한다. 이것을 동적 디스패치라고 한다. 모든 같은 이름의 함수가 가상 호출이 되는 것은 아니다.

가상함수와 일반함수 비교

다음 코드에서 label은 virtual이고 code는 일반 함수다. Circle 객체에 연결된 Shape 참조로 label을 호출하면 Circle의 재정의를, code를 호출하면 참조의 정적 타입 Shape의 함수를 사용한다. 파생 클래스의 같은 이름이 자동으로 가상함수를 만드는 것은 아니다.

한정된 Shape::label 호출은 가상 선택을 억제해 기반 구현을 직접 지정할 수 있다. 생성·소멸 도중 가상 호출은 완성된 최종 객체 상태의 일반 호출과 조건이 다르므로 이 예제는 정상 생성 완료 후에만 호출한다.

struct Shape {
    virtual int label() const { return 1; }
    int code() const { return 10; }
    virtual ~Shape() = default;
};
struct Circle : Shape {
    int label() const override { return 2; }
    int code() const { return 20; }
};
Circle c;
Shape& r = c;
// 예상: r.label()는2, r.code()는10

값 복사와 참조의 차이

Shape s=c처럼 기반 객체로 값 복사하면 파생 부분은 저장되지 않는 slicing이 생긴다. s 자체의 동적 타입은 Shape이므로 label은1을 반환한다. 참조 r은 원래 Circle 객체와 연결되므로 예제의 가상 선택이 유지된다.

가상 호출을 구현하는 vtable 같은 방식은 흔하지만 언어가 특정 메모리 배치로만 구현하라고 요구하는 것은 아니다. 예제의 결론은 언어의 호출 의미로 추적하며 실제 주소나 성능 측정 결과를 주장하지 않는다.

기본 인수와 실행할 함수는 같은 기준으로 결정될까?
판단할 장면선택 또는 상태따로 확인할 조건

r.f()

B 선언의 인수 2 / D 본문 / 결과 20

기본 인수는 정적 형식 기준

d.f()

D 선언의 인수 5 / D 본문 / 결과 50

같은 객체라도 호출 선언이 다름

r.f(3)

명시 인수 3 / D 본문 / 결과 30

기본 인수 불필요

r.B::f()

인수 2 / B 본문 / 결과 3

명시 한정은 가상 선택을 억제

각 행에서 인수 칸을 먼저 고르고 그다음 함수 본문을 고른다. 20과 50의 차이를 서로 다른 객체 상태나 실제 실행 시간 차이로 설명하지 않는다.

중간 과정을 따라가는 예제

위 코드에서 r.label(),r.code(),c.code(),Shape s=c 뒤 s.label() 결과를 예상하라.

  1. r의 정적 타입은 Shape, 실제 객체는 Circle이므로 가상 label 호출의 결과는 2이다.

  2. r.code는 비가상이므로 10, c.code는 Circle에서 20이다.

  3. s는 기반 객체로 값 복사되므로 label 결과는 1이다.

예상값2,10,20,1이다. 실제 실행은 하지 않았다.

조건을 바꾸어 비교하기

같은 객체에서 두 기본 인수가 갈라지는 이유

위 r.f()와 d.f()의 값을 구하고 한 결정만으로 설명할 수 있는지 검사하라.

  1. r에서는 B 선언의 기본값 2를 쓰고 D 본문이 10*2를 계산한다.

  2. d에서는 D 선언의 기본값 5를 쓰고 D 본문이 10*5를 계산한다.

각각 20과 50이다. 동적 객체가 같아도 생략한 인수의 출처가 다르다.

비교할 점

base의 label()에는 인수가 없어 이 두 단계 차이가 드러나지 않았다.

생성·소멸 중 가상 호출의 경계

별도 B/D 모형에서 B::tag()는 1, D::tag()는 2를 반환한다. B 생성자 본문, D 생성자 본문, 완성 후 B 참조, D 소멸자 본문, B 소멸자 본문이 자기 객체의 tag()를 부른다. 순서를 추적하라. pure virtual은 없고 다른 파생 멤버를 읽지 않는다.

  1. B 생성자에서는 B의 tag를 호출하고 D 생성자에서는 D의 tag를 호출한다.

  2. 완성 후 참조는 D의 tag를 호출한다. 소멸자에서는 현재 실행 중인 소멸자의 클래스 기준을 적용한다.

순서대로 1, 2, 2, 2, 1이다. 실제 로그를 실행한 결과가 아닌 언어 규칙의 손추적이다.

비교할 점

완성된 객체를 통한 일반 호출과 생성·소멸 중 호출을 같은 장면으로 합치지 않는다.

소멸자 본문이 끝나면 객체 전체의 정리도 끝날까?

새 D는 public virtual 소멸자를 가진 B를 상속하고 M m이라는 값 멤버를 하나 가진다. D 소멸자 본문은 D, M 소멸자는 M, B 소멸자 본문은 B라는 사건 이름을 남긴다고 가정한다. 생성이 성공한 단일 D를 new로 만들고 B*로 보관한 뒤 일반 delete로 한 번 정리한다. 소멸자는 예외를 던지지 않으며 특수한 destroying delete나 배열 삭제는 쓰지 않는다.

가상 소멸자는 올바른 가장 파생된 소멸 과정으로 진입하게 한다. 그 뒤 D의 본문, D의 멤버, B 부분을 순서대로 정리한다. 본문 종료와 하위 객체 정리는 별도 사건이다. 기본 deleter를 사용하는 unique_ptr<B>도 결국 같은 삭제 조건을 필요로 한다. 소유권을 자동화하는 도구가 잘못된 기반 클래스 삭제 계약을 자동 고쳐 주지는 않는다.

먼저 확인할 개념
  • constructor와 destructor

    완성된 멤버를 선언 순서의 반대로 정리하는 수명 규칙을 연결한다.

  • unique_ptr

    자동 소유자의 기본 삭제에도 올바른 대상 형식 계약이 필요함을 확인한다.

객체 파괴와 메모리 반환

소멸자는 객체 수명이 끝날 때 자원을 정리하는 함수이다. delete는 동적으로 생성한 객체의 소멸과 저장 공간 반환을 연결한다. 자동 저장 객체를 임의로 delete하거나 new[]로 만든 배열을 단일 delete하는 것은 이 예제의 계약 밖이다.

파생 객체를 기반 포인터로 일반적인 단일 delete할 설계라면 기반 소멸자를 virtual로 둔다. 파생 소멸자에서 필요한 정리를 한 뒤 기반 소멸자로 이어진다. 기반에 다른 virtual 함수가 있어도 소멸자가 자동으로 virtual이 되는 것은 아니다.

정리 순서를 추적하기

기반 소멸자가 public virtual인 다음 예제에서 delete p는 Derived 소멸자 본체 뒤 Base 소멸자 본체를 호출한다. 실제 객체 전체를 파괴하기 위한 계약이다. 파생의 멤버·기반 부분 정리에도 순서가 있지만 이 짧은 예제에는 별도 멤버가 없다.

non-virtual 기반 소멸자로 파생 객체를 기반 포인터에서 일반 delete하면 정의되지 않은 동작이다. “항상 기반만 호출한다”라는 고정 출력으로 설명하면 언어의 보장을 잘못 전달한다.

struct Base {
    virtual ~Base() { /* 기반 정리 */ }
};
struct Derived : Base {
    ~Derived() override { /* 파생 정리 */ }
};
Base *p = new Derived;
delete p;
// 예상 순서: Derived 소멸자 본체 → Base 소멸자 본체

설계에 맞는 접근성

기반 포인터에서 파괴를 허용하지 않는 기반 타입은 protected non-virtual 소멸자 같은 다른 설계를 사용할 수 있다. 일반 클래스마다 무조건 virtual을 붙이는 규칙은 아니다. public virtual 또는 protected non-virtual은 Core Guidelines의 기반 설계 권고이다.

스마트 포인터도 삭제 계약을 이해해야 한다. unique_ptr<Base>의 기본 삭제는 기반 포인터 delete와 관련된다. 적절한 virtual 소멸자 없이 그것만 사용한다고 조건이 자동 해결되지는 않는다. 다른 커스텀 삭제 정책은 별도이다.

interface와 override

함수 이름이 같지만 const가 빠지면 같은 약속을 구현한 걸까?

준비 개념과 학습 목표

준비 개념

  • 클래스와 멤버함수

  • 포인터·참조와 객체 수명

학습 목표

  • 인터페이스와 실제 객체 타입을 구별한다.

  • 상속·합성 관계와 호출·파괴 조건을 추적한다.

컴파일러가 override를 인정하면 서비스 약속도 지켜질까?

I는 public virtual int read() const=0과 public virtual 소멸자를 가진 측정 인터페이스다. 문서상 read는 0부터 100까지의 정수를 반환하며 객체의 관찰 상태를 바꾸지 않는다고 약속한다. Good의 int read() const override는 7을 반환한다. 새 사례에서는 서명이 맞는지와 이 의미 계약이 맞는지를 별도로 검사한다.

인수나 const가 달라지면 같은 이름이어도 재정의가 아닐 수 있다. override는 그 실수를 번역 단계에서 드러낸다. 반면 정확한 서명으로 -1을 반환하는 Bad는 함수 재정의 검사를 통과할 수 있어도 문서의 범위 약속을 어긴다. final은 추가 재정의를 막는 언어 장치이며 의미 계약의 자동 증명 도구가 아니다.

먼저 확인할 개념
  • virtual과 dynamic dispatch

    기반 가상 함수와 같은 재정의 관계인지부터 확인한다.

  • const correctness

    read()와 read() const를 서로 다른 멤버 함수로 구별한다.

공통 약속과 구현

인터페이스는 호출자가 사용할 동작의 약속이다. C++에서는 순수 가상함수를 가진 추상 클래스로 인터페이스를 표현할 수 있다. =0은 함수 반환값 0을 뜻하는 것이 아니라 순수 가상 지정이다.

최종 재정의 함수가 순수 가상인 클래스는 추상이고 직접 객체를 생성할 수 없다. 포인터·참조로 접근하는 것은 가능하다. 구현 클래스가 필요한 약속을 완성하면 그 객체를 만들어 공통 인터페이스로 사용할 수 있다.

override로 의도를 검사

override는 이 함수가 기반의 가상함수를 재정의해야 한다는 컴파일 검사 요구이다. 이름·매개변수·const 등이 맞지 않으면 오류가 되어 오타나 다른 함수 선언을 일찍 발견할 수 있다. 반환형에는 공변 반환 같은 규칙이 있지만 이 단원은 동일 int 반환형만 쓴다.

기반에서는 virtual로 새 가상함수를 선언하고 파생에서는 override로 재정의 의도를 보인다. override를 빼도 올바른 재정의의 가상성은 유지되지만 실수 검사와 독자 이해에 불리할 수 있다.

struct Meter {
    virtual int read() const = 0;
    virtual ~Meter() = default;
};
struct FixedMeter : Meter {
    int read() const override { return 7; }
};
FixedMeter m;
Meter& r = m;
// 예상: r.read() == 7

기능을 재사용하고 싶다는 이유만으로 상속해도 될까?

새 Counter 인터페이스는 상태 value가 0..10이고 add(n)의 허용 입력은 정수 0..10이라고 정한다. n<=10-value이면 true와 value+n, 아니면 false와 원래 상태 보존을 약속한다. 구현은 가상 add로 바꿀 수 있지만 이 공개 약속을 믿는 호출자에게 결과의 의미도 유지해야 한다.

EvenCounter는 코드를 재사용하려고 상속하지만 홀수 n은 무조건 false로 거절한다. 컴파일러는 정확한 override 서명을 인정해도 value=2에서 n=3이라는 기반의 유효 요청을 처리하지 못한다. 짝수 전용 기능이 목적이면 그 도움 객체를 값 멤버로 넣은 EvenTool이 자기 addEven 계약만 제공하도록 합성할 수 있다. 새로운 API를 기반 Counter의 완전한 대체라고 주장할 필요가 없다.

  • private와 public API

  • interface와 override

    재정의 서명의 성공과 공개 의미 약속의 성공을 따로 확인한다.

관계의 의미부터 고르기

public 상속은 파생 객체를 기반 인터페이스에서 사용하는 관계에 적합하다. Circle이 Shape의 한 종류라는 개념과 자동차가 Engine을 포함한다는 개념은 다르다. 코드를 복사하지 않으려는 목적만으로 공개 상속을 선택하면 의미가 틀어질 수 있다.

합성은 멤버 객체로 다른 기능을 포함하고 필요한 호출을 위임한다. Car 안에 Engine을 두면 Car를 Engine으로 사용할 수 있다고 주장하지 않고 엔진 기능을 이용한다. 단순히 메서드가 비슷하다는 이유만으로 같은 타입 관계가 되지는 않는다.

멤버에 위임하는 작은 예

다음 예제에서 Car::start는 멤버 engine의 start를 호출한다. Car는 Engine에서 파생되지 않았고 엔진을 보유한다. 외부에는 자동차의 의미 있는 동작만 제공한다.

엔진 교체 방법은 소유·참조·인터페이스 설계에 따라 달라진다. 이 예제는 값 멤버 고정 구현이며 실행 중 임의 Engine 교체 기능을 제공하지 않는다. 합성이라고 자동으로 모든 결합 문제가 사라지는 것도 아니다.

struct Engine {
    int start() { return 1; }
};
struct Car {
    Engine engine;
    int start() { return engine.start(); }
};
Car car;
// 예상: car.start() == 1

상속 관계를 쓸 때는 기반 사용자가 기대하는 동작을 파생 객체도 지킬 수 있는지 확인한다. 상속했지만 기반 동작 대부분을 금지하거나 의미 없이 예외로 처리해야 하면 인터페이스 관계가 잘못되었을 수 있다.

합성은 기능 보유 관계를 표현하고 인터페이스 상속은 공통 약속을 표현할 수 있어 두 방식을 함께 쓸 수 있다. 예컨대 Renderer 인터페이스를 구현하는 객체가 내부에 Cache 멤버를 보유할 수 있다. 어느 방식이 항상 우월하다고 하지 않고 관계·수명·변경 방향을 평가한다.

  2. false 경로는 원래 value=9를 보존해야 하는데 실제 정책은 10으로 바꾼다.

결과 bool이 같아도 상태 보존 계약이 깨진다.

호출·정리·대체 가능성을 한 설계에서 구별하기

각 부분은 독립적인 새 객체에서 시작한다. (A) B의 f 기본 인수는 2이고 본문은 x+1, D의 f 기본 인수는 5이고 override 본문은 10*x다. 완성된 D를 B& r로 보고 r.f(), d.f(), r.B::f(4)를 계산하라. (B) public virtual 소멸자를 가진 B를 상속한 D는 M first; M second;를 선언 순서대로 가진다. 성공한 단일 D를 B*로 일반 delete할 때 D/first/second/B 사건 순서를 적고, public nonvirtual B로 바꾼 같은 삭제의 정상 로그를 예측할 수 있는지 판단하라. (C) 위 Counter 계약의 value=2에서 EvenCounter의 add(3), value=9에서 Saturating의 add(2)를 대조하고 짝수 전용 기능의 합성 API를 제안하라. 모든 소멸자는 예외를 던지지 않으며 특수 삭제·배열 삭제·실제 실행은 하지 않는다.

힌트 1

A는 생략 인수와 가상 본문을 두 칸으로 나누고 B는 본문 다음 멤버의 역순을 적용한다.

힌트 2

C는 반환값뿐 아니라 기반이 허용한 요청과 실패 전후 상태를 함께 검사한다.

풀이와 답 확인

  1. A의 r.f()는 인수 2와 D 본문으로 20, d.f()는 인수 5와 D 본문으로 50이다. r.B::f(4)는 한정 B 본문으로 5다.

  2. B의 정리는 D 본문, second, first, B 본문 순서다. nonvirtual B를 통한 해당 일반 삭제는 정의되지 않은 동작이므로 정상 B-only 로그를 예측하지 않는다.

  3. C에서 기반 Counter는 value=2의 add(3)을 true/value=5로 처리해야 한다. EvenCounter의 false/value=2는 허용 요청을 새로 거절한다.

  4. value=9의 add(2)는 기반에서 false/value=9다. Saturating의 false/value=10은 실패 보존을 깨뜨린다.

  5. 짝수 전용 EvenTool은 도움 객체를 멤버로 두고 addEven의 입력·실패 계약만 공개한다. 이를 Counter의 완전한 대체라고 주장하지 않는다.

A는 20/50/5, B는 D→second→first→B이며 nonvirtual 오류에는 정상 로그가 없다. C의 두 파생 정책은 서로 다른 방식으로 기반 계약을 어기므로 별도 합성 API 또는 기반 약속을 충족하는 구현이 필요하다.
