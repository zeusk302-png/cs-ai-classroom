소단원 13.1

throw·catch·stack unwinding

함수 안에서 실패했을 때 여러 호출자를 한꺼번에 빠져나오면서 자원도 정리할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 함수 호출과 지역 변수

  • 객체의 생성과 소멸

  • RAII와 소유권

학습 목표

  • throw 뒤의 실행 경로를 추적한다.

  • 일치하는 catch와 재던지기의 역할을 설명한다.

  • 완전히 생성된 객체의 소멸 순서를 판정한다.

정상 경로에서 오류 경로로 이동하기

throw는 예외를 발생시키며 다음 정상 명령으로 이어가지 않는다. 호출 경로에서 해당 예외를 처리할 catch를 찾는다. try는 오류가 전파될 수 있는 작업을 감싸고 catch는 받아들일 예외 타입을 선언한다. 실패를 처리한 뒤에는 try의 중단된 명령으로 되돌아가지 않는다.

여기서는 <stdexcept>의 std::runtime_error를 던지고 const std::exception&로 받는 C++17 흐름을 다룬다. 일반적으로 구체적인 파생 예외 처리를 앞에, 더 넓은 기본 타입 처리를 뒤에 둔다. 예외를 잡았다는 사실만으로 실패한 작업을 성공으로 표시해서는 안 된다.

생성 완료의 역순으로 정리하기

처리할 catch로 제어가 이동하는 동안 범위를 벗어나는, 생성이 완료된 자동 객체는 stack unwinding으로 소멸한다. 같은 범위에서 A 다음 B가 완전히 생성되었다면 B 다음 A 순서다. 스마트 포인터 같은 RAII 객체의 소멸자가 소유 자원을 정리하도록 설계하는 이유가 여기 있다.

여기서 생성자 실패는 다른 생성자에 위임하지 않는 생성자를 기준으로 설명한다. 생성이 완료되기 전에 예외로 끝나면 그 완전 객체 자신의 소멸자는 호출되지 않고, 이미 생성된 멤버와 기반 클래스 등의 하위 객체는 정리된다. 위임 대상 생성자가 완료된 뒤 위임 생성자의 본문이 예외로 끝나는 경우에는 완전 객체의 소멸자가 호출되는 별도 규칙이 있다. 원시 포인터 변수 자체의 소멸은 그 포인터가 가리키는 동적 자원 삭제와 다르므로 소유권을 RAII 객체에 맡긴다.

처리할 책임이 있는 곳에서 받기

catch에서 원인을 기록하고 다른 호출자에게 계속 알릴 필요가 있다면 throw;로 현재 처리 중인 예외를 다시 던진다. 아무 예외도 처리하지 않는 곳에서 throw;를 실행하는 것은 유효한 재던지기가 아니다. 모든 예외를 빈 catch로 삼키면 실패 정보가 사라질 수 있다.

처리할 catch가 전혀 없으면 std::terminate가 호출된다. 이 경우 terminate 전까지 전체 스택이 반드시 정리된다고 약속할 수 없다. 이 단원의 소멸 순서 예제는 일치하는 catch가 존재하고 소멸자가 예외를 밖으로 보내지 않는 상황으로 한정한다.

중간 과정을 따라가는 예제

outer의 try에서 A가 생성되고 inner에서 B가 생성된 뒤 runtime_error가 발생한다. 일치하는 outer의 catch가 있으며 A와 B의 생성·소멸은 실패하지 않는다고 가정한다.

  1. A 생성이 완료된다.

  2. inner에서 B 생성이 완료된다.

  3. throw 뒤 inner의 정상 경로는 중단된다.

  4. B가 소멸하고 inner를 벗어난다.

  5. A가 소멸한 뒤 outer의 catch 본문이 실행된다.

생성 순서 A→B, 정리 순서 B→A→catch다. 이는 실제 로그를 얻은 결과가 아니라 자체 호출 흐름을 추적한 것이다.

종이와 본문으로 직접 해보기

B의 비위임 생성자가 완료되기 전에 예외를 던진다면 B 자신의 소멸자와 A의 소멸자는 어떻게 되는가?

힌트 보기

완전히 생성된 객체인지 먼저 구분한다.

풀이 보기

B 자신의 소멸자는 호출되지 않는다. B 안에서 이미 생성된 하위 객체는 정리되며, A는 생성 완료 상태이므로 catch로 이동하면서 소멸한다.

오해와 반례

예외가 발생하면 new로 얻은 자원은 모두 자동 삭제된다.

범위를 벗어나는 자동 객체의 소멸과 모든 동적 자원의 삭제는 다르다. 원시 포인터의 값만 사라져도 동적 자원이 남을 수 있다. unique_ptr처럼 소유권과 해제를 묶는 RAII 설계가 필요하다.

답과 이유 보기

실행되지 않는다.

일치하는 처리기를 찾는 오류 경로로 이동한다.

catch 안에서 동일 예외를 다시 전달하는 기본 문법은?

답과 이유 보기

throw;다.

현재 처리 중인 예외를 재던지는 문법이다.

처리기가 없는 경우에도 모든 지역 객체 정리가 보장되는가?

답과 이유 보기

보장되지 않는다.

terminate 호출 전에 스택을 정리하는지는 그 상황에서 구현에 따른다.

한 단계 더

A, B, C가 차례로 생성된 뒤 일치하는 catch로 이동하는 경우를 추가하고 C→B→A의 정리 순서를 그려 보자. 소멸자가 예외를 던지는 경우는 다음 소단원의 terminate 조건과 연결하라.

소단원 13.2

noexcept

예외를 보내지 않겠다는 선언을 붙이면 실제로 실패가 사라질까?

준비 개념과 학습 목표

준비 개념

  • throw와 catch

  • 함수 선언

  • stack unwinding

학습 목표

  • noexcept의 경계 의미를 설명한다.

  • 내부 처리와 외부 전파를 구분한다.

  • 선언·연산자·복구 성공의 차이를 구분한다.

밖으로 예외가 나가지 않는 경계

함수 뒤의 noexcept는 noexcept(true)와 같은 비던짐 예외 명세다. 예외가 그 함수 밖으로 전파하려 하면 std::terminate가 호출된다. noexcept(false)는 잠재적으로 던질 수 있다는 명세다. 함수 몸체를 모든 실패로부터 보호하는 마법이 아니다.

noexcept 함수 안에서 throw가 일어났더라도 함수 내부의 catch가 처리해 경계를 넘지 않는다면 그 이유만으로 terminate가 호출되는 것은 아니다. 반대로 함수 밖의 호출자 catch로 처리하려는 예외는 먼저 비던짐 경계에 걸리므로 호출자 catch가 일반 예외처럼 받아 복구할 수 없다.

정리 함수의 약속

소멸자에서 밖으로 예외를 보내지 않는 규칙은 자원 정리에 특히 중요하다. 이미 다른 예외 때문에 stack unwinding 중인데 소멸자가 또 예외를 던져 밖으로 끝나면 terminate 조건이 된다. 실패할 수 있는 작업은 별도의 명시적 함수에서 보고하고, 소멸 경로는 안전한 정리를 맡기는 설계를 생각한다.

어떤 함수가 noexcept라고 해서 파일을 잘 저장했거나 입력이 유효하다는 의미는 아니다. 함수는 오류 코드를 반환할 수도 있고 내부에서 실패를 처리할 수도 있다. 프로그램 종료나 비정상 입력에 대한 다른 위험도 이 명세만으로 사라지지 않는다.

선언과 검사 연산자를 구분하기

bool 상수식을 넣은 noexcept(condition)은 조건에 따라 함수 명세를 정하는 선언 문법이다. 별도로 noexcept(expression)이라는 연산자는 식이 잠재적으로 예외를 던지는지 정적으로 판정하며 그 식을 실행하지 않는다.

예를 들어 void safe() noexcept;와 void risky();를 선언했다면 noexcept(safe())는 true, noexcept(risky())는 false다. risky가 실제 구현에서 아무 예외도 던지지 않더라도 명세상 잠재적 던짐이므로 판정은 false일 수 있다. 실제 호출 횟수나 수행 시간 측정과 구별한다.

중간 과정을 따라가는 예제

f는 noexcept로 선언된다. 경로 P에서는 내부 throw를 내부 catch가 처리하고 반환한다. 경로 Q에서는 예외가 f 밖으로 나가려 한다. f 호출자는 바깥 try/catch를 갖는다.

  1. P는 내부에서 처리되어 예외가 f 경계를 넘지 않는다.

  2. 따라서 P는 다른 실패가 없다는 가정 아래 정상 반환할 수 있다.

  3. Q는 비던짐 경계를 벗어나려 하므로 terminate가 호출된다.

  4. 바깥 catch로 일반 전파되는 결과를 예상해서는 안 된다.

P는 반환 가능, Q는 terminate다. Q에서 호출자 catch가 복구하는 흐름은 이 명세와 맞지 않는다.

종이와 본문으로 직접 해보기

safe와 risky 선언에 대해 noexcept(safe()), noexcept(risky())를 적고 각 함수가 이 검사만으로 호출되는지도 판정하라.

힌트 보기

실제 실행과 잠재적 던짐 판정을 나눈다.

풀이 보기

각각 true, false다. 두 검사식은 함수를 실행하지 않으므로 호출 횟수는 0이다. 선언과 식의 명세를 판정한 것이다.

오해와 반례

noexcept면 함수 내부에 throw 문이 들어갈 수 없다.

핵심은 예외가 함수 경계를 벗어나는지다. 내부에서 발생한 예외를 내부 catch가 처리할 수 있다. 밖으로 전파하면 terminate이며 noexcept가 실패를 자동 복구하는 것은 아니다.

자기점검

비던짐 명세를 뜻한다.

잠재적으로 던지는 함수가 실제로 한 번도 안 던졌으면 noexcept 연산자가 true인가?

답과 이유 보기

그 관찰만으로 true가 아니다.

연산자는 관찰한 실행 횟수가 아니라 식의 잠재적 던짐을 판정한다.

unwinding 중 소멸자가 예외를 밖으로 던지면?

답과 이유 보기

terminate 조건이 된다.

진행 중인 예외 정리에서 새 예외가 정리 함수 밖으로 나가는 상황이다.

한 단계 더

템플릿 함수가 내부 작업의 명세를 noexcept(noexcept(work()))로 반영하는 형태를 조사하라. 첫 noexcept는 선언이고 안쪽은 연산자라는 역할을 표시해 보자. 실제 템플릿 컴파일은 미수행이다.

소단원 13.3

예외 안전성의 수준

실패했다는 말 뒤에도 데이터가 그대로인지, 일부 바뀌었는지 약속할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 불변조건

  • RAII

  • 예외의 전파

학습 목표

  • 기본·강한·비던짐 보장의 차이를 설명한다.

  • 실패 지점을 기준으로 상태를 추적한다.

  • 준비 후 반영 방식의 조건과 비용을 비교한다.

실패 후에 남는 상태의 계약

기본 보장은 예외가 발생해도 자원이 새지 않고 객체의 불변조건이 유지되는 수준이다. 내용이 일부 바뀔 수 있다. 강한 보장은 예외로 실패하면 관찰 가능한 상태가 작업 전과 같다는 수준이다. 성공하거나 효과 없이 실패하는 거래처럼 설명할 수 있다.

비던짐 보장은 예외를 밖으로 전파하지 않는다는 별도의 약속이다. noexcept라고 적기만 해서 실제 성공이나 올바른 복구가 증명되는 것은 아니다. 예외 안전성은 함수가 호출하는 작업, 객체의 소유권, 정리 경로까지 함께 검토해야 한다.

변경을 미루고 마지막에 반영하기

원본을 바로 바꾸기보다 임시 상태에 준비한 후, 모든 준비가 성공하면 실패하지 않는 반영 단계로 교체하는 설계를 생각할 수 있다. 준비 중 예외가 발생하면 임시 RAII 자원을 정리하고 원본을 유지한다. 복사 비용과 추가 메모리가 필요할 수 있다.

이 방식도 모든 swap이나 대입이 언제나 실패하지 않는다고 가정하면 안 된다. 반영 단계의 보장을 확인해야 한다. 준비 중 원본 밖의 로그나 외부 서비스에 되돌릴 수 없는 영향을 주었다면 원본 객체 유지만으로 작업 전체의 강한 보장을 말할 수도 없다.

작은 상태표로 보장 점검하기

자체 모형의 상태는 음수가 아닌 두 카운터 x와 y이고 초기값은 (4,6)이다. 목표는 각각 1 증가시키는 것이다. 직접 x를 5로 바꾼 뒤 y 준비에서 실패하여 (5,6)이 남으면 불변조건은 유지되지만 작업 전 상태는 아니다.

임시 상태 (5,7)를 만들다가 y 준비에서 실패할 경우 원본은 (4,6)에 둔다. 준비가 모두 성공하고 마지막 교체가 실패하지 않는다는 조건에서만 성공 상태를 (5,7)로 반영한다. 이 상태표는 실제 vector나 다른 컨테이너의 특정 API 보장을 대신하지 않는다.

중간 과정을 따라가는 예제

설명에 정한 (x,y)=(4,6) 작업에서 y 준비가 예외로 실패한다. 직접 변경 방식과 임시 준비 방식의 최종 원본을 비교하라. 자원 정리는 성공하며 각 상태가 음수가 아닌 불변조건을 만족한다고 가정한다.

  1. 직접 방식은 x를 5로 바꾼 후 y 준비에서 실패한다.

  2. 원본은 (5,6)이며 유효하지만 작업 전과 달라 기본 보장에 맞고 강한 보장은 아니다.

  3. 임시 방식에서는 원본 (4,6)을 유지한 채 준비한다.

  4. 준비 실패로 임시 상태를 정리하여 원본은 (4,6) 그대로다.

직접 방식의 예제는 기본 보장만 충족한다. 임시 준비 방식은 실패 시 원본 유지 조건을 충족한다. 전체 함수의 강한 보장은 모든 실패와 외부 영향까지 검사해야 한다.

종이와 본문으로 직접 해보기

두 준비 단계가 성공하고 마지막 교체도 비던짐이면 임시 방식의 상태는 무엇인가? 마지막 교체가 일부 변경 뒤 던질 수 있다면 강한 보장을 단정할 수 있는가?

힌트 보기

실패할 수 있는 마지막 단계도 상태표에 넣는다.

풀이 보기

모든 단계 성공이면 (5,7)이다. 교체가 일부 변경 후 실패할 수 있다면 원본 유지가 깨질 수 있어 강한 보장을 단정하지 못한다. 반영 단계의 계약을 확인해야 한다.

오해와 반례

catch에서 메시지를 출력하면 강한 예외 보장이 생긴다.

메시지와 상태 복원은 다른 문제다. 이미 (5,6)이 남았다면 출력해도 (4,6)으로 돌아오지 않는다. 보장은 실제 변경·복원·자원 정리 경로에서 성립해야 한다.

임시 복사를 쓰면 모든 함수가 자동으로 강한 보장인가?

답과 이유 보기

예외가 나도 음수 없는 (5,6)이 남는 이 모형은 작업 전 상태인가?

답과 이유 보기

초기 상태 (4,6)과 첫 필드가 달라졌다.

한 단계 더

상태표에 자원 개수 열을 추가해 성공·실패 모두 소유 자원 누수가 없는지 확인하라. 실제 메모리 누수 검사와 실패 주입은 수행하지 않았으며, 개별 표준 컨테이너 연산의 보장은 해당 API에서 따로 읽어야 한다.

소단원 13.4

optional·variant와 결과 타입

값이 없다는 것과 값을 얻는 과정이 실패했다는 것은 같은 뜻일까?

준비 개념과 학습 목표

준비 개념

  • 템플릿과 타입

  • 조건문

  • 예외와 실패 계약

학습 목표

  • optional의 값 없음과 0을 구분한다.

  • variant의 대안과 접근 검사를 설명한다.

  • 예외·결과 타입을 목적에 따라 선택한다.

optional은 값이 있거나 없는 상태

C++17의 std::optional<int>는 int 값이 있거나 값이 없는 상태를 표현한다. 0은 유효한 int 값이므로 빈 optional과 다르다. has_value()나 bool 검사로 값 존재를 먼저 확인하고, 존재할 때 *result로 값을 읽는다.

빈 optional에서 value()를 호출하면 bad_optional_access가 발생한다. *result는 값 존재를 확인한 뒤 사용해야 하며 빈 상태의 역참조를 안전한 빈 값 반환처럼 기대하지 않는다. value_or(기본값)는 빈 경우 기본값을 선택하지만 값 없음의 의미를 사용자가 놓칠 수 있다.

variant로 서로 다른 결과를 구분하기

std::variant<int, ParseError>처럼 성공 값과 오류 정보를 다른 타입의 대안으로 표현할 수 있다. 같은 시점에 보유한 대안은 하나다. 타입으로 접근하는 get_if는 원하는 대안이면 포인터를, 아니면 nullptr을 반환하므로 조건문으로 안전하게 나눌 수 있다.

get은 다른 대안을 요구하면 bad_variant_access를 던질 수 있다. variant의 대안 변경 중 예외가 발생하면 valueless_by_exception 상태가 가능하므로 일반 variant가 어떤 경우에도 반드시 대안 값을 갖는다고 확대하지 않는다. 여기의 작은 분류 모형은 값 대입과 오류 객체 생성이 성공한 것으로 한정한다.

실패 표현의 의미를 계약에 적기

optional은 주로 값 없음 자체가 충분한 정보인 검색 등에 맞는다. 성공 값과 여러 오류 원인을 전달하려면 자체 결과 타입이나 variant 등으로 원인 정보를 보낼 수 있다. 함수의 예외 정책과 반환 타입의 오류 정책을 동시에 문서화해야 한다.

자체 분류기는 오직 문자열 "0"과 "7"을 정수로 인정하고, 빈 문자열은 Empty, 그 밖의 입력은 Invalid라는 오류 대안으로 정한다. 일반 숫자 파서가 아니며 메모리 할당 실패까지 없다는 약속도 아니다. 결과 타입을 쓰더라도 내부 작업이 예외를 던질 수 있다.

중간 과정을 따라가는 예제

자체 분류 계약에 입력 "0", "7", "", "x"를 적용한다. 검색 결과 optional<int>도 값 0과 nullopt를 비교하라.

  1. "0"은 성공 대안 int 0, "7"은 int 7이다.

  2. ""는 ParseError의 Empty, "x"는 Invalid다.

  3. get_if<int>는 두 성공 결과에서만 비널 포인터다.

  4. 값 0을 가진 optional의 has_value는 true이고 nullopt는 false다.

0은 빈 상태가 아닌 성공 값이다. 오류 대안은 0으로 위장하지 않고 Empty/Invalid라는 별도 정보를 전달한다.

종이와 본문으로 직접 해보기

힌트 보기

일반 파서의 관습을 자체 계약에 덧붙이지 않는다.

풀이 보기

"07"과 "-1"은 둘 다 Invalid다. value_or(0)는 값 없음과 실제 값 0을 같은 숫자 0으로 보여 주므로 원래의 존재 여부를 구별하지 못한다.

오해와 반례

optional을 쓰면 어떤 경우에도 예외가 발생하지 않는다.

빈 optional의 value()는 예외를 던지고 내부 T의 생성·복사 등도 예외를 던질 수 있다. 값 없음의 표현과 함수 전체의 비던짐 보장은 다르다.

true다.

존재 여부와 숫자의 참/거짓 값은 다르다.

variant가 오류 대안을 갖는데 get<int>를 요청하면?

답과 이유 보기

bad_variant_access를 던질 수 있다.

요청 대안과 실제 보유 대안이 다르다.

get_if<int>에서 nullptr을 받으면 그 포인터를 역참조해도 되는가?

답과 이유 보기

안 된다.

int 대안을 얻지 못했으므로 다른 대안을 처리해야 한다.

한 단계 더

검색에서 값 없음이 정상인 상황과 파싱 실패 이유를 보여 줘야 하는 상황의 API를 각각 설계하라. expected는 C++23의 별도 기능이므로 C++17 코드에 바로 넣을 수 있다고 가정하지 않는다. 실제 파서나 결과 타입 코드는 실행하지 않았다.
