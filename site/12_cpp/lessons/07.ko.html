소단원 7.1

copy constructor·assignment

코드에 = 기호가 있다고 모두 같은 대입 연산일까?

준비 개념과 학습 목표

준비 개념

  • 객체 초기화는 새 객체를 만드는 과정이고 대입은 이미 살아 있는 객체의 값을 바꾸는 과정이다.

  • copy constructor는 같은 타입 객체로 새 객체를 초기화한다. copy assignment는 보통 T& operator=(const T&) 형태로 정의한다.

학습 목표

  • 선언 초기화와 대입을 구별한다.

  • 기본 멤버별 복사를 종이로 추적한다.

  • 참조 별칭과 새 객체를 구분한다.

기본 복사는 내부 참조의 화살표도 다시 연결할까?

새 구조체 Link는 int& target; int tag;를 이 순서로 가진다. 살아 있는 x=4에 Link a{x,1};을 만든 뒤 Link b=a;로 새 객체를 초기화한다. 기본 복사 생성은 참조 멤버를 원본과 같은 x에 연결하고 tag 값 1을 복사한다. b는 별개 Link지만 참조 대상까지 별개 int를 만드는 것은 아니다.

이후 b.tag=9는 a.tag를 바꾸지 않지만 b.target=7은 같은 x를 수정해 a.target에서도 7을 읽게 한다. 반면 b=a라는 기존 객체 대입에는 기본 대입의 삭제 조건이 걸린다. 참조 멤버를 가진 Link의 암시적 copy assignment는 삭제되므로 이를 참조 재연결이나 x 값 복사라고 실행 추측하지 않는다. 생성과 대입은 가능한 연산 자체가 다를 수 있다.

먼저 확인할 개념
  • 참조와 읽기 경로

    참조 멤버의 화살표와 새 값을 구별한다.

  • 멤버 초기화와 대입

    생성 때 연결 가능한 참조가 기존 객체 대입과 다른 조건을 가진다.

새 객체인지 먼저 표시하기

단순 구조체 Point{int x;int y;}에서 Point b=a는 b 선언과 초기화다. 이름에 대입 기호가 보여도 이미 있는 b에 값을 넣는 문장이 아니다. 뒤에 b=a만 쓰면 기존 b에 copy assignment를 한다. 이 단원은 lvalue a와 단순 값 멤버만 사용한다.

작업 초안의 기본 복사는 멤버별로 적용된다. x와 y는 int 값으로 복사되어 새 Point를 만든 뒤 b.x를 바꿔도 a.x는 바뀌지 않는다. 이 사실을 포인터가 가리키는 대상이나 모든 사용자 정의 클래스에 그대로 확장하지 않는다.

대입은 기존 값의 처리가 필요하기

a=(2,5), b=(9,9)가 이미 있으면 b=a 뒤 b=(2,5)다. b 자체가 a라는 이름으로 바뀌는 것이 아니다. b가 자원을 소유한다면 기존 자원 처리와 새 값 복사의 정책도 중요하지만 int 예제는 그런 자원이 없다.

대입 연산자는 흔히 *this를 참조로 반환하여 c=b=a를 연결한다. 연결 대입은 오른쪽부터 b=a, 다음 c=b의 값 갱신으로 이해하자. 사용자 정의 operator=는 자신이 정한 계약을 따라야 하며 문법만으로 의미가 안전해지지는 않는다.

참조는 별개의 복사 객체가 아니기

Point& r=a는 참조를 a에 연결한다. r.x를 바꾸면 같은 a.x를 바꾼다. b 복사와 r 별칭의 두 화살표를 구분하면 어느 값이 영향을 받는지 예측하기 쉽다. 수명 밖의 참조를 사용하는 사례는 이 단순 모형에서 제외한다.

반환값·임시 객체·이동·복사 생략 등은 다른 조건을 가진다. 아래는 그런 사건을 세지 않는 직접 lvalue 초기화/대입 추적이다. 실제 컴파일러 출력이나 특별멤버 호출 로그를 실행해 관찰하지 않았다.

유효한 실행 결과 없음

새 객체의 정체성과 각 멤버의 의미를 두 층으로 읽는다. 이 Link에는 사용자 정의 대입을 제공하지 않았으며 선언이 거절되는 사례에 고정 출력값을 쓰지 않는다.

중간 과정을 따라가는 예제

Point a{2,5}; Point b=a; Point c{0,0}; c=b; b.x=9; Point& r=a; r.y=7; 뒤 a,b,c 값을 구하라.

  1. b 선언은 copy initialization이라 처음 b=(2,5)다.

  2. c=b는 기존 c 대입으로 c=(2,5)가 된다.

  3. b.x=9는 b만 바꾸므로 b=(9,5)다.

  4. r은 a의 별칭이라 r.y=7 뒤 a=(2,7), c=(2,5)는 그대로다.

a=(2,7), b=(9,5), c=(2,5)다.

조건을 바꾸어 비교하기

const 값 멤버의 다른 경계

struct Ticket { const int id; int score; }; Ticket a{2,5}; Ticket b=a; 뒤 b.score=8을 수행한다.

  1. 복사 생성으로 id=2,score=5를 초기화할 수 있다.

  2. b의 score 변경은 a의 score를 바꾸지 않는다.

a는 id 2/score 5, b는 id 2/score 8이다. 기본 b=a 대입은 const int 멤버 때문에 삭제된다.

비교할 점

복사 생성 가능성과 기본 대입 가능성을 분리한다.

참조 별칭은 새 Link가 아니다

Link a{x,1}; Link& r=a; Link b=a;에서 r.tag=3을 수행한다.

  1. r은 a 자체의 별칭이고 b는 별개 객체다.

  2. r.tag 수정은 a.tag만 바꾼다.

a.tag는 3, b.tag는 1이다. 양쪽 target은 여전히 같은 x다.

비교할 점

객체 참조와 객체 안의 참조 멤버를 별도 화살표로 그린다.

종이와 본문으로 직접 해보기

초기 a(1,4),b(8,8),c(0,0)에서 c=b=a; b.y=6; 을 추적하고 초기화 사건이 있는지 적어라.

힌트 보기

풀이 보기

Point b=a의 =는 항상 copy assignment다.

b가 선언되는 문장은 초기화이며 이미 있는 b=a 문장과 다르다. 참조 r=a는 또 다른 별칭 연결이다. 객체의 생성 시점과 타입을 먼저 확인한다.

소단원 7.2

얕은·깊은 복사

포인터 주소를 복사하면 주소에 있는 배열도 두 개로 늘어날까?

준비 개념과 학습 목표

준비 개념

  • 포인터 값은 대상 위치를 표현하며 포인터 변수 자체와 가리키는 대상은 별개다.

  • 얕은 복사는 주소 값 등 표현을 복사한다. 깊은 복사는 여기서 소유 배열 내용을 새 공간에 독립적으로 복사하는 정책을 뜻한다.

학습 목표

  • 주소와 배열 값을 구별한다.

  • 별칭에 따른 변경을 추적한다.

  • 소유권과 자원 해제 책임을 연결한다.

안쪽 값과 바깥 관찰 포인터를 함께 복사하면 누구를 관찰할까?

새 Record는 vector<int> values; const int* view;를 가진다. a.values는 {2,4}이고 a.view는 그 첫 원소를 가리킨다. a와 저장소는 계속 살아 있으며 원소 수 변경·재할당은 없다고 고정한다. 기본 복사로 b=a를 생성하면 b.values는 독립 int 원소를 가지지만 b.view는 여전히 a의 첫 원소를 가리킨다.

b.values[0]=9 뒤 b.view에서 읽는 값은 2다. 이제 a.values[0]=7로 바꾸면 양쪽 view가 7을 관찰하고 b.values[0]은 9다. 클래스 안의 포인터가 항상 자기 소유 원소를 가리켜야 한다는 불변조건은 기본 멤버 복사가 자동 유지하지 못한다. 인덱스를 저장해 자기 vector에서 관찰하거나 복사 정책에서 새 저장소에 다시 연결하는 설계를 비교한다.

먼저 확인할 개념
  • vector의 값과 저장소

    원소 값 복사와 원본 저장소의 재할당 수명을 구별한다.

  • 바깥 복사와 안쪽 관계

    언어 규칙을 동일시하지 않고 중첩 관계 그림을 복사 정책에 적용한다.

얕은 복사에 공유가 남기

가상 a.p가 공간S의 배열[3,6]을 가리킬 때 b.p=a.p이면 b도 S를 가리킨다. b.p[0]=8은 S를 바꾸므로 a에서 읽는 값도8이다. 포인터 값 두 개와 실제 배열 하나라는 그림을 그리자. 실제 주소 숫자를 같은 프로그램 밖에서도 유효한 값으로 다루지 않는다.

기본 멤버별 복사는 raw pointer 값도 복사하지만 그 대상 배열을 자동 복제하지 않는다. 얕은 복사 자체가 항상 틀린 것은 아니다. 비소유 관찰 포인터나 명시적 공유 의미에 맞을 수 있지만 대상 수명·수정 권한 조건은 별도다.

독립 값이 필요하면 소유 정책 정하기

독립 배열 값이 계약이면 b를 만들 때 새 공간T를 확보하고[3,6]을 옮겨 적는다. 이후 b의 첫 값8은 T만 바꾸므로 S는[3,6]다. 여기서는 배열 원소가 int여서 내용 복사가 단순하며 중첩 포인터를 가진 구조의 모든 그래프 복제를 자동 해결하지 않는다.

std::vector<int> 같은 자원 관리 멤버로 값을 표현하면 기본 멤버 복사를 통해 독립 원소 값이 생긴다. 반면 vector<int*>는 포인터 원소를 복사하므로 대상까지 깊게 복사한다는 뜻이 아니다. 타입과 복사 계약을 함께 읽는다.

소멸 때 누가 해제하는지 추적하기

a와 b 모두S를 독점 소유한다고 착각하여 각 소멸자가 같은 배열을 delete[]하면 두 번 해제하는 잘못된 설계가 된다. 첫 해제 뒤의 포인터는 유효한 배열 접근을 보장하지 않고 두 번째 해제의 결과는 정의된 정상 숫자 출력이 아니다. 위험 사례는 실제 실행하지 않는다.

독점 소유라면 복사를 제한하거나 새 소유 공간을 만들 수 있다. 명시적 공유는 별도의 수명 관리가 필요하다. 단순히 주소가 다르다는 조건만으로 복사 실패·기존 자원 누수·공유 그래프까지 검증 완료라고 할 수 없다.

소단원 7.3

rule of zero·five

특별멤버 다섯 개를 모두 손으로 쓰는 것이 언제나 좋은 설계일까?

준비 개념과 학습 목표

준비 개념

  • 특별멤버 중 복사생성·복사대입·이동생성·이동대입·소멸을 다섯 개로 묶어 소유 정책을 검토한다. 기본생성자까지 포함하는 언어의 전체 특별멤버 목록과 이 묶음은 다르다.

  • rule of zero는 자원 관리를 적절한 멤버 타입에 맡겨 위 연산을 직접 정의할 필요를 줄이는 권고다.

  • raw pointer는 자동 소유권 관리가 없는 포인터다. unique_ptr는 한 소유자 책임을 관리하는 표준 타입이고, rvalue는 임시 값 등 이동 후보로 쓰이는 표현 범주다. overload는 같은 이름의 후보 함수 중 사용할 함수를 고르는 규칙이다.

학습 목표

  • zero와 five를 목적에 맞게 구별한다.

  • 암시적 이동에 영향을 주는 선언을 찾는다.

  • 복사 가능성과 독점소유 정책을 연결한다.

default라고 쓴 소멸자도 연산 후보를 바꿀까?

새 Plain은 int value만 두고 특별멤버를 선언하지 않는다. 새 Logged도 int value만 두지만 ~Logged()=default;를 선언한다. Logged의 소멸자는 사용자 선언이므로 암시적 이동 생성/대입 조건을 막는다. 그러나 유효한 const& 복사 후보가 있으면 rvalue 표현도 복사로 받을 수 있어 모든 문장이 실패하는 것은 아니다.

새 MoveOnly는 이동 생성자를 명시적으로 default하고 복사를 선언하지 않은 단순 int 클래스라고 하자. 암시적 복사 생성과 복사 대입은 삭제된다. 따라서 lvalue에서 복사하는 계획을 별도로 금지/제공해야 한다. rule of five는 일관된 정책 검토의 권고이며 다섯 함수의 무조건 수동 구현 명령도, 언어가 다섯 함수의 몸체를 자동으로 안전하게 만들어 준다는 약속도 아니다.

먼저 확인할 개념
  • 관리 책임을 멤버에 위임

    zero는 정리를 없애는 것이 아니라 책임을 관리 타입으로 옮긴다.

  • 선언이 후보에 미치는 영향

    사용자 선언과 사용자 구현 및 삭제 정책을 구별한다.

멤버가 자원을 관리하면 기본 동작 활용하기

Report가 std::string title과 std::vector<int> scores만 가진다면 이 멤버가 값과 자원을 관리한다. 소유 raw pointer를 직접 해제하는 소멸자를 추가할 필요가 없다. 기본 복사/대입은 멤버의 계약을 통해 Report의 값을 복사한다.

이것이 rule of zero 권고의 핵심이다. 자원 관리가 사라진다는 뜻이 아니라 책임이 멤버로 내려간다. unique_ptr를 멤버로 가진 클래스는 기본 복사가 불가능할 수 있으므로 zero가 항상 모든 연산 가능을 뜻하지 않는다.

소유 배열을 해제하려고 소멸자를 직접 선언하면 기본 얕은 복사가 맞는지 다시 봐야 한다. 복사생성·대입·이동생성·대입과 소멸의 계약은 연결된다. C.21은 하나를 정의하거나 삭제할 때 나머지를 함께 검토·명시하도록 권한다.

자기대입과 실패 안전성

복사할 메모리를 확보하기 전에 기존 값을 지우면 실패했을 때 무엇이 남을까?

준비 개념과 학습 목표

준비 개념

  • 자기대입 x=x는 같은 객체를 원본과 대상에 쓰는 대입이다.

  • 강한 예외 보장은 여기서 연산 실패 시 대상의 원래 값이 유지되는 계약이다. 기본 보장의 유효 상태·누수 없음과 다르다.

  • RAII는 자원 해제를 객체 수명에 연결하는 관리 방식이다. noexcept는 예외로 빠져나가지 않겠다는 선언이고 구현이 이를 어기면 종료될 수 있다. 커밋은 준비한 새 값을 대상에 확정하는 단계다.

학습 목표

  • 자기대입의 원본/대상 별칭을 찾는다.

  • 준비와 커밋을 분리한다.

  • 실패 보장의 조건과 비용을 설명한다.

객체 두 멤버가 각각 안전하게 대입되어도 전체는 강한 보장일까?

새 Document는 제목 string과 정수 점수 배열을 소유한다. 자체 사건 모형에서 title 대입은 성공하지만 scores 대입 준비는 실패할 수 있다고 명시한다. 전체 대상이 옛 제목 OLD/점수 [2,4]이고 원본이 NEW/[7,8]일 때 title부터 실제 대상에 대입한 뒤 scores가 실패하면 NEW/[2,4]라는 혼합 값이 남을 수 있다.

이것은 각각 유효한 멤버 상태라도 전체 Document의 원래 값이 유지되었다는 강한 보장을 뜻하지 않음을 보여 준다. 임시 Document를 끝까지 준비하고 제목/점수 두 소유 상태를 함께 무실패 교환하면 실패 준비는 기존 OLD/[2,4]를 보존한다. 교환과 임시 소멸/해제가 예외 없이 정상 수행된다는 조건을 명시하며 외부 로그·파일 효과는 포함하지 않는다.

원본을 지우는 잘못된 순서 찾기

소유 배열 대입이 기존 배열부터 지우고 원본에서 복사한다면 x=x에서 원본도 지워진다. 그 뒤 원본을 읽는 것은 유효한 정상 계산이 아니다. 앞에서 this==&rhs면 돌아오는 검사로 자기대입을 막을 수 있지만 일반 rhs의 할당 실패까지 자동 해결하지는 않는다.

표준 컨테이너의 자기대입이 안전한 멤버에 기본 대입을 맡기는 zero 설계가 단순할 수 있다. C.62는 자기대입의 값 보존과 swap 같은 구조도 다룬다. 모든 대입 앞에 같은 if 문을 기계적으로 붙이는 것이 목표는 아니다.

실패할 준비를 먼저 하고 커밋하기

자체 단일 int 배열 복사 모형에서는 새 공간 확보·원소 복사를 임시 소유자 안에서 끝낸 뒤 대상과 교환한다. 확보가 실패하면 기존 대상은 아직 그대로다. 교환이 실패하지 않고 임시 소멸이 던지지 않으며 자원 해제가 정상인 조건에서 교환 뒤 기존 자원은 임시가 정리한다.

이를 copy-and-swap 식의 준비/커밋으로 볼 수 있다. 실제 일반 T의 복사·swap·소멸이 예외를 던지면 같은 보장을 무조건 일반화할 수 없다. 임시도 RAII로 정리해야 하며 자원 규칙 없이 주소만 바꾸면 누수를 막았다는 증거가 되지 않는다.

자기대입과 실패를 각각 시험할 계획 세우기

대상 S=[4,7], 원본 R=[1,2]일 때 성공은 대상 값 [1,2], 준비 실패는 [4,7]로 남는 계약이다. 자기대입도 먼저 별도 임시에 값을 복사한 뒤 안전 교환하면 [4,7] 값이 유지된다. 임시 할당이 늘 수 있으므로 성능은 실측 없이 최고라고 단정하지 않는다.

관찰 화살표와 전체 값 대입의 책임

각 부분은 새 독립 초기 상태로 시작한다. 첫 부분은 살아 있는 x=4, Link a{x,1}, Link b=a에서 b.target=8; b.tag=3;을 수행한다. x와 두 Link의 target/tag 및 기본 b=a 대입 가능성을 적어라. 둘째 부분은 Record a의 values={2,4}, view=첫 원소이며 기본 b=a 복사 뒤 b.values[0]=9; a.values[0]=6;을 수행한다. 재할당은 없고 a는 살아 있다. 두 vector와 두 view를 적고 자기 저장소 관찰 정책의 수정안을 설명하라. 셋째 부분은 대상 Document OLD/[2,4]와 원본 NEW/[7,8]에 대한 순차 멤버 대입의 둘째 준비 실패 및 전체 임시 준비 실패/성공을 비교하라. 무실패 전체 교환과 정상 해제를 전제하며 실제 C++/할당 실패/학생 실행은 하지 않는다.

힌트 1

새 객체 수와 각 참조·포인터의 대상을 별도로 그린다. 복사 생성과 참조 멤버의 기본 대입 삭제를 나눈다.

힌트 2

전체 대상에 첫 필드를 저장한 시점과 임시만 준비한 시점을 구별한다. 성공 교환 뒤에는 임시가 옛 자원을 받는다.

풀이와 답 확인

  1. Link의 x는 8이며 두 target도 8이다. a.tag는 1, b.tag는 3이다. 참조 멤버가 있어 기본 copy assignment는 삭제되므로 b=a의 실행값을 만들지 않는다.

  2. Record의 a.values는 [6,4], b.values는 [9,4]다. 두 view는 a의 첫 원소 6을 읽는다. 인덱스를 저장하고 각 객체 자신의 vector에서 조회하면 자기 저장소 정책으로 바뀌며 범위 조건을 유지해야 한다.

  3. 순차 title 대입 성공 뒤 scores 준비 실패는 NEW/[2,4]라는 혼합 대상이 남을 수 있다. 전체 임시 준비 실패는 대상 OLD/[2,4]를 그대로 두고 완료된 임시 자원을 정리한다.

  4. 전체 임시 성공과 무실패 교환 후 대상은 NEW/[7,8], 임시는 OLD/[2,4]를 소유하고 정상 소멸 때 옛 자원을 정리한다. 이 모형의 강한 보장은 외부 I/O·실제 동시성까지 검증한 것이 아니다.

Link의 공유 target은 8이며 tag는 a 1/b 3이다. Record 값 배열은 a [6,4]/b [9,4]이며 두 view는 6이다. Document의 멤버별 실패와 전체 임시 실패는 NEW/[2,4] 대 OLD/[2,4]로 구별하고 성공 뒤 옛 자원은 임시가 정리한다.
