소단원 7.1

copy constructor·assignment

코드에 = 기호가 있다고 모두 같은 대입 연산일까?

준비 개념과 학습 목표

준비 개념

  • 객체 초기화는 새 객체를 만드는 과정이고 대입은 이미 살아 있는 객체의 값을 바꾸는 과정이다.

  • copy constructor는 같은 타입 객체로 새 객체를 초기화한다. copy assignment는 보통 T& operator=(const T&) 형태로 정의한다.

학습 목표

  • 선언 초기화와 대입을 구별한다.

  • 기본 멤버별 복사를 종이로 추적한다.

  • 참조 별칭과 새 객체를 구분한다.

새 객체인지 먼저 표시하기

단순 구조체 Point{int x;int y;}에서 Point b=a는 b 선언과 초기화다. 이름에 대입 기호가 보여도 이미 있는 b에 값을 넣는 문장이 아니다. 뒤에 b=a만 쓰면 기존 b에 copy assignment를 한다. 이 단원은 lvalue a와 단순 값 멤버만 사용한다.

작업 초안의 기본 복사는 멤버별로 적용된다. x와 y는 int 값으로 복사되어 새 Point를 만든 뒤 b.x를 바꿔도 a.x는 바뀌지 않는다. 이 사실을 포인터가 가리키는 대상이나 모든 사용자 정의 클래스에 그대로 확장하지 않는다.

대입은 기존 값의 처리가 필요하기

a=(2,5), b=(9,9)가 이미 있으면 b=a 뒤 b=(2,5)다. b 자체가 a라는 이름으로 바뀌는 것이 아니다. b가 자원을 소유한다면 기존 자원 처리와 새 값 복사의 정책도 중요하지만 int 예제는 그런 자원이 없다.

대입 연산자는 흔히 *this를 참조로 반환하여 c=b=a를 연결한다. 연결 대입은 오른쪽부터 b=a, 다음 c=b의 값 갱신으로 이해하자. 사용자 정의 operator=는 자신이 정한 계약을 따라야 하며 문법만으로 의미가 안전해지지는 않는다.

참조는 별개의 복사 객체가 아니기

Point& r=a는 참조를 a에 연결한다. r.x를 바꾸면 같은 a.x를 바꾼다. b 복사와 r 별칭의 두 화살표를 구분하면 어느 값이 영향을 받는지 예측하기 쉽다. 수명 밖의 참조를 사용하는 사례는 이 단순 모형에서 제외한다.

반환값·임시 객체·이동·복사 생략 등은 다른 조건을 가진다. 아래는 그런 사건을 세지 않는 직접 lvalue 초기화/대입 추적이다. 실제 컴파일러 출력이나 특별멤버 호출 로그를 실행해 관찰하지 않았다.

중간 과정을 따라가는 예제

Point a{2,5}; Point b=a; Point c{0,0}; c=b; b.x=9; Point& r=a; r.y=7; 뒤 a,b,c 값을 구하라.

  1. b 선언은 copy initialization이라 처음 b=(2,5)다.

  2. c=b는 기존 c 대입으로 c=(2,5)가 된다.

  3. b.x=9는 b만 바꾸므로 b=(9,5)다.

  4. r은 a의 별칭이라 r.y=7 뒤 a=(2,7), c=(2,5)는 그대로다.

a=(2,7), b=(9,5), c=(2,5)다.

종이와 본문으로 직접 해보기

초기 a(1,4),b(8,8),c(0,0)에서 c=b=a; b.y=6; 을 추적하고 초기화 사건이 있는지 적어라.

힌트 보기

세 객체는 이미 살아 있고 연결 대입은 오른쪽부터다.

풀이 보기

b=a 뒤 b(1,4), c=b 뒤 c(1,4), b.y=6 뒤 b(1,6)이다. a(1,4),c(1,4)는 유지된다. 이 두 줄에 새 객체 선언 초기화는 없다.

오해와 반례

Point b=a의 =는 항상 copy assignment다.

b가 선언되는 문장은 초기화이며 이미 있는 b=a 문장과 다르다. 참조 r=a는 또 다른 별칭 연결이다. 객체의 생성 시점과 타입을 먼저 확인한다.

자기점검

Point b=a에서 b는 새 객체인가?

답과 이유 보기

그렇다.

선언 초기화다.

c=b는 기존 c가 있을 때 무엇인가?

답과 이유 보기

대입이다.

새 객체 생성과 구분한다.

Point& r=a의 r.x 변경은?

답과 이유 보기

a.x를 바꾼다.

r은 a를 가리키는 별칭이다.

한 단계 더

각 줄에 새 객체/기존 객체 변경/별칭을 세 색으로 표시하자. const 멤버·참조 멤버·복사 불가능 멤버가 있으면 기본 대입이 삭제될 수 있음을 다음 탐구로 연결하되 실제 컴파일 검증은 미수행이다.

출처와 확인 범위
  • C++ working draft — Copy/move constructors

    실제 copy constructor 매개변수 형식·암시적 선언·이동 선언/소멸자의 영향 및 기본 memberwise copy 본문을 읽었다. 현재 작업 초안과 아래 명시한 간단한 값 모형을 구별한다.

  • C++ working draft — Copy/move assignment

    실제 copy assignment 형식·암시적 삭제 조건·memberwise assignment 본문을 읽었다. 생성과 이미 살아 있는 객체 대입의 차이를 자체 예제로 추적한다.

calculations: Point 예제 a2/7,b9/5,c2/5 및 연결대입 a1/4,b1/6,c1/4를 사건순서대로 손추적했다. · code_execution: not_executed — 자체 종이 예제와 원문 대조이며 교육 코드·장비·실제 회의/사고 대응을 수행하지 않았다. · learner_review: not_performed

소단원 7.2

얕은·깊은 복사

포인터 주소를 복사하면 주소에 있는 배열도 두 개로 늘어날까?

준비 개념과 학습 목표

준비 개념

  • 포인터 값은 대상 위치를 표현하며 포인터 변수 자체와 가리키는 대상은 별개다.

  • 얕은 복사는 주소 값 등 표현을 복사한다. 깊은 복사는 여기서 소유 배열 내용을 새 공간에 독립적으로 복사하는 정책을 뜻한다.

학습 목표

  • 주소와 배열 값을 구별한다.

  • 별칭에 따른 변경을 추적한다.

  • 소유권과 자원 해제 책임을 연결한다.

얕은 복사에 공유가 남기

가상 a.p가 공간S의 배열[3,6]을 가리킬 때 b.p=a.p이면 b도 S를 가리킨다. b.p[0]=8은 S를 바꾸므로 a에서 읽는 값도8이다. 포인터 값 두 개와 실제 배열 하나라는 그림을 그리자. 실제 주소 숫자를 같은 프로그램 밖에서도 유효한 값으로 다루지 않는다.

기본 멤버별 복사는 raw pointer 값도 복사하지만 그 대상 배열을 자동 복제하지 않는다. 얕은 복사 자체가 항상 틀린 것은 아니다. 비소유 관찰 포인터나 명시적 공유 의미에 맞을 수 있지만 대상 수명·수정 권한 조건은 별도다.

독립 값이 필요하면 소유 정책 정하기

독립 배열 값이 계약이면 b를 만들 때 새 공간T를 확보하고[3,6]을 옮겨 적는다. 이후 b의 첫 값8은 T만 바꾸므로 S는[3,6]다. 여기서는 배열 원소가 int여서 내용 복사가 단순하며 중첩 포인터를 가진 구조의 모든 그래프 복제를 자동 해결하지 않는다.

std::vector<int> 같은 자원 관리 멤버로 값을 표현하면 기본 멤버 복사를 통해 독립 원소 값이 생긴다. 반면 vector<int*>는 포인터 원소를 복사하므로 대상까지 깊게 복사한다는 뜻이 아니다. 타입과 복사 계약을 함께 읽는다.

소멸 때 누가 해제하는지 추적하기

a와 b 모두S를 독점 소유한다고 착각하여 각 소멸자가 같은 배열을 delete[]하면 두 번 해제하는 잘못된 설계가 된다. 첫 해제 뒤의 포인터는 유효한 배열 접근을 보장하지 않고 두 번째 해제의 결과는 정의된 정상 숫자 출력이 아니다. 위험 사례는 실제 실행하지 않는다.

독점 소유라면 복사를 제한하거나 새 소유 공간을 만들 수 있다. 명시적 공유는 별도의 수명 관리가 필요하다. 단순히 주소가 다르다는 조건만으로 복사 실패·기존 자원 누수·공유 그래프까지 검증 완료라고 할 수 없다.

중간 과정을 따라가는 예제

a가S=[3,6]을 가리킨다. 얕은 b는S를 공유, 깊은 c는T=[3,6]을 따로 가진다. b[0]=8 뒤 c[1]=9라면 각각 읽는 배열은?

  1. 시작은 a/b→S,c→T이고 배열은 두 개다.

  2. b[0]=8로 S=[8,6]이 되어 a와 b에서 같은 값을 읽는다.

  3. c[1]=9로 T=[3,9]가 되고S는 바뀌지 않는다.

  4. 이 추적에서는 객체 수명과 접근이 모두 유효하고 해제 사건은 아직 없다.

a/b=[8,6], c=[3,9]다.

종이와 본문으로 직접 해보기

vector<int> 두 개를 값 복사한 경우와 vector<int*> 두 개에 같은 S포인터를 넣은 경우를 비교하라. 후자의 대상 변경은 어디서 보이는가?

힌트 보기

벡터 원소의 타입과 포인터 대상은 별개다.

풀이 보기

int 원소 값은 복사 후 한 벡터 변경이 다른 값 원소에 영향을 주지 않는다. int* 원소는 주소를 복사해 같은 S대상 변경이 양쪽을 통해 관찰된다. 대상 수명은 벡터 자동 소멸만으로 해결되지 않는다.

오해와 반례

얕은 복사는 항상 나쁘고 vector를 쓰면 모든 대상도 깊은 복사다.

의도한 비소유 별칭은 얕은 복사가 맞을 수 있다. vector<int*> 반례는 컨테이너 복사와 포인터 대상 복제가 다름을 보인다. 값·공유·독점 계약을 먼저 정한다.

자기점검

두 포인터가S를 가리키면 배열은 몇 개인가?

답과 이유 보기

한 개다.

주소 사본 수와 대상 수는 다르다.

깊은 c의T를 바꾸면S도 바뀌는가?

답과 이유 보기

이 모형에서는 아니다.

독립 int 배열을 확보했다.

같은 소유 배열을 두 번 delete[]해도 되는가?

답과 이유 보기

안 된다.

두 번째 해제는 유효한 정상 동작이 아니다.

한 단계 더

소유자·비소유 관찰자·자원 수명의 세 열을 만들고 같은 공간을 가리키는 모든 화살표를 적자. 중첩 객체 그래프는 공유 보존이나 순환 처리 같은 추가 복사 정책이 필요한 별도 문제로 남긴다.

출처와 확인 범위
  • C++ working draft — Copy/move constructors

    실제 copy constructor 매개변수 형식·암시적 선언·이동 선언/소멸자의 영향 및 기본 memberwise copy 본문을 읽었다. 현재 작업 초안과 아래 명시한 간단한 값 모형을 구별한다.

  • C++ Core Guidelines — C.20/21/61/62/83–85

    실제 C.20 rule of zero·C.21 five 및 암시적 move 영향·C.61 값/포인터 의미·C.62 자기대입과 swap 설명을 읽었다. 권고와 언어 문법을 구분하며 교육 코드를 실행하지 않았다.

calculations: S/T 독립배열[8,6]/[3,9]와 포인터복사별칭을 종이로 추적했다. 잘못된 해제 코드는 실행하지 않았다. · code_execution: not_executed — 자체 종이 예제와 원문 대조이며 교육 코드·장비·실제 회의/사고 대응을 수행하지 않았다. · learner_review: not_performed

소단원 7.3

rule of zero·five

특별멤버 다섯 개를 모두 손으로 쓰는 것이 언제나 좋은 설계일까?

준비 개념과 학습 목표

준비 개념

  • 특별멤버 중 복사생성·복사대입·이동생성·이동대입·소멸을 다섯 개로 묶어 소유 정책을 검토한다. 기본생성자까지 포함하는 언어의 전체 특별멤버 목록과 이 묶음은 다르다.

  • rule of zero는 자원 관리를 적절한 멤버 타입에 맡겨 위 연산을 직접 정의할 필요를 줄이는 권고다.

  • raw pointer는 자동 소유권 관리가 없는 포인터다. unique_ptr는 한 소유자 책임을 관리하는 표준 타입이고, rvalue는 임시 값 등 이동 후보로 쓰이는 표현 범주다. overload는 같은 이름의 후보 함수 중 사용할 함수를 고르는 규칙이다.

학습 목표

  • zero와 five를 목적에 맞게 구별한다.

  • 암시적 이동에 영향을 주는 선언을 찾는다.

  • 복사 가능성과 독점소유 정책을 연결한다.

멤버가 자원을 관리하면 기본 동작 활용하기

Report가 std::string title과 std::vector<int> scores만 가진다면 이 멤버가 값과 자원을 관리한다. 소유 raw pointer를 직접 해제하는 소멸자를 추가할 필요가 없다. 기본 복사/대입은 멤버의 계약을 통해 Report의 값을 복사한다.

이것이 rule of zero 권고의 핵심이다. 자원 관리가 사라진다는 뜻이 아니라 책임이 멤버로 내려간다. unique_ptr를 멤버로 가진 클래스는 기본 복사가 불가능할 수 있으므로 zero가 항상 모든 연산 가능을 뜻하지 않는다.

하나를 선언하면 나머지도 고려하기

소유 배열을 해제하려고 소멸자를 직접 선언하면 기본 얕은 복사가 맞는지 다시 봐야 한다. 복사생성·대입·이동생성·대입과 소멸의 계약은 연결된다. C.21은 하나를 정의하거나 삭제할 때 나머지를 함께 검토·명시하도록 권한다.

작업 초안에서 사용자 선언 소멸자는 암시적 이동생성 조건을 막는다. =default라도 사용자 선언이다. 이동이 없으면 어떤 표현은 복사로 처리될 수 있으므로 항상 컴파일 오류라고 일반화하지 않는다. 직접 이동을 선언하면 암시적 복사 삭제 등 다른 영향도 있다.

가능한 연산과 원하는 연산 구별하기

독점 자원 소유자는 복사를=delete로 제한하고 이동만 제공하는 정책도 가능하다. five는 다섯 몸체를 무조건 복붙하라는 뜻이 아니라 제공/기본화/금지와 자원 관계를 일관되게 정하라는 권고다. 사용자 정의 이동의 원본 상태도 소멸 가능한 상태로 정해야 한다.

아래는 선언 분류이며 실제 컴파일러의 overload와 예외 명세를 전부 검증한 것이 아니다. 표준·멤버 조건·사용 문장을 함께 봐야 한다. 예제는 C++11 이후 이동 개념을 전제로 하고 현재 작업 초안의 정확한 규칙은 출처로 따로 확인한다.

중간 과정을 따라가는 예제

값 멤버string/vector만 가진 Report A, 소유 raw배열+사용자소멸자의 B, unique_ptr 멤버만 가진 C의 정책 점검 항목을 분류하라.

  1. A는 멤버에 관리를 맡겨 zero를 우선 검토한다. 기본 값 복사를 의도한다.

  2. B는 소멸 외 복사/대입의 얕은 소유 문제와 암시적 이동 억제를 검토해야 한다.

  3. C는 독점 소유 멤버 때문에 기본 복사가 가능하다고 쓰지 않는다. 이동 정책을 별도로 본다.

  4. 모든 클래스에 다섯 함수 몸체를 추가하는 결론은 나오지 않는다.

A zero 우선, B five 정책 재검토, C 복사 불가 가능성과 독점 이동을 확인한다.

소단원 7.4

자기대입과 실패 안전성

복사할 메모리를 확보하기 전에 기존 값을 지우면 실패했을 때 무엇이 남을까?

준비 개념과 학습 목표

준비 개념

  • 자기대입 x=x는 같은 객체를 원본과 대상에 쓰는 대입이다.

  • 강한 예외 보장은 여기서 연산 실패 시 대상의 원래 값이 유지되는 계약이다. 기본 보장의 유효 상태·누수 없음과 다르다.

  • RAII는 자원 해제를 객체 수명에 연결하는 관리 방식이다. noexcept는 예외로 빠져나가지 않겠다는 선언이고 구현이 이를 어기면 종료될 수 있다. 커밋은 준비한 새 값을 대상에 확정하는 단계다.

학습 목표

  • 자기대입의 원본/대상 별칭을 찾는다.

  • 준비와 커밋을 분리한다.

  • 실패 보장의 조건과 비용을 설명한다.

원본을 지우는 잘못된 순서 찾기

소유 배열 대입이 기존 배열부터 지우고 원본에서 복사한다면 x=x에서 원본도 지워진다. 그 뒤 원본을 읽는 것은 유효한 정상 계산이 아니다. 앞에서 this==&rhs면 돌아오는 검사로 자기대입을 막을 수 있지만 일반 rhs의 할당 실패까지 자동 해결하지는 않는다.

표준 컨테이너의 자기대입이 안전한 멤버에 기본 대입을 맡기는 zero 설계가 단순할 수 있다. C.62는 자기대입의 값 보존과 swap 같은 구조도 다룬다. 모든 대입 앞에 같은 if 문을 기계적으로 붙이는 것이 목표는 아니다.

실패할 준비를 먼저 하고 커밋하기

자체 단일 int 배열 복사 모형에서는 새 공간 확보·원소 복사를 임시 소유자 안에서 끝낸 뒤 대상과 교환한다. 확보가 실패하면 기존 대상은 아직 그대로다. 교환이 실패하지 않고 임시 소멸이 던지지 않으며 자원 해제가 정상인 조건에서 교환 뒤 기존 자원은 임시가 정리한다.

이를 copy-and-swap 식의 준비/커밋으로 볼 수 있다. 실제 일반 T의 복사·swap·소멸이 예외를 던지면 같은 보장을 무조건 일반화할 수 없다. 임시도 RAII로 정리해야 하며 자원 규칙 없이 주소만 바꾸면 누수를 막았다는 증거가 되지 않는다.

자기대입과 실패를 각각 시험할 계획 세우기

대상 S=[4,7], 원본 R=[1,2]일 때 성공은 대상 값 [1,2], 준비 실패는 [4,7]로 남는 계약이다. 자기대입도 먼저 별도 임시에 값을 복사한 뒤 안전 교환하면 [4,7] 값이 유지된다. 임시 할당이 늘 수 있으므로 성능은 실측 없이 최고라고 단정하지 않는다.

아래는 추상 사건표이고 완전한 배열 클래스 코드는 아니다. 실제 할당 실패 주입·컴파일·자기대입 실행을 하지 않았다. 이론 계약을 검토할 때 조건을 명시하고 실행 검증과 별도로 기록한다.

중간 과정을 따라가는 예제

S=[4,7], R=[1,2]에서 임시 T를 복사해 준비하고 noexcept 교환/던지지 않는 해제를 가정한다. 준비 실패·성공의 S와 해제 대상을 추적하라.

  1. 준비 실패는 교환 전이므로 S=[4,7] 유지, 부분 임시는 RAII로 정리한다고 가정한다.

  2. 성공 준비 후 T=[1,2], S=[4,7]다.

  3. 교환 후 S=[1,2], T는 옛 S=[4,7] 자원을 가진다.

  4. T 소멸이 옛 S 자원을 정리하며 S의 새 값은 유지한다. 교환/해제 무실패 조건을 확인한다.

실패 S=[4,7], 성공 S=[1,2]이며 옛 자원은 임시가 정리한다.

종이와 본문으로 직접 해보기

S=S에서 먼저 T에 값을 복사한 뒤 교환하는 경우와, 기존 S를 먼저 해제한 뒤 S에서 읽는 경우를 그려라.

힌트 보기

이름이 달라도 원본/대상이 같은 자원인지 확인한다.

풀이 보기

첫 경우 T=[4,7]을 별도 확보한 후 교환하므로 S의 값 [4,7]이 유지된다. 둘째는 읽을 원본 자원을 이미 해제해 유효 접근을 보장하지 못한다. 정의된 쓰레기 값 숫자를 답으로 만들지 않는다.

오해와 반례

자기대입 if 검사가 있으면 모든 대입의 강한 예외 보장이 해결된다.

다른 객체 대입에서도 기존 자원을 먼저 지운 뒤 할당에 실패하면 원래 값을 잃을 수 있다. 자기대입 검사와 실패 준비/커밋 설계는 별도 문제다.

자기점검

답과 이유 보기

[4,7]이다.

기존 대상을 아직 바꾸지 않았다.

성공 교환 뒤 옛 S 자원은 누가 정리하는가?

답과 이유 보기

임시 소유자다.

교환으로 임시가 옛 자원을 받는다.

강한 보장에 swap 실패 가능성을 무시해도 되는가?

답과 이유 보기
