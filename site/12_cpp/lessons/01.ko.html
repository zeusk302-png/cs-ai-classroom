소단원 1.1

compiler·표준·프로젝트

파일 이름을 .c에서 .cpp로 바꾸면 같은 프로그램이 될까?

준비 개념과 학습 목표

준비 개념

  • C의 소스→번역→목적 파일→링크 흐름.

  • 미니복습: 헤더의 선언은 사용 계약을 제공하고 함수 정의는 실제 몸통을 제공한다.

  • 이 단원의 std::cout에서 ::는 std라는 이름공간 안의 이름을 고르는 기호이고, <<는 값을 출력 흐름에 보내는 연산자이다. int a{2}의 중괄호는 초기값 2를 준다.

학습 목표

  • C++ 언어 모드와 도구 제품·버전을 구분한다.

  • 프로젝트의 소스·헤더·빌드 설정을 묶어 설명한다.

  • C와 C++의 호환성을 단순 포함 관계로 오해하지 않는다.

C++는 별도의 언어 규칙을 가진다

C와 C++는 많은 문법과 관례를 공유하지만 C++를 '모든 C 코드에 클래스만 추가한 언어'라고 보면 정확하지 않다. 같은 텍스트를 어느 언어 규칙으로 분석하느냐에 따라 허용 여부와 의미가 달라질 수 있다. 예를 들어 C에서 malloc의 void* 반환은 다른 객체 포인터형으로 암묵 변환할 수 있지만 C++에서는 같은 암묵 변환을 허용하지 않는다.

이 수업은 C++17 hosted 환경을 기준으로 하며 C++20·23의 새로운 문법을 기본 예제에 섞지 않는다. auto의 의미도 현대 C++에서는 타입 추론과 연결되므로 C17의 저장 클래스 용법과 같다고 읽으면 안 된다. 언어판·파일 형식·컴파일러 모드를 함께 명시하는 이유이다.

컴파일러 드라이버와 라이브러리

GCC 계열에서 g++는 C++ 프로그램에 맞는 드라이버이다. .cpp 파일은 일반적으로 C++ 소스로 처리되고 g++는 C++ 표준 라이브러리의 연결도 지원한다. gcc도 언어를 선택하여 C++ 소스를 처리할 수 있지만 링크 설정을 그대로 같다고 생각해서는 안 된다.

선택 명령 g++ -std=c++17 -Wall -Wextra main.cpp -o demo는 기준판과 입력·출력을 지정한다. 이 명령은 도구 인터페이스이므로 MSVC의 옵션 표기와 다르다. 최신 도구의 기본판이나 확장 동작은 바뀔 수 있어 기준판을 명시한다. 아래 예상 출력은 정상 입출력과 적절한 라이브러리가 제공되는 환경을 가정한다.

#include <iostream>
int main() {
    int a{2};
    int b{3};
    std::cout << a + b << '\n';
    return 0;
}

프로젝트는 코드와 재현 조건의 묶음이다

작은 프로젝트도 소스 파일, 필요한 헤더, 빌드 대상, 언어판, 의존 라이브러리의 정보를 가진다. 편집기 화면에 파일이 보이는 것만으로 그 파일이 빌드에 포함된 것은 아니다. 별도 함수 파일을 목록에서 누락하면 C에서처럼 링크에 실패할 수 있다.

C++는 템플릿과 inline 함수 등 정의 배치에 관한 추가 규칙을 가진다. 이 첫 단원은 파일을 나누는 기본 모델까지만 다루고, 세부 one-definition rule은 후속 단원으로 연결한다. 빌드 성공은 인터페이스와 정의가 도구 조건에서 연결되었다는 증거이며 모든 입력의 정확성을 자동 보장하지 않는다.

중간 과정을 따라가는 예제

위 main.cpp를 C++17로 분석한다고 가정한다. a,b의 초기값과 출력, 필수 프로젝트 정보를 적는다.

  1. <iostream>은 std::cout 선언 등 스트림 인터페이스를 제공한다.

  2. int a{2}, b{3}은 각각 int 객체를 2,3으로 초기화한다.

  3. a+b=5이며 std::cout으로 5와 줄바꿈을 보낸다.

  4. 빌드 기록에는 main.cpp, g++ 제품/버전, -std=c++17, 출력 대상과 명령을 적는다.

오해와 반례

C++는 C의 완전한 상위 집합이므로 모든 C 코드는 그대로 맞다.

C17에서 int* p=malloc(sizeof *p) 같은 void* 암묵 변환은 허용되지만 C++에서는 그렇지 않다. 두 언어의 공통부분과 별도 규칙을 구분하고, C++에서 소유 자원은 표준 컨테이너 등으로 표현하는 설계를 검토한다.

소단원 1.2

namespace·overload

같은 이름의 함수 둘을 보고 컴파일러는 어떻게 하나를 고를까?

준비 개념과 학습 목표

준비 개념

  • 함수 인자와 반환형; int와 double의 구분.

  • 자가진단: 2는 int 리터럴, 2.0은 double 리터럴이다. 같은 수학적 값이라도 표현식 타입이 다르다.

학습 목표

  • 한정 이름으로 이름 공간을 구분한다.

  • 단순 오버로드 집합에서 인자 타입으로 함수를 선택한다.

  • 반환형만 다른 오버로드와 모호한 호출을 구분한다.

이름의 주소를 만드는 namespace

namespace는 타입·함수·변수 등 이름을 논리적인 범위에 묶는 선언 영역이다. math::twice에서 ::는 범위 한정자로, math 안의 twice를 찾으라는 의미이다. 다른 라이브러리에도 twice가 있을 때 전체 이름을 구분하면 충돌을 줄일 수 있다.

std::cout의 std는 표준 라이브러리 이름 공간이다. using 선언은 특정 이름을, using namespace 지시문은 이름 공간의 이름들을 한정 없이 찾을 수 있게 하는 도구이다. 뒤의 방식은 공유 헤더에서 예상 못한 충돌을 만들 수 있어 첫 예제는 한정 이름을 유지한다. namespace 자체가 객체나 함수 호출인 것은 아니다.

오버로드는 이름과 인자 계약을 함께 본다

같은 범위에 이름이 같고 인자 타입이나 수가 다른 여러 함수를 선언할 수 있다. 이를 함수 오버로딩이라고 한다. 이 예제에서는 twice(int)와 twice(double)가 있으며 호출 인자의 타입과 정확히 일치하는 후보를 선택하는 단순 상황이다.

2와 2.5는 각각 int와 double이므로 서로 다른 함수를 고른다. 반환형만 int에서 double로 바꾼 동일 인자 함수 둘은 이 방식으로 구분할 수 없다. 호출 결과를 받을 변수 타입을 보고 원하는 오버로드를 임의로 골라 주는 모델로 생각하면 안 된다.

변환이 있으면 선택 조건을 따져야 한다

모든 호출에 정확한 일치가 있는 것은 아니다. 타입 변환을 허용하는 후보 중 더 나은 것을 고르는 규칙이 있고, 뚜렷한 우선 후보가 없으면 모호한 호출로 번역 오류가 생긴다. 따라서 '소스에서 먼저 선언된 함수를 실행한다'는 규칙은 없다.

여기서는 정확 일치만 추적한다. int와 double 혼합, 사용자 정의 변환, 템플릿이 들어가면 후보 집합과 변환 순위를 추가로 다뤄야 한다. 컴파일 시간의 오버로드 선택과 실행 시간의 가상 함수 선택도 별개이며 뒤의 내용은 객체지향 단원에서 다룬다.

#include <iostream>
namespace math {
    int twice(int x) { return 2 * x; }
    double twice(double x) { return 2 * x; }
}
int main() {
    std::cout << math::twice(2) << ' ' << math::twice(2.5) << '\n';
}

중간 과정을 따라가는 예제

위 두 호출의 namespace와 인자 타입을 적고 결과를 추적하라. 스트림의 기본 숫자 표시 형식을 가정한다.

  1. math:: 한정은 math의 두 twice 선언을 찾게 한다.

  2. 2는 int이므로 twice(int)의 x=2, 반환값 4이다.

  3. 2.5는 double이므로 twice(double)의 x=2.5, 반환값 5.0이다.

  4. 기본 스트림 표시에서 double 5.0은 5로 표시되며 중간 공백과 줄바꿈을 넣는다.

예상 화면 출력은 4 5이다. 두 번째 계산 값의 타입은 double이며 화면에 소수점이 없다는 이유로 int이라고 결론 내리지 않는다.

종이와 본문으로 직접 해보기

함수 카드 f(int)와 f(double)를 그려 f(3), f(3.0)의 화살표를 연결하라. 별도 코드에서 int g(int)와 double g(int)를 동시에 선언하여 반환형으로만 나누려는 시도가 가능한지 적어라.

힌트 보기

먼저 호출 인자의 타입을 본다. 반환형만의 차이는 오버로드를 구성하지 못한다.

풀이 보기

f(3)→f(int), f(3.0)→f(double). g 두 선언은 인자 목록이 같아 반환형만으로 구분하는 유효한 오버로드가 아니다.

오해와 반례

오버로드는 파일에 먼저 나온 함수를 선택한다.

double 인자 2.5는 예제에서 뒤에 정의한 twice(double)을 고른다. 선언 순서가 아니라 후보와 인자 변환 규칙이 핵심이며 동률처럼 모호하면 오류가 될 수 있다.

소단원 1.3

초기화·auto·type inference

타입 이름을 쓰지 않았는데도 auto 변수는 왜 마음대로 종류를 바꿀 수 없을까?

준비 개념과 학습 목표

준비 개념

  • 선언은 객체의 이름과 타입을 정한다. 대입은 이미 존재하는 객체의 값을 바꾼다.

  • 미니복습: int는 정수형이고 double은 실수형이다. int 3과 double 3.0은 타입이 다르다.

학습 목표

  • 객체 초기화와 이후 대입을 구분한다.

  • auto의 정적 타입 추론을 설명한다.

  • auto 복사와 auto& 별칭을 추적한다.

  • 단순 정수의 중괄호 초기화와 축소 변환 진단을 구분한다.

처음 값을 만드는 초기화

int n{3}은 n이라는 int 객체를 3으로 초기화한다. 이후 n=4는 같은 객체에 새 값을 대입한다. int zero{}처럼 빈 중괄호로 초기화한 단순 int의 값은 0이다. 반면 함수 안의 int unknown;을 읽는 코드는 안전한 0 초기값을 보장하지 않는다. 이 설명은 C++17의 지역 스칼라 객체에 대한 조건이다.

중괄호 초기화는 축소 변환에 관한 검사를 제공한다. int bad{3.5}는 double의 소수 부분을 버리는 축소 변환이므로 허용되는 초기화가 아니다. 그렇다고 중괄호가 모든 클래스 생성자 선택과 의미 오류를 해결하는 것은 아니다. 표준 컨테이너는 괄호와 중괄호의 의미가 달라질 수 있다.

auto는 컴파일 때 타입을 추론한다

auto value=3은 초기화 식의 타입을 근거로 value의 타입을 추론하며 여기서는 int이다. 실행 중 value에 넣는 값마다 타입을 바꾸는 동적 변수라는 뜻이 아니다. value=3.5는 int에 대입하는 변환이 일어나며 이 작은 값에서는 소수 부분을 버려 3이 된다.

auto real=3.5는 double이다. 리터럴 표기가 추론에 영향을 준다. 따라서 어떤 값이 수학적으로 정수처럼 보이는지보다 초기화 식의 C++ 타입을 봐야 한다. 이 수업은 auto x=식 형태로 시작하고 auto x={3}처럼 initializer_list가 되는 별도 규칙은 심화로 남긴다.

복사와 참조의 구분

int original{3}; auto copy=original;은 새 int 객체 copy를 값 3으로 만든다. auto& alias=original;은 참조 alias를 original에 연결한다. alias=8은 original을 바꾸지만 copy는 이전 값 3을 유지한다. &는 이 선언에서 참조를 지정하는 기호이며 C의 주소 연산 문맥과 구분한다.

참조를 쓰면 복사 비용을 줄이거나 원본을 수정할 수 있지만 대상 객체의 수명 조건을 따라야 한다. 이 예제의 original은 끝까지 살아 있으므로 alias 사용이 유효하다. 원본이 사라진 뒤 참조를 읽는 문제는 auto가 자동으로 방지하지 않는다.

#include <iostream>
int main() {
    int original{3};
    auto copy = original;
    auto& alias = original;
    alias = 8;
    std::cout << original << ' ' << copy << '\n';
}

중간 과정을 따라가는 예제

위 프로그램에서 각 선언 뒤 타입과 값 관계를 표시하라.

  1. original은 int 객체이며 값 3이다.

  2. copy는 새 int 객체이며 값 3이다. original과 같은 객체가 아니다.

  3. alias는 int&이며 original을 가리키는 참조이다.

  4. alias=8은 original의 값만 8로 바꾼다. copy는 3이다.

예상 출력은 8 3이다. auto는 여기서 컴파일 시 int를 추론하고 auto&는 int& 참조를 만든다.

auto n=3은 int 객체를 만든다. n=3.5는 int에 맞추는 대입 변환이지 n의 타입을 double로 바꾸는 것이 아니다. 또한 auto copy=original은 별도 복사이며 참조는 auto&로 명시한다.

소단원 1.4

C식 자원관리의 문제

메모리를 한 번 얻었는데 함수에서 나가는 길이 세 갈래라면 누가 반납을 책임질까?

준비 개념과 학습 목표

준비 개념

  • C의 malloc은 실패할 수 있고 성공한 할당은 적절히 free해야 한다.

  • 준비 진단: 포인터를 복사한다고 할당이 두 개 생기지는 않는다. 소유자는 해제 책임을 가지며 빌림은 임시 사용만 한다.

학습 목표

  • 획득 후 정상·조기 반환·실패 경로에서 해제 책임을 추적한다.

  • 메모리 누수·중복 해제·댕글링 사용을 구분한다.

  • RAII가 자원 수명을 객체 수명에 연결하는 원리를 설명한다.

  • RAII 보장과 경계 접근 안전성의 범위를 구분한다.

C의 수동 정리에는 모든 경로가 중요하다

동적 메모리는 함수의 지역 포인터 변수가 사라진다고 자동으로 free되는 자원이 아니다. 포인터는 주소를 담는 값이고 할당 영역의 소유 책임은 프로그램 설계에 있다. 성공한 malloc 영역을 해제하지 않으면 누수가, 같은 영역을 두 번 해제하면 중복 해제 문제가 생긴다.

자원을 얻은 뒤 조기 return이나 실패 분기가 추가되면 각 경로의 정리를 확인해야 한다. 아래 C 스타일 조각은 할당 실패를 확인하지만 reject가 참이면 free 전에 빠져나가 누수 경로를 만든다. 이는 C 언어 자체가 잘못이라는 뜻이 아니라 수동 관리 계약을 모든 경로에서 지킬 필요가 있다는 뜻이다.

/* C 스타일 설명 조각: reject는 외부 조건이라고 가정 */
int* data = malloc(3 * sizeof *data);
if (data == NULL) return 1;
if (reject) return 2; /* 할당 성공 후 해제 누락 */
data[0] = 2; data[1] = 3; data[2] = 4;
free(data);
return 0;

RAII는 책임을 소유 객체에 묶는다

RAII(Resource Acquisition Is Initialization)는 자원 획득·해제 책임을 객체의 초기화와 소멸에 연결하는 설계 원리이다. std::vector<int>는 원소 저장 공간을 관리하는 표준 컨테이너이다. 지역 vector가 성공적으로 생성되면 그 소멸 시 저장 공간 정리 책임을 수행한다.

정상 scope 종료뿐 아니라 return으로 나가거나 일반적인 예외 전파로 stack unwinding이 진행될 때 완전히 생성된 지역 객체의 소멸자가 호출된다. vector를 쓴 함수의 각 return 앞에 사용자가 free를 반복할 필요가 없다. '객체가 stack에 있으니 모든 원소도 stack에 있다'고 설명하면 틀리며 컨테이너 객체와 관리하는 저장 공간을 구분해야 한다.

수명 안전성에도 적용 범위가 있다

RAII는 일반적인 scope 정리에 강한 도구지만 모든 메모리 오류를 해결하지는 않는다. vector의 범위 밖 operator[] 사용, 이미 소멸한 객체에 대한 참조, 비소유 포인터의 수명 위반은 여전히 문제가 된다. 소유 객체와 빌린 포인터·참조를 표시하고 사용 종료 시점을 함께 생각한다.

강제 프로세스 종료나 std::abort, std::exit처럼 지역 scope 정리를 우회하는 종료는 일반적인 지역 객체 소멸과 구분한다. 또한 메모리 할당 실패로 vector 생성이 완료되지 않으면 정상 sum 경로에 도달하지 않는다. 예제는 할당 성공, 유효한 인덱스, 작은 정수 합이 표현 범위 안이라는 조건을 가정한다.

#include <iostream>
#include <vector>
int sum(bool reject) {
    std::vector<int> data{2, 3, 4};
    if (reject) return -1;
    return data[0] + data[1] + data[2];
}
int main() {
    std::cout << sum(false) << ' ' << sum(true) << '\n';
}

중간 과정을 따라가는 예제

C 스타일 조각과 C++ sum 함수에서 reject=false와 true의 자원 경로를 비교한다. 메모리 할당 성공을 가정한다.

  1. C 조각 false: 획득→원소 설정→free→return 0으로 정상 해제한다.

  2. C 조각 true: 획득→return 2이며 free를 건너뛰어 누수 경로가 된다.

  3. C++ false: vector 생성→2+3+4=9 계산→반환 경로에서 vector 소멸과 정리를 수행한다.

  4. C++ true: vector 생성→return -1 경로에서도 vector 소멸과 정리를 수행한다.

C++ main의 예상 출력은 9 -1이다. RAII는 이 두 반환 경로에서 저장 자원의 정리 책임을 vector에 묶는다.

종이와 본문으로 직접 해보기

종이에 자원 상자 R 하나와 소유자 P, 빌린 주소 Q를 그린다. P가 해제한 뒤 Q가 원소를 읽는 상황과 P,Q가 둘 다 해제하는 상황을 구분하라. 이어 vector를 가진 함수의 두 반환 화살표에 소멸 사건을 넣어라.

힌트 보기

주소가 남아 있다는 것과 자원이 살아 있다는 것은 다르다.

풀이 보기

P 해제 뒤 Q 읽기는 수명 종료 후 사용이며 Q도 해제하면 중복 해제이다. vector의 정상/조기 return 두 화살표에는 완전히 생성된 vector의 소멸과 저장 정리가 들어간다. 빌린 주소를 함수 밖으로 반환해 소멸 뒤 사용하면 RAII만으로 해결되지 않는다.

오해와 반례

vector를 쓰면 모든 포인터·인덱스·수명 오류가 사라진다.

원소가 세 개인 vector에서 data[3]을 읽는 범위 위반이나 소멸한 vector의 원소 참조 사용은 여전히 잘못이다. vector는 소유 저장의 정리를 관리하며 모든 사용 계약을 자동 증명하지 않는다.
