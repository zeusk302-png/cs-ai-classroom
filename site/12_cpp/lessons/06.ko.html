소단원 6.1

private와 public API

숫자 한 개를 숨기는 것이 왜 프로그램을 더 이해하기 쉽게 만들까?

준비 개념과 학습 목표

준비 개념

  • 클래스는 상태와 그 상태에 대한 연산을 함께 정의하는 사용자 타입이다.
  • C++20 문맥의 아래 조각은 종이로만 추적했다.
  • 불변조건은 객체가 유효할 때 지켜야 하는 상태 조건이다.

학습 목표

  • 접근 제어와 상태를 읽는 공개 API를 구분한다.
  • 공개 연산의 성공·실패 계약을 추적한다.
  • private가 정확성을 자동 보증하지 않는 이유를 설명한다.

허용한 통로로 바꾸기

Counter는 0부터 10까지의 작은 값만 허용하는 자체 교육 모델이다. value_는 표현을 저장하는 private 멤버이고 value()와 add()가 사용자에게 허용한 public 통로다. c.value_=100처럼 외부에서 바로 대입하는 코드는 접근 규칙에 맞지 않는다. 반면 클래스의 멤버 함수는 내부 표현을 사용할 수 있다.

class의 기본 멤버 접근은 private지만 struct의 기본은 public이다. 접근 제어는 어떤 코드가 이름을 사용할 수 있는지 정하는 언어 규칙이며 암호화나 악성 코드에 대한 보안 경계로 해석하지 않는다. 객체가 메모리에 있다는 사실까지 숨기는 장치도 아니다.

함수 이름보다 계약을 읽는다

아래 add(n)는 n이 음수이거나 남은 여유 10−value_보다 클 때 false를 반환하고 상태를 그대로 둔다. 성공하면 새 값 value_+n을 저장하고 true를 반환한다. 음수 n은 먼저 거부하고, 작은 0~10 범위만 더하므로 이 모델에서는 int 덧셈 오버플로를 피한다.

value()의 const는 이 함수가 일반적인 비가변 멤버를 변경하지 않는 인터페이스임을 나타낸다. 클래스 전체의 영원한 불변성이나 동시에 여러 스레드가 사용할 때의 안전성을 이 표기 하나가 보장하지는 않는다. 스레드 간 동기화는 이 단원의 범위 밖이다.

#include <stdexcept>
class Counter {
    int value_;
public:
    explicit Counter(int x) : value_(x) {
        if (x < 0 || x > 10) throw std::invalid_argument("range");
    }
    int value() const { return value_; }
    bool add(int n) {
        if (n < 0 || n > 10 - value_) return false;
        value_ += n;
        return true;
    }
};
// C++20 교육용 조각, 실제 컴파일·실행하지 않음
// Counter c(3); c.add(4); c.add(5); c.value();

정확한 상태 변화가 인터페이스다

public 함수가 많아질수록 각 함수가 상태 조건을 지켜야 하는 통로도 늘어난다. set_value(int)라는 무제한 대입 함수를 추가하면 private 표현만으로 0~10 조건을 지킬 수 없다. 필요한 작업을 제한된 의미로 제공하고 실패 때 상태를 명시해야 한다.

사용자는 내부 변수 이름보다 “성공 시 얼마나 변하는가, 실패 시 어떤 값이 남는가”를 읽으면 된다. 표현이 나중에 바뀌어도 공개 계약을 유지하면 사용자 코드를 이해하는 기준이 안정적이다.

중간 과정을 따라가는 예제

Counter c(3) 뒤 add(4), add(5), value()를 순서대로 종이 추적한다. 실패가 상태를 바꾸지 않는 계약을 적용하라.

  1. 초기 3은 0~10 안에 있어 객체 생성이 완료된다고 가정한다.
  2. add(4): 여유 7이고 4≤7이므로 true, 새 값 7이다.
  3. add(5): 여유 3이고 5>3이므로 false, 값은 7이다.
  4. value()는 7을 반환할 것으로 예상된다. 출력 코드는 없고 실제 실행도 하지 않았다.

반환은 true, false, 7이며 마지막 상태는 7이다. 실패한 요청을 받아 값 12로 바꾸지 않는다.

종이와 본문으로 직접 해보기

상태 7에서 add(-1), add(3), add(0), add(1)을 차례로 계산하라.

힌트 보기

각 요청 직전의 값에서 여유를 다시 계산한다.

풀이 보기

add(-1)은 false·7 유지. add(3)은 true·10. add(0)은 true·10 유지. add(1)은 여유 0보다 커 false·10 유지. 성공이 항상 값을 증가시킨다는 말은 n=0이 반례다.

오해와 반례

데이터를 private로 바꾸기만 하면 모든 상태가 올바르다.

멤버 함수 내부에서 value_=100을 대입할 수 있다. private는 통로를 제한하고 그 통로의 로직을 자동 증명하지 않는다. 검사를 누락한 public setter가 반례다.

소단원 6.2

constructor·destructor

객체가 생기고 사라질 때 해야 하는 일을 어디에 모을까?

준비 개념과 학습 목표

준비 개념

  • 생성자는 객체의 초기 상태를 정하고 소멸자는 객체 수명 종료의 정리에 연결된다.
  • 중괄호 블록 안의 자동 객체와 동적으로 할당한 객체는 수명 관리가 다르다.
  • 아래 Trace 프로그램은 C++20 규칙으로 예상 순서만 계산했다.

학습 목표

  • 생성 완료와 블록 종료의 소멸 순서를 추적한다.
  • 전체 객체와 멤버의 정리를 구별한다.
  • 표준 자원 소유 멤버로 정리 책임을 표현한다.

쓰기 전에 유효하게 만들기

생성자는 클래스 이름을 사용하고 반환 타입을 쓰지 않는다. Counter의 생성자는 초기값을 받아 검사한다. 유효하지 않은 값에서 예외를 던지면 정상적인 완성 객체를 얻었다고 볼 수 없다. 호출자는 성공·실패의 결과를 구분해야 하며 실패한 객체를 계속 정상 사용한다고 생각하지 않는다.

std::vector나 std::string처럼 자원을 소유하는 멤버를 사용하면 보통 그 멤버의 소멸이 정리를 담당한다. 직접 소유하는 원시 포인터를 대충 복사하고 delete하는 방식보다 소유 관계를 타입에 표현한다. 정리해야 할 것이 없고 멤버들이 스스로 정리하면 사용자 소멸자를 억지로 쓰지 않아도 된다.

괄호를 닫을 때의 역순

정상적으로 블록을 떠나는 아래 예제에서 a를 먼저 만들고 b를 나중에 만든다. 안쪽 블록이 끝나면 b가 사라지고 바깥 블록 끝에서 a가 사라진다. 이는 자동 객체의 범위 기반 수명 추적이다. 객체 이름이 가려지거나 참조를 넘긴다고 수명이 자동으로 연장되는 것은 아니다.

소멸자 ~Trace()는 인수를 받지 않고 반환 값을 돌려주지 않는다. 아래 출력은 관찰용 교육 장치다. 실제 정리 코드를 쓸 때는 예외 처리 중 또 다른 예외가 밖으로 나가는 문제도 고려하며 소멸자에서 실패를 던지는 설계를 피한다.

#include <iostream>
struct Trace {
    int id;
    explicit Trace(int x) : id(x) { std::cout << "+" << id << " "; }
    ~Trace() { std::cout << "-" << id << " "; }
};
int main() {
    Trace a(1);
    { Trace b(2); }
}

완성된 부분과 전체 객체

클래스의 소멸자 본문이 끝난 뒤에도 멤버와 기반 객체의 정리가 이어진다. 선언 순서로 만들어진 멤버는 역순으로 소멸한다. 상속 없는 본문만 보고 멤버 자원이 아직 남는지 추적할 수 있어야 한다.

생성 도중 예외가 나면 이미 완성된 하위 객체는 정리되지만 완성되지 못한 전체 객체의 일반 소멸자가 실행되었다고 말하면 안 된다. 외부 자원을 생성자 안에서 직접 획득했다면 완성된 자원 소유 멤버가 이를 책임지도록 설계한다. 이 단원은 실제 파일이나 장비를 열어 보지 않았다.

중간 과정을 따라가는 예제

Trace 예제에서 정상 종료 때 +와 -의 순서를 구하고 각 이벤트의 블록을 표시하라.

  1. a(1)를 생성하여 +1을 기록한다.
  2. 안쪽 b(2)를 생성하여 +2를 기록한다.
  3. 안쪽 블록 종료에서 b 소멸, -2를 기록한다.
  4. main 블록 종료에서 a 소멸, -1을 기록한다.

예상 출력 순서 +1 +2 -2 -1. 이는 종이 수명 추적이며 실제 콘솔 로그가 아니다.

종이와 본문으로 직접 해보기

안쪽 블록을 { Trace b(2); Trace c(3); }로 바꾸면 순서를 적어라.

힌트 보기

같은 블록에서는 나중에 완성된 자동 객체부터 정리한다.

풀이 보기

예상 순서는 +1 +2 +3 -3 -2 -1이다. c와 b의 종료는 같은 블록이지만 선언·생성 순서의 역순이며 a는 바깥 블록까지 살아 있다.

오해와 반례

생성자 중간에 실패하면 항상 전체 객체의 소멸자가 정리해 준다.

전체 객체가 완성되지 않았으면 그 객체의 일반 소멸자 실행을 기대할 수 없다. 이미 완성된 멤버가 자기 자원을 정리하게 만드는 설계가 필요하다. 첫 멤버 완성 후 둘째 멤버 생성 실패가 반례다.

자기점검

소멸자에 반환 타입 int를 붙일 수 있는가?

답과 이유 보기

없다.

소멸자의 선언 형태는 일반 반환 함수와 다르다.

자동 객체를 먼저 만들면 같은 블록에서 먼저 소멸하는가?

답과 이유 보기

일반적으로 정상 블록 종료에서는 역순이다.

a/b/c의 + 순서와 - 순서를 분리해 읽는다.

vector 멤버가 있으면 꼭 직접 delete해야 하는가?

답과 이유 보기

아니다.

소유 멤버가 자기 정리를 수행한다. 별도 원시 자원 소유 여부를 구분해야 한다.

한 단계 더

멤버 두 개를 가진 상속 없는 객체의 생성·소멸 사건표를 그리자. 정상 종료와 둘째 멤버 생성 실패를 분리하고 실제 예외 프로그램을 실행한 것으로 기록하지 않는다.

소단원 6.3

member 초기화 순서

초기화 목록을 거꾸로 쓰면 멤버도 거꾸로 만들어질까?

준비 개념과 학습 목표

준비 개념

  • 멤버 선언은 클래스 정의 안의 순서이고 초기화 목록은 생성자 뒤 콜론에 쓴 목록이다.
  • 초기화는 생성 과정이며 생성자 본문 안의 대입과 다르다.
  • 예제는 상속 없는 C++20 객체이고 실제 컴파일하지 않았다.

학습 목표

  • 초기화 목록 표기와 실제 초기화 순서를 구별한다.
  • 앞 멤버에 의존하는 값이 안전한 순서를 점검한다.
  • 초기화하지 않은 값을 읽는 예제를 숫자 결과로 단정하지 않는다.

선언 순서가 기준이다

상속 없는 아래 Pair의 비정적 멤버는 base_가 먼저 선언되고 next_가 다음에 선언된다. 목록에서 next_를 먼저 써도 실제로는 base_를 먼저 초기화한다. 혼동을 줄이려면 목록도 선언 순서에 맞춰 쓰는 편이 좋다.

상속을 포함한 일반 규칙에는 기반 객체의 순서도 들어가지만 여기서는 멤버 두 개와 본문에 집중한다. 멤버 초기화가 끝난 다음 생성자 본문이 실행되므로, 본문에서 base_를 100으로 대입해도 이미 계산된 next_가 자동으로 다시 계산되지는 않는다.

class Pair {
    int base_;
    int next_;
public:
    explicit Pair(int n) : next_(base_ + 1), base_(n) {}
    int base() const { return base_; }
    int next() const { return next_; }
};
// Pair p(4);  // 종이 예상: base()==4, next()==5

이미 만들어진 값만 읽기

이 예제의 base_+1은 이미 초기화된 base_를 읽으며 작은 입력 4에서는 int 범위를 넘지 않는다. 반대로 next_를 먼저 선언하고 next_(base_+1)을 그대로 쓰면 base_가 아직 초기화되지 않은 시점의 값을 읽는 문제가 된다. “목록 뒤에서 base_(n)를 먼저 적으면 해결”이라고 결론 낼 수 없다.

초기화하지 않은 값 읽기에는 임의의 출력 숫자를 붙이지 않는다. 최신 공개 초안에는 C++20 이후 용어·규칙도 들어 있으므로 이 강의는 그 차이를 섞어 특정 오류 출력이 보장된다고 설명하지 않는다. 의존하는 멤버의 선언을 바로잡거나 전달 인수 n으로 직접 next_를 계산하는 설계를 비교한다.

초기화와 대입의 차이

const 데이터 멤버와 참조 멤버 등은 생성 시 초기화를 요구한다. 생성자 본문에서 나중에 값을 집어넣는 대입으로 바꿀 수 없는 경우가 있다. 클래스 타입 멤버도 먼저 생성된 뒤 대입되는 방식과 처음부터 원하는 값으로 생성되는 방식이 서로 다른 작업이다.

멤버 사이 의존성이 있으면 선언 순서, 인수 범위, 초기화 식을 함께 표로 적는다. 작은 교육값에서는 정수 계산이 안전해도 n이 int의 최댓값이면 n+1을 그대로 계산하는 설계는 범위를 추가로 제한해야 한다. 이 단원의 입력 4와 7은 안전한 범위로 고정한다.

중간 과정을 따라가는 예제

Pair p(4)의 목록 표기와 실제 사건표를 나누어 base()/next() 예상 반환을 구하라.

  1. 목록의 글자 순서는 next_ 식, base_ 식이다.
  2. 실제 비정적 멤버 순서는 클래스 선언의 base_, next_다.
  3. base_=4를 초기화하고 next_=base_+1=5를 초기화한다.
  4. 빈 생성자 본문 뒤 완성 객체에서 base()=4, next()=5를 예상한다.

실제 순서 base_→next_→본문, 예상 반환 4와 5. 목록 위치는 이 멤버 순서를 바꾸지 않는다.

종이와 본문으로 직접 해보기

정상 선언 순서에서 n=7로 만들고 생성자 본문에 base_=100을 추가하면 두 반환은? 이어 멤버 선언만 거꾸로 바꾼 경우 안전성을 판단하라.

힌트 보기

next_는 초기화 때 한 번 계산한 int 값이다. 아직 초기화하지 않은 값을 읽는 경우는 숫자를 만들지 않는다.

풀이 보기

정상 선언에서는 base_=7, next_=8 초기화 후 본문 대입으로 base_=100이 되어 반환 100과 8이다. 선언만 역전하면 next_ 초기화가 base_의 초기화보다 앞서므로 안전하지 않은 초기화 의존성이다. 그 경우 8이라는 고정 결과를 주장하지 않는다.

오해와 반례

초기화 목록에서 먼저 쓴 멤버가 언제나 먼저 초기화된다.

Pair에서 목록 첫 next_보다 선언 첫 base_가 먼저 초기화된다. 목록을 잘 읽어도 선언 순서를 확인하지 않으면 의존성을 잘못 판단할 수 있다.

소단원 6.4

invariant와 책임

조건을 검사하는 줄 하나가 객체의 모든 기능을 지킬 수 있을까?

준비 개념과 학습 목표

준비 개념

  • Counter의 유효 상태는 0≤value_≤10이다.
  • 사전조건은 호출 전에 필요한 조건이고 사후조건은 호출 후 보장이다.
  • 불변조건을 유지하는 증명과 실제 테스트는 다른 증거다.

학습 목표

  • 생성·성공·실패 분기로 불변조건 유지 논증을 나눈다.
  • 사용자와 클래스의 책임을 계약에 적는다.
  • 공개 참조·새 연산·동시성으로 증명 범위가 변함을 설명한다.

상태의 약속을 한 문장으로 쓰기

불변조건 I(v)를 0≤v≤10이라 쓰면 모든 유효 Counter 상태에 같은 질문을 할 수 있다. 생성자는 x가 이 범위를 벗어나면 객체를 완성시키지 않고, 범위 안이면 I를 세운다. 범위 조건은 사람이 설명한 설계 계약이며 private 키워드가 자동으로 생성한 수학 명제는 아니다.

불변조건은 모든 내부 줄의 순간을 같은 방식으로 제한한다는 단순 구호보다 공개 연산 경계의 약속으로 읽는다. 연산 내부에서 여러 필드를 잠시 갱신할 수 있어도 외부에 유효 객체를 돌려주는 시점에는 계약을 지켜야 한다. 예외나 별칭 때문에 외부에서 중간 상태를 볼 수 있다면 그 가능성도 설계에 포함해야 한다.

세 분기로 검산하기

앞 소단원의 add는 음수이거나 n>10−v이면 값을 바꾸지 않아 I가 유지된다. 성공 분기에서는 0≤n≤10−v이므로 0≤v+n≤10이다. 실패 분기와 성공 분기를 따로 논증하면 허용되지 않은 요청이 음수 상태나 11을 만들지 않는 이유가 보인다.

이 논증의 전제는 연산 시작에 I가 참이고 같은 객체를 다른 스레드가 동시에 바꾸지 않으며 외부 가변 참조가 표현을 바꾸지 않는다는 것이다. 그 전제를 빼고 무조건 안전하다고 주장하지 않는다. 동시 접근·자원 정리·예외 보장은 각각 추가 계약과 검토가 필요하다.

I(v) : 0 <= v <= 10
생성 성공: 0 <= x <= 10 -> I(x)
거부: n < 0 또는 n > 10-v -> v 유지 -> I(v)
성공: 0 <= n <= 10-v -> 0 <= v+n <= 10 -> I(v+n)

책임을 통로마다 다시 묻기

사용자는 실패 반환을 읽고 다음 행동을 정한다. 클래스는 문서에 약속한 거부·상태 유지·성공 결과를 구현한다. 사용자에게 “항상 알아서 올바른 값만 넣으라”고 말하면서 공개 API가 어떤 입력을 거부하는지 숨기면 오류 책임을 이해하기 어렵다.

새 reset(n)을 만들거나 int&로 내부 값을 내보내면 기존 증명이 덮는 통로가 늘어난다. reset은 n 검사와 실패 상태 계약이 필요하고, 외부 가변 참조는 사용자가 검사 없이 표현을 바꾸는 통로가 된다. 공개 기능을 추가할 때 계약·증명·테스트 항목을 같이 갱신한다.

중간 과정을 따라가는 예제

I가 참인 v=8에서 add(2)와 이어 add(1)을 판정하고, 일반 성공 분기의 부등식 논증을 이 숫자에 대입하라.

  1. v=8의 여유는 2이고 n=2는 0≤2≤2이므로 성공한다.
  2. 새 값은 10이며 0≤10≤10이다.
  3. 다음 n=1은 여유 0보다 커 거부한다. 값 10이 그대로 남는다.
  4. 일반 부등식의 하한은 v+n≥0, 상한은 n≤10−v에서 v+n≤10으로 얻는다.

첫 요청 true·10, 다음 false·10이며 두 공개 연산 후 모두 I가 참이다.

종이와 본문으로 직접 해보기

reset(n)이 value_=n만 한다면 n=-3과 n=12에서 I가 유지되는지 판단하고 실패 상태를 보존하는 계약을 적어라.

힌트 보기

0≤n≤10 검사와 거부 시 기존 v 보존을 연결한다.

풀이 보기

무검사 reset(-3)은 하한을, reset(12)은 상한을 깨뜨린다. 수정 계약은 범위 밖 n을 거부해 이전 값을 보존하고 범위 안에서는 n을 저장하는 것이다. 생성자만 검사해 놓은 상태로 새 공개 통로를 추가하면 충분하지 않다.

오해와 반례

한 번 생성자가 검사했으면 이후 모든 멤버 함수도 자동으로 조건을 지킨다.

무검사 reset과 가변 참조 반환은 생성 후 상태를 깨뜨리는 통로다. 생성 성공은 출발점일 뿐 각 연산의 유지 논증이 따로 필요하다.
