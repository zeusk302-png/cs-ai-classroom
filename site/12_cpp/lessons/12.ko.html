function·class template

같은 템플릿의 값 멤버가 언제는 독립 값이고 언제는 관찰 창일까?

새 Slot은 template<class T> struct Slot{T value;};다. 템플릿은 value의 형식을 바꾸지만 그 형식의 복사 의미까지 같은 것으로 만들지는 않는다. Slot<int>의 int는 값이고 Slot<int*>의 포인터도 값이지만 그 포인터가 가리키는 int를 자동 복제하지 않는다. 이 단원은 명시한 템플릿 인수만 사용하여 class template argument deduction은 요구하지 않는다.

수명 책임을 템플릿 이름으로 추측하지 말고 대입되는 T의 계약에서 읽는다. Slot<std::string>은 문자열의 독립 복사본을 소유할 수 있다. Slot<std::string_view>은 기존 문자 저장 공간의 주소와 길이를 빌린다. 두 Slot 모두 자기 멤버를 가지지만 뒤의 창은 대상 문자열의 수명을 늘리지 않는다. 각 문제는 별도 초기 상태에서 시작하고 문자열 복사는 성공한다고 가정한다.

먼저 확인할 개념
  • 복사와 대입

    멤버 값 복사와 가리키는 대상의 복제를 구별한다.

  • string과 string_view

    소유하는 문자열과 빌린 문자 창의 수명 계약을 적용한다.

타입을 매개변수로 둔다

template<class T>는 T라는 타입 매개변수를 선언한다. 같은 자리에 typename T를 써도 이 문맥에서는 같은 뜻이다. choose_small<int>와 choose_small<double>은 한 함수 템플릿에서 서로 다른 타입 인자로 만든 함수 specialization이다.

템플릿은 실행 중 임의 타입으로 변하는 변수를 만들지 않는다. 각 호출에서 사용할 구체적인 타입과 요구 연산이 정해진다. 아래 함수는 T 두 값을 비교하고 선택한 값을 T로 반환할 수 있어야 한다.

함수와 저장 구조를 함께 설계한다

함수 템플릿은 연산을 정의하고 class template은 타입에 맞춘 저장 구조와 멤버를 정의한다. Box<int>는 int value를, Box<double>은 double value를 가진 별개 타입이다. 물리 메모리 크기나 바이너리 개수는 이 예제에서 측정하지 않는다.

template<class T> struct Box { T value; };에 Box<int>{4}처럼 초기 값을 준다. 이 단순 aggregate에서는 초기화가 value를 설정한다. 모든 클래스의 생성 규칙이나 모든 T의 연산을 보장하는 구조는 아니다.

generic이라는 이름에도 조건이 있다

choose_small은 a < b가 유효하고 bool 조건으로 쓸 수 있어야 한다. 비교가 없는 사용자 타입을 넣으면 그 연산이 필요한 시점에 오류가 될 수 있다. 같은 템플릿 문법이 모든 타입을 허용한다는 뜻은 아니다.

이 함수는 값으로 반환하므로 함수의 지역 매개변수에 대한 참조를 반환하는 문제를 피한다. 반대로 const T& 반환과 값 매개변수를 섞어 지역 객체 참조를 내보내면 수명 문제가 생긴다. generic 코드에도 이전 수명 규칙이 그대로 적용된다.

같은 템플릿의 값 멤버가 언제는 독립 값이고 언제는 관찰 창일까?
타입·호출 조건결과 또는 검사 단계보존해야 할 계약

int x=4; Slot<int> a{x}; auto c=a

c.value와 a.value는 서로 다른 int

c.value=9여도 a.value=4

Slot<int*> a{&x}; auto c=a

두 포인터 값은 같은 x를 가리킴

*c.value=9이면 x=9

string s="cat"; Slot<string> a{s}

문자열 값 복사

s[0] 수정이 a를 바꾸지 않음

같은 s에서 Slot<string_view> v{s}

길이 3의 빌린 창

주소 유효성·s 수명이 별도 전제

행의 auto c=a는 Slot 자체의 복사다. 첫 두 행의 int 값과 int* 값은 모두 복사되지만 화살표 뒤 대상의 개수가 다르다. 문자열 행은 s가 살아 있고 재할당 없는 원소 수정만 비교한다.

중간 과정을 따라가는 예제

다음 C++20 이상 예제를 template_demo.cpp에 저장하는 후속 실습을 할 수 있으나 여기서는 컴파일·실행하지 않고 손 추적한다. 

#include <iostream>
template<class T> T choose_small(T a, T b) {
    return a < b ? a : b;
}
template<class T> struct Box { T value; };
int main() {
    Box<int> a{choose_small<int>(7, 4)};
    Box<double> b{choose_small<double>(2.5, 1.5)};
    std::cout << a.value << " " << b.value << "\n";
}

  1. 첫 호출에서 T=int이며7<4는 거짓이라4를 반환해 a.value에 저장한다.

  2. 두번째 T=double이며2.5<1.5는 거짓이라1.5를 반환한다. 작은 값은 정확히 표현 가능한 이진 분수라 이 예제의 소수 비교가 단순하다.

  3. 예상 출력은4 1.5이다. Box<int>와 Box<double>은 다른 타입이며 결과 객체가 서로 바뀌지 않는다.

a.value=4, b.value=1.5이다. 하나의 템플릿 정의에 서로 다른 타입 인자를 적용했다.

조건을 바꾸어 비교하기

같은 Slot 복사의 다른 영향

첫 비교는 x=4,Slot<int> a{x},c=a에서 c.value=9다. 둘째는 새 x=4,Slot<int*> a{&x},c=a에서 *c.value=9다.

  1. 첫째 c의 int 멤버만 9가 되고 a의 멤버와 x는 4다.

  2. 둘째 복사된 포인터가 같은 x를 가리켜 x가 9가 된다.

첫째 x/a/c는 4/4/9다. 둘째 x와 두 역참조 값은 모두 9다.

비교할 점

base Box의 값 저장에 대상 공유 여부를 추가한다.

원본 수정과 소멸의 두 경계

s="cat"에서 Slot<string> own{s},Slot<string_view> view{s}를 만든다. s[0]='b' 뒤 값을 읽고, 별도 s 소멸 뒤 접근 가능성을 분류하라.

  1. 원소 수정은 s를 bat으로 만들고 주소·길이는 유지한다. own은 cat, view는 bat이다.

  2. s가 소멸하면 own의 복사 문자열은 자기 수명 동안 유효하지만 view의 대상 수명이 끝난다.

수정 뒤 own="cat",view="bat"다. 소멸 뒤 view를 정상 문자열로 읽는 계약은 없다.

비교할 점

const 관찰과 대상 불변성, 멤버 존재와 대상 수명을 분리한다.

종이와 본문으로 직접 해보기

별도 Box<int> c{choose_small<int>(9,9)}를 만들고 a.value를8로 바꾸면 c.value는? 반환식이 같은 값에서 어느 매개변수를 고르는가?

힌트 보기

a<b는 같은 값에서 거짓이다. 객체는 별도 초기화되었다.

풀이 보기

c.value는9를 유지하며 a.value만8이다. 동일값 비교에서는 b를 선택하지만 값은 둘 다9다. 값 객체 사이에 자동 별칭이 생기지 않는다.

오해와 반례

템플릿은 타입 검사를 없애고 Box<int>와 Box<double>을 같은 타입으로 만든다.

각 specialization은 구체 타입 규칙과 요구 연산을 지킨다. 두 Box는 별개 타입이고 연산을 지원하지 않는 T는 해당 사용을 만족하지 못한다.

두 인자에서 타입을 합의할지 한 인자에서 먼저 정할지 설계할 수 있을까?

C++20의 <type_traits>를 사용하여 template<class T> T second_as(T first,std::type_identity_t<T> second){return second;}를 생각한다. first의 값은 결과 계산에 사용하지 않지만 그 타입이 T를 결정하는 증거다. type_identity_t<T>는 T라는 타입을 뜻하면서 이 자리에서는 T 추론에 참여하지 않는다. 먼저 정해진 타입으로 둘째 값을 전달할 변환이 허용되는지를 뒤에 검사한다.

base smaller(T,T)는 두 인자가 같은 T를 요구하여 혼합 int/double 추론이 충돌했다. 새 함수는 공통 타입을 자동 발명하지 않고 첫 인자 쪽 타입을 정책으로 정한다. 따라서 인자 순서를 바꾸면 허용되는 변환과 결과 타입이 달라질 수 있다. 여기의 double 2.75와 int 5는 모두 안전한 작은 범위이며 double에서 int로 변환하면 소수부가 버려진다. 일반 입력에는 표현 범위 조건도 필요하다.

  • 식의 타입과 값 범주

    결과 타입과 같은 수치의 관찰을 별도로 기록한다.

인자마다 타입을 맞춰 본다

template<class T> T smaller(T a,T b)에서 smaller(8,3)은 두 인자의 int로부터 T=int를 얻는다. smaller(8,3.5)는 첫 인자에서 int, 둘째에서 double을 요구해 이 단일 T 템플릿의 추론이 실패한다.

컴파일러가 모든 혼합 인자를 자동으로 double로 바꾸는 일반 규칙은 아니다. smaller<double>(8,3.5)는 T를 명시했으므로8을 double로 전달하고 double 결과를 얻는다. 어떤 변환을 허용할지는 인터페이스 설계의 일부다.

값과 참조에서 보존하는 정보가 다르다

값 매개변수 T x에 const int를 전달하면 T를 int로 추론하는 것이 기본이다. 복사해서 받은 값의 최상위 const는 원래 객체의 const와 다른 정보다. T& x에서는 원래 객체를 참조하므로 const를 보존한 T=const int가 될 수 있다.

배열을 T x의 값 매개변수로 전달하면 배열에서 포인터로 조정되어 T를 요소 포인터 타입으로 추론한다. 배열 길이를 알고 싶으면 const T (&a)[N] 같은 배열 참조 형식으로 크기 N을 따로 받을 수 있다. 아래 예제는 완벽 전달이나 rvalue reference를 다루지 않는다.

호출 결과를 타입 증거로 사용하지 않는다

반환값을 double 변수에 저장한다고 smaller(8,3.5)의 인자 추론 충돌이 해결되지 않는다. 일반적인 이 함수 호출의 T는 함수 인자에서 추론하며 주변 결과 변수의 타입이 공통 T를 만들어 주지 않는다.

호출 지점의 실제 타입, 매개변수 P, 추론한 T를 표로 적는다. 추론 뒤 필요한 변환과 본문 연산도 별도로 확인한다. 타입이 정해졌다는 사실은 모든 본문 연산이 유효하다는 결론이 아니다.

instantiation와 오류 읽기

템플릿 정의가 읽히는 것과 특정 타입으로 본문을 확인하는 시점은 어떻게 다를까?

준비 개념과 학습 목표

준비 개념

  • 템플릿 타입 대입

  • 멤버 함수

  • 컴파일 진단과 실행 실패

학습 목표

  • 구체 타입 대입 후 필요한 연산을 확인한다.

  • 사용하지 않은 멤버 본문과 필요한 본문을 구별한다.

  • 진단을 호출 지점·타입·원인 연산으로 나눠 읽는다.

객체 하나를 만들었다고 사용하지 않은 모든 연산까지 검증됐을까?

새 Meter는 template<class T> struct Meter{T value; int width()const{return sizeof(T);} T merged()const{return value+value;}}다. 교육 입력 Plain은 struct Plain{int n;};이며 +가 없다. T는 int 또는 Plain 같은 완전한 작은 객체 타입만 사용하고 width의 sizeof 결과는 int로 표현 가능하다고 가정한다. 어떤 ABI 바이트 수인지는 정하지 않는다.

Meter<Plain>을 완전한 객체로 만들면 value의 형식과 멤버 선언이 필요하다. 그러나 호출하지 않은 merged 본문을 그 사실 하나로 인스턴스화했다고 결론 내리지 않는다. width를 호출하려면 그 본문을, merged를 호출하려면 + 연산을 확인한다. 오류를 템플릿 파일의 마지막 줄로만 읽지 말고 사용자 호출→구체 T→필요한 본문의 연산 순서로 연결한다.

먼저 확인할 개념
  • 멤버와 공개 호출 계약

    객체 상태와 선택해서 호출한 연산의 요구를 나눈다.

  • 완료된 객체의 수명

    사용되지 않은 함수 본문과 완성된 객체를 혼동하지 않는다.

필요한 구체 정의를 확인한다

instantiation은 템플릿에 구체 인자를 적용해 필요한 specialization을 만드는 과정이다. 템플릿의 명백한 문법 오류까지 사용 시점에만 발견된다는 뜻은 아니다. 타입에 의존하는 연산은 구체 타입을 알 때 유효성을 확인할 수 있다.

함수 호출에는 해당 함수 본문이 필요하고 클래스 객체에는 완전한 클래스 정의가 필요하다. 클래스가 구체화된다고 사용하지 않은 모든 일반 멤버 함수 본문이 한 번에 필요해지는 것은 아니다. 예제는 명시 specialization이나 별도 빌드 예외를 쓰지 않는다.

작은 클래스에서 단계별로 본다

Probe<T>는 T value와 value + value를 반환하는 twice 멤버를 가진다. Probe<int>에는 int 덧셈이 있어 twice를 호출할 수 있다. 더하기가 없는 Plain을 멤버로 저장하는 객체 자체와 twice 호출은 서로 다른 요구다.

Plain은 단순 int n을 가진 구조체로 초기화·복사가 가능하지만 operator+를 정의하지 않는다. Probe<Plain> p{{5}}의 저장은 가능해도 p.twice()로 Plain+Plain을 요구하면 이 사용에서 오류다. 타입 이름의 존재와 연산 지원을 구별한다.

긴 오류에서 세 단서를 찾는다

진단을 읽을 때 첫째 어떤 호출에서 필요한 정의가 생겼는지, 둘째 T에 어떤 타입이 들어갔는지, 셋째 어떤 표현을 만들지 못했는지 적는다. exact 오류 문구와 줄 순서는 컴파일러마다 다를 수 있다.

오류를 없애려 무조건 캐스트하거나 지원되지 않는 연산을 추가하기보다 요구한 의미가 맞는지 검토한다. Plain의 n 합계를 원하면 n을 합하는 별도 함수를 설계할 수 있다. 템플릿의 조건을 문서 또는 다음 소단원의 concept로 드러내는 방법도 있다.

표의 가능은 해당 멤버·표현식만 고려한 언어 판단이다. 오류 행을 실행하여 예외가 발생했다고 기록하지 않는다. 크기 행은 바이트 수를 종이에 임의로 4로 정하지 않는다.

중간 과정을 따라가는 예제

독립 사례의 성립 여부를 손 분석하라. 

template<class T> struct Probe {
    T value;
    T twice() const { return value + value; }
};
struct Plain { int n; };
// A: Probe<int> a{5}; int x = a.twice();
// B: Probe<Plain> b{{5}};
// C: auto y = b.twice();

C는 의도적인 오류 사례라 정상 예제에 활성화하여 실행했다고 주장하지 않는다.

  1. A는 T=int로 value5이고5+5=10을 반환한다. 작은 합은 int 범위 안이다.

  2. B는 Plain value를 저장하는 객체이고 Plain의 n=5다. twice 본문을 필요한 호출이 아직 없다.

  3. C를 B 뒤 활성화하면 value+value가 Plain+Plain이다. operator+가 없어 필요한 twice 정의의 사용이 성립하지 않는다. y의 런타임 값을 예측하지 않는다.

호출 가능한 read와 안전한 센서 계약을 어떤 층에서 검사할까?

C++20 <concepts>를 사용한 새 조건 ReadInt는 template<class T> concept ReadInt=requires(const T& t){{t.read()} noexcept -> std::same_as<int>;};다. read 표현식이 const 객체 경로에서 유효한지, 잠재적으로 던지는지, decltype((t.read()))가 정확히 int인지 순서대로 확인한다. ByValue는 int read()const noexcept, ByRef는 const int& read()const noexcept, Mutable는 int read()noexcept, Throwing은 int read()const 선언만 가진다.

새 API의 의미 계약은 read 값이 0..100이라는 별도 약속이다. Liar는 int read()const noexcept{return -1;}이라 ReadInt는 만족하지만 의미 계약은 어긴다. requires 속의 t는 런타임 센서를 생성하거나 읽는 객체가 아니다. 조건 검사는 형식·식의 일부 성질을 검사하며 모든 입력의 상태 불변성, 값 범위, 실제 장치 정확성까지 증명하지 않는다.

먼저 확인할 개념
  • const 참조 접근

    조건 속 const T&가 허용하는 멤버 호출을 확인한다.

  • 값과 비교 계약

    문법에 맞는 표현식과 사용자가 요구한 의미 관계를 구별한다.

이름 있는 타입 조건을 붙인다

C++20의 concept는 템플릿 인자에 대한 제약에 이름을 붙인다. 아래 ClosedPlus<T>는 T 값 둘을 더하는 표현이 유효하고 결과 타입이 정확히 T인지 검사한다. 이름은 표준 concept가 아닌 자체 정의다.

template<ClosedPlus T>는 이 조건을 만족하는 T로 함수 후보를 제한한다. 같은 조건을 template<class T> requires ClosedPlus<T> 형태로 적을 수도 있다. 예제는 <concepts>의 std::same_as를 쓰며 C++20 이상으로 읽는다.

검사하는 식을 실제로 실행하지 않는다

requires(T a,T b) { { a+b } -> std::same_as<T>; }에서 a/b는 요구 표현을 기술하기 위한 이름이다. 이 검사 때문에 실제 숫자 두 개를 더하거나 객체가 생성되었다고 생각하지 않는다. compound requirement는 표현의 유효성과 결과 타입 조건을 확인한다.

단순 요구 a+b;만 쓰면 결과 타입이 T라는 조건은 없다. 아래 char 사례는 char의 모든 값을 int가 표현할 수 있는 구현을 가정한다. 이때 char+char는 정수 승격으로 int 결과를 만들어 단순 더하기는 유효해도 ClosedPlus<char>에는 맞지 않는다. 그 가정 밖에서는 unsigned int로 승격될 수 있으나 결과가 char가 아니라는 결론은 같다. int와 double의 같은 타입 덧셈 결과는 각 타입이다.

형식 조건과 의미 약속을 나눈다

ClosedPlus<int>가 참이어도 INT_MAX+1 같은 signed int 범위 초과를 안전하게 만들어 주지는 않는다. 사용자 타입의 operator+가 기대한 합을 반환한다는 의미도 이 조건만으로 증명하지 않는다. 값을 제한하거나 별도 검사·속성 검증이 필요하다.

제약을 도입하면 지원하지 않는 타입이 본문 깊은 곳까지 들어가기 전에 후보 조건에서 배제될 수 있다. 실제 오류 메시지가 얼마나 친절한지는 컴파일러와 환경에 따라 다르므로 여기서는 성능·진단 실험 결과를 주장하지 않는다.

중간 과정을 따라가는 예제

다음 C++20 예제를 손 분석하라. 

#include <concepts>
#include <iostream>
template<class T> concept ClosedPlus = requires(T a, T b) {
    { a + b } -> std::same_as<T>;
};
template<ClosedPlus T> T add_same(T a, T b) { return a + b; }
struct Plain { int n; };
int main() {
    std::cout << add_same(2, 3) << " "
              << add_same(1.5, 2.5) << "\n";
    // add_same(Plain{1}, Plain{2}); // unsupported
}

  1. T=int는 int+int의 결과int라 조건을 만족한다. 작은 입력2+3의 예상값5다.

  2. T=double은 double+double의 결과double로 조건을 만족한다. 정확히 표현 가능한1.5+2.5=4.0이고 기본 출력에서는4가 예상된다.

  3. Plain에는 operator+가 없어 ClosedPlus<Plain>은 거짓이다. 해당 주석을 활성화한 호출은 이 함수 후보의 제약을 만족하지 않으며 실행 값은 없다.

정상 두 호출의 예상 출력은5 4다. Plain 호출은 조건 불충족 사례이며 실제 컴파일 로그는 아니다.

조건을 바꾸어 비교하기

값 반환과 참조 반환 조건을 구별

ByValue와 ByRef의 ReadInt 결과를 분류하고 ByRef를 자동 int 복사하면 해결된다는 주장을 평가하라.

  1. ByValue의 호출 식은 int prvalue라 decltype((E))가 int다.

  2. ByRef의 호출 식은 const int lvalue라 decltype((E))가 const int&다.

ByValue만 참이다. 요구 자체는 자동 복사한 뒤 타입을 검사하지 않는다.

비교할 점

base ClosedPlus의 결과 타입 검사에 값 범주와 참조의 차이를 더한다.

형식 검사 통과와 범위 계약 실패

Liar의 ReadInt와 read()==-1이 새 센서 API에 적합한지 각각 적어라.

  1. read는 const·noexcept·int 조건을 모두 만족한다.

  2. -1은 요구한 0..100 밖이다.

형식 조건은 참이고 의미 계약은 실패한다.

비교할 점

concept 이름이 의미의 전체 증명을 대신하지 않음을 반례로 확인한다.

종이와 본문으로 직접 해보기

char의 모든 값을 int가 표현할 수 있는 구현에서 ClosedPlus<char>와 단순 requires(T a,T b){ a+b; }의 char 조건을 비교하라. ClosedPlus<int>가 참이면 모든 두 int 합이 안전한지도 설명하라.

힌트 보기

연산 결과 타입과 입력값 범위는 별도다. char는 정수 승격된다.

풀이 보기

이 구현에서는 char 더하기 자체는 유효하므로 단순 조건은 참이지만 결과가 int라 ClosedPlus<char>는 거짓이다. char의 전체 범위를 int가 표현하지 못해 unsigned int로 승격하는 구현에서도 ClosedPlus<char>는 거짓이다. int 조건이 참이어도 결과가 범위를 넘으면 signed overflow 위험이 남는다.

오해와 반례

concept가 통과하면 모든 입력에서 올바른 의미·수명·성능이 증명된다.

제약은 명시한 타입·표현 조건을 확인한다. 입력 범위, 수명, 수학적 의미와 성능은 별도 계약·검증이다.

다른 문제에 적용하기

형식의 증거와 런타임 책임을 분리한 데이터 읽기 설계

각 비교는 별도 초기 상태다. (A) string s="cat"에서 Slot<string> own{s},Slot<string_view> view{s}를 만든 뒤 s[0]='b'를 수행하고 두 값을 비교하라. s 소멸 뒤의 접근도 분류하라. (B) second_as(3,2.75)와 second_as(2.75,3)의 T와 반환값을 구하라. (C) Meter<Plain>{{4}}의 width 호출과 merged 호출을 분리하라. (D) 위 ReadInt와 0..100 의미 계약에 대해 ByRef/Throwing/Liar의 실패 층을 분류하고 Liar를 거절하는 후속 경계를 설계하라. 선언·작은 범위·정상 복사 성공 전제는 위와 같으며 이론 추적이다.

힌트 1

A에서는 T가 소유자냐 창이냐를, B에서는 첫 타입 증거와 뒤 변환을 먼저 적는다.

힌트 2

C에서는 실제 필요한 본문을 표시하고 D에서는 const 호출·noexcept·정확 타입과 반환 범위를 별도 열로 나눈다.

풀이와 답 확인

  1. A의 own은 cat,view는 bat이다. s 소멸 뒤 own은 자기 수명 동안 유효하고 view의 대상 읽기는 유효성을 잃는다.

  2. B의 첫 T=int이며 반환값은 int 2다. 둘째 T=double이며 반환값은 double 3이다.

  3. C에서 width는 sizeof(Plain)에 해당하는 크기만 요구하며 정확 ABI 숫자는 정하지 않는다. merged는 Plain+Plain이 없어 호출을 추가하면 번역 오류다.

  4. D에서 ByRef는 정확 int 대신 const int& 결과라 실패한다. Throwing은 noexcept 조건 실패다. Liar는 ReadInt를 만족하지만 -1로 범위 계약을 어긴다. 값을 한 번 받아 검사하고 후속 상태 변경 전에 거절한다.

템플릿 형식의 증거를 확보한 뒤에도 빌린 대상 수명·손실 변환·사용 본문 요구·반환 범위와 상태 효과를 각각 확인해야 한다.

해결한 뒤 점검할 것

  • 소유 문자열과 관찰 창의 수정·소멸 경계를 값과 함께 설명한다.

  • 두 호출의 T와 반환 타입·값을 위치별로 적는다.

  • 객체 구성·width·merged의 요구를 구별하며 ABI 크기를 만들지 않는다.

  • 형식 실패 세부 층과 Liar의 의미 실패를 구별하고 실제 실행·학생 미수행을 유지한다.
