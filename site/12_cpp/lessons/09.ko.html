소단원 9.1

move constructor·assignment

큰 자료의 소유권을 새 객체로 넘기면 복제 비용을 줄일 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 생성자와 대입

  • 소유권과 RAII

학습 목표

  • 이동 생성과 이동 대입의 대상 수명 차이를 구별한다.

  • 자원 전달과 이전 자원의 정리를 추적한다.

기본 이동이 모든 멤버를 빈 상태로 만들까?

새 구조체 Parcel은 std::unique_ptr<int> p와 int count를 선언 순서대로 가진다. 복사는 금지하고 이동 생성·대입은 default다. p가 가리키는 동적 int를 자원 R이라고 부른다. count는 자료 개수 메타데이터이며 새 불변조건을 count==0이면 p가 비고 count>0이면 p가 존재한다고 정해 보자. 단순한 기본 이동이 이 관계까지 지켜 주는지 살핀다.

unique_ptr의 이동은 손잡이를 넘기지만 int 멤버의 이동은 값을 전달하고 원본 int를 0으로 재설정하지 않는다. 기본 이동은 멤버별 연산을 조합한다. 개별 멤버가 정상 상태여도 클래스 전체의 관계가 깨질 수 있다. count가 별도 관계를 필요로 하지 않는 단순 표식인 경우와 이 새 계약을 구별한다. 할당은 성공하고 서로 다른 객체의 이동만 먼저 다룬다.

먼저 확인할 개념
  • 기본 특별 멤버의 제공 조건

    default 이동과 복사 금지의 정책을 확인한다.

  • unique_ptr의 소유권 전달

    자원 이동 뒤 null 보장을 int 멤버까지 확대하지 않는다.

새 객체 만들기와 기존 객체 바꾸기

이동 생성자는 X(X&&)처럼 새 객체를 초기화하는 역할이다. 이동 대입은 X& operator=(X&&)처럼 이미 존재하는 객체의 상태를 바꾼다. 새 상자를 받는 일과 쓰던 상자의 내용을 교체하는 일을 구별하면 자원 정리 책임을 이해하기 쉽다.

이동은 클래스가 정의한 연산이다. 소유한 동적 자료의 손잡이를 전달하는 설계에서는 큰 자료를 복제하지 않을 수 있다. 모든 member가 int인 형식이라면 이동이 값 복사와 비슷한 비용일 수 있으므로 이동이라는 이름만으로 속도 개선을 단정하지 않는다.

소유권을 표준 구성 요소에 맡기기

아래 Box는 unique_ptr로 하나의 int를 독점 소유한다. 이동 생성과 대입을 default로 두면 member의 이동 연산을 사용한다. 복사를 금지해 한 자원을 두 Box가 동시에 독점 소유한다고 오해하는 상황을 막는다.

원시 포인터를 직접 소유하는 클래스에서는 단순히 포인터 값만 복사하면 이중 해제 위험이 있다. 가능한 한 RAII 구성 요소에 맡기고, 직접 작성할 때는 이전 대상 자원과 전달 뒤 원본 상태를 함께 설계한다.

#include <memory>
#include <utility>
struct Box {
    std::unique_ptr<int> p;
    explicit Box(int n) : p(std::make_unique<int>(n)) {}
    Box(Box&&) noexcept = default;
    Box& operator=(Box&&) noexcept = default;
    Box(const Box&) = delete;
    Box& operator=(const Box&) = delete;
};
Box a(7);
Box b(std::move(a));
Box c(9);
c = std::move(b);

효율에도 클래스의 약속이 필요하다

이 예제의 int 값 7을 가진 자원과 9를 가진 자원은 서로 다른 동적 객체다. b 생성은 a의 소유권을 가져오고, c 대입은 기존 9 자원을 정리한 뒤 7 자원을 가져온다. 원본 a와 b는 null 포인터가 되어 파괴할 수 있다.

noexcept는 이 default 연산과 member의 예외 약속을 살핀 선언이다. 임의의 클래스 이동이 언제나 예외 없이 성공한다고 일반화하지 않는다. 상속과 member의 이동 가능 여부에 따라 기본 이동 연산이 삭제될 수도 있다.

중간 과정을 따라가는 예제

코드의 a,b,c가 소유하는 자원을 순서대로 적어라. 메모리 할당은 성공하고 서로 다른 객체 사이의 이동이라고 가정한다.

  1. a(7) 뒤 a는 자원7을 소유한다.

  2. b(std::move(a))는 이동 생성: b가 자원7, a는 null이다.

  3. c(9)는 별도 자원9를 소유한다.

  4. c=std::move(b)는 이동 대입: c의 자원9를 정리하고 자원7을 가져온다. b는 null이다.

최종 a와 b는 null, c만 자원7을 소유한다. 자원9는 대입 과정에서 정리된다.

조건을 바꾸어 비교하기

정수 멤버는 자동으로 비지 않는다

a는 R/count=3이다. Parcel b(std::move(a)) 뒤 a와 b의 새 관계를 검사하라.

  1. p는 b로 이전되고 a.p는 null이다.

  2. count의 int 값 3은 b에 전달되며 a.count도 3이다.

b는 관계를 만족하지만 a는 null/3으로 새 관계를 위반한다.

비교할 점

base Box에는 이 count 관계가 없어 같은 문제가 나타나지 않는다.

대입 대상의 옛 자원과 원본 메타데이터

a는 R/count=3, c는 S/count=2이고 c=std::move(a)를 한다. 기본 deleter와 서로 다른 객체를 전제한다.

  1. c.p의 옛 S가 정리되고 R을 넘겨받는다.

  2. c.count는 3이고 a는 null/3이다.

S는 정리되며 c는 R/3이다. a의 관계를 별도로 회복해야 한다.

비교할 점

대입은 새 객체를 만드는 사건과 달리 기존 S 정리 책임이 있다.

소단원 9.2

std::move의 의미

move라는 이름의 함수 호출만 하면 객체의 내용이 옮겨질까?

준비 개념과 학습 목표

준비 개념

  • lvalue와 rvalue의 기초

  • 오버로드와 const

학습 목표

  • std::move의 변환과 실제 이동 연산을 구별한다.

  • const 여부와 연산 제공 여부에 따라 선택을 추적한다.

삭제한 이동과 아예 없는 이동은 같은 결과일까?

이 절에서는 세 후보 모형을 비교한다. CopyOnly는 const T& 복사 생성자만 사용자 선언하여 암시적 이동이 없다. Blocked는 그 복사 후보와 T(T&&)=delete를 명시한다. Regular는 복사와 사용 가능한 T(T&&)를 제공한다. 각 호출은 새 원본에서 독립적으로 시작하고 실제 연산 본문은 이론 후보 선택만 다룬다.

std::move는 const를 지우거나 후보 목록을 고치지 않는다. 이동 후보가 아예 없으면 복사가 받을 수 있지만, 더 좋은 후보로 선택된 명시 삭제 이동은 호출 오류를 만든다. 한편 default로 선언했으나 멤버 조건 때문에 삭제된 이동 생성자는 후보에서 무시되는 특별 규칙이 있다. 이 특별 규칙을 모든 =delete에 적용하면 안 된다.

먼저 확인할 개념
  • 오버로드 후보 선택

    먼저 후보를 고르고 선택한 함수의 사용 가능성을 확인한다.

  • const 경로의 제한

    const를 이동 표시로 없애지 않는다는 점을 연결한다.

표현식에 이동 후보라는 표시 붙이기

std::move는 대상을 가리키는 표현식을 이동 연산의 후보로 쓸 수 있는 xvalue로 바꾸는 유틸리티다. 함수 자체가 자원을 복제하거나 해제하거나 원본을 비우는 작업을 수행하는 것은 아니다. 실제 작업은 그 표현식을 받는 생성자나 대입 등의 연산에서 결정된다.

따라서 std::move(a);만 쓰고 결과를 사용하지 않으면 a의 값이 이 호출 때문에 바뀌지는 않는다. 이름과 효과를 분리해 읽어야 불필요한 이동 표시를 추가하는 실수를 줄일 수 있다.

받는 연산이 무엇인지 확인하기

T가 T(const T&)와 T(T&&)를 모두 제공하고 a가 const가 아닌 T라면 T b(std::move(a));에서 보통 이동 생성자가 선택된다. 반면 T에 사용 가능한 이동 생성자가 없고 복사 생성자가 받는 경우에는 복사가 선택될 수 있다. 삭제된 이동 생성자를 명시한 경우 등은 오류가 될 수 있어 무조건 복사 대체라고 말하지 않는다.

const T a에 std::move를 적용하면 const 성질은 없어지지 않는다. const T&&는 보통의 T&& 이동 생성자에 묶을 수 없지만 const T& 복사 생성자는 받을 수 있다. 표시는 이동 후보를 만들 뿐 형식의 제약을 우회하지 않는다.

이름 있는 rvalue 참조도 표현식으로 다시 보기

함수 인자 T&& x는 형식에 &&가 있어도 본문에서 이름 x를 쓰는 표현식은 lvalue다. 전달 대상으로 이동 연산을 원하면 std::move(x)처럼 표현식의 범주를 바꾸어야 한다. 참조 형식과 표현식 범주를 따로 기록하면 혼동을 줄일 수 있다.

이동 표시를 붙인 뒤 원본을 다시 사용하는 경우에는 실제 받는 연산이 원본에 어떤 상태를 남기는지 확인한다. std::move라는 표시는 사용 권한을 언어적으로 삭제하는 장치가 아니다.

준비 개념과 학습 목표

준비 개념

  • 객체 수명과 전제조건

학습 목표

  • 유효하지만 미지정인 상태와 특정 보장을 구별한다.

이동 뒤의 값을 몰라도 조건을 확인해 다시 쓸 수 있을까?

표준 vector<int> v를 이동 생성에 사용한 뒤 v의 실제 원소 수를 가정하지 않는다. 유효하지만 미지정인 상태라는 계약만으로 size()/empty()를 검사할 수 있다. front()는 비어 있지 않을 때만 호출한다. 검사 결과가 0이거나 2라는 두 가상 관찰을 비교하되 어느 결과가 실제 구현에서 나타난다고 주장하지 않는다.

사용자 클래스 Cache는 별도 계약을 정해야 한다. 이 절의 새 계약은 moved-from 상태를 ready=false로 두고 peek는 ready일 때만, reset(새 값)은 어느 유효 상태에서도 호출 가능하게 하는 것이다. unique_ptr의 특별 null 보장, 표준 컨테이너의 일반 보장, Cache의 자체 약속을 분리한다. 객체 존재와 모든 연산 허용을 같은 의미로 쓰지 않는다.

먼저 확인할 개념
  • 이동한 unique_ptr의 null 보장

    형식별 특별 보장과 일반 원본 상태를 구별한다.

  • vector의 size와 존재하는 원소

    전제조건을 원소 수 검사에 연결한다.

소유권 전달과 객체의 수명은 다르다

이동한 원본 객체도 대체로 자신의 수명이 끝날 때까지 존재한다. 원본이 사라졌다는 표현 대신, 원본의 값과 자원 소유 상태가 달라졌다고 생각하자. 파괴 시 어떤 자원을 정리하는지는 이동 연산이 남긴 상태에 달렸다.

표준 라이브러리 형식은 별도 규정이 없으면 이동 뒤 유효하지만 구체 값이 미지정인 상태를 갖는다. 유효함은 형식의 불변조건을 만족한다는 뜻이지 이동 전의 값이나 빈 상태를 보장한다는 뜻이 아니다.

사용할 연산의 조건부터 확인하기

파괴하거나 새 값을 대입하는 사용은 일반적인 정상 사용 경로다. 그러나 문자열의 첫 글자를 읽거나 컨테이너의 front를 부르는 동작처럼 비어 있지 않아야 하는 연산은 해당 조건을 먼저 확인한다. 유효한 객체라는 사실만으로 모든 member 연산의 전제조건이 충족되지는 않는다.

자체 클래스는 이동 후 상태를 문서화하고 자기 클래스의 불변조건을 지켜야 한다. 표준 라이브러리의 일반 규칙을 임의의 사용자 형식에 자동 적용하는 것은 잘못이다. 계약을 읽거나 설계해야 한다.

구체적인 보장이 있으면 그만큼만 사용하기

unique_ptr는 서로 다른 객체로 이동 생성한 뒤 원본 get()==nullptr를 보장한다. 이 보장으로 원본이 자원을 소유하지 않는다고 판단할 수 있지만 원본 포인터를 역참조할 수 있다는 뜻은 아니다. null 검사 후 행동을 나누어야 한다.

std::string 등의 일반 이동 후 상태를 항상 빈 문자열이라고 가정해서는 안 된다. 원하는 상태가 필요하면 명시적으로 값을 대입한다. 자원 전달, 사용 가능한 연산, 원본을 재설정할 시점을 함께 기록하면 안전한 흐름이 된다.

준비 개념과 학습 목표

준비 개념

  • 복사와 이동 생성자

이동을 못 하는 형식도 바로 반환할 수 있을까?

새 클래스 Fixed는 사용 가능한 기본 생성자와 public 소멸자를 갖고 복사 및 이동 생성자를 모두 =delete한다. C++17 이상에서 같은 Fixed 형식의 일반 변수 초기화를 다룬다. Fixed direct(){return Fixed{};}와 이름 있는 지역 객체를 반환하는 named를 비교한다. 앞의 경로는 결과 객체에 직접 생성하므로 삭제 복사/이동을 부르지 않는다.

named에서 NRVO가 적용될 수 있다는 허용은 필요한 복사/이동의 사용 가능성 검사를 면제하는 보장이 아니다. Fixed local; return local;은 삭제된 생성자가 필요한 경로 때문에 정상 함수로 받아들일 수 없다. 사용할 수 있는 이동 생성자가 있는 다른 Trace 형식의 선택적 NRVO 횟수와 구별하자. 소멸자는 여전히 접근 가능하고 삭제되지 않아야 한다.

  • 생성과 소멸의 수명 조건

    생략된 중간 이동과 소멸자의 사용 가능성을 따로 본다.

  • 새 객체의 초기화와 대입

    동일 형식 결과 변수 초기화를 기존 변수 대입과 구별한다.

결과 객체를 바로 만들기

C++17 이상에서 동일 클래스 형식의 prvalue로 대상 객체를 초기화하면 그 결과 객체에 직접 생성하는 규칙을 사용한다. T make(){ return T{}; }에서 반환할 값과 호출 결과를 연달아 복제해야 한다고 생각하지 않는다. 파괴자는 접근 가능하고 삭제되지 않아야 한다.

이 규칙은 흔히 보장된 복사 생략이라 부르지만, 이미 만들어진 원본을 복사하다가 최적화로 건너뛰는 모형보다 결과 객체에 직접 생성하는 모형이 정확하다. 이 단원의 횟수 계산은 동일 형식 반환과 보통의 변수 초기화 범위에 한정한다.

이름 있는 지역 객체의 NRVO는 선택적이다

T make(){ T local; return local; }처럼 이름 있는 적격 지역 객체를 반환하면 구현은 local을 결과 객체에 직접 만들 수 있다. 이것이 NRVO이며 항상 적용된다고 보장하지 않는다. 함수 인자나 volatile 객체 등은 이 단순 규칙과 다르다.

NRVO가 없을 때도 적격 반환에서 이동 생성자가 선택될 수 있다. 이동 가능성이나 복사 가능성을 갖춘 형식이라면 값 반환을 단순히 비용 낭비로 볼 필요는 없다. 부수 효과가 있는 생성자 횟수도 허용된 생략에 따라 달라질 수 있다.

불필요한 이동 표시가 생략 기회를 없앨 수 있다

return std::move(local);은 반환 표현식이 local의 이름 자체가 아니므로 위 NRVO 조건에서 벗어난다. 빨라 보이는 표기를 추가했지만 오히려 한 번의 이동을 요구할 수 있다. 보통은 return local;로 두고 반환 규칙을 활용한다.

중간 과정을 따라가는 예제

C++17 이상, 위 T, 직접 변수 초기화라는 조건에서 direct와 named의 복사·이동 횟수를 비교하라. default 생성은 별도로 센다.

  1. direct는 반환할 prvalue로 결과 객체를 직접 만든다. 기본 생성1, 복사0, 이동0이다.

  2. named에서 NRVO가 적용되면 local이 결과 객체라 기본 생성1, 복사0, 이동0이다.

  3. named에서 NRVO가 적용되지 않으면 적격 local에서 결과 객체로 이동1이 발생한다. 복사는0이다.

  4. 호출 결과로 동일 형식 변수를 초기화하는 단계에서 별도 이동을 더하지 않는다.

direct는 이동0이 보장되는 이 조건이며 named는 NRVO 여부에 따라 이동0 또는1이다.

  1. 같은 형식 prvalue가 x의 결과 객체를 직접 초기화한다.

  2. 별도 중간 Fixed를 만든 다음 옮기는 단계를 붙이지 않는다.

기본 생성 1, 복사 0, 이동 0이다. 소멸자는 사용 가능해야 한다.

const 지역 객체의 선택적 생략

Trace는 복사 const&와 이동 T&&가 있다. const Trace local; return local;로 같은 형식 변수를 초기화한다.

  1. const를 무시한 같은 클래스와 비volatile 자동 지역 이름은 NRVO 조건에 들어갈 수 있다.

  2. NRVO가 없으면 const 원본을 non-const T&&로 옮길 수 없어 복사한다.

생략 시 복사 0, 미생략 시 복사 1이다. 두 경우 이동은 0이다.

std::move(local)은 이름 자체가 아닌 xvalue 표현식이다. 위 NRVO 조건을 충족하지 않아 local에서 결과 객체로 이동1을 모델링한다. 결과 변수 초기화에 추가 이동을 붙이지 않는다.

값 반환은 항상 복사 두 번, std::move 반환은 항상 더 빠르다.

동일 형식 prvalue 직접 생성은 복사·이동을 요구하지 않는다. named 반환에 std::move를 추가하면 선택적 NRVO의 조건을 없앨 수 있다.

다른 문제에 적용하기

이동 후보·관계·반환 경로를 함께 감사하기

세 비교는 각각 새 객체에서 독립적으로 시작한다. (A) default 이동 Parcel a는 p→R/count=4, c는 p→S/count=2이며 c=std::move(a)를 한다. 새 관계는 count==0 iff p가 비어 있음이다. 결과와 보완 정책을 적어라. (B) const Regular k를 std::move하여 초기화하고, non-const Blocked a를 std::move하여 초기화하는 후보를 비교하라. 후보는 위 절의 복사 const&/일반 이동 T&& 또는 명시 삭제 이동이다. (C) 같은 형식의 일반 변수 초기화에서 Fixed direct와 Fixed named, 사용 가능한 Trace의 const 지역 named를 비교하라. 번역 오류 경로에 정상 실행 횟수를 붙이지 말라.

힌트 1

A는 포인터와 정수를 따로 추적하고 B는 const 바인딩부터 검사한다.

힌트 2

C는 직접 prvalue와 선택적 NRVO를 먼저 구분하고 삭제 후보의 사용 가능성을 확인한다.

풀이와 답 확인

  1. A에서 S는 정리되고 c는 R/4다. a는 null/4이므로 새 관계를 위반한다. 원본 count를 0으로 만드는 정책 또는 관계를 달리 설계해야 한다.

  2. B에서 const Regular는 const& 복사, non-const Blocked는 명시 삭제 T&&가 선택되어 오류다.

  3. C에서 Fixed direct는 기본 생성 1/복사 0/이동 0이다. Fixed named는 삭제 생성자 조건 실패로 정상 횟수가 없다.

  4. const Trace named는 NRVO 적용 시 복사 0, 미적용 시 복사 1이며 이동은 두 경우 모두 0이다.

  5. 모든 횟수는 C++17 이상과 사용 가능한 소멸자를 전제한 이론 추적이며 실제 컴파일·성능 결과가 아니다.

A는 대상 R/4와 원본 null/4의 관계 실패, B는 복사와 오류, C는 직접 생성 보장·오류·선택적 복사 0/1로 나뉜다.
