소단원 4.1

vector·deque·list

한 줄로 늘어선 카드라도 어떤 보관함은 가운데 수정에 더 적합할까?

준비 개념과 학습 목표

준비 개념

  • 시퀀스는 순서가 있는 값의 모음이다. 인덱스 i는 0부터 세며 n개 중 유효한 원소 위치는 0≤i<n이다.

  • std::vector<int>는 int 원소를 저장하는 표준 컨테이너 타입이다. size는 현재 원소 수이며 capacity는 vector가 재할당 없이 보관할 수 있는 수다.

학습 목표

  • 시퀀스 세 종류의 접근·수정 계약을 비교한다.

  • 원소 순서와 물리적 연속성을 구별한다.

  • 위치를 찾는 비용과 삽입 자체 비용을 나눈다.

vector의 순서와 연속성

vector<int>는 원소를 연속해서 보관하며 인덱스 접근은 상수 시간이다. 마지막에 원소를 더하는 push_back은 상환 상수 시간이지만 재할당하는 한 번의 호출은 기존 원소 수에 비례할 수 있다. 이 설명의 원소는 int이며 vector<bool>의 비트 프록시 특수화에는 같은 참조·연속성 설명을 자동 적용하지 않는다.

reserve(k)는 최소 보관 여유를 요청하고 size를 늘리지 않는다. 따라서 size=2에서 reserve(8) 뒤 v[2]에 대입하는 것은 존재하는 원소 접근이 아니다. 새 원소를 만들려면 push_back이나 적절한 resize를 사용한다. 실제 capacity가 정확히 k라고 단정하지 않는다.

deque와 list의 차이

deque<int>는 양끝 추가·삭제와 인덱스 접근을 지원하지만 전체 원소의 하나의 연속 배열 보장을 주지 않는다. vector처럼 v.data() 하나를 받아 모든 deque 원소를 C 배열로 넘긴다고 생각하면 안 된다. 가운데 수정의 비용과 무효화 규칙은 양끝 수정과 다르다.

list<int>는 양방향 iterator로 차례로 접근하며 임의 인덱스의 operator[]를 제공하지 않는다. 이미 적합한 iterator가 주어졌다면 원소 하나 삽입·삭제는 상수 시간이다. 값 30을 먼저 탐색하는 전체 작업은 최대 n개를 읽어야 하므로 탐색 비용을 생략한 상수 시간 주장과 다르다.

같은 논리 결과, 다른 작업

아래 소스는 같은 초기 값의 vector,deque,list를 각각 수정한다. 예제는 할당이 성공하고 예외 없이 정상 완료한다고 가정한다. 실제 주소나 CPU 시간은 예상 시퀀스로부터 알 수 없으며 메모리 지역성의 기대를 측정 결과로 바꾸지 않는다.

list 삽입 위치는 두 번째 원소를 가리키는 iterator를 먼저 얻어야 한다. 삽입은 그 위치 앞에 일어난다. 모든 컨테이너의 push_back(40)이 마지막 위치에 더한다는 논리 계약과 그 연산이 원소 참조를 보존하는지의 계약을 따로 읽자.

#include <vector>
#include <deque>
#include <list>
#include <iostream>
int main() {
 std::vector<int> v{10,30}; v.insert(v.begin()+1,20);
 std::deque<int> d{10,30}; d.push_front(5);
 std::list<int> l{10,30}; auto it=l.begin(); ++it; l.insert(it,20);
 for(int x:v) std::cout<<x<<" "; std::cout<<"\n";
 for(int x:d) std::cout<<x<<" "; std::cout<<"\n";
 for(int x:l) std::cout<<x<<" "; std::cout<<"\n";
}

중간 과정을 따라가는 예제

정상 완료 가정에서 예제 세 시퀀스를 종이로 구하라.

  1. v의 begin()+1은 30 위치이고 그 앞에 20을 삽입하여 [10,20,30]이다.

  2. d의 앞에 5를 추가하여 [5,10,30]이다.

  3. l의 iterator를 한 번 증가하면 30이며 그 앞 삽입 후 [10,20,30]이다.

  4. 출력 루프는 각 원소를 순서대로 읽고 각 값 뒤 공백을 출력한다.

예상 세 줄은 10 20 30 / 5 10 30 / 10 20 30이며 각 줄 마지막 값 뒤에도 공백이 있다. 실제 C++ 출력 기록은 없다.

풀이 보기

두 번 증가하여 c를 찾고 그 앞에 넣어 [a,b,x,c,d]이다. 한 원소 삽입은 상수 시간 계약이지만 일반 위치까지의 순차 탐색을 포함하면 선형 비용이다.

오해와 반례

list는 어느 위치든 항상 가장 빠르다.

위치를 찾아야 하는 경우 탐색 비용이 있고 노드별 할당·메모리 접근의 실제 상수도 다르다. 복잡도 상한 하나가 모든 장치·입력의 시간 순위를 증명하지 않는다.

한 단계 더

초기 n개 vector에서 위치 i 앞에 하나를 삽입하는 가상 이동 모형을 만들자. 기존 i…n−1을 오른쪽으로 옮기면 이동 수 n−i이고 새 값 쓰기 하나가 추가된다. i=n이면 기존 이동이 0이지만 재할당이 발생하면 n개 기존 원소의 새 저장소 이동이 필요할 수 있다. 이 계산은 int 원소의 교육 모형이며 구현이 반드시 동일한 대입 순서나 복사 횟수를 실행한다는 주장은 아니다.

소단원 4.2

map·set·unordered 계열

이름으로 찾는 사전과 순서대로 읽는 목록은 어떤 계약이 다를까?

준비 개념과 학습 목표

준비 개념

  • 키는 검색에 사용하는 값이다. map은 키와 대응 값을 저장하고 set은 키 자체를 저장한다.

  • find(k)의 결과는 발견 원소 위치 또는 end이다. end는 실패 표시로 비교할 수 있지만 원소처럼 역참조하지 않는다.

학습 목표

  • 순서·키 동치·중복 정책을 구별한다.

  • 조회와 삽입의 차이를 추적한다.

  • unordered 평균 비용과 최악 비용을 분리한다.

정렬과 동치의 계약

map과 set은 비교 객체가 정한 순서로 순회한다. 기본 int 비교에서는 작은 키부터 읽는다. map/set의 키 유일성은 일반적으로 !(comp(a,b)) && !(comp(b,a))라는 비교 동치에 따른다. 사용자 비교 함수는 strict weak ordering을 만족해야 하며, 반환 true를 더 많이 만드는 것이 좋은 정렬은 아니다.

map은 대응 값을 변경할 수 있지만 컨테이너 안의 키를 직접 고쳐 순서를 깨뜨려서는 안 된다. set 원소도 키이므로 iterator로 키를 대입하지 않는다. 같은 키의 여러 항목이 필요한 경우 multimap/multiset 같은 중복 지원 계열의 계약을 사용한다.

조회도 저장 상태를 바꿀 수 있다

m.find(k)는 없는 키를 추가하지 않는다. 반면 map<int,int>의 m[k]는 키가 없으면 대응 int를 0으로 초기화한 항목을 삽입하고 그 값에 대한 참조를 돌려준다. 사전 조회를 한다고 생각한 코드가 실제 크기를 바꿀 수 있으므로 읽기에는 find나 at의 실패 정책을 의식적으로 고른다.

아래는 키 2의 삽입 실패와 키 3의 자동 삽입을 대비한다. emplace(2,99)의 반환 쌍에서 second는 false이고 기존 대응 값 20을 덮어쓰지 않는다. insert_or_assign 같은 다른 API의 갱신 의미와 섞지 말자.

#include <map>
#include <set>
#include <iostream>
int main() {
 std::map<int,int> m{{2,20},{1,10}};
 auto r=m.emplace(2,99);
 auto missing=m.find(3); bool absent=(missing==m.end());
 int z=m[3];
 std::set<int> s{3,1,3};
 std::cout<<r.second<<" "<<absent<<" "<<z<<" "<<m.size()<<" "<<s.size()<<"\n";
}

unordered는 순서를 약속하지 않는다

unordered_map/set은 해시와 키 동치 술어를 사용한다. 동치인 두 키에는 같은 해시 값이 필요하지만 같은 해시 값이라고 동치인 것은 아니다. 서로 다른 키가 같은 버킷에 모이는 충돌이 가능하므로 해시는 키의 유일한 신분증이 아니다.

기본적인 조회의 평균 비용은 상수 시간 계약이고 최악은 선형일 수 있다. 평균이라는 말을 모든 호출의 지연 상한이나 확률 분포 없이 산출한 시간으로 바꾸지 않는다. 원소 순회는 정렬 순서나 삽입 순서를 보장하지 않으며 재해시는 iterator를 무효화할 수 있다.

중간 과정을 따라가는 예제

예제의 emplace 반환, find, m[3], 두 size를 추적하라.

  1. m은 키 1→10,2→20 두 항목이다. emplace의 키 2는 이미 있어 r.second=false이다.

  2. find(3)는 end이며 absent=true다. 이 단계까지 크기는 2다.

  3. m[3]은 새 대응 int 0을 만들어 z=0이며 m 크기 3이다.

  4. set의 중복 키 3은 하나만 남아 키 집합 {1,3}, 크기 2다.

예상 출력은 0 1 0 3 2와 줄바꿈이다. 기본 bool 출력 형식 가정이며 실제 실행은 하지 않았다.

종이와 본문으로 직접 해보기

빈 map<int,int>에서 find(7) 뒤 크기와 m[7] 뒤 크기를 적어라. 해시값 5를 가진 서로 다른 키 a,b를 같은 키라고 판정할 수 있는지도 설명하라.

힌트 보기

탐색 API와 삽입 API를 분리하고 hash와 equality를 각각 쓰자.

풀이 보기

find 뒤 크기 0, m[7] 뒤 크기 1·대응 값 0이다. hash(a)=hash(b)=5만으로 동치가 결론나지 않는다. 동치 술어를 따로 검사해야 한다.

오해와 반례

unordered는 모든 경우 O(1)이므로 map보다 무조건 빠르다.

충돌이 집중되면 조회가 선형일 수 있고 해시 계산·키 비교 비용도 값 타입에 따라 다르다. 정렬 순회·범위 질의가 필요하면 map의 다른 계약이 요구를 더 직접 충족한다.

한 단계 더

단순 교육 해시 h(k)=0을 모든 키에 주고 동치는 int의 ==로 유지하자. 동치인 키는 반드시 같은 해시이므로 올바름 계약에는 맞지만 n개 키가 같은 버킷에 모일 수 있다. 없는 키를 확인하는 탐색은 최악에서 기존 키들을 비교하므로 선형 비용을 배제할 수 없다. 올바른 해시라는 조건만으로 좋은 분포나 적대적 입력에 대한 성능 상한을 증명할 수 없는 반례다.

소단원 4.3

iterator와 범위

첫 카드부터 끝까지 읽을 때 마지막 뒤의 위치는 왜 필요할까?

준비 개념과 학습 목표

준비 개념

  • iterator는 원소 위치를 다루는 추상 객체다. *it는 유효 원소를 읽고 ++it는 다음 위치로 진행한다.

  • [first,last)는 first를 포함하고 last는 포함하지 않는 반열린 범위다. 빈 범위에서는 두 끝이 같다.

학습 목표

  • end를 원소와 구별한다.

  • 컨테이너와 iterator 범주의 허용 연산을 연결한다.

  • 삭제 중 순회의 종료와 누락 없음을 설명한다.

끝을 제외하는 범위

begin은 첫 원소 위치, end는 마지막 원소 뒤의 경계를 나타낸다. 빈 컨테이너에서는 begin==end여서 읽을 원소가 없다. 같은 시퀀스에서 first를 유한 번 증가시켜 last에 도달할 수 있어야 해당 [first,last)가 유효하다. 서로 다른 컨테이너의 끝을 섞은 범위를 만들지 않는다.

루프에서 it!=end를 먼저 검사한 뒤 *it를 읽는 이유는 end가 유효한 원소가 아니기 때문이다. end에 도달하면 증가도 멈춰야 한다. 정수 인덱스 n이 마지막 원소가 아니라 원소 수인 것과 같은 경계 구조다.

지원 연산이 다르다

vector와 deque iterator는 random access로 it+3 같은 이동을 제공한다. list와 map은 bidirectional로 ++와 --를 제공하지만 it+3은 지원하지 않는다. unordered 계열은 forward 순회를 제공하며 이전 위치로 돌아가는 --를 일반 계약으로 요구할 수 없다.

const_iterator는 그 iterator를 통한 원소 변경을 막는 접근 형태다. iterator 객체를 이동시키는 ++ 자체를 막는다는 뜻이 아니다. 반대로 const로 선언한 일반 iterator 객체는 위치 재대입·증가를 제한하더라도 가리킨 원소의 수정 가능성을 자동 제거하지 않는다.

변경 루프는 새 위치를 받기

vector에서 원소를 erase하면 삭제 지점과 그 이후의 기존 iterator가 무효화된다. 따라서 it=erase(it)로 돌려받은 다음 원소의 새 iterator를 사용하고 삭제 가지에서 ++를 추가하지 않는다. 남긴 원소에서는 한 번만 증가한다. 아래는 int 원소·정상 완료·동시 수정 없음 조건의 완전한 예제다.

range-for도 내부적으로 시작과 끝을 사용하는 순회이므로 반복 중 push_back을 하면 재할당이나 end 무효화 문제를 피하지 못한다. 문법이 간결하다고 iterator 계약이 사라지는 것은 아니다. 변경해야 하는 작업은 출력만 하는 순회와 구별해서 설계하자.

#include <vector>
#include <iostream>
int main() {
 std::vector<int> v{2,3,4,5};
 for(auto it=v.begin(); it!=v.end();) {
  if(*it%2==0) it=v.erase(it);
  else ++it;
 }
 for(int x:v) std::cout<<x<<" "; std::cout<<"\n";
}

중간 과정을 따라가는 예제

짝수를 지우는 예제에서 현재 검사 값과 시퀀스 변화를 추적하라.

  1. 2를 검사하여 지우면 [3,4,5]이고 erase 반환 iterator는 새 첫 원소 3이다.

  2. 3은 남기고 증가하여 4로 간다.

  3. 4를 지우면 [3,5]이고 반환 iterator는 5다.

  4. 5를 남겨 증가하면 현재 end에 도달해 종료한다.

남는 값은 [3,5], 예상 출력은 3 5 뒤 공백과 줄바꿈이다. 실제 C++ 실행은 하지 않았다.

종이와 본문으로 직접 해보기

동일한 루프로 [2,4]와 []를 따로 추적하라. 삭제 뒤 무조건 ++it를 더하면 어떤 문제가 생기는가?

힌트 보기

erase가 이미 다음 위치를 돌려준다는 점을 기억하자.

풀이 보기

[2,4]는 첫 삭제 뒤 4를 검사하고 둘째 삭제 뒤 end로 가서 []가 된다. 빈 입력은 처음 조건부터 거짓이다. 삭제 뒤 또 증가하면 원소를 건너뛰거나 end를 증가시키는 잘못된 경로를 만들 수 있다.

오해와 반례

모든 iterator는 숫자 인덱스처럼 +와 -를 지원한다.

list/map iterator에는 it+1이 없다. 지원 범주를 만족하는 알고리즘을 고르거나 순차 증가의 비용을 포함해야 한다.

답과 이유 보기

한 단계 더

삭제 루프의 불변식은 현재 it 앞의 원소들은 모두 검사했고 모두 홀수이며, it가 가리키는 원소부터 end 직전까지는 아직 검사하지 않았고 원래 순서를 유지한다는 것이다. 짝수 삭제는 그 원소만 제거하고 다음 미검사 위치를 반환한다. 홀수 가지는 그 원소를 검사 완료 접두부로 넘긴다. 각 단계에서 남은 미검사 원소 수가 정확히 하나 감소하므로 유한 입력에서 종료한다. 빈 입력도 초기 미검사 수 0으로 성립한다. vector의 반복 삭제 전체 비용은 이동을 포함하여 최악 O(n²)일 수 있으며 종료 증명은 선형 시간 증명이 아니다.

소단원 4.4

무효화·복잡도·선택

같은 값을 가리키던 손잡이가 수정 뒤에도 쓸 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 참조는 대상 원소의 별칭이고 iterator는 순회 위치의 추상 객체다. 둘의 보존 규칙이 같다고 가정하지 않는다.

  • 무효화는 기존 손잡이를 더 이상 해당 계약에 따라 사용할 수 없게 되는 일이다. 잘못된 접근의 결과를 특정 숫자로 예상하지 않는다.

학습 목표

  • 재할당·삽입·삭제·재해시 조건을 분류한다.

  • 최악·상환·평균 비용을 구별한다.

  • 요구를 근거로 컨테이너를 선택한다.

vector의 여유와 경계

재할당은 vector의 모든 원소 참조·포인터·iterator와 end를 무효화한다. 재할당 없는 삽입은 삽입 위치 앞의 손잡이만 보존하며 그 위치와 뒤, 기존 end는 무효화한다. 끝 삽입도 기존 end를 보존하지 않는다.

아래 reserve(8) 뒤 capacity≥8이고 size=3이다. 그 뒤 끝에 하나만 추가하면 재할당하지 않아 첫 원소 참조와 iterator는 보존된다. 하지만 이후 가운데 삽입은 재할당이 없어도 삽입 위치 이후 손잡이를 무효화한다. reserve를 모든 무효화의 해법으로 말하면 틀린다.

std::vector<int> v{10,20,30};
v.reserve(8);
auto first=v.begin(); int& r=v[0]; auto old_end=v.end();
v.push_back(40); // first,r 유효; old_end 무효
v.insert(v.begin()+1,15); // first,r은 삽입점 앞이라 유효

다른 보관함의 손잡이

deque 양끝 삽입은 기존 원소 참조를 보존하지만 iterator를 무효화한다. 가운데 삽입은 둘 다 무효화한다. list의 삽입은 기존 원소 iterator·참조를 보존하며 삭제는 삭제 원소의 손잡이만 무효화한다. map/set의 보통 삽입·삭제도 기존 원소에 대한 이 보존·삭제 원칙을 제공한다.

unordered의 재해시는 iterator를 무효화하지만 원소 포인터·참조를 무효화하지 않는다. 삭제 원소의 참조는 보존되지 않는다. 컨테이너 전체 파괴, 원소 추출, 대입·이동 등은 별도 계약을 읽어야 하며 여기의 간단 삽입 규칙을 모든 연산에 확대하지 않는다.

비용 보장은 선택의 일부

끝 append가 많은 연속 시퀀스는 vector, 양끝 작업과 인덱스 접근은 deque, 이미 주어진 위치에서 잦은 삽입과 참조 안정성은 list를 후보로 볼 수 있다. 정렬 키 순회는 map/set, 정렬 필요 없는 키 조회는 unordered 계열을 검토한다. 요구하는 안정성과 연산을 먼저 적는다.

복잡도는 비교·원소 연산 등의 추상 비용이며 실제 지연 상한과 같다며 배포하지 않는다. vector 끝 추가의 상환 상수는 긴 작업열의 합을 나눈 보장이고 unordered의 평균 상수는 다른 의미다. 복사·해시·할당이 비싸거나 적대적 입력이 있으면 이 조건과 실제 비용 모형을 따로 확인해야 한다.

중간 과정을 따라가는 예제

제시한 vector 조각의 두 수정 뒤 first,r,old_end와 최종 시퀀스를 판정하라.

  1. reserve 뒤 생성한 first는 10 위치, r은 그 원소 별칭, old_end는 당시 끝이다.

  2. push_back(40)은 size 4≤capacity라 재할당 없고 first,r은 유효, old_end는 무효다.

  3. begin()+1 앞에 15를 삽입한다. size 5≤capacity이고 first,r은 삽입점 앞이다.

  4. 최종 [10,15,20,30,40]이며 first와 r은 계속 10을 가리킨다. old_end는 재사용하지 않는다.

정상 완료 조건에서 first,r 유효, old_end 무효다. 조각을 실제 컴파일하거나 무효 iterator를 비교·역참조하지 않았다.

종이와 본문으로 직접 해보기

deque [a,b]의 첫 원소 참조와 iterator를 각각 그린 뒤 push_back(c)를 표시하라. unordered 재해시의 원소 참조와 iterator도 비교하라.

deque 양끝 삽입 뒤 기존 a 참조는 유효하지만 iterator는 무효다. unordered 재해시 뒤 기존 원소 참조는 유효하지만 iterator는 무효다. 삭제나 컨테이너 파괴를 하지 않는 조건이다.

오해와 반례

reserve하면 iterator가 영구적으로 안전하다.

capacity를 넘으면 재할당하고 가운데 삽입·삭제는 재할당 없이도 일부 iterator를 무효화한다. 컨테이너 파괴 뒤에는 reserve 이력과 관계없이 원소 수명도 끝난다.

iterator 무효화와 원소 포인터·참조 보존을 구분한다.

비싼 한 호출의 비용을 작업열 전체에 분배하는 분석이다.

한 단계 더

용량이 1,2,4,…로 늘어나는 자체 교육 vector 모형에서 빈 시퀀스에 m≥1번 append할 때 m=1이면 확장 없이 기존 원소 이동이 0이다. m≥2이면 기존 원소 이동 합은 마지막 확장 전 용량까지의 기하합 1+2+…+2^k<2m이다. 새 원소 쓰기 m을 합하면 총 비용<3m이므로 호출당 상환 상수다. 이 모형은 C++ 표준이 정확한 배증 배율을 강제한다는 증명이 아니다. reserve(size()+1)를 매번 호출해 불필요한 재할당을 유도하는 작업열은 이 특정 배증 논증의 전제를 보장하지 않는다. 실제 용량 정책과 할당 비용은 구현별 검증이 필요하다.
