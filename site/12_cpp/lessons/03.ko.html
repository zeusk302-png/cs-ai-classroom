소단원 3.1

string·string_view의 수명

문자열의 작은 창을 복사하면 원래 글자도 함께 살아남을까?

준비 개념과 학습 목표

준비 개념

  • std::string은 char 원소를 소유하는 객체다. 지역 객체는 블록을 떠날 때 소멸한다.

  • 참조는 같은 객체를 가리키는 이름이고 복사는 독립된 객체를 만드는 일이다. 길이 n의 뷰 원소 인덱스는 0…n−1이다.

학습 목표

  • 소유 문자열과 비소유 뷰의 수명을 구별한다.

  • 뷰를 통한 읽기 전제를 설명한다.

  • 부분 문자열의 복사와 뷰를 추적한다.

문자 수를 가진 view는 중간의 NUL에서 끝날까?

이 보강은 base의 C++20 조건을 유지한다. 살아 있는 char a[4]={'1','2','\0','x'}에 std::string_view whole(a,4)를 만들면 길이는 4다. NUL은 길이를 끝내는 표지가 아니라 범위 안의 세 번째 문자다. 반대로 std::string(a)는 NUL로 끝나는 문자열 생성 규약을 써서 처음 두 문자를 복사한다. 같은 주소도 인터페이스가 받는 길이와 종료 규약에 따라 읽는 범위가 달라진다.

auto short_view=whole; short_view.remove_prefix(1);은 view의 시작과 길이를 바꾼다. a 자체나 whole의 길이를 바꾸지 않는다. 이후 a[1]='9'이면 두 view는 그 실제 문자 변경을 관찰하지만 앞서 만든 소유 string의 값은 유지된다. view를 반환하거나 저장하기 전에는 데이터가 계속 살아 있고 해당 범위가 무효화되지 않는지를 확인한다. data()만 C 문자열 API에 전달하면 view의 끝을 전달하지 못한다.

이 소단원의 각 예제와 각 연습은 별도로 새 char a[4]={'1','2','\0','x'}와 그 위의 길이 4인 whole view에서 시작한다. 한 예제에서 수행한 a[1]='9' 변경을 다음 연습으로 이어받지 않는다. 문제 안에 적힌 변경 사건만 해당 문제의 상태에 적용한다.

먼저 확인할 개념
  • 빌린 대상의 수명

    복사한 참조 정보가 원본 대상의 수명을 늘리지 않는 이유를 적용한다.

  • NUL과 길이

    종료 문자 기반 읽기와 명시한 문자 수를 구별한다.

소유와 관찰

std::string s="cat"은 자신의 문자 저장 공간을 관리한다. std::string copy=s는 독립된 문자열을 만든다. std::string_view v=s는 주소와 길이를 담은 관찰 창이어서 소유 문자열의 수명을 늘리지 않는다. 창을 복사해도 데이터를 복사하지 않는다.

string_view가 읽기 전용으로 원소를 제공한다는 말은 원본이 절대 바뀌지 않는다는 뜻이 아니다. 원본의 유효한 문자 객체를 다른 경로로 수정하면 뷰에서도 바뀐 값을 볼 수 있다. 따라서 const 접근·불변 데이터·소유권은 다른 조건이다.

수명과 변경을 함께 점검하기

원본 소멸 뒤의 뷰를 읽으면 유효한 데이터라는 전제를 잃는다. std::string_view v=std::string("cat");처럼 임시 소유자를 쓰면 문장 끝의 임시 소멸 뒤 뷰가 매달린다. 읽기 결과를 cat 또는 빈 문자열이라고 약속할 수 없다.

append 등 원본 저장 공간을 재할당할 수 있는 연산 뒤에는 예전 주소의 뷰를 계속 믿지 않는다. 모든 변경이 항상 무효화한다고 일반화할 필요는 없지만 변경 뒤 규칙을 확인하거나 새 뷰를 만드는 정책이 안전하다. 아래는 길이/주소를 바꾸지 않는 기존 원소 대입만 수행한다.

std::string s="cat";
std::string copy=s;
std::string_view v=s;
s[0]='b';
auto tail=v.substr(1,2);

길이와 널 종료

뷰의 substr은 같은 저장 공간의 더 좁은 창이다. string의 substr은 소유하는 새 문자열이다. v.substr(1,2)는 위치 1에서 최대 두 원소를 가리키며 호출 순간 원본이 살아 있어야 하고 사용 순간에도 유효해야 한다.

string_view는 널 종료를 보장하지 않는다. v.data()를 C 문자열 함수에 넘기면 창의 끝을 넘어 읽거나 의도하지 않은 뒤 글자를 포함할 수 있다. 길이를 받는 함수 또는 명시적 std::string(v) 복사를 사용하자. char 원소 수는 UTF-8 코드 포인트 수나 사용자가 보는 글자 수와 같다고 보장되지 않는다.

사건/입력데이터 또는 소비 상태판정/주의

whole(a,4)

1 / 2 / NUL / x, 길이 4

NUL 뒤 x도 범위 안

std::string owned(a)

1 / 2, 길이 2

NUL 앞까지 복사

short_view.remove_prefix(1)

2 / NUL / x, 길이 3

whole 길이 4와 a 유지

a[1]='9'

whole의 두 번째와 short_view의 첫 번째가 9

owned는 12 유지

행의 슬래시는 문자 위치를 구별하며 실제 저장 문자 슬래시가 아니다. NUL을 눈에 보이는 빈칸으로 지워 읽지 않는다. 소유자 종료 뒤 view를 읽는 행은 만들지 않는다.

중간 과정을 따라가는 예제

위 코드에서 s,copy,v,tail의 내용을 소유 관계와 함께 추적하라.

  1. 처음 s와 copy는 각자 cat 문자를 소유하고 v는 s의 세 칸을 본다.

  2. s[0]의 기존 문자만 b로 바꾸면 s는 bat이다.

  3. copy는 다른 객체라 cat이고 v는 같은 유효한 저장 공간을 보아 bat이다.

  4. tail은 s의 인덱스 1,2를 보는 비소유 뷰라 at이며 길이는 2다.

s=bat, copy=cat, v=bat, tail=at이다. 네 객체 모두 해당 블록 안에서 살아 있는 상태의 예상 내용이다.

조건을 바꾸어 비교하기

같은 주소의 다른 두 범위

a에서 whole과 owned의 길이, whole[3]을 비교하라.

  1. whole은 명시된 네 문자를 본다.

  2. owned는 첫 NUL 전 두 문자를 독립 복사한다.

길이 4와 2이며 whole[3]은 x다.

비교할 점

C 문자열 길이를 모든 view의 길이로 적용하지 않는다.

범위 이동과 원본 수정

short_view의 prefix를 하나 제거한 뒤 a[1]을 9로 바꾸면 어떤 문자가 보이는가?

  1. short_view는 a[1]에서 시작한다.

  2. 소유 복사는 원본의 새 쓰기를 따라가지 않는다.

short_view[0]=9, whole[1]=9, owned는 12다.

비교할 점

view 객체의 범위 변경과 데이터 변경은 별도 사건이다.

종이와 본문으로 직접 해보기

원본 s를 블록 안에서 만든 뒤 v만 블록 밖으로 내보내는 경우, tail을 std::string으로 복사해 내보내는 경우를 구별하라.

힌트 보기

문자 저장 공간의 소유자가 누구인지 화살표로 그린다.

풀이 보기

s 소멸 뒤 v는 매달린 뷰이므로 읽으면 안 된다. s가 살아 있을 때 tail을 std::string에 복사한 소유 객체는 자신의 수명 안에서 at를 유지한다.

오해와 반례

뷰가 const로 읽히므로 원본의 변경이나 소멸과 무관하다.

위 예제에서 원본 문자 변경은 v에 보이고 원본 소멸은 유효성을 없앤다. const 접근은 소유권이나 수명 연장이 아니다.

준비 개념

  • istream은 문자 입력을 추출하고 ostream은 값을 문자로 삽입한다. >>와 <<가 이 문맥에서 입출력 연산이다.

필드 구분자와 줄 끝을 누구에게 소비시킬까?

새 텍스트 규약은 한 줄에 quantity;name을 담는다. 이름에는 공백을 허용하고 세미콜론은 허용하지 않으며, 수량은 다음 소단원의 별도 숫자 검증을 거친다. std::getline(input,line)으로 줄 하나를 먼저 얻은 뒤 std::istringstream row(line); getline(row,quantity_text,';'); getline(row,name);으로 두 부분을 나누는 설계를 종이에 추적한다. 이는 구분자 없는 줄까지 올바른 두 필드라고 인증하는 완성 파서가 아니다. 세미콜론 정확히 하나와 비어 있지 않은 두 필드를 따로 검증한다.

3;Ada Lee 2;Bo 의 두 번째 줄은 빈 문자열이다. getline은 줄 끝을 소비하고 결과에 넣지 않는다. 빈 줄도 줄 끝 문자를 소비했으므로 그 읽기 자체는 성공할 수 있지만 이 자료 규약에서는 빈 레코드로 거절한다. >>std::ws로 모든 선행 공백을 없애면 빈 줄이나 이름 앞 공백을 자료에서 구별해야 하는 계약을 바꾼다. 입력 방식은 허용 데이터 모양에 맞춘다.

흐름과 저장소

std::cin과 std::cout은 표준 입출력 스트림이다. std::istringstream은 메모리 문자열을 입력원으로 삼고 std::ostringstream은 출력 문자를 메모리에 모은다. 따라서 사용자 설치나 키보드 입력 없이 고정 문자열의 파싱 흐름을 종이로 추적할 수 있다.

정수 추출 >>는 선택 로캘의 숫자와 공백 규칙에 영향을 받는다. 본문의 스트림은 std::locale::classic()을 명시해 기본 C 로캘로 고정한다. 성공한 값과 잔여 입력을 기록하되 숫자 하나 추출의 성공을 레코드 전체의 성공이라고 해석하지 않는다.

토큰과 한 줄

>>로 std::string에 추출하면 기본 설정에서 선행 공백을 건너뛰고 다음 공백 앞까지 읽는다. std::getline(in,line)은 기본 구분자 개행을 소비하지만 결과 문자열에 넣지 않는다. 중간 공백은 이름의 일부로 남는다.

숫자를 >>로 읽은 뒤 곧바로 getline을 호출하면 남아 있던 개행을 만나 빈 문자열을 얻을 수 있다. 이는 이름이 비어 있다는 사용자 응답과 구별해야 한다. getline(in>>std::ws,line)은 선행 공백과 빈 줄까지 건너뛰므로 빈 줄이 의미 있는 계약에서는 무조건 적용할 수 없다.

std::istringstream in("7\nAda Lee\n");
in.imbue(std::locale::classic());
int n=0; std::string first, name;
in>>n;
std::getline(in,first);
std::getline(in,name);

추출 계약과 출력 계약

if(in>>n)는 추출 후 스트림 성공 여부를 확인한다. 실패하면 그 값을 업무 처리에 쓰지 않는 정책을 세운다. 숫자 뒤의 x를 따로 거절하지 않으면 7x에서도 7이라는 접두부를 얻을 수 있으므로 전체 레코드 문법을 추가한다.

ostringstream의 str()은 모인 문자열을 얻는다. 화면에 출력했다는 뜻이 아니며 객체의 메모리 결과다. 저장과 표시를 분리하면 테스트에서 기대 문자열을 비교할 수 있지만 종이 비교가 실제 콘솔·파일·학생 실험의 증거로 바뀌지는 않는다.

준비 개념과 학습 목표

준비 개념

  • 상태 비트는 서로 배타적인 이름표가 아니라 여러 조건을 함께 기록할 수 있는 플래그다.

  • 스트림 성공 검사와 good(), eof(), fail(), bad()는 동일한 질문이 아니다.

학습 목표

  • eofbit와 failbit의 조합을 구별한다.

  • 읽기 성공을 반복 조건으로 삼는다.

  • clear와 입력 소비를 분리한다.

오류 플래그를 지우면 잘못된 문자가 사라질까?

새 정상 istringstream의 내용이 q 7 이고 classic locale 및 기본 예외 마스크를 가정한다. 처음 int를 >>로 읽으면 q를 정수로 해석하지 못해 failbit가 설정된다. q는 여전히 입력 쪽에 남는다. clear()는 상태 플래그를 다시 설정할 뿐 소비 위치를 전진시키지 않는다. 따라서 clear만 한 뒤 같은 정수 추출을 반복하면 같은 문제를 다시 만난다.

이 사례의 회복 규약은 잘못된 줄 전체를 하나의 거절로 기록한 뒤 다음 줄로 간다. clear(); getline(input,rejected);으로 q와 newline을 소비하면 다음 int 추출은 7을 읽는다. 반면 입력이 newline 없는 7뿐이면 성공한 정수 추출에서 eofbit만 설정될 수 있다. bool(input)은 !fail()이고 good()은 모든 상태 비트가 없는지 보므로, 성공·EOF 동시 상태에서 두 함수 값이 다를 수 있다.

끝에 도달했다는 상태

eofbit는 입력 동작이 끝을 만났다는 기록이며 읽기 전에 앞으로 끝인지 미리 알려주는 예언자가 아니다. 마지막 정수의 숫자를 끝까지 정상 해석하며 EOF를 만나면 eofbit만 설정되는 경우가 있다. 이때 failbit/badbit가 없으면 스트림의 bool 성공 검사는 참일 수 있다.

good()는 모든 오류 상태가 없을 때 참이므로 eofbit만 있어도 거짓이다. fail()은 failbit 또는 badbit, bad()는 badbit, eof()는 eofbit를 본다. 본문은 기본 exception mask를 사용하여 상태 보고로 처리하며 예외를 켠 설정이면 제어흐름이 달라질 수 있다.

읽기 후의 성공으로 반복하기

while(in>>x)는 이번 추출이 성공한 경우에만 x를 사용한다. while(!in.eof())는 아직 읽지 않은 실패를 몸 안에서 일으킬 수 있고, EOF가 아닌 문법 오류가 있으면 조건이 계속 참인 상태로 재시도를 반복할 수도 있다.

아래 classic 로캘 정수 스트림의 "7"은 첫 추출 때 값 7을 얻고 끝을 관찰한다. 다음 추출은 새 값을 얻지 못하고 fail 상태가 추가된다. 실패한 추출 뒤의 값 내용을 일반 규칙으로 외워 사용하는 대신 성공 가지에만 처리 코드를 두자.

std::istringstream in("7");
in.imbue(std::locale::classic());
int x=0, count=0;
while(in>>x) { ++count; }

상태 복구와 자료 복구

clear()는 저장된 상태를 바꾸며 입력 문자까지 제거하지 않는다. 잘못된 문자 q가 남아 있는 경우 상태만 지우고 같은 정수를 다시 읽으면 같은 일치 실패가 돌아올 수 있다. 복구 정책은 상태 재설정과 잘못된 레코드 소비, 종료 이유 보고를 함께 정한다.

badbit는 단순한 숫자 형식 오류보다 스트림 무결성/버퍼 오류에 관련된 상태다. 오류를 지워서 장치가 고쳐졌다고 주장할 수 없다. EOF를 정상 종료로 인정할지, 문법 오류를 사용자에게 알릴지, 장치 오류를 재시도할지는 응용 계약에 따라 다르다.

준비 개념과 학습 목표

준비 개념

  • 표시는 사람이 읽는 모양이고 파싱은 허용 문법에서 값을 얻는 과정이다. 여러 값이 같은 표시로 합쳐지면 역복원은 불가능하다.

  • [first,last)는 첫 문자부터 끝 직전까지의 유효한 연속 범위다. last는 마지막 문자 뒤 위치이며 원소가 아니다.

학습 목표

  • formatting의 정보 손실을 설명한다.

  • from_chars의 오류와 전체 소비를 검사한다.

  • 정수 범위와 업무 범위를 분리한다.

숫자로 해석됨과 허용되는 표기는 같은가?

새 수량 텍스트 계약은 ASCII 0 또는 1–9로 시작하는 한 개 이상의 숫자이며 값은 0–100이다. 따라서 003은 from_chars로 숫자 3이 될 수 있지만 이 계약의 표준 표기는 아니다. 12x는 앞부분 12를 해석하더라도 끝 포인터가 입력 끝과 다르다. +3이나 앞 공백은 이 정수 from_chars 패턴으로 허용되지 않는다. signed int의 −3은 숫자로 해석될 수 있으나 업무 범위에서 거절한다.

출력 표준화는 검증 뒤에 한다. 예를 들어 요청 수량을 폭 3의 십진 표시로 남기는 자체 규약은 값 3을 003, 값 12를 012로 표시한다. 이 출력 규약과 입력의 선행 0 금지 규약은 다른 역할이다. 표시 003을 새 요청으로 다시 넣으면 원래 입력 계약에는 맞지 않는다. 이 예는 부동소수 반올림을 실험하지 않고 정수 값·입력 표기·출력 표시를 구별한다.

표시 정밀도와 값은 다르다

fixed와 setprecision(2)를 결합하면 소수점 뒤 두 자리 표시를 요청한다. precision 설정 자체가 저장된 double을 두 자리의 십진수로 바꾸지 않는다. 출력 로캘도 소수점과 구분 표현에 영향을 주므로 기계 교환 형식에는 이를 명시해야 한다.

이 예제는 double이 이진 부동소수 표현을 사용하고 리터럴 1.25와 해당 십진 출력을 정확하게 처리하는 구현을 가정한다. 1.25=1+1/4는 이 가정에서 정확히 표현되므로 classic 로캘의 fixed 두 자리 결과는 1.25다. 일반 반올림 표시에서는 서로 다른 원래 값이 같은 텍스트로 합쳐질 수 있어 표시 문자열을 다시 읽어 원본 비트값까지 복원한다고 약속하면 안 된다. C++20이라는 언어 판본만으로 모든 구현의 부동소수 기수와 변환 정확도를 고정하지 않는다.

std::ostringstream out;
out.imbue(std::locale::classic());
out<<std::fixed<<std::setprecision(2)<<1.25;

변환 오류와 전체 소비

C++17부터의 정수 from_chars는 유효한 문자 범위를 받으며 로캘 공백을 자동 건너뛰지 않는다. 반환의 ec는 변환 오류를, ptr은 소비 끝을 나타낸다. ec가 성공이어도 ptr이 끝에 도달하지 않으면 전체 입력 계약을 충족하지 않는다.

base=10 정수 파싱은 선행 +를 허용하지 않으며 signed 타입의 −는 허용한다. 아래 정책은 그 뒤 업무 범위 0…100도 요구하므로 −1은 문법상 정수지만 업무상 거절된다. 공백을 허용하려면 별도 전처리 규칙을 추가해야 하고 조용히 정책을 바꾸면 안 된다.

한 번만 공개하는 성공 값

아래 파서는 std::string의 살아 있는 연속 범위를 사용한다. 빈 입력·너무 큰 정수·뒤 문자·범위 밖 값을 거절한다. from_chars의 표현 범위 오류에서는 대상 값이 바뀌지 않지만 그 성질을 성공 판단으로 사용하지 않고 ec로 판단한다.

C++20을 대상으로 하되 여기서는 널 종료를 요구하지 않는 from_chars와 전통 스트림 표시를 사용한다. 문법과 표시 규칙은 다른 계약이다. 이 파서는 숫자를 허용하는 텍스트에서 수량을 얻지만 UTF-8 유효성·사용자 문장·네트워크 인증까지 검증하는 것은 아니다.

#include <charconv>
#include <string>
#include <system_error>
bool quantity(const std::string& text,int& result) {
    int value=0;
    const char* first=text.data();
    const char* last=first+text.size();
    auto r=std::from_chars(first,last,value,10);
    if(r.ec!=std::errc{} || r.ptr!=last || value<0 || value>100) return false;
    result=value;
    return true;
}

새 입력의 네 줄은 3;Ada Lee, 003;Bo, 12x;Cy, 빈 줄이다. 각 줄에는 newline이 있고 이름에는 semicolon이 없다. T2 규약으로 줄·필드를 얻고 T4의 표기/전체 소비/0–100 조건을 검사한다. 기존 total=5에 허용 수량만 더하며 이름은 소유 string으로 보관한다. 각 줄은 독립 요청이며 실패 시 total을 보존한다. 마지막으로 별도 살아 있는 char a[4]={1 문자,2 문자,NUL,x 문자}의 view(a,4)를 숫자 전체 범위로 보내면 허용되는지도 설명하라. 실제 C++/서비스/학생 실행은 하지 않는다.

힌트 1

읽은 줄 수와 형식 후보·숫자 허용 수를 나눈다.

힌트 2

NUL은 명시된 네 문자 view 범위를 끝내지 않는다.

풀이와 답 확인

  1. 네 줄 읽기는 성공한다. 빈 줄 하나는 형식 거절이고 나머지 세 줄은 두 필드 형식 후보다.

  2. 3만 숫자 규약을 통과한다. 003은 선행 0, 12x는 전체 소비 조건에서 거절된다.

  3. total은 5에서 8로 한 번만 바뀌며 나머지 실패에서 8을 보존한다. 보관한 이름은 Ada Lee의 소유 복사다.

  4. 별도 view 길이는 4이며 from_chars는 12 앞부분 뒤 NUL에서 멈추므로 ptr가 끝보다 앞이다. 전체 소비 검사로 거절한다. 이 view를 임의의 C 문자열 길이 2로 축소하여 요청을 바꾸지 않는다.

읽기 4개, 형식 후보 3개, 최종 허용 1개, 최종 거절 3개다. total=8과 소유 이름 Ada Lee를 남긴다. 네 문자 view 요청은 NUL 뒤까지 범위가 남아 전체 소비 실패다.
