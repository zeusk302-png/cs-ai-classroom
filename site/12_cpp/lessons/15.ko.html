소단원 15.1

translation unit·ODR

같은 헤더를 두 cpp 파일이 읽으면 함수 정의도 두 번 만들어도 될까?

준비 개념과 학습 목표

준비 개념

  • 선언과 정의

  • include

  • 컴파일과 링크

학습 목표

  • 전처리 후 번역 단위를 설명한다.

  • 헤더 가드의 적용 범위를 구별한다.

  • 일반 함수와 inline 정의의 조건을 비교한다.

번역 단위의 경계

전통적인 include 방식의 작은 프로젝트에서는 각 cpp 파일과 그 파일이 포함한 헤더 내용을 전처리한 결과를 하나의 translation unit, 즉 번역 단위로 생각한다. a.cpp와 b.cpp가 같은 헤더를 읽어도 서로 다른 번역 단위다. 여기서는 C++ 모듈의 import 규칙을 다루지 않는다.

선언은 이름과 호출의 약속을 알려 주고 정의는 함수 본체 등을 제공한다. 서로 다른 번역 단위가 같은 함수를 호출할 때 선언을 헤더에 공유하고 일반적인 외부 함수 본체를 하나의 cpp 파일에 두는 구성을 먼저 배운다.

헤더 가드와 프로그램 전체 규칙

헤더 가드는 같은 번역 단위에서 같은 헤더를 거듭 처리하는 일을 막는다. a.cpp의 가드 상태가 b.cpp의 별도 전처리에 전달되는 것은 아니다. 따라서 가드 안에 일반 외부 함수 정의를 넣으면 두 번역 단위 각각에 정의가 생길 수 있다.

ODR은 정의를 배치하고 일치시키는 규칙이다. 이 단원의 외부 연결 비 inline·비 template 함수는 프로그램에 한 정의를 둔다. 규칙 위반이 항상 원하는 오류 메시지로 발견된다고 기대하지 않는다. 링크 성공을 ODR 준수의 증명으로 쓰지 않는다.

허용되는 반복도 조건을 가진다

inline 함수는 조건을 만족하면 여러 번역 단위에 정의를 둘 수 있다. 이 단원의 단순 헤더 함수에서는 같은 토큰과 같은 이름 해석을 유지한다. inline을 붙이는 것이 다른 함수 본체의 충돌을 모두 허용하는 것은 아니다.

inline은 이 문맥에서 정의 배치 규칙과 관련된다. 호출 코드가 반드시 본체로 치환되거나 빨라진다는 보장이 아니다. 현재 공개 작업 초안의 ODR 조항을 참고하되 본문 예제는 전통적인 C++17 프로젝트로 한정했다.

중간 과정을 따라가는 예제

가드가 있는 math.hpp에 int twice(int x) { return 2 * x; }를 넣고 a.cpp와 b.cpp가 각각 포함한다. 함수가 헤더에 한 번 적혔으니 외부 정의도 하나라는 주장을 판단하라.

  1. a.cpp의 전처리에서는 헤더를 처음 읽어 함수 본체가 들어간다. a.cpp 안에서 재포함하면 가드가 막는다.

  2. b.cpp는 별도 전처리이므로 같은 헤더의 본체가 다시 들어간다. 이 조건에서 일반 외부 함수의 정의가 두 번역 단위에 생긴다.

  3. 한 해결은 헤더를 int twice(int x); 선언으로 바꾸고 math.cpp에 본체를 한 번 두는 것이다. 다른 단순 해결은 동일한 inline 정의를 헤더에 두되 필요한 일치 조건을 유지하는 것이다.

  4. 정상 정의 twice(3)의 자체 산술은 2 × 3 = 6이다. 위반 프로그램의 실행 결과나 특정 링크 오류는 예측하지 않는다.

가드는 번역 단위 안의 반복을 막는다. 프로그램 전체의 일반 외부 함수 중복 정의를 자동 해결하지 않는다.

오해와 반례

여러 정의에는 일치 조건이 있고 기계 코드의 인라이닝과 성능은 별도 문제다.

한 단계 더

같은 헤더의 inline 본체가 조건부 매크로로 달라지는 경우를 그려 본다. 두 번역 단위의 전처리 결과를 비교하는 활동을 제안하되 실제 컴파일을 했는지 기록한다.

출처와 확인 범위
  • C++ working draft — Separate translation

    분리 번역과 전처리 번역 단위의 실제 조항을 읽었다. 전통적인 include 예제로 범위를 제한했다.

  • C++ working draft — One-definition rule

    한 번역 단위의 중복 금지, odr-use의 정의 요구, 여러 번역 단위의 비 inline 함수 및 토큰·이름 일치 조건 본문을 읽었다. 작업 초안이며 모든 모듈 조건을 강의하지 않는다.

소단원 15.2

header와 dependency

헤더 위치를 알려 주는 것과 라이브러리를 링크하는 것은 같은 일일까?

준비 개념과 학습 목표

준비 개념

  • 선언과 구현

  • 상대 경로

  • 라이브러리

학습 목표

  • 공용 헤더와 구현 파일을 나눈다.

  • include 경로와 링크 의존성을 구별한다.

  • target의 PRIVATE·PUBLIC·INTERFACE 범위를 해석한다.

자체 라이브러리의 파일 역할

자체 프로젝트는 include/stats.hpp, src/stats.cpp, tests/test_stats.cpp를 가진다. 헤더에는 std::vector<int>의 읽기 전용 참조를 받는 count_at_least 선언을 두고 구현 cpp에 반복문을 둔다. test 파일은 공용 헤더를 통해 함수를 호출한다.

헤더는 자신이 쓰는 std::vector와 std::size_t를 위해 <vector>와 <cstddef>를 직접 포함한다. 우연히 다른 헤더가 먼저 포함해 준다는 전제에 의존하지 않는다. 헤더 가드는 같은 번역 단위의 재포함을 처리한다.

찾기와 연결을 나눈다

include 경로는 컴파일할 때 stats.hpp를 찾는 데 쓰인다. 함수 정의가 담긴 라이브러리를 최종 실행 파일에 연결하는 링크 의존성은 다른 역할이다. 헤더를 찾았다는 이유로 함수 구현까지 연결됐다고 판단하지 않는다.

stats.cpp는 count_at_least의 구현이다. test_stats.cpp만 따로 컴파일하고 stats의 정의를 연결하지 않으면 호출을 만족시키지 못할 수 있다. 특정 플랫폼의 라이브러리 확장자와 오류 문구는 설치한 도구에서 확인한다.

필요한 범위만 전달한다

CMake include 경로의 PRIVATE는 해당 target만 사용하고 INTERFACE는 소비하는 쪽으로 제공한다. PUBLIC은 둘 모두다. stats.cpp와 test_stats.cpp 모두 공용 include 경로가 필요하므로 자체 예제는 stats에 PUBLIC include 경로를 둔다.

내부 구현 전용 헤더 위치를 공개 API에 필요하지 않은데 PUBLIC으로 퍼뜨리지 않는다. 반대로 공용 헤더가 외부 라이브러리 자료형을 드러내면 소비자도 필요한 의존성이 무엇인지 점검한다. scope 키워드는 저장소 접근 권한이 아니다.

중간 과정을 따라가는 예제

다음 헤더와 구현에서 {2,5,5,9}, 기준 5와 빈 배열의 반환값을 구하고 구현이 읽기 전용 계약에 맞는지 확인하라.

  1. include/stats.hpp: 

    #ifndef STATS_HPP
#define STATS_HPP
#include <cstddef>
#include <vector>
namespace stats {
std::size_t count_at_least(const std::vector<int>& values, int minimum);
}
#endif

  2. src/stats.cpp: 

    #include "stats.hpp"
namespace stats {
std::size_t count_at_least(const std::vector<int>& values, int minimum) {
    std::size_t count = 0;
    for (int value : values) {
        if (value >= minimum) ++count;
    }
    return count;
}
}

  3. 값 2는 제외되고 5, 5, 9가 포함된다. count는 0→0→1→2→3이다. 빈 vector는 반복이 없어 0을 반환한다.

  4. 함수는 원소를 복사해 읽고 입력 vector를 변경하거나 참조를 보관하지 않는다. const 참조 자체가 다른 스레드의 변경을 막아 주는 잠금은 아니다.

기준 5의 개수는 3이고 빈 입력은 0이다. 호출 동안 입력 수명이 유지되고 충돌하는 동시 변경이 없다는 계약이 필요하다.

종이와 본문으로 직접 해보기

기준을 6으로 바꿀 때 값은? include 경로를 stats의 PRIVATE로만 두면 소비자의 헤더 탐색 요구까지 자동 전달되는가?

힌트 보기

9만 세는 계산과 scope 전달을 분리한다.

풀이 보기

개수는 1이다. PRIVATE include 경로는 stats 자체에 적용되며 소비자에게 같은 경로를 인터페이스로 전달하지 않는다. 이 프로젝트는 PUBLIC이 적절하다.

오해와 반례

include가 성공하면 라이브러리의 구현도 링크됐다.

선언을 찾는 컴파일 단계와 정의를 연결하는 링크 단계를 각각 확인한다.

한 단계 더

include/stats.hpp만 별도로 포함한 작은 소비자 파일을 제안한다. 구현 전용 헤더가 필요하지 않은지 읽고, 실제 빌드 검증을 수행하지 않았다면 계획으로 남긴다.

소단원 15.3

CMake·재현 가능한 빌드

내 컴퓨터의 build 폴더를 보내면 다른 사람도 같은 조건으로 다시 만들 수 있을까?

준비 개념과 학습 목표

준비 개념

  • target과 의존성

  • 컴파일 옵션

  • 소스와 생성 파일

학습 목표

  • CMake의 설정·생성과 실제 빌드를 나눈다.

  • 라이브러리와 테스트 target을 연결한다.

  • 재현을 위한 환경 정보를 적는다.

프로젝트의 관계를 적는다

CMakeLists.txt는 target의 소스, include 경로, 언어 요구, 링크 관계를 기술한다. CMake가 설정을 읽고 선택한 generator의 빌드 파일을 만든 뒤 실제 컴파일러와 빌드 도구가 작업한다. CMake 파일을 적었다는 것만으로 실행 파일이 생긴 것은 아니다.

자체 stats는 STATIC 라이브러리이고 test_stats는 그것을 소비하는 실행 target이다. test target에 stats를 링크하면 구현의 연결과 stats가 공개한 사용 요구를 관계로 표현한다. 한 파일에 모든 환경의 절대 경로를 고정하는 방식을 피한다.

소스와 빌드 폴더를 구별한다

cmake -S . -B build는 현재 소스에서 build 디렉터리로 설정·생성을 요청한다. cmake --build build는 그 빌드 트리의 실제 빌드를 요청한다. multi-config generator에서는 --config Debug 같은 구성을 지정하고 실행 파일 위치도 구성별로 확인한다.

소스, 공용 헤더, CMakeLists.txt와 테스트 소스를 함께 보존한다. 생성된 object나 개인 머신의 CMake cache가 소스 계약을 대신하지 않는다. 다른 도구 체인을 쓸 때는 별도 빌드 트리에서 설정을 확인하는 편이 명확하다.

같은 절차와 같은 바이트는 별도다

README에 소스 revision, CMake·compiler·generator 버전, 운영체제, C++ 표준, 구성, 외부 의존성 버전과 실제 명령을 적는다. 이 자체 예제는 추가 외부 패키지가 없으며 C++17을 요구한다. 최소 CMake 버전은 사용할 명령을 위한 하한이지 설치 버전의 고정이 아니다.

같은 소스를 다시 빌드할 수 있다는 절차 재현과 산출물이 바이트 단위로 같다는 검증을 구분한다. 경로, 시간 정보, 도구 버전 등도 결과에 영향을 줄 수 있다. 이 강의에서는 새 머신 빌드나 hash 일치 실험을 하지 않았으므로 성공을 주장하지 않는다.

중간 과정을 따라가는 예제

앞 소단원의 stats 파일과 다음 설정을 읽고 include·표준 요구·링크·테스트의 경로를 설명하라. tests/test_stats.cpp 내용은 다음 소단원에 있다.

  1. CMakeLists.txt: 

    cmake_minimum_required(VERSION 3.16)
project(StatsLesson LANGUAGES CXX)
add_library(stats STATIC src/stats.cpp)
target_include_directories(stats PUBLIC ${CMAKE_CURRENT_SOURCE_DIR}/include)
target_compile_features(stats PUBLIC cxx_std_17)
add_executable(test_stats tests/test_stats.cpp)
target_link_libraries(test_stats PRIVATE stats)
enable_testing()
add_test(NAME stats_contract COMMAND test_stats)

  2. stats.cpp가 라이브러리의 구현 소스다. PUBLIC include와 cxx_std_17은 stats와 소비자가 필요한 사용 조건이다. cxx_std_17은 지원 기능을 요구하며 정확히 같은 compiler를 고정하지 않는다.

  3. test_stats는 stats에 연결된다. enable_testing과 add_test는 테스트를 등록하며 CMake 설정 단계에서 테스트를 실제로 실행하지 않는다.

  4. 제안 명령은 cmake -S . -B build, cmake --build build --config Debug, ctest --test-dir build -C Debug --output-on-failure다. 해당 도구와 지원 compiler를 설치한 환경에서 실행할 수 있도록 제안하며 여기서는 미실행이다.

소스 2개를 서로 다른 target의 역할로 배치하고 테스트 target을 라이브러리에 연결한다. 설정·빌드·테스트 실행은 각각 확인해야 한다.

소단원 15.4

API·소유권 문서와 테스트

함수의 반환값이 맞으면 입력의 수명과 소유권도 검증됐다고 할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • const 참조

  • vector의 수명

  • 테스트의 기대값

학습 목표

  • 입력의 차용과 소유권 이전을 구별한다.

  • 정상·빈 입력·경계값 테스트를 만든다.

  • 시험이 확인한 범위와 미확인 범위를 문서화한다.

사용자에게 약속을 적는다

count_at_least는 vector를 차용해 읽는다. 호출하는 동안 유효한 vector가 있어야 하며 함수는 이를 수정하거나 참조를 보관하지 않는다. 반환값은 기준 이상인 원소 개수이고 빈 입력은 0이다. 메모리 소유권을 함수로 넘기는 인터페이스가 아니다.

원소 수를 반환하므로 값의 합에 관한 int overflow 문제를 계산하지 않는다. const 참조는 이 함수 경로의 수정을 제한하며 다른 경로의 동시 쓰기를 안전하게 만들지 않는다. 계약 문서는 동시 충돌이 없다는 사용 조건도 포함한다.

표현과 책임을 맞춘다

Core Guidelines는 일반 raw pointer나 reference로 소유권 이전을 숨기는 일을 피하도록 권한다. 새 결과가 필요하면 값 반환을 고려하고 참조 의미가 필요할 때 적절한 스마트 포인터로 책임을 표현한다. 이는 설계 지침이며 모든 기존 raw pointer API를 무조건 잘못된 것으로 판정하는 언어 규칙이 아니다.

이 자체 count 함수는 이미 입력을 차용하고 정수 개수를 값으로 돌려준다. 호출자 vector를 delete하거나 해제하는 코드는 넣지 않는다. API에 반환 포인터를 추가한다면 어느 객체의 일부인지, 언제 무효화되는지, 누가 소유하는지 별도로 적어야 한다.

시험의 목적과 한계를 드러낸다

tests/test_stats.cpp는 경계 포함, 빈 입력, 아무 값도 포함하지 않는 경우와 입력 보존을 확인한다. 기대값을 API 계약에서 직접 만든다. 테스트가 코드와 같은 잘못된 비교식을 복제하면 오류를 놓칠 수 있으므로 >= 계약과 > 변이의 차이를 직접 비교한다.

테스트는 실패 시 비영 종료를 반환하므로 Release에서 assert가 비활성화되는 문제에 의존하지 않는다. 몇 개의 시험 통과로 모든 길이·수명·동시성·ABI·다른 compiler를 검증했다고 주장하지 않는다. 실제 테스트 실행도 아직 하지 않았다.

중간 과정을 따라가는 예제

다음 테스트의 기대값을 계산하고 구현의 >=를 >로 잘못 바꾸면 어느 조건이 실패하는지 판단하라.

  1. tests/test_stats.cpp: 

    #include "stats.hpp"
#include <vector>
int main() {
    const std::vector<int> values{2, 5, 5, 9};
    if (stats::count_at_least(values, 5) != 3) return 1;
    if (stats::count_at_least(values, 10) != 0) return 2;
    if (stats::count_at_least({}, 5) != 0) return 3;
    if (values != std::vector<int>{2, 5, 5, 9}) return 4;
    return 0;
}

  2. 정상 계약에서 기준 5는 5, 5, 9를 포함해 3이다. 기준 10은 0이고 빈 임시 vector는 호출 동안 유효하며 개수 0이다.

  3. 입력을 보관하지 않는 구현이므로 빈 임시 vector가 호출 뒤 파괴되는 것이 저장된 참조 문제를 만들지 않는다. values의 네 원소는 그대로여서 입력 보존 조건도 만족한다.

  4. > 변이는 기준 5에서 9 하나만 세어 1이 된다. 첫 기대값 3과 달라 return 1 경로를 예상한다. 정상 구현은 네 조건을 통과하여 return 0으로 예상하지만 실제 C++ 실행 결과는 아니다.

정상 예상 종료 상태는 0이고 > 변이의 예상 상태는 1이다. 계약에서 만든 경계값 시험이 비교 연산 오류를 드러낸다.
