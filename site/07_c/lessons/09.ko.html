소단원 9.1

구조체와 member 접근

학생 이름표에 번호와 점수를 함께 붙이면 변수 관리는 어떻게 바뀔까?

준비 개념과 학습 목표

준비 개념

  • 기본형 변수

  • 포인터와 주소

학습 목표

  • 구조체 값과 구조체 포인터의 접근 문법을 구별한다.

  • 값 복사와 포인터 별칭의 효과를 추적한다.

기록을 복사했는데 왜 내부 화살표가 같은 값을 볼까?

새 struct Box { int count; int *reading; };와 살아 있는 int sensor=7을 둔다. a={2,&sensor}, b=a, p=&a로 초기화한다. b.count=5는 b의 별도 int member만 바꾼다. *b.reading=9는 두 기록이 공유하는 sensor를 바꾼다. p->count=3은 p가 가리킨 a의 member를 바꾼다. 기록의 값 복사와 포인터 member의 대상 공유를 같은 그림에 표시하면 어떤 저장 칸이 독립인지 분리할 수 있다.

b=a는 member의 값을 복사하지만 동적 블록이나 외부 객체를 새로 만들지 않는다. count는 별도 칸이고 reading은 같은 대상의 주소값을 가진 별도 포인터 칸이다. 대상 sensor와 기록 a/b의 수명·수정 권한은 모두 유지된다고 전제한다. 구조체 대입은 소유권 전달이나 깊은 복사 계약을 자동 제공하지 않으며 실제 C 실행은 하지 않는다.

먼저 확인할 개념
  • 별칭과 값 스냅샷

    정수 member와 포인터 member의 복사 효과를 분리한다.

  • 소유권과 빌림

    구조체 값 복사가 해제 책임을 복제하지 않음을 설명한다.

관련 있는 값을 하나의 기록으로 묶기

struct는 여러 member를 가진 기록 형식이다. struct Result { int id; int score; };는 학생 번호와 점수를 한 값으로 다루는 형식을 정의한다. 형식 정의만으로 특정 학생의 값이 생기는 것은 아니며 별도 변수를 선언해야 한다.

서로 다른 member는 각자 값을 가진다. 아래 예제에서는 a.id와 a.score가 한 기록에 속하지만 점수 변경이 학생 번호 변경을 뜻하지는 않는다. 필요한 필드를 의미에 맞게 선택해야 한다.

점과 화살표로 같은 필드 찾아가기

구조체 객체에는 a.score처럼 점을 쓴다. 해당 객체를 가리키는 유효한 포인터 p에는 p->score를 쓴다. p->score는 (*p).score와 같은 member를 지정하며 괄호는 연산자의 결합 순서를 분명하게 한다.

포인터가 NULL이거나 이미 수명이 끝난 객체를 가리키면 접근할 수 없다. 화살표 문법 자체가 주소의 유효성을 검사하지 않으므로 접근 전에 수명과 주소 조건을 생각해야 한다.

struct Result { int id; int score; };
struct Result a = {3, 70};
struct Result b = a;
struct Result *p = &a;
p->score += 5;
b.score = 40;

복사와 같은 객체의 다른 이름 구별하기

b=a는 이 예제의 정수 member 값을 복사해 별도 기록 b를 만든다. p=&a는 a를 가리키는 주소를 저장하므로 p를 통한 변경은 a에 나타난다. 값 복사와 주소 복사는 결과가 다르다.

구조체에 포인터 member가 있다면 그 member의 주소 값도 복사된다. 가리키는 데이터까지 깊게 복사되는 것은 아니다. 현재 예제의 독립성은 두 member가 정수인 조건에서 이해해야 한다.

각 기록의 reading 칸은 별도로 존재한다. 표에서 대상이 같은 것은 두 칸에 저장된 주소가 같아서이며 구조체 자체가 같은 객체이기 때문은 아니다. p는 계속 a를 지정한다.

중간 과정을 따라가는 예제

위 코드에서 마지막 a와 b의 id, score를 계산하라. 모든 포인터 접근은 유효하다고 가정한다.

  1. 처음 a=(3,70)이고 b=a 후 b=(3,70)이다.

  2. p는 a의 주소를 저장한다. p->score+=5는 a.score를 75로 바꾼다.

  3. b.score=40은 별도 객체 b의 점수만 바꾼다.

  4. id에는 대입하지 않았으므로 둘 다 3이다.

a=(3,75), b=(3,40)이다.

조건을 바꾸어 비교하기

포인터 member를 다시 지정한다

표 뒤 새 int spare=20을 두고 b.reading=&spare; *b.reading=21;을 수행한다.

  1. b의 포인터 칸만 spare를 지정한다.

  2. sensor는 9, spare는 21이며 a.reading은 sensor를 계속 지정한다.

두 기록의 관찰 대상이 이제 다르다.

비교할 점

대상 값 쓰기와 포인터 member 재대입을 나눈다.

구조체 안의 배열은 별도 저장이다

struct Label {char text[3];}; x={{'A','B',0}}, y=x; 뒤 y.text[0]='Z'를 쓴다.

  1. 배열 member의 내용은 구조체 값 복사에 포함된다.

  2. x의 text는 AB, y의 text는 ZB이며 각각 자기 저장 칸이다.

포인터 member와 달리 이 배열은 복사된 기록 안에 있다.

비교할 점

배열 단독 대입 금지와 구조체 전체 대입의 배열 member 복사를 혼동하지 않는다.

종이와 본문으로 직접 해보기

마지막에 (*p).id=8을 추가하면 두 기록은 어떻게 되는가?

힌트 보기

p가 어느 객체의 주소를 가진지 먼저 표시한다.

풀이 보기

p는 여전히 a를 가리킨다. a.id만 8로 바뀌어 a=(8,75), b=(3,40)이 된다.

오해와 반례

구조체를 복사하면 내부 포인터가 가리키는 데이터도 모두 복제된다.

포인터 member는 주소 값으로 복사된다. 같은 외부 데이터를 함께 가리킬 수 있으므로 복사 후 독립성은 member의 형식에 따라 달라진다.

자기점검

객체 a의 점수 접근은?

답과 이유 보기

a.score.

점은 객체의 member를 선택한다.

포인터 p의 점수 접근은?

답과 이유 보기

p->score 또는 (*p).score.

먼저 p가 가리키는 객체를 찾는다.

NULL에 화살표를 쓰면 안전한가?

답과 이유 보기

아니다.

유효한 객체를 가리킨다는 조건이 필요하다.

스스로 풀어보기

먼저 답과 이유를 적고, 필요한 만큼 힌트를 한 단계씩 열어 보세요.

연습 1 · 값과 상태 예측

표 뒤 b.reading=&spare를 하기 전 int saved=*a.reading을 복사하고 sensor=12로 바꾼다. saved와 두 관찰값은?

힌트 1

saved는 별도 int다.

힌트 2

두 reading은 아직 같은 sensor다.

풀이와 답 확인

  1. saved는 9를 보존한다.

  2. *a.reading과 *b.reading은 모두 12다.

9 / 12 / 12다.

흔한 오답에서 다시 생각하기

saved도 포인터이므로 12다.

선언된 int 값 복사에는 주소 경로가 없다.

연습 2 · 오류 찾아 고치기

동적 블록을 가리키는 owner member가 있는 a를 b=a로 복사한 뒤 a.owner와 b.owner를 각각 free했다. 책임을 고쳐라.

힌트 1

포인터 대상은 새로 만들어지지 않았다.

힌트 2

소유자와 빌린 관찰을 분리한다.

풀이와 답 확인

  1. 같은 블록 두 번 해제를 하지 않는다.

  2. 하나만 소유하게 명시하거나 새 블록을 실제 별도로 할당/복사하는 깊은 복사 설계를 둔다.

대입과 독립 소유 생성은 다르다.

흔한 오답에서 다시 생각하기

기록 두 개라 동적 블록도 두 개다.

포인터 member 값 복사가 블록 할당을 수행하지 않는다.

연습 3 · 직접 만들어 보기

a.count만 8로 바꾸는 객체/포인터 표현을 두 개 쓰라. p=&a는 유효하다.

힌트 1

점과 화살표를 비교한다.

힌트 2

대상 정체성은 같다.

풀이와 답 확인

  1. a.count=8과 p->count=8을 각각 쓸 수 있다.

  2. (*p).count=8도 같은 member를 지정한다.

형식이 다른 접근 문법이 같은 객체를 지정한다.

흔한 오답에서 다시 생각하기

p.count는 a의 member다.

p 자체는 포인터 객체여서 점으로 Box member를 고르지 않는다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

sensor가 안쪽 블록의 자동 int였다면 그 블록 뒤 b를 복사해 두었다는 사실이 reading 대상 수명을 늘리는가?

힌트 1

복사된 주소와 대상 수명을 분리한다.

힌트 2

필요한 정수 값은 종료 전에 복사한다.

풀이와 답 확인

  1. 구조체 복사는 sensor의 수명을 늘리지 않는다.

  2. 종료 전에 값 snapshot을 별도 int member로 복사하거나 더 오래 살아 있는 저장소를 설계한다.

종료 뒤 낡은 reading 값을 읽지 않는다.

흔한 오답에서 다시 생각하기

구조체가 밖에 살아 있으니 내부 대상도 살아 있다.

기록의 수명과 포인터 대상의 수명은 각각이다.

내 말로 설명하기

기록 안 배열과 포인터 복사는?

배열 member는 기록 안 별도 저장으로 복사되고 포인터 member는 주소값을 복사한다.

포인터 member가 소유자라는 근거는?

소단원 9.2

typedef·enum

점수를 int라고 쓰는 대신 뜻 있는 이름을 붙이면 새로운 형식이 생길까?

준비 개념과 학습 목표

준비 개념

  • 정수 상수

  • 형식 선언

학습 목표

  • 형식 별칭과 새 형식의 차이를 말한다.

  • 열거 상수의 값을 순서대로 계산한다.

같은 숫자의 상태 이름 두 개를 switch로 구별할 수 있을까?

새 enum Mode {OFF=0, RUN=4, ACTIVE=4, STOP};는 0/4/4/5의 상수값을 갖는다. RUN과 ACTIVE는 같은 정수 4의 이름이므로 저장된 숫자만 보고 어느 이름으로 대입했는지 복원하지 못한다. 두 이름을 switch의 서로 다른 case로 쓰면 같은 값 case 중복이라는 제약을 위반한다. 이름을 추가하는 것과 구별할 수 있는 상태를 늘리는 것은 다르다.

typedef int Count;와 typedef int Score;는 둘 다 int의 별칭이다. Count 값을 Score 변수에 대입했다는 이유만으로 형식 오류나 0–100 검사가 생기지 않는다. 외부 코드에는 OFF/RUN/STOP의 숫자 약속을 별도로 고정하고 알 수 없는 입력을 검증해야 한다. 아래 C11 초안의 enum 규칙은 다른 C 개정의 확장을 설명한 것이 아니다.

먼저 확인할 개념
  • 정수형의 범위와 부호

    외부 숫자와 실제 저장형의 허용 범위를 구별한다.

  • 성공 상태와 결과값

    외부 숫자 검증의 실패 상태를 enum 결과와 다른 통로로 보낸다.

이름으로 의도 보여 주기

typedef int Score;는 기존 int 형식에 Score라는 별칭을 붙인다. Score s=90;처럼 쓰면 점수라는 의도가 드러나지만 int와 구별되는 독립적인 강한 형식이 되는 것은 아니다. 이름을 붙였다는 이유만으로 점수 범위가 검사되지도 않는다.

구조체 선언과 함께 별칭을 붙이면 사용부의 표현을 줄일 수 있다. typedef struct { int id; int score; } Result;는 Result라는 이름으로 기록을 선언하게 한다. 별칭의 편리함과 값 검증 책임을 구별하자.

선택지에 정수 이름 붙이기

enum은 상태와 같은 선택지에 이름을 붙인다. 이 단원의 C11 기본 규칙에서는 값을 지정하지 않은 첫 상수는 0이고 이후에는 직전 상수보다 1 크다. 중간에 값을 명시하면 그 뒤의 자동 값도 그 숫자에서 이어진다.

열거 상수는 이름 있는 정수 상수이며 값이 같아도 선언될 수 있다. enum 변수의 내부 정수 형식은 구현 선택과 관련되므로 저장 크기를 항상 4바이트라고 가정하지 않는다. C의 enum은 모든 불법 상태 값을 자동으로 막는 장치가 아니다.

typedef int Score;
enum State { IDLE, RUN = 4, STOP, FAULT = 9 };
Score score = 72;
enum State state = STOP;

표시 이름과 저장 규약을 따로 정하기

switch로 각 상태의 행동을 나누되 알 수 없는 숫자의 처리도 설계한다. 별칭은 범위 검사 함수와 함께, 열거형은 입력 검증과 함께 사용할 때 의도와 실제 허용 조건이 일치한다.

소단원 9.3

union과 표현

정수 또는 실수를 담는 한 칸에 지금 어떤 종류의 값이 들어 있는지 누가 기억할까?

준비 개념과 학습 목표

준비 개념

  • struct와 member

  • enum 상태 이름

학습 목표

  • 공용체 저장 공간의 중첩을 설명한다.

  • 태그와 현재 값 종류를 일치시키는 규칙을 설계한다.

새 값을 거절할 때 태그만 먼저 바꿔도 될까?

새 기록은 enum Kind {COUNT,RATIO};와 int count/double ratio 공용체를 갖는다. 순차 API set_ratio는 0–1의 유한 입력만 허용하고 실패 때 기존 기록을 보존한다고 정한다. 초기 COUNT/count=6에서 후보 1.5를 받았다면 태그나 payload를 쓰기 전에 거절해야 한다. 후보 .5는 검사 뒤 지역 후보 RATIO/ratio=.5를 완성하고 전체 기록에 대입한다.

태그와 payload의 일치는 자체 불변식이다. 별도 관찰자는 호출 중간을 보지 않는 순차 계약이며 기록 대입이 동시 원자적이라고 주장하지 않는다. 공용체의 다른 member 읽기를 숫자 변환으로 쓰지 않는다. 표의 숫자는 선택한 member로만 해석하고 다른 표현이나 trap 가능성을 실제 실행하지 않는다.

먼저 확인할 개념
  • 검사 뒤 결과 커밋

    태그 변경보다 실패 조건 검사를 먼저 끝낸다.

  • 형변환과 정수 승격

    값 변환과 저장 비트 재해석의 차이를 연결한다.

여러 칸이 같은 저장 공간을 사용하기

union은 여러 member의 저장 공간이 겹치는 형식이다. struct가 여러 값을 함께 보관하는 기록이라면 union은 한 시점의 값 표현을 선택하는 용도로 생각할 수 있다. int와 double member가 있다고 두 값을 동시에 독립 보관하는 것은 아니다.

union의 크기는 가장 큰 member를 담을 수 있어야 하며 정렬과 여백 때문에 정확한 크기는 구현에 따라 달라질 수 있다. member 크기를 전부 더해서 공용체 크기를 구하는 방법은 맞지 않는다.

현재 값 종류는 태그에 기록하기

다음 tagged union은 kind와 value를 함께 가진 구조체다. kind가 COUNT이면 value.count, RATIO이면 value.ratio를 읽는다는 규칙을 만든다. C 문법이 두 필드의 일치를 자동으로 검사하지 않으므로 쓰기와 읽기 함수에서 이 불변조건을 지켜야 한다.

태그를 RATIO로 바꾸고 count에만 값을 쓰는 행동은 규약 위반이다. 새로운 값을 넣을 때 데이터와 태그를 같은 논리 작업으로 갱신한다. 동시 접근이 있다면 중간 상태의 노출을 막는 문제도 추가된다.

enum Kind { COUNT, RATIO };
union Value { int count; double ratio; };
struct Item { enum Kind kind; union Value value; };
struct Item x = {COUNT, {.count = 5}};
x.value.ratio = 0.25;
x.kind = RATIO;

다른 member 읽기를 값 변환과 혼동하지 않기

정수를 실수로 변환하려면 (double)n처럼 변환 연산을 쓴다. union의 다른 member로 읽는 일은 저장 비트를 다른 표현으로 해석하는 문제다. C11에서는 이 재해석이 명시되어 있지만 표현과 trap 가능성 등 조건이 있어 이식 가능한 숫자 변환으로 사용할 수 없다.

C++의 union 수명 규칙과도 혼동하지 않는다. 이 단원에서는 마지막으로 저장한 종류에 맞는 member를 읽는 규약을 기본으로 사용한다. 외부 비트 형식을 조사하는 고급 코드는 별도로 표현 조건을 검토해야 한다.

위 x의 초기 상태와 두 대입 이후의 상태를 태그 규약으로 설명하라. 동시 관찰자는 없다고 가정한다.

  1. 처음 kind=COUNT이며 count=5가 저장되어 있다.

  2. ratio=0.25 대입 후에는 실수 값의 저장 공간을 사용한다. 이전 count=5 보존을 기대하지 않는다.

  3. kind=RATIO 대입으로 종류 표시가 실수와 일치한다.

  4. 최종 독자는 kind를 보고 ratio를 선택해야 한다.

초기는 개수 5, 최종은 비율 0.25다. 같은 union에 개수 5도 남아 있다고 단정할 수 없다.

  1. payload에는 아직 count=6을 저장한 상태다.

  2. 기존 기록 보존과 태그/payload 일치를 모두 잃는다.

태그 검사/커밋 순서를 수정한다.

비교할 점

실패 상태 반환만으로 이전 기록을 되돌리지 않는다.

명시적 숫자 변환

정상 COUNT/count=6을 ratio에 수학적으로 6.0으로 변환하고 싶다. 단, set_ratio의 0–1 규약은 그대로다.

  1. (double)count는 표현 재해석과 다른 숫자 변환이다.

  2. 6.0은 정상 변환 결과지만 set_ratio 범위 밖이어서 이번 API는 거절한다.

언어 변환 성공과 업무 입력 허용은 별도다.

비교할 점

숫자 변환이 된다는 사실만으로 모든 후속 API에 허용되는 것은 아니다.

소단원 9.4

padding·정렬과 직렬화 주의

기록의 필드가 6바이트라면 파일에도 6바이트만 쓰면 될까?

준비 개념과 학습 목표

준비 개념

  • 바이트와 주소

  • 구조체 필드

학습 목표

  • 명시한 배치 모델에서 여백과 sizeof를 계산한다.

  • 메모리 배치와 외부 직렬화 규약을 구별한다.

같은 기록 두 개의 메모리 바이트가 반드시 같을까?

새 가상 ABI는 char 크기/정렬 1, short 크기/정렬 2, int 크기/정렬 4이며 구조체 정렬은 member 정렬의 최댓값으로 정한다. struct Packet {char tag; short code; int count;}에서 tag는 offset 0이고 offset 1에 여백을 둔다. code는 2–3, count는 4–7에 놓여 전체 크기는 8바이트다. 이 모델은 실제 ABI 측정이나 모든 C 구현의 정답이 아니다.

외부 규약은 호스트 배치와 독립적으로 8-bit octet을 사용해 tag 1개 / code 2개 / count 2개, 총 5개를 큰 자리부터 보낸다고 정한다. code/count는 0–65535 범위로 검증한다. tag=1, code=0x0201, count=3의 전송은 [01,02,01,00,03]이다. padding이나 host int 바이트를 복사하지 않는다. 논리 필드가 같아도 padding 표현은 같다고 보장되지 않으므로 memcmp를 필드 동등성의 필요조건으로 쓰지 않는다. 새 송신은 이미 유효한 비음수 short code가 외부 범위에도 속할 때만 허용한다. short의 크기가 2바이트라는 가정은 65535의 signed 표현 가능성을 보장하지 않는다. 수신 wire code가 0–65535여도 SHRT_MAX보다 크면 short에 대입하기 전에 거절한다. 더 넓은 범위를 저장하려면 unsigned 또는 충분한 범위의 다른 형을 쓰는 별도 호스트 설계를 정한다. count도 INT_MAX를 넘으면 int 대입 전에 거절한다. 여기서 사용한 0x0201과 0x1234 및 count 3/256은 기본 short/int 최소 보장 범위 안이다.

먼저 확인할 개념
  • 바이트 길이와 저장 용량

    고정 외부 길이와 문자열 종료 규약을 혼동하지 않는다.

  • 정수형의 범위와 부호

    외부 16-bit 범위와 signed short/int 표현 가능성을 각각 확인한다.

필드 사이에 빈 공간이 들어갈 수 있다

정렬은 특정 형식의 객체를 놓을 주소 경계와 관련된다. 구현은 구조체 member의 선언 순서를 유지하면서 사이와 끝에 padding을 둘 수 있다. 처음 member 앞에 padding을 두지 않는 C11 규칙과 모든 필드가 빈틈없이 붙는다는 주장은 다르다.

이 단원 계산은 char 크기·정렬 1, int 크기·정렬 4, 구조체 정렬 4인 가상 모델이다. 실제 ABI와 컴파일러 설정에서는 크기·정렬이 다를 수 있으므로 계산 결과를 모든 C 환경의 상수로 외우지 않는다.

배치표를 주소 순서로 계산하기

char a; int b; char c; 순서라면 a는 offset 0에 놓인다. 다음 int는 4의 배수 경계에서 시작해야 하므로 1~3은 빈 공간이다. b는 4~7, c는 8이다. 연속 배열의 다음 구조체도 정렬을 맞추도록 9~11에 끝 여백을 두어 크기 12가 된다.

같은 모델에서 int b; char a; char c; 순서라면 b가 0~3, a가 4, c가 5이고 6~7에 끝 여백을 둔다. 크기는 8이다. 필드 순서 변경은 외부 인터페이스에 영향이 있으므로 공간 절약만 보고 공개 형식을 바꾸지 않는다.

파일에는 값의 약속을 써야 한다

구조체 전체 바이트를 그대로 전송하면 padding, 정수 바이트 순서, 형식 크기 차이가 외부로 드러난다. padding 값도 필드의 논리적 값이 아니므로 두 구조체의 memcmp 결과를 필드 동등성으로 단정하지 않는다.

직렬화는 각 필드의 폭과 순서, 부호, 바이트 순서를 명시하는 과정이다. 예를 들어 8비트 octet을 쓰는 규약에서 16비트 비음수 값 0x1234를 큰 자리부터 보내면 0x12,0x34다. 이 규약은 호스트 int 크기와 별개이며 범위 검사와 CHAR_BIT=8 등의 구현 조건을 확인해야 한다.

중간 과정을 따라가는 예제

위 가상 모델에서 char/int/char 구조체의 필드 합, 내부 padding, 끝 padding, 전체 크기를 계산하라.

  1. 필드 크기 합은 1+4+1=6바이트다.

  2. int를 offset 4에 놓기 위해 1~3에 내부 padding 3바이트가 들어간다.

  3. 마지막 char 뒤의 9~11에 끝 padding 3바이트가 들어간다.

  4. 전체 크기는 6+3+3=12바이트다.

필드 합은 6, 내부 여백은 3, 끝 여백은 3, 전체는 12바이트다. 이 결과는 명시한 모델에 한정된다.

다른 문제에 적용하기

새 순차 기록은 tag=1, code=0x0201, count=3이며 앞의 가상 Packet ABI와 5octet 외부 규약을 사용한다. Packet b=a로 값을 복사하고 b.count=256으로 변경한다. 각각의 메모리 크기와 외부 바이트를 구하라. 별도로 enum OFF=0/RUN=4/ACTIVE=4/STOP의 외부 숫자 4를 읽었을 때 RUN/ACTIVE의 원래 이름을 알 수 있는지 판단하라. 새 COUNT/count=6 tagged union에 set_ratio 후보 1.5를 넣을 때 실패 보존 절차를 적어라. 실제 C/파일/네트워크 실행은 하지 않는다.

힌트 1

정수 member의 구조체 복사와 외부 직렬화의 범위/순서를 따로 계산한다.

힌트 2

같은 숫자의 이름 역사와 태그/payload 상태 보존은 다른 정보 문제다.

풀이와 답 확인

  1. b.count만 256으로 바뀌어 a.count=3은 보존된다. 두 객체의 가상 크기는 각각 8바이트다.

  2. a는 [01,02,01,00,03], b는 [01,02,01,01,00]으로 각각 5octet이다.

  3. 외부 숫자 4는 RUN/ACTIVE 모두의 상수값이라 원래 어느 이름으로 대입했는지 알 수 없다.

  4. 후보 1.5는 0–1 범위 밖이므로 태그/payload 쓰기 전에 실패해 COUNT/count=6을 보존한다.

  5. 메모리 모델·외부 규약·값 변환·상태 계약의 확인과 실제 실행을 구별한다.

두 가상 구조체는 각각 8바이트, 외부 기록은 각각 5octet이다. a와 b의 count는 3/256이며 코드 4의 원래 alias 이름은 복원 불가다. tagged union은 거절 후 COUNT/6을 유지한다.

해결한 뒤 점검할 것

  • 값 복사의 독립 int member를 추적한다.

  • 외부 폭/순서와 가상 padding을 분리한다.

  • 동일 enum 숫자의 정보 손실을 설명한다.

  • 실패 때 태그와 payload 모두 보존한다.
