소단원 9.1

구조체와 member 접근

학생 이름표에 번호와 점수를 함께 붙이면 변수 관리는 어떻게 바뀔까?

준비 개념과 학습 목표

준비 개념

  • 기본형 변수
  • 포인터와 주소

학습 목표

  • 구조체 값과 구조체 포인터의 접근 문법을 구별한다.
  • 값 복사와 포인터 별칭의 효과를 추적한다.

관련 있는 값을 하나의 기록으로 묶기

struct는 여러 member를 가진 기록 형식이다. struct Result { int id; int score; };는 학생 번호와 점수를 한 값으로 다루는 형식을 정의한다. 형식 정의만으로 특정 학생의 값이 생기는 것은 아니며 별도 변수를 선언해야 한다.

서로 다른 member는 각자 값을 가진다. 아래 예제에서는 a.id와 a.score가 한 기록에 속하지만 점수 변경이 학생 번호 변경을 뜻하지는 않는다. 필요한 필드를 의미에 맞게 선택해야 한다.

점과 화살표로 같은 필드 찾아가기

구조체 객체에는 a.score처럼 점을 쓴다. 해당 객체를 가리키는 유효한 포인터 p에는 p->score를 쓴다. p->score는 (*p).score와 같은 member를 지정하며 괄호는 연산자의 결합 순서를 분명하게 한다.

포인터가 NULL이거나 이미 수명이 끝난 객체를 가리키면 접근할 수 없다. 화살표 문법 자체가 주소의 유효성을 검사하지 않으므로 접근 전에 수명과 주소 조건을 생각해야 한다.

struct Result { int id; int score; };
struct Result a = {3, 70};
struct Result b = a;
struct Result *p = &a;
p->score += 5;
b.score = 40;

복사와 같은 객체의 다른 이름 구별하기

b=a는 이 예제의 정수 member 값을 복사해 별도 기록 b를 만든다. p=&a는 a를 가리키는 주소를 저장하므로 p를 통한 변경은 a에 나타난다. 값 복사와 주소 복사는 결과가 다르다.

구조체에 포인터 member가 있다면 그 member의 주소 값도 복사된다. 가리키는 데이터까지 깊게 복사되는 것은 아니다. 현재 예제의 독립성은 두 member가 정수인 조건에서 이해해야 한다.

중간 과정을 따라가는 예제

위 코드에서 마지막 a와 b의 id, score를 계산하라. 모든 포인터 접근은 유효하다고 가정한다.

  1. 처음 a=(3,70)이고 b=a 후 b=(3,70)이다.
  2. p는 a의 주소를 저장한다. p->score+=5는 a.score를 75로 바꾼다.
  3. b.score=40은 별도 객체 b의 점수만 바꾼다.
  4. id에는 대입하지 않았으므로 둘 다 3이다.

a=(3,75), b=(3,40)이다.

힌트 보기

풀이 보기

오해와 반례

구조체를 복사하면 내부 포인터가 가리키는 데이터도 모두 복제된다.

포인터 member는 주소 값으로 복사된다. 같은 외부 데이터를 함께 가리킬 수 있으므로 복사 후 독립성은 member의 형식에 따라 달라진다.

소단원 9.2

typedef·enum

점수를 int라고 쓰는 대신 뜻 있는 이름을 붙이면 새로운 형식이 생길까?

준비 개념과 학습 목표

준비 개념

  • 정수 상수
  • 형식 선언

학습 목표

  • 형식 별칭과 새 형식의 차이를 말한다.
  • 열거 상수의 값을 순서대로 계산한다.

이름으로 의도 보여 주기

typedef int Score;는 기존 int 형식에 Score라는 별칭을 붙인다. Score s=90;처럼 쓰면 점수라는 의도가 드러나지만 int와 구별되는 독립적인 강한 형식이 되는 것은 아니다. 이름을 붙였다는 이유만으로 점수 범위가 검사되지도 않는다.

구조체 선언과 함께 별칭을 붙이면 사용부의 표현을 줄일 수 있다. typedef struct { int id; int score; } Result;는 Result라는 이름으로 기록을 선언하게 한다. 별칭의 편리함과 값 검증 책임을 구별하자.

선택지에 정수 이름 붙이기

enum은 상태와 같은 선택지에 이름을 붙인다. 이 단원의 C11 기본 규칙에서는 값을 지정하지 않은 첫 상수는 0이고 이후에는 직전 상수보다 1 크다. 중간에 값을 명시하면 그 뒤의 자동 값도 그 숫자에서 이어진다.

열거 상수는 이름 있는 정수 상수이며 값이 같아도 선언될 수 있다. enum 변수의 내부 정수 형식은 구현 선택과 관련되므로 저장 크기를 항상 4바이트라고 가정하지 않는다. C의 enum은 모든 불법 상태 값을 자동으로 막는 장치가 아니다.

typedef int Score;
enum State { IDLE, RUN = 4, STOP, FAULT = 9 };
Score score = 72;
enum State state = STOP;

표시 이름과 저장 규약을 따로 정하기

IDLE 같은 이름은 프로그램 이해를 돕는다. 외부 파일이나 통신에 상태를 보낼 때는 코드값 0,4,5,9를 명시한 규약이 필요하다. 나중에 선언 순서를 바꾸면 자동 값이 바뀔 수 있으므로 외부 약속에는 의도적으로 숫자를 지정하는 편이 분명하다.

switch로 각 상태의 행동을 나누되 알 수 없는 숫자의 처리도 설계한다. 별칭은 범위 검사 함수와 함께, 열거형은 입력 검증과 함께 사용할 때 의도와 실제 허용 조건이 일치한다.

중간 과정을 따라가는 예제

위 선언에서 IDLE, RUN, STOP, FAULT의 값과 state가 가진 상수값을 구하라.

  1. IDLE은 첫 상수이며 지정이 없으므로 0이다.
  2. RUN은 명시적으로 4다.
  3. STOP은 바로 앞 RUN의 다음 값 4+1=5다.
  4. FAULT는 명시값 9이고 state=STOP이므로 state에 해당하는 값은 5다.

상수값은 0,4,5,9이며 state는 STOP(5)이다.

종이와 본문으로 직접 해보기

RUN=4 다음에 PAUSE를 새로 삽입하고 STOP을 그 뒤에 두면 두 자동 값은?

힌트 보기

이전 상수+1 규칙을 두 번 적용한다.

풀이 보기

PAUSE=5, STOP=6이다. 기존 STOP의 외부 코드 5를 유지해야 한다면 순서 변화에 맡기지 말고 명시값과 충돌 규칙을 검토해야 한다.

오해와 반례

typedef로 Score를 만들면 음수나 int 대입이 자동 금지된다.

Score는 int의 별칭이므로 형식 이름만으로 점수 범위가 강제되지 않는다. 0~100 검사는 입력과 대입 경계에 별도로 둬야 한다.

답과 이유 보기

구현별 표현과 외부 저장 규약을 구별해야 한다.

한 단계 더

세 상태를 파일 코드로 저장할 때 각 값, 알 수 없는 값의 처리, 다음 버전에서 보존해야 할 값의 표를 작성해 보자.

소단원 9.3

union과 표현

정수 또는 실수를 담는 한 칸에 지금 어떤 종류의 값이 들어 있는지 누가 기억할까?

준비 개념과 학습 목표

준비 개념

  • struct와 member
  • enum 상태 이름

학습 목표

  • 공용체 저장 공간의 중첩을 설명한다.
  • 태그와 현재 값 종류를 일치시키는 규칙을 설계한다.

여러 칸이 같은 저장 공간을 사용하기

union은 여러 member의 저장 공간이 겹치는 형식이다. struct가 여러 값을 함께 보관하는 기록이라면 union은 한 시점의 값 표현을 선택하는 용도로 생각할 수 있다. int와 double member가 있다고 두 값을 동시에 독립 보관하는 것은 아니다.

union의 크기는 가장 큰 member를 담을 수 있어야 하며 정렬과 여백 때문에 정확한 크기는 구현에 따라 달라질 수 있다. member 크기를 전부 더해서 공용체 크기를 구하는 방법은 맞지 않는다.

현재 값 종류는 태그에 기록하기

다음 tagged union은 kind와 value를 함께 가진 구조체다. kind가 COUNT이면 value.count, RATIO이면 value.ratio를 읽는다는 규칙을 만든다. C 문법이 두 필드의 일치를 자동으로 검사하지 않으므로 쓰기와 읽기 함수에서 이 불변조건을 지켜야 한다.

태그를 RATIO로 바꾸고 count에만 값을 쓰는 행동은 규약 위반이다. 새로운 값을 넣을 때 데이터와 태그를 같은 논리 작업으로 갱신한다. 동시 접근이 있다면 중간 상태의 노출을 막는 문제도 추가된다.

enum Kind { COUNT, RATIO };
union Value { int count; double ratio; };
struct Item { enum Kind kind; union Value value; };
struct Item x = {COUNT, {.count = 5}};
x.value.ratio = 0.25;
x.kind = RATIO;

다른 member 읽기를 값 변환과 혼동하지 않기

정수를 실수로 변환하려면 (double)n처럼 변환 연산을 쓴다. union의 다른 member로 읽는 일은 저장 비트를 다른 표현으로 해석하는 문제다. C11에서는 이 재해석이 명시되어 있지만 표현과 trap 가능성 등 조건이 있어 이식 가능한 숫자 변환으로 사용할 수 없다.

C++의 union 수명 규칙과도 혼동하지 않는다. 이 단원에서는 마지막으로 저장한 종류에 맞는 member를 읽는 규약을 기본으로 사용한다. 외부 비트 형식을 조사하는 고급 코드는 별도로 표현 조건을 검토해야 한다.

중간 과정을 따라가는 예제

위 x의 초기 상태와 두 대입 이후의 상태를 태그 규약으로 설명하라. 동시 관찰자는 없다고 가정한다.

  1. 처음 kind=COUNT이며 count=5가 저장되어 있다.
  2. ratio=0.25 대입 후에는 실수 값의 저장 공간을 사용한다. 이전 count=5 보존을 기대하지 않는다.
  3. kind=RATIO 대입으로 종류 표시가 실수와 일치한다.
  4. 최종 독자는 kind를 보고 ratio를 선택해야 한다.

초기는 개수 5, 최종은 비율 0.25다. 같은 union에 개수 5도 남아 있다고 단정할 수 없다.

종이와 본문으로 직접 해보기

최종 상태에서 kind만 COUNT로 바꾼다면 오류는 어디에 있는가?

힌트 보기

저장한 종류와 읽을 종류를 나란히 적는다.

풀이 보기

저장한 값은 ratio인데 태그가 count를 읽도록 지시한다. 태그-값 불변조건이 깨졌다. 다른 member 읽기의 숫자를 추측하지 말고 count 값을 새로 저장하거나 태그 변경을 취소해야 한다.

오해와 반례

union에 int를 쓰고 double을 읽으면 자동 숫자 변환이 된다.

숫자 변환은 별도의 캐스트나 대입 변환이다. union의 다른 member 읽기는 표현 재해석이므로 구현 표현과 trap 가능성을 검토해야 한다.

소단원 9.4

padding·정렬과 직렬화 주의

기록의 필드가 6바이트라면 파일에도 6바이트만 쓰면 될까?

준비 개념과 학습 목표

준비 개념

  • 바이트와 주소
  • 구조체 필드

학습 목표

  • 명시한 배치 모델에서 여백과 sizeof를 계산한다.
  • 메모리 배치와 외부 직렬화 규약을 구별한다.

필드 사이에 빈 공간이 들어갈 수 있다

정렬은 특정 형식의 객체를 놓을 주소 경계와 관련된다. 구현은 구조체 member의 선언 순서를 유지하면서 사이와 끝에 padding을 둘 수 있다. 처음 member 앞에 padding을 두지 않는 C11 규칙과 모든 필드가 빈틈없이 붙는다는 주장은 다르다.

이 단원 계산은 char 크기·정렬 1, int 크기·정렬 4, 구조체 정렬 4인 가상 모델이다. 실제 ABI와 컴파일러 설정에서는 크기·정렬이 다를 수 있으므로 계산 결과를 모든 C 환경의 상수로 외우지 않는다.

배치표를 주소 순서로 계산하기

char a; int b; char c; 순서라면 a는 offset 0에 놓인다. 다음 int는 4의 배수 경계에서 시작해야 하므로 1~3은 빈 공간이다. b는 4~7, c는 8이다. 연속 배열의 다음 구조체도 정렬을 맞추도록 9~11에 끝 여백을 두어 크기 12가 된다.

같은 모델에서 int b; char a; char c; 순서라면 b가 0~3, a가 4, c가 5이고 6~7에 끝 여백을 둔다. 크기는 8이다. 필드 순서 변경은 외부 인터페이스에 영향이 있으므로 공간 절약만 보고 공개 형식을 바꾸지 않는다.

파일에는 값의 약속을 써야 한다

구조체 전체 바이트를 그대로 전송하면 padding, 정수 바이트 순서, 형식 크기 차이가 외부로 드러난다. padding 값도 필드의 논리적 값이 아니므로 두 구조체의 memcmp 결과를 필드 동등성으로 단정하지 않는다.

직렬화는 각 필드의 폭과 순서, 부호, 바이트 순서를 명시하는 과정이다. 예를 들어 8비트 octet을 쓰는 규약에서 16비트 비음수 값 0x1234를 큰 자리부터 보내면 0x12,0x34다. 이 규약은 호스트 int 크기와 별개이며 범위 검사와 CHAR_BIT=8 등의 구현 조건을 확인해야 한다.

중간 과정을 따라가는 예제

위 가상 모델에서 char/int/char 구조체의 필드 합, 내부 padding, 끝 padding, 전체 크기를 계산하라.

  1. 필드 크기 합은 1+4+1=6바이트다.
  2. int를 offset 4에 놓기 위해 1~3에 내부 padding 3바이트가 들어간다.
  3. 마지막 char 뒤의 9~11에 끝 padding 3바이트가 들어간다.
  4. 전체 크기는 6+3+3=12바이트다.

필드 합은 6, 내부 여백은 3, 끝 여백은 3, 전체는 12바이트다. 이 결과는 명시한 모델에 한정된다.

종이와 본문으로 직접 해보기

int/char/char 순서의 배치와 값 0x0201의 큰 자리 우선 두 octet을 계산하라.

힌트 보기

배치의 마지막 주소와 4배수 크기, 값의 상위·하위 8비트를 각각 찾는다.

풀이 보기

배치는 0~3,4,5로 끝나고 6~7이 여백이라 크기 8이다. 0x0201의 상위 8비트는 0x02, 하위는 0x01이므로 전송 순서는 [0x02,0x01]이다.

오해와 반례

sizeof(struct)는 필드 크기를 더하면 항상 나온다.

정렬과 내부·끝 padding 때문에 더 클 수 있다. 예제의 합은 6이지만 모델의 전체 크기는 12다.
