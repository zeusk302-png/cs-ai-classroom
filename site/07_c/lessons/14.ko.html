mask·shift와 플래그

비트 필드를 교체할 때 OR만 하면 옛 값도 지워질까?

새 저장 계약은 unsigned int의 낮은 8비트만 쓰며 상위 비트는 0이다. 비트 0은 RUN, 비트 1은 ALERT, 비트 2–4는 0–7인 level, 비트 5–7은 예약 영역이다. level의 마스크는 7u << 2, 즉 28이다. 값을 넣을 때 먼저 기존 필드를 지우고 새 비트를 넣는다. (flags & ~28u) | (level << 2)는 옛 level과 새 level이 섞이지 않게 한다. 예약 비트가 있는 입력은 거절한다는 자체 계약도 둔다. 이는 실제 권한 또는 장치 레지스터에 대한 쓰기 규약이 아니다.

flags=23은 RUN/ALERT와 level=5다. level=2를 OR만 하면 23 | 8 = 31로 level=7이 되어 요구와 다르다. 지우고 넣으면 11이 되고 두 독립 플래그는 보존된다. 검사는 (flags & 3u) == 3u로 두 플래그가 모두 있는지 묻는다. flags & 3u == 3u는 연산 결합상 flags & (3u == 3u)라서 RUN만 검사하는 꼴이다. 괄호는 표를 코드 식으로 옮길 때의 계약이다.

먼저 확인할 개념
  • 승격과 공통 타입

    ~와 비트 논리를 작은 저장 폭만으로 해석하지 않는다.

  • 검사 이전 접근 금지

    필드 값과 예약 비트를 먼저 검사한 뒤 후보를 저장한다.

자리마다 약속을 붙인다

가상 권한 표시에서 오른쪽 비트를 읽기, 다음 비트를 쓰기, 세 번째 비트를 실행 표시로 약속하자. C 상수 READ = 1u, WRITE = 2u, EXEC = 4u는 각각 다른 비트 하나를 선택한다. 이 표시는 학습용 값이며 실제 접근 권한을 부여하지 않는다.

&는 같은 자리에서 두 값이 모두 1인 비트만 남긴다. |는 어느 한쪽이 1인 비트를 남기며 ^는 두 비트가 다른 자리를 남긴다. !와 &&는 전체 값의 참·거짓을 다루므로 비트 마스크의 대용이 아니다.

검사·설정·해제·반전을 구별한다

flags | WRITE는 쓰기 비트를 설정하고 flags & ~WRITE는 그것만 해제한다. flags ^ WRITE는 현재 상태를 뒤집으므로 이미 설정된 비트에도 다시 설정하려는 경우에는 맞지 않는다. 결과를 flags에 저장해야 이후 상태가 바뀐다.

검사는 (flags & READ) != 0처럼 괄호를 써 뜻을 드러낸다. 여러 플래그 mask에 대해 하나라도 있는지 묻는 식은 (flags & mask) != 0이고 모두 있는지 묻는 식은 (flags & mask) == mask다. 비트가 1인 자리와 요구 조건을 같이 읽는다.

이동과 작은 그림의 범위를 밝힌다

1u << k는 유효한 이동 수 k에서 위치 k의 마스크를 만든다. 아래 예제는 unsigned int의 낮은 세 비트만 표시하며 전체 정수 폭이 3비트라는 뜻은 아니다. 더 높은 비트는 여기서 모두 0으로 시작한다.

flags >> 1처럼 이동한 결과는 원래 플래그 이름과 대응하지 않을 수 있다. 비트 배치를 통신 형식으로 쓰려면 각 위치의 의미와 예약 비트를 문서화한다. 이동 수가 타입 폭 안인지 확인하는 규칙은 다음 소단원에서 다룬다.

중간 과정을 따라가는 예제

READ = 1u, WRITE = 2u, EXEC = 4u다. flags = 5u에서 쓰기를 설정하고 읽기를 해제한 뒤 실행 표시를 반전하라.

  1. 5의 낮은 세 비트는 101이며 읽기와 실행이 있다.

  2. 5 | 2 = 7로 111이 된다. 7 & ~1u = 6으로 낮은 비트는 110이다.

  3. 6 ^ 4 = 2로 낮은 비트는 010이 된다. 최종 값에는 쓰기만 있다.

상태는 5 → 7 → 6 → 2다. 단순 검사만으로 실제 권한이 생성되지는 않는다.

조건을 바꾸어 비교하기

교체와 누적의 차이

초기 23에서 level을 2로 바꾸는 두 방식을 대조하라.

  1. OR만 한 31에서 level은 7이다.

  2. 23 & ~28u는 3이며 여기에 8을 넣어 11이다.

교체 결과는 11이다.

비교할 점

OR는 비트를 더할 뿐 선택된 필드 전체를 새 값으로 바꾸지 않는다.

모두 검사의 괄호

flags=1에서 flags & 3u == 3u와 (flags & 3u) == 3u를 비교하라.

  1. 첫 식은 1 & 1u이므로 참이다.

  2. 둘째는 1 == 3u여서 거짓이다.

두 플래그 모두 요구하는 식은 둘째다.

비교할 점

컴파일 가능 여부와 의도에 맞는 조건은 다르다.

종이와 본문으로 직접 해보기

flags = 1u, mask = READ | WRITE다. 하나라도 있는가, 모두 있는가를 판단하고 flags ^ WRITE를 두 번 적용하라.

힌트 보기

선택 결과는 1이고 mask는 3이다. 반전은 두 번 하면 돌아온다.

풀이 보기

하나라도는 참, 모두는 거짓이다. 반전 상태는 1 → 3 → 1이므로 두 번 반전은 쓰기를 항상 설정하는 연산과 다르다.

오해와 반례

flags && WRITE로 쓰기 비트만 검사할 수 있다.

flags가 읽기만 가진 1이어도 두 피연산자는 모두 0이 아니어서 참이다. 해당 비트 검사는 flags & WRITE의 결과를 확인한다.

8비트 변수의 ~와 <<는 8비트로 계산될까?

새 가상 C11 구현은 CHAR_BIT=8, unsigned char 범위 0–255, int 범위 −2147483648–2147483647, unsigned int 값 비트 32개이며 두 int 타입에 패딩이 없다고 정한다. unsigned char x=240은 int로 승격된다. ~x의 결과 타입도 int다. signed 표현 방식에 따라 그 음수 값을 하나로 단정하지 말고 unsigned 변환을 활용해 원하는 낮은 8비트 보수를 명시하자. (~(unsigned int)x) & 255u는 15다. 이 모형의 x << 1은 int로 480이며 다시 unsigned char에 저장하면 224다.

mask 생성은 먼저 이동 수가 0 이상이고 승격된 왼쪽 타입 폭 미만인지 확인한다. 자체 field 함수에서는 유효 입력 level<=7u를 먼저 검사하고 unsigned 식 level << 2를 계산하여 최대 28만 만든다. (unsigned int)(signed_value << 2)는 위험한 signed 이동을 나중에 고치지 못한다. sizeof*CHAR_BIT는 이 모형에서 패딩이 없다고 가정했기에 폭으로 쓰지만 모든 C 타입의 값 비트 수로 일반화하지 않는다.

먼저 확인할 개념
  • 저장 타입의 범위

    바이트 수·비트 수·값의 상한을 각각 적는다.

  • 작은 정수의 승격

    unsigned char와 식의 결과 타입이 같다는 가정을 피한다.

값 범위를 먼저 적는다

이 소단원은 C11 초안을 기준으로 규칙을 읽는다. signed 범위 밖 계산은 일반적인 감기 결과로 예측할 수 없고 unsigned 계산은 결과 타입의 최대값 다음을 기준으로 나머지를 취한다. 폭과 부호를 같이 기록한다.

가상 unsigned 8비트 모형은 0..255다. 250 + 10의 저장 결과를 이 모형에서 4라고 계산할 수 있지만 C의 unsigned char 피연산자는 int 등으로 승격될 수 있다. 모형 계산과 실제 C 식의 타입을 혼동하지 않는다.

이동 전에 피연산자와 이동 수를 확인한다

이동 수는 음수가 아니고 승격된 왼쪽 타입의 폭보다 작아야 한다. 32비트 unsigned int라고 별도로 가정하면 1u << 31은 유효하지만 1u << 32와 1u << -1의 결과를 정수로 예측해서는 안 된다.

C11에서 signed 왼쪽 이동은 음이 아닌 값이고 이동 결과가 해당 타입에 표현 가능해야 한다. 음수 오른쪽 이동은 구현 정의다. unsigned의 이동 규칙을 signed 음수에도 그대로 붙이지 말고 판본과 구현 조건을 확인한다.

안전한 작은 추적으로 규칙을 배운다

아래 손계산은 실제 장치나 컴파일러 출력이 아니다. 범위 안인 signed 식과 unsigned 식을 골라 비교한다. 정의되지 않은 식은 실행해 보아 한 번 숫자가 나왔다고 허용하지 않는다.

한 번 읽은 값을 비교했는데 왜 반환 값은 달라질까?

새 source 함수 take()는 가상 대기 목록의 첫 값을 꺼내며 값은 모두 int 범위 안이다. 목록 [4,9]에서 MIN(take(),6)을 쓰면 조건에서 4를 소비하여 참이 되고 선택된 분기에서 9를 다시 소비한다. 결과는 9여서 방금 비교한 4의 최솟값도, 상한 6 안의 값도 아니다. 괄호가 완전해도 토큰 복제로 실제 관찰 대상이 달라진다. 이 순차 예제는 같은 스칼라의 순서 없는 중복 변경을 출력으로 예측하는 예제와 구별한다.

목록 [8,2]라면 조건에서 8을 읽어 거짓이므로 결과 6이고 2는 남는다. 임시 변수 saved=take(); 뒤 MIN(saved,6)을 쓰면 두 경우 모두 하나만 소비한다. 함수 min_int로 바꿔도 두 인수의 평가 순서는 왼쪽부터 보장되지 않는다. 호출자에게 둘의 관찰 순서가 중요하면 서로 다른 문장에 저장한다. GNU 확장 내부 임시 변수와 표준 C의 작은 함수는 빌드 의존성도 다르다.

먼저 확인할 개념
  • 호출 인수의 순서

    함수로 바꾸는 것과 호출 전 관찰 순서를 정하는 것을 나눈다.

  • 지역 값의 복사

    먼저 얻은 saved를 읽는 것은 source를 다시 호출하지 않는다.

치환은 함수 호출과 다르다

매크로는 전처리 과정에서 토큰을 바꾼다. #define MIN(a,b) ((a) < (b) ? (a) : (b))에서 인수 이름이 두 번 나오는 위치에 인수 식도 반복해서 들어간다. C의 일반 함수처럼 인수 값을 먼저 한 번씩 저장해 놓는다는 보장이 없다.

(a)와 (b), 전체 식의 괄호는 주변 연산의 결합을 보호한다. 괄호를 잘 썼다고 중복 평가까지 사라지는 것은 아니다. 매크로 정의와 실제 인수를 같이 전개해 읽어야 한다.

부수 효과가 있으면 값을 바꾼다

가상 함수 next()는 공유 카운터를 먼저 1 늘리고 그 값을 반환한다고 정하자. MIN(next(), 10)은 먼저 조건에서 next()를 호출하고 참이면 선택된 분기에서 다시 호출한다. 평가 횟수가 값에 영향을 준다.

SQUARE(i++)를 ((i++) * (i++))로 전개하면 같은 변수의 두 변경이 순서 없이 겹칠 수 있어 C11에서는 정의되지 않은 동작이다. 2번 증가한다고 정해 숫자를 출력하지 않는다. 중복 평가의 위험과 순서 규칙을 함께 확인한다.

값을 먼저 보관한다

int saved = next(); 뒤에 MIN(saved, 10)을 쓰면 saved를 여러 번 읽어도 next() 호출은 한 번이다. 타입이 정해진 작은 함수 min_int(int a, int b)를 쓰는 방법도 있다. 호출 인수에 서로 의존하는 부수 효과를 넣는 별도 문제까지 사라지는 것은 아니다.

GNU의 statement expression 등 확장으로 임시 변수를 넣는 매크로도 있지만 표준 C 예제로 아무 설명 없이 사용하지 않는다. 필요한 타입, 변환, 범위와 호출자 계약을 정하고 실제 빌드 조건을 확인한다.

중간 과정을 따라가는 예제

카운터 c = 0이고 next()는 ++c를 반환한다. MIN(next(), 10)을 손추적하고 saved = next(); MIN(saved, 10)과 비교하라.

  1. 직접 매크로는 ((next()) < (10) ? (next()) : (10))으로 전개된다.

  2. 첫 호출은 c = 1과 값 1이라 조건이 참이다. 선택된 두 번째 호출은 c = 2와 값 2를 낸다.

  3. 직접 결과는 2, 호출 횟수는 2다. c를 다시 0으로 둔 임시 변수 방식은 saved = 1, 결과 1, 호출 횟수 1이다.

전처리 치환과 한 번 값 보관은 결과와 호출 횟수가 다르다. 실제 C 실행 결과가 아니라 규칙의 손추적이다.

설정 값이 0인데도 기능이 빌드에 들어간 이유는 무엇일까?

헤더를 먼저 포함하면 설정 값도 이미 결정될까?

새 가상 config.h는 고유 guard CLASSROOM_CONFIG_H 안에서 LOG_LEVEL이 미정의면 0으로 기본 정의하고, 값이 0 또는 1인지 조건부 컴파일로 검사한다. 값이 범위 밖이면 #error 경로를 남긴다. 이어 #if LOG_LEVEL로 로그 선언을 선택한다. source A는 LOG_LEVEL=1을 정의한 뒤 처음 포함한다. source B는 아무 정의 없이 포함하여 기본 0을 얻은 뒤 매크로를 undef하고 1로 정의해 재포함한다. B의 두 번째 포함은 guard로 생략되어 이미 선택한 선언을 다시 만들지 않는다.

각 .c의 번역 단위는 자기 전처리 상태로 시작한다. A에서 guard를 정의했다는 것이 B의 첫 포함까지 막지 않는다. 반대로 서로 다른 헤더가 같은 guard를 쓰면 한 번역 단위에서 두 번째 파일의 선언을 숨긴다. 설정은 첫 포함 이전에 통일하며 파일마다 같은 설정이 필요한 ABI 계약도 별도로 관리한다. 헤더 guard만으로 서로 다른 번역 단위의 외부 함수 중복 정의나 ABI 불일치를 해결했다고 하지 않는다.

  • 실행 전후의 단계

    실행 중 변수 변경은 전처리 때 생략한 소스를 되살리지 않는다.

빌드 전에 남길 텍스트를 고른다

조건부 컴파일은 전처리에서 특정 소스 부분을 남기거나 생략한다. #ifdef DEBUG는 정의 여부를 보고 #if DEBUG는 펼쳐진 수치 식의 값을 본다. #define DEBUG 0이면 전자는 참이고 후자는 거짓이다.

일반 if (debug)와는 단계가 다르다. 실행 중 변수가 바뀌어도 이미 생략된 코드는 돌아오지 않는다. 빌드 옵션과 정의 값을 문서에 남기고 기능이 실제로 포함되었는지는 해당 빌드에서 확인한다.

중복 포함을 한 번만 처리한다

가상 학습 헤더 classroom_flags.h의 전체 내용을 #ifndef CLASSROOM_FLAGS_H, #define CLASSROOM_FLAGS_H, 마지막 #endif로 감싼다. 같은 번역 단위에서 다시 포함되면 guard가 이미 정의되어 내용이 생략된다.

헤더마다 다른 이름을 쓰지 않으면 다른 파일까지 잘못 생략할 수 있다. 사용자 guard는 밑줄로 시작하는 예약 이름을 피하고 프로젝트·파일을 드러내는 이름을 고른다. guard는 여러 .c 파일을 하나로 합치거나 링크 중복 정의를 모두 해결하는 장치가 아니다.

전처리기가 아는 것을 구별한다

GCC 설명의 #if 식에서 정의되지 않은 식별자는 0으로 취급된다. 그러므로 오타를 기능 꺼짐으로 놓칠 수 있다. DEBUG를 0 또는 1로 정의하는 자체 규약과 누락 검사를 함께 두면 의도가 명확해진다.

전처리기는 C의 타입을 알지 못하므로 #if sizeof(int) 같은 식을 타입 검사처럼 쓰지 않는다. enum 상수 역시 여기서 언어의 enum 값으로 평가되지 않는다. 필요하면 컴파일 단계의 정적 검사와 분리하고 각 플랫폼 빌드를 실제 확인한다.

필드 갱신·관찰·빌드 계약 연결

각 부분은 새 시작이다. 저장값 flags=23에서 level=2로 바꾸되 입력 거절/실패 보존 계약을 지켜 후보를 구하라. 같은 초기값에서 level=8이면 끝 상태는? 가상 C11 32-bit unsigned int, 8-bit unsigned char/int 승격 모형에서 x=240의 x<<1과 저장 결과를 구하라. source 목록 [4,9]의 MIN(take(),6)과 저장 후 방식을 비교하라. config.h를 기본 LOG_LEVEL=0으로 먼저 포함한 뒤 1로 재정의하고 재포함한 B의 선언 선택을 판단하라. 실제 C·전처리기·장치·학생 실행은 하지 않는다.

힌트 1

마스크 28과 상한 7을 확인하고 OR만 한 결과와 교체 후보를 구별한다.

힌트 2

계산 타입/저장 변환·실제 관찰 횟수·첫 전처리 선택의 시점을 따로 적는다.

풀이와 답 확인

  1. level=2는 유효하며 (23 & ~28u) | (2u << 2)=3 | 8=11이다. RUN/ALERT는 그대로다.

  2. level=8은 계산/저장 전에 거절하여 기존 23을 보존한다.

  3. x<<1은 승격된 int 값 480이고 unsigned char에 저장하면 224다.

  4. 직접 MIN은 4를 비교한 뒤 9를 다시 소비하여 결과 9/소비 2개다. 저장 후에는 결과 4/소비 1개다.

  5. B는 첫 포함의 기본 0으로 로그 선언을 생략한다. 재포함은 guard로 생략되므로 새 값 1만으로 선언이 추가되지 않는다.

유효 필드 교체 11, 범위 밖은 23 보존, 계산 480/저장 224, 직접 9·2개 대 저장 4·1개, B의 로그 선언은 계속 생략이다. 모두 서로 다른 단계의 계약으로 설명한다.
