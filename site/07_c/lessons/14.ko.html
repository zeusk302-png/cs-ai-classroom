소단원 14.1

mask·shift와 플래그

켜짐 상태 세 개를 정수 하나에 담으면 특정 상태만 어떻게 바꿀까?

준비 개념과 학습 목표

준비 개념

  • 2진수의 자리값

  • unsigned 정수

  • 조건문

학습 목표

  • 마스크로 선택한 비트를 검사하고 설정·해제한다.

  • 비트 논리와 참·거짓 논리를 구별한다.

  • 여러 플래그의 하나라도/모두 조건을 작성한다.

자리마다 약속을 붙인다

가상 권한 표시에서 오른쪽 비트를 읽기, 다음 비트를 쓰기, 세 번째 비트를 실행 표시로 약속하자. C 상수 READ = 1u, WRITE = 2u, EXEC = 4u는 각각 다른 비트 하나를 선택한다. 이 표시는 학습용 값이며 실제 접근 권한을 부여하지 않는다.

&는 같은 자리에서 두 값이 모두 1인 비트만 남긴다. |는 어느 한쪽이 1인 비트를 남기며 ^는 두 비트가 다른 자리를 남긴다. !와 &&는 전체 값의 참·거짓을 다루므로 비트 마스크의 대용이 아니다.

검사·설정·해제·반전을 구별한다

flags | WRITE는 쓰기 비트를 설정하고 flags & ~WRITE는 그것만 해제한다. flags ^ WRITE는 현재 상태를 뒤집으므로 이미 설정된 비트에도 다시 설정하려는 경우에는 맞지 않는다. 결과를 flags에 저장해야 이후 상태가 바뀐다.

검사는 (flags & READ) != 0처럼 괄호를 써 뜻을 드러낸다. 여러 플래그 mask에 대해 하나라도 있는지 묻는 식은 (flags & mask) != 0이고 모두 있는지 묻는 식은 (flags & mask) == mask다. 비트가 1인 자리와 요구 조건을 같이 읽는다.

이동과 작은 그림의 범위를 밝힌다

1u << k는 유효한 이동 수 k에서 위치 k의 마스크를 만든다. 아래 예제는 unsigned int의 낮은 세 비트만 표시하며 전체 정수 폭이 3비트라는 뜻은 아니다. 더 높은 비트는 여기서 모두 0으로 시작한다.

flags >> 1처럼 이동한 결과는 원래 플래그 이름과 대응하지 않을 수 있다. 비트 배치를 통신 형식으로 쓰려면 각 위치의 의미와 예약 비트를 문서화한다. 이동 수가 타입 폭 안인지 확인하는 규칙은 다음 소단원에서 다룬다.

중간 과정을 따라가는 예제

READ = 1u, WRITE = 2u, EXEC = 4u다. flags = 5u에서 쓰기를 설정하고 읽기를 해제한 뒤 실행 표시를 반전하라.

  1. 5의 낮은 세 비트는 101이며 읽기와 실행이 있다.

  2. 5 | 2 = 7로 111이 된다. 7 & ~1u = 6으로 낮은 비트는 110이다.

  3. 6 ^ 4 = 2로 낮은 비트는 010이 된다. 최종 값에는 쓰기만 있다.

상태는 5 → 7 → 6 → 2다. 단순 검사만으로 실제 권한이 생성되지는 않는다.

종이와 본문으로 직접 해보기

flags = 1u, mask = READ | WRITE다. 하나라도 있는가, 모두 있는가를 판단하고 flags ^ WRITE를 두 번 적용하라.

힌트 보기

선택 결과는 1이고 mask는 3이다. 반전은 두 번 하면 돌아온다.

풀이 보기

하나라도는 참, 모두는 거짓이다. 반전 상태는 1 → 3 → 1이므로 두 번 반전은 쓰기를 항상 설정하는 연산과 다르다.

오해와 반례

flags && WRITE로 쓰기 비트만 검사할 수 있다.

flags가 읽기만 가진 1이어도 두 피연산자는 모두 0이 아니어서 참이다. 해당 비트 검사는 flags & WRITE의 결과를 확인한다.

자기점검

flags = 5에서 flags & WRITE의 값은?

답과 이유 보기

0

101과 010의 같은 자리에 1이 없다.

이미 있는 비트를 그대로 설정하려면 |와 ^ 중 무엇인가?

답과 이유 보기

|

반전은 이미 있는 비트를 없앤다.

READ와 WRITE를 모두 요구하는 마스크 값은?

답과 이유 보기

3u

서로 다른 비트 1과 2를 OR한 값이다.

한 단계 더

가상 입력 flags = 13의 낮은 세 비트는 101이지만 비트 3도 켜져 있다. 허용 mask = 7u만 인정하는 규약이면 flags & ~7u = 8이므로 예약 비트 위반이다. 낮은 비트가 맞아도 전체 입력 계약이 맞는 것은 아니다.

소단원 14.2

정수 폭과 signed 연산

작은 종이에 그린 8비트 덧셈을 C의 모든 정수에 그대로 적용해도 될까?

준비 개념과 학습 목표

준비 개념

  • 타입과 값 범위

  • 비트 이동

  • 정수 승격

학습 목표

  • 표현 폭 가정과 실제 C 타입을 구별한다.

  • unsigned 계산과 signed 범위 밖 계산을 나눈다.

  • C11 이동의 유효 조건을 검사한다.

값 범위를 먼저 적는다

이 소단원은 C11 초안을 기준으로 규칙을 읽는다. signed 범위 밖 계산은 일반적인 감기 결과로 예측할 수 없고 unsigned 계산은 결과 타입의 최대값 다음을 기준으로 나머지를 취한다. 폭과 부호를 같이 기록한다.

가상 unsigned 8비트 모형은 0..255다. 250 + 10의 저장 결과를 이 모형에서 4라고 계산할 수 있지만 C의 unsigned char 피연산자는 int 등으로 승격될 수 있다. 모형 계산과 실제 C 식의 타입을 혼동하지 않는다.

이동 전에 피연산자와 이동 수를 확인한다

이동 수는 음수가 아니고 승격된 왼쪽 타입의 폭보다 작아야 한다. 32비트 unsigned int라고 별도로 가정하면 1u << 31은 유효하지만 1u << 32와 1u << -1의 결과를 정수로 예측해서는 안 된다.

C11에서 signed 왼쪽 이동은 음이 아닌 값이고 이동 결과가 해당 타입에 표현 가능해야 한다. 음수 오른쪽 이동은 구현 정의다. unsigned의 이동 규칙을 signed 음수에도 그대로 붙이지 말고 판본과 구현 조건을 확인한다.

안전한 작은 추적으로 규칙을 배운다

아래 손계산은 실제 장치나 컴파일러 출력이 아니다. 범위 안인 signed 식과 unsigned 식을 골라 비교한다. 정의되지 않은 식은 실행해 보아 한 번 숫자가 나왔다고 허용하지 않는다.

입력으로 이동 수를 받는 함수는 먼저 0 이상인지와 정한 폭 미만인지 검사해야 한다. 비트 수, sizeof의 바이트 수, CHAR_BIT를 구별한다. 이 단원은 특정 플랫폼에 존재하는 모든 패딩이나 확장 타입까지 구현하지 않는다.

중간 과정을 따라가는 예제

unsigned int의 값 비트가 32개, signed int의 최댓값이 2,147,483,647인 C11 환경을 가정한다. UINT_MAX + 1u, 1u << 31, INT_MAX + 1, 1u << 32를 분류하라.

  1. 첫 식은 unsigned 결과 범위 0..4,294,967,295에서 나머지 0이다.

  2. 1u << 31은 이동 수 31이 32보다 작고 결과는 2,147,483,648이다.

  3. INT_MAX + 1은 signed 범위 밖이며 정의되지 않은 동작이다. 음수 감기 출력값을 정하지 않는다.

  4. 1u << 32도 이동 수가 폭과 같아서 정의되지 않은 동작이다.

첫 두 식만 각각 0과 2,147,483,648로 계산한다. 뒤 두 식의 출력은 약속하지 않는다.

종이와 본문으로 직접 해보기

같은 조건에서 12u >> 2, 3 << 2, -3 >> 1, -3 << 1을 분류하라. 가상 unsigned 8비트 모형에서 255 + 2를 계산하라.

힌트 보기

unsigned 나누기와 signed 음수 이동을 따로 살핀다.

풀이 보기

12u >> 2는 3, 3 << 2는 표현 가능한 12다. C11의 -3 >> 1은 구현 정의, -3 << 1은 정의되지 않은 동작이다. 가상 모형의 257 mod 256은 1이며 실제 C의 작은 타입 식은 승격을 따로 확인한다.

오해와 반례

signed 범위 밖도 unsigned처럼 항상 감겨 같은 숫자가 나온다.

C11에서 두 규칙은 다르다. 한 번 실행 결과를 보아도 signed 범위 밖 동작의 표준 보장이 생기지 않는다.

자기점검

32비트 왼쪽 타입의 이동 수 32는 유효한가?

답과 이유 보기

아니다.

이동 수는 폭보다 작아야 한다.

가상 8비트 모형 결과만으로 unsigned char 식의 결과 타입을 알 수 있나?

답과 이유 보기

아니다.

정수 승격을 확인해야 한다.

이 단원의 음수 오른쪽 이동 규칙이 적용된 기준은?

답과 이유 보기

C11

다른 판본과 구현에 대한 동일성은 별도 확인한다.

한 단계 더

필드에 5비트 값만 담는 가상 규약이면 허용 최댓값은 2^5 − 1 = 31이다. 32를 단순히 mask = 31로 잘라 저장하면 0이 된다. 범위 오류를 거절할지 낮은 비트만 쓰기로 계약할지 먼저 정해야 한다.

소단원 14.3

매크로의 중복 평가

함수를 한 번 적었는데 왜 실행 횟수는 두 번이 될 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 함수 호출

  • 조건 연산자

  • 부수 효과

학습 목표

  • 함수형 매크로의 텍스트 치환을 전개한다.

  • 괄호와 평가 횟수 문제를 분리한다.

  • 임시 변수나 함수로 부수 효과를 통제한다.

치환은 함수 호출과 다르다

매크로는 전처리 과정에서 토큰을 바꾼다. #define MIN(a,b) ((a) < (b) ? (a) : (b))에서 인수 이름이 두 번 나오는 위치에 인수 식도 반복해서 들어간다. C의 일반 함수처럼 인수 값을 먼저 한 번씩 저장해 놓는다는 보장이 없다.

(a)와 (b), 전체 식의 괄호는 주변 연산의 결합을 보호한다. 괄호를 잘 썼다고 중복 평가까지 사라지는 것은 아니다. 매크로 정의와 실제 인수를 같이 전개해 읽어야 한다.

부수 효과가 있으면 값을 바꾼다

가상 함수 next()는 공유 카운터를 먼저 1 늘리고 그 값을 반환한다고 정하자. MIN(next(), 10)은 먼저 조건에서 next()를 호출하고 참이면 선택된 분기에서 다시 호출한다. 평가 횟수가 값에 영향을 준다.

SQUARE(i++)를 ((i++) * (i++))로 전개하면 같은 변수의 두 변경이 순서 없이 겹칠 수 있어 C11에서는 정의되지 않은 동작이다. 2번 증가한다고 정해 숫자를 출력하지 않는다. 중복 평가의 위험과 순서 규칙을 함께 확인한다.

값을 먼저 보관한다

int saved = next(); 뒤에 MIN(saved, 10)을 쓰면 saved를 여러 번 읽어도 next() 호출은 한 번이다. 타입이 정해진 작은 함수 min_int(int a, int b)를 쓰는 방법도 있다. 호출 인수에 서로 의존하는 부수 효과를 넣는 별도 문제까지 사라지는 것은 아니다.

GNU의 statement expression 등 확장으로 임시 변수를 넣는 매크로도 있지만 표준 C 예제로 아무 설명 없이 사용하지 않는다. 필요한 타입, 변환, 범위와 호출자 계약을 정하고 실제 빌드 조건을 확인한다.

중간 과정을 따라가는 예제

카운터 c = 0이고 next()는 ++c를 반환한다. MIN(next(), 10)을 손추적하고 saved = next(); MIN(saved, 10)과 비교하라.

  1. 직접 매크로는 ((next()) < (10) ? (next()) : (10))으로 전개된다.

  2. 첫 호출은 c = 1과 값 1이라 조건이 참이다. 선택된 두 번째 호출은 c = 2와 값 2를 낸다.

  3. 직접 결과는 2, 호출 횟수는 2다. c를 다시 0으로 둔 임시 변수 방식은 saved = 1, 결과 1, 호출 횟수 1이다.

전처리 치환과 한 번 값 보관은 결과와 호출 횟수가 다르다. 실제 C 실행 결과가 아니라 규칙의 손추적이다.

종이와 본문으로 직접 해보기

처음 c = 10인 직접 매크로와 임시 변수 방식을 각각 추적하라. SQUARE(i++)의 값을 한 숫자로 쓰면 되는가?

힌트 보기

첫 next()가 11이면 조건이 거짓이라 선택된 분기에 next()가 없다.

풀이 보기

직접 방식은 c = 11, 결과 10, 호출 1번이다. 임시 방식도 c = 11, saved = 11, 결과 10이다. 매크로는 항상 두 번 호출하는 것이 아니라 선택 조건에 따라 달라진다. SQUARE(i++)는 C11의 순서 없는 같은 변수 변경 문제로 결과를 약속하지 않는다.

오해와 반례

인수와 전체 식을 괄호로 둘러싸면 안전한 매크로다.

연산 결합은 보호하지만 인수 식이 복제되는 위치와 부수 효과는 남는다. 정의와 호출 인수를 전개해 평가 횟수를 점검한다.

자기점검

MIN(next(), 10)의 두 번째 호출은 항상 일어나나?

답과 이유 보기

아니다.

조건의 참 분기를 선택했을 때만 일어난다.

saved 변수를 여러 번 읽으면 next()도 다시 호출되나?

답과 이유 보기

아니다.

함수 호출은 저장 문장에서 끝났다.

SQUARE(i++)의 정의되지 않은 동작을 실제 한 출력으로 정당화할 수 있나?

답과 이유 보기

없다.

컴파일러 출력은 표준의 결과 보장을 만들지 않는다.

한 단계 더

#define BAD(x) x * x에 BAD(1 + 2)를 넣으면 1 + 2 * 1 + 2로 바뀌어 5다. 괄호를 넣은 ((x) * (x))에서는 9지만 i++의 순서 문제는 남는다. 연산 결합과 평가 횟수를 다른 검사 항목으로 적어 보자.

소단원 14.4

조건부 컴파일·header guard

설정 값이 0인데도 기능이 빌드에 들어간 이유는 무엇일까?

준비 개념과 학습 목표

준비 개념

  • 헤더 포함

  • 매크로 정의

  • 컴파일과 실행

학습 목표

  • #ifdef와 #if의 조건을 구별한다.

  • 헤더 반복 포함을 guard로 방지한다.

  • 빌드 선택과 실행 중 조건을 분리한다.

빌드 전에 남길 텍스트를 고른다

조건부 컴파일은 전처리에서 특정 소스 부분을 남기거나 생략한다. #ifdef DEBUG는 정의 여부를 보고 #if DEBUG는 펼쳐진 수치 식의 값을 본다. #define DEBUG 0이면 전자는 참이고 후자는 거짓이다.

일반 if (debug)와는 단계가 다르다. 실행 중 변수가 바뀌어도 이미 생략된 코드는 돌아오지 않는다. 빌드 옵션과 정의 값을 문서에 남기고 기능이 실제로 포함되었는지는 해당 빌드에서 확인한다.

중복 포함을 한 번만 처리한다

가상 학습 헤더 classroom_flags.h의 전체 내용을 #ifndef CLASSROOM_FLAGS_H, #define CLASSROOM_FLAGS_H, 마지막 #endif로 감싼다. 같은 번역 단위에서 다시 포함되면 guard가 이미 정의되어 내용이 생략된다.

헤더마다 다른 이름을 쓰지 않으면 다른 파일까지 잘못 생략할 수 있다. 사용자 guard는 밑줄로 시작하는 예약 이름을 피하고 프로젝트·파일을 드러내는 이름을 고른다. guard는 여러 .c 파일을 하나로 합치거나 링크 중복 정의를 모두 해결하는 장치가 아니다.

전처리기가 아는 것을 구별한다

GCC 설명의 #if 식에서 정의되지 않은 식별자는 0으로 취급된다. 그러므로 오타를 기능 꺼짐으로 놓칠 수 있다. DEBUG를 0 또는 1로 정의하는 자체 규약과 누락 검사를 함께 두면 의도가 명확해진다.

전처리기는 C의 타입을 알지 못하므로 #if sizeof(int) 같은 식을 타입 검사처럼 쓰지 않는다. enum 상수 역시 여기서 언어의 enum 값으로 평가되지 않는다. 필요하면 컴파일 단계의 정적 검사와 분리하고 각 플랫폼 빌드를 실제 확인한다.

중간 과정을 따라가는 예제

DEBUG가 미정의, 0, 1인 세 빌드에서 #ifdef DEBUG와 #if DEBUG의 텍스트 포함을 비교하라. guard가 있는 한 헤더를 같은 번역 단위에 두 번 포함하면?

  1. 미정의 상태에서는 #ifdef가 거짓이다. GCC의 #if DEBUG도 미정의 식별자 0으로 거짓이다.

  2. DEBUG = 0이면 정의 여부는 참, 수치 조건은 거짓이다. DEBUG = 1이면 둘 다 참이다.

  3. 첫 헤더 포함은 guard를 정의하고 내용을 남긴다. 두 번째는 이미 정의된 guard 때문에 본문을 건너뛴다.

조건 쌍은 거짓/거짓, 참/거짓, 참/참이다. 헤더 본문은 같은 번역 단위에서 한 번 처리된다.

종이와 본문으로 직접 해보기

다른 a.h와 b.h가 둘 다 CLASSROOM_COMMON_H라는 guard를 쓰고 a.h를 먼저 포함한다. 무슨 문제가 생기나? 실행 중 debug = 1로 바꾸면 #if DEBUG에서 생략된 부분이 돌아오나?

힌트 보기

두 번째 헤더를 만날 때 이미 정의된 이름과 선택 시점을 확인한다.

풀이 보기

b.h의 본문까지 생략되어 필요한 선언이 빠질 수 있다. 헤더마다 고유한 guard 이름을 써야 한다. 실행 중 변수 변경은 전처리 선택을 되돌리지 않으므로 생략된 부분은 돌아오지 않는다.

오해와 반례

header guard가 있으면 헤더의 일반 함수 정의를 모든 .c 파일에 넣어도 링크 문제가 없어진다.

guard는 번역 단위 내부의 반복 포함을 막는다. 여러 번역 단위의 외부 정의 문제는 함수 선언/정의 위치와 연결 규칙을 따로 설계한다.

자기점검

DEBUG가 0으로 정의되면 #ifdef DEBUG는?

답과 이유 보기

참이다.

값이 아니라 정의 여부를 검사한다.

미정의 이름의 #if 처리 때문에 오타가 놓칠 수 있는가?

답과 이유 보기

그렇다.

GCC에서는 미정의 식별자를 0으로 취급한다.

guard를 모든 헤더에 같은 이름으로 쓰면 되는가?

답과 이유 보기

안 된다.

먼저 포함한 파일이 다른 헤더를 생략시킬 수 있다.

한 단계 더

가상 소스 A는 DEBUG = 0 빌드에서 #if DEBUG로 로그 코드를 생략한다. 소스 B는 실행 중 if로 로그 표시를 고른다. 제공 기능·빌드 산출물·실행 중 바꿀 수 있는 조건을 세 칸 장부로 비교하라. 어느 쪽이 더 빠르거나 안전한지는 실제 측정 없이 확정하지 않는다.
