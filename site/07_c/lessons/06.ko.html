소단원 6.1

null 종료와 길이

여섯 칸에 글자를 넣었는데 strlen이 왜 1을 돌려줄까?

준비 개념과 학습 목표

준비 개념

  • char 배열은 문자 저장용 칸들의 객체다. char a[6]은 여섯 char를 가지며 유효 번호는 0~5이다. C의 sizeof(char)는 1이지만 그 바이트가 언제나 8비트라는 가정은 하지 않는다.

  • '\0'는 정수값 0인 null 문자다. 글자 '0'나 포인터의 NULL과 역할이 다르다. 문자열의 끝을 표시하는 0이 배열 안에 있어야 한다.

  • 자가진단: [A,0,B]에서 첫 0 앞의 문자열 내용은 몇 칸인가? 답은 1이다. 첫 0 자체까지 확인하면 읽은 칸은 2이고, 전체 저장 칸은 3이다. 문자열 길이·확인한 읽기 수·저장 용량은 서로 다른 질문의 답이다.

학습 목표

  • C 문자열의 끝과 strlen의 길이를 정의한다.

  • 저장 용량·논리 길이·첫 NUL 뒤의 데이터를 구별한다.

  • 상한을 가진 탐색의 접근 안전성·종료와 실패 반환을 설명한다.

첫 NUL이 정하는 문자열

C11에서 문자열은 첫 null 문자까지, 그 문자를 포함해 이어진 문자 시퀀스다. 반면 문자열 길이는 그 null 앞의 바이트 수다. char a[6]={'A','\0','B','C','\0','\0'}에서 a가 가리키는 문자열 길이는 1이고 배열 용량은 6이다. 뒤에 B와 C가 존재해도 strlen(a)는 첫 0 뒤를 문자열 내용으로 세지 않는다.

strlen은 종료 0을 찾을 수 있는 유효 문자열을 요구한다. 배열에 0이 없는데 strlen을 호출해 길이를 알아낸 다음 검사하는 방식은 이미 계약을 위반할 수 있다. 길이 0인 빈 문자열은 처음 칸이 0인 문자열이며, 저장 칸이 없거나 NULL인 포인터와 같지 않다. 한 칸짜리 char empty[1]={0}은 빈 문자열을 담을 수 있다.

길이를 먼저 신뢰하지 않는 검사

아래 bounded_length는 s가 cap개의 읽을 수 있는 살아 있는 char를 제공하고 out이 쓰기 가능한 size_t 객체를 가리킨다는 호출 계약을 갖는다. cap=0이면 s를 읽지 않으므로 이 자체 함수에서 s=NULL도 허용할 수 있지만 out은 여전히 계약상 유효하게 준다. cap>0에서 s=NULL이면 그 계약을 어긴다. 반환 1일 때만 *out을 새 길이로 쓰며, 반환 0은 제공한 구간에 종료 문자가 없었다는 뜻이다.

조건 i<cap && s[i]!='\0'에서 &&는 왼쪽이 참일 때만 오른쪽을 평가한다. 따라서 i==cap이면 s[cap]을 읽지 않는다. 매 반복 전 0≤i≤cap이며 이전 i개 칸은 모두 0이 아니라는 불변식이 성립한다. 종료는 발견한 0의 위치를 돌려주거나 i==cap의 실패로 나뉜다. cap의 거짓 값을 전달하면 이 검사는 실제 객체 경계까지 보장하지 못한다.

바이트 길이와 사람의 글자 수

strlen은 인코딩의 문자 개수나 화면 글자 수를 해석하지 않는다. 예를 들어 8비트 바이트의 UTF-8이라는 추가 조건에서 U+AC00 가는 EA B0 80이라는 세 바이트로 저장되며 종료 00을 더하면 최소 네 칸이다. 길이는 3이다. 기본 C char 문자열이 무조건 UTF-8이라고 말하지 않으며 아래 코드는 실행 문자 집합의 기본 문자 A,B,C,X,Y,Z만 사용한다.

외부 파일에는 데이터 중간의 0도 있을 수 있다. 이런 이진 데이터는 실제 바이트 길이를 별도로 전달하는 계약이 적합하며 strlen으로 길이를 복원할 수 없다. 문자 디코딩·정규화·표시 글자 구분은 또 다른 계층이다. 아래 raw는 세 칸의 이진 내용이고 C 문자열이 아니므로 strlen(raw)나 %s로 읽지 않는다.

#include <stdio.h>
#include <stddef.h>
#include <string.h>
static int bounded_length(const char *s, size_t cap, size_t *out) {
    size_t i = 0;
    while (i < cap && s[i] != '\0') {
        ++i;
    }
    if (i == cap) return 0;
    *out = i;
    return 1;
}
int main(void) {
    char a[6] = {'A', '\0', 'B', 'C', '\0', '\0'};
    char raw[3] = {'X', 'Y', 'Z'};
    size_t len = 99;
    int ok = bounded_length(a, sizeof a, &len);
    printf("%zu %zu %d %zu\n", sizeof a, strlen(a), ok, len);
    ok = bounded_length(raw, sizeof raw, &len);
    printf("%d %zu\n", ok, len);
    return 0;
}

중간 과정을 따라가는 예제

완전 예제에서 a와 raw의 저장 내용·반환값·len 변화를 추적한다. 정상 출력 성공을 가정하고 실제 실행은 하지 않는다.

  1. a의 용량은 6이고 첫 0은 인덱스 1이다. sizeof a=6, strlen(a)=1이며 뒤 칸은 길이 계산에 포함되지 않는다.

  2. bounded_length(a,6,&len)는 i=0에서 A를 확인하고 i=1에서 멈춘다. 반환 1과 len=1이므로 첫 줄 인자는 6,1,1,1이다.

  3. raw의 세 칸 X,Y,Z에는 0이 없다. i=0,1,2에서 증가하고 i=3일 때 왼쪽 조건이 거짓이므로 네 번째 칸을 읽지 않는다.

  4. 실패 반환 0에서 *out 대입은 생략된다. 이전 len=1이 남는다. 반환값을 무시하면 raw의 길이를 1이라고 오해할 수 있다.

예상 stdout은 첫 줄 6 1 1 1, 둘째 줄 0 1이다. 실패 시 남은 len은 raw 문자열 길이를 뜻하지 않는다.

종이와 본문으로 직접 해보기

다섯 칸 [P,Q,0,R,0]과 네 칸 [P,Q,R,S]를 그린다. 각 배열을 정확한 cap과 함께 bounded_length에 전달하고 초기 out 값은 77로 둔다. 반환과 out, 마지막으로 읽은 번호를 구한다.

힌트 보기

0 자체를 만나는 읽기도 한 번의 검사다. 실패에서는 out 대입이 없고 cap 번호는 읽지 않는다.

풀이 보기

첫 배열은 번호 0,1,2를 읽고 반환 1,out=2다. 둘째는 번호 0~3을 읽고 i=4에서 멈춰 반환 0,out=77을 유지한다. cap=4라는 수와 out의 이전 값은 문자열 길이라는 보장이 없다.

오해와 반례

문자 배열이면 strlen이 용량을 안전하게 알려 준다.

a[6]의 strlen은 1이고 sizeof a는 6이다. 0 없는 raw[3]에서 strlen을 호출하면 종료 탐색이 객체 밖으로 나갈 수 있어 정의되지 않은 동작이다. UB의 출력은 어떤 고정 숫자로 예측하지 않는다.

자기점검

char e[1]={0};의 길이와 용량은?

답과 이유 보기

길이 0, 용량 1이다.

종료 0은 저장 칸을 차지하지만 길이에 포함되지 않는다.

중간에 0이 든 여덟 바이트 패킷의 전체 길이를 strlen으로 구할 수 있는가?

답과 이유 보기

일반적으로 불가능하다.

첫 0 이후 데이터는 strlen이 세지 않으므로 패킷 계약의 길이를 별도로 보존한다.

cap=3에서 i=3일 때 코드가 s[3]을 읽는가?

답과 이유 보기

읽지 않는다.

&&의 왼쪽 i<cap가 거짓이라 오른쪽은 평가되지 않는다.

한 단계 더

심화 증명: 반복 시작에서 0≤i≤cap이고 j<i인 모든 제공 칸 s[j]가 0이 아니라고 가정한다. 조건이 참이면 i<cap라 현재 칸은 유효하고 그것도 0이 아니므로 증가 후 불변식이 유지된다. 자연수 변량 cap−i가 매 반복 1 줄어 유한 종료한다. i<cap로 끝나면 s[i]=0이며 이전에 0이 없으므로 첫 종료 위치다. i=cap이면 전 구간에 0이 없다. size_t의 i는 증가 직전에 i<cap이므로 최대 cap까지이며 cap=SIZE_MAX인 모형에서도 마지막 증가가 넘치지 않는다. 다만 실제로 그만한 읽기 가능한 객체가 존재한다는 계약은 별도다.

소단원 6.2

문자배열·literal

같은 "cat"에서 만든 a와 p는 왜 수정 가능성이 다를까?

준비 개념과 학습 목표

준비 개념

  • 배열은 실제 원소를 가진 객체이고 포인터는 어떤 객체의 위치를 가리키는 값이다. const char *p는 p를 통한 char 변경을 허용하지 않는 타입이며 p 자체의 재대입 금지와는 다르다.

  • 초기화는 새 객체의 시작 내용을 정한다. char a[]="cat"은 포인터를 저장하는 선언이 아니라 문자 배열을 만든다. char *p="cat"은 문자열 리터럴의 첫 문자를 가리키는 포인터를 만든다.

  • 자가진단: 'A'는 문자 상수이고 "A"는 종료 0이 있는 문자열 리터럴이다. C에서 둘은 타입과 저장 내용이 다르다.

학습 목표

  • 문자 배열 초기화와 문자열 리터럴을 구별한다.

  • 종료 칸 포함 여부와 sizeof가 측정하는 객체를 설명한다.

  • 수명·const 접근·리터럴 수정 UB를 분리한다.

초기화로 독립된 배열을 만든다

C11의 보통 문자열 리터럴 "cat"은 기본 문자 c,a,t 뒤에 0을 포함한 char 배열로 구현되며 정적 저장기간을 가진다. char a[]="cat"은 그 네 문자를 초기값으로 가진 별도 배열 객체 a를 만든다. 아래 a는 main 블록의 자동 저장기간에 살아 있으며 a[0]='b'로 수정해 "bat"이 된다. 같은 텍스트로 만든 리터럴을 수정한 것이 아니다.

char b[6]="cat"이면 [c,a,t,0,0,0]이다. 문자 배열 초기화에서는 크기를 정확히 3으로 정한 char raw[3]="cat"도 C11에서 허용되지만 종료 문자가 들어갈 자리가 없어 [c,a,t]만 가진다. 이 유효한 초기화가 raw를 C 문자열로 만드는 것은 아니다. raw는 코드에서 각 원소를 %c로 읽으며 %s와 strlen에는 주지 않는다.

리터럴의 타입과 수정 금지는 다르다

C의 보통 리터럴 배열 원소 타입은 char이지만 그 배열을 변경하려 하면 정의되지 않은 동작이다. C++의 리터럴 타입 설명을 C11에 그대로 옮기지 않는다. C에서 char *q="cat"이 허용되는 상황이어도 q[0]='b'는 안전한 수정이 아니다. const char *p를 쓰면 의도한 읽기 전용 접근이 타입에 드러나 실수를 줄인다.

const char *p의 const는 가리킨 문자를 p를 통해 바꾸지 못하게 한다. p="dog"처럼 다른 리터럴을 가리키게 하는 대입은 가능하다. 포인터 자체의 재대입도 막으려면 char *const와 같은 별도 위치의 const가 필요하다. 서로 같은 리터럴의 저장 배열이 합쳐질 수 있는지는 지정되지 않으므로 포인터 주소 동일성으로 텍스트 동등성을 판단하지 않는다.

sizeof와 객체 수명

a의 sizeof는 네 char 배열의 크기 4다. p의 sizeof는 포인터 객체 크기라서 문자열 길이나 종료 공간을 뜻하지 않고 특정 숫자로 고정하지 않는다. strlen(a)는 현재 첫 0 앞 세 바이트를 세므로 3이다. 문자 상수 'A'의 타입은 C에서 int이지만 "A"는 char 두 칸 배열이다. sizeof('A')는 sizeof(int)이며 1이라고 가정하지 않는다.

리터럴은 정적 저장기간이므로 그것을 가리키는 포인터를 함수 밖에 반환하는 것 자체는 수명 면에서 가능하다. 반대로 함수 안의 자동 char tmp[]="cat"을 가리키는 포인터를 반환하면 함수 종료 뒤 그 배열 수명이 끝난다. 쓰기 가능성과 충분한 용량뿐 아니라 대상 객체가 아직 살아 있는지도 계약에 포함해야 한다. 아래 프로그램은 모든 자동 배열을 살아 있는 main 안에서만 읽는다.

#include <stdio.h>
#include <string.h>
int main(void) {
    char a[] = "cat";
    const char *p = "cat";
    char raw[3] = "cat";
    a[0] = 'b';
    printf("%zu %zu %s %s\n", sizeof a, strlen(a), a, p);
    printf("%zu %c%c%c\n", sizeof raw, raw[0], raw[1], raw[2]);
    return 0;
}

중간 과정을 따라가는 예제

완전 예제의 a,p,raw를 별도의 객체 표에 적고 a[0] 변경 뒤 예상 두 줄을 구한다.

  1. a는 [c,a,t,0] 네 칸, p는 정적 리터럴 [c,a,t,0]의 첫 칸을 가리킨다. raw는 [c,a,t] 세 칸이다.

  2. a[0]='b'는 별도 수정 가능한 배열의 첫 칸만 바꾼다. p가 읽는 리터럴의 c는 그대로다.

  3. sizeof a=4이고 strlen(a)=3이다. %s 두 개는 종료 있는 a와 p만 읽어 bat,cat을 표시한다.

  4. sizeof raw=3이다. 세 %c가 raw의 각 칸을 개별로 읽으므로 종료 0을 찾는 연산이 아니고 cat을 출력한다.

예상 stdout은 첫 줄 4 3 bat cat, 둘째 줄 3 cat이다. raw를 %s로 바꾸는 변형은 안전한 실행 예제로 취급하지 않는다.

종이와 본문으로 직접 해보기

char x[5]="Hi"; char y[2]="Hi"; const char *z="Hi"; 세 선언의 내용을 그린다. sizeof와 문자열 길이를 말할 수 있는 대상을 구별하고 x[0]='B', z="Bye", z[0]='B'를 판정한다.

힌트 보기

Hi의 기본 문자 두 개 뒤 종료 0을 추가한다. 명시한 크기가 부족하면 char 배열 초기화에서 종료 칸이 빠질 수 있다.

풀이 보기

x=[H,i,0,0,0], sizeof x=5, strlen(x)=2다. y=[H,i], sizeof y=2이며 strlen(y)의 사전조건은 충족되지 않는다. sizeof z는 포인터 크기이고 strlen(z)=2다. x[0] 변경과 z의 재대입은 가능하다. z[0] 변경은 const 접근 규칙을 어겨 진단이 필요하며 const를 제거해 리터럴을 변경해도 UB다.

오해와 반례

C 리터럴의 원소 타입이 char이므로 수정해도 되고 sizeof 포인터로 문자열 저장 크기를 알 수 있다.

타입 설명과 리터럴 변경 금지는 별개의 규칙이다. char *p="cat"의 p[0] 변경은 UB이고 sizeof p는 포인터 객체 크기다. char a[]="cat"이라는 독립 배열의 sizeof a=4와 a[0] 수정은 이 반례와 구별한다.

한 단계 더

소단원 6.3

표준 문자열 함수

길이 인자가 있는 strncpy는 왜 문자열 끝을 보장하지 않을까?

준비 개념과 학습 목표

준비 개념

  • 복사는 원본의 내용을 목적지의 저장 칸에 쓰는 일이다. 원본 읽기 가능 범위, 목적지 쓰기 가능 범위, 객체 수명을 각각 확인한다. 반환 포인터가 성공 용량 검사를 대신하지 않는다.

  • 두 구간이 일부 칸을 공유하면 겹침이다. 같은 배열 안의 [0,5)와 [1,6)은 겹친다. 서로 다른 살아 있는 배열 bytes와 copy는 별도 객체다.

  • 자가진단: [A,B,0]을 문자열로 복사하려면 A,B뿐 아니라 0도 포함한 세 칸이 필요하다. [X,0,Y]라는 세 바이트를 복사할 때는 내부 0 뒤 Y도 보존해야 한다.

학습 목표

  • strcpy와 strncpy의 종료·패딩·용량 계약을 대조한다.

  • memcpy와 memmove의 명시적 바이트 수·겹침 조건을 설명한다.

  • 함수 선택과 별도 경계 검사를 결합해 예제를 추적한다.

문자열을 종료 칸까지 복사하기

strcpy(dst,src)는 유효한 원본 문자열을 종료 0까지 복사한다. 원본의 길이 L이면 목적지에 최소 L+1칸이 있어야 하고 구간이 겹치면 UB다. 이 함수에는 용량 인자가 없으며 알아서 크기를 검사하거나 새 공간을 확보하지 않는다. 코드의 dst[5]와 "cat"은 네 칸 복사라 충분하다. 원본 측정에서 목적지 쓰기까지 내용을 바꿀 수 있는 별도 실행 주체가 있다면 길이 측정 한 번만으로 안전을 증명할 수 없다.

strncpy(dst,src,n)는 원본에서 첫 0 뒤 문자를 더 복사하지 않지만, 원본 문자열이 n보다 짧으면 목적지 전체 n칸이 채워질 때까지 0을 덧쓴다. 반대로 첫 n개에 0이 없으면 n개만 복사하고 종료를 추가하지 않는다. 그러므로 쓰기 가능한 목적지 n칸과 계약상 유효한 원본 읽기 범위가 필요하다. 겹침도 허용하지 않는다. 아래 raw[3]의 결과 W,X,Y는 종료 없는 데이터이며 문자열 출력에 쓰지 않는다.

명시한 바이트를 복사하기

memcpy(dst,src,n)는 문자열 끝을 탐색하지 않고 n개의 char 단위 바이트를 복사한다. 내부 0 뒤도 복사하고 자동 종료 0을 더하지 않는다. 목적지 쓰기 n칸과 원본 읽기 n칸이 유효하며 겹치지 않아야 한다. n=0이 허용되는 표준 문자열 라이브러리 함수라도 명시적인 예외가 없으면 포인터 인자는 유효해야 한다는 C11 규칙이 있으므로 일반 memcpy(NULL,NULL,0)를 안전 관용구로 가르치지 않는다.

memmove는 같은 n칸의 요구를 갖지만 겹치는 복사도 임시 비겹침 배열을 거친 것처럼 처리한다. 실제 구현이 임시 배열을 반드시 할당한다는 뜻은 아니다. 코드에서는 "ABCD"의 다섯 칸 A,B,C,D,0을 오른쪽으로 한 칸 옮겨 [A,A,B,C,D,0]으로 만든다. 원본 [0,5)와 목적지 [1,6)는 모두 여섯 칸 배열 안에 있다. 함수가 겹침을 허용해도 객체 밖까지 쓰는 것은 해결하지 않는다.

함수 이름 대신 계약을 고른다

코드의 pad[5]는 strncpy로 Q,0,0,0,0이 된다. raw는 W,X,Y이고 copy는 X,0,Y다. 이 세 결과의 읽는 방식이 다르다. pad는 종료 있는 문자열로 읽을 수 있지만 raw의 세 문자와 copy의 내부 0 이후 Y는 길이를 따로 알고 원소별로 읽어야 한다. 검사 없이 함수 이름에 safe라는 기대를 붙이면 종료 없음·패딩 비용·겹침 문제를 놓친다.

쓰기 수와 필요한 읽기 수를 호출별로 종이에 표시하면 함수를 비교할 수 있다. strcpy는 첫 0까지, strncpy는 0을 만날 때까지 최대 n의 원본 탐색과 n칸 쓰기, memcpy/memmove는 명시한 n칸이다. 이 본문은 목적지 확장·메모리 할당 실패·동시 접근 안전을 제공한다고 주장하지 않는다. 완전 예제는 충분한 고정 배열과 살아 있는 원본만 사용하며 UB 변형의 출력은 정답으로 제시하지 않는다.

#include <stdio.h>
#include <string.h>
int main(void) {
    char dst[5];
    char raw[3];
    char pad[5];
    char overlap[6] = "ABCD";
    const char bytes[3] = {'X', '\0', 'Y'};
    char copy[3];
    strcpy(dst, "cat");
    strncpy(raw, "WXYZ", sizeof raw);
    strncpy(pad, "Q", sizeof pad);
    memmove(overlap + 1, overlap, 5);
    memcpy(copy, bytes, sizeof copy);
    printf("%s %c%c%c\n", dst, raw[0], raw[1], raw[2]);
    printf("%d %d %d %d\n", pad[1] == 0, pad[2] == 0,
           pad[3] == 0, pad[4] == 0);
    printf("%s %c %d %c\n", overlap, copy[0], copy[1] == 0, copy[2]);
    return 0;
}

중간 과정을 따라가는 예제

완전 예제의 다섯 복사를 순서대로 추적하고 종료 없는 raw를 출력하는 방식이 안전한 이유를 설명한다.

  1. strcpy 뒤 dst는 c,a,t,0을 포함한다. strncpy raw는 첫 세 W,X,Y만 쓰며 종료 0이 없다. 첫 줄은 dst를 %s, raw를 세 %c로 표시한다.

  2. strncpy pad는 Q 한 칸 뒤 네 칸을 0으로 채운다. 네 비교 pad[k]==0은 모두 참인 int 1을 돌려준다.

  3. memmove는 이전 원본 A,B,C,D,0을 보존한 것처럼 위치 1~5에 배치한다. overlap 전체는 A,A,B,C,D,0이므로 문자열 AABCD다.

  4. memcpy copy는 X,0,Y 세 칸을 모두 복사한다. %c,비교,%c로 X,1,Y를 표시하므로 첫 0에서 멈추는 문자열 출력과 다르다.

예상 stdout은 cat WXY / 1 1 1 1 / AABCD X 1 Y의 세 줄이다. 슬래시는 줄 구분이며 실제 출력 문자가 아니다. 실제 C 실행은 하지 않았다.

종이와 본문으로 직접 해보기

char a[5]="ABCD";에서 memmove(a,a+1,4)의 결과를 그린다. 별도 char b[4]에 strncpy(b,"Hi",4)를 했을 때 네 칸을 적는다. 겹침 복사를 memcpy로 바꾸어도 같은 출력이라고 말할 수 있는가?

힌트 보기

원본 a+1의 네 칸은 B,C,D,0이다. strncpy의 원본이 짧으면 n칸까지 0 패딩을 한다.

풀이 보기

a는 [B,C,D,0,0]이 되고 문자열은 BCD다. 마지막 기존 0은 덮지 않는다. b는 [H,i,0,0]이다. a의 원본/목적지는 겹치므로 memcpy로 바꾸면 UB이며 BCD라는 출력 예측을 정답으로 삼을 수 없다.

오해와 반례

strncpy는 언제나 NUL을 붙이고 memmove는 공간도 자동 확보한다.

raw[3]에 "WXYZ"를 n=3으로 복사하면 WXY뿐이며 NUL이 없다. memmove(a+1,a,5)에 a가 다섯 칸밖에 없으면 목적지 마지막 칸이 객체 밖이다. 겹침 지원은 저장 용량 검사가 아니다.

자기점검

strncpy(d,"Q",5)는 몇 칸을 쓰는가?

답과 이유 보기

다섯 칸이다.

Q 뒤 종료와 추가 패딩을 합해 0 네 칸을 써서 n칸을 채운다.

memcpy는 첫 0 뒤 바이트도 복사하는가?

답과 이유 보기

명시한 n 범위 안이면 복사한다.

문자열 종료를 탐색하지 않는 바이트 복사 함수다.

겹치는 구간의 memcpy 결과를 관찰해 잘 작동하면 표준 계약이 성립하는가?

답과 이유 보기

아니다.

겹침은 UB의 조건이고 한 구현 관찰은 C11 보장을 만들지 못한다.

한 단계 더

심화: 오른쪽으로 한 칸 겹쳐 옮길 때 단순한 왼쪽부터 대입은 a[1]=a[0] 다음 a[2]=a[1]에서 이미 바뀐 A를 복사해 원래 B를 잃는다. 원본 끝부터 오른쪽 목적지로 옮기면 아직 필요한 원본을 덮지 않는다는 불변식으로 해당 방향 복사를 증명할 수 있다. 반대로 왼쪽 이동에는 앞에서 뒤로가 적절하다. memmove는 이런 방향 선택을 직접 구현하지 않고도 원래 n바이트와 같은 결과를 계약으로 제공한다. strcpy 전에 L+1≤cap를 검사하려면 덧셈 넘침을 피하는 L<cap와 유효·안정적인 원본 문자열을 함께 요구한다. 동적 할당 크기로 L+1을 계산할 때는 L==SIZE_MAX를 먼저 거절해야 한다.

소단원 6.4

버퍼 크기와 절단 처리

다섯 칸 버퍼에 planet을 출력하면 반환값은 저장한 네 글자일까, 필요한 여섯 글자일까?

준비 개념과 학습 목표

준비 개념

  • 버퍼 용량 cap는 실제 쓰기 가능한 char 칸 수다. 문자열 내용에 L칸과 종료에 한 칸이 필요하다. 문자열을 담으려면 cap>0이고 L<cap여야 한다.

  • 형식 지정 출력의 %s는 유효한 원본 문자열을 읽는다. snprintf의 n은 목적지에 쓸 수 있는 상한이며 원본의 유효성·읽기 경계를 대신 검사하지 않는다.

  • 자가진단: 다섯 칸을 그리고 마지막 한 칸을 종료 0용으로 남기면 내용은 최대 네 칸이다. 원하는 여섯 칸과 실제 저장 네 칸을 다른 색으로 표시하자.

학습 목표

  • snprintf의 필요한 길이 반환값과 실제 저장량을 구별한다.

  • 음수 오류·n=0·n=1·정확한 절단 경계를 판정한다.

  • 절단 정책과 인코딩·형식 문자열·겹침 조건을 설명한다.

snprintf의 공간 계약

C11 snprintf(s,n,format,...)은 n>0인 정상적인 출력에서 최대 n−1칸의 내용을 쓰고 끝에 0을 붙인다. 목적지는 실제로 n칸을 쓸 수 있어야 한다. n=0이면 아무것도 쓰지 않으며 이 특별한 경우 s=NULL도 허용된다. n=1과 비어 있지 않은 내용이면 저장 내용은 없고 첫 칸 0만 남는다. 문자열을 자동으로 확장하는 함수는 아니다.

정상 반환 r은 버퍼가 충분했다면 쓰였을 내용 길이이며 종료 0은 제외한다. 인코딩 오류면 음수다. r≥0을 확인한 뒤 r<n이면 전 내용 저장, r≥n이면 절단으로 판정한다. n=0에서 r=0이어도 0<0은 거짓이므로 빈 문자열을 목적지에 써 주었다고 말하지 않는다. 아래 기본 문자열 예제는 필요한 길이가 int 범위 안이고 정상 형식 출력이 가능하다는 조건에서 예상한다.

오류와 절단을 다르게 처리하기

다섯 칸 out에 "planet"을 출력하면 정상 반환 r=6이고 저장은 p,l,a,n,0이다. strlen(out)=4이며 반환 6을 복사된 칸 수로 사용해 배열을 읽으면 안 된다. 고정 예제에서는 sizeof out=5가 int에 표현 가능하므로 (int)sizeof out 비교가 안전하다. 일반적인 임의 size_t 용량을 int로 줄이는 방식은 그 조건 없이 사용하지 않는다.

일반 함수에서 r<0을 먼저 처리하고 비음수 r과 cap을 서로 값이 보존되는 타입으로 비교해야 한다. 예컨대 <stdint.h>의 uintmax_t에 둘을 변환하면 size_t 값과 비음수 int 값을 표현할 수 있어 (uintmax_t)r < (uintmax_t)cap을 사용할 수 있다. 음수를 먼저 거르지 않고 부호 없는 값으로 변환하면 오류가 큰 길이처럼 보인다. 음수 결과 뒤의 버퍼를 성공한 완성 문자열로 읽지 말고 오류 정책으로 넘어간다.

저장 안전성과 내용의 의미

절단된 문자열을 수용할지, 입력을 거절할지, 검증 후 더 큰 공간으로 다시 시도할지는 프로그램 정책이다. 식별자나 파일 경로를 조용히 절단하면 서로 다른 원본이 같은 접두사로 바뀔 수 있으므로 실패로 처리하는 정책이 적절할 수 있다. 두 번 호출해 필요한 길이를 얻고 할당하려면 양수 여유 공간, 길이+1의 넘침, 할당 실패, 두 호출 사이 원본·형식 인자의 안정성까지 따로 검증해야 한다.

종료 0이 있어도 8비트 UTF-8 시퀀스 중간을 자르면 잘못된 텍스트가 될 수 있다. 출력 상한은 바이트 저장 규칙이지 Unicode 문자 경계 보장이나 보안 정책이 아니다. 원본 입력을 형식 문자열로 직접 쓰지 말고 snprintf(out,cap,"%s",input)처럼 고정 형식을 사용한다. 이 방식도 input 문자열의 유효성을 요구한다. snprintf(buf,cap,"%s",buf)처럼 원본과 목적지가 겹치는 호출은 C11에서 UB이므로 아래는 별도 리터럴을 원본으로 쓴다.

#include <stdio.h>
#include <string.h>
int main(void) {
    char out[5];
    int r = snprintf(out, sizeof out, "%s", "planet");
    if (r < 0) {
        puts("encoding error");
        return 1;
    }
    printf("%d %zu %s\n", r, strlen(out), out);
    if (r >= (int)sizeof out) puts("truncated");
    else puts("complete");
    int needed = snprintf(NULL, 0, "%s", "planet");
    if (needed < 0) return 1;
    printf("%d\n", needed);
    return 0;
}

중간 과정을 따라가는 예제

out[5]의 성공 경로와 NULL,0 측정 호출을 종이에 추적한다. 실제 컴파일·출력은 하지 않았으며 음수 오류 경로는 실행 정답으로 주장하지 않는다.

  1. 원본 planet은 기본 문자 여섯 개와 종료 0을 가진다. 충분한 목적지라면 내용 여섯 칸을 쓸 것이므로 정상 r=6이다.

  2. n=5이므로 앞 네 문자 plan과 종료 0이 저장된다. r<0 검사는 거짓이고 strlen(out)=4다.

  3. sizeof out=5는 int에 표현 가능하다. 6≥5라 절단 분기로 들어가 truncated를 표시한다. 내용을 출력할 수 있다는 사실과 완전 저장 성공은 다르다.

  4. snprintf(NULL,0,...)은 목적지에 쓰지 않고 정상 필요한 길이 6을 반환한다. 배열 길이 측정 결과와 출력 내용 측정 결과를 혼동하지 않는다.

정상 성공 경로 예상 stdout은 6 4 plan / truncated / 6의 세 줄이다. 절단이 탐지되었다. 음수 인코딩 오류 경로의 발생이나 출력은 실제 관찰하지 않았다.

종이와 본문으로 직접 해보기

기본 문자 "Hello"를 별도 목적지에 snprintf로 출력한다. 용량 0,1,5,6에 대해 정상 반환값·저장 내용·완전 저장 여부를 표로 적는다. n=0의 목적지는 NULL이어도 된다고 가정하고 나머지는 해당 크기의 유효 배열이다.

힌트 보기

필요한 내용 길이 5는 용량이 바뀌어도 같다. n>0일 때 내용은 최대 n−1이고 완전 조건은 5<n이다.

풀이 보기

모두 정상 반환 5다. n=0은 쓰지 않으며 저장 문자열 없음, 완전 조건 거짓이다. n=1은 [0]인 빈 문자열, 절단이다. n=5는 Hell과 0, 절단이다. n=6은 Hello와 0, 완전 저장이다. n=5에서 반환==용량은 성공 완료가 아니라 절단 경계다.

오해와 반례

NUL을 붙이는 snprintf라면 절단·보안·Unicode까지 모두 안전하다.

out[5]는 plan으로 종료되어도 planet이 완전히 저장되지 않았다. 인코딩된 다바이트 문자 중간 절단은 유효 UTF-8을 깨뜨릴 수 있고 식별자 접두사 충돌도 별도 문제다. 또한 실제 공간보다 큰 n을 주거나 원본/목적지를 겹치게 하는 호출은 함수 이름으로 정당화되지 않는다.

자기점검

정상 r=5,n=5이면 완전히 저장했는가?

답과 이유 보기

아니다. 절단이다.

종료 칸이 필요하므로 완전 조건은 엄격한 r<n이다.

snprintf(NULL,0,...)이 정상 길이 6을 반환하면 NULL에 종료 0을 썼는가?

답과 이유 보기

아니다. 아무것도 쓰지 않는다.

n=0은 쓰지 않고 필요한 길이만 계산할 수 있는 명시적 예외다.

r<0을 검사하지 않고 size_t로 바꿔 필요한 길이로 사용해도 되는가?

답과 이유 보기

안 된다.

음수 오류가 부호 없는 큰 값으로 변환될 수 있어 오류 분기를 먼저 분리해야 한다.

한 단계 더

심화 증명: 정상 반환 L≥0이고 n>0일 때 저장 내용 길이는 min(L,n−1), 종료 칸을 포함한 쓰기 수는 min(L,n−1)+1≤n이다. 전 내용이 보존되려면 L≤n−1, 즉 L<n이며 n=0의 무쓰기 경우와 분리한다. 용량 5의 절단 정책은 planet과 plank 두 원본을 모두 plan으로 만들 수 있으므로 원본→저장 결과는 단사가 아니다. 식별자 유일성을 유지하려면 절단을 거절하거나 충돌을 별도로 다루어야 한다. 길이 L+1을 할당 크기로 사용할 때 L의 size_t 표현 가능성과 덧셈의 넘침을 확인하며, 성공한 측정 호출이 다음 출력까지 원본 불변이나 공간 확보 성공을 보증하지 않는다는 점도 남는다. 여기서 저장 내용 길이는 snprintf가 생성한 출력 문자 수를 뜻한다. 출력에 내부 NUL이 없을 때만 그 수가 strlen으로 센 길이와 같다. 예를 들어 유효한 두 칸 배열에 snprintf(buf,2,"%c",0)를 정상 수행하면 반환값은 1이고 buf는 [0,0]이므로 strlen(buf)는 0이다. 이 반례는 종이 계약 추적이며 실행하지 않았다.
