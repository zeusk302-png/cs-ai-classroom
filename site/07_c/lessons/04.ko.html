소단원 4.1

prototype과 호출

함수 본문이 뒤에 있어도 앞에서 안전하게 호출하려면 무엇을 알려 주어야 할까?

준비 개념과 학습 목표

준비 개념

  • 선언은 이름과 타입을 소개하고 정의는 함수 본문을 제공한다. int는 정수 타입이며 세미콜론은 선언의 끝이다.

  • 인수는 호출 괄호 안의 식이고 매개변수는 함수가 받는 지역 이름이다. 2+3은 이 단원의 모든 C 구현에서 int로 표현 가능한 작은 값이다.

학습 목표

  • prototype에 반환형과 매개변수 타입을 표시한다.

  • C11의 (void)와 빈 () 선언을 구별한다.

  • 타입 검사와 의미 계약의 차이를 설명한다.

호출 앞에 놓는 타입 약속

int add(int a, int b);는 두 int를 받아 int를 돌려주는 함수의 prototype이다. 여기의 a,b 이름은 설명을 돕고 호출자 이름과 같을 필요가 없다. 본문을 뒤에 두어도 호출 지점에서 이 선언이 보이면 타입 정보를 사용할 수 있다.

아래는 표준 라이브러리 외 의존성이 없는 완전한 소스다. add의 정의도 선언과 호환되어야 한다. 선언이 존재하는 것과 정의가 실제 프로그램에 포함되는 것은 별개이므로 다른 파일로 옮기면 링크 단계에서 정의를 함께 제공해야 한다.

#include <stdio.h>
int add(int a, int b);
int main(void) { int r=add(2,3); printf("%d\n",r); return 0; }
int add(int a, int b) { return a+b; }

인수 변환과 검사 범위

prototype이 보이는 호출에서는 인수 수와 타입의 허용 관계가 제약을 받으며 각 인수 값은 해당 매개변수 타입으로 대입하듯 변환된다. double 값을 int 인수로 넘기는 것이 항상 문법 오류는 아니다. 유한한 2.75를 int로 변환하면 2지만 정수 부분이 대상 범위 밖이면 안전한 호출로 간주할 수 없다.

타입 정보는 a+b가 int 범위 안인지, 포인터가 살아 있는 객체를 가리키는지까지 증명하지 않는다. add의 의미 계약은 두 입력과 수학적 합이 int로 표현 가능하다는 조건이다. 제약 위반에는 진단이 요구되지만 모든 컴파일러가 반드시 번역을 거부한다고 일반화하지 않는다.

판본과 평가 순서를 고정하기

이 단원은 C11이다. int ping(void);는 매개변수가 없다는 prototype이다. 반면 정의가 아닌 int ping(); 선언의 빈 괄호는 매개변수 수와 타입 정보를 제공하지 않는다. C++나 C23의 빈 괄호 규칙을 이 설명에 섞지 않는다.

함수 호출의 인수는 본체 진입 전에 평가되지만 인수들이 왼쪽부터 평가된다는 보장은 없다. 순서가 필요한 변경은 독립 문장으로 먼저 수행하고 그 결과를 인수로 전달하자. 같은 스칼라를 순서 없는 인수 식에서 여러 번 변경하는 코드는 이 단원의 출력 예제로 사용하지 않는다.

중간 과정을 따라가는 예제

완전한 add 소스에서 main의 r과 예상 표준출력을 추적하라.

  1. main 진입 뒤 add 선언의 두 int와 호출 인수 2,3이 대응한다.

  2. 매개변수 a=2,b=3을 가진 함수 호출이 시작한다.

  3. a+b=5가 int 범위 안에 있으므로 return 5가 호출 식의 값이다.

  4. main의 r=5가 되고 printf의 %d에 int 값 5가 전달된다.

예상 출력은 5와 줄바꿈이다. 실제 컴파일·실행 기록은 없다.

종이와 본문으로 직접 해보기

int f(void);와 int g();를 종이에 쓰고 C11에서 어느 선언이 무인수 호출 계약을 명시하는지 표시하라. add(4,5)도 추적하라.

힌트 보기

정의가 아니라 선언을 읽고 있다는 점을 유지하자.

풀이 보기

f는 매개변수 없음, g는 정보 없음이다. add의 매개변수는 4,5이고 합은 9다. g가 어떤 인수도 안전하게 받는다는 결론은 나오지 않는다.

오해와 반례

prototype이 있으면 모든 잘못된 입력이 자동 차단된다.

타입이 맞는 add(INT_MAX,1)도 수학적 합이 int 범위를 넘으면 signed overflow로 정의되지 않은 동작이다. 타입 검사와 값의 사전조건을 함께 확인해야 한다.

자기점검

prototype의 매개변수 이름이 정의의 이름과 같아야 하는가?

답과 이유 보기

아니다.

대응 타입과 개수 등 호환성이 중요하며 이름은 호출 계약의 타입 일부가 아니다.

C11의 int f(); 선언은 매개변수 없음인가?

답과 이유 보기

정보를 제공하지 않는다.

무인수 prototype은 int f(void);로 명시한다.

add(2,3)이 5를 반환함을 타입 검사만으로 증명하는가?

답과 이유 보기

아니다.

정의의 연산과 표현 범위까지 확인해야 의미적 결과를 얻는다.

한 단계 더

두 인수의 이름을 x,y로 바꾸어도 결과가 보존되는 이유를 설명하자. 각 매개변수의 사용을 일관되게 치환하고 다른 이름과 충돌하지 않으면 a+b와 x+y는 동일한 전달 값의 합이다. 반면 return a-b로 본문을 바꾸면 타입은 같아도 add의 합 계약을 깨뜨린다. 함수의 타입과 명세가 서로 다른 층이라는 반례다.

소단원 4.2

값 전달·반환

함수 안에서 매개변수를 바꾸면 호출자 변수도 바뀔까?

준비 개념과 학습 목표

준비 개념

  • 변수는 값을 보관하는 객체에 붙인 이름이다. 대입은 오른쪽 값을 왼쪽 객체에 저장한다.

  • &x는 x를 가리키는 포인터를 만들고 *p는 p가 가리키는 객체를 사용한다. 역참조에는 유효하고 살아 있는 적합한 객체가 필요하다.

학습 목표

  • 값 복사와 가리킨 객체 변경을 구별한다.

  • return의 결과와 출력의 역할을 구별한다.

  • 반환 포인터의 수명 조건을 설명한다.

별도의 매개변수 객체

C의 인수 전달은 값 전달이다. 함수에 int를 보내면 해당 값으로 매개변수를 초기화하고 매개변수에 대입해도 호출자의 int 객체에는 대입하지 않는다. 아래 bump에서 n과 x는 별도의 객체이며 n=6과 return 6은 서로 다른 행동이다.

반환 값을 사용하지 않고 bump(x);만 호출하면 x는 그대로다. 반환 식의 값이 호출 식으로 전달되며 그 값을 호출자가 y에 저장해야 y가 생긴다. printf는 출력 부작용을 수행할 뿐 호출자의 x를 함수 반환 값으로 교체하는 문장이 아니다.

int bump(int n) { n=n+1; return n; }

포인터 값도 복사된다

포인터 전달도 값 전달이지만 복사한 주소를 통해 같은 대상 객체를 변경할 수 있다. set7의 p=&x는 호출 동안 살아 있고 수정 가능한 int x를 가리킨다는 사전조건이 필요하다. NULL, 이미 수명이 끝난 객체의 주소, 부적합한 타입의 주소를 역참조하는 사용은 계약 밖이다.

함수 내부에서 p를 다른 주소로 바꾸는 것과 *p를 변경하는 것은 다르다. 전자는 지역 포인터의 값 변경이고 후자는 대상 객체 변경이다. 배열 모양의 매개변수 선언도 포인터 타입으로 조정되므로 전체 배열과 길이가 자동 복사된다고 추측하지 않는다.

void set7(int *p) { *p=7; }

반환 값과 살아 있는 대상

int 값을 반환하면 그 값은 지역 이름의 사용 가능 범위가 끝나도 호출자가 사용할 수 있다. 그러나 지역 자동 객체의 주소를 반환했다고 그 객체의 수명이 연장되지는 않는다. 수명이 끝난 대상에 대한 접근에는 고정 출력이 없다.

구조체를 값으로 전달할 때도 포인터 필드가 가리키는 대상까지 깊은 복사하는 것은 아니다. 또한 비void 함수는 사용되는 결과를 모든 정상 반환 경로에서 제공해야 한다. 이 단원은 main의 특별한 끝 도달 규칙을 일반 함수에 확대하지 않는다.

중간 과정을 따라가는 예제

x=5에서 y=bump(x)를 수행하고 set7(&x)를 수행한 뒤 x,y를 추적하라.

  1. bump 진입 때 지역 n에 x의 값 5가 복사된다.

  2. n=6이 되지만 호출자의 x는 5다.

  3. return 6을 받아 y=6을 저장한다.

  4. set7의 p는 &x 값을 받아 *p=7을 수행하므로 x=7이 된다.

예상 상태 x=7,y=6이다. 주소 숫자나 실제 실행 결과를 측정하지 않았다.

종이와 본문으로 직접 해보기

호출자 x=3을 그리고 가상 함수 void change(int *p)에 &x를 전달했다고 하자. 함수의 지역 매개변수 p가 처음에 x를 가리킨다. 함수 안에서 int z=9; p=&z;만 수행하는 경우와 *p=9;만 수행하는 경우의 x를 비교하라. 두 경우는 따로 시작한다.

힌트 보기

지역 포인터 상자와 대상 x 상자를 분리하자.

풀이 보기

p=&z만 하면 x=3이다. *p=9만 하면 x=9다. 첫 경우 함수 종료 후 z를 가리킨 포인터를 반환해 사용해서는 안 된다.

오해와 반례

주소를 넘기므로 C는 참조 전달 언어다.

복사되는 값이 주소일 뿐이다. 지역 p 자체를 재대입해도 호출자의 포인터 객체는 바뀌지 않는다. 그 포인터 객체를 바꾸려면 적합한 포인터의 포인터 계약 등이 필요하다.

자기점검

bump(x)의 반환 값을 버리면 x는 증가하는가?

답과 이유 보기

아니다.

n의 변경은 별도 매개변수 객체에 일어난다.

set7(NULL)이 안전한가?

답과 이유 보기

아니다.

NULL을 역참조하지 않는다는 검사가 없고 유효한 int 대상 사전조건도 만족하지 않는다.

지역 int의 주소를 반환하면 수명이 연장되는가?

답과 이유 보기

아니다.

주소 값 반환과 대상 객체 수명은 별개의 조건이다.

한 단계 더

교환 함수 void swap(int *a,int *b)를 설계하자: int t=*a; *a=*b; *b=t;. 두 포인터가 호출 전체 동안 살아 있는 수정 가능한 int를 가리키면 서로 다른 대상일 때 옛 A,B가 B,A가 된다. 같은 대상을 가리키면 t가 그 값이고 두 대입 뒤에도 원래 값이라 역시 교환 관계를 만족한다. NULL이나 수명이 끝난 대상은 이 증명의 전제 밖이다. 호출자 변수 이름을 교환하는 것이 아니라 두 대상의 값을 교환한다.

소단원 4.3

지역·전역·static

함수를 두 번 부르면 무엇은 새로 시작하고 무엇은 이어질까?

준비 개념과 학습 목표

준비 개념

  • 블록은 { } 사이 영역이며 안쪽 선언이 같은 이름의 바깥 선언을 가릴 수 있다.

  • 함수 호출 순서가 서로 다른 문장에 있으면 앞 호출을 끝내고 다음 호출로 진행한다. static은 위치에 따라 해석해야 한다.

학습 목표

  • 지역과 파일 범위 이름을 구별한다.

  • 블록 static 객체의 상태 보존을 추적한다.

  • 재진입 및 동시 호출의 한계를 설명한다.

지역은 범위를 말한다

흔히 전역 변수라 부르는 파일 범위 객체 이름은 선언 뒤부터 번역 단위 끝까지 사용할 수 있다. 함수 안의 보통 지역 변수 이름은 해당 블록 안에서 사용한다. 안쪽 x가 바깥 x를 가리는 것은 바깥 객체를 삭제하거나 값을 복사해 덮어쓴다는 뜻이 아니다.

지역이라는 말만으로 수명을 판정하면 안 된다. 블록 안의 static 변수도 지역 이름이지만 객체는 호출마다 새로 시작하지 않는다. 범위는 소스에서 이름을 쓰는 영역, 수명은 실행 중 객체가 존재하는 기간이다.

두 종류의 카운터

아래 next는 블록 static n=0 하나를 계속 사용한다. 처음 두 호출은 1,2를 반환한다. fresh의 자동 n은 각 호출의 초기화에서 0을 저장하여 두 호출 모두 1을 반환한다. 호출 수를 제한하여 int 증가가 표현 범위를 넘지 않는다고 가정한다.

C11에서 정적 저장기간 객체는 프로그램 시작 전에 한 번 초기화된다. 이 블록 static 초기화를 C++의 첫 진입 시 동적 초기화나 Java 클래스 초기화와 같은 규칙으로 설명하지 않는다. static 초기값 표현에는 C의 별도 제약이 있고 여기의 상수 0은 이를 만족한다.

int next(void) { static int n=0; ++n; return n; }
int fresh(void) { int n=0; ++n; return n; }

숨은 공유 상태의 대가

next는 인수 없이 호출해도 과거 호출에 따라 결과가 달라진다. 순차 호출에서는 편리하지만 테스트를 독립적으로 시작하려면 상태 초기화 정책이 필요하다. 이 단원의 카운터는 동시 스레드의 안전한 카운터가 아니다. static 키워드는 증가의 원자성이나 동기화를 제공하지 않는다.

전역 상태에 의존하는 함수를 인수와 결과 중심 함수로 바꾸면 의존성이 드러난다. 그러나 입력 포인터가 공유된 수정 가능한 객체를 가리키면 지역 이름만 쓰는 함수도 공유 부작용을 낸다. 지역 변수라는 표면만 보고 순수하거나 재진입 가능하다고 판정하지 말자.

중간 과정을 따라가는 예제

처음 상태에서 a=next(); b=next(); c=fresh(); d=fresh();를 서로 다른 문장으로 수행하라.

  1. 정적 n의 초기 값은 0이며 첫 next에서 1로 증가하여 a=1이다.

  2. 두 번째 next는 같은 객체의 1을 읽어 2로 만들므로 b=2다.

  3. 첫 fresh의 자동 n은 0으로 초기화되고 c=1이 된다.

  4. 두 번째 fresh의 새 호출도 n=0 초기화부터 시작하여 d=1이다.

예상 a,b,c,d는 1,2,1,1이다. 함수 호출을 printf 인수 여러 개에 넣어 그 평가 순서를 추측하지 않는다.

종이와 본문으로 직접 해보기

int x=4; { int x=8; x=9; }에서 바깥 x를 추적하라. 이어 fresh 대신 static n을 쓰는 함수의 세 번째 순차 반환을 적어라.

힌트 보기

동일 철자의 이름이 서로 다른 객체를 가리키는지 표시하자.

풀이 보기

블록 안의 x만 9가 되고 바깥 x는 4다. next의 세 번째 반환은 3이다. 안쪽 범위 종료는 바깥 값을 복구하는 대입이 아니다.

오해와 반례

static 변수는 다른 파일에서 접근할 수 있는 전역 변수다.

블록 static 이름은 블록 범위이며 linkage가 없다. 파일 범위 static 이름은 internal linkage다. 둘 다 정적 저장기간이라는 공통점과 이름 접근 규칙의 차이를 분리해야 한다.

자기점검

블록 static은 함수가 끝나면 객체가 사라지는가?

답과 이유 보기

아니다.

이 예제 객체의 정적 저장기간은 전체 프로그램 실행에 걸친다.

안쪽 x의 대입이 바깥 x를 바꾸는가?

답과 이유 보기

이 예제에서는 아니다.

이름 가림으로 서로 다른 객체를 지정한다.

static ++n이 동시 호출에도 안전한가?

답과 이유 보기

보장되지 않는다.

static은 동기화나 원자적 연산을 지정하지 않는다.

한 단계 더

상태 불변식을 순차 호출 k회 뒤 n=k로 잡자. 초기 k=0에서 초기화 n=0으로 성립한다. k<INT_MAX이고 다른 변경이 없으면 다음 ++n은 정의되며 n=k+1이 되어 귀납 단계가 성립한다. k=INT_MAX 뒤의 호출은 이 증명에서 제외된다. 수학의 무한 자연수 카운터를 유한 int 프로그램에 무조건 옮길 수 없는 이유다.

소단원 4.4

저장기간과 linkage

이름을 더 이상 쓸 수 없다는 말과 객체가 사라졌다는 말은 같을까?

준비 개념과 학습 목표

준비 개념

  • 번역 단위는 전처리 뒤 한 소스 파일의 내용이다. 여러 번역 단위를 연결해 프로그램을 만들 수 있다.

  • 이름, 객체, 선언을 분리해 그리자. 같은 객체에 대한 선언 둘과 같은 철자의 서로 다른 객체가 모두 가능하다.

학습 목표

  • scope·storage duration·linkage를 세 축으로 분류한다.

  • 외부 선언과 정의의 관계를 설명한다.

  • 할당 객체와 자동 객체의 수명 위험을 구별한다.

세 질문을 따로 묻기

scope는 이 위치에서 이름을 쓸 수 있는가, storage duration은 객체의 저장공간을 어느 실행 기간 동안 보장하는가, linkage는 다른 선언이 같은 객체나 함수를 가리키는가를 묻는다. linkage가 없는 지역 객체에도 수명은 존재하고 내부 연결 객체도 여러 선언을 통해 같은 대상을 지정할 수 있다.

C11의 객체 저장기간은 static, thread, automatic, allocated 네 종류다. 함수는 객체가 아니므로 파일 static 함수에 객체의 저장기간을 붙이지 않는다. stack/heap이라는 구현 배치 비유도 이 네 언어 분류를 대신하지 않는다.

선언 표를 완성하기

아래 g는 파일 범위·external linkage·static 저장기간 객체다. hidden은 파일 범위·internal linkage·static 저장기간이다. f의 local은 블록 범위·no linkage·automatic이고 memo는 블록 범위·no linkage·static이다. 함수 f 자체에는 외부 연결이 있지만 객체 저장기간 칸은 적용하지 않는다.

extern int g;는 이 경우 앞선 g와 같은 대상을 선언하며 새 값을 초기화하지 않는다. extern이 언제나 external linkage를 만든다고 말하면 틀린다. 앞서 보이는 static 선언의 연결을 이어받는 경우가 있으므로 선언 순서와 가시성을 확인해야 한다.

int g=2;
static int hidden=3;
extern int g;
void f(void) { int local=4; static int memo=5; (void)local; (void)memo; }

객체 종료와 소유권 계약

malloc으로 성공적으로 얻은 할당 저장공간은 그것을 가리키던 지역 포인터 변수의 범위가 끝났다고 자동 해제되지 않는다. 반대로 free로 해제되면 포인터 변수 이름이 남아 있어도 대상에 접근할 권리는 없다. 할당 실패 검사, 크기 계산의 범위, 정확한 해제 대상과 소유권을 후속 메모리 단원에서 함께 다룬다.

자동 객체 주소를 바깥에 저장해도 블록 종료는 그 객체의 수명을 끝낸다. 이후 접근은 정의되지 않은 동작이며 N1570은 수명 끝의 관련 포인터 값도 indeterminate로 규정한다. 주소 숫자가 우연히 같거나 데이터가 화면에 남아 보이는 현상으로 유효성을 증명하지 않는다.

중간 과정을 따라가는 예제

예제의 g,hidden,local,memo,f를 세 축으로 분류하고 f가 두 번 호출될 때 memo 객체의 수를 판단하라.

  1. g: 파일 범위, 외부 연결, 정적 저장기간이다. extern 선언은 같은 g를 지정한다.

  2. hidden: 파일 범위, 내부 연결, 정적 저장기간이다.

  3. local: 블록 범위, 연결 없음, 자동 저장기간이며 각 호출에 해당하는 객체가 있다. memo: 블록 범위, 연결 없음, 정적 저장기간이다.

  4. f: 파일 범위, 외부 연결인 함수이며 객체 저장기간 분류 대상이 아니다. memo는 순차 두 호출에서 같은 객체 하나다.

이 분류는 C11 선언과 수명 규칙에 대한 종이 판정이며 실제 링커 심볼이나 메모리 배치를 측정하지 않았다.

종이와 본문으로 직접 해보기

파일 범위 static int x=1; 다음에 extern int x;가 있다. x의 연결과 저장기간을 적어라. 함수 내부 static int y=2;와 비교하라.

힌트 보기

extern을 읽기 전에 앞서 보이는 선언을 찾자.

풀이 보기

뒤 extern x도 앞 static x의 내부 연결을 이어받으며 객체는 정적 저장기간이다. y는 블록 범위·연결 없음·정적 저장기간이다. 같은 static 저장기간이어도 이름의 연결은 다르다.

오해와 반례

지역 포인터 변수가 살아 있으니 그 대상도 살아 있다.

포인터 객체와 대상의 수명은 별개다. 대상이 free로 해제되거나 자동 객체 블록이 끝났다면 포인터 이름이 남아 있어도 대상 접근을 정당화하지 못한다.

자기점검

함수에 automatic 저장기간을 붙이는가?

답과 이유 보기

아니다.

저장기간의 이 분류는 객체에 관한 것이다.

파일 static x 뒤 보이는 extern x는 무조건 external linkage인가?

답과 이유 보기

아니다.

앞선 내부 연결 선언을 이어받는 규칙을 적용한다.

malloc 대상은 지역 포인터 범위 종료만으로 해제되는가?

답과 이유 보기

아니다.

할당 저장공간의 수명과 포인터 변수의 자동 저장기간은 다르다.

한 단계 더

모듈 내부 static int total=0;을 두고 읽기 함수와 범위를 검사하는 변경 함수만 외부에 제공하는 설계를 생각하자. 외부에서 이름 total을 직접 선언하여 같은 내부 객체를 지정할 수는 없으므로 의도하지 않은 직접 이름 접근을 줄인다. 그러나 주소를 반환하면 외부 코드가 그 객체를 변경할 수 있고, 함수가 검사 없이 overflow를 일으켜도 linkage는 막지 않는다. 내부 연결은 모든 메모리 안전성이나 정보 보안을 증명하는 장치가 아니며 제공하는 인터페이스 계약을 따로 증명해야 한다.
