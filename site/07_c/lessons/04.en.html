Subtopic 4.1

Prototypes and Calls

What must a caller know to call a function safely when its body appears later in the file?

Preparation and learning goals

Preparation

  • A declaration introduces a name and its type; a definition provides the function body. int is an integer type, and a semicolon ends a declaration.
  • An argument is an expression inside the call parentheses; a parameter is the local name that receives it. The small value 2+3 is representable as int on every C implementation considered in this unit.

Learning goals

  • Identify the return type and parameter types in a prototype.
  • Distinguish (void) from an empty () declaration in C11.
  • Explain the difference between type checking and a semantic contract.

A type agreement before the call

int add(int a, int b); is a prototype for a function that takes two ints and returns an int. The names a,b aid explanation and need not match names used by the caller. Even if the body appears later, the caller can use the type information when this declaration is visible at the call site.

The following is a complete source file with no dependencies beyond the standard library. The definition of add must also be compatible with the declaration. Having a declaration and including a definition in the actual program are separate requirements: if the definition is moved into another file, it must still be supplied at link time.

#include <stdio.h>
int add(int a, int b);
int main(void) { int r=add(2,3); printf("%d\n",r); return 0; }
int add(int a, int b) { return a+b; }

Argument conversions and the limits of checking

When a prototype is visible, a call is subject to constraints on the number of arguments and their permitted types; each argument value is converted to the corresponding parameter type as if by assignment. Passing a double as an int argument is not always a syntax error. Converting the finite value 2.75 to int produces 2, but a call cannot be treated as safe if the integer part is outside the target range.

Type information does not prove that a+b lies within the int range or that a pointer refers to a live object. The semantic contract of add requires that both inputs and their mathematical sum be representable as int. A constraint violation requires a diagnostic, but do not generalize this into a requirement that every compiler must reject translation.

Fix the edition and evaluation-order assumptions

This unit uses C11. int ping(void); is a prototype specifying no parameters. In contrast, in an int ping(); declaration that is not a definition, the empty parentheses provide no information about parameter count or types. Do not mix the C++ or C23 empty-parentheses rules into this explanation.

The arguments of a function call are evaluated before entry to its body, but left-to-right argument evaluation is not guaranteed. Perform changes that require an order in separate statements first, then pass their results as arguments. This unit does not use multiple modifications of the same scalar in unsequenced argument expressions as examples with predicted output.

A worked example, step by step

Trace r in main and the expected standard output of the complete add source.

  1. After entering main, the two int parameters in the add declaration correspond to the call arguments 2,3.
  2. The function call begins with parameters a=2,b=3.
  3. Because a+b=5 lies within the int range, return 5 supplies the value of the call expression.
  4. The caller stores r=5, and passes the int value 5 for the %d conversion in printf.

The expected output is 5 followed by a newline. There is no actual compilation or execution record.

Try it with paper and the lesson

Write int f(void); and int g(); on paper and mark which declaration explicitly specifies a no-argument call contract in C11. Also trace add(4,5).

Show hint

Keep in mind that you are reading declarations, not definitions.

Show solution

f specifies no parameters; g provides no parameter information. The add parameters are 4,5 and their sum is 9. This does not imply that g can safely accept arbitrary arguments.

Misconception and counterexample

A prototype automatically blocks every invalid input.

Even the correctly typed call add(INT_MAX,1) has undefined behavior from signed overflow when its mathematical sum exceeds the int range. Check both types and value preconditions.

Check your understanding

Must parameter names in the prototype match those in the definition?

Show answer and reasoning

No.

Compatibility of corresponding types, counts, and related requirements matters; names are not part of the call-contract type.

Does the C11 declaration int f(); specify no parameters?

Show answer and reasoning

It provides no parameter information.

Write int f(void); to specify a no-argument prototype.

Does type checking alone prove that add(2,3) returns 5?

Show answer and reasoning

No.

The operations in the definition and their representable ranges must also be checked to obtain the semantic result.

Explore further

Explain why renaming the two parameters to x,y preserves the result. If every use of each parameter is consistently renamed without collisions with other names, a+b and x+y add the same transmitted values. In contrast, changing the body to return a-b preserves the type but violates the sum contract of add. This counterexample shows that a function type and its specification are different layers.

Subtopic 4.2

Passing Values and Returning Results

If a function changes its parameter, does the caller’s variable change too?

Preparation and learning goals

Preparation

  • A variable is a name for an object that holds a value. Assignment stores the right-hand value in the left-hand object.
  • &x produces a pointer to x, and *p accesses the object that p points to. Dereferencing requires a valid, live object of a suitable type.

Learning goals

  • Distinguish copying a value from changing the object it points to.
  • Distinguish a return value from printed output.
  • Explain the lifetime requirements of a returned pointer.

A separate parameter object

C passes arguments by value. Passing an int initializes a parameter with that value; assigning to the parameter does not assign to the caller’s int object. In bump below, n and x are separate objects, and n=6 and return 6 are different actions.

If the caller uses only bump(x); and discards the result, x remains unchanged. The value of the return expression becomes the value of the call expression; the caller must store it in y to give y that value. printf performs an output side effect; it is not a statement that replaces the caller’s x with a function result.

int bump(int n) { n=n+1; return n; }

Pointer values are copied too

Passing a pointer is also passing by value, but the copied address can be used to modify the same target object. For set7, p=&x requires the precondition that x is a live, modifiable int throughout the call. Dereferencing NULL, an address of an object whose lifetime has ended, or an address of an unsuitable type is outside the contract.

Reassigning p to a different address inside the function differs from changing *p. The former changes the local pointer value; the latter changes the target object. An array-shaped parameter declaration is adjusted to a pointer type, so do not assume the entire array and its length are automatically copied.

void set7(int *p) { *p=7; }

Returned values and live targets

When an int value is returned, the caller can use it even after the scope in which the local name was usable has ended. Returning the address of a local automatic object, however, does not extend that object’s lifetime. Access to a target whose lifetime has ended has no fixed output.

Passing a structure by value does not deeply copy the targets of its pointer fields either. A non-void function must also provide a result on every normal return path where that result is used. This unit does not extend the special end-of-main rule to ordinary functions.

A worked example, step by step

Starting with x=5, execute y=bump(x) and then set7(&x). Trace x,y.

  1. On entry to bump, the value 5 from x is copied into the local n.
  2. n becomes 6, but the caller’s x remains 5.
  3. The caller receives return 6 and stores y=6.
  4. The p parameter of set7 receives &x and executes *p=7, so x becomes 7.

The expected state is x=7,y=6. No numerical addresses or actual execution results were measured.

Try it with paper and the lesson

Draw the caller’s x=3 and suppose &x is passed to a hypothetical function void change(int *p). Its local parameter p initially points to x. Compare x when the function performs only int z=9; p=&z; with x when it performs only *p=9;. Start the two cases separately.

Show hint

Draw the local pointer box separately from the target x box.

Show solution

With only p=&z, x=3. With only *p=9, x=9. In the first case, a pointer to z must not be returned and used after the function ends.

Misconception and counterexample

Because addresses are passed, C is a pass-by-reference language.

The copied value happens to be an address. Reassigning the local p does not change a pointer object belonging to the caller. Changing that pointer object requires a separate suitable contract, such as passing a pointer to it.

Check your understanding

Does discarding the return value of bump(x) increment x?

Show answer and reasoning

No.

The modification of n occurs in a separate parameter object.

Is set7(NULL) safe?

Show answer and reasoning

No.

There is no check preventing NULL dereference, and the valid-int-target precondition is not satisfied.

Does returning the address of a local int extend its lifetime?

Show answer and reasoning

No.

Returning an address value and extending its target object’s lifetime are separate matters.

Explore further

Design void swap(int *a,int *b) with int t=*a; *a=*b; *b=t;. If both pointers refer to live, modifiable ints throughout the call, distinct targets with old values A,B end with B,A. If the pointers refer to the same target, t holds that value and both assignments leave the original value unchanged, which also satisfies the swap relation. NULL and targets whose lifetimes have ended lie outside the proof’s assumptions. The function exchanges two target values, not the caller’s variable names.

Subtopic 4.3

Local, Global, and static

When a function is called twice, which state starts over and which state carries on?

Preparation and learning goals

Preparation

  • A block is the region between { }, and an inner declaration can hide an outer declaration with the same name.
  • When calls appear in separate statements, the earlier call finishes before execution proceeds to the next one. Interpret static according to where it appears.

Learning goals

  • Distinguish local names from file-scope names.
  • Trace state retained by a block-scope static object.
  • Explain the limits concerning reentrancy and concurrent calls.

Local describes scope

A file-scope object name, often called a global variable name, is usable after its declaration up to the end of the translation unit. An ordinary local variable name inside a function is used within its block. When an inner x hides an outer x, this neither deletes the outer object nor copies a value over it.

Do not determine lifetime from the word local alone. A static variable inside a block has a local name, but its object does not start anew on every call. Scope is the region of source text where a name can be used; lifetime is the period of execution during which an object exists.

Two kinds of counter

The next function below keeps using a single block-scope static n=0. Its first two calls return 1,2. The automatic n in fresh is initialized to 0 on each call, so both calls return 1. Assume the number of calls is restricted so that int increments remain representable.

In C11, an object with static storage duration is initialized once before program startup. Do not describe this block-scope static initialization using the same rules as first-entry dynamic initialization in C++ or Java class initialization. C imposes separate constraints on a static initializer expression, and the constant 0 used here satisfies them.

int next(void) { static int n=0; ++n; return n; }
int fresh(void) { int n=0; ++n; return n; }

The cost of hidden shared state

Although next takes no arguments, its result depends on earlier calls. This is convenient for sequential calls, but independently starting tests requires a state-reset policy. The counter in this unit is not a safe concurrent-thread counter: static supplies neither atomic increments nor synchronization.

Changing a global-state-dependent function into one organized around arguments and results can make its dependencies visible. However, if an input pointer refers to a shared, modifiable object, a function using only local names can still have shared side effects. Do not judge a function pure or reentrant merely from the presence of local variables.

A worked example, step by step

From the initial state, execute a=next(); b=next(); c=fresh(); d=fresh(); as separate statements.

  1. The static n starts at 0; the first next increments it to 1, so a=1.
  2. The second next reads 1 from the same object and changes it to 2, so b=2.
  3. The automatic n in the first fresh is initialized to 0, and c=1.
  4. The second fresh call also begins by initializing n=0, so d=1.

The expected a,b,c,d are 1,2,1,1. Do not put the function calls into multiple printf arguments and assume their evaluation order.

Try it with paper and the lesson

Trace the outer x in int x=4; { int x=8; x=9; }. Then write the third sequential result of the function that uses static n rather than fresh.

Show hint

Mark whether identically spelled names refer to different objects.

Show solution

Only the inner x becomes 9; the outer x remains 4. The third next result is 3. Ending the inner scope is not an assignment restoring the outer value.

Misconception and counterexample

A static variable is a global variable accessible from other files.

A block-scope static name has block scope and no linkage. A file-scope static name has internal linkage. Distinguish their common static storage duration from their different name-access rules.

Check your understanding

Does a block-scope static object disappear when the function ends?

Show answer and reasoning

No.

The static storage duration of this example’s object spans the entire program execution.

Does assignment to the inner x change the outer x?

Show answer and reasoning

Not in this example.

Name hiding makes the names refer to different objects.

Is static ++n safe under concurrent calls?

Show answer and reasoning

It is not guaranteed.

static specifies neither synchronization nor an atomic operation.

Explore further

Use the state invariant n=k after k sequential calls. At k=0, initialization to n=0 establishes it. If k<INT_MAX and there are no other modifications, the next ++n is defined and produces n=k+1, establishing the inductive step. A call after k=INT_MAX is excluded from this proof. This explains why an unbounded mathematical natural-number counter cannot be transferred unconditionally into a finite int program.

Subtopic 4.4

Storage Duration and Linkage

Does a name becoming unusable mean that its object has disappeared?

Preparation and learning goals

Preparation

  • A translation unit is the content of a source file after preprocessing. Multiple translation units can be linked into a program.
  • Draw names, objects, and declarations separately. Two declarations for one object and identically spelled names for different objects are both possible.

Learning goals

  • Classify scope, storage duration, and linkage as three separate axes.
  • Explain the relationship between an external declaration and a definition.
  • Distinguish lifetime risks for allocated and automatic objects.

Ask three separate questions

Scope asks whether a name is usable at this source location; storage duration asks during which period of execution storage is guaranteed for an object; linkage asks whether other declarations designate the same object or function. A local object with no linkage still has a lifetime, and multiple declarations with internal linkage can designate the same target.

C11 has four object storage durations: static, thread, automatic, and allocated. A function is not an object, so do not assign an object storage duration to a file-scope static function. Stack/heap implementation-layout analogies do not replace these four language categories.

Complete the declaration table

Below, g is an object with file scope, external linkage, and static storage duration. hidden has file scope, internal linkage, and static storage duration. In f, local has block scope, no linkage, and automatic storage duration; memo has block scope, no linkage, and static storage duration. The function f itself has external linkage, but the object-storage-duration column does not apply to it.

In this case, extern int g; declares the same target as the preceding g and does not initialize a new value. It is incorrect to say that extern always creates external linkage. It can inherit the linkage of a preceding visible static declaration, so check declaration order and visibility.

int g=2;
static int hidden=3;
extern int g;
void f(void) { int local=4; static int memo=5; (void)local; (void)memo; }

Object lifetime ending and ownership contracts

Allocated storage obtained successfully through malloc is not automatically released when the scope of the local pointer variable referring to it ends. Conversely, once free deallocates it, a remaining pointer name does not give permission to access the target. A later memory unit addresses allocation-failure checks, bounds on size calculations, the precise object to deallocate, and ownership together.

Storing an automatic object’s address elsewhere does not prevent the object’s lifetime from ending at block exit. Later access has undefined behavior; N1570 also specifies that the related pointer value becomes indeterminate at the end of the target’s lifetime. An address that happens to look the same, or data that seems to remain on screen, does not prove validity.

A worked example, step by step

Classify g,hidden,local,memo,f in the example along all three axes and determine how many memo objects exist when f is called twice.

  1. g has file scope, external linkage, and static storage duration. The extern declaration designates the same g.
  2. hidden has file scope, internal linkage, and static storage duration.
  3. local has block scope, no linkage, and automatic storage duration, with an object for each call. memo has block scope, no linkage, and static storage duration.
  4. f is a function with file scope and external linkage, not an object to which the storage-duration classification applies. The two sequential calls use the same single memo object.

This is a paper classification using C11 declaration and lifetime rules; no actual linker symbols or memory layout were measured.

Try it with paper and the lesson

A file-scope static int x=1; is followed by extern int x;. Write x’s linkage and storage duration. Compare it with static int y=2; inside a function.

Show hint

Before interpreting extern, locate any preceding declaration that is visible.

Show solution

The later extern x inherits the internal linkage of the earlier static x, and the object has static storage duration. y has block scope, no linkage, and static storage duration. Names can have different linkage despite sharing static storage duration.

Misconception and counterexample

If a local pointer variable is still alive, its target is alive too.

The pointer object and target have separate lifetimes. If free deallocates the target or the block of an automatic object ends, a remaining pointer name does not justify access to that target.

Check your understanding

Do we assign automatic storage duration to a function?

Show answer and reasoning

No.

This storage-duration classification concerns objects.

Does a visible extern x after a file-scope static x necessarily have external linkage?

Show answer and reasoning

No.

Apply the rule that inherits the preceding declaration’s internal linkage.

Is a malloc target freed merely because a local pointer’s scope ends?

Show answer and reasoning

No.

The lifetime of allocated storage differs from the pointer variable’s automatic storage duration.

Explore further

Consider a module with internal static int total=0; that exposes only a reading function and a range-checking modification function. An external declaration of the name total cannot directly designate that same internally linked object, reducing unintended direct access by name. However, returning its address can allow external code to modify the object, and linkage does not prevent an unchecked function from overflowing. Internal linkage is not a proof of all memory safety or information security: the supplied interface contract must be proved separately.
