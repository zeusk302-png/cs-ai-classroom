소단원 10.1

malloc·calloc·realloc·free

배열 크기를 실행 중에 정하면 저장 공간은 누가 돌려줄까?

준비 개념과 학습 목표

준비 개념

  • 포인터와 배열

  • sizeof와 조건문

학습 목표

  • 할당 크기와 객체 수명을 구별한다.

  • 성공과 실패 경로에서 소유권을 추적한다.

공간이 늘어났다는 사실이 새 원소의 값까지 만들어 줄까?

새 동적 int 배열의 capacity는 3, used는 2이며 초기화한 원소는 [4,9]다. 이 모형에서 sizeof(int)는 4이고 모든 양수 크기 계산은 표현 가능하다고 전제한다. capacity를 6으로 늘리는 realloc 요청은 24바이트다. 성공하면 옛 12바이트에 해당하는 내용이 보존되지만 읽기 가능한 초기화 원소 수는 여전히 2다. 세 번째 칸은 이전에도 초기화하지 않았고 새로 늘어난 칸도 값을 자동 제공하지 않는다. used/capacity/초기화 여부를 각각 기록해야 한다.

realloc의 양수 요청 결과를 tmp에 받는다. 실패하면 원래 블록과 owner/used/capacity를 유지한다. 성공하면 옛 블록의 수명은 끝나므로 옛 포인터를 비교하거나 빌린 포인터를 읽지 않는다. owner를 새 결과로 바꾸고 저장한 정수 인덱스로 빌림을 다시 만든다. 새 주소의 숫자가 같아 보이더라도 옛 포인터 사용을 정당화하지 않는다. calloc의 all-bits-zero는 모든 형식의 의미상 초기화를 대신하지 않는다. 포인터 member는 NULL로, 실수 member는 원하는 값으로 명시적으로 초기화한다.

먼저 확인할 개념
  • 소유권과 빌림의 재지정

    재할당 성공 뒤 옛 빌림을 재사용하지 않는다.

  • 사용 길이와 저장 용량

    capacity와 읽어도 되는 원소 범위를 구별한다.

필요한 만큼 빌리기

동적 할당은 실행 중 정한 크기의 저장 공간을 요청하는 것이다. malloc은 바이트 수를 받아 공간을 제공하지만 내용이 초기화되어 있지 않으므로 읽기 전에 값을 써야 한다. calloc은 원소 수와 크기를 받아 모든 비트를0으로 만든다.

모든 비트0이 모든 타입의 의미상0을 보장하는 것은 아니다. 포인터나 부동소수점 표현의 이식성을 따로 살핀다. 할당 함수는 실패할 수 있으며 반환값NULL을 검사한 뒤에만 유효 객체에 접근한다.

크기를 바꿀 때의 계약

양수 크기의 realloc 성공은 이전 객체 수명을 끝내고 새 객체를 반환한다. 내용은 이전·새 크기 중 작은 범위까지 보존되고 늘어난 부분은 초기화되지 않는다. 주소가 같아 보여도 이전 별칭으로 계속 접근하는 코드를 쓰지 않는다.

실패하면 NULL이 반환되고 이전 객체는 그대로 유지된다. p=realloc(p,...)로 바로 덮어쓰면 실패시 기존 주소를 잃을 수 있다. 임시 포인터로 결과를 받은 뒤 성공시에만 소유 포인터를 갱신한다. 이 단원은0크기 요청을 하지 않는다.

int *tmp = realloc(p, new_count * sizeof *p);
if (tmp != NULL) {
    p = tmp;
}
/* new_count는 양수이며 곱셈 검사를 앞에서 끝냈다고 가정 */

사용이 끝났을 때 반환

free는 할당 시작 주소로 공간을 돌려준다. free(NULL)은 아무 일도 하지 않지만 임의 주소·배열 중간 포인터·이미 해제한 주소를 넘기면 정의되지 않은 동작이다. free가 배열 개수를 받아 각각 호출하는 연산은 아니다.

소유권은 누가 해제할 책임이 있는지에 관한 약속이다. 하나의 할당 블록은 한 책임 경로에서 정확히 한 번 해제한다. 포인터 변수는 객체와 별개이므로 free 후 p=NULL로 바꿔도 다른 별칭의 안전이 자동으로 확보되지 않는다.

표의 성공/실패 행은 서로 다른 경로다. 재할당 성공만으로 used를 6으로 바꾸지 않는다. 세 번째 행에서 capacity 안의 모든 원소를 출력하면 초기화하지 않은 칸을 읽는 잘못이 생긴다. 이론 상태표이며 실제 할당을 수행하지 않았다.

중간 과정을 따라가는 예제

int4바이트 환경에서3개 배열에10,20,30을 쓴 후 양수5개로 realloc한다. 성공/실패에서 크기와 값의 상태를 써라.

  1. 처음 요청은3×4=12바이트이다.

  2. 성공하면5×4=20바이트의 새 객체,처음3값 보존·뒤2값 미초기화이다.

  3. 실패하면 이전12바이트 객체와3값이 유지된다.

성공은20바이트 새 객체,실패는12바이트 기존 객체 유지이다. 뒤2값은 쓰기 전 읽지 않는다.

조건을 바꾸어 비교하기

실패에서도 빌린 관찰은 유지된다

used=2인 시작 상태에서 index=1을 저장하고 옛 원소 1을 빌려 둔다. 재할당이 실패한다.

  1. 옛 블록의 수명은 끝나지 않았고 상태도 그대로다.

  2. 빌림은 실패 경로에서는 기존 계약 안에서 원소 값 9를 관찰할 수 있다.

실패와 성공의 빌림 수명은 다르다.

비교할 점

성공 경로의 수명 종료를 실패 경로에 적용하지 않는다.

비트 영과 형식 초기화

struct Node {int *next; double weight;};의 저장소를 calloc으로 얻었다. 이 API는 next=NULL, weight=1.0을 요구한다.

  1. calloc은 모든 비트를 0으로 만들지만 모든 구현의 NULL 포인터나 double 의미 값을 그 사실만으로 단정하지 않는다.

  2. 할당 성공 뒤 next=NULL, weight=1.0을 형식에 맞게 대입하고 객체를 게시한다.

요구한 의미상 초기화를 명시한다.

비교할 점

int 배열의 영 초기화와 임의 기록의 모든 요구값을 구별한다.

owner=realloc(owner,24) 뒤 NULL이면 실패를 반환한다. 어떤 정보가 사라질 수 있는가?

  2. tmp에 받고 실패면 owner를 보존하며 성공할 때만 새 결과를 커밋한다.

실패 보존을 지키는 임시 포인터가 필요하다.

소단원 10.2

배열 크기와 overflow

큰 원소 수를 곱했는데 요청 크기가 작아지면 무슨 일이 생길까?

준비 개념과 학습 목표

준비 개념

  • 포인터와 배열

  • sizeof와 조건문

학습 목표

  • 할당 크기와 객체 수명을 구별한다.

  • 성공과 실패 경로에서 소유권을 추적한다.

원소 곱만 안전하면 헤더를 더한 크기도 안전할까?

새 포맷은 헤더 7바이트와 원소당 6바이트를 한 블록에 저장한다. 실제 size_t 구현과 별개의 가상 비음수 크기 상한 M=255를 두고 양수 원소 수 n만 허용한다. n*6+7을 먼저 계산해 검사하지 않고, 7<=M 확인 뒤 n<=(M-7)/6인지 정수 나눗셈으로 확인한다. 최대 n은 41이며 41개는 253바이트, 42개는 259바이트라 거부한다. 곱의 안전 조건 n<=255/6만 쓰면 42개를 잘못 통과시킨다.

검사는 덧셈과 곱셈을 수행하기 전에 각 단계를 보호한다. 외부 음수 입력을 size_t로 바꾸기 전에는 부호를 검증한다. 저장 가능한 값으로 바뀌었다는 사실을 사용자 요청의 적합성으로 쓰지 않는다. 실제 C의 정수 승격/형식 폭은 별도로 확인해야 하며 이 작은 상한 모델은 특정 C 형식의 실제 wrap 실행이 아니다. capacity를 두 배로 늘리는 정책도 곱셈 전 상한을 확인하고 사용 길이와 헤더 비용을 함께 고려한다.

먼저 확인할 개념
  • 필요 길이와 저장 용량

    종료 문자나 헤더처럼 추가 공간을 계산에 포함한다.

  • 검사 뒤 결과 커밋

    크기 거부 시 기존 소유 상태를 보존한다.

개수와 바이트 수

n개 원소에 필요한 바이트 수는 n×sizeof *p이다. sizeof p는 포인터 자체 크기이므로 배열 원소 크기와 혼동하지 않는다. sizeof *p는 일반적인 비VLA 원소 타입에서 포인터를 실제 역참조하지 않고 타입 크기를 계산한다.

size_t는 객체 크기를 표현하는 unsigned 정수 타입이다. 표현 한계를 넘는 unsigned 곱셈은 모듈로 줄어들어 의도한 크기보다 작은 값이 될 수 있다. 이 현상을 흔히 할당 크기 overflow라고 부르지만 C의 signed overflow와 규칙이 다르다.

곱하기 전에 비교

곱셈 결과로 검사하면 이미 잘린 값만 볼 수 있다. 양의 원소크기 k에 대해 n>SIZE_MAX/k이면 요청 바이트 수를 표현할 수 없으므로 곱하기 전에 거부한다. 이 단원은 n=0도 별도 거부해0크기 할당의 차이를 피한다.

외부에서 받은 음수 값을 먼저 size_t로 바꾸면 매우 큰 양수로 보일 수 있다. 입력의 문법과 부호·범위를 확인한 뒤 타입 변환과 크기 검사를 수행한다. 통과해도 실제 메모리 자원이 부족할 수 있다.

#include <stdint.h>
#include <stdlib.h>
int *p = NULL;
/* n은 검증된 size_t 값 */
if (n == 0 || n > SIZE_MAX / sizeof *p) {
    /* 입력 크기 거부 */
} else {
    p = malloc(n * sizeof *p);
    /* p != NULL을 확인한 뒤 사용 */
}

경계와 실제 용량

크기 표현 가능성, 할당 성공, 배열 첨자 유효성은 세 가지 다른 검사다. n개 배열의 첨자는0부터n−1까지이며 n은 마지막 다음 위치다. 충분히 할당했어도 p[n]을 원소로 접근하면 범위를 벗어난다.

예제는 정수 승격을 생략한 추상 16비트 unsigned 곱셈 모형이다. 실제 C에서는 작은 정수 타입이 int 등으로 승격될 수 있어 size_t가 16비트라는 사실만으로 곱셈 자체가 16비트 unsigned라고 단정할 수 없다. 실제 구현의 타입과 변환 규칙을 확인하며, sizeof int가 항상 4바이트라고 단정하지 않는다.

소단원 10.3

누수·dangling·double free

포인터를 복사하면 해제 책임도 두 개가 생길까?

준비 개념과 학습 목표

준비 개념

  • 포인터와 배열

  • sizeof와 조건문

학습 목표

  • 할당 크기와 객체 수명을 구별한다.

  • 성공과 실패 경로에서 소유권을 추적한다.

소유자가 바뀌면 블록을 먼저 해제해야 할까?

자체 자원 장부에서 블록 A는 12바이트, B는 20바이트다. 시작 시 p가 A를 소유하고 q는 NULL이다. q=p; p=NULL의 명시적 소유권 전달은 A를 해제하지 않고 책임만 q로 옮긴다. 순차 설계에서 이 두 대입 사이에 관찰자가 없고 이전에 q가 다른 블록을 소유하지 않는다고 전제한다. q를 통해 A를 쓰고 마지막에 한 번 free한다. 소유권 전달을 복사된 포인터 모두의 독립 소유로 해석하면 이중 해제 위험이 생긴다.

p가 A의 유일한 소유자일 때 p=B의 주소로 덮으면 A는 살아 있어도 장부에서 해제 경로를 잃는다. 이때 B를 해제하는 것으로 A의 누수가 해결되지 않는다. 반대로 서비스가 나중에 사용/해제할 수 있는 캐시를 계약상 보유한다는 사실만으로 누수라고 단정하지 않는다. 객체 수명과 책임 경로를 확인해야 한다. free 뒤 옛 빌림의 값을 읽거나 비교하지 않으며 소유자 한 칸을 NULL로 바꿔도 다른 빌림이 자동 갱신되지 않는다.

먼저 확인할 개념
  • 객체 수명과 낡은 별칭

    해제 뒤 비교나 읽기를 하지 않는 경계를 확인한다.

  • 포인터 member의 얕은 복사

    주소 복사와 독립 소유 생성의 차이를 연결한다.

블록과 화살표를 구별하기

포인터 변수는 할당 블록을 가리키는 주소를 담는다. p와q가 같은 블록을 가리키면 새 블록이 두 개 생긴 것이 아니다. 종이에 블록 한 개와 화살표 두 개를 그리면 별칭을 이해하기 쉽다.

동적 메모리 누수는 더 이상 필요 없는 할당을 해제하지 못해 자원이 남는 경우다. 마지막 소유 주소를 다른 값으로 덮어쓰면 나중에 free할 경로를 잃을 수 있다. 필요한 동안 의도적으로 보관하는 저장 공간과 구별한다.

int *p = malloc(2 * sizeof *p);
if (p != NULL) {
    int *q = p;  /* 같은 블록의 별칭 */
    free(p);
    p = NULL;
    /* q는 이제 유효한 객체를 가리키지 않는다 */
}

수명이 끝난 객체 접근

dangling 포인터는 수명이 끝난 객체를 가리키던 포인터다. free 후 q를 역참조해 값을 읽거나 쓰면 정의되지 않은 동작이다. 우연히 전에 쓰던 숫자가 보이는 현상은 언어가 동작을 보장한다는 증거가 아니다.

p=NULL은 p 변수만 바꾼다. q가 저절로 NULL이 되는 것은 아니다. C11에서는 객체 수명이 끝나면 그 객체를 가리키던 포인터 값은 미정(indeterminate)이 된다. q의 값을 출력하거나 비교해 안전을 판단하지 말고, 별칭을 사용하는 구간과 객체 수명을 함께 설계한다. 성공 realloc도 이전 객체 수명을 끝내므로 저장된 내부 포인터를 계속 쓰지 않는다.

해제는 한 번만

double free는 같은 해제된 공간을 다시 해제하려는 오류다. q=p 뒤 free(p),free(q)를 수행하면 두 블록을 정리한 것이 아니다. 중간 원소 포인터도 할당 반환 주소가 아니므로 free에 넘기면 안 된다.

소유 포인터 하나를 정하고 별칭은 빌려 쓰는 관례를 문서화하면 책임을 추적하기 쉽다. 프로그램 종료에서 운영체제가 메모리를 회수할 수 있어도 오래 실행되는 작업의 누수를 방치하는 설계 근거로 쓰지 않는다.

  1. 할당 블록 수명은 free에서 끝난다.

  2. p는 NULL로 바뀐다.

  3. q는 유효한 객체를 가리키지 않는 별칭이다. q를 역참조하거나 다시 해제하면 안 된다.

소단원 10.4

할당 실패와 정리 경로

두 번째 할당이 실패하면 첫 번째 공간은 어떻게 정리할까?

준비 개념과 학습 목표

준비 개념

  • 포인터와 배열

  • sizeof와 조건문

학습 목표

  • 할당 크기와 객체 수명을 구별한다.

  • 성공과 실패 경로에서 소유권을 추적한다.

성공 때도 임시 자원을 모두 지우면 반환 객체는 무엇을 소유할까?

새 builder는 호출자 출력이 비어 있다는 계약 아래 H 8바이트와 D 16바이트를 순서대로 할당한다. H는 D를 가리킬 member를 가지지만 임시 준비 단계에서 builder가 두 블록을 소유한다. D 실패면 H를 정리하고 출력은 빈 상태로 유지한다. 모두 성공하면 초기화한 H/D를 한 소유 결과로 호출자에게 전달한다. 이 성공 경로에서는 두 블록을 해제하지 않는다. 결과 destructor가 D를 먼저, H를 나중에 각각 한 번 해제한다.

base의 준비 함수는 결과 숫자만 반환하여 성공 때도 임시 두 블록을 해제했다. 이번 builder는 동적 객체 자체를 반환하므로 성공 정리 정책이 다르다. 계약이 바뀌면 cleanup 경로의 소유 책임도 바뀐다. 실제 할당 실패를 주입하거나 C를 실행하지 않고 서로 배타적인 상태표를 추적한다. 어떤 경로에서도 초기화 전에 H의 D member를 읽지 않도록 임시 포인터를 NULL로 시작하고 성공한 준비 이후만 member를 게시한다.

먼저 확인할 개념
  • 복수 할당의 책임

    부분 준비와 결과 전달을 구별한다.

  • 실패 시 출력 보존

    빈 출력에 성공 결과만 커밋하는 순서를 연결한다.

실패도 정상적인 분기

malloc은 요청 크기를 표현할 수 있어도 자원 부족으로NULL을 반환할 수 있다. 실패를 확인하지 않고 p[0]을 쓰면 유효한 객체가 없는 곳에 접근한다. 실패시 호출자에게 명확한 오류 상태를 반환한다.

작업 여러 단계에서 자원이 생기면 각 실패 위치마다 이미 얻은 자원을 정리해야 한다. 두 번째 할당 실패가 첫 번째 할당을 자동으로 해제하는 것은 아니다. 획득 성공과 현재 소유 상태를 종이에 표로 적는다.

한 곳에 모은 정리

단순 C 함수에서 포인터를 NULL로 초기화하고 정리 라벨에서 free하는 방식은 여러 실패 경로의 반복을 줄일 수 있다. free(NULL)이 허용되므로 아직 얻지 못한 자원도 같은 정리 경로에 놓기 쉽다.

성공 시 자원 소유권을 호출자에게 넘기는 함수는 여기서 모두 free하는 예제와 다르다. 반환 계약을 정해야 한다. 다음 함수는 임시 작업만 하고 두 할당을 함수 안에서 전부 해제한다. 크기를 상수 양수로 고정하고 2 * sizeof *a와 3 * sizeof *b가 size_t에 표현 가능한 환경을 가정해 곱셈 검사 예제와 구분한다.

#include <stdlib.h>
int prepare(void) {
    int result = -1;
    int *a = NULL;
    int *b = NULL;
    a = malloc(2 * sizeof *a);
    if (a == NULL) goto cleanup;
    b = malloc(3 * sizeof *b);
    if (b == NULL) goto cleanup;
    a[0] = 1;
    b[0] = 2;
    result = 0;
cleanup:
    free(b);
    free(a);
    return result;
}

경로마다 책임 확인

첫 할당 실패에서는 a,b가 NULL이다. 둘째 실패에서는 a만 살아 있고 b는 NULL이다. 성공에서는 둘 다 살아 있다가 정리된다. 각 경로에서 살아 있는 블록을 한 번씩만 해제하는지 검사한다.

goto 자체가 실패를 숨기는 것은 아니지만 임의 점프가 많으면 흐름이 복잡해진다. 여기서는 마지막 정리로만 이동하는 좁은 관례를 사용한다. 파일이나 다른 자원은 각자의 정리 함수·반환 규칙을 사용하며 free를 모든 자원에 쓰지 않는다.

  1. 출력은 이미 수명이 끝난 객체를 가리키게 된다.

  2. 전달한 성공 자원은 builder의 임시 정리 대상에서 제외해야 한다.

초기화하지 않은 member로 실패 정리

H 성공 뒤 D가 실패했다. 아직 쓰지 않은 H->data를 읽어 free하려 한다.

  1. H->data가 초기화되지 않았으므로 그 값을 읽어 정리하지 않는다.

  2. NULL로 시작한 별도 임시 D 또는 명시적으로 초기화한 member를 사용한다.

실패 정리에서도 초기화 전제와 소유 사실을 지킨다.

다른 문제에 적용하기

새 builder의 데이터 블록은 헤더 7바이트와 원소당 6바이트이고 가상 크기 상한은 255다. 양수 n=41과 n=42를 각각 새 빈 출력에서 요청한다. H는 별도 8바이트다. 허용 요청에서 H 성공 후 D 실패 / 둘 다 성공을 각각 추적하라. 성공 결과의 D는 원소 capacity만 확보했으며 아직 used=0이다. 첫 원소를 초기화한 뒤 used=1로 바꾸고 결과를 소멸하는 책임 순서를 적어라. 실제 C/할당 실패 주입은 하지 않는다.

힌트 1

D 전체 크기에 헤더를 넣고 곱/합을 수행하기 전에 상한을 검사한다.

힌트 2

성공 전달과 실패 정리, 공간 확보와 초기화한 사용 길이를 따로 기록한다.

풀이와 답 확인

  1. 최대 원소 수는 (255-7)//6=41이다. n=41은 D 253바이트 요청, n=42는 크기 검사에서 거부한다.

  2. 허용 요청에서 H만 성공하고 D가 실패하면 H 8바이트를 해제하고 빈 출력과 살아 있는 0바이트를 유지한다.

  3. 둘 다 성공하면 8+253=261바이트가 두 블록에 나뉘어 살아 있다. 255 상한은 각 크기 표현에 대한 제한이며 전체 장부 합의 제한이 아니다.

  4. capacity=41이어도 used=0이므로 아직 원소를 읽지 않는다. 첫 원소를 초기화한 뒤 used=1로 커밋한다.

  5. 호출자가 결과를 사용한 뒤 D를 먼저, H를 나중에 각각 한 번 해제한다. 옛 빌림을 읽거나 비교하지 않는다.

n=41 허용, n=42 거부다. D 실패 경로는 최종 0바이트, 성공 반환은 두 블록 합 261바이트와 capacity=41 / used=0이다. 초기화 뒤 used=1이며 결과 destructor는 D 뒤 H를 정리한다.
