소단원 3.1

if·switch·loop

같은 숫자를 만나도 왜 어떤 프로그램은 한 번, 어떤 프로그램은 여러 번 일을 할까?

준비 개념과 학습 목표

준비 개념

  • 조건식은 0이면 거짓이고 0이 아니면 참이다. 정수 비교의 결과는 0 또는 1이다.

  • 상태표에는 현재 변수 값과 다음 실행 문장을 함께 쓴다. i++는 이 예제의 독립 문장에서 i를 1 증가시킨다.

학습 목표

  • 선택문과 반복문의 진입 순서를 구별한다.

  • switch의 시작 위치와 fall-through를 추적한다.

  • 반복 횟수의 경계와 종료 조건을 설명한다.

조건으로 길 선택하기

if는 조건에 따라 문장을 선택한다. else if 사슬은 위에서 처음 참이 된 가지 하나를 선택하므로 조건의 순서도 계약의 일부다. 예를 들어 점수 0…100에서 90 이상을 먼저 검사한 뒤 60 이상을 검사해야 높은 점수가 낮은 등급 가지로 흡수되지 않는다.

중괄호는 여러 문장을 하나의 블록으로 묶는다. else는 문법상 연결 가능한 가장 가까운 if에 붙는다. 들여쓰기는 읽기를 돕지만 결합 규칙을 바꾸지 않으므로 초심자는 각 가지에 중괄호를 쓰고 조건과 행동을 따로 표로 확인하자.

switch는 진입 위치를 정한다

switch의 정수 값과 case 상수는 값에 따라 시작 위치를 정한다. case는 독립적인 if 블록이 아니다. 진입 뒤 break를 만나지 않으면 뒤쪽 문장이 이어진다. 의도한 공유 처리는 주석으로 표시하고, 각 선택을 분리하려면 break를 둔다.

break는 가장 안쪽 switch 또는 반복문을 벗어난다. 따라서 반복문 안의 switch에서 break가 반복문까지 멈춘다고 추측하면 안 된다. default가 없는 switch에서 어떤 case도 맞지 않으면 본체를 실행하지 않고 다음 문장으로 진행한다.

int x=1, y=0;
switch(x) { case 1: y+=2; case 2: y+=3; break; default: y=9; }

반복의 진입과 진행

while은 본체 전에 검사하므로 0회가 가능하다. do…while은 먼저 본체를 수행하므로 정상 진입 시 최소 1회다. for의 순서는 초기화→조건→본체→증감→조건이다. 조건이 참인 동안만 본체를 반복하며 계속 참이라는 사실 자체는 종료 보장이 아니다.

아래 작은 합에서는 i가 0…3을 거쳐 각 증가와 합이 int의 최소 보장 범위 안에 있다. 일반 n의 합을 같은 코드로 확장할 때는 i 증가와 s 누적의 표현 범위를 별도로 검사해야 한다. 종료 논증은 수학의 감소량과 C 연산이 정의된다는 조건을 함께 필요로 한다.

int s=0;
for (int i=0; i<3; ++i) { s+=i; }

중간 과정을 따라가는 예제

x=1인 switch와 i<3인 합의 최종 값을 종이로 추적하라.

  1. switch는 case 1에서 시작하여 y=2가 된다.

  2. break가 아직 없어 case 2의 y+=3을 수행하고 y=5가 된다.

  3. 합의 i=0,1,2에서 s=0,1,3으로 바뀐다.

  4. 증가 뒤 i=3에서 조건이 거짓이므로 본체를 더 수행하지 않는다.

y=5, s=3이다. 예상 상태이며 실제 C 실행 결과는 아니다.

종이와 본문으로 직접 해보기

switch의 x를 2와 7로 바꾸고 합의 조건을 i<0으로 바꿔라.

힌트 보기

시작 case와 검사 시점을 먼저 표시한다.

풀이 보기

x=2면 y=3, x=7이면 default로 y=9다. i=0에서 i<0이 거짓이므로 합은 0이며 본체는 0회다.

오해와 반례

case마다 자동으로 실행이 끝난다.

case 1의 예제는 y=2에서 끝나지 않고 y=5가 된다. 레이블은 시작점이며 break 등의 제어 이동이 끝점을 결정한다.

자기점검

while과 do…while 중 처음 조건이 거짓이어도 본체를 하는 것은?

답과 이유 보기

답과 이유 보기

본체를 건너뛴다.

일치하는 진입 레이블이 없다.

for i=0;i<3;++i의 본체 i 값은?

답과 이유 보기

0,1,2

i=3은 조건 검사에서 탈락한다.

한 단계 더

불변량 s=0+…+(i−1), 0≤i≤3을 검사 직전 상태에서 증명해 보자. 초기 i=0의 빈 합은 0이고 본체의 s+=i와 증가가 다음 상태의 합을 만든다. 종료 i=3에서 0+1+2=3을 얻는다. 이는 표현 범위가 보장된 작은 예제의 전체 정확성 논증이다.

소단원 3.2

제어흐름의 경계

올바른 반복도 마지막 칸에서 실패하는 이유는 무엇일까?

준비 개념과 학습 목표

준비 개념

  • 길이 n의 배열에서 유효 인덱스는 0≤i<n이다. 길이 3의 칸 번호는 0,1,2다.

  • &&는 왼쪽이 거짓이면 오른쪽을 평가하지 않는다. 범위를 검사한 뒤 배열을 읽는 순서는 안전 조건이다.

학습 목표

  • 경계 검사와 접근의 순서를 정한다.

  • continue와 break가 진행에 미치는 영향을 추적한다.

  • 부분 정확성과 종료를 분리한다.

경계는 마지막 값뿐 아니라 순서다

배열을 읽고 나서 i<n인지 검사해도 이미 범위 밖 접근이 발생했을 수 있다. i<n && a[i]!=0처럼 먼저 경계를 확인해야 한다. 여기서 i는 0 이상으로 시작하고 감소하지 않는다는 조건도 필요하다. 음수 i는 i<n만으로 걸러지지 않는다.

a는 적어도 n개의 유효한 int 객체를 가리키고, 0≤n≤3으로 제한한 예제다. 빈 입력 n=0에서는 첫 조건이 거짓이므로 a[0]을 읽지 않는다. 논리 연산의 단락 평가와 배열의 유효 범위가 함께 안전성을 만든다.

int a[3]={4,0,7};
int n=3, i=0;
while(i<n && a[i]!=0) { ++i; }

continue는 증가를 대신하지 않는다

while 안에서 continue는 다음 조건 검사로 이동한다. 본체 끝에 있는 ++i를 건너뛰는 가지가 있으면 i가 그대로여서 같은 원소를 반복할 수 있다. for에서 continue는 증감 식을 거쳐 조건을 검사하므로 두 문법을 같은 그림으로 그리면 틀린다.

break는 현재 반복을 종료하지만 목표 조건을 만족했다는 뜻은 아니다. 값 발견, 오류, 사용자 취소처럼 종료 이유가 다르면 반환값이나 별도 상태로 구분해야 한다. 일찍 끝났다는 관찰을 성공이라고 해석하지 않는다.

정의된 연산과 종료

현재 i 앞에 0이 없다는 불변량은 검색 결과의 정확성을 뒷받침한다. n−i가 매 반복 1씩 감소하고 음수가 되지 않는다면 반복은 유한 번 안에 끝난다. 그러나 ++i가 실행되지 않는 가지에서는 이 감소 논증을 사용할 수 없다.

일반 int의 i<=INT_MAX 조건 아래 ++i를 하는 코드는 끝값에서 signed overflow를 만든다. 이것을 무한 반복이나 음수 순환이라는 특정 출력으로 약속하면 안 된다. 배열 경계와 정수 범위, 진행 여부를 각각 점검해야 한다.

중간 과정을 따라가는 예제

a={4,0,7}, n=3인 검색에서 i와 실제 읽은 칸을 추적하라.

  1. 처음 i=0에서 0<3이 참이고 a[0]=4를 읽는다.

  2. 본체가 i를 1로 증가시킨다.

  3. 1<3은 참이지만 a[1]=0이므로 두 번째 조건이 거짓이다.

  4. 반복 뒤 i=1이며 a[2]는 읽지 않았다.

처음 0의 인덱스는 1이다. n에 도달한 종료와 구별한다.

종이와 본문으로 직접 해보기

a={4,5,7} 및 n=0을 각각 추적하고 while 본체의 ++i를 지운 경우도 설명하라.

힌트 보기

범위 조건이 거짓이면 오른쪽 칸을 읽지 않는다.

풀이 보기

첫 경우 0,1,2를 읽고 i=3에서 멈춘다. n=0이면 아무 칸도 읽지 않는다. 증가를 지우고 n=3, a[0]=4이면 같은 i=0 조건이 계속 참이라 종이 모형에서 진행하지 않는다.

오해와 반례

경계 조건이 들어 있으면 순서는 상관없다.

a[i]!=0 && i<n은 i=n에서 왼쪽 접근부터 시도한다. 정의되지 않은 동작을 일으킬 수 있어 특정 결과를 예측하지 않는다.

자기점검

i=n일 때 i<n && a[i]!=0은 a[i]를 읽는가?

답과 이유 보기

읽지 않는다.

왼쪽이 거짓이므로 단락 평가한다.

while에서 증가 전 continue를 만나면 증가하는가?

답과 이유 보기

해당 본체 끝 증가를 건너뛴다.

continue는 다음 검사로 이동한다.

불변량이 맞으면 반드시 종료하는가?

답과 이유 보기

아니다.

진행과 감소량은 별도 증명이 필요하다.

한 단계 더

검색 계약을 결과 i에 대해 0≤i≤n, i<n이면 a[i]=0, 모든 j<i에서 a[j]≠0으로 적어 보자. i=n은 부재다. 초기·보존·종료를 증명하되 a의 수명, 길이, 정수 범위라는 전제를 계약 밖으로 숨기지 않는다.

소단원 3.3

scanf와 반환값

입력 함수가 끝났다는 사실과 숫자를 얻었다는 사실은 같을까?

준비 개념과 학습 목표

준비 개념

  • &x는 x 객체의 주소이며 scanf의 %d는 int*를 요구한다. printf의 %d는 int 값이므로 두 함수의 인수 계약이 다르다.

  • 입력 스트림은 아직 읽지 않은 문자들의 순서다. 반환값과 저장된 변수, 남은 문자를 세 칸으로 기록하자.

학습 목표

  • 성공한 대입 개수를 확인한다.

  • 일치 실패와 입력 실패를 구별한다.

  • 숫자 변환의 표현 범위 한계를 설명한다.

반환값을 먼저 판단하기

scanf는 요청한 입력이 모두 성공했는지 자동으로 보장하지 않는다. 아래 두 정수에서는 반환값이 2일 때만 두 결과를 새로 얻었다고 판단한다. 1이면 첫 값만 대입되었고 0이면 첫 변환도 일치하지 못했다. 변수 초기화는 실패한 입력을 성공으로 바꾸지 않는다.

첫 변환이 완료되기 전 입력 실패가 발생하면 EOF를 돌려줄 수 있다. EOF는 항상 −1이라는 숫자로 고정하지 말고 매크로와 비교하자. 입력 종료와 오류의 세부 구분은 feof/ferror 같은 스트림 상태 확인이 추가로 필요하다.

int x=-1, y=-1;
int r=scanf("%d %d", &x, &y);
if(r==2) { printf("%d %d\n",x,y); }

부분 소비와 재시도

표현 가능한 입력 12 q에서는 첫 정수 12만 대입되고 두 번째 %d는 q에서 일치하지 않는다. q가 남아 있을 때 같은 %d를 반복하면 다시 실패할 수 있다. 재시도에는 잘못된 레코드를 소비하거나 한 줄 단위로 새로 읽는 정책이 필요하다.

%c는 기본적으로 공백을 건너뛰지 않는다. 숫자 뒤 개행을 그대로 읽을 수 있으므로 " %c"의 선행 공백을 둘지 계약을 정한다. 반대로 입력 형식 끝의 공백은 다음 비공백을 기다릴 수 있어 단순히 개행 하나를 읽는 명령이 아니다.

성공 개수로 막을 수 없는 문제

형식과 포인터 타입이 맞지 않거나 숫자가 대상 타입에 표현되지 않으면 안전한 실패값을 기대할 수 없다. C17의 scanf 정수 변환을 범위 검증용으로 믿지 말자. 아주 큰 정수 입력에서 r만 확인하는 방식은 안전한 입력 파서가 아니다.

문자 배열의 %s에는 널 종료 공간을 뺀 필드 폭이 필요하다. char word[8]이면 %7s처럼 제한하지만 이는 한 단어의 일부만 소비할 수 있고 줄 전체의 문법 검증을 대신하지 않는다. 다음 소단원은 줄 읽기와 변환을 분리한다.

중간 과정을 따라가는 예제

int 표현 범위 안의 문자열 "12 q"가 입력일 때 위 호출의 r,x,y와 남은 문자를 추적하라.

  1. %d가 12를 읽고 x=12로 대입한다.

  2. 형식의 공백이 사이 공백을 건너뛰어 q에서 멈춘다.

  3. 두 번째 %d는 q와 일치하지 않아 y를 대입하지 않는다.

  4. 반환값은 대입 1개를 센 r=1이고 q는 아직 남아 있다.

x=12,y=−1,r=1이며 if(r==2) 본체를 실행하지 않는다. 예상 추적이다.

종이와 본문으로 직접 해보기

입력이 "7 8", "q", 첫 문자 전 즉시 EOF인 경우를 표로 쓰라. 모든 숫자는 int 범위 안이다.

힌트 보기

EOF는 첫 변환 전 입력 실패에만 해당하는 이 사례를 구별한다.

풀이 보기

7 8은 r=2,x=7,y=8. q는 r=0,x=y=−1. 즉시 EOF는 r=EOF,x=y=−1이다. 초기값은 실패를 식별하기 위한 성공 기준이 아니라 관찰 보조다.

오해와 반례

scanf 반환값만 확인하면 어떤 큰 숫자도 안전하게 거절할 수 있다.

대상 int에 표현되지 않는 변환은 정의되지 않은 동작이다. r=0 또는 EOF로 거절될 것이라 예측하지 않는다. 먼저 문자열로 받고 strtol의 범위 보고를 사용한다.

한 단계 더

입력 소비량과 대입 개수는 서로 다르다. %*d는 값을 소비하지만 대입을 억제하며 %n도 성공 대입 개수에 포함되지 않는다. 두 정수 계약의 r==2 규칙을 다른 형식에 기계적으로 옮기지 말고 각 지시자의 계약을 확인하자.

소단원 3.4

fgets·변환함수로 안전한 입력

숫자 12를 찾는 것과 입력 전체가 올바른 숫자인지 확인하는 것은 어떻게 다를까?

준비 개념과 학습 목표

준비 개념

  • C 문자열은 널 문자로 끝나는 char 배열이다. 개행 \n과 문자열 끝 \0은 다른 문자다.

  • strtol은 문자열 앞부분을 long으로 변환하고 end 포인터로 멈춘 위치를 알려준다. long 범위와 업무 범위는 별도로 검사한다.

학습 목표

  • 버퍼와 레코드 길이를 분리한다.

  • endptr·errno·업무 범위를 모두 확인한다.

  • 실패 뒤 데이터 사용을 금지하는 계약을 만든다.

한 줄 읽기의 계약

fgets(buf,32,stdin)는 성공 시 최대 31개 문자를 읽고 널 종료한다. 읽은 개행은 버퍼에 남는다. 반환값이 NULL이면 결과를 숫자로 파싱하지 않는다. 줄이 길면 일부만 읽으므로 성공과 줄 전체 수집을 같은 뜻으로 해석하지 않는다.

이 수업 입력은 C 로캘의 텍스트이며 입력 안의 널 바이트는 허용하지 않는다는 외부 계약을 둔다. buf에 개행이 없으면 더 읽어 끝인지 확인하는 절차가 필요하다. 아래 간단 구현은 개행 없는 마지막 줄도 보수적으로 거절하며, 실제 서비스는 EOF로 끝난 완전한 마지막 줄을 별도 처리할 수 있다.

변환과 검증을 나누기

strtol(buf,&end,10) 전 errno=0을 둔다. end==buf는 변환된 숫자가 없음을 뜻하며 0이라는 반환값만으로 실패와 숫자 0을 구별할 수 없다. errno==ERANGE이면 long 범위를 벗어난 것이다. long 값이 있어도 이 예제의 허용 수량 0…100 밖이면 거절한다.

뒤에 남은 문자는 C 로캘의 공백만 허용한다. 12x는 앞의 12가 변환되어도 전체 계약에 맞지 않는다. isspace에는 (unsigned char)로 변환한 값을 넘겨 음수 char 문제를 피한다. 성공 후에만 작은 범위의 long을 int로 변환하고 사용한다.

실패 상태를 하나의 흐름으로 묶기

아래 완전 프로그램은 한 줄만 읽고 수량을 출력한다. 개행이 버퍼에 있어야 하므로 숫자 외 공백을 포함한 줄 전체 길이가 31문자 이내이고 개행이 있어야 통과한다. 긴 줄의 나머지를 소비하여 재시도하지 않으며 즉시 실패 종료하므로 다른 입력 레코드와 합쳐지지 않는다.

이 정책의 안전은 모든 종류의 입력을 받아들인다는 뜻이 아니다. 예를 들어 EOF로 끝나는 12를 보수적으로 거절한다. 허용 형식은 strtol의 C 로캘 10진 선택 부호와 앞 공백을 포함하므로 +12도 허용한다. 부호를 금지하는 계약이라면 변환 전에 문법을 추가로 검사한다.

#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <ctype.h>
#include <errno.h>
int main(void) {
    char buf[32], *end;
    if(!fgets(buf,sizeof buf,stdin)) return 1;
    if(!strchr(buf,'\n')) return 1;
    errno=0;
    long value=strtol(buf,&end,10);
    if(end==buf || errno==ERANGE) return 1;
    while(isspace((unsigned char)*end)) ++end;
    if(*end!='\0' || value<0 || value>100) return 1;
    printf("%d\n",(int)value);
    return 0;
}

중간 과정을 따라가는 예제

개행이 있는 " 12 \n"을 위 입력 정책으로 추적하라.

  1. fgets가 공백·1·2·공백·개행과 널 종료를 저장하고 성공한다.

  2. 개행 존재 검사를 통과하고 errno를 0으로 둔 뒤 value=12, end는 숫자 뒤 공백을 가리킨다.

  3. 공백과 개행을 건너뛴 end가 널 종료에 도달한다.

  4. ERANGE가 없고 0≤12≤100이므로 int로 변환하여 출력할 수 있다.

조건을 만족하는 실행의 예상 출력은 12와 개행이다. 실제 컴파일하지 않았다.

종이와 본문으로 직접 해보기

"0\n", "12x\n", "101\n", "\n", 개행 없이 EOF로 끝나는 "12"를 분류하라.

힌트 보기

숫자 존재·뒤 문법·업무 범위·레코드 정책을 따로 체크한다.

풀이 보기

0은 허용된다. 12x는 뒤 x 때문에, 101은 업무 범위 때문에, 빈 줄은 end==buf 때문에 거절된다. 마지막 12는 이 구현의 개행 필수 정책 때문에 거절되지만 완전한 숫자 문자열이라는 사실까지 부정하는 것은 아니다.

오해와 반례

strtol이 12를 돌려주면 12x도 올바른 입력이다.

변환은 접두부의 성공이고 전체 문법은 별도다. end에 x가 남아 있으면 허용한 뒤 공백 규칙에 맞지 않는다.

자기점검

strtol 반환 0만으로 실패를 판단할 수 있나?

답과 이유 보기

없다.

문자열 0도 정상 값 0이다.

long에서 int로 줄이기 전 왜 0…100을 검사하나?

답과 이유 보기

업무 범위와 안전한 값 보존을 보장한다.

0…100은 모든 표준 int 범위에 들어간다.

fgets 성공에 개행이 없으면 반드시 EOF인가?

답과 이유 보기

아니다.

버퍼가 먼저 찼거나 마지막 줄이 EOF로 끝났을 수 있다.

한 단계 더

성공 조건을 P=read_success∧newline_present∧digits_present∧no_ERANGE∧tail_space_only∧0≤value≤100으로 쓰자. P의 한 항씩 제거한 반례를 구성하면 각 검사가 필요한 이유가 드러난다. 일반 바이너리 입력에서 내장 널을 검증하려면 문자열 함수만으로는 부족하며 실제 읽은 바이트 수를 관리하는 별도 레코드 리더가 필요하다.
