소단원 2.1

정수형의 범위·부호

정수 1을 더하는데 왜 결과를 숫자 하나로 답할 수 없는 경우가 있을까?

준비 개념과 학습 목표

준비 개념

  • 타입은 허용 값과 연산 규칙의 묶음이다. 수학의 정수는 크기 제한이 없지만 C 객체의 저장 공간은 유한하다.
  • 범위 [a,b]는 양 끝을 포함한다. 0부터 255까지는 256개의 서로 다른 값이다.
  • C 첫 단원의 소스→번역→실행 구분: 번역 성공은 실행 중 범위 조건을 보장하지 않는다.

학습 목표

  • 정수형의 실제 범위를 limits.h로 확인하는 이유를 설명한다.
  • unsigned 연산과 signed overflow를 구분한다.
  • 덧셈 전에 범위를 검사하는 조건을 유도한다.

크기는 이름만으로 고정되지 않는다

C17의 char, short, int, long, long long은 모든 구현에서 같은 비트 폭을 약속하지 않는다. sizeof(char)=1이며 한 C byte의 비트 수 CHAR_BIT는 최소 8이다. sizeof(int)=4를 모든 컴퓨터의 법칙으로 쓰면 이식성을 잃는다. signed/unsigned 대응 타입과 정수 변환 순위를 구분한다.

limits.h의 INT_MIN, INT_MAX, UINT_MAX, CHAR_BIT를 읽으면 선택 구현의 한계를 알 수 있다. 최소 보장 int 범위는 −32767…32767이고 실제 범위가 더 넓을 수 있다. 아래 별도 수치 모형은 int가 −2147483648…2147483647, unsigned int가 0…4294967295인 구현을 가정한다. 실제 측정값이 아니다.

unsigned의 순환과 signed의 미정의동작

unsigned int 연산은 수학적 결과를 UINT_MAX+1로 나눈 나머지에 대응한다. UINT_MAX+1u는 0이며 0u−1u는 UINT_MAX다. 이는 음수가 저장된다는 뜻이 아니라 해당 unsigned 값으로 해석된다는 뜻이다. 단, unsigned char끼리의 식은 먼저 int로 승격될 수 있어 작은 타입의 저장 범위와 연산 범위를 구분해야 한다.

signed int 식 INT_MAX+1의 수학적 결과는 int로 표현되지 않는다. C17에서는 미정의동작(UB)이므로 음수로 돌아간다고 정하지 않는다. 구현이 우연히 그렇게 보이거나 경고 없이 번역되어도 언어 계약은 없다. INT_MIN을 int로 부호 반전하는 경우도 양수가 표현되지 않으면 같은 문제다.

먼저 검사해야 검사도 정의된다

0≤a≤INT_MAX,0≤b≤INT_MAX인 두 int를 안전하게 더하려면 b≤INT_MAX−a를 먼저 검사한다. 뺄셈 INT_MAX−a는 가정 아래 표현 가능하다. 통과하면 a+b≤INT_MAX라 합을 계산할 수 있다. 실패하면 합을 계산하지 않고 오류를 전달한다.

a+b>INT_MAX로 검사하면 이미 위험한 덧셈을 수행한 뒤다. unsigned의 정의된 순환도 금액·길이 계약에는 오류일 수 있다. 언어가 결과를 정의하는 것과 응용이 결과를 허용하는 것은 별도 질문이다.

중간 과정을 따라가는 예제

int의 위 수치 모형에서 a=2147483640,b=8을 더하려 한다. 별도로 unsigned int u=UINT_MAX; u=u+1u;를 추적하라.

  1. INT_MAX−a=2147483647−2147483640=7을 계산한다.
  2. b=8은 7보다 커서 실패를 반환하고 signed 합은 계산하지 않는다. 수학적 합 2147483648은 자료형 밖이다.
  3. unsigned 식은 4294967296 mod 4294967296=0이어서 u=0이다.

signed 안전 검사 실패; unsigned u의 예상값은 0. signed 위험식에는 출력값을 배정하지 않는다.

종이와 본문으로 직접 해보기

같은 int 모형에서 a=2147483640,b=7 및 b=0의 허용 여부를 구하라. INT_MAX+1이 음수로 보였다는 한 번의 관측으로 C17 규칙을 정할 수 있는지도 답하라.

힌트 보기

허용 조건 b≤INT_MAX−a를 사용한다. 수학적 합과 C 실행 계약을 구분한다.

풀이 보기

두 b 모두 7 이하라 통과한다. 합은 각각 2147483647과 2147483640. 위험식의 우연한 관측은 UB의 언어 보장이 아니다.

오해와 반례

모든 정수형은 범위를 넘으면 자동으로 순환한다.

unsigned int의 순환과 signed int의 범위 밖 산술은 다르다. INT_MAX+1은 UB이며 허용 결과 목록을 만드는 문제가 아니다.

자기점검

sizeof(char)=1이면 한 byte는 항상 8 bit인가?

답과 이유 보기

아니다.

CHAR_BIT는 최소 8이며 구현값을 확인한다.

0u−1u의 타입과 값은?

답과 이유 보기

unsigned int, UINT_MAX.

두 피연산자 모두 unsigned int라 해당 범위의 모듈러 연산이다.

signed 합을 먼저 계산해 음수 여부로 넘침을 검사해도 되는가?

답과 이유 보기

안 된다.

합 계산 자체가 UB일 수 있어 계산 전 범위 검사가 필요하다.

한 단계 더

음수까지 허용하면 b>0일 때 a>INT_MAX−b, b<0일 때 a<INT_MIN−b를 오류 조건으로 나눈다. 각 가지의 뺄셈은 int 범위에 있다. 모든 부호 조합을 한 식으로 뭉치기보다 조건의 정의 가능성부터 증명하라. 다음 배열 길이 단원에서는 signed 값의 음수 검사 후에 unsigned 크기 타입으로 변환한다.

소단원 2.2

실수형·문자형

화면의 0.1과 문자 1은 같은 숫자로 저장될까?

준비 개념과 학습 목표

준비 개념

  • 분수 1/10은 십진수로 0.1이다. 진법이 바뀌면 유한 표현 여부가 바뀔 수 있다.
  • 작은따옴표 문자 상수와 큰따옴표 문자열은 다른 구문이다. printf는 지정한 형식으로 값을 표시한다.
  • 표현된 값·연산 결과·화면에 반올림한 문자열을 구분한다.

학습 목표

  • 실수 수학 모형과 부동소수점 값을 구분한다.
  • 문자형·문자 상수·문자열의 역할을 설명한다.
  • 정수 나눗셈과 실수 나눗셈의 변환 시점을 추적한다.

실수의 일부를 유한 공간에 표현한다

float,double,long double은 실수의 유한 표현과 근사 연산을 제공한다. C17이 모든 구현에 IEEE 754 binary32/binary64를 요구하지는 않는다. float.h의 FLT_RADIX와 정밀도·범위가 실제 계약을 설명한다. 0.1은 double 상수, 0.1f는 float 상수다. long double이 언제나 double보다 엄격히 더 정밀한 것도 아니다.

이진 유한 소수는 분모가 2의 거듭제곱인 유리수다. 1/10의 기약 분모에는 5가 있어 이진 유한 자리로 정확히 표현되지 않는다. 흔한 IEEE binary64 기본 반올림 환경에서는 0.1+0.2와 0.3이 서로 다른 근삿값일 수 있다. 특정 출력의 마지막 자릿수를 모든 C17 구현에 고정하지 않는다.

나눗셈 전에 피연산자의 타입을 고른다

int a=5,b=2; double x=a/b;에서는 a/b가 정수 나눗셈이므로 먼저 2를 얻고 이를 2.0으로 변환한다. double y=(double)a/b;는 a를 먼저 double로 만들어 b도 공통 실수형으로 변환하므로 2.5를 얻는다. 아래 2.5·3.5를 정확한 결과로 쓰는 실수 나눗셈 예제는 FLT_RADIX=2이고 해당 작은 값을 정확히 표현하며 이 나눗셈을 올바르게 반올림하는 구현을 가정한다. C17 전체가 이 정확도나 이진 진법을 강제하는 것은 아니다.

정수 나눗셈은 표현 가능한 몫에서 0 방향으로 소수 부분을 버린다. −5/2는 −2다. 분모 0과 signed 최솟값/−1처럼 몫을 표현할 수 없는 경우에는 UB가 있으므로 “항상 정수”라는 말만으로 실행 안전성을 결론 내리지 않는다.

문자 코드는 수학적 숫자와 다르다

char는 한 byte 정수형이다. plain char의 부호는 구현이 정한다. C의 보통 문자 상수 '1'은 int 타입이며 실행 문자 집합의 코드값을 뜻한다. 문자열 "1"은 문자 '1'과 종료 문자 '\0'을 담은 배열이다. 같은 모양이라도 int 1, 문자 코드, 문자배열은 다르다.

기본 실행 문자 집합의 '0'…'9'는 연속이라 숫자 문자 c가 이 범위인지 먼저 확인하면 c−'0'으로 값 0…9를 얻는다. '1'의 절대 코드값을 49로 고정하려면 ASCII라는 추가 가정이 필요하다. UTF-8의 한국어 한 글자는 여러 byte일 수 있으므로 char 하나를 모든 인간 언어의 문자 하나와 동일시하지 않는다.

중간 과정을 따라가는 예제

위의 이진 표현·올바른 반올림 가정에서 int a=5,b=2; double x=a/b,y=(double)a/b; char c='7'; int digit=c−'0';를 종이로 추적하라.

  1. a/b는 두 int의 나눗셈이라 2다. 저장 변환 후 x=2.0이다.
  2. y는 첫 피연산자가 double이라 5.0/2.0=2.5다.
  3. c가 '0'…'9' 범위 안이고 연속 코드 차이 7이라 digit=7이다.

x=2.0,y=2.5,digit=7이 예상된다. c 자체는 숫자 7과 같은 의미의 값이 아니다.

종이와 본문으로 직접 해보기

같은 실수 연산 가정에서 int a=7,b=2에서 double x=(double)(a/b)와 y=(double)a/b를 비교하라. c='9'의 digit 값도 구하라.

힌트 보기

cast가 괄호 밖이면 정수 나눗셈 뒤다. 표시 모양보다 변환 시점을 읽는다.

풀이 보기

x는 7/2=3 뒤 변환되어 3.0, y는 7.0/2.0=3.5다. 유효 숫자 문자 '9'−'0'=9이다.

오해와 반례

실수 변수에 저장하면 원래 정수 나눗셈의 버린 부분이 되살아난다.

5/2를 수행한 뒤 double로 바꾸면 이미 몫 2이다. 계산 전에 피연산자를 바꿔야 2.5를 얻는다. 부동소수점도 임의의 실수 정확성을 보장하지 않는다.

자기점검

C의 보통 문자 상수 'A'의 타입은?

답과 이유 보기

int다.

char 객체와 문자 상수의 타입을 구분한다. C++의 보통 문자 상수 규칙과도 다르다.

−5/2의 정의된 정수 몫은?

답과 이유 보기

−2다.

분모가 0 아니고 몫이 표현 가능하며 0 방향 절단이다.

C17의 double은 반드시 binary64인가?

답과 이유 보기

아니다.

구현의 radix/정밀도/범위를 확인해야 한다.

한 단계 더

계산 오차 허용을 |x−y|≤atol+rtol·|y|처럼 모델링하면 기준값 y와 단위, 유한값 조건 및 허용오차의 근거를 정해야 한다. 가격이 정수 원 단위라면 정수 단위 표현을 고려하되 범위 초과를 함께 검사한다. 근사 비교는 원자료의 입력 형식·범위를 검증하는 절차를 대신하지 않는다.

소단원 2.3

형변환과 정수승격

작은 unsigned 값 두 개를 빼면 왜 음수가 나올 수도 있을까?

준비 개념과 학습 목표

준비 개념

  • 식의 타입은 저장할 변수의 타입과 다를 수 있다. 대입은 오른쪽 계산 후 왼쪽 타입으로 변환한다.
  • 타입의 범위가 값을 포함하면 값은 그대로 옮겨질 수 있다. 범위 밖에서는 별도 규칙이 필요하다.
  • 이 단원 예제의 8-bit unsigned char와 32-bit int는 선택한 가상 구현 조건이다.

학습 목표

  • 정수승격과 보통 산술 변환을 단계별로 설명한다.
  • signed/unsigned 혼합 비교를 추적한다.
  • 연산 전 cast와 연산 후 cast의 차이를 찾는다.

작은 타입을 먼저 올린다

정수승격은 보통 char/short 등 int 이하 변환 순위의 해당 정수형을 int 또는 unsigned int로 바꾸는 과정이다. int가 원래 타입의 모든 값을 담으면 int, 그렇지 않으면 unsigned int로 바꾼다. 값과 부호를 보존한다. 저장 변수의 작은 폭이 식의 계산 폭을 결정하지 않는다.

8-bit unsigned char가 0…255이고 int가 이를 모두 담는 모형에서 unsigned char a=3,b=5; a−b는 두 값을 int로 올린 뒤 −2를 계산한다. unsigned char z=a−b;에 저장할 때는 다시 256을 법으로 변환되어 254다. signed overflow가 일어난 예제가 아니다.

공통 타입의 선택이 비교에도 영향을 준다

보통 산술 변환은 먼저 승격하고 두 정수의 공통 타입을 정한다. 같은 부호면 높은 순위를 고른다. 혼합 부호에서 unsigned의 순위가 signed 이상이면 unsigned로 변환한다. signed 순위가 더 높고 unsigned 모든 값을 담으면 signed로, 못 담으면 그 signed에 대응하는 unsigned로 변환한다.

int i=−1; unsigned int u=1; i<u는 같은 순위의 혼합 비교다. i는 UINT_MAX로 변환되어 UINT_MAX<1은 거짓이다. 원래 수학 정수 −1<1의 의미와 다르다. 음수 검사 후 크기 타입으로 옮기는 계약을 사용하면 이런 놀라움을 줄인다.

cast는 범위 검사도 시간 여행도 아니다

(double)(a/b)는 정수 몫을 만든 뒤 변환한다. (double)a/b는 계산의 공통 타입을 바꾼다. 마찬가지로 큰 signed 곱을 계산한 뒤 long long으로 cast해도 이미 UB이면 복구하지 못한다. 먼저 넓은 피연산자로 바꾸고 새 타입 범위를 증명한다.

실수→정수 변환은 유한값의 소수 부분을 0 방향으로 버린다. 정수 부분이 대상 타입에 표현되지 않으면 UB다. signed 정수→더 작은 signed 변환에서 표현 못 하는 결과는 C17에서 구현 정의 결과 또는 구현 정의 신호이며 signed 산술 overflow와 구분한다. cast라는 글자를 쓰는 것만으로 모든 변환이 안전해지지 않는다.

중간 과정을 따라가는 예제

8-bit unsigned char와 충분한 int 모형에서 a=3,b=5,z=a−b의 각 타입/값과 int i=−1; unsigned int u=1;의 i<u를 구하라.

  1. a,b는 각각 unsigned char 저장값 3,5이다. 뺄셈 전에 int로 승격된다.
  2. int 식 결과 −2를 z에 저장하며 −2 mod 256=254다.
  3. 비교에서 i는 unsigned int UINT_MAX로 바뀐다. UINT_MAX<1은 거짓이므로 관계식 int 값은 0이다.

뺄셈식 int −2, 저장 z=254, 비교 i<u의 예상값 0.

종이와 본문으로 직접 해보기

풀이 보기

오해와 반례

unsigned라는 이름이 붙은 변수는 모든 식에서 unsigned로 계산된다.

unsigned char의 모든 값을 int가 담으면 int로 승격된다. 3−5는 이 모형에서 int −2다. 단, unsigned int끼리 식은 unsigned int이고 구현 범위가 다른 작은 타입의 승격도 다시 판단해야 한다.

연산자 우선순위·부작용

괄호를 더 쓰면 값을 읽고 바꾸는 순서도 원하는 대로 정해질까?

준비 개념과 학습 목표

준비 개념

  • 우선순위는 식을 어떤 트리로 묶는지 정한다. 평가 순서는 그 트리를 실행할 때 어느 계산/변경이 먼저인지 정한다.
  • 부작용은 변수 저장값 변화나 입출력처럼 계산 밖에 관찰되는 변화다. i++는 옛값을 만들고 i를 증가시킨다.
  • 이 예제는 C17의 내장 연산자 규칙이다. C++20이나 연산자 재정의 규칙을 가져오지 않는다.

학습 목표

  • 구문 묶음과 sequenced before를 구분한다.
  • 동일 객체의 unsequenced 변경·읽기에 따른 UB를 찾는다.
  • 짧은 회로와 별도 문장으로 정의된 추적을 만든다.

우선순위는 트리를 만든다

2+3*4는 2+(3*4)로 묶여 14다. (2+3)*4는 다른 트리라 20이다. 이 순수 상수 식에서 실행 순서는 값에 영향을 주지 않지만, f()+g()*h()의 곱셈 우선순위가 f,g,h의 호출 순서를 왼쪽부터 보장하지는 않는다.

결합 방향도 구문 규칙이다. a−b−c는 (a−b)−c이다. 괄호로 덧셈 양쪽을 묶어도 보통 덧셈의 두 피연산자를 순서대로 평가하게 바꾸지는 않는다. 순서가 필요한 부작용은 문장과 계약으로 드러낸다.

동일 객체의 충돌에는 허용 결과가 없다

sequenced before는 한 평가/부작용이 다른 것보다 먼저 완료된다는 관계다. C17에서 i++ + i++처럼 같은 scalar 객체를 변경하는 두 부작용이 서로 unsequenced이면 UB다. i++ + i도 변경과 같은 값 읽기가 unsequenced여서 UB다. 괄호 (i++)+(i++)로 고쳐도 같은 문제다.

서로 다른 객체의 x++ + y++는 값이 표현 가능하다는 가정 아래 이 충돌 규칙의 UB가 아니다. 각 피연산자 평가 순서가 지정되지 않아도 옛 x/y의 합과 각각 한 증가가 정해진다. unspecified order와 UB를 같은 단어로 취급하면 정의된 코드도 잘못 분류한다.

순서를 요구할 때는 문장을 나눈다

int i=1; int a=i++; int b=i++; int sum=a+b;는 각 full expression을 끝내고 다음 문장을 시작하므로 a=1,i=2,b=2,i=3,sum=3으로 추적된다. 모든 합/증가는 여기의 작은 int 범위 안이다. 출력은 마지막 상태를 읽는 별도 문장으로 한다.

내장 &&와 ||는 왼쪽을 먼저 평가하고 결과에 따라 오른쪽을 생략한다. int n=0; int ok=(n!=0 && 10/n>1);은 오른쪽을 실행하지 않아 ok=0이다. 비트 연산자 &로 바꾸면 두 피연산자를 평가하여 0으로 나누는 UB를 피하지 못한다. 함수 인수 사이의 쉼표는 comma 연산자의 순서 보장과 다르다.

중간 과정을 따라가는 예제

int i=1; int a=i++; int b=i++; int sum=a+b;와 n=0의 (n!=0 && 10/n>1)을 추적하라. i++ + i++에는 숫자 출력 대신 분류를 붙여라.

  1. 첫 문장 a에 옛 1을 저장하고 i는 2가 된다.
  2. 다음 문장 b에 옛 2를 저장하고 i는 3이 된다. 합은 3이다.
  3. n!=0이 거짓이므로 나눗셈을 실행하지 않고 논리식 int 결과 0이다.
  4. i++ + i++는 같은 객체의 unsequenced 두 변경으로 UB이며 예측 출력 목록을 적지 않는다.

정의된 문장 분리는 a=1,b=2,i=3,sum=3; 짧은 회로 값 0. 위험식은 UB.

종이와 본문으로 직접 해보기

i=2에서 a=i++; b=i++; sum=a+b;를 종이로 추적하라. x=2,y=4의 x++ + y++와 (i++)+(i++)를 각각 분류하라.

힌트 보기

문장의 경계와 동일 객체인지부터 본다. 단순 괄호는 sequencing 관계를 만들지 않는다.

풀이 보기

오해와 반례

우선순위나 괄호가 있으면 왼쪽부터 모든 부작용을 수행한다.

f()+g()의 함수 호출 순서는 보통 왼쪽 우선으로 지정되지 않는다. (i++)+(i++) 역시 UB다. 별도 full expression이나 내장 &&/||의 실제 순서 규칙을 사용해야 한다.

답과 이유 보기

답과 이유 보기

답과 이유 보기

아니다.
