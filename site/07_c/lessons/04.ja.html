小節 4.1

プロトタイプと呼び出し

関数の本体を後に置いても、その前から安全に呼び出すには何を知らせる必要があるだろう？

準備する概念と学習目標

準備する概念

  • 宣言は名前と型を示し、定義は関数の本体を提供する。intは整数型で、セミコロンは宣言の終わりを示す。
  • 実引数は呼び出しの括弧内に書く式で、仮引数は関数が受け取るローカルな名前である。2+3は、この単元で扱うすべてのC実装でintに表現できる小さな値である。

学習目標

  • プロトタイプに戻り値の型と仮引数の型を示す。
  • C11の(void)と空の()による宣言を区別する。
  • 型の検査と意味上の契約の違いを説明する。

呼び出しより前に示す型の約束

int add(int a, int b);は、二つのintを受け取りintを返す関数のプロトタイプである。ここでのa,bという名前は説明を助けるもので、呼び出し側の名前と同じでなくてもよい。本体を後に置いても、呼び出す位置でこの宣言が見えていれば型情報を利用できる。

以下は標準ライブラリ以外に依存しない完全なソースである。addの定義も宣言と互換でなければならない。宣言が存在することと、定義が実際のプログラムに含まれることは別なので、別ファイルに移す場合はリンク段階で定義も提供する必要がある。

#include <stdio.h>
int add(int a, int b);
int main(void) { int r=add(2,3); printf("%d\n",r); return 0; }
int add(int a, int b) { return a+b; }

実引数の変換と検査の範囲

プロトタイプが見える呼び出しでは、実引数の個数と型の許される関係に制約があり、各実引数の値は対応する仮引数の型へ代入する場合と同様に変換される。double値をintの実引数として渡しても、必ず構文エラーになるわけではない。有限な2.75をintに変換すると2だが、整数部分が変換先の範囲外なら、安全な呼び出しとみなせない。

型情報だけでは、a+bがintの範囲内であることや、ポインタが生存中のオブジェクトを指すことまでは証明できない。addの意味上の契約は、二つの入力とその数学的な和がintで表現可能であることだ。制約違反には診断が要求されるが、すべてのコンパイラが必ず翻訳を拒否すると一般化してはいけない。

版と評価順序を固定する

この単元はC11を扱う。int ping(void);は仮引数がないことを示すプロトタイプである。一方、定義ではないint ping();という宣言の空の括弧は、仮引数の個数と型の情報を提供しない。C++やC23の空の括弧の規則を、この説明に混ぜない。

関数呼び出しの実引数は本体に入る前に評価されるが、左から順に評価される保証はない。順序が必要な変更は独立した文で先に行い、その結果を実引数として渡そう。同じスカラーを順序付けられていない実引数の式で複数回変更するコードは、この単元の出力例には使わない。

途中の過程をたどる例題

完全なaddのソースで、mainのrと予想される標準出力を追跡しよう。

  1. mainに入った後、add宣言の二つのintと、呼び出しの実引数2,3が対応する。
  2. 仮引数a=2,b=3を持つ関数呼び出しが始まる。
  3. a+b=5はintの範囲内なので、return 5が呼び出し式の値となる。
  4. mainのr=5となり、printfの%dへint値5が渡される。

予想出力は5と改行である。実際にコンパイル・実行した記録はない。

紙と本文で試してみよう

int f(void);とint g();を紙に書き、C11で引数なしという呼び出し契約を明示する宣言はどちらか印を付けよう。add(4,5)も追跡しよう。

ヒントを見る

定義ではなく宣言を読んでいることを忘れないようにしよう。

解答を見る

fは仮引数なし、gは情報なしである。addの仮引数は4,5で、和は9である。gがどんな実引数でも安全に受け取るという結論にはならない。

よくある誤解と反例

プロトタイプがあれば、誤った入力はすべて自動的に遮断される。

型が合うadd(INT_MAX,1)でも、数学的な和がintの範囲を超えると符号付き整数のオーバーフローによる未定義動作になる。型の検査と値の事前条件を両方確認する必要がある。

理解を確かめる

プロトタイプの仮引数名は定義の名前と同じでなければならないか？

答えと理由を見る

いいえ。

対応する型や個数などの互換性が重要であり、名前は呼び出し契約の型の一部ではない。

C11のint f();という宣言は仮引数なしを意味するか？

答えと理由を見る

情報を提供しない。

引数なしのプロトタイプはint f(void);と明示する。

add(2,3)が5を返すことは、型の検査だけで証明できるか？

答えと理由を見る

いいえ。

定義の演算と表現可能な範囲まで確認して初めて、意味上の結果を得られる。

もう一歩先へ

二つの実引数に対応する仮引数の名前をx,yに変えても結果が保たれる理由を説明しよう。各仮引数の使用を一貫して置き換え、ほかの名前と衝突しなければ、a+bとx+yは同じ渡された値の和である。一方、本体をreturn a-bに変えると、型は同じでもaddの和の契約を破る。関数の型と仕様が異なる層であることを示す反例だ。

小節 4.2

値の受け渡しと戻り値

関数の中で仮引数を変えると、呼び出し側の変数も変わるだろうか？

準備する概念と学習目標

準備する概念

  • 変数は、値を保持するオブジェクトに付けた名前である。代入は右側の値を左側のオブジェクトに格納する。
  • &xはxを指すポインタを作り、*pはpが指すオブジェクトを使う。間接参照には、有効で生存中の適切なオブジェクトが必要である。

学習目標

  • 値のコピーと、指し示すオブジェクトの変更を区別する。
  • returnの結果と出力の役割を区別する。
  • 返すポインタに必要な生存期間の条件を説明する。

別々の仮引数オブジェクト

Cの実引数の受け渡しは値渡しである。intを関数に渡すと、その値で仮引数を初期化する。仮引数に代入しても、呼び出し側のintオブジェクトには代入しない。以下のbumpではnとxは別々のオブジェクトであり、n=6とreturn 6は異なる動作である。

戻り値を使わずbump(x);だけを呼び出すと、xはそのままである。returnの式の値が呼び出し式へ渡され、その値を呼び出し側がyに格納して初めてyができる。printfは出力という副作用を行うだけであり、呼び出し側のxを関数の戻り値に置き換える文ではない。

int bump(int n) { n=n+1; return n; }

ポインタの値もコピーされる

ポインタの受け渡しも値渡しだが、コピーしたアドレスを通じて同じ対象オブジェクトを変更できる。set7でp=&xとなる場合、呼び出しの間ずっと生存し変更可能なint xを指しているという事前条件が必要である。NULL、生存期間が終わったオブジェクトのアドレス、不適切な型のアドレスを間接参照する使い方は契約の範囲外である。

関数内でpを別のアドレスに変えることと、*pを変更することは異なる。前者はローカルなポインタの値の変更であり、後者は対象オブジェクトの変更である。配列の形をした仮引数宣言もポインタ型へ調整されるので、配列全体と長さが自動的にコピーされると推測しない。

void set7(int *p) { *p=7; }

戻り値と生存中の対象

int値を返せば、ローカルな名前を使える範囲が終わっても呼び出し側はその値を使える。しかし、ローカルな自動オブジェクトのアドレスを返しても、そのオブジェクトの生存期間は延長されない。生存期間の終わった対象へのアクセスには、固定された出力はない。

構造体を値渡ししても、ポインタフィールドが指す対象まで深いコピーをするわけではない。また、void以外を返す関数は、使われる結果を正常に戻るすべての経路で提供する必要がある。この単元では、mainの末尾到達に関する特別な規則を一般の関数へ拡大しない。

途中の過程をたどる例題

x=5からy=bump(x)を行い、set7(&x)を行った後のx,yを追跡しよう。

  1. bumpに入ると、ローカルなnへxの値5がコピーされる。
  2. n=6になるが、呼び出し側のxは5のままである。
  3. return 6を受け取り、y=6を格納する。
  4. set7のpは&xの値を受け取り*p=7を行うので、x=7になる。

予想される状態はx=7,y=6である。アドレスの数値や実際の実行結果は測定していない。

紙と本文で試してみよう

呼び出し側のx=3を描き、仮の関数void change(int *p)へ&xを渡したとしよう。関数のローカルな仮引数pは、最初はxを指している。関数内でint z=9; p=&z;だけを行う場合と、*p=9;だけを行う場合のxを比べよう。二つの場合は別々に開始する。

ヒントを見る

ローカルなポインタの箱と、対象xの箱を分けよう。

解答を見る

p=&zだけならx=3である。*p=9だけならx=9である。最初の場合、関数終了後にzを指すポインタを返して使用してはいけない。

よくある誤解と反例

アドレスを渡すので、Cは参照渡しの言語である。

コピーされる値がアドレスであるだけだ。ローカルなp自体へ再代入しても、呼び出し側のポインタオブジェクトは変わらない。そのポインタオブジェクトを変えるには、適切なポインタへのポインタの契約などが必要になる。

理解を確かめる

bump(x)の戻り値を捨てるとxは増えるか？

答えと理由を見る

いいえ。

nの変更は、別の仮引数オブジェクトで起こる。

set7(NULL)は安全か？

答えと理由を見る

いいえ。

NULLを間接参照しないための検査がなく、有効なint対象という事前条件も満たさない。

ローカルなintのアドレスを返すと生存期間が延長されるか？

答えと理由を見る

いいえ。

アドレス値を返すことと、対象オブジェクトの生存期間は別の条件である。

もう一歩先へ

交換関数void swap(int *a,int *b)を設計しよう：int t=*a; *a=*b; *b=t;。二つのポインタが呼び出し全体を通じて生存中で変更可能なintを指すなら、異なる対象の場合、元のA,BはB,Aになる。同じ対象を指す場合、tはその値であり、二つの代入後も元の値なので、やはり交換の関係を満たす。NULLや生存期間の終わった対象は、この証明の前提外である。呼び出し側の変数名ではなく、二つの対象の値を交換している。

小節 4.3

ローカル・グローバル・static

関数を二度呼ぶと、何が新しく始まり、何が続くだろう？

準備する概念と学習目標

準備する概念

  • ブロックは{ }の間の領域であり、内側の宣言が同じ名前の外側の宣言を隠す場合がある。
  • 関数呼び出しが別々の文にあるときは、前の呼び出しを終えてから次へ進む。staticは書かれた位置に応じて解釈する必要がある。

学習目標

  • ローカルな名前とファイルスコープの名前を区別する。
  • ブロック内のstaticオブジェクトの状態保持を追跡する。
  • 再入可能性と同時呼び出しの限界を説明する。

ローカルという言葉はスコープを表す

よくグローバル変数と呼ばれる、ファイルスコープのオブジェクト名は、宣言後から翻訳単位の終わりまで使える。関数内の通常のローカル変数名は、そのブロック内で使う。内側のxが外側のxを隠しても、外側のオブジェクトを削除したり、その値をコピーして上書きしたりするわけではない。

ローカルという言葉だけで生存期間を判断してはいけない。ブロック内のstatic変数もローカルな名前だが、オブジェクトは呼び出しのたびに新しく始まるわけではない。スコープはソース内で名前を使う領域であり、生存期間は実行中にオブジェクトが存在する期間である。

二種類のカウンタ

以下のnextは、ブロック内のstatic n=0という一つのオブジェクトを使い続ける。最初の二回の呼び出しは1,2を返す。freshの自動オブジェクトnは各呼び出しの初期化で0を格納し、二回とも1を返す。呼び出し回数を制限し、intの増加が表現可能な範囲を超えないと仮定する。

C11では、静的記憶域期間のオブジェクトはプログラム開始前に一度初期化される。このブロックstaticの初期化を、C++の初回進入時の動的初期化やJavaのクラス初期化と同じ規則で説明しない。staticの初期値の式にはC独自の制約があり、ここでの定数0はそれを満たす。

int next(void) { static int n=0; ++n; return n; }
int fresh(void) { int n=0; ++n; return n; }

隠れた共有状態の代償

nextは実引数なしで呼んでも、過去の呼び出しによって結果が変わる。逐次呼び出しには便利だが、テストを独立して開始するには状態の初期化方針が必要である。この単元のカウンタは、並行スレッド向けの安全なカウンタではない。staticキーワードは、増加の原子性や同期を提供しない。

グローバルな状態に依存する関数を、入力と結果を中心とする関数へ変えると、依存関係が見える。ただし、入力ポインタが共有された変更可能なオブジェクトを指す場合、ローカルな名前しか使わない関数も共有状態への副作用を起こす。ローカル変数という表面だけで、純粋な関数や再入可能な関数だと判断しないようにしよう。

途中の過程をたどる例題

初期状態から、a=next(); b=next(); c=fresh(); d=fresh();を別々の文で行おう。

  1. 静的なnの初期値は0で、最初のnextで1へ増えるのでa=1である。
  2. 二回目のnextは同じオブジェクトの1を読み、2にするのでb=2である。
  3. 最初のfreshの自動オブジェクトnは0で初期化され、c=1になる。
  4. 二回目のfreshの新しい呼び出しもn=0の初期化から始まり、d=1になる。

予想されるa,b,c,dは1,2,1,1である。関数呼び出しをprintfの複数の実引数に入れて、その評価順序を推測しない。

紙と本文で試してみよう

int x=4; { int x=8; x=9; }で外側のxを追跡しよう。次に、freshの代わりにstatic nを使う関数の三回目の逐次呼び出しの戻り値を書こう。

ヒントを見る

同じつづりの名前が、別々のオブジェクトを指しているか印を付けよう。

解答を見る

ブロック内のxだけが9になり、外側のxは4である。nextの三回目の戻り値は3である。内側のスコープが終わることは、外側の値を復元する代入ではない。

よくある誤解と反例

static変数は、別ファイルからアクセスできるグローバル変数である。

ブロック内のstaticの名前はブロックスコープを持ち、リンケージはない。ファイルスコープのstaticの名前には内部リンケージがある。どちらも静的記憶域期間を持つという共通点と、名前へのアクセス規則の違いを分ける必要がある。

理解を確かめる

ブロック内のstaticは、関数が終わるとオブジェクトが消えるか？

答えと理由を見る

いいえ。

この例のオブジェクトの静的記憶域期間は、プログラムの実行全体にわたる。

内側のxへの代入は外側のxを変えるか？

答えと理由を見る

この例では変えない。

名前を隠す規則によって別々のオブジェクトを指定している。

static ++nは同時呼び出しでも安全か？

答えと理由を見る

保証されない。

staticは同期や原子的な演算を指定しない。

もう一歩先へ

状態の不変条件を、k回の逐次呼び出し後にn=kであることとしよう。初期のk=0では、初期化n=0により成立する。k<INT_MAXでほかの変更がなければ、次の++nは定義されており、n=k+1となるので帰納段階が成立する。k=INT_MAXとなった後の呼び出しは、この証明から除外する。数学の無限の自然数カウンタを、有限のintを使うプログラムへ無条件に移せない理由である。

小節 4.4

記憶域期間とリンケージ

名前がもう使えないということと、オブジェクトが消えたということは同じだろうか？

準備する概念と学習目標

準備する概念

  • 翻訳単位は、前処理後の一つのソースファイルの内容である。複数の翻訳単位をリンクしてプログラムを作ることができる。
  • 名前、オブジェクト、宣言を分けて描こう。同じオブジェクトに対する二つの宣言も、同じつづりを持つ別々のオブジェクトもあり得る。

学習目標

  • スコープ・記憶域期間・リンケージを三つの軸で分類する。
  • 外部宣言と定義の関係を説明する。
  • 割り当てられたオブジェクトと自動オブジェクトの生存期間に関する危険を区別する。

三つの問いを別々に考える

scope（スコープ）はこの位置で名前を使えるか、storage duration（記憶域期間）は実行中のどの期間にオブジェクトの記憶領域を保証するか、linkage（リンケージ）は別の宣言が同じオブジェクトや関数を指すか、という問いである。リンケージのないローカルなオブジェクトにも生存期間があり、内部リンケージを持つオブジェクトも複数の宣言を通じて同じ対象を指定できる。

C11のオブジェクトの記憶域期間は、static、thread、automatic、allocatedの四種類である。関数はオブジェクトではないので、ファイルスコープのstatic関数にオブジェクトの記憶域期間を付けない。stack/heapという実装上の配置の比喩も、この四つの言語上の分類に代わるものではない。

宣言の分類表を完成させる

以下のgは、ファイルスコープ・外部リンケージ・静的記憶域期間のオブジェクトである。hiddenはファイルスコープ・内部リンケージ・静的記憶域期間を持つ。fのlocalはブロックスコープ・リンケージなし・自動記憶域期間で、memoはブロックスコープ・リンケージなし・静的記憶域期間である。関数f自体には外部リンケージがあるが、オブジェクトの記憶域期間の欄は適用しない。

extern int g;は、この場合、先のgと同じ対象を宣言し、新しい値で初期化しない。externはいつも外部リンケージを作ると言うと誤りになる。先に見えているstatic宣言のリンケージを引き継ぐ場合があるので、宣言の順序と可視性を確認する必要がある。

int g=2;
static int hidden=3;
extern int g;
void f(void) { int local=4; static int memo=5; (void)local; (void)memo; }

オブジェクトの終了と所有権の契約

mallocによって正常に得た割り当て記憶領域は、それを指していたローカルなポインタ変数のスコープが終わっただけでは自動的に解放されない。逆に、freeで解放されると、ポインタ変数の名前が残っていても対象へアクセスする権利はない。割り当て失敗の検査、サイズ計算の範囲、正しい解放対象と所有権は、後のメモリの単元で併せて扱う。

自動オブジェクトのアドレスを外側に保存しても、ブロック終了によってそのオブジェクトの生存期間は終わる。その後のアクセスは未定義動作であり、N1570は生存期間が終わった際の関連するポインタ値もindeterminate（不定）と規定している。アドレスの数値が偶然同じだったり、データが画面に残って見えたりすることから、有効性を証明してはいけない。

途中の過程をたどる例題

例のg,hidden,local,memo,fを三つの軸で分類し、fを二度呼んだときのmemoオブジェクトの数を判断しよう。

  1. g：ファイルスコープ、外部リンケージ、静的記憶域期間。extern宣言は同じgを指定する。
  2. hidden：ファイルスコープ、内部リンケージ、静的記憶域期間。
  3. local：ブロックスコープ、リンケージなし、自動記憶域期間であり、各呼び出しに対応するオブジェクトがある。memo：ブロックスコープ、リンケージなし、静的記憶域期間。
  4. f：ファイルスコープ、外部リンケージを持つ関数であり、オブジェクトの記憶域期間の分類対象ではない。memoは、二回の逐次呼び出しで同じ一つのオブジェクトである。

この分類は、C11の宣言と生存期間の規則に基づく紙上の判断であり、実際のリンカのシンボルやメモリ配置は測定していない。

紙と本文で試してみよう

ファイルスコープのstatic int x=1;の後にextern int x;がある。xのリンケージと記憶域期間を書こう。関数内のstatic int y=2;と比べよう。

ヒントを見る

externを読む前に、先に見えている宣言を探そう。

解答を見る

後のextern xも、先のstatic xの内部リンケージを引き継ぎ、オブジェクトは静的記憶域期間を持つ。yはブロックスコープ・リンケージなし・静的記憶域期間である。同じ静的記憶域期間でも、名前のリンケージは異なる。

よくある誤解と反例

ローカルなポインタ変数が生存中なので、その対象も生存中である。

ポインタオブジェクトと対象の生存期間は別である。対象がfreeで解放されたり、自動オブジェクトのブロックが終わったりすれば、ポインタの名前が残っていても対象へのアクセスを正当化できない。

理解を確かめる

関数にautomatic記憶域期間を付けるか？

答えと理由を見る

いいえ。

この記憶域期間の分類は、オブジェクトについてのものである。

ファイルスコープのstatic xの後で見えるextern xは、必ず外部リンケージを持つか？

答えと理由を見る

いいえ。

先の内部リンケージの宣言を引き継ぐ規則を適用する。

mallocの対象は、ローカルなポインタのスコープが終わるだけで解放されるか？

答えと理由を見る

いいえ。

割り当て記憶領域の生存期間と、ポインタ変数の自動記憶域期間は異なる。

もう一歩先へ

モジュール内にstatic int total=0;を置き、読み取り関数と、範囲を検査して変更する関数だけを外部へ提供する設計を考えよう。外部から名前totalを直接宣言して同じ内部オブジェクトを指定することはできないので、意図しない直接の名前によるアクセスを減らせる。しかし、アドレスを返せば外部コードがそのオブジェクトを変更でき、関数が検査なしでオーバーフローを起こしてもリンケージは防いでくれない。内部リンケージは、すべてのメモリ安全性や情報セキュリティを証明する仕組みではなく、提供するインターフェースの契約を別に証明する必要がある。
