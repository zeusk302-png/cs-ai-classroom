소단원 1.1

소스·전처리·컴파일·링크

함수의 이름은 알려 주었는데 몸통이 없으면 어느 단계에서 문제가 생길까?

준비 개념과 학습 목표

준비 개념

  • 함수는 입력을 받아 계산하고 값을 반환하는 절차이다.

  • 진단: add(2,3)의 계약이 두 정수의 합이면 반환값은 5이다. 선언은 계약을 알리고 정의는 계산 몸통을 제공한다.

학습 목표

  • 소스에서 실행파일까지의 단계와 산출물을 구분한다.

  • 함수 선언과 정의의 차이로 번역 오류와 링크 오류를 분류한다.

  • 컴파일 성공·링크 성공·실행 정확성을 서로 다른 주장으로 구분한다.

소스와 전처리 결과

C 소스는 사람이 작성한 텍스트이다. #include와 #define 같은 전처리 지시문은 본격적인 언어 번역 전에 처리된다. #include <stdio.h>는 표준 입출력 기능을 사용할 선언을 제공하는 헤더를 포함시키는 지시이며, printf 구현 전체를 사용자가 손으로 복사하라는 뜻은 아니다.

GCC에서 -E는 전처리 결과를 보는 선택 도구이다. 전처리 결과를 포함한 하나의 번역 단위가 컴파일의 대상이 된다. 헤더 경로가 없으면 본문 함수의 계산을 시작하기도 전에 실패할 수 있다. 여기서 단계는 GCC 도구의 처리 모델이며 모든 구현이 같은 파일 이름의 중간 산출물을 저장해야 하는 것은 아니다.

컴파일과 어셈블

컴파일 단계는 구문과 타입을 분석하고 기계 실행으로 이어질 코드를 만든다. 어셈블러는 어셈블리 표현을 목적 파일로 바꾼다. 수업에서 '컴파일한다'는 말은 전체 빌드나 이 중 일부를 뜻할 수 있으므로 어느 단계인지 명확히 해야 한다.

GCC의 -S는 어셈블리 출력에서, -c는 목적 파일 생성에서 멈춘다. 목적 파일에는 기계 코드뿐 아니라 다른 파일의 함수와 연결하기 위한 심벌 정보가 담길 수 있다. 다른 곳의 add 함수를 호출하는 코드도 add의 적절한 선언을 알고 있다면 목적 파일 단계까지 진행할 수 있다.

링크는 정의를 연결한다

함수 선언 int add(int,int)는 이름·인자·반환 타입의 계약을 알려 준다. 정의 int add(int a,int b){return a+b;}는 실제 동작을 제공한다. 링크는 여러 목적 파일과 필요한 라이브러리 사이의 참조를 연결한다. add를 요구하는 목적 파일만 있고 정의를 가진 파일이 없으면 보통 미해결 심벌로 링크에 실패한다.

링크 성공은 요구한 심벌이 연결되었다는 증거이다. 올바른 수학식을 썼는지, 입력을 잘 처리하는지는 별도 문제이다. add 정의가 a-b를 반환해도 빌드에 성공할 수 있다. 이를 단계별로 분류하면 문법 수정을 해야 할지 빌드 파일 목록을 고쳐야 할지 판단하기 쉽다.

/* main.c */
#include <stdio.h>
int add(int a, int b);
int main(void) {
    printf("%d\n", add(2, 3));
    return 0;
}
/* add.c */
int add(int a, int b) { return a + b; }

중간 과정을 따라가는 예제

위 main.c와 add.c를 서로 다른 파일로 저장했다고 가정한다. GCC로 main.c만 목적 파일로 만들고 연결할 때와 두 파일 모두 연결할 때를 비교한다.

  1. gcc -std=c17 -c main.c -o main.o: add 선언이 있으므로 호출 타입을 검사하고 목적 파일을 만드는 것으로 예상한다.

  2. gcc main.o -o demo: add의 정의를 제공하지 않았으므로 링크 실패를 예상한다.

  3. gcc -std=c17 -c add.c -o add.o 후 gcc main.o add.o -o demo: 정의가 연결된다.

  4. 실행 시 main→add(2,3)→5→printf 순서이다. Windows GCC라면 demo.exe 같은 실행파일 이름을 사용할 수 있다.

두 목적 파일이 연결된 프로그램의 예상 출력은 5와 줄바꿈이다. 단계별 명령은 설명 예이며 여기서 실행하지 않았다.

풀이 보기

오해와 반례

컴파일이 끝나면 함수 정의는 모두 존재하고 결과도 맞다.

-c는 링크를 하지 않으므로 add의 정의가 없어도 목적 파일을 만들 수 있다. 정의가 존재하더라도 a-b라는 잘못된 계산은 별도 테스트나 논증으로 발견해야 한다.

한 단계 더

소단원 1.2

main과 종료코드

화면에 0이 안 보이는데 return 0;은 누구에게 값을 보내는 것일까?

준비 개념과 학습 목표

준비 개념

  • 함수의 반환값은 호출 쪽에 전달된다.

  • 진단: print와 return을 구분하듯 printf 출력과 함수 반환은 다른 사건이다.

학습 목표

  • hosted C 환경에서 main의 역할과 int 반환을 설명한다.

  • 표준 출력과 종료 상태를 따로 추적한다.

  • 0·EXIT_SUCCESS·EXIT_FAILURE의 의미와 OS별 표시 한계를 구분한다.

main은 사용자 코드의 진입점이다

이 단원은 운영체제와 표준 라이브러리가 제공되는 hosted C 환경을 가정한다. 프로그램 시작 시 런타임은 main을 호출한다. 이 예제의 int main(void)는 정수 값을 반환하며 인자 없는 형태임을 나타낸다. 임베디드의 freestanding 환경은 시작점과 라이브러리 지원이 다를 수 있으므로 이 형태를 모든 장치에 일반화하지 않는다.

main도 함수 몸통 안의 문장을 실행한다. return을 만나면 함수의 실행을 끝내며 뒤 문장은 실행하지 않는다. C99 이후 hosted 환경에서 main의 마지막 }에 도달하면 0을 반환한 것처럼 취급하지만, 다른 int 함수의 반환 누락까지 같은 규칙으로 생각하면 안 된다.

출력과 종료 상태는 다른 통로이다

printf는 표준 출력에 텍스트를 쓰는 동작이다. main의 return 값은 프로그램을 시작한 환경에 종료 상태를 전달한다. return 0;은 화면에 문자 0을 쓰지 않는다. 따라서 출력이 없는 프로그램도 성공 상태로 끝날 수 있다.

C의 hosted 환경에서 0 또는 EXIT_SUCCESS는 성공 종료를 뜻한다. EXIT_FAILURE는 실패 종료를 표현하는 표준 매크로이며 <stdlib.h>로 제공된다. 그 외 정수 값의 해석은 환경마다 다를 수 있다. '비영이면 무조건 같은 실패 코드'라고 표준 보장을 확대하지 않는다.

분기로 종료 경로를 읽는다

실패를 감지하면 실패 경로로 돌아가고 정상 경로에서는 성공으로 끝내도록 설계할 수 있다. 여기서는 입력 함수 없이 count=-1을 고정해 논리만 추적한다. count가 음수일 때에는 계산 결과를 출력하지 않고 EXIT_FAILURE로 종료한다.

선택 실습에서 PowerShell은 네이티브 프로그램의 종료 결과를 $LASTEXITCODE로 확인할 수 있다. 표시되는 정확한 정수와 운영체제의 변환을 검증하려면 실제 환경 기록이 필요하다. 이 종이 수업에서는 '성공'과 '실패'라는 의미를 예측하고 숫자의 실제 관측과 구분한다.

#include <stdio.h>
#include <stdlib.h>
int main(void) {
    int count = -1;
    if (count < 0) return EXIT_FAILURE;
    printf("%d\n", count);
    return EXIT_SUCCESS;
}

중간 과정을 따라가는 예제

위 프로그램을 count=-1과 count=2 두 경우로 추적한다. 출력과 종료 의미를 각각 적는다.

  1. -1<0은 참이므로 return EXIT_FAILURE에 도달한다.

  2. return 이후 printf는 실행되지 않아 프로그램의 표준 출력은 없다.

  3. count=2이면 조건이 거짓이므로 printf가 2를 출력한다.

  4. 이후 EXIT_SUCCESS로 종료한다. return을 화면 출력으로 세지 않는다.

-1: 출력 없음, 실패 종료 의미. 2: 예상 출력 2와 줄바꿈, 성공 종료 의미. 실제 OS 종료 정수는 여기서 측정하지 않았다.

힌트 보기

return은 제어 흐름을 끝낸다.

풀이 보기

첫 함수는 표준 출력 없이 성공 종료한다. 수정 함수는 ready와 줄바꿈을 출력한 뒤 성공 종료한다. return 뒤의 later는 두 경우 모두 출력되지 않는다.

오해와 반례

return 0은 숫자 0을 화면에 출력한다.

printf가 없는 int main(void){return 0;}은 출력 없이 성공 종료한다. 화면 결과와 종료 상태는 서로 다른 관찰 항목이다.

실행 결과를 (표준 출력, 표준 오류, 종료 의미)의 세 칸으로 기록해 보라. 사용자가 보는 안내와 스크립트가 판단할 성공 상태를 분리하면 여러 프로그램을 이어 실행할 수 있다. 표준 오류 및 셸의 조건 실행은 시스템프로그래밍에서 더 다룬다.

경고와 컴파일 옵션

경고가 사라졌다는 것이 모든 버그가 사라졌다는 뜻일까?

준비 개념과 학습 목표

준비 개념

  • 오류 메시지는 처리 단계에 관한 단서이며 성공은 문제 계약과 별개이다.

  • 미니복습: 경고는 의심스러운 코드에 관한 진단이고 옵션은 도구의 동작을 선택하는 인자이다.

학습 목표

  • GCC의 언어 모드·경고·최적화·디버그 옵션 역할을 구분한다.

  • 경고 없음과 정확성 보장의 차이를 반례로 설명한다.

  • 재현 가능한 빌드 명령을 기록한다.

옵션은 도구에 주는 조건이다

gcc -std=c17 -Wall -Wextra -Wpedantic -O0 -g main.c -o demo는 GCC용 명령 예이다. -std=c17은 기준 언어 모드, -o는 출력 파일, -O0는 최적화 수준, -g는 디버깅 정보를 요청한다. 명령은 C 소스 문장이 아니라 셸에서 컴파일러에 전달하는 조건이다.

이 옵션 이름을 MSVC 등 모든 도구에 그대로 적용할 수는 없다. 컴파일러 제품·버전·대상 플랫폼도 함께 기록해야 같은 진단을 재현할 가능성이 높아진다. 도구 기본 언어 모드가 바뀔 수 있으므로 예제는 기본값 대신 기준 모드를 명시한다.

경고 집합과 실패 처리

-Wall은 이름과 달리 가능한 모든 경고를 켜는 옵션이 아니다. -Wextra는 추가 진단 묶음을 요청하고 -Wpedantic은 선택한 기준 표준과 관련한 진단을 요청한다. -Werror는 발생한 경고를 오류로 다루어 빌드를 실패시키는 정책이다. 켜지지 않은 검사까지 자동으로 모두 켜는 것은 아니다.

경고는 코드의 문제 가능성을 알려 주지만 검사 범위, 데이터 흐름, 최적화 등에 따라 달라질 수 있다. 예를 들어 사용하지 않는 지역변수는 선택한 경고 옵션에서 진단될 수 있다. 경고 메시지의 정확한 문구는 버전마다 다르므로 이 수업은 원인과 처리 정책을 구분한다.

도구 검사와 의미 검증을 연결한다

컴파일러는 문법과 많은 타입 문제를 확인할 수 있지만 사람이 의도한 요구사항을 자동으로 모두 알지 못한다. 두 정수의 합을 원했는데 a-b를 쓰는 코드가 경고 없이 빌드되는 것은 자연스러운 반례이다. 정상 결과·경계 조건·실패 경로를 따로 점검해야 한다.

디버그 정보는 추적을 돕고 최적화 옵션은 코드 생성 방식을 바꾼다. 어느 옵션도 미정의 동작을 올바른 동작으로 바꾸는 보장은 없다. 옵션을 바꾸었을 때 결과가 달라지면 구현 탓으로 결론 내리기 전에 소스의 가정 위반과 미정의 동작 가능성을 확인한다.

int add(int a, int b) {
    return a - b; /* 문법·타입은 유효해도 합계 계약은 위반 */
}

중간 과정을 따라가는 예제

합계 함수 add(2,3)의 기대값은 5다. 위 코드가 경고 없이 빌드되었다고 가정한다. -Werror를 추가하면 결과를 자동으로 고칠 수 있을까?

  1. a와 b는 int이며 뺄셈 자체는 이 작은 입력에서 정의된 연산이다.

  2. 반환값은 2-3=-1이다.

  3. 진단이 없으면 -Werror가 실패로 바꿀 경고도 없다.

  4. 요구사항의 합계 5와 비교해야 의미 오류가 드러난다.

-Werror는 코드의 -를 +로 바꾸지 않는다. 예상 반환값 -1은 여전히 잘못된 합계이다.

소단원 1.4

표준 C와 구현 차이

한 컴퓨터에서 int가 4바이트이면 모든 컴퓨터에서 같은 크기일까?

준비 개념과 학습 목표

준비 개념

  • 타입은 가능한 값과 연산을 정하는 계약이다.

  • 진단: 언어 규칙, 컴파일러 옵션, 운영체제 관례는 서로 다른 층이다.

학습 목표

  • 언어 표준과 개별 구현의 보장을 구분한다.

  • 구현 정의·미지정·미정의 동작의 의미를 입문 수준에서 구별한다.

  • sizeof의 C 바이트와 물리적 비트 수를 구분한다.

표준은 공통 계약이고 구현은 구체적 선택이다

C17, C23은 언어 규칙의 서로 다른 판이다. GCC, Clang, MSVC 등은 특정 판과 확장을 구현하는 도구이다. 이 단원의 작은 예제는 C17 hosted 환경을 기준으로 한다. 최신판의 모든 특징이나 모든 컴파일러의 지원을 가정하지 않는다.

-std=c17과 -std=gnu17은 GCC의 기준 모드와 GNU 확장 모드의 구분이다. 확장이 있는 코드가 한 도구에서 받아들여졌다는 사실만으로 모든 표준 C 구현에 이식 가능하다고 결론 내릴 수 없다. 여기의 출처는 공개 구현 문서이며 ISO 유료 원문을 읽어 조항 준수를 인증한 자료가 아니다.

바이트와 정수 크기를 조건과 함께 읽는다

C의 sizeof 결과 단위는 C 바이트이며 sizeof(char)는 정의상 1이다. 한 C 바이트의 비트 수는 <limits.h>의 CHAR_BIT로 알 수 있다. 따라서 'char는 1바이트'와 'char는 항상 8비트'는 서로 다른 주장이다. 일반적인 환경의 8비트를 모든 구현의 필수값으로 확대하지 않는다.

sizeof(int)는 구현마다 다를 수 있다. 정수의 범위는 <limits.h>의 INT_MIN·INT_MAX 등으로 확인한다. 아래 출력에서 첫 수는 1로 예측할 수 있지만 나머지를 실행 없이 4와 8로 확정해서는 안 된다. 크기 가정이 중요한 파일 형식이나 통신은 폭과 표현을 따로 설계해야 한다.

#include <stdio.h>
#include <limits.h>
int main(void) {
    printf("%zu %zu %d\n", sizeof(char), sizeof(int), CHAR_BIT);
    return 0;
}

보장 종류를 구분한다

구현 정의 행동은 구현이 선택을 문서화해야 하는 경우이다. 미지정 행동은 허용된 여러 가능성 중 선택하지만 각 선택을 문서화할 의무가 없는 경우이다. 예를 들어 별도 부작용이 없는 두 함수 인자의 평가 순서를 한쪽으로 고정하여 모든 구현에 기대해서는 안 된다.

미정의 동작은 언어 규칙이 결과 요구를 부과하지 않는 경우이다. signed 정수 오버플로, 유효 범위 밖 배열 접근 같은 사례에 '이 컴퓨터에서는 이렇게 보였다'는 값 하나를 정답으로 부여할 수 없다. 실행 관측은 해당 실행의 현상이며 표준 보장이 아니다. 후속 단원에서는 각각의 연산에 유효 범위와 수명 조건을 명시한다.

중간 과정을 따라가는 예제

가상 구현 A는 CHAR_BIT=8,sizeof(int)=4이고 B는 CHAR_BIT=16,sizeof(int)=1이라고 가정한다. sizeof(char)는 두 구현에서 1이다. 위 출력과 int 객체의 저장 비트 수를 계산하라. 이 가상 표는 특정 제품의 실제 측정이 아니다.

  1. A의 출력 예상은 1 4 8이다. int 저장 크기는 4*8=32비트이다.

  2. B의 출력 예상은 1 1 16이다. int 저장 크기는 1*16=16비트이다.

  3. sizeof 값이 같거나 작아도 바이트의 비트 수를 곱해야 비트 단위를 얻는다.

  4. 저장 비트 수만으로 부호 표현과 값 비트·패딩을 모두 결정할 수는 없다.

가정 안에서 A는 저장 32비트, B는 저장 16비트이다. 'sizeof(int)=1이면 숫자 범위가 8비트'라는 결론은 성립하지 않는다.

풀이 보기

오해와 반례

내 실행 결과는 모든 표준 C 프로그램의 정답이다.

sizeof(int)가 4인 관측은 그 구현의 사실일 뿐 2인 구현의 가능성을 없애지 않는다. 미정의 동작은 특히 한 번의 출력으로 언어 보장을 세울 수 없다.
