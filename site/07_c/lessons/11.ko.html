재귀 안의 local과 static은 같은 개수로 생길까?

새 함수 walk는 0–5의 정수만 받으며 바깥에서 허용 범위를 먼저 검사한다. 각 호출은 int mark=n을 선언하고, n>0이면 walk(n-1)을 한 번 부른 다음 mark를 보고한다. walk(2)의 보고 순서는 0,1,2다. 안쪽 호출이 바깥 mark를 덮지 않는 이유는 자동 객체가 재귀 진입마다 별도 인스턴스를 갖기 때문이다. 이 개념 모형의 최대 활성 호출은 3개이며 실제 프레임 크기를 뜻하지 않는다.

반면 함수 안 static int visits=0을 두고 매 호출마다 visits를 한 번 증가시키면 모든 진입이 같은 객체를 쓴다. 초기 visits=0인 한 walk(2)의 세 호출은 visits를 3으로 만들며 반환 중에는 모두 같은 최종 3을 볼 수 있다. 이후 walk(0)을 다시 호출하면 4가 된다. 입력 범위와 전체 호출 수가 int 범위 안이라고 가정한다. 종료 증명, 자동 객체 독립성, 공유 static 상태, 실제 실행 자원은 서로 다른 주장이다.

    작은 허용 입력과 호출 관계를 먼저 고정한다.

  • 객체 수명

    각 재귀 진입의 자동 객체와 살아 있는 구간을 연결한다.

작아지는 입력과 바닥

재귀는 함수가 자신을 직접 또는 다른 호출을 통해 다시 호출하는 구조다. 종료조건에 도달할 수 있는 입력 범위와 감소량이 필요하다. 바닥 조건을 써 놓았어도 입력이 그쪽으로 움직이지 않으면 종료를 설명할 수 없다.

여기서는 내장 int의0부터100까지만 받는 합계 함수로 범위를 한정한다. 이 범위의 최대 합5050은 C가 보장하는 최소 int최댓값32767 안에 있다. 큰 입력의 signed overflow를 결과 계산으로 정당화하지 않는다.

호출은 기다리고 반환은 돌아온다

sum(3)이3+sum(2)를 계산하려면 안쪽 sum(2)가 값을 줄 때까지 기다린다. 개념 그림에서 호출별 n과 돌아갈 위치를 쌓고 바닥에서 값을 돌려준다. 재귀 진입의 자동 객체는 각 진입에 별도 인스턴스가 있다.

흔히 호출 스택이라고 설명하지만 C언어가 모든 구현에 같은 프레임 바이트나 무한 깊이를 약속하지 않는다. 컴파일러가 호출을 최적화할 수도 있다. 아래 활성호출 수는 소스수준 개념모형이며 실제 메모리측정이 아니다.

범위와 실패를 먼저 처리한다

범위 밖 입력은-1을 오류 표시로 돌려주는 자체 계약을 쓴다. 허용 합은0 이상이므로 이 예제에서는 구별된다. 이 방식이 모든 함수의 오류정책이라는 뜻은 아니다.

종료와 메모리는 별개다. 수학적으로 언젠가 끝나더라도 실행환경의 자원이 먼저 부족할 수 있다. 작은 사례를 손으로 추적한 후 실제 실습에서 입력·컴파일 옵션·실행결과를 따로 기록한다. 본문 코드는 실행하지 않았다.

중간 과정을 따라가는 예제

다음 코드에서 sum(3)의 호출과 반환, 최대 개념 활성호출을 추적하라. 

int sum(int n) {
    if (n < 0 || n > 100) return -1;
    if (n == 0) return 0;
    return n + sum(n - 1);
}

  1. 호출 인수 n은 3→2→1→0으로 매번 1씩 줄어 0에 도달한다.

  2. 반환은 0→1+0=1→2+1=3→3+3=6 순서다.

  3. 바닥 sum(0)에서 소스 수준의 개념 활성 호출은 4개다.

합은 6이고 최대 개념 활성 호출은 4개다. 실제 스택 바이트나 컴파일러 실행 기록은 아니다.

같은 테스트를 두 번 호출한다

초기 visits=0에서 walk(2) 다음 walk(0)을 순서대로 부른다.

  1. 첫 호출 묶음에서 3번 증가해 visits=3이다.

  2. 다음 walk(0)은 한 번 증가해 4가 되고 mark=0을 보고한다.

비교할 점

함수 호출 경계와 static 초기화 시점을 구별한다.

감소 폭과 바닥 조건의 불일치

n==0만 종료하고 그 외 walk(n-2)를 부른다. 시작 n=3에 범위 검사가 없는 결함 설계를 가정한다.

  1. 3→1→−1로 이동하며 0을 건너뛴다.

  2. 이 단계만으로 0을 향한 감소 증명이 깨졌음을 확인하고 더 깊은 signed 산술을 실행하지 않는다.

n<=0 종료나 허용 입력/감소 규약을 다시 설계해야 한다.

준비 개념과 학습 목표

준비 개념

  • struct와 포인터

  • malloc 실패와 초기화

학습 목표

  • 자기 포인터를 가진 구조체를 설명한다

  • 실패 때 기존 머리를 보존한다

새 링크 두 개를 준비하다 실패하면 기존 사슬도 바꿔야 할까?

새 독점 소유 목록 A(value=8)→B(value=5)→NULL에 두 값을 2,3 순서로 앞에 붙이는 append_front_pair를 설계한다. 결과는 X(2)→Y(3)→A→B다. X와 Y를 임시로 할당하고 값을 초기화한 뒤 Y.next=A, X.next=Y를 만든다. 호출자 head를 바꾸는 커밋은 마지막 한 번이다. 첫 할당 실패는 임시 자원이 없고, 두 번째 실패는 X만 해제하며 기존 A/B의 링크와 head를 보존한다.

한 노드씩 기존 head에 바로 붙이는 두 prepend 호출은 두 번째 실패에서 첫 변경이 남을 수 있다. 그것은 부분 성공 API로 별도 명시할 수 있지만 이번 전부 성공/실패 보존 계약과 같지 않다. 각 노드는 별도 살아 있는 객체이며 같은 value가 같은 노드라는 뜻도 아니다. 임시 노드의 next는 읽기 전에 명시적으로 설정한다. 순차 독점 소유·비순환 및 크기 표현 가능성을 전제하고 실제 malloc 실패를 주입하지 않는다.

    임시 노드 정리와 기존 사슬 보존을 함께 설계한다.

값과 링크를 나눈다

struct Node에는 value와 next가 있다. next는 다음 노드의 주소이며 값이 같다 해도 같은 노드라는 뜻은 아니다. 마지막next=NULL로 끝나는 표현을 선택한다. NULL은 정상 종료표시이지 읽을 수 있는 노드가 아니다.

자기 구조체 값을 직접 멤버로 넣을 수는 없지만 자기 구조체를 가리키는 포인터는 넣을 수 있다. 동적노드가 주소순서대로 연속 배치된다는 보장은 없으며 숫자주소 대신 A/B같은 라벨로 그려도 연결을 추적할 수 있다.

할당 성공 뒤 초기화한다

malloc(sizeof *p)는 노드 한 개의 필요한 크기를 타입에 맞춰 요청한다. 실패하면NULL을 반환할 수 있고 성공한 객체의 초기값은 indeterminate이므로 value/next를 읽기전에 설정한다. sizeof는 실제 필드 크기·padding을 반영하므로 임의로8바이트라 단정하지 않는다.

prepend는 새노드가 준비되면 기존head를next에 넣고 새주소를 반환한다. malloc실패이면 새노드는 없고 기존head도 변경하지 않는 계약이다. 실패반환을 그대로head에 대입하면 기존목록을 잃을 수 있으므로 임시변수로 확인한다.

누가 머리를 바꾸는가

함수에 포인터 값을 전달하면 함수의 매개변수는 호출자 변수와 별개다. 새 머리를 반환하고 호출자가 받아야 자신의 head가 바뀐다. Node**로 갱신하는 다른 설계도 가능하지만 이 예제에서는 반환 방식을 쓴다.

동적할당 객체는 함수가 끝났다는 이유만으로 사라지지 않는다. 반면 함수의 지역Node주소를 반환하면 그자동객체의 수명종료 뒤 접근할 수 없다. 모든 동적노드의 해제 책임을 하나의 소유자에게 두고 공유별칭은 별도관리한다.

#include <stdlib.h>
struct Node { int value; struct Node *next; };
static struct Node *prepend(struct Node *head, int value) {
    struct Node *p = malloc(sizeof *p);
    if (p == NULL) return NULL;
    p->value = value;
    p->next = head;
    return p;
}

노드를 삭제한 뒤 다음 주소를 찾는 대신 어떤 칸을 먼저 바꿀까?

새 독점 소유 목록 A(4)→B(9)→C(4)→D(2)→NULL에서 모든 값 4를 삭제한다. link는 현재 노드를 가리키는 포인터 칸의 주소다. 처음 link=&head다. 현재 노드 p=*link를 읽고 삭제 대상이면 살아 있는 p에서 next=p->next를 먼저 저장하여 *link=next로 다시 연결한 뒤 p를 free한다. 삭제 후 link는 그대로 유지해 같은 칸의 새 대상을 검사한다. 보존 대상이면 link=&p->next로 옮긴다.

이 방식은 삭제 대상의 이전 노드가 없을 때도 head 칸을 같은 규칙으로 다룬다. 모든 포인터 칸은 살아 있는 호출자 head나 보존한 노드의 next이며 외부 별칭/동시 변경/공유 꼬리는 제외한다. free한 p에서 next를 읽거나 &p->next를 만들지 않는다. 입력 목록이 유한 비순환이라는 종료 전제와 노드별 독점 해제 책임을 따로 확인한다.

먼저 확인할 개념
  • 포인터를 저장한 칸의 주소

    link가 노드 자체가 아니라 head/next 칸을 지정함을 설명한다.

  • 해제 뒤 빌림 종료

    free 이전 연결 수정과 이후 읽기 금지를 연결한다.

살아있는 유한 사슬을 전제한다

순회는 현재 p가 NULL이 아닌 동안 노드의 값을 확인하고 p=p->next로 이동한다. 모든 링크가 살아있는 노드 또는 NULL이고 사슬이 유한·비순환이라는 조건을 전제한다. 순환이면 NULL을 못 만나며 해제된 링크이면 NULL 검사만으로 안전해지지 않는다.

여기서는 소유자가 유일하고 각 노드를 한 번만 malloc했으며 동시 변경과 외부 별칭이 없는 목록을 쓴다. 이 조건을 벗어난 공유 꼬리·순환·다른 스레드 변경은 별도 소유권과 동기화 설계가 필요하다.

다음을 먼저 저장한다

free(p) 후 p->next를 읽으면 이미 수명이 끝난 객체에 접근한다. 다음 주소를 먼저 next=p->next로 저장하고 free(p), p=next 순으로 진행한다. 다음 노드는 아직 살아있다는 조건이 필요하다.

free는 그 동적 객체의 저장 공간을 회수 가능하게 만든다. 그 객체를 가리키던 포인터 값은 수명 끝 뒤 indeterminate이 되므로 해제된 별칭을 비교·역참조해 확인하지 않는다. 변수에 NULL을 대입하는 것은 다른 별칭까지 자동으로 고치는 것이 아니다.

호출자 머리도 끝상태로 만든다

해제 함수는 새 머리 NULL을 반환하고 호출자가 head=destroy(head)로 저장하도록 한다. 함수 내 로컬 p만 NULL이 되어도 호출자 head를 자동 갱신하는 것은 아니다. 외부에 빌려준 노드 주소는 해제 전에 사용 종료를 합의해야 한다.

빈 목록 해제는 루프가 한 번도 돌지 않고 NULL을 반환한다. 같은 노드를 두 번 free하면 정의되지 않은 동작이며 이미 해제된 head를 재사용해서 확인하는 방법은 안전한 테스트가 아니다. 실제 코드는 도구 검증도 필요하지만 여기서는 종이 추적만 한다.

독점소유·비순환·살아있는 동적목록A2→B5→C8→NULL을 다음코드로 해제한다고가정하고순서를추적하라. 

static struct Node *destroy(struct Node *p) {
    while (p != NULL) {
        struct Node *next = p->next;
        free(p);
        p = next;
    }
    return NULL;
}
/* caller: head = destroy(head); */

  1. p=A에서 next=B를 보존한 뒤 A를 free하고 p=B로 갱신한다.

  2. B에서 C를 보존한 뒤 B를 해제한다. C에서는 NULL을 보존한 뒤 C를 해제한다.

  3. NULL에서 종료하고 호출자의 head에 NULL을 저장한다. free는 총 3회이며 해제된 노드의 next를 읽지 않는다.

빈 큐와 마지막 삭제에서 머리만 바꾸면 충분할까?

새 dummy 없는 큐는 head/tail/count를 함께 유지한다. 빈 큐는 두 포인터가 NULL이고 count=0이다. 한 노드이면 head와 tail이 같은 살아 있는 객체를 지정한다. enqueue는 준비한 새 노드의 next=NULL을 정하고 빈 경우 두 포인터를 모두 새 노드로, 비어 있지 않으면 옛 tail.next를 새 노드로 바꾸고 tail을 옮긴다. count는 실제 성공한 연결 때만 증가한다. 일반 enqueue는 count가 실제 저장 정수형의 최댓값이면 새 할당이나 링크 변경 전에 거절하여 기존 head/tail/count를 보존한다. 허용 증가도 해당 형의 표현 범위 안에서만 계산한다.

dequeue는 빈 경우 실패 보존이다. 비어 있지 않으면 살아 있는 head의 값과 next를 보존하고 head를 next로 바꾼다. 새 head가 NULL이면 tail도 NULL로 바꾼 후 옛 노드를 해제한다. count도 하나 줄인다. 마지막 삭제에서 tail을 남기면 수명 끝난 포인터를 다음 삽입에서 읽는 문제가 생긴다. count가 맞는다는 사실만으로 비순환·tail 도달·마지막 next=NULL 불변식을 증명하지 않는다. 이 큐는 순차 독점 소유이며 실제 할당자/성능을 측정하지 않았다.

무엇을 할지와 어떻게 담을지

스택은 최근 넣은 값을 먼저 꺼내는 연산 규칙이고 연결 목록은 값과 next의 표현이다. 같은 스택을 배열로도 만들 수 있다. 클라이언트가 내부 next를 마음대로 바꾸면 연산 계약이 깨질 수 있어 인터페이스 뒤에 표현을 숨기는 설계를 배운다.

CMU15-122는 C0 연결 구조로 스택·큐와 표현 불변식을 설명한다. 이 본문의 NULL 종료 C목록·수동 free는 원문의 dummy 노드·자동 회수와 다르다. 개념을 참고하되 코드와 소유권 조건을 섞지 않는다.

연산비용에는 조건을 붙인다

살아있는 목록에서 이미 알고 있는 머리 앞에 노드를 연결하는 포인터 대입 수는 상수다. 하지만 할당자 비용까지 항상 상수라고 보장하거나 임의 위치 검색이 무료라고 가정하지 않는다.

0부터 세는 i번째 값은 앞에서 i번 next 이동해 도달한다. 배열의 유효 인덱스 접근과 달리 순차 위치 탐색이 필요하다. 삭제하려는 노드와 이전 노드를 이미 아는 경우와 값으로 찾아야 하는 경우의 전체 비용도 다르다.

불변식과 작은 반례를 준비한다

NULL 종료 목록의 불변식은 유한·비순환, 각 next가 살아있는 다음 노드 또는 NULL, 각 동적 노드의 독점 소유와 해제 책임이다. 연산 전후 이 조건이 유지되는지 그림으로 확인한다.

연결 목록의 삽입은 언제나 전체 O(1)이다.

다른 문제에 적용하기

새 독점 소유 비순환 목록 A(4)→B(9)→C(4)→NULL에서 2/3 쌍 삽입을 실패 보존 방식으로 준비한다. X 성공 뒤 Y 실패일 때와 X/Y 성공 때를 각각 독립 시작에서 추적하라. 성공 목록에서 모든 값 4를 link 방식으로 삭제하고 유지 값/비교/free 수를 구하라. 유지 노드를 FIFO 큐로 해석하여 모두 dequeue한 끝상태도 적어라. 별도로 visits=0인 walk(2)의 mark 보고/공유 visits와 뒤 walk(0)을 계산하라. 실제 C/할당/학생 실행은 하지 않는다.

힌트 1

임시 새 노드만 정리하는 실패와 전체 성공 커밋을 나눈다. 삭제 뒤 같은 link를 유지한다.

힌트 2

큐의 마지막 삭제에서 head/tail/count를 함께 갱신하고 재귀의 자동 mark와 공유 visits를 따로 센다.

풀이와 답 확인

  1. Y 실패면 새 X만 1회 해제하고 기존 A→B→C 및 head=A를 보존한다.

  2. 둘 다 성공이면 X(2)→Y(3)→A(4)→B(9)→C(4)다.

  3. 값 4 삭제는 다섯 노드를 각각 비교하고 A/C를 2회 해제해 2→3→9를 유지한다.

  4. 세 유지 노드의 FIFO 출력은 2,3,9이며 각각 한 번 해제한 뒤 head=tail=NULL, count=0이다. 이 단계의 free는 3회로 앞의 삭제 2회와 구별한다.

  5. walk(2)의 mark 보고는 0,1,2이고 visits=3이다. 같은 실행에서 뒤 walk(0)은 mark=0을 보고하고 visits=4다.

실패는 기존 4/9/4를 보존하고 X만 정리한다. 성공 뒤 삭제는 비교 5회/free 2회/유지 2,3,9다. 이후 큐 소멸은 추가 free 3회와 빈 세 필드다. 재귀의 호출별 mark와 공유 visits=3→4를 구별한다.
