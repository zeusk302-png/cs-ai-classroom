소단원 13.1

FILE과 text·binary

파일 이름을 안다고 해서 바로 그 파일의 내용을 읽을 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 포인터와 NULL
  • 문자 배열
  • 함수 반환값

학습 목표

  • 파일 이름과 열린 스트림을 구분한다.
  • 읽기·쓰기·추가 모드의 영향을 설명한다.
  • 텍스트 모드와 바이너리 모드의 조건을 구분한다.

파일을 여는 이유

파일 이름은 저장된 대상을 찾는 데 쓰는 문자열이고, FILE *는 열린 스트림을 다루는 포인터다. 스트림에는 읽는 위치, 버퍼, 끝과 오류를 나타내는 상태 등이 연결된다. 물건의 주소와 물건을 받아 오는 창구가 서로 다른 것처럼, 이름과 열린 스트림도 역할이 다르다.

<stdio.h>를 포함하고 fopen의 반환값을 검사한다. 반환값이 NULL이면 열기에 실패했으므로 그 포인터로 읽거나 닫지 않는다. 실패 원인은 권한이나 존재 여부 등 환경에 따라 다르며, 이름을 보고 성공을 단정할 수 없다.

모드를 먼저 선택하기

r은 기존 텍스트 파일을 읽는다. w는 쓰기 위해 파일을 만들거나 기존 내용을 길이 0으로 지운다. a는 쓰기를 파일 끝에 추가한다. rb와 wb는 바이너리 모드의 읽기와 쓰기다. 이미 자료가 든 파일에 w를 선택하는 일은 내용을 유지한 채 수정하는 일과 다르다.

읽기와 쓰기를 모두 허용하는 + 모드는 방향 전환 규칙도 갖는다. C11 기준으로 출력 뒤 입력에는 fflush 또는 위치 변경이 필요하다. 입력 뒤 출력에는 위치 변경이 필요하지만 직전 입력이 파일 끝에 도달한 경우는 예외다. 이 단원에서는 먼저 단방향 읽기를 익힌다.

텍스트와 바이너리의 경계

텍스트 모드는 줄바꿈 등 외부 표현과 프로그램 안의 문자 표현 사이에서 변환을 할 수 있다. 어떤 환경에서는 r과 rb의 결과가 같더라도 모든 환경에서 같다고 일반화하지 않는다. 이 모드만으로 문자 인코딩이 자동으로 원하는 언어로 바뀌는 것도 아니다.

바이너리 모드는 데이터를 일정한 표현으로 다룰 때 사용하지만, 정수 크기나 저장 순서를 자동으로 통일하지 않는다. C11 초안에는 바이너리 스트림 끝에 구현이 정한 수의 널 문자가 추가될 수 있다는 조건도 있다. 바이트를 주고받는 형식은 별도 계약으로 정해야 한다.

중간 과정을 따라가는 예제

이미 3줄이 저장된 notes.txt를 읽어 보여 주려 한다. r, w, a 중 어떤 모드를 선택하고 실패 시 무엇을 해야 하는가?

  1. 읽기만 필요하므로 r을 선택한다.
  2. fopen의 결과가 NULL인지 먼저 검사한다.
  3. NULL이면 읽기와 fclose를 하지 않고 실패 경로로 끝낸다. 성공한 스트림만 사용한 뒤 닫는다.

r을 선택한다. w는 기존 내용을 지울 수 있으며 a는 끝에 쓰는 모드이므로 읽기 목적과 맞지 않는다.

종이와 본문으로 직접 해보기

기존 기록을 유지하면서 새 한 줄을 끝에 쓰는 작업과 파일 전체를 새 결과로 바꾸는 작업에 각각 모드를 배정하라.

힌트 보기

추가와 길이 0으로 초기화의 차이를 생각한다.

풀이 보기

끝에 추가하는 작업은 a, 전체를 새로 쓰는 작업은 w다. 두 작업 모두 열기와 쓰기·닫기 결과를 확인해야 하며 실제 원본을 바꾸는 실습은 여기서 수행하지 않는다.

오해와 반례

FILE *에 파일 경로가 들어 있으므로 값을 직접 복사하면 같은 스트림을 만들 수 있다.

FILE은 라이브러리가 관리하는 객체다. FILE 객체를 복사해 원래 객체 대신 사용해도 된다는 보장은 없다. 열린 스트림의 포인터를 정해진 함수에 전달하고 닫은 뒤에는 다시 사용하지 않는다.

자기점검

fopen이 NULL을 반환하면 fclose를 호출해야 하는가?

답과 이유 보기

아니다.

열기에 실패하여 유효한 열린 스트림 포인터가 없다.

기존 내용이 있는 파일을 wb로 열면 보존되는가?

답과 이유 보기

보존되지 않는다.

wb도 기존 파일을 길이 0으로 줄이거나 새로 만드는 쓰기 모드다.

rb를 사용하면 모든 컴퓨터의 int 크기가 같아지는가?

답과 이유 보기

아니다.

스트림 모드와 자료형 표현 계약은 서로 다른 문제다.

한 단계 더

같은 파일을 r과 rb로 읽었을 때 줄바꿈 처리 차이가 생길 수 있는 환경을 조사하고, 관찰한 환경과 다른 환경에 대한 보장을 구분해 적어 보자. 실제 비교 실행은 미수행이다.

출처와 확인 범위
  • WG14 N1570: C11 공개 위원회 초안

    §7.21.3, §7.21.5.2–3의 스트림·모드·NULL·방향 전환 규칙을 읽었다. PDF를 메모리에서 직접 읽었다. 최신 C 표준 전체를 검토했다는 뜻은 아니다.

  • CS50 Manual: fopen

    전체 설명의 r/w/a/b 모드와 실패 시 NULL을 확인했다. POSIX 및 glibc 확장을 모든 C 환경의 규칙으로 사용하지 않았다.

calculations: r/w/a의 목적을 조건별로 대조했다. 파일 3줄은 자체 예제의 초기 상태이며 실제 파일을 변경하지 않았다. · code_execution: not_executed: C 컴파일과 실제 파일 입출력은 수행하지 않았다. 예제 반환값과 내용은 명시한 가정에 대한 종이 추적이다. · learner_review: not_performed

소단원 13.2

read·write·seek

세 칸을 읽으라고 요청했는데 두 칸만 돌아오면 무엇을 믿어야 할까?

준비 개념과 학습 목표

준비 개념

  • 배열 용량
  • size_t
  • 파일 모드

학습 목표

  • 요청량과 실제 반환량을 구분한다.
  • 요소 수와 바이트 수를 구분한다.
  • 위치 변경의 성공 여부와 텍스트 제한을 설명한다.

반환값만큼 처리하기

fread(buf, size, count, fp)는 size 크기의 요소를 최대 count개 읽고, 성공적으로 읽은 요소 수를 돌려준다. size가 1이면 반환값을 읽은 C 바이트 수로 해석할 수 있지만 size가 2이면 반환값 2는 완전한 요소 두 개를 뜻한다.

요청한 수만큼 항상 읽히지는 않는다. 파일 끝이나 읽기 오류를 만나면 짧게 읽을 수 있다. 불완전한 요소는 그 값이 불확정이므로 완전한 요소처럼 해석하지 않는다. 입력 버퍼는 요청한 전체 크기를 담을 용량을 갖춰야 한다.

읽기 위치를 추적하기

이 예제는 8비트 바이트를 쓰고 추가 널 문자가 없는, 위치 변경 가능한 바이너리 파일을 가정한다. 내용이 10, 20, 30, 40, 50이고 시작 위치가 0이라면 크기 1인 요소를 세 개 읽을 때 반환값은 3, 다음 위치는 3이다.

같은 요청을 한 번 더 하면 40과 50만 있어 반환값은 2다. 처리할 내용은 이번에 얻은 두 값이며 이전 버퍼의 세 번째 칸을 새 자료로 처리해서는 안 된다. 짧은 읽기의 이유는 끝과 오류 상태를 확인해 구분한다.

쓰기와 위치 변경도 결과를 검사하기

fwrite 역시 성공한 요소 수를 반환한다. 요청한 수와 다르면 전체 기록이 완료됐다고 보고할 수 없다. fclose에서도 지연된 출력 오류가 나타날 수 있으므로 닫기 결과까지 확인한다. 버퍼에 보낸 것과 저장 장치에 영구 보존된 것은 같은 보장이 아니다.

fseek(fp, 0L, SEEK_SET)가 성공하면 처음으로 돌아가며 파일 끝 표시도 지워진다. 만족시킬 수 없는 위치 변경은 0이 아닌 값을 반환하므로 C 코드에서는 != 0으로 실패를 검사한다. 텍스트 스트림의 0 아닌 offset은 같은 파일에서 성공한 ftell로 얻은 값과 SEEK_SET 조합을 사용하는 제한이 있다.

중간 과정을 따라가는 예제

설명에 정한 5바이트 파일에서 fread(buf, 1, 3, fp)를 두 번 수행한다. 이후 fseek(fp, 0L, SEEK_SET)가 성공하고 다시 한 번 읽는다.

  1. 첫 읽기: 반환 3, 유효한 값 10·20·30, 위치 3.
  2. 둘째 읽기: 반환 2, 유효한 값 40·50, 위치 5. 세 번째 버퍼 칸은 새 입력이 아니다.
  3. 성공한 fseek로 위치를 0으로 옮긴다.
  4. 다시 읽기: 반환 3, 값 10·20·30.

세 번의 읽기 반환값은 3, 2, 3이다. 세 번째 읽기는 위치 변경 성공을 전제로 한다.

종이와 본문으로 직접 해보기

같은 파일에서 두 칸씩 읽는다면 세 번의 반환값과 유효한 값을 적어 보자.

힌트 보기

파일에는 5개가 있으므로 요청량 6개를 모두 채울 수 없다.

풀이 보기

2개(10·20), 2개(30·40), 1개(50)다. 세 번째 호출에서 남은 버퍼 칸을 출력하면 이전 값과 새 값을 혼동한다.

오해와 반례

fread의 반환값은 언제나 바이트 수다.

반환값은 완전하게 읽은 요소 수다. size=1일 때만 수치가 바이트 수와 같다. size=2, count=3이면 최대 6바이트를 요청하고 완전한 요소가 2개일 때 반환값은 2다. 부분 요소는 별도로 유효하다고 가정하지 않는다.

자기점검

fwrite가 요청 4개 중 3개를 반환했을 때 완전한 성공인가?

답과 이유 보기

아니다.

한 요소가 완료되지 않았으므로 오류 경로를 처리해야 한다.

텍스트 파일에서 임의로 fseek(fp, 7, SEEK_SET)를 쓰는 것은 항상 이식 가능한가?

답과 이유 보기

아니다.

0 아닌 offset은 같은 파일에서 성공한 ftell로 얻은 값이어야 한다.

C 표준에 맞춰 fseek 실패를 어떻게 검사하는가?

답과 이유 보기

반환값 != 0을 검사한다.

특정 환경의 -1 규칙에만 기대지 않고 비영 성공 실패 규칙을 사용한다.

한 단계 더

텍스트 파일의 위치를 fgetpos로 저장하고 fsetpos로 복원하는 방법을 찾아 보자. 저장된 위치 정보를 임의의 숫자로 만들지 않고 같은 파일에서 얻는 이유를 설명하라.

출처와 확인 범위
  • WG14 N1570: C11 공개 위원회 초안

    §7.21.8.1–2와 §7.21.9.1–4의 반환 요소 수, 부분 요소, 위치 제한을 직접 읽었다. PDF를 메모리에서 직접 읽었다. 최신 C 표준 전체를 검토했다는 뜻은 아니다.

  • CS50 Manual: fread, fwrite

    요소 수 반환과 짧은 읽기의 EOF/error 구분을 전체 본문에서 확인했다.

  • CS50 Manual: fseek

    위치 변경 설명을 확인했다. POSIX의 -1/errno와 C11의 비영 실패를 구분했다.

calculations: 5개 자료를 3개 단위와 2개 단위로 나눠 3+2=5와 2+2+1=5를 대조했다. fseek 성공 조건을 붙인 종이 추적이다. · code_execution: not_executed: C 컴파일과 실제 파일 입출력은 수행하지 않았다. 예제 반환값과 내용은 명시한 가정에 대한 종이 추적이다. · learner_review: not_performed

소단원 13.3

EOF와 I/O 실패

읽기가 멈췄다는 사실만으로 정상적으로 파일을 다 읽었다고 말할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 조건문과 반복문
  • int와 unsigned char
  • 반환값 검사

학습 목표

  • EOF와 실제 입력 바이트를 구분한다.
  • 읽기 반환값으로 반복하고 오류 상태를 확인한다.
  • 실패 후 기존 자료를 처리하지 않는 흐름을 설계한다.

EOF는 입력 문자 한 개가 아니다

fgetc는 읽은 unsigned char 값을 int로 변환해 반환하거나, 끝 또는 오류를 나타내는 EOF를 반환한다. 따라서 먼저 int에 받아 EOF와 비교한다. char로 먼저 좁히면 실제 입력 값과 종료 표시를 혼동할 수 있다.

여기서는 8비트 바이트를 쓰는 환경에서 두 바이트 0x41, 0xFF가 든 자체 파일을 가정한다. 두 성공 반환값은 65와 255이며 0xFF도 자료다. EOF는 라이브러리의 음수 정수 상수이므로 숫자 -1을 직접 써서 모든 환경의 표현을 단정하지 않는다.

읽은 뒤 상태를 판정하기

feof는 다음 읽기가 성공할지 예언하는 함수가 아니다. 이미 세워진 끝 표시를 검사한다. 마지막 자료를 성공적으로 읽은 직후에도 아직 끝 표시가 세워지지 않을 수 있어 while (!feof(fp))만으로 본문 실행을 결정하면 실패한 읽기까지 처리하기 쉽다.

while ((ch = fgetc(fp)) != EOF)처럼 성공 반환값에 따라 자료를 처리한다. 반복이 끝난 뒤 ferror로 오류 여부를 확인한다. 정상 끝과 입력 오류는 모두 EOF 반환을 만들 수 있으므로 종료 표시 하나만으로 성공 보고를 하지 않는다.

/* fp는 이미 성공적으로 열린 입력 스트림이다. */
int ch;
while ((ch = fgetc(fp)) != EOF) {
    /* 이 위치에서만 ch를 유효한 입력으로 처리한다. */
}
if (ferror(fp)) {
    /* 읽기 실패를 호출자에게 알린다. */
}

오류를 지우는 것과 원인을 해결하는 것

clearerr는 끝과 오류 표시를 지우지만 파일 권한이나 고장 원인을 해결하는 함수는 아니다. 원인을 확인하지 않은 채 표시만 지우고 무한히 재시도하면 반복 실패할 수 있다. 재시도 횟수와 실패 보고 경로를 따로 정한다.

출력에서도 요청한 요소 수가 쓰였는지, 닫기가 성공했는지 확인한다. fwrite가 전부 반환해도 버퍼를 실제로 내보내는 fclose에서 오류가 발견될 수 있다. fclose가 실패하더라도 스트림은 파일과 분리되므로 같은 포인터로 fclose를 반복하지 않는다.

중간 과정을 따라가는 예제

설명에 정한 두 바이트를 fgetc로 읽는다. 모든 실제 읽기는 성공하고 끝을 지나 읽을 때만 EOF가 반환된다고 가정한다. 처리 횟수와 종료 상태를 추적하라.

  1. 첫 호출은 65를 반환하므로 자료 한 개를 처리한다.
  2. 둘째 호출은 255를 반환하므로 두 번째 자료를 처리한다.
  3. 셋째 호출은 EOF를 반환하므로 자료 처리 본문에 들어가지 않는다.
  4. ferror가 0이고 끝 표시가 세워진 상태를 확인하여 정상 끝으로 해석한다.

자료 처리 횟수는 2회이며 읽기 호출은 3회다. 255를 EOF로 오인하면 한 바이트가 누락된다.

종이와 본문으로 직접 해보기

같은 입력에서 두 번째 읽기가 오류로 EOF를 반환하고 ferror가 비영이라고 가정하라. 성공 처리 수와 보고를 적어라.

힌트 보기

원래 입력에 자료가 있다는 사실과 이번 읽기의 성공은 다르다.

풀이 보기

첫 바이트만 성공 처리하므로 1개다. 둘째는 자료로 처리하지 않고 읽기 오류를 보고한다. 파일을 다 읽었다고 정상 완료를 표시하지 않는다.

오해와 반례

feof가 거짓이면 다음 fgetc는 반드시 성공한다.

feof는 과거에 세워진 끝 표시를 검사한다. 아직 끝을 발견하지 않았거나 다음 읽기에 오류가 생길 수 있다. 실제 호출의 반환값으로 성공 여부를 결정한다.

자기점검

0xFF를 읽은 값을 왜 int에 받는가?

답과 이유 보기

자료 값과 EOF를 함께 구분하기 위해서다.

8비트 예제에서 자료 255와 음수 EOF는 int에서 구별되지만 char 변환은 그 구별을 해칠 수 있다.

EOF 반환은 항상 정상적인 파일 끝인가?

답과 이유 보기

아니다.

입력 오류도 EOF 반환을 만들 수 있으므로 ferror를 확인한다.

clearerr를 호출하면 고장 난 저장 장치가 정상으로 바뀌는가?

답과 이유 보기

아니다.

스트림의 표시를 지우는 일과 실제 실패 원인을 고치는 일은 다르다.

한 단계 더

첫 읽기부터 실패한 경우를 종이에 추가하라. 처리 수 0과 오류 보고를 구분하고, 열린 스트림을 한 번 닫는 경로를 그려 보자. 실제 고장 주입은 수행하지 않았다.

소단원 13.4

저장형식·endianness·버전

같은 정수를 파일에 넣었는데 다른 컴퓨터가 다른 값으로 읽으면 무엇이 빠졌을까?

준비 개념과 학습 목표

준비 개념

  • 배열과 구조체
  • 2진수·16진수
  • 바이트 단위 입출력

학습 목표

  • 메모리 표현과 교환용 파일 형식을 구분한다.
  • 바이트 순서를 명시해 값을 복원한다.
  • 식별자·버전·길이를 검사하는 순서를 설계한다.

메모리를 그대로 저장하는 한계

구조체 전체를 fwrite로 저장하는 방법은 해당 구현의 객체 표현을 기록한다. 멤버 사이 패딩, 자료형 크기, 바이트 순서가 다른 구현에서 같다는 보장은 없다. rb로 읽는 것만으로 이러한 차이가 사라지지는 않는다.

교환용 형식에는 필드 순서, 필드의 비트 수, 숫자의 순서, 문자열 인코딩을 따로 정한다. 이 소단원의 자체 형식은 8비트 바이트를 가정한다. C의 한 바이트가 언제나 8비트라고 일반화하지 않고, 실제 구현에서는 CHAR_BIT 등의 조건을 확인해야 한다.

큰 부분을 먼저 쓸지 작은 부분을 먼저 쓸지

자체 형식에서 부호 없는 16비트 값 0x1234는 십진수 4660이다. big-endian은 높은 부분인 0x12를 먼저, little-endian은 낮은 부분인 0x34를 먼저 둔다. 순서가 다른 바이트 열을 동일한 규칙으로 해석하면 값이 달라진다.

8비트 바이트를 big-endian으로 정한 두 칸 a, b는 a×256+b로 복원한다. 0x01, 0x02는 1×256+2=258이다. unsigned char 두 칸을 정수 연산으로 해석하면, 해당 컴퓨터의 unsigned int 메모리 순서에 기대는 방법과 구별할 수 있다.

버전과 길이를 먼저 확인하기

이 예제의 형식은 식별자 43 53 두 바이트, 버전 01 한 바이트, 값 개수 두 바이트의 big-endian 숫자, 이어서 각 값 두 바이트다. 버전 1만 지원하며 입력 전체 길이가 정확히 5+2×개수인 경우만 받아들인다고 정한다.

파서는 먼저 헤더 5바이트가 있는지, 식별자가 맞는지, 버전이 지원되는지 확인한다. 다음에 개수와 크기 계산의 범위를 검사하고 자료 길이가 맞는지 확인한다. 길이 검사를 통과하기 전에는 배열 밖의 자료를 읽지 않는다. 실제 프로그램은 곱셈 오버플로와 입력 상한도 따로 검사한다.

중간 과정을 따라가는 예제

자체 형식의 바이트 열 43 53 01 00 02 01 02 03 04를 해석하라. 모든 숫자는 16진수 표기이며 입력은 정확히 9바이트다.

  1. 43 53은 약속한 식별자, 01은 지원하는 버전이다.
  2. 개수 00 02는 0×256+2=2다.
  3. 필요한 길이는 헤더 5+2×2=9바이트이므로 실제 길이와 같다.
  4. 값 01 02는 258, 값 03 04는 3×256+4=772다.

버전 1의 값 두 개 258과 772로 읽을 수 있다. 합은 1030이다. 이 형식은 외부 표준이 아니라 자체 교육용 계약이다.

종이와 본문으로 직접 해보기

마지막 04가 빠져 8바이트만 도착한 경우와 버전만 02로 바뀐 9바이트 입력을 각각 처리하라.

힌트 보기

값이 그럴듯한지보다 길이와 지원 버전을 먼저 확인한다.

풀이 보기

첫 입력은 개수 2에 필요한 길이 9보다 1바이트 짧아 거부한다. 둘째는 이 파서가 버전 1만 지원하므로 지원되지 않는 버전으로 거부한다. 버전 2의 형식을 추측해서 읽지 않는다.

오해와 반례

바이너리로 저장한 구조체는 어느 기기에서도 그대로 읽힌다.

바이너리 모드는 스트림 표현의 선택이며 구조체 배치 계약이 아니다. 패딩이나 정수 크기·순서가 달라질 수 있다. 필드를 명시한 형식으로 직렬화하고 길이와 버전을 검사한다.

자기점검

big-endian 바이트 12 34가 뜻하는 십진수는?

답과 이유 보기

4660이다.

0x12=18, 0x34=52이므로 18×256+52=4660이다.

같은 두 바이트를 little-endian으로 읽으면?

답과 이유 보기

13330이다.

52×256+18=13330이며 바이트 순서의 계약이 달라졌다.

헤더가 개수 3을 나타낼 때 이 형식의 필요한 길이는?

답과 이유 보기

11바이트다.

고정 헤더 5바이트에 3×2바이트를 더한다. 이 계산 자체도 실제 코드에서는 범위를 검사한다.

한 단계 더

이 형식에 이름 문자열을 추가하려면 길이의 단위가 바이트인지 문자 수인지, 인코딩이 무엇인지 결정해야 한다. 두 조건과 최대 허용 길이를 자체 계약에 적어 보자. 새 버전의 실제 파서는 작성·실행하지 않았다.
