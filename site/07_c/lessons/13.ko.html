파일 이름을 안다고 해서 바로 그 파일의 내용을 읽을 수 있을까?

+ 모드의 방향 전환은 어느 쪽에서도 같은가?

새 순차 작업은 기존 파일을 r+b로 성공적으로 열어 처음 2바이트를 읽고 같은 위치에서 새 바이트를 쓰려 한다. 입력 뒤 출력에는 파일 위치 변경 함수가 사이에 필요하다. 단, 직전 입력이 파일 끝에 도달한 경우는 예외다. 일반 입력 뒤 fflush만 호출하는 것은 C11에서 이 방향 전환을 해결하지 않으며 최근 동작이 입력인 update stream의 fflush 자체도 정의된 사용이 아니다. 반대 방향인 출력 뒤 입력에는 fflush 또는 위치 변경 함수가 필요하다. 두 방향의 규칙을 대칭으로 외우지 않는다.

새 종이 파일은 추가 널 문자가 없고 위치 변경 가능한 8-bit 바이너리 파일로 정한다. r+b에서 읽기 뒤 성공한 fseek(fp,0L,SEEK_SET)를 수행하면 처음 위치로 옮기면서 다음 출력도 허용한다. a+b에서 성공한 seek로 처음 위치에 가더라도 후속 쓰기는 당시 파일 끝으로 강제된다. r+b와 a+b의 쓰기 목적은 다르다. FILE* 복사 q=p는 새 열린 스트림을 만들지 않고 같은 스트림의 별칭이다. 한 소유 경로에서 한 번 닫은 뒤 두 포인터 모두 다시 사용하지 않는다.

파일을 여는 이유

파일 이름은 저장된 대상을 찾는 데 쓰는 문자열이고, FILE *는 열린 스트림을 다루는 포인터다. 스트림에는 읽는 위치, 버퍼, 끝과 오류를 나타내는 상태 등이 연결된다. 물건의 주소와 물건을 받아 오는 창구가 서로 다른 것처럼, 이름과 열린 스트림도 역할이 다르다.

<stdio.h>를 포함하고 fopen의 반환값을 검사한다. 반환값이 NULL이면 열기에 실패했으므로 그 포인터로 읽거나 닫지 않는다. 실패 원인은 권한이나 존재 여부 등 환경에 따라 다르며, 이름을 보고 성공을 단정할 수 없다.

모드를 먼저 선택하기

r은 기존 텍스트 파일을 읽는다. w는 쓰기 위해 파일을 만들거나 기존 내용을 길이 0으로 지운다. a는 쓰기를 파일 끝에 추가한다. rb와 wb는 바이너리 모드의 읽기와 쓰기다. 이미 자료가 든 파일에 w를 선택하는 일은 내용을 유지한 채 수정하는 일과 다르다.

읽기와 쓰기를 모두 허용하는 + 모드는 방향 전환 규칙도 갖는다. C11 기준으로 출력 뒤 입력에는 fflush 또는 위치 변경이 필요하다. 입력 뒤 출력에는 위치 변경이 필요하지만 직전 입력이 파일 끝에 도달한 경우는 예외다. 이 단원에서는 먼저 단방향 읽기를 익힌다.

텍스트와 바이너리의 경계

텍스트 모드는 줄바꿈 등 외부 표현과 프로그램 안의 문자 표현 사이에서 변환을 할 수 있다. 어떤 환경에서는 r과 rb의 결과가 같더라도 모든 환경에서 같다고 일반화하지 않는다. 이 모드만으로 문자 인코딩이 자동으로 원하는 언어로 바뀌는 것도 아니다.

바이너리 모드는 데이터를 일정한 표현으로 다룰 때 사용하지만, 정수 크기나 저장 순서를 자동으로 통일하지 않는다. C11 초안에는 바이너리 스트림 끝에 구현이 정한 수의 널 문자가 추가될 수 있다는 조건도 있다. 바이트를 주고받는 형식은 별도 계약으로 정해야 한다.

  2. fopen의 결과가 NULL인지 먼저 검사한다.

  3. NULL이면 읽기와 fclose를 하지 않고 실패 경로로 끝낸다. 성공한 스트림만 사용한 뒤 닫는다.

조건을 바꾸어 비교하기

두 방향을 분리한다

r+b의 성공 출력 뒤 입력하려는 경우와 정상 2바이트 입력 뒤 출력하려는 경우를 각각 분석하라.

  1. 출력 뒤 입력에는 성공 여부를 확인한 fflush 또는 위치 변경을 둔다.

  2. EOF를 만나지 않은 입력 뒤 출력에는 위치 변경을 둔다.

같은 한 함수 호출을 두 방향의 만능 해법으로 쓰지 않는다.

비교할 점

최근 동작과 방향의 계약이 다르다.

append의 위치 착각

가상 내용 AB에서 a+b를 성공적으로 열고 처음으로 seek한 뒤 C를 추가한다. 모든 동작이 성공하며 추가 패딩은 없다고 가정한다.

  1. seek가 처음 위치를 설정해도 append 쓰기는 당시 끝으로 강제된다.

  2. 기존 AB 뒤에 C를 붙인다.

가상 끝 내용은 ABC다.

비교할 점

종이와 본문으로 직접 해보기

힌트 보기

풀이 보기

끝에 추가하는 작업은 a, 전체를 새로 쓰는 작업은 w다. 두 작업 모두 열기와 쓰기·닫기 결과를 확인해야 하며 실제 원본을 바꾸는 실습은 여기서 수행하지 않는다.

오해와 반례

FILE *에 파일 경로가 들어 있으므로 값을 직접 복사하면 같은 스트림을 만들 수 있다.

FILE은 라이브러리가 관리하는 객체다. FILE 객체를 복사해 원래 객체 대신 사용해도 된다는 보장은 없다. 열린 스트림의 포인터를 정해진 함수에 전달하고 닫은 뒤에는 다시 사용하지 않는다.

완전 요소 두 개를 읽었다면 세 번째 조각도 값인가?

새 가상 입력은 8-bit 바이트 01,02,03,04,05이며 추가 패딩이 없다. 요청 fread(buf,2,3,fp)는 6바이트 용량을 갖춘 버퍼에 최대 세 요소를 읽는다. 정상 EOF로 다섯 바이트를 읽었다면 완전 요소는 두 개여서 반환은 2다. 마지막 한 바이트는 세 번째 불완전 요소의 일부이며 그 요소 값은 불확정이다. 완전 요소 두 개만 처리한다. 이 모델의 위치는 5지만 읽기 오류가 났다면 C11의 위치 표시가 불확정일 수 있어 반환 요소 수로 실제 위치를 역산하지 않는다.

교환 형식의 두 octet 값을 해석하려면 size=1로 바이트를 모아 길이와 순서를 검증하는 절차를 쓸 수 있다. unsigned char[6]에 읽은 다섯 바이트 중 앞 네 바이트는 두 값 258/772를 구성하지만 마지막 05는 짝이 없어 전체 세 값 요구를 완성하지 못한다. 이는 fread의 size=2 부분 요소를 int 값처럼 사용하는 것과 다르다. 짧은 fwrite 뒤에도 일부 효과가 남을 수 있으므로 단순 재시도나 새 호출 성공만으로 전체 원자 쓰기를 선언하지 않는다.

반환값만큼 처리하기

fread(buf, size, count, fp)는 size 크기의 요소를 최대 count개 읽고, 성공적으로 읽은 요소 수를 돌려준다. size가 1이면 반환값을 읽은 C 바이트 수로 해석할 수 있지만 size가 2이면 반환값 2는 완전한 요소 두 개를 뜻한다.

요청한 수만큼 항상 읽히지는 않는다. 파일 끝이나 읽기 오류를 만나면 짧게 읽을 수 있다. 불완전한 요소는 그 값이 불확정이므로 완전한 요소처럼 해석하지 않는다. 입력 버퍼는 요청한 전체 크기를 담을 용량을 갖춰야 한다.

읽기 위치를 추적하기

이 예제는 8비트 바이트를 쓰고 추가 널 문자가 없는, 위치 변경 가능한 바이너리 파일을 가정한다. 내용이 10, 20, 30, 40, 50이고 시작 위치가 0이라면 크기 1인 요소를 세 개 읽을 때 반환값은 3, 다음 위치는 3이다.

같은 요청을 한 번 더 하면 40과 50만 있어 반환값은 2다. 처리할 내용은 이번에 얻은 두 값이며 이전 버퍼의 세 번째 칸을 새 자료로 처리해서는 안 된다. 짧은 읽기의 이유는 끝과 오류 상태를 확인해 구분한다.

쓰기와 위치 변경도 결과를 검사하기

fwrite 역시 성공한 요소 수를 반환한다. 요청한 수와 다르면 전체 기록이 완료됐다고 보고할 수 없다. fclose에서도 지연된 출력 오류가 나타날 수 있으므로 닫기 결과까지 확인한다. 버퍼에 보낸 것과 저장 장치에 영구 보존된 것은 같은 보장이 아니다.

fseek(fp, 0L, SEEK_SET)가 성공하면 처음으로 돌아가며 파일 끝 표시도 지워진다. 만족시킬 수 없는 위치 변경은 0이 아닌 값을 반환하므로 C 코드에서는 != 0으로 실패를 검사한다. 텍스트 스트림의 0 아닌 offset은 같은 파일에서 성공한 ftell로 얻은 값과 SEEK_SET 조합을 사용하는 제한이 있다.

읽기가 멈췄다는 사실만으로 정상적으로 파일을 다 읽었다고 말할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 조건문과 반복문

  • int와 unsigned char

  • 반환값 검사

학습 목표

  • EOF와 실제 입력 바이트를 구분한다.

  • 읽기 반환값으로 반복하고 오류 상태를 확인한다.

  • 실패 후 기존 자료를 처리하지 않는 흐름을 설계한다.

EOF 표시를 지우면 새 자료가 저절로 생길까?

새 가상 입력에는 한 바이트 41만 있다. 첫 fgetc는 65를 반환하고 다음은 EOF를 반환하여 끝 표시를 세운다. 끝 표시가 이미 있으면 후속 fgetc도 EOF를 반환한다. 오류 없는 스트림에 clearerr를 호출하면 끝/오류 표시는 지워지지만 위치는 여전히 끝이며 자료도 생기지 않는다. 같은 파일 조건에서 다음 읽기는 다시 EOF를 발견한다. 표시 변경과 위치 변경 및 외부 원인 해결을 나눈다.

오류 표시는 과거 오류를 기억하며 성공한 fseek가 끝 표시를 지워도 오류 표시까지 지운다는 규칙은 아니다. rewind는 오류 표시도 지우지만 반환값이 없다. 위치 변경 성공을 보고 싶으면 반환값을 검사할 수 있는 fseek를 고를 수 있다. 출력은 fwrite가 전부 반환해도 fclose에서 실패를 발견할 수 있다. 닫기 실패도 스트림을 파일과 분리하므로 같은 포인터로 재닫지 않는다. 자료 처리 성공 수/읽기 오류/닫기 오류를 서로 다른 보고 필드로 남기는 편이 원인을 보존한다.

먼저 확인할 개념
  • 자료 값과 정수 범위

    8-bit 자료 255와 음수 EOF를 int에 받아 구별한다.

  • 종료 이유와 진행

    읽기 종료를 정상 완료와 오류로 분리한다.

EOF는 입력 문자 한 개가 아니다

fgetc는 읽은 unsigned char 값을 int로 변환해 반환하거나, 끝 또는 오류를 나타내는 EOF를 반환한다. 따라서 먼저 int에 받아 EOF와 비교한다. char로 먼저 좁히면 실제 입력 값과 종료 표시를 혼동할 수 있다.

여기서는 8비트 바이트를 쓰는 환경에서 두 바이트 0x41, 0xFF가 든 자체 파일을 가정한다. 두 성공 반환값은 65와 255이며 0xFF도 자료다. EOF는 라이브러리의 음수 정수 상수이므로 숫자 -1을 직접 써서 모든 환경의 표현을 단정하지 않는다.

읽은 뒤 상태를 판정하기

feof는 다음 읽기가 성공할지 예언하는 함수가 아니다. 이미 세워진 끝 표시를 검사한다. 마지막 자료를 성공적으로 읽은 직후에도 아직 끝 표시가 세워지지 않을 수 있어 while (!feof(fp))만으로 본문 실행을 결정하면 실패한 읽기까지 처리하기 쉽다.

while ((ch = fgetc(fp)) != EOF)처럼 성공 반환값에 따라 자료를 처리한다. 반복이 끝난 뒤 ferror로 오류 여부를 확인한다. 정상 끝과 입력 오류는 모두 EOF 반환을 만들 수 있으므로 종료 표시 하나만으로 성공 보고를 하지 않는다.

/* fp는 이미 성공적으로 열린 입력 스트림이다. */
int ch;
while ((ch = fgetc(fp)) != EOF) {
    /* 이 위치에서만 ch를 유효한 입력으로 처리한다. */
}
if (ferror(fp)) {
    /* 읽기 실패를 호출자에게 알린다. */
}

오류를 지우는 것과 원인을 해결하는 것

clearerr는 끝과 오류 표시를 지우지만 파일 권한이나 고장 원인을 해결하는 함수는 아니다. 원인을 확인하지 않은 채 표시만 지우고 무한히 재시도하면 반복 실패할 수 있다. 재시도 횟수와 실패 보고 경로를 따로 정한다.

출력에서도 요청한 요소 수가 쓰였는지, 닫기가 성공했는지 확인한다. fwrite가 전부 반환해도 버퍼를 실제로 내보내는 fclose에서 오류가 발견될 수 있다. fclose가 실패하더라도 스트림은 파일과 분리되므로 같은 포인터로 fclose를 반복하지 않는다.

헤더와 길이가 맞으면 호출자 자료를 바로 바꿔도 될까?

base의 CS 버전 1 형식에 새 응용 제한을 덧붙인다. 개수는 0–3, 각 16-bit 값은 0–1000이며 합은 충분한 범위의 연산형에서 계산한다. 저장한 호출자 결과는 count=1, value=9로 시작한다. 파서는 지역 후보에 전체 입력을 검증한 뒤 한 번 커밋한다. 식별자/버전/개수/정확 길이가 맞아도 값 범위가 틀리면 원래 결과를 보존한다. 실제 C 연산형은 값 65535 및 합 3000을 표현할 수 있도록 선택하고 검사한다.

새 입력 43 53 01 00 02 00 02 03 E9는 길이 9/개수 2지만 값 2와 1001이므로 거절한다. 첫 값 2를 바로 호출자 배열에 쓰는 파서는 실패 보존을 깨뜨린다. 반면 43 53 01 00 02 00 02 03 E8은 2와 1000으로 성공하여 합은 1002다. 지원하지 않는 버전은 길이가 그럴듯해도 거절한다. 읽기에서 완성한 지역 후보가 있어도 정한 전체 작업 계약이 닫기 성공까지 요구하면 닫기 실패에서 커밋하지 않는다. 이로써 호출자 결과를 보존할 수 있지만 입력 파일 소비나 저장 장치 지속성을 되돌렸다는 뜻은 아니다.

메모리를 그대로 저장하는 한계

구조체 전체를 fwrite로 저장하는 방법은 해당 구현의 객체 표현을 기록한다. 멤버 사이 패딩, 자료형 크기, 바이트 순서가 다른 구현에서 같다는 보장은 없다. rb로 읽는 것만으로 이러한 차이가 사라지지는 않는다.

교환용 형식에는 필드 순서, 필드의 비트 수, 숫자의 순서, 문자열 인코딩을 따로 정한다. 이 소단원의 자체 형식은 8비트 바이트를 가정한다. C의 한 바이트가 언제나 8비트라고 일반화하지 않고, 실제 구현에서는 CHAR_BIT 등의 조건을 확인해야 한다.

큰 부분을 먼저 쓸지 작은 부분을 먼저 쓸지

자체 형식에서 부호 없는 16비트 값 0x1234는 십진수 4660이다. big-endian은 높은 부분인 0x12를 먼저, little-endian은 낮은 부분인 0x34를 먼저 둔다. 순서가 다른 바이트 열을 동일한 규칙으로 해석하면 값이 달라진다.

8비트 바이트를 big-endian으로 정한 두 칸 a, b는 a×256+b로 복원한다. 0x01, 0x02는 1×256+2=258이다. unsigned char 두 칸을 정수 연산으로 해석하면, 해당 컴퓨터의 unsigned int 메모리 순서에 기대는 방법과 구별할 수 있다.

버전과 길이를 먼저 확인하기

이 예제의 형식은 식별자 43 53 두 바이트, 버전 01 한 바이트, 값 개수 두 바이트의 big-endian 숫자, 이어서 각 값 두 바이트다. 버전 1만 지원하며 입력 전체 길이가 정확히 5+2×개수인 경우만 받아들인다고 정한다.

파서는 먼저 헤더 5바이트가 있는지, 식별자가 맞는지, 버전이 지원되는지 확인한다. 다음에 개수와 크기 계산의 범위를 검사하고 자료 길이가 맞는지 확인한다. 길이 검사를 통과하기 전에는 배열 밖의 자료를 읽지 않는다. 실제 프로그램은 곱셈 오버플로와 입력 상한도 따로 검사한다.

중간 과정을 따라가는 예제

자체 형식의 바이트 열 43 53 01 00 02 01 02 03 04를 해석하라. 모든 숫자는 16진수 표기이며 입력은 정확히 9바이트다.

  1. 43 53은 약속한 식별자, 01은 지원하는 버전이다.

  2. 개수 00 02는 0×256+2=2다.

  3. 필요한 길이는 헤더 5+2×2=9바이트이므로 실제 길이와 같다.

  4. 값 01 02는 258, 값 03 04는 3×256+4=772다.

후보 완성과 전체 성공·수명 종료를 나누고 방향 전환의 두 규칙을 따로 확인한다.

풀이와 답 확인

  1. 첫 입력은 개수 2/정확 길이 9이지만 값 2와 1001이라 둘째 값의 허용 상한 1000을 넘어 거절한다.

  2. 첫 입력은 호출자 count=1/value=9를 보존한다. 열린 스트림은 한 번 닫고 정리 오류가 있다면 원래 검증 실패와 따로 보고한다.

  3. 두 번째 독립 입력은 2와 1000/합 1002인 후보를 만들지만 닫기 실패 때 전체 커밋하지 않아 count=1/value=9를 유지한다. 닫기는 1회이며 재닫지 않는다.

  4. EOF 미도달 입력 뒤 출력에는 위치 변경이 필요하다. 최근 입력 update stream의 fflush는 그 대체가 아니다.
