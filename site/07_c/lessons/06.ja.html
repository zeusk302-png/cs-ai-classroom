小節 6.1

NUL 終端と長さ

六つの枠に文字を入れたのに、なぜ strlen は 1 を返すのだろうか？

準備する概念と学習目標

準備する概念

  • char 配列は文字を保存する枠からなるオブジェクトである。char a[6] は六つの char を持ち、有効な添字は 0～5 である。C の sizeof(char) は 1 だが、そのバイトが常に 8 ビットだとは仮定しない。
  • '\0' は整数値 0 のナル文字である。文字 '0' やポインタの NULL とは役割が異なる。文字列の終わりを示す 0 が配列内になければならない。
  • 自己確認：[A,0,B] の最初の 0 より前の内容は 1 個である。0 自体まで確認すれば読み取りは 2 個、配列全体の保存枠は 3 個となる。文字列の長さ・検査のために読む枠数・保存容量は異なる量である。

学習目標

  • C 文字列の終わりと strlen が数える長さを定義する。
  • 保存容量・論理的な長さ・最初の NUL より後のデータを区別する。
  • 上限付き探索のアクセス安全性・終了・失敗時の返却を説明する。

最初の NUL が決める文字列

C11 では、文字列は最初のナル文字まで、その文字を含めて連続する文字の列である。一方、文字列の長さはそのナル文字より前のバイト数である。char a[6]={'A','\0','B','C','\0','\0'} で a が指す文字列の長さは 1、配列の容量は 6 である。後ろに B と C があっても、strlen(a) は最初の 0 より後を文字列の内容として数えない。

strlen には終端の 0 を見つけられる有効な文字列が必要である。0 のない配列に strlen を呼び出し、長さを得てから検査する方法は、その時点ですでに契約を破る可能性がある。長さ 0 の空文字列は最初の枠が 0 の文字列であり、保存枠がないことや NULL ポインタとは異なる。1 枠の char empty[1]={0} は空文字列を保存できる。

長さを先に信用しない検査

下の bounded_length の呼び出し契約では、s が生存している読み取り可能な char を cap 個提供し、out が書き込み可能な size_t オブジェクトを指す。cap=0 なら s を読まないため、この独自関数では s=NULL も許せるが、out は契約上依然として有効でなければならない。cap>0 で s=NULL なら契約違反である。返却値が 1 の場合だけ *out に新しい長さを書き、0 は提供された範囲に終端文字がなかったことを示す。

条件 i<cap && s[i]!='\0' の && は、左側が真のときだけ右側を評価する。したがって i==cap では s[cap] を読まない。各反復の前には 0≤i≤cap であり、それまでの i 個の枠がすべて 0 でないという不変条件が成り立つ。終了時には見つかった 0 の位置を返すか、i==cap の失敗となる。実際と異なる cap を渡すと、この検査では実オブジェクトの境界までは保証できない。

バイト数と人が数える文字数

strlen は符号化された文字数や画面上の文字数を解釈しない。たとえば 8 ビットのバイトによる UTF-8 という追加条件の下で、U+AC00 の 가 は EA B0 80 の 3 バイトとして保存される。終端の 00 を加えると少なくとも 4 枠が必要で、長さは 3 である。基本的な C の char 文字列が必ず UTF-8 だとは述べない。下のコードは実行文字集合の基本文字 A,B,C,X,Y,Z だけを使う。

外部ファイルではデータの途中に 0 がある場合もある。このようなバイナリデータには、実際のバイト長を別途渡す契約が適しており、strlen で長さを復元することはできない。文字の復号・正規化・表示文字の区切りは別の層である。下の raw は 3 枠のバイナリ内容で、C 文字列ではないため strlen(raw) や %s では読まない。

#include <stdio.h>
#include <stddef.h>
#include <string.h>
static int bounded_length(const char *s, size_t cap, size_t *out) {
    size_t i = 0;
    while (i < cap && s[i] != '\0') {
        ++i;
    }
    if (i == cap) return 0;
    *out = i;
    return 1;
}
int main(void) {
    char a[6] = {'A', '\0', 'B', 'C', '\0', '\0'};
    char raw[3] = {'X', 'Y', 'Z'};
    size_t len = 99;
    int ok = bounded_length(a, sizeof a, &len);
    printf("%zu %zu %d %zu\n", sizeof a, strlen(a), ok, len);
    ok = bounded_length(raw, sizeof raw, &len);
    printf("%d %zu\n", ok, len);
    return 0;
}

途中の過程をたどる例題

完全な例で a と raw の保存内容・返却値・len の変化を追跡する。通常の出力成功を仮定し、実際には実行しない。

  1. a の容量は 6、最初の 0 の添字は 1 である。sizeof a=6、strlen(a)=1 であり、後ろの枠は長さに含まれない。
  2. bounded_length(a,6,&len) は i=0 で A を確認し、i=1 で止まる。返却値 1、len=1 なので、最初の行の引数は 6,1,1,1 となる。
  3. raw の 3 枠 X,Y,Z に 0 はない。i=0,1,2 で増加し、i=3 では左側の条件が偽になるため 4 番目の枠は読まない。
  4. 失敗の返却値 0 の場合、*out への代入は行われず、以前の len=1 が残る。返却値を無視すると、raw の長さが 1 だと誤解するおそれがある。

予想 stdout は、最初の行が 6 1 1 1、次の行が 0 1 である。失敗時に残る len は raw の文字列の長さを意味しない。

紙と本文で試してみよう

5 枠の [P,Q,0,R,0] と 4 枠の [P,Q,R,S] を描く。各配列を正確な cap とともに bounded_length に渡し、out の初期値を 77 とする。返却値と out、最後に読んだ添字を求めよう。

ヒントを見る

0 自体を読むことも 1 回の検査である。失敗時には out への代入はなく、添字 cap は読まない。

解答を見る

最初の配列は添字 0,1,2 を読み、返却値は 1、out=2 となる。次の配列は添字 0～3 を読み、i=4 で止まり、返却値 0、out=77 を保つ。cap=4 や以前の out の値が文字列の長さだという保証はない。

よくある誤解と反例

文字配列であれば strlen が容量を安全に教えてくれる。

a[6] の strlen は 1 で、sizeof a は 6 である。0 のない raw[3] に strlen を呼び出すと、終端探索がオブジェクトの外へ出る可能性があり、未定義動作となる。UB の出力を固定した数値として予測しない。

理解を確かめる

char e[1]={0}; の長さと容量は？

答えと理由を見る

長さ 0、容量 1。

終端の 0 は保存枠を使うが、長さには含まれない。

途中に 0 のある 8 バイトのパケット全体の長さを strlen で求められるか？

答えと理由を見る

一般にはできない。

strlen は最初の 0 より後を数えないため、パケットの契約で定める長さを別途保持する。

cap=3、i=3 のとき、コードは s[3] を読むか？

答えと理由を見る

読まない。

&& の左側 i<cap が偽なので、右側は評価されない。

もう一歩先へ

発展の証明：反復開始時に 0≤i≤cap であり、j<i を満たすすべての提供された枠 s[j] が 0 でないと仮定する。条件が真なら i<cap なので現在の枠は有効で、これも 0 ではない。増加後も不変条件が保たれる。自然数の変量 cap−i は反復ごとに 1 減るため有限回で終了する。i<cap で終われば s[i]=0 であり、それより前に 0 がないため最初の終端位置である。i=cap なら全範囲に 0 がない。size_t の i は増加直前に i<cap なので最大でも cap であり、cap=SIZE_MAX のモデルでも最後の増加でオーバーフローしない。ただし、それだけの読み取り可能なオブジェクトが実際に存在するという契約は別途必要である。

小節 6.2

文字配列とリテラル

同じ "cat" から作った a と p は、なぜ変更できる範囲が違うのだろうか？

準備する概念と学習目標

準備する概念

  • 配列は実際の要素を持つオブジェクトで、ポインタはオブジェクトの位置を指す値である。const char *p は p を通じた char の変更を許さない型であり、p 自体への再代入禁止とは異なる。
  • 初期化は新しいオブジェクトの初期内容を定める。char a[]="cat" はポインタを保存する宣言ではなく文字配列を作る。char *p="cat" は文字列リテラルの最初の文字を指すポインタを作る。
  • 自己確認：'A' は文字定数で、"A" は終端の 0 を持つ文字列リテラルである。C では両者の型と保存内容が異なる。

学習目標

  • 文字配列の初期化と文字列リテラルを区別する。
  • 終端枠の有無と sizeof が測るオブジェクトを説明する。
  • 寿命・const を通じたアクセス・リテラル変更の UB を区別する。

初期化で独立した配列を作る

C11 の通常の文字列リテラル "cat" は基本文字 c,a,t の後に 0 を含む char 配列として実装され、静的記憶域期間を持つ。char a[]="cat" は、この 4 文字を初期値とする別の配列オブジェクト a を作る。下の a は main ブロックの自動記憶域期間中に生存し、a[0]='b' によって "bat" に変更できる。同じテキストのリテラルを変更しているのではない。

char b[6]="cat" なら [c,a,t,0,0,0] となる。文字配列の初期化では、サイズをちょうど 3 にした char raw[3]="cat" も C11 で許される。ただし終端文字の場所がなく、[c,a,t] だけを持つ。この有効な初期化によって raw が C 文字列になるわけではない。コードでは各要素を %c で読み、%s や strlen には渡さない。

リテラルの型と変更禁止は別の規則

C の通常のリテラル配列の要素型は char だが、その配列を変更しようとすると未定義動作になる。C++ のリテラル型の説明を C11 にそのまま移さない。C で char *q="cat" が許されても、q[0]='b' は安全な変更ではない。const char *p を使うと、意図した読み取り専用アクセスが型に表れ、誤りを減らせる。

const char *p の const は、指す文字を p を通して変更できないことを示す。p="dog" のように別のリテラルを指す代入は可能である。ポインタ自体への再代入も禁止するには char *const のように別の位置の const が必要になる。同じリテラルの保存配列が統合されるかどうかは規定されていないため、ポインタのアドレス一致でテキストの同等性を判断しない。

sizeof とオブジェクトの寿命

sizeof a は 4 個の char の配列のサイズ 4 である。sizeof p はポインタオブジェクトのサイズであり、文字列の長さや終端用の空間を意味せず、特定の数値に固定しない。strlen(a) は現在の最初の 0 より前の 3 バイトを数えるため 3 である。文字定数 'A' の型は C では int だが、"A" は 2 枠の char 配列である。sizeof('A') は sizeof(int) であり、1 とは仮定しない。

リテラルには静的記憶域期間があるため、それを指すポインタを関数の外へ返すこと自体は寿命の点では可能である。一方、関数内の自動 char tmp[]="cat" を指すポインタを返すと、関数終了後にはその配列の寿命が終わる。書き込み可能性と十分な容量だけでなく、対象オブジェクトがまだ生存していることも契約に含める必要がある。下のプログラムでは、すべての自動配列を生存中の main 内だけで読む。

#include <stdio.h>
#include <string.h>
int main(void) {
    char a[] = "cat";
    const char *p = "cat";
    char raw[3] = "cat";
    a[0] = 'b';
    printf("%zu %zu %s %s\n", sizeof a, strlen(a), a, p);
    printf("%zu %c%c%c\n", sizeof raw, raw[0], raw[1], raw[2]);
    return 0;
}

途中の過程をたどる例題

完全な例の a,p,raw を別々のオブジェクト表に書き、a[0] の変更後の予想出力 2 行を求める。

  1. a は [c,a,t,0] の 4 枠、p は静的リテラル [c,a,t,0] の最初の枠を指す。raw は [c,a,t] の 3 枠である。
  2. a[0]='b' は、別の変更可能な配列の最初の枠だけを変える。p が読むリテラルの c は変わらない。
  3. sizeof a=4、strlen(a)=3 である。二つの %s は終端を持つ a と p だけを読み、bat と cat を表示する。
  4. sizeof raw=3 である。三つの %c は raw の各枠を個別に読むため、終端の 0 を探す操作ではなく cat を出力する。

予想 stdout は 1 行目が 4 3 bat cat、2 行目が 3 cat である。raw を %s に変えた例を、安全な実行例として扱わない。

紙と本文で試してみよう

char x[5]="Hi"; char y[2]="Hi"; const char *z="Hi"; の内容を描く。sizeof と文字列の長さを述べられる対象を区別し、x[0]='B'、z="Bye"、z[0]='B' を判定する。

ヒントを見る

Hi の基本文字 2 個の後に終端の 0 を加える。明示したサイズが足りない場合、char 配列の初期化では終端枠が省かれることがある。

解答を見る

x=[H,i,0,0,0]、sizeof x=5、strlen(x)=2 である。y=[H,i]、sizeof y=2 で、strlen(y) の事前条件は満たされない。sizeof z はポインタのサイズで、strlen(z)=2 である。x[0] の変更と z の再代入は可能である。z[0] の変更は const アクセス規則に違反するため診断が必要であり、const を取り除いてリテラルを変更しても UB になる。

よくある誤解と反例

C のリテラルの要素型は char なので変更でき、sizeof ポインタで文字列の保存サイズも分かる。

型の説明とリテラルの変更禁止は別の規則である。char *p="cat" の p[0] の変更は UB で、sizeof p はポインタオブジェクトのサイズである。char a[]="cat" という独立した配列の sizeof a=4 と a[0] の変更は、この反例と区別する。

理解を確かめる

char s[3]="cat"; は C11 では宣言そのものが必ず誤りか？

答えと理由を見る

いいえ。終端の 0 を含めない 3 枠の初期化が許される。

場所がなければリテラルの終端枠が初期化から省かれるため、文字列操作の安全性は別の問題である。

const char *p では p="dog" という代入も禁止されるか？

答えと理由を見る

いいえ。

この宣言の const は指す char に付いており、ポインタオブジェクト p 自体が const なのではない。

関数の自動 char local[]="ok" のアドレスを返してから使ってよいか？

答えと理由を見る

使ってはいけない。

関数のブロックを出ると自動オブジェクトの寿命が終わる。終端の 0 があるだけでは有効なアクセスにならない。

発展：リテラル "AB\0CD" は基本文字 A,B,0,C,D と付加された終端の 0 を含む 6 個の char の配列である。char s[] の初期値にすると sizeof s=6 だが strlen(s)=2 である。最初の文字列より後の C,D も配列の内容として存在する。したがって、すべての文字列リテラルを内部の 0 がない一つの可視テキストと一般化できない。リテラルの記憶領域が統合される可能性も考慮し、s の要素の比較でテキストを判断する必要がある。二つのポインタが同じか異なるかという事実だけでは、別々の宣言の内容全体を一般に証明できない。

小節 6.3

標準文字列関数

長さの引数を持つ strncpy は、なぜ文字列の終端を保証しないのだろうか？

準備する概念と学習目標

準備する概念

  • コピーは、元の内容をコピー先の保存枠に書く操作である。元の読み取り可能範囲、コピー先の書き込み可能範囲、オブジェクトの寿命をそれぞれ確認する。返されるポインタは容量検査の代わりにはならない。
  • 二つの区間が一部の枠を共有すると重なりがある。同じ配列内の [0,5) と [1,6) は重なる。別々の生存する配列 bytes と copy は別のオブジェクトである。
  • 自己確認：[A,B,0] を文字列としてコピーするには A,B だけでなく 0 を含む 3 枠が必要である。[X,0,Y] という 3 バイトをコピーするときは、内部の 0 より後の Y も保持する。

学習目標

  • strcpy と strncpy の終端・パディング・容量の契約を比較する。
  • memcpy と memmove の明示的なバイト数・重なりの条件を説明する。
  • 関数の選択と別途の境界検査を組み合わせ、例を追跡する。

文字列を終端枠までコピーする

strcpy(dst,src) は有効な元の文字列を終端の 0 までコピーする。元の長さが L なら、コピー先には少なくとも L+1 枠が必要であり、区間が重なると UB になる。この関数には容量の引数がなく、自動でサイズを検査したり新しい領域を確保したりしない。コードの dst[5] と "cat" では 4 枠のコピーなので十分である。長さの測定からコピー先への書き込みまでに、別の実行主体が内容を変えられるなら、長さの測定 1 回だけでは安全性を証明できない。

strncpy(dst,src,n) は元の最初の 0 より後の文字をコピーしないが、元の文字列が n より短いと、コピー先全体の n 枠を埋めるまで 0 を書き足す。逆に最初の n 個に 0 がなければ、n 個だけをコピーし、終端を追加しない。したがって書き込み可能なコピー先 n 枠と、契約上有効な元の読み取り範囲が必要である。重なりも許されない。下の raw[3] の結果 W,X,Y は終端のないデータであり、文字列出力には使わない。

明示したバイト数をコピーする

memcpy(dst,src,n) は文字列の終わりを探さず、char 単位のバイトを n 個コピーする。内部の 0 より後もコピーし、終端の 0 を自動で追加しない。コピー先への n 枠の書き込みと元からの n 枠の読み取りが有効であり、重なりがないことが必要である。n=0 を許す標準文字列ライブラリ関数でも、明示的な例外がなければポインタ引数は有効でなければならないという C11 の規則がある。そのため一般の memcpy(NULL,NULL,0) を安全な慣用句として教えない。

memmove も同じ n 枠の要求を持つが、重なるコピーも、一時的な重ならない配列を経由したかのように扱う。実装が必ず一時配列を割り当てるという意味ではない。コードでは "ABCD" の 5 枠 A,B,C,D,0 を右へ 1 枠動かし、[A,A,B,C,D,0] にする。元の [0,5) とコピー先の [1,6) はどちらも 6 枠の配列内である。関数が重なりを許しても、オブジェクトの外への書き込みは解決しない。

関数名ではなく契約を選ぶ

コードの pad[5] は strncpy により Q,0,0,0,0 となる。raw は W,X,Y、copy は X,0,Y である。この三つは読み方が異なる。pad は終端を持つ文字列として読めるが、raw の 3 文字と copy の内部の 0 より後の Y は、長さを別途把握して要素ごとに読む必要がある。検査なしで関数名に「安全」という期待を付けると、終端なし・パディングの費用・重なりの問題を見落とす。

書き込む数と必要な読み取り数を呼び出しごとに紙に書くと、関数を比較できる。strcpy は最初の 0 まで、strncpy は 0 に出会うまで最大 n 個を元から探索して n 枠を書き、memcpy/memmove は明示した n 枠を扱う。この本文は、コピー先の拡張・メモリ割り当て失敗への対応・並行アクセスの安全性を提供するとは述べない。完全な例では十分な固定配列と生存している元のデータだけを使い、UB の変形例の出力を解答にはしない。

#include <stdio.h>
#include <string.h>
int main(void) {
    char dst[5];
    char raw[3];
    char pad[5];
    char overlap[6] = "ABCD";
    const char bytes[3] = {'X', '\0', 'Y'};
    char copy[3];
    strcpy(dst, "cat");
    strncpy(raw, "WXYZ", sizeof raw);
    strncpy(pad, "Q", sizeof pad);
    memmove(overlap + 1, overlap, 5);
    memcpy(copy, bytes, sizeof copy);
    printf("%s %c%c%c\n", dst, raw[0], raw[1], raw[2]);
    printf("%d %d %d %d\n", pad[1] == 0, pad[2] == 0,
           pad[3] == 0, pad[4] == 0);
    printf("%s %c %d %c\n", overlap, copy[0], copy[1] == 0, copy[2]);
    return 0;
}

途中の過程をたどる例題

完全な例の五つのコピーを順に追跡し、終端のない raw の出力方法が安全である理由を説明する。

  1. strcpy の後、dst は c,a,t,0 を含む。strncpy による raw は最初の W,X,Y の 3 枠だけを書き、終端の 0 はない。最初の行では dst を %s、raw を三つの %c で表示する。
  2. strncpy による pad は Q の 1 枠の後、4 枠を 0 で埋める。四つの比較 pad[k]==0 はすべて真を表す int の 1 を返す。
  3. memmove は以前の元データ A,B,C,D,0 を保持したかのように位置 1～5 に置く。overlap 全体は A,A,B,C,D,0 なので、文字列は AABCD となる。
  4. memcpy による copy は X,0,Y の 3 枠すべてをコピーする。%c・比較・%c によって X,1,Y を表示するため、最初の 0 で止まる文字列出力とは異なる。

予想 stdout は cat WXY / 1 1 1 1 / AABCD X 1 Y の 3 行である。スラッシュは行の区切りを表し、実際の出力文字ではない。実際の C 実行は行っていない。

紙と本文で試してみよう

char a[5]="ABCD"; に対する memmove(a,a+1,4) の結果を描く。別の char b[4] に strncpy(b,"Hi",4) を行ったときの 4 枠も書こう。重なるコピーを memcpy に変えても同じ出力になると言えるか？

ヒントを見る

元の a+1 の 4 枠は B,C,D,0 である。strncpy は元が短い場合、n 枠まで 0 でパディングする。

解答を見る

a は [B,C,D,0,0] となり、文字列は BCD である。以前の最後の 0 は上書きしない。b は [H,i,0,0] である。a の元とコピー先は重なるため memcpy に変えると UB となり、BCD という出力予測を解答にはできない。

よくある誤解と反例

strncpy は常に NUL を追加し、memmove は領域も自動確保する。

raw[3] に "WXYZ" を n=3 でコピーすると WXY だけになり、NUL はない。memmove(a+1,a,5) で a が 5 枠しかなければ、コピー先の最後の枠はオブジェクトの外になる。重なりへの対応は保存容量の検査ではない。

理解を確かめる

strncpy(d,"Q",5) は何枠を書くか？

答えと理由を見る

5 枠。

Q の後の終端と追加パディングを合わせて 0 を 4 枠書き、n 枠を埋める。

memcpy は最初の 0 より後のバイトもコピーするか？

答えと理由を見る

明示した n の範囲内ならコピーする。

文字列の終端を探さないバイトコピー関数だからである。

重なる区間の memcpy がうまく動いたという観察によって、標準の契約が成立するか？

答えと理由を見る

いいえ。

重なりは UB の条件であり、一つの実装での観察によって C11 の保証は生まれない。

もう一歩先へ

発展：重なった範囲を右へ 1 枠移すとき、単純に左から代入すると a[1]=a[0] の後の a[2]=a[1] はすでに変更された A をコピーし、元の B を失う。元の末尾から右のコピー先へ移せば、まだ必要な元データを上書きしないという不変条件により、この方向のコピーを証明できる。逆に左への移動には前から後ろへの順が適している。memmove は、この方向選択を自分で実装しなくても、元の n バイトと同じ結果を契約として提供する。strcpy の前に L+1≤cap を確認するには、加算のオーバーフローを避ける L<cap と、有効で安定した元の文字列の両方を要求する。動的割り当てのサイズとして L+1 を計算するときは、まず L==SIZE_MAX を拒否しなければならない。

小節 6.4

バッファ容量と切り詰め処理

5 枠のバッファに planet を出力したとき、返却値は保存した 4 文字だろうか、必要な 6 文字だろうか？

準備する概念と学習目標

準備する概念

  • バッファ容量 cap は、実際に書き込み可能な char の枠数である。文字列の内容に L 枠、終端に 1 枠が必要である。文字列を保存するには cap>0 かつ L<cap でなければならない。
  • 書式付き出力の %s は有効な元の文字列を読む。snprintf の n はコピー先への書き込み上限であり、元の有効性や読み取り境界を代わりに検査するものではない。
  • 自己確認：5 枠を描き、最後の 1 枠を終端の 0 用に残すと、内容は最大 4 枠になる。希望する 6 枠と、実際に保存する 4 枠を別の色で示そう。

学習目標

  • snprintf が返す必要な長さと実際の保存量を区別する。
  • 負のエラー・n=0・n=1・正確な切り詰め境界を判定する。
  • 切り詰め方針と符号化・書式文字列・重なりの条件を説明する。

snprintf の領域契約

C11 の snprintf(s,n,format,...) は n>0 の通常の出力で最大 n−1 枠の内容を書き、末尾に 0 を付ける。コピー先は実際に n 枠を書き込めなければならない。n=0 なら何も書かず、この特別な場合には s=NULL も許される。n=1 で内容が空でなければ、保存する内容はなく、最初の枠に 0 だけが残る。文字列を自動拡張する関数ではない。

正常な返却値 r は、十分なバッファがあれば書かれたはずの内容の長さで、終端の 0 を含まない。符号化エラーでは負になる。r≥0 を確認した後、r<n なら全内容を保存し、r≥n なら切り詰めと判定する。n=0 では r=0 でも 0<0 は偽であり、コピー先に空文字列を書いたとは言えない。下の基本文字列の例では、必要な長さが int の範囲内で通常の書式出力が可能という条件の下で予測する。

エラーと切り詰めを別に処理する

5 枠の out に "planet" を出力すると、正常な返却値は r=6、保存内容は p,l,a,n,0 である。strlen(out)=4 であり、返却値 6 をコピーされた枠数として配列を読んではいけない。固定した例では sizeof out=5 を int で表現できるため、(int)sizeof out との比較は安全である。一般の任意の size_t 容量を int に縮小する方法を、この条件なしでは使わない。

一般の関数ではまず r<0 を処理し、非負の r と cap を値が保持される型で比較する。たとえば <stdint.h> の uintmax_t に両者を変換すれば、size_t の値と非負の int の値を表現でき、(uintmax_t)r < (uintmax_t)cap を使える。負の値を先に除かず符号なしの値に変換すると、エラーが大きな長さのように見える。負の結果の後でバッファを正常な完成文字列として読まず、エラー処理方針に進む。

保存の安全性と内容の意味

切り詰めた文字列を受け入れるか、入力を拒否するか、検証後により大きな領域で再試行するかはプログラムの方針である。識別子やファイルパスを黙って切り詰めると、異なる元データが同じ接頭辞になり得るため、失敗として扱う方針が適切な場合もある。2 回呼び出して必要な長さを得てから割り当てるなら、正の余裕領域、長さ+1 のオーバーフロー、割り当て失敗、2 回の間の元データと書式引数の安定性も別途検証する。

終端の 0 があっても、8 ビットの UTF-8 シーケンスの途中で切ると不正なテキストになり得る。出力上限はバイト保存の規則であって、Unicode の文字境界保証やセキュリティ方針ではない。元の入力をそのまま書式文字列にせず、snprintf(out,cap,"%s",input) のように固定書式を使う。この方法でも input 文字列の有効性は必要である。snprintf(buf,cap,"%s",buf) のように元とコピー先が重なる呼び出しは C11 で UB なので、下では別のリテラルを元データに使う。

#include <stdio.h>
#include <string.h>
int main(void) {
    char out[5];
    int r = snprintf(out, sizeof out, "%s", "planet");
    if (r < 0) {
        puts("encoding error");
        return 1;
    }
    printf("%d %zu %s\n", r, strlen(out), out);
    if (r >= (int)sizeof out) puts("truncated");
    else puts("complete");
    int needed = snprintf(NULL, 0, "%s", "planet");
    if (needed < 0) return 1;
    printf("%d\n", needed);
    return 0;
}

途中の過程をたどる例題

out[5] の成功経路と NULL,0 による測定呼び出しを紙上で追跡する。実際のコンパイル・出力は行わず、負のエラー経路を実行による解答とは述べない。

  1. 元の planet は基本文字 6 個と終端の 0 を持つ。十分なコピー先なら内容 6 枠を書くため、正常な r=6 となる。
  2. n=5 なので先頭の 4 文字 plan と終端の 0 が保存される。r<0 の検査は偽で、strlen(out)=4 となる。
  3. sizeof out=5 は int で表現できる。6≥5 なので切り詰め分岐に進み、truncated を表示する。内容を出力できることと、全内容の保存成功は異なる。
  4. snprintf(NULL,0,...) はコピー先に書かず、正常な必要長 6 を返す。配列の長さの測定と出力内容の長さの測定を混同しない。

通常の成功経路での予想 stdout は 6 4 plan / truncated / 6 の 3 行である。切り詰めが検出された。負の符号化エラー経路の発生や出力を実際に観察したわけではない。

紙と本文で試してみよう

基本文字の "Hello" を別のコピー先に snprintf で出力する。容量 0,1,5,6 について正常な返却値・保存内容・全内容の保存可否を表にする。n=0 のコピー先は NULL でもよく、他の場合は該当サイズの有効な配列とする。

ヒントを見る

必要な内容長 5 は容量を変えても同じである。n>0 のとき内容は最大 n−1 枠であり、完全保存の条件は 5<n である。

解答を見る

すべて正常な返却値は 5 である。n=0 は書き込まず、保存文字列はなく、完全保存条件は偽である。n=1 は [0] の空文字列で、切り詰めである。n=5 は Hell と 0 で、切り詰めである。n=6 は Hello と 0 で、完全保存である。n=5 の返却値==容量は、成功完了ではなく切り詰めの境界である。

よくある誤解と反例

NUL を付ける snprintf なら、切り詰め・セキュリティ・Unicode まで全部安全である。

out[5] が plan で終端されていても、planet は完全には保存されていない。符号化された多バイト文字の途中での切り詰めは有効な UTF-8 を壊すことがあり、識別子の接頭辞の衝突も別の問題である。実領域より大きい n や、元とコピー先が重なる呼び出しも、関数名だけでは正当化できない。

理解を確かめる

正常な r=5,n=5 なら全内容を保存したか？

答えと理由を見る

いいえ。切り詰めである。

終端枠が必要なので、完全保存条件は厳密な r<n である。

snprintf(NULL,0,...) が正常な長さ 6 を返したとき、NULL に終端の 0 を書いたか？

答えと理由を見る

いいえ。何も書かない。

n=0 は書かずに必要な長さだけを計算できる明示的な例外である。

r<0 を検査せず、size_t に変換して必要な長さとして使ってよいか？

答えと理由を見る

使ってはいけない。

負のエラーが符号なしの大きな値に変換され得るため、先にエラー分岐を分離する必要がある。

発展の証明：正常な返却値 L≥0、n>0 のとき、保存する内容の長さは min(L,n−1)、終端枠を含む書き込み数は min(L,n−1)+1≤n である。全内容が保たれるには L≤n−1、つまり L<n が必要で、n=0 の無書き込みの場合と区別する。容量 5 の切り詰め方針は planet と plank をともに plan にし得るため、元データから保存結果への写像は単射ではない。識別子の一意性を保つには、切り詰めを拒否するか衝突を別途扱う。L+1 を割り当てサイズに使う際は L が size_t で表現可能か、加算がオーバーフローしないかを確認する。成功した測定呼び出しは、次の出力まで元データが不変であることや、領域の確保成功を保証しない。ここで保存する内容の長さは、snprintf が生成する出力文字数を意味する。内部 NUL がない場合だけ、その数は strlen が数える長さと一致する。たとえば有効な 2 枠の配列に snprintf(buf,2,"%c",0) を正常に行うと、返却値は 1、buf は [0,0] となり、strlen(buf) は 0 である。この反例は契約に基づく紙上追跡であり、実行していない。
