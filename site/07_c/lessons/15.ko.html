배열의 부분 범위를 전달하면 함수가 원래 길이도 알까?

base의 count_at_least를 재사용하되 새 호출은 배열 a={2,5,5,9}의 부분 범위 a+1,n=2,minimum=5다. 실제 배열 수명과 두 읽기 가능한 int가 존재하므로 결과는 2다. 같은 a+1에 n=4를 붙이면 원래 네 원소 배열이라는 사실만으로 안전하지 않다. 포인터 뒤 읽을 수 있는 원소는 세 개다. 공용 헤더는 타입을 공유하지만 길이의 진실과 수명을 확인해 주는 실행 검사기는 아니다.

새 계약은 n=0일 때 NULL과 one-past를 허용하되 해당 포인터를 역참조하거나 산술하지 않고 개수 0을 반환한다. 이 계약은 일반 라이브러리 전체의 NULL 허용 규칙이 아니다. size_t count는 최대 n이므로 값의 합산 overflow를 만들지 않는다. >=를 >로 바꾼 구현은 같은 prototype과 안전한 메모리 접근을 유지해도 경계 의미를 바꾼다. 타입·읽기 범위·관찰할 값의 의미를 다른 검토 항목으로 둔다.

먼저 확인할 개념
  • 배열 길이와 포인터

    부분 범위의 실제 길이는 포인터 자체의 sizeof로 얻지 않는다.

  • const 접근 경로

    const가 잠금이나 불변 snapshot을 만들어 주지 않는다.

헤더에는 공유할 선언

자체 count_at_least 함수는 배열에서 기준 이상인 값의 개수를 반환한다. count.h에는 선언을, count.c에는 구현을 둔다. 구현과 호출하는 쪽이 같은 헤더를 include하면 인자와 반환 자료형의 약속을 함께 확인할 수 있다.

include guard는 같은 translation unit에서 헤더 내용을 반복 처리하지 않도록 조건부 전처리를 한다. 서로 다른 구현 파일에 외부 함수의 정의를 여러 번 만들지 않게 하는 자동 해결책은 아니다. 이 예제의 외부 함수 정의는 count.c에 한 번 둔다.

길이와 수명도 함수의 약속

계약은 n > 0이면 values가 읽을 수 있는 int 원소 n개를 가리키고 그 수명이 호출 동안 유지된다는 것이다. n = 0이면 아무 원소도 읽지 않고 0을 반환하므로 NULL도 전달할 수 있다. 함수가 전달 포인터의 실제 할당 크기를 자동으로 알아내는 것은 아니다.

반환 개수는 size_t이고 값 자체의 덧셈은 하지 않는다. 각 원소는 >= minimum으로 검사하므로 기준과 같은 값도 센다. 이 코드에서 const는 이 포인터를 통해 원소를 바꾸지 않겠다는 인터페이스이며 다른 경로의 동시 변경을 막는 잠금이 아니다.

각 소스를 object로, 그다음 연결

GCC의 -c는 소스를 object로 만들고 링크하지 않는다. main.c와 count.c를 각각 컴파일한 뒤 main.o와 count.o를 실행 파일로 연결하는 단계를 설명할 수 있다. 헤더는 이 예제에서 독립 실행 파일이 아니라 두 소스가 포함하는 선언이다.

GCC를 준비한 환경의 제안 명령은 gcc -std=c11 -Wall -Wextra -c main.c, gcc -std=c11 -Wall -Wextra -c count.c, gcc main.o count.o -o demo다. Windows의 실행 파일 이름과 실행 방법은 설치 도구에 맞춰 확인한다. 이 단원에서는 명령을 실제 실행하지 않았다.

중간 과정을 따라가는 예제

다음 세 파일을 읽고 배열 {2,5,5,9}에서 minimum 5의 출력과 count.o를 링크에서 빠뜨렸을 때의 문제를 설명하라.

  1. count.h: 

    #ifndef COUNT_H
#define COUNT_H
#include <stddef.h>
size_t count_at_least(const int *values, size_t n, int minimum);
#endif

  2. count.c: 

    #include "count.h"
size_t count_at_least(const int *values, size_t n, int minimum) {
    size_t count = 0;
    for (size_t i = 0; i < n; ++i) {
        if (values[i] >= minimum) {
            ++count;
        }
    }
    return count;
}

  3. main.c: 

    #include <stdio.h>
#include "count.h"
int main(void) {
    int values[] = {2, 5, 5, 9};
    size_t n = sizeof values / sizeof values[0];
    printf("%zu\n", count_at_least(values, n, 5));
    return 0;
}

  4. i = 0에서는 2라 제외하고 i = 1, 2, 3에서는 5, 5, 9라 센다. count는 0→0→1→2→3이다. 이 sizeof 길이 계산은 실제 배열이 있는 main에서 수행한다.

  5. 선언은 호출의 약속이며 함수 본체를 대신하지 않는다. count.o가 빠진 일반 링크에서는 count_at_least의 정의를 찾지 못할 수 있다. 정확한 오류 문구는 linker 환경에 따라 확인한다.

정상 계약에서 예상 출력은 3이다. 선언만 포함한 main.o로는 구현의 연결을 대신할 수 없다.

학습 목표

  • 공유 헤더의 의존 간선을 적는다.

디렉터리가 바뀔 때마다 모든 object도 새로 만들까?

새 가상 GNU Make 규칙은 main.o: main.c count.h | build와 count.o: count.c count.h | build이며 demo는 두 object에 일반 의존한다. build는 출력 폴더를 먼저 준비하는 order-only prerequisite다. 일반 의존은 먼저 준비될 순서와 target 갱신 여부를 모두 연결하지만 order-only는 먼저 준비하는 순서만 연결한다. 폴더의 변경 시각이 파일 추가마다 바뀐다고 기존 object까지 모두 재생성할 이유가 되지 않게 한다.

자체 시작 시각은 main.c=8,count.c=9,count.h=7,main.o=10,count.o=10,demo=12,build=20이다. 모든 target은 존재하고 성공한 recipe만 새 시각을 얻는 종이 모형이다. build만 30이 되어도 object는 유지한다. 반면 count.h=31이면 일반 의존 두 object를 시각 32에 재생성하고 demo를 33에 재연결한다. count.h를 | 오른쪽에 잘못 옮기면 필요한 헤더 변경을 놓친다. 옵션/도구 변경은 이 시각 규칙에 별도로 연결한 정책이 없으면 자동 감지한다고 하지 않는다.

  • 처음 선택된 설정

    헤더와 설정이 object에 준 영향은 의존성에 반영해야 한다.

명령 묶음보다 의존 관계

Makefile 규칙은 target: prerequisites와 수행할 recipe로 구성한다. target은 생성할 object나 실행 파일일 수 있고 prerequisite는 그 생성에 쓰는 입력이다. recipe의 기본 시작은 탭이므로 겉보기 비슷한 공백과 구별한다.

이 자체 예제에서 demo는 main.o와 count.o에 의존하고 main.o는 main.c와 count.h, count.o는 count.c와 count.h에 의존한다. 헤더를 의존 목록에서 빠뜨리면 그 변경이 어느 object에 영향을 주는지 규칙에 전달하지 못한다.

변경 시각 모형을 종이에서 실행하기

다음 계산은 target이 없거나 명시된 입력 시각보다 오래되면 다시 만드는 자체 시각 모형이다. 명령은 성공하고 새 생성물 시각은 현재 입력보다 크다고 가정한다. 내용 해시 비교나 실제 make 실행 로그가 아니다.

이 모형에서 count.c 변경은 count.o 재생성으로 이어지고 그 뒤 demo도 재생성한다. count.h 변경은 두 object에 연결된다. 입력 파일이 바뀌지 않고 명령 옵션만 달라진 경우도 자동 감지된다고 가정하지 않고 별도 rebuild 정책을 정한다.

의존성과 재현 조건을 보존하기

공유 헤더뿐 아니라 생성 코드, 외부 라이브러리와 도구 버전도 결과에 영향을 줄 수 있다. 작은 규칙에 모든 프로젝트의 의존성을 담았다고 주장하지 않는다. 컴파일러, 옵션, 경로와 환경을 기록하고 필요한 입력을 규칙 또는 별도 빌드 정책으로 연결한다.

프로그램이 이상할 때 값을 따라가는 도구와 오류를 탐지하는 도구는 무엇이 다를까?

준비 개념과 학습 목표

준비 개념

  • 루프와 인덱스

  • 호출 흐름

  • 메모리 경계

학습 목표

  • 중단점과 값 추적의 목적을 설명한다.

  • ASan과 UBSan의 탐지 범위를 구별한다.

메모리 진단 무보고인데 개수가 틀리면 통과인가?

새 시험 대상은 >=를 >로 바꾼 count 함수다. 읽기 범위는 여전히 i<n이므로 {5},기준 5의 값 0은 메모리 접근이 정의돼도 기능 요구의 기대값 1과 다르다. ASan의 대상 메모리 오류와 기능 assertion은 다른 문제를 본다. 도구 무보고를 기대 출력의 증거로 쓰지 않는다. 실제 debugger·sanitizer는 여기서 실행하지 않았고 주소/stack trace도 만들지 않는다.

새 가상 추적은 i<=n인 결함에서 길이 4의 i=4를 최초 허용 범위 밖 후보로 찾는다. 그러나 실제 실행을 이미 UB 지점까지 이어가 여러 숫자를 정상 기록처럼 적지 않는다. sanitizer 계획에는 코드 버전·compile/link 옵션·runtime·입력·실제 보고를 묶어야 한다. ASan은 계측과 runtime이며 최종 연결에도 flag를 둔다. UBSan의 recover/trap 선택에 따라 보고 후 흐름이 다르므로 보고 개수를 모든 오류 개수로 읽지 않는다.

먼저 확인할 개념
  • 경계 이전 검증

    첫 잘못된 접근 이전 상태를 계약과 대조한다.

  • 범위 밖 연산

    UB 뒤 출력 숫자로 정상 계약을 만들지 않는다.

멈춘 위치에서 질문하기

debugger는 지정한 위치에서 멈추고 값과 호출 흐름을 살펴보는 도구다. GDB의 중단점은 함수나 줄에 지정할 수 있고 조건이 참일 때만 멈추도록 설정할 수도 있다. 도구를 켜기 전에 기대되는 i, n과 읽기 범위를 적으면 관찰 목적이 분명해진다.

자체 count_at_least의 루프 경계를 실수로 i <= n으로 바꿨다고 하자. n = 4에서 i = 4도 본문에 들어가므로 유효 원소 0부터 3까지를 넘는다. 종이 추적은 최초 잘못된 접근을 찾지만 실제 debugger의 정지 위치나 출력 주소는 확인하지 않았다.

실행 중 오류를 보고하는 계측

AddressSanitizer는 컴파일 계측과 runtime으로 경계 밖 접근, 해제 후 사용, 잘못된 free 등의 메모리 오류를 탐지한다. 지원 환경과 설정의 차이를 확인하며 보고한 실행 경로를 조사한다. 여기서는 실제 ASan 실행 보고를 만들어 제시하지 않는다.

UndefinedBehaviorSanitizer는 signed overflow, 잘못된 shift, 일부 경계와 null 또는 alignment 오류 등 선택한 검사를 수행한다. 각 도구가 모든 종류의 오류를 동일하게 잡는 것은 아니다. UBSan의 보고 후 계속 또는 종료 동작도 선택한 설정에 따라 다를 수 있다.

정상 결과의 증명과 관찰은 다르다

진단을 위해 환경을 준비했다면 예를 들어 clang의 -g와 -fsanitize=address 또는 -fsanitize=undefined를 컴파일·링크 단계에 맞춰 적용한다. 공식 도구 문서의 지원 플랫폼과 runtime 요구를 확인한다. 이 제안은 현재 작업 환경에서 설치·빌드·실행을 완료했다는 뜻이 아니다.

오류가 보고되지 않은 한 번의 실행은 미실행 입력과 모든 요구사항을 증명하지 않는다. 작은 정수와 문자열 경계, 빈 입력, 실제 자원 실패 조건을 추가한다. 도구가 보고한 주소를 안다고 비밀 자료를 출력하거나 위험한 외부 입력을 무조건 실행하는 방식으로 확장하지 않는다.

미실행

각 행은 다른 증거다. 계획한 도구 이름을 적었다고 실제 실행 증거가 생기지 않는다. 잘못된 메모리 접근은 특정 출력 예상 문제로 쓰지 않는다.

중간 과정을 따라가는 예제

길이 4 배열의 올바른 조건 i < n과 오류 조건 i <= n을 i = 0부터 손으로 추적하라. 최초 잘못된 인덱스를 찾고 n = 0도 비교하라.

  1. 정상 조건에서는 i = 0, 1, 2, 3만 읽고 i = 4에서 종료한다.

  2. 오류 조건에서는 i = 4에서도 참이라 values[4]를 읽으려 한다. 이 접근은 배열의 한 칸 뒤이므로 허용된 원소 읽기가 아니다.

  3. n = 0의 정상 루프는 아무것도 읽지 않는다. 오류 조건은 초기 0 <= 0이 참이므로 values[0]을 읽으려 한다.

  4. debugger에서는 i와 n 및 호출 계약을 조사할 계획을 세우고 sanitizer에서는 해당 경로의 실제 보고를 확인할 계획을 세운다. 여기서는 두 도구를 실행하지 않았다.

길이 4에서 오류 조건의 최초 잘못된 인덱스는 4다. 빈 범위에서도 오류 조건은 인덱스 0에 접근하려 한다. UB의 결과 출력은 예측하지 않는다.

계획한 실패 시험을 실제 통과 수에 넣어도 될까?

새 순차 작업은 지역 자원 A와 B를 둘 다 얻어 읽기만 수행한 뒤 모두 정리하고 반환하는 함수다. 외부에 소유권을 넘기지 않고 malloc 실패만 가상으로 정한다. A 실패면 살아 있는 블록 0개, B 실패면 A만 살아 있으므로 A 한 번 정리, 둘 다 성공하면 B/A 각각 한 번 정리다. free 호출 횟수와 실제 살아 있던 블록 해제 개수는 다르다. NULL 초기화 후 공통 cleanup에서 free(b),free(a)를 호출하면 호출 수는 매 경로 2이지만 실제 블록 해제는 0/1/2다.

새 시험 계획에는 정상 함수값 2개, 빈 입력 1개, 비교 경계 1개, A 실패 1개, B 실패 1개로 총 6개가 있다. 실제로 수행했다는 가상 장부에는 앞 4개만 실행됐고 3개 통과/비교 경계 1개 실패라고 적혀 있다. 실행 비율 4/6, 수행한 시험 통과율 3/4, 계획 대비 통과 3/6을 나눠 읽는다. 여기서 그 장부 자체도 합성 사례이며 실제 C 시험 기록이 아니다. 남은 자원 실패 2개를 미수행으로 두고 기능 수정 후 회귀와 실패 경로를 실제 검증할 계획을 세운다.

먼저 확인할 개념
  • 공통 cleanup의 자원 상태

    NULL 초기화와 확보된 블록의 정리를 구별한다.

  • 해제 이전 사용 종료

    별칭을 자동 갱신한다고 하지 않고 수명 종료 경로를 정한다.

크기 계산 전에 한계 확인

n개의 int를 할당하려면 n * sizeof(int)의 크기를 사용한다. 곱셈의 자료형 범위를 넘어 작은 값으로 바뀌지 않도록 n > SIZE_MAX / sizeof(int) 같은 사전 조건을 검토한다. 이 검사는 포인터의 실제 유효 범위까지 자동으로 검증하는 것은 아니다.

malloc은 실패하면 null 포인터를 반환할 수 있고 반환 공간은 읽기 전에 필요한 값을 초기화해야 한다. n = 0은 이번 도구에서 별도로 처리하도록 계약을 정하면 zero-size 할당의 구현별 선택에 기대지 않을 수 있다. 현재 예제의 main은 고정 배열을 쓰므로 실제 동적 할당 코드를 추가한 것이 아니다.

해제는 이름 하나의 변경이 아니다

free는 할당한 공간을 해제한다. free(NULL)은 아무 동작을 하지 않지만 이미 해제한 공간을 다시 free하는 것은 허용되지 않는다. p와 q가 같은 할당을 가리키면 free(p) 뒤 q를 통해 원소를 읽는 경로도 수명이 끝난 공간에 접근한다.

p = NULL은 p의 값만 바꾸고 q를 자동 갱신하지 않는다. 소유자는 누구이며 어떤 참조가 언제까지 유효한지 계약을 적는다. 이 단원은 포인터의 해제 후 주소 숫자를 출력해 예측하는 활동을 하지 않고 유효성 관계를 종이에서 추적한다.

실패 경로도 종료 경로

첫 자원 A를 확보한 뒤 둘째 B 확보에 실패하면 B를 사용하지 않고 A를 정리한 뒤 실패를 반환하는 흐름을 설계한다. 모든 경로에서 필요한 자원을 한 번 정리하는지 본다. 이미 확보하지 못한 자원과 이전에 해제한 자원을 구별한다.

시험표에는 n = 0, n = 1, 최소값과 같은 값, 전체 제외, 정상 배열, 크기 한계와 할당 실패를 넣을 수 있다. 할당 실패를 실제 재현하지 않았다면 가상 흐름으로 표시한다. 논리적으로 올바른 값 계산과 메모리 수명·실제 오류 관찰을 함께 확인한다.

free(NULL)은 아무 동작이 없지만 호출 자체는 장부에 존재한다. 표의 성공 경로도 사용 종료 후 자원을 전부 해제하는 계약이며 소유권 이전 함수에 그대로 복제하지 않는다.

중간 과정을 따라가는 예제

자체 모형에서 sizeof(int)=4바이트, n=4이며 할당 A가 성공했다. p와 q는 A의 별칭이다. 초기화 후 free(p)를 하고 p=NULL로 바꿨다. 필요한 바이트 수와 이후 q를 통한 원소 읽기 또는 free(q)의 유효성을 판정하라.

  1. 필요 크기는 4 × 4 = 16바이트다. 실제 sizeof(int)는 환경에서 확인해야 하며 여기서는 4라고 가정했다.

  2. free(p)에서 A의 수명이 종료된다. p와 q가 가리키던 할당은 같은 A다.

  3. p = NULL은 p만 바꾸므로 q를 통한 원소 읽기는 유효 수명 계약을 어긴다. free(q)도 이미 해제된 공간을 다시 해제하는 경로라 허용되지 않는다.

  4. 이 결과에 대해 특정 출력, 충돌 또는 sanitizer 보고를 보장하지 않는다. 잘못된 경로를 실행하지 않고 소유·수명 모형을 검토했다.

가정 크기는 16바이트다. A 해제 후 q를 통해 원소를 읽거나 같은 A를 다시 해제하면 안 된다. p를 NULL로 바꾸는 것만으로 q를 보호하지 못한다.

조건을 바꾸어 비교하기

호출 둘과 해제 하나

A 성공/B 실패에서 공통 cleanup의 두 free를 추적하라.

  1. b는 NULL이므로 free(b)는 블록을 해제하지 않는다.

  2. a는 A를 가리켜 free(a)가 A를 한 번 해제한다.

호출 2회/블록 해제 1개다.

비교할 점

호출 수만 세어 double-free라고 판정하지 않는다.

서로 다른 분모

합성 장부의 계획 6/수행 4/통과 3을 분류하라.

  1. 수행 비율은 4/6이다.

  2. 수행 통과율은 3/4이고 계획 대비 통과는 3/6이다.

힌트 보기

같은 자원의 확보·해제 횟수를 표에 적는다.

풀이 보기

첫 경우는 A의 정리를 놓쳐 자원 누수 위험이 남는다. 둘째는 같은 할당을 두 번 해제하는 잘못된 경로다. 성공한 자원의 소유권과 모든 종료 경로를 연결하여 한 번 정리한다. 실제 실패 주입은 미수행이다.

오해와 반례

메모리를 free한 뒤 포인터 하나를 NULL로 만들면 모든 별칭이 안전해진다.

다른 참조는 자동 변경되지 않는다. 사용 가능한 기간과 해제 책임을 공유하고 수명이 끝난 공간의 재사용 경로를 막아야 한다.
