소단원 14.1

정규식과 match

입력 속에 코드가 들어 있는 것과 입력 전체가 코드인 것은 어떻게 구별할까?

준비 개념과 학습 목표

준비 개념

  • 문자열

  • None과 조건문

  • 딕셔너리

학습 목표

  • search·match·fullmatch의 범위를 구별한다.

  • 간단한 패턴과 이름 붙인 그룹을 읽는다.

  • 실패 결과를 검사한 뒤 그룹을 꺼낸다.

끝에 개행이 붙은 입력도 $가 있으면 전체 검사인가?

기본 플래그에서 패턴 ^[A-Z]{2}-[0-9]{2}$를 match로 AB-07 뒤 개행 하나인 문자열에 적용하면 코드 부분이 일치할 수 있다. $는 문자열 끝뿐 아니라 마지막 개행 직전에도 맞는다. fullmatch를 이용해 입력 전체가 코드인지 요구하면 남은 개행 때문에 실패한다. 경계 표기의 실제 API 계약을 먼저 읽자.

외부 입력을 strip한 뒤 검사하는 것은 공백/개행을 허용해 정규화하는 새 정책이다. 원본을 그대로 제한하는 요구와 다르므로 어느 문자열을 검증하고 그 뒤 무엇을 사용할지 고정한다. raw 문자열 접두사는 Python 문자열 처리의 편의를 주며 자동 신뢰 검증 장치가 아니다.

str 패턴의 \d는 기본적으로 Unicode 십진 숫자를 포함한다. ASCII 계약이면 [0-9] 또는 명시 ASCII 플래그를 선택한다. 모양 검사와 숫자 값 1..99 검사는 별도 단계이며 00은 모양을 통과해도 값에서 거부한다. 아래는 짧은 입력만 손예측하며 정규식 성능/서비스는 시험하지 않는다.

먼저 확인할 개념
  • 문자와 바이트 경계

    문자 입력의 규칙과 외부 바이트 해독을 나눈다.

  • 구문과 실행 오류

    불일치 None을 정상 결과로 처리하고 그룹 접근을 보호한다.

문자열 전체인지 일부인지

정규식은 문자 모양의 규칙을 표현한다. search는 어디에든 맞는 부분이 있는지, match는 시작 위치에서 맞는지, fullmatch는 전체가 맞는지 확인한다. 사용자 입력 전체를 특정 형식으로 제한하려면 일부 일치만 확인해서는 부족하다.

일치하면 Match 객체, 일치하지 않으면 None이 나온다. None에서 group을 호출하면 실패하므로 먼저 검사한다. 여기의 match는 re 모듈의 함수 이름이며 구조적 패턴 매칭의 match 문과 별개다.

읽을 수 있는 작은 패턴

[A-Z]{2}는 ASCII 대문자 두 글자, [0-9]{2}는 숫자 두 글자다. 가운데 -는 이 위치에서 그대로 하이픈 문자다. Python 문자열의 역슬래시 처리가 규칙과 섞이지 않도록 보통 r 접두사의 raw 문자열로 적는다.

숫자의 범위가 ASCII인지 다른 유니코드 숫자도 허용하는지 요구를 정한다. 이 예제는 [0-9]를 써서 ０ 같은 전각 숫자를 허용하지 않는다. 모양 검사 후 숫자를 int로 바꾸거나 범위를 확인하는 의미 검사는 별도다.

그룹은 추출할 부분에 이름을 붙인다

(?P<label>...)처럼 이름을 붙이면 groupdict로 그 부분들의 딕셔너리를 얻는다. number의 '07'은 문자열이며 int로 변환하면 7이다. 앞자리 0을 보존할지 목적에 따라 결정한다.

아래를 regex_demo.py에 저장해 python regex_demo.py로 실행할 수 있다. 성공과 실패를 같이 보며 입력을 AB-07x로 바꾸면 전체 검사에서 실패한다. 정규식 하나로 모든 복잡한 문서의 구조나 의미가 검증된다고 일반화하지 않는다.

import re
pattern = re.compile(r'(?P<label>[A-Z]{2})-(?P<number>[0-9]{2})')
match = pattern.fullmatch('AB-07')
print(match.groupdict() if match else None)

예제 패턴으로 AB-07, AB-07x, prefix AB-07, AB-７７을 fullmatch한다. 같은 패턴을 prefix AB-07에 search하면?

  1. AB-07은 전체가 맞고 label='AB', number='07'을 얻는다.

  2. 나머지 셋은 뒤 문자, 앞 문자 또는 전각 숫자가 규칙 밖이므로 None이다.

  3. search는 prefix AB-07의 코드 부분을 찾으며 시작·끝 인덱스는 (7,12)다. 끝 12는 포함하지 않는다.

fullmatch 성공은 첫 입력 하나다. search의 부분 일치는 전체 입력 허용과 다르다.

날짜·수학·random

2월 28일부터 3월 1일까지는 언제나 하루일까?

준비 개념과 학습 목표

준비 개념

  • 모듈 import

  • 실수 오차

  • 객체와 메서드

학습 목표

  • date와 timedelta로 달력 차이를 계산한다.

  • 실수 비교의 허용 오차를 설명한다.

  • 재현 가능한 의사난수와 보안 난수를 구별한다.

달력 모양·실제 날짜·근사값·난수 상태는 각각 무엇을 검증할까?

YYYY-MM-DD 모양은 실제 달력의 존재를 판정하지 못한다. 2023-02-29는 모양이 맞지만 날짜 생성에서 ValueError다. date.fromisoformat은 20240229 같은 기본 형식도 받을 수 있으므로 정확한 하이픈 정책은 먼저 모양을 검사하고 그 뒤 달력 값을 만든다.

isclose는 동등관계의 대체가 아니다. rel_tol=0, abs_tol=1이라는 자체 수학 비교에서 0과 0.75, 0.75와 1.5는 가깝지만 0과 1.5는 가깝지 않다. 근사 일치를 연쇄해 하나의 동일 키처럼 묶으면 요구가 달라진다. 0 비교에는 상대 허용치만으로 작은 비영 값을 허용하지 못한다.

Random 상태를 S에서 저장한 뒤 같은 알고리즘 호출을 같은 순서로 재생해야 대응하는 위치를 비교할 수 있다. 결과를 r1,r2,r3이라고 이름 붙이면 상태 복원 뒤 하나를 버리고 두 번 읽은 결과는 r2,r3이다. 숫자가 우연히 같을 수도 있지만 위치 대응은 바뀐다. 인증 토큰에는 이 재현 목적 생성기를 쓰지 않는다.

먼저 확인할 개념
  • 오류와 입력 조건

    달력 ValueError와 정상 날짜를 구별한다.

  • 상태를 가진 호출

    난수 호출 순서와 상태 공유를 추적한다.

문자열을 달력 값으로 바꾸기

날짜 문자열은 글자이며 date 객체는 달력의 연·월·일을 표현한다. date.fromisoformat으로 변환하고 두 date를 빼면 timedelta가 된다. 윤년과 월 길이를 반영하므로 날짜 문자열의 마지막 숫자만 빼서는 안 된다.

date는 날짜만 표현하며 시간대나 시각을 담지 않는다. datetime의 시간대와 실제 경과 시간을 다룰 때는 별도 조건이 필요하다. 또한 fromisoformat은 하이픈 형식만 허용하는 전용 검사기가 아니므로 엄격한 입력 형식은 추가로 확인한다.

수학 함수와 비교의 조건

math는 제곱근 같은 함수와 isclose 비교를 제공한다. 이진 실수에서 0.1+0.2가 0.3과 정확히 같지 않을 수 있으므로 문제에 맞는 상대·절대 허용 오차를 정한다.

isclose의 기본 허용치는 모든 문제의 정답 기준이 아니다. 0과의 비교에서는 작은 양수를 허용하려면 적절한 abs_tol이 필요할 수 있다. 돈을 정확한 십진 단위로 처리하는 문제와 측정 오차 문제도 구별한다.

의사난수의 재현과 용도

random.Random으로 독립 생성기를 만들고 seed 또는 상태를 기록하면 같은 환경의 실험을 재현하는 데 도움이 된다. randrange(1,7)은 1부터 6까지 정수 중 하나를 고르며 7은 포함하지 않는다.

의사난수는 비밀번호나 인증 토큰에 쓰는 보안 난수 용도가 아니다. 그런 용도는 secrets 등 적절한 API를 사용한다. 여러 호출의 순서나 Python 버전이 달라지면 일부 알고리즘의 결과열은 바뀔 수 있어 seed만으로 모든 환경 동일성을 보장하지 않는다.

소단원 14.3

argparse·logging

옵션 입력과 프로그램이 남기는 기록을 왜 print 한 줄로 모두 처리하지 않을까?

준비 개념과 학습 목표

준비 개념

  • 문자열과 int

  • 조건문

  • 함수 인자

학습 목표

  • 명령행 인자 변환과 허용 범위를 정의한다.

  • logging의 수준과 출력 조건을 구별한다.

  • 입력 오류와 진단 기록을 나누어 다룬다.

DEBUG가 숨겨져도 메시지 인수 계산은 실행될까?

logger.debug("value=%s", compute())에서 함수 인수 compute()는 호출 전에 계산된다. logger가 DEBUG를 버려도 그 함수의 비용/부작용은 이미 발생할 수 있다. 포매팅 지연과 인수 표현 계산 지연은 다르다. 효과를 피할 목적이면 isEnabledFor(DEBUG)를 먼저 검사하는 경로를 설계한다.

argparse의 type=int는 명령행 문자열 변환이며 모든 경로의 업무 검증기가 아니다. 문자열 default="3"는 변환될 수 있지만 비문자 default=3.5는 그대로다. 원래 count 계약이 정확 int이며 범위 1..5라면 파싱 뒤 의미 검증을 따로 유지해야 한다.

type=bool은 문자열 "False"를 False라는 의미로 해석하지 않고 비어 있지 않아서 True로 바꾼다. 존재 여부 플래그는 store_true, 값 선택은 명시 허용값과 변환으로 정한다. 로그의 경로/수준은 결과 출력과 별도이며 비밀 입력 원문을 남기지 않는다.

먼저 확인할 개념
  • 함수 인자와 호출

    인수 표현 평가와 호출 내부 필터를 순서로 나눈다.

  • 오류 처리 경계

    변환 실패와 의미 조건 실패를 구별한다.

명령행 문자열을 규칙으로 바꾸기

argparse의 ArgumentParser에 옵션을 등록하고 parse_args로 읽는다. --count의 type=int는 입력 문자열을 정수로 바꾸고 choices는 허용값을 제한한다. 변환에 성공해도 서비스에 맞는 값인지 확인해야 한다.

parse_args에 직접 문자열 리스트를 전달하면 실제 명령행 없이 파서의 핵심을 연습할 수 있다. 기본 호출은 sys.argv에서 읽는다. 잘못된 입력은 사용법과 오류를 내며 종료할 수 있으므로 정상 결과가 나온 것처럼 처리하지 않는다.

플래그는 켜짐·꺼짐을 표현한다

action='store_true'는 옵션이 있을 때 True, 없을 때 기본 False가 되는 플래그다. '--verbose' 뒤에 'True'라는 문자열을 반드시 붙이는 문법이 아니다. 이름과 기본값을 사용법에서 설명한다.

count를 1–5로 제한하면 --count 0은 정수 변환에는 성공하지만 choices 조건에 실패한다. 범위 제한과 자료형 변환의 실패를 구별하면 오류 안내를 이해하기 쉽다.

기록 수준과 정보 범위

logging은 DEBUG·INFO·WARNING 등 기록 수준과 처리기를 구성한다. 기본 수준은 WARNING이므로 INFO를 호출했어도 보이지 않을 수 있다. 로그가 안 보인다고 해당 코드가 실행되지 않았다고 단정하지 않는다.

진단에 필요한 상태를 남기되 비밀번호나 외부 입력 전체를 무조건 기록하지 않는다. 이 예제는 INFO 수준에 count 숫자만 남기고 파일 대신 메모리 스트림으로 확인한다. 기록의 유무가 결과의 정확성이나 감사의 완전성을 자동 입증하지 않는다.

텍스트 뜻과 불일치

행은 서로 다른 파서 설정의 독립 비교다. default/type 처리 사실을 업무 값 범위나 모든 예외 포장으로 확대하지 않는다.

중간 과정을 따라가는 예제

--count는 int, choices=range(1,6), default=2다. --verbose는 store_true다. ['--count','3','--verbose']를 파싱하고 INFO 수준 기록에 DEBUG와 INFO를 각각 호출한다.

  1. 파싱 결과 count=3, verbose=True다.

  2. INFO 수준에서 DEBUG의 hidden 메시지는 나타나지 않는다.

  3. format='%(levelname)s:%(message)s'로 INFO의 count 값을 기록하면 INFO:count=3이다.

실제 Python 3.12.7 파서와 StringIO 로그에서 3 True 및 INFO:count=3을 확인했다. 외부 명령행·파일 로그·운영 서비스는 실행하지 않았다.

compute는 가상 사건 횟수를 1 늘리고 4를 반환한다. DEBUG 비활성에서 debug의 인수로 호출한다.

  1. 인수 compute가 먼저 수행된다.

  2. DEBUG 메시지는 필터될 수 있다.

  3. 사건 횟수는 1 증가한다.

출력 없음과 부작용 없음은 다르다.

표준 라이브러리가 읽어 준 데이터라면 내용까지 믿어도 될까?

준비 개념과 학습 목표

준비 개념

  • JSON

  • 예외

  • 입력 검증

학습 목표

  • 구문 변환과 의미 검증을 구별한다.

  • 입력 크기·형식·자료형·범위를 점검한다.

  • 신뢰하지 않는 객체 역직렬화의 위험을 설명한다.

JSON에서 같은 키가 두 번 나왔다면 사전 검사만으로 발견할까?

기본 json.loads는 {"count":2,"count":5}의 마지막 값을 남긴다. 파싱 뒤 키 집합이 count 하나인지 확인하면 중복했던 이력은 이미 사라졌다. 중복 이름을 거부하는 새 계약이면 object_pairs_hook에서 순서 있는 쌍을 받아 dict로 축약하기 전에 검사해야 한다.

키 집합 일치와 값의 정확 타입/범위는 계속 필요하다. true는 bool이고 3.0은 float이며 숫자처럼 보여도 정확 int 계약과 다르다. NaN 같은 기본 허용 확장을 거부하려면 parse_constant 정책도 별도다. 크기 한도와 해독/깊이/정수 변환 비용을 하나의 키 검사로 보장하지 않는다.

이 절의 계약은 메모리 문자열로 된 작은 설정이다. 바이트 입력이면 해독 전 바이트 한도와 해독 후 문자 검사 위치를 나눈다. 이미 받은 거대한 문자열의 len 검사는 앞선 수신/할당 비용을 되돌리지 않는다. 검증한 값으로만 사용하는 소비 단계를 연결하며 eval/pickle 실행으로 바꾸지 않는다.

먼저 확인할 개념
  • JSON의 구조와 값

    파싱과 형/키/범위 검증을 나눈다.

  • dict의 같은 키

    동일 키 대입으로 이전 값이 사라지는 원리를 적용한다.

읽기 성공은 첫 단계다

json.loads는 JSON 문법을 Python 값으로 변환한다. 문법이 맞더라도 값이 사전인지, 필요한 키가 있는지, count가 허용 범위인지 별도 확인한다. [3]도 유효 JSON이지만 count 설정 사전과 같은 계약은 아니다.

입력 크기를 변환 전에 제한하면 과도한 자원 사용을 줄이는 데 도움이 된다. 표준 모듈이라고 무제한 데이터의 안전한 시간·메모리 사용을 보장하지 않는다. 파싱 예외와 업무 규칙 실패를 구별하여 안내한다.

자료형에도 경계가 있다

이 예제의 계약은 count 키만 있는 사전이고 count는 bool이 아닌 정수 1–5다. Python에서 bool은 int의 하위형이므로 isinstance(True,int)는 참이다. 이 계약의 정확한 정수 조건에는 type(value) is int 등을 사용할 수 있다.

문자열 '3'을 자동 변환할지 거절할지 미리 정한다. 지금은 JSON 숫자 3만 허용한다. 알 수 없는 키를 허용하는 확장 정책도 별도 결정이며, 본문은 오타를 찾기 위해 count 외 키를 거절하는 가상 규칙이다.

데이터와 실행 가능한 객체를 구별하기

pickle 역직렬화는 신뢰하지 않는 데이터에서 코드 실행으로 이어질 수 있어 외부 파일을 무조건 읽는 용도로 쓰면 안 된다. JSON을 선택해도 데이터 크기와 내용 검증을 없애도 된다는 뜻은 아니다.

예제는 메모리 문자열만 사용한다. 실제 파일 접근에서는 인코딩, 접근할 위치와 오류도 확인해야 한다. 외부 문자열을 eval로 실행하여 설정을 읽는 식으로 데이터와 코드를 섞지 않는다.

다른 문제에 적용하기

작은 메모리 설정은 정확 키 {code,date,count}를 가지며 중복 해독 키를 거부한다. code는 base ASCII 패턴 전체 일치와 번호 1..99, date는 정확 YYYY-MM-DD 모양 후 실제 달력, count는 정확 int이며 범위 1..5다. C1={"code":"AB-07","date":"2024-02-29","count":2}다. C2는 C1의 code 끝에 개행을 하나 붙인다. C3는 C1의 date만 2023-02-29로 바꾼다. C4는 C1의 count만 true로 바꾼다. C5는 C1의 원문에서 count 키가 값 2와 5로 두 번 등장한다. 다섯 입력을 각각 새로 검사한다. 각 실패 단계를 정하고 성공값만 계산에 전달하라. DEBUG 비활성에서 logger.debug("count=%s",compute())를 쓰면 compute가 count를 사용하는 가상 사건을 남기는지, isEnabledFor로 보호하면 어떻게 다른지 적어라. 실제 입력/regex/달력/parser/logger/학생은 실행하지 않는다.

힌트 1

중복은 dict 축약 전, code는 fullmatch, date는 모양과 달력 두 단계다. true는 정확 int가 아니다.

힌트 2

로그 함수의 인수는 호출 전에 평가되지만 보호 조건이 거짓이면 그 문장에 도달하지 않는다.

풀이와 답 확인

  1. C1은 모든 조건을 통과하여 count 값 2를 계산에 전달한다. 날짜는 윤년의 유효한 2월 29일이다.

  2. C2는 개행이 남아 code 전체 형식 실패, C3는 모양은 통과하나 달력 ValueError다.

  3. C4는 bool 타입 실패, C5는 파싱 중 중복 count 실패다. 거부값을 정상 계산에 넘기지 않는다.

  4. C1만 성공한 경로에서 직접 debug(...,compute())는 compute를 먼저 수행한다. DEBUG 출력 없음은 계산 사건 없음이 아니다.

  5. 같은 설정의 별도 경로에서 isEnabledFor(DEBUG)가 False이면 보호된 compute를 호출하지 않는다. 메시지의 비밀 원문을 제외하며 실제 운영 증거로 주장하지 않는다.

C1만 허용이다. C2 형식/C3 달력/C4 타입/C5 중복 실패이며 직접 DEBUG 호출의 인수 사건은 발생할 수 있고 보호 조건의 거짓 경로에서는 발생하지 않는다.

해결한 뒤 점검할 것

  • 중복 정보 손실 전 검사를 설명한다.

  • code 전체 형식과 숫자 의미를 나눈다.

  • 날짜 모양과 달력 존재를 구별한다.

  • 거부값을 계산에 전달하지 않는다.

  • 인수 평가와 로그 필터를 나누고 실제 미수행을 유지한다.
