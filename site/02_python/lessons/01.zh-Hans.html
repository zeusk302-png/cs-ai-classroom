小节 1.1

文件、工作目录与运行命令

如果有两个文件都叫 hello.py，计算机会运行哪一个？

预备知识与学习目标

预备知识

  • 文件是有名字的已保存内容；文件夹是把文件组织起来的位置。
  • 预备检查：在“学校/教室/课桌”这样的地址中，只知道最后一个名字能找到课桌吗？多个位置有同名对象时，需要完整位置。

学习目标

  • 区分源文件、解释器与工作目录。
  • 结合相对路径与工作目录，确定实际运行的文件。
  • 在运行记录中同时写下命令和位置。

文本与解释器承担不同职责

hello.py 是保存 Python 语句的文本文件。扩展名是提示用途的惯例，保存文件并不会让语句自动执行。解释器是读取文件、按语言规则处理它的程序。编辑器修改文本，终端是传递命令的窗口，要区分这三种职责。

纸面活动只需自己阅读源代码和输入，逐步追踪结果。可选的计算机练习使用已经有 Python 3 解释器的环境。python、python3 和 Windows 的 py 启动器选择解释器的方式可能因环境而异，不能只凭名字就认定版本相同。

# 保存到 hello.py 的源代码
print("Ready")

工作目录是相对路径的起点

工作目录是当前命令使用的基准目录。相对路径 hello.py 指向该目录中的文件；绝对路径则从盘符或根目录指定位置。因此，换一个工作目录，同一命令也可能选择另一个文件，或找不到文件。

例如 C:\Study\A 和 C:\Study\B 中各有 hello.py，在 C:\Study\A 中运行 python hello.py 会读取 A 的文件。在编辑器里打开 B 的文件，并不意味着命令的工作目录也变成 B。脚本内部用相对路径访问数据，通常也以工作目录为基准，不会自动改为源文件所在目录。

拆解并记录命令

在 python hello.py 中，第一项是要运行的解释器，下一项是交给它的文件参数。路径有空格时，要用引号包住，避免 shell 把路径拆成多个参数。shell 命令与 Python 语句使用不同语法，混在同一输入区域可能失败。

在 PowerShell 中用 Get-Location 检查位置、用 python --version 检查版本，属于可选练习。必须同时记录位置、源代码内容、命令、输入与结果，别人才可能复现相同条件。“找不到文件”的消息是此阶段的问题，不代表 print 的计算结果错误。

# 可选练习：在 PowerShell 中输入
Get-Location
python --version
python ".\hello.py"

逐步推导的例题

C:\Study\A\hello.py 中是 print(2+3)，C:\Study\B\hello.py 中是 print(9)。工作目录为 A，假定 Python 3 可用。python hello.py 会读取哪个文件？预期输出是什么？

  1. 命令的文件参数是相对路径 hello.py。
  2. 与工作目录 A 结合，得到 C:\Study\A\hello.py。
  3. 该文件计算 2+3=5，print 将它显示为一行。

运行 A 的文件，预期输出为 5。即使正在编辑 B 的文件，此命令的路径也不会因此改变。

用纸笔和正文动手试一试

在纸上画出文件夹 A、B 及各自的 hello.py。假定从工作目录 B 运行 python ../A/hello.py，用箭头表示路径移动。本题采用通常的文件路径解释：/ 分隔目录，.. 表示父目录。

查看提示

.. 到达当前目录的父目录。先找到 B 的父目录。

查看解答

依次是 B→Study→A→hello.py。最终选中 A 的 hello.py，预期输出 5。工作目录仍为 B，只是文件路径指定了 A。

常见误解与反例

屏幕上打开的文件一定就是运行的文件。

终端命令通过文件参数选择目标。即使打开 B，在 A 中运行 python hello.py 也会读取 A 的文件。编辑器运行按钮如何设置工作目录因工具而异，所以应记录实际命令。

检查理解

源文件与 Python 解释器是同一个东西吗？

查看答案与理由

不是。源文件是待处理的文本，解释器是处理它的程序。

职责不同，所以只有源文件而找不到解释器时仍无法运行。

把工作目录改为 B 后运行 python hello.py，预期输出是什么？

查看答案与理由

9

同一相对路径现在解释为 B 内的文件。

用绝对路径指定源文件，就能消除所有环境问题吗？

查看答案与理由

不能。

文件选择虽然明确，但解释器版本、输入、依赖文件和访问权限仍可能不同。

进一步探索

假定两个目录里还有同名的 data.txt。从 B 中通过绝对路径运行 A 的脚本，脚本使用 open('data.txt') 时，通常寻找 B 的 data.txt。分别画出源文件位置与工作目录并解释。文件读取语法将在后续单元介绍。

小节 1.2

REPL 与脚本

像计算器一样直接输入 2+3，与把 2+3 写进文件，屏幕显示会相同吗？

预备知识与学习目标

预备知识

  • 表达式计算一个值。2+3 的值是 5。
  • 语句规定要执行的动作。x=2 把名字 x 绑定到值 2。

学习目标

  • 区分交互式表达式显示与 print 输出。
  • 区分同一会话中的名字状态与新脚本进程的状态。
  • 把赋值追踪为先计算右侧，再绑定名字。

REPL 交替接收输入并反馈结果

REPL 是 Read、Evaluate、Print、Loop 的缩写，表示读取输入、求值、显示结果，然后等待下一个输入的交互模式。Python 的基本交互会话用 >>> 提示可以输入。提示符本身不是 Python 语法，不应复制到源文件中。

交互式输入表达式 2+3，通常显示值 5。print(2+3) 执行输出动作，也显示 5，但调用本身的返回值是 None。默认交互式解释器不会单独显示 None，所以两个输入的屏幕表现可能类似，含义却不同。

>>> 2 + 3
5
>>> print(2 + 3)
5

脚本按保存的语句顺序执行

脚本执行文件中保存的语句。只在文件里写 2+3，并没有显示结果的动作，因此需要 print。不能把交互模式自动显示值的行为推广到所有运行方式。

普通的新脚本进程不会自动继承其他进程或 REPL 中创建的 x；同一 REPL 会话里的 x 则可以用于后续输入。教学笔记本与编辑器可能保留状态。本例假定基本 Python 解释器和一个新进程。

赋值改变状态，不是恒等式

x=x+3 不是宣称两边永远相等的数学命题。它读取 x 的当前值，计算右侧 x+3，再把 x 重新绑定到结果。x 若尚未定义，右侧求值时会出现 NameError。

x=2 后执行 y=x，y 也绑定到值 2。之后 x=x+3 把 x 重新绑定到 5，却不会同时重新绑定 y。在这个整数例子中，最终 x=5、y=2。可变对象的共享是另一问题，将在后续单元区分。

x = 2
y = x
x = x + 3
print(x, y)

逐步推导的例题

假定新 Python 3 脚本依次执行 x=2; y=x; x=x+3; print(x,y)。

  1. x=2：名字 x 指向值 2。
  2. y=x：把 y 也绑定到右侧当前值 2。
  3. x=x+3：计算 2+3=5，再把 x 改为 5；y 保持 2。
  4. print 的默认分隔符是空格，所以两个值之间有一个空格。

预期输出为 5 2，后面跟换行。

用纸笔和正文动手试一试

在纸上画名字 x、y 与值框，追踪 x=4; y=x; x=1; print(y)。再预测：关闭 REPL，重新启动一个新会话，仅输入 y，会出现哪一类问题？

查看提示

重新赋值不会移动连接到旧值的所有名字标签。

查看解答

x=4 得到 x→4；y=x 得到 y→4；x=1 改为 x→1，而 y→4 保留。预期输出 4。新的基本 REPL 没有 y 的绑定，预计出现 NameError。

常见误解与反例

REPL 中显示的所有值，在脚本里也会自动显示。

脚本只有 2+3 时会计算值，却不显示。显式输出需要 print 等输出动作，要与交互式自动显示功能区分。

检查理解

应把 >>> 写入脚本吗？

查看答案与理由

不应。

它是基本 REPL 的提示符，不是代码。

x=8; y=x; x=9; print(y) 的预期输出是什么？

查看答案与理由

8

x 的重新绑定不会重新绑定 y。

新脚本第一行 x=x+1 一定把 x 设为 1 吗？

查看答案与理由

不是。在本题假设下会出现 NameError。

必须先定义名字，才能在右侧读取 x。

进一步探索

比较 x=2; y=x; x=x+3 与 x=2; x=x+3; y=x 两种顺序。它们分别结束于 (5,2) 和 (5,5)。把每条语句看作“名字→值”状态的变换，解释为什么这些变换的复合不可交换。

小节 1.3

输出、输入与错误消息

人输入了数字 7，程序为什么仍可能拒绝计算 7+1？

预备知识与学习目标

预备知识

  • 数字 7 与文本 '7' 看起来相似，但类型不同。
  • 语句顺序与基本加法。预备检查：连接 '7' 与 '1' 得到 '71'，数值加法得到 8。

学习目标

  • 区分 input 返回字符串与 int 转换。
  • 把语法错误、NameError、ValueError、TypeError 与原因对应。
  • 把 traceback 作为失败位置的证据来阅读。

输入从文本开始

input('Count? ') 显示提示，读取一行输入，去掉末尾换行，返回字符串。即使输入 7，返回的也是字符串 '7' 而非整数 7。若要进行数值计算，应明确用 int 转换适当的整数文本。

int('7') 返回 7，int('seven') 则抛出 ValueError。可转换与符合问题的有效输入是不同性质。例如 int('-2') 转换成功，但是否允许负数量，必须由问题约定另行决定。

text = input("Count? ")
count = int(text)
print(count + 1)

输出效果不等于返回值

print 把参数显示为文本，默认在多个参数之间放空格，末尾放换行。print('Count:', count) 在同一行显示标签与值。引号中的 count 是字面文本，不是名字查找；print('count') 显示单词而不是变量值。

输出是外部效果，与后续计算使用的返回值不同。print 调用返回 None。在 n=print(7) 中，屏幕显示 7，但 n 不保存整数 7。把屏幕输出、输入和名字状态分成记录表中的不同栏，更容易看清差异。

错误说明程序执行到了哪里

语法错误表示代码形式不符合语言规则。普通脚本在执行前会整体解析，所以文件后面缺少括号，可能使前面的 print 也无法执行。运行时异常则是语法有效的代码在实际执行过程中失败。

读取未定义名字的 NameError、不合适整数文本的 ValueError、字符串与整数相加的 TypeError，是不同线索。traceback 显示调用路径和失败位置。先读最后的异常名称与消息，再检查对应源代码行及输入类型。消息措辞可能随解释器版本变化，所以下面预测的是异常类别和失败阶段。

逐步推导的例题

对上方三行程序，比较输入 7 与输入 seven 的情况。

  1. 输入 7：text 是字符串 '7'，int(text) 得到整数 7，count+1 得到 8。
  2. print 显示 8 与换行。提示 'Count? '（包括问号后的一个空格）更早显示。
  3. 输入 seven：text 是 'seven'，int(text) 处发生 ValueError。
  4. 没有异常处理代码，因此最后的 print 不执行。

输入 7 时，计算结果的预期输出是 8。输入 seven 时发生 ValueError，不会显示计算结果 8。提示与用户键入字符要和结果输出分别记录。

用纸笔和正文动手试一试

不调用 input，而是假定 text='9'。纸面追踪 A: print(text+'1')，B: print(int(text)+1)，C: print(text+1)，区分计算、输出与错误。

查看提示

写出 + 两侧操作数的类型。

查看解答

A 连接字符串，预期输出 91；B 进行整数加法 9+1，输出 10；C 在 str 与 int 之间尝试不支持的加法，预计出现 TypeError。准确错误措辞取决于解释器版本。

常见误解与反例

只要修改错误中显示的那一行，就一定能消除根本原因。

即使在 text+1 处看到 TypeError，原因也可能是更早的设计未把输入转换为数字。失败位置与原因位置可能不同，应同时检查输入约定和中间值。

检查理解

input 默认返回什么类型？

查看答案与理由

字符串 str。

看起来像数字的输入也不会自动变成整数。

输入为 '12' 时，int(text)+1 的值是什么？

查看答案与理由

13

先把文本转为整数 12，再相加。

int('-2') 成功时，这一定是有效数量吗？

查看答案与理由

取决于问题条件。

转换成功不会检查“禁止负数”等语义条件。

进一步探索

对语法有效的 print('start'); int('oops'); print('end')，预测只打印 start。反之，若文件末尾有语法错误，整体解析可能先失败。讨论“按顺序读每一行”的比喻为什么不能解释所有执行前分析阶段。

小节 1.4

问题分解与运行记录

只写下“答案是 9”，朋友能复现你的计算吗？

预备知识与学习目标

预备知识

  • 输入、处理、输出的顺序，以及基本四则运算。
  • 预备检查：单价 3、数量 2，总额为 6。计算之前先写出值与单位。

学习目标

  • 把小需求分解成输入约定、计算和输出。
  • 用状态追踪表与运行记录保存复现条件。
  • 区分预测、实际运行观察和核验这几种证据。

先写问题约定

编程之前要明确输入与输出。优惠券总额可以约定为：“接收整数单价、整数数量和整数优惠金额，从小计中只减一次优惠。”若价格指单件还是全部金额不明确，同一代码也可能解决不同问题。

首次练习把 price、count、discount 直接写在代码中，假定它们都是非负整数，且优惠不超过原小计。真实用户输入、货币小数和范围检查留给后续任务。先说明假设，不是在隐藏困难，而是在明确当前论证的适用范围。

分解让中间结果可见

输入阶段包含 price、count、discount。处理分为 subtotal=price*count 和 total=subtotal-discount，输出阶段显示 total。单独记录 subtotal，便于比较优惠前后，缩小错误位置的范围。

记录名字的意义与单位。price 是每件金额，count 是件数，subtotal 与 total 是金额。从件数中减优惠金额，语法上可能有效，但不符合单位和需求。计算机允许的表达式，并不自动适合问题的含义。

price = 4
count = 3
discount = 2
subtotal = price * count
total = subtotal - discount
print(total)

预测记录不是实际运行结果

追踪表记录行号、新计算值、当前名字状态及输出事件。上例依次为 price=4、count=3、discount=2、subtotal=12、total=10。正确手算说明检查过预测，并不等于确认过真实解释器。

实际运行时，应记录源代码版本、工作目录、命令、解释器版本、输入、实际输出、错误与时间。预测和实际不同，就找最早不同的中间状态。一个值相同，也不能证明全部输入都正确。通过通常情况、数量为零、优惠为零、全额优惠等不同条件检查约定。

逐步推导的例题

用单价 4、数量 3、优惠 2 追踪上方代码。同伴改为 total=(price-discount)*count，判断是否满足相同需求。

  1. 原计算：subtotal=4*3=12。
  2. 一次优惠：total=12-2=10。
  3. 同伴计算：(4-2)*3=6。
  4. 改后的表达式每件减 2，合计优惠 6，不是约定的一次优惠 2。

预期结果是 10。同伴的 6 实现了不同需求。最早的差别是优惠的作用范围。

用纸笔和正文动手试一试

纸面制作单价 5、数量 2、优惠 10 的追踪表，再比较相同单价和数量、优惠为 0 的情况。决定“是否执行”栏应写什么。

查看提示

原小计是 10，在小计上只减一次优惠。

查看解答

第一种 subtotal=10、total=0；第二种 subtotal=10、total=10。两者都是手算预测。如果活动未安装或运行解释器，执行栏写 not_executed。

常见误解与反例

一个例子的实际输出正确，就证明整个程序正确。

discount=0 时，正确表达式与错误的 (price-discount)*count 结果相同；优惠 2、数量 3 时才有差别。测试能找反例并增加信心，但一般正确性需要覆盖需求及所有适用条件的论证。

进一步探索

对允许的输入 p、c、d，计算正确表达式 pc-d 与错误表达式 (p-d)c 的差，得到 d(c-1)。只用 d=0 或 c=1 的测试无法区分这个缺陷。解释怎样用表达式之差设计能区分实现的测试。
