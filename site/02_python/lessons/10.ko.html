소단원 10.1

pathlib와 상대·절대경로

프로그램 파일 옆의 data.txt가 왜 실행 위치에 따라 안 보일까?

준비 개념과 학습 목표

준비 개념

  • 폴더와 파일

  • 문자열과 객체

학습 목표

  • 경로와 파일 내용을 구별한다.

  • 작업 디렉터리를 기준으로 상대경로를 해석한다.

기준 폴더에 이름을 붙였는데 다른 루트로 옮겨지는 이유는?

주소를 조립할 때 두 번째 조각이 항상 하위 이름이라는 전제를 확인해야 한다. PurePosixPath("/course") / "/tmp/input.json"은 /course/tmp/input.json이 아니라 /tmp/input.json이다. 오른쪽 절대 경로가 이전 기준을 대신한다.

이 단원은 POSIX 및 Windows의 순수 경로 표현을 따로 탐구한다. 실제 파일·존재·권한·링크를 조회하지 않는다. 부분 경로의 ..는 순수 표현에서 자동으로 제거하지 않으며 실제 resolve의 링크 해석과 같다고 하지 않는다. 경로 표현의 소속 판정도 실제 파일 접근 제한을 검증한 결과는 아니다.

작업 폴더를 기준으로 하는 경로와 프로그램 설정에 적힌 기준 폴더를 구분하면 실행 재현 기록을 만들 수 있다. 어떤 OS 표현과 기준을 쓰는지 적고, 그 다음 별도 접근 단계에서 실패를 처리한다.

먼저 확인할 개념
  • 주 실행의 시작 문맥

    실행 명령의 작업 폴더와 모듈 위치를 별도로 기록한다.

  • 문자열의 표현

    경로 이름 문자열과 파일의 내용 바이트를 구별한다.

주소를 담는 객체

Path는 파일이나 폴더의 위치를 표현한다. Path("data.txt")를 만든다고 파일이 생성되거나 읽히는 것은 아니다. 실제 읽기·쓰기 메서드를 호출해야 저장장치 접근이 생긴다. PurePath 계열은 경로 표현 계산만 제공한다.

경로 결합은 문자열에 슬래시를 임의로 붙이는 대신 / 연산자를 쓸 수 있다. Path("data") / "scores.csv"는 하위 경로를 만든다. 같은 / 문자가 숫자 나눗셈과 다른 의미인 것은 피연산자 종류에 따른다.

from pathlib import Path
p = Path("data") / "scores.csv"
print(p.name)  # 예상 이름: scores.csv

상대경로의 출발점

상대경로는 현재 작업 디렉터리에서 출발한다. 작업 디렉터리는 스크립트가 있는 폴더와 다를 수 있으므로 실행한 위치를 확인해야 한다. Path.cwd()는 그 출발점을 확인하는 수단이다.

절대경로는 루트부터 위치를 지정한다. Windows에서는 드라이브와 루트를 함께 살핀다. C:notes.txt처럼 드라이브만 있는 표현은 C:/notes.txt와 같은 절대경로가 아니다. 한 컴퓨터의 절대경로를 다른 컴퓨터에서 그대로 쓸 수 있다고 보장하지 않는다.

경로 정리와 존재는 별개

parent는 상위 경로, name은 마지막 이름, suffix는 마지막 확장자를 나타낸다. 확장자는 이름의 일부이며 그 파일의 실제 형식이 맞다는 증거는 아니다. 이름이 .json이어도 내용 검증은 따로 한다.

resolve()는 실제 플랫폼의 경로를 해석하며 심볼릭 링크 등이 개입할 수 있다. ..를 문자 삭제만으로 처리한 결과가 실제 파일 접근과 항상 같지 않다. 여기서는 심볼릭 링크가 없는 단순 폴더 모형을 종이로 추적한다.

표의 ..가 남는 것은 실수가 아니라 순수 표현의 규칙이다. 링크 없는 종이 폴더 모형으로 단순 목적지를 계산하는 활동과 실제 OS의 경로 해석은 추가 가정이 다르다.

중간 과정을 따라가는 예제

심볼릭 링크 없는 POSIX 모형에서 작업 폴더 /home/student이고 상대경로 data/scores.csv이다. 목적 위치와 마지막 이름을 구하라.

  1. 작업 폴더 뒤 data를 붙인다.

  2. 그 아래 scores.csv를 붙여 /home/student/data/scores.csv를 얻는다.

  3. 마지막 이름은 scores.csv이고 확장자는 .csv이다.

/home/student/data/scores.csv, 이름 scores.csv이다. 파일 존재는 확인하지 않았다.

조건을 바꾸어 비교하기

Windows 드라이브와 루트

PureWindowsPath의 C:notes.txt, C:/notes.txt, /notes.txt를 drive/root/is_absolute로 구분하라.

  1. 첫째는 drive C:, root 없음이다.

  2. 둘째는 drive C:와 루트 구분자를 갖고 셋째는 루트 구분자만 갖는다. 실제 PureWindowsPath.root 반환은 두 경우 모두 역슬래시 한 문자다. 입력에는 /도 허용된다.

  3. 셋째는 드라이브가 없어 절대 경로로 판정하지 않는다.

절대 판정은 False/True/False다.

소단원 10.2

text·binary와 encoding

한 글자인 “가”가 파일에서 몇 바이트일까?

준비 개념과 학습 목표

준비 개념

  • 문자와 바이트

  • 파일 열기 모드

학습 목표

  • str와 bytes 반환을 구별한다.

  • 인코딩과 줄바꿈 처리를 명시한다.

같은 UTF-8 바이트인데 읽은 길이는 왜 달라질까?

문자 해독과 줄바꿈 처리는 별도 단계다. 자체 원문 바이트는 41 EA B0 80 0D 0A, 즉 A가 뒤 CRLF다. UTF-8 해독만 하면 네 코드 포인트 A/가/CR/LF이고 기본 텍스트 줄바꿈 변환 뒤에는 A/가/LF 세 코드 포인트다.

이 바이트 모형의 길이 6과 텍스트 길이 3 또는 4를 같은 파일 크기로 보고하지 않는다. newline=None은 읽을 때 CRLF/CR/LF를 LF로 바꾸고 newline=""는 원래 줄 끝을 보존한다. 오류 처리도 인코딩과 별도로 명시한다.

잘못된 UTF-8 바이트를 ignore하면 나머지가 정상 점수 문자열처럼 보일 수 있다. 닫기를 수행했는지와 입력 내용이 손실 없이 읽혔는지는 다른 확인이다. 실제 파일 생성·읽기 없이 주어진 바이트의 예상 변환만 추적한다.

먼저 확인할 개념
  • 코드 포인트와 UTF-8

    바이트 수와 문자열 길이의 단위를 나눈다.

  • 파일 수명의 종료

    파일 닫기와 해독 성공을 서로 다른 책임으로 읽는다.

파일의 바이트를 문자로 읽기

저장된 바이트를 문자로 해석하는 규칙을 인코딩이라고 한다. text 모드 읽기는 바이트를 해독해 str을 반환하고 binary 모드는 해독 없이 bytes를 반환한다. 사진을 문자 파일처럼 읽으면 잘못된 해독이 생길 수 있다.

UTF-8에서 ASCII 문자 A는1바이트, 한글 음절 가는3바이트로 표현된다. Python len("가")는 문자 코드 포인트 개수1이며 인코딩 뒤의 바이트 수와 다르다. 화면상 한 글자 모양과 코드 포인트 수도 항상 같지는 않다.

text = "가"
raw = text.encode("utf-8")
# 종이 예상: len(text) == 1, len(raw) == 3

모드와 인코딩은 계약

읽기 r, 새로 쓰기 w, 덧붙이기 a, 새 파일 전용 x의 목적을 구별한다. w는 기존 내용을 잘라낼 수 있으므로 입력 원본을 출력 경로로 쓰지 않는다. 예제는 읽기만 보여 주고 실제 사용자 파일은 건드리지 않는다.

text에서 encoding="utf-8"을 명시하면 기본 환경에 의존하지 않는다. binary에는 encoding을 지정하지 않는다. UTF-8 파일을 다른 규칙으로 읽으면 오류나 깨진 문자가 생길 수 있고 errors="ignore"는 잘못된 바이트를 버려 자료 손실을 숨길 수 있다.

with open("sample.txt", "r", encoding="utf-8") as f:
    text = f.read()
# 실제 파일 읽기는 이 집필 과정에서 수행하지 않음

닫기와 줄바꿈

with 블록은 파일을 연 뒤 정상 종료와 예외 경로에서 닫도록 돕는다. 파일 닫기는 문자 해독과 별개 문제다. 줄바꿈 변환도 text 모드의 기능으로, 읽는 문자 수와 원파일 바이트 수를 다르게 만들 수 있다.

바이트 그대로 비교해야 하는 작업에는 binary가 적합하다. 텍스트 해독 뒤 길이를 파일 크기로 단정하지 말고 무엇을 센 수인지 써야 한다. 이 활동에서는 알려진 바이트와 문자만 종이로 계산한다.

CSV·JSON 읽고 쓰기

이름에 쉼표가 들어가면 CSV 한 줄을 split(",")로 나눠도 될까?

준비 개념과 학습 목표

준비 개념

  • 리스트와 딕셔너리

  • 문자열과 숫자

학습 목표

  • CSV 인용과 JSON 구조를 파서로 처리한다.

  • 파일과 문자열 API 및 저장 형식의 한계를 구별한다.

JSON 왕복 뒤 키가 달라지거나 점수가 사라질 수 있을까?

자료를 다시 읽을 수 있다는 사실과 원래 객체를 그대로 보존한다는 사실을 구별하자. JSON 객체의 키는 문자열이다. Python의 {1:"one"}을 기본 JSON으로 표현했다가 읽으면 키는 "1"인 문자열이다. 숫자 키를 요구한 원래 dict와 같지 않다.

기본 json.loads는 객체 안의 반복 이름을 받아 마지막 값만 남길 수 있다. {"score":40,"score":90}을 읽으면 score=90이며 읽은 dict만 검사해서는 앞 40의 존재를 복구하지 못한다. 중복 이름을 거절할 교환 계약은 object_pairs_hook 같은 파싱 단계 규칙으로 정해야 한다.

반복 dump의 두 객체 문서, 하나의 배열 문서, 줄별 독립 문서는 구분 계약이 다르다. ensure_ascii는 문자 표기 옵션이며 파일 encoding을 정하지 않는다. 본문은 문서 문자열의 의미 추적이고 실제 parser/파일 쓰기를 실행하지 않는다.

먼저 확인할 개념
  • 사전의 키와 값

    숫자 키와 문자열 키 및 반복 이름의 최종 값을 구별한다.

  • 문자열과 바이트

    JSON 문자열 표기 옵션과 파일 인코딩을 구별한다.

행과 열을 읽는 CSV

CSV는 행마다 필드를 구분하며 필드 안에 쉼표·줄바꿈이 있으면 인용 규칙이 필요하다. csv.reader는 그 규칙을 해석한다. 단순 split(",")는 따옴표 안의 쉼표까지 나누므로 이름 “Kim, Mina”를 잘못 두 필드로 만들 수 있다.

기본 reader 결과의 필드는 문자열이다. 점수 "80"을 숫자로 계산하려면 검증 뒤 int 변환 등을 해야 한다. DictReader는 헤더 이름으로 필드를 연결하고 DictWriter는 명시한 열 목록 순서로 쓴다. 파일은 encoding과 newline=""을 명시한다.

import csv
with open("scores.csv", encoding="utf-8", newline="") as f:
    rows = list(csv.DictReader(f))
# rows의 점수 필드는 기본적으로 문자열

중첩 구조를 담는 JSON

JSON은 객체·배열·문자열·수·불리언·null을 표현한다. Python에서는 보통 dict·list·str·int/float·bool·None과 대응한다. JSON 객체 키는 문자열이며 집합이나 임의 사용자 객체를 그대로 저장할 수는 없다.

json.load/dump는 파일 객체를, loads/dumps는 문자열을 다룬다. 파일 인코딩은 open 단계에서 명시하고 ensure_ascii=False는 비ASCII 문자를 읽기 쉽게 쓰도록 하는 옵션이다. 이 옵션이 파일 인코딩을 정하는 것은 아니다.

import json
value = json.loads('{"scores": [80, 90], "passed": true}')
text = json.dumps(value, ensure_ascii=False)
# 코드 흐름으로 예상: scores는 list, passed는 True

읽기·쓰기와 검증의 경계

CSV가 행으로 읽히거나 JSON이 파싱되어도 데이터의 의미가 옳다는 보장은 없다. 필요한 키와 범위·자료형을 검사한다. 원자료를 덮어쓰지 않고 새 출력으로 저장하며 파일 쓰기는 실패할 수도 있으므로 오류 경로를 둔다.

같은 파일에 dump를 반복하면 여러 JSON 문서가 이어져 보통 하나의 유효한 JSON 문서가 되지 않는다. Python json 기본값에는 NaN·Infinity 허용 같은 확장이 있어 엄격한 다른 시스템과 교환할 때 규칙을 확인한다. 스키마와 교환 조건을 별도로 합의한다.

{"score":90}

업무 범위

{"score":90}

[40,90]

{"a":1}{"b":2}

문서 경계 규약

마지막 행은 문자열 전체를 하나의 문서로 loads하는 계약이다. raw_decode로 일부만 읽는 다른 API와 혼합하지 않는다. 기본 동작이 모든 교환 상대의 규칙과 같다고 하지 않는다.

중간 과정을 따라가는 예제

CSV 행은 따옴표를 포함해 “"Kim, Mina",80”이고 JSON은 {"scores":[80,90]}이다. 필드와 점수 합을 종이로 구하라.

  1. CSV 인용된 이름 전체가 첫 필드이고80이 두 번째 필드이다.

  2. 기본 CSV 점수는 문자열 "80"이다.

  3. JSON scores 배열의 수80+90=170이다.

CSV2필드: Kim, Mina / 문자열80. JSON 합170이다.

조건을 바꾸어 비교하기

키 왕복은 원래 객체와 다른가

x={1:"one"}의 기본 dumps→loads를 종이로 예상한다.

  1. 출력 객체 키는 JSON 문자열 "1"이다.

  2. 읽은 dict의 키도 Python 문자열 "1"이다.

  3. int 키 1과 str 키 "1"은 원래 계약에서 다른 키다.

{"1":"one"}이며 x와 동일한 객체/키 계약이 아니다.

비교할 점

기본 JSON 자료형 대응에 키 변환의 한계를 추가한다.

같은 파일에 두 번 저장한다

첫 dump {"a":1}, 다음 dump {"b":2}를 구분자 없이 같은 파일에 수행하는 계획을 평가하라.

  1. 원문은 두 객체가 붙은 표현이다.

  2. 단일 문서 parser는 첫 객체 뒤 추가 문서를 만난다.

  3. 한 배열 [{"a":1},{"b":2}]로 묶거나 명시한 별도 스트림 계약이 필요하다.

반복 dump만으로 단일 유효 JSON 문서가 되지 않는다.

파일 부재·잘못된 데이터 처리

없는 파일과 잘못된 점수는 같은 오류 메시지로 처리하면 충분할까?

준비 개념과 학습 목표

준비 개념

  • try·except

  • 딕셔너리 키와 타입

학습 목표

  • 열기·해독·파싱·의미 검증 오류를 구분한다.

  • 좁은 예외 처리와 명확한 실패 결과를 설계한다.

잘못된 바이트와 120점은 같은 검사를 실패한 걸까?

읽기 파이프라인을 주소/접근→해독→문법→업무 조건으로 나누면 고칠 대상을 찾기 쉽다. 파일이 없으면 문법 검사는 아직 수행하지 못했고, 정상 JSON의 120점은 문법 성공 뒤 업무 범위에서 실패한다.

자체 score 계약은 루트 내장 dict, score 키가 있고 값의 정확한 타입이 int, 범위 0..100이다. bool이나 float 80.0은 허용하지 않는다. 성공은 ("ok",score), 실패는 ("error",stage)라는 별도 결과로 계획한다. 실제 읽기나 구현을 실행하지 않고 주어진 사례를 판정한다.

정상 빈 자료와 읽기 실패를 같은 []로 반환하지 않는다. 공개 안내는 고칠 조건을 설명하되 원문 개인정보나 시스템 내부 전체 경로를 무조건 출력하지 않는다. exists 확인과 open 사이의 변경도 가능하므로 실제 접근에서 발생한 실패를 처리해야 한다.

먼저 확인할 개념
  • 실패 원인별 복구

    입력 교정과 접근 환경 확인 및 버그 수정을 나눈다.

  • 키 없음과 값

    누락 score와 정상 값 0을 구분한다.

어느 단계가 실패했는가

파일이 없으면 FileNotFoundError, 권한 문제 등은 OSError 계열로 나타날 수 있다. 바이트 해독은 UnicodeDecodeError, JSON 구문 해석은 JSONDecodeError로 실패할 수 있다. 같은 “읽기 실패”라도 사용자가 고쳐야 하는 대상이 다르다.

파일이 존재하는지 먼저 확인했더라도 열기 전에 사라질 수 있으므로 실제 열기 오류를 처리한다. 모든 예외를 잡아 빈 리스트를 반환하면 실제 빈 데이터와 오류가 구별되지 않아 결과를 오해할 수 있다.

문법 뒤에는 의미 검사

{"score":120}은 유효한 JSON이지만0–100점 계약에는 어긋난다. 키가 없거나 루트가 배열이면 기대 객체와 다르다. Python bool은 int의 하위 타입이므로 isinstance(v,int)만으로 True를 숫자 점수로 허용할 수 있다는 점도 계약에 맞게 다룬다.

학습용 예제는 정수 점수만 허용하려고 type(v) is int를 사용한다. 실제 서비스에는 다른 숫자 타입·범위·누락 정책을 명시해야 한다. 오류 메시지는 잘못된 조건을 알려 주되 민감한 원자료를 무조건 출력하지 않는다.

def validate(data):
    if not isinstance(data, dict):
        raise ValueError("객체가 필요합니다")
    score = data.get("score")
    if type(score) is not int or not 0 <= score <= 100:
        raise ValueError("정수 점수 0~100이 필요합니다")
    return score

실패를 숨기지 않는 경로

try 블록은 필요한 작업으로 좁히고 처리 가능한 예외만 잡는다. 알 수 없는 오류를 성공처럼 반환하지 않는다. with로 파일을 닫고 입력이 검증된 뒤 계산하며 출력 성공도 별도로 확인한다.

재시도는 원인에 따라 결정한다. 없던 입력을 사용자가 지정해 다시 읽는 것은 가능하지만 JSON 문법 오류가 그대로라면 같은 재시도만 반복해도 해결되지 않는다. 본문 코드는 예외 흐름 예상이며 실제 파일 실패 실험을 수행하지 않았다.

import json
try:
    with open("input.json", encoding="utf-8") as f:
        data = json.load(f)
    score = validate(data)
except FileNotFoundError:
    print("입력 경로를 확인하세요")
except (UnicodeDecodeError, json.JSONDecodeError, ValueError):
    print("입력 형식과 점수 조건을 확인하세요")
except OSError:
    print("파일 접근에 실패했습니다")

중간 과정을 따라가는 예제

validate에 {"score":80}, {"score":120}, {"score":true}에 대응하는 Python 객체가 들어온다. 경로를 예측하라.

  1. 80은 type int이고 범위 안이므로 반환80이다.

  2. 120은 범위 밖이라 ValueError이다.

  3. JSON true는 Python True이며 type bool이므로 type is int 조건에 실패한다.

80만 허용하며120과True는 검증 실패이다. 실제 실행 결과가 아니다.

조건을 바꾸어 비교하기

값이 같아 보여도 종류는 다르다

파싱된 {"score":80}, {"score":80.0}, {"score":true}를 정확 int 계약으로 검사한다.

  1. 80은 int이며 범위 안이다.

  2. 80.0은 float라 거절한다.

  3. true는 bool True라 거절한다.

80만 ok이며 나머지 둘은 schema 실패다.

비교할 점

기본 bool 거절에 float의 같은 수치와 정확 종류를 비교한다.

누락과 정상 0을 섞지 않는다

{}와 {"score":0}을 검사하고 data.get("score",0)의 위험을 설명한다.

  1. 빈 dict는 필수 키가 없다.

  2. 두 번째는 int 0으로 허용된다.

  3. 기본값 0은 누락을 정상 점수로 바꿀 수 있다.

error/schema 대 ok/0이다.

다른 문제에 적용하기

심볼릭 링크 없는 POSIX 종이 모형에서 cwd=/course이며 상대 경로 data/score.json을 읽는 계획을 작성하라. 알려진 UTF-8 문서는 {"score":0,"score":100} 뒤 CRLF다. 접근과 해독이 성공한다고 가정한다. 기본 json.loads의 값, 정확 int 0..100 검사, 중복 이름 거절 교환 계약의 판정을 각각 구하라. 최종 dict만으로 중복 검사를 할 수 있는지 설명하라. 입력 경로를 그대로 w 출력에 사용한 계획의 위험과, 모든 파싱/업무 검증 후 별도 출력 문서를 구성하는 순서를 적어라. 줄바꿈을 보존하거나 변환하는 읽기 설정 및 성공/실패 카드도 구성하라. 실제 파일 접근/쓰기는 요구하지 않으며 후보 검증 선행은 실제 쓰기 원자성·지속성 보장을 대신하지 않는다.

힌트 1

기본 parser는 마지막 score=100을 남기지만, 중복 금지 계약은 원래 쌍을 파싱 단계에서 확인해야 한다.

힌트 2

cwd와 경로 표현, encoding과 newline, 검증과 실제 출력 성공을 별도 항목으로 적는다.

풀이와 답 확인

  1. 모형 목적은 /course/data/score.json이다. 실제 존재/권한/링크는 확인하지 않았다.

  2. UTF-8 strict와 newline=""는 CRLF를 보존하고 None은 LF로 변환한다. JSON 문서 뒤의 이 공백은 여기의 값 구조를 바꾸지 않는다.

  3. 기본 읽은 값은 {"score":100}이고 정확 int 및 범위는 통과한다. 중복 이름 거절 계약은 원문 쌍의 두 score를 발견해 실패한다. 최종 dict만으로 앞 0의 존재를 복원하지 못한다.

  4. 원본에 w를 열면 기존 내용을 잘라낼 수 있다. 모든 파싱/교환/업무 검사를 통과한 뒤 별도 출력의 문서 후보를 만들고 출력 오류를 별도로 보고하는 계획을 쓴다.

  5. 카드는 주소 기준/읽기 가정/해독 및 줄바꿈/기본 파싱 결과/중복 계약 실패/출력 미수행을 나눈다. 이번 중복 금지 계약에서는 출력 반영을 진행하지 않는다.

기본 파싱과 점수 범위는 100으로 통과하지만 중복 이름 계약은 실패다. 원본을 덮어쓰지 않고 출력 미수행과 실제 저장 보장의 한계를 기록한다.

해결한 뒤 점검할 것

  • 상대 경로의 기준과 실제 접근 미수행을 명시한다.

  • encoding/newline과 바이트/문자 보존을 구별한다.

  • 기본 파싱/업무 조건/교환 중복 정책을 각각 판정한다.

  • 원본 w 절단 위험과 검증 후 별도 출력 계획을 설명한다.

  • 실제 저장 성공·원자성·지속성·학생 미수행을 정직하게 기록한다.
