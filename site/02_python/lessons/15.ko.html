화면 앞의 사용자와 약속하기

CLI는 명령과 인자로 기능을 요청하는 인터페이스다. 자체 도구 sumtool은 UTF-8 텍스트의 한 줄에 정수 하나를 읽고 빈 줄을 무시한다. --min 이상인 값의 개수와 합을 표준 출력에 한 줄로 쓴다. 음수도 정수로 허용하지만 2.5 같은 문자열은 거부한다.

사용 예는 python sumtool.py numbers.txt --min 5다. --min의 기본값은 0이고 경계 값 자체도 포함한다. 입력 파일을 변경하지 않는 읽기 도구다. 성공 출력의 count는 필터를 통과한 정수 개수이며 전체 비어 있지 않은 줄 수와 다를 수 있다.

도움말·오류·결과의 통로

argparse는 위치 인자와 선택 인자를 해석하고 도움말과 사용법을 만든다. 기본 인자 오류는 stderr에 설명을 쓰고 종료 코드 2로 끝난다. 아래 코드에서 --help는 읽기를 시작하지 않고 도움말 뒤 종료 코드 0으로 끝난다.

자체 계약의 자료·파일 오류는 stderr에 error:로 시작하는 설명을 쓰고 코드 1을 반환한다. 성공은 stdout에 count와 sum을 쓰고 0을 반환한다. 호출 프로그램은 stdout만 결과로 다루고 종료 코드도 확인할 수 있다. 특정 외부 명령의 관행을 모든 도구의 규칙이라고 일반화하지 않는다.

중간 과정을 따라가는 예제

자체 sumtool.py의 흐름을 읽고 파일의 줄 4, 5, 9를 --min 5로 처리할 때 결과를 설명하라. 빈 줄은 무시한다.

  1. import argparse
import sys

def read_numbers(lines):
    values = []
    for number, line in enumerate(lines, 1):
        text = line.strip()
        if not text:
            continue
        try:
            values.append(int(text))
        except ValueError as exc:
            raise ValueError(f'line {number}: expected integer') from exc
    return values

def summarize(values, minimum):
    selected = [value for value in values if value >= minimum]
    return len(selected), sum(selected)

def main(argv=None):
    parser = argparse.ArgumentParser(prog='sumtool')
    parser.add_argument('path')
    parser.add_argument('--min', type=int, default=0, dest='minimum')
    args = parser.parse_args(argv)
    try:
        with open(args.path, encoding='utf-8') as stream:
            values = read_numbers(stream)
        count, total = summarize(values, args.minimum)
    except (OSError, UnicodeError, ValueError) as exc:
        print(f'error: {exc}', file=sys.stderr)
        return 1
    print(f'count={count} sum={total}')
    return 0

if __name__ == '__main__':
    raise SystemExit(main())

  2. int 변환으로 [4, 5, 9]를 얻고 >= 5 조건으로 [5, 9]를 고른다. 개수는 2이고 합은 14다.

  3. main은 결과 한 줄을 stdout에 쓰고 0을 반환한다. 직접 스크립트를 실행하면 SystemExit가 그 값을 종료 코드로 전달한다.

설정 우선순위를 명령줄→선택 파일→기본 0으로 정한 새 설계에서 명령줄의 미지정 표식을 None으로 둔다. 최종 값만 보면 기본 0과 사용자가 명시한 0을 구별할 수 없다. truthiness로 선택하면 명시 0을 거짓으로 취급해 파일의 7이 덮어쓰는 오류가 생긴다. 값과 출처를 함께 보존한다.

자체 정책은 명시 CLI 값이 있으면 그것을 사용하고 선택 파일 값은 없을 때만 채택한다. 필수 설정 파일은 CLI가 있더라도 읽기 실패를 오류로 취급한다는 별도 요구로 정한다. 이는 구현된 base 기능이 아니라 설계 비교다. ConfigParser.read가 파일을 열지 못해도 무시할 수 있는 사실과 정책을 혼동하지 않는다.

입력 읽기 도중 앞 값이 내부에 들어왔어도 정상 결과를 공개하지 않는 base의 전부 검사 후 출력 흐름을 유지한다. 이 성질은 출력 파일 원자 저장이나 여러 외부 작업의 롤백을 뜻하지 않는다. 필수 읽기, 파싱 오류, 잘못된 정수와 출력 실패의 보호 범위를 각각 적는다.

설정의 출처와 우선순위

첫 예제의 설정은 기본 minimum 0 또는 명령줄 --min이다. 설정 파일을 더하면 예를 들어 명령줄, 파일, 기본값 순으로 채택한다고 정할 수 있다. 이 순서는 자체 정책이며 모든 라이브러리의 자동 우선순위가 아니다. 적용한 최종 값과 출처를 설명할 수 있게 설계한다.

ConfigParser.read는 열 수 없는 파일을 무시할 수 있으므로 필수 설정 실패를 자동으로 보장하지 않는다. 필수 파일은 with로 열고 read_file로 읽는 방법 등을 검토한다. 이 단원은 설정 정책을 설명하며 첫 예제에 INI 설정 기능을 구현했다고 주장하지 않는다.

실패를 원인과 단계로 구분하기

파일 없음과 읽기 권한 오류는 OSError 계열, UTF-8 해석 실패는 UnicodeError 계열로 나타날 수 있다. 정수 아닌 줄은 자체 ValueError로 줄 번호를 설명한다. 메시지의 운영체제별 세부 문구보다 실패 단계와 코드 계약을 먼저 확인한다.

첫 예제는 파일 전체를 읽고 검사한 후에만 성공 결과를 출력한다. 두 번째 줄이 bad이면 앞의 값은 내부 리스트에 들어갔어도 성공 합계를 내보내지 않는다. 모든 예외를 삼켜 0으로 반환하면 자료 문제를 성공으로 오해할 수 있다.

자원과 출력의 범위를 밝히기

결과 숫자만 맞는 테스트가 오류 통로도 잡을까?

기본 세 단위 시험은 중요한 계약 사례이지만 CLI의 모든 연결을 포함하지 않는다. 결과 stdout, 진단 stderr, main 반환/프로세스 상태를 다른 관찰 열로 둔다. 예를 들어 오류 메시지를 stdout으로 옮긴 변형은 핵심 summarize 시험을 통과할 수 있지만 호출자가 stdout을 숫자 결과로 읽는 계약을 깬다.

기대값은 구현과 독립적으로 사용 계약에서 정한다. 자체 작은 변형 V1은 >=를 >로 바꾸고 V2는 오류를 안내한 뒤 상태 0을 반환하며 V3는 정상 count와 sum의 이름을 뒤바꾼다. 입력 [0,3]과 최소값 0의 정확 (2,3), bad의 실패 1, 정확 결과 문법은 서로 다른 결함을 겨냥한다.

단위 함수의 반복 가능성과 실제 설치 실행 경로는 별도다. README의 환경/폴더/파일/입력/예상/실제 칸이 일치하는지 확인한다. 여기서는 변형과 새 시험 설계만 손추적하며 실제 unittest runner나 별도 실행기를 새로 돌리지 않는다. base의 이전 실제 작은 시험은 유지한다.

설치 명령이 성공했어도 내가 만든 wheel을 실행했는지 어떻게 확인할까?

소스 폴더의 import가 성공한 사실만으로 설치한 wheel의 내용을 확인할 수 없다. 같은 이름이 검색 경로에 있으면 소스를 먼저 읽을 수 있다. 새 환경에서 소스 경로가 섞이지 않는 작업 위치와 실행기·가져온 모듈 위치·배포물 버전을 기록해야 검증한 대상을 설명할 수 있다.

배포 이름과 import 이름, 설치되는 CLI 이름은 각각 역할이 다르다. 자체 설계 distribution=sumtool-demo, import=sumtool_pkg, command=sumtool을 정하면 모두 이름이 같을 필요는 없다. project.scripts의 sumtool = "sumtool_pkg.cli:main"은 실행 진입점 연결을 선언한다. 이를 문서에 썼다는 사실은 실제 script 생성/설치/동작 증거가 아니다.

build-system requires와 runtime dependency를 나눈다. 가상 build 도구 요구 B>=2,<3과 runtime R>=4,<5는 서로 다른 이름/역할이며 숫자 구간을 한 라이브러리의 교집합으로 계산하지 않는다. 지원 Python 선언과 실제 시험 버전도 분리한다. 외부 업로드·설치·빌드는 이 보강에서 수행하지 않는다.

소스 실행과 배포물 생성

sumtool.py를 직접 실행하는 단계와 설치 가능한 프로젝트를 만드는 단계는 다르다. PyPA의 공개 입문 자료는 pyproject.toml, README, LICENSE와 src 아래 package의 구조를 보여 준다. 배포 이름과 import 이름의 구별도 이후 설치 시험에서 확인한다.

sdist는 소스 배포, wheel은 빌드된 배포 형식이다. 이름에 built가 있다고 모든 wheel에 기계어가 들어가는 것은 아니다. 현재 단원은 구조와 확인 계획을 다루며 첫 sumtool을 실제 패키지로 만들거나 등록하지 않았다.

빌드 조건과 실행 조건

pyproject.toml의 build-system에는 backend와 빌드에 필요한 dependency를 적는다. project에는 이름, 버전, README와 지원 Python 조건 같은 metadata를 넣는다. runtime dependency와 빌드 도구의 dependency는 역할이 다르다.

버전 제약의 >= 표기는 설치 조건이지 미래 모든 버전에서 직접 시험했다는 증거가 아니다. 필요한 자원 파일이 배포물에 포함됐는지도 backend 설정과 결과물에서 확인해야 한다. 소스 폴더에 파일이 있다는 사실만으로 설치 뒤 같은 상대 경로가 있다고 가정하지 않는다.

다른 환경에서 다시 확인하기

확인 계획은 빌드 도구 준비, 프로젝트 폴더에서 python -m build, 결과물 검사, 새 가상환경에 로컬 wheel 설치, import와 CLI 실행의 순서로 적는다. 실제 실행한 단계만 완료로 기록한다. 외부 패키지 서버에 올리는 것은 별도의 공개 행동이다.

다른 문제에 적용하기

자체 새 sumtool 설계는 CLI 명시 여부를 None으로 보존하고 명령줄→선택 파일→기본 0 순으로 최소값을 고른다. 선택 파일 값은 7이고, 필수 설정 파일은 없으면 별도 실패로 처리한다. R1은 명시 --min 0과 입력 −2/빈 줄/0/3, R2는 CLI 미지정과 같은 입력, R3는 명시 --min 0과 −2/bad/3, R4는 --min five, R5는 명시 --min 0이 있지만 필수 파일을 열지 못한 경우다. 각 요청을 새 상태에서 판단하여 최소값 출처·stdout 정상 결과 여부·실패 단계를 적어라. [0,3]과 min0으로 >=를 >로 바꾼 변형의 합/개수를 비교하고 시험 관찰을 고른다. 이 새 기능은 설계이며 base에 구현하지 않았다. 마지막으로 소스 폴더 import만 확인한 상태에서 설치물 검증을 완료로 쓰지 않도록 다섯 단계 증거 카드를 구성하라. 실제 새 CLI/설정/시험/빌드/설치/학생 실행은 미수행이다.

힌트 1

명시 0은 미지정 None이 아니다. bad 이후 정상 결과는 공개하지 않는다. 필수성은 우선순위와 별도다.

힌트 2

정상과 변형의 합은 같아도 개수는 다르다. 배포물/새 환경/모듈 위치/CLI 관찰/미수행을 각각 적는다.

풀이와 답 확인

  1. R1은 명령줄 0을 채택하여 [0,3]을 고르므로 count=2 sum=3이다. R2는 파일 7을 채택하여 빈 선택의 count=0 sum=0이다. 둘 다 정상 상태 0이라는 설계다.

  2. R3는 자료 오류로 정상 결과 없음·실패 1이다. R4는 파싱에서 중단되며 자료 읽기 전 상태 2다.

  3. R5는 새 필수 파일 정책의 읽기 실패다. 이 설계에서는 자료/파일 오류 상태 1로 처리하고 정상 결과를 공개하지 않는다.

  4. 정상 [0,3]은 (2,3), > 변형은 [3]이라 (1,3)이다. 합만 검사하면 차이를 놓치므로 개수와 합을 함께 본다.

  5. 증거 카드에는 산출물 식별·새 실행기와 설치 버전·실제 모듈 위치/작업 경로·정상/오류 CLI 관찰·미수행 환경/외부 업로드를 둔다. 소스 import만으로 뒤 칸을 성공으로 채우지 않는다.

R1 명령줄 0/2와 3, R2 파일 7/0과 0, R3 자료 실패 1, R4 파싱 실패 2, R5 필수 읽기 실패 1이다. 경계 변형은 합 3이 같지만 개수 2와 1이 다르다. 설치물 검증은 아직 미수행이다.
