화면 앞의 사용자와 약속하기

CLI는 명령과 인자로 기능을 요청하는 인터페이스다. 자체 도구 sumtool은 UTF-8 텍스트의 한 줄에 정수 하나를 읽고 빈 줄을 무시한다. --min 이상인 값의 개수와 합을 표준 출력에 한 줄로 쓴다. 음수도 정수로 허용하지만 2.5 같은 문자열은 거부한다.

사용 예는 python sumtool.py numbers.txt --min 5다. --min의 기본값은 0이고 경계 값 자체도 포함한다. 입력 파일을 변경하지 않는 읽기 도구다. 성공 출력의 count는 필터를 통과한 정수 개수이며 전체 비어 있지 않은 줄 수와 다를 수 있다.

도움말·오류·결과의 통로

argparse는 위치 인자와 선택 인자를 해석하고 도움말과 사용법을 만든다. 기본 인자 오류는 stderr에 설명을 쓰고 종료 코드 2로 끝난다. 아래 코드에서 --help는 읽기를 시작하지 않고 도움말 뒤 종료 코드 0으로 끝난다.

자체 계약의 자료·파일 오류는 stderr에 error:로 시작하는 설명을 쓰고 코드 1을 반환한다. 성공은 stdout에 count와 sum을 쓰고 0을 반환한다. 호출 프로그램은 stdout만 결과로 다루고 종료 코드도 확인할 수 있다. 특정 외부 명령의 관행을 모든 도구의 규칙이라고 일반화하지 않는다.

작은 함수를 연결하기

read_numbers는 줄 번호를 붙여 자료 오류를 설명하고 summarize는 필터와 합계를 담당한다. main은 인자와 파일을 연결한다. 계산 함수는 파일 경로를 몰라도 시험할 수 있다. 예제는 학습용 작은 파일을 리스트에 담으며 임의 크기 입력에 대한 메모리 보장을 하지 않는다.

다음 코드를 UTF-8로 sumtool.py에 저장한다. 같은 폴더에 numbers.txt를 만들고 4, 5, 9를 각각 다른 줄에 적으면 --min 5에서 count=2 sum=14를 예상할 수 있다. 실행 전 현재 폴더와 Python 명령을 확인한다. 아래의 실제 확인 범위는 verification에 별도로 기록한다.

중간 과정을 따라가는 예제

자체 sumtool.py의 흐름을 읽고 파일의 줄 4, 5, 9를 --min 5로 처리할 때 결과를 설명하라. 빈 줄은 무시한다.

  1. import argparse
import sys

def read_numbers(lines):
    values = []
    for number, line in enumerate(lines, 1):
        text = line.strip()
        if not text:
            continue
        try:
            values.append(int(text))
        except ValueError as exc:
            raise ValueError(f'line {number}: expected integer') from exc
    return values

def summarize(values, minimum):
    selected = [value for value in values if value >= minimum]
    return len(selected), sum(selected)

def main(argv=None):
    parser = argparse.ArgumentParser(prog='sumtool')
    parser.add_argument('path')
    parser.add_argument('--min', type=int, default=0, dest='minimum')
    args = parser.parse_args(argv)
    try:
        with open(args.path, encoding='utf-8') as stream:
            values = read_numbers(stream)
        count, total = summarize(values, args.minimum)
    except (OSError, UnicodeError, ValueError) as exc:
        print(f'error: {exc}', file=sys.stderr)
        return 1
    print(f'count={count} sum={total}')
    return 0

if __name__ == '__main__':
    raise SystemExit(main())

  2. int 변환으로 [4, 5, 9]를 얻고 >= 5 조건으로 [5, 9]를 고른다. 개수는 2이고 합은 14다.

  3. main은 결과 한 줄을 stdout에 쓰고 0을 반환한다. 직접 스크립트를 실행하면 SystemExit가 그 값을 종료 코드로 전달한다.

정상 입력의 결과는 count=2 sum=14이며 성공 코드 0이다. --min 경계인 5도 포함된다.

필수 설정 파일을 못 읽었는데 기본값으로 조용히 계속해도 될까?

준비 개념과 학습 목표

준비 개념

  • 예외 처리

  • with

  • 기본값과 우선순위

학습 목표

  • 필수 파일과 선택 설정의 정책을 구별한다.

  • 실패 위치와 입력 줄 번호를 추적한다.

  • 자료 오류 뒤 부분 결과를 성공으로 내보내지 않는다.

설정의 출처와 우선순위

첫 예제의 설정은 기본 minimum 0 또는 명령줄 --min이다. 설정 파일을 더하면 예를 들어 명령줄, 파일, 기본값 순으로 채택한다고 정할 수 있다. 이 순서는 자체 정책이며 모든 라이브러리의 자동 우선순위가 아니다. 적용한 최종 값과 출처를 설명할 수 있게 설계한다.

ConfigParser.read는 열 수 없는 파일을 무시할 수 있으므로 필수 설정 실패를 자동으로 보장하지 않는다. 필수 파일은 with로 열고 read_file로 읽는 방법 등을 검토한다. 이 단원은 설정 정책을 설명하며 첫 예제에 INI 설정 기능을 구현했다고 주장하지 않는다.

실패를 원인과 단계로 구분하기

파일 없음과 읽기 권한 오류는 OSError 계열, UTF-8 해석 실패는 UnicodeError 계열로 나타날 수 있다. 정수 아닌 줄은 자체 ValueError로 줄 번호를 설명한다. 메시지의 운영체제별 세부 문구보다 실패 단계와 코드 계약을 먼저 확인한다.

첫 예제는 파일 전체를 읽고 검사한 후에만 성공 결과를 출력한다. 두 번째 줄이 bad이면 앞의 값은 내부 리스트에 들어갔어도 성공 합계를 내보내지 않는다. 모든 예외를 삼켜 0으로 반환하면 자료 문제를 성공으로 오해할 수 있다.

자원과 출력의 범위를 밝히기

with 블록을 벗어나면 파일이 닫히며 블록 안의 자료 오류에도 닫힘을 처리한다. 이것은 입력 읽기의 자원 관리다. 파일 내용을 고치거나 출력 파일의 원자 교체, 여러 프로세스의 동시 쓰기까지 구현한 것이 아니다.

sumtool의 stdout 쓰기 실패는 현재 코드의 자료 오류 처리 범위 밖이다. 닫힌 파이프, 매우 큰 입력과 서비스 보안 정책은 실제 운영 요구에 따라 추가로 설계한다. 작은 예제의 처리 범위를 모든 실패 상황의 완전 복구로 확장하지 않는다.

중간 과정을 따라가는 예제

첫 예제의 입력이 세 줄 4, bad, 9라면 read_numbers와 main의 흐름은?

  1. 첫 줄 4는 정수로 변환된다. 둘째 줄 bad의 int 변환이 ValueError를 일으킨다.

  2. read_numbers는 line 2: expected integer라는 자체 ValueError를 전파한다. with를 빠져나오며 파일을 닫는다.

  3. main은 stderr에 error: line 2: expected integer를 출력하고 1을 반환한다. 성공 count/sum은 출력하지 않고 셋째 줄 9도 이 호출에서 처리되지 않는다.

자료 오류 코드 1이며 부분 합 4를 정상 결과로 내보내지 않는다.

경계와 계약에서 시험 고르기

sumtool의 >= 조건을 >로 잘못 바꾸면 경계 5를 놓친다. [4,5,9]와 minimum 5의 기대 (2,14)는 그 차이를 잡는다. 빈 입력의 (0,0), 잘못된 줄의 ValueError도 따로 시험한다. 기대값은 구현 출력을 그대로 복사하기보다 사용 계약에서 계산한다.

아래 시험을 UTF-8 test_sumtool.py로 sumtool.py 옆에 저장할 수 있다. 파일 이름이 같아야 import가 해당 모듈을 찾는다. import 때 main은 실행되지 않도록 __name__ 조건을 사용했다. 시험 환경과 실제 학습자 환경의 실행 결과는 별도로 기록한다.

작은 단위와 연결 경로

unittest의 assertEqual은 값을 비교하고 assertRaises는 지정한 예외를 기대한다. 단위 시험은 함수의 계약을 확인한다. CLI 연결은 정상 파일과 잘못된 인자를 별도로 주어 출력 통로와 종료 상태까지 살펴야 한다.

세 단위 시험의 통과가 모든 OS, 모든 크기와 모든 오류를 검증하지 않는다. 도움말과 missing 파일, 잘못된 UTF-8도 추가 후보이며 실제 수행한 입력만 실행 기록에 적는다. 기능이 바뀌면 사용 계약과 시험의 기대값을 함께 재검토한다.

README를 실행 안내로 쓰기

자체 README 초안에는 Python 버전, sumtool.py와 numbers.txt의 위치, 입력 인코딩, 실행 명령과 예상 출력을 적는다. 프로그램 소개만 길게 쓰고 실행 폴더를 생략하면 입문자는 파일을 못 찾을 수 있다. 명령의 python은 해당 환경에서 확인한 실행기 이름으로 바꾼다.

정상 예와 실패 예를 구분하여 bad 줄이면 코드 1, --min five이면 코드 2라는 계약을 안내한다. 파일 경로에 공백이 있으면 쉘에서 한 인자로 전달할 인용 방법도 설명한다. 개인정보가 담긴 실제 입력이나 비밀 설정을 README 예로 올리지 않고 자체 작은 자료를 사용한다.

중간 과정을 따라가는 예제

소단원 15.4

패키징 입문과 배포환경 기록

소스가 내 폴더에서 실행되면 설치 가능한 패키지도 이미 만들어진 걸까?

준비 개념과 학습 목표

준비 개념

  • 모듈과 package

  • 가상환경

  • 버전과 dependency

학습 목표

  • 소스·sdist·wheel과 설치를 구별한다.

  • 빌드 backend와 runtime dependency를 나눈다.

  • 검증한 환경과 미수행 배포를 기록한다.

소스 실행과 배포물 생성

sumtool.py를 직접 실행하는 단계와 설치 가능한 프로젝트를 만드는 단계는 다르다. PyPA의 공개 입문 자료는 pyproject.toml, README, LICENSE와 src 아래 package의 구조를 보여 준다. 배포 이름과 import 이름의 구별도 이후 설치 시험에서 확인한다.

sdist는 소스 배포, wheel은 빌드된 배포 형식이다. 이름에 built가 있다고 모든 wheel에 기계어가 들어가는 것은 아니다. 현재 단원은 구조와 확인 계획을 다루며 첫 sumtool을 실제 패키지로 만들거나 등록하지 않았다.

빌드 조건과 실행 조건

pyproject.toml의 build-system에는 backend와 빌드에 필요한 dependency를 적는다. project에는 이름, 버전, README와 지원 Python 조건 같은 metadata를 넣는다. runtime dependency와 빌드 도구의 dependency는 역할이 다르다.

버전 제약의 >= 표기는 설치 조건이지 미래 모든 버전에서 직접 시험했다는 증거가 아니다. 필요한 자원 파일이 배포물에 포함됐는지도 backend 설정과 결과물에서 확인해야 한다. 소스 폴더에 파일이 있다는 사실만으로 설치 뒤 같은 상대 경로가 있다고 가정하지 않는다.

다른 환경에서 다시 확인하기

확인 계획은 빌드 도구 준비, 프로젝트 폴더에서 python -m build, 결과물 검사, 새 가상환경에 로컬 wheel 설치, import와 CLI 실행의 순서로 적는다. 실제 실행한 단계만 완료로 기록한다. 외부 패키지 서버에 올리는 것은 별도의 공개 행동이다.

환경 기록에는 Python과 OS 버전, dependency와 도구 버전, 명령, 입력과 관찰 결과를 적는다. 이 단원의 소규모 함수 시험이 있었다면 그 실행 범위만 적고 새 환경 설치나 다른 OS 시험은 미수행으로 유지한다. 라이선스는 실제 프로젝트의 승인된 조건과 일치시킨다.

중간 과정을 따라가는 예제

자체 가상 확인표에서 소스 함수 시험은 완료, sdist/wheel 생성은 계획, 새 환경 설치와 CLI 확인은 미수행이다. 프로젝트의 Python 조건을 >=3.10으로 적었다. 무엇을 배포 완료라고 말할 수 있나?

  1. 완료한 증거는 기록된 환경의 소스 함수 시험뿐이다. 배포물과 설치 확인은 실제 결과가 없다.

  2. Python >=3.10은 지원 조건을 선언한 metadata이며 모든 해당 버전의 시험 목록이 아니다.

  3. 빌드와 새 환경 설치, 실제 CLI 확인을 후속 계획으로 남긴다. 외부 업로드를 수행했다고 쓰지 않는다.

소스 함수 시험 범위만 완료라고 설명하고 패키징·설치·공개 배포는 미완료로 기록한다.
