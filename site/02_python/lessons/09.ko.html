소단원 9.1

예외의 발생·전파

작은 함수의 실패를 호출한 사람이 어떻게 알아차릴까?

준비 개념과 학습 목표

준비 개념

  • 함수 호출과 반환

  • 정수 변환과 나눗셈

학습 목표

  • 실패 지점 이후의 실행을 추적한다.

  • 예외 종류와 호출 경계를 구별한다.

돌아올 값 대신 전달되는 실패

배송 수량을 읽는 함수가 숫자 대신 글자를 받았다고 생각해 보자. int("두 개")는 정수를 만들지 못하므로 ValueError가 발생한다. 그 문장 다음의 성공 경로는 진행하지 않는다. 잘못된 입력을 0개로 취급하면 실제 주문과 구별할 수 없으므로 실패를 별도로 전달하는 편이 낫다.

예외는 종류와 정보를 가진 객체다. ZeroDivisionError는 나눗셈의 0인 분모, ValueError는 값의 형식 문제처럼 실패 원인을 구별하는 이름이다. 문법을 해석하지 못하는 SyntaxError와 실행 중 나타나는 예외도 구별해야 한다.

호출 경계를 따라 올라가기

안쪽 함수에 처리기가 없으면 실패가 호출한 함수로 전파된다. 처리기를 찾기 전까지 각 함수의 정상 반환 경로와 아직 실행하지 않은 문장을 건너뛴다. 호출 스택을 아래에서 위로 읽으면 누가 오류를 처리할 수 있는지 알 수 있다.

다음 예제에서 parse는 변환만 맡고 request는 사용자 안내를 맡는다. 예외를 request에서 처리하면 화면의 계속 실행 여부를 결정할 수 있다. 처리되지 않으면 프로그램의 실행 맥락까지 전파되며 traceback은 실패 지점과 호출 경로를 조사하는 단서가 된다.

def parse(text):
    return int(text)

def request(text):
    try:
        count = parse(text)
        return count * 3
    except ValueError:
        return "수량을 숫자로 입력하세요"

직접 발생시키기와 다시 전달하기

음수 수량처럼 변환은 성공해도 업무 규칙을 어기는 경우에는 raise ValueError("수량은 0 이상이어야 합니다")처럼 직접 실패를 표시할 수 있다. 문자열 변환의 성공과 주문 수량의 유효성은 서로 다른 조건이다.

현재 예외를 기록한 뒤 위쪽에서 결정하게 하려면 except 안의 bare raise로 다시 전달한다. 실패를 새로운 의미의 예외로 바꿀 때는 raise ... from ...으로 원인을 연결할 수 있다. 오류를 기록했다는 사실만으로 문제가 해결된 것은 아니다.

중간 과정을 따라가는 예제

위 코드에 request("4")와 request("네 개")를 각각 넣는다. 다른 오류는 없다고 가정하고 반환 경로를 비교하라.

  1. "4"는 parse에서 정수 4로 변환된다.

  2. request의 count는 4이고 4×3=12를 반환한다.

  3. "네 개"의 int 변환은 ValueError를 발생시켜 count 대입과 곱셈을 건너뛴다.

  4. 호출한 request의 ValueError 처리기로 이동해 안내 문자열을 반환한다.

첫 호출은 12, 둘째 호출은 안내 문자열이다. 실패 경로에서는 숫자 결과를 만들지 않는다.

풀이 보기

오해와 반례

안쪽 함수에서 예외가 나면 호출한 함수도 반드시 종료된다.

상위 호출자가 맞는 예외를 처리하면 이후 실행을 계속할 수 있다. 다만 실패한 함수의 중단된 문장부터 자동으로 재개되는 것은 아니다.

소단원 9.2

try·except·finally

성공·실패와 관계없이 정리할 일이 있다면 어디에 둘까?

준비 개념과 학습 목표

준비 개념

  • 예외 종류

  • 조건 분기

학습 목표

  • try의 네 경로를 구별한다.

  • finally에서 결과를 덮어쓰는 위험을 설명한다.

작은 보호 구간과 맞는 처리기

try에는 실패 가능성이 있는 작업을 좁게 넣는다. except ValueError는 그 보호 구간에서 전파된 해당 종류의 예외를 처리한다. 여러 처리기가 있으면 먼저 맞는 하나가 선택되므로 넓은 종류를 먼저 쓰면 구체적인 처리가 가려질 수 있다.

처리기 안에서 새 오류가 발생해도 같은 try에 나열된 다음 except가 그것을 이어서 잡지는 않는다. 예외 처리 자체도 실패할 수 있으므로 보호 구간과 처리 구간을 다른 단계로 읽어야 한다.

성공 구간과 마무리 구간

else는 try가 예외 없이 정상 완료되었을 때 실행한다. finally는 정상 완료, 처리된 예외, 아직 전파 중인 예외와 반환 등에서 마무리를 담당한다. 실패가 처리되지 않았다면 finally 이후에 전파가 이어진다.

아래 코드는 사건 이름을 붙여 경로를 살펴보는 예제다. n 변환이 실패하면 else에 들어가지 않는다. else에서 오류가 생기면 앞의 ValueError 처리기가 받지 않으며 finally는 실행된다.

events = []
try:
    n = int(text)
    events.append("변환")
except ValueError:
    events.append("입력 오류")
else:
    events.append("성공")
finally:
    events.append("정리")

정리가 원래 결과를 가리지 않도록

finally 안에서 return을 쓰면 try의 반환값이나 전파 중인 예외를 덮어쓸 수 있다. 마무리 코드는 닫기·해제 같은 책임에 집중하고, 결과 선택은 성공·실패 구간에서 하는 편이 흐름을 이해하기 쉽다.

finally는 언어의 정상적인 제어 흐름에서 제공되는 정리 규칙이다. 프로세스 강제 종료나 전원 차단까지 정리를 보장하는 저장 장치로 해석해서는 안 된다. 중요한 외부 기록의 복구는 별도 설계가 필요하다.

중간 과정을 따라가는 예제

위 코드에서 text가 "8" 또는 "여덟"일 때 events를 구하라. append 자체는 실패하지 않는다고 가정한다.

  1. "8"의 변환은 성공해 "변환"을 추가한다.

  2. try 정상 완료 후 else에서 "성공"을 추가한다. finally에서 "정리"를 추가한다.

  3. "여덟"은 int에서 실패하므로 "변환"도 추가하지 않는다.

  4. except가 "입력 오류"를 추가하고 else는 생략한다. finally에서 "정리"를 추가한다.

성공은 [변환, 성공, 정리], 실패는 [입력 오류, 정리]다.

종이와 본문으로 직접 해보기

try가 ZeroDivisionError를 발생시키고 except는 ValueError만 받는다고 하자. finally가 "정리"를 기록하면 마지막 상태는?

힌트 보기

발생한 종류와 처리기의 종류가 맞는지 먼저 비교한다.

풀이 보기

ValueError 처리기는 선택되지 않는다. finally가 정리를 기록한 뒤 ZeroDivisionError가 바깥으로 전파된다. 정리 수행과 실패 처리 완료는 다르다.

오해와 반례

finally가 실행되었으므로 예외가 해결되었다.

정리만 하고 처리되지 않은 예외를 계속 전달할 수 있다. 정리를 확인하는 로그와 작업 성공을 확인하는 로그를 구별해야 한다.

답과 이유 보기

같은 try의 다음 except가 처리기 안에서 난 오류를 잡는가?

답과 이유 보기

아니다.

처리기 본문은 원래 보호 구간 밖이다.

finally의 return은 왜 피하는가?

답과 이유 보기

원래 반환값 또는 예외를 가릴 수 있다.

정리 구간에서 새 제어 흐름을 선택하기 때문이다.

한 단계 더

성공, 예상된 입력 실패, 예상하지 못한 실패의 세 경로에 사건표를 그리고 finally의 공통 부분을 표시해 보자.

소단원 9.3

with와 context manager

파일을 열고 난 뒤 계산이 실패해도 닫는 책임을 잊지 않으려면?

준비 개념과 학습 목표

준비 개념

  • 파일 열기와 닫기

  • finally

학습 목표

  • with의 진입·본문·종료를 추적한다.

  • 종료 호출과 예외 억제를 구별한다.

자원 수명에 경계 붙이기

파일 손잡이처럼 사용하는 동안 유지하고 끝나면 반환할 자원에는 수명이 있다. with open(...) as f:는 파일 사용 구간을 들여쓰기로 보여 주고 종료 시 닫기를 맡긴다. 파일 전체 데이터를 메모리에 보관하는 것과 열린 자원을 보유하는 것은 다른 문제다.

파일 열기 자체가 실패하면 본문에 들어가지 못한다. 자원 획득 성공을 전제로 한 정리를 획득 실패에도 무조건 수행하는 방식보다, 성공한 수명에 정리를 묶는 방식이 안전하다.

with open("counts.txt", encoding="utf-8") as f:
    first = f.readline()
    count = int(first)
# 이 위치에서는 파일 사용 구간이 끝났다.

진입과 종료의 약속

context manager는 __enter__와 __exit__를 통해 진입과 종료를 제공한다. __enter__가 정상 반환한 뒤에는 본문 또는 as 대상 대입에서 오류가 생겨도 __exit__가 호출된다. __enter__ 자체가 실패하면 그 관리자의 __exit__ 호출을 기대할 수 없다.

as에 받는 값은 관리자의 __enter__ 반환값이다. 항상 관리자 객체 그 자체일 필요는 없다. 이 구별은 연결을 관리하는 객체가 실제 사용할 연결 손잡이를 따로 돌려주는 설계에서도 중요하다.

종료 호출은 실패를 지운다는 뜻이 아니다

본문에서 예외가 나면 __exit__는 그 정보를 받는다. 그 반환값이 참이면 해당 예외를 억제하고 거짓이면 전파를 계속한다. 정상 종료에서는 이 반환값으로 본문의 반환 위치를 바꾸지 않는다.

파일의 with 사용은 파일을 닫지만 int 변환 실패를 성공으로 바꾸지는 않는다. 여러 자원을 중첩하여 진입하면 안쪽 자원부터 종료한다. 뒤쪽 자원 획득 실패 시에도 먼저 성공한 바깥 자원의 정리가 필요하다.

중간 과정을 따라가는 예제

파일 열기와 readline은 성공하고 첫 줄은 "많음"이라고 가정한다. 위 코드의 파일 상태와 예외 경로를 추적하라.

  1. open과 진입이 성공하여 f를 얻는다.

  2. readline이 "많음"을 first에 저장한다.

  3. int(first)에서 ValueError가 발생하므로 count 대입은 완료되지 않는다.

  4. 파일 관리자의 종료 처리가 파일을 닫고 예외는 바깥으로 이어진다.

파일은 닫히고 ValueError는 처리되지 않은 상태로 전파된다.

소단원 9.4

오류 분류와 복구

다시 입력받기, 재시도하기, 개발자가 고치기는 어떤 기준으로 나눌까?

준비 개념과 학습 목표

준비 개념

  • 입력 검증

  • 예외 처리와 함수 경계

학습 목표

  • 실패 원인에 맞는 복구 정책을 정한다.

  • 일시 실패의 제한된 재시도와 버그 수정의 차이를 설명한다.

이름보다 원인과 책임 보기

수량 문자열이 잘못된 경우에는 사용자가 입력을 고칠 수 있다. 파일 경로가 없는 경우에는 경로 설정이나 파일 준비를 확인해야 한다. 내부 인덱스 계산이 틀린 경우에는 개발자가 코드를 고쳐야 한다. 모두 같은 기본값으로 대체하면 책임과 해결 방법이 사라진다.

예외 종류는 분류의 단서지만 업무 맥락까지 설명하지는 않는다. 같은 ValueError도 사용자의 입력과 개발자가 잘못 넘긴 내부 값에서 생길 수 있다. 예상 가능한 실패는 조건과 안내를 명시하고, 예상 밖 오류는 원인을 보존해 조사한다.

재시도는 조건을 바꾸거나 기다릴 근거가 있어야 한다

숫자가 아닌 문자열에 같은 int 변환을 반복해도 성공하지 않는다. 반면 일시적인 외부 연결 실패는 제한된 재시도를 고려할 수 있다. 횟수, 대기 시간, 마지막 실패 전달 방법을 정하고 무한 반복을 피한다.

재시도 대상 작업이 외부 효과를 남겼는지도 중요하다. 응답을 못 받았다고 결제 자체가 실패했다고 단정하고 다시 수행하면 중복 결제가 생길 수 있다. 실제 서비스에서는 작업 식별자와 결과 확인 등 중복 효과를 통제하는 정책이 별도로 필요하다.

복구한 척하지 않고 결과를 구별하기

입력 오류를 안내하고 새 입력을 요청하는 것은 복구 기회를 주는 일이다. 오류를 기록만 하거나 조용히 무시하는 것은 복구와 다르다. 함수의 반환 규약에 성공 결과와 실패 상태를 구별할 방법을 마련해야 한다.

일반적인 except Exception으로 기록 후 raise하는 것은 예상 밖 실패를 보존하는 한 방법이다. KeyboardInterrupt와 SystemExit 등은 Exception의 범위 밖이며 프로그램 종료 신호까지 무조건 삼키지 않는다. 광범위한 처리가 특정 실패의 복구 규칙을 대신할 수는 없다.

중간 과정을 따라가는 예제

가상 읽기 작업은 외부 쓰기 효과가 없고 최대 3회 시도한다. 관찰 결과는 일시 실패, 일시 실패, 값 6이다. 성공하면 즉시 멈추는 정책을 추적하라.

  1. 1회는 실패하므로 정한 대기 뒤 다음 기회를 사용한다.

  2. 2회도 실패하여 남은 기회는 1회다.

  3. 3회에 값 6을 얻으므로 반복을 종료하고 성공 결과를 전달한다.

  4. 세 번 모두 실패하는 다른 경로에서는 마지막 오류를 전달하며 4회째를 실행하지 않는다.

주어진 경로는 3회 수행 후 값 6으로 성공한다. 재시도 한도는 3회이며 성공을 보장하지 않는다.

종이와 본문으로 직접 해보기

입력 "abc", 없는 로컬 파일, 내부 배열 경계 버그에 대해 첫 조치를 각각 정하라.

힌트 보기

같은 요청을 반복하면 실패 조건이 바뀌는지 생각한다.

풀이 보기

"abc"는 숫자 형식 안내 후 새 입력을 요청한다. 없는 파일은 경로와 준비 상태를 확인한다. 내부 경계 버그는 재현 경로를 보존하고 코드를 수정한다. 세 경우 모두 무조건 동일 요청을 반복하는 정책은 부적절하다.

오해와 반례

예외를 잡으면 문제를 해결한 것이다.

처리기는 실패를 보고할 수도 있고 다시 전달할 수도 있다. 성공 조건을 회복했는지와 정해진 대체 동작을 수행했는지 확인해야 복구라고 할 수 있다.

자기점검

같은 "abc"를 int로 3번 바꾸면?

답과 이유 보기

매번 실패한다.

입력 조건이 바뀌지 않았다.

최대 3회가 성공을 보장하는가?

답과 이유 보기

아니다.

한도는 자원 사용을 제한할 뿐 실패 원인을 제거하지 않는다.

응답 없는 외부 쓰기를 바로 반복해도 되는가?

답과 이유 보기

중복 효과와 결과 확인 정책을 먼저 검토한다.

응답 실패와 작업 수행 실패는 같다고 단정할 수 없다.
