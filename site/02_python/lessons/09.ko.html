예외의 발생·전파

작은 함수의 실패를 호출한 사람이 어떻게 알아차릴까?

준비 개념과 학습 목표

준비 개념

  • 함수 호출과 반환

  • 정수 변환과 나눗셈

학습 목표

  • 실패 지점 이후의 실행을 추적한다.

  • 예외 종류와 호출 경계를 구별한다.

오류를 알렸는데 앞서 바꾼 리스트는 원래대로 돌아갈까?

친구에게 맡긴 계산이 실패했다고 해서 앞서 써 놓은 메모가 저절로 지워지지는 않는다. 예외는 실행 경로를 바꾸지만 일반 리스트의 변경을 되돌리는 거래 기능은 아니다. 이 차이를 놓치면 “실패했으니 재시도해도 된다”는 잘못된 판단을 하게 된다.

자체 함수 append_count(log,text)는 먼저 log에 "start"를 추가하고 n=int(text)를 계산한 뒤, n<0이면 ValueError를 발생시킨다. 성공할 때만 n을 추가하고 반환한다. log는 이 과제에서 내장 리스트, text는 내장 문자열이고 append와 메모리 할당 실패는 제외한다. 호출자는 ValueError만 처리하며 실패한 함수의 중간부터 재개하지 않는다.

형식 오류와 업무 범위 오류를 구별하고 싶다면 경계에서 새 의미의 예외로 연결할 수 있다. 예외 이름을 바꿀 때 원인을 남기는 raise ... from ...과 기록 후 같은 예외를 전달하는 bare raise는 서로 다른 목적이다.

먼저 확인할 개념
  • 반환 완료와 호출 경계

    성공한 반환과 전파로 종료한 호출을 구별한다.

  • 공유 리스트의 변경

    호출 전에 가진 별칭이 실패 뒤에도 같은 log의 변경을 관찰한다.

돌아올 값 대신 전달되는 실패

배송 수량을 읽는 함수가 숫자 대신 글자를 받았다고 생각해 보자. int("두 개")는 정수를 만들지 못하므로 ValueError가 발생한다. 그 문장 다음의 성공 경로는 진행하지 않는다. 잘못된 입력을 0개로 취급하면 실제 주문과 구별할 수 없으므로 실패를 별도로 전달하는 편이 낫다.

예외는 종류와 정보를 가진 객체다. ZeroDivisionError는 나눗셈의 0인 분모, ValueError는 값의 형식 문제처럼 실패 원인을 구별하는 이름이다. 문법을 해석하지 못하는 SyntaxError와 실행 중 나타나는 예외도 구별해야 한다.

호출 경계를 따라 올라가기

안쪽 함수에 처리기가 없으면 실패가 호출한 함수로 전파된다. 처리기를 찾기 전까지 각 함수의 정상 반환 경로와 아직 실행하지 않은 문장을 건너뛴다. 호출 스택을 아래에서 위로 읽으면 누가 오류를 처리할 수 있는지 알 수 있다.

다음 예제에서 parse는 변환만 맡고 request는 사용자 안내를 맡는다. 예외를 request에서 처리하면 화면의 계속 실행 여부를 결정할 수 있다. 처리되지 않으면 프로그램의 실행 맥락까지 전파되며 traceback은 실패 지점과 호출 경로를 조사하는 단서가 된다.

def parse(text):
    return int(text)

def request(text):
    try:
        count = parse(text)
        return count * 3
    except ValueError:
        return "수량을 숫자로 입력하세요"

직접 발생시키기와 다시 전달하기

음수 수량처럼 변환은 성공해도 업무 규칙을 어기는 경우에는 raise ValueError("수량은 0 이상이어야 합니다")처럼 직접 실패를 표시할 수 있다. 문자열 변환의 성공과 주문 수량의 유효성은 서로 다른 조건이다.

현재 예외를 기록한 뒤 위쪽에서 결정하게 하려면 except 안의 bare raise로 다시 전달한다. 실패를 새로운 의미의 예외로 바꿀 때는 raise ... from ...으로 원인을 연결할 수 있다. 오류를 기록했다는 사실만으로 문제가 해결된 것은 아니다.

중간 과정을 따라가는 예제

위 코드에 request("4")와 request("네 개")를 각각 넣는다. 다른 오류는 없다고 가정하고 반환 경로를 비교하라.

  1. "4"는 parse에서 정수 4로 변환된다.

  2. request의 count는 4이고 4×3=12를 반환한다.

  3. "네 개"의 int 변환은 ValueError를 발생시켜 count 대입과 곱셈을 건너뛴다.

  4. 호출한 request의 ValueError 처리기로 이동해 안내 문자열을 반환한다.

첫 호출은 12, 둘째 호출은 안내 문자열이다. 실패 경로에서는 숫자 결과를 만들지 않는다.

원인 연결과 다시 발생시키기

parse가 int("bad")에서 ValueError를 발생시킨다. 경계에서 except ValueError as err: raise RuntimeError("수량 읽기 실패") from err로 바꾸면 호출자는 무엇을 받는가?

  1. 바깥으로 전달되는 현재 종류는 RuntimeError다.

  2. 직접 원인은 err인 ValueError로 연결된다.

  3. 같은 위치의 bare raise라면 ValueError 자체가 전달된다.

현재 종류와 원인을 따로 기록한다. RuntimeError를 ValueError 처리기만으로 받지는 못한다.

소단원 9.2

try·except·finally

성공·실패와 관계없이 정리할 일이 있다면 어디에 둘까?

준비 개념과 학습 목표

준비 개념

  • 예외 종류

  • 조건 분기

학습 목표

  • try의 네 경로를 구별한다.

  • finally에서 결과를 덮어쓰는 위험을 설명한다.

정리 로그가 있는데 왜 함수는 여전히 실패할까?

교실을 정리했다는 확인과 수업 과제를 완성했다는 확인은 별개다. try/except/else/finally도 같은 구분이 필요하다. 특히 else 또는 처리기에서 생긴 새 오류는 동일 try의 다른 except가 받지 않는다.

자체 read_half(text,events)는 try에서 n=int(text)와 "parsed" 기록을 수행한다. ValueError 처리기는 "bad"를 기록하고 None을 반환한다. else는 "ok"를 기록한 뒤 10/n을 반환한다. finally는 "clean"만 기록한다. text는 문자열이며 사건 기록 자체는 실패하지 않는다고 가정한다. 정상적인 언어 제어 흐름만 다루며 강제 종료는 제외한다.

return 표현은 finally 전에 계산된다. finally에서 반환을 덮어쓰지 않더라도 반환할 가변 객체를 변경하면 호출자가 관찰하는 내용은 달라질 수 있다. 반환값의 선택과 같은 객체의 내용 변경을 분리해 추적하자.

  • 반환 표현의 값

  • 같은 리스트 객체

    finally가 반환 예정 리스트를 바꾸면 호출자가 변경된 객체를 받는다.

작은 보호 구간과 맞는 처리기

try에는 실패 가능성이 있는 작업을 좁게 넣는다. except ValueError는 그 보호 구간에서 전파된 해당 종류의 예외를 처리한다. 여러 처리기가 있으면 먼저 맞는 하나가 선택되므로 넓은 종류를 먼저 쓰면 구체적인 처리가 가려질 수 있다.

처리기 안에서 새 오류가 발생해도 같은 try에 나열된 다음 except가 그것을 이어서 잡지는 않는다. 예외 처리 자체도 실패할 수 있으므로 보호 구간과 처리 구간을 다른 단계로 읽어야 한다.

성공 구간과 마무리 구간

else는 try가 예외 없이 정상 완료되었을 때 실행한다. finally는 정상 완료, 처리된 예외, 아직 전파 중인 예외와 반환 등에서 마무리를 담당한다. 실패가 처리되지 않았다면 finally 이후에 전파가 이어진다.

아래 코드는 사건 이름을 붙여 경로를 살펴보는 예제다. n 변환이 실패하면 else에 들어가지 않는다. else에서 오류가 생기면 앞의 ValueError 처리기가 받지 않으며 finally는 실행된다.

events = []
try:
    n = int(text)
    events.append("변환")
except ValueError:
    events.append("입력 오류")
else:
    events.append("성공")
finally:
    events.append("정리")

정리가 원래 결과를 가리지 않도록

finally 안에서 return을 쓰면 try의 반환값이나 전파 중인 예외를 덮어쓸 수 있다. 마무리 코드는 닫기·해제 같은 책임에 집중하고, 결과 선택은 성공·실패 구간에서 하는 편이 흐름을 이해하기 쉽다.

finally는 언어의 정상적인 제어 흐름에서 제공되는 정리 규칙이다. 프로세스 강제 종료나 전원 차단까지 정리를 보장하는 저장 장치로 해석해서는 안 된다. 중요한 외부 기록의 복구는 별도 설계가 필요하다.

with와 context manager

파일을 열고 난 뒤 계산이 실패해도 닫는 책임을 잊지 않으려면?

준비 개념과 학습 목표

준비 개념

  • 파일 열기와 닫기

  • finally

학습 목표

  • with의 진입·본문·종료를 추적한다.

  • 종료 호출과 예외 억제를 구별한다.

안쪽 관리자가 실패를 억제하면 바깥 관리자는 어떤 종료 정보를 받을까?

여러 자원을 사용하는 동안 누가 실제 진입했는지를 표시하면 정리 순서를 이해할 수 있다. 실패한 진입에 대응하는 종료는 호출되지 않으며, 이미 진입한 바깥 관리자는 실패 정보를 받는다. 이 규칙은 실제 파일을 만들지 않고 사건 카드로 탐구할 수 있다.

자체 관리자 A/B의 진입 반환은 각각 "a-handle"/"b-handle"이며 관리자 객체 자체와 다르다. 종료는 이름과 오류 종류 또는 None을 기록한다. 별도 명시한 경우 외에는 진입/종료/기록이 정상적으로 끝나고 종료 반환은 False다. 본문의 ValueError를 B가 True로 억제하면 바깥 A의 종료에는 예외가 없는 정상 정보가 전달된다.

with A as a, B as b는 중첩으로 읽는다. as 대입 자체의 실패도 성공한 진입 뒤의 실패라 종료 대상이다. 종료 시도와 성공적인 자원 반환, 예외 억제, 외부 저장의 지속성은 서로 다른 주장이다.

먼저 확인할 개념
  • 정리와 실패 전파

    종료 메서드가 실행된 사실과 실패가 처리된 사실을 나눈다.

  • 진입 메서드의 반환

    as가 받는 손잡이와 관리자 객체를 구별한다.

자원 수명에 경계 붙이기

파일 손잡이처럼 사용하는 동안 유지하고 끝나면 반환할 자원에는 수명이 있다. with open(...) as f:는 파일 사용 구간을 들여쓰기로 보여 주고 종료 시 닫기를 맡긴다. 파일 전체 데이터를 메모리에 보관하는 것과 열린 자원을 보유하는 것은 다른 문제다.

파일 열기 자체가 실패하면 본문에 들어가지 못한다. 자원 획득 성공을 전제로 한 정리를 획득 실패에도 무조건 수행하는 방식보다, 성공한 수명에 정리를 묶는 방식이 안전하다.

with open("counts.txt", encoding="utf-8") as f:
    first = f.readline()
    count = int(first)
# 이 위치에서는 파일 사용 구간이 끝났다.

진입과 종료의 약속

context manager는 __enter__와 __exit__를 통해 진입과 종료를 제공한다. __enter__가 정상 반환한 뒤에는 본문 또는 as 대상 대입에서 오류가 생겨도 __exit__가 호출된다. __enter__ 자체가 실패하면 그 관리자의 __exit__ 호출을 기대할 수 없다.

as에 받는 값은 관리자의 __enter__ 반환값이다. 항상 관리자 객체 그 자체일 필요는 없다. 이 구별은 연결을 관리하는 객체가 실제 사용할 연결 손잡이를 따로 돌려주는 설계에서도 중요하다.

종료 호출은 실패를 지운다는 뜻이 아니다

본문에서 예외가 나면 __exit__는 그 정보를 받는다. 그 반환값이 참이면 해당 예외를 억제하고 거짓이면 전파를 계속한다. 정상 종료에서는 이 반환값으로 본문의 반환 위치를 바꾸지 않는다.

파일의 with 사용은 파일을 닫지만 int 변환 실패를 성공으로 바꾸지는 않는다. 여러 자원을 중첩하여 진입하면 안쪽 자원부터 종료한다. 뒤쪽 자원 획득 실패 시에도 먼저 성공한 바깥 자원의 정리가 필요하다.

준비 개념과 학습 목표

  • 예외 처리와 함수 경계

재시도 횟수를 정하기 전에 무엇이 이미 변경됐는지 확인했을까?

학생 명단 일부를 읽고 나서 한 줄이 잘못됐을 때, 처음부터 다시 읽으면 이미 반영한 앞줄이 중복될 수 있다. 읽기 실패라는 이름만 보고 안전한 재시도로 분류하지 말고 관찰한 효과를 먼저 확인하자.

자체 변환 작업은 text 목록을 순서대로 int로 바꾸어 공유 out에 즉시 추가한다. ["2","bad","4"]에서 변환 실패 뒤 out=[2]가 남는다. 새 입력을 받는 정책, 지역 후보를 만든 뒤 예상 검사가 모두 성공하면 반영하는 정책, 읽기만 하는 일시 실패의 제한 재시도는 서로 다른 복구다.

여기서 최대 3회는 처음 시도를 포함한다. 각 시도 시간이 2ms, 실패 뒤 대기가 3ms라면 두 실패 후 세 번째 성공까지 2+3+2+3+2=12ms다. 작업/대기 시간은 가정이며 실제 서비스 지연이나 성공 확률을 뜻하지 않는다.

먼저 확인할 개념
  • 예외 전 부작용

    앞서 완료한 변경이 남아 재시도에 영향을 줄 수 있음을 확인한다.

  • 지역 변수와 외부 상태

    검증 후보를 지역에 두고 언제 외부 out을 바꿀지 정한다.

이름보다 원인과 책임 보기

수량 문자열이 잘못된 경우에는 사용자가 입력을 고칠 수 있다. 파일 경로가 없는 경우에는 경로 설정이나 파일 준비를 확인해야 한다. 내부 인덱스 계산이 틀린 경우에는 개발자가 코드를 고쳐야 한다. 모두 같은 기본값으로 대체하면 책임과 해결 방법이 사라진다.

예외 종류는 분류의 단서지만 업무 맥락까지 설명하지는 않는다. 같은 ValueError도 사용자의 입력과 개발자가 잘못 넘긴 내부 값에서 생길 수 있다. 예상 가능한 실패는 조건과 안내를 명시하고, 예상 밖 오류는 원인을 보존해 조사한다.

재시도는 조건을 바꾸거나 기다릴 근거가 있어야 한다

숫자가 아닌 문자열에 같은 int 변환을 반복해도 성공하지 않는다. 반면 일시적인 외부 연결 실패는 제한된 재시도를 고려할 수 있다. 횟수, 대기 시간, 마지막 실패 전달 방법을 정하고 무한 반복을 피한다.

재시도 대상 작업이 외부 효과를 남겼는지도 중요하다. 응답을 못 받았다고 결제 자체가 실패했다고 단정하고 다시 수행하면 중복 결제가 생길 수 있다. 실제 서비스에서는 작업 식별자와 결과 확인 등 중복 효과를 통제하는 정책이 별도로 필요하다.

복구한 척하지 않고 결과를 구별하기

입력 오류를 안내하고 새 입력을 요청하는 것은 복구 기회를 주는 일이다. 오류를 기록만 하거나 조용히 무시하는 것은 복구와 다르다. 함수의 반환 규약에 성공 결과와 실패 상태를 구별할 방법을 마련해야 한다.

일반적인 except Exception으로 기록 후 raise하는 것은 예상 밖 실패를 보존하는 한 방법이다. KeyboardInterrupt와 SystemExit 등은 Exception의 범위 밖이며 프로그램 종료 신호까지 무조건 삼키지 않는다. 광범위한 처리가 특정 실패의 복구 규칙을 대신할 수는 없다.

  1. 1회는 실패하므로 정한 대기 뒤 다음 기회를 사용한다.

  2. 2회도 실패하여 남은 기회는 1회다.

  3. 3회에 값 6을 얻으므로 반복을 종료하고 성공 결과를 전달한다.

주어진 경로는 3회 수행 후 값 6으로 성공한다. 재시도 한도는 3회이며 성공을 보장하지 않는다.

시도 2회, 시간 7ms, 반환 8이다.

다른 문제에 적용하기

세 방식/입력 비교는 각각 새 out=[9]에서 시작한다. 즉시 추가 방식의 같은 입력 재시도만 첫 실패에서 남은 out을 이어 사용한다. 고정 문자열 목록 texts를 정수로 바꾸어 기존 내장 리스트 out에 추가하는 이론 설계를 하라. out=[9], texts=["2","bad","4"]에서 즉시 추가 방식의 실패 상태를 구하고, 같은 입력 재시도의 결과도 쓰라. 변환 ValueError에는 out을 보존하는 후보 우선 방식으로 고쳐라. 가상 자원 A가 정상 진입하고 내부 B의 진입이 RuntimeError로 실패한다. A 종료는 False를 반환하고 실패하지 않는다. 종료 사건과 전파를 적어라. 모든 변환이 성공한 texts=["2","4"]에서 최종 out을 쓰라. append/extend/할당 실패는 제외하며 이 설계는 파일·서비스 거래나 강제 종료 복구를 보장하지 않는다. 변환 실패는 새 입력 안내, 진입 실패는 환경/자원 확인으로 분류하고, 같은 입력의 무조건 반복을 피하는 근거를 설명하라.

힌트 1

즉시 추가의 첫 2는 변환 실패 전 완료한 변경이다. 후보 방식은 외부 반영 전 모든 변환을 끝낸다.

힌트 2

B 진입 실패는 B 종료 대상이 아니다. 이미 성공한 A만 오류 정보를 받아 종료하며 False는 전파를 유지한다.

풀이와 답 확인

  1. 즉시 추가는 첫 실패 뒤 out=[9,2], 같은 입력 재시도 뒤 [9,2,2]다. 값 4는 처리되지 않는다.

  2. 후보 방식은 candidate에서 2를 만든 뒤 bad에서 실패한다. 외부 out=[9]는 보존하고 ValueError를 안내 계층에 전달한다.

  3. 정상 입력 ["2","4"]의 후보는 [2,4]이며 마지막 반영 후 out=[9,2,4]다.

  4. A 진입 후 B 진입이 실패한다. B 종료와 본문은 없고 A 종료가 RuntimeError를 받아 False를 반환한 뒤 오류가 전파된다.

  5. 변환 실패는 입력 교정, 진입 실패는 환경/자원 확인으로 분류한다. 예상 변환 실패 보존을 외부 거래·할당 실패·강제 종료 복구로 확대하지 않는다.

부분 반영 [9,2]/재시도 [9,2,2]와 후보 방식 실패 [9]를 구별한다. 성공은 [9,2,4]다. B 진입 실패 때 A만 종료하고 RuntimeError는 남는다. 정리와 성공·복구를 구분한다.
