Subtopic 5.1

list and tuple

Why can we replace an entry in one ordered collection but not in another?

Preparation and learning goals

Preparation

  • Mini-review: name a is a label pointing to an object; a = expression evaluates the right side before connecting that label.
  • For a sequence of length n, valid nonnegative indices run from 0 to n−1. Negative index −1 refers to the last entry only when the sequence is nonempty. An empty sequence has no valid element index.
  • Self-check: the first entry in [3, 1] is 3 and its length is 2. You can begin if you can distinguish these answers.

Learning goals

  • Explain lists and tuples as ordered collections of references.
  • Distinguish the mutation and return value of append from the removal and return value of pop.
  • Distinguish a tuple’s own immutability from mutability of objects inside it.

Two ordered types

A list is a mutable sequence preserving element order. [3, 1] and [1, 3] are unequal because the order differs. a[0] = 9 replaces the reference in the first entry; append adds an entry at the end. A tuple also preserves order, but its entry references and length cannot be directly changed after creation.

An empty tuple is (), and a one-element tuple is (3,). (3) merely puts parentheses around integer 3. tuple(a) creates a tuple containing the element references of a in the same order. Replacing a list entry later does not replace the tuple entry. This conversion does not clone the contained objects.

A method’s effect and returned value

For a built-in list, a.append(x) adds x at the end and returns None. Access the changed list through a, not through the method’s returned value. a.pop() removes the last element and returns it. Popping an empty list raises IndexError, so the removal contract requires a nonempty list.

Append x to sequence contents S, then pop normally without intervening changes: the removed value is x and the contents return to S, because the last entry is the newly appended x. This restores contents and length, not the history of memory allocations or every observed state. Failures or intervening or concurrent changes invalidate the unchanged contract.

Where immutability ends

The tuple ([1],) has one entry pointing to a list. You cannot assign another object to that entry, but you can append through it to the inner list. On paper, t = ([1],) followed by t[0].append(2) makes t appear as ([1, 2],). The identity of the list referenced by the tuple remains the same.

For a record intended never to change, checking only the outer tuple is insufficient. The executed example contains immutable integers, so the old element values can safely be compared. Files, user-defined objects, and nested lists require investigation of their individual mutation contracts.

A worked example, step by step

Using only built-in lists and integers, execute each statement normally in order. Find the final contents of a and t, and last. 

a = [3, 1]
t = tuple(a)
a.append(2)
last = a.pop()
a[0] = 9
print(a, t, last)
  1. a is [3, 1] and t is (3, 1), containing the two integers in the same order. The outer list and tuple are separate objects.
  2. After append(2), a is [3, 1, 2]. The append return value None is unused.
  3. pop() returns the last integer 2 and binds last to it; a returns to [3, 1].
  4. a[0] = 9 changes only the first list entry. Thus a is [9, 1], t is (3, 1), and last is 2.

Changing the list does not change the entries of the tuple already created. Actual stdout (inherited Korean execution): 

[9, 1] (3, 1) 2

Try it with paper and the lesson

On paper, trace a = [4]; t = tuple(a); r = a.append(6); p = a.pop(). Find a, t, r and p, and compare the types of (4) and (4,). Do not execute this activity.

Show hint

Beside each method, write its state change and its returned value separately.

Show solution

After append, a is [4, 6] and r is None. After pop, a is [4] and p is 6. t remains (4,). (4) is an int; (4,) is a one-element tuple.

Misconception and counterexample

Converting to a tuple permanently freezes every contained value.

The inner list of ([1],) can change through append. Tuple immutability prevents replacing its directly contained references; it does not make the entire reference graph immutable.

Check your understanding

What do append and pop return?

Show answer and reasoning

append returns None; a normal pop returns the removed element.

append mutates the list in place, while pop removes and returns a value. Popping an empty list does not return normally.

After a = [2]; t = tuple(a); a[0] = 8, what is t?

Show answer and reasoning

(2,).

Replacing the first entry of a does not replace the entry of t, and integer 2 itself does not change.

Does t[0].append(7) with t = ([0],) violate tuple immutability?

Show answer and reasoning

No. The inner list changes to [0, 7].

The tuple entry still points to the same list. Inner object mutation differs from tuple-entry assignment.

Explore further

Write sequence S as (s₀, …, sₙ₋₁). Compose the contracts of length n+1 after append(x) and length n after pop to prove restoration of contents. The integer-example tuple retains the old references. Include the counterexample that a contained mutable object can still change. This proof establishes neither performance nor memory usage.

Subtopic 5.2

dict and set

Why do occurrence counts and the question of whether a name appeared need different data?

Preparation and learning goals

Preparation

  • Mini-review: for label in a list binds each element to label in turn.
  • Occurrences include repetitions; distinct kinds exclude them. b, a, b has three occurrences and two distinct kinds.
  • A key is a label for finding a value; the value is the data associated with that label.

Learning goals

  • Distinguish dictionary lookup, get and membership from set deduplication.
  • Explain the hashable key contract more precisely than a slogan about immutability.
  • Prove prefix occurrence counts using an inductive invariant.

Dictionary lookup and insertion

A built-in dict associates keys with values. d[key] raises KeyError for an absent key, whereas d.get(key, default) returns default. get itself does not insert that key. key in d and for key in d concern keys, not values. Thus 3 in d is False for {"x": 3}.

In Python 3.12, dict preserves key insertion order. Updating an existing key’s value does not move its position; deleting and reinserting places it at the end. A set has no such insertion-order contract. To display sorted results, apply sorted to mutually comparable values. The lowercase string keys here are comparable.

Hashability and sets

Dictionary keys and set elements must be hashable: their hash is stable throughout their lifetime, they can be compared for equality, and objects comparing equal must have equal hashes. The reverse is invalid: equal hashes do not establish equal values. Hash collisions are possible, so a hash is neither object identity nor a unique identifier.

Built-in list, dict and set are mutable containers and cannot be keys. A tuple is hashable only if every element is hashable, so ([1],) also cannot be a key. User-defined objects have their own contracts; do not generalize that all mutable objects are forbidden. A set does not store equal elements repeatedly, so set(["b", "a", "b"]) retains only two kinds and loses counts 2 and 1. An empty set is set(); {} is an empty dictionary.

The counting invariant

Assume a finite list of strings, no other code changing counts, and each update completing normally. After the first k elements, each value in counts is the number of occurrences of its string in that prefix. For unseen strings, get interprets the count as 0. Initially k=0 and the empty dictionary represents zero counts throughout.

Read the previous count using get(label, 0) and add exactly 1 for the next label. Other keys remain unchanged, preserving the inductive hypothesis for k+1. Each input contributes to exactly one count, so the sum of all stored counts is k. This example uses only string keys. For general keys, equal keys such as 1 and True can refer to the same entry, so the required data distinctions must be specified separately.

A worked example, step by step

Count the input strings b, a, b. Check whether reading z using get inserts it, and display the distinct kinds in sorted order. 

counts = {}
for label in ["b", "a", "b"]:
    counts[label] = counts.get(label, 0) + 1
print(counts["b"], counts.get("z", 0), "z" in counts)
seen = set(counts)
print(sorted(seen))
  1. With an empty dictionary, processing the first b makes get return 0, then assignment inserts b: 1. The count sum is 1.
  2. Processing a adds a: 1. The last b updates only its existing value to 2. The dictionary has b: 2, a: 1, with sum 3.
  3. counts["b"] is 2 and counts.get("z", 0) is 0. Since get does not insert, "z" in counts is False.
  4. set(counts) contains keys b and a. sorted(seen) creates list ["a", "b"]. The original frequencies remain only in counts.

Keep frequencies and distinct kinds separately; merely looking up z does not create a key. Actual stdout (inherited Korean execution): 

2 0 False
['a', 'b']

Try it with paper and the lesson

On paper, record counts and their sum after each prefix of a, b, a, c. After get("z", 0), compare the number of keys with the number of distinct kinds in set(counts). Do not execute.

Show hint

Begin with sum 0 for the empty state; each processed input increases exactly one entry by 1.

Show solution

The dictionaries are successively {a: 1}, {a: 1, b: 1}, {a: 2, b: 1}, {a: 2, b: 1, c: 1}; the sums are 1, 2, 3, 4. get does not insert z, so both key count and set size are 3. The set alone cannot recover a’s frequency of 2.

Misconception and counterexample

Equal hashes mean equal keys, and a set preserves the original frequencies.

A hash collision does not prove equality. Also, ["a", "a"] and ["a"] both become {"a"}, so their frequencies cannot be distinguished using the set alone.

Check your understanding

After d = {"a": 1}; d.get("z", 0), what is "z" in d?

Show answer and reasoning

False.

get returns the default 0 without inserting the key.

For inputs a, a, b, what are the count sum and set size?

Show answer and reasoning

The sum is 3 and the number of distinct kinds is 2.

counts includes repeated occurrences; the set stores a and b once each.

Can immutable tuple ([1],) be a dict key?

Show answer and reasoning

No.

Its list element is unhashable, making the tuple unhashable too. Outer immutability is insufficient.

Explore further

Prove the induction invariant in two parts: the exact count for every key, and the sum of all counts k. A correct sum can coexist with incorrect individual counts. For b, a, b, the result b: 1, a: 2 sums to 3 but violates the specification. Correctness requires the per-key invariant; this proof includes no execution-speed or worst-case time guarantee.

Subtopic 5.3

Nested structures and copying

Why can changing a copied list still change the original?

Preparation and learning goals

Preparation

  • Mini-review: [[1], [2]] contains one outer list and two inner lists.
  • a[0].append(9) mutates the first inner list; a[0] = [9] replaces the reference in the first outer entry.
  • Two arrows pointing to the same box represent aliasing. Identical displayed contents do not establish that the boxes are the same.

Learning goals

  • Compare the reference graphs of assignment, shallow copying and deep copying.
  • Explain the affected scope of inner mutation versus outer-entry replacement.
  • Explain how deepcopy’s memo preserves aliases within the copy, and its conditions and limits.

Assignment and shallow copying

b = a does not copy the outer list; b refers to the same list as a. In contrast, b = a.copy() for a built-in list creates a new outer list containing the existing element references. The outer identities differ, but the inner lists are shared. To describe depth, identify the object layer copied rather than listing element values alone.

b[0].append(9) mutates a shared inner object, so 9 is visible through a[0] too. However, b[1] = [7] connects only b’s second entry to a new list; a’s second entry retains the old [2]. A shallow copy does not mean that no mutation is independent: independence has different outer and inner scopes.

Deep copying and memo

copy.deepcopy recursively copies components of supported compound objects. For the built-in lists and integers here, c’s inner lists are separate from the originals, so c[0].append(5) changes neither a nor b. Objects safe to share, such as immutable integers, do not necessarily receive new identities.

One copying operation records previously processed objects in memo. With row = [0]; a = [row, row], a normal c = deepcopy(a) of built-in lists makes c[0] and c[1] refer to the same cloned row. The original row and cloned row differ. Thus copying separates from the original while preserving sharing within the clone. Treating every encounter with an object as a mandatory fresh, distinct copy is incorrect.

Limits of the copy contract

memo also supports recursively processing self-referential structures. Still, deepcopy is not a universal contract for fully independent cloning of every object. User-defined classes can change behavior through __deepcopy__; functions and classes are returned as their original objects, and external resources such as files and sockets are not ordinary value-copy targets.

The reasoning here concerns normally processed graphs of built-in lists and integers. Before adding copying to application data, decide which resources must remain shared and which mutable state must be separated. Copying does not duplicate external files, freeze remote state, or make concurrent access atomic.

A worked example, step by step

Create shallow copy b and deep copy c of a containing only built-in lists and integers, then trace different mutations in order. 

from copy import deepcopy
a = [[1], [2]]
b = a.copy()
c = deepcopy(a)
b[0].append(9)
b[1] = [7]
c[0].append(5)
print(a, b, c)
  1. a has outer A with inner [1] and [2]. New outer B of b shares those two inner lists. New outer C of c has separate inner [1] and [2].
  2. b[0].append(9) makes the shared first inner list [1, 9], visible through both a and b. The first inner list of c remains [1].
  3. b[1] = [7] changes only B’s second arrow. The second entries of a and c each retain [2].
  4. c[0].append(5) changes only its cloned first inner list to [1, 5]. a is [[1, 9], [2]], b is [[1, 9], [7]], and c is [[1, 5], [2]].

Mutating a shared inner object and replacing one outer entry propagate along different paths. Actual stdout (inherited Korean execution): 

[[1, 9], [2]] [[1, 9], [7]] [[1, 5], [2]]

Try it with paper and the lesson

On paper, draw row = [0]; a = [row, row]; b = a.copy(); c = deepcopy(a), then trace b[0].append(4) and c[1].append(6). Find a, b, c and c[0] is c[1]. Do not execute this variant.

Show hint

Draw one original row R and one cloned row R′. Use memo to avoid mistakenly splitting c’s entries into separate rows.

Show solution

Both a and b show [[0, 4], [0, 4]] through shared R. c points twice to R′ and shows [[0, 6], [0, 6]]. The expression `c[0] is c[1]` evaluates to True, while `c[0] is row` evaluates to False. Aliasing within the clone and separation from the original coexist.

Misconception and counterexample

deepcopy makes every reference point to a different object and duplicates every resource.

A repeated row remains shared within the clone. Original returns for functions and classes and user-defined copy rules also limit fresh-object guarantees. Objects with external resources need explicit, separate resource contracts.

Check your understanding

Does b = a.copy() make the inner lists of a nested list independent too?

Show answer and reasoning

No. It creates a new outer list but shares inner references.

The shallow-copy contract distinguishes the outer compound object from existing contained-object references.

After a = [[1]]; b = a.copy(); b[0] = [8], what is a?

Show answer and reasoning

[[1]].

Only b’s first outer entry is replaced; neither the previously shared inner object nor a’s entry changes.

After deepcopy of row = [0]; a = [row, row], must the two copied rows differ?

Show answer and reasoning

No. A normal deepcopy of these built-in lists shares the same cloned row.

memo reuses the copy corresponding to one original object, preserving aliases within the clone.

Explore further

In a finite built-in list graph, imagine memo assigning one clone R′ to each original object R. If two original arrows converge on R, their corresponding cloned arrows converge on R′. This explains preservation of sharing. For cycles, reuse a reference to a clone already created to avoid endlessly cloning it again. This is not a universal theorem about custom copy hooks or external resources, and the extension code was not executed.

Subtopic 5.4

Mutability, aliases and errors

Why do a name assignment and an inner mutation affect other names differently?

Preparation and learning goals

Preparation

  • Mini-review: separate name labels from boxes representing lists. Assignment can change a label’s arrow.
  • == compares equality of values; is compares object identity. Separate lists can have the same contents.
  • [row] * 3 repeats a one-element sequence. Do not initially assume it creates the inner row three times.

Learning goals

  • Trace the difference between repeated references and creation of fresh rows.
  • Distinguish object mutation, name rebinding and container-entry replacement.
  • Explain the error of assigning a method’s None return back to a name.

Object nodes and reference arrows

Draw objects as nodes, and names and container entries as arrows. view = grid adds another arrow to the same outer node. grid = a new list moves only the grid name’s arrow to a new outer node; the arrow from view to the old node does not move automatically.

view[1].append(8) mutates the inner node reached through view’s second entry. Every path reaching that node can observe the mutation. In contrast, view[1] = [8] replaces one outer-entry arrow rather than mutating the old inner node. Distinguish a changed node from a changed arrow when resolving sharing problems.

Repetition and fresh objects

[row] * 3 creates a new outer list containing three references to row. What matters is not just that three entries appear equal, but that all three are the same row. Mutating the row through one path is visible through the other two. Sequence repetition does not clone the elements themselves.

In [[0] for _ in range(3)], the expression [0] creates a fresh built-in list each iteration. The three rows therefore have equal contents but distinct identities. In contrast, [row for _ in range(3)] stores the same row reference three times and does not remove sharing. The syntax name comprehension alone cannot guarantee independent rows; inspect the repeated expression.

Identity checks and return-value errors

For built-in lists x = [1]; y = [1], x == y is True but x is y is False. is is not for comparing contents. Implementations can reuse immutable integers or strings, so do not use is to test equal values. The example checks only explicitly shared built-in lists.

a = a.append(2) first adds 2 to the old list, then rebinds a to the returned None. Another name pointing to that old list can still see the mutation. A later a.append call fails because None has no list append method. Use a.append(2) as a standalone call for the intended mutation. This is a paper error trace; the erroneous variant was not actually executed.

A worked example, step by step

Share one row through three entries, then bind only grid to a new structure. Compare mutation through view of the old structure with the new grid. 

row = [0]
grid = [row] * 3
grid[0][0] = 7
view = grid
grid = [[1], [2], [3]]
view[1].append(8)
print(view)
print(grid)
print(view[0] is view[2])
  1. row is inner R containing [0]. All three grid entries point to R. grid[0][0] = 7 changes R to [7], visible in all three entries.
  2. view = grid shares old outer G. grid = [[1], [2], [3]] connects only grid to new outer H and three fresh inner rows.
  3. view[1].append(8) still reaches R, making it [7, 8]. All G entries share R, so view is [[7, 8], [7, 8], [7, 8]].
  4. H does not share R, so grid is [[1], [2], [3]]. view[0] and view[2] are the same R, making the is check True.

Rebinding a name does not move existing aliases; a shared-row mutation is visible along every shared path. Actual stdout (inherited Korean execution): 

[[7, 8], [7, 8], [7, 8]]
[[1], [2], [3]]
True

Try it with paper and the lesson

Without executing, trace row = [0]; a = [row] * 2; b = a; a[0] = [5]; b[1].append(6); a = []. Find final a, b, row and b[0] is b[1].

Show hint

Initially both entries in outer G share R. Replacing the first entry separates their arrows. The last line moves only name a.

Show solution

The first entry refers to fresh [5], and the second to R. After append, R is [0, 6]. Finally a is [], b is [[5], [0, 6]], and row is [0, 6]. The expression `b[0] is b[1]` evaluates to False. b still points to G and is unaffected by the last rebinding of a.

Misconception and counterexample

Reassigning a name also changes every alias, and using a comprehension removes all inner sharing.

After view = grid, rebinding grid does not move view. Also, [row for _ in range(3)] repeatedly references row. Examine name assignment and the inner creation expression separately.

Check your understanding

For x = [1]; y = [1], what are x == y and x is y?

Show answer and reasoning

True and False, respectively.

The contents match, but the two list expressions create distinct built-in list objects.

Does row = [0]; a = [row for _ in range(2)] create two independent rows?

Show answer and reasoning

No. It references the same row twice.

The repeated expression row does not create a fresh list. Independent rows require an expression such as [0] that creates a new object each iteration.

After a = [1]; b = a; a = a.append(2), what are a and b?

Show answer and reasoning

a is None and b is [1, 2].

The right-side append first mutates the existing list and returns None; only then a is bound to None while b still references the changed list.

Explore further

List the shared paths first to predict the scope of a mutation. When three entries share row R, appending to R changes the observed values of all three paths. Connecting one entry to fresh R′ separates only that path. Specify separately whether a contract permits input-list mutation, returns a fresh list, or shares inner objects. This reference model establishes neither numerical memory addresses, deallocation timing nor thread safety.
