소단원 3.1

Unicode와 인코딩

화면에는 두 글자인 A가가 왜 UTF-8에서는 네 바이트일까?

준비 개념과 학습 목표

준비 개념

  • 값과 자료형: str은 텍스트 값, bytes는 바이트 값의 순서열이다. 같은 모양의 출력이어도 자료형과 해석 계약이 다를 수 있다.
  • 코드 포인트는 Unicode에서 쓰는 정수 번호다. U+AC00처럼 U+ 뒤의 숫자는 16진 표기이며 한글 가의 번호다. 바이트는 여기서 8비트로 0~255의 값을 갖는다.
  • 함수의 복원: 인코더 E가 텍스트를 바이트로 만들고 디코더 D가 되돌린다. D(E(x))=x는 두 규칙과 허용 입력이 맞아야 성립한다.

학습 목표

  • str 길이·코드 포인트·사용자가 보는 문자·UTF-8 바이트 길이를 구별한다.
  • 명시한 인코딩과 strict 오류 정책으로 encode/decode를 추적한다.
  • 정규화가 텍스트 비교의 정책이며 모든 시각적 유사성을 같게 만들지는 않음을 설명한다.

텍스트와 저장 표현은 다른 값이다

Python 3.12의 str은 Unicode 코드 포인트의 불변 순서열이다. len(s)는 코드 포인트 개수를 세며 파일 바이트 수나 화면 글자 폭을 세지 않는다. 코드 포인트 하나가 곧 사용자 인식 문자 하나라는 보장도 없다. 예를 들어 é를 U+00E9 한 개로 쓰거나 e와 결합 악센트 U+0301 두 개로 쓸 수 있다. 표시가 비슷해도 내부 순서열은 다르다.

bytes는 0~255 정수의 불변 순서열이다. s.encode("utf-8")는 텍스트에서 바이트로, b.decode("utf-8")는 바이트에서 텍스트로 간다. A가에는 A와 가 두 코드 포인트가 있고 UTF-8에서는 41 EA B0 80 네 바이트다. 바이트 하나를 조회한 b[0]은 정수이고 str의 s[0]은 길이 1인 str이다.

인코딩과 오류 정책을 함께 명시한다

정상적인 Unicode scalar value로 구성된 str을 UTF-8 strict로 인코딩하고 같은 인코딩 strict로 디코딩하면 원래 코드 포인트 순서를 복원한다. Python str에 넣을 수 있는 모든 값이 이 조건을 자동 만족하는 것은 아니다. 특히 단독 surrogate 코드 포인트는 표준 UTF-8 strict 인코딩에서 오류가 난다. 다른 인코딩은 표현 가능한 문자 집합도 다르므로 ASCII에는 가를 그대로 담을 수 없다.

잘못된 UTF-8은 strict에서 UnicodeDecodeError를 낸다. replace는 복원 불가 부분을 대체 문자로, ignore는 삭제로 처리해 원자료 정보가 사라질 수 있다. 따라서 오류를 조용히 지웠다는 사실이 올바른 입력 검증은 아니다. 네 바이트 A가의 앞 두 바이트 41 EA만 자르면 가의 다중 바이트 표현이 끊겨 decode가 실패한다. 임의의 바이트 slice는 텍스트 경계를 보존하지 않는다.

비교 전에 무엇을 같다고 볼지 정한다

str의 ==는 코드 포인트 순서의 같음을 비교한다. "\u00e9"와 "e\u0301"는 길이 1과 2여서 그대로는 같지 않다. unicodedata.normalize("NFC", s)는 canonical 분해와 가능한 재합성의 규칙으로 이 두 표현을 같은 NFC 형태로 바꾼다. NFC가 길이나 철자를 언제나 그대로 보존한다고 가정하지 않는다.

NFKC는 compatibility 차이까지 합칠 수 있어 원자료 보존 정책과 별도로 선택한다. 정규화해도 모든 닮은 글자·폰트·언어 의미가 같아지지는 않으며 암호나 식별자를 임의로 바꾸면 요구를 깨뜨릴 수 있다. Python02의 원문 보존·형식 검증 흐름처럼 raw를 보관하고 필요할 때 명시한 비교용 형태를 별도로 만든다. 실제 사람의 이름·허용 문자 정책은 이 예제가 정해 주지 않는다.

중간 과정을 따라가는 예제

고정 str A가를 UTF-8로 변환하고 é의 두 표현을 NFC 비교한다. 아래 코드는 외부 파일과 사용자 입력을 사용하지 않는다.

  1. s의 len은 2, encode 결과의 len은 4다. hex는 41 ea b0 80이며 같은 UTF-8 decode 뒤 s와 == 비교는 True다.
  2. one은 U+00E9 한 개, two는 U+0065/U+0301 두 개다. len 1/2, 원래 ==는 False다.
  3. NFC를 양쪽에 적용하면 두 코드 포인트 표현을 동일한 é로 맞춰 비교가 True다. 이는 명시한 canonical 비교 정책이다.
  4. b[:2]는 41 EA다. EA 뒤 필요한 바이트가 없어 strict decode가 UnicodeDecodeError를 내고 except가 그 이름만 출력한다.

실제 stdout은 2 4 41 ea b0 80 / True / 1 2 False / True / UnicodeDecodeError의 다섯 줄이다. 표시 글자 수·코드 포인트 수·바이트 수의 차이를 관찰했으며 일반 사용자 문자의 경계를 측정한 것은 아니다.

오해와 반례

len(s)가 보이는 글자 수이며 bytes에 str()을 쓰면 원하는 원문이 자동 복원된다.

é의 한 코드 포인트와 e+악센트 두 코드 포인트가 비슷하게 보여도 len은 1/2다. str(b"A")는 bytes의 표시 문자열 "b'A'"이고 b"A".decode("utf-8")처럼 인코딩을 지정한 복원과 다르다. bytes는 이미지 등 텍스트 아닌 값일 수도 있다.

아니다.

서로 다른 canonical 표현을 NFC가 합칠 수 있으며 원래 인코딩 길이·바이트 배열은 다를 수 있다.

한 단계 더

심화: 허용 입력 집합 X에 대해 D(E(x))=x가 모두 성립하면 E는 일대일이다. E(x)=E(y)에 D를 적용하면 x=y이기 때문이다. 그러나 비교용 N을 NFC나 casefold로 정하면 N(x)=N(y)인데 x≠y인 경우가 있으므로 N을 원문 복원 인코더로 쓸 수 없다. 유효 UTF-8 byte sequence에 대한 복원과 text normalization의 동등성 정책을 따로 명세하라.

소단원 3.2

index·slice

문자열의 99번째 원소는 오류인데 99부터 자른 문자열은 왜 빈 문자열일까?

준비 개념과 학습 목표

준비 개념

  • 순서열은 원소에 순서가 있는 값이다. len(s)=L이면 str의 코드 포인트 위치는 0부터 L−1까지다. 빈 문자열은 L=0이다.
  • 음수 index −1은 끝에서 첫째다. 유효 음수 index i는 L+i라는 0 이상 위치로 바꿔 생각한다. −0은 0이다.
  • 끝을 제외하는 구간 [start, stop)은 start부터 stop 바로 전까지다. 정수 step은 다음 위치로 얼마나 이동할지 정한다.

학습 목표

  • 양수·음수 index와 IndexError를 구별해 추적한다.
  • 양수·음수 step slice의 포함 위치와 끝 제외를 계산한다.
  • 코드 포인트 slice와 사용자 인식 문자/바이트 경계의 차이를 설명한다.

한 원소 조회는 유효 위치가 필요하다

s[i]는 한 코드 포인트를 담은 길이 1의 str을 준다. 정수 i가 −L≤i<L 범위에 있어야 하고 음수이면 L+i로 환산한다. L=4인 A가BC에서 s[0]은 A, s[1]은 가, s[−1]은 C다. s[4]나 s[−5]는 IndexError다. 빈 str에는 유효 index가 없다.

길이와 index는 저장 바이트 기준이 아니다. s="e\u0301"에서 s[0]은 e이고 s[1]은 결합 악센트라 사용자에게 보이는 한 문자를 나눌 수 있다. str에는 별도의 char 자료형이 없고, 한 원소도 str이다. s[i]가 글리프나 사용자 인식 문자 전체라는 가정은 하지 않는다.

slice는 끝을 제외하고 경계를 조정한다

s[start:stop:step]은 정한 시작에서 step씩 진행해 stop을 포함하지 않는 위치들을 모은 str이다. step 생략은 1이다. 양수 step일 때 생략한 시작/끝은 0/L이고, 길이 밖의 경계는 잘린다. A가BC의 [1:3]은 위치 1,2의 가B이며 [99:]는 선택 위치가 없어 빈 str이다. 이런 조정은 단일 index 오류와 다른 계약이다.

양수 step에서 [i:j]를 0≤i≤j≤L로 이미 조정했다면 길이는 j−i다. i≥j이면 빈 str이고 임의의 원래 음수/초과값에 이 빼기만 바로 적용하지 않는다. step=0은 진행 규칙이 없어 ValueError다. slice로 얻는 순서와 경계를 종이에 먼저 표시하면 off-by-one 오류를 줄일 수 있다.

뒤로 읽기에는 다른 생략 경계가 있다

음수 step은 큰 위치에서 작은 위치로 이동한다. s[::-1]은 끝 원소부터 시작 원소까지 뒤집는다. 생략한 stop은 처음 원소 앞의 경계여서 위치 0도 포함한다. 그러나 명시한 stop=−1은 실제 마지막 위치로 환산된다. 따라서 s[:-1:-1]은 끝에서 시작해 끝 위치 바로 전에 멈추라는 요청이 되어 이 예제에서는 빈 str이다. 생략과 −1은 다르다.

끝 위치를 포함시키려고 무조건 1을 더하거나 빼기보다 진행 방향과 stop 제외를 함께 살핀다. "012345"의 [4:0:−2]는 4,2를 골라 "42"이고 0은 제외한다. str을 역순으로 만드는 [::-1]도 code point 순서를 뒤집을 뿐 결합문자나 복잡한 emoji 단위를 보존하는 전용 텍스트 연산은 아니다.

중간 과정을 따라가는 예제

s="A가BC"에서 한 원소, 앞/뒤 slice, 초과 경계와 0 step을 비교한다. 예외는 코드에서 종류를 구분해 처리한다.

  1. L=4이고 위치표는 0:A/1:가/2:B/3:C다. len(s), s[0], s[−1]의 첫 출력은 4 A C다.
  2. [1:3]은 가B, [::-1]은 CB가A, [99:]는 빈 문자열이다. repr가 빈 값을 작은따옴표 두 개로 보이게 한다.
  3. [:-1:-1]의 명시한 끝 −1은 마지막 위치라 선택된 원소가 없어 빈 문자열을 출력한다.
  4. s[99]는 IndexError, s[::0]은 ValueError다. 각각 except에서 종류 이름을 출력해 정상 빈 slice와 구별한다.

실제 출력은 4 A C / '가B' 'CB가A' '' / '' / IndexError / ValueError의 다섯 줄이다. 인덱스와 슬라이스의 경계 계약 차이를 확인했다.

종이와 본문으로 직접 해보기

s="012345"의 [−5:−1:2], [4:0:−2], [:0], 빈 문자열의 [−1] 결과를 종이에 예측하라.

힌트 보기

L=6이므로 −5는 1, −1은 5로 환산한다. slice의 끝은 제외하고 빈 값의 단일 index는 존재하지 않는다.

풀이 보기

첫 slice의 위치 1,3으로 "13", 둘째 4,2로 "42", [:0]은 빈 str이다. 빈 문자열 [−1]은 IndexError다. 이 답은 종이 추적이며 아래 네 풀이 예제 실행과 구별한다.

오해와 반례

slice는 한 원소 index와 같은 오류 규칙이고 s[0:L−1]은 전체를 준다.

s[99:]는 빈 값이어도 s[99]는 오류다. 끝 제외 때문에 A가BC의 [0:3]은 A가B여서 마지막 C를 누락한다. 전체는 s[:] 또는 [0:L]로 표현할 수 있다.

자기점검

s="abc"에서 s[−2]는?

답과 이유 보기

"b".

L=3이므로 3−2=1 위치다.

"abc"[1:99]는 오류인가?

답과 이유 보기

아니며 "bc"다.

slice 끝이 길이로 조정되고 위치 1,2를 고른다.

"abc"[::-1]과 "abc"[:-1:-1]은 같은가?

답과 이유 보기

아니다. 각각 "cba"와 빈 str이다.

음수 step의 생략 stop과 마지막 위치로 환산되는 명시 −1은 다른 경계다.

한 단계 더

심화: 이미 정규화된 양수 step k>0과 0≤i≤j≤L에 대해 slice 원소 수는 max(0, ceil((j−i)/k))다. j−i=0이면 0, 양수이면 (j−i+k−1)//k로 계산한다. 예를 들어 i=1,j=5,k=2면 위치 1,3의 두 개다. 이 식을 조정 전 음수/초과 index나 음수 step에 그대로 적용하지 않는다. Python의 slice(i,j,k).indices(L)가 정규화된 경계를 주는 선택 도구이며 필수 설치 활동은 아니다.

소단원 3.3

문자열 메서드와 formatting

공백을 정리한 이름과 보기 좋게 출력한 수가 원자료와 같은 정보일까?

준비 개념과 학습 목표

준비 개념

  • 메서드는 value.method(...)처럼 특정 값에서 호출하는 함수다. 반환값을 받는 것과 원래 값을 바꾸는 것은 별개다.
  • list는 여러 값을 순서대로 담는 묶음이다. split의 반환은 문자열 목록이고 join은 문자열 목록의 사이에 구분자를 넣어 하나로 합친다.
  • 표시 형식은 사람에게 보여 줄 문자열을 만드는 규칙이다. Python02처럼 숫자의 값·자료형·허용 범위와 표시를 구별한다.

학습 목표

  • strip·split·join·replace와 prefix 제거의 입력/출력을 설명한다.
  • f-string의 폭·정밀도·문자열 변환과 입력 검증을 구별한다.
  • 원문과 처리용 문자열을 분리해 정보 손실 여부를 판단한다.

메서드마다 제거하는 대상이 다르다

raw.strip()은 양끝 공백을 제거한 str을 반환하며 내부 공백은 남긴다. strip(chars)는 chars 문자열 전체를 prefix/suffix로 지우는 것이 아니라 그 안의 문자 집합에 속한 양끝 문자를 반복 제거한다. "abba".strip("ab")는 모두 제거해 빈 값이고 removeprefix("ab")는 앞의 한 "ab"만 제거해 "ba"다. 파일 확장자나 이름을 잘못 자르지 않도록 제거 대상을 명시한다.

replace(old,new)는 기본적으로 모든 해당 부분 문자열을 바꾼 결과를 반환한다. lower는 소문자 형태, casefold는 Unicode의 대소문자 무시 비교용 형태를 만든다. "ß".casefold()는 "ss"여서 길이까지 바뀔 수 있다. 사용자의 이름을 title-case하거나 비교용 변환으로 원문을 덮는 것은 자동 정답이 아니다. raw를 유지하고 clean 또는 비교 key를 별도로 만든다.

나누고 합치는 규칙을 계약으로 둔다

split(",")는 쉼표로 나누며 연속 쉼표의 빈 필드도 유지한다. "Kim,7,,"은 ["Kim","7","",""]다. 반면 split()은 공백의 연속을 한 구분으로 보고 양끝 빈 필드를 만들지 않는다. 빈 문자열도 split(",")에서는 [""]이고 split()에서는 []다. 누락된 필드와 없는 레코드는 같은 상황이 아니므로 형식별로 판단한다.

",".join(parts)는 모든 원소가 str인 묶음 사이에 쉼표를 넣는다. 숫자 원소는 자동 변환하지 않고 TypeError를 낸다. 단순 쉼표 split은 인용부호·필드 안 쉼표·개행을 처리하는 CSV 파서가 아니다. 이 단원의 고정 입력에는 인용/이스케이프 규칙이 없다고 정하며 실제 CSV는 후속 파일 단원의 csv 도구와 명세를 사용한다.

formatting은 출력 표현을 만든다

f"{count:03d}"는 정수 값을 최소 폭 3의 십진 표현으로 만들며 부족한 앞자리를 0으로 채운다. count=7이면 "007"이다. 최소 폭이므로 1234를 잘라 "234"로 만들지 않는다. f"{price:.2f}"는 소수점 뒤 두 자리의 표시이며 price=2.5는 "2.50"이 된다. 반환은 str이고 원래 count/price 값은 그대로다.

float의 표시 반올림이 원래 수를 정확한 십진 값으로 바꾸거나 허용 범위를 검증하지는 않는다. 외부 입력은 먼저 형식·자료형·범위를 확인하고 그 다음 표시한다. f-string의 표현식은 실제 Python 계산으로 실행되므로 부작용 있는 함수를 무심코 넣지 않는다. 사용자가 준 문자열을 f-string 템플릿이나 코드로 평가하는 흐름은 이 예제에 없다. 고정 템플릿의 필드 값으로만 넣는다.

중간 과정을 따라가는 예제

가상 인용 없는 텍스트 " Kim,7,, "를 처리해 빈 필드를 보존하고 수를 표시한다. 고정 입력의 둘째 필드는 유효 정수 7이라고 정하며 일반 파서의 입력 검증은 별도다.

  1. raw를 남기고 clean=raw.strip()으로 "Kim,7,,"를 얻는다. 내부 쉼표는 그대로다.
  2. split(",")의 네 필드는 Kim/7/빈/빈이다. name은 첫 값, int 변환한 count는 7이다.
  3. 고정 f-string에 name/count/price를 넣어 "Kim: 007 / 2.50"를 만든다. 2.5의 표시는 두 소수자리지만 원래 float를 변경하지 않는다.
  4. strip("ab")와 removeprefix("ab")는 빈 값/ba로 다르고, casefold한 ß는 ss 길이 2다. 메서드 이름보다 실제 계약으로 결과를 확인한다.

실제 stdout은 raw/clean repr, 네 필드 목록, Kim: 007 / 2.50, 빈 str과 ba의 repr, ss 2를 각각 출력한다. raw는 양끝 공백을 계속 보유한다.

종이와 본문으로 직접 해보기

종이에서 " A B ".split()과 "a,,b,".split(",")를 쓰고 둘째 결과를 "|"로 join하라. f"{1234:03d}"가 무엇인지 예측하라.

힌트 보기

공백 기본 split과 명시 쉼표 split은 빈 필드 규칙이 다르다. 폭 3은 최대가 아니라 최소다.

풀이 보기

첫 결과 ["A","B"], 둘째 ["a","","b",""]다. join은 "a||b|"다. 정수 1234 표시는 "1234"로 네 자리 모두 남는다. 종이 활동이며 이 입력들을 추가 실행했다고 기록하지 않는다.

오해와 반례

strip(".txt")는 확장자 하나를 정확히 제거하며 formatting은 숫자값을 검증한다.

strip은 문자 집합 {.,t,x}를 양끝에서 제거하므로 원하는 이름까지 자를 수 있다. "text.txt".strip(".txt")는 "e"지만 removesuffix(".txt")는 "text"다. "999"를 표시해도 상한 100 요구는 검사되지 않으며 숫자 검증은 별도 조건이다.

자기점검

"a,,b".split(",")의 중간 빈 필드는 사라지는가?

답과 이유 보기

아니며 ["a","","b"]다.

명시 구분자의 연속은 빈 필드를 생성한다.

"-".join(["A",7])은 자동으로 "A-7"이 되는가?

답과 이유 보기

아니며 TypeError다.

join의 원소는 str이어야 하며 자동 숫자 변환은 없다.

price=2.5를 .2f로 표시하면 원래 price는 문자열로 바뀌는가?

답과 이유 보기

아니다.

표시 결과는 "2.50"인 str이고 price에 재대입하지 않아 원래 float값은 유지된다.

한 단계 더

심화: sep가 길이 1인 str이고 parts가 비어 있지 않은 str 목록이며 어느 필드에도 sep가 없다면 sep.join(parts).split(sep)==parts다. 각 구분자는 join이 삽입한 경계에만 나타나고, 명시 split이 빈 필드도 보존하므로 복원된다. parts=[]이면 join은 빈 str이고 명시 split은 [""]여서 실패한다. 다문자 sep에서는 필드에 sep가 없다는 조건만으로 부족하다. sep="aa", parts=["a",""]이면 join은 "aaa"이고 split은 왼쪽의 "aa"를 먼저 찾아 ["","a"]가 된다. 구분자가 삽입 경계를 가로질러 겹칠 수 있기 때문이다. 다문자 구분자의 사용에는 이런 추가 매칭을 배제하는 조건이나 quoting/escaping 명세가 필요하다. 길이 1 sep=","와 parts=["a",""]는 "a,"로 정상 복원된다. 임의 CSV 파서를 증명한 것은 아니다.

소단원 3.4

문자열 불변성

두 이름이 같은 문자열을 가리키는데 한 이름을 고치면 다른 이름도 바뀔까?

준비 개념과 학습 목표

준비 개념

  • 바인딩은 이름이 값을 가리키는 관계다. s=t는 이름 s를 오른쪽 값에 묶으며 등식의 선언이 아니다.
  • 불변 객체는 생성 후 그 객체의 원소를 바꿀 수 없다. 이름이 다른 객체를 가리키게 하는 재바인딩은 가능하다.
  • 별칭은 여러 이름이 같은 객체를 가리키는 관계다. 문자열 값 비교 ==와 객체 동일성 is는 서로 다른 질문이다.

학습 목표

  • 메서드 반환값·재바인딩·원소 대입을 단계별로 구별한다.
  • 여러 이름과 문자열의 불변성을 그림으로 추적한다.
  • 불변 문자열과 가변 목록을 합쳐도 입력 목록의 변경이 결과 문자열을 바꾸지 않음을 설명한다.

바뀌는 이름과 바뀌지 않는 객체

s="cat"; t=s는 두 이름이 같은 str을 가리키게 한다. s.replace("c","b")는 내용 bat인 결과를 계산해 반환하지만 기존 cat의 첫 코드 포인트를 고치지 않는다. 반환을 저장하지 않으면 두 이름은 계속 cat을 읽는다. s=s.replace(...)라면 오른쪽 결과를 평가한 뒤 s의 바인딩만 바꾸므로 t는 cat에 남는다.

str 원소 s[0]="r" 대입은 허용되지 않아 TypeError다. s+=suffix도 str에서 내용을 제자리 변경하는 허가가 아니다. 덧붙인 결과에 이름을 다시 묶는 의미로 추적한다. 결과가 같을 때 구현이 기존 str 객체를 재사용하는지는 프로그램의 값 계약과 다르므로 "메서드를 호출하면 언제나 다른 id"라는 규칙을 만들지 않는다.

문자열과 가변 컨테이너의 경계

parts=["a","가"]라는 목록은 원소 슬롯을 바꿀 수 있다. merged="".join(parts)는 그 시점의 문자열 값들을 합친 a가라는 str이다. 나중에 parts[0]="b"를 실행하면 목록의 첫 슬롯이 달라질 뿐 이미 만든 merged의 코드 포인트는 바뀌지 않는다. 다시 join한 결과는 b가다.

불변 str을 담았다고 목록 전체가 불변인 것은 아니다. 반대로 문자열을 "리스트로 바꿔 수정하고 다시 join"하는 선택 구현은 새로운 값을 만드는 것이지 원래 str을 고치는 것이 아니다. 이 흐름의 인덱스는 여전히 코드 포인트 기준이므로 결합문자 경계 보존이나 사용자 인식 글자 편집을 자동 해결하지 않는다.

값 의미와 비용을 따로 판단한다

문자열의 같음은 ==로 비교한다. is는 동일 객체인지 묻고 일부 문자열 재사용·interning은 구현에 의존하므로 같음 검사의 대신이 아니다. 불변성 때문에 alias가 기존 값의 내용을 뒤에서 바꾸지 못한다는 성질은 유용하지만 실행 중 변수 이름이 계속 같은 문자열을 가리킨다는 뜻은 아니다.

많은 조각을 반복 +로 누적하면 매 단계 새 결과를 만드는 일반 모형에서 복사량이 커질 수 있다. 길이 1 조각 n개를 매번 처음부터 복사하면 1+2+…+n=n(n+1)/2 코드 포인트 규모다. 목록에 모아 한 번 join하는 방식이 일반적인 대안이다. CPython의 특수 최적화·문자 내부 표현·실제 메모리 크기는 별도이며 이 식을 모든 Python 실행의 측정 시간으로 주장하지 않는다.

중간 과정을 따라가는 예제

cat 문자열의 두 별칭과 replace의 저장 여부를 추적하고, join 뒤 입력 목록 변경을 비교한다. 모든 값은 고정 예제다.

  1. s="cat",t=s 뒤 반환을 버리는 replace 호출은 s/t를 바꾸지 않아 cat cat이 출력된다.
  2. 반환을 s에 대입하면 s는 bat, t는 cat이어서 bat cat이다. 기존 cat 객체를 수정한 것이 아니다.
  3. s[0]="r"는 TypeError이며 except가 종류 이름을 출력한다. 이 오류 뒤 문자열의 코드 포인트를 수정하지 않았다.
  4. merged는 a가다. 목록의 첫 슬롯을 b로 바꾼 뒤에도 merged는 a가이며 새 join만 b가여서 a가 b가가 출력된다.

실제 stdout 네 줄은 cat cat / bat cat / TypeError / a가 b가다. 문자열 불변성과 이름·목록 슬롯의 변경을 구별했다.

오해와 반례

str이 불변이면 s=s+"!"도 불가능하고 문자열 메서드는 원래 내용을 고친다.

한 단계 더

심화: 길이 1 조각 n개를 접합하며 매번 전체 결과를 복사한다는 모형에서 n(n+1)/2를 양끝 항 묶기로 증명하라. n=4이면 1+2+3+4=10이고 최종 길이는 4다. 중간 복사 총량과 마지막 문자열 길이는 다른 지표다. 실제 Python 시간은 최적화/할당/내부표현의 영향을 받으며 이 단원에서 성능 벤치마크를 하지 않았다. 후속 컬렉션과 함수 단원에서는 결과를 반환하는 함수와 원본을 제자리 변경하는 메서드의 계약을 계속 구별한다.
