소단원 11.1

traceback·breakpoint

오류 메시지의 마지막 줄과 그 위의 호출 목록은 각각 무엇을 알려 줄까?

준비 개념과 학습 목표

준비 개념

  • 함수 호출

  • 리스트 인덱스

학습 목표

  • 예외 종류와 호출 위치를 구별한다

  • 최소 재현 입력을 기록한다

  • 중단점에서 상태를 확인하는 절차를 설명한다

관찰 명령이 실패 입력을 고쳐 버리면 무엇을 조사한 걸까?

검사 전에 상태를 적으면 예외가 생긴 줄과 그 상태를 만든 줄을 구별할 수 있다. def take(items): return items.pop(0)에서 빈 목록은 실패한다. 하지만 멈춘 디버거에서 p items.append(7)을 평가하면 입력이 바뀐다. 이후 성공은 원래 실패가 해결됐다는 증거가 아니다.

p는 현재 문맥에서 표현식을 평가한다. 읽기처럼 보이는 함수도 변경을 할 수 있다. 관찰용으로 len(items), items[:] 같은 제한된 내장 목록 표현을 선택하고 원래 입력을 별도 기록한다. 사용자 정의 객체의 속성/복사까지 부작용 없다고 확대하지 않는다.

아래는 실행한 디버거 기록이 아닌 순차 손추적이다. traceback의 실제 파일/줄과 hook 설정은 실제 실행 때 확인해야 한다. next도 호출된 함수의 변경을 수행할 수 있으며 step과의 차이는 변경 여부가 아니라 다음 멈춤 문맥이다.

먼저 확인할 개념
  • 목록의 변경

    pop과 append가 같은 목록 객체를 바꾸는지 따라간다.

  • 예외 이전 효과

    예외 관찰 전에 완료한 변경을 별도로 적는다.

마지막 줄에서 현상을 읽는다

traceback의 마지막 줄은 예외 종류와 메시지를 보여 주고 그 위는 호출 맥락을 보여 준다. 오류가 표시된 줄이 원인 전체를 뜻하지는 않는다. 잘못된 입력을 만든 위치나 먼저 바뀐 상태를 따라가야 할 수 있다.

SyntaxError는 파싱 중 문제이고 IndexError·ValueError 등의 예외는 실행 중 나타날 수 있다. 파싱 자체가 실패하면 원하는 중단점까지 실행이 진행되지 않는다. 버전·파일·입력·오류 종류를 기록하고 민감한 값은 공개하지 않는다.

작은 입력으로 재현한다

실패하는 최소 사례를 만든 뒤 예상 행동과 실제 관찰을 나누어 적는다. 이 자료에서는 실제 실행을 하지 않았으므로 아래는 코드 의미로 예측하는 과정이다. 실습한다면 파일을 저장하고 같은 입력으로 다시 실행해 결과를 확인한다.

빈 리스트에서 첫 원소를 찾는 코드라면 리스트가 비었다는 조건이 핵심이다. 예외를 무조건 숨기거나 임의 기본값으로 바꾸면 잘못된 상태가 뒤로 전달될 수 있다. 빈 입력에 대한 정책을 먼저 정한다.

멈춘 문맥에서 확인한다

기본 hook의 Python3.7 이상에서 breakpoint()를 호출하면 디버거로 들어갈 수 있다. 다른 hook이나 환경 설정에 따라 동작이 달라질 수 있다. p items로 값을 확인하고 next로 현재 함수의 다음 줄, step으로 호출 안쪽, continue로 계속 진행한다.

디버거에서 함수를 호출하거나 표현식을 평가하면 상태가 바뀔 수도 있다. 관찰용 값 확인과 변경하는 명령을 구분하고 중단 때문에 달라진 타이밍을 원래 동시 실행으로 일반화하지 않는다. 실습을 마치면 넣은 breakpoint를 제거한다.

둘째 행은 원래 실패를 관찰한 것이 아니라 입력을 변경한 새 실험이다. 반환 7과 호출 뒤 빈 목록을 모두 적어야 변경 경로가 보인다.

중간 과정을 따라가는 예제

코드: def first(items): return items[0] 이고 호출은 first([])다. 손 추적으로 예외 위치와 원인 조건, 개선 정책을 설명하라.

  1. items는 길이0인 리스트다.

  2. items[0]은 존재하지 않는 위치를 요구하므로 IndexError가 예상된다.

  3. 호출자와 first의 줄을 따라 빈 입력이 허용되는지 확인한다. 정책을 빈 입력 ValueError로 명시한다면 if not items: raise ValueError("empty")를 앞에 둔다.

원래는 IndexError가 예상되고 빈 입력 정책을 명시한 수정은 ValueError가 예상된다. 실제 traceback의 정확한 줄번호·표시는 실행 버전에 따라 확인해야 한다.

소단원 11.2

assert와 단위테스트

테스트 코드가 있다고 테스트를 실행한 것까지 증명될까?

준비 개념과 학습 목표

준비 개념

  • 조건문과 예외

  • 함수 반환값

학습 목표

  • assert와 필수 입력 검사를 구분한다

  • unittest의 기대값·예외 검사를 작성한다

  • 실패와 예외 종류·미실행 상태를 구별한다

예외를 기대하는 검사가 통과했어도 상태 계약이 틀릴 수 있을까?

검사는 기대 예외와 그 뒤 상태를 둘 다 볼 수 있다. 가상 add_checked(log,n)는 음수 n을 거절하면서 log를 보존해야 한다. 잘못된 구현이 log.append(n) 후 ValueError를 내면 assertRaises(ValueError)만으로는 통과할 수 있지만 보존 계약은 틀린다.

검사마다 새 log=[]를 준비하면 서로의 잔여 상태를 숨기거나 떠넘기지 않는다. 예외 검사를 마친 뒤 self.assertEqual(log, [])를 별도로 둔다. 사용자 코드의 assert 문장과 unittest의 검사 메서드는 실행 방식이 다르다.

assert 안의 필요한 변경은 최적화 때 없어질 수 있다. assert log.append(7) is None은 일반 실행에서는 7을 추가하고 조건도 참이지만 -O에서는 그 변경 자체를 기대할 수 없다. 필수 처리와 개발용 기대 검사를 나누는 이유다. 아래 테스트는 설계/예측이며 실제 runner는 실행하지 않는다.

먼저 확인할 개념
  • 실패 후 상태

    기대 예외와 완료 변경을 함께 관찰한다.

  • 외부 목록과 함수

    매 검사에 새 목록을 주어 공유 상태를 통제한다.

내부 기대와 외부 계약

assert는 개발 중 기대하는 조건을 검사하는 문장이다. 일반 실행에서 거짓이면 AssertionError를 일으키지만 -O 최적화에서는 assert 코드가 생략될 수 있다. 항상 필요한 입력 검사나 보안 검사를 이것만으로 구현하지 않는다.

외부 입력의 잘못된 값은 if 조건과 raise 등으로 명시적으로 처리한다. assert 안에 필요한 상태 변경을 넣으면 최적화 때 그 변경까지 없어질 수 있다. 테스트용 표현식은 가능한 한 상태를 바꾸지 않게 쓴다.

입력과 기대를 쌍으로 쓴다

단위테스트는 작은 동작에 입력을 주고 반환값이나 예외를 기대와 비교한다. unittest.TestCase 안의 test로 시작하는 메서드에 self.assertEqual(실제값,기대값)을 쓸 수 있다. 예상 예외는 with self.assertRaises(ValueError): 안에서 해당 호출을 한다.

예상 예외가 나오면 예외 테스트가 통과할 수 있다. 예외가 전혀 없으면 실패하고 다른 예외가 나오면 오류다. 코드를 작성한 사실과 실행 결과는 별개이며 통과한 사례만으로 모든 입력의 정확성을 증명하지 않는다.

저장과 실행을 구분한다

학습자가 같은 폴더에 calc.py와 test_calc.py를 저장했다면 test_calc.py에서 from calc import double로 가져올 수 있다. 터미널을 그 폴더로 옮겨 python -m unittest -v test_calc로 실행하고 발견된 테스트 수·각 결과·오류를 확인한다.

이 자료에는 테스트를 실제 실행한 로그가 없다. 모듈 이름과 파일 경로가 맞지 않으면 ImportError 등이 생길 수 있고 테스트 이름을 잘못 쓰면 의도한 검사가 발견되지 않을 수 있다. 발견0개를 원하는 동작이 검증됐다고 기록하지 않는다.

준비 개념과 학습 목표

준비 개념

  • 정수와 비교

  • 함수 계약과 예외

학습 목표

  • 계약에서 정상·경계·오류 입력을 만든다

  • 기대값을 구현과 독립적으로 정한다

  • 유형과 값 오류를 구분한다

경계 테스트 목록에도 결함을 못 잡는 기대가 들어갈 수 있을까?

경계 입력을 골라도 기대값이 같은 잘못된 조건에서 만들어지면 검사가 약하다. 배송 규칙은 1000 이상 무료다. 잘못된 구현의 >1000을 기대 계산에도 복제하면 입력 1000의 잘못된 배송비 300을 정상이라고 받아들인다.

규칙 문장을 기준으로 고정한 표와 구현을 비교하자. True와 1의 값 동등성도 반환 종류 계약을 자동 검증하지 않는다. 0과 False는 동등 비교에서 같을 수 있으므로 반환값이 정확 내장 int여야 한다면 값과 type을 함께 확인한다.

작은 유한 영역을 전부 비교하는 활동은 그 영역 안의 보장을 줄 수 있지만 무한 정수·모든 타입·외부 입력기까지 증명하지 않는다. 어떤 후보 결함을 잡았는지와 남은 영역을 적는다. 실제 테스트나 완전 열거는 실행하지 않고 아래 표를 손으로 계산한다.

먼저 확인할 개념
  • 조건의 포함 경계

    이상과 초과가 같은 입력에서 갈리는 지점을 찾는다.

  • 값과 정확 타입

    bool 값 동등성과 내장 int 계약을 분리한다.

규칙을 먼저 적는다

이 예제의 상품 소계는 bool을 제외한 Python 내장 int이며0 이상이다.1000 이상은 배송비0, 그 미만은300이다. 문자열을 자동 변환하지 않고 음수는 ValueError, 다른 타입은 TypeError를 내는 계약이다.

type(x) is int 검사는 bool과 int의 하위타입도 제외하는 이 예제의 의도적인 좁은 계약이다. 일반 라이브러리의 모든 숫자를 허용하는 규칙으로 확대하지 않는다. 허용 타입을 바꾸면 테스트도 새 계약에 맞춰 바꾼다.

경계의 양옆을 선택한다

정상 사례500은 배송300,1500은0이다. 핵심 경계에는999/1000/1001을 고르고0도 최저 허용값으로 고른다. 오류에는-1,"1000",True를 각각 선택한다. 각 입력의 기대를 규칙에서 먼저 계산한다.

구현의 조건식을 그대로 복사해 기대값을 계산하면 같은 실수를 놓칠 수 있다. 사람이 규칙으로 기대값을 정하거나 독립 계산을 한다. 경계 사례 몇 개가 모든 상태·타입·연동을 검증한다는 의미는 아니다.

오류도 계약된 결과다

아래 shipping 함수는 먼저 타입을 검사하고 다음 음수 값을 검사한다. True는 Python에서 int의 하위타입이지만 type(True) is not int이므로 TypeError로 분기한다. "1000" 역시 TypeError다. 음수 내장 정수-1은 두 번째 검사에서 ValueError다.

테스트는 반환값뿐 아니라 기대 예외도 검사한다. 실제 UI 입력 문자열을 받아 정수로 변환하는 정책은 이 함수 바깥의 별도 작업이다. 여기서는 함수를 실행하지 않고 분기와 값을 손으로 예측한다.

중간 과정을 따라가는 예제

아래 함수에999/1000/1001/0/-1을 넣었을 때를 추적하라. 

def shipping(subtotal):
    if type(subtotal) is not int:
        raise TypeError("subtotal must be an integer")
    if subtotal < 0:
        raise ValueError("subtotal must be nonnegative")
    return 0 if subtotal >= 1000 else 300

소단원 11.4

테스트 가능한 함수 분리

계산을 확인할 때마다 키보드 입력과 출력까지 꼭 거쳐야 할까?

준비 개념과 학습 목표

준비 개념

  • 함수 인수·return

  • 입력 문자열과 정수 변환

학습 목표

  • 계산과 입력·출력을 분리한다

  • 명시적 의존성이 테스트를 돕는 이유를 설명한다

  • 단위 확인과 전체 연동 확인을 구분한다

계산 검사가 맞는데 입력 오류가 정상 무료 배송으로 표시되면?

입력 변환·계산·표시를 나누면 결함의 책임을 지정할 수 있다. 문자열 abc를 int로 바꾸지 못했는데 무료 배송 0으로 대신하면 계산 함수가 제대로 되어 있어도 전체 결과는 잘못이다. 실패 표시와 정상 0을 별도 경로로 둔다.

고정 입력 문맥의 handle(raw,emit)은 변환/계산 실패 때 emit("error")를 한 번, 성공 때 emit(f"fee:{fee}")를 한 번 호출하는 설계다. emit은 주입한 내장 목록의 append라고 가정하여 출력 계획을 조사할 수 있다. 출력 소비자의 실패·실제 화면·메모리 실패 계약은 별도다.

외부 설정도 명시 인수로 받는다. 무료 경계 threshold가 전역에서 바뀌면 같은 subtotal만으로 결과가 고정되지 않는다. subtotal과 threshold의 계약을 함께 적고 core의 단위 확인과 adapter의 전달/표시 확인을 따로 설계한다. 실제 함수를 실행하지 않는다.

먼저 확인할 개념
  • 매개변수와 return

    숨은 전역과 명시 인수를 구별한다.

  • try의 실패/else 경로

    변환 실패 때 정상 표시 경로에 들어가지 않도록 한다.

계산의 입력을 매개변수로 받는다

shipping(subtotal)은 인수에서 계산하고 배송비를 return한다. 계산 중 input이나 print, 파일 읽기, 현재시각 조회를 하지 않으면 같은 명시 입력을 여러 사례로 비교하기 쉽다. 모든 함수가 반드시 이런 모양이어야 한다는 규칙이 아니라 핵심 계산을 분리하는 설계다.

return값과 화면출력은 다르다. print만 하는 함수는 끝에 도달하면 None을 반환하므로 테스트가 배송비 숫자를 직접 비교할 수 없다. 화면과 반환을 둘 다 요구한다면 각 책임을 분명히 한다.

외부 경계에서 변환한다

사용자 입력은 문자열이므로 UI나 main에서 정수로 변환한 후 계산 함수에 전달한다. 변환 실패와 소계 범위 오류는 서로 다른 위치의 문제다. 어떤 오류를 사용자에게 어떤 문구로 보여 줄지는 별도 정책이다.

아래 최소 CLI는 strip/int 변환을 쓰므로 주변공백이나 부호는 int의 규칙에 따른다. 통화 기호·쉼표 등을 모두 받는 결제 입력기라고 주장하지 않는다. 이 예제에서는 입력 한 번에 끝나고 재시도 루프도 없다.

단위와 연동을 각각 확인한다

핵심 함수만 확인해도 잘못된 경계조건을 찾을 수 있다. 반면 파일경로·모듈 가져오기·입력 변환·예외 표시 같은 전체 흐름은 별도 사례로 확인해야 한다. 함수 분리는 연동검사를 없애는 것이 아니다.

시간·난수·외부 서비스가 필요하면 결과를 인수나 작은 인터페이스로 전달하는 방법을 생각한다. 숨겨진 전역값이나 호출마다 바뀌는 의존성이 남아 있으면 같은 인수만으로 결과를 결정한다고 부를 수 없다. 실제 외부 서비스를 호출하지 않는다.

다른 문제에 적용하기

강의 신청 수량의 순수 core를 설계한다. quantity는 bool 제외 정확 내장 int이고 1..3을 허용한다. 그 외 타입은 TypeError, 내장 정수의 범위 밖은 ValueError다. 성공 반환은 정확 내장 int인 quantity*2다. 어댑터는 raw.strip()을 int로 변환한 뒤 core에 전달한다. 실패는 emit("error"), 성공은 emit(f"slots:{result}")를 각각 한 번 계획한다. emit은 새 내장 목록 records의 append라고 가정한다. raw="0","1","3","4","abc"의 경로와 기대를 적고 core(True)를 따로 검사하라. 수량 >=3을 거절하는 경계 변이와 성공 False 반환 변이를 잡는 검사, 오류 뒤 외부 records가 새 문구 하나만 갖는 검사를 설계하라. 모든 raw 비교는 각각 새 records=[]에서 시작한다. 실제 runner/화면/학생은 실행하지 않는다.

힌트 1

1과 3은 포함 경계다. abc는 core 이전 변환에서 실패하며 True는 어댑터 문자열 경로와 다른 직접 core 입력이다.

힌트 2

예외 종류·정확 반환 타입·emit 횟수/내용은 별개 검사다. 변이 결과를 기대 생성에 복제하지 않는다.

풀이와 답 확인

  1. 0과 4는 변환 후 core ValueError로 records=["error"]다. abc는 변환 ValueError여서 core 호출 없이 같은 표시다.

  2. 1과 3은 결과 2/6, records=["slots:2"]/["slots:6"]다. core(True)는 TypeError다.

  3. quantity=3의 성공 기대 6으로 >=3 거절 변이를 잡는다. 성공 반환은 type(result) is int 및 고정 수치로 검사하여 False 반환 변이를 구별한다.

  4. 각 검사에 새 records를 만들고 기대 예외 뒤 상태/표시도 확인한다. 오류 뒤 정상 emit이 이어져 records에 두 항목이 생기면 실패다.

  5. 명세에서 기대를 고정하고 실제 발견/실행/통과 수는 미수행으로 남긴다. 가짜 emit 설계가 실제 UI나 메모리/출력 장애를 증명하지 않는다.

오류 표시는 0/4/abc의 ["error"], 정상은 1→["slots:2"], 3→["slots:6"]다. abc와 범위 실패의 계층을 나누고 True는 직접 core TypeError다. 값/정확 타입/예외/표시 횟수를 각각 검사한다.
