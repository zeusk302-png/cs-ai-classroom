import와 module 경로

같은 import 계산을 두 번 쓰면 파일도 두 번 처음부터 실행될까?

준비 개념과 학습 목표

준비 개념

  • 함수 정의

  • 변수와 대입

  • 파일·폴더

학습 목표

  • 모듈 객체와 가져온 이름을 구별한다.

  • 검색 경로와 가림을 설명한다.

파일을 고쳤는데 같은 프로그램에서 다시 import한 값은 왜 옛것일까?

이미 가져온 모듈은 이름별 모듈 캐시에서 찾을 수 있다. 파일 수정과 현재 모듈 객체의 변경은 다른 사건이다. 정상적으로 처음 불러온 자체 모듈 settings의 limit=4를 파일에서 7로 고쳤다고 하자. 같은 interpreter에서 다시 import하기만 하면 캐시를 재사용하는 조건 아래 현재 limit는 여전히 4다.

from으로 가져온 이름도 모듈 속성의 실시간 연결선이 아니다. 하지만 함수 객체는 자신이 정의된 모듈의 전역 공간을 사용한다. 모듈 속성 limit를 재대입하면 과거에 가져온 정수 이름은 그대로인데 같은 모듈 전역 limit를 읽는 함수의 결과는 바뀔 수 있다.

순환 import는 캐시와 초기화 순서를 함께 생각해야 한다. 모듈 객체가 캐시에 있다는 사실과 필요한 속성이 이미 정의됐다는 사실은 다르다. 여기서는 단일 interpreter, 정상 기본 import, 명시한 순서이며 reload·캐시 삭제·import hook 조작은 수행하지 않는다.

먼저 확인할 개념
  • 이름과 객체 결박

    가져온 정수 이름과 모듈 속성 재결박을 구별한다.

  • 함수가 읽는 전역 공간

    함수 호출자의 지역 값이 아니라 정의 모듈의 전역을 읽는다.

파일을 모듈 이름으로 만나기

모듈은 정의와 실행 문장을 담은 코드 단위다. import calc 는 calc 라는 이름을 모듈 객체에 연결한다. calc.total 처럼 점 뒤 이름으로 모듈 안 대상을 찾는다. from calc import total 은 현재 공간에 total 을 연결하고 calc 라는 이름을 새로 만들지는 않는다.

보통 처음 import 할 때 최상위 문장이 실행되어 정의와 초기 상태가 생기고 같은 interpreter 에서 다시 import 하면 이미 불러온 모듈을 재사용한다. reload·별도 프로세스·직접 스크립트 실행은 다른 조건이다. 함수 본체는 def 로 정의한 것만으로 호출되지 않는다.

이름을 복사하는 것과 객체 공유

from calc import rate 는 그 시점 객체에 현재 이름 rate 를 연결한다. 이후 calc.rate 를 다른 정수 객체에 재대입해도 현재 rate 결합은 자동으로 따라가지 않는다. 반면 같은 리스트를 참조하고 그 리스트 내용을 바꾸면 두 이름으로 변경을 볼 수 있다.

값처럼 보이는 문자열이나 정수도 이름과 객체를 분리해 생각하면 재대입을 설명할 수 있다. 모듈을 통한 calc.rate 읽기는 그때 모듈의 속성을 찾는다. 프로그램의 모든 변수에 실시간 연결선을 만드는 import 라고 생각하면 틀린 예측을 한다.

어느 파일을 찾는가

공식 기본 설명은 built-in 이름을 먼저 확인하고 그렇지 않으면 sys.path 디렉터리를 검색한다. 일반 스크립트 디렉터리, PYTHONPATH, 설치별 기본 경로가 관련된다. 고급 import hook 은 더 넓은 동작을 가질 수 있으므로 이 순서를 모든 모듈 로더의 완전한 명세라고 하지 않는다.

프로젝트 안 random.py 가 표준 라이브러리 random 을 가릴 수 있다. 보이는 파일 이름만으로 출처를 추측하지 말고 모듈의 __file__이 있는 경우 실제 위치를 점검한다. built-in 은 파일 위치가 없을 수도 있다. 불필요한 sys.path 변경보다 패키지 구조와 실행 위치를 명확히 한다.

read_limit은 return limit인 함수로 정의한다. 함수가 반환하는 값은 호출 시 모듈의 전역에서 읽고, from으로 가져온 정수 이름은 옛 객체를 가리킨다. 별도 파일 수정만 했다면 세 번째 행의 재대입과 같은 효과라고 해석하지 않는다.

중간 과정을 따라가는 예제

자체 calc.py 는 최상위 print("load"), rate=3, 함수 double(x)가 2*x 를 반환한다. 처음 import calc, 다시 import calc, from calc import rate, calc.rate=9, double 을 calc.double(4)로 호출한다. reload 나 예외는 없다.

  1. 첫 import 는 load 를 한 번 출력할 것으로 추론하고 모듈 이름 calc 를 연결한다.

  2. 둘째 import 는 같은 모듈을 재사용하므로 load 가 다시 출력되지 않는다.

  3. from 으로 가져온 rate 는 정수 3 에 연결된다. calc.rate=9 는 모듈 속성만 9 로 바꾼다.

  4. calc.double(4)는 2×4=8 이며 rate 의 재대입과 관계없다.

예상 load 1 회, 현재 rate=3, calc.rate=9, 함수 결과 8 이다. 실제 실행 결과가 아니다.

조건을 바꾸어 비교하기

파일 수정은 살아 있는 속성 대입이 아니다

처음 settings의 limit=4를 불러온 뒤 파일 내용만 limit=7로 바꿨다. 같은 interpreter의 반복 import와 새 interpreter의 첫 import를 비교하라. 새 환경은 수정한 소스를 정상 로드한다고 가정한다.

  1. 같은 환경은 이미 있는 모듈을 재사용해 4다.

  2. 새 환경은 수정 소스를 로드해 7이다.

  3. 파일 위치/소스 캐시/검색 문맥을 관측하지 않았다면 실제 파일 로드 결과로 주장하지 않는다.

명시한 모형의 예상은 4/7이다.

비교할 점

기본의 반복 초기화 수에서 파일과 객체 상태의 차이를 추가한다.

반쯤 초기화된 모듈을 읽는다

a.py는 먼저 import b, 다음 ready=9다. b.py는 import a 다음 observed=a.ready다. 둘 다 처음 불러오는 환경에서 import a를 추적하라.

  1. a 객체를 캐시에 넣고 a의 첫 문장으로 b를 시작한다.

  2. b의 import a는 초기화 중인 a 객체를 찾는다.

  3. 아직 ready=9를 수행하지 않아 a.ready 조회가 실패한다.

캐시 존재가 초기화 완료를 뜻하지 않는다. 실제 순환 모듈은 실행하지 않았다.

비교할 점

기본의 성공한 반복 import와 부분 초기화의 속성 부재를 비교한다.

종이와 본문으로 직접 해보기

모듈 bag=[1]을 from calc import bag 로 가져온 뒤 calc.bag.append(2), 이어 calc.bag=[8]로 재대입하면 현재 bag 은? 일반 검색 목록을 [프로젝트,표준경로]라 하고 두 곳에 random.py 가 있다면 어느 파일 후보를 먼저 찾는가?

힌트 보기

append 는 기존 객체를 바꾸고 대입은 이름 결합을 바꾼다. built-in 이 아닌 파일 후보 모형이다.

풀이 보기

append 뒤 두 이름은 [1,2]를 공유한다. 재대입 뒤 현재 bag 은 [1,2], calc.bag 은 [8]이다. 명시한 후보 모형에서는 프로젝트 파일을 먼저 찾는다.

오해와 반례

import 는 모든 변수를 원본과 계속 동기화한다.

rate=3 을 가져온 뒤 calc.rate=9 로 바꿔도 현재 rate 는 3 이다. 리스트 공유와 이름 재대입을 구별해야 하며 반복 import 도 새 프로세스에서는 새 초기화가 된다.

계산 결과, 출력, 종료 상태는 서로 다른 채널이다. main()이 정수 2를 반환해도 호출한 쪽이 버리면 그것만으로 프로세스 종료 상태 2가 되지 않는다. sys.exit(main())처럼 연결해야 한다. 여기서는 정상 종료를 방해하는 다른 예외나 종료 정리 실패는 제외한다.

주 실행 이름 __main__과 import의 모듈 이름을 나누면 실행 전용 코드를 설계할 수 있다. 다만 guard 밖 대입과 함수 정의는 첫 import 초기화에서 수행된다. 입력 처리·출력을 main에 두고 계산 함수는 값을 받아 값을 돌려주게 설계한다.

python -m school.report는 패키지 문맥에서 모듈을 찾고 주 실행 환경으로 실행하는 계획이다. __name__은 __main__이어도 패키지 상대 import에 필요한 정보가 함께 존재할 수 있다. 이름 한 칸만 보고 직접 파일 실행과 동일하다고 하지 않는다.

프로그램의 처음과 재사용 부분

__name__은 모듈 안에서 자신의 실행 이름을 나타내는 문자열이다. 파일을 주 프로그램으로 직접 실행하면 __main__이 되고 일반 import 면 모듈 이름이 된다. if __name__ == "__main__": 아래에 실행용 호출을 두면 import 에서 그 호출을 건너뛴다.

guard 는 파일 전체를 비활성화하는 장치가 아니다. guard 밖 print·대입·def 같은 최상위 문장은 import 초기화 때 실행된다. 라이브러리로 쓸 계산 함수와 사용자 입력·출력·종료를 분리하는 것이 핵심이다.

main 함수에 시작 흐름 모으기

main() 안에서 입력을 해석하고 계산 함수를 부르면 계산 부분은 직접 값으로 시험하거나 다른 코드에서 가져오기 쉽다. def main 은 이름을 만드는 문장이고 main()은 본체를 호출하는 표현식이다. 둘을 같은 사건으로 세면 출력 순서를 잘못 예측한다.

예외와 return 의 처리 정책도 main 경계에 적는다. main 이 값을 반환했다고 그 값이 자동으로 프로세스 종료 코드가 되는 것은 아니다. sys.exit(main())처럼 실제 종료 연결을 써야 한다. 이 단원 예제는 종료 코드와 입력을 제외한 최소 모형이다.

venv와 dependency

두 프로젝트가 같은 라이브러리의 서로 다른 버전을 요구하면 어떻게 공존할까?

준비 개념과 학습 목표

준비 개념

  • 프로그램 실행

  • 파일 경로

  • 버전 번호

학습 목표

  • 가상환경과 interpreter 를 구별한다.

  • 의존 요구의 교집합을 계산한다.

가상환경 이름이 같으면 사용하는 Python도 같을까?

같은 .venv 폴더 이름은 같은 interpreter라는 증거가 아니다. 생성에 사용한 Python과 실행에 사용한 Python의 경로를 따로 기록한다. 가상환경 활성화는 PATH를 조정하는 방법이며 전체 경로로 환경의 Python을 지정하면 활성화 없이도 사용할 수 있다.

설치 요구의 교집합과 실제 설치 상태도 나눈다. 여기 버전은 prerelease/postrelease가 없는 두 정수 (major,minor)로만 주고 사전식 정수 순서로 비교한다. 1.10은 1.9보다 크며 소수 1.10=1.1로 읽으면 안 된다. 실제 전체 버전 규격이나 dependency solver를 구현하는 문제는 아니다.

가상 요구가 만족돼도 외부 파일·OS·서비스의 동작과 보안 격리는 별도다. 환경을 생성하거나 패키지를 설치할 필요 없이 요구표와 관찰 계획을 만들 수 있다. 실제 성공은 관측한 경우에만 쓴다.

먼저 확인할 개념
  • 문자열과 값의 표현

    버전 표시를 실수의 소수점과 혼동하지 않는다.

  • 동시 조건의 교집합

    모든 요구를 함께 통과해야 후보가 된다.

프로젝트별 설치 공간

venv 는 특정 Python interpreter 를 바탕으로 프로젝트별 패키지 설치 공간을 만든다. A 가 라이브러리 1.0, B 가 2.0 을 요구하면 각 환경에 따로 설치해 충돌을 줄인다. 가상환경이 운영체제 전체나 모든 파일 접근을 격리하는 보안 상자는 아니다.

python -m venv .venv 는 실행한 Python 버전을 바탕으로 만든다. 원하는 3.12 환경을 3.14 실행 파일로 만들면 자동 3.12 가 되는 것이 아니다. 생성 interpreter 와 패키지 버전은 서로 다른 기록 항목이다.

어느 pip 를 사용하는가

activation 은 shell 에서 python 명령을 해당 환경 실행 파일로 찾도록 환경을 조정한다. 환경 Python 의 전체 경로로 실행하면 activation 없이 사용할 수도 있다. 단지 프롬프트 모양을 보는 것보다 sys.executable 과 python -m pip 의 interpreter 연결을 확인한다.

python -m pip install ...은 그 Python 으로 pip 모듈을 실행한다. 외부 pip 명령이 다른 설치를 가리키면 엉뚱한 환경을 바꿀 수 있다. 공식 문서처럼 activation 이 PYTHONPATH 를 자동으로 지우지 않으므로 외부 경로가 검색에 섞이는 조건도 기록한다.

준비 개념과 학습 목표

준비 개념

  • 폴더

학습 목표

같은 freeze 기록인데 코드가 달라지면 같은 프로그램일까?

패키지 구조는 import 이름의 지도를 만들고 설치 기록은 환경의 일부를 설명한다. 둘을 하나의 증거로 합치면 상대 import 오류나 코드 변경을 놓친다. school/tools/report.py의 패키지는 school.tools이며 .calc는 그 안, ..calc는 school 안을 뜻한다.

일반 패키지의 __init__.py와 namespace package를 구별한다. 이 문제는 명시한 일반 패키지 구조만 사용한다. 설치 배포 이름과 import 이름이 다를 수 있으므로 배포 기록에 적힌 이름만으로 어느 파일이 실행됐는지 결정하지 않는다.

pip freeze는 현재 설치 목록을 요구 파일 형식으로 보고하며 solver 결과나 lockfile을 계산하는 명령은 아니다. 코드·데이터·실행 인수·OS·실행 경로·실제 비교 결과는 별도 기록한다. 같은 설치표는 결과 동등성의 충분조건이 아니다.

먼저 확인할 개념
  • 모듈 검색과 결박

    import 이름과 실행된 모듈의 출처를 연결한다.

  • 입력과 결과의 계약

    코드/입력/외부 조건이 결과 검증의 대상임을 읽는다.

점으로 이어진 이름 지도

자체 구조는 study/__init__.py, study/mathops.py, study/report.py 다. study.mathops 는 패키지 study 안 하위 모듈을 가리킨다. __init__.py 는 일반 패키지 초기화 코드이며 빈 파일이어도 된다. namespace package 라는 별도 방식에서는 이 파일 없는 구조도 가능하므로 모든 패키지의 절대 요건이라 하지 않는다.

from study.mathops import add 는 add 이름만 현재 공간에 연결한다. import study.mathops 는 모듈을 전체 경로로 사용한다. 파일명·import 이름·설치 배포 이름이 항상 동일하지 않다는 점도 기억한다. 이 예제에서는 단순하게 동일한 프로젝트 이름을 사용한다.

패키지 안에서 이웃 찾기

report.py 의 from .mathops import add 는 현재 패키지 안 mathops 를 가리키는 명시 상대 import 다. 점은 OS 경로 구분자가 아니라 패키지 관계다. 해당 파일을 임의 직접 실행하면 패키지 문맥이 없어 상대 import 가 실패할 수 있다.

예제 계획은 프로젝트 부모에서 python -m study.report 로 실행해 패키지 문맥을 확보한다. __init__.py 에서 네트워크 요청이나 과한 출력 대신 필요한 초기화만 하면 재사용하기 쉽다. __all__은 별표 import 의 이름 목록과 관련되며 모든 하위 파일을 자동 발견하는 목록은 아니다.

버전은 무엇의 버전인가

requirements 에 pkg==1.2 처럼 쓰는 것은 특정 패키지 버전 요구다. pip freeze 는 현재 환경의 설치 목록을 설치 입력 형식으로 기록한다. 목록에는 직접 필요하지 않은 패키지도 포함될 수 있고 모든 실행 파일·데이터·외부서비스를 기록하지는 않는다.

다른 문제에 적용하기

일반 패키지 school/__init__.py, school/calc.py, school/report.py를 설계한다. calc는 limit=4, 함수 total(values)는 정수 합, 함수 allowed(values)는 total(values)≤limit를 반환한다. report는 from .calc import limit, allowed를 사용한다. 정상 첫 import 뒤 같은 interpreter의 다른 코드가 school.calc.limit=7로 재대입했고 report는 [2,3]을 검사한다. report의 가져온 limit와 allowed의 결과를 각각 쓰라. import 시 입력/출력을 하지 않고 main에서 결과를 출력하며 성공이면 0, 실패면 2를 반환해 종료에 연결하는 계획을 작성하라. 같은 interpreter에서 변경 후 main을 호출한 경우와 별도 새 프로세스의 -m school.report를 비교하라. 새 프로세스에는 외부 설정 7을 주입하지 않으며 원본 파일의 초기값 4를 읽는다. 가상 의존 X>=1.9,<2.0/Y>=1.10,<1.12에 후보 1.9/1.10/1.12를 대조하라. 버전은 최종 두 정수 성분만 비교한다. freeze가 같은데 calc의 합 함수를 두 배 합으로 바꾼 revision에서 결과까지 같다고 말할 수 있는지 설명하고, 실행 출처/코드/데이터/환경 및 실제 미수행을 포함한 기록 카드를 구성하라. 모든 모듈/명령은 설계와 손추적이며 실제 생성/실행/설치는 요구하지 않는다.

힌트 1

가져온 정수는 옛 4지만 allowed의 전역은 calc의 현재 limit를 읽는다. main의 반환과 출력/종료 연결을 분리한다.

힌트 2

버전의 minor는 소수가 아니다. 같은 freeze에도 revision 변경의 입력/출력 반례를 별도로 적는다.

풀이와 답 확인

  1. report.limit는 4, 합은 5이고 allowed([2,3])는 현재 calc.limit=7과 비교해 True다.

  2. report의 정의와 import는 입력/출력을 만들지 않게 한다. main이 계산/출력 후 True면 0, False면 2를 반환하고 guard 안 sys.exit(main())로 연결한다. 같은 interpreter에서 limit를 7로 바꾼 뒤 main을 호출하면 True와 반환 0을 예측한다.

  3. 프로젝트 부모에서 별도 새 프로세스로 -m school.report를 실행하는 계획과 환경 Python의 전체 경로를 명시한다. 외부 설정 7이 없으면 새 calc.limit=4이므로 합 5는 허용되지 않아 False와 종료 상태 2를 예측한다. 기존 interpreter의 재대입 상태는 새 프로세스로 자동 전달되지 않는다. 실제 출처 확인과 실행은 아직 미수행이다.

  4. 동시 요구는 [1.10,1.12)다. 1.9는 Y 미달, 1.10은 통과, 1.12는 Y 상한 제외다. 이것은 설치 성공 판정이 아니다.

  5. 두 배 합 revision은 [2,3]의 합을 10으로 만들어 limit=7에서 False다. 같은 freeze만으로 True와 False의 결과를 같다고 할 수 없다.

  6. 카드는 코드 revision/데이터 [2,3]/실행 인수·현재 limit/모듈 출처/환경 Python 경로·버전/패키지 기록/OS/예상 출력·상태/실제 미수행을 나눈다.

같은 interpreter에서 재대입한 뒤에는 report의 옛 값 4와 현재 전역을 읽는 True를 분리하고 main의 반환 0을 예측한다. 외부 설정 없이 시작한 별도 새 -m 프로세스는 초기 limit=4에서 False와 상태 2다. 반환을 종료로 연결하고 패키지 문맥·환경 경로를 계획한다. 후보 중 1.10만 통과한다. 현재 limit=7에서 수정 revision의 합 10/False가 재현 반례이며 실제 실행 성공은 기록하지 않는다.
