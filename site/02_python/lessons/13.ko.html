소단원 13.1

iterable·iterator protocol

같은 목록을 새로 읽는 일과 소진한 책갈피를 다시 넘기는 일은 어떻게 다를까?

준비 개념과 학습 목표

준비 개념

  • 리스트

  • 예외와 객체

학습 목표

  • iterable과 iterator를 구별한다.

  • iter와 next의 위치를 추적한다.

  • 소진과 새 반복자 생성을 나눈다.

목록의 평균을 두 번의 순회로 구하면 반복자는 어떤 답을 남길까?

평균 함수가 먼저 sum(values), 다음에 sum(1 for _ in values)를 수행한다고 가정한다. 고정 목록 [2,6]은 각 순회가 새 반복자를 얻어 합 8과 개수 2가 된다. 같은 값을 가진 iterator를 전달하면 첫 순회가 소진시켜 두 번째 개수는 0이다. 값의 열뿐 아니라 소비 가능한 현재 위치가 입력 계약의 일부다.

두 번 읽는 요구를 그대로 유지하려면 재반복 가능한 고정 자료 또는 새 반복자를 만들어 주는 함수를 명시해야 한다. 이미 소진한 객체에 iter를 다시 호출하는 것은 복원이 아니다. 한 번 읽는 평균은 total/count를 같은 반복 안에서 갱신해 문제를 줄이지만 예외·무한 입력·빈 입력의 정책도 필요하다.

이 절은 고정 유한 내장 정수와 정상 순차 소비만 손으로 추적한다. 같은 반복자에 별칭을 붙인 뒤 두 소비자가 번갈아 next를 요청하면 위치를 공유한다. 서로 다른 이름의 요청은 새 데이터 복제라는 의미가 아니다.

    동일 객체를 참조하는 두 이름과 새 반복자의 차이를 그린다.

  • 합·개수·빈 상태

반복 대상과 현재 위치를 나눈다

iterable은 반복에 필요한 iterator를 얻을 수 있는 대상이다. 리스트에서 iter(items)를 호출해 반복자를 얻는다. iterator는 next로 다음 값을 반환하고 항목이 없으면 StopIteration 종료 신호를 제공한다. for는 이 절차를 사용해 반복을 마친다.

같은 리스트에서 얻은 별개 반복자 두 개는 같은 요소를 읽어도 위치가 독립적이다. 새 반복자를 얻어 처음부터 읽는 일과 기존 반복자가 현재 위치를 기억하는 일을 구별한다. 이 예제는 반복 중 원본을 바꾸지 않는다.

next는 남은 항목을 소비한다

a와 b는 각각 같은 리스트의 처음에서 시작한다. next(a)를 두 번 호출하면 4와 7을 읽어 a는 9 앞에 남는다. next(b)는 4를 읽어 b는 7 앞에 남는다. list(a)는 남은 9를 새 리스트에 담으며 a를 끝까지 소비한다.

두 번째 list(a)는 빈 리스트다. list(b)는 남은 7과 9를 담아 b도 소진된다. iter(b)는 b 자신을 반환해 처음으로 돌아가지 않는다. 아래 예제의 실제 출력과 위치를 대응시킨다.

items = [4, 7, 9]
a = iter(items)
b = iter(items)
print(next(a), next(a), next(b))
print(list(a), list(a), list(b))
print(iter(b) is b)
try:
    next(b)
except StopIteration:
    print("end")

소진 이후의 계약을 지킨다

정상 iterator는 한번 StopIteration을 낸 뒤 이후 next에서도 종료 신호를 내야 한다. 임의로 다시 값을 내면 소비자의 종료 기대를 깨뜨린다. 처음부터 읽으려면 재반복 가능한 원본에서 새 반복자를 얻거나 필요한 자료를 보존한다.

모든 iterable이 여러 번 처음부터 읽히지는 않는다. iterator와 generator도 iterable이지만 같은 객체를 다시 사용하면 남은 값만 읽는다. 파일과 네트워크처럼 외부 자원이 있는 대상은 iter 호출만으로 새 자료를 얻는다는 보장이 없다.

소단원 13.2

yield와 지연 계산

함수 호출 뒤 함수 안의 출력이 아직 나오지 않을 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 함수와 return

  • range

  • iterator

학습 목표

  • 호출과 본문 실행을 나눈다.

  • yield 중단·재개를 추적한다.

  • 지연 계산의 저장과 오류 한계를 밝힌다.

yield 뒤 finally는 소비자가 멈춘 순간에 이미 끝났을까?

자작 generator는 try 안에서 1을 yield하고 이어 0으로 나누며 finally에서 정리 사건을 남긴다. 객체 생성은 본문을 아직 실행하지 않는다. 첫 next는 1에서 중단하며 뒤 나눗셈과 finally도 아직 없다. 두 번째 next에서 나눗셈 오류가 생기고 finally를 거쳐 전파된다.

첫 값만 받은 뒤 break한 소비자를 상상하자. break는 이 generator의 close를 호출하는 명시적 계약이 아니다. 객체를 보유한 채 정리가 끝났다고 판단하면 위험하다. 고정 generator에서 close를 명시하면 중단 지점에 GeneratorExit가 전달되어 finally가 수행되고 generator는 닫힌다. 실제 자원을 다루는 경우 with의 책임 경계와 닫기 계획을 정한다.

지연은 입력을 항상 고정하지도 않는다. data=[1,2], g=(x*factor for x in data), factor=10 뒤 factor=3으로 바꾸고 소비하면 현재 factor 3을 사용한다. 바깥 iterable의 표현은 만들 때 평가되지만 뒤 결과 식과 이름 읽기는 소비 때다. 참조한 목록 내용도 자동 snapshot이 아니다.

먼저 확인할 개념
  • finally의 마무리

    보호 구간이 아직 중단 상태일 때와 실제 종료할 때를 나눈다.

  • 이름의 현재 결박

    지연 결과 식이 소비 시 읽는 외부 이름을 확인한다.

필요할 때 값을 만든다

yield를 포함하는 이 함수를 호출하면 generator 객체가 생긴다. 호출 직후 본문 전체가 실행되는 대신 next로 요구할 때 시작한다. yield는 값을 전달하고 지역 변수와 다음 실행 위치를 보존하며 중단한다.

다음 next는 중단 지점 다음부터 이어진다. return이 실행을 끝내는 것과 달리 yield 이후 반복을 이어 갈 수 있다. 함수가 끝나면 generator도 소진되며 같은 객체를 list로 다시 읽어도 처음부터 계산하지 않는다.

출력이 발생한 시점을 추적한다

doubled(3) 직후에는 start가 아직 출력되지 않아 created가 먼저 나온다. 첫 next는 start와 make 0을 출력하고 0을 넘긴다. 바깥 print가 0을 출력한 뒤 둘째 next는 make 1과 값 2로 이어진다.

list(g)는 남은 값을 모두 요구한다. make 2 뒤 4가 yield되고 다시 재개하면 done 뒤 끝난다. 따라서 done이 [4]의 출력보다 먼저 나온다. yield 뒤의 코드는 그 재개가 없으면 아직 수행되지 않는다.

def doubled(stop):
    print("start")
    for n in range(stop):
        print("make", n)
        yield 2 * n
    print("done")

g = doubled(3)
print("created")
print(next(g))
print(next(g))
print(list(g))
print(list(g))

지연이 모든 저장을 없애지 않는다

하나씩 값을 넘기면 출력 전체의 중간 목록을 피할 수 있다. 그러나 함수 안에서 큰 리스트를 만들거나 소비자가 list(g)로 모두 모으면 자료가 메모리에 남는다. 입력 참조와 지역 상태도 존재한다.

본문 오류는 객체 생성 대신 소비 중 드러날 수 있다. 파일 같은 자원은 중단된 generator에 남을 수 있어 닫기 범위를 계획해야 한다. 여기서는 작은 range만 실제 실행했으며 큰 자료나 자원 성능은 미수행이다.

소단원 13.3

list·dict·set comprehension

값을 그대로 담는 일과 중복을 없애거나 이름으로 덮어쓰는 일은 같을까?

준비 개념과 학습 목표

준비 개념

  • for와 if

  • 리스트·dict·set

  • 나머지와 제곱

학습 목표

  • 일반 반복문으로 풀어 읽는다.

  • 각 결과 구조의 중복 규칙을 구별한다.

  • 복잡한 표현의 순서와 가독성을 검토한다.

중복 점수의 마지막 값을 남길까, 모든 값을 누적할까?

자료 [("a",2),("b",4),("a",5)]에서 dict comprehension은 a의 마지막 값 5를 남긴다. 합산 요구라면 a는 7이어야 하므로 같은 자료를 받아도 계약이 다르다. 짧은 문법이 원하는 중복 정책을 선택해 주지는 않는다.

순서를 가진 목록 결과와 키별 값, 중복 없는 집합을 구분해 보자. 목록은 세 점수 2/4/5를 보존한다. 집합은 동일 값의 반복을 제거하며 표시 순서를 고정하지 않는다. dict의 같은 키 값 교체는 기존 키의 삽입 위치를 새로 뒤로 보내는 일이 아니다.

comprehension에 두 for가 있으면 왼쪽이 바깥이다. 반면 generator expression은 아직 계산하지 않은 결과가 남는다. 외부 부수효과와 복잡한 검사를 한 식에 넣으면 추적이 어려워져 일반 for와 이름 붙인 단계가 도움이 된다. 여기서는 고정 내장 자료의 값/순서만 추적한다.

먼저 확인할 개념
  • 복사와 내부 참조

    새 결과 컨테이너와 원소 객체의 깊은 독립을 나눈다.

  • 누적 불변식

    덮어쓰기와 누적 요구의 차이를 상태로 확인한다.

통과한 입력에 식을 적용한다

list comprehension의 [x*x for x in data if x%2==0]은 각 x를 읽고 짝수인지 검사한 뒤 통과한 값의 제곱을 새 리스트에 담는다. 입력 3, 2, 3, 4에서 2와 4만 통과해 [4, 16]이 된다. 원래 data는 그대로다.

두 for가 있으면 앞 for가 바깥 반복이고 뒤 for가 안쪽 반복이다. 들여쓴 일반 반복문으로 먼저 풀어 읽으면 결과 순서와 제외된 값의 이유를 확인하기 쉽다. 앞쪽 결과 식과 뒤쪽 입력·조건을 나누어 읽는다.

중괄호 안의 형태가 규칙을 바꾼다

{x%3 for x in data}는 set으로, 3 → 0, 2 → 2, 3 → 0, 4 → 1에서 중복된 0을 제거한다. set은 순서를 보장하지 않아 코드가 sorted(unique)로 [0, 1, 2]를 출력한다. 정렬한 목록의 출력과 set 자체 순서를 혼동하지 않는다.

dict comprehension의 name:score는 키별 값을 저장한다. a의 5, b의 7, a의 9 순서에서는 마지막 a의 9가 이전 a의 5를 덮어쓴다. 같은 이름의 점수를 모두 보존하거나 합산하는 요구에는 이 규칙이 맞지 않아 별도 구조나 누적이 필요하다.

data = [3, 2, 3, 4]
values = [x * x for x in data if x % 2 == 0]
unique = {x % 3 for x in data}
labels = {name: score for name, score in [("a", 5), ("b", 7), ("a", 9)]}
pairs = [(x, y) for x in [1, 2] for y in [2, 3] if x != y]
print(values)
print(sorted(unique))
print(labels)
print(pairs)

짧음보다 추적 가능성을 본다

pairs에서 x = 1이면 y = 2와 y = 3이 모두 통과해 (1, 2), (1, 3)이 생긴다. x = 2일 때 y = 2는 빠지고 y = 3만 통과해 (2, 3)이 뒤에 붙는다. 두 for를 바꾸면 일반적으로 순서가 달라진다.

변환과 부수효과를 한 줄에 쌓으면 중간 오류를 찾기 어렵다. 그 경우 일반 for로 단계를 이름 붙일 수 있다. list/set/dict comprehension은 결과 구조를 완성해 저장하므로 지연 generator expression과 다르다.

같은 입력의 다른 중복 정책
읽은 쌍마지막 값 dict누적 합 dict

각 열의 행은 전체 현재 상태다. 두 a가 별개 키가 되는 것이 아니라 같은 키의 갱신 규칙이 다르다.

중간 과정을 따라가는 예제

네 출력을 입력 순서와 중복 정책으로 추적한다.

  1. 짝수 2와 4의 제곱은 [4, 16]이다.

  2. 나머지 0·2·0·1의 집합을 정렬하면 [0, 1, 2]다.

  3. a의 값은 5에서 9로 갱신되고 pairs는 (1, 2), (1, 3), (2, 3)이다.

실제 출력은 [4, 16] / [0, 1, 2] / {'a': 9, 'b': 7} / [(1, 2), (1, 3), (2, 3)]이다.

조건을 바꾸어 비교하기

최종 값과 누적 합

세 입력을 마지막 값 dict와 합산 dict로 각각 구성한다.

  1. a의 첫 값 2를 저장한다.

  2. b의 4를 저장한다.

  3. a의 두 번째 5에서 대입은 5, 누적은 2+5다.

마지막 a=5, 누적 a=7, 둘 다 b=4다.

비교할 점

base 동일 키 갱신에 다른 요구의 구현을 대조한다.

for 순서가 보이는 필터

x=[1,2], y=[2,3], 조건 없이 (x,y)를 담는다.

  1. x 바깥이면 (1,2)/(1,3) 뒤 (2,2)/(2,3)이다.

  2. y 바깥이면 (1,2)/(2,2) 뒤 (1,3)/(2,3)이다.

  3. 원소 집합은 같아도 목록 순서가 다르다.

중간 두 위치가 다르다.

비교할 점

특정 필터의 우연 일치에서 일반 규칙을 분리한다.

종이와 본문으로 직접 해보기

data를 [2, 2, 5]로 바꾸면 짝수 제곱 list와 나머지 set은 무엇인가? 본문 dict의 a 값을 5 + 9 = 14로 해석해도 되는가?

힌트 보기

list는 중복을 유지하고 set은 제거하며 dict는 여기서 합산하지 않는다.

풀이 보기

list는 [4, 4], 나머지 set은 {2}다. 본문 dict의 a 값은 9이며 14로 합산하지 않는다. 추가 입력은 종이로 추적했다.

오해와 반례

중괄호를 쓰면 set과 dict도 입력의 모든 중복과 순서를 보존한다.

set은 중복을 제거하고 순서를 보장하지 않으며 dict는 같은 키의 값을 덮어쓴다. list와 다른 계약이다. 빈 {}는 dict이며 빈 set은 set()으로 만든다.

파일 전체를 한꺼번에 보관하지 않고도 합계를 구할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 텍스트 파일·UTF-8

  • with

  • 반복과 누적

학습 목표

  • 파일 반복과 전체 읽기의 저장 차이를 설명한다.

  • 빈줄·숫자·EOF와 오류를 구별한다.

  • 긴 줄과 집계 상태의 메모리 한계를 밝힌다.

파일을 한 번 읽으면서 검사도 하면 실패 뒤 일부 합을 완성으로 보여도 될까?

자작 줄 소비 계약은 strip 뒤 빈줄을 건너뛰고, 나머지를 int로 변환한 뒤 합과 개수를 갱신한다. 입력 줄 "2 ", "bad ", "6"에서 2 뒤 상태는 합 2/개수 1이나 다음 줄의 변환 실패로 전체 결과는 미완성이다. 오류를 숨겨 평균 2라고 발표하면 요청의 전체 입력 계약을 바꾼다.

실패는 외부 저장을 자동 취소하지 않는다. 중간 상태가 보이는 설계라면 진행 상태와 최종 완료를 구별해야 한다. 이 예제는 함수의 지역 상태만 누적하고 정상 EOF 이후에 완성 결과를 반환한다. 파일을 연 with 안에서 전체 소비하면 성공/예외 뒤 닫기 책임을 확인하기 쉽다.

한 줄 순회는 파일 전체 목록을 피하지만 현재 줄, 문자열 strip 결과, 정수 자릿수와 집계 상태는 남는다. 최대 문자 길이를 읽은 뒤 검사하는 코드는 거대한 줄을 이미 읽었다는 한계가 있다. 엄격한 읽기 중 바이트 제한은 조각 해독/토큰 경계의 별도 설계로 바꿔야 한다.

먼저 확인할 개념
  • 텍스트 해독과 with

    문자 줄을 얻기까지의 해독/수명 책임을 연결한다.

  • 실패와 finally

    실패 시 정리와 정상 결과 선택의 차이를 확인한다.

읽으면서 필요한 상태를 누적한다

file 객체를 for로 반복하면 줄을 차례로 읽을 수 있다. 합계와 개수만 필요하면 이전 줄을 모두 목록에 넣을 필요가 없다. 반면 read()와 readlines() 또는 list(file)는 전체 내용이나 줄 목록을 만들어 큰 저장공간이 필요할 수 있다.

텍스트 인코딩을 지정하고 with 안에서 읽으면 정상 종료나 예외 뒤 파일을 닫는다. generator를 with 밖에서 소비하면 이미 닫힌 파일을 읽으려 할 수 있어 자원의 수명과 소비 범위를 함께 정한다. 파일 반복이 숫자 형식을 자동 검증하는 것은 아니다.

작은 파일로 절차를 확인한다

예제는 임시 폴더에 4, 빈줄, 7, 마지막 개행이 없는 9를 기록한 작은 UTF-8 파일을 만든다. 기존 파일을 덮어쓰지 않으며 임시 폴더는 with 종료 뒤 자동 정리된다. 실제 실행은 이 작은 파일만 확인했으며 큰 파일 성능 시험은 아니다.

strip 결과가 빈 문자열이면 이 예제는 해당 줄을 건너뛴다. 나머지는 int로 변환해 합계와 개수를 누적한다. 마지막 개행이 없는 9도 읽고 for는 EOF에서 끝난다. readline의 빈줄은 개행 문자를 포함하며 EOF의 빈 문자열과 다르다.

from pathlib import Path
from tempfile import TemporaryDirectory

with TemporaryDirectory() as directory:
    path = Path(directory) / "numbers.txt"
    path.write_text("4\n\n7\n9", encoding="utf-8")
    total = 0
    count = 0
    with path.open("r", encoding="utf-8") as file:
        for line_number, line in enumerate(file, start=1):
            text = line.strip()
            if not text:
                continue
            value = int(text)
            total += value
            count += 1
    print(count, total)
    print(total / count if count else "no data")
    print(file.closed)

입력 실패와 저장 한계를 남긴다

세 숫자의 합은 20, 개수는 3이므로 평균은 20/3이다. 전부 빈줄이면 개수가 0이므로 평균을 정의하지 않고 no data를 출력한다. 숫자가 아닌 bad가 있으면 현재 코드는 ValueError로 중단하며 자동으로 0으로 세지 않는다.

한 줄씩 읽어도 한 줄이 매우 길면 그 줄의 저장 공간이 필요하다. 누적 정수도 값이 커지면 자릿수가 늘고 문자열 변환에도 저장이 필요하다. 최대 줄 길이 L과 집계 상태 A를 유지하는 관점으로 보며 모든 파일에 고정 바이트나 빠른 실행을 보장한다고 하지 않는다.

다른 문제에 적용하기

한 번만 읽을 수 있는 줄 iterator의 내용을 2, 빈줄, 6, bad, 8의 다섯 줄로 정한다. 각 비교는 새 iterator에서 시작한다. A는 total=sum(int(s.strip()) for s in rows if s.strip()) 뒤 별도 count 순회를 하며, B는 하나의 for에서 빈줄 제외·변환 성공 뒤 total/count를 갱신해 정상 EOF 뒤에만 (total,count)를 반환한다. 실패를 잡아 별도 error 상태를 표시하며 정상 결과로 바꾸지 않는다. 두 방식이 어디까지 소비하고 결과가 있는지 추적하라. bad를 제거한 네 줄 입력으로 두 방식을 다시 비교하고 B 결과의 평균을 구하라. 마지막으로 B를 with 안에서 전부 소비하는 경우와 with 안에서 generator만 만들어 밖에서 소비하는 경우를 비교하라. 실제 파일/반복자/학생 실행은 하지 않는다.

힌트 1

bad는 int 변환에서 실패하므로 뒤 8은 아직 읽지 않는다. A의 count 순회에 도달했는지부터 보라.

힌트 2

정상 입력에서 A의 첫 순회는 일회성 rows를 소진한다. B는 같은 순회에서 합과 개수를 함께 만든다.

풀이와 답 확인

  1. 오류 입력에서 A는 2와 6 뒤 bad에서 실패하므로 total 대입 자체가 완료되지 않으며 count 순회도 없다. 뒤 8은 미소비다.

  2. B는 실패 직전 지역 total=8/count=2지만 정상 반환은 없고 error 상태다. 뒤 8은 미소비다.

  3. 새 정상 입력 2/빈줄/6/8에서 A는 total=16 뒤 소진 rows의 count=0이다. 빈 정책 None을 주더라도 실제 숫자 입력이 빈 것이 아니다.

  4. B는 (16,3)을 정상 반환하며 평균은 16/3이다. 별도 새 iterator로 각 비교를 시작한다.

  5. with 안에서 B를 전부 소비하면 종료/예외 시 파일 닫기 책임을 지킨다. generator만 반환하면 밖 소비 시 파일이 이미 닫혀 실패할 수 있어 자원 소유 계약을 다시 설계해야 한다.

오류 입력은 두 방식 모두 정상 결과 없음/error, 뒤 8 미소비다. 정상 입력 A는 16/0의 잘못된 두 순회 상태, B는 16/3의 완성 집계다. 파일 수명 안에 실제 소비를 두어야 한다.

해결한 뒤 점검할 것

  • 오류 발생 시점과 대입 완료 여부를 분리한다.

  • 부분 합을 전체 성공으로 표시하지 않는다.

  • 비교마다 새 입력을 시작하고 일회성 소진을 추적한다.

  • 단일 순회 합/개수와 빈 평균 정책을 연결한다.

  • 파일 수명과 지연 소비를 구별하고 실제 미수행을 유지한다.
