소단원 8.1

저널·로그·copy-on-write

파일 이름표와 내용 중 하나만 저장된 순간 전원이 꺼지면 무엇을 읽게 될까?

준비 개념과 학습 목표

준비 개념

  • 파일 데이터와 메타데이터

  • 휘발·영속 저장

학습 목표

  • redo 저널의 영속 순서를 추적한다.

  • 저널과 LFS와 COW의 역할을 구별한다.

로그가 있어도 두 거래를 거꾸로 복구하면 최신 값이 사라질까요?

기본의 두 블록 갱신을 연속된 두 거래로 확장합니다. A와 B의 초기 값은 모두 0입니다. 자체 물리 redo 모형의 거래 T1은 둘을 1로, 다음 거래 T2는 둘을 2로 바꿉니다. 로그에는 최종 블록 값을 기록하고 거래 본문이 영속화된 뒤 원자적인 commit 표지가 영속화됩니다. 여기서 영속화는 명시한 장치 규약 아래 전원 손실 뒤에도 남는다는 뜻이며 단순 캐시 응답과 다릅니다.

완료 거래만 로그 순서대로 재실행합니다. 미완료 거래는 홈 블록에 쓰지 않았다고 정하며, 완료한 거래의 홈 반영은 checkpoint라고 부릅니다. 이 모형은 순서를 포함한 복구 규약을 설명하기 위한 것이며 모든 실제 저널 구현을 같은 세부 형식으로 단정하지 않습니다. 실제 전원 차단이나 파일시스템 복구는 수행하지 않았습니다.

먼저 확인할 개념
  • 저널·로그·copy-on-write

    기본 본문에서 commit 전후와 홈 블록 반영을 구분합니다.

  • 일관성·스냅샷·복구

    복구가 보장하는 범위와 여러 파일의 응용 일관성을 비교합니다.

서로 맞아야 하는 여러 기록

파일의 데이터 블록, 그 블록을 가리키는 inode, 사용 여부 bitmap을 따로 바꾸면 중간 충돌로 서로 불일치할 수 있다. 메모리에 갱신했다고 장치에 모두 남는 것은 아니다.

redo 저널은 최종 위치를 덮기 전에 재적용할 내용을 기록한다. 이 절의 단순 모델은 저널 본문을 안전하게 남긴 뒤 원자적인 commit 표시를 남기고, 그다음 최종 위치에 checkpoint한다. 장치가 요구한 순서와 영속 완료를 지킨다는 조건이다.

로그라는 같은 단어의 다른 쓰임

저널의 로그는 기존 위치 갱신을 복구하기 위한 추가 기록이다. LFS는 데이터와 메타데이터 자체를 새 위치의 큰 segment로 모아 저장하는 배치를 중심으로 한다. 둘 다 로그를 쓰지만 최종 자료의 위치와 복구 구조는 같지 않다.

copy-on-write는 기존에 참조되는 버전을 바로 덮지 않고 새 내용을 다른 공간에 저장한 뒤 새 버전으로 참조를 연결하는 방식이다. 새 블록·참조·루트의 안전한 갱신과 옛 공간 회수 규칙이 필요하다. COW라는 이름만으로 어떤 다중 갱신도 원자적이라고 결론 내릴 수 없다.

commit 뒤 반복해도 같은 복구

물리 redo는 최종 블록을 새 내용으로 덮어쓴다. 이미 일부가 새 내용이어도 다시 같은 내용을 쓰면 결과가 동일하다. 아직 commit되지 않은 불완전 저널을 적용해서는 안 된다.

데이터까지 저널하는 방식과 메타데이터만 저널하는 방식은 보장 범위가 다르다. 아래는 데이터도 포함한 작은 종이 모델이며 ext4의 모든 모드·실제 전원 차단을 재현한 것이 아니다.

중간 과정을 따라가는 예제

A=0,B=0을 A=1,B=1로 바꾼다. 두 값을 저널에 남겨 영속 완료하고 commit도 영속 완료한 뒤 A만 checkpoint한 때 충돌했다. 재부팅 뒤는?

  1. 최종 위치는 충돌 직전A=1,B=0으로 부분 갱신이다.

  2. 유효한 commit과 본문이 있으므로 두 새 값을 redo한다.

  3. A에1을 다시 쓰고 B에1을 쓰면A=B=1이 된다.

복구 뒤A=1,B=1. A를 다시 써도 결과가 바뀌지 않는다.

조건을 바꾸어 비교하기

복구 순서가 최신 값을 결정한다

표의 중단 상태에서 T1 다음 T2를 재실행한 결과와 T2 다음 T1을 실행한 결과를 구하세요. 거래 사이에서 다른 쓰기는 없습니다.

  1. T1을 적용하면 홈 값은 1 / 1입니다.

  2. T2를 적용하면 홈 값은 2 / 2입니다.

  3. 거꾸로 T2를 적용한 뒤 T1을 적용하면 1 / 1이 되어 최신 거래를 덮습니다.

정상 순서의 최종 값은 2 / 2입니다. 역순 결과는 1 / 1입니다.

비교할 점

같은 값을 다시 쓰는 멱등성과 거래 사이의 올바른 순서는 서로 다른 조건입니다.

반복 가능한 복구와 로그 해제

T2까지 정상 복구해 A/B가 2 / 2가 된 뒤 같은 완료 로그를 다시 복구합니다. 이어서 홈 블록에 A만 2를 쓴 시점에 T2 로그를 없앴다면 무엇이 달라지나요? 후자의 경우 T1 홈 값 1 / 1에서 시작합니다.

  1. 정상 로그를 순서대로 다시 적용하면 T1이 1 / 1, T2가 2 / 2를 만듭니다. 최종 값은 같습니다.

  2. 별도 조기 해제 경우의 홈 상태는 2 / 1입니다.

  3. T2 로그가 사라졌으므로 B를 2로 복구할 근거를 잃었습니다.

반복 복구는 2 / 2를 유지하지만 조기 로그 해제는 2 / 1을 남깁니다.

비교할 점

완료 기록을 유지해야 하는 기간과 멱등 재실행의 값을 함께 확인합니다.

종이와 본문으로 직접 해보기

저널 본문만 일부 남고 commit은 없다. 최종 위치는 아직0,0이다. 같은 모델의 복구 결과를 적자.

힌트 보기

완료된 거래인지 먼저 구분한다.

풀이 보기

불완전 기록을 건너뛰어 최종0,0을 유지한다. 최종 위치를 commit 전 덮지 않는 가정이 필요하다.

오해와 반례

장치가 쓰기 요청에 응답했으면 반드시 정전 후에도 남는다.

장치의 휘발 캐시에만 들어간 응답일 수 있다. flush·순서·원자 단위 등 실제 장치 계약을 확인해야 한다.

스스로 풀어보기

먼저 답과 이유를 적고, 필요한 만큼 힌트를 한 단계씩 열어 보세요.

연습 1 · 값과 상태 예측

T1만 완료했고 T2의 본문 일부만 영속화되어 commit 표지는 없습니다. 홈 값은 0 / 0이며 미완료 거래는 홈에 반영하지 않습니다. 복구 결과는?

힌트 1

commit이 있는 거래를 먼저 고릅니다.

힌트 2

거래 본문 일부가 있는 것과 완료 표지는 다릅니다.

풀이와 답 확인

  1. T1의 완료 표지를 확인합니다.

  2. T2를 제외하고 T1의 A=1, B=1을 적용합니다.

복구 결과는 1 / 1입니다.

흔한 오답에서 다시 생각하기

더 최신 본문이므로 T2를 무조건 적용한다.

완료 규약을 만족하지 않은 부분 기록을 최종 거래로 인정하지 않습니다.

연습 2 · 오류 찾아 고치기

로그 본문과 commit을 장치에 한꺼번에 보내고 commit만 먼저 영속화될 수 있게 했습니다. 복구자가 commit만 확인하면 안전하다는 설명을 고치세요.

힌트 1

요청을 보낸 순서와 영속 저장된 순서를 나눕니다.

힌트 2

완료 표지가 가리키는 전체 본문도 남아 있어야 합니다.

풀이와 답 확인

  1. 본문 전체를 영속화하는 규약을 먼저 만족시킵니다.

  2. 그 뒤 원자적인 완료 표지를 영속화하고 홈 반영으로 넘어갑니다.

commit만 남고 본문이 빠진 상태를 배제할 저장 순서와 장치 규약이 필요합니다.

흔한 오답에서 다시 생각하기

성공 응답은 모든 장치에서 전원 손실까지 자동 보장한다.

캐시 응답의 의미와 flush·순서·원자 단위의 실제 보장을 확인해야 합니다.

연습 3 · 직접 만들어 보기

COW 트리의 새 잎 L1과 새 루트 R1을 만듭니다. 기존 루트 R0가 남아 있고 새 루트 게시를 원자적으로 영속화할 수 있다고 가정합니다. 게시 전후 중단 상태의 읽기 경로를 구성하세요.

힌트 1

새 루트가 참조하는 자식부터 영속화합니다.

힌트 2

기존 루트의 게시 상태와 새 루트의 게시 상태를 구분합니다.

풀이와 답 확인

  1. L1과 필요한 새 내부 노드를 먼저 영속화합니다.

  2. 그다음 R1을 게시하고 영속화합니다.

  3. 게시 전 중단은 R0, 게시 완료 뒤 중단은 완성된 R1을 읽습니다.

지정한 원자 게시 규약 아래 독자는 오래된 완성 트리 또는 새 완성 트리를 읽습니다.

흔한 오답에서 다시 생각하기

새 루트만 먼저 저장하고 자식은 나중에 쓰면 충분하다.

새 루트가 없는 자식을 가리키는 상태를 만들 수 있으므로 게시 순서를 반대로 두지 않습니다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

메타데이터만 저널에 넣고 파일의 데이터 블록은 저널 밖에 썼습니다. 파일 이름과 할당 구조를 복구할 수 있다는 사실에서 두 응용 파일의 내용 갱신도 한 거래라고 결론 내릴 수 있나요?

힌트 1

저널에 포함한 대상의 범위를 적습니다.

힌트 2

파일시스템 구조와 응용 거래의 경계를 나눕니다.

풀이와 답 확인

  1. 메타데이터의 일관성을 복구하는 범위를 확인합니다.

  2. 응용의 두 파일 내용에 별도 거래 규약이 있는지 확인합니다.

메타데이터 저널만으로 두 파일 내용의 응용 원자성을 보장하지 못합니다.

흔한 오답에서 다시 생각하기

저널이 있으면 모든 응용 동작이 자동 거래다.

기록 대상과 완료 경계를 확대해서 해석하면 보장하지 않은 내용을 주장하게 됩니다.

어제의 스냅샷이 같은 디스크에 있으면 디스크 파손에서도 어제를 지킬까?

준비 개념과 학습 목표

준비 개념

  • 블록 참조

  • 시점과 백업

학습 목표

스냅샷 두 개를 지워도 회수되는 블록 수가 서로 다를까요?

기본 단일 스냅샷을 두 시점으로 확장합니다. A/B/C는 각각 4 KiB이고 서로 다른 세 물리 데이터 블록을 사용합니다. 스냅샷은 변경 전 블록을 공유하며 변경은 새 블록 한 개를 할당한다고 정합니다. 메타데이터, 압축, 중복 제거, 다른 참조와 회수 비용은 제외한 자체 계산입니다.

현재 상태와 각 스냅샷의 참조를 종이에 표시하면 지운 이름의 수와 실제 회수 가능한 블록 수를 분리할 수 있습니다. 실제 Btrfs 스냅샷도 공유 블록을 사용하지만 삭제 뒤 청소는 별도 단계일 수 있습니다. 여기의 회수 후 용량은 청소 완료와 다른 참조 없음까지 가정한 값입니다. 스냅샷·백업·응용의 거래 일관성은 서로 같은 뜻이 아닙니다.

일관성에는 대상이 있다

파일시스템 구조 일관성은 참조와 할당 등 내부 규칙이 맞는 상태다. 응용 프로그램이 두 파일에 나눠 저장한 거래의 의미가 완성됐는지는 별도 문제다. 한 파일만 새 값이면 파일시스템은 정상이어도 거래는 미완성일 수 있다.

복구는 유효한 로그나 이전 루트로 일관된 구조를 다시 만든다. 사용자가 원한 모든 최근 입력이 남는다는 뜻과 같지 않다. 언제 완료로 응답했는지와 데이터·메타데이터 영속 계약을 함께 봐야 한다.

스냅샷의 공유와 분기

COW 스냅샷은 생성 순간 기존 블록을 함께 참조하고 이후 변경을 새 블록으로 분기할 수 있다. 처음부터 모든 파일을 물리 복사하지 않으므로 빠르고 공간 효율적일 수 있다.

어느 버전이라도 참조하는 옛 블록은 아직 회수할 수 없다. 스냅샷과 원본이 같은 장치와 같은 블록을 공유하면 장치 실패나 해당 블록 손상에 같이 영향을 받는다. 별도 장애 경계의 백업을 대체하지 못한다.

복원 범위를 정하기

읽기 전용 스냅샷은 그 시점 자료를 고정해 백업을 만들기 쉽게 하지만 실행 중인 DB의 거래 일관성은 응용 절차가 필요할 수 있다. 복원하려는 시점·대상·중첩 저장소를 적는다.

Btrfs의 중첩 subvolume은 부모 스냅샷에 내용까지 자동 재귀 복사되지 않는다. 다른 파일시스템에도 같은 세부 규칙이라고 일반화하지 않는다. 아래 계산은 메타데이터·압축·중복제거를 제외한 동크기 데이터 블록만 센다.

두 스냅샷이 보존하는 서로 다른 과거 블록
관측 대상참조한 데이터 블록

스냅샷 S0

A, B, C

B를 바꾼 뒤 만든 S1

A, B2, C

C까지 바꾼 현재

A, B2, C2

표의 서로 다른 블록은 A, B, B2, C, C2 다섯 개입니다. 같은 이름 A가 세 곳에 있어도 물리 블록을 세 번 더하지 않습니다.

중간 과정을 따라가는 예제

원본이4KiB 블록A,B,C 3개를 사용한다. 스냅샷S를 만들고 원본B를새B2로 바꾼다. 고유 데이터 공간과 두 버전의 블록 목록은?

  1. 초기에는A,B,C 세 블록12KiB를 공유한다.

  2. 변경 후 원본은A,B2,C이고 S는A,B,C다.

  3. 고유 블록A,B,B2,C 네 개이므로16KiB다.

스냅샷은옛B, 원본은B2를 읽는다. 고유 데이터16KiB.

조건을 바꾸어 비교하기

삭제 순서와 남은 참조

S0와 S1이 모두 있는 표의 물리 데이터 용량을 구하고 S0를 지운 뒤 청소가 끝난 용량을 구하세요.

  1. 고유 블록 다섯 개는 5×4=20 KiB입니다.

  2. S0 삭제 뒤 B만 다른 참조가 없습니다. C는 아직 S1이 참조합니다.

  3. B 회수 뒤 고유 블록은 네 개입니다.

전체는 20 KiB이며 S0 삭제와 청소 뒤 16 KiB입니다.

비교할 점

S0의 참조 세 개를 모두 빼면 공유된 A와 C까지 잘못 회수합니다.

다른 스냅샷을 먼저 지운 경우

처음 상태로 돌아가 S1부터 삭제하고 청소합니다. 그다음 S0도 삭제하고 청소합니다. 각 단계의 용량은?

  1. S1의 A는 현재와 S0에도 있습니다. B2는 현재에, C는 S0에 있습니다.

  2. 따라서 S1만 삭제하면 회수 가능한 데이터 블록이 없어 20 KiB입니다.

  3. S0까지 삭제하면 B와 C가 회수되어 현재의 세 블록만 남습니다.

S1만 삭제한 뒤 20 KiB, S0까지 삭제한 뒤 12 KiB입니다.

비교할 점

같은 크기의 스냅샷을 지워도 남은 참조에 따라 회수량이 달라집니다.

종이와 본문으로 직접 해보기

S를 삭제하고 다른 참조가 전혀 없다고 하자. 옛B는 회수 가능한가? 남은 데이터 공간은?

힌트 보기

현재 원본이 무엇을 참조하는지 본다.

풀이 보기

옛B에 참조가 없으므로 회수 가능하다. 실제 회수 완료 뒤A,B2,C 세 블록12KiB다. 삭제 호출 직후 즉시 공간 반환을 보장하지 않는다.

오해와 반례

스냅샷은 독립된 전체 백업이다.

같은 장치의 공유 블록 손상은 원본과 스냅샷 모두에 영향을 줄 수 있다. 백업의 저장 위치·권한·복원 가능성을 별도로 확인한다.

연습 1 · 값과 상태 예측

표에서 S0부터 지우고 청소한 뒤 S1도 지우고 청소했습니다. 둘째 단계에서 회수하는 블록과 용량은?

힌트 1

첫 단계에서는 B가 회수되었습니다.

힌트 2

현재 상태는 A, B2, C2입니다.

풀이와 답 확인

  1. S1이 마지막으로 잡고 있던 C의 참조를 제거합니다.

  2. C 한 블록을 회수하면 16−4=12 KiB입니다.

둘째 단계는 C의 4 KiB를 회수하여 12 KiB가 됩니다.

연습 2 · 오류 찾아 고치기

파일 X와 Y는 합계 100을 유지해야 합니다. X=60,Y=40에서 X만 70으로 바꾼 직후 응용을 멈추지 않고 스냅샷했습니다. Y=30은 아직 쓰지 않았습니다. 파일 구조는 정상입니다. 이 스냅샷을 응용 일관 상태라고 부른 설명을 고치세요.

힌트 1

힌트 2

파일시스템 구조가 정상인 것과 합계 불변식을 비교합니다.

풀이와 답 확인

  1. 스냅샷은 지정한 순간의 X=70,Y=40을 담습니다.

  2. 합계는 110으로 응용의 100 불변식을 어깁니다.

응용의 거래 완료 지점과 스냅샷 시점을 맞추는 별도 규약이 필요합니다.

같은 장치의 스냅샷 보관 외에 독립 보관과 복구 검증이 필요합니다. 여기서는 계획만 세웠고 복구를 실행하지 않았습니다.

SSD·비휘발성 메모리

저장장치에서4KiB를 바꿨는데 내부에서는 더 많이 쓸 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 논리 주소와 물리 주소

  • 캐시와 영속성

학습 목표

  • 페이지·erase block·FTL을 구분한다.

  • 쓰기 증폭과 영속 순서의 조건을 설명한다.

쓰기 증폭 두 개를 단순 평균하면 전체 증폭이 될까요?

기본의 페이지 쓰기 계산을 크기가 다른 두 작업으로 확장합니다. host write는 호스트가 요청한 데이터 바이트, internal write는 지정한 측정 범위에서 장치 내부가 쓴 바이트입니다. 여기서는 페이지 크기 4 KiB, 압축과 메타데이터 쓰기 없음으로 정하고 새 데이터와 GC의 유효 페이지 복사만 내부 쓰기로 셉니다.

GC는 사용 중인 페이지를 다른 곳으로 옮긴 뒤 매핑을 올바르게 바꾸고 지울 블록을 회수합니다. 논리 주소가 같아도 물리 페이지는 달라질 수 있습니다. TRIM은 불필요해진 범위를 알려 주는 역할이며 즉시 안전한 물리 삭제의 증거가 아닙니다. DAX는 CPU가 주소로 접근 가능한 저장장치의 직접 접근 조건을 다루며 일반 SSD 전체의 속성이나 자동 영속 거래를 뜻하지 않습니다. 실제 SSD·DAX·전원 차단은 실행하지 않았습니다.

먼저 확인할 개념

    기본의 FTL, GC, NAND 지우기 단위와 DAX 조건을 확인합니다.

플래시의 두 크기

NAND 플래시는 페이지 단위로 읽고 program하지만 이미 사용한 내용을 바꾸려면 더 큰 erase block의 제약을 고려한다. SSD는 새 위치에 쓰고 논리주소→물리주소 맵을 갱신하는 FTL로 이를 감춘다.

덮어쓴 옛 페이지는 쓰레기 공간이 된다. GC는 아직 유효한 페이지를 다른 곳으로 옮기고 블록을 지운다. 호스트 파일 블록, 가상메모리 페이지, 플래시 페이지가 항상 같은 크기라는 가정은 피한다.

성능 뒤의 추가 쓰기

쓰기 증폭은 같은 범위에서 센 내부 실제 쓰기 바이트를 호스트 쓰기 바이트로 나눈 비율이다. GC 복사와 메타데이터 등 포함 범위를 명시해야 비교할 수 있다. 장치 마모와 지연은 작업량·빈 공간·구현에 따라 다르다.

아래는 메타데이터 제외, 새 호스트 페이지 하나와 GC 복사 페이지 두 개를 세는 교육 예다. 실제 모델명이나 최신 장치 수명·성능으로 이 수치를 일반화하지 않는다.

CPU가 직접 보는 저장소도 계약이 필요하다

일부 비휘발성 메모리는 CPU가 주소로 접근하는 형태를 제공한다. 지원되는 DAX는 페이지 캐시의 불필요한 복사를 피하고 파일을 직접 매핑할 수 있다. 일반 SSD가 모두 이런 형태는 아니다.

저장 매체가 비휘발성이어도 CPU·장치 캐시의 완료와 영속 완료, 여러 필드의 원자적 갱신은 같은 말이 아니다. 정확한 지속 영역과 flush·순서·복구 프로토콜이 필요하다. 여기서는 명령어 실행이나 정전 시험을 하지 않는다.

    실제 PDF 물리 11·12쪽 전체의 유효 페이지 이동과 매핑 갱신 후 erase, 무효 페이지와 TRIM의 의미를 읽었다. 자체 쓰기 증폭은 정한 내부 측정 범위로 계산했다.

  • Linux kernel: Direct Access for files

    실제 공식 본문 앞부분의 CPU 직접 주소 접근·지원 장치와 파일시스템 조건, FS_XFLAG_DAX와 S_DAX 구분 및 기존 파일을 사용하는 모든 프로세스가 닫아야 적용되는 조건을 읽었다.

로그 순서 적용은 최종 2 / 2이며 역순은 1 / 1이다. 미완료 T2 제외 시 1 / 1이고 조기 로그 해제의 홈은 2 / 1이다. 스냅샷의 고유 블록 다섯 개는 20 KiB이며 S0 삭제 뒤 네 개 16 KiB, 모두 삭제 뒤 세 개 12 KiB다. S1 먼저 삭제 시 다른 참조가 모두 남아 20 KiB다. 자체 SSD 두 작업 합계는 내부 48 KiB / 호스트 40 KiB=1.2이고 메타데이터 한 페이지 추가 시 1.3이다. 전이의 복구 4 / 4, 용량 32 KiB, 쓰기 증폭 1.4를 손으로 추적했다.
