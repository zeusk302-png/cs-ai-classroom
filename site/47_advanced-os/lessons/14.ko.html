취소된 예약을 두 번 반환하면 가용량이 늘어날까요?

기본 예약 모형에 성공한 예약의 수명과 취소를 추가합니다. 전체 용량은 10이며 free와 고유 예약 ID별 active 수량을 저장합니다. 성공한 양수 예약은 free에서 수량을 빼고 active 기록을 원자적으로 만듭니다. 같은 ID를 다시 쓰는 요청은 충돌로 거부합니다. 취소는 active인 ID만 수량을 돌려주고 inactive로 바꾸는 하나의 원자 단계입니다. 예약 수량은 비음수 정수입니다. 충돌하지 않는 ID에 대한 수량 0의 요청은 예외적으로 성공하되 free와 ID 기록을 모두 유지하고 active 기록을 만들지 않습니다. 음수 입력과 free를 넘는 요청은 거부하며 ID 기록을 만들지 않습니다.

불변식은 free와 모든 active 수량의 합이 10이라는 것입니다. 실패한 예약과 반복 취소는 상태를 보존합니다. 같은 취소를 두 번 처리하거나 free 증가와 inactive 변경을 나누면 총량이 틀릴 수 있습니다. 이는 자체 정수 상태 설계이며 실제 kernel patch·lock·C 컴파일·장치·취소 실행은 수행하지 않았습니다.

증상에서 좁은 가설로

커널은 메모리·파일·장치·실행 시간을 함께 관리한다. 작은 변경도 다른 경로에 영향을 줄 수 있어 문제 조건과 기대 동작을 먼저 고정한다. 예를 들어 자원 요청 실패 뒤 남은 수량이 줄어드는 증상이 있다면, 실패 시 상태를 보존한다는 가설을 만들 수 있다. 모든 성능과 안정성을 동시에 개선한다는 말은 무엇으로 틀렸다고 판단할지 알기 어렵다.

기준 소스 버전·설정·입력·호출 경로·관찰 값을 적는다. 수정할 한 조건과 유지할 인터페이스를 구별한다. 여기서는 실제 Linux 함수가 아닌 자체 자원 예약 모형을 쓴다. 커널 패치 파일이나 실행 결과가 없는 상태를 구현 완료라고 부르지 않는다.

확인한 뒤 상태를 바꾸는 계약

자체 모형은 비음수 정수 free와 request를 받는다. request가 free 이하이면 성공하고 free−request가 된다. 초과하면 실패하고 free가 그대로다. 0 요청은 성공하며 상태가 그대로다. 음수는 잘못된 입력으로 거절한다. free가 비음수라는 불변식과 실패의 무부작용을 함께 검사한다.

먼저 빼고 나중에 음수 여부를 보는 잘못된 모형은 free=4, request=6에서 상태를 −2로 망가뜨릴 수 있다. 비교 후 성공 경로에서만 빼는 설계는 실패 상태 4를 유지한다. 이 정수 모형을 C로 옮길 때에는 정수 타입·범위·오버플로·반환 형식을 별도로 정의해야 한다. unsigned 값의 뺄셈을 음수 검사로 대체할 수는 없다.

직렬 정답에서 동시 계약까지

공유 free=5에서 요청 4와 3이 모두 초기 5를 보고 통과하면 총 예약 7이 가용량 5를 넘는다. 각각 마지막에 1과 2를 저장하는 잃어버린 갱신도 생길 수 있다. 비교와 감소 전체를 하나의 원자적 단계로 만드는 조건이 필요하다. 단지 마지막 저장만 보호하면 앞선 비교가 낡을 수 있다.

한 임계 구역에서 4를 먼저 처리하면 free=1이고 다음 3은 실패한다. 3을 먼저 처리하면 free=2이고 다음 4가 실패한다. 둘 중 어느 순서를 보장할지는 명세의 다른 선택이며 둘 다 용량 보존은 만족한다. 실제 커널에서는 잠금 문맥·수명·취소·할당 실패를 검토해야 한다. 이 종이 순서가 실제 잠금 구현의 안전성을 인증하지 않는다.

중간 과정을 따라가는 예제

자체 예약 모형에서 free=4이다. 요청 6이 실패하면 상태를 보존한다. 이어 요청 3, 요청 0, 요청 2를 직렬로 처리할 때 반환 상태를 구하라.

  1. 요청 6은 4보다 크므로 실패하고 free=4를 유지한다. 잘못된 선차감 모형의 −2와 다르다.

  2. 요청 3은 성공하고 free=1이다.

  3. 요청 0은 성공하고 free=1을 유지한다.

  4. 요청 2는 실패하고 free=1이다. 성공한 예약 합 3과 남은 1의 합은 초기 4다.

실패/성공/성공/실패, 상태는 4→1→1→1이다. 모두 자체 종이 계약이며 실제 커널 반환 코드는 아니다.

조건을 바꾸어 비교하기

예약 실패와 반복 취소

표에서 A와 B 예약 뒤 C가 2를 요청합니다. A 취소 뒤 다시 A 취소와 C의 2 예약을 순서대로 처리하세요.

  1. free=1에서 C의 2는 실패하고 free=1, active=9를 유지합니다.

  2. A 취소로 free=7, active B=3입니다.

  3. 반복 A 취소는 inactive여서 변화가 없습니다.

  4. C의 새 예약 2가 성공하면 free=5이고 active B=3, C=2입니다.

최종 free 5와 active 합 5가 용량 10을 보존합니다.

비교할 점

실패한 첫 C 요청에는 active ID 기록이 없다는 자체 계약입니다.

반환 뒤 표식만 늦게 쓴다

A=6, B=3 예약 뒤 free=1입니다. 취소 두 호출이 둘 다 A active를 보고 각각 free에 6을 더한 뒤 inactive로 바꿉니다.

  1. 첫 반환은 free를 7로 바꿉니다.

  2. 둘째 반환은 13으로 바꿉니다.

  3. 남은 B active=3과 합하면 16으로 용량 10을 어깁니다.

이 이력의 중복 반환 초과량은 6입니다.

비교할 점

free가 양수인지 보는 검사만으로 중복 반환을 찾지 못합니다.

종이와 본문으로 직접 해보기

초기 free=5에서 요청 3을 먼저, 4를 나중에 하나의 보호 구역에서 처리하라. 둘이 모두 초기 5를 확인해 성공하는 반례에서 예약 초과량도 구하라.

힌트 보기

보호 구역의 두 번째 비교는 첫 번째 감소 뒤 값을 읽는다.

풀이 보기

3은 성공해 free=2, 4는 실패해 2를 유지한다. 잘못된 두 성공의 예약은 7이므로 5보다 2 많다. 마지막 free 값만 양수라는 검사로 총 예약 보존을 증명할 수 없다.

오해와 반례

단일 호출 예제가 맞으면 동시 커널 변경도 맞다.

두 호출이 낡은 5를 함께 읽는 반례에서 각각 통과해도 총 7을 예약한다. 비교와 갱신의 원자성·오류·수명 조건을 별도로 검토한다.

연습 1 · 값과 상태 예측

초기 용량 10에서 A가 4를 예약하고 B가 5를 예약한 뒤 B를 취소합니다. 상태는?

힌트 1

힌트 2

  2. 취소 뒤 free=6이고 active A=4입니다.

연습 2 · 오류 찾아 고치기

초기 free=10에서 A 예약 6의 free 차감은 저장됐지만 active 기록 생성이 실패했습니다. free=4를 성공 상태로 보고했습니다. 빠진 원자 조건을 고치세요.

힌트 1

힌트 2

없어진 6을 추적합니다.

풀이와 답 확인

  1. 기록이 없으면 free 4와 active 0의 합은 4입니다.

  2. 실패 시 free 10을 복원하고 active를 만들지 않도록 명시한 원자 작업을 설계합니다.

이 반례는 6의 누수입니다. 실제 rollback 구현의 동시 안전성은 별도로 검토해야 합니다.

검사를 열 개 통과해도 한 가지 요구만 확인했을 수 있을까요?

자체 요구는 R1 성공 예약, R2 부족 실패의 상태 보존, R3 0 예약, R4 중복 취소의 보존, R5 두 동시 예약의 용량 보존, R6 성능 범위입니다. 검사 T1부터 T10까지는 모두 R1의 같은 입력을 반복합니다. 가상 표에서 열 개가 통과해도 요구 여섯 개 중 하나만 다루었습니다.

검사 개수·요구 연결·비교한 상태·실제 수행은 다른 축입니다. 반환값만 보는 검사는 누수를 놓칠 수 있고 전체 보존만 보는 검사는 잘못된 ID의 취소를 놓칠 수 있습니다. KUnit의 expectation과 준비 assertion, 빈 검사의 의미 및 kselftest 선택 범위를 확인하되 실제 도구는 실행하지 않았습니다.

기대 결과를 먼저 만드는 검사

단위 검사는 한 행동을 작은 입력으로 고립해 기대 상태와 비교한다. 준비→호출→비교의 순서를 명확히 한다. 앞 모형은 부족 요청 실패뿐 아니라 실패 뒤 상태 보존, 같은 수량 요청, 0, 음수, 두 호출 순서를 검사할 수 있다. 반환값 하나만 맞으면 충분하다고 정하면 상태 손상을 놓친다.

KUnit은 커널 내부 동작을 검사하는 도구이며 사용자 공간에서 보이는 동작을 검사하는 경로와 범위가 다르다. 아무 기대 조건도 없는 빈 검사도 통과할 수 있다는 원문 예시는 성공 표시의 한계를 보여 준다. assertion으로 중단해야 할 준비 실패와 여러 expectation을 계속 확인할 동작 실패를 구별한다. 여기서는 실제 KUnit 코드를 실행하지 않는다.

새 동작과 기존 약속을 함께 본다

기능 검사는 바꾼 행동이 계약을 지키는지 확인한다. 회귀 검사는 변경 전의 유효 동작이 유지되는지 확인한다. 충분한 요청·0 요청·실패 상태 보존은 새 경로와 기존 약속을 각각 검사하는 사례가 된다. 회귀 계획에는 영향받는 호출자·오류 경로·자원 정리와 동시 접근도 포함할 수 있다.

빌드 성공은 실행 동작의 정답이 아니다. 일부 대상만 빌드됐거나 일부 suite만 실행했다면 그 범위를 기록한다. kselftest의 대상 선택이나 실행 환경을 확인하지 않고 전체 커널 검증이라고 확대하지 않는다. 준비 실패·skip·시간 초과를 정상 통과로 합치지 않고 근거와 다음 확인을 적는다.

성능은 올바른 같은 일을 비교한다

정확성 조건을 먼저 맞추고 같은 입력·같은 작업량·같은 자원과 계측 범위로 기준과 변경을 비교한다. 벽시계 지연, 처리율, CPU 사용, 메모리 사용은 서로 다른 지표다. 더 적은 요청을 처리해 빨라진 결과는 같은 일을 빠르게 처리한 결과가 아니다. 반복 원자료와 예열·준비 포함 범위를 남긴다.

계획 여섯 개 중 네 개를 수행했다면 수행 범위는 4/6이다. 그 네 개 중 세 개 통과면 수행 검사 통과율은 3/4이다. 나머지 두 개는 실패로도 통과로도 바꾸지 않는다. 아래 표 전체는 가상 보고 사례이며 실제 커널·교육 실험 수행 수는 0이다. 작은 모형 계산을 실제 검사 로그로 꾸미지 않는다.

중간 과정을 따라가는 예제

가상 검사 계획 F1 정상 예약, F2 부족 실패의 상태 보존, F3 0 요청, F4 같은 수량 요청, R1 동시 순서, P1 반복 성능 총 여섯 개다. 가상 후보 기록은 F1 통과, F2 실패, F3 통과, F4 통과이고 R1/P1 미수행이다. 실제 실행이 아닌 표 읽기다. 수행 범위와 통과율 및 변경 승인 여부를 구하라.

  1. 가상 수행 표의 네 개는 F1–F4다. 수행 범위 4/6=2/3이다.

  2. 그중 통과는 F1/F3/F4 세 개이므로 수행 검사 통과율 3/4=75%다.

  3. F2 실패는 부족 요청 뒤 상태가 바뀌는 계약 위반이다. 속도와 무관하게 수정해야 한다.

  4. R1/P1은 가상 표에서도 미수행이다. 이 표를 실제 KUnit 로그·실측 결과로 부르지 않는다.

가상 수행 범위 약 66.67%, 수행 중 통과 75%이며 기능 실패와 두 미수행이 남는다. 실제 커널 검사는 수행되지 않았으므로 실제 통과율은 정의하지 않는다.

빠른 경우와 느린 경우를 하나의 평균으로 숨기지 않으려면?

자체 비교의 입력 P에서는 기준 10 ms, 변경 8 ms이고 입력 Q에서는 기준 20 ms, 변경 30 ms입니다. 둘은 모두 같은 계약의 성공 작업이고 각 지연이 고정됐다고 가정합니다. 작업 구성은 P 아홉 개와 Q 하나일 수도 있고 P 하나와 Q 아홉 개일 수도 있습니다.

수치 보고는 workload 구성과 실패 여부, 준비 포함 범위, 메모리 비용을 함께 둡니다. 변경이 빨라진 입력을 고르는 것과 실제 사용 분포에서 좋아지는 것은 다릅니다. Linux 지침의 비용 설명·검토와 테스트 구별을 읽었지만 커널 코드를 작성하거나 제출하거나 실제 성능을 측정하지 않았습니다.

독자가 다시 확인할 수 있는 보고

보고서는 문제를 재현하는 조건, 변경 가설, 기준과 변경의 차이, 검사 방법과 원자료를 연결한다. 소스 식별자·설정·도구 버전·자원·입력·반복 수·시간 범위를 적어 다른 사람이 같은 비교를 구성할 수 있게 한다. 수학 모형·예상 결과·실측 결과를 다른 상태로 표시한다.

성능 숫자는 무엇을 유지하고 무엇을 바꾸었는지 없으면 해석하기 어렵다. 불리한 입력이나 실패 표본도 남긴다. Linux 변경 설명 지침도 성능·메모리 등 이득을 수치로 뒷받침하면서 CPU·메모리·읽기 쉬움·서로 다른 workload의 비용을 설명하도록 한다. 아래 보고는 실제 커널 연구 성과가 아닌 자체 가상 자료 연습이다.

부분 개선과 입력별 비용

중앙값 시간 비율 T기준/T변경을 speedup으로 정의한다. 시간이 20에서 16으로 줄면 speedup 1.25, 시간 감소 20%다. 속도 향상 25%와 시간 감소 20%는 분모가 다른 수치다. 평균·중앙값·꼬리 지연은 다른 질문을 답하므로 하나를 다른 것처럼 보고하지 않는다.

전체 100 ms 중 40 ms 부분만 1.25배 개선하면 그 부분은 32 ms이고 나머지 60 ms가 남아 총 92 ms다. 전체 speedup은 100/92이다. 다른 입력 B의 시간이 10에서 12 ms로 늘면 20% 느려진다. A의 이득으로 B의 비용을 지워 모든 입력에서 개선됐다고 주장하지 않는다.

검토와 실행은 서로 대체하지 않는다

설계 검토는 가정과 논리를 확인하고 실행 검사는 특정 환경의 실제 행동을 확인한다. 공식 개발 지침의 Reviewed-by와 Tested-by도 다른 근거를 담는다. 실제로 수행하지 않은 커널·장치·학생 실험이나 타인의 검토를 자기 보고의 완료 기록으로 만들지 않는다.

잔여 한계에는 동시 경로, 메모리 부족, 다양한 아키텍처, 장시간 부하, 하드웨어 의존 동작처럼 아직 확인하지 못한 조건을 구체적으로 적는다. 가상 표로 가설을 좁힌 것과 실제 구현이 채택 가능한 것의 차이를 유지한다. 다음 실험은 남은 한계를 반증할 입력과 실패 조건으로 정하고, 결과가 없으면 미수행으로 둔다.

중간 과정을 따라가는 예제

자체 가상 입력 A의 기준 시간은 [20,22,18,21,19] ms, 변경은 [16,17,15,18,14] ms다. 별도 입력 B는 10→12 ms다. 전체 100 ms 중 40 ms 부분만 A의 중앙값 비율로 개선된다고 가정한다. 수치와 보고 결론을 구하라.

  1. A 기준 중앙값은 20, 변경 중앙값은 16이다. 비율 20/16=5/4=1.25다.

  2. A 시간 감소는 (20−16)/20=20%다. B 시간 증가는 (12−10)/10=20%다.

  3. 전체의 개선 부분은 40/(5/4)=32 ms이고 나머지 60과 합해 92 ms다.

  4. 전체 speedup은 100/92=25/23≈1.087, 시간 감소는 8%다. 실제 커널 측정이 아니라 같은 조건을 가정한 합성 산술이다.

가상 A는 중앙값 기준 1.25배지만 B는 시간 20% 증가다. 별도 전체 계산은 92 ms·약 1.087배다. 모든 입력 또는 실제 커널에서 개선됐다는 결론은 내리지 않는다.

용량 12에서 A가 5를 예약하고 B가 4를 예약한 뒤 A를 취소하고 같은 A 취소를 반복합니다. 원자적 수명 계약의 free와 active를 구하세요. 요구 여덟 개 중 두 요구만 같은 입력으로 반복한 가상 검사 열두 개가 모두 통과했습니다. 수행 통과율과 요구 대응 비율을 나누세요. 별도 P 지연은 기준 6 ms와 변경 4 ms, Q는 기준 10 ms와 변경 14 ms입니다. P 세 개와 Q 하나의 순차 전체와 시간 감소율을 구하고 실제 커널 실행 여부를 적으세요.

힌트 3

풀이와 답 확인

  1. 예약 뒤 free=3이고 active 총량=9입니다.

  2. A 취소 뒤 free=8이고 B active=4입니다. 반복 취소는 이 상태를 유지합니다.

  3. 가상 수행 통과율은 12/12=100%이고 요구 대응 비율은 2/8=25%입니다.

  4. 기준 전체는 3×6+10=28 ms이고 변경은 3×4+14=26 ms입니다.

  5. 감소율은 2/28=1/14로 약 7.14%입니다.

  6. 자체 모형과 가상 표의 손판정이며 실제 커널·도구·장치·학생 실행은 미수행입니다.

free 8과 active 4로 용량 12를 보존합니다. 가상 수행 통과 100%와 요구 대응 25%는 다르며 전체 시간은 28 ms에서 26 ms로 약 7.14% 감소합니다.
