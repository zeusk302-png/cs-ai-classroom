소단원 7.1

VMM·가상 CPU·I/O

가상 CPU 네 개를 만들면 물리 CPU도 네 개가 생길까?

준비 개념과 학습 목표

준비 개념

  • 운영체제와 프로세스

  • CPU 시간

학습 목표

  • 가상 하드웨어와 물리 자원 배정을 구별한다.

  • 가상 CPU 실행과 I/O 경계를 설명한다.

VMM은 가상 기계를 관리한다

가상 머신 모니터 VMM은 게스트 운영체제가 보는 CPU·메모리·장치를 물리 자원과 연결한다. 게스트는 자신의 커널을 실행하지만 실제 자원 사용은 가상화 계층과 호스트의 관리 영향을 받는다.

가상 CPU는 실행 상태를 가진 논리적 실행 단위다. 개수만큼 물리 코어가 독점 배정된다고 가정하면 안 된다. 여러 가상 CPU가 호스트에서 번갈아 실행될 수 있다.

모든 명령을 일일이 흉내 내지는 않는다

하드웨어 지원 가상화에서는 게스트 코드가 CPU에서 실행되고 처리 경계에서 VMM으로 돌아올 수 있다. KVM_RUN은 가상 CPU를 실행하며 반환된 이유에 따라 필요한 처리를 이어 간다.

여기서는 호스트 사용자 공간의 장치 처리 모델을 예로 든다. 실제 가상화 구조·장치 방식에 따라 경로가 달라지므로 모든 명령이 매번 사용자 공간으로 넘어온다고 설명하지 않는다.

I/O는 실행 경계를 만든다

KVM_EXIT_IO와 KVM_EXIT_MMIO는 KVM이 직접 처리하지 않은 장치 접근을 사용자 공간이 처리할 상황을 전달한다. 처리 값과 상태를 반영하고 다시 진입하는 흐름을 연결해서 보아야 한다.

경계 이동을 줄이면 비용을 줄일 여지가 있지만 정확한 장치 의미를 보존해야 한다. 아래 이동 비용은 가정값이며 실제 장치 속도나 특정 하드웨어의 측정값이 아니다.

중간 과정을 따라가는 예제

서로 독립이고 계속 실행 가능한 가상 CPU 4 개가 각각 CPU 작업 10 ms를 수행한다. 물리 코어는 2 개이고 다른 작업·전환 비용은 없다. 별도로 경계 이동 1000 회가 회당 2 μs면 추가 비용은?

  1. 필요한 총 CPU 시간은 4×10=40 ms다.

  2. 두 코어가 균등하게 일을 나누면 이상적 벽시계 시간은 40/2=20 ms다. 네 물리 코어를 실제 확보했을 때의 10 ms와 다르다.

  3. 경계 비용은 1000×2=2000 μs=2 ms다. 횟수를 200 으로 줄이고 다른 비용을 유지하면 0.4 ms이며 감소량은 1.6 ms다.

이상적 작업 완료는 20 ms다. 별도 경계 비용 모델은 2 ms이며 경계 감소만의 절약은 1.6 ms다. 두 예를 실제 측정처럼 합산하지 않는다.

종이와 본문으로 직접 해보기

같은 네 작업을 물리 코어 하나에서 실행하면 최소 벽시계 시간을 계산하자.

힌트 보기

필요한 CPU 시간 총합은 바뀌지 않는다.

풀이 보기

40/1=40 ms다. 병렬 실행 자원이 줄었기 때문이다.

오해와 반례

가상 CPU 수를 두 배로 늘리면 모든 작업 시간이 절반이 된다.

물리 코어 2 개에 이미 네 독립 작업이 있으면 가상 CPU 수만 늘려도 총 40 ms의 CPU 작업을 2 개 코어가 처리해야 한다. 직렬 의존성이나 경쟁이 있으면 더 느릴 수도 있다.

소단원 7.2

컨테이너와 자원 통제

보이는 프로세스를 나누는 것과 사용 가능한 메모리를 제한하는 것은 같을까?

준비 개념과 학습 목표

준비 개념

  • 프로세스

  • 커널

  • 메모리 단위

학습 목표

  • namespace와 cgroup의 역할을 구별한다.

  • CPU 할당량과 메모리 제한의 조건을 계산한다.

이름 공간은 보는 범위를 나눈다

컨테이너 프로세스들은 호스트 커널의 기능으로 격리된 관점을 얻는다. PID namespace는 프로세스 번호의 관점을, mount namespace는 마운트 목록의 관점을 나누는 예다.

다른 PID namespace 안에 각각 PID 1 이 있다고 해서 호스트에서 같은 프로세스라는 뜻은 아니다. 또한 보이는 이름의 분리만으로 CPU 시간이나 메모리 사용량 제한이 자동 완성되는 것은 아니다.

cgroup은 사용량과 한계를 관리한다

cgroup v2 는 프로세스 집단의 자원 사용량과 통제를 제공한다. cpu.max의 quota와 period는 적용 대상 스케줄링 클래스에서 일정 기간 허용되는 집단의 CPU 시간을 나타낸다.

50000 100000 은 100000 μs 기간에 50000 μs의 총 CPU 시간 한도다. 평균적으로 0.5 CPU 상당이지만 어느 순간에도 정확히 코어 절반만 쓴다는 뜻이나 지연 시간 보장은 아니다.

메모리 압력과 최종 한계를 구분한다

memory.high는 초과 시 회수와 억제를 유도하는 경계이며 그 자체로 OOM을 일으키는 최종 제한은 아니다. memory.max는 회수 후 한계를 지키지 못할 때 OOM 등 처리가 발생하는 상한이다.

실제 할당 종류와 회수 가능성에 따라 결과가 달라지고 일시적 초과도 가능하다. 상한을 여러 컨테이너에 설정했다고 그만큼의 메모리가 미리 예약되는 것도 아니다.

중간 과정을 따라가는 예제

cpu.max=50000 100000 인 집단에서 두 스레드가 서로 다른 코어에서 각각 CPU 시간 25 ms를 쓴다. 기간 시작에 이전 사용은 0 이고 적용 조건을 만족한다. 별도 호스트는 512 MiB 중 128 MiB를 남기고 컨테이너별 최대 64 MiB의 동시 최댓값을 계획한다.

  1. 집단 소비량은 25+25=50 ms다. 두 스레드가 동시에 실행하면 벽시계 25 ms 동안 기간의 quota를 모두 쓸 수 있다.

  2. 추가로 실행 가능한 작업이 있어도 이 quota가 소진된 뒤 기간 갱신까지 제한될 수 있다. 이를 항상 50 ms 동안 실행한 것으로 읽지 않는다.

  3. 계획 가능한 메모리는 512−128=384 MiB다. 384/64=6 이므로 이 단순 최댓값 예산으로는 여섯 집단까지다. 실제 추가 비용과 상위 cgroup 한계는 별도 확인한다.

두 스레드의 합계로 quota 50 ms가 소진된다. 단순 메모리 예산은 여섯 컨테이너이며 실제 배치 승인이나 예약 보장은 아니다.

종이와 본문으로 직접 해보기

같은 기간에서 스레드 하나가 CPU 시간 30 ms를 썼다면 남은 quota는?

힌트 보기

quota는 벽시계 시간이 아니라 집단의 CPU 시간이다.

풀이 보기

50−30=20 ms다. 다른 스레드의 소비도 더해 한도를 계산한다.

오해와 반례

PID 이름 공간을 나누면 메모리 상한도 자동으로 생긴다.

이름 공간의 관점 분리와 cgroup 사용량 통제는 서로 다른 기능이다. namespace만 있는 예에는 64 MiB 같은 상한이 주어지지 않는다.

한 단계 더

PID 관점·CPU quota·메모리 상한을 서로 다른 세 칸에 적고 필요한 통제 기능을 연결해 보자.

소단원 7.3

격리·성능·공유의 균형

평균 응답 시간이 같으면 이웃의 간섭도 같다고 할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 가상 머신

  • 컨테이너

  • 평균

학습 목표

  • 격리 경계와 공유 자원을 함께 평가한다.

  • 평균과 꼬리 지연을 비교하고 최댓값 예산을 세운다.

격리 경계는 위협에 맞춘다

VM은 별도 게스트 커널을 두고 컨테이너는 호스트 커널의 격리 기능을 이용한다. 어느 구성이 적절한지는 신뢰하지 않는 코드가 무엇에 접근할 수 있는지와 관리 경계를 함께 보고 결정한다.

컨테이너의 권한과 호스트 디렉터리 공유는 중요한 조건이다. 호스트 루트를 쓰기 가능하게 공유한 구성을 이름 공간만 보고 안전하다고 판정하면 안 된다. VM에도 위험한 장치·파일 공유 설정이 있을 수 있다.

공유는 비용을 줄이지만 간섭을 남긴다

CPU·캐시·메모리·저장 장치를 공유하면 자원을 효율적으로 쓸 수 있다. 동시에 다른 작업의 부하가 응답을 흔드는 noisy neighbor 문제를 고려해야 한다.

CPU quota 하나가 모든 I/O와 네트워크 지연을 제한하지는 않는다. 처리량·평균·상위 백분위 응답 시간을 나누어 관측해야 하며 특정 구성이 늘 빠르거나 늘 안전하다는 순위는 성립하지 않는다.

평균과 최대 수요를 함께 본다

백분위는 정렬한 응답 중 일정 위치의 값이다. 여기서는 표본 100 개의 p99 를 nearest-rank 규칙에 따라 99 번째 값으로 정의한다. 규칙을 명시해야 다른 도구와 비교할 수 있다.

메모리를 과다 약속하면 평소에는 여유가 있어도 동시에 커지는 순간 부족할 수 있다. 평균 사용량에 맞춘 계획과 모두의 최대치를 보장하는 계획을 구별한다.

중간 과정을 따라가는 예제

응답 A는 98 개가 1 ms, 2 개가 51 ms다. B는 100 개 모두 2 ms다. 각각 평균과 위 정의의 p99 를 구하자. 별도 호스트는 4 GiB 중 1 GiB를 호스트에 남기고 네 작업이 평소 각 0.5 GiB, 최대 각 1.5 GiB를 요구한다.

  1. A의 합은 98+102=200 ms로 평균 2 ms다. 정렬한 99 번째는 51 ms다.

  2. B의 평균과 p99 는 모두 2 ms다. 같은 평균이 같은 꼬리 지연을 뜻하지 않는다.

  3. 게스트에 계획 가능한 양은 4−1=3 GiB다. 평소 합계 4×0.5=2 GiB는 들어가지만 동시에 최대가 되면 4×1.5=6 GiB로 3 GiB를 초과한다.

평균은 같지만 p99 는 A 51 ms/B 2 ms다. 평소 메모리는 들어가도 전체 최대 수요를 보장할 수 없는 예산이다.

종이와 본문으로 직접 해보기

A에서 느린 응답이 하나만 101 ms이고 나머지 99 개가 1 ms라면 평균과 p99 는?

힌트 보기

99 번째 표본과 100 번째 표본을 구별한다.

풀이 보기

평균=(99+101)/100=2 ms, p99 는 1 ms다. p99 만 보면 가장 느린 한 건은 보이지 않는다.

오해와 반례

컨테이너면 항상 안전하고 VM이면 항상 느리다.

권한·공유 장치·호스트 커널·자원 경쟁과 실행 경로에 따라 달라진다. 이 단원은 측정 없이 제품별 성능 순위나 침입 불가능성을 주장하지 않는다.

자기점검

A와 B의 평균만으로 선택할 수 있나?

답과 이유 보기
