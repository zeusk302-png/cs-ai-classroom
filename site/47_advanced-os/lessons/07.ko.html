소단원 7.1

VMM·가상 CPU·I/O

가상 CPU 네 개를 만들면 물리 CPU도 네 개가 생길까?

준비 개념과 학습 목표

준비 개념

  • 운영체제와 프로세스

  • CPU 시간

학습 목표

  • 가상 하드웨어와 물리 자원 배정을 구별한다.

  • 가상 CPU 실행과 I/O 경계를 설명한다.

CPU 작업 총합을 코어 수로 나누면 언제나 실제 완료 시간이 나오나요?

기본 네 vCPU의 같은 길이 작업을 길이가 다른 세 작업으로 바꿉니다. vCPU는 가상 CPU이고 각각 실행 가능한 논리적 상태이지 전용 물리 코어의 증거가 아닙니다. 새 작업 A는 CPU 시간 12 ms, B는 1 ms, C는 1 ms가 필요합니다. 세 작업은 서로 독립이며 모두 시각 0 ms에 준비됩니다. 물리 코어는 둘이고 추가 비용은 0이며, 한 작업은 동시에 코어 둘에서 실행되지 않습니다.

KVM 장치 예제는 사용자 공간에 반환된 요청과 완료된 게스트 상태를 구분합니다. 요청 데이터가 보였거나 값을 채웠다는 것만으로 이 I/O 연산의 완료를 판정하지 않습니다. 실제 VM·장치·live migration을 실행하지 않았고 아래 일정 및 가상 경계 비용은 종이 입력입니다.

  • 컨테이너와 자원 통제

VMM은 가상 기계를 관리한다

가상 머신 모니터 VMM은 게스트 운영체제가 보는 CPU·메모리·장치를 물리 자원과 연결한다. 게스트는 자신의 커널을 실행하지만 실제 자원 사용은 가상화 계층과 호스트의 관리 영향을 받는다.

가상 CPU는 실행 상태를 가진 논리적 실행 단위다. 개수만큼 물리 코어가 독점 배정된다고 가정하면 안 된다. 여러 가상 CPU가 호스트에서 번갈아 실행될 수 있다.

모든 명령을 일일이 흉내 내지는 않는다

하드웨어 지원 가상화에서는 게스트 코드가 CPU에서 실행되고 처리 경계에서 VMM으로 돌아올 수 있다. KVM_RUN은 가상 CPU를 실행하며 반환된 이유에 따라 필요한 처리를 이어 간다.

여기서는 호스트 사용자 공간의 장치 처리 모델을 예로 든다. 실제 가상화 구조·장치 방식에 따라 경로가 달라지므로 모든 명령이 매번 사용자 공간으로 넘어온다고 설명하지 않는다.

I/O는 실행 경계를 만든다

KVM_EXIT_IO와 KVM_EXIT_MMIO는 KVM이 직접 처리하지 않은 장치 접근을 사용자 공간이 처리할 상황을 전달한다. 처리 값과 상태를 반영하고 다시 진입하는 흐름을 연결해서 보아야 한다.

경계 이동을 줄이면 비용을 줄일 여지가 있지만 정확한 장치 의미를 보존해야 한다. 아래 이동 비용은 가정값이며 실제 장치 속도나 특정 하드웨어의 측정값이 아니다.

코어실행 구간코어 CPU 시간

총 CPU 시간은 14 ms라 총량 하한은 7 ms입니다. 하지만 A 하나가 12 ms 필요해 완료 하한도 12 ms이고 표가 이를 달성합니다.

중간 과정을 따라가는 예제

서로 독립이고 계속 실행 가능한 가상 CPU 4 개가 각각 CPU 작업 10 ms를 수행한다. 물리 코어는 2 개이고 다른 작업·전환 비용은 없다. 별도로 경계 이동 1000 회가 회당 2 μs면 추가 비용은?

  1. 필요한 총 CPU 시간은 4×10=40 ms다.

  2. 두 코어가 균등하게 일을 나누면 이상적 벽시계 시간은 40/2=20 ms다. 네 물리 코어를 실제 확보했을 때의 10 ms와 다르다.

  3. 경계 비용은 1000×2=2000 μs=2 ms다. 횟수를 200 으로 줄이고 다른 비용을 유지하면 0.4 ms이며 감소량은 1.6 ms다.

이상적 작업 완료는 20 ms다. 별도 경계 비용 모델은 2 ms이며 경계 감소만의 절약은 1.6 ms다. 두 예를 실제 측정처럼 합산하지 않는다.

조건을 바꾸어 비교하기

총량 하한과 긴 작업 하한

표의 최소 전체 완료 시간과 전체 CPU 시간을 쓰세요. A를 같은 vCPU 상태로 두 코어에서 동시에 실행시켜 7 ms에 끝낸다는 안도 평가하세요.

  1. 총량 하한은 (12+1+1)/2=7 ms입니다.

  2. 한 작업이 동시에 코어 둘을 쓸 수 없으므로 A의 12 ms가 하한입니다.

  3. 표는 12 ms에 끝나 두 하한 중 큰 값을 달성합니다.

전체 CPU 14 ms, 최소 벽시계 완료 12 ms입니다.

비교할 점

이 모형에서 한 작업의 순차 실행 상태를 두 코어에서 동시에 진행시키는 안은 조건을 위반합니다.

경계 고정비와 사건별 비용

별도 모형에서 독립적으로 버퍼링 가능한 기록 1000개를 처리합니다. 사용자 처리 경계 한 번의 고정비는 3 μs, 기록당 비용은 1 μs입니다. 개별 기록마다 처리하는 1000경계와 기록 열 개씩 묶는 100경계를 비교하세요. 배치가 순서·오류 의미를 그대로 보존한다고 지정하고 대기 시간은 별도로 봅니다.

  1. 개별은 1000×3+1000×1=4000 μs입니다.

  2. 배치는 100×3+1000×1=1300 μs입니다.

  3. 기록당 일은 그대로이며 경계 고정비 2700 μs를 줄입니다.

4000 μs 대 1300 μs, 가상 비용 절약 2700 μs입니다.

비교할 점

모든 실제 KVM I/O를 임의로 배치할 수 있다는 뜻이 아닙니다. 장치 의미와 배치 대기도 별도 검토합니다.

종이와 본문으로 직접 해보기

같은 네 작업을 물리 코어 하나에서 실행하면 최소 벽시계 시간을 계산하자.

힌트 보기

필요한 CPU 시간 총합은 바뀌지 않는다.

풀이 보기

40/1=40 ms다. 병렬 실행 자원이 줄었기 때문이다.

오해와 반례

가상 CPU 수를 두 배로 늘리면 모든 작업 시간이 절반이 된다.

물리 코어 2 개에 이미 네 독립 작업이 있으면 가상 CPU 수만 늘려도 총 40 ms의 CPU 작업을 2 개 코어가 처리해야 한다. 직렬 의존성이나 경쟁이 있으면 더 느릴 수도 있다.

연습 1 · 값과 상태 예측

A/B/C 길이를 모두 4 ms로 바꿉니다. 세 작업은 나눌 수 없고 두 코어에서 작업당 한 번 연속 실행하며 추가 비용은 0입니다. 최소 완료 시간과 총 CPU 시간은?

힌트 1

두 코어 중 하나는 작업 두 개를 맡습니다.

힌트 2

작업 중간 분할은 허용하지 않았습니다.

풀이와 답 확인

  1. 총 CPU 시간은 12 ms입니다.

  2. 한 코어에 4+4=8 ms, 다른 코어에 4 ms인 일정이 가능합니다.

  3. 어느 코어든 두 작업을 맡으므로 8 ms가 필요합니다.

최소 완료는 8 ms, 총 CPU 시간은 12 ms입니다.

흔한 오답에서 다시 생각하기

총합 12를 2로 나눈 6 ms가 항상 달성된다.

총량 하한 6 ms와 나눌 수 없는 작업 조건의 달성 가능한 일정은 다릅니다.

연습 2 · 오류 찾아 고치기

KVM_EXIT_MMIO로 read 요청이 왔고 userspace가 data를 채운 직후 visible state만 저장해 migration합니다. 아직 KVM_RUN에 재진입하지 않았습니다. 완료 판단을 고치세요.

힌트 1

공식 규약은 이 연산의 완료에 재진입이 필요하다고 합니다.

힌트 2

미완료 내부 상태는 userspace에 보이는 상태에 보존되지 않습니다.

풀이와 답 확인

  1. 요청 처리값을 채우는 단계와 게스트 연산 완료를 구분합니다.

  2. live migration 전에 KVM_RUN에 재진입하여 pending operation을 완료해야 합니다.

값을 채운 직후만으로 일관된 완료 상태 저장을 주장하지 않습니다.

흔한 오답에서 다시 생각하기

요청값만 복사했으니 게스트 명령도 이미 완료다.

사용자 공간 장치 처리와 kernel 재진입 완료 경계가 다릅니다.

연습 3 · 직접 만들어 보기

KVM_EXIT_IO_IN에서 size=2, count=3, data_offset=64입니다. kvm_run 매핑 시작 주소를 기준으로 응답의 상대 구간 길이와 위치를 쓰세요. 유효한 매핑 공간이 충분하다고 가정합니다.

힌트 1

데이터는 원소 사이 간격 없이 이어진 packed array입니다.

힌트 2

data_offset은 절대주소가 아니라 kvm_run 시작으로부터의 offset입니다.

풀이와 답 확인

  1. 총 응답 길이는 2×3=6바이트입니다.

  2. 매핑 시작으로부터 64에서 70 미만 구간에 넣습니다.

  3. 이후 KVM_RUN 재진입으로 해당 연산을 완료합니다.

상대 구간은 [64,70), 길이는 6바이트입니다. 실제 절대주소 64가 아닙니다.

흔한 오답에서 다시 생각하기

count가 3이므로 3바이트를 절대주소 64에 쓴다.

각 원소의 size와 배열의 count를 곱하고 매핑 기준 상대주소를 구분합니다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

1000개 기록의 배치 크기를 20으로 바꾸고 같은 가상 비용을 유지합니다. 전체 경계 수와 비용은? 별도 한 배치의 첫 기록은 0 ms, 마지막 기록은 19 ms에 도착하며 전부 기다린 뒤 처리합니다. 첫 기록의 처리 전 대기는?

힌트 1

1000개 기록은 정확히 20으로 나뉩니다.

힌트 2

도착 대기 시간은 처리 비용과 다릅니다.

풀이와 답 확인

  1. 경계는 50번입니다. 고정비 150 μs와 기록 비용 1000 μs를 더합니다.

  2. 별도 한 배치의 첫 기록은 마지막 도착까지 19 ms 기다립니다.

전체 비용은 1150 μs, 별도 한 배치의 첫 기록 대기는 19 ms입니다.

흔한 오답에서 다시 생각하기

총비용이 작아졌으니 첫 기록의 응답 시간도 항상 줄었다.

CPU 비용 감소와 배치 도착 대기는 서로 다른 수치입니다.

내 말로 설명하기

총량을 코어 수로 나눈 값은 무엇인가요?

설명 기준 확인

장치 요청을 받았으면 게스트 상태가 완료됐나요?

설명 기준 확인

CPU quota 60 ms를 두 코어에서 쓰면 벽시계도 60 ms일까요?

기본 quota를 60000 100000으로 바꾸고 이상적인 두 스레드 시간표를 그립니다. CPU 시간은 코어들이 일한 시간의 합입니다. 여기서는 정확한 100 ms 기간 경계, burst=0, 적용되는 스케줄링 범위, 다른 상위 제한과 경쟁 없음, 추가 비용 0, 이용 가능한 두 코어를 정합니다. 실제 cgroup의 정밀한 제한 시각을 보장하는 설명은 아닙니다.

namespace는 관점을 나누고 cgroup은 사용량을 통제합니다. 별도 메모리 예산의 호스트용 128 MiB와 작업 최댓값은 계획 수치입니다. memory.high와 memory.max 값만으로 지정량이 실제로 예약됐다거나 어떤 프로세스가 곧바로 종료된다고 기록하지 않습니다.

먼저 확인할 개념
  • 컨테이너와 자원 통제

    quota의 집단 CPU 시간과 메모리 압력·상한을 구분합니다.

  • 격리·성능·공유의 균형

    최댓값 예산과 정책을 실제 격리 완료 증거로 바꾸지 않습니다.

이름 공간은 보는 범위를 나눈다

컨테이너 프로세스들은 호스트 커널의 기능으로 격리된 관점을 얻는다. PID namespace는 프로세스 번호의 관점을, mount namespace는 마운트 목록의 관점을 나누는 예다.

다른 PID namespace 안에 각각 PID 1 이 있다고 해서 호스트에서 같은 프로세스라는 뜻은 아니다. 또한 보이는 이름의 분리만으로 CPU 시간이나 메모리 사용량 제한이 자동 완성되는 것은 아니다.

cgroup은 사용량과 한계를 관리한다

cgroup v2 는 프로세스 집단의 자원 사용량과 통제를 제공한다. cpu.max의 quota와 period는 적용 대상 스케줄링 클래스에서 일정 기간 허용되는 집단의 CPU 시간을 나타낸다.

50000 100000 은 100000 μs 기간에 50000 μs의 총 CPU 시간 한도다. 평균적으로 0.5 CPU 상당이지만 어느 순간에도 정확히 코어 절반만 쓴다는 뜻이나 지연 시간 보장은 아니다.

메모리 압력과 최종 한계를 구분한다

memory.high는 초과 시 회수와 억제를 유도하는 경계이며 그 자체로 OOM을 일으키는 최종 제한은 아니다. memory.max는 회수 후 한계를 지키지 못할 때 OOM 등 처리가 발생하는 상한이다.

실제 할당 종류와 회수 가능성에 따라 결과가 달라지고 일시적 초과도 가능하다. 상한을 여러 컨테이너에 설정했다고 그만큼의 메모리가 미리 예약되는 것도 아니다.

중간 과정을 따라가는 예제

cpu.max=50000 100000 인 집단에서 두 스레드가 서로 다른 코어에서 각각 CPU 시간 25 ms를 쓴다. 기간 시작에 이전 사용은 0 이고 적용 조건을 만족한다. 별도 호스트는 512 MiB 중 128 MiB를 남기고 컨테이너별 최대 64 MiB의 동시 최댓값을 계획한다.

  1. 집단 소비량은 25+25=50 ms다. 두 스레드가 동시에 실행하면 벽시계 25 ms 동안 기간의 quota를 모두 쓸 수 있다.

  2. 추가로 실행 가능한 작업이 있어도 이 quota가 소진된 뒤 기간 갱신까지 제한될 수 있다. 이를 항상 50 ms 동안 실행한 것으로 읽지 않는다.

  3. 계획 가능한 메모리는 512−128=384 MiB다. 384/64=6 이므로 이 단순 최댓값 예산으로는 여섯 집단까지다. 실제 추가 비용과 상위 cgroup 한계는 별도 확인한다.

두 스레드의 합계로 quota 50 ms가 소진된다. 단순 메모리 예산은 여섯 컨테이너이며 실제 배치 승인이나 예약 보장은 아니다.

조건을 바꾸어 비교하기

한 스레드와 두 스레드의 같은 총량

두 스레드는 각각 40 ms를 표대로 처리합니다. 별도 한 스레드가 80 ms를 같은 기간 quota로 처리하면 최소 벽시계 완료는? 동일한 모형 조건입니다.

  1. 두 스레드는 첫 30 ms에 합계 60 ms, 다음 기간의 10 ms에 합계 20 ms를 소비합니다.

  2. 한 스레드는 0–60 ms에 60 ms를 소비하고 60–100 ms에 대기하며 100–120 ms에 20 ms를 소비합니다.

  3. 총 CPU 소비는 모두 80 ms지만 기간 안의 소비 속도가 다릅니다.

두 스레드의 완료는 110 ms, 한 스레드는 120 ms입니다.

비교할 점

평균 0.6 CPU 상당이라는 값만으로 순간 실행 모양이나 최악 지연을 확정하지 않습니다.

최댓값을 합한 계획

호스트 전체 512 MiB에서 호스트용 128 MiB를 남깁니다. A/B/C는 각각 memory.max=128 MiB이며 이를 사용 가능한 최댓값으로 계획합니다. 실제 예약은 없고 추가 비용은 제외합니다. 셋의 동시 최댓값과 D의 64 MiB를 추가한 경우를 구하세요.

  1. 작업 계획 예산은 512−128=384 MiB입니다.

  2. A/B/C 최댓값 합계도 384 MiB로 예산과 같습니다.

  3. D를 추가하면 448 MiB로 64 MiB 초과합니다.

셋만의 가상 최댓값 예산은 맞고 D 추가는 초과합니다.

비교할 점

각 max 설정이 이 최댓값만큼 공간을 미리 확보했다는 뜻은 아닙니다.

준비 개념과 학습 목표

준비 개념

  • 가상 머신

  • 컨테이너

학습 목표

  • 격리 경계와 공유 자원을 함께 평가한다.

  • 평균과 꼬리 지연을 비교하고 최댓값 예산을 세운다.

전체 성공률이 99%여도 작은 수강 집단이 좋은 경험을 했을까요?

기본 평균·꼬리 비교를 집단별 관측으로 확장합니다. 전체 1000건 중 집단 A는 990건, B는 10건입니다. 성공은 정확하고 주어진 마감 안에 응답한 경우로 정하며 실패와 지연은 명시한 조건으로만 셉니다. 실제 학생 응답 표본이 아닌 자체 자료입니다.

격리는 설정된 공유 경로까지 보아야 합니다. 아래 간단한 권한 모형은 명시한 파일 접근만 판정하며 전체 커널 취약점·사이드채널·모든 장치 공유의 안전 증명이 아닙니다. VM이든 컨테이너든 기능상 허용한 공유를 선택한 보호 목표와 비교합니다.

먼저 확인할 개념
  • 격리·성능·공유의 균형

    공유 권한과 평균·꼬리 수치의 평가 범위를 나눕니다.

  • 컨테이너와 자원 통제

    자원 사용량 제한이 파일 접근 권한을 대신하지 않음을 확인합니다.

격리 경계는 위협에 맞춘다

VM은 별도 게스트 커널을 두고 컨테이너는 호스트 커널의 격리 기능을 이용한다. 어느 구성이 적절한지는 신뢰하지 않는 코드가 무엇에 접근할 수 있는지와 관리 경계를 함께 보고 결정한다.

컨테이너의 권한과 호스트 디렉터리 공유는 중요한 조건이다. 호스트 루트를 쓰기 가능하게 공유한 구성을 이름 공간만 보고 안전하다고 판정하면 안 된다. VM에도 위험한 장치·파일 공유 설정이 있을 수 있다.

공유는 비용을 줄이지만 간섭을 남긴다

CPU·캐시·메모리·저장 장치를 공유하면 자원을 효율적으로 쓸 수 있다. 동시에 다른 작업의 부하가 응답을 흔드는 noisy neighbor 문제를 고려해야 한다.

CPU quota 하나가 모든 I/O와 네트워크 지연을 제한하지는 않는다. 처리량·평균·상위 백분위 응답 시간을 나누어 관측해야 하며 특정 구성이 늘 빠르거나 늘 안전하다는 순위는 성립하지 않는다.

평균과 최대 수요를 함께 본다

백분위는 정렬한 응답 중 일정 위치의 값이다. 여기서는 표본 100 개의 p99 를 nearest-rank 규칙에 따라 99 번째 값으로 정의한다. 규칙을 명시해야 다른 도구와 비교할 수 있다.

메모리를 과다 약속하면 평소에는 여유가 있어도 동시에 커지는 순간 부족할 수 있다. 평균 사용량에 맞춘 계획과 모두의 최대치를 보장하는 계획을 구별한다.

중간 과정을 따라가는 예제

응답 A는 98 개가 1 ms, 2 개가 51 ms다. B는 100 개 모두 2 ms다. 각각 평균과 위 정의의 p99 를 구하자. 별도 호스트는 4 GiB 중 1 GiB를 호스트에 남기고 네 작업이 평소 각 0.5 GiB, 최대 각 1.5 GiB를 요구한다.

  1. A의 합은 98+102=200 ms로 평균 2 ms다. 정렬한 99 번째는 51 ms다.

  2. B의 평균과 p99 는 모두 2 ms다. 같은 평균이 같은 꼬리 지연을 뜻하지 않는다.

  3. 게스트에 계획 가능한 양은 4−1=3 GiB다. 평소 합계 4×0.5=2 GiB는 들어가지만 동시에 최대가 되면 4×1.5=6 GiB로 3 GiB를 초과한다.

평균은 같지만 p99 는 A 51 ms/B 2 ms다. 평소 메모리는 들어가도 전체 최대 수요를 보장할 수 없는 예산이다.

전체와 작은 집단의 동시 기준

표의 서비스 기준은 전체 99% 이상이며 각 집단 90% 이상도 요구합니다. 만족 여부와 B에서 최소 몇 건이 성공해야 하는지 쓰세요. 다른 결과는 고정합니다.

  1. 전체 990/1000=99%는 전체 기준을 만족합니다.

  2. B는 0/10=0%로 집단 기준에 실패합니다.

  3. B에서 성공이 아홉 건이면 90%, 전체는 999/1000=99.9%입니다.

현재 집단 기준에 실패하며 B의 최소 아홉 건을 성공으로 고쳐야 합니다.

비교할 점

전체만 보는 결론과 집단별 기준을 함께 요구한 결론을 혼동하지 않습니다.

읽기 전용 공유도 비밀 읽기는 허용한다

호스트의 비밀 파일 F를 컨테이너 안에 read-only로 공유했고 접근제어도 F 읽기를 허용한다고 정합니다. 목표는 ①F 변조 금지, ②F 내용 열람 금지입니다. 이 공유의 두 목표 판정은? 다른 접근 경로는 제외합니다.

  1. 지정한 공유의 쓰기 권한이 없어 이 경로로 F를 수정할 수 없습니다.

  2. 읽기 권한은 있으므로 F 내용을 볼 수 있습니다.

  3. 두 보호 목표는 같지 않습니다.

①이 경로의 변조는 금지되지만 ②내용 열람 금지는 충족하지 않습니다.

비교할 점

read-only를 모든 비밀 보호나 전체 호스트 격리의 증거로 바꾸지 않습니다.
