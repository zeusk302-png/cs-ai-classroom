소단원 11.1

권한·sandbox·capability

문서 변환 프로그램에 전체 관리자 권한까지 필요할까?

준비 개념과 학습 목표

준비 개념

  • 프로세스와 커널

  • 파일 읽기·쓰기

  • 집합의 교집합

학습 목표

  • 최소 권한과 sandbox의 보호 범위를 구별한다.

  • Linux capability와 객체 기반 권한 용어를 혼동하지 않는다.

새 파일 열기를 막아도 이미 열어 둔 파일의 읽기는 남을까요?

기본의 권한 교집합은 이미 열린 descriptor와 helper가 없는 자체 모형이었습니다. 이번에는 이 가정을 바꿉니다. 프로세스는 비밀 파일 F를 읽기로 열어 fd=9를 얻은 뒤 Landlock 제한을 적용합니다. 새 F 열기는 거부하도록 지원되는 정책을 성공적으로 설치했고 기존 fd=9는 유지하며 다른 통제는 해당 read를 허용한다고 정합니다.

Landlock 문서는 파일을 열 때의 권한과 이미 열린 descriptor의 이후 동작을 구분합니다. 따라서 경로 목록만으로 프로그램이 가질 수 있는 모든 통로를 판정하지 않습니다. seccomp는 직접 syscall 번호와 인수 등을 검사하는 필터이지 임의 포인터의 경로 문자열을 역참조하는 완전 sandbox가 아닙니다. 실제 정책 설치·파일·프로세스·권한 변경은 실행하지 않았습니다.

먼저 확인할 개념
  • 권한·sandbox·capability

    기본 모형에서 제외했던 열린 통로와 syscall 필터의 범위를 확인합니다.

  • 커널 취약성의 원인

    검사 대상과 실제 사용 대상의 동일성을 연결합니다.

필요한 권한부터 적는다

최소 권한은 프로그램이 해야 할 작업에 필요한 권한을 주고 불필요한 권한을 줄이는 원칙이다. 파일 변환에 입력 읽기와 결과 쓰기가 필요하다면 시스템 설정 변경이나 다른 사용자의 비밀 읽기까지 요구하지는 않는다. 버그가 없다고 가정하기보다 버그가 생겼을 때 영향을 받는 범위를 생각한다.

권한은 사용자·그룹·파일 규칙·프로세스 특권·추가 접근 통제와 함께 확인한다. 한 층이 허용한다고 다른 모든 층도 허용하는 것은 아니다. 반대로 실제로 이미 열어 둔 file descriptor나 helper의 권한을 보지 않고 경로 목록만으로 전체 권한을 이해했다고 말할 수 없다.

sandbox와 syscall 필터를 구별한다

sandbox는 프로그램이 접근할 수 있는 자원과 동작을 제한하는 실행 환경의 설계다. Linux Landlock은 자체 접근 제한을 추가하는 예이며 기존 통제를 자동 대체하는 것은 아니다. 운영 커널의 지원 ABI와 실제 enforcement 성공 여부를 확인해야 한다.

seccomp는 호출 가능한 syscall 표면을 줄이는 도구다. 공식 문서도 이것 하나를 완전한 sandbox로 부르지 않는다. read와 open 계열 호출을 허용했더라도 어느 파일을 읽을지의 정책은 별도로 필요하다. seccomp 필터는 포인터가 가리키는 임의 문자열을 읽어 모든 파일 경로를 비교하는 도구로 가정하면 안 된다.

같은 capability라는 말의 두 맥락

Linux capabilities는 전통적으로 root에 묶인 특권을 여러 단위로 나누는 방식이며 effective set 등이 있다. CAP_NET_BIND_SERVICE와 CAP_SYS_ADMIN은 범위가 같지 않다. 특정 작은 기능만 필요할 때 매우 넓은 관리 특권을 주면 최소 권한의 목적을 약화할 수 있다.

객체 기반 capability 시스템에서 말하는 객체에 대한 권한 참조와 Linux의 특권 비트 체계는 같은 구현이 아니다. seL4 같은 시스템의 용어를 읽을 때 어느 모델인지 확인한다. 이 소단원의 종이 표는 자원·행동별 허용 집합 모형이며 Linux 실제 정책 파일이나 API 호출 결과가 아니다.

표는 기존 descriptor까지 끊는 별도 조치가 없다는 조건입니다. 실제 전체 격리 증명이 아닙니다.

중간 과정을 따라가는 예제

자체 문서 변환 모형의 기존 권한 D는 {입력 읽기,결과 쓰기,임시 쓰기,비밀 읽기}다. 추가 sandbox 허용 S는 {입력 읽기,결과 쓰기,임시 쓰기}이고 두 층 모두 허용해야 한다. 변환에 필요한 세 작업과 비밀 읽기의 결과를 구하라.

  1. effective 허용 모형은 D∩S={입력 읽기,결과 쓰기,임시 쓰기}다.

  2. 변환의 입력 읽기와 결과 쓰기, 임시 쓰기는 두 집합에 모두 있어 허용된다.

  3. 비밀 읽기는 D에는 있지만 S에 없어 거부된다. sandbox를 추가했다고 원래 D만 보면 결과를 알 수 없다.

  4. 이 표는 기존 열린 descriptor·특권 helper·네트워크 같은 다른 통로가 없다는 자체 제한 모형이다. 실제 적용을 증명한 것이 아니다.

세 변환 작업은 허용하고 비밀 읽기는 거부하는 교집합 모형이다.

조건을 바꾸어 비교하기

열린 통로의 목록을 함께 만든다

표의 새 F 열기 거부가 모든 F 읽기 거부를 뜻하나요? fd=9를 실제로 닫고 상속·전달·helper 통로도 없다고 추가 가정한 경우와 비교하세요.

  1. 기존 fd=9의 read는 새 open과 다른 동작입니다.

  2. 현재 가정에서는 기존 읽기 통로가 남아 있어 내용 접근 금지를 주장하지 못합니다.

  3. 별도 조건에서 fd=9를 닫고 모든 명시한 대체 통로를 제외하면 이 모형의 F 읽기 경로는 없습니다.

원래는 읽기 통로가 남습니다. 추가 조건을 만족한 자체 통로 모형에서는 해당 F 읽기를 차단합니다.

비교할 점

추가 가정의 판정을 현실의 모든 IPC·장치·다른 통로까지 확장하지 않습니다.

더 뒤에 설치한 필터가 앞의 거부를 취소하나요?

seccomp 필터 F1은 특정 호출에 ERRNO를, 뒤의 F2는 같은 호출에 ALLOW를 반환한다고 정합니다. 문서의 우선순위로 호출 실행 여부를 판정하세요.

  1. 여러 필터의 반환 중 우선순위가 높은 action을 선택합니다.

  2. ERRNO는 ALLOW보다 높은 우선순위입니다.

  3. 호출을 실행하지 않고 설정한 오류를 반환합니다.

뒤 필터의 ALLOW만으로 앞 필터의 ERRNO 거부를 풀지 못합니다.

비교할 점

같은 우선순위의 DATA 선택 규칙과 서로 다른 action 우선순위를 섞지 않습니다.

종이와 본문으로 직접 해보기

기존 D에서 결과 쓰기를 제거했지만 S에는 남아 있다. 결과 파일을 쓸 수 있는가? syscall 필터가 write를 허용하면 이 정책 거부가 사라지는가?

힌트 보기

두 자원 권한 층을 모두 통과해야 한다는 모형과 호출 종류 허용을 따로 본다.

풀이 보기

결과 쓰기는 D에 없으므로 D∩S에도 없어 거부된다. write 호출 종류를 허용한 것만으로 다른 접근 통제의 거부를 취소하지 않는다. 실제 열림 상태·대상 descriptor·정책 적용 범위는 별도 점검한다.

오해와 반례

capability 하나를 주거나 seccomp를 켜면 모든 자원 접근이 완전히 안전하다.

capability마다 특권 범위가 다르고 syscall 필터는 완전 sandbox가 아니다. 필요한 자원·동작·상속·helper·기존 열린 통로를 함께 확인해야 한다. 정책을 설치한 뒤 실제 성공과 허용·거부 동작도 검증해야 한다.

연습 1 · 값과 상태 예측

파일 권한 D={입력 읽기,결과 쓰기,비밀 읽기}, 정책 S1={입력 읽기,결과 쓰기}, S2={입력 읽기}입니다. 새 경로 접근은 세 층 모두 허용해야 하며 다른 통로는 없습니다. 최종 허용은?

힌트 1

세 집합의 교집합을 구합니다.

힌트 2

추가 층은 기존에 없는 권한을 늘리지 않습니다.

풀이와 답 확인

  1. D와 S1의 교집합은 입력 읽기와 결과 쓰기입니다.

  2. S2와도 교집합을 구하면 입력 읽기만 남습니다.

최종 허용은 입력 읽기 하나입니다.

뒤 정책에 하나라도 있으면 전체 허용이다.

모든 적용 층이 허용해야 하는 자체 규약입니다.

연습 2 · 오류 찾아 고치기

부모가 정책을 성공적으로 적용했다고 했지만 기존 형제 스레드까지 함께 적용하는 옵션·지원 조건은 확인하지 않았습니다. 모든 스레드 제한을 검증했다고 쓴 보고를 고치세요.

힌트 1

현재 스레드와 이후 자손의 적용을 구분합니다.

힌트 2

기존 형제 스레드 적용은 실제 ABI와 TSYNC 등의 조건을 확인합니다.

풀이와 답 확인

  1. 정책 적용 대상과 성공 결과를 기록합니다.

  2. 기존 형제와 다중 스레드 동기 적용의 지원·옵션·결과를 별도로 확인합니다.

현재 스레드와 이후 자손의 제한을 기존 모든 형제 스레드의 자동 제한으로 확대하지 않습니다.

흔한 오답에서 다시 생각하기

프로세스라는 이름 아래 스레드 정책도 무조건 한꺼번에 바뀐다.

현재 문서의 스레드별 적용과 지원되는 동기 적용 조건을 확인해야 합니다.

연습 3 · 직접 만들어 보기

자체 helper H는 F를 읽을 수 있고 작업자 W는 F를 직접 열 수 없습니다. H가 W의 아무 경로 요청이나 대신 읽어 내용을 돌려줍니다. W에게 F 내용 금지라는 목표를 만족하도록 인터페이스 계약을 보완하세요.

힌트 1

대신 실행하는 권한도 접근 통로입니다.

힌트 2

작업자의 요청이 helper의 권한을 임의 사용하지 못하게 합니다.

풀이와 답 확인

  1. H가 명시한 허용 입력 객체만 처리하도록 검증합니다.

  2. W의 임의 경로를 H의 전체 읽기 권한으로 바꾸지 않습니다.

  3. 허용·거부 요청과 열린 descriptor 전달 및 내용 반환의 범위를 검증할 계획을 만듭니다.

helper가 전달하는 정보와 권한 경계도 제한해야 합니다. 여기서는 계약 계획이며 실제 enforcement를 검증하지 않았습니다.

흔한 오답에서 다시 생각하기

W의 직접 open만 막으면 helper가 대신 읽어도 안전하다.

내용 반환을 통한 간접 읽기가 보호 목표를 위반할 수 있습니다.

커널 취약성의 원인

길이 검사 하나가 빠지면 사용자 입력이 왜 커널의 문제로 이어질까?

준비 개념과 학습 목표

준비 개념

  • 배열 경계

  • 정수 자료형

  • 동시 실행과 수명

학습 목표

  • 경계·길이 산술·객체 수명·검사와 사용의 간격을 찾는다.

  • 버그의 존재와 실제 악용 가능성을 구별한다.

헤더를 더하는 계산까지 넘치지 않았는지 확인했나요?

기본의 수량×크기 산술에 헤더를 더합니다. 자체 패킷은 헤더 12바이트와 원소당 5바이트이며 n=50입니다. 필요한 총량은 수학적 정수로 계산하지만 오류 모형은 8비트 unsigned의 저장값, 즉 256으로 나눈 나머지만 할당합니다. 실제 커널의 자료형이나 알려진 취약성이라는 주장이 아닙니다.

보호 조건은 곱셈만 아니라 더하는 헤더와 확보한 용량을 함께 포함합니다. 먼저 capacity≥header인지 확인한 뒤 n≤floor((capacity−header)/size)를 확인하면 모형의 뺄셈 부족과 전체 범위를 나눠 검사할 수 있습니다. 객체 수명에서도 같은 주소를 다시 썼다는 사실만으로 이전 객체의 동일성이 유지되지 않습니다. 안정된 참조와 세대·검사 사용 경계를 별도로 검토합니다.

먼저 확인할 개념

  • 형식 검증·fuzzing 개요

신뢰 경계에서 자료를 해석한다

커널은 사용자 요청과 장치 입력 등을 받아 권한이 큰 작업을 수행한다. 입력 길이와 인덱스, 결과 저장 크기를 확인하지 않으면 경계 밖 접근이 생길 수 있다. 사용자 주소를 그대로 믿거나 실제 복사 성공과 길이를 확인하지 않은 채 다음 단계로 진행하는 설계도 문제가 될 수 있다.

수량×원소 크기를 작은 정수에 넣으면 wrap으로 실제 필요한 공간보다 작게 보일 수 있다. 다음 자체 예제는 일부러 8비트 unsigned 산술을 가정한 오류 모형이다. 실제 커널이 언제나 이 자료형을 쓰거나 이 오류가 존재한다는 주장은 아니다. 제한 조건과 연산을 명시해 원인을 배운다.

객체 수명과 동시 실행

객체를 해제한 뒤 이전 참조로 접근하는 use-after-free와 배열 범위 밖 접근은 메모리 안전 오류다. KASAN은 이런 오류를 실행 중 탐지하는 도구다. 하지만 탐지 가능 경로·설정·모드가 있으므로 보고가 없다고 모든 실행에 오류가 없다는 결론을 내리지 않는다.

다른 작업이 객체나 이름 연결을 바꾸는 동안 검사한 조건을 나중에 그대로 믿으면 검사와 사용 사이의 의미가 달라질 수 있다. 동시 접근의 data race와 더 넓은 논리적 TOCTOU 문제는 구별한다. KCSAN의 동적 race 탐지나 sampling 결과가 모든 논리적 경쟁을 자동 증명하는 것은 아니다.

고치는 조건과 위험을 따로 기록한다

길이 계산은 올바른 폭에서 계산하고 넘침을 사전에 검사하며, 복사는 확보한 공간 안에서 수행한다. 객체 수명은 사용 기간의 소유권·참조 관리로 보호한다. 검사 후 사용하는 객체가 같아야 한다면 안정된 참조를 얻거나 적절한 동기화·원자 연산을 검토한다.

버그를 찾으면 재현 입력·기대 결과·실제 관찰·수정 조건을 나눠 적는다. 경계 오류의 종이 반례만으로 원격 코드 실행이나 권한 상승이 실제 가능하다고 확정하지 않는다. 본문은 특정 제품 취약성을 공격하는 실습 대신 자체 오류 모형과 방어 조건을 다룬다.

중간 과정을 따라가는 예제

자체 오류 모형에서 원소 수 n = 70이고 원소 크기 s = 4바이트다. 잘못된 계산은 n × s를 8비트 unsigned에 넣어 256으로 나눈 나머지만큼 버퍼를 잡고, 복사 반복은 70개 원소 전체를 쓴다. 필요한 용량과 할당 용량을 비교하라.

  1. 실제 자료 공간은 70×4=280바이트다.

  2. 8비트 저장 결과는 280 mod 256 = 24바이트이므로 잘못된 할당은 24바이트다.

  3. 70개를 복사하려면 바이트 offset 0부터 279까지 쓰지만 예약 범위는 0부터 23까지다. 7번째 원소의 시작 offset 24부터 경계를 넘는다.

  4. 8비트 길이로 4바이트 원소를 저장해야 한다면 n ≤ floor(255 / 4) = 63인지 사전에 검사한다. n = 64이면 필요한 256바이트가 저장 값 0으로 바뀌므로 허용하면 안 된다. 더 큰 용량이 필요하면 적절한 큰 폭과 overflow 검사로 설계한다.

필요 용량 280바이트와 할당 용량 24바이트가 불일치한다. 이 자체 모형의 첫 잘못된 원소는 7번째다.

조건을 바꾸어 비교하기

곱셈은 맞아도 헤더 덧셈은 넘친다

n=50에서 잘못 할당한 용량과 정상 총량을 비교하고 헤더부터 쓴다면 첫 범위 밖 바이트를 구하세요.

  1. 필요 총량은 12+250=262바이트입니다.

  2. 잘못 저장한 8비트 길이는 262 mod 256=6바이트입니다.

  3. 할당 범위는 [0,6)이며 헤더 쓰기의 offset 6부터 범위 밖입니다.

필요 262바이트를 6바이트에 넣으려 하며 헤더의 일곱 번째 바이트부터 경계를 넘습니다.

비교할 점

실제 접근 코드를 실행하거나 악용한 결과가 아닌 자체 산술 반례입니다.

뺄셈 검사 순서

capacity=64, header=12, size=5일 때 최대 n을 구하세요. 별도 capacity=8에서 8비트로 capacity−header를 먼저 계산해 252를 얻었다면 판정을 고치세요.

  1. 64≥12를 확인한 뒤 남은 52바이트를 셉니다.

  2. floor(52/5)=10이므로 원소 열 개의 총량 62바이트는 맞고 열한 개는 67바이트로 초과합니다.

  3. capacity=8은 헤더 12보다 작아 뺄셈 전에 거부해야 합니다.

용량 64에서는 최대 열 원소입니다. 용량 8에서는 헤더부터 들어가지 않아 거부합니다.

비교할 점

unsigned의 wrap 결과 252를 실제 남은 공간으로 읽지 않습니다.

모든 분기를 지나갔는데도 잘못된 결과를 놓칠까요?

기본 coverage 설명을 작은 자체 함수로 확인합니다. 명세 f(x)=2x는 정수 입력 x≥0에 적용합니다. 오류 구현은 x=0이면 0, 그렇지 않으면 x+1을 반환합니다. 입력 0과 1은 기대값에 맞고 두 분기를 모두 지나가지만 같은 분기의 다른 값에서는 명세가 어긋날 수 있습니다. sanitizer가 보고할 메모리 오류 없이도 결과 오류가 가능합니다.

다른 자체 루프는 i=0에서 시작해 i+1<n인 동안 a[i]와 a[i+1]을 읽고 i를 2만큼 늘립니다. 수학적 정수 산술·n≥0·배열 유효 수명·정해진 길이를 가정하며 언어 overflow는 모델에서 제외합니다. 범위 밖 접근이 없다는 명제와 모든 원소를 읽었다는 명제는 서로 다릅니다. 기계 prover·fuzzer·kernel·학생 실행은 수행하지 않았습니다.

무엇을 증명하는지 먼저 정의한다

형식 검증은 명세와 모델을 정하고 구현이 명세를 만족하는지 논리적으로 다루는 접근이다. 명세가 사용자 의도와 다르거나 하드웨어 가정이 충족되지 않으면 증명된 문장의 적용도 달라진다. 어떤 구성·플랫폼·소스 또는 binary가 대상인지 함께 기록해야 한다.

seL4는 kernel functional correctness와 특정 구성의 binary correctness 등을 기계적으로 확인한 사례다. 공식 자료는 구성별 범위와 hardware·boot·DMA 등의 가정도 명시한다. 이를 전체 사용자 응용과 장치까지 아무 조건 없이 완전히 검증됐다는 주장으로 확장하지 않는다.

입력을 바꾸며 반례를 찾는다

fuzzing은 입력이나 호출 순서를 많이 생성·변형하며 오류를 찾는 시험 방식이다. coverage-guided 방식은 새 실행 지점을 만난 입력 등을 이후 탐색에 활용한다. syzkaller는 kernel fuzzing의 사례이며 compiler가 만든 coverage 지점과 원본 코드 줄의 대응은 항상 단순하지 않다.

충돌이나 sanitizer 보고를 관찰하는 것만으로 모든 잘못된 출력·권한 오류를 잡는 것은 아니다. 기대 성질을 판정할 oracle이 필요하다. 시험 입력 공간·실행 경로·환경이 제한돼 있으므로 많은 시험의 통과를 모든 입력의 증명으로 바꾸지 않는다.

자체 작은 명제를 손으로 확인한다

길이 n 배열에 대해 0≤i<n인 인덱스만 읽는 루프라면 수학적 정수 산술과 유효한 배열 수명 가정 안에서 범위 밖 인덱스를 읽지 않는다. 이 결론은 i의 초기값·증가·종료 조건이 실제 구현과 같은지 확인해야 한다. i≤n으로 바꾸면 n번째 인덱스에 도달하는 반례가 생긴다.

이런 손으로 쓴 명제는 학습용 논리 점검이며 Isabelle 같은 prover로 코드 전체를 검증한 결과가 아니다. 실제 구현 검증은 언어의 overflow·pointer·동시성·에러 경로를 모델에 포함하고 검토된 구현과 증명 대상이 일치하는지 확인해야 한다.

중간 과정을 따라가는 예제

자체 배열 길이 n=3에서 루프는 i=0으로 시작해 i<n 동안 a[i]를 읽고 i를 1 증가시킨다. 읽는 인덱스를 추적하라. 비교를 i≤n으로 바꾼 오류도 추적하라.

  1. 올바른 비교 i < 3에서 i = 0, 1, 2일 때 조건이 참이므로 a[0], a[1], a[2]를 읽는다. i = 3에서 거짓이 되어 종료한다.

  2. 오류 비교 i ≤ 3은 i = 3에서도 참이므로 a[3]까지 읽고 i = 4에서 종료한다.

  3. 유효 인덱스는 0부터 2까지이므로 a[3]은 반례다. 정상 초기화와 수학적 정수 증가, 배열 수명 가정을 유지한다.

  4. n = 0에서도 올바른 루프는 아무것도 읽지 않고, 오류 루프는 a[0]을 읽으려 한다. 빈 배열 경계 시험은 오류 발견 후보다.

정상 읽기의 인덱스는 0, 1, 2이며 오류 비교는 인덱스 3을 추가로 읽는다. 실제 C나 kernel 실행이 아니라 손으로 추적한 결과다.

오해와 반례

fuzzing에서 새 coverage가 많이 늘면 프로그램의 모든 요구사항이 증명된다.

coverage는 탐색의 한 관찰 지표다. 같은 경로의 다른 값·동시 실행 순서·잘못된 결과를 놓칠 수 있고 oracle의 범위도 제한된다. 형식 검증과 fuzzing은 서로 다른 증거이며 수정 후 둘의 대상 SHA와 조건도 확인해야 한다.

다른 문제에 적용하기

정책 전에 열린 읽기 fd=6을 유지하면서 새 파일 F 열기만 거부했습니다. 기존 읽기 통로를 판정하세요. 별도 8비트 길이 모형은 헤더 20바이트·원소당 6바이트·n=40입니다. 필요한 총량과 저장 길이, 최대 안전 n을 구하세요. 또 다른 짝 읽기 루프에서 n=3일 때 원래 읽기와 tail 추가 뒤 읽기를 비교하고, 각각의 종이 판정과 실제 kernel/prover 실행 여부를 표시하세요.

힌트 1

새 open과 기존 descriptor 읽기를 나눕니다.

힌트 2

255에서 헤더를 남긴 뒤 원소 크기로 나눕니다.

힌트 3

쌍 루프 종료의 i와 단일 tail 조건을 확인합니다.

풀이와 답 확인

  1. 기존 fd=6은 명시한 별도 통제 없음 조건에서 읽기 통로를 유지합니다.

  2. 전체 길이는 20+40×6=260바이트이고 8비트 저장값은 4입니다.

  3. 최대 안전 n은 floor((255−20)/6)=39입니다.

  4. n=3의 쌍 읽기는 0,1이고 tail을 더하면 2도 읽습니다.

  5. 수치와 권한은 자체 손판정이며 실제 정책·sanitizer·prover·학생 실행은 미수행입니다.

기존 fd=6 읽기 통로가 남습니다. 자체 필요 길이는 260바이트, 저장된 길이는 4바이트이며 최대 안전 원소 수는 39입니다. 짝 루프는 인덱스 0과 1을 읽고 tail 추가 뒤에는 2까지 처리합니다.

해결한 뒤 점검할 것

  • 열린 권한·helper와 신규 경로 통제를 구분합니다.

  • 헤더 포함 전체 길이와 뺄셈 조건을 확인합니다.

  • 범위 안전·전체 처리·coverage를 다른 명제로 기록합니다.

  • 현재 대상과 증거 SHA 및 실제 실행 여부를 구별합니다.

세 자원 권한 층의 교집합은 입력 읽기 하나다. 기존 descriptor의 유지와 새 open의 거부를 구별했고, seccomp의 ERRNO는 ALLOW보다 우선한다. 헤더가 12바이트이고 원소가 5바이트일 때 원소 48개의 필요 길이는 252바이트이고 저장값도 252다. 원소 49개에서는 필요 길이 257바이트가 저장값 1이 되며, 원소 50개에서는 필요 길이 262바이트가 저장값 6이 된다. 6바이트 할당의 첫 범위 밖 offset은 6이다. 용량 64바이트에는 원소 열 개의 총량 62바이트가 들어가지만 열한 개의 총량 67바이트는 들어가지 않는다. 용량 8바이트는 헤더보다 작아 뺄셈 전에 거부한다. 최대 255의 길이 범위에서 안전한 최대 원소 수는 48이다. 필요한 입력 14바이트에 실제 11바이트를 받으면 3바이트가 부족하다. 세대 2의 옛 손잡이는 현재 세대 3과 다르다. 오류 함수의 입력 2에서는 구현 결과 3이 명세의 4와 다르다. 길이 5의 짝 루프는 인덱스 0부터 3까지 읽으며 tail을 추가하면 인덱스 4도 읽는다. 조건을 i<n으로 약화하면 인덱스 5가 범위 밖이다. 길이 0과 길이 1에서는 원래 쌍 읽기가 없고, 길이 1의 tail은 인덱스 0을 읽는다. 전이 문제의 필요 길이는 260바이트이고 저장값은 4이며 안전한 최대 원소 수는 39다. 길이 3의 쌍 읽기는 인덱스 0과 1을 읽고 tail은 인덱스 2를 읽는다. 이를 명시한 자체 모형에서 손으로 확인했다.
