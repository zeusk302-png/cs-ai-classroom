소단원 9.1

배치·비동기 I/O

요청 열 개를 한꺼번에 맡기면 완료도 같은 순서일까?

준비 개념과 학습 목표

준비 개념

  • 시스템 호출은 사용자 프로그램과 커널 사이의 요청이다.
  • 입출력에는 데이터 이동과 완료 확인이 필요하다.

학습 목표

  • 요청 제출과 완료를 분리한다.
  • 배치 고정 비용과 데이터 처리 비용을 계산한다.

배치는 여러 요청의 고정 비용 나누기

작은 요청마다 같은 준비와 호출 비용을 내면 실제 데이터 처리보다 주변 작업이 커질 수 있다. 배치는 여러 요청을 한 번에 전달하여 공통 비용을 나누는 방식이다. 요청의 개수가 사라지는 것이 아니라 전달 횟수를 줄이는 관점이다.

한꺼번에 묶기 위해 기다리는 시간도 고려한다. 첫 요청이 온 뒤 묶음이 찰 때까지 기다리면 처리량은 좋아져도 첫 요청의 지연이 길어질 수 있다. 배치 크기와 최대 대기 시간을 함께 정하는 이유다.

비동기는 제출과 완료의 분리

Linux io_uring은 SQ에 요청을 넣고 CQ에서 완료 결과를 받는 구조를 제공한다. 공유 ring으로 여러 요청을 제출할 수 있다. SQPOLL 등 설정에 따라 호출 방식이 달라지므로 아래 호출 수 계산은 별도 polling이 없는 기본 제출 축소 모형이다.

일반적인 단발 요청의 완료 순서는 제출 순서와 다를 수 있다. user_data 같은 식별자로 어느 요청의 결과인지 확인해야 한다. multishot이나 성공 CQE 생략 설정은 완료 개수 규칙도 바꾸므로 여기서는 사용하지 않는다.

완료의 의미와 버퍼 수명

비동기 요청에 쓰는 읽기·쓰기 데이터 버퍼는 작업이 진행 중인 동안 유효해야 한다. 제출 함수가 돌아왔다고 즉시 버퍼를 덮으면 잘못된 데이터를 다룰 수 있다. 결과의 길이와 오류를 확인하고 필요한 나머지 작업을 결정한다.

공유 ring은 데이터 파일의 모든 바이트 복사를 자동으로 없앤다는 뜻이 아니다. 요청 전달 최적화와 실제 payload 이동을 구별한다. 의존하는 요청에는 명시적인 순서 제약 등 해당 API의 안전한 구성이 필요하다.

중간 과정을 따라가는 예제

독립 요청 10개의 제출 고정 비용을 호출당 4μs, 요청별 기술 비용을 1μs로 가정하자. 완료 대기와 장치 처리 비용은 제외한다. 한 번에 최대 4개를 제출할 수 있고 배치가 이미 준비되어 있다. A·B·C를 제출한 뒤 CQ에는 B(4096), A(2048), C(−5)가 도착했다고 하자.

  1. 한 개씩 제출하면 10×4+10×1=50μs다.
  2. 4·4·2로 묶으면 제출 호출은 3회이며 3×4+10×1=22μs다. 차이는 28μs이고 50 대비 56% 감소다.
  3. 완료 식별자로 B는 4096바이트, A는 2048바이트의 결과에 대응시킨다. C의 음수 결과는 이 가상 기록의 오류이며 성공 바이트 수로 더하지 않는다.

축소 제출 비용은 50→22μs다. 완료 순서 B/A/C는 요청 식별자로 연결해야 하며 장치 전체 실행 시간이 56% 감소했다는 측정은 아니다.

종이와 본문으로 직접 해보기

한 번에 최대 5개로 바꾸면 비용은 얼마인가? A가 4096바이트를 요청했는데 결과가 2048이면 모두 처리했다고 결론 내릴 수 있는가?

힌트 보기

제출 횟수는 올림(10/5)이고 요청 기술 비용은 그대로다.

풀이 보기

2×4+10×1=18μs다. A는 요청량보다 작은 결과이므로 그 작업의 의미에 따라 남은 2048바이트 처리나 EOF 등을 확인해야 한다. 결과만으로 전체 4096바이트 완료를 선언하지 않는다.

오해와 반례

비동기는 빠르고 제출 순서대로 무조건 완료된다.

비동기는 호출자와 완료 시점을 분리한다. 독립 요청의 완료 순서는 바뀔 수 있고 지연과 성능은 장치·큐·부하에 달린다. 이 예제는 실제 속도 측정이 아니다.

4개씩 10개를 제출하면 몇 묶음인가?

답과 이유 보기

3묶음이다.

제출 반환 직후 진행 중인 쓰기 버퍼를 덮어도 되는가?

답과 이유 보기

한 단계 더

요청 ID, 요청량, 완료량, 성공/오류, 버퍼 재사용 가능 여부를 표로 만들자. 같은 표로 완료 순서만 섞어 보면 제출 순서에 의존한 프로그램이 왜 위험한지 확인할 수 있다.

소단원 9.2

커널 우회와 polling

알림을 기다리는 대신 계속 확인하면 공짜로 빨라질까?

준비 개념과 학습 목표

준비 개념

  • 시스템 호출은 사용자 프로그램과 커널 사이의 요청이다.
  • 입출력에는 데이터 이동과 완료 확인이 필요하다.

학습 목표

  • 전통적인 네트워크 경로와 사용자 공간 처리의 차이를 설명한다.
  • polling의 확인 비용과 대기 지연을 비교한다.

우회하는 경로를 정확히 말하기

DPDK PMD는 사용자 공간에서 네트워크 장치의 Rx/Tx descriptor를 다루며 전통적인 커널 네트워크 데이터 경로를 우회한다. 운영체제가 아예 사라진다는 의미는 아니다. 장치와 메모리 설정, 프로그램 보호와 관리의 다른 역할은 여전히 고려한다.

기본 packet polling은 수신 알림을 기다리기보다 큐를 직접 확인한다. 링크 상태 변경 알림 같은 예외도 있으므로 모든 인터럽트가 존재하지 않는다고 단정하지 않는다. 어떤 장치·드라이버·경로를 사용했는지 밝히는 것이 중요하다.

처리 방식과 소유권

run-to-completion은 같은 core가 받아 처리하고 송신하는 방식이고 pipeline은 core 사이 ring으로 작업을 넘기는 방식이다. 분업은 가능하지만 전달 비용과 큐 관리도 필요하다. core를 추가했다는 이유만으로 선형 속도 향상을 보장하지 않는다.

PMD의 기본 lock-free 호출에는 사용 규칙이 있다. 같은 Rx queue를 여러 core가 동시에 polling하는 것으로 안전성을 가정하지 않는다. 서로 다른 큐에 대한 병렬 처리와 공유 대상을 위한 보호를 구분하며 특별한 Tx 기능의 예외를 일반 Rx 규칙에 옮기지 않는다.

확인 주기의 지연과 비용

짧은 주기로 확인하면 패킷이 온 뒤 발견하기까지의 기다림을 줄일 수 있지만 빈 큐도 자주 확인하게 된다. busy polling은 유휴 시에도 CPU 시간을 사용할 수 있어 절전이나 다른 작업과의 균형을 생각해야 한다.

아래는 일정 주기와 가상 확인 비용을 둔 종이 모형이다. 실제 DPDK loop가 고정된 주기만 사용한다는 설명이 아니다. 평균 대기 T/2는 도착 위상이 주기 안에서 균등하다는 추가 가정이 있을 때만 성립한다.

중간 과정을 따라가는 예제

가상 polling 주기는 20μs이고 한 번 확인하는 CPU 비용은 0.5μs다. 처리 비용을 제외하고 1초 동안 규칙적으로 확인한다. 패킷 도착 위상은 각 주기 안에서 균등하다고 가정한다. 비교 설정은 주기 5μs, 동일 확인 비용이다.

  1. 20μs 설정은 1,000,000/20=50,000회/초다. 확인 CPU 시간은 25,000μs=25ms로 단일 core 1초의 2.5%다.
  2. 평균 발견 대기는 20/2=10μs이며 다음 확인 직전까지의 대기는 20μs보다 작다. 확인 시점 바로 도착하는 경계는 즉시 확인하는 규칙으로 정한다.
  3. 5μs 설정은 200,000회·100ms·10%이며 평균 대기는 2.5μs다. 평균 대기 7.5μs를 줄이는 대신 확인 시간은 75ms 늘어난다.

더 짧은 가상 주기는 평균 대기를 10→2.5μs로 줄이지만 확인 비용을 2.5→10%로 늘린다. 실제 패킷 처리와 메모리 비용은 계산에 포함하지 않았다.

종이와 본문으로 직접 해보기

주기 10μs의 확인 횟수·CPU 시간·평균 대기를 구하자. 도착이 항상 확인 직후로 몰리면 평균 대기가 여전히 T/2라고 할 수 있는가?

힌트 보기

주기와 확인 비용을 곱하지 말고, 1초 안의 확인 횟수에 확인 비용을 곱하자.

풀이 보기

100,000회, 50ms, 단일 core 5%, 균등 위상 가정의 평균 대기 5μs다. 확인 직후에 도착이 몰리면 거의 10μs를 기다릴 수 있으므로 균등 위상 가정 없이 T/2를 쓰면 안 된다.

오해와 반례

커널 우회와 polling이면 CPU 비용도 없어지고 모든 큐를 아무 core나 만져도 된다.

전통적 데이터 경로를 바꾸어도 사용자 공간 처리·메모리·확인 비용은 남는다. 기본 PMD 큐 소유 규칙도 지켜야 한다. 우회는 모든 보호와 동기화가 필요 없다는 뜻이 아니다.

자기점검

답과 이유 보기

50,000번이다.

1초는 1,000,000μs다.

같은 Rx queue를 두 core가 기본 lock-free API로 동시에 읽어도 안전한가?

답과 이유 보기

그렇게 가정하면 안 된다.

기본 PMD 규칙은 같은 수신 큐에 대한 병렬 호출을 허용하지 않는다.

평균 발견 대기 T/2는 무슨 가정에 기대는가?

답과 이유 보기

주기 내 도착 위상이 균등하다는 가정이다.

도착이 편향되면 평균도 달라진다.

한 단계 더

두 core와 두 Rx queue를 그려 각 큐의 단일 담당자를 표시하자. pipeline으로 바꾸면 전달 ring을 추가하고, 처리량뿐 아니라 유휴 CPU 시간과 tail latency도 별도 비교 항목으로 적자. 실제 NIC 실험은 수행하지 않았다.

소단원 9.3

zero-copy·CPU 비용

복사를 줄이면 데이터를 보내는 모든 비용이 0이 될까?

준비 개념과 학습 목표

준비 개념

  • 시스템 호출은 사용자 프로그램과 커널 사이의 요청이다.
  • 입출력에는 데이터 이동과 완료 확인이 필요하다.

학습 목표

  • 복사 제거의 범위와 남는 비용을 구분한다.
  • 전송 반환·버퍼 재사용·수신 완료의 차이를 설명한다.

어느 복사를 없앴는가

zero-copy라는 말은 특정 경로에서 불필요한 CPU 복사를 피한다는 뜻으로 읽어야 한다. sendfile은 파일과 다른 descriptor 사이 전송을 커널에서 수행하여 read 후 write로 사용자 공간을 왕복하는 경로를 줄인다. 장치 이동이나 모든 메모리 접근이 없어지는 것은 아니다.

MSG_ZEROCOPY는 보내는 사용자 버퍼의 공유·page 관리와 완료 통지 비용을 추가한다. 작은 데이터에는 복사보다 이 주변 비용이 클 수 있다. 실제 커널 문서는 어느 정도 큰 쓰기에서 유리하다고 설명하지만 모든 환경의 고정 임계값으로 외우지 않는다.

버퍼를 언제 다시 쓸 수 있는가

복사 방식과 달리 버퍼를 공유하면 보내는 함수가 돌아온 뒤에도 내용이 사용 중일 수 있다. MSG_ZEROCOPY의 완료 통지는 커널의 해당 메모리 보유가 끝나 재사용할 수 있다는 신호다. 상대 응용이 데이터를 다 읽었다는 보장과는 다르다.

요청이 실제로는 복사로 처리되는 fallback도 있다. 커널 문서는 deferred copy 및 copied 표시를 설명한다. TCP/UDP의 로컬 loopback 경로도 제약이 있으므로 같은 컴퓨터의 시험만으로 복사 회피 성공이나 원격 성능을 증명하지 않는다.

부분 전송과 조건을 먼저 확인

sendfile의 성공 반환값도 요청한 전체 길이보다 작을 수 있다. 반환 바이트 수와 남은 구간을 계산하여 재시도나 종료 조건을 처리해야 한다. 파일을 socket/pipe에 전송하는 zero-copy 조건에서는 상대가 소비하기 전 원본 구간을 변경하지 않는 제약도 살펴야 한다.

복사량 절감, CPU 시간 절감, 전체 응답 시간 절감은 다른 수치다. 다음 예제는 가상의 비용 계수를 정해 비교하며 커널·메모리·네트워크 측정 결과가 아니다. 실제 채택에는 오류 처리와 버퍼 수명이 먼저 맞아야 한다.

중간 과정을 따라가는 예제

가상 비용에서 N바이트의 복사 경로 CPU 시간은 0.002Nμs, 공유 경로는 고정 관리 20μs다. 다른 비용은 같아 제외한다. N=4096과 N=65536을 비교하자. 또 10,000바이트 sendfile 요청이 6000을 반환한 뒤 다음 호출이 4000을 반환했다고 하자.

  1. 4096바이트 복사 비용은 8.192μs이므로 가상 공유 20μs가 더 크다.
  2. 65536바이트 복사 비용은 131.072μs이고 공유 20μs보다 111.072μs 크다. 같아지는 점은 0.002N=20, N=10,000바이트다.
  3. 첫 성공 반환 뒤 남은 것은 10,000−6000=4000바이트다. 두 번째 성공 후 누적 10,000으로 이 요청량의 전송 처리가 끝난다. 상대의 응용 소비 완료를 이 반환값만으로 선언하지 않는다.

가상 모형은 작은 요청에는 복사가 유리하고 큰 요청에는 공유가 유리하다. 경계 10,000바이트는 설정한 계수의 결과이며 실제 API의 보장 임계값이 아니다.

종이와 본문으로 직접 해보기

가상 공유 관리 비용을 40μs로 바꾸면 교차점은? 전송 함수는 시각2ms에 반환하고 메모리 보유 해제 통지가 시각7ms에 왔다고 하자. 시각3ms에 버퍼를 덮어도 되는가?

힌트 보기

0.002N=40을 풀고 함수 반환과 메모리 수명을 분리하자.

풀이 보기

교차점은 20,000바이트다. 시각3ms는 통지 전이므로 아직 공유 버퍼를 덮으면 안 된다. 시각7ms의 해당 완료 통지는 버퍼 재사용의 근거이며 상대가 응용에서 모두 소비했다는 증거는 아니다.

오해와 반례

zero-copy 요청이면 실제 복사도 CPU 비용도 항상 0이다.

fallback 복사가 가능하고 page 관리·통지·protocol 처리 비용이 남는다. 이 예제의 20μs도 명시적으로 남는 비용이다. 실제 전송 경로와 완료 상태를 확인해야 한다.
