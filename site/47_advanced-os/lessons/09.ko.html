소단원 9.1

배치·비동기 I/O

요청 열 개를 한꺼번에 맡기면 완료도 같은 순서일까?

준비 개념과 학습 목표

준비 개념

  • 시스템 호출은 사용자 프로그램과 커널 사이의 요청이다.

  • 입출력에는 데이터 이동과 완료 확인이 필요하다.

학습 목표

  • 요청 제출과 완료를 분리한다.

  • 배치 고정 비용과 데이터 처리 비용을 계산한다.

완료된 쓰기가 짧다면 그다음 읽기도 준비된 것일까요?

기본 독립 요청을 서로 의존하는 요청으로 바꿉니다. 파일의 구간 7000바이트를 W로 갱신한 뒤 그 구간을 R로 읽으려 합니다. W의 성공 반환이 4000바이트라고 정하면 완료했다는 사실과 요청 구간 전체를 갱신했다는 사실이 다릅니다. 실제 io_uring 실행 대신 요청 ID·구간·결과를 종이에 기록합니다.

이 단원은 기본 단발 요청만 사용하며 multishot, 성공 CQE 생략, SQPOLL, zero-copy 네트워크용 추가 완료는 사용하지 않습니다. 읽기·쓰기 payload 버퍼는 작업 완료까지 유효하게 둡니다. 제출 때만 필요한 보조 구조의 수명과 작업 진행 중 사용하는 데이터의 수명을 같은 것으로 단정하지 않습니다. 완료에는 user_data로 어느 요청의 결과인지 연결하는 과정도 필요합니다.

배치는 여러 요청의 고정 비용 나누기

작은 요청마다 같은 준비와 호출 비용을 내면 실제 데이터 처리보다 주변 작업이 커질 수 있다. 배치는 여러 요청을 한 번에 전달하여 공통 비용을 나누는 방식이다. 요청의 개수가 사라지는 것이 아니라 전달 횟수를 줄이는 관점이다.

한꺼번에 묶기 위해 기다리는 시간도 고려한다. 첫 요청이 온 뒤 묶음이 찰 때까지 기다리면 처리량은 좋아져도 첫 요청의 지연이 길어질 수 있다. 배치 크기와 최대 대기 시간을 함께 정하는 이유다.

비동기는 제출과 완료의 분리

Linux io_uring은 SQ에 요청을 넣고 CQ에서 완료 결과를 받는 구조를 제공한다. 공유 ring으로 여러 요청을 제출할 수 있다. SQPOLL 등 설정에 따라 호출 방식이 달라지므로 아래 호출 수 계산은 별도 polling이 없는 기본 제출 축소 모형이다.

일반적인 단발 요청의 완료 순서는 제출 순서와 다를 수 있다. user_data 같은 식별자로 어느 요청의 결과인지 확인해야 한다. multishot이나 성공 CQE 생략 설정은 완료 개수 규칙도 바꾸므로 여기서는 사용하지 않는다.

완료의 의미와 버퍼 수명

비동기 요청에 쓰는 읽기·쓰기 데이터 버퍼는 작업이 진행 중인 동안 유효해야 한다. 제출 함수가 돌아왔다고 즉시 버퍼를 덮으면 잘못된 데이터를 다룰 수 있다. 결과의 길이와 오류를 확인하고 필요한 나머지 작업을 결정한다.

공유 ring은 데이터 파일의 모든 바이트 복사를 자동으로 없앤다는 뜻이 아니다. 요청 전달 최적화와 실제 payload 이동을 구별한다. 의존하는 요청에는 명시적인 순서 제약 등 해당 API의 안전한 구성이 필요하다.

W의 완료를 기다리는 것만으로 전체 길이 성공은 확인되지 않습니다. 순서 제약과 요청량 검사는 따로 지킵니다.

중간 과정을 따라가는 예제

독립 요청 10개의 제출 고정 비용을 호출당 4μs, 요청별 기술 비용을 1μs로 가정하자. 완료 대기와 장치 처리 비용은 제외한다. 한 번에 최대 4개를 제출할 수 있고 배치가 이미 준비되어 있다. A·B·C를 제출한 뒤 CQ에는 B(4096), A(2048), C(−5)가 도착했다고 하자.

  1. 한 개씩 제출하면 10×4+10×1=50μs다.

  2. 4·4·2로 묶으면 제출 호출은 3회이며 3×4+10×1=22μs다. 차이는 28μs이고 50 대비 56% 감소다.

  3. 완료 식별자로 B는 4096바이트, A는 2048바이트의 결과에 대응시킨다. C의 음수 결과는 이 가상 기록의 오류이며 성공 바이트 수로 더하지 않는다.

축소 제출 비용은 50→22μs다. 완료 순서 B/A/C는 요청 식별자로 연결해야 하며 장치 전체 실행 시간이 56% 감소했다는 측정은 아니다.

조건을 바꾸어 비교하기

남은 구간을 새 요청으로 만든다

W의 첫 요청은 파일 offset 1000에서 길이 7000입니다. 4000바이트를 쓴 뒤 다음 요청의 offset과 길이를 구하세요. 다른 쓰기는 없으며 둘째 요청은 전부 성공합니다.

  1. 처리한 파일 범위는 [1000,5000)입니다.

  2. 남은 범위는 [5000,8000)이고 길이는 3000바이트입니다.

  3. 둘째 완료 3000을 확인하면 누적 7000바이트입니다.

다음 offset은 5000, 길이는 3000이며 그 성공 확인 뒤 전체 구간 읽기를 시작합니다.

비교할 점

요청을 연결해 순서만 맞춰도 첫 작업의 부분 성공을 자동 전체 성공으로 바꾸지 않습니다.

준비된 요청의 제출 고정비

독립 요청 열두 개가 이미 준비됐습니다. 제출 호출 고정비는 5 μs, 요청 기술 비용은 1 μs입니다. 한 번에 최대 다섯 개씩 제출하는 경우와 한 개씩 제출하는 경우를 비교하세요. 완료 대기·장치 처리·polling은 제외합니다.

  1. 개별 제출은 12×5+12×1=72 μs입니다.

  2. 다섯 개씩 묶으면 5+5+2의 세 호출입니다.

  3. 배치 제출 비용은 3×5+12×1=27 μs입니다.

자체 제출 비용은 72 μs에서 27 μs로 45 μs 줄어듭니다.

비교할 점

전체 I/O 시간이 그만큼 줄었다는 실제 측정이 아닙니다.

종이와 본문으로 직접 해보기

한 번에 최대 5개로 바꾸면 비용은 얼마인가? A가 4096바이트를 요청했는데 결과가 2048이면 모두 처리했다고 결론 내릴 수 있는가?

힌트 보기

제출 횟수는 올림(10/5)이고 요청 기술 비용은 그대로다.

풀이 보기

2×4+10×1=18μs다. A는 요청량보다 작은 결과이므로 그 작업의 의미에 따라 남은 2048바이트 처리나 EOF 등을 확인해야 한다. 결과만으로 전체 4096바이트 완료를 선언하지 않는다.

오해와 반례

비동기는 빠르고 제출 순서대로 무조건 완료된다.

비동기는 호출자와 완료 시점을 분리한다. 독립 요청의 완료 순서는 바뀔 수 있고 지연과 성능은 장치·큐·부하에 달린다. 이 예제는 실제 속도 측정이 아니다.

연습 1 · 값과 상태 예측

같은 열두 요청을 최대 여섯 개씩 제출하면 호출 수와 제출 비용은?

힌트 1

6+6으로 나눕니다.

힌트 2

각 요청의 기술 비용은 그대로입니다.

풀이와 답 확인

  1. 호출은 두 번입니다.

  2. 고정비 10 μs와 요청 기술 비용 12 μs를 더합니다.

두 호출이며 제출 비용은 22 μs입니다.

연습 2 · 오류 찾아 고치기

동시에 진행 중인 A와 B 모두 user_data=7을 사용했고 둘 다 같은 길이 읽기입니다. 서로 다른 버퍼를 쓰는 두 CQE가 도착했을 때 도착 순서만으로 A/B를 정한 코드를 고치세요.

힌트 1

독립 요청은 완료 순서가 달라질 수 있습니다.

힌트 2

진행 중 요청을 서로 구별할 식별자가 필요합니다.

풀이와 답 확인

  1. 같은 ID의 두 요청은 그 ID만으로 어느 버퍼의 결과인지 구별되지 않습니다.

  2. 동시에 진행 중인 요청에 고유한 ID 또는 안전한 세대 포함 식별자를 부여합니다.

  3. ID와 요청 버퍼·요청량의 연결을 완료 처리까지 유지합니다.

도착 순서를 대신할 명확한 요청별 식별 관계가 필요합니다.

먼저 제출한 A는 CQ에서도 항상 먼저다.

기본 독립 요청의 완료 순서에는 그 보장이 없습니다.

연습 3 · 직접 만들어 보기

세 단발 읽기 요청의 ID는 101,102,103이고 요청량은 각각 4096,2048,1024바이트입니다. CQ 기록은 (103,−5), (101,2048), (102,2048)입니다. 요청별 상태와 알려진 성공 바이트 합계를 구성하세요.

힌트 1

음수 res를 성공 바이트로 더하지 않습니다.

힌트 2

요청량과 성공 결과를 각각 비교합니다.

풀이와 답 확인

  1. 103은 오류이며 성공 바이트 합계에서 제외합니다.

  2. 101은 2048바이트 부분 성공이고 나머지 2048바이트 정책을 검토합니다.

  3. 102는 지정 요청량 2048바이트 성공입니다.

  4. 알려진 성공량 합계는 4096바이트입니다.

101은 부분 성공, 102는 요청량 성공, 103은 오류입니다. 성공량 합계는 4096바이트입니다.

흔한 오답에서 다시 생각하기

오류 −5를 빼서 성공량은 4091바이트다.

음수 결과는 바이트 증감값이 아닌 오류 정보입니다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

SQ에 한 번에 새로 넣을 수 있는 슬롯이 다섯 개뿐인 상태에서 열두 요청을 동시에 배열에 넣었다고 합니다. 기본 제출 비용 27 μs만으로 이 동작의 올바름도 증명했나요?

힌트 1

비용 계산과 사용 가능한 슬롯을 분리합니다.

힌트 2

실제 SQ 공간을 확인하고 API의 제출·회수 절차를 지킵니다.

풀이와 답 확인

  1. 다섯 개뿐인 공간에 열두 새 요청을 동시에 저장하면 공간 조건을 위반합니다.

  2. 사용 가능한 슬롯만 얻어 제출하고 필요한 다음 공간 확보를 확인합니다.

  3. 공간 확보 대기나 실제 완료 시간은 27 μs의 축소 비용에 포함하지 않았습니다.

제출 비용 계산은 큐 공간과 실제 API 사용의 올바름을 증명하지 않습니다.

소단원 9.2

커널 우회와 polling

알림을 기다리는 대신 계속 확인하면 공짜로 빨라질까?

준비 개념과 학습 목표

준비 개념

  • 시스템 호출은 사용자 프로그램과 커널 사이의 요청이다.

  • 입출력에는 데이터 이동과 완료 확인이 필요하다.

학습 목표

  • 전통적인 네트워크 경로와 사용자 공간 처리의 차이를 설명한다.

  • polling의 확인 비용과 대기 지연을 비교한다.

단계를 나누면 첫 패킷의 지연도 줄어들까요?

기본 polling을 실제처럼 보이는 숫자에만 기대지 않고 자체 일정으로 분석합니다. 확인 시각은 0, 8, 16, 24 μs이고 정확히 확인 시각에 도착한 패킷은 즉시 발견한다고 정합니다. 발견 대기와 패킷 처리 시간은 별도입니다. 각 주기 안의 도착 위상이 균등하지 않으면 평균 대기를 자동 T/2로 정할 수 없습니다.

다른 자체 모형에서는 수신·처리·송신 세 단계의 CPU 시간이 각각 2, 5, 1 μs입니다. pipeline은 각 단계를 전용 코어 하나가 맡고 단계마다 한 패킷씩 처리하며 전달 비용 0, 큐 공간 충분, 패킷 순서 유지로 정합니다. 실제 DPDK PMD의 기본 Rx queue는 단일 담당자가 polling하도록 구성해야 합니다. pipeline 수치만으로 같은 Rx queue의 임의 병렬 호출을 허용하지 않습니다.

  • 커널 우회와 polling

    기본 PMD의 경로와 큐 소유 규칙을 확인합니다.

  • 배치·비동기 I/O

우회하는 경로를 정확히 말하기

DPDK PMD는 사용자 공간에서 네트워크 장치의 Rx/Tx descriptor를 다루며 전통적인 커널 네트워크 데이터 경로를 우회한다. 운영체제가 아예 사라진다는 의미는 아니다. 장치와 메모리 설정, 프로그램 보호와 관리의 다른 역할은 여전히 고려한다.

기본 packet polling은 수신 알림을 기다리기보다 큐를 직접 확인한다. 링크 상태 변경 알림 같은 예외도 있으므로 모든 인터럽트가 존재하지 않는다고 단정하지 않는다. 어떤 장치·드라이버·경로를 사용했는지 밝히는 것이 중요하다.

처리 방식과 소유권

run-to-completion은 같은 core가 받아 처리하고 송신하는 방식이고 pipeline은 core 사이 ring으로 작업을 넘기는 방식이다. 분업은 가능하지만 전달 비용과 큐 관리도 필요하다. core를 추가했다는 이유만으로 선형 속도 향상을 보장하지 않는다.

PMD의 기본 lock-free 호출에는 사용 규칙이 있다. 같은 Rx queue를 여러 core가 동시에 polling하는 것으로 안전성을 가정하지 않는다. 서로 다른 큐에 대한 병렬 처리와 공유 대상을 위한 보호를 구분하며 특별한 Tx 기능의 예외를 일반 Rx 규칙에 옮기지 않는다.

확인 주기의 지연과 비용

짧은 주기로 확인하면 패킷이 온 뒤 발견하기까지의 기다림을 줄일 수 있지만 빈 큐도 자주 확인하게 된다. busy polling은 유휴 시에도 CPU 시간을 사용할 수 있어 절전이나 다른 작업과의 균형을 생각해야 한다.

아래는 일정 주기와 가상 확인 비용을 둔 종이 모형이다. 실제 DPDK loop가 고정된 주기만 사용한다는 설명이 아니다. 평균 대기 T/2는 도착 위상이 주기 안에서 균등하다는 추가 가정이 있을 때만 성립한다.

중간 과정을 따라가는 예제

가상 polling 주기는 20μs이고 한 번 확인하는 CPU 비용은 0.5μs다. 처리 비용을 제외하고 1초 동안 규칙적으로 확인한다. 패킷 도착 위상은 각 주기 안에서 균등하다고 가정한다. 비교 설정은 주기 5μs, 동일 확인 비용이다.

  1. 20μs 설정은 1,000,000/20=50,000회/초다. 확인 CPU 시간은 25,000μs=25ms로 단일 core 1초의 2.5%다.

  2. 평균 발견 대기는 20/2=10μs이며 다음 확인 직전까지의 대기는 20μs보다 작다. 확인 시점 바로 도착하는 경계는 즉시 확인하는 규칙으로 정한다.

  3. 5μs 설정은 200,000회·100ms·10%이며 평균 대기는 2.5μs다. 평균 대기 7.5μs를 줄이는 대신 확인 시간은 75ms 늘어난다.

더 짧은 가상 주기는 평균 대기를 10→2.5μs로 줄이지만 확인 비용을 2.5→10%로 늘린다. 실제 패킷 처리와 메모리 비용은 계산에 포함하지 않았다.

조건을 바꾸어 비교하기

처리량과 첫 응답을 별도로 비교한다

패킷 P1, P2, P3, P4가 모두 시각 0 μs에 준비됩니다. 표의 pipeline과 한 코어에서 패킷별 수신→처리→송신을 연속 실행하는 경우의 완료 시각을 구하세요. 다른 비용은 없습니다.

  1. 한 코어에서는 패킷마다 2+5+1=8 μs가 필요합니다. P1은 8 μs, P2는 16 μs, P3는 24 μs, P4는 32 μs에 완료됩니다.

  2. pipeline에서는 P1이 8 μs, P2가 13 μs, P3가 18 μs, P4가 23 μs에 완료됩니다.

  3. 첫 패킷의 완료는 둘 다 8 μs이고 전체 완료는 32 μs와 23 μs입니다.

pipeline은 네 패킷 전체 완료를 9 μs 줄이지만 첫 패킷은 8 μs로 같습니다.

비교할 점

추가 코어의 처리량 효과를 모든 개별 응답의 지연 감소로 단정하지 않습니다.

지정한 입력 목록의 발견 대기

P1은 1 μs, P2는 2 μs, P3는 15 μs, P4는 16 μs에 도착합니다. 확인 시각은 0 μs, 8 μs, 16 μs, 24 μs입니다. 각 발견 대기와 네 패킷 평균을 구하세요.

  1. P1과 P2는 시각 8 μs에 발견되어 각각 7 μs와 6 μs 기다립니다.

  2. P3는 시각 16 μs에 발견되어 1 μs 기다립니다.

  3. P4는 경계 규칙에 따라 시각 16 μs에 즉시 발견되므로 대기는 0 μs입니다.

  4. 평균은 (7+6+1+0)/4=3.5 μs입니다.

이 입력의 평균 발견 대기는 3.5 μs입니다.

비교할 점

주기 절반인 4 μs는 균등 위상 가정의 평균이지 모든 유한 입력의 평균은 아닙니다.

커널 우회와 polling이면 CPU 비용도 없어지고 모든 큐를 아무 core나 만져도 된다.

  • 전송 반환·버퍼 재사용·수신 완료의 차이를 설명한다.

복사 회피 완료 통지는 바이트 수를 세나요, 호출을 세나요?

기본 비용 모형을 페이지 관리와 fallback까지 확장합니다. 자체 비용에서 복사는 바이트당 0.003 μs이고 공유 경로는 고정 비용 12 μs에 4 KiB 페이지당 1 μs를 더합니다. 버퍼는 페이지 정렬이고 크기는 페이지의 정수 배수이며 다른 비용은 제외합니다. 이 계수는 실제 커널의 임계값이 아닙니다.

실제 MSG_ZEROCOPY 통지는 해당 소켓에서 데이터를 성공적으로 보낸 호출의 32비트 ID를 다룹니다. 실패나 길이 0은 카운터를 늘리지 않으며 통지 범위 [ee_info, ee_data]의 양끝을 포함합니다. 아래는 wrap이 없는 범위이고 다른 스레드의 호출은 없습니다. 통지는 메모리 보유 해제의 근거이며 전송 또는 원격 응용 소비 완료와 같지 않습니다. 실제 송신·커널·NIC 실행은 수행하지 않았습니다.

어느 복사를 없앴는가

zero-copy라는 말은 특정 경로에서 불필요한 CPU 복사를 피한다는 뜻으로 읽어야 한다. sendfile은 파일과 다른 descriptor 사이 전송을 커널에서 수행하여 read 후 write로 사용자 공간을 왕복하는 경로를 줄인다. 장치 이동이나 모든 메모리 접근이 없어지는 것은 아니다.

MSG_ZEROCOPY는 보내는 사용자 버퍼의 공유·page 관리와 완료 통지 비용을 추가한다. 작은 데이터에는 복사보다 이 주변 비용이 클 수 있다. 실제 커널 문서는 어느 정도 큰 쓰기에서 유리하다고 설명하지만 모든 환경의 고정 임계값으로 외우지 않는다.

버퍼를 언제 다시 쓸 수 있는가

복사 방식과 달리 버퍼를 공유하면 보내는 함수가 돌아온 뒤에도 내용이 사용 중일 수 있다. MSG_ZEROCOPY의 완료 통지는 커널의 해당 메모리 보유가 끝나 재사용할 수 있다는 신호다. 상대 응용이 데이터를 다 읽었다는 보장과는 다르다.

요청이 실제로는 복사로 처리되는 fallback도 있다. 커널 문서는 deferred copy 및 copied 표시를 설명한다. TCP/UDP의 로컬 loopback 경로도 제약이 있으므로 같은 컴퓨터의 시험만으로 복사 회피 성공이나 원격 성능을 증명하지 않는다.

부분 전송과 조건을 먼저 확인

sendfile의 성공 반환값도 요청한 전체 길이보다 작을 수 있다. 반환 바이트 수와 남은 구간을 계산하여 재시도나 종료 조건을 처리해야 한다. 파일을 socket/pipe에 전송하는 zero-copy 조건에서는 상대가 소비하기 전 원본 구간을 변경하지 않는 제약도 살펴야 한다.

복사량 절감, CPU 시간 절감, 전체 응답 시간 절감은 다른 수치다. 다음 예제는 가상의 비용 계수를 정해 비교하며 커널·메모리·네트워크 측정 결과가 아니다. 실제 채택에는 오류 처리와 버퍼 수명이 먼저 맞아야 한다.

중간 과정을 따라가는 예제

가상 비용에서 N바이트의 복사 경로 CPU 시간은 0.002Nμs, 공유 경로는 고정 관리 20μs다. 다른 비용은 같아 제외한다. N=4096과 N=65536을 비교하자. 또 10,000바이트 sendfile 요청이 6000을 반환한 뒤 다음 호출이 4000을 반환했다고 하자.

  1. 4096바이트 복사 비용은 8.192μs이므로 가상 공유 20μs가 더 크다.

  2. 65536바이트 복사 비용은 131.072μs이고 공유 20μs보다 111.072μs 크다. 같아지는 점은 0.002N=20, N=10,000바이트다.

  3. 첫 성공 반환 뒤 남은 것은 10,000−6000=4000바이트다. 두 번째 성공 후 누적 10,000으로 이 요청량의 전송 처리가 끝난다. 상대의 응용 소비 완료를 이 반환값만으로 선언하지 않는다.

가상 모형은 작은 요청에는 복사가 유리하고 큰 요청에는 공유가 유리하다. 경계 10,000바이트는 설정한 계수의 결과이며 실제 API의 보장 임계값이 아니다.

조건을 바꾸어 비교하기

페이지 관리와 fallback의 비용

4096바이트와 16384바이트에 자체 복사·공유 비용을 구하세요. 별도 fallback은 공유 준비 비용을 이미 지불한 뒤 동일 복사 비용까지 더한다고 정합니다.

  1. 4096바이트 복사는 12.288 μs, 공유는 12+1=13 μs입니다.

  2. 16384바이트 복사는 49.152 μs, 공유는 12+4=16 μs입니다.

  3. 16384바이트 fallback의 자체 비용은 16+49.152=65.152 μs입니다.

작은 버퍼는 지정 모형에서 복사가 유리하고 큰 버퍼는 성공적인 공유가 유리합니다. fallback 비용은 65.152 μs입니다.

비교할 점

fallback의 실제 비용을 언제나 이 합계라고 단정하지 않습니다. 덧셈은 별도로 지정한 자체 가정입니다.

묶인 완료 범위와 재사용 가능한 구간

표의 모든 호출 뒤 통지 [1,2]만 받았습니다. 어느 요청의 메모리를 재사용할 근거가 있고 아직 남은 ID는 무엇인가요? 상대의 소비 상태는 알려 주지 않았습니다.

  1. 양끝을 포함하여 ID 1과 2가 해제되었습니다.

  2. D의 8000바이트와 E의 첫 성공 구간 2000바이트는 해당 보유가 끝났습니다.

  3. ID 0의 A와 ID 3의 나머지 구간은 아직 통지되지 않았습니다.

통지 범위는 두 성공 호출입니다. D와 E의 앞 2000바이트 구간에 대한 보유는 끝났습니다. A와 E의 나머지 구간은 통지 확인 전 재사용하지 않습니다. E 전체 버퍼를 해제하거나 덮어쓰지 않습니다. 원격 소비 여부는 미상입니다.

비교할 점

E 첫 구간의 통지가 나머지 구간의 보유까지 자동 해제하지 않습니다.
