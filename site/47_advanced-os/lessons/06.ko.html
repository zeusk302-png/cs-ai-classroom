소단원 6.1

NUMA·huge page·TLB

메모리는 모두 같은 거리일까? 주소 변환 캐시 한 칸은 몇 바이트를 담당할까?

준비 개념과 학습 목표

준비 개념

  • 가상 주소는 페이지별로 물리 메모리에 대응한다. TLB는 주소 변환 결과의 캐시다.

  • NUMA 노드는 CPU와 가까운 메모리를 묶은 단위로 원격 접근 비용이 다를 수 있다.

학습 목표

  • 배치와 주소 변환 캐시의 서로 다른 병목을 구별한다.

  • 가상 노드 지연과 TLB coverage를 계산한다.

페이지를 어디에 둘까

NUMA에서는 작업이 실행되는 CPU 노드와 데이터가 할당된 메모리 노드가 다를 수 있다. preferred는 특정 노드를 먼저 시도하고 실패하면 다른 노드를 고려하며 bind는 허용 노드를 제한한다. interleave는 페이지를 여러 노드로 분산한다.

정책은 범위에 따라 task/VMA/shared에 적용된다. 기존에 fault가 난 페이지는 정책만 바꾼다고 자동으로 모두 옮겨지지 않는다. 실제 migration과 CPU 배치/ 공유 접근 패턴을 같이 보아야 한다. 이 본문의 노드 수와 지연은 실제 하드웨어 측정 값이 아니다.

변환을 더 넓게 캐시한다

TLB entry가 4KiB를 매핑하고 64 칸이라면 단순 coverage는 256KiB다. 한 entry가 2MiB를 매핑하면 128MiB다. 실제 CPU는 페이지 크기별 entry 수/ 연관도/ 계층이 다르므로 같은 64라는 가정에서만 이 비율을 쓴다.

huge page는 변환 캐시 miss/ 초기 fault 수를 줄일 수 있다. 하지만 큰 페이지 초기화/ 연속 공간 확보의 비용이 늘고,2MiB 영역에서 1바이트만 쓰면 4KiB보다 불필요한 공간을 많이 차지할 수 있다. 모든 프로그램에서 성능 향상을 보장하지 않는다.

병목을 나누어 읽는다

지역/ 원격 메모리 지연과 TLB miss는 분리된 사건이다. TLB에 주소가 있어도 원격 메모리를 읽는 비용은 남는다. 큰 페이지를 쓴다고 데이터가 자동으로 가까운 노드로 옮겨지는 것도 아니다.

평균 접근 지연 모형을 local 비율 r와 지연 L,R로 rL +(1 −r)R라 둔다. 캐시 miss/ 대기열/ 병렬성/ 페이지 walk는 빼고 NUMA 비중만 계산한다. 모형 결과를 실제 실행 속도 향상률이라고 보고하지 않는다.

중간 과정을 따라가는 예제

local 80ns/remote 140ns,local 비중.75 인 자체 모형의 평균 지연을 구하라. 같은 64 TLB entry의 4KiB/2MiB coverage도 구하라.

  1. 평균 =.75×80 +.25×140 =60 +35 =95ns다.

  2. 64×4KiB =256KiB다.

  3. 64×2MiB =128MiB다.

  4. 비율 2MiB/4KiB =512다.

가상 평균 95ns,coverage 256KiB/128MiB로 512 배다. 실제 CPU entry 수가 같다는 보장은 없다.

힌트 보기

풀이 보기

소단원 6.2

메모리 회수·zero-copy

안 쓰는 페이지를 돌려 받는 일과 데이터 복사를 줄이는 일은 왜 별개일까?

준비 개념과 학습 목표

준비 개념

  • page cache는 파일 데이터의 메모리 복사다. dirty 페이지는 디스크와 내용이 다르다.

  • 참조/ 핀은 페이지가 사용 중임을 나타내며 임의 재사용하면 안 된다.

학습 목표

  • 회수 가능 조건과 복사 절감의 조건을 분리한다.

  • short transfer와 남은 바이트를 추적한다.

회수에는 보존할 정보가 있다

clean file cache는 필요 시 파일에서 다시 읽을 수 있어 버릴 수 있는 후보다. dirty cache는 변경분을 보존하려면 writeback 등을 먼저 고려한다. 익명 메모리는 파일의 동일 복사가 아니므로 swap/ 압축/ 다른 정책 없이 살아 있는 내용을 그냥 버릴 수 없다.

물리 메모리가 부족하면 background 회수 작업과 할당자가 직접 회수하는 경로가 있다. direct reclaim은 할당 요청의 지연을 늘릴 수 있다. 특정 페이지가 핀 되어 있으면 회수/ 이동이 제한되므로 총 사용량만으로 즉시 회수 가능량을 판단하지 않는다.

사용자 공간 왕복을 줄인다

read 후 write 모형은 커널 파일 cache →사용자 버퍼 →커널 출력으로 두 번의 사용자 공간 경계를 넘는다. sendfile은 커널 안에서 입력 fd에서 출력 fd로 전송하여 그 왕복을 줄이는 API다. zero-copy라는 말은 어느 경계의 복사를 줄였는지 명시해야 한다.

커널 내부 복사·장치 DMA·암호화·프로토콜 처리는 여전히 필요할 수 있다. 앱 버퍼 복사 제거가 전체 비용 0이나 즉시 완료를 뜻하지 않는다. 지원 조건과 파일 내용의 수명/ 수정 제약은 API마다 확인한다.

전송의 완료를 세어야 한다

sendfile 성공 반환 값은 실제 전송 바이트 수이며 요청보다 작을 수 있다. 남은 양과 offset을 갱신하고 재호출할 수 있도록 설계한다. EAGAIN은 비차단 출력이 현재 진행 불가라는 뜻이며 무한 busy-loop로 해결되는 것이 아니다.

socket/pipe의 zero-copy 지원 경로에서는 상대가 데이터를 소비할 때까지 해당 파일 영역을 수정하지 말아야 하는 조건이 있다. 조기 free/ 재사용은 복사 절감의 대가로 추가된 수명 책임을 위반한다. 여기서는 호출을 실행하지 않고 반환 수열만 종이 추적한다.

중간 과정을 따라가는 예제

파일 10000바이트 전송에서 가상 sendfile 반환이 4096,4096,1808이다. 시작 offset0, 각 반환은 성공이고 EAGAIN은 없다. 남은 양/offset을 추적하라.

  1. 첫 반환 후 offset 4096,remaining 5904다.

  2. 둘째 후 offset8192,remaining1808이다.

  3. 셋째 후 offset10000,remaining0이다.

  4. 4096 +4096 +1808 =10000으로 완료를 확인한다.

세 성공 호출의 총 전송 10000바이트다. 첫 성공만으로 전체 완료라고 하지 않는다.

종이와 본문으로 직접 해보기

두 번째 시도 EAGAIN 뒤 4096,1808이 반환되면 누적 전송 수는? EAGAIN에서 offset/remaining을 바꿀까?

힌트 보기

오류 시 전송 수 −1을 바이트 수로 더하지 않는다.

풀이 보기

첫 4096 뒤 5904 남고 EAGAIN에서는 성공 전송량을 늘리지 않는다. 진행 가능 상태를 기다린 후 4096/1808을 더해 총 10000이다. errno 처리와 대기는 모형의 설계 책임이다.

오해와 반례

zero-copy 니까 버퍼와 파일을 즉시 바꿔도 되고 회수 가능 메모리는 늘기만 한다.

전송 영역 수명 조건 때문에 사용 중 페이지가 더 오래 유지될 수 있다. 복사량 감소와 회수 가능성은 같은 방향으로 항상 움직이지 않는다.

소단원 6.3

할당 정책과 지연

평균 할당 시간이 작으면 마감이 있는 작업에도 충분할까?

준비 개념과 학습 목표

준비 개념

  • 가상 연속은 프로그램 주소가 이어지는 것, 물리 연속은 실제 페이지가 이어지는 것이다.

  • 백분위는 정렬한 표본에서 정한 순위의 값이며 정의가 여럿이다.

학습 목표

  • 빠른 경로와 회수/ 실패 경로의 조건을 구별한다.

  • 내부 단편화와 꼬리 지연을 자체 표본으로 계산한다.

요청 크기와 공간 모양

작은 객체 여러 개는 slab 같은 크기별 캐시로 재사용할 수 있다. 페이지는 buddy 등의 정책으로 관리할 수 있으며 요청 크기/ 정렬이 반올림을 일으킨다. 여기서는 버킷16/32/64바이트의 자체 할당기 모형을 쓴다.

kmalloc과 vmalloc은 인터페이스의 연속성 조건이 다르다. vmalloc은 가상으로 연속이지만 물리 연속을 보장하지 않는다. DMA처럼 물리 조건이 필요한 요청에 가상 주소가 이어진다는 것만으로 충분하다고 하지 않는다.

기다림을 허용할까

GFP_KERNEL은 메모리 압박에서 direct reclaim 등으로 잠들 수 있는 경로를 허용한다. 호출 문맥이 sleep 가능해야 한다. NOWAIT처럼 direct reclaim을 피하는 정책은 빠른 실패 가능성이 있으므로 실패 처리가 필요하다. 이는 실제 커널 코드를 실행한 결과가 아닌 공식 규약의 설명이다.

미리 풀을 준비하면 임계 경로의 할당을 줄일 수 있지만 풀 용량/ 초과 요청/ 수명오류를 관리해야 한다. 미리 할당한 것을 아직 사용 중인데 반환하면 use-after-free가 생기고, 무한대 풀을 가정하면 메모리 예산을 무시한다.

평균과 꼬리를 함께 본다

99개 요청이 1 μs, 한 개가 101 μs이면 평균은 2 μs다. 빠른 경로가 대부분이라 평균만 보면 마감 10 μs를 넘는 요청이 숨겨진다. 이 표본의 최대 101을 장차 모든 실행의 최악 상한이라고 증명할 수도 없다.

여기서는 nearest-rank percentile을 사용한다. 표본 100개에서 p99는 ceil(.99×100)=99번째, p100은 100번째다. 이 정의에서 p99 =1,p100 =101이다. 보간 정의를 쓰면 다른 값이 가능하므로 보고 시 정의를 적는다.

중간 과정을 따라가는 예제

크기13/17/33바이트 객체를 각 1 개 버킷16/32/64에 배정한다. 요청합/ 배정합/ 내부낭비를 구하라.99개 1 μs와 1개 101 μs 표본의 평균도 구하라.

  1. 요청 13 +17 +33 =63 바이트다.

  2. 배정 16 +32 +64 =112 바이트다.

  3. 낭비 3 +15 +31 =49 바이트다.

  4. 평균(99 +101)/100 =2 μs다.

내부 낭비 49바이트, 배정 대비49/112=43.75 %, 평균 2 μs다.

종이와 본문으로 직접 해보기

같은 표본의 nearest-rank p95/p99/p100과 10 μs 마감 초과율은?

힌트 보기

정렬 후95/99번째는 빠른 99개 안이다.

풀이 보기

p95 =1,p99 =1,p100 =101 μs다. 마감 초과1/100=1 %다. p99가 작아도 모든 요청이 10 이하라는 보장은 없다.

오해와 반례

비차단 할당은 반드시 성공하며 지연 상한을 제공한다.

메모리 부족에서 실패할 수 있다. 잠들지 않는 것과 정해진 시간 내 성공을 보장하는 것은 별개며 실패/ 재시도/ 풀 고갈 규칙이 필요하다.
