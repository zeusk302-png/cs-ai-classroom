소단원 6.1

NUMA·huge page·TLB

메모리는 모두 같은 거리일까? 주소 변환 캐시 한 칸은 몇 바이트를 담당할까?

준비 개념과 학습 목표

준비 개념

  • 가상 주소는 페이지별로 물리 메모리에 대응한다. TLB는 주소 변환 결과의 캐시다.

  • NUMA 노드는 CPU와 가까운 메모리를 묶은 단위로 원격 접근 비용이 다를 수 있다.

학습 목표

  • 배치와 주소 변환 캐시의 서로 다른 병목을 구별한다.

  • 가상 노드 지연과 TLB coverage를 계산한다.

페이지는 커졌는데 실제 사용 메모리도 그대로일까요?

기본 TLB coverage 계산을 다른 entry 수와 희소 접근으로 확장합니다. TLB는 가상 주소의 변환을 기억하는 캐시이며 coverage는 entry 수와 한 entry의 페이지 크기를 곱한 단순 도달 범위입니다. 여기서는 페이지별 계층·연관도·충돌을 제외한 종이 모형이고 실제 CPU 사양을 뜻하지 않습니다.

새 모형은 4 KiB 페이지 TLB 64칸, 2 MiB 페이지 TLB 16칸입니다. sparse 사례에서는 서로 다른 2 MiB 정렬 영역 여덟 개에서 각각 한 바이트만 쓰며, 각 영역에는 전용 4 KiB 또는 2 MiB 페이지 하나가 실제로 배정된다고 정합니다. 공유 zero page·압축·회수·THP 분할은 이 비교에서 제외합니다. KiB=1024바이트, MiB=1024 KiB입니다.

먼저 확인할 개념
  • NUMA·huge page·TLB

    변환 범위와 메모리 노드 거리를 따로 봅니다.

  • 할당 정책과 지연

    큰 페이지 공간 비용과 할당 실패 가능성을 연결합니다.

페이지를 어디에 둘까

NUMA에서는 작업이 실행되는 CPU 노드와 데이터가 할당된 메모리 노드가 다를 수 있다. preferred는 특정 노드를 먼저 시도하고 실패하면 다른 노드를 고려하며 bind는 허용 노드를 제한한다. interleave는 페이지를 여러 노드로 분산한다.

정책은 범위에 따라 task/VMA/shared에 적용된다. 기존에 fault가 난 페이지는 정책만 바꾼다고 자동으로 모두 옮겨지지 않는다. 실제 migration과 CPU 배치/ 공유 접근 패턴을 같이 보아야 한다. 이 본문의 노드 수와 지연은 실제 하드웨어 측정 값이 아니다.

변환을 더 넓게 캐시한다

TLB entry가 4KiB를 매핑하고 64 칸이라면 단순 coverage는 256KiB다. 한 entry가 2MiB를 매핑하면 128MiB다. 실제 CPU는 페이지 크기별 entry 수/ 연관도/ 계층이 다르므로 같은 64라는 가정에서만 이 비율을 쓴다.

huge page는 변환 캐시 miss/ 초기 fault 수를 줄일 수 있다. 하지만 큰 페이지 초기화/ 연속 공간 확보의 비용이 늘고,2MiB 영역에서 1바이트만 쓰면 4KiB보다 불필요한 공간을 많이 차지할 수 있다. 모든 프로그램에서 성능 향상을 보장하지 않는다.

병목을 나누어 읽는다

지역/ 원격 메모리 지연과 TLB miss는 분리된 사건이다. TLB에 주소가 있어도 원격 메모리를 읽는 비용은 남는다. 큰 페이지를 쓴다고 데이터가 자동으로 가까운 노드로 옮겨지는 것도 아니다.

평균 접근 지연 모형을 local 비율 r와 지연 L,R로 rL +(1 −r)R라 둔다. 캐시 miss/ 대기열/ 병렬성/ 페이지 walk는 빼고 NUMA 비중만 계산한다. 모형 결과를 실제 실행 속도 향상률이라고 보고하지 않는다.

페이지 크기와 entry 수가 동시에 다른 모형
페이지TLB entry 수단순 coverage

coverage 비율은 (16×2048)/(64×4)=128입니다. 페이지 크기 비율 512만으로 두 TLB 전체 범위의 비율을 정하지 않습니다.

중간 과정을 따라가는 예제

local 80ns/remote 140ns,local 비중.75 인 자체 모형의 평균 지연을 구하라. 같은 64 TLB entry의 4KiB/2MiB coverage도 구하라.

  1. 평균 =.75×80 +.25×140 =60 +35 =95ns다.

  2. 64×4KiB =256KiB다.

  3. 64×2MiB =128MiB다.

  4. 비율 2MiB/4KiB =512다.

가상 평균 95ns,coverage 256KiB/128MiB로 512 배다. 실제 CPU entry 수가 같다는 보장은 없다.

조건을 바꾸어 비교하기

희소 쓰기의 공간 비용

여덟 영역에서 한 바이트씩만 쓰는 모형의 작은 페이지와 큰 페이지 배정량, 유용한 바이트 대비 배정 비율을 계산하세요.

  1. 작은 페이지는 8×4096=32768바이트, 즉 32 KiB입니다.

  2. 큰 페이지는 8×2097152=16777216바이트, 즉 16 MiB입니다.

  3. 유용한 데이터는 8바이트라 배정/유용 비율은 각각 4096과 2097152입니다.

큰 페이지 배정량은 작은 페이지의 512배입니다.

비교할 점

TLB coverage가 넓어진 이점과 실제 사용하는 데이터 대비 공간 비용은 별도 평가합니다.

같은 페이지를 다른 CPU가 읽기

두 NUMA 노드에 열 개 페이지를 5개씩 배치합니다. CPU0의 노드0 접근은 70 ns, 노드1 접근은 150 ns이고 각 페이지 접근 횟수는 같습니다. CPU0 혼자 전부 읽는 경우와 CPU0/CPU1이 각자 자기 노드의 5개만 읽는 경우를 비교하세요. CPU1의 자기 노드 지연도 70 ns이고 다른 비용은 제외합니다.

  1. CPU0 혼자면 local 비중 1/2입니다. 평균 (70+150)/2=110 ns입니다.

  2. 각자 자기 노드만 읽으면 각 접근은 70 ns입니다.

  3. 두 경우의 총 접근 수를 같게 유지한 접근당 지연 비교입니다.

접근당 가상 평균 110 ns 대 70 ns입니다.

비교할 점

작업의 전체 완료 시간은 병렬성·동기화 등을 더 알아야 하므로 110/70을 실측 speedup이라고 하지 않습니다.

힌트 보기

풀이 보기

연습 1 · 값과 상태 예측

표의 두 TLB에서 작은 페이지 entry를 128개로만 늘립니다. 두 coverage와 큰/작은 비율은?

힌트 1

작은 coverage만 두 배가 됩니다.

힌트 2

32 MiB를 KiB로 바꾸어 나눕니다.

풀이와 답 확인

  1. 작은 coverage는 128×4=512 KiB입니다.

  2. 큰 coverage는 32768 KiB라 32768/512=64입니다.

512 KiB와 32 MiB, 비율 64입니다.

흔한 오답에서 다시 생각하기

페이지 크기 비율 512이므로 답도 512다.

entry 수가 서로 다르므로 전체 범위 비율은 두 곱의 비율입니다.

연습 2 · 오류 찾아 고치기

CPU0가 원격 노드1에 있는 데이터를 계속 읽습니다. 4 KiB를 2 MiB 매핑으로 바꾸었다는 사실만으로 원격 접근 지연 150 ns가 local 70 ns가 됐다는 주장을 고치세요.

힌트 1

매핑의 크기와 데이터의 물리 노드가 별개입니다.

힌트 2

이 변경에는 데이터 이동이나 CPU 이동이 없습니다.

풀이와 답 확인

  1. 주소 변환 조건은 바뀔 수 있습니다.

  2. 데이터는 여전히 노드1에 있어 이 모형의 메모리 접근은 150 ns입니다.

원격 노드 접근은 남습니다. TLB 효과와 NUMA 효과를 분리합니다.

흔한 오답에서 다시 생각하기

변환 entry 하나가 커지면 데이터가 CPU 가까이 온다.

TLB는 주소 변환 정보를 기억하며 데이터 배치를 자동 이동시키지 않습니다.

연습 3 · 직접 만들어 보기

열 페이지 배치 예제에서 CPU0만 모든 페이지를 읽어야 합니다. 노드0에 충분한 공간이 있고 이동 뒤 다른 접근자가 없다는 모형에서 평균 70 ns를 만들 배치를 쓰세요.

힌트 1

작업을 둘로 나눌 수 없으므로 데이터 배치를 바꿉니다.

힌트 2

이미 배정된 페이지의 정책만 바꾸는 것과 실제 이동은 다릅니다.

풀이와 답 확인

  1. 노드1의 5개를 실제로 노드0로 이동해 열 개를 노드0에 둡니다.

  2. 그 뒤 CPU0의 local 비중은 1입니다.

이동이 완료된 뒤 접근당 70 ns입니다. 이동 비용과 실패는 별도로 평가합니다.

흔한 오답에서 다시 생각하기

preferred 정책만 설정하면 과거 페이지도 전부 즉시 옮겨진다.

정책 변경만으로 이미 fault된 페이지 전부의 이동을 증명하지 않습니다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

이동 전 반복 한 회의 비용이 11 ms, 이동 뒤 7 ms이고 일회성 이동 비용 10 ms라고 새로 정합니다. k회 전체 비용을 비교하고 처음 유리한 정수 k를 구하세요.

힌트 1

이동하지 않으면 11k입니다.

힌트 2

이동은 한 번만 비용 10을 냅니다.

풀이와 답 확인

  1. 이동 안은 10+7k ms입니다.

  2. 10+7k<11k이면 k>2.5입니다.

처음 유리한 k=3이며 비용 31 ms 대 33 ms입니다.

흔한 오답에서 다시 생각하기

한 회가 빨라졌으니 k=1부터 항상 유리하다.

k=1에서는 이동 안 17 ms 대 기존 11 ms로 더 느립니다. 반복 이익이 일회성 비용을 상쇄해야 합니다.

소단원 6.2

메모리 회수·zero-copy

안 쓰는 페이지를 돌려 받는 일과 데이터 복사를 줄이는 일은 왜 별개일까?

준비 개념과 학습 목표

준비 개념

  • page cache는 파일 데이터의 메모리 복사다. dirty 페이지는 디스크와 내용이 다르다.

  • 참조/ 핀은 페이지가 사용 중임을 나타내며 임의 재사용하면 안 된다.

학습 목표

  • 회수 가능 조건과 복사 절감의 조건을 분리한다.

  • short transfer와 남은 바이트를 추적한다.

전송이 끝났다는 반환과 파일을 다시 써도 된다는 시점이 같을까요?

기본 10000바이트 전송에 더해, 시작 위치가 500인 별도 6000바이트 구간을 추적합니다. 아래 반환값은 직접 호출한 기록이 아니라 성공·EAGAIN·EOF를 지정한 종이 사건입니다. 명시적 offset 변수를 전달하면 그 변수가 바뀌며 입력 fd 자체의 현재 위치와 구분해야 합니다.

회수 모형은 지금 버릴 수 있는 clean cache, writeback 뒤 가능한 dirty cache, 핀 때문에 유지할 페이지를 나눕니다. 실제 Linux 회수 정책 전체를 구현했다는 뜻은 아닙니다. sendfile은 사용자 공간 왕복을 줄이는 API이며 상대가 소비할 때까지 파일 구간 수정 금지가 필요한 경로를 따로 확인합니다.

먼저 확인할 개념
  • 메모리 회수·zero-copy

회수에는 보존할 정보가 있다

clean file cache는 필요 시 파일에서 다시 읽을 수 있어 버릴 수 있는 후보다. dirty cache는 변경분을 보존하려면 writeback 등을 먼저 고려한다. 익명 메모리는 파일의 동일 복사가 아니므로 swap/ 압축/ 다른 정책 없이 살아 있는 내용을 그냥 버릴 수 없다.

물리 메모리가 부족하면 background 회수 작업과 할당자가 직접 회수하는 경로가 있다. direct reclaim은 할당 요청의 지연을 늘릴 수 있다. 특정 페이지가 핀 되어 있으면 회수/ 이동이 제한되므로 총 사용량만으로 즉시 회수 가능량을 판단하지 않는다.

사용자 공간 왕복을 줄인다

read 후 write 모형은 커널 파일 cache →사용자 버퍼 →커널 출력으로 두 번의 사용자 공간 경계를 넘는다. sendfile은 커널 안에서 입력 fd에서 출력 fd로 전송하여 그 왕복을 줄이는 API다. zero-copy라는 말은 어느 경계의 복사를 줄였는지 명시해야 한다.

커널 내부 복사·장치 DMA·암호화·프로토콜 처리는 여전히 필요할 수 있다. 앱 버퍼 복사 제거가 전체 비용 0이나 즉시 완료를 뜻하지 않는다. 지원 조건과 파일 내용의 수명/ 수정 제약은 API마다 확인한다.

전송의 완료를 세어야 한다

sendfile 성공 반환 값은 실제 전송 바이트 수이며 요청보다 작을 수 있다. 남은 양과 offset을 갱신하고 재호출할 수 있도록 설계한다. EAGAIN은 비차단 출력이 현재 진행 불가라는 뜻이며 무한 busy-loop로 해결되는 것이 아니다.

socket/pipe의 zero-copy 지원 경로에서는 상대가 데이터를 소비할 때까지 해당 파일 영역을 수정하지 말아야 하는 조건이 있다. 조기 free/ 재사용은 복사 절감의 대가로 추가된 수명 책임을 위반한다. 여기서는 호출을 실행하지 않고 반환 수열만 종이 추적한다.

조건을 바꾸어 비교하기

fd 위치와 명시적 offset

표에서 입력 fd의 현재 위치는 처음 99이고, 별도 offset=500을 전달하며 이외 위치 변경은 없습니다. 마지막 두 위치와 총 전송량을 쓰세요.

  1. 성공 반환 합은 2048+1024+2928=6000입니다.

  2. 명시적 offset은 500+6000=6500입니다.

  3. 명시적 offset 사용은 입력 fd 자체 위치를 변경하지 않습니다.

명시적으로 전달한 offset의 최종 값은 6500입니다. 입력 fd 자체의 현재 위치는 99로 유지되며, 실제로 전송한 양은 총 6000바이트입니다.

비교할 점

fd 위치도 6500이라고 덮어쓰면 별도 위치와 공유 파일 위치를 혼동합니다.

회수 후보와 실제 확보량

배타적인 페이지 집합에 clean/unpinned 6개, dirty/unpinned 3개, clean/pinned 2개, live anonymous/no swap 4개가 있습니다. 이 종이 정책에서는 첫 집합만 즉시 버리고 dirty는 writeback 완료 뒤 버리며 나머지는 유지합니다. 지금 8개가 필요하면 부족량과 dirty 중 2개 writeback 완료 뒤 확보량은?

  1. 지금 즉시 후보는 6개라 8−6=2개 부족합니다.

  2. dirty 2개 writeback 후에는 이 모형에서 추가2개를 버릴 수 있습니다.

  3. 핀2개와 살아 있는 anonymous4개는 유지합니다.

지금 확보할 수 있는 페이지는 6개이므로 요청한 8개보다 2개 부족합니다. 지정한 dirty 페이지 2개의 writeback이 끝나면 총 8개를 확보할 수 있습니다.

비교할 점

전체15개를 모두 즉시 회수 가능하다고 세지 않습니다. 실제 회수의 추가 조건은 이 단순 정책 밖입니다.

오해와 반례

zero-copy 니까 버퍼와 파일을 즉시 바꿔도 되고 회수 가능 메모리는 늘기만 한다.

연습 1 · 값과 상태 예측

6000바이트 모형에서 첫 성공 2048 다음 성공 1024 직후 EOF 반환 0입니다. 원래 구간을 다 보냈나요? 파일이 더 늘어나지 않는 조건의 누적량과 미전송량은?

힌트 1

0은 오류 −1과 다릅니다.

힌트 2

지정 구간은 6000바이트입니다.

풀이와 답 확인

  1. 누적량은 3072입니다.

  2. 미전송량은 6000−3072=2928입니다.

  3. EOF 후 원래 구간 전체 완료로 보고하지 않습니다.

실제로 전송한 양은 3072바이트이고, 원래 요청 구간에서 보내지 못한 양은 2928바이트입니다. EOF를 전체 전송 완료와 구분해서 처리합니다.

흔한 오답에서 다시 생각하기

0은 성공이니 남은 양을 0으로 만든다.

반환0은 요청한 남은 바이트를 실제로 모두 전송했다는 의미가 아닙니다.

준비 개념과 학습 목표

준비 개념

  • 가상 연속은 프로그램 주소가 이어지는 것, 물리 연속은 실제 페이지가 이어지는 것이다.

  • 백분위는 정렬한 표본에서 정한 순위의 값이며 정의가 여럿이다.

학습 목표

  • 빠른 경로와 회수/ 실패 경로의 조건을 구별한다.

  • 내부 단편화와 꼬리 지연을 자체 표본으로 계산한다.

빈 페이지 네 개가 있으면 두 페이지 연속 요청 두 번도 성공할까요?

기본 버킷과 평균 지연에서 공간의 모양 및 풀 고갈로 확장합니다. 새 물리 페이지 모형은 번호가 0부터 7까지이며, 빈 페이지는 0번, 2번, 4번, 6번입니다. 나머지 페이지는 할당 중입니다. 페이지를 이동하지 않으면 두 개의 연속 페이지를 요구하는 요청을 만족하지 못합니다. 실제 Linux buddy의 모든 정렬·zone 규칙을 모델링하지 않습니다.

풀 예제는 미리 만든 객체 세 개를 배타적으로 빌려주며 사용자가 반환할 때까지 재사용하지 않습니다. 무기한 성공이나 지연 상한을 주장하지 않습니다. 별도 지연 표본은 97개가 1 μs, 세 개가 101 μs이고 nearest-rank는 정렬 표본의 ceil(p×100)번째 값입니다.

요청 크기와 공간 모양

작은 객체 여러 개는 slab 같은 크기별 캐시로 재사용할 수 있다. 페이지는 buddy 등의 정책으로 관리할 수 있으며 요청 크기/ 정렬이 반올림을 일으킨다. 여기서는 버킷16/32/64바이트의 자체 할당기 모형을 쓴다.

kmalloc과 vmalloc은 인터페이스의 연속성 조건이 다르다. vmalloc은 가상으로 연속이지만 물리 연속을 보장하지 않는다. DMA처럼 물리 조건이 필요한 요청에 가상 주소가 이어진다는 것만으로 충분하다고 하지 않는다.

기다림을 허용할까

GFP_KERNEL은 메모리 압박에서 direct reclaim 등으로 잠들 수 있는 경로를 허용한다. 호출 문맥이 sleep 가능해야 한다. NOWAIT처럼 direct reclaim을 피하는 정책은 빠른 실패 가능성이 있으므로 실패 처리가 필요하다. 이는 실제 커널 코드를 실행한 결과가 아닌 공식 규약의 설명이다.

미리 풀을 준비하면 임계 경로의 할당을 줄일 수 있지만 풀 용량/ 초과 요청/ 수명오류를 관리해야 한다. 미리 할당한 것을 아직 사용 중인데 반환하면 use-after-free가 생기고, 무한대 풀을 가정하면 메모리 예산을 무시한다.

평균과 꼬리를 함께 본다

99개 요청이 1 μs, 한 개가 101 μs이면 평균은 2 μs다. 빠른 경로가 대부분이라 평균만 보면 마감 10 μs를 넘는 요청이 숨겨진다. 이 표본의 최대 101을 장차 모든 실행의 최악 상한이라고 증명할 수도 없다.

여기서는 nearest-rank percentile을 사용한다. 표본 100개에서 p99는 ceil(.99×100)=99번째, p100은 100번째다. 이 정의에서 p99 =1,p100 =101이다. 보간 정의를 쓰면 다른 값이 가능하므로 보고 시 정의를 적는다.
