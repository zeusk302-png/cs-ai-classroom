소단원 5.1

원자 연산·fence

증가를 한 번만 했는데 다른 스레드의 증가가 사라질 수 있을까?

준비 개념과 학습 목표

준비 개념

  • atomic은 다른 접근과 비교하여 한 연산을 쪼개지 않는 원자적 접근이다. RMW는 읽기·수정·쓰기를 한 원자 연산으로 묶는 방식이다.

  • fence는 메모리 순서 제약을 주는 동기화 연산이다. 언어의 보장과 CPU 명령어·캐시의 구현을 구별한다.

학습 목표

  • 개별 원자 접근과 원자적 증가의 차이를 추적한다.

  • fence를 통한 공개에서 필요한 연결 조건을 찾는다.

각 읽기와 쓰기가 원자적이면 더하기 전체도 원자적일까요?

기본 두 작업의 n=0 증가에서 출발합니다. 아래 새 사례는 세 작업이 각각 먼저 load하고 나중에 store하는 경우입니다. n은 atomic이고 초기화는 스레드 시작 전에 끝나며 정수 범위 초과와 다른 쓰기는 없습니다. 개별 연산의 순서가 가장 강한 seq_cst여도 두 연산을 묶은 증가가 하나의 연산이 되지는 않습니다.

fence는 공유 상태를 읽거나 횟수를 증가시키지 않습니다. 종이 사건에서 다른 스레드와 연결되는 atomic 객체와 실제 read-from 관계를 찾아야 합니다. 실제 컴파일러·CPU 실행이나 성능 측정은 수행하지 않았습니다. read-from은 읽기가 어느 쓰기의 값을 받았는지이고, fence는 순서 연결을 위한 경계입니다.

먼저 확인할 개념
  • 원자 연산·fence

    load/store와 read-modify-write의 보호 범위를 복습합니다.

  • 메모리 모델과 happens-before

    fence 사이에 필요한 동기화 연결과 일반 데이터의 보호를 확인합니다.

읽기와 쓰기가 각각 원자여도 묶음은 다르다

atomic 정수 n을 load하여 1을 더하고 store하는 두 연산은 그 사이에 다른 스레드가 끼어들 수 있다. 각 접근이 찢어지지 않아도 전체 증가가 하나의 원자 연산인 것은 아니다. fetch_add는 읽은 값에 증가를 반영하는 RMW라 그 묶음의 경쟁을 다룬다.

이 단원의 카운터는 0에서 두 번만 증가하여 오버플로가 없다. 모든 접근이 atomic이고 초기화는 스레드 시작 전 완료했다고 정한다. 비원자 정수의 동기화 없는 경쟁은 C++에서 정의되지 않은 동작이며 특정 결과 1이나 2를 정상 예상 출력으로 약속하지 않는다.

원자성과 다른 값의 공개는 별개다

relaxed 접근은 해당 원자 객체의 원자성을 제공하지만 다른 데이터의 공개 순서를 자동 연결하지 않는다. 카운트만 필요하고 다른 값의 전달에 사용하지 않는다면 relaxed RMW를 검토할 수 있다. 완료 후 스레드 join으로 카운터를 읽는 것과 중간 카운트를 보고 다른 공유값을 읽는 것은 다른 요구다.

atomic이라는 단어만으로 lock-free나 wait-free라는 진행 성질까지 보장하지 않는다. 어떤 타입·플랫폼에서 내부 잠금을 쓰는지는 별도다. 먼저 결과 정확성과 메모리 공개 조건을 설명하고 실제 처리시간·구현 명령어는 따로 확인한다.

fence에는 값을 읽는 다리가 필요하다

공개 예제는 생산자가 일반 data에 42를 쓰고 release fence 뒤 atomic flag에1을 relaxed store한다. 소비자는 flag의 relaxed load가 바로 그 store의 1을 읽은 뒤 acquire fence를 실행하고 data를 읽는다. 두 fence 사이의 같은 atomic 객체와 read-from 관계가 동기화의 다리다.

data의 다른 쓰기는 없고 소비자는 조건을 만족한 뒤에만 읽는다고 정했다. 이때 data 쓰기가 읽기보다 happens-before여서42를 얻는다. flag를 읽지 않고 두 스레드에 fence만 놓거나 초기 0을 읽었는데 data를 읽으면 같은 보장을 만들지 못한다. 실제 컴파일·실행은 수행하지 않았다.

모든 load가 먼저이므로 각 작업의 계산 결과는 1입니다. 각 행은 원자적이어도 세 번의 증가를 보존하지 않습니다.

중간 과정을 따라가는 예제

n=0인 atomic 정수에 두 스레드가 relaxed load 후 읽은 값+1을 relaxed store한다. P load,Q load,P store,Q store 순서를 추적하고, 두 fetch_add(1)로 바꾼 경우를 비교하라.

  1. P load는 0을 받아 임시값 1을 계산한다. Q load도 아직 store 전이라 0을 받는다.

  2. P store는 1, Q store도1을 저장하여 최종 n=1이다. 개별 load/store는 원자지만 증가 하나를 잃었다.

  3. fetch_add 두 개는 n의 수정 순서에서 하나가 먼저다. 첫 연산은 0을 읽어1, 둘째는 1을 읽어2로 만든다.

  4. 반환된 옛 값의 집합은{0,1}, 최종 2다. 어느 스레드가 0을 받는지는 이 입력만으로 정하지 않는다.

분리 증가의 명시한 순서는 1, RMW 두 번은2다. 완료 뒤 join으로 읽는 조건이다.

조건을 바꾸어 비교하기

seq_cst도 잘못된 분할 증가를 고치지 않는다

표의 최종 값과, A가 load/store를 마친 뒤 B와 C가 차례로 load/store하는 순서의 최종 값을 비교하세요.

  1. 표의 세 store는 모두 1을 씁니다.

  2. 완전히 차례로 처리하면 A는 1, B는 2, C는 3을 씁니다.

  3. 두 사건 순서 모두 각 작업의 load가 자신의 store보다 앞입니다.

표는 1, 차례로 완료하는 순서는 3입니다.

비교할 점

허용되는 실행 하나가 성공했다는 사실은 모든 실행의 정확성을 증명하지 않습니다.

같은 flag가 만드는 fence 연결

일반 data=0, atomic flag=0입니다. P는 data=7, release fence, flag.store(1,relaxed) 순서입니다. Q는 flag.load(relaxed)가 바로 이 store의 1을 읽은 뒤 acquire fence, data 읽기 순서입니다. 다른 쓰기는 없습니다. data 결과를 설명하세요.

  1. release fence는 flag 쓰기보다 앞입니다.

  2. Q의 flag 읽기는 그 쓰기의 값을 받으며 acquire fence보다 앞입니다.

  3. 이 연결로 data 쓰기가 data 읽기보다 happens-before이므로 7을 읽습니다.

주어진 read-from 관계와 fence 위치에서 data=7입니다.

비교할 점

flag에서 0을 읽거나 서로 다른 flag를 사용하면 이 증명이 성립하지 않습니다.

종이와 본문으로 직접 해보기

data=42→release fence→flag.store(1,relaxed)와 flag.load(relaxed)→acquire fence→data 읽기의 그림을 그려라. 어떤 load 값에서 data 읽기가 허용되는가?

힌트 보기

소비자의 load가 누구의 store에서 읽었는지를 표시한다.

풀이 보기

초기 flag 0, 다른 쓰기 없음에서 생산자 store의 1을 읽은 경우만 data를 읽는다. release fence→store와 load→acquire fence 순서 및 read-from이 두 fence를 연결한다. 0을 읽으면 data 읽기를 하지 않으며 42 공개를 주장하지 않는다.

오해와 반례

atomic load/store를 사용하거나 fence만 추가하면 여러 단계의 갱신과 모든 다른 변수도 자동 안전하다.

둘 다 0을 읽고 1을 쓰면 최종 1이라는 원자 카운터 반례가 있다. fence 공개에는 실제 flag store에서 읽는 연결이 필요하다. 일반 data의 무동기화 경쟁을 정의된 낡은값 출력으로 가르치면 안 된다.

스스로 풀어보기

먼저 답과 이유를 적고, 필요한 만큼 힌트를 한 단계씩 열어 보세요.

연습 1 · 값과 상태 예측

n=10에서 네 작업이 각각 fetch_add(2,relaxed)를 한 번 실행하고 모두 끝납니다. 반환값들의 집합과 최종 n을 쓰세요.

힌트 1

하나의 read-modify-write가 이전 값을 반환하고 2를 더합니다.

힌트 2

어느 작업이 어느 값을 받는지는 지정하지 않습니다.

풀이와 답 확인

  1. 수정 순서의 첫 반환은 10이고 다음은 12,14,16입니다.

  2. 네 번의 총 증가는 8입니다.

반환 집합 {10,12,14,16}, 최종 18입니다.

흔한 오답에서 다시 생각하기

relaxed이면 증가를 잃어서 최종 12도 된다.

각 fetch_add 자체는 원자적입니다. 다른 데이터의 순서 보장이 약한 것과 증가를 잃는 것은 다릅니다.

연습 2 · 오류 찾아 고치기

위 fence 예제에서 Q가 acquire fence를 flag.load보다 먼저 실행했습니다. flag=1을 읽었다는 사실만으로 data 읽기를 안전하다고 증명할 수 있나요?

힌트 1

fence-fence 연결은 읽기가 acquire fence보다 앞이어야 합니다.

힌트 2

일반 data에 다른 동기화가 없는 조건입니다.

풀이와 답 확인

  1. Q의 읽기는 fence보다 뒤라 필요한 연결 조건을 만족하지 않습니다.

  2. P의 일반 쓰기와 Q의 일반 읽기 사이 happens-before를 만들지 못합니다.

안전 증명에 실패하며 data 경쟁이 있는 실행은 undefined behavior입니다.

흔한 오답에서 다시 생각하기

1을 실제로 읽었으니 fence 위치는 상관없다.

값의 관측과 동기화 조건을 함께 확인해야 합니다. 정의된 오래된 값 결과로 바꾸어 설명하지 않습니다.

연습 3 · 직접 만들어 보기

fence 예제의 Q가 flag에서 0을 읽을 때도 data를 읽습니다. 성공 관측 뒤에만 읽도록 종이 제어 흐름을 고치세요.

힌트 1

0은 초기 쓰기에서 온 값입니다.

힌트 2

1을 읽은 뒤 acquire fence를 실행하는 분기를 표시합니다.

풀이와 답 확인

  1. flag를 relaxed로 읽고 0이면 data에 접근하지 않습니다.

  2. 해당 P store의 1을 읽었을 때 acquire fence를 실행한 뒤 data를 읽습니다.

0에서는 읽지 않고, 연결된 1에서는 fence 뒤 data=7을 읽습니다.

흔한 오답에서 다시 생각하기

0에서 data=0이면 우연히 맞으므로 항상 읽어도 된다.

일반 데이터의 충돌 접근은 값이 우연히 맞아도 경쟁 판단에서 제외되지 않습니다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

다른 동기화 없이 release/acquire atomic_thread_fence를 atomic_signal_fence로 바꾸었습니다. 다른 스레드 P/Q 사이 같은 증명을 쓸 수 있나요?

힌트 1

signal fence의 대상은 같은 스레드와 그 스레드의 signal handler입니다.

힌트 2

같은 이름의 order 인자가 대상 범위를 같게 만들지는 않습니다.

풀이와 답 확인

  1. atomic_signal_fence는 inter-thread fence 연결을 제공하는 대체물이 아닙니다.

  2. P/Q 일반 data 접근 보호를 다시 마련해야 합니다.

다른 스레드 사이의 이 안전 증명은 유지되지 않습니다.

흔한 오답에서 다시 생각하기

둘 다 acquire/release라고 쓰니 동일하다.

연산 이름과 적용 대상까지 봐야 합니다. 신호 처리 예제를 스레드 간 동기화 예제로 확장하지 않습니다.

원자성이란 더하기 전체를 보호한다는 뜻인가요?

설명 기준 확인

load와 store 각각의 원자성과 두 연산 전체의 원자성은 다릅니다.

fence는 어떤 값에 의존하나요?

설명 기준 확인

이 예제에서는 같은 atomic flag의 쓰기를 실제로 읽는 연결과 두 fence 위치에 의존합니다.

한 단계 더

세 스레드가 fetch_add를 한 번씩 수행하면 옛 값은{0,1,2}, 최종 3이다. CAS(compare-exchange)는 기대값과 현재값이 같을 때 바꾸는 다른 RMW이며 반복 실패와 진행 보장은 별도 학습 주제다. 이 숫자는 CPU 실험 로그가 아니다.

  • C++ working draft: Data races

준비 개념과 학습 목표

준비 개념

  • 메모리 모델은 어떤 접근·관찰이 허용되는지 정하는 언어 규칙이다. happens-before는 공유 접근 사이의 보장된 순서 관계다.

  • sequenced-before는 한 스레드 안의 순서, synchronizes-with는 맞는 동기화 연산 사이의 연결이다. read-from은 load가 특정 store의 값을 읽는 관계다.

학습 목표

  • release/acquire의 값을 통한 연결을 그린다.

  • 관계의 추이성으로 일반 데이터의 공개를 설명한다.

값 1을 보았다는 것과 작업 완료를 인계받았다는 것은 같은가요?

기본 release/acquire 출판을 두 방향의 인계로 확장합니다. 일반 payload와 answer는 atomic이 아닙니다. 각 공유 일반 데이터의 충돌 접근에 필요한 happens-before 경로를 따로 그려야 합니다. 초기화는 스레드 시작 전에 끝나고 각 변수에 적힌 쓰기 이외의 쓰기는 없다고 정합니다. ready와 done은 atomic이며 각각 0으로 초기화합니다. happens-before는 한 사건이 다른 사건보다 앞서도록 프로그램과 동기화 규칙으로 보장하는 관계입니다.

한 번 안전하게 출판한 데이터라도 생산자가 다시 덮어쓰면 새로운 쓰기를 별도로 보호해야 합니다. 아래 재사용 예제는 ready 값이 1이라는 숫자만으로 새 출판 여부를 구분할 수 없는 문제를 다룹니다. 실제 프로그램 실행이나 학생 이해 실험을 했다는 뜻은 아닙니다.

    스레드 안의 순서와 스레드 간 동기화 경로를 연결합니다.

  • 원자 연산·fence

    flag의 원자성과 payload의 비원자성을 구분합니다.

시간 추측을 보장된 관계로 바꾼다

동시 실행에서는 한 스레드가 오래 기다렸다고 다른 스레드의 쓰기를 읽는 규칙이 자동 생기지 않는다. C++의 happens-before는 같은 스레드의 sequenced-before, 스레드 사이 synchronizes-with 및 그 추이적 연결로 정의한다. sleep 시간이나 화면 출력 순서를 이 관계의 대신으로 쓰지 않는다.

고정된 비원자 변수에서 충돌하는 다른 스레드 접근에 쓰기가 있고 어느 방향의 happens-before도 없으면 데이터 경쟁이 될 수 있다. C++은 이를 undefined behavior로 정하므로 값이 단지 오래되었다는 정상 결과 하나로 설명하지 않는다. 언어별 규정도 같은 이름만 보고 섞지 않는다.

공개 표시를 읽어 같은 연결을 만든다

생산자가 data=42를 쓴 뒤 flag.store(true,release)를 한다. 소비자가 flag.load(acquire)에서 이 store의 true를 읽고 data를 읽는다면 release와 acquire가 동기화한다. data 쓰기→release→acquire→data 읽기의 네 사건을 연결하면 data 쓰기가 읽기보다 happens-before다.

초기 flag=false, data=0이며 두 초기화는 스레드 시작 전에 완료한다. 생산자는 한 번만 42와 true를 쓰고 소비자는 true일 때만 data를 읽으며 다른 접근은 없다고 정한다. 여러 생산자·재사용 flag라면 어떤 값을 읽었는지와 객체 수명 등 조건을 더 분석해야 한다.

일부 객체의 순서와 전체 순서는 다르다

각 atomic 객체에는 자신의 수정 순서가 있다. x의 수정 순서와 y의 수정 순서가 존재한다고 해서 모든 스레드의 모든 접근을 한 전역 순서로 합칠 수 있다는 뜻은 아니다. 다음 단원의 두 객체 반례는 이 차이를 보여 준다.

seq_cst는 해당 연산에 더 강한 총순서 조건을 준다. 그렇더라도 혼합된 약한 접근과 비원자 경쟁을 무시하고 프로그램 전체가 안전하다고 결론 내리지 않는다. 먼저 어떤 연산이 무엇을 읽고 어느 공개와 연결되는지 표시하는 것이 입문 검사의 시작이다.

한 방향 출판의 조건별 안전 판단
출판 쓰기관측 읽기일반 payload의 판단

ready.store(1,release)

해당 1을 acquire로 읽음

이 출판 이전 payload를 안전하게 읽음

ready.store(1,release)

해당 1을 relaxed로 읽음

이 연결만으로 일반 payload 보호 불가

ready.store(1,relaxed)

해당 1을 acquire로 읽음

release 출판이 없어 보호 불가

ready.store(1,release)

초기 0을 acquire로 읽음

출판 store를 읽지 않음

양쪽 order와 read-from을 한 행에서 함께 봅니다. 마지막 행에서 payload를 읽지 않으면 그 읽기 경쟁은 발생하지 않습니다.

중간 과정을 따라가는 예제

일반 data=0,atomic flag=false의 초기화는 스레드 시작 전이다. P:data=42; flag.store(true,release). Q:flag.load(acquire)가 P의 true를 읽으면 data를 읽는다. 네 사건의 관계와 읽는 값을 구하라.

  1. A=data42쓰기, B=flag release store, C=그 true의 acquire load, D=data 읽기로 이름을 붙인다.

  2. P 안에서 A→B, Q 안에서 C→D는 sequenced-before다.

  3. C가 B의 값을 읽어 B synchronizes-with C다. 추이적으로 A happens-before D다.

  4. data의 다른 쓰기가 없어 D는 42다. Q가 false를 읽으면 D를 실행하지 않는 조건을 유지했다.

read-from으로 연결된 acquire 경로에서는 일반 data 42가 안전하게 공개된다.

조건을 바꾸어 비교하기

왕복 인계로 응답을 돌려받기

P는 payload=5 뒤 ready.store(1,release)입니다. Q는 그 1을 acquire로 읽고 payload를 두 배하여 answer=10, done.store(1,release)입니다. P는 그 done의 1을 acquire로 읽은 뒤 answer를 읽습니다. 결과와 보호 경로를 쓰세요.

  1. P payload 쓰기 → ready 출판 → Q acquire → payload 읽기입니다.

  2. Q answer 쓰기 → done 출판 → P acquire → answer 읽기입니다.

  3. 두 출판 모두 해당 store를 읽는 관계이고 추가 쓰기가 없습니다.

Q payload=5, P answer=10입니다.

비교할 점

ready만 안전하게 연결해도 반대 방향 answer가 자동 보호되는 것은 아닙니다.

ready가 이미 1인 저장 공간 재사용

첫 출판 payload=5와 ready=1은 완료됐습니다. P가 일반 payload를 9로 덮어쓰고 ready를 1로 다시 release store합니다. Q의 acquire load는 첫 store의 1을 읽고 payload를 읽었습니다. 두 번째 payload 쓰기에 대한 안전성을 판단하세요.

  1. 첫 ready 쓰기는 두 번째 payload 쓰기보다 앞입니다.

  2. 첫 쓰기를 읽는 acquire는 그 뒤의 payload 덮어쓰기를 인계받지 못합니다.

  3. 다른 동기화가 없으면 새로운 쓰기와 읽기의 happens-before 관계가 없습니다.

새 payload 접근을 보호하지 못하며 경쟁 실행은 undefined behavior입니다.

비교할 점

ready 숫자가 1이고 acquire라는 사실만으로 모든 미래 덮어쓰기까지 보호하지 않습니다.

종이와 본문으로 직접 해보기

flag의 store와 load를 둘 다 relaxed로 바꾸고 true 뒤 일반 data를 읽는다면 무엇이 빠지는가? 값 0을 정상 출력이라고 써도 되는가?

힌트 보기

원자 flag의 값 연결과 일반 data의 동기화 관계를 별도로 본다.

풀이 보기

release/acquire synchronizes-with 연결이 없다. data 쓰기와 읽기의 happens-before가 확보되지 않아 비원자 data에 경쟁이 생기는 실행은 undefined behavior다. 0을 정의된 출력으로 약속하면 안 되며 맞는 동기화 설계를 다시 해야 한다.

오해와 반례

happens-before는 현실 시계에서 먼저 일어났다는 뜻이며 기다리기만 하면 모든 변수가 보인다.

P가 먼저 실행된 것처럼 보여도 sleep만으로 data의 공개 연결을 만들지 못한다. acquire가 release의 값을 읽는 등 규정된 연결과 그 앞뒤 순서가 필요하다.

소단원 5.3

약한 순서의 반례

각 변수는 원자인데 두 스레드가 모두 상대의 초기 0을 읽을 수 있을까?

준비 개념과 학습 목표

준비 개념

  • x,y는 서로 다른 atomic 정수이며 시작 전 0으로 초기화한다. r1,r2는 각 스레드만 쓰는 지역 결과다.

  • 순차 일관성 SC는 스레드 내부 순서를 보존하는 한 총순서로 설명하는 모형이다. 여기서는 네 접근 모두 seq_cst인 경우와 relaxed인 경우를 비교한다.

학습 목표

  • store-buffering litmus의 허용 결과와 SC 불가능을 구별한다.

  • 하드웨어 관측과 언어 허용 규칙의 차이를 설명한다.

허용되는 결과를 찾는 것과 자주 발생함을 측정하는 것은 어떻게 다를까요?

기본 store-buffering 두 atomic 변수에서 출발해 다른 반례로 확장합니다. x와 y는 atomic이고 0 초기화는 스레드 시작 전에 끝납니다. 모든 예제는 다른 쓰기가 없고 각 스레드에 표시한 순서를 유지합니다. 일반 데이터 경쟁을 약한 순서의 정상 숫자 결과와 섞지 않습니다.

아래 결과는 C++ 추상 메모리 모형에서 허용 여부를 판단합니다. 특정 CPU에서 반드시 나타난다거나 확률이 얼마라는 주장은 하지 않습니다. seq_cst 비교에서는 모든 표시 연산이 seq_cst입니다. 일부만 강화한 경우로 증명을 그대로 옮기지 않습니다. Wx/Wy는 x/y에 1을 쓰는 사건, Rx/Ry는 x/y를 읽는 사건입니다. SC는 seq_cst의 줄임말입니다.

먼저 확인할 개념
  • 약한 순서의 반례

    서로 다른 atomic 객체의 관측 결과를 전체 순서와 비교합니다.

  • 메모리 모델과 happens-before

    실제로 값을 읽은 관계가 동기화를 만드는지 확인합니다.

두 객체를 읽는 작은 검사

P는 x.store(1,relaxed) 뒤 r1=y.load(relaxed)를 한다. Q는 y.store(1,relaxed) 뒤 r2=x.load(relaxed)를 한다. 서로 다른 객체를 통한 동기화는 없다. C++ relaxed 모형은 r1=r2=0을 허용할 수 있으며 각 객체의 수정 순서만으로 그 결과를 배제하지 않는다.

이는 P의 지역 계산을 마음대로 어긴다고 가정하는 것과 다르다. 각 load가 초기값을 읽는 관계를 규칙에 맞게 배치하는 약한 관찰 모형이다. x86 등 특정 기계의 store buffer 설명은 한 구현 직관일 수 있지만 모든 언어·아키텍처를 같은 명령어 모형으로 단정하지 않는다.

SC의 가정 아래 순서 모순을 만든다

네 접근을 모두 seq_cst로 놓고 두 load가 0이라고 가정하자. 초기화 뒤 각 객체에는 한 번의 1 store밖에 없으므로 y 0 읽기는 y 1 쓰기보다 총순서상 앞, x 0 읽기는 x 1 쓰기보다 앞이어야 한다.

스레드 순서는 x쓰기→y읽기와 y쓰기→x읽기다. 이를 합치면 x쓰기→y읽기→y쓰기→x읽기→x쓰기의 순환이 되어 엄격한 총순서가 될 수 없다. 따라서 이 SC 모형의 (0,0)은 불가능하다. 다른 세 결과가 실제로 어떤 빈도로 나오는지는 종이 증명에 포함되지 않는다.

허용·필연·관측을 구별한다

relaxed에서 (0,0)이 허용된다는 말은 매 실행 그 값이 나와야 한다는 뜻이 아니다. 한 실험에서 (0,0)을 못 봤다는 사실도 그 결과가 금지되었다는 증거가 아니다. 컴파일러·장치·실행 횟수·코드를 기록한 관측과 언어 규칙에 근거한 판정을 별도로 둔다.

두 store를 release, 두 load를 acquire로 바꿔도 각 load가 초기 0을 읽으면 상대 release의 1을 읽는 동기화가 없다. 이 변경만으로 항상 (0,0)을 배제했다고 할 수 없다. 필요한 보장은 올바른 SC 설계 또는 분석한 fence 프로토콜 등으로 다시 확인한다.

두 쓰기와 두 관측으로 만든 메시지 전달 반례
스레드스레드 내부 사건검토할 결과

P

x.store(1,relaxed) → y.store(1,relaxed)

x 출판이 먼저인 프로그램 순서

Q

y.load(relaxed) → x.load(relaxed)

y=1,x=0 허용 여부

다른 객체의 relaxed 쓰기에는 Q가 y의 새 값을 읽었다고 x의 새 값을 읽어야 할 보장이 없습니다.

중간 과정을 따라가는 예제

SC에서 가능한 실행 P store x1, P load y, Q store y1, Q load x 순서를 따라 r1/r2를 구하라. 이후(0,0)의 총순서 모순도 적어라.

  1. 첫 store 뒤 x=1,y=0이다. P load는 y 0을 읽어 r1=0이다.

  2. Q store 뒤 y=1이고 Q load는 x 1을 읽어 r2=1이다. 결과 (0,1)은 SC로 가능하다.

  3. (0,0)을 가정하면 두 load가 각 상대 store보다 앞이어야 한다.

  4. 내부 순서와 함께 Wx<Ry<Wy<Rx<Wx의 순환이 생겨 SC 총순서가 없다.

제시한 SC 표는 (0,1)이고 (0,0)은 SC 조건에서 불가능하다.

조건을 바꾸어 비교하기

메시지 전달의 relaxed와 SC 비교

표의 Q 결과 y=1,x=0을 검토하세요. 이어 모든 네 연산을 seq_cst로 바꿨을 때 전체 순서 모순을 쓰세요.

  1. relaxed는 y의 쓰기를 읽어도 두 스레드 사이 x 출판의 동기화를 만들지 않아 이 결과를 허용합니다.

  2. SC에서 P 내부 순서는 Wx < Wy이고 Q 내부는 Ry < Rx입니다.

  3. Ry=1이면 Wy < Ry, Rx=0이면 Rx < Wx입니다. 합치면 Wx < Wy < Ry < Rx < Wx입니다.

relaxed는 허용하고 전체 SC는 순환 모순으로 금지합니다.

비교할 점

허용은 실제 CPU에서 이 결과가 반드시 관측된다는 뜻이 아닙니다.

같은 객체의 관측은 뒤로 가지 않는다

atomic x를 0으로 시작해 P가 x.store(1,relaxed) 한 번만 합니다. Q는 두 번 연속 x.load(relaxed)합니다. 첫 읽기가 1이면 둘째가 0이 될 수 있나요?

  1. Q의 첫 읽기는 둘째보다 sequenced-before이므로 happens-before입니다.

  2. 같은 atomic 객체의 read-read coherence는 둘째 읽기가 첫 관측 쓰기 또는 그 이후 쓰기를 읽도록 제한합니다.

  3. 수정 순서에서 초기 0 다음 쓰기는 1뿐이고 이후 0 쓰기가 없습니다.

첫 1 뒤에 둘째 0은 허용되지 않습니다.

비교할 점

다른 객체의 전체 순서가 약하다는 것을 한 객체의 coherence도 없다는 뜻으로 해석하지 않습니다.

종이와 본문으로 직접 해보기

SC 결과(1,0)과(1,1)을 각각 주는 네 사건 순서를 종이에 적어라. release/acquire 변경에서 두 load가 초기 0이면 동기화 화살표가 생기는가?

힌트 보기

상대 쓰기 전 읽기 또는 두 쓰기 후 두 읽기를 배치한다.

풀이 보기

(1,0)은 Wy,Rx,Wx,Ry, (1,1)은 Wx,Wy,Ry,Rx로 가능하다. release/acquire의 두 load가 초기 0을 읽으면 상대 release에서 읽은 1이 아니므로 그 store-load 동기화는 다리가 없다.

오해와 반례

모든 변수가 atomic이면 항상 SC이며 acquire load는 그 이름만으로 모든 release와 연결된다.

relaxed의 (0,0) 허용이 첫 오해의 반례다. acquire가 초기값을 읽으면 상대 release의 값을 읽는 조건이 없다. 원자성·순서 강도·read-from을 분리해 검사한다.

한 단계 더

(r1,r2)의 네 경우에 SC 순서 그림이 있는지 표를 만들자. 혼합된 seq_cst와 약한 접근에는 네 접근 모두 SC라는 증명을 그대로 적용하지 않는다. 일반 비원자 변수로 예제를 바꾸면 데이터 경쟁으로 정의되지 않은 동작이 될 수 있어 같은 결과표를 이식하지 않는다.

    2026-10-11 happens-before 정의와 객체별 coherence, 비원자 충돌의 data-race undefined behavior 관련 원문을 실제 읽고 왕복·재사용·같은 객체 반복 관측을 대조했습니다.

세 작업의 load/store를 분리한 표에서는 최종 카운터가 1이고 세 작업을 완전히 차례로 처리하면 최종 카운터가 3입니다. 초기값 10에 네 fetch_add(2)를 완료하면 반환값 집합은 {10,12,14,16}이고 최종 카운터는 18입니다. 왕복 인계 예제에서 payload를 두 배로 계산한 answer는 10이며, payload에 3을 더하는 활동의 answer는 8입니다. 초기 출판의 ready를 읽는 acquire는 이후 재사용 덮어쓰기를 인계하지 않으며 두 방향 일반 데이터는 각각 필요한 동기화를 갖춰야 합니다. 두 SC 예제의 전체 순서 순환 모순을 손으로 확인했습니다. 같은 atomic 객체의 첫 읽기가 1인 뒤 둘째 읽기가 0일 수 있는지는 이후 0 쓰기의 존재를 구별합니다. 전이의 payload 12를 2로 나눈 응답 answer는 6입니다. 초기 n=5에 세 fetch_add(3)를 완료하면 반환값 집합은 {5,8,11}이고 최종 n은 14입니다. 모든 값과 순서는 추상 모형의 손유도이며 실제 CPU 실행과 학생 실험은 수행하지 않았습니다.
