소단원 12.1

원격 파일·캐시·일관성

같은 원격 파일을 읽는데 내 컴퓨터와 친구의 화면이 다를 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 파일 읽기·쓰기·닫기

  • 캐시와 원본

  • 버전과 동시 작업

학습 목표

  • 서버 값·client 캐시·업무 값을 분리한다.

  • 자체 재검증 정책의 값 변화를 추적한다.

  • 캐시 최신성과 동시 갱신의 원자성을 구별한다.

새 데이터가 도착해도 오래된 요청이 캐시를 덮어쓸 수 있을까요?

기본의 open 재검증 모형을 비동기 응답으로 확장합니다. 서버는 값과 단조 증가 버전을 함께 반환합니다. A 요청은 시각 0에 버전 7과 값 70을 읽어 응답이 지연됩니다. 서버가 시각 1에 버전 8과 값 80으로 바뀌고 B 요청은 시각 2에 그 쌍을 읽습니다. B 응답은 시각 3, A 응답은 시각 5에 도착합니다. 모든 시간은 자체 모형의 밀리초이며 실제 NFS 동작의 측정값이 아닙니다.

캐시의 마지막 도착 순서와 서버의 변경 순서는 다를 수 있습니다. 쌍을 원자적으로 저장하면서 보유 버전 이상인 응답만 받아들이면 이 모형의 역행을 막습니다. 버전은 비교 가능한 같은 자원의 버전이고 서버 복원이나 버전 재사용은 없다고 가정합니다. 이것도 응답이 도착한 시점의 최신 버전을 항상 보장하지는 않습니다. 읽기 신선도와 동시 갱신 계약을 각각 적습니다.

이름이 같은 파일과 값이 같은 읽기

원격 파일 접근은 로컬 파일 API처럼 보일 수 있지만 client cache·서버·네트워크 사이를 거친다. 서버가 바뀌었어도 client가 이전 내용을 쓰면 다른 값이 보일 수 있다. 파일 이름이 같다는 사실만으로 각 읽기가 같은 시점의 데이터를 가져오지는 않는다.

캐시 정책은 어떤 사건에서 원본을 확인하는지 정한다. Linux NFS 문서의 NFSv3 close-to-open 예시는 닫기와 뒤의 열기를 경계로 설명한다. 이것이 파일을 열어 둔 모든 client의 모든 읽기가 즉시 최신이라는 뜻은 아니다. 실제 설정·버전·쓰기 완료·locking 조건을 확인해야 한다.

자체 재검증 모형으로 값 추적하기

아래 모형에서는 서버의 값과 버전을 한 쌍으로 저장한다. client는 open 시 서버 버전을 확인하고 달라졌으면 내용을 가져오며 열린 동안에는 보유 캐시를 읽는다. close한 writer의 서버 갱신은 성공하고 관찰된다고 가정한다. 이 규칙은 교육용이며 NFS 구현 전체를 그대로 흉내 낸 것이 아니다.

캐시에 있는 값이 옛 값인 것은 정책의 결과일 수 있다. 필요한 업무가 어떤 최신성 경계를 요구하는지 먼저 적고 그 경계에서 재검증·오류 처리를 선택한다. attribute cache를 줄인다고 모든 data race가 사라지는 것도 아니다.

최신 값을 읽어도 두 갱신은 부딪힌다

두 client가 모두 값 10을 최신으로 읽은 뒤 각자 1을 더해 11을 저장하면 최종 값이 11일 수 있다. 의도한 두 증가의 합 12가 되지 않은 것은 읽기-계산-쓰기 전체를 묶지 않았기 때문이다.

file locking이나 검증된 compare-version 갱신은 애플리케이션의 직렬화 설계에 포함할 수 있다. lock이 로컬 client끼리만 유효한지 서버와 다른 client에도 적용되는지, 장애 후 수명은 어떤지 별도로 확인한다. 캐시를 없애는 것과 업무 트랜잭션을 만드는 것은 다른 일이다.

버전과 내용을 한 쌍으로 읽습니다. 먼저 보낸 요청의 응답이 먼저 도착한다고 가정하지 않습니다.

중간 과정을 따라가는 예제

자체 정책에서 서버는 (값 10, 버전 1)이다. A와 B가 open하여 같은 쌍을 캐시한다. A가 값 20을 써 성공적으로 close하고 서버 버전은 2가 된다. B는 기존 open 상태로 한 번 읽은 뒤 close/open하여 다시 읽는다. 이후 별도 모형에서 두 client가 값 10을 읽고 각각 +1 결과를 조건 없이 저장한다.

  1. A close 후 서버는 (20,2)다. B의 기존 열린 캐시는 (10,1)이므로 첫 읽기는 10이다.

  2. B가 새 open에서 버전 2를 확인하면 캐시를 (20,2)로 바꾸어 둘째 읽기는 20이다. 재검증 실패·동시 변경은 이 표에서 제외했다.

  3. 별도 증가 모형에서 C와 D 모두 10+1=11을 써 최종 값은 11이다. 두 증가를 직렬 수행하면 10→11→12로 달라진다.

자체 정책의 B 읽기는 10 뒤 20이다. 별도 비원자적 갱신의 최종 값 11은 기대 12와 다르다. 실제 NFS의 모든 읽기를 예측하는 실험은 아니다.

조건을 바꾸어 비교하기

마지막 응답과 최신 버전

초기 캐시가 버전 6일 때 무조건 덮어쓰기와 버전 비교를 나란히 추적하세요.

  1. 시각 3에 두 정책 모두 B의 값 80, 버전 8을 저장합니다.

  2. 시각 5의 무조건 덮어쓰기는 값 70, 버전 7로 되돌아갑니다.

  3. 버전 비교 정책은 7<8이므로 A 응답을 버립니다.

무조건 도착 정책은 70으로 역행하고 버전 비교 정책은 80을 유지합니다.

비교할 점

이 비교는 단조 버전과 원자적 쌍이라는 자체 계약의 결과입니다.

비교 뒤 저장을 나누면

초기 버전 6에서 A와 B가 각각 검사만 한 뒤 B 저장, A 저장 순서로 끝납니다.

  1. A는 7≥6을, B는 8≥6을 보고 각각 통과합니다.

  2. B가 버전 8을 저장한 뒤 A가 이미 통과했다는 이유로 버전 7을 저장합니다.

  3. 검사와 갱신을 같은 보호 구간에서 다시 비교해야 합니다.

검사를 추가했어도 최종 버전이 7로 역행할 수 있습니다.

비교할 점

단조 검사 문구와 실제 원자적 검사·갱신을 구분합니다.

종이와 본문으로 직접 해보기

별도 모형에서 B의 새 open까지 서버 검사를 생략하도록 정책을 바꾸면 값은 무엇인가? 증가 모형에서는 버전 1일 때만 쓰기를 허용하고 첫 쓰기 성공 시 버전 2로 바꾼다. D가 버전 충돌 후 새 값 11을 읽어 재계산하면?

힌트 보기

새 open이 있어도 검사를 하지 않는 정책이다. 충돌 뒤에는 옛 결과 11을 그대로 쓰지 않는다.

풀이 보기

검사를 생략하고 캐시가 남으면 B는 계속 10을 읽는다. 조건부 증가에서는 C가 11/버전 2로 저장하고 D의 옛 버전 요청은 거절된다. D가 새 11에 1을 더해 새 버전 조건으로 성공하면 최종 12다. 버전 검사와 값 갱신이 서버에서 원자적이라는 추가 가정이 필요하다.

오해와 반례

매번 서버에서 최신 값을 읽으면 분산 read-modify-write도 자동으로 원자적이다.

둘이 모두 10을 최신으로 읽어도 각각 11을 쓰면 한 증가가 사라질 수 있다. 재검증은 읽기의 신선도 문제이고 여러 작업을 하나로 묶는 조건은 별도다.

연습 1 · 값과 상태 예측

버전 8의 캐시에 값 90, 버전 9 응답을 저장했습니다. 같은 자원의 값 80, 버전 8 응답이 뒤에 왔습니다. 원자적 단조 규약에서 최종 쌍은?

힌트 1

보유 버전을 먼저 봅니다.

힌트 2

더 작은 버전은 버립니다.

풀이와 답 확인

  1. 9를 저장한 뒤 8은 작습니다.

  2. 옛 응답은 저장하지 않습니다.

최종 값 90, 버전 9입니다.

흔한 오답에서 다시 생각하기

나중에 왔으니 80이 최신이다.

도착 시각과 변경 버전은 다릅니다.

연습 2 · 오류 찾아 고치기

파일 내용은 버전 9인데 별도 metadata 캐시는 버전 8입니다. 내용과 버전 쌍이 원자적으로 관찰됐다고 쓴 기록을 고치세요.

힌트 1

두 자료의 조회 시점이 다릅니다.

힌트 2

일관된 쌍을 보장한 규약을 확인합니다.

풀이와 답 확인

  1. 다른 시점의 관찰을 한 쌍으로 결합했습니다.

  2. 해당 보장이 없으면 비교 기준이 불명확합니다.

내용과 버전을 일관된 쌍으로 읽거나 원자적으로 검증하는 별도 계약이 필요합니다.

같은 파일 이름이면 두 응답 시점도 같다.

연습 3 · 직접 만들어 보기

서버 값은 40, 버전 3입니다. C와 D가 같은 쌍을 읽고 각각 +2 합니다. 서버의 원자적 버전 조건 갱신과 충돌 뒤 재계산으로 두 증가를 보존하세요.

힌트 1

첫 성공은 버전을 4로 바꿉니다.

힌트 2

충돌 뒤 옛 계산값을 재사용하지 않습니다.

풀이와 답 확인

  1. C가 조건 버전 3으로 값 42, 버전 4를 저장합니다.

  2. D의 버전 3 요청은 거부합니다.

  3. D가 값 42와 버전 4를 읽고 44를 계산하여 조건 버전 4로 성공하면 버전 5입니다.

최종 값 44, 버전 5입니다.

흔한 오답에서 다시 생각하기

충돌 뒤 버전만 4로 바꿔 옛 값 42를 쓴다.

재검사뿐 아니라 새 상태에 대한 재계산이 필요합니다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

캐시 hit 비용은 1 ms, 성공한 재검증 읽기는 7 ms입니다. 여섯 읽기 중 두 번만 재검증하는 자체 순차 정책의 비용과 모두 재검증하는 비용을 비교하세요.

힌트 1

hit은 네 번입니다.

힌트 2

비용은 전체 요청 비용으로 중복 합산하지 않습니다.

풀이와 답 확인

  1. 혼합 비용은 2×7+4×1=18 ms입니다.

  2. 모두 재검증하면 6×7=42 ms입니다.

비용은 18 ms와 42 ms입니다. 비용만으로 요구 최신성을 만족했다고 판정하지 않습니다.

OS와 분산서비스의 책임

운영체제가 파일을 저장하고 패킷을 보내 주면 서비스의 주문 처리도 한 번만 끝날까?

학습 목표

처리 기록을 다른 사용자의 요청에도 그대로 재사용하면 될까요?

자체 포인트 서비스의 중복 식별자는 사용자와 업무 ID의 쌍입니다. 사용자 A와 B의 초기 포인트는 각각 10이고 둘 다 ID=7로 +3을 요청합니다. 계약은 각 사용자의 요청 하나가 한 번만 효과를 내는 것입니다. ID 숫자 하나만 전역 저장하면 서로 다른 사용자의 업무를 잘못 같은 것으로 취급할 수 있습니다.

원자적 식별자 확인·효과·결과 저장은 그 작업에 포함된 저장소만 묶습니다. 알림 발송 예정 기록을 같은 작업에 넣어도 외부 발송과 수신은 별도입니다. 로컬 파일 fsync도 파일 자료와 디렉터리 항목의 경계를 확인해야 합니다. 아래는 계약 비교이며 실제 DB, 메일, 파일 동기화나 장애 주입을 수행하지 않았습니다.

계층별로 성공이 뜻하는 것

OS는 process·주소 공간·device·I/O 같은 자원을 관리하고 API 결과를 제공한다. 네트워크 stack의 전송 성공이나 원격 파일 요청의 성공과 주문이 올바르게 한 번 적용됐다는 결론은 서로 다른 계약이다. 어떤 API에서 어떤 성공을 받았는지 이름을 붙인다.

로컬 fsync의 내구성 범위도 해당 파일시스템·장치 계약에 달리고, 원격 파일의 flush/commit은 원격 서버 계약을 함께 확인한다. 둘 중 한 저장 성공이 다른 저장소의 업데이트나 메일 전송까지 원자적으로 묶지는 않는다.

서비스가 지켜야 하는 업무 불변식

자체 포인트 서비스의 불변식은 같은 업무 요청 식별자가 한 번만 포인트를 증가시킨다는 것이다. 서버가 식별자 확인·값 갱신·처리 결과 기록을 원자적이고 내구적으로 완료하고 그 뒤 응답한다고 가정하면 중복 요청에 기록된 결과를 돌려줄 수 있다.

로컬 cache나 RPC transaction ID만으로 이 가정 전체가 성립한다고 주장하지 않는다. 식별자 범위·보존 기간·같은 식별자의 다른 payload·서버 재시작·데이터 복원 정책도 설계 대상이다. OS는 요청의 업무 의미를 스스로 알아내지 못한다.

경계를 넘는 외부 효과

데이터베이스 갱신과 외부 알림이 다른 시스템에 있으면 하나가 성공하고 다른 하나가 실패할 수 있다. 자체 종이 모형에서는 발송 예정 기록을 업무와 함께 저장하고 나중에 발송자가 처리하는 구조를 생각할 수 있다.

발송 예정 기록은 전달 의도를 남기는 장치이며 메일이 정확히 한 번 도착하는 보장은 아니다. 재시도 중 중복을 수신 측이 처리할지, 확인하지 못한 결과를 어떻게 표시할지 별도 계약이 필요하다. 특정 분산 트랜잭션 도구를 실행한 결과로 제시하지 않는다.

중간 과정을 따라가는 예제

자체 서버의 포인트는 10이다. 요청 U는 +3이다. 식별자 확인·포인트 갱신·결과 저장은 하나의 원자적 내구 작업이고 같은 U는 같은 입력이며 기록은 유지된다. U 처리 후 서버는 13과 결과 기록을 저장했지만 응답은 유실된다. client가 U를 다시 보내면? 별도 메일 발송은 이미 한 번 성공했지만 발송자의 성공 기록 전에 process가 종료됐다고 하자.

  1. 첫 원자 작업 뒤 포인트는 13이며 U 결과 13이 기록된다. 응답 유실은 저장 결과를 지우지 않는다.

  2. U 재요청은 기존 결과 13을 반환하고 +3을 다시 하지 않는다. 식별자 없이 새로운 요청 V로 보내면 별도 업무로 허용되어 16이 될 수 있다.

  3. 메일은 이미 한 번 발송됐지만 성공 기록이 없어 재시도하면 두 번째 메일이 갈 수 있다. 포인트 원자 작업만으로 외부 발송을 한 번으로 묶지 못했다.

가정한 U 재시도는 포인트 13을 유지한다. V로 바꾸면 16이 될 수 있다. 메일은 별도 성공/기록 경계에서 중복 가능성이 남는다.

발송과 기록 사이의 간격

단일 예정 알림 O를 발송하고 성공 기록 전에 종료했습니다. 재시도하면 발송 시도와 수신 횟수는 어떻게 구분하나요?

  1. 첫 발송 성공은 외부 효과이고 O의 완료 기록은 아직 없습니다.

  2. 재시도에서 다시 발송하면 두 번의 발송 효과가 가능하며 수신 계약은 별도입니다.

  3. 수신 측이 안정된 O ID로 원자 중복 방지를 제공하면 그 가정 아래 수신 효과 하나를 설계할 수 있습니다.

예정 기록만으로 외부 수신 효과가 한 번이라는 결론을 얻지 못합니다.

오해와 반례

신뢰할 수 있는 OS와 TCP를 사용하면 여러 저장소와 외부 효과의 업무 원자성이 자동으로 생긴다.

전송·로컬 저장·원격 실행·업무 갱신·외부 발송의 성공 범위가 다르다. 각 경계에서 실패할 때의 상태를 적고 원자성·중복 방지 가정을 검증해야 한다.

한 단계 더

한 주문의 재고·결제·메일을 세 칸에 놓고 실제 원자 작업에 포함되는 칸을 표시하자. 각 칸의 완료·미완료·결과 불명 상태와 필요한 확인 정책을 적되 실제 결제나 외부 발송은 수행하지 않는다.

출처와 확인 범위
  • RFC 5531 — RPC version 2

    실제 347–381/396–415행의 응답 유실·재시도·transaction ID·TCP에서도 무응답의 모호함·binding 및 인증 경계를 읽었다. 개별 NFS 버전의 복구·중복 제어와 전체 업무 원자성을 같다고 부르지 않는다.

  • Linux nfs-utils — nfs(5)

    실제 75–110행의 hard/soft·timeout 및 991–1056행의 NFSv3 CTO·WCC·attribute caching·동시 갱신 한계를 읽었다. 최신 모든 분산 저장소의 동일 계약으로 일반화하지 않고 예제는 자체 캐시 정책이다.

  • 무응답과 서버 미실행을 구별한다.

  • 지연·유실·process 종료·partition의 관찰을 비교한다.

  • 불명 결과를 안전하게 재확인하는 조건을 설명한다.

시간 초과 뒤 재시도하면 요청 수와 효과 수는 얼마나 달라질까요?

자체 RPC client는 시각 0에 요청 U를 보내며 응답이 없으면 시각 40과 80 ms에 같은 U를 재전송합니다. 세 전송 모두 server에 도착하고 각각 10 ms 뒤 실행됩니다. 모든 응답은 시각 100까지 client에 도달하지 않는다고 가정합니다. 동일 U의 원자적 내구 중복 방지는 있는 경우와 없는 경우를 따로 계산합니다.

RPC 규격의 transaction ID는 응답 대응과 재전송 식별에 사용되며 순서 번호로 해석하지 않습니다. 실제 RPC와 모든 업무의 exactly-once가 자동으로 같지는 않습니다. 시간 초과는 관찰이며 취소 요청도 서버의 미실행 증명이 아닙니다. 실제 네트워크 재전송·취소·복구는 수행하지 않았습니다.

무응답은 여러 실행과 양립한다

로컬 함수 호출에 비해 원격 호출에는 요청 경로·서버·응답 경로의 별도 실패가 있다. 요청이 도착하지 않음, 서버가 처리 전에 종료, 처리 후 응답 유실, 오래 걸리는 정상 실행 모두 client의 시간 초과처럼 보일 수 있다.

RPC 공식 문서는 TCP를 사용하더라도 응답을 받지 못한 경우 원격 procedure가 실행되지 않았다고 가정할 수 없다고 설명한다. timeout은 client의 기다림 정책에 따른 관찰이며 원격의 최종 상태 증명이 아니다.

부분 실패와 계속 남은 사본

한 client만 server에 닿지 않고 다른 client는 계속 접근하는 경우가 있다. 네트워크 partition에서 각 노드의 관찰이 달라지고 오래된 cache가 남을 수 있다. 서버 process 재시작 시에도 영속 데이터·메모리 중복 기록·연결 상태의 수명이 서로 다르다.

어떤 데이터가 남고 어떤 기록을 잃는지 장애 모델에 명시해야 재시도 결과를 분석한다. crash만 다룬 시험을 손상된 저장소·악의적 응답·동시 partition까지 검증했다고 부르지 않는다.

재시도와 확인도 조건부 설계

자체 업무에서는 결과 불명 상태를 따로 두고 안정된 식별자로 결과를 조회하거나 재요청하도록 설계할 수 있다. 동일 식별자 처리가 원자적이고 내구적이며 기록이 유지된다는 가정이 없다면 앞 소단원의 한 번 효과 결론도 유지되지 않는다.

Linux NFS 문서의 hard/soft는 시간 초과 후 재시도와 오류 반환의 정책을 설명한다. 옵션은 응답성·데이터 무결성의 tradeoff이며 이를 가볍게 바꾸어 문제가 해결됐다고 주장하지 않는다. 아래 시간은 실제 NFS timeout 설정이 아닌 자체 request 모형이다.

중간 과정을 따라가는 예제

자체 client는 요청 U(+5)를 시각 0 ms에 보내고 100 ms에 응답 없으면 결과 불명으로 표시한다. 초기 값 10이다. 이력 A에서는 요청이 유실되어 값 10, B에서는 서버가 20 ms에 값 15로 처리하고 응답이 유실, C에서는 처리와 응답이 느려 120 ms에 완료된다. 세 이력의 100 ms 관찰로 결과를 구별할 수 있는가?

  1. 100 ms에는 세 이력 모두 응답이 없다. A는 아직 효과 0, B는 효과 +5, C는 미래 완료 가능성이 남는다. timeout 화면만으로 이를 구별하지 못한다.

  2. 새 식별자 V(+5)로 무조건 재시도하여 둘 다 처리되는 B의 이력이면 10→15→20이 된다. 응답 유실이 실패라는 판단이 중복 효과를 만든다.

  3. 내구적 U 결과 조회를 제공하고 동일 U 원자 중복 방지가 유지되는 추가 모형이라면 B의 조회는 완료 15를 확인한다. A의 조회가 미처리여도 원래 요청이 나중에 실행될 가능성과 서버 계약을 함께 확인해야 한다.

100 ms 무응답만으로 A/B/C를 구별할 수 없다. B에서 새 V 재시도는 20이 될 수 있다. 안정된 U와 검증된 내구 처리 계약이 있을 때 재확인을 설계한다.

각 성공이 포함한 대상을 씁니다.

풀이와 답 확인

  1. 버전 4는 보유한 5보다 작아 버리고 값 50을 유지합니다.

  2. 분리된 검사는 옛 캐시에서 통과한 뒤 값 40을 늦게 저장할 수 있습니다.

  3. 기록이 유지되면 첫 +2만 적용하여 32입니다.

  4. 첫 기록 소실 뒤 네 재전송 모두 실행되면 전체 다섯 효과로 40입니다.

  5. 파일 fsync만으로 디렉터리 이름이나 외부 메일의 완료를 단정하지 않습니다.

단조 원자 정책은 값 50을 유지합니다. 포인트는 기록 유지에서 32, 명시한 기록 소실 이력에서는 40입니다. 각 성공의 대상과 별도 완료 경계를 확인합니다.

해결한 뒤 점검할 것

  • 버전과 도착 순서를 구분합니다.

  • 원자 검사·갱신과 보존 기간을 명시합니다.

  • API 성공과 업무 및 외부 효과를 구별합니다.

  • 종이 이력과 실제 장애 실험을 구별합니다.

보강 자료의 출처와 확인 범위
  • RFC 5531: RPC Version 2

    실제 4/5/6/7절과 xid 메시지 설명을 읽어 무응답의 실행 모호성, 재전송/ID 비교와 응답 대응, binding·authentication 범위를 대조했다. 전체 RFC를 읽었다고 주장하지 않으며 자체 업무 원자성·시각은 규격의 실측이 아니다.

  • nfs-utils maintained source mirror: nfs(5)

    공식 man7 접근이 시간 초과되어 nfs-utils 원문 mirror의 hard/soft, noac, local_lock/nolock, cto 및 DATA AND METADATA COHERENCE의 CTO/WCC/attribute caching 본문을 실제 읽었다. 문서 표제의 2012 역사 버전을 최신 전체 NFS 계약으로 일반화하지 않는다. 비동기 버전 응답은 자체 모형이다.

  • Linux man-pages author source: fsync(2)

    실제 2021 표제 원문의 DESCRIPTION/RETURN VALUE/ERRORS 앞부분을 읽어 파일 자료와 metadata 및 별도 directory fsync, 오류 반환을 대조했다. 전체 장치 내구성이나 다른 저장소 업무 원자성의 증거로 확대하지 않았다.

비동기 응답의 도착 시각 3과 5 ms를 추적하여 무조건 덮어쓰기는 값 70으로 역행하고 단조 원자 갱신은 값 80을 유지함을 확인했다. 분리 검사에서는 옛 버전 6에서 두 요청이 통과한 뒤 늦은 버전 7이 버전 8을 덮을 수 있다. 조건부 두 증가의 최종 값은 44이고 버전은 5다. 여섯 읽기의 비용은 혼합 정책 18 ms와 모두 재검증 42 ms다. 사용자별 ID를 적용하면 A와 B의 포인트가 각각 13이며 같은 사용자 재시도는 그 값을 유지한다. 다른 입력은 충돌로 거부한다. 시각 10, 50, 90 ms의 세 실행에서 중복 방지가 없으면 포인트가 32이고 내구 중복 방지가 유지되면 24다. 기록을 시각 60에 제거하면 마지막 실행으로 28이 된다. 최대 중첩 DB 시도는 여섯 번으로 초기 20이 26이 된다. 전이의 단조 캐시 값은 50이며 포인트는 기록 유지에서 32, 명시한 소실 뒤 다섯 효과에서 40이다. 자체 시각과 산술을 손으로 대조했다.
