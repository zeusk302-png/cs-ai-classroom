소단원 3.1

CPU affinity·load balancing

한 CPU에 계속 남기는 것이 좋을까, 빈 CPU로 옮기는 것이 좋을까?

준비 개념과 학습 목표

준비 개념

  • 실행 가능한 thread는 CPU를 기다린다. I/O 대기 중 thread와 runnable thread를 같은 부하로 세지 않는다.
  • cache는 최근 사용한 자료를 재사용한다. thread 이동 뒤 cache·TLB 상태를 다시 채우는 비용이 생길 수 있다.
  • 부하 균형은 작업 수만 같게 만드는 것이 아니다. 남은 실행량·CPU 속도·허용 CPU·기한을 함께 따진다.

학습 목표

  • 허용 affinity와 cache 지역성 선호를 구별한다.
  • 다중 큐의 불균형과 이동 비용을 계산한다.
  • 작업 수·작업량·공정성의 다른 목표를 설명한다.

허용 집합과 선호는 다르다

hard affinity mask는 thread가 실행할 수 있는 CPU의 집합을 제한한다. {0,1}이면 둘 중 어느 CPU도 가능하지만 특정 CPU를 항상 우선한다는 뜻은 아니다. cache affinity라는 선호는 이전 CPU에 남아 자료를 재사용하고 싶은 이유다. Linux의 mask는 thread별 속성이므로 한 process의 모든 thread가 자동으로 같은 설정을 갖는다고 단정하지 않는다.

실제 허용 집합은 지정 mask와 온라인/존재하는 CPU, 관리자가 부여한 cpuset 등의 제약을 함께 적용한다. 허용 CPU가 하나라도 전용으로 독점한다는 뜻은 아니다. 다른 작업과 interrupt가 그 CPU를 사용할 수 있으며 mask가 비어지는 요청은 실패할 수 있다. 문서의 성능 동기를 모든 workload의 최대 속도 보장으로 일반화하지 않는다.

실행 큐를 나누면 새로운 문제가 생긴다

전역 큐는 빈 CPU가 같은 작업 목록에서 꺼낼 수 있어 직관적으로 균형을 맞추기 쉽다. 그러나 여러 CPU가 같은 큐를 수정하려면 동기화가 필요하고 그 경합이 커질 수 있다. CPU별 큐는 공통 구조 접근을 줄이고 cache 지역성을 돕지만 한 큐가 길고 다른 큐가 비어 있는 상황을 만들 수 있다.

load balancing은 작업을 이동해 이런 불균형을 줄인다. 한 번에 몇 개 옮기는지, 주기적으로 확인하는지, idle CPU가 일을 가져오는지 등의 정책은 구현에 따라 다르다. 데이터가 있던 cache·NUMA node에서 멀어지고 이동 자체에도 시간이 들 수 있어 작업 수만 반반으로 만드는 것이 항상 유리하지 않다.

남은 작업과 이동비용을 함께 본다

동일 속도 두 CPU에서 CPU0에 A6ms/B2ms, CPU1에 C2ms가 있으면 이동하지 않을 때 끝나는 시간은 max(8,2)=8ms다. B를 CPU1로 옮기면 나눔이6/4가 되지만 이동 비용이 붙는다. 작업은 독립이고 미실행 상태에서 이동하며 각 CPU는 하나씩 순차 실행한다는 조건을 명시한다.

여러 runnable thread에 같은 CPU 시간 몫을 주는 공정성과 짧은 완료시간은 별도 목표다. {0}만 허용한 thread를 CPU1로 옮겨 균형을 맞추는 것은 제약을 위반한다. 실제 CPU는 SMT·속도 차이·interrupt가 있어 작은 동일 CPU 모형의 max 계산을 그대로 적용하기 전에 조건을 확인해야 한다.

중간 과정을 따라가는 예제

동일 CPU 두 개에서 0에 A6ms/B2ms, 1에 C2ms를 배정한다. 독립 미실행 작업이며 각 CPU 순차 실행, 기타 비용0이다. B를 옮기면 CPU1에 migration+cache 회복1ms가 먼저 들어간다. 유지/이동의 최종 완료시간을 비교하라.

  1. 유지는 CPU0의 A+B=8ms, CPU1의 C=2ms다. 전체 완료는8ms이며 CPU1은2..8ms 동안 idle이다.
  2. 이동 후 CPU0은 A6ms다. CPU1은 이동비1+C2+B2=5ms다. 순서는 이 총량에서 결과를 바꾸지 않는다.
  3. 전체 완료는 max(6,5)=6ms로2ms 줄었다. 일 자체10ms에 이동1ms가 추가되어 총 실행/비용 합11ms다.
  4. 경과시간비6/8=.75이고 기존 대비 감소25%다. 비용이 추가되어도 병렬 배정으로 경과시간은 줄 수 있다. 이는 실제 스케줄러 측정값이 아니다.

유지8ms, 이동6ms다. 총 비용 합과 모든 작업의 완료 경과시간을 구별한다.

힌트 보기

풀이 보기

오해와 반례

affinity를 고정하면 언제나 더 빠르고 CPU도 독점한다.

CPU0에 작업을 묶고 CPU1을 idle로 남긴8ms 예에서는 허용된 이동이6ms로 더 빠르다. 반대로 이동비5ms면9ms로 더 느리다. 고정mask는 실행 위치 제한이며 전용 CPU·최적 성능 보장은 아니다.

소단원 3.2

NUMA와 공정성

CPU 시간을 똑같이 주면 두 작업의 진척도도 같을까?

준비 개념과 학습 목표

준비 개념

  • NUMA는 메모리가 여러 node에 나뉘어 접근 위치에 따라 비용이 다른 구조다. CPU와 가까운 메모리를 local이라고 부른다.
  • CPU 시간 몫과 완료한 작업량은 다르다. 같은10ms라도 명령·메모리 대기 때문에 처리량이 달라질 수 있다.
  • 메모리 정책은 새 페이지의 할당 위치를 정할 수 있다. thread를 옮기는 것과 페이지를 옮기는 것은 별도 동작이다.

학습 목표

  • CPU 배치와 메모리 배치를 함께 설명한다.
  • local/remote 비용의 가중 평균을 계산한다.
  • 공정성 기준과 locality·병렬성의 상충을 구별한다.

thread 옆으로 메모리가 자동 이동하지는 않는다

node0의 CPU가 node0 메모리를 읽는 local 접근과 node1 메모리를 읽는 remote 접근의 지연·대역폭이 다를 수 있다. 가상 주소가 같고 자료가 정확해도 실행 위치에 따라 비용은 달라진다. CPU migration 뒤 페이지가 원래 node에 남으면 remote 비중이 커질 수 있으므로 CPU mask만으로 전체 지역성을 보장하지 않는다.

local allocation에서 page fault를 처리하며 실제로 페이지가 배정될 때의 위치가 중요하다. 한 thread가 모든 페이지를 먼저 건드린 뒤 다른 node의 worker들이 처리하면 배치가 기대와 달라질 수 있다. allocator·기존 페이지·공유 매핑·정책·여유 메모리가 영향을 주므로 단순히 malloc 호출 CPU만으로 모든 물리 배치를 확정하지 않는다.

지역성 정책도 여러 목적을 가진다

bind는 정한 node 집합에서 할당하려는 강한 제약이고 preferred는 선호 위치에서 실패하면 다른 위치를 찾는 식의 정책이다. interleave는 페이지를 여러 node에 분산해 대역폭 활용과 용량 균형을 돕는 선택이다. 어느 정책도 모든 접근의 최소 지연을 자동 보장하지 않는다. 관리자의 허용 node와 정책 범위도 함께 적용한다.

정책을 바꿔도 이미 fault-in 된 페이지가 항상 자동 이동하는 것은 아니다. Linux 문서는 기본적으로 새 할당에 적용되는 범위와 명시적인 page migration 기능을 구별한다. 따라서 현재 정책 설정, 실제 page 위치, thread 실행 node를 따로 관찰해야 한다. 본문은 익명 페이지 중심의 개념 모형이며 모든 file-backed 공유 페이지의 같은 동작을 주장하지 않는다.

공정성을 어떤 양으로 정의하는지 적는다

동일 priority·weight인 runnable 작업에 같은 CPU 시간 몫을 주는 기준은 처리량의 동일성과 다르다. cache hit, remote 비중, interrupt와 실행되는 명령이 다르면 같은 시간에 완료한 연산도 다르다. 가중 몫을 쓰면 weight가2:1인 두 작업의 이상 CPU 배분은2/3:1/3이며 이것도 deadline 보장이 아니다.

locality를 위해 특정 node에 머무르면 그 node의 큐가 길어지고 다른 node가 idle일 수 있다. 반대로 모두 균등 분산하면 remote 접근이 늘 수 있다. 목표를 총 완료시간, 최소 진척, CPU 시간 몫, 사용자별 지연 중 무엇으로 잡았는지 밝혀야 상충을 비교할 수 있다. CPU와 메모리 양쪽의 경합을 무시한 평균 접근 모형은 실제 작업의 전체 시간을 대신하지 않는다.

중간 과정을 따라가는 예제

순차적 독립 메모리 접근 10만 회에서 local 80ns, remote 160ns이며 다른 비용·겹침은 없다. node0에 실행할 때 80% local, node1로 이동 후 20% local이라면 메모리 시간은? 별도 이상 CPU 공유 구간 30ms에서 A/B weight 2:1의 시간 몫도 계산하라.

  1. node0 평균은 .8×80+.2×160=96ns다. 10만 회면9,600,000ns=9.6ms다.
  2. node1 평균은 .2×80+.8×160=144ns다. 10만 회면14.4ms다.
  3. 동일 접근 수의 시간비14.4/9.6=1.5다. CPU 이동을 했지만 페이지 배치가 유지되어 remote 비중이 증가한 모형이다.
  4. CPU 공유30ms를 weight2:1로 이상 배분하면 A20ms/B10ms다. 이 몫 계산은 위 접근 시간 모형과 별도이며 완료 작업량2:1을 뜻하지 않는다.

메모리 접근9.6→14.4ms, 시간비1.5다. 가중 CPU 몫은20/10ms이며 처리 진척과 구별한다.

오해와 반례

NUMA에서 local만 쓰면 부하 균형과 공정성도 자동으로 최적이다.

한 node에만 모두 머물러 큐가 길고 다른 node가 idle이면 기다리는 시간은 커질 수 있다. 반대로 interleave는 지연을 늘려도 메모리 대역폭 이용을 도울 수 있다. local 비중은 목적의 한 항이지 모든 사용자 진척의 증명이 아니다.

소단원 3.3

병목 측정과 확장성

CPU를 더 붙였는데 두 배 빨라지지 않았다면 어디를 봐야 할까?

준비 개념과 학습 목표

준비 개념

  • 같은 고정 작업의 speedup S(p)=T1/Tp, 효율 E(p)=S(p)/p다. 작업 크기가 바뀌면 다른 비교가 된다.
  • critical section은 한 번에 한 실행만 들어가야 할 수 있다. 경합·대기·cache line 이동이 CPU 수 증가와 함께 커질 수 있다.
  • 측정 counter는 정의된 사건을 센다. CPU 모델과 이벤트 정의를 확인해야 다른 장비 숫자를 비교할 수 있다.

학습 목표

  • 직렬 부분과 추가 비용의 확장성 모형을 유도한다.
  • 시간·처리량·CPU 사용·counter의 다른 의미를 읽는다.
  • 측정 계획과 실제 수행 증거를 분리한다.

직렬 부분은 CPU를 늘려도 남는다

같은 작업의 기준 시간 T1에서 fraction f가 직렬이고 나머지가 이상적으로 p개 CPU에 분배되면 Tideal(p)=T1[f+(1−f)/p]다. 직렬 경로는 다른 CPU가 기다리며 순서대로 처리해야 한다. 분모를 나누면 이상 speedup은1/[f+(1−f)/p]이고 f>0이면 p→∞에서1/f로 제한된다.

실제 추가 비용 O(p)을 별도로 더하면 Tp=Tideal(p)+O(p)다. O에는 실행 큐 경합·lock 대기·migration·통신 등의 추가 경과시간을 넣되 이미 f나 병렬 부분에 들어간 비용을 중복 계산하지 않는다. O는 p에 따라 늘거나 줄 수 있고 일부 겹침도 있으므로 식은 명시한 모델이다. 작은 p에서 추정한 값으로 모든 p의 실제 시간을 단정하지 않는다.

수치 하나가 원인을 확정하지 않는다

높은 CPU 사용률은 유용한 처리만큼 spin 대기·재시도도 포함할 수 있다. cache miss 수가 늘었다고 lock 경합이 유일 원인이라는 결론도 성립하지 않는다. 경과시간과 throughput, runnable/blocked 시간, context switch/migration, memory bandwidth 등을 함께 보고 가능한 설명을 좁힌다.

perf stat은 사건 통계를 모으고 record/report는 표본을 기록·분석하는 도구 경로다. hardware PMU 사건은 CPU 모델에 따라 지원과 의미가 다르며 generic cache-misses가 어떤 cache를 뜻하는지도 확인한다. multiplex된 counter의 scaling, 주파수 변화, 관찰 오버헤드, 표본 오차를 확인해야 한다. counter를 읽었다는 것과 특정 인과 가설이 증명됐다는 것은 다르다.

공정한 실험은 바뀐 조건을 좁힌다

코어 수 외에 workload 크기·입력·결과 정확성·thread 수·affinity·NUMA 배치·초기 cache·주파수·다른 프로그램 부하를 기록한다. warm-up과 반복 구간을 나누고 중앙값·변동폭을 함께 본다. 실험을 반복해도 같은 숨은 편향이 반복될 수 있어 변경 조건을 하나씩 비교한다.

이 단원은 도구 사용의 목적과 종이 숫자를 제공한다. 실제 Linux 환경·counter 권한·입력/출력·실행일·반복 결과를 확보하기 전에는 measured나 PASS라고 표시하지 않는다. 특정 lock을 제거하는 선택은 자료구조 정확성 조건까지 유지해야 하며 더 빠른 예상값만으로 변경을 승인하지 않는다.

중간 과정을 따라가는 예제

고정 작업 T1=100ms,f=.2다. p4의 추가 비용6ms,p8의 추가 비용18ms인 모형에서 T4/T8,S/E를 구하라. 추가 비용0인 무한 CPU speedup도 계산하라.

  1. 직렬20ms와 병렬80ms를 나눈다. p4의 이상 시간20+80/4=40ms다.
  2. T4=40+6=46ms다. S4=100/46=50/23≈2.174,E4=25/46≈.5435다.
  3. p8의 이상 시간20+80/8=30ms지만 T8=30+18=48ms다. S8=25/12≈2.083,E8=25/96≈.2604다.
  4. 8개가4개보다2ms 느리다. 추가 비용0의 p→∞ 한계는100/20=5배다. 실제 모든 O(p)를 모르면 실제 최대값을 이 한계로 대체하지 않는다.

T4=46ms,T8=48ms다. 이상 분배 개선10ms보다 추가 비용 증가12ms가 커서 느려졌다.
