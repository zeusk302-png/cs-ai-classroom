소단원 10.1

admission control·QoS

이미 바쁜 컴퓨터가 새 요청을 모두 받아야 서비스가 더 좋아질까?

준비 개념과 학습 목표

준비 개념

  • CPU 시간

  • 주기와 마감

  • 비율

학습 목표

  • 입장 허용을 자원 예산과 연결한다.

  • 가중치·상한·예약 및 지연 목표의 차이를 설명한다.

CPU 이용률이 낮은데도 동시에 나온 마감을 놓칠 수 있나요?

기본 단일 CPU 모델의 마감과 주기가 같다는 조건을 바꾸어 조건의 역할을 확인합니다. 새 작업 A와 B는 각각 실행시간 상한 C가 2 ms, 주기 P가 10 ms, 상대 마감 D가 2 ms입니다. 두 작업은 시각 0에 동시에 준비되고 한 CPU에서 선점할 수 있으며 차단과 추가 비용은 0입니다. 평균 요구량 C/P를 더하는 것과 짧은 마감 안의 총 요구를 만족하는 것은 서로 다른 검사입니다.

별도 수용 정책은 CPU 비율 합 0.8, RAM 256 MiB, I/O 요구 50단위 이하를 모두 요구합니다. RAM은 실제로 동시에 필요한 자체 상한이며 중복 공유나 회수는 제외합니다. Linux 스케줄러를 설정한 실험이 아니며 WCET·메모리 상한을 실제 측정했다고 주장하지 않습니다. 설정값을 작게 쓰는 것만으로 실제 요구량이 줄어들지는 않습니다.

먼저 확인할 개념
  • admission control·QoS

    기본 EDF의 마감=주기 가정과 상한·예약의 차이를 확인합니다.

  • tail latency·간섭

    평균과 마감 실패의 관계를 비교합니다.

처리를 시작하기 전에 약속을 확인한다

admission control은 새 작업을 받아도 기존 약속과 자원 조건을 만족할 수 있는지 판단하는 절차다. 수용량보다 많은 요구를 모두 받으면 대기가 쌓이거나 마감을 어길 수 있다. 거절·대기·낮은 품질로 전환하는 정책도 자원 관리의 일부다.

QoS(quality of service)는 처리량, 응답시간, 손실률처럼 제공하려는 품질과 이를 관리하는 정책을 말한다. 특정 수치를 목표로 쓴 것과 그 수치를 보장한 것은 다르다. 어떤 부하와 자원 가정에서 목표를 평가하는지 명시하고 실제 위반도 기록해야 한다.

예약 계산은 작업 모델이 필요하다

실행시간 상한 C, 주기 P인 작업은 평균 CPU 요구 비율 C/P를 갖는다. 한 CPU의 이상적인 선점 EDF 모델에서 독립 주기/산발 작업의 상대 마감이 모두 주기와 같고 차단·스케줄러 비용을 무시하면 합 C/P≤1 조건으로 마감을 논의할 수 있다. Linux 문서는 이 단일 CPU 조건과 다른 마감 및 다중 CPU의 조건 차이를 구분한다.

운영 정책은 일부 여유를 남겨 합을0.8 이내로 제한할 수 있다. 이 수치만 만족했다고 메모리와 I/O 요구까지 충족한 것은 아니다. Linux SCHED_DEADLINE의 runtime/deadline/period는 작업의 WCET 및 실제 도착 간격과 맞아야 하며 지원되는 admission 검사를 함께 고려한다. 이번 예산표는 실제 커널 설정을 변경하지 않는 종이 모델이다.

비율과 상한을 최소 보장으로 바꾸지 않는다

가중치는 경쟁하는 활성 그룹 사이의 상대 배분이다. Linux cgroup의 cpu.weight는 적용되는 스케줄러와 계층 조건에서 비율을 조정한다. 반면 cpu.max는 기간마다 사용할 수 있는 최대 CPU 대역폭을 제한한다. 최대40%라는 설정을 최소40%를 받는 약속으로 읽으면 안 된다.

CPU만 분리해도 메모리와 디스크의 경쟁은 남을 수 있다. memory.high는 초과 때 회수 압력과 지연을 유발하는 경계이며 memory.max의 하드 제한과 같지 않다. 제어가 어떤 자원·스케줄러·계층에 적용되는지 확인해야 품질 정책의 범위를 설명할 수 있다.

중간 과정을 따라가는 예제

한 CPU의 가상 수용 정책은 예약 비율 합≤0.8이다. A는2ms/10ms, B는3ms/10ms, 새 C는4ms/10ms다. 모두 독립, 마감=주기, 비용0이다. C를3ms/10ms로 바꾸는 선택과 비교하라.

  1. A의 비율 .2, B .3이므로 기존 합 .5다.

  2. 원래 C의 .4를 더하면 .9로 정책 상한 .8을 넘으므로 거절 또는 조건 변경 대상이다.

  3. C를 .3으로 바꾸면 합 .8이 되어 가상 수용 기준을 만족한다. 그러나 실제 C가3ms 안에 끝난다는 근거가 있어야 한다.

  4. 원래 합 .9는 이상적 단일CPU EDF의≤1 조건에는 들어가지만 여유를 남기는 수용 정책 .8과는 다르다. 정책 거절을 수학적으로 절대 실행 불가능하다는 뜻으로 읽지 않는다.

원래 C는 정책 거절, 실행 요구가 실제로 줄어든 C는 정책 수용이다. 서로 다른 기준을 명시해야 한다.

조건을 바꾸어 비교하기

이용률만으로 짧은 마감을 판정하지 않는다

마감 2 ms인 새 A/B의 이용률 합과 최초 마감 충족 가능 여부를 구하세요.

  1. 이용률 합은 2/10+2/10=0.4입니다.

  2. 0부터 2 ms까지 한 CPU가 제공하는 실행량은 최대 2 ms입니다.

  3. 두 작업은 그때까지 합계 4 ms가 필요하므로 모두 완료할 수 없습니다.

이용률은 0.4지만 동시에 나온 첫 두 마감은 모두 만족할 수 없습니다.

비교할 점

기본의 모든 상대 마감=주기 가정을 뺀 뒤 같은 충분 조건을 재사용하지 않습니다.

모든 자원 조건을 함께 확인한다

표의 새 C를 받을 수 있나요? 별도 개선으로 실제 RAM 요구 상한을 70 MiB로 낮출 근거가 있다고 주면 다시 판정하세요. CPU와 I/O는 그대로입니다.

  1. CPU 합은 0.6≤0.8, I/O 합은 45≤50입니다.

  2. 원래 RAM 합은 300 MiB로 44 MiB 초과하여 거절합니다.

  3. 실제 C 요구를 70 MiB로 낮춘 경우 RAM 합은 250 MiB입니다.

원래는 RAM 조건 때문에 거절하며 실제 요구가 바뀐 두 번째 모형은 세 정책 조건을 만족합니다.

비교할 점

메모리 제한 숫자만 70으로 적고 실제 작업이 120을 요구하는 경우와 구분합니다.

종이와 본문으로 직접 해보기

항상 실행 가능한 두 형제 그룹의 가중치가100과300이고 다른 제한이 없는 이상적 비례 모델에서 비율을 구하라. 별도로 cpu.max=40000 100000의 의미를 해석하라.

힌트 보기

가중치의 합400으로 나눈다. CPU 인터페이스 시간 단위는 μs다.

풀이 보기

비례 모델의 비율은25%와75%다. cpu.max는100000μs 기간에 최대40000μs CPU 시간을 허용하는 대역폭 상한40%를 뜻한다. 이 상한만으로 최소 보장이나 모든 순간의 일정40% 실행을 약속하지 않는다.

오해와 반례

상한이나 높은 가중치를 설정하면 응답시간도 자동 보장된다.

상한은 최대량, 가중치는 경쟁 배분이다. CPU 대기 외의 차단·I/O·메모리 압력과 부하를 고려해야 지연 보장 범위를 정할 수 있다.

연습 1 · 값과 상태 예측

마감 2 ms인 A/B의 실행시간 상한을 각각 1 ms로 줄이고 다른 조건은 유지합니다. 첫 실행 일정과 이용률 합을 구하세요.

힌트 1

A를 0–1에, B를 1–2에 실행할 수 있습니다.

힌트 2

마감과 같은 시각의 완료를 허용합니다.

풀이와 답 확인

  1. 두 첫 작업은 2 ms까지 모두 끝납니다.

  2. 이용률 합은 1/10+1/10=0.2입니다.

A를 0–1 ms, B를 1–2 ms에 실행하면 첫 마감에 맞습니다. 이용률 합은 0.2입니다.

흔한 오답에서 다시 생각하기

이용률 0.2이므로 아무 일정이나 마감에 맞는다.

실제 일정의 준비 시각·우선순위·마감 조건을 함께 확인합니다.

연습 2 · 오류 찾아 고치기

실제 C의 필요 RAM은 여전히 120 MiB인데 memory.max만 70 MiB로 설정하면 표의 계획을 완전히 해결했다고 썼습니다. 고치세요.

힌트 1

상한은 실제 메모리 요구의 감소 증거가 아닙니다.

힌트 2

회수·할당 실패·작업 정확성도 따로 봅니다.

풀이와 답 확인

  1. 설정 제한과 실제 상한 측정치를 구분합니다.

  2. 실제 요구를 줄이는 변경과 그 검증을 수행해야 70 MiB 계획을 사용할 수 있습니다.

제한만 바꿨다는 사실로 필요한 데이터를 처리할 수 있거나 지연을 만족한다고 주장하지 않습니다.

연습 3 · 직접 만들어 보기

RAM을 70 MiB로 개선한 표에 D를 추가합니다. D는 CPU 비율 0.15, RAM 4 MiB, I/O 4단위입니다. 세 합계와 정책 판정을 구성하세요.

힌트 1

개선한 합계 0.6,250,45에서 시작합니다.

힌트 2

한 정책만 보지 않습니다.

풀이와 답 확인

  1. CPU 합계는 0.75, RAM은 254 MiB, I/O는 49단위입니다.

  2. 세 수치는 각각 0.8,256 MiB,50단위 이하입니다.

정한 세 수용 정책은 모두 통과합니다. 실제 전체 QoS를 검증한 결과는 아닙니다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

단일 CPU에서 D가 P보다 짧을 때 밀도 C/min(D,P)의 합≤1은 충분 조건입니다. 그 합이 1을 넘으면 반드시 불가능하다고 결론 내릴 수 있나요?

힌트 1

충분 조건의 역을 적용하지 않습니다.

힌트 2

정확한 마감 분석은 요구량과 시간 구간을 더 조사합니다.

풀이와 답 확인

  1. 밀도 합≤1이면 정한 이론 모델에서 가능한 집합을 판정할 수 있습니다.

  2. 그 조건을 만족하지 않은 집합에는 가능한 경우도 있으므로 별도 정확 분석이 필요합니다.

충분 조건 실패만으로 모든 일정의 불가능을 단정하지 않습니다.

두 서버가 각각 90% 빠르다는 것만으로 전체 확률은 정해지나요?

기본 독립 팬아웃을 공동 지연 자료로 확장합니다. 요청은 두 하위 결과를 모두 기다리고 각 하위가 정한 마감 안에 끝난 경우를 빠르다고 부릅니다. 추가 비용은 0이며 하위 하나라도 느리면 전체도 마감을 넘습니다. 각자의 빠른 확률이 같아도 둘의 실패가 얼마나 겹치는지에 따라 전체 성공률은 다릅니다.

아래 1000건은 실제 서비스 측정이 아닌 자체 표입니다. 분위수는 기본과 같은 nearest-rank 규칙으로 정렬한 N개 중 ceil(pN)번째를 고릅니다. 다른 예제의 늦은 요청 복제도 부작용 없는 읽기이며 추가 간섭과 취소 비용을 제외한 모델입니다. 실제 복제 요청이나 지연 측정은 수행하지 않았습니다.

긴 응답들의 위치를 본다

latency는 요청에서 응답까지 걸린 시간이다. tail latency는 분포의 느린 쪽 끝을 살펴보는 관점으로 p95/p99 같은 분위수를 사용한다. 같은 평균이어도 소수의 큰 값이 있으면 경험이 달라질 수 있다. 관측 수와 분위수 계산 규칙을 함께 적어야 숫자를 비교할 수 있다.

이번 예제는 정렬한 N개에서 p분위수를 ceil(pN)번째 값으로 정하는 nearest-rank 규칙을 쓴다. 자료가100개면 p99는99번째 값이다. 라이브러리별 보간 방식이 다를 수 있으며 표본p99 하나로 앞으로 모든 요청이 그 시간 안에 끝난다고 보장하지 않는다.

여러 하위 요청을 기다리면 최댓값이 중요하다

요청 하나가 여러 서버에 병렬로 일을 보내고 모두의 결과를 기다린다고 하자. 추가 비용을 무시하면 전체 지연은 가장 늦은 하위 요청의 지연이다. 각 서버가99% 확률로 기준 안에 끝나고 서로 독립이라면 k개 모두 기준 안에 끝날 확률은 .99^k다.

독립 가정이 없으면 단순 곱을 사용할 수 없다. 같은 네트워크나 호스트 장애 때문에 지연이 함께 움직일 수 있다. Google Research의 The Tail at Scale 공개 초록은 규모와 이용률이 커질 때 일시적인 긴 지연이 전체 서비스 성능을 지배할 수 있다고 설명한다. 아래 확률은 논문 측정치를 복사한 것이 아니라 자체 모델이다.

옆 작업의 영향과 원인을 분리한다

같은 CPU·캐시·메모리 대역폭·디스크를 쓰는 다른 작업 때문에 내 요청이 느려질 수 있다. CPU 제한 뒤의 throttling, 메모리 회수, I/O 대기를 구분하고 실행 중 관련 지표와 요청 시간을 함께 관측한다. 느린p99와 이웃 작업의 존재만으로 원인을 확정하지 않는다.

격리·수용량 조정·작업 분할이 도움될 수 있지만 한 자원만 관리했다고 모든 간섭이 없어지는 것은 아니다. 지연 원인에 맞는 비교 실험을 설계하고 같은 부하에서 평균과 tail을 함께 비교한다. 빠른 요청을 더 빠르게 만든 최적화가 드문 느린 요청을 악화시킬 수도 있다.

중간 과정을 따라가는 예제

자체100개 요청 자료 A는10ms짜리98개와100ms짜리2개다. 자료 B는8ms짜리98개와200ms짜리2개다. nearest-rank p99와 평균을 구하라. 모두 기다리는 독립 하위 요청10개 각각의 기준내 확률은.99다.

  1. A 합=98×10+2×100=1180ms, 평균11.8ms다. 정렬99번째는100ms여서p99=100ms다.

  2. B 합=98×8+2×200=1184ms, 평균11.84ms이며p99=200ms다. 대다수는 빨라졌지만 tail은 두 배다.

  3. 독립10개 모두 기준내 확률 .99^10≈.904382, 하나라도 기준을 넘을 확률≈.095618이다.

  4. 전체 기준내 확률은 각각99%보다 낮지만 독립/동일확률/전부기다림 가정의 계산이다.

평균11.8→11.84만 보면 큰 tail 악화를 놓칠 수 있다. 10개 병렬 팬아웃의 기준 초과 확률은 이 가정에서 약 9.56%다.

조건을 바꾸어 비교하기

같은 주변 확률과 다른 공동 확률

표에서 A/B 각 성공률과 전체 성공률을 구하세요. 각 성공률을 곱한 독립 예측과 비교하세요.

  1. A와 B는 각각 900/1000=90% 빠릅니다.

  2. 자체 공동 표에서 둘 다 빠른 비율은 860/1000=86%입니다.

  3. 독립을 가정한 계산은 0.9×0.9=81%지만 이 표와 다릅니다.

각 하위 성공률은 90%, 이 자체 공동 자료의 전체 성공률은 86%입니다.

비교할 점

주변 확률만으로 독립성을 주장하거나 공동 자료를 곱으로 덮지 않습니다.

복제의 완료 시간과 요청 수

부작용 없는 읽기 여섯 건이 0에 시작합니다. 원래 시간은 5,5,5,5,50,50 ms입니다. 10 ms까지 미완료인 두 건에만 복제를 시작하며 각각 추가 5 ms 뒤 성공합니다. 최초 성공 결과를 택하고 원본을 취소하며 간섭·취소 비용은 0입니다. 평균, nearest-rank p95와 호출 수를 비교하세요.

  1. 원래 평균은 (20+100)/6=20 ms이고 p95는 여섯 번째인 50 ms입니다.

  2. 복제를 쓴 완료는 5,5,5,5,15,15 ms이고 평균은 50/6=25/3 ms입니다.

  3. 새 p95는 15 ms이고 호출 수는 원래 여섯 개에 복제 둘을 더한 여덟 개입니다.

지정 모형에서 평균은 20 ms에서 25/3 ms, p95는 50 ms에서 15 ms로 줄지만 호출은 6에서 8로 늘어납니다.

비교할 점

간섭·비용과 부작용을 뺀 계산이므로 실제 공유 자원에서 같은 개선을 보장하지 않습니다.

종이와 본문으로 직접 해보기

자료 C는 10ms 값 99개와 1000ms 값 1개다. nearest-rank p99와 최대/평균을 구하라. 하위 요청100개를 기다리는 독립 모델의 .99^100도 비교하라.

힌트 보기

99번째와100번째의 위치를 나눈다.

풀이 보기

C의 p99=10ms, 최대1000ms, 평균(990+1000)/100=19.9ms다. p99만으로 최악을 알 수 없다. .99^100≈.366032로 모두 기준 내는 약 36.60%, 하나 이상 초과는 약 63.40%다.

오해와 반례

p99가 좋으면 모든 요청이 그 시간 안에 끝나고 병렬 서버를 늘려도 기준내 확률은 같다.

표본 분위수는 최댓값이 아니고 미래 보장도 아니다. 전부 기다리는 독립 팬아웃 모델에서는 서버 수가 늘수록 모두 기준내일 확률이 줄어든다.

연습 1 · 값과 상태 예측

각 하위가 100건씩 느린 1000건 자료에서 두 느림의 겹침이 0인 경우와 100인 경우의 전체 성공률은?

힌트 1

실패 합집합은 100+100−겹침입니다.

힌트 2

전체 성공은 1000에서 합집합을 뺍니다.

풀이와 답 확인

  1. 겹침 0이면 전체 실패 200건으로 성공 80%입니다.

  2. 겹침 100이면 전체 실패 100건으로 성공 90%입니다.

같은 각 성공률 90%에서도 전체 성공률은 각각 80%와 90%입니다.

흔한 오답에서 다시 생각하기

각 성공률이 같으니 모든 경우 전체는 81%다.

81%는 독립이라는 추가 가정의 결과입니다.

연습 2 · 오류 찾아 고치기

실제 네트워크를 공유하는 네 하위 요청의 각각 빠른 확률이 99%입니다. 독립 증거 없이 전체가 정확히 0.99의 네제곱이라고 기록했습니다. 고치세요.

힌트 1

주변 확률과 공동 확률을 나눕니다.

힌트 2

실패 합집합의 상한도 쓸 수 있습니다.

풀이와 답 확인

  1. 정확한 곱셈에는 독립성이 필요합니다.

  2. 실패 확률 각각 1%의 합집합은 최대 4%라 전체 성공은 적어도 96%입니다.

  3. 모두 성공은 어떤 한 하위 성공보다 높을 수 없어 최대 99%입니다.

주변 확률만으로 전체는 96% 이상 99% 이하라고 제한할 수 있지만 정확한 값을 정하지 못합니다.

공유 원인이 있어도 모든 확률은 무조건 곱한다.

공동 관측이나 독립 모델의 근거가 필요합니다.

연습 3 · 직접 만들어 보기

98개는 2 ms, 두 개는 102 ms인 자체 100건 표의 평균·p95·p99와 10 ms 마감 위반률을 구성하세요.

힌트 1

nearest-rank는 p95의 95번째와 p99의 99번째입니다.

힌트 2

실패한 두 건을 분모에서 빼지 않습니다.

풀이와 답 확인

  1. 전체 합은 98×2+2×102=400 ms입니다.

  2. 평균은 4 ms, p95는 2 ms, p99는 102 ms입니다.

  3. 마감 위반은 2/100=2%입니다.

흔한 오답에서 다시 생각하기

평균이 10보다 작으니 모든 요청이 마감 안이다.

평균은 개별 큰 지연을 제한하지 않습니다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

별도 간섭 모형에서 복제 대상은 원래 느린 두 요청으로 미리 고정하며 추가 복제는 하지 않습니다. 복제 완료 시각은 15 ms로 같지만 추가 부하로 기존 네 빠른 요청이 각각 5 ms에서 20 ms로 느려졌다고 정합니다. 새 평균과 원래 평균을 비교하세요.

힌트 1

두 느린 원본의 선택된 결과는 15 ms로 유지합니다.

힌트 2

새 자료는 20 네 개와 15 두 개입니다.

풀이와 답 확인

  1. 새 합은 4×20+2×15=110 ms입니다.

  2. 평균은 110/6=55/3 ms로 원래 20 ms보다 5/3 ms 작습니다.

  3. 네 빠른 요청은 실제로 15 ms씩 악화됐습니다.

전체 평균은 55/3 ms로 조금 개선되지만 네 요청의 지연은 악화됩니다.

기본 벤치마크의 경계·캐시를 실패 포함 지표로 확장합니다. 자체 100번 시도에서 A는 성공 80건이 10 ms, 실패 20건이 1 ms입니다. B는 성공 95건이 11 ms, 실패 5건이 1 ms입니다. 성공은 올바른 결과를 얻은 경우이며 실패도 시도 분모에 포함합니다. 실패 응답이 빠르다고 유효한 결과를 더 빨리 제공한 것으로 읽지 않습니다.

부하 발생기도 측정 대상의 일부입니다. 한 번에 요청 하나만 내고 응답을 받은 뒤 다음을 내면 느린 응답 중에 새 요청이 발생하지 않습니다. 외부에서 정해진 시각에 계속 도착하는 부하의 대기를 그 기록만으로 대표할 수 없습니다. 아래는 설명용 자료와 계획이며 실제 벤치마크·부하·자원 관측을 실행하지 않았습니다.

먼저 확인할 개념

    기본 측정 경계·실패 포함·부하 발생기 병목을 확인합니다.

  • tail latency·간섭

무엇의 시작과 끝을 재는가

벤치마크는 정의한 입력과 조건에서 성능을 측정하는 실험이다. 서버가 내부 함수를 실행한 시간과 클라이언트가 기다린 시간은 다르다. 네트워크와 큐 대기를 포함하는지, 실패 요청도 집계하는지, 초당 성공 처리량인지 전체 시도량인지 먼저 정한다.

환경에는 소프트웨어 버전, 빌드 설정, 하드웨어와 전원 상태, 자원 제한이 포함된다. 입력 크기와 동시 요청 수, 캐시 상태도 결과를 바꾼다. 조건을 다르게 놓고 수치만 비교하면 코드 변경의 효과와 환경 효과를 분리할 수 없다.

측정 도구와 부하 발생기도 시스템이다

짧은 작업은 시간 읽기나 로그 출력의 비용에 크게 영향을 받는다. 자체 모델에서 실제100μs 작업에 측정 20μs가 더해지면 관측120μs다. 실제 작업을80μs로 줄이면 관측100μs여서 실제 개선비100/80=1.25와 관측비120/100=1.2가 다르다. 측정 비용을 무조건 일정하다고 빼는 것도 실제 검증이 필요한 가정이다.

부하 발생기가 단일 스레드나 네트워크 때문에 충분한 요청을 못 보내면 서버의 최대 수용량을 측정하지 못한다. Brendan Gregg의 Active Benchmarking은 측정 중 다른 관측 도구로 실제 제한 요소를 확인하도록 설명한다. 도구 이름을 나열하는 것과 병목의 증거를 확보한 것은 다르다.

예열·반복·실패를 공정하게 다룬다

첫 요청이100ms, 예열 뒤10ms라면 캐시가 비어 있는 실험과 채워진 실험을 따로 보고한다. 한 후보는 처음 실행하고 다른 후보는 예열 뒤 실행하면 비교가 치우친다. 사용자에게 첫 실행이 중요한 경우 첫 값을 없애 버리는 것도 잘못이다. 비교 목적에 맞게 cold와warm을 구분한다.

한 번의 최고값만 선택하거나 실패한 느린 요청을 빼면 성능이 좋아 보일 수 있다. 같은 부하와 조건의 반복에서 성공률·처리량·분포를 함께 보고하고 변동을 보존한다. 관측은 원인을 자동 증명하지 않으므로 변경 한 가지씩 비교하고 관련 자원 지표로 해석을 뒷받침한다.

중간 과정을 따라가는 예제

종이 기록에서 후보 A는 cold 첫 실행 100ms, warm 두 실행 10/10ms다. B는 이미 예열된 상태의 세 실행 12/12/12ms다. 세 값의 평균만 비교한 결론과 warm 성능만 비교한 결론을 나눠라.

  1. A 전체 평균(100+10+10)/3=40ms다. B 평균12ms다. 단순 평균 비40/12≈3.33으로 B가 좋아 보인다.

  2. A는cold를 포함하고 B는 포함하지 않아 동일 조건의 세 실행 비교가 아니다.

  3. warm 기록만 비교하면 A10ms, B12ms로 이 자료에서는 A가 더 빠르다. 시간비12/10=1.2다.

  4. cold A 100ms도 가상 기록에 존재하므로 삭제해 없던 것으로 표시하지 않는다. B cold 측정을 추가해야 첫 실행 성능을 공정하게 비교한다.

초기 상태가 달라 전체 평균의 우열을 코드 효과라고 단정할 수 없다. cold/warm 범위를 나눠 보고하고 빠진 조건은 추가 측정한다.

조건을 바꾸어 비교하기

시도 평균과 성공 조건부 평균

표의 전체 평균, 성공률, 성공 조건부 평균을 계산하고 A가 모든 품질에서 우월하다는 결론을 평가하세요.

  1. A 전체 평균은 (80×10+20×1)/100=8.2 ms입니다.

  2. B 전체 평균은 (95×11+5×1)/100=10.5 ms입니다.

  3. 성공률은 각각 80%와 95%, 성공 조건부 평균은 10 ms와 11 ms입니다.

A는 지정 평균과 성공 응답 시간은 작지만 B는 성공률이 높습니다. 모든 품질에서 A가 우월하지 않습니다.

비교할 점

성공 조건부 평균의 분모 80/95와 전체 시도 평균의 분모 100을 섞지 않습니다.

발생기 상한과 서버 최대량

응답마다 정확히 5 ms가 걸리고 추가 비용이 없는 한 요청씩 발생기가 1초 동안 측정합니다. 서버가 다중 동시 요청에서 초당 1000건 처리할 수 있다는 별도 가정이 있습니다. 이 단일 발생기로 확인한 최대 완료 수와 서버 최대 검증 여부는?

  1. 한 주기는 5 ms입니다.

  2. 1000/5=200번의 응답 대기를 셉니다.

  3. 이 발생기는 서버의 동시 처리 가능량까지 부하를 공급하지 않습니다.

지정 단일 발생기의 완료는 200건입니다. 그 측정으로 별도 서버 수용량 1000건/초를 검증하지 못합니다.

비교할 점

발생기에서 관측한 200을 서버의 절대 최대량으로 바꾸지 않습니다.

종이와 본문으로 직접 해보기

가상 실제 작업 100→80μs, 각각 측정 비용 20μs일 때 두 관측과 개선비를 구하라. 별도로 기준 200ms→150ms의 시간 감소율과 speedup을 구별하라.

힌트 보기

감소율은 감소량/기준, speedup은 기준 시간/새 시간이다.

풀이 보기

관측 120→100μs로 관측 speedup은 1.2, 실제는 1.25다. 200→150ms의 감소율은 50/200=25%, speedup은 200/150=4/3≈1.333이다. 33.3% 시간 감소라고 바꾸면 안 된다.

오해와 반례

가장 빠른 한 번과 성공한 요청만 집계하면 시스템 성능을 정확하게 대표한다.

성공 조건부 평균의 분모와 전체 시도 분모를 나눕니다.

풀이와 답 확인

  1. 이용률 합은 3/20+3/20=0.3입니다. 첫 두 작업은 4 ms까지 6 ms가 필요해 둘 다 마감에 맞출 수 없습니다.

  2. 전체 실패는 50+50−20=80건이며 성공률은 920/1000=92%입니다.

  3. 전체 평균은 (90×12+10×2)/100=11 ms입니다. 성공률은 90%, 성공 조건부 평균은 12 ms입니다.

  4. 모든 결과는 자체 입력의 손계산이고 실제 커널·서비스·학생 실험은 미수행입니다.

첫 모형은 이용률 합 0.3이지만 첫 마감을 모두 만족하지 못합니다. 공동 자료의 전체 성공률은 92%입니다. 마지막 시도 자료의 전체 평균은 11 ms, 성공률은 90%, 성공 조건부 평균은 12 ms입니다.

해결한 뒤 점검할 것

  • 이론 조건의 마감과 주기 가정을 확인합니다.

  • 독립 가정 없이 주변 확률을 곱하지 않습니다.

  • 성공과 실패를 같은 시도 분모로 보존합니다.

  • 모형 결과와 실제 관측을 구분합니다.

보강 자료의 출처와 확인 범위
  • Linux kernel: Deadline Task Scheduling

    실제 공식 §1과 §2.1, §3.1–3.4 및 §4–4.1 본문을 읽었다. WCET/D/P, 마감=주기 조건, 밀도 충분 조건은 필요 조건이 아니라는 설명, 다중 CPU와 admission 및 실제 요구와 runtime 관계를 대조했다.

  • Dean and Barroso: The Tail at Scale

    실제 Google Research 공개 초록 전체를 읽었다. 규모·이용률이 커질 때 일시적 긴 지연이 전체 성능을 지배할 수 있다는 동기를 대조했다. 논문 본문이나 복제 기법의 실측을 읽었다고 주장하지 않으며 공동 확률과 복제 일정은 자체 모델이다.

  • Brendan Gregg: Active Benchmarking

    실제 원저자 페이지 전체를 읽었다. 실행 중 다른 관측으로 진짜 제한을 확인하는 Summary/Active Benchmarking, 이웃·자원제한·단일 발생기·버전·비현실 부하의 Problem Checklist와 잘못된 측정에 통계만 적용하는 문제를 대조했다. 자체 수치는 실측이 아니다.

  • Linux kernel: Control Group v2

    이번 연속 집필의 앞선 07단원에서 실제 공식 CPU max/burst와 Memory Interface current/high/max 본문을 읽은 범위를 재사용했다. memory.max가 실제 요구량 감소나 예약 증거가 아니라는 범위를 대조했으며 이번 단원에서 문서 전체를 새로 읽었다고 주장하지 않는다.

짧은 마감 모형에서 CPU 이용률 합은 0.4이지만 첫 2 ms 안에 필요한 실행시간은 4 ms입니다. 두 작업의 실행시간 상한을 각각 1 ms로 바꾸면 첫 작업은 1 ms에, 둘째 작업은 2 ms에 완료하며 CPU 이용률 합은 0.2입니다. 세 자원 표에서 CPU 요구 비율 합은 0.6, RAM 요구 합은 300 MiB, I/O 요구 합은 45단위입니다. 개선 후 RAM 요구 합은 250 MiB입니다. 작업 D를 추가하면 CPU 요구 비율 합은 0.75, RAM 요구 합은 254 MiB, I/O 요구 합은 49단위입니다. 자체 공동 자료의 전체 성공률은 86%입니다. 같은 주변 성공 확률에서도 실패의 겹침을 바꾸면 전체 성공률은 80% 또는 90%가 됩니다. 네 하위 작업의 주변 성공 확률이 각각 99%라는 정보만 있을 때 전체 성공 확률은 96% 이상 99% 이하입니다. 원래 복제 예제의 평균 지연은 20 ms이고 p95 지연은 50 ms입니다. 복제 후 평균 지연은 25/3 ms이고 p95 지연은 15 ms입니다. 간섭 조건을 바꾸면 평균 지연은 55/3 ms입니다. 100건의 지연 표에서 평균 지연은 4 ms, p95 지연은 2 ms, p99 지연은 102 ms이고 마감 위반률은 2%입니다. 시도 전체를 포함한 A의 평균 지연은 8.2 ms이고 B의 평균 지연은 10.5 ms입니다. A의 성공률은 80%이고 B의 성공률은 95%입니다. 수정한 A의 평균 지연은 9.1 ms이고 성공률은 90%입니다. 단일 발생기가 만드는 요청은 1초에 200건입니다. 측정 교란 예제의 두 관측값은 45 μs와 50 μs입니다. 전이 과제에서 CPU 이용률 합은 0.3, 짧은 마감 안의 실행 요구는 6 ms, 공동 성공률은 92%입니다. 전이 자료의 시도 전체 평균 지연은 11 ms이고 성공한 시도에 한정한 평균 지연은 12 ms입니다. 이 값과 조건은 자체 이론 모델의 자료로 손대조했습니다.
