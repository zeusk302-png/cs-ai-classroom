CPU가 쓰는 주소를 그대로 장치에 주면 같은 바이트를 찾을까?

주소는 누가 읽는지에 따라 의미가 달라질 수 있다. 자체 모형에서 같은 256바이트 버퍼의 CPU 가상 시작은 X=0x1000, 물리 시작은 Y=0x8000, DMA 매핑이 돌려준 장치 주소는 Z=0x2000이다. CPU가 offset 12를 읽을 주소는 X+12=0x100C이고 장치에 전달할 주소는 Z+12=0x200C다. 물리 주소 0x800C가 이 장치의 DMA 주소와 같다고 가정하지 않는다. 실제 매핑의 성공·허용 범위·수명은 먼저 확인해야 한다.

흩어진 메모리를 scatter/gather 목록으로 전달할 수도 있다. 자체 입력 길이 [128,128,64,192]의 네 항목을 매핑했더니 앞의 두 항목이 장치 관점에서 합쳐져 [256,64,192]의 세 항목이 됐다고 정한다. 장치에는 매핑 결과의 세 항목을 설정하지만 Linux DMA API의 목록 unmap과 sync에 전달하는 nents는 원래 네 항목이다. 두 개수는 서로 다른 목록을 설명하므로 이름과 함께 보존한다.

coherent DMA 메모리는 CPU와 장치가 변경 내용을 일관되게 볼 수 있도록 하지만, 모든 쓰기의 관찰 순서까지 자동으로 맞추는 뜻은 아니다. 공식 가이드의 descriptor 예는 주소를 먼저 쓰고 쓰기 barrier를 거친 다음 유효 표시를 쓰도록 설명한다. 유효 표시가 먼저 보이면 장치가 오래된 주소를 읽을 수 있다는 별도 문제다. 실제 장치 프로토콜이 요구하는 barrier와 완료 조건을 확인해야 한다.

진행 중 버퍼를 다시 쓰는 것도 주소 계산과 별개의 책임이다. streaming 매핑에서는 장치가 사용하는 동안 CPU가 임의로 내용을 고쳐서는 안 된다. 반복 사용 때 CPU용 sync와 장치용 sync를 필요한 방향으로 수행하고, 마지막 작업이 실제 끝났을 때 대응 unmap을 수행한다. 이 설명은 드라이버를 실행한 결과가 아니라 공식 계약을 읽고 만든 주소·수명 연습이다.

장치의 언어를 감추는 드라이버

응용프로그램은 보통 파일 읽기 같은 공통 인터페이스를 사용한다. 커널의 파일·블록 계층은 필요한 작업을 드라이버로 전달한다. 드라이버는 특정 장치의 명령 형식과 상태 규칙에 맞추어 요청을 설정하고, 완료나 오류를 위 계층에 돌려주는 코드다. 각 응용프로그램이 장치 레지스터를 직접 제어할 필요가 줄어든다.

교육용 장치는 상태 레지스터로 준비 여부, 명령 레지스터로 할 일, 데이터 레지스터로 값을 주고받는다고 생각할 수 있다. 실제 장치는 더 복잡한 큐와 규칙을 쓴다. 메모리 매핑 I/O는 주소를 통해 장치 레지스터에 접근하는 방식이며 그 주소가 일반 RAM처럼 동작한다는 뜻은 아니다.

완료를 묻거나 완료 소식을 받는다

폴링은 CPU가 상태를 반복해서 확인한다. 인터럽트 방식에서는 요청을 시작한 뒤 기다리는 프로세스를 재우고 다른 일을 할 수 있다. 장치 완료 신호에 따라 커널의 처리기가 상태와 오류를 확인하고 기다리는 작업을 깨운다. 신호를 받았다는 사실과 요청 전체가 성공했다는 판정은 구별해야 한다.

아주 짧은 장치 작업에서는 인터럽트 처리와 문맥 전환 비용이 폴링보다 클 수 있다. 신호가 너무 잦으면 처리만 하느라 유용한 일을 못 할 수 있다. 여러 완료를 묶는 방식은 신호 수를 줄이지만 응답 지연을 늘릴 수 있으므로 인터럽트가 항상 더 빠르다는 결론은 성립하지 않는다.

데이터 운반도 CPU가 계속 해야 할까?

프로그램된 I/O에서는 CPU가 데이터 전송을 직접 수행한다. DMA에서는 커널과 드라이버가 전송 위치·길이 등을 설정하고 DMA 엔진이 메모리와 장치 사이 전송을 맡는다. 전송이 끝나면 완료를 확인한다. CPU가 매 데이터 조각을 복사하는 부담을 줄여 다른 작업과 겹칠 여지가 생긴다.

DMA도 설정과 완료 처리, 유효한 메모리 관리, 오류 처리가 필요하다. 전송 자체의 시간과 버스 사용량이 사라지지 않으며 버퍼를 너무 일찍 재사용하면 안 된다. 아래 수치는 이 원리를 비교하기 위한 가상 비용 모델이고 실제 하드웨어 측정 결과가 아니다.

중간 과정을 따라가는 예제

가상 장치는 4바이트 단위 PIO 데이터 이동마다 CPU 2사이클을 쓴다. DMA는 4096바이트를 한 요청으로 전송하며 CPU 설정 40사이클과 완료 처리 20사이클만 센다. 두 방식의 CPU 비용은?

  1. PIO 이동 횟수는 4096/4=1024회다.

  2. PIO CPU 비용은 1024×2=2048사이클이다.

  3. DMA CPU 비용은 40+20=60사이클이다. 전송 엔진의 시간과 메모리 버스 비용은 이 합에 포함하지 않는다.

이 모델에서 데이터 이동 관련 CPU 비용은 2048 대 60사이클이다. 전체 완료 시간이 같은 비율로 줄었다고 해석할 수는 없다.

offset 12의 동일한 바이트를 CPU와 장치가 각각 접근할 때 사용할 주소는?

  1. CPU 가상 시작 X에 12를 더해 0x100C를 얻는다.

  2. 장치는 성공한 매핑의 Z에 12를 더해 0x200C를 사용한다.

  3. 물리 Y+12=0x800C를 DMA 주소라고 대체하지 않는다.

CPU 0x100C, 장치 0x200C다. 매핑 실패나 이미 해제된 매핑에서는 사용할 수 없다.

비교할 점

주소 계산이 맞아도 매핑 방향·범위·수명 조건을 따로 확인한다.

목록 길이가 줄었을 때

입력 네 항목이 장치 목록 세 항목으로 합쳐졌다. 설정할 descriptor 수와 unmap nents는?

  1. 입력 길이 합은 128+128+64+192=512다.

  2. 결과 길이 합도 256+64+192=512이며 장치 항목 수는 3이다.

  3. 원래 입력 nents=4를 unmap 및 해당 목록 sync 계약에 사용한다.

장치 설정 3항목, unmap nents 4다. 길이 합은 같지만 항목 수의 역할은 다르다.

비교할 점

map이 0을 반환하는 실패 경로에서는 정상 매핑 목록처럼 전송을 시작하지 않는다.

힌트 보기

PIO 데이터 단위 수를 w라 두면 2w=60이다.

풀이 보기

오해와 반례

DMA를 쓰면 CPU는 I/O에 전혀 관여하지 않는다.

드라이버가 요청과 버퍼를 설정하고 완료·오류를 처리한다. 예제에서도 CPU 비용이 60사이클 남는다. DMA는 데이터 운반 부담을 줄이는 방식이다.

연습 1 · 값과 상태 예측

offset을 255로 바꿔 CPU와 장치 주소를 구하고, offset 256은 어떻게 판정할지 적어라.

힌트 1

버퍼 길이는 256바이트다.

힌트 2

시작부터 유효 offset은 0–255다.

풀이와 답 확인

  1. 255는 0xFF라 CPU 주소는 0x10FF, DMA 주소는 0x20FF다.

  2. 256은 다음 바이트의 위치지만 이 버퍼의 유효 바이트 범위 밖이다.

마지막 유효 바이트는 offset 255다. 주소 덧셈이 가능하다는 이유로 offset 256을 전송하지 않는다.

흔한 오답에서 다시 생각하기

덧셈이 넘치지 않았으니 256도 유효하다.

주소 산술과 할당·매핑 범위 검사는 다른 조건이다.

연습 2 · 오류 찾아 고치기

장치 항목이 3개라 dma_unmap_sg에도 nents=3을 전달한다고 썼다. 고쳐라.

힌트 1

원래 목록은 네 항목이다.

힌트 2

장치에 보이는 결과 개수와 API가 요구하는 입력 개수를 나눈다.

풀이와 답 확인

  1. 장치에는 반환된 세 매핑 항목을 설정한다.

  2. unmap에는 원래 목록과 nents=4를 전달한다.

  3. 해당 목록 sync에도 원래 nents=4를 보존한다.

세 개는 descriptor 설정용 개수다. 모든 함수 인자에 같은 개수를 복사하지 않는다.

개수가 줄었으니 원래 입력 목록 정보는 버려도 된다.

매핑 해제·동기화 계약에 원래 항목 수가 다시 필요하다.

연습 3 · 직접 만들어 보기

descriptor의 주소와 유효 표시를 게시하는 순서를 만들고, 완료 뒤 마지막 버퍼 반환 조건을 붙여라.

힌트 1

coherent는 모든 저장 순서의 자동 보장이 아니다.

힌트 2

장치가 여전히 사용하는 메모리를 반환하면 안 된다.

풀이와 답 확인

  1. 주소와 장치가 먼저 읽어야 할 내용을 쓴다.

  2. 해당 장치·DMA 계약의 필요한 쓰기 barrier 뒤 유효 표시를 게시한다.

  3. 진짜 완료와 결과를 확인하고 마지막 사용에 대응하는 unmap·반환을 수행한다.

내용 준비→필요한 순서 보장→유효 게시→완료 확인→반환이다. 실제 장치 계약을 별도로 적용해야 한다.

흔한 오답에서 다시 생각하기

coherent이면 주소보다 유효 표시를 먼저 써도 안전하다.

가시성 일관성과 descriptor 필드 관찰 순서는 별개의 조건이다.

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

8바이트 쓰기가 세 바이트만 성공한 뒤에는 어느 위치에서 다시 시작할까?

자체 출력 상태기계는 ASCII ABCDEFGH의 여덟 바이트를 순서대로 보내며, 양의 반환만큼 누적 전달량을 늘린다. 하부 write 결과가 3, -1/EAGAIN, 2, 3이라고 정하면 요청 크기는 각각 8, 5, 5, 3바이트이고 시작 offset은 각각 0, 3, 3, 5다. 전달한 부분은 ABC, 없음, DE, FGH다. EAGAIN에서는 기다릴 조건을 마련하고 같은 남은 부분을 다시 시도하며 처음부터 전체를 중복 전송하지 않는다.

이 상태표는 프로그램이 직접 하부 쓰기를 관리하는 교육 모형이다. stdio 내부의 실패 후 버퍼 상태가 정확히 같은 방식이라는 주장이 아니다. 양수 요청의 write가 0을 반환한 경우에도 이 모형은 진행 없음으로 다뤄 별도 오류 처리나 제한된 재시도 정책으로 넘긴다. 읽기의 EOF 의미를 쓰기에 그대로 옮기거나 무한히 바쁜 재시도를 하지 않는다.

전달 누적 8은 하부 write가 여덟 바이트를 받아들였다는 기록이다. 영구 저장까지 완료했다는 기록은 아니다. stdio로 출력했다면 사용자 공간에 남은 데이터가 있으므로 fflush의 성공을 확인한 다음 파일 fsync의 결과를 확인해야 한다. 파일 fsync를 먼저 성공시켜도 아직 라이브러리에 남은 새 바이트를 동기화한 증거가 되지 않는다.

fflush 성공 뒤 fsync 실패가 나면 영구 저장 완료를 확정하지 못한다. 일부 변경이 저장됐을 수 있어 “모두 저장됨”과 “전혀 저장 안 됨” 모두 단정하지 않는다. 새 이름의 디렉터리 항목까지 보존하려면 파일의 동기화와 디렉터리 동기화를 별도로 확인한다. 실제 장애 복구 시험과 문서 계약에 따른 상태 판정은 구별한다.

버퍼는 속도와 단위의 차이를 흡수한다

버퍼링은 데이터를 잠시 모아 두거나 생산자와 소비자의 진행 속도를 맞추는 방식이다. 문자 몇 개마다 전송하기보다 블록으로 모으면 작은 요청의 반복을 줄일 수 있다. C의 stdio는 비버퍼·줄 버퍼·블록 버퍼 모드를 제공한다. 줄 버퍼는 줄바꿈 등 정해진 조건에, 블록 버퍼는 버퍼가 차거나 명시적 비우기 등에 따라 데이터를 내보낸다.

버퍼가 있다는 이유로 모든 API 호출이 정확히 한 번의 시스템 호출에 대응하지는 않는다. 라이브러리 구현과 전송 크기, 오류 등에 따라 달라진다. 아래 묶음 수는 완전히 정한 가상 규칙의 결과다. 버퍼를 직접 제공하는 경우에는 라이브러리가 사용하는 동안 그 메모리 수명을 유지해야 한다.

캐시는 다시 사용할 사본을 남긴다

캐싱은 다시 요청할 가능성이 있는 데이터를 보관하여 다음 접근 비용을 줄이는 방식이다. 파일 블록을 캐시에 남기면 같은 블록의 재읽기에서 장치 접근을 줄일 수 있다. 버퍼의 주목적이 흐름과 묶음 조절이라면 캐시의 주목적은 재사용이다. 한 저장 공간이 두 역할을 함께 할 수도 있으므로 이름만으로 동작을 판단하지 않는다.

캐시는 용량과 교체 정책을 가진다. LRU는 최근 사용된 항목을 남기고 가장 오래 사용되지 않은 항목을 내보낸다. 적중은 필요한 항목이 현재 캐시에 있다는 뜻이다. 이것만으로 전원이 꺼져도 값이 보존된다는 뜻은 아니며 이 단원의 파일 블록 캐시 모델을 CPU 캐시의 모든 규칙과 동일시하지 않는다.

어디까지 도착했는지 따로 확인한다

stdio 출력 버퍼에 든 데이터는 fflush의 성공으로 하부 쓰기 경로에 전달된다. fflush는 사용자 공간 출력 버퍼를 비우는 작업이고 저장장치까지의 영구 보존을 보장하는 작업은 아니다. write가 성공해도 실제 영구 저장을 보장하지 않는다. fsync는 해당 파일의 변경 데이터와 관련 메타데이터를 동기화하며 오류도 확인해야 한다.

stdio로 파일을 썼다면 아직 라이브러리에 남은 데이터를 먼저 fflush로 내보내고 성공을 확인한 뒤 파일 디스크립터에 fsync를 적용하는 순서를 생각한다. 새 파일의 이름 같은 디렉터리 항목은 파일 fsync만으로 보존이 보장되지 않아 해당 디렉터리의 동기화도 별도 문제다. 읽기에 새 값이 보인다는 사실과 장애 후 복구되는 사실을 구별한다.

먼저 취소를 요청한 버퍼는 바로 다음 작업에 써도 될까?

등록 순서·완료 순서·결과 회수 순서는 다를 수 있다. 자체 두 슬롯 모형에서 S0의 세대 1은 A 요청을, S1의 세대 1은 B 요청을 담으며 각각 최대 네 바이트를 읽는다. B가 먼저 두 바이트로 완료되면 B 상태와 결과를 확인하고 그 두 바이트만 소비한다. A가 진행 중이면 A 제어 블록과 버퍼는 계속 유지한다. 두 요청을 배열 순서만으로 혼동하지 않는다.

POSIX AIO의 aio_cancel은 취소 시도다. AIO_NOTCANCELED이면 적어도 일부 요청이 계속 진행하므로 각 요청의 상태를 확인해야 한다. AIO_ALLDONE은 대상들이 이미 끝났다는 뜻이며 전부 취소 성공이나 전부 읽기 성공이라는 뜻은 아니다. 실제 취소된 요청은 ECANCELED 상태와 -1 결과로 처리한다. aio_return은 aio_error가 EINPROGRESS가 아닌 뒤 해당 요청마다 한 번만 회수한다.

자체 슬롯 관리기는 요청을 완료 확인하고 결과를 회수한 다음에만 슬롯을 재사용하며 새 요청마다 세대를 증가시킨다고 정한다. B의 S1 세대 1 결과를 회수한 뒤 C를 S1 세대 2에 넣었다면 뒤늦게 온 B 세대 1 중복 알림을 C의 완료로 소비해서는 안 된다. 실제 API가 이 세대 필드를 제공한다는 뜻이 아니라, 재사용 가능한 저장 공간과 작업 정체성을 구별하는 자체 설계다. 상태 판정과 재사용은 필요한 동기화 아래 수행한다.

비동기 겹침도 작업 의존성에 따라 달라진다. 자체 모형에서 A는 8ms에 완료되고 B는 3ms에 완료되며, 독립 CPU 작업은 5ms 걸린다. 셋을 t = 0에 시작하면 모두 끝나는 때는 max(8, 3, 5) = 8ms다. 하지만 CPU 작업이 A 데이터를 필요로 하면 8ms부터 5ms를 수행하여 13ms다. 등록 시각·요청 수·비동기라는 이름만으로 최종 완료 시간이나 데이터 성공을 결정하지 않는다.

먼저 확인할 개념
  • 장치가 쓰는 버퍼 수명

    장치·진행 요청이 보유 중인 메모리를 조기에 바꾸지 않는다.

  • 실제 결과와 목표 길이

    네 바이트 요청이 두 바이트 완료하면 두 바이트만 유효하다.

대기 방식과 완료 방식을 나누어 본다

블로킹 읽기는 현재 준비된 조건에 따라 호출한 흐름을 기다리게 할 수 있고 반환값으로 실제 읽은 양을 알려준다. 논블로킹 읽기는 해당 대상에 지금 데이터가 없어 대기할 상황이면 EAGAIN 또는 대상에 따라 EWOULDBLOCK으로 돌아올 수 있다. 논블로킹은 기다리지 않는 인터페이스 조건이며 요청을 계속 수행하여 나중에 완료 결과를 통지하는 비동기 요청과 구별한다.

비동기 I/O는 등록과 완료 확인을 분리한다. POSIX AIO에서는 aio_read로 요청을 등록하고 aio_error로 상태를 확인한 뒤 완료된 요청의 aio_return으로 결과를 얻는다. 준비 이벤트는 지금 시도할 기회이고 요청 완료는 특정 작업의 결과이므로 혼동하지 않는다. 파일·소켓·API마다 지원과 의미가 다르다.

완료 전에는 아직 장치가 버퍼를 사용한다

진행 중인 요청의 제어 블록과 버퍼는 유효하게 유지하고 임의로 변경하거나 재사용하지 않는다. 완료를 확인한 뒤 실제 결과에 맞추어 버퍼를 소비한다. 요청 A를 먼저 등록해도 B가 먼저 완료될 수 있으므로 각 요청의 정체성과 결과를 연결해야 한다. 취소 호출은 취소를 시도하는 것이며 무조건 즉시 작업이 끝났다는 증명이 아니다.

비동기라는 이름이 CPU 작업이나 내부 스레드가 전혀 없다는 뜻도 아니다. Linux의 POSIX AIO에 대한 glibc 구현은 사용자 공간 스레드를 사용한다. 이 구현 설명을 모든 비동기 I/O API로 일반화하지 않는다. 프로그램의 다른 작업이 독립적일 때 겹칠 수 있지만 같은 버퍼의 결과를 먼저 요구하면 기다려야 한다.

요청 크기와 완료 크기는 다르다

read는 최대 count바이트를 요청하며 양의 짧은 반환은 오류가 아닐 수 있다. 양수 count로 호출하여 0이 돌아오면 EOF를 해석한다. count를 0으로 호출하여 0이 돌아온 경우까지 EOF라고 결론내리지 않는다. 음수 반환은 errno를 확인하고 신호 중단과 지금 준비되지 않음 같은 상황을 구별한다.

write도 짧게 성공할 수 있으므로 실제 처리량만큼 위치를 전진시키고 남은 부분을 처리해야 한다. 비동기 요청 역시 등록한 버퍼 크기만큼 반드시 읽힌다는 보장이 없다. 결과의 양수 길이·EOF·오류를 구분하는 책임은 비동기를 선택해도 사라지지 않는다.

중간 과정을 따라가는 예제

가상 비동기 읽기에서 t=0에 8바이트 버퍼 요청을 등록하고 t=5ms에 3바이트로 성공 완료한다. 별도 작업은 4ms 걸리며 이 버퍼를 참조하지 않는다. 등록·확인 비용은 모델에서 0으로 둔다. 겹쳐 수행할 때와 읽기 후 별도 작업을 할 때 시간은?

  1. 버퍼와 제어 블록을 0–5ms 동안 유지한다. 별도 작업은 0–4ms에 수행한다.

  2. 전체 완료는 max(5,4)=5ms다. 순서대로 하면 5+4=9ms다.

  3. 완료 시 소비 가능한 길이는 실제 결과 3바이트이며 요청 크기 8바이트가 아니다.

가정한 총 시간은 5 대 9ms, 유효 데이터는 3바이트다. 실제 시스템 벤치마크나 모든 작업의 가속 보장은 아니다.

취소 시도와 요청 종료는 다르다.

힌트 2

A 상태가 아직 EINPROGRESS일 수 있다.

풀이와 답 확인

  1. A 상태를 확인하고 진행 중이면 제어 블록·버퍼를 유지한다.

  2. 종료 상태에서 A의 결과를 요청당 한 번 회수하고 성공·취소·기타 오류를 구별한다.

  3. 그 뒤 자체 재사용 계약을 만족할 때 새 세대로 C를 등록한다.

취소 호출의 반환만으로 재사용하지 않는다.

흔한 오답에서 다시 생각하기

NOTCANCELED는 취소 처리 함수가 돌아왔다는 뜻이니 종료다.

일부 작업이 계속 진행할 수 있다는 결과이므로 실제 요청 종료를 따로 확인해야 한다.

연습 3 · 직접 만들어 보기

대상 A/B에 aio_cancel이 ALLDONE을 반환했다. A는 성공하여 3바이트를 반환했고 B는 ECANCELED 상태와 -1 결과를 얻었다. 결과 기록을 작성하라.

힌트 1

이미 종료됨은 성공 종류를 확정하지 않는다.

힌트 2

각 요청의 상태와 결과를 한 번씩 연결한다.

풀이와 답 확인

  1. A는 종료 성공으로 결과 3바이트를 회수·소비한다.

  2. B는 취소 종료로 오류 ECANCELED와 결과 -1을 기록하고 성공 데이터로 쓰지 않는다.

  3. 각 결과 회수와 수명 정리를 별도로 완료한다.

종료된 둘 중 A 성공·B 취소다. ALLDONE 자체로 둘 다 성공이나 둘 다 취소를 추정하지 않는다.

흔한 오답에서 다시 생각하기

ALLDONE이면 결과는 자동으로 전부 성공이다.

종료 여부와 성공·취소·오류의 결과 종류를 혼동했다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

5ms 걸리는 CPU 작업이 A 결과를 필요로 하도록 조건을 바꾸자. A는 8ms에 완료되고 B는 3ms에 완료될 때 전체 종료는? 다른 조건은 그대로다.

힌트 1

CPU 작업은 A 완료 전에 시작할 수 없다.

힌트 2

B는 이미 3ms에 끝난다.

풀이와 답 확인

  1. A를 8ms에 완료 확인한 뒤 CPU 작업을 8–13ms에 수행한다.

  2. B는 3ms에 끝나므로 13ms보다 늦지 않다.

  3. 전체 종료는 13ms다.

독립일 때의 8ms와 결과 의존일 때의 13ms 차이는 의존성 조건이다.

흔한 오답에서 다시 생각하기

비동기라면 데이터 의존성도 무시하고 CPU 작업을 0ms부터 수행한다.

아직 없는 A 결과를 사용하는 작업은 그 결과 확인 뒤 시작해야 한다.

한 단계 더

A와 B 요청을 각각 식별해 등록하고 B가 먼저 2바이트, A가 나중에 4바이트 완료했다고 해 보자. 각 요청의 버퍼·길이를 기록해야 하며 등록 순서대로 결과를 붙이면 데이터 의미가 뒤바뀔 수 있다. 별도 작업이 읽기 결과를 필요로 하면 위 4ms 작업을 0ms에 시작할 수 없다는 조건도 비교하자.

다른 문제에 적용하기

주소·전달·종료 기록을 분리하는 I/O 보고

보고서가 자체 버퍼의 CPU 가상 시작 X = 0x1000, 물리 시작 Y = 0x8000, DMA 시작 Z = 0x2000에서 offset 12의 장치 주소를 0x800C라고 했다. 원래 네 항목의 SG가 세 항목으로 매핑되자 unmap nents도 3이라고 했다. ABCDEFGH의 첫 write가 3바이트를 반환한 뒤 EAGAIN에서 처음부터 8바이트를 다시 보냈고, 진행 중 A의 취소 결과 NOTCANCELED 뒤 버퍼도 반환했다. 네 문제를 고치고 저장 완료를 확인할 조건을 적어라.

힌트 1

주소와 항목 수의 관점·역할을 먼저 정한다.

힌트 2

실제 전달량과 종료 확인·회수·동기화 성공을 각각 기록한다.

풀이와 답 확인

  1. DMA 장치 주소는 매핑 Z + 12 = 0x200C이며 CPU 가상 주소는 0x100C다.

  2. 장치 설정 개수 3과 원래 unmap nents 4를 따로 보존한다.

  3. 첫 3바이트 전달 뒤 offset 3과 남은 길이 5바이트를 유지한다. EAGAIN에서 누적 전달량을 초기화하지 않는다.

  4. A가 진행 중이면 버퍼를 유지하고 종료 확인 후 결과를 한 번 회수한 뒤 정리한다.

  5. stdio 출력은 fflush 성공 뒤 파일 fsync 성공을 확인하고, 새 이름 보존까지 요구하면 디렉터리 동기화도 확인한다.

  6. 문서 계약의 확인과 실제 장치·장애·학습자 실험의 미수행을 구별한다.

주소·원래 목록·반환 목록·누적 전달·요청 종료·영구 저장의 상태를 서로 다른 증거로 기록한다.

해결한 뒤 점검할 것

  • 장치 주소 0x200C, SG 설정 개수 3, unmap의 원래 nents 4를 역할과 함께 설명한다.

  • EAGAIN 뒤 offset 3과 남은 길이 5바이트를 유지하여 중복을 피한다.

  • NOTCANCELED 뒤 진행 중 버퍼 유지와 종료 후 일회 회수를 설명한다.

  • fflush·파일 fsync·필요한 디렉터리 동기화의 순서와 오류 판정을 구별한다.
