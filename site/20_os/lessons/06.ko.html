소단원 6.1

세마포어·조건변수·모니터

빈 공간이 생겼다는 알림과 저장해 둔 입장권은 같은 도구일까?

준비 개념과 학습 목표

준비 개념

  • 상호 배제는 동시에 공유 상태를 고치지 못하게 하는 규칙이고 조건 대기는 작업을 진행할 상태가 될 때까지 기다리는 규칙이다.

  • 여기서는 세마포어를 비음수 허가 수와 대기열로 설명하고 wait/post를 오류 없이 수행하는 추상 모형을 쓴다. 실제 API 오류· 취소· 시간 제한은 별도 처리한다.

학습 목표

  • 동기화 도구의 상태와 기다리는 조건을 구별하여 설명한다.

  • 종이에 스케줄을 적어 불변식· 경쟁· 교착· 기아의 조건을 확인한다.

완료 사건 하나를 기다리는 사람이 셋이면 허가 하나로 충분할까?

세마포어 허가와 영구 완료 상태의 차이를 새 모형으로 확인한다. 두 관찰자 T1과 T2가 동일 작업의 완료를 각각 알아야 한다. 초기 허가가 0인 세마포어에 완료 주체가 post를 한 번만 하면 성공한 wait는 최대 하나다. 누가 먼저 성공하는지는 별도 대기 정책에 달려 있다. 둘 다 완료를 알게 하려는 목적을 허가 하나 소비와 동일시하면 다른 관찰자가 남는다.

자체 완료 모니터에서는 같은 mutex 아래 done을 false에서 true로 한 번 기록하고 조건 변수의 모든 대기자를 깨운다. 각 관찰자는 잠금을 보유한 채 while(!done)으로 기다리고, 돌아온 뒤 다시 done을 검사한다. done은 읽어도 소비되지 않는다. T1,T2가 차례로 잠금을 얻어 true를 보면 둘 다 완료를 관찰할 수 있다. 늦게 온 T3도 현재 true를 보고 기다리지 않는다.

세마포어에 허가 두 개를 넣으면 두 wait는 가능하지만 뒤 T3의 세 번째 wait용 허가는 없다. 관찰자 수를 미리 알고 각자 한 번 소비하도록 설계한 다른 목적에는 쓸 수 있다. 누구나 늦게 와도 영구 완료를 관찰하는 목적이라면 상태 기록을 따로 둬야 한다. broadcast도 미래 관찰자를 위한 허가 저장이 아니며 상태와 재검사 규율이 핵심이다.

모니터의 모든 공유 done 접근이 같은 보호 규칙을 따른다고 정한다. 독자가 잠금 없이 일반 변수를 읽거나 완료 게시 뒤 다시 false로 바꾸는 재사용을 허용하면 전제가 달라진다. 반복 작업은 세대 번호 등으로 어떤 완료를 기다리는지 정하는 추가 계약이 필요하며, 이번 모형은 한 번만 완료되는 작업이다.

세마포어는 허가를 기억한다

세마포어의 성공한 wait(P)는 허가 하나를 얻는다. 허가가 없으면 대기하고 post(V)가 허가를 공급하여 대기자를 진행시킬 수 있다. 대기자 없이 post를 하면 허가가 남아 나중 wait가 사용할 수 있다. 초기 값은 사용 가능한 자원의 수라는 뜻에서 정한다.

초기 값 1의 세마포어는 규율에 따라 상호 배제용으로 쓰지만 그 자체가 잠금 소유자 검사까지 하는 mutex는 아니다. post를 잘못 두 번 하면 허가가 늘어 여러 실행이 들어갈 수 있다. 실제 구현 내부의 음수 대기자 카운트와 여기의 비음수 가용 허가 수를 구별한다.

조건 변수는 조건의 참을 저장하지 않는다

조건 변수는 같은 mutex로 보호한 공유 술어를 기다릴 때 쓴다. 술어는 count>0처럼 현재 상태가 만족해야 하는 명제다. wait(cv,m)은 m을 보유한 상태에서 대기를 등록하고 잠금을 해제하는 과정을 원자적으로 연결하며, 돌아오기 전 m을 다시 획득한다.

signal은 기다리는 스레드를 깨울 기회이고 미래용 허가를 쌓지 않는다. 기다리는 사람이 없으면 알림을 기억해 두지 않으므로 완료 여부는 done 같은 공유 변수에 기록한다. Mesa 방식에서는 깨어난 뒤 술어가 참이라는 보장이 없어 while로 다시 확인한다.

모니터는 상태· 연산· 잠금의 경계를 만든다

모니터는 공유 데이터와 접근 연산을 묶고 진입 상호 배제와 조건 대기를 통합하는 추상화다. 조건 대기로 잠금을 놓을 때도 공유 불변식이 일관되게 유지되도록 연산을 구성해야 한다. 단순히 클래스를 만드는 것만으로 모니터 규칙이 생기지는 않는다.

호출자는 잠금 소유 여부· 대기하는 술어· 깨울 조건을 함께 알아야 한다. 이 단원의 의사 절차는 Mesa 재확인 규칙을 쓴다. 깨운 실행으로 즉시 소유권을 넘기는 Hoare 모니터의 강한 의미를 모든 라이브러리에 적용하지 않는다.

허가 소비와 영구 조건의 관찰은 다른 요구다. 즉시 CPU 배정이나 잠금 획득 시간 상한은 표에서 보장하지 않는다.

중간 과정을 따라가는 예제

자원 2개를 뜻하는 세마포어에서 T1/T2/T3가 차례로 wait를 하고 T1이 post한다. 별도로 조건 변수에 대기자 없이 signal을 보낸 뒤 done =false인 스레드가 기다리는 경우를 비교하자.

  1. 처음 가용 허가 2다. T1 성공 후 1, T2 성공 후 0이며 각각 자원을 하나 갖는다. T3는 허가가 없어 대기열에 들어간다.

  2. T1이 자원을 돌려주고 post 하면 T3가 허가를 얻어 진행할 수 있다. T3가 성공적으로 wait에서 돌아온 뒤 가용 허가는 0이고 자원 사용자는 T2/T3다. 정확한 깨움 순서나 즉시 실행은 보장하지 않는다.

  3. 대기자 없는 조건 변수 signal은 저장된 허가를 만들지 않는다. 이후 done =false를 보고 wait 하면 다음 상태 변경과 알림이 없다면 계속 대기할 수 있다.

  4. 반면 세마포어 초기 0에서 먼저 post 하면 허가 1이 남아 이후 wait가 얻을 수 있다. 알림 기억 여부가 두 도구의 차이다.

세마포어는 허가를 축적할 수 있고 조건 변수는 공유 상태 술어를 따로 기록해야 한다.

조건을 바꾸어 비교하기

알림 하나와 두 관찰자

T1과 T2가 같은 완료를 기다린다. 초기 허가가 0인 세마포어에 post를 한 번 하면 둘의 wait가 모두 성공하는가?

  1. post가 공급하는 허가는 하나다.

  2. 성공 wait 하나가 그 허가를 소비한다.

  3. 다른 성공 wait에는 추가 허가가 필요하다.

한 post만으로 두 성공을 보장하지 못한다.

오해와 반례

조건 변수 signal은 다음 wait용 입장권이고 깨어났으면 항상 조건이 참이다.

대기자 없는 signal은 미래 허가로 저장되지 않는다. 다른 스레드가 먼저 자원을 가져가면 깨어난 실행이 잠금을 다시 잡을 때 count =0일 수 있다. 상태 기록과 while 재확인이 필요하다.

생산자·소비자·독자쓰기

가져갈 물건을 기다리는 동안 창고 열쇠까지 쥐고 있으면 누가 채울 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 생산자는 유한 버퍼에 항목을 넣고 소비자는 꺼낸다. 용량 N의 상태 count는 0 ≤count ≤N을 지켜야 한다.

  • 독자 쓰기 문제는 공유 자료를 바꾸지 않는 여러 독자를 허용하면서 작가(쓰기 실행)는 단독으로 접근하게 한다. 공정성은 별도 조건이다.

학습 목표

  • 동기화 도구의 상태와 기다리는 조건을 구별하여 설명한다.

  • 종이에 스케줄을 적어 불변식· 경쟁· 교착· 기아의 조건을 확인한다.

세마포어 허가 합이 용량보다 작으면 버퍼가 망가진 것일까?

용량이 3인 자체 슬롯 모형을 여섯 상태로 나눈다. E는 아직 예약되지 않은 빈 슬롯, P는 생산자가 예약했으나 삽입 전인 슬롯, U는 삽입됐으나 full에 공개 전인 슬롯이다. F는 소비자가 예약할 수 있게 공개된 항목, C는 소비자가 예약했으나 제거 전인 항목, V는 제거됐으나 empty에 반환 전인 슬롯이다. 한 슬롯은 정확히 하나의 상태에 속한다.

각 슬롯의 정상 순서는 E→P→U→F→C→V→E다. 따라서 E+P+U+F+C+V=3이 유지된다. 실제 버퍼에 들어 있는 항목 수 count는 U+F+C이며, 가용 empty 허가에 대응하는 수는 E, 가용 full 허가에 대응하는 수는 F다. 중간 예약·공개·반환 상태가 있으면 E+F의 합이 항상 3이어야 한다고 요구할 수 없다. 모든 중간 범주의 값이 0인 정지 지점에서만 E=3−count와 F=count가 맞는다.

처음 E가 3인 상태에서 한 생산자가 예약하면 E는 2, P는 1, count는 0이다. 삽입 뒤에는 E가 2, U가 1, count가 1이며 공개 뒤에는 E가 2, F가 1, count가 1이다. 소비자가 예약하면 E가 2, C가 1, count가 1이다. 제거 뒤에는 E가 2, V가 1, count가 0이며 반환 뒤에는 E가 3, count가 0이다. 슬롯 소유 이전과 실제 큐 변경을 나누면 어느 불변식을 언제 검사할지 알 수 있다. 이 표는 실제 API 내부 semaphore 값이나 실행 로그가 아니다.

실패 정리는 작업의 단계에 따라 달라진다. 예약 P에서 삽입하기 전에 포기하면 자기 예약을 반환하여 P→E로 되돌릴 수 있다. 그러나 U에서 항목을 이미 넣었는데 empty만 post하면 실제 항목을 남긴 채 빈 허가를 늘린다. U→F로 성공 공개를 마치거나, 보호 아래 실제 삽입을 취소하여 U→E로 돌리는 등 명시한 정리 정책이 필요하다. 실제 pthread 취소 안전 구현까지 이 종이 모형으로 인증하지 않는다.

유한 버퍼의 상태와 두 조건

mutex 아래 생산자는 while(count ==N)에서 not_full을 기다리고 공간이 생기면 넣어 count를 늘린다. 소비자는 while(count ==0)에서 not_empty를 기다리고 꺼내 count를 줄인다. 각 변경 후 반대편이 기다리는 조건 변수에 signal한다.

여러 생산자· 소비자가 같은 조건 변수에서 기다리면 필요 없는 쪽만 깨워 진행을 막을 수 있다. not_empty와 not_full을 분리하거나 적절한 broadcast 정책을 설계한다. signal 뒤 현재 실행이 잠금을 놓기 전 다른 실행이 임계 구역에 들어오지는 않는다.

세마포어의 자원 예약과 mutex 순서

세마포어 버퍼는 empty =N, full =0, mutex용 허가 1로 시작한다. 생산자는 empty를 먼저 확보하고 mutex를 잡아 넣은 뒤 mutex를 풀고 full을 post한다. 소비자는 full을 먼저 확보하고 mutex를 잡아 꺼낸 뒤 mutex를 풀고 empty를 post한다.

empty/full은 예약과 발표를 포함하므로 실행 중간에 가용 허가 empty +full이 항상 N이라고 단정하지 않는다. 예약은 되었지만 아직 넣거나 발표하지 않은 순간이 있다. 모든 작업이 끝나 예약이 없는 정지 지점에서만 가용 empty =N −count와 full =count로 맞춰 본다.

독자는 함께, 작가는 단독 — 그리고 기아

간단한 독자 우선 규칙에서는 보호한 readers 수를 늘려 첫 독자가 쓰기 문을 잠그고 마지막 독자가 풀도록 한다. 두 번째 이후 독자는 기존 독자 무리에 합류한다. 작가는 쓰기 문을 단독으로 얻은 동안만 자료를 바꾼다.

이 규칙의 안전성은 작가와 독자가 동시에 자료에 접근하지 않는 데 있다. 새 독자가 계속 들어오면 readers가 0이 되지 않아 기다리는 작가가 무한히 밀릴 수 있다. 기아 방지에는 대기 작가를 새 독자의 진입 조건에 반영하는 정책과 스케줄 공정성 가정이 추가로 필요하다.

  1. put(A) 후[A] count 1, put(B) 후[A,B] count 2다. 세 번째 생산자는 가득 찬 술어를 보고 wait하여 mutex를 놓고 C를 아직 넣지 않는다.

  2. 소비자가 A를 꺼내[B] count 1로 만들고 not_full을 signal한다. 생산자가 다시 mutex를 획득해 공간을 확인한 뒤 C를 넣어[B,C] count 2다.

  4. 독자 수는 R1 진입 1,R2 진입 2,R1 퇴장 1,R2 퇴장 0이다. W는 첫 독자부터 마지막 독자까지 쓰기 문을 얻지 못하다가 마지막 퇴장 후 획득할 수 있다. 즉시 스케줄된다고 보장한 것은 아니다.

완료 알림을 보냈는데 대기자가 영원히 잠들 수 있는 틈은 어디일까?

준비 개념과 학습 목표

준비 개념

  • Mesa 방식의 깨움은 재검사 기회다. shared predicate는 같은 mutex로 읽고 바꾸며 wait의 등록/ 해제 원자성을 이용한다.

학습 목표

  • 동기화 도구의 상태와 기다리는 조건을 구별하여 설명한다.

  • 종이에 스케줄을 적어 불변식· 경쟁· 교착· 기아의 조건을 확인한다.

큐를 닫으면 남은 데이터와 기다리는 생산자는 어떻게 될까?

자체 닫힘 정책은 새 생산을 금지하고 이미 들어온 항목은 FIFO로 모두 소비한다. count와 closed는 같은 mutex 아래 읽고 바꾼다. 소비자는 while(count==0 and not closed)로 대기한다. 다시 검사하여 count가 0이고 closed가 true이면 END를 반환하고, count가 양수이면 한 항목을 꺼낸다. closed라는 이름만으로 즉시 모든 항목을 폐기하는 정책을 뜻하지 않는다.

생산자도 종료 조건이 필요하다. 용량N에서 while(count==N and not closed)로 기다린 뒤 closed true면 삽입을 거절한다. 빈 공간이 남아도 닫힌 큐에 새 항목을 넣지 않는다. close 연산은 잠금 아래 closed를 기록하고 소비자의 not_empty와 생산자의 not_full 모두에 broadcast한다. 빈 큐 소비자만 깨우고 가득 찬 큐 생산자를 남겨 두면 영구히 재검사하지 못할 수 있다.

용량 2인 FIFO에 [A,B]가 있고 close한 뒤 C1, C2, C3가 이 순서로 mutex를 얻는다고 정하자. C1은 A를 꺼내 count를 1로 만들고, C2는 B를 꺼내 count를 0으로 만든다. C3는 END를 반환한다. 처음 두 소비자도 다음 호출에서는 빈 닫힌 큐의 END를 본다. 모든 대기자 깨움은 동시 제거 허가가 아니라 각각 잠금을 다시 얻어 현재 조건을 확인할 기회다.

생산자 P가 가득 찬 열린 큐에서 기다리다 close로 깨어난 경우에도 삽입하지 않고 거절한다. 나중 소비자가 공간을 만들어도 닫힘 상태는 유지된다. close와 생산 삽입이 경쟁하면 같은 잠금에서 어느 연산이 먼저 완료했는지로 계약을 정한다. 먼저 삽입한 항목은 잔여 소비 대상이고, 먼저 close한 뒤 시도한 삽입은 거절한다. 이 원고는 실제 라이브러리 종료·취소 API를 실행하지 않았다.

검사와 잠듦 사이의 빈틈

잘못된 개념 절차를 가정하자. T가 done =false를 읽은 뒤 잠시 멈춘 사이 W가 done =true로 바꾸고 signal한다. 대기자가 없어 알림은 사라지고 T가 그 뒤 무조건 잠들면 다음 알림이 없어 계속 잠들 수 있다. 실제 pthread_cond_wait의 mutex 인자를 생략한 유효 코드라는 뜻이 아니다.

옳은 규율에서는 T가 m을 잡고 done을 검사한다. false라면 wait(cv,m)이 대기 등록과 m 해제를 연결하고 W는 같은 m을 잡은 뒤 상태를 바꾼다. W가 먼저 변경했다면 T는 true 를 보고 안 기다리고,T가 먼저 검사했다면 W가 잠금을 얻을 때 대기 등록이 연결되어 있다.

if 대신 while로 자원을 다시 확인한다

C1이 빈 버퍼에서 wait하고 P가 한 항목을 넣어 C1을 깨웠다고 하자. C1이 mutex를 다시 얻기 전에 C2가 먼저 그 항목을 꺼낼 수 있다. C1은 돌아올 때 count 0이라 다시 기다려야 한다. 깨어남이 항목 예약을 뜻하지 않는다.

while은 이 경쟁과 허위 깨움에서도 술어를 재확인한다. if로 한 번 검사한 뒤 복귀하면 조건을 건너뛰어 빈 버퍼에서 꺼내려 할 수 있다. 반대로 while만 쓴다고 잘못 선택한 대기열이나 누락된 상태 기록까지 자동 교정되지는 않는다.

깨울 대상과 종료 상태를 설계한다

생산자와 소비자를 한 cv에 섞고 하나만 깨우면 빈 버퍼가 되었는데 다른 소비자만 깨우고 생산자는 그대로 잠드는 스케줄이 가능하다. 서로 다른 술어별 cv를 사용하면 새 항목 때 소비자를, 빈 공간 때 생산자를 깨우도록 명료해진다.

영구 종료에는 closed 같은 상태를 mutex 아래 기록하고 대기자 전체를 깨우는 정책이 필요할 수 있다. 소비자 조건을 count ==0 AND not closed로 두고 복귀 후 count 0/closed이면 종료한다. 버퍼에 항목이 남아 있다면 닫혔어도 먼저 소비할지 즉시 취소할지 정책을 명시한다.

while count == 0 and not closed: wait(not_empty, m)
if count == 0 and closed:
    unlock(m); return END
item = remove(); count = count - 1
signal(not_full); unlock(m)

허가·중간 상태·종료 정책의 다른 불변식

완료 주체의 post 한 번으로 세 관찰자 모두의 진행을 보장한다고 썼다. 용량 3의 E가 2이고 U가 1인 상태를 가용 empty와 full의 합이 2이므로 오류라고 적었다. 큐 [A,B]를 닫고 소비자만 깨운 뒤 모든 호출이 즉시 END라고 기록했다. 단원의 자체 모형에 따라 세 주장을 고쳐라.

힌트 1

소비되는 허가와 보호된 done 상태를 구별한다.

힌트 2

count=U+F+C와 여섯 슬롯 범주 합, 잔여 항목 소비 정책을 사용한다.

풀이와 답 확인

  1. post 한 번은 성공 wait 하나의 허가를 공급한다. 여러 영구 관찰에는 done=true와 broadcast, 같은 잠금 및 while 재검사 계약을 쓴다.

  2. E가 2이고 U가 1이면 전체 범주 합은 3, count는 1, 가용 허가 합 E+F는 2다. 정상적인 중간 상태다.

  3. close는 새 생산을 금지하고 not_empty·not_full 모두 깨운다.

  4. 지정 C1,C2,C3 순서는 A,B,END이며 닫힌 빈 큐의 늦은 소비자도 현재 closed로 END를 판정한다.

  5. 실패 정리는 예약과 삽입·공개 단계에 맞게 정하며 이 종이 모형으로 실제 API 취소 안전을 인증하지 않는다.

허가 소비·영구 상태·슬롯 예약 및 실제 데이터·닫힘 정책을 각각 명시한다.
