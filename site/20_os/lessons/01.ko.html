소단원 1.1

추상화·격리·자원관리

두 앱이 같은 CPU와 파일을 원할 때 누가 차례와 접근 범위를 정할까?

준비 개념과 학습 목표

준비 개념

  • 프로그램은 실행할 명령과 데이터의 표현이고 프로세스는 그 프로그램을 실행하는 상태와 자원을 가진 실행 단위다. 같은 프로그램도 여러 프로세스로 실행될 수 있다.

  • CPU는 명령을 실행하고 메모리는 실행 중 값과 명령을 담는다. 파일은 저장 데이터에 접근하는 이름 있는 추상화다.

  • 준비는 실행 가능하지만 CPU를 배정받지 않은 상태, 실행은 CPU에서 명령을 수행하는 상태, 대기는 사건 완료를 기다려 지금 실행할 수 없는 상태다. 이번 모형은 각 프로세스의 스레드 하나만 다룬다.

학습 목표

  • 운영체제의 추상화·격리·자원관리 책임을 구별한다.

  • 단일 CPU에서 대기·준비·실행 상태를 추적한다.

  • 공유 허용과 보호, 메커니즘과 정책의 차이를 설명한다.

1. 물리 자원을 쓰기 쉬운 대상으로 바꾼다

운영체제는 CPU·메모리·장치를 응용이 이용할 수 있는 프로세스·주소공간·파일 등의 추상화로 제공한다. 앱은 파일의 바이트를 읽겠다고 요청하고 일반적으로 디스크 제어기의 모든 명령과 물리 블록 배치를 직접 관리하지 않는다. 단일 CPU도 여러 프로세스의 실행을 번갈아 수행하여 각 프로세스가 진행할 기회를 줄 수 있다.

추상화는 물리 제약을 없애는 마법이 아니다. 메모리와 CPU는 유한하고 파일 읽기는 실패하거나 기다릴 수 있다. 화면과 메뉴는 운영체제를 이용하는 인터페이스의 일부지만 화면이 없는 서버에서도 프로세스 실행·보호·저장 관리가 필요하다.

2. 격리는 모든 공유 금지가 아니다

주소공간 보호는 한 프로세스의 임의 메모리 접근이 다른 프로세스나 커널의 데이터를 망가뜨리지 않도록 한다. 하드웨어 주소 변환·권한과 커널의 설정·검사가 함께 필요하다. 두 프로세스가 같은 가상 주소 숫자를 쓰더라도 서로 다른 물리 페이지로 연결될 수 있다.

격리는 허용된 공유까지 없애는 것이 아니다. 파일 권한과 명시적인 공유 메모리·메시지 전달은 필요한 협력을 허용한다. 같은 파일을 둘 다 쓸 수 있다는 권한이 있어도 응용의 모든 여러 단계 갱신을 하나의 거래로 자동 처리해 주지는 않는다. 데이터 의미의 일관성에는 응용 프로토콜이나 DB 트랜잭션도 필요할 수 있다.

3. 자원관리의 메커니즘과 정책

문맥을 저장하고 다음 실행 상태를 복원하는 기능은 교체를 가능하게 하는 메커니즘이다. 준비된 대상 중 누구를 언제 실행할지는 스케줄링 정책이다. 메모리를 누구에게 얼마나 주고 어떤 I/O를 먼저 처리할지도 자원관리의 결정이다. 처리량·응답 시간·공정성은 서로 영향을 주므로 한 목표만으로 모든 상황의 최선이 정해지지 않는다.

A가 파일 읽기를 요청했다고 반드시 대기하는 것은 아니다. 캐시에서 바로 처리될 수도 있다. 아래 예제는 데이터가 아직 없어 대기하는 블로킹 읽기라고 명시한다. I/O 완료는 A를 준비 상태로 만들고, A의 실제 실행은 별도의 선택이다. 단일 CPU의 두 사용자 실행 흐름이 같은 순간에 실행 상태일 수는 없지만 CPU와 장치는 동시에 작업할 수 있다.

중간 과정을 따라가는 예제

사용자 실행 흐름을 배정할 CPU 하나, 프로세스 A와 B 각 스레드 하나가 있다. A는 현재 실행, B는 준비다. A의 읽기는 I/O를 기다려야 하고, 이 예제 정책은 I/O 완료 뒤에도 현재 B를 계속 실행시킨다. 커널 처리 시간은 표에서 생략한다.

  1. 처음 상태는 A=실행,B=준비다. A가 읽기를 요청하여 필요한 데이터를 기다린다.

  2. A=대기가 되고 스케줄러가 B를 선택한다. A=대기,B=실행이다.

  3. I/O 완료 사건으로 A=준비가 된다. 예제 정책에 따라 B=실행은 유지된다.

  4. B의 실행 구간이 끝나고 스케줄러가 A를 선택하면 A=실행,B=준비다. A는 읽기 결과를 처리한다.

상태쌍은 (실행,준비)→(대기,실행)→(준비,실행)→(실행,준비)다. 완료와 즉시 실행은 같은 사건이 아니다. 다른 정책에서는 완료 후 더 빨리 A를 선택할 수 있다.

종이와 본문으로 직접 해보기

종이에 CPU 카드 1장과 A,B 상태 카드를 놓는다. 둘 다 준비에서 A 배정→A 대기→B 배정→A I/O 완료를 수행하라. 마지막 CPU 카드는 누구에게 있으며 A가 실행하려면 어떤 사건이 더 필요한가?

힌트 보기

대기에서 준비로 옮길 때 CPU 카드를 자동으로 가져오지 않는다. 프로세스 상태와 장치 완료 사건을 따로 표시한다.

풀이 보기

A 배정 뒤 A=실행,B=준비. A 대기 뒤 B를 배정하면 A=대기,B=실행. 완료 뒤 A=준비,B=실행이므로 CPU 카드는 B에게 있다. 스케줄러가 B를 중단하거나 B가 대기·종료하고 A를 선택해야 A가 실행한다. 실제 OS를 조작하는 활동이 아닌 상태 모형이다.

오해와 반례

파일 읽기가 끝나면 기다리던 프로세스가 반드시 즉시 CPU를 얻는다.

I/O 완료는 실행 가능 조건을 만족시켜 준비로 옮긴다. 스케줄링 정책과 다른 준비 프로세스에 따라 실제 실행 시점은 다르다. 예제에서 A 준비와 B 실행이 동시에 성립하는 상태가 반례다.

자기점검

같은 프로그램 파일을 두 번 실행하면 프로세스 상태도 반드시 하나인가?

답과 이유 보기

아니다. 서로 다른 실행 상태를 가진 두 프로세스가 될 수 있다.

프로그램은 표현, 프로세스는 실행 상태와 자원 단위다.

단일 CPU 모형에서 A=대기,B=실행일 때 A I/O가 끝나면 기본적으로 A의 다음 상태는?

답과 이유 보기

준비 상태다.

실행 가능해져도 실제 CPU 배정은 별도 사건이다.

두 앱의 같은 파일 쓰기를 허용하면 여러 번 쓰는 전체 업무도 자동 원자적인가?

답과 이유 보기

그렇지 않다.

접근 허용과 응용의 여러 단계 거래 일관성은 다른 보장이다.

소단원 1.2

사용자 모드와 특권 모드

앱이 “지금부터 내가 커널이다”라고 말하면 보호 장치가 해제될까?

준비 개념과 학습 목표

준비 개념

  • CPU 실행 모드는 현재 명령이 가진 하드웨어 권한 수준이다. 사용자 이름이나 창의 종류가 아니다.

  • 특권 명령·레지스터는 제한된 모드에서만 접근할 수 있는 제어 기능이다. 주소공간 권한도 어떤 메모리 접근이 허용되는지 결정한다.

  • 트랩은 예외·시스템 호출·인터럽트 등의 사건으로 정해진 처리 경로에 제어를 옮기는 개념이다. 문맥교환은 실행 흐름을 다른 대상으로 바꾸는 일이라서 모드 전환과 구별한다.

학습 목표

  • 사용자 신원과 CPU 모드를 구별한다.

  • 허용된 진입점·인수 검사·반환이 보호 경계를 만드는 이유를 설명한다.

  • RISC-V 교육용 xv6의 U/S/M 가정과 범용 설명의 한계를 적는다.

1. 모드는 하드웨어가 지키는 실행 권한이다

일반 앱은 사용자 모드에서 숫자 계산·자신에게 허용된 메모리 접근 등을 수행한다. 페이지 테이블 제어·특정 인터럽트 제어 같은 기능은 특권 경계를 가진다. 사용자 코드가 금지된 명령을 시도하면 그 명령을 허용된 것처럼 실행하지 않고 예외 처리로 이어질 수 있다. 모든 주소 접근에 대한 실제 판정은 모드와 페이지 권한·아키텍처의 규칙을 함께 본다.

이 단원은 RISC-V의 교육용 xv6 예를 사용한다. RISC-V에는 사용자 U, 감독자 S, 기계 M 수준이 있으며 xv6 커널의 일반 실행은 S 모드다. M 모드는 부팅 등의 더 높은 권한 문맥과 관련된다. 모든 CPU가 정확히 두 수준이라는 단정이나 xv6가 실제 모든 OS 구조를 대표한다는 단정은 하지 않는다.

2. 경계는 통제된 진입과 검증으로 유지한다

응용의 읽기 요청은 지정한 시스템 호출 경로로 들어간다. 사용자 코드가 마음대로 커널 내부의 중간 주소를 골라 호출하게 하면 앞부분의 권한 검사를 건너뛸 수 있다. 따라서 진입 경로와 반환 모드는 하드웨어·커널이 통제하고 커널은 호출 번호·열린 파일·사용자 버퍼·길이 등의 인수를 검증한다.

모드가 바뀌었다고 사용자 제공 주소가 안전해지는 것은 아니다. 특히 가상 주소는 호출 프로세스의 주소공간에서 어떤 메모리에 대응하는지 확인해야 한다. 범위의 시작뿐 아니라 복사하는 전체 구간, 읽기/쓰기 방향, 길이 계산의 넘침과 실패 경로를 검토한다. 실제 세부 검사는 시스템 호출과 구현에 따라 다르며 한 번의 숫자 비교가 전체 안전성 증명은 아니다.

3. 모드 전환과 프로세스 변경은 다른 축이다

A의 사용자 실행에서 A의 시스템 호출을 처리하는 커널 실행으로 갔다가 A로 돌아오면 모드 전환은 있지만 B로 바꾸지는 않았다. 반대로 요청 처리 중 A가 잠들면 스케줄러가 B를 골라 별도의 문맥교환을 할 수 있다. 현재 누구의 실행 문맥인지와 CPU 모드를 따로 적어야 사건을 혼동하지 않는다.

관리자 계정이 응용에게 많은 업무 권한을 줄 수는 있어도 그 응용의 평범한 명령이 곧바로 S 모드 명령이 되는 것은 아니다. 권한 정책과 하드웨어 실행 모드는 연관된 다른 개념이다. 커널도 코드이므로 결함이 있을 수 있다. 하드웨어 경계는 커널의 올바른 설정·인수 검증을 대신하지 않는다.

중간 과정을 따라가는 예제

가상 교육용 시스템에서 A의 쓰기 가능한 사용자 버퍼는 반열린 구간 [1000,1100) 바이트 주소다. read가 그 버퍼에 데이터를 쓴다. 가능한 전체 쓰기 범위만 검사하는 단순 모형으로 (주소 1096,길이 4)와 (주소 1098,길이 4)를 비교한다.

  1. 첫 요청 범위는 [1096,1100), 실제 주소 1096,1097,1098,1099다. 모두 허용 구간 안이다.

  2. 둘째 요청 범위는 [1098,1102), 실제 주소 1098,1099,1100,1101이다. 마지막 두 주소가 밖이다.

  3. 사용자→커널 진입 후 둘째 요청을 거부하는 정책이라면 커널은 허용 구간 밖으로 복사하지 않고 오류를 반환한다.

  4. 오류 반환 후 A의 사용자 실행으로 돌아올 수 있다. 이 실패 자체가 B로 바꾸었다는 뜻은 아니다.

첫 범위는 이 모형의 범위 검사 통과, 둘째는 거부다. 통과는 파일 권한·페이지 매핑·다른 조건까지 모두 성공했다는 뜻은 아니다. 숫자는 실제 장치 주소가 아닌 가상 예제다.

종이와 본문으로 직접 해보기

(A,U)→(A,S)→(A,U)와 (A,U)→(A,S)→(B,S)→(B,U)를 종이에 적고 모드 전환과 대상 변경을 표시하라. 주소 1097,길이 3의 바이트 범위도 검사하라.

힌트 보기

괄호의 첫 항은 실행 문맥, 둘째는 모드다. [1097,1100)의 끝 주소 1100은 포함하지 않는다.

풀이 보기

첫 경로는 U→S와 S→U의 두 모드 전환만 있고 대상은 A 그대로다. 둘째는 A,S→B,S에서 대상 변경이 있고 모드는 S 그대로다. 주소 범위는 1097,1098,1099 세 바이트로 허용 범위 안이다. 실제 트랩·스케줄러 경로는 더 복잡하지만 이 두 축의 구별은 유지된다.

오해와 반례

관리자 계정으로 실행한 응용은 항상 커널 모드에서 실행한다.

계정의 권한은 접근 정책의 입력이고 CPU 모드는 현재 명령의 하드웨어 권한이다. 관리자 응용도 일반 계산은 사용자 모드에서 할 수 있으며 허용된 시스템 호출 경로로 특권 서비스를 요청한다. 계정 이름 변경만으로 특권 명령을 직접 실행할 수 없다.

자기점검

xv6/RISC-V 예에서 일반 응용 모드와 커널의 일반 실행 모드는?

답과 이유 보기

응용 U 모드, 커널 S 모드다.

부팅 등의 M 모드와 구별하며 모든 ISA의 모드 이름으로 일반화하지 않는다.

[1000,1100)에서 주소 1095,길이 5는 이 범위 모형을 통과하는가?

답과 이유 보기

통과한다. 접근 주소는 1095부터 1099까지다.

주소+길이는 1100이고 끝 주소는 포함하지 않는다.

A가 시스템 호출로 S 모드에 들어가면 반드시 B로 문맥교환하는가?

답과 이유 보기

아니다. A 요청을 처리하고 A에 바로 돌아갈 수도 있다.

모드 전환과 실행 대상 변경은 별도의 축이다.

소단원 1.3

커널 구조와 시스템 호출

파일 읽기 함수 한 줄 안에서 무엇이 라이브러리이고 무엇이 커널의 일일까?

준비 개념과 학습 목표

준비 개념

  • 커널은 보호된 권한으로 자원과 실행을 관리하는 핵심 소프트웨어다. 라이브러리는 응용에서 호출할 수 있는 함수 구현을 제공하며 모든 함수가 시스템 호출을 하지는 않는다.

  • 파일 디스크립터는 프로세스가 열린 자원을 가리킬 때 쓰는 작은 정수 핸들이다. 같은 숫자가 다른 프로세스에서 같은 파일을 뜻한다고 단정할 수 없다.

  • 호출 규약은 인수·호출 번호·결과를 전달하는 약속이다. POSIX/Linux의 사용자 API 결과 규약과 xv6의 교육용 내부 규약을 구별해야 한다.

학습 목표

  • 단일 커널과 마이크로커널의 배치와 보호 경계를 비교한다.

  • 함수→호출 요청→검사→작업→반환 흐름을 추적한다.

  • read의 요청량·실제 반환량·오류를 구별한다.

1. 커널에 무엇을 넣을지 결정한다

단일 커널 구조는 파일시스템·메모리·스케줄링·많은 드라이버 등의 서비스를 커널 권한 공간 안에 배치한다. 모듈로 코드가 나뉘어 있어도 같은 특권 경계에서 실행하면 단일 커널 구조일 수 있다. xv6는 단순한 교육용 단일 커널이다. 직접 협력은 편리하지만 특권 코드의 결함이 넓은 범위에 영향을 줄 수 있다.

마이크로커널은 핵심 보호·실행·통신 기능을 작게 두고 파일 서버 같은 서비스를 사용자 프로세스로 분리하려는 설계다. 서비스 요청에는 커널이 제공하는 프로세스 간 통신과 스케줄링이 관여할 수 있다. 모든 서비스가 반드시 사용자 공간에 있거나 항상 더 빠르다는 뜻은 아니다. 경계·실패 범위·통신 비용을 함께 비교하며 실제 OS에는 다양한 혼합 선택도 있다.

2. 시스템 호출은 함수 호출 이상의 경계다

응용은 read 같은 API를 함수 모양으로 사용하지만 라이브러리 래퍼는 시스템 호출 규약에 맞춰 요청을 전달한다. xv6/RISC-V에서는 호출 번호와 인수를 레지스터에 넣고 ecall을 통해 지정된 트랩 경로로 들어간다. 커널이 호출 번호를 해석해 구현을 선택하고 인수를 검사하며 반환값을 저장한 뒤 사용자 실행을 재개한다. ISA·OS마다 이 규약이 다르므로 한 시스템의 레지스터 번호를 다른 시스템에 복사해서는 안 된다.

모든 함수 호출은 모드 전환이라는 생각은 틀리다. 메모리에 이미 있는 문자열 길이를 계산하는 함수는 사용자 공간에서 끝날 수 있다. 반대로 출력 함수 한 번도 버퍼링에 따라 즉시 시스템 호출하지 않거나 여러 번 호출할 수 있다. 호출 요청이 블로킹하면 다른 프로세스를 실행했다가 나중에 결과를 돌려줄 수 있다.

3. 성공은 요청한 양을 전부 받았다는 뜻이 아니다

Linux/POSIX 계열 read(fd,buf,count)는 최대 count 바이트를 읽으려 한다. 양의 count로 일반 파일을 읽을 때 양수 반환은 실제 받은 바이트 수이며 요청보다 작아도 오류가 아닐 수 있다. 파일 위치도 실제 읽은 수만큼 이동한다. 0은 파일 끝을 나타낼 수 있고 오류는 사용자 API에서 −1과 errno로 보고한다. count=0의 반환 0을 무조건 파일 끝이라고 해석하지 않도록 요청량도 함께 본다.

사용자 버퍼는 결과를 쓸 수 있는 전체 구간이어야 한다. 유효한 핸들·읽기 권한·주소·길이·장치 상태 등에 따라 오류가 가능하다. 이번 흐름은 Unix 계열을 설명하는 종이 추적이며 Windows에서 read를 실제 실행했다는 주장이 아니다. xv6의 간단한 음수 오류 규약과 Linux 라이브러리의 errno 규약도 구별한다.

중간 과정을 따라가는 예제

Linux/POSIX식 의미를 따르는 가상 읽기 추적이다. 일반 파일 내용은 ASCII 바이트 ABCDE, 초기 위치 0, fd는 유효하고 각 버퍼는 충분히 크다. 장애·신호·동시 변경은 없고 남은 요청 가능 바이트를 모두 반환한다고 추가 가정한다. read 요청량은 차례로4,4,4다.

  1. 첫 요청은 위치 0부터 ABCD 네 바이트를 받아 반환 4, 파일 위치 4다.

  2. 둘째 요청은 E 한 바이트만 남아 반환 1, 파일 위치 5다. 요청 4보다 작지만 정상이다.

  3. 셋째는 위치가 끝이므로 반환 0, 위치 5 그대로다.

  4. 함수 인수 전달→커널 진입→핸들·버퍼 검사→읽기→실제 수 기록→사용자 반환의 경로가 각 요청에 있다. 캐시 처리인지 장치 대기인지는 이 출력만으로 알 수 없다.

예상 반환값은 [4,1,0], 유효 데이터는 ABCD와 E다. 세 번째는 양의 요청에서 EOF이며 실제 실행 로그가 아닌 명시한 모형의 결과다.

종이와 본문으로 직접 해보기

같은 모형에서 내용 XYZ, 초기 위치 0, 요청량 2,2,2의 결과·위치를 종이에 적어라. count=0인 별도 요청의 반환 0만 보고 EOF라고 결론낼 수 있는지도 설명하라.

힌트 보기

매번 min(요청량,남은 바이트)를 반환한다는 모형 가정을 쓴다. 파일 내용의 문자열 길이가 바이트 수와 같은 이유는 ASCII라는 전제다.

풀이 보기

첫 결과 XY, 반환 2, 위치 2. 둘째 결과 Z, 반환 1, 위치 3. 셋째 반환 0,위치 3이다. count=0은 읽기를 요청하지 않은 경우이므로 반환 0만으로 EOF를 판정하지 않는다. 이 단순 모형 외 파이프·신호·비차단 I/O 등의 결과는 별도 조건을 확인해야 한다.

오해와 반례

read가 성공하면 언제나 count 바이트를 반환하며 모든 함수 호출은 커널로 들어간다.

다섯 바이트 파일의 두 번째 요청 4가 정상 반환 1인 예가 첫 주장의 반례다. 사용자 메모리 안에서 문자열 길이만 세는 함수는 모드 전환 없이 끝날 수 있어 두 번째 주장도 틀리다. 요청량·실제 결과·호출 계층을 나누어 관찰한다.

자기점검

파일 서버를 사용자 프로세스로 분리하고 메시지로 요청하는 설계는 어떤 방향인가?

답과 이유 보기

마이크로커널 방향이다.

서비스 배치와 보호 경계의 선택이며 파일 추상화를 제공하지 않는다는 뜻은 아니다.

예제 ABCDE의 첫 두 요청 뒤 누적 수신 바이트와 파일 위치는?

답과 이유 보기

5바이트, 위치 5다.

실제 반환 4+1로 누적하며 요청 4+4=8을 받은 것으로 계산하지 않는다.

양의 count에서 반환 2가 요청 8보다 작으면 반드시 오류인가?

답과 이유 보기

아니다. 짧은 성공 반환일 수 있다.

실제로 받은 바이트 수를 처리하고 자원 종류·EOF·신호 등 규약을 확인해야 한다.
