소단원 15.1

시스템 호출·스케줄러 수정

새 시스템 호출을 추가하면 함수 하나를 만들기만 하면 모든 프로그램이 사용할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 사용자 모드와 커널 모드

  • 시스템 호출 번호와 dispatch

  • 프로세스 상태와 잠금

  • 실행 중인 CPU와 문맥

학습 목표

  • 사용자 요청부터 커널 반환까지 변경 지점을 연결한다.

  • 프로세스별 설정과 fork 상속 범위를 명시한다.

  • 스케줄 정책과 동시에 실행하면 안 되는 불변식을 구별한다.

경계 전체를 한 장에 그린다

교육용 xv6의 호출 경로를 사용자 선언 → 호출 stub → ecall → 커널 dispatch → 구현 → 반환으로 나눠 읽는다. 새 호출 번호가 사용자와 커널에서 다르거나 dispatch 항목이 빠지면 구현 함수만 있어도 연결되지 않는다. 설치 없이 종이에 인터페이스 이름, 입력, 오류, 반환값과 변경 파일의 역할을 써 보는 것이 첫 단계다.

연습 요구는 프로세스마다 관찰할 호출 종류를 선택하는 trace 설정이다. 번호를 비트 위치로 사용하는 mask를 받아 해당 호출의 반환 때 기록한다고 정한다. 설정이 caller와 이후 fork된 자식에만 적용되는지, 이미 존재하는 다른 프로세스에도 적용되는지 명확히 해야 한다. 실제 MIT lab의 범위는 caller와 미래 자식이다. 사용자 입력을 커널 주소로 그대로 믿거나 단순 로그가 권한 검사를 대신한다고 생각하지 않는다.

정책을 바꾸기 전에 유지할 조건을 적는다

스케줄러는 RUNNABLE인 프로세스를 선택하여 RUNNING으로 바꾸고 문맥을 전환한다. 선택 순서를 바꾸는 정책과 하나의 프로세스를 두 CPU가 동시에 실행하지 못하게 하는 불변식은 서로 다르다. xv6는 proc lock과 상태·CPU의 현재 proc·커널 스택 관계를 함께 유지한다. swtch를 가로질러 잠금이 인계되는 코드에는 이유가 있으므로 임의로 잠금 범위를 줄이지 않는다.

자체 우선순위 대안은 같은 priority에서는 기존 순서를 유지하고, 낮은 우선순위도 언젠가 선택되도록 별도 aging 규칙을 제안할 수 있다. 다만 선택 로그 몇 줄로 공정성·기아 없음·실시간 deadline을 증명할 수 없다. 이 단원의 종이 예제는 실행 순서를 설명하는 모형이며 xv6의 실제 정책을 구현했다는 보고가 아니다.

검증 항목은 기능과 불변식으로 나눈다

호출 기능 검사는 정상 mask, mask 0, 설정 전·후, fork 자식, 무관한 프로세스, 오류 입력과 반환값을 포함한다. 스케줄러 변경에서는 선택 결과뿐 아니라 RUNNING 중복, 상태 전이, 종료·sleep/wakeup, 다중 CPU 조건을 검사한다. 예측한 결과와 실제 수집한 실행 로그를 다른 칸에 적는다.

실제 확장은 해당 강좌의 lab 버전과 빌드 환경을 고정하고 원본 tests를 먼저 실행한 후 작은 변경을 추가한다. 현재는 커널 실행 환경을 확인하거나 tests를 수행하지 않았다. 따라서 파일 변경 계획과 자체 계산은 설계 자료이며 통과 배지나 완료된 커널 결과로 표시하지 않는다.

중간 과정을 따라가는 예제

자체 모형에서 read 번호 2, write 번호 4다. A가 mask=(1<<2)|(1<<4)를 설정한 뒤 B를 fork한다. C는 기존 별도 프로세스이며 mask 0이다. 각 프로세스가 read와 exit(번호 1)를 호출한다. 기록 범위를 구하라.

  1. 비트 2는 4, 비트 4는 16이므로 mask는 20이다. 호출 번호는 이 예제의 가상 번호이며 xv6 실제 번호를 주장하지 않는다.

  2. A의 read는 20 & 4가 0이 아니므로 기록한다. exit는 번호 1이므로 비트 값 1<<1=2인데, 이 비트가 켜지지 않아 기록하지 않는다.

  3. B는 fork 시 A의 mask를 복사하는 계약이므로 read를 기록한다. C는 mask 0이라 두 호출 모두 기록하지 않는다.

  4. 별도 2-CPU 모형에서 CPU0이 잠금 아래 P를 RUNNING으로 바꿨다면 CPU1은 같은 P를 RUNNABLE로 선택할 수 없다. 두 CPU의 P 실행이 동시에 있으면 정책 성능 이전에 불변식 위반이다.

mask 20으로 A·B의 read만 기록한다. 범위와 스케줄 불변식은 각각 검사해야 하며 실제 커널 로그는 아직 없다.

풀이 보기

오해와 반례

스케줄러 선택 순서를 바꿔 빨라졌으면 커널 수정은 안전하다.

실측도 없고 실행 중복·잠금·sleep 같은 기능 조건도 남는다. 같은 프로세스가 두 CPU에서 실행되는 결함은 처리율 하나로 발견하거나 정당화할 수 없다.

소단원 15.2

페이지·파일 기능 검증

새 페이지가 읽히고 큰 파일이 열리면 메모리와 파일 기능이 모두 올바른 것일까?

준비 개념과 학습 목표

준비 개념

  • 가상 주소와 PTE 권한

  • 할당·매핑·해제 lifecycle

  • 논리 파일 블록과 디스크 블록

  • 직접·간접 포인터

학습 목표

  • 페이지의 내용·권한·해제 시점을 함께 검사한다.

  • 작은 double-indirect 주소 모형의 경계 인덱스를 계산한다.

  • 기능 성공과 자원 회수 성공을 별도로 확인한다.

페이지는 내용만 아니라 접근 규칙이다

xv6 page-table lab의 USYSCALL은 사용자 프로그램이 읽을 수 있는 pid 정보를 페이지에 놓는 연습이다. 사용자 읽기를 허용하되 쓰기는 허용하지 않는 권한이 핵심이다. 사용자 프로그램이 pid를 읽었다는 한 관찰만으로 쓰기 차단이나 다른 프로세스 격리가 확인되는 것은 아니다.

설계 표에는 할당, 초기화, page table 매핑, 정상 조회, 잘못된 쓰기, fork/종료, 매핑 제거, 실제 물리 페이지 해제를 적는다. 가상 주소가 이웃한다고 물리 주소도 이웃이라는 결론은 나오지 않는다. PTE를 출력할 때도 valid 항목과 leaf 또는 다음 수준의 page table을 구분해야 잘못된 주소를 데이터 페이지처럼 해석하지 않는다.

작은 파일 모형으로 주소 경계를 계산한다

자체 모형은 블록 64바이트, 포인터 4바이트라 간접 블록 한 개에 16개 주소가 들어간다고 가정한다. inode에는 직접 데이터 주소 2개, single-indirect 주소 1개, double-indirect 주소 1개가 있다. 데이터 용량은 2+16+16×16=274블록이다. 간접 주소를 담는 메타데이터 블록은 데이터 용량 274에 더하지 않는다.

논리 블록 bn은 파일 안 순번이며 실제 디스크 블록 번호와 다르다. bn 0–1은 직접, 2–17은 single, 18–273은 double 영역이다. double 영역에서는 j=bn−18, 상위 인덱스 j//16, 하위 인덱스 j%16으로 주소를 찾는다. bn 274는 허용 범위를 벗어난다. 이 숫자는 실제 xv6의 block size나 최대 파일 크기가 아니라 손으로 접근하기 위한 별도 예제다.

읽기 성공과 회수 성공을 따로 검증한다

큰 파일을 쓰고 다시 읽는 검사는 각 경계의 데이터가 맞는지 확인한다. 삭제·truncate 뒤에는 데이터와 single/double 간접 메타데이터도 정확히 해제되어야 한다. 참조만 끊고 블록을 남기면 반복 생성·삭제에서 누수가 생긴다. 이중 해제도 다른 파일을 망가뜨릴 수 있으므로 소유와 해제 횟수를 확인한다.

xv6의 메모리 inode와 디스크 inode 표현을 변경할 때 배열 길이 등 호환 조건을 같이 유지하고 파일 시스템 image의 형식 변경도 고려한다. bread로 얻은 버퍼를 brelse하는 규약과 블록 할당 실패 정리도 검사한다. 현재 예제는 주소 계산·소유표 연습이며 실제 파일 시스템 이미지나 커널 페이지 권한 테스트를 실행한 결과가 아니다.

중간 과정을 따라가는 예제

위 274블록 모형에서 bn 18,33,34,273,274의 주소 경로를 구하라. double 영역의 데이터 17개만 순서대로 할당했을 때 double 관련 메타데이터 수는?

  1. 18−18=0이므로 상위 0/하위 0이다. 33−18=15이므로 0/15다.

  2. 34−18=16이므로 1/0이다. 273−18=255이므로 15/15다. 274는 전체 데이터 블록 수와 같아 거부한다.

  3. double 영역 데이터 17개는 첫 하위 간접 블록에 16개, 둘째에 1개를 담는다. 상위 double 주소 블록 1개와 하위 주소 블록 2개가 필요하다.

  4. 그 영역의 데이터 17개와 메타데이터 3개는 구분한다. 이 부분을 전부 truncate하면 총 20개 블록을 각 한 번 해제한다. 직접/single 영역이 따로 사용됐다면 그 자원은 별도로 더한다.

경로는 0/0,0/15,1/0,15/15,범위 오류다. 해당 double 부분은 데이터 17개·메타데이터 3개이며 20개를 회수한다.

소단원 15.3

경쟁상태·장애 테스트와 설계 기록

알림을 보냈는데 기다리던 프로세스가 계속 잠든다면 어떤 순서가 빠졌을까?

준비 개념과 학습 목표

준비 개념

  • 조건 변수와 조건 잠금

  • sleep/wakeup

  • 경쟁 실행 이력

  • 실패 주입과 원상 회복

학습 목표

  • lost wakeup을 작은 사건 순서로 설명한다.

  • 잠든 동안 조건 잠금을 계속 잡는 오류와 올바른 인계를 구별한다.

  • 실제 실행 근거와 종이 설계를 분리한 보고를 작성한다.

알림보다 실제 조건이 기준이다

자체 소비자는 count>0이면 하나를 꺼내고 count=0이면 기다린다. 생산자는 count를 늘리고 wakeup한다. 소비자가 0을 확인한 뒤 sleep하기 전에 생산자가 값과 알림을 보내면 아직 잠든 대상이 없어 알림이 지나갈 수 있다. 소비자가 그 후 잠들면 count는 1인데 진행하지 못한다. 이 작은 순서가 lost wakeup이다.

조건을 확인하고 잠듦을 등록하는 사이에 틈을 없애는 동기화 규약이 필요하다. 그러나 조건 잠금을 잡은 채 영원히 sleep하면 생산자도 count를 변경할 잠금을 못 얻어 교착한다. xv6 sleep(chan, &condition_lock)는 proc lock을 확보한 뒤 조건 잠금을 놓고 잠듦 상태를 기록하는 인계로 이 구간을 보호한다. 돌아오면 조건 잠금을 다시 얻는다. 이 규약을 모르는 상태에서 잠금을 단순 제거하지 않는다.

깨어났다고 조건이 예약된 것은 아니다

wakeup은 대상을 RUNNABLE로 만드는 것이지 즉시 실행시키거나 데이터 하나를 특정 소비자에게 예약하는 동작이 아니다. 소비자가 여럿 깨어나면 먼저 실행한 소비자가 하나를 꺼내고 나머지는 다시 count=0을 볼 수 있다. 그래서 조건을 while로 다시 검사한다. if 한 번만 검사하고 복귀 뒤 무조건 소비하면 음수 count나 빈 버퍼 접근이 생긴다.

실제 동시 테스트에서는 CPU 수, 시작 장벽, 반복 수와 순서 로그를 기록하고 단일 실행 성공을 전 순서의 증명으로 바꾸지 않는다. 할당 잠금 실습의 test-and-set 수는 경쟁에 관한 지표이지 모든 상황의 처리율·정확성 보증이 아니다. CPU별 free list 개선도 stealing과 자원 전체 보존 조건을 함께 검사해야 한다.

실패 기록은 재현 입력과 종료 상태까지 남긴다

실패 주입 표에는 어느 단계의 할당 또는 읽기를 실패시키는지, 이전에 획득한 자원, 되돌리는 순서, 최종 상태와 사용자 반환을 적는다. 예를 들어 데이터 블록 할당 뒤 주소 블록 할당이 실패하면, 새 데이터 자원을 남기거나 부분 inode를 성공처럼 공개하지 않도록 실패 계약을 정한다. 실제 xv6의 모든 함수가 이 자체 예제와 같다고 단정하지 않고 코드를 확인해야 한다.

설계 기록에는 요구, 변경 경계, 불변식, 사건 순서, 예상 결과, 실제 실행 여부, 실패 원인과 수정 후 재검사를 담는다. 본 단원에서 실제 수행한 것은 정수·순차 상태 모형 계산이다. 커널 수정·QEMU·race 테스트·성능 측정·학습자 활동은 미수행 상태로 남긴다. 실험 환경을 준비했을 때만 버전과 실행 명령, 실제 출력으로 증거를 확장한다.

중간 과정을 따라가는 예제

count=0이다. 잘못된 소비자 C는 count를 확인하고 조건 잠금을 놓은 뒤 나중에 sleep한다. 그 사이 생산자 P가 count를 1로 만들고 wakeup한다. 두 소비자 C1/C2가 함께 깨어난 별도 경우도 검사하라.

  1. C: count=0 확인 → 잠금 해제. 아직 C의 SLEEPING 등록이 없다.

  2. P: 잠금 획득 → count=1 → wakeup. 잠든 C가 없으므로 이 알림으로 C의 대기가 해제되지 않는다. P가 잠금을 놓는다.

  3. C: 뒤늦게 sleep. 최종 count=1인데 C는 잠든 상태가 되어 진행이 막힐 수 있다. 올바른 인계는 조건 확인과 잠듦 등록 사이 틈을 보호한다.

  4. 별도 count=1에서 C1/C2가 RUNNABLE이 되었다. C1이 잠금 아래 소비하여 0을 만들고, C2가 잠금을 얻어 while로 재검사하면 다시 기다린다. C2가 무조건 감소시키는 잘못된 코드라면 −1이 된다.

첫 이력은 lost wakeup이며 두 번째는 재검사가 필요한 이유다. count가 1→0일 때 나머지 소비자가 다시 기다려야 한다.

종이와 본문으로 직접 해보기

실패 전 free 블록은 10개다. 새 데이터 블록 1개를 얻어 9개가 됐지만 다음 주소 블록 할당이 실패했다. 성공으로 공개하지 않는 계약에서 정리 후 free 수는? 해제를 빠뜨리면 3회 반복 뒤 수는?

힌트 보기

실패한 요청마다 확보한 새 자원을 돌려줘야 한다. 다른 요청의 자원은 건드리지 않는다.

풀이 보기

올바르게 새 데이터 블록 1개를 돌려주면 10으로 복구한다. 매 실패마다 1개씩 누수되고 다른 변화가 없다면 3회 뒤 10−3=7이다. 실제 할당기가 같은 순서로 실패했는지는 별도 커널 로그로 확인해야 한다.

오해와 반례

wakeup을 받았으므로 if 한 번으로 검사하고 곧바로 데이터를 꺼내면 된다.

wakeup은 실행 가능 상태이며 데이터 예약이 아니다. 다른 소비자가 먼저 꺼냈을 수 있어 잠금 아래 while로 조건을 재검사해야 한다.
