남은 메모리 총량이 충분한데 큰 연속 할당은 왜 실패할까?

준비 개념과 학습 목표

준비 개념

  • 페이지와 바이트

  • 2의 거듭제곱

학습 목표

  • 페이지 수와 order를 계산한다.

  • 총 여유와 물리 연속성을 구별한다.

  • 할당 조건과 대응 해제를 설명한다.

크기가 같은 인접 자유 블록은 항상 하나로 합칠 수 있을까?

자체 buddy 모형은 PFN 0–7의 여덟 frame을 관리한다. order k 블록은 2^k개 frame이며 시작 PFN은 그 크기의 배수여야 한다. 같은 크기의 두 자유 블록도 하나의 정렬된 부모 안에 속하는 짝일 때만 합친다. 시작 x의 buddy 시작은 x XOR 2^k로 계산한다고 정한다. XOR는 이진수의 해당 비트를 뒤집는 연산이다. 노드·zone·예약·회수 같은 실제 커널 제약은 제외한다.

자유 order 1 블록 [2,4)와 [4,6)은 각각 두 frame이며 물리적으로 인접한다. 그러나 start 2의 buddy는 2 XOR 2=0, start 4의 buddy는 4 XOR 2=6이다. 두 블록의 합 [2,6)은 시작 2가 크기 4의 배수가 아니라 order 2 블록이 될 수 없다. 총 여유 네 frame이라는 사실만으로 정렬된 네 frame 요청이 성공하지 않는다.

이 상태에서 [6,8)을 추가 반환하면 [4,6)과 [6,8)이 부모 [4,8)로 합쳐진다. 시작 4는 네 frame 경계에 맞으므로 order 2 요청을 만족할 수 있다. 아직 [2,4)는 별도로 남는다. 단순히 가능한 가장 긴 자유 구간의 길이를 검사하는 것과 buddy의 크기·정렬·짝 상태 규칙은 다른 조건이다.

바이트 요구에서도 실제로 담을 모든 내용을 먼저 센다. payload 8193바이트와 자체 header 128바이트를 함께 저장하면 총 8321바이트다. page 4096에서 최소 세 page이고 order 2는 네 page 16384바이트를 확보한다. header까지 뺀 미사용량은 8063바이트다. exact 최소 page 모형은 12288바이트, 미사용 3967바이트다. 실제 성공과 올바른 해제는 계산과 별도이며 할당 인터페이스·order 또는 size 기록을 유지해야 한다.

페이지는 물리 메모리 관리의 단위

커널은 물리 메모리를 페이지 단위로 관리한다. 페이지 크기는 시스템과 설정에 따라 달라지며 이 단원은 계산용으로4096바이트를 가정한다. 연속 물리 페이지 요구는 페이지 프레임 번호가 이어지는 영역을 필요로 한다. 가상 주소가 이어진다는 사실만으로 물리 주소도 이어지는 것은 아니다.

Linux의 alloc_pages는 order에 따라 2^order 페이지를 요청하는 인터페이스다. order0은1페이지, order1은2페이지, order2는4페이지다. 바이트 요구를 페이지 수로 올림한 뒤 그 수를 덮는 거듭제곱 크기를 선택하는 산술과 실제 할당 성공은 구별한다.

올림과 내부 낭비

9000바이트를 저장하려면4096페이지 두 개의8192바이트로는 부족해 최소3페이지가 필요하다. 거듭제곱 페이지 요청은4페이지로 올라가므로 사용 목적보다 큰 공간이 할당될 수 있다. 이는 할당 단위에서 생기는 내부 낭비다.

Linux의 alloc_pages_exact는 요청 바이트를 덮는 최소 페이지 수의 물리 연속 영역을 다루며 free_pages_exact와 짝을 맞춘다. alloc_pages와 해당 order 해제를 섞어 쓰는 것은 올바른 수명 정책이 아니다. 예제의 두 계산은 서로 다른 인터페이스의 크기 모형이지 모든 커널 할당에 같은 올림을 적용하는 규칙이 아니다.

연속성과 호출 문맥의 제약

여유 페이지가 여러 곳에 흩어지면 총량은 커도 연속 요청을 만족하지 못할 수 있다. 노드·zone·정렬·회수 가능성 등의 제약도 요청에 영향을 준다. 본문의 작은 자유목록 모형은 재배치·회수·예약 없이 고정된 프레임만 보고 연속성 조건을 검사한다.

GFP 플래그는 어떤 문맥과 방식으로 메모리를 찾는지 표현한다. GFP_KERNEL은 직접 회수와 수면을 허용하므로 수면할 수 있는 호출 문맥이어야 한다. NOWAIT나 ATOMIC도 성공 보장이 아니며 실패 처리와 대체 경로가 필요하다. 여유 총량만 읽고 무조건 성공으로 기록하지 않는다.

중간 과정을 따라가는 예제

페이지 크기4096을 가정한다. 9000바이트 요구의 최소 페이지 수, 최소 적합 order와 할당 크기를 구하라. alloc_pages_exact 크기 모형과 남는 바이트를 비교하라.

  1. 2×4096=8192<9000≤12288=3×4096이므로 최소3페이지다.

  2. 2^1=2는 부족하고2^2=4가 충분하므로 최소 order2,크기16384다. 남는 공간은16384−9000=7384바이트다.

  3. exact의 최소3페이지 크기는12288,남는 공간3288바이트다. 두 크기 차이는4096바이트다.

최소3페이지지만 order2 요청은4페이지다. 물리 연속 영역의 실제 존재나 API 실행 성공은 이 크기 계산으로 증명하지 않는다.

조건을 바꾸어 비교하기

인접하지만 합칠 수 없는 두 블록

자유 [2,4),[4,6)으로 왜 네 frame의 order 2를 만들 수 없는가?

  1. 각 order 1의 시작은 2와 4로 두 frame 경계에 맞는다.

  2. 합친 시작 2는 네 frame 경계에 맞지 않는다.

  3. buddy 시작은 각각 0과 6이라 서로 짝이 아니다.

총 자유량 네 frame과 정렬된 order 2 한 블록의 존재는 다르다.

비교할 점

실제 커널의 추가 placement 제약까지 확인한 모형은 아니다.

같은 저장 목적, 다른 확보 단위

payload 8193와 header 128을 담는 order 모형과 exact 모형의 미사용량을 계산하라.

  1. 총 요구량은 8321이며 두 page 8192로 부족하다.

  2. order 모형은 네 page 16384를 확보하여 8063바이트가 남는다.

  3. exact 모형은 세 page 12288을 확보하여 3967바이트가 남는다.

확보량과 미사용량 차이는 각각 한 page 4096바이트다.

비교할 점

header를 공간 비용에서 빼먹거나 exact 할당을 order 해제로 섞지 않는다.

연습 1 · 값과 상태 예측

자유 [2,4),[4,6)에서 정확히 [6,8)을 반환하면 자유 블록과 order 2 시작을 구하라.

힌트 1

start 4의 order 1 buddy는 6이다.

힌트 2

합친 부모의 시작과 크기를 검사한다.

풀이와 답 확인

  1. [4,6)과 [6,8)이 [4,8)로 합쳐진다.

  2. [2,4)는 별도이며 정렬 order 2 시작은 4다.

order 2 하나를 확보할 수 있다. 모든 여유 frame이 한 부모로 합쳐진 것은 아니다.

흔한 오답에서 다시 생각하기

인접 [2,4)도 붙여서 order 2 크기를 여섯 frame으로 만든다.

order 크기는 거듭제곱이며 임의 길이 여유 구간을 그 order로 부르지 않는다.

연습 2 · 오류 찾아 고치기

start 2의 order 1 buddy를 단순히 다음 시작 4라고 쓴 계산을 고쳐라.

힌트 1

order 1 크기는 이진수 10이다.

힌트 2

start 2도 이진수 10이다.

풀이와 답 확인

  1. 10 XOR 10=00이라 buddy 시작은 0이다.

  2. start 4는 100 XOR 010=110이라 buddy 시작이 6이다.

다음 이웃이 항상 buddy는 아니다. 정렬된 부모의 반쪽 짝을 구한다.

흔한 오답에서 다시 생각하기

같은 크기의 오른쪽 이웃을 언제나 짝으로 합치면 된다.

서로 다른 부모 경계를 넘는 이웃은 정렬된 큰 블록을 만들지 못한다.

연습 3 · 직접 만들어 보기

[2,4),[4,8)가 자유일 때 [0,2)를 반환하여 전체 [0,8)을 만드는 병합 순서를 적어라.

힌트 1

먼저 같은 order끼리 합친다.

힌트 2

새로 생긴 부모에서 한 단계 위 buddy를 다시 검사한다.

풀이와 답 확인

  1. [0,2)와 [2,4)를 합쳐 order 2 [0,4)를 만든다.

  2. [0,4)와 [4,8)를 합쳐 order 3 [0,8)을 만든다.

1→2→3의 단계별 병합이며 모든 해당 frame이 실제 자유라는 전제가 필요하다.

흔한 오답에서 다시 생각하기

살아 있는 [0,2)도 필요하면 자유로 취급하여 합칠 수 있다.

할당 중인 소유자의 frame을 자유목록에 포함하면 중복 할당과 자료 손상이 생길 수 있다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

같은 payload 8193에 header를 0으로 줄여도 최소 order가 바뀌는가? header가 4096이면?

힌트 1

page 4096이며 총 요구량을 다시 계산한다.

힌트 2

order는 필요한 page 수를 덮는 거듭제곱이다.

풀이와 답 확인

  1. header 0의 총 8193은 세 page라 order 2다.

  2. header 4096의 총 12289는 네 page라 역시 order 2다.

  3. 두 경우 모두 확보 16384지만 미사용량은 8191과 4095바이트다.

요구량 변화가 언제나 order 변화로 이어지지는 않는다. 각 page·거듭제곱 경계를 따로 검사한다.

흔한 오답에서 다시 생각하기

header가 늘면 한 바이트마다 order도 하나씩 증가한다.

order는 바이트 단위가 아니라 거듭제곱 page 수 구간을 나타낸다.

C의 malloc과 커널의 kmalloc은 이름만 다른 같은 함수일까?

살아 있는 객체 수가 같으면 allocator가 확보한 page 수도 같을까?

자체 슬롯 allocator는 page 4096바이트, 슬롯 128바이트로 한 page에 32개를 놓는다. 객체 33개가 A page에 32개와 B page에 한 개로 배치돼 있다고 정한다. 이번에는 살아 있는 객체를 자동 이동하지 않고, 완전히 빈 page만 즉시 반환하는 정책을 명시한다. A의 두 객체를 해제하면 A에 30개, B에 한 개가 남아 총 31개지만 두 page가 모두 필요하다.

같은 처음 상태에서 B의 한 객체와 A의 한 객체를 해제하면 A에 31개, B에 영 개다. 빈 B를 반환하는 정책이라 한 page만 확보한다. 두 경우 모두 살아 있는 객체 수 31개인데 확보량은 8192와 4096바이트다. 내용과 포인터를 이동하지 않는 배치, 빈 page 반환 여부에 따라 차이가 난다. 빈 page를 캐시에 유지하는 정책으로 바꾸면 후자도 당장 확보량을 줄이지 않을 수 있다.

객체 요구를 계산할 때 작은 정수라도 넘침을 검사한다. 자체 8비트 unsigned size는 최대 255이며 header 32, 원소 크기 50바이트인 배열 객체를 생각한다. n=5의 실제 필요량은 32+5×50=282지만 순환 산술에서는 26이 된다. 작아진 26을 할당하고 원소 다섯 개를 쓰는 것은 크기 계산을 잘못한 것이다. 표현 가능 조건 n≤floor((255−32)/50)=4를 실제 계산 전에 검사한다.

n=4의 총량 232는 표현 가능하지만 할당 성공까지 보장하지 않는다. 사용자 malloc, 커널 객체·page 할당의 문맥과 실패 계약은 별도다. Linux 공식 가이드는 배열 및 구조 크기 계산 helper와 GFP 문맥·대체 경로를 설명한다. 자체 8비트 예를 실제 size_t 폭이나 특정 커널의 정확한 객체 크기라고 읽지 않는다.

사용자 힙의 주소와 커널 객체

malloc은 사용자 프로그램에 요청 크기의 동적 저장 공간을 주는 라이브러리 인터페이스다. glibc allocator는 관리하는 영역을 다시 사용하거나 필요할 때 brk/mmap 등을 이용한다. 따라서 malloc 호출 하나가 커널의 물리 페이지 요청 하나와 항상 일대일로 대응하지 않는다.

반면 kmalloc 등은 커널 코드의 객체를 위한 할당이다. 사용자 malloc 포인터를 kfree로 해제하거나 커널 kmalloc 객체를 사용자 free로 해제하지 않는다. 서로 다른 권한·주소 공간·allocator 계약을 구별해야 한다. user pointer를 커널에서 다루는 일도 별도 검증·복사 API의 문제다.

객체 크기와 페이지 크기는 다르다

작은 객체를 많이 만들면 페이지를 쪼개 일정 크기 슬롯으로 관리하는 slab 계열 접근이 유용하다. Linux는 kmem_cache로 같은 종류 객체를 관리할 수 있다. 실제 슬롯 크기·정렬·메타데이터·페이지 배치는 구성에 따라 다르므로 고정값을 제품 규칙처럼 외우지 않는다.

본문의 계산은 페이지4096,슬롯128,객체요구100바이트이며 메타데이터와 정렬 추가 비용이 없다는 자체 슬롯 모형이다. 한 페이지에32슬롯이다. 객체 요구 바이트 합,슬롯 점유 바이트,실제로 확보한 페이지 바이트는 서로 다른 수치다.

초기화와 해제도 계약의 일부

malloc과 일반 kmalloc을 받았다고 모든 바이트가0이라고 가정하면 안 된다. calloc이나 kzalloc처럼0 초기화를 명시한 API와 구별한다. 배열 크기의 곱셈 overflow를 안전하게 확인하고 할당 실패를 검사해야 한다. 이미 해제한 객체를 다시 해제하거나 계속 접근하면 수명 오류다.

큰 커널 가상 연속 영역을 위한 vmalloc은 물리 연속을 보장하지 않는다. kvmalloc은 kmalloc을 시도하고 필요 시 vmalloc 경로를 쓸 수 있어 그 반환값도 물리 연속을 가정하면 안 된다. 해당 반환값의 해제에는 kvfree 등 문서가 정한 쌍을 사용한다.

객체 자동 이동은 없고 B가 완전히 빈 경우에만 반환하는 지정 정책이다. 실제 Linux의 slab page 회수나 사용자 RSS를 측정한 표가 아니다.

중간 과정을 따라가는 예제

자체 슬롯 모형 페이지4096,슬롯128,객체요구100바이트에서 객체33개를 만든다. 페이지 수·요구 바이트·슬롯 점유 및 페이지 전체와 요구량의 차이를 구하라.

  1. 한 페이지의 슬롯 수는4096/128=32이므로33개는2페이지가 필요하다. 전체8192바이트다.

  2. 요구 바이트33×100=3300,슬롯 점유33×128=4224다. 각 슬롯의 추가28바이트가33개라924바이트다.

  3. 남는31슬롯의3968바이트와 내부924를 합하면4892다.8192−3300=4892와 같다.

페이지 확보8192,요구3300,슬롯점유4224이며 차이4892바이트다. 실제 Linux 메모리 사용량이나 RSS 측정이 아닌 가정된 모형이다.

조건을 바꾸어 비교하기

개수는 같지만 page는 다름

두 경우의 살아 있는 객체 수와 실제 확보 page 수를 비교하라.

  1. A30/B1은 두 page에 live 슬롯이 남는다.

  2. A31/B0은 빈 B를 즉시 반환하는 정책이라 한 page만 남는다.

  3. 두 경우의 live 합은 각각 31이다.

live 객체 수만으로 확보 page 수를 확정할 수 없다.

비교할 점

최소 packing 가능량과 현재 배치를 혼동하지 않는다.

줄어든 정수 값의 함정

8비트 unsigned size 모형에서 n=5, header 32 바이트, 원소당 50 바이트로 계산한 순환 결과 26 바이트를 올바른 요구량으로 볼 수 있는가?

  1. 수학적 총량은 282다.

  2. 282 mod 256=26이지만 이는 표현 범위를 넘겨 줄어든 값이다.

  3. 원소의 실제 저장 요구를 26바이트가 충족하지 못한다.

요청을 거절하거나 충분한 폭과 검사 계약으로 바꾸어야 한다.

비교할 점

계산된 정수 값이 작다고 작은 객체 요구라는 결론을 내리지 않는다.

풀이 보기

연습 1 · 값과 상태 예측

같은 A32/B1 상태에서 A 한 개만 해제한다. 객체 요구가 각 100바이트라면 live 요구 합과 확보량은?

힌트 1

A31/B1이라 총 live32다.

힌트 2

빈 page가 없어 반환하지 않는다.

풀이와 답 확인

  1. live 요구 합은 32×100=3200바이트다.

  2. 확보량은 두 page 8192바이트다.

객체 요구 합과 확보량은 다르며 해당 슬롯의 나머지와 빈 슬롯도 포함한다.

흔한 오답에서 다시 생각하기

32개면 반드시 한 page이므로 확보량은 4096이다.

현재 배치는 두 page에 걸쳐 있고 자동 이동하지 않는다고 정했다.

연습 2 · 오류 찾아 고치기

n=4이면 232가 255 이하라 커널 할당도 반드시 성공한다고 썼다. 조건을 나누어 고쳐라.

힌트 1

산술 표현 가능성과 자원 확보는 다른 검사다.

힌트 2

GFP와 수면 가능 문맥도 별도 조건이다.

풀이와 답 확인

  1. 232의 표현 가능성은 크기 산술을 통과했다는 뜻이다.

  2. 적절한 API·문맥과 실제 반환 성공 여부를 확인해야 한다.

  3. 실패 때 사용할 대체 또는 오류 반환 정책을 마련한다.

크기 검사만으로 allocator 성공을 인증하지 않는다.

흔한 오답에서 다시 생각하기

overflow만 없으면 물리 연속성과 모든 API 조건도 해결된다.

표현 범위는 placement·자원량·문맥·권한을 대신 검사하지 않는다.

연습 3 · 직접 만들어 보기

8비트 unsigned 최대255,header32,원소50에서 허용할 최대 n을 먼저 계산하고 n=4/5를 분류하라.

힌트 1

255−32를 먼저 구한다.

힌트 2

비음수 정수 나눗셈의 몫을 사용한다.

풀이와 답 확인

  1. 남은 표현 가능량은 223바이트다.

  2. floor(223/50)=4라 최대 n은 4다.

  3. n=4의 총 요구량은 232 바이트로 표현 범위를 통과하고, n=5의 총 요구량은 282 바이트라 거절한다.

곱셈·덧셈의 순환 결과를 계산한 뒤 작아 보이는 값만 검사하지 않는다.

흔한 오답에서 다시 생각하기

순환 산술의 계산 결과가 26≤255이므로 n=5도 통과한다.

실제 필요한 크기가 표현 범위를 넘겼는지 계산 이전 경계 조건으로 검사한다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

A31/B0 상태에서 allocator가 빈 page를 캐시하는 정책으로 바뀌면 확보량은 즉시 줄어야 하는가? 캐시와 누수를 구별할 기록은?

힌트 1

page 반환 조건이 바뀌었다.

힌트 2

의도적으로 소유한 재사용 저장 공간인지 확인한다.

풀이와 답 확인

  1. B가 빈 상태여도 정책상 유지하면 두 page 확보 8192가 남을 수 있다.

  2. 재사용·반환 주체와 정책, live 슬롯 수·소유 기록을 확인한다.

  3. 잊은 소유 참조나 반환 경로 누락으로 남은 객체는 단순 의도된 캐시와 구별한다.

즉시 반환은 새로운 정책의 보장이 아니다. 실제 커널 지표를 이 계산으로 판정하지 않는다.

큐에 객체를 넣을 때 소유권을 넘기는가, 새 참조를 나누는가?

객체 O의 생산자 참조가 한 개로 시작한다. 자체 큐 계약 첫 방식은 소유권 이전이다. enqueue 성공 때 기존 한 참조가 생산자에서 큐로 이동하여 계수는 한 개를 유지한다. 생산자는 성공 뒤 O를 더 사용하거나 반납하지 않는다. dequeue 성공 때 같은 참조가 큐에서 소비자로 이동하고 소비자가 마지막 put을 수행하여 release한다. 포인터 위치가 바뀌는 사건과 새 생존 책임을 추가하는 사건은 다르다.

다른 계약은 생산자가 O를 계속 보유하면서 큐에 독립 참조를 추가하는 방식이다. 유효 생산자 참조 아래 enqueue 전에 get하여 계수가 두 개가 된다. enqueue 성공 뒤 큐의 참조는 소비자가 받고, 생산자와 소비자가 각각 put해야 한다. 어떤 순서로 끝나도 2→1→0이다. 두 계약을 섞어 생산자가 소유권 이전 뒤 put까지 하면 큐가 사용할 객체를 너무 일찍 해제할 수 있다.

실패 경로도 계약마다 다르다. 소유권 이전 계약에서 enqueue가 실패하고 소비자가 전혀 보지 않았다고 정하면 참조는 여전히 생산자 한 개다. 생산자가 오류를 처리하면서 한 번 put한다. 독립 참조 추가 계약에서 get 뒤 enqueue가 실패하여 큐가 참조를 받지 않았다면, 미전달 참조를 put하여 2→1로 되돌리고 생산자 자신의 참조도 사용 종료 때 put하여 1→0으로 만든다. 실패와 동시에 소비자에게 전달될 수 있는 큐라면 별도 계약을 다시 정해야 한다.

숫자 계수가 맞아도 사용 가능 여부를 확인해야 한다. raw 포인터 별칭은 소유 참조를 자동 늘리지 않는다. 마지막 put 뒤 그 값을 다시 읽으면 해제된 메모리에 접근할 수 있다. 또한 put의 반환 영은 “내 호출이 마지막 해제를 하지 않았다”는 결과일 뿐, 다른 소유자가 이미 마지막 put을 했을 가능성까지 배제하는 영구 생존 증명은 아니다. 객체 내용 동기화와 lookup 수명 보호는 별도다.

살아 있어야 할 이유를 센다

참조계수는 객체를 계속 사용할 권한과 책임을 가진 참조의 수를 추적한다. 단순히 포인터 변수가 몇 개인지 세는 것과 같지 않다. 임시 별칭은 별도 참조 취득을 하지 않을 수 있지만 사용 기간은 이미 가진 소유 참조로 보호해야 한다.

Linux kref_init은 새 객체의 계수를1로 둔다. 다른 작업자에게 독립적으로 유지할 참조를 넘기기 전에 kref_get을 하고,사용이 끝나면 kref_put을 한다. 마지막 참조가 사라지면 release 콜백으로 객체 정리를 한다. 이 단원은 콜백이 즉시 한 번 해제하는 단순 모형을 쓴다.

순서가 객체 수명을 보호한다

기존 유효 참조를 가진 상태에서 다른 사용자에게 넘기기 전에 증가해야 한다. 먼저 넘기고 나중에 증가하면 받은 작업자가 먼저 반납해 마지막 해제가 일어난 뒤 증가하려는 경쟁이 생길 수 있다. 새로운 참조가 생겼다는 기록과 실제 사용 가능 시점의 순서를 맞춘다.

목록에서 객체를 찾아 기존 참조 없이 새로 취득할 때는 lookup과 마지막 해제 사이 수명을 보호해야 한다. get_unless_zero 같은 함수 이름만으로 이미 해제된 메모리 접근이 안전해지지 않는다. 잠금이나 적절한 수명 보호가 필요하며 성공 반환값도 확인해야 한다.

계수만으로 모든 문제를 해결하지는 않는다

참조계수는 객체의 생존을 다루며 객체 내용의 동시 변경까지 직렬화하지 않는다. 두 사용자가 같은 필드를 바꾸면 별도 동기화가 필요하다. 한 취득에 반납을 빠뜨리면 계수가0이 되지 않아 사용자가 없어도 객체가 남을 수 있다. 중복 반납은 반대로 너무 일찍 해제할 수 있다.

서로 강한 참조를 보유한 두 객체는 외부 사용자가 사라져도 서로의 계수가 남을 수 있다. 단순 참조계수 방식에서 순환을 자동 수집한다고 가정하면 안 된다. 약한 참조나 명시적 연결 해제 등 설계가 필요하며 캐시로 의도적으로 유지한 메모리와 잊은 참조 누수도 구별한다.

중간 과정을 따라가는 예제

새 객체 O의 부모 참조는1이다. 부모가 A에게 넘기기 전get, B에게 넘기기 전get을 한다. A완료put,부모완료put,B완료put 순서다. 다른 참조는 없고 마지막 release가 객체를 해제한다고 하자.

  1. 초기1→A취득2→B취득3이다. 두 작업자는 부모의 저장 공간 종료와 독립된 참조를 받는다.

  2. A반납3→2,부모반납2→1이라 아직 B가 사용할 수 있다.

  3. B반납1→0에서 release가1번 호출되어 객체를 해제한다. 이후 포인터가 남아 있어도 사용할 권한은 없다.

계수1→2→3→2→1→0,release1번이다. 마지막 반납 뒤 접근하지 않는 조건이 필요하다.

소유권 이전의 성공

생산자 참조1에서 enqueue 성공·dequeue 성공·소비자 완료가 이어진다. 추가 get 없이 안전할 조건은?

  1. enqueue 성공 때 기존 참조의 소유 주체를 큐로 바꾼다.

  2. 생산자는 이후 접근과 put을 하지 않는다.

  3. dequeue 뒤 소비자가 같은 참조를 받아 마지막 put한다.

계수는 1→1→1→0이며 release 한 번이다. 큐의 수명·직렬화는 별도 올바른 계약을 가정한다.

비교할 점

생산자가 계속 객체를 써야 하는 계약에는 추가 소유 참조가 필요하다.

독립 참조를 추가했지만 전달 실패

생산자가 get하여 계수2가 됐지만 enqueue가 소비자 전달 없이 실패했다. 최종 오류 반환까지 put 횟수는?

  1. 미전달 참조를 회수하는 put으로 2→1이다.

  2. 생산자가 더 사용할 일이 없을 때 자신의 put으로 1→0이다.

  3. 소비자는 참조를 받지 않아 put하지 않는다.

총 put 두 번, release 한 번이다. 실패라는 이유로 추가 get을 잊거나 소비자에게 가상 put을 맡기지 않는다.

성공과 실패에서 같은 종료 책임을 가진 주체가 누구인지 각각 적는다.

연습 1 · 값과 상태 예측

독립 참조 성공에서 생산자는 아직 O를 사용하고 소비자가 먼저 put했다. 계수와 생산자의 사용 근거는?

힌트 1

생산자와 큐에 각각 독립 참조가 있었다.

힌트 2

소비자는 자기 참조만 반납했다.

풀이와 답 확인

  1. 계수는 2→1이다.

  2. 남은 한 참조는 생산자 소유라 생산자는 자기 사용 기간에 O를 유지한다.

  3. 생산자도 사용을 끝내면 put하여 release한다.

생산자의 현재 소유 참조가 생존 근거다. 다른 호출의 이전 반환값만으로 생존을 추정하지 않는다.

소비자가 put했으니 생산자의 소유 참조도 자동으로 사라진다.

각 독립 참조는 그 책임을 가진 주체의 반납으로 제거한다.

연습 2 · 오류 찾아 고치기

소유권 이전 성공 뒤 생산자가 “항상 마지막에 put”하여 계수1→0으로 만들었다. 소비자가 아직 큐에 있는 객체를 읽으려 한다. 어디서 고쳐야 하는가?

힌트 1

enqueue 성공 때 생산자 소유권은 이미 이동했다.

힌트 2

계수1은 현재 큐의 참조다.

풀이와 답 확인

  1. 생산자는 이전 성공 뒤 자신의 put을 하지 않아야 한다.

  2. 소비자에게 넘어간 참조가 사용 종료 때 마지막 put한다.

  3. 생산자가 추가로 사용할 필요가 있다면 독립 참조 계약으로 바꾸고 get·put 책임을 명시한다.

소유권 이전과 공유 소유 계약을 섞은 조기 해제 오류다.

흔한 오답에서 다시 생각하기

put은 아무 주체나 같은 횟수만 맞추면 안전하다.

계수의 총량뿐 아니라 사용 중인 참조의 실제 소유 책임과 마지막 시점이 중요하다.

연습 3 · 직접 만들어 보기

소유권 이전 enqueue가 전달 없이 실패한 경우와 독립 참조 enqueue가 get 뒤 전달 없이 실패한 경우의 정리 경로를 각각 적어라.

힌트 1

두 경우 모두 최종적으로 생산자도 사용을 끝낸다.

힌트 2

큐나 소비자는 실패한 O를 참조하지 않는 계약이다.

풀이와 답 확인

  1. 소유권 이전 실패에서는 생산자의 참조 한 개가 그대로 남으므로 생산자가 한 번 put하여 계수를 1에서 0으로 만든다.

  2. 독립 참조 추가 뒤 실패에서는 미전달 참조의 put으로 계수를 2에서 1로 되돌린 다음, 생산자 종료 put으로 1에서 0으로 만든다.

실패 전에 실제 취득한 참조와 전달 여부에 따라 정리 횟수가 달라진다.

흔한 오답에서 다시 생각하기

두 계약 모두 실패했으니 무조건 같은 한 번 put하면 된다.

독립 참조 계약은 get으로 추가한 미전달 책임을 별도로 회수해야 한다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

두 소유자가 있던 O에서 P의 put 반환이 0이었다. P가 자기 참조를 반납한 뒤 그 결과를 근거로 raw 별칭을 계속 읽어도 되는가?

힌트 1

다른 소유자는 언제든 자신의 마지막 put을 수행할 수 있다.

힌트 2

P는 이미 자기 수명 보호 참조를 반납했다.

풀이와 답 확인

  1. 반환0은 P 호출이 마지막 참조를 제거하지 않았다는 정보다.

  2. Q가 뒤이어 마지막 put을 하면 O가 해제될 수 있다.

  3. P의 raw 별칭 자체는 생존 참조가 아니므로 계속 접근할 근거가 없다.

계속 읽어서는 안 된다. 필요한 사용 기간에는 유효 소유 참조 또는 적절한 수명 보호 계약을 유지해야 한다.

put 반환0이면 이후에도 객체는 계속 살아 있다고 인증됐다.

다른 호출자가 마지막 해제를 할 수 있어 그 결과만으로 미래 수명을 보장하지 않는다.

풀이와 답 확인

  1. [2,4)의 시작 PFN 2에서 order 1 buddy 시작은 2 XOR 2=0이다. [4,6)의 시작 PFN 4에서 buddy 시작은 4 XOR 2=6이므로 이 두 블록은 서로 짝이 아니어서 합칠 수 없다.

  2. A의 두 객체를 해제하면 A에 30개, B에 한 개가 남는다. 두 page 모두 live 슬롯이 있으므로 확보량은 8192 바이트다. 객체 자동 이동은 없다는 조건이다.

  3. 소유권 이전 성공 뒤 생산자는 O를 사용하거나 put하지 않는다.

  4. 큐에서 소비자로 옮긴 같은 참조는 소비자의 사용 종료 put에서 계수가 1에서 0으로 내려가며 release된다.

  5. 크기·현재 배치·호출 문맥·실패·소유권·정리 시점을 별도의 조건으로 기록한다.

총 자유량·live 개수·put 총횟수만 보지 않고 정렬 부모, 실제 배치와 참조 소유 계약을 확인한다.

해결한 뒤 점검할 것

  • 시작 PFN 2의 buddy가 2 XOR 2=0이고 시작 PFN 4의 buddy가 4 XOR 2=6임을 계산한다.

  • live31이면서 두 page 확보가 남는 배치를 설명한다.

  • 이전 성공 뒤 생산자 접근·put 금지와 마지막 소비자 책임을 명시한다.

  • 실제 Linux 할당·큐 실행·학습자 실험의 미수행을 구별한다.

[6,8)을 반환하면 [4,8)로 합쳐지고 [0,2)까지 반환하면 [0,4)와 [4,8)을 거쳐 [0,8)로 합쳐진다. payload 8193 바이트와 header 128 바이트의 총 요구량은 8321 바이트다. order 2는 16384 바이트를 확보해 8063 바이트가 남고 exact 최소 page 모형은 12288 바이트를 확보해 3967 바이트가 남는다. header가 0 바이트이면 총 8193 바이트, header가 4096 바이트이면 총 12289 바이트이며 두 경우 모두 order 2이고 미사용량은 각각 8191 및 4095 바이트다. 슬롯의 A30/B1 배치는 live 31개와 확보 8192 바이트이고 A31/B0 배치는 같은 live 31개라도 빈 page 즉시 반환 정책에서 확보 4096 바이트다. 8비트 unsigned size의 header 32와 원소당 50 바이트는 최대 n=4를 허용하며 총 232 바이트다. n=5의 실제 총량 282 바이트가 순환 산술에서 26이 되는 것은 거절할 크기 오류다. 큐 소유권 이전 성공은 계수 1을 유지하다 소비자 put에서 0이 되고 실패는 생산자 put 한 번으로 0이 된다. 독립 참조 추가 성공과 실패 모두 취득 뒤 2에서 각 책임의 두 put을 거쳐 0이 되지만 실패의 첫 put은 미전달 책임 회수다. 마지막 release는 각 경로에서 한 번이다. put 반환값 0은 이후 수명을 보장하지 않으며 raw 별칭은 이미 반납한 소유 참조를 대신하지 못한다. 모든 전이 조건도 같은 모형으로 손대조했다.
