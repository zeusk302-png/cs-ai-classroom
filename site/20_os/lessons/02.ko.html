소단원 2.1

부트 흐름과 초기화

켜진 CPU는 아직 준비되지 않은 커널 함수를 바로 호출해도 될까?

준비 개념과 학습 목표

준비 개념

  • CPU는 명령을 실행하는 장치다. PC는 다음에 실행할 명령 주소, 레지스터는 CPU 안의 작은 저장 장소다. 메모리 주소는 바이트 위치를 가리키는 숫자다.

  • 스택은 함수의 임시 상태와 반환 정보를 담는 영역이다. 스택 포인터 sp는 그 영역에서 현재 사용할 위치를 표시한다. 이 단원은 주소가 감소하는 방향으로 자라는 스택을 가정한다.

  • 초기화는 이후 코드가 요구하는 유효한 상태를 먼저 만드는 일이다. hart는 RISC-V에서 독립 실행 상태를 가진 하드웨어 실행 단위이며 여기서는 서로 다른 hart의 시작 스택을 구별한다.

학습 목표

  • 부팅의 진입 조건과 초기화의 의존 순서를 설명한다.

  • hart별 스택 구간을 계산하고 겹침 여부를 확인한다.

  • 한 hart의 전역 초기화 완료와 다른 hart의 안전한 관찰을 구별한다.

1. 전원을 켠 순간과 커널 진입은 다르다

부팅은 시작 상태에서 실행 가능한 운영체제 상태까지 가는 과정이다. 실제 기계에는 펌웨어와 로더, 장치 탐색 등 여러 경로가 있다. 여기서는 xv6의 QEMU 커널 직접 적재 경로를 참고한다. 읽은 entry.S는 0x80000000에서 시작하도록 설명한다. 이 주소나 흐름을 모든 PC의 부팅 규칙으로 일반화하지 않는다.

CPU가 C 함수를 실행하려면 해당 코드가 적재되어 있고 스택 등 호출에 필요한 상태가 유효해야 한다. 종이 모형에서는 적재 성공·주소 접근 가능·hart 번호 범위가 이미 만족한다고 가정한다. 부팅 성공이 사용자 앱 성공이나 저장 데이터의 정확성까지 뜻하지는 않는다.

2. 스택을 만든 뒤 권한과 주소 상태를 준비한다

읽은 entry.S는 hart 번호 h에 대해 sp=stack0+(h+1)·4096으로 시작 스택 끝을 만든다. start.c는 머신 모드에서 supervisor 모드로 이어질 반환 상태, 페이지 변환의 초기 상태, 인터럽트 위임과 타이머 등을 준비한 뒤 mret로 main에 진입한다. 이는 xv6의 특정 구현 경로다.

자체 스택 모형에서 밑주소 B와 크기 S>0를 정하고 hart h의 영역을 [B+hS,B+(h+1)S)로 둔다. h가 서로 다른 정수이고 각 영역이 실제 확보되었다면 영역 내부는 겹치지 않는다. sp가 상단 경계라는 것은 그 경계 바이트를 이미 써도 된다는 뜻이 아니다. 첫 저장은 스택 규약에 맞게 안쪽으로 내려온 뒤 수행한다.

3. 초기화는 목록보다 의존 관계가 중요하다

main.c에서 hart 0은 메모리 할당기, 커널 페이지 테이블, 프로세스·트랩·장치 관련 구조를 준비하고 첫 사용자 프로세스를 만든다. 다른 hart는 started의 완료를 기다린 뒤 자신의 주소 변환과 트랩·인터럽트 상태를 준비한다. 모든 초기화가 모든 hart에서 반복되는 것은 아니다.

공유 완료 표시는 자료를 완성한 뒤 게시해야 한다. 현재 읽은 main.c의 release 저장과 acquire 관찰은 다른 hart가 완료 뒤 초기화 결과를 보는 연결을 제공한다. 종이에서는 완료 플래그 F를 마지막에 1로 만드는 규칙으로 표현한다. 실제 병렬 하드웨어에서 일반 변수에 숫자만 쓰는 것으로 같은 보장을 얻는다고 주장하지 않는다.

중간 과정을 따라가는 예제

가상 밑주소 B=0x1000, hart 2개(h=0,1), 각 시작 스택 S=0x1000바이트. 실제 메모리는 확보되었고 주소 넘침은 없다. 공통 자료 준비 뒤 F=1을 게시하며 hart 1은 F=1을 관찰한 뒤 사용한다. 스택 구간과 안전한 순서를 구하라.

  1. hart 0의 구간은 [0x1000,0x2000), 초기 sp는 0x2000이다.

  2. hart 1의 구간은 [0x2000,0x3000), 초기 sp는 0x3000이다. 경계 0x2000은 첫 구간에 포함되지 않는다.

  3. hart 0이 공통 자료를 준비하는 동안 F=0이다. hart 1은 공통 자료 사용 단계에 진입하지 않는다.

  4. 자료 완성→F=1 게시→hart 1의 완료 관찰→hart 1 자신의 설정→실행 선택 순서가 가능하다. 실제 메모리 순서는 release/acquire 등의 구현 조건이 필요하다.

각 영역은 4096바이트이며 교집합이 없다. 완료 관찰은 초기화된 자료 사용의 선행 조건이다. 이 추적은 실제 부팅 측정이 아니다.

종이와 본문으로 직접 해보기

종이에 B=1000, S=100, h=0,1,2인 세 스택의 반열린 구간과 sp를 적어라. 준비 A→준비 B→F=1이라는 순서에서 F=1을 준비 A 앞에 옮기면 어떤 잘못된 관찰이 가능한가? 주소는 십진수이며 넘침은 없다.

힌트 보기

왼쪽 경계는 포함하고 오른쪽은 제외한다. 다른 hart가 F=1을 본 직후 자료 B를 읽는 장면을 그린다.

풀이 보기

구간은 [1000,1100), [1100,1200), [1200,1300), sp는 1100,1200,1300이다. 먼저 F=1을 쓰면 다른 hart가 준비 B가 끝나기 전에 B를 읽을 수 있다. 영역 분리와 완료 게시의 순서는 각각 다른 오류를 막는다.

오해와 반례

부팅 화면이 보이면 모든 CPU와 사용자 프로그램 초기화가 끝난 것이다.

출력은 특정 지점에 도달했다는 관측이다. main.c의 부팅 출력 뒤에도 여러 초기화가 이어진다. 준비 완료 전의 출력과 완료 플래그를 혼동하면 다른 hart의 미완성 자료 접근을 허용한다.

자기점검

B=500, S=50, h=2이면 구간과 초기 sp는?

답과 이유 보기

[600,650), sp=650.

500+2·50=600이며 상단은 500+3·50=650이다. 영역 확보와 감소 방향 스택을 가정한다.

완료 플래그를 자료 작성 전에 게시해도 기다리는 hart가 안전한가?

답과 이유 보기

일반적으로 안전하지 않다.

완료를 관찰하고 미완성 자료를 사용할 반례가 가능하다. 게시 순서와 실제 메모리 순서 보장이 필요하다.

xv6의 0x80000000 진입을 모든 컴퓨터 부트 주소로 써도 되는가?

답과 이유 보기

안 된다.

이 주소는 읽은 QEMU·xv6 경로의 조건이며 펌웨어·ISA·기계에 따라 시작 경로가 다르다.

한 단계 더

심화: 영역 겹침이 없다는 사실을 증명하라. h<k이면 h+1≤k이므로 첫 영역의 모든 주소 x는 x<B+(h+1)S≤B+kS이고 둘째 영역의 주소는 B+kS 이상이다. 단, 정수 주소 계산에 넘침이 없어야 한다. 완료 플래그가 참이어도 초기화 중 실패를 무시했다면 유효 상태를 보장하지 못한다. 실패 시 완료 게시 금지 또는 명시적 실패 상태를 추가하는 계약을 설계해 보라.

소단원 2.2

트랩 프레임과 반환

앱 실행을 잠깐 멈추고 커널이 레지스터를 쓰면 원래 값을 어떻게 되찾을까?

준비 개념과 학습 목표

준비 개념

  • 사용자 모드는 제한된 권한, supervisor 모드는 커널이 쓰는 권한 상태다. 권한 변경은 주소공간 변경과 별개의 설정이다.

  • 트랩은 시스템 호출·예외·인터럽트 등으로 처리 코드에 진입하는 전이를 통칭한다. 예외는 현재 명령과 관련되고 인터럽트는 외부 사건 등에 의해 요청된다.

  • 레지스터 값과 실행 위치를 저장한 상태를 복원해야 중단된 계산을 이어 갈 수 있다. 트랩 프레임은 소프트웨어가 이 복귀 상태를 담는 메모리 구조다.

학습 목표

  • 하드웨어 트랩 처리와 소프트웨어 레지스터 저장을 구별한다.

  • 원인에 따라 복귀 PC를 선택하는 이유를 설명한다.

  • 정상적인 시스템 호출의 반환값과 다른 레지스터 복원을 추적한다.

1. 진입 정보와 모든 실행 상태는 다르다

RISC-V의 supervisor 트랩 경로는 원래 실행 위치와 원인 등 전용 상태를 기록하고 지정된 처리 주소로 제어를 보낸다. 범용 레지스터 전체를 자동으로 사용자별 메모리 구조에 저장하는 것으로 이해하면 안 된다. xv6의 uservec가 레지스터를 트랩 프레임에 저장한다. 이 구현의 x0는 항상 0인 레지스터라 별도 저장하지 않으며, 값이 변할 수 있는 나머지 범용 레지스터를 저장·복원한다.

종이 모형은 PC, 모드, 레지스터 a0와 t0만 그리지만 실제 프로세스에는 더 많은 상태가 있다. 저장 전에 t0를 작업용으로 덮으면 원래 t0를 잃을 수 있다. 따라서 처리 코드가 보존해야 하는 항목을 먼저 정하고 저장·복원 절차가 그 계약을 지키는지 검사한다.

2. 프레임과 페이지 테이블을 안전하게 연결한다

읽은 trampoline.S는 사용자 a0를 sscratch에 임시 보존하고 트랩 프레임 주소를 얻은 뒤 필요한 레지스터를 저장한다. 커널 스택·페이지 테이블 정보를 읽어 처리 코드로 간다. trampoline 코드의 같은 가상 주소 매핑은 페이지 테이블 전환을 가로질러 실행을 이어 가기 위한 xv6 설계다.

트랩 프레임이 사용자 주소공간에 매핑되어 있다는 말은 사용자가 마음대로 그 프레임을 수정할 수 있다는 뜻이 아니다. 접근 권한을 구별해야 한다. 종이 불변식은 “복귀에 사용할 저장 상태는 커널의 계약에 따라 보호되고, 처리 중 임시 레지스터 변경과 구별된다”이다. 다른 OS의 프레임 위치나 주소공간 전환 방식을 자동으로 같다고 가정하지 않는다. 현재 proc.c의 TRAPFRAME 매핑은 PTE_R|PTE_W이며 PTE_U를 넣지 않아 사용자 모드 접근을 허용하지 않는다.

3. 원인에 맞는 복귀 위치와 결과를 정한다

xv6 usertrap은 사용자 ecall에서 저장 PC에 4를 더한다. ecall은 이 경로에서 4바이트 명령이며 이미 요청한 호출을 다시 실행하지 않기 위해 다음 명령으로 돌아간다. 처리 결과는 a0 같은 약속된 반환 레지스터에 들어간다. 나머지 보존 대상은 원래 값으로 복원한다.

모든 트랩에 PC+4를 적용하면 안 된다. 해결 가능한 페이지 폴트는 실패했던 명령을 다시 실행해야 할 수 있고, 인터럽트는 저장된 재개 위치를 유지한다. 해결할 수 없는 예외는 프로세스 종료 등으로 이어져 사용자 복귀 자체가 없을 수 있다. 중첩 트랩과 스케줄링은 저장 상태의 수명·소유권을 더 요구하며 이 예제는 중첩 없는 정상 복귀 하나만 다룬다.

중간 과정을 따라가는 예제

가상 사용자 상태 PC=0x1000의 4바이트 ecall, a0=7,t0=9. 호출은 정상 완료하여 반환값 3을 a0에 넣고 t0는 보존한다. 단일 트랩이며 프로세스 종료·중첩·스케줄링은 없다.

  1. 트랩 진입에 따라 원인과 저장 PC=0x1000을 기록하고 커널 처리 경로로 간다. 하드웨어 기록과 범용 레지스터 저장은 구별한다.

  2. 소프트웨어가 프레임에 원래 a0=7,t0=9를 저장한다. 이후 커널 작업용 t0=99를 써도 프레임의 t0=9는 유지한다.

  3. 시스템 호출 계약에 따라 프레임의 a0를 반환값 3으로 바꾸고 복귀 PC를 0x1000+4=0x1004로 정한다.

  4. 복귀 준비 후 a0=3,t0=9를 복원하고 사용자 모드에서 PC=0x1004로 이어 간다. 임시 t0=99는 사용자 결과가 아니다.

복귀 상태는 사용자 모드, PC=0x1004,a0=3,t0=9다. a0의 의도된 결과 변경과 보존 레지스터의 복원은 양립한다.

종이와 본문으로 직접 해보기

실패한 명령의 저장 PC=200이고, 처리기가 페이지 매핑을 보완하여 같은 명령 재시도를 허용한다고 가정하라. 프레임의 t0=8, 처리 중 t0=40이다. 재시도 복귀 PC와 t0를 쓰고 PC에 무조건 4를 더할 때의 문제를 적어라.

힌트 보기

“처리 성공”은 원래 실패한 명령까지 이미 실행되었다는 뜻이 아니다. 프레임과 작업 레지스터를 따로 그린다.

풀이 보기

PC=200,t0=8로 복귀하여 실패했던 명령을 다시 실행한다. PC=204로 바꾸면 원래 명령의 일을 건너뛸 수 있다. 실제 페이지 폴트 처리의 지원 조건을 증명하는 활동은 아니며, 명시한 재시도 계약의 상태 추적이다.

오해와 반례

트랩 프레임을 복원하면 모든 레지스터가 반드시 원래와 같아야 한다.

보존 대상과 결과 전달 대상은 다르다. 정상 호출 예제는 t0=9를 보존하지만 a0=7을 결과 3으로 의도적으로 바꾼다. 종료되는 예외에는 원래 사용자 상태로의 복귀가 없다.

소단원 2.3

디바이스 인터럽트 처리

장치의 완료 신호가 오면 기다리던 앱이 그 순간 바로 실행되는 걸까?

준비 개념과 학습 목표

준비 개념

  • 장치는 CPU와 별도로 I/O를 진행할 수 있다. 완료 상태, 오류 상태와 CPU에 보낸 알림은 다른 정보다.

  • 인터럽트 제어기는 장치의 요청을 CPU에 연결한다. 인터럽트 서비스 루틴은 원인을 확인하고 장치 및 커널 상태를 처리하는 코드다.

  • 대기는 아직 실행할 수 없는 프로세스 상태, 준비는 실행 가능하지만 CPU를 배정받지 않은 상태, 실행은 실제 CPU를 사용하는 상태다.

학습 목표

  • 장치 원인 확인·데이터 처리·제어기 완료 통보를 구별한다.

  • 알림 하나와 요청 하나의 대응을 자동 가정하지 않는다.

  • I/O 완료부터 준비·실행까지의 상태와 지연을 추적한다.

1. 알림을 받으면 원인부터 확인한다

xv6의 외부 인터럽트 처리에서는 PLIC에서 IRQ를 claim하고 번호에 맞는 UART 또는 디스크 처리기를 호출한 뒤 0이 아닌 IRQ를 complete한다. claim은 어떤 원인을 처리할지 얻는 일이고 complete는 제어기에 처리 완료를 알리는 일이다. 장치 자체의 상태 확인이나 데이터 처리는 별도 책임이다.

자체 종이 장치는 완료 큐 Q와 알림 상태 I를 갖는다. 장치가 Q에 완료 항목을 넣고 I를 요청한다. 처리기는 Q를 조사하여 실제 완료·오류를 구별한다. 모형에서 I=1은 Q를 조사할 이유이지 모든 요청의 성공 증명은 아니다. 실제 제어기의 claim·pending·in-service 규칙을 이 한 비트 모형과 동일하다고 주장하지 않는다.

2. 한 알림이 여러 항목을 가리킬 수 있다

장치는 여러 완료를 모아 알림 하나로 전달할 수 있고, 처리기는 한 번 들어와 여러 큐 항목을 처리할 수 있다. 반대로 공유 인터럽트나 이미 처리된 상태 때문에 조사 시 새 작업이 없을 수도 있다. 따라서 인터럽트 횟수만 세어 완료 요청 수나 사용자 바이트 수를 추정하면 조건이 빠진다.

종이 모형은 큐에서 모든 항목을 가져오고 상태를 갱신한 뒤 알림을 정리하며, 그 사이 새 완료가 추가되지 않는다고 가정한다. 새 완료가 끼어들 수 있다면 큐 재확인·재활성화 절차가 필요하다. 큐를 확인한 직후 새 항목이 추가되고 그 알림을 무심코 지우는 순서는 작업을 놓치는 반례다.

3. 깨우기와 사용자 실행, 성능을 나누어 본다

완료 항목을 확인하여 기다리던 프로세스를 준비 상태로 옮겨도 실제 실행은 스케줄러의 선택을 기다린다. 아래 시간표는 처리·스케줄 지연을 따로 둔다. 성공한 장치 요청과 앱의 결과 해석 완료 시점도 같지 않다. 실시간 마감 보장을 주장하려면 최악 지연과 모든 관련 가정이 더 필요하다.

폴링은 소프트웨어가 상태를 반복 확인하고 인터럽트는 알림을 받아 처리한다. DMA는 데이터 이동 방식으로 두 알림 방식과 별개의 축이다. 많은 일을 한 번에 처리하면 진입 비용을 줄일 수 있지만 너무 오래 처리하면 다른 작업 지연을 늘릴 수 있다. 이 교환 관계를 실제 장치 속도 측정으로 오해하지 않는다.

중간 과정을 따라가는 예제

가상 단일 CPU. A,B는 각 자기 요청을 기다리는 대기 상태, C는 실행 중이다. t=10ms에 장치가 성공 완료 [A,B]를 큐 Q에 넣고 알림 한 번을 보낸다. 처리기는 10~12ms 동안 두 항목을 모두 처리하며 그 사이 새 완료는 없다. 12ms에는 C를 계속 실행하고 15ms에 A를 배정한다.

  1. 10ms 직전 Q는 비어 있고 A,B는 대기, C는 실행이다. 완료 둘이 Q에 들어가지만 알림은 하나다.

  2. 10~12ms 처리기는 원인을 확인하고 두 성공 항목을 소비한다. 이 구간 CPU는 커널 처리 중이며 C의 사용자 실행은 중단된다.

  3. 12ms에 A,B를 준비로 옮기고 Q를 비운 뒤 알림 처리 완료를 통보한다. 정책에 따라 C의 사용자 실행을 재개한다.

  4. 15ms에 A를 실행한다. A의 장치 완료부터 실행까지는 15−10=5ms, 완료 확인 뒤 준비부터 실행까지는 15−12=3ms이다. B는 아직 준비다.

완료 두 건·알림 한 번·A 실행 한 번은 서로 다른 수다. 처리 지연 2ms와 준비 후 대기 3ms를 합쳐 A의 완료-실행 지연은 5ms다.

종이와 본문으로 직접 해보기

완료 큐 [X,Y,Z]를 알림 하나로 처리한다. 진입 고정 비용 2단위, 각 항목 비용 1단위이며 전부 처리하는 동안 새 완료가 없다. 묶음 하나 비용과 각 항목을 별도 진입으로 처리하는 비용을 비교하라. 이 비용으로 실제 최악 응답 시간을 알 수 있는가?

힌트 보기

묶음은 고정 비용을 한 번, 분리는 세 번 낸다. 시간 단위를 밀리초로 바꾸지 말고 가상 비용 단위를 유지한다.

풀이 보기

묶음은 2+3·1=5단위, 세 번 진입은 3·(2+1)=9단위다. 4단위가 줄지만 실제 장치·락·다른 인터럽트·스케줄링 지연 조건이 없으므로 실제 최악 응답 시간을 알 수 없다.

오해와 반례

인터럽트 하나가 발생하면 요청 하나가 성공하고 기다린 앱 하나가 즉시 실행된다.

예제는 완료 둘을 알림 하나로 처리하고 A,B를 준비로 만들지만 C가 계속 실행한다. 오류 알림도 가능하다. 알림 수·성공 수·CPU 배정 수는 장치 및 처리 계약을 확인한 뒤 관계를 정해야 한다.
