소단원 3.1

상태 전이와 제어 블록

프로그램이 멈춰 보일 때, 실행 준비가 된 것과 데이터를 기다리는 것은 어떻게 다를까?

준비 개념과 학습 목표

준비 개념

  • 프로그램은 실행할 명령의 기록이고 프로세스는 주소 공간·자원·실행 상태를 갖는 실행 중인 인스턴스다. CPU 한 개는 특정 순간 하나의 명령 흐름을 실행한다고 모형화한다.

  • 스레드는 실행 흐름이다. 일반적인 다중 스레드 프로세스는 주소 공간을 공유하지만 각 스레드에 PC·레지스터·스택과 실행 상태가 필요하다. 스택이 별도여도 포인터로 서로 접근할 가능성까지 금지되는 것은 아니다.

  • 불변식은 허용된 모든 상태 전이에서 유지되는 성질이다. lock은 공유 상태의 검사와 갱신을 보호한다. 준비 상태와 실행 상태를 같은 단어로 부르면 불변식을 쓰기 어렵다.

학습 목표

  • RUNNABLE,RUNNING,SLEEPING을 구분한다.

  • 프로세스 제어 블록과 스레드별 실행 상태를 설명한다.

  • 한 CPU 모형의 실행 소유권 불변식을 추적한다.

제어 블록의 역할

커널은 각 실행 인스턴스의 상태를 잊지 않기 위해 프로세스 제어 블록 PCB를 유지한다. xv6의 struct proc에는 상태·PID·부모·대기 채널·종료 코드와 페이지 테이블·trapframe·kernel context·열린 파일 등의 정보가 있다. PCB는 사용자 프로그램의 일반 변수와 달리 커널이 관리하는 제어 정보다.

일반 OS의 다중 스레드 프로세스에서는 주소 공간과 자원 정보를 프로세스 수준에 두고 실행 문맥을 스레드 수준에 둘 수 있다. 현재 xv6 기본 모형의 프로세스별 실행 흐름을 설명하는 것과, 일반 OS의 여러 사용자 스레드 구현을 동일시하지 않는다. 공유 주소 공간은 공유 데이터의 경쟁 가능성도 만든다.

이름마다 다른 전이

현재 읽은 xv6 procstate는 UNUSED,USED,SLEEPING,RUNNABLE,RUNNING,ZOMBIE다. UNUSED는 사용하지 않는 슬롯, USED는 초기화 중 확보한 슬롯이다. RUNNABLE은 선택되면 실행할 수 있는 상태이고 RUNNING은 CPU에 배정된 상태다. SLEEPING은 사건을 기다리며, ZOMBIE는 종료 정보를 부모가 회수할 때까지 남긴 상태다.

교육용 한 CPU 안정 상태 모형에서는 dispatch:RUNNABLE→RUNNING, yield:RUNNING→RUNNABLE, block:RUNNING→SLEEPING, wake:SLEEPING→RUNNABLE을 쓴다. wake는 바로 실행을 뜻하지 않는다. 실제 커널에서는 이 변화와 CPU 소유권 전달의 중간 구간을 lock과 문맥교환 규칙으로 보호하므로 단순 표의 한 화살표가 곧 단일 기계 명령은 아니다.

상태만으로 충분하지 않은 이유

실행 불변식은 안정 상태에서 RUNNING인 프로세스가 최대 하나이며 그것이 CPU 소유자와 같다는 것이다. 두 scheduler가 보호 없이 같은 RUNNABLE 항목을 동시에 고르면 같은 실행 흐름을 둘이 실행할 위험이 있다. xv6는 프로세스 lock을 보유하며 상태 선택과 문맥 전달을 수행한다. 여러 CPU 시스템에서는 각 프로세스가 동시에 여러 CPU에서 실행되지 않는 조건과 CPU별 소유권을 함께 관리한다.

대기와 깨우기도 조건 검사와 대기 등록의 순서가 중요하다. 지금 읽은 riscv branch는 sleep_prepare로 채널을 등록하고, wakeup이 채널을 먼저 지우면 뒤 sleep이 실제로 잠들지 않도록 한다. 오래된 sleep(chan,lock) 예제와 함수 인터페이스를 섞지 않는다. 깨어난 뒤 공유 조건은 다시 검사해야 하며, 깨우기만으로 조건이 계속 참임을 보장하지 않는다.

중간 과정을 따라가는 예제

한 CPU, P와 Q는 처음 RUNNABLE이다. 사건 dispatch P, block P, dispatch Q, wake P, yield Q, dispatch P를 순서대로 추적한다. 전이는 보호된 하나의 사건으로 가정한다.

  1. dispatch P 뒤 P=RUNNING,Q=RUNNABLE,CPU=P다.

  2. block P 뒤 P=SLEEPING이고 CPU는 비어 있다. dispatch Q 뒤 Q=RUNNING,CPU=Q다.

  3. wake P 뒤 P=RUNNABLE이지만 Q가 계속 RUNNING이다. wake가 P에 CPU를 즉시 주지 않는다.

  4. yield Q 뒤 둘 다 RUNNABLE이고 CPU는 빈다. dispatch P 뒤 P=RUNNING,Q=RUNNABLE,CPU=P다.

모든 안정 상태에서 RUNNING은 최대 하나다. 기다림을 끝내는 것과 실제 실행을 시작하는 것은 다르다.

종이와 본문으로 직접 해보기

P가 RUNNING이고 Q가 RUNNABLE일 때 dispatch Q를 바로 허용하면 무슨 문제가 생기는가? P가 block한 뒤 dispatch Q와 wake P를 수행한 상태도 적어라.

힌트 보기

CPU 소유자와 RUNNING 항목 수를 함께 적는다.

풀이 보기

P가 CPU를 가진 채 Q까지 RUNNING으로 바꾸면 한 CPU 불변식을 깬다. P block 후 Q dispatch와 P wake를 하면 P=RUNNABLE,Q=RUNNING,CPU=Q이며 합법이다.

오해와 반례

RUNNABLE이면 이미 CPU에서 실행하고 있다.

실행할 준비만 된 상태다. 예제에서 P는 wake 뒤 RUNNABLE이지만 Q가 CPU를 사용한다. 준비 상태가 얼마나 기다릴지는 scheduler와 부하 및 공정성 가정에 의존한다.

소단원 3.2

문맥교환

다른 일을 했다가 돌아와도 함수가 이어지는 비밀은 어디에 저장되어 있을까?

준비 개념과 학습 목표

준비 개념

  • 문맥은 실행을 이어가는 데 필요한 상태다. 레지스터는 CPU 안의 작업 값이고 스택은 함수 호출의 지역 값과 반환 정보 등을 담는 메모리다.

  • 호출 규약에서 callee-saved 레지스터는 호출된 함수가 돌아올 때 보존할 책임이 있는 값이다. caller-saved 값은 호출자가 필요하면 보존한다. 모든 레지스터를 같은 방식으로 처리하지 않는다.

  • 사용자 trapframe은 trap에서 사용자 실행을 복원하기 위한 정보이고 kernel context는 커널 실행 흐름을 다시 이어가기 위한 저장 정보다. 둘은 목적과 저장 범위가 다르다.

학습 목표

  • trap 진입과 kernel swtch를 구별한다.

  • xv6 context의 저장·복원과 반환 위치를 추적한다.

  • lock 전달·메모리 수명·성능 경계를 설명한다.

서로 다른 저장 영역

사용자 코드에서 trap이 발생하면 사용자 레지스터와 복귀 PC를 별도 trapframe에 보존한다. 이어 커널에서 프로세스 실행 흐름을 scheduler로 바꾸는 swtch는 또 다른 kernel context를 사용한다. xv6 context는 ra,sp와 s0부터 s11을 저장하며 64비트 항목14개, 총112바이트다. 이는 전체 프로세스 메모리 크기도, 모든 trap 저장 공간의 크기도 아니다.

커널 문맥교환은 C 함수 호출 경계를 이용하므로 callee-saved 값과 스택·반환 위치를 보존한다. 필요한 caller-saved 값은 호출 규약에 따라 호출자가 처리한다. x0는 고정0이라 저장 대상이 아니다. 임의의 사용자 실행 시점에서 이14개만 저장하면 충분하다는 주장은 trapframe 역할을 누락한다.

어디로 돌아가는가

swtch(old,new)는 현재 ra,sp,s 레지스터를 old에 저장하고 new의 값을 CPU로 읽는다. 마지막 ret는 방금 복원한 new의 ra로 돌아간다. 따라서 다른 흐름이 예전에 swtch를 호출했던 지점의 다음 실행으로 이어진다. 처음 생성한 흐름은 커널이 초기 ra와 sp를 준비해야 한다.

각 흐름의 스택은 메모리에 남아 있으므로 문맥교환마다 전체 스택이나 heap을 복사할 필요는 없다. 하지만 새 sp가 가리키는 스택과 저장 context는 복원될 때까지 유효해야 한다. 종료 중인 흐름의 현재 스택을 너무 일찍 회수하면 scheduler로 넘어가는 코드 자체가 해제한 메모리를 사용할 수 있다.

scheduler 경계와 비용

xv6에서 P가 yield하면 상태를 RUNNABLE로 바꾸고 p->lock을 보유한 채 sched를 통해 P context→CPU scheduler context로 교환한다. scheduler가 Q를 고르면 scheduler context→Q context로 다시 교환한다. lock 전달은 상태 전환 중 다른 CPU가 같은 프로세스를 잘못 실행하지 못하게 하는 불변식의 일부다. 일반 사용자 mutex를 이런 방식으로 다른 흐름에 넘겨도 된다는 규칙은 아니다.

trap과 swtch,주소 공간 선택 및 복귀 과정은 서로 다른 단계다. 같은 프로세스의 일반 사용자 스레드 교환은 주소 공간을 유지할 수 있지만 다른 프로세스에서는 주소 공간 선택이 달라질 수 있다. 112바이트 저장이라는 계산만으로 문맥교환 전체 시간이나 캐시·TLB 영향을 알 수 없다. 아래 가상 주소와 반환값은 실제 kernel 측정값이 아니다.

중간 과정을 따라가는 예제

가상 kernel context에서 P의 현재 ra=0x120,sp=0x8000,s0=7이고 Q의 저장 값은 ra=0x340,sp=0x9000,s0=11이다. swtch(P,Q) 뒤 Q가 yield하여 swtch(Q,P)한다고 가정한다. 다른 s 레지스터도 정상 보존한다.

  1. 첫 swtch는 P 저장 영역에 0x120,0x8000,7과 나머지 s값을 쓴다.

  2. Q 저장 영역에서 ra=0x340,sp=0x9000,s0=11을 읽어 CPU 레지스터를 바꾼다. ret는 Q의 0x340으로 간다.

  3. Q가 진행하여 다시 교환할 때 자신의 현재 반환 위치와 스택을 Q 영역에 저장한다. 이 값은 처음의 0x340과 같을 필요가 없다.

  4. P 영역을 복원하면 ra=0x120,sp=0x8000,s0=7로 돌아간다. P 스택은 복사하지 않고 기존 메모리를 다시 사용한다.

ret의 목적지는 복원한 문맥의 ra다. P의 중간 값은 저장 context와 유지된 스택을 통해 이어진다.

종이와 본문으로 직접 해보기

ra,sp,s0…s11을 각각 8바이트로 저장할 때 전체 크기와 s0,s11 offset을 구하라. P 스택을 해제한 뒤 P context를 복원하면 왜 잘못되는지도 설명하라.

힌트 보기

ra가 offset 0,sp가8이다. s0 앞에는 두 항목이 있다.

풀이 보기

14×8=112바이트다. s0 offset=16,s11=16+11×8=104다. 저장 sp가 해제한 스택을 가리키면 다음 스택 접근이 유효한 P의 호출 상태를 보존하지 못하므로 복원 계약을 깬다.

오해와 반례

문맥교환은 프로세스 메모리를 전부 복사한다.

소단원 3.3

프로세스 생성·종료의 커널 구현

종료한 프로그램의 정보를 왜 즉시 지우지 않고 부모가 회수하게 할까?

준비 개념과 학습 목표

준비 개념

  • fork는 새 프로세스를 만드는 인터페이스이고 부모와 자식은 반환값으로 흐름을 구분한다. exec는 기존 프로세스의 프로그램 이미지를 교체하는 동작이며 새 프로세스 생성과 다르다.

  • 참조 계수는 공유 자원을 참조하는 수를 기록한다. 프로세스가 하나 종료되어도 다른 참조가 남으면 공유 파일 객체를 바로 파괴할 수 없다.

  • 종료 코드는 부모에게 전달하는 결과 정보다. wait는 종료한 자식 정보를 회수할 수 있다. 할당 실패와 사용자 메모리로 결과 복사 실패도 함수 계약의 일부다.

학습 목표

  • 생성의 초기화·공개·실패 정리를 설명한다.

  • fork 메모리와 공유 파일 참조를 구분한다.

  • exit와wait 사이의 ZOMBIE 수명 및 회수 조건을 추적한다.

실행 가능하게 공개하기 전

방문 당시 xv6의 kfork는 allocproc으로 슬롯과 trapframe·페이지 테이블·첫 kernel context를 준비한 뒤 uvmcopy로 현재 할당되어 있는 사용자 페이지를 별도 메모리에 복사한다. 아직 물리 페이지가 없는 지연 할당 구간은 이 방문 구현에서 건너뛴다. 부모 trapframe을 복사하고 자식 a0를 0으로 만들어 fork 반환을 구분한다. 부모는 새PID를 반환받는다. 이 구현의 메모리 복사는 현대 OS의 copy-on-write 구현과 같은 방식이라고 주장하지 않는다.

파일 descriptor 표 항목은 파일 객체 참조를 복제하며 사용자 메모리처럼 파일 객체 전체를 복사하지 않는다. 부모 연결과 초기화를 완료한 뒤 자식 상태를 RUNNABLE로 공개한다. 초기 할당이나 사용자 메모리 복사가 실패하면 확보한 자원을 정리하고 실패를 반환해야 한다. 초기화 중인 USED를 정상 실행 후보로 고르면 안 된다.

종료와 회수의 분리

kexit는 열린 파일 참조와 현재 디렉터리 참조를 정리하고 자식의 부모를 init으로 옮긴다. 종료 코드 xstate를 남기고 ZOMBIE로 바꾼 뒤 scheduler로 넘어가 돌아오지 않는다. 부모는 kwait에서 자식 상태를 검사해 종료 코드를 복사하고 freeproc으로 남은 trapframe·사용자 메모리·페이지 테이블 등을 회수한다.

ZOMBIE는 CPU를 계속 쓰는 살아 있는 사용자 흐름이 아니다. 반면 종료 정보를 회수하지 않았으므로 슬롯은 아직 UNUSED도 아니다. 현재 실행 스택이 안전하게 더는 쓰이지 않는다는 경계와 부모의 결과 관찰을 함께 보호해야 한다. 방문 코드에서는 프로세스 kernel stack 매핑을 부팅 때 마련하므로 exit마다 모든 kernel stack을 새로 free한다고 설명하지 않는다.

부모가 기다리는 조건

부모의 wait는 자식이 있으나 아직 종료하지 않았다면 기다렸다 깨어나 다시 검사한다. wait_lock과 자식 lock의 순서를 지키며 종료·부모 연결·대기 등록을 조정한다. 방문한 코드의sleep_prepare와sleep 분리는 대기 등록 후 깨우기가 먼저 와도 영구히 잠들지 않게 하는 구현이다. 부모가 child를 회수하는 시점에 child의 exit/swtch가 아직 스택을 쓰지 않도록 자식 lock도 필요하다.

종료 코드를 사용자 주소에 copyout할 때 실패하면 kwait는−1을 반환하며 그 ZOMBIE를 회수하지 않는다. 자식이 없거나 부모가 killed 상태일 때도 실패 경로가 있다. 따라서 wait를 호출했다는 사실만으로 자식 회수 성공을 기록하면 안 된다. 커널의 내부 성공 조건과 사용자의 관측 반환값을 같이 확인한다. 주소 0은 종료 코드를 받지 않겠다는 선택이어서 copyout을 생략하고 정상 회수할 수 있다. 따라서 위 복사 실패는 실제 copyout을 시도하는 비영 주소에서의 실패다.

중간 과정을 따라가는 예제

종이 xv6 수명 모형에서 부모 PID 10이 자식 PID 11을 만든다. 부모의 사용자 변수 v=5를 복사하고 공유 파일 객체 F의 참조는 처음1개다. 생성 성공 뒤 자식이 v=9로 바꾸고 종료코드 3으로 exit하며 부모가 유효한 주소로 wait에 성공한다.

  1. 생성 직후 자식 사용자 메모리 v=5이고 부모 v=5다. F 참조를 복제하면 이 두 프로세스의 참조는 2개다. 다른 참조는 없다고 가정한다.

  2. 자식 v←9는 복사한 사용자 메모리에 쓰므로 부모 v=5는 유지된다. 자식 fork 반환은 0,부모는 11이다.

  3. 자식 exit가 F 참조 하나를 닫으면 남은 참조는 1개다. 자식은 xstate=3,ZOMBIE로 남고 실행을 재개하지 않는다.

  4. 부모 wait가 종료코드 3을 유효한 사용자 주소에 복사하고 자식의 남은 자원을 회수하면 자식 슬롯은 UNUSED가 된다. 부모의 F 참조는 남는다.

부모는PID 11과 종료코드 3을 회수한다. 독립 사용자 메모리와 공유 파일 참조의 수명은 다르다.

오해와 반례

fork는 모든 자원을 완전히 독립 복사하고 exit는 모든 것을 즉시 없앤다.

방문 xv6는 사용자 메모리를 복사하지만 열린 파일 객체는 참조를 공유한다. exit 뒤에도 결과 회수를 위한 ZOMBIE와 일부 자원이 남는다. 한 프로세스 종료만으로 부모가 쓰는 파일 객체가 사라지지 않는다.
