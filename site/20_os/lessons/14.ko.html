사용자·권한·격리

같은 파일 이름을 아는 두 사람이 모두 그 파일을 바꿀 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 파일과 디렉터리

  • 프로세스

  • 읽기와 쓰기

학습 목표

  • 프로세스 ID와 접근 자격을 구별한다.

  • 일반 파일의 권한 클래스를 선택한다.

  • 권한 검사와 격리된 보기를 구별한다.

내용을 못 고치는 읽기 전용 파일도 이름은 지울 수 있을까?

자체 Unix 기본 권한 모형에서 디렉터리 D의 owner는 900, group은 200, mode는 730이다. 주체 S의 fsuid는 1001이며 보조 그룹 200에 속한다. S가 선택하는 D의 group 비트 3은 w+x다. 이름 항목 변경과 알려진 이름 검색을 허용하지만 목록 읽기 r은 없다. 파일 F의 mode가 444여서 내용 쓰기를 허용하지 않아도, D에서 알려진 F 이름을 제거하는 unlink 권한은 따로 판정한다.

디렉터리 r은 목록 읽기, x는 알려진 항목을 검색하며 경로를 통과하기, w는 필요한 검색 권한과 함께 이름 항목을 변경하는 의미다. 이름을 열거할 수 없음과 이미 아는 이름에 접근할 수 없음은 같지 않다. 파일 내용을 쓰는 권한과 부모 디렉터리의 이름을 제거하는 권한도 다른 객체에 적용된다.

이번 모형은 경로 앞부분의 검색 권한이 이미 있고 일반 파일·기본 mode만 사용한다. ACL·sticky bit·특권·immutable·읽기 전용 마운트·추가 정책은 제외한다. 따라서 이름 제거 가능이라는 종이 판정을 실제 삭제 성공이나 보안 소거 증거로 바꾸지 않는다. 학생이나 서비스에 읽기만 맡길 목적이라면 파일 비트뿐 아니라 디렉터리와 실행 자격의 작업 범위도 점검한다.

먼저 확인할 개념
  • 격리 보기와 허용 작업

    자원 보기를 나누는 기능만으로 이름 변경 권한을 제한하지 않는다.

  • 공유 자원 작업의 조건

    작업의 실행 위치뿐 아니라 주체·객체·허용 작업을 명시한다.

누가 어떤 작업을 하는지 판단한다

보호는 주체가 객체에 할 수 있는 작업을 정하고 집행하는 문제다. 객체는 파일·메모리·장치 등이고 작업은 읽기·쓰기·실행 등이다. 파일 이름을 아는 것, 파일이 보이는 것, 쓰기가 허용되는 것은 다른 사실이다. 운영체제는 작업 요청에 붙은 자격과 정책을 확인한다.

PID는 실행 중인 프로세스를 식별하는 번호다. 파일 권한을 정하는 사용자·그룹 ID와 같지 않다. Linux에서는 파일 접근에 파일시스템 사용자/그룹 ID와 보조 그룹 등이 관여한다. 보통 fsuid/fsgid가 유효 ID와 같지만 이 사실을 PID와 혼동하지 않는다.

권한은 클래스부터 선택한다

일반 파일의 기본 mode는 owner/group/other 세 클래스에 읽기 r·쓰기 w·실행 x를 둔다. 8진 숫자에서 r=4, w=2, x=1을 합한다. 640은 owner rw-, group r--, other ---다. 먼저 소유자인지, 아니라면 관련 그룹인지, 그 외인지 판정하고 그 클래스의 비트를 확인한다. 허용 비트를 모든 클래스에서 합쳐 고르는 규칙이 아니다.

아래는 일반 파일·기본 mode만 있는 모형이다. ACL·capability·특수 비트·추가 보안 정책·읽기 전용 파일시스템 등은 제외한다. 경로의 디렉터리 검색 권한이 이미 있고 파일이 존재한다고 가정한다. 실제 성공을 예측하려면 이 조건들도 별도로 확인해야 한다.

보이는 범위와 허용 작업은 다르다

namespace는 특정 자원에 대한 프로세스의 보기를 나눌 수 있다. mount namespace가 다르면 같은 경로 문자열이 서로 다른 파일 트리를 가리킬 수 있고 PID namespace가 다르면 보이는 프로세스 번호가 달라질 수 있다. 보기의 분리만으로 파일 쓰기 권한이나 자원 사용량 상한이 자동 설정되지는 않는다.

최소 권한은 필요한 작업만 허용하는 설계다. 읽기 학습 자료를 표시하는 과정이 관리용 쓰기 자격까지 가질 필요가 있는지 따져 본다. 실패를 무시하거나 관리자 권한을 무조건 부여하는 대신 실제 작업·주체·객체·정책을 기록한다.

중간 과정을 따라가는 예제

일반 파일 F의 owner는 1000, group은 200, mode는 640이다. A의 fsuid=1000, B의 fsuid=1001이며 보조 그룹에 200이 있다. C의 fsuid=1002이고 group 200에 속하지 않는다. 위 기본 권한 모형에서 각자의 읽기/쓰기를 판정하라.

  1. A는 owner 클래스의 6=4+2를 선택하므로 읽기와 쓰기가 허용된다.

  2. B는 owner가 아니지만 group 200에 속하므로 group 클래스의 4를 선택한다. 읽기는 허용되고 쓰기는 거절된다.

  3. C는 other 클래스의 0을 선택한다. 읽기와 쓰기가 모두 거절된다. PID 값은 이 판정 표에 필요하지 않다.

이 모형에서 A는 읽기/쓰기, B는 읽기만, C는 둘 다 불가다. 실제 syscall 성공은 경로·파일시스템·추가 정책과 특권도 조사해야 한다.

조건을 바꾸어 비교하기

읽기 전용 내용과 지울 수 있는 이름

S가 F 내용을 못 쓰는데도 이름을 지울 수 있는 이유는?

  1. 내용 쓰기는 F의 w 비트를 검사한다.

  2. unlink는 부모 D의 이름 연결을 변경한다.

  3. D의 group3은 w+x이며 이번 제외 조건 아래 변경을 허용한다.

서로 다른 객체와 작업의 권한을 판정했기 때문이다.

비교할 점

파일 읽기 전용 설정만으로 이름 삭제도 막는다고 가정하지 않는다.

목록 없이 알려진 이름 찾기

D의 group3에서 목록은 못 읽는데 알려진 D/F를 읽을 수 있는가?

  1. D의 r이 없어 이름 열거는 허용되지 않는다.

  2. D의 x가 있어 알려진 항목을 검색할 수 있다.

  3. F의 해당 r이 있고 다른 경로 조건도 만족한다고 정했다.

이 모형에서는 알려진 F를 읽을 수 있다. 내용이나 이름의 실제 존재는 별도다.

비교할 점

목록 읽기와 경로 검색을 같은 비트로 생각하지 않는다.

힌트 보기

owner가 일치하면 owner 클래스를 먼저 선택한다. group 비트와 합치지 않는다.

풀이 보기

A는 owner의 0을 사용하므로 읽기 불가다. B는 group의 4로 읽기 가능하다. A가 그룹에도 속한다는 이유로 group 권한을 대신 가져오지 않는다. 이는 특권/ACL 없는 지정 모형의 판정이다.

오해와 반례

파일 이름을 알고 있거나 root라는 표시가 보이면 모든 격리와 권한이 사라진다.

이름·보기·자격·작업의 정책은 각각 다르다. 실제 user namespace의 ID 매핑과 capability 범위도 조사해야 한다. 표시 문자열이나 PID만으로 모든 자원 접근을 확정하지 않는다.

연습 1 · 값과 상태 예측

D의 mode만 740으로 바꾸면 S의 목록 읽기·검색·unlink는 각각 가능한가?

힌트 1

group4는 r만 있다.

힌트 2

x 없는 경로 검색과 w 없는 이름 변경을 따로 판정한다.

풀이와 답 확인

  1. 목록 읽기 r은 있다.

  2. 알려진 하위 항목 검색 x는 없다.

  3. unlink에 필요한 w+x도 없다.

기본 비트 판정은 목록 가능·검색 불가·unlink 불가다. 목록의 세부 stat 정보까지 모두 얻는 보장은 아니다.

흔한 오답에서 다시 생각하기

r만 있으면 목록의 모든 이름을 열고 지울 수 있다.

검색·이름 변경에는 별도의 x·w 조건이 필요하다.

연습 2 · 오류 찾아 고치기

F에 w가 없으니 부모 권한과 무관하게 unlink도 무조건 거절이라고 썼다. 고쳐라.

힌트 1

힌트 2

풀이와 답 확인

  2. D의 w+x는 알려진 이름 제거의 기본 조건이다.

  3. sticky·immutable·마운트·추가 정책 등을 실제 환경에서 더 확인한다.

연습 3 · 직접 만들어 보기

학습 자료 읽기는 허용하지만 이름 변경을 막는 group 비트를 제안하라. 알려진 항목 검색과 목록도 필요하다.

힌트 1

힌트 2

디렉터리 w를 주지 않는다.

풀이와 답 확인

  1. D의 group을5=r+x로 둔다.

  2. F의 해당 class는4=r로 둔다.

  3. 다른 쓰기 자격·ACL·특권 경로가 없다는 조건을 확인한다.

기본 모형에서 목록·검색·파일 읽기를 허용하며 이름 변경 w는 부여하지 않는다.

파일만444로 두고 D의 group3을 유지하면 이름도 보호된다.

group3에는 이름 변경 w가 남아 읽기 전용 목적과 다를 수 있다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

S의 fsuid가 D owner인 900으로 바뀌고 mode 730은 그대로면 D에서 선택하는 비트와 세 작업은?

힌트 1

owner가 일치하면 owner7을 선택한다.

힌트 2

보조 그룹 여부로 owner 비트를 다른 class와 합치지 않는다.

풀이와 답 확인

  1. owner7은 r+w+x다.

  2. 목록·검색·기본 이름 변경을 모두 허용한다.

  3. 여전히 실제 예외 조건은 별도 확인한다.

자격 변경으로 선택 class가 바뀐다. mode 숫자를 바꾸지 않아도 판정이 달라질 수 있다.

한 단계 더

주체 A/B/C, 객체 학습 자료/평가 답안, 작업 읽기/쓰기의 허용 표를 직접 설계하라. 이름이 보이지 않는 상태와 보이지만 읽기가 거절되는 상태를 각각 설명하고 실제 환경의 검사는 미수행으로 표시하라.

출처와 확인 범위
  • Linux credentials(7)

    실제 0–218행의 process/user/group 식별자와 90–150행의 실제·유효·파일시스템 ID 및 보조 그룹 설명을 읽었다. PID를 파일 접근 자격으로 대체하지 않는다.

  • Linux inode(7)

자식 두 집단에 상한40씩 주면 부모50 안에서도 합80을 쓸 수 있을까?

자체 계층 예산 모형에서 부모 P의 100 ms 기간 CPU 총량은 50 core-ms이고 자식 A·B의 상한은 각각 40 core-ms다. 기간 경계를 맞추고 burst·잔여 slice·관리 비용을 제외하며 부모 사용량은 두 자식의 합이라고 정한다. 각 자식의 사용량이 40 이하라는 조건과 합이 50 이하라는 조건을 동시에 만족해야 한다. A가 30, B가 20을 쓰는 배정은 가능하지만 A와 B가 각각 40을 쓰면 부모 상한을 넘는다. 상한의 합은 실제 제공량 예약이 아니다.

부모에서 A가 40 core-ms를 썼다면 이번 기간에 B가 더 사용할 수 있는 자체 예산은 min(40,50−40)=10 core-ms다. 두 자식이 동시에 한 코어씩 전속 실행하는 가상 시간선에서는 25 ms 뒤 각각 25 core-ms를 써서 합 50 core-ms를 소진한다. 그 시점에 각 자식의 예산이 15 core-ms씩 남아도 부모 예산은 끝났다. 실제 CFS의 slice·burst·기간 경계·스케줄 선택을 그대로 재현한 표가 아니며 문서의 계층 제한 원리를 분리해 계산한다.

메모리도 계층을 함께 본다. 자체 회수 없는 admission 모형에서 부모 상한은 240 MiB, 각 자식의 상한은 200 MiB다. 현재 사용량은 A가 180 MiB, B가 40 MiB여서 합은 220 MiB다. B에 30 MiB를 더하면 B의 70 MiB는 자체 상한 이하지만 부모 사용량은 250 MiB로 초과한다. 이 모형은 추가 허가를 거절한다. 실제 memory.max는 회수·OOM·일시 초과 등의 계약이 있어 모든 allocation이 같은 방식으로 즉시 실패한다고 단정하지 않는다. memory.high의 회수 압박과 hard limit도 구별한다.

namespace는 보기를 분리하고 상한은 사용량을 제어하는 다른 조건이다. 컨테이너를 만들었다는 사실만으로 부모 예산·메모리·CPU 예약이 설정되지는 않는다. 계층별 유효 자격과 controller 설정, 현재 사용량·회수 가능량·오류를 확인해야 한다. 실제 VM·컨테이너·cgroup를 설정하지 않았으므로 이 수치를 운영 환경의 측정값으로 보고하지 않는다.

가상 머신은 guest 시스템을 실행한다

하이퍼바이저는 물리 자원을 가상 머신에 제공하고 실행을 관리한다. 각 VM은 guest 운영체제와 그 안의 프로그램을 실행할 수 있다. type 1은 하드웨어 위에서 직접 동작하는 형태, type 2는 host 운영체제 위에서 동작하는 형태로 설명한다. 실제 구현의 가속·드라이버·관리 구성은 제품별로 확인해야 한다.

가상 CPU 개수는 항상 같은 수의 독점 물리 코어를 뜻하지 않는다. 하이퍼바이저가 여러 VM의 실행 시간을 공유할 수 있다. 격리 경계가 생겨도 host·공유 하드웨어·설정·관리 경로에 대한 장애와 보안 문제가 모두 없어지는 것은 아니다.

컨테이너도 격리 조건을 설계한다

Linux의 전형적인 프로세스 기반 컨테이너는 host 커널을 공유하면서 namespace 등으로 프로세스·네트워크·파일 트리의 보기를 나눈다. 실행 파일과 라이브러리 같은 사용자 공간을 묶는 것과 독립 guest 커널을 실행하는 것은 다르다. 컨테이너를 VM 안에서 실행하는 조합도 가능하다.

namespace는 보기와 식별 공간을 나누고 cgroup은 프로세스 집단의 자원 분배·사용량을 관리한다. cgroup v2에는 CPU·메모리 등의 controller가 있다. 상한, 가중치, 예약은 같은 말이 아니며 같은 숫자를 설정한다고 항상 그 자원이 즉시 제공되지는 않는다.

용량 표의 중복과 누락을 확인한다

아래 메모리 숫자는 실제 제품의 기본 비용이 아닌 자체 예산이다. host 기본 사용량은 한 번 세고, VM마다 정한 guest 비용과 앱 비용을 더한다. 컨테이너마다 정한 앱 비용만 더하는 단순 표는 별도 관리 비용을 제외하므로 현실의 모든 비용을 담지 않는다.

CPU 사용량 상한을 정해도 지연 마감이 보장되지는 않는다. 메모리 제한에는 회수·제한 초과 처리 등 controller의 실제 규약이 있으며 모든 할당이 즉시 같은 방식으로 거절되는 것은 아니다. 도구를 설정하지 않았다면 표 계산과 실제 운영 결과를 분리한다.

중간 과정을 따라가는 예제

자체 예산에서 물리 메모리는 1024 MiB이고 host 기본 사용량은 256 MiB다. 두 VM은 각각 guest 256 MiB와 앱 128 MiB를 쓴다고 정한다. 두 컨테이너는 각각 앱 128 MiB만 추가한다고 정하며 이 비교에서 기타 비용은 0이다. 총량과 남은 예산을 비교하라.

  1. VM 두 개의 추가량은 2×(256+128)=768 MiB다. host를 한 번 더하면 총 1024 MiB로 남는 예산은 0이다.

  2. 컨테이너 두 개의 추가량은 2×128=256 MiB다. host와 합하면 512 MiB로 남는 예산은 512 MiB다.

  3. 실제 guest·공유 페이지·관리 비용과 working set은 이 표의 값과 다를 수 있다. 표의 차이를 실제 메모리 절감률이나 보안 등급으로 보고하지 않는다.

지정한 가상 예산에서 VM 방식은 1024 MiB, 컨테이너 방식은 512 MiB다. 실제 제품과 운영 조건의 측정은 별도다.

두 코어 시간 합이 같으면 데이터 의존성도 같은 종료 시간을 줄까?

자체 작업 그래프에서 비용 6 ms인 A가 끝난 뒤 비용 2 ms인 B를 실행해야 한다. 비용이 각각 4 ms인 C와 D는 독립이다. 동일 속도 코어 둘, 이동·관리 비용 0, 작업 분할 없음, 시작 시각 0을 가정한다. 전체 CPU량 16 core-ms의 두 코어 하한은 8 ms이고 A→B 의존 경로도 8 ms다. C0에 A를 0–6 ms와 B를 6–8 ms에 배정하고 C1에 C를 0–4 ms와 D를 4–8 ms에 배정하면 두 하한을 달성한다.

같은 CPU량에 A→C 의존성을 더하면 A→C 경로는 10 ms가 된다. C0에서 A를 0–6 ms와 B를 6–8 ms에 실행하고 C1에서 D를 0–4 ms에 실행한 뒤 4–6 ms에 대기하고 C를 6–10 ms에 실행하면 10 ms에 끝난다. 단순히 16/2=8만 보고 의존 결과가 준비되지 않은 C를 먼저 실행하면 안 된다. 하한에는 총량뿐 아니라 가장 긴 의존 경로가 포함된다.

원래 그래프에서 A·B·C를 C0에만 허용하면 C0의 작업 합은 12 ms다. C0에서 A를 0–6 ms, B를 6–8 ms, C를 8–12 ms에 실행하고 C1에서 D를 0–4 ms에 실행하면 12 ms에 끝난다. 코어가 남아도 허용 CPU 제약 때문에 C를 C1으로 옮길 수 없다. 의존성·허용 CPU·대기·관리 비용의 어떤 조건이 종료를 늘렸는지 나누어 보고한다.

다른 자체 단계 모형으로 전속 직렬 단계 8 ms 뒤 완전히 나눌 수 있는 병렬 CPU량 8 core-ms를 생각하면 두 코어 종료는 8+8/2=12 ms다. 이것은 앞 그래프의 배정과 다른 모형이며 잠금 경합을 실제 측정한 값은 아니다. Linux scheduler domain의 균형 조정은 실제 구현 조건을 읽어야 하고 작은 이상적 시간선을 실행 결과로 바꾸어 보고하지 않는다.

실행할 곳과 순서를 정한다

멀티코어 운영체제는 실행 가능한 작업을 여러 CPU에서 실행하고 균형을 조정한다. CPU별 실행 큐가 있다면 한쪽이 바쁘고 다른 쪽이 비는 상황에서 이동을 고려할 수 있다. Linux scheduler domain은 CPU 범위와 그룹 계층을 사용해 부하 균형을 다룬다. 아래 작은 표는 그 구현 전체를 흉내 내는 것이 아니다.

작업 affinity는 실행할 수 있는 CPU 범위를 제한할 수 있다. 공유 캐시·NUMA 메모리 위치·실행 주체의 제약도 배정에 영향을 준다. 논리 CPU 두 개가 물리 코어 두 개와 동일한 독립 계산 능력을 제공한다고 가정하지 않는다. SMT 스레드는 코어 자원을 공유할 수 있다.

균형과 이동 비용을 함께 센다

작업이 완전히 독립이고 두 코어가 같은 속도이며 전환 비용이 0일 때 종료 시간은 각 코어에 배정한 비용 합 중 큰 값이다. 균등 개수와 균등 비용은 다르다. 계산량이 큰 작업 하나를 쪼갤 수 없는 경우 그 작업의 비용은 전체 종료의 하한이 된다.

이동하면 캐시가 차갑거나 원격 메모리 접근이 늘 수 있다. 이동 전에 두 큐의 합만 비교하면 관리·지역성 비용을 놓칠 수 있다. 현재 시점의 실행 중/대기 중을 구별해야 하며 이미 사용한 시간을 다시 처음부터 더하지 않는다.

공유 상태의 정확성이 먼저다

여러 CPU에서 실행하면 공유 데이터의 갱신이 겹칠 수 있다. 잠금·원자 연산·메모리 순서 계약은 작업의 정확성을 지키기 위한 조건이다. 잠금 대기와 직렬 구간은 코어를 추가해도 남을 수 있다. 스케줄이 빨라 보여도 누락된 갱신을 올바른 결과로 취급하지 않는다.

실제 성능 비교에서는 완료된 같은 작업량·대기·이동·캐시 상태·반복 환경을 기록한다. 이 단원에서는 상태 표와 비용 산술만 다루며 실제 Linux 스케줄러나 CPU를 실행해 관찰한 결과는 없다.

  2. J2를 옮기면 C0는 6 ms, C1은 2+2+2=6 ms가 되어 비용 0인 이동에서는 종료 6 ms다.

group 200 주체가 mode 730인 D 안에서 mode 444인 F를 읽는다. 보고서는 파일 내용 쓰기가 불가하니 이름 삭제도 무조건 불가라고 했다. 같은 기간의 CPU 부모 상한은 50 core-ms, 두 자식 상한은 각각 40 core-ms인데 합 80 core-ms 사용을 허용했다. 비용 6 ms인 A에서 비용 4 ms인 C로 의존성을 추가했는데도 총 CPU량 16 core-ms를 코어 2개로 나눈 값 8 ms만으로 종료를 확정했다. 각각 지정 모형의 오류를 고쳐라.

풀이와 답 확인

  1. D의 group3은 w+x라 알려진 이름의 기본 unlink를 허용한다. F444의 내용 w 없음과 다르다. 실제 예외는 별도다.

  2. 각 자식 상한 40 core-ms와 부모 합 상한 50 core-ms를 동시에 만족해야 한다. 따라서 두 자식이 각각 40을 쓰는 합 80 core-ms는 불가다.

  3. A→C 경로의 6+4=10 ms가 총량 하한 8 ms보다 크다.

  4. C0에 A를 0–6 ms와 B를 6–8 ms에 배정하고 C1에 D를 0–4 ms와 C를 6–10 ms에 배정하여 10 ms 종료를 실현한다.

  5. 모든 결과는 명시된 종이 모형이며 실제 권한·cgroup·스케줄러·학습자 시험은 미수행이다.
