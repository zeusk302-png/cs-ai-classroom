소단원 5.1

임계구역과 원자 연산

두 사람이 동시에 남은 좌석 1개를 읽으면 둘 다 예약해도 되는 걸까?

준비 개념과 학습 목표

준비 개념

  • 공유 변수는 여러 스레드가 함께 접근하는 값이다. 임계구역은 함께 지켜야 할 상태를 읽고 바꾸는 구간이다.

  • 우선 이해를 위해 읽기·더하기·쓰기를 작은 단계로 나눈 순차 일관 종이 모형을 사용한다. 이것은 실제 언어의 모든 실행을 재현하는 장비 실험이 아니다.

  • 인터리빙은 스레드들의 작은 단계가 섞이는 순서다. mutex는 상호배제를 제공하는 락, data race는 아래에서 정의하는 언어의 데이터 경쟁, happens-before는 언어가 정한 선행 관계, undefined behavior는 언어가 동작을 보장하지 않는 상태다.

학습 목표

  • 인터리빙에서 잃어버린 갱신을 설명한다.

  • 원자 연산 하나와 여러 값의 불변조건을 구분한다.

한 자리만 남은 예약표를 두 사람이 동시에 보면 어떻게 될까?

재고 숫자를 한 번 읽는 행동과 예약을 끝내는 행동은 다르다. 읽은 재고가 1이어도 다른 사람이 그사이 예약할 수 있다. 두 사람의 행동을 작은 카드로 나누고 카드 사이에 상대 행동을 끼워 넣어 보자.

임계구역은 함께 지켜야 하는 상태를 바꾸는 구간이다. 이 구간을 한 사람이 끝낸 뒤 다음 사람이 시작하도록 같은 잠금으로 보호하면 불변식을 유지할 수 있다. 여기의 카드 표는 순차적으로 카드가 진행되는 종이 모형이며 C++의 보호 없는 일반 변수 실행 결과를 예언하는 표가 아니다.

먼저 확인할 개념
  • 변수와 상태

    이름, 읽은 값, 공유 값의 변화를 따로 기록한다.

  • 상태 전이와 제어 블록

    실행 중, 실행 가능, 잠든 상태를 구별하고 공유 주소 공간을 떠올린다.

한 줄과 한 원자 동작은 다르다

공유 x에 x=x+1을 적었다고 전체가 자동으로 한 동작은 아니다. 종이 모형에서는 x 읽기→개인 임시값에 1 더하기→x 쓰기의 세 단계다. A와 B가 둘 다 0을 읽으면 각자 1을 쓰므로 두 증가 뒤에도 1이 될 수 있다. 순서를 더 촘촘히 나누어 볼 때 드러나는 논리 오류를 잃어버린 갱신이라고 한다.

경쟁 상태는 실행 시점에 따라 결과가 달라지는 넓은 논리 문제다. C++ data race는 적어도 하나가 비원자인 충돌 접근에 happens-before가 없는 특정 언어 규칙 위반이다. C++에서 이런 x의 무동기 공유 접근은 undefined behavior이므로 실제 실행 결과가 반드시 1이나 2 중 하나라고 말할 수 없다. 본문의 1/2는 제한된 종이 모형 결과다.

모두 같은 약속을 사용한다

적절한 mutex로 x의 전체 읽기·갱신 구간을 감싸면 다른 스레드가 그 mutex를 획득하기 전까지 기다린다. 모든 충돌 접근이 같은 보호 규칙을 사용해야 한다. 한쪽만 lock을 잡고 다른 쪽이 그대로 읽거나 쓴다면 보호가 완성되지 않는다. 중간 오류·예외로 unlock을 빠뜨리는 것도 문제라 실제 코드에서는 수명 기반 관리 등을 배운다.

원자 fetch_add는 하나의 공유 객체에 대한 읽고 바꾸기를 나뉘지 않는 작업으로 제공한다. 각각 이전 값을 받아 같은 증가를 잃지 않는다. 그러나 잔액·예약 목록 같은 여러 객체를 함께 바꾸는 규칙은 원자 변수 하나만으로 해결되지 않는다. 원자 load와 원자 store를 따로 사용하여 load+1을 store하는 것도 전체 fetch_add와 다르다.

자물쇠를 직접 만드는 사고실험

flag가 0이면 1로 바꾸고 들어가는 단순 검사 후 대입은 두 스레드가 동시에 0을 읽을 수 있다. test-and-set은 이전 flag를 반환하면서 1로 바꾸는 동작을 하나로 묶는 원자 primitive다. 동시 호출에서 이전 0을 받은 하나만 진입하고 나머지는 이전 1을 받아 기다리게 할 수 있다.

상호배제는 동시 진입을 막는 안전성이다. 결국 진입하는가라는 진행, 특정 스레드가 끝없이 기다리는가라는 기아, 성능은 별도 질문이다. 실제 락에는 원자 primitive뿐 아니라 적절한 메모리 순서가 필요하며, 여기서는 제품용 락을 직접 완성했다고 주장하지 않는다.

중간 과정을 따라가는 예제

초기 x=0에서 A/B가 각각 1 증가한다. A 읽기,B 읽기,A 쓰기,B 쓰기 순서와, 각 atomic fetch_add(1) 순서를 종이로 비교하라.

  1. A가 0을 읽고 개인 값 1을 만든다. B도 아직 0을 읽어 1을 만든다.

  2. A 쓰기 1 뒤 B 쓰기 1이면 종이 x=1이다. 두 증가 중 하나가 반영되지 않는다.

  3. 원자 fetch_add가 A 먼저면 A의 이전 값 0/새 값 1, B의 이전 값 1/새 값 2다. B 먼저면 역할만 바뀐다.

  4. 동기화된 원자 두 증가의 최종 값 2와 원자 연산이 반환한 이전 값 0/1을 구분한다. 비원자 C++ 코드 실행의 정상 출력 보장은 아니다.

종이 인터리빙의 잃은 갱신 1, 원자 두 증가의 모형 값 2다. 실제 C++ 비원자 레이스는 undefined behavior다.

조건을 바꾸어 비교하기

한 숫자의 원자성과 여러 상태의 불변식

자리는 1개다. 검사와 예약 목록 갱신은 잠금 없이 하고 남은 자리의 감소만 원자적으로 한다. 두 요청이 먼저 검사에 통과한 뒤 각각 fetch_sub(1)을 한다.

  1. 첫 요청의 감소는 이전 값 1을 돌려주고 남은 자리를 0으로 만든다.

  2. 두 번째 감소는 이전 값 0을 돌려주고 남은 자리를 −1로 만든다. 감소가 원자적이어도 이미 통과한 두 검사를 되돌려 주지는 않는다.

  3. 같은 mutex 안에서 자리 검사, 자리 감소, 예약 추가를 함께 수행하면 A가 먼저 확정한 뒤 B는 0을 보고 거절한다. 모든 관련 접근이 이 규칙을 따라야 한다.

단일 원자 감소만으로 예약 성공을 확정하면 두 예약이 생긴다. 이 단순 설계에서는 전체 예약 결정을 같은 잠금으로 묶어야 한다.

비교할 점

기존 카운터 예제는 한 숫자의 갱신 유실을 보였다. 이 예제는 갱신이 유실되지 않아도 여러 상태를 묶은 조건은 실패할 수 있음을 보인다.

나뉜 검사와 원자 교환

추상 잠금 flag는 처음 0이다. A와 B는 0이면 1로 바꾸고 들어가려 한다. 먼저 별도 읽기/쓰기를, 다음으로 하나의 원자 exchange(1)을 비교한다.

  1. 별도 읽기는 A와 B 모두 0을 볼 수 있다. 각자 1을 쓰면 둘 다 자신이 획득했다고 잘못 판단한다.

  2. 교환 순서가 A 다음 B이면 A는 이전 값 0, B는 이전 값 1을 받는다. 이전 값 0인 A만 들어간다. 순서가 바뀌면 B만 들어간다.

  3. 이 한 번의 획득 구별은 보호 자료의 메모리 순서, 해제, 수명, 기아 방지까지 구현한 완성 잠금이라는 뜻은 아니다.

검사와 설정을 하나로 묶으면 이 획득 경쟁에서 한 명만 성공한다.

오해와 반례

연습 1 · 값과 상태 예측

힌트 1

힌트 2

별도 저장값은 둘 다 10이다. RMW 두 번째는 첫 수정 뒤 값을 읽는다.

풀이와 답 확인

  1. 별도 읽기에서는 A의 지역 값과 B의 지역 값이 모두 8이다.

  2. A가 10, B도 10을 저장하므로 최종 10이다.

  3. fetch_add에서는 이전 값 8, 10을 돌려주고 최종 12이다.

별도 load/store는 10, fetch_add 두 번은 12이다.

소단원 5.2

스핀락·블로킹 락

자물쇠가 열릴 때까지 문 앞에서 계속 확인하는 것과 잠시 쉬는 것은 언제 차이가 날까?

준비 개념과 학습 목표

준비 개념

  • 락 소유자만 임계구역을 실행하고 끝나면 해제한다. 대기자는 아직 소유권이 없다.

  • 종이 모형의 CPU는 한 시점에 한 스레드만 실행한다. 멀티코어에서는 다른 CPU의 소유자가 동시에 진행할 수 있다.

학습 목표

  • 회전 대기와 잠드는 대기의 CPU 사용을 비교한다.

  • 깨움과 소유권·공정성의 차이를 설명한다.

차례를 기다리는 사람이 계속 문손잡이를 돌려야 할까, 이름을 남기고 쉬어도 될까?

반복 확인은 아직 사용할 수 없는 CPU를 계속 소비한다. 잠드는 방법은 CPU를 다른 흐름에 줄 수 있지만 대기 등록과 깨우기 연결이 필요하다. “기다린다”는 말만으로 실행 상태를 알 수 없다.

잠든 흐름은 깨워져 실행 가능 상태가 되더라도 즉시 CPU나 잠금을 받지 않는다. 아래에서는 소유권을 직접 넘기는 handoff 잠금이 아닌 재경쟁 모형을 쓴다. 수치는 가상 시간표이며 실제 OS 측정이 아니다.

    실행 중, 실행 가능, 잠든 상태를 구별하고 공유 주소 공간을 떠올린다.

  • 공정성과 기아

    상호배제가 성립해도 각 대기자가 기회를 얻는지는 별도 조건임을 구별한다.

기다리는 동안 무엇을 하는가

스핀락 대기자는 락이 잡혀 있는 동안 반복해서 획득을 시도하여 CPU 시간을 쓴다. 블로킹 락은 필요할 때 대기 큐에 등록하여 스레드를 잠들게 하고 다른 작업이 CPU를 사용하게 한다. 잠들기·깨우기·스케줄링에도 비용이 있어 아주 짧은 기다림에서는 회전이 합리적일 수 있다. 그러나 항상 더 빠르다는 주장은 할 수 없다.

일반 사용자 코드가 단일 CPU에서 스핀하면서 선점도 자발적 양보도 없다면 락 소유자가 다시 실행될 기회가 없어 해제되지 않는다. 단일 코어 자체보다 소유자가 진행할 수 있는 스케줄링 조건을 확인해야 한다. 실제 커널 스핀락·인터럽트·선점 규칙은 플랫폼별로 다르다.

잠들기 전 조건이 바뀌면

단순히 락이 잡혔다고 읽은 뒤 나중에 잠드는 두 단계만 있으면 그 사이에 소유자가 풀고 깨울 수 있다. 아직 대기자가 잠들기 전이라 깨움이 사라지고 그 뒤 잠들어 오래 기다리는 깨움 손실이 가능하다. 따라서 검사·대기 등록·수면 진입을 안전하게 연결하는 프로토콜이 필요하다.

futex 같은 기술은 값이 기대한 상태인지 다시 검사하여 조건이 바뀌었으면 잠들지 않는 방식을 제공한다. 라이브러리 락은 이를 비롯한 내부 원자 동작으로 대기를 조정한다. 깨어났다는 사실은 조건이 여전히 맞거나 반드시 즉시 락을 얻었다는 뜻이 아니다. 구현의 약속에 따라 직접 인계하거나 다시 획득을 시도한다.

효율과 기아를 분리한다

상호배제는 한 번에 한 소유자라는 안전 규칙이다. 공정성은 누구에게 어떤 기회가 오는지에 대한 규칙이다. 잠드는 락이라고 자동 FIFO는 아니며 다른 새 스레드가 먼저 획득할 수 있는 구현도 있다. 큐의 존재만으로 운영체제의 실행 순서 전체를 증명하면 안 된다.

현대 락은 짧게 spin한 뒤 잠드는 혼합 방식도 쓸 수 있다. 언어의 std::mutex 계약은 소유권과 동기화를 주지만 내부 모든 경로가 항상 OS 수면이라는 뜻은 아니다. 제품 코드에서는 검증된 라이브러리 사용과 짧은 임계구역을 우선하고 필요한 성능은 측정한다.

중간 과정을 따라가는 예제

단일 CPU 선점 가능 모형에서 A가 락을 가진 채 시각 0에 멈추고 B가 0..5 동안 5단위 대기한 뒤 A가 5..7에 남은 2단위 일을 한다. spin과 blocking의 대기 CPU 사용을 비교하라. blocking에서는 B가 시각 0에 0.2단위 등록 후 잠들고 A가 0.2..2.2 실행한다고 가정한다.

  1. spin의 B는 0..5의 5단위 동안 반복 검사한다. 지정한 스케줄에서 A는 5에 돌아와 7에 해제한다.

  2. blocking의 B는 0..0.2 등록 후 잠든다. A는 0.2에 돌아와 2.2에 해제한다.

  3. B의 대기 중 CPU 사용은 spin 5와 blocking 등록 0.2다. 깨운 뒤 획득/실행 비용은 이 비교에 주어지지 않아 추가하지 않는다.

  4. 시간 7과 2.2는 주어진 스케줄 가정의 값이다. 모든 CPU나 라이브러리에서 실측된 속도 비율이 아니다.

이 모형은 소유자에게 CPU를 돌려주는 대기가 유리할 수 있음을 보인다. 수면·깨움 실제 비용이나 성능 측정은 미수행이다.

조건을 바꾸어 비교하기

벽시계 지연과 소비한 CPU 시간

두 CPU 모형에서 A는 4 ms 뒤 해제한다. B의 spin은 [0,4) 전체에서 자기 CPU를 쓴다. block 모형은 [0,0.3) 등록, [0.3,4) 수면, [4,4.2) 복귀 비용 후 획득한다. 다른 경쟁자는 없다.

  1. spin의 기다림은 4 ms, 대기 CPU 소비도 4 ms다.

  2. block의 획득까지 간격은 4.2 ms, B가 쓴 대기 절차 CPU는 0.3 + 0.2 = 0.5 ms다.

  3. 수면 3.7 ms는 CPU 소비 합에 넣지 않는다. 이 모형의 두 기준은 서로 다른 방식에 유리하다.

spin은 더 이른 획득, block은 더 적은 대기 CPU 소비다. 실제 장치의 우열은 이 가상표로 판정하지 않는다.

비교할 점

기존 한 CPU 예제는 소유자의 실행 기회를 비교했다. 여기서는 소유자가 별도 CPU에서 진행할 때 시간 간격과 CPU 소비가 다른 지표임을 비교한다.

깨우기를 놓치는 틈을 닫기

flag 1을 본 B가 잠들기로 결정한다. A가 flag를 0으로 바꾸고 깨운 뒤 B가 잠드는 잘못된 순서를 살핀다. 이후 A의 깨우기는 없다.

  1. 단순 sleep은 이미 지난 깨우기를 기억하지 않으므로 B가 계속 잠들 수 있다.

  2. Linux FUTEX_WAIT의 기대값 검사와 대기 시작은 같은 futex word의 다른 futex 연산에 대해 원자적으로 연결된다. 현재 값이 기대값 1과 다른 0이면 EAGAIN으로 잠들지 않는다.

  3. 반환 뒤에도 사용자 쪽 잠금 조건을 재검사한다. futex wait 자체가 mutex 획득 전체나 C++ 보호 자료의 메모리 순서를 대신하는 것은 아니다.

검사와 수면 사이 틈을 닫는 대기 프로토콜과 재검사가 필요하다.

소단원 5.3

메모리 순서 입문

준비됐다는 표지를 보았다면 그 앞에 작성한 내용도 안전하게 볼 수 있을까?

준비 개념과 학습 목표

준비 개념

  • C++11 이후 기능의 개념 예로 atomic<bool> ready와 일반 int data를 사용한다. 두 스레드 시작 전에 ready=false,data=0으로 초기화한다.

  • 쓰기 스레드는 data를 한 번 쓰고 게시한다. 읽기 스레드는 게시를 확인한 뒤 한 번 읽는다. 이후 동시 변경과 재사용은 없다.

  • release는 게시 쪽의 메모리 순서, acquire는 수신 쪽의 메모리 순서다. synchronizes-with는 두 연산을 연결하는 동기화 관계이고 happens-before는 이 연결과 스레드 내부 순서를 합친 선행 관계다. 실제 같은 스레드에 두 구간을 이어 실행하는 완성 프로그램이 아니라 두 스레드 역할을 나눈 개념 조각이다.

학습 목표

  • 한 객체의 원자성과 다른 데이터의 공개 순서를 분리한다.

  • release/acquire 연결 조건으로 happens-before 경로를 그린다.

상자를 다 채우고 “준비 완료” 표지를 올렸다면, 표지만 읽은 사람이 내용도 안전하게 볼까?

표지 자체가 찢어지지 않는다는 것과 상자의 내용을 안전하게 읽는다는 것은 별개다. atomic은 표지 객체의 연산을 다루고 release/acquire 연결은 먼저 쓴 내용을 뒤의 읽기에 연결한다.

여기서는 스레드 시작 전에 수명이 확보된 일반 data와 atomic ready가 있고, 한 작성자가 한 번 쓰며 한 독자가 해당 공개를 확인한 뒤 읽는다. 공개 뒤 재작성과 저장공간 재사용은 없다. 이 조건을 빼면 한 번의 준비 표지만으로 안전성을 설명할 수 없다.

먼저 확인할 개념
  • 변수와 상태

    이름, 읽은 값, 공유 값의 변화를 따로 기록한다.

  • 임계구역과 원자 연산

    개별 원자 연산의 보장과 일반 공유 자료 보호를 구별한다.

나뉘지 않는 값과 앞뒤의 순서

atomic ready의 접근은 나뉘지 않는다고 해도 주변 일반 data에 대한 스레드 간 순서가 자동으로 생기지는 않는다. relaxed는 원자 객체 자체의 안전한 접근에 쓸 수 있지만 다른 객체의 게시 순서를 만드는 약속이 아니다. 단순히 두 스레드가 벽시계에서 나중에 실행됐다는 관측도 언어의 동기화 근거와 다르다.

메모리 순서는 컴파일러·CPU가 허용하는 재배열과 관측을 언어 계약으로 제한한다. 특정 기계에서 한 번 잘 나왔다는 실험은 다른 기계와 최적화까지의 증명이 아니다. volatile을 붙이는 것도 C++ 스레드 간 동기화를 대신하지 않는다.

게시와 수신을 연결한다

작성자는 data=42를 쓴 뒤 ready.store(true,release)를 한다. 수신자는 ready.load(acquire)가 그 release 쓰기의 true를 읽었을 때 data를 읽는다. 같은 ready의 release→acquire가 동기화 연결을 만들고 작성자의 data 쓰기→게시→수신→data 읽기의 happens-before 경로가 이어진다. 명시한 단발 모형에서는 data 읽기의 42를 설명할 수 있다.

acquire를 썼어도 false를 읽었다면 그 게시를 받았다는 뜻이 아니다. 다른 atomic 객체를 acquire로 읽는 것도 이 게시를 연결하지 않는다. 여러 게시자,데이터의 재사용,반복 변경이 있으면 추가 프로토콜이 필요하다. 이 간단한 예제에서 임의 메시지 큐 전체의 안전성으로 확장하지 않는다.

// 개념 코드: 두 스레드 시작 전에 초기화되어 수명이 유지됨
std::atomic<bool> ready{false};
int data = 0;
// 작성 스레드
data = 42;
ready.store(true, std::memory_order_release);
// 수신 스레드
if (ready.load(std::memory_order_acquire)) {
    int observed = data;  // 단발 게시 조건에서 42
}

안전한 기본 수단부터 선택한다

같은 mutex로 보호한 일반 data의 쓰기와 읽기는 unlock→후속 lock의 동기화로 설명할 수 있다. 초보자에게는 복잡한 수동 메모리 순서보다 그 보호 약속을 일관되게 사용하는 편이 검토하기 쉽다. seq_cst는 해당 원자 연산들에 추가 총순서 제약을 주지만 임의 일반 변수의 data race를 없애 주지 않는다.

ready만 relaxed로 바꿔 true를 관측해도 일반 data 쓰기와 읽기에는 동기화가 없어 C++ data race가 생길 수 있다. 이 경우 observed가 0이나 42 중 하나라고 예상 출력 목록을 쓰면 잘못이다. 일반 변수 레이스는 undefined behavior다. 만약 data도 atomic이면 data race 문제와 여러 객체의 공개 순서 논리 문제를 다시 분리해 분석한다.

중간 과정을 따라가는 예제

단발 게시에서 W1:data=42, W2:ready release=true, R1:ready acquire가 W2의 true 읽음, R2:data 읽음의 네 사건 관계를 그려라.

  1. 작성 스레드 내 W1은 W2보다 앞선다. 수신 스레드 내 R1은 R2보다 앞선다.

  2. R1이 같은 ready의 W2 true를 읽어 W2가 R1과 동기화된다.

  3. 관계를 합치면 W1 happens-before R2다. 그 사이에 다른 data 쓰기가 없으므로 R2는 42를 읽는다.

  4. R1이 false를 읽으면 if 본문을 실행하지 않아 data를 읽지 않는다. 모든 load가 결국 true를 읽는다는 진행 시간 보장은 이 예제에서 증명하지 않는다.

성공적으로 연결된 단발 게시의 observed=42다. 이것은 언어 규칙에 따른 정적 해석이며 실제 실행 결과 기록이 아니다.

조건을 바꾸어 비교하기

표지의 이름이 다른 경우

작성자는 data를 쓰고 ready에 release true를 저장한다. 독자는 다른 atomic ping에서 acquire true를 읽은 뒤 data를 읽는다. ping의 true는 스레드 시작 전 초기값이며 추가 동기화는 없다.

  1. acquire라는 이름만으로 임의의 release와 연결되지 않는다.

  2. ping에서 읽은 값은 ready에 수행한 공개에서 온 값이 아니다. W2 → R1 연결이 없다.

  3. 일반 data의 상충 읽기/쓰기에 다른 happens-before도 없으므로 C++ 데이터 경합 문제가 남는다.

별개 표지의 acquire로 ready 공개를 대신할 수 없다. ready의 해당 release를 읽도록 프로토콜을 바꿔야 한다.

  1. 첫 쓰기 73은 공개를 통해 독자의 읽기보다 앞선다.

  3. 두 번째 쓰기와 읽기 사이에 happens-before가 없으면 일반 data에 데이터 경합이 생긴다. 같은 true를 다시 확인해도 새 쓰기의 안전한 완료 확인이 아니다.

공개 후 불변 자료라는 가정을 유지하거나 재작성과 읽기를 같은 mutex 등 새 동기화로 보호해야 한다. 출력이 73 또는 91뿐이라고 제한할 수 없다.

한 단계 더

프로그램 검토 시에 변수별로 일반/atomic을 표시하고 모든 충돌 쌍을 찾은 뒤 happens-before 선을 그려 보자. 선이 없다면 실험을 반복해 운 좋은 출력을 찾기보다 동기화 설계를 수정한다. release/acquire를 낮은 수준 최적화에 쓰려면 전체 프로토콜·객체 수명·진행 조건을 검토해야 한다.

출처와 확인 범위
  • C++ working draft, Order and consistency

    [atomics.order] 실제1–2 및 seq_cst 관련 절에서 relaxed의 원자성, release/acquire가 같은 객체의 값을 읽어 연결되는 조건을 읽었다. 현재 초안은consume 항목을 포함하지 않아 원고도 다루지 않는다.

  • C++ working draft, Data races

    [intro.races]의 실제 data race 정의, happens-before와 비원자 충돌의 undefined behavior 절을 읽었다. 종이 인터리빙은 실제 C++ data-race 프로그램의 허용 출력 목록이라는 뜻이 아니다.

  • C++ working draft, Mutex requirements

    실제 lock/unlock의소유권·블로킹 및 unlock과 같은mutex 후속 획득 동기화 절을 읽었다. 특정 OS의 공정성이나 내부기술을 언어계약에서 단정하지 않는다.

다른 문제에 적용하기

공유 미리보기 상자는 일반 필드 title과 count, atomic ready를 가진다. 작성자 한 명이 title = "별", count = 2를 채워 공개하고 여러 독자가 한 번 읽는다. 공개 뒤 수정은 없다. 안전한 공개 절차를 적고, 수정 기능이 추가되어 count = 3과 title = "달"을 별도 순서로 덮어쓰는 변경안을 평가하라. 수정판은 같은 mutex로 전체 쌍을 보호한다고 설계해 보라. 실제 스레드를 실행할 필요는 없다.

힌트 1

한 번 공개의 수명·작성자·값 출처 조건과 이후 수정의 보호 조건을 나눠 적는다.

힌트 2

수정판에서는 작성뿐 아니라 독자의 두 필드 읽기도 같은 mutex 안에서 수행한다.

풀이와 답 확인

  1. 처음에는 자료와 ready의 수명을 스레드 사용 전체에 확보하고 두 필드를 먼저 채운다.

  2. ready에 release true를 저장한다. 각 독자는 같은 공개 값을 acquire로 읽은 경우만 불변 필드를 읽는다. 독자 수가 늘어도 읽기끼리는 상충 쓰기가 없지만 모든 독자에게 공개 연결이 필요하다.

  3. 공개 뒤 일반 필드를 동기화 없이 수정하면 독자와 상충하여 데이터 경합이 생길 수 있다. 같은 true를 읽는 것으로 새 수정이 보호되지 않는다.

  4. 수정판에서는 title과 count 쓰기 및 쌍 읽기를 동일 mutex로 묶고 임계구역 밖으로 참조를 남겨 동시 읽지 않는다. ready의 첫 초기화 공개와 수명 조건도 보존한다.

  5. 재경쟁형 blocking 잠금에서 깨운 독자는 소유권을 재획득한다. CPU 소비나 공정성은 이 설계의 안전성과 별도로 평가한다.

한 번 공개에서는 조건을 지킨 독자가 (별,2)를 읽는다. 동기화 없는 수정판의 실제 C++ 결과를 두 값 쌍으로 한정하지 않는다. 동일 mutex를 지킨 수정판에서는 수정과 읽기 순서에 따라 완전한 이전 쌍 (별,2) 또는 새 쌍 (달,3)을 읽는다. 수명, 초기 공개, 모든 상충 접근의 보호가 전제다.

해결한 뒤 점검할 것

  • 일반 자료와 atomic 표지를 구별한다.

  • 같은 객체의 release/acquire와 읽은 값 출처를 명시한다.

  • 재작성의 데이터 경합을 유한 출력 목록으로 바꾸지 않는다.

  • 쌍의 모든 읽기·쓰기를 같은 mutex로 보호한다.

  • 깨우기와 소유권, 안전성과 성능을 분리한다.
