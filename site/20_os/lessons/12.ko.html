inode·디렉터리·블록 할당

두 파일 이름이 같은 내용을 가리킬 때 저장공간도 두 배로 필요할까?

준비 개념과 학습 목표

준비 개념

  • 이름과 데이터의 구별

  • 몫과 나머지

학습 목표

  • 디렉터리 이름과 inode 및 데이터 블록의 역할을 구별한다.

  • 직접·간접 포인터를 따라 파일 오프셋을 찾는다.

  • 논리 크기와 모형의 할당 공간을 계산한다.

논리적으로 다섯 블록에 걸친 파일도 데이터 블록은 세 개만 가질 수 있을까?

이번 자체 모형은 본문의 1024바이트 블록·직접 포인터 두 개·단일 간접 포인터를 유지하면서 sparse 구멍을 명시적으로 추가한다. 길이는 4097바이트이고 논리 블록 0, 2, 4에만 데이터가 있다. 물리 데이터 번호는 각각 10, 20, 30이며 논리 블록 1, 3은 구멍이다. 구멍은 파일 범위 안에서 읽으면 값이 0인 바이트들을 반환하고 별도의 데이터 블록을 확보하지 않는다고 정한다. 포인터 블록 번호는 7이며 inode·디렉터리·비트맵 공간은 계산에서 제외한다.

논리 범위는 0–4096의 4097바이트로 다섯 논리 블록에 걸친다. 실제 데이터 세 블록은 3072바이트이고 간접 블록 하나를 더하면 확보량은 4096바이트다. 모든 논리 블록을 확보하는 dense 모형은 데이터 5120바이트와 포인터 1024바이트로 합계 6144바이트다. 같은 논리 길이에서도 확보량이 다르며 끝 블록의 실제 유효 바이트는 한 바이트다.

구멍을 가로지르는 읽기도 먼저 논리 블록 경계를 자른다. offset 1020에서 1030바이트를 읽으면 첫 블록의 마지막 4바이트, 구멍 블록의 값이 0인 1024바이트, 다음 데이터 블록의 첫 2바이트다. inode가 이미 메모리에 있고 다른 캐시는 비어 있다는 자체 읽기 비용 모형에서는 물리 데이터 블록 10과 20 및 간접 포인터 블록 7을 읽는다. 구멍의 내용을 얻으려고 별도 데이터 블록을 읽지 않는다.

이 기능을 모든 파일시스템에 덧씌우면 안 된다. 실제 열람한 xv6 bmap은 없는 블록을 할당할 수 있고 writei는 현재 길이를 건너뛴 쓰기를 거절한다. 따라서 이 sparse 모형을 xv6가 구현했다고 주장하지 않는다. Linux lseek 문서도 SEEK_DATA/SEEK_HOLE가 실제 할당 공간을 언제나 정확히 알려주는 것은 아니라고 설명한다. 영 값이 있다는 사실만으로 구멍이나 미할당을 판정하지 않는다.

이름을 찾는 표와 파일의 설명서

전통적인 Unix 계열 모형에서 디렉터리는 이름과 inode 번호를 연결하는 항목을 갖는다. inode는 파일 종류, 권한, 소유자, 크기와 데이터 위치를 설명하는 메타데이터다. 이름 자체와 파일의 내용은 같은 개념이 아니다.

하드 링크는 두 이름을 같은 파일에 연결한다. 같은 파일시스템 안에서 a와 b가 inode 7을 가리키면 두 이름이 존재해도 내용 전체가 복사된 것은 아니다. inode 번호는 파일시스템과 함께 식별해야 하며 모든 장치에서 영원히 유일한 번호가 아니다.

데이터를 잘라 저장하는 방법

이 단원은 빈 구멍이 없는 일반 파일을 1024바이트 블록으로 저장하는 자체 모형을 사용한다. inode 안에 직접 포인터 두 개, 단일 간접 포인터 한 개를 둔다. 직접 포인터는 데이터 블록을 가리키고 간접 포인터는 데이터 블록 번호들이 들어 있는 별도 블록을 가리킨다.

블록 번호 한 개를 4바이트로 저장하면 간접 블록에 1024 ÷ 4 = 256개가 들어간다. 이 단순 모형의 데이터 블록 최대 개수는 2 + 256 = 258개다. 실제 파일시스템은 다중 간접 포인터나 연속 범위를 기록하는 extent 등 다른 구조를 쓰므로 이 최대값을 실제 OS 제한으로 외우지 않는다.

길이와 할당 공간은 다르다

파일의 논리 길이는 읽을 수 있는 바이트 범위다. 2500바이트 파일은 이 모형에서 데이터 블록 세 개를 사용하며 마지막 블록의 일부가 남는다. 포인터 블록과 inode·디렉터리의 공간은 데이터 길이에 포함하지 않는다.

빈 블록을 찾고 배정 여부를 기록하는 비트맵도 메타데이터다. 파일을 만들려면 데이터뿐 아니라 필요한 메타데이터 공간도 마련해야 한다. 실제 sparse 파일은 일부 논리 범위를 물리 블록 없이 나타낼 수 있어 여기의 단순 올림 계산을 그대로 적용할 수 없다.

중간 과정을 따라가는 예제

위 모형에서 파일 길이는 2500바이트다. 직접 데이터 블록 번호는 5와 8, 간접 블록 번호는 3이고 그 첫 데이터 번호는 11이다. 파일 오프셋 2300의 위치와 공간을 구하라. 블록 번호 0의 시작을 저장장치 바이트 위치 0으로 정한다.

  1. 2500 ÷ 1024를 올림하면 데이터 블록 세 개다. 데이터 할당은 3072바이트, 남는 공간은 3072 − 2500 = 572바이트다.

  2. 2300 = 2 × 1024 + 252이므로 논리 블록 2의 내부 오프셋 252다. 0·1은 직접 포인터를 쓰고 2는 간접 블록 3의 첫 항목을 통해 데이터 블록 11에 도달한다.

  3. 저장장치 모형의 바이트 위치는 11 × 1024 + 252 = 11516이다. 이것은 RAM 주소가 아니다.

  4. 간접 블록 하나도 필요하므로 데이터 세 블록과 포인터 한 블록의 합은 4096바이트다. inode·디렉터리·비트맵 공간은 이 합에서 제외했다.

오프셋 2300은 데이터 블록 11의 252번째 오프셋에 있다. 데이터 할당 3072바이트, 이 파일의 포인터 블록을 더한 합 4096바이트다.

조건을 바꾸어 비교하기

같은 길이, 다른 확보량

이 파일의 sparse와 dense 확보량을 계산하라.

  1. 다섯 논리 블록에 걸치지만 sparse 데이터 할당은 세 블록으로 3072바이트다.

  2. 두 직접 범위를 넘는 데이터 블록 20과 30 때문에 포인터 블록 1024바이트를 추가한다.

  3. dense는 데이터 다섯 블록 5120바이트와 포인터 블록 1024바이트를 확보한다.

sparse 확보량은 4096바이트, dense 확보량은 6144바이트이며 차이는 2048바이트다. 논리 길이는 둘 다 4097바이트다.

비교할 점

inode와 디렉터리 등 제외된 비용까지 전체 저장장치 사용량으로 확정하지 않는다.

구멍과 데이터 사이 읽기

offset 1020에서 길이 1030바이트인 읽기를 논리 구간과 물리 읽기로 분해하라.

  1. [1020,1024)는 데이터 블록 10의 끝 4바이트다.

  2. [1024,2048)는 구멍에서 읽는 값이 0인 1024바이트다.

  3. [2048,2050)는 포인터 블록 7을 따라 데이터 블록 20의 첫 2바이트를 읽는다.

유효 결과 길이는 4 + 1024 + 2 = 1030바이트이며 자체 cold 비용은 데이터 두 블록과 포인터 한 블록으로 총 3회다.

비교할 점

파일 내용의 바이트 수와 물리 블록 읽기 횟수를 같은 단위로 합치지 않는다.

연습 1 · 값과 상태 예측

위 읽기 직후 같은 범위를 다시 읽는다. 이번에는 포인터7만 캐시에 있고 데이터 캐시는 비었다고 새로 정하자. 블록 읽기 횟수는?

힌트 1

두 데이터 블록10·20은 다시 필요하다.

힌트 2

구멍에는 별도 데이터 블록이 없다.

풀이와 답 확인

  1. 포인터7은 캐시에서 얻어 물리 읽기를 추가하지 않는다.

  2. 데이터10과20 두 블록을 읽는다.

자체 모형에서 블록 읽기는 2회다. 앞 읽기의 모든 데이터가 캐시에 남았다고 가정하지 않는다.

캐시 상태를 명시했으므로 포인터만 적중이고 데이터는 실패다.

힌트 1

힌트 2

풀이와 답 확인

  1. 동일한 영 값 구간은 미할당 구멍과 할당된 영 데이터 양쪽에서 나올 수 있다.

  2. 파일시스템의 지원 계약과 할당 정보를 별도로 확인한다.

  3. SEEK_HOLE 결과만으로 정확한 물리 배정을 보장하지 않는다.

읽은 내용만으로 미할당 여부를 확정하지 않는다.

힌트 1

힌트 2

풀이와 답 확인

  2. [4096,4097)의 데이터30 첫 한 바이트를 얻는다.

  3. 파일 끝을 넘는 나머지 두 바이트는 유효 결과에 넣지 않는다.

이 모형에서 반환 길이는 2바이트다. 두 값이 모두 0이어도 첫 구멍과 끝 데이터 할당을 구별한다.

lseek 뒤 read를 묶으면 다른 흐름의 위치 변경을 피할 수 있을까?

자체 일반 파일 ABCDEFGH의 열린 설명 F를 두 번호가 공유하고 처음 offset은0이다. P는 처음 두 바이트, Q는 offset4의 두 바이트를 읽고 싶다. P가 lseek(0), Q가 lseek(4), P가 read(2), Q가 read(2)를 성공적으로 수행한 순서를 정하면 P는 EF, Q는 GH를 읽는다. 두 시스템 호출 사이에 다른 위치 변경이 끼어들었기 때문이다. 각 호출 자체의 성공이 둘을 하나의 묶음으로 만든 것은 아니다.

pread는 seek 가능한 파일의 지정 offset에서 최대 count를 읽고 열린 설명의 공유 offset을 바꾸지 않는다. 같은 파일이 변하지 않고 두 요청이 정확히 두 바이트 성공한다는 자체 조건에서 P의 pread offset0은 AB, Q의 offset4는 EF이며 F의 offset은0으로 남는다. 이 방법은 공유 위치 경합을 피하지만 파일 내용 자체의 동시 변경·짧은 반환·오류까지 없애지는 않는다.

번호 재연결도 여러 호출을 임의로 합치면 위험하다. 번호1이 설명 O, 번호3이 설명 F를 가리키며 번호0·2·3은 이미 사용 중이라고 정한다. close(1) 후 다른 흐름이 open하여 가장 낮은 빈 번호1을 얻으면, 이어 dup(3)은 이제 번호4를 얻는다. 원하는 번호1 재지정을 하지 못했다. Linux dup2(3,1)는 대상 번호의 닫기와 재연결을 원자적으로 수행하지만 성공 반환·소유 책임은 따로 확인한다.

설명과 번호 플래그의 층도 분리한다. dup 번호들은 file status flags와 offset을 공유하지만 FD_CLOEXEC 같은 descriptor flag는 각 번호의 속성이다. 이번 연습은 C/Linux 호출 계약의 종이 추적이며 Python os.dup의 상속 기본값이나 본문 Windows 실행 증거와 같다고 쓰지 않는다. 이미 수행된 v1 예제 증거는 보존하고 신규 경합 실행은 미수행으로 남긴다.

서로 다른 파일시스템을 연결하는 문

Linux VFS는 파일 관련 시스템 호출을 각 파일시스템 구현으로 연결하는 공통 계층이다. 프로그램은 익숙한 열기·읽기 인터페이스를 사용하고 커널은 해당 파일시스템의 동작을 선택한다. 디스크 파일만이 아니라 장치 등도 이 인터페이스에 연결될 수 있다.

VFS의 dentry는 메모리에 유지하는 이름 조회 객체이며 디스크 디렉터리 항목 그 자체가 아니다. inode 객체는 파일을 설명하고 열린 file 객체는 사용 중인 파일에 대한 참조와 동작을 갖는다. Linux 설명을 모든 운영체제의 내부 구조라고 일반화하지 않는다.

번호와 열기 상태를 분리하기

파일 디스크립터는 프로세스가 사용하는 작은 정수 번호다. 이 번호로 열린 파일 설명을 찾는다. 일반 파일의 열린 설명에는 현재 읽기 위치와 파일 상태 플래그가 포함된다. 같은 이름을 다시 open하면 보통 별도의 열린 설명이 생겨 위치도 별개로 움직인다.

dup은 새 번호를 만들지만 원래 열린 설명을 공유한다. 따라서 한 번호로 읽거나 위치를 옮기면 다른 번호가 보는 위치도 바뀐다. 모든 플래그가 공유되는 것은 아니다. Linux의 파일 디스크립터 플래그와 파일 상태 플래그는 구별되며 Python의 상속 규칙도 API 문서로 확인해야 한다.

작은 읽기로 공유 위치 확인하기

아래 Python 코드를 fd_example.py로 저장하고 python fd_example.py로 실행할 수 있다. Python 표준 라이브러리만 쓰며 자신의 임시 폴더와 여섯 바이트 파일을 만든 뒤 닫고 정리한다. Windows에서는 O_BINARY를 더해 텍스트 변환을 피한다. Linux VFS 내부 추적 실험은 아니다.

handles는 종료할 번호들을 담는다. try/finally는 읽기 중 오류가 나도 확보한 번호를 닫기 위한 구조다. os.read는 일반적으로 요청보다 적은 바이트를 반환할 수 있으므로 임의의 장치·네트워크 프로그램에서 정확히 두 바이트를 보장하는 코드로 사용하지 않는다. 여기서는 작은 일반 파일의 실제 관찰을 다룬다. Python의 버퍼가 있는 고수준 파일 읽기를 같은 열린 설명에 섞지 않는다.

import os
import tempfile
from pathlib import Path

with tempfile.TemporaryDirectory(prefix="fd-lesson-") as folder:
    path = Path(folder) / "letters.bin"
    path.write_bytes(b"ABCDEF")
    handles = []
    try:
        flags = os.O_RDONLY | getattr(os, "O_BINARY", 0)
        first = os.open(path, flags)
        handles.append(first)
        shared = os.dup(first)
        handles.append(shared)
        separate = os.open(path, flags)
        handles.append(separate)
        print(os.read(first, 2))
        print(os.read(shared, 2))
        print(os.read(separate, 2))
        print(os.lseek(first, 0, os.SEEK_CUR),
              os.lseek(shared, 0, os.SEEK_CUR),
              os.lseek(separate, 0, os.SEEK_CUR))
        os.close(first)
        handles.remove(first)
        print(os.read(shared, 2))
    finally:
        for fd in handles:
            os.close(fd)

풀이와 답 확인

  2. dup2 뒤 O는 번호 4의 한 참조를, F는 번호 1과 3의 두 참조를 갖는다.

  3. 번호 3을 닫은 뒤 O는 번호 4, F는 번호 1의 한 참조씩 남는다.

이름 current를 새 파일로 교체하면 이미 열린 독자도 새 내용을 읽을까?

자체 Unix 일반 파일 모형에서 current와 backup은 옛 객체 O의 두 하드 링크다. 임시 이름 tmp는 새 객체 N을 가리킨다. 기존 독자는 current를 이미 열어 O를 참조한다. 같은 마운트 파일시스템에서 rename(tmp,current)가 성공하면 current는 N을 가리키고 tmp 이름은 사라진다. backup과 기존 독자의 열린 참조는 O를 계속 가리킨다. 열린 번호는 이름을 다시 조회할 때마다 다른 객체로 자동 바뀌지 않는다.

새 독자가 성공한 rename 뒤 current를 열면 N을 얻는다. 기존 current가 원자적으로 교체되는 계약은 대상 이름이 중간에 없어지는 틈을 만들지 않는다는 뜻이다. 모든 독자가 동시에 N으로 바뀐다거나 두 파일의 내용·다른 이름·전원 장애 뒤 저장까지 한 번에 묶인다는 뜻은 아니다. 실제 파일 내용은 완성·검증 후 게시하고 저장 동기화 조건은 따로 확인해야 한다.

이름과 열린 참조를 따로 세면 O 링크 수는2→1이고 독자 참조는1로 남는다. 이후 backup도 unlink하면 O 링크0·독자 참조1이다. 마지막 독자가 닫아 링크0·참조0이 돼야 이 단순 모형에서 공간 재사용이 가능하다. 다른 매핑·커널 참조는 제외했다. N은 current 링크를 유지한다. 하드 링크 이름을 교체하는 동작과 파일 내용을 제자리에서 수정하는 동작은 구별한다.

호출 경계와 실패도 확인한다. 같은 객체의 두 하드 링크를 oldpath와 newpath로 rename하면 문서 계약에서는 성공하지만 아무 것도 하지 않는다. 서로 다른 마운트 파일시스템 사이의 rename은 EXDEV로 실패할 수 있어 단순 복사·삭제를 동일한 원자적 교체로 바꾸어 부를 수 없다. exists 확인 뒤 생성도 한 묶음이 아니므로 충돌 거부가 목적이면 지원 조건 아래 O_CREAT|O_EXCL의 결과를 확인한다. 플랫폼·네트워크 오류에 따른 예외는 실제 계약을 다시 읽는다.

이름을 제거해도 참조는 남는다

Unix 계열에서 unlink는 디렉터리의 이름 연결을 제거한다. 다른 하드 링크가 남으면 그 이름으로 파일을 계속 찾는다. 마지막 이름이 없어도 이미 열려 있는 파일은 참조를 통해 사용할 수 있다.

다른 문제에 적용하기

파일의 값·위치·이름을 나누어 확인하기

자체 4097바이트 파일은 논리 블록 0, 2, 4에만 데이터 블록 10, 20, 30을 할당하고 포인터 블록 7을 사용한다. 보고서가 논리 다섯 블록이니 데이터 할당량은 5120바이트라고 했다. 공유 열린 설명에서 P가 lseek로 위치 0을 지정하고, Q가 lseek로 위치 4를 지정한 뒤, P가 2바이트를 읽으면 AB를 얻는다고 했다. tmp의 N을 current의 O로 rename하면 기존 열린 독자도 N을 읽는다고 했다. 세 설명을 고쳐라.

힌트 1

논리 블록·실제 데이터·포인터 비용과 공유 offset을 따로 센다.

힌트 2

이름 화살표와 이미 열린 설명의 화살표를 따로 그린다.

풀이와 답 확인

  1. 실제 데이터 할당은 세 블록으로 3072바이트이며 포인터 블록을 포함하면 4096바이트다. 다섯 논리 블록과 다르다.

  2. P의 read 시점에 공유 offset은 4다. 정확히 2바이트 읽기에 성공하면 EF를 얻는다.

  3. 위치 지정 읽기는 pread의 offset을 각 요청에 붙이고 실제 반환량을 확인한다.

  4. rename 성공 뒤 current는 N을 가리키고 기존 독자는 O를 유지한다.

  5. 새로 여는 독자와 기존 독자의 객체·위치·참조 수명을 구별한다.

  6. 원자적 이름 교체·파일 내용 완성·저장 동기화·실제 실행 증거를 별도 확인한다.

논리 값과 물리 배정, 번호와 열린 위치, 현재 이름과 기존 열린 객체를 같은 상태로 합치지 않는다.

해결한 뒤 점검할 것

  • sparse의 데이터 3072바이트와 포인터 1024바이트를 더한 4096바이트를 dense의 6144바이트와 구별한다.

  • 공유 위치 경합과 pread의 해결 범위·짧은 반환을 설명한다.

  • current→N·기존 열린 설명→O를 서로 다른 화살표로 그린다.

  • 기존 Windows 실행 증거와 신규 Linux 경합·rename 미수행을 구별한다.
