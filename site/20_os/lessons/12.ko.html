소단원 12.1

inode·디렉터리·블록 할당

두 파일 이름이 같은 내용을 가리킬 때 저장공간도 두 배로 필요할까?

준비 개념과 학습 목표

준비 개념

  • 바이트와 KiB: 1 KiB는 1024바이트

  • 이름과 데이터의 구별

  • 몫과 나머지

학습 목표

  • 디렉터리 이름과 inode 및 데이터 블록의 역할을 구별한다.

  • 직접·간접 포인터를 따라 파일 오프셋을 찾는다.

  • 논리 크기와 모형의 할당 공간을 계산한다.

이름을 찾는 표와 파일의 설명서

전통적인 Unix 계열 모형에서 디렉터리는 이름과 inode 번호를 연결하는 항목을 갖는다. inode는 파일 종류, 권한, 소유자, 크기와 데이터 위치를 설명하는 메타데이터다. 이름 자체와 파일의 내용은 같은 개념이 아니다.

하드 링크는 두 이름을 같은 파일에 연결한다. 같은 파일시스템 안에서 a와 b가 inode 7을 가리키면 두 이름이 존재해도 내용 전체가 복사된 것은 아니다. inode 번호는 파일시스템과 함께 식별해야 하며 모든 장치에서 영원히 유일한 번호가 아니다.

데이터를 잘라 저장하는 방법

이 단원은 빈 구멍이 없는 일반 파일을 1024바이트 블록으로 저장하는 자체 모형을 사용한다. inode 안에 직접 포인터 두 개, 단일 간접 포인터 한 개를 둔다. 직접 포인터는 데이터 블록을 가리키고 간접 포인터는 데이터 블록 번호들이 들어 있는 별도 블록을 가리킨다.

블록 번호 한 개를 4바이트로 저장하면 간접 블록에 1024 ÷ 4 = 256개가 들어간다. 이 단순 모형의 데이터 블록 최대 개수는 2 + 256 = 258개다. 실제 파일시스템은 다중 간접 포인터나 연속 범위를 기록하는 extent 등 다른 구조를 쓰므로 이 최대값을 실제 OS 제한으로 외우지 않는다.

길이와 할당 공간은 다르다

파일의 논리 길이는 읽을 수 있는 바이트 범위다. 2500바이트 파일은 이 모형에서 데이터 블록 세 개를 사용하며 마지막 블록의 일부가 남는다. 포인터 블록과 inode·디렉터리의 공간은 데이터 길이에 포함하지 않는다.

빈 블록을 찾고 배정 여부를 기록하는 비트맵도 메타데이터다. 파일을 만들려면 데이터뿐 아니라 필요한 메타데이터 공간도 마련해야 한다. 실제 sparse 파일은 일부 논리 범위를 물리 블록 없이 나타낼 수 있어 여기의 단순 올림 계산을 그대로 적용할 수 없다.

중간 과정을 따라가는 예제

위 모형에서 파일 길이는 2500바이트다. 직접 데이터 블록 번호는 5와 8, 간접 블록 번호는 3이고 그 첫 데이터 번호는 11이다. 파일 오프셋 2300의 위치와 공간을 구하라. 블록 번호 0의 시작을 저장장치 바이트 위치 0으로 정한다.

  1. 2500 ÷ 1024를 올림하면 데이터 블록 세 개다. 데이터 할당은 3072바이트, 남는 공간은 3072 − 2500 = 572바이트다.

  2. 2300 = 2 × 1024 + 252이므로 논리 블록 2의 내부 오프셋 252다. 0·1은 직접 포인터를 쓰고 2는 간접 블록 3의 첫 항목을 통해 데이터 블록 11에 도달한다.

  3. 저장장치 모형의 바이트 위치는 11 × 1024 + 252 = 11516이다. 이것은 RAM 주소가 아니다.

  4. 간접 블록 하나도 필요하므로 데이터 세 블록과 포인터 한 블록의 합은 4096바이트다. inode·디렉터리·비트맵 공간은 이 합에서 제외했다.

오프셋 2300은 데이터 블록 11의 252번째 오프셋에 있다. 데이터 할당 3072바이트, 이 파일의 포인터 블록을 더한 합 4096바이트다.

종이와 본문으로 직접 해보기

파일이 2048바이트일 때 필요한 데이터·간접 블록 수를 구하라. 길이를 2049바이트로 늘리면? 이 모형의 최대 논리 길이도 계산하라.

힌트 보기

직접 포인터는 정확히 두 블록까지다. 세 번째 데이터 블록을 쓰는 순간 포인터 블록도 추가한다.

풀이 보기

2048바이트는 데이터 두 블록이고 간접 블록이 필요 없다. 2049바이트는 데이터 세 블록과 간접 한 블록으로 4096바이트를 배정한다. 최대는 258 × 1024 = 264192바이트, 즉 258 KiB다. 모든 항목을 사용한 단순 모형이며 실제 파일 크기 제한이 아니다.

오해와 반례

파일 이름이 두 개면 데이터 블록도 반드시 두 벌이다.

하드 링크는 같은 inode를 가리키므로 내용 블록을 공유한다. 복사한 별도 파일과 하드 링크를 구별해야 한다. 심볼릭 링크는 대상 경로를 담는 별도 객체이므로 같은 구조로 취급하지 않는다.

소단원 12.2

VFS와 파일 디스크립터

같은 파일을 두 번 열기와 열린 번호를 복제하기는 왜 결과가 다를까?

준비 개념과 학습 목표

준비 개념

  • 읽은 위치를 나타내는 오프셋

  • 경로와 파일

  • 프로세스

학습 목표

  • Linux VFS의 공통 인터페이스와 객체를 설명한다.

  • 파일 디스크립터와 열린 파일 설명을 구별한다.

  • 독립 open과 dup의 오프셋을 추적한다.

서로 다른 파일시스템을 연결하는 문

Linux VFS는 파일 관련 시스템 호출을 각 파일시스템 구현으로 연결하는 공통 계층이다. 프로그램은 익숙한 열기·읽기 인터페이스를 사용하고 커널은 해당 파일시스템의 동작을 선택한다. 디스크 파일만이 아니라 장치 등도 이 인터페이스에 연결될 수 있다.

VFS의 dentry는 메모리에 유지하는 이름 조회 객체이며 디스크 디렉터리 항목 그 자체가 아니다. inode 객체는 파일을 설명하고 열린 file 객체는 사용 중인 파일에 대한 참조와 동작을 갖는다. Linux 설명을 모든 운영체제의 내부 구조라고 일반화하지 않는다.

번호와 열기 상태를 분리하기

파일 디스크립터는 프로세스가 사용하는 작은 정수 번호다. 이 번호로 열린 파일 설명을 찾는다. 일반 파일의 열린 설명에는 현재 읽기 위치와 파일 상태 플래그가 포함된다. 같은 이름을 다시 open하면 보통 별도의 열린 설명이 생겨 위치도 별개로 움직인다.

dup은 새 번호를 만들지만 원래 열린 설명을 공유한다. 따라서 한 번호로 읽거나 위치를 옮기면 다른 번호가 보는 위치도 바뀐다. 모든 플래그가 공유되는 것은 아니다. Linux의 파일 디스크립터 플래그와 파일 상태 플래그는 구별되며 Python의 상속 규칙도 API 문서로 확인해야 한다.

작은 읽기로 공유 위치 확인하기

아래 Python 코드를 fd_example.py로 저장하고 python fd_example.py로 실행할 수 있다. Python 표준 라이브러리만 쓰며 자신의 임시 폴더와 여섯 바이트 파일을 만든 뒤 닫고 정리한다. Windows에서는 O_BINARY를 더해 텍스트 변환을 피한다. Linux VFS 내부 추적 실험은 아니다.

handles는 종료할 번호들을 담는다. try/finally는 읽기 중 오류가 나도 확보한 번호를 닫기 위한 구조다. os.read는 일반적으로 요청보다 적은 바이트를 반환할 수 있으므로 임의의 장치·네트워크 프로그램에서 정확히 두 바이트를 보장하는 코드로 사용하지 않는다. 여기서는 작은 일반 파일의 실제 관찰을 다룬다. Python의 버퍼가 있는 고수준 파일 읽기를 같은 열린 설명에 섞지 않는다.

import os
import tempfile
from pathlib import Path

with tempfile.TemporaryDirectory(prefix="fd-lesson-") as folder:
    path = Path(folder) / "letters.bin"
    path.write_bytes(b"ABCDEF")
    handles = []
    try:
        flags = os.O_RDONLY | getattr(os, "O_BINARY", 0)
        first = os.open(path, flags)
        handles.append(first)
        shared = os.dup(first)
        handles.append(shared)
        separate = os.open(path, flags)
        handles.append(separate)
        print(os.read(first, 2))
        print(os.read(shared, 2))
        print(os.read(separate, 2))
        print(os.lseek(first, 0, os.SEEK_CUR),
              os.lseek(shared, 0, os.SEEK_CUR),
              os.lseek(separate, 0, os.SEEK_CUR))
        os.close(first)
        handles.remove(first)
        print(os.read(shared, 2))
    finally:
        for fd in handles:
            os.close(fd)

중간 과정을 따라가는 예제

코드의 first는 첫 open, shared는 dup(first), separate는 새 open이다. ABCDEF 파일을 각 호출 순서대로 두 바이트씩 읽고 위치를 추적하라.

  1. first로 AB를 읽으면 공유 설명의 위치가 0에서 2가 된다. shared는 같은 설명을 보므로 CD를 읽고 위치가 4가 된다.

  2. separate는 독립 위치 0에서 AB를 읽어 위치 2가 된다. 현재 세 번호로 조회한 위치는 4, 4, 2다.

  3. first 번호를 닫아도 shared 번호가 같은 열린 설명을 참조한다. shared가 EF를 읽고 위치 6에 도달한다.

  4. 예상 출력은 b'AB', b'CD', b'AB', 4 4 2, b'EF'의 다섯 줄이다. 숫자 fd 자체는 실행마다 달라질 수 있어 출력하지 않는다.

복제 번호는 위치를 공유하고 새 open은 별도 위치를 갖는다. 번호 하나를 닫는 것과 모든 참조를 닫는 것은 다르다.

힌트 보기

풀이 보기

오해와 반례

정수 번호가 다르면 읽기 위치도 반드시 다르다.

dup으로 만든 번호는 같은 열린 설명을 가리킨다. 반대로 같은 파일 내용을 두 번 open한 경우는 서로 다른 설명과 위치를 가질 수 있다. 번호·설명·파일의 세 층을 나눠 그려야 한다.

한 단계 더

번호 두 개가 설명 하나를 가리키는 그림과 번호 두 개가 설명 두 개를 가리키는 그림을 그리자. 읽기 위치뿐 아니라 종료 책임도 표시하자. 실제 동시 스레드·fork·네트워크·커널 추적은 이 작은 실행으로 검증한 것이 아니다.

소단원 12.3

파일 생성·열기·삭제

파일 이름을 지웠는데 이미 열린 프로그램은 왜 계속 읽을 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 디렉터리 이름과 inode

  • 열린 파일 설명과 번호

  • 하드 링크

학습 목표

  • 생성·열기·잘라내기 동작을 구별한다.

  • Unix 이름 삭제와 열린 파일 수명을 추적한다.

  • 삭제와 영속화·보안 소거의 차이를 설명한다.

생성과 열기는 서로 다른 요청

새 파일을 만들려면 부모 디렉터리에서 이름 항목을 추가하고 파일 메타데이터를 준비한다. 권한·읽기 전용 여부·공간 부족 등으로 실패할 수 있다. open은 사용할 파일을 찾아 접근권한과 요청을 검사하고 열린 설명과 번호를 마련한다.

파일이 없을 때 만들도록 지정하는 O_CREAT와 기존 내용을 길이 0으로 자르는 O_TRUNC는 다르다. O_CREAT만 지정했다고 기존 파일의 내용이 반드시 지워지지 않는다. 기존 이름과 충돌을 거부하려면 적절한 배타 생성 옵션을 사용해야 한다. 실제 API의 모드와 오류를 확인한다.

이름을 제거해도 참조는 남는다

Unix 계열에서 unlink는 디렉터리의 이름 연결을 제거한다. 다른 하드 링크가 남으면 그 이름으로 파일을 계속 찾는다. 마지막 이름이 없어도 이미 열려 있는 파일은 참조를 통해 사용할 수 있다.

아래 표는 일반 파일에 다른 메모리 매핑·커널 참조가 없다는 교육 모형이다. 링크 수가 0이고 마지막 열린 참조도 끝나면 저장 공간을 재사용할 수 있다. 심볼릭 링크의 이름을 삭제하는 것은 링크 자체를 지우는 것이며 대상 내용의 삭제와 다르다.

플랫폼과 저장 약속을 확인하기

이 단원의 삭제 수명 표는 Unix 동작이다. Python os.remove 문서는 Windows에서 사용 중인 파일의 제거가 예외를 낼 수 있다고 구별한다. 그러므로 현재 Windows 실행 결과 없이 Linux 삭제 표를 실제 컴퓨터에서 관찰했다고 쓰지 않는다.

이름을 지우는 것은 저장장치 모든 복사본을 안전하게 덮어쓰는 보안 소거가 아니다. close나 이름 변경만으로 전원 손실 후 영속성이 모두 보장되는 것도 아니다. 파일시스템의 일관성·복구·동기화와 백업 정책은 별도 조건을 갖는다.

중간 과정을 따라가는 예제

Unix 모형에서 a와 b 두 이름이 inode 7을 가리키고 파일을 한 번 열어 fd 하나를 가진다. 다른 참조는 없다. a 삭제, b 삭제, fd 종료를 순서대로 추적하라.

  1. 처음 링크 수는 2, 열린 설명의 사용 참조는 1이다. a를 unlink하면 링크 수가 1이 되며 b로 찾을 수 있다.

  2. b도 unlink하면 링크 수는 0이다. 경로 이름 둘은 사라졌지만 fd는 원래 파일을 계속 사용할 수 있다. 데이터 공간을 아직 해제한 것으로 세지 않는다.

  3. 마지막 fd를 닫으면 이름도 열린 참조도 없으므로 이 모형에서는 파일 공간을 재사용할 수 있다. 실제 즉시 물리 덮어쓰기라는 뜻은 아니다.

  4. b 삭제 후 fd 종료 전에 a라는 새 파일을 만들어도 기존 fd는 옛 객체를 참조한다. 새 객체의 inode 번호가 반드시 8이어야 하는 규칙은 없으며 번호 재사용도 가능하다.

링크 수 2→1→0과 열린 참조 1→1→1→0을 따로 추적한다. 마지막 이름 삭제와 기존 열린 참조 종료는 다른 사건이다.

처음 a와 b가 있는 파일을 열지 않았다면 a 삭제 후와 b 삭제 후 수명은? a를 새로 만들면 이전 내용이 자동 복원되는가?

힌트 보기

열린 참조가 0인 상태에서 링크 수를 따져 본다.

풀이 보기

a 삭제 후 링크 하나가 남으므로 b로 접근한다. b 삭제 후 링크·열린 참조가 모두 0이므로 모형에서 공간 재사용이 가능하다. 같은 이름을 새로 만드는 것만으로 이전 파일의 내용이 복구되지는 않는다. 백업이나 별도 복구 근거가 필요하다.

오해와 반례

삭제는 파일의 모든 내용을 즉시 물리적으로 지워서 복구 가능성을 없앤다.

unlink는 우선 이름 연결을 없앤다. 다른 링크·열린 참조·백업·저장장치 특성 때문에 이름 제거와 모든 데이터 사본의 소거는 같지 않다. 실제 보안 소거를 수행하지 않은 종이 추적은 삭제 보안의 증거가 아니다.

이름·inode·열린 설명·번호를 각각 상자로 그린 뒤 삭제 때 지워지는 화살표와 close 때 지워지는 화살표를 표시하자. 실제 파일을 삭제하지 않고 종이로 수행한다. 백업에서 복원할 때 이름만 맞는지 내용도 맞는지 구별하는 확인 질문을 만들어 보자.
