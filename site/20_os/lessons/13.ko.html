선행 쓰기 두 개를 반드시 서로 순서대로 저장해야 할까?

자체 게시 모형은 D1·D2에 각각 새 조각을 준비한 뒤 M으로 두 조각의 사용을 선언한다. 각 D의 상태는 old 또는 new, M은 0 또는 1이다. 불변식은 M = 1이면 D1과 D2가 모두 new라는 조건이다. 서로 독립적인 두 데이터 준비는 어느 쪽이 먼저 지속돼도 된다. 하지만 M 제출 전에는 둘 모두의 지속 성공을 확인해야 한다. 하나의 고정 호출 순서를 외우기보다 어떤 쓰기가 어느 쓰기에 의존하는지 먼저 그린다.

원자적인 조각 쓰기와 실패 시 메모리 캐시가 사라지는 자체 장애 모형에서 순서 제약 없이 세 쓰기를 제출하면 2³=8개 지속 부분집합이 가능하다. M이 남았는데 D1·D2 중 하나라도 old인 세 경우가 불변식에 실패한다. 두 데이터 완료 확인 뒤 M을 제출하면 {},{D1},{D2},{D1,D2},{D1,D2,M}의 다섯 경우만 가능하다. 중괄호는 지속된 새 쓰기의 집합이지 호출을 실행한 횟수가 아니다.

불변식은 사용을 선언한 조각의 안전성을 말한다. M=0일 때 데이터 일부가 이미 준비된 상태도 허용한다. 반대로 M=1을 성공으로 응답하려면 M 자체의 지속도 확인해야 한다. 데이터가 안전하게 준비됐다는 조건과 새 버전의 게시 완료 약속은 다른 조건이다. 어느 하나의 동기화가 실패했다면 후속 게시를 성공으로 처리하지 않는다.

이 모형의 완료는 지속 저장이 확인됐다는 계약으로 정의한다. 일반 write 반환이나 장치 인터럽트를 그 증거로 자동 대체하지 않는다. Linux fsync의 실제 계약과 디렉터리 항목의 별도 범위를 확인하고 장치·파일시스템별 실행 증거는 분리한다. 원문의 오래된 512바이트 원자성 사례를 현재 모든 장치의 보장으로 쓰지 않는다.

여러 층의 완료는 서로 다르다

응용 프로그램은 사용자 공간 버퍼에 먼저 쓰고, 운영체제는 변경된 페이지를 메모리에 보관할 수 있다. 장치도 쓰기 캐시를 사용할 수 있다. 응용에서 새 값을 읽었다는 관찰은 그 값이 정전 뒤에도 남는다는 관찰이 아니다. 어느 층의 버퍼가 어느 장애에서 사라지는지 적어야 한다.

성능을 위해 쓰기를 모으거나 순서를 바꾸는 동작은 유용하지만, 앞 작업이 남아야 뒤 작업이 해석되는 의존 관계를 깨면 문제가 된다. 데이터 블록을 기록하기 전에 그 블록을 가리키는 메타데이터만 남으면 오래된 내용이 새 파일의 일부처럼 읽힐 수 있다.

의존 관계를 지속 저장 순서로 만든다

아래 자체 모형에서 D는 데이터 블록이며 M은 그 블록을 사용하는지 나타내는 표식이다. 처음 D = 옛값, M = 0이다. 목표 D = 새값, M = 1이다. M = 1이면 D가 새값이어야 한다는 불변식을 정한다. M = 0일 때 D에 새값이 있어도 아직 사용하지 않는 준비 블록일 수 있다.

단순히 D 쓰기 호출 후 M 쓰기 호출을 했다는 순서만으로 충분하다고 가정하지 않는다. 이 모형은 성공한 D 동기화가 D의 지속을 보장한다는 계약을 추가하고 그 확인 뒤 M을 제출한다. 실제 장치·파일시스템에서 그런 계약과 실패 처리를 확인해야 한다.

오류와 이름 변경은 별도로 확인한다

Linux fsync는 파일 데이터와 관련 메타데이터를 장치로 동기화하며 성공 또는 오류를 반환한다. 파일 동기화가 그 파일 이름을 가진 디렉터리 항목까지 반드시 남기는 것은 아니므로 이름 생성·교체에는 디렉터리 동기화도 별도 고려한다.

동기화 실패를 성공처럼 처리하면 프로그램의 다음 단계가 거짓 전제 위에서 실행된다. 이전 값이 남았는지 새 값이 남았는지 모르면 미확정으로 보고해야 한다. 이 수업은 성공한 동기화 계약을 가정한 상태표이며 실제 전원 차단 검증을 대신하지 않는다.

D1·D2 지속 성공을 모두 확인한 뒤에만 M을 제출한다. 부분 조각 찢김·오류·장치 거짓 성공은 이 표 밖의 추가 조건이다.

중간 과정을 따라가는 예제

D = 옛값, M = 0에서 두 쓰기를 제출했다. 장치는 M = 1만 먼저 지속 저장한 뒤 장애가 날 수 있다. 불변식 M = 1 ⇒ D = 새값을 검사하고 개선된 절차를 적어라.

  1. 호출 순서가 D 다음 M이어도 장치의 지속 순서를 제한하지 않았으므로 상태 (옛값,1)이 허용된다. 불변식에 실패한다.

  2. D = 새값을 제출하고 D 동기화 성공을 기다린다. 실패하거나 확인하지 못하면 M = 1 단계로 넘어가지 않는다.

  3. 성공 확인 뒤 M = 1을 제출하고 동기화한다. 모형에서 남을 수 있는 진행 상태는 (옛값,0), (새값,0), (새값,1)이다.

  4. 첫 두 상태는 M이 0이라 새 블록 사용을 선언하지 않는다. 마지막은 실제 새 데이터가 있어 불변식을 지킨다.

의존하는 M이 먼저 지속되는 위험을 D의 성공 동기화 후 M 제출로 제한한다. 이는 모형의 계약 아래 불변식 보장이며 모든 실제 저장 장치 시험 통과가 아니다.

왜 여덟 상태 중 세 개가 위험한가?

순서 없는 세 쓰기의 실패 집합을 구하라.

  1. M이 없는 네 집합은 미게시라 조건을 위반하지 않는다.

  2. M이 있는 네 집합 중 두 D가 모두 있는 하나만 통과한다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

풀이와 답 확인

죽은 블록이 적은 세그먼트를 먼저 정리하면 비용이 얼마나 달라질까?

자체 정리 비용 모형은 세그먼트 10블록 전체를 읽고 살아 있는 u블록을 다른 안전한 공간으로 옮긴 뒤 원래 10블록을 회수한다. 순 자유 증가량은 10 − u다. 사용자가 그 자유 공간을 새 데이터로 모두 채운다면 데이터 쓰기 합은 살아 있는 복사 u와 사용자 새 쓰기 10 − u로 총 10블록이다. 읽기와 메타데이터 비용은 이 기본 쓰기 증폭 계산에서 제외하며 삭제한다고 살아 있는 데이터를 버리지 않는다.

u = 4이면 순 자유 공간은 6블록이고 데이터 쓰기 10 / 사용자 쓰기 6 = 5/3배다. u = 8이면 순 자유 공간은 2블록이고 데이터 쓰기 10 / 사용자 쓰기 2 = 5배다. 둘 다 세그먼트 하나의 10블록을 반환하지만 실제로 확보하는 순 공간과 필요한 사용자 바이트당 이동 비용이 다르다. 대상 블록이 이후 덮어써지는 빈도·여유 공간·지연까지 포함하면 정책 선택은 더 복잡해진다.

최신 참조 확인도 정리의 전제다. 자체 summary에 주소 20의 블록이 파일 7의 offset 0이라고 적혀 있고 현재 inode의 그 포인터는 50이라고 정하면 주소 20은 현재 파일 7의 그 버전에서 제외됐다. 포인터가 20인 블록은 살아 있다. snapshot 등 다른 참조가 없다는 가정이 필요하며 복사 후 새 참조를 안전하게 게시하기 전에 옛 세그먼트를 반환해서는 안 된다.

복구 기록의 재실행 방식도 비용과 별개다. 물리 redo가 “x를 130으로 설정”이면 두 번 적용해도 130이지만 “x에 30을 더함”은 100에서 130, 160으로 누적된다. 후자는 무조건 같은 재생 규칙으로 반복하면 안 되고 식별·적용 기록 등 다른 프로토콜이 필요하다. 같은 단어 로그라도 저장 배치·복구 기록·업무 증가 연산의 계약이 같다고 가정하지 않는다.

저널은 원위치 갱신의 복구 근거다

저널링은 변경 결과를 복구 기록에 먼저 남기고 유효한 완료 기록이 지속된 뒤 원위치를 갱신하는 방식으로 설명할 수 있다. 장애 뒤 완성된 기록을 재생하면 일부만 바뀐 원위치를 다시 맞출 수 있다. 보호 범위가 메타데이터인지 데이터까지인지에 따라 보장이 달라진다.

로그에 무엇이든 쓰기만 하면 되는 것은 아니다. 완전한 결과 기록, commit의 유효성, 기록 재사용 시점과 중복 재생 처리를 정해야 한다. 파일시스템 수준 일관성과 응용의 계좌 이체 같은 여러 동작의 트랜잭션은 같은 범위가 아니다.

로그 구조는 최신 위치를 계속 바꾼다

로그 구조 파일시스템은 새 데이터와 메타데이터를 모아 새 세그먼트 위치에 기록한다. 자주 원위치를 덮는 대신 새 버전을 기록하므로 최신 inode의 주소도 바뀐다. inode 번호에서 최신 주소를 찾는 inode map 같은 간접 구조와 그 구조를 찾는 기준점이 필요하다.

자체 모형에서는 파일 번호 7의 최신 inode 주소를 표에서 찾고, inode의 블록 포인터를 따라 데이터를 읽는다. 예전 버전은 물리적으로 남아도 현재 참조에서 제외될 수 있다. 주소가 크다는 이유만으로 항상 최신이라고 판단하지 않고 신뢰하는 최신 표를 사용한다.

모아서 쓰는 이득과 정리 비용

연속 큰 쓰기는 특히 회전 디스크의 위치 이동 비용을 나눠 부담하는 데 도움이 된다. 모든 읽기도 연속이거나 모든 저장 매체에서 항상 더 빠르다는 뜻은 아니다. 버퍼 지연, 메타데이터 추적, 살아 있는 블록 복사와 공간 정리 비용이 추가된다.

기준점 갱신과 장애 뒤 로그 탐색도 필요하다. 이 절의 주소 표는 최신 표가 이미 안전하게 확인되었다고 가정하며 실제 LFS의 모든 복구 절차를 구현하지 않는다. 오래된 공간을 정리할 때 현재 참조가 남은 블록을 삭제하면 안 된다.

commit 표시가 있고 체크섬이 맞아도 모든 복구 검사를 생략할 수 있을까?

자체 작은 로그 검증기는 트랜잭션 식별자·필수 결과 A/B·commit의 연결을 확인한 완전한 기록만 재생한다고 정한다. Tx7에 A = 2만 있고 B 결과가 없는데 commit7이 있으면 완전한 Tx7로 인정하지 않는다. 이 프로토콜은 유효 기록 확인 전에는 원위치를 갱신하지 않는다. commit 모양 하나만 찾는 검사와 기록 전체를 연결하는 검사는 다르다.

약한 자체 체크섬을 (A + B) mod 10으로 정하면 올바른 A = 2, B = 2의 체크섬은 4다. 잘못된 A = 3, B = 1도 체크섬이 4라 일치해도 A = B 불변식은 실패한다. 이는 임의로 정한 작은 합 체크섬의 충돌 반례다. 실제 파일시스템이 이런 체크섬을 쓴다는 주장도, 특정 강한 체크섬의 손상 확률을 측정한 결과도 아니다. 기록 정체성·길이·완전성·불변식 등 검증 목적을 따로 적는다.

유효한 순차 Tx7의 결과 A = 2, B = 2와 그 뒤 Tx8의 결과 A = 3, B = 3이 모두 남아 있다면 그 순서를 보존하여 재생한다. Tx8 뒤 Tx7을 잘못 적용하면 최종 A = 2, B = 2라 두 값은 같지만 마지막 commit된 값 3을 잃는다. A = B 검사는 통과해도 최신성 약속은 실패한다. 기록의 원래 순서·checkpoint 범위·재사용된 식별자의 세대를 유지해야 한다.

복구 도중 다시 장애가 날 수 있다. Tx7의 결과 설정에서 A만 2로 바뀌고 B는 1인 채 재장애가 나도 로그를 보존하고 같은 완전한 결과 A = 2, B = 2를 다시 설정하면 복구된다. A/B 둘의 지속 확인 전에 로그를 회수하면 이 근거를 잃는다. 실제 시험에서는 재장애 위치와 관찰을 남겨야 하며 이번 작업은 자체 상태와 반례의 손추적이다.

먼저 장애 모형과 정답 기준을 쓴다

실험 설계에는 무엇이 사라지는지부터 정한다. 프로세스만 종료되는 장애는 OS 캐시를 지우지 않을 수 있고 전원 장애는 다른 범위의 버퍼를 잃는다. 가상 머신 재시작이 실제 장치의 정전과 동일하다고 가정하지 않는다. 쓰기 단위의 원자성·순서·동기화·오류 조건도 명시한다.

이 절은 A와 B가 같은 버전이어야 한다는 안전성, 그리고 성공 응답을 받은 버전은 복구 뒤 남아야 한다는 지속성 두 조건을 사용한다. 장애 뒤 두 값이 모두 옛값이면 안전성을 지킬 수 있지만 이미 새 버전 성공을 응답했다면 지속성 조건을 어길 수 있다.

각 사건 사이에 장애를 끼워 넣는다

초기 A = B = 1이다. 결과 로그에 A = B = 2를 지속 저장하고 commit을 지속 저장한 뒤 A, B 순서로 원위치에 저장한다. 두 원위치 값이 지속된 뒤 로그를 회수한다. 기록과 commit은 검증되며 유효 commit이 있으면 재생하고 없으면 원위치 쓰기를 시작하지 않는 자체 프로토콜이다.

각 단계가 이 모형의 완전한 지속 사건이면 사건 이전과 사건 사이에 장애를 넣어 복구값을 표로 만들 수 있다. 실제 부분 쓰기·재정렬·오류를 허용하면 경우가 더 늘어난다. 이 표는 지정한 모형의 경우를 모두 다룰 뿐 모든 실제 장애를 완전히 다룬 결과가 아니다.

성공 응답 위치가 보장을 바꾼다

안전한 프로토콜도 성공 응답을 너무 일찍 보내면 약속을 어긴다. 로그 결과만 있고 commit 전인 시점에 성공을 보냈다면 장애 뒤 로그가 무시되어 옛값으로 돌아갈 수 있다. 반면 유효 commit의 지속 확인 후 성공 응답은 그 기록을 재생할 수 있다는 모형의 복구 보장과 연결된다.

실제 실습을 한다면 전용 복제 환경에서 입력·실패 위치·재시작·검사·관찰 로그를 남긴다. 여기서는 그런 장비를 실행하지 않았다. 표의 예상 결과, 수행 여부, 실제 관찰 칸을 구별하며 실제 관찰은 미수행으로 둔다.

Tx7 재생 중 A = 2만 지속되고 B = 1인 상태에서 장애가 났다. 완전한 Tx7 로그가 남아 다시 같은 설정을 재생하면?

힌트 1

기록의 결과는 A = 2, B = 2다.

힌트 2

설정은 같은 값에 다시 적용해도 누적되지 않는다.

풀이와 답 확인

  1. A에 2를 다시 설정해도 2다.

  2. B에 2를 설정해 2가 된다.

  3. 둘의 지속 확인 후 A = 2, B = 2로 완료한다.

복구 결과는 A = 2, B = 2다. 이번 모형의 유효 로그 보존과 설정 기록 계약이 전제다.

흔한 오답에서 다시 생각하기

A는 이미 2라 두 번째 재생에서는 4로 증가한다.

기록은 더하기가 아니라 결과 값 2를 설정하는 것이다.

연습 2 · 오류 찾아 고치기

Tx7의 A = 2, Tx8의 B = 3, commit7을 조합해 Tx7의 완전한 기록이라고 썼다. 고쳐라.

힌트 1

A와 B가 어느 트랜잭션에 속하는지 확인한다.

힌트 2

필수 결과와 commit을 같은 식별·세대에 연결한다.

풀이와 답 확인

  1. Tx7에는 B 결과가 없다.

  2. Tx8의 B = 3을 Tx7에 붙이면 트랜잭션의 정체성이 섞인다.

  3. 이번 검증기에서는 완전한 Tx7로 인정하지 않는다.

commit7만으로 다른 기록의 부족한 부분을 채우지 않는다.

흔한 오답에서 다시 생각하기

A/B 필드가 각각 있으면 식별자는 중요하지 않다.

서로 다른 업데이트 결과를 합치면 존재하지 않았던 버전을 재생할 수 있다.

연습 3 · 직접 만들어 보기

복구 보고서에 안전성·최신성·관찰 여부 세 칸을 만들고 역순 재생 결과 A = 2, B = 2를 기록하라.

힌트 1

최신 commit은 Tx8의 3/3이다.

힌트 2

실제 장비 실험은 수행하지 않았다.

풀이와 답 확인

  1. 안전성 A=B는 통과다.

  2. 최신 commit 결과 A = 3, B = 3의 지속은 실패다.

  3. 관찰은 실제 장비 미수행·자체 손추적 예상으로 기록한다.

하나의 통과를 전체 복구 성공으로 합치지 않는다.

흔한 오답에서 다시 생각하기

값이 같으니 실제 크래시 시험까지 전부 성공이다.

서로 다른 검사와 실제 수행 증거를 모두 한 결론으로 바꾸었다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

같은 약한 체크섬 4를 가지면서 A = B 조건도 만족하는 다른 0–9 한 자리 쌍을 찾아라. 그것도 최신 결과 (2, 2)를 증명하는가?

힌트 1

A = B = x라면 2x mod 10 = 4다.

힌트 2

x가 2인 경우 외에 7인 경우도 계산한다.

풀이와 답 확인

  1. 7 + 7 = 14라 체크섬은 4다.

  2. A = 7, B = 7은 값 같음도 통과한다.

  3. 하지만 목표 최신 결과 A = 2, B = 2와 다르다.

7/7이 반례다. 체크섬과 값 같음만으로 정확한 최신 버전까지 인증하지 못한다.

흔한 오답에서 다시 생각하기

체크섬과 A=B 둘이 맞으면 목표 버전도 반드시 맞다.

내용 검증의 목적에는 정확한 버전·식별자·기록 연결 등 별도 조건이 있다.

그럴듯한 복구 성공 보고를 반례로 검사하기

보고서가 D1의 지속 성공만으로 D2가 미확정인데 M을 게시했다. live가 8인 10블록 세그먼트 정리로 새 공간 10블록을 얻는다고 했다. Tx7의 결과 (2, 2), 그 뒤 Tx8의 결과 (3, 3)을 역순 재생해 (2, 2)가 되자 안전성 통과로 최신 복구 성공이라 했다. 세 오류를 고치고 수행 증거의 범위를 적어라.

힌트 1

M에는 모든 선행 조각의 지속이 필요하다.

힌트 2

순 공간·재생 순서·안전성·최신성·실제 관찰을 분리한다.

풀이와 답 확인

  1. D1과 D2의 지속 성공을 둘 다 확인한 뒤 M을 제출한다.

  2. live인 8블록의 이동 공간을 빼면 순 자유 공간은 10 − 8 = 2블록이다.

  3. 사용자 새 쓰기 2블록을 분모로 한 데이터 쓰기 증폭은 (8 + 2)/2 = 5배다.

  4. 순차 Tx7 → Tx8을 재생하면 최신 결과 (3, 3)이다. 역순 결과 (2, 2)는 안전성 통과·최신성 실패다.

  5. 완전한 로그와 정체성·순서를 검증하고 재장애 동안 로그를 보존한다.

  6. 이번 결과는 명시된 자체 손모형이며 실제 장치·전원 장애·학습자 시험은 미수행이다.
