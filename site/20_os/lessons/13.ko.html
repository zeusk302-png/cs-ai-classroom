소단원 13.1

쓰기 순서와 캐시

저장 버튼을 눌러 새 값이 화면에 보이면 전원이 꺼져도 남는다고 말할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 메모리와 저장 장치

  • 파일과 디렉터리

  • 성공·실패 상태

학습 목표

  • 프로그램 버퍼·OS 캐시·장치 저장을 구별한다.

  • 의존하는 쓰기의 지속 순서를 추적한다.

  • 동기화 확인과 이름 항목의 보장을 구별한다.

여러 층의 완료는 서로 다르다

응용 프로그램은 사용자 공간 버퍼에 먼저 쓰고, 운영체제는 변경된 페이지를 메모리에 보관할 수 있다. 장치도 쓰기 캐시를 사용할 수 있다. 응용에서 새 값을 읽었다는 관찰은 그 값이 정전 뒤에도 남는다는 관찰이 아니다. 어느 층의 버퍼가 어느 장애에서 사라지는지 적어야 한다.

성능을 위해 쓰기를 모으거나 순서를 바꾸는 동작은 유용하지만, 앞 작업이 남아야 뒤 작업이 해석되는 의존 관계를 깨면 문제가 된다. 데이터 블록을 기록하기 전에 그 블록을 가리키는 메타데이터만 남으면 오래된 내용이 새 파일의 일부처럼 읽힐 수 있다.

의존 관계를 지속 저장 순서로 만든다

아래 자체 모형에서 D는 데이터 블록이며 M은 그 블록을 사용하는지 나타내는 표식이다. 처음 D = 옛값, M = 0이다. 목표 D = 새값, M = 1이다. M = 1이면 D가 새값이어야 한다는 불변식을 정한다. M = 0일 때 D에 새값이 있어도 아직 사용하지 않는 준비 블록일 수 있다.

단순히 D 쓰기 호출 후 M 쓰기 호출을 했다는 순서만으로 충분하다고 가정하지 않는다. 이 모형은 성공한 D 동기화가 D의 지속을 보장한다는 계약을 추가하고 그 확인 뒤 M을 제출한다. 실제 장치·파일시스템에서 그런 계약과 실패 처리를 확인해야 한다.

오류와 이름 변경은 별도로 확인한다

Linux fsync는 파일 데이터와 관련 메타데이터를 장치로 동기화하며 성공 또는 오류를 반환한다. 파일 동기화가 그 파일 이름을 가진 디렉터리 항목까지 반드시 남기는 것은 아니므로 이름 생성·교체에는 디렉터리 동기화도 별도 고려한다.

동기화 실패를 성공처럼 처리하면 프로그램의 다음 단계가 거짓 전제 위에서 실행된다. 이전 값이 남았는지 새 값이 남았는지 모르면 미확정으로 보고해야 한다. 이 수업은 성공한 동기화 계약을 가정한 상태표이며 실제 전원 차단 검증을 대신하지 않는다.

중간 과정을 따라가는 예제

D = 옛값, M = 0에서 두 쓰기를 제출했다. 장치는 M = 1만 먼저 지속 저장한 뒤 장애가 날 수 있다. 불변식 M = 1 ⇒ D = 새값을 검사하고 개선된 절차를 적어라.

  1. 호출 순서가 D 다음 M이어도 장치의 지속 순서를 제한하지 않았으므로 상태 (옛값,1)이 허용된다. 불변식에 실패한다.

  2. D = 새값을 제출하고 D 동기화 성공을 기다린다. 실패하거나 확인하지 못하면 M = 1 단계로 넘어가지 않는다.

  3. 성공 확인 뒤 M = 1을 제출하고 동기화한다. 모형에서 남을 수 있는 진행 상태는 (옛값,0), (새값,0), (새값,1)이다.

  4. 첫 두 상태는 M이 0이라 새 블록 사용을 선언하지 않는다. 마지막은 실제 새 데이터가 있어 불변식을 지킨다.

의존하는 M이 먼저 지속되는 위험을 D의 성공 동기화 후 M 제출로 제한한다. 이는 모형의 계약 아래 불변식 보장이며 모든 실제 저장 장치 시험 통과가 아니다.

종이와 본문으로 직접 해보기

D 동기화가 오류를 반환했는데도 M = 1을 쓰면 어떤 상태를 배제하지 못하는가? 파일 내용을 동기화한 뒤 새 이름을 만들고 디렉터리 동기화를 확인하지 않은 경우 무엇이 미확정인가?

힌트 보기

오류에서는 D의 지속 상태를 하나로 고정하지 않는다.

풀이 보기

D가 옛값인 채 M = 1이 남는 상태를 배제하지 못한다. 두 번째 경우에는 파일 내용과 별개로 장애 뒤 새 이름 항목이 남는지가 미확정이다. 현재 읽기 성공을 정전 뒤 이름 지속의 증거로 쓰지 않는다.

오해와 반례

쓰기 호출 순서와 현재 읽기 성공이면 정전 뒤 순서까지 증명된다.

OS와 장치 버퍼가 끼어 있다. 자체 반례에서는 M만 먼저 남는다. 지속 순서·성공 확인·오류 처리가 필요하고 실제 장치 검증은 별도다.

자기점검

답과 이유 보기

아니다.

새 블록 사용을 아직 선언하지 않았으며 역방향 조건은 요구하지 않는다.

한 단계 더

저널링·로그 구조

로그에 먼저 적는 저널과 모든 새 버전을 새 위치에 쓰는 구조는 같은 방식일까?

준비 개념과 학습 목표

준비 개념

  • 원위치 갱신

  • 간접 참조

  • 로그와 복구

학습 목표

  • 저널의 복구 기록과 로그 구조 파일시스템의 저장 배치를 구별한다.

  • 주소 변경을 간접 표로 추적한다.

  • 공간 회수와 성능 비용을 함께 설명한다.

저널은 원위치 갱신의 복구 근거다

저널링은 변경 결과를 복구 기록에 먼저 남기고 유효한 완료 기록이 지속된 뒤 원위치를 갱신하는 방식으로 설명할 수 있다. 장애 뒤 완성된 기록을 재생하면 일부만 바뀐 원위치를 다시 맞출 수 있다. 보호 범위가 메타데이터인지 데이터까지인지에 따라 보장이 달라진다.

로그에 무엇이든 쓰기만 하면 되는 것은 아니다. 완전한 결과 기록, commit의 유효성, 기록 재사용 시점과 중복 재생 처리를 정해야 한다. 파일시스템 수준 일관성과 응용의 계좌 이체 같은 여러 동작의 트랜잭션은 같은 범위가 아니다.

로그 구조는 최신 위치를 계속 바꾼다

로그 구조 파일시스템은 새 데이터와 메타데이터를 모아 새 세그먼트 위치에 기록한다. 자주 원위치를 덮는 대신 새 버전을 기록하므로 최신 inode의 주소도 바뀐다. inode 번호에서 최신 주소를 찾는 inode map 같은 간접 구조와 그 구조를 찾는 기준점이 필요하다.

자체 모형에서는 파일 번호 7의 최신 inode 주소를 표에서 찾고, inode의 블록 포인터를 따라 데이터를 읽는다. 예전 버전은 물리적으로 남아도 현재 참조에서 제외될 수 있다. 주소가 크다는 이유만으로 항상 최신이라고 판단하지 않고 신뢰하는 최신 표를 사용한다.

모아서 쓰는 이득과 정리 비용

연속 큰 쓰기는 특히 회전 디스크의 위치 이동 비용을 나눠 부담하는 데 도움이 된다. 모든 읽기도 연속이거나 모든 저장 매체에서 항상 더 빠르다는 뜻은 아니다. 버퍼 지연, 메타데이터 추적, 살아 있는 블록 복사와 공간 정리 비용이 추가된다.

기준점 갱신과 장애 뒤 로그 탐색도 필요하다. 이 절의 주소 표는 최신 표가 이미 안전하게 확인되었다고 가정하며 실제 LFS의 모든 복구 절차를 구현하지 않는다. 오래된 공간을 정리할 때 현재 참조가 남은 블록을 삭제하면 안 된다.

중간 과정을 따라가는 예제

자체 기록 표에서 최신 표 map[7] = 41이고 inode 41은 데이터 40을 가리킨다. 이전 inode 11은 데이터 10을 가리킨다. 새 버전 inode 71과 데이터 70을 준비한 뒤 최신 표를 71로 바꾼다. 표 변경이 확인된 상태의 읽기 경로와 네 블록의 현재 사용 여부를 적어라.

  1. 변경 전 읽기는 파일 번호 7 → inode 41 → 데이터 40이다. 11과 10은 현재 경로에서 제외되어 있다.

  2. 새 데이터 70과 새 inode 71을 기록한다. inode 71의 포인터는 70이다. 기록만 하고 최신 표를 바꾸지 않았으면 읽기는 여전히 41 → 40이다.

  3. 최신 표 map[7] = 71이 유효하게 확인되면 읽기는 71 → 70이다. 현재 참조가 없다는 추가 가정에서 41과 40은 이전 버전이다.

  4. 정리 때 71과 70은 유지한다. 다른 파일이나 snapshot이 오래된 블록을 참조한다면 그 참조도 검사해야 한다.

표 확인 뒤 최신 읽기는 71 → 70이다. 최신성을 결정하는 것은 유효 참조 표이며 단순히 가장 큰 물리 주소를 선택한 결과가 아니다.

종이와 본문으로 직접 해보기

힌트 보기

풀이 보기

오해와 반례

로그 구조 파일시스템은 저널링과 같아서 오래된 블록을 즉시 모두 삭제해도 된다.

복구용 로그와 주 저장 배치는 역할이 다르다. 오래된 위치가 다른 현재 참조에 사용되는지와 최신 표의 안전한 갱신을 확인해야 한다.

소단원 13.3

크래시 일관성 실험

한 번의 장애에서 복구가 됐다면 모든 장애 위치에서 안전하다고 말할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 사건 순서

  • 불변식

  • 예상 결과와 관찰 결과

학습 목표

  • 자체 프로토콜의 장애 절단점을 열거한다.

  • 복구의 안전성과 최신 성공 응답의 지속성을 구별한다.

  • 종이·시뮬레이터·실물 실험을 구별하여 보고한다.

먼저 장애 모형과 정답 기준을 쓴다

실험 설계에는 무엇이 사라지는지부터 정한다. 프로세스만 종료되는 장애는 OS 캐시를 지우지 않을 수 있고 전원 장애는 다른 범위의 버퍼를 잃는다. 가상 머신 재시작이 실제 장치의 정전과 동일하다고 가정하지 않는다. 쓰기 단위의 원자성·순서·동기화·오류 조건도 명시한다.

이 절은 A와 B가 같은 버전이어야 한다는 안전성, 그리고 성공 응답을 받은 버전은 복구 뒤 남아야 한다는 지속성 두 조건을 사용한다. 장애 뒤 두 값이 모두 옛값이면 안전성을 지킬 수 있지만 이미 새 버전 성공을 응답했다면 지속성 조건을 어길 수 있다.

각 사건 사이에 장애를 끼워 넣는다

초기 A = B = 1이다. 결과 로그에 A = B = 2를 지속 저장하고 commit을 지속 저장한 뒤 A, B 순서로 원위치에 저장한다. 두 원위치 값이 지속된 뒤 로그를 회수한다. 기록과 commit은 검증되며 유효 commit이 있으면 재생하고 없으면 원위치 쓰기를 시작하지 않는 자체 프로토콜이다.

각 단계가 이 모형의 완전한 지속 사건이면 사건 이전과 사건 사이에 장애를 넣어 복구값을 표로 만들 수 있다. 실제 부분 쓰기·재정렬·오류를 허용하면 경우가 더 늘어난다. 이 표는 지정한 모형의 경우를 모두 다룰 뿐 모든 실제 장애를 완전히 다룬 결과가 아니다.

성공 응답 위치가 보장을 바꾼다

안전한 프로토콜도 성공 응답을 너무 일찍 보내면 약속을 어긴다. 로그 결과만 있고 commit 전인 시점에 성공을 보냈다면 장애 뒤 로그가 무시되어 옛값으로 돌아갈 수 있다. 반면 유효 commit의 지속 확인 후 성공 응답은 그 기록을 재생할 수 있다는 모형의 복구 보장과 연결된다.

실제 실습을 한다면 전용 복제 환경에서 입력·실패 위치·재시작·검사·관찰 로그를 남긴다. 여기서는 그런 장비를 실행하지 않았다. 표의 예상 결과, 수행 여부, 실제 관찰 칸을 구별하며 실제 관찰은 미수행으로 둔다.

중간 과정을 따라가는 예제

정상 모형의 지속 사건을 L(결과 로그), C(commit), A(원위치 A=2), B(원위치 B=2), R(로그 회수) 순으로 정한다. 초기 1/1에서 사건 0·1·2·3·4·5개가 끝난 직후 장애를 넣고 복구값을 적어라. 유효 C가 남으면 2/2를 재생한다.

  1. 0개 종료: 로그 없음, 원위치 1/1이므로 복구 1/1이다.

  2. L만 종료: C가 없고 원위치 쓰기도 없어 복구 1/1이다.

  3. L,C 종료: 원위치 1/1이지만 유효 기록을 재생하여 복구 2/2다.

  4. L,C,A 종료: 원위치 2/1이지만 재생하여 2/2다.

  5. L,C,A,B 종료: 원위치 2/2이며 재생해도 2/2다.

  6. R까지 종료: 로그를 회수했지만 원위치 둘의 지속을 이미 확인했으므로 복구 2/2다.

여섯 위치의 복구 예상은 1/1, 1/1, 2/2, 2/2, 2/2, 2/2다. 모든 위치가 동등한 두 값이라는 안전성을 지킨다. 실제 장애 관찰은 아직 없다.

종이와 본문으로 직접 해보기

잘못된 프로토콜이 L 완료 직후 성공을 응답했다. 그 직후 장애가 나면 안전성과 성공한 버전 지속성 중 무엇이 실패하는가? 다른 위반에서 C와 A만 완료한 뒤 R로 로그를 지우면?

힌트 보기

값이 같은지와 약속한 버전 2가 남는지를 따로 검사한다.

풀이 보기

첫 경우 복구는 1/1이라 안전성은 통과하지만 성공한 버전 2의 지속성은 실패한다. 두 번째는 원위치 2/1에서 로그를 잃어 정상 재생 근거가 없어 안전성도 실패할 수 있다. 정상 R은 B 지속 확인 뒤에만 허용된다.

오해와 반례

장애 후 값이 같거나 종이 표가 통과하면 실제 크래시 시험도 성공이다.

같은 옛값은 조기 성공 응답의 지속성 실패일 수 있다. 종이 모형 검증은 실제 장치·시뮬레이터·재시작 로그와 별개며 미수행 관찰을 성공으로 채우지 않는다.
