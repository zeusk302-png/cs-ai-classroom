유효한 기록 하나와 같은 분포의 기록들은 어떤 차이가 있을까요?

기본의 p=23,q=11,g=2,x=3,y=8인 작은 군을 그대로 쓰되, 정직한 검증자의 도전 c는 r와 독립인 0 또는 1의 균등한 비트라고 정합니다. 매 대화마다 r를 0부터 10까지 균등하고 독립적으로 새로 고르고 t=g^r를 먼저 보낸 뒤 c를 받아 s=r+cx mod11을 보냅니다. 이 도전 범위는 기본의 c=2 계산과 다른 자체 모형입니다. 작은 공간은 손으로 전부 열거할 수 있으므로 실제 암호 안전성을 뜻하지 않습니다.

정직한 검증자가 보는 (t,c,s)의 분포를 비교하려고, 비밀 x를 사용하지 않는 시뮬레이터가 c를 균등한 비트로, s를 0부터 10까지 균등하게 고른 뒤 t=g^s y^(−c) mod23을 계산하게 합니다. 고정된 c에서 r↔s=r+cx는 나머지 11의 일대일 대응입니다. 따라서 두 절차의 각 유효 기록은 확률 1/22로 나타납니다. 이는 이 자체 모형의 정직한 검증자 기록 분포에 대한 설명이며, 악의적 검증자 전체나 실제 작은 군의 안전성을 증명한 것은 아닙니다.

양자내성 알고리즘을 비교할 때도 이름보다 역할을 먼저 봅니다. KEM에서는 공개 encapsulation key와 ciphertext가 오가고 공유 비밀과 decapsulation key는 공개 전송량에 넣지 않습니다. 아래 크기 계산은 FIPS203 표3의 바이트 수를 사용하는 자체 전송 모형이며, 신원 인증·메시지 프레이밍·실행 시간·표준 적합성을 평가한 결과가 아닙니다.

보여 주는 명제와 숨기는 증인

영지식은 공개 명제가 맞음을 확인하면서 추가 비밀 정보의 유출을 제한하는 증명 체계의 성질이다. 증인 w가 공개 입력 y와 관계R(y,w)를 만족한다고 생각하자. 정직한 절차가 맞는 명제를 받아들이는 완전성과 잘못된 명제를 속여 받아들이기 어렵게 하는 건전성은 영지식과 별개다. 지식 보유 증명은 증인 추출의 별도 의미도 다루므로 모든 대화형 증명과 같은 말로 쓰지 않는다.

영지식의 근거는 비밀 증인 없이 검증자가 보는 기록을 적절한 분포로 만드는 시뮬레이터다. 정직한 검증자만 다루는 조건과 악의적 검증자까지 다루는 정의를 구분한다. 비밀 숫자를 화면에 쓰지 않았다는 관찰만으로 이 성질을 증명할 수 없다. 공개 명제 자체가 드러내는 정보나 입력·출력의 공개도 없던 일이 되는 것은 아니다.

작은 대화식은 계산 연결만 보여 준다

자체 소수차수 부분군에서 공개 y=gˣ,증명자의 임시 비밀r,첫 메시지t=gʳ라 하자. 검증자가 도전값c를 보내면 응답은s=r+cx modq이고 gˢ=t·yᶜ를 확인한다. x나r를 직접 보내지 않지만 r를 재사용해 서로 다른c에 답하면 비밀이 복원될 수 있다. 아래p23/q11은 손으로 탐색 가능한 작은 공간이어서 실제 안전성을 제공하지 않는다.

정직한 검증자에 대한 개요에서는c와s를 먼저 균등하게 고르고t=gˢy⁻ᶜ로 기록을 만드는 시뮬레이션을 생각할 수 있다. 실제 대화에서 첫t가 도전보다 먼저 고정되는 순서는 건전성에 중요하다. 시뮬레이터가 기록을 만들 수 있다는 사실과 실제 참가자가 도전 뒤에 첫 메시지를 바꿔도 된다는 주장은 다르다.

양자내성은 역할과 가정을 가진다

양자내성 암호는 양자 컴퓨터를 쓰는 공격자까지 고려하는 알고리즘 설계 방향이다. 양자 통신 장비가 있어야만 실행되는 뜻은 아니다. NIST FIPS203의 ML-KEM은 공유 비밀을 확립하는 KEM, FIPS204의 ML-DSA와 FIPS205의 SLH-DSA는 서명이다. 공유 비밀은 후속 대칭 암호 등의 입력으로 사용되며 KEM을 문서 서명으로 바꾸어 부르지 않는다.

표준 이름만 바꿨다고 키 관리·신원 인증·재전송·난수·부채널 문제가 없어지지 않는다. 여기서는 공개 문서의 역할을 비교하며 표준 전체 적합성이나 모든 양자 공격에 대한 무조건적 안전성을 주장하지 않는다. 새 구현을 선택할 때는 최신 정오표·매개변수·프로토콜 조합을 함께 확인한다.

중간 과정을 따라가는 예제

자체 부분군 p=23,q=11,g=2에 x=3,r=4,c=2를 사용한다. y,t,s를 계산하고 검증식 양변을 비교하라. 2¹¹ mod23=1인 비항등 g는 소수11차수임을 사용한다.

  1. y=2³ mod23=8,t=2⁴ mod23=16이다. s=4+2·3 mod11=10이다.

  2. 왼쪽2¹⁰=1024 mod23=12다. 오른쪽16·8² mod23에서8² mod23=18이므로16·18=288 mod23=12다.

  3. 검증식은 일치한다. 이는 정직한 계산 연결의 예이며 작은 군에서 실제 위조 안전성·일반 영지식·양자내성을 증명한 것이 아니다.

y8,t16,s10이며 양변12로 같다. 비밀x를 직접 보내지 않는 식의 구조를 확인했다.

조건을 바꾸어 비교하기

한 기록에서 22개 기록의 분포로

c=1,s=2 기록을 실제 방식과 시뮬레이터 방식으로 각각 만들고, 왜 모든 s에서도 확률이 같은지 설명하세요.

  1. 실제 방식의 r=2−1·3 mod11=10이므로 t=2¹⁰ mod23=12입니다.

  2. 시뮬레이터에서는 8의 mod23 역원이 3이므로 t=2²·3 mod23=12입니다.

  3. 각 고정 c에서 s를 바꾸면 r=s−3c가 0..10을 정확히 한 번씩 방문합니다.

  4. c의 두 값과 s의 열한 값으로 22개 유효 기록이 있고 각각 1/2·1/11=1/22입니다.

한 기록의 양변 일치에 더해, 일대일 대응으로 이 모형의 전체 기록 분포가 같음을 확인했습니다.

비교할 점

단 한 번 t가 같았다는 계산만으로 분포 전체나 악의적 검증자 보장을 결론내리지 않습니다.

키 크기와 공개 전송량의 구분

자체 전송에서는 KEM 공개키를 처음 한 번 보내고 ciphertext 한 번을 보냅니다. 다른 필드는 모두 제외합니다. ML-KEM-512와 ML-KEM-768의 첫 공개 전송량과 공개키가 이미 있는 경우의 전송량을 계산하세요.

  1. FIPS203 표3에서 512의 공개키는 800바이트, ciphertext는 768바이트입니다. 첫 전송 합은 1568바이트입니다.

  2. 768의 공개키는 1184바이트, ciphertext는 1088바이트입니다. 첫 전송 합은 2272바이트입니다.

  3. 첫 전송 차이는 2272−1568=704바이트입니다. 공개키를 이미 가진 경우에는 각각 ciphertext 768바이트와 1088바이트만 이 모형에서 새로 보냅니다.

  4. 각 방식의 공유 비밀 32바이트와 비밀 decapsulation key는 공개 합에 넣지 않습니다.

ML-KEM-512의 첫 전송량은 1568바이트이고 ML-KEM-768은 2272바이트입니다. 공개키가 이미 있으면 각각 768바이트와 1088바이트를 보냅니다. 이는 필드 크기 비교입니다.

비교할 점

바이트 수만으로 실행 지연이나 신원 인증의 유무를 판정하지 않습니다. KEM을 문서 서명으로 사용한다는 뜻도 아닙니다.

종이와 본문으로 직접 해보기

힌트 보기

s₂=4+15 mod11이다. −3 mod11은8이며8의 역원은7이다. 이 활동은 재사용 실패의 작은 산술 반례다.

풀이 보기

연습 1 · 값과 상태 예측

같은 비트 도전 모형에서 c=0,s=2 기록의 r,t,발생 확률을 구하세요. c=1,s=2와 첫 메시지를 비교하세요.

힌트 1

c=0이면 s=r입니다.

힌트 2

도전과 임시 비밀을 독립적으로 고릅니다.

풀이와 답 확인

  1. r=2이므로 t=4입니다.

  2. 확률은 1/2·1/11=1/22입니다.

  3. c=1,s=2의 t=12와 다르지만 둘 다 해당 분포에서 같은 확률입니다.

임시 비밀 r은 2이고 첫 메시지 t는 4입니다. 해당 기록의 확률은 1/22입니다. 도전 c가 1이고 응답 s가 2인 기록의 첫 메시지 t=12와는 다릅니다.

흔한 오답에서 다시 생각하기

응답 s가 같으므로 t도 항상 같아야 한다.

s=r+cx이므로 c를 바꾸면 대응하는 r도 바뀝니다. 공개 y를 사용하는 시뮬레이터 식으로 다시 비교하세요.

연습 2 · 오류 찾아 고치기

자체 도전 맞히기 모형에서 세 번 모두 0을 예상합니다. 세 라운드의 도전이 각각 독립 균등 비트인 경우와, 하나의 균등 비트를 세 라운드가 그대로 공유하는 경우의 연속 성공 확률을 구하세요.

힌트 1

독립인 경우에만 각 1/2를 곱합니다.

힌트 2

공유 비트에서는 가능한 도전열이 000과 111뿐입니다.

풀이와 답 확인

  1. 독립이면 세 개의 0이 나올 확률은 (1/2)³=1/8입니다.

  2. 공유하면 000의 확률은 1/2이므로 세 번 성공할 확률도 1/2입니다.

  3. 각 라운드의 첫 메시지를 그 라운드 도전 전에 고정하는 조건도 따로 유지합니다.

독립 도전에서는 세 번 모두 성공할 확률이 1/8이고, 공유 도전에서는 1/2입니다. 반복 횟수만으로 독립성을 대신하지 못합니다.

흔한 오답에서 다시 생각하기

어쨌든 세 번 검사했으니 두 경우 모두 1/8이다.

균등성과 비예측성을 구별한다

암호 비밀에는 공격자가 예측하기 어려운 난수 생성이 필요하다. 반복 가능한 고정 seed는 테스트 재현에는 유용하지만 모두가 아는 seed로 운영 비밀을 생성하면 숨겨진 정보가 아니다. VM 스냅샷 복구나 상태 복제도 출력 반복 문제를 만들 수 있다. 실패 처리를 무시하거나 약한 대체값으로 진행하는 정책도 검토한다.

작은 정수 범위를 나머지 연산으로 줄이면 균등한 입력조차 출력이 편향될 수 있다. 예를 들어0..7의8가지 값을%3으로 줄이면0과1은각3가지,2는2가지에서 나온다. 균등 출력만으로 비예측성이 보장되는 것도 아니다. 공식 암호 라이브러리의 목적별 난수 API를 읽고 두 성질을 구분한다.

태그를 이미 붙인 암호문에 태그 길이를 다시 더하면 어떻게 될까요?

앞 본문의 자체 봉투에서 헤더 4바이트, 공개 nonce 24바이트, 태그 16바이트를 유지합니다. XChaCha20-Poly1305-IETF의 combined 출력에는 본문 암호문 뒤에 태그가 포함되고, detached 출력에서는 본문과 태그가 별도입니다. 같은 필드를 한 번씩 담는 봉투라면 두 방식의 총 길이는 같습니다. 라이브러리 출력 길이와 응용 프로그램 봉투 길이를 구분하면 태그를 두 번 세는 오류를 찾을 수 있습니다.

안전한 알고리즘을 호출해도 반환 상태를 무시하거나 예전 버퍼의 내용을 정상 평문처럼 처리하면 응용 프로그램 계약을 어깁니다. 이 단원은 구조 길이, 자체 자원 한도, 인증 성공, 업무 실행을 서로 다른 검사 단계로 놓습니다. 아래 실패 경로와 검증표는 설계 기대값이며 라이브러리를 실행해 확인한 관측값은 아닙니다.

암호 알고리즘보다 먼저 사용할 계약을 적는다

프로그램의 보호 목적·키 소유자·저장 기간·공개 메타데이터·실패 시 처리 정책을 정한다. 지원되는 라이브러리 버전과 알고리즘·키/nonce/태그 길이·허용 메시지 길이·반환값을 공식 문서에서 확인한다. 직접 블록 암호와 MAC을 임의로 이어 붙이기보다 문서화된 고수준 AEAD 계약을 사용한다.

XChaCha20-Poly1305 combined 모드는 암호문 뒤에 인증 태그를 붙이며 AD도 인증하지만 숨기지는 않는다. decrypt의0은 성공,−1은 검증 실패 계약이다. 실패일 때 검증되지 않은 버퍼를 정상 평문처럼 사용하지 않는다. 실제 상수와 길이는 사용하는 라이브러리에서 확인하고 아래 자체 패킷 계산을 제품 규격처럼 사용하지 않는다.

한 번 되돌리기보다 더 많은 근거가 필요하다

왕복 테스트는 encrypt 후 decrypt 결과가 원문과 같음을 확인한다. 같은 버그가 양쪽에 있으면 왕복만으로 놓칠 수 있으므로 독립된 공식 테스트 벡터나 다른 검증된 구현과의 기준 비교도 필요하다. 암호문·태그·AD·키·nonce를 바꿨을 때 실패를 안전하게 처리하는지, 빈 입력과 잘린 입력의 길이 계약도 확인한다.

각 변경의 인증 실패가 실제로 발생했는지 기록해야 한다. 안전한 인증에서도 유한 태그의 우연 성공 확률은 존재하며 모든 수학적 입력에서 절대 실패라고 주장하지 않는다. 이 절에서는 설계한 기대 결과와 실제 실행 결과를 분리한다. 실제 호출하지 않은 테스트는 계획으로 남긴다.

키·nonce·출력의 상태도 시험한다

한 키의 nonce 유일성은 한 함수 호출의 성공 반환만으로 검증되지 않는다. 동시 작업·프로세스 재시작·VM 복원·백업 복구에서 키와nonce 상태의 관계를 확인한다. 로그에 키나 평문을 그대로 남기지 않으며 인증 실패 후 업무 실행이나 재시도가 어떤 상태를 만들지도 본다.
