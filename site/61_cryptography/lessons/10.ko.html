소단원 10.1

이산로그·Diffie–Hellman

각자 숨긴 수를 직접 보내지 않고도 같은 값을 계산할 수 있을까요?

준비 개념과 학습 목표

준비 개념

  • 거듭제곱과나머지

  • 공개값과비밀값

  • 유한순환군의기본뜻

학습 목표

  • 이산로그의 입력과 찾는 값을 구별한다.

  • DH 두 방향의 공유값을 계산한다.

  • 값의 일치와 보안 가정을 구별한다.

공개값이 2..27 사이면 원하는 군에 속했다고 말할 수 있나요?

자체 모형에서 p=29를 유지하되 생성원은 g=16, 군의 차수는 q=7로 바꿉니다. g의 거듭제곱은 1,16,24,7,25,23,20이고 다음은 1입니다. 이 일곱 원소가 새로 선택한 부분군입니다. 기본 예제 g=2의 차수 28과 지수의 법을 섞지 않습니다. 이 작은 모형은 NIST 승인 매개변수나 안전한 배포용 키가 아닙니다.

후보 Y=12는 2..27 범위에 있지만 원하는 부분군에 없습니다. 12²≡28, 12⁴≡1이므로 12의 차수는 4입니다. Y^7≡17≠1로 부분군 검사를 통과하지 못합니다. 범위 검사와 군 소속 검사는 서로 다른 조건입니다. 적절한 도메인 매개변수가 먼저 검증되어야 하는 실제 규격의 전제도 작은 수 계산과 구별합니다.

나머지 세계의 거듭제곱

소수 p로 나눈 나머지의 곱셈에서0이 아닌 값들은 역원을 가집니다. 이 중 생성원 g의 거듭제곱이 만드는 순환군을 생각합니다. 군의 크기 q이면 지수는 q를 주기로 되풀이됩니다. 공개 g와 A=g^a를 보고 지수 a를 q를 법으로 찾는 문제가 이산로그입니다. 보통 실수 로그로 계산하는 문제가 아닙니다.

자체 종이 예제는 p=29,g=2입니다. 반복 두 배 후29로 나눠0..27 지수의 나머지를 쓰면1,2,4,8,16,3,6,12,24,19,9,18,7,14,28,27,25,21,13,26,23,17,5,10,20,11,22,15입니다. 다음2배는30이라1로 돌아옵니다. 서로 다른28개 값이라 이 예제의 군 크기는28입니다. 작은 전체 표를 만들 수 있어 암호용으로 안전하지 않습니다.

서로 다른 길로 같은 값을 계산

Diffie–Hellman에서A쪽은 비밀 a를 고르고 공개 A=g^a를 보내며,B쪽은 비밀 b를 고르고 공개 B=g^b를 보냅니다. A쪽은 B^a,B쪽은 A^b를 계산합니다. 군에서(B)^a=(g^b)^a=g^(ab)=(g^a)^b라 두 공유값이 같습니다. 처음부터 대칭키를 암호화해 보내는 방식과 다릅니다.

자체 예제 a=3,b=5이면A=8,B=3입니다. A쪽은3³=27,B쪽은8⁵를29로 나눈27을 얻습니다. p,g,A,B는 공개이고a,b와공유값은 비밀로 다루려는 대상입니다. 실제 키에는 적절한 군/지수/입력검증과후속 키유도 등 더 많은 조건이 필요합니다.

역문제와 난도 가정

이산로그를 풀 수 있으면 공개 A에서 a를 얻어 B^a로 공유값을 계산합니다. 공개g,g^a,g^b에서g^(ab)를 계산하는 문제를 CDH라고 부르며 이산로그와 같은 문제라고 단정하지 않습니다. 안전성에는 사용하는 군과 공격자의 계산 능력에 관한 가정이 붙습니다.

두 참가자가 같은 값을 얻었다는 대수적 확인은 도청자가 값을 못 구한다는 보안 증명이 아닙니다. 자체 예제에서는 표를 보고 8의 지수가 3임을 알아 공유값 27을 구할 수 있습니다. 실제 보안 크기나 알고리즘 권장값을 이 작은 예제에서 추정하지 않습니다. 다음 소단원은 값 교체가 가능한 공격자의 경우를 다룹니다.

중간 과정을 따라가는 예제

p=29,g=2,a=3,b=5인 자체 교환의 A,B와 공유값을 계산하라. B쪽의 8⁵는 중간마다 나머지를 줄여라.

  1. A=2³=8,B=2⁵=32≡3 (mod29)다.

  2. B^a=3³=27이다.

  3. 8²=64≡6,8⁴≡6²=36≡7,8⁵≡7×8=56≡27이다. 두방향이같다.

공개A8/B3와 공유값27이다. 종이 계산이며 실제 안전한 키를 만든 것이 아니다.

조건을 바꾸어 비교하기

새 부분군에서 두 방향 계산

g=16, q=7, a=3, b=5의 공개값과 공유값을 구하세요.

  1. 16²≡24, 16³≡7이므로 A=7입니다.

  2. 16⁴≡25, 16⁵≡23이므로 B=23입니다.

  3. B³≡23²×23≡7×23≡16이고 A⁵≡7⁴×7≡23×7≡16입니다.

  4. ab=15≡1 (mod 7)이므로 g^(ab)=16으로도 일치합니다.

A=7, B=23, 공유값 16입니다.

비교할 점

기본 차수 28 예제의 공개값 8/3과 공유값 27을 그대로 쓰지 않습니다.

차수 4 입력이 남기는 지수 조건

검증 없이 Y=12를 받았다고 가정합니다. a를 0..6에서 사용할 때 Y^a의 값을 나누세요.

  1. a mod 4가 0,1,2,3이면 출력은 각각 1,12,28,17입니다.

  2. a=3이면 17이고 a=5이면 12입니다.

  3. 공유값을 직접 드러내는 추가 관찰을 허용했다면 지수의 법 4 잔여를 좁힐 수 있습니다. 그런 관찰이 실제 존재하는지는 별도 조건입니다.

가능한 공유값은 네 개뿐입니다. 작은 차수 입력은 원하는 차수 7 입력과 다릅니다.

공개값이 원하는 군에 있어도 누가 보낸 값인지 알 수 있나요?

앞 소단원의 g=16, a=3, b=5를 이어 사용하며, 이 문단의 거듭제곱 결과는 모두 mod 29입니다. 정상 공개값은 A=7, B=23이고 공유값은 16입니다. 중간자가 양쪽에 g=16을 대신 보내고 자신의 두 지수를 모두 1로 선택하면, A 쪽은 16³≡7, B 쪽은 16⁵≡23을 얻습니다. 중간자는 공개 A와 B를 각각 1승하여 두 구간의 값을 압니다. 교체한 16도 원하는 부분군의 유효한 원소입니다. 산술 검증만으로 교환 상대를 인증할 수 없습니다.

서명을 쓰는 자체 종이 설계에서는 버전·서명자의 역할·두 주체·두 공개값·세션 식별자를 명확하게 인코딩합니다. 기대하는 상대의 신뢰된 검증키로 이 맥락을 확인한다는 조건을 붙입니다. 숫자만 서명하거나 메시지에 들어 있는 어떤 키든 믿는 절차와 구별합니다. 이 일곱 바이트 형식은 TLS의 실제 메시지 형식이나 완전한 키교환 프로토콜이 아닙니다.

    기본 중간자 예와 달리, 산술 검사를 통과한 부분군 원소를 바꾸는 경우를 비교합니다.

값을 바꿀 수 있는 상대

인증 없는 DH는 공개값이 정말 의도한 상대에게서 왔는지 확인하지 않습니다. 중간자가 메시지를 가로채고 다른 공개값을 보내면 A쪽과 B쪽은 각각 중간자와 공유값을 만들 수 있습니다. 큰 수의 이산로그를 푸는 대신 자신이 아는 지수로 두 교환을 이어 붙이는 공격입니다.

자체 예제의 정상 공개값은 A=8,B=3입니다. 중간자는 c=4의 C=16을 A쪽에 B의 값인 척 보내고,d=6의 D=6을 B쪽에 A의 값인 척 보냅니다. 여기서는 중간자가 두 경로의 공개값을 교체할 수 있다고 명시하며 실제 네트워크에 접근하지 않습니다.

서로 다른 두 공유값

A쪽은 C^a=16³≡7을 계산합니다. 중간자는 A^c=8⁴≡7을 계산해 A쪽 공유값을 압니다. B쪽은 D^b=6⁵≡4를 계산하고 중간자는 B^d=3⁶≡4를 계산합니다. A/B의 공유값 7과4는 서로 다르지만 중간자는 둘 다 압니다.

이 두 값에서 통신 키를 유도하여 메시지를 받아 읽고 다른 키로 보내는 가상 흐름을 생각할 수 있습니다. 정확한 라이브러리나 실제 암호문을 계산한 실습은 아닙니다. 자기 키로 태그를 정당하게 만들 수 있는 중간자는 각 구간의 인증암호를 깨뜨릴 필요도 없습니다. 상대 신원과 교환을 연결하는 인증이 빠진 것입니다.

교환과 신원 연결하기

인증된 키교환은 신뢰하는 공개 서명키나 미리 공유한 비밀 등 신뢰의 시작점과 교환의 주체·맥락을 연결합니다. 서명을 쓴다면 단순 공개값뿐 아니라 누가 누구에게 어떤 프로토콜에서 보낸 교환인지도 검토합니다. 인증서가 있다는 사실만으로 어떤 주체 이름도 믿어서는 안 됩니다. 신뢰 경로와 기대 이름 검사 등 프로토콜의 규칙이 함께 필요합니다.

자체 문서로 T=(버전v1,A주체,B주체,A공개값8,B공개값3)를 정해 보세요. A가 B의 신뢰된 서명키로 T를 검증한다고 가정하면,B공개값을16으로 바꾼 T′는 다른 인증 대상입니다. 안전한 서명·명확한 인코딩·기대 주체 검증이라는 가정이 있어야 변경 거절을 주장할 수 있습니다. 이 정리 틀은 TLS 핸드셰이크 전체를 구현한 예제가 아닙니다.

HKDF expand의 입력은 PRK, info, 요청 길이 L입니다. 해시 출력 길이를 32바이트로 두면 T₁=HMAC(PRK,info||0x01), T₂=HMAC(PRK,T₁||info||0x02)로 이어집니다. L은 몇 블록을 계산하고 어디까지 잘라 쓰는지 정하지만, 이 기본식의 블록 입력에는 직접 들어가지 않습니다. 따라서 같은 PRK·info에서 L=16과 L=48의 출력은 앞 16바이트가 같습니다. 출력 바이트를 실제 계산하지 않고 식의 입력 동일성을 비교합니다.

필요한 용도·프로토콜·주체·방향 등을 명확한 info에 연결하고, 요청 길이까지 분리하려면 길이도 info에 인코딩하는 자체 설계를 생각할 수 있습니다. info는 IKM 값과 독립적이라는 규격의 조건을 보존합니다. 유도 출력 길이가 늘어도 원래 비밀 후보 수가 늘지 않습니다. 전방향안전성에서는 유출된 키의 종류·시점·남아 있는 임시 비밀과 세션 키를 따로 점검합니다.

먼저 확인할 개념
  • 키 유도와 forward secrecy

    기본 42바이트 예제에 길이가 다른 출력의 공통 접두부와 유출 범위를 더합니다.

  • 비밀번호 해시·salt·KDF

    비밀 엔트로피와 계산 비용의 역할을 구별하고 HKDF를 비밀번호 후보 지연 함수로 오해하지 않게 합니다.

공유값을 키 재료로 다루기

DH 결과는 군원소이며 이를 곧바로 모든 암호의 키로 쓰는 것과 키 유도는 다릅니다. HKDF의 extract는 입력 재료 IKM과 salt에서 중간 키 PRK를 만들고 expand는 PRK,맥락 info,요청 길이 L에서 출력 재료를 만듭니다. DH 입력은 extract를 건너뛰지 않는 범위로 생각합니다. 원래 입력에 없던 비밀 엔트로피가 유도로 새로 생기는 것은 아닙니다.

양쪽은 DH 원소를 같은 방식으로 바이트로 표현해야 합니다. 자체 공유값 27을 한쪽은 한 바이트 0x1b,다른 쪽은 문자열27의 두 문자 바이트로 넣으면 다른 입력이 됩니다. 실제 프로토콜의 정해진 인코딩을 따르는 의무를 보여 주는 예이며 HKDF 출력을 계산한 시험 벡터는 아닙니다.

용도와 길이 정하기

자체 설계표의 info는(프로토콜v1,주체A,주체B,용도A→B)입니다. B가 같은 수신 키를 유도하려면 같은 바이트 맥락을 써야 합니다. 반대 방향에는 용도B→A를 쓰며 암호키와 다른 용도의 재료도 레이블로 구분합니다. 다른 info의 키가 수학적으로 절대 충돌하지 않는다는 주장이 아니라 용도 분리와 보안 분석을 위한 입력입니다.

HKDF의 해시 출력 길이를 32바이트로 두고 L=42를 요청하면 expand 블록 두 개가 필요합니다. 첫 32바이트와 둘째 블록의 첫 10바이트로 42를 구성합니다. 각 블록은 이전 블록·info·한 바이트 카운터를 HMAC 입력에 연결하므로 같은 32바이트 출력을 단순 반복하는 것이 아닙니다. 이 절은 길이와 호출 연결만 손으로 검사합니다.

유출의 시간선과 삭제

전방향안전성은 정한 장기 인증키가 나중에 유출돼도 이미 완료한 세션의 키·기록을 보호하려는 성질입니다. 매 세션 새로운 비밀 지수,적절한 인증 교환,난도 및 키 유도 조건과 필요 없는 세션·임시 비밀의 삭제가 연결되어야 합니다. 현재 세션키 자체를 훔친 경우나 앞으로 위조할 수 있는 인증키를 이미 가진 공격까지 같은 보장으로 설명하지 않습니다.

자체 감사표를 t1교환,t2세션 종료,t3장기 서명키 유출로 정합시다. t2 뒤 로그에 비밀 a=3과 공개 B=3을 남겼다면 공유값 27을 계산할 수 있어 삭제 조건을 깨뜨립니다. 임시 지수와 키를 남기지 않는 변경 정책은 필요한 조건의 하나지만 p=29는 공개값만으로도 전수 표를 만들 수 있어 실제 전방향안전성을 보여 주지 못합니다. 안전한 군·전체 프로토콜의 가정과 작은 종이 계산을 끝까지 구별합니다.

조건을 바꾸어 비교하기

길이는 구분 레이블을 대신하지 않는다

같은 PRK·info에서 L=16을 짧은 키, L=48을 다른 용도의 긴 키로 사용했습니다. 어떤 바이트가 겹치나요?

  1. L=16의 출력은 T₁[0:16]입니다.

  2. L=48의 출력은 T₁||T₂[0:16]입니다.

  3. 긴 출력의 앞 16바이트는 짧은 출력 전체와 같습니다.

짧은 키 전체가 긴 출력의 접두부입니다.

비교할 점

길이를 달리 요청했다는 이유만으로 독립된 용도 키를 얻었다고 할 수 없습니다.

블록 입력 길이만 계산하기

info가 5바이트이고 L=65입니다. 각 expand HMAC의 메시지 입력 길이와 합을 구하세요.

  1. T₁ 입력은 빈 T₀+info 5+카운터 한 바이트로 6입니다.

  2. T₂와 T₃ 입력은 이전 출력 32+info 5+카운터 1로 각각 38입니다.

  3. 합은 6+38+38=82바이트입니다.

expand HMAC 메시지 입력 길이는 6,38,38이고 합은 82입니다.

비교할 점

HMAC 내부 해시의 패딩·키 처리·압축 호출 수를 센 것이 아니며, extract의 입력도 이 합에 넣지 않았습니다.

12의 차수는 4입니다. 유효한 군원소도 상대 신원을 보장하지 않습니다.

힌트 2

HKDF의 블록 입력에 L이 직접 들어가는지 확인하고, 임시 지수 로그를 따로 봅니다.

풀이와 답 확인

  1. ① 범위는 통과하지만 12⁷≡17≠1이므로 소속은 실패합니다.

  2. ② A 구간 7, B 구간 23이며 중간자도 둘 다 압니다. 정상 공유값 16과 구별합니다.

  3. ③ 공통 접두부는 앞 16바이트입니다. 서로 다른 용도의 키 분리를 길이만으로 주장하지 않습니다.

  4. ④ 24³≡20입니다. 남아 있는 임시 비밀로 재료를 다시 계산하는 종이 예입니다.

입력 유효성·상대 인증·용도 분리·과거 비밀 보존은 서로 다른 조건입니다.

해결한 뒤 점검할 것

  • 원소의 법 29와 지수의 법 7을 구별합니다.

  • 군 소속과 신뢰된 상대 인증을 구별합니다.

  • 같은 PRK·info라는 접두부 조건을 명시합니다.

  • 종이 모형을 실제 안전한 교환·키 삭제·TLS 실행 증거로 제시하지 않습니다.

보강 자료의 출처와 확인 범위
  • NIST SP 800-56A Rev.3 — Public-key validation

    실제 5.6.2.3 및 5.6.2.3.1의 사전 도메인 검증·범위·차수 소속 검사와 5.6.2.3.2의 partial 검사 적용 전제를 읽었다. p=29,q=7은 승인 매개변수가 아닌 자체 산술 모형이다.

  • RFC 5869 — HKDF expand and context

    실제 2.2/2.3의 extract·블록 연결·한 바이트 카운터·출력 잘라 쓰기, 3.2의 맥락과 길이 info 및 IKM 독립 조건, 3.3의 DH extract, 4의 엔트로피 및 지연 비용 한계를 읽었다. 16/48 접두부와 6/38/38 입력 길이는 식으로 손유도했으며 HMAC 출력은 실행하지 않았다.

  • RFC 8446 — CertificateVerify and compromise scope

    실제 4.4.3의 서명 대상 구성·역할별 context·검증 입력과 E.1의 장기 비밀 뒤늦은 유출 조건, E.1.5의 미래 보장 한계를 읽었다. 일곱 바이트 형식과 두 교환 수치는 자체 모형이며 실제 TLS 연결·서명·키 삭제는 미수행이다.

g=16의 일곱 원소는 1,16,24,7,25,23,20입니다. 공개 A=7,B=23의 두 방향 공유값은 16이고 a=6,b=5에서는 24입니다. 차수 4의 12는 범위만 통과하고 12⁷=17로 부분군 소속에 실패합니다. 관찰 12^a=12와 a∈1..6에서는 후보 1,5가 남습니다. 지수 1의 두 중간자 구간 공유값은 7과 23입니다. 자체 서명 맥락의 변경 필드와 64+33+1+32=130을 확인했습니다. HKDF의 동일 PRK·info에서 16/48 요청의 앞 16바이트는 같습니다. info 5바이트·L65의 expand 메시지 입력은 6,38,38바이트로 합 82입니다. 로그 a=3의 두 공개값 23/24에서 재계산한 공유값은 16/20입니다. 모두 손유도입니다.
