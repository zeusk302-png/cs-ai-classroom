소단원 13.1

challenge-response

지난번에 맞았던 인증 응답을 다시 보내면 이번에도 문이 열려야 할까?

준비 개념과 학습 목표

준비 개념

  • MAC과 공유 비밀

  • 전자서명과 검증

  • 조건문과 집합

학습 목표

  • 새 challenge에 묶인 응답과 고정 응답을 구분한다.

  • 인증 대상 필드와 한 번 사용 상태를 함께 설계한다.

질문에 묶인 답으로 비밀 보유를 확인하기

서버가 새 질문값인 challenge를 만들고 클라이언트가 그 값과 정해진 맥락에 대한 인증자를 돌려주는 흐름을 challenge-response라 한다. 공유 비밀 방식이면 MAC, 공개키 방식이면 서명을 사용할 수 있다. 검증자는 같은 질문·맥락·키로 인증자의 유효성을 확인한다. 비밀번호 자체를 그대로 응답에 넣는 방식과 구별하자.

관찰자가 지난 답을 보유하더라도 이번 질문이 다르면 그 답을 그대로 사용할 수 없어야 한다. 이를 위해 질문이 충분히 새롭고 인증 대상에 포함돼야 한다. 단순히 화면에 새 숫자를 보이는 것은 부족하다. 공격자가 바꿀 수 있는 필드가 MAC이나 서명 대상에서 빠졌다면 인증자 검증은 그 변경을 보지 못한다.

누가 누구에게 무엇을 증명하는가

이 절의 자체 모형은 프로토콜 버전, 서버와 클라이언트 식별자, 역할, 세션 번호, 작업, nonce를 순서·길이가 정해진 인코딩으로 묶어 MAC한다. 키는 안전하게 공유됐고 MAC은 안전한 알고리즘이라고 가정한다. 실제 MAC 수치는 만들지 않고 검증 성공 여부를 문제의 입력으로 준다. 예측 가능한 작은 숫자를 실제 인증 nonce로 추천하는 활동이 아니다.

역할을 구별하지 않으면 상대에게 받은 질문을 되돌려 상대가 만든 답을 이용하는 반사 공격의 기회가 생길 수 있다. 역할·상대·사용 목적을 묶는 것은 응답의 맥락을 분리한다. 다만 이 목록만으로 모든 프로토콜의 안전성을 증명한 것은 아니다. 비밀 보유 검증과 계정 주체의 키 연결, 작업 실행 권한은 각각 확인한다.

암호 검증 뒤에도 상태가 필요하다

서버는 자신이 발급한 미사용 질문, 해당 세션, 만료 조건을 저장한다. 응답이 유효하고 모든 조건을 만족하면 미사용→사용됨 전환과 작업 결정을 중복 수락되지 않도록 원자적으로 처리한다. 원자적이라는 말은 동시에 두 요청이 와도 둘 다 미사용이라고 보고 통과할 수 없게 하나의 결정으로 묶는다는 뜻이다.

타임스탬프가 허용 범위라는 조건은 같은 응답의 반복을 자동으로 막지 않는다. 여러 서버가 같은 요청을 처리한다면 사용 기록의 공유 범위도 중요하다. 질문을 발급하지 않은 서버가 임의의 nonce에 대한 유효 응답만 보고 수락하는 정책은 이 모형의 검증 정책과 다르다.

중간 과정을 따라가는 예제

자체 모형에서 서버S가 클라이언트C의 세션7·작업open에 nonce901을 시각100에 발급했다. 유효 조건은 현재 시각<130이고 발급한 정확한 필드의 MAC 검증 성공 및 미사용 상태다. 시각110의 정확한 응답은 검증 성공으로 주어졌다. 시각111에 같은 응답이 또 오면 두 요청은 어떻게 처리하는가?

  1. 110은130보다 작고 발급된 세션·역할·작업·nonce가 모두 같다. 검증 성공은 문제에서 주어진 입력이며 실제 MAC을 계산하지 않았다.

  2. 첫 요청에서 미사용 상태를 원자적으로 사용됨으로 전환하고 한 번 수락한다.

  3. 111도 시각 조건은 맞고 같은 MAC은 여전히 유효할 수 있다. 그러나 질문이 이미 사용됐으므로 두 번째 요청은 거부한다.

110의 첫 응답만 수락한다. 111의 재전송은 시간과 MAC 조건만으로 통과시키지 않는다.

소단원 13.2

인증된 키교환·TLS 흐름

둘이 같은 비밀을 계산했다면, 상대가 원래 만나려던 사람이라는 것도 알 수 있을까?

준비 개념과 학습 목표

준비 개념

  • Diffie–Hellman 키교환

  • 인증서와 전자서명

  • 해시와 MAC

학습 목표

  • 공유 비밀 계산과 상대 인증을 구분한다.

  • TLS 1.3 인증서 기반 흐름에서 CertificateVerify와 Finished의 역할을 설명한다.

같은 키 재료를 얻는 것과 상대를 믿는 것

키교환은 두 참가자가 통신을 통해 같은 비밀 재료를 얻는 절차다. 인증 없는 Diffie–Hellman 값 교환만으로는 그 값이 원하는 상대에게서 왔음을 알 수 없다. 중간자가 양쪽과 각각 별도 교환을 맺는 문제를 인증된 키교환에서 다룬다. 키 재료를 얻었다는 계산과 주체·대화 맥락을 확인했다는 근거를 분리하자.

아래 작은 소수 DH는 나머지 연산의 연결만 보여 준다. 실제 TLS가 이 작은 수를 쓰거나 이 결과 정수를 직접 암호화 키로 쓰는 것이 아니다. TLS 1.3은 선택된 키교환과 해시, 키 스케줄에 따라 비밀 및 대화 기록을 이용해 용도와 방향이 다른 키를 파생한다.

서버 인증서가 있는 전체 핸드셰이크를 따라가기

여기서는 TLS 1.3의 인증서 기반 서버 인증, 새 (EC)DHE 교환을 다루고 PSK·0-RTT·HelloRetryRequest·클라이언트 인증서는 생략한다. ClientHello에 클라이언트 키 공유값, ServerHello에 서버 키 공유값이 온다. 이어 서버의 EncryptedExtensions, Certificate, CertificateVerify, Finished가 오고 클라이언트 Finished가 이어진다. ServerHello 뒤의 핸드셰이크 메시지는 파생된 핸드셰이크 키로 보호된다.

Certificate의 발급자 서명과 CertificateVerify의 서버 서명은 역할이 다르다. 발급자 서명은 인증서의 키·이름 등의 관계를 발급자에 연결한다. CertificateVerify는 해당 개인키 보유와 현재 핸드셰이크 기록의 관계를 확인하게 한다. 검증자는 인증서 경로와 서비스 이름 등 정책도 확인해야 한다. 서버 인증만 수행한 이 흐름은 클라이언트의 계정 신원을 인증서로 인증했다는 뜻이 아니다.

대화 기록과 키 확인을 묶기

TLS 1.3의 CertificateVerify는 서버와 클라이언트의 서로 다른 맥락 문자열과 현재까지의 핸드셰이크 해시를 포함한 입력을 서명한다. 상대 역할과 기록을 묶어 다른 맥락의 서명을 옮겨 쓰는 문제를 줄인다. Finished는 파생된 finished_key로 핸드셰이크 기록에 MAC을 계산해 무결성과 해당 키의 보유를 확인한다. 잘못된 서명이나 Finished는 정상 인증 완료가 아니다.

키 스케줄은 HKDF와 용도별 라벨을 사용하며 핸드셰이크·애플리케이션 및 송수신 방향의 키를 구별한다. 같은 DH 비밀이 계산됐다는 이유로 이 단계들을 생략하지 않는다. 규격에는 서버가 먼저 애플리케이션 데이터를 보내거나0-RTT를 다루는 별도 조건이 있다. 이 절의 종이 흐름은 양쪽 Finished를 확인하는 정상 완료 경로만 그린다.

중간 과정을 따라가는 예제

자체 DH 모형에서 p=23, g=2, 클라이언트 a=3, 서버 b=4라 하자. 두 공개값과 공유 재료를 계산하라. 이후 인증서 정책·CertificateVerify·Finished가 모두 통과했다고 주어질 때 이 세 입력과 DH 계산의 역할을 구분하라.

  1. A=2³ mod23=8,B=2⁴ mod23=16이다.

  2. 클라이언트는16³을 계산한다. 16² mod23=3이므로16³ mod23=48 mod23=2다. 서버는8² mod23=18,8⁴ mod23=18² mod23=324 mod23=2를 얻는다.

  3. 공유 재료2는 일치한다. 인증서 정책 통과는 주체의 키를 신뢰 입력에 연결하는 판단, CertificateVerify 통과는 그 키와 현재 대화의 서명 관계, Finished 통과는 파생키와 대화 기록의 확인이다. 세 검증 성공은 문제에서 준 조건이며 실제 암호를 실행하지 않았다.

A8,B16,공유 재료2다. 일치만으로 상대 인증이 완성되지 않으며 문제의 별도 인증·기록·키 확인 조건이 필요하다.

오해와 반례

인증서가 있으니 현재 키교환 값도 자동으로 검증된 것이다.

인증서는 키와 이름 등의 관계를 제공하지만 현재 핸드셰이크에 대한 CertificateVerify와 Finished 검증을 대체하지 않는다. 인증서 파일이 있다는 사실, 신뢰 정책 통과, 현재 기록 서명 검증은 각각 다른 사건이다.

한 단계 더

종이에 메시지 누적 기록을 적고 CertificateVerify 검증 시점과 Finished 검증 시점의 기록 범위를 구분해 보자. Finished는 자신보다 앞선 해당 핸드셰이크 메시지를 해시하므로 자기 메시지를 그 검증 입력에 다시 포함하지 않는다. 서버 CertificateVerify가 있는 정상 흐름에서는 그 메시지도 서버 Finished의 기록에 들어간다. 이 활동은 RFC의 메시지 의미를 추적하며 실제 바이트 인코딩·서명·HKDF 계산은 수행하지 않는다.

준비 개념과 학습 목표

준비 개념

  • 조건문과 상태 전이

  • TLS 핸드셰이크

  • 중복 요청과 집합

학습 목표

  • 연결의 암호 검증과 애플리케이션 중복 실행 방지를 구분한다.

  • 키 확인·레코드 순번·재전송 상태의 범위를 설명한다.

메시지가 맞아도 지금 받을 메시지인가

프로토콜 구현은 바이트 검증뿐 아니라 현재 상태에서 허용되는 메시지인지 확인한다. 자체 학습 흐름을 시작→키 재료 확보→서버 정책·서명 확인→서버 Finished 확인→클라이언트 Finished 전송→완료로 그려 보자. 아직 확인하지 않은 조건을 생략하고 완료 상태로 넘어가면 계산된 비밀의 의미를 잘못 받아들이게 된다.

키 확인은 상대가 대화에 필요한 키를 보유한다는 근거를 제공하지만 인증되지 않은 상대의 키 확인만으로 원하는 주체의 신원이 생기지는 않는다. 어떤 키·방향·대화 기록을 확인했는지를 적어야 한다. 이 상태 표는 학습용 정상 흐름이며 TLS의 모든 분기와 경고를 구현한 표가 아니다.

TLS 레코드의 순번과 nonce 범위

TLS 1.3은 읽기와 쓰기의 레코드 순번을 각각64비트로 관리한다. 해당 키의 첫 순번은0이고 레코드마다 증가하며 넘치기 전에 재키잉하거나 연결을 닫는다. AEAD nonce는 순번을 네트워크 바이트 순서로 IV 길이까지 왼쪽0으로 채운 뒤 해당 쓰기 IV와 XOR해 만든다. 키가 바뀌면 해당 순번을0으로 재설정한다.

같은 쓰기 키와 IV에서 순번을 임의로0으로 되돌리면 같은 nonce를 재사용한다. 이는 정상적인 새 키로의 전환과 다르다. TLS 레코드 순번을 애플리케이션 거래 번호로 착각하지 말자. 새로운 연결에서 정상적으로 보호된 같은 거래 요청이 다시 들어올 수 있으며, 암호 프로토콜이 애플리케이션의 업무 중복을 모두 막지는 않는다.

업무에서 한 번과 연결에서 한 번

애플리케이션은 작업 식별자와 사용자·요청 내용 등 범위를 정하고 처음 처리한 결과를 저장할 수 있다. 같은 식별자의 같은 요청 재시도는 저장된 결과를 반환하고 작업을 다시 실행하지 않는 정책이 멱등 재시도다. 다른 내용으로 같은 식별자를 썼을 때의 충돌 처리도 정의한다. 검사·실행·결과 저장을 실제 장애와 동시성에서 어떻게 묶을지는 별도의 시스템 설계 문제다.

TLS 1.3의0-RTT는 연결 사이 재전송 불가를 일반적으로 보장하지 않는다. 여러 서버의 상태 공유·티켓 재사용 정책·애플리케이션 요청의 의미가 중요하며, TLS가 차단한 연결도 클라이언트 재시도로 업무 요청을 중복시킬 수 있다. 그래서 이 절은0-RTT를 켜고 끄는 설정 실험 대신 암호 검증과 업무 상태를 분리해 추적한다.

중간 과정을 따라가는 예제

자체 장부의 시작 잔액은100이고 거래T7은30을 차감한다. 같은 사용자가 서로 다른 두 정상 TLS 연결에서 T7을 재전송했으며 두 연결의 암호 검증은 모두 성공했다고 가정한다. 중복 식별자 정책이 없는 경우와 전체 처리 서버가 공유하는 원자적 거래 기록이 있는 경우의 잔액을 비교하라.

  1. 업무 중복 검사가 없으면 첫 처리100−30=70,두 번째 처리70−30=40이다. 정상 암호화라는 입력은 차감 횟수를 제한하지 않는다.

  2. 공유 기록 정책은 첫 T7의 요청 내용과 결과70을 저장하고 차감은 한 번 수행한다.

  3. 두 번째 T7은 같은 내용이므로 저장된 결과70을 돌려주고 새 차감은 하지 않는다. 실제 데이터베이스 트랜잭션을 실행한 결과가 아니라 정책을 만족하는 가상 장부 추적이다.

중복 방지 없이는40,명시한 공유·원자적 정책에서는70이다. 연결별 검증 성공과 전체 거래 한 번 처리는 다르다.

종이와 본문으로 직접 해보기

새 장부 100에서 T8의 20 차감을 두 번 보내라. 중복 정책 유무의 잔액을 비교하라. 별도로 12바이트 쓰기 IV의 마지막 바이트가 A0이고 나머지는 0이라고 하자. 순번 0/1/2에서 XOR nonce 마지막 바이트를 쓰고 같은 키·IV로 순번을 0으로 초기화한 위험을 설명하라.

힌트 보기

차감 횟수를1회와2회로 나눈다. 작은 순번에서는 패딩한 앞 바이트가0이며 A0 XOR01=A1이다. 이는 실제 AEAD 실행이 아닌 바이트 계산이다.

풀이 보기

두 번 실행하면60,한 번 실행·같은 결과 재사용이면80이다. nonce 마지막 바이트는순번0에서A0,1에서A1,2에서A2다. 같은 키·IV로0을 다시 쓰면 원래A0 nonce를 재사용한다. 정상 새 키 전환의 순번 초기화와 구별한다.

오해와 반례

TLS가 정상인 요청이면 업무 재전송도 반드시 거부한다.

새 연결의 정상 암호 요청도 동일한T7을 포함할 수 있다. 레코드 보호·연결 상태와 업무 거래 식별자의 범위는 다르다. 여러 노드의 사용 기록이나 멱등 결과 정책 없이 전체 한 번 처리를 주장하지 않는다.
