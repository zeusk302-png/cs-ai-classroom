소단원 8.1

충돌·원상·제2원상

같은 해시를 찾는다는 세 질문은 무엇이 먼저 주어졌는지에 따라 어떻게 달라질까?

준비 개념과 학습 목표

준비 개념

  • 함수와 입력·출력

  • 비트 수와 경우의 수

  • 서로 다른 값의 구별

학습 목표

  • 세 찾기 문제의 주어진 값과 목표를 구별한다.

  • 충돌 존재와 충돌 찾기의 어려움을 나눈다.

  • 작은 비보안 대응표로 세 문제를 직접 푼다.

짧은 요약과 정보 손실

해시는 입력을 일정 길이의 요약값으로 보내는 함수다. n비트 출력에는 2ⁿ개 값이 있다. 이보다 많은 서로 다른 입력을 보내면 같은 출력으로 가는 쌍이 존재한다. 따라서 충돌 저항성은 충돌이 전혀 없다는 뜻이 아니다. 실용 자원 안에서 충돌을 찾기 어렵다는 보안 성질이다.

같은 바이트와 같은 설정에 대한 해시는 같지만 서로 다른 입력의 해시는 반드시 다르다고 단정할 수 없다. 작은 수를 더해 나머지를 취하는 체크섬은 계산 연습에는 좋지만 암호학적 해시의 보안 성질을 보여 주지 못한다.

무엇을 먼저 주는가

원상 찾기는 출력 y를 주고 H(m)=y인 입력 하나를 찾게 한다. 원래 사용한 입력과 반드시 같은 것을 되찾는 문제가 아니다. 제2원상 찾기는 특정 입력 m을 먼저 주고 m′≠m이면서 H(m′)=H(m)인 다른 입력을 찾게 한다.

충돌 찾기는 두 입력을 모두 선택할 수 있는 상황에서 m≠m′,H(m)=H(m′)인 쌍을 찾는 문제다. 미리 고정된 입력을 대체하는 상황과 아무 두 입력을 고를 수 있는 상황은 공격자의 자유도가 다르다. 세 저항성을 이름이 비슷하다고 동일한 보장으로 취급하지 않는다.

요약값을 어디서 받았는가

자료와 해시를 같은 신뢰하지 않는 곳에서 받으면 둘 다 바뀔 수 있다. 해시 비교는 신뢰할 수 있는 기준 요약을 이미 갖고 있을 때 의미가 있다. 공개 해시 하나는 작성자의 신원이나 메시지 진실성을 자동 인증하는 비밀키가 아니다.

아래 작은 대응표는 약한 함수를 의도적으로 완전히 보여 준다. 이 표에서 쉽게 답을 찾는 것은 보안 해시 공격을 실행한 증거가 아니다. 실제 라이브러리 해시 계산·충돌 탐색·학생 실험은 수행하지 않았다.

중간 과정을 따라가는 예제

자체 대응표 H(a)=00,H(b)=01,H(c)=00,H(d)=10,H(e)=11에서 출력00의 원상 하나, 입력a의 제2원상, 충돌 쌍 하나를 찾자.

  1. 출력00에 대응하는 a 또는c를 고르면 원상이다.

  2. a가 먼저 주어졌으면 다른c가 제2원상이다. a 자신은 허용되지 않는다.

  3. 입력을 자유롭게 고를 수 있으면(a,c)가 충돌 쌍이다.

  4. a와c는 다르고 해시00은 같다.

원상은 a(또는 c), a의 제2원상은 c, 충돌 쌍은 (a,c)다. 요구한 문제에 따라 먼저 주어진 값이 다르다.

종이와 본문으로 직접 해보기

같은 표에서 출력01의 원상을 찾고 입력b의 제2원상이 이 표 안에 있는지 확인하자. 입력d와e는 충돌인가?

힌트 보기

입력의 동일성과 출력의 동일성을 따로 검사하자.

풀이 보기

01의 원상은 b다. 표의 다섯 입력 중 b와 같은 01을 갖는 다른 입력은 없어 이 제한된 표 안에서는 제2원상을 찾지 못한다. d와 e의 출력은 각각 10과 11이므로 충돌이 아니다. 표 밖 입력에 대해서는 정보가 없다.

오해와 반례

충돌 저항 해시에는 충돌이 존재하지 않는다.

유한 출력보다 큰 입력 집합이면 비둘기집 원리상 충돌이 존재한다. 저항성은 특정 자원 범위에서 찾기 어렵다는 뜻이다. 약한 공개 표의 충돌과 실제 알고리즘의 찾기 난도를 혼동하면 안 된다.

소단원 8.2

Merkle 구조

큰 자료 전체를 보내지 않고 그중 한 조각이 어떤 요약에 포함됨을 어떻게 확인할까?

준비 개념과 학습 목표

준비 개념

  • 해시와 충돌 저항성

  • 이진 트리

  • 순서와 연결

학습 목표

  • leaf와 내부 노드 해시 입력을 구별한다.

  • 네 leaf의 포함 경로를 순서대로 재구성한다.

  • 포함 증명·원본 진실성·append-only 증명을 분리한다.

요약을 다시 요약한다

순서 있는 자료 d₀,d₁,d₂,d₃의 leaf를 ℓᵢ=H(0x00||dᵢ)로 만들고 내부 결합을 N(x,y)=H(0x01||x||y)라 하자. ||는 바이트 연결이고 왼쪽·오른쪽 순서가 중요하다. root는 N(N(ℓ₀,ℓ₁),N(ℓ₂,ℓ₃))다. 여기서는 길이가 고정된 해시와 명확한 자료 인코딩을 가정한다.

leaf와 내부 노드의 접두표를 달리하는 domain separation은 자료 자체와 요약 두 개를 결합한 입력을 혼동하지 않게 한다. 모든 Merkle 구현이 같은 트리 모양·인코딩을 쓰는 것은 아니다. 여기서 참고한 RFC9162는 길이에 따라 정해지는 ordered tree 규칙을 갖는다.

형제 요약으로 경로를 채운다

d₂를 검증하려면 ℓ₂를 계산하고 오른쪽 형제 ℓ₃와 결합해 오른쪽 부모를 만든다. 다음에는 왼쪽 부모 p₀₁=N(ℓ₀,ℓ₁)를 받아 root를 재계산한다. 자료 전체 대신 경로에서 빠진 형제 요약을 받으면 된다. leaf index와 전체 tree size도 경로 해석에 필요하다.

기준 root는 별도로 신뢰할 수 있어야 한다. 공격자가 자료·증명·root를 전부 새로 만들어 보내면 내부 계산 일치만으로 원래 자료임을 증명할 수 없다. root의 서명·신뢰하는 배포 경로·기록 시점 같은 인증 조건을 함께 다룬다.

무엇이 증명되었는가

보안 해시와 올바른 인코딩·검증, 인증된 root 가정 아래 포함 증명은 특정 자료가 그 트리에 포함됨을 확인한다. 자료가 사실인지, 모든 필요한 항목이 로그에 들어왔는지, 새 로그가 이전 로그를 보존했는지는 별도 질문이다. RFC의 consistency proof는 이전 leaf들의 append-only 보존을 위한 다른 증명이다.

균형 잡힌2ᵏ leaf에서는 한 포함 경로에 k개 형제 요약이 필요하다. 이 숫자는 네 leaf의 손 구조 계산에 적용한다. 실제 해시 바이트 계산이나 RFC 프로토콜 실행, 공개 로그 서비스 검증은 수행하지 않았다.

중간 과정을 따라가는 예제

네 leaf 트리에서 d₂ 포함을 검증하자. 증명 목록이 [ℓ₃,p₀₁]이고 위치2,크기4,신뢰 root R가 주어졌다. 필요한 계산 순서와 해시 호출 수는?

  1. h₂=H(0x00||d₂)를 만든다. leaf 해시1회다.

  2. 오른쪽 부모 p₂₃=N(h₂,ℓ₃)를 만든다. 순서는 h₂가 왼쪽이다.

  3. R′=N(p₀₁,p₂₃)를 만든다. 이번에는 증명값 p₀₁이 왼쪽이다.

  4. R′=R인지와 위치2가0≤2<4 조건에 맞는지 확인한다.

형제 요약2개를 받아 leaf1회·내부2회, 총 해시3회로 root를 재구성한다. 실제 해시 출력 바이트를 계산한 결과는 아니다.

종이와 본문으로 직접 해보기

d₁을 검증할 때 필요한 형제 요약과 결합 순서를 적자. 네 leaf 트리 전체를 처음 만들 때 해시 횟수는?

힌트 보기

d₁은 왼쪽 하위 트리의 오른쪽 leaf다.

풀이 보기

증명은 [ℓ₀,p₂₃]다. ℓ₁ 계산 후 p₀₁=N(ℓ₀,ℓ₁), root=N(p₀₁,p₂₃) 순서다. 전체 구성은 leaf4회·부모2회·root1회로7회다.

오해와 반례

Merkle 포함 증명을 통과하면 자료가 현실의 사실임까지 증명된다.

검증은 신뢰 root에 묶인 바이트의 포함에 대한 것이다. 잘못된 주장도 자료로 넣을 수 있으며 root 자체의 신뢰가 없다면 공격자 트리와도 일치한다. 내용 진실성과 공개 로그의 완전성은 별도 증거가 필요하다.

소단원 8.3

비밀번호 해시·salt·KDF

공개된 salt를 더하는데도 왜 같은 비밀번호를 여러 계정에 비교하기 어려워질까?

준비 개념과 학습 목표

준비 개념

  • 해시와 추측

  • 확률적 입력과 공개·비공개

  • 단위 시간 계산

학습 목표

  • 비밀번호용 KDF의 salt·비용 매개변수를 설명한다.

  • salt와 비밀번호 강도·비밀키의 역할을 구별한다.

  • 자체 직렬 비용 모형의 작업 횟수를 계산한다.

되돌리기 대신 후보를 검사한다

비밀번호 저장은 원문을 그대로 저장하거나 나중에 복호화할 수 있는 형태로 보관하는 문제와 다르다. 비밀번호용 해시/KDF는 비밀번호·salt·비용 설정으로 검증값을 만들고 로그인 후보에도 같은 저장 설정을 적용해 비교한다. 알고리즘·버전·salt·매개변수와 검증값을 함께 관리해야 한다.

공격자가 검증값 파일을 얻으면 후보 비밀번호를 오프라인으로 시험할 수 있다. 그래서 일반적인 빠른 파일 해시 한 번만 쓰는 것과 달리 각 후보의 계산 비용을 늘리도록 설계된 방식이 필요하다. 온라인 로그인 횟수 제한은 서버를 거치지 않는 오프라인 계산을 직접 막지 못한다.

salt는 공개해도 되는 서로 다른 입력

비밀번호별 충분히 큰 무작위 salt는 같은 비밀번호의 입력을 계정마다 다르게 만들고 공통 사전 계산의 재사용을 어렵게 한다. salt는 검증에 필요하므로 해시와 함께 저장할 수 있다. salt를 비밀 비밀번호처럼 감추어야만 작동하는 구조가 아니다.

서로 다른 salt가 출력의 수학적 무충돌을 보장하지는 않는다. 같은 비밀번호라고 반드시 같은 저장값이 되는 성질을 없애려는 입력 분리다. 약한 비밀번호의 후보 수가 자동으로 커지거나 사용자 비밀번호에 entropy가 추가되는 것은 아니다. 한 계정의 후보 추측은 여전히 가능하다.

시간·메모리와 실제 환경

Argon2 같은 memory-hard 함수는 메모리와 passes·parallelism 등을 입력으로 갖는다. 비용은 로그인 지연·서버 부하·공격자의 자원에 영향을 주므로 공식 방식과 신뢰할 수 있는 구현을 사용하고 실제 환경을 측정해 설정한다. 이 단원은 특정 운영 설정을 측정하거나 추천값으로 확정하지 않는다.

아래100ms는 설명용 가정이며 실제 Argon2 속도가 아니다. 후보 계산을 직렬로 하고 모든 호출 시간이 같다고 가정한다. 공격자의 병렬 장비·캐시·메모리 제약과 실패 정책은 포함하지 않았다. 코드를 반복 해시해 자체 보안 방식을 만드는 활동은 요구하지 않는다.

중간 과정을 따라가는 예제

자체 직렬 모형에서 한 KDF 호출이100ms다. 후보100개를 계정 하나에 검사할 때와 서로 다른 salt를 가진 계정10개에 각100개씩 검사할 때 시간은?

  1. 한 계정은100호출×0.1초=10초다.

  2. 계정10개의 서로 다른 salt 입력을 각 검사하면10×100=1000호출이다.

  3. 1000×0.1초=100초다.

  4. salt가 같고 동일 알고리즘·매개변수라면 한 후보 계산 결과를 여러 검증값과 비교하는 재사용이 가능하다는 차이를 본다.

단순 직렬 모형은10초와100초다. 실제 공격 속도나 모든 후보가 정답일 확률을 측정한 것이 아니다.

오해와 반례

salt가 공개되면 무용하고, salt를 넣으면 짧은 비밀번호도 추측할 수 없다.

salt는 계정별 사전 계산 공유를 줄이려는 공개 입력이다. 공개여도 역할이 있지만 한 계정의 후보를 검증하는 것은 가능하다.3후보 예제처럼 작은 후보 공간은 느린 함수에서도 시험할 수 있으므로 salt·비용·비밀번호 강도는 역할이 다르다.

한 단계 더

salt를 충분히 큰 무작위 공간에서 독립 생성해도 중복 가능성이 완전히0은 아니다. 실제 구현은 공식 지침의 길이·난수·저장 형식을 따른다. 별도 비밀값을 추가하는 방식은 공개 salt와 역할이 다르며 비밀 관리·회전·복구까지 설계해야 한다. 이 단원에서는 그 운영 체계를 구현하거나 시험하지 않았다.
