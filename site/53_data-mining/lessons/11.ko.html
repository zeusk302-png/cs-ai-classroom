소단원 11.1

MapReduce와 집계

자료를 두 사람이 나누어 센 뒤 결과를 합쳐도 한 사람이 센 것과 같게 하려면 무엇을 전달해야 할까?

준비 개념과 학습 목표

준비 개념

  • 키와 값

  • 합과 평균

  • 결합법칙·교환법칙

학습 목표

  • map·키별 모으기·reduce를 구별한다.

  • 부분 집계의 병합 조건을 확인한다.

  • 부분 평균만 합치는 오류를 고친다.

합과 개수를 정확히 병합하면 모든 통계도 복원할 수 있을까?

새 두 입력 부분은 A=[0,0,6], B=[8,12]다. 모든 값은 정확한 정수이며 같은 키에 속한다. 평균에는 합 s와 개수 n을 보내고, 모집단 분산도 필요하면 제곱합 q를 추가한다. A의 상태는 (6,3,36), B의 상태는 (20,2,208)이며 성분별 덧셈으로 (26,5,244)가 된다. 전체 평균은 26/5다. 이는 실제 MapReduce 실행이 아닌 지정 정수 상태의 손계산이다.

각 부분의 평균만 보내고 크기를 잃으면 전체 평균을 올바르게 병합할 수 없다. 두 부분 평균 2와 10을 단순 평균하면 6인데 전체 평균 26/5와 다르다. 모집단 분산은 q/n−(s/n)²로 계산해 544/25다. 여기서는 표본 분산이 아니라 다섯 값 전체의 모집단 분산을 요구하며 빈 전체에서는 나눗셈을 정의하지 않는다.

요약은 필요한 질문에 맞춰야 한다. 독립 자료 [0,0,6]과 [1,2,3]은 모두 (s,n)=(6,3)이지만 중앙값은 각각 0과 2다. 따라서 합과 개수로 평균을 정확히 복원할 수 있다는 사실이 중앙값까지 복원한다는 뜻은 아니다. 중앙값을 요구하는 집계에 이 요약만 보내는 것은 정보 손실이다.

정수 덧셈의 결합성은 중복 반영의 안전성과도 다르다. A의 같은 부분 결과가 두 번 반영되면 (32,8,280)이 되어 평균은 4다. 자체 대안은 고정 작업 판본 안에서 부분 ID와 정확한 내용의 원자적 등록·합계를 하나의 보호 구간에서 확정하는 장부다. 같은 ID와 같은 내용은 과거 반영을 반환하고 다른 내용은 충돌로 거절한다. 서로 다른 정당한 레코드가 같은 값이라는 이유로 제거하지 않는다. 외부 알림까지 자동 한 번으로 보장하는 설계는 아니다.

먼저 확인할 개념
  • 병합 상태와 부수효과

    앞 본문의 합·개수 상태 및 외부 효과의 별도 원자/멱등 조건을 제곱합과 중복 반영에 적용한다.

  • 작은 요약의 목적

    앞 본문의 모든 값을 요구하는 문제와 작은 요약을 병합하는 문제의 구별을 중앙값 손실로 구체화한다.

키가 같은 중간 값을 모은다

MapReduce에서 map은 입력 레코드를 중간 키·값으로 바꾼다. 중간 단계는 같은 키의 값들을 모아 reduce로 전달한다. 단어를 세려면 각 단어에 값 1을 붙이고 같은 단어의 값을 더할 수 있다.

입력 파일이 나뉘는 위치와 최종 집계 키가 나뉘는 위치는 다르다. 같은 단어가 서로 다른 입력 부분에 나와도 최종적으로 합쳐야 한다. 아래 가상 단어는 이미 토큰으로 나뉘었고 대소문자·문장부호 처리 규칙은 별도 문제다.

병합 가능한 작은 요약을 만든다

정수 합은 결합 순서와 교환에 관계없이 같은 결과를 만든다. 같은 의미와 자료형의 부분 합을 모아 합칠 수 있어 선택적 combiner가 전송 전 값을 줄일 수 있다. 결합 결과를 다음 병합의 입력으로 다시 쓸 수 있어야 한다.

평균은 부분 평균의 단순 평균으로 병합하면 크기 차이를 잃는다. 합 s와 개수 n의 쌍을 유지하고 (s₁,n₁)⊕(s₂,n₂)=(s₁+s₂,n₁+n₂)로 병합한 뒤 s/n을 구한다. 빈 전체는 n=0이라 평균 미정의이며 빈 부분의 상태 (0,0)는 병합 항등원이다.

재실행과 순서에 주의한다

분산 작업은 실패 시 다시 실행될 수 있다. map 안에서 외부 수업 등록을 추가하는 부수효과는 반복 시 중복될 수 있어 별도 원자성·멱등성 설계가 필요하다. 여기서 실패 복구가 모든 외부 효과를 자동 한 번으로 만드는 것으로 설명하지 않는다.

부동소수점 덧셈은 유한 정밀도 때문에 수학적 실수의 결합법칙과 다를 수 있다. 결과 재현성이나 정확한 합 요구를 따로 정한다. 이 단원의 정수 종이 집계를 실제 클러스터와 장애 복구 시험으로 부르지 않는다.

중간 과정을 따라가는 예제

첫 부분 토큰은 [a,b,a], 둘째는 [b,c]다. 각 map의 (단어,1)과 키별 최종 합, 부분 집계를 썼을 때 전송 레코드 수를 구하라.

  1. map은 첫 부분 (a,1),(b,1),(a,1), 둘째 (b,1),(c,1)을 만든다. 총 5개다.

  2. 첫 부분을 합치면 (a,2),(b,1), 둘째는 (b,1),(c,1)로 총 4개다.

  3. 최종 a=2, b=2, c=1이며 합은 5다. 부분 집계로 줄어든 수 1개가 실제 바이트 절감률과 동일하다고 단정하지 않는다.

최종 a2·b2·c1, 부분 집계 전 5개와 후 4개 레코드다.

크기를 유지한 평균과 분산

A와 B의 평균 및 모집단 분산을 구하라.

  1. 합 26과 개수 5로 평균은 26/5다.

  2. 분산은 244/5−676/25=(1220−676)/25=544/25다.

비교할 점

실제 부동소수점 분산 알고리즘의 안정성이나 분산 엔진 성능은 측정하지 않았다.

동일 요약이 숨기는 중앙값

[0,0,6]과 [1,2,3]의 (s,n)과 중앙값을 비교하라.

  1. 두 상태의 합은 6이고 개수는 3이다.

  2. 정렬된 세 값의 가운데는 각각 0과 2다.

같은 (6,3)에서 다른 중앙값이 나오므로 이 요약만으로 중앙값을 결정할 수 없다.

비교할 점

새 반례는 (s,n)의 부족함을 보이며 모든 다른 요약의 불가능성을 증명하는 것은 아니다.

힌트 보기

풀이 보기

오해와 반례

각 부분의 평균을 다시 평균하면 항상 전체 평균이다.

부분 크기가 다르면 가중치가 사라진다. 합과 개수 또는 같은 정보를 보존하는 상태로 병합한다.

같은 부분 ID를 확인한 뒤 보호 구간 밖에서 합계를 바꾸는 두 요청을 허용했다. 중복 방지를 고쳐라.

힌트 1

풀이와 답 확인

  2. 이미 반영된 같은 내용은 재합산하지 않고 다른 내용은 충돌로 거절한다.

이는 자체 장부의 계약이며 실제 저장 시스템의 원자성 시험은 하지 않았다.

  • persist 요청과 실제 자료 계산·재사용을 구별한다.

잃은 캐시를 재계산해도 같은 입력과 효과를 다시 보는가?

새 자체 평가 모형의 두 부분은 P=[1,2], Q=[3,4]이며 f(x)=x²다. 순차적으로 부분을 평가하고, 각 action은 모든 결과를 요구하며, 캐시가 있으면 f를 다시 부르지 않는다고 지정한다. 최적화·추측 실행·실패 재시도·다른 비용은 제외한다. 이 호출 장부는 실제 Spark task 수나 보장된 실행 횟수가 아니다.

변환 계획과 persist 요청만 적고 action이 없으면 이번 장부의 f 호출은 0회다. 첫 count는 네 값을 계산해 두 부분을 모두 유지하고 결과 4를 반환한다. 그 뒤 Q 캐시만 잃고 sum을 요청하면 P의 1,4는 재사용하고 Q의 9,16을 다시 계산한다. 합은 30이며 첫 action부터 누적 f 호출은 6회다.

같은 결과 30이라도 부수효과는 반복될 수 있다. f가 호출할 때마다 외부 목록에 입력 ID를 추가한다고 별도로 가정하면 목록은 [1,2,3,4,3,4]가 된다. 논리 입력 네 개와 호출 여섯 번, 외부 기록 여섯 개를 구별한다. 캐시를 정확한 한 번 처리의 증거로 사용하지 않는다.

재계산의 값 보존에는 고정 입력과 결정적 변환 조건이 필요하다. 독립 대안에서 f가 외부 배수 m을 읽고 m×x²를 반환한다고 하자. 처음 m=1로 두 부분을 유지한 뒤 m=2로 바뀌고 Q만 잃으면 결과는 [1,4,18,32], 합 55다. 전부 옛 배수의 합 30도 전부 새 배수의 합 60도 아니다. 이는 외부 상태를 읽는 자체 변환의 불일관 사례이며 Spark가 불변 RDD 값을 임의로 바꿨다는 주장이 아니다. 입력·함수·설정 판본을 결과의 계약에 연결한다.

먼저 확인할 개념
  • 계획·action·persist

    앞 본문의 지연 계산과 부분 손실 뒤 재계산을 명시적 종이 호출 장부로 추적한다.

  • 외부 효과의 별도 계약

    앞 본문의 반복 작업과 부수효과 원자/멱등 조건을 재계산의 외부 목록에 적용한다.

자료 부분과 계산 계획을 표현한다

Spark의 RDD는 여러 부분으로 나뉘어 병렬 처리할 수 있는 자료 추상화다. Driver는 프로그램을 시작하고 작업을 조정한다. Worker의 값을 driver의 보통 지역 변수와 같은 공유 상태로 생각하면 안 된다.

RDD는 Spark의 한 추상화이며 DataFrame 등 다른 인터페이스도 있다. 이 단원은 작은 RDD 개념을 설명하고 SQL 최적화나 최신 모든 API를 다뤘다고 하지 않는다. 장치 수와 레코드의 순서도 동일한 개념이 아니다.

계획과 결과 요청을 나눈다

map·filter 같은 transformation은 새 RDD의 계산 계획을 만든다. Action은 필요한 계산을 요청하여 개수나 집계 결과 등을 얻는다. 변환 호출만으로 모든 항목의 함수가 이미 실행됐다고 결론내리지 않는다.

예를 들어 짝수만 남기고 제곱하는 계획에서 count와 sum을 요청하면 서로 다른 결과를 얻는다. 두 action은 일반적으로 필요한 계산을 다시 수행할 수 있다. 정확한 실제 작업 수는 엔진 최적화와 실행 조건에 따라 확인해야 한다.

저장 요청과 실제 유지 상태를 나눈다

persist나 cache는 재사용을 위해 결과를 유지하도록 지정할 수 있다. 지연 계산 자체를 즉시 모두 수행하는 명령이라는 뜻은 아니다. 저장 수준·공간·실행 및 손실에 따라 실제 남은 부분을 확인한다.

필요한 부분을 잃으면 다시 계산하는 경우가 있고 메모리와 디스크 저장의 비용도 다르다. collect는 전체 결과를 driver로 모으므로 큰 자료를 무조건 모으는 방식은 위험할 수 있다. 작은 집계만 필요한데 모든 중간 레코드를 가져오는지 살펴본다.

  • 분할과 키

전송 레코드를 줄이고 작업을 분산하면 시간과 공간도 같은 비율로 줄까?

새 자료는 같은 키 H의 값 80개와 서로 다른 다른 키의 값 20개다. 두 입력 부분에는 각각 H가 40개와 다른 키가 10개 있다. 원레코드는 각각 16 B, 키별 안전한 요약은 각각 64 B인 자체 고정 크기 모형이다. 원자료 전송은 1600 B이며 입력 부분별 집계 뒤에는 H 요약 두 개와 다른 키 요약 20개로 22개, 1408 B다. 레코드 감소 78%와 바이트 감소 12%를 구별한다.

별도 시간 모형에서는 부분 집계 없이 원레코드 하나를 처리하는 데 1 ms가 걸린다. 네 reduce 작업 중 H가 한 작업에 모이고 다른 키가 나머지에 7,7,6개로 배분되면 종료 시간은 80 ms다. 네 작업의 전체 자료량이 분산됐다는 말만으로 한 키의 작업 80개가 네 곳에 나뉘지 않는다.

독립 대안은 H를 네 보조 키로 나누고 각 20개를 처리한 뒤 원래 H로 병합한다. 첫 단계 네 작업에는 각각 H 20개와 다른 키 5개를 배정해 동시에 시작하므로 25 ms다. 모두 끝난 뒤 H 요약 네 개를 하나의 작업이 각각 1 ms로 병합하면 둘째 단계는 4 ms, 합계 경과는 29 ms다. 단계 간 장벽·중첩 없음·다른 비용 제외를 가정한다. 네 보조 키 결과를 최종 H 답 네 개로 남기지 않는다.

이 시간 대안의 전송은 첫 원레코드 1600 B와 추가 H 요약 네 개의 256 B를 합쳐 1856 B다. 원자료 전송만 하는 1600 B보다 16% 증가한다. 앞 단락의 입력 부분별 집계 대안과 조건을 섞지 않는다. 시간 개선과 통신 증가가 함께 가능하며 실제 클러스터 측정은 아니다.

한 작업의 동시 공간은 cache 300 MiB, 집계 상태 180 MiB, 버퍼 50 MiB로 530 MiB다. 그 작업의 512 MiB를 18 MiB 넘는다. cache를 30 MiB 줄이면 합은 500 MiB이고 여유는 12 MiB지만 제외한 runtime 비용까지 감당한다는 보장은 없다. 다른 작업이나 클러스터 전체의 빈 공간은 이 작업의 사용 가능 공간과 같은 값이 아니다.

먼저 확인할 개념
  • 전송 바이트와 한 작업 공간

    앞 본문의 크기·최대 시간·동시 공간 조건을 큰 키와 두 단계 작업으로 확장한다.

  • 요약의 병합 의미

    앞 본문의 키별 집계와 안전한 요약 병합을 보조 키의 최종 H 복원에 적용한다.

같은 키를 모으는 이동이 생긴다

서로 다른 부분의 같은 키를 함께 처리하려면 shuffle 같은 재분배가 필요할 수 있다. 자료를 직렬화하고 네트워크나 디스크로 옮기는 비용이 생긴다. 이미 알맞게 나뉜 자료를 재사용할 수 있는 조건도 있어 모든 연산의 전송량이 항상 같지는 않다.

groupByKey로 모든 값을 모으는 요구와 작은 요약을 병합하는 요구는 다르다. 가능한 집계에서는 먼저 합을 줄일 수 있지만 모든 값을 필요로 하는 문제에 임의 요약을 적용하면 정보를 잃는다. 정확한 연산 목적을 정한 뒤 비용을 줄인다.

큰 키와 메모리 상태를 찾는다

키 하나에 값이 몰리면 그 키의 작업이 병목이 될 수 있다. 전체 자료가 많지 않아도 한 작업의 메모리와 시간이 클 수 있다. 일부 메모리 구조가 공간을 넘으면 디스크로 spill하여 추가 비용이 생길 수 있다.

캐시 크기만으로 전체 메모리 필요량을 끝내지 않는다. 실행 중 집계 상태, 직렬화 버퍼와 기타 비용이 함께 존재한다. 클러스터 전체 용량 합이 크다는 이유로 특정 driver나 한 작업이 감당할 수 있다고 보장하지 않는다.

단순 비용표의 가정을 공개한다

아래 바이트 표는 헤더·키·전송량을 사람이 정한 장난감 모델이다. 실제 압축·프로토콜·재전송·정렬과 병렬 중첩을 측정하지 않았다. 바이트 감소를 실행 시간의 같은 비율 감소라고 바꾸지 않는다.

공간과 처리 시간을 줄이는 선택에는 재계산 비용과 정확성 요구가 따른다. 큰 원본 전체를 driver에 모으기 전 필요한 출력이 무엇인지 확인한다. 실측은 작업 조건·표본·실패 및 측정 방법을 함께 남겨야 한다.

중간 과정을 따라가는 예제

가상으로 중간 100개 레코드가 각각 20 byte이고 모두 전송된다. 안전한 부분 집계 뒤 10개 레코드가 각각 28 byte다. 전후 바이트와 감소 비율을 구하라.

  1. 전송 전은 100×20=2000 byte다.

  2. 부분 집계 후는 10×28=280 byte다. 개수는 90% 감소해도 바이트는 같은 비율이 아니다.

  3. 줄어든 양은 1720 byte, 감소 비율 1720/2000=86%다.

2000 byte에서 280 byte로 86% 감소한다. 실제 네트워크 측정이 아니다.

  1. 개수는 100개에서 22개로 78% 감소한다.

기본 세 소단원 전체, 두 실제 primary의 관련 범위, 같은 11단원의 세 고유 선수 설명을 읽었다. 정상 상태 (26,5,244)의 평균은 26/5, 모집단 분산은 544/25, 표본 분산은 136/5다. 중복 상태 (32,8,280)의 평균은 4다. 같은 (6,3)에서 중앙값 0과 2가 나오는 두 자료를 손대조했다. 고정 평가 규약의 count는 4, sum은 30이다. Q 손실 뒤 누적 호출은 6회이며 이후 두 부분을 모두 잃으면 10회다. 손실 없는 두 action의 호출은 4회이고 비캐시 대안은 8회다. 외부 기록 여섯 개와 논리 입력 네 개를 구별하고, 배수 판본 혼합의 합 55와 일관된 옛 합 30·새 합 60을 확인했다. 원자료 전송 1600 B에서 부분 요약 1408 B로 감소하는 비율은 12%다. 단일 H 작업 모형의 종료는 80 ms이고 평균은 25 ms다. 별도 두 단계 경과는 29 ms이며 전송 1856 B는 16% 증가한 값이다. 동시 공간 530 MiB는 18 MiB 초과하며 변경 공간 500 MiB의 여유는 12 MiB다. 요약 크기의 엄격 경계 z<800/11에서 양의 정수 크기는 1부터 72 B까지임을 확인했다. 저장본 전체의 세 표, 여섯 예제, 12과제의 힌트·풀이·답·오답, recap, 전이, 출처와 검산을 재독했고 여섯 의미 HTML 앵커를 검증했다.
