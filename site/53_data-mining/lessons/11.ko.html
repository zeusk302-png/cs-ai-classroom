소단원 11.1

MapReduce와 집계

자료를 두 사람이 나누어 센 뒤 결과를 합쳐도 한 사람이 센 것과 같게 하려면 무엇을 전달해야 할까?

준비 개념과 학습 목표

준비 개념

  • 키와 값

  • 합과 평균

  • 결합법칙·교환법칙

학습 목표

  • map·키별 모으기·reduce를 구별한다.

  • 부분 집계의 병합 조건을 확인한다.

  • 부분 평균만 합치는 오류를 고친다.

키가 같은 중간 값을 모은다

MapReduce에서 map은 입력 레코드를 중간 키·값으로 바꾼다. 중간 단계는 같은 키의 값들을 모아 reduce로 전달한다. 단어를 세려면 각 단어에 값 1을 붙이고 같은 단어의 값을 더할 수 있다.

입력 파일이 나뉘는 위치와 최종 집계 키가 나뉘는 위치는 다르다. 같은 단어가 서로 다른 입력 부분에 나와도 최종적으로 합쳐야 한다. 아래 가상 단어는 이미 토큰으로 나뉘었고 대소문자·문장부호 처리 규칙은 별도 문제다.

병합 가능한 작은 요약을 만든다

정수 합은 결합 순서와 교환에 관계없이 같은 결과를 만든다. 같은 의미와 자료형의 부분 합을 모아 합칠 수 있어 선택적 combiner가 전송 전 값을 줄일 수 있다. 결합 결과를 다음 병합의 입력으로 다시 쓸 수 있어야 한다.

평균은 부분 평균의 단순 평균으로 병합하면 크기 차이를 잃는다. 합 s와 개수 n의 쌍을 유지하고 (s₁,n₁)⊕(s₂,n₂)=(s₁+s₂,n₁+n₂)로 병합한 뒤 s/n을 구한다. 빈 전체는 n=0이라 평균 미정의이며 빈 부분의 상태 (0,0)는 병합 항등원이다.

재실행과 순서에 주의한다

분산 작업은 실패 시 다시 실행될 수 있다. map 안에서 외부 수업 등록을 추가하는 부수효과는 반복 시 중복될 수 있어 별도 원자성·멱등성 설계가 필요하다. 여기서 실패 복구가 모든 외부 효과를 자동 한 번으로 만드는 것으로 설명하지 않는다.

부동소수점 덧셈은 유한 정밀도 때문에 수학적 실수의 결합법칙과 다를 수 있다. 결과 재현성이나 정확한 합 요구를 따로 정한다. 이 단원의 정수 종이 집계를 실제 클러스터와 장애 복구 시험으로 부르지 않는다.

중간 과정을 따라가는 예제

첫 부분 토큰은 [a,b,a], 둘째는 [b,c]다. 각 map의 (단어,1)과 키별 최종 합, 부분 집계를 썼을 때 전송 레코드 수를 구하라.

  1. map은 첫 부분 (a,1),(b,1),(a,1), 둘째 (b,1),(c,1)을 만든다. 총 5개다.

  2. 첫 부분을 합치면 (a,2),(b,1), 둘째는 (b,1),(c,1)로 총 4개다.

  3. 최종 a=2, b=2, c=1이며 합은 5다. 부분 집계로 줄어든 수 1개가 실제 바이트 절감률과 동일하다고 단정하지 않는다.

최종 a2·b2·c1, 부분 집계 전 5개와 후 4개 레코드다.

종이와 본문으로 직접 해보기

첫 수치 부분 [2,4], 둘째 [10]의 전체 평균을 부분 상태로 구하라. 부분 평균만 단순 평균하면?

힌트 보기

합과 개수를 둘 다 전달한다.

풀이 보기

부분 상태 (6,2),(10,1)을 병합하면 (16,3)으로 평균 16/3이다. 부분 평균 3과 10을 단순 평균하면 13/2로 틀린다.

오해와 반례

각 부분의 평균을 다시 평균하면 항상 전체 평균이다.

부분 크기가 다르면 가중치가 사라진다. 합과 개수 또는 같은 정보를 보존하는 상태로 병합한다.

답과 이유 보기

미정의다.

정수 합과 부동소수점 합은 항상 같은 결합 규칙을 갖는가?

한 단계 더

(s,n) 병합은 성분별 정수 덧셈이라 결합·교환 법칙을 만족한다. 세 부분 (6,2),(10,1),(0,0)을 어느 순서로 병합해도 (16,3)이다. 최종 나눗셈 전에는 합·개수 상태를 유지해야 한다.

Spark 개념

변환을 적었다는 것과 실제 결과를 계산해 받았다는 것은 어떻게 다를까?

준비 개념과 학습 목표

준비 개념

  • 변환 함수

  • 리스트 filter/map

  • 합과 개수

학습 목표

  • RDD와 driver 역할을 구별한다.

  • transformation과 action을 추적한다.

  • persist 요청과 실제 자료 계산·재사용을 구별한다.

자료 부분과 계산 계획을 표현한다

Spark의 RDD는 여러 부분으로 나뉘어 병렬 처리할 수 있는 자료 추상화다. Driver는 프로그램을 시작하고 작업을 조정한다. Worker의 값을 driver의 보통 지역 변수와 같은 공유 상태로 생각하면 안 된다.

RDD는 Spark의 한 추상화이며 DataFrame 등 다른 인터페이스도 있다. 이 단원은 작은 RDD 개념을 설명하고 SQL 최적화나 최신 모든 API를 다뤘다고 하지 않는다. 장치 수와 레코드의 순서도 동일한 개념이 아니다.

계획과 결과 요청을 나눈다

map·filter 같은 transformation은 새 RDD의 계산 계획을 만든다. Action은 필요한 계산을 요청하여 개수나 집계 결과 등을 얻는다. 변환 호출만으로 모든 항목의 함수가 이미 실행됐다고 결론내리지 않는다.

예를 들어 짝수만 남기고 제곱하는 계획에서 count와 sum을 요청하면 서로 다른 결과를 얻는다. 두 action은 일반적으로 필요한 계산을 다시 수행할 수 있다. 정확한 실제 작업 수는 엔진 최적화와 실행 조건에 따라 확인해야 한다.

저장 요청과 실제 유지 상태를 나눈다

persist나 cache는 재사용을 위해 결과를 유지하도록 지정할 수 있다. 지연 계산 자체를 즉시 모두 수행하는 명령이라는 뜻은 아니다. 저장 수준·공간·실행 및 손실에 따라 실제 남은 부분을 확인한다.

필요한 부분을 잃으면 다시 계산하는 경우가 있고 메모리와 디스크 저장의 비용도 다르다. collect는 전체 결과를 driver로 모으므로 큰 자료를 무조건 모으는 방식은 위험할 수 있다. 작은 집계만 필요한데 모든 중간 레코드를 가져오는지 살펴본다.

중간 과정을 따라가는 예제

자체 종이 입력 [1,2,3,4,5,6]에서 짝수를 filter하고 제곱을 map한다. count와 합 집계를 요청했을 때 논리적 결과는?

  1. filter 결과의 의미는 [2,4,6]이다. 아직 action 없이 실제 계산이 끝났다고 하지 않는다.

  2. 제곱 결과의 의미는 [4,16,36]이다.

  3. count는 3, 합은 4+16+36=56이다. 결과 값과 실행 작업 수는 다른 기록이다.

논리적 count 3, 합 56이다. 실제 Spark 실행 결과가 아니다.

힌트 보기

풀이 보기

오해와 반례

cache를 쓰면 모든 데이터가 영구히 RAM에 있으며 다시 계산하지 않는다.

지연 계산·저장 수준·공간·손실 조건에 따라 다르다. 실제 유지와 다시 계산 가능성을 확인한다.

소단원 11.3

통신·메모리 비용

계산량을 절반으로 나누어도 같은 키를 한 곳에 모으는 시간이 커질 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 레코드와 바이트

  • 분할과 키

  • 최대와 합

학습 목표

  • shuffle의 자료 이동을 설명한다.

  • 레코드 수와 전송 바이트를 구별한다.

  • key skew와 메모리 한계를 비용표로 확인한다.

같은 키를 모으는 이동이 생긴다

서로 다른 부분의 같은 키를 함께 처리하려면 shuffle 같은 재분배가 필요할 수 있다. 자료를 직렬화하고 네트워크나 디스크로 옮기는 비용이 생긴다. 이미 알맞게 나뉜 자료를 재사용할 수 있는 조건도 있어 모든 연산의 전송량이 항상 같지는 않다.

groupByKey로 모든 값을 모으는 요구와 작은 요약을 병합하는 요구는 다르다. 가능한 집계에서는 먼저 합을 줄일 수 있지만 모든 값을 필요로 하는 문제에 임의 요약을 적용하면 정보를 잃는다. 정확한 연산 목적을 정한 뒤 비용을 줄인다.

큰 키와 메모리 상태를 찾는다

키 하나에 값이 몰리면 그 키의 작업이 병목이 될 수 있다. 전체 자료가 많지 않아도 한 작업의 메모리와 시간이 클 수 있다. 일부 메모리 구조가 공간을 넘으면 디스크로 spill하여 추가 비용이 생길 수 있다.

캐시 크기만으로 전체 메모리 필요량을 끝내지 않는다. 실행 중 집계 상태, 직렬화 버퍼와 기타 비용이 함께 존재한다. 클러스터 전체 용량 합이 크다는 이유로 특정 driver나 한 작업이 감당할 수 있다고 보장하지 않는다.

단순 비용표의 가정을 공개한다

아래 바이트 표는 헤더·키·전송량을 사람이 정한 장난감 모델이다. 실제 압축·프로토콜·재전송·정렬과 병렬 중첩을 측정하지 않았다. 바이트 감소를 실행 시간의 같은 비율 감소라고 바꾸지 않는다.

공간과 처리 시간을 줄이는 선택에는 재계산 비용과 정확성 요구가 따른다. 큰 원본 전체를 driver에 모으기 전 필요한 출력이 무엇인지 확인한다. 실측은 작업 조건·표본·실패 및 측정 방법을 함께 남겨야 한다.

중간 과정을 따라가는 예제

가상으로 중간 100개 레코드가 각각 20 byte이고 모두 전송된다. 안전한 부분 집계 뒤 10개 레코드가 각각 28 byte다. 전후 바이트와 감소 비율을 구하라.

  1. 전송 전은 100×20=2000 byte다.

  2. 부분 집계 후는 10×28=280 byte다. 개수는 90% 감소해도 바이트는 같은 비율이 아니다.

  3. 줄어든 양은 1720 byte, 감소 비율 1720/2000=86%다.

2000 byte에서 280 byte로 86% 감소한다. 실제 네트워크 측정이 아니다.
