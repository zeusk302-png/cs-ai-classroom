소단원 5.1

delegation

도서관 안내 직원이 책 검색을 다른 직원에게 맡기면 누가 이용자에게 답할 책임이 있을까?

준비 개념과 학습 목표

준비 개념

  • 객체는 상태와 메서드를 갖는다.

  • 참조 두 개가 같은 객체를 가리킬 수 있다.

  • 호출 계약은 성공과 실패 시 행동을 정한다.

학습 목표

  • 위임 호출의 수신자를 구별한다.

  • 합성 구조와 행동적 위임을 연결한다.

  • 공유 상태·오류·수명 책임을 설명한다.

바깥 객체의 format을 바꾸면 안쪽 join도 자동으로 바뀔까?

앞 본문에서 FrontDesk는 Catalog를 참조하여 조회를 맡겼다. 참조를 통한 호출은 안쪽 객체의 수신자를 바깥 객체로 바꾸지 않는다. 새 Formatter F의 format(x)는 문자열 x를 그대로 반환한다. join(x,y)는 자기 자신의 format(x)와 format(y)를 호출하고 두 결과 사이에 |를 붙인다. 이 사례에서 자기 자신은 항상 F다.

장식자 U는 F를 보관한다. U.format(x)는 F.format(x)의 결과를 대문자로 바꾸며 바깥 format 호출 횟수 c를 1 늘린다. U.join은 F.join에 그대로 맡긴다. c=0에서 U.format("a")는 A를 반환하고 c는 1이다. 이어 U.join("b","c")는 b|c를 반환하며 c는 여전히 1이다. 안쪽의 두 자기 호출은 U.format을 거치지 않는다.

원하는 새 계약이 join의 두 항목에도 대문자 변환을 적용하는 것이라면, U.join은 U.format(x), U.format(y)를 직접 조합할 수 있다. 같은 초기 상태에서 첫 format 뒤 이 join을 수행하면 B|C가 반환되고 c는 3이다. 기존 F.join의 코드가 고장 난 것이 아니라, 바깥 장식자가 약속한 의미를 구현하는 경계를 선택하는 문제다.

다른 선택은 F가 명시적인 formatCallback을 받아 join에서 그 콜백을 호출하게 하는 것이다. 이때 재진입 고리를 만들지 않도록 U.format은 F의 원래 format만 호출한다. U.format이 다시 F.join을 호출하도록 바꾸면 호출 그래프가 순환할 수 있다. 아래 기록은 새 클래스 실행이 아닌 명시된 순차 호출 계약의 손추적이다.

먼저 확인할 개념
  • 참조와 실제 호출 수신자

    위임 호출의 자기 자신이 누구인지 결정한 뒤 바깥 호출 기록을 계산한다.

  • 내부 자기 호출과 확장 지점

    외부 forwarding과 내부 호출 재지정을 구별한다.

1. 부탁하는 객체와 실행하는 객체

delegation은 한 객체가 맡은 작업을 다른 객체의 연산에 넘겨 수행하도록 하는 것이다. 이 단원은 흔한 객체 부품 호출의 의미로 사용한다. 언어의 delegate 타입이나 객체 시스템의 특별한 this 재결합 기능과 같은 뜻으로 한꺼번에 쓰지 않는다. FrontDesk가 Catalog 필드를 보유하면 합성 구조이고, FindBook을 처리하면서 Catalog.Lookup을 부르면 위임 행동이다.

부품을 갖는 것만으로 위임이 일어나지는 않는다. 필드를 전혀 사용하지 않을 수도 있다. 또한 FrontDesk가 Catalog를 상속하는 것은 아니다. 외부 이용자에게 공개한 FindBook 계약은 여전히 FrontDesk가 지켜야 한다. Catalog가 반환한 값에 아무 설명 없이 추가 수수료나 별도 상태 변경을 끼워 넣으면 외부 계약을 깨뜨릴 수 있다.

2. 두 객체의 상태를 따로 추적하기

자체 순차 모형에서 Catalog.Lookup(code)는 조회 횟수를 1 증가시키고 code=7 일 때 "moon", code=9 일 때 "river"를 반환한다. FrontDesk.FindBook은 Lookup을 한 번 호출한 뒤 반환 문자열 앞에 "title:"을 붙인다. 입력은 7 또는 9 로 제한하고 해당 Lookup은 실패하지 않는다고 가정한다. 두 FrontDesk가 동일 Catalog를 참조하면 조회 횟수는 공유된다.

FrontDesk A가 7 을, B가 9 를 조회하면 각각 title:moon과 title:river를 반환하고 Catalog 횟수는 0→1→2 다. FrontDesk가 두 개여도 Catalog 객체는 하나다. 다른 부품 두 개를 생성한 경우와 같은 결과일 필요는 없다. 종이 모형의 모든 상태는 주어진 정의로 계산했으며 검색 서비스나 교육 프로그램을 실행하지 않았다.

3. 호출 경계에서 정해야 할 정책

보통의 부품 메서드 호출에서는 수신자가 부품 객체다. Catalog 내부에서 자기 메서드를 부르면 그 자기 참조는 Catalog를 가리킨다. 이 호출이 자동으로 FrontDesk의 비슷한 이름 메서드에 돌아오는 것은 아니다. 돌아오게 하려면 callback 같은 별도 관계를 명시해야 한다. 무한 순환 위임을 피하려면 A→B→A에서 어떤 입력에 호출을 끝낼지도 정한다.

생성자에서 null 부품을 거부할지, 조회 실패를 전달할지 다른 응답으로 바꿀지, 부품을 누가 종료할지 계약에 적는다. 특히 공유 Catalog를 A가 일방적으로 종료하면 B의 이용이 깨질 수 있다. 전달받은 참조가 배타적 소유권을 뜻하지는 않는다. 동시 호출을 허용하려면 공유 횟수 갱신의 동기화 조건도 추가해야 하며 순차 계산 2 를 동시 실행 보장으로 주장하지 않는다.

중간 과정을 따라가는 예제

공유 Catalog의 조회 횟수는 0 이다. A.FindBook(7), B.FindBook(9), A.FindBook(7)을 순서대로 처리한 반환값과 최종 횟수를 구하라.

  1. A와 B의 필드 화살표가 같은 Catalog로 향하는 그림을 그린다.

  2. 첫 7 조회는 moon을 받아 title:moon을 반환하고 공유 횟수는 1 이다.

  3. B의 9 조회는 river를 받아 title:river를 반환하고 공유 횟수는 2 다.

  4. 마지막 7 조회도 Lookup을 한 번 부르므로 title:moon과 횟수 3 을 얻는다.

  5. 각 호출의 반환 문자열과 부품의 공유 횟수를 서로 다른 칸에 적는다.

반환 순서는 title:moon / title:river / title:moon이며 공유 횟수 3 이다.

조건을 바꾸어 비교하기

같은 첫 결과 뒤에서 갈리는 장식 범위

표의 두 설계에서 U.format("a") 뒤 U.join("b","c")를 추적하라.

  1. 첫 호출은 두 설계 모두 A를 반환하며 c=1이다.

  2. forwarding join은 F의 두 자기 호출로 b|c를 반환하고 바깥 c를 바꾸지 않는다.

  3. 직접 구성 join은 U.format에 두 번 진입하여 B|C를 반환하고 c=3이 된다.

첫 반환이 같아도 join의 장식 범위와 계측 결과가 다르다.

비교할 점

합성이라는 구조 이름만으로 모든 내부 동작이 바깥 장식을 통과한다고 추론하지 않는다.

명시 콜백의 안전한 방향과 재진입 고리

F.join이 받은 콜백을 각 항목에 적용한다. 콜백 U.format은 F의 원래 format을 호출한다. 이어 U.format을 F.join(x,x)에 맡기는 잘못된 변형을 비교하라.

  1. 정상 경로는 F.join→U.format→F.format에서 끝나므로 항목 두 개가 대문자로 바뀐다.

  2. 잘못된 경로는 F.join→U.format→F.join으로 돌아온다. 종료 조건이 별도로 없으므로 첫 결과에 도달하지 못한다.

  3. 콜백이라는 이름보다 호출 간선과 종료 경계를 확인한다.

정상 콜백은 두 항목을 변환하지만 변형 고리는 비종료다.

비교할 점

원래 F.join을 그대로 맡기는 경우와 명시 콜백 주입을 구분한다.

종이와 본문으로 직접 해보기

풀이 보기

오해와 반례

위임하면 책임도 전부 부품으로 넘어가고 자기 참조는 자동으로 외부 객체를 가리킨다.

FrontDesk는 공개 약속을 지킬 책임이 남는다. 일반 부품 호출에서 Catalog의 자기 참조는 Catalog다. 공유 부품의 종료와 순환 호출은 자동 해결되지 않는다. title: 접두사가 계약인데 부품 값을 그대로 반환하는 경우는 위임을 했어도 외부 약속을 어기는 반례다.

힌트 1

힌트 2

풀이와 답 확인

  2. U.format이 F.format만 호출하도록 유지하여 재진입 고리를 만들지 않는다.

공개 join의 반환까지 장식 계약에 맞춘다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

기존 forwarding join은 원문을 그대로 반환하는 계약을 만족한다. 이를 직접 구성 join으로 바꾸면 언제 기존 고객에게도 안전한가? 문자열 대소문자를 정확히 비교하는 고객을 포함하라.

힌트 1

새 계약과 기존 계약을 분리한다.

힌트 2

b|c와 B|C를 같은 문자열로 취급할 약속이 있는지 확인한다.

풀이와 답 확인

  1. 기존 계약이 원문 보존을 요구하면 직접 구성은 그 계약의 대체 구현이 아니다.

  2. 고객이 처음부터 대문자화 계약을 선택했거나 명세가 이 결과를 허용하는 경우에만 그 관찰에 맞춰 교체한다.

소단원 5.2

subtyping과 대체가능성

같은 push·pop 이름을 제공하는 두 보관함을 언제 안전하게 바꿔 끼울 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 선행 조건은 호출 전에 요구하는 조건이다.

  • 후행 조건은 성공 뒤 값과 상태의 약속이다.

  • 불변식은 허용된 객체 상태를 제한한다.

학습 목표

  • 타입 적합성과 행동 계약 적합성을 구별한다.

  • 입력 집합과 허용 결과로 대체성을 판정한다.

  • 실패·상태변경·여러 호출의 약속을 확인한다.

삽입한 값은 맞지만 다른 키가 사라진 구현도 대체할 수 있을까?

앞 본문의 Queue 계약은 모든 허용 입력과 FIFO 결과를 비교했다. 새 Ledger는 유한 문자열 키에서 정수 값으로 가는 표다. put(k,v)는 어떤 기존 키도 허용하고, 기존 k 값이 있으면 그 값을 반환하며 없으면 MISSING을 반환한다. 성공 뒤 k의 값은 v이고, k 이외의 모든 키와 값은 그대로다. 자원 실패와 동시 호출은 이번 모형 밖이다.

변형 R은 기존 키가 있으면 거절한다. 같은 메서드 이름을 가져도 원래 허용된 덮어쓰기에 더 강한 입력 조건을 붙였다. 변형 C는 처음 표를 비운 다음 k만 저장한다. 요청 키의 최종 값이 맞아도 다른 키 보존 조건을 깨뜨렸다. 반환의 MISSING은 정수 0과 구별된 특별 결과이며 저장 값 0도 정상 값이다.

초기 표 {a:2,b:5}에 put(a,7)을 수행하면 정상 구현은 2를 반환하고 {a:7,b:5}를 남긴다. R은 거절하고 원래 표를 유지한다. C는 지우기 전에 기존 a 값을 보관하여 2를 반환한다고 정해도 {a:7}만 남기므로 기존 계약을 만족하지 않는다. 결과 값 하나가 맞다는 검사로 C를 인정할 수 없다.

반대로 새 입력 범위를 넓히는 일만으로 대체 실패를 단정하지 않는다. 원래 Ledger가 정수 값만 받는다면, 더 넓은 값 타입도 처리하는 별도 구현은 원래 정수 입력에서 기존 결과·효과를 모두 보존할 때 그 고객의 계약을 만족할 수 있다. 허용 입력의 집합과 각 입력의 사후 상태를 함께 비교한다.

먼저 확인할 개념
  • 입력·결과·상태의 대체 계약

    허용 덮어쓰기와 다른 키 보존 조건을 별도로 검사한다.

  • 공유 대상의 관찰

    원래 요청 키 외의 별도 관찰도 같은 대상 상태를 읽는다.

1. 선언이 맞는 것과 행동이 맞는 것

subtyping은 한 타입의 값을 다른 타입의 기대 위치에서 사용할 수 있게 하는 관계다. 언어가 요구하는 메서드 선언과 반환 타입 등이 맞으면 정적 타입 적합성을 확인할 수 있다. 하지만 컴파일러는 일반적으로 FIFO 순서나 실패 시 상태 보존 같은 모든 의미 약속을 자동 증명하지 않는다.

행동적 대체 가능성은 상위 역할을 믿고 작성한 이용자가 하위 구현으로 바꿔도 공개 계약을 깨뜨리지 않는다는 요구다. Cornell의 클라이언트 명세와 구현 확장용 명세의 구별이 중요한 이유다. 이용자가 의존할 계약과 특정 구현의 내부 호출 습관을 섞으면 대체 판단이 불필요하게 좁아지거나 실제 약속이 사라질 수 있다.

2. 더 까다로운 입력을 요구하지 않기

자체 Queue 역할은 초기 빈 상태에서 Push가 정수 1..5 를 허용하고 뒤에 추가하며, Pop은 비어 있지 않을 때 가장 먼저 넣은 값을 제거해 반환한다. 이 모형에는 용량 제한이 없고 호출은 순차적이다. 하위 구현 OddQueue가 1,3,5 만 받으면 원래 허용된 2 를 거부하므로 선행 조건을 강화해 대체성을 깨뜨린다.

ExtendedQueue가 0..5 를 받고 원래 1..5 에는 동일 FIFO를 보장하면 이 부분의 계약은 강화된다. 더 많은 입력을 처리하므로 클라이언트 요구는 줄어들고 원래 입력의 결과 약속은 유지된다. 반면 모든 입력을 받아도 마지막 값을 먼저 돌려주는 구현은 후행 조건을 깨뜨린다. 허용 입력 확대만으로 다른 모든 오류가 면제되지는 않는다.

3. 상태와 실패의 약속까지 유지하기

Push(2), Push(4), Pop()의 계약 결과는 2 와 남은[4]다. 값 4 를 먼저 반환하거나 2 를 반환하면서 둘 다 지우면 각각 반환 순서 또는 상태 약속을 어긴다. 여러 호출 뒤 관찰이 중요하므로 한 메서드의 반환형만 비교해서 충분하지 않다. 상위 불변식과 외부에 약속한 과거 상태의 제약도 지켜야 한다.

실패 계약을 추가하여 TryPush가 용량 부족 때 false와 상태 불변을 보장한다고 하자. false를 반환하되 기존 요소를 지우는 구현은 부적합하다. 예외도 상위 계약에서 허용하는 조건과 효과를 따라야 한다. 입력을 더 넓게 받는 조건과 원래 유효 입력에서 더 강한 결과를 보장하는 조건은 순수한 한 호출 판단의 유용한 기준이며 모든 상태·실패·동시성 계약을 대신하지 않는다.

소단원 5.3

상속취약성과 합성

기반 클래스의 내부 구현만 바꿨는데 파생 클래스의 집계 값이 왜 달라질까?

준비 개념과 학습 목표

준비 개념

  • virtual 호출은 실제 객체의 재정의된 본문을 선택할 수 있다.

  • 공개 계약과 내부 구현 절차는 구별한다.

  • 합성 객체는 공개 연산을 선택적으로 노출한다.

학습 목표

  • 기반 클래스의 자기 호출에 대한 숨은 의존을 추적한다.

  • 동일 공개 결과를 가진 기반 변경의 영향을 비교한다.

  • 상속과 합성의 비용 및 남는 책임을 평가한다.

배치 호출이 실패한 뒤 계측할 값은 요청 수일까, 실제 저장 수일까?

앞 본문의 CountingBag는 내부 자기 호출 구조가 바뀌면 계측 결과도 바뀌었다. 새 Store에는 중복을 허용하는 목록이 있다. addMany(xs)는 앞에서부터 각 값을 저장하며 지정 실패 위치에 도달하면 예외를 던진다. 이미 저장한 접두부는 남고 나머지는 방문하지 않는다. count()는 현재 목록 길이를 반환한다. 단일 작업 중 다른 수정은 없고 count 조회는 실패하지 않는다는 자체 전제를 둔다.

확장 훅 H는 각 항목이 저장된 직후 정확히 한 번 onCommit을 호출한다는 별도 specializer 계약이 있다고 정한다. n=3 중 둘째 저장 직전에 실패하면 저장은 첫 항목 하나이고 H의 성공 카운터도 1이다. public 계약만 있어 onCommit의 호출 시점·횟수가 약속되지 않았다면, 우연한 내부 add 호출을 관찰하는 상속 계측을 이 훅과 같은 보장으로 해석할 수 없다.

합성 계측 W는 before=count()를 읽고 addMany를 맡긴 뒤, 성공이나 예외 어느 경로에서도 after=count()를 읽어 성공 카운터에 after−before를 더하고 원래 예외를 다시 전달한다. 이는 이 모형의 다른 수정 없음·조회 성공·삭제 없음 전제에서 실제 추가 수를 계측한다. 성공 경로에서만 after를 읽는 변형 W0는 일부 저장 뒤 예외가 나면 이미 저장된 항목을 놓친다.

전제가 사라지면 W도 보편 해법이 아니다. 다른 작업이 항목을 두 개 추가하면 차분에는 그 작업이 섞인다. 세대나 요청 ID별 성공 장부처럼 관찰 가능한 추가 계약이 필요할 수 있다. 합성 구조의 장점과 충분한 계측 계약의 존재를 따로 평가한다. 여기서는 정수 오버플로와 할당 실패를 실제 언어로 실행하지 않고 유한 목록과 작은 수만 손추적한다.

먼저 확인할 개념
  • 고객 계약과 확장자 계약

    우연한 내부 호출과 명시적으로 보장된 저장 후 훅을 구별한다.

  • 합성 객체의 관찰 가능 범위

    합성 계측도 내부 성공을 관찰할 공개 계약과 전제가 필요하다.

1. 공개 약속보다 더 많이 의존하기

상속취약성은 파생 구현이 기반의 내부 호출 구조나 상태 표현에 의존하여 기반의 허용된 변경에도 깨지는 문제다. 모든 상속이 취약하거나 모든 기반 변경이 안전하다는 뜻은 아니다. 확장용 호출 계약을 명시하고 보호할 수 있는 계층도 있다. Cornell은 클라이언트 계약과 specializer가 의존하는 구현 약속을 구분한다.

자체 Bag은 Add(x)로 요소 하나를 저장하고 AddMany(xs)로 모든 요소를 저장한다. 중복 허용, 순차 입력, 실패 없음, 초기 빈 상태를 가정한다. 공개 계약은 최종 저장된 요소이며 AddMany가 내부에서 Add를 몇 번 부르는지는 공개 약속이 아니라고 정한다. 그러나 파생 CountingBag이 내부 자기 호출 횟수에 의존하면 이 숨은 사실이 취약점이 된다.

2. 이중 집계가 생기는 경로

모형에서 기반 Bag.AddMany는 각 요소에 대해 가상 Add를 호출한다. CountingBag.Add는 count를 1 올리고 기반 Add를 부른다. CountingBag.AddMany는 count를 입력 길이만큼 올린 뒤 기반 AddMany를 부른다. [3,5,8]의 입력에서 처음 길이 3 을 더하고 내부 가상 Add 세 번이 다시 3 을 더해 count6 이 된다. 요소는 3 개만 저장되므로 제출 요소 수를 세려던 목적과 어긋난다.

기반 AddMany를 내부 저장소에 직접 세 요소를 추가하는 구현으로 바꾸면 공개 Bag 결과는 그대로지만 count는 3 이 된다. 처음 파생 AddMany의 3 만 남고 파생 Add가 호출되지 않기 때문이다. 두 숫자의 차이는 언어 버그가 아니라 의존한 내부 확장 경로의 차이다. 실제 라이브러리의 AddMany 구현을 이 모형처럼 단정하지 않는다. 이 사례는 자체 정의한 가상 호출 모형의 종이 추적이다.

3. 합성으로 노출 경계를 선택하기

CountedBag이 Bag 부품을 보유하고 자기 AddMany에서 성공한 입력 길이를 count에 더한 뒤 부품 AddMany에 한 번 위임한다고 하자. 부품 내부 자기 호출의 수신자는 부품 Bag이므로 외부 CountedBag.Add로 자동 되돌아오지 않는다. 주어진 실패 없는 모형에서 제출 3 개와 count3 을 얻는다. 필요한 역할만 공개하여 기반의 모든 API가 자동으로 바깥에 노출되는 것도 피할 수 있다.

합성도 비용이 있다. 전달 메서드를 작성하고 외부 역할을 명시하며 부품의 상태·수명·예외를 다뤄야 한다. 부분 실패가 가능하다면 입력 길이를 먼저 더하는 방식이 정확한 성공 집계를 보장하지 않으므로 계약 또는 집계 위치를 고쳐야 한다. 상속에서 합성으로 바꾸면 기존 하위 타입 대입이 사라질 수 있어 클라이언트 API도 검토한다. 재사용과 타입 관계를 함께 얻을 필요가 있으며 확장 계약을 유지할 수 있는 경우에는 상속이 합리적일 수 있다.

  1. 차분 5−2=3은 두 작업의 전체 증가다.

  2. 이번 요청의 성공 수는 1이므로 차분을 요청 성공 수로 쓰면 2만큼 과장된다.

  3. 요청 ID별 장부나 작업 분리 같은 추가 관찰 계약 없이 차분만으로 분해할 수 없다.

합성 W의 정확성은 다른 수정 없음이라는 전제에 의존한다.
