소단원 9.1

strategy·command

할인 계산 방법을 바꾸는 일과 나중에 실행할 작업을 저장하는 일은 어떻게 다를까?

준비 개념과 학습 목표

준비 개념

  • 인터페이스

  • 객체와 함수

학습 목표

  • 교체 가능한 정책과 요청 객체를 구별한다.

  • undo의 필요한 상태를 추적한다.

같은 요청을 저장했는데 실행할 때 정책이 바뀌면 결과도 바뀔까요?

전략은 계산을 선택하는 방법이고 명령은 어느 대상에 어떤 요청을 적용할지 보관하는 방법이다. 둘을 함께 쓰면 정책을 언제 읽는지 정해야 한다. 정책 객체의 참조를 저장하는 일은 정책의 의미를 고정하는 일과 다르다. 객체 내부 설정이 나중에 바뀔 수 있기 때문이다.

자체 모형의 카운터 값은 정수 5이고 입력 수량은 3이다. 정책 V1은 수량 그대로 증가량을 반환하고 V2는 수량에 5를 더한다. 명령 C는 생성 때 계산한 증가량 3을 불변 값으로 저장한다. 명령 L은 실행 때 현재 정책으로 증가량을 계산한다. 모든 비교는 새 카운터 값 5에서 독립적으로 시작한다.

실행 성공 뒤에는 실제로 더한 증가량을 기록한다. undo는 다른 변경이 없는 조건에서 그 기록을 빼며, redo는 기록한 증가량을 다시 더한다고 정한다. 이는 제한된 역작업 계약이다. 외부 편집·여러 명령의 순서·외부 전송과 수명은 별도 문제이고, Qt 명령을 실제로 실행한 결과는 아니다.

전략은 바뀌는 계산을 전달한다

Strategy는 같은 역할의 계산 정책을 호출자에게서 분리한다. 정렬에 Comparator를 전달하는 API처럼 호출자는 정렬 흐름을 유지하면서 비교 정책을 바꿀 수 있다. 반드시 정책마다 거대한 클래스가 필요한 것은 아니며 단순 함수로 주입할 수도 있다.

명령은 실행 요청을 객체로 만든다

Command는 대상·인자·작업을 한 요청 단위로 보관하여 나중 실행, 기록, 실행 취소 같은 기능에 연결한다. Qt의 QUndoCommand도 redo와 undo를 파생 구현이 제공한다. 객체 이름만 Command라고 붙였다고 undo가 생기지는 않는다.

되돌릴 정보와 정책 시점을 정한다

문서 추가의 undo는 추가 전 상태 또는 정확한 추가 범위를 알아야 한다. 이미 외부에 보낸 메일처럼 취소가 불가능한 효과도 있다. 요청이 생성될 때 정책을 캡처하는지 실행 때 최신 정책을 읽는지 계약에 적어 예상하지 못한 변경을 막는다.

실행 기록과 현재 정책을 혼동

첫 두 행은 각각 새 값 5에서 시작한다. 마지막 행은 C의 실행 뒤 값 8에서 잘못 취소한 반례이다. 정책 이름이 아닌 실제 적용량이 역작업의 자료다.

중간 과정을 따라가는 예제

종이 문서 AB에 Append(C), Append(D)를 차례로 실행한다. undo는 바로 직전 명령을 한 번만 역순 취소하며 다른 편집은 없다. 별도 가격 100의 정책 normal=p, vip=0.8p를 비교하라.

  1. 첫 추가 뒤 ABC, 둘째 뒤 ABCD다.

  2. 둘째 undo로 D만 지워 ABC가 된다.

  3. 별도 정책 결과 normal 100, vip 80이다. 정책은 계산이고 Append는 저장한 작업이다.

문서는 ABC, 정책은 100/80이다.

조건을 바꾸어 비교하기

캡처한 값과 살아 있는 정책 참조

위 C와 L을 V2 교체 뒤 실행하고 각각 undo하라. 현재 정책은 undo 때도 V2이다.

  1. C는 저장한 3을 더하여 8이 되고 기록한 3을 빼면 5다.

  2. L은 실행 때 3+5=8을 더하여 13이 되고 기록한 8을 빼면 5다.

  3. C가 현재 정책을 다시 계산하여 8을 빼면 0이라 복원 계약을 어긴다.

정상 undo는 둘 다 5로 돌아간다. 실행 결과는 C가 8, L이 13으로 다르다.

비교할 점

앞 본문의 할인 비교에 정책 시점과 실제 역작업 자료를 추가했다.

명령을 합치는 조건은 마지막 실행만 남기는 것이 아니다

초기 문자열은 A이다. 동일 문서의 Append(B), Append(C)를 하나의 명령으로 합치려 한다. 중간 외부 편집은 없고 원문은 명령 외부에서 바뀌지 않는다. 합친 redo/undo와 C만 저장한 변형을 비교하라.

  1. 두 redo의 전체 효과는 A→AB→ABC이다.

  2. 합친 명령은 BC 전체를 더하고 undo에서 그 전체 두 글자를 제거하여 A를 복원한다.

  3. C만 저장하면 redo 결과가 AC이거나 이미 실행된 ABC에서 undo 뒤 AB가 되어 두 명령의 역효과와 다르다.

합친 요청은 BC와 대상 문서를 보존하여 redo의 순방향 효과와 undo의 역순 효과 모두에 맞아야 한다.

연습 1 · 값과 상태 예측

새 카운터 값 5에서 C를 실행한 뒤 정책을 V2로 둔 채 undo, redo를 수행한다. 정상 계약의 세 값과 마지막에 기록할 증가량을 구하라.

힌트 1

생성 때 저장한 증가량은 3이다.

힌트 2

undo/redo는 현재 정책을 다시 부르지 않는다.

풀이와 답 확인

  1. 실행 뒤 값은 8이다.

  2. undo 뒤 값은 5, redo 뒤 값은 8이다.

  3. 명령 기록의 증가량은 계속 3이다.

값은 차례로 8, 5, 8이며 기록한 증가량은 3이다.

흔한 오답에서 다시 생각하기

redo도 최신 정책을 써서 마지막 값은 13이다.

이 명령의 redo 계약은 최초 적용량 재적용이다. 최신 정책을 쓰려면 별도의 새 요청이라는 계약이 필요하다.

연습 2 · 오류 찾아 고치기

C가 V1 정책 객체의 참조만 저장한다. 같은 객체의 내부 보너스를 0에서 5로 바꾼 뒤 C가 이 객체를 호출하여 입력 3을 계산한다. 생성 시 의미를 고정했다는 주장을 고쳐라.

힌트 1

참조 대상의 내부 상태가 바뀌었는지 확인한다.

힌트 2

불변 증가량이나 불변 정책 설정의 독립 복사본을 생각한다.

풀이와 답 확인

  1. 같은 참조라도 계산 결과는 이제 8이다.

  2. 생성 시 계산한 증가량 3을 저장하거나 당시 설정을 불변 값으로 보존한다.

  3. 명령 대상과 입력의 수명·변경 조건도 따로 정한다.

참조 저장만으로는 의미 캡처가 아니다. 값 또는 불변 정책 스냅샷을 저장해야 한다.

흔한 오답에서 다시 생각하기

정책 객체의 주소가 같으므로 결과도 3이다.

정체성과 내부 상태는 다르다. 동일 객체의 설정 변경이 결과를 바꾼 명시 사례다.

연습 3 · 직접 만들어 보기

카운터 명령의 실행 상태를 Ready/Applied/Undone으로 나눈다. 한 번 적용한 명령을 실수로 두 번 실행하여 중복 증가시키지 않는 전이 계약을 작성하라. 다른 편집은 없고 최초 적용량은 3이다.

힌트 1

같은 요청의 재호출과 의도한 redo를 구별한다.

힌트 2

Ready에서 execute, Applied에서 undo, Undone에서 redo만 성공시키는 표를 만든다.

풀이와 답 확인

  1. Ready의 execute는 3을 더하고 Applied가 된다.

  2. Applied의 execute는 거절하여 값과 기록을 보존한다.

  3. Applied의 undo는 3을 빼고 Undone, Undone의 redo는 3을 더하고 Applied가 된다.

  4. 정의하지 않은 요청은 거절하고 상태를 보존한다.

초기 값 5에서 execute 두 번, undo, redo의 값은 8, 8, 5, 8이다. 중복 실행은 상태 검사에서 거절한다.

흔한 오답에서 다시 생각하기

execute를 부를 때마다 더하면 명령 패턴이 중복도 해결해 준다.

객체 포장이 재호출 의미를 정하지 않는다. 상태·요청 ID·재시도 등의 계약을 설계자가 제공해야 한다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

두 독립 문서 A와 Z에 각각 Append(B)를 만들어 같은 종류라는 이유만으로 합친다. 정상 두 실행의 문서 쌍과 하나의 대상만 남긴 변형을 비교하라.

힌트 1

명령 종류뿐 아니라 receiver가 같은지도 확인한다.

힌트 2

문서 쌍 (A,Z)의 두 좌표가 모두 바뀌어야 한다.

풀이와 답 확인

  1. 정상 결과는 (AB,ZB)다.

  2. 첫 문서만 남겨 BB를 더하면 (ABB,Z)로 다르다.

  3. 합치려면 같은 대상·연속성·순방향과 역방향 효과의 보존 조건을 검증한다.

같은 명령 종류는 합치기 충분조건이 아니다. 이 두 대상의 명령은 별도 유지한다.

흔한 오답에서 다시 생각하기

두 글자 B를 더했으므로 어디에 더했는지는 중요하지 않다.

외부에서 관찰하는 문서별 상태가 다르다. 총 글자 수가 같은 것으로 효과 동치를 판단하지 않는다.

통지 도중 구독을 해제하면 이미 시작한 통지도 사라질까요?

관찰자 목록의 현재 값과 이번 전달을 위해 복사한 목록은 다르다. 자체 직렬 모형은 성공 전이를 먼저 확정하고, 확정된 revision과 상태를 불변 이벤트 값으로 만들며, 현재 구독 목록을 복사한 뒤 A, B 순서로 전달한다. 구독 해제는 다음 이벤트의 목록에만 적용되고 이미 복사한 이번 목록을 취소하지 않는다고 정한다.

상태는 Draft에서 submit으로 Review, Review에서 approve로 Done, Review에서 cancel로 Draft가 된다. 나머지 요청은 거절하며 revision과 통지는 증가하지 않는다. Observer는 결과 전달, State는 어떤 요청을 허용할지의 역할이다. 상태별 객체를 사용하지 않아도 이 전이표를 먼저 검토할 수 있다.

통지 중 요청을 바로 처리하면 재진입이 생긴다. 이 단원의 즉시 처리 대안은 같은 호출 스택에서 새 전이와 통지를 마친 뒤 옛 전달을 이어간다. 대기열 대안은 현재 전달이 끝난 뒤 요청을 처리한다. 둘은 서로 다른 계약이며 .NET의 통지 순서나 Qt의 비동기 event loop를 이 종이 순서로 일반화하지 않는다.

먼저 확인할 개념
  • 관찰 통지와 상태 전이

    앞 본문의 정상 전이·구독 해제를 통지 도중까지 확장한다.

  • 명령과 실행 시점

    콜백 안 요청의 즉시 처리/대기열 처리 시점을 연결한다.

observer는 수신자에게 변화를 전달한다

Observer는 provider의 변화를 구독한 관찰자에게 통지한다. 데이터와 화면의 직접 연결을 줄일 수 있지만 구독 수명과 해제, 재진입과 예외 처리 조건이 필요하다. .NET IObservable의 통지 순서는 인터페이스만으로 정해지지 않는다.

state는 현재 상태의 행동을 결정한다

State 설계는 현재 상태에 따라 같은 요청의 처리가 달라지는 구조를 분리한다. 아래 종이 모델은 전이표로 의미를 먼저 정의하고 상태 객체에 행동을 맡길 수 있다. 상태마다 클래스를 만들기 전에 가능한 상태와 금지된 전이를 확인한다.

전이와 통지의 계약을 연결한다

전이를 성공시킨 뒤 확정된 상태를 통지한다고 정하면 관찰자가 어떤 값을 보는지 분명하다. 통지 실패가 상태를 되돌리는지, 구독 중단이 이미 진행 중인 통지를 취소하는지 별도 조건이다. Qt 상태 머신의 비동기 event loop와 이 단원의 직렬 종이 추적은 실행 모델이 다르다.

중간 과정을 따라가는 예제

종이 모델은 Closed에서 open→Open, Open에서 close→Closed이며 나머지 요청은 거부한다. 성공 전이마다 현재 구독자에게 한 번 통지한다. A/B가 구독 중이고 Closed에서 open, open, B 해제, close를 순차 수행한다. 통지 예외·동시성은 없다.

  1. 첫 open 성공: Open이 되고 A/B에 각 한 번 통지한다.

  2. 두 번째 open은 거부되어 상태와 통지 횟수는 그대로다.

  3. B 해제 후 close 성공: Closed가 되고 A만 두 번째 통지를 받는다.

최종 Closed, A 2 회/B 1 회 통지다. 관찰자는 행동 전이 자체의 정책이 아니다.

이번 목록과 다음 목록

Draft, revision 0이고 A/B가 구독한다. submit 통지에서 A가 B를 해제한다. 재진입은 없고 두 콜백은 정상이다. 이후 cancel을 요청한다.

  1. submit은 Review, revision 1을 확정하고 [A,B]를 복사한다.

  2. A가 B를 해제해도 이미 복사한 목록의 B는 이벤트 (1,Review)를 받는다.

  3. cancel은 Draft, revision 2이며 새 목록 [A]에만 전달한다.

A는 두 이벤트, B는 첫 이벤트 한 개를 받는다. 최종 상태는 Draft, revision은 2다.

재진입으로 새 이벤트가 옛 이벤트를 앞지르기

별도로 Draft, revision 0에서 A/B가 구독한다. 즉시 처리 대안에서 submit의 이벤트를 받은 A가 approve를 한 번 호출한다. 새 이벤트에서는 요청하지 않고 누구도 구독 해제하지 않는다.

  1. 첫 submit은 이벤트 (1,Review)를 만들고 A에게 전달한다.

  2. A의 approve가 Done, revision 2를 확정하고 새 이벤트 (2,Done)를 A/B에게 전부 전달한다.

  3. 옛 전달로 돌아와 B가 이벤트 (1,Review)를 받는다. 현재 provider 상태는 Done이다.

B의 수신 revision 순서는 2, 1이다. 이벤트 payload와 현재 provider 상태를 혼동하면 옛 이벤트까지 Done으로 읽게 된다.

연습 1 · 값과 상태 예측

새 Draft/revision 0에서 A/B가 구독한다. 재진입·해제·예외 없이 submit, submit, approve, cancel을 차례로 처리한다. 최종 상태·revision·각 통지 수를 구하라.

힌트 1

Review에서는 submit이 정의되지 않았다.

힌트 2

Done의 cancel도 거절한다.

풀이와 답 확인

  1. 첫 submit은 Review/revision 1로 성공한다.

  2. 둘째 submit은 거절하고 approve만 Done/revision 2로 성공한다.

  3. 마지막 cancel은 거절하며 성공 두 번만 각각 A/B에게 통지한다.

최종 Done, revision 2이고 A/B는 각각 두 번 통지받는다.

흔한 오답에서 다시 생각하기

요청 네 개이므로 revision과 통지도 네 번이다.

요청 수와 성공 전이 수는 다르다. 거절 경로는 상태·revision·통지를 보존한다.

연습 2 · 오류 찾아 고치기

위 재진입 예제에서 화면 B가 매 이벤트마다 provider.currentState만 읽어 이벤트 기록을 만든다. B의 두 이벤트가 모두 Done으로 기록되는 이유와 수정안을 설명하라.

힌트 1

B가 첫 이벤트를 받을 때 revision 2가 이미 확정되었다.

힌트 2

불변 payload의 revision과 상태를 기록한다.

풀이와 답 확인

  1. B가 새 이벤트와 뒤늦은 옛 이벤트를 받을 때 현재 provider는 둘 다 Done이다.

  2. 이벤트 payload는 각각 (2,Done), (1,Review)이다.

  3. payload를 기록하거나 전달을 직렬 대기열로 바꾸는 계약을 선택한다.

현재 상태 읽기는 이벤트 당시 상태 복원이 아니다. 전달 payload를 사용하면 두 사건이 구별된다.

흔한 오답에서 다시 생각하기

Observer를 쓰면 현재 상태가 언제나 이벤트 시점 상태다.

통지 패턴 자체는 재진입이나 늦은 전달을 막지 않는다. 상태 확정 시점과 전달 시점을 따로 읽는다.

연습 3 · 직접 만들어 보기

같은 재진입 예제의 A가 approve를 요청하되 요청을 대기열에 넣는다. 현재 submit 전달을 끝내고 다음 요청을 처리하는 규약에서 B의 수신 순서와 구독 해제 효과를 설계하라. 해제는 발생하지 않는다.

힌트 1

현재 이벤트 [A,B]를 전부 전달한 뒤 다음 요청을 꺼낸다.

힌트 2

approve의 전이 허용 여부는 꺼낼 당시 상태에서 확인한다.

풀이와 답 확인

  1. A의 요청은 아직 상태를 바꾸지 않고 큐에 들어간다.

  2. B가 (1,Review)를 받은 뒤 approve를 꺼내 현재 Review에서 성공시킨다.

  3. 새 이벤트 (2,Done)를 A/B에게 전달한다.

  4. 일반적으로 해제는 새 이벤트 스냅샷부터 적용한다고 유지한다.

B의 순서는 revision 1, 2다. 큐에 들어갔다고 성공이 확정된 것은 아니고 실제 처리 때 전이를 확인한다.

흔한 오답에서 다시 생각하기

큐 삽입 성공이면 이후 어떤 상태에서도 approve 성공을 보장한다.

큐는 요청 시점을 미룬다. 사이의 다른 요청이 상태를 바꾸면 실행 시 검증이 여전히 필요하다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

새 Draft에서 submit을 확정한 뒤 A의 콜백은 실패한다. 정책 P는 실패를 기록하고 B 전달을 계속하고, Q는 그 예외로 이번 전달을 즉시 중단한다. 모두 전이 롤백은 하지 않는다. 상태와 B 호출 수를 비교하라.

힌트 1

전이 확정은 콜백보다 앞이다.

힌트 2

P/Q 각각 새 Draft에서 시작하는 독립 대안이다.

풀이와 답 확인

  1. 두 대안 모두 Review, revision 1은 유지된다.

  2. P는 A 실패 기록 후 B를 한 번 호출한다.

  3. Q는 B를 호출하지 않는다.

상태는 둘 다 Review, revision 1이다. B 호출은 P가 1회, Q가 0회다. 통지 성공률과 전이 성공은 별도로 보고한다.

흔한 오답에서 다시 생각하기

A 실패 때문에 둘 다 Draft로 되돌아간다.

문제 계약은 롤백하지 않는다. 예외 처리와 상태 복원은 패턴 이름이 자동으로 제공하지 않는다.

패턴 조합과 과잉설계

새 클래스가 많아질수록 변경도 항상 쉬워질까?

준비 개념과 학습 목표

준비 개념

  • strategy·command

  • observer·state

학습 목표

  • 변화 원인별 역할을 조합한다.

  • 패턴의 이득과 유지 비용을 비교한다.

문서 변경은 성공했지만 화면 통지가 실패하면 같은 요청을 다시 실행해도 될까요?

자체 편집 서비스는 전략으로 새 문자열의 길이를 검사하고 명령으로 변경과 undo 기록을 묶으며 관찰자에게 결과를 전달한다. 초기 문서는 A, 길이 한도는 3이다. 실행 전 검사 실패는 문서와 기록·revision을 모두 보존한다. 성공하면 문서·명령 기록·revision을 함께 확정한 뒤 통지한다. 이 종이 모형의 확정 묶음은 설계 가정이지 실제 트랜잭션 구현 증거가 아니다.

한 명령의 통지 실패는 문서 변경 성공을 취소하지 않는다고 정한다. 따라서 결과를 문서 적용 여부와 통지 결과로 나누어 보고한다. 화면 갱신 재시도는 이미 확정된 이벤트를 다시 전달할 수 있지만 명령을 또 적용하지 않는다. 수신자의 중복 통지 처리는 별도 revision 규약이 필요하다.

패턴의 수와 클래스 수를 설계 품질 점수로 쓰지 않는다. 교체할 검증 정책과 기록할 요청·독립 구독자라는 실제 요구가 있을 때 경계를 나눈다. 아래 비용은 개발·변경에 붙인 가상 점수이며 처리 시간이나 생산성 실측이 아니다. 함수를 주입하는 작은 대안도 같은 계약을 만족하면 비교 대상이다.

    undo가 새 정책의 검사인지 기록된 변경의 역작업인지 구별한다.

  • 상태 확정과 통지 실패

    문서 적용 성공을 콜백 전달 성공과 분리하여 재시도를 설계한다.

변화가 있는 경계부터 나눈다

문서 편집의 요청 기록은 Command, 검증 정책 교체는 Strategy, 상태 표시 통지는 Observer와 연결할 수 있다. 패턴 이름을 최대한 많이 넣는 것이 목적은 아니다. 어떤 요구 변화가 어느 코드에 영향을 주는지 먼저 적는다.

실행과 통지의 순서를 계약으로 만든다

검증 실패한 요청은 문서를 바꾸거나 성공 통지를 보내지 않는다고 정하자. 성공 작업의 undo가 새 통지를 보내는지도 결정한다. 패턴을 조합해도 부분 실패·원자성·중복 효과가 저절로 해결되지 않는다. 기록된 Command와 현재 정책 사이의 관계를 명시해야 한다.

작은 대안도 같은 요구로 비교한다

통지 하나만 필요한 프로그램에는 일반 이벤트나 직접 함수 호출이 충분할 수 있다. 함수 하나로 정책을 전달할 수 있다면 클래스 계층의 생성·추적 비용을 줄인다. 반대로 실제 독립 정책이 늘어나면 분리의 이득이 커진다. 자체 비용표는 설계 토론용이며 실측 생산성 순위가 아니다.

각 행은 앞 행의 문서 상태를 이어받는다. 첫 행의 관찰자 B 이름과 추가 글자 B는 역할이 다르다. 기록 [B,C]는 적용된 글자 두 명령의 순서이며 실패한 D를 넣지 않는다.

중간 과정을 따라가는 예제

자체 비용 단위로 단순 구현은 초기 2, 정책 한 개 변경마다 3이다. 분리 구현은 초기 8, 변경마다 1이다. 변경 4 회에서 총비용을 비교하라. 단위는 시간 측정이 아니고 다른 비용은 없다.

  1. 단순 구현은 2+4×3=14다.

  2. 분리 구현은 8+4×1=12다.

  3. 분리 쪽이 2 만큼 작지만 변경 1 회면 단순 5/분리 9로 반대다.

변경 4 회의 모델에서는 14 대 12다. 변경 수와 비용 가정에 따라 선택이 달라진다.

조건을 바꾸어 비교하기

전달 실패를 실행 실패로 뭉뚱그리기

새 A에서 Append(B)가 성공하고 관찰자 X는 성공, Y는 실패한다. 호출자가 전체 실패라고 보고 같은 Append(B)를 다시 적용하면 한도 3 안에서 어떤 중복이 생기는가?

  1. 첫 적용 뒤 문서는 AB, revision 1이며 이미 효과가 있다.

  2. 다시 적용하면 ABB의 길이 3도 통과하여 revision 2가 된다.

  3. 통지 실패만 복구하려면 문서 AB를 유지하고 revision 1 이벤트의 전달을 별도로 다룬다.

전체 실패라는 이름만으로 명령을 다시 적용하면 글자 B가 중복된다. 문서 적용 성공/통지 부분 실패를 구별한다.

비교할 점

명령·관찰자 조합이 업무 재시도의 원자성을 자동 보장하지 않음을 보여준다.

정책 교체 뒤 undo를 새 편집 검증과 구별하기

새 A에서 한도 3으로 Append(BC)를 적용하여 ABC가 되었다. 한도를 0으로 바꾼 뒤 다른 편집 없이 undo한다. 이 계약에서 undo는 기록된 이전 문자열 복원이며 새 한도 검사를 받지 않는다.

  1. 적용 기록은 이전 A와 추가 BC를 보존한다.

  2. 한도 0은 새 편집의 허용 조건이다.

  3. undo는 이전 A로 복원하고 별도 성공 이벤트를 만들며 revision을 한 번 증가시킨다.

undo 뒤 문서는 A이며 적용과 undo 두 성공의 revision은 2다. 새 한도 검사를 강제하면 이 계약의 복원 경로가 막힌다.

비교할 점

실제 서비스에서 undo도 새 정책을 따르게 할 수 있지만 그렇다면 복원 보장 범위를 새로 명시해야 한다.

먼저 답과 이유를 적고, 필요한 만큼 힌트를 한 단계씩 열어 보세요.

연습 1 · 값과 상태 예측

표의 세 요청 뒤 한도를 유지하고 최근 성공 명령 하나를 undo한다. 다른 편집은 없고 undo도 성공 이벤트를 하나 만든다. 문서·적용 기록·revision을 구하라.

힌트 1

실패한 D는 기록되지 않았다.

힌트 2

최근 성공은 C이고 이전 문자열은 AB다.

풀이와 답 확인

  1. 세 요청 뒤 문서는 ABC, 기록은 [B,C], revision은 2다.

  2. C를 undo하여 AB를 복원하고 현재 적용 기록은 [B]가 된다.

  3. undo 성공으로 revision은 3이 된다.

문서는 AB, 적용 기록은 [B], revision은 3이다.

흔한 오답에서 다시 생각하기

실패한 D를 undo하므로 문서는 ABC 그대로다.

실패한 요청과 적용 기록을 혼동했다. undo 대상은 적용되어 기록된 성공 명령이다.

연습 2 · 오류 찾아 고치기

편집기가 Append(D)의 후보 ABCD를 검사하기 전에 문서를 ABCD로 바꾸고 기록 D를 넣는다. 길이 검사가 실패하면 거절 메시지만 반환한다. 원자적인 실패 보존 목표를 만족하도록 순서를 고쳐라.

힌트 1

변경 전 후보를 별도 값으로 만든다.

힌트 2

문서·기록·revision을 함께 확정할 경계를 정한다.

풀이와 답 확인

  1. ABC와 기록 [B,C]를 먼저 보존한다.

  2. 별도 후보 ABCD를 검사하여 실패하면 공개 상태를 바꾸지 않는다.

  3. 성공 후보만 문서·기록·revision을 함께 확정하고 나서 통지한다.

거절 뒤 문서 ABC, 기록 [B,C], revision 2를 유지하도록 후보 검증을 먼저 한다. 실제 동시 구현에서는 확정 경계도 보장해야 한다.

흔한 오답에서 다시 생각하기

거절이라고 반환했으니 내부 ABCD 상태는 상관없다.

반환과 관찰 가능한 상태가 계약의 두 부분이다. 거절 뒤 실패 보존이 이미 깨졌다.

연습 3 · 직접 만들어 보기

정책은 함수 한 개, 수신자는 고정 함수 한 개이며 지연 실행·undo·명령 기록 요구가 없는 작은 도구를 설계하라. 검증 실패 보존과 성공 뒤 통지는 여전히 필요하다. 가장 작은 역할 분리를 적어라.

힌트 1

필요하지 않은 명령 계층을 먼저 제거해 본다.

힌트 2

후보 계산→검증→확정→통지 순서는 작은 함수에서도 가능하다.

풀이와 답 확인

  1. 입력으로 검증 함수를 받는 편집 함수가 후보를 만든다.

  2. 검증 실패면 기존 값을 그대로 반환하고 통지하지 않는다.

  3. 성공하면 값을 확정하고 고정 콜백을 부르되 전달 실패와 적용 여부를 나누어 보고한다.

함수와 명시 결과 자료로 계약을 유지할 수 있다. 미래에 undo·동적 구독 요구가 생기면 그 경계를 추가 검토한다.

흔한 오답에서 다시 생각하기

이벤트와 정책이 있으니 반드시 네 패턴 클래스 계층을 만들어야 한다.

요구를 만족하는 역할과 클래스 수는 동일하지 않다. 고정 작은 도구에 추상화 관리 비용만 추가할 수 있다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

가상 비용 점수 S는 초기 1, 정책 변경 n회마다 2다. 분리 설계 P는 초기 7, 정책 변경마다 1이고 구독자 연동 변경 m회마다 추가 1이다. S에는 이 모형에서 m 관련 추가 점수를 따로 두지 않는다. n,m은 비음수 정수이다. m=2에서 동률과 P가 작은 최소 n을 구하라.

힌트 1

S=1+2n, P=7+n+m이다.

힌트 2

P<S를 엄격 부등식으로 풀고 정수 조건을 적용한다.

풀이와 답 확인

  1. m=2이면 P=9+n이다.

  2. 동률 1+2n=9+n은 n=8이고 양쪽 17이다.

  3. P가 작으려면 n>8이므로 최소 정수는 9이고 S=19, P=18이다.

m=2에서 n=8은 동률, P가 작은 최소 n은 9다. 실제 비용이나 모든 프로젝트의 우열은 아니다.

흔한 오답에서 다시 생각하기

초기 추상화가 있으면 n=1부터 언제나 P가 작다.

초기와 추가 연동 비용을 빼먹었다. 같은 요구·범위의 모형인지부터 검토하고 총합을 비교해야 한다.

힌트 1

실제로 적용한 증가량, 불변 이벤트, 확정된 문서를 각각 기록한다.

힌트 2

재진입의 새 이벤트 전달과 옛 이벤트 재개, 재시도의 대상이 전달인지 적용인지 나눈다.

풀이와 답 확인

  1. C는 증가량 3을 기록하므로 카운터 값은 8, 5, 8이다. 현재 정책 V2로 undo/redo를 재계산하지 않는다.

  2. B는 (2,Done)를 먼저 받고 이어 (1,Review)를 받는다. 마지막 provider는 Done, revision 2다. 늦은 payload가 현재 상태를 되돌렸다는 뜻은 아니다.

  3. 문서는 이미 AB, revision 1로 적용되었다. X 전달 성공/Y 전달 실패를 보고하고 문서를 재적용하지 않는다. 재적용하면 한도 안에서 ABB, revision 2가 되어 중복된다.

  4. n=8,m=2에서 S=1+16=17, P=7+8+2=17로 동률이다. 이 점수는 명시 모형이고 실측 순위가 아니다.

카운터는 8→5→8이다. B의 payload revision은 2→1이고 현재 provider는 Done/revision 2다. 문서 AB의 적용 성공과 Y 전달 실패를 구별하며 재적용 중복 ABB를 피한다. 비용은 두 설계 모두 17이다.
