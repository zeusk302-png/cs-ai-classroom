소단원 12.1

code smell

코드가 길다는 사실만으로 잘못된 설계라고 결론내려도 될까?

준비 개념과 학습 목표

준비 개념

  • 메서드와 클래스

  • 중복

  • 변경 책임

학습 목표

  • 냄새와 결함을 구분한다.

  • 변경 이유를 근거로 설계 문제를 조사한다.

  • 동일한 코드와 동일한 책임을 구별한다.

복사한 조건 셋과 같은 숫자 둘을 같은 이유로 합쳐도 될까?

냄새를 발견한 다음에는 변경의 이름과 영향을 적는다. 자체 가상 앱의 화면 V, 영수증 R, 결제 P는 같은 배송 규칙을 각각 갖는다. 대여 L과 식사 M은 우연히 같은 가격을 사용하지만 다른 정책이다. 배송 기준 변경, 대여료 변경, 식사 가격 변경은 서로 다른 업무 요청이다. 파일 개수와 줄 수만으로 책임을 판단하지 않는다.

배송 기준은 현재 10000이고 그 이상이면 배송비 0, 미만이면 2000이다. 세 소비자가 같은 정책임을 확인한 뒤 명시 입력 amount를 받는 공통 계산 F를 추출할 수 있다. 첫 단계에서는 기준과 호출 위치를 그대로 유지한다. 이후 기준 12000으로 바꾸는 것은 별도의 기능 변경이다. 한 파일이 적게 바뀐다는 이유만으로 기능 변경과 구조 변경을 합쳐 부르지 않는다.

매개변수를 묶는 것도 보존할 계약이 있다. 이 단원의 별도 범위 객체는 정수 start/end와 start≤end를 갖고 변경되지 않는 값이다. 기존 조회는 닫힌 구간 [start,end]를 포함한다. 객체로 묶으면서 [start,end)로 바꾸면 끝 날짜의 기록을 잃는다. 날짜 형·시간대·실제 저장소는 이 작은 정수 모형에 포함하지 않는다.

먼저 확인할 개념
  • 같은 지식과 우연한 중복

    기본의 배송 정책과 서로 다른 가격 책임을 변경 영향 행렬로 구체화한다.

  • 구조 변경과 기능 변경

    보존한 조건의 추출과 정책 기준 변경을 별도 단계로 기록한다.

냄새는 판정이 아니라 조사 출발점

code smell은 설계 속 더 깊은 문제를 의심하게 하는 표면 신호다. 긴 메서드, 반복된 조건, 함께 이동하는 인자 묶음 등을 쉽게 발견할 수 있다. 발견했으면 어떤 변경이 어려운지와 어느 지식이 여러 곳에 흩어졌는지 질문한다. 길이 기준을 넘었다는 이유만으로 버그라고 단정하지 않는다.

예를 들어 긴 표를 출력하는 메서드는 한 책임일 수 있지만 짧은 메서드 안에서 결제 승인과 학생 출석 변경을 함께 한다면 변경 이유가 섞여 있다. 줄 수는 조사 신호이고 책임·의존 관계·실제 오류가 판단 근거다. 반대로 실행 결과가 지금 맞다고 유지보수 문제가 없는 것도 아니다.

같이 바뀌는 지식을 찾는다

같은 배송 규칙을 화면·영수증·결제에 각각 작성하면 조건 변경 때 세 곳을 고쳐야 한다. 한 곳을 놓치면 같은 주문의 표시와 실제 결제가 다르게 된다. 이때 핵심은 비슷하게 생긴 글자보다 같은 규칙이라는 의미다. 여러 곳의 공통 규칙을 명확한 함수나 정책 객체로 연결할 수 있다.

우연히 같은 숫자를 사용하는 다른 규칙까지 합치면 불필요하게 서로 묶인다. 도서 대여료와 식사 가격이 둘 다 2,000이라고 하나의 가격 상수를 공유하면 한쪽 변경이 다른쪽을 흔든다. 같아 보이는 코드에 먼저 이름과 변경 이유를 적어 의미가 같은지 확인한다.

작은 대안으로 원인을 드러낸다

개선 후보에는 함수 추출, 이름 개선, 함께 전달되는 인자 묶기, 책임 분리 등이 있다. 인자를 객체로 묶으면 어떤 값이 하나의 개념인지 표현하기 쉬워지지만 필요 없는 공용 가방에 모든 값을 넣으면 책임이 더 흐려진다. 후보를 선택할 때 현재 변경 문제를 얼마나 줄이는지 설명한다.

소단원 활동에서는 배송 경계 표를 종이에 추적해 문제를 조사한다. 자동 smell 도구가 경고해도 이 문맥과 규칙을 사람이 검토한다. 점수나 경고 개수가 낮아졌다는 사실을 학습자 이해·운영 오류 감소의 실제 증거로 대신하지 않는다.

배송 행의 세 위치는 같은 지식이 분산되었다는 조사 근거다. 가격 두 행은 숫자가 같아도 함께 바뀌지 않는다. 표는 실제 저장소의 변경 이력이나 줄 수 측정이 아닌 명시한 가상 요구다.

중간 과정을 따라가는 예제

동일 배송 규칙은 주문액 10,000 이상이면 0원, 그 미만이면 2,000원이다. 화면/영수증/결제가 이를 따로 구현한다. 기준을 12,000으로 바꾸는 기능 변경에서 화면만 고쳤다면 11,000원 주문의 세 배송비는?

  1. 새 기준 화면에서11,000<12,000이므로2,000이다.

  2. 영수증과 결제는 옛 기준11,000>=10,000이라0이다.

  3. 같은 규칙의 중복을 부분 수정해 표시와 청구가 달라졌다.

  4. 먼저 옛 규칙을 한곳으로 모으는 행동보존 변경을 검토한 뒤 별도로 새 기준을 적용할 수 있다.

화면2,000/영수증0/결제0. 같은 책임의 여러 구현이 변경 누락의 위험을 만든다.

조건을 바꾸어 비교하기

먼저 모으고 나중에 정책을 바꾼다

세 배송 소비자가 모두 옛 규칙을 갖는다. amount 11000에서 공통 F 추출 뒤와 기준 12000 적용 뒤의 배송비를 비교하라.

  1. 추출 직후에는 세 소비자 모두 기준 10000을 쓰므로 배송비 0이다.

  2. 다음 기능 변경에서 F의 기준만 12000으로 바꾸면 세 소비자 모두 배송비 2000이다.

  3. 화면만 새 기준으로 바꾸면 화면 2000, 영수증과 결제 0이라는 불일치가 생긴다.

추출은 0을 보존하고 정책 변경은 2000으로 바꾼다. 단계의 목적과 관찰을 나누어 적는다.

비교할 점

단일 정책 담당은 의미 일치가 전제이며 모든 유사 코드를 합치라는 규칙은 아니다.

범위의 포장과 끝 점의 뜻

가상 기록의 날짜는 2,3,4다. 기존 조회 [2,4]를 범위 객체로 바꾼 뒤 잘못된 반열린 조회 [2,4)를 사용했다. 반환 날짜를 비교하라.

  1. 기존 닫힌 범위는 2와 4를 모두 포함해 [2,3,4]를 반환한다.

  2. 반열린 변형은 끝 4를 제외해 [2,3]을 반환한다.

  3. 객체로 묶는 구조와 포함 규칙은 독립이므로 끝 점 포함을 그대로 두어야 한다.

정상 결과는 세 기록이고 변형은 두 기록이다. 입력 포장만 바꿨다는 설명으로 손실을 숨기지 않는다.

비교할 점

실제 날짜 API를 실행하지 않은 정수 구간 사례다.

연습 1 · 값과 상태 예측

배송 기준 12000 변경 뒤 amount 11999와 12000의 세 소비자 결과를 각각 쓰라. 두 주문은 독립이다.

힌트 1

기준 미만과 같은 경우를 나눈다.

힌트 2

각 소비자는 같은 F를 사용한다.

풀이와 답 확인

  1. 11999에서는 V/R/P 모두 배송비 2000이다.

  2. 12000에서는 V/R/P 모두 배송비 0이다.

아래 경계는 유료이고 정확 경계는 무료다.

흔한 오답에서 다시 생각하기

12000도 기준보다 크지 않으니 유료다.

계약은 이상 조건으로 동점을 포함한다.

연습 2 · 오류 찾아 고치기

L과 M의 2000을 공용 price로 합쳤다. 식사만 2500으로 바꾸었더니 대여료도 바뀌었다. 원래 변경 책임을 보존하는 수정을 설계하라.

힌트 1

공유할 것은 값의 모양이 아니라 정책 의미다.

힌트 2

수정 뒤 두 독립 값을 적는다.

풀이와 답 확인

  1. 대여 가격과 식사 가격을 서로 다른 이름/담당으로 분리한다.

  2. 식사 가격만 2500으로 바꾸고 대여료 2000을 유지한다.

새 값 두 개와 변경 이유를 각각 기록한다.

흔한 오답에서 다시 생각하기

같은 숫자라면 항상 같은 지식이다.

값이 우연히 같아도 승인 주체와 변경 요청이 다르면 정책을 결합할 근거가 없다.

연습 3 · 직접 만들어 보기

start가 4이고 end도 4인 유효 범위와 start가 5이고 end가 4인 잘못된 범위의 객체 생성·조회 계약을 구성하라. 기록은 날짜 4 하나다.

힌트 1

빈 폭과 유효하지 않은 역순을 구별한다.

힌트 2

거절할 입력을 보정해 새 뜻을 만들지 않는다.

풀이와 답 확인

  1. [4,4]는 유효한 닫힌 범위라 날짜 4의 기록 하나를 반환한다.

  2. 역순 [5,4]는 생성 단계에서 거절하고 조회를 요청하지 않는다.

동점 범위의 한 기록과 역순 거절을 독립적으로 검증한다.

흔한 오답에서 다시 생각하기

동점이면 언제나 빈 구간이다.

반열린 구간의 규칙을 닫힌 계약에 옮기면 실제 끝 점 포함이 달라진다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

앞의 불변 범위와 다른 변형으로, 공유 범위 객체의 end를 바꿀 수 있다고 가정한다. 조회가 start를 읽은 뒤 외부에서 end를 바꾸면 입력 객체를 묶었다는 사실만으로 일관성이 생기는가? 명시한 대안을 설계하라.

힌트 1

포장은 값의 안정성을 자동 보장하지 않는다.

힌트 2

변경되지 않는 스냅샷을 어떤 경계에서 만드는지 적는다.

풀이와 답 확인

  1. 변경 가능한 공유 객체라면 조회 중 서로 다른 시점의 start/end를 관찰할 수 있다.

  2. 검증된 불변 범위 값을 전달하거나 전체 쌍을 원자적으로 읽는 별도 계약을 계획한다. 실제 동시 구현은 하지 않는다.

객체 수가 줄었다는 것과 같은 요청의 입력 쌍이 안정적이라는 주장을 분리한다.

흔한 오답에서 다시 생각하기

인자가 하나면 경쟁도 하나라 안전하다.

인자 개수와 공유 상태의 원자성은 다른 조건이다.

소단원 12.2

행동보존 변경

같은 숫자를 반환하면 언제나 행동을 보존한 변경일까?

준비 개념과 학습 목표

준비 개념

  • 함수 추출

  • 조건문

  • 상태와 부작용

학습 목표

  • 관찰 가능한 행동 범위를 작성한다.

  • 입력·경계·예외·부작용을 전후 대조한다.

  • 기능 변경과 구조 변경을 분리한다.

값을 한 번 읽어 재사용하면 언제 같은 결과가 될까?

새 자체 quote는 readAmount를 호출해 x를 얻고 x<0이면 Range 오류를 낸다. 그렇지 않으면 같은 협력자를 다시 호출해 y를 얻고 y<0이면 Range 오류를 낸다. 두 값이 모두 유효하면 x+fee(y)를 반환한다. fee(y)는 y≥10000이면 0, 미만이면 2000이다. 각 readAmount 호출은 Read 사건 하나를 남긴다. 모든 값은 정수이고 산술은 무한 정밀도 손모형이다.

관찰 계약은 반환 또는 오류 종류와 순서대로 남은 Read 사건 목록이다. 추출안 E는 fee만 같은 순수 함수로 옮기고 두 읽기의 위치와 음수 검사를 유지한다. 캐시안 C는 첫 x를 한 번 읽고 검사한 뒤 x+fee(x)를 반환한다. 선읽기안 G는 두 읽기를 먼저 하고 나중에 음수를 검사한다. 셋을 구별하는 핵심은 이름이나 함수 개수가 아니라 읽은 값의 시점과 오류까지 발생한 사건이다.

표와 각 문제는 새 대역에서 독립적으로 시작한다. 대역은 주어진 값 목록을 차례로 반환하며 이 단원에서 두 읽기까지 충분한 답을 준다. 실제 대역·코드·서비스는 실행하지 않는다. 읽기 로그가 계약에서 빠지더라도 값이 시간에 따라 바뀌면 캐시안의 결과 차이는 남을 수 있다. 무엇을 관찰하는지 좁힌 뒤에야 보존 여부를 다시 판정한다.

먼저 확인할 개념
  • 값·평가 횟수·실패 관찰

    기본 read()+read()의 결과/로그 반례를 서로 다른 반환과 오류 시점으로 확장한다.

  • 독립 회귀 기대와 미수행

    추출안을 실제 테스트 통과가 아닌 명시 입력의 종이 추적으로 검토한다.

무엇을 같게 유지할지 먼저 정한다

리팩터링은 외부 관찰 행동을 유지하면서 내부 구조를 바꾸는 작업이다. 반환값 외에도 상태 변경, 로그·파일·요청 횟수, 예외, 호출 순서가 계약에 포함될 수 있다. 모든 내부 변수 이름이 같아야 한다는 뜻은 아니며 사용자가 의존하는 관찰 범위를 먼저 적는다.

성능이나 시간이 요구 조건일 때는 결과 숫자만 같아도 충분하지 않을 수 있다. 예외를 빈 값으로 바꾸거나 원래 두 번 보냈던 외부 요청을 한 번으로 바꾸면 의도와 무관하게 행동이 달라진다. 잘못된 옛 행동을 고치는 작업도 필요하지만 그때는 별도의 기능 수정으로 설명한다.

한 변환씩 추적한다

배송비 계산 블록을 shippingFee(amount)로 추출할 때 조건과 반환 값을 그대로 옮긴다. 기존 호출 위치와 필요한 입력을 유지하고 새 함수가 전역 값에 의존하지 않도록 계약을 드러낸다. 추출과 동시에 무료 기준까지 바꾸면 어떤 변경 때문에 결과가 달라졌는지 찾기 어렵다.

순수 계산의 추출은 입력/출력 표로 확인하기 쉽다. 상태 읽기나 예외가 있는 블록은 평가 횟수·순서도 추적한다. 두 호출을 하나의 임시 변수로 합치기 전에 호출이 같은 값을 주는지와 부작용이 없는지 확인한다. 작은 변환 뒤 대조하면 문제를 좁힐 수 있다.

예상과 실행 증거를 구별한다

기존 행동을 먼저 표로 기록하고 정상·경계·실패 입력을 새 구조와 비교한다. 종이 추적은 조건 이해에 도움이 되지만 실제 컴파일·실행·회귀 시험의 통과와는 다르다. 실제 프로젝트에서는 관련 테스트를 실행하고 검사한 관찰 범위와 남은 미확인 범위를 기록한다.

테스트가 기존 내부 호출 구조에 과도하게 묶이면 의도한 구조 변경에도 불필요하게 깨질 수 있다. 공개 계약의 결과와 필요한 부작용을 확인하되 내부 함수명이 바뀐 것만 실패라고 판정하지 않는다. 다만 요청 횟수처럼 계약의 일부인 상호작용은 관찰 대상에 포함한다.

행마다 결과와 사건 수를 둘 다 읽는다. 원래 quote와 E는 모든 행에서 같다. C는 값의 시점을 바꾸고 G는 첫 음수 뒤에도 협력자를 다시 읽는다. 표의 네 입력 일치가 모든 임의 구현의 동치를 증명한 것은 아니다.

중간 과정을 따라가는 예제

amount는 0 이상 정수이고 기존 배송비는 amount>=10000이면 0, 아니면 2000이다. 같은 조건의 shippingFee 함수로 추출한다. amount 0/9999/10000/10001의 전후 결과를 비교하라.

  1. 0은 기준 미만이라 2000이다.

  2. 9999도 2000이다.

  3. 10000은 >= 경계를 포함하므로 0이다.

  4. 10001도 0이며 새 함수도 같은 조건이므로 네 결과가 일치한다.

전후 모두 2000/2000/0/0이다. 이 표는 네 입력에 대한 예상 대조이며 전체 프로그램 실행 증거는 아니다.

조건을 바꾸어 비교하기

같은 결과에서 다른 읽기 계약

[10000,10000]에서 원래 quote와 C를 비교하라. 이후 관찰 계약에서 Read 목록만 제외하면 이 한 입력의 판정은?

  1. 원래는 둘째 10000의 무료 배송으로 10000을 반환하고 Read 두 사건이다.

  2. C는 첫 값으로 같은 10000을 반환하나 Read 한 사건이다.

  3. 원래 관찰 계약에서는 다르다. Read를 제외한 좁은 계약에서 이 입력의 반환은 같지만 다른 입력까지 동치라는 뜻은 아니다.

관찰 범위를 바꾸면 같은 입력의 판정이 달라질 수 있다. 전체 보존은 별도로 논증한다.

비교할 점

관찰 계약 변경 자체를 과거 계약의 리팩터링이라고 부르지 않는다.

오류까지의 접두 사건을 보존한다

[−1,5]에서 G가 읽기를 앞으로 옮겼다. 마지막 오류 종류가 같으면 충분한가?

  1. 원래는 첫 −1 직후 Range이며 둘째 값을 읽지 않는다.

  2. G는 −1과 5를 둘 다 읽고 Range라서 사건 수가 두 번이다.

  3. 외부 읽기 사건이 계약이므로 오류 종류만 비교하는 검사는 차이를 놓친다.

Range는 같지만 오류 직전 사건 접두부는 Read 1회와 2회로 다르다.

비교할 점

둘째 읽기가 실제 오류를 낼 수 있는 다른 계약에서는 오류 우선순위도 별도로 다루어야 한다.

연습 1 · 값과 상태 예측

새 목록 [5,−1]을 원래 quote/E/C에 각각 준다. 반환/오류와 Read 수를 예측하라.

힌트 1

둘째 음수는 원래의 별도 검사에 걸린다.

힌트 2

C는 둘째 값을 읽지 않는다.

풀이와 답 확인

  1. 원래와 E는 첫 5 뒤 둘째 −1을 읽고 Range를 내며 Read 두 사건이다.

  2. C는 첫 5만 검사해 5+2000=2005를 반환하고 Read 한 사건이다.

원래와 E의 실패가 C에서는 성공 반환으로 바뀐다.

흔한 오답에서 다시 생각하기

첫 값이 양수면 모든 변환이 성공한다.

원래 계약에는 둘째 관찰의 유효성 검사도 있다.

연습 2 · 오류 찾아 고치기

함수 추출 중 fee 조건을 y>10000으로 바꿨다. 새 목록 [10000,10000]에서 원래와 변형 반환을 비교하고 구조만 바꾸는 수정을 적어라.

힌트 1

같은 경계값도 무료인지 본다.

힌트 2

Read 횟수는 이 변형에서 두 번을 유지한다.

풀이와 답 확인

  1. 원래 반환은 10000이고 변형은 배송비 2000을 더해 12000이다.

  2. fee의 이상 조건을 복원하고 두 읽기와 실패 시점을 그대로 둔다.

추출의 의미와 정책 경계를 함께 보존한다.

흔한 오답에서 다시 생각하기

함수 이름이 같으면 관찰도 같다.

이름이 아니라 조건식과 실제 경계 결과를 대조해야 한다.

연습 3 · 직접 만들어 보기

원래 quote가 x에 한 번, y에 한 번 협력자를 평가하는 순서를 보존하는 추출안을 단계로 설계하라. 첫 음수와 둘째 음수도 처리하라.

힌트 1

순수 fee에는 이미 읽은 y를 전달한다.

힌트 2

실패 뒤 다음 외부 읽기를 시작하지 않는다.

풀이와 답 확인

  1. x를 읽고 음수면 바로 Range를 낸다. 유효할 때만 y를 읽고 음수면 Range를 낸다.

  2. 그 뒤 순수 fee(y)를 계산해 x에 더한다. 추출 함수 안에서 readAmount를 다시 호출하지 않는다.

외부 평가를 원래 위치에 두고 순수 계산만 옮긴 E다.

흔한 오답에서 다시 생각하기

fee 함수 안에서 값을 다시 읽어도 결과만 같으면 된다.

세 번째 관찰은 값과 사건 목록을 바꿀 수 있으며 원래 두 번 읽기 계약을 어긴다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

Read 목록을 관찰에서 제외하고 두 읽기가 항상 같은 유효 비음수 값을 준다는 추가 전제를 둔다. C의 값 보존을 보이라. 이 전제를 빼면 [9999,10001]은?

힌트 1

원래 x와 y가 같을 때 식을 비교한다.

힌트 2

전제를 제거한 구체 반례도 계산한다.

풀이와 답 확인

  1. x=y이면 원래 x+fee(y)와 C의 x+fee(x)는 같은 값이다. 음수나 읽기 실패는 이 전제에서 제외되어 있다.

  2. 전제 없이 원래 반환은 9999이고 C는 11999여서 2000 차이가 난다.

제한된 추가 계약에서는 값 보존을 증명하지만 일반 계약까지 확대하지 않는다.

로그를 보지 않으면 모든 캐시는 행동을 보존한다.

외부 읽기의 반환 시점과 실패 가능성도 보존 조건에 포함된다.

검사 네 개를 세 개로 줄이면 같은 위험을 확인할까?

이제 같은 quote의 회귀 검사 계획을 고른다. 가상 변형 네 개는 H: fee의 ≥를 >로 변경, C: 첫 값 캐시, J: 두 읽기와 검사는 유지하되 배송비를 합계에서 생략, G: 검사 전 두 읽기다. 하나씩 독립적으로 적용한다. 실제 변형 코드나 검사 도구는 실행하지 않은 종이 분석이다.

검사 A는 [10000,10000], B는 [9999,10001], D는 [−1,5]를 사용한다. 검사 K는 [9999,9999]다. 네 검사는 반환/Range와 Read 목록을 모두 비교한다. 가상 준비 비용은 A가 1, B가 3, K와 D가 각각 2 작업 단위다. 비용은 벽시계나 운영 성능이 아니라 이 선택 문제의 주어진 값이다.

검사 수보다 어떤 변형을 어떤 관찰로 구별하는지 표를 읽는다. A/K/D 세 검사는 네 변형을 모두 구별할 수 있고 비용 합은 5다. B는 첫/둘째 관찰 시점의 값을 직접 다루는 추가 근거지만 현재 네 변형 집합의 전수 구별만 목적이면 중복일 수 있다. 빠진 실제 위험이 없다는 주장은 하지 않는다. Read 관찰을 제거하면 C를 구별하던 고정 값 검사가 더는 충분하지 않아 B의 역할이 바뀐다.

먼저 확인할 개념
  • 고유 위험과 회귀 근거

    기본의 결과/연결 관찰과 대안표를 변형별 구별 행렬로 확장한다.

  • 반환·오류·부작용의 범위

    관찰 계약을 줄이면 같은 검사 집합의 검출 범위도 달라진다.

설계안은 목적과 조건에서 비교한다

가상 주문 앱은 배송 정책이 하나이고 바뀌는 곳을 줄이고 싶다. A안은 공통 함수를 추출하고 B안은 전략 인터페이스와 정책 클래스를 도입한다. A는 구조가 작아 읽기 쉽고 B는 여러 정책 교체를 표현하기 쉽지만 추가 타입과 연결 코드를 배워야 한다. 현재 정책 수와 예상 변경이 근거이며 클래스 수가 많다는 것만으로 더 좋지 않다.

대안에 목적, 보존할 행동, 변경되는 파일, 복잡도, 시험 방법을 같이 적는다. 없는 요구를 상상해 모든 확장 구조를 먼저 넣으면 읽기와 검증 부담이 커질 수 있다. 반대로 정책이 여러 지역에서 실제로 교체된다면 한 함수의 긴 분기보다 명시한 전략이 유리할 수 있다.

회귀 검증은 기존 약속에 연결한다

회귀 검증은 수정으로 원래 기능이 깨졌는지 확인한다. 배송 기준이면 경계 9999/10000을 포함하고 통합된 최종 금액도 비교한다. 원래 반환값만 복제한 시험보다 정책 설명으로 예상값을 독립 계산한 시험이 같은 실수를 반복할 위험을 줄인다.

함수 시험은 규칙을 좁게 확인하고 화면/결제 연결 시험은 값이 올바른 위치에 쓰이는지 확인한다. 둘의 질문이 다르면 둘 다 필요할 수 있다. 다만 검증 숫자를 채우려고 같은 조건을 모든 층에서 반복하지 말고 고유한 연결 위험을 찾는다. 검사 시간과 실패 원인도 판단 근거다.

결정 기록은 과장 없는 증거를 남긴다

결정 기록에는 선택안, 현재 요구, 대안을 선택하지 않은 이유, 시험한 관찰 범위, 미수행 검증을 적는다. 작업자가 쓴 표를 독립 검토자가 계산하면 같은 가정을 확인할 수 있지만 실제 자동 시험이나 학습자 실험을 대신했다고 표시하지 않는다.

실제 측정 없이 빠르다거나 오류가 사라졌다고 말하지 않는다. 성능이 목적이면 실제 대표 입력과 환경을 고정해 측정하고, 이해가 목적이면 읽는 사람의 검토를 별도로 한다. 설계는 변경 목적을 설명하는 선택이며 모든 시나리오에서 한 안이 항상 최선이라는 판정이 아니다.

중간 과정을 따라가는 예제

정책 1개인 학습 앱에서 A 공통 함수와 B 전략 클래스군을 비교한다. 배송비 조건 >=10000 무료/미만 2000은 유지한다. 회귀 입력 주문액 9999와 10000의 최종 지불 금액을 계산하고 현재 요구로 선택 근거를 적어라.

  1. 9999는 배송 2000을 더해 11999다.

  2. 10000은 무료여서 10000이다.

  3. A와 B 모두 두 값을 보존해야 한다.

  4. 현재 교체 정책 요구가 없고 중복 제거가 목적이면 작은 A를 선택할 수 있다. 지역별 여러 정책 교체가 요구되면 B를 다시 비교한다.

관찰값 11999/10000을 보존한다. 현재 A 선택은 복잡도와 요구에 근거하며 B가 항상 나쁘다는 뜻은 아니다.

조건을 바꾸어 비교하기

세 검사와 네 검사의 서로 다른 근거

A/K/D와 A/B/K/D의 변형 구별 범위·주어진 비용을 비교하라.

  1. A가 H와 C를 구별하고 K가 J와 C를 구별하며 D가 G를 구별한다.

  2. 세 검사 비용은 1+2+2=5이며 네 변형을 모두 구별한다. B를 더하면 비용 8이고 이 네 변형의 합집합은 같다.

  3. B는 값의 변화가 있는 관찰 사례를 추가하지만 현재 목적만으로 실측 성능이나 이해도 개선을 주장하지 않는다.

범위는 네 변형으로 같고 비용은 5와 8이다. 계획 목적과 추가 가치의 근거를 기록한다.

비교할 점

실제로 검사 도구를 실행한 결과나 일반 결함 검출률은 아니다.

관찰을 좁히면 검사를 다시 고른다

Read 목록을 계약과 검사에서 제외한다. H/C/J/G 중 각 검사에 남는 차이를 쓰라.

  1. A는 H만 구별하고 K는 J만 구별한다. 고정 값에서 C 반환은 원래와 같다.

  2. B는 원래 9999 대 C 11999로 C를 구별한다.

  3. D에서는 원래와 G의 Range가 같으므로 이 입력과 좁은 관찰에서는 G를 구별하지 못한다. G의 추가 Read는 이제 제외된 관찰이다.

H/C/J를 구별하려면 A/B/K가 필요하며 비용 6이다. 원래 네 변형의 구별 요구를 그대로 완료했다고 보고하지 않는다.

비교할 점

G에 대한 이 판정은 지정 대역의 두 반환과 좁은 계약 범위이며 임의 외부 실패까지 보존을 증명하지 않는다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

후보 U는 공통 함수 하나, 후보 V는 정책 객체군이다. 현재 한 정책만 요구되고 표의 행동은 모두 보존한다고 가정한다. 미래 두 지역 정책 요구가 승인되면 선택 기록을 어떻게 갱신하는가?

힌트 1

타입 개수만으로 순위를 정하지 않는다.

힌트 2

현재 검증과 새로운 요구의 검증을 분리한다.

풀이와 답 확인

  1. 현재 중복 제거와 한 정책이면 작은 U를 선택한 이유와 검증 범위를 기록할 수 있다.

  2. 두 지역 정책의 선택·등록·잘못된 지역 거절 요구를 명시하고 U의 분기와 V의 정책 교체 비용을 다시 비교한다. 기존 회귀와 새 연결/실패 검사를 계획한다.

새 요구가 대안 비교의 전제를 바꾸므로 비용·행동·미수행 검증을 갱신한다. 실제 사용자 가독성/성능은 아직 측정하지 않았다.

흔한 오답에서 다시 생각하기

패턴을 먼저 많이 넣으면 미래 선택도 항상 옳다.

예상 확장과 실제 승인된 변경은 다르며 불필요한 연결과 검사 부담이 생길 수 있다.

내 말로 설명하기

행렬의 모든 열을 구별하면 실제 결함이 모두 사라지는가?

설명 기준 확인

주어진 변형·입력·관찰에 대한 손분석일 뿐이다. 구현·실행·운영 검증은 별도로 남는다.

직접 검사와 연결 검사를 왜 나누는가?

설명 기준 확인

같은 규칙의 중복 확인만 늘리기보다 올바른 값이 소비자 결과에 실제 쓰이는 위험을 따로 확인한다.

한 단계 더

정책이 국내/해외 2개로 바뀌는 가상 요구를 추가하고 대안표를 갱신하라. 선택 기준·검사 대상·미수행 사항이 바뀌는 부분을 적는다.

출처와 확인 범위
  • Martin Fowler Refactoring

    외부 관찰 행동 보존 정의, 작은 변환의 연속, 매 단계 동작·빈번한 시험 설명을 읽음.

  • Ham Vocke The Practical Test Pyramid

    What to Test?/Test Structure에서 관찰 행동·정상/경계·구현과 과도한 결합 회피, Arrange/Act/Assert 및 탐색검토 한계를 읽음.

다른 문제에 적용하기

추출 제안과 회귀 계획의 결정 기록

각 비교는 새 초기 상태에서 시작한다. 배송 F를 추출하면서 기준을 10000에서 12000으로 바꾸자는 제안의 두 목적을 나누고 amount 11000의 전후 값을 쓰라. 별도 quote 모형의 [9999,10001]에서 원래/E/C의 반환과 Read 수를 비교하라. 원래 관찰 계약의 A/K/D 회귀 계획 비용과 네 변형 구별 범위를 계산하고 예산 4일 때 완료 주장을 검토하라. 마지막으로 Read 관찰을 제외했을 때 C를 구별하는 추가 검사와 G의 남는 미확인 범위를 기록하라. 실제 프로그램·자동 시험은 실행하지 않는다.

힌트 1

추출 직후 옛 정책을 먼저 보존하고 이후 기능 기준을 바꾼다. quote의 첫 값과 배송 판단의 둘째 값을 따로 적는다.

힌트 2

회귀 비용과 위험 범위를 따로 계산한다. Read가 빠진 행렬에서 고정 값의 C와 오류 종류가 같은 G를 다시 보라.

풀이와 답 확인

  1. F 추출 직후 amount 11000의 배송비는 0이다. 기준 12000의 기능 변경 뒤에는 2000이다. 두 단계의 관찰 목적을 분리한다.

  2. 새 [9999,10001]에서 원래와 E는 9999를 반환하고 Read 두 사건이다. C는 11999를 반환하고 Read 한 사건이다.

  3. A/K/D 비용은 5이며 H/C/J/G 네 변형을 구별한다. 예산 4이면 이 세 검사 모두를 넣었다고 주장할 수 없다. K/D만 넣으면 비용 4이나 H가 빠진다.

  4. Read를 제외하면 C를 값으로 구별하는 B를 추가한다. A/B/K 비용은 6이다. D의 Range만으로는 G를 구별하지 못하며 실제 외부 읽기 실패 등 다른 계약은 아직 확인하지 않았다.

추출의 배송비 0과 기능 변경의 배송비 2000을 나눈다. E는 원래의 반환 9999와 두 읽기를 보존하지만 C는 반환 11999와 한 읽기로 다르다. 원래 관찰의 A/K/D 비용 5는 예산 4를 넘는다. 좁힌 관찰에서는 B가 필요하고 G의 일반 보존과 실제 회귀 실행은 미확인이다.

해결한 뒤 점검할 것

  • 동일 지식과 변경 책임을 근거로 구조/기능 단계를 구별한다.

  • 반환·오류·Read 목록과 각 문제의 독립 초기 상태를 추적한다.

  • 검사 비용·변형 구별 집합·관찰 계약 변경을 각각 계산한다.

  • 손분석과 실제 코드·자동 회귀·운영·학생 미수행을 구별한다.

보강 자료의 출처와 확인 범위
  • Martin Fowler Code Smell

    실제 전체 본문 76–80행의 표면 신호·항상 문제는 아님·더 깊은 책임 조사·한 냄새씩 학습을 읽었다. 배송 영향 행렬과 가격 책임은 자체 가상 설계다.

  • Martin Fowler Refactoring

    실제 64–76/86–93행의 외부 행동 보존·작은 변환·기능 전후 구조 변경·도구 없이 빈번한 시험·정의를 읽었다. E/C/G의 읽기 시점과 오류 장부는 자체 모형이다.

  • Introduce Parameter Object

    실제 63–76행의 함께 전달되는 날짜 인자 두 개를 객체로 묶는 전후 선언을 읽었다. 닫힌 정수 범위·역순 거절·불변 입력의 추가 계약은 자체 설계다.

  • Extract Function

    실제 63–90행의 계산 뒤 상세 출력 블록 추출·출력 위치와 순서·별칭을 읽었다. 순수 fee 추출의 외부 읽기 위치 보존은 자체 손논증이며 실제 도구는 쓰지 않았다.

  • Ham Vocke The Practical Test Pyramid

    실제 What to Test 275–296행과 Test Structure 297–305행의 공개 관찰·정상/경계·내부 구조 과결합 회피·Arrange/Act/Assert, 850–859행의 자동화 미완전/탐색 검토를 읽었다. 네 변형 행렬과 가상 비용은 자체 구성이다.

기본 세 설명과 같은 단원의 선수 세 설명을 전체 읽었다. 배송 추출 직후 11000의 배송비 0과 기준 변경 뒤 2000, 닫힌 [2,4]의 세 기록과 반열린 두 기록을 손계산했다. quote 네 목록에서 첫/둘째 관찰·음수 실패 시점·반환과 Read 수를 분리하고 E의 보존·C/G 반례를 손유도했다. A/K/D의 구별 합집합 H/C/J/G와 비용 5, K/D의 비용 4와 H 누락, 전체 네 검사 비용 8을 계산했다. Read 관찰 제외 시 A/B/K 비용 6과 D의 G 미구별을 별도 확인했다. 전이와 모든 12 과제/두 힌트/오답을 손논증했으며 실제 코드·리팩터링 도구·대역·자동 회귀·동시성·성능·학생은 실행하지 않았다.
