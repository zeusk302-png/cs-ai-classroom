소단원 6.1

class·sequence 모델

상자 그림은 프로그램의 구조를 말할까, 한 번의 실행을 말할까?

준비 개념과 학습 목표

준비 개념

  • 클래스는 객체들의 구조와 행동을 분류한다.

  • 객체는 특정 실행에 참여하는 인스턴스다.

  • 메서드 호출에는 호출자·수신자·입력·결과가 있다.

학습 목표

  • 클래스 모델과 상호작용 모델을 구분한다.

  • 특정 인스턴스 사이의 요청·응답을 추적한다.

  • 순서 그림의 범위와 시간 의미를 설명한다.

같은 클래스의 두 책을 찾으면 두 결과의 순서까지 정해질까?

앞 본문은 Copy7과 Copy8이 같은 Copy 클래스의 서로 다른 객체임을 설명했다. 새 검색은 제목이 아니라 고유 copyId로 객체를 돌려준다. 두 권 모두 제목은 같은 문자열이지만 Copy7은 AVAILABLE, Copy8은 ON_LOAN이다. 클래스의 공통 연산과 개별 객체의 상태를 서로 다른 칸으로 적어야 두 결과를 섞지 않는다.

먼저 서로 다른 네 생명선이 참여하는 두 독립 메시지를 생각하자. 메시지 A의 발신을 a, 수신을 A라고 쓰고 다른 메시지의 발신을 b, 수신을 B라고 쓴다. 각 메시지에서 a<A, b<B만 주어지며 다른 사건 사이에는 추가 순서가 없다. 가능한 전체 나열은 여섯 개지만 이것은 각 경우가 실제로 발생했다거나 같은 확률이라는 뜻이 아니다.

두 메시지를 같은 발신 생명선에서 차례대로 보내 a<b까지 명시하면 가능한 나열이 세 개로 줄어든다. 그래도 A<B가 자동으로 생기지는 않는다. 수신자가 다르면 a,b,B,A처럼 둘째 수신이 먼저인 나열도 주어진 순서를 지킨다. 호출의 동기·비동기 가정과 참여 생명선을 먼저 써야 그림의 아래쪽 위치를 과도하게 해석하지 않는다.

응답을 화면에 적용할 때는 순서 외에 요청의 의미도 연결한다. ui가 요청 R1으로 Copy7을 찾고 이어 R2로 Copy8을 선택했다면, 늦게 온 R1의 결과를 최신 선택에 붙이면 잘못된 책을 보여 줄 수 있다. 새 정책은 현재 선택 요청 ID와 응답 ID가 같은 경우만 화면에 반영한다. 이는 실제 UI 구현이 아닌 자체 비동기 관찰 계약이다.

먼저 확인할 개념
  • class·sequence 모델

    종류와 개별 생명선을 구별한 뒤 새 독립 사건의 순서를 읽는다.

  • 모델·코드 일치

    같은 반환 모양이어도 수신 객체·요청 ID가 계약과 맞는지 비교한다.

종류의 구조와 개별 참여자

자체 도서 대출 모델에서 Catalog 는 검색을, Copy 는 개별 책 한 권의 상태를, Loan 은 대출 기록을 책임진다. 같은 제목의 Copy 두 개는 하나의 클래스가 분류하는 두 객체다. 클래스 모델에는 상태·연산·관계를 적고 특정 한 권의 실행 순서를 그리지 않는다.

순서 모델의 생명선은 c1:Copy 처럼 개별 참여자를 나타낸다. 클래스 Copy 자체를 모든 책 한 권인 것처럼 표시하면 어떤 상태가 변했는지 모호해진다. 구현 전에 이름·입력·반환 타입을 표로 정하면 두 모델을 연결하기 쉽다.

구조에 실행 경로를 더하기

자체 성공 시나리오는 ui 가 catalog.find(copyId)를 호출하고 c1 을 받은 뒤 c1.borrow(userId)를 요청해 대출 결과를 받는다. 위에서 아래로 읽으며 각 생명선 안의 사건 순서와 메시지의 발신이 수신보다 먼저라는 관계를 확인한다. 순서 모델은 클래스 정의 목록이 아니라 선택한 상호작용이다.

그림의 세로 간격이 10 칸이라고 10 초가 걸렸다는 뜻은 아니다. 시간 제약을 별도 명시하지 않았다면 상대적인 사건 순서만 읽는다. 서로 독립된 생명선의 모든 사건을 하나의 전역 시간 순서로 강제로 정하지 않는다. 이 예제는 이해를 위해 단일 순차 동기 호출로 한정한다.

구조(교육용 텍스트 모델):
Catalog.find(copyId): Copy 또는 없음
Copy.borrow(userId): 대출 성공 또는 거절

성공 경로(동기 호출):
ui → catalog: find(7)
catalog → ui: c1
ui → c1: borrow(U1)
c1 → ui: 성공

생략한 경로를 표시하기

Copy7 을 찾지 못하면 borrow 호출로 넘어가지 않는다. 책이 이미 대출 중이면 거절 경로가 필요하다. 성공 그림만 작성했다면 전체 동작을 모두 보여 준다고 주장하지 말고 입력·초기 상태·생략한 실패를 적는다.

UML 은 구조와 상호작용을 표현하는 언어이며 그림을 그렸다는 사실이 프로그램 실행이나 정확성 증명이 되지는 않는다. 실제 구현에서는 반환 타입·예외·동시 요청을 계약과 연결한다. 본문은 설치 없이 텍스트 모델을 읽으며 UML 도구나 도서 시스템을 실행하지 않는다.

추가 조건허용 전체 나열개수

a<A, b<B만 있음

aAbB, abAB, abBA, bBaA, baBA, baAB

소문자는 발신, 대문자는 대응 수신이다. 각 문자열은 네 사건을 각각 한 번 쓴다. 첫 행의 네 생명선은 서로 독립이다. 둘째 행부터 발신자가 하나라는 별도 조건을 적용한다. 세로 길이는 초 단위가 아니며 나열 수는 실행 횟수나 확률이 아니다.

중간 과정을 따라가는 예제

Copy7 은 AVAILABLE, Copy8 은 ON_LOAN 이다. find(7)은 c1, find(8)은 c2, find(9)는없음을 반환한다. 한 요청에서 find 성공 뒤에만 borrow 를 호출한다. 각 입력의 경로를 쓰라.

  1. 7: find→c1, c1.borrow→성공. find 와 borrow 두 요청이 있다.

  2. 8: find→c2, c2.borrow→거절. 객체를 찾았다는 사실만으로 대출 성공은 아니다.

  3. 9: find→없음, 종료. borrow 를 호출할 수신자가 없어 호출하지 않는다.

7 성공·8 대출 거절·9 검색 실패이며 호출 수는 2·2·1 이다. 클래스 한 개에 서로 다른 인스턴스 상태가 있다.

조건을 바꾸어 비교하기

한 발신 생명선의 순서가 두 수신의 순서를 정하지는 않는다

같은 발신자의 a<b와 두 메시지 발신-수신 제약만 있을 때 abBA를 검사하라.

  1. a는 A보다 앞이고 b는 B보다 앞이다.

  2. a도 b보다 앞이므로 세 제약을 모두 지킨다.

  3. B가 A보다 먼저라는 이유만으로 이 나열을 거절할 수 없다.

별도 A<B 조건이 없으면 abBA는 허용된다.

비교할 점

동기 호출에서 첫 작업의 응답을 받은 뒤 둘째 작업을 발신한다는 추가 계약이라면 aAbB만 남는다. 여기서 A는 첫 요청의 수신 사건이며 응답 사건은 네 기호에 따로 적지 않았다.

늦은 검색 결과를 최신 책으로 오해하는 화면

R1은 Copy7, R2는 Copy8을 검색한다. 현재 선택은 R2이고 응답은 R2, R1 순서로 온다. 각 검색의 결과 객체는 원래 요청과 일치한다.

  1. R2 응답의 객체 Copy8을 반영한다. 화면은 ON_LOAN이다.

  2. R1은 현재 선택 ID와 달라 화면에 반영하지 않는다.

  3. 무조건 마지막 도착을 반영하면 Copy7의 AVAILABLE을 최신 선택 Copy8에 잘못 붙인다.

요청 ID 검사는 최신 선택과 화면 결과를 연결한다.

비교할 점

검색 결과 자체가 맞는 것과 그 결과를 현재 화면에 적용해도 되는 것은 다르다.

종이와 본문으로 직접 해보기

7 을 성공 대출한 뒤 같은 7 을 다시 요청한다. 어떤 경로이며 처음과 무엇이 달라졌는가?

힌트 보기

Catalog 검색 결과의 존재와 Copy 의 대출 상태를 별도로 적는다.

풀이 보기

다시 find(7)은 c1 을 반환하지만 상태가 ON_LOAN 으로 변해 borrow 는거절한다. 두 호출은 유지되나 두 번째 호출 결과가 달라진다.

오해와 반례

클래스 모델에 Copy 하나를 그리면 실제 책도 하나만 존재한다.

클래스는 객체들의 종류다. Copy7·Copy8 두 생명선과 서로 다른 상태를 가진 인스턴스가 있을 수 있다. 그림의 상자 수를 런타임 객체 수로 해석하지 않는다.

스스로 풀어보기

먼저 답과 이유를 적고, 필요한 만큼 힌트를 한 단계씩 열어 보세요.

연습 1 · 값과 상태 예측

네 독립 생명선에서 baAB는 허용되는가? 같은 발신자의 a<b를 추가한 경우도 판정하라.

힌트 1

a가 A보다 먼저인지 확인한다.

힌트 2

b와 a의 위치를 비교한다.

풀이와 답 확인

  1. baAB는 두 발신이 각 수신보다 먼저이므로 첫 모형에서 허용한다.

  2. 둘째 모형에서는 b가 a보다 앞이라 a<b를 위반한다.

독립 모형은 허용, 같은 발신자의 지정 순서 모형은 거절이다.

흔한 오답에서 다시 생각하기

수신 A가 B보다 앞이므로 두 경우 모두 허용한다.

수신 순서만 보면 발신 생명선의 a<b 조건을 놓친다.

연습 2 · 오류 찾아 고치기

Copy 클래스 한 칸에 status=AVAILABLE을 쓰고 Copy7/Copy8 모두 대출 가능하다고 설명했다. 고쳐라.

힌트 1

클래스는 같은 종류를 분류한다.

힌트 2

Copy8의 개별 상태가 ON_LOAN이다.

풀이와 답 확인

  1. 공통 연산은 클래스 모델에 남긴다.

  2. 객체 상태는 Copy7=AVAILABLE, Copy8=ON_LOAN으로 따로 적고 후자는 대출 거절 경로를 연결한다.

클래스 한 칸을 모든 객체의 현재 상태로 해석하지 않는다.

흔한 오답에서 다시 생각하기

클래스 그림을 두 개로 복사하면 서로 다른 클래스로 해결된다.

같은 Copy 타입의 서로 다른 인스턴스이므로 종류를 나눌 필요가 없다.

연습 3 · 직접 만들어 보기

a<A, b<B, a<b에 A<B를 추가했을 때 허용되는 전체 나열을 모두 만들라.

힌트 1

첫 사건은 a다.

힌트 2

a 다음에는 A 또는 b를 선택할 수 있다.

풀이와 답 확인

  1. a 다음 A를 고르면 aAbB다.

  2. a 다음 b를 고르면 A가 B보다 먼저여야 하므로 abAB다.

aAbB와 abAB의 두 나열이다.

흔한 오답에서 다시 생각하기

abBA도 발신이 수신보다 앞이라 포함한다.

새 A<B 제약까지 모두 만족해야 한다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

현재 R2 선택 중 R1 응답을 버린다. 이 정책만으로 서버의 R1 대출 변경이나 자원 사용도 취소됐다고 주장할 수 있는가?

힌트 1

이번 규칙은 화면 반영만 정했다.

힌트 2

응답 소비와 서버 작업 종료를 분리한다.

풀이와 답 확인

  1. 버린 것은 화면 반영이며 서버 연산 취소 계약은 없다.

  2. 실제 취소를 원하면 서버 요청 ID·취소 수락·이미 완료된 효과 처리 등의 별도 계약이 필요하다.

늦은 응답 무시는 서버 작업 취소 증거가 아니다.

흔한 오답에서 다시 생각하기

화면에 없으므로 서버 효과도 없어진다.

관측을 숨기는 일과 원격 상태를 되돌리는 일은 별도다.

소단원 6.2

실행경로와 책임

화면 객체가 대출 중인 책을 직접 AVAILABLE 로 바꿔도 될까?

준비 개념과 학습 목표

준비 개념

  • 책임은 판단·정보·변경을 맡는 역할이다.

  • 불변조건은 허용된 상태가 지켜야 하는 조건이다.

  • 동기 호출은 결과를 얻은 뒤 다음 단계를 진행하는 모형이다.

학습 목표

  • 경로마다 책임 객체와 상태 변경을 연결한다.

  • 대출 성공·거절의 조건을 독립적으로 추적한다.

  • 정보를 가진 객체의 규칙 보존을 설명한다.

책과 대출 기록을 서로 다른 객체가 바꾸면 누가 실패를 복구할까?

앞 본문은 한 Copy의 status와 borrower를 함께 바꾸고 거절 때 유지했다. 새 모델은 두 Copy와 Ledger를 연결한다. Ledger는 고유 copyId에서 현재 대출자로 가는 표다. 불변조건은 각 책이 AVAILABLE일 때 Ledger에 그 키가 없고, ON_LOAN일 때 Ledger의 해당 값이 Copy.borrower와 같은 것이다. 한 객체의 두 필드가 맞아도 두 객체 사이 관계는 틀릴 수 있다.

새 BorrowService는 유효한 사용자와 AVAILABLE을 검사하고, Copy와 Ledger를 한 업무 전이로 변경한다. 성공은 둘 다 반영되며 지정한 Ledger 실패는 둘 다 원래 상태로 보존하고 거절한다. 여기서는 실패 시 rollback이 가능한 순차 종이 계약을 가정한다. 실제 저장소/예외/동시 실행에서 그 원자성이 이미 구현됐다는 주장은 하지 않는다.

단순 절차 P는 Copy를 먼저 ON_LOAN으로 만든 뒤 Ledger 기록에 실패하면 거절만 반환한다. 초기 Copy7=(AVAILABLE,없음), Ledger={}에서 P는 Copy7=(ON_LOAN,U1), Ledger={}를 남긴다. 첫 객체의 내부 필드는 일치해도 전체 관계는 깨진다. 반대로 Ledger만 먼저 쓰고 Copy 변경을 생략해도 실패한다.

책임을 Service에 놓았다고 동시 안전이 자동으로 생기지도 않는다. 두 요청이 함께 AVAILABLE을 관찰하고 둘 다 성공 반환하면 하나의 최종 Ledger 값만 있어도 두 사용자에게 성공을 약속한 셈이다. 요청의 검사와 두 객체 변경을 보호할 정책을 명시해야 한다. 책임 모델은 보호할 범위를 찾는 도구이지 잠금 구현의 증거가 아니다.

판단을 맡을 곳을 정하기

자체 Copy 는 status 가 AVAILABLE 또는 ON_LOAN 이며 현재 borrower 가 없을 때와 있을 때를 일치시킨다. AVAILABLE 이면 borrower 없음, ON_LOAN 이면 borrower 있음이라는 불변조건을 정한다. UI 는 요청을 전달하고 결과를 보여 주며 대출 규칙을 검사 없이 직접 변경하지 않는다.

Catalog 는 식별자로 Copy 를 찾고 Copy.borrow 는 현재 상태를 검사한다. 이 책임 배분은 이 예제의 설계 선택이다. 큰 서비스에서는 별도 도메인 서비스나 트랜잭션을 사용해도 되지만 누가 최종 규칙을 보존하는지 분명해야 한다.

성공 경로와 거절 경로

borrow(U1)에서 AVAILABLE 이면 두 필드를 함께 ON_LOAN·U1 로 변경하고 성공을 돌려준다. 이미 ON_LOAN 이면 상태를 유지하고 거절한다. borrower 만 지우거나 status 만 바꾸면 두 필드의 의미가 어긋난다.

여기서는 한 요청이 끝나야 다음 요청이 시작하는 순차 모형이다. 상태 검사와 변경 사이에 다른 요청이 들어오는 실제 동시 환경은 이 종이 추적만으로 검증되지 않는다. 두 요청의 동시 성공을 막으려면 별도의 원자성 정책과 구현 증거가 필요하다.

경로의 길이와 변경량을 구분하기

실패도 실행 경로다. 검색 실패는 Copy 에 도달하기 전에 끝나고 이미 대출 거절은 Copy 까지 도달해도 상태를 바꾸지 않는다. 호출 수가 같다는 이유로 같은 작업을 수행했다고 판단하지 않는다.

구현 로그를 모델과 연결할 때 수신 객체·요청 ID·판단 조건을 식별하면 어느 분기를 탔는지 확인할 수 있다. 다만 로그 몇 줄을 관찰한 것은 모든 경로나 동시성을 증명한 것이 아니다. 이 절은 자체 순차 모델의 책임과 가능한 경로를 설명한다.

각 실패 행은 같은 초기 상태에서 독립 시작한다. 빈 표와 값이 없는 Copy를 같은 객체로 보지 않는다. 원자 계약 행은 요구하는 사후 상태이며 실제 트랜잭션 실행 결과가 아니다.

중간 과정을 따라가는 예제

  1. U1 요청은 AVAILABLE 이므로 성공해(ON_LOAN,U1)이 된다.

  2. U2 요청은 이미 ON_LOAN 이라 거절하고(ON_LOAN,U1)을 유지한다.

  3. U1 반납은 현재 borrower 와 일치해 성공하고 (AVAILABLE,없음)이 된다.

한 객체 검사가 통과해도 관계가 실패한다

P의 Ledger 실패 뒤 Copy 내부 조건과 전체 조건을 각각 검사하라.

  1. ON_LOAN과 borrower U1은 Copy 내부 조건을 만족한다.

  2. Ledger에는 키 7이 없어 현재 대출 기록이 일치하지 않는다.

  3. 반환은 거절인데 Copy가 변경된 것 또한 새 실패 보존 계약을 위반한다.

성공한 앞 요청과 실패한 뒤 요청의 다른 복구 범위

새 원자 업무 계약으로 Copy7 대출 U1이 성공했다. 이어 AVAILABLE인 Copy8에 U2를 대출하려는데 Ledger 기록이 실패한다.

  1. 첫 요청 뒤 Copy7의 상태는 ON_LOAN이고 대출자는 U1이며, Ledger는 {7:U1}이다.

  2. 둘째 실패는 Copy8을 AVAILABLE로 유지하고 키 8을 추가하지 않는다.

  3. 이미 완료한 첫 요청의 기록 7은 유지한다.

최종 Ledger는 {7:U1}이며 Copy7 대출은 유지된다.

비교할 점

실패 보존은 둘째 요청의 시작 상태를 보존하는 뜻이다. 전체 실행을 처음으로 되감는 뜻이 아니다.

소단원 6.3

모델·코드 일치

그림에서 실패는 상태를 유지한다는데 코드가 먼저 상태를 바꾼다면 무엇을 믿어야 할까?

준비 개념과 학습 목표

준비 개념

  • 모델은 선택한 범위의 계약과 경로를 표현한다.

  • 코드 정적 추적은 실제 실행 관찰과 다르다.

  • 같은 버전과 같은 가정에서 비교해야 한다.

학습 목표

  • 연산·조건·상태·결과의 일치표를 만든다.

  • 검사 순서 때문에 생기는 모델 불일치를 발견한다.

  • 변경 시 모델과 구현을 함께 갱신할 근거를 설명한다.

최종 책 상태가 같으면 중간 알림까지 같은 실행일까?

앞 본문은 같은 거절 반환이어도 실패 전에 바꾼 상태가 다를 수 있음을 보여 줬다. 새 계약의 관찰 범위는 Copy의 상태/대출자, Ledger 내용, 반환값, 그리고 외부 알림 목록이다. 내부 임시 변수는 비교에서 숨겨도 고객에게 전달한 알림은 숨기지 않는다. 어떤 상태를 비교할지 먼저 정해야 모델·코드 일치가 의미를 갖는다.

정상 절차는 검사 모두 통과 후 Copy와 Ledger를 함께 반영하고 성공 알림 loan(7,U1)을 한 번 추가한다. 거절은 세 상태 모두 보존하고 알림도 추가하지 않는다. 알림을 포함한 원자 성공은 이 자체 모델의 요구이며 실제 네트워크 전달을 한 번만 보장한 구현이 아니다.

변형 M은 먼저 loan(7,U1)을 알린 뒤 Ledger 실패가 나면 Copy와 Ledger를 되돌리고 거절한다. 최종 저장 상태와 거절 반환은 정상 실패와 같지만 알림이 남는다. 상태 복구만으로 이미 관찰한 외부 효과를 없앨 수 없다. 따라서 성공 경로 하나 또는 마지막 스냅샷만 비교하는 검사는 M을 놓친다.

내부 revision을 모델에서 숨기는 일은 별도 선택이다. 실패마다 revision을 증가시키는 구현도 revision이 계약 밖이고 모든 허용된 고객 관찰이 같다면 그 변경 자체가 불일치인 것은 아니다. 그러나 고객에게 revision을 반환하거나 그것으로 후속 요청을 거절한다면 더 이상 숨길 수 없다. 추상화는 관찰에 영향을 주는 차이를 임의로 지우는 권한이 아니다.

먼저 확인할 개념
  • 모델·코드 일치

    반환 외의 상태 효과를 비교한 뒤 알림이라는 외부 효과를 추가한다.

  • 실행경로와 책임

    관계 불변조건과 실패 보존을 관측 범위에 넣는다.

비교할 항목을 작게 나누기

자체 모델의 borrow 는 유효 userId 와 AVAILABLE 조건에서만 상태를 바꾼다. 모델의 연산이 코드의 어느 메서드인지, 조건이 어느 분기인지, 결과가 어느 반환인지 연결한다. 이름이 같다는 것만으로 계약까지 같지는 않다.

코드가 모델에 없는 예외를 던지거나 실패 전에 상태를 바꾸면 관측 차이가 생긴다. 모델도 설계의 초안일 수 있으므로 무조건 그림만 정답으로 정하지 말고 요구사항과 합의된 계약을 확인한다. 이후 같은 변경 버전에서 두 자료를 함께 맞춘다.

검사 전에 변경하는 잘못된 경로

아래는 자체 의사코드다. userId 가 빈 문자열이면 거절해야 하지만 먼저 status 를 ON_LOAN 으로 바꾸면 실패한 요청 뒤 borrower 가 없고 status 는 ON_LOAN 인 상태가 남는다. 성공 결과만 확인하면 이 경로를 놓친다.

고친 절차는 입력 검사→현재 상태 검사→두 필드 변경→성공 반환이다. 검사를 모두 통과한 뒤 변경하므로 주어진 순차 모형에서 거절은 상태를 유지한다. 실제 중간 오류나 동시 요청은 별도 검증 범위이며 이 의사코드를 완전한 서비스 구현이라고 주장하지 않는다.

잘못된 절차:
status = ON_LOAN
if userId가 빈 값: return 거절
borrower = userId
return 성공

수정 절차:
if userId가 빈 값: return 거절
if status != AVAILABLE: return 거절
status = ON_LOAN; borrower = userId
return 성공

한 사례와 전체 범위를 구별하기

AVAILABLE·유효 ID, AVAILABLE·빈 ID, ON_LOAN·유효 ID 의 세 경로를 각각 확인한다. 모델이 한 경로만 보여 준다면 미표시 경로 목록을 붙인다. 모델을 모든 실행의 증명으로 표시하지 않는다.

교정 기록에는 문제 조건·변경 전후 결과·검토 버전을 남긴다. 타입·반환·오류 정책을 바꾸면 클래스 모델과 순서 모델의 메시지도 영향받는다. 자동 생성 도구를 쓰더라도 불변조건과 업무 의미 일치는 사람의 검토가 필요하다.

중간 과정을 따라가는 예제

초기 AVAILABLE·borrower 없음에서 빈 userId 를 잘못된 절차와 수정 절차에 각각 넣고 반환·상태·불변조건을 비교하라.

  1. 잘못된 절차는 먼저 status=ON_LOAN 으로 만든다.

  2. 빈 입력 검사에서 거절하며 borrower 대입은 실행하지 않는다. 따라서 ON_LOAN·없음으로 불변조건을 위반한다.

  3. 수정 절차는 첫 검사에서 거절하므로 AVAILABLE·없음을유지한다.

둘 다 거절이지만 상태 효과가 다르다. 반환값만으로 모델과 코드의 일치를 판정하지 않는다.

조건을 바꾸어 비교하기

거절과 마지막 저장값이 같아도 다른 관찰

표의 정상 실패와 M을 모델과 비교하라.

  1. Copy와 Ledger는 모두 초기 상태라 이 두 칸만 보면 같다.

  2. 둘 다 거절하므로 반환만 보는 검사도 같다.

  3. M의 알림은 하나이며 정상 실패의 알림은 비어 있어 거절 무효과 계약을 위반한다.

외부 알림 목록이 두 실행을 구별하는 증인이다.

비교할 점

이미 발신한 알림을 지역 리스트에서 지웠다는 것으로 실제 수신자의 관찰을 되돌렸다고 주장하지 않는다.

숨긴 revision이 다음 요청에서 보이기 시작한다

초기 revision=4이며 첫 실패 때 내부 구현만 5로 올린다. 모델은 실패 때 revision을 4로 유지한다. 다음 요청은 expectedRevision=4를 보내고, 현재 revision과 다르면 거절한다. 이 다음 요청은 나머지 입력·대출 상태 검사를 모두 통과하며 저장 실패도 없다고 가정한다.

  1. 첫 실패의 반환과 저장 내용은 같을 수 있다.

  2. 다음 expectedRevision=4 요청은 모델의 revision 4와 일치해 성공하지만 구현의 revision 5와 불일치하여 거절된다.

  3. 후속 거절 차이가 생기므로 revision을 완전히 관찰 밖이라고 할 수 없다.

직접 반환하지 않아도 후속 결과에 영향을 주는 상태는 비교 대상이다.

비교할 점

공개하지 않은 필드 이름이라는 이유만으로 추상 관찰에서 제외하지 않는다.

다른 문제에 적용하기

비동기 화면과 원자 대출을 같은 계약에 연결하기

현재 화면 선택은 R2=Copy8이다. R1=Copy7의 검색 응답이 늦게 왔다. 별도 새 Copy7=(AVAILABLE,없음), Ledger={}, 알림=[], revision=4에서 U1 대출의 Ledger 기록이 실패했다. 구현 M은 먼저 성공 알림을 보내고 저장 상태만 복구하며 revision을 5로 바꾼다. 정상 실패 모델은 revision도 4로 유지한다. 화면 정책과 전체 실패 관찰을 계산하라. 다음 요청은 expectedRevision=4를 보내고 현재 revision과 다르면 거절한다. 이 요청의 나머지 조건은 모두 통과하고 저장 실패도 없다. 모델과 구현의 후속 결과도 비교하라.

힌트 1

화면 요청 ID와 업무 Copy ID는 다른 맥락이며 각각의 초기 상태를 따른다.

힌트 2

실패 보존은 반환뿐 아니라 Ledger·Copy·알림과 후속 공개 결과를 포함한다.

풀이와 답 확인

  1. 현재 R2 선택과 R1 응답이 달라 해당 화면 반영은 생략한다. 이것이 별도 서버 업무 취소를 의미하지 않는다.

  2. M은 거절 후 Copy7과 Ledger는 초기 상태지만 알림 [loan(7,U1)]이 남는다. 정상 실패는 알림 []까지 유지해야 하므로 불일치다.

  3. 실패 때 revision을 5로 바꾼 구현은 expectedRevision=4의 후속 요청을 거절한다. 실패 때 revision 4를 유지한 모델은 나머지 조건도 모두 통과하여 성공한다. 후속 결과가 달라 revision을 관찰 범위에서 숨길 수 없다.

  4. 교정 계약은 검사 후 저장/성공 알림을 하나의 명시 업무 전이로 정하고 거절은 모든 관찰을 보존한다. 실제 서버·알림 전달 원자성은 별도 구현 및 검증 대상이다.

늦은 화면 응답 무시, 실패의 외부 효과 보존, 후속 요청의 revision 관찰을 각각 구별한다.

해결한 뒤 점검할 것

  • 화면 선택과 응답 ID를 비교하고 서버 취소를 주장하지 않았다.

  • 실패의 Copy·Ledger·반환·알림 네 관찰을 모두 계산했다.

  • revision의 후속 요청 차이를 구체적으로 설명했다.

  • 종이 모델과 실제 구현/학습자 실행의 범위를 구분했다.
