inversion of control

내 함수가 일을 시작하는 대신 누군가 정해진 때에 불러 준다면?

학습 목표

종료 요청이 왔다는 사실과 자원을 해제해도 된다는 판단은 같은가?

호출 순서를 host에 맡기면 확장 코드는 자신을 부르는 사람의 수명 계약을 따라야 한다. 등록은 호출 예약의 가능성을 만들지만 준비 완료나 작업 종료를 뜻하지 않는다. 아래 자체 host는 단일 실행 흐름에서 사건을 순서대로 처리하며 실제 .NET event loop를 재현하지 않는다.

host의 상태는 Running, Closing, Closed다. Running에서 입력을 받으면 작업을 큐에 넣는다. 하나를 시작하면 큐에서 빼고 active를 1 늘린다. stop 요청은 Closing으로 바꾸고 새 입력만 거절한다. 이미 받은 작업은 끝까지 처리하는 drain 정책이다. active와 큐가 모두 0일 때만 자원을 한 번 해제하고 Closed로 간다. 실패한 작업도 완료 사건으로 active를 줄이지만 성공 출력으로 세지 않는다.

DI는 필요한 객체를 밖에서 연결하는 방식이며 해제 책임은 별도다. 공식 .NET 컨테이너가 생성한 객체와 외부에서 만든 인스턴스 등록은 해제 책임이 같지 않다. 자체 모형에서는 scope가 만든 출력기 R은 scope가 소유하고, 외부에서 빌린 출력기 E는 외부 소유자가 해제한다. 플러그인은 두 객체를 빌려 쓰며 임의로 해제하지 않는다. long-lived 객체에 요청 R을 저장해 scope 종료 뒤 다시 쓰면 연결은 성공해도 수명 계약을 어긴다.

프로그램의 진행을 맡긴다

보통 라이브러리는 내 코드가 원하는 순간 호출한다. 프레임워크는 행사 진행자처럼 시작·입력·종료 순서를 관리하고 내가 등록한 확장 코드를 정해진 지점에서 부른다. 이것이 제어 역전의 한 모습이다. callback과 event loop는 호출 주도권을 이해하는 좋은 예다.

확장점은 단순 함수 이름 외에 언제·몇 번·어떤 스레드·어떤 상태에서 부르는지도 계약해야 한다. 등록을 했다는 사실만으로 초기화가 끝났거나 종료 후 호출이 금지됐다고 추측하지 않는다.

의존성도 밖에서 전달한다

DI는 객체가 필요한 구현을 내부에서 고정 생성하는 대신 밖에서 전달받게 해 의존성 연결의 제어를 이동시키는 기법이다. 생성자 interface 매개변수로 같은 처리기에 실물 저장소 또는 테스트 대역을 연결할 수 있다. DI는 IoC를 실현하는 방식 중 하나다.

container 없이 수동으로 생성자에 객체를 넣어도 DI다. container는 등록·구성·수명을 자동 관리하는 도구다. singleton이 thread-safe를 뜻하지 않으며 요청 수명 객체를 장수 객체에 잘못 보관하면 수명 계약이 깨질 수 있다.

종이 프레임워크를 설계한다

교육 host는 Start→각 입력에 Transform 한 번→출력 기록→Stop 순서로 수행한다고 정한다. plugin의 Transform(x)=2x는 입력을 계산할 뿐 host를 다시 시작하지 않는다. register는 콜백을 저장하고 즉시 실행하지 않는 자체 규칙이다.

테스트 대역 출력기로 호출 목록을 기록하면 제어 흐름을 검토할 수 있다. 그러나 실제 프레임워크 event loop·DI 해제·동시성은 실행하지 않았으므로 그 규칙까지 증명한 것은 아니다.

중간 과정을 따라가는 예제

위 host 입력 [2,4], Transform(x)=2x다. Start/Stop 각 1회, 입력 순서대로 단일 스레드에서 처리한다.

  1. host가 Start를 1회 호출한다.

  2. Transform(2)=4를 기록하고 Transform(4)=8을 기록한다.

  3. Stop 1회 호출한다. Transform 2회, 출력 목록 [4,8]이다.

host가 호출 순서를 주도하며 출력 [4,8], 전체 확장 호출 4회다.

조건을 바꾸어 비교하기

늦게 완료된 작업과 이미 닫힌 출력기

표에서 stop 직후 자원을 해제하는 변형을 적용한다. A는 그 뒤 출력기를 쓰고 B도 아직 대기한다. 정상 drain과 비교하라.

  1. 정상은 A/B의 사용을 마친 뒤 해제한다.

  2. 변형은 active 1과 큐 1이 남은 상태에서 해제하여 뒤 사용의 전제를 깨뜨린다.

  3. 종료 요청 시각과 마지막 사용 시각을 분리한다.

새 입력 거절만으로 남은 작업의 사용이 끝난 것은 아니다.

비교할 점

종료 이벤트 호출 성공을 수명 종료 증거로 오인하는 경우를 다룬다.

주입한 객체 둘의 해제 책임

scope가 R을 만들고 외부 소유자가 E를 만든다. 플러그인이 둘을 주입받았고 작업을 끝냈다. scope 종료 뒤 외부 소유자 종료까지 해제 장부를 적어라.

  1. 플러그인은 빌린 R/E를 해제하지 않는다.

  2. scope 종료에서 R을 한 번 해제하고 E는 그대로다.

  3. 외부 소유자 종료에서 E를 한 번 해제한다.

두 객체 각각 해제 1회이며 책임 주체가 다르다.

비교할 점

주입 여부가 소유권 이전을 자동 결정하지 않는다.

연습 1 · 값과 상태 예측

표에서 A는 성공 출력 4를 만들고 B는 실패하여 출력이 없다. stop 이후 C 입력도 거절한다. 마지막 성공 출력 수·접수 작업 수·해제 횟수를 구하라.

힌트 1

거절 C는 접수 장부에 없다.

힌트 2

B 실패도 active 감소를 동반한다.

풀이와 답 확인

  1. 접수한 작업은 A/B 두 개이며 성공 출력은 A 한 개다.

  2. 둘 다 완료한 뒤 active와 큐가 0이 되어 해제는 한 번이다.

성공 출력은 1개, 접수 작업은 2개, 해제는 1회다.

흔한 오답에서 다시 생각하기

실패 B는 작업이 아니므로 active가 영원히 1로 남는다.

성공 결과와 작업 수명 완료는 다른 장부다.

연습 2 · 오류 찾아 고치기

장수 host가 첫 요청 scope의 출력기 R을 필드에 저장한다. scope는 요청 종료에서 R을 해제했고 다음 요청이 같은 필드를 사용한다. 주입 경계를 고쳐라.

힌트 1

필드 참조가 있다고 객체의 사용 가능 기간이 연장되지는 않는다.

힌트 2

요청 작업 전체가 자기 scope 안에서 끝나도록 설계한다.

풀이와 답 확인

  1. 각 요청의 scope 안에서 출력기를 얻고 모든 해당 작업의 마지막 사용까지 scope를 유지한다.

  2. host에는 이미 해제된 요청 객체 대신 요청 처리 기능이나 scope 생성 역할을 연결한다.

참조가 있는 기간과 계약상 사용 가능한 기간을 맞추고 첫 R의 다음 요청 재사용을 막는다.

흔한 오답에서 다시 생각하기

singleton으로 등록하면 모든 의존 객체도 안전해진다.

장수 객체와 요청 객체의 수명을 맞추지 못하면 동기화와 별도로 문제가 남는다.

연습 3 · 직접 만들어 보기

정상 drain의 Closing 상태에서 작업 완료·새 입력·다음 작업 시작을 처리하는 세 규칙을 작성하라. 각 작업 완료는 정확히 한 번 보고되며 음수 active는 허용하지 않는다.

힌트 1

완료 뒤 큐가 비어도 다른 active가 남을 수 있다.

힌트 2

Closed 전이 조건을 두 장부의 논리곱으로 적는다.

풀이와 답 확인

  1. 완료는 해당 active 작업을 제거하고 수를 줄인다. 새 입력은 거절하여 상태를 보존한다.

  2. 큐의 기존 작업은 시작 가능하며 큐에서 빼고 active를 증가시킨다.

  3. 큐와 active가 모두 0인 경계에서 한 번 해제하고 Closed로 간다.

세 규칙과 마지막 조건으로 작업이 남은 조기 해제 및 중복 해제를 배제한다.

흔한 오답에서 다시 생각하기

큐만 비면 active와 무관하게 닫는다.

실행 중 작업의 마지막 사용이 남을 수 있다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

별도 cancel 정책은 Closing에서 대기 B를 버리되 이미 실행 중 A는 취소 완료 확인 전까지 active로 둔다. A의 취소 요청 후 완료 확인이 아직 없다. B 제거만으로 닫을 수 있는가?

힌트 1

취소 요청과 완료 확인은 다르다.

힌트 2

큐 0과 active 1을 함께 기록한다.

풀이와 답 확인

  1. B를 버리면 큐는 0이다.

  2. A 완료 확인 전 active는 1이므로 해제 조건은 거짓이다.

  3. A 완료 확인 뒤 active 0에서 닫는다.

drain과 다른 정책이지만 어느 쪽도 요청만으로 실행 중 작업을 사라졌다고 보지 않는다.

흔한 오답에서 다시 생각하기

취소 함수 반환이 항상 마지막 사용 종료를 뜻한다.

그 보장은 API와 작업 계약에서 확인해야 하며 이 모형은 명시 완료 사건을 요구한다.

플러그인 변수를 비웠는데 왜 해제 완료를 말할 수 없을까?

플러그인 경계의 검사에는 계약 타입의 정체성과 지원 기능의 교집합이 있다. 자체 host는 정체성 H와 major 1, 필수 기능 {transform,cancel}을 요구한다. manifest는 실제 타입 검사의 대체가 아니며 기능 이름이 있다는 사실만으로 해당 행동이 올바르다고 증명하지 않는다. 별도 로드 문맥은 의존성 충돌을 다루지만 신뢰하지 않는 코드를 같은 프로세스에서 안전하게 실행하는 sandbox가 아니다.

해제 요청과 해제 완료도 나눈다. 자체 참조 그림에서 host의 필드 F와 정적 이벤트의 callback K는 플러그인 객체 P를 강하게 가리킨다. 실행 작업 W에는 플러그인 메서드가 남아 있다. F를 비워도 K와 W가 남는다. 이 그림의 두 외부 강한 참조와 한 실행 위치는 서로 다른 방해 조건이다. 객체별 단순 참조 수로 실제 GC의 완료를 계산한다고 주장하지 않는다.

종료는 새 작업 차단→기존 작업의 종료 확인→callback 등록 해제→host 보관 참조 제거→해제 요청/완료 확인의 계약을 세운다. 실제 .NET collectible 문맥 해제는 협력적이며 외부 강한 참조나 실행 스택이 남으면 완료되지 않을 수 있다. timeout 보고는 종료가 확인되지 않았다는 결과다. 확인되지 않은 작업에 쓰이는 자원을 재사용하면 격리 계획과 별도로 위험이 남는다.

먼저 확인할 개념
  • 공통 계약 정체성

    이름 일치와 실제 공유 타입을 구별하는 앞 본문을 기능 협상까지 확장한다.

  • host 종료와 확장 수명

    확장 콜백의 마지막 사용이 끝나야 참조를 제거할 수 있음을 연결한다.

접속 규격부터 함께 갖는다

plugin은 host가 공개한 작은 계약을 구현하고 자신의 내부 의존성을 숨긴다. 입력·출력·지원 버전·오류·취소·자원 수명까지 경계의 일부다. 모든 host 내부 객체를 전달하면 독립 확장보다 내부 구현에 결합하기 쉬워진다.

공통 interface assembly는 host와 plugin이 같은 정체성으로 공유해야 한다. 이름과 코드가 똑같다는 것만으로 서로 다른 assembly/load context의 타입이 같은 것은 아니다. 계약 DLL을 plugin별로 중복 로드하는 실수를 경계 검사에서 찾는다.

의존성 분리와 보안 분리

별도 AssemblyLoadContext와 resolver는 plugin 의존 라이브러리 충돌을 다루는 수단이다. 이것이 신뢰할 수 없는 코드의 보안 sandbox는 아니다. host와 같은 process에서 실행되는 code는 그 process 권한에 영향을 줄 수 있다.

보안·강한 장애 격리가 필요하면 OS process/가상화와 메시지 계약 등 다른 경계를 검토한다. 별도 process에서도 timeout·데이터 크기·인증·종료 정책은 남는다. DLL을 발견했다고 바로 안전한 plugin으로 승인하지 않는다.

경계 실패를 기록한다

교육 loader의 판정은 공통 계약 정체성 일치와 major 버전 지원 두 조건의 논리곱으로 정한다. 실제 .NET 타입 검사 모든 세부를 재현하는 코드가 아니라 문제를 분리하기 위한 표다.

unload 가능 context여도 다른 곳의 참조·callback·스레드가 남으면 해제가 완료됐다고 할 수 없다. host는 stop→등록 해제→자원 해제 계약을 세우고 실패를 보고해야 한다. 본문은 plugin을 설치하거나 실행하지 않는다.

소단원 10.3

API 버전과 호환성

함수 이름과 매개변수가 그대로면 오래된 사용자는 항상 괜찮을까?

준비 개념과 학습 목표

준비 개념

  • public interface

  • 전제/결과 계약

  • 컴파일과 실행

학습 목표

  • source/binary/behavior 호환성을 구별한다.

  • 확장 변경의 소비자 영향을 찾는다.

  • 호환 시험과 이행 정책을 세운다.

새 라이브러리를 쓰는 오래된 바이너리와 다시 빌드한 소스가 같은 답을 낼까?

같은 소비자를 유지할 때 재컴파일 가능성, 기존 바이너리의 연결 가능성, 반환/예외/효과 계약을 별도로 적는다. 새 타입이나 함수가 추가됐다는 사실만으로 세 층이 모두 유지되지는 않는다. 이 단원은 실제 바이너리 회귀를 수행하지 않고 명시한 호출 규약으로 영향만 추론한다.

자체 C#형 API Fee(int units=2)는 전달된 units의 세 배를 반환한다. v2는 동일 이름·형을 유지하고 기본값만 4로 바꾼다. 일반 정적 C# 호출에서 생략한 선택 인수의 값은 컴파일한 호출자에 반영된다고 정한다. v1으로 컴파일된 Fee() 호출은 새 라이브러리에서도 2를 전달해 6이며 v2로 다시 컴파일하면 4를 전달해 12다. 명시 Fee(2)는 두 경우 모두 6이다. dynamic/다른 언어는 이 사례 범위 밖이다.

별도 변경 N은 매개변수 이름 units를 count로 바꾸되 형과 계산은 유지한다. 기존 named argument 소스 Fee(units:2)는 재컴파일 실패하며 기존 정적 바이너리는 동일 메서드 형과 위치 인수를 유지한 이 제한 조건에서 연결과 값 6을 유지한다. 이름 변경이 모든 연결을 깨뜨리거나 어느 연결에도 영향을 주지 않는다고 일반화하지 않는다.

별도 동작 변경 V는 허용 범위를 0≤units≤10에서 1≤units≤10으로 줄이며 형과 이름은 그대로다. 이전 0의 반환 0이 예외로 바뀌므로 행동 차이가 있다. 신규 명시 API나 정책 버전으로 이행하면 기존 규약을 보존할 수 있지만 버전 번호만으로 회귀 시험을 대신하지 않는다.

먼저 확인할 개념
  • 소스·바이너리·행동의 세 층

    앞 본문의 같은 서명 배송비 변경에서 호출자에 저장된 기본값까지 구별한다.

  • 확장 버전과 지원 선언

    지원 major 선언이 모든 소비자의 관측 의미를 보장하지 않음을 연결한다.

호환성에는 여러 층이 있다

source 호환은 기존 소스가 다시 컴파일되는가, binary 호환은 기존 빌드가 새 라이브러리와 연결·실행되는가를 묻는다. behavior 호환은 호출자가 약속받은 결과·예외·부작용을 계속 관측하는가를 본다. 한 층이 유지돼도 다른 층이 깨질 수 있다.

매개변수 이름 변경은 named argument 소스에 영향이 있고 공개 member 제거·반환 타입 변경은 더 직접적인 경계 변화다. 공개 타입의 레이아웃·직렬화·상속 확장 계약도 소비자가 의존하는지 확인한다.

추가는 언제 안전할까

구현이 필요한 새 abstract member를 확장 가능한 공개 base class에 추가하면 기존 subclass가 구현하지 못한다. interface의 default 구현 같은 기능은 예외가 있지만 모든 언어·runtime·충돌 상황에서 안전하다는 보편 결론은 아니다.

새 overload도 overload resolution을 바꿀 수 있어 단순 추가가 항상 harmless하지 않다. semantic version의 숫자는 변경 정책을 전달하지만 테스트나 호환성 증명 자체가 아니다. 유지보수자가 명시한 정책과 지원 runtime을 확인한다.

행동 계약을 표로 남긴다

자체 API Shipping(total)은 v1에서 total≥20000이면 0, 그보다 작으면 3000원을 반환한다. v2가 서명은 유지하지만 무료 경계를 25000으로 바꾸면 기존 사용자의 일부 결과가 변한다. 배송 규칙의 개정이 의도적일 수 있어도 행동 변화는 숨기지 않는다.

이행 기간에 새 API/정책 매개변수를 두거나 버전별 동작을 제공할 수 있다. 지원 종료·deprecation 안내와 실제 소비자 입력 회귀가 필요하다. 아래는 API 교체나 binary 실행을 하지 않은 계약 비교다.
