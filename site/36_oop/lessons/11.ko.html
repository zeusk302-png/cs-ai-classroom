소단원 11.1

test double

도서 예약 규칙을 검사하려고 매번 실제 알림을 보내야 할까?

준비 개념과 학습 목표

준비 개념

  • 인터페이스와 메서드

  • 입력과 결과 확인

학습 목표

  • 테스트 대상과 협력자를 구별한다

  • double의 역할을 명시한다

  • 상태 검증과 호출 검증의 한계를 설명한다

두 번 읽은 재고가 다르면 고정 stub이 숨기는 오류는 무엇일까?

대역의 이름보다 지금 맡은 역할을 설명하자. 반환을 정하는 stub과 요청을 기록하는 spy를 함께 쓸 수 있지만 기록은 배달 성공과 다르다. 아래는 실제 프레임워크 없이 대상의 명시한 알고리즘과 협력자의 답 목록을 손으로 추적한다. 각 문제는 대역의 읽기 위치와 기록을 새로 시작한다.

자체 대상 R은 양의 요청량 n에 대해 재고를 한 번 읽는다. 읽은 값 v가 n보다 작으면 거절하고 성공 알림을 요청하지 않는다. 충분하면 v−n을 결과 값으로 반환하고 성공 알림을 한 번 요청한다. 대상 자체를 stub으로 바꾸지 않는다. 실제 재고 저장·동시 예약·알림 배달은 구현하지 않은 별도 경계다.

변형 M은 첫 재고를 읽어 버리고 둘째 읽기만 검사한다. 고정 답 5를 매번 주면 R과 M이 같은 업무 결과를 만들 수 있다. 답 순서 [2,5]를 주면 호출 횟수와 선택한 관찰 시점이 드러난다. 이 경우 한 번 읽기라는 자체 계약을 사용하며 모든 업무에서 조회 한 번이 최선이라는 주장은 하지 않는다.

  • 대역과 제공자의 계약

    대역의 재고 답 목록이 어떤 계약을 나타내는지 확인한다.

협력자를 제어한다

테스트 대상 객체가 현재 시각·저장소·알림 서비스에 의존하면 외부 조건 때문에 같은 입력을 반복하기 어렵다. production 협력자를 테스트용 대역으로 바꾸는 것이 test double의 일반적인 역할이다. 대상 객체 자체를 전부 바꾸면 검사하려던 동작도 사라질 수 있다.

이 단원은 Fowler가 소개한 Meszaros 용어를 따른다. dummy는 자리를 채우지만 사용하지 않고 stub은 미리 정한 답을 준다. fake는 실제로 동작하는 단순 구현이지만 메모리 저장소처럼 운영 조건을 모두 갖추지는 않는다.

관찰하는 방식도 다르다

spy는 호출 정보를 기록하여 나중에 횟수나 내용을 확인하게 한다. mock은 기대한 호출을 미리 정하고 검증한다. 도구가 모두 mock이라는 이름을 써도 현재 검사에서 맡은 역할은 따로 설명한다.

결과 상태를 확인하는 것과 어떤 호출이 있었는지 확인하는 것은 다른 질문이다. 예약 성공값과 남은 수량을 보려면 상태 검증이 필요하고 알림 요청이 한 번 전달됐는지 보려면 호출 기록을 볼 수 있다. 기록은 실제 이메일 전달 증거가 아니다.

대역이 현실 전체는 아니다

원본 인터페이스에 맞는 대역을 주입하면 성공·거절 조건을 제어하기 쉽다. 그러나 대역이 잘못된 약속을 하면 실제 협력자와 연결할 때 실패할 수 있다. 다음 소단원의 계약 확인으로 이 경계를 보완한다.

내부 호출을 지나치게 세세하게 기대하면 결과를 보존한 리팩터링도 테스트를 깨뜨릴 수 있다. 업무상 중요한 외부 상호작용과 단순 구현 세부를 구별한다. 실제 알림·서비스·테스트 프레임워크는 여기서 실행하지 않는다.

행마다 대역을 새로 만든다. 읽기 횟수와 결과를 별도 열에서 비교하자. 앞 두 행만 보면 잘못된 둘째 읽기를 발견하지 못하지만 뒤 두 행은 결과까지 갈린다. 성공 알림 수는 대상의 요청 기록이다.

중간 과정을 따라가는 예제

자체 예약 규칙: 재고≥요청량이면 새 재고를 반환하고 성공 알림을 한 번 요청한다. 입력 재고5·요청2, 양의 요청 조건이다. 재고 stub과 알림 spy를 쓴 종이 추적을 하라.

  1. stub이 재고5를 반환하므로5≥2가 참이다.

  2. 대상 규칙이 새 재고5−2=3과 성공을 만든다.

  3. spy에는 성공 알림 호출 한 건을 기록한다. 실제 알림을 보낸 것은 아니다.

성공, 새 재고 3, 알림 요청 기록 1이다. 대상 규칙은 유지하고 외부 협력자만 통제했다.

조건을 바꾸어 비교하기

고정된 답에서 살아남은 변형

표의 고정 5 두 행에서 결과와 알림만 검사한다. 읽기 한 번을 기대하는 mock을 추가하면 무엇이 달라지는가?

  1. 두 대상 모두 성공 결과 2와 알림 요청 1을 만든다.

  2. R은 읽기 1회, M은 읽기 2회이므로 명시한 한 번 읽기 기대는 M에서 실패한다.

  3. 그 기대는 이 문제의 관찰 계약에 근거한다. 결과를 보존한 임의 리팩터링의 모든 내부 호출을 고정하지 않는다.

결과 검사만으로는 둘 다 통과하지만 한 번 읽기 계약 검사는 M을 구별한다.

비교할 점

어떤 호출 기대가 외부 약속이고 어떤 것은 구현 세부인지 먼저 정한다.

실패한 배달과 남아 있는 요청 기록

R의 재고는 5, 요청량은 3이다. 알림 spy는 요청을 먼저 기록하고 미배달 상태를 반환한다. R은 결과 값 2를 반환하며 배달 성공을 추가로 주장하지 않는 계약이다.

  1. 요청 기록은 1개이며 미배달 결과가 따로 있다.

  2. 결과 값 2와 배달 성공은 다른 관찰이다.

  3. spy의 기록 증가를 실제 수신 완료로 바꾸어 보고하면 근거가 없다.

예약 계산은 성공 결과 2, 알림 요청 1개, 배달은 미완료다.

비교할 점

성공 결과가 어떤 범위를 뜻하는지 문제 계약으로 한정한다.

종이와 본문으로 직접 해보기

거절하고 재고 5를 유지하며 성공 알림 기록은 0이다. 이 경우 성공 알림 1회를 잘못 기대한 mock은 실패하므로 기대도 거절 계약에 맞춰야 한다.

오해와 반례

spy 기록1이면 사용자에게 실제 알림이 도착한 사실도 증명된다.

기록은 대상이 요청했다는 증거다. 실제 전송·배달·수신은 외부 연결과 서비스 관측이 추가로 필요하다.

스스로 풀어보기

먼저 답과 이유를 적고, 필요한 만큼 힌트를 한 단계씩 열어 보세요.

연습 1 · 값과 상태 예측

새 순서 stub [2,5]와 요청량 2를 R/M에 각각 독립적으로 준다. 결과 값과 읽기 횟수는?

힌트 1

첫 값 2도 요청량 2 이상이다.

힌트 2

M은 첫 값을 버리고 둘째 값 5를 검사한다.

풀이와 답 확인

  1. R은 첫 2에서 성공 결과 0과 읽기 1회를 얻는다.

  2. M은 둘째 5에서 성공 결과 3과 읽기 2회를 얻는다.

R의 결과는 0이고 M의 결과는 3이다. 둘 다 성공 알림을 1회 요청하지만 같은 결과는 아니다.

흔한 오답에서 다시 생각하기

성공 여부가 같으니 반환값과 호출도 같다.

성공 분류·값·관찰 횟수는 별도 칸이다.

연습 2 · 오류 찾아 고치기

고정 5의 mock에 재고 읽기 정확히 2회를 기대했다. R을 검사하니 실패한다. 한 번 읽기 업무 계약을 유지하면서 검사 기대를 고쳐라.

힌트 1

대상이 계약을 어긴 것인지 기대가 어긴 것인지 구별한다.

힌트 2

재고 조회와 성공 알림의 기대를 각각 적는다.

풀이와 답 확인

  1. 재고 읽기 기대를 1회로 바꾼다.

  2. 요청량 3의 성공 알림은 1회와 결과 값 2를 함께 검사한다.

R을 M으로 바꾸지 않고 잘못된 읽기 기대를 고친다.

흔한 오답에서 다시 생각하기

검사 통과를 위해 R도 불필요하게 두 번 읽게 한다.

시험 기대가 계약과 맞는지 먼저 점검해야 한다.

연습 3 · 직접 만들어 보기

요청량 3의 R에서 부족 경로와 정확히 맞는 경로를 구별하는 두 새 stub 답 및 기대 기록을 설계하라.

힌트 1

부족에는 3보다 작은 값을 준다.

힌트 2

정확 경계는 v=n이며 결과 0을 성공으로 취급한다.

풀이와 답 확인

  1. 답 2이면 거절·읽기 1회·성공 알림 0회다.

  2. 답 3이면 성공 결과 0·읽기 1회·성공 알림 1회다.

서로 다른 두 검사로 거절 보존과 0 결과의 성공을 확인한다.

흔한 오답에서 다시 생각하기

결과 0은 항상 실패다.

성공 여부를 숫자의 참/거짓 변환으로 대신하지 않는다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

대역에 send 호출이 2번 기록되었고 제공자는 같은 ID를 중복 처리하지 않는다고 주장한다. 실제 배달 수가 1이라고 결론낼 수 있는가? 필요한 추가 관찰을 계획하라.

힌트 1

요청 기록과 제공자의 실제 수락/배달을 나눈다.

힌트 2

두 요청의 ID와 중복 상태, 수신 완료 근거를 따로 확인한다.

풀이와 답 확인

  1. 기록만으로 알 수 있는 것은 요청 2회다.

  2. 제공자의 ID 계약 검사와 실제 수락·배달 관측이 추가로 필요하다.

실제 배달 수는 현재 미확인이다. 중복 정책의 선언을 운영 관측으로 바꾸지 않는다.

흔한 오답에서 다시 생각하기

ID 정책이 있으니 실제 전달 1건이 자동 증명된다.

선언·검사·운영 수행은 다른 증거다.

설명 기준 확인

입력과 시점에 따라 달라지는 협력자 행동을 숨길 수 있다. 필요한 관찰 계약을 드러내는 답을 추가한다.

spy와 mock은 무엇으로 구별하는가?

설명 기준 확인

현재 검사에서 기록을 나중에 읽는 역할과 미리 지정한 호출 기대를 검증하는 역할을 명시한다. 도구 이름만으로 결정하지 않는다.

한 단계 더

동일한 성공 결과를 유지하면서 재고 조회를 두 번에서 한 번으로 바꿨다고 생각하라. 조회2회 기대는 깨질 수 있지만 업무 결과가 틀렸다는 결론은 별도다. 필요한 호출 계약인지 구현 세부인지 먼저 판단하고 실제 테스트 실행 여부는 따로 기록하라.

대역에서는 성공하지만 진짜 서비스에서만 깨진다면 무엇을 확인할까?

준비 개념과 학습 목표

준비 개념

학습 목표

  • 형식·필수필드·상태 의미를 검사한다

  • 계약 검사와 전체 서비스 검증을 분리한다

필드가 모두 있어도 서로 모순되는 응답은 계약을 지켰을까?

필드별 검사에 더해 관계를 적어야 한다. 자체 상태 응답은 정수 available와 reserved가 모두 음이 아니고, 정수 capacity도 음이 아니며 available+reserved≤capacity를 만족해야 한다. 문자열 unit은 정확히 seat다. 이 문제는 추가 필드를 허용하고 필수 네 필드는 누락할 수 없다. bool은 정수로 인정하지 않는다.

통과는 이 접점의 형식·단위·관계에 대한 판정이다. 제공자가 실제 좌석을 과다 예약하지 않았는지, 응답이 최신인지, 인증이나 지연 요구를 지켰는지는 따로 검사한다. 대역과 제공자 둘 다 같은 잘못된 검사를 쓰면 일치만으로 오류를 발견할 수 없다.

별도 시간 계약에서 v1 필드 delayMs는 음이 아닌 정수 밀리초다. v2가 같은 필드 이름에 초 단위 값을 넣으면 타입은 유지해도 단위 계약은 달라진다. 소비자가 받는 값 2를 밀리초로 읽을 때 제공자가 의도한 2초와 1000배 차이가 난다. 버전별 어댑터와 의미 검사로 경계를 명시한다.

먼저 확인할 개념
  • 필수·타입·범위 계약

    앞 본문의 amount/currency를 여러 필드의 관계 검사로 확장한다.

  • 제어된 대역의 한계

    대역과 제공자 둘의 같은 실수 및 독립 기대의 필요성을 확인한다.

접점의 약속을 적는다

외부 서비스 호출에는 경로·입력·응답 필드·타입·실패 상태 같은 약속이 있다. 소비자가 필요로 하는 계약을 명시하고 double가 그 약속을 표현하는지 확인한다. 같은 메서드 이름이라는 사실만으로 호환성을 증명할 수 없다.

계약테스트는 이런 접점을 별도로 확인한다. 로컬 대상 테스트가 대역으로 빠르게 동작해도 제공자가 응답을 바꾸면 대역과 현실이 어긋날 수 있다. 변경 주기와 테스트 환경을 정해 계약을 재확인한다.

고정값과 의미를 구별한다

가격이 날짜마다 바뀌는 서비스라면 특정 숫자가 계속 같은지보다 숫자형과 통화·단위·누락 여부가 계약일 수 있다. 반대로 고정 테스트 시나리오에서 수량 거절 상태는 정확히 비교할 필요가 있다. 검사의 기준을 먼저 적는다.

여기서는 자체 응답 계약을 가정한다. 필수 필드 amount는 음이 아닌 정수의 원 단위이고 currency는 문자열 KRW이며 추가 필드는 허용한다. 실제 외부 API 규격을 발견했다고 주장하지 않는다. 부동소수 가격·다른 통화·문자열 숫자는 현재 계약 밖이다.

실패를 새 근거로 처리한다

제공자의 응답과 double가 다르면 대역만 맞춰 버리기 전에 소비자 요구와 제공자 변경을 확인한다. 소비자가 잘못 기대했는지, 제공자가 약속을 깨뜨렸는지, version을 함께 올려야 하는지 판단한다.

계약 검사 통과는 처리 지연·장애 복구·인증·실제 전체 사용자 흐름의 성공까지 증명하지 않는다. 공개 운영 서비스에 테스트 요청을 임의로 보내는 대신 합의한 테스트 instance를 사용한다. 이 단원은 요청을 실제로 보내지 않는다.

A/B는 각 숫자만 보면 모두 음이 아니다. 마지막 관계 열을 빼면 B 오류가 숨는다. D는 누락 필드를 0으로 채워 관계를 계산하는 대신 필수 조건에서 실패한다. 각 응답은 독립된 가상 기록이다.

중간 과정을 따라가는 예제

자체 계약에 대해 A={amount:1200,currency:"KRW"}, B={amount:"1200",currency:"KRW"}, C={amount:1300,currency:"KRW",note:"new"}, D={amount:1200}를 검사하라. 숫자는 정수 값이고 추가 필드를 허용한다.

  1. A는 필수 두 필드와 타입·범위를 만족한다. B의 amount는 문자열이므로 실패다.

  2. C의 amount1300은 허용 범위이며 추가note를 허용하므로 통과한다. 가격1200 고정 계약은 아니다.

  3. D는 currency가 없어 실패한다.

통과는 A/C 두 개, 실패는 B/D 두 개다. 특정 실제 서비스 검사 결과가 아닌 표 판정이다.

조건을 바꾸어 비교하기

공통 필드 검사로 숨은 초과

대역과 제공자가 모두 B를 반환하고 양쪽 검사는 숫자형·음이 아님만 확인한다. 동일 응답이면 계약 성공인지 판단하라.

  1. 두 응답의 일치는 사실이지만 합은 3+3=6이다.

  2. capacity 5를 넘으므로 명시 계약 실패다.

  3. 검사도 같은 관계 조건을 빠뜨렸으므로 독립 기대를 보완한다.

양쪽 일치와 무관하게 B는 관계 실패다.

비교할 점

동일 결함을 가진 두 구현을 서로의 유일 oracle로 삼지 않는다.

숫자 2의 단위를 바꾼 제공자

v1 소비자는 delayMs=2를 받았다. 제공자가 새로 2초를 의미한다고 문서화했다. 변환 없이 기존 소비자가 판단한 시간과 변환 뒤 시간을 비교하라.

  1. 변환 없는 소비자의 해석은 2ms다.

  2. 제공자의 2초는 2000ms이므로 1000배 차이다.

  3. 버전과 단위를 확인한 어댑터에서 1000을 곱하며 기존 필드 의미를 조용히 바꾸지 않는다.

2ms 대 2000ms이며 타입 일치만으로 호환하지 않는다.

준비 개념과 학습 목표

준비 개념

  • 매개변수와 반환값

  • 객체의 외부 상태

학습 목표

  • 순수 함수의 두 조건을 설명한다

  • 판단값과 외부 실행을 나눈다

  • 순수성만으로 업무정확성을 증명하지 않음을 설명한다

계획이 같은데 재시도 후 외부 효과가 두 번 나타날 수 있을까?

순수 핵심은 명시 입력을 받아 결과 값과 작업 계획을 만든다. 별도 외부층이 그 계획을 실행한다. 자체 plan(price,day,id)는 앞 본문의 할인 규칙으로 total을 정하고 [Save(id,total),Notify(id,total)]를 반환한다. 입력 price는 정수 0..10000, day는 정수이며 id는 고정된 문자열이다. 입력 객체는 변경하지 않는다.

외부층은 Save 뒤 Notify를 순서대로 요청한다. 아래 손모형에서 Save는 매 요청을 기록하고 Notify도 요청/완료를 구별한다. 첫 실행은 Save 성공 후 Notify 실패다. 핵심을 다시 호출하면 같은 입력이므로 같은 계획을 얻지만 이미 성공한 Save가 자동 취소되지는 않는다. 이 단원에서 실제 저장소나 알림은 호출하지 않는다.

계획만 만드는 함수의 순수성과 계획을 해석하는 외부층의 실패·중복 계약은 독립이다. 임의 내부 지역 합계 변경은 외부에서 보이는 입력/상태를 바꾸지 않는 조건에서 순수성을 깨지 않는다. 반대로 숨은 시계를 읽거나 입력 객체의 필드를 바꾸면 명시 입력만의 계산이라는 약속을 어긴다.

결정에 필요한 값을 받는다

순수핵심은 같은 입력에 같은 결과를 내고 외부 상태를 바꾸지 않는 계산이다. 시계읽기·파일쓰기·네트워크전송은 외부와 연결되는 작업이다. 외부층에서 필요한 값을 읽어 핵심에 전달하면 결정 규칙을 독립적으로 추적할 수 있다.

OOP 언어에서도 계산 메서드를 이렇게 구성할 수 있다. 객체를 사용한다는 사실과 외부효과를 섞는 것은 같은 선택이 아니다. 입력 객체 자체를 변경하면 호출자에게 효과가 드러날 수 있으므로 새 값 반환과 기존 참조 수정도 구별한다.

계획은 실행 결과가 아니다

핵심은 저장/알림해야 할 계획을 값으로 반환하고 외부층이 실제 실행할 수 있다. 계획 반환은 이메일 전달이나 DB commit 성공 증거가 아니다. 외부층의실패·재시도·중복 실행을 별도로 확인한다.

교육 할인은 정수 원 금액0–10000와명시시각 정수day를 쓴다. day≤30이면discount100,그뒤0이며 total=max(0,price−discount)다. 실제 세금·결제·시간대 정책은 현재 모형에 포함하지 않는다.

검사를 쉬워져도 규칙은 검증한다

시간을 매개변수로 주면 실제 날짜가 변해도 day30/31 경계를 반복할 수 있다. 출력값을 계산한 기대와 비교하고 입력이 보존됐는지 확인한다. 외부층은 저장·알림연결 같은 적은접점을 통합검사할 수 있다.

순수하다는 성질만으로 할인식이 업무요구와맞는 것은아니다. 항상0을반환하는함수도외부효과가없을수있지만 요구는어긴다. 입력범위·경계·실패 처리와 실제외부결과를나누어 검토한다.

  1. R은 첫 재고 2로 거절하며 재고를 1회 읽고 성공 알림은 요청하지 않는다. M은 둘째 재고 5에서 성공 결과 2를 반환하며 재고를 2회 읽고 성공 알림을 1회 요청한다.

  2. 응답의 합은 6으로 capacity 5를 초과하므로 대역과 같아도 계약 실패다. 필수·타입·범위·단위 이후 관계 검사를 추가한다.

  3. 순수 핵심의 total은 150이다. 전체 계획을 재실행하면 최종 저장 요청은 2회, 알림 요청은 2회, 알림 완료는 1회다.

  4. 완료 장부를 쓰면 최종 저장 요청은 1회, 알림 요청은 2회, 알림 완료는 1회다. 이 비교는 명시한 순차 실행과 신뢰된 기록의 모형이며 실제 장애 복구 증거는 아니다.

R은 거절하고 M은 성공 결과 2를 반환한다. 두 응답이 같아도 합 관계의 실패를 공유할 수 있다. 동일한 total 150에서도 전체 재실행의 저장 요청은 2회이고 완료 장부를 이용한 재시도의 저장 요청은 1회다. 두 정책 모두 알림 요청은 2회이고 완료는 1회다.

해결한 뒤 점검할 것

  • 대역 반환과 대상 규칙을 따로 추적하고 호출 기록을 배달로 보고하지 않는다.

  • 필드별 통과와 합 관계 실패 및 독립 기대를 설명한다.

  • 순수 결과와 저장/알림 요청·완료 장부를 분리하여 두 재시도 정책을 계산한다.

  • 실제 서비스/장애/학생 미수행과 모형 조건을 보존한다.
