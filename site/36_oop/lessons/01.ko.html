소단원 1.1

요구와 변경점

대출 화면에 ‘승인’이라고 나오면 저장 실패 뒤에도 대출이 완료된 것일까?

준비 개념과 학습 목표

준비 개념

  • 상태는 현재 값들의 묶음이다. 회원등록 여부와 대출기록은 지금의 상태, 대출요청은 이를 바꾸려는 사건이다.

  • 클래스는 비슷한 객체의 구조/연산을 정의한다. 메서드는 그 객체에 요청하는 연산이다. 아직 문법을 몰라도 카드에 요청과 응답을 적을 수 있다.

  • 조건 A AND B는 두 조건 모두 참일 때 참이다. 대출이 가능한 이유를 여러 조건으로 나누어 보자.

학습 목표

  • 사용자 요구를 관찰 가능한 성공/실패 계약으로 바꾼다.

  • 정책 변경과 저장 구현 변경을 분리한다.

  • 불명확한 요구에 필요한 질문과 조건을 도출한다.

한도를 낮췄다는 이유로 이미 빌린 책이 자동 반납되는가?

문 앞에 붙은 이용 규칙을 바꾸는 일과 이미 작성한 대출 장부를 바꾸는 일은 서로 다른 사건이다. 앞 본문의 count < L은 새 요청을 승인할 때 적용한 조건이다. 이 보강에서는 기존 대출을 유지하며 새 요청부터 현재 한도를 적용하는 자체 정책을 추가한다. 한도 변경 자체는 대출 기록을 삭제하지 않는다.

예를 들어 한도 4에서 기록이 3개인 회원에게 한도를 2로 낮추면 기존 기록은 여전히 3개다. 새 요청은 3 < 2가 거짓이므로 거절된다. count ≤ 현재 L을 모든 시점의 불변식이라고 새로 주장하면 이미 있는 기록을 처리할 별도 이행 규칙이 필요하다. 새 요청의 사후조건과 정책 변경 뒤 전체 상태 조건을 섞지 않는다.

책 제목은 상품명에, 사본 ID는 실제 물건의 꼬리표에 가깝다. 같은 제목의 사본 X와 Y가 있어도 X의 대출은 Y의 대출 여부를 결정하지 않는다. 제목을 키로 삼은 저장은 어떤 물건이 나갔는지 잃으며, 이는 단순한 내부 자료구조 변경과 다르다.

모든 사례는 등록 회원, 유효한 사본, 순차 메모리 요청과 유효한 초기 기록을 전제한다. 거절 이유는 앞 본문과 같이 INVALID, BUSY, LIMIT 순서다. 정상 대출 성공과 한도 변경을 별도 연산으로 정의하여 어떤 상태가 바뀌는지 관찰한다. 실제 도서관 정책이나 저장소를 구현하는 활동은 아니다.

먼저 확인할 개념
  • 신규 요청의 조건과 실패 보존

    현재 count와 한도의 비교가 신규 승인 조건이라는 점을 사용한다.

  • 사본 정체성과 기준 기록

    제목과 사본의 구별 및 count를 기록에서 얻는 책임을 사용한다.

목표를 검증 가능한 결과로 쓰기

요구는 사용자가 어떤 상황에서 어떤 결과를 필요로 하는지 정하는 것이다. ‘대출을 편리하게’만으로는 승인·거절의 경계가 정해지지 않는다. 여기서는 등록 회원이 사용 가능한 실물 사본 한 개를 빌리는 작은 시스템을 설계한다. 책 제목(Book)과 실물 사본(Copy)을 구별한다. 같은 제목 두 사본을 각각 빌릴 수 있으므로 제목만으로 대출 상태를 저장하면 정보를 잃는다.

정책을 고정하자. 등록 회원이어야 하고 해당 사본은 미대출이어야 하며 회원의 현재 활성 대출 수 count가 한도 L 미만이어야 한다. L은 양수 정수이고 기본3이다. 성공하면 그 회원-사본의 활성 대출 기록을 정확히 하나 추가한다. 거절하면 모든 대출 상태를 유지한다.

오류와 경계를 명세에 포함하기

회원 없음/사본 없음, 이미 대출 중, 한도 도달을 구별한 결과를 반환한다. 여러 거절 이유가 동시에 있으면 이 예에서는 INVALID→BUSY→LIMIT 순서로 우선한다. 이 순서는 보편적인 도서관 규칙이 아니라 자체 인터페이스 계약이다. 오류 우선순위를 정하지 않으면 동일 입력에서 서로 다른 메시지를 내는 구현을 평가하기 어렵다.

count는 활성 기록 중 해당 회원의 기록 수로 정의한다. 사본당 활성 기록은 최대 하나라는 불변식이 있다. 여기서는 요청을 하나씩 처리하는 메모리 모델이고 운영 중 저장 장애·인증·개인정보·벌금·예약은 제외한다. 실제 시스템으로 확장할 때 제외한 실패 경로를 별도 계약으로 추가해야 한다.

어떤 변화가 어느 약속에 영향을 주는가

한도3→5는 정책 변경이다. 배열로 저장하던 기록을 다른 저장 구조로 옮기는 것은 구현 변경이다. 후자는 같은 조회와 갱신 의미를 제공한다면 클라이언트의 대출 판단을 유지할 수 있다. 반면 정책 변경은 어떤 요청이 승인되는지 바꾸므로 행동이 완전히 동일한 리팩터링이라고 부르면 안 된다.

변경을 예상한다는 말은 모든 가능성을 위한 클래스를 미리 만든다는 뜻이 아니다. 실제로 알려진 변화인 한도 L과 저장방식을 경계 뒤로 모으고, 그 경계의 성공/실패 결과를 시험할 수 있게 한다. 결과 조건과 구현 절차를 구분하면 자료구조를 바꿀 자유가 생긴다.

첫 행은 독립 비교다. 둘째 행부터는 같은 기록 3개 상태를 이어간다. 두 숫자는 각각 기록 수와 현재 한도이며 한도를 기록 수에서 빼는 계산이 아니다. 둘째 행의 3 > 2는 기존 기록을 유지한다는 정책에서 허용되지만 신규 요청을 허용한다는 뜻은 아니다.

중간 과정을 따라가는 예제

등록 회원 U는 활성 기록2개를 갖고 새 사본 X는 존재하며 미대출이다. L=3. 다음에는 다른 미대출 사본 Y도 요청한다.

  1. U/X 유효, X미대출 확인.

  2. 2<3이므로 X요청 승인. (U,X) 하나 추가되어 count=3.

  3. Y요청에서 유효성과 미대출은 참이나3<3은 거짓.

  4. LIMIT를 반환하고 count3 및 기존 기록을 보존.

X성공, Y거절이다. 한도는 count≤L이 아니라 새 요청 시 count<L로 검사한다.

조건을 바꾸어 비교하기

현재 한도와 기존 대출의 수명을 분리한다

U의 기록은 A, B, C 세 개이며 한도는 4다. 한도를 2로 낮추고 새 X를 요청한 뒤, 한도를 5로 높이고 같은 미대출 X를 다시 요청한다. 기존 기록 유지 정책을 쓴다.

  1. 한도 변경 뒤 A, B, C는 삭제되지 않아 count는 3이다.

  2. 첫 X 요청은 유효하고 미대출이지만 3 < 2가 거짓이므로 LIMIT다. X는 계속 미대출이다.

  3. 한도 5로 변경 뒤 3 < 5이므로 두 번째 X 요청은 OK이고 count는 4다.

응답은 LIMIT 뒤 OK이며 기록 수는 3, 3, 4로 변한다. 낮춘 한도만으로 자동 반납을 추가하지 않는다.

비교할 점

고정 한도에서 count를 증가시키는 예제와 달리 정책 사건이 어떤 상태를 바꾸는지 명시한다.

제목 하나에 사본 두 개가 있다

제목 T의 사본 X는 U에게 대출 중이고 Y는 미대출이다. V는 활성 기록 0개, 한도 2인 등록 회원이다. V가 X와 Y를 순서대로 요청한다.

  1. X는 유효하지만 이미 대출 중이므로 BUSY다. V의 기록은 0개로 유지된다.

  2. Y는 X와 다른 사본이므로 미대출 조건이 참이고 0 < 2다.

  3. (V,Y)를 추가하면 V의 count는 1이며 T의 대출 중인 사본은 두 개가 된다.

X 요청은 BUSY, Y 요청은 OK다. 제목 T를 대출 중이라는 하나의 boolean으로 표현하면 Y를 잘못 거절한다.

비교할 점

명사에서 클래스를 찾는 일을 넘어 두 사본을 구별하는 정보가 계약에 필요한 이유를 확인한다.

오해와 반례

요구는 화면 문구를 정하는 일이고 설계는 클래스 이름을 고르면 끝난다.

화면이 성공을 보여도 기록이 없다면 성공 효과를 만족하지 못한다. 이름보다 입력·결과·상태 보존·제외 조건을 먼저 명시해야 실패도 검토할 수 있다.

연습 1 · 값과 상태 예측

각 요청은 독립 상태다. U의 count는 3이고 한도를 4에서 2로 낮췄다. 미대출 X 요청과 이미 대출 중 Y 요청의 결과, 기록 수를 예측하라.

힌트 1

현재 한도는 2이며 기존 기록은 지우지 않는다.

힌트 2

BUSY가 LIMIT보다 먼저다.

풀이와 답 확인

  1. X는 3 < 2가 거짓이므로 LIMIT다.

  2. Y는 이미 대출 중이므로 BUSY다. 두 거절에서 count는 3이다.

X는 LIMIT, Y는 BUSY이며 각각 기록 3개를 보존한다.

흔한 오답에서 다시 생각하기

count가 한도보다 크므로 두 요청은 INVALID다.

INVALID는 회원/사본 유효성의 결과다. 한도와 대출 여부는 별도 거절 조건이며 자체 우선순위를 적용한다.

연습 2 · 오류 찾아 고치기

새 한도 설정 함수가 L을 2로 바꾼 뒤 count ≤ L을 맞추려고 임의 기록 한 개를 삭제한다. 원래 기록은 3개다. 기존 기록 유지 정책과의 충돌을 고쳐라.

힌트 1

한도 설정의 허용 효과부터 적는다.

힌트 2

어느 회원-사본을 반납할지 요구에 있는가?

풀이와 답 확인

  1. 설정은 한도만 바꾸고 기존 기록을 보존해야 한다.

  2. 임의 삭제는 count를 2로 만들지만 요청되지 않은 반납 효과를 만든다. 삭제를 제거하고 신규 요청에서 현재 한도를 검사한다.

한도는 2, 기록은 3개로 유지한다. 실제 반납이 필요하다면 별도 입력과 결과 계약을 추가해야 한다.

흔한 오답에서 다시 생각하기

최종 숫자가 한도와 같으면 올바른 요구 구현이다.

수치 조건 하나를 맞추어도 기존 사본의 대출 사실을 임의로 지우면 금지된 효과를 만든다.

연습 3 · 직접 만들어 보기

같은 제목 T의 사본 X/Y를 구별하지 못하는 저장을 잡을 최소 시험을 설계하라. 회원 U/V는 유효하고 한도는 충분하다.

힌트 1

하나의 사본만 먼저 빌린다.

힌트 2

다른 회원이 같은 제목의 다른 사본을 요청한다.

풀이와 답 확인

  1. 빈 기록에서 U가 X를 빌려 OK를 기대한다.

  2. V가 Y를 빌려 OK를 기대하고 최종 기록 (U,X), (V,Y)를 확인한다.

  3. V가 X를 별도 요청하면 BUSY이며 두 기록 보존도 확인한다.

다른 사본의 두 성공과 같은 사본의 거절을 함께 검사한다. 제목만 저장하면 두 번째 성공을 설명하지 못한다.

준비 개념과 학습 목표

준비 개념

  • 객체는 상태와 그 상태를 다루는 연산을 가진 실행 대상이다. 같은 Member 클래스의 U와 V는 서로 다른 회원 객체일 수 있다.

  • 책임은 맡아서 알고 있거나 수행해야 하는 일이다. count를 안다는 것과 대출을 승인하고 기록한다는 일을 구별하자.

  • 참조는 다른 객체에 요청할 수 있도록 대상을 가리키는 관계다. 이 과목에서는 종이에 객체 카드 사이 화살표로 표현한다.

학습 목표

  • 객체·역할·책임과 클래스의 차이를 설명한다.

  • 책임을 정보와 불변식에 맞게 배분한다.

  • 중복 상태와 책임 집중의 비용을 반례로 찾는다.

같은 대출 정보를 두 색인에 넣으면 누구의 책임이 늘어나는가?

주소록에 사람별 전화번호와 전화번호별 사람 목록을 함께 두면 읽기는 편하지만 둘의 내용이 맞아야 한다. 대출 장부도 회원별 기록 M과 사본별 빌린 사람 C를 함께 두는 자체 대안을 생각하자. 이는 같은 사실의 두 표현이며 서로 다른 사실을 마음대로 저장하는 두 권한이 아니다.

불변식은 M에 회원 U의 사본 X가 있으면 C[X]도 U이고 그 역도 성립한다는 것이다. 각 사본은 한 회원에게만 속하며 모든 ID는 유효하다. count는 M[U]의 항목 수다. 한쪽에만 추가한 상태는 count 숫자가 그럴듯해도 허용되지 않는다.

새 LoanLedger 역할은 두 색인을 함께 변경하는 책임을 가진다. MemberDirectory와 CopyCatalog는 존재 정보를, Policy는 한도를 제공한다. 화면이 두 색인에 직접 쓰면 단일 기준 역할의 계약 밖에서 모순을 만들 수 있다. 역할은 파일이나 클래스 수가 아니라 어떤 변경이 같은 경계 안에 있어야 하는지로 설명한다.

배열의 순서를 바꾸거나 회원별 목록을 집합으로 바꾸어도 같은 활성 회원-사본 관계를 나타낼 수 있다. 허용 표현을 관계로 읽는 설명과 두 색인이 일치한다는 조건이 함께 필요하다. private 필드 선언만으로 누락된 갱신이나 내부 가변 목록 노출이 해결되지는 않는다.

객체의 정체성과 역할을 구별하기

객체는 실행 중 정체성·상태·행동을 가진 대상이다. 역할은 특정 협력에서 수행하는 의무다. LoanLedger는 활성 대출을 관리하는 역할 이름이며 현재 메모리 구현이나 나중의 저장소 구현이 그 역할을 맡을 수 있다. 역할이 항상 클래스 하나와 일대일이어야 한다는 규칙은 없다.

도메인에서 명사를 찾는 일은 후보를 발견하는 출발점이다. 날짜·한도처럼 단순 값이면 충분한 대상에 무조건 독립 클래스를 만들 필요는 없다. 반대로 승인 정책·대출기록 관리처럼 동작 중심 책임은 눈에 띄는 실물 명사가 없어도 필요할 수 있다.

누가 무엇을 알고 무엇을 바꾸는가

이 설계에서는 MemberDirectory가 회원 존재를, CopyCatalog가 사본 존재를 제공한다. LoanLedger는 활성 회원-사본 기록과 사본당 하나의 대출 불변식을 관리한다. count(member)는 Ledger에서 기록 수를 계산한다. LoanPolicy는 한도 L에 따른 승인 조건을 제공하고 LoanService는 한 요청의 협력을 조직한다. 이름은 자체 예제의 설계 선택이며 유일한 정답이 아니다.

책임 배분의 근거는 필요한 정보와 일관성을 관리할 경계다. 모든 객체가 서로의 내부 배열을 직접 고치면 검증이 여러 곳으로 흩어진다. 연산을 통해 질문/변경을 요청하도록 하면 저장 표현을 바꿀 여지가 생긴다. 정보 가까이에 계산을 두는 원칙도 불변식·변경·보안 경계를 무시할 만능 규칙은 아니다.

중복 상태보다 한 기준을 먼저 세우기

Member.count와 Copy.borrower와 Ledger.records를 각각 따로 저장하면 셋을 함께 갱신해야 한다. 하나만 바뀌면 count2인데 기록3개인 모순이 생긴다. 첫 예제에서는 Ledger의 기록을 기준 사실로 두고 count/대출중 여부를 거기서 구해 중복 불변식을 줄인다. 이것이 모든 실제 서비스의 캐시나 인덱스를 금지하는 뜻은 아니다.

거짓: 회원이 불일치

각 행은 독립 표현 비교이며 위에서 아래로 모두 실행하는 연산 절차가 아니다. 두 화살표는 같은 활성 대출 관계를 반대 방향에서 조회하는 색인이다. 개수 비교만으로는 마지막 행의 회원 불일치를 찾지 못하므로 정확한 ID 쌍을 대조한다.

같은 항목 수라도 내용은 불일치한다

M은 U → {A,X}, V → {}이고 C는 A → U, X → V다. 두 색인 항목 수는 모두 2다. 이를 유효 장부라고 판정해도 되는가?

  1. M의 (U,A)는 C의 A → U와 맞는다.

  2. M의 (U,X)는 C의 X → V와 맞지 않고 C의 (V,X)는 M에 없다.

  3. 총수 2라는 조건은 대응 회원이 같다는 조건보다 약하다.

유효하지 않다. X의 소유 회원을 기준 사실에 맞춰 함께 교정할 계약이 필요하며 총수만으로 어느 쪽이 사실인지 결정하지 않는다.

소단원 1.3

협력의 설계

각 객체가 제 일을 잘해도 승인 뒤 기록과 알림의 순서가 틀리면 어떤 일이 생길까?

준비 개념과 학습 목표

준비 개념

  • 협력은 여러 대상이 요청과 응답을 주고받아 한 목표를 달성하는 과정이다. 질문만 하는 호출과 상태를 바꾸는 호출을 다른 색으로 표시해 보자.

  • 순서는 결과에 영향을 준다. 기록하기 전 성공 알림을 보내는 것과 기록 성공 뒤 보내는 것은 실패 때 결과가 다르다.

  • 불변식은 허용한 경계에서 항상 유지해야 할 조건이다. 사본 하나에 활성 대출이 최대 하나라는 조건을 예로 든다.

학습 목표

  • 정상/거절 메시지 경로를 설계한다.

  • 한 연산의 성공효과를 일관된 상태 전이로 확인한다.

  • 동시성·저장·알림 실패의 추가 조건을 구분한다.

알림이 실패했는데 대출을 다시 만들면 무엇이 두 번 일어나는가?

택배 접수 장부와 문자 발송은 서로 다른 결과다. 문자 실패가 접수 자체의 실패라는 뜻은 아니다. 앞 본문의 대출 협력을 확장하여 요청 ID r의 결과 J[r]와 아직 전달하지 않은 알림 항목 N[r]을 같이 기록하는 자체 종이 모델을 만든다.

유효한 새 요청에서 Ledger는 현재 BUSY/LIMIT를 검사한다. OK일 때 대출 기록, 요청 입력과 결과, 대기 알림을 하나의 상태 묶음으로 공개한다. 거절은 대출과 알림을 만들지 않고 해당 요청의 거절 결과만 기록한다. 이 모형은 공개 전 준비 실패라면 전체 묶음을 보존한다는 계약을 전제하며 실제 DB 구현을 주장하지 않는다.

같은 r와 같은 입력이 다시 오면 먼저 J를 확인하여 저장된 결과를 돌려주고 새로운 대출이나 알림을 만들지 않는다. 같은 r인데 회원 또는 사본이 다르면 CONFLICT다. 이 예는 요청 결과를 무기한 보존하며 사본/회원 카탈로그가 바뀌지 않는 순차 모델이다. 저장한 거절 결과도 재사용하므로 이후 한도가 늘어도 같은 ID의 결과는 바뀌지 않는다.

전달자는 N의 항목을 보고 알림을 보낸 뒤 성공을 확인한 경우에만 그 대기 항목을 제거한다. 보내고 제거하기 전에 중단하면 다음 시도에 같은 알림을 보낼 수 있다. 대출의 중복 방지와 알림의 정확히 한 번 전달은 다른 계약이다. 받는 쪽의 ID 중복 처리까지 없으면 알림 한 번을 보장하지 않는다.

먼저 확인할 개념
  • 기록 성공과 알림 효과

    대출의 상태 효과와 외부 전달 결과가 다르다는 경계를 사용한다.

  • 실패 보존과 오류 우선순위

    새 요청의 거절과 재사용되는 과거 결과를 구별한다.

요청에서 결과까지 메시지로 설명하기

LoanService는 요청(memberId,copyId)을 받고 Directory/Catalog에 존재를 질문한다. 유효하지 않으면 INVALID로 끝낸다. 유효한 경우 Ledger의 대출 여부/회원 count와 Policy의 한도를 사용한다. BUSY와 LIMIT 경로는 기록을 바꾸지 않는다. 이 질문들은 저장표현을 노출하지 않는 인터페이스 계약이다.

성공 경로의 핵심은 상태 변경이다. 메모리 순차 모델에서는 모든 조건을 확인하고 활성 기록 하나를 추가한 뒤 OK를 반환한다. 아래 createIfAllowed는 존재 확인을 끝낸 유효 ID와 한도 L을 받아 Ledger의 현재 사본 상태/count를 확인하고 거절 또는 추가를 한 연산으로 수행한다고 명세한다. 앞의 조회만 믿어 무조건 추가하는 연산과 구별한다.

협력의 경계에서 불변식을 지키기

createIfAllowed의 성공 효과는 기록 하나 추가, 거절 효과는 상태 불변이다. 사본이 미대출이어야 추가하므로 사본당 기록 최대 하나를 유지한다. count<L에서 하나 추가하므로 새 count≤L이다. 이것은 정해진 순차 메모리 모델의 논리이며 실제 DB 트랜잭션을 구현했다는 주장이 아니다.

두 요청이 동시에 count2를 읽고 각각 추가하면 한도3인데 count4가 될 수 있다. 따라서 실제 동시 서비스에서는 조건 검사와 기록 추가를 함께 보호하는 경계가 필요하다. 이 예의 한 메서드 호출이 있다는 사실만으로 자동 원자성/내구성/동시 안전성이 보장되지 않는다. 잠금·트랜잭션 등 구현과 실패 계약을 따로 검증한다.

알림은 기록의 결과와 다른 효과다

성공 알림은 기록 성공을 확인한 다음 실행하는 것이 이해하기 쉽다. 알림 실패를 대출 실패와 같은 결과로 응답하면 사용자가 재요청하여 중복을 만들 수 있다. 확장 예에서는 대출 성공과 알림 전달 상태를 구분한다. 여기 본문의 기본 모델에는 알림/재시도가 없으며 이 논의는 경계를 늘릴 때 필요한 조건이다.

협력 그림은 정상 화살표만 그리면 부족하다. 거절에서는 어떤 호출을 생략하고 어떤 상태가 유지되는지, 성공에서 어느 시점에 결과를 확정하는지 적어야 한다. 테스트 대역으로 알림 오류를 넣어도 저장소의 실제 장애 복구를 증명한 것은 아니므로 검사 범위를 기록한다.

U의 count는 3, 한도는 3, X는 미대출이다. 새 r=(U,X)를 요청해 LIMIT를 기록한다. 한도를 5로 바꾼 뒤 같은 r와 같은 입력을 재시도하고, 새 s=(U,X)를 요청한다.

  1. 첫 r는 LIMIT이며 대출 count는 3, 알림은 없고 J[r]에 LIMIT를 저장한다.

  2. 같은 r는 먼저 저장 결과를 읽어 LIMIT다. 한도 변경을 근거로 재계산하지 않는다.

  3. 새 s는 현재 3 < 5를 검사해 OK이고 count는 4, J[s]는 OK, N[s]는 대기다.

같은 ID는 LIMIT를 재사용하고 새 ID는 OK를 얻는다. 같은 r로 X 대신 Y를 요청하면 CONFLICT다.

대출은 한 번인데 알림은 두 번일 수 있다

새 r의 성공 묶음 공개가 끝났다. 전달자가 알림을 보내 수신자가 관찰했지만 N[r] 제거 전에 중단했다. 재개 뒤 N[r]을 다시 보낸다.

  1. 대출과 J[r]는 처음 성공 공개 때 한 번 생겼다.
