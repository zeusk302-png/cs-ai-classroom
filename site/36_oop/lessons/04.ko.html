소단원 4.1

응집·결합

같은 클래스에 들어 있다는 이유만으로 같은 일을 하는 코드라고 볼 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 모듈은 함께 이해하고 변경하는 코드의 단위다. 여기서는 클래스 이름으로 표시한다.

  • A→B는 A의 코드가 B의 이름이나 약속을 알아야 한다는 의존 간선이다. 실행 호출 방향과 관련 있지만 모든 간선이 같은 비용은 아니다.

  • 응집은 한 단위 안의 기능이 얼마나 관련되는지, 결합은 단위 사이의 의존과 변화 영향을 살펴보는 관점이다.

학습 목표

  • 변경 이유로 기능을 묶고 분리한다.

  • 간선 수와 실제 변경 영향을 구분하여 작은 의존 그림을 분석한다.

화살표가 하나 늘면 설계가 반드시 더 나빠졌을까?

앞 본문은 세 직접 의존성으로 변화 영향을 계산했다. 이번 그래프는 Policy, Renderer, FileReader, Composition을 이름으로 가진 소스 모형이다. 화살표 A→B는 A의 소스가 B의 타입이나 호출 계약을 직접 안다는 뜻이다. 실행 횟수와 객체 수는 세지 않는다. 직접 설계는 Policy→FileReader, Renderer→FileReader, Composition→Policy/Renderer/FileReader의 다섯 화살표다.

추상 설계에는 IRead가 추가된다. Policy와 Renderer는 IRead를 알고, FileReader도 IRead를 구현한다. Composition은 여전히 Policy/Renderer/FileReader를 안다. 따라서 여섯 화살표다. 수가 늘어도 정책이 특정 파일 구현을 몰라도 되는 변화 경계가 생겼다. 새 DbReader가 같은 계약을 구현하면 Policy와 Renderer 소스를 바꾸지 않고 Composition의 선택과 새 구현을 바꿀 수 있다.

모든 화살표를 없애는 일은 목표가 아니다. 실제 객체를 고르는 Composition에는 구체 타입을 아는 책임이 남는다. IRead의 반환 단위를 숫자 점수에서 퍼센트 문자열로 바꾸면 추상 설계에서도 그 계약을 쓰는 Policy와 Renderer, 구현과 조립을 검토해야 한다. 인터페이스 이름을 그대로 두는 것은 계약을 보존하는 일이 아니다.

전역 설정은 별도 관찰이 필요하다. 여기서 세는 화살표는 명시된 타입 의존성뿐이다. 두 객체가 숨은 GlobalMode를 매번 읽으면 그 전역 값을 바꿀 때 둘의 행동이 함께 바뀔 수 있다. 타입 화살표 표가 같다는 이유로 실행 중 결합이 없다고 말하지 않는다. 아래 사례는 새 프로그램 실행 없이 소스 그래프와 명시된 행동을 손으로 비교한다.

먼저 확인할 개념
  • 변화 영향과 직접 의존성

    간선의 정의를 고정한 뒤 개수와 영향 범위를 따로 계산한다.

  • 조립 책임과 의존역전

    구체 타입을 고르는 곳까지 구체 의존성을 금지하는 오해를 피한다.

함께 바뀌는 이유를 찾기

응집이 높다는 것은 한 클래스의 기능과 자료가 의미 있는 목적을 공유한다는 뜻이다. 점수 범위 검사와 점수 합계 계산을 함께 이해해야 할 수 있지만, 프린터 연결 설정과 로그인 비밀번호 변경까지 같은 객체가 맡는다면 서로 다른 이유로 자주 바뀔 수 있다. 함수가 적다는 사실이나 메서드 이름의 길이는 응집을 직접 증명하지 않는다.

변경의 요청자와 정책을 질문한다. 교사가 평균의 반올림 규칙을 바꾸는 것, 디자이너가 보고서 색을 바꾸는 것, 저장 관리자가 파일 형식을 바꾸는 것은 독립 변화일 수 있다. 실제로 항상 함께 변경되는 일도 있어 무조건 세 클래스로 쪼개는 것이 정답은 아니다. 관찰한 변화와 기대되는 변경 범위를 먼저 적는다.

필요한 결합과 표현에 묶이는 결합

모듈들이 협력하면 결합을 완전히 없애기는 어렵다. Report가 Calculator의 Average 약속을 사용한다면 기능상 필요한 의존이다. 반면 Calculator가 Report의 임시 화면 필드를 직접 읽으면 평균 정책이 화면 표현에 묶인다. 인터페이스를 써도 오류·순서·단위·성능 약속에 의존하므로 결합이0이 되는 것은 아니다.

아래에서는 간선을 중복 없이 세는 단순 지표를 쓴다. 이는 전체 설계 품질 점수가 아니다. 같은1개 간선도 안정적인 표준 계약을 쓰는 경우와 자주 바뀌는 내부 배열 구조를 읽는 경우에 영향이 다르다. 실행 때 하나의 객체를 여러 번 호출한 횟수와 소스 의존 간선 수를 섞지 않는다.

작은 변경 사례로 비교하기

설계 A는 AllInOne이 계산·표시·저장을 다 맡는다. 설계 B는 Report→Calculator, Report→Formatter, Report→Store의 세 소스 의존으로 나눈다. B의 클래스 수와 간선 수는 A보다 늘 수 있지만 표시 변경이 계산 내부까지 건드리지 않도록 계약을 만들 수 있다. 구조 그림의 개수 대신 실제 변경 시나리오를 대조한다.

입력의 점수 의미가 바뀌면 여러 모듈을 함께 바꿔야 할 수 있다. 평균 반환값이 정수에서 소수로 바뀌는 계약 변경은 Formatter도 영향을 받을 수 있다. 겉으로만 분리하고 서로의 내부 필드에 접근하면 독립 변화가 어려워진다. 모든 수와 영향 범위는 자체 교육 모형의 문서 판정이며 실제 리팩터링·시험 결과가 아니다.

조립의 세 구체 타입은 Policy, Renderer, FileReader다. 인터페이스 구현 화살표도 이번 계산에서는 한 의존성으로 센다. 새 설계의 여섯은 코드 줄 수나 실제 호출 여섯 번이라는 뜻이 아니다. 어떤 변경이 어느 계약을 통과하는지 다음 예제로 확인한다.

중간 과정을 따라가는 예제

설계 B의 간선은 Report→Calculator, Report→Formatter, Report→Store뿐이다. Formatter 안의 색만 바꾸는 경우와 Calculator의 공개 반환 단위를 점수에서 백분율 문자열로 바꾸는 경우를 비교하라. Report는 숫자 평균을 Formatter에 전달한다고 정한다.

  1. 중복 없는 소스 의존 간선은3개다. 이 숫자는 호출 횟수나 모든 상태 의존 수가 아니다.

  2. 색 변경이 Formatter의 입력·출력 계약을 보존하면 이 모형에서는 Formatter 내부만 변경할 수 있다.

  3. Calculator가 숫자 대신 문자열을 반환하면 Report가 숫자를 전달한다는 약속과 충돌한다. Calculator와 Report의 연결과 Formatter의 입력 조건까지 검토한다.

  4. 따라서 같은 세 간선을 가진 그림이어도 내부 변경과 계약 변경의 영향은 다르다. 변경 후 시험 계획을 세워야 하며 그림만으로 실행 성공을 보장하지 않는다.

간선3개, 색의 내부 변경은 국소화 가능하다. 평균 반환 계약 변경은 사용하는 쪽으로 영향이 전파된다.

조건을 바꾸어 비교하기

구현 교체는 조립에서 구체적으로 끝난다

FileReader를 같은 IRead 계약의 DbReader로 교체한다. 추상 설계에서 어느 소스를 새로 작성하거나 수정하며 어떤 기존 소스를 유지하는가?

  1. DbReader를 새로 작성하고 IRead 구현 관계를 확인한다.

  2. Composition의 생성 대상을 FileReader에서 DbReader로 바꾼다.

  3. Policy와 Renderer는 기존 IRead의 입력·결과·효과 계약이 모두 보존되면 유지할 수 있다.

화살표 수만 줄이는 대신 기존 정책과 표시의 변경 경로를 끊는다.

비교할 점

교체 비용과 간선 개수는 같은 측정값이 아니다. 추상 계약을 유지하지 않는 교체는 이 결론에 포함되지 않는다.

숨은 전역 선택과 주입된 선택의 차이

Reader A는 같은 요청에 20, B는 80을 반환한다. 전역 탐색 고객 L은 호출마다 현재 reader를 조회하고, 고객 J는 생성 때 A를 주입받아 보관한다. 전역 선택을 A에서 B로 바꾼 뒤 다시 호출한다.

  1. 변경 전 L과 J 모두 A의 결과 20을 얻는다.

  2. 변경 뒤 L은 B를 조회해 80을 얻지만 J의 저장 참조는 여전히 A여서 20을 얻는다.

  3. A의 내부 상태를 바꾸는 별도 사건은 J에도 영향을 줄 수 있으므로 주입을 곧 독립 복제로 해석하지 않는다.

타입 의존성 수가 같아도 선택을 읽는 시점과 공유 상태가 행동을 바꾼다.

오해와 반례

클래스를 많이 만들고 간선을 줄이면 언제나 좋은 설계다.

한 함수의 고정 계산을 여러 전달 클래스에 쪼개면 읽기·조립 비용만 늘 수 있다. 반대로 필요한 의존을 없애려 공유 전역 상태에 숨기면 간선 그림은 단순해도 실제 결합은 커진다.

연습 1 · 값과 상태 예측

직접/추상 그래프의 간선 수를 구하고, 추상 설계의 파일 내부 인코딩 변경과 IRead 반환 단위 변경을 비교하라. 내부 인코딩 변경은 외부 계약을 그대로 지킨다.

힌트 1

구현 관계와 조립의 세 간선을 빠뜨리지 않는다.

힌트 2

외부 반환 타입·단위가 같은지 먼저 판정한다.

풀이와 답 확인

  1. 직접은 2+3=5, 추상은 2+1+3=6이다.

  2. 내부 인코딩 변경은 FileReader에 한정할 수 있지만 반환 단위 변경은 IRead 고객과 구현·조립을 검토한다.

간선 수의 증가만으로 변화 영향이 커졌다고 결론내리지 않는다.

흔한 오답에서 다시 생각하기

여섯이 다섯보다 크므로 모든 변경에서 추상 설계가 불리하다.

간선의 대상과 변경 계약이 달라 하나의 총수로 모든 변화 비용을 비교할 수 없다.

연습 2 · 오류 찾아 고치기

추상 설계에서 Composition도 FileReader를 알면 안 된다며 전역 탐색 객체로 옮겼다. 의존성이 사라졌는가?

힌트 1

누군가는 실제 구현을 선택해야 한다.

힌트 2

전역 탐색 객체의 구현과 호출 시점을 추적한다.

풀이와 답 확인

  1. 구체 선택 책임이 전역 탐색 객체로 옮겨졌을 뿐이다.

  2. 조립 시점에 선택하고 필요한 고객에 명시적으로 넘기면 선택 책임과 사용 책임을 읽을 수 있다.

구체 생성 자체를 없앴다는 주장을 고친다. 전역 탐색이 항상 금지된다는 보편 결론도 내리지 않는다.

흔한 오답에서 다시 생각하기

인터페이스 변수로 반환하므로 구체 구현을 선택하는 곳은 없다.

변수의 정적 타입과 실제 구현 생성 책임은 서로 다르다.

연습 3 · 직접 만들어 보기

위 두 고객 L/J에서 타입 화살표 표는 그대로지만 결과가 달라지는 사건과, 둘의 결과가 함께 달라지는 별도 사건을 만들어라.

힌트 1

전역 선택과 A 내부 값을 각각 독립적으로 변경한다.

힌트 2

의존역전과 주입

점수 계산기가 파일 저장 장치를 직접 만들지 않아도 결과를 저장할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 추상 계약은 무엇을 해야 하는지, 구체 구현은 어떻게 하는지를 설명한다.

  • 생성자 인자로 필요한 객체를 받는 것을 생성자 주입이라고 부른다.

  • DIP는 소스 의존 구조의 원칙, DI는 필요한 의존을 제공하는 구성 기법이다. 둘은 같은 단어가 아니다.

학습 목표

  • 정책이 사용할 계약과 구성 지점의 역할을 분리한다.

  • 테스트 대역의 관찰과 실제 장치 보장을 구별한다.

생성자로 넘긴 자원은 누가 닫아야 할까?

앞 본문은 Sink를 생성자로 전달해 정상 입력만 한 번 저장했다. 이번에는 수명이 있는 Session을 넘긴다. Session은 열린 동안 read()가 7을 반환하고 닫힌 뒤 호출은 CLOSED 오류를 내는 자체 계약이다. 요청의 Composition이 Session을 만들고 닫을 책임을 소유한다. Reporter는 이를 빌려 사용하며 닫을 권한을 넘겨받지 않는다.

요청 A에서 Session A를 만든 뒤 Reporter에 주입했다고 해서 두 수명이 같아지는 것은 아니다. Reporter를 다음 요청까지 보관하면 A 종료 때 닫힌 Session A도 보관한다. 요청 B에 새 Session B가 열려 있어도 Reporter의 참조가 자동으로 B로 바뀌지 않는다. 명시적으로 매 요청 Reporter를 만들거나 현재 요청의 Session을 호출 인수로 제공하는 방법을 비교할 수 있다.

생성자 주입은 의존성을 드러내는 전달 방식이고 의존역전은 정책이 어떤 계약에 의존하는지에 관한 소스 방향이다. 둘 중 하나만으로 소유권·수명·공유 상태·실제 저장 효과가 정해지지 않는다. 여기서는 프레임워크 컨테이너나 특정 scope 자동 검사를 실행하지 않고 개별 생성/닫힘/참조 사건만 다룬다.

가짜 Sink가 save(70) 인수를 기록해 trace=[70]을 만들면 호출 계약의 일부는 확인할 수 있다. 실제 저장소가 70을 지속시켰는지, 이후 장애 뒤 복구되는지는 다른 경계다. 모형 호출 기록을 실제 저장 증명으로 바꾸지 않는다. 객체를 교체할 때 값 반환뿐 아니라 누가 언제 무엇을 끝내는지도 계약에 포함한다.

먼저 확인할 개념
  • 주입과 외부 의존성의 교체

    명시 전달이 해결하는 선택과 해결하지 않는 자원 수명을 구별한다.

  • 객체 관계와 변경 영향

고수준 정책이 필요한 약속을 정한다

의존역전은 고수준 정책이 저수준 구현 세부에 직접 묶이지 않고 양쪽이 적절한 추상 계약에 의존하도록 설계하는 원칙이다. 예컨대 ScoreReporter는 유효 점수의 합계를 한 번 저장하려 한다. 특정 파일 포맷·경로·네트워크 연결을 만드는 책임까지 Reporter에 넣지 않고 ITotalSink.Save(total) 계약을 사용할 수 있다.

추상 이름만 붙이고 Save(FileDeviceHandle h)처럼 저수준 핸들을 그대로 요구하면 정책은 여전히 장치 세부를 알아야 한다. 계약은 호출자의 목적과 오류·효과를 표현해야 한다. 아래에서는 Save가 받은 정수를 순서대로 한 번 기록하며 실패하지 않는 단순 대역을 사용한다. 실제 저장소는 실패·중복·지속성 조건을 따로 정의해야 한다.

주입은 누가 객체를 고르는지 바꾼다

Reporter 생성자가 ITotalSink를 받으면 사용할 구현을 외부 구성 지점이 선택할 수 있다. 실행 중 메서드는 계약을 호출하고, 시작 코드 같은 구성 지점은 MemorySink나 FileSink를 조립한다. 프로그램 어디선가는 실제 구현을 알아야 하므로 모든 구체 의존이 사라진다는 주장은 틀리다. 변화에 민감한 정책에서 조립 책임을 이동하는 것이다.

DI에는 거대한 프레임워크가 필수인 것은 아니다. new Reporter(new MemorySink()) 같은 손수 조립도 주입이다. 반대로 Reporter(FileSink sink)는 외부에서 받는 주입이지만 여전히 구체 타입에 의존하여 DIP의 목표를 충분히 이루지 못할 수 있다. global locator에서 객체를 가져오면 생성자에 안 보이는 의존이 생겨 수명·시험 상태를 별도로 살펴야 한다.

형식과 행동 계약을 함께 지킨다

interface 구현 선언은 메서드 이름과 인자 형식을 맞추는 도움을 준다. 그러나 Save가 조용히 값을 버리거나 두 번 저장해도 형식만으로 적발하지 못할 수 있다. 반환값·부작용·오류·순서·수명을 문서화하고 대역/실제 구현에 같은 계약을 검토한다. 테스트 대역의 통과는 실제 파일의 전원 손실 내구성이나 원격 중복 제거를 증명하지 않는다.

이 단원의 종이 알고리즘은 Report(xs): 모든 원소가0..100인 정수인지 먼저 확인하고, 하나라도 잘못되면 false와 저장0회, 모두 유효하면 수학적 합계를 Save로 한 번 전달하고 true다. 빈 목록은 유효하여 합0을 저장한다. 수학적 정수로 합하며 실제 C#/Java의 넘침과 호출 실패는 추가 구현 조건이다. 수명을 가진 자원을 주입할 때는 누가 해제하고 공유하는지도 정해야 한다.

준비 개념

  • 사전조건은 호출자가 지킬 입력 조건, 사후조건은 호출 뒤 구현이 보장할 결과다.

  • 유효한 입력을 이전보다 적게 허용하면 사전조건을 강화한 것이다.

학습 목표

  • 다섯 원칙을 구체 변경과 계약에 연결한다.

  • 추상화 이득과 이해·구성 비용을 비교한다.

반환값이 같아도 대체 구현이 고객의 다음 동작을 바꿀까?

앞 본문은 ReadScore의 입력 범위와 반환 범위로 대체 가능성을 확인했다. 새 Reader는 유한 점수 목록 v와 cursor를 가진다. 0≤i<len(v)에서 peek(i)는 v[i]를 반환하며 cursor를 바꾸지 않는다. readNext는 cursor가 범위 안이면 해당 값을 반환한 뒤 cursor를 1 늘린다. 여기서는 성공 경로만 손추적하며 끝의 별도 오류 정책은 비교하지 않는다.

변형 Fast.peek(i)는 같은 v[i]를 반환하지만 cursor=i+1로 만든다. 고객은 peek 뒤 readNext의 값까지 관찰한다. v=[20,40,60], cursor=0에서 peek(1)의 반환 40은 같아도 정상 구현의 다음 반환은 20이고 Fast의 다음 반환은 60이다. 정적 타입과 첫 결과를 지켜도 상태 보존이라는 frame 조건을 어기면 대체할 수 없다.

원칙의 비용도 조건부로 비교한다. 허용된 두 설계 D와 A가 동일 계약을 지킨다는 전제에서, 지정 변화 k번의 가상 비용은 D=8k, A=18+4k다. k는 비음수 정수이며 A는 준비 18과 매번 비용 4를 치른다. 비용 단위는 자체 작업점수이며 실측 시간이나 코드 복잡도 통계가 아니다. A가 싸려면 k>4.5이므로 정수 k에서는 5부터다.

변경 종류를 넓히면 결론도 바뀐다. 비교한 지정 변화 밖의 사건 b번이 A에만 추가 3씩 든다는 별도 모형이면 A=18+4k+3b다. b도 비음수 정수다. k=5라도 b=2에서는 D=40, A=44로 뒤집힌다. 이 조건을 숨기고 인터페이스는 항상 이익이라고 말하지 않는다. 계약 위반 후보는 싸더라도 허용 후보 비교에서 먼저 제외한다.

원칙이 묻는 서로 다른 질문

SRP는 관련된 변경 이유와 역할을 모으고 독립 변화는 분리하자는 관점이다. “한 클래스에는 메서드가 하나”라는 수 규칙이 아니다. OCP는 선택한 확장 축에서 기존 정책을 크게 고치지 않고 구현을 추가하는 구조를 찾는다. 오류 수정과 요구 변경까지 기존 코드를 영원히 수정하지 말라는 금지가 아니다. 어떤 변화에 대비했는지 정해야 한다.

LSP는 대체 구현이 상위 계약을 유지하여 호출자의 정당한 기대를 깨지 않도록 요구한다. ISP는 사용하지 않는 관련 없는 기능에 호출자나 구현을 불필요하게 묶지 않는 계약 분리를 지향한다. DIP는 정책과 세부의 소스 의존을 추상 경계로 정리한다. 서로 관련되지만 동일한 기준 다섯 번이 아니며 클래스 수만 세어서 점수를 낼 수 없다.

대체 가능성을 입력과 결과로 검사한다

기본 ReadScore(i)의 계약을 유효 i=0,1,2에서 원래0..100 점수를 돌려주는 것이라고 정한다. FastReader가 i=0,1만 허용하면 호출자가 합법적으로 준2를 거절하므로 사전조건을 강화했다. 반환을 항상0으로 해도 형식과 범위는 맞지만 원래 점수라는 사후조건을 지키지 못한다. 성능 개선을 이유로 약속을 줄일 수 없다.

동일한 구현이 불필요한 Write/Delete 메서드를 억지로 제공하게 하는 큰 인터페이스라면 읽기 계약을 별도로 분리할 수 있다. 하지만 한 메서드마다 서로 무관한 인터페이스를 끝없이 만들면 탐색·조립·수명 관계의 복잡성이 커진다. 실제 사용자의 필요한 능력 단위와 실패 동작을 기준으로 분리하며 타입 이름만 많아지는 설계를 좋은 것이라 단정하지 않는다.

예상 변화와 비용을 나란히 적는다

추상 경계는 교체와 시험에 도움이 되지만 인터페이스·구현·구성 지점·문서의 유지 비용이 있다. 항상 하나의 고정 수학 함수만 필요한 작은 프로그램이라면 확장 구조를 미리 크게 만들 필요가 없을 수 있다. 반대로 여러 저장 장치나 명확한 정책 변화가 이미 있으면 경계를 만드는 근거가 강하다. 실제 요구와 변화 증거를 사용한다.

아래 비용 표는 보편 법칙이 아닌 교육 가정이다. 매 변경의 수정 비용, 초기 추상화 비용, 실제 발생한 변경 수를 비교한다. 숫자가 더 적더라도 행동 계약을 위반한 후보는 탈락이다. 안전·품질·이해도를 단순 줄 수 하나로 모두 대체하지 않는다. LSP의 입력/출력 판정과 비용 비교는 종이로 수행한다.

  2. B는 예컨대 위치1에서 기대40 대신0을 돌려줘 사후조건 위반이다. C는 이 정의의 값과 입력을 유지한다.

  3. 변경1회 총 비용은 단순0+6=6, 추상12+2=14다. 이 비용만 보면 단순 후보가8만큼 적다.

  4. 변경4회는 단순24, 추상20이다. 추상이4만큼 적지만 표의 가정과 계약 유지에만 근거한 판정이며 실제 제품 개발 시간을 측정한 값은 아니다.

대체 가능한 후보는 이 세 정의 중 C다. 비용의 우열은 변경 횟수와 초기 비용에 따라 달라진다.

조건을 바꾸어 비교하기

같은 첫 반환과 다른 다음 관찰

표의 두 독립 구현에서 peek(1); readNext를 수행하고 마지막 cursor까지 적어라.

  1. 정상 peek는 40을 반환하고 cursor=0을 보존한다. readNext는 20을 반환하고 cursor=1이다.

  2. Fast는 40을 반환하고 cursor=2를 만든다. readNext는 60을 반환하고 cursor=3이다.

  3. 원래 peek의 상태 보존 약속을 Fast가 강화 입력 없이 깨뜨렸다.

관찰열은 정상 [40,20], Fast [40,60]이다. 반환 범위만 맞추는 검사로는 부족하다.

선택한 변화 축의 경계와 역전

D=8k, A=18+4k에서 k=4와 5를 비교한다. 별도 추가 비용 3b가 A에만 있을 때 k=5,b=2를 다시 계산하라.
