소단원 4.1

응집·결합

같은 클래스에 들어 있다는 이유만으로 같은 일을 하는 코드라고 볼 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 모듈은 함께 이해하고 변경하는 코드의 단위다. 여기서는 클래스 이름으로 표시한다.
  • A→B는 A의 코드가 B의 이름이나 약속을 알아야 한다는 의존 간선이다. 실행 호출 방향과 관련 있지만 모든 간선이 같은 비용은 아니다.
  • 응집은 한 단위 안의 기능이 얼마나 관련되는지, 결합은 단위 사이의 의존과 변화 영향을 살펴보는 관점이다.

학습 목표

  • 변경 이유로 기능을 묶고 분리한다.
  • 간선 수와 실제 변경 영향을 구분하여 작은 의존 그림을 분석한다.

함께 바뀌는 이유를 찾기

응집이 높다는 것은 한 클래스의 기능과 자료가 의미 있는 목적을 공유한다는 뜻이다. 점수 범위 검사와 점수 합계 계산을 함께 이해해야 할 수 있지만, 프린터 연결 설정과 로그인 비밀번호 변경까지 같은 객체가 맡는다면 서로 다른 이유로 자주 바뀔 수 있다. 함수가 적다는 사실이나 메서드 이름의 길이는 응집을 직접 증명하지 않는다.

변경의 요청자와 정책을 질문한다. 교사가 평균의 반올림 규칙을 바꾸는 것, 디자이너가 보고서 색을 바꾸는 것, 저장 관리자가 파일 형식을 바꾸는 것은 독립 변화일 수 있다. 실제로 항상 함께 변경되는 일도 있어 무조건 세 클래스로 쪼개는 것이 정답은 아니다. 관찰한 변화와 기대되는 변경 범위를 먼저 적는다.

필요한 결합과 표현에 묶이는 결합

모듈들이 협력하면 결합을 완전히 없애기는 어렵다. Report가 Calculator의 Average 약속을 사용한다면 기능상 필요한 의존이다. 반면 Calculator가 Report의 임시 화면 필드를 직접 읽으면 평균 정책이 화면 표현에 묶인다. 인터페이스를 써도 오류·순서·단위·성능 약속에 의존하므로 결합이0이 되는 것은 아니다.

아래에서는 간선을 중복 없이 세는 단순 지표를 쓴다. 이는 전체 설계 품질 점수가 아니다. 같은1개 간선도 안정적인 표준 계약을 쓰는 경우와 자주 바뀌는 내부 배열 구조를 읽는 경우에 영향이 다르다. 실행 때 하나의 객체를 여러 번 호출한 횟수와 소스 의존 간선 수를 섞지 않는다.

작은 변경 사례로 비교하기

설계 A는 AllInOne이 계산·표시·저장을 다 맡는다. 설계 B는 Report→Calculator, Report→Formatter, Report→Store의 세 소스 의존으로 나눈다. B의 클래스 수와 간선 수는 A보다 늘 수 있지만 표시 변경이 계산 내부까지 건드리지 않도록 계약을 만들 수 있다. 구조 그림의 개수 대신 실제 변경 시나리오를 대조한다.

입력의 점수 의미가 바뀌면 여러 모듈을 함께 바꿔야 할 수 있다. 평균 반환값이 정수에서 소수로 바뀌는 계약 변경은 Formatter도 영향을 받을 수 있다. 겉으로만 분리하고 서로의 내부 필드에 접근하면 독립 변화가 어려워진다. 모든 수와 영향 범위는 자체 교육 모형의 문서 판정이며 실제 리팩터링·시험 결과가 아니다.

중간 과정을 따라가는 예제

설계 B의 간선은 Report→Calculator, Report→Formatter, Report→Store뿐이다. Formatter 안의 색만 바꾸는 경우와 Calculator의 공개 반환 단위를 점수에서 백분율 문자열로 바꾸는 경우를 비교하라. Report는 숫자 평균을 Formatter에 전달한다고 정한다.

  1. 중복 없는 소스 의존 간선은3개다. 이 숫자는 호출 횟수나 모든 상태 의존 수가 아니다.
  2. 색 변경이 Formatter의 입력·출력 계약을 보존하면 이 모형에서는 Formatter 내부만 변경할 수 있다.
  3. Calculator가 숫자 대신 문자열을 반환하면 Report가 숫자를 전달한다는 약속과 충돌한다. Calculator와 Report의 연결과 Formatter의 입력 조건까지 검토한다.
  4. 따라서 같은 세 간선을 가진 그림이어도 내부 변경과 계약 변경의 영향은 다르다. 변경 후 시험 계획을 세워야 하며 그림만으로 실행 성공을 보장하지 않는다.

간선3개, 색의 내부 변경은 국소화 가능하다. 평균 반환 계약 변경은 사용하는 쪽으로 영향이 전파된다.

종이와 본문으로 직접 해보기

B에 Calculator→Formatter와 Formatter→Calculator를 추가한다. 간선 수와 순환을 적고, 저장 파일 이름만 바꾸되 Store의 Save 계약을 유지할 때 Report 변경이 필수인지 판단하라.

힌트 보기

두 방향 간선은 하나로 합치지 않는다. 순환은 A에서 B를 거쳐 다시 A로 돌아오는 길이다.

풀이 보기

간선은5개이며 Calculator↔Formatter의 순환이 생긴다. 파일 이름이 Store 내부 설정이고 Save의 오류/효과 계약도 유지된다면 Report 소스 변경은 필수가 아니다. 실제 파일 경로를 Report가 몰래 알고 있었다면 처음의 세 간선 가정이 불완전한 것이다.

오해와 반례

클래스를 많이 만들고 간선을 줄이면 언제나 좋은 설계다.

한 함수의 고정 계산을 여러 전달 클래스에 쪼개면 읽기·조립 비용만 늘 수 있다. 반대로 필요한 의존을 없애려 공유 전역 상태에 숨기면 간선 그림은 단순해도 실제 결합은 커진다.

소단원 4.2

의존역전과 주입

점수 계산기가 파일 저장 장치를 직접 만들지 않아도 결과를 저장할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 추상 계약은 무엇을 해야 하는지, 구체 구현은 어떻게 하는지를 설명한다.
  • 생성자 인자로 필요한 객체를 받는 것을 생성자 주입이라고 부른다.
  • DIP는 소스 의존 구조의 원칙, DI는 필요한 의존을 제공하는 구성 기법이다. 둘은 같은 단어가 아니다.

학습 목표

  • 정책이 사용할 계약과 구성 지점의 역할을 분리한다.
  • 테스트 대역의 관찰과 실제 장치 보장을 구별한다.

고수준 정책이 필요한 약속을 정한다

의존역전은 고수준 정책이 저수준 구현 세부에 직접 묶이지 않고 양쪽이 적절한 추상 계약에 의존하도록 설계하는 원칙이다. 예컨대 ScoreReporter는 유효 점수의 합계를 한 번 저장하려 한다. 특정 파일 포맷·경로·네트워크 연결을 만드는 책임까지 Reporter에 넣지 않고 ITotalSink.Save(total) 계약을 사용할 수 있다.

추상 이름만 붙이고 Save(FileDeviceHandle h)처럼 저수준 핸들을 그대로 요구하면 정책은 여전히 장치 세부를 알아야 한다. 계약은 호출자의 목적과 오류·효과를 표현해야 한다. 아래에서는 Save가 받은 정수를 순서대로 한 번 기록하며 실패하지 않는 단순 대역을 사용한다. 실제 저장소는 실패·중복·지속성 조건을 따로 정의해야 한다.

주입은 누가 객체를 고르는지 바꾼다

Reporter 생성자가 ITotalSink를 받으면 사용할 구현을 외부 구성 지점이 선택할 수 있다. 실행 중 메서드는 계약을 호출하고, 시작 코드 같은 구성 지점은 MemorySink나 FileSink를 조립한다. 프로그램 어디선가는 실제 구현을 알아야 하므로 모든 구체 의존이 사라진다는 주장은 틀리다. 변화에 민감한 정책에서 조립 책임을 이동하는 것이다.

DI에는 거대한 프레임워크가 필수인 것은 아니다. new Reporter(new MemorySink()) 같은 손수 조립도 주입이다. 반대로 Reporter(FileSink sink)는 외부에서 받는 주입이지만 여전히 구체 타입에 의존하여 DIP의 목표를 충분히 이루지 못할 수 있다. global locator에서 객체를 가져오면 생성자에 안 보이는 의존이 생겨 수명·시험 상태를 별도로 살펴야 한다.

형식과 행동 계약을 함께 지킨다

interface 구현 선언은 메서드 이름과 인자 형식을 맞추는 도움을 준다. 그러나 Save가 조용히 값을 버리거나 두 번 저장해도 형식만으로 적발하지 못할 수 있다. 반환값·부작용·오류·순서·수명을 문서화하고 대역/실제 구현에 같은 계약을 검토한다. 테스트 대역의 통과는 실제 파일의 전원 손실 내구성이나 원격 중복 제거를 증명하지 않는다.

이 단원의 종이 알고리즘은 Report(xs): 모든 원소가0..100인 정수인지 먼저 확인하고, 하나라도 잘못되면 false와 저장0회, 모두 유효하면 수학적 합계를 Save로 한 번 전달하고 true다. 빈 목록은 유효하여 합0을 저장한다. 수학적 정수로 합하며 실제 C#/Java의 넘침과 호출 실패는 추가 구현 조건이다. 수명을 가진 자원을 주입할 때는 누가 해제하고 공유하는지도 정해야 한다.

중간 과정을 따라가는 예제

MemorySink는 호출 인자를 순서대로 기록하며 오류가 없다. Report([30,40]), Report([10,101]), Report([])를 처리하라. Reporter→ITotalSink, MemorySink→ITotalSink, 구성→Reporter/MemorySink의 의존을 구분하라.

  1. 첫 목록의 두 점수는 유효하여 합70을 Save에 한 번 전달하고 true다. 대역 기록[70]이다.
  2. 둘째 목록은101이 있어 저장 전 거절 false다. 대역 기록은[70] 그대로다. 앞의10을 먼저 저장하지 않는 검증 순서를 지킨다.
  3. 빈 목록은 모든 원소 조건이 참이며 합의 초기값0을 한 번 저장해 true, 기록[70,0]이다.
  4. 정책 Reporter와 구현 MemorySink는 ITotalSink 계약을 안다. 구성 지점은 둘의 구체 이름을 알고 조립한다. 호출 방향이 Reporter에서 sink로 간다고 소스 의존이 MemorySink에 직접 생긴 것은 아니다.

대역 기록[70,0], 결과 true/false/true다. 정책의 추상 의존과 구성의 구체 의존을 분리한다.

오해와 반례

DI 컨테이너를 쓰면 모든 의존과 수명 오류가 자동으로 해결된다.

공유 singleton에 짧은 수명의 객체를 붙이거나 필요한 구현 등록을 빠뜨리면 구성 문제가 남는다. 자동 생성은 계약 준수·지속성·스레드 안전을 증명하지 않는다. 손수 조립과 컨테이너의 검증 범위를 따로 적는다.

소단원 4.3

SOLID의 적용한계

다섯 원칙의 첫 글자를 외우면 설계의 정답을 자동으로 얻을 수 있을까?

준비 개념과 학습 목표

준비 개념

  • SRP/OCP/LSP/ISP/DIP는 설계 판단을 돕는 원칙의 약자다.
  • 사전조건은 호출자가 지킬 입력 조건, 사후조건은 호출 뒤 구현이 보장할 결과다.
  • 유효한 입력을 이전보다 적게 허용하면 사전조건을 강화한 것이다.

학습 목표

  • 다섯 원칙을 구체 변경과 계약에 연결한다.
  • 추상화 이득과 이해·구성 비용을 비교한다.

원칙이 묻는 서로 다른 질문

SRP는 관련된 변경 이유와 역할을 모으고 독립 변화는 분리하자는 관점이다. “한 클래스에는 메서드가 하나”라는 수 규칙이 아니다. OCP는 선택한 확장 축에서 기존 정책을 크게 고치지 않고 구현을 추가하는 구조를 찾는다. 오류 수정과 요구 변경까지 기존 코드를 영원히 수정하지 말라는 금지가 아니다. 어떤 변화에 대비했는지 정해야 한다.

LSP는 대체 구현이 상위 계약을 유지하여 호출자의 정당한 기대를 깨지 않도록 요구한다. ISP는 사용하지 않는 관련 없는 기능에 호출자나 구현을 불필요하게 묶지 않는 계약 분리를 지향한다. DIP는 정책과 세부의 소스 의존을 추상 경계로 정리한다. 서로 관련되지만 동일한 기준 다섯 번이 아니며 클래스 수만 세어서 점수를 낼 수 없다.

대체 가능성을 입력과 결과로 검사한다

기본 ReadScore(i)의 계약을 유효 i=0,1,2에서 원래0..100 점수를 돌려주는 것이라고 정한다. FastReader가 i=0,1만 허용하면 호출자가 합법적으로 준2를 거절하므로 사전조건을 강화했다. 반환을 항상0으로 해도 형식과 범위는 맞지만 원래 점수라는 사후조건을 지키지 못한다. 성능 개선을 이유로 약속을 줄일 수 없다.

동일한 구현이 불필요한 Write/Delete 메서드를 억지로 제공하게 하는 큰 인터페이스라면 읽기 계약을 별도로 분리할 수 있다. 하지만 한 메서드마다 서로 무관한 인터페이스를 끝없이 만들면 탐색·조립·수명 관계의 복잡성이 커진다. 실제 사용자의 필요한 능력 단위와 실패 동작을 기준으로 분리하며 타입 이름만 많아지는 설계를 좋은 것이라 단정하지 않는다.

예상 변화와 비용을 나란히 적는다

추상 경계는 교체와 시험에 도움이 되지만 인터페이스·구현·구성 지점·문서의 유지 비용이 있다. 항상 하나의 고정 수학 함수만 필요한 작은 프로그램이라면 확장 구조를 미리 크게 만들 필요가 없을 수 있다. 반대로 여러 저장 장치나 명확한 정책 변화가 이미 있으면 경계를 만드는 근거가 강하다. 실제 요구와 변화 증거를 사용한다.

아래 비용 표는 보편 법칙이 아닌 교육 가정이다. 매 변경의 수정 비용, 초기 추상화 비용, 실제 발생한 변경 수를 비교한다. 숫자가 더 적더라도 행동 계약을 위반한 후보는 탈락이다. 안전·품질·이해도를 단순 줄 수 하나로 모두 대체하지 않는다. LSP의 입력/출력 판정과 비용 비교는 종이로 수행한다.

중간 과정을 따라가는 예제

원래 점수[20,40,60]의 ReadScore는0..2에서 원래 값을 반환한다. 구현 A는2를 거절, B는 모든 위치에서0, C는 배열을 읽는다. 비용 후보 단순형 초기0/변경당6, 추상형 초기12/변경당2라는 가정에서 변경1회와4회의 총 비용도 비교하라.

  1. A는 입력2라는 기본 계약의 유효 요청을 거절하므로 대체 계약 위반이다.
  2. B는 예컨대 위치1에서 기대40 대신0을 돌려줘 사후조건 위반이다. C는 이 정의의 값과 입력을 유지한다.
  3. 변경1회 총 비용은 단순0+6=6, 추상12+2=14다. 이 비용만 보면 단순 후보가8만큼 적다.
  4. 변경4회는 단순24, 추상20이다. 추상이4만큼 적지만 표의 가정과 계약 유지에만 근거한 판정이며 실제 제품 개발 시간을 측정한 값은 아니다.

대체 가능한 후보는 이 세 정의 중 C다. 비용의 우열은 변경 횟수와 초기 비용에 따라 달라진다.
