소단원 8.1

adapter·facade

같은 wrapper라도 단위를 바꾸는 것과 복잡한 호출을 줄이는 것은 같은 목적일까?

준비 개념과 학습 목표

준비 개념

  • 인터페이스

  • 위임

  • 자료 단위

학습 목표

  • adapter와 facade의 목적을 구별한다.

  • 단위 변환과 호출 순서의 책임을 계산한다.

조회 이름으로 부르는 메서드가 다음 값을 버리면 계약이 맞을까?

앞 본문의 adapter는 밀리도를 섭씨로 바꾸었다. 결과의 단위뿐 아니라 입력을 언제 소비하는지도 계약이다. 새 자체 Source.pull()은 다음 정수를 소비해서 반환하고 끝이면 End를 반환한다. Iterator.hasNext()는 다음 값의 존재만 알려주며 반복 호출해도 next()가 돌려줄 값을 잃지 않아야 한다. next()는 한 값을 소비하고 끝이면 오류다.

연결 객체는 Empty, Buffered(v), Ended 중 하나의 상태를 가진다. Empty에서 hasNext는 Source를 한 번 호출해 결과를 보관한다. Buffered에서는 true만 반환하고 원본을 다시 부르지 않는다. next는 Buffered의 값을 반환하고 Empty로 바꾸며, Empty에서는 먼저 같은 준비 절차를 거친다. Ended에서는 hasNext가 false이고 next는 오류다. 원본의 정수와 End 표식은 구별된다.

facade의 간단한 표면에도 완료 범위가 필요하다. 아래 export는 열기·변환·저장·닫기 순서이며 열린 자원만 한 번 닫는다. 저장 성공 뒤 닫기 실패가 나면 저장 효과는 남는다. 결과를 SavedCleanupFailed로 구별하는 자체 계약이지 facade 패턴이 트랜잭션 롤백을 자동 제공한다는 뜻이 아니다.

먼저 확인할 개념
  • adapter·facade

    다른 인터페이스의 값·오류·자원 의미를 맞추는 동기와 facade의 단순한 진입점을 연결한다.

  • 외부시스템 격리

    부분 완료나 응답 실패가 작업 미수행을 뜻하지 않는다는 경계 조건을 확인한다.

호출자가 원하는 계약에 맞추기

adapter는 이미 존재하는 객체의 인터페이스를 호출자가 기대하는 인터페이스로 바꾸어 연결한다. 기대한 이름·인자·결과뿐 아니라 단위나 오류 의미가 맞는지도 확인한다. 메서드 이름만 동일하게 붙이는 것으로 계약이 맞았다고 할 수 없다.

자체 센서는 readMilliDegrees()로 정수 밀리도를 준다. 교실 코드의 temperatureC():double에 맞추려면1000.0으로 나눈다. 정수 나눗셈을 쓰면 소수점이 사라지므로 반환 타입과 단위 조건을 함께 설계한다. 예시 수치는 실제 센서 관측이 아니다.

사용 경로를 간단하게 보여주기

facade는 복잡한 하위 시스템에 사용하기 쉬운 진입점을 제공한다. 문서 내보내기에서 열기·변환·저장·닫기라는 여러 동작을 export() 한 번으로 정리하는 교육 예를 생각할 수 있다. 이 목적은 기존 호출자 인터페이스와 정확히 맞추는 adapter의 목적과 다르다.

facade가 있다고 하위 시스템에 직접 접근하는 일이 물리적으로 금지되는 것은 아니다. 오류와 자원 책임을 숨겨 없애는 것도 아니다. 간단한 표면 아래 어떤 계약을 보존하는지 명시하고 실패 시 어디까지 완료됐는지 알려야 한다.

목적을 먼저 고른다

한 wrapper가 두 목적을 함께 수행할 수도 있다. 중요한 것은 이름표보다 바꾸려는 문제다. 단위 변환은 adapter, 여러 호출의 사용 경로 단순화는 facade라는 동기를 먼저 적으면 과한 계층을 피할 수 있다.

단순 getter 하나만 필요한데 거대한 범용 facade를 만들면 관리 비용이 커진다. 반대로 외부 라이브러리의 내부 타입이 여기저기 새면 교체 비용이 커진다. 변경되는 부분과 사용자 계약을 찾아 최소한의 경계를 설계한다.

double temperatureC() {
    return sensor.readMilliDegrees() / 1000.0;
}

중간 과정을 따라가는 예제

자체 센서가21500과−500밀리도를 반환한다. adapter의 섭씨 결과를 계산하라. 별도 facade export는 open→convert→save→close 순서다. 각 단계 정상 한 번씩 수행하고 사용자가 export 한 번 호출하면 총 하위 호출 수는?

  1. 21500/1000.0=21.5℃다.

  2. −500/1000.0=−0.5℃다. 정수 나눗셈으로 소수부를 버리지 않는다.

  3. facade는 내부에서 open,convert,save,close 네 단계를 한 번씩 호출한다.

  4. 호출자 진입은1번, 하위 호출은4번이다. 표면 호출 수 감소와 실제 작업 소멸은 다르다.

예상 온도21.5/−0.5℃, facade 진입1회·하위4회다.

조건을 바꾸어 비교하기

같은 조회 두 번의 소비 차이

표와 같은 원본에서 hasNext, hasNext, next를 부른다. 잘못된 adapter는 hasNext마다 pull하고 마지막 결과 하나만 보관한다.

  1. 정상 첫 조회는 4를 보관하고 둘째 조회는 보관 상태만 읽는다. next는 4를 반환한다.

  2. 잘못된 첫 조회는 4, 둘째 조회는 9를 가져와 이전 값을 덮는다. next는 9를 반환한다.

  3. 호출 이름과 반환 타입이 같아도 값 4가 누락되는 관찰 차이가 생긴다.

정상은 원본 호출 1회·반환 4, 변형은 원본 호출 2회·반환 9다.

비교할 점

끝이 아닌 유효 값에서 실패하므로 빈 입력 처리만 고쳐서는 충분하지 않다.

저장 뒤 닫기 실패의 보고

독립 export에서 open/convert/save는 성공했고 save가 문서 1개를 저장했다. close만 실패한다. 실패하면 저장 문서를 지우는 기능은 없다.

  1. 하위 호출은 네 단계 모두 한 번씩 시도한다.

  2. 문서는 이미 저장되어 1개이며 close 실패가 이를 0개로 바꾸지 않는다.

  3. SavedCleanupFailed로 저장 완료와 정리 실패를 함께 보고한다.

저장 1개와 정리 실패를 분리한다.

비교할 점

convert 실패라면 save를 생략하고 열린 자원 close를 시도하는 다른 경로다.

종이와 본문으로 직접 해보기

온도−500에 정수 나눗셈(0쪽으로 절단)을 쓰면 결과는? convert에서 실패했을 때 save를 수행하지 않고 finally에서 close한다고 정한다. 하위 호출 순서와 횟수는?

힌트 보기

정수 소수부 절단과 명시한 실패 정책을 추적한다.

풀이 보기

정수 나눗셈은0으로 잘못 표현한다. 실패 경로는 open→convert 실패→close의 3회이며 save는 없다. 실제 처리 정책은 하위 시스템 계약에 맞춰 정한다.

오해와 반례

facade를 두면 복잡한 작업과 오류가 모두 사라진다.

export 한 번도 내부 4작업이며 convert 실패에 자원 정리와 오류 보고가 필요하다. 단순 사용 표면과 작업 책임을 구별한다.

연습 1 · 값과 상태 예측

새 원본이 End만 반환한다. hasNext를 두 번 호출하고 next를 호출할 때 원본 호출 수, 반환과 최종 상태를 구하라.

힌트 1

첫 조회의 End를 기억한다.

힌트 2

끝 상태에서 원본을 재조회하지 않는다.

풀이와 답 확인

  1. 첫 조회가 End를 읽어 false와 Ended가 된다.

  2. 두 번째 조회도 false이고 next는 끝 오류다. 원본 호출은 총 1회다.

false, false, 끝 오류이며 Ended가 유지된다.

흔한 오답에서 다시 생각하기

끝 오류가 난 뒤 정수 0을 대신 반환한다.

0도 유효 정수일 수 있다. 이 계약의 끝은 별도 상태와 오류다.

연습 2 · 오류 찾아 고치기

hasNext는 값을 보관하지만 next가 반환 뒤 Buffered 상태를 그대로 둔다. 원본의 값이 4, 9일 때 hasNext, next, next를 부르면 무엇을 반환하는가? 수정할 상태 전이를 써라.

힌트 1

반환 뒤 같은 버퍼가 남는지 본다.

힌트 2

한 값은 한 번만 소비한다.

풀이와 답 확인

  1. 변형은 두 next 모두 4를 반환하여 중복한다.

  2. 첫 next가 4를 반환한 뒤 Empty로 바꾸면 두 번째 next는 9를 준비하고 반환한다.

버퍼를 반환 뒤 비워 중복을 막는다.

흔한 오답에서 다시 생각하기

원본 pull이 유일하므로 반환 중복도 불가능하다.

보관 값의 재사용 경로는 원본 소비와 별개다.

연습 3 · 직접 만들어 보기

open 실패, convert 실패, 모두 성공의 세 독립 export 경로를 만든다. 성공한 open 뒤에는 close를 한 번 시도하며 convert 실패 뒤 save는 생략한다. 각각 호출 순서와 저장 수를 적어라.

힌트 1

존재하지 않는 열린 자원을 닫지 않는다.

힌트 2

모두 성공 경로의 save는 문서 1개를 만든다.

풀이와 답 확인

  1. open 실패는 open만 시도하고 저장 0개다.

  2. convert 실패는 open, convert, close이며 저장 0개다.

  3. 모두 성공은 open, convert, save, close이며 저장 1개다.

호출은 각각 1회, 3회, 4회이고 완료 범위를 함께 적는다.

흔한 오답에서 다시 생각하기

모든 실패는 네 단계를 모두 호출한 것이다.

실패 지점 뒤 일반 작업과 열린 자원의 정리를 구별해야 한다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

읽기 Source는 정수 −999999를 오류 표식으로 쓴다. 실제 측정 가능한 값에도 −999999가 포함된다. adapter가 모두 1000.0으로 나누면 어떤 정보가 사라지는가? 계약 수정 방향을 써라.

힌트 1

같은 반환 값의 두 의미를 비교한다.

힌트 2

이미 섞인 두 의미를 나눗셈만으로 복원할 수 있는지 본다.

풀이와 답 확인

  1. 유효 측정과 오류가 모두 −999.999로 바뀌어 구별되지 않는다.

  2. 원본 계약을 Value(v)/Failure의 분리된 결과로 바꾸거나 별도 오류 채널을 확보해야 한다.

원본이 구별해 주지 않으면 adapter만으로 두 의미를 복원할 수 없다.

흔한 오답에서 다시 생각하기

음수 결과를 전부 오류로 처리한다.

정상 음수 측정도 허용된 계약이므로 정상값을 잃는다.

캐시가 먼저 답하면 안쪽 검사도 수행되었을까?

앞 본문의 덧셈과 배수 decorator는 같은 인터페이스라도 순서가 결과를 바꾸었다. 새 자체 Read(doc) 인터페이스의 Base는 문서 문자열을 반환한다. Auth는 각 호출의 현재 permission을 확인해 false면 거절하고 안쪽을 호출하지 않는다. Cache는 처음 성공한 문자열을 보관하고 hit면 안쪽을 건너뛴다. 실패는 캐시하지 않는다. 두 호출은 같은 사용자·문서이고 permission만 true에서 false로 바뀐다.

Auth(Cache(Base))는 hit에서도 바깥 검사가 수행된다. Cache(Auth(Base))는 성공한 첫 호출 뒤 hit가 안쪽 검사를 생략할 수 있다. 이것은 이 수업의 현재 권한 검사 정책과 캐시 동작을 결합한 반례다. 모든 플랫폼 캐시가 같은 동작을 한다고 주장하지 않는다.

또 다른 자체 Log는 자신에게 들어온 호출마다 사건 하나를 남기고, Retry는 첫 호출 실패에만 한 번 더 안쪽을 부른다. 로그를 요청 단위로 셀지 시도 단위로 셀지에 따라 둘의 배치가 다르다. 요청 1개·시도 2개·성공 1개를 서로 다른 수로 기록한다.

동일한 역할을 감싸기

decorator는 기존 객체와 호환되는 인터페이스로 감싸 기능을 덧붙이거나 조정한다. 호출자는 같은 역할로 사용하고 wrapper는 내부 객체에 위임한다. adapter가 다른 인터페이스에 맞추는 목적과 구별한다.

자체 quote():int 인터페이스에서 Base가100을 반환하고 Add10은 내부 결과에10을 더하며 Double은2배한다. 둘 모두 quote를 제공하지만 값의 의미는 바뀐다. 실제 가격 API에 붙이려면 세금·통화·반올림 등 업무 계약을 먼저 정해야 한다. 여기 단위는 가상 점수다.

바깥에서 안쪽으로 호출하기

Double(Add10(Base))는 바깥 Double이 Add10에 위임하고 Add10이 Base에 위임한다. 돌아올 때 100→110→220이다. Add10(Double(Base))는 100→200→210으로 다르다. 합성과 순서는 교환 가능하지 않다.

로그·검사·캐시 decorator에서도 순서가 중요하다. Log(Cache(Base))에서는 바깥 로그가 cache hit에서도 호출을 기록한다고 정한다. Cache(Log(Base))에서는 바깥 캐시가 hit일 때 내부 로그와 Base 호출을 건너뛴다고 정한다. 이런 동작은 자체 캐시 계약이며 모든 캐시 구현의 보편 규칙은 아니다. 여기 기본 예제는 값 변환만 하고 캐시 정책은 별도 확장이다.

quote(Double(Add10(Base))) = 2*(100+10)
quote(Add10(Double(Base))) = 2*100+10

합성이 보존해야 할 계약

인터페이스가 같다는 사실만으로 원래 객체의 모든 행동 계약을 보존하는 것은 아니다. quote 결과를 non-negative라고 약속했다면 100에서 200을 빼는 wrapper는 그 계약을 깨뜨린다. 사용자가 어떤 관찰에 기대는지 먼저 확인한다.

여러 wrapper는 중복 효과·자원 소유·예외·동등성 판단을 복잡하게 한다. 필요한 책임만 추가하고 구체 객체 타입 검사에 의존하기보다 인터페이스 계약으로 사용한다. 실제 객체 실행이 아니라 종이 합성 계산으로 순서를 검증한다.

문서 반환: 검사 생략

두 배치는 각각 새 빈 캐시에서 시작하는 독립 대안이다. 두 번째 대안의 false는 현재 permission이며 캐시 안에 저장한 자료의 내용과 다르다.

중간 과정을 따라가는 예제

자체 Base.quote()=100, Add10(x)=x+10, Double(x)=2x다. Double(Add10(Base)), Add10(Double(Base))의호출 방향과 반환 값을 구하라.

  1. 첫 경로는Double→Add10→Base로 들어가고100을 반환한다.

  2. 안쪽Add10이110으로 바꾸고바깥Double이220으로 바꾼다.

  3. 둘째 경로는Add10→Double→Base이며100→200→210이다.

  4. 동일한 두 기능을 사용해도순서가 달라 10의 차이를 만든다.

첫220, 둘째210이며차이는 10이다.

조건을 바꾸어 비교하기

같은 문서의 권한 변경

표의 두 배치에서 첫 호출 뒤 권한을 철회한다. 문서와 사용자 이름은 같고 요청은 두 개다.

  1. 검사가 바깥이면 둘째 false에서 거절하며 Cache와 Base는 부르지 않는다.

  2. 캐시가 바깥이면 hit가 문서 문자열을 반환하고 Auth를 부르지 않는다.

  3. 같은 사용자 키를 사용했다는 사실도 시간에 따른 현재 권한 변경을 검사하지는 않는다.

Auth 누계는 2 대 1이며 둘째 결과는 거절 대 문서다.

비교할 점

캐시 키가 다른 사용자 자료를 섞는 문제와 이번의 권한 변경 문제는 구별한다.

요청 로그와 시도 로그

Base의 첫 시도는 실패, 둘째는 성공이다. 각각 새 Base에서 Log(Retry(Base))와 Retry(Log(Base))를 호출한다. Retry는 최대 두 시도다.

  1. Log가 바깥이면 요청 한 번의 사건을 남기고 안쪽 Retry가 Base를 두 번 부른다.

  2. Retry가 바깥이면 첫 실패 뒤 안쪽 Log를 다시 부르므로 사건은 두 개다.

  3. 두 대안 모두 요청 1개·Base 시도 2개·정상 반환 1개다.

로그는 각각 1개와 2개이며 분모가 다르다.

비교할 점

실제 로그 파일이나 재시도를 실행한 결과가 아니다.

스스로 풀어보기

먼저 답과 이유를 적고, 필요한 만큼 힌트를 한 단계씩 열어 보세요.

연습 1 · 값과 상태 예측

새 빈 캐시의 Auth(Cache(Base))에서 permission은 false, true, true 순서다. Base는 항상 성공한다. Auth/Cache/Base의 호출 수와 결과를 구하라.

힌트 1

false는 안쪽에 도달하지 않는다.

힌트 2

두 번째는 miss, 세 번째는 hit다.

풀이와 답 확인

  1. 첫 호출 거절, 두 번째 문서 반환과 캐시 저장, 세 번째 문서 반환이다.

  2. Auth는 3회, Cache는 2회, Base는 1회 호출된다.

첫 요청은 거절되고 둘째와 셋째 요청은 문서를 반환한다. Auth는 3회, Cache는 2회, Base는 1회 호출된다.

흔한 오답에서 다시 생각하기

같은 문서 세 요청이면 Base도 세 번 실행한다.

검사 거절과 캐시 hit는 안쪽 경로를 생략한다.

연습 2 · 오류 찾아 고치기

Retry(Log(Base))의 로그 2개를 요청 성공률의 분모로 사용해 정상 반환 1개이므로 성공률 50%라고 보고했다. 하나의 요청은 정상 반환했다. 오류를 고쳐라.

힌트 1

로그는 시도 단위다.

힌트 2

요청 완료와 개별 시도를 나눈다.

풀이와 답 확인

  1. 시도 정상 비율은 1/2=50%다.

  2. 요청 정상 비율은 1/1=100%다. 각각 분모 이름을 표시한다.

두 비율은 서로 다른 질문에 답한다.

흔한 오답에서 다시 생각하기

시도 수와 요청 수는 로그 파일에 있으면 같은 수다.

wrapper의 배치와 기록 계약에 따라 호출 수가 달라진다.

연습 3 · 직접 만들어 보기

모든 요청에서 현재 권한을 확인하고 요청 로그도 한 번 남기되, 허용된 요청은 캐시를 활용하려 한다. Log는 결과와 상관없이 진입 시 기록한다. 가능한 배치와 거절 경로를 구성하라.

힌트 1

로그도 거절 요청을 보아야 한다.

힌트 2

현재 권한 검사는 hit 앞에서 수행해야 한다.

풀이와 답 확인

  1. Log(Auth(Cache(Base)))를 선택한다.

  2. false이면 Log 기록 후 Auth가 거절하며 Cache/Base는 부르지 않는다. true일 때만 Cache에 도달한다.

바깥 로그와 그 안의 현재 검사로 두 요구를 명시한다.

흔한 오답에서 다시 생각하기

Cache(Log(Auth(Base)))도 모든 요청을 기록한다.

hit에서 안쪽 Log/Auth가 생략되어 두 요구를 모두 어길 수 있다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

원래 quote는 값이 0 이상이라는 계약이고 Sub50은 내부 값을 50 줄인다. Clamp0은 내부 값이 음수면 0으로 바꾼다. Base=40에서 Clamp0(Sub50(Base))와 Sub50(Clamp0(Base))를 비교하라.

힌트 1

반환은 안쪽에서 바깥으로 변한다.

힌트 2

내부의 Clamp가 뒤 변환까지 보장하지 않는다.

풀이와 답 확인

  1. 첫 배치는 40→−10→0으로 계약을 만족한다.

  2. 둘째 배치는 40→40→−10으로 계약을 위반한다.

같은 두 wrapper도 최종 반환은 0과 −10으로 다르다.

흔한 오답에서 다시 생각하기

Clamp가 한 번 있으므로 모든 배치에서 최종값은 0 이상이다.

검사/수정 이후에 값을 다시 바꾸는 바깥 동작을 확인해야 한다.

  • 상태와 오류

학습 목표

외부 오류 둘을 같은 Failed로 바꾸면 재시도도 같아질까?

앞 본문의 N/D/E/U 번역은 내부 상태 이름을 외부에서 격리했다. 새 자체 공급자는 WAIT, OK, BUSY, DENIED를 준다. WAIT는 Pending, OK는 Done, BUSY와 DENIED는 둘 다 Failed로 번역한다. 그러나 업무 정책은 BUSY만 재시도 후보이며 DENIED는 영구 거절이다. 번역 결과에서 원래 오류 종류를 버리면 정책에 필요한 정보가 사라진다.

번역층이 모든 업무 흐름을 대신 결정할 필요는 없다. 내부 결과를 Failure(Temporary) 또는 Failure(Permanent)로 구별해 제공하고, 업무 계층이 재시도 횟수와 기한을 정할 수 있다. 알 수 없는 새 코드 LATE는 Unknown으로 구별한다. 여기의 새 타입과 코드는 자체 모형이며 특정 공급자의 공식 API가 아니다.

자료 모양만 같아도 단위가 다를 수 있다. 공급자 A의 amount=1250은 KRW 1원 단위, B의 amount=1250은 USD 1센트 단위라고 명시한다. 번역은 금액과 통화를 함께 보존한다. 환율이나 화폐 간 비교 규칙은 주어지지 않았으므로 값 1250이라는 숫자만으로 같은 금액이라고 결론 내리지 않는다.

  • 외부시스템 격리

    의미 번역·Unknown·결과 불명과 대역 검증의 범위를 연결한다.

  • adapter·facade

    같은 숫자나 이름이라도 단위·오류 계약을 확인하는 adapter 책임을 연결한다.

의미가 섞이지 않는 경계

외부 시스템의 상태 이름·통화·식별자·시간 표현이 내부 도메인과 다를 수 있다. 번역 경계를 두면 내부 규칙이 외부 자료 모양에 직접 의존하는 범위를 줄인다. Azure의 anti-corruption layer는 이런 의미 격리를 위한 facade나 adapter를 설명한다.

자체 외부 코드 N/D/E를 내부 Pending/Done/Failed로 매핑한다. 모르는 U는 Done으로 짐작하지 않고 Unknown 또는 명시 오류로 처리하는 정책을 정한다. 외부 표현의 변경과 내부 업무 규칙을 각각 관리하며 뜻을 확인하지 않은 코드를 자동 성공으로 표시하지 않는다.

오류와 시간도 계약이다

timeout은 응답을 제시간에 못 받았다는 뜻이지 외부 작업이 미수행이라는 증명은 아니다. 저장 요청이 외부에서 성공한 뒤 응답만 잃으면 재시도는 중복 작업이 될 수 있다. 단순 wrapper만으로 이를 자동 해결하지 못한다.

번역층은 단위/자료 검증과 오류 분류에 집중하고 재시도·업무 흐름은 명확한 정책에 둔다. 독립 서비스로 만들면 추가 지연·운영비·관측 책임도 생긴다. 내부 일관성과 외부 일관성의 경계를 숨겨 없애지 않는다.

대역으로 확인하는 범위

fake는 특정 응답을 돌려주는 교육 대역이다. N/D/E/U를 넣어 매핑을 확인하면 내부 변환 규칙을 검토할 수 있지만 실제 서버의 인증·네트워크·오류 정책까지 검증한 것은 아니다. 실제 통합 확인은 따로 수행한다.

대역과 실제 구현이 같은 port 계약을 사용하도록 설계하되 대역에 없는 예외를 찾는다. 기록에는 입력 코드·내부 결과·지연 모형·실제 접속 여부를 분리한다. 개인정보나 비밀 키 없이 진단할 관측성과 상관 ID도 계획할 수 있다.

다대일 번역의 원상과 숫자의 단위를 복원할 정보가 남아 있는지 확인한다.

풀이와 답 확인

  1. 정상 조회는 첫 값 4를 보관하여 반환 4·원본 호출 1회다. 변형은 9로 덮어 반환 9·원본 호출 2회가 된다.

  2. 캐시 바깥 배치는 둘째 hit에서 검사를 생략한다. Auth(Cache(Base))는 현재 false를 검사해 거절한다.

  3. BUSY/DENIED는 Temporary/Permanent를 보존하고 금액은 통화/최소 단위와 함께 보존한다. 숫자만으로 통화 가치 비교는 할 수 없다.

  4. 저장은 완료되었으므로 저장 1개와 close 실패를 함께 보고한다. 자동 롤백 기능은 주어지지 않았다.

소비 계약을 지키는 버퍼, hit 앞의 현재 검사, 업무에 필요한 번역 정보, 부분 완료 보고를 각각 구성한다. 패턴 이름만으로 이 네 계약이 보장되지는 않는다.

해결한 뒤 점검할 것

  • adapter의 정상/변형 반환과 원본 호출 수를 구별한다.

  • 캐시 hit에서 검사 생략을 추적하고 현재 권한 정책을 보존한다.

  • 오류 종류·통화/단위 손실에 맞는 내부 자료를 구성한다.

  • 저장 완료와 정리 실패 및 실제 실행 미수행을 분리한다.

전체 기본과 같은 단원의 세 고유 선수 설명 및 여섯 HTML 앵커를 읽었다. 정상 버퍼는 4를 반환하고 원본 호출은 1회이며, 반복 조회 변형은 9를 반환하고 원본 호출은 2회다. export의 open 실패/convert 실패/정상 경로는 하위 호출이 각각 1/3/4회이며 저장 뒤 정리 실패는 저장 1개를 유지한다. 권한 true 뒤 false인 두 캐시 배치의 Auth 호출은 각각 2/1회, Base 호출은 각 1회다. 로그 배치에 따른 사건은 1/2개이며 요청 성공률 100%와 시도 정상 비율 50%의 분모를 구별했다. Clamp0을 바깥/안쪽에 둔 결과는 0/−10이다. 오류 원상, 통화와 단위, 수정 번호의 정보 손실을 손검산했다. 저장본 전체 세 소단원·여섯 예제·열두 과제·각 두 힌트·오답·recap·전이 및 출처를 재독했고 전이의 매 조회 호출과 저장 문서 수를 명확화했다.
