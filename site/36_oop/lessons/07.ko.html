소단원 7.1

factory·builder

객체를 한 번에 만드는 일과 여러 설정을 모아 만드는 일은 어떻게 다를까?

준비 개념과 학습 목표

준비 개념

  • 생성자
  • 객체와 참조
  • DI(의존성 주입)는 객체가 필요한 협력 객체를 외부에서 제공받는 방식이다. container는 등록에 따라 객체를 만들고 연결하며 scope는 정해진 사용 기간의 경계다.

학습 목표

  • 생성 책임을 호출자에서 분리한다.
  • 단계적 구성과 완성 시 검사를 설명한다.

생성 방법을 한곳에 모으기

factory는 필요한 객체를 만들어 돌려주는 역할이다. 예를 들어 CreateReader("text")가 TextReader를, "binary"가 BinaryReader를 돌려주도록 하면 호출자는 구체적인 생성자 선택을 반복하지 않는다. 알 수 없는 종류는 오류로 처리한다는 계약도 함께 정한다.

단순 생성 함수와 GoF의 Factory Method 패턴은 구별한다. 후자는 하위 클래스가 생성 방식을 바꾸는 확장점을 둔다. 교체 가능성이 없는 작은 프로그램에 상속 구조를 추가하면 이해 비용이 커질 수 있다.

builder로 설정을 단계적으로 모으기

builder는 아직 완성되지 않은 설정을 모으는 별도 객체다. 이 수업에서는 timeout은 1..30초, retries는 0..3회인 요청 설정을 만든다. SetTimeout과 SetRetries로 후보를 바꾸고 Build에서 두 조건을 모두 검사한다. 중간 후보는 아직 요청에 사용하지 않는다.

성공한 Build는 설정값을 복사한 불변 결과를 반환한다는 자체 계약을 둔다. 이후 builder를 바꿔도 이전 결과는 바뀌지 않는다. 모든 builder가 자동으로 복사하거나 자동으로 검증하는 것은 아니므로 실제 API의 계약을 확인해야 한다.

선택 기준과 실패 경계

종류 하나를 골라 즉시 만들면 되는 경우에는 factory가 간단하다. 여러 선택 사항과 조합 조건을 모으는 경우에는 builder가 구성 과정을 읽기 쉽게 할 수 있다. 둘을 함께 써 factory가 적절한 builder를 고를 수도 있다.

실패한 Build가 결과를 반환하지 않고 후보를 유지한다고 정하자. retries=4로 실패한 뒤 2로 수정하면 다시 시도할 수 있다. 검사가 실패했는데 반쪽짜리 요청을 내보내는 설계는 완성 객체의 유효성 보장을 깨뜨린다.

중간 과정을 따라가는 예제

후보 timeout=5, retries=4에서 Build하고, retries를 2로 바꿔 다시 Build한 뒤 timeout을 9로 바꾼다. 성공 결과는?

  1. 5는 1..30 안이지만 4는 0..3 밖이므로 첫 Build는 실패한다.
  2. retries=2로 바꾸면 두 조건이 맞아 결과 R=(5,2)를 만든다.
  3. builder의 timeout=9는 새 후보만 바꾸므로 R은 (5,2)로 남는다.

성공한 첫 결과는 R=(5,2)이며 이후 후보 수정과 분리된다.

종이와 본문으로 직접 해보기

timeout=0,retries=1인 후보를 유효하게 고치고 결과를 만든 뒤 retries=3으로 바꿔 이전 결과를 적어라.

힌트 보기

각 범위와 결과 복사 계약을 따로 적용한다.

풀이 보기

timeout을 예컨대 1로 고치면 R=(1,1)이다. 후보를 (1,3)으로 바꿔도 R=(1,1)이다.

오해와 반례

Builder를 쓰면 유효성 검사가 저절로 보장된다.

검사 없는 builder도 있다. Build가 timeout=0을 허용하면 패턴 이름과 무관하게 자체 계약을 위반한다.

소단원 7.2

수명과 소유권

내가 받은 객체를 언제 닫아야 할까?

준비 개념과 학습 목표

준비 개념

  • 참조와 별칭
  • 자원 해제
  • DI(의존성 주입)는 객체가 필요한 협력 객체를 외부에서 제공받는 방식이다. container는 등록에 따라 객체를 만들고 연결하며 scope는 정해진 사용 기간의 경계다.

학습 목표

  • 생성과 사용 및 해제 책임을 구별한다.
  • 빌린 자원과 소유한 자원의 수명 경계를 추적한다.

소유자는 해제 책임을 맡는다

여기서 소유권은 자원의 해제 책임을 누가 지는지 정한 계약이다. 파일 스트림을 직접 열고 소유한 객체는 사용을 마친 뒤 닫아야 한다. 다른 객체에서 빌린 스트림은 사용하는 동안 유효해야 하지만 사용자가 임의로 닫으면 다른 사용자가 실패할 수 있다.

메모리를 회수하는 GC와 파일·연결 같은 자원의 적절한 해제는 별개의 문제다. 닫는 책임을 명시하고 오류가 나도 해제되는 경로를 마련한다. 언어와 라이브러리에 따라 Dispose, close 또는 RAII 등 방법이 다르다.

컨테이너가 만든 객체의 범위

Microsoft DI에서 컨테이너가 생성한 해제 가능한 scoped 서비스는 해당 scope가 끝날 때 해제한다. 서비스는 빌려 사용하는 소비자가 따로 해제하지 않는다. 웹 요청에 대응하는 scope와 직접 만든 scope를 구별한다.

이미 생성한 인스턴스를 AddSingleton(instance)로 제공한 경우에는 컨테이너가 만든 것이 아니므로 제공자가 해제 책임을 진다는 지침이 있다. singleton이라는 이름만 보고 모든 경우의 해제 책임을 같다고 판단하면 안 된다.

참조가 남아도 사용 가능성은 끝날 수 있다

scope가 끝난 후 참조가 남았다고 해서 닫힌 연결을 계속 사용할 수 있는 것은 아니다. 이 예제에서는 scope 종료 시 연결 상태가 Open에서 Closed로 바뀌며 이후 Read는 오류라는 자체 계약을 둔다. 참조의 존재와 자원의 유효성을 따로 추적한다.

오래 사는 singleton에 짧게 사는 scoped 서비스를 보관하면 수명 불일치가 생길 수 있다. 필요한 작업마다 명시적 scope를 만들고 그 안에서 얻은 서비스를 scope 밖으로 내보내지 않는 방법을 검토한다.

중간 과정을 따라가는 예제

scope S가 연결 C를 생성한다. 소비자 A와 B가 빌려 읽고 S가 종료된 뒤 A가 다시 Read한다. 누가 닫고 마지막 결과는?

  1. S 안에서 C는 Open이고 A와 B의 읽기는 가능하다.
  2. S 종료 시 소유자인 컨테이너가 C를 해제하여 Closed가 된다.
  3. A의 참조가 남아도 마지막 Read는 자체 계약상 오류다.

컨테이너가 scope 종료 때 닫으며 마지막 Read는 오류다.

종이와 본문으로 직접 해보기

사용자가 직접 생성한 singleton 인스턴스 X를 컨테이너에 제공했다. 컨테이너 종료 후 누가 X를 해제해야 하는가?

힌트 보기

컨테이너가 생성했는지 먼저 확인한다.

풀이 보기

제공자인 사용자가 해제 책임을 진다. 별도의 소유권 이전 계약이 없는 이 지침의 경우다.

오해와 반례

참조를 받은 모든 객체가 Dispose하면 안전하다.

빌린 자원을 A가 먼저 닫으면 B의 사용을 망칠 수 있다. 소유자 하나와 빌리는 사용자의 계약을 명시해야 한다.

소유한 스트림과 빌린 스트림을 받는 두 생성자의 계약을 작성하고 예외가 나는 경로에서도 해제 책임을 표로 추적하라.

소단원 7.3

singleton의 trade-off

객체를 하나만 만들면 협업과 테스트도 쉬워질까?

준비 개념과 학습 목표

준비 개념

  • 공유 상태
  • 동시 실행
  • DI(의존성 주입)는 객체가 필요한 협력 객체를 외부에서 제공받는 방식이다. container는 등록에 따라 객체를 만들고 연결하며 scope는 정해진 사용 기간의 경계다.

학습 목표

  • singleton의 범위를 명시한다.
  • 생성 안전성과 사용 안전성을 구별한다.

하나라는 말에 범위를 붙이기

DI singleton은 같은 컨테이너에서 같은 등록을 요청할 때 같은 인스턴스를 반환하는 수명이다. 서로 다른 컨테이너나 서로 다른 프로세스까지 하나라고 보장하지 않는다. 인터넷 전체에서 유일한 객체라는 뜻도 아니다.

비싼 설정 읽기 결과처럼 여러 소비자가 공유할 필요가 있는 객체에 유용할 수 있다. 반면 전역 접근과 변경 가능한 상태를 함께 두면 누가 값을 바꿨는지 추적하기 어렵다. 한 번 정한 불변 설정과 요청별 가변 값을 분리한다.

생성의 안전성과 사용의 안전성

컨테이너의 안전한 생성·조회는 서비스 내부의 count++ 같은 연산을 원자적으로 만들지 않는다. count++를 읽기, 더하기, 쓰기의 세 단계로 모델링하면 두 작업이 같은 0을 읽고 각각 1을 써 최종 1이 될 수 있다.

이것은 동시 프로그램의 특정 종이 실행 순서이며 실제 스케줄을 측정한 결과가 아니다. 공유 가변 상태에는 적절한 동기화가 필요하다. 여러 스레드에서 안전한 불변 값 읽기와 변경 가능한 카운터 갱신은 구별한다.

테스트 간 오염과 대안

같은 singleton에서 테스트 A가 mode="fast"를 남겨두면 초기값 "safe"를 기대한 테스트 B가 순서에 따라 실패할 수 있다. 각 테스트에 새 컨테이너와 새 서비스를 제공하거나 상태를 명시적으로 초기화하면 조건을 통제하기 쉬워진다.

의존성을 생성자로 받으면 테스트용 구현을 전달할 수 있다. singleton 수명이 필요한지, scoped나 transient가 더 적절한지 실제 사용 범위로 결정한다. singleton에 짧은 scope의 객체를 직접 잡아 두는 수명 불일치도 함께 점검한다.

중간 과정을 따라가는 예제

count=0에서 A읽기0, B읽기0, A쓰기1, B쓰기1 순서로 두 증가를 수행한다. 직렬 수행과 비교하라.

  1. 동시 모형에서 A와 B가 같은 옛값 0을 읽는다.
  2. 각자 0+1=1을 써 최종 count=1이다.
  3. 직렬로 A의 읽기·쓰기를 끝낸 뒤 B가 읽으면 B는 1을 읽고 2를 써 최종 2다.

주어진 동시 순서에서는 1, 직렬 순서에서는 2다.

종이와 본문으로 직접 해보기

테스트 A가 공유 mode를 fast로 바꾸고 B가 safe를 기대한다. B가 안정적으로 시작하게 하는 두 방법을 적어라.

힌트 보기

공유 범위와 초기 상태를 분리한다.

풀이 보기

B마다 새 컨테이너·인스턴스를 만들거나 명시적 초기화를 수행한다. 단순히 실행 순서만 숨기는 것은 해결이 아니다.

오해와 반례

singleton이면 자동으로 모든 메서드가 스레드 안전하다.
