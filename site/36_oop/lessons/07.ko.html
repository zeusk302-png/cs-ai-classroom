소단원 7.1

factory·builder

객체를 한 번에 만드는 일과 여러 설정을 모아 만드는 일은 어떻게 다를까?

준비 개념과 학습 목표

준비 개념

  • 생성자

  • 객체와 참조

  • DI(의존성 주입)는 객체가 필요한 협력 객체를 외부에서 제공받는 방식이다. container는 등록에 따라 객체를 만들고 연결하며 scope는 정해진 사용 기간의 경계다.

학습 목표

  • 생성 책임을 호출자에서 분리한다.

  • 단계적 구성과 완성 시 검사를 설명한다.

불변 결과 안에 빌린 목록이 있으면 과거 설정도 바뀔까?

앞 본문의 builder는 timeout과 retries라는 값 두 개를 복사했다. 새 자체 설정은 URL, auth, headers 목록을 갖는다. URL은 비어 있지 않아야 하고 auth=true이면 URL이 https://로 시작해야 한다. Build는 모든 조건을 검사하고 실패하면 결과를 내보내지 않으며 후보도 그대로 유지한다. 후보는 중간에 부적합할 수 있지만 완성 결과는 적합해야 한다.

헤더는 문자열의 순서 있는 목록이며 각 문자열 자체는 불변이다. 여기서는 Build마다 목록 내용도 새 불변 튜플로 복사한다. 결과 객체의 필드 재대입만 금지하고 후보 목록을 그대로 가리키는 설계는 그 목록의 내용 변경을 막지 못한다. 복사 깊이는 자료 형태와 계약을 함께 읽어 정한다.

검증을 통과한 뒤 자원을 생성하는 factory와 builder를 결합할 수도 있다. 다만 두 번째 자원 생성이 실패하면 이미 만든 첫 자원을 누가 닫을지 따로 정해야 한다. 이 수업의 실패 보존은 후보와 공개 결과에 관한 계약이며 외부 로그나 자원 생성 자체를 없던 일로 만들지는 않는다.

먼저 확인할 개념
  • factory·builder

    단계적 후보와 Build 검증/불변 값 복사 계약을 확인한다.

  • 수명과 소유권

    검증 뒤 부분 생성이 실패해도 이미 만든 자원의 해제 책임이 남음을 연결한다.

생성 방법을 한곳에 모으기

factory는 필요한 객체를 만들어 돌려주는 역할이다. 예를 들어 CreateReader("text")가 TextReader를, "binary"가 BinaryReader를 돌려주도록 하면 호출자는 구체적인 생성자 선택을 반복하지 않는다. 알 수 없는 종류는 오류로 처리한다는 계약도 함께 정한다.

단순 생성 함수와 GoF의 Factory Method 패턴은 구별한다. 후자는 하위 클래스가 생성 방식을 바꾸는 확장점을 둔다. 교체 가능성이 없는 작은 프로그램에 상속 구조를 추가하면 이해 비용이 커질 수 있다.

builder로 설정을 단계적으로 모으기

builder는 아직 완성되지 않은 설정을 모으는 별도 객체다. 이 수업에서는 timeout은 1..30초, retries는 0..3회인 요청 설정을 만든다. SetTimeout과 SetRetries로 후보를 바꾸고 Build에서 두 조건을 모두 검사한다. 중간 후보는 아직 요청에 사용하지 않는다.

성공한 Build는 설정값을 복사한 불변 결과를 반환한다는 자체 계약을 둔다. 이후 builder를 바꿔도 이전 결과는 바뀌지 않는다. 모든 builder가 자동으로 복사하거나 자동으로 검증하는 것은 아니므로 실제 API의 계약을 확인해야 한다.

선택 기준과 실패 경계

종류 하나를 골라 즉시 만들면 되는 경우에는 factory가 간단하다. 여러 선택 사항과 조합 조건을 모으는 경우에는 builder가 구성 과정을 읽기 쉽게 할 수 있다. 둘을 함께 써 factory가 적절한 builder를 고를 수도 있다.

실패한 Build가 결과를 반환하지 않고 후보를 유지한다고 정하자. retries=4로 실패한 뒤 2로 수정하면 다시 시도할 수 있다. 검사가 실패했는데 반쪽짜리 요청을 내보내는 설계는 완성 객체의 유효성 보장을 깨뜨린다.

실패; R1/R2 유지

각 행은 이전 행 뒤의 상태다. 괄호 안 A/B는 헤더 문자열이며 실제 언어의 튜플 코드를 실행한 것이 아니다. 후보와 R1/R2의 내부 목록 공유 여부를 값과 별도로 확인한다.

중간 과정을 따라가는 예제

후보 timeout=5, retries=4에서 Build하고, retries를 2로 바꿔 다시 Build한 뒤 timeout을 9로 바꾼다. 성공 결과는?

  1. 5는 1..30 안이지만 4는 0..3 밖이므로 첫 Build는 실패한다.

  2. retries=2로 바꾸면 두 조건이 맞아 결과 R=(5,2)를 만든다.

  3. builder의 timeout=9는 새 후보만 바꾸므로 R은 (5,2)로 남는다.

성공한 첫 결과는 R=(5,2)이며 이후 후보 수정과 분리된다.

조건을 바꾸어 비교하기

겉의 불변성과 내부 별칭

표의 두 Build를 내부 목록 복사 방식과 후보 목록 공유 방식으로 비교하라. 공유 방식도 결과 필드 자체는 재대입할 수 없다고 가정한다.

  1. 복사 방식에서 R1은 (A), R2는 (A,B)다.

  2. 공유 방식에서는 후보에 B를 추가할 때 R1이 관찰하는 목록도 [A,B]가 된다. R2도 같은 목록을 가리킨다.

  3. 후보에 C까지 추가하면 복사한 R1/R2는 유지되지만 공유 결과 둘은 [A,B,C]를 관찰한다.

결과 객체만 불변인 것과 과거 설정 내용이 불변인 것은 다르다.

비교할 점

문자열이 불변이므로 이 모형에서는 문자열 자체를 다시 복제할 필요가 없다.

부분 생성 뒤의 실패

검증을 마친 Build가 새 자원 X를 만든 뒤 Y 생성에 실패했다. 반환 전에는 builder가 X를 소유하며 성공할 때만 결과 객체에 소유권을 넘긴다는 계약이다.

  1. Y 실패에서는 결과가 반환되지 않으므로 X의 소유권도 이전되지 않았다.

  2. builder의 실패 정리 경로가 X를 한 번 닫고 후보 값은 유지한다.

  3. 성공 대안에서는 결과가 X/Y를 소유하고 결과 종료 경계에서 둘을 닫는다.

검증과 실패 정리 및 성공 소유권 이전을 각각 적는다.

비교할 점

실제 생성·해제 API를 호출하거나 실패를 주입한 기록은 아니다.

종이와 본문으로 직접 해보기

timeout=0,retries=1인 후보를 유효하게 고치고 결과를 만든 뒤 retries=3으로 바꿔 이전 결과를 적어라.

힌트 보기

각 범위와 결과 복사 계약을 따로 적용한다.

풀이 보기

timeout을 예컨대 1로 고치면 R=(1,1)이다. 후보를 (1,3)으로 바꿔도 R=(1,1)이다.

오해와 반례

Builder를 쓰면 유효성 검사가 저절로 보장된다.

검사 없는 builder도 있다. Build가 timeout=0을 허용하면 패턴 이름과 무관하게 자체 계약을 위반한다.

Factory Method는 하위 클래스의 생성 변경 확장점이 중심이다.

스스로 풀어보기

먼저 답과 이유를 적고, 필요한 만큼 힌트를 한 단계씩 열어 보세요.

연습 1 · 값과 상태 예측

각 대안은 새 표의 시작 상태에서 시작한다. auth=true에서 URL을 http://a로 바꿔 Build하고, 다시 https://b로 고쳐 Build한다. 헤더는 [A]다.

힌트 1

조합 조건은 두 필드를 함께 본다.

힌트 2

실패는 후보를 초기화하지 않는다.

풀이와 답 확인

  1. 첫 Build는 인증과 URL 조합 때문에 실패한다. 후보 URL은 http://a, auth는 true, headers는 [A]로 유지된다.

  2. 둘째 Build는 성공한다. 새 결과의 URL은 https://b, auth는 true, headers는 (A)다.

실패 뒤 수정한 후보를 다시 검증한다.

흔한 오답에서 다시 생각하기

첫 실패가 URL을 빈 값으로 초기화한다.

이 모형의 실패는 후보 유지이며 초기화 계약은 없다.

연습 2 · 오류 찾아 고치기

불변 결과라는 설명 뒤에서 R.headers가 builder.headers 목록을 그대로 가리킨다. 후보 헤더 변경에 대해 어떤 계약이 깨지고 어떻게 고칠까?

힌트 1

필드 재대입과 목록 내용 변경을 나눈다.

힌트 2

이 모형의 원소는 불변 문자열이다.

풀이와 답 확인

  1. 후보에 B를 추가하면 R의 내용도 바뀌므로 과거 스냅샷 보존이 깨진다.

  2. Build에서 현재 문자열들을 새 불변 튜플로 모아 결과에 저장한다.

현재 자료 형태에는 새 목록 내용 복사와 결과의 변경 제한이 필요하다.

흔한 오답에서 다시 생각하기

결과 필드가 readonly이면 충분하다.

그 필드가 가리키는 목록의 변경은 별도 경로다.

연습 3 · 직접 만들어 보기

URL과 auth를 각각 따로 검사하면 통과하지만 조합 검사는 실패하는 후보, 그리고 헤더가 달라 두 Build 결과가 다른 후보 이력을 만들어라.

힌트 1

http://a도 비빈 문자열이다.

힌트 2

헤더 추가는 성공한 첫 Build 뒤에 한다.

풀이와 답 확인

  1. URL=http://a, auth=true는 각 형/비빈 검사에 맞지만 https 조합에 실패한다.

  2. 별도의 유효한 후보에서 URL은 https://a, auth는 true, headers는 [A]다. R1을 만든 뒤 후보에 B를 추가해 R2를 만들면 R1의 헤더는 (A), R2의 헤더는 (A,B)다.

조합 반례와 독립 스냅샷 이력을 따로 구성한다.

흔한 오답에서 다시 생각하기

모든 필드가 개별적으로 적합하면 객체도 적합하다.

필드 사이 관계는 개별 검사에 포함되지 않을 수 있다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

X 생성 성공, Y 생성 실패 뒤 X를 닫지 않고 후보만 유지했다. 다음 재시도는 X2/Y2 성공이다. 각 자원은 서로 다른 새 자원이다. 종료 정리를 두 경우로 비교하라.

힌트 1

실패한 첫 시도의 X와 성공 결과의 X2는 다르다.

힌트 2

공개되지 않은 자원에도 소유자가 필요하다.

풀이와 답 확인

  1. 잘못된 경로는 X가 열린 채 남고 성공 결과는 X2/Y2만 닫는다.

  2. 올바른 실패 정리는 첫 X를 즉시 닫으며 성공 결과 종료는 X2/Y2를 각각 닫는다.

성공 결과만 정리해도 이전 실패 자원은 회수되지 않는다.

흔한 오답에서 다시 생각하기

나중 성공이 이전 X의 소유권까지 자동으로 가져간다.

이 계약의 결과는 그 시도에서 만든 자원만 받는다.

설명 기준 확인

수명과 소유권

준비 개념과 학습 목표

준비 개념

  • 참조와 별칭

  • 자원 해제

  • DI(의존성 주입)는 객체가 필요한 협력 객체를 외부에서 제공받는 방식이다. container는 등록에 따라 객체를 만들고 연결하며 scope는 정해진 사용 기간의 경계다.

학습 목표

  • 생성과 사용 및 해제 책임을 구별한다.

  • 빌린 자원과 소유한 자원의 수명 경계를 추적한다.

빌린 자원을 감싸는 객체가 끝나면 원본도 닫아야 할까?

자체 wrapper는 입력 스트림을 빌리거나 소유한다. borrow 모드는 종료 때 자기 작업 상태만 닫고 입력은 닫지 않는다. own 모드는 입력의 해제 책임을 받아 종료 때 입력을 닫는다. 모드 이름이 실제 라이브러리 API는 아니며 호출자와 객체가 약속한 계약이다. 입력이 Closed이면 이후 읽기는 오류다.

Microsoft DI가 생성한 해제 가능한 transient를 root provider에서 여러 번 얻으면 참조를 지역에서 지워도 컨테이너의 해제 추적 때문에 provider 종료까지 유지될 수 있다. 짧은 작업 수명이 필요한 자체 factory 소유 객체는 각 작업 종료에 직접 닫는 대안이다. 둘을 혼동해 빌린 서비스에 Dispose를 부르지는 않는다.

Microsoft DI의 명시적 scopes는 계층적이지 않다. A scope가 살아 있는 동안 별도 B scope를 만들었다고 B가 A의 자식으로 자동 소유되는 것은 아니다. 어떤 scope를 닫았는지, 각 객체를 어떤 scope가 생성했는지의 장부로 추적한다.

먼저 확인할 개념
  • 수명과 소유권

    생성한 객체/직접 제공한 객체의 해제 책임과 Closed 뒤 사용을 확인한다.

  • factory·builder

    새 객체를 만드는 factory의 반환 계약과 성공 소유권 이전을 연결한다.

소유자는 해제 책임을 맡는다

여기서 소유권은 자원의 해제 책임을 누가 지는지 정한 계약이다. 파일 스트림을 직접 열고 소유한 객체는 사용을 마친 뒤 닫아야 한다. 다른 객체에서 빌린 스트림은 사용하는 동안 유효해야 하지만 사용자가 임의로 닫으면 다른 사용자가 실패할 수 있다.

메모리를 회수하는 GC와 파일·연결 같은 자원의 적절한 해제는 별개의 문제다. 닫는 책임을 명시하고 오류가 나도 해제되는 경로를 마련한다. 언어와 라이브러리에 따라 Dispose, close 또는 RAII 등 방법이 다르다.

컨테이너가 만든 객체의 범위

Microsoft DI에서 컨테이너가 생성한 해제 가능한 scoped 서비스는 해당 scope가 끝날 때 해제한다. 서비스는 빌려 사용하는 소비자가 따로 해제하지 않는다. 웹 요청에 대응하는 scope와 직접 만든 scope를 구별한다.

이미 생성한 인스턴스를 AddSingleton(instance)로 제공한 경우에는 컨테이너가 만든 것이 아니므로 제공자가 해제 책임을 진다는 지침이 있다. singleton이라는 이름만 보고 모든 경우의 해제 책임을 같다고 판단하면 안 된다.

참조가 남아도 사용 가능성은 끝날 수 있다

scope가 끝난 후 참조가 남았다고 해서 닫힌 연결을 계속 사용할 수 있는 것은 아니다. 이 예제에서는 scope 종료 시 연결 상태가 Open에서 Closed로 바뀌며 이후 Read는 오류라는 자체 계약을 둔다. 참조의 존재와 자원의 유효성을 따로 추적한다.

오래 사는 singleton에 짧게 사는 scoped 서비스를 보관하면 수명 불일치가 생길 수 있다. 필요한 작업마다 명시적 scope를 만들고 그 안에서 얻은 서비스를 scope 밖으로 내보내지 않는 방법을 검토한다.

중간 과정을 따라가는 예제

scope S가 연결 C를 생성한다. 소비자 A와 B가 빌려 읽고 S가 종료된 뒤 A가 다시 Read한다. 누가 닫고 마지막 결과는?

  1. S 안에서 C는 Open이고 A와 B의 읽기는 가능하다.

  2. S 종료 시 소유자인 컨테이너가 C를 해제하여 Closed가 된다.

  3. A의 참조가 남아도 마지막 Read는 자체 계약상 오류다.

컨테이너가 scope 종료 때 닫으며 마지막 Read는 오류다.

조건을 바꾸어 비교하기

root에서 세 작업의 transient를 얻는다

각 작업은 새 disposable transient 하나를 root provider에서 얻고 사용 뒤 지역 참조만 지운다. 다른 참조는 없어도 root가 해제를 추적한다. 세 작업 순차 완료 뒤와 root 종료를 비교하라.

  1. 각 작업에서 열린 자원 수는 1, 2, 3으로 늘고 root 종료 전에는 3이다.

  2. root 종료 때 세 자원을 각각 해제해 0이 된다.

  3. 별도 factory 소유 대안은 각 작업 종료마다 닫으므로 열린 수의 피크는 1이고 작업 사이에는 0이다.

참조를 지우는 것과 예정된 소유자 종료는 다르다.

비교할 점

세 작업/열린 수는 자체 장부이며 실제 container나 handle을 측정하지 않았다.

겹쳐 살아 있는 독립 scopes

A가 C1, B가 C2를 각각 생성하고 둘은 다른 객체다. B를 만든 뒤 A만 Dispose하고 B는 유지한다.

  1. A 종료가 C1을 닫는다. B는 별도 scope라 C2는 Open이다.

  2. 남은 C1 참조로 Read하면 오류, C2의 Read는 성공한다.

  3. B를 명시적으로 종료하면 C2도 Closed다.

scope 생성 시각의 중첩만으로 자동 부모·자식 해제를 추론하지 않는다.

소단원 7.3

singleton의 trade-off

객체를 하나만 만들면 협업과 테스트도 쉬워질까?

준비 개념과 학습 목표

준비 개념

  • 공유 상태

  • 동시 실행

  • DI(의존성 주입)는 객체가 필요한 협력 객체를 외부에서 제공받는 방식이다. container는 등록에 따라 객체를 만들고 연결하며 scope는 정해진 사용 기간의 경계다.

학습 목표

  • singleton의 범위를 명시한다.

  • 생성 안전성과 사용 안전성을 구별한다.

하나의 캐시가 원자적이어도 사용자 자료를 섞을 수 있을까?

자체 provider P 안의 같은 등록 K는 같은 객체를 반환한다. Q라는 새 provider가 자체 생성한 K는 별도 객체다. 그러나 외부에서 만든 X를 두 provider에 모두 공급하면 같은 X를 공유할 수 있다. provider가 다르다는 사실만으로 실제 객체가 다름을 결론내리지 않는다.

자체 카운터는 count=0에서 A가 3, B가 5를 더한다. 각각 읽기와 쓰기 사이에는 다른 작업이 끼어들 수 있다. 값을 읽어 합을 계산하고 쓰는 복합 동작 전체를 원자적으로 만들지 않으면 더한 값 하나가 사라질 수 있다. 아래 순서는 종이 모형이며 언어의 자료 경쟁 동작을 실행한 것이 아니다.

별도 캐시는 문서 번호만 키로 삼고 사용자별 보기 결과를 저장한다. 민과 서가 같은 문서라도 다른 허용 내용을 보는 정책에서, (사용자, 문서)를 키로 삼거나 요청별 결과를 저장하지 않는 대안이 필요하다. 키/값의 원자적 저장만으로 잘못된 의미 키나 인가 누락이 고쳐지지는 않는다.

    동일 등록의 공유 범위와 생성 안전/가변 상태 사용 안전의 차이를 확인한다.

  • 수명과 소유권

    provider 외부에서 제공한 같은 객체의 책임과 짧은 요청 수명을 연결한다.

하나라는 말에 범위를 붙이기

DI singleton은 같은 컨테이너에서 같은 등록을 요청할 때 같은 인스턴스를 반환하는 수명이다. 서로 다른 컨테이너나 서로 다른 프로세스까지 하나라고 보장하지 않는다. 인터넷 전체에서 유일한 객체라는 뜻도 아니다.

비싼 설정 읽기 결과처럼 여러 소비자가 공유할 필요가 있는 객체에 유용할 수 있다. 반면 전역 접근과 변경 가능한 상태를 함께 두면 누가 값을 바꿨는지 추적하기 어렵다. 한 번 정한 불변 설정과 요청별 가변 값을 분리한다.

생성의 안전성과 사용의 안전성

컨테이너의 안전한 생성·조회는 서비스 내부의 count++ 같은 연산을 원자적으로 만들지 않는다. count++를 읽기, 더하기, 쓰기의 세 단계로 모델링하면 두 작업이 같은 0을 읽고 각각 1을 써 최종 1이 될 수 있다.

이것은 동시 프로그램의 특정 종이 실행 순서이며 실제 스케줄을 측정한 결과가 아니다. 공유 가변 상태에는 적절한 동기화가 필요하다. 여러 스레드에서 안전한 불변 값 읽기와 변경 가능한 카운터 갱신은 구별한다.

테스트 간 오염과 대안

같은 singleton에서 테스트 A가 mode="fast"를 남겨두면 초기값 "safe"를 기대한 테스트 B가 순서에 따라 실패할 수 있다. 각 테스트에 새 컨테이너와 새 서비스를 제공하거나 상태를 명시적으로 초기화하면 조건을 통제하기 쉬워진다.

의존성을 생성자로 받으면 테스트용 구현을 전달할 수 있다. singleton 수명이 필요한지, scoped나 transient가 더 적절한지 실제 사용 범위로 결정한다. singleton에 짧은 scope의 객체를 직접 잡아 두는 수명 불일치도 함께 점검한다.

추가량이 다른 두 갱신

A는 3, B는 5를 더한다. A가 0을 읽고 B도 0을 읽은 뒤 A가 3을 쓰고 B가 5를 쓰는 순서다. 두 읽기는 그대로 먼저 두고 쓰기 둘의 순서만 바꾸는 대안, 직렬로 A 뒤 B를 완료하는 대안과 비교하라.

  1. 주어진 순서는 마지막 B가 5를 써 최종 5다.

  2. 읽기 둘이 여전히 먼저인 채 B가 5를 쓰고 A가 3을 쓰면 최종 count는 3이다.

  3. 직렬로 A가 3을 끝내고 B가 그 3을 읽으면 최종 8이다.

첫 순서의 최종 count는 5, 쓰기 역순 대안은 3, 직렬 대안은 8이다. 차이는 각 작업이 읽은 옛값과 마지막 쓰기에서 나온다.

    실제 전체 0–16행에서 하위 클래스 Factory Method, 합성 대안, Builder의 단계적 구성과 변화 필요에 따른 복잡성 선택을 읽었다. 자체 URL/헤더 및 부분 자원 생성은 종이 설계다.

  • Microsoft — DI guidelines

    실제 전체 0–308행을 읽었다. 43–45/127–139행의 생성/외부 제공별 해제 책임, 141–169행 factory·scope 및 비계층 scope, 191–195행 생성과 사용 동시성 구별, 227행 root transient 유지와 238–257행 captive 의존성/검증을 대조했다.
