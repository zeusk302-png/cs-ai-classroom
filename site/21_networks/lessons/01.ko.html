소단원 1.1

패킷 교환과 계층화

큰 사진을 보내는 중에 다른 사람의 짧은 메시지도 같은 링크를 사용할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 1바이트(B)는 8비트(bit)다. 여기서는 Mbps=10⁶bit/s, MB=10⁶B인 십진 단위를 쓰며 MiB=2²⁰B와 구별한다.

  • 링크는 이웃한 네트워크 장치 사이의 전송 연결이다. 경로는 링크 여러 개를 차례로 잇는다.

  • 패킷은 헤더와 데이터로 이루어진 전송 단위다. 헤더에는 목적지·프로토콜 등 해석과 전달에 필요한 정보가 들어간다.

학습 목표

  • 패킷 단위 자원 공유와 전용 예약의 차이를 설명한다.

  • 저장 후 전달의 두 링크 시간표를 계산한다.

  • 응용·전송·인터넷·링크 계층의 책임과 캡슐화를 구별한다.

1. 데이터를 나누어 같은 자원을 공유한다

패킷 교환은 여러 흐름의 패킷이 공유 링크를 차례로 이용하도록 한다. 어떤 흐름이 조용할 때 다른 흐름이 그 전송 기회를 쓸 수 있어 수요가 들쭉날쭉한 응용에 유리하다. 회선 교환의 전용 자원 예약과 달리 일반적인 최선 노력 패킷 전달은 한 흐름의 일정한 지연이나 전송률을 자동 보장하지 않는다.

패킷 하나를 보내는 동안 다른 패킷이 기다릴 수 있고 버퍼가 차면 버릴 수도 있다. 패킷 교환이라는 선택만으로 모든 패킷이 반드시 도착하거나 순서가 유지되지는 않는다. 신뢰성과 혼잡 처리는 해당 계층의 추가 규칙으로 설명해야 한다.

2. 저장 후 전달과 파이프라인

이번 계산 모형의 라우터는 패킷의 모든 비트를 받은 뒤 다음 링크로 보내는 저장 후 전달 방식을 쓴다. 길이 L비트, 전송률 R비트/초이면 링크에 모든 비트를 밀어 넣는 시간이 L/R초다. 두 링크를 지난 한 패킷은 전파·처리·대기가 없을 때 2L/R 뒤 완전히 도착한다.

같은 크기 패킷 둘을 연속 보내면 라우터가 첫 패킷을 둘째 링크로 보내는 동안 출발지는 둘째 패킷을 첫 링크로 보낼 수 있다. 서로 다른 링크의 작업은 겹친다. 두 패킷 전체는 4L/R가 아니라 3L/R에 끝난다. 전송률이 다르거나 다른 트래픽·헤더·전파 시간이 있으면 이 시간표를 다시 구성해야 한다.

3. 계층은 서로 다른 질문을 담당한다

응용은 메시지 의미, 전송 계층은 프로세스 간 통신과 선택한 전송 서비스를, IP 계층은 네트워크 사이 패킷 전달을, 링크 계층은 인접 노드 사이 전달을 다룬다. 여기에 물리 신호를 별도 층으로 세는 5계층 설명도 있다. 계층 수는 쓰는 모형을 선언하며 OSI의 7계층 이름과 기계적으로 같다고 하지 않는다.

캡슐화는 상위 데이터에 해당 계층의 제어 정보를 붙여 하위 서비스로 보내는 방식이다. 수신측은 약속된 형식대로 이를 해석한다. 라우터는 보통 응용 메시지를 실행하지 않고 전달을 위한 정보를 처리하며 다음 링크의 프레임으로 다시 보낸다. IP의 홉 제한/TTL 같은 필드는 전달 중 바뀔 수 있다. 봉투 비유는 주소와 포함 관계에 유용하지만 전기 신호·동시 전송·프로토콜별 실패를 모두 설명하지 못한다.

중간 과정을 따라가는 예제

1000 B 패킷 두 개를 S→라우터→D로 연속 전송한다. 두 링크는 1Mbps이고 저장 후 전달, 전파·처리·대기·헤더 비용은 0, 다른 트래픽·손실은 없다.

  1. 각 패킷은 8000bit이고 한 링크의 전송 시간은 8000/10⁶s=8ms다.

  2. 0–8 ms: S가 첫 패킷을 라우터로 보낸다.

  3. 8–16 ms: 라우터는 첫 패킷을 D로, S는 둘째 패킷을 라우터로 동시에 보낸다.

  4. 16–24 ms: 라우터가 둘째 패킷을 D로 보낸다. 첫 패킷 완전 도착은 16 ms, 둘째는 24ms다.

전체 예상 완료 시간 24 ms. 같은 패킷 내부의 두 링크 전송은 순차지만 서로 다른 패킷의 링크 전송은 겹친다.

종이와 본문으로 직접 해보기

같은 조건에서 패킷을 세 개로 늘려 각 링크의 8 ms 시간 칸에 번호를 적어라. 이어 링크당 헤더가 20B이고 데이터 1000B인 패킷 하나의 두 링크 시간을 계산하라.

힌트 보기

첫 링크의 번호 1,2,3에 둘째 링크 번호 1,2,3이 한 칸 늦게 따라간다. 헤더도 전송 비트 수에 포함한다.

풀이 보기

첫 링크는 0–8:1,8–16:2,16–24:3. 둘째는 8–16:1,16–24:2,24–32:3이므로 전체 32ms다. 헤더를 포함하면 1020 B=8160 bit, 한 링크 8.16 ms, 한 패킷 두 링크 16.32ms다. 헤더 20B는 가상 수치이며 특정 IP/TCP 규격 길이가 아니다.

오해와 반례

패킷 교환이면 경로 전체가 예약되어 다른 통신 때문에 기다리지 않는다.

공유 출력 링크에 먼저 온 다른 패킷이 있으면 기다릴 수 있다. 예약이 없는 최선 노력 전달과 자원 예약은 서로 다른 서비스다. 패킷 단위 처리 자체가 고정 응답 시간을 보장하지 않는다.

답과 이유 보기

한 단계 더

심화: 같은 크기 패킷 N개와 같은 전송률의 저장 후 전달 링크 h개에서 위 가정을 유지하면 완료 시간은(N+h−1)L/R이다. 첫 패킷이 h칸을 지나고 이후 패킷이 한 칸마다 도착하는 시간표로 유도하라. 실제 망의 서로 다른 전송률·헤더·대기·전파·재전송은 이 단순식의 전제 밖이다.

소단원 1.2

지연·처리율·손실

같은 용량의 인터넷에서 영상 다운로드와 짧은 메시지 응답이 서로 다르게 느껴지는 이유는 무엇일까?

준비 개념과 학습 목표

준비 개념

  • 지연은 사건 사이의 경과 시간이다. 처리율은 구간 동안 실제 전달한 양을 그 시간으로 나눈 비율이다.

  • 전송 시간 L/R과 전파 시간 d/v는 각각 비트 수/전송률과 거리/신호 전파 속도로 계산한다.

  • 대기열은 출력 자원이 바쁠 때 순서를 기다리는 저장 공간이며 용량이 유한할 수 있다.

학습 목표

  • 처리·대기·전송·전파 지연을 단위와 함께 합한다.

  • 링크 전송률·관측 처리율·유효 데이터 처리율을 구별한다.

  • 유한 버퍼 손실과 왕복 요청의 가상 모형을 추적한다.

1. 시간을 네 원인으로 나누어 본다

패킷은 헤더 검사 등의 처리, 출력 차례 대기, 비트 전송, 신호 전파에 시간을 쓴다. 한 패킷의 특정 홉에 대한 단순 지연 합은 d_proc+d_queue+L/R+d/v다. 다중 홉과 패킷 파이프라인에서는 어떤 작업이 겹치는지 함께 고려해야 전체 파일의 완료 시간을 맞게 계산한다.

전송률을 높이면 L/R는 줄지만 거리와 매질에 따른 d/v는 그대로일 수 있다. 대기와 서버 처리도 자동으로 줄지 않는다. 왕복시간 RTT는 요청과 응답이 오가는 시간이며 방향별 시간·대기·처리가 달라 한 방향 시간을 항상 정확히 2배로 계산할 수는 없다.

2. 무엇을 분자에 넣었는가

링크 용량은 이용 가능한 전송률의 상한 모형이고 처리율은 관측 구간에서 실제 전달한 비트/시간이다. 응용에 필요한 데이터만 세는 유효 처리율은 헤더·재전송·중복을 제외한 양으로 정의한다. 측정 구간·방향·데이터의 포함 범위를 선언해야 서로 비교할 수 있다.

10Mbps와 2 Mbps 링크를 순차로 지나가는 긴 흐름은 다른 병목이 없더라도 지속 처리율이 2Mbps를 넘을 수 없다. 이것은 단일 패킷의 지연과 다르다. 실제 혼잡 제어·경쟁 흐름·손실·서버 제한이 있으면 더 작아질 수 있으며 명목 용량만 보고 응용 속도를 확정할 수 없다.

3. 밀린 패킷과 버린 패킷

버퍼가 유한하면 순간 유입이 처리보다 많을 때 넘치는 패킷을 버릴 수 있다. 평균 도착률이 평균 서비스율보다 작아도 큰 순간 버스트는 손실을 만들 수 있다. 손실률은 정한 관측 구간에서 잃은 수/보낸 수로 계산하며 “언제나 정확히 그 비율”이라는 확률 보장은 아니다.

전송 성공과 업무 완료도 구별한다. 손실 없는 연결이라도 서버 계산이 오래 걸릴 수 있다. TCP의 복구가 응용 바이트 순서를 제공하려 하지만 영구 장애에서 무조건 결과가 돌아온다는 뜻은 아니다. 이 단원은 가상 지연·유한 버퍼 모형의 정확한 계산이며 실제 망의 손실 확률 추정은 하지 않는다.

중간 과정을 따라가는 예제

가상 응용은 아주 작은 요청 뒤 왕복 전파 등 고정 시간 40ms를 기다리고 1 MB 파일을 받는다. 서버 처리·헤더·대기·손실·설정 비용은 0, 파일은 한 병목 링크에서 8Mbps로 지속 전송된다. 고정 40ms는 파일 전송 시간과 합산하는 직렬 지연으로 가정한다. 전송률을 16Mbps로 바꾸면?

  1. 1 MB=10⁶B=8×10⁶bit다.8Mbps에서 파일 전송은 1s다.

  2. 전체 시간은 1 s+0.040 s=1.040s다.

  3. 16Mbps에서는 전송 0.5 s, 전체 0.540s다.

  4. 전체 시간은 1.040/0.540≈1.926배 빨라졌다. 정확히 절반인 0.520s와는 다르다.

예상 시간 1.040 s→0.540 s. 링크 전송률 2배가 고정 지연까지 2배 개선하지는 않는다. 관측 구간을 전체 응답으로 정한 유효 처리율은 8 Mbit/1.040 s≈7.692Mbps다.

종이와 본문으로 직접 해보기

가상 출력 링크는 한 패킷 처리에 10 ms, 처리 중 1개 외 기다리는 공간 1개다. t=0에 p1, p2, p3가 이 순서로 도착하고 첫 패킷은 즉시 서비스를 시작한다. 처리·전파는 추가 0이며 이후 도착은 없다. 버린 수·손실률·각 수락 패킷 완료시각을 구하라.

힌트 보기

처리 중 자리와 대기 자리를 구별한다. 동시에 온 패킷의 처리 순서는 문제에서 지정했다.

풀이 보기

p1이 0–10 ms 처리, p2는 유일한 대기 자리에 들어가 10–20 ms 처리, p3는 대기 공간이 꽉 차 버린다. 완료시각 10 ms,20 ms, 손실 1/3이다. p2의 대기 지연 10ms와 전송/서비스 10ms를 구별한다. 이 3개 표본의 1/3은 망 전체의 확정 손실 확률이 아니다.

오해와 반례

대역폭이 두 배면 응답 지연도 언제나 절반이다.

파일 전송이 아닌 40 ms 고정 부분이 남아 예제의 1.040s는 0.540s가 된다. 작은 메시지일수록 고정 지연의 비중이 더 클 수 있다. 지연·처리율·손실 중 무엇을 개선하려는지 먼저 정해야 한다.

심화: 가상 stop-and-wait는 데이터 패킷 1000B를 8Mbps로 보내고 전송 완료 뒤 ACK가 돌아올 때까지 고정 40 ms 기다린다. ACK 전송·오류는 무시한다. 한 주기 41ms에 8000bit를 보내 유효 처리율은 약 0.195Mbps다. 여러 패킷을 동시에 비행시키는 윈도우가 왜 필요한지 생각하고, 이 수치를 실제 TCP 측정값으로 해석하지 않는다.

소단원 1.3

프로토콜·서비스·인터페이스

“보내기 함수가 성공했다”는 말만으로 상대 앱이 메시지를 처리했음을 알 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 프로토콜은 통신 상대 사이 메시지 형식·순서·사건에 대한 동작 규칙이다. 상태는 규칙이 다음 행동을 결정할 때 기억하는 정보다.

  • 서비스는 상위 이용자에게 제공하는 기능과 보장이다. 인터페이스는 그 기능을 요청하고 결과를 받는 사용 방식이다.

  • ACK는 어떤 수신 또는 처리 사실을 확인하는 메시지다. 무엇을 확인하는지는 해당 프로토콜이 정의하며 이름만으로 디스크 저장·업무 완료를 뜻하지 않는다.

학습 목표

  • 상대끼리의 규칙과 같은 장치 내부 API를 구별한다.

  • 계층의 서비스 보장 범위와 응용의 완료 의미를 구별한다.

  • ACK 손실·재시도·중복을 가상 상태기계로 추적한다.

1. 누구와의 약속인가

같은 계층의 원격 상대와 주고받는 바이트 형식·메시지 순서·오류 대응은 프로토콜이다. 로컬 응용이 운영체제에 send를 호출하는 함수 형태는 인터페이스다. 상위에 어떤 통신 기능을 제공하는지는 서비스다. 세 개념은 연결되지만 같은 말이 아니다. 다른 로컬 언어의 API라도 원격 바이트 규칙을 일치시켜 같은 프로토콜로 통신할 수 있다.

계층 n은 하위 서비스를 이용해 자신의 프로토콜을 구현하고 상위에 새 서비스를 제공한다. 요청 인수·결과·오류 계약을 정의한 인터페이스는 이용 방법을 정하지만 원격 상대가 그 정보를 어떻게 해석해야 하는지는 프로토콜이 정한다. 함수 이름을 같게 붙였다고 두 구현이 상호 운용되는 것은 아니다.

2. TCP의 바이트 서비스와 응용 메시지

TCP는 연결된 응용 사이에 순서 있는 바이트 스트림 서비스를 제공한다. 응용이 두 번 보내는 호출을 했다는 경계를 수신측의 두 번 읽기 경계로 보존하지 않는다. 응용은 길이 필드·구분자 등 메시지 경계를 별도로 표현해야 한다. TCP 순서·재전송 기능도 원격 업무의 정확히 한 번 완료 계약은 아니다.

로컬 전송 함수가 바이트를 받아들인 사실, 상대 전송 계층이 받은 사실, 상대 응용이 해석한 사실, 데이터가 영속 저장된 사실은 서로 다르다. 프로토콜에서 어떤 ACK를 쓰는지와 실패·종료 시 어떤 결과를 보고하는지 정의해야 완료 의미가 명확해진다. 영구 연결 실패는 응용에 오류로 나타날 수 있다.

3. 재시도에 필요한 상태와 가정

가상 메시지 프로토콜은 DATA(id, 값), ACK(id)를 쓴다. 수신측은 같은 id를 처음 받으면 기록에 한 번 추가하고 ACK를 보낸다. 이미 처리한 id면 다시 추가하지 않고 ACK만 재전송한다. 발신측은 시간 내 ACK가 없으면 같은 id로 재전송한다. 네트워크가 ACK를 잃을 수 있어 ACK 부재만으로 DATA 미수신을 결론낼 수 없다.

이 모형은 연결된 한 발신자, 충돌하지 않는 ID와 같은 ID 재시도에서 바뀌지 않는 값, 수신측의 처리 ID 기억이 재시도 동안 유지됨, 순차 원자적 상태 변경, 프로세스 장애 없음으로 제한한다. 그 기억을 잃으면 중복 기록이 생길 수 있다. 기록을 디스크에 영속 저장했다는 보장도 없다. 상태·수명·실패 모델을 빼고 “ID가 있으니 언제나 정확히 한 번”이라고 주장해서는 안 된다.

중간 과정을 따라가는 예제

위 가상 프로토콜에서 발신측이 DATA(7, A)를 보낸다. 수신 기록·처리 ID 집합은 처음 비어 있고 첫 ACK만 손실된다. 수신 상태는 재시도까지 유지된다.

  1. 수신측이 id7을 처음 받아 기록[A], 처리 ID{7}로 만들고 ACK7을 보낸다.

  2. ACK7이 손실되어 발신측은 확인하지 못한다. 기록[A]는 이미 존재한다.

  3. 발신측이 같은 DATA7을 재전송한다. 수신측은 7이 집합에 있어 추가하지 않고 ACK7만 보낸다.

  4. 두 번째 ACK가 도착하면 발신측이 완료 확인을 한다. 수신 기록은 계속[A]다.

DATA 두 번 수신, 기록 추가는 한 번이다. ACK 성공은 이 가상 프로토콜의 메모리 기록 처리 확인이며 영속 저장·실제 업무 완료까지 주장하지 않는다.

종이와 본문으로 직접 해보기

첫 DATA7 처리 뒤 수신측이 장애로 처리 ID 집합만 잃고 기록[A]는 남았다고 모형을 바꿔라. ACK 손실 후 재시도하면 어떤 기록이 남는가? 프로토콜 보장이 실패한 전제를 적어라.

힌트 보기

다시 받은 7은 빈 ID 집합에서 처음 받은 것으로 보인다. 원래 모형의 상태 유지 가정과 비교한다.

풀이 보기

다시 A를 추가해 기록[A, A], ID{7}가 된다. 처리 ID와 기록을 함께 일관되게 유지한다는 전제가 깨졌다. 실제 내구성 있는 중복 방지는 ID·결과의 원자적 영속 기록과 복구 정책 등을 추가로 설계해야 한다. 함수를 한 번 호출하는 문법만으로 이 보장이 생기지 않는다.

오해와 반례

ACK가 없으면 상대는 데이터도 받지 않았다.

예제에서는 DATA가 처리되어[A]가 남았지만 ACK만 손실됐다. 타임아웃은 현재 확인을 못 했다는 관측이며 상대 처리 여부의 확정 증거가 아니다. 재시도는 중복 가능성을 고려해야 한다.
