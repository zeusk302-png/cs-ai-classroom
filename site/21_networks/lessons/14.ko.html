패킷 캡처와 필터

화면에서 패킷을 숨기면 저장된 패킷도 사라질까?

조건을 좁힌 뒤에는 어떤 질문을 더 이상 답할 수 없을까요?

사진에서 사람 몇 명을 가리는 일과 처음부터 그 사람이 없는 사진만 찍는 일은 다릅니다. 캡처 필터는 수집의 입구를, 표시 필터는 이미 수집한 자료의 화면을 제한합니다. 먼저 원자료의 범위를 적고 그 안에서 조건을 적용하세요.

아래 P1부터 P6은 자체 패킷 표입니다. 각 행에는 IPv4 헤더 하나와 지정한 전송 헤더 하나만 있고, TCP 플래그가 정상 해석된다고 가정합니다. 실제 캡처나 숨겨진 내부 헤더를 분석한 기록은 아닙니다. A·B·C·D는 서로 다른 주소입니다.

먼저 확인할 개념
  • 수집 전에 거르기와 수집 후 숨기기

    저장된 관찰의 범위를 표시 결과와 구별할 때 사용합니다.

  • 응용 메시지의 경계와 완료 기준

    소켓 상태나 수신 조각을 응용 요청의 정확한 완료와 구별할 때 사용합니다.

캡처는 한 지점에서 얻는 관찰이다

패킷 분석기는 선택한 인터페이스나 저장된 자료에서 통신 내용을 보여 준다. 관찰 위치에 따라 보이는 내용이 다르다. 클라이언트에서 보인 패킷과 서버에서 처리한 요청은 같은 사건을 다른 위치에서 본 기록이며 서로 빠진 구간이 있을 수 있다. 보지 못한 패킷이 네트워크 전체에 없었다고 단정하지 않는다.

인터페이스·시각·수집 기간·필터·캡처 길이와 누락 여부를 함께 기록한다. 암호화된 통신의 패킷 길이나 주소가 보인다고 응용 본문이 평문으로 보이는 것은 아니다. 여기서는 자체 가상 패킷 표만 사용하며 실제 타인의 통신을 수집하지 않는다.

수집 전에 거르기와 수집 후 숨기기

Wireshark의 캡처 필터는 수집 대상을 제한하고 libpcap 문법을 사용한다. 표시 필터는 이미 가진 패킷에서 화면에 나타낼 대상을 고른다. 화면에서 숨겼다는 사실은 저장된 원자료를 지웠다는 뜻이 아니다. 캡처에서 제외한 자료는 이후 표시 필터를 풀어도 복원되지 않는다.

같은 목적도 두 문법으로 다르게 표현한다. TCP의 양쪽 포트 중 443을 고르는 캡처 조건은 tcp port 443이고 표시 조건은 tcp.port == 443이다. 복합 조건은 괄호로 의미를 분명히 적는다. 이 필터 문장은 의미를 설명하는 예이며 실제 도구에 입력해 실행한 결과는 아니다.

필드 존재와 값은 다른 질문이다

표시 필터 tcp.flags.syn은 SYN 필드의 존재를 묻는다. SYN이 1인 패킷만 원하면 tcp.flags.syn == 1처럼 값을 검사한다. 디코더가 필드를 보여 주는 것과 그 값이 참이라는 사실을 혼동하지 않는다.

주소나 포트 하나가 같아도 TCP·UDP, 방향, 연결의 다른 끝과 시점이 다를 수 있다. 필요한 조건을 더해 후보를 줄인 뒤 원자료와 맥락을 확인한다. 필터 일치는 공격·오류·응용 성공의 자동 판정이 아니다.

포트가 한쪽 끝에 있다는 조건과 목적지 포트라는 조건을 구별합니다. 각 행의 주소·프로토콜·플래그를 따로 확인한 뒤 AND 또는 OR로 합칩니다.

중간 과정을 따라가는 예제

자체 평범한 IPv4 패킷 표에서 P1은 TCP A:50000→B:443 SYN=1, P2는 TCP B:443→A:50000 SYN=1, P3은 TCP A:50000→B:443 SYN=0, P4는 UDP A:51000→B:443, P5는 TCP C:52000→D:80 SYN=1이다. 주소 A–D는 상징이다. TCP 양쪽 포트 443 캡처 후 SYN=1만 표시하는 두 단계의 대상을 구하라.

  1. 캡처 조건은 프로토콜 TCP이고 출발 또는 도착 포트가 443인 행이다. P1·P2·P3을 수집한다.

  2. UDP인 P4와 양쪽 포트 모두 443이 아닌 P5는 처음부터 제외한다.

  3. 수집된 세 행에 SYN 값 1 표시 조건을 적용하면 P1·P2만 보인다. P3은 수집 자료에는 남는다.

  4. 이 표는 각 행에 TCP 헤더가 하나인 모형이다. 터널처럼 같은 필드가 여러 번 있는 경우는 별도 필드 의미를 확인한다.

수집 3행, 표시 2행, 수집됐지만 숨은 행 1개다. 실제 pcap 파일이나 프로그램 출력이 아니다.

조건을 바꾸어 비교하기

수집 범위와 표시 범위의 교집합

전체 표에 캡처 필터 tcp port 443 and host A를 적용했습니다. 저장된 자료에서 ip.src == A and tcp.flags.syn == 1이라는 표시 조건을 적용하면 어떤 행이 보일까요? A는 실제 문장 입력에서는 그 주소 값으로 치환합니다.

  1. TCP 443인 P1·P2·P3·P4 중 양쪽 주소에 A가 있는 P1·P2·P3을 저장합니다.

  2. 저장된 세 행에서 출발 주소 A인 것은 P1·P3입니다. 그중 SYN=1은 P1뿐입니다.

  3. P2·P3은 화면에서 숨겨졌고 원자료에는 남아 있습니다. P4·P5·P6은 처음 수집에서 제외했습니다.

저장 3행, 표시 1행 P1입니다. 표시 조건을 풀면 P1·P2·P3을 다시 볼 수 있습니다.

비교할 점

전체 여섯 행에서 표시 조건만 적용했다면 P6도 맞습니다. 수집 단계가 이후 답할 수 있는 질문을 제한합니다.

방향과 응답 플래그를 함께 묻기

전체 표에서 TCP이며 목적지 포트 443이고 SYN=1, ACK=0인 행을 고릅니다.

  1. 목적지 443인 TCP는 P1·P3·P4입니다. P2는 출발지 포트가 443이라 제외합니다.

  2. SYN=1인 P1·P4를 남깁니다. 두 행 모두 ACK=0입니다.

  3. P5는 목적지 443이어도 UDP이므로 제외합니다.

P1·P4 두 행입니다. 대응하는 표시 문장은 tcp and tcp.dstport == 443 and tcp.flags.syn == 1 and tcp.flags.ack == 0입니다.

비교할 점

tcp.port == 443은 양방향 포트 조건입니다. 존재하는 tcp.flags.syn 필드만 검사하는 것도 SYN=1 검사와 다릅니다.

종이와 본문으로 직접 해보기

캡처부터 SYN=1인 해당 TCP만 수집하도록 바꿨다고 가정하라. 나중에 SYN 조건을 풀어 P3을 볼 수 있는가? 별도로 전체 다섯 행을 가진 표시 화면에서 TCP 또는 UDP 443 후보 수를 구하라.

힌트 보기

수집에 없던 행과 화면에서 숨은 행을 구별한다.

풀이 보기

처음부터 제외한 P3은 해당 수집 자료에서 복원되지 않는다. 전체 다섯 행을 이미 가졌다면 양쪽 포트 443의 TCP 또는 UDP는 P1·P2·P3·P4 네 행이다. P5는 포트 조건에서 빠진다.

오해와 반례

표시 필터로 민감한 패킷을 숨기면 공유할 캡처 파일도 안전해진다.

원자료에 숨은 패킷이 남을 수 있다. 공유 범위와 실제 파일 내용을 별도로 확인해야 하며 화면 필터를 자료 삭제로 해석하지 않는다.

연습 1 · 값과 상태 예측

전체 표에 tcp port 443 or host A라는 캡처 조건을 적용하면 몇 행인가요? AND 조건의 저장 결과와 비교하세요.

힌트 1

OR는 어느 한 조건만 맞아도 됩니다.

힌트 2

TCP 443 집합과 A가 있는 집합을 각각 적으세요.

풀이와 답 확인

  1. TCP 443은 P1·P2·P3·P4입니다.

  2. A가 있는 행은 P1·P2·P3·P5·P6입니다. 합집합은 여섯 행, 교집합은 세 행입니다.

OR는 6행, AND는 P1·P2·P3의 3행입니다.

흔한 오답에서 다시 생각하기

OR도 TCP 443인 네 행만 저장합니다.

두 번째 조건 host A는 프로토콜을 TCP로 제한하지 않습니다. P5와 P6을 다시 확인하세요.

연습 2 · 오류 찾아 고치기

P1·P2·P3만 저장된 파일에서 tcp.flags.syn을 입력한 뒤 P3이 보입니다. 필터가 고장 난 걸까요?

힌트 1

필드가 있는지와 그 값이 1인지를 나누세요.

힌트 2

P3에도 해석된 SYN 필드가 있고 값은 0입니다.

풀이와 답 확인

  1. 필드 존재 조건은 세 TCP 행 모두에 맞습니다.

  2. SYN 설정만 찾으려면 tcp.flags.syn == 1로 비교합니다.

고장이라고 결론 내리지 않습니다. 존재 검사에서는 세 행, 값 비교에서는 P1·P2 두 행입니다.

흔한 오답에서 다시 생각하기

SYN=0인 P3이 보이면 반드시 분석기 오류입니다.

요청한 조건이 값 비교가 아니었습니다. 먼저 필터 문장의 뜻을 고쳐야 합니다.

연습 3 · 직접 만들어 보기

처음에 TCP 443만 저장했습니다. 이후 UDP 443도 분석하고 싶습니다. 현재 파일에서 복원 가능한지와, 다음 수집의 새 조건을 쓰세요.

힌트 1

표시 필터는 없는 데이터를 만들지 않습니다.

힌트 2

프로토콜 두 조건을 OR로 합치세요.

풀이와 답 확인

  1. 현재 저장 집합 P1·P2·P3·P4에는 P5가 없습니다.

  2. 다음 수집의 조건은 (tcp port 443) or (udp port 443)입니다. 자체 표에서는 P1부터 P5까지 저장합니다.

현재 파일만으로 P5를 복원할 수 없습니다. 다음 수집은 5행을 대상으로 합니다.

흔한 오답에서 다시 생각하기

표시 조건 udp.port == 443이면 P5가 되살아납니다.

수집되지 않은 패킷은 표시 조건의 입력에 없습니다. 새 관찰이 필요합니다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

표시 결과 P1 한 행만 보이는 원파일을 공유하면 다른 행이 없어졌다고 보장할 수 있나요? 이 문제의 별도 내보내기 계약이 “선택한 P1 패킷만 담고 다른 패킷은 제외”라면 새 파일의 패킷 행 수는 얼마인가요?

힌트 1

화면의 숨김과 파일 내용의 제거를 구별하세요.

힌트 2

새 계약은 패킷 행만 말하며 메타데이터나 P1 본문을 지웠다고 하지 않습니다.

풀이와 답 확인

  1. 원파일에는 P1·P2·P3이 남아 있으므로 한 행만 있다고 보장할 수 없습니다.

  2. 명시된 새 내보내기 계약이면 패킷 행은 P1 하나입니다. P1 내용이나 별도 메타데이터의 민감성은 추가 검토가 필요합니다.

원파일 3행, 계약에 맞는 새 파일 1행입니다. 한 행이라는 사실만으로 모든 민감정보 제거를 인증하지 않습니다.

흔한 오답에서 다시 생각하기

표시 필터를 켠 원파일은 다른 패킷이 자동 삭제되어 안전합니다.

표시 필터는 원자료 삭제 계약이 아닙니다. 실제 공유 파일과 내보내기 범위를 확인하세요.

같은 표시 조건의 결과가 파일마다 다른 이유는?

설명 기준 확인

각 파일의 수집 집합이 다를 수 있습니다. 표시 조건은 그 파일에 실제 있는 행만 고릅니다.

포트 443이라는 값만으로 HTTPS 요청이 성공했다고 할 수 있나요?

설명 기준 확인

준비 개념과 학습 목표

준비 개념

관찰을 하나씩 통과했을 때 무엇까지 확인한 셈일까요?

복도에 불이 켜져 있다고 교실의 수업이 정상 진행된다고 단정할 수 없습니다. Echo 응답, TCP 연결, 응용 내용도 각각 다른 질문의 결과입니다. 대상 주소·주소족·시점이 같은지를 먼저 맞추세요.

다음 기록은 다섯 Echo 탐색과 별도 진단을 가상으로 만든 것입니다. 다섯 탐색에는 중복 응답이 없고, 제한 시간 안에 온 네 응답의 RTT가 6·8·10·12 ms입니다. 남은 하나는 무응답이며 0 ms 측정이 아닙니다.

먼저 확인할 개념
  • 수집 전에 거르기와 수집 후 숨기기

    저장된 관찰의 범위를 표시 결과와 구별할 때 사용합니다.

  • 응용 메시지의 경계와 완료 기준

    소켓 상태나 수신 조각을 응용 요청의 정확한 완료와 구별할 때 사용합니다.

한 도구의 성공은 한 조건의 증거다

ping은 ICMP Echo 요청에 대한 응답과 왕복 시간을 관찰한다. TCP 서비스가 그 포트에서 듣는지, 응용 인증이 성공하는지, 응답 내용이 맞는지까지 시험하지 않는다. 반대로 Echo 응답이 없다는 결과에는 ICMP 정책, 경로, 응답 제한과 시간 초과 등 여러 설명이 가능하다.

진단을 이름 해석→경로와 응답→TCP 연결→응용 요청처럼 질문 목록으로 나눈다. 같은 주소를 사용했는지, IPv4/IPv6가 같은지와 시험 시점을 적는다. 여기서는 실제 도구를 실행하지 않고 가상 기록을 읽는다.

중간 홉의 별표는 관찰 공백이다

traceroute는 TTL을 늘려 보낸 탐색에 대한 응답으로 중간 홉을 추정한다. 출력의 각 시간은 그 탐색의 왕복 시간이며 바로 옆 두 홉 사이 링크 지연을 직접 측정한 값이 아니다. 경로와 응답 정책이 달라질 수 있으므로 단순 차감으로 정확한 링크 지연을 만들지 않는다.

별표는 해당 탐색에서 정한 시간 안에 응답을 얻지 못했다는 뜻이다. 뒤 홉이 응답했는데 앞 홉의 별표만으로 그 장비가 모든 패킷을 버린다고 결론 내리면 모순을 놓친다. 탐색 종류·타임아웃·반복 횟수와 정책을 함께 본다.

로컬 소켓 목록과 원격 도달은 별개다

Linux ss는 소켓 상태와 통계를 보여 준다. 기본 목록과 listening 소켓을 보는 선택은 다르다. ss -l 같은 옵션은 로컬에서 듣는 소켓의 관찰에 도움을 준다. 이 명령 표기는 읽기 설명이며 여기서 실행하지 않는다.

127.0.0.1에만 묶인 TCP listening 소켓은 다른 기계가 서버의 네트워크 주소로 바로 접속하는 리스너와 다르다. 로컬 listening 기록이 있다고 원격 방화벽·라우팅·응용 성공을 보장하지 않는다. 반대로 연결 상태가 established여도 유효한 응용 응답을 받았다는 증거는 아니다.

중간 과정을 따라가는 예제

가상 Echo 탐색 4개 중 응답 3개의 RTT가 8·12·10 ms이고 하나는 시간 내 무응답이다. 별도 가상 traceroute는 TTL 1에서 2 ms, TTL 2에서 *, TTL 3에서 9 ms 응답이다. 같은 시점의 로컬 서비스는 127.0.0.1:9000에서만 listening이다. 각 기록으로 확정할 수 있는 사실을 적어라.

  1. Echo의 관찰 무응답 비율은 1/4=25%다. 응답 RTT 평균은 (8+12+10)/3=10 ms다. 무응답을 RTT 0으로 넣지 않는다.

  2. traceroute의 TTL 2 탐색은 응답을 못 받았고 TTL 3 탐색은 응답을 받았다. 중간 장비의 전체 고장을 확정하지 않는다.

  3. 9−2=7 ms를 홉 1에서 홉 3까지의 정확한 편도 링크 시간으로 부르지 않는다. 두 숫자는 각각 왕복 탐색이다.

  4. 로컬 127.0.0.1:9000 listening은 loopback 리스너의 증거다. 다른 기계의 직접 접근이나 웹 요청 성공은 아직 시험하지 않았다.

무응답 25%와 응답 평균 RTT 10 ms는 지정한 표의 통계다. 경로 고장 원인·원격 서비스 도달·응용 성공은 이 자료만으로 확정하지 않는다.

조건을 바꾸어 비교하기

분모가 다른 두 비율

다섯 Echo 탐색 중 네 응답이 6·8·10·12 ms입니다. 응답 평균과 관찰 무응답률, 응답 중 RTT 10 ms 이하 비율을 구하세요.

  1. 응답 평균은 36/4=9 ms입니다.

  2. 무응답률은 1/5=20%입니다. 무응답의 RTT는 평균에 넣지 않습니다.

  3. 응답 중 10 ms 이하인 것은 세 개이므로 3/4=75%입니다.

평균 9 ms, 무응답 20%, 응답 조건부 빠른 비율 75%입니다. 전체 탐색 중 시간 내 빠른 응답을 확인한 비율은 3/5=60%입니다.

비교할 점

75%와 60%는 질문의 분모가 다릅니다. 둘 중 하나를 근거 없이 전체 네트워크 손실률이나 모든 요청 성공률로 바꾸지 않습니다.

왕복 관찰을 링크 길이처럼 빼지 않기

별도 traceroute 표는 TTL 1 응답 15 ms, TTL 2 응답 4 ms, TTL 3 무응답, TTL 4 응답 18 ms입니다. 홉 1과 2 사이의 정확한 편도 지연이 얼마인가요?

  1. 4−15=−11 ms이지만 두 숫자는 서로 다른 탐색의 왕복 시간입니다.

  2. 응답 처리·귀환 경로·시점이 달라질 수 있으므로 이 차이는 정확한 편도 링크 측정이 아닙니다.

  3. TTL 3은 시간 내 응답이 없었으며 TTL 4에서는 응답을 받았습니다.

이 표만으로 편도 링크 지연을 확정할 수 없습니다. TTL 3 장비의 전체 단절도 확정하지 않습니다.

비교할 점

앞 단원의 양수 차감 반례를 넘어, 음수 차이가 나와도 관찰 자체가 곧 불가능한 것은 아니라는 점을 봅니다.

메시지 조각과 성능 숫자를 같은 완료 계약으로 읽을 수 있을까요?

택배 상자 여러 개가 한 번에 도착하거나 하나씩 나뉘어 와도 물건 목록은 같아야 합니다. TCP 스트림의 수신 조각도 메시지 경계와 같지 않습니다. 길이 헤더까지 나뉘는 경우를 따로 추적해 보세요.

기본 원고의 1바이트 길이 규약과 비교하기 위해 여기서는 자체 규약을 새로 정합니다. 길이 헤더는 2바이트 큰 엔디언이며 값은 256×첫 바이트+둘째 바이트입니다. 본문 길이는 1부터 6만 허용합니다. 완전한 헤더가 나오면 범위를 검사하고, 부족한 헤더나 본문은 기다리다가 EOF에서 불완전 오류로 처리합니다.

먼저 확인할 개념
  • 수집 전에 거르기와 수집 후 숨기기

    저장된 관찰의 범위를 표시 결과와 구별할 때 사용합니다.

  • 응용 메시지의 경계와 완료 기준

    소켓 상태나 수신 조각을 응용 요청의 정확한 완료와 구별할 때 사용합니다.

먼저 송수신의 계약을 쓴다

프로토콜은 서로 어떤 바이트를 어떤 의미로 주고받는지 정한 계약이다. 길이·종류·허용 범위·순서·오류·종료를 먼저 적는다. TCP는 바이트 스트림이므로 한 번의 recv 결과가 하나의 메시지라는 가정으로 구현하지 않는다. 헤더나 본문이 나뉘고 여러 메시지가 한 번에 함께 올 수 있다.

아래 자체 규약은 첫 1바이트가 본문 길이이며 1부터 4까지만 허용하고 본문은 그 길이의 바이트다. 부족하면 다음 조각을 기다리고, 초과 길이는 즉시 오류로 처리한다. 연결 종료 때 미완성 메시지가 남으면 불완전 오류다. 실제 TCP 코드가 아니라 종이 파서 계약이다.

정확성 시험이 비교의 입장 조건이다

정상 메시지 하나뿐 아니라 헤더와 본문 분할, 두 메시지 결합, 범위 밖 길이, 도중 종료를 시험한다. 같은 바이트열을 다르게 나누어 제공해도 완성 메시지의 의미가 같아야 한다. 오류를 빠르게 무시하는 구현을 올바른 구현보다 빠르다고 칭찬하면 비교 목적을 잃는다.

부분 송신·부분 수신 처리와 종료 규약을 지키는지 먼저 확인한다. 응용 메시지를 처리한 완료와 커널이 송신 바이트를 받아들인 사실은 다르다. 단계별 기록을 구별해서 어떤 완료를 측정하는지 정한다.

속도 숫자는 분모와 경계를 가진다

처리율은 완료된 같은 단위의 작업량을 관찰 시간으로 나눈다. 유효 응용 바이트와 헤더·재전송까지 포함한 전송 바이트는 다른 분자다. 지연은 요청마다 시작·완료 경계를 정하고 실패·시간 초과를 평균에서 조용히 지우지 않는다.

실제 실험을 한다면 장치·연결·메시지 크기·동시성·기간·반복과 준비 시간을 기록해야 한다. 아래 숫자는 가상 비교표다. 작은 표의 계산이 실제 인터넷 성능이나 구현 성공을 인증하지 않는다. 성능보다 먼저 명시한 정확성 조건의 결과를 확인한다.

  1. 길이 2의 헤더 [0,2]와 길이 1의 헤더 [0,1]을 붙이면 [0,2,70,71,0,1,72]입니다.

  2. 가능한 조각은 [0], [2,70,71,0], [1,72]입니다. 첫 본문 완료 뒤 두 번째 헤더의 첫 바이트를 남깁니다.

총 7바이트의 스트림이며 예시의 세 조각에서도 [70,71]과 [72]로 복원합니다.

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

D의 네 표본 요청 지연이 20·20·20·100 ms라고 별도 관찰했습니다. 표본 평균과 50 ms 이하 비율을 구하고, “모든 요청 50 ms 이하” 조건을 이 네 표본만으로 통과했다고 할 수 있는지 쓰세요.

힌트 1

평균 합은 160 ms입니다.

힌트 2

100 ms 표본 하나가 모든 요청 조건의 반례입니다.

풀이와 답 확인

  1. 평균은 160/4=40 ms이며 네 표본 중 세 개만 50 ms 이하입니다.

  2. 표본 비율은 3/4=75%이고 관찰한 100 ms 요청은 모든 요청 조건을 위반합니다. 전체 99개 완료 지연 분포는 이 네 값만으로 만들 수 없습니다.

평균 40 ms, 네 표본의 기준 충족 75%, 모든 요청 50 ms 이하 조건은 통과하지 못합니다.

평균 40 ms이므로 모든 요청이 50 ms 이하입니다.

다른 문제에 적용하기

별도 가상 수업 실험입니다. TCP 443과 host A를 AND로 수집한 P1·P2·P3 중 SYN=1만 표시했습니다. Echo는 다섯 탐색에 네 응답 6·8·10·12 ms이며 중복 없습니다. 새 2바이트 길이 규약의 스트림 [0,2,70] 뒤 EOF입니다. 저장·표시 행 수, Echo 평균과 무응답률, 파서 결과를 적고 “서비스 정상”이라는 종합 결론을 낼 수 있는지 쓰세요.

힌트 1

SYN=1의 P1과 P2를 다시 확인하고, 표시에서 숨은 P3이 파일에서 삭제됐는지 구별하세요.

힌트 2

길이 2의 본문이 몇 바이트 왔는지 세고, 서로 다른 관찰을 응용 성공으로 합치지 마세요.

풀이와 답 확인

  1. 저장 행은 3개이며 SYN 값 1인 P1·P2 두 행을 표시합니다. P3은 원자료에 남습니다.

  2. Echo 응답 평균은 36/4=9 ms, 관찰 무응답률은 1/5=20%입니다.

  3. 헤더 [0,2] 뒤 본문 [70] 한 바이트뿐이어서 EOF에서 본문 불완전 오류입니다.

  4. 필터 통계나 Echo 응답은 메시지 계약 위반을 없애지 않습니다. 이 사례의 응용 메시지는 정상 완료하지 않았습니다.

저장 3행/표시 2행, 응답 평균 9 ms/무응답 20%, 본문 불완전 오류입니다. 응용 정상 완료 기준은 실패하며, 네트워크 전체 고장 원인을 이 표만으로 단정하지 않습니다.
