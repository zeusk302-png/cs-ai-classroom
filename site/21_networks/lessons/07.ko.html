소단원 7.1

IPv4·IPv6와 서브넷

주소가 같은 동네인지 숫자만 보고 판단할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 비트는0/1이고 8비트 한 옥텟은0부터255다.

  • 접두(prefix)는 주소 왼쪽의 공통 비트다.

학습 목표

  • 마스크로 IPv4 블록을 구한다.

  • IPv6 압축 표기를 복원한다.

호스트 수가 다른 세 모임에 같은 크기의 주소 블록을 주어야 할까?

새 주소 배치 모형은 문서용 198.51.100.0/24 안에 일반 브로드캐스트 서브넷 세 개를 만든다. 각 모임에는 호스트 주소 60개, 28개, 12개가 필요하다. 여기서 호스트 수는 게이트웨이 등 배정해야 할 인터페이스를 모두 포함한 요구량이다. 실제 주소를 장비에 설정하지 않는다. 큰 요구부터 배치하면 60에는 /26의 62개, 28에는 /27의 30개, 12에는 /28의 14개를 쓸 수 있다.

첫 블록은 .0–.63, 둘째는 .64–.95, 셋째는 .96–.111이다. 각각 첫 주소와 마지막 주소를 제외한 호스트 범위가 생긴다. 소비한 전체 주소는 64+32+16=112개지만 필요한 호스트는 100개다. 사용 가능한 호스트 합 106과 요구 100의 차이 6개, 블록마다 두 개씩의 예약 주소 6개를 분리하면 112=100+6+6으로 설명할 수 있다.

빈 구간 .112–.255는 144개다. 144는 2의 거듭제곱이 아니므로 하나의 정확한 CIDR 블록으로 쓸 수 없다. .112/28의 16개와 .128/25의 128개로 정확히 덮을 수 있다. 표기의 접두가 정렬되는지와 실제 범위가 겹치는지 둘 다 확인한다. 같은 블록 계산은 인터넷에서 실제로 통신할 수 있다는 증거가 아니다.

먼저 확인할 개념
  • 접두와 마스크

    블록 크기와 비트 정렬을 앞 설명에서 확인한다.

  • 주소와 실제 통신의 구별

    블록 배치만으로 반환 경로와 서비스 성공을 판정하지 않는다.

주소와 접두

IPv4 주소는32 비트를 점으로 나눈 네 옥텟으로 쓴다. /p는 왼쪽 p 비트를 블록의 접두로 고정한다는 뜻이며 남은32−p 비트는 블록 안에서 달라진다. 주소 하나만으로 접두 길이를 추측하지 않는다.

마스크는 앞 p 비트1, 뒤 비트0이다. 주소와 마스크를 비트 AND하면 블록의 첫 주소를 구한다. 블록 크기는2^(32−p)이므로 아무 숫자에서나 같은 크기의 블록이 시작하는 것은 아니다.

사용 주소와 전체 주소

통상적인 IPv4 브로드캐스트 서브넷은 맨 처음을 네트워크 주소, 맨 끝을 브로드캐스트 주소로 사용하여 그 사이를 호스트에 배정한다. 이 단원 예제는 주소 수가 4보다 큰 일반 서브넷(p≤29)에서 이 규칙을 사용한다.

2^(32−p)−2를 모든 p에 기계적으로 적용하면 안 된다. /31 점대점 링크와 /32 단일 주소는 용도가 다르다. 같은 접두에 속한다는 계산은 실제 링크 연결·라우팅·보안 허용까지 보장하지 않는다.

IPv6 숫자를 읽기

IPv6는128 비트를16진수 16비트 묶음 여덟 개로 쓴다. 묶음 앞의0은 생략할 수 있고 연속0 묶음을 ::로 한 번 압축할 수 있다. 두 번 쓰면 어느 구간에 몇 묶음의0을 채울지 모호하다.

IPv6 /p도 왼쪽 p 비트의 접두이며 전체 주소 수는2^(128−p)다. IPv4의 브로드캐스트 호스트 수 공식을 그대로 옮기지 않는다. 표기 압축은 주소 비트를 줄이는 것이 아니라 같은128 비트의 글자 표현을 줄인다.

요구량에는 예약 주소를 넣지 않는다. 마지막 열의 전체 주소 합과 호스트 합을 별도로 더한다. /28의 시작은 마지막 옥텟에서 16의 배수여야 한다.

중간 과정을 따라가는 예제

문서용 IPv4 192.0.2.150/26의 마스크·블록·일반 호스트 범위를 구한다. IPv6 2001:db8:0:0:0:0:0:5도 압축한다.

  1. /26은 마지막 옥텟의 앞2비트까지 고정하여 마스크255.255.255.192다. 150=10010110₂,192=11000000₂의 AND는128=10000000₂다.

  2. 남은6비트로64 주소, 블록은192.0.2.128부터191이다. 일반 호스트는129부터190,62개다.

  3. IPv6의 여덟 묶음 중 3번째부터7번째가0이므로 2001:db8::5로 쓴다. ::는 여기서 다섯 묶음이다.

IPv4 블록192.0.2.128/26, 일반 호스트62개. IPv6 압축은2001:db8::5다.

조건을 바꾸어 비교하기

빈 공간을 정확히 덮는다

.112–.255를 추가 할당 없이 CIDR로 표현하라.

  1. .112는 16의 배수이고 .112–.127을 /28로 덮는다.

  2. .128은 128의 배수이며 .128–.255를 /25로 덮는다.

198.51.100.112/28과 198.51.100.128/25로 덮는다. 전체 주소는 144개다.

비교할 점

하나의 /24는 이미 배정한 .0–.111도 포함한다. 주소 수를 맞추는 것과 정확한 범위를 맞추는 것은 다르다.

IPv6 접두의 부분 묶음

2001:db8:1234:abcd::9/60과 2001:db8:1234:abce::1/60의 접두를 구하라.

  1. 처음 세 묶음은 48비트이고 네 번째 묶음의 상위 12비트를 더 고정한다.

  2. abcd와 abce의 하위 4비트를 0으로 만들면 둘 다 abc0이 된다.

둘 다 2001:db8:1234:abc0::/60이다. /64에서는 네 번째 묶음이 각각 abcd와 abce로 달라진다.

비교할 점

::를 먼저 여덟 묶음으로 복원한다. 끝의 숫자 9가 네 번째 묶음으로 이동하는 것은 아니다.

종이와 본문으로 직접 해보기

192.0.2.64/26을 /27 두 블록으로 나누고 각 일반 호스트 수를 적는다. 2001:db8:1::9를 여덟 묶음으로 복원한다.

힌트 보기

한 비트를 접두에 추가하면 크기는 절반이다. IPv6에서 보이는 네 묶음을 먼저 센다.

풀이 보기

두 블록은64/27과96/27로 각각32주소다. 일반 호스트는65–94와97–126,각30개다. IPv6는2001:db8:1:0:0:0:0:9로 복원하여 ::가 네 묶음임을 확인한다.

오해와 반례

/26은 언제나26 개의 주소다.

/26은 고정 비트 수이며 주소 수는2^6=64 다. 또 /31을 같은 호스트 공식에 넣어0이라고 결론 내리면 점대점 용도를 놓친다.

스스로 풀어보기

먼저 답과 이유를 적고, 필요한 만큼 힌트를 한 단계씩 열어 보세요.

연습 1 · 값과 상태 예측

198.51.100.94와 198.51.100.97이 위 세 블록 중 어디에 속하고 각각 일반 호스트 주소인지 판단하라.

힌트 1

둘째는 .64–.95다.

힌트 2

셋째의 예약 주소는 마지막 옥텟이 96인 주소와 111인 주소다.

풀이와 답 확인

  1. .94는 둘째 호스트 범위 .65–.94의 끝이다.

  2. .97은 셋째 호스트 범위 .97–.110의 시작이다.

둘 다 일반 호스트지만 서로 다른 접두에 속한다.

흔한 오답에서 다시 생각하기

가까운 숫자이므로 같은 서브넷이다.

거리 대신 각 접두의 마스크와 범위를 비교한다.

연습 2 · 오류 찾아 고치기

둘째 블록을 198.51.100.80/27이라고 적고 마지막 옥텟 80부터 111까지 배정했다. 오류를 고쳐라.

힌트 1

/27의 블록 크기는 주소 32개다.

힌트 2

80과 마스크 마지막 옥텟 224의 AND를 계산한다.

풀이와 답 확인

  1. 80의 이진 표기는 01010000이고 224의 이진 표기는 11100000이다. AND 결과는 64다.

  2. 마지막 옥텟 80에 /27을 붙인 표기가 가리키는 실제 블록은 64부터 95까지다.

둘째의 정식 블록은 .64/27이다. .80–.111은 하나의 정렬된 /27이 아니다.

흔한 오답에서 다시 생각하기

시작 주소에 32를 더하면 어느 주소에서도 /27을 만들 수 있다.

크기뿐 아니라 시작 주소의 하위 5비트가 0인지 확인한다.

연습 3 · 직접 만들어 보기

60·28·12 호스트 요구를 모두 /26으로 배정하는 대안과 현재 배치를 비교하라.

힌트 1

/26 하나는 전체 주소 64개와 일반 호스트 주소 62개를 갖는다.

힌트 2

예약 주소와 남는 호스트 주소를 따로 센다.

풀이와 답 확인

  1. 균등 배치는 마지막 옥텟 0, 64, 128에서 시작하는 세 /26이다. 전체 주소 192개와 일반 호스트 주소 186개가 있으므로 요구량 100개를 빼면 호스트 주소 86개가 남는다.

  2. 현재 배치는 전체 주소 112개와 호스트 주소 106개다. 남는 호스트 주소는 6개이며 두 배치 모두 예약 주소는 6개다.

균등 배치의 전체 소비량은 주소 80개만큼 더 크다. 주소 절약과 관리 정책의 선택을 구별한다.

흔한 오답에서 다시 생각하기

큰 블록이면 요구가 같아도 실제 장비가 더 많아진다.

용량과 실제 배정량은 서로 다른 값이다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

2001:db8:1234:abcd::9와 2001:db8:1234:abce::1은 /60과 /64에서 각각 같은 블록에 속하는가? /60을 /64로 나누면 몇 블록인가?

힌트 1

/60은 네 번째 묶음의 하위 4비트를 고정하지 않는다.

힌트 2

접두를 4비트 늘리면 선택지는 2^4개다.

풀이와 답 확인

  1. /60 접두의 네 번째 묶음은 모두 abc0이다. /64 접두에서는 각각 abcd와 abce다.

  2. abc0부터 abcf까지 /64 블록 16개가 있다.

/60에서는 같고 /64에서는 다르다. /64 블록이 16개라는 사실은 실제 장비가 16대라는 뜻이 아니다.

흔한 오답에서 다시 생각하기

압축 표기에 콜론이 적으면 비트 수도 적다.

글자 수를 바꾸어도 각 주소는 128비트다.

내 말로 설명하기

144개의 연속 주소가 왜 한 CIDR이 아닌가?

설명 기준 확인

단일 CIDR의 전체 크기는 2의 거듭제곱이며 시작도 그 크기에 맞게 정렬되어야 한다.

호스트 요구량에 게이트웨이를 언제 더하나?

설명 기준 확인

요구의 정의를 먼저 확인한다. 이번 요구량은 이미 모든 배정 인터페이스를 포함하므로 다시 더하지 않는다.

한 단계 더

192.0.2.128/26의 /27 두 블록과192.0.2.192/26을 그려 보라. 같은 크기 블록의 시작점 정렬과 주소 전체 수/호스트 수를 구별한다. /64 IPv6의2^64는 배정된 실제 장비 수가 아님도 설명한다.

출처와 확인 범위
  • IETF RFC4632 §3.1

    실제 32 비트 CIDR 접두 길이·마스크·2의 거듭제곱 블록과 /31 예외 표를 읽었다. 자체 주소의 AND와 분할은 종이 계산이다.

  • IETF RFC4291 §2.2–2.3

    실제 16비트 8묶음·선행0 생략·한 번의 :: 및 접두 길이 본문을 읽었다.

  • IETF RFC8200 §1/2/4.5/5

    실제 128 비트 주소·link/path MTU 정의·송신자만의 IPv6 분할·1280 최소 링크 MTU 본문을 읽었다.

소단원 7.2

프래그먼트·MTU

한 링크가 큰 봉투를 통과시키지 못하면 IP는 어떻게 할까?

준비 개념과 학습 목표

준비 개념

  • 패킷은 헤더와 데이터로 구성된다.

  • MTU는 해당 링크에서 전달 가능한 IP 패킷 크기 한도다.

학습 목표

  • IPv4 조각의 offset/MF를 계산한다.

  • IPv4와 IPv6의 분할 위치를 구별한다.

이미 나뉜 조각이 더 작은 링크에 도착하면 offset은 다시 0부터 시작할까?

새 IPv4 모형은 옵션 없는 헤더 20바이트, 원래 데이터 2000바이트, DF=0을 가정한다. 첫 링크의 MTU가 1500바이트이면 데이터 길이 1480바이트와 520바이트인 두 조각으로 나눈다. 첫 조각의 offset은 0이고 MF는 1이다. 둘째 조각의 offset은 185이고 MF는 0이다. 다음 링크의 MTU가 620바이트이면 데이터 상한은 600바이트다. 이는 8의 배수이므로 앞 조각의 데이터 1480바이트를 600바이트, 600바이트, 280바이트로 다시 나눈다.

재분할 offset은 부모 조각 내부가 아니라 원래 데이터 2000바이트의 위치를 가리킨다. 새 조각의 시작 위치 0, 600, 1200을 8로 나누면 offset은 각각 0, 75, 150이다. 이 세 조각의 MF는 모두 1이다. 셋째는 부모의 마지막 부분이지만 원래 데이터의 시작 위치 1480에서부터 길이 520바이트인 조각이 아직 남아 있기 때문이다. 마지막 조각은 헤더 포함 540바이트로 MTU 620바이트 이하여서 offset 185와 MF=0을 유지한다.

최종 네 조각의 전체 길이는 각각 620바이트, 620바이트, 300바이트, 540바이트다. 합계 2080바이트를 데이터 2000바이트와 헤더 80바이트로 나눈다. 첫 링크에서 보낸 길이 2040바이트와 둘째 링크에서 보낸 길이 2080바이트를 더하면 4120바이트다. 이는 목적지에서 복원하는 데이터 2000바이트와 다르며 링크 계층 헤더와 재전송을 제외한 경로별 전송량 모형이다.

먼저 확인할 개념
  • offset과 MF

    원래 데이터 기준의 8바이트 단위와 마지막 표시를 재분할에 적용한다.

  • IPv4와 IPv6의 구별

    같은 작은 MTU 예제를 IPv6 라우터 분할로 옮기지 않는다.

경로에서 가장 작은 한도

링크마다 MTU가 다를 수 있으며 경로 MTU는 그 경로 링크 MTU들의 최솟값이다. 응용 데이터만의 길이와 헤더까지 포함한 IP 패킷 길이를 구별해야 넘침 여부를 판단한다. MTU는 한 링크가 전달하는 패킷의 최대 크기다. DF는 분할 금지, MF는 뒤에 조각이 더 있다는 표시다.

IPv4에서 분할을 허용한 큰 데이터그램은 라우터에서 더 작은 조각으로 나뉠 수 있다. DF가 1이면 분할 대신 폐기 대상이다. 재조립은 목적지에서 하고 IP 자체가 잃은 조각의 재전송을 보장하지 않는다.

조각의 자리 번호

IPv4 조각마다 헤더가 붙고 offset은 원래 데이터 시작점에서8 바이트 단위 거리다. 마지막을 제외한 데이터 길이를8의 배수로 골라 다음 조각의 offset을 정수로 표현한다. MF1은 뒤에 더 남은 조각이 있다는 뜻이다.

같은 데이터그램의 조각은 source/destination/protocol/identification을 함께 사용해 구별한다. 도착 순서가 바뀌어도 위치 정보로 배열할 수 있지만 일부가 빠지면 완전한 원래 데이터가 되지 않는다. 이 예제는 옵션 없는20 바이트 헤더와 중복·겹침 없는 분할이다.

IPv6와 경로 조절

IPv6 라우터는 IPv6 계층에서 분할하지 않는다. 송신자는 경로에 맞춘 작은 패킷을 보내거나 필요한 경우 Fragment 헤더를 사용하여 분할한다. 기본40 바이트 헤더와 추가 헤더의 비용도 계산에 포함한다.

IPv6의 최소 링크 MTU는1280이다. 더 작은 프레임만 전달 가능한 링크는 IPv6 아래 계층에서 그 크기를 지원하도록 처리해야 한다. 따라서 작은 교육 MTU를 IPv6 표준 링크인 것처럼 해석하지 않는다. 경로 MTU 정보가 변할 수도 있다.

조건을 바꾸어 비교하기

부모의 MF를 보존한다

데이터 길이 520바이트, offset 185, MF=0인 둘째 부모 조각이 MTU 420바이트인 링크를 지나면 어떻게 다시 나뉘는가?

  1. 헤더 20바이트를 빼면 데이터 상한은 400바이트이며 8의 배수다. 첫 자식은 원래 위치 1480부터 길이 400바이트, 다음 자식은 위치 1880부터 길이 120바이트다.

  2. 첫 자식의 offset은 185이고 MF는 1이다. 둘째 자식의 offset은 235이고 MF는 0이다.

전체 길이는 각각 420바이트와 140바이트, offset은 각각 185와 235다. 원래 데이터 520바이트를 보존한다.

비교할 점

각 부모마다 offset을 0으로 초기화하면 다른 부모의 구간과 겹치게 된다.

IPv6 추가 헤더의 비용

별도 IPv6 송신자 모형은 기본 헤더 40바이트와 Fragment 헤더 8바이트 외에 확장 헤더가 없다. 분할 가능한 부분은 2000바이트이고 경로 MTU는 1280바이트다. 목적지가 데이터 2000바이트와 기본 헤더 40바이트의 재조립을 수용한다고 가정한다. 최대 크기부터 나누어라.

  1. 데이터 상한은 1280−40−8=1232바이트이며 8의 배수다.

  2. 첫 데이터 1232바이트의 offset은 0이고 M은 1이다. 남은 데이터 768바이트의 offset은 154이고 M은 0이다.

두 패킷의 전체 길이는 각각 1280바이트와 816바이트, 합계 2096바이트다. IPv6 라우터가 아니라 송신자가 분할한다.

비교할 점

원래 전체 길이 2040바이트보다 56바이트 늘어난다. 각 조각의 기본 헤더 40바이트와 Fragment 헤더 8바이트를 모두 센다. 1500바이트를 초과하는 재조립의 수용 능력은 별도로 가정했다.

연습 1 · 값과 상태 예측

표의 조각이 offset 185, 0, 150, 75의 순서로 도착할 때 데이터가 모두 있는지 확인하라.

힌트 1

각 offset에 8을 곱하면 원래 데이터 시작 위치다.

힌트 2

구간을 정렬하고 앞 구간의 끝과 다음 구간의 시작을 비교한다.

풀이와 답 확인

  1. 정렬된 구간은 [0,600), [600,1200), [1200,1480), [1480,2000)이다.

  2. 겹침이나 공백 없이 [0,2000)을 덮는다.

같은 식별 문맥과 정상 내용이라는 조건에서 길이상 완전하다. 도착 순서가 바뀌었다는 이유만으로 누락이라고 판정하지 않는다.

흔한 오답에서 다시 생각하기

MF=0인 조각이 먼저 오면 앞 조각이 필요 없다.

MF=0은 원래 끝 위치를 알려줄 뿐 앞쪽 데이터를 포함하지 않는다.

연습 2 · 오류 찾아 고치기

offset 150인 데이터 280바이트 조각을 재분할의 마지막이라 MF=0으로 적었다. 고쳐라.

힌트 1

데이터 1480바이트인 부모의 원래 MF는 1이다.

힌트 2

원래 데이터의 [1480,2000) 구간이 뒤에 남는지 확인한다.

풀이와 답 확인

  1. 앞 부모의 마지막 자식은 부모의 MF=1을 보존한다.

  2. 원래 마지막은 offset 185인 데이터 520바이트 조각이다.

offset 150의 MF는 1이고 offset 185의 MF는 0이다.

흔한 오답에서 다시 생각하기

재분할할 때 마지막 자식의 MF는 항상 0이다.

그 부모가 원래 데이터그램의 마지막이었는지 먼저 확인한다.

힌트 2

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

별도 IPv6 예에서 Fragment 헤더 8바이트를 누락하여 첫 데이터 길이를 1240바이트로 골랐다. 어떤 계산이 틀리는가?

힌트 1

기본 헤더 40바이트와 Fragment 헤더 8바이트를 모두 더한다.

힌트 2

MTU 1280바이트와 실제 전체 길이를 비교한다.

풀이와 답 확인

  1. 전체 길이는 1240+40+8=1288바이트로 MTU보다 8바이트 크다.

  2. 실제 첫 분할 부분의 상한은 1232바이트이며 다음 offset은 154다.

헤더 누락은 첫 조각 크기와 다음 offset을 모두 잘못 만든다. 실제 장비에서 전송한 결과가 아니다.

흔한 오답에서 다시 생각하기

IPv6 기본 헤더에 Fragment 필드가 이미 포함된다.

분할할 때 추가하는 헤더 8바이트는 기본 헤더 40바이트와 별도다.

IPv4 재분할 뒤 목적지에서 복원하는 길이는?

설명 기준 확인

최종 헤더를 제외한 원래 데이터 길이다. 이 예제에서는 2000바이트이며 여러 링크의 전송 합 4120바이트와 다르다.

IPv6의 MTU 1280바이트는 큰 재조립을 무조건 허용하는가?

설명 기준 확인

링크 패킷 크기와 목적지 재조립 능력은 다르다. 1500바이트보다 큰 재조립에는 수용 가능하다는 별도 근거가 필요하다.

한 단계 더

경로 링크 MTU1500/1400/900의 경로 MTU를 구하고 IPv4 옵션20 바이트가 추가될 때 첫 데이터 상한을 다시 계산한다. 900−40=860에서8배수856을 선택한다. 옵션 복사 여부로 실제 조각 헤더가 달라질 수 있으므로 이는 모든 조각 헤더40인 별도 모형이라고 명시한다.

소단원 7.3

ICMP와 주소 변환

공유 인터넷 주소 뒤의 두 컴퓨터에 답장이 어떻게 돌아갈까?

준비 개념과 학습 목표

준비 개념

  • IP 주소는 인터페이스를 식별한다.

  • TCP/UDP 포트는 해당 호스트에서 통신 끝점을 구별한다.

학습 목표

  • ICMP의 제어 역할과 관찰 한계를 구별한다.

  • NAPT의 반환 주소/포트 대응을 추적한다.

외부 포트 숫자가 같으면 TCP·UDP·Echo도 같은 반환 표를 쓸까?

새 변환 모형의 외부 주소는 203.0.113.20이다. TCP의 내부 끝점 10.1.0.2:6000은 외부 포트 41000, TCP의 10.1.0.3:6000은 외부 포트 41001에 대응한다. 별도 UDP의 10.1.0.4:6000은 UDP 외부 포트 41000에 대응한다. 숫자 41000이 겹쳐도 프로토콜이 달라 이 모형에서는 TCP와 UDP 표를 따로 찾는다. 반환 조회는 프로토콜과 외부 끝점 외에 이미 정한 상대와 필터 정책도 검사한다고 가정한다.

Echo에는 TCP나 UDP 포트가 없다. 내부 10.1.0.2와 10.1.0.3이 각각 사용한 identifier 9를 외부 identifier 900과 901에 대응한다. 요청 sequence가 둘 다 4여도 외부 식별자로 두 흐름을 구별한다. 외부 identifier 901과 sequence 4인 Reply는 내부 10.1.0.3의 identifier 9와 sequence 4로 복원한다. 모든 NAT가 이 번호 선택이나 같은 매핑 정책을 쓴다는 뜻은 아니다.

ICMP 오류의 바깥 목적 주소만 내부로 고치면 충분하지 않다. payload에 인용된 원래 TCP 패킷의 외부 출발 203.0.113.20:41001도 내부 10.1.0.3:6000에 맞춰야 한다. 변경한 IP·ICMP 등의 필드에 맞는 체크섬 처리도 필요하다. 오류 메시지는 매칭 단서를 제공하지만 웹 서비스 정상이나 공격 차단을 그 자체로 증명하지 않는다.

먼저 확인할 개념
  • NAPT 반환과 Echo

    주소·포트 표와 Echo 식별자를 각각 읽고 별도 문맥으로 확장한다.

  • 조각의 식별 문맥

    숫자 하나가 아니라 프로토콜과 주소 문맥을 함께 조회하는 이유를 연결한다.

상태를 알리는 메시지

ICMP는 IP와 함께 오류·진단 정보를 전달한다. IPv4 Echo Request 8과 Reply 0은 identifier/sequence/data로 요청과 응답을 맞춘다. TCP/UDP 데이터 전송의 성공 판정과 별도다.

IPv4 TTL은 전달 과정에서 줄어 패킷의 무한 순환을 막는다. 만료의 Time Exceeded 11 같은 정보로 경로를 살필 수 있지만 오류 메시지 자체도 필터링·손실될 수 있다. 응답 없음만으로 상대 컴퓨터가 꺼졌다고 단정하지 않는다.

주소와 포트를 함께 바꾸기

Basic NAT는 내부/외부 주소를 대응한다. NAPT는 내부 주소·포트를 외부 주소·포트와 대응하여 여러 호스트가 외부 주소 하나를 공유하게 한다. 아래는 TCP이며 상대 서버까지 같은 두 흐름을 다른 외부 포트로 구별하는 모형이다.

나가는 패킷의 출발 주소·포트를 바꾼 상태를 표에 기록한다. 돌아오는 패킷은 목적 외부 주소·포트와 흐름 문맥을 보고 내부 목적지로 되돌린다. 구현의 매핑 범위·시간 만료·필터링 정책은 다양하며 표의 대응을 모든 NAT의 유일 규칙으로 일반화하지 않는다.

변환은 모든 문제의 해답이 아니다

NAPT가 있어도 인터넷 경로·서버·방화벽 허용이 있어야 통신된다. 암호화나 인증을 대신하지 않으며 자동으로 모든 외부 연결 요청을 내부로 전달하는 것도 아니다. 미리 정한 전달 규칙 등 별도 정책이 필요할 수 있다.

ICMP 오류는 원래 패킷 일부를 담을 수 있어서 변환 장치가 그 내용도 일관되게 처리해야 한다. TCP/UDP 포트가 없는 ICMP Echo는 identifier 같은 별도 정보로 구별하므로 아래 TCP 포트 표를 그대로 붙일 수 없다.

중간 과정을 따라가는 예제

문서용 서버192.0.2.80:443으로 내부10.0.0.2:5000과10.0.0.3:5000이 접속한다. NAPT 외부203.0.113.9가 첫 흐름40001/둘째40002로 대응한다고 가정한다.

  1. 나가는 첫 TCP의 출발은203.0.113.9:40001, 둘째는203.0.113.9:40002가 된다. 서버 목적지는 둘 다192.0.2.80:443이다.

  2. 서버의 첫 답장 목적203.0.113.9:40001은 내부10.0.0.2:5000으로 복원한다.

  3. 둘째 목적40002는10.0.0.3:5000으로 복원한다. 같은 내부 포트5000이어도 내부 주소가 달라 두 흐름이다.

외부40001→10.0.0.2:5000,40002→10.0.0.3:5000 대응으로 반환한다. 이는 실제 접속 결과가 아닌 지정한 표의 종이 추적이다.

조건을 바꾸어 비교하기

같은 숫자의 별도 네임스페이스

같은 허용된 상대에서 TCP 포트 41000과 UDP 포트 41000으로 답장이 돌아온다. 각 내부 목적지는 어디인가?

  1. TCP 표의 외부 포트 41000은 내부 10.1.0.2:6000이다.

  2. UDP 표의 외부 포트 41000은 내부 10.1.0.4:6000이다.

TCP는 10.1.0.2:6000, UDP는 10.1.0.4:6000으로 돌린다.

비교할 점

출발 상대나 필터 정책이 맞지 않는 패킷도 같은 행이라는 이유만으로 허용한다는 뜻은 아니다.

오류 속의 원래 패킷

TCP 외부 포트 41001 흐름에 대한 ICMP 오류가 외부 주소로 온다. 주소 변경이 필요한 바깥과 안쪽 위치를 써라.

  1. 바깥 IP 목적 주소 203.0.113.20을 10.1.0.3으로 복원한다.

  2. 인용된 원래 IP 출발 주소 203.0.113.20과 TCP 출발 포트 41001을 내부 10.1.0.3:6000에 맞춘다.

바깥 주소와 안쪽 인용 패킷의 주소·포트 및 관련 체크섬을 일관되게 처리한다.

비교할 점

ICMP 오류의 바깥 IP 출발은 오류를 보낸 라우터일 수 있다. 이를 원래 서버라고 무조건 단정하지 않는다.

종이와 본문으로 직접 해보기

세 번째10.0.0.2:5001에 외부40003을 배정한다. 서버에서40003으로 돌아오는 패킷의 내부 목적지를 쓰고 Echo identifier7/sequence4 응답을 구별할 정보를 적는다.

힌트 보기

같은 내부 주소에서도 포트가 다르면 다른 끝점이다. Echo의 식별자와 TCP 포트는 다른 필드다.

풀이 보기

40003은10.0.0.2:5001로 복원한다. Echo Reply는 type0이며 대응 identifier7/sequence4와 반환 data를 확인한다. 응답이 없으면 손실·필터 등도 가능하여 서비스 실패 원인을 단정할 수 없다.

오해와 반례

Echo Reply를 받았으므로 웹 서비스도 정상이다.

IP Echo 응답과 TCP 443의 웹 서비스 상태는 다르다. 호스트는 Echo에 답하지만 웹 서버가 내려갔을 수도 있고 그 반대도 가능하다.

한 단계 더

표가 만료된 뒤40001 답장이 오면 무슨 내부 주소로 돌려야 하는지 정보가 충분한가? 정적 규칙 등 추가 정보가 없다는 조건에서는 복원 근거가 없다. 변환 상태 보존과 ICMP 오류의 원래 패킷 정보를 연결해 설명한다.

    실제 Echo 8/Reply 0·identifier/sequence/data 반환 및 Time Exceeded 11과 TTL 설명 본문을 읽었다. 폐기 정책에 따른 응답 부재를 성공으로 해석하지 않는다.

  • IETF RFC3022 §2.1–2.2

    실제 Basic NAT 주소 대응과 NAPT 주소/포트 튜플·반환 방향 변환 본문을 읽었다. 자체 표는 교육 모형이다.

힌트 2

③ 프로토콜을 조회 키에 포함하고 Echo 식별자와 TCP 포트를 섞지 않는다.

풀이와 답 확인

  1. ① 배치는 198.51.100.0/26, 198.51.100.64/27, 198.51.100.96/28이다. 빈 구간은 198.51.100.112/28과 198.51.100.128/25로 덮는다. 소비한 전체 주소 112개는 요구량 100개, 남는 호스트 주소 6개, 예약 주소 6개의 합이다.

  2. ② 최종 데이터 길이는 각각 600바이트, 600바이트, 280바이트, 520바이트다. offset은 각각 0, 75, 150, 185이며 MF는 각각 1, 1, 1, 0이다. 첫 링크의 전체 길이는 2040바이트, 둘째 링크는 2080바이트다. 링크 합계는 4120바이트이며 원래 데이터는 2000바이트다.

  3. ③ TCP 외부 포트 41000은 10.1.0.2:6000, UDP 외부 포트 41000은 10.1.0.4:6000으로 복원한다. Echo 외부 identifier 901은 10.1.0.3의 identifier 9다. TCP 외부 포트 41001 오류에서 안쪽 원래 출발 주소와 포트를 10.1.0.3:6000으로 복원하고 바깥 목적 주소와 관련 체크섬도 처리한다.

주소 배치·분할·변환은 각각 명시한 모형에서 검산한다. 범위 계산을 통신 성공으로, 링크 전송량 합을 원래 데이터 길이로, 숫자 하나를 전체 흐름 식별자로 보고하지 않는다.

해결한 뒤 점검할 것

  • 주소 범위의 겹침 없음과 접두 정렬을 확인하고 전체 주소·호스트 주소·예약 주소를 분리한다.

  • offset을 원래 데이터 기준으로 계산하고 부모 MF의 보존과 헤더 비용을 포함한다.

  • 프로토콜별 변환과 Echo 식별자·인용 헤더의 서로 다른 필드를 구별한다.

  • 실제 네트워크 실행과 학생 시험은 미수행으로 유지한다.
