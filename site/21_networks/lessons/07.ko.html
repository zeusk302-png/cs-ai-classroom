소단원 7.1

IPv4·IPv6와 서브넷

주소가 같은 동네인지 숫자만 보고 판단할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 비트는0/1이고 8비트 한 옥텟은0부터255다.

  • 접두(prefix)는 주소 왼쪽의 공통 비트다.

학습 목표

  • 마스크로 IPv4 블록을 구한다.

  • IPv6 압축 표기를 복원한다.

주소와 접두

IPv4 주소는32 비트를 점으로 나눈 네 옥텟으로 쓴다. /p는 왼쪽 p 비트를 블록의 접두로 고정한다는 뜻이며 남은32−p 비트는 블록 안에서 달라진다. 주소 하나만으로 접두 길이를 추측하지 않는다.

마스크는 앞 p 비트1, 뒤 비트0이다. 주소와 마스크를 비트 AND하면 블록의 첫 주소를 구한다. 블록 크기는2^(32−p)이므로 아무 숫자에서나 같은 크기의 블록이 시작하는 것은 아니다.

사용 주소와 전체 주소

통상적인 IPv4 브로드캐스트 서브넷은 맨 처음을 네트워크 주소, 맨 끝을 브로드캐스트 주소로 사용하여 그 사이를 호스트에 배정한다. 이 단원 예제는 주소 수가 4보다 큰 일반 서브넷(p≤29)에서 이 규칙을 사용한다.

2^(32−p)−2를 모든 p에 기계적으로 적용하면 안 된다. /31 점대점 링크와 /32 단일 주소는 용도가 다르다. 같은 접두에 속한다는 계산은 실제 링크 연결·라우팅·보안 허용까지 보장하지 않는다.

IPv6 숫자를 읽기

IPv6는128 비트를16진수 16비트 묶음 여덟 개로 쓴다. 묶음 앞의0은 생략할 수 있고 연속0 묶음을 ::로 한 번 압축할 수 있다. 두 번 쓰면 어느 구간에 몇 묶음의0을 채울지 모호하다.

IPv6 /p도 왼쪽 p 비트의 접두이며 전체 주소 수는2^(128−p)다. IPv4의 브로드캐스트 호스트 수 공식을 그대로 옮기지 않는다. 표기 압축은 주소 비트를 줄이는 것이 아니라 같은128 비트의 글자 표현을 줄인다.

중간 과정을 따라가는 예제

문서용 IPv4 192.0.2.150/26의 마스크·블록·일반 호스트 범위를 구한다. IPv6 2001:db8:0:0:0:0:0:5도 압축한다.

  1. /26은 마지막 옥텟의 앞2비트까지 고정하여 마스크255.255.255.192다. 150=10010110₂,192=11000000₂의 AND는128=10000000₂다.

  2. 남은6비트로64 주소, 블록은192.0.2.128부터191이다. 일반 호스트는129부터190,62개다.

  3. IPv6의 여덟 묶음 중 3번째부터7번째가0이므로 2001:db8::5로 쓴다. ::는 여기서 다섯 묶음이다.

IPv4 블록192.0.2.128/26, 일반 호스트62개. IPv6 압축은2001:db8::5다.

종이와 본문으로 직접 해보기

192.0.2.64/26을 /27 두 블록으로 나누고 각 일반 호스트 수를 적는다. 2001:db8:1::9를 여덟 묶음으로 복원한다.

힌트 보기

한 비트를 접두에 추가하면 크기는 절반이다. IPv6에서 보이는 네 묶음을 먼저 센다.

풀이 보기

두 블록은64/27과96/27로 각각32주소다. 일반 호스트는65–94와97–126,각30개다. IPv6는2001:db8:1:0:0:0:0:9로 복원하여 ::가 네 묶음임을 확인한다.

오해와 반례

/26은 언제나26 개의 주소다.

/26은 고정 비트 수이며 주소 수는2^6=64 다. 또 /31을 같은 호스트 공식에 넣어0이라고 결론 내리면 점대점 용도를 놓친다.

자기점검

/26 마스크의 마지막 수는?

답과 이유 보기

192다.

상위2비트11 뒤6비트0으로128+64다.

150과170은 위 /26 블록에서 같은가?

답과 이유 보기

같다.

둘 다128–191 구간이고 AND 결과128이다.

IPv6 ::를 두 번 써도 되나?

답과 이유 보기

안 된다.

생략된0 묶음 수를 유일하게 복원할 수 없다.

한 단계 더

192.0.2.128/26의 /27 두 블록과192.0.2.192/26을 그려 보라. 같은 크기 블록의 시작점 정렬과 주소 전체 수/호스트 수를 구별한다. /64 IPv6의2^64는 배정된 실제 장비 수가 아님도 설명한다.

출처와 확인 범위
  • IETF RFC4632 §3.1

    실제 32 비트 CIDR 접두 길이·마스크·2의 거듭제곱 블록과 /31 예외 표를 읽었다. 자체 주소의 AND와 분할은 종이 계산이다.

  • IETF RFC4291 §2.2–2.3

    실제 16비트 8묶음·선행0 생략·한 번의 :: 및 접두 길이 본문을 읽었다.

  • IETF RFC8200 §1/2/4.5/5

    실제 128 비트 주소·link/path MTU 정의·송신자만의 IPv6 분할·1280 최소 링크 MTU 본문을 읽었다.

calculations: 마스크 AND128·64/62·/27의32/30 및 IPv6 다섯/네0묶음을 손계산했다. · code_execution: not_executed — 공식 원문 읽기와 종이 주소·조각·매핑 추적만 수행했다. 실제 패킷 송수신·라우터/NAT 구성·교육 코드와 학생 검증은 미수행이다. · learner_review: not_performed

소단원 7.2

프래그먼트·MTU

한 링크가 큰 봉투를 통과시키지 못하면 IP는 어떻게 할까?

준비 개념과 학습 목표

준비 개념

  • 패킷은 헤더와 데이터로 구성된다.

  • MTU는 해당 링크에서 전달 가능한 IP 패킷 크기 한도다.

학습 목표

  • IPv4 조각의 offset/MF를 계산한다.

  • IPv4와 IPv6의 분할 위치를 구별한다.

경로에서 가장 작은 한도

링크마다 MTU가 다를 수 있으며 경로 MTU는 그 경로 링크 MTU들의 최솟값이다. 응용 데이터만의 길이와 헤더까지 포함한 IP 패킷 길이를 구별해야 넘침 여부를 판단한다. MTU는 한 링크가 전달하는 패킷의 최대 크기다. DF는 분할 금지, MF는 뒤에 조각이 더 있다는 표시다.

IPv4에서 분할을 허용한 큰 데이터그램은 라우터에서 더 작은 조각으로 나뉠 수 있다. DF가 1이면 분할 대신 폐기 대상이다. 재조립은 목적지에서 하고 IP 자체가 잃은 조각의 재전송을 보장하지 않는다.

조각의 자리 번호

IPv4 조각마다 헤더가 붙고 offset은 원래 데이터 시작점에서8 바이트 단위 거리다. 마지막을 제외한 데이터 길이를8의 배수로 골라 다음 조각의 offset을 정수로 표현한다. MF1은 뒤에 더 남은 조각이 있다는 뜻이다.

같은 데이터그램의 조각은 source/destination/protocol/identification을 함께 사용해 구별한다. 도착 순서가 바뀌어도 위치 정보로 배열할 수 있지만 일부가 빠지면 완전한 원래 데이터가 되지 않는다. 이 예제는 옵션 없는20 바이트 헤더와 중복·겹침 없는 분할이다.

IPv6와 경로 조절

IPv6 라우터는 IPv6 계층에서 분할하지 않는다. 송신자는 경로에 맞춘 작은 패킷을 보내거나 필요한 경우 Fragment 헤더를 사용하여 분할한다. 기본40 바이트 헤더와 추가 헤더의 비용도 계산에 포함한다.

IPv6의 최소 링크 MTU는1280이다. 더 작은 프레임만 전달 가능한 링크는 IPv6 아래 계층에서 그 크기를 지원하도록 처리해야 한다. 따라서 작은 교육 MTU를 IPv6 표준 링크인 것처럼 해석하지 않는다. 경로 MTU 정보가 변할 수도 있다.

중간 과정을 따라가는 예제

IPv4 전체 길이4020 바이트(헤더20+데이터4000), DF0, MTU1500이다. 최대 크기부터 분할하여 각 데이터 길이/전체 길이/offset/MF를 구한다.

  1. 조각 데이터 상한1500−20=1480이며1480/8=185로 정수다. 첫 조각은1480/1500/offset0/MF1이다.

  2. 둘째도1480데이터로 원래1480부터 시작한다. 전체1500/offset185/MF1이다.

  3. 남은4000−2960=1040데이터, 전체1060, offset2960/8=370, MF0이다. 전체 전송 길이는4060으로 추가 헤더40이 생긴다.

(1480,1500,0,1),(1480,1500,185,1),(1040,1060,370,0). 원래 데이터4000이 보존된다.

종이와 본문으로 직접 해보기

같은 IPv44000데이터를 MTU1000으로 최대부터 분할한다. 모든 조각의 데이터/offset/MF를 적는다.

힌트 보기

상한980을 그대로 쓰면8의 배수가 아니다. 8·floor(980/8)을 먼저 구한다.

풀이 보기

앞 네 데이터는976씩이다. 시작0/976/1952/2928의 offset은0/122/244/366이며 MF1이다. 남은96은 offset390/MF0이다. 전체 길이는996 네 개와116 하나,합4100이다.

오해와 반례

offset은 앞 조각의 전체 길이만큼 증가한다.

첫 예제 다음 offset은1500/8이 아니라 데이터1480/8=185다. 원래 데이터 배열에 헤더가 들어가지 않기 때문이다.

자기점검

첫 예제 마지막 MF는?

답과 이유 보기

0이다.

마지막 조각 뒤에는 데이터가 더 없다.

DF1이고4020>1500이면?

답과 이유 보기

IPv4 분할 대신 폐기 대상이다.

DF는 분할 금지이며 오류 통보 가능성과 별도로 원래 패킷이 전달되지 않는다.

IPv6 라우터가 큰 패킷을 분할하나?

답과 이유 보기

하지 않는다.

IPv6 분할은 송신자에서 하며 경로에 맞춘 크기를 선택해야 한다.

한 단계 더

경로 링크 MTU1500/1400/900의 경로 MTU를 구하고 IPv4 옵션20 바이트가 추가될 때 첫 데이터 상한을 다시 계산한다. 900−40=860에서8배수856을 선택한다. 옵션 복사 여부로 실제 조각 헤더가 달라질 수 있으므로 이는 모든 조각 헤더40인 별도 모형이라고 명시한다.

출처와 확인 범위
  • IETF RFC791 fragmentation

    실제 DF·8옥텟 분할 경계·offset·MF와 재조립 네 식별 필드 본문을 읽었다. 옵션 없는 자체 패킷을 계산한다.

  • IETF RFC8200 §1/2/4.5/5

    실제 128 비트 주소·link/path MTU 정의·송신자만의 IPv6 분할·1280 최소 링크 MTU 본문을 읽었다.

calculations: 4000분할1480/1480/1040 및976×4+96,offset185/370/122/244/366/390·추가 헤더를 손계산했다. · code_execution: not_executed — 공식 원문 읽기와 종이 주소·조각·매핑 추적만 수행했다. 실제 패킷 송수신·라우터/NAT 구성·교육 코드와 학생 검증은 미수행이다. · learner_review: not_performed

소단원 7.3

ICMP와 주소 변환

공유 인터넷 주소 뒤의 두 컴퓨터에 답장이 어떻게 돌아갈까?

준비 개념과 학습 목표

준비 개념

  • IP 주소는 인터페이스를 식별한다.

  • TCP/UDP 포트는 해당 호스트에서 통신 끝점을 구별한다.

학습 목표

  • ICMP의 제어 역할과 관찰 한계를 구별한다.

  • NAPT의 반환 주소/포트 대응을 추적한다.

상태를 알리는 메시지

ICMP는 IP와 함께 오류·진단 정보를 전달한다. IPv4 Echo Request 8과 Reply 0은 identifier/sequence/data로 요청과 응답을 맞춘다. TCP/UDP 데이터 전송의 성공 판정과 별도다.

IPv4 TTL은 전달 과정에서 줄어 패킷의 무한 순환을 막는다. 만료의 Time Exceeded 11 같은 정보로 경로를 살필 수 있지만 오류 메시지 자체도 필터링·손실될 수 있다. 응답 없음만으로 상대 컴퓨터가 꺼졌다고 단정하지 않는다.

주소와 포트를 함께 바꾸기

Basic NAT는 내부/외부 주소를 대응한다. NAPT는 내부 주소·포트를 외부 주소·포트와 대응하여 여러 호스트가 외부 주소 하나를 공유하게 한다. 아래는 TCP이며 상대 서버까지 같은 두 흐름을 다른 외부 포트로 구별하는 모형이다.

나가는 패킷의 출발 주소·포트를 바꾼 상태를 표에 기록한다. 돌아오는 패킷은 목적 외부 주소·포트와 흐름 문맥을 보고 내부 목적지로 되돌린다. 구현의 매핑 범위·시간 만료·필터링 정책은 다양하며 표의 대응을 모든 NAT의 유일 규칙으로 일반화하지 않는다.

변환은 모든 문제의 해답이 아니다

NAPT가 있어도 인터넷 경로·서버·방화벽 허용이 있어야 통신된다. 암호화나 인증을 대신하지 않으며 자동으로 모든 외부 연결 요청을 내부로 전달하는 것도 아니다. 미리 정한 전달 규칙 등 별도 정책이 필요할 수 있다.

ICMP 오류는 원래 패킷 일부를 담을 수 있어서 변환 장치가 그 내용도 일관되게 처리해야 한다. TCP/UDP 포트가 없는 ICMP Echo는 identifier 같은 별도 정보로 구별하므로 아래 TCP 포트 표를 그대로 붙일 수 없다.

중간 과정을 따라가는 예제

문서용 서버192.0.2.80:443으로 내부10.0.0.2:5000과10.0.0.3:5000이 접속한다. NAPT 외부203.0.113.9가 첫 흐름40001/둘째40002로 대응한다고 가정한다.

  1. 나가는 첫 TCP의 출발은203.0.113.9:40001, 둘째는203.0.113.9:40002가 된다. 서버 목적지는 둘 다192.0.2.80:443이다.

  2. 서버의 첫 답장 목적203.0.113.9:40001은 내부10.0.0.2:5000으로 복원한다.

  3. 둘째 목적40002는10.0.0.3:5000으로 복원한다. 같은 내부 포트5000이어도 내부 주소가 달라 두 흐름이다.

외부40001→10.0.0.2:5000,40002→10.0.0.3:5000 대응으로 반환한다. 이는 실제 접속 결과가 아닌 지정한 표의 종이 추적이다.

종이와 본문으로 직접 해보기

세 번째10.0.0.2:5001에 외부40003을 배정한다. 서버에서40003으로 돌아오는 패킷의 내부 목적지를 쓰고 Echo identifier7/sequence4 응답을 구별할 정보를 적는다.

힌트 보기

같은 내부 주소에서도 포트가 다르면 다른 끝점이다. Echo의 식별자와 TCP 포트는 다른 필드다.

풀이 보기

40003은10.0.0.2:5001로 복원한다. Echo Reply는 type0이며 대응 identifier7/sequence4와 반환 data를 확인한다. 응답이 없으면 손실·필터 등도 가능하여 서비스 실패 원인을 단정할 수 없다.

오해와 반례

Echo Reply를 받았으므로 웹 서비스도 정상이다.

IP Echo 응답과 TCP 443의 웹 서비스 상태는 다르다. 호스트는 Echo에 답하지만 웹 서버가 내려갔을 수도 있고 그 반대도 가능하다.

한 단계 더

표가 만료된 뒤40001 답장이 오면 무슨 내부 주소로 돌려야 하는지 정보가 충분한가? 정적 규칙 등 추가 정보가 없다는 조건에서는 복원 근거가 없다. 변환 상태 보존과 ICMP 오류의 원래 패킷 정보를 연결해 설명한다.

출처와 확인 범위
  • IETF RFC792 Echo/Time Exceeded

    실제 Echo 8/Reply 0·identifier/sequence/data 반환 및 Time Exceeded 11과 TTL 설명 본문을 읽었다. 폐기 정책에 따른 응답 부재를 성공으로 해석하지 않는다.

  • IETF RFC3022 §2.1–2.2

    실제 Basic NAT 주소 대응과 NAPT 주소/포트 튜플·반환 방향 변환 본문을 읽었다. 자체 표는 교육 모형이다.
