소단원 3.1

TCP·UDP 소켓

두 번 보낸 데이터를 한 번에 받으면 두 메시지가 하나가 된 것일까?

준비 개념과 학습 목표

준비 개념

  • 소켓은 프로그램이 통신을 요청하는 운영체제 인터페이스의 끝점이다. IP 주소는 호스트 쪽 주소이고 포트는 한 호스트에서 통신 끝점을 구분하는 번호다. 포트 번호 자체는 사용자의 신원이나 권한을 증명하지 않는다.
  • 바이트는 8비트다. 바이트 흐름은 순서 있는 연속 데이터이고 데이터그램은 독립적인 메시지 단위다. 프로그램의 send 호출과 네트워크 패킷은 같은 단위가 아니다.
  • blocking 호출은 결과를 기다리며 실행이 멈출 수 있다. nonblocking 호출은 지금 진행할 수 없다는 결과를 돌려줄 수 있다. 종료·기다림·오류는 구분해야 한다.

학습 목표

  • TCP 흐름과 UDP 데이터그램을 비교한다.
  • 듣기 소켓과 연결 소켓을 구별한다.
  • 부분 송수신과 응용 성공의 차이를 설명한다.

연결의 인터페이스

전형적인 TCP 서버는 socket으로 끝점을 만들고 bind로 지역 주소를 정한 뒤 listen으로 연결을 받도록 준비한다. accept가 성공하면 특정 상대와 통신하는 새 연결 소켓을 얻는다. 듣기 소켓과 연결 소켓은 다른 자원이며 각각 소유권과 닫기 책임이 필요하다. 클라이언트는 connect로 연결을 요청한다. 실제 오류 계약은 사용하는 언어와 운영체제 문서를 확인한다.

TCP 연결은 양쪽 주소·포트와 프로토콜 문맥으로 구분되는 양방향 바이트 흐름이다. 전송 계층이 순서와 재전송을 관리하지만 상대가 내용을 검증하거나 기록했는지는 응용 응답으로 확인한다. connect 성공도 이후 상대가 영원히 살아 있다는 증명은 아니다.

흐름과 데이터그램

TCP에서 AB와 CD를 각각 send해도 recv가 AB와 CD로 나뉘어 반환된다는 보장은 없다. ABCD를 한 번에 받거나 A,BC,D로 받을 수 있다. 정상적으로 받은 흐름의 바이트 순서는 보존되지만 응용 메시지 경계는 별도 프로토콜이 정한다.

UDP는 데이터그램 경계를 사용한다. 충분한 수신 버퍼로 정상 수신한 데이터그램은 메시지 경계를 유지하지만 UDP 자체는 전달·순서·중복 방지를 보장하지 않는다. 작은 버퍼의 잘림과 오류 표시는 API에 의존한다. UDP connect API를 호출한다고 TCP의 연결 설정과 신뢰 전송이 생기는 것도 아니다.

반환값을 추적하기

stream send가 요청보다 작은 양의 수 k를 반환하면 앞 k바이트를 처리한 것이므로 다음 요청은 미처리 접미부부터 보낸다. n바이트를 모으는 recv 반복에서도 누적 길이를 유지한다. Python stream recv의 양의 버퍼 크기 요청에서 b""는 수신 방향 종료를 뜻하며, 지금 읽을 데이터가 없는 nonblocking 오류나 timeout과 다르다.

한 방향 송신만 끝내는 half-close와 전체 close는 다르다. 상대가 송신을 끝냈더라도 반대 방향으로 응답을 보낼 수 있는 경우가 있다. 읽기 루프의 종료 조건과 응용 메시지의 완결 조건을 따로 정하지 않으면 무한 대기나 잘린 메시지 수락이 생긴다. 이 소단원은 실제 연결 대신 종이 반환값 모형을 쓴다.

중간 과정을 따라가는 예제

TCP stream에서 ABCDE의 send 반환이 2,3이고 recv 결과가 A,BCD,E인 성공 모형을 추적한다. 응용 메시지 길이는 5바이트로 정한다.

  1. 송신 offset=0에서 ABCDE를 요청한다. 반환 2면 AB가 처리되어 offset=2다.
  2. 다음 요청은 CDE이고 반환 3이면 offset=5다. 요청 데이터 전체를 지역 API가 처리했다.
  3. 수신 측은 A,BCD,E를 순서대로 누적하여 길이 1,4,5가 된다. send 경계와 recv 경계는 다르다.
  4. 누적 흐름은 ABCDE이며 지정한 5바이트 메시지가 완결된다. 상대의 업무 처리 성공은 별도 응용 응답 없이는 알 수 없다.

흐름의 내용은 같지만 호출 경계는 다르다.

종이와 본문으로 직접 해보기

송신 AB,CD에 대해 TCP 수신 ABC,D와 AC,BD가 각각 가능한 정상 분할인지 판단하라. UDP에서 CD,AB 순서로 도착할 가능성도 생각하라.

힌트 보기

TCP는 이어 붙인 전체 바이트 순서를 검사한다. UDP의 기본 보장에는 순서 보존이 없다.

풀이 보기

ABC,D는 ABCD이므로 가능하다. AC,BD는 ACBD로 순서가 바뀌어 정상 TCP 흐름이 아니다. UDP에서 CD,AB 순서로 도착하는 것은 배제되지 않는다.

오해와 반례

TCP send 성공은 상대의 업무 실행 성공이다.

지역 송신 처리는 응용 성공 확인과 다르다. 서버가 수신 후 거절하거나, 처리 뒤 응답 전에 종료할 수도 있다. 확인 응답의 의미를 업무 계약으로 정해야 한다.

한 단계 더

부분 송신 불변식: D의 길이 n과 다음 미처리 위치 o에 대해 0≤o≤n, 이미 처리한 접두부=D[:o]를 유지한다. 0<k≤n−o인 성공 반환 뒤 o←o+k로 갱신하면 불변식이 유지되고 남은 양 n−o는 감소한다. 하지만 계속 양의 진행 반환을 받는다는 가정 없이는 종료를 증명할 수 없다. 오류와 timeout은 별도의 전이로 다룬다.

소단원 3.2

프레이밍과 직렬화

한글 한 글자는 메시지 길이에서 1일까, 3일까?

준비 개념과 학습 목표

준비 개념

  • 직렬화는 값을 바이트로 표현하는 규칙이고 역직렬화는 값을 복원하는 과정이다. 프레이밍은 흐름 안에서 메시지 경계를 판별하는 규칙이다.
  • UTF-8에서 A는 41 한 바이트, 가는 EA B0 80 세 바이트다. A가의 문자 수는 2지만 바이트 수는 4다.
  • big-endian 두 바이트 h0,h1의 정수는 256h0+h1이다. 길이 필드 폭·단위·byte order·최대값을 양쪽이 같은 계약으로 정해야 한다.

학습 목표

  • 임의 수신 조각에서 길이 프레임을 복원한다.
  • 문자 수와 바이트 수를 구분한다.
  • 길이 초과·미완결 EOF·인코딩 오류를 검사한다.

자체 길이 프로토콜

교육용 프로토콜을 2바이트 big-endian 길이 n과 정확히 n바이트의 UTF-8 본문으로 정한다. 정수 0≤n≤1024만 허용하고 n=0은 빈 문자열 메시지다. 길이는 본문 바이트만 세며 헤더 두 바이트는 포함하지 않는다. 1024 초과 헤더는 더 기다리지 않고 오류로 거절한다.

A가를 문자 수 2로 선언하면 UTF-8 바이트 중간에서 프레임이 잘린다. 바이트 수준에서 프레임을 완결한 뒤 strict UTF-8로 해석한다. 여기서는 문자열 하나지만 구조화된 실제 메시지에는 필드 타입·필수 항목·버전 등의 스키마도 필요하다.

버퍼와 소비

새 조각을 버퍼에 붙인다. 두 바이트가 없으면 기다린다. 헤더가 있으면 n을 검사하고, 버퍼가 2+n바이트보다 작으면 미완결 상태로 둔다. 충분하면 앞 프레임을 해석하고 소비한 뒤 남은 접미부에 같은 절차를 반복한다. 한 조각에 여러 프레임이 있을 수 있다.

헤더나 한글 바이트가 나뉘어 도착해도 완결한 본문의 바이트는 같다. delimiter 방식도 가능하지만 본문 안의 delimiter를 escape하거나 금지하는 규칙이 필요하다. 단순 split은 모든 바이너리 입력을 위한 프레이밍 계약이 아니다.

거절과 자원 범위

EOF에 남은 버퍼가 비어 있으면 이미 완결한 프레임 접두부 처리 뒤 종료한다. 한 바이트 헤더나 미완결 본문이 남으면 truncated frame 오류다. 길이 초과와 strict UTF-8 오류도 거절한다. 전송 계층의 종료가 응용 프레임 완결을 대신하지 않는다. 이 모형은 거절 후 같은 parser를 복구해 계속 사용하는 계약을 제공하지 않는다. 일부 프레임을 이미 낸 뒤 오류가 생긴 경우에도 앞의 완결 메시지와 오류 이후의 처리를 별도로 정해야 한다.

길이 제한은 메시지 하나만 제한한다. 무제한 조각 누적이나 완결 메시지 목록 저장은 총 메모리를 늘릴 수 있으므로 운영 구현에는 연결별 버퍼·큐·전체 자원 제한이 추가로 필요하다. 아래 Python은 짧은 고정 입력의 메모리 모형이며 운영 서버가 아니다.

중간 과정을 따라가는 예제

A가와 B를 연속 프레임으로 만들고 수신 조각 00 / 04 41 EA / B0 80 00 01 42를 처리한다.

  1. A가의 본문은 41 EA B0 80으로 4바이트다. 첫 프레임은 00 04 41 EA B0 80이다.
  2. B의 프레임은 00 01 42다. 전체는 00 04 41 EA B0 80 00 01 42, 9바이트다.
  3. 첫 조각 뒤 버퍼는 1바이트, 둘째 뒤는 4바이트다. 헤더 n=4는 알지만 필요한 6바이트보다 작아 메시지를 아직 내지 않는다.
  4. 셋째 뒤 앞 6바이트에서 A가를 내고 나머지 00 01 42에서 B를 낸다. 버퍼가 비어 EOF도 정상이다.

결과는 A가,B 두 문자열이고 조각 경계는 의미를 바꾸지 않는다.

종이와 본문으로 직접 해보기

00 00 00 01 41을 처리하라. 또 EOF까지 00 04 41만 온 경우를 판단하라.

힌트 보기

빈 본문도 헤더는 소비한다. EOF의 실제 길이를 선언한 길이와 비교한다.

풀이 보기

첫 입력은 빈 문자열과 A다. n=0이어도 헤더 두 바이트를 소비한다. 둘째는 선언 본문 4바이트 중 1바이트만 있어 미완결 오류이며 A를 정상 메시지로 내지 않는다.

오해와 반례

TCP는 신뢰성이 있으므로 길이 검사가 필요 없다.

TCP는 응용 스키마를 검증하지 않는다. 00 04 41 뒤 종료되어도 선언한 본문은 완결되지 않았다. 길이와 strict decode 계약이 필요하다.

한 단계 더

분할 독립성: 버퍼는 원래 흐름에서 미소비한 접미부라는 불변식을 유지한다. 헤더가 정하는 2+n 길이는 조각 경계와 무관하므로 완결할 때 소비하는 접두부가 같다. 이후 프레임에 귀납적으로 같은 주장을 적용한다. 유효한 유한 흐름의 모든 바이트가 도착한다는 가정 아래 동일 메시지열을 얻는다. 실제 Python은 지정 9바이트의 여덟 경계마다 자르거나 유지하는 2^8=256개 비어 있지 않은 조각 분할을 모두 검사했다. 전체 입력 형식 검증은 아니다.

소단원 3.3

타임아웃·동시 요청

응답이 늦으면 서버는 실패한 것일까, 이미 일을 끝냈지만 답만 늦은 것일까?

준비 개념과 학습 목표

준비 개념

  • 요청 ID는 요청과 응답을 대응시키는 식별자다. 동일 ID 재시도는 같은 의미·같은 payload라는 계약이 필요하며 ID 자체는 사용자 인증이 아니다.
  • 타임아웃은 최대 기다림 기간, deadline은 기다림을 끝낼 시각이다. 단조 시계는 경과 시간을 재는 동안 뒤로 가지 않도록 설계된 시계다.
  • 동시 요청은 처리 구간이 겹치는 요청이다. 원자적 전이는 다른 요청이 중간 상태를 보지 못하도록 보호한 상태 변화다. 프레이밍과 상태 원자성은 다른 계약이다.

학습 목표

  • 전체 deadline에서 남은 시간을 계산한다.
  • timeout 관측과 업무 완료를 구분한다.
  • 동시 응답 대응과 중복 방지의 가정을 설명한다.

전체 예산

시작 t0에 예산 B를 정하면 deadline d=t0+B다. 단계마다 남은 양 max(0,d−now)를 계산한다. connect·송신·수신에 각각 B를 다시 주면 전체 기다림은 B를 넘을 수 있다. API 호출별 timeout과 전체 요청 deadline을 구분한다.

로컬 단조 시계 값이 다른 서버와 자동 동기화되지는 않는다. 다른 호스트에 같은 숫자 시각을 그대로 전달하려면 시계 계약이 필요하다. gRPC는 경과 기간을 뺀 timeout으로 전파하는 기능을 제공하지만 모든 소켓 프로토콜에 자동으로 존재하지 않는다.

관측과 효과

timeout은 지정 시각까지 유효 응답을 관찰하지 못했다는 뜻이다. 서버가 요청을 못 받았거나 처리 중이거나 완료 뒤 응답만 늦었을 수 있다. 클라이언트가 기다림을 끝내도 이미 생긴 서버 효과가 자동 취소되지는 않는다. 취소의 도착과 업무 커밋도 다른 경계다.

부작용 중복 방지를 위해 같은 ID와 payload를 재사용하고 서버의 결과표 검사·상태 변경·결과 기록을 같은 보호 경계에 둘 수 있다. 결과 보존 기간과 재시작 복구도 정해야 한다. 새 소켓으로 다시 보내는 것만으로 exactly-once 업무 보장이 생기지는 않는다.

동시 요청과 대응

요청 7과 8을 보내고 8이 먼저 완료될 수 있다면 응답 ID나 명시적 순서 계약이 필요하다. TCP는 보내진 바이트 순서를 유지할 뿐 서버의 업무 완료 순서를 정하지 않는다. 받는 쪽은 미해결 ID 표와 늦은·중복·알 수 없는 ID의 처리 규칙을 둔다.

여러 writer가 같은 stream에 독립적으로 헤더와 본문을 쓰면 바이트가 끼어들어 프레임을 깨뜨릴 수 있다. 단일 writer 큐나 프레임 직렬화 경계가 필요하다. 여러 reader도 메시지 일부를 나눠 가져갈 수 있으므로 하나의 parser가 완결 메시지를 분배하도록 설계할 수 있다. 이는 업무 데이터의 경쟁 조건을 자동 해결하지 않는다.

중간 과정을 따라가는 예제

단조 시각 0 ms에서 요청 7의 예산은 100 ms다. connect는 30 ms, 송신까지 추가 30 ms 걸린다. 서버는 70 ms에 상태를 바꾸고 응답은 120 ms에 도착하는 가상 모형이다.

  1. deadline은 100 ms다. connect 뒤 남은 양은 70 ms다.
  2. 송신 뒤 now=60 ms이므로 응답 대기는 40 ms만 남는다. 다시 100 ms를 주지 않는다.
  3. 서버는 70 ms에 완료했지만 클라이언트는 100 ms까지 답을 못 보고 timeout으로 기다림을 종료한다.
  4. 120 ms의 응답은 이미 timeout한 요청 7의 늦은 결과다. 새 요청 8의 성공으로 대응시키지 않는다.

클라이언트 timeout과 서버 완료는 동시에 참일 수 있다. 40 ms는 가정한 시간표 계산이다.

종이와 본문으로 직접 해보기

미해결 요청 {7,8}에 응답 ID 8,7이 순서대로 온다. 대응 표를 적고, 동일 ID 7로 payload를 바꾼 재시도의 문제를 설명하라.

힌트 보기

도착 순서 대신 ID로 찾는다. 기존 결과표가 어느 의미의 요청을 기록했는지 생각한다.

풀이 보기

첫 응답 뒤 {7}, 둘째 뒤 빈 표가 된다. 같은 ID의 다른 payload는 기존 결과 재사용과 충돌할 수 있다. 동일 ID는 동일 의미로 제한하고 불일치를 거절하는 등의 계약이 필요하다.

오해와 반례

timeout이면 서버 상태는 바뀌지 않았다.

서버는 70 ms에 변경했고 클라이언트는 100 ms에 timeout을 관찰했다. 응답을 못 본 완료 가능성을 고려해 조회·재시도·중복 방지 계약을 정해야 한다.

한 단계 더

결과표 귀납: 여기서는 고정된 요청 ID 이름공간과 동일 payload의 동일 업무 의미를 가정한다. 보호 전이에서 처음 ID r이 없을 때만 상태를 한 번 바꾸고 (r,payload,result)를 함께 기록한다. 이후 동일 r,payload는 기록된 결과만 반환한다. 초기 기록이 없는 상태에서 시작하면 기록된 각 ID의 효과 횟수≤1 불변식이 유지된다. 보호 경계가 없으면 두 worker가 동시에 없음으로 검사해 두 번 실행할 수 있다. 결과표를 잃는 재시작·ID 재사용·보호 밖 외부 효과는 증명 가정 밖이다.
