소단원 13.1

SDN과 제어 분리

같은 목적지의 패킷을 다른 길로 보내려면 누가 결정을 바꾸고 누가 그 결정을 실행할까?

준비 개념과 학습 목표

준비 개념

  • 패킷의 목적지

  • 라우터의 전달 표

  • 그래프의 경로

학습 목표

  • 제어와 전달 역할을 구별한다.

  • 정책 변경 중 서로 다른 규칙이 섞이는 반례를 추적한다.

  • 논리적 제어와 물리적 배치를 구별한다.

결정을 만드는 쪽과 적용하는 쪽

전달 평면은 들어온 패킷에 설치된 규칙을 적용하여 다음 포트를 선택하거나 패킷을 버린다. 제어 평면은 어떤 규칙이 필요한지 결정하고 장치에 전달한다. SDN은 이 관계를 프로그램으로 다루기 쉽게 분리한다. 예를 들어 학교 건물 사이의 영상 트래픽을 특정 경로로 보내라는 정책은 제어 쪽에서 결정하고, 실제 패킷은 각 스위치가 처리한다.

분리는 역할과 인터페이스의 분리다. 반드시 제어기가 한 대의 컴퓨터에만 있어야 한다는 뜻은 아니다. RFC 7426은 구현마다 평면이 함께 놓이거나 물리적으로 떨어질 수 있는 개념 모델을 설명한다. 이 자료는 2015년의 정보성 RFC이므로 특정 제품의 최신 설정법으로 사용하지 않는다.

설치된 규칙은 작은 프로그램이다

이 수업의 가상 장치는 목적지와 다음 장치의 대응표만 가진다. 목적지 D에 대해 S1의 다음 장치가 S2이면 S1은 패킷을 S2로 보낸다. S2의 다음 장치가 D이면 도착한다. 표에 해당 목적지가 없으면 버린다는 기본 규칙도 정한다. 실제 장치는 우선순위·헤더 필드·큐 등 더 많은 조건을 사용한다.

제어기와의 통신이 끊겨도 기존 규칙을 계속 적용하는지, 언제 만료되는지, 새 트래픽은 어떻게 처리하는지는 시스템의 계약에 달려 있다. 제어 장애와 전달 장애를 같은 사건으로 단정하지 말고 기존 표·만료·연결 상태를 각각 확인해야 한다.

좋은 최종 표도 중간에는 실패할 수 있다

여러 장치의 표를 한순간에 바꾸기는 어렵다. 이전 표와 새 표가 각각 정상 경로를 만들더라도 갱신 도중의 조합은 순환이나 손실을 만들 수 있다. 그래서 변경 계획에는 최종 경로뿐 아니라 설치 순서, 적용 확인, 실패 시 되돌리기도 들어간다.

아래 활동은 제어 메시지가 지정한 순서로 성공하고 그 사이에 패킷이 들어오는 자체 모형이다. 실제 SDN의 버전 태그·일관된 갱신 알고리즘을 구현한 실험이 아니다. 다만 최종 상태의 검사만으로 중간 상태의 안전성을 판단할 수 없다는 이유를 보여 준다.

중간 과정을 따라가는 예제

목적지 D의 이전 표는 S1→S2, S2→D이고 새 표는 S1→D, S2→S1이다. D는 도착하면 전달을 끝낸다. S2를 먼저 바꾼 직후 S1에 들어온 패킷을 추적하라. 링크 장애나 표 만료는 없다고 가정한다.

  1. 갱신 전에는 S1→S2→D로 도착한다.

  2. S2만 바꾸면 S1의 옛 규칙은 여전히 S2를 가리키고 S2의 새 규칙은 S1을 가리킨다.

  3. 패킷은 S1→S2→S1→S2로 되돌아간다. 반복을 확인하면 경로 추적을 멈춘다. 실제 IP 패킷은 TTL 같은 제한으로 결국 버려질 수 있다.

  4. S1도 바꾼 최종 상태에서는 S1→D, S2→S1→D로 도착한다.

최종 표는 도착하지만 S2만 먼저 바꾼 중간 상태는 순환한다. 최종 상태만 검사하면 이 문제를 놓친다.

종이와 본문으로 직접 해보기

같은 이전/새 표에서 S1을 먼저 바꾸는 경우를 그려 보라. 중간 상태에 S1과 S2 각각에서 시작한 패킷이 어디로 가는가?

힌트 보기

바뀌지 않은 S2의 규칙도 그대로 적어 두어라.

풀이 보기

중간 상태는 S1→D, S2→D다. 두 출발점 모두 D에 도착한다. 이후 S2를 바꾸면 S2→S1→D다. 이 모형에서는 S1 먼저가 순환을 피하지만 모든 토폴로지에서 같은 순서가 통하는 일반 정리는 아니다.

오해와 반례

SDN이면 모든 패킷을 중앙 제어기가 직접 전달한다.

제어기는 규칙을 결정하고 전달 장치는 설치된 규칙을 실행할 수 있다. 예제의 패킷 경로에는 제어기를 넣지 않았다. 일부 미등록 흐름을 제어 쪽에 문의하는 설계도 있으므로 문의와 모든 데이터의 경유를 구별한다.

로드밸런싱·CDN

서버 두 대에 요청을 똑같이 나누면 작업량도 똑같을까? 가까운 캐시는 무엇을 줄일까?

준비 개념과 학습 목표

준비 개념

  • 요청과 응답

  • 평균의 분모

  • 서버와 캐시

학습 목표

  • 요청 수 분배와 부하 분배를 구별한다.

  • 로드밸런서와 CDN의 역할을 설명한다.

  • 캐시 재사용 조건과 가상 비용을 계산한다.

요청을 어디에 보낼지 정한다

로드밸런서는 서비스의 여러 서버 중 요청을 받을 대상을 고른다. 돌아가며 고르는 round-robin은 요청 수를 비교적 균등하게 나누지만 각 요청의 처리 비용까지 같게 만들지는 않는다. 적은 활성 연결을 가진 서버를 고르는 방식도 있으나 연결 수 역시 CPU 비용이나 응답 시간을 완전히 나타내지는 않는다.

요청이 다른 서버로 갈 수 있으므로 로그인 상태를 한 서버 메모리에만 보관하면 다음 요청에서 상태를 찾지 못할 수 있다. 공유 저장소나 명시적인 세션 설계가 필요하다. 특정 서버에 붙이는 방식도 서버 장애와 상태 복구를 대신 해결하지 않는다.

CDN은 재사용 가능한 응답을 가까이 둔다

CDN은 여러 위치의 노드를 활용해 콘텐츠를 제공하는 체계다. 이 절에서는 그중 공개 콘텐츠 캐시를 다룬다. 원본 서버에서 받은 응답을 캐시에 보관하고 조건이 맞으면 다음 요청에 재사용한다. 로드밸런싱은 대상을 고르는 문제이고 캐싱은 이전 결과를 재사용하는 문제여서 한 서비스에서 함께 쓸 수 있다.

캐시는 URL만 같다고 언제나 재사용할 수 없다. 언어 등 요청 조건이 달라지면 Vary에 따라 캐시 키를 구별할 수 있다. 공유 캐시에는 private·no-store와 인증 요청의 별도 조건도 있다. 개인의 성적표를 공개 이미지와 같은 규칙으로 저장해서는 안 된다.

적중률과 시간은 서로 다른 수치다

이 수업의 적중률은 캐시에서 그대로 만족시킨 요청 수를 전체 요청 수로 나눈다. 원본을 확인해야 하는 재검증은 여기서는 적중으로 세지 않는다. 실제 운영 지표의 정의는 다를 수 있으므로 분모와 분류를 먼저 적는다.

RFC 9111의 신선도 판단은 freshness_lifetime > current_age다. 남은 시간이 없으면 별도 재검증이나 허용된 stale 제공 조건을 검토해야 한다. 캐시 만료는 원본 변경을 즉시 통지하는 장치가 아니다. 아래 지연값은 합성된 가정이며 실제 CDN 사업자나 네트워크 성능 수치가 아니다.

중간 과정을 따라가는 예제

요청 6개의 가상 처리 비용은 순서대로 8,1,1,1,1,1 작업 단위다. 두 서버 A/B에 A부터 교대로 보낸다. 별도 공개 이미지 요청 6개는 캐시 적중 4개/미적중 2개이며 적중 응답 5 ms, 미적중의 원본 조회를 포함한 전체 응답 45 ms다. 처리 비용과 응답 시간을 각각 계산하라.

  1. A는 1/3/5번을 받아 비용 8+1+1=10, B는 2/4/6번을 받아 1+1+1=3이다. 요청 수는 각각 3개다.

  2. 이미지 적중률은 4/6=2/3이다. 이 모형에서 원본 조회는 2개다.

  3. 평균 전체 응답 시간은 (4×5+2×45)/6=110/6=55/3 ms, 약 18.33 ms다.

  4. 45 ms는 이미 원본 조회를 포함하므로 5 ms를 또 더하지 않는다. 서버 작업 단위와 이미지 응답 ms는 서로 다른 실험 표다.

요청 수는 3/3이지만 작업량은 10/3이다. 별도 캐시 표의 적중률은 약 66.67%, 평균 응답은 약 18.33 ms다. 이 값으로 실제 처리율을 추정하지 않는다.

종이와 본문으로 직접 해보기

가상 캐시의 freshness_lifetime은 30초다. current_age가 29초/30초/31초일 때 신선도를 판정하라. 요청 언어가 한국어에서 영어로 바뀌고 Vary: Accept-Language가 있다면 같은 한국어 응답을 그대로 써도 되는가?

힌트 보기

신선도는 엄격한 > 비교다. 시간 조건과 요청 조건을 둘 다 검사하라.

풀이 보기

29초만 신선하고 30초/31초는 신선하지 않다. 영어 요청은 원래의 언어 조건과 맞지 않으므로 한국어 응답을 그대로 재사용하지 않는다. 신선하지 않다는 것은 무조건 삭제와 같지 않으며 재검증 등 별도 규칙을 확인한다.

오해와 반례

로드밸런서가 있으면 모든 서버의 작업량이 같고 캐시는 언제나 최신이다.

비용 8인 요청 하나가 A에 있어 요청 수가 같아도 작업량 10/3이다. 캐시는 신선도와 키·권한 조건을 따라 이전 응답을 재사용하므로 원본 변경을 즉시 알고 있다는 보장이 없다.

소단원 13.3

QUIC와 현대 전송의 개요

UDP 위에 놓인 QUIC은 왜 순서와 신뢰성을 제공할 수 있을까? 한 흐름의 빈칸은 다른 흐름도 막을까?

준비 개념과 학습 목표

준비 개념

  • TCP의 바이트 순서

  • UDP 데이터그램

  • 오프셋과 재전송

학습 목표

  • UDP와 QUIC의 기능 계층을 구별한다.

  • 흐름 내부 순서와 흐름 사이 독립성을 추적한다.

  • 흐름 제어와 연결 이동의 조건을 설명한다.

UDP가 운반하고 QUIC이 기능을 더한다

RFC 9000의 QUIC 버전 1은 UDP 데이터그램으로 패킷을 운반하지만 그 위에서 연결·신뢰성 있는 스트림·흐름 제어·혼잡 제어와 TLS 통합을 제공한다. UDP만 보내는 프로그램과 QUIC 연결을 만드는 프로그램은 같은 기능을 가진다고 볼 수 없다. HTTP/3는 HTTP의 의미를 QUIC 위에 대응시키는 별도 응용 프로토콜이다.

패킷과 스트림은 다르다. 패킷 하나가 여러 스트림의 데이터를 담을 수 있고, 손실 뒤에는 필요한 데이터를 다시 보내더라도 원래 패킷의 경계가 응용에 보존되는 것은 아니다. 응용 메시지 경계는 여전히 응용 프로토콜이 정해야 한다.

스트림마다 자신의 빈칸을 기다린다

일반적인 순서 있는 스트림 읽기에서 오프셋은 각 스트림의 바이트 위치다. 앞부분이 빠진 스트림은 뒤부분을 받았어도 순서대로 내보내려면 빈칸을 기다린다. 다른 스트림의 완성된 데이터는 그 빈칸 때문에 같은 순서 제약을 받지 않는다. 스트림 사이의 전역 전달 순서도 QUIC이 정해 주지 않는다.

이 특성은 모든 지연을 제거한다는 뜻은 아니다. 스트림들은 연결의 혼잡 제어, 경로 대역폭, 연결 흐름 제어와 응용의 의존성을 공유할 수 있다. 예를 들어 응용이 A의 결과가 있어야 B를 처리한다면 B가 도착했어도 응용 단계에서 기다릴 수 있다.

이동과 속도에는 조건이 있다

연결 ID는 주소가 바뀌는 상황에서도 연결을 식별하는 데 쓰인다. RFC 9000의 이동은 핸드셰이크 확인과 경로 검증·상대의 제한 같은 조건을 따른다. 연결 ID만 안다고 임의 주소에 마음대로 대량 전송할 수 있는 기능이 아니다. 새 경로에서 손실이나 사용 가능 대역폭이 달라질 수도 있다.

0-RTT 역시 이전 통신이나 설정을 필요로 하는 선택 기능이다. 항상 첫 방문부터 왕복이 없거나 항상 TCP보다 빠르다고 판단하지 말라. 이 절의 시간선은 지정한 수신 사건에서 순서 규칙을 비교하는 종이 모형이며 QUIC 구현이나 인터넷 성능 시험이 아니다.

중간 과정을 따라가는 예제

순서 있는 읽기를 제공하는 가상 수신기가 있다. 스트림 A의 오프셋 2에 CD가 시각 2 ms에 도착하지만 오프셋 0의 AB는 8 ms에 도착한다. 스트림 B의 오프셋 0에 XY는 3 ms에 도착한다. A/B 사이 응용 의존성·흐름 제어 제한은 없고 수신 즉시 가능한 데이터를 읽는다고 가정한다.

  1. 2 ms에 A는 오프셋 0/1이 비어 있으므로 CD를 보관하고 순서 있는 읽기에는 내보내지 않는다.

  2. 3 ms에 B의 앞부분은 XY로 완성되므로 B는 XY를 내보낼 수 있다. A가 비었다는 이유로 B의 오프셋까지 비어 있는 것은 아니다.

  3. 8 ms에 AB가 도착하면 A의 0–3이 이어져 ABCD를 내보낸다.

  4. 비교용 단일 TCP 바이트열을 ABCDXY로 정하고 최초 AB만 같은 시각까지 빠졌다면 일반 순서 읽기는 뒤의 XY도 앞 빈칸을 기다린다. 이 비교는 정확한 사건을 고정한 모형이지 두 구현의 처리속도 측정이 아니다.

B는 3 ms, A는 8 ms에 순서 있는 데이터를 읽을 수 있다. 스트림 내부 순서는 유지하면서 서로 다른 스트림의 빈칸은 구별한다.

종이와 본문으로 직접 해보기

같은 사건에서 B의 XY도 9 ms에 도착하면 어느 스트림이 먼저 읽히는가? 별도 가상 송신 제한으로 A에 새 바이트 5개/B에 5개를 보내려는데 스트림별 한도는 각각 5, 연결 전체 새 바이트 한도는 8이다. 모두 한 번에 보내도 되는가?

힌트 보기

시각 사건과 연결 합계를 각각 계산하라.

풀이 보기

A는 8 ms, B는 9 ms여서 A가 먼저다. 스트림 간 순서는 고정되지 않는다. 새 바이트 합 10은 연결 한도 8을 넘으므로 모두 보낼 수 없다. A에 5바이트, B에 3바이트를 보내면 스트림별 한도와 연결 합 8을 만족한다. 이 표는 남은 전송 허용량을 가정하여 새 바이트만 세며 재전송을 새 바이트로 중복 계산하지 않는다. 실제 규격의 한도는 누적 오프셋을 기준으로 한다.

오해와 반례

QUIC은 UDP 기반이므로 순서나 재전송이 없고 손실이 있어도 다른 작업은 절대 느려지지 않는다.

UDP 운반과 QUIC의 기능은 별도다. A의 빈칸은 A의 순서 읽기를 지연시킨다. B는 그 순서 제약을 피할 수 있어도 공유 혼잡·흐름 제어·응용 의존성으로 느려질 수 있으므로 절대 지연 없음은 보장하지 않는다.

한 단계 더

B가 A의 처리 결과를 참조하는 응용이라면 B의 네트워크 도착 3 ms와 응용 처리 가능 8 ms를 별도 열로 적어 보라. 전송 독립성과 응용 의존성을 분리하면 도착 순서만 보고 전체 서비스 완료를 단정하는 실수를 줄일 수 있다.
