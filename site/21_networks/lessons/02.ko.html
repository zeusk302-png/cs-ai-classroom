소단원 2.1

클라이언트·서버·P2P

친구에게 파일을 받던 컴퓨터가 다른 친구에게 파일을 줄 수도 있을까?

준비 개념과 학습 목표

준비 개념

  • 프로세스는 프로그램이 실행되는 상태다. 호스트는 네트워크에 연결된 실행 환경이며 프로세스의 역할과 물리 컴퓨터 한 대는 같은 분류가 아니다.

  • 요청은 상대에게 원하는 일을 표시한 메시지이고 응답은 그 요청에 대한 결과 메시지다. 메시지 도착과 요청한 업무 성공을 구별한다.

  • 가상 연결 화살표 X→Y는 X가 Y에 요청한다는 뜻이다. 이번 종이 모형에서는 모든 참여자 주소를 알고 메시지는 손실 없이 전달된다고 가정한다.

학습 목표

  • 연결별 요청자/제공자 역할과 전체 서비스 배치를 구별한다.

  • 한 프로그램이 서로 다른 연결에서 양쪽 역할을 하는 예를 추적한다.

  • 혼합 P2P의 탐색 의존성과 이미 알려진 상대 전송을 분리한다.

두 친구에게 파일을 나누어 받아도 목록 서버는 필요할까?

새 종이 서비스에서 파일 F는 조각 F1/F2로 나뉜다. A는 목록 D에 두 조각의 제공자를 묻고 12 ms 뒤 B/C의 주소를 얻는다. A는 두 주소를 사전에 모른다. B의 F1 전송은 40 ms, C의 F2 전송은 60 ms다. 이 시간은 각 요청 시작부터 완전 수신까지이며 두 전송에는 서로 독립된 충분한 자원이 있다고 정한다. 지연·전송 비용을 추가로 중복 더하지 않는다. 조각 번호·버전·내용 검사가 모두 통과하고 손실이 없다고 가정한다.

두 조각을 동시에 요청하면 시각 12 ms에 둘 다 시작한다. F1은 52 ms, F2는 72 ms에 끝나므로 전체 F는 72 ms에 완성된다. 같은 일을 직렬로 하면 12+40+60=112 ms다. 독립 자원이 없는 공유 병목에서는 두 단독 전송 시간을 그대로 병렬 완료식에 넣을 수 없다. 이 모형의 계산은 P2P 자체의 무조건적인 속도 보장이 아니다.

A는 D/B/C에 요청할 때 이용자이고, 전체 F를 가진 뒤 K의 요청을 처리할 때 제공자가 된다. K의 요청은 A가 전체 F를 받은 직후 시작하고 30 ms가 걸린다고 정하면 K는 102 ms에 완성한다. D는 파일 본문을 전달하지 않아도 새로운 제공자를 찾는 기능의 의존점이다. 목록 응답 이후 D만 고장 나는 것과 B/C가 고장 나는 것은 서로 다른 실패다.

먼저 확인할 개념
  • 연결별 역할과 혼합 구조

    목록 조회와 파일 전송에 각각 요청자/제공자를 붙인다.

  • 완료 조건과 객체 의존성

    조각 하나의 완료를 파일 전체 완료로 바꾸지 않는다.

1. 역할을 연결에 붙인다

클라이언트·서버 모형은 요청하는 쪽과 요청을 처리하여 응답하는 쪽을 구별한다. HTTP 규칙에서도 이 말은 특정 연결에서의 역할이다. S가 여러 클라이언트의 요청을 처리하는 서비스를 제공할 수 있지만 S라는 컴퓨터가 다른 모든 통신에서도 반드시 서버인 것은 아니다.

종이 서비스에서 학생 A가 목록 서버 D에 “파일 F를 가진 사람”을 묻고 D가 B를 알려 준다고 하자. 이 요청에서 A는 클라이언트이고 D는 서버다. 이어 A가 B에 F를 요청하면 그 연결에서는 B가 제공자다. A도 나중에 C의 F 요청을 받아 줄 수 있다. 같은 A의 역할이 연결마다 바뀌어도 모순이 없다.

2. P2P도 기능별로 구조를 나눈다

P2P에서는 참여자가 서비스를 이용하면서 다른 참여자에게 자원을 제공할 수 있다. 모두가 같은 성능이나 항상 같은 역할을 가져야 한다는 뜻은 아니다. 중앙 목록이나 등록 기능과 참여자 사이 전송을 결합한 혼합 구조도 가능하다. P2P와 중앙 기능을 단 하나의 장비 유무로만 판별하지 않는다.

자체 모형은 D가 주소 목록을 제공하고 A,B,C가 파일을 전달한다. 탐색이 D에 의존하더라도 이미 얻은 B의 주소를 사용한 전송은 별도 경로로 수행될 수 있다. 반대로 D가 고장 나면 처음 들어온 참여자가 상대를 찾지 못할 수 있다. 실제 시스템에는 주소 변경·접근권한·NAT·참여자 이탈과 인증 조건이 더 필요하다.

3. 배치 이름만으로 품질을 증명하지 않는다

중앙 서버는 자원·정책을 모아서 관리하기 쉽지만 그 기능의 장애나 병목에 대한 설계가 필요하다. 참여자 분산은 제공 경로를 늘릴 수 있지만 상대가 사라지거나 협력하지 않는 경우를 처리해야 한다. 아래 예제는 파일이 작고 전송 성공을 명시적으로 가정하므로 실제 처리율이나 신뢰도 결론은 내리지 않는다.

요청을 보냈다는 사실과 파일을 받았다는 사실, 받은 파일이 원하는 버전이라는 사실은 서로 다른 관측이다. 종이 계약에서는 F의 식별자와 내용이 고정되어 있고 제공자가 정확한 F를 보내면 수신자가 저장했다고 기록한다. 외부 서비스나 실제 파일을 조회하는 활동은 필수로 하지 않는다.

중간 과정을 따라가는 예제

가상 파일 F의 내용은 고정이다. D 목록에는 F→B가 있고 B가 F를 보유한다. A는 D와 B 주소를 안다. 손실·지연·권한 오류는 없고 목록 질의1회, 파일 전송1회씩만 한다. 다음에 C가 이미 알고 있는 A에게 F를 요청한다.

  1. A→D 목록 요청, D→A B주소 응답. 이 연결에서 A=클라이언트,D=서버다. 파일 내용은 아직 전송되지 않았다.

  2. A→B F요청, B→A F전송. B는 이 연결의 서버 역할이며 정상 수신 뒤 A도 F를 보유한다.

  3. C→A F요청, A→C F전송. A는 새 연결에서 서버 역할이 된다. C는 D를 다시 물을 필요가 없다고 가정했다.

  4. 목록 응답1개와 파일 전송2개를 구별한다. A는 첫 두 요청의 클라이언트이고 마지막 요청의 서버다.

역할은 A라는 호스트에 영구히 하나로 붙지 않는다. D의 탐색 기능과 B/A의 파일 제공 기능은 서로 다른 의존 경로다.

왜 전체 F는 52 ms가 아니라 72 ms에 완성하는가?

  1. F1/F2 모두 있어야 전체 파일을 조립한다.

  2. 병렬 완료는 max(12+40,12+60)=72 ms다.

종이와 본문으로 직접 해보기

같은 모형에서 D가 첫 목록 응답 뒤 멈춘다. A는 B의 주소를 이미 저장했고 B는 살아 있으며 F전송을 허용한다. A의 기존 전송과 B의 주소를 전혀 모르는 새 E의 탐색이 각각 가능한지 종이에 판단하라.

힌트 보기

실패한 기능이 필요한 단계인지 확인한다. E가 다른 탐색 경로를 가졌다고 임의로 추가하지 않는다.

풀이 보기

A는 저장된 주소로 B에게 F를 받을 수 있다. E는 D만을 통한 탐색 계약에서는 B를 찾지 못한다. D 장애가 모든 기존 연결을 자동 종료하거나 반대로 모든 참여자의 서비스가 계속된다는 보장을 뜻하지 않는다.

오해와 반례

P2P이면 중앙 기능이 없고 어느 참여자가 사라져도 모든 작업이 성공한다.

중앙 탐색 D를 가진 혼합 구조가 반례다. E의 탐색은 D에 의존하며 F의 유일 제공자 B가 없어지면 A의 전송도 실패할 수 있다. 역할 분산만으로 가용성 보장이 생기지 않는다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

목록 d≥0, 독립 조각 n≥1개의 완료 비용 t_i≥0일 때 전체 완료식을 쓰고 공유 병목에서 왜 재계산하는지 설명하라.

힌트 1

모든 요청은 목록 완료 후 동시에 시작한다.

힌트 2

각 t_i는 다른 조각과 함께 실행되어도 유지된다는 가정이다.

풀이와 답 확인

  1. 독립 병렬 완료는 d+max_i(t_i)다.

  2. 직렬이면 d+Σ_i t_i다.

  3. 같은 제한된 링크를 공유하면 t_i 자체가 변하므로 자원 배치와 사건표를 다시 정한다.

가정이 유지된 범위에서만 두 식을 사용한다.

소단원 2.2

HTTP와 웹 객체

HTML을 받았는데 그림은 아직 보이지 않는 이유는 무엇일까?

준비 개념과 학습 목표

준비 개념

  • URI는 자원을 식별하는 표현이다. 자원과 그 시점에 전송하는 표현 데이터는 구별한다. 같은 자원의 표현은 시간·선택 조건에 따라 바뀔 수 있다.

  • 웹 객체는 이 단원의 간단한 모형에서 HTML이나 이미지처럼 따로 요청하는 표현이다. 1kB=1000바이트이고 1바이트=8비트다.

  • 왕복 시간 RTT는 요청이 갔다 응답이 돌아오는 경로 지연의 모형 값이다. 초 s와 밀리초 ms는 1s=1000ms로 연결한다.

학습 목표

  • 메서드·대상·상태·표현을 구별한다.

  • HTML과 참조 객체의 의존 요청 순서를 추적한다.

  • 캐시의 신선도와 실제 최신 내용 보장을 구별한다.

캐시 재검증의 304는 빈 웹페이지를 뜻할까?

새 HTTP 종이 모형은 /index HTML 1,000 B를 받은 뒤에야 /a와 /b 이미지 URI를 알게 된다. 이미지 크기는 2,000 B/3,000 B다. 모든 연결은 이미 준비되어 있고 각 요청 RTT는 10 ms, 본문 유효 전송률은 각각 1,000,000 bit/s다. 헤더·요청·처리·TLS·DNS·손실 비용을 무시한다. 두 이미지 요청은 독립 자원으로 병렬 실행되며 HTML·두 이미지의 완전 수신을 완료로 정한다. 실제 브라우저의 렌더링 시간표는 아니다.

HTML은 10+8=18 ms다. 이어 이미지들은 각각 10+16=26 ms와 10+24=34 ms가 걸려 44/52 ms에 끝난다. 전체는 52 ms다. 직렬 이미지라면 18+26+34=78 ms다. URI를 HTML에서 처음 알아내는 조건 때문에 처음부터 세 요청을 동시에 시작한 34 ms는 허용되지 않는다.

별도 캐시 예제는 /a의 한 선택된 표현만 저장하고 저장·선택 조건은 모두 충족한다고 정한다. 강한 ETag "v1", 본문 2,000 B, 신선도 수명 30 s를 저장했다. 현재 age가 30 s이면 엄격한 비교 30>30이 거짓이라 stale다. 이 모형은 stale 제공을 허용하지 않아 If-None-Match: "v1"으로 재검증한다. 서버가 같은 선택 표현을 확인해 대응하는 304를 반환하면 저장 본문을 재사용하고 제공된 메타데이터를 갱신한다. 304 자체에 새 2,000 B 본문이 없다고 해서 저장 본문까지 없어지는 것은 아니다.

표현이 바뀌어 서버가 새 ETag "v2"와 2,000 B 본문을 담은 200을 반환하면 새 응답을 사용한다. 재검증 비용은 헤더를 무시한 모형에서 304는 RTT 10 ms, 전체 200은 26 ms다. fresh는 그 캐시 규칙에 따른 재사용 가능성이고 실제 원본이 한 번도 바뀌지 않았다는 보증이 아니다. 검증 응답의 선택·매칭 조건을 생략해 아무 304로 모든 캐시를 갱신하지 않는다.

  • 연결별 요청자와 제공자

    같은 캐시도 응답 제공자이면서 재검증 요청자가 될 수 있다.

1. 요청 메시지와 표현을 구별한다

HTTP 요청에는 메서드와 대상이 있고 응답에는 상태 코드와 해당 의미에 맞는 데이터 등이 있다. GET은 대상 자원의 선택된 표현을 요청한다. 성공한 GET의 표현이 곧 서버의 모든 저장 상태이거나 요청자에게 가능한 모든 표현을 뜻하지 않는다. 코드200만 보고 화면이 의도대로 완성되었다고 판단할 수도 없다.

자체 사이트 모형에서 /index는 HTML이고 그 내용이 /pic.png를 참조한다. 첫 요청 성공 뒤 HTML을 해석해야 이미지 URI를 알 수 있다고 가정한다. 여기서는 HTML과 이미지의 두 표현을 모두 받는 것을 완료 조건으로 정한다. 브라우저 렌더링·스크립트 실행·다른 요청은 모델에서 제외한다.

2. 전송 시간을 계산하려면 숨은 조건을 적는다

아래 모형은 연결이 이미 준비된 직렬 요청 두 개, 고정 RTT=20ms, 유효 전송률 r=800000비트/s를 가정한다. 각 객체의 시간은 RTT+8L/r이다. 요청·헤더 바이트와 처리·TLS·DNS·혼잡·손실 비용은 무시하고 RTT에는 객체 본문 직렬화 시간을 중복 포함하지 않는다. 이 식은 HTTP 표준의 성능 보장식이 아니다.

HTML L=1000바이트의 본문시간은 10ms, 이미지 L=3000바이트는 30ms다. 두 요청을 직렬로 완료하면 30+50=80ms다. 실제 HTTP 버전·연결 재사용·다중화·캐시·미리 가져오기와 병렬 요청이 바뀌면 이 단순 합을 그대로 적용할 수 없다. 바이트와 비트를 섞으면 8배 오류가 난다.

3. 캐시는 조건을 만족할 때 표현을 재사용한다

HTTP 캐시는 저장된 응답의 재사용 가능성·요청 조건 등을 확인한다. 신선도 계산은 freshness_lifetime>current_age라는 엄격 부등호를 사용한다. 아래 활동은 다른 모든 캐시 허용조건이 만족되고 강제 검증 요청도 없으며, 제공된 age가 이미 올바르게 계산되었다고 가정한다. 시간 경과만으로 모든 캐시 규칙을 대신하지 않는다.

fresh는 정해진 캐시 정책에서 검증 없이 사용할 수 있다는 성질이며 서버의 현재 내용과 반드시 동일하다는 증명이 아니다. 만료된 응답도 상황에 따라 검증이나 별도의 stale 허용 규칙이 관련될 수 있다. 이 단원 활동은 stale이면 재사용 전에 검증하도록 좁힌 계약이며 실제 전체 캐시 구현을 시험하지 않는다.

중간 과정을 따라가는 예제

연결 준비 완료, 직렬 GET 두 개. 첫 HTML은 1000바이트, 그 HTML 해석 뒤 필요한 이미지는 3000바이트다. r=800000비트/s, RTT=20ms이며 헤더·서버 처리·DNS·TLS·손실은 제외한다. HTML과 이미지 전체 수신을 완료로 정한다.

  1. HTML 본문은 1000·8=8000비트다. 8000/800000=0.01s=10ms이다.

  2. HTML 요청 완료 시간은 20+10=30ms이다. 이때 이미지 URI를 알게 된다고 가정한다.

  3. 이미지는 3000·8/800000=0.03s=30ms, 요청 완료 시간은 20+30=50ms이다.

  4. 직렬 의존 요청이므로 전체는 30+50=80ms이다. 총 본문 4000바이트의 전송 시간 40ms와 RTT 두 번 40ms를 더해도 80ms다.

가상 모형의 전체 수신 시간은 80ms이다. 실제 웹페이지 로딩 시간을 측정한 값이 아니다.

소단원 2.3

DNS와 이름 해석

이름을 주소로 바꾸었는데 왜 웹서비스는 아직 실패할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 도메인 이름은 점으로 나눈 이름 구조다. DNS는 이름에 연결된 자원 레코드를 질의하는 분산 시스템이다.

  • 리졸버는 질의 결과를 찾는 역할이고 권한 서버는 자기가 담당하는 영역의 레코드를 제공한다. 안내 referral은 최종 답 대신 다음에 질의할 서버를 알려 주는 응답이다.

  • TTL은 레코드 캐시의 남은 유지 시간과 관련되는 초 단위 값이다. 캐시 레코드와 웹 본문 캐시는 서로 다른 자료다.

학습 목표

  • 레코드 타입과 질의 대상을 구별한다.

  • 재귀 요청과 referral을 따르는 리졸버의 반복 질의를 추적한다.

  • TTL 경과·이름 없음·주소 자료 없음·일시 실패를 구별한다.

별칭과 주소의 TTL이 다르면 무엇을 다시 물어야 할까?

새 DNS 종이 캐시는 시각 0 s에 x의 IN CNAME y를 TTL 20 s로, y의 IN A 예시주소 P=192.0.2.10을 TTL 60 s로 저장한다. 각각의 RR은 별도 만료를 갖는다. 시각 10 s에는 남은 TTL이 10/50 s여서 두 기록으로 주소를 얻는다. 각 레코드를 τ≤t<τ+TTL에서만 재사용하는 정책이고 stale 제공은 하지 않는다. 질의 지연은 0 s로 이상화하며 권한 서버 주소를 이미 알고 있어 아래 외부 질의는 해당 레코드 조회 한 건씩만 센다. 루트·상위 위임·추가 주소 질의 비용은 이 새 모형에 없다.

시각 20 s에는 x의 별칭만 만료한다. 권한 서버에서 현재 x→z와 TTL 20 s를 받는다. z의 A는 캐시에 없어 별도로 질의해 주소 Q=192.0.2.20과 TTL 40 s를 저장한다. 외부 질의는 두 번이다. y의 A에는 여전히 40 s가 남지만 현재 x는 z를 가리키므로 y의 주소를 사용하면 다른 이름의 답을 섞게 된다. 시각 30 s에는 x의 CNAME에 10 s, z의 A에 30 s가 남아 외부 질의 없이 재사용한다.

시각 40 s에 x 별칭을 다시 묻자 서버는 x→y, TTL 20 s를 돌려준다고 정한다. y의 A는 시각 0의 TTL 60 s가 아직 20 s 남아 있어 재사용하고 외부 질의는 한 번이다. z의 A 역시 남아 있지만 이번 x 답에는 쓰이지 않는다. 같은 문자열이 캐시에 있다는 이유만으로 타입과 별칭 연결을 무시하지 않는다.

또 다른 관계 x→y/y→x에서는 주소가 나오지 않는 순환을 발견한다. 자체 리졸버는 이번 질의에서 방문한 이름을 기록하고 반복을 발견하면 별칭 순환 오류로 멈춘다. 이 오류는 이름이 없다는 권한 응답과 다르다. TTL 0인 A는 현재 진행 중 질의에서만 쓸 수 있고 다음 독립 질의에 캐시 재사용하지 않는다. 주소 획득과 실제 서버/포트/권한/HTTP 성공도 별도다.

먼저 확인할 개념
  • 레코드 타입·TTL·질의 책임

    CNAME은 다른 이름이고 A는 주소이며 각각의 만료 시계를 추적한다.

  • DNS 자료와 HTTP 본문 캐시

    주소의 TTL을 본문 신선도와 같은 저장물로 취급하지 않는다.

1. 이름은 항상 하나의 주소와 일대일이 아니다

DNS 자원 레코드는 이름, 타입, 클래스, TTL과 타입별 자료를 가진다. IN 클래스 A는 IPv4 주소를 담고 CNAME은 별칭의 정식 이름을 가리킨다. 같은 이름에 주소 여러 개가 가능하고 다른 타입의 자료도 있다. 이름을 단순히 문자열 하나에서 숫자 하나로 바꾸는 전체 일대일 함수라고 가정하지 않는다.

아래 가상 질의는 한 이름의 IN A 레코드만 찾고 별칭은 없다고 가정한다. 답변은 192.0.2.10이라는 예시 주소이며 실제 접속하지 않는다. 주소를 얻어도 그 주소의 서버가 살아 있는지, 원하는 포트가 열려 있는지, 사용자 권한과 웹 내용이 정확한지는 별도 문제다.

2. 재귀와 반복 질의의 책임을 분리한다

클라이언트는 리졸버에 최종 결과를 찾아 달라고 재귀 질의를 요청할 수 있다. 리졸버는 필요할 때 다른 서버에서 받은 referral을 따라 다음 서버에 질의한다. 모든 DNS 서버가 모든 클라이언트에 재귀 서비스를 제공해야 하는 것은 아니다.

종이 모형은 캐시 없는 리졸버 R이 루트→상위 영역→권한 서버 순서로 세 번 질의하여 최종 A를 얻는다고 정한다. 루트가 웹 파일을 보내거나 항상 최종 주소를 직접 주는 모형이 아니다. 실제 캐시·이미 알려진 위임·별칭·오류·병렬성에 따라 질의 횟수는 달라질 수 있다. 세 번이라는 수에는 루트 주소의 시작 설정과 안내된 서버의 접속 주소 확보를 가정한다. 이 주소를 추가 DNS 질의로 찾아야 하면 그 질의도 따로 세어야 한다.

3. 캐시 수명은 서비스 건강 검사가 아니다

TTL은 레코드를 캐시에 유지할 시간 제한이다. 단순 캐시 모형에서 t=0에 TTL 60s로 답을 저장하면 경과 t에서 남은 값은 60−t초이고 0≤t<60에서는 남은 시간이 양수다. 이 활동은 t≥60이면 만료하여 재질의하고 연장하거나 stale을 제공하지 않는 정책을 명시한다.

권한 측 주소가 TTL 안에 바뀌어도 캐시 답은 이전 값일 수 있다. 따라서 TTL이 남았다는 것은 현재 내용 동일성이나 가용성 증명이 아니다. 이름이 없다는 결과와 이름은 있지만 원한 타입 자료가 없는 결과, 일시적 질의 실패도 구별한다. 시간 초과만으로 권한 서버가 영구히 멈췄다고 판정하지 않는다.

주소는 P다. x의 CNAME에 남은 TTL은 1 s, y의 A에 남은 TTL은 41 s이며 외부 질의는 0회다.

  2. TTL 0 A를 첫 질의에 사용해도 두 번째는 새로 조회한다.

다른 문제에 적용하기

세 보고서를 고쳐라. ① 목록을 12 ms 만에 받은 뒤 독립 자원에서 각각 40 ms와 60 ms가 필요한 두 조각을 동시에 받는다. 전체 파일 F의 완료 시간이 112 ms라는 주장과 목록 응답 뒤 D의 고장이 A의 전송을 반드시 중단한다는 주장을 검토하라. ② HTML은 1,000 B이고 이를 받은 뒤 두 이미지 URI를 알게 된다. 이미지 크기는 2,000 B와 3,000 B, 각 RTT는 10 ms이고 각 전송률은 1 Mbps다. 완료 시간이 34 ms라는 주장과 매칭 304가 저장 본문을 삭제한다는 주장을 검토하라. ③ 시각 0 s에 x의 CNAME을 TTL 20 s로, y의 A를 TTL 60 s로 저장했다. 시각 20 s의 새 별칭은 x→z이고 z의 A는 미저장인데, 외부 질의 없이 P를 쓴다는 주장을 검토하라. 모든 가상 조건과 실제 미수행 범위를 적어라.

풀이와 답 확인

  1. ① 전체 파일 F의 완료 시간은 12+max(40,60)=72 ms다. D의 응답 뒤 A에는 유효한 주소가 있으므로 살아 있는 B와 C에서 전송을 계속할 수 있다.
