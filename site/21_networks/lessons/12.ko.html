  • 암호화가 제공하는 범위와 키 관리 조건을 설명한다.

전송 내용이 보호되어도 다른 학생의 파일 삭제 요청을 받아들여야 할까?

새 과제 서비스의 서버가 검증한 주체는 학생 S 또는 교사 T다. 파일 X의 소유자는 S, 파일 Y의 소유자는 다른 학생 U다. 정책은 학생이 자기 파일을 읽고 수정할 수 있고, 교사는 배정된 학급의 파일을 읽고 수정할 수 있으며, 삭제는 소유자에게만 허용한다고 정한다. 로그인 신원과 대상 파일의 소유자·학급 정보를 서버가 제공한 모형이다.

요청 본문에 role=teacher라고 적는 것은 서버가 확인한 신원을 바꾸지 않는다. 신원 인증 이후에도 주체·동작·대상·학급을 이용해 허용 조건을 따로 검사한다. HTTPS 전송이 성공했다고 이 업무 조건을 생략하면 보호된 경로를 통해 잘못된 작업이 실행될 수 있다.

보호할 자산도 나눈다. 경로에서 과제 내용이 읽히는 문제, 허가 없이 수정되는 문제, 서버가 멈추는 문제는 각각 기밀성·무결성·가용성의 질문을 만든다. 보호 채널과 권한 정책을 마련해도 손상된 끝점이나 공개 로그까지 자동 해결됐다는 뜻은 아니다.

무엇을 누구에게서 보호할지 정한다

위협을 이야기하려면 먼저 보호할 자산과 경로를 정한다. 예를 들어 과제 파일, 로그인 자격 증명, 서버 사용 가능 시간은 서로 다른 자산이다. 우연한 오류도 문제를 만들 수 있으며 모든 사고를 의도적인 공격으로 단정하지 않는다.

허가 없는 읽기는 기밀성, 몰래 바꾸는 행위는 무결성, 사용할 수 없게 만드는 행위는 가용성 문제로 볼 수 있다. 가능한 위험인 위협, 약점인 취약점, 이미 일어난 행위를 구별하면 근거 없이 성공률을 붙이는 일을 줄인다.

이름을 말하는 것과 증명하는 것은 다르다

인증은 제시한 신원 등의 주장을 근거로 확인하는 과정이다. 메시지의 이름 칸에 교사라고 적는 것만으로 교사 신원을 확인한 것은 아니다. 인증 결과를 이용해 허용할 작업을 정하는 권한 부여는 별도 판단이다.

로그인한 학생도 자기 제출물을 읽을 권한만 있고 다른 학생의 내용을 바꿀 권한은 없을 수 있다. 공유 계정·유출된 자격 증명·종료되지 않은 세션은 인증 근거의 의미를 약하게 만들 수 있다. 단순 사용자 이름 비교는 안전한 로그인 시스템 구현이 아니다.

내용 보호와 출처 확인을 함께 설계한다

암호화는 적절한 키를 가진 쪽만 내용을 해석하도록 만드는 수단이다. 키를 어디서 얻고 상대가 누구인지 어떻게 확인했는지가 중요하다. 암호화라는 단어 하나만으로 변경 탐지나 신원 확인이 항상 제공되는 것은 아니다.

현대 보호 채널은 인증과 변경 탐지를 함께 구성한다. TLS 1.3은 인증된 암호화 방식으로 통신 내용을 보호하지만 끝점의 탈취·업무 권한·서비스 중단은 다른 문제다. 교육용 문자 치환이나 무키 체크섬을 실제 보안 알고리즘 대신 쓰지 않는다.

중간 과정을 따라가는 예제

자체 과제 서비스에서 세 사건을 분류하라. X는 경로에서 과제 내용을 읽는다. Y는 점수 80을 90으로 바꾼다. Z는 자신을 교사라고 주장하며 다른 학생의 점수를 수정하려 한다. 각 사건에 필요한 확인 질문을 적어라.

  1. X에는 누가 내용을 읽을 권한이 있는지, 전송 경로에서 평문이 노출되는지 묻는다. 적절한 보호 채널은 경로 노출을 줄이지만 서버 내부 접근은 별도다.

  2. Y에는 원본과 변경을 검증하는 근거가 있는지, 바뀐 메시지를 받아들이지 않는지 묻는다. 일반 암호화 사용 여부만 확인하고 끝내지 않는다.

  3. Z에는 교사라는 주장을 검증했는지 먼저 묻고, 그 계정이 해당 학생의 점수를 바꿀 권한이 있는지도 따로 확인한다.

X는 주로 기밀성, Y는 무결성, Z는 신원 인증과 권한 부여 문제다. 한 수단으로 모든 질문이 해결됐다고 세지 않는다.

조건을 바꾸어 비교하기

교사 인증과 삭제 권한을 나눈다

담당 교사 T가 U의 파일 Y를 수정하고 삭제하려 한다. 두 결과를 구하라.

  1. T의 신원이 확인되어 있고 U가 담당 학급이므로 수정 조건을 만족한다.

  2. 삭제는 소유자만 허용하고 Y의 소유자는 U이므로 T의 삭제 요청은 거부한다.

수정 허용, 삭제 거부다. 교사 신원 확인만으로 삭제 정책을 변경하지 않는다.

비교할 점

기본 학생의 타인 접근 거부를 교사의 제한된 업무 권한으로 확장한다.

본문의 이름은 인증 근거가 아니다

S의 인증 세션에서 Y 수정 요청 본문에 actor=T와 role=teacher가 들어왔다. 서버 모형의 결과는?

  1. 검증 주체는 여전히 S다. 요청자가 적은 역할과 이름을 인증 결과로 대체하지 않는다.

  2. Y는 U의 파일이라 학생 S의 자기 파일 수정 조건을 충족하지 않는다.

거부한다. 본문 내용이 암호화되어 도착했어도 업무 권한의 근거가 되지 않는다.

연습 1 · 값과 상태 예측

교사 T가 담당하지 않는 학급의 학생 V 파일 Z를 읽으려 한다. 주체 인증은 성공했다. 결과는?

힌트 1

교사 읽기는 담당 학급 조건이 있다.

힌트 2

신원 확인과 대상 범위를 따로 검사한다.

풀이와 답 확인

  1. T는 교사지만 V가 담당 학급에 없어서 읽기 조건을 만족하지 않는다.

  2. 이 요청은 주어진 정책에서 거부한다.

읽기 거부다. 인증 성공은 학급 범위 조건을 대신하지 않는다.

역할뿐 아니라 대상과 담당 범위를 포함한 정책을 적용해야 한다.

풀이와 답 확인

  1. 검증 주체 S와 대상 소유자 U를 별도 값으로 유지한다.

  2. 자기 파일 조건이 아니므로 학생 S의 수정·삭제를 거부한다.

HTTPS를 소유권 증거로 사용하지 않는다. 서버가 확인한 소유자와 작업 권한을 검사한다.

학생 S의 자기 파일 X 수정과 삭제를 허용하고 타인 파일 Y에는 둘 다 거부하는 결정표를 구성하라.

힌트 1

힌트 2

주어진 정책에서 소유 여부가 두 동작에 어떻게 쓰이는지 확인한다.

풀이와 답 확인

  1. X는 S 소유이므로 수정 허용과 삭제 허용이다.

  2. Y는 U 소유이므로 수정 거부와 삭제 거부다.

X={수정 허용,삭제 허용}, Y={수정 거부,삭제 거부}다. 실제 API 검증을 수행한 결과가 아닌 정책표다.

자기 파일을 수정할 수 있어도 이 정책에서는 삭제를 못 한다.

주어진 삭제 규칙은 소유자에게 허용한다. 일반적인 상상을 보태지 말고 명시한 업무 조건을 적용한다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

서버가 TLS로 받은 X를 공개 로그에 기록했고 장애로 접속도 끊겼다. 노출과 중단을 분류하고 TLS 성공이 왜 해결 근거가 아닌지 설명하라.

힌트 1

힌트 2

풀이와 답 확인

  1. 로그의 허가 없는 읽기는 기밀성 문제다.

  2. 접속 중단은 가용성 문제이며 원인이 장애·실수·공격인지는 추가 증거가 필요하다.

TLS 전송 보호와 별도로 로그 접근 정책 및 서비스 복구를 검토해야 한다. 실제 원인을 추정하여 공격 성공으로 기록하지 않는다.

끝점 저장과 서비스 운영은 통신 구간 보호의 보장 범위를 벗어난다.

한 레이블 wildcard와 재전송 안전성은 어디까지 적용될까?

새 이름 비교 모형에서 기준 이름은 a.learn.example이고 제시된 인증서의 DNS 식별자는 *.learn.example이다. wildcard를 지원하는 기술과 클라이언트라고 정한다. 이 별표는 가장 왼쪽의 완전한 한 레이블을 대신하므로 a.learn.example은 맞지만 learn.example이나 b.a.learn.example은 맞지 않는다. 이름 검사만으로 신뢰 경로·기간·키 소유 등 다른 검증을 끝낸 것은 아니다.

별도 경로는 브라우저 C→프록시 P→서버 S다. C–P는 TLS, P–S는 평문이고 P는 TLS를 종료한다. 경로에 있는 관찰자와 끝점 P가 내용을 볼 수 있는지는 다르다. P–S도 TLS로 바꾸면 그 구간의 경로 내용은 보호하지만 P와 S가 자기 끝점의 내용을 사용하는 사실은 남는다.

0-RTT의 보호된 데이터에는 연결 사이의 재전송을 자동 배제하는 보장이 없다. 새 가상 응용은 요청 하나마다 제출 횟수를 1 증가시키며 중복 제거가 없다. 같은 요청이 두 번 처리되면 2가 된다. 이는 실제 재전송 공격 실험이 아니라 처리 의미를 비교하는 종이 모형이다. 업무 식별자 기반 중복 제거를 별도로 적용하는 경우도 TLS 자체 보장과 구별한다.

  • 인증과 업무 권한

협상과 보호된 데이터 전송

TLS는 두 끝점 사이의 보호 채널을 구성한다. TLS 1.3의 handshake는 사용할 조건과 키 자료를 정하고 필요한 신원을 확인한다. 이후 record 계층이 통신 데이터의 기밀성과 변경 탐지를 제공한다. 알고리즘 명칭과 키 교환·서명·사용자 로그인은 서로 같은 동작이 아니다.

일반적인 인증서 기반 웹 연결에서는 서버 인증을 수행한다. 클라이언트 인증서는 별도 선택이며 웹의 사용자 로그인은 보통 그 위의 응용 기능이다. 사전 공유 키 방식도 있으므로 모든 TLS 연결이 같은 인증서 메시지를 보내는 것으로 외우지 않는다.

기대한 이름을 확인한다

클라이언트는 접속하려는 서비스의 기준 이름과 서버가 제시한 인증서 신원을 맞춰야 한다. 신뢰할 수 있는 인증 경로와 유효 기간 등도 검사하며 이름이 맞는 것 하나만으로 전체 검증을 끝내지 않는다. 인증 경로 상세 검증과 이름 비교는 연결된 다른 검사다.

아래 예제는 소문자 ASCII 이름이 정확히 일치하는 단순 사례다. learn.example과 api.example은 서로 다르다. 실제 이름 검사는 subjectAltName의 적절한 식별자를 사용하고 IP 접속·국제화 이름·wildcard는 별도 규칙을 따른다. 인증서의 Common Name만 비교하는 자체 검증기를 만들지 않는다.

TLS가 끝나는 곳을 표시한다

클라이언트 C가 프록시 P와 TLS를 맺고 P가 서버 S로 다른 연결을 만들면 두 구간은 별개다. P는 첫 연결의 끝점이므로 전달할 내용을 해석할 수 있다. C–P가 보호돼도 P–S의 평문 전송이나 S 내부 저장까지 자동 보호되지 않는다.

내용을 전송 중 숨겨도 목적지 IP·전송 시각·크기 같은 관측 정보가 모두 사라지는 것은 아니다. TLS는 서버의 교육 자료가 참인지, 서버가 악성 동작을 하지 않는지, 로그인 권한이 올바른지까지 증명하지 않는다. TLS 1.3의 0-RTT 데이터에는 재전송 위험도 있어 임의의 중복 민감 작업에 일반 1-RTT와 같은 보장을 적용하지 않는다.

유효 wildcard 형식 아님

결과는 DNS 이름 비교 부분에 한정한다. 유효 wildcard는 가장 왼쪽 레이블 전체의 별표 한 개이며 이 표는 실제 인증서 검증기를 구현한 기록이 아니다.

중간 과정을 따라가는 예제

C가 learn.example에 접속한다. 가상 기록 A는 신뢰 경로·기간 검사가 성공하고 인증서 DNS 이름도 learn.example이다. B는 같은 검사에 성공하지만 이름이 api.example이다. A에서는 C–P가 TLS이고 P–S는 평문이다. 각 결론을 적어라.

  1. A는 이 가상 표의 신뢰·기간·이름 조건을 충족한다. 실제 인증서 서명·키 소유 증명·핸드셰이크를 수행한 기록은 아니므로 실제 접속 성공이라고 쓰지 않는다.

  2. B는 기대 이름과 다르므로 다른 검사 성공만으로 learn.example의 서버 신원 검증에 성공했다고 볼 수 없다. 경고를 무시하도록 해결하지 않는다.

  3. A에서 C–P의 경로 관찰자는 TLS 보호를 받는 응용 내용을 직접 평문으로 읽지 못하는 조건이지만 P는 끝점이다. P–S의 관찰자에는 별도의 내용 보호가 없다.

  4. P–S에도 적절히 검증한 TLS를 구성하면 그 구간을 별도로 보호할 수 있다. P와 S 끝점이 내용을 사용할 수 있다는 사실은 남는다.

이름 검증 B는 실패다. A의 C–P 보호를 전체 경로 보호로 확대하지 않는다. 프록시 종료와 뒤쪽 구간을 따로 표시한다.

요청 의미의 중복을 계산한다

제출 횟수는 처음에 0이다. 같은 업무 요청 q가 서로 다른 연결에서 두 번 처리된다. 중복 제거가 없는 모형과 공유 원장에서 q를 최초 한 번만 적용하는 모형을 비교하라.

  1. 중복 제거가 없으면 두 처리에서 각각 1을 더하므로 제출 횟수는 2가 된다.

  2. 공유 기록에서 q를 최초 한 번만 적용한다고 정하면 두 번째 처리는 기존 결과를 반환하고 제출 횟수를 1로 유지한다.

중복 제거가 없으면 결과는 2이고 공유 원장에서 최초 한 번만 적용하면 1이다. 이 차이는 응용 상태의 조건이며, 모든 0-RTT 요청이 반드시 재전송된다는 뜻은 아니다.

방화벽·터널·VPN

허용된 포트로 들어온 패킷과 VPN 안의 패킷은 무조건 안전할까?

준비 개념과 학습 목표

준비 개념

  • IP·포트·프로토콜

  • 경로와 끝점

  • 정책 규칙

학습 목표

  • 방화벽의 정책 판단과 내용 보장을 구별한다.

  • 터널의 캡슐화와 암호화 조건을 구별한다.

  • VPN 끝점·라우팅·오버헤드 범위를 판단한다.

좁은 허용 규칙이 넓은 거부 규칙 아래에 있으면 적용될까?

새 가상 방화벽은 첫 일치 규칙을 적용한다. 먼저 TCP 목적지 포트가 22이고 출발지가 192.0.2.0/24에 속하면 거부한다. 다음으로 TCP 목적지 포트가 22이고 출발지가 192.0.2.64/26에 속하면 허용한다. 그다음 TCP 목적지 포트가 443이면 허용하며, 나머지는 거부한다. 각 입력은 신규 패킷이며 실제 연결 상태나 운영망 규칙을 변경하지 않는다.

두 번째 규칙의 /26에 속하는 마지막 바이트 범위는 64–127이다. 이 주소들은 앞의 /24에도 모두 포함되므로 원래 순서에서는 좁은 허용 규칙에 도달하지 못한다. IP 라우팅의 최장 접두사 선택을 이 첫 일치 정책에 가져오면 결과가 달라진다. 두 규칙을 교환하면 예외를 허용하지만, 새로 접근이 열리는 범위도 명시해야 한다. 이 비교는 규칙의 의미를 연습하는 자체 사례다.

별도 중첩 터널 모형에서 내부 패킷 길이를 L이라고 하자. 터널 1은 60바이트를 추가하고 터널 2는 다시 40바이트를 추가한다. 터널 1의 출력 링크 MTU는 1460바이트이고 터널 2의 출력 링크 MTU는 1500바이트다. 이 고정 오버헤드는 실제 IPsec 제품 수치가 아니다. 두 링크의 출력 길이 조건을 모두 만족해야 한다.

  • 보호 구간과 종료 지점

정책으로 통과 여부를 정한다

방화벽은 설정한 조건에 따라 네트워크 경계의 통신을 제한한다. 패킷 헤더만 보는 단순 규칙, 연결 상태를 고려하는 방식, 응용 내용을 고려하는 방식은 판단 근거가 다르다. 허용 포트로 들어왔다는 사실이 해당 자료의 정확성이나 악성 코드 부재를 증명하지 않는다.

아래 모형은 새로 들어오는 TCP 패킷의 목적 포트와 출발지 그룹을 위에서 아래로 검사하고 처음 맞는 규칙 하나를 적용한다. 실제 제품은 체인·방향·상태·우선순위 규칙이 다를 수 있다. 이 모형을 실제 운영망 설정으로 실행하지 않는다.

터널은 안쪽 패킷을 바깥 패킷으로 운반한다

터널은 원래 패킷을 다른 전송 구조 안에 넣어 두 끝점 사이로 운반하는 방법이다. 내부 목적지와 외부 터널 목적지가 다를 수 있다. 캡슐화 자체는 암호화와 같지 않으므로 보호 알고리즘과 키·인증 조건을 따로 확인한다.

예를 들어 적절한 암호화·무결성 설정의 IPsec 터널은 터널 구간의 내부 패킷을 보호한다. RFC 4301에는 보호·폐기·보호 없이 통과하는 정책도 있다. AH·ESP 및 선택 서비스의 차이가 있어 IPsec이라는 이름만으로 모든 패킷이 모두 암호화됐다고 결론내리지 않는다.

VPN의 범위와 추가 길이를 정한다

VPN은 떨어진 사용자나 망을 논리적으로 연결한다. 어느 트래픽이 터널로 가는지는 라우팅과 정책에 달려 있다. 터널이 끝난 뒤의 연결, VPN 끝점의 접근권한, 사용자 계정·DNS 경로도 별도 조건이다. VPN 접속만으로 익명성이나 모든 서버의 신뢰를 보장하지 않는다.

바깥 헤더와 보호 정보는 패킷 길이를 늘린다. 아래 60바이트 추가 길이는 이해를 위한 고정 모형이며 특정 IPsec·VPN 제품의 실제 고정값이 아니다. 실제 길이는 프로토콜·암호·패딩·IP 버전 등에 따라 달라지고 MTU 조정·분할·경로 발견 처리가 필요할 수 있다.

중간 과정을 따라가는 예제

자체 첫 일치 정책은 ① TCP 목적 포트 443 허용, ② admin 그룹의 TCP 목적 포트 22 허용, ③ 나머지 거부다. 신규 패킷 A=(guest,TCP,443), B=(guest,TCP,22), C=(admin,TCP,22), D=(admin,UDP,443)을 분류하라. 별도 터널 모형의 내부 길이가 1000바이트이고 추가 길이 60, 바깥 MTU 1500이면 길이를 계산하라.

  1. A는 첫 규칙으로 허용된다. B는 첫·둘째 조건에 맞지 않아 거부된다. C는 둘째 규칙으로 허용된다. D는 TCP 조건이 아니므로 거부된다.

  2. 이 표에서 guest가 실제로 믿을 만한 출발지라는 인증까지 수행한 것은 아니다. 출발지 그룹 판정의 근거는 모형이 주는 조건이며 실제 스푸핑 방지와 구별한다.

  3. 내부 1000 + 추가 60 = 바깥 1060바이트라 모형의 MTU 이내다. 이 추가 길이가 고정이면 내부 길이의 단순 상한은 1500 − 60 = 1440바이트다.

  4. A의 허용과 터널의 길이 계산만으로 악성 내용 검사·VPN 인증·성능·전체 경로 보호가 성공한 것으로 세지 않는다.

A와 C는 허용, B와 D는 거부다. 바깥 길이 1060과 모형의 내부 상한 1440은 실제 제품 측정값이 아니다.

중첩 터널의 두 MTU를 동시에 맞춘다

두 터널과 링크 조건에서 분할 없이 통과할 수 있는 내부 패킷 길이의 상한을 구하라.

  1. 첫 링크의 조건은 L + 60 ≤ 1460이므로 L ≤ 1400이다.

  2. 둘째 링크의 조건은 L + 60 + 40 ≤ 1500이므로 L ≤ 1400이다. 두 조건 중 작은 상한을 사용한다.

내부 길이의 상한은 1400바이트다. 첫 출력은 1460바이트이고 둘째 출력은 1500바이트이므로 각각의 MTU 경계에 맞는다.

  2. 둘째 출력은 1501바이트이므로 둘째 MTU를 1바이트 초과한다.

두 링크에서 각각 1바이트 초과한다. 실제로 분할하거나 폐기하는지는 이 모형에 주어지지 않았다.

바깥 MTU만 맞추면 첫 링크의 초과는 상관없다.

패킷은 두 링크를 통과해야 하므로 각 출력의 제약을 따로 적용한다.

연습 2 · 오류 찾아 고치기

원래 표에서 출발지 192.0.2.70의 TCP 목적지 포트 22를 /26이 더 구체적이라는 이유로 허용했다. 이 판단을 고쳐라.

힌트 1

문제에서 정한 정책은 첫 일치다.

힌트 2

첫 /24 규칙도 같은 입력에 일치한다.

풀이와 답 확인

  1. 첫 규칙의 TCP 목적지 포트 22 및 /24 거부 조건에서 검사를 멈춘다.

  2. /26 허용을 적용하려면 규칙 순서를 바꾼 다른 정책이 필요하다.

원래 정책의 결과는 거부다. 최장 접두사 선택 규칙을 여기에 적용하지 않는다.

모든 네트워크 표는 가장 긴 접두사를 우선한다.

선택 기준은 표의 역할과 명시한 규칙에 달려 있다. 라우팅과 이번 필터 모형은 기준이 다르다.

연습 3 · 직접 만들어 보기

터널 2의 오버헤드만 40바이트에서 80바이트로 변경한다. 두 MTU를 유지하면서 새 내부 길이 상한을 구하라.

힌트 1

첫 조건인 L ≤ 1400은 변하지 않는다.

힌트 2

둘째 출력의 누적 추가 길이는 60 + 80바이트다.

풀이와 답 확인

  1. 둘째 조건은 L + 140 ≤ 1500이므로 L ≤ 1360이다.

  2. 두 상한의 최솟값 min(1400, 1360)은 1360이다. 이때 첫 출력은 1420바이트이고 둘째 출력은 1500바이트다.

내부 길이 상한은 1360바이트다. 실제 암호나 패딩의 가변 길이는 이 고정 모형에 포함하지 않았다.

흔한 오답에서 다시 생각하기

터널 2의 오버헤드가 40바이트 늘어도 첫 MTU가 같으므로 상한도 같다.

새 둘째 조건이 더 작은 상한을 만든다. 한 링크의 제약만 검사해서는 안 된다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

VPN 라우팅은 목적지 10.0.0.0/8만 터널로 보내고 나머지는 직접 경로로 보낸다. 10.2.3.4와 203.0.113.7의 경로를 나누고, VPN 접속만으로 전체 보호를 주장할 수 있는지 설명하라.

힌트 1

두 목적지 주소의 첫 바이트를 비교한다.

힌트 2

직접 경로에 별도 TLS가 있는지는 주어지지 않았다.

풀이와 답 확인

  1. 10.2.3.4는 /8 대상이므로 터널로 가며, 203.0.113.7은 직접 경로로 간다.

  2. 터널 뒤 서버 구간과 응용 권한은 별도 조건이다. 직접 경로의 내용 보호 여부는 여기서 미확인이다.

모든 트래픽이 터널을 통과한다는 주장은 틀리다. 직접 경로가 반드시 평문이라고도 추정하지 않는다.

VPN 연결 아이콘이 있으면 모든 주소가 터널을 통과한다.

선택 경로는 주어진 라우팅과 정책에 달려 있다.

어떤 입력의 결과가 바뀌는지 주소·프로토콜·포트별로 비교한다. 좁은 예외도 업무 접근을 열 수 있다.

캡슐화 길이를 알면 암호화도 확인된 것인가?

설명 기준 확인

길이 계산과 보호 서비스 선택은 별도다. 터널이나 IPsec이라는 명칭만으로 모든 패킷의 암호화를 결론내리지 않는다.

한 단계 더

집에서 VPN 게이트웨이까지의 터널과 게이트웨이 뒤 서버까지의 경로를 그리자. 보호 끝점과 허용 서비스, 터널 밖으로 나가는 트래픽을 각각 표시하자. 실제 네트워크 규칙을 바꾸지 않고 종이 정책의 순서만 바꾸어 결과를 비교한다.

다른 문제에 적용하기

새 통합 모형에서 검증된 학생 S가 다른 학생 U의 파일 Y를 수정한다. HTTPS 기준 이름은 a.learn.example이며 *.learn.example이 제시된다. 이름 외 검증도 성공했다고 가정한다. 업무 정책은 자기 파일 수정만 허용한다. 별도 VPN 중첩 모형에서 터널의 추가 길이는 차례로 60바이트와 80바이트이고, 두 출력 링크의 MTU는 각각 1460바이트와 1500바이트다. 내부 패킷 길이는 L = 1380바이트다. 채널 검증·업무 권한·길이 조건을 각각 판정하고, 한 조건의 성공이 다른 조건의 실패를 없애지 않음을 설명하라.

힌트 1

TLS 서비스 이름과 응용 사용자를 서로 다른 신원으로 보라.

힌트 2

각 단계의 출력 길이를 해당 링크의 MTU와 비교하라.

풀이와 답 확인

  1. 기준 이름의 a라는 한 레이블은 별표와 일치한다. 다른 검증도 성공했다고 주었으므로 모형의 TLS 검증 조건은 성공이다.

  2. 학생 S는 파일 Y의 소유자가 아니므로 업무 수정 요청은 거부한다.

  3. 터널 1의 출력은 1380 + 60 = 1440바이트로 첫 MTU인 1460바이트 이내다. 터널 2의 출력은 1440 + 80 = 1520바이트로 둘째 MTU인 1500바이트를 20바이트 초과한다. 새 내부 길이 상한은 1360바이트다.

TLS 검증 조건은 성공이고 업무 수정은 거부한다. 첫 링크의 길이 조건은 만족하지만 둘째 링크에서는 20바이트 초과한다. 이는 명시된 모형의 판정이며 실제 TLS 접속·인증서·VPN·방화벽·API 시험 결과가 아니다.
