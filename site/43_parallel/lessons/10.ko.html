소단원 10.1

coalescing·shared memory

32명이 옆 칸을 읽는 경우와 멀리 떨어진 칸을 읽는 경우는 같은 메모리 비용일까?

준비 개념과 학습 목표

준비 개념

  • 스레드와 warp

  • 바이트 주소

  • 배열 인덱스

학습 목표

  • 4바이트 접근이 걸치는32바이트 구간을 센다.

  • global coalescing과 shared memory bank 충돌을 구별한다.

같은 주소를 여러 thread가 읽으면 요청 바이트와 고유 바이트가 같을까요?

새 주소 모형은 compute capability 6.0 이상 문서의 32바이트 구간, t = 0부터 31까지인 warp의 32개 thread, 한 읽기 명령의 thread당 정렬된 4바이트 단어를 사용한다. 주소 4t를 읽는 32개 thread는 고유 128바이트를 네 구간에서 읽는다. 주소 4 floor(t/2)를 읽으면 두 thread씩 같은 단어를 읽어 요청 합은 여전히 128바이트이지만 고유 바이트는 64바이트이며 구간은 두 개다. 요청 합을 구간 용량 64바이트로 나눈 200%는 고유 바이트의 공간 사용률이 아니다.

별도 참여 모형에서는 짝수 t만 주소 4t를 읽는다. 16개 단어, 고유 64바이트를 네 구간에서 읽으므로 고유 사용률은 50%다. 짝수 t만 주소 4(t/2)를 읽도록 연속 압축하면 두 구간에 들어가 고유 사용률은 100%다. 참여 수만으로 구간 수를 정할 수 없으며 주소 집합과 자료 폭을 함께 써야 한다.

shared 손모형은 bank = word_index mod 32이며 같은 주소의 읽기는 broadcast로 구별한다. 모든 t가 word 7을 읽으면 하나의 주소다. word 7+16t는 두 bank에 각각 서로 다른 주소 16개가 몰린다. word 7+17t는 32개 bank를 한 번씩 방문한다. 17과 32의 최대공약수가 1이므로 같은 나머지가 나오려면 thread 번호 차이가 32의 배수여야 한다. global 구간 수와 shared bank 분포는 별도 장부다.

    기본의 정렬 구간과 shared 나머지 계산을 같은 주소의 반복과 구별한다.

  • 논리적 입력 요청

    요청 합을 실제 장치 전송 또는 시간으로 바꾸지 않는다.

요청한 바이트와 가져온 구간

여러 스레드의 메모리 요청을 적은 거래로 묶는 것을 coalescing이라고 한다. 본 절은 NVIDIA 문서의 compute capability6.0 이상·warp32개·각4바이트 읽기 조건을 사용하는 구간 계산이다. 실제 장치 전체의 캐시 미스나 DRAM 거래 수를 직접 측정한 것은 아니다.

스레드가 요청한 주소를 먼저 적고 각 주소가 포함되는 정렬32바이트 segment 번호 floor(address/32)를 구하자. 같은 segment의 여러 요청은 하나의 구간으로 묶어 센다. 연속이라는 말만으로 충분하지 않고 시작 정렬·자료 폭·참여 스레드 조건을 함께 본다.

shared memory는 블록 안에서 협력한다

여러 스레드가 재사용할 값을 블록의 shared memory에 올려 서로 읽을 수 있다. global에서 여러 번 가져오는 요청을 줄이는 설계에 유용하지만 값을 쓰기 전에 읽지 않도록 동기화해야 한다. 서로 다른 블록이 이 공간 하나를 자동 공유하는 것은 아니다.

공간 크기도 제한 자원이다. 큰 타일은 재사용을 늘릴 수 있지만 한 장치에 함께 배치할 블록 수를 제한할 수 있다. 따라서 shared memory를 늘리면 항상 빨라진다는 단정 대신 자료 이동·동기화·레지스터·occupancy를 함께 측정할 계획이 필요하다.

은행 충돌은 또 다른 주소 문제

아래 shared memory 교육 규칙은 연속32비트 단어를32개 bank에 배정하여 bank=word_index mod32로 본다. 서로 다른 주소가 같은 bank로 몰리면 충돌할 수 있다. 같은 주소를 읽는 broadcast와 서로 다른 주소의 충돌을 구별한다.

32열 배열의 열을 읽으면 행마다32단어 간격이어서 같은 bank로 간다. 33열 padding은 실제 데이터 열을 하나 늘리는 대신 저장 간격을 바꾼다. 이 예제의 은행 분산은 좋아지지만 모든 크기·자료형·하드웨어에서 같은 공식으로 최적화를 보장하지 않는다.

같은 주소를 여러 thread가 읽으면 요청 바이트와 고유 바이트가 같을까요?
조건계산과 결과구별할 대상

32개 thread, 주소 4 floor(t/2)

요청 합 128 B, 고유 64 B, 두 구간이다.

중복 요청 비율과 고유 사용률은 다르다.

짝수 thread, 주소 4t

고유 64 B를 네 구간에서 읽는다.

같은 참여 수의 압축 주소는 두 구간이다.

shared word 7+16t

bank 7과 23에 서로 다른 주소가 16개씩이다.

word 7 하나의 broadcast와 다르다.

shared word 7+17t

32개 bank를 한 번씩 방문한다.

이 32비트 손모형의 분포다.

요청 합과 주소 합집합의 고유 크기를 먼저 구별한다. 그 뒤 정렬 구간 번호를 센다. bank가 같더라도 주소까지 같은지를 확인한다.

중간 과정을 따라가는 예제

global base=0에서32개 스레드 t=0..31이4바이트 단어를 읽는다. 주소가4t일 때와4+4t일 때 각32바이트 segment 수를 구하라. 모두 정렬된4바이트 접근이며 한 warp의 한 읽기 명령이다.

  1. 4t는0..124에서 시작하여 마지막 단어 바이트127까지 사용한다. segment 번호는0,1,2,3으로4개다.

  2. 4+4t는4..128에서 시작해 마지막 바이트131까지 읽는다. segment0..4로5개다.

  3. 서로 다른128바이트를 요청하지만 구간 용량은4×32=128 대5×32=160바이트다. 이 단순 모형의 사용 비율은100% 대80%다.

정렬 시작은4구간,4바이트 밀린 시작은5구간이다. 모형 비율80%는 실제 GPU 속도80%라는 주장이 아니다.

조건을 바꾸어 비교하기

중복 요청의 200%

주소 4 floor(t/2)를 읽는 32개 thread의 두 바이트 장부와 구간 수를 구하라.

  1. 단어 인덱스는 0부터 15까지이며 각 단어를 두 번 요청한다. 요청 합은 32×4=128 B, 고유 크기는 16×4=64 B다.

  2. 단어들이 바이트 0부터 63까지를 사용하여 두 구간에 들어간다. 고유 사용률은 64/64=100%다.

요청 합 비율 200%를 공간 사용률이라고 부르지 않는다.

비교할 점

중복 요청은 공간 사용률의 분자를 중복시키면 안 된다.

같은 bank와 같은 주소

word 7, word 7+16t, word 7+17t의 한 warp 읽기를 비교하라.

  1. word 7은 모든 thread가 같은 주소를 읽는 broadcast다. 16t는 짝수 t가 bank 7, 홀수 t가 bank 23이며 각각 주소 16개가 다르다.

  2. 17t의 bank는 순열이므로 각 bank에 하나씩이다.

broadcast, 두 bank의 서로 다른 주소 집중, 전체 bank 분산을 구별한다.

비교할 점

bank 번호 하나만으로 broadcast라고 판정하지 않는다.

종이와 본문으로 직접 해보기

스레드 t가 주소32t의4바이트를 읽으면 구간 수와 사용 비율은? shared 배열의 word_index=32t와33t의 bank번호를 t0..3에 써라.

힌트 보기

각 주소를32로 나누고 shared 인덱스는32로 나눈 나머지를 구한다.

풀이 보기

주소0,32,..992는32개 다른 구간으로 총1024바이트 구간 중128바이트 요청, 비율12.5%다. 32t bank는0/0/0/0,33t는0/1/2/3이다. 전자는 다른 주소의 충돌 모형이고 후자는 분산된다.

오해와 반례

global 읽기가 coalesced이면 shared memory도 반드시 충돌이 없다.

같은 global 구간을 효율적으로 가져와도 shared 배열에 열 방향으로 놓으면32t 인덱스가 같은 bank에 몰릴 수 있다. 두 공간의 주소 배치와 문제를 따로 확인한다.

연습 3 · 직접 만들어 보기

각 t가 서로 다른 주소를 읽되 모든 bank에 한 개씩 배정하는 word_index 규칙을 구성하고 증명하라.

힌트 1

홀수 간격을 사용한다.

힌트 2

32와 서로소인 간격의 나머지를 비교한다.

풀이와 답 확인

  2. 두 bank가 같으면 17(t−u)가 32의 배수이고 서로소 조건으로 t−u도 32의 배수다. 0≤t,u≤31에서는 t=u다.

입력·계산·출력을 모두 넣으면 기본의 두 단계 시간이 유지될까요?

새 파이프라인 손모형은 세 조각, 조각당 H2D 2 ms, 계산 3 ms, D2H 2 ms를 사용한다. 입력 전송 엔진, 계산 엔진, 출력 전송 엔진은 서로 독립이며 각자 한 작업씩 처리한다. 조각별 버퍼는 별도이고 시작 비용은 0이다. H1은 0–2 ms, H2는 2–4 ms, H3는 4–6 ms다. K1은 2–5 ms, K2는 5–8 ms, K3는 8–11 ms이며 출력 D1은 5–7 ms, D2는 8–10 ms, D3는 11–13 ms다. 전체 결과는 13 ms에 준비되며 순차 21 ms와 같은 포함 범위로 비교한다.

두 방향 전송이 하나의 copy 엔진을 공유하는 별도 모형에서는 위의 H3 4–6 ms와 D1 5–7 ms가 겹쳐 불가능하다. H1,H2,H3,D1,D2,D3 순서로 엔진에 배정하면 D1은 6–8 ms가 된다. K2는 5–8 ms로 진행하고 D2는 8–10 ms, D3는 11–13 ms여서 전체 완료는 여전히 13 ms다. 전체 시간이 같아도 첫 조각 응답은 7 ms에서 8 ms로 달라진다. 이 배정이 모든 가능한 입력에서 최적이라는 주장은 하지 않는다.

버퍼 수는 stream 수와 다르다. 조각별 입력·중간 결과 공간을 하나의 재사용 슬롯에 둔 별도 수명 계약에서는 D2H가 끝나야 그 슬롯 전체를 다시 쓴다. 슬롯 하나로는 세 조각이 0–7,7–14,14–21 ms로 순차 처리된다. 두 슬롯이면 첫 둘은 겹칠 수 있지만 셋째는 첫 슬롯이 7 ms에 반환된 뒤 H3를 시작한다. 실제 CUDA 겹침에는 pinned host memory, 완료 의존, 하드웨어 자원이 필요하며 이 시간선은 API 실행 결과가 아니다.

빨리 반환해도 작업이 끝난 것은 아니다

비동기 호출은 CPU가 다른 일을 할 수 있도록 요청을 넣는 방식이다. 함수가 반환했다고 GPU 전송이나 계산의 결과를 즉시 읽어도 된다는 뜻은 아니다. 결과 접근과 버퍼 재사용에는 완료 확인이 필요하다.

CUDA의 CPU 메모리 전송을 실제로 비동기 수행하려면 pinned/page-locked host buffer 같은 조건을 확인한다. pageable 자료가 동기처럼 동작할 수 있으며, 호출 이름에 Async가 있다는 사실만으로 겹침을 측정했다고 말하지 않는다.

같은 조각의 의존은 유지한다

각 조각은 전송이 끝나야 그 조각의 계산을 시작한다. 같은 stream의 전송 뒤 계산은 순서가 보존된다. 다른 조각은 다른 버퍼를 쓰면 다음 전송과 현재 계산을 겹칠 기회가 생긴다. 서로 다른 stream이라고 같은 버퍼를 안전하게 동시에 덮어써도 되는 것은 아니다.

실제 겹침은 장치의 copy/compute 자원과 설정에 달렸다. legacy default stream, per-thread default stream, nonblocking stream의 관계도 구별해야 한다. 본 시간선은 명시적으로 독립 자원 두 개와 별도 버퍼를 가정하며 CUDA 호출 목록을 실행한 결과가 아니다.

파이프라인의 시작과 끝 비용

전송 엔진과 계산 엔진은 각자 한 번에 하나의 조각만 처리한다고 하자. 첫 전송 동안 계산할 자료가 없고 마지막 계산에는 다음 전송을 겹칠 수 없다. 정상 구간이 겹쳐도 시작과 끝 비용이 남는다.

큰 자료를 너무 작은 조각으로 나누면 요청·커널 시작·동기화 비용이 커질 수 있다. 아래는 이 비용과 GPU→CPU 반환을 제외한다. 같은 포함 범위의 순차 시간과 비교해야 한다. 가장 긴 단계가 전체 처리 간격을 제한한다.

경계 타일의 0도 실제 입력 읽기와 덧셈 수에 모두 포함할까요?

새 행렬 손모형은 A가 2×3, B가 3×2이며 A=[[1,2,3],[4,5,6]], B=[[1,0],[0,1],[1,1]]이다. C=[[4,5],[10,11]]이다. 네 출력을 각각 길이 3의 내적으로 계산하면 입력 원소 요청은 4×6=24회, 곱셈은 12회다. 첫 항을 대입하고 남은 두 항을 더하는 약속에서는 덧셈이 출력당 두 번, 총 여덟 번이다. 0에서 시작하는 누산 약속에서는 총 12번이므로 연산 수를 적을 때 약속도 쓴다.

K 방향을 폭 2 타일로 나누면 첫 타일에서 A 네 칸과 B 네 칸, 둘째 타일에서 실제 A 두 칸과 B 두 칸을 읽는다. 합계 12회다. 둘째 타일의 부족한 A 두 칸과 B 두 칸은 경계 밖 주소를 읽지 않고 shared에 0을 쓴다. 총 적재 자리 16개와 실제 global 요청 12회는 다르다. 타일 폭대로 두 번씩 산술을 하면 곱셈은 16회가 되어 실제 내적의 12회보다 많다. 재사용이 요청을 줄여도 산술을 반드시 줄이지는 않는다.

별도 정확 정수 reduction은 값 [2,−2,5,1,4]를 여덟 자리의 [2,−2,5,1,4,0,0,0]으로 둔다. 인접 쌍 트리는 [0,6,4,0]→[6,4]→10이다. 단계 깊이는 세 번이고 실제 수행한 덧셈은 일곱 번이다. 다섯 실제 값을 직렬로 첫 값에서 누적하면 덧셈은 네 번이다. 서로 다른 연산 수와 깊이 비교이며 GPU 시간 인증은 아니다. CUB의 첫 num_valid thread 값 기여 계약과 thread 0의 유효 반환, 임시 공간 재사용 장벽도 별도 API 계약으로 읽는다.

타일은 작은 조각을 다시 쓰는 설계

행렬 곱의 출력 하나는 행과 열의 내적이다. 출력마다 필요한 원소를 다시 읽는 논리에서 같은 입력이 반복된다. 타일링은 작은 A/B 조각을 협력해 읽고 여러 출력에 재사용한다.

아래는 2×2 행렬 하나 전체를 한 타일로 둔다. 원시 읽기 요청을 센 것이며 캐시가 있어 실제 global transaction은 이미 줄어들 수 있다. 논리적 요청 감소를 그대로 DRAM 대역폭·속도 배율로 바꾸지 않는다.

협력의 단계 사이에는 순서가 있다

타일을 shared memory에 채우고 다른 스레드가 읽는다면 필요한 범위의 동기화가 있어야 한다. 다음 타일로 덮어쓰기 전에 현재 타일의 읽기가 끝나야 한다. 배열 크기가 타일 배수가 아니면 경계 밖 원소를 읽지 않도록 조건을 처리한다.

타일 크기는 저장량과 스레드/레지스터 사용을 함께 바꾼다. 모든 경계 스레드가 조기에 반환해서 필요한 barrier에 참여하지 않으면 문제가 생길 수 있다. 범위 밖 입력을 안전한 값으로 채우는 설계와 조건부 결과 쓰기를 따로 생각하자.

reduction은 여러 값을 하나로 모은다

정확한 작은 정수 합에서 두 값씩 더하면 합 트리를 만들 수 있다. 8개 입력은4개 부분합→2개→1개로 줄어3단계, 총7번 덧셈이다. 단계 깊이와 총 연산 수는 서로 다르며3단계가 실제3GPU사이클이라는 뜻은 아니다.

블록 합은 전체 GPU의 합과도 구별한다. 여러 블록이면 부분 결과를 다시 합칠 절차가 필요하다. CUB BlockReduce 문서의 반환값은 지정된 thread0에 유효하므로 모든 스레드의 반환값을 무조건 출력으로 쓰지 않는다. 부동소수점에서는 합 순서에 따라 반올림 결과가 달라질 수 있다.

세 독립 종이 모형을 검증하라. ① 짝수 t만 base 28 B의 주소 28+4(t/2)를 읽는 4바이트 global 접근과 모든 t가 shared word 7+16t를 읽는 접근을 구별하라. ② 세 조각 각각의 H 시간은 2 ms, K 시간은 3 ms, D 시간은 2 ms이며 독립 세 엔진과 전체 수명 슬롯 두 개를 사용한다. 슬롯은 해당 D 완료 뒤 반환한다. ③ [2,−2,5,1,4]를 여덟 자리로 0 패딩한 합 트리와 두 block의 부분 합을 비교하라. 실제 성능 측정으로 확대할 수 없는 이유도 쓰라.

힌트 1

① 고유 주소 범위와 bank별 서로 다른 주소 수를 센다. ② 셋째 H는 슬롯 반환 뒤 시작한다.

힌트 2

③ 트리 깊이와 덧셈 수, 지역 결과와 전체 결과를 별도 장부로 쓴다.

풀이와 답 확인

  1. ① 고유 범위는 바이트 28부터 91까지의 64 B이며 세 구간 용량 96 B에서 사용률 2/3이다. shared는 bank 7과 23에 서로 다른 주소가 16개씩이므로 같은 주소 broadcast가 아니다.

  2. ② H1 0–2, H2 2–4, K1 2–5, K2 5–8, D1 5–7, D2 8–10 ms다. H3 7–9, K3 9–12, D3 12–14 ms여서 전체 14 ms다.

  3. ③ 트리는 [0,6,4,0]→[6,4]→10이며 세 단계와 일곱 덧셈이다. 별도 두 block의 지역 합 5와 5는 추가 합으로 10이 되고 첫 값 대입 직렬 약속의 전체 덧셈은 네 번이다.

  4. 세 사례는 주소·자원·정확 정수 연산의 자체 모형이다. 캐시/하드웨어 동시성/컴파일 및 실측 지연을 확인하지 않았으므로 사용률·단계 깊이를 실제 속도 비율로 바꾸지 않는다.

고유 사용률 2/3과 두 bank의 다른 주소 집중, 두 슬롯 전체 완료 14 ms, 합 10의 세 단계/일곱 덧셈 대 별도 지역 결합 네 덧셈을 구별한다.

해결한 뒤 점검할 것

  • 요청 합·고유 바이트·구간·broadcast/다른 주소 집중을 정확하게 나눈다.

  • 각 조각의 의존, 세 엔진의 비겹침, 두 슬롯의 D 완료 반환을 검사한다.

  • 두 합 방식의 최종 값 10과 연산 수 약속을 설명하고 새 GPU 실행/성능/학생 검증으로 주장하지 않는다.
