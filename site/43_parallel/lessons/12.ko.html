CAS와 lock-free 입문

두 사람이 같은 숫자를 보고 하나씩 늘리면 반드시 두 번 늘어날까?

준비 개념과 학습 목표

준비 개념

  • 공유 변수와 lost update

  • 원자 연산

  • 반복과 스레드

학습 목표

  • CAS의 비교와 갱신을 한 사건으로 설명한다.

  • 반복 갱신에서 실패 후 재읽기를 추적한다.

  • 선형화와 lock-free·wait-free를 구별한다.

한 번 읽은 잔액으로 두 인출 요청을 모두 승인해도 될까요?

새 손모형에서 정수 잔액은 처음 10이다. P는 7을, Q는 6을 인출하려고 둘 다 10을 읽었다. 잔액 이상을 인출하지 않고, 승인된 요청마다 정확히 그 금액을 한 번 차감하는 계약이다. P의 strong CAS(10,3)이 먼저 성공한다. Q의 CAS(10,4)는 실패한다. Q가 새 잔액 3을 읽으면 6을 인출할 수 없으므로 거절해야 한다. 성공한 P의 상태 전환은 CAS 사건에서 선형화되고 Q의 거절은 부족한 잔액 관찰에서 설명할 수 있다. 이 모형에는 다른 입금이나 출금이 없다.

Q가 expected만 3으로 고치고 desired를 옛 값 4로 유지하면 CAS(3,4)가 성공할 수 있다. 원자적 갱신 자체는 성공하지만 잔액을 늘리면서 6의 인출을 승인하므로 업무 계약은 실패한다. 재시도할 때는 최신 값에서 승인 조건과 새 결과를 함께 다시 계산해야 한다. strong CAS의 이 실패 사례는 다른 변경과 연결되지만 weak CAS는 비교가 맞아도 허위 실패할 수 있으므로 실패 횟수를 곧바로 경쟁 갱신 수로 읽지 않는다.

별도 참조 모형에서 A와 B는 내용이 모두 (잔액 10, 판본 0)이지만 서로 다른 살아 있는 객체다. 현재 AtomicReference는 B를 가리킨다. Java 8의 compareAndSet(A,C)는 내용이 같아도 A와 B가 같은 참조가 아니므로 실패한다. B를 expected로 삼으면 다른 변경이 없을 때 성공할 수 있다. 객체의 내용을 직접 바꾸는 쓰기는 참조 CAS만으로 함께 보호되지 않는다. 또 재시도 함수 안의 외부 통지나 비용 청구는 여러 번 수행될 수 있다. 새 상태 계산은 부작용 없는 함수로 두고 성공 뒤의 외부 처리에도 별도의 중복 방지 계약을 마련한다.

lock-free는 충분히 계속되는 시스템 단계에서 어떤 연산이 진전한다는 성질이며, 특정 P의 유한 재시도 상한과는 다르다. 다른 요청이 P의 매 CAS 직전에 성공하는 이력을 계속 만들면 P만 계속 실패할 수 있다. CAS를 썼다는 사실만으로 전체 알고리즘의 lock-free 증명이 되지 않으며 메모리 할당, 회수 및 실제 원자 연산 구현의 진전 조건도 확인해야 한다.

읽기와 쓰기 사이에 끼어드는 작업

공유 카운터가 5인데 P와 Q가 모두 5를 읽고 각자 6을 쓰면 최종값은 6이다. 두 번의 증가가 하나로 보이는 lost update다. 읽기와 계산과 쓰기를 따로 수행했기 때문이다.

CAS(location, expected, desired)는 현재값이 expected와 같으면 desired로 갱신하고 성공을 알리는 원자 비교·갱신이다. 이 설명에서는 허위 실패가 없는 강한 CAS를 가정한다. Java의 참조 CAS는 내용의 equals 비교가 아니라 같은 객체 참조인지 비교한다.

실패하면 현재값에서 다시 계산한다

순수 카운터 증가에서는 old를 읽고 old + 1을 계산해 CAS를 시도한다. 실패하면 현재값을 다시 읽고 새 desired를 계산한다. 실패한 시도에서 계산한 값을 그대로 다시 쓰면 다른 사람의 변경을 덮을 수 있다.

성공한 CAS가 이 증가의 선형화 시점이다. 각 호출이 시작과 종료 사이 한 순간에 일어난 듯한 순서를 만들어 결과를 설명한다. 하나의 CAS만으로 임의의 다중 필드 자료구조가 올바르게 되지는 않는다. 초기화한 자료의 공개 순서와 언어 메모리 모델도 별도로 필요하다.

어느 작업의 진전을 보장하는가

lock-free 알고리즘은 계속 실행되는 전체 시스템에서 어떤 연산이 유한 단계 안에 완료하는 진전 조건을 갖는다. 특정 P가 반복해서 지고 Q만 완료할 수 있으므로 P의 굶주림을 막는다는 뜻은 아니다. wait-free는 각 연산이 다른 스레드의 실행과 무관하게 제한된 자기 단계 안에 끝나는 더 강한 조건이다.

CAS가 있다는 사실만으로 전체 함수가 lock-free인 것은 아니다. 메모리 할당·다른 잠금·회수 절차·atomic 구현까지 살펴야 한다. 다음 예제는 순차적으로 일정을 적은 이론 표이며 하드웨어 명령의 시간이나 스레드 실행을 측정하지 않는다.

각 행에서 공유 상태와 지역 계산을 나누고 승인 사건을 표시한다. 성공한 원자 명령의 효과가 요구한 금액 차감과 일치하는지도 따로 검사한다.

중간 과정을 따라가는 예제

처음 x = 5다. P와 Q가 old = 5, desired = 6을 계산했다. P의 CAS(5, 6), Q의 CAS(5, 6), Q의 재읽기와 재시도를 순서대로 추적하라.

  1. P는 현재 5와 기대 5가 맞아 성공하고 x = 6이 된다.

  2. Q는 현재 6이 기대 5와 달라 실패하며 x는 6이다.

  3. Q가 old = 6을 다시 읽고 desired = 7을 계산하면 CAS(6, 7)가 성공해 x = 7이 된다.

성공은 두 번, 실패는 한 번이다. 최종 x = 7이며 선형화 순서는 P 다음 Q다.

조건을 바꾸어 비교하기

재계산을 생략한 인출

P가 CAS(10,3)에 성공한 뒤 Q가 expected만 3으로 바꾸고 desired 4를 유지했다. 무엇이 잘못인가?

  1. 현재 값 3과 expected 3이 같아 strong CAS는 다른 변경이 없으면 성공한다.

  2. 그러나 새 잔액은 4로 1 늘었고 요청 금액 6의 차감도 없다. 최신 잔액 3에서 부족 조건을 검사해 거절해야 한다.

명령 성공과 인출 계약 실패가 동시에 나타난다. 올바른 최종 잔액은 3이다.

비교할 점

원자성은 계산한 새 값의 업무 의미를 대신 검증하지 않는다.

같은 내용의 다른 expected

살아 있는 서로 다른 A와 B의 내용이 같다. 현재 B에서 compareAndSet(A,C)와 compareAndSet(B,C)를 비교하라. 두 호출은 각각 현재 B인 별도 이력이다.

  1. A와 B는 내용 동등하지만 참조 동일하지 않다. 첫 호출은 실패하고 B를 유지한다.

  2. 둘째 호출은 현재 참조 B와 비교하므로 다른 변경이 없으면 성공하여 C가 된다.

첫 이력은 실패, 둘째 이력은 성공이다.

비교할 점

객체 내용의 equals 판정으로 Java 참조 CAS의 계약을 바꾸지 않는다.

종이와 본문으로 직접 해보기

힌트 보기

성공할 때만 현재값이 1 늘어난다. 강한 CAS는 현재값과 기대값을 비교한다.

풀이 보기

최종값은 11, 성공 3회·실패 2회다. R이 계속 기대값 8로 시도하면 현재 9 이상과 달라 계속 실패한다. 값을 다시 읽고 증가 목표도 다시 계산해야 한다.

오해와 반례

잠금 없이 반복하므로 모든 스레드가 일정 시간 안에 완료하고 어떤 자료구조든 안전하다.

다른 작업이 계속 먼저 성공하면 특정 작업은 오래 실패할 수 있다. 시스템 진전과 개인 완료·시간 제한은 다르다. CAS 한 곳의 원자성과 자료구조의 불변식·메모리 수명·공개 순서도 각각 검토해야 한다.

풀이와 답 확인

  2. 후보 계산의 외부 효과를 제거하고 성공 업무 ID를 별도로 기록한다. 성공 뒤 전송도 재전송·충돌에 대한 수신 측 중복 방지가 필요하다.

판본 태그와 hazard pointer는 같은 오류를 막을까요?

별도 살아 있는 객체의 스택에서 처음 head는 A이고 A.next는 B, B.next는 C다. P는 A와 B를 읽고 멈췄다. Q가 A를 pop하고 B를 pop한 뒤 A.next를 C로 바꾸어 A를 다시 push하면 head는 다시 A다. P의 낡은 CAS(A,B)는 참조가 다시 같아 성공할 수 있지만 제거된 B를 다시 head로 올린다. 이 논리 ABA 모형에서는 객체를 해제하지 않았으므로 use-after-free가 없어도 오류가 생긴다. head만 검사해서는 옛 successor가 여전히 올바르다는 사실을 알 수 없다.

head와 stamp를 한 원자 쌍으로 관리하고 성공한 head 변경마다 stamp를 하나 늘리면 처음 (A,5)는 Q의 세 변경 뒤 (A,8)이 된다. P의 expected (A,5)는 실패한다. 그러나 새 2비트 태그 모형에서는 stamp가 0,1,2,3 뒤 순환한다. (A,1)에서 head가 A→B→C→D→A로 네 번 바뀌면 stamp도 1→2→3→0→1로 돌아온다. 객체는 모두 살아 있으며 각 변경은 원자 쌍을 갱신한다. P가 지연되는 동안 변경 수를 제한하지 않으면 유한 태그만으로 영구적인 ABA 방지를 주장할 수 없다.

회수는 별도 계약이다. 제거된 객체를 retire 목록에 두고, 올바른 hazard pointer 프로토콜로 보호된 객체는 보호가 끝날 때까지 회수하지 않는다. 추상 순차 일관 사건 모형에서 P가 head A를 읽은 직후 Q가 A를 제거·retire·회수했다면, P가 나중에 A를 hazard 슬롯에 적는 것만으로 객체가 살아나지 않는다. P는 객체를 역참조하기 전에 보호 등록과 원본 head 재확인을 수행해야 한다. 재확인 때 head C라면 옛 A를 사용하지 않고 다시 시작한다. 실제 구현에는 적절한 메모리 순서와 검증된 라이브러리 프로토콜이 필요하며 단순 집합 차이 계산만으로 구현의 안전성을 증명하지 않는다.

모든 보호가 유효하게 설정·재확인된 안정된 회수 시점의 별도 집합 사례에서 retire={A,B,C,D}, 보호={B,D}이면 회수 후보는 {A,C}다. B의 보호를 해제한 뒤 보호={D}이면 새 후보에 B가 포함된다. A와 C를 이미 회수한 뒤라면 남은 retire={B,D} 중 후보는 B 하나다. 보호가 끝난 것은 회수 가능 조건이지 실제 라이브러리가 바로 그 시점에 회수했다는 관찰은 아니다. hazard pointer의 수명 보호를 살아 있는 노드의 재연결로 생기는 모든 논리 ABA의 해결로 일반화하지 않는다.

    head 비교가 successor의 과거 상태까지 인증하지 않는다는 경계를 확인한다.

같은 A가 다른 연결을 갖는다

스택이 A → B → C다. P는 head A와 그 next B를 읽고 멈춘다. Q가 A를 pop하고 B를 pop한 다음 A를 다시 push하면 현재 스택은 A → C다. P가 head가 여전히 A라는 이유로 CAS(A, B)를 성공시키면 이미 제거한 B를 되살리는 잘못된 연결이 된다.

이 종이 모형에서는 A/B/C 객체를 아직 해제하지 않아 낡은 연결 문제만 보인다. 실제 메모리를 해제하고 같은 주소에 새 객체를 할당하면 주소 일치와 객체 수명 문제가 추가된다. 현재 참조 하나만 비교하는 CAS는 중간 A → 다른 값 → A의 변경 이력을 기억하지 않는다.

버전과 수명은 다른 보장이다

head와 stamp를 한 쌍으로 원자 갱신하며 각 변경에 stamp를 증가시킨다고 하자. 처음 (A, 10), 두 pop 뒤 (C, 12), A push 뒤 (A, 13)이라면 P가 기대한 (A, 10)은 일치하지 않는다. 읽기도 참조와 stamp를 함께 읽어야 한다.

유한 stamp가 한 바퀴 돌아 같은 값이 되거나 갱신자가 규칙을 지키지 않으면 이 비교만으로 영구적인 방지가 되지 않는다. stamp는 객체를 살아 있게 보존하는 장치도 아니다. 낡은 포인터를 해제 후 역참조하지 않도록 별도의 수명 보호가 필요하다.

삭제와 해제 사이를 분리한다

hazard pointer 접근자는 가리킬 객체를 보호하겠다고 게시하고 공유 포인터를 다시 읽어 같은 객체인지 확인한 뒤 사용한다. 그 사이 바뀌었다면 게시를 정리하고 다시 시도하며 낡은 객체를 읽지 않는다. 단순히 주소를 읽고 나중에 게시하기만 하면 그 전에 회수될 수 있다.

제거자는 자료구조에서 떼어낸 객체를 retire 목록에 넣는다. 올바른 게시·재검증·메모리 순서가 성립하는 프로토콜에서 보호가 남은 객체는 회수를 늦추고 안전해진 객체만 reclaim한다. 이론 집합 표는 회수 시점 이해를 돕지만 실제 C++ 메모리 모델 증명이나 실행 가능한 회수 구현을 대신하지 않는다.

쓰기 집합이 겹치지 않으면 두 트랜잭션 모두 승인해도 될까요?

새 당직 모형의 비트 a=b=1이며 a+b≥1을 유지해야 한다. P는 a와 b를 모두 읽고 b=1이면 a=0을 쓰는 후보를 만든다. Q도 둘을 읽고 a=1이면 b=0 후보를 만든다. 둘 다 초기 자료를 읽었다면 P의 쓰기 집합 {a}와 Q의 쓰기 집합 {b}는 다르다. 그러나 서로의 읽기 조건을 무시하고 둘 다 적용하면 (a,b)=(0,0)으로 불변식을 깨뜨린다. 쓰기 집합만의 충돌 검사는 이 read-write 의존을 놓친다.

별도 완전 읽기 집합 검증 모형은 각 항목의 판본을 읽어 저장하고, 모든 읽기 판본 검사와 후보 쓰기를 하나의 원자 commit 사건으로 수행한다고 가정한다. 처음 a와 b 판본은 모두 0이다. P가 먼저 검증·적용하면 a=0, 판본 a=1이 된다. Q는 자신이 읽은 a 판본 0이 현재 1과 달라 abort한다. Q가 다시 읽으면 a=0이라 b를 끄지 않으며 b=1을 유지한다. 현재 상태는 (0,1)이고 불변식이 성립한다. 이는 읽기 검증을 원자적으로 묶은 자체 모형이지 모든 TM의 내부 구현 알고리즘이라는 주장이 아니다.

충돌의 단위도 구별한다. 독립 값 u=v=0에 P가 u만 읽고 u=1을 쓰고 Q가 v만 읽고 v=1을 쓴다면 항목별 판본 모형에서는 둘 다 commit해 (1,1)을 만들 수 있다. 같은 후보를 하나의 전체 판본 0으로 검증하면 P 뒤 전체 판본 1이어서 Q가 abort한 뒤 재시도한다. Q의 v 관찰이 틀려진 것은 아니므로 이 abort는 자료 단위가 거칠어서 생긴 보수적 충돌이다. 불필요한 abort를 줄이는 것과 필요한 읽기 충돌을 없애는 것은 다른 변경이다.

외부 전송은 별도 모형이다. 거래 R이 메시지 q를 전송한 뒤 abort하고, 재시도 R이 같은 q를 다시 전송한 뒤 commit하면 전송 시도 두 번에 commit은 한 번이다. commit과 함께 업무 q의 발송 장부를 원자 기록해도 발송자가 송신 후 확인 전에 멈추면 q를 재전송할 수 있다. 수신자가 업무 ID q의 효과를 이미 반영했는지 기록하고 중복을 제거해야 한 번의 업무 효과를 구성할 수 있다. GNU libitm에는 serial mode와 blocking 경로가 있으므로 TM 사용을 자동 lock-free로 읽지 않는다. 일반 코드와의 자료 공유도 해당 언어와 DRF 동기화 계약을 지켜야 한다.

먼저 확인할 개념
  • 읽기·쓰기 집합과 commit

    기본의 판본 검증을 disjoint write의 read-write 충돌과 외부 효과에 적용한다.

  • 원자성·진전의 다른 기준

    업무 불변식과 진전 보장을 CAS 또는 TM 사용 사실만으로 인증하지 않는다.

여러 접근을 한 논리 작업으로 묶기

서가 재고 x와 대출 수 y가 처음 (4, 1)이다. 한 대출은 x를 1 줄이고 y를 1 늘려 합 5를 보존한다. x만 먼저 바꾸고 y를 나중에 바꾸면 중간 (3, 1)을 다른 관찰자가 볼 수 있다. 메모리 트랜잭션은 이런 여러 접근을 다른 참여 트랜잭션과 원자적이고 격리된 작업으로 다루려는 방법이다.

STM은 소프트웨어가 접근·검증·변경 기록 등을 관리하고 HTM은 하드웨어 기능을 이용한다. 여기서는 실제 구현 대신 버전 검사와 미공개 쓰기 버퍼를 가진 자체 낙관 모형을 사용한다. 데이터베이스 영속성·네트워크 전송·파일 저장이 자동 포함되는 것은 아니다.

충돌이면 중간 계획을 버린다

자체 모형은 값과 버전을 읽고 새 값을 개인 버퍼에 계산한다. commit에서는 읽은 버전이 그대로인지 검증하는 일과 버퍼를 원자 적용하는 일이 하나의 동기화된 절차라고 가정한다. 그 사이 다른 commit이 끼어들지 않는다는 조건이 중요하다.

동시에 같은 재고를 읽었다면 먼저 commit한 작업만 처음 버전을 유지할 수 있다. 뒤 작업은 낡은 읽기임을 발견해 버퍼를 버리고 현재값에서 다시 계산한다. 읽기 집합과 다른 작업의 쓰기 집합이 겹치는지 보는 표는 충돌 후보를 찾는 단순 모형이며 모든 STM의 실제 알고리즘은 아니다.

경계 밖 작업과 진전 조건

트랜잭션 안에서 외부 메시지를 보내고 이후 abort하면 이미 보낸 메시지를 메모리 rollback만으로 회수할 수 없다. 따라서 재시도 가능한 계산과 외부 효과를 분리하고, 필요하면 commit 이후 전달·중복 식별 등 별도 프로토콜을 둔다. 뒤로 옮겼다는 사실만으로 전달의 정확히 한 번 수행이 보장되지는 않는다.

GCC 문서는 일반 비트랜잭션 접근과 충돌하는 접근에 data-race-free 조건을 요구한다. 어떤 TM은 내부 lock이나 직렬 fallback을 사용하고 반복 abort도 생긴다. TM을 쓴다는 이유만으로 lock-free·무제한 병렬 실행·항상 빠름을 주장할 수 없다.

중간 과정을 따라가는 예제

처음 (x, y) = (4, 1), 두 버전은 0이다. P와 Q가 이를 읽고 각각 (3, 2)를 개인 버퍼에 계획했다. P가 먼저 원자 commit해 두 버전을 1로 만들었다. Q의 검증과 재시도를 추적하라.

  1. P commit 뒤 공유값은 (3, 2), 버전은 (1, 1)이다. 합은 5다.

  2. Q는 읽은 버전 0과 현재 1이 달라 abort하고 (3, 2) 버퍼를 버린다.

  3. Q가 (3, 2)와 버전 1을 다시 읽으면 새 계획은 (2, 3)이다. 충돌 없이 commit하면 두 버전은 2가 되고 합은 5다.

공유 상태는 (4, 1)→(3, 2)→(2, 3)이다. 두 대출을 반영하고 합 5를 유지한다. 이 표는 원자 검증/적용을 가정한 자체 모형이다.

쓰기 충돌이 없는 당직 실패

초기 a=b=1을 읽은 P가 a=0, Q가 b=0을 쓴다. 쓰기 집합만 검증한 결과와 완전 읽기 검증을 비교하라.

  1. 쓰기 집합은 서로 다르지만 두 후보를 적용하면 a+b=0이다.

  2. 완전 읽기 검증에서 P가 먼저 a 판본을 1로 바꾸면 Q가 저장한 a 판본 0은 불일치한다. Q가 다시 읽으면 a=0을 보고 b=1을 유지한다.

쓰기만 검사하면 실패하며 완전 읽기 검증 모형의 최종 상태는 (0,1)이다.

외부 발송과 commit의 수

R이 q를 발송한 뒤 abort하고 재시도에서 q를 다시 발송해 commit했다. 발송 시도·commit·중복 방지 없는 수신 효과를 세라.

  1. 발송 시도는 두 번이고 성공 commit은 한 번이다.

  2. 두 메시지가 모두 도착하고 매번 효과를 적용하는 수신 모형이면 업무 효과도 두 번이다.

발송 시도 두 번, commit 한 번, 지정 수신 모형의 효과 두 번이다.

P와 U는 집합이 분리돼 이 모형의 자료 충돌 후보가 아니다. P와 Q는 x에서 겹친다. 재고 1의 첫 대출 뒤 x = 0이면 두 번째는 재읽기 후 대출 불가로 끝내며 x를 −1로 줄이지 않는다. 내부 자료구조·캐시나 구현 단위로 인한 추가 충돌은 이 집합 표에 포함하지 않았다.

오해와 반례

메모리 트랜잭션이 abort하면 이메일도 취소되고 일반 변수 접근도 모두 보호된다.

메모리 버퍼와 외부 효과는 경계가 다르다. 비참여 접근은 언어와 runtime의 조건에 맞춰 동기화해야 한다. 원자성·영속성·외부 전달·진전을 하나의 자동 보장으로 합치지 않는다.

다른 문제에 적용하기

세 독립 손모형을 대조하라. ① 잔액 12에서 P가 8, Q가 7을 인출하려고 둘 다 12를 읽었다. P의 CAS(12,4)가 먼저 성공한 뒤 Q의 옛 시도와 올바른 재시도 결과를 구하라. Q가 expected만 4로 바꾸고 옛 desired 5를 쓰는 오류도 판정하라. ② 모든 객체가 살아 있는 태그 모형의 초기 쌍은 (A,2)이고 2비트 tag를 사용한다. head가 A→B→C→D→A로 네 번 바뀔 때 마지막 쌍과 옛 expected의 검출 여부를 구하라. 별도 올바른 보호 프로토콜의 안정된 회수 시점에서 retire={A,B,C}, 보호={A}의 후보도 구하라. ③ 초기 당직 a=b=1에서 P는 b를 읽어 a=0 후보, Q는 a를 읽어 b=0 후보를 만든다. 쓰기만 검사한 결과와 모든 읽기 판본의 검증·적용을 한 원자 사건으로 묶은 P 우선 이력을 비교하고, q의 commit 장부 한 행 뒤 두 번 전달된 메시지의 중복 효과 방지 조건을 쓰라.

힌트 1

① CAS 성공의 비트 조건과 요청 금액 차감의 의미를 나눈다.

힌트 2

② tag의 나머지와 수명 보호 집합을 독립 계산한다. ③ 다른 요청이 바꾸는 읽기 조건도 검사한다.

풀이와 답 확인

  1. ① P 뒤 잔액은 4다. Q의 CAS(12,5)는 실패하며 새 잔액 4는 7보다 작아 거절한다. CAS(4,5)는 명령으로 성공할 수 있지만 잔액을 늘리므로 인출 계약을 깨뜨린다.

  2. ② tag는 2→3→0→1→2이어서 마지막 쌍은 (A,2)다. 옛 쌍만으로 네 변경을 검출할 수 없다. 별도 안정된 보호 사례의 회수 후보는 {B,C}이며 이를 실제 회수 완료나 모든 ABA 해결로 바꾸지 않는다.

  3. ③ 쓰기만 검사하면 (0,0)이 되어 당직 합이 0이다. 완전 읽기 검증 모형에서 P 뒤 Q의 a 판본이 틀려 abort하고 재시도에서는 a=0을 보고 b=1을 유지하므로 최종 (0,1)이다.

  4. q의 장부 한 행은 전달 횟수 한 번을 뜻하지 않는다. 수신 측이 ID q의 처리 기록과 업무 효과를 원자적으로 묶어 이미 처리한 q의 효과를 반복하지 않는 계약을 확인한다.

올바른 잔액은 4, 태그 마지막 쌍은 (A,2), 별도 회수 후보는 {B,C}, 완전 읽기 검증의 당직 상태는 (0,1)이다. 외부 중복 효과는 수신 측 계약으로 막는다.

해결한 뒤 점검할 것

  • expected·desired·부족 조건을 함께 재계산하고 명령 성공과 업무 실패를 분리한다.

  • 네 tag 전환과 살아 있는 객체 조건을 쓰며 보호 후보와 실제 회수를 구별한다.

  • 쓰기 충돌과 읽기 충돌을 구별하고 commit의 원자 검증·적용 가정을 명시한다.

  • 발송 장부·전달 수·수신 효과를 각각 세며 중복 방지 계약을 제시한다.
