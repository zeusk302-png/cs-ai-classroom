소단원 5.1

정적·동적 배정

반복 횟수를 반씩 나누면 두 작업자의 종료 시각도 같을까?

준비 개념과 학습 목표

준비 개념

  • 작업자는 실제 작업을 수행하는 스레드이며 작업은 배정할 계산 묶음이다.

  • chunk는 여러 반복을 한 번에 묶은 단위다. 총 종료 시간 makespan은 마지막 작업자가 끝나는 시각이다.

학습 목표

  • 정적 배정과 완료 후 동적 배정을 추적한다.

  • 일량 불균형과 배정 비용을 함께 판단한다.

같은 작업 목록에서 chunk 크기만 바꿔도 마지막 완료가 달라질까요?

새 독립 작업의 길이는 ID 순서대로 [6,1,1,6,1,1] 시간단위다. 동일한 두 작업자 P와 Q는 시각 0부터 실행하며 각 chunk 내부는 ID 순서로 비선점 실행한다. 정적 연속 배정은 P가 앞 세 개, Q가 뒤 세 개를 맡는다. 정적 순환 chunk 1은 P가 ID 1,3,5를, Q가 ID 2,4,6을 맡는다. 두 방식 모두 각 작업자 계산량이 8이어서 완료 시각은 8이다.

동적 배정의 큐는 ID 순서이며 동시에 요청하면 P가 먼저 가져간다. 현재 chunk를 마친 뒤 다음 chunk를 요청한다. 배정 비용이 0이고 chunk 크기가 1이면 P는 ID 1을 [0,6)에, Q는 ID 2와 3을 [0,1)과 [1,2)에 처리한 뒤 ID 4를 [2,8)에 처리한다. P는 남은 ID 5와 6을 [6,7)과 [7,8)에 처리한다. 완료는 8이다. chunk 크기 2이면 처음 두 묶음의 길이가 각각 7이고 남은 묶음 길이가 2여서 완료는 9다.

별도 요청 비용 모형은 성공한 chunk 요청마다 요청자의 자원을 1시간단위 점유한다. 다른 작업자의 요청과 계산에는 겹칠 수 있으며 중앙 큐의 추가 직렬 비용은 0이다. 빈 큐 확인 비용도 0이다. 정적 배정 비용은 0으로 둔다. 동적 chunk 1의 완료는 11이고 chunk 2도 11이다. 이는 런타임의 실제 비용이 아니라 비용 위치를 명시한 손모형이다. 동일한 일량만으로 요청 횟수의 영향까지 결정할 수 없다.

먼저 확인할 개념
  • 정적 배정과 동적 요청

    기본의 명시 chunk·완료 후 요청·동률 규칙을 새 비용 목록에 적용한다.

  • 준비된 작업의 범위

    모든 새 작업이 독립이라는 조건과 실행 중 작업을 분할하지 않는 계약을 확인한다.

반복 수와 비용은 다를 수 있다

여섯 장의 사진 처리에 필요한 시간이 8,8,1,1,1,1이라고 하자. 앞 두 장과 뒤 네 장의 반복 수만 보고 비슷하게 배정하면 실제 계산 시간은 크게 다르다. 정적 배정은 실행 중의 완료 상황과 관계없이 미리 정한 위치·chunk 규칙으로 일을 나눈다.

정적이 반드시 한 작업자에게 연속된 절반을 준다는 뜻은 아니다. OpenMP static에 chunk 크기를 주면 chunk를 스레드 번호 순으로 돌아가며 배정한다. 크기를 생략하면 대략 균등한 반복 수의 분할을 하지만 정확한 경계를 모든 구현에서 동일하다고 가정하지 않는다. 아래는 우리가 정한 6개 작업 모형이다.

끝낸 작업자가 다음 일을 받는다

동적 배정은 대기열에서 chunk를 받고 끝낸 작업자가 다음 chunk를 요청하는 방식이다. 작업 비용 차이가 커도 빠르게 끝낸 작업자에게 더 많은 작업을 보낼 수 있다. 여기서는 작업 하나가 chunk이고 번호 순 대기열, 동시 요청이면 작업자 P 먼저라는 규칙을 사용한다.

더 잘 나누는 대가로 대기열 동기화와 요청 비용이 든다. 작은 작업마다 비싼 배정을 하면 작업보다 관리가 더 비쌀 수 있다. 메모리 접근의 근접성도 실제 성능에 영향을 주지만 이 종이 표는 캐시와 통신 비용을 0으로 놓는다. 실측 성능과 구분한다.

안전성과 성능은 다른 검사다

배정을 바꾸려면 작업들이 독립이거나 의존성·공유 데이터의 동기화를 갖춰야 한다. 앞 반복의 결과가 다음 반복에 필요한 계산을 단지 dynamic으로 나눠도 안전해지지 않는다. 먼저 어떤 작업이 실행 가능한지 확인하고 그 뒤 어디에 보낼지 정한다.

총일량 20과 두 작업자의 처리율 1을 가정하면 종료 시간은 최소 10이다. 어떤 배정이 10을 달성하는지는 구체 표로 확인해야 한다. 균등 부하와 낮은 관리 비용이 함께 가능한 경우도 있어 동적 배정이 모든 입력에서 유리하다는 결론을 내리지 않는다.

요청 횟수만 같거나 다르다고 완료를 확정하지 않는다.

작업 ID와 작업 길이는 다른 수다. 동적 큐는 아직 배정하지 않은 chunk를 담으며 마지막 성공 요청 이후 빈 큐 확인은 무료라고 명시했다. 실제 OpenMP의 미지정 static chunk 경계나 동적 요청 순서를 이 표와 동일하다고 주장하지 않는다.

중간 과정을 따라가는 예제

시간(8,8,1,1,1,1)의 6작업을 두 작업자에 배정한다. 정적 연속 P=1,2/Q=3..6과 명시한 dynamic1을 비교하라. 배정 비용 0이다.

  1. 정적에서 P의 작업시간8+8=16, Q는1+1+1+1=4이므로 종료16이다.

  2. dynamic에서 t0에 P작업1/Q작업2를 받아 둘 다 t8에 끝난다.

  3. t8에 P작업3/Q작업4, t9에 P작업5/Q작업6을 받아 t10에 모두 끝난다.

  4. 총20/작업자2=10 하한을 dynamic이 달성했다. 정적도 chunk1 순환 배정이면 P1,3,5/Q2,4,6로 각10이 될 수 있다.

이 모형에서 연속 정적16, dynamic1은10, 정적 chunk1 순환도10이다.

성공 요청당 비용 1에서 동적 chunk 1을 추적하라.

  2. Q는 다음 요청 [2,3) 뒤 ID 3을 [3,4), 요청 [4,5) 뒤 ID 4를 [5,11)에 실행한다.

소단원 5.2

작업 훔치기와 부하균형

내 대기열은 비었는데 옆 작업자에게 실행하지 않은 일이 남아 있다면?

준비 개념과 학습 목표

준비 개념

  • 대기 작업과 이미 실행 중인 작업은 다르다.

  • 작업 훔치기 work stealing는 빈 작업자가 다른 작업자의 준비된 대기 작업을 가져오는 방식이다.

학습 목표

  • 실행 중·대기 중·완료 상태를 나누어 일정을 그린다.

  • 부하균형의 한계와 대기열 접근의 안전성을 설명한다.

늦게 시작하는 도둑도 항상 완료를 앞당길까요?

새 비선점 작업 A의 길이는 8이고 B와 C의 길이는 각각 2다. P는 시각 0에 A를 시작하며 자신의 대기열에는 B 다음 C가 있다. Q는 시각 5부터 사용 가능하다. Q가 훔치지 않으면 P가 A 다음 B 다음 C를 실행하여 완료는 12다. 세 작업은 독립이고 각각 정확히 한 번 실행되어야 한다.

자체 훔치기 정책에서 Q는 시각 5에 대기열 끝의 C를 원자적으로 예약한다. 이동 비용 σ≥0은 Q의 자원을 점유하고 그 뒤 C를 계산한다. 예약한 C는 이동 중에도 P가 다시 가져가지 않는다. Q가 끝나면 대기열의 B를 요청하며, 동시 요청이면 소유자 P가 우선한다. P가 자기 큐에서 작업을 가져오는 비용은 0이다. A는 이미 실행 중이므로 훔칠 수 없다.

σ=0이면 Q의 C는 [5,7), B는 [7,9)이고 전체 완료는 9다. σ=1이면 C는 [6,8)에 실행되고 시각 8의 동률에서 P가 B를 [8,10)에 실행하여 완료는 10이다. σ=6이면 C는 이동 [5,11) 뒤 [11,13)에 실행되고 P의 B는 [8,10)에 끝난다. 전체 완료 13은 훔치지 않은 12보다 늦다. 이 반례는 큐 예약의 정확성과 이동의 이익이 다른 판단임을 보여 준다.

먼저 확인할 개념
  • 실행 중과 준비 대기의 구별

    기본의 A 실행과 B/C 대기 상태를 늦은 Q 및 명시 이동 비용에 적용한다.

  • 논리 작업과 작업자

    작업 ID를 보존하고 실제 자원 사용 가능 시각을 따로 기록한다.

일을 가진 곳을 찾아간다

중앙 대기열에서 모든 일을 받는 모형과 달리 작업자별 대기열을 둘 수 있다. 한 작업자가 일을 여러 개 생성했고 다른 작업자가 한가하면 준비된 작업을 옮겨 쓸 수 있다. Oracle fork/join은 이런 work stealing을 사용하는 공식 예시다. 구체적인 대기열 양끝 규칙과 도움 실행 정책은 런타임마다 다르다.

여기서는 P의 첫 작업 A는 이미 실행 중이고 B,C는 독립적으로 실행 가능한 대기 작업이다. Q는 먼저 C를 가져오고 다음 B를 가져오는 자체 정책을 정한다. 실행 중 A를 자동으로 반씩 잘라 가져온다고 가정하지 않는다. 기존 코드에 표시한 준비 작업만 이동한다.

한 번만 실행되도록 가져온다

P와 Q가 같은 대기 작업 B를 동시에 집으려 하면 둘 중 하나만 성공해야 한다. 큐 접근은 원자 연산이나 적절한 잠금 등으로 보호해야 하며 데이터 경쟁을 예상 시간표에서 숨기면 안 된다. 처리 중 데이터의 권한·수명도 확인한다.

훔치기에 성공했다고 원래 작업의 공유 데이터 접근도 자동으로 안전해지는 것은 아니다. 서로 다른 출력 칸을 쓰는 독립 계산과 같은 누적값을 수정하는 계산은 다르게 설계한다. 반대로 모든 준비 작업이 없고 의존 결과를 기다리는 상황에서는 다른 큐를 돌아봐도 실행 가능 일이 생기지 않는다.

옮길 수 있는 일이 있어야 효과가 있다

일량 W를 p 작업자가 처리해도 한 긴 의존 경로 S보다 빨리 끝날 수 없으므로 이상 하한은 max(W/p,S)다. 훔치기는 배정 불균형을 줄이는 도구지만 순차 의존이나 이미 실행 중인 큰 작업을 없애지는 않는다. 작업이 너무 잘게 나뉘면 이동 비용이 커질 수 있다.

실제 메모리 위치에 따라 다른 작업자에게 옮겼을 때 캐시·NUMA 비용이 달라질 수 있다. 수치 성능을 주장하려면 실제 측정이 필요하다. 여기서는 일량·의존성과 별도 0비용 이동 모형만 계산한다. 특정 work stealing 기대시간 정리의 조건을 모든 스레드 프로그램에 확장하지 않는다.

늦게 시작하는 도둑도 항상 완료를 앞당길까요?

중간 과정을 따라가는 예제

P대기열은 A8,B2,C2이고 P는 t0에 A를 시작했다. Q는 t0에 C를 훔치고 끝나면 B를 훔친다. 세 작업 독립·이동 비용 0이다. 훔치기 없는 경우와 비교하라.

  1. 훔치기 없으면 P가 A0..8,B8..10,C10..12를 실행하고 Q는 빈다. 종료 12다.

  2. 훔치기 있으면 Q가 C0..2,B2..4를 실행한다. P의 A는 0..8 그대로다.

  3. 마지막 작업 A가 끝나는 8이 전체 종료다. 총일량 12라 W/2=6이지만 긴 A8이라는 추가 하한이 있다.

  4. 따라서 6까지 단축되지 않으며 주어진 분할의 하한 8을 달성한다.

종료 12→8이다. A를 분할하지 않아 Q가 4..8에 한가하다.

조건을 바꾸어 비교하기

시각 8의 동시 요청을 판정한다

σ=1의 C/B 소유권과 완료를 구하라.

  1. Q가 시각 5에 C를 예약하고 이동 뒤 [6,8)에 계산한다.

  2. 시각 8에 P의 A와 Q의 C가 끝난다. 소유자 우선 규칙으로 P가 B를 가져온다.

B는 [8,10)에 실행되고 전체 완료는 10이다.

실제 런타임의 경쟁 결과가 아니라 명시한 동률 정책의 결과다.

예약 이후 되가져올 수 없는 작업

σ=6에서 P가 시각 10에 C를 다시 실행해 완료를 12로 줄였다고 한다. 감사하라.

  1. C는 이미 시각 5에 Q가 예약했으므로 P 대기열에서 제거되었다.

  2. Q의 이동은 [5,11), C 실행은 [11,13)이며 P가 동시에 실행하면 ID C를 중복 처리한다.

계약상 올바른 완료는 13이다.

비교할 점

예상 시간이 짧아도 소유권 규칙을 어긴 후보는 같은 모형의 일정이 아니다.

훔칠 대기 작업이 있는지와 중복 실행을 별개로 묻는다.

풀이 보기

A 하나를 분할하지 않는 모형은 여전히 종료 8이다. 동시 B 접근에서는 대기열의 원자적인 가져오기로 한 작업자만 B를 얻도록 해야 한다. 실제 동기화 코드를 검증했다는 뜻은 아니다.

오해와 반례

한가한 작업자가 있으면 현재 실행 중인 작업도 항상 자동으로 반씩 나눠 간다.

우리 A는 이미 실행 중인 8단위 작업이며 Q가 훔칠 수 있는 것은 B,C뿐이다. 모든 작업이 긴 순차 하나라면 가져올 준비 작업이 없다. 분할 설계가 먼저 필요하다.

스레드풀·fork-join

작업을 천 개 만들면 운영체제 스레드도 천 개 만들어야 할까?

준비 개념과 학습 목표

준비 개념

  • 스레드풀은 여러 작업에 대해 작업자 스레드를 재사용하는 구조다.

  • fork는 논리적으로 자식 작업을 나누고 join은 필요한 결과의 완료를 기다리는 관계다.

학습 목표

  • 논리적 작업 수와 실제 작업자 수를 구분한다.

  • 분할 기저 조건·join·풀 대기의 위험을 추적한다.

더 많은 논리 작업이 언제 실제 완료를 줄일까요?

새 정확 정수 합은 1부터 12까지이며 기저 길이가 3 이하이면 순차로 직접 합한다. 반씩 나누면 잎 구간은 1..3, 4..6, 7..9, 10..12이고 합은 6,15,24,33이다. 중간 합은 21과 57이며 루트는 78이다. 작업 노드는 7개지만 덧셈은 잎마다 2회와 결합 3회로 모두 11회다. 작업 노드 수와 산술 연산 수가 같던 기본 길이 8 예제를 모든 길이로 확대하지 않는다.

덧셈마다 1시간단위이고 작업 생성·통신·대기는 비용 0이며 작업자 네 명이 시각 0부터 사용 가능하다고 정한다. 네 잎의 순차 두 덧셈은 [0,2)에 동시에 수행하고 두 중간 결합은 [2,3), 루트는 [3,4)에 수행한다. 총 작업량은 11이고 span은 4여서 완료 4를 달성한다. 기저 임계값을 6으로 바꾸면 두 잎의 합은 21과 57이고 잎마다 다섯 덧셈 후 루트 한 번으로 완료는 6이다.

별도 준비 비용 비교는 모든 논리 작업 노드를 하나의 준비자가 먼저 등록한 뒤 계산을 시작한다. 노드당 준비 비용은 β≥0이며 계산과 겹치지 않는다. 임계값 3의 전체 시간은 7β+4, 임계값 6은 3β+6이다. 이 일괄 준비 모형은 실제 재귀 fork 생성 과정이 아니다. 또 하나의 작업자 풀에서 부모가 자식을 넣고 같은 작업자를 점유한 채 완료를 기다리면 자식은 실행할 수 없다. 자식 완료 뒤 실행될 continuation을 등록하고 자원을 반환하는 별도 설계는 순환 점유를 피할 수 있다.

먼저 확인할 개념
  • 작업 노드와 덧셈 수

    기본 fork-join 트리의 기저·join·실제 작업자 구별을 길이 12로 확장한다.

  • 대기하는 부모와 작업자 점유

    기본 스레드풀 설명의 부모 대기와 자식 실행 자원 부족을 확인하고 결과 의존을 유지한 자원 반환과 비교한다.

작업과 운영체제 스레드는 같은 수일 필요가 없다

배열 합을 반씩 나누면 논리적 작업은 트리처럼 늘어난다. 풀은 몇 개의 작업자가 여러 준비 작업을 차례로 처리하게 할 수 있다. fork를 만났다고 즉시 새 운영체제 스레드가 하나 생긴다고 생각하지 않는다. 논리적 병렬 가능성을 실제 하드웨어에 배치하는 일은 스케줄러가 한다.

작업 크기가 작으면 그 구간을 직접 계산하고 크면 둘로 나눈다. 분할 크기는 줄어야 종료하며 임계값은 관리 비용과 병렬 가능성의 절충이다. 임계값과 실제 스레드 수는 서로 다른 설정이다. 여기서는 길이 2 이하를 직접 합산한다.

결과를 사용하기 전에 합류한다

1..8합은 왼쪽 1..4와 오른쪽 5..8로 분할하고 두 결과가 완료된 뒤 더한다. 자식 결과가 아직 없는데 부모가 즉시 더하면 완료되지 않은 값을 읽을 수 있다. MIT spawn/sync 모형에서 sync는 이런 의존성을 명시한다.

정수 덧셈은 이 예제의 작은 범위에서 정확하게 계산한다고 가정한다. 일반 부동소수점 합은 덧셈 순서가 바뀌면 반올림 결과도 달라질 수 있다. 병렬 합과 직렬 합이 수학적으로 같다는 사실을 모든 구현의 비트 단위 동일 결과로 확대하지 않는다.

풀 안에서 기다리는 작업도 설계해야 한다

고정 2작업자 풀에서 부모 P,Q가 각 작업자를 차지하고 각자 자식 일을 같은 풀에 넣은 뒤 완료까지 작업자를 점유한 채 블록한다고 하자. 자식은 대기열에 있어도 빈 작업자가 없어 진행할 수 없다. 풀을 썼다는 사실만으로 이 의존 교착이 사라지지 않는다.

fork/join 런타임은 작업 도움 실행 같은 정책을 사용할 수 있지만 임의의 외부 I/O나 잠금 대기까지 항상 해결한다고 보장하면 안 된다. 준비 작업·대기 관계·풀의 대기 정책을 함께 검토한다. 이 단원은 Java 코드 실행이 아닌 추상 작업 트리를 추적한다.

더 많은 논리 작업이 언제 실제 완료를 줄일까요?

정수 합은 작은 정확 범위이고 일반 부동소수점의 비트 동일성을 주장하지 않는다. 일괄 준비 비용과 재귀 생성 비용은 구별하며 continuation이라는 말만으로 실제 런타임의 블록 대기를 검증한 것은 아니다.

중간 과정을 따라가는 예제

정수 배열 1..8을 길이 2 이하에서 직접 합산하는 fork-join 트리로 구하라. 작업 노드 수와 덧셈 수도 세라.

  1. 네 잎 작업은 1+2=3,3+4=7,5+6=11,7+8=15다.

  2. 왼 부모는 3+7=10,오른 부모는 11+15=26이다.

  3. 루트는 두 결과 join 후 10+26=36이다.

  4. 작업 노드는 잎4+중간2+루트1=7이다. 덧셈은 잎4회+중간2회+루트1회=7회다.

  5. fork/join 관리 비용 0·덧셈 1시간·4작업자이면 잎 1시간,중간 1시간,루트 1시간의 3단계 일정이 가능하다.

합 36,작업 7,덧셈 7이다. 3시간은 관리 비용을 제외한 4작업자의 종이 일정이다.

작업 수와 덧셈 수가 달라진 트리

  1. 네 잎 합은 6,15,24,33이고 각 잎은 두 덧셈을 수행한다.

  2. 중간은 6+15=21 및 24+33=57, 루트는 21+57=78이다.

비교할 점

노드마다 한 덧셈을 수행한다는 일반화가 기저의 실제 연산을 놓친다.

준비 비용의 경계

노드당 일괄 준비 비용 β에서 두 임계값의 전체 시간 차를 구하라.

  1. 세분 설계 시간에서 굵은 설계 시간을 빼면 (7β+4)−(3β+6)=4β−2다.

  2. β=1/2에서 차는 0이며 모두 15/2이다.

0≤β<1/2이면 임계값 3이 빠르고 β>1/2이면 임계값 6이 빠르다.

  2. 중간 결합 둘을 [4,5)에, 루트를 [5,6)에 처리한다.

  3. 전체 완료 시각을 T라 하면 각 잎의 결과 뒤에는 길이 1인 중간 결합과 길이 1인 루트 결합이 남는다. 따라서 네 잎은 모두 T−2까지 완료해야 한다. 잎의 총 작업량은 8이고 작업자가 두 명이므로 잎을 모두 완료하는 데 최소 4가 필요하다. 그러므로 T≥6이며 앞 일정이 이 하한을 달성한다.

세 독립 모형을 감사하라. ① 작업 길이는 ID 순서 [6,1,1,6,1,1]이고 두 작업자·번호순 동적 큐·동률 P 우선이다. 배정 비용 0에서 chunk 1과 2의 완료를 비교하고, 성공 요청마다 요청자 시간을 한 단위 점유하는 별도 모형도 비교하라. ② P의 A는 [0,8)에 실행 중이고 길이 2의 B,C는 대기 중이다. Q는 시각 5에 C를 예약하며 이동 비용 σ는 Q에서 수행한다. 동시 B 요청에서는 P가 우선이다. σ=0,1,6의 전체 완료를 비훔치기와 비교하라. ③ 1..12의 합을 기저 길이 3 또는 6으로 분할하고 덧셈당 시간 1·작업자 네 명·비용 0에서 계산한다. 노드당 비용 β의 일괄 준비를 계산 전에 추가했을 때의 경계와, 단일 풀의 블록 부모/자식 대기를 구별하라.

힌트 1

① 비용 없는 계산과 요청자 자원의 관리 구간을 따로 그린다. ② 예약한 C를 P가 중복 실행하지 않는다.

힌트 2

③ 잎의 덧셈 횟수와 노드 수는 다르다. 논리 의존뿐 아니라 블록 점유 자원도 확인한다.

풀이와 답 확인

  1. ① 비용 0의 동적 chunk 1은 시각 8에, chunk 2는 시각 9에 완료한다. 요청당 비용 1의 별도 모형에서는 두 설계 모두 시각 11에 완료한다.

  2. ② 비훔치기 완료는 12다. σ=0이면 Q가 C와 B를 시각 9까지 실행한다. σ=1이면 P가 동률에서 B를 가져와 전체 완료가 10이다. σ=6이면 Q의 C가 시각 13에 끝나 전체 완료도 13이다.

  3. ③ 임계값 3은 잎 합 6,15,24,33과 결합 21,57,78로 노드 7개·덧셈 11회·완료 4다. 임계값 6은 노드 3개·덧셈 11회·완료 6이다. 일괄 준비를 더하면 전체 시간은 7β+4와 3β+6이며 β=1/2에서 모두 15/2다.

  4. 단일 풀에서 부모의 블록 점유가 자식 실행을 막으면 종료하지 못한다. 자원 반환 뒤 자식 완료에 따라 준비되는 continuation은 결과 의존을 유지한 별도 설계다.

작업 ID와 결과 보존, 요청 비용의 위치, 큐 예약과 완료 개선, 논리 노드와 산술 수 및 자원 점유를 각각 명시한다.

해결한 뒤 점검할 것

  • 모든 작업의 정확히 한 번 배정과 출력 보존을 확인한다.

  • σ=0과 σ≥1의 B 예약 갈래를 구별하고 안전한 훔치기가 느려지는 반례를 설명한다.

  • 임계값별 노드·덧셈·span과 일괄 준비의 경계를 제시한다.

  • 작업 준비와 작업자 가용을 구별하고 실제 OpenMP/Java/학생 실행을 주장하지 않는다.
