소단원 8.1

snooping·directory 개요

두 CPU가 같은 점수의 복사본을 갖고 있을 때, 한쪽이 고치면 다른 쪽은 어떻게 알아차릴까?

학습 목표

복사본에 붙이는 규칙

캐시 일관성(coherence)은 같은 메모리 위치의 쓰기 순서와 복사본이 관측하는 값의 관계를 관리한다. CPU의 가까운 캐시에 데이터가 있다고 해서 다른 CPU의 갱신을 영원히 무시할 수는 없다. 캐시는 보통 변수 하나보다 큰 라인을 단위로 복사하고 무효화한다.

쓰기 무효화 모형에서는 쓰기 권한을 얻는 CPU가 다른 유효 복사본을 무효화한 뒤 새 값을 쓴다. 최신 값은 수정한 캐시에 남을 수 있어 주 메모리가 항상 최신이라는 뜻은 아니다. 서로 다른 주소의 연산 순서와 프로그램의 데이터 경쟁은 메모리 모델·원자 연산·동기화가 따로 다룬다.

모두 듣기와 담당자에게 묻기

단순 snooping은 캐시들이 공유 전달망의 요청을 감시하고 자신이 가진 라인과 관련 있는지 검사한다. 방송은 작은 시스템에서 직관적이지만 코어 수가 늘면 각 캐시가 검사해야 하는 요청과 전달망 부담이 커진다. 현대 시스템이 모두 단일 버스를 사용한다는 뜻은 아니다.

Directory는 라인별 home에 공유자 또는 소유자 정보를 두고 관련 캐시로 요청을 보낸다. 읽기 실패는 home을 찾아가며, 쓰기는 기존 공유자에게 무효화를 보내고 필요한 확인을 받는다. 전체 시스템을 대상으로 하는 방송을 줄여도 home 병목·메타데이터 공간·복잡한 동시 요청 처리는 남는다.

교육 모형을 먼저 닫기

이 절에서는 한 라인, 정확한 공유자 집합, 쓰기 무효화, 요청이 순차 완료되는 교육 모형을 사용한다. 실제 프로토콜의 일시 상태·재시도·응답 순서와 MESI/MOESI 전체 상태표는 생략한다. 메시지 개수를 계산할 때는 데이터 응답·확인까지 포함했는지 별도로 정해야 한다.

학습자는 라인 카드에 유효 복사본 보유자를 적고 요청마다 갱신하면 된다. 읽은 CPU가 늘면 공유자 집합도 늘고, 한 CPU가 독점 쓰기를 얻으면 다른 공유자는 유효 집합에서 빠진다. 이 추적이 실제 CPU 시뮬레이터 실행이나 성능 측정은 아니다.

중간 과정을 따라가는 예제

CPU A,B,C가 있다. 라인 L의 값은 0이고 directory 공유자는 {A,B}, 두 복사본은 clean이다. C가 L을 읽은 뒤 A가 독점 쓰기 권한을 얻어 1을 쓴다. 순차 완료 모형에서 무효화 대상을 구하라.

  1. C의 읽기 요청은 L의 home으로 간다. clean 데이터 응답 후 공유자 집합은 {A,B,C}가 된다.
  2. A의 쓰기 권한 요청에서 A 자신의 복사본은 무효화 대상에서 제외한다. 대상은 B와 C이다.
  3. B,C의 무효화 완료 확인 후 A가 단독 쓰기 소유자가 된다. A의 라인에 값 1이 저장된다.
  4. 주 메모리 갱신은 write-back 정책에 따라 나중일 수 있으므로 이 순간 주 메모리도 1이라고 단정하지 않는다.

무효화 대상은 B,C 두 캐시다. A의 최신 유효 값은 1이며 주 메모리 상태는 별도다.

오해와 반례

캐시가 일관되면 락이나 원자 연산은 필요 없다.

동시에 같은 정수를 읽고 증가시킨 뒤 쓰면 두 CPU가 같은 이전 값을 보고 갱신 하나를 잃을 수 있다. 캐시 일관성은 여러 명령으로 된 증가 전체를 하나의 원자적 작업으로 만들지 않는다.

소단원 8.2

false sharing·NUMA

서로 다른 두 카운터를 각자 고치는데도 왜 CPU들이 서로 기다릴까?

준비 개념과 학습 목표

준비 개념

  • 캐시 라인
  • 배열 주소와 정렬
  • 메모리 지연시간

학습 목표

  • false sharing과 실제 데이터 공유를 구별한다.
  • 주소로 캐시 라인 경계를 계산한다.
  • NUMA 배치와 CPU 배치를 함께 고려한다.

변수는 달라도 라인은 같다

두 스레드가 서로 다른 변수를 변경해도 변수가 같은 캐시 라인에 있으면 쓰기 권한이 번갈아 이동할 수 있다. 이것이 false sharing이다. 언어 수준에서 같은 변수를 경쟁적으로 접근한다는 뜻과는 다르며, 최소 한쪽에 쓰기가 있어야 이 무효화 비용이 문제가 된다.

읽기 전용 두 값이 한 라인에 있는 것은 공간 지역성을 돕기도 한다. 해결책은 뜨거운 쓰기 데이터를 분리하거나 스레드별 누적 후 합치기지만 padding을 늘리면 메모리·캐시·TLB 부담이 증가한다. 무조건 모든 변수를 한 라인씩 차지하게 하지 않는다.

라인 경계와 정렬

라인 크기 B와 주소 a가 주어지면 라인 번호는 floor(a/B)이다. 이 예제는 B=64바이트, 주소0이 라인 경계이고 8바이트 카운터가 경계를 넘지 않는다고 가정한다. 실제 하드웨어 라인 크기와 allocator의 정렬은 확인해야 한다.

카운터 사이에 64바이트를 띄웠다는 말과 구조체 전체를 64바이트 정렬했다는 말은 다르다. 데이터가 라인 경계를 가로지르면 더 많은 라인을 건드릴 수 있다. 컴파일러가 레지스터에 누적하고 마지막에 한 번만 저장하는 코드라면 예상한 쓰기 빈도도 달라진다.

메모리가 물리적으로 가까운가

NUMA는 공유 주소 공간 안에서도 CPU와 메모리 노드의 거리에 따라 접근 비용이 다른 구조다. 캐시 적중이면 DRAM까지 가지 않지만, 실패와 대역폭 부담에는 배치가 영향을 준다. 일관성이 유지된다고 모든 메모리 접근 시간이 같아지는 것은 아니다.

지역 할당 정책에서 페이지를 처음 실제로 접근하며 할당하는 스레드와 이후 작업 스레드가 다르면 원격 메모리가 될 수 있다. Linux 정책 변경은 보통 이후 할당에 적용하며 기존 페이지가 자동으로 모두 옮겨지는 것은 아니다. 스레드 고정·페이지 배치·작업 분할을 함께 계획하고 실제 이익은 측정해야 한다.

중간 과정을 따라가는 예제

64바이트 라인 모형에서 CPU A는 주소0의 8바이트 카운터, B는 주소8의 8바이트 카운터를 반복 저장한다. B의 카운터를 주소64로 옮기면 라인 번호가 어떻게 변하는가?

  1. floor(0/64)=0이고 floor(8/64)=0이므로 두 카운터가 라인0에 있다. 각 변수는 다르지만 저장으로 한 라인의 권한을 경합할 수 있다.
  2. 주소64의 라인 번호는 floor(64/64)=1이다. 두 카운터가 각각 라인0과1을 차지한다.
  3. 두 64바이트 슬롯을 예약한다면 총128바이트이고 실제 카운터 데이터16바이트보다112바이트 더 예약한다. 이는 이 배치 모형의 공간 비용이다.

라인0 공동 사용에서 라인0/1 분리로 바뀐다. false sharing 후보는 줄지만 속도 향상 수치는 실측하지 않았다.

종이와 본문으로 직접 해보기

힌트 보기

가중합을 접근 수로 나눈다.

오해와 반례

NUMA가 있으면 무조건 모든 페이지를 한 노드에 몰아야 한다.

그 노드의 대역폭이나 용량이 병목일 수 있다. 여러 노드에서 읽는 공유 데이터는 interleave가 유리할 수도 있고 스레드별 전용 데이터는 지역 배치가 나을 수 있다. 접근 패턴과 제약에 맞춘다.

카운터를 스레드별로 n회 누적한 뒤 한 번 합치는 방식은 공유 저장 횟수를 줄인다. 단, 다른 스레드가 매 순간 최신 합계를 필요로 하면 의미가 달라진다. 읽기 요구와 동기화 시점을 먼저 정하고 주소·빈도·성능 카운터를 실제 측정하는 후속 실험을 설계해 보자. 여기서는 수행하지 않았다.

통신 비용을 나누어 보기

데이터 이동에는 시작 지연과 전송량에 비례하는 시간이 있다. 단순 모형 T=α+N/β에서 α는 시작 비용, N은 바이트, β는 바이트/초 대역폭이다. 작은 메시지를 합치면 시작 비용을 줄일 수 있지만 묶는 동안 기다리는 시간과 메모리 사용이 늘어난다.

동시에 전송하거나 계산과 겹치는 시스템에서는 시간을 무조건 더하면 안 된다. 이 절의 수치는 직렬 처리·중첩 없음·고정 대역폭인 교육 가정이다. 통신이 캐시 간 라인 이동인지 네트워크 메시지인지도 구별해 모델을 정한다.

경합을 계산 밖으로 빼기

락이 보호하는 공용 카운터를 매번 갱신하면 스레드들이 같은 직렬 구간과 라인의 권한을 기다린다. 각 스레드가 지역 합계를 만들고 마지막에 한 번 합치면 갱신 횟수를 줄일 수 있다. 자료 구조와 알고리즘을 바꾸는 것이 락 명령 하나를 바꾸는 것보다 효과적일 수 있다.

일괄 처리는 모든 중간 결과가 즉시 공유된다는 의미를 포기할 수 있다. 동일 변수의 원자 연산도 일관성 통신과 직렬화 비용이 있으므로 무한 확장하지 않는다. false sharing은 서로 다른 값의 배치 문제이고 진짜 경합은 같은 자원의 의미상 공유 문제다.

미리 가져오기와 너무 멀리 가져오기

프리패치는 곧 사용할 데이터를 미리 요청하여 실패 지연을 계산과 겹치려는 방법이다. 반복마다 c초의 독립 계산을 한다면 d회 앞을 가져올 때 준비시간은 대략 dc이다. 지연 L을 가리려면 dc≥L이 필요하다는 단순 조건을 얻지만 대역폭·큐 깊이·의존성 때문에 충분 조건은 아니다.

너무 가까우면 늦고 너무 멀면 사용 전에 쫓겨나거나 캐시를 오염시킨다. 불규칙한 주소나 다음 포인터를 읽어야만 알 수 있는 순차 의존도 한계다. GCC의 지원과 명령 생성은 대상에 따라 다르며 프리패치는 동기화나 값 갱신의 보장이 아니다. 주소 표현식 자체도 유효해야 한다.

중간 과정을 따라가는 예제

중첩 없는 전송 모형에서 α=2μs, β=1000바이트/μs이다. 100바이트 메시지10개를 각각 보내는 시간과 1000바이트 한 개로 묶는 시간을 계산하라.

  1. 각 메시지는2+100/1000=2.1μs다.10개를 직렬 전송하면21μs다.
  2. 한 묶음은2+1000/1000=3μs다. 시작 지연이10번에서1번으로 줄었다.
  3. 줄어든18μs에 묶는 계산·대기·헤더·실제 대역폭 변화는 포함하지 않았다.

교육 모형에서는21μs와3μs다. 실측 성능이나 항상7배 빠른 프로그램이라는 의미는 아니다.

종이와 본문으로 직접 해보기

실패 지연120ns, 반복당 독립 계산20ns인 모형에서 최소 몇 반복 앞의 프리패치가 필요한가? 지연이140ns면?

힌트 보기

dc≥L을 만족하는 최소 정수 d를 고른다.

풀이 보기

120/20=6이므로6회 앞,140/20=7이므로7회 앞이다. 충분한 대역폭과 요청 중첩을 가정한 시점 계산이며 실제 성능은 따로 검증한다.

오해와 반례

프리패치를 넣으면 데이터 경쟁도 해결되고 언제나 빨라진다.

프리패치는 값을 보호하지 않으며 락·원자 연산의 의미를 대신하지 않는다. 필요 없는 라인을 가져오면 대역폭과 캐시를 낭비하여 느려질 수도 있다.
