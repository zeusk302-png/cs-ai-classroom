소단원 11.1

MPI식 통신 모델

서로 다른 컴퓨터에 있는 배열을 어떻게 안전하게 주고받을까?

준비 개념과 학습 목표

준비 개념

  • 프로세스와 주소 공간

  • 배열과 자료형

  • 순서와 대기

학습 목표

  • rank·communicator·tag를 사용해 메시지의 상대와 종류를 구별한다.

  • 통신 완료와 계산 완료를 구별하고 순환 대기를 찾는다.

지역 데이터와 메시지의 경계

메시지 전달 방식에서는 각 프로세스가 자기 데이터를 관리하고 필요한 값을 다른 프로세스에 보낸다. 이 단원은 공유 메모리를 직접 사용하는 방식 대신 별도 주소 공간 사이의 통신을 생각한다. 같은 이름의 배열이 있어도 두 프로세스의 배열이 자동으로 같은 저장소가 되지는 않는다.

MPI는 이런 통신을 표현하는 표준 인터페이스다. 여기서는 MPI 4.1의 한 그룹 안 통신인 intra-communicator를 기준으로 개념을 공부한다. rank는 그 communicator 안에서 프로세스를 식별하는 번호다. 한 프로세스가 다른 그룹에서는 다른 rank를 가질 수 있으므로 rank 0이라는 말만으로 컴퓨터 전체의 고유 번호를 뜻하지 않는다.

봉투와 내용은 따로 확인한다

메시지를 편지에 비유하면 communicator는 통신 세계, source와 destination은 보낸 사람과 받는 사람, tag는 편지 종류다. 수신은 상대·tag·communicator 조건이 맞는 메시지를 찾는다. tag가 같아도 communicator가 다르면 별개의 통신이다. 자료형과 원소 수는 그 안에 담긴 내용을 해석하고 저장할 때 확인한다.

MPI_INT 두 원소를 보낸다면 count는 2다. count를 바이트 수로 읽으면 안 된다. 수신 버퍼는 메시지 전체를 담을 수 있어야 한다. 큰 버퍼가 작은 메시지를 받는 것은 가능하지만 작은 버퍼에 큰 메시지를 넣는 것을 정상적인 부분 수신으로 취급할 수 없다. 실제 원소 수는 상태 정보와 MPI_Get_count 등을 사용하는 다음 실습에서 확인할 수 있다.

함수의 반환이 보장하는 것

표준 blocking send의 정상 완료는 송신 버퍼를 다시 사용할 수 있다는 뜻이다. 내부 버퍼에 복사되어 반환할 수도 있으므로 상대의 응용 계산까지 끝났다는 뜻은 아니다. 반면 blocking receive가 정상 완료되면 받은 데이터가 수신 버퍼에 들어 있다. 송신 완료와 수신 뒤 계산 완료를 구별하면 잘못된 확인 메시지를 줄일 수 있다.

두 프로세스가 모두 상대의 메시지를 먼저 기다리면 아무도 보내는 단계에 도달하지 못한다. 둘 다 send를 먼저 호출하는 방법도 표준 통신의 충분한 내부 버퍼에 기대면 큰 메시지에서 막힐 수 있다. 순서를 비대칭으로 정하거나 서로 맞는 수신과 송신을 먼저 시작한 뒤 완료를 기다리는 설계가 필요하다. 여기서는 코드 실행 없이 호출 순서를 종이에 추적한다.

중간 과정을 따라가는 예제

같은 communicator C의 rank 0이 rank 1에 tag 11로 정수 [4,7]을 보낸다. rank 1은 source 0, tag 11, MPI_INT, 수신 count 2를 지정한다. 정상 수신 뒤 두 수를 더하라. 다른 tag와 부족한 버퍼도 비교하라.

  1. 수신자가 rank 1이고 source 0·tag 11·C가 일치하므로 해당 메시지는 수신 조건에 맞는다.

  2. 송신은 MPI_INT 2원소이고 수신도 2원소 공간이므로 [4,7] 전체를 담는다.

  3. 정상 수신 뒤 4+7=11이다. 수신 tag를 12로 한정하면 이 메시지는 맞지 않으므로 이것만으로 수신이 완료되지 않는다.

  4. 수신 공간을 1원소로 줄이면 메시지 전체를 담을 수 없다. 이를 정상적인 [4] 수신이라고 가정하지 말고 오류로 다룬다.

정상 조건에서는 합 11이다. tag 불일치와 버퍼 부족은 서로 다른 문제다.

종이와 본문으로 직접 해보기

rank 0과 1 모두 “상대에서 receive → 상대에게 send” 순서다. 화살표로 각 receive가 기다리는 send를 연결하라. rank 0만 send → receive로 바꾸면 무엇이 달라지는가?

힌트 보기

실행되지 못하는 다음 단계와 현재 대기가 의존하는 단계를 구별한다.

풀이 보기

처음에는 0의 receive가 1의 뒤쪽 send를, 1의 receive가 0의 뒤쪽 send를 기다린다. 둘 다 다음 단계로 못 가므로 순환 대기다. 0이 먼저 send하면 1의 이미 시작한 receive와 맞고 이후 1의 send와 0의 receive가 맞는다. 양쪽 모두 send부터 하는 버퍼 의존 해법과 구별한다.

오해와 반례

MPI_Send가 반환하면 상대가 받은 값을 이용한 계산도 끝났다.

내부 버퍼에 복사되어 송신이 완료되어도 상대는 아직 계산 전일 수 있다. 계산 완료가 필요한 프로토콜이라면 상대가 실제 계산 후 별도의 확인을 보내는 등 그 사건을 명시해야 한다.

자기점검

rank 0은 모든 communicator에서 같은 프로세스를 뜻하는가?

답과 이유 보기

아니다.

rank는 그룹 안의 상대 번호다.

MPI_INT 2원소의 count는 반드시 8인가?

답과 이유 보기

아니다. count는 2다.

원소 수와 바이트 수는 다르며 정수의 저장 크기도 따로 확인한다.

양쪽이 receive부터 시작하면 내부 송신 버퍼가 커서 해결되는가?

답과 이유 보기

아니다.

송신 호출 자체에 도달하지 못한다.

소단원 11.2

broadcast·all-reduce

한 사람의 설정을 모두에게 보내는 일과 모두의 점수를 합치는 일은 어떻게 다를까?

준비 개념과 학습 목표

준비 개념

  • 프로세스의 rank

  • 합과 최댓값

  • 가중평균

학습 목표

  • broadcast와 reduce·all-reduce의 입력·결과 위치를 구별한다.

  • 모든 참여자의 호출 순서와 자료 조건을 확인한다.

하나의 입력을 복사하는 broadcast

방송인 broadcast는 지정한 root의 데이터를 그룹 전체에 전달한다. 여기서 root는 그룹 안 번호이며 항상 0일 필요는 없다. root를 포함한 그룹 구성원이 같은 communicator와 같은 root를 사용해 해당 호출에 참여한다. 받는 프로세스의 자료 공간도 올바르게 준비해야 한다.

rank 2의 설정을 방송할 때 rank 0·1·3의 원래 설정을 모아서 평균을 내는 것은 아니다. 각 결과가 rank 2의 입력과 같아지는 연산이다. 여러 사람의 값을 모으는 gather나 합치는 reduction과 목적이 다르다.

여러 입력을 결합하는 reduction

reduction은 각 참여자의 값을 합·최댓값 등의 연산으로 결합한다. reduce는 지정한 root에 결과를 두고, all-reduce는 모든 참여자에게 결합 결과를 제공한다. 같은 연산과 자료 조건으로 참여해야 하며 벡터 합에서는 같은 위치끼리 합친다. 배열 하나를 방송하는 것과 각자의 배열을 합치는 일을 구별하자.

합 연산을 선택해도 평균은 자동 계산되지 않는다. 모든 참여자의 자료 수가 같으면 지역 평균들의 평균이 전체 평균과 같지만, 자료 수가 다르면 각각의 합과 개수를 모아야 한다. 아래 정수 예제는 값과 결과가 자료형 범위 안에 든다고 가정한다. 부동소수점 합은 결합 순서에 따라 반올림 결과가 달라질 수 있어 수학적 실수 합과 동일한 비트 결과를 보장한다고 말하지 않는다.

모두의 호출이 하나의 약속이다

한 communicator의 집합통신은 그룹 전체에서 같은 순서로 호출해야 한다. 일부는 broadcast부터, 일부는 all-reduce부터 시작하면 서로 다른 연산을 맞추는 잘못된 프로그램이 된다. 특정 rank만 if문 안에서 호출하고 다른 rank가 건너뛰는 설계도 그룹 전체 참여 약속을 깨뜨린다.

broadcast의 데이터 전달 완료를 별도의 barrier처럼 가정하지 않는다. 구현이 동기화 효과를 보일 수는 있어도 필요한 프로그램 순서를 그 효과에 기대어 설계하지 않는다. 자신의 결과 버퍼를 안전하게 사용하는 조건과 모든 구성원이 특정 지점에 도달했다는 조건은 구별해야 한다.

중간 과정을 따라가는 예제

그룹 rank 0..3에서 root 2의 [3,5]를 방송한다. 이어 각 rank의 값 3,5,7,9를 합 all-reduce한다. 또 각 배열 [1,4],[2,3],[5,1],[0,2]를 원소별로 합한다.

  1. broadcast가 정상 완료된 각 rank의 버퍼는 [3,5]다. 다른 rank의 원래 버퍼 값은 방송의 입력을 바꾸지 않는다.

  2. 스칼라 합은 3+5+7+9=24이므로 네 rank 모두 결합 결과 24를 얻는다. 최댓값 연산이었다면 9다.

  3. 배열 첫 위치는 1+2+5+0=8, 둘째 위치는 4+3+1+2=10이다. 따라서 모두 [8,10]을 얻는다.

  4. 같은 합을 reduce로 수행했다면 결과를 받는 곳은 지정한 root다. 모든 rank의 수신 버퍼에 같은 결과가 있다고 가정하면 안 된다.

broadcast는 [3,5]를 복사하고 all-reduce는 입력을 결합해 24 또는 [8,10]을 모두에게 준다.

종이와 본문으로 직접 해보기

두 프로세스의 자료 수가 2와 6이고 각 지역 평균이 2와 8이다. 지역 평균을 단순 평균한 결과와 전체 평균을 비교하고 어떤 수를 합쳐야 하는지 적어라.

힌트 보기

지역 합은 평균×자료 수다. 두 합과 두 개수를 각각 더한다.

풀이 보기

단순 평균은 (2+8)/2=5다. 지역 합은 4와 48이므로 합 52, 자료 수 8을 얻어 전체 평균 52/8=6.5다. 합과 개수를 결합한 뒤 나눈다. 빈 지역은 개수 0과 합 0으로 다루고 전체 개수도 0이면 나눗셈을 수행하지 않는다.

오해와 반례

all-reduce에 지역 평균을 넣으면 자료 수가 달라도 정확한 전체 평균이다.

2개 평균 2와 6개 평균 8의 반례에서 단순 평균 5와 전체 평균 6.5는 다르다. 무엇을 결합할지 먼저 정의해야 한다. 합만 하는 all-reduce 자체가 자료 수 차이를 추론해 주지는 않는다.

자기점검

broadcast의 root도 호출에 참여하는가?

답과 이유 보기

그렇다.

이 단원의 intra-communicator 방송에서는 root도 그룹 구성원이다.

all-reduce SUM이 자료를 모두 연결해 긴 배열을 만드는가?

답과 이유 보기

아니다.

같은 위치의 입력을 합친다. 연결하여 모으는 연산은 다른 목적이다.

일부 rank가 broadcast→all-reduce, 나머지가 반대로 호출해도 되는가?

답과 이유 보기

안 된다.

같은 communicator에서 집합통신의 호출 순서가 일치해야 한다.

논리적인 이웃을 먼저 그린다

통신 토폴로지는 어느 프로세스가 어느 상대와 통신할지를 그리는 연결 모양이다. 네 프로세스의 논리 고리에서 rank r의 왼쪽은 (r+3) mod 4, 오른쪽은 (r+1) mod 4다. 이 모양이 실제 네 컴퓨터가 같은 고리 케이블로 연결되어 있다는 뜻은 아니다. rank 번호와 물리적으로 가까운 위치도 같다고 단정하지 않는다.

자료를 나눈 격자 계산에서는 이웃 경계값을 교환하고, 전체 합에서는 멀리 떨어진 부분 결과를 결합한다. 문제의 데이터 의존성에 따라 필요한 연결이 달라진다. 고리의 모든 rank가 blocking receive부터 시작하면 앞 소단원의 순환 대기 문제가 그대로 나타날 수 있어 모양뿐 아니라 호출 순서도 그려야 한다.

단계 수와 메시지 수를 구별한다

교육용 모형으로 한 전송 비용을 α+βm이라 하자. α는 시작 비용, m은 바이트 수, β는 바이트당 시간이다. 동시에 전송 가능한 서로 다른 연결이 간섭하지 않고 각 단계가 끝나야 다음 단계가 시작된다고 가정한다. 이는 실제 MPI 구현이나 네트워크 성능을 보장하는 식이 아니다.

root가 나머지 일곱 rank에 하나씩 순차 전송하면 7단계다. 받은 프로세스도 다음 단계에 한 명에게 전달하는 8명 방송은 보유자 수가 1→2→4→8로 늘어 3단계가 된다. 두 경우 모두 전송 메시지는 7개지만 임계 경로의 단계 수는 다르다. 큰 메시지·연결 경쟁·장치 배치에 따라 실제 최선 알고리즘은 달라질 수 있다.

barrier는 도착 조건을 확인한다

이 단원의 intra-communicator barrier는 그룹 전원이 호출에 들어온 뒤에야 어느 호출도 반환할 수 있다. 먼저 온 프로세스는 늦게 온 프로세스를 기다린다. 모든 프로세스가 정확히 같은 시각에 반환한다거나 계산 부하가 균등해진다는 보장은 아니다.

barrier가 다른 비차단 통신 요청의 완료 확인을 대신하지는 않는다. 특정 수신 버퍼를 사용하려면 그 요청의 완료를 확인해야 한다. 또한 모든 호출에 barrier를 붙이면 기다림이 늘어 통신과 계산을 겹칠 기회를 줄일 수 있다. 필요한 의존성 지점에만 동기화하고 실제 성능 주장은 장비에서 별도로 측정한다.

중간 과정을 따라가는 예제

8개 rank의 방송을 순차 root 전송과 단계별 배가 전송으로 비교한다. α=2μs, β=0.01μs/바이트, m=100바이트이고 독립 연결은 같은 단계에 병렬 전송된다고 가정한다.

  1. 한 전송의 모형 비용은 2+0.01×100=3μs다.

  2. root 순차 전송은 7개 메시지를 7단계에 보내므로 7×3=21μs다.

  3. 배가 모형은 첫 단계 0→1, 둘째 0→2·1→3, 셋째 0→4·1→5·2→6·3→7로 모두 받는다.

  4. 단계별 메시지는 1,2,4개여서 총 7개이고, 3단계×3μs=9μs다. 실제 시간은 측정하지 않았으며 이 모형의 결과다.

총 메시지는 모두 7개지만 모형 시간은 21μs와 9μs다. MPI_Bcast가 반드시 이 트리로 동작한다는 뜻은 아니다.

종이와 본문으로 직접 해보기

네 rank가 시각 2,4,7,3ms에 barrier에 들어온다. barrier 내부 비용을 0으로 놓은 이상 모형에서 반환 가능한 가장 이른 시각과 각 대기를 구하라. 고리의 rank 0과 3 이웃도 적어라.

힌트 보기

가장 늦은 도착 7ms를 기준으로 도착 시각을 뺀다. 이웃은 나머지 연산으로 구한다.

풀이 보기

가장 이른 반환 가능 시각은 7ms이며 기다림은 rank 순서대로 5,3,0,4ms다. 실제 반환은 overhead 때문에 더 늦거나 서로 다를 수 있다. rank 0은 왼쪽 3·오른쪽 1, rank 3은 왼쪽 2·오른쪽 0이다.

오해와 반례

barrier를 추가하면 비차단 receive도 끝나고 모든 프로세스가 동시에 출발한다.

barrier는 그룹의 호출 진입 조건을 보장한다. 별도 receive 요청이 완료됐는지는 그 요청으로 확인해야 하며 정확한 동시 반환도 보장하지 않는다. 데이터 의존성과 단계 동기화를 별도 표시하라.

한 단계 더

8명 결과를 트리로 root에 줄이는 3단계와 다시 방송하는 3단계를 이어 all-reduce의 한 교육 모형을 그려라. 전송은 7+7=14개, 단계는 6개다. 실제 라이브러리는 메시지 크기와 장치에 따라 다른 알고리즘을 선택할 수 있으므로 이 모형을 모든 all-reduce의 비용으로 일반화하지 않는다.
