thread·block·warp

백 개의 값을 더하는 일을 GPU의 작업자들에게 어떻게 나눌까?

준비 개념과 학습 목표

준비 개념

  • 배열 인덱스는 0부터 시작한다.

  • 서로 다른 배열 원소를 독립적으로 계산할 수 있다.

학습 목표

  • thread/block/grid를 구별하고 1차원 인덱스를 계산한다.

  • warp 수와 유효 데이터 수를 분리한다.

실행한 thread보다 warp의 전체 lane 자리가 더 많을까요?

새 1차원 SIMT 손모형은 원소 수 N = 83, block 크기 B = 40을 사용한다. block 수는 ceil(83/40) = 3이고 launch한 thread 수는 120이다. 각 block의 첫 warp에는 32개 thread, 둘째 warp에는 8개 thread가 있다. 따라서 warp는 총 여섯 개다. 전체 192개 lane 자리 중 72개에는 애초에 thread가 없고, launch한 thread 중 37개는 i < 83 조건을 만족하지 않아 배열 작업을 하지 않는다. 두 종류를 더한 109개는 이 한 배열 작업에 참여하지 않는 자리이며 오류 수나 실제 실행 시간은 아니다.

block 2는 전역 인덱스 80부터 119까지를 담당한다. 첫 warp의 threadIdx.x = 0,1,2만 배열 원소 80,81,82를 처리한다. 이때 마지막으로 번호를 붙인 둘째 warp에는 데이터 작업 thread가 하나도 없다. 데이터 작업을 가진 마지막 warp와 launch 구성의 마지막 warp는 다를 수 있다. 여러 block의 남는 여덟 thread를 한 warp로 합치면 CUDA의 block별 구성을 바꾸게 된다.

별도 손모형에서는 두 block에 네 thread씩, 총 여덟 thread를 launch하여 N = 13개를 처리한다. 전역 시작 번호 g는 0부터 7이고 각 thread는 g, g+8, g+16 등을 N보다 작은 동안 처리한다. 예를 들어 g = 0은 0과 8을, g = 4는 4와 12를, g = 5는 5만 처리한다. 모든 i는 8로 나눈 나머지와 몫이 유일하므로 담당 thread도 유일하다. 여덟 thread로 13개를 처리할 수 있지만 한 thread가 정확히 한 원소를 처리한다는 첫 모형과는 다른 계약이다.

먼저 확인할 개념
  • block별 warp와 배열 인덱스

    기본의 인덱스 식과 block마다 남는 lane을 별도로 계산한다.

  • 상주 warp와 유효 작업

    warp 수를 lane 작업량 또는 실행 시간으로 확대하지 않는다.

작업의 주소를 만들기

CUDA SIMT 커널은 많은 thread가 같은 프로그램을 자기 인덱스로 실행하는 방식이다. block은 thread 묶음이고 grid는 launch한 block 묶음이다. 1차원에서 i=blockIdx.x×blockDim.x+threadIdx.x로 각 thread의 배열 담당 번호를 만든다.

block 크기 B와 데이터 수 N을 알면 ceil(N/B)개의 block을 사용할 수 있다. 마지막 block의 모든 thread가 데이터 범위 안에 있는 것은 아니므로 i<N일 때만 배열을 접근한다. N=0에서는 이 예제의 일을 생략하며 무조건 0-block launch를 한다고 가정하지 않는다.

warp는 데이터 크기와 다르다

thread는 block 안에서 32개 단위 warp로 묶인다. block마다 ceil(B/32) warp이므로 여러 block의 남는 lane을 하나의 warp로 합치지 않는다. warp의 lane 번호와 전체 grid의 배열 인덱스는 다른 좌표다.

예를 들어 64-thread block은 2 warp이다. 데이터 범위 밖 thread도 launch 구성에는 포함되지만 보호 조건 때문에 실제 배열 작업을 하지 않을 수 있다. launch thread 수가 곧 모든 데이터 접근 수는 아니다.

실행 순서를 기대하지 않기

기본 block들은 임의 순서로 배치될 수 있다. block 0이 반드시 block 1보다 먼저 끝난다고 생각하면 잘못된 통신 계획을 만들 수 있다. 각 block이 독립적으로 진행하도록 설계한다.

한 block 내 협력에는 shared memory와 적절한 동기화를 쓸 수 있다. 같은 warp라는 사실만으로 임의의 메모리 통신을 자동 동기화했다고 생각하지 않는다. cluster나 cooperative 기능은 이 단원의 일반 block 모형 밖에서 조건을 따로 배운다.

여덟 thread가 13개 원소를 한 번씩 처리한다.

한 thread의 담당 원소가 여러 개일 수 있다.

먼저 block 수와 각 block의 warp 수를 센다. 그 뒤 thread가 아예 없는 lane 자리, launch했지만 배열 범위를 벗어난 thread, 실제 원소 작업을 구별한다. grid-stride의 반복 간격은 전체 launch thread 수이며 warp 크기로 임의 교체하지 않는다.

중간 과정을 따라가는 예제

N=100개 원소, 1차원 B=64 thread/block으로 i<N인 thread만 C[i]=A[i]+B배열[i]를 계산한다. grid block 수, launch thread 수, warp 수와 작업하지 않는 thread 수를 구하라. 여기서 B=64는 block 크기 기호다.

  1. ceil(100/64)=2 block이다. launch thread 수는 2×64=128이다.

  2. block0은 i=0..63, block1은 i=64..127이다. 두 block마다 2 warp이므로 총 4 warp이다.

  3. 유효 인덱스는 0..99로 100개다. block1의 i=100..127인 28 thread는 배열 접근을 하지 않는다.

  4. block1의 두 번째 warp은 i=96..127이며 96..99인 4 thread만 이 배열 연산을 수행한다.

2 block, 128 launch thread, 4 warp, 범위 밖 28 thread다. 마지막 warp의 유효 데이터 작업 lane은 4개다.

  • launch 반환과 작업 완료를 구분한다.

범위 밖 thread는 shared 준비 장벽에서도 빠져야 할까요?

새 꼬리 block 모형은 여덟 thread와 입력 x = [0,1,2,3,4]를 사용한다. 유효 출력은 y[i] = x[i] + x[i+1]이고, x[5]는 배열을 읽는 대신 경계 값 0으로 정의한다. shared 배열 s의 여덟 칸을 준비하여 thread t가 t < 5일 때 x[t]를 넣고 그 밖에는 0을 넣는다. 모든 여덟 thread는 같은 block 장벽에 도달한 뒤 t < 5인 thread만 s[t]+s[t+1]을 출력한다. 배열 범위 검사와 장벽 참여 조건은 서로 다르다.

출력은 [1,3,5,7,4]다. 직접 global 방식은 유효 출력 다섯 개에 대해 자기 원소를 총 다섯 번 읽고 다음 유효 원소를 총 네 번 읽어 총 아홉 번의 원소 요청을 만든다. shared 방식의 준비 global 요청은 다섯 번이지만, shared 읽기 요청 열 번과 여덟 칸 쓰기 및 장벽은 남는다. 캐시·전송 묶음·컴파일 최적화는 세지 않았으므로 아홉 대 다섯을 실제 장치 전송 횟수나 실행 시간 비율로 주장하지 않는다.

별도 시간선에서는 한 stream의 입력 복사가 0 ms부터 2 ms까지, 커널이 2 ms부터 5 ms까지, 결과 복사가 5 ms부터 6 ms까지 실행된다. host에 세 비동기 요청의 제출이 모두 반환된 시각은 0.1 ms라고 가정한다. 필요한 완료 확인 후 host 결과를 읽는 가장 이른 시각은 6 ms다. 커널 구간은 3 ms이고 전체 파이프라인 구간은 6 ms다. 서로 다른 stream에 의존 작업을 넣는 것만으로 이 순서가 생기지는 않으며 명시적 완료 의존성이 필요하다.

데이터가 있는 곳과 사용하는 곳

host는 CPU 쪽, device는 GPU 쪽이다. 이 단원은 별도 device 배열을 준비하여 입력을 복사하고 커널을 실행한 뒤 결과를 host로 가져오는 교육 모형을 쓴다. unified memory 등 다른 접근 방식은 별도 조건을 가진다.

global memory는 device의 여러 SM에서 접근하는 데이터 공간이다. register는 thread별 값을 담고 shared memory는 block 내 협력에 쓰는 공간이다. 이름만 보고 shared가 모든 block 사이의 일반 공유 배열이라고 해석하지 않는다.

재사용은 준비와 읽기 순서를 요구한다

종이 예제에서 8개 thread가 자기 원소와 다음 원소를 읽는다고 하자. global에서 직접 두 번씩 읽으면 총 16번의 원소 읽기다. 각 원소를 shared에 한 번씩 옮긴 뒤 재사용하면 global 읽기는 8번이다.

다른 thread가 저장한 값을 읽으므로 쓰기가 끝났음을 보장하는 block 동기화가 필요하다. 모든 참여 thread가 합의된 장벽에 도달하도록 설계한다. 범위 검사로 일부만 장벽에 들어가는 임의 계획은 안전한 해법이 아니다. 이 모형은 속도를 재지 않고 원소 접근 수만 센다.

반환과 완료는 다른 사건

커널 launch가 host로 돌아온 시점과 device 작업 완료는 다르다. 같은 stream의 연산 순서와 필요한 완료 확인을 사용하여 결과를 읽는다. CPU의 launch 직후 시간차만으로 GPU 계산 시간을 확정하지 않는다.

의존성 없는 작업의 겹침은 장비·stream·복사 방식 등 조건에 따른다. 앞 작업의 결과가 필요한 다음 작업까지 무조건 겹칠 수는 없다. 이 단원에서는 복사→커널→결과 복사가 순서대로 완료된 뒤 host가 읽는 시간선만 다룬다.

중간 과정을 따라가는 예제

A/B/C에 각각 100개 원소가 있고 원소당 4바이트다. host의 A/B를 device로 복사하여 C=A+B를 계산하고 C를 host로 가져온다. 패딩/추가 버퍼는 없으며 전송은 중복되지 않는다. 복사 바이트 수를 구하라. 가상 시간선에서 입력 복사 완료 t=2, 커널 완료 t=5, 결과 복사 완료 t=7이다. host가 안전하게 결과를 읽는 시점은?

  1. 배열 하나는 100×4=400바이트다. 두 입력 host→device는 800바이트다.

  2. 출력 device→host는 400바이트이므로 총 전송 내용은 1200바이트다.

  3. kernel launch 반환 시점은 완료 시점 t=5와 별개다. 결과 host 버퍼의 완료는 t=7이다.

  4. 따라서 필요한 완료 확인 뒤 t=7 이후에 host 결과를 읽는다. 시간은 교육 가정이고 측정값이 아니다.

입력 800바이트, 출력 400바이트, 총 1200바이트다. 완료 확인 후 t=7 이후 읽는다.

조건을 바꾸어 비교하기

범위 검사 뒤 남는 협력

여덟 thread의 꼬리 block에서 x=[0,1,2,3,4]와 오른쪽 영 경계의 출력을 구하라.

  1. s[0]부터 s[4]까지는 0,1,2,3,4이고 s[5]부터 s[7]까지는 0으로 준비한다. 모든 thread가 장벽을 통과한다.

  2. 유효 thread 0부터 4까지의 출력은 각각 1,3,5,7,4다. 직접 global 요청 아홉 번 대신 준비 요청 다섯 번을 사용하지만 shared 읽기는 열 번이다.

마지막 출력 4를 얻으려면 준비된 경계 값 0을 읽으며 배열 x[5]는 읽지 않는다.

비교할 점

빠른 제출이 짧은 커널인가?

요청 제출이 0.1 ms에 반환했고 입력/커널/출력 복사는 각각 [0,2], [2,5], [5,6] ms 구간이다. 커널과 host 결과 대기 시간을 구하라.

  1. 커널 구간 길이는 5−2 = 3 ms다. 전체 작업 시작부터 host 결과 완료까지는 6 ms다.

  2. 제출 반환 이후 결과 완료까지는 6−0.1 = 5.9 ms다. 반환 직후 host 결과를 읽어도 된다는 결론은 없다.

커널 구간은 3 ms, 전체 구간은 6 ms, 제출 반환 뒤 남은 대기는 5.9 ms다.

비교할 점

세 수치는 각 시작 사건이 다른 구간이며 실제 측정치가 아니다.

종이와 본문으로 직접 해보기

8-thread 한 block이 x[0..7]에서 x[t]+x[(t+1) mod8]를 계산한다. 각 thread가 두 원소를 global에서 직접 읽는 방식과 각자 한 원소를 shared에 저장 후 모두 완료를 확인하고 읽는 방식의 global 원소 읽기 수를 비교하라. x[i]=i일 때 thread7의 합도 쓰라.

힌트 보기

자체 모형에서 캐시 효과는 제외하고 프로그램이 요청한 원소 읽기만 센다.

풀이 보기

직접 방식 8×2=16번, shared 준비 방식 8×1=8번이다. thread7은 x7+x0=7이다. shared 쓰기 완료를 보장하는 block 동기화를 거친다. shared 읽기까지 사라지는 것은 아니다.

오해와 반례

launch 호출이 반환했으므로 host 결과 배열도 완성됐다.

launch 반환, kernel 완료, device→host 복사 완료를 나눠 확인한다. 예제에서 kernel이 끝난 t=5에도 host 결과 복사가 t=7까지 진행한다.

소단원 9.3

분기 발산·occupancy

GPU에 더 많은 warp가 올라가면 언제나 더 빨라질까?

준비 개념과 학습 목표

준비 개념

  • warp는 32개 thread의 실행 묶음이다.

  • SM의 register/shared 자원은 유한하다.

학습 목표

  • warp 안의 서로 다른 경로와 활성 lane을 구별한다.

  • 가상 자원 한도로 occupancy를 계산하되 성능으로 단정하지 않는다.

자원 수를 반올림하면 같은 occupancy 계산이 유지될까요?

새 가상 SM은 thread 한도 1,024개, warp 한도 32개, register 32,768개, shared 48 KiB, block 한도 여덟 개다. grid에는 계산한 상주 수를 채울 만큼 block이 충분하다. 먼저 자원 할당 반올림이 없고 나열한 것 밖의 추가 자원 제약도 없는 종이 모형을 쓴다. block당 160개 thread, thread당 register 40개, block당 shared 12 KiB이면 thread 한도는 여섯 block, register 한도는 다섯 block, shared 한도는 네 block이다. 네 block이 상주하며 block당 다섯 warp이므로 상주 warp는 20개, occupancy는 20/32 = 62.5%다.

shared를 block당 8 KiB로만 줄이면 이상 모형에서는 다섯 block과 25개 warp가 상주하여 occupancy가 78.125%다. 그러나 별도 가상 할당 규칙으로 block의 register 요청을 1,024개 단위로 올림하면, 요청 6,400개는 7,168개를 예약한다. register 한도는 네 block으로 내려가고 occupancy는 62.5%다. 이 1,024개 단위는 자체 가상 규칙이며 실제 CUDA 아키텍처의 할당 단위라고 주장하지 않는다. 실제 문서에서도 할당 단위와 아키텍처별 한도를 확인해야 한다.

별도 슬롯 모형에서는 한 warp의 여덟 lane이 두 명령 경로, 24개 lane이 여섯 명령 경로를 선택하며 두 경로를 각각 처리한다. 유효 lane명령은 8×2+24×6 = 160이고 가능한 lane명령 자리는 32×(2+6) = 256으로 비율은 5/8이다. 상주 warp 비율과 한 warp의 유효 슬롯 비율은 분모가 다르다. 둘을 곱한 값도 실제 처리량으로 인증되지 않는다. 명령 지연·메모리·컴파일러 및 실행 겹침을 생략한 두 종이 비율이다.

먼저 확인할 개념
  • 최소 자원 한도와 occupancy

    기본의 정수 내림과 warp 분모에 별도 할당 올림 조건을 추가한다.

  • shared 재사용의 다른 비용

    중복 읽기 감소와 shared의 상주 자원 제약을 동시에 확인한다.

warp 안에서 갈라지는 조건

같은 warp의 일부 thread가 한 경로, 나머지가 다른 경로를 선택하면 분기 발산을 생각할 수 있다. 경로를 처리하는 동안 해당하지 않는 lane이 마스킹되는 모형으로 이해한다. 서로 다른 warp가 각각 한 경로만 선택하는 것과 구분한다.

원고의 슬롯 계산은 두 경로를 각각 처리하는 단순 교육 모형이다. 실제 컴파일러의 predication·최적화, 명령 지연과 thread 실행 방식까지 재현하지 않는다. 계산한 비율은 실제 커널 시간이나 GPU 전체 사용률이 아니다.

올라갈 수 있는 warp의 비율

occupancy는 SM에 활성 상태로 상주한 warp 수를 그 SM의 최대 상주 warp 수로 나눈 비율이다. thread 수뿐 아니라 block별 shared, thread별 register, 최대 block 수 등 가장 좁은 한도가 제한한다.

이 단원 가상 계산은 자원을 나누어 정수 내림한 뒤 최소를 취한다. 실제 register 할당의 반올림 단위·구조별 한도는 생략하므로 실제 장비 수치로 사용하지 않는다. 자원이 너무 커 한 block도 들어갈 수 없으면 launch 가능성을 먼저 검토한다.

비율과 성능을 나눠 판단하기

상주 warp가 많으면 다른 warp를 실행하며 지연을 숨길 여지가 생긴다. 그러나 occupancy가 높다는 이유만으로 계산이 빨라진다고 보장할 수 없다. register를 지나치게 줄이면 spill 등 다른 비용도 발생할 수 있다.

분기 발산, global 접근, 명령 의존성, 전송과 launch 비용을 같이 살핀다. 서로 다른 가상 설정의 occupancy 비교는 병목 후보를 찾는 활동이며 실측을 수행한 최적 설정 추천은 아니다.

중간 과정을 따라가는 예제

가상 SM은 최대 2048 thread=64 warp, register 65536개, shared 64KiB, 최대 16 block이다. block당256 thread, thread당32 register, block당 shared16KiB다. 자원 할당 반올림과 기타 제약은 없으며 grid는 충분히 크다. 상주 block 수와 occupancy를 구하라.

  1. thread 한도 floor(2048/256)=8 block이다. block당 register는256×32=8192개로 register 한도 floor(65536/8192)=8 block이다.

  2. shared 한도 floor(64/16)=4 block이며 최대 block 한도는16이다. 최소 min(8,8,4,16)=4 block이다.

  3. 한 block은256/32=8 warp다. 4×8=32 warp가 상주한다.

  4. occupancy=32/64=50%다. 이 모형의 제한은 shared이며 실제 GPU 측정치가 아니다.

4상주 block, 32상주 warp, occupancy50%다.

shared를 줄여도 남는 register 제한

가상 SM에서 B = 160, register 40, shared 8 KiB의 이상 모형과 별도 1,024개 단위 올림 모형을 비교하라.

  1. 이상 register 요청은 6,400개여서 한도는 다섯 block이다. thread와 shared 한도는 각각 여섯 block, 최대 block 한도는 여덟이다. 상주 warp는 25개다.

  2. 별도 올림에서는 register 예약이 7,168개가 된다. 4×7,168 = 28,672개는 들어가지만 5×7,168 = 35,840개는 한도를 넘는다. 네 block과 20개 warp다.

occupancy는 이상 모형에서 78.125%, 올림 모형에서 62.5%다.

비교할 점

요청한 register와 실제 예약한 register를 같다고 두면 제한을 놓친다.

발산한 두 경로의 서로 다른 무게

여덟 lane이 두 명령, 24개 lane이 여섯 명령을 수행하는 슬롯 모형과 16개씩 나눈 모형을 비교하라.

  1. 첫 모형의 유효 슬롯은 160개이고 가능한 슬롯은 256개로 5/8이다.

  2. 16개씩 나누면 유효 슬롯은 16×2+16×6 = 128개이고 가능한 슬롯은 256개로 1/2이다.

같은 두 경로 길이여도 lane 분포에 따라 슬롯 비율은 5/8과 1/2로 다르다.

비교할 점

힌트 1

block마다 warp를 세고 입력 경계 값과 장벽 참여 조건을 따로 적는다. 제출 반환 뒤에도 결과 복사가 남는다.

힌트 2

register 요청을 예약 단위로 먼저 올린 뒤 전체 자원 한도의 최소를 구한다. 두 비율은 각각의 분모를 보고한다.

풀이와 답 확인

  1. ① 세 block과 launch thread 120개 및 여섯 warp다. 범위 밖 thread는 38개다. block 2에서는 인덱스 80과 81의 두 thread만 배열 작업을 하며 둘째 warp의 유효 작업은 0개다.

  2. ② 출력은 [4,8,12,16,9]다. 직접 global 요청은 아홉 번이고 shared 준비 요청은 다섯 번이다. 여덟 thread 모두 경계 값을 포함해 준비하고 같은 장벽에 참여한 뒤 유효 다섯 thread가 출력한다.

  3. ③ 커널 구간은 3 ms이고 전체 파이프라인 구간은 6 ms다. 제출 반환 뒤 host 결과 완료까지는 5.9 ms가 남으며 결과 복사 완료 확인 후 읽는다.

  4. ④ 이상 모형은 다섯 block과 25개 warp로 occupancy 78.125%다. 별도 올림 모형은 register 예약 7,168개로 네 block과 20개 warp이며 occupancy 62.5%다.

  5. ⑤ 유효 슬롯은 160개, 가능한 슬롯은 256개로 비율 5/8이다. 상주 비율과 곱해 실제 처리량을 인증할 수 없으며 정확성·자원·시간 측정은 별도다.

담당 원소, launch 구성, 모든 협력 참여, stream 완료 사건, 자원 예약 및 슬롯 비율의 서로 다른 분모를 유지한다.

해결한 뒤 점검할 것

  • 세 block/120개 thread/여섯 warp와 범위 밖 thread 38개를 각각 이름으로 적는다.

  • 출력 [4,8,12,16,9], global 요청 아홉 번과 다섯 번 및 여덟 thread의 장벽 참여를 적는다.

  • 커널 3 ms/전체 6 ms/반환 뒤 남은 5.9 ms와 host 읽기 조건을 구별한다.

  • register 예약 7,168개 및 두 occupancy 78.125%와 62.5%를 가상 규칙으로 명시한다.

  • 슬롯 비율 5/8을 실제 GPU 처리량·장비 검증으로 주장하지 않는다.
