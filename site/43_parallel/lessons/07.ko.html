락·배리어·원자 연산

같이 계산하는 두 사람이 같은 숫자를 바꾸면 왜 답이 사라질까?

준비 개념과 학습 목표

준비 개념

  • 스레드

  • 변수의 읽기와 쓰기

학습 목표

  • 상호 배제와 단계 동기화를 구별한다.

  • 원자적 증가와 분리된 읽기·쓰기를 비교한다.

두 원자 잔액을 읽으면 전체 합도 항상 같을까요?

새 두 계좌의 초기 잔액은 a=10, b=0이다. 이체 작업은 a에서 4를 빼고 이어 b에 4를 더한다. 두 잔액을 원자 객체로 두어 각 연산 자체가 쪼개지지 않게 해도, 관찰자가 첫 갱신과 둘째 갱신 사이에 a=6과 b=0을 읽으면 합은 6이다. 이 반례는 각 계좌의 data race 없이도 전체 상태 불변식이 깨질 수 있음을 보여 준다. 이체 전의 합과 이체 후의 합은 모두 10이지만 중간 상태는 별개다.

이체 작업이 같은 mutex M을 두 갱신 전체 동안 소유하고 관찰자도 M을 소유한 동안 두 값을 읽는 계약이라면, 관찰자는 이체 전 (10,0) 또는 이체 후 (6,4)를 얻는다. 관찰 뒤에 M을 풀고 또 다른 변경 뒤의 b를 따로 읽는 방법은 이 전체 관찰 계약이 아니다. a와 b를 각각 다른 잠금으로 보호하거나 두 갱신 사이에 M을 풀면 중간 상태를 숨길 수 없다. mutex를 쓴다는 사실보다 보호 범위와 모든 접근자의 준수가 중요하다.

새 barrier 손모형은 참가자 A, B, C 세 명과 매 라운드 정확히 한 번 도착이라는 계약을 사용한다. 첫 도착 시각은 각각 1 ms, 4 ms, 2 ms다. 마지막 도착 뒤 모든 참가자가 즉시 풀린다고 이상화하면 해제 시각은 4 ms이고 대기는 각각 3 ms, 0 ms, 2 ms다. 이어 각 참가자의 다음 라운드 준비 시간은 5 ms, 1 ms, 3 ms다. 다음 도착 시각은 9 ms, 5 ms, 7 ms이고 다음 해제 시각은 9 ms다. POSIX의 실제 반환·스케줄 지연을 측정한 결과가 아니라 도착만으로 정한 모형이다. 필요한 참가자 하나가 오지 않으면 barrier는 도착 수를 채우지 못하며, 이는 data race와 다른 진행 문제다.

먼저 확인할 개념
  • 전체 불변식의 mutex 범위

    기본의 소유권·배타성과 모든 접근자의 공통 잠금 규칙을 두 계좌에 적용한다.

  • 안전성과 진행의 구별

    경합 없는 상태 관찰과 모든 참가자가 실제 도착하는 조건을 따로 확인한다.

락은 한 사람씩 지나가는 문이다

임계 구역은 공유 상태를 일관되게 읽고 바꿔야 하는 범위다. 배타적 mutex를 모든 접근자가 같은 규칙으로 사용하면 소유한 스레드만 그 구역에 들어간다. 읽는 쪽도 보호 대상이라면 같은 락 규칙에 참여해야 한다.

락의 범위는 객체 사이의 불변식을 포함해야 한다. 잔액을 줄이고 다른 계좌를 늘리는 작업에서 각각의 정수만 따로 보호하면 중간 합계가 잘못 보일 수 있다. 락은 공정성이나 완료 시간을 자동으로 보장하지 않는다.

배리어는 단계 사이의 약속이다

배리어는 정해진 참여자들이 한 단계의 일을 마칠 때까지 다음 단계를 기다리게 한다. 행렬의 각 행을 계산한 뒤 전체 결과를 함께 이용하는 상황이 예다. 가장 늦은 도착자가 그 단계의 출발 시각을 결정한다.

배리어를 임계 구역의 배타적 입장권으로 생각하면 안 된다. 통과한 여러 참여자는 다시 동시에 일할 수 있다. 한 참여자가 예외나 잘못된 분기로 빠져 도착하지 않으면 나머지는 계속 기다릴 수 있다.

원자 연산은 나눠 보이지 않는 한 동작이다

원자적 read-modify-write는 읽은 값에 계산을 적용하고 저장하는 과정을 하나의 수정으로 다룬다. 원자 변수에 대한 load 다음 store 두 동작은 각각 원자적이어도 그 사이에 다른 스레드가 들어갈 수 있다.

카운터 증가에는 fetch_add 같은 RMW가 맞지만 여러 변수 사이의 조건까지 한꺼번에 지키는 것은 아니다. 원자 연산이 구현에서 반드시 락 없이 수행된다는 뜻도 아니다. 다른 데이터의 공개 순서는 다음 소단원에서 따로 살핀다.

원자 계좌의 중간 관찰과 mutex로 보호한 전체 관찰은 서로 다른 실행 계약이다. barrier 시각은 공통 원점에서 센 값이며 각 대기 시간을 합쳐 전체 경과 시간이라고 하지 않는다. 실제 API에서는 수신자가 지정되지 않은 한 참가자가 특별 반환값을 받고 나머지는 0을 받지만, 가장 먼저 도착한 참가자가 그 역할이라는 보장은 없다.

중간 과정을 따라가는 예제

초기 카운터 0에 두 작업자가 각각 세 번 증가한다. 모든 작업은 끝나며 정수 오버플로는 없다고 가정한다. 추가로 세 작업자의 배리어 도착 시각은 2, 5, 3 ms다. 배리어 비용은 0으로 둔다.

  1. RMW 증가 여섯 번을 하나의 수정 순서로 세면 0→1→2→3→4→5→6이다.

  2. 분리된 원자 load/store에서는 두 작업자가 같은 0을 읽고 둘 다 1을 저장할 수 있다. 이 두 증가만 보면 결과가 2 대신 1이다. 이는 원자 변수이므로 그 자체로 비원자 데이터 경쟁은 아니다.

  3. 배리어 출발 시각은 max(2,5,3)=5 ms다. 기다림은 각각 3, 0, 2 ms다.

RMW 카운터의 최종 값은 6이다. 배리어는 단계의 도착을 맞추며 카운터 증가의 배타성까지 대신하지 않는다.

읽기에도 필요한 같은 잠금

두 원자 계좌의 갱신 사이를 관찰한 경우와 전체 M 잠금 관찰을 비교하라.

  1. 첫 갱신으로 a는 6이 되고 b는 아직 0이다. 관찰 합 6은 초기 및 완료 합 10과 다르다.

  2. 전체 이체와 관찰이 같은 M을 사용하면 관찰자는 갱신 사이에 들어갈 수 없다. 따라서 (10,0) 또는 (6,4)를 얻는다.

전체 잠금 계약에서는 합 10을 보존하는 관찰만 허용한다.

서로 다른 원자 객체에서 일어난 정상 연산으로도 업무 불변식의 중간 상태가 보일 수 있다.

라운드마다 다시 세는 barrier

첫 라운드 뒤 준비 시간이 A에서 5 ms, B에서 1 ms, C에서 3 ms라면 둘째 대기를 구하라.

  1. 첫 해제 시각 4 ms에 각각 준비 시간을 더하여 둘째 도착 시각 9 ms, 5 ms, 7 ms를 얻는다.

  2. 둘째 해제 시각 9 ms에서 각 도착을 빼면 A의 대기는 0 ms, B의 대기는 4 ms, C의 대기는 2 ms다.

  2. data race가 없다는 증명만으로 barrier 완료를 증명하지 못한다. 정상 완료의 특별 반환값을 특정 참가자 A에게 고정할 수도 없다.

메모리 일관성

한 변수의 변화 순서를 알면 다른 변수까지 같은 순서로 보일까?

준비 개념과 학습 목표

준비 개념

  • 원자 변수

  • 서로 다른 스레드의 사건

학습 목표

  • 객체별 수정 순서와 객체 사이 순서를 구분한다.

  • release/acquire와 seq_cst의 조건을 설명한다.

값이 같으면 같은 공개 사건을 읽은 걸까요?

새 두 원자 객체 data와 flag의 초기 값은 0이다. 생산자는 data에 relaxed store로 7을 저장한 뒤 flag에 release store로 1을 저장한다. 중계자는 그 1 뒤에 flag의 relaxed fetch_add(1)를 수행하여 값 2를 만든다. 소비자의 acquire load가 이 RMW가 쓴 2를 읽으면, RMW가 release sequence에 포함되어 원래 release와 동기화된다. 따라서 data 쓰기가 소비자 읽기보다 happens-before이고, 다른 data 쓰기가 없다는 전제에서 소비자의 relaxed data 읽기는 7을 얻는다. 중계자가 relaxed라는 사실만으로 이 release sequence가 끊기는 것은 아니다.

중계자의 RMW를 별도 relaxed store(2)로 바꾸면 현재 C++ 규정의 release sequence가 그 plain store를 포함하지 않는다. 소비자가 그 2를 읽는다는 사실만으로 생산자의 release와 동기화되지 않는다. data를 원자 객체로 둔 이 반례에서는 0을 읽는 결과를 메모리 계약이 배제하지 못한다. data를 비원자 객체로 바꾼 같은 실행에서는 보호 순서가 없는 충돌 접근이 data race가 되므로 결과값을 0이라고 예측하는 대신 undefined behavior를 판정해야 한다.

공개 세대를 같은 숫자로 반복하는 것도 주의한다. 첫 data 값 7을 flag 값 1로 공개하고 다음 data 값 9를 또 flag 값 1로 공개한다. acquire load의 반환값이 1이라는 정보만으로 어느 release에서 읽었는지 식별할 수 없다. 첫 공개와 동기화한 읽기를 다음 공개의 증거로 쓸 수 없다. 공개 이후 버퍼를 다시 쓰려면 소비 완료가 생산자에게 돌아오는 별도 순서도 필요하다. 세대 번호와 소비 완료 확인은 값의 식별과 재사용 수명의 서로 다른 조건이다.

  • happens-before의 전이성

객체별 순서와 전체 순서를 나눈다

캐시 일관성 또는 coherence는 같은 메모리 위치의 변화가 일관되게 관찰되는 문제를 다룬다. 메모리 일관성 모델은 여러 위치의 연산을 어떤 순서로 관찰할 수 있는지도 정한다. C++ 원자 객체에는 각각의 수정 순서가 있다.

소스 코드의 줄 순서만으로 다른 스레드의 모든 관찰 순서를 결론내릴 수 없다. 언어가 허용하는 실행을 먼저 확인하고 컴파일러와 프로세서가 그 약속을 구현한다고 생각해야 한다.

relaxed와 공개 신호의 차이

relaxed 원자 접근도 한 연산으로 관찰되며 해당 객체의 수정 순서를 지킨다. 그러나 다른 비원자 데이터까지 공개하는 동기화는 만들지 않는다. 횟수만 세는 카운터와 결과가 준비됐다는 신호는 요구가 다르다.

한 생산자가 data=42를 쓴 뒤 flag에 release로 1을 저장하고 소비자의 acquire 읽기가 그 저장의 1을 읽으면 앞선 데이터 쓰기가 뒤의 데이터 읽기보다 happens-before가 된다. 생산자가 공개 후 data를 다시 바꾸지 않고 초기화와 객체 수명이 올바르다는 가정이 필요하다.

순차 일관성의 단일 줄

seq_cst 원자 연산에는 해당 연산들에 대한 하나의 전체 순서가 추가된다. 모두 seq_cst인 작은 예에서는 각 스레드의 순서를 지키며 원자 연산들을 한 줄로 놓고 읽기가 왜 가능한지 확인할 수 있다.

일부 연산만 seq_cst로 바꾸면 프로그램 전체가 자동으로 같은 단순 모델에 들어가지 않는다. 비원자 데이터 경쟁도 seq_cst라는 이름만으로 없어지지 않는다. 가장 강한 순서와 가장 빠른 구현을 동일시하지 말자.

값이 같으면 같은 공개 사건을 읽은 걸까요?
조건 또는 사건관찰 또는 상태검사할 계약

release flag 1 → relaxed RMW flag 2 → acquire가 2 읽기

다른 data 쓰기가 없으면 data 읽기는 7이다.

RMW는 현재 release sequence의 다음 수정이다.

release flag 1 → relaxed plain store 2 → acquire가 2 읽기

생산자와의 동기화를 이 구성만으로 증명하지 못한다.

plain store는 해당 release sequence에 포함되지 않는다.

서로 다른 두 release가 모두 flag 1 저장

반환 숫자 1만으로 새 세대를 식별하지 못한다.

어느 store를 읽었는지와 수명 계약을 함께 확인한다.

표의 data는 처음 두 경우에서 원자 객체다. 비원자 변형의 data race를 원자 읽기의 허용 결과로 섞지 않는다. 공개 숫자의 같음과 읽은 공개 사건의 같음도 구별한다. 새로운 공개값을 확인해도 생산자가 소비 완료 전에 버퍼를 재사용하면 전체 접근 순서는 아직 부족하다. 이 표의 flag 수정 앞뒤는 해당 객체의 modification order를 뜻하며, 스레드 사이의 추가 잠금이나 다른 동기화 간선은 없다고 전제한다. 초기화는 모든 스레드의 사용 전에 완료되어 있다.

중간 과정을 따라가는 예제

원자 x,y는 0으로 초기화되어 있다. A는 x=1을 저장한 뒤 y를 읽어 rA에 넣고, B는 y=1을 저장한 뒤 x를 읽어 rB에 넣는다. 두 스레드가 종료한 후 값을 확인한다.

  1. 모든 접근이 relaxed이면 서로 다른 객체의 교차 순서가 강제되지 않아 rA=0,rB=0이 허용될 수 있다. 특정 컴퓨터에서 반드시 관찰된다는 주장은 아니다.

  2. 모든 접근이 seq_cst라고 바꾼다. rA=0이면 y의 읽기 Ly가 y의 저장 Sy보다 앞서야 한다. rB=0이면 Lx가 Sx보다 앞서야 한다.

  3. 스레드 순서 Sx<Ly와 Sy<Lx를 합치면 Sx<Ly<Sy<Lx<Sx라는 순환이 된다. 한 전체 순서에서는 불가능하다.

두 읽기의 0/0은 이 조건의 relaxed 모델에서 가능하지만 모두 seq_cst인 모델에서는 불가능하다.

조건을 바꾸어 비교하기

relaxed RMW가 잇는 공개

중계자의 fetch_add가 생산자의 flag 1 다음 수정이고 소비자가 그 결과 2를 읽는다. data의 허용 결과를 판정하라.

  1. release sequence의 머리는 생산자의 release store다. 그 뒤 같은 객체의 RMW가 이어져 소비자가 읽은 2까지 포함된다.

  2. 생산자의 data 쓰기는 release보다 앞이고 소비자 data 읽기는 acquire보다 뒤다. 동기화와 전이성으로 data 쓰기가 읽기보다 앞선다.

다른 data 쓰기가 없다면 소비자 data 읽기는 7이다.

비교할 점

RMW 자체의 relaxed와 release sequence를 통한 동기화는 함께 성립할 수 있다.

세 스레드의 SC 순환

초기 x=y=z=0이며 모두 SC다. A는 x←1 뒤 y 읽기, B는 y←1 뒤 z 읽기, C는 z←1 뒤 x 읽기다. 세 읽기가 모두 0인 결과를 검사하라.

  1. 세 읽기가 0이려면 각각 대응하는 1의 store보다 먼저 놓여야 한다. 같은 스레드의 store는 자신의 load보다 먼저다.

  2. SC 순서는 Sx < Ly < Sy < Lz < Sz < Lx < Sx가 되어 엄격한 순환을 만든다. 단일 전체 순서에서 불가능하다.

모두 SC인 이 구성에서는 세 읽기 모두 0을 배제한다.

비교할 점

모두 relaxed로 바꾼 모형에서는 객체별 순서만으로 이 전체 순환을 배제하지 못한다. 실제 CPU에서 관찰했다는 주장은 아니다.

오해와 반례

relaxed라도 비원자 data의 옛값을 읽으면 그냥 오래된 데이터다.

공개 관계 없이 비원자 data 쓰기와 읽기가 충돌하면 C++에서는 데이터 경쟁으로 정의되지 않은 동작이 될 수 있다. 허용된 오래된 원자 값과 비원자 데이터 경쟁을 구분한다.

소단원 7.3

데이터 경쟁과 happens-before

실제 시각에 겹치지 않았다는 관찰만으로 안전을 증명할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 읽기와 쓰기

  • release/acquire

학습 목표

  • 충돌 접근과 데이터 경쟁의 조건을 구분한다.

  • 사건 그래프에서 happens-before 연결을 찾는다.

읽기 완료의 확인을 먼저 보내도 버퍼 재사용이 안전할까요?

새 단일 생산자·단일 소비자 프로토콜은 비원자 버퍼 data와 두 원자 세대 표시 ready, ack를 사용한다. 생산자는 첫 버퍼 쓰기 W1 뒤 ready에 release로 1을 저장한다. 소비자는 그 1을 acquire로 읽고 버퍼 읽기 R1을 마친 뒤 ack에 release로 1을 저장한다. 생산자가 그 ack 1을 acquire로 읽은 뒤 다음 버퍼 쓰기 W2를 시작한다면 W1은 R1보다 앞이고 R1도 W2보다 앞이다. 값의 공개뿐 아니라 다음 덮어쓰기까지 소비 접근 수명이 보호된다. 초기 세대는 0이고 각 단계는 지정한 store를 실제로 읽는다고 전제하며 숫자 순환은 다루지 않는다.

소비자가 ack 공개를 R1보다 먼저 실행하면 생산자는 그 확인을 읽고 W2를 시작할 수 있다. ack 공개에서 W2로 가는 순서는 생기지만 아직 실행되지 않은 R1에서 W2로 가는 순서는 없다. 소비자 읽기와 다음 생산자 쓰기 사이에 happens-before가 없으므로 비원자 버퍼에 data race가 발생한다. ready에서 R1으로 첫 내용이 공개된 사실만으로 재사용까지 보호되지는 않는다. 실제 시계에서 R1이 우연히 먼저 끝난 것을 C++의 보호 순서로 대신할 수도 없다.

순서 보호와 잠금 진행도 따로 본다. 새 세 스레드 A, B, C가 각각 L1, L2, L3를 소유한 채 A는 L2, B는 L3, C는 L1을 기다리는 상태는 순환 대기다. 모든 보호 접근이 잠금 아래 있어 data race가 없어도 이 상태에서 진행이 멈출 수 있다. 모든 스레드가 잠금을 L1 < L2 < L3의 증가 순서로만 얻고 기다릴 때 더 큰 번호만 요구한다는 계약이면 유한 잠금 집합의 이런 순환은 불가능하다. 이 증명은 자원 대기 순환을 배제할 뿐, 스케줄러 공정성이나 고정 완료 시간까지 증명하지 않는다.

  • 잠금의 소유와 진행

    배타적 소유를 지켜도 순환 대기와 기아를 별도 검토한다.

겹치는 주소보다 충돌하는 접근을 본다

같은 메모리 위치를 두 접근이 건드리고 그중 하나가 쓰기이면 충돌할 수 있다. C++에서 잠재적으로 동시에 실행되는 충돌 접근 중 적어도 하나가 비원자이고 어느 방향으로도 happens-before가 없으면 데이터 경쟁이 된다. 두 읽기만으로는 이 쓰기 조건을 만족하지 않는다.

특정 실행에서 우연히 쓰기가 먼저 끝났다는 시계 기록은 언어의 동기화 관계를 대신하지 못한다. 데이터 경쟁이 있으면 결과를 단순히 두 값 중 하나로 예측할 수 없는 정의되지 않은 동작의 영역에 들어간다.

화살표를 이어 안전한 공개를 증명한다

한 스레드 안에서 순서가 정해진 사건과 스레드 사이의 synchronizes-with 연결을 잇는다. 같은 mutex의 unlock에서 뒤의 성공 lock으로 이어지는 연결이 대표적이다. 연결을 합쳐 앞의 쓰기에서 뒤의 읽기까지 경로가 있으면 happens-before를 설명할 수 있다.

release flag를 acquire로 읽는 예에서도 data 쓰기→release 저장→그 값을 읽은 acquire→data 읽기의 경로를 확인한다. 단지 둘 다 flag를 접근했다는 말보다 어떤 읽기가 어떤 저장을 관찰했는지가 더 정확하다.

안전성과 진행은 다른 질문이다

데이터 경쟁이 없다고 모든 작업이 끝나는 것은 아니다. 두 mutex를 반대 순서로 잡으면 서로 기다리는 교착이 생길 수 있다. 배리어 참여자가 빠져도 공유 변수의 경쟁 없이 정지할 수 있다.

volatile은 장치 접근 등에서 별도 의미를 갖지만 일반 C++ 스레드의 공개 동기화를 대신하지 않는다. 안전한 공유를 설계할 때는 보호 규칙, 수명, 종료와 오류 경로를 함께 적는다.

경합 없음과 진행 보장은 다르다.

화살표는 C++ 스레드 내 sequenced-before와 실제 읽은 release/acquire의 동기화에서 유도한다. 실제 시각 비교는 그래프의 간선을 자동으로 추가하지 않는다. 잠금 그래프의 화살표는 소유한 잠금에서 기다리는 잠금으로 향하므로, 메모리 사건 그래프와 같은 기호를 쓰더라도 의미를 분리한다.

중간 과정을 따라가는 예제

초기화된 data에 생산자가 42를 쓰고 release flag=1을 저장한다. 소비자가 acquire로 바로 그 1을 읽은 다음 data를 읽는다. 공개 후 data 변경은 없고 객체 수명은 유지된다.

  1. P1=data 쓰기, P2=release 저장, C1=acquire 읽기, C2=data 읽기로 이름 붙인다.

  2. P1은 P2보다 sequenced-before이고 P2는 C1과 synchronizes-with이며 C1은 C2보다 sequenced-before다.

  3. 이를 이으면 P1 happens-before C2다. 다른 data 쓰기가 없으므로 C2의 값은 42다.

이 공개 경로에서는 data 읽기가 안전하다. 이후 생산자가 data를 다시 쓰면 별도 동기화가 필요하다.

완료 확인의 전이성

정상 프로토콜의 W1, R1, W2 사이에서 필요한 순서를 증명하라.

증가 순서가 배제하는 순환

잠금을 번호 증가 순서로만 얻는 규칙이 자원 대기 순환을 배제하는 이유를 설명하라.

  1. 대기 간선마다 소유 번호보다 요청 번호가 크다. 순환이 있으면 시작 번호에서 여러 번 엄격히 증가한 뒤 같은 번호로 돌아와야 한다.

  2. 유한 잠금 집합에서 이 엄격한 증가 순환은 불가능하다. 다만 한 스레드가 계속 스케줄되지 않는 기아는 이 논증으로 배제하지 못한다.

증가 순서는 지정한 잠금 대기 순환을 배제하지만 완료 시간의 상한은 아니다.

공통 순서와 접근 보호를 함께 정하고 기아 및 시간 상한은 별도 조건으로 남긴다.

계좌·중계·버퍼 수명의 서로 다른 보호 경계

① 원자 계좌의 초기 잔액은 a=12, b=3이다. 이체가 a에서 5를 빼고 이어 b에 5를 더한다. 첫 갱신 직후 관찰 합과 완료 합을 구하고 같은 M 아래 전체 관찰의 허용 상태를 적어라. ② data=0, flag=0에서 data에 원자 relaxed store로 9를 쓰고 flag에 release로 1을 쓴다. 그 다음 수정이 relaxed fetch_add(2)이고 소비자가 acquire로 그 결과 3을 읽는다. 다른 data 쓰기는 없다. RMW를 plain store(3)으로 바꾼 경우와 공개 보장을 비교하라. ③ 정상 비원자 버퍼 프로토콜의 W1, R1, W2 순서를 증명하고 ack를 R1보다 먼저 보내는 변경의 결함을 판정하라. ④ 세 참가자 barrier의 도착 시각은 첫 라운드 1 ms, 4 ms, 2 ms이며 다음 준비 시간은 5 ms, 1 ms, 3 ms다. 각 해제 시각과 둘째 대기를 구하고 참가자 누락과 잠금 순환을 data race와 구별하라. 모든 시각은 도착 후 즉시 해제하는 손모형이며 실제 실행 결과가 아니다.

힌트 1

각 객체의 원자성과 전체 관찰의 잠금 범위를 구별한다. acquire가 읽은 정확한 수정과 release sequence를 검사한다.

힌트 2

ready 방향과 ack 방향의 간선을 각각 잇는다. 도착·대기·진행 계약은 별도로 적는다.

풀이와 답 확인

  1. ① 첫 갱신 뒤 a는 7이고 b는 3이므로 관찰 합은 10이다. 완료 상태는 (7,8)이며 합은 15다. 전체 이체와 관찰이 같은 M을 사용하면 허용 상태는 (12,3) 또는 (7,8)이고 합은 모두 15다.

  2. ② RMW가 만든 3은 생산자 release sequence에 포함된다. 그 3을 읽은 acquire와 다른 쓰기가 없다는 전제에서 data 읽기는 9다. plain store(3)으로 바꾸면 그 store가 release sequence를 잇지 않으므로 같은 공개 보장을 얻지 못한다. 원자 data 읽기에서 0을 배제하지 못하지만 비원자 변형이라면 data race를 판정한다.

  3. ③ 정상 프로토콜은 W1에서 ready를 거쳐 R1으로, R1에서 ack를 거쳐 W2로 happens-before를 잇는다. ack를 R1보다 먼저 보내면 R1과 W2 사이의 순서가 없어 비원자 충돌 접근이 data race다.

  4. ④ 첫 해제 시각은 4 ms다. 둘째 도착 시각은 9 ms, 5 ms, 7 ms이고 해제는 9 ms다. 둘째 대기는 각각 0 ms, 4 ms, 2 ms다. 필요한 참가자 누락과 잠금 순환은 경합 없음만으로 배제하지 못하는 진행 문제다.

계좌의 전체 합, 공개의 reads-from 및 release sequence, 소비 완료와 재사용의 순서, 도착 수와 잠금 대기를 각각 다른 계약으로 보고한다.

해결한 뒤 점검할 것

  • 계좌의 중간 합 10과 완료 합 15를 이름별로 보고하고 전체 잠금에서 합 15를 보존하는 조건을 적는다.

  • RMW 결과 3에서 공개되는 data 값 9와 plain store의 보장 부재를 구별한다.

  • W1, R1, W2의 두 방향 순서를 증명하고 이른 확인의 data race를 판정한다.

  • barrier의 해제 시각 4 ms와 9 ms 및 둘째 대기 0 ms, 4 ms, 2 ms를 계산한다. 경합 부재·진행·실시간 상한과 실제 실행을 구별한다.

보강 자료의 출처와 확인 범위
  • C++ working draft: Order and consistency

    현재 공식 작업 초안의 전체 181행을 실제 읽었다. relaxed의 객체별 불가분성, acquire가 release sequence의 값을 실제 읽는 동기화, SC 전체 순서와 약한 순서 혼합의 제한, RMW가 바로 앞 값을 읽는 규칙을 대조했다. 새 중계 및 세 스레드 순환은 이 규칙에서 손유도한 사례이며 설치 컴파일러의 특정 표준 구현이나 실제 CPU 관찰로 주장하지 않는다.

  • C++ working draft: Data races

    전체 322행을 실제 읽어 객체 수명의 충돌, 객체별 modification order, release sequence의 머리와 후속 RMW 조건, synchronizes-with 및 happens-before의 전이성, 원자 coherence와 비원자 data race의 undefined behavior를 대조했다. 과거 plain store까지 포함하는 규정을 현재 규정에 섞지 않았다. 반복 공개값의 reads-from과 버퍼 수명은 자체 조건으로 명시했다.

  • C++ working draft: Mutex requirements

    실제 0–397행 해당 본문을 읽어 mutex 소유, lock/이전 unlock의 동기화, try_lock의 허위 실패 가능성과 실패 시 동기화 부재, 배타 소유와 소유 중 파괴 금지를 대조했다. 전체 계좌 관찰과 증가 잠금 순서의 논증은 별도 손모형이며 공정성 또는 고정 시간 보장으로 확대하지 않았다.

  • POSIX Issue 8 pthread_barrier_wait

    man7 및 Debian HTML 도구 접근 실패와 구별하여 Open Group 공식 HTML을 urllib로 받아 planning/source-cache/parallel07-barrier.html에 저장하고 NAME부터 CHANGE HISTORY까지 전체 텍스트를 실제 읽었다. 필요한 참가자 도착, 지정되지 않은 한 참가자의 특별 반환값, 나머지 0과 정상 완료 후 재설정, 초기화되지 않은 객체의 undefined behavior 및 신호 규정을 확인했다. 새 두 라운드 표는 모두 도착 후 즉시 해제하는 이상화이며 API 호출이나 스케줄 지연 측정 결과가 아니다.

기본 세 소단원 전체와 같은 단원의 세 고유 선수 설명을 실제 읽었다. 두 원자 계좌의 중간 상태 (6,0)에서 합 6과 완료 상태 (6,4)에서 합 10을 손계산했고 공통 M의 전체 소유 범위와 관찰자를 구별했다. 첫 barrier 해제 시각 4 ms와 대기 3 ms, 0 ms, 2 ms, 둘째 도착 9 ms, 5 ms, 7 ms와 해제 9 ms 및 대기 0 ms, 4 ms, 2 ms를 손계산했다. release 뒤 relaxed RMW의 공개값 7과 plain store의 보장 부재를 현재 release sequence 규정으로 유도했다. 원자 data의 허용 결과와 비원자 변형의 data race를 구별했다. 세 SC 스레드의 세 0 결과를 전체 순서의 엄격한 순환으로 배제하고 읽기 0, 0, 1의 유효 전체 순서를 구성했다. 반복 공개 숫자와 읽은 사건, 소비 완료 확인과 버퍼 재사용 수명을 구별했다. 정상 W1 → R1 → W2의 순서와 이른 확인의 두 후속 사건 사이 순서 부재를 손논증했다. 서로 다른 mutex 및 시계 비교는 동기화 증명이 아니며 증가 잠금 번호는 순환 대기만 배제함을 확인했다. 전이 계좌의 중간 합 10과 완료 합 15, RMW 공개값 9와 plain store 변형, 버퍼 그래프와 barrier 표를 다시 손검산했다. 저장본의 세 소단원 전체, 모든 예제와 12개 과제, 전이, 출처 및 검산 기록을 실제로 다시 읽었다. 같은 단원의 세 고유 기본 설명과 여섯 의미 링크를 대조했고 여섯 HTML 앵커의 존재도 검사했다.
