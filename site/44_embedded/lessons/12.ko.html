소단원 12.1

sleep·clock·전력 측정

처리할 때만 깨어 있는 장치는 언제나 배터리를 더 오래 사용할까?

준비 개념과 학습 목표

준비 개념

  • 전류·전압·전력

  • 주기와 가중 평균

  • clock와 주변장치

학습 목표

  • 활동·기상·sleep 구간의 에너지를 더한다.

  • clock 변경과 상태 보존·응답시간을 구별한다.

  • 가상 계산과 실제 전력 측정 범위를 구별한다.

잠자는 방식도 상태를 선택한다

MCU의 sleep은 필요한 회로만 남기고 다른 회로의 clock이나 전원을 줄이는 방식이다. 어떤 RAM·timer·핀·통신 상태가 남고 어떤 사건으로 깨어나는지 먼저 확인한다. ESP32의 light/deep sleep 설명은 해당 칩의 예이며 모든 MCU가 같은 상태를 보존하는 것은 아니다.

주파수를 낮추면 한 작업의 시간이 늘 수 있고 기상·통신 재연결·센서 안정화 비용도 생긴다. 주파수가 줄었다는 사실만으로 총 에너지가 반드시 줄었다고 결론 내리지 않는다. 응답 마감과 주변장치의 clock 요구도 함께 확인한다.

구간마다 소비한 전하를 더하기

일정 전압 V에서 구간별 전류 I와 시간 Δt를 알면 전하 Q = ΣIΔt, 에너지 E = VQ다. 한 주기 T의 평균 전류는 Q/T다. 같은 길이 구간이 아니면 단순 전류 산술평균 대신 시간 가중 평균을 쓴다.

아래 전류와 전압은 만든 숫자다. 실제로는 센서·regulator·LED·USB/디버거 등을 포함하는 측정 경계를 정하고 전류 변화와 기상 순간을 놓치지 않도록 시간 해상도·범위·계측 부하를 기록해야 한다. 평균만으로 짧은 피크나 reset 원인을 알 수는 없다.

긴 sleep과 짧은 sleep의 차이

sleep 진입·기상에 추가 전하가 들면 그 비용보다 절약되는 전하가 커야 이득이다. 전류 차이를 ΔI, 추가 전하를 Q_overhead라 하면 단순 모형의 이득 조건은 ΔI·sleep 시간 > Q_overhead다. 실제 장치의 상태 전환 시간과 동작 제약은 이 식 밖에도 있다.

배터리 용량/평균 전류는 이상적인 시간 추정이다. 실제 usable 용량·전압·온도·자기 방전·효율·통신 실패 재시도가 달라져 수명이 달라진다. 이 소단원에서는 장치 조작 없이 단위와 구간표를 계산한다.

중간 과정을 따라가는 예제

3 V 일정 전원의 가상 장치는 1초마다 활동 10 mA로 0.10초, 기상 5 mA로 0.02초, sleep 0.1 mA로 0.88초를 쓴다. 한 주기 전하·평균 전류·에너지는?

  1. 전하는 10×0.10 + 5×0.02 + 0.1×0.88 = 1.188 mA·s다. mA·s는 mC다.

  2. 평균 전류는 1.188 mC/(1 s) = 1.188 mA다.

  3. 에너지는 3 V×1.188 mC = 3.564 mJ다.

전하 1.188 mC, 평균 전류 1.188 mA, 한 주기 에너지 3.564 mJ다. sleep 전류 0.1 mA를 주기 평균으로 쓰지 않는다.

종이와 본문으로 직접 해보기

활동을 낮은 clock에서 6 mA·0.20초로 늘리고 기상 5 mA·0.02초, sleep 0.1 mA·0.78초로 바꿨다. 전하와 기존 대비를 구하라. awake idle 1 mA와 sleep 0.1 mA의 차이, 추가 전하 0.09 mC라면 sleep 시간의 단순 손익 경계는?

힌트 보기

구간합 1초를 확인한다. 0.09 mC/(0.9 mA)는 시간이다.

풀이 보기

전하는 1.2 + 0.1 + 0.078 = 1.378 mC다. 기존보다 0.190 mC 늘어 낮은 활동 전류만으로 절약을 판단할 수 없다. sleep이 0.10초일 때 전하가 같고 이 단순 모형에서 0.10초보다 길면 절약한다.

오해와 반례

sleep 전류와 배터리 용량만 나누면 실제 수명과 deadline을 확정할 수 있다.

기상과 활동·주변장치 전류를 포함한 평균이 필요하다. 이상 용량 계산은 실제 수명 인증이 아니며 긴 기상 지연이 deadline을 넘을 수도 있다.

소단원 12.2

bootloader·펌웨어 갱신

새 프로그램을 쓰다가 전원이 끊기면 다음 부팅에서 무엇을 실행할까?

준비 개념과 학습 목표

준비 개념

  • 비휘발 메모리와 reset

  • 검증과 상태 기록

  • 실패 복구

학습 목표

  • bootloader와 application의 역할을 구별한다.

  • 후보 수신·검증·시험·확정·복귀를 추적한다.

  • 전원 중단과 모드별 차이를 설명한다.

처음 실행하는 작은 프로그램

bootloader는 reset 뒤 application보다 먼저 실행해 실행 후보를 검사하고 필요한 초기화와 선택을 수행한다. application은 센서 읽기나 사용자 기능을 담당한다. firmware 갱신은 수신 파일을 받은 것에서 끝나지 않고 다음 부팅의 선택·무결성·정상 동작까지 다룬다.

현재 정상 image A와 새 후보 B를 구분해 보관하면 쓰기 중 실패에 대비하는 설계에 도움이 된다. 실제로는 slot 크기·헤더·metadata·erase 단위·scratch·주소 배치가 맞아야 한다. 두 파일 이름만 만들었다고 전원 중단에 안전한 flash 갱신이 되는 것은 아니다.

다운로드 완료와 사용 확정 사이

자체 상태 모형은 후보 쓰기 → 완전성/정책 검사 → 다음 reset에서 시험 실행 → 정상 검사 → 확정으로 이어진다. 검증 실패면 후보를 실행하지 않는다. 시험 뒤 확정 전 재부팅이면 정상 A로 돌아간다는 정책을 둔다.

MCUboot의 test/revert를 지원하는 모드에서는 새 image가 OK를 표시하지 않으면 다음 reset에서 이전 image를 복귀시키는 절차가 있다. permanent 선택은 그 복귀와 다르다. 지원 mode와 설정·trailer 상태를 확인해야 하며 모든 업데이트 방식에 이 정책이 자동 생기는 것은 아니다.

전원 중단 상태도 설계의 일부다

전원 중단이 후보의 일부 쓰기 뒤·metadata 변경 중·slot swap 중 언제 발생하는지 나눠 생각한다. 다음 부팅이 중간 상태를 인식하고 안전하게 재개·거절·복귀하도록 구현해야 한다. 정상 image와 필요한 기록을 먼저 지우면 돌아갈 길을 잃을 수 있다.

신규 firmware가 자료 형식을 바꿨다면 이전 code로 돌아가도 자료를 읽지 못할 수 있다. code 복귀와 설정·데이터 호환성은 별도 조건이다. 다음 순서표는 그 호환성과 신뢰 A를 가정한 종이 모형이며 실제 전원 차단·쓰기·장치 복구를 수행하지 않는다.

중간 과정을 따라가는 예제

정상 A가 확정돼 있다. 후보 B가 일부만 써진 상태에서 reset하면 거절한다고 가정한다. B가 완전 검증됐으면 한 번 시험하고 정상 검사 OK 때만 확정한다. 세 reset 상황을 판정하라: 일부 B, 검증 B의 첫 시험, 시험 뒤 OK 없는 재부팅.

  1. 일부 B는 완전성 검사를 통과하지 못하므로 A를 선택한다.

  2. 완전 검증 B의 첫 시험에서는 B를 실행하되 아직 확정하지 않는다.

  3. 시험 뒤 OK 없이 재부팅하면 정책에 따라 A로 복귀한다.

순서대로 A·B 시험·A 복귀다. 후보 수신과 시험과 확정은 다르며 이 모형의 전원 중단 정책을 가정했다.

종이와 본문으로 직접 해보기

B의 시험 뒤 정상 조회와 센서 검사는 성공했지만 저장된 설정 해독은 실패했다. OK를 표시해야 하는가? 모든 필수 검사가 성공해 OK를 기록했다면 다음 reset은? A/B 두 image가 각 96 KiB, 공용 metadata 8 KiB면 이 단순 저장 합은?

힌트 보기

필수 검사에는 데이터 호환성도 포함한다. 단순 용량 합과 실제 erase 배치를 구별한다.

풀이 보기

설정 해독 실패면 확정하지 않고 원인을 기록한다. 복귀 조건의 A/데이터 호환성도 확인한다. 모든 필수 검사와 OK 기록이 유효하면 다음 reset도 B를 선택한다. 단순 저장 합은 200 KiB지만 bootloader·scratch·alignment·실제 trailer 여유는 포함하지 않았다.

오해와 반례

서버에서 파일 받기에 성공했으니 장치 업데이트도 완료됐다.

파일 완전성·허용 정책·부팅·필수 기능·확정 상태는 다른 확인이다. 시험만 하고 OK를 남기지 않으면 복귀하는 정책도 있으며 검증 실패 후보를 실행해서는 안 된다.

어떤 키를 믿는지가 출발점이다

보안 부팅은 실행 전에 허용된 신뢰 기준으로 image의 무결성과 서명을 검사하는 경로다. 검증하는 boot code와 신뢰키 설정도 보호돼야 하며 받은 image가 자기 키를 넣었다는 이유로 신뢰해서는 안 된다.

일반적인 공개키 방식에서 장치는 검증용 공개키 또는 그 신뢰 hash를 보관하고 생산 측은 서명용 private key를 보호한다. 공개키는 비밀이 아니지만 허용키를 바꾸는 권한은 중요한 보호 대상이다. 서명 성공은 모든 버그·런타임 침해·비밀 노출이 없다는 뜻이 아니다.

오래된 정상 파일의 재사용을 제한한다

공격자가 과거의 정상 서명 image를 다시 제공할 수 있다. 이를 막는 정책은 보호된 최소 security counter와 image의 인증된 counter를 비교한다. 아래 자체 정책에서는 신뢰키·서명·대상 장치가 맞고 image counter가 최소값 이상이어야 실행 후보가 된다.

counter와 사용자에게 보이는 release version을 꼭 같은 숫자로 둘 필요는 없다. MCUboot 설명에서도 같은 counter의 이전 release를 허용할 수 있고 hardware 보호는 옵션과 플랫폼 구현을 요구한다. 단순 flash 파일을 수정 가능한 위치에 두면 그 값을 신뢰 최소값으로 쓸 수 없다.

기능 복귀와 보안 경계의 충돌

앞 소단원의 test/revert는 나쁜 기능 갱신에서 이전 image로 돌아가려는 정책이다. anti-rollback은 취약한 옛 security 상태로 돌아가지 못하게 하려는 정책이다. 이름에 rollback이 들어가더라도 목적이 같지 않다.

최소 counter를 일찍 올리면 아직 시험 중인 B가 실패했을 때 A의 낮은 counter 때문에 복귀가 막힐 수 있다. 지원 boot mode·counter 갱신 시점·신뢰된 복구 image와 데이터 호환성까지 함께 설계한다. 여기의 상태표는 실제 MCUboot 구현의 모든 모드에 대한 증명이나 key provisioning 지시가 아니다.

중간 과정을 따라가는 예제

가상 신뢰키 K, 대상 D, 최소 counter 4다. X는 K 서명 성공·D·counter 4, Y는 K 성공·D·3, Z는 다른 키 J 성공·D·5, W는 K 성공·다른 대상 E·5다. J≠K, E≠D일 때 후보는?

  1. X는 허용키·서명·대상·counter 조건을 모두 만족한다.

  2. Y는 정상 서명이어도 counter 3 < 4여서 거절한다.

  3. Z는 허용키 불일치, W는 대상 불일치로 거절한다.

X만 실행 정책 후보가 된다. X의 실제 기능 정상 여부는 시험/확정 단계에서 따로 확인한다. 실제 서명 검증은 하지 않았다.

종이와 본문으로 직접 해보기

정상 A의 counter는 4, 시험 B는 5다. B 확정 전 최소값을 5로 올리고 B가 실패했다. 최소 counter 정책에서 A로 바로 복귀할 수 있는가? 최소값이 여전히 4라면 서명·대상도 맞는 A는 후보인가?

힌트 보기

A의 4와 현재 최소값을 비교한다. 보안 counter 이외의 검증도 유지한다.

풀이 보기

최소값 5에서는 A의 4가 부족해 이 정책으로 바로 복귀할 수 없다. 최소값 4이고 다른 조건이 모두 맞으면 A는 후보다. 무조건 counter를 내려 해결한다고 하지 말고 지원 모드·신뢰된 복구 경로·갱신 시점을 함께 검토한다.

오해와 반례

서명 성공이면 신뢰키·대상·옛 보안 버전은 확인하지 않아도 된다.

정상 서명된 Y도 최소 counter 정책을 위반한다. 받은 키가 허용된 키인지와 대상이 맞는지도 확인해야 한다. 서명 자체와 선택 정책·기능 정상은 다른 판단이다.

한 단계 더

허용키 폐기와 새 키 추가의 승인·신뢰 기록을 가상 표에 넣어 보자. 탈취된 서명키와 취약한 옛 image는 다른 실패 원인이다. 실제 device key·fuse·counter를 쓰거나 지우지 않고 조건만 분석한다.
