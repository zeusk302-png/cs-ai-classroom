반환 숫자가 같으면 드라이버를 바꿔도 정책이 같을까요?

새 센서 A는 원시 코드에 0.1 °C를 곱하고 센서 B는 화씨 온도를 반환한다. A의 코드 250과 B의 77 °F는 모두 25 °C다. 어댑터는 값뿐 아니라 성공 여부, 측정 시각, 단위와 오차 범위를 공통 계약으로 바꾼다. 애플리케이션은 성공한 유효 측정에만 정책을 적용한다. 드라이버·HAL·응용의 파일 이름이나 개수보다 이 경계의 의미가 중요하다.

B는 90 ms에 측정하고 100 ms에 반환했다고 하자. 현재 시각 110 ms에서 측정 나이는 20 ms이지만 반환 후 경과는 10 ms다. 유효 나이 상한을 15 ms로 정하면 이 측정은 오래되어 거절한다. 반환 시각으로 측정 시각을 대신하면 같은 값을 잘못 통과시킨다. 값을 새로 포장해도 실제 측정이 새로워지는 것은 아니다.

별도 8비트 밀리초 시계는 256마다 되감긴다. 현재 표시 10과 측정 표시 250의 차이를 modulo 256으로 계산하면 16 ms다. 이 해석은 실제 경과가 0 이상 256 ms 미만임을 다른 계약으로 보장할 때만 가능하다. 표시 두 개만으로는 16 ms와 272 ms를 구별할 수 없다. 또한 공통 값 25 °C의 오차가 ±2 °C이고 정책이 실제 온도 25 °C 이상일 때 켠다는 계약이면 가능한 실제 구간 [23,27] °C가 경계를 가로지른다. 값을 통일해도 이 정책의 켜짐을 확정할 수는 없다.

세 층이 각각 답하는 질문

드라이버는 특정 장치와 대화한다. 레지스터 주소, 통신 순서, 변환 완료 비트처럼 장치 설명서에 따라 달라지는 일이 이 층의 책임이다. 응용은 온도가 높으면 팬을 켠다는 목표를 결정한다. 중간의 HAL(hardware abstraction layer)은 응용이 장치 차이를 덜 알도록 공통 연산을 제공하는 층이다. HAL과 드라이버의 경계와 이름은 프로젝트마다 다르므로 세 층이 반드시 서로 다른 파일 세 개라는 뜻은 아니다.

이 강의의 계약은 read_temperature()가 성공 여부와 섭씨 온도를 함께 돌려준다는 것이다. 어떤 센서는 원시 정수에 배율을 곱해야 하고 어떤 센서는 통신 주소가 다르다. 이 차이를 아래쪽에서 처리하면 응용은 정상 값에 대해 temperature >= 25만 판단할 수 있다. Zephyr의 subsystem API는 장치 구현과 일반 API를 구분하는 구체적인 사례다.

숫자만 같게 만드는 추상화는 부족하다

반환값이 200이라는 사실만으로는 200°C인지 변환 전 코드인지 모른다. 단위, 유효 범위, 측정 시각, 오류 표시까지 약속해야 다른 장치로 바꿔도 정책의 뜻이 유지된다. 센서 읽기에 실패했을 때 0을 반환하면 실제 0°C와 실패를 구별할 수 없으므로 상태와 값을 분리한다.

공통 함수도 모든 장치 기능을 똑같이 제공할 수는 없다. 필요한 기능의 지원 여부를 검사하고 지원하지 않으면 명시적인 오류를 반환한다. 초기화가 끝나기 전 호출하지 않는 조건과 최대 응답 시간도 제어 응용에서 중요하다. 함수 이름을 통일했다고 정확도나 시간 특성이 자동으로 같아지는 것은 아니다.

장치마다 다른 설정과 실행 중 상태

설정에는 버스 주소, 연결 핀, 변환 배율처럼 장치를 구별하는 정보가 들어간다. 실행 중 상태에는 최근 읽은 값, 진행 중인 요청, 오류 횟수가 들어간다. 센서 두 개를 같은 드라이버로 다룰 때도 각 인스턴스의 상태를 분리해야 한 센서의 결과가 다른 센서의 값으로 섞이지 않는다. Zephyr는 읽기 전용 config와 변경 가능한 data, API 연결을 구분한다.

응용을 종이에서 검토할 때 가짜 입력으로 정상·경계·실패를 주면 정책이 하드웨어 없이도 분석된다. 이것은 실제 버스 동작이나 보드 성능 검증을 대신하지 않는다. 계층별 시험의 질문을 구분하면 정책 오류인지 단위 변환 오류인지 장치 통신 오류인지 좁혀 갈 수 있다.

중간 과정을 따라가는 예제

가상 센서 A의 섭씨 값은 raw × 0.1이다. 읽기 성공 때만 25°C 이상이면 팬을 켜며, 실패 때는 오류 상태로 전환한다. raw=200과 270, 읽기 실패를 순서대로 해석하라.

  1. 200 × 0.1 = 20°C이므로 정상 읽기에서는 팬을 켜지 않는다.

  2. 270 × 0.1 = 27°C이므로 팬을 켠다.

  3. 실패는 온도 비교에 넣지 않는다. 오류 상태로 전환하며 팬의 안전 상태는 별도 제품 정책으로 정한다.

정상 20°C는 조건 거짓, 정상 27°C는 참, 실패는 유효 온도가 아니다. 안전 상태를 무조건 팬 끄기로 가정하지 않는다.

서로 다른 원시 값의 같은 온도

  1. A의 공통 온도는 250×0.1=25 °C다.

큐가 값을 복사하면 그 값이 가리키는 데이터도 안전할까요?

크기 두 칸인 큐에 구조체 자체를 복사하는 경우와 구조체의 주소만 복사하는 경우를 구별하자. 하나의 살아 있는 버퍼 B에 값 1을 쓰고 주소 &B를 넣은 뒤, 같은 B를 값 2로 바꾸어 다시 &B를 넣는다. 두 항목을 나중에 읽으면 두 포인터가 모두 같은 B를 가리켜 [2,2]를 본다. 첫 번째 항목에 원래 값 1이 보존된 것은 아니다. 같은 시점에 기록 자체를 복사했다면 [1,2]가 보존된다.

포인터를 큐로 넘기는 계약도 가능하지만 생산자·대기 큐·소비자의 소유권과 반환 시점을 정해야 한다. 함수의 지역 버퍼 주소를 넣고 반환하여 수명이 끝나면 소비자의 역참조는 유효하지 않다. 그때 읽히는 값이 반드시 0이나 마지막 값이라고 가정해서는 안 된다. Zephyr 메시지 큐는 고정 크기 항목을 복사하며 포인터 항목을 쓰면 데이터 자체의 복사와 수명은 별도 책임이다.

별도 두 칸 FIFO는 초기 상태가 비어 있다. A가 0 ms, B가 1 ms, C가 2 ms에 도착하며 소비는 3 ms와 4 ms에 한 항목씩 일어난다. 새 항목 버리기 정책이면 C를 버려 소비 순서는 A,B다. 가장 오래된 항목 버리기라는 자체 정책이면 C 도착 때 A를 버려 소비 순서는 B,C다. Zephyr 예제의 전체 purge를 이 자체 한 항목 삭제와 혼동하지 않는다. 원자적인 각 값의 읽기·쓰기 역시 여러 값의 일관된 스냅샷까지 자동 보장하지 않는다.

다시 들어오는 함수와 겹치는 실행

재진입은 함수가 아직 끝나지 않았는데 다른 호출이 그 함수에 들어와도 각 호출의 올바른 결과를 보존하는 성질이다. 메인 코드가 함수의 공용 임시 버퍼를 쓰는 중에 ISR이 같은 함수를 호출해 버퍼를 덮으면 먼저 시작한 호출의 중간 상태가 사라진다. 호출마다 별도 저장 공간을 쓰면 이 특정 충돌은 없앨 수 있다.

지역 변수를 쓴다는 사실만으로 함수 전체가 안전해지는 것은 아니다. 함수가 접근하는 전역 상태, 장치, 동적 메모리 관리와 다른 함수의 내부 상태도 확인해야 한다. 멀티스레드에서의 동시 호출 안전성과 ISR에서 호출할 수 있는지는 다른 질문이다. 기다릴 수 있는 스레드용 API라도 ISR에서는 사용할 수 없는 경우가 있다.

한 줄의 증가도 여러 단계일 수 있다

카운터 증가는 기존 값 읽기, 더하기, 새 값 쓰기로 나뉠 수 있다. 두 실행 흐름이 모두 0을 읽은 뒤 각각 1을 쓰면 총 두 번 증가를 요청했어도 최종 값은 1이다. 공유 상태를 보호하는 범위는 하나의 저장 명령만이 아니라 읽기에서 쓰기까지의 전체 갱신이다.

대응책에는 해당 문맥에서 지원되는 원자 연산, 짧은 임계구역, 하나의 소유자에게 메시지를 보내는 설계가 있다. 단일 코어의 인터럽트 차단은 ISR과의 충돌을 막는 범위에서 쓸 수 있지만 다른 코어의 접근까지 막는 일반 자물쇠는 아니다. IRQ lock을 유지한 채 수면하면 안 되며 오래 잠그면 긴급 이벤트의 응답 시간도 나빠진다.

큐는 자료 전달과 넘침 정책을 함께 설계한다

메시지 큐는 생산자가 넣고 소비자가 꺼내는 고정 용량의 통로다. Zephyr 메시지 큐는 고정 크기 항목을 복사하므로 작은 기록을 보낼 때 호출자의 원래 버퍼 수명과 큐 안 기록의 수명을 분리할 수 있다. 포인터만 복사한다면 포인터가 가리키는 데이터의 수명과 소유권은 따로 약속해야 한다.

가득 찬 큐에서는 새 항목 버리기, 오래된 항목 버리기, 생산자 대기 같은 정책 중 요구에 맞게 선택한다. ISR은 큐 공간을 기다리며 잠들 수 없으므로 실패 처리나 손실 기록이 필요하다. 순서대로 저장된다는 사실이 무손실을 보장하지 않는다. 평균 유입량이 소비량보다 크면 유한 큐는 결국 가득 찬다.

높은 우선순위만 지정하면 응답 마감도 보장될까요?

단일 CPU의 자체 일정에서 로그 작업은 협력 실행이고 0 ms에 시작하여 CPU 작업량 6 ms를 수행한 뒤 기다림 상태로 간다. 센서 사건은 1 ms에 발생하고 ISR은 1 ms부터 1.1 ms까지 실행하여 높은 우선순위 센서 작업을 준비 상태로 만든다. ISR 비용도 실제 경과 시간에 포함한다. 로그는 ISR 뒤 다시 실행하며 남은 5 ms를 수행하여 6.1 ms에 기다림 상태가 된다. 센서 작업량은 2 ms이므로 완료는 8.1 ms, 사건부터의 응답은 7.1 ms다.

같은 로그를 선점 가능한 낮은 우선순위 작업으로 바꾸고 전환 비용은 0으로 정하면, ISR 뒤 1.1 ms에 센서가 실행되어 3.1 ms에 완료한다. 응답은 2.1 ms다. 사건 시각부터 3 ms의 상대 마감, 즉 절대 시각 4 ms를 적용하면 협력 모형은 4.1 ms 늦고 선점 모형은 통과한다. 이 두 결과는 명시한 일정 모형이며 실제 RTOS·CPU 지연을 측정한 것이 아니다. Zephyr의 협력 스레드는 준비되지 않은 상태로 바뀌기 전까지 높은 우선순위 작업도 지연시킬 수 있고 ISR은 두 종류 스레드보다 먼저 실행한다.

선점 모형에서도 다른 요인이 남는다. 별도 일정은 센서가 기다리는 장치 응답이 1.1 ms부터 5.1 ms까지이며, 그동안 센서는 준비 상태가 아니다. 장치 응답 뒤 2 ms 처리하면 7.1 ms에 완료하여 응답 6.1 ms로 마감에 실패한다. 우선순위는 준비 상태 작업 사이의 선택을 정할 뿐 장치 대기를 없애지 않는다. RAM도 앱 30 KiB, 커널 5 KiB, ISR 스택 3 KiB, 데이터 풀 8 KiB, 작업 스택 세 개 각각 2 KiB라는 별도 장부로 센다. 합은 52 KiB다. 64 KiB 한도에서 64항목×32바이트 큐의 본문만 2 KiB 더하면 합 54 KiB·남은 10 KiB다. 큐 관리 정보·정렬과 다른 비용은 이 장부에 없으므로 실물의 잔여량 주장으로 확대하지 않는다.

누가 다음 일을 실행하는가

bare-metal은 이 문맥에서 범용 운영체제나 RTOS 스케줄러 없이 초기화 뒤 주 반복문과 ISR로 일을 조직하는 방식이다. 간단한 superloop는 순서대로 일을 검사하므로 이해하기 쉽지만 한 작업이 오래 실행되면 다음 검사까지 기다린다. 인터럽트가 있는 bare-metal도 겹치는 실행과 공유 상태 문제를 가진다.

RTOS는 스레드의 준비/대기 상태와 우선순위에 따라 다음 실행 대상을 선택한다. 선점형 스레드는 높은 우선순위의 준비된 일을 먼저 처리할 수 있다. 다만 Zephyr에는 cooperative thread도 있어 자발적으로 양보할 때까지 다른 스레드를 지연시킬 수 있다. RTOS라는 이름만으로 모든 작업이 선점 가능하다고 가정하지 않는다.

마감 시간은 설계와 측정으로 확인한다

작업의 응답 시간은 실행 시간만이 아니라 시작까지의 기다림, 인터럽트 처리, 스케줄링, 자원 경쟁까지 포함한다. 높은 우선순위를 주어도 긴 인터럽트 차단이나 다른 ISR, 잠긴 자원 때문에 늦어질 수 있다. 정해진 마감 시간을 보장하려면 최악 실행 시간과 간섭의 상한을 따져야 한다.

종이 시간표는 명시한 가정에서의 결과를 보여 준다. 실제 보드에서는 캐시, 통신과 장치 대기, 다른 작업, 스택 사용량을 확인해야 한다. 단순한 구조로도 충분히 짧은 반복문이라면 bare-metal이 적합할 수 있고 여러 독립 작업과 대기 조건을 관리해야 한다면 RTOS가 구조를 명확하게 할 수 있다.

스택과 상태를 위한 예산도 선택 기준이다

여러 스레드는 각자 실행을 이어 갈 상태와 스택이 필요하다. 작은 RAM에서는 커널 자료구조, 큐, 응용 버퍼, ISR 스택을 포함해 합산한다. 스레드 수만 보고 남는 RAM을 계산하면 정적 버퍼와 인터럽트 공간을 빠뜨릴 수 있다.

스레드가 많아지면 상태 공유와 동기화가 늘고 디버깅할 실행 순서도 늘어난다. 반대로 모든 작업을 하나의 반복문에 몰아넣으면 긴 처리를 잘게 나누는 상태기계를 직접 관리해야 할 수 있다. 목적은 RTOS 유무를 등급으로 판단하는 것이 아니라 요구된 응답 시간과 기능을 설명 가능한 구조로 만족시키는 것이다.

중간 과정을 따라가는 예제

가상의 로그 작업은 t=0부터 8ms 동안 중단 없이 실행한다. 센서 이벤트는 t=1ms에 생기며 센서 처리는 2ms, 마감은 발생 후 5ms인 t=6ms이다. 주 반복문은 로그 후 센서를 처리한다. 비교 RTOS 모델은 이벤트부터 센서 시작까지 ISR·스케줄링 비용 총 0.2ms, 센서 선점 우선순위가 높고 다른 간섭은 없다.

  1. 주 반복문은 센서를 t=8에 시작해 t=10에 끝낸다. 이벤트부터 9ms이므로 t=6 마감을 4ms 넘긴다.

  2. RTOS 모델은 t=1.2에 센서를 시작해 t=3.2에 끝낸다. 응답 시간 2.2ms로 5ms 이내다.

  3. 이는 주어진 선점·비용·무간섭 가정의 비교다. 모든 RTOS 시스템이 2.2ms에 끝난다는 보장은 아니다.

  4. 로그를 최대 1ms 조각으로 나누고 매 조각 뒤 이벤트를 검사하는 다른 반복문이라면 시작 대기가 최대 1ms, 센서 처리 2ms로 응답 상한 3ms가 될 수 있다. 이 모델은 다른 검사 비용을 0으로 가정한다.

연습 1 · 값과 상태 예측

협력 로그의 CPU 작업량만 6 ms에서 2 ms로 바꾼다. ISR과 센서 조건은 같다. 센서 완료·응답·절대 마감 4 ms를 판정하라.

힌트 1

로그의 벽시계 완료에 ISR 0.1 ms를 더한다.

힌트 2

센서가 실행할 수 있는 첫 시각에 2 ms를 더한다.

풀이와 답 확인

  1. 로그는 2.1 ms에 기다림 상태가 되고 센서는 4.1 ms에 완료한다.

  2. 사건부터 응답은 3.1 ms로 상대 마감 3 ms를 초과한다. 완료 시각 4.1 ms는 절대 마감 4 ms보다 0.1 ms 늦다.

센서 완료는 4.1 ms, 응답은 3.1 ms이며 마감에 실패한다.

흔한 오답에서 다시 생각하기

로그 작업량 2 ms와 센서 작업량 2 ms의 합 4 ms가 마감과 같으므로 통과한다.

ISR의 실제 경과 비용과 사건의 시작 시각을 모두 포함한다.

잠드는 센서를 높은 우선순위로 설정하면 1.1 ms부터 5.1 ms의 장치 대기도 다른 작업을 선점하여 처리할 수 있다고 했다. 고쳐라.

힌트 1

준비 상태와 기다림 상태는 다르다.

힌트 2

장치 응답이 언제 준비 상태를 만드는지 확인한다.

풀이와 답 확인

  1. 장치 대기 동안 센서는 준비 상태가 아니며 CPU 선택 대상이 아니다.

  2. 장치 응답 5.1 ms 이후에야 실행할 수 있다. 높은 우선순위의 CPU 선택과 외부 응답 시간을 분리한다.

우선순위 변경만으로 지정 장치 대기를 제거할 수 없다.

힌트 1

힌트 2

풀이와 답 확인

  1. 작업 스택 합은 6 KiB이며 큐 본문은 2,048바이트, 즉 2 KiB다.

  2. 총합은 46+6+2=54 KiB로 명시 항목만 센 잔여는 10 KiB다.

총합은 54 KiB, 장부상 잔여는 10 KiB다. 미계상 관리 정보는 추가 확인해야 한다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

다른 비용을 0으로 둔 6 ms 협력 로그 대신, 각 협력 조각의 CPU 작업량을 최대 b ms로 제한하고 조각 뒤 높은 우선순위 센서가 실행할 수 있도록 양보한다. 사건이 조각 시작 직후에 오고 ISR 비용 0.1 ms·센서 작업량 2 ms다. 응답 상한 3 ms를 위한 b의 충분조건을 구하라.

힌트 1

최악의 남은 조각 시간은 b ms 이하로 둔다.

힌트 2

ISR와 센서 실행 시간을 추가한다.

풀이와 답 확인

  1. 명시한 양보·우선순위 조건에서 응답은 b+0.1+2 ms 이하로 보수적으로 묶인다.

  2. 이 상계가 3 ms 이하이려면 b≤0.9 ms가 충분하다. 실제 전환·추가 ISR·차단은 모형 밖이므로 더해야 한다.

0<b≤0.9 ms이면 지정 상계가 3 ms 이하이다. 이 조건은 해당 모형의 충분조건이다.

측정 계약·큐 수명·응답 장부 연결

서로 독립인 세 종이 모형을 분석하라. ① A의 코드 250에는 0.1 °C/code를 곱하고 B는 77 °F를 반환한다. B는 90 ms에 측정하고 100 ms에 반환하며 현재는 110 ms다. 두 공통 온도와 측정 나이 상한 15 ms에서 B의 판정을 구하라. ② 하나의 살아 있는 B에 값 1을 쓰고 &B를 큐에 넣은 뒤 값 2로 바꾸어 같은 주소를 다시 넣는다. 소비는 두 넣기 뒤다. 내용 자체를 넣는 순간 복사한 별도 경우와 비교하라. 두 칸 FIFO에 A,B,C가 0,1,2 ms에 도착하고 소비가 3,4 ms일 때 두 포화 정책의 소비 순서도 구하라. ③ 로그는 0 ms부터 CPU 작업량 6 ms이며 센서 사건은 1 ms, ISR은 1–1.1 ms, 센서 작업량은 2 ms다. 전환 비용은 0이다. 협력 로그는 전체 작업 뒤 기다림 상태가 되고 선점 로그는 센서보다 낮은 우선순위다. 두 완료 시각과 상대 마감 3 ms의 판정을 구하라. 새 MCU/API/RTOS/큐/학생 실행은 하지 않는다.

힌트 1

화씨를 섭씨로 바꾸고 반환 시각 대신 측정 시각으로 나이를 구한다. 포인터 복사와 내용 복사를 따로 추적한다.

힌트 2

협력 로그의 완료에 ISR 0.1 ms를 포함한다. 사건 1 ms에 상대 마감 3 ms를 더하면 절대 마감 4 ms다.

풀이와 답 확인

  1. A와 B의 공통 온도는 각각 25 °C다. B의 측정 나이는 20 ms로 15 ms 상한을 초과하여 거절한다.

  2. 같은 버퍼의 주소 두 개는 나중에 각각 2를 읽어 [2,2]가 된다. 넣는 순간 내용 복사는 [1,2]를 보존한다. 새 항목 버리기는 A,B를 소비하고 가장 오래된 항목 버리기는 B,C를 소비한다.

  3. 협력 로그는 ISR 비용을 포함하여 6.1 ms에 기다림 상태로 바뀌고 센서는 8.1 ms에 완료한다. 응답은 7.1 ms로 마감에 실패한다.

  4. 선점 로그에서는 센서가 1.1–3.1 ms에 실행한다. 응답은 2.1 ms로 마감에 통과한다. 실제 장치 대기·추가 ISR·전환 비용은 이 모형 밖이다.

두 공통 온도는 25 °C이며 B는 나이 20 ms로 거절한다. 주소 큐 관측은 [2,2], 내용 복사는 [1,2]다. 새 항목 버리기의 소비 순서는 A,B이고 가장 오래된 항목 버리기는 B,C다. 센서 완료는 협력 모형 8.1 ms·선점 모형 3.1 ms이며 상대 마감 3 ms에서 각각 실패·통과한다.

    실제 전체 0–444행을 읽었다. 공통 API, 장치별 config/data/API, 여러 인스턴스와 초기화 단계·오류 반환 계약을 대조했다. 센서 단위·측정 시각·오차 범위는 자체 어댑터 계약이며 Zephyr가 자동 변환한다고 주장하지 않는다.

  • Zephyr Message Queues

    실제 전체 0–157행을 읽어 고정 크기 항목 복사, ISR의 비대기 요구, 복사 비용과 큰 데이터의 포인터 사용을 확인했다. 문서 예제의 purge는 전체 큐 비우기이며 자체 두 칸 FIFO의 가장 오래된 항목 한 개 삭제와 구별했다. 원본 수명·변경 시각은 별도 자체 모형이다.

  • Zephyr Interrupts

    실제 0–185행을 읽었다. ISR의 비동기 선점·별도 스택·API 제한, IRQ 잠금 중 sleep 금지와 짧은 ISR 뒤 스레드로 일 이관하는 조건을 대조했다. 자체 ISR 0.1 ms는 실제 장치 측정값이 아니며 zero-latency 예외를 일반 ISR에 확대하지 않았다.

  • Zephyr Scheduling

    실제 전체 0–237행을 읽었다. 준비 상태 우선순위, ISR 우선, 협력·선점 실행, yield/sleep과 스케줄러 잠금, 시간 조각의 CPU 시간 공평성 한계 및 idle 검사 뒤 잠듦의 경쟁 조건을 대조했다. 새 일정은 단일 CPU·지정 작업량·전환 비용 0의 종이 모형이다. 문서의 실제 실행이나 RTOS 응답 보장을 시험한 것이 아니다.
