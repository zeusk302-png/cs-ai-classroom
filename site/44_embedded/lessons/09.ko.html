소단원 9.1

DMA 요청·버퍼 소유권

CPU가 읽는 버퍼에 주변장치가 새 데이터를 쓰면 누가 그 순간의 내용을 보장할까?

준비 개념과 학습 목표

준비 개념

  • 버퍼는 데이터를 담는 메모리 영역이다.
  • 비동기 작업은 요청한 뒤 나중에 끝날 수 있다.

학습 목표

  • DMA 설정·시작·완료 및 버퍼 인계 단계를 설명한다.
  • 주소·방향·캐시 조건과 버퍼 사용 권한을 구별한다.

CPU 대신 데이터 옮기기

DMA controller는 주변장치와 메모리 등 사이의 전송을 맡아 CPU의 반복 복사 부담을 덜 수 있다. CPU는 주소·길이·방향·채널 등을 준비하고 시작과 완료를 관리한다. DMA라고 설정이나 처리 작업이 전부 사라지는 것은 아니다.

주소가 장치에 접근 가능하고 정렬·길이 조건에 맞아야 한다. CPU 가상 주소가 장치의 DMA 주소와 항상 같지는 않다. 이 단원의 수치 예제는 유효한 버퍼가 이미 준비되었다고 가정하고 특정 보드 API 호출을 제공하지 않는다.

상태별 사용 권한

교육 수신 모형에서 FREE→DMA_WRITING→READY→CPU_READING→FREE를 쓴다. DMA_WRITING 중에는 CPU가 그 버퍼를 읽거나 고치지 않는다. 완료 확인과 필요한 가시성 조치 후 READY를 CPU에 넘긴다.

CPU 처리가 끝나기 전에 다음 DMA 수신 대상으로 재사용하면 이전 데이터를 덮어쓸 수 있다. 소유권은 누가 메모리를 할당했는지뿐 아니라 지금 누가 유효 내용을 접근·변경할 수 있는지에 관한 약속이다.

완료와 데이터 가시성

DMA 완료 통지는 전송 진행 상태에 관한 정보다. 비일관 캐시를 가진 시스템은 플랫폼의 캐시 동기화 등 추가 조치를 요구할 수 있다. coherent 메모리에서도 순서 장벽이 필요한 경우가 있다. volatile 하나로 모든 장치 가시성 문제를 해결하지 않는다.

Linux의 DMA mapping/sync와 Zephyr의 DMA 요구는 각각 자기 환경 규칙이다. 서로의 함수를 섞는 대신 문서에서 방향·완료·재인계 조건을 확인한다. 이 원고는 전용 소유권 규칙을 사용하는 종이 모형이다.

중간 과정을 따라가는 예제

유효 수신 버퍼는 128개의 16비트 샘플을 담고 샘플당2바이트다. DMA가 t=0ms에 시작하여 t=4ms 완료 확인·필요한 캐시 조치 후 CPU가 t=4..7ms에 처리한다. 구간은 시작 포함·끝 제외이고 t=7에 해제한다. 바이트 수와 t=2/5/7의 권한을 추적하라.

  1. 길이는128×2=256바이트다. 샘플128과 바이트256을 구분한다.
  2. t=2는[0,4) DMA_WRITING이므로 CPU 처리 금지다.
  3. t=5는[4,7) CPU_READING이므로 CPU가 읽고 DMA는 재사용하지 않는다.
  4. t=7에는 처리 종료가 먼저 반영되어 FREE다. 다음 DMA에 인계할 수 있지만 FREE만으로 전송이 자동 시작되지는 않는다.

256바이트, t2 DMA 소유/t5 CPU 처리/t7 해제다. t4 완료와 가시성 조치를 확인한 뒤 읽는다.

종이와 본문으로 직접 해보기

CPU가 t=7까지 처리하는데 t=6에 같은 버퍼로 다음 DMA를 시작하려 한다. 무엇을 바꾸어야 하는가?

힌트 보기

아직 사용 중인 버퍼를 덮는 대신 자유 버퍼 또는 지연을 생각한다.

풀이 보기

t6에는 CPU 처리가 진행 중이므로 같은 버퍼 재사용을 금지한다. 다른 FREE 버퍼를 인계하거나 입력을 안전하게 늦추는 정책을 쓴다. 늦출 수 없는 입력이면 손실/오버런 정책을 명시한다.

오해와 반례

전송 완료 인터럽트가 왔으니 모든 시스템에서 캐시 조치 없이 읽어도 된다.

플랫폼이 DMA cache coherency를 보장하는지 확인해야 한다. 비일관 시스템에서는 필요한 동기화가 빠지면 오래된 데이터를 볼 수 있다. 완료와 가시성은 별도 조건이다.

자기점검

샘플512개, 샘플2바이트 수신 길이는?

답과 이유 보기

1024바이트다.

512×2다. API 길이 단위는 문서로 별도 확인한다.

CPU 처리가 끝나지 않은 버퍼의 DMA 재사용은?

답과 이유 보기

본문 모형에서 금지다.

읽는 중 덮어써 내용의 일관성을 잃을 수 있다.

CPU 가상 주소와 DMA 주소는 항상 같은가?

답과 이유 보기

아니다.

장치 주소 변환과 접근 가능 범위가 다를 수 있다.

한 단계 더

송신 모형을 CPU_WRITING→DMA_READING→FREE로 그려라. DMA_READING 동안 CPU가 내용을 수정하지 않는 이유와 다음 데이터 작성은 완료·해제 뒤라는 조건을 적는다.

소단원 9.2

double buffering

한 버퍼를 처리하는 동안 다른 버퍼로 다음 데이터를 받을 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 사용 중인 버퍼는 재사용하지 않는다.
  • 입력 도착률과 처리 시간은 유한하다.

학습 목표

  • 두 버퍼의 교대 시간선을 만든다.
  • 버퍼 두 개가 무한 지연을 흡수하지 못함을 설명한다.

두 공간을 교대로 인계하기

double buffering은 두 버퍼를 번갈아 사용하여 수신과 처리가 서로 다른 공간에서 진행하도록 하는 방식이다. 한 버퍼를 CPU가 처리하는 동안 다른 버퍼를 DMA가 채울 수 있다. 두 역할이 같은 버퍼에 동시에 붙지 않도록 상태를 추적한다.

이 원고의 자동 교대 시간선은 장치가 완료 경계에서 다음 유효 버퍼로 바꿀 수 있고 인계 비용은0이라는 가정이다. 실제 장비는 descriptor·callback·cache 비용 및 전환 지원을 확인해야 한다.

소비 시간이 교대 간격보다 길면

블록 도착 간격이4ms면 같은 버퍼는 두 블록 뒤 다시 필요하다. A가 t4에 완료되어 t8에 다음 수신 대상으로 필요할 때 CPU 처리를 t8 전에 끝내야 한다. 두 버퍼가 있어도 소비자가 지속적으로 느리면 재사용 시점과 충돌한다.

처리 시간3ms인 일정은 여유가 있지만6ms인 일정은 A가 아직 처리 중인 t8에 A를 요구한다. 이때 몰래 덮는 것이 아니라 입력 중지·손실 기록·버퍼 확장 등 시스템 정책이 필요하다. 버퍼를 늘려도 장기 평균 처리율 부족을 없애지는 못한다.

준비 이벤트와 해제 이벤트 구별

Zephyr async UART는 다음 버퍼 요청과 데이터 준비, 버퍼 해제를 별도로 알린다. 같은 버퍼에서 데이터 준비가 여러 번 발생할 수 있다. 준비된 구간을 처리하는 정보와 버퍼 전체를 재제공할 권한을 구별한다.

해당 API에서는 driver가 사용 중인 버퍼를 다시 제공하면 안 된다. BUF_RELEASED 뒤에도 응용 처리가 남았다면 응용의 소유권 조건까지 확인해야 한다. 이 원고 시간선은 전체 블록 완료 및 driver 해제를 확인한 뒤 CPU 처리하는 단순 모형이며 부분 처리 API를 재현하지 않는다.

중간 과정을 따라가는 예제

각 버퍼256바이트인 A/B 두 개다. DMA는 한 블록당4ms, CPU는 완성 블록당3ms 처리한다. CPU/DMA는 서로 다른 버퍼에서 겹칠 수 있으며 인계 비용0, t0 시작, 완료와 해제가 경계에서 먼저 반영된다. 첫 세 블록의 수신·처리 시간과 총 버퍼 용량을 적어라.

  1. 블록1은 A에[0,4) 수신, A의 CPU 처리는[4,7)이다.
  2. 블록2는 B에[4,8) 수신, B 처리는[8,11)이다.
  3. A는 t7에 자유 상태이므로 블록3을 A에[8,12) 수신하고 CPU는[12,15) 처리한다.
  4. 총 버퍼 용량256×2=512바이트다. 수신과 처리는 다른 버퍼라 겹치며 첫3블록 처리 종료는 t15다.

A0–4/4–7, B4–8/8–11, A8–12/12–15다. 용량512바이트이고 첫3블록 완료 처리 종료15ms다.

종이와 본문으로 직접 해보기

같은 두 버퍼에서 CPU 처리가6ms라면 첫 충돌 시점과 버퍼를 구하라. CPU는 블록1부터 순서대로 처리한다.

힌트 보기

A의 첫 처리 [4,10)과 A의 다음 수신 시작8을 비교한다.

풀이 보기

t8에 A를 블록3용으로 요구하지만 CPU가 A를 t10까지 읽고 있어 충돌한다. t8에 A를 덮지 않아야 한다. 입력을 멈출 수 없다면 손실을 기록하는 등 정책이 필요하다.

오해와 반례

double buffering이면 CPU가 아무리 느려도 데이터 손실이 없다.

유한 버퍼는 유한 지연만 흡수한다. 4ms마다 한 블록이 오는데 처리에6ms가 지속되면 도착이 처리보다 빠르다. 두 버퍼의 재사용 시점도 충돌한다.

답과 이유 보기

동시에 같은 데이터 두 사본이 필요하다는 뜻이 아니라 두 공간 용량 합이다.

RX_RDY가 곧 전체 버퍼 재제공 허가인가?

답과 이유 보기

아니다.

동일 버퍼에서 여러 데이터 준비 이벤트가 가능하며 driver 해제를 확인한다.

처리가 정확히4ms인 자체 이상 모형은 t8에 A 재사용 가능한가?

답과 이유 보기

A 처리가[4,8)이고 t8에 해제가 먼저 반영된다는 가정이다. 실제 비용·지연 여유는 별도다.

한 단계 더

단일 버퍼에서 수신4ms 후 처리3ms를 끝내고 다음 수신을 시작하는 중지 가능한 입력 모형은3블록에21ms다. 두 버퍼의15ms와 비교하되 중지 불가능한 연속 입력은 단일 버퍼의 이 일정에서 손실이 생길 수 있음을 구분하라.

소단원 9.3

전송·처리·인터럽트 비용

DMA가 바이트를 대신 옮기면 CPU 사용 시간은 얼마나 줄어들까?

준비 개념과 학습 목표

준비 개념

  • 전송 경과 시간과 CPU 점유 시간은 다르다.
  • 블록당 고정 비용과 바이트당 비용을 구분한다.

학습 목표

  • 전송·설정·완료 처리·본문 처리 비용을 따로 센다.
  • 블록 크기 증가의 CPU 비용과 지연/메모리 절충을 비교한다.

시간의 종류를 구분하기

전송 경과 시간은 데이터가 이동하는 데 걸린 시간이다. CPU 점유 시간은 CPU가 설정·interrupt·처리 등에 실제 사용하는 시간이다. DMA 전송 중 CPU가 다른 일을 할 수 있어 두 수를 단순 합쳐 CPU 부하라고 하면 안 된다.

버스 경합과 cache 처리도 비용이 될 수 있다. 이 단원의 가상 모형은 이런 추가 비용을0으로 놓고 명시한 비용만 센다. 실제 보드의 속도 개선이나 실시간 보장으로 주장하지 않는다.

바이트마다 깨우기와 블록마다 깨우기

자체 비교에서 interrupt 방식은 바이트마다 CPU 작업을 한다. DMA 방식은 한 블록 설정·한 블록 완료 처리와 별도의 데이터 처리를 한다. 블록을 키우면 초당 완료 이벤트 수가 줄어 고정 비용을 분산할 수 있다.

큰 블록은 버퍼를 더 쓰고 전체 블록이 모일 때까지 기다리는 시간을 늘린다. 작은 입력에도 언제나 최대 블록이 최적이라고 결론 내릴 수 없다. 부분 완료와 timeout 기능이 있으면 지연 계산도 달라진다.

수신율과 처리율 확인하기

평균 CPU 부하는 초당 CPU 작업 시간/1초로 계산한다. 이 숫자가 낮아도 우선순위·최악 지연·버퍼 인계가 만족된다는 보장은 아니다. ISR에서 긴 처리를 하고 버퍼 재제공을 놓치는 경우도 따로 살핀다.

통지는 완료와 오류를 구별해야 한다. UART async 송신 중단 이벤트는 일부 데이터가 이미 나갔을 수 있다. 요청 길이만 보고 전부 성공했다고 기록하지 않는다. 전송 성공 바이트 수와 CPU 비용 계산의 가정을 같이 남긴다.

중간 과정을 따라가는 예제

가상 입력률64000바이트/초, 블록256바이트다. DMA 블록당 CPU 설정8μs, 완료 처리12μs, 내용 처리40μs다. 매 블록 완료 이벤트 하나이며 기타 비용0이다. 비교 방식은 바이트당 CPU2μs이고 내용 처리는 같은 블록당40μs다. 초당 CPU 점유와 비율을 비교하라.

  1. 블록률64000/256=250블록/초다. DMA CPU 비용은 블록당8+12+40=60μs다.
  2. DMA 초당 CPU 점유250×60=15000μs=15ms로1초의1.5%다.
  3. 바이트 interrupt 방식은64000×2=128000μs, 별도 내용 처리250×40=10000μs다. 총138000μs=138ms=13.8%다.
  4. 차이는138−15=123ms/초, CPU 점유 비율은13.8−1.5=12.3퍼센트포인트다. 실제 전송 완료 지연 또는 성능측정으로 해석하지 않는다.

DMA15ms/초(1.5%), 바이트 방식138ms/초(13.8%)다. 자체 비용 가정에서123ms/초 줄지만 실제 장비 측정이 아니다.

종이와 본문으로 직접 해보기

블록512바이트로 바꿔 설정8μs/완료12μs는 유지하고 내용 처리는80μs다. 입력률은64000바이트/초다. 블록률·DMA CPU점유·전체 블록 채움 시간을 계산하라. 첫 바이트는 시간0에 이미 받은 것으로 놓지 않고 빈 버퍼가 일정률로 채워지는 유체 모형이다.

힌트 보기

블록률은 입력률/블록 크기, 채움 시간은 반대 비율이다.

풀이 보기

125블록/초, CPU블록당100μs로12500μs=12.5ms/초(1.25%)다. 채움512/64000=0.008초=8ms다. 원래256바이트는4ms라 메모리/대기시간 증가와 고정비용 감소가 함께 있다.

오해와 반례

DMA CPU 부하 1.5%면 모든 데이터가 1.5%의 시간에 전송된다.

CPU 점유 비율과 입력이 블록을 채우는 경과 시간은 다른 지표다. 예제의 256바이트를 채우는 시간은 4ms이며 CPU는 블록당 60μs 사용한다. 낮은 평균 부하가 마감시간 보장을 대신하지 않는다.
