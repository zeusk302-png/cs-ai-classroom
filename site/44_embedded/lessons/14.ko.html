  • 상태와 조건

학습 목표

입력에서 출력까지 계약을 연결한다

교육 프로젝트는 가상 온도 센서, 제어 상태, 표시용 메시지를 연결한다. 드라이버가 얻은 raw 값은 규약에 따라 단위로 바꾸고 상태·시각과 함께 전달한다. raw 정수, 섭씨 값, 수신 시각, 실제 획득 시각은 서로 다른 정보다. 숫자 하나만 넘기면 통신 지연이나 측정 실패를 구별하기 어렵다.

자체 드라이버 계약은 valid 표시, 정수 raw, 공통 단조 시계의 acquired_ms, sequence를 반환한다. valid가 거짓이면 raw를 정상 온도로 쓰지 않는다. 성공이라도 값의 범위와 나이를 검사한다. 이 규약은 실제 특정 센서의 register 형식이 아니다.

서로 다른 문턱으로 상태를 유지한다

자체 교육 모형은 raw 한 단위를 0.25 °C로 정한다. 정상 OFF 상태에서 T≥30 °C이면 ON으로, 정상 ON에서 T≤28 °C이면 OFF로 전이한다. 28<T<30에서는 이전 상태를 유지한다. 두 문턱을 둔 hysteresis는 문턱 근처에서 출력이 반복 뒤집히는 현상을 줄이는 설계다.

이 모형은 화면의 가상 팬 표시만 제어한다. valid가 거짓이거나 측정 나이가 허용 범위를 벗어나면 FAULT 상태에서 표시를 OFF로 둔다. 실제 냉각·가열 장치에서 OFF가 안전한지는 장치·고장·위험 분석으로 따로 정해야 하며 이 교육 선택을 일반 안전 보증으로 사용하지 않는다.

보고와 제어의 시계를 맞춘다

측정 나이는 now_ms−acquired_ms다. 나이가 0 이상 200 ms 이하인 값만 fresh로 정한다. received_ms가 최근이라는 이유로 acquired_ms를 새 값으로 바꾸지 않는다. 시계가 다르면 이 뺄셈을 직접 할 수 없고 동기화나 보정 계약이 필요하다. 음수 나이는 이 모형에서 시간 정보 오류다.

보고 메시지에는 단위·상태·원래 획득 시각·sequence를 남긴다. 전송 실패와 제어 입력 실패도 다른 사건으로 기록한다. 버퍼 한도와 오래된 메시지 처리 규약을 정하고 표시 통신이 느리다고 제어 값을 무제한 재사용하지 않는다.

중간 과정을 따라가는 예제

자체 모형의 현재 상태는 OFF다. 정상 fresh 입력 raw=112, raw=120, raw=116, raw=112를 순서대로 처리하라. raw는 0.25 °C 단위이고 ON 문턱은 30, OFF 문턱은 28 °C다.

  1. 112×0.25=28 °C다. OFF에서 30 미만이므로 OFF를 유지한다.

  2. 120×0.25=30 °C다. OFF의 포함 경계 T≥30을 만족해 ON으로 간다.

  3. 116×0.25=29 °C다. ON에서 28보다 크므로 ON을 유지한다.

  4. 마지막 112는 28 °C이므로 ON의 포함 경계 T≤28을 만족해 OFF가 된다.

상태는 OFF→OFF→ON→ON→OFF다. 실제 센서나 팬 동작을 측정한 기록은 아니다.

드라이버의 계약을 먼저 문서화한다

드라이버는 장치와 응용 사이에서 읽기·변환·실패를 표현한다. Zephyr의 Fetch and Get은 fetch에서 표본을 driver 내부에 저장한 뒤 get으로 채널을 읽는 규약이다. 여러 context가 locking 없이 섞어 호출하면 안전한 독점 접근이 자동 제공되지 않는다. 본문은 API를 실행하는 대신 입력 객체를 독립적으로 전달하는 자체 모형을 사용한다.

하나의 제어 담당이 상태를 소유하고 표본은 immutable 복사본으로 받는다고 정한다. 실패 코드가 남아 있는데 이전 raw를 새 정상 표본처럼 보고하지 않는다. 버퍼 수명·채널·단위·시각·순서·호출 가능 context를 문서에 적는다.

FAULT는 별도 복구 사건을 요구한다

이 단원은 OFF/ON/FAULT 세 상태를 사용한다. 정상 상태에서 invalid 또는 stale 사건은 FAULT로 보내고 출력 표시를 OFF로 만든다. FAULT에서는 정상 표본만 도착해도 상태를 유지한다. manual_reset 사건과 valid·fresh·T≤28 조건이 동시에 참일 때만 OFF로 복구한다.

리셋은 가상 교육 사건이다. 실제 장비의 수동 복구나 안전 기능을 인증하는 절차가 아니다. FAULT 상태에서 높은 온도 표본과 리셋이 함께 와도 OFF 복구 조건을 만족하지 않는다. 복구 뒤 다시 정상 규칙을 적용하는 시점을 명시하여 같은 사건에서 곧바로 켜지지 않도록 한다.

표와 구현과 검증의 연결을 남긴다

설계 문서에는 상태마다 입력 조건·다음 상태·출력·로그를 한 행으로 쓴다. 초기 상태 OFF, FAULT 출력 0, 정상 band에서 이전 상태 유지라는 불변식을 기록한다. 이벤트 우선순위는 먼저 invalid/stale, 그다음 FAULT 복구, 그다음 정상 문턱 판정으로 정한다.

실제 SMF에는 entry/run/exit와 초기화·전이·종료의 호출 규약이 있다. 상태 표가 올바르다고 모든 API 사용도 자동으로 올바르지는 않는다. 어떤 함수에서 전이를 호출할 수 있는지와 종료 후 실행 중단을 확인해야 한다. 여기서는 Zephyr의 컴파일이나 상태기계 실행은 하지 않았다.

중간 과정을 따라가는 예제

초기 OFF에서 시각 0/100/200/300/400/500/600 ms의 사건을 처리하라. 차례대로 fresh valid 온도 29/31/29/27 °C, invalid, fresh valid 27 °C, manual_reset과 fresh valid 27 °C다. 각 상태와 출력 표시를 적어라.

  1. 0 ms의 29는 OFF 유지, 100 ms의 31은 ON, 200 ms의 29는 ON 유지, 300 ms의 27은 OFF다.

  2. 400 ms invalid는 FAULT로 간다. 출력은 OFF 표시 0이다. 실패 raw는 정상 판정에 쓰지 않는다.

  3. 500 ms의 정상 27만으로는 복구하지 않아 FAULT와 출력 0을 유지한다.

  4. 600 ms는 manual_reset·valid·fresh·27≤28을 모두 만족하여 OFF로 복구한다.

사건 뒤 상태는 OFF/ON/ON/OFF/FAULT/FAULT/OFF, 출력은 0/1/1/0/0/0/0이다. 실제 보드 사건 기록이 아니라 계약에 따른 추적이다.

어떤 환경에서 무엇을 관찰했는지 적는다

종이 추적은 계약에 따른 예상 상태를 계산한다. 순수 함수 실행은 작성한 코드와 예상 결과의 차이를 볼 수 있지만 실제 센서·bus·전압·OS 지연까지 확인하지 못한다. simulator는 자신이 제공하는 장치·시간·환경 모형 안의 실행이며 실물 시험은 별도 근거다.

Zephyr native_sim은 host용 native executable로 응용과 커널을 함께 빌드할 수 있다. 특정 embedded CPU나 보드 전체를 모사하는 것은 아니며 가상 시간이 host 실시간과 분리될 수 있다. 실행 파일 이름이 zephyr.exe여도 이 설명의 대상은 Linux 환경이다. 이 자료에서는 native_sim을 빌드하거나 실행하지 않았다.

같은 입력 표와 판정 규약을 보존한다

재현 기록에는 원고/코드 버전, 상태 초기화, 사건 순서, 시각 기준, 단위, valid, reset, 출력 예상값을 남긴다. 실제 실행했으면 관측값과 환경·실패 로그를 추가한다. 실행하지 않은 예상값을 observed 칸으로 옮기지 않는다.

정상 경계 30/28, band 유지, invalid, stale, FAULT 복구를 각각 별도 경우로 설계한다. 임의 입력 하나가 잘 맞았다는 사실만으로 모든 분기나 시간 동작이 검증된 것은 아니다. 센서 정확도·GPIO 반응·통신 장애는 장비 없는 과제의 미확인 목록에 남는다.

가상의 비용 합과 실제 지연을 구별한다

자체 비용 모형은 주기 최대 대기 100 ms, 획득 최대 5 ms, 제어 계산 최대 2 ms, 출력 갱신 최대 3 ms를 겹치지 않고 합한다고 정한다. 사건이 표본 직후 발생한 경우를 포함한 반응 상한은 110 ms다. 이 값은 정한 모든 상한이 실제로 지켜진다는 가정에 의존한다.

실제 bus 지연·interrupt·work queue·스케줄링·통신은 그 가정에 추가 비용을 만들 수 있다. official trigger 문서도 callback 지연의 변동을 설명한다. simulator의 110 가상 ms와 장비의 110 ms를 같은 측정으로 발표하지 않는다.

중간 과정을 따라가는 예제

가상의 관측 표에서 순수 코드 환경 P는 계획한 여섯 경우를 모두 실행해 다섯 경우 일치했고 하나 불일치했다고 가정한다. simulator S는 여섯 중 네 경우 실행해 모두 일치했다. 실물 H는 실행 0이다. 각 환경의 실행한 경우 중 일치율과 계획 대비 실행율을 구하라. 이 표는 실제 시험 기록이 아니다.

  1. P의 실행 분모는 6이므로 일치율 5/6≈83.33%, 계획 대비 실행율 6/6=100%다. 불일치 한 경우를 삭제하지 않는다.

  2. S의 일치율은 실행 분모로 4/4=100%지만 계획 대비 실행율은 4/6≈66.67%다. 나머지 두 경우는 미실행이다.

  3. H는 0건이므로 일치율을 0/0으로 계산하지 않고 미수행으로 기록한다. 계획 대비 실행율은 0/6=0%다.

  4. 환경을 합친 비율 하나로 실물 검증을 주장하지 않는다. 특히 P와 S 수치는 문제의 가상 관측값이다.

P는 일치 5/6와 실행 6/6, S는 일치 4/4와 실행 4/6, H는 일치율 미수행과 실행 0/6이다. 실제 세 환경은 모두 미수행이다.
