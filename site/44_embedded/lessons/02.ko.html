소단원 2.1

Cortex-M과 명령·레지스터

작은 보드가 같은 숫자를 더하려면 값은 어디에서 기다릴까?

준비 개념과 학습 목표

준비 개념

  • 비트는 0/1 한 자리다. 여기서 바이트는 8비트, word는 32비트이며 주소는 바이트 위치 번호다. 0x는 16진 표기로 0x10=16이다.
  • 레지스터는 코어 안의 값 저장 자리이고 메모리는 주소로 찾는 저장 공간이다. 명령은 값을 읽고 정해진 규칙으로 상태를 바꾸는 단계다.
  • 자가진단: 주소 0x20000000에 값 7을 둔다면 주소는 위치,7은 내용이다. 둘은 같은 종류의 숫자가 아니다.

학습 목표

  • Cortex-M3 판본을 다른 Cortex-M과 구별한다.
  • 범용 레지스터·SP·LR·PC의 역할을 설명한다.
  • 작은 load/add/store 상태를 종이에 추적한다.

먼저 코어와 칩을 구별한다

Cortex-M은 하나의 동일한 칩 이름이 아니라 Arm의 마이크로컨트롤러용 코어 계열이다. 이 단원은 Armv7-M Cortex-M3를 DUI 0552A의 설명으로 한정한다. 주변장치·실제 SRAM 용량·클록·Flash 배치는 코어를 넣은 반도체 제조사의 칩 설계에 따라 달라진다. Cortex-M4의 선택 FPU나 Armv8-M의 보안/stack-limit 기능을 M3의 기본 기능으로 가져오지 않는다.

M3의 R0–R12는 32비트 범용 레지스터다. R13은 현재 선택된 스택 포인터 SP이고 MSP/PSP 두 저장값이 있으며, R14인 LR은 호출 복귀 정보를, R15인 PC는 명령 주소를 나타낸다. 상태 레지스터에는 결과 조건과 예외 상태도 있다. PC를 일반 데이터 레지스터처럼 자유롭게 다루는 것은 명령별 제약을 무시한다.

명령의 의미와 도구의 일을 나눈다

load는 주소의 메모리 값을 레지스터로 읽고 store는 레지스터 값을 메모리로 쓴다. ADD는 피연산자를 더해 목적 레지스터를 갱신한다. 모든 명령이 같은 길이이거나 같은 사이클 비용인 것은 아니며 Thumb 명령 인코딩에는 16/32비트 형태가 있다. 어셈블러의 표기를 읽는 것과 기계어 인코딩·시간 측정을 확인하는 것은 다른 작업이다.

예제는 실제 명령 이름 LDR/ADD/STR의 값 의미를 따르지만 원시 바이트 인코딩·PC의 파이프라인 읽기값·플래그·fault 타이밍은 추적에서 제외한다. R1은 유효한 정렬 주소, 메모리는 정상 RAM, 접근은 허용되고 다른 주체가 값을 바꾸지 않는다고 가정한다. 따라서 이 표를 하드웨어 실행 로그라고 부르지 않는다.

하나의 상태 전이를 계산한다

처음 R1=0x20000000이고 그 주소의 32비트 word가 7이다. LDR R0,[R1] 뒤 R0=7이고 ADD R0,R0,#5 뒤 12가 된다. STR R0,[R1,#4]는 다음 word 주소 0x20000004에 12를 쓴다. 원래 주소의 7은 그대로다. 덧셈은 여기서 overflow 없는 작은 값만 사용한다.

저장 위치는 주소+바이트 오프셋으로 계산한다. word 하나가 4바이트라 +4는 다음 word이고 +1은 다음 바이트다. M3에서 일부 비정렬 접근이 지원된다는 사실만으로 모든 주소·명령·Device 접근이 안전한 것은 아니다. 실제 칩의 접근 폭·정렬·권한 계약을 확인해야 한다.

중간 과정을 따라가는 예제

위 정상 RAM 모형에서 R1=0x20000000, word[R1]=7이다. LDR R0,[R1]; ADD R0,R0,#5; STR R0,[R1,#4]의 상태를 구한다.

  1. 초기 표에 R1의 주소와 메모리 값 7을 별도 칸에 쓴다.
  2. LDR 뒤 R0=7이다. 메모리를 변경하지 않는다.
  3. ADD 뒤 R0=12이며 이번 작은 값은 32비트 범위 안이다.
  4. STR의 목적 주소는 0x20000004다. 그 word를 12로 쓰고 0x20000000의 7을 유지한다.

R0=12이고 두 word는 7,12다. 실행시간·PC·플래그는 이 추적의 출력이 아니다.

종이와 본문으로 직접 해보기

같은 모형에서 처음 word[R1]=20으로 바꾸고 LDR R2,[R1]; ADD R2,R2,#3; STR R2,[R1]을 추적한다. 주소와 내용을 서로 다른 색으로 적는다.

힌트 보기

마지막 store는+4가 없어 처음 주소를 덮는다.

풀이 보기

R2는 20→23이 되고 word[0x20000000]=23이다. 주소 R1은 변하지 않는다. 처음 값 20은 덮여서 남지 않는다.

오해와 반례

Cortex-M이라는 이름만 같으면 주변장치 주소와 부동소수점 명령도 모두 같다.

M3와 M4/다른 코어는 명령 및 선택 기능이 다르고 같은 M3라도 제조사 주변장치가 다르다. 특정 칩의 매뉴얼을 생략한 주소 접근은 정당화되지 않는다.

한 단계 더

심화: 값 추적은 귀납적으로 증명할 수 있다. 유효 주소 A에서 최초 M[A]=v라면 LDR 뒤 R=v, ADD #k 뒤 R=(v+k) mod 2^32, STR [A+4] 뒤 M[A+4]=R다. A와 A+4가 겹치지 않는 유효 word이고 접근 fault/동시 쓰기가 없다는 조건에서 M[A]=v가 유지된다. 메모리 맵이 Device라면 읽기/쓰기 부작용과 접근 폭 계약 때문에 이 정상 RAM 불변식은 자동으로 성립하지 않는다.

소단원 2.2

메모리 맵과 주변장치

같은 store 명령이 한 주소에서는 숫자를 저장하고 다른 주소에서는 장치를 움직일까?

준비 개념과 학습 목표

준비 개념

  • 메모리 맵은 주소 범위와 연결된 대상·속성을 정한 지도다. 범위 [A,B)는 A를 포함하고 B는 포함하지 않는다.
  • 주변장치는 코어 밖의 입출력 기능이며 메모리 매핑 레지스터로 제어할 수 있다. 읽기와 쓰기의 효과가 서로 다를 수도 있다.
  • 자가진단: 값 1을 쓰면 플래그를 지우는 장치는 보통 RAM의 값을 1로 저장하는 규칙과 다르다.

학습 목표

  • 코어 기본 영역과 구현된 실제 저장 공간을 구별한다.
  • 주변장치 레지스터의 접근 계약을 적용한다.
  • 읽기-수정-쓰기가 안전한 조건과 반례를 설명한다.

주소가 있다고 자원이 있는 것은 아니다

M3 기본 맵의 Code 영역은 0x00000000부터, SRAM은 0x20000000부터, Peripheral은 0x40000000부터 시작한다. 이것은 영역 분류이며 모든 주소가 물리 메모리로 구현되어 있다는 뜻은 아니다. 수 GB 주소 공간과 실제 칩의 작은 RAM 용량을 구별한다. 허용되지 않은 접근은 fault를 일으킬 수 있다.

여기서는 가상 칩이 SRAM [0x20000000,0x20000100)을 구현하고 가상 장치의 STATUS를 0x40001000, ACK를 0x40001004에 둔다. 실제 판매 칩의 레지스터 이름·주소가 아니다. SRAM은 정상 저장이고 두 장치 레지스터는 정렬된 32비트 접근만 받는다고 계약한다.

접근은 상태 전이 계약이다

STATUS의 bit0은 완료 플래그, bit1은 오류 플래그다. 읽기는 현재 값을 반환하고 상태를 바꾸지 않는다. ACK에 쓰면 쓴 값의 1비트에 해당하는 STATUS 비트만 지운다는 write-one-to-clear 계약을 만든다. ACK 읽기는 금지하고 다른 비트는 항상 0이라고 가정한다. 초기 STATUS=3에서 ACK에 1을 쓰면 STATUS=2다.

Normal 메모리와 Device 메모리는 순서·투기 접근 등의 속성이 다르다. C의 volatile로 표현된 접근이 필요할 수 있지만 volatile은 언어 접근 관찰에 관한 수단이며 원자적 읽기-수정-쓰기나 모든 버스 순서를 보장하는 만능 장치가 아니다. 실제 코어 barrier와 제조사 레지스터 요구를 따로 확인해야 한다.

읽기-수정-쓰기의 반례

STATUS=3을 읽어 bit0을 제거한 값 2를 ACK에 쓰면 완료가 아니라 bit1 오류만 지워져 STATUS=1이 된다. RAM식 s&~1을 장치 ACK에 적용한 것이 문제다. 요청한 완료 플래그만 지우려면 ACK에 마스크 1을 직접 쓴다.

공유 레지스터의 읽기와 쓰기 사이에 인터럽트나 장치가 상태를 바꾸면 읽은 값은 이미 오래된 상태일 수 있다. 별도 SET/CLEAR 레지스터·원자 기능·임계 구역 등은 장치와 동시성 계약에 맞게 선택한다. 인터럽트를 잠깐 막아도 DMA나 외부 장치의 자체 변경까지 멈춘다는 보장은 없다.

중간 과정을 따라가는 예제

가상 STATUS=3, ACK는 write-one-to-clear다. 완료만 지우는 직접 쓰기와 읽기-수정-쓰기 값 2를 비교한다. 실행 사이 다른 변경은 없다.

  1. 3을 이진 11로 적어 완료 bit0과 오류 bit1을 표시한다.
  2. ACK=1이면 지울 마스크는 01이다. STATUS는 11 & ~01=10이다.
  3. 다시 초기 11에서 ACK=2이면 마스크 10을 지워 01이 남는다.
  4. 두 경우 모두 메모리 값 저장이 아니라 STATUS 전이이며 ACK를 읽어 확인하지 않는다.

직접 1 쓰기는 오류 2를 보존하고 완료를 지운다. 값 2 쓰기는 반대로 완료 1을 남긴다.

종이와 본문으로 직접 해보기

초기 STATUS=2에서 장치가 bit0을 추가해 3이 된 다음 ACK에 1을 쓰면 무엇이 남는가? 정상 SRAM 끝 주소 0x20000100에 word를 저장할 수 있는지도 판정한다.

힌트 보기

ACK 전이는 바로 그 순간 상태에서 1비트만 지운다. SRAM 끝 주소는 반열린 범위 밖이다.

풀이 보기

3→2로 오류가 남는다. SRAM 끝 주소는 구현 범위에 포함되지 않으므로 저장을 정당화할 수 없다. 마지막 유효 정렬 word 시작은 0x200000FC다.

오해와 반례

32비트 주소 공간이면 모든 주소에 32비트 RAM 값이 있다.

Peripheral과 PPB는 장치이며 일부 주소는 미구현·예약이다. 위 가상 SRAM은 256바이트만 구현한다. 주소 폭은 자원의 실재나 접근 권한을 보장하지 않는다.

자기점검

ACK에 0을 쓰면 무엇을 지우는가?

답과 이유 보기

아무것도 지우지 않는다.

volatile 접근 두 개가 하나의 원자 연산인가?

답과 이유 보기

일반적으로 아니다.

중간에 다른 주체의 변경이 끼어들 수 있다.

가상 SRAM의 마지막 정렬 word 시작은?

답과 이유 보기

0x200000FC다.

4바이트가FC,FD,FE,FF에 들어가 끝 100을 넘지 않는다.

한 단계 더

심화 증명: 마스크 m에 의한 ACK 전이를 S′=S & ~m으로 정의하면 m 밖의 모든 비트 i는 S′ᵢ=Sᵢ다. m 안의 비트는 0이다. 따라서 원하는 플래그만 포함한 마스크를 쓰면 당시 다른 플래그를 보존한다. 그러나 장치가 이후 다시 플래그를 설정할 수 있으므로 성공한 clear가 미래의 영구 0을 보장하지 않는다. 예약 비트·쓰기 부작용·폭·읽기 허용 조건이 다른 실제 장치에는 이 가상 증명을 그대로 적용하지 않는다.

소단원 2.3

스택·startup·링커 설정

전원을 켰을 때 main보다 먼저 누가 변수의 첫 값을 준비할까?

준비 개념과 학습 목표

준비 개념

  • 스택은 호출·지역 상태를 임시 보관하는 영역이다. full descending 스택은 저장 전에 SP를 낮춘다. 저장 크기와 정렬 조건을 별도로 정한다.
  • 링커는 코드·데이터 조각을 주소에 배치하고 기호를 결합한다. VMA는 실행 시 사용하는 주소, LMA는 초기 이미지가 놓이는 주소다.
  • 자가진단: Flash의 초기값 5가 RAM에 복사되지 않았다면 RAM 변수가 5라는 결론은 아직 성립하지 않는다.

학습 목표

  • M3 리셋의 초기 MSP와 Thumb 벡터를 추적한다.
  • 링커 배치와 실제 런타임 초기화를 구별한다.
  • RAM 데이터·bss·스택의 겹침과 공간을 계산한다.

리셋 진입의 계약

M3의 이 판본에서는 리셋 시 주소 0의 첫 word를 MSP로 읽고 주소 4의 reset vector로 실행을 시작한다. reset vector의 bit0은 Thumb 상태 표시로 1이어야 한다. 실제 메모리가 이 주소에 어떤 Flash/ROM을 노출하는지는 칩의 부트 맵에 따른다. 첫 word는 실행 명령이 아니라 초기 스택 값이다.

가상 프로젝트는 Flash 이미지가 주소 0에 보이고 첫 word=0x20000100, 둘째 word=0x00000081이라고 정의한다. 실행 주소는 Thumb 표시 비트를 뺀 0x80이고 MSP는 SRAM 끝 100이다. 끝 주소 자체에 쓰는 것이 아니라 full descending 저장 전에 아래로 이동한다. 실제 예외 프레임/ABI 정렬/중첩 사용량은 별도 요구다.

배치 정보는 실행 코드가 아니다

가상 .data의 LMA=0x000000C0, VMA=0x20000000, 길이 8바이트다. 이미지의 두 32비트 초기값은 5,9이고 .bss는 [0x20000008,0x20000010)이다. startup의 런타임 초기화가 8바이트 복사하고 bss8바이트를 0으로 채운 뒤 main을 호출한다. 이 초기화 성공 및 추가 변형 없음이 변수 첫 값의 근거다.

CMSIS 문서는 Reset_Handler가 보통 SystemInit 후 C/C++ 런타임을 거쳐 main으로 이어짐을 설명한다. 실제 순서·전역 변수 사용 가능 시점은 프로젝트 런타임에 달려 있다. GNU ld의 AT/AT>는 LMA를 배치할 뿐 복사 명령을 저절로 수행하지 않는다. .bss의 영 초기화도 초기화 코드나 해당 런타임 계약이 필요하다.

메모리 공간을 증명한다

가상 SRAM은 [0x20000000,0x20000100), 스택 예약은 [0x200000C0,0x20000100)이다. 초기 데이터/bss의 끝 10은 스택 시작C0보다 작아 겹치지 않는다. 스택은 64바이트이고 현재 예제의 4바이트 저장 두 개는 SP를 100→FC→F8로 만든다. 나중 호출의 최대 동시 점유를 따로 합해야 안전하다.

RAM의 합계만 맞아도 배치가 겹치면 안 된다. 정렬·섹션 경계·벡터 보존·startup에 쓰이는 기호 이름과 복사 길이가 실제 링크 이미지와 일치해야 한다. Cortex-M3에는 최신 CMSIS 템플릿의 모든 Armv8-M stack-limit 기능이 있는 것이 아니므로 소프트웨어 검사·보호 가능성도 해당 칩 기준으로 검토한다.

중간 과정을 따라가는 예제

위 가상 Flash/RAM 배치에서 리셋 후 초기화 및 4바이트 스택 저장 두 개를 종이에 추적한다. 실제 바이너리나 보드 실행은 아니다.

  1. 벡터 첫 word에서 MSP=0x20000100, reset vector0x81에서 Thumb bit0=1과 실행 위치 0x80을 구한다.
  2. startup이 C0의 8바이트를 RAM00부터 복사해 word5,9를 준비한다.
  3. bss RAM08~0F를 0으로 채워 main 진입의 초기화 계약을 완성한다.
  4. 스택 두 word 저장은 SP FC,F8에 배치하며 예약C0~FF 안이다. 데이터 끝 10과 겹치지 않는다.

데이터 5,9·bss0·SP=0x200000F8이다. 순서와 주소가 맞다는 종이 결과이며 부팅 성공을 측정하지 않았다.

종이와 본문으로 직접 해보기

가상 스택 64바이트에서 한 활성 호출의 추가 점유 12바이트, 예외 프레임과 처리기 추가 점유 합 32바이트라고 가정한다. 동시에 세 호출과 한 예외가 있으면 안전한가? 두 호출이면 어떠한가?

힌트 보기

동시에 살아 있는 점유만 더한다. 실제 M3의 모든 예외 비용을 32바이트로 단정한 것이 아니라 이 활동의 합계 계약이다.

풀이 보기

세 호출은 3×12+32=68바이트라 64를 넘는다. 두 호출은 24+32=56바이트로 8바이트 남는다. 정렬 패딩·다른 중첩·런타임 사용량을 제외한 이 가정 안에서만 판정한다.

오해와 반례

링커가 .data 주소를 정했으므로 main 전에 RAM에 초기값이 반드시 들어간다.

LMA/VMA 배치는 복사해야 할 위치를 지정한다. startup을 생략하거나 길이 기호가 틀리면 RAM은 미초기화일 수 있다. 두 역할의 계약을 함께 확인해야 한다.

한 단계 더

심화 증명: 초기 SP=S, 각각 4바이트인 비음수 정수 k개 저장을 누적하면 SP=S−4k이고 사용 구간은 [S−4k,S)이다. 스택 예약 [L,S)에 안전하려면 4k≤S−L 및 해당 정렬·접근 조건이 필요하다. 임의 호출 크기 sᵢ와 중첩 예외 크기 eⱼ로 일반화하면 동시에 활성인 합 Σsᵢ+Σeⱼ가 예약을 넘지 않아야 한다. 실제 최대 중첩과 컴파일러의 프레임·패딩을 모르면 소스의 지역 변수 크기만으로 충분성을 주장할 수 없다.
