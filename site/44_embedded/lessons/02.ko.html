소단원 2.1

Cortex-M과 명령·레지스터

작은 보드가 같은 숫자를 더하려면 값은 어디에서 기다릴까?

준비 개념과 학습 목표

준비 개념

  • 비트는 0/1 한 자리다. 여기서 바이트는 8비트, word는 32비트이며 주소는 바이트 위치 번호다. 0x는 16진 표기로 0x10=16이다.

  • 레지스터는 코어 안의 값 저장 자리이고 메모리는 주소로 찾는 저장 공간이다. 명령은 값을 읽고 정해진 규칙으로 상태를 바꾸는 단계다.

  • 자가진단: 주소 0x20000000에 값 7을 둔다면 주소는 위치,7은 내용이다. 둘은 같은 종류의 숫자가 아니다.

학습 목표

  • Cortex-M3 판본을 다른 Cortex-M과 구별한다.

  • 범용 레지스터·SP·LR·PC의 역할을 설명한다.

  • 작은 load/add/store 상태를 종이에 추적한다.

같은 네 명령이라도 저장 순서가 읽은 값을 바꿀까요?

기본과 같은 Armv7-M Cortex-M3의 값 의미만 쓰는 새 종이 추적이다. 정상 RAM의 정렬된 word 주소 A=0x20000020, B=A+4=0x20000024에 각각 7과 11이 있고 R1=A다. 다른 주체의 변경과 fault는 없으며 플래그·기계어 인코딩·사이클은 추적하지 않는다. LDR R0,[R1] 다음 STR R0,[R1,#4], LDR R2,[R1,#4], ADD R2,R2,#5를 실행하면 R0는 7, B의 word는 7, R2는 7을 읽은 뒤 12가 된다. 처음 B에 있던 11을 계속 참조하면 저장 효과를 누락한다.

두 원래 word를 보존하여 계산하려면 두 load를 store보다 먼저 수행한다. LDR R0,[R1], LDR R2,[R1,#4], STR R0,[R1,#4], ADD R2,R2,#5 순서에서는 B는 똑같이 7이지만 R2는 원래 11을 보존한 레지스터라 16이다. 끝 메모리 두 word가 같아도 레지스터 결과는 다르다. 첫 load 뒤 메모리 A를 20으로 바꿔도 이미 읽은 R0가 자동으로 20이 되지는 않는다. 여기의 연산 순서는 단일 주체의 값 추적이며 외부 버스 완료 순서 전체를 인증하지 않는다.

별도 포인터 갱신은 R1을 A+4로 바꾼 뒤 [R1,#4]를 접근하면 A+8=0x20000028에 닿는다. 원래 기준 A의 다음 word B와 현재 기준 R1의 다음 word를 구별한다. 유효 범위를 [A,A+12)로 정하면 A+8에서 시작한 4바이트 word는 끝 A+12 직전까지 들어간다. A+12에서 시작한 word는 범위 밖이다. 주소가 코어의 SRAM 분류 영역 안이라는 사실만으로 이 가상 칩의 해당 저장 공간이 구현된 것은 아니다.

먼저 확인할 개념
  • load 뒤 레지스터와 store 효과

    읽은 값의 보존과 나중 메모리 변경을 상태별로 구별한다.

  • 주소 영역과 실제 접근 범위

    word의 모든 바이트와 칩의 구현 범위를 함께 확인한다.

먼저 코어와 칩을 구별한다

Cortex-M은 하나의 동일한 칩 이름이 아니라 Arm의 마이크로컨트롤러용 코어 계열이다. 이 단원은 Armv7-M Cortex-M3를 DUI 0552A의 설명으로 한정한다. 주변장치·실제 SRAM 용량·클록·Flash 배치는 코어를 넣은 반도체 제조사의 칩 설계에 따라 달라진다. Cortex-M4의 선택 FPU나 Armv8-M의 보안/stack-limit 기능을 M3의 기본 기능으로 가져오지 않는다.

M3의 R0–R12는 32비트 범용 레지스터다. R13은 현재 선택된 스택 포인터 SP이고 MSP/PSP 두 저장값이 있으며, R14인 LR은 호출 복귀 정보를, R15인 PC는 명령 주소를 나타낸다. 상태 레지스터에는 결과 조건과 예외 상태도 있다. PC를 일반 데이터 레지스터처럼 자유롭게 다루는 것은 명령별 제약을 무시한다.

명령의 의미와 도구의 일을 나눈다

load는 주소의 메모리 값을 레지스터로 읽고 store는 레지스터 값을 메모리로 쓴다. ADD는 피연산자를 더해 목적 레지스터를 갱신한다. 모든 명령이 같은 길이이거나 같은 사이클 비용인 것은 아니며 Thumb 명령 인코딩에는 16/32비트 형태가 있다. 어셈블러의 표기를 읽는 것과 기계어 인코딩·시간 측정을 확인하는 것은 다른 작업이다.

예제는 실제 명령 이름 LDR/ADD/STR의 값 의미를 따르지만 원시 바이트 인코딩·PC의 파이프라인 읽기값·플래그·fault 타이밍은 추적에서 제외한다. R1은 유효한 정렬 주소, 메모리는 정상 RAM, 접근은 허용되고 다른 주체가 값을 바꾸지 않는다고 가정한다. 따라서 이 표를 하드웨어 실행 로그라고 부르지 않는다.

하나의 상태 전이를 계산한다

처음 R1=0x20000000이고 그 주소의 32비트 word가 7이다. LDR R0,[R1] 뒤 R0=7이고 ADD R0,R0,#5 뒤 12가 된다. STR R0,[R1,#4]는 다음 word 주소 0x20000004에 12를 쓴다. 원래 주소의 7은 그대로다. 덧셈은 여기서 overflow 없는 작은 값만 사용한다.

저장 위치는 주소+바이트 오프셋으로 계산한다. word 하나가 4바이트라 +4는 다음 word이고 +1은 다음 바이트다. M3에서 일부 비정렬 접근이 지원된다는 사실만으로 모든 주소·명령·Device 접근이 안전한 것은 아니다. 실제 칩의 접근 폭·정렬·권한 계약을 확인해야 한다.

같은 네 명령이라도 저장 순서가 읽은 값을 바꿀까요?
지정 조건추적 결과판정 범위

store 뒤 B를 load한다.

R2는 7을 읽고 덧셈 뒤 12다.

처음 B의 11은 덮어써졌다.

B를 먼저 load한다.

R2는 11을 보존하여 덧셈 뒤 16이다.

끝 B의 word는 여전히 7이다.

R1을 A+4로 바꾼다.

[R1,#4]의 주소는 A+8이다.

오프셋은 현재 레지스터 기준이다.

범위 [A,A+12)의 마지막 word

시작 주소 A+8은 허용된다.

시작 주소 A+12는 허용되지 않는다.

각 명령 뒤 레지스터와 메모리 word를 별도 칸으로 갱신한다. 주소는 현재 기준값에 바이트 오프셋을 더하고 접근 끝을 반열린 범위와 비교한다.

중간 과정을 따라가는 예제

위 정상 RAM 모형에서 R1=0x20000000, word[R1]=7이다. LDR R0,[R1]; ADD R0,R0,#5; STR R0,[R1,#4]의 상태를 구한다.

  1. 초기 표에 R1의 주소와 메모리 값 7을 별도 칸에 쓴다.

  2. LDR 뒤 R0=7이다. 메모리를 변경하지 않는다.

  3. ADD 뒤 R0=12이며 이번 작은 값은 32비트 범위 안이다.

  4. STR의 목적 주소는 0x20000004다. 그 word를 12로 쓰고 0x20000000의 7을 유지한다.

R0=12이고 두 word는 7,12다. 실행시간·PC·플래그는 이 추적의 출력이 아니다.

조건을 바꾸어 비교하기

끝 메모리는 같지만 계산값이 다르다

처음 주소 A와 B의 word 값은 각각 7과 11이다. B를 읽는 시점을 store 전후로 바꾸는 본문의 두 순서에서 끝 B의 word와 ADD 5 뒤 최종 R2를 비교하라.

  1. store는 두 순서 모두 B에 7을 남긴다.

  2. 나중 load는 7을 읽어 12가 되고 먼저 load는 11을 읽어 16이 된다.

끝 메모리 B는 7로 같지만 최종 R2는 각각 12와 16이다.

비교할 점

끝 메모리 일치만으로 모든 중간값과 반환값 일치를 인증할 수 없다.

주소 기준도 상태다

A=0x20000020에서 R1을 A+4로 바꾼 뒤 [R1,#4]로 4바이트를 접근한다. [A,A+12)에 들어가는가?

  1. 시작 주소는 0x20000028이다.

  2. 접근 구간은 [A+8,A+12)이므로 지정 범위에 들어간다.

현재 기준에서 두 word 뒤 주소에 접근하며 범위 안이다.

비교할 점

R1의 초기값을 계속 쓰면 B와 혼동한다.

종이와 본문으로 직접 해보기

같은 모형에서 처음 word[R1]=20으로 바꾸고 LDR R2,[R1]; ADD R2,R2,#3; STR R2,[R1]을 추적한다. 주소와 내용을 서로 다른 색으로 적는다.

힌트 보기

마지막 store는+4가 없어 처음 주소를 덮는다.

풀이 보기

R2는 20→23이 되고 word[0x20000000]=23이다. 주소 R1은 변하지 않는다. 처음 값 20은 덮여서 남지 않는다.

오해와 반례

Cortex-M이라는 이름만 같으면 주변장치 주소와 부동소수점 명령도 모두 같다.

M3와 M4/다른 코어는 명령 및 선택 기능이 다르고 같은 M3라도 제조사 주변장치가 다르다. 특정 칩의 매뉴얼을 생략한 주소 접근은 정당화되지 않는다.

스스로 풀어보기

먼저 답과 이유를 적고, 필요한 만큼 힌트를 한 단계씩 열어 보세요.

연습 1 · 값과 상태 예측

A의 word가 7일 때 R0로 load한 뒤 A에 20을 store한다. 추가 load 없이 R0에 5를 더하면 R0와 A의 word는?

힌트 1

레지스터와 메모리는 별도 상태다.

힌트 2

처음 읽은 7은 R0에 남는다.

풀이와 답 확인

  1. R0는 7+5=12다.

  2. 메모리 A의 word는 20이다.

R0는 12이고 A의 word는 20이다.

흔한 오답에서 다시 생각하기

메모리가 20이 되었으므로 R0도 25가 된다.

이미 읽은 레지스터는 이후 store로 자동 갱신되지 않는다.

연습 2 · 오류 찾아 고치기

store 뒤 B를 load한 추적에서 최종 R2를 16으로 적었다. 어느 상태를 잘못 사용했는가?

힌트 1

store 뒤 B의 새 값을 적는다.

힌트 2

load는 그 시점의 B를 읽는다.

풀이와 답 확인

  1. B는 11에서 7로 바뀌었다.

  2. 따라서 R2는 7을 읽고 5를 더해 12다.

초기 B의 11을 나중 load에 재사용한 오류다.

흔한 오답에서 다시 생각하기

읽은 위치가 B이면 언제나 초기 B의 값을 쓴다.

위치뿐 아니라 접근 시점의 상태를 추적해야 한다.

연습 3 · 직접 만들어 보기

원래 A와 B를 각각 레지스터에 보존한 뒤 B를 A의 값으로 덮어쓰고 원래 B+5를 얻는 네 명령의 순서를 설계하라.

힌트 1

두 load를 store 앞에 놓는다.

힌트 2

마지막 ADD의 입력은 B를 미리 읽은 레지스터다.

풀이와 답 확인

  1. R0로 A를 읽고 R2로 B를 읽는다.

  2. R0를 B에 store한 뒤 R2에 5를 더한다. 끝 B는 7, R2는 16이다.

load A, load B, store B, ADD R2 순서다.

흔한 오답에서 다시 생각하기

store를 먼저 해도 원래 B는 자동으로 보존된다.

별도 저장 전에 덮어쓴 원래 값은 사라진다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

정렬된 정상 RAM [A,A+4n)이 있고 n은 양의 정수다. A+4k에서 4바이트 word를 접근하는 정수 k의 조건은?

힌트 1

시작이 A 이상이어야 한다.

힌트 2

접근 끝 A+4k+4는 상한 이하이어야 한다.

풀이와 답 확인

  1. k≥0이고 k+1≤n이다.

  2. 따라서 0≤k≤n−1이며 k=n은 범위 밖이다.

허용 정수는 0부터 n−1까지다.

흔한 오답에서 다시 생각하기

반열린 상한 A+4n도 마지막 word의 시작이다.

상한에서 시작하면 네 바이트 모두 범위 밖이다.

레지스터는 원래 메모리의 별명인가?

설명 기준 확인

load로 복사한 값이며 나중 store와 자동 연동하지 않는다.

코어 영역 안이면 모든 word가 유효한가?

설명 기준 확인

실제 구현 범위와 접근 폭·정렬·권한을 별도로 확인한다.

한 단계 더

심화: 값 추적은 귀납적으로 증명할 수 있다. 유효 주소 A에서 최초 M[A]=v라면 LDR 뒤 R=v, ADD #k 뒤 R=(v+k) mod 2^32, STR [A+4] 뒤 M[A+4]=R다. A와 A+4가 겹치지 않는 유효 word이고 접근 fault/동시 쓰기가 없다는 조건에서 M[A]=v가 유지된다. 메모리 맵이 Device라면 읽기/쓰기 부작용과 접근 폭 계약 때문에 이 정상 RAM 불변식은 자동으로 성립하지 않는다.

메모리 맵과 주변장치

같은 store 명령이 한 주소에서는 숫자를 저장하고 다른 주소에서는 장치를 움직일까?

준비 개념과 학습 목표

준비 개념

  • 메모리 맵은 주소 범위와 연결된 대상·속성을 정한 지도다. 범위 [A,B)는 A를 포함하고 B는 포함하지 않는다.

  • 주변장치는 코어 밖의 입출력 기능이며 메모리 매핑 레지스터로 제어할 수 있다. 읽기와 쓰기의 효과가 서로 다를 수도 있다.

  • 자가진단: 값 1을 쓰면 플래그를 지우는 장치는 보통 RAM의 값을 1로 저장하는 규칙과 다르다.

학습 목표

  • 코어 기본 영역과 구현된 실제 저장 공간을 구별한다.

  • 주변장치 레지스터의 접근 계약을 적용한다.

  • 읽기-수정-쓰기가 안전한 조건과 반례를 설명한다.

한 비트 플래그는 같은 종류의 두 사건을 셀 수 있을까요?

기본의 가상 STATUS와 ACK 계약을 그대로 쓴다. STATUS bit0은 완료, bit1은 오류이고 읽기는 상태를 바꾸지 않는다. ACK 읽기는 금지되며 정렬된 32비트 write-one-to-clear만 허용한다. 새 이력에서 STATUS=1을 읽은 뒤 장치가 bit1을 세워 STATUS=3으로 만든다. ACK에 마스크 1을 쓰면 현재 상태 3의 bit0만 지워 최종 STATUS=2다. 오래된 읽기값 1을 다시 STATUS에 일반 RAM처럼 저장하는 연산은 이 계약의 ACK 연산이 아니다.

반대로 STATUS=1을 읽은 뒤 같은 완료 종류의 두 번째 사건이 와도 bit0은 이미 1이라 STATUS는 그대로 1이다. 그 다음 ACK 1은 bit0을 지워 0을 남긴다. 읽은 시점 이후 새 사건이 없었던 이력과 새 완료가 하나 더 있었던 이력이 같은 읽기값과 최종값을 만든다. 이 플래그는 미처리 여부의 한 비트이며 완료 횟수나 새 사건의 ID를 저장하지 않는다. CPU 인터럽트를 막아도 장치의 자체 재설정까지 중단한다는 조건은 없다.

완료 개수까지 보존할 새 설계는 장치가 사건마다 단조 카운터를 올리거나 FIFO에 서로 다른 ID를 넣는 등의 별도 계약이 필요하다. 예를 들어 감김 없는 카운터에서 처음 5, 나중 7이면 두 사건을 센다. 이는 기본 STATUS 레지스터에 이미 존재하는 기능이 아니라 새 설계 제안이다. 단순히 volatile을 붙이거나 메모리 barrier를 추가해도 저장되지 않은 사건 개수가 복원되지 않는다. 접근 관찰·순서 요구와 데이터 표현의 정보량을 구별한다.

주소가 있다고 자원이 있는 것은 아니다

M3 기본 맵의 Code 영역은 0x00000000부터, SRAM은 0x20000000부터, Peripheral은 0x40000000부터 시작한다. 이것은 영역 분류이며 모든 주소가 물리 메모리로 구현되어 있다는 뜻은 아니다. 수 GB 주소 공간과 실제 칩의 작은 RAM 용량을 구별한다. 허용되지 않은 접근은 fault를 일으킬 수 있다.

여기서는 가상 칩이 SRAM [0x20000000,0x20000100)을 구현하고 가상 장치의 STATUS를 0x40001000, ACK를 0x40001004에 둔다. 실제 판매 칩의 레지스터 이름·주소가 아니다. SRAM은 정상 저장이고 두 장치 레지스터는 정렬된 32비트 접근만 받는다고 계약한다.

접근은 상태 전이 계약이다

STATUS의 bit0은 완료 플래그, bit1은 오류 플래그다. 읽기는 현재 값을 반환하고 상태를 바꾸지 않는다. ACK에 쓰면 쓴 값의 1비트에 해당하는 STATUS 비트만 지운다는 write-one-to-clear 계약을 만든다. ACK 읽기는 금지하고 다른 비트는 항상 0이라고 가정한다. 초기 STATUS=3에서 ACK에 1을 쓰면 STATUS=2다.

Normal 메모리와 Device 메모리는 순서·투기 접근 등의 속성이 다르다. C의 volatile로 표현된 접근이 필요할 수 있지만 volatile은 언어 접근 관찰에 관한 수단이며 원자적 읽기-수정-쓰기나 모든 버스 순서를 보장하는 만능 장치가 아니다. 실제 코어 barrier와 제조사 레지스터 요구를 따로 확인해야 한다.

읽기-수정-쓰기의 반례

STATUS=3을 읽어 bit0을 제거한 값 2를 ACK에 쓰면 완료가 아니라 bit1 오류만 지워져 STATUS=1이 된다. RAM식 s&~1을 장치 ACK에 적용한 것이 문제다. 요청한 완료 플래그만 지우려면 ACK에 마스크 1을 직접 쓴다.

공유 레지스터의 읽기와 쓰기 사이에 인터럽트나 장치가 상태를 바꾸면 읽은 값은 이미 오래된 상태일 수 있다. 별도 SET/CLEAR 레지스터·원자 기능·임계 구역 등은 장치와 동시성 계약에 맞게 선택한다. 인터럽트를 잠깐 막아도 DMA나 외부 장치의 자체 변경까지 멈춘다는 보장은 없다.

스택·startup·링커 설정

전원을 켰을 때 main보다 먼저 누가 변수의 첫 값을 준비할까?

준비 개념과 학습 목표

준비 개념

  • 스택은 호출·지역 상태를 임시 보관하는 영역이다. full descending 스택은 저장 전에 SP를 낮춘다. 저장 크기와 정렬 조건을 별도로 정한다.

  • 링커는 코드·데이터 조각을 주소에 배치하고 기호를 결합한다. VMA는 실행 시 사용하는 주소, LMA는 초기 이미지가 놓이는 주소다.

  • 자가진단: Flash의 초기값 5가 RAM에 복사되지 않았다면 RAM 변수가 5라는 결론은 아직 성립하지 않는다.

학습 목표

  • M3 리셋의 초기 MSP와 Thumb 벡터를 추적한다.

  • 링커 배치와 실제 런타임 초기화를 구별한다.

  • RAM 데이터·bss·스택의 겹침과 공간을 계산한다.

전체 RAM이 넉넉하면 초기화 구간도 안전할까요?

새 가상 이미지에서 .data A의 ROM LMA는 0xC0, RAM VMA는 0x20000000이고 두 word 초기값은 5와 9다. 별도 .data B의 ROM LMA는 0xD0, RAM VMA는 0x20000010이며 한 word 초기값은 12다. 두 복사 사이의 RAM [0x20000008,0x20000010)은 초기화 대상 밖의 보존 구간으로 정의하고, 직전에 두 word 77과 88이 있다. .bss는 [0x20000014,0x2000001C)의 두 word다. 올바른 초기화는 A의 8바이트와 B의 4바이트를 각각 복사하고 bss의 8바이트만 0으로 만든다.

ROM 0xC0부터 네 word를 일괄 복사하는 잘못된 계획은 A 뒤 ROM 0xC8/0xCC의 가상 padding 값 100/200까지 RAM 보존 구간에 쓰고, ROM 0xD0의 12는 아직 복사하지 않는다. 총량 16바이트라는 숫자만으로 올바른 섹션 두 개를 복사했다고 볼 수 없다. GNU ld의 AT로 LMA를 정하는 것과 실제 복사 표의 시작·목적·길이를 구현하는 것은 다른 작업이다. .bss의 길이 8바이트를 word 개수 8로 잘못 읽으면 32바이트를 지워 지정 끝보다 24바이트 더 쓴다.

CMSIS의 일반 Reset_Handler 경로는 SystemInit 이후 C/C++ 런타임과 main으로 이어진다. 프로젝트가 복사 전에 SystemInit을 호출하고 그 함수가 raw RAM word A를 읽는 별도 추적에서는 값 77이 남아 있다고 지정하면 77을 읽는다. 복사 뒤 main에서 같은 word를 읽으면 5다. 이는 초기화 전 C 전역 변수 접근을 안전한 C 코드로 실행했다는 주장이 아니라, 런타임 준비 시점의 raw 메모리 손모형이다. 해당 초기화 경로의 전역 자료 사용 가능 시점을 프로젝트마다 확인해야 한다.

별도 스택 예약은 [0x200000D0,0x20000100)의 48바이트이고 초기 SP는 0x20000100이다. 두 활성 호출이 각각 8바이트, 추가 예외·처리 전체가 32바이트를 동시에 쓴다는 용량 계약이면 총 48바이트로 SP는 0x200000D0까지 내려가 등호로 맞는다. 여기에 8바이트를 추가하면 SP는 0x200000C8로 예약 아래에 8바이트를 쓴다. 여기의 32바이트는 지정 총량이며 실제 ABI 추가 저장·정렬·중첩을 측정한 값이 아니다. 한 번의 낮은 사용량이나 guard의 현재 무변경은 미래 최대 사용량을 인증하지 않는다.

리셋 진입의 계약

M3의 이 판본에서는 리셋 시 주소 0의 첫 word를 MSP로 읽고 주소 4의 reset vector로 실행을 시작한다. reset vector의 bit0은 Thumb 상태 표시로 1이어야 한다. 실제 메모리가 이 주소에 어떤 Flash/ROM을 노출하는지는 칩의 부트 맵에 따른다. 첫 word는 실행 명령이 아니라 초기 스택 값이다.

가상 프로젝트는 Flash 이미지가 주소 0에 보이고 첫 word=0x20000100, 둘째 word=0x00000081이라고 정의한다. 실행 주소는 Thumb 표시 비트를 뺀 0x80이고 MSP는 SRAM 끝 100이다. 끝 주소 자체에 쓰는 것이 아니라 full descending 저장 전에 아래로 이동한다. 실제 예외 프레임/ABI 정렬/중첩 사용량은 별도 요구다.

배치 정보는 실행 코드가 아니다

가상 .data의 LMA=0x000000C0, VMA=0x20000000, 길이 8바이트다. 이미지의 두 32비트 초기값은 5,9이고 .bss는 [0x20000008,0x20000010)이다. startup의 런타임 초기화가 8바이트 복사하고 bss8바이트를 0으로 채운 뒤 main을 호출한다. 이 초기화 성공 및 추가 변형 없음이 변수 첫 값의 근거다.

CMSIS 문서는 Reset_Handler가 보통 SystemInit 후 C/C++ 런타임을 거쳐 main으로 이어짐을 설명한다. 실제 순서·전역 변수 사용 가능 시점은 프로젝트 런타임에 달려 있다. GNU ld의 AT/AT>는 LMA를 배치할 뿐 복사 명령을 저절로 수행하지 않는다. .bss의 영 초기화도 초기화 코드나 해당 런타임 계약이 필요하다.

메모리 공간을 증명한다

가상 SRAM은 [0x20000000,0x20000100), 스택 예약은 [0x200000C0,0x20000100)이다. 초기 데이터/bss의 끝 10은 스택 시작C0보다 작아 겹치지 않는다. 스택은 64바이트이고 현재 예제의 4바이트 저장 두 개는 SP를 100→FC→F8로 만든다. 나중 호출의 최대 동시 점유를 따로 합해야 안전하다.

RAM의 합계만 맞아도 배치가 겹치면 안 된다. 정렬·섹션 경계·벡터 보존·startup에 쓰이는 기호 이름과 복사 길이가 실제 링크 이미지와 일치해야 한다. Cortex-M3에는 최신 CMSIS 템플릿의 모든 Armv8-M stack-limit 기능이 있는 것이 아니므로 소프트웨어 검사·보호 가능성도 해당 칩 기준으로 검토한다.

힌트 1

레지스터의 보존값과 store 뒤 메모리를 따로 적고, ACK는 현재 상태에 마스크를 적용한다.

힌트 2

초기화는 주소·길이·단위를 항목별로 나누고 스택은 동시 총량을 계산한다.

풀이와 답 확인

  1. ① 끝 B는 두 순서 모두 7이다. 최종 R2는 store 뒤 load이면 12, 미리 load이면 16이다.

  2. ② 오류 추가 뒤 현재 3에 ACK 1을 쓰면 2다. 완료 추가 뒤 현재 1에 ACK 1을 쓰면 0이며 새 완료가 없던 경우도 0이다. 끝값만으로 횟수를 복원할 수 없다.

  3. ③ 복사 A는 ROM 0xC0에서 RAM 0x20000000으로 8바이트, 복사 B는 ROM 0xD0에서 RAM 0x20000010으로 4바이트다. 영 초기화는 RAM 0x20000014부터 8바이트다. 연속 16바이트 복사는 보존값 77과 88을 각각 100과 200으로 덮고 B를 누락한다.

  4. ④ 현재 스택은 48바이트로 예약에 맞고 추가 호출 뒤 56바이트로 8바이트 넘는다. 초기 SP 0x20000100에서 끝 SP는 각각 0x200000D0와 0x200000C8이다.

접근 시점·장치 정보량·초기화 구간·동시 스택 수명을 각각 확인한다. 이 결과는 지정 손모형이며 보드 실행 증거가 아니다.

해결한 뒤 점검할 것

  • 끝 B는 두 순서에서 7로 같지만, store 뒤 load의 최종 R2는 12이고 먼저 load의 최종 R2는 16임을 명시한다.

  • 새 오류는 남지만 같은 종류의 새 완료 횟수는 한 비트에서 구별되지 않음을 설명한다.

  • 두 복사 구간과 bss 영 초기화 및 보존 구간을 바이트 단위로 적는다.

  • 현재 스택 총량은 48바이트, 추가 호출 뒤 총량은 56바이트이며 예약 초과는 8바이트임을 설명하고 실행 미수행을 유지한다.
