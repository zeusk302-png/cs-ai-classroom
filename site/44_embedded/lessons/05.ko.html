소단원 5.1

주기·캡처·compare

프로그램이 바빠도 일정한 시각을 재고 신호가 들어온 순간을 기억할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 타이머는 클록에 따라 변하는 카운터다. tick은 카운터가 한 번 변하는 시간 간격이다.

  • PSC는 분주 설정, ARR은 되돌아갈 경계, CCR은 비교 또는 캡처 값을 담는 레지스터 이름이다. 실제 의미는 칩과 모드에 따라 확인한다.

학습 목표

  • 주파수에서 tick과 주기를 단위까지 계산한다.

  • 출력 비교와 입력 캡처를 구별하고 한 바퀴 경계를 처리한다.

한 번 증가하는 시간과 한 주기를 구별한다

예제는 타이머 입력 클록 f=8 MHz를 PSC+1로 나누는 이상적 상향 카운터다. PSC=7이면 8 MHz/8=1 MHz라 tick은 1 µs다. ARR=999이고 0부터 999까지 센 뒤 0으로 돌아가면 한 주기는 1000 tick이다. 따라서 주기는 1 ms다. 마지막 숫자 999와 칸의 수 1000을 구별해야 한다.

타이머 입력 클록은 CPU 클록과 항상 같지 않다. 클록 트리와 버스 배수, 카운터 모드, 분주·ARR의 적용 시점을 실제 설명서에서 확인해야 한다. 이 모형은 설정이 이미 적용되었고 t=0에서 CNT=0이며 매 tick마다 한 칸 증가한다고 정했다. 초기화 update 이벤트와 실제 시작 지연은 포함하지 않는다.

비교는 예정 값, 캡처는 관찰 값이다

compare는 현재 카운터가 미리 정한 CCR 값과 일치하는 사건이다. 이 모형에서 CCR=250이면 첫 일치는 t=250 µs다. 일치 때 핀을 바꾸는지 인터럽트만 발생시키는지는 별도 설정이다. CCR 숫자 하나만으로 PWM의 극성이나 실제 출력 파형 전체를 정했다고 말할 수 없다.

capture는 외부의 지정한 에지가 왔을 때 카운터 값을 CCR에 저장하는 방식이다. 두 에지의 저장 값 차이를 tick으로 환산하면 시간 간격을 얻는다. 에지 선택, 입력 필터, 캡처 분주와 누락 여부도 실제 설정에 달린다. CPU가 나중에 읽더라도 저장 값은 캡처 시점의 카운터이며 ISR 시작 시각 자체와 다르다.

되돌아가는 숫자에는 추가 조건이 필요하다

16비트 카운터가 0..65535를 돈다면 모듈러스 M=65536이다. 앞 값 a, 뒤 값 b의 차이는 (b−a) mod M으로 계산한다. 단, 실제 간격이 한 바퀴보다 짧다는 조건이 있어야 이것이 실제 tick 수다. 같은 두 숫자는 한 바퀴를 더 돈 긴 간격에서도 나올 수 있다.

ARR를 줄여 0..999만 반복하도록 했다면 모듈러스는 1000이지 저장 레지스터의 비트 수로 정한 65536이 아니다. 긴 시간을 재려면 overflow 횟수 같은 추가 정보를 안전하게 함께 기록해야 한다. 여기서는 여러 바퀴와 기록 경쟁을 해결한 펌웨어를 실행하지 않았으며 짧은 구간만 종이로 계산한다.

중간 과정을 따라가는 예제

입력 8 MHz, PSC=7, ARR=999의 주기와 CCR=250의 첫 일치 시각을 구하라. 별도의 16비트 자유 카운터에서 캡처 65000→1000, tick=1 µs, 간격<65536 µs일 때 시간도 구하라.

  1. 분주비는 7+1=8이므로 tick 주파수는 1 MHz, tick 시간은 1 µs다.

  2. 0..999에는 1000칸이 있어 주기는 1000 µs=1 ms다. 첫 250 도달은 250 tick 뒤라 250 µs다.

  3. 자유 카운터의 차이는 1000−65000=−64000이다. 한 바퀴 65536을 더하면 1536 tick이다.

  4. 간격은 1536 µs=1.536 ms다. 주기 카운터와 자유 카운터는 서로 다른 설정이므로 모듈러스를 섞지 않았다.

주기 1 ms, 첫 비교 250 µs, 두 캡처 간격 1.536 ms다.

종이와 본문으로 직접 해보기

0..999를 반복하고 tick=2 µs인 카운터가 900→100을 캡처했다. 간격이 한 바퀴보다 짧다면 시간은? 이 조건을 빼면 어떤 간격들이 가능할까?

힌트 보기

차이에 모듈러스 1000을 더한 뒤 tick 시간을 곱한다.

풀이 보기

100−900+1000=200 tick이라 400 µs다. 한 바퀴가 2000 µs이므로 추가 회전이 가능하면 400+2000k µs(k=0,1,2,…)도 같은 값 쌍을 낸다. 두 레지스터만으로 k를 결정하지 못한다.

오해와 반례

ARR=999면 주기는 999 tick이며 capture 값을 단순히 빼면 항상 실제 시간이 나온다.

0을 포함한 1000개 값이므로 주기는 1000 tick이다. 900→100의 음수 차이를 그대로 시간으로 쓰면 틀리며, 모듈러스를 더해도 여러 바퀴 가능성은 별도 정보가 필요하다.

한 단계 더

tick 해상도와 긴 측정 범위의 절충을 계산하자. M=65536에서 tick을 1 µs→10 µs로 바꾸면 한 바퀴는 65.536 ms→655.36 ms로 늘지만 한 칸의 시간 구별은 거칠어진다. 실제 오차에는 클록 정확도·동기화·에지 지터도 필요하므로 이 값은 실측 정확도가 아니다.

소단원 5.2

ISR와 우선순위

중요한 외부 사건이 오면 지금 하던 계산을 잠시 멈추고 어떻게 처리할까?

준비 개념과 학습 목표

준비 개념

  • IRQ는 인터럽트 요청, ISR은 요청에 응답하는 처리 루틴이다. 선점은 현재 처리를 중단하고 더 높은 우선순위 처리를 실행하는 일이다.

  • 지연 latency는 사건에서 처리 시작까지의 시간이며 실행 시간과 다르다. 우선순위 숫자의 의미는 장치별로 확인한다.

학습 목표

  • 중첩 인터럽트의 중단·재개를 시간표로 계산한다.

  • 짧은 ISR과 후속 처리, 이벤트 기록의 차이를 설명한다.

높은 우선순위가 들어오는 순간을 표시한다

중첩이 허용되고 H가 L보다 높은 우선순위인 모형을 생각하자. L이 실행 중 H가 발생하면 L의 남은 실행 상태를 보존하고 H를 먼저 처리한 뒤 L로 돌아간다. 높은 우선순위가 오래 실행되면 낮은 ISR의 완료도 늦어진다. 우선순위는 일을 없애는 것이 아니라 순서를 바꾼다.

실제 처리 시작에는 하드웨어 진입, 인터럽트 마스킹, 더 높은 ISR, 문맥 저장 등 시간이 들 수 있다. 예제는 이 비용을 0으로 놓아 순서를 배우는 표다. 모든 CPU에서 낮은 숫자가 높은 우선순위라고 가정하거나, 종이의 0 지연을 실제 장치 보장으로 쓰지 않는다.

빠르게 기록하고 오래 걸리는 일은 넘긴다

ISR에서는 사건을 확인하고 필요한 데이터를 짧게 보관한 뒤 후속 처리에 알리는 설계가 흔하다. 예를 들어 캡처 값을 큐에 넣고 스레드가 나중에 표시·분석하게 할 수 있다. Zephyr는 FIFO·세마포어·workqueue 등을 통한 넘기기를 설명하지만 실제로 어떤 API가 ISR에서 허용되는지는 각각 확인해야 한다.

ISR이 잠들거나 후속 스레드의 결과를 기다리는 차단 호출을 하면 정상 스케줄링과 충돌할 수 있다. 작업을 넘긴 뒤 스레드가 즉시 시작하는지도 다른 준비 작업의 우선순위에 달린다. 짧게 넘기는 것은 후속 일을 삭제하거나 그 마감을 자동 보장하는 것이 아니다.

사건 하나와 사건 횟수는 다른 정보다

bool 플래그를 true로 만드는 두 사건은 소비 전에 연이어 오면 true 하나로 합쳐질 수 있다. 사건이 있었다는 정보만 필요하면 괜찮지만 두 번의 펄스를 세려면 카운터나 큐 등 다른 기록이 필요하다. 용량이 유한한 큐에는 가득 찼을 때의 정책도 있어야 한다.

volatile 표시는 공유 카운터의 읽기·증가·쓰기 전체를 원자적으로 만들지 않는다. ISR과 스레드의 접근에는 맞는 원자 연산이나 짧은 보호 구간이 필요하다. 하드웨어 pending 플래그를 지우는 방식도 칩마다 달라 무조건 0을 쓰라는 규칙을 만들지 않는다. 본문은 동기화 코드를 실행하여 증명한 결과가 아니다.

중간 과정을 따라가는 예제

L은 t=0부터 실행시간 5가 필요하다. H는 t=1에 발생하며 실행시간 2, H>L이고 중첩 가능하다. 모든 진입·전환 비용 0일 때 완료 시각과 L의 추가 지연을 구하라.

  1. L은 0..1에 1만큼 실행하여 4가 남는다.

  2. H는 t=1에 바로 선점하여 1..3에 실행하고 3에 완료한다. H의 시작 지연은 0이다.

  3. L은 3에 재개하여 남은 4를 실행하므로 t=7에 끝난다.

  4. H가 없을 때 L의 완료는 5였으므로 완료는 2만큼 늦어진다. L이 7만큼 CPU를 쓴 것은 아니며 실제 CPU 사용은 5다.

H 완료3, L 완료7이며 L의 완료 지연2다. 숫자는 이상적인 중첩 모형의 값이다.

종이와 본문으로 직접 해보기

같은 사건에서 L이 끝날 때까지 H가 마스킹된다고 정하자. H의 시작·완료·시작 지연을 계산하라. 소비 전에 두 사건이 bool 플래그를 true로 만들면 횟수도 2로 남는가?

힌트 보기

H 발생은 t=1이지만 시작은 L 완료 뒤다. 플래그의 가능한 값도 적는다.

풀이 보기

L은 0..5에 끝나고 H는 5..7에 실행한다. H 시작 지연은 5−1=4다. 두 번 true를 써도 최종 값은 true 하나이므로 횟수 2를 보관하지 못한다. 시간표와 정보 손실은 별개의 설계 검사다.

오해와 반례

ISR를 높은 우선순위로 두고 volatile을 쓰면 모든 지연과 데이터 경쟁이 사라진다.

마스킹된 H는 높은 우선순위여도 4만큼 기다린다. volatile 카운터의 증가 중간에 다른 접근이 끼어들면 갱신을 잃을 수 있다. 우선순위·마스킹·공유 기록의 원자성을 각각 확인한다.

한 단계 더

소단원 5.3

이벤트 기반 상태 설계

오래된 타임아웃이 새 작업을 취소한다면 어떤 정보를 빠뜨린 걸까?

준비 개념과 학습 목표

준비 개념

  • 상태는 현재 허용되는 반응을 결정하는 기억이다. 이벤트는 입력된 사건이며 전이는 현재 상태와 사건에 따른 다음 상태다.

  • 세대 번호 g는 작업을 새로 시작할 때 증가하는 식별자다. 이 종이 모형은 번호가 되돌아가지 않고 이벤트를 하나씩 순서대로 처리한다.

학습 목표

  • 상태·사건·조건·동작을 표로 표현한다.

  • 지연된 사건을 현재 작업의 사건과 구별한다.

같은 사건도 현재 상태에 따라 다르게 처리한다

Idle은 대기, Waiting은 작업 결과 대기, Done은 완료 확인 상태다. Idle에서 start를 받으면 g를 1 늘려 Waiting으로 가고 timeout(g)를 예약한다. Waiting에서 현재 g와 같은 done(g)를 받으면 Done으로 가고 타이머를 취소한다. Done에서 reset을 받으면 Idle로 간다.

Waiting에서 현재 g와 같은 timeout(g)를 받으면 Idle로 돌아간다. 다른 상태의 사건 또는 세대가 다른 done·timeout은 무시한다고 명시한다. 전이를 표에 없는 사건까지 적어야 도착 순서에 따라 임의로 상태가 바뀌는 것을 막을 수 있다. 취소가 이미 큐에 들어온 사건을 반드시 지운다고 가정하지 않는다.

긴 대기 대신 사건을 한 번씩 처리한다

상태 처리 함수가 외부 결과를 기다리며 오랫동안 멈추면 다른 버튼이나 리셋 사건도 처리하기 어렵다. 이벤트 방식에서는 지금 온 사건에 대한 짧은 전이만 수행하고 다음 사건을 기다린다. Zephyr의 버튼 예제는 이벤트 게시와 상태 실행을 나누어 이런 구조를 보여 준다.

실제 ISR가 사건을 전달하고 스레드가 상태를 갱신한다면 큐와 상태의 소유권을 정해야 한다. 본문은 단일 소비자가 한 번에 한 사건을 처리한다고 정했다. 이 조건 없이 여러 스레드가 같은 상태를 동시에 수정하면 표의 순차 추적만으로 안전하다고 할 수 없다.

작업의 신원을 상태와 함께 기억한다

Waiting이라는 이름만으로 어느 작업을 기다리는지는 알 수 없다. 첫 작업의 지연된 timeout(1)이 둘째 작업 Waiting에서 도착하면 세대 번호 없이 새 작업을 취소할 수 있다. 현재 g=2인지 비교하면 이전 사건을 걸러 낼 수 있다. 상태와 작업 식별자가 함께 충분한 기억을 이룬다.

무시가 모든 사건에 좋은 정책은 아니다. 기록·재시도·오류 전이 등이 필요한 시스템도 있다. 여기서는 입문용 단일 작업 모형의 정책을 전부 명시했다. 실제 번호 폭이 유한하면 wraparound와 오래된 사건의 생존 기간도 설계해야 하며 무한 정수라는 종이 조건을 그대로 장치에 적용하지 않는다.

중간 과정을 따라가는 예제

초기 Idle,g=0에서 start, done(1), reset, start, timeout(1), done(2)의 순서로 처리하라. 각 상태와 g를 기록하라.

  1. start 후 g=1, Waiting이며 timeout(1)을 예약한다.

  2. done(1)은 현재 세대이므로 Done,g=1이고 취소를 요청한다. reset 후 Idle,g=1이다.

  3. 둘째 start 후 Waiting,g=2이며 timeout(2)를 예약한다.

  4. timeout(1)은 세대가 달라 무시하여 Waiting,g=2를 유지한다.

  5. done(2)는 유효하여 Done,g=2다. 취소했던 이전 timeout이 이미 큐에 있어도 새 작업을 망치지 않았다.

마지막은 Done,g=2이며 이전 timeout(1)은 상태를 바꾸지 않는다.

종이와 본문으로 직접 해보기

Idle,g=0에서 start, timeout(1), done(1), start, done(1), timeout(2)를 추적하라.

힌트 보기

타임아웃 후 Idle에서 오는 done과 새 Waiting에서 오는 옛 done을 모두 구별한다.

풀이 보기

start→Waiting,g1, timeout1→Idle,g1, done1은 Idle이라 무시한다. 다음 start→Waiting,g2, done1은 세대가 달라 무시한다. timeout2는 현재 작업의 사건이므로 Idle,g2다. 종료 원인이 타임아웃이었는지 완료였는지 표로 확인한다.

오해와 반례

타이머 취소를 호출했으므로 오래된 타임아웃은 검사할 필요가 없다.

이미 전달 큐에 들어온 timeout(1)은 취소 뒤에도 도착할 수 있다. 둘째 Waiting,g2에서 단순 상태 검사만 하면 새 작업을 취소하지만 세대 검사까지 하면 무시한다. 취소 의미는 실제 API 계약에서도 따로 확인해야 한다.

한 단계 더

전이별로 상태·사건·guard 조건·동작·다음 상태의 다섯 칸을 그려 보자. 유효 완료와 타임아웃이 같은 시각에 오면 입력 큐 순서에 따라 먼저 처리한 사건이 결론을 정한다. 어느 사건을 우선할지 요구사항이 있다면 큐 규칙을 추가하고 다시 전이를 검토한다.
