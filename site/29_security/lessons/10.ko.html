소단원 10.1

인증서·체인·호스트 확인

배달원이 유효한 신분증을 보여 주어도 내가 주문한 가게의 배달원인지 확인해야 할까?

준비 개념과 학습 목표

준비 개념

  • 공개키와 서명

  • DNS 이름

  • 참·거짓의 논리곱

학습 목표

  • 신뢰 경로와 서비스 이름 검사를 구별한다.

  • 참조 이름과 SAN의 일치를 직접 판단한다.

  • 여러 검사를 모두 만족해야 하는 이유를 반례로 설명한다.

공개키를 누구의 것으로 받아들일까

인증서는 이름과 공개키 등 정보를 발급자의 서명으로 묶은 자료다. 인증서 자체는 공개해도 되는 정보이며, 해당 공개키의 개인키를 공개해도 된다는 뜻이 아니다. 인증서와 개인키를 같은 파일이라고 생각하면 배포 실수를 발견하기 어렵다.

신뢰는 종이 위에 신뢰한다는 문장이 있다는 이유로 생기지 않는다. 클라이언트는 사전에 신뢰한 앵커와 검증 정책을 출발점으로 삼는다. 서버가 낯선 자체 서명 인증서를 보내도 그 사실만으로 클라이언트의 신뢰 목록에 들어가지 않는다.

체인의 연결과 서비스 이름은 다른 질문

인증 경로 검증은 발급자와 서명, 유효 시각, CA 역할과 경로 제약 등을 검토한다. 본문에서는 상세 정책 전체를 구현하는 대신 각 검사의 결과가 문제에 주어진다고 가정한다. 폐기 여부도 필요한 정책에 따라 별도 확인해야 한다. 서명에 성공했다는 조건 하나로 모든 제약을 지우지 않는다.

호스트 확인은 검증된 공개키가 내가 접속하려던 서비스 이름에 해당하는지 묻는다. 참조 이름은 서버가 내민 이름을 그대로 복사하지 않고 URL이나 신뢰한 설정에서 만든다. 다른 서비스가 유효한 인증서를 내밀더라도 참조 이름이 다르면 원하는 서비스의 인증으로 받아들이지 않는다.

SAN과 와일드카드의 경계

DNS 이름은 SAN의 dNSName에서 비교하며 RFC9525 기준으로 Common Name만을 대체 이름으로 사용하지 않는다. ASCII DNS 이름의 대소문자는 구별하지 않는다. 이 절의 와일드카드 허용 모형은 왼쪽 첫 레이블 전체인 *만 인정하고, 그 별 하나가 정확히 한 레이블을 대신한다.

따라서 *.school.example은 lab.school.example에 맞지만 school.example이나 a.lab.school.example에는 맞지 않는다. IP 주소로 직접 접속하는 경우의 IP-ID는 SAN의 iPAddress 바이트와 비교한다. DNS 조회로 얻은 주소가 같다는 사실만으로 URL의 DNS 참조 이름을 IP 이름으로 바꾸지 않는다.

중간 과정을 따라가는 예제

참조 이름은 lab.school.example이고 현재는 가상 시각 50이다. 경로는 신뢰 앵커 R→중간 I→서버 L이다. I 유효 구간 [0,80], L 구간 [10,60], 서명·CA·정책·폐기 검사는 모두 성공으로 주어진다. L의 DNS SAN은 *.school.example이다. 이를 A라 하자. B는 A와 같지만 SAN이 shop.example이다. C는 이름과 시각이 맞지만 앵커가 신뢰되지 않는다. D는 A에서 L의 만료 시각만 40으로 바뀐다. 네 후보를 판단하라.

  1. A의 두 서명 연결과 나머지 경로 조건은 주어진 성공 입력이다. 시각50은 두 인증서 구간 안에 있다.

  2. A의 참조 이름 lab.school.example은 별이 lab 한 레이블을 대신하므로 맞는다. A를 승인한다.

  3. B는 경로가 맞아도 이름이 다르다. C는 이름이 맞아도 신뢰 출발점이 없다. D는50>40이므로 시각 조건에 실패한다.

  4. 네 개 중 승인1개, 거부3개다. 이는 실제 공개 서버를 검사한 통계가 아니라 가상 조건표의 결과다.

A만 승인한다. 경로·시간·이름 등의 논리곱에서 어느 한 필수 조건이 거짓이어도 승인할 수 없다.

종이와 본문으로 직접 해보기

A의 SAN을 유지한 채 참조 이름만 SCHOOL.EXAMPLE, LAB.SCHOOL.EXAMPLE, a.lab.school.example, shop.example으로 바꾸면 각각 맞는가? 그리고 IP로 직접 접속하는 참조192.0.2.7에 대해 SAN iPAddress192.0.2.8은 맞는가?

힌트 보기

별의 레이블 개수와 비교 대상 타입을 먼저 구별하라. 대소문자는 레이블 개수를 바꾸지 않는다.

풀이 보기

school.example은 별을 대신할 레이블이 없어 불일치, LAB.SCHOOL.EXAMPLE은 한 레이블 lab이어서 일치, a.lab.school.example은 두 레이블이어서 불일치, shop.example은 뒤 레이블도 달라 불일치다. IP의 마지막 바이트7≠8이므로 불일치다. 다섯 사례 중 이름 검사 성공은1개며 경로 검증은 별도다.

오해와 반례

신뢰된 CA가 서명했으면 어떤 도메인에 접속해도 그 인증서를 받아도 된다.

유효한 shop.example 인증서는 lab.school.example을 인증하지 않는다. 체인 성공과 이름 성공을 각각 표시하면 이 반례를 볼 수 있다. 반대로 이름이 맞아도 만료·폐기·신뢰 앵커·제약 실패가 있으면 승인할 수 없다.

자기점검

Common Name만 lab.school.example이고 DNS SAN에는 그 이름이 없다면 RFC9525 기준으로 대체할 수 있는가?

답과 이유 보기

아니요.

서비스 DNS 식별자는 dNSName SAN을 사용하며 Common Name으로 누락을 보충하지 않는다.

*.school.example은 school.example도 포함하는가?

답과 이유 보기

아니요.

왼쪽 별은 한 레이블을 대신해야 하며 빈 레이블을 대신하지 않는다.

A의 현재 시각이70이면 무엇이 달라지는가?

답과 이유 보기

L이 만료되어 거부한다.

I의 상한80 안에 있어도 L의 상한60을 넘으므로 전체 경로 조건을 만족하지 않는다.

한 단계 더

A와 같은 경로를 두 클라이언트가 받았으나 한 클라이언트만 R을 신뢰한다고 하자. 다른 조건은 같아도 판단은 달라질 수 있다. 신뢰 앵커가 검증 알고리즘의 입력이라는 점을 적고, 사용자가 임의 인증서를 신뢰 목록에 넣는 행동이 정책을 어떻게 바꾸는지 설명해 보자. 실제 인증서 설치는 하지 않는다.

소단원 10.2

키교환·채널 보장

공개키로 서버를 알아본 뒤 왜 연결마다 다른 비밀을 만드는가?

준비 개념과 학습 목표

준비 개념

  • 공개키와 개인키

  • 대칭키와 인증 태그

  • 모듈러 거듭제곱

학습 목표

  • 인증·키교환·트래픽 보호의 역할을 구분한다.

  • 작은 DH 모형의 공유값을 계산한다.

  • 전방향 안전성과 채널 끝점의 조건을 설명한다.

신원 확인과 연결 키 만들기

이 절은 TLS1.3의 인증서 기반 전체 핸드셰이크와 임시 DH 교환을 생각한다. 공개 인증서만 복사해서 전송하는 것과 개인키를 보유했음을 증명하는 것은 다르다. CertificateVerify는 핸드셰이크 문맥에 대한 서명 검증을 요구하며, Finished는 계산한 키와 앞선 핸드셰이크를 확인한다.

인증서의 개인키가 모든 본문 데이터를 직접 암호화하는 모형으로 읽지 말자. 연결에서 마련한 키 재료는 방향과 용도를 구별해 트래픽 보호에 사용된다. 아래 작은 정수 DH는 공유값을 이해하는 교육 예시이며 실제 TLS 그룹이나 안전한 키 크기, 키 유도 과정을 대신하지 않는다.

임시 비밀과 나중의 유출

임시 키교환과 안전한 키 유도, 필요한 키 삭제가 이루어진 연결에서는 장기 인증키가 나중에 유출되어도 과거 연결 키가 함께 드러나지 않도록 설계할 수 있다. 이를 전방향 안전성이라고 한다. 공격자가 당시 기록한 공개 교환값과 나중의 인증키를 얻었다는 상황을 구별해서 생각한다.

연결 트래픽 키 자체나 평문 기록이 남아 유출되면 그 데이터는 보호되지 않는다. TLS1.3이라는 이름만 보고 모든 모드에 같은 보장을 붙이지 않는다. 임시 DH 없이 PSK만 쓰는 모드와 0-RTT 데이터에는 관련 한계가 있으며, 0-RTT는 재전송 위험도 별도로 다뤄야 한다.

보호 구간은 두 TLS 끝점 사이

트래픽 보호는 비밀성과 변조 탐지를 목표로 하지만 서버의 저장 데이터나 브라우저 내부에 도착한 평문을 자동으로 보호하지 않는다. 사용자 계정의 권한 검사와 서버가 정직한지 여부도 별개다. 길이·시각 같은 통신 관찰 정보가 모두 사라지는 것도 아니다.

브라우저와 프록시에서 TLS가 끝나고 프록시가 애플리케이션에 평문으로 전달한다면, 뒤 구간은 앞 연결의 보호 밖이다. 뒤에도 별도 TLS를 구성할 수 있으나 두 연결은 다른 키와 끝점을 가진다. 프록시는 두 구간 사이에서 평문을 볼 수 있으므로 최종 애플리케이션만 읽는 하나의 종단간 비밀 통신이라고 주장하지 않는다.

중간 과정을 따라가는 예제

가상 DH는 p=23,g=2다. 클라이언트 임시 지수 a=3, 서버 임시 지수 b=5이며 공개값은 A=g^a mod p,B=g^b mod p다. 공개값과 양쪽 공유값을 구하라. 별도 인증서·이름·CertificateVerify·Finished 검사는 모두 성공으로 주어지고, 이 작은 군은 실사용에 안전하지 않다고 가정한다.

  1. A=2³ mod23=8이다. B=2⁵ mod23=32 mod23=9다.

  2. 클라이언트는 B³=9³=729에서23×31=713을 빼16을 얻는다.

  3. 서버는 A²=64 mod23=18, A⁴=18² mod23=2, A⁵=2×8 mod23=16을 얻는다.

  4. 양쪽 공유값은16이지만 실제 TLS는 이 값을 그대로 데이터 키로 쓰지 않고 키 유도와 방향 분리를 한다. 작은 지수는 공개값에서 쉽게 탐색되므로 실용 보안 증명이 아니다.

공개값A=8,B=9, 공유값16이다. 인증 성공은 입력 조건이며 DH 계산 자체가 이름 검증을 제공한 것은 아니다.

종이와 본문으로 직접 해보기

같은 작은 군에서 두 번째 연결의 a=2,b=3을 쓰면 A,B,공유값은 얼마인가? 또한 브라우저→프록시→앱→DB의 세 링크 중 앞 두 링크만 각각 TLS이고 앱→DB는 평문이라면 보호된 링크 수와 보호 밖 링크 수를 세어라.

힌트 보기

공유값은 B^a 또는 A^b로 구한다. 링크 수는 노드 수보다1개 적고 각 TLS 끝점을 따로 표시한다.

풀이 보기

A=4,B=8, B²=64 mod23=18이고 A³도64 mod23=18이다. 첫 연결16과 둘째18이 다르지만 임의 모든 연결에서 항상 다른 값이라는 보편 주장은 아니다. 세 링크 중 TLS2개, 평문1개다. 프록시·앱·DB에서 각자 처리하는 평문과 저장 데이터 보호는 링크 수와 별도다.

오해와 반례

TLS만 사용하면 데이터가 서버에 저장된 뒤에도 안전하고, 서버도 사용자를 인증한 것이다.

채널 끝점이 읽은 평문이 로그에 저장되면 네트워크 암호화만으로 로그 유출을 막지 못한다. 서버 인증서 기반 기본 연결에서 클라이언트의 사용자 신원은 별도 로그인이나 요청된 클라이언트 인증 등의 문제다. HTTP 권한 검사도 TLS 성공으로 대신할 수 없다.

자기점검

CertificateVerify를 실패로 주면 DH 공유값이 양쪽16이어도 인증서 기반 연결을 계속 승인할 수 있는가?

답과 이유 보기

아니요.

공유 계산 일치만으로 서버의 인증키 보유와 핸드셰이크 서명을 검증하지 못한다.

임시 키가 삭제됐어도 과거 평문 로그가 유출되면 전방향 안전성이 그 로그를 감추는가?

답과 이유 보기

아니요.

키교환의 과거 연결 키 보호와 저장 평문 보호는 다른 문제다.

한 단계 더

양쪽 DH 값은 맞지만 인증 검사를 모두 생략한 모형을 상상하자. 중간자가 각각 다른 키교환 상대를 맡아 두 공유값을 만들 수 있다. 공유값을 계산할 수 있다는 능력과 원하는 상대와 공유했다는 사실을 구별해 그려 보자. 실제 가로채기·서비스 실험은 하지 않는다.

준비 개념과 학습 목표

준비 개념

  • 인증서와 개인키의 구별

  • 시간선

  • TLS 끝점과 로그

학습 목표

  • 인증서 교체와 실제 활성 상태를 구별한다.

  • 개인키 공유·만료·검증 비활성화의 위험을 설명한다.

  • 가상 점검 결과와 실제 운영 검증을 구분한다.

파일을 바꾸는 것과 제공 상태를 바꾸는 것

배포에는 인증서뿐 아니라 키의 보관 위치, 읽기 권한, 서비스가 실제 제공하는 체인과 갱신 상태가 포함된다. 새 인증서 파일을 저장해도 실행 중 프로세스가 이전 값을 계속 쓰면 이용자가 보는 상태는 바뀌지 않는다. 따라서 파일 목록과 외부에서 제공되는 상태를 분리해 기록한다.

아래 일정은 가상 장애 계산이며 특정 서버의 재시작 동작을 보편화하지 않는다. 갱신 뒤 각 인스턴스의 인증서 이름·만료·체인과 설정을 확인할 계획이 필요하다. 라이브러리 패치와 설정 검사도 계획 항목이며, 아직 검사하지 않았다면 통과로 적을 수 없다.

공유한 개인키는 함께 대응해야 한다

공개 인증서는 여러 사람이 알아도 되지만 개인키는 접근을 제한해야 한다. 하나의 개인키를 서로 다른 신뢰 수준의 서비스와 여러 인스턴스에 복사하면, 한 사본의 유출이 다른 사용처의 인증에도 영향을 줄 수 있다. 와일드카드의 편리함을 키 관리 범위와 함께 판단한다.

만료됐거나 잘못된 인증서 오류를 없애려고 클라이언트 검증을 끄면 경고만 없어진 것이 아니라 상대 확인 조건을 지운 것이다. 내부 CA도 승인된 신뢰 정책과 배포가 필요하다. 개인키가 유출됐을 때 새 키를 쓰고 해당 사용처와 인증서 폐기·교체를 관리하는 계획을 세우며, 파일명을 바꿨다는 이유만으로 유출된 키가 무효가 됐다고 생각하지 않는다.

암호화 이후의 데이터 경로 확인

로그인 화면만 TLS로 보호해도 이후 요청에 세션 비밀이 평문으로 나가면 채널 보호가 끊긴다. TLS 페이지가 평문으로 읽은 외부 자원을 포함하는 상황과 저장 캐시도 검토할 수 있다. 민감한 응답의 HTTP 캐시 정책은 전송 암호화와 별도다.

교육 점검표에는 가정, 관찰하려는 항목, 기대 결과, 실제 수행 여부를 따로 둔다. 배포한 실제 서비스가 없으면 인증서 교체 시험이나 키 접근 차단 시험을 하지 않았다고 기록한다. 계획이8개라는 수치가 통과8개를 의미하지 않는다. 종이 표의 이상을 찾는 연습과 실제 운영 증거를 분리한다.

중간 과정을 따라가는 예제

가상 시각은 시간 단위다. 같은 개인키K를 쓰는 인스턴스 A/B/C가 있으며 기존 인증서는100시까지 유효(100시 포함)하다. 새 인증서는90시부터200시까지 유효하다. 새 파일은95시에 세 곳에 저장됐지만 실제 제공 전환은 A96시/B104시/C109시다. 현재105시의 실패 인스턴스와 각 만료 이후 지연 길이를 계산하라. 다른 검사는 모두 성공이며,100시 초과부터 새 제공 전환 직전까지 기존 인증서는 만료로 거부된다고 정한다.

  1. A는96시에 바뀌어 기존 유효 기간과 새 유효 기간이 겹치므로 만료 공백0시간이다.

  2. B는100시 초과부터104시 전환 전까지 공백 길이4시간이다. C는109시까지 공백 길이9시간이다.

  3. 105시에 A와B는 새 인증서를 제공하고 C만 기존 만료 인증서를 제공하므로 세 곳 중 실패1개다.

  4. 각 공백 길이 합은0+4+9=13 인스턴스·시간이다. 요청 발생률을 주지 않았으므로 실패 요청 수나 사이트 전체 중단13시간으로 해석할 수 없다.

105시에는 C만 실패, 만료 공백은 A0/B4/C9시간, 합13 인스턴스·시간이다. 파일 저장95시만으로 전환 완료를 판단할 수 없다.

종이와 본문으로 직접 해보기

B/C의 제공 전환을 각각99시/102시로 앞당기면 공백 길이와 합은 얼마인가? 또 K가 A/B/C에 각각1사본 있고 백업에2사본 있다면 총사본 수는 얼마인가? 공개 인증서만 있는 문서함1개는 키 사본에 포함하지 않는다.

힌트 보기

전환이100시 이하이면 만료 공백0이고,100시보다 늦으면 차이가 길이다. 인증서와 개인키를 따로 세어라.

풀이 보기

A0/B0/C2시간으로 합2 인스턴스·시간이다. 개인키 사본은3+2=5개이며 공개 인증서 문서함은 더하지 않는다.5개 사본 전부의 접근·교체 책임을 파악해야 한다. 서로 다른 키로 분리하면 공유 범위를 줄일 수 있으나 실제 보안 검증을 완료했다는 뜻은 아니다.

오해와 반례

새 인증서를 저장했고 개인키 파일 이름도 바꿨으니 운영 교체와 유출 대응이 끝났다.

파일 저장과 실제 제공은 다른 상태다. B/C가 오래된 인증서를 제공한 시간선이 반례다. 이름만 바꾼 개인키가 같은 비밀값이면 공격자가 갖고 있는 사본은 사라지지 않는다. 새 키와 모든 사용처 파악·적절한 폐기 및 교체 확인이 필요하며 검증 비활성화는 해결이 아니다.
