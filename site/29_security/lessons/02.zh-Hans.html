小节 2.1

密码·MFA·会话

询问两次密码就算双因素认证吗？

预备知识与学习目标

预备知识

  • 主体是账户或服务等被授予权限的对象。身份认证确认的是对所声称主体的认证手段的控制。
  • 秘密是不应公开的值；哈希是将输入转换为固定长度值的函数。同一输入得到同一哈希，并不意味着具有恢复原文的功能。
  • 会话是将认证后连续的交互联系起来的状态。时间差 t−s 必须采用相同的时间基准和单位计算。

学习目标

  • 区分认证因素的种类与数量。
  • 分别判定会话的总寿命和不活动超时。

密码校验的契约

服务器使用与账户绑定的密码验证信息。它不以明文保存密码，而使用包含 salt（盐）和成本参数的专用密码哈希方法进行验证。盐使跨账户共享预计算结果变得更困难，不必像密码一样保密。保存了哈希也不能消除对弱密码的候选猜测。

认证结果是控制该账户认证手段的证据。是否允许修改特定文档属于另一个授权问题。公开资料也可以在没有认证的情况下允许访问，因此不能得出所有资源都需要登录的结论。

两个因素与认证后的风险

因素可分为所知、所持有、身体特征等不同类别。密码与 PIN 都属于知识因素，即使提出两个问题，也不是两个不同因素。密码和独立持有手段的验证，在适当的组合流程中可以构成两个因素。生物特征也要按其与实际认证设备及验证流程的结合方式处理。

仅有 MFA 这个名称不能保证抗钓鱼或防止会话被窃取。例如认证后发放的 bearer 会话秘密以出示者为准，窃取秘密的一方也可能使用它。受保护的信道、会话秘密保护、过期和重新认证，应与初始认证一起设计。

纸上会话的两种时间限制

本节的虚构服务器使用以整数分钟计量的单调时间。认证成功时设 created=last=t、valid=true。只有 valid 为真且 0≤t−created<12、0≤t−last<5 时，会话检查才成功。仅成功的会话检查将 last 更新为 t；失败则设 valid=false。这是自拟政策，不是 NIST 的时间值。

活动不会延长总寿命，只会更新不活动计时。退出登录将 valid 设为 false。边界不含等号，因此恰好达到 5 分钟或 12 分钟时检查失败。这是排除时间倒退与并发检查的顺序模型；实际分布式服务器还需要时钟、原子性和恢复契约。

逐步推导的例题

在 t=0 通过双因素认证建立会话。依次在 t=4,9,10 检查，追踪上述政策的结果和 last。

  1. t=0：设 created=last=0、valid=true。认证成功本身不会授予修改所有资源的权限。
  2. t=4：总经过时间 4<12，不活动时间 4<5，检查成功，last=4。
  3. t=9：总经过时间 9<12，但不活动时间 9−4=5 达到严格边界，因此失败，valid=false。
  4. t=10：即使再次出示秘密，由于 valid=false 仍然失败。last 保持最后一次成功的值 4。

结果为成功、失败、失败，last=4。重新建立会话必须来自新的认证流程。

用纸笔和正文动手试一试

从新会话 created=last=0 开始，把 t=4,8,12 的检查结果写成表格。再解释密码+PIN 能否称为两个因素。

查看提示

每次成功仅改变 last；最后一次先检查总寿命。

查看解答

t=4 成功，last=4；t=8 成功，last=8；t=12 因总寿命达到 12 而失败。密码和 PIN 都属于知识因素，因此不是两种因素。

常见误解与反例

已经通过 MFA，即使会话秘密泄露也安全。

在 bearer 会话中，出示窃取秘密的一方可能被允许访问。加强初始认证与保护认证后的会话是两个不同边界。

检查理解

密码与 PIN 是两种因素吗？

查看答案与理由

不是。

两者都是证明所知值的知识因素。

有效会话 created=0、last=8，在 t=12 检查会怎样？

查看答案与理由

失败。

不活动时间 4 可接受，但总寿命 12 不满足 <12。

仅凭认证成功就可以修改他人的文档吗？

查看答案与理由

没有另外的权限就不允许。

确认账户与授权主体、对象、操作是不同的判定。

进一步探索

会话的不变式是在成功后 created≤last≤t，并且没有新的认证时 created 不变。创建时 created=last=t，因此成立。成功检查前 t≥last≥created；成功后把 last 改成当前 t，仍保持不等式。失败与退出登录都不改变 created 和 last，也不允许之后再成功。这一归纳论证只针对单调时间的顺序模型。若通过重新认证重设寿命，必须说明新认证的强度和旧会话的废止政策。不能仅凭这张虚构时间表声称满足实际服务的 NIST 适用范围及各 AAL 要求。

小节 2.2

访问控制·角色·capability

被称为教师，就可以修改所有学生的成绩吗？

预备知识与学习目标

预备知识

  • 对象是受保护的文档、记录等资源。操作是 read 或 update 等针对资源执行的运算。
  • R 的子集 R′⊆R 表示 R′ 的每个元素也属于 R。{read}⊆{read,update} 为真。
  • 角色是将共同权限分组授予多个主体的分类。ACL 是附在对象上的按主体列出的许可列表。

学习目标

  • 建立包含主体、对象、操作和情境的许可条件。
  • 比较基于角色的许可与 capability 的权限缩减。

谁可以对什么做什么

访问控制把请求的主体 u、对象 o、操作 a 和情境与政策 P 对照。默认拒绝模型仅在明确的许可条件为真时放行。请求中的 owner 或 role 字符串必须与可信服务器信息区分。难以猜测的对象编号不能代替权限检查。

在虚构学校中，学生可以 read 自己的成绩，但不能 update。教师可以 read 或 update 自己负责班级的成绩。因此，除了角色，还需要所有权关系或班级关系。服务器认证主体后查询实际对象的班级，再作判定。

角色与对象上的列表

RBAC 通过用户→角色和角色→操作的关系管理共同规则。即使角色相同，没有附加对象范围也可能把权限扩展到别的班级。ACL 列出对特定对象允许哪些主体执行哪些操作。这两者是政策表示方法，其名称不会自动保证实现正确。

本模型允许学生 s 在 owner(o)=s 时 read；允许教师 T 在 class(o)=assigned(T) 时 read/update。其他情况拒绝。所有受保护操作的入口都必须经过这一判定；仅隐藏界面按钮并不能实施服务器政策。

capability 与缩减权限

capability 是不可伪造的、指向特定对象及其操作权限的凭证。这里假定一种抽象凭证，其对象编号、权限集合和过期时间由可信发行方发放并可验证。只在普通 JSON 中写下权限，不会产生不可伪造性。若采用 bearer 方式，权限会传给持有它的一方，因此传递和保管也属于政策范围。

在允许缩减权限的发行流程中，由原始 (o,R,e) 生成 (o,R′,e′) 时，要求 R′⊆R、e′≤e。验证者检查有效的发行/委托链，以及当前 t<e′。因此，缩减凭证允许的操作也属于原权限。不能通过任意编辑字符串更换对象或增加权限，是这一论证的关键前提。

逐步推导的例题

s 是学生，也是成绩 X 的所有者；T 是教师，负责班级 A。X 属于班级 A，Y 属于班级 B。判定请求 s/read/X、s/update/X、T/update/Y，以及 capability C=(X,{read,update},10) 的缩减 C′=(X,{read},8)。

  1. s/read/X 因 owner(X)=s 而允许。
  2. s/update/X 因学生规则中没有 update 操作而拒绝。
  3. T/update/Y 因 class(Y)=B≠A 而拒绝。仅有教师角色不予放行。
  4. C′ 保持同一对象，权限为子集，且 8≤10，是有效缩减的候选。验证可信发行链后，t=7 的 read 允许，t=8 因过期而拒绝。这里 t 是时间，与教师名称 T 不同。

前三个请求分别允许/拒绝/拒绝。capability 的 read 也需要凭证验证和时间条件。

用纸笔和正文动手试一试

从 C=(X,{read},10) 出发，在 (X,{read,update},9)、(Y,{read},9)、(X,{read},11) 中选择有效的缩减候选。

查看提示

检查权限包含、对象相同、过期时间不增加这三个条件。

查看解答

都不合适。第一个增加 update，第二个更换对象，第三个延长过期时间。原始凭证本身或 (X,{read},9) 满足条件，但还需要验证发行链。

常见误解与反例

隐藏对象 ID 或检查教师角色后，访问控制就完成了。

知道其他班级对象 ID 的教师可以通过角色检查，却违反班级关系。必须在服务器实际使用对象的位置检查范围条件。

检查理解

s/read/X 中，X 的所有者变成另一名学生时怎样？

查看答案与理由

拒绝。

当前 owner(X)=s 条件为假。

R′⊆R 证明了权限缩减的什么性质？

查看答案与理由

缩减凭证的许可操作包含在原凭证的许可操作中。

若 a∈R′，按子集定义有 a∈R。

任意写有权限列表的文件就是 capability 吗？

查看答案与理由

本身不是。

需要不可伪造的发行和验证，或受保护对象引用等实施依据。

进一步探索

连续缩减权限时保持 R2⊆R1⊆R0、e2≤e1≤e0。确实，若 a∈R2，则 a∈R1，再有 a∈R0。若 t<e2，则 t<e1、t<e0 也成立。在每一步保持同一对象和有效发行链的前提下，重复这一论证可知任意有限委托步骤都不会产生新的操作权限或更晚的过期时间。然而，原凭证被窃取、违反禁止委托的规则、对象含义变化、撤销传播，都不能仅靠包含关系解决，需要另外的契约。

小节 2.3

权限提升与审计

仅凭一条拒绝日志，就能确定攻击者是谁吗？

预备知识与学习目标

预备知识

  • 权限提升是获得政策不允许的更广访问。垂直提升指更高角色，水平提升指访问同一层级他人的资源。
  • 审计记录是供之后追踪所观测事件的资料。记录的主体标识不是对实际人的完整证明。
  • 原子转换是模型中不会被其他转换插入中间的一步。政策版本是区分采用哪组规则作判定的编号。

学习目标

  • 区分请求输入与可信角色信息。
  • 说明检查与使用的边界，以及日志的证据范围。

提升与合法权限变更

教师按批准流程获得新的负责班级，是正常权限变更。相反，若服务器仅相信客户端发来的 role=admin 就允许管理员操作，这便是垂直权限提升。访问其他学生成绩而非自己的成绩属于水平提升，同样违反主体、对象、操作政策。

防御模型使用认证取得的服务器主体，以及服务器当前的角色和关系。权限授予本身也需要规定谁可以向谁授予什么范围。若把授予权限的功能与普通文档修改权限混为一谈，最小权限设计便会失效。

检查后、写入前的间隙

通过权限检查后，实际写入前仍可能撤销权限。要求检查时允许与要求使用时也允许，是两种不同政策。本节选择使用时政策，把当前版本的检查和修改合为一个原子转换。若撤销先发生，后续写入拒绝。

读取了版本 v 这一事实本身不会产生原子性。实际实现需要检查与更新同步、事务，或基于版本比较的冲突处理与失败契约。这里的顺序原子表说明该契约的含义，不是实际数据库或操作系统的性能及并发安全测试。

审计能说明什么

审计按规定格式保存请求标识、观测到的主体、对象、操作、允许/拒绝、原因、政策版本等。若原样记录密码或 bearer 令牌，日志就会成为新的泄露资源。还应防止不加处理地记录输入换行，使其看起来像伪造事件的问题。

限制记录访问、检测修改和保留政策可提高资料可信度，但记录本身不能防止违规或确定行为人。账户可能被窃取，观测点之外的事件也可能缺失。不能仅凭不同机器的时间戳确定全部因果顺序；本例的序号只限于单个服务器所观测的顺序。

逐步推导的例题

在政策 v0 下，学生 s 不能修改 X。依次原子处理以下请求与权限变更：s 携带 role=admin 请求修改 X；可信管理员授予 s 修改 X 的权限(v1)；s 修改 X；管理员撤销(v2)后 s 再修改 X。实际角色依据仅使用服务器信息。

  1. 第一条请求不把客户端 role 当作权限依据。在 v0 下拒绝，X 不变。
  2. 拥有政策管理权限的管理员通过授予转换建立 v1。这是获批准的权限变更。
  3. s 的下一次修改在当前 v1 下允许。成功审计事件记录主体 s、对象 X、操作 update、版本 v1。
  4. 撤销在 v2 完成后，再次修改拒绝。单个服务器的审计顺序和政策版本展示判定依据，却不能证明是名为 s 的人亲自发出了请求。

结果为拒绝、正常授予、允许、撤销后拒绝。在此模型中失败的修改不会改变 X。

用纸笔和正文动手试一试

只在 v1 下通过检查的请求还在等待时，v2 撤销已先完成。比较缓存检查结果后直接写入与使用时原子重查的结果。再解释是否可以在日志中记录密码。

查看提示

本节政策要求使用时有权限。区分过去通过检查的事实与当前许可条件。

查看解答

仅相信缓存可能允许违反当前政策的写入。在 v2 下原子重查则拒绝。不要直接记录密码，用请求 ID、判定原因等最少信息完成审计目的。

常见误解与反例

有审计日志就能防止权限违规并确定实际行为人。

错误放行的请求也可以出现在日志里，因此记录不同于预防。即使日志留下被窃取账户的主体 ID，断定账户所有者是实际行为人仍需要另外的证据。

检查理解

请求字段 role=admin 是管理员权限的依据吗？

查看答案与理由

不是。

必须检查可信服务器政策与主体关系。

在使用时政策下，撤销后仅相信过去检查结果的写入安全吗？

查看答案与理由

它不能保证该契约。

没有反映检查与使用之间的政策变更。

审计应记录原始 bearer 令牌吗？

查看答案与理由

不直接记录。

读取令牌的一方可能滥用会话，使审计成为泄露路径。

进一步探索

受保护写入的不变式是：“每次成功转换的主体、对象、操作，都曾由该转换使用的政策版本允许。”初始没有成功记录，没有需要检查的成功写入，因此条件成立。如果下一转换是拒绝或政策变更，没有新的成功写入，先前记录按其版本作出的判定也不变。如果下一转换是成功写入，因为只在同一原子转换内通过当前政策检查才允许写入，新记录也满足条件。因此，在所有入口都经过同一判定且检查与使用原子的前提下，可归纳证明该不变式。这不表示后来的撤销会追溯使过去写入失效。审计存储失败时拒绝敏感写入还是记录到另一个队列，属于服务契约；若记录与写入缺乏原子性和持久性，不能仅凭一个普通函数调用就声称两者一起成功。
