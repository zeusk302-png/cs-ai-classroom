소단원 7.1

origin·cookie·browser boundary

같은 회사 사이트라면 다른 페이지의 비밀 자료도 읽을 수 있을까?

준비 개념과 학습 목표

준비 개념

  • URL은 scheme·host·port·path로 나눌 수 있다.

  • cookie는 브라우저가 범위 조건에 맞는 요청에 첨부하는 값이다.

학습 목표

  • origin을 세 요소로 비교한다.

  • cookie 범위와 origin 경계가 다름을 설명한다.

주소의 경로만 바꾸었는데 cookie가 사라지는 이유는 무엇일까요?

같은 origin인지 확인할 때는 HTTP(S) 주소의 scheme·host·유효 port를 비교한다. 경로와 query는 그 묶음에 들어가지 않는다. 그러나 cookie의 전송 조건에는 경로가 들어간다. 이 때문에 같은 origin인데 cookie가 없는 요청과 다른 origin인데 같은 cookie를 보낼 수 있는 요청이 모두 가능하다.

아래에서는 보통의 HTTP(S) 문서용 주소, 이미 정상 저장된 cookie, 같은 site 문맥과 충족된 다른 전송 조건을 가정한다. opaque origin, localhost 예외와 추가 브라우저 차단은 다루지 않는다. 전송 조건을 통과했다는 판정은 서버가 유효 세션으로 승인했다거나 script가 응답을 읽었다는 판정이 아니다.

먼저 확인할 개념
  • origin과 cookie 범위

    scheme·host·port와 Domain·Path의 서로 다른 비교 항목을 확인한다.

  • 세션과 서버 상태

    cookie가 첨부된 다음의 유효성·권한 확인을 연결한다.

브라우저가 나누는 경계

보통의 HTTP(S) URL에서 origin은 scheme, host, 유효 port의 묶음이다. https의 생략된 port는 443으로 비교한다. path와 query가 바뀌어도 같은 묶음이면 같은 origin이다. 여기서는 opaque origin이나 file URL 같은 특수 경우를 다루지 않는다.

Same-origin policy는 다른 origin의 자료를 마음대로 읽는 것을 제한한다. 그러나 외부 그림 삽입이나 링크 이동·일부 form 전송까지 모두 금지하는 규칙은 아니다. 요청이 발생한 사실과 호출한 script가 응답 내용을 읽을 수 있는 사실을 따로 적어야 한다.

cookie는 별도 범위로 간다

Domain을 생략한 cookie는 설정한 host에 한정된다. Domain을 허용된 상위 domain으로 지정하면 그 domain과 하위 host에 전달될 수 있다. cookie의 host 범위에는 origin처럼 port가 포함되지 않는다. Path도 전송할 경로를 좁히지만 같은 origin 내부의 강한 비밀 경계가 아니다.

Secure는 보통 HTTPS 전달을 요구하고 HttpOnly는 script의 cookie 값 접근을 제한한다. HttpOnly cookie도 조건에 맞는 HTTP 요청에 첨부될 수 있다. SameSite는 origin과 별개인 site 기준이며 교차 site 요청의 첨부 조건을 다룬다. 아래 계산은 same-site 문맥으로 다른 제한이 없다는 가정이다.

경계 안의 신뢰도 확인한다

같은 origin에서 실행되는 script는 대체로 그 origin의 자원에 강한 권한을 가진다. 그러므로 자료를 HTML에 무심코 넣어 script로 실행되게 하면 origin 경계를 유지하면서도 피해가 생길 수 있다. 외부 코드를 로드할 때도 어떤 권한으로 실행되는지 살펴야 한다.

Same-origin policy, cookie 속성, 서버의 권한 확인은 서로 다른 단계다. 브라우저가 읽기를 막았다는 이유로 서버가 요청을 처리하지 않았다고 결론 내리거나, host-only cookie라는 이유로 서버의 사용자 확인을 생략하면 안 된다.

중간 과정을 따라가는 예제

기준 URL은 https://learn.example/a다. 후보 https://learn.example:443/b, http://learn.example/a, https://api.learn.example/a, https://learn.example:8443/a의 origin을 비교한다. host-only Secure cookie sid, Path=/class가 있다고 하자.

  1. 기준 묶음은 (https,learn.example,443)다. 첫 후보는 path만 다르므로 같은 origin이다.

  2. 둘째는 scheme/유효 port가 다르고, 셋째는 host가 다르며, 넷째는 port가 다르므로 나머지 셋은 다른 origin이다.

  3. same-site 문맥이고 cookie의 다른 조건도 충족한다고 가정하면 https://learn.example/class/1에는 sid를 첨부한다. https://api.learn.example/class/1에는 host-only 조건 때문에 첨부하지 않는다.

  4. https://learn.example:8443/class/1은 다른 origin이지만 cookie의 host·path·Secure 조건을 만족하여 sid가 첨부될 수 있다. /classroom은 /class와 경로 경계가 달라 일치하지 않는다.

origin은 첫 후보만 같다. cookie 첨부 범위는 origin 비교와 같지 않다.

조건을 바꾸어 비교하기

경로 경계와 query를 나누기

같은 host의 HTTPS 요청 /lab, /lab/, /lab/a?next=/other, /lab2, /other?next=/lab에 Path=/lab cookie를 붙일 수 있는가?

  1. 정확히 /lab인 경로는 일치한다.

  2. /lab/와 /lab/a는 다음 문자가 /이므로 일치한다. query는 경로 비교에 넣지 않는다.

  3. /lab2는 다음 문자가 2이고 /other는 접두가 달라 일치하지 않는다.

앞의 세 요청만 경로 조건에 일치한다. query에 /lab이 있다는 이유로 /other가 일치하지 않는다.

비교할 점

단순한 부분 문자열 검색과 cookie의 경로 일치 규칙은 다르다.

Domain을 넓혀도 origin은 그대로

school.example가 Domain=school.example, Path=/lab, Secure cookie를 저장했다. https://sub.school.example/lab 요청과 https://school.example:9443/lab 요청을 기준 origin과 비교하라.

  1. sub.school.example는 하위 host라 Domain 범위에 들어간다.

  2. 9443 요청은 같은 host라 cookie 범위에 들어간다.

  3. 두 요청은 각각 host와 port가 달라 기준 origin과는 다르다.

다른 조건이 충족되면 둘 다 cookie 전송 대상이고 둘 다 다른 origin이다.

비교할 점

Domain 속성은 origin의 host를 바꾸는 기능이 아니라 cookie 범위를 지정하는 기능이다.

종이와 본문으로 직접 해보기

sid를 Domain=learn.example, Path=/class, Secure, HttpOnly로 바꾼다. same-site HTTPS 문맥에서 api.learn.example/class/x, learn.example/classroom, learn.example:8443/class를 비교하고 script의 sid 읽기를 판단한다.

힌트 보기

Domain은 하위 host를 포함하고 Path는 문자열 일부가 아니라 경로 경계까지 확인한다.

풀이 보기

첫 URL은 하위 host와 경로가 맞아 첨부 대상이고, 둘째는 Path 불일치다. 셋째는 port와 무관하게 첨부 대상이다. HttpOnly 때문에 document.cookie로 sid 값을 직접 읽을 수 없지만 허용되는 요청에는 첨부될 수 있다.

오해와 반례

다른 origin이면 cookie도 절대 전송되지 않는다.

port만 다른 두 URL은 다른 origin이면서 cookie host 범위를 공유할 수 있다. 반대로 같은 origin도 Path 조건 때문에 특정 요청에 cookie가 없을 수 있다.

스스로 풀어보기

먼저 답과 이유를 적고, 필요한 만큼 힌트를 한 단계씩 열어 보세요.

연습 1 · 값과 상태 예측

기준은 https://school.example/lab이다. https://school.example:443/x?y=1과 https://school.example:9443/lab의 origin을 비교하고, 위 표의 sid가 각 요청에 전송될 수 있는지 구하라.

힌트 1

생략된 https port는 443이다.

힌트 2

cookie Path=/lab을 URL 경로와 따로 비교한다.

풀이와 답 확인

  1. 첫 요청은 같은 origin이지만 /x라 sid 경로 조건에 맞지 않는다.

  2. 둘째 요청은 다른 origin이지만 host·Secure·/lab 조건에 맞는다.

첫 요청은 같은 origin/전송 범위 아님, 둘째는 다른 origin/전송 범위이다.

흔한 오답에서 다시 생각하기

같은 origin이면 sid가 반드시 있다.

cookie 전송에는 경로·속성·저장 여부 등의 별도 조건이 있다.

연습 2 · 오류 찾아 고치기

개발자가 HttpOnly가 설정되었으므로 이 cookie는 서버에도 전달되지 않으며 CSRF 방어도 끝났다고 적었다. 두 결론을 고쳐라.

힌트 1

script가 값을 읽는 일과 브라우저가 요청에 붙이는 일은 다르다.

힌트 2

서버의 상태 변경 요청 검증을 따로 본다.

풀이와 답 확인

  1. HttpOnly는 script의 cookie 값 접근을 제한한다.

  2. 조건을 만족하는 HTTP 요청에는 여전히 첨부될 수 있다.

  3. 상태 변경의 권한과 CSRF 검증을 별도로 설계한다.

HttpOnly를 전송 금지나 완전한 CSRF 방어로 해석하지 않는다.

흔한 오답에서 다시 생각하기

script가 cookie 값을 못 읽으면 어떤 인증 요청도 못 보낸다.

브라우저가 첨부하는 인증값을 script가 직접 읽을 필요는 없다.

연습 3 · 직접 만들어 보기

학교가 수업 서비스와 신뢰하지 않는 별도 서비스를 같은 host의 다른 port에 두려고 한다. 민감한 cookie가 port 경계로 격리될 것이라는 계획의 문제와 수정 방향을 설명하라.

힌트 1

origin의 port와 cookie의 host 범위를 비교한다.

힌트 2

추가적으로 분리된 host와 서버 권한 정책을 생각한다.

풀이와 답 확인

  1. 다른 port는 다른 origin이지만 cookie를 port별로 격리하지 못한다.

  2. 신뢰 경계가 다른 서비스는 분리된 host와 좁은 host-only 범위를 검토한다.

  3. 그 계획에서도 서버 세션 유효성·권한과 각 접근 경로를 확인한다.

port 분리만을 민감 cookie의 보호 경계로 삼지 않는다. host와 정책을 포함하여 신뢰 경계를 설계한다.

흔한 오답에서 다시 생각하기

port를 바꾸면 Secure cookie는 그 port에만 속한다.

Secure는 전송 scheme 조건이며 port 범위를 만드는 속성이 아니다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

Path=/lab/와 Path=/lab cookie를 비교한다. 요청 /lab, /lab/, /lab/a, /lab2 각각에 대해 두 경로 조건을 판정하라.

힌트 1

끝의 /도 cookie 경로의 일부이다.

힌트 2

정확 일치와 접두 뒤 경계 규칙을 차례로 적용한다.

풀이와 답 확인

  1. /lab/ cookie는 /lab에는 불일치하며 /lab/와 /lab/a에는 일치한다.

  2. /lab cookie는 /lab·/lab/·/lab/a에 일치한다.

  3. 둘 다 /lab2에는 불일치한다.

/lab/의 일치 결과는 아니오·예·예·아니오이고 /lab은 예·예·예·아니오이다.

흔한 오답에서 다시 생각하기

두 Path는 비슷하므로 네 결과가 모두 같다.

문자 하나의 차이도 정확 일치와 접두 규칙을 바꾼다. 강한 보안 격리라는 주장과는 별개의 전송 판정이다.

내 말로 설명하기

origin과 cookie 표를 두 장으로 나누는 이유는 무엇인가?

설명 기준 확인

비교 항목이 다르기 때문이다. origin의 port와 cookie의 경로·host 범위를 혼동하면 서로 다른 결과를 놓친다.

Path로 신뢰하지 않는 응용을 강하게 격리할 수 있는가?

설명 기준 확인

전송 경로 제한을 강한 읽기·설정 격리로 확대할 수 없다. 같은 host의 다른 경로에 있는 응용의 신뢰도도 확인한다.

한 단계 더

origin 표와 cookie 표를 두 장으로 그려 같은-origin 여부·전송 가능 여부·script 값 읽기 여부를 각각 적는다. 같은 site인 하위 domain들도 서로 다른 origin일 수 있으므로 SameSite만으로 모든 하위 domain의 신뢰 문제를 해결할 수 없는 이유를 설명한다.

출처와 확인 범위
  • MDN: Same-origin policy

    실제 scheme/host/port 정의, 읽기·쓰기·삽입 구별, origin 별 storage와 cookie의 별도 domain 규칙 본문을 읽었다. 자체 문서용 URL 비교는 종이 계산이다.

  • MDN: Using HTTP cookies

    실제 세션 흐름과 Secure/HttpOnly/Domain/Path/SameSite 및 Path의 보안 경계 부적합 본문을 읽었다. localhost 등 예외를 사용하지 않는 HTTPS 문서용 호스트 모형이다.

세션·인증 흐름

로그인 창이 닫힌 다음 요청은 어떻게 같은 사용자임을 알까?

준비 개념과 학습 목표

준비 개념

  • HTTP 요청마다 서버에 새 메시지가 간다.

  • 인증은 사용자 확인이고 인가는 해당 행동의 허용 여부다.

학습 목표

  • 세션 ID와 서버 상태의 대응을 추적한다.

  • 로그아웃·만료·권한 확인을 분리한다.

로그인 뒤 새 번호를 받은 사람의 권한은 언제까지 유지될까요?

세션 ID는 서버 표에서 사용자와 상태를 찾는 불투명한 식별자이다. 여기서 A와 B는 종이 표의 이름이며 실제 보안 ID 길이나 난수성을 나타내지 않는다. 인증 성공 시 새 B로 바꾸고 A를 무효화하는 규칙을 먼저 정해, 로그인 전의 상태가 인증 권한으로 이어지지 않게 한다.

이 단원은 시간 단위를 분으로 쓰고 전체 경과 시간과 비활동 시간을 각각 계산한다. 시간 한도와 권한을 모두 통과한 요청만 last를 갱신하며, 만료나 로그아웃이면 서버 유효 상태를 false로 바꾼다. 권한 부족만으로 거절한 요청은 last를 유지하고 유효 세션 자체는 유지하는 자체 정책이다. 제시한 한도 숫자는 OWASP의 권장값이라고 주장하지 않는다.

먼저 확인할 개념
  • 세션·인증의 시간표

    issued와 last의 역할, 서버 무효화와 권한 거절을 확인한다.

  • cookie의 전달 조건

    브라우저 값이 있다는 사실과 서버 승인 사이의 단계를 연결한다.

값보다 대응 관계가 중요하다

세션은 여러 요청을 하나의 문맥으로 연결한다. 이 단원은 브라우저의 불투명한 session ID를 서버 표의 사용자·권한·시간에 대응시키는 모형이다. ID가 존재한다는 것만으로 로그인한 사용자라는 뜻은 아니며 익명 세션도 가능하다.

인증 성공 후 새 예측 어려운 ID를 발급하고 이전 ID를 무효화하는 방식으로 로그인 전후의 권한 경계를 분리한다. 아래 A/B 같은 한 글자는 표 설명용 이름이며 실제 ID의 안전한 길이·난수성을 나타내지 않는다. 비밀번호를 cookie에 넣는 예제가 아니다.

매 요청에서 세 조건을 확인한다

서버는 ID가 자신이 발급한 유효 세션인지, 만료되었는지, 요청한 자원에 권한이 있는지를 확인한다. cookie가 첨부되었다는 사실은 이 세 조건을 자동 통과시키지 않는다. 학생 세션은 인증되어도 관리자 기능을 허용하지 않을 수 있다.

idle timeout은 마지막으로 인정한 활동부터의 간격이고 absolute timeout은 발급부터의 전체 시간이다. 이 예제는 간격이 한도 이상이면 거절하며 거절된 요청은 활동 시간을 갱신하지 않는 자체 정책이다. 어떤 행위를 활동으로 세는지도 서버 정책에 명시한다.

끝난 세션의 양쪽을 정리한다

로그아웃하면 브라우저의 cookie 제거와 서버 세션 무효화를 함께 처리한다. 브라우저 값만 지우고 서버 표를 남기면 이미 복사된 ID가 여전히 유효할 수 있다. 반대로 cookie가 남아도 서버가 무효화했다면 세션으로 승인해서는 안 된다.

HttpOnly·Secure·SameSite는 세션 전달을 보완하지만 서버의 권한 확인이나 상태 변경 요청의 CSRF 방어를 대신하지 않는다. ID가 갱신된 후 이전 ID를 계속 허용할지 같은 예외를 무심코 만들면 보안 규칙이 달라진다.

한도와 같으면 만료로 정했다. 시간상 유효하지만 권한이 없는 t=5와 시간이 만료된 t=10의 상태 변화를 구별한다.

중간 과정을 따라가는 예제

가상 분 단위 시간이다. t=0 익명 A를 받았다. t=2 인증 성공으로 A를 무효화하고 학생 B를 발급한다. B의 last=2, issued=2, idle 한도5, absolute 한도12다. t=5 일반 조회는 허용하여 last=5다. t=6 관리자 요청은 권한 부족으로 거절한다. t=10 일반 조회는?

  1. t=2 이후 A로 온 요청은 이전 ID 무효화 때문에 거절한다. B만 학생 사용자에 대응한다.

  2. t=5에서는 idle=3<5, age=3<12이며 일반 조회 권한도 있어 허용한다. last를 5로 고친다.

  3. t=6 관리자 요청은 시간 조건과 무관하게 학생 권한으로 거절하며 정한 정책에 따라 last는 5다.

  4. t=10은 idle=10−5=5로 한도 이상이다. age=8<12여도 idle 실패로 거절한다. 두 시간 조건과 권한을 모두 만족해야 한다.

t=10 조회는 idle 만료로 거절한다. 로그인과 모든 기능의 인가는 같지 않다.

조건을 바꾸어 비교하기

활동이 있어도 전체 시간은 늘어나지 않기

별도 경로에서 issued=1분, last=1분인 B가 t=3,6,9분의 일반 조회를 모두 통과했다. t=11분 조회의 결과는?

  1. 성공한 활동으로 last는 3→6→9분이 된다.

  2. t=11에서 비활동 시간은 11−9=2분으로 4분 미만이다.

  3. 전체 경과 시간은 11−1=10분으로 전체 한도에 도달한다.

전체 시간 만료로 거절하고 유효 상태를 false로 바꾼다. last=9분을 성공 활동으로 더 갱신하지 않는다.

비교할 점

last를 갱신하는 일과 issued를 새로 정하는 일은 다르다.

브라우저에서 지운 값과 서버에서 끝낸 세션

복사된 B가 있다는 가정에서 t=7분 로그아웃한다. 계획 P는 브라우저 cookie만 지우고, 계획 Q는 서버 B도 무효화한다. 다른 시간·권한 조건은 유효할 때 복사된 B를 제출한 요청을 비교하라.

  1. P의 서버 표에는 여전히 유효 B가 남는다.

  2. Q의 서버 표는 B의 유효 상태를 false로 바꾼다.

  3. 브라우저의 삭제 동작을 서버 표의 변경으로 가정하지 않는다.

P는 복사된 B를 여전히 승인할 수 있지만 Q는 서버 무효화 때문에 거절한다.

비교할 점

클라이언트 쪽 상태 변화와 서버 쪽 상태 변화를 나눠 추적한다.

종이와 본문으로 직접 해보기

같은 B에서 t=5,8,11 일반 조회가 모두 허용된 별도 경로를 계산한다. t=14 조회는? 또 t=12 로그아웃했다면 t=13에 남은 B cookie를 보낸 요청은?

힌트 보기

발급 시각은 2로 유지하고 last만 허용된 활동마다 바꾼다. 로그아웃은 별도 분기다.

풀이 보기

별도 경로에서 last=11이며 t=14의 idle=3<5지만 age=12≥12로 absolute 만료다. 로그아웃 분기에서는 t=12 서버 B를 무효화했으므로 t=13은 cookie가 남아도 거절한다. 시간 계산과 서버 표 조회를 분리한다.

오해와 반례

cookie만 지우면 서버에서도 세션이 사라진다.

cookie 제거는 브라우저의 상태 변화다. 서버 표에 B가 남은 모형에서는 복사된 B를 별도로 보낼 때 서버가 승인할 수 있어 서버 무효화가 필요하다.

스스로 풀어보기

먼저 답과 이유를 적고, 필요한 만큼 힌트를 한 단계씩 열어 보세요.

연습 1 · 값과 상태 예측

issued=2분, last=2분, 유효 B, idle 한도 5분, 전체 한도 9분이다. 일반 조회는 권한이 있다. t=6,10,11분에 순서대로 온 요청의 결과와 last를 구하라.

힌트 1

성공한 활동마다 last만 갱신한다.

힌트 2

전체 한도는 issued=2분에서 계산한다.

풀이와 답 확인

  1. t=6분은 전체 경과 시간 4분과 비활동 시간 4분이 모두 각 한도 미만이라 허용하여 last=6분이 된다.

  2. t=10분은 전체 경과 시간 8분과 비활동 시간 4분이 모두 각 한도 미만이라 허용하여 last=10분이 된다.

  3. t=11분은 전체 경과 시간이 9분으로 한도에 도달하여 만료로 거절하고 last=10분을 유지한다.

허용·허용·거절이며 마지막 last는 10분, 유효 상태는 false이다.

흔한 오답에서 다시 생각하기

t=11의 비활동 시간이 1분이므로 계속 허용한다.

두 시간 조건은 모두 충족해야 한다. 비활동 통과가 전체 만료를 상쇄하지 않는다.

연습 2 · 오류 찾아 고치기

인증 후 B를 발급했지만 이전 익명 A를 서버에서 학생 권한으로 계속 받아준다. 개발자는 ID를 새로 발급했으므로 이전 상태와 분리되었다고 말한다.

힌트 1

새 ID 생성과 옛 ID 무효화는 서로 다른 동작이다.

힌트 2

이 모형의 인증 경계에서 이전 A가 통과하는지 확인한다.

풀이와 답 확인

  1. B를 발급한 사실만으로 A가 사라지지 않는다.

  2. 이 정책에서는 인증 전 A를 무효화해야 한다.

  3. 보호된 요청은 현재 유효 ID와 사용자·권한을 서버에서 확인한다.

이전 A를 무효화하고 보호 요청의 서버 판정을 유지한다.

흔한 오답에서 다시 생각하기

새 B가 존재하면 서버가 옛 A를 자동으로 거절한다.

서버 표의 실제 변경 규칙이 필요하다. 갱신되었다는 이름만으로 무효화를 가정하지 않는다.

연습 3 · 직접 만들어 보기

학생 B는 일반 조회만 허용되고 관리자 삭제는 불허된다. last=4분이며 t=6분에 관리자 삭제가 온다. 시간은 유효하다. 이 단원 정책에 맞는 상태 전이와 다음 조회의 비교 기준을 적어라.

힌트 1

권한 부족은 이 모형에서 성공 활동이 아니다.

힌트 2

세션 자체의 시간 만료와 구별한다.

풀이와 답 확인

  1. 삭제는 권한 부족으로 거절한다.

  2. last=4분과 유효 상태 true를 유지한다.

  3. 다음 조회는 새 시각에서 issued·last와 조회 권한을 다시 확인한다.

권한 거절 뒤 last=4분을 유지하며 다음 요청에서 시간을 새로 계산한다.

흔한 오답에서 다시 생각하기

거절해도 접속했으므로 last=6분으로 바꾼다.

그것은 다른 활동 정의이다. 여기서는 허용된 요청만 갱신하도록 명시했다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

같은 사용자의 B와 C가 각각 유효한 별도 서버 세션이다. B 로그아웃 시 B만 무효화하는 정책 P와 해당 사용자의 모든 세션을 무효화하는 정책 Q를 비교하라. 다른 조건은 유효하다.

힌트 1

사용자와 세션 ID가 같은 단위인지 확인한다.

힌트 2

무효화 대상 집합을 먼저 적는다.

풀이와 답 확인

  1. P의 대상 집합은 {B}이며 C는 남는다.

  2. Q의 대상 집합은 {B,C}이며 둘 다 거절된다.

  3. 사용자에 속한 세션을 찾고 처리하는 실제 구현은 별도로 필요하다.

P에서는 C가 여전히 유효하고 Q에서는 C도 무효이다. 하나의 로그아웃 정책을 모든 시스템의 기본 동작으로 일반화하지 않는다.

흔한 오답에서 다시 생각하기

B에서 로그아웃하면 C도 언제나 자동 종료된다.

무효화 범위는 서버 정책이다. 특정 세션 종료와 사용자 전체 세션 종료를 구별한다.

내 말로 설명하기

세션 ID가 첨부되면 어떤 검사가 남는가?

설명 기준 확인

서버가 발급하고 유지하는 유효성, 전체·비활동 시간과 요청별 권한을 확인한다.

time out 숫자와 활동 정의를 함께 적어야 하는 이유는 무엇인가?

설명 기준 확인

last를 갱신하는 사건과 경계의 ≥ 규칙이 달라지면 같은 요청 시간표의 결과도 달라지기 때문이다.

한 단계 더

세션 표에 user와 role을 따로 적고 같은 사용자라도 역할 변경 시 재확인과 ID 갱신이 왜 필요한지 설명한다. 실제 정책에서 허용되는 활동의 정의와 동시 요청의 last 갱신 순서를 명시해야 같은 시간표를 재현할 수 있다.

소단원 7.3

CORS·CSP의 역할

응답을 읽어도 된다는 허락과 script를 실행해도 된다는 허락은 같을까?

준비 개념과 학습 목표

준비 개념

  • origin은 scheme/host/port다.

  • HTTP header는 요청·응답에 붙는 정책 정보다.

학습 목표

  • CORS의 응답 공유 조건을 판정한다.

  • CSP의 자원별 허용 목록과 한계를 구별한다.

읽기 허용을 받았는데 문서 정책이 연결을 막는 이유는 무엇일까요?

CORS는 다른 origin에서 응답을 읽는 브라우저 script에 대한 공유 조건을 정한다. CSP는 문서가 어떤 자원을 연결·로드·실행할지 제한한다. 서버의 세션 승인과 요청별 권한은 이 두 정책과 다른 층에 남는다. 아래 표는 주어진 조건을 종이로 판정하며 실제 네트워크 성공을 나타내지 않는다.

preflight 없는 GET에서도 서버 요청과 응답 읽기 판정은 다른 사건이다. 반대로 preflight가 필요한 요청은 그 승인을 먼저 확인한다. 예제에서는 추가 브라우저 제한, redirect와 preflight cache를 제외한다. CSP는 명시한 자원 directive를 사용하고, 없을 때만 대응하는 fallback을 적용한다. Report-Only 정책은 보고용이며 그 정책 자체로 강제 차단하지 않는다.

먼저 확인할 개념
  • CORS·CSP의 기본 역할

    읽기 공유·preflight·자원별 fallback과 inline 조건을 확인한다.

  • 서버 세션과 요청 권한

    응답 공유 허용을 서버의 인가 성공으로 확대하지 않도록 연결한다.

누가 응답을 읽을 수 있나

CORS는 서버가 다른 origin의 브라우저 script에 응답 공유를 허용하는 방식이다. 일반적인 교차 origin fetch에서 credentials는 기본으로 포함하지 않으며 include를 선택해도 cookie 자체 범위·SameSite·브라우저 정책을 따로 충족해야 한다.

preflight가 필요한 요청은 먼저 OPTIONS로 method/header 등을 확인한다. 반면 조건을 만족한 단순 GET 같은 요청은 preflight 없이 전송되고 응답 읽기 단계에서 차단될 수 있다. CORS는 서버의 로그인·인가나 CSRF 방어를 대신하지 않고 일반 HTTP client를 막는 경계도 아니다.

문서가 실행·로드할 자원은 무엇인가

CSP는 문서에 적용되어 script·그림·연결 등의 자원 허용 정책을 제한한다. default-src는 해당 fetch directive가 없을 때의 대체 규칙이고 명시한 script-src나 img-src는 그 자원에 우선 적용한다. self는 그 문서의 같은 origin이다.

외부 script URL이 허용 목록에 들어도 inline script 허용과 같지 않다. nonce/hash 등 별도 허용이 없는 정책에서 inline 코드는 차단된다. CSP의 script 허용 목록만으로 입력을 안전하게 만들거나 서버의 권한을 보장하지 못하므로 의미에 맞는 출력 처리도 필요하다.

서로 다른 판정을 함께 통과한다

교차 origin 자료를 fetch할 때 CSP의 connect-src와 CORS의 응답 공유 조건이 각각 관련될 수 있다. 하나를 통과한 사실만으로 다른 것을 통과했다고 할 수 없다. 여기서는 CSP 예제와 CORS 예제를 별도로 판정하여 조건을 숨기지 않는다.

정책 표의 통과는 실제 접속 성공이 아니다. DNS·TLS·서버 상태·추가 응답 header·브라우저별 제한이 남을 수 있다. 아래 활동은 지정한 정책만 종이로 분석하며 실제 요청이나 공격을 실행하지 않는다.

다른 조건도 충족하면 읽기 공유 허용

A는 https://school.example, B는 https://api.school.example이다. include인 행은 cookie 자체 조건도 충족한다고 가정한다. 모든 행의 서버 권한과 실제 DNS·TLS·응답 상태는 별도로 확인해야 한다.

중간 과정을 따라가는 예제

A=https://learn.example의 script가 B=https://api.example의 단순 GET 응답을 읽으려 한다. 첫 경우 credentials를 보내지 않고 B가 Allow-Origin:*를 반환한다. 둘째는 credentials:include이며 cookie의 다른 전송 조건도 충족하고 B가 Allow-Origin:*와 Allow-Credentials:true를 반환한다. 별도 A 문서 CSP는 default-src self; script-src self; img-src https://images.example이며 nonce/hash/unsafe-inline은 없다. self는 실제 header에서 따옴표로 쓰는 키워드다.

  1. 첫 GET은 다른 공유 제한이 없다는 조건에서 wildcard CORS로 응답을 읽을 수 있다. 인증 여부는 별도다.

  2. 둘째는 credentialed 응답에 wildcard origin을 쓸 수 없어 읽기가 차단된다. 이미 GET이 서버에 도착했는지는 응답 차단과 다른 문제다.

  3. CSP에서 A의 외부 /app.js는 script-src self로 허용되지만 B의 /app.js와 inline script는 허용되지 않는다.

  4. 그림은 명시한 img-src 때문에 images.example만 허용한다. A의 /logo.png도 이 정책에는 self가 없어서 허용되지 않는다. default-src self를 그림 목록에 자동 합치지 않는다.

CORS 첫 경우만 읽기 허용이다. CSP script와 그림은 서로 다른 명시 목록을 따른다.

조건을 바꾸어 비교하기

명시한 그림 목록은 fallback과 합치지 않기

A의 정책이 default-src 'self'; script-src 'self'; img-src https://pictures.example이다. 추가 nonce·hash·unsafe-inline은 없다. A의 /a.js, inline script, A의 /a.png와 pictures.example의 그림을 판정하라.

  1. A의 외부 script는 script-src의 self로 허용된다.

  2. inline script는 별도 허용 조건이 없어 차단된다.

  3. 그림에는 명시한 img-src만 적용하여 A 그림은 불허하고 pictures.example 그림은 허용한다.

판정은 허용·차단·불허·허용이다. default-src의 self를 img-src에 자동으로 더하지 않는다.

비교할 점

같은 origin인 그림과 script도 자원별 directive에 따라 결과가 다르다.

보고용 새 정책과 현재 강제 정책

강제 CSP는 script-src 'self'이고 별도 Report-Only 정책은 script-src 'none'이다. A의 외부 script가 있고 다른 제한은 없다. 보고 endpoint는 정상 설정했다고 가정한다.

  1. 강제 정책은 A의 외부 script를 허용한다.

  2. 보고용 정책은 none 위반을 보고하도록 평가하지만 자체로 실행을 막지 않는다.

  3. 보고 전송의 실제 관측 여부는 종이 판정과 다르다.

강제 정책상 허용이며 보고용 정책의 위반 대상이다. 실제 보고를 수신했다고 기록하지 않는다.

비교할 점

보고 정책의 none을 강제 정책과 합쳐 차단이라고 판정하면 모드를 혼동한다.

종이와 본문으로 직접 해보기

둘째 CORS 응답을 Allow-Origin:https://learn.example와 Allow-Credentials:true로 고친다. 다른 조건은 모두 충족한다. CSP img-src에 self를 추가하면 A 그림은? 단순 GET에서 Allow-Origin을 없애면 서버의 부작용도 반드시 없어지나?

풀이 보기

오해와 반례

CORS를 켜면 CSP도 통과하고 서버 권한 검사도 필요 없다.

CORS가 A에 읽기를 허용해도 문서의 connect-src가 B를 막을 수 있다. 또 미인증 사용자에게 자원을 제공할지는 서버가 별도로 판단한다.

먼저 답과 이유를 적고, 필요한 만큼 힌트를 한 단계씩 열어 보세요.

연습 1 · 값과 상태 예측

A에서 B로 preflight가 필요 없는 GET을 보낸다. 문서 CSP는 연결을 허용하고 cookie 조건도 충족한다. credentials:include이며 응답은 Access-Control-Allow-Origin:*와 Access-Control-Allow-Credentials:true이다. 읽기와 서버 처리 여부를 구별하라.

힌트 1

자격증명 포함의 wildcard 조건을 확인한다.

힌트 2

이미 보낸 GET의 처리를 응답 읽기 차단과 구별한다.

풀이와 답 확인

  1. include 응답에서 wildcard origin은 공유 조건을 통과하지 못한다.

  2. script의 응답 읽기는 차단된다.

  3. 그 차단만으로 서버에 요청이 도착하지 않았거나 처리되지 않았다고 결론 낼 수 없다.

읽기 공유는 거절된다. 서버 처리 부재는 이 판정만으로 증명하지 못한다.

흔한 오답에서 다시 생각하기

응답을 못 읽으면 GET도 처음부터 없었던 것이다.

읽기 공유 조건은 이미 전송한 요청의 효과를 취소하는 기능이 아니다.

연습 2 · 오류 찾아 고치기

문서의 connect-src는 'self'만 허용한다. 다른 origin B가 A를 정확히 Allow-Origin에 넣었다. 개발자가 CORS 성공이므로 연결 정책도 통과한다고 적었다.

힌트 1

self는 A의 origin이다.

힌트 2

B의 공유 허용과 A 문서의 연결 허용을 나눈다.

풀이와 답 확인

  1. B는 A와 다른 origin이라 connect-src self에 들지 않는다.

  2. B의 CORS 허용으로 A의 CSP를 바꾸지 않는다.

  3. 필요한 신뢰 대상 연결 목록과 서버 권한을 각각 검토한다.

A 문서의 연결 정책에서 B가 불허된다. CORS 허용만으로 fetch 성공을 주장할 수 없다.

흔한 오답에서 다시 생각하기

두 정책 중 하나만 통과하면 전체가 통과한다.

각 관련 조건을 모두 확인해야 한다. 서로 다른 주체가 다른 범위를 정한다.

연습 3 · 직접 만들어 보기

A가 B에 POST와 Content-Type:application/json, X-Class:1을 보내려 한다. preflight cache는 없다. 문서 연결은 허용한다. credentials는 omit이다. 필요한 preflight 확인과 응용 권한 확인을 계획하라.

힌트 1

application/json과 X-Class는 이 모형에서 safelisted 조건을 넘는다.

힌트 2

CORS에서의 method/header 허용과 요청별 권한을 구별한다.

풀이와 답 확인

  1. OPTIONS preflight로 B의 A origin·POST·Content-Type과 X-Class 허용 조건을 확인한다.

  2. 승인이 없는 경우 이 경로의 실제 POST를 보내지 않는다.

  3. 승인이 있어도 실제 POST의 서버 인증·인가와 응답 공유 조건을 각각 확인한다.

preflight의 origin·method·header와 실제 요청의 서버 권한·응답 조건을 단계별로 확인하는 계획이다.

흔한 오답에서 다시 생각하기

POST라는 이름이면 항상 preflight가 없다.

method뿐 아니라 Content-Type과 수동 header 등도 조건이다. 이 요청은 preflight가 필요하다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

강제 CSP의 script-src는 'self'이다. 보고용 정책은 script-src 'none'이다. A의 외부 script와 외부 B의 script를 각각 판정하라. 추가 허용 표현은 없다.

힌트 1

강제 정책의 허용 목록부터 본다.

힌트 2

보고용 정책의 위반 판정은 차단 모드가 아니다.

풀이와 답 확인

  1. A script는 강제 정책에서 허용되고 보고용 none에서는 위반 대상이다.

  2. B script는 강제 self에서 차단되며 보고용 none에서도 위반 대상이다.

  3. 실제 보고 수신 여부는 실행과 관측이 없으므로 미확인이다.

A는 강제 허용·보고용 위반, B는 강제 차단·보고용 위반이다.

흔한 오답에서 다시 생각하기

보고용 none이 있으므로 둘 다 그 정책 때문에 차단된다.

차단의 근거는 강제 정책이다. 보고용 평가와 실제 보고 관측도 구별한다.

내 말로 설명하기

CORS와 서버 권한 확인의 질문은 어떻게 다른가?

설명 기준 확인

CORS는 브라우저 script의 다른 origin 응답 공유 조건이다. 서버는 요청한 사용자와 자원·동작의 권한을 별도로 판단한다.

Report-Only에서 보고가 예상되면 배포 검증을 마쳤는가?

설명 기준 확인

종이 위반 판정은 실제 보고 수신이나 강제 차단 검증이 아니다. 실제 응답 header·브라우저 동작·보고 관측이 필요하다.

한 단계 더

connect-src self를 추가한 문서에서 B의 CORS가 허용되더라도 fetch 연결이 정책을 통과하지 못함을 설명한다. 이후 CSP를 실제 운영에 적용할 때는 Report-Only 관찰과 실제 강제 차단을 구별해야 하며 이 종이 표를 배포 검증으로 표시하지 않는다.

    실제 response header·directive fallback·self/none·외부/inline script와 nonce·XSS 방어의 한계 본문을 읽었다. 자체 정책의 허용표는 브라우저 실행 결과가 아니다.

calculations: wildcard 비인증/credentialed 및 명시 origin 판정, 자원별 self/외부/inline 5개 사례를 종이 대조했다. · code_execution: not_executed — 웹 세션/CORS/CSP·컴파일러 타입 검사·Raft 교육 구현은 실행하지 않았다. 실제 브라우저 통신·서버·클러스터·학습자 검증은 미수행이다. · learner_review: not_performed

다른 문제에 적용하기

A는 https://school.example/lab, B는 https://school.example:9443/lab/api이다. A host-only sid는 Secure·HttpOnly·Path=/lab이며 다른 cookie 조건은 충족한다. 서버 세션은 issued=1분, last=9분, idle 한도 4분, 전체 한도 10분이고 t=11분에 일반 조회가 온다. CSP connect-src는 self뿐이고 B는 A를 정확히 공유 허용했다. origin·cookie 전송 범위·서버 시간 승인·연결 정책을 각각 판정하라. 네트워크가 실제 성공했다고 가정하지 않는다.

힌트 1

다른 port는 origin에 들어가지만 cookie 범위의 port 제한은 아니다.

힌트 2

11−9와 11−1을 각각 계산하며 self는 A의 origin이다.

풀이와 답 확인

  1. B는 port 9443이 달라 A와 다른 origin이다.

  2. host·Secure·Path 조건상 sid는 B 전송 범위에 들지만 HttpOnly라 script가 값을 직접 읽지는 못한다.

  3. 비활동 시간은 2분이나 전체 경과 시간이 10분으로 한도에 도달하여 이 서버 정책은 만료 거절한다.

  4. B의 공유 허용과 무관하게 connect-src self는 B를 불허한다. 전송 범위 판정을 실제 요청 발생으로 확대하지 않는다.

다른 origin, cookie 전송 범위에 포함, 서버 전체 시간 만료 거절, 문서 연결 정책 불허이다. 서로 다른 단계의 조건 판정이며 실제 통신·서버 실행 결과가 아니다.

해결한 뒤 점검할 것

  • port의 origin 영향과 cookie 범위를 분리한다.

  • HttpOnly의 script 접근 제한을 설명한다.

  • 전체 10분과 비활동 2분을 구별한다.

  • CSP·CORS·서버 승인·실제 요청 발생을 구별한다.

보강 자료의 출처와 확인 범위
  • MDN — Same-origin policy

    실제 본문 174–195,221–240,282–286을 읽어 tuple·전송/읽기/삽입·storage와 cookie의 별도 범위를 확인했다. 특수 origin과 deprecated domain 변경은 새 활동에서 제외했다.

  • MDN — Using HTTP cookies

    실제 세션 흐름 186–190과 304–344를 읽어 Secure·HttpOnly·Domain·경로 일치와 Path의 한계를 확인했다. localhost 예외와 추가 전송 조건을 모형 범위에 명시했다.

  • IETF HTTPWG — RFC 6265

    실제 82–84,327–338,586–593을 읽어 port 비격리·경로 일치·path와 sibling 신뢰의 한계를 확인했다. 이 RFC가 모든 최신 browser cookie 기능을 포괄한다고 주장하지 않는다.

  • OWASP — Session Management

    실제 329–336,481–485,508–529,533–539를 읽어 서버 대응·ID 교체·무효화·idle/absolute와 renewal 범위를 확인했다. 수치 한도와 활동 정의는 자체 정책이고 권장값 복사가 아니다.

  • MDN — CORS

    실제 208–265,428–480,487–553을 읽어 safelisted 조건·include·wildcard 제한·쿠키 추가 정책·명시 origin과 preflight 역할을 확인했다. 새로운 요청은 실행하지 않았다.

  • MDN — CSP

    실제 224–338,419–478,685–697을 읽어 자원별 fallback·self·inline과 보고용/강제 모드를 확인했다. 정책 표와 보고 기대는 실제 브라우저 및 endpoint 관측이 아니다.

전체 기본과 세 실제 의미 앵커, 여섯 공식 원문 범위를 읽었다. origin tuple·다섯 cookie 행·두 Path와 query 조건, issued/last 분 단위 시간표, ID 무효화 집합, CORS/CSP 층·보고용/강제와 전이 조건을 손추적했다. 최종 저장본 전체 3소단원·12과제·전이·출처를 재독하고 predict 시간 풀이를 전체 경과 시간과 비활동 시간의 문장으로 풀어 썼다.

not_executed: 새 브라우저 cookie·세션·CORS/CSP 요청, 서버 상태 변경, preflight·보고 endpoint와 학습자 실험은 수행하지 않았다. 자체 종이 모형이며 canonical v1을 보존한다.
