소단원 6.1

암호화·MAC·서명의 차이

공개된 안내문에 서명을 붙이면 내용도 비밀이 될까?

준비 개념과 학습 목표

준비 개념

  • 기밀성은 내용을 숨기는 목표, 무결성은 변경을 알아내는 목표다.
  • 대칭 키는 비밀 키를 공유하고 공개 키 서명은 서명 비밀 키와 검증 공개 키를 나눈다.

학습 목표

  • 세 도구의 목표와 키 보유자를 구별한다.
  • 변조 검증과 replay 방지를 별도 판단한다.

숨김과 확인은 다른 질문이다

암호화는 내용을 알아보기 어렵게 변환한다. 그러나 기밀성만 정의한 암호가 모든 변조를 검출한다고 보장할 수는 없다. 현대 응용에서는 검증된 인증 암호 API를 사용해 숨김과 변조 검사를 함께 수행한다. 여기서 실제 암호 수식의 보안 증명을 대신하는 장난감 변환은 만들지 않는다.

MAC은 공유 비밀 키와 메시지로 인증 tag를 만든다. 키가 없는 사람이 변경한 메시지에 맞는 tag를 만들기 어렵게 하는 목적이며 메시지 자체를 숨기지는 않는다. 키를 공유한 두 사람 모두 tag를 만들 수 있어 제3자에게 어느 한 사람만 작성했다고 증명하는 용도와 다르다.

서명은 공개 검증을 위한 연결이다

디지털 서명에서는 서명자의 비밀 키로 서명하고 공개 키로 검사한다. 공개 키를 아는 사람은 검사할 수 있지만 검증 키만으로 새 유효 서명을 만드는 것은 별도 문제다. 메시지 표현은 그대로 남을 수 있으므로 서명된 공개 공지 역시 모두 읽을 수 있다.

검증자는 그 공개 키가 누구의 것인지 신뢰할 근거를 먼저 확보해야 한다. 공격자가 자기 키로 서명한 안내문과 자기 공개 키를 함께 보내면 수학적으로 유효할 수 있어도 학교장의 공지로 받아들이면 안 된다. 서명 검증의 성공과 키 신원 확인을 함께 설계한다.

목표를 조합하고 처리 상태를 남긴다

AEAD는 메시지를 숨기고 변조를 검증하며 공개 메타데이터인 추가 데이터도 인증할 수 있다. 수신자는 확인이 성공한 뒤에만 내용을 업무에 적용한다. 검증이 있다는 이유만으로 모든 키·nonce· 재전송 정책이 해결되는 것은 아니다.

이미 유효한 메시지를 다시 보내는 replay는 변조가 아니다. 순번을 인증 범위에 넣고 수신자가 마지막 처리 순번을 기록하는 등 별도 상태 규칙이 필요하다. 서명이나 MAC이 진짜인지와 그 요청을 지금 다시 적용해도 되는지는 서로 다른 검사다.

중간 과정을 따라가는 예제

메시지 M =회비 10,000원에 대해 A/B가 MAC 키 K를 공유한다. C는 A의 신뢰하는 서명 공개 키만 가진다. 각 도구의 공개 읽기·C 검증·B의 새 인증 생성 가능성을 판단하라.

  1. 평문 +MAC은 내용을 숨기지 않으므로 C도 메시지를 읽을 수 있다.
  2. C는 K가 없어 MAC 검증 능력을 전제로 할 수 없다. B는 K로 새 MAC을 만들 수 있다.
  3. 평문 +서명도 C가 읽고 A의 공개 키로 검사할 수 있다. B가 공개 키만 가진다면 새 A 서명을 만들 능력은 없다.
  4. AEAD는 키 없는 C에게 내용을 숨긴다. 수신 B는 키로 변조 검사를 수행한다. 각각의 안전한 키·nonce 사용을 가정한 비교다.

MAC/ 서명은 단독으로 숨김을 주지 않으며 공개 검증에는 신뢰하는 서명 공개 키가 필요하다.

종이와 본문으로 직접 해보기

유효한 MAC 요청 순번 7을 수신자가 이미 처리했고 마지막 처리 순번이 7이다. 같은 메시지/tag가 다시 오면 검증과 적용을 각각 판단하라. 이후 인증된 순번 8은?

힌트 보기

예제 정책은 검증 성공 뒤 순번이 마지막 값보다 큰 경우에만 적용한다.

풀이 보기

재전송 7은 MAC 검증에 성공할 수 있지만 7>7이 거짓이므로 적용하지 않는다. 인증된 8은 8>7이라 적용 후 마지막 값을 8로 바꾼다. 순번도 MAC 입력에 포함해야 한다. 순번 없는 본문만 인증하면 공격자가 순번만 변경할 여지가 있다.

오해와 반례

서명하면 내용도 암호화되고 replay도 자동으로 막힌다.

공개 공지 +서명은 누구나 읽고 같은 유효 서명을 다시 보내도 수학적 검증은 성공할 수 있다. 숨김과 순번 상태는 별도로 필요하다.

자기점검

답과 이유 보기

그렇다.

공유 키를 사용하는 MAC 생성과 검증을 할 수 있어 A만의 작성 증거가 되지 않는다.

서명 검증 공개 키를 이메일 첨부로 받기만 하면 학교장 신원이 확인되는가?

답과 이유 보기

공격자가 자기 키를 첨부할 수 있어 키 신뢰를 먼저 확보해야 한다.

순번 7 재전송의 tag가 유효하면 반드시 다시 적용하는가?

답과 이유 보기

마지막 처리 순번 7 과의 상태 검사가 반복 적용을 거부한다.

한 단계 더

각 도구의 표에 기밀성/ 변조 검출/ 검증자/ 키 신뢰/replay 상태 열을 추가하자. 서명 비밀 키 유출 시 가짜 서명은 유효할 수 있으므로 키 폐기· 갱신 정책도 필요하다. 여기서는 법적 책임이나 모든 의미의 부인 방지를 단정하지 않는다.

소단원 6.2

키·nonce·난수

비밀이 아닌 숫자를 암호화마다 바꾸는 이유는 무엇일까?

준비 개념과 학습 목표

준비 개념

  • 키는 내용을 보호하는 비밀 재료다. nonce는 한 키 아래 암호 호출을 구별하는 값이다.
  • XOR는 두 비트가 다르면 1이고 같으면 0이다. 이 단원 4비트 XOR는 위험의 직관이며 실사용 암호가 아니다.

학습 목표

  • 키 예측 불가능성과 nonce 중복 금지를 구별한다.
  • 작은 균등 난수에서 충돌 및 모듈러 편향을 계산한다.

비밀 키와 공개 nonce의 역할

키는 공격자가 예측하기 어렵게 생성하고 공개 저장소나 로그에 넣지 않는다. 라이브러리의 keygen은 필요한 크기의 키를 만들도록 돕는다. 이름이 비밀번호인 짧은 문장을 곧바로 강한 암호 키라고 취급하면 키 공간과 추측 문제를 놓친다.

XChaCha20-Poly1305의 공개 nonce는 동일 키 아래 재사용하지 않아야 한다. nonce 자체는 비밀이거나 예측 불가능할 필요가 없다. 지속 저장된 카운터처럼 중복을 피하는 방식과 충분히 큰 공간의 보안 난수를 쓰는 방식을 구별한다. 어떤 방식이든 실제 선택한 알고리즘의 조건을 따라야 한다.

중복은 숨겨야 할 관계를 드러낼 수 있다

직관용 XOR 모형에서 C1 =P1 XOR S, C2 =P2 XOR S처럼 같은 마스크 S를 두 번 쓰면 C1 XOR C2 =P1 XOR P2다. 한 평문을 알면 다른 평문도 복원할 수 있다. 이는 재사용 위험을 보여 주는 작은 모형이고 실제 인증 암호의 전체 공격 분석을 대체하지 않는다.

서로 독립인 균등 b 비트 nonce의 두 번 추출은 1/2^b 확률로 같다. 더 많이 추출하면 생일 효과로 쌍의 수가 빠르게 늘어난다. 큰 공간의 무작위 nonce가 실용적이라는 설명은 중복 확률이 수학적으로 0이라는 뜻이 아니다.

난수 API와 재시작을 함께 본다

보안 난수는 공격자가 다음 출력을 예측하기 어렵다는 조건이 중요하다. 테스트용 결정적 생성기는 같은 seed에서 같은 열을 내도록 설계될 수 있으므로 seed 고정은 반복 실험에는 유용해도 매번 새 nonce가 된다는 보장이 아니다. 가상 머신 snapshot 복원 역시 상태 반복 가능성을 살펴야 한다.

작은 난수를 나머지 연산으로 줄이면 분포가 편향될 수 있다. 0..7 균등 수를 3으로 나누면 나머지0/1/2의 원상 개수는3/3/2다. 보안 라이브러리의 균등 범위 API는 이런 편향을 피하는 역할을 한다. 직접 구현의 종이 계산과 실제 안전한 API 호출은 구별한다.

중간 과정을 따라가는 예제

4비트 모형 P1 =1010,P2 =0011,S =1100이다. 암호문 두 개와 그 XOR를 구한 뒤 P1을 아는 관찰자가 P2를 어떻게 구하는지 적어라.

  1. C1 =1010 XOR 1100 =0110이다.
  2. C2 =0011 XOR 1100 =1111이다.
  3. C1 XOR C2 =0110 XOR 1111 =1001이며 P1 XOR P2 도 1001이다.
  4. 1001 XOR P1(1010)=0011 =P2다. 마스크를 몰라도 두 암호문의 관계와 한 평문으로 다른 값을 복원한다.

C1 =0110,C2 =1111, 둘의 XOR =1001이고 P2 =0011을 복원한다.

종이와 본문으로 직접 해보기

균등 2 비트 nonce를 독립적으로 3번 고른다. 전체 경우 수와 모두 다른 경우 수 및 중복 확률을 계산하라. 지속 카운터 0,1,2와 재시작 후 0을 같은 키에 쓰면?

힌트 보기

2 비트 값은 4개다. 순서 있는 서로 다른 선택은 4×3×2다.

풀이 보기

전체 4³ =64, 모두 다른 경우 24이므로 중복 확률 1 −24/64=5/8이다. 카운터 0,1,2는 중복 없지만 같은 키로 재시작해 0을 다시 쓰면 재사용이다. 카운터 지속성이나 키 갱신 등 모형 밖 정책이 필요하다.

오해와 반례

nonce가 공개되면 암호가 깨지므로 숨기기만 하면 같은 값을 반복해도 된다.

동일 키의 nonce 중복을 피하는 조건이 핵심이다. 작은 XOR 모형은 마스크 재사용만으로 평문 관계가 드러나며 nonce의 비밀 여부와 별개다.

한 단계 더

m 개 균등 값을 독립 추출할 때 적어도 한 충돌의 확률은 1 −∏(1 −j/2 ^b), j =0..m −1이다(m ≤2 ^b). 쌍별 충돌 사건의 합 m(m −1)/(2·2 ^b)는 union bound이며 항상 정확한 확률이 아니다. 실제 192 비트 nonce의 위험을 2 비트 숫자 그대로 비교하지 않는다.

소단원 6.3

구성 오류와 안전한 API

변조 검사를 했다는 메시지가 있으면 언제 결과를 적용해도 될까?

준비 개념과 학습 목표

준비 개념

  • AEAD는 ciphertext와 tag를 검사하며 추가 데이터는 숨기지 않고 인증한다.
  • 반환 값은 성공/ 실패를 표현하는 API 규약이며 숫자의 의미를 문서에서 확인해야 한다.

학습 목표

  • 인증 실패에서 업무 적용으로 이어지는 경로를 차단한다.
  • nonce·AAD· 길이· 재전송 상태를 명시한 수신 절차를 추적한다.

검증된 구성을 경계까지 사용한다

암호·MAC· 패딩· 키 유도 등을 임의 조합하기보다 목표에 맞는 검증된 API를 선택한다. XChaCha20-Poly1305의 combined API는 암호문 뒤에 tag를 포함하고 detached는 tag를 별도 보관한다. 형식만 다른 두 모드에서도 인증 검사를 생략해도 된다는 뜻은 아니다.

예제 API에서 decrypt 반환 0은 성공, −1은 실패다. 반환을 무시하고 출력 버퍼를 업무 입력으로 쓰면 검증의 의미가 사라진다. 실패 버퍼가 모든 라이브러리에서 어떤 바이트로 초기화되는지 가정하지 않고 성공 분기 안에서만 복호 결과를 사용한다.

공개 메타데이터도 의미를 바꾼다

요청의 사용자· 버전· 순번 같은 헤더가 본문 해석을 바꾸면 AAD로 인증할 후보가 된다. AAD는 ciphertext 안에 숨지 않아 관찰자에게 보일 수 있다. 수신자는 송신자와 동일한 바이트 열을 제공해야 검증이 맞는다.

필드 연결을 모호하게 하지 않는다. user =ab,seq =c와 user =a,seq =bc를 길이 없이 이어 붙이면 둘 다 abc다. 자체 예제에서는 각 필드 길이와 구분을 명확히 하는 형식을 정한다. AAD가 안전하다는 말은 인코딩 규칙을 생략해도 된다는 말이 아니다.

암호 성공 이후에도 업무 상태를 검사한다

수신자는 최대 길이· 최소 tag 공간 등 형식 조건을 검사하고 적절한 키/nonce/AAD로 인증 복호를 호출한다. 성공하면 순번· 권한· 업무 조건을 검사한다. 암호문이 유효하더라도 재전송이나 허용되지 않은 동작은 있을 수 있다.

아래는 단일 연결에서 순번이 증가할 때만 적용하는 종이 모형이다. 상태 갱신과 업무 적용을 하나의 원자적 처리로 묶는다고 가정한다. 그렇지 않으면 같은 순번을 동시에 받은 두 요청이 모두 이전 값을 보고 중복 적용될 수 있다. 실제 동시성· 저장 복구 구현은 이 종이 표에서 수행하지 않는다.

중간 과정을 따라가는 예제

수신자의 last =4다. 인증된 순번 5(A), tag 실패 순번 6(B), 다시 인증된 5(C), 인증된 7(D)를 순서대로 받는다. 성공 반환 0/ 실패 −1이고 성공 뒤 seq>last일 때만 원자적으로 적용한다.

  1. A는 0이고 5>4 라 적용하며 last =5다.
  2. B는 −1이라 평문을 업무에 사용하지 않고 last =5다. 순번만 높아도 실패를 뒤집지 못한다.
  3. C는 0이지만 5>5가 거짓이므로 replay로 거부하고 last =5다.
  4. D는 0이고 7>5 라 적용해 last =7이다. 이 정책은 6의 누락을 허용하며 연속 순번 정책과 다르다.

적용은 A/D 두 번, B/C 거부, 최종 last =7이다.

종이와 본문으로 직접 해보기

D의 seq =7을 숨기지 않은 AAD에 넣었다. 관찰자가 7을 9로 바꾼 경우, 송신자가 처음부터 유효한 9를 보낸 경우를 나누어라. 또한 두 요청 5가 동시에 last 4를 읽으면?

힌트 보기

AAD 변경은 tag 검사 입력을 바꾼다. 합법 순번의 순서 검사와 분리한다.

풀이 보기

헤더만 바꾼 9는 인증에 포함되어 있어 변조 검출 대상이다. 정상적으로 생성된 9는 검증 성공 뒤 9>last라 이 모형에서 허용될 수 있다. 동시 5 두 개가 검사와 갱신을 따로 하면 모두 4를 읽고 중복 적용할 수 있으므로 명시한 원자 처리 조건이 중요하다.

오해와 반례

AEAD 검증을 호출하기만 하면 반환 값이나 replay 상태는 무시해도 된다.

예제 B의 실패 결과를 적용하면 인증이 업무를 보호하지 못하고 C 는 유효 tag 여도 재전송이다. 성공 분기와 별도 상태 검사가 모두 필요하다.

자기점검

decrypt 반환 −1이면 출력 평문을 업무에 쓰는가?

답과 이유 보기

쓰지 않는다.

문서의 실패 분기이며 출력 버퍼 내용을 신뢰할 근거가 없다.

AAD는 비밀인가?

답과 이유 보기

일반적으로 아니다. 인증되는 공개 데이터다.

암호문에 숨겨지는 본문과 다른 역할이다.

마지막 값 5에서 인증된 7을 허용하는 이 정책은 누락 없는 연속 처리인가?

답과 이유 보기

아니다.

조건은 7>5이며 7 =5 +1을 요구하지 않는다.

한 단계 더

순번이 반드시 last +1이어야 하는 정책으로 바꾸면 위 D는 거부되고 last 5에 남는다. 순서 바뀐 메시지를 버퍼링할지 버릴지까지 정해야 한다. 라이브러리 API 문서의 성공 규약과 애플리케이션 프로토콜의 요구를 각각 적어 보자.

출처와 확인 범위

    공식 실제 combined/detached·keygen·nonce192 비트·동일키 재사용 금지·추가 데이터와 decrypt 반환값 본문을 읽었다. 문서 예제는 읽기만 했고 실행하지 않았다.

  • Libsodium: AEAD constructions

    공식 실제 AEAD 목적·추가 데이터·nonce 선택과 replay 관련 본문을 읽었다. 기밀성/변조 검증/메타데이터/상태 검사의 구별을 확인했다. 자체 표와 프로토콜은 종이 모형이다.
