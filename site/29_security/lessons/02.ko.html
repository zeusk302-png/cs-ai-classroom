소단원 2.1

비밀번호·MFA·세션

비밀번호를 두 번 물으면 두 요소 인증이 될까?

준비 개념과 학습 목표

준비 개념

  • 주체는 계정이나 서비스처럼 권한이 부여되는 대상이다. 인증은 주장한 주체의 인증 수단을 통제함을 확인하는 과정이다.

  • 비밀은 공개되지 않아야 하는 값이고, 해시는 입력을 고정된 길이의 값으로 변환하는 함수이다. 같은 입력의 같은 해시가 곧 원문 복구 기능을 뜻하지 않는다.

  • 세션은 인증 후 연속된 상호작용을 묶는 상태이다. 시간 차 t−s는 같은 시간 기준과 단위로 계산한다.

학습 목표

  • 인증 요소의 종류와 개수를 구분한다.

  • 세션의 전체 수명과 비활동 만료를 각각 판정한다.

활동을 계속하면 전체 수명도 늘어날까?

자체 세션 정책은 정수 분 단조 시간에서 valid이며 0≤t−created<15와 0≤t−last<4일 때만 성공이다. 성공만 last=t로 바꾸고 실패는 valid=false로 만든다. 새 인증 없이 created는 바뀌지 않는다. 이 시간은 자체 예제이며 NIST 권고 시간이 아니다.

created=last=0에서 3,6,9,12분은 모두 성공해도 15분에는 전체 수명 때문에 실패한다. 비밀번호와 PIN을 두 번 확인하는 것과 서로 다른 종류의 인증 요소를 확인하는 것도 구별하자. 세션 비밀과 권한 검사는 인증 후에도 필요하다.

비밀번호를 검사하는 계약

서버는 계정에 결합된 비밀번호의 검증 정보를 사용한다. 비밀번호를 평문으로 보관하는 대신 salt와 비용 인자를 포함한 전용 비밀번호 해시 방식으로 검증한다. salt는 계정별 사전 계산의 공유를 어렵게 하는 값이며 비밀번호처럼 반드시 비밀이어야 하는 값은 아니다. 해시가 있어도 약한 비밀번호의 후보 추측이 사라지지 않는다.

인증 결과는 이 계정의 인증 수단을 통제한다는 근거이다. 특정 문서의 수정 허용은 별도 인가 문제이다. 공개 자료는 인증 없이도 허용할 수 있으므로 모든 자원에 로그인이 필요하다는 결론도 성립하지 않는다.

두 요소와 인증 후의 위험

요소는 알고 있는 것, 소유한 것, 신체적 특징 같은 서로 다른 종류로 나눈다. 비밀번호와 PIN은 모두 지식 요소라 두 개의 질문이어도 서로 다른 두 요소가 아니다. 비밀번호와 별도 소유 수단의 검증은 적절한 결합 절차에서 두 요소가 될 수 있다. 생체 특징도 실제 인증 장치 및 검증 절차와 결합되는 방식에 따라 다룬다.

MFA라는 이름만으로 피싱 저항성이나 세션 탈취 방지가 보장되지 않는다. 예를 들어 인증 후 발급된 bearer 세션 비밀은 제시하는 쪽을 통과시키므로 비밀을 탈취한 쪽도 이용할 수 있다. 보호된 채널, 세션 비밀의 보호, 만료와 재인증은 초기 인증과 함께 설계한다.

종이 세션의 두 시계

이 단원의 가상 서버는 정수 분 단위의 단조 시간을 사용한다. 인증 성공 시 created=last=t, valid=true로 시작한다. 세션 검사는 valid이고 0≤t−created<12 및 0≤t−last<5일 때만 성공한다. 성공한 세션 검사만 last=t로 갱신하며 실패하면 valid=false로 만든다. 이는 자체 정책으로 NIST 시간 값이 아니다.

전체 수명은 활동으로 늘어나지 않고 비활동 시간만 갱신된다. 로그아웃은 valid=false로 만든다. 경계에서 등호를 허용하지 않으므로 정확히 5분 또는 12분이 되면 실패한다. 시간 역행과 동시 검사 문제를 제외한 순차 모형이며 실제 분산 서버의 시계·원자성·복구 계약은 추가로 필요하다.

모든 결과는 자체 순차 상태표다. 실패 뒤의 새 성공은 새 인증으로 세션을 만들었는지부터 구별한다.

중간 과정을 따라가는 예제

t=0에 두 요소 인증으로 세션을 만든다. t=4,9,10에 순서대로 검사한다. 위 정책의 결과와 last를 추적하라.

  1. t=0: created=last=0, valid=true로 둔다. 인증 성공 자체가 모든 자원의 수정 권한을 부여하지는 않는다.

  2. t=4: 전체 4<12, 비활동 4<5이므로 성공하고 last=4가 된다.

  3. t=9: 전체 9<12이지만 비활동 9−4=5가 엄격한 경계에 걸려 실패한다. valid=false가 된다.

  4. t=10: 비밀을 다시 제시해도 valid=false라 실패한다. last는 마지막 성공 값 4를 유지한다.

성공, 실패, 실패이며 last=4이다. 세션 재시작은 새 인증 절차의 결과여야 한다.

조건을 바꾸어 비교하기

비활동 만료와 전체 만료

서로 다른 새 세션에서 검사열 [3,7,8]과 [3,6,9,12,15]를 추적하라.

  1. 첫 열은 3분 성공 뒤 7−3=4로 실패하며 8분도 실패다.

  2. 둘째 열은 12분까지 성공하고 15분에서 전체 한도로 실패한다.

두 한도의 종류를 구별하고 실패 뒤에는 valid=false를 유지한다.

비교할 점

앞 열의 실패를 뒤 열에 섞지 않는다. 서로 별도 생성이다.

두 질문과 두 요소

비밀번호+PIN, 비밀번호+별도 보유 수단 검증을 비교하라.

  1. 첫 조합은 둘 다 알고 있는 지식 요소다.

  2. 둘째는 지식과 소유라는 종류가 다르지만 결합 절차도 확인해야 한다.

질문의 개수만으로 MFA를 판정하지 않는다.

한 단계 더

세션의 불변식은 성공 후 created≤last≤t이며 created는 새 인증 없이 바뀌지 않는다는 것이다. 생성 시 created=last=t라 성립한다. 성공 검사 전에는 t≥last≥created이고 성공 후 last를 현재 t로 바꾸므로 부등식이 보존된다. 실패와 로그아웃은 created와 last를 바꾸지 않으며 이후의 성공을 허용하지 않는다. 이는 단조 시간의 순차 모형에서만 한 귀납 논증이다. 재인증으로 수명을 재설정하려면 새 인증의 강도와 이전 세션 폐기 정책을 명시해야 한다. 실제 서비스의 NIST 적용 범위 및 AAL별 요구를 이 가상 시간표만으로 충족했다고 주장할 수 없다.

출처와 확인 범위
  • NIST SP 800-63B — Authentication and Authenticator Management

    AAL2의 서로 다른 인증 요소, 비밀번호의 salt·비용 인자를 갖는 해시 저장, Session Management의 세션 비밀과 만료 본문을 실제 읽었다. 아래 5분·12분은 자체 가상 정책이며 NIST 권고 시간을 재현하지 않는다.

접근통제·역할·capability

교사라는 이름이 붙으면 모든 학생의 성적을 고칠 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 객체는 보호할 문서·레코드 같은 자원이다. 행동은 read나 update처럼 그 자원에 수행하는 연산이다.

  • 집합 R의 부분집합 R′⊆R는 R′의 모든 원소가 R에도 있다는 뜻이다. {read}⊆{read,update}는 참이다.

  • 역할은 여러 주체에게 공통 권한을 묶어 부여하는 분류이다. ACL은 객체에 붙은 주체별 허용 목록이다.

학습 목표

  • 주체·객체·행동·상황을 포함한 허용 조건을 만든다.

  • 역할 기반 허용과 capability의 권한 축소를 비교한다.

권한 축소를 두 번 해도 원본보다 커질 수 없을까?

자체 원본 capability C0=(문서 41,{read,update},20)을 신뢰한 발급기가 만들었다. 축소는 객체 동일, 권한 부분집합, 만료 감소와 유효한 발급 연결을 요구한다. 임의 JSON을 편집하는 것이 아니라 이 검증 절차를 가정한다.

C1=(41,{read},16), C2=(41,{read},12)라면 read는 원본에도 있고 t<12이면 t<16과 t<20도 성립한다. 그러나 C0가 계속 유효하다면 C2의 축소가 C0를 자동 철회하지는 않는다. 원본 보유와 위임본 사용을 나누자.

먼저 확인할 개념
  • 접근통제·역할·capability

    이 절의 신뢰 값과 순차 정책을 확인한다.

  • 권한 상승과 감사

    인증·객체 권한·감사의 서로 다른 보장을 연결한다.

누가 무엇을 할 수 있는가

접근통제는 요청의 주체 u, 객체 o, 행동 a와 상황을 정책 P에 대조하는 판정이다. 기본 거절 모형은 명시한 허용 조건이 참일 때만 통과시킨다. 요청에 담긴 owner나 role 문자열은 신뢰할 수 있는 서버 정보와 구별해야 한다. 추측하기 어려운 객체 번호는 권한 검사를 대신하지 않는다.

가상 학교에서 학생은 자기 성적을 read할 수 있고 update할 수 없다. 교사는 자기 담당 학급의 성적을 read 또는 update할 수 있다. 따라서 역할과 함께 소유 관계 또는 학급 관계가 필요하다. 서버가 주체를 인증한 뒤 실제 객체의 학급을 조회하여 판정한다.

역할과 객체별 목록

RBAC는 사용자→역할과 역할→행동의 관계로 공통 규칙을 관리한다. 동일 역할에도 객체 범위를 덧붙이지 않으면 다른 학급으로 권한이 넓어질 수 있다. ACL은 특정 객체에서 어떤 주체에게 어떤 행동을 허용하는지 나열한다. 두 방식은 정책 표현 방법이지 구현의 정확성을 자동 보장하는 이름이 아니다.

이 모형에서는 학생 s의 read는 owner(o)=s일 때 허용하고, 교사 T의 read/update는 class(o)=assigned(T)일 때 허용한다. 그 밖은 거절한다. 모든 보호 연산의 진입점이 이 판정을 거쳐야 하며 화면의 버튼 숨김만으로는 서버의 정책을 시행하지 못한다.

capability와 줄어드는 권한

capability는 특정 객체와 연산 권한에 대한 위조 불가능한 증표이다. 여기서는 신뢰한 발급기가 만든 객체 번호·권한 집합·만료를 검증하는 추상 증표를 가정한다. 단순 JSON에 권한을 적은 것만으로 위조 불가능성이 생기지 않는다. bearer 방식이라면 이를 보유한 상대에게 권한이 전달되므로 전달과 보관도 정책 대상이다.

권한 축소가 허용된 발급 절차에서 원본 (o,R,e)로부터 (o,R′,e′)를 만들 때 R′⊆R, e′≤e를 요구한다. 검증기는 유효한 발급·위임 연결과 현재 t<e′를 확인한다. 따라서 축소본이 허용한 행동은 원본 권한에도 속한다. 객체 바꾸기나 권한 추가를 임의 문자열 편집으로 허용하지 않는다는 전제가 이 논증의 핵심이다.

중간 과정을 따라가는 예제

  1. s/read/X는 owner(X)=s라 허용한다.

  2. s/update/X는 학생 규칙의 행동에 update가 없어 거절한다.

  3. T/update/Y는 class(Y)=B≠A라 거절한다. 교사 역할만으로 통과시키지 않는다.

준비 개념

  • 권한 상승은 정책상 허용되지 않은 더 넓은 접근을 획득하는 일이다. 수직 상승은 더 높은 역할, 수평 상승은 같은 수준의 타인 자원 접근을 뜻한다.

  • 감사 기록은 관측한 사건을 나중에 추적하기 위한 자료이다. 기록의 주체 식별값은 실제 사람에 대한 완전한 증명이 아니다.

  • 원자 전이는 다른 전이가 중간에 끼지 않는 모형의 한 단계이다. 정책 버전은 어떤 규칙으로 판정했는지 구분하는 번호이다.

학습 목표

  • 요청 입력과 신뢰한 역할 정보를 구분한다.

  • 검사-사용 경계와 로그의 증거 범위를 설명한다.

정책 버전을 읽는 것과 원자적으로 쓰는 것은 같을까?

자체 서버에서 교사 서의 문서 41 수정 권한이 v3에는 있고 v4에서 철회된다. 이 단원은 실제 쓰기 시점의 현재 정책을 요구한다. 검사·쓰기·성공 감사 반영을 한 원자 전이로 정한 종이 모형에서 순서를 비교하자.

검사 결과를 따로 기억한 채 철회 뒤 쓰면 사용 시점 정책을 위반할 수 있다. 버전 번호 자체는 잠금이나 트랜잭션이 아니다. 로그의 계정이 남아도 그 사람이 직접 행위했다는 증명은 아니며 감사 실패 처리도 명시해야 한다.

먼저 확인할 개념
  • 권한 상승과 감사

    이 절의 신뢰 값과 순차 정책을 확인한다.

  • 비밀번호·MFA·세션

    인증·객체 권한·감사의 서로 다른 보장을 연결한다.

상승과 합법적인 권한 변경

교사가 승인 절차에 따라 새 담당 학급을 받는 것은 정상적인 권한 변경이다. 반면 클라이언트가 role=admin을 보내는 것만 믿고 서버가 관리자 행동을 허용하면 수직 권한 상승이 된다. 자기 성적 대신 다른 학생 성적에 접근하는 수평 상승도 같은 주체·객체·행동 정책 위반이다.

방어 모형은 인증으로 얻은 서버의 주체와 서버의 현재 역할·관계를 사용한다. 권한 부여 자체에도 누가 누구에게 어느 범위를 부여할 수 있는지 정책이 필요하다. 권한을 주는 기능을 일반 문서 수정 권한과 혼동하면 최소권한 설계가 무너진다.

확인한 뒤 쓰기 전의 틈

권한 검사를 통과한 다음 실제 쓰기 전에 권한이 철회될 수 있다. 검사 당시 허용을 요구하는 정책과 사용 시점에도 허용을 요구하는 정책은 서로 다르다. 이 단원은 사용 시점 정책을 택하고 현재 버전의 검사와 변경을 하나의 원자 전이로 묶는다. 철회가 먼저 일어나면 뒤의 쓰기는 거절한다.

버전 v를 읽었다는 사실만으로 원자성이 생기지 않는다. 실제 구현에는 검사-갱신의 동기화, 트랜잭션 또는 버전 비교를 이용한 충돌 처리와 실패 계약이 필요하다. 여기의 순차 원자 표는 그 계약의 의미를 설명하며 실제 데이터베이스나 운영체제의 성능·동시 안전성 시험은 아니다.

감사에서 알 수 있는 것

감사에는 요청 식별자, 관측한 주체, 객체, 행동, 허용/거절, 이유, 정책 버전 등을 정해진 형식으로 남긴다. 원 비밀번호나 bearer 토큰을 그대로 넣으면 로그가 새 유출 자원이 된다. 입력에 포함된 줄바꿈을 무비판적으로 기록해 가짜 사건처럼 보이게 하는 문제도 방지해야 한다.

기록 접근 제한과 변경 탐지, 보존 정책은 자료의 신뢰를 높이지만 기록만으로 예방이나 범인 확정이 되지는 않는다. 계정이 탈취되었거나 관측 지점 밖 사건이 누락될 수 있다. 서로 다른 기계의 시각만으로 전체 인과 순서를 확정하지 말고, 이 예제의 순번은 단일 서버가 관측한 순서로 한정한다.

중간 과정을 따라가는 예제

정책 v0에서 학생 s는 X 수정 불가이다. 다음 요청과 권한 변경을 순서대로 원자적으로 처리한다: s가 role=admin을 실어 X 수정, 신뢰한 관리자가 s에게 X 수정 권한 부여(v1), s가 X 수정, 관리자가 철회(v2) 후 s가 X 수정. 실제 역할 입력은 서버 정보만 쓴다.

  1. 첫 요청은 클라이언트 role을 권한으로 채택하지 않는다. v0에서 거절하며 X는 변하지 않는다.

  2. 정책 관리 권한을 가진 관리자의 부여 전이가 v1을 만든다. 이 행위는 승인된 권한 변경이다.

  3. s의 다음 수정은 현재 v1에서 허용된다. 성공 감사 사건에 주체 s, 객체 X, 행동 update, 버전 v1을 남긴다.

  4. 철회가 v2로 완료된 뒤의 수정은 거절한다. 이 단일 서버의 감사 순서와 정책 버전은 판정 근거를 보여 주지만 s라는 사람이 직접 요청했음을 증명하지는 않는다.

거절, 정상 부여, 허용, 철회 후 거절이다. 실패한 수정은 X를 바꾸지 않는 모형이다.

한 단계 더

보호된 쓰기의 불변식은 “각 성공 전이의 주체·객체·행동은 그 전이에서 사용한 정책 버전에 의해 허용되었다”이다. 처음에는 성공 기록이 없어 조건이 빈 경우로 성립한다. 다음 전이가 거절 또는 정책 변경이면 새 성공 쓰기가 없고 이전 기록의 버전별 판정은 바뀌지 않는다. 다음 전이가 성공 쓰기이면 같은 원자 전이에서 현재 정책 검사를 통과한 경우만 쓰기를 허용하므로 새 기록도 조건을 만족한다. 따라서 모든 진입점이 동일 판정을 통과하고 검사-사용이 원자적이라는 전제에서 귀납적으로 성립한다. 이는 나중의 철회가 과거 쓰기를 소급해 무효화한다는 뜻이 아니다. 감사 저장 실패 때 민감한 쓰기를 거절할지 별도 큐에 기록할지는 서비스 계약이며, 기록과 쓰기의 원자성·내구성이 없는 단순 함수 호출만으로 함께 성공했다고 주장할 수 없다.

유효 세션과 줄인 권한을 현재 정책에 연결하기

세션 created=0,last=9,valid=true를 t=12에 검사한다. 증표 C2=(41,{read},12)를 t=12에 제시하고 이전 v3 수정 승인을 v4 철회 뒤 재사용하려 한다. 세 검사와 안전한 감사 필드를 적어라.

힌트 1

세션은 전체 15분 미만·비활동 4분 미만이다.

힌트 2

증표 만료와 현재 정책은 세션 성공과 별개다.

풀이와 답 확인

  1. 전체 경과는 12분이고 비활동 경과는 12−9=3분이다. 각각 15분 미만과 4분 미만이라 세션 검사는 성공하고 last=12분으로 갱신한다.

  2. C2는 12<12가 거짓이라 거절이며 update 권한도 없다.

  3. v4 철회 뒤 수정은 현재 인가에서 거절한다. 과거 승인을 재사용하지 않는다.

  4. 요청 ID·주체·객체·행동·거절 이유·버전을 남기되 원 세션 비밀은 기록하지 않는다.

세션 성공만으로 객체 권한·증표 만료·현재 정책을 통과했다고 주장하지 않는다.

해결한 뒤 점검할 것

  • 세션의 두 시간 조건을 각각 계산했다.

  • 엄격한 증표 만료 경계를 지켰다.

  • 현재 인가와 원자성의 가정을 밝혔다.

  • 감사 관찰과 실제 행위자 확정을 구별했다.
