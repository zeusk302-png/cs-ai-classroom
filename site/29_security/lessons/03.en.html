Subtopic 3.1

Buffers, integers and use-after-free

Why can storage be insufficient even when a length is positive? May we read a value still visible after free?

Preparation and learning goals

Preparation

  • A buffer is storage for a fixed number of elements. Capacity C differs from current usage n. An array with C=4 has element indices 0,1,2,3. Readiness check: three content characters plus one terminator occupy four slots.
  • An integer type’s representable range is its set of possible values. Integer promotions and the usual arithmetic conversions determine the actual operation type before calculation. Do not use a small stored type’s width directly as the operation width.
  • Object lifetime is the period during which storage is guaranteed for access to that object. Aliases are different names or pointers referring to the same object. Clearing one alias does not automatically update others.

Learning goals

  • Determine read/write bounds and space for a terminator.
  • Check the operation type and representability of a length product first.
  • Distinguish object lifetime and permitted access through every alias before and after deallocation.

Elements within bounds and the one-past position

Spatial safety means that a read or write location is within the valid range of the relevant live object. In C11, if a is an array of N elements and 0≤i<N, a+i can point to that element. a+N can be formed as a one-past pointer, but that position cannot be dereferenced as an element. Observing other data nearby does not legalize access outside the array’s bounds.

Copying string content of length L together with its terminator requires L+1 slots. Checking C>0 and L≤C−1 for destination capacity C also reserves the terminator slot. Use this condition together with premises that the source is an actually readable string of that length, the destination is writable, and the selected copying function’s overlap contract is satisfied. A length value alone proves neither pointer validity nor lifetime.

Check length calculations before performing them

Mathematically, n elements of size s require ns storage units. Actual integer operations first need a representability check for the result type. In C11, if the operation’s result type is unsigned, an arithmetic result above its maximum M is reduced modulo M+1. Although this modular behavior is defined, it can lose the mathematical length intended for an allocation. An unrepresentable arithmetic result in a signed result type is UB: do not give a small negative result or an inevitable crash as its predicted value.

For positive s and 0≤n≤M, checking n≤floor(M/s) establishes ns≤M before multiplication. In actual C, apply a SIZE_MAX/sizeof(element) check consistently with the actual operation type and conversion rules. Reject negative input before conversion to a size type, and check addition n+h before calculation, for example using n≤M−h. Obtaining a legal small allocation size does not imply that the original request was small.

Remaining bytes do not restore an ended lifetime

Temporal safety means that the target object’s lifetime is still valid when accessed. If p and q refer to successfully allocated object O and free(p) deallocates it, O’s lifetime ends. In C11, pointer values referring to O or its one-past position become indeterminate. Do not assume that reading and using such a value again is a permitted normal pointer operation, in addition to the use-after-free caused by dereferencing q. free(NULL), which does nothing, is a separate rule.

Assigning p=NULL after free(p) writes a new value into pointer object p without reading its previous deallocated value, but does not repair q. Design live ownership paths so that deallocation happens once, after all access ends, or delay deallocation if other accessors remain. In C++, separately check delete, object lifetime and invalidation on container reallocation against the applicable standard/API. The details of free and promotions here are C11 conditions and must not be copied as all C++ rules.

A worked example, step by step

Judge independent paper cases. Copy strings of L=7 and L=8 into capacity C=8, including the terminator. A separate hypothetical unsigned operation is defined to have result range 0..255, with n=70,s=4. Successfully allocated O has aliases p,q, and p is assigned NULL after deallocation.

  1. The first copy needs L+1=8 slots and satisfies L≤C−1. Write indices are 0..7; the last slot is the terminator.
  2. The second needs L+1=9>8 and is rejected. Do not predict the last value or subsequent control flow of an actual C program copying without the check.
  3. The hypothetical result type’s mathematical product is 280; its modular value is 280 mod256=24. The precheck limit is floor(255/4)=63, so 70 is rejected. This is not a measurement of the promoted result of an actual unsigned char multiplication.
  4. Before deallocation, p and q refer to O. After deallocation, O’s lifetime has ended. Writing NULL into p does not make access to q’s old value valid again. No output value for q is supplied.

The first copy is conditionally permitted; the second is rejected. The hypothetical product reduces to 24, but the allocation calculation must be rejected in advance. Alias access after deallocation is not permitted, and no predicted UB output is given.

Try it with paper and the lesson

Judge the conditions for copying content of length 5/6 into capacity C=6. Also check n=60,s=4 in the same hypothetical 0..255 operation. If only p among aliases p,q is assigned NULL and the object has not yet been deallocated, what happens to q and the object’s lifetime?

Show hint

Add a terminator slot and compare with floor(255/4)=63. Distinguish changing a pointer variable from ending the object’s lifetime with free.

Show solution

Length 5 needs six slots and is conditionally permitted; length 6 needs seven and is rejected. Since 60≤63 and 240≤255, the product is preserved. Without deallocation, reassigning p alone does not end O’s lifetime; the live O referred to by q remains. Separately check whether later loss of the only ownership path could cause a leak.

Misconception and counterexample

Using unsigned removes memory problems, and a value that looks unchanged after free is safe.

The hypothetical 24 from 70×4 is defined but does not represent the required 280 slots. Observing unchanged deallocated bytes does not restore object lifetime. Judge bounds and lifetime by language/object contracts, not output.

Check your understanding

Because a+N can be formed for an N-element array, may its element be read?

Show answer and reasoning

No.

Forming a one-past pointer and dereferencing that position have different conditions.

If hypothetical unsigned result range 0..255 gives 70×4 as 24, is mathematical 280 the same allocation request as 24?

Show answer and reasoning

No.

The modular result differs from the original required total, so the length precheck rejects it.

If p=NULL after free, is q, which referred to the same O, automatically NULL too?

Show answer and reasoning

No.

Assigning a pointer object does not update other aliases. The deallocated target’s lifetime has ended.

Explore further

Proof: for integers 0≤n≤M and s≥1, n≤floor(M/s) implies ns≤M, while n>floor(M/s) implies ns>M. Write q=floor(M/s), M=qs+r,0≤r<s. If n≥q+1, then ns≥qs+s>qs+r=M. Thus, under these conditions, the check is necessary and sufficient for representability of the product. Allocation success, actual object size, alignment, write permission and lifetime are additional premises. For C≥1, L content slots plus one terminator give equivalent conditions L+1≤C and L≤C−1. Lifetime safety separately requires every access event e to occur within that object’s live interval; a length inequality alone cannot prove it.

Subtopic 3.2

Input and control flow

If content was read as characters, how could it change the next action to execute?

Preparation and learning goals

Preparation

  • Input is a value arriving from outside a function, not necessarily trustworthy state. Parsing interprets bytes/fields into a specified data structure; validation checks whether interpreted values satisfy a contract.
  • Control flow determines the next execution location through branches, calls and returns. Data supplies values to those calculations. Distinguish legal branching on input from corrupted control data.
  • Readiness check: in paper command table {0:view,1:save}, input 2 does not automatically mean any function. Define a contract rejecting values outside the table’s domain.

Learning goals

  • Compare a declared length with actual input size before use.
  • Distinguish checks for valid command kinds, lifetime and permissions.
  • Explain the different guarantees of memory safety, control-flow integrity and request authorization.

Interpret values crossing a trust boundary first

The original packet model receives an already readable byte sequence, already interpreted integer fields h=content length and op=command, and actually available content r. Copy-buffer capacity C is specified separately. A declared length h does not make h actual slots exist. Checking h≤r and h≤C before access bounds both source and destination in this model. A terminated string requires a separate contract for h+1 slots and checking an actual terminator.

Distinguish integer interpretation errors, negatives, units, versions and character encodings, and state the rejection criterion. Narrowing a longer raw input to a short type before checking can lose its original magnitude. If checked storage can be replaced, deallocated or modified before use, validation and use may see different states. This subtopic is restricted to a sequential model with input and policy fixed throughout the call.

Different ways data-access errors can change actions

A memory error can damage content itself or affect values used for control. In particular implementations, damaged function pointers or return information, or damaged data used by conditional checks, can change subsequent actions. Out-of-bounds writes in standard C are UB, so do not treat a diagram placing a return address immediately after every array as a general rule. Out-of-bounds reads can also risk disclosure of data that should not be public.

Maintaining an allowed function-call table differs from maintaining a requester’s permission to save. Even if valid command op=1 maps to allowed function save, the subject may lack permission to save that data. Conversely, checking that all input consists of certain characters does not automatically establish buffer length, object lifetime or authorization. State each success condition separately and use their conjunction.

Restrict success to requests that pass the checks

The model first checks the nonnegative-integer contract for h, then h≤r and h≤C, then op∈{0,1}, and finally authorization. Define op=0 as permitted viewing and op=1 as permitted only when can_write is true. Reject without copying or acting if any check fails; only on success copy h slots and act through the fixed table. Actual parser error recovery and concurrent request state are not part of this contract.

To prove the policy, use the invariant that length conditions, an allowed command and authorization are all true for every successful request. Numeric checks alone cannot establish memory safety without caller premises that the source actually has r live slots and the destination has C writable slots. Record the guaranteed input, state and behavior rather than merely a validation function’s success label.

A worked example, step by step

Assume C=4, fixed input/policy, a writable destination and a live source. Check four requests (h,r,op,can_write)=(3,3,0,false),(4,3,0,false),(2,2,2,true),(2,2,1,false) in order. This is a byte-copy model requiring no terminator.

  1. The first satisfies 3≤3 and 3≤4, and op0 is allowed, so viewing succeeds. Copy indices are 0,1,2; can_write is not required for viewing permission.
  2. The second has 4>r3 and is rejected for insufficient actual input. It could fit the destination but fails the source-reading condition.
  3. The third passes length checks but op2 is outside the table’s domain and is rejected. Do not execute by treating the input value as an arbitrary function address.
  4. The fourth passes length and op1 checks but can_write=false, so it is rejected. Successful memory-bounds checks do not replace write authorization.

Only the first request succeeds: viewing and copying three slots. The others are rejected for different reasons: actual input length, command kind and authorization. These are not observations of actual service responses.

Try it with paper and the lesson

For C=4, judge (4,4,1,true),(5,5,0,false),(0,0,0,false). The last provides a valid live object/view representing empty input; it is not a case of passing a NULL pointer to a library function. What if only can_write in the first request changes to false?

Show hint

Compare length separately with C and r. The h=0 copy is an original loop accessing no elements. Check command and authorization all the way through.

Show solution

The first succeeds in saving four slots; the second is rejected for destination capacity 5>4; the third succeeds in viewing zero slots. Changing the first request’s permission to false rejects saving. An empty loop does not automatically satisfy every library’s NULL contract for input pointers.

Misconception and counterexample

Restricting input characters alone proves memory safety and permission to save.

Even four allowed characters can violate a length contract when written into a three-slot buffer. A length-valid op1 is still rejected if authorization is false. Conversely, even input with valid length and authorization violates lifetime if it uses a deallocated buffer, so another premise is needed.

Check your understanding

Does checking only h≤C permit reading h source slots?

Show answer and reasoning

No.

Actually readable r and source lifetime must also be checked.

If op1 is in the allowed function table, may it save when can_write=false?

Show answer and reasoning

No.

An allowed control target and a requester’s authorization are different conditions.

Does an out-of-bounds write to a C array necessarily change only the immediately following return-address slot?

Show answer and reasoning

No.

Layout varies by implementation, and standard C’s UB guarantees neither subsequent state nor a successful attack.

Explore further

Proof: under fixed state, a request passing every check satisfies 0≤h≤min(r,C), op∈{0,1}, and (op=1⇒can_write). Set i=0 before copying, loop condition i<h, and invariant 0≤i≤h. At access, i<h≤r,C, so the index is within both ranges. Increasing i by one preserves i≤h. The nonnegative integer h−i decreases each time, establishing termination. For h=0, the loop ends without access. This proof relies on defined arithmetic, live objects and fixed input; it is not full conformance proof for actual C pointers or a command parser. Adding a concurrent model in which policy changes after success requires new authorization-at-use and atomic-boundary definitions.

Subtopic 3.3

Isolated exercise environments and reproduction

How much does a record of one stop on the same input explain about the cause and completion of a fix?

Preparation and learning goals

Preparation

  • Reproduction reconstructs specified conditions to check whether a particular observation can be repeated. Source, input, tool versions, options and execution state are conditions; exit code, standard output and error output are observations.
  • Isolation configures limits on writes, connections and permissions during an exercise. The name virtual machine or container alone does not remove external connections or access to host files. An environment plan can be drawn on paper without installation.
  • Readiness check: is running a different binary on the same input the same experiment? Compare source SHA, build options, executable SHA and runtime together.

Learning goals

  • Write an exercise plan covering self-owned code, isolation and blocked external connections.
  • Record causal arguments, expected results and actual observations in separate columns.
  • State the scope of fixed-input regression results and unperformed tests.

The basic path is paper; optional execution fixes the ownership boundary

The basic activities draw object slots, lengths and event tables and require no execution environment. If designing optional execution, restrict it to small normal code you wrote and are authorized to use, synthetic input and a working directory without secrets. Existing services, arbitrary sites, actual personal data and external devices are excluded. Understanding the concept does not require executing a vulnerable variation.

An optional exercise’s boundary plan includes how to disable network adapters/egress, conditions avoiding host-folder sharing, clipboard and device connections, non-administrator execution, time/memory limits, and exit/reset procedures. Do not mark isolation complete before checking that these settings actually apply. A virtual-machine snapshot can define a restoration state, but does not guarantee reversal of damage to external networks or host assets.

Bundle exact code with tool conditions

An execution plan preserves full source and SHA-256, full input and hash, compiler/standard mode/libraries/OS/architecture, exact command/working directory, built-file hash and exit code/stdout/stderr. If using a sanitizer, also record version, instrumentation options, runtime, suppression lists and uninstrumented modules. The same source hash alone implies neither the same binary nor the same execution state.

AddressSanitizer detects memory errors in instrumented execution, with configuration-specific checks and support boundaries. Absence of a report does not prove safety for every input, path, object lifetime and integer operation. The documentation also states that this runtime is not a production security protection mechanism. Do not record options or speeds from web documentation as specifications installed and executed on the current computer.

Distinguish causes, observations and the scope of fixes

A crash is an observation that a process stopped; its cause needs a separate argument. Establish a bounds violation or access after lifetime end through the language contract and trace the relationship between that code path and the reported location. Do not predict a particular output or an identical crash every time for UB. Instrumented and uninstrumented execution may change memory layout and performance, so observation conditions differ too.

A fix is a concrete change to check placement or ownership; a regression test separately observes that change on selected inputs. Recording that a hypothetical table covers n=0, a boundary and an excessive value is not a security proof of the entire C program or classroom validation. Do not hide failed reproduction: record condition differences, unperformed execution and failed source access separately.

A worked example, step by step

Audit original paper records. A lists source S, input I and options O, with only “normal result expected.” B has source S but options O2/executable X2 and “assume an error exit was observed.” C has a modified version of source S/input I and a normal expected result. None of the three was actually executed.

  1. A’s expected value is not an observation. Do not fill environment, command, build hash, stdout/stderr or exit code without actual performance of the run; mark execution as unperformed.
  2. B has different options and a different binary, so it cannot be grouped with A as a same-environment repeat. The error exit is also a fictional record statement, not an actual observation here.
  3. C changes code and therefore needs a new source SHA. A normal-result expectation alone proves neither a passing regression execution on I nor elimination of all vulnerabilities.
  4. In the cause column, write the assumed bounds inequalities and lifetime premises; in the observation column, write unperformed; in the scope column, write paper model of synthetic input I only. Separate source, execution, causal argument and proof status.

A/B/C are all paper records. B is not a same-environment reproduction of A, and C is not evidence of a passing actual regression. There is no actual crash or sanitizer output.

Try it with paper and the lesson

A new paper plan selects synthetic input lengths 0,4,5 for allowed range 0..4. It has only full-source/input hashes, with no OS, compiler options, egress or output record. Write the conditions to add and each input’s expected length judgment, and decide whether the plan may be reported as actually complete.

Show hint

Distinguish two allowed values from one excessive value. Separate environment/isolation plans from actual checks, and do not fabricate observations to fill the record.

Show solution

Lengths 0 and 4 are expected to pass the length condition; 5 is expected to be rejected. Plan OS/architecture, compiler/runtime/version, standard mode/options, command/folder, binary SHA, permissions/egress/host sharing, resource limits and reset procedures. Fill exit code/stdout/stderr only after actual execution. This activity is an unexecuted plan and cannot be recorded as a completed or passing exercise.

Misconception and counterexample

No sanitizer warning and execution in a container mean safety on all inputs and complete isolation.

Unexecuted paths or uninstrumented modules may be outside observation scope. A container with host write permission or external egress is not isolated merely by its name. Error detection, configured isolation and a proof of overall safety are different claims.

Check your understanding

If source hashes match, do executions with different options/libraries reproduce the same environment?

Show answer and reasoning

No.

Conditions affecting build results and execution state remain, so record them separately.

Does absence of a crash prove all C bounds/lifetime conditions were satisfied?

Show answer and reasoning

No.

UB does not appear only as crashes, and finite observations do not include other inputs or paths.

May actual stdout be invented for this activity, which only writes paper expectations?

Show answer and reasoning

No.

Separate expected results from actual observations and retain the unperformed-execution status.

Explore further

Extension: for specification P and finite test set T, passing the observational judgment of P for every t∈T generally does not imply ∀x∈D:P(x) for the entire input set D. For example, with D={0,1,2,3,4,5}, T={0,4}, and Q(x)=(x≤4), Q is true on T but false at x=5. Even if T=D, concluding that finite proposition requires actually checking all model inputs, a correct oracle and fixed hidden-state conditions. A source SHA proves byte identity, not certification of a proof of P. Define reproduction record R=(source,input,build,environment,initialstate,observation). Comparing all coordinates except observation first distinguishes tracing a cause by changing one variable from repeating identical conditions. This manuscript only supplies a plan for R and creates no actual observation values for R.
