소단원 11.1

정적 분석·fuzzing

코드를 읽는 검사와 이상한 입력을 계속 넣는 검사는 같은 실수를 찾을까?

준비 개념과 학습 목표

준비 개념

  • 배열 인덱스와 길이

  • 조건문

  • 함수의 입력과 출력

학습 목표

  • 정적 분석과 입력 기반 동적 탐색을 구별한다.

  • 테스트 대상·초기 입력·오류 판정 기준을 설계한다.

  • 경고와 커버리지를 실제 취약성 증거와 구별한다.

더 많은 길을 지나갔다면 결과도 더 정확해졌을까요?

운동장의 모든 길을 걸어 봤다는 말과 각 길에서 규칙을 지켰다는 말은 다르다. 프로그램의 커버리지도 어떤 실행 지점에 도달했는지 알려 주지만 출력 명세와 입력 안전성을 전부 증명하지 않는다. 아래 집합은 코드의 실제 측정값이 아닌 자체 가상 경로 이름이다.

시험 연결 코드도 확인 대상이다. 입력이 파서에 실제 전달되어야 하고 상태가 누적되면 같은 바이트가 순서에 따라 다른 결과를 낼 수 있다. 정적 경고·실행 중 메모리 오류·출력 명세 위반을 서로 다른 기록으로 남겨야 무엇을 확인했는지 말할 수 있다.

먼저 확인할 개념
  • 정적 분석·fuzzing

    배열 길이·접두 길이와 오류 판정기를 구별한다.

  • 재현·원인·수정

    경고나 입력 축소 뒤에도 실제 원인을 다시 확인해야 하는 이유를 연결한다.

실행하지 않고 가능한 경로를 살핀다

정적 분석은 소스나 중간 표현을 대상으로 문제 경로를 추론한다. 예를 들어 포인터가 null인 경우 뒤에서 역참조하는지, 배열 범위를 넘는 인덱스가 가능한지 살핀다. 심볼릭 실행에서는 특정 숫자 대신 기호 입력과 경로 조건을 사용한다. 모든 도구가 모든 경로를 완벽히 다루지는 않는다.

분석 경고는 확인할 후보다. 실제 호출 계약이나 도구가 모르는 함수 때문에 오탐이 생길 수 있고, 분석하지 않은 코드에서 문제를 놓칠 수도 있다. 경고를 없애는 주석이나 억제는 잘못된 입력 처리를 수정하는 것과 다르다. 먼저 입력이 어디서 오고 경로가 실제 가능한지 확인한다.

fuzzing은 입력을 바꾸며 실제 동작을 탐색한다

Fuzzing은 시험 대상을 반복 실행하며 입력을 생성하거나 변형한다. 대상 함수와 호출을 묶은 시험용 연결 코드를 harness라고 한다. 씨앗 입력들의 모음을 코퍼스라고 부른다. 커버리지 기반 방식은 새 코드 경로에 도달한 입력을 후속 변형의 재료로 삼는다.

임의 입력에는 빈 배열·짧은 헤더·큰 길이·형식이 틀린 데이터도 있다. 파서는 이를 안전하게 거절해야 한다. 작은 대상 함수가 상태를 초기화하고 같은 입력에서 같은 결과를 내도록 하면 원인을 찾기 쉽다. 실제 업무 서비스 대신 자신이 소유하거나 시험 허가가 있는 격리된 코드로 범위를 정한다.

무엇이 실패인지 먼저 정한다

크래시, sanitizer 보고, 시간 제한 초과, 명세를 어긴 결과는 서로 다른 판정 기준이다. Sanitizer는 실행 중의 메모리 오류 등을 감지하도록 계측한다. 단순히 프로세스가 종료하지 않았다는 사실만으로 논리 결과까지 옳다고 할 수 없다.

특정 기간에 오류가 발견되지 않았거나 커버리지가 증가해도 모든 입력이 안전하다는 증명이 되지는 않는다. 보고에는 대상 버전·설정·입력·판정 기준을 적는다. 이 단원은 작은 파서의 손추적으로 탐색 원리를 배우며 실제 도구를 돌렸다고 주장하지 않는다.

크래시 유무만으로 대체하지 않음

경로 집합을 합칠 때 중복을 다시 세지 않는다. 숫자는 이 문제에서 정의한 관찰 항목일 뿐 실제 도구의 모든 커버리지 종류를 대표하지 않는다.

중간 과정을 따라가는 예제

첫 바이트가 본문 길이 L인 입력을 생각하자. 잘못된 파서는 n≥1만 확인하고 i=0..L−1에서 data[1+i]를 읽는다. 전체 길이 n=2인 [3,65]에서 어떤 일이 생기는가?

  1. 길이 접두 바이트는 3이고 실제 본문은 65 한 바이트뿐이다.

  2. i = 0의 인덱스 1은 유효하다. i = 1의 인덱스 2는 배열의 유효 범위 0..1 밖이다. 최초 범위 오류가 여기서 생긴다.

  3. 정적 검사는 L과 n의 관계가 보장되지 않는 경로를 의심할 수 있다. 실제 동적 시험에서는 해당 입력으로 잘못된 읽기에 도달한다. 도구가 반드시 탐지한다고 단정하지 않는다.

  4. Harness는 바이트 배열과 실제 n을 파서에 전달하고 오류 판정기를 함께 사용해야 한다. [0]·[1,65] 같은 정상 씨앗과 [3,65] 같은 비정상 입력을 구분해 저장한다.

문제는 읽기 전에 L ≤ n − 1을 보장하지 않은 것이다. n = 2, L = 3에서 최초 잘못된 인덱스는 2다.

조건을 바꾸어 비교하기

두 입력의 경로를 합치기

전체 가상 경로는 {A,B,C,D,E,F}이다. 입력 X는 {A,B,D}, Y는 {A,C,D}에 도달한다고 문제에 주어졌다. 각 입력 수와 합집합 커버리지를 계산하라.

  1. 각 입력은 경로 3개에 도달한다.

  2. 합집합은 {A,B,C,D} 네 개이다.

  3. 전체 6개 중 4개로 4/6=2/3이다. 중복 A,D를 두 번 세지 않는다.

합집합 도달 4개·가상 비율 2/3이다.

비교할 점

3+3을 곧바로 전체 6개 도달로 해석할 수 없다.

살아 있는 프로그램의 틀린 합

자체 파서의 명세는 길이가 맞으면 본문 바이트의 합을 반환한다. 입력[2,4,7]의 본문은 4와 7이다. 후보 P는 크래시 없이 11을 반환, Q는 크래시 없이 7을 반환한다고 문제에 주어졌다.

  1. 접두 2와 실제 본문 수 2가 맞는다.

  2. 명세의 기대 합은 4+7=11이다.

  3. P는 기대 결과와 같고 Q는 생존했어도 결과가 다르다.

P만 이 출력 기준을 만족한다. 실제 실행은 수행하지 않았다.

비교할 점

메모리 오류 판정기와 출력 명세 판정기는 서로를 대신하지 않는다.

종이와 본문으로 직접 해보기

[0], [1,65], [2,65,66], [2,65]를 길이 규약과 대조하라. 네 입력을 모두 읽어도 긴 본문 입력의 안전이 증명되나?

힌트 보기

전체 길이 n에서 접두 한 바이트를 빼 실제 본문 수를 센다.

풀이 보기

앞의 세 입력은 각각 0·1·2 바이트 본문으로 길이가 맞다. 마지막은 L = 2지만 실제 본문은 1바이트라 거절해야 한다. 네 사례 통과는 이 네 사례의 결과이며 모든 입력의 안전 증명이 아니다.

오해와 반례

정적 분석 경고가 없고 커버리지가 높으면 취약성이 없다.

분석 범위·가정·판정 기준의 한계가 있다. 높아진 커버리지는 더 많은 실행 지점을 관찰했다는 증거이며 명세와 모든 입력에 대한 완전성을 보장하지 않는다.

힌트 1

힌트 2

풀이와 답 확인

  2. F만 미도달이다.

연습 2 · 오류 찾아 고치기

시험 연결 코드가 입력 바이트를 받지만 항상 고정 [0]만 파서에 전달한다. 입력 100개가 들어왔고 크래시가 없다는 기록으로 파서의 100개 입력 안전성을 주장했다. 고쳐라.

힌트 1

힌트 2

풀이와 답 확인

  1. 파서는 주어진 연결에서[0]만 받는다.

  2. 생성 바이트와 실제 길이를 대상에 전달하고 판정 결과를 연결해야 한다.

100개 서로 다른 생성 입력이 파서까지 전달됐다는 증거가 없다. 연결을 수정한 시험 계획으로 남긴다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

바이트 대신 0/1/2 세 기호만 쓰는 길이 2의 고정 입력 공간이다. 서로 다른 입력 4개를 검사했다. 가능한 전체와 검사 비율을 구하고 실제 가변 길이 파서의 완전성으로 옮길 수 있는지 말하라.

  2. 가변 길이·256가지 바이트 등의 실제 공간은 이 모형과 다르다.

더 짧은 실패 입력이면 같은 원인을 찾은 것일까요?

원본을 보존하고 복사본을 줄이는 것은 실험 조건을 통제하는 일이다. 짧아진 입력이 여전히 잘못된 배열 접근을 만들더라도 다른 위치·원인의 오류일 수 있다. 종이 손추적은 가능 경로를 설명하며 실제 동일 sanitizer 보고의 재현 확인과 구별한다.

형식 계약도 먼저 정하자. 이 단원의 기본 규약은 헤더 한 바이트와 정확히 L개 본문이며 뒤 바이트를 허용하지 않는다. “최소한 L개만 있으면 된다”는 다른 규약을 혼용하면 안전한 읽기와 올바른 형식 승인을 혼동하게 된다.

먼저 확인할 개념
  • 재현·원인·수정

    빈 입력을 먼저 거절하고 엄격한 길이를 검사하는 순서를 확인한다.

  • 회귀시험과 책임 있는 보고

    정상 입력을 보존하는 수정과 미실행 회귀시험 표를 연결한다.

같은 입력만으로 충분하지 않을 수 있다

재현은 기록한 조건에서 같은 문제를 다시 관찰하는 과정이다. 원본 입력의 바이트와 길이, 코드 커밋, 컴파일러·빌드 옵션, 운영체제·아키텍처, 계측 도구를 함께 보존한다. 시간 초과는 제한값까지 기록한다. 같은 파일도 다른 빌드에서는 관찰 결과가 달라질 수 있다.

원본 증거는 그대로 두고 복사본을 줄인다. 입력 축소는 작게 만드는 것 자체가 목적이 아니라 동일한 실패 조건을 유지하며 불필요한 요소를 없애는 일이다. 더 짧은 입력이 다른 오류로 죽었다면 같은 원인의 최소 사례라고 즉시 결론내리지 않는다.

증상 위치에서 잘못된 가정으로 거슬러 올라간다

오류 보고의 읽기 위치는 증상일 수 있다. 그 위치가 받은 길이 값은 누가 만들었는지, 입력 길이와 어느 시점에 대조했는지 찾아간다. 잘못된 배열 접근을 가리는 try-catch나 오류 보고 억제로 입력 계약이 올바르게 되는 것은 아니다.

앞 파서의 규약을 이 예제에서는 엄격하게 정하자. 헤더가 존재하고 본문 수가 정확히 L이며 뒤따르는 바이트가 없는 형식만 받는다. 이 명세는 길이보다 큰 입력도 허용하는 다른 형식과 다르다. 무엇을 허용할지 결정해야 조건식이 맞는지 평가할 수 있다.

접근 전에 안전한 조건을 확보한다

먼저 n = 0이면 헤더를 읽지 않고 거절한다. 다음 L을 읽어 L = n − 1인지 확인한 후 본문을 읽는다. 이 순서이면 n − 1은 음수가 되는 빈 입력에서 계산되지 않으며, 0 ≤ i < L인 본문 인덱스 1 + i는 n − 1 이하임을 보일 수 있다. 실제 C에서는 n의 타입과 정수 변환까지 살펴야 한다.

본문 길이 L은 한 바이트 수치라 0..255지만 실제 입력 크기 n은 별도다. 전체 길이를 작은 타입에 무심코 줄여 비교하면 큰 입력이 다른 값으로 바뀔 수 있다. 여기서는 충분한 범위의 길이 타입에서 비교하는 추상 알고리즘을 사용한다. 수정은 악성처럼 보이는 한 파일 이름을 차단하는 방식이 아니다.

중간 과정을 따라가는 예제

엄격한 길이 접두 규약에 맞게 앞 파서를 고쳐 [3,65], [1,65], [0], 빈 배열을 손추적하라.

  1. 규칙은 n = 0이면 거절, 그렇지 않으면 L = data[0]을 읽고 L ≠ n − 1이면 거절, 같으면 i = 0..L − 1의 본문을 읽는 순서다.

  2. [3,65]는 n = 2, L = 3, n − 1 = 1이라 본문 읽기 전에 거절한다.

  3. [1,65]는 n = 2, L = 1로 검사 통과 후 인덱스 1의 65를 읽는다. [0]은 n = 1, L = 0이라 빈 반복으로 받아들인다.

  4. 빈 배열은 첫 검사에서 거절하여 data[0]에 접근하지 않는다.

  5. 통과한 일반 입력에서 i ≤ L − 1 = n − 2이므로 1 + i ≤ n − 1이다. L = 0일 때는 반복이 없어 별도로 안전하다.

네 입력은 거절/허용/허용/거절이다. 수정의 근거는 입력 길이와 접두 길이 관계를 접근 전에 보장한 것이다.

연습 1 · 값과 상태 예측

연습 2 · 오류 찾아 고치기

힌트 1

힌트 2

거절의 위치를 헤더 읽기 전으로 옮긴다.

풀이와 답 확인

  1. 먼저 n=0이면 즉시 거절한다.

  2. 그렇지 않을 때만 data[0]을 읽고 엄격 길이를 검사한다.

빈 입력의 헤더 접근을 없앤 순서가 필요하다. 실제 구현 언어의 평가·타입 규칙은 추가 확인한다.

흔한 오답에서 다시 생각하기

최종 거절만 같으면 중간 범위 오류는 없다.

결과 전에 이미 잘못된 접근을 시도했다. 접근 전 조건을 확보해야 한다.

연습 3 · 직접 만들어 보기

엄격 길이 확인 뒤 0≤i<L만 읽는다고 하자. L≥1인 일반 경우의 최대 인덱스를 식으로 적고 L=0을 따로 설명하라.

힌트 1

최대 i는 L−1이다.

힌트 2

승인 조건 L=n−1을 대입한다.

풀이와 답 확인

  1. 최대 접근 1+(L−1)=L=n−1이다.

  2. 최소는 1이며 L≥1일 때 n≥2라 존재한다. L=0은 반복이 없어 본문 접근이 없다.

본문 접근은 유효 범위 안이며 L=0은 빈 반복이다. 이는 추상 알고리즘의 경계 논증이다.

흔한 오답에서 다시 생각하기

L=0에도 인덱스 1을 한 번 읽는다.

반복 조건 0≤i<0을 만족하는 i가 없다. 빈 반복을 한 번 실행하는 것으로 읽지 않는다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

원래 잘못된 파서는 n≥1만 검사한 뒤 i를 0부터 L−1까지 바꾸며 data[1+i]를 읽는다. 입력 [3,65,66]을 [3,65]와 [3]로 줄였다. 최초 범위 밖 인덱스를 각각 구하고 “같은 실제 오류 보고”까지 입증했는지 설명하라.

힌트 1

각 배열의 실제 n을 다시 센다.

힌트 2

인덱스 1부터 순서대로 비교한다.

풀이와 답 확인

  1. 원본의 n=3은 인덱스 1과 2 다음의 3에서 처음 범위 밖을 시도한다.

  2. n=2인 복사본은 인덱스 2, n=1인 복사본은 인덱스 1이 최초 범위 밖이다.

  3. 세 경우의 길이 불일치 원리는 같지만 실제 실행 보고를 관찰하지 않았다.

최초 인덱스 3·2·1이며 같은 실제 보고의 재현 완료로 표시하지 않는다.

소단원 11.3

회귀시험과 책임 있는 보고

버그 한 개가 고쳐졌다는 말에 어떤 시험과 기록을 붙이면 다른 사람이 확인할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 재현 입력과 명세

  • 수정 전후 비교

  • 공개 저장소와 비공개 연락

학습 목표

  • 수정 사례와 정상 사례를 포함하는 회귀시험표를 만든다.

  • 실행 결과와 기대 결과를 구별한다.

  • 확인 사실과 미확인 영향을 분리해 보고와 공개를 조율한다.

시험표를 채웠다는 말과 실행했다는 말은 어떻게 다를까요?

시험 계획의 기대값은 명세에서 나온다. 실제 결과는 정해진 빌드와 입력을 실행하여 관찰한 값이다. 이 활동은 승인 여부와 거절 조건 및 정상 본문 값을 종이에 계산하므로 실제 결과 칸은 계속 미실행으로 둔다.

보고도 확인한 범위를 유지한다. 작은 파서의 손추적에서 범위 오류 가능성을 찾았다고 원격 서비스의 악용이나 모든 버전 영향을 확인한 것은 아니다. 실제 제보는 프로젝트의 보안 정책과 비공개 경로를 확인하고 공개 일정은 조율한다. 이 단원은 외부 보고나 메시지를 보내지 않는다.

먼저 확인할 개념
  • 회귀시험과 책임 있는 보고

    기대 결과·실제 결과 및 공개/비공개 보고의 다른 단계를 확인한다.

  • 정적 분석·fuzzing

    커버리지·판정 기준과 시험의 확인 범위를 연결한다.

같은 문제가 다시 들어오지 않도록 시험한다

회귀시험은 과거에 고쳤던 동작이 변경 후에도 유지되는지 확인하는 시험이다. 재현 입력만 거절하도록 만든 수정은 정상 입력까지 거절할 수 있으므로 허용 사례도 필요하다. 시험마다 입력·기대 결과·실제 결과·판정 기준을 적는다. 아직 실행하지 않았다면 실제 결과 칸은 미실행이다.

이 파서의 기대 결과는 정상 입력에서는 정확한 본문을 반환하고, 길이가 맞지 않거나 헤더가 없으면 안전하게 거절하는 것이다. 거절하면서 크래시가 나는 것은 통과가 아니다. 오류 탐지 계측과 출력 검사를 함께 설계한다. 여기서는 시험표를 손검토할 뿐 CI가 성공했다고 말하지 않는다.

확인한 영향과 추정한 영향을 구별한다

크래시나 범위 밖 읽기가 확인되었다고 원격 코드 실행·모든 버전 영향까지 확인된 것은 아니다. 보고는 관찰한 현상, 도달 조건, 시험한 버전, 예상 보안 영향, 확인하지 않은 항목을 나눈다. 동일 입력으로 동일 원인에 도달한 여러 보고는 개별 사건 수와 원인 수가 다를 수 있다.

실제 취약성 제보가 필요하면 해당 프로젝트의 보안 정책과 비공개 경로를 확인한다. 자신의 최소 재현과 로그에서 개인 데이터·토큰·계정 비밀은 제거하고 필요한 조건을 유지한다. 허가되지 않은 외부 서비스를 더 시험하여 영향을 입증하려고 범위를 넓히지 않는다.

수정과 안내가 사용자에게 도달하게 한다

유지관리자에게 먼저 비공개로 사실을 전달하고 접수·재현·수정·공개 일정과 범위를 조율한다. 모든 프로젝트에 같은 대기 일수나 보상이 자동 적용되는 것은 아니다. 공개 시에는 영향을 받는 버전·수정 버전·사용자 조치가 읽히도록 안내한다.

연락 경로를 찾는 공개 질문에 아직 고쳐지지 않은 취약성 세부 입력을 함께 올리지 않는다. 또한 비공개 제보와 공개 advisory는 다른 단계다. 이 학습 활동은 가상의 파서 보고서를 작성하며 누구에게도 실제 메시지를 보내거나 공개 등록하지 않는다.

다른 문제에 적용하기

새 파서 입력으로 시험과 보고 구분하기

자체 엄격 합 파서에서 [2,5,9]는 접두 2와 본문 2개가 맞는다. 잘못된 후보는 엄격 길이 검사 후 첫 본문 바이트만 반환한다. 다른 변형 [3,5,9]의 원래 잘못된 파서는 n≥1만 검사하고 i를 0부터 L−1까지 바꾸며 data[1+i]를 읽는다. 두 입력의 기대 결과·후보의 틀린 값·최초 범위 밖 위치와 보고의 확인 범위를 적어라. 실제 코드 실행은 없다.

힌트 1

정상 본문 합과 후보의 반환 방식을 구별한다.

힌트 2

n=3의 유효 인덱스는 0부터 2까지이다.

풀이와 답 확인

  1. [2,5,9]의 기대값은 5+9=14이며 후보는 5를 반환하므로 정상 출력 회귀에 실패한다.

  2. [3,5,9]는 엄격 수정에서 본문 2개와 L=3의 불일치로 거절해야 한다.

  3. 원래 잘못된 반복은 인덱스 1과 2 다음의 3에서 처음 범위 밖 접근을 시도한다.

  4. 보고에는 종이 추적과 수정 계획만 적는다. 실제 컴파일·sanitizer·제품 버전·원격 영향·제보는 미수행 또는 미확인으로 남긴다.

정상 기대값 14와 후보의 5는 다르다. 불일치 입력은 거절하며 원래 파서의 최초 범위 밖 인덱스는 3이다. 실제 재현과 제품 영향은 확인하지 않았다.

해결한 뒤 점검할 것

  • 엄격 길이와 본문 값을 둘 다 검사한다.

  • 최초 잘못된 인덱스를 실제 n과 대조한다.

  • 기대 손계산과 실행·접수·공개의 증거를 구별한다.

Z를 추가한 합집합은 다섯 개이므로 5/6이며 F만 미도달이다. 입력 [2,4,7]의 기대 합은 11로, 후보 P의 반환 11과 일치하고 Q의 반환 7과 다르다. 상태 초기화 없이 [0]을 두 번 호출하면 정상 다음 ERROR이고, 매번 초기화하면 두 번 모두 정상이다. 세 기호로 길이 2를 구성하는 공간은 3²=9개이며 네 입력의 검사 비율은 4/9이다. 입력 [1,65,66]은 엄격 계약에서 거절하고 여유 계약에서 승인하여 65만 읽는다. 반복 끝을 잘못 포함한 [2,65,66]은 인덱스 3에서 처음 범위 밖을 읽는다. 길이 검증이 없는 [3,65,66], [3,65], [3]의 최초 범위 밖 인덱스는 각각 3, 2, 1이다. 엄격 길이와 정상 반복에서는 최대 접근이 1+(L−1)=L=n−1이며 L=0이면 본문 접근이 없다. 네 회귀시험에서 후보 A, B, C의 기대 일치는 각각 2/4, 4/4, 3/4이다. 후보 D는 추가 시험 [2,3,4]의 기대값 7을 3으로 잘못 반환하여 다섯 시험 중 네 개만 일치한다. 가상 기록 세 개는 주어진 원인 분류에 따라 두 원인으로 묶인다. 전이의 [2,5,9]는 기대값 14와 후보 반환 5가 다르며, 길이 검증 없는 [3,5,9]는 인덱스 3에서 처음 범위 밖을 읽는다. 모두 종이 손계산이며 실제 실행이나 제품 영향 확인은 수행하지 않았다.
