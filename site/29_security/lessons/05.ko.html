소단원 5.1

사용자·권한·격리

같은 컴퓨터의 두 프로그램이 같은 파일을 마음대로 바꿀 수 있어야 할까?

준비 개념과 학습 목표

준비 개념

  • 주체는 요청하는 사용자나 프로세스, 객체는 파일 같은 자원이다.
  • r은 읽기, w는 쓰기, 일반 파일의 x는 실행이며 디렉터리의 x는 이름을 따라 검색하는 권한이다.

학습 목표

  • 권한 표에서 한 주체의 허용 동작을 구한다.
  • 허용 권한과 관찰 범위를 나누어 설명한다.

누구의 어떤 요청인지 적는다

학교의 공유 폴더를 생각하자. 보고서를 읽는 학생과 수정하는 담당자의 역할은 다르다. 운영체제는 요청한 프로세스의 자격 증명과 대상 객체의 정책을 비교한다. 화면에 표시된 사용자 이름만으로 판단하지 않으며, 프로그램이 어떤 권한으로 실행되는지도 중요하다.

여기서는 추가 ACL, 관리자 우회, capability, 특수 실행 비트를 제외한 기본 파일 권한 모형을 쓴다. Linux 실제 파일 검사는 보통 유효 사용자와 같은 fsuid 및 파일시스템 그룹을 사용한다. 단순 모형의 답을 모든 실제 장비의 결과라고 옮기지 않는다.

소유자·그룹·기타 중 한 칸을 선택한다

기본 모형에서는 파일 소유자이면 소유자 칸, 아니면서 파일 그룹에 속하면 그룹 칸, 둘 다 아니면 기타 칸을 쓴다. 세 칸의 허용 동작을 합치는 방식이 아니다. rw−/r−−/−−−는 소유자 읽기·쓰기, 그룹 읽기, 기타 허용 없음이라는 뜻이다. 숫자 4,2,1은 각각 r,w,x를 나타내어 이 표를 640으로 적는다.

파일 내용 읽기가 허용되어도 그 파일까지 가는 경로의 디렉터리를 검색할 수 없으면 경로를 이용한 접근이 실패할 수 있다. 디렉터리 x를 프로그램 실행이라고 해석하면 잘못이다. 읽기 r와 검색 x 역시 같은 뜻이 아니다. 이 활동에서는 이미 열린 파일 핸들을 이용한 접근은 제외한다.

권한과 보이는 세계를 함께 설계한다

namespace는 어떤 프로세스 목록, 마운트, 네트워크 같은 자원을 어떤 범위에서 보게 할지 나눈다. 파일의 w 비트를 끄는 것은 쓰기 권한의 제한이고, 별도 mount namespace는 보이는 마운트 구성을 나누는 일이다. 서로 다른 질문에 답하므로 한 장치가 다른 장치를 대신한다고 생각하지 않는다.

최소 권한은 해야 할 일에 필요한 동작만 주는 원칙이다. 보고서 표시 프로그램에 전체 디스크 수정 권한을 줄 이유가 없다. 하지만 읽기만 허용한 프로그램도 읽은 내용을 허용된 통신 경로로 전송할 수 있다. 정보의 흐름과 모든 출구를 함께 살펴야 한다.

중간 과정을 따라가는 예제

파일 소유자 Alice, 그룹 study, 모드640이다. Bob은 study 구성원, Eve는 아니다. 세 사용자의 읽기·쓰기를 표로 구하라. 경로 검색은 모두 허용한다고 가정한다.

  1. 640=6/4/0이며 6=4+2라 소유자 rw−다.
  2. Alice는 소유자 칸으로 읽기와 쓰기 모두 허용된다.
  3. Bob은 그룹 칸 r−−이므로 읽기 허용·쓰기 거부다.
  4. Eve는 기타 칸 −−−이므로 둘 다 거부다. 같은 파일에서도 주체가 달라 결과가 다르다.

Alice: 읽기O 쓰기O, Bob: 읽기O 쓰기X, Eve: 읽기X 쓰기X다.

풀이 보기

604에서 Bob은 그룹 칸0으로 읽기 거부, Eve는 기타4로 읽기 허용이다. 모드640으로 되돌려도 Bob의 경로상 디렉터리 검색이 거부되면 그 경로를 따라 파일을 열 수 없다. 파일 권한만으로 전체 경로 검사를 끝낼 수 없다.

오해와 반례

그룹 권한이 부족하면 기타 사용자 권한을 추가로 적용한다.

주어진 기본 모형은 한 등급을 고른다. 604에서 그룹 구성원 Bob은 읽지 못하고 기타 Eve는 읽는다. 더 높은 역할 이름이 자동으로 더 많은 권한을 뜻하지 않는다. 실제 ACL 등 추가 정책은 별도로 분석한다.

소단원 5.2

시스템 호출과 정책

프로그램이 자기 안에서만 “쓰기 금지”라고 검사하면 침해된 뒤에도 지킬까?

준비 개념과 학습 목표

준비 개념

  • 시스템 호출은 사용자 프로그램이 커널에 요청하는 인터페이스다.
  • 허용 목록은 나열한 요청만 허용하고 나머지는 거부하는 정책이다.

학습 목표

  • 요청·검사·실행을 구분해 추적한다.
  • 호출 필터의 경계와 인자 검사의 한계를 설명한다.

정책은 요청이 실제로 지나가는 곳에서 검사한다

프로그램이 파일을 쓰려면 커널의 서비스를 요청한다. 프로그램 내부의 if문만으로 금지하면 프로그램이 바뀌었을 때 그 검사를 건너뛸 수 있다. 커널 같은 신뢰하는 경계에서 요청을 검사하면 침해된 프로그램도 해당 경계를 통과해야 한다. 단, 정책 밖의 다른 경로가 있으면 전체 목표가 깨질 수 있다.

정책을 세울 때 정상 작업에 필요한 요청부터 적는다. 숫자 계산만 하는 장난감 프로그램은 외부 연결이 필요 없을 수 있다. 실제 런타임은 메모리 관리·신호 등 여러 호출을 추가로 사용하므로 아래 세 호출 모형을 실제 프로그램의 완전한 seccomp 목록으로 쓰면 안 된다.

필터 결정과 커널 실행은 별개다

Linux seccomp 필터는 호출 번호, 아키텍처, 인자 등으로 결정을 내릴 수 있다. ERRNO 결과는 호출을 실행하지 않고 오류를 돌려주며, ALLOW는 다음 커널 처리로 넘어간다. LOG는 로깅 대상으로 처리하면서 호출 실행을 계속하므로 거부와 다르다. 실제 LOG 기록에는 actions_logged 설정에 log가 포함되어야 한다. 아래 종이 모형은 로깅이 활성화되어 있다고 가정하며 실제 로그 존재를 확인한 것은 아니다. 여러 필터와 권한 검사가 이어지는 실제 환경의 세부 규칙은 공식 문서를 확인해야 한다.

ALLOW가 최종 성공이라는 뜻도 아니다. 허용된 read라도 잘못된 파일 기술자나 파일 권한 때문에 실패할 수 있다. 반대로 syscall을 거부하는 정책은 특정 파일의 소유권 검사와 다른 층이다. 예시에서는 호출명만으로 판단하지만 실제 필터는 아키텍처에 따른 호출 번호 해석도 검증해야 한다.

포인터 인자를 이름 문자열로 오해하지 않는다

파일 열기 호출의 인자는 파일명 자체가 아니라 사용자 메모리를 가리키는 주소일 수 있다. seccomp BPF는 그 주소가 가리키는 문자열을 자유롭게 읽어 파일명 정책을 구현하는 장치가 아니다. 주소 숫자가 같아도 메모리 내용이 바뀔 수 있다는 점을 먼저 구별한다.

파일별 정책은 이미 제한해서 전달한 핸들, 별도 접근 제어 또는 신뢰하는 broker 등 적절한 장치와 결합해야 한다. 호출 필터만으로 완전한 sandbox가 되지 않는다는 공식 문서의 범위가 중요하다. 알맞은 경계와 검사 시점을 정하지 않고 문자열 비교를 붙이면 검사와 실제 사용 사이에 값이 바뀌는 문제도 생긴다.

중간 과정을 따라가는 예제

장난감 정책에서 read/write/exit는 ALLOW, connect는 ERRNO, 그 밖은 ERRNO다. read, connect, write, exit 요청의 필터 결정을 순서대로 적어라.

  1. read는 목록 안이므로 ALLOW다. 성공 여부는 뒤의 실제 커널 검사에 달린다.
  2. connect는 ERRNO라 연결 동작이 실행되지 않는다.
  3. write는 ALLOW다. 해당 파일이나 핸들의 쓰기 권한까지 자동으로 주는 것은 아니다.
  4. exit는 ALLOW다. 결정열은 허용/오류/허용/허용이다.

필터상 통과3회·거부1회다. 실제 읽기·쓰기 성공 횟수는 이 정보만으로 알 수 없다.

힌트 보기

LOG의 실행 여부와 파일 권한을 서로 다른 줄에 적는다.

풀이 보기

필터에 의한 차단은0회다. connect는 실행 처리로 넘어간다. 로깅이 활성화되었다는 이 모형에서는 기록 대상이며, 실제 기록 여부는 actions_logged 같은 설정을 확인해야 한다. write의 ALLOW는 읽기 전용 객체의 쓰기 권한을 추가하지 않아 성공을 보장하지 못한다. 이 답은 실제 프로그램 실행 기록이 아니다.

오해와 반례

허용된 호출은 반드시 성공하고 기록된 호출은 거부된다.

ALLOW 이후 다른 검사가 실패할 수 있고 LOG는 실행을 계속한다. 허용/기록/성공은 세 개의 다른 속성이다. 파일명 주소만 허용 목록에 두는 것으로 그 파일의 문자열 내용까지 검증했다고 주장할 수도 없다.

소단원 5.3

컨테이너·브라우저 격리

웹 페이지를 그리는 프로그램에 내 모든 파일을 직접 수정할 권한을 줘도 될까?

준비 개념과 학습 목표

준비 개념

  • broker는 제한된 프로그램의 요청을 대신 검사하고 수행하는 신뢰 구성요소다.
  • namespace는 보이는 자원 범위, cgroup은 사용 자원의 집계·제한에 관련된다.

학습 목표

  • 컨테이너와 브라우저의 보호 경계를 그린다.
  • 설정과 공유 자원이 격리 목표에 미치는 영향을 찾는다.

보이는 자원과 사용할 수 있는 양을 구분한다

컨테이너는 프로세스를 격리된 자원 관찰 범위에 두는 운영체제 기술들을 결합한다. PID나 mount namespace는 프로세스 목록·마운트의 관찰 범위를 나눌 수 있다. cgroup의 CPU·메모리 제한은 한 작업이 자원을 과도하게 쓰는 위험을 줄이는 다른 역할이다. 자원량 제한을 파일 비밀 보호와 동일시하지 않는다.

컨테이너에 호스트의 민감한 디렉터리를 쓰기 가능하게 공유하면 그 공유 경로의 수정이 가능할 수 있다. 격리라는 이름만으로 공유 설정이 사라지지 않는다. Linux 컨테이너의 경계는 호스트 커널과 권한 설정에도 의존한다. 가상 머신과 동일한 별도 커널 경계라고 가정하지 않는다.

침해된 renderer를 가정하고 요청을 검사한다

브라우저의 sandbox 설계에서는 페이지 처리용 target가 악성 입력으로 침해되었다고 가정한다. 높은 권한의 broker는 제한된 요청을 받아 정책을 검사하고 필요한 결과만 제공한다. target의 클라이언트 검사는 편의·최적화일 수 있어도 침해된 target를 막는 최종 신뢰 경계가 될 수 없다.

이때 모든 파일 경로를 자유롭게 전달하게 하는 것보다 허용된 객체에 한정된 권한을 주는 편이 목표를 설명하기 쉽다. 실제 Chromium의 구체적 구현은 운영체제에 따라 다르다. 아래의 보고서 핸들 모형은 특정 브라우저 버전의 실제 API나 설정 화면을 재현한 것이 아니다.

모든 요청 경로를 표에 넣는다

우리 broker는 보고서R의 읽기만 대행한다고 하자. target의 R읽기는 허용, R쓰기는 거부, 다른 파일S읽기도 거부한다. 정책의 주체·객체·동작을 한 행으로 적으면 “파일 접근 허용” 같은 넓은 말의 빈칸이 드러난다. broker 자신도 불필요한 권한을 줄이고 입력을 검사해야 한다.

target가 R을 이미 읽었다면 읽은 내용을 화면이나 허용된 통신 채널에 보낼 수 있다. 따라서 파일 수정 방지와 비밀 유출 방지는 별도 목표다. cgroup 메모리 제한을 낮춰도 읽은 비밀의 전송을 자동으로 막지는 않는다. 한 경계의 성공을 모든 위험의 제거라고 확장하지 않는다.

중간 과정을 따라가는 예제

broker 정책은 (R,read)만 허용한다. 요청 (R,read),(R,write),(S,read),(R,read)를 추적하라. target 내부 검사는 모두 허용한다고 가정한다.

  1. broker는 첫 요청의 객체R·동작read를 확인해 대행한다.
  2. 두 번째는 동작write가 정책에 없어 거부한다.
  3. 세 번째는 객체S가 정책에 없어 거부한다.
  4. 네 번째는 다시 허용한다. target 내부 허용은 broker의 두 거부를 뒤집지 못한다.

허용2·거부2다. R 내용을 읽게 하는 목표이며 모든 정보 유출 방지를 증명한 표는 아니다.

오해와 반례

컨테이너나 sandbox 안에 넣으면 설정과 관계없이 모든 자원이 안전하다.

공유 파일·허용 통신·권한 추가가 경계를 바꾼다. 읽기만 필요한데 쓰기 가능 공유를 제공하는 것은 목표와 충돌한다. 또한 메모리 제한이 파일 접근 정책을 대신하지 않는다.
