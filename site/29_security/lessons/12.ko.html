소단원 12.1

의존성·빌드·서명

내가 작성한 코드만 확인하면 다른 사람이 만든 부품과 빌드 도구도 함께 믿을 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 파일과 해시

  • 직접·간접 의존성

  • 공개키 서명의 목적

학습 목표

  • 소스·의존성·빌드·산출물의 연결을 그린다.

  • 버전 고정과 서명의 보장 범위를 구별한다.

  • 기대값으로 가상 배포 기록을 판정한다.

완성 파일 이전의 경로

도서관 앱 A가 해독 부품 B를 쓰고 B가 문자 처리 부품 C를 쓴다고 하자. A에서 B는 직접 의존성이고 C는 전이 의존성이다. C의 변경도 A의 동작에 영향을 줄 수 있어 A의 직접 부품 목록만으로는 관계가 충분히 드러나지 않는다.

빌드는 소스·부품·설정·도구를 사용해 실행 파일 같은 산출물을 만드는 과정이다. A → B → C와 소스 → 빌드 환경 → 산출물은 다른 관계다. 각 경계에서 누가 무엇을 선택하며 어떤 증거가 남는지 그려 보자.

고정과 안전성은 다른 판단

버전·잠금 파일과 commit을 기록하면 선택 대상을 더 분명히 한다. GitHub는 외부 action의 전체 commit SHA 고정과 코드 확인을 안내한다. 이동 가능한 tag와 특정 commit의 참조를 구별한다. 그러나 고정한 코드도 목적과 다르게 동작할 수 있다.

SBOM은 부품 목록을, provenance는 산출물이 만들어진 경로를 설명한다. 목록과 생산 기록은 서로 보완하지만 모든 의존성을 빠짐없이 기록했다고 자동 보장하지 않는다. 특정 버전을 고정했다는 사실을 취약점 부재의 증명으로 바꾸지 않는다.

서명에 기대 조건을 붙인다

신뢰하는 서명자에 연결된 기록인지 확인한 뒤 받은 파일의 해시와 기록 대상, 허용 빌드 주체·저장소·설정을 대조한다. 서명 성공이어도 다른 저장소에서 만든 파일이면 기대 배포와 다를 수 있다. 기록을 검사하지 않으면 기록 존재만으로 선택 정책을 적용하지 못한다.

아래 K·B·R·C·H는 사람이 붙인 가상 식별 기호다. 실제 공개키·해시가 아니며 서명 성공도 문제의 가정이다. 조건 비교를 연습할 뿐 암호 검증이나 SLSA 등급 인증은 하지 않는다. 통과 파일의 모든 동작 안전성도 별도 문제다.

중간 과정을 따라가는 예제

정책은 서명자 K, 빌드 주체 B, 저장소 R, commit C, 파일 해시 H를 요구한다. X는 서명 성공과 (K,B,R,C,H), Y는 서명 성공과 (K,B,Q,C,H), Z는 서명 성공과 기록 (K,B,R,C,H)이나 받은 파일의 해시 J다. Q≠R, J≠H일 때 통과 행은?

  1. X는 모든 기대값과 서명 성공 조건이 맞는다.

  2. Y는 저장소 Q가 R과 달라 실패한다.

  3. Z는 실제 받은 파일 J가 기록 대상 H와 달라 연결이 실패한다.

X만 정책을 통과한다. 서명이 성공한 Y·Z도 각각 저장소·산출물 조건에서 실패한다. X의 동작 안전성은 증명하지 않았다.

종이와 본문으로 직접 해보기

W는 서명 성공과 (K,D,R,C,H), V는 X와 같은 값이지만 서명 실패다. D≠B일 때 판정하라. A→B→C에서 직접 목록에 B만 적으면 C의 변경이 드러나는가?

힌트 보기

허용 빌드 주체 B와 서명 조건을 따로 확인한다. 의존성 화살표를 두 번 따라간다.

풀이 보기

W는 D 때문에, V는 서명 실패 때문에 거절한다. 직접 목록의 B만으로 C가 바뀌었는지 알 수 없다. B가 사용하는 C의 버전·잠금 정보와 생산 기록까지 추적한다.

오해와 반례

서명과 버전 고정이 있으면 코드 검토는 필요 없다.

특정 주체의 파일 확인과 코드의 안전성은 다르다. Y처럼 서명이 맞아도 기대 저장소가 다를 수 있고 X도 취약한 동작의 가능성은 별도로 검토해야 한다.

소단원 12.2

비밀·패치·로그

비밀이 찍힌 한 줄을 지우고 업데이트 버튼을 누르면 운영 보안이 끝날까?

준비 개념과 학습 목표

준비 개념

  • 인증과 권한

  • 버전과 테스트

  • 시각과 사건 기록

학습 목표

  • 서비스 자격증명의 교체·폐기를 구별한다.

  • 수정 검사와 정상 기능 회귀를 구별한다.

  • 민감값 없이 사건 기록을 설계한다.

비밀의 수명과 권한

서비스 API token은 사람의 비밀번호와 용도·수명 정책이 다를 수 있다. 필요한 작업만 허용하고 소비자·만료·폐기 방법을 정한다. 화면에서 가리거나 앱에서 지운 값도 발급 서버가 유효하다고 인정하면 계속 사용할 수 있다.

노출된 서비스 token에서는 기존 값의 권한 폐기와 새 값 연결을 구별한다. 교체가 옛 값의 폐기를 자동 보장하는지 확인한다. 여기서는 T0·T1이라는 이름만 쓰며 실제 자격증명을 만들거나 적지 않는다. 사용자 암호를 무조건 정기 변경하라는 일반 규칙으로 확대하지 않는다.

패치와 유지할 기능을 함께 검사한다

공지의 부품·영향 버전·수정 버전·설정을 실제 사용과 대조한다. 테스트 환경 업데이트 뒤에는 문제 동작을 막는 검사와 정상 기능을 유지하는 회귀 검사를 함께 둔다. 전이 부품이면 직접 사용하는 부품과의 연결도 살핀다.

다음 표는 자체 가상 공지에서 2.0의 길이 검사 결함이 2.1에서 수정됐다고 가정한다. 실제 제품이나 CVE에 대응하지 않는다. 버전 이름만 바꾸거나 경고를 숨기는 일은 수정 동작의 증거가 아니다. 실패가 있으면 원인과 다시 수행한 결과를 남긴다.

로그도 보호해야 할 관찰이다

시각·주체·대상·행위·결과·관련 이벤트 식별자는 사건을 연결하는 데 도움이 된다. token 원문이나 암호는 직접 적지 않는다. 외부 입력의 줄바꿈·구분 기호를 안전하게 처리하고 로그 읽기·변경 권한도 제한한다.

실패 요청 하나를 공격의 확정 증거로 단정하지 않는다. 시계 차이나 기록 누락도 해석에 영향을 준다. 아래는 같은 시계를 쓰고 빠짐없이 기록됐다는 가정이다. 실제 환경에서는 시각 기준·누락·보존 범위와 추정을 함께 공개해야 한다.

중간 과정을 따라가는 예제

T0 만료는 11:00, 노출 발견은 10:10, 발급 서버 폐기 적용은 10:14다. 폐기 시각 이상에서 거절한다. 다른 권한 조건이 맞을 때 10:12/10:15 결과는? 패치 2.1의 N1 정상 조회 성공, N2 정상 저장 실패, B 잘못된 길이 거절은 전체 통과인가?

  1. 10:12는 만료와 폐기 전이므로 T0가 유효하다.

  2. 10:15는 폐기 뒤라 거절된다. 발견부터 적용까지 4분이다.

  3. N1과 B는 기대를 만족하지만 N2는 정상 기능 회귀 실패다. 기대 성공은 2/3이다.

10:12는 유효, 10:15는 폐기로 거절이다. 패치 표는 전체 통과가 아니다. token 원문 대신 가상 식별자·시각·행위·결과를 기록한다.

종이와 본문으로 직접 해보기

T1이 유효하며 조회만 허용한다. 10:16 조회와 10:17 삭제를 판정하고 로그 필드를 적어라. N2 수정 후 N1/N2/B가 모두 통과하면 첫 결과를 지워야 하는가?

힌트 보기

유효성과 작업 권한을 구별한다. 새 결과와 이전 관찰을 함께 생각한다.

풀이 보기

조회 허용, 삭제는 권한 부족 거절이다. 같은 시계의 시각·T1 식별자·대상·행위·결과·이벤트 ID를 적되 실제 비밀은 적지 않는다. 새 3/3 결과를 버전과 함께 추가하고 첫 2/3 결과는 보존 정책에 따라 변경 이력으로 남긴다.

오해와 반례

로그를 지우면 token도 못 쓰고 경고를 숨기면 결함도 사라진다.

로그 삭제는 발급 서버 유효성을 바꾸지 않고 경고 숨기기는 코드 동작을 고치지 않는다. 폐기 적용·수정 검사·회귀라는 별도 관찰이 필요하다. 노출 기록의 처리는 증거 보존과 접근 제한도 고려한다.

소단원 12.3

복사본의 실패 조건을 그린다

수업 노트를 같은 폴더에 복사했다가 폴더 전체가 사라지면 두 파일이 함께 사라질 수 있다. 원본과 복사본이 어떤 실패를 같이 겪는지 먼저 적는다. 접근 권한·위치·암호화된 자료를 여는 정보도 복구 계획의 일부다.

파일 존재와 복원 성공은 다르다. 읽을 수 있는지, 필요한 버전·설정·데이터가 함께 있는지, 복원 뒤 핵심 업무가 되는지 확인한다. 여기서는 종이 표로 조건을 연습하며 실제 파일 삭제나 서비스 장애를 만들지 않는다.

조사와 복구의 근거를 남긴다

사건의 범위와 영향을 분석하고 담당자에게 전달한다. 확인한 사실·가정·수행 조치를 나누어 기록하며 증거의 출처와 접근을 보호한다. 복구를 서두른다는 이유로 조사 기록을 무조건 지워 버리지 않는다.

사용할 복구 자산은 손상·침해 흔적을 미리 검사하고 복구한 시스템도 정상 연결 전에 확인한다. 불안전한 설정·비밀을 그대로 되살릴 가능성을 검토한다. 실제 계정 문제는 담당자 절차를 따르고 이 활동에서 다른 사람의 설정을 바꾸지 않는다.

두 시간 목표와 종료 기준

가상 도서관은 장애 후 30분 안에 필수 조회를 제공하고 최대 10분 전의 데이터 상태까지 복구하기로 정한다. 앞은 서비스 복구 시간, 뒤는 복구 가능한 데이터 시점의 목표다. 시작과 끝을 명시해 각각 비교한다.

여기서 데이터 손실 구간은 장애 시각과 복구한 데이터 시각의 차이다. 실제 손실 건수와 같지 않으며 그 사이 변경이 없을 수도 있다. 조회·권한·데이터 검사와 종료 승인·사후 개선을 완료 기준으로 둔다. 프로세스 시작만으로 업무 정상화를 선언하지 않는다.

중간 과정을 따라가는 예제

장애는 14:00이다. A는 13:55 데이터이며 사전 자산 검사·복구 뒤 필수 업무와 권한 검사를 통과해 14:24 재개한다. B는 13:58 데이터지만 사전 검사 실패다. 목표 30분과 데이터 시점 차이 10분을 비교하라.

  1. A의 중단 구간은 24분으로 30분 이내다.

  2. A의 데이터 시점 차이는 5분으로 10분 이내다.

  3. B의 차이는 2분이지만 복구 자산 검사 실패를 해결하지 못한다. 최신이라는 이유만으로 고르지 않는다.

주어진 검사 조건에서 A는 두 목표를 만족한다. B는 최근이어도 신뢰 조건을 만족하지 않는다. 실제 복구 성공을 관찰한 것은 아니다.

종이와 본문으로 직접 해보기

검사를 통과한 C는 14:35 재개·13:56 데이터, D는 14:20 재개·13:45 데이터다. 두 목표를 각각 판정하라. 13:58 이상 요청 관찰, 14:00 장애 확인, 14:04 격리 적용에서 추정과 조치를 구별하라.

힌트 보기

재개−14:00, 14:00−데이터 시각을 각각 계산한다. 이상 요청이 원인이라고 적혀 있지는 않다.

풀이 보기

C는 35분으로 시간 목표 실패, 4분으로 데이터 목표 통과다. D는 20분으로 시간 목표 통과, 15분으로 데이터 목표 실패다. 요청은 관찰, 장애는 확인, 격리는 수행 조치다. 세 기록만으로 요청이 원인이라고 확정하지 않고 조사 근거를 추가한다.

오해와 반례

최근 백업으로 서버를 시작했으니 원인 조사와 정상 확인도 끝났다.

B처럼 최근이어도 자산 검사에 실패할 수 있다. 프로세스 실행과 업무·권한·데이터 정상은 다른 관찰이며 원인·재발 방지·증거 기록도 별도로 확인한다.
