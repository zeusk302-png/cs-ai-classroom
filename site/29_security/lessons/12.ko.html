소단원 12.1

의존성·빌드·서명

내가 작성한 코드만 확인하면 다른 사람이 만든 부품과 빌드 도구도 함께 믿을 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 파일과 해시

  • 직접·간접 의존성

  • 공개키 서명의 목적

학습 목표

  • 소스·의존성·빌드·산출물의 연결을 그린다.

  • 버전 고정과 서명의 보장 범위를 구별한다.

  • 기대값으로 가상 배포 기록을 판정한다.

부품 하나를 고쳤는데 왜 두 앱을 다시 확인할까요?

교내 도서관 앱 A와 전시 앱 D가 같은 문자 처리 부품 C를 간접으로 사용한다고 하자. A가 직접 호출하는 부품만 나열하면 공통 C가 빠진다. 의존성 그래프는 무엇을 사용하는지, 생산 기록은 누가 어떤 소스로 파일을 만들었는지 설명한다. 두 관계를 겹쳐서 보되 같은 종류의 증거로 취급하지 않는다.

이 활동의 식별자와 서명 결과는 가상이다. 서명 성공과 기대 정책 일치를 모두 따지며, 정책 자체를 임의로 바꿀 권한이 있는지도 생각한다. 조건표 통과는 주어진 배포 선택의 판단이지 모든 동작의 안전성이나 실제 암호 검증 결과가 아니다.

먼저 확인할 개념
  • 의존성·빌드·서명

    직접·전이 의존성과 산출물 해시 대조를 그래프와 정책표에 적용한다.

  • 비밀·패치·로그

    간접 부품 갱신 뒤에도 정상 기능과 결함 재현 검사가 필요한 이유를 연결한다.

완성 파일 이전의 경로

도서관 앱 A가 해독 부품 B를 쓰고 B가 문자 처리 부품 C를 쓴다고 하자. A에서 B는 직접 의존성이고 C는 전이 의존성이다. C의 변경도 A의 동작에 영향을 줄 수 있어 A의 직접 부품 목록만으로는 관계가 충분히 드러나지 않는다.

빌드는 소스·부품·설정·도구를 사용해 실행 파일 같은 산출물을 만드는 과정이다. A → B → C와 소스 → 빌드 환경 → 산출물은 다른 관계다. 각 경계에서 누가 무엇을 선택하며 어떤 증거가 남는지 그려 보자.

고정과 안전성은 다른 판단

버전·잠금 파일과 commit을 기록하면 선택 대상을 더 분명히 한다. GitHub는 외부 action의 전체 commit SHA 고정과 코드 확인을 안내한다. 이동 가능한 tag와 특정 commit의 참조를 구별한다. 그러나 고정한 코드도 목적과 다르게 동작할 수 있다.

SBOM은 부품 목록을, provenance는 산출물이 만들어진 경로를 설명한다. 목록과 생산 기록은 서로 보완하지만 모든 의존성을 빠짐없이 기록했다고 자동 보장하지 않는다. 특정 버전을 고정했다는 사실을 취약점 부재의 증명으로 바꾸지 않는다.

서명에 기대 조건을 붙인다

신뢰하는 서명자에 연결된 기록인지 확인한 뒤 받은 파일의 해시와 기록 대상, 허용 빌드 주체·저장소·설정을 대조한다. 서명 성공이어도 다른 저장소에서 만든 파일이면 기대 배포와 다를 수 있다. 기록을 검사하지 않으면 기록 존재만으로 선택 정책을 적용하지 못한다.

아래 K·B·R·C·H는 사람이 붙인 가상 식별 기호다. 실제 공개키·해시가 아니며 서명 성공도 문제의 가정이다. 조건 비교를 연습할 뿐 암호 검증이나 SLSA 등급 인증은 하지 않는다. 통과 파일의 모든 동작 안전성도 별도 문제다.

기대 정책이 보호되는가?

화살표는 왼쪽이 오른쪽 부품을 사용한다는 뜻이다. 생산 기록의 빌드 주체를 의존성 그래프의 부품 이름으로 대신하지 않는다.

중간 과정을 따라가는 예제

정책은 서명자 K, 빌드 주체 B, 저장소 R, commit C, 파일 해시 H를 요구한다. X는 서명 성공과 (K,B,R,C,H), Y는 서명 성공과 (K,B,Q,C,H), Z는 서명 성공과 기록 (K,B,R,C,H)이나 받은 파일의 해시 J다. Q≠R, J≠H일 때 통과 행은?

  1. X는 모든 기대값과 서명 성공 조건이 맞는다.

  2. Y는 저장소 Q가 R과 달라 실패한다.

  3. Z는 실제 받은 파일 J가 기록 대상 H와 달라 연결이 실패한다.

X만 정책을 통과한다. 서명이 성공한 Y·Z도 각각 저장소·산출물 조건에서 실패한다. X의 동작 안전성은 증명하지 않았다.

조건을 바꾸어 비교하기

공통 전이 부품 찾기

A→B→C, D→E→C이며 이 외 의존성은 없다. C의 변경을 조사할 앱과 두 앱의 직접 부품 목록을 적어라.

  1. A의 직접 부품은 B, D의 직접 부품은 E이다.

  2. 두 경로 모두 C에 도달한다.

  3. A와 D를 조사 대상으로 삼되 실제 영향은 호출과 수정 내용을 확인한다.

직접 목록은 각각 {B}, {E}; C는 두 앱의 전이 의존성이다.

비교할 점

원문의 단일 앱 경로를 두 앱의 공통 부품으로 확장한다.

검사값을 바꾸면 통과가 늘어나는 이유

기존 정책은 서명자 K, 빌더 B, 저장소 R, commit C, 받은 해시 H를 기대한다. X는 서명 성공과 (K,B,Q,C,H)이고 Q≠R이다. 작업자가 기대 저장소를 Q로 고친 뒤 X가 통과했다고 한다.

  1. 기존 정책에서는 저장소 불일치로 실패한다.

  2. 변경된 정책에서는 주어진 다섯 조건과 서명이 맞는다.

  3. 정책 변경의 승인과 근거가 없으면 원래 배포 요구를 충족했다고 말할 수 없다.

검사 결과는 변경된 정책 기준의 통과다. 승인 없는 기대값 변경을 원래 요구의 충족으로 보고하지 않는다.

비교할 점

검사 대상뿐 아니라 판정 기준의 변경도 추적한다.

종이와 본문으로 직접 해보기

W는 서명 성공과 (K,D,R,C,H), V는 X와 같은 값이지만 서명 실패다. D≠B일 때 판정하라. A→B→C에서 직접 목록에 B만 적으면 C의 변경이 드러나는가?

힌트 보기

허용 빌드 주체 B와 서명 조건을 따로 확인한다. 의존성 화살표를 두 번 따라간다.

풀이 보기

W는 D 때문에, V는 서명 실패 때문에 거절한다. 직접 목록의 B만으로 C가 바뀌었는지 알 수 없다. B가 사용하는 C의 버전·잠금 정보와 생산 기록까지 추적한다.

오해와 반례

서명과 버전 고정이 있으면 코드 검토는 필요 없다.

특정 주체의 파일 확인과 코드의 안전성은 다르다. Y처럼 서명이 맞아도 기대 저장소가 다를 수 있고 X도 취약한 동작의 가능성은 별도로 검토해야 한다.

연습 1 · 값과 상태 예측

A→B→C와 A→F→C에서 A의 직접·전이 부품 집합과 서로 다른 전체 부품 수를 구하라.

힌트 1

A 바로 다음 이름부터 모은다.

힌트 2

중복 C는 한 번만 센다.

풀이와 답 확인

  1. 직접은 {B,F}, 전이는 {C}이다.

  2. 서로 다른 부품은 B,F,C 세 개이다.

직접 2개, 전이 1개, 전체 3개이다.

흔한 오답에서 다시 생각하기

경로가 둘이므로 C도 두 부품이다.

경로 수와 서로 다른 부품 수를 분리한다.

연습 2 · 오류 찾아 고치기

기록 해시는 H, 받은 파일 해시는 J≠H인데 서명 성공만으로 승인했다. 어떤 연결 검사를 추가할까?

힌트 1

서명한 내용의 대상 파일을 찾는다.

힌트 2

실제로 받은 파일과 연결되어야 한다.

풀이와 답 확인

  1. 서명과 신뢰 주체를 확인한다.

  2. 받은 파일의 해시를 기록 대상 해시와 대조해 불일치를 거절한다.

주어진 J≠H에서는 승인하지 않는다.

흔한 오답에서 다시 생각하기

서명된 종이가 있으니 파일도 같다.

서명된 기록과 받은 파일의 연결이 빠졌다.

연습 3 · 직접 만들어 보기

부품 C를 갱신한 A 앱의 확인표를 세 칸으로 설계하라. 버전 기록만으로 끝내지 말라.

힌트 1

무엇을 선택했는지와 어떻게 만들었는지 분리한다.

힌트 2

실제 기능 검사는 별도 칸이다.

풀이와 답 확인

  1. B를 통한 C의 선택 버전·관계를 기록한다.

  2. 산출물 대상·신뢰 주체·빌드 기대 조건을 기록한다.

  3. C를 사용하는 정상 기능과 결함 재현 검사의 결과·환경을 기록한다.

부품 선택 / 생산·대상 검증 / 기능·보안 회귀의 세 칸이다.

흔한 오답에서 다시 생각하기

서명 성공 칸 하나면 충분하다.

서명은 정상 기능 검사와 부품 선택 근거를 대체하지 않는다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

A→B→C에서 B만 고정했고 B가 C의 이동 가능한 참조를 사용한다. A와 B의 식별자가 같다는 이유로 두 빌드의 모든 부품이 같다고 할 수 있을까?

힌트 1

고정의 범위를 확인한다.

힌트 2

C의 실제 선택 기록이 필요한지 생각한다.

풀이와 답 확인

  1. B 식별자 동일은 C 선택 동일을 자동 보장하지 않는다.

  2. 각 빌드에서 선택한 C와 전체 입력을 비교해야 한다.

주어진 정보로 모든 부품의 동일성을 결론낼 수 없다.

흔한 오답에서 다시 생각하기

직접 부품 하나를 고정하면 그 아래도 모두 고정된다.

전이 선택 규칙과 실제 해결 결과를 함께 확인한다.

한 단계 더

기대값을 누구나 바꿀 수 있다면 비교 결과도 약해진다. 가상 정책 변경 승인자와 이력을 추가해 보자. 전체 SLSA 요구사항을 구현하지 않으며 계정·도구 없이 관계와 조건만 연습한다.

소단원 12.2

비밀·패치·로그

비밀이 찍힌 한 줄을 지우고 업데이트 버튼을 누르면 운영 보안이 끝날까?

준비 개념과 학습 목표

준비 개념

  • 인증과 권한

  • 버전과 테스트

  • 시각과 사건 기록

학습 목표

  • 서비스 자격증명의 교체·폐기를 구별한다.

  • 수정 검사와 정상 기능 회귀를 구별한다.

  • 민감값 없이 사건 기록을 설계한다.

폐기 버튼을 누른 시각과 실제로 거절된 시각은 같을까요?

가상의 서비스 token T0가 노출되었을 때 새 T1을 만들었다는 사실만으로 T0의 사용이 끝나지는 않는다. 발급 서버와 소비자가 폐기를 적용하는 시점을 확인한다. 다음 시각은 문제에 주어진 모델이며 실제 제품의 전파 지연을 측정한 값이 아니다.

패치는 정상 요청을 유지하면서 알려진 결함도 막아야 한다. 조사 로그에는 사건을 연결할 식별자와 결과를 남기되 token 본문을 남기지 않는다. 서로 다른 장치의 시계가 어긋나면 화면에 먼저 보인 시각만으로 사건 순서나 원인을 확정하지 않는다.

먼저 확인할 개념
  • 비밀·패치·로그

    교체와 폐기, 정상 기능 회귀, 민감정보 없는 기록의 원래 조건을 확장한다.

  • 백업·복구·사고 대응

    기록의 출처와 실제 조치를 분리해 사고 대응 시간표를 작성한다.

비밀의 수명과 권한

서비스 API token은 사람의 비밀번호와 용도·수명 정책이 다를 수 있다. 필요한 작업만 허용하고 소비자·만료·폐기 방법을 정한다. 화면에서 가리거나 앱에서 지운 값도 발급 서버가 유효하다고 인정하면 계속 사용할 수 있다.

노출된 서비스 token에서는 기존 값의 권한 폐기와 새 값 연결을 구별한다. 교체가 옛 값의 폐기를 자동 보장하는지 확인한다. 여기서는 T0·T1이라는 이름만 쓰며 실제 자격증명을 만들거나 적지 않는다. 사용자 암호를 무조건 정기 변경하라는 일반 규칙으로 확대하지 않는다.

패치와 유지할 기능을 함께 검사한다

공지의 부품·영향 버전·수정 버전·설정을 실제 사용과 대조한다. 테스트 환경 업데이트 뒤에는 문제 동작을 막는 검사와 정상 기능을 유지하는 회귀 검사를 함께 둔다. 전이 부품이면 직접 사용하는 부품과의 연결도 살핀다.

다음 표는 자체 가상 공지에서 2.0의 길이 검사 결함이 2.1에서 수정됐다고 가정한다. 실제 제품이나 CVE에 대응하지 않는다. 버전 이름만 바꾸거나 경고를 숨기는 일은 수정 동작의 증거가 아니다. 실패가 있으면 원인과 다시 수행한 결과를 남긴다.

로그도 보호해야 할 관찰이다

시각·주체·대상·행위·결과·관련 이벤트 식별자는 사건을 연결하는 데 도움이 된다. token 원문이나 암호는 직접 적지 않는다. 외부 입력의 줄바꿈·구분 기호를 안전하게 처리하고 로그 읽기·변경 권한도 제한한다.

실패 요청 하나를 공격의 확정 증거로 단정하지 않는다. 시계 차이나 기록 누락도 해석에 영향을 준다. 아래는 같은 시계를 쓰고 빠짐없이 기록됐다는 가정이다. 실제 환경에서는 시각 기준·누락·보존 범위와 추정을 함께 공개해야 한다.

중간 과정을 따라가는 예제

T0 만료는 11:00, 노출 발견은 10:10, 발급 서버 폐기 적용은 10:14다. 폐기 시각 이상에서 거절한다. 다른 권한 조건이 맞을 때 10:12/10:15 결과는? 패치 2.1의 N1 정상 조회 성공, N2 정상 저장 실패, B 잘못된 길이 거절은 전체 통과인가?

  1. 10:12는 만료와 폐기 전이므로 T0가 유효하다.

  2. 10:15는 폐기 뒤라 거절된다. 발견부터 적용까지 4분이다.

  3. N1과 B는 기대를 만족하지만 N2는 정상 기능 회귀 실패다. 기대 성공은 2/3이다.

10:12는 유효, 10:15는 폐기로 거절이다. 패치 표는 전체 통과가 아니다. token 원문 대신 가상 식별자·시각·행위·결과를 기록한다.

어긋난 시계 보정

서버 A 로그 10:02는 실제보다 2분 빠르고 B 로그 10:01은 실제보다 1분 느리다. 보정값은 문제에서 확정했다고 가정한다. 실제 시각 순서를 구하라.

  1. A 실제 시각은 10:02−2분=10:00이다.

  2. B 실제 시각은 10:01+1분=10:02이다.

  3. 보정 전 표시 순서와 실제 순서가 다르다.

A 사건이 먼저다. 이 순서만으로 두 사건의 인과관계는 확정하지 않는다.

힌트 보기

유효성과 작업 권한을 구별한다. 새 결과와 이전 관찰을 함께 생각한다.

풀이 보기

조회 허용, 삭제는 권한 부족 거절이다. 같은 시계의 시각·T1 식별자·대상·행위·결과·이벤트 ID를 적되 실제 비밀은 적지 않는다. 새 3/3 결과를 버전과 함께 추가하고 첫 2/3 결과는 보존 정책에 따라 변경 이력으로 남긴다.

오해와 반례

로그를 지우면 token도 못 쓰고 경고를 숨기면 결함도 사라진다.

로그 삭제는 발급 서버 유효성을 바꾸지 않고 경고 숨기기는 코드 동작을 고치지 않는다. 폐기 적용·수정 검사·회귀라는 별도 관찰이 필요하다. 노출 기록의 처리는 증거 보존과 접근 제한도 고려한다.

연습 1 · 값과 상태 예측

09:00 노출부터 09:05 폐기 적용까지 노출 후 유효 구간 길이와 09:05:00 T0의 판정을 구하라.

힌트 1

끝 시각부터 거절한다고 명시했다.

힌트 2

풀이와 답 확인

  1. 09:05−09:00=5분이다.

  2. 09:05:00은 거절 구간에 포함된다.

흔한 오답에서 다시 생각하기

연습 2 · 오류 찾아 고치기

패치 검사에서 정상 입력 N1만 성공했고 결함 입력 D와 정상 N2는 실행하지 않았다. 완료 보고를 고쳐라.

힌트 1

힌트 2

기능과 결함 재현을 나누어 적는다.

풀이와 답 확인

  1. N1 성공을 기록한다.

  2. N2와 D는 미수행으로 기록하고 시험 환경에서 추가 검사를 계획한다.

N1만 확인; 패치 효과와 전체 회귀 확인은 미완료이다.

흔한 오답에서 다시 생각하기

1/1 성공이므로 수정 완료다.

검사 집합에서 빠진 필요한 조건을 분모에서 지웠다.

연습 3 · 직접 만들어 보기

조회 거절 사건을 token 본문 없이 추적할 로그 필드를 설계하라.

힌트 1

누가·어디서·언제·무엇을 했는지 적는다.

힌트 2

상호작용 식별자와 결과를 연결한다.

풀이와 답 확인

  1. 서비스·시각·비밀이 아닌 주체 식별자·상호작용 ID를 적는다.

  2. 대상·조회 행위·거절·이유를 적고 token과 비밀번호는 제외한다.

  3. 구분자와 줄바꿈을 안전하게 처리하고 로그 접근 권한과 시계 조건을 관리한다.

예: 서비스 S, 시각 09:06, 주체 U, 사건 E7, 대상 도서 목록, 조회, 거절, 폐기된 자격증명. 실제 token은 넣지 않는다.

흔한 오답에서 다시 생각하기

token을 그대로 넣어야 사건을 연결한다.

비밀 자체 대신 별도 식별자로 연결하며 기록 저장소도 보호한다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

힌트 1

각 사건의 가능한 실제 구간을 만든다.

힌트 2

구간이 겹치면 한 가지 순서만 가능한지 확인한다.

풀이와 답 확인

  1. A 실제 구간은 [10:00,10:04], B는 [10:02,10:04]이다.

  2. A가 먼저일 수도 B가 먼저일 수도 있고 동시일 수도 있다.

구간이 겹쳐 순서를 확정할 수 없다.

흔한 오답에서 다시 생각하기

표시 10:02가 10:03보다 작으니 A가 먼저다.

시각의 불확실성을 비교에 포함해야 한다.

설명 기준 확인

로그가 원인 증명인가?

설명 기준 확인

관찰·시계 조건·누락 가능성을 기록하며 순서만으로 인과관계나 모든 사용을 증명하지 않는다.

한 단계 더

T0 소비자 셋 중 둘만 T1로 옮겼다면 남은 하나의 실패를 어떤 기록으로 찾을지 그려 보자. 실제 비밀을 출력하거나 외부 서비스에 요청하지 않는다. 마스킹이 변환된 모든 비밀까지 자동 처리한다고 가정하지 않는다.

출처와 확인 범위
  • OWASP — Secrets Management

    독립 검토자가 실제 426–477행의 감사·시간 동기·권한·교체·폐기·만료·백업 복원과 770–788행의 노출 대응을 읽었다. 사용자 암호의 정기 교체 제외와 서비스 token의 권한 폐기를 구별했다.

  • OWASP — Logging

    독립 검토자가 실제 340–416/466–498행의 행위·주체·결과·이벤트 연결·token/암호 제외·줄바꿈 처리·시간 동기·접근 보호·보존 기간을 읽었다. 실제 비밀 대신 가상 식별자만 기록한다.

소단원 12.3

백업·복구·사고 대응

백업 파일이 있고 서버가 켜지면 사고에서 회복했다고 할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 파일과 버전

  • 서비스 가용성

  • 시간 차이와 데이터 시점

학습 목표

  • 백업 존재·복원 가능·업무 정상을 구별한다.

  • 복구 전후 검사와 사고 기록을 설명한다.

  • 가상 복구 시간과 데이터 시점을 비교한다.

최근 백업을 여는 열쇠도 같은 장애로 사라진다면?

백업 파일을 다른 위치에 두더라도 그것을 여는 암호 정보가 원본 서비스에만 있으면 장애 때 읽지 못할 수 있다. 복원에 필요한 데이터·설정·접근 정보가 어떤 실패를 함께 겪는지 적는다. 실습은 종이 위의 가상 상황이며 파일을 실제로 지우지 않는다.

복구 시간 목표와 데이터 시점 목표를 모두 만족해도 업무 검사나 침해 흔적 검사가 빠졌다면 종료 판단이 남아 있다. 시간 간격과 실제 잃어버린 기록 수는 다른 값이다. 손실 건수는 해당 구간에 무슨 변경이 있었는지 추가로 알아야 계산할 수 있다.

먼저 확인할 개념
  • 백업·복구·사고 대응

    백업 자산 검사·복구 뒤 업무 검사와 두 시간 목표를 추가 실패 조건에 적용한다.

  • 비밀·패치·로그

    폐기된 비밀을 백업에서 되살리지 않도록 접근 정보와 사건 기록을 연결한다.

복사본의 실패 조건을 그린다

수업 노트를 같은 폴더에 복사했다가 폴더 전체가 사라지면 두 파일이 함께 사라질 수 있다. 원본과 복사본이 어떤 실패를 같이 겪는지 먼저 적는다. 접근 권한·위치·암호화된 자료를 여는 정보도 복구 계획의 일부다.

파일 존재와 복원 성공은 다르다. 읽을 수 있는지, 필요한 버전·설정·데이터가 함께 있는지, 복원 뒤 핵심 업무가 되는지 확인한다. 여기서는 종이 표로 조건을 연습하며 실제 파일 삭제나 서비스 장애를 만들지 않는다.

조사와 복구의 근거를 남긴다

사건의 범위와 영향을 분석하고 담당자에게 전달한다. 확인한 사실·가정·수행 조치를 나누어 기록하며 증거의 출처와 접근을 보호한다. 복구를 서두른다는 이유로 조사 기록을 무조건 지워 버리지 않는다.

사용할 복구 자산은 손상·침해 흔적을 미리 검사하고 복구한 시스템도 정상 연결 전에 확인한다. 불안전한 설정·비밀을 그대로 되살릴 가능성을 검토한다. 실제 계정 문제는 담당자 절차를 따르고 이 활동에서 다른 사람의 설정을 바꾸지 않는다.

두 시간 목표와 종료 기준

가상 도서관은 장애 후 30분 안에 필수 조회를 제공하고 최대 10분 전의 데이터 상태까지 복구하기로 정한다. 앞은 서비스 복구 시간, 뒤는 복구 가능한 데이터 시점의 목표다. 시작과 끝을 명시해 각각 비교한다.

여기서 데이터 손실 구간은 장애 시각과 복구한 데이터 시각의 차이다. 실제 손실 건수와 같지 않으며 그 사이 변경이 없을 수도 있다. 조회·권한·데이터 검사와 종료 승인·사후 개선을 완료 기준으로 둔다. 프로세스 시작만으로 업무 정상화를 선언하지 않는다.

시간 목표와 종료 승인도 확인

후보 이름은 실제 백업 제품이 아니다. 최근 파일이나 프로세스 실행만으로 표의 다른 칸을 채우지 않는다.

중간 과정을 따라가는 예제

장애는 14:00이다. A는 13:55 데이터이며 사전 자산 검사·복구 뒤 필수 업무와 권한 검사를 통과해 14:24 재개한다. B는 13:58 데이터지만 사전 검사 실패다. 목표 30분과 데이터 시점 차이 10분을 비교하라.

  1. A의 중단 구간은 24분으로 30분 이내다.

  2. A의 데이터 시점 차이는 5분으로 10분 이내다.

  3. B의 차이는 2분이지만 복구 자산 검사 실패를 해결하지 못한다. 최신이라는 이유만으로 고르지 않는다.

주어진 검사 조건에서 A는 두 목표를 만족한다. B는 최근이어도 신뢰 조건을 만족하지 않는다. 실제 복구 성공을 관찰한 것은 아니다.

조건을 바꾸어 비교하기

시간 목표와 건수는 다른 계산

장애 15:00, 검사를 통과한 복구 데이터 시점 14:52, 필수 업무 재개 15:18이다. 목표는 복구 20분, 데이터 시점 차이 5분이다. 14:52 이후 장애까지 추가된 기록은 14:54의 2건, 14:58의 1건뿐이며 다른 변경은 없다.

  1. 업무 중단 구간은 18분으로 20분 이내다.

  2. 데이터 시점 차이는 8분으로 5분을 초과한다.

  3. 복구에 없는 추가 기록은 2+1=3건이다.

복구 시간 목표 충족, 데이터 시점 목표 미충족, 주어진 기록 손실은 3건이다.

비교할 점

시간 차이를 기록 수로 바꾸지 않고 별도 변경 목록을 사용한다.

원인이 같은 복사본

원본 O와 복사본 P는 같은 저장 장치에 있고 Q는 별도 장치에 있다. 장치 하나 고장 때 그 장치의 파일만 사라진다고 가정한다. 그러나 Q의 열쇠가 원본 장치에만 있다.

  1. 원본 장치 고장으로 O와 P가 함께 사라진다.

  2. Q 파일은 남지만 열쇠를 사용할 수 없다.

  3. Q의 복원 가능성은 파일 존재만으로 확인되지 않는다.

P는 공통 장치 실패에 취약하고 Q도 현재 조건에서 읽을 수 없다. 별도 보호·시험된 접근 정보가 필요하다.

비교할 점

위치 분리 뒤에도 복원 의존성이 남는 경우를 비교한다.

종이와 본문으로 직접 해보기

검사를 통과한 C는 14:35 재개·13:56 데이터, D는 14:20 재개·13:45 데이터다. 두 목표를 각각 판정하라. 13:58 이상 요청 관찰, 14:00 장애 확인, 14:04 격리 적용에서 추정과 조치를 구별하라.

힌트 보기

재개−14:00, 14:00−데이터 시각을 각각 계산한다. 이상 요청이 원인이라고 적혀 있지는 않다.

풀이 보기

C는 35분으로 시간 목표 실패, 4분으로 데이터 목표 통과다. D는 20분으로 시간 목표 통과, 15분으로 데이터 목표 실패다. 요청은 관찰, 장애는 확인, 격리는 수행 조치다. 세 기록만으로 요청이 원인이라고 확정하지 않고 조사 근거를 추가한다.

다른 문제에 적용하기

가상 앱 A→B→C에서 C를 갱신했다. 배포 파일 서명은 성공하나 받은 해시 J는 기록 H와 다르다. T0 폐기는 11:04부터 적용되고 T1은 11:03부터 조회만 허용된다. T0의 기존 조회 권한과 다른 인증 조건은 충족한다고 가정한다. 11:03:30 T0 조회와 T1 삭제를 판정하라. 별도 장애는 12:00, 검사를 모두 통과한 데이터는 11:54, 업무 재개는 12:16이며 목표는 20분과 데이터 시점 5분이다. 배포·권한·복구의 판단을 따로 보고하라.

힌트 1

서명 성공 외에 받은 파일과 기록을 연결한다.

힌트 2

token 유효 시각·권한·두 복구 시간 차이를 분리한다.

풀이와 답 확인

  1. J≠H이므로 대상 연결 실패로 배포 승인하지 않는다.

  2. 11:03:30 T0는 주어진 폐기 적용 전으로 조회 허용이고 T1 삭제는 권한에서 거절이다.

  3. 복구 16분은 20분 이내지만 데이터 시점 차이 6분은 5분을 초과한다.

  4. 이 판단은 문제 조건의 모델이며 실제 배포·폐기·복원을 수행한 것이 아니다.

배포 대상 검증 실패 / T0 조회 허용, T1 삭제 거절 / 복구 시간 충족, 데이터 시점 목표 미충족. 실제 손실 건수는 변경 목록이 없어 알 수 없다.

해결한 뒤 점검할 것

  • 해시 불일치와 서명 성공을 구별한다.

  • 폐기 적용 전후와 새 token 권한을 나누어 판정한다.

  • 16분·6분을 각각 계산하고 손실 건수를 추측하지 않는다.
