소단원 8.1

XSS·SQL injection·CSRF

받은 글자가 화면의 명령이나 다른 사람의 요청으로 바뀌면 무엇이 잘못된 걸까?

준비 개념과 학습 목표

준비 개념

  • 브라우저는 HTML·스크립트를 해석한다.

  • 서버는 요청을 받아 데이터베이스를 조회하고 상태를 바꾼다.

학습 목표

  • 세 취약점의 경계를 구분한다.

  • 위협에 맞는 방어를 골라 설명한다.

저장할 때 검사한 댓글을 다시 화면에 보낼 때는 무엇을 확인할까요?

입력은 여러 해석기를 지난다. 댓글을 데이터베이스에 안전하게 저장한 뒤에도 화면에서 HTML로 해석시키면 새로운 경계가 생긴다. SQL 바인딩은 질의와 값을 구별하는 장치이며, 출력 문맥에서의 텍스트 처리와는 역할이 다르다.

CSRF에서는 이미 인증된 브라우저가 원하지 않은 상태 변경 요청을 보내는 조건을 본다. 이 단원의 종이 모형은 서버 세션에 연결된 토큰을 요청의 별도 필드와 비교하며, cookie 전송 조건은 충족한다고 명시한다. 토큰 T나 U는 이름표일 뿐 실제 안전한 난수 문자열이 아니다. 토큰이 일치해도 요청별 객체 권한은 따로 확인한다.

먼저 확인할 개념
  • 세 취약점의 경계

    입력→해석기와 인증→상태 변경의 다른 질문을 확인한다.

  • 출력 문맥과 바인딩

    같은 데이터가 지나가는 해석기별 처리를 연결한다.

XSS: 글과 실행을 구별하기

XSS는 신뢰하지 않은 입력이 페이지의 실행 가능한 내용으로 해석되어 사용자의 브라우저에서 원치 않는 동작을 하는 문제다. 저장된 글, 요청에 반영된 글, 브라우저의 DOM 처리 등 여러 경로가 있다. 위험은 어디서 입력했는지만이 아니라 어느 해석 지점에 도착했는지에 달려 있다.

댓글을 일반 글자로 표시하려면 HTML로 끼워 넣는 대신 텍스트 출력 기능과 문맥에 맞는 인코딩을 쓴다. 서식 HTML을 꼭 허용한다면 검증된 HTML 정화 기능이 필요하다. HttpOnly 쿠키나 CSP 한 가지로 모든 XSS를 해결했다고 보지 않는다.

SQL injection: 질의와 값을 구별하기

SQL injection은 입력을 질의 문자열에 이어 붙여 데이터가 SQL 구조로 해석되게 만드는 문제다. 이름에 따옴표가 있는 정상 입력도 문자열 경계를 흔들 수 있다. 위험 문자를 무조건 삭제하면 정상 이름을 훼손하고 다른 문맥의 문제를 남긴다.

파라미터화는 질의의 문법과 바인딩할 값을 분리한다. 데이터베이스 드라이버의 실제 바인딩 API를 사용해야 하며, 완성 문자열을 만든 뒤 prepared라고 이름만 붙이는 것으로는 바뀌지 않는다. 이 방어가 HTML 출력이나 접근 권한까지 대신하지는 않는다.

CSRF: 인증된 요청과 사용자의 의도

CSRF는 다른 출처에서 유도한 요청에 사용자의 인증 쿠키가 함께 실려 서비스가 원치 않은 상태 변경을 받아들이는 상황이다. 쿠키가 실리는 조건은 SameSite·브라우저 정책 등에 따라 다르다. 로그인되어 있다는 사실과 그 행동을 사용자가 의도했다는 사실은 별개다.

쿠키 인증 서비스는 상태 변경 요청에 프레임워크의 CSRF 보호를 적용하고 서버가 토큰을 검증한다. 출처 검증과 SameSite 같은 보조 수단도 고려한다. GET으로 상태를 바꾸는 설계는 피한다. XSS가 같은 출처 권한으로 동작하면 CSRF 방어도 우회할 수 있어 둘을 함께 다뤄야 한다.

한 요청 경로의 보호 대상을 나누기

사용자·객체·행동의 권한 확인

한 단계가 통과해도 다른 단계의 질문은 남는다. 표는 실제 공격이나 취약성 검사의 실행 결과가 아니라 설계 검토용 분류이다.

중간 과정을 따라가는 예제

가상 도서관에 댓글 보기, 제목 검색, 대출 연장 기능이 있다. 댓글을 HTML로 삽입하고 검색 SQL을 문자열 연결하며 연장은 쿠키만 확인한다. 기능별 검토 대상 경계를 적어라.

  1. 댓글은 입력→HTML 해석 경계이므로 XSS의 출력 지점을 검사한다.

  2. 검색은 입력→SQL 문법 경계이므로 실제 값 바인딩을 적용한다.

  3. 연장은 브라우저 인증→사용자 의도 경계이므로 상태 변경 CSRF 보호를 적용한다.

  4. 각 기능의 대상 도서/대출에 대한 서버 권한 검사는 공통으로 별도 필요하다.

각각 XSS 출력 방어, SQL 파라미터화, CSRF 요청 검증이 필요하며 한 조치가 나머지 모두를 대체하지 않는다.

조건을 바꾸어 비교하기

안전하게 저장한 평문을 잘못 출력하기

검색어는 <b>안내</b>라는 평문이며 실제 SQL 바인딩으로 저장했다. 결과를 일반 div에 textContent로 넣는 경로 P와 HTML 삽입 기능으로 넣는 경로 Q를 비교하라.

  1. P는 문자열을 글자로 다뤄 <b>와 </b>까지 화면의 글이 된다.

  2. Q는 HTML 문법을 해석하여 b 요소를 만들 수 있다.

  3. 이 문자열 자체가 악성이라는 주장은 아니다. 임의 입력이 마크업으로 해석되는 경계가 남음을 찾는다.

P는 평문 의도를 유지한다. Q에는 별도의 HTML 허용·정화 검토가 필요하며 SQL 바인딩으로 해결되지 않는다.

비교할 점

저장 단계의 SQL 안전성과 화면 단계의 해석 여부는 다른 성질이다.

다른 세션의 유효 토큰

서버 세션 B의 토큰은 T, 세션 C의 토큰은 U이다. B cookie를 보내며 별도 필드에 U를 넣은 상태 변경 요청과 T를 넣은 요청을 비교하라. 둘 다 요청 권한은 있다고 가정한다.

  1. B의 기대 토큰은 T이다.

  2. U는 C에서 유효하다는 이유로 B의 기대값과 같아지지 않는다.

  3. T가 일치하는 경우는 이 토큰 검사만 통과한다. 실제 신뢰할 생성·전송과 다른 보호 조건은 별도로 필요하다.

U는 B의 토큰 검사에서 거절되고 T는 해당 검사에서 통과한다.

비교할 점

어딘가에서 유효한 값이라는 사실과 이 세션에 연결한 값이라는 사실을 구별한다.

종이와 본문으로 직접 해보기

검색을 파라미터화했지만 검색어를 결과 제목에 HTML로 삽입한다면 무엇을 더 확인해야 하는가?

힌트 보기

데이터베이스로 갈 때와 브라우저로 갈 때의 해석기를 따로 보자.

풀이 보기

SQL 구조는 보호해도 결과 화면의 XSS 경계는 남는다. 검색어를 해당 출력 문맥에 맞게 글자로 렌더링해야 한다.

오해와 반례

로그인 확인만 하면 이 세 취약점이 모두 사라진다.

로그인한 사용자의 댓글도 다른 사용자에게 출력되고, 로그인 상태의 브라우저도 원치 않는 요청에 이용될 수 있다. 인증과 코드/데이터 경계 및 요청 의도 검증은 다른 책임이다.

스스로 풀어보기

먼저 답과 이유를 적고, 필요한 만큼 힌트를 한 단계씩 열어 보세요.

연습 1 · 값과 상태 예측

댓글 문자열 A&B를 실제 SQL 바인딩으로 저장했다. 일반 div의 textContent에 원문을 넣는 P와 원문을 HTML 텍스트용으로 인코딩하여 서버 템플릿에 넣는 Q의 화면 글을 구하라.

힌트 1

textContent에는 원문을 전달한다.

힌트 2

템플릿의 HTML 표현과 화면 글을 나눈다.

풀이와 답 확인

  1. P는 원문 A&B를 텍스트로 표시한다.

  2. Q의 HTML 표현은 A&amp;B이며 화면에서는 A&B로 보인다.

  3. 둘 다 평문 표시라는 목표를 갖지만 전달 표현은 다르다.

화면의 글은 둘 다 A&B이다. P는 원문, Q는 해당 HTML 문맥용 인코딩 표현을 사용한다.

흔한 오답에서 다시 생각하기

textContent에도 반드시 A&amp;B를 넣어야 한다.

일반 div의 textContent는 HTML 파싱을 하지 않는다. 미리 인코딩하면 엔티티 글자가 그대로 보일 수 있다.

연습 2 · 오류 찾아 고치기

상태 변경 서버가 CSRF 토큰이 비어 있지 않은지만 확인한다. B의 서버 기대 토큰은 T인데 요청 토큰 U도 비어 있지 않아 승인했다. 오류를 고쳐라.

힌트 1

존재 검사와 세션 기대값 일치를 나눈다.

힌트 2

T와 U는 서로 다른 이름이다.

풀이와 답 확인

  1. U의 존재만으로 B의 기대 토큰과 연결되지 않는다.

  2. 요청 토큰의 존재와 B에 연결된 값의 유효성·일치를 확인한다.

  3. 실패 시 변경을 거절하고 권한 검사도 별도로 유지한다.

존재만 확인한 검사를 세션에 연결된 토큰 검증으로 고친다.

흔한 오답에서 다시 생각하기

긴 문자열이면 어느 세션에서도 유효하다.

길이만으로 생성·비밀성·세션 연결과 서버 검증을 대신하지 못한다.

연습 3 · 직접 만들어 보기

평문 댓글 저장·조회와 즐겨찾기 변경의 종이 방어 계획을 작성하라. 댓글은 서식 HTML을 허용하지 않고 쿠키 인증을 사용한다.

힌트 1

저장·출력·상태 변경을 각각 나눈다.

힌트 2

서버의 사용자·객체·동작 권한을 모든 경로에서 확인한다.

풀이와 답 확인

  1. 댓글 저장 질의는 드라이버의 실제 값 바인딩을 사용한다.

  2. 일반 요소에 원문 텍스트를 출력하거나 해당 서버 템플릿 문맥에 맞게 인코딩한다.

  3. 즐겨찾기 변경은 GET에 두지 않고 프레임워크의 CSRF 보호를 서버에서 검증한다.

  4. 각 대상 객체의 조회·변경 권한을 요청마다 확인한다.

세 경계의 방어와 요청별 권한을 명시한 계획이다. 실제 서비스 검사 완료라는 표시는 하지 않는다.

흔한 오답에서 다시 생각하기

로그인 사용자 입력만 받으므로 출력 경계는 생략해도 된다.

인증된 사용자도 다른 사람에게 표시될 데이터를 제공한다. 인증은 해석기 경계를 없애지 않는다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

세션 B의 토큰 T를 정상 검증했다. 그러나 같은 origin에서 이미 실행되는 잘못 삽입한 코드가 T를 읽고 B 권한으로 요청할 수 있다고 가정한다. 토큰 검사 통과가 무엇을 증명하지 못하는가?

힌트 1

문제에서 같은 origin 코드의 실행을 이미 허용했다.

힌트 2

외부 요청 위조 방어를 같은 origin 코드의 모든 행동 방어로 확대하지 않는다.

풀이와 답 확인

  1. 같은 origin 코드가 토큰을 사용할 수 있다는 조건에서 토큰 검사가 통과할 수 있다.

  2. 통과가 XSS 부재나 사용자가 실제 원한 행동임을 단독으로 증명하지 못한다.

  3. 출력·실행 경계를 보강하고 객체 권한도 유지한다.

CSRF 토큰 검증을 XSS의 완전한 방어로 확대하지 않는다.

흔한 오답에서 다시 생각하기

CSRF 토큰이 있으므로 같은 origin의 어떤 코드도 변경 요청을 못 한다.

입력·출력·파라미터화

이름 O’Neil을 지우지 않고도 안전하게 저장하고 표시할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 문법과 데이터는 처리 단계에서 구분해야 한다.

  • 검증은 허용 형식과 범위를 확인하는 작업이다.

학습 목표

  • 검증·출력 인코딩·SQL 바인딩의 역할을 구분한다.

  • 문맥별로 적절한 처리 순서를 설계한다.

표시용 표현을 원본으로 저장하면 다음 화면에 무엇이 보일까요?

원본 데이터와 전달 표현은 구별해야 한다. 텍스트 문맥의 서버 템플릿은 HTML 표현을 만들지만, 일반 DOM 요소의 textContent는 원문을 텍스트 노드로 넣는다. HTML 인코딩된 표현을 다시 textContent에 넣으면 두 방법을 중복 적용하게 된다.

SQL 값과 질의 구조도 따로 다룬다. 아래 모형에서 정렬 선택지는 서버의 고정 방향으로 대응시키고 검색값은 실제 드라이버로 바인딩한다. 사용자 문자열에 ASC나 DESC가 포함되어 있다는 부분 검색으로 구조를 선택하지 않는다. 업무 수량 검증과 대상 권한도 바인딩 이후에 자동으로 해결되지 않는다.

먼저 확인할 개념
  • 검증·출력·파라미터화

    원본과 HTML 표현, 값과 구조의 다른 계약을 확인한다.

  • XSS와 SQL 경계

    한 해석기에서의 안전성을 다른 해석기에 그대로 옮기지 않도록 연결한다.

입력 검증은 의미를 검사한다

수량은 정수이며 1~10, 이름은 정한 길이 이내처럼 업무 규칙을 서버에서 검사한다. 화면의 입력 제한은 사용성을 도울 수 있지만 서버 검사를 대신하지 않는다. 범위를 벗어난 입력을 거부하는 것과 임의로 글자를 삭제해 다른 값으로 바꾸는 것은 다르다.

입력이 정상 형식이어도 출력하는 곳에서 안전하게 다뤄야 한다. 이름의 따옴표·부등호처럼 일상적인 문자가 SQL 또는 HTML에서는 특별할 수 있다. 한 번 정화한 안전 문자열이라는 꼬리표로 모든 문맥을 통과시키지 않는다.

출력 시점의 해석 문맥

일반 HTML 텍스트로 A&B <C>를 표시할 때 &와 < 등은 엔티티로 인코딩한다. 텍스트를 기대하는 DOM API는 문자열을 마크업으로 해석하지 않게 해준다. 이 값이 HTML 속성·URL·JavaScript에 들어가면 필요한 규칙이 달라진다.

URL의 형식/스킴 허용검증은 HTML 인코딩만으로 해결되지 않는다. 실행 코드 문맥에 임의 데이터를 직접 넣지 않는 설계를 우선한다. 이미 인코딩한 값을 반복 인코딩하면 화면에 &amp; 같은 표현이 남을 수 있어 저장 데이터와 출력 표현을 구분한다.

질의 틀과 바인딩 값

SELECT title FROM books WHERE id = ?처럼 틀을 고정하고 id를 드라이버 바인딩으로 전달한다. 자리표시자 문법은 API마다 달라 실제 문서를 확인한다. 문자열의 따옴표를 직접 늘려 탈출시키는 방식 대신 코드/데이터 분리를 유지한다.

테이블 이름이나 정렬 방향 같은 SQL 구조는 일반 값 자리표시자로 대체할 수 없는 경우가 많다. 사용자가 직접 SQL 조각을 보내게 하지 말고 서버가 허용한 선택지에서 구조를 고른다. 파라미터화와 업무상 수량/권한 검증을 함께 적용한다.

표의 마지막 행은 목표한 원문과 다른 글을 표시한다. 원문을 지우거나 임의로 바꾸지 않고 목적에 맞는 출력 지점에서 처리한다.

중간 과정을 따라가는 예제

가상 검색 요청의 id는 문자열 "12", 표시 문구는 "A&B <C>"다. id 허용조건은 정수1~100이고 SQL은 id 값 바인딩, 화면은 HTML 텍스트 출력이다. 단계별 값을 적어라.

  1. id를 서버에서 정수로 해석해12를 얻고 범위1~100을 확인한다.

  2. 고정 질의의 id 자리에 숫자12를 값으로 바인딩한다. 질의 문자열을 사용자 값과 연결하지 않는다.

  3. 표시 문구를 텍스트 문맥 인코딩하면 A&amp;B &lt;C&gt;이고 브라우저에 보이는 글은 A&B <C>다.

  4. 원본 표시 데이터와 렌더링 표현을 별도로 생각한다. 실제 드라이버·브라우저 실행은 하지 않았다.

id12는 허용되며 질의 값은12, HTML 표현은 A&amp;B &lt;C&gt;다. 글의 의미는 유지한다.

조건을 바꾸어 비교하기

두 번 인코딩한 표현

HTML 텍스트 인코딩 E는 &를 &amp;, <를 &lt;, >를 &gt;로 바꾼다고 정한다. 원문 A&B에 E를 한 번 적용한 표현과 그 표현에 다시 E를 적용한 결과를 비교하라.

  1. E(A&B)는 A&amp;B이다.

  2. 두 번째 E는 앞의 표현에 있는 &를 다시 바꿔 A&amp;amp;B를 만든다.

  3. HTML 텍스트로 한 번 파싱하면 각각 A&B와 A&amp;B라는 글이 된다.

두 번 인코딩한 표현은 원문 대신 엔티티 글자를 보이게 할 수 있다.

비교할 점

인코딩 횟수를 늘리는 것이 항상 같은 의미의 안전한 출력이 되는 것은 아니다.

값 바인딩과 정렬 선택

선택지는 up→ASC, down→DESC뿐이다. 검색 이름은 O'Neil이고 정렬 입력은 up이다. 이름의 처리와 방향의 처리를 비교하라.

  1. 이름 O'Neil은 전체 문자열을 값으로 바인딩한다.

  2. up은 정확한 선택지 조회를 거쳐 서버 고정 ASC로 대응한다.

  3. 질의 구조에는 서버가 선택한 고정 방향만 쓰고 사용자의 이름이나 정렬 원문을 직접 연결하지 않는다.

바인딩 값은 O'Neil, 선택한 고정 방향은 ASC이다. 정상 이름의 따옴표를 지우지 않는다.

비교할 점

일반 값의 바인딩과 구조의 허용목록 선택은 서로 다른 절차이다.

종이와 본문으로 직접 해보기

값의 범위와 구조 선택을 따로 확인한다.

풀이 보기

101은 범위 밖이라 거부한다. ascending은 서버의 고정 ASC 선택으로 대응하며 사용자 문자열을 SQL 조각으로 직접 연결하지 않는다.

오해와 반례

파라미터화하면 입력 검증이 필요 없다.

바인딩은 SQL 구조 해석을 막지만 수량101이 업무상 적절한지는 판단하지 않는다. 질의가 안전해도 허용되지 않은 값·대상에 대한 요청은 별도로 거부해야 한다.

소단원 8.3

권한·세션·업로드 검증

파일 이름과 로그인 상태만 보고 그 파일을 열어도 될까?

준비 개념과 학습 목표

준비 개념

  • 인증은 사용자 식별, 인가는 특정 행동의 허용 여부다.

  • 업로드 요청의 이름·형식 표시는 사용자가 보낸 정보다.

학습 목표

  • 대상 객체별 서버 권한을 확인한다.

  • 세션과 업로드의 수명·검증·저장 경계를 설명한다.

작은 업로드 파일이 처리 과정에서는 큰 자원을 요구할 수 있을까요?

로그인과 업로드 권한, 대상 문서 권한, 파일 처리 조건은 다른 검사이다. 아래 모형은 파일을 비공개 임시 구역에 두고 정해진 검사를 통과한 뒤에만 공개 가능 상태로 옮긴다. 표시용 원래 이름과 서버가 지정한 저장 이름을 구별하고, 조회 때도 요청별 권한을 다시 확인한다.

전송 크기 한도는 처리 후 크기 한도와 같지 않다. 압축된 파일이 작아도 풀어서 처리할 때 큰 공간을 요구할 수 있다. 이 모형의 1MiB·4MiB 한도는 자체 숫자이며, 실제 파서·압축 해제·자원 측정은 하지 않았다. Content-Type·확장자·서명 일부만으로 전체 형식과 안전을 확정하지 않는다.

먼저 확인할 개념
  • 권한·세션·업로드

    객체별 권한과 파일 검증·저장 경계를 확인한다.

  • 입력 검증과 문맥

    사용자가 보낸 이름·형식 표시와 서버의 허용 조건을 구별한다.

식별자는 권한 증명이 아니다

사용자가 로그인했더라도 모든 문서를 읽거나 바꿀 수 있는 것은 아니다. 요청마다 사용자·행동·대상 객체를 확인해 소유권·공유 정책을 평가하고 기본적으로 거부한다. 화면에서 버튼을 감추는 것은 서버 접근 제어가 아니다.

문서 번호를 무작위 긴 문자열로 만들면 추측은 어려워지지만 우연히 알게 된 다른 사람의 번호에 대한 접근 권한을 부여하지는 않는다. 조회뿐 아니라 수정·삭제·다운로드에도 같은 대상별 검사가 필요하다.

세션의 수명과 변화

세션 토큰은 인증 상태에 연결되는 민감한 값이다. 전송·저장 노출을 줄이고 로그인이나 권한 상승 뒤 식별자를 갱신하며 로그아웃·만료 때 서버가 무효화한다. 클라이언트 쿠키만 지우면 서버 토큰이 계속 유효할 수 있다.

Secure는 쿠키의 HTTPS 전송을, HttpOnly는 스크립트의 직접 쿠키 접근 제한을 돕는다. 이 속성들이 모든 요청 위조·XSS 행동·객체 권한 문제를 자동 해결하지는 않는다. 유휴 시간과 절대 만료를 구분해 서비스의 위험과 사용성을 고려한다.

업로드는 여러 검사를 통과한다

확장자 허용목록·실제 형식·파서 처리·크기/압축해제 한도·권한을 함께 확인한다. 요청의 Content-Type이나 파일 이름만 믿지 않는다. 허용된 이미지도 처리 라이브러리의 취약점이나 자원 소모 위험이 있어 적절한 설정과 갱신이 필요하다.

서버 생성 파일명과 안전한 저장 위치를 사용하고 실행 가능한 웹 경로와 분리한다. 조회는 권한을 검사하는 핸들러로 제공할 수 있다. 실패 검사 이후 원본을 공개하지 않고, 업로드 자체도 상태 변경이므로 인증 방식에 맞게 CSRF 보호를 적용한다.

중간 과정을 따라가는 예제

가상 서비스에서 지수는 문서 D1의 소유자, 민수는 소유자도 공유 대상도 아니다. 민수가 로그인 세션으로 D1 다운로드와 이미지 업로드를 요청한다. 업로드 제한은 실제 PNG·1MiB 이하이고 제출 파일은 1.2MiB다. 판단하라.

  1. 다운로드는 로그인 유효성만으로 허용하지 않는다. D1 공유/소유 정책상 민수는 거부한다.

  2. 업로드 역할을 허용했다고 가정해도 파일 크기 조건을 따로 검사한다.

  3. 1.2MiB>1MiB이므로 업로드 거부다. 이름이 picture.png여도 용량 조건을 넘는다.

  4. 검사 실패 파일은 공개 경로로 옮기지 않는다. 실제 서버 처리나 파일 디코딩은 수행하지 않았다.

다운로드는 객체 권한 실패, 업로드는 용량 실패로 각각 거부한다. 실패 이유가 서로 다른 경계에 있다.

조건을 바꾸어 비교하기

경계 한 바이트를 비교하기

1MiB=1,048,576바이트이다. 전송 파일 A는 1,048,576바이트, B는 1,048,577바이트이다. 한도 이하만 허용한다.

  1. A는 한도와 정확히 같아 크기 조건을 통과한다.

  2. B는 한도보다 1바이트 커서 크기 조건에서 거절한다.

  3. 둘 다 아직 실제 형식과 처리 후 조건을 확인해야 한다.

A는 해당 크기 조건 통과, B는 초과 거절이다.

MiB를 1,000,000바이트로 바꾸거나 경계의 ≤를 <로 바꾸면 다른 정책이 된다.

업로드 성공 뒤 공유가 철회되기

민이 소유한 파일 F를 윤에게 다운로드만 공유했다. 업로드·내용 검사는 완료되었다고 가정한다. 윤의 수정 요청과 공유 철회 뒤의 새 다운로드 요청을 판정하라.

  1. 다운로드 공유에는 수정 권한을 넣지 않았다.

  2. 수정은 요청별 행동 권한이 없어 거절한다.

  3. 철회 후 새 다운로드 요청은 현재 공유 상태를 다시 확인하여 거절한다.

두 요청 모두 거절한다. 이전 업로드 성공은 현재 요청 권한의 증거가 아니다.

이미 윤이 받은 파일의 복사본을 서버에서 회수할 수 있다는 주장은 하지 않는다.

연습 1 · 값과 상태 예측

전송≤1MiB·처리 후≤4MiB 한도이다. 파일 S는 786,432바이트이고 처리 후 크기는 4,194,304바이트이다. 크기 조건 결과와 남은 검사 범위를 설명하라.

힌트 1

786,432는 1MiB의 3/4이다.

힌트 2

4MiB=4,194,304바이트이며 경계 이하를 허용한다.

풀이와 답 확인

  1. 전송 크기는 1MiB 미만이다.

  2. 처리 후 크기는 4MiB와 같아서 두 크기 조건을 통과한다.

  3. 권한·실제 형식·파서와 저장·조회 조건은 별도로 남는다.

두 크기 조건은 통과하지만 파일의 전체 안전 검증이 완료된 것은 아니다.

흔한 오답에서 다시 생각하기

크기가 맞으면 형식과 소유권도 자동으로 유효하다.

크기 비교의 판정 범위는 정해진 두 수치 조건까지이다.

연습 2 · 오류 찾아 고치기

프로그램이 사용자 이름 report.png와 Content-Type:image/png를 보고 즉시 공개 경로에 옮긴 뒤 내용 검사 실패 시 삭제한다. 검사 실패 전 잠시 공개될 수 있다. 순서를 고쳐라.

힌트 1

사용자가 제공한 두 표시는 전체 형식 증명이 아니다.

힌트 2

공개하기 전에 정한 검사를 끝낼 구역을 생각한다.

풀이와 답 확인

  1. 비공개 임시 저장 구역에서 검사한다.

  2. 확장자·내용·파서·크기·권한 등 정한 조건을 확인한다.

  3. 성공한 경우에만 서버 저장 이름과 조회 정책을 적용하여 제공하고 실패 원본은 공개하지 않는다.

검사 이전의 공개를 제거하고 승인 뒤 제공하는 흐름으로 바꾼다.

흔한 오답에서 다시 생각하기

나중에 삭제하므로 앞의 공개는 아무 영향이 없다.

삭제 전의 조회 가능 시간은 남는다. 실제 공개·다운로드가 없었다고 가정할 수 없다.

연습 3 · 직접 만들어 보기

업로드한 파일의 원래 이름은 학습자 표시용으로 유지하고 저장 이름은 서버가 생성한다. 소유자 민과 읽기 공유 윤이 있다. 수정·조회·삭제와 실패 파일의 상태를 포함한 계획을 작성하라.

힌트 1

표시 이름을 파일 경로나 실행 명령으로 사용하지 않는다.

힌트 2

윤의 읽기 권한을 다른 행동으로 넓히지 않는다.

풀이와 답 확인

  1. 표시 이름은 텍스트 문맥에 맞게 처리하고 저장 경로는 서버가 결정한다.

  2. 민의 소유 권한과 윤의 읽기 공유를 행동별로 검사한다.

  3. 윤의 수정·삭제는 불허하고 조회 때 현재 공유를 재확인한다.

  4. 검사 실패 파일은 비공개 상태로 유지한 뒤 정한 폐기 정책을 적용한다.

저장 이름·표시 문맥·행동별 현재 권한·실패 비공개를 함께 명시한 계획이다.

흔한 오답에서 다시 생각하기

서버 저장 이름이 무작위면 조회 권한 검사는 필요 없다.

추측하기 어려운 이름을 알고 있다는 사실이 조회 허용의 증거는 아니다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

서버가 파일 F의 조회를 권한 핸들러에서 거절한다. 하지만 같은 F를 권한 없이 주는 직접 정적 URL도 존재한다고 가정한다. 보호 목표와 수정 범위를 설명하라.

힌트 1

요청 경로를 핸들러 하나로 한정하지 않는다.

힌트 2

직접 정적 경로는 서버 권한 검사에 도달하는지 확인한다.

풀이와 답 확인

  1. 핸들러 경로에서의 거절은 직접 경로의 응답을 막지 않는다.

  2. 직접 제공 경로를 제거하거나 동일한 권한 경계로 제한한다.

  3. 다른 복사본·캐시·이미 받은 파일의 범위도 별도로 정의한다.

F를 제공하는 모든 새 요청 경로에서 정책을 적용해야 한다. 실제 설정 변경이나 시험 결과는 아니다.

흔한 오답에서 다시 생각하기

핸들러 하나를 검사했으므로 모든 파일 접근 경로도 검증되었다.

누락된 직접 경로가 문제의 명시된 반례이다. 일부 경로의 판정을 전체로 확대하지 않는다.

설명 기준 확인

요청자가 제공한 표시이다. 실제 내용·허용 형식·파서와 자원 조건을 별도로 확인해야 한다.

조회 권한 검사를 업로드 시점에 한 번만 해도 되는가?

설명 기준 확인

아니다. 공유·세션·대상과 행동이 바뀔 수 있어 새 요청의 현재 조건을 확인하고 모든 제공 경로에 적용한다.

한 단계 더

사용자/행동/문서 소유·공유 조건별로 허용 표를 만들고, 업로드 파일의 허용 형식·저장 위치·조회 권한·삭제 수명까지 종이 설계를 확장하라. 실제 서비스 보안 검증 완료로 표시하지 않는다.

출처와 확인 범위
  • OWASP: Authorization

    기본 거부와 요청마다 서버 권한 검증, 식별자와 접근 권한의 차이를 실제 읽었다.

  • OWASP: Session Management

    세션 토큰 취급·인증/권한 변경 시 갱신·만료·Secure/HttpOnly 및 서버 무효화를 읽었다.

  • OWASP: File Upload

    확장자·실제 파일형식·용량·서버 생성 파일명·webroot 밖 저장·권한·파서 및 CSRF 방어를 읽었다.

다른 문제에 적용하기

가상 도서 서비스는 이름 O'Neil을 실제 SQL 값으로 바인딩한다. 검색 결과 댓글 R&D <노트>는 이미 HTML 인코딩한 표현을 일반 div의 textContent에 넣는다. B의 기대 CSRF 토큰은 T인데 별도 요청 필드 U를 비어 있지 않다는 이유로 승인한다. 업로드는 전송 786,432바이트·처리 후 5MiB이며 전송≤1MiB·처리 후≤4MiB이다. 네 경계를 각각 판정하고 수정 방향을 써라.

힌트 1

원본과 인코딩 표현, 존재와 세션 일치 검사를 나눈다.

힌트 2

전송 조건의 통과가 처리 후 조건의 통과를 뜻하지 않는다.

풀이와 답 확인

  1. 이름은 바인딩 값으로 유지하며 따옴표를 지우거나 SQL 조각으로 연결하지 않는다.

  2. textContent에는 원문 R&D <노트>를 전달하여 엔티티 글자가 그대로 보이는 중복 처리를 고친다.

  3. U는 B의 기대 T와 달라 토큰 검사를 거절하고 요청 권한도 따로 확인한다.

  4. 전송은 0.75MiB로 통과하지만 처리 후 5MiB가 4MiB를 넘으므로 업로드를 거절하여 공개하지 않는다.

SQL 값 분리는 유지하고, 출력은 원문 텍스트 전달로 고친다. CSRF 세션 일치 검사와 처리 후 용량 조건은 실패하므로 해당 변경·업로드를 거절한다.

해결한 뒤 점검할 것

  • 바인딩과 표시 문맥을 구별한다.

  • textContent의 원문 전달 계약을 설명한다.

  • 토큰 존재와 세션 연결을 구별한다.

  • 전송 0.75MiB와 처리 후 5MiB를 따로 판정한다.

보강 자료의 출처와 확인 범위
  • OWASP — XSS Prevention

    실제 243–284,291–361을 읽어 일반 요소의 textContent 원문 계약, 문맥별 인코딩·URL 조건·정화 뒤 변경과 safe sink 범위를 확인했다. 새 문자열은 자체 표현 모형이며 위험 문자열의 실제 실행은 없다.

  • OWASP — SQL Injection Prevention

    실제 229–258,333–380을 읽어 코드/데이터 분리·값 바인딩·구조 허용목록·업무 검증과 최소 권한의 다른 역할을 확인했다. 드라이버 호출은 새로 실행하지 않았다.

  • OWASP — CSRF Prevention

    실제 267–289,291–307을 읽어 프레임워크 보호·상태 변경 검증·세션 연결 토큰과 XSS 한계를 확인했다. T/U는 자체 표의 이름이고 실제 생성·배포·요청이 아니다.

  • OWASP — Authorization

    실제 194–207,211–233을 읽어 인증과 인가·기본 거절·모든 요청의 권한 검증 범위를 확인했다. 파일의 직접 경로와 현재 공유 조건은 자체 사례다.

  • OWASP — File Upload

    실제 205–248,263–292,299–329를 읽어 표시의 불신·서명 검사 단독 한계·서버 이름·저장 위치·권한·처리 후 자원과 요청 제한을 확인했다. 새 1MiB/4MiB 한도와 바이트 계산은 자체 종이 조건이다.

전체 기본과 세 실제 의미 앵커, 다섯 OWASP 본문 범위를 읽었다. HTML 전달 표현과 textContent 원문, 두 번 인코딩, 정렬 정확 일치와 부분 검사 반례, 세션 토큰 연결, MiB 바이트 경계·처리 후 용량·공유 철회·직접 경로와 전이를 손추적했다. 최종 저장본 전체 3소단원·12과제·전이·출처를 실제 다시 읽어 SQL 안전과 업무 의미, 평문 원문과 인코딩 표현, 검사 계획과 실행 관측의 구분을 확인했다.
