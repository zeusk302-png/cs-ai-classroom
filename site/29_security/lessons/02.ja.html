小節 2.1

パスワード・MFA・セッション

パスワードを二度尋ねれば二要素認証になるだろうか？

準備する概念と学習目標

準備する概念

  • 主体とは、アカウントやサービスなど、権限が与えられる対象である。認証は、名乗った主体の認証手段を制御していることを確認する過程である。
  • 秘密とは公開されるべきでない値であり、ハッシュは入力を固定長の値へ変換する関数である。同じ入力が同じハッシュになることは、元の入力を復元できることを意味しない。
  • セッションは認証後の連続したやり取りをまとめる状態である。時間差 t−s は同じ時間基準と単位で計算する。

学習目標

  • 認証要素の種類と個数を区別する。
  • セッションの全体の有効期間と無操作による期限切れをそれぞれ判定する。

パスワードを検証する契約

サーバーはアカウントに結び付けられたパスワードの検証情報を使う。パスワードを平文で保存する代わりに、salt とコストパラメーターを含む専用のパスワードハッシュ方式で検証する。salt はアカウント間で事前計算を共有しにくくする値であり、パスワードのように必ず秘密であるべき値ではない。ハッシュがあっても、弱いパスワードの候補を推測する余地はなくならない。

認証結果は、このアカウントの認証手段を制御していることの根拠である。特定の文書を変更してよいかは、別の認可の問題である。公開資料は認証なしで許可できるので、すべての資源にログインが必要だという結論も成り立たない。

二要素と認証後のリスク

要素は、知っているもの、持っているもの、身体的特徴など、異なる種類に分ける。パスワードと PIN はどちらも知識要素なので、二つの質問でも異なる二要素ではない。パスワードと別の所持手段の検証は、適切な結合手順の下で二要素になり得る。生体的特徴も、実際の認証装置や検証手順とどう組み合わせるかに応じて扱う。

MFA という名前だけで、フィッシング耐性やセッションの乗っ取り防止が保証されるわけではない。例えば、認証後に発行された bearer 型のセッション秘密は、それを提示する相手を通すため、秘密を盗んだ相手も利用できる。保護された通信路、セッション秘密の保護、期限切れ、再認証を、初回認証とともに設計する。

紙上セッションの二つの時計

この単元の仮想サーバーは、整数の分を単位とする単調な時間を使う。認証成功時には created=last=t, valid=true で開始する。セッション検査は valid が真で、0≤t−created<12 および 0≤t−last<5 のときだけ成功する。成功したセッション検査だけが last=t に更新し、失敗時には valid=false にする。これは独自の方針であり、NIST の時間値ではない。

全体の有効期間は操作を行っても延びず、無操作時間の基準だけが更新される。ログアウトは valid=false にする。境界では等号を認めないため、ちょうど5分または12分になると失敗する。時間の逆行と同時検査の問題を除いた逐次モデルであり、実際の分散サーバーでは時計・原子性・復旧の契約を追加する必要がある。

途中の過程をたどる例題

t=0 に二要素認証でセッションを作り、t=4,9,10 に順番に検査する。上記の方針による結果と last を追跡せよ。

  1. t=0: created=last=0, valid=true とする。認証成功そのものがすべての資源の変更権限を与えるわけではない。
  2. t=4: 全体4<12、無操作4<5なので成功し、last=4になる。
  3. t=9: 全体9<12だが、無操作9−4=5が厳密な境界に達するため失敗する。valid=falseになる。
  4. t=10: 秘密を再び提示しても、valid=falseなので失敗する。last は最後に成功した値4を保つ。

成功、失敗、失敗で、last=4である。セッションの再開始は、新たな認証手順の結果でなければならない。

紙と本文で試してみよう

新しいセッション created=last=0 で、t=4,8,12 の検査結果を表にせよ。パスワード+PIN を二要素と呼べるかも説明せよ。

ヒントを見る

成功するたびに last だけを変える。最後には全体の有効期間を先に確認する。

解答を見る

t=4 は成功して last=4、t=8 は成功して last=8、t=12 は全体の有効期間が12なので失敗する。パスワード+PIN はどちらも知識要素なので、二種類の要素ではない。

よくある誤解と反例

MFA を通ったので、セッション秘密が漏れても安全だ。

bearer 型のセッションでは、盗んだ秘密を提示する相手が許可され得る。初回認証の強化と、認証後のセッション保護は異なる境界である。

理解を確かめる

パスワードと PIN は二種類の要素か？

答えと理由を見る

違う。

どちらも知っている値を証明する知識要素である。

created=0, last=8 の有効なセッションを t=12 に検査すると？

答えと理由を見る

失敗する。

無操作時間4は許容されるが、全体の有効期間12は <12 を満たさない。

認証成功だけで他人の文書を変更できるか？

答えと理由を見る

別の権限がなければ許可されない。

アカウントの確認と、主体・対象・操作に対する認可は別の判定である。

もう一歩先へ

セッションの不変条件は、成功後に created≤last≤t が成り立ち、created は新しい認証なしでは変わらないことである。生成時には created=last=t なので成り立つ。成功検査前には t≥last≥created であり、成功後に last を現在の t に変えるので不等式が保たれる。失敗とログアウトは created と last を変えず、その後の成功を認めない。これは単調な時間の逐次モデルに限った帰納的議論である。再認証で有効期間をリセットするには、新しい認証の強度と以前のセッションを廃棄する方針を明示しなければならない。実際のサービスにおける NIST の適用範囲や AAL ごとの要件を、この仮想時間表だけで満たしたとは主張できない。

小節 2.2

アクセス制御・役割・capability

教員という名前が付けば、すべての学生の成績を変更できるだろうか？

準備する概念と学習目標

準備する概念

  • 対象は、保護する文書・レコードなどの資源である。操作は read や update のように、その資源に対して行う演算である。
  • 集合 R の部分集合 R′⊆R とは、R′のすべての要素が R にも含まれることである。{read}⊆{read,update} は真である。
  • 役割は、複数の主体に共通の権限をまとめて与える分類である。ACL は対象に付けられた主体別の許可リストである。

学習目標

  • 主体・対象・操作・状況を含む許可条件を作る。
  • 役割に基づく許可と、capability の権限縮小を比較する。

誰が何をできるか

アクセス制御は、要求の主体 u、対象 o、操作 a と状況を方針 P と照合する判定である。デフォルト拒否モデルは、明示した許可条件が真のときだけ通す。要求に含まれる owner や role の文字列は、信頼できるサーバー情報と区別しなければならない。推測しにくい対象番号は権限検査の代わりにならない。

仮想の学校では、学生は自分の成績を read できるが update できない。教員は担当するクラスの成績を read または update できる。したがって、役割に加えて所有関係またはクラスとの関係が必要である。サーバーが主体を認証した後、実際の対象のクラスを調べて判定する。

役割と対象別リスト

RBAC はユーザー→役割と役割→操作の関係によって共通規則を管理する。同じ役割でも対象の範囲を加えなければ、別のクラスにまで権限が広がり得る。ACL は特定の対象について、どの主体にどの操作を許可するかを列挙する。両者は方針の表現方法であり、実装の正しさを自動的に保証する名前ではない。

このモデルでは、学生 s の read は owner(o)=s のとき許可し、教員 T の read/update は class(o)=assigned(T) のとき許可する。それ以外は拒否する。すべての保護された操作の入口がこの判定を通らなければならず、画面のボタンを隠すだけではサーバーの方針を実施できない。

capability と縮小される権限

capability は、特定の対象と操作権限に関する偽造不可能な証票である。ここでは、信頼された発行者が作った対象番号・権限集合・期限を検証する抽象的な証票を仮定する。単純な JSON に権限を記すだけでは偽造不可能性は生まれない。bearer 方式なら、それを持つ相手へ権限が渡るので、受け渡しと保管も方針の対象になる。

権限縮小が許された発行手順で、元の (o,R,e) から (o,R′,e′) を作るとき、R′⊆R, e′≤e を要求する。検証側は有効な発行・委譲の連鎖と、現在 t<e′ を確認する。したがって、縮小版が許可した操作は元の権限にも含まれる。対象の変更や権限の追加を任意の文字列編集で認めないという前提が、この議論の核心である。

途中の過程をたどる例題

s は学生で成績 X の所有者、T はクラス A を担当する教員である。X はクラス A、Y はクラス B に属する。要求 s/read/X, s/update/X, T/update/Y と、capability C=(X,{read,update},10) の縮小 C′=(X,{read},8) を判定せよ。

  1. s/read/X は owner(X)=s なので許可する。
  2. s/update/X は学生規則の操作に update がないので拒否する。
  3. T/update/Y は class(Y)=B≠A なので拒否する。教員という役割だけでは通さない。
  4. C′は同じ対象、部分集合の権限、8≤10により、有効な縮小の候補である。信頼できる発行の連鎖を確認した後、t=7 の read は許可し、t=8 は期限切れで拒否する。ここで t は時間であり、教員の名前 T とは異なる。

最初の三要求は許可/拒否/拒否である。capability の read にも証票の検証と時間条件が必要である。

紙と本文で試してみよう

C=(X,{read},10) からの (X,{read,update},9), (Y,{read},9), (X,{read},11) のうち、有効な縮小の候補を選べ。

ヒントを見る

権限の包含・対象の同一性・期限を延長しないことという三条件をすべて検査する。

解答を見る

すべて不適合である。第一は update を追加し、第二は対象を変更し、第三は期限を延ばす。元のまま、または (X,{read},9) は条件を満たす候補だが、発行の連鎖の検証も必要である。

よくある誤解と反例

対象 ID を隠すか教員の役割を確認すれば、アクセス制御は終わる。

別のクラスの対象 ID を知った教員は役割検査を通っても、クラス関係に違反する。実際に対象を使うサーバーの箇所で範囲条件を確認しなければならない。

理解を確かめる

s/read/X において、X の所有者が別の学生に変わったら？

答えと理由を見る

拒否する。

現在の owner(X)=s 条件が偽である。

R′⊆R は権限縮小のどの性質を証明するか？

答えと理由を見る

縮小版の許可操作が、元の許可操作に含まれること。

a∈R′なら、部分集合の定義から a∈R である。

権限リストを書いた任意のファイルは capability か？

答えと理由を見る

それだけでは違う。

偽造不可能な発行と検証、または保護された対象参照など、実施の根拠が必要である。

もう一歩先へ

権限縮小を繰り返すと、R2⊆R1⊆R0, e2≤e1≤e0 が保たれる。実際、a∈R2 なら a∈R1 であり、さらに a∈R0 である。t<e2 なら t<e1 と t<e0 も成り立つ。同じ対象と有効な発行の連鎖を各段階で保つという前提の下で、この議論を繰り返すと、任意の有限な委譲段階でも新しい操作権限や、より長い期限を作らない。しかし元の証票の盗難、委譲禁止への違反、対象の意味の変更、取り消しの伝播は、この包含関係だけでは解決できず、別の契約が必要である。

小節 2.3

権限昇格と監査

拒否ログが残っているだけで、攻撃者を特定できるだろうか？

準備する概念と学習目標

準備する概念

  • 権限昇格は、方針上許されない、より広いアクセスを獲得することである。垂直の昇格はより高い役割、水平の昇格は同じ水準の他人の資源へのアクセスを意味する。
  • 監査記録は観測した出来事を後で追跡するための資料である。記録された主体の識別値は、実在の人物に関する完全な証明ではない。
  • 原子的な遷移は、別の遷移が途中に割り込まないモデルの一段階である。方針のバージョンは、どの規則で判定したかを区別する番号である。

学習目標

  • 要求の入力と信頼された役割情報を区別する。
  • 検査と使用の境界、およびログの証拠としての範囲を説明する。

昇格と正当な権限変更

教員が承認手順によって新しい担当クラスを得るのは、正常な権限変更である。一方、クライアントが role=admin を送ったことだけを信じてサーバーが管理者操作を認めると、垂直の権限昇格になる。自分の成績ではなく別の学生の成績へアクセスする水平の昇格も、同じ主体・対象・操作の方針違反である。

防御モデルは、認証で得たサーバー側の主体と、サーバーの現在の役割・関係を使う。権限付与自体にも、誰が誰へどの範囲を与えられるかという方針が必要である。権限を与える機能と一般の文書変更権限を混同すると、最小権限の設計が崩れる。

確認から使用までの隙間

権限検査を通ってから実際に書き込むまでに、権限が取り消される場合がある。検査時の許可を要求する方針と、使用時にも許可を要求する方針は異なる。この単元は使用時の方針を選び、現在のバージョンの検査と変更を一つの原子的遷移にまとめる。取り消しが先に行われれば、その後の書き込みは拒否する。

バージョン v を読んだという事実だけで原子性は生まれない。実際の実装には、検査と更新の同期、トランザクション、またはバージョン比較を用いた競合処理と失敗時の契約が必要である。ここでの逐次的な原子状態表はその契約の意味を説明するものであり、実際のデータベースや OS の性能・並行安全性試験ではない。

監査から分かること

監査には、要求識別子、観測した主体、対象、操作、許可/拒否、理由、方針のバージョンなどを、決めた形式で残す。元のパスワードや bearer トークンをそのまま入れると、ログが新たな漏洩資源になる。入力に含まれる改行を無批判に記録して、偽の出来事のように見せる問題も防がなければならない。

記録へのアクセス制限、変更の検知、保存方針は資料の信頼性を高めるが、記録だけで予防や犯人の特定はできない。アカウントが盗まれたり、観測箇所の外の出来事が欠落したりすることもある。異なる機械の時刻だけで全体の因果順序を確定せず、この例の連番は単一サーバーが観測した順序に限定する。

途中の過程をたどる例題

方針 v0 では学生 s は X を変更できない。次の要求と権限変更を順に原子的に処理する：s が role=admin を添えて X の変更を要求し、信頼された管理者が s に X の変更権限を与え(v1)、s が X を変更し、管理者が取り消した(v2)後に s が X の変更を要求する。実際の役割情報にはサーバー情報だけを使う。

  1. 最初の要求では、クライアントの role を権限として採用しない。v0 で拒否し、X は変わらない。
  2. 方針の管理権限を持つ管理者の付与遷移が v1 を作る。この行為は承認された権限変更である。
  3. s の次の変更は現在の v1 で許可される。成功した監査出来事には主体 s、対象 X、操作 update、バージョン v1 を残す。
  4. 取り消しが v2 として完了した後の変更は拒否する。この単一サーバーの監査順序と方針バージョンは判定の根拠を示すが、s という人物が直接要求したことは証明しない。

拒否、正常な付与、許可、取り消し後の拒否である。失敗した変更は X を変えないモデルである。

紙と本文で試してみよう

v1 で検査だけを通った要求が待機する間に、v2 の取り消しが先に完了した。検査結果をキャッシュしたまま書き込む場合と、使用時に原子的に再検査する場合の結果を比べよ。パスワードをログに入れてよいかも説明せよ。

ヒントを見る

この単元の方針は使用時の権限である。過去の検査の事実と、現在の許可条件を分ける。

解答を見る

キャッシュだけを信じると、現在の方針に違反する書き込みを許可し得る。v2 で原子的に再検査すれば拒否する。パスワードはログに直接入れず、要求 ID・判定理由などの最小限の情報で監査の目的を達成する。

よくある誤解と反例

監査ログがあれば、権限違反を防ぎ、実際の行為者を特定できる。

誤って許可した要求もログに残り得るため、記録は予防とは異なる。盗まれたアカウントの主体 ID が残っても、アカウントの所有者が実際の行為者だという結論には別の根拠が必要である。

理解を確かめる

要求フィールド role=admin は管理者権限の根拠か？

答えと理由を見る

違う。

信頼されたサーバーの方針と主体の関係を確認しなければならない。

使用時の方針では、取り消し後に過去の検査結果だけを信じて書き込んでも安全か？

答えと理由を見る

その契約は保証されない。

検査と使用の間の方針変更を反映できない。

元の bearer トークンを監査に記録すべきか？

答えと理由を見る

直接記録しない。

トークンを読んだ相手がセッションを悪用し得るため、監査が漏洩経路になる。

もう一歩先へ

保護された書き込みの不変条件は、「各成功遷移の主体・対象・操作は、その遷移で使った方針バージョンによって許可された」である。最初は成功記録がないので、空の場合として成り立つ。次の遷移が拒否または方針変更なら、新しい成功書き込みはなく、以前の記録のバージョンごとの判定は変わらない。次の遷移が成功書き込みなら、同じ原子的遷移の中で現在の方針検査を通った場合だけ書き込みを許すので、新しい記録も条件を満たす。したがって、すべての入口が同じ判定を通り、検査と使用が原子的であるという前提で、帰納的に成り立つ。これは、後の取り消しが過去の書き込みを遡って無効にするという意味ではない。監査保存に失敗したときに機密性の高い書き込みを拒否するか、別のキューに記録するかはサービスの契約である。記録と書き込みの原子性・耐久性がない単純な関数呼び出しだけで、両方が成功したとは主張できない。
