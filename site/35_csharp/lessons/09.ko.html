query·method syntax

필터와 투영의 순서를 바꾸어도 같은 질의가 될까?

앞 본문에서는 같은 Where/Select 연산을 두 문법으로 적었다. 같은 연산의 문법 변환과 연산 순서 변경은 구별해야 한다. 자체 입력 [1,2,3]에서 먼저 원래 값 n>2를 고르고 2*n을 만들면 [6]이다. 먼저 2*n으로 만든 값 m에서 m>2를 검사하면 [4,6]이다. 둘째 조건은 원래 n>1이라는 뜻이 되어 다른 질의다.

순서를 바꾸려면 조건의 뜻도 새 요소 타입에 맞춰 옮긴다. 같은 입력과 정수 범위에서 m=2*n 뒤 m>4는 원래 n>2와 일치한다. 입력은 작은 값이고 곱셈 오버플로가 없다는 조건이다. 더 일반적인 손실 투영에는 같은 조건을 복원할 정보가 남지 않을 수 있다. 이름만 남긴 학생 요소에는 앞 학년 필드가 없을 수 있다.

평가에서 관찰되는 효과와 실패까지 계약으로 삼으면 단순 결과 목록만 비교해서는 부족하다. 자체 배열 [0,2]에 대해 n!=0으로 먼저 필터한 뒤 12/n을 투영하면 [6]이다. 먼저 12/n을 만든 뒤 필터하는 변형은 첫 0에서 예외를 낸다. 이 단원은 LINQ to Objects와 작은 고정 입력의 손추적이며 실제 C#이나 provider를 실행하지 않는다.

질의는 원하는 결과를 설명한다

LINQ는 여러 자료원에 질의를 표현하는 C# 모델이다. 먼저 자료원을 정하고 질의를 만들고 열거해 결과를 얻는 단계를 나눈다. 이 단원은 메모리 안 정수 목록의 LINQ to Objects를 사용하며 DB의 번역 규칙은 따로 다룬다.

문법을 연산에 대응하기

from은 입력 요소를 이름에 연결하고 where는 조건을 통과한 요소를 남기며 select는 결과를 만든다. 같은 연산을 Where와 Select의 메서드 호출로 표현할 수 있다. 컴파일러는 query 표현을 메서드 호출로 바꾸므로 문법 자체가 다른 알고리즘이나 자동 최적화 보장은 아니다.

int[] nums = { 1, 2, 3, 4 };
var q = from n in nums where n % 2 == 0 select n * 10;
var m = nums.Where(n => n % 2 == 0).Select(n => n * 10);
var a = q.ToArray();
var b = m.ToArray();

중간 요소의 타입을 따라가기

Where 뒤에도 정수 요소가 흐르지만 Select로 문자열을 만들면 결과 요소 타입도 바뀐다. lambda의 입력과 반환을 적어 합성이 가능한지 확인한다. Count처럼 단일 값을 반환하는 연산은 메서드 문법을 섞어 표현한다. using System.Linq가 연산을 사용할 범위를 제공한다.

중간 과정을 따라가는 예제

고정 배열 [1,2,3,4]에서 짝수만 남겨 각각 10배 한다. 두 표현을 ToArray로 열거한 결과를 구하라.

  1. 1과 3은 n%2==0을 만족하지 않는다.

  2. 2와 4를 순서대로 남긴다.

  3. 각각 2×10=20,4×10=40으로 투영한다.

두 표현의 결과는 모두 [20,40]이며 원본은 [1,2,3,4]다.

조건을 바꾸어 비교하기

같은 숫자 상수는 다른 의미가 된다

표의 첫 두 계획이 다른 이유를 원래 n의 조건으로 적어라.

  1. 첫 계획은 n>2다.

  2. 둘째는 2*n>2라 이 작은 정수 입력에서 n>1이다.

원래 2는 첫 계획에서 탈락하지만 둘째에서 4로 반환된다.

비교할 점

앞 본문의 문법 변환을 연산 재배치로 확대하지 않는다.

실패를 피하는 순서

새 [0,2]에서 0 제거 후 12/n과 12/n 먼저 수행을 비교하라.

  1. 안전한 계획은 0을 투영하지 않는다.

  2. 역순은 첫 투영에서 0으로 나눈다.

안전한 결과 [6]과 역순의 예외는 다른 관찰이다.

비교할 점

결과가 만들어지기 전의 실패도 등가성 조건에 포함한다.

소단원 9.2

filter·projection·group·join

이름을 고르는 일과 학년별로 모으는 일, 같은 번호끼리 붙이는 일은 어떻게 다를까?

준비 개념과 학습 목표

준비 개념

  • 필터와 투영

  • 키와 값

학습 목표

  • 네 연산의 입력과 결과 형태를 구별한다.

  • 중복 키 조인의 결과를 세어 본다.

조인 뒤 합계를 구하면 원래 금액 합계가 유지될까?

자체 주문 A는 키 1과 금액 10, B는 키 1과 금액 20, C는 키 2와 금액 7을 갖는다. 이름표 X와 Y는 각각 키 1이며 Z는 키 2다. Join의 모든 일치 쌍은 A/X, A/Y, B/X, B/Y, C/Z다. 쌍마다 주문 금액을 더하면 10 + 10 + 20 + 20 + 7 = 67이다. 원래 세 주문의 금액 합은 37로 이 결과와 다르다. 일치 행을 만들었다는 사실만으로 주문 하나당 한 번이라는 업무 계약이 유지되지 않는다.

그룹도 중복을 저절로 없애지 않는다. 조인 뒤 주문 키로 GroupBy하면 키 1의 요소는 네 개이며 합은 60이다. 키 2의 요소는 한 개이며 합은 7이다. 먼저 주문을 키별로 합산하면 키 1의 합은 30이고 키 2의 합은 7이다. 이 결과를 이름표와 조인해도 키 1의 합 30이 X와 Y에 각각 한 번씩 등장해 전체 합은 67이다. 선집계가 키 중복 정책을 대신하지 않는다.

원래 주문 총액이 필요하면 주문 자체를 합산하거나, 모든 쌍에서 주문 ID가 유지된 상태에서 각 ID를 정확히 한 번 세는 정책을 설계한다. 금액만 Distinct하면 A와 B의 금액이 우연히 같은 다른 입력에서 서로 다른 주문을 잃는다. 이 보강의 키/ID는 null 없는 고정 정수/이름이며 순차 LINQ to Objects의 기본 일치 규칙을 사용한다.

  • 일치하는 모든 쌍과 그룹

    중복 키의 쌍 수가 집계에 미치는 영향을 본다.

  • 투영에서 정보 유지

    주문 ID를 버리면 행 정체성을 복원하기 어렵다.

선별과 변환을 분리하기

Where는 개별 요소의 통과 여부를 정하고 Select는 남은 요소에서 필요한 값이나 새 객체를 만든다. 학생 객체에서 이름만 뽑으면 결과에는 학년 필드가 없을 수 있다. 뒤 연산에 필요한 키를 너무 일찍 버리지 않도록 연산 순서를 설계한다.

그룹은 키와 요소 묶음이다

GroupBy는 같은 키의 요소를 묶는다. 각 IGrouping은 Key와 열거 가능한 요소를 가진다. 그룹을 만들었다고 요소가 자동으로 하나의 합계가 되지는 않는다. 그룹별 Count나 Sum을 이어 계산한다.

조인은 일치하는 모든 짝을 만든다

Enumerable.Join은 키가 같은 양쪽 요소의 inner equijoin이다. 한쪽 키가 두 번이면 각각의 행이 상대의 일치 행과 짝을 이룬다. 일치하지 않는 행은 결과에 없으며 모든 학생을 보존하는 left join과 다르다. 이 예제의 키는 null 없는 정수다.

소단원 9.3

deferred execution·materialization

질의를 만들고 나서 목록에 수를 추가하면 어떤 결과가 바뀔까?

준비 개념과 학습 목표

준비 개념

  • IEnumerable

  • 목록과 반복

학습 목표

  • 지연 실행과 결과 저장의 시점을 추적한다.

  • 스트리밍과 전체 읽기가 필요한 연산을 구별한다.

Count로 미리 센 질의를 다시 읽으면 검사가 반복될까?

자체 q는 고정 [1,2,3]에 Where(P)를 적용한다. P는 호출할 때마다 해당 숫자를 로그에 넣고 짝수 여부를 반환한다. q.Count() 뒤 q.ToList()를 각각 정상 완료하면 두 열거에서 P를 세 번씩 호출하여 로그는 [1,2,3,1,2,3]이다. Count 결과 1과 목록 [2]가 같아 보여도 검사 효과는 반복되었다.

자료화한 saved=q.ToList()를 한 번 만든 뒤 saved.Count 속성과 saved 열거를 사용하면 원래 P는 한 번의 계산에서 세 번 호출된다. 이후 목록 소비는 P를 재실행하지 않는다. 이 사례는 Where 조건 호출을 세는 것이며 특정 컬렉션의 Count 최적화가 무조건 모든 입력을 열거한다는 일반 주장이 아니다. 저장 공간과 정수 결과 보존의 목적을 함께 고려한다.

첫 결과 한 개만 쓰는 계획도 앞 연산에 따라 전체 소비가 필요하다. 자체 자료 [(B,2),(A,1),(B,3),(A,4)]를 GroupBy(키).Take(1)하면 첫 그룹은 B이고 요소는 2,3이다. 그룹을 완성하려면 전체 네 입력을 읽는다. 반면 같은 자료의 Where(키==B).Take(1)은 첫 B 항목에서 결과를 만들 수 있다. 그룹 순서는 키 정렬이 아니라 키가 처음 나타난 순서다.

먼저 확인할 개념
  • 지연 질의와 저장한 결과

    반복 열거의 재계산과 정상 완료한 목록 재사용을 분리한다.

  • 그룹의 키와 모든 요소

    첫 그룹을 반환하기 전에 뒤의 같은 키 요소도 모아야 한다.

질의 변수는 결과 저장소가 아닐 수 있다

메모리 목록의 Where/Select는 보통 열거할 때 원본을 읽는 지연 질의다. 생성 시점과 실행 시점을 나누면 원본 갱신이 어느 결과에 영향을 주는지 설명할 수 있다. 반복 열거는 재계산과 부수 효과를 반복할 수 있어 비용과 일관성을 확인한다.

ToList는 그때의 요소를 저장한다

ToList나 ToArray는 질의를 열거해 새 컨테이너에 결과를 저장한다. 이후 원본의 구조 변경과 새 컨테이너는 분리되지만 요소가 가변 객체라면 참조 공유는 남을 수 있다. 깊은 복사나 원본의 영원한 불변성을 자동 보장하지 않는다.

지연과 스트리밍은 같은 말이 아니다

Where는 통과할 요소를 찾아 차례로 내보낼 수 있다. OrderBy나 GroupBy는 열거가 시작된 뒤 전체 자료를 읽어야 첫 결과를 만들 수 있다. 지연 질의라고 무한 입력을 안전하게 정렬하거나 메모리 부담 없이 그룹화할 수 있는 것은 아니다.

IEnumerable·IQueryable 차이 입문

조건식을 프로그램에서 실행하는 것과 다른 서비스에 질의로 전달하는 것은 같을까?

준비 개념과 학습 목표

준비 개념

  • 질의와 열거

  • lambda

학습 목표

  • 열거 계약과 provider 표현식 계약을 구별한다.

  • 번역과 데이터 이동의 범위를 설명한다.

로컬로 옮긴 조건은 수신량만 바꾸고 결과는 항상 같을까?

교육용 provider의 자체 이름 표는 ID 1의 ab, ID 2의 AB, ID 3의 aa다. 서버 문자열 일치는 대소문자를 구별하는 정확 비교이고, 로컬 조건은 OrdinalIgnoreCase로 ab와 비교한다고 명시한다. 서버에서 name==ab를 처리하면 ID 1만 남는다. 전체를 받은 뒤 로컬 조건을 적용하면 ID 1과 2가 남는다. 두 계획은 비교 의미부터 다르므로 단순 성능 비교의 같은 결과 전제를 만족하지 않는다.

AsEnumerable는 입력을 IEnumerable로 보게 하여 뒤 Enumerable 연산을 고르는 경계다. 호출 자체가 결과를 리스트에 저장하거나 SQL을 실행하는 단계는 아니다. 자체 provider가 ID<=2 조건을 번역할 수 있으면 그 조건은 앞에서 수행해 두 행을 받은 뒤 로컬의 대소문자 무시 비교를 할 수 있다. 결과 두 행은 같아도 전체 세 행을 받는 계획보다 전송 행 수가 줄었다.

행 수 외에 투영한 행 폭도 비용의 단위다. 별도 자체 provider는 고정 여섯 행에 대해 원격 ID 투영을 지원하며 전체 행은 1000바이트, ID 결과는 8바이트로 정의한다. 원격 투영은 6×8=48바이트, 전체 행을 받아 로컬 투영하면 6×1000=6000바이트다. 이는 프로토콜 헤더/압축/캐시 없는 손모형이다. 실제 SQL·네트워크 측정값이나 모든 provider의 최적화 보장이 아니다.

먼저 확인할 개념
  • provider와 연산 경계

    번역 능력뿐 아니라 문자열 비교 의미를 확인한다.

  • 연산의 요소 타입과 의미

    같은 질의 표면 문법이 실행 의미의 동일성을 자동 보장하지 않는다.

IEnumerable은 요소를 열거하는 계약이다

IEnumerable<T>는 요소를 차례로 얻는 인터페이스다. 자료가 이미 전부 메모리에 있다는 뜻은 아니며 파일이나 사용자 정의 iterator도 가능하다. Enumerable의 Where는 전달한 함수를 .NET 코드로 적용하는 연산이다.

IQueryable은 질의를 provider에 표현한다

IQueryable은 요소 타입·Expression·Provider를 제공하며 표준 Queryable 연산은 식 트리로 질의를 표현한다. 열거하면 provider가 이를 실행하며 SQL 번역 같은 방식은 provider별로 다르다. 지원하지 않는 C# 함수가 자동으로 다른 언어에 번역되는 것은 아니다.

경계를 옮기면 읽는 양이 달라진다

원격 필터를 번역해 실행하면 필요한 행만 받을 수 있지만 AsEnumerable 이후의 Enumerable 필터는 로컬 실행 경계를 만든다. AsEnumerable 호출 자체가 즉시 전체 자료를 저장하는 것은 아니다. IQueryable이라는 이름만으로 반드시 원격 DB나 빠른 실행을 보장하지 않는다.

중간 과정을 따라가는 예제

교육용 원격 provider의 표는 100 행이고 score>=60을 SQL로 번역할 수 있어 20 행이 맞는다. 필터가 원격에서 수행되는 A와, 먼저 전체 행을 열거해 로컬에서 필터하는 B의 수신량을 비교하라. 캐시·다른 최적화는 없다.

  1. A는 provider가 조건을 원격에 전달하므로 맞는 20 행을 수신한다.

  2. B는 원본 100 행을 수신한 뒤 로컬에서 20 행을 남긴다.

  3. 최종 20 행은 같아도 수신량 차이는 100−20=80 행이다.

A는 20 행, B는 100 행 수신이다. 특정 provider가 조건 번역을 지원한다는 가정이 필요하다.

다른 문제에 적용하기

가상 금액 보고서를 감사하라. 주문 A(키1,금액10), B(키1,금액20), C(키2,금액7)와 이름표 X(키1),Y(키1),Z(키2)를 쓰며 모든 입력은 고정이다. (1) 원래 금액>10을 Where한 뒤 두 배 투영하는 계획과 두 배 투영 후 >10 계획을 비교한다. (2) 원래 주문과 이름표의 Join 쌍 수/금액 합 및 주문 원장 합을 구한다. (3) 원래 주문에 Where(P)를 두되 P는 ID를 로그에 넣고 금액>10을 검사한다. 새 로그에서 q.Count() 뒤 q.ToList()의 P 호출 수와 한 번 자료화 뒤 재사용의 호출 수를 비교한다. (4) 별도 여섯 행 provider가 ID 원격 투영을 지원하며 전체 행 1000바이트/ID 8바이트다. 같은 ID 결과를 두 위치에서 투영할 때 전송량을 비교한다. 각 항목은 독립 초기 상태이고 실제 DB/서비스 실행은 없다.

힌트 1

질의의 요소가 원래 금액인지 투영 금액인지, 집계 단위가 주문인지 쌍인지 적는다.

힌트 2

결과 재사용과 질의 재실행을 분리하고 행 수와 행 폭을 함께 적는다.

풀이와 답 확인

  1. 원래 조건은 B만 남겨 [40]이다. 투영 먼저 하면 [20,40,14] 모두 >10을 만족한다. 조건의 의미가 다르다.

  2. 조인은 A/X,A/Y,B/X,B/Y,C/Z의 다섯 쌍이며 합은 67이다. 원래 주문 합은 37이다.

  3. Count는 P를 A,B,C에 한 번씩 적용해 결과 1이다. ToList도 같은 세 검사를 다시 수행해 [B]를 저장한다. 합계 P 호출은 6회다. 별도 한 번 자료화 경로는 P 호출 3회이며 저장 목록 재사용은 P를 다시 호출하지 않는다.

  4. 원격 ID 결과 전송은 6×8=48바이트다. 전체 행을 수신한 뒤 로컬 ID 투영은 6×1000=6000바이트다. 차이 5952바이트이며 실제 시간 배율은 추론하지 않는다.

두 목록 [40] 대 [20,40,14], Join 다섯 쌍/67 대 원장 37, P 호출 6회 대 자료화 3회, 수신 48바이트 대 6000바이트를 각각 다른 계약/단위로 설명한다.

해결한 뒤 점검할 것

  • 원래 조건과 투영 조건의 의미를 같은 것으로 취급하지 않는다.

  • 쌍 수/금액 합/주문 ID 원장을 분리한다.

  • 반복 P 효과와 저장 결과의 재사용을 구별한다.

  • 지원 provider의 고정 바이트 모형과 실측 시간·학생 미수행을 구별한다.
