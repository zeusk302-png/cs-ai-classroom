소단원 2.1

value·reference type

struct를 복사했는데 왜 그 안의 배열을 바꾸면 원본에서도 바뀔까?

준비 개념과 학습 목표

준비 개념

  • 변수는 현재 값을 저장하는 장소다. 대입은 기본적으로 그 값을 복사하며 원래 장소의 이름을 복사하는 것이 아니다.

  • struct는 여러 필드를 한 값으로 묶는 값 타입이고 class와 배열은 참조 타입이다. Packet의 Number는 int, Data는 int[]로 서로 다른 종류의 필드다.

  • 종이에서는 struct 상자를 두 개 그리고 배열은 별도 상자로 만든다. 배열 필드는 배열 객체 자체가 아니라 참조값을 가진다.

학습 목표

  • 값 타입 복사와 참조 타입 참조 복사를 설명한다.

  • 참조 필드를 가진 struct의 얕은 복사를 추적한다.

  • 값/참조 타입을 물리 stack/heap 배치와 동일시하지 않는다.

구조체를 함수에 복사해 넘겼는데 배열만 바뀌었다면 반환을 빠뜨린 것일까?

새 구조체 Sample은 int Stamp와 int[] Data를 가진다. a의 Stamp는 1이고 Data는 배열 A=[2,3]을 가리킨다. 함수 Edit(Sample p)는 ref 없이 값을 받고 p.Stamp=9, p.Data[0]=7, p.Data=new int[]{8,9}를 차례로 수행한 뒤 p를 반환한다. 호출자는 처음에 Edit(a)의 반환을 버린다고 가정한다. 숫자 필드는 복사된 p에서 바뀌지만 처음 배열 칸은 a와 p가 함께 가리킨다.

따라서 함수가 끝난 뒤 a의 Stamp는 1이고 a.Data는 [7,3]이다. p의 마지막 배열 B=[8,9]는 반환을 보관했다면 그 반환값의 필드로 접근할 수 있었지만 a의 필드로 자동 설치되지는 않는다. 이 그림은 ref 매개변수, 예외, 동시 변경을 사용하지 않는 정상 실행 의미의 손추적이며 실제 C# 호출이나 할당 관찰은 아니다.

새 초기 상태에서 Sample c=Edit(a)로 반환을 보관하면 a의 Stamp는 1, c의 Stamp는 9이며 배열은 a가 A=[7,3], c가 B=[8,9]를 가리킨다. 같은 함수에서 생긴 공유 변경과 마지막 참조 분리를 동시에 표시해야 한다. 반환을 저장했다고 이전에 바뀐 A의 첫 칸이 되돌아가는 것은 아니다.

원본 숫자와 배열 내용을 보존하는 변환이 목적이라면 p.Data의 참조를 새 배열 복사로 먼저 바꾼 뒤 칸을 수정하고 반환해야 한다. 이 int[]에서는 칸의 int 값 복사가 충분하지만 참조 원소의 배열에는 더 깊은 객체 범위 계약이 남는다. 값 타입이라는 분류만으로 모든 변경이 호출자에게 보이지 않는다고 단정하지 않는다.

    매개변수의 숫자 값과 배열 참조값을 따로 그린다.

  • boxing의 복사 시점

타입과 대입의 의미

본문은 C# 12/.NET 8 예제다. int·bool과 사용자 struct 등은 값 타입이고 class·string·배열 등은 참조 타입이다. 값 타입 변수의 일반 대입은 값을 복사하며 참조 타입 변수의 일반 대입은 객체를 가리키는 참조값을 복사한다. 여기서는 ref/out 별칭 매개변수를 사용하지 않는다.

값 타입이라는 사실만으로 모든 값이 stack에만 있다는 결론은 나오지 않는다. 객체의 필드·배열 칸·boxed 값 등 저장 맥락이 다르다. 타입의 논리적 복사 규칙을 실행기 구현의 특정 메모리 배치나 성능 측정으로 바꾸어 말하지 않는다.

구조체 복사는 재귀적 깊은 복사가 아니다

Packet a를 b에 복사하면 Number 값과 Data 참조값을 각각 복사한다. b.Number=9는 a.Number를 바꾸지 않지만 b.Data[0]=8은 공통 배열 객체를 바꾸므로 a.Data[0]도 8이다. 구조체가 참조 필드를 가질 수 있음을 반드시 포함해야 “값 타입은 독립된 복사”라는 설명의 범위가 정확해진다.

b.Data=new int[]{2}는 b 내부 참조 필드만 재대입한다. a.Data는 원래 배열을 계속 가리킨다. 따라서 공유 객체 변경과 구조체 내부 필드 변경을 서로 다른 단계로 그린다. 깊은 복사가 필요하면 어떤 객체까지 새로 만들지 별도 계약과 구현이 필요하다.

using System;
struct Packet { public int Number; public int[] Data; }
class Program {
 static void Main() {
  Packet a=new Packet { Number=3, Data=new int[]{4} };
  Packet b=a; b.Number=9; b.Data[0]=8;
  Console.WriteLine($"{a.Number} {b.Number} {a.Data[0]} {b.Data[0]}");
  b.Data=new int[]{2};
  Console.WriteLine($"{a.Data[0]} {b.Data[0]}");
 }
}

같은 문법을 다른 언어 규칙으로 읽지 않는다

C#에는 struct 같은 사용자 값 타입이 있지만 Java의 일반 클래스 변수는 참조값을 가진다. 언어마다 타입/표현의 범위가 다르므로 Java에서 만든 메모리 그림을 이름만 바꿔 C#에 적용하면 struct 복사 부분을 놓친다. 본문 비교는 이 작은 예제의 규칙이며 모든 플랫폼 타입을 두 언어에서 완전히 대응시키지 않는다.

복사가 싸다는 일반 성능 결론도 나오지 않는다. 큰 struct 복사는 작업량이 클 수 있고 참조를 공유하면 동시 변경 계약이 필요하다. 값/참조 선택은 의미와 수명, 관찰 가능한 변경 요구를 먼저 정하고 실제 환경의 측정은 별도로 한다.

정상 Edit 호출에서 처음 공유한 배열과 마지막 새 배열
조건 또는 사건복사하거나 읽은 대상관찰 가능한 결과

함수 진입

a와 p의 Stamp는 각각 1 / 둘 다 A를 참조

A의 내용은 [2,3]

p.Stamp=9

p의 숫자 필드만 변경

a의 Stamp는 1, p의 Stamp는 9

p.Data[0]=7

공통 배열 A의 칸 변경

a와 p를 통해 읽는 A는 [7,3]

p.Data를 B로 재대입

p의 참조 필드만 B로 변경

a는 A=[7,3], p는 B=[8,9]

행은 한 호출의 순서다. 함수 매개변수 p는 별도의 구조체 값이고 A/B는 서로 다른 배열 객체의 이름이다. 새 배열이 생성되었다는 의미를 실제 주소나 GC 수집 시각으로 바꾸지 않는다.

조건을 바꾸어 비교하기

반환을 버려도 공유 칸 변경은 남는다

새 a에서 Edit(a)의 반환을 버린 뒤 a의 두 필드를 예측하라.

  1. p.Stamp 변경은 복사본에만 남는다.

  2. A의 첫 칸은 공유 상태에서 7로 바뀐다.

  3. 마지막 p.Data 재대입은 a.Data를 바꾸지 않는다.

a의 Stamp는 1이고 Data는 [7,3]이다.

비교할 점

값 반환의 저장 여부와 공유 객체 변경 여부를 따로 본다.

반환을 저장해 두 배열을 분리한다

독립적인 새 a에서 c=Edit(a)를 수행한 뒤 c.Data[1]=0을 수행하라.

  1. Edit 결과 c는 Stamp 9와 B=[8,9]를 가진다.

  2. c.Data[1] 변경 뒤 B는 [8,0]이다.

  3. a는 A=[7,3]을 계속 가리킨다.

a는 Stamp 1 / 배열 [7,3], c는 Stamp 9 / 배열 [8,0]이다.

비교할 점

반환의 새 참조 분리 이후 변경은 옛 배열로 전파되지 않는다.

종이와 본문으로 직접 해보기

a.Number=1, a.Data→{5}, b=a 뒤 b.Number=2와 b.Data[0]=6을 수행하면 a/b의 Number와 Data[0]는?

힌트 보기

Number는 두 상자, Data 화살표는 한 배열로 그린다.

풀이 보기

Number는 a는 1, b는 2, Data[0]는 a는 6, b는 6이다. 복사된 참조값들이 같은 배열 칸을 가리키기 때문이다.

오해와 반례

값 타입 복사는 모든 내부 객체의 깊은 복사다.

Packet의 Data 배열 공유가 반례다. 참조 필드의 값만 복사되므로 구조체의 숫자 필드와 내부 배열의 변경 효과가 다르다.

소단원 2.2

boxing·conversion

object에 담긴 int를 바로 long으로 꺼내면, 값 7이 long 범위 안인데도 왜 실패할까?

준비 개념과 학습 목표

준비 개념

  • object 변수는 객체 참조를 저장한다. 값 타입을 넣을 때 boxing으로 값의 복사본을 감싼다.

  • int와 long은 서로 다른 값 타입이다. 숫자 변환과 boxed 값의 타입 검사는 다른 작업이다.

  • C# byte는 0..255의 부호 없는 8비트 값이며 Java byte의 −128..127과 다르다.

학습 목표

  • boxing 복사와 원래 변수 변경을 추적한다.

  • 정확한 unboxing 후 숫자 변환을 수행한다.

  • checked/unchecked 정수 축소 조건을 비교한다.

checked로 함수 호출을 감싸면 함수 몸체의 축소도 검사될까?

새 helper Wrap(int n)은 몸체에 return unchecked((byte)n);을 명시한다. 입력 변수 n=258을 checked(Wrap(n))에 넘겨도 몸체의 unchecked 변환은 258 mod 256인 2를 반환한다. 호출을 둘러싼 checked가 별도 함수 몸체로 전파되는 계약은 아니다. CheckedWrap(int n)은 return checked((byte)n);을 명시하므로 같은 입력에서는 OverflowException이다.

checked(Wrap(n+int.MaxValue))에서는 다르다. n=1인 독립 입력이면 인수 식의 덧셈이 checked 괄호 안에서 평가되어 helper에 진입하기 전에 OverflowException이 발생한다. 호출 인수의 식과 함수 몸체의 변환을 다른 위치로 표시해야 실패 시점을 맞힐 수 있다. 여기서는 내장 정수 연산만 사용하고 모든 입력은 변수이며 새 코드는 실제 실행하지 않았다.

object o=(short)258이라는 별도 입력에서는 checked((byte)(int)o)가 범위 검사를 시작하기 전에 boxed short를 int로 꺼내려다 InvalidCastException을 낸다. checked((byte)(short)o)는 정확한 타입을 꺼낸 다음 byte 범위를 검사하므로 OverflowException이다. 작은 값 12를 short로 boxing한 새 입력이면 후자는 12를 반환한다. 같은 실패라는 이름으로 두 단계의 원인을 합치지 않는다.

기록할 결과는 성공 값 또는 실패 단계다. 실패를 모두 0으로 바꾸면 정상 byte 값 0과 구별하지 못한다. unchecked 축소는 상한 검증을 한 것도 아니며 잘못된 업무 수량 258을 작은 수 2로 숨길 수 있다. 허용 범위와 변환 정책을 먼저 정한다.

먼저 확인할 개념
  • unboxing과 정수 축소

    정확한 기저 타입 확인과 byte 범위 검사를 순서대로 적용한다.

  • 식의 평가 순서와 효과

    함수 진입 전에 인수 식이 실패하는 경우를 구별한다.

boxed 값은 별도의 복사본

int x=7;object box=x;는 7의 boxed 복사본을 만들고 box에 참조를 넣는다. x=9로 바꿔도 boxed 값은 7이다. (int)box는 정확한 boxed int인지 확인하고 int 값을 꺼낸다. unboxing은 원래 변수x의 별칭을 되살리는 작업이 아니다.

(long)box는 boxed int를 boxed long인 것처럼 꺼내려 하므로 InvalidCastException이다. (long)(int)box는 먼저 int 값 7을 꺼낸 뒤 long 값 7로 숫자 변환하여 성공한다. null 객체를 nonnullable 값으로 꺼내면 NullReferenceException이다. nullable boxing은 뒤 절의 별도 규칙이다.

변환에서 범위를 확인한다

int→long은 모든 int 값을 보존하지만 int→float 같은 암시적 변환은 정밀도를 잃을 수 있다. 명시적 cast가 있다는 사실은 범위와 의미를 검증했다는 증거가 아니다. 값 보존 요구라면 입력 범위와 해당 숫자 타입의 표현을 따로 확인한다.

int n=260을 byte로 바꿀 때 unchecked는 높은 비트를 버려 4가 된다. checked는 260이 0..255 밖이라 OverflowException이다. 본문은 문맥을 명시하여 프로젝트 기본 overflow 설정에 의존하지 않는다. 실수→정수 범위 밖 unchecked 결과를 이 낮은 비트 규칙과 동일시하지 않는다.

using System;
class Program {
 static void Main() {
  int x=7; object box=x; x=9;
  Console.WriteLine($"{x} {(int)box}");
  try { long bad=(long)box; Console.WriteLine(bad); }
  catch(InvalidCastException) { Console.WriteLine("wrong-unboxing"); }
  Console.WriteLine((long)(int)box);
  int n=260;
  Console.WriteLine(unchecked((byte)n));
  try { Console.WriteLine(checked((byte)n)); }
  catch(OverflowException) { Console.WriteLine("overflow"); }
 }
}

상수와 런타임 및 평가 위치

byte b=7;은 범위 안 int 상수의 특별 대입 규칙으로 허용되지만 int n=7;byte b=n;은 암시적 int→byte 변환이 없어 그대로 허용되지 않는다. checked 상수 표현식의 범위 초과는 컴파일 오류, 변수로 계산하는 checked 범위 초과는 런타임 예외일 수 있다.

checked라는 이름으로 함수 호출을 감싼다고 함수 몸체 안의 모든 정수 연산까지 자동 checked로 바뀌는 것은 아니다. 평가되는 코드의 문맥을 명시해야 한다. 본문은 built-in int/byte 연산만 사용하며 사용자 변환/연산자 정의는 별도 계약으로 남긴다.

operator·flow control

x++ + x++는 C#에서도 C처럼 출력을 정할 수 없을까?

준비 개념과 학습 목표

준비 개념

  • 후위 x++는 기존 값을 식의 결과로 내고 x를 1 증가시킨다. 전위 ++x는 증가 후 값을 낸다.

  • 우선순위는 식의 결합 구조, 피연산자 평가 순서는 값과 부작용이 발생하는 순서다. 같은 개념이 아니다.

  • 배열 Length는 칸 수이고 유효 인덱스는 0..Length−1이다. bool 조건은 true/false다.

학습 목표

  • C# 피연산자 순서와 후위 증가를 추적한다.

  • 조건부 논리와 반복 제어의 실행 순서를 설명한다.

  • 부분합 불변량과 종료 조건의 범위를 명시한다.

최종 bool 값이 같아도 검사 함수의 호출 수가 다르면 같은 제어인가?

새 Probe(string name,bool value)는 외부의 관찰 목록에 name을 추가하고 value를 반환한다고 정의한다. 목록 쓰기는 성공하고 예외나 동시 변경은 없다. 각 식은 빈 목록에서 독립적으로 시작한다. Probe("A",false) && Probe("B",true)는 false와 목록 [A]를 만들지만 같은 식의 & 변형은 false와 목록 [A,B]를 만든다. 반환값 하나만 비교하면 오른쪽 효과의 차이가 가려진다.

또 다른 독립 식 Probe("A",true) || Probe("B",false) && Probe("C",false)는 &&가 더 강하게 결합하지만 A가 true이므로 오른쪽 전체를 건너뛴다. 결과는 true, 목록은 [A]다. (Probe("A",true) || Probe("B",false)) && Probe("C",false)는 A 뒤 B를 생략하지만 C를 호출해 false, 목록 [A,C]다. 괄호는 구조를 정하고 각 조건부 연산은 필요한 경로만 평가한다.

반복에서도 값과 효과의 위치를 함께 적는다. 새 배열 [2,−1,5]를 for로 순회하면서 음수면 continue하고 나머지는 더한 뒤 채택 개수를 증가시키면 합은 7, 채택 수는 2다. continue 전에 방문 수를 증가시키면 방문 수는 3이다. for의 갱신은 continue 이후에도 실행되므로 다음 인덱스로 이동한다. 방문 수와 채택 수를 같은 분모로 읽지 않는다.

동일 입력에서 while의 갱신을 본문 마지막에만 두고 음수에서 continue하면 인덱스 1이 바뀌지 않아 종료하지 않을 수 있다. 이 종료 실패는 실제 무한 루프를 실행하여 확인할 필요가 없는 상태 반례다. 작은 합의 계산은 범위 안이며 일반화할 때는 int overflow 정책, 배열 변경, 검사 효과의 실패도 따로 정한다.

먼저 확인할 개념
  • 조건부 평가와 반복 갱신

    bool 값과 실제 평가 경로 및 for의 continue 후 갱신을 나눈다.

  • 실패하는 식의 위치

    건너뛴 식은 실패와 부작용도 발생시키지 않는다는 범위를 적용한다.

결합 구조와 평가 순서

C# built-in 연산의 피연산자는 왼쪽부터 평가한다. x=1에서 x++ + x++는 왼쪽 값 1/상태 2, 오른쪽 값 2/상태 3을 만들고 합 3이다. C의 unsequenced 수정 UB 규칙을 C#에 그대로 적용할 수 없다. 규칙이 정의되어도 읽기 쉬운 코드는 부작용을 별도 문장으로 나누는 편이 낫다.

2+3*4의 구조는 2+(3*4)이지만 우선순위가 왼쪽 피연산자를 언제 관찰하는지의 규칙을 대체하지 않는다. 조건부 &&/||는 필요 없으면 오른쪽을 생략한다. bool &/|는 두 쪽을 평가한다. 사용자 정의 연산자나 다른 타입을 논할 때는 그 별도 정의까지 확인한다.

반복과 배열 경계를 함께 읽는다

for 초기화는 1회이고 매회 조건→본문→갱신이 이어진다. C# 12의 continue는 가장 안쪽의 대상 반복에서 현재 본문 나머지를 건너뛰고 for라면 갱신으로 가며 break는 해당 반복을 나간다. foreach는 요소 값을 차례로 읽으며 일반적인 value 반복변수를 바꾸어 배열 칸을 수정하는 것으로 생각하지 않는다.

Flow는 음수를 continue하여 {3,−2,4}에서 3+4를 더한다. absent!=null && absent.Length>0은 null일 때 길이 접근을 건너뛴다. 빈 배열은 존재하는 객체로 0회 반복이고 null은 객체 부재라 접근 규칙이 다르다. 이 null 참조 문법은 Nullable enable인 C# 12 프로젝트에서 사용한다.

using System;
class Program {
 static void Main() {
  int x=1; int z=x++ + x++;
  Console.WriteLine($"{z} {x}");
  int[] a={3,-2,4}; int sum=0;
  for(int i=0;i<a.Length;i++) {
   if(a[i]<0) continue;
   sum+=a[i];
  }
  Console.WriteLine(sum);
  int[]? absent=null;
  Console.WriteLine(absent!=null && absent.Length>0);
 }
}

합 계산의 증명과 한계

반복 시작에 sum은 이미 본 칸들의 음수가 아닌 합이다. 처음 빈 합 0, 음수면 보존, 아니면 현재값을 더하므로 i 증가 후에도 맞는다. Length−i가 감소하여 종료하면 전체 합이 된다. 이 설명은 고정 배열·정상 본문 종료·합이 int 범위 안이라는 조건에서 수학 합을 논한다.

checked/unchecked는 정수 overflow의 처리도 바꾸므로 매우 큰 합이 항상 수학 합이라고 말할 수 없다. 본문 작은 배열은 안전하지만 일반 API의 원소 상한·길이·합 범위를 따로 계약해야 한다. 예외·동시 변경·취소 정책은 이 작은 코드의 실제 실행으로 검증되지 않는다.

소단원 2.4

null과 nullable value

int?의 null과 0은 어떻게 다르고 string?의 물음표도 같은 구조를 만들까?

준비 개념과 학습 목표

준비 개념

  • 일반 int는 0을 가질 수 있지만null을 직접 담을 수 없다. “없음”을 0과 구분해야 할 때 다른 표현이 필요하다.

  • 참조형 string의 null은 객체 부재이며 빈 문자열과 다르다. string?는 nullable 참조 분석을 위한 표기다.

  • a ?? b는 a가null일 때만 b로 대체한다. a?.Length는null에서 직접 역참조하지 않고 부재 결과를 낸다.

학습 목표

  • Nullable<T>의 HasValue/Value와 null을 설명한다.

  • nullable 값의 boxing 및 대체값을 추적한다.

  • nullable 참조 주석의 정적 분석과 런타임 안전을 구별한다.

부재를 0이나 false로 먼저 바꾸면 어떤 판정이 사라질까?

새 세 상태의 입력 수량 n은 int?이며 null, 0, 2를 구별한다. n??0은 앞의 null과 실제 0을 모두 0으로 바꾼다. 수량 합계만 필요하면 이 정책을 택할 수 있지만 미입력 경고를 유지해야 한다면 정보가 사라진다. 형식 오류까지 있는 업무라면 missing/invalid/valid 상태를 Nullable 하나로 모두 표현하지 않는다.

object? o=n으로 boxing한 결과는 n이 null이면 null 참조이고 n이 0이나 2면 boxed int다. 따라서 (int?)o로 되돌리는 것은 boxed int 또는 null이라는 입력에서 허용되지만 (long?)o로 같은 숫자를 확대하려는 것은 boxed int 입력에서 타입 불일치다. 먼저 int?로 꺼낸 뒤 long?으로 숫자 변환하는 순서를 써야 한다. 부재는 이 변환에서도 부재로 남는다.

별도의 bool? 승인 값 p는 true, false, null 중 하나다. p & false는 모든 입력에서 false이고 p | true는 모든 입력에서 true다. null과 true의 &는 null이며 null과 false의 |도 null이다. 이 연산은 bool?의 3값 규칙이며 &&와 ||는 bool? 피연산자를 직접 지원하지 않는다. null을 false로 바꾼 bool 연산은 정책 변경이지 항상 같은 관찰이 아니다.

보강의 승인 정책은 p==true일 때만 승인하고 null은 보류, false는 거절로 표시한다. 모두 bool 하나로 줄이면 보류와 거절이 합쳐진다. 별도 int? a=null, b=2에서 a<b도 a>=b도 false이므로 첫 관계를 부정한 true가 둘째 관계와 같다고 하지 않는다. Nullable 비교의 규칙을 보통 정수의 모든 경우 구분과 혼합하지 않는다.

먼저 확인할 개념
  • 부재와 실제 0

    정보를 합치는 대체값 정책의 범위를 확인한다.

  • 정확한 타입의 unboxing

    nullable boxing의 기저 타입과 후속 숫자 변환을 분리한다.

값 타입에 부재를 더한다

int?는 System.Nullable<int>라는 값 타입으로 모든 int 값과 부재를 표현한다. n=null이면 HasValue는 false이고, n=0이면 HasValue는 true, Value는 0이다. 따라서 0을 없는 값처럼 임의 처리하면 원자료의 의미를 잃는다. HasValue가 false일 때 Value를 읽으면 InvalidOperationException이다.

n ?? 5는 부재면 5, 값 0이 있으면 0을 준다. nullable 값의 default도 부재다. 하지만 지역 변수 int? n;을 대입 없이 읽어도 된다는 뜻은 아니다. 필드와 배열 칸의 default, 지역 변수의 확정 대입은 다른 규칙이다. 이 예제는 n=null로 명시적으로 대입한다.

boxing과 비교의 특별 규칙

nullable 값을 object로 boxing하면 부재일 때는 null 참조, 값이 있을 때는 기저 타입 T의 값을 boxing한다. int? a=null; object? box=a;의 box==null은 true다. 값이 7이면 boxed Nullable<int> 객체를 일반적으로 찾는 것이 아니라 boxed int 값이라는 규칙을 사용한다.

nullable int의 관계 비교 <,>,<=,>=는 어느 쪽이 null이면 false다. 따라서 !(a<b)가 항상 a>=b와 같지는 않다. ==는 양쪽 null이면 true라는 별도 규칙이다. bool?의 &와 |도 일반 nullable 산술의 null 전파와 다른 3값 규칙이므로 모든 연산을 한 규칙으로 일반화하지 않는다. 이 비교와 논리식은 본문 코드와 별도의 종이 조건이다.

using System;
class Program {
 static void Main() {
  int? n=null;
  Console.WriteLine($"{n.HasValue} {n ?? 5}");
  n=0;
  Console.WriteLine($"{n.HasValue} {n.Value}");
  int? a=null; object? box=a;
  Console.WriteLine(box==null);
  string? text=null;
  Console.WriteLine(text?.Length ?? -1);
  try { int bad=a.Value; Console.WriteLine(bad); }
  catch(InvalidOperationException) { Console.WriteLine("no-value"); }
 }
}

참조형의 물음표는 같은 wrapper가 아니다

Nullable enable에서 string?는 null 가능성을 표시해 흐름 분석 경고를 돕지만 System.Nullable<string>을 만드는 것은 아니다. 참조형 주석은 기존 런타임 타입을 새 별개 타입으로 바꾸거나 null을 자동 차단하지 않는다. 변수 뒤의 !도 경고를 억제할 뿐 객체를 만들거나 검사하지 않는다.

text?.Length ?? -1은 text가 없으면 −1, 존재하면 길이다. −1을 부재 기호로 쓸지, 허용하지 않을지는 API 계약으로 정한다. 컴파일 경고 없음·실행 성공·도메인 제약 충족은 서로 다른 증거다. 예제는 실패를 보이려고 a.Value를 읽어 CS8629 경고와 실제 예외를 함께 기록한다.

논리 값뿐 아니라 Probe 호출 목록을 적는다. nullable 값을 대체하기 전 존재 여부와 승인 세 상태를 분류한다.

풀이와 답 확인

  1. ① a는 Stamp 1과 A=[7,3], c는 Stamp 9와 B=[8,0]이다. 원본 보존형은 배열 칸을 바꾸기 전에 int[]를 복제해 참조를 분리한다.

  2. ② checked(Wrap(258))은 2, CheckedWrap(258)은 OverflowException이다. boxed short를 int로 꺼내는 식은 InvalidCastException, short로 먼저 꺼내는 식은 byte 범위에서 OverflowException이다.

  3. ③ 첫 논리식은 true와 [A], 괄호를 바꾼 식은 false와 [A,C]다. 반복의 방문은 3회, 채택은 2회, 합은 7이다.

  4. ④ 두 수량의 대체 숫자는 모두 0이지만 boxing은 null 참조와 boxed int 0으로 다르다. nullable OR는 null, 대체 이후 bool OR는 false다. HasValue와 true/false/null 판정으로 원래 상태를 보존한다.

구조체 복사에도 최초 공유 배열 변경은 남는다. checked 이름보다 실제 변환 위치와 boxed 타입을 확인한다. 효과 목록과 방문/채택 분모를 구별하고 대체값 이전의 부재 정보를 보존한다. 실제 C#·CLR·학생 실험은 미수행이다.
