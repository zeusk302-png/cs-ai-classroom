동시에 시작할 수 있다는 말에 작업 개수 제한도 포함될까?

앞 본문은 독립인 두 대기를 먼저 시작하면 가상 종료 시각이 두 시간의 합이 아니라 큰 값이 된다고 설명했다. 새 입력은 A, B, C, D 네 작업이며 각각 시작 뒤 8, 3, 5, 2밀리초에 끝난다. 작업끼리 독립이고 시작/완료 처리 비용은 0이며 외부 자원이 충분하다는 자체 시간 모형이다. 모든 작업을 시각 0에 시작하면 마지막 A가 끝나는 시각 8에 전체가 완료된다. 이때 살아 있는 작업은 네 개까지 늘어난다.

외부 연결은 최대 두 개만 허용한다는 새 요구에서는 같은 시작 전략이 허용되지 않는다. 자체 FIFO 규약은 남은 작업을 A, B, C, D 순서로 선택하고 작업이 끝날 때 빈 슬롯에 다음 작업을 넣는다. 시각 0에 A와 B, 시각 3에 B가 끝난 자리에서 C, 시각 8에 A와 C가 끝난 뒤 D가 시작한다. 전체는 시각 10에 끝나며 활성 작업 수는 2 이하이다. 시각 8의 두 완료를 모두 처리한 뒤 새 시작을 기록한다는 사건 규약도 고정한다.

제한 1에서는 네 시간이 합쳐져 18밀리초이고 제한 없는 경우는 8밀리초다. 제한 2의 10밀리초를 실제 서버 성능이나 모든 입력의 최적 스케줄이라고 주장하지 않는다. 요구한 자원 상한을 만족하는 특정 일정의 계산이다. Task.WhenAll은 이미 얻은 Task들의 종료를 함께 관찰할 뿐, 자체 FIFO나 연결 개수 제한을 자동으로 설계하지 않는다.

기다림과 계산을 나누기

비동기는 오래 걸리는 작업의 완료를 기다리는 동안 호출자가 다른 일을 이어 갈 수 있게 하는 흐름이다. 병렬은 같은 시점에 여러 계산이 실제로 실행되는 상태다. 파일이나 네트워크의 완료를 기다리는 비동기 흐름이 반드시 여러 CPU에서 계산한다는 뜻은 아니다.

Task는 앞으로 완료될 작업의 상태를 표현한다. Task<T>는 완료하면 T형 결과를 제공한다. async 표시는 메서드에서 await를 사용할 수 있게 하지만 새 스레드를 자동으로 만들지 않는다. CPU 계산을 분리하는 Task.Run과 장치의 비동기 API는 목적을 구별해야 한다.

먼저 시작할지 먼저 기다릴지

await A(); await B();는 A 호출의 완료를 기다린 다음 B를 호출한다. 반면 var a = A(); var b = B(); 뒤에 두 작업을 기다리면 A와 B가 먼저 호출된다. 이때 두 API가 실제 작업을 시작하며 서로 독립이라는 조건에서 대기 시간이 겹칠 수 있다.

작업을 무조건 많이 시작하면 서버나 메모리 한도를 넘을 수 있다. 비동기라는 이름만으로 처리량 향상이나 응답 시간 감소를 보장하지 않는다. 작업 수, 의존 관계와 외부 자원의 용량을 먼저 적는다.

두 작업의 완료를 묶기

Task.WhenAll(a, b)는 주어진 작업들이 모두 끝나는 것을 나타내는 Task를 반환한다. 호출 자체가 현재 스레드를 끝까지 붙잡는 대기는 아니며, 반환된 Task를 await해 완료를 관찰한다.

이미 시작한 두 작업이라면 await a 뒤에 await b를 해도 b의 시작이 뒤로 밀리지 않는다. 다만 오류 관찰과 종료 관리까지 포함한 설계에서는 모든 작업의 완료를 명시적으로 묶는 편이 이해하기 쉽다.

시간은 가상 밀리초다. 같은 작업의 시작과 종료 사이를 활성 기간으로 세고 종료된 작업은 새 시작 전에 제거한다. 무제한 8과 FIFO 두 슬롯 10은 서로 다른 자원 조건이다.

중간 과정을 따라가는 예제

가상 다운로드 A는 6 ms, B는 4 ms다. 시작 비용은 0이고 두 작업은 독립이며 동시에 진행할 외부 용량이 있다. 세 가지 호출 순서를 비교하라.

  1. A를 호출하고 완료 후 B를 호출하면 A는 0–6 ms, B는 6–10 ms다.

  2. A와 B를 모두 0 ms에 시작하면 각각 6 ms와 4 ms에 끝난다. WhenAll 완료는 6 ms다.

  3. 두 작업을 0 ms에 먼저 시작한 뒤 a를 await하면 6 ms에 돌아온다. b는 이미 완료되어 다음 await도 6 ms에 끝난다.

직렬 호출은 10 ms, 먼저 시작한 두 흐름은 이 가정에서 6 ms다. CPU 병렬 실행의 증거는 아니다.

첫 await 앞의 일도 이미 다른 호출과 겹치는가?

async 메서드를 호출하면 첫 미완료 await까지의 동기 구간은 호출 과정에서 진행된다. 새 자체 F는 호출 시 2밀리초의 CPU 준비를 한 뒤 I/O를 시작하고 기다린다. 같은 호출 스레드에서 A용 F를 먼저 호출하고 반환된 Task를 저장한 뒤 B용 F를 호출한다. A의 I/O 대기는 시작 뒤 6밀리초, B의 대기는 시작 뒤 4밀리초이며 둘 다 실제로 미완료 await를 만난다고 가정한다.

A 준비는 시각 0부터 2까지이며 I/O는 2부터 8까지다. A 호출이 미완료 Task를 반환한 뒤 B 준비는 2부터 4까지이고 B의 I/O는 4부터 8까지다. 두 I/O가 겹치지만 전체는 시각 8에 끝난다. I/O 대기 숫자 6과 4의 큰 값만 사용한 6밀리초는 동기 준비를 제외한 다른 모형이다. 이 표는 특정 CPU를 측정한 결과가 아니다.

await 대상이 이미 완료한 경우에는 그 위치에서 호출자에게 반드시 돌아가는 것이 아니다. 새 함수가 L을 기록하고 이미 완료한 Task를 await한 뒤 R을 기록하고 반환하면, 호출자는 그 뒤 C를 기록하여 L,R,C 순서가 된다. 별도 미완료 대상에서 지정한 사건 순서는 L,C,R이다. 어느 실제 스레드에서 R이 실행되는지는 이 로그만으로 판정하지 않는다.

지역 변수가 있어도 참조 대상까지 snapshot이 되는 것은 아니다. 새 단일 사건 모형에서 시작 값이 4인 box를 읽어 정수 saved에 저장하고, await 대기 중 다른 사건이 box 값을 9로 바꾼다. 재개 뒤 saved는 4이고 같은 box에서 다시 읽은 값은 9다. 이는 데이터 경쟁을 실제로 시험한 결과가 아니라 명시한 순차 사건의 별칭과 값 복사 차이다.

미완료이면 이어 할 일을 남기기

await 대상이 아직 완료되지 않았다면 비동기 메서드는 그 뒤에 이어 할 일을 등록하고 호출자에게 제어를 돌려줄 수 있다. 이 이어 할 흐름을 continuation이라고 부른다. 필요한 지역 변수와 진행 상태는 이어 실행할 수 있게 보존된다.

메서드의 최초 부분은 호출한 흐름에서 시작하며, 처음 만난 미완료 await까지 동기적으로 진행할 수 있다. async 메서드를 호출했다는 이유만으로 첫 문장부터 별도 스레드에 간다고 생각하면 로그 순서를 잘못 예측한다.

이미 끝났다면 바로 이어 가기

await 대상이 이미 완료되었다면 완료 결과를 꺼내 다음 문장으로 진행할 수 있다. 모든 await가 반드시 일시 중단을 만들지는 않는다. Task<int>를 정상적으로 await한 표현식의 값은 int 결과다.

이어 실행되는 스레드와 문맥은 호출 환경 및 설정에 영향을 받는다. 여기서는 특정 UI 스레드 복귀나 새 스레드 사용을 가정하지 않고, 완료 이전과 이후의 제어 흐름만 추적한다.

중단은 종료가 아니다

try 안의 await에서 대기한다고 해서 finally가 곧바로 실행되지는 않는다. 메서드가 그 try 범위를 실제로 나가거나 예외·취소로 빠져나갈 때 finally가 실행된다. 대기 중에도 아직 사용하는 자원을 일찍 해제해서는 안 된다.

동기적인 .Result나 .Wait()로 비동기 흐름을 억지로 기다리면 호출 스레드를 막는다. 초보 단계에서는 호출자를 포함해 Task를 반환하고 await로 연결하여 완료와 실패를 관찰하는 구조를 먼저 익힌다.

취소 요청 함수가 실패하면 요청도 없었던 일이 될까?

앞 본문은 Cancel 요청과 작업의 관찰/정리 종료를 나눴다. 새 사례는 취소 알림에 등록한 콜백 자체의 실패다. 새 source에 A를 먼저, B를 나중에 등록했으며 A는 문자 A를 로그에 더하고 정상 반환한다. B는 문자 B를 더한 뒤 예외 E를 던진다. source는 처음 미취소이며 다른 등록/재등록/동시 호출은 없다고 가정한다.

Cancel(false)는 등록 콜백을 동기적으로 역등록 순서로 호출한다. B가 먼저 로그를 남기고 실패해도 A를 계속 호출하여 로그 B,A를 얻고, 콜백의 예외를 모은 AggregateException을 호출자에게 보고한다. 토큰의 IsCancellationRequested는 true이다. Cancel 호출의 실패와 취소 요청 상태를 같은 성공/실패 스위치로 취급하면 이 상태를 놓친다.

별도 새 source에서 Cancel(true)를 호출하면 B의 첫 예외가 즉시 전파되어 남은 A 콜백을 처리하지 않는다. 로그는 B이고 요청 상태는 여전히 true다. 이 차이는 예외를 던지는 콜백을 권장한다는 뜻이 아니다. 공식 문서는 콜백과 취소 가능한 작업에서 예외를 피하도록 권한다. 콜백 실패 뒤에도 자원 정리/작업 종료의 책임을 설계해야 한다.

같은 source에 Cancel(false)를 다시 호출하는 변형에서는 이미 실행한 콜백을 재등록하지 않았으므로 동일 콜백 로그를 다시 더하지 않는다. 새 요청을 시작하려면 새 취소 수명과 source를 설계한다. 취소 알림은 작업이 외부에 이미 반영한 효과를 자동으로 되돌리는 rollback도 아니며 source를 정리하는 Dispose도 Cancel의 대체가 아니다.

소유자는 요청하고 작업은 관찰하기

CancellationTokenSource는 취소를 요청할 수 있는 소유자이고, CancellationToken은 요청 상태를 관찰하도록 작업에 전달하는 값이다. source.Cancel()은 요청을 알리며 작업의 스레드를 강제로 종료시키는 명령이 아니다.

토큰을 받은 작업은 적절한 지점에서 상태를 검사하거나 토큰을 지원하는 대기 API에 전달한다. ThrowIfCancellationRequested로 요청을 관찰하면 OperationCanceledException을 통해 정상 결과 대신 취소 흐름을 나타낼 수 있다.

전달하지 않으면 이어지지 않기

상위 메서드가 토큰을 받아도 실제 하위 작업에 전달하지 않으면 그 작업은 해당 요청을 알지 못한다. 독립적인 token을 넘긴 작업도 다른 source의 요청만으로 취소되지 않는다. 함수 인자에서 실제 관찰 지점까지 경로를 확인한다.

취소 여부는 한 번 요청되면 그 token에서 다시 미요청으로 되돌리지 않는다. 새 작업 묶음에는 새 source를 사용한다. source의 Dispose는 정리이며 Cancel을 대신하는 버튼이 아니므로 역할을 구별한다.

정리가 끝날 때까지 수명 유지하기

취소 요청을 관찰한 뒤에도 파일 닫기나 임시 상태 정리 같은 작업이 필요할 수 있다. 작업이 쓰는 자원을 먼저 없앤 뒤 완료를 기다리면 오류를 만든다. 소유자는 요청 후 실제 작업 완료를 관찰하고 관련 자원의 수명을 끝내야 한다.

검사 간격만으로 정확한 취소 완료 시간을 일반화할 수 없다. 스케줄링 지연, 취소를 지원하지 않는 대기와 정리 비용이 더해질 수 있다. 이미 외부에 반영한 변경은 token을 취소했다고 자동으로 되돌아가지 않는다.

준비 개념과 학습 목표

준비 개념

  • 취소 요청과 완료

학습 목표

  • 작업 실패와 대기 제한 시간 초과를 구별한다.

  • WhenAll의 완료·실패 상태를 추적한다.

  • 시작한 작업의 완료 관찰과 자원 정리를 설계한다.

먼저 끝난 Task를 얻었으면 그 작업도 성공한 것인가?

앞 본문은 WhenAll이 모든 종료를 기다리고 timeout이 원래 작업을 강제 중단하지 않는다고 설명했다. 새 입력 A는 시각 2에 예외 E로 실패하고 B는 시각 6에 정수 20으로 성공한다. 둘 다 시각 0에 이미 시작했다. WhenAny가 반환하는 바깥 Task는 첫 종료 A를 결과로 주며 RanToCompletion으로 끝난다. 바깥 성공은 A의 성공이 아니라 A라는 Task를 얻었다는 뜻이다.

따라서 바깥을 await하여 winner를 얻은 뒤 winner 자체를 await하면 A의 E를 관찰한다. B는 WhenAny 때문에 취소되지 않으며 시각 6까지 계속할 수 있다. 실패 후 B를 버릴 때도 B의 종료·예외 관찰·자원 정리를 담당할 주체가 필요하다. 같은 A/B의 WhenAll은 B까지 끝난 시각 6에 Faulted가 되고 A의 실패를 담는다.

새 별도 성공 입력 A는 값 10을 시각 6에, B는 값 20을 시각 2에 반환한다. WhenAll(new[]{A,B})의 결과 배열은 완료 순서 B,A가 아니라 입력 순서 A,B의 [10,20]이다. 완료순 결과가 필요하면 별도 요구와 수집 구조를 설계한다. 두 입력이 모두 실패하면 WhenAll의 Exception에서 모든 실패를 확인할 수 있지만 await가 던진 한 예외를 전체 실패 목록과 동일시하지 않는다.

전체 응답 마감은 또 다른 경계다. 새 연속 단계 X는 0부터 4까지, Y는 4부터 8까지 걸린다. 각 단계에 새 5밀리초 WaitAsync를 걸면 두 대기 모두 자기 제한 안에 끝나 총 8이 된다. 전체 시작부터 5밀리초라는 요구는 위반한다. 같은 시계의 전체 마감 시각 5를 고정하면 X 뒤 남은 예산은 1이고 Y 대기는 5에 timeout이다. Y의 실제 terminal은 여전히 8이므로 owner 수명은 그 종료 계약까지 관리한다.

실패는 await에서 관찰하기

Task로 표현된 비동기 작업에서 발생한 예외는 작업의 실패 상태에 담길 수 있으며, 그 Task를 await하면 예외를 관찰하고 catch에서 처리한다. 성공 값, 실패, 취소를 같은 성공 문구로 표시하지 않는다.

시작만 하고 Task를 버리면 완료와 예외를 놓치기 쉽다. 일반적인 비동기 메서드는 Task 또는 Task<T>를 반환하여 호출자가 관찰하게 한다. 작업의 실패가 이미 반영한 외부 효과까지 자동으로 취소한다는 뜻은 아니다.

대기의 시간 제한과 작업의 취소

task.WaitAsync(TimeSpan)로 얻은 대기 Task는 지정 시간 안에 원래 작업이 완료되지 않으면 TimeoutException으로 실패할 수 있다. 이 대기 제한만으로 원래 작업에 취소 요청을 전달하지는 않는다.

WaitAsync의 대기용 token과 원래 작업에 전달한 token도 구별한다. 작업 자체를 중단하려면 그 작업이 지원하는 취소 경로에 요청하고 실제 종료를 관찰해야 한다. 외부 서비스가 요청을 이미 받아 처리했다면 결과 확인이나 복구를 별도로 설계한다.

묶인 작업은 모두 끝난 뒤 판단하기

WhenAll은 모든 입력 작업이 끝나는 것을 표현한다. 하나라도 실패하면 결합 Task는 실패하고, 실패가 없지만 취소가 있으면 취소이며, 모두 정상 완료하면 정상 완료한다. 한 작업 실패만으로 나머지 입력 작업이 자동으로 취소되는 것은 아니다.

종료 절차에서는 새 작업을 막고, 필요한 취소를 요청하고, 시작한 작업들의 완료 및 실패를 관찰한 뒤 자원을 정리한다. 여러 실패를 조사하려면 결합 Task의 예외 집합도 확인한다. UI의 종료 표시와 실제 백그라운드 작업 종료를 구별한다.

  2. ② A의 준비는 시각 0–2, 대기는 2–8이다. B의 준비는 시각 2–4, 대기는 4–8이다. 전체 종료 시각은 8이다. 별도 box 입력의 재개 시 saved의 값은 4이고 box의 현재 읽기는 9다.

  3. ③ false는 B 실패 뒤 A도 처리하여 B,A와 AggregateException, true는 B만 처리하고 첫 E를 전파한다. 두 독립 source의 요청 플래그는 모두 true다.

  4. ④ WhenAny 바깥은 시각 2에 정상 완료하여 A를 주지만 winner await는 E를 관찰한다. B는 시각 6까지 남는다. X가 끝난 시각 4에서 남은 예산은 1밀리초이므로 Y 대기자는 시각 5에 timeout한다. 그러나 Y의 원래 종료 시각 8까지 관찰과 자원 수명의 책임은 남는다.
