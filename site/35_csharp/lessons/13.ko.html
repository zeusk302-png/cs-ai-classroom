소단원 13.1

비동기와 병렬의 구별

다운로드를 기다리는 동안 화면을 움직이면 계산도 동시에 두 개씩 하는 것일까?

준비 개념과 학습 목표

준비 개념

  • 메서드 호출

  • 시간선

  • Task

학습 목표

  • 비동기 대기와 병렬 계산을 구별한다.

  • 작업을 시작하는 시점과 기다리는 시점을 추적한다.

  • 가정에 따라 직렬·겹침 시간선을 계산한다.

기다림과 계산을 나누기

비동기는 오래 걸리는 작업의 완료를 기다리는 동안 호출자가 다른 일을 이어 갈 수 있게 하는 흐름이다. 병렬은 같은 시점에 여러 계산이 실제로 실행되는 상태다. 파일이나 네트워크의 완료를 기다리는 비동기 흐름이 반드시 여러 CPU에서 계산한다는 뜻은 아니다.

Task는 앞으로 완료될 작업의 상태를 표현한다. Task<T>는 완료하면 T형 결과를 제공한다. async 표시는 메서드에서 await를 사용할 수 있게 하지만 새 스레드를 자동으로 만들지 않는다. CPU 계산을 분리하는 Task.Run과 장치의 비동기 API는 목적을 구별해야 한다.

먼저 시작할지 먼저 기다릴지

await A(); await B();는 A 호출의 완료를 기다린 다음 B를 호출한다. 반면 var a = A(); var b = B(); 뒤에 두 작업을 기다리면 A와 B가 먼저 호출된다. 이때 두 API가 실제 작업을 시작하며 서로 독립이라는 조건에서 대기 시간이 겹칠 수 있다.

작업을 무조건 많이 시작하면 서버나 메모리 한도를 넘을 수 있다. 비동기라는 이름만으로 처리량 향상이나 응답 시간 감소를 보장하지 않는다. 작업 수, 의존 관계와 외부 자원의 용량을 먼저 적는다.

두 작업의 완료를 묶기

Task.WhenAll(a, b)는 주어진 작업들이 모두 끝나는 것을 나타내는 Task를 반환한다. 호출 자체가 현재 스레드를 끝까지 붙잡는 대기는 아니며, 반환된 Task를 await해 완료를 관찰한다.

이미 시작한 두 작업이라면 await a 뒤에 await b를 해도 b의 시작이 뒤로 밀리지 않는다. 다만 오류 관찰과 종료 관리까지 포함한 설계에서는 모든 작업의 완료를 명시적으로 묶는 편이 이해하기 쉽다.

중간 과정을 따라가는 예제

가상 다운로드 A는 6 ms, B는 4 ms다. 시작 비용은 0이고 두 작업은 독립이며 동시에 진행할 외부 용량이 있다. 세 가지 호출 순서를 비교하라.

  1. A를 호출하고 완료 후 B를 호출하면 A는 0–6 ms, B는 6–10 ms다.

  2. A와 B를 모두 0 ms에 시작하면 각각 6 ms와 4 ms에 끝난다. WhenAll 완료는 6 ms다.

  3. 두 작업을 0 ms에 먼저 시작한 뒤 a를 await하면 6 ms에 돌아온다. b는 이미 완료되어 다음 await도 6 ms에 끝난다.

직렬 호출은 10 ms, 먼저 시작한 두 흐름은 이 가정에서 6 ms다. CPU 병렬 실행의 증거는 아니다.

풀이 보기

B는 A의 완료 6 ms 이후에 시작하므로 10 ms다. 의존 관계를 없애지 않은 채 WhenAll로 감싸도 빨라지지 않는다.

오해와 반례

async를 붙이면 모든 메서드가 새 스레드에서 병렬로 실행된다.

async는 비동기 제어 흐름을 위한 표기다. 실제 실행 자원과 작업 시작은 API 및 스케줄링 방식에 달려 있다.

소단원 13.2

await와 continuation

await 뒤의 문장은 메서드가 사라졌다가 다시 호출되는 것일까?

준비 개념과 학습 목표

준비 개념

  • Task<T>

  • 지역 변수

  • try·finally

학습 목표

  • 완료된 대기와 미완료된 대기의 차이를 설명한다.

  • continuation의 역할과 로그 순서를 추적한다.

  • 대기 중단과 메서드 종료를 구별한다.

미완료이면 이어 할 일을 남기기

await 대상이 아직 완료되지 않았다면 비동기 메서드는 그 뒤에 이어 할 일을 등록하고 호출자에게 제어를 돌려줄 수 있다. 이 이어 할 흐름을 continuation이라고 부른다. 필요한 지역 변수와 진행 상태는 이어 실행할 수 있게 보존된다.

메서드의 최초 부분은 호출한 흐름에서 시작하며, 처음 만난 미완료 await까지 동기적으로 진행할 수 있다. async 메서드를 호출했다는 이유만으로 첫 문장부터 별도 스레드에 간다고 생각하면 로그 순서를 잘못 예측한다.

이미 끝났다면 바로 이어 가기

await 대상이 이미 완료되었다면 완료 결과를 꺼내 다음 문장으로 진행할 수 있다. 모든 await가 반드시 일시 중단을 만들지는 않는다. Task<int>를 정상적으로 await한 표현식의 값은 int 결과다.

이어 실행되는 스레드와 문맥은 호출 환경 및 설정에 영향을 받는다. 여기서는 특정 UI 스레드 복귀나 새 스레드 사용을 가정하지 않고, 완료 이전과 이후의 제어 흐름만 추적한다.

중단은 종료가 아니다

try 안의 await에서 대기한다고 해서 finally가 곧바로 실행되지는 않는다. 메서드가 그 try 범위를 실제로 나가거나 예외·취소로 빠져나갈 때 finally가 실행된다. 대기 중에도 아직 사용하는 자원을 일찍 해제해서는 안 된다.

동기적인 .Result나 .Wait()로 비동기 흐름을 억지로 기다리면 호출 스레드를 막는다. 초보 단계에서는 호출자를 포함해 Task를 반환하고 await로 연결하여 완료와 실패를 관찰하는 구조를 먼저 익힌다.

중간 과정을 따라가는 예제

F는 before를 기록하고 gate를 await한 뒤 after를 기록해 7을 반환한다. 호출자는 F를 호출한 다음 caller를 기록한다. gate는 미완료이며 caller 기록 이후에 완료된다고 가정한다.

  1. F 호출 시 before가 먼저 기록된다.

  2. 미완료 gate에서 F가 대기하므로 호출자가 caller를 기록한다.

  3. gate가 완료된 뒤 F의 continuation이 after를 기록하고 결과 7을 제공한다.

  4. gate가 호출 전부터 완료되어 있었다면 F가 중단 없이 after까지 진행한 다음 호출자가 caller를 기록한다.

미완료 조건에서는 before → caller → after다. 이미 완료된 조건에서는 before → after → caller다. 결과 값은 둘 다 7이다.

종이와 본문으로 직접 해보기

F의 try 안에서 gate를 기다리고 finally에서 closed를 기록한다. 위 미완료 조건에서 closed가 caller보다 먼저 찍힌다고 주장할 수 있는가?

힌트 보기

await의 대기 중단과 try 범위의 종료를 구별한다.

풀이 보기

그 조건에서는 주장할 수 없다. 대기 중단만으로 finally에 가지 않는다. gate 완료 후 F가 try를 나갈 때 closed를 기록한다. gate가 끝나지 않으면 그 종료도 아직 일어나지 않는다.

오해와 반례

await를 만나면 항상 메서드가 종료되고 finally가 즉시 실행된다.

미완료 대기에서는 흐름을 잠시 중단한다. 메서드와 try 범위의 실제 종료는 별도 사건이며, 완료된 대상은 중단하지 않을 수도 있다.

답과 이유 보기

한 단계 더

미완료 gate가 정상 완료하는 경우와 예외로 완료하는 경우를 각각 그려 본다. 예외 경우에는 after 실행 여부와 finally 실행을 따로 표시한다. 여기서는 로그 프로그램을 실제 실행하지 않았다.

소단원 13.3

CancellationToken

취소 버튼을 누른 순간 이미 시작한 모든 일이 끝났다고 말할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 작업 완료

  • 예외

  • 자원 소유권

학습 목표

  • 취소 요청과 취소 관찰을 구별한다.

  • CancellationTokenSource와 token의 역할을 설명한다.

  • 취소 이후 정리와 완료를 포함한 시간선을 계산한다.

소유자는 요청하고 작업은 관찰하기

CancellationTokenSource는 취소를 요청할 수 있는 소유자이고, CancellationToken은 요청 상태를 관찰하도록 작업에 전달하는 값이다. source.Cancel()은 요청을 알리며 작업의 스레드를 강제로 종료시키는 명령이 아니다.

토큰을 받은 작업은 적절한 지점에서 상태를 검사하거나 토큰을 지원하는 대기 API에 전달한다. ThrowIfCancellationRequested로 요청을 관찰하면 OperationCanceledException을 통해 정상 결과 대신 취소 흐름을 나타낼 수 있다.

전달하지 않으면 이어지지 않기

상위 메서드가 토큰을 받아도 실제 하위 작업에 전달하지 않으면 그 작업은 해당 요청을 알지 못한다. 독립적인 token을 넘긴 작업도 다른 source의 요청만으로 취소되지 않는다. 함수 인자에서 실제 관찰 지점까지 경로를 확인한다.

취소 여부는 한 번 요청되면 그 token에서 다시 미요청으로 되돌리지 않는다. 새 작업 묶음에는 새 source를 사용한다. source의 Dispose는 정리이며 Cancel을 대신하는 버튼이 아니므로 역할을 구별한다.

정리가 끝날 때까지 수명 유지하기

취소 요청을 관찰한 뒤에도 파일 닫기나 임시 상태 정리 같은 작업이 필요할 수 있다. 작업이 쓰는 자원을 먼저 없앤 뒤 완료를 기다리면 오류를 만든다. 소유자는 요청 후 실제 작업 완료를 관찰하고 관련 자원의 수명을 끝내야 한다.

검사 간격만으로 정확한 취소 완료 시간을 일반화할 수 없다. 스케줄링 지연, 취소를 지원하지 않는 대기와 정리 비용이 더해질 수 있다. 이미 외부에 반영한 변경은 token을 취소했다고 자동으로 되돌아가지 않는다.

중간 과정을 따라가는 예제

자체 가상 작업은 0 ms에 시작한다. 소유자가 3 ms에 취소를 요청하고 작업은 5 ms 검사 지점에서 처음 관찰한다. 정리는 2 ms 걸린다. 다른 지연은 없다고 가정한다.

  1. 요청 시점은 3 ms이고 관찰 시점은 5 ms이므로 관찰 지연은 2 ms다.

  2. 관찰 후 정리는 5–7 ms다.

  3. 실제 종료는 7 ms이며 요청부터 종료까지 7−3=4 ms다.

  4. 3 ms에 완료로 표시하면 관찰과 정리 4 ms를 빠뜨린다.

요청 3 ms, 관찰 5 ms, 종료 7 ms를 구별한다. 실제 완료는 7 ms이며 요청 후 4 ms다.

종이와 본문으로 직접 해보기

같은 조건에서 관찰 지점이 4 ms로 앞당겨지고 정리 시간이 3 ms로 늘면 언제 끝나는가? 하위 작업에 token을 전달하지 않은 경우에도 이 계산을 쓸 수 있는가?

힌트 보기

관찰 시점에 정리 시간을 더한다. 먼저 그 작업이 요청을 실제로 관찰하는지 확인한다.

풀이 보기

관찰하는 작업은 4+3=7 ms에 끝난다. token을 전달하지 않아 요청을 관찰하지 않는 하위 작업에는 이 종료 가정을 적용할 수 없다.

오해와 반례

Cancel이 반환했으므로 모든 작업과 외부 변경이 이미 취소되었다.

Cancel은 협력적 요청이다. 실제 작업 완료와 정리를 관찰해야 하며 이미 일어난 외부 효과의 복구는 별도 설계다.

자기점검

취소를 요청하는 객체는?

답과 이유 보기

CancellationTokenSource다.

작업에는 요청 권한 대신 관찰용 token을 전달할 수 있다.

취소된 같은 token을 초기 상태로 되돌려 새 작업에 재사용하는가?

답과 이유 보기

그렇게 되돌리지 않는다.

취소 요청 상태는 한 방향으로 바뀌므로 새 source를 준비한다.

상위 인자에 token이 있으면 모든 하위 API에 자동으로 전달되는가?

답과 이유 보기

아니다.

실제 인자 전달과 해당 API의 취소 지원을 확인해야 한다.

한 단계 더

작업 A는 취소를 관찰해 정리하고, 작업 B는 이미 서버에 저장을 완료한 상황을 그린다. B의 외부 상태를 취소와 별도로 어떻게 확인할지 적는다. 실제 서버에 요청을 보내지 않는다.

소단원 13.4

예외·timeout·종료 처리

3초 안에 기다리지 못했다는 사실이 원래 작업도 멈췄다는 뜻일까?

준비 개념과 학습 목표

준비 개념

  • await

  • 취소 요청과 완료

  • try·catch·finally

학습 목표

  • 작업 실패와 대기 제한 시간 초과를 구별한다.

  • WhenAll의 완료·실패 상태를 추적한다.

  • 시작한 작업의 완료 관찰과 자원 정리를 설계한다.

실패는 await에서 관찰하기

Task로 표현된 비동기 작업에서 발생한 예외는 작업의 실패 상태에 담길 수 있으며, 그 Task를 await하면 예외를 관찰하고 catch에서 처리한다. 성공 값, 실패, 취소를 같은 성공 문구로 표시하지 않는다.

시작만 하고 Task를 버리면 완료와 예외를 놓치기 쉽다. 일반적인 비동기 메서드는 Task 또는 Task<T>를 반환하여 호출자가 관찰하게 한다. 작업의 실패가 이미 반영한 외부 효과까지 자동으로 취소한다는 뜻은 아니다.

대기의 시간 제한과 작업의 취소

task.WaitAsync(TimeSpan)로 얻은 대기 Task는 지정 시간 안에 원래 작업이 완료되지 않으면 TimeoutException으로 실패할 수 있다. 이 대기 제한만으로 원래 작업에 취소 요청을 전달하지는 않는다.

WaitAsync의 대기용 token과 원래 작업에 전달한 token도 구별한다. 작업 자체를 중단하려면 그 작업이 지원하는 취소 경로에 요청하고 실제 종료를 관찰해야 한다. 외부 서비스가 요청을 이미 받아 처리했다면 결과 확인이나 복구를 별도로 설계한다.

묶인 작업은 모두 끝난 뒤 판단하기

WhenAll은 모든 입력 작업이 끝나는 것을 표현한다. 하나라도 실패하면 결합 Task는 실패하고, 실패가 없지만 취소가 있으면 취소이며, 모두 정상 완료하면 정상 완료한다. 한 작업 실패만으로 나머지 입력 작업이 자동으로 취소되는 것은 아니다.

종료 절차에서는 새 작업을 막고, 필요한 취소를 요청하고, 시작한 작업들의 완료 및 실패를 관찰한 뒤 자원을 정리한다. 여러 실패를 조사하려면 결합 Task의 예외 집합도 확인한다. UI의 종료 표시와 실제 백그라운드 작업 종료를 구별한다.

중간 과정을 따라가는 예제

가상 작업 A는 2 ms에 실패하고 B는 5 ms에 성공한다. 둘을 WhenAll로 묶는다. 별도 작업 C는 8 ms에 끝나며 0 ms부터 WaitAsync로 3 ms만 기다린다. 취소는 요청하지 않는다.

  1. A 실패 뒤에도 B는 주어진 가정대로 진행한다. 모든 입력이 끝나는 5 ms에 결합 Task가 실패 상태로 완료한다.

  2. C의 대기는 3 ms에 TimeoutException으로 실패하지만 원래 C를 취소한 것은 아니다.

  3. C는 주어진 가정에서 8 ms에 정상 완료한다. 대기 실패와 원래 작업 완료를 따로 기록한다.

WhenAll(A,B)는 5 ms에 실패한다. C의 제한 대기는 3 ms에 실패하고 원래 C는 8 ms에 끝난다.

종이와 본문으로 직접 해보기

A가 정상 완료하고 B가 취소 상태로 끝나며 둘 다 5 ms까지 완료했다면 WhenAll 상태는? C 대기 timeout 뒤 자원을 바로 해제하면 왜 위험한가?

힌트 보기

실패가 있는지 먼저 살피고, 자원을 실제로 사용하는 작업의 종료를 확인한다.

풀이 보기

실패가 없고 취소가 있으므로 결합 Task는 취소 상태다. C가 아직 자원을 쓰고 있을 수 있으므로 대기 timeout만 보고 자원을 해제하면 수명 오류가 생긴다. 취소 지원과 실제 완료를 확인한 뒤 정리한다.

오해와 반례

timeout을 처리했으므로 원래 작업과 같은 묶음의 다른 작업도 모두 종료되었다.

대기 제한 시간 초과는 그 대기의 결과다. 원래 작업의 상태와 다른 작업의 실제 완료는 각각 확인해야 한다.

자기점검

WhenAll 입력 중 하나가 실패하고 다른 하나가 취소되면 결합 상태는?

답과 이유 보기

실패다.

실패가 하나라도 있으면 Faulted가 우선한다.

WaitAsync의 시간 제한만으로 원래 작업을 취소하는가?

답과 이유 보기

아니다.

대기 완료 조건과 원래 작업의 취소 경로는 별도다.

비동기 종료에서 자원 해제 전에 확인할 것은?

답과 이유 보기

그 자원을 사용하는 시작된 작업의 실제 완료와 필요한 정리다.

화면 표시나 취소 요청만으로 사용이 끝났다고 보장하지 않는다.

한 단계 더

결합 작업에 두 실패가 있는 경우 await에서 관찰한 예외와 결합 Task에 저장된 예외 집합을 구별해 조사 절차를 적는다. 실제 C# 실행 결과로 단정하지 않는다.
