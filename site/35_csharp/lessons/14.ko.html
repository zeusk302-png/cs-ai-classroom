소단원 14.1

race와 lock

두 사람이 동시에 마지막 좌석을 보고 예약하면 둘 다 성공해도 될까?

준비 개념과 학습 목표

준비 개념

  • 공유 변수

  • 조건문

  • 스레드와 작업

학습 목표

  • 검사와 수정 사이의 경쟁 경로를 추적한다.

  • 같은 잠금으로 보호할 범위를 정한다.

  • 잠금과 작업 성공 조건을 구별한다.

한 줄처럼 보이는 처리도 나뉜다

좌석 수를 읽고 양수인지 검사한 뒤 하나 줄이는 예약은 여러 단계다. 자체 모형에서 좌석이 1개이고 A와 B가 각각 1을 읽은 뒤 성공으로 처리하면 실제 자리 하나에 성공 기록 둘을 만들 수 있다.

이 단원은 종이에서 읽기·판단·쓰기 순서를 정한 경쟁 반례다. 실제 CPU의 모든 명령이나 C#의 모든 실행 순서를 관찰한 것은 아니다. 빠른 실행 한 번이 정상이라고 경쟁 가능성이 없다고 판단하지 않는다.

조건과 갱신을 같은 구간에 둔다

전용의 같은 잠금 객체 gate를 모든 관련 경로에서 사용하고 검사와 감소를 하나의 lock 구간에 둔다. A가 먼저 잠금을 잡고 1을 0으로 바꾼 뒤 B가 진입하면 B는 0을 보고 실패한다.

검사만 잠금 안에서 하고 감소를 밖에서 하면 두 작업이 검사 사이를 통과하는 문제가 남는다. 각 요청이 서로 다른 new object를 잠금으로 쓰는 것도 같은 공유 상태를 보호하지 못한다. 잠금은 모든 갱신 경로가 따르는 공통 계약이어야 한다.

짧은 구간과 실패 경로

lock은 정상 종료뿐 아니라 예외로 구간을 나가도 잠금을 해제하도록 구성된다. 그렇다고 이미 수정한 여러 값을 자동으로 이전 상태로 돌리는 데이터 트랜잭션은 아니다. 변경 순서와 불변 조건도 정해야 한다.

잠금을 잡은 채 오래 걸리는 외부 작업을 수행하면 다른 요청을 막을 수 있다. lock 본문에는 await를 쓸 수 없으므로 비동기 외부 작업과 짧은 상태 확정을 나누고 필요한 재검사를 계획한다. 실제 예약·네트워크·컴파일은 수행하지 않았다.

중간 과정을 따라가는 예제

좌석 1개에서 A와 B가 읽기·검사·남은 수 쓰기를 수행한다. 각각 읽은 값에서 1을 빼서 쓴다고 정한다. 무잠금 일정과 공통 gate의 전체 구간 잠금을 비교한다.

  1. 무잠금 일정: A가 1을 읽고 B도 1을 읽는다. 둘 다 양수 검사에 통과한다.

  2. A가 0을 쓰고 B도 0을 쓴다. 남은 수는 0이지만 성공 기록은 2개다.

  3. 전체 구간 잠금 일정: A가 1을 읽고 0으로 감소해 성공한 뒤 해제한다.

  4. B는 그 뒤 0을 읽어 실패한다. 성공 기록은 1개다.

무잠금 반례는 남은 수 0·성공 2개, 같은 gate로 전체 구간을 보호하면 이 일정에서 남은 수 0·성공 1개다.

풀이 보기

A 진입 때 2, A 완료 뒤 1, B 진입 때 1, B 완료 뒤 0이다. 둘 다 성공한다. 검사와 수정 사이를 보호하지 않으면 다른 작업이 끼어들 수 있어 검사만의 잠금은 충분하지 않다.

오해와 반례

lock 키워드가 어디든 있으면 모든 공유 상태가 안전하다.

같은 잠금 객체를 모든 관련 경로가 사용하고 필요한 검사·수정 전체를 보호해야 한다. 다른 객체의 잠금이나 구간 밖 수정은 이 계약을 깨뜨린다.

소단원 14.2

thread-safe collection

안전한 큐에서 개수를 확인한 뒤 하나 꺼내는 두 동작도 항상 한 묶음일까?

준비 개념과 학습 목표

준비 개념

  • 큐

  • 사전

  • 개별 연산과 연속 처리

학습 목표

  • 개별 연산의 안전성과 복합 계약을 구별한다.

  • 실패 반환값을 사용하는 소비 경로를 설명한다.

  • 사전 생성 함수의 부작용 위험을 찾는다.

안전성의 범위를 정한다

일반 List나 Dictionary를 여러 스레드가 동시에 수정할 때는 별도의 동기화 계약이 필요하다. ConcurrentQueue 같은 컬렉션은 동시 사용을 위한 개별 연산을 제공한다. 자료 구조 이름에 안전이 붙어도 주변 코드의 모든 판단이 자동 원자화되지는 않는다.

자체 큐 [7]에서 A가 Count가 양수라고 확인한 뒤 B가 7을 먼저 꺼낼 수 있다. A가 나중에 꺼내는 시도는 실패할 수 있다. 실패를 반환하는 TryDequeue의 결과를 검사해야 한다.

관찰 대신 시도 결과를 판단한다

큐가 비어 있을 가능성을 정상 상태로 취급하고 TryDequeue가 true일 때만 반환 항목을 처리한다. false이면 대기·종료·다른 작업 중 계약에 맞는 선택을 한다. 실패 때의 out 값을 정상 항목으로 처리하지 않는다.

이 자체 일정에서는 B의 성공 항목 7이 한 번 처리되고 A는 실패 분기로 간다. A와 B 중 누가 먼저 성공할지는 일정을 별도로 주지 않으면 확정할 수 없다. Count는 미래의 예약권이 아니다.

사전 안과 함수 밖의 경계

ConcurrentDictionary는 TryAdd·TryUpdate처럼 조건을 포함한 연산을 제공한다. 키가 없음을 확인하고 별도의 추가를 하는 두 호출은 하나의 독점 계약이 아니다. 원하는 조건에 맞는 단일 연산과 반환값을 사용한다.

GetOrAdd나 AddOrUpdate에 넘긴 함수는 내부 잠금 밖에서 실행될 수 있다. 자체 일정에서 두 함수가 각각 값을 계산했어도 사전에 채택되는 값은 하나일 수 있다. 함수 안의 결제·알림을 정확히 한 번 수행한다고 기대하지 말고 중복 가능한 계산과 외부 부작용을 분리한다.

중간 과정을 따라가는 예제

ConcurrentQueue의 자체 일정은 초기 [7], A의 Count 확인, B의 성공 TryDequeue, A의 TryDequeue 순서다. 각 시도의 성공과 처리 항목을 정한다.

  1. A의 관찰 때 개수는 1이다.

  2. B가 7을 꺼내는 시도는 성공하고 큐는 비어 있다.

  3. A의 뒤늦은 시도는 실패한다. 앞선 Count 관찰은 항목을 예약하지 않았다.

  4. 반환 성공을 검사하는 코드라면 B만 7을 처리하고 A는 실패 정책을 따른다.

B는 true와 7, A는 false다. A는 실패 시 out 값을 정상 항목으로 처리하지 않는다.

종이와 본문으로 직접 해보기

초기 키가 없는 사전에서 A/B의 GetOrAdd 생성 함수가 각각 10과 20을 계산한다. 이 일정에서는 A의 10이 먼저 저장되고 키 제거는 없다고 정한다. 함수 호출 수와 A/B가 얻는 저장 값을 구분하라.

힌트 보기

자체 일정이 두 함수의 실제 호출을 가정한다. 계산 횟수와 채택 값의 수는 다르다.

풀이 보기

이 일정의 함수 호출은 2회지만 새 키에 채택된 값은 10 하나다. 키가 유지되므로 A와 B는 저장된 10을 얻는다. 모든 실행에서 함수가 반드시 2회 실행된다는 주장은 아니며 외부 부작용 1회를 보장하지도 않는다.

오해와 반례

ConcurrentDictionary의 생성 함수는 무조건 정확히 한 번 실행되므로 그 안에서 외부 지급을 해도 된다.

함수 코드가 연산의 원자성에 포함되지 않는다. 경쟁으로 호출이 겹칠 수 있어 계산과 외부 지급의 중복 계약을 별도로 설계한다.

성공 반환값이 없는 상태다.

소단원 14.3

Task.WhenAll와 제한된 병렬성

모든 작업의 완료를 기다리는 함수가 동시에 시작할 작업 수까지 정해 줄까?

준비 개념과 학습 목표

준비 개념

  • Task

  • await

  • 허가 수

학습 목표

  • 완료 결합과 실행 수 제한을 구별한다.

  • 허가 획득과 반환의 경로를 설계한다.

  • 완료 순서와 결과 순서 및 실패 상태를 추적한다.

기다릴 작업들을 묶는다

WhenAll은 제공한 작업들의 완료를 나타내는 Task를 만든다. 그것만으로 작업들을 새로 생성하거나 동시 실행 수를 제한하지 않는다. 이미 시작한 작업들이 언제 끝나는지와 결과를 어떻게 받는지를 나누어 설명한다.

자체 목록 [A, B, C]의 결과가 각각 2, 4, 6이고 완료는 B → C → A라고 정하자. 모두 정상 완료한 Task<T>의 WhenAll 결과 배열은 제공한 순서 [2, 4, 6]이다. 완료 순서대로 정렬하는 함수는 아니다.

작업 수의 별도 계약

실행 구간에 동시에 진입할 수 있는 수를 SemaphoreSlim의 허가 수로 제한하는 모형을 쓸 수 있다. 허가를 획득한 뒤 실행하고, 획득에 성공한 경로는 finally에서 정확히 한 번 Release한다.

WaitAsync의 취소나 실패로 획득하지 못한 경로에서 무조건 Release하면 허가 계약이 깨진다. 또한 작업 구간 수를 제한해도 대기 Task를 무한히 생성하는 설계의 메모리 문제까지 해결하지 않는다. 큰 입력은 작업 생성량 자체도 제한할 수 있어야 한다.

시간과 상태를 가정해 계산한다

자체 비용 모형에서 A/B/C/D가 각각 3/2/4/1초 걸리고 제한이 2개라고 하자. 대기 순서 A → B → C → D, 진입·전환 비용 0, 작업 간 간섭 없음으로 정하면 A/B가 0초에 시작한다.

B가 2초에 끝나 C가 2~6초, A가 3초에 끝나 D가 3~4초에 실행되어 전체 완료는 6초다. 실제 SemaphoreSlim은 대기 순서의 FIFO를 보장하는 스케줄러로 설명하지 않는다. 실패한 작업이 있으면 WhenAll의 결합 상태는 실패이며, 실패가 없고 취소가 있으면 취소다.

중간 과정을 따라가는 예제

가상 작업 A/B/C/D의 시간은 3/2/4/1초다. 두 허가, 명시한 대기 순서 A → B → C → D, 전환 비용 0과 독립 실행을 가정한다.

  1. 0초에 A와 B가 허가를 얻어 실행한다.

  2. 2초에 B가 끝나 허가를 반환하고 C가 2~6초에 실행한다.

  3. 3초에 A가 끝나 허가를 반환하고 D가 3~4초에 실행한다.

  4. 마지막 C가 6초에 완료한다. 순차 합 3 + 2 + 4 + 1 = 10초와 비교한다.

이 모형은 전체 6초이며 순차 모형은 10초다. 실제 시간 측정이나 대기 순서 보장은 아니다.

종이와 본문으로 직접 해보기

작업 결과 목록 [A, B, C]에서 B가 먼저 4, C가 다음 6, A가 마지막 2를 반환했다. WhenAll 결과 순서를 구하라. B는 취소, C는 실패로 바꾼 다른 경우의 결합 상태도 정하라.

힌트 보기

결과는 제공한 작업 순서다. 결합 상태에서는 실패 유무를 먼저 본다.

풀이 보기

모두 정상인 경우 결과는 [2, 4, 6]이다. 다른 경우 C가 실패했으므로 결합 상태는 Faulted다. B의 취소를 전체 정상 완료로 처리하지 않는다.

오해와 반례

WhenAll을 썼으므로 동시 작업은 자동으로 2개이며 작업 수가 많아도 공간은 일정하다.

WhenAll은 완료 결합이다. 동시 진입 수와 생성·대기량을 별도로 제한해야 한다. 두 허가 모형도 무한한 대기 객체의 공간을 자동 없애지 않는다.

자기점검

WaitAsync 실패 뒤 아직 획득하지 않은 허가를 Release하는가?

답과 이유 보기

하면 안 된다.

획득한 허가만 반환하는 계약이다.

WhenAll 결과 배열은 완료 순서인가?

답과 이유 보기

제공한 작업 순서다.

모두 정상 완료한 일반 결과형 계약을 적용한다.

실패와 취소가 함께 있으면 결합 상태는?

답과 이유 보기

Faulted다.

실패가 없는 경우에만 취소 상태 조건을 적용한다.

한 단계 더

허가를 1개로 바꾸면 같은 작업 순서의 모형은 10초다. 허가 4개와 모두 0초 시작이라는 새 가정에서는 최대 시간 4초다. 이 모형의 차이를 실제 CPU 수나 서비스 속도 향상으로 확정하지 말라.

소단원 14.4

deadlock·context·shared state

작업 A가 B를 기다리고 B도 A를 기다리면 시간이 지나기만 해도 풀릴까?

준비 개념과 학습 목표

준비 개념

  • 잠금

  • await와 대기

  • UI 실행 경로

학습 목표

  • 순환 대기를 화살표로 설명한다.

  • 단일 실행 경로의 동기 대기와 continuation을 구별한다.

  • 공유 수정 없이 결과를 모으는 대안을 제시한다.

보유한 것과 기다리는 것을 그린다

자체 일정에서 A는 잠금 X를 갖고 Y를 기다리며 B는 Y를 갖고 X를 기다린다. 둘 다 다른 잠금을 얻기 전 자기 잠금을 놓지 않고 취소·외부 해제도 없다고 정하면 진행할 수 없는 순환 대기다.

두 잠금이 필요하면 모든 경로가 X 다음 Y 같은 공통 획득 순서를 따르는 방법을 검토한다. 한 경로만 순서를 바꿔도 계약이 깨진다. 이 방법은 두 잠금 모형의 순환을 막는 조건이지 모든 종류의 교착을 자동 증명한 것은 아니다.

UI 경로를 막으면 돌아올 곳이 없다

자체 단일 UI 실행 경로 U에서 비동기 작업을 시작하고 아직 완료되지 않은 Task의 Result를 동기로 기다린다고 하자. 그 작업의 남은 continuation이 U에서 실행되어야 완료되는 조건이면 U는 완료를 기다리고 완료는 U의 실행을 기다린다.

await로 UI 경로를 반환하면 필요한 남은 동작을 실행할 기회가 생긴다. 모든 Result가 언제나 교착이라는 말은 아니며 완료 상태·실행 context 조건이 중요하다. ConfigureAwait나 Task.Run 하나를 모든 교착의 자동 해결로 선언하지 않는다.

공유 누적을 줄이는 설계

각 작업이 공유 total에 값을 더하면 작은 코드에도 경쟁이 생길 수 있다. 작업이 자기 결과를 반환하고 모든 정상 결과가 모인 뒤 한 경로에서 합산하는 대안을 사용하면 그 공유 수정 구간을 줄일 수 있다.

자체 결과 [2, 4, 6]의 합은 12다. 일부 작업이 실패하면 없는 결과를 0으로 조용히 바꾸는 것은 다른 정책이다. 모두 성공 시 전체 합, 실패 시 오류 기록 같은 명시적 계약을 먼저 정한다. 실제 UI·스레드·교착 재현은 수행하지 않았다.

중간 과정을 따라가는 예제

A가 X를 보유하고 Y를 기다리며 B가 Y를 보유하고 X를 기다린다. 둘 다 필요한 두 잠금 전에는 해제하지 않고 취소나 외부 해제는 없다.

  1. A → Y 보유자 B의 진행을 기다리는 화살표를 그린다.

  2. B → X 보유자 A의 진행을 기다리는 화살표를 그린다.

  3. A → B → A 순환이며 두 작업 모두 현재 조건에서는 진행할 수 없다.

  4. 모든 경로가 X 다음 Y를 획득하도록 바꾸면 B가 Y만 선점하는 이 반례 일정은 성립하지 않는다.

원래 조건은 순환 대기다. 공통 획득 순서는 이 두 잠금 반례의 원인을 제거하지만 모든 프로그램의 무교착 증명은 아니다.

종이와 본문으로 직접 해보기

단일 UI 경로 U가 Task 완료를 Result로 기다리고, 미완료 Task는 U의 continuation을 실행해야 완료된다는 가상 조건을 그려라. 정상 결과 [2,4,6]을 한 경로에서 합산하는 값도 구하라.

힌트 보기

U → Task 완료와 Task 완료 → U를 연결한다.

풀이 보기

동기 대기가 U를 막으면 두 의존성이 순환한다. 비동기 await로 경로를 반환하는 설계를 검토한다. 정상 결과의 합은 2 + 4 + 6 = 12다. 실제 UI 재현이나 await로 모든 교착이 해결됐다는 증거는 아니다.

오해와 반례

await가 있으면 잠금과 공유 상태의 교착이나 경쟁은 모두 없어진다.

다른 자원을 보유한 순환 대기와 공유 자료 수정은 여전히 가능하다. 대기 의존성·실행 context·보유 자원과 결과 계약을 함께 점검한다.

예제는 U 실행이 필요한 미완료 작업을 기다린다.

답과 이유 보기

아니다.

실패 처리 정책이 달라진다.

한 단계 더

한 작업이 실패하는 결과 결합 정책을 적어라. 전체 취소·부분 결과 표시·재시도 중 선택 근거를 밝히고 이 단원의 모두 정상 합 12와 혼동하지 말라. 작업 반환형 설계도 다른 공유 객체까지 자동 안전하게 만들지는 않는다.
