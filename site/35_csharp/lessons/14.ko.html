다른 스레드를 막았는데 왜 잘못된 중간 잔액을 읽을 수 있을까?

앞 본문의 좌석 예제는 검사와 감소를 같은 gate 안에서 처리했다. 새 사례는 같은 gate를 사용하는 두 계좌 잔액 A와 B이며 초기 값은 각각 10과 0이다. 합계 10을 유지하며 A에서 B로 3을 옮기려 한다. 새 구현은 gate를 잡고 A를 7로 만든 뒤 외부 알림 콜백을 호출하고, 그 뒤 B를 3으로 만든다. 콜백은 같은 스레드에서 합계 조회 함수를 호출하며 그 함수도 같은 gate를 잠근다.

일반 객체에 대한 lock은 같은 스레드의 재진입을 허용한다. 따라서 콜백은 자기 스레드가 이미 가진 gate를 다시 잡고 중간 상태 A = 7, B = 0을 읽을 수 있다. 합계는 7이다. 다른 스레드가 끼어들지 않아도 외부에 공개한 중간 불변식이 깨졌다. 서로 배제하는 능력과 업무 상태가 항상 완전하게 보이는 능력을 구별해야 한다.

콜백이 예외 E를 던져 B 대입 전에 빠져나가는 변형에서는 gate가 해제되지만 잔액은 자동 복구되지 않는다. finally를 통한 잠금 해제는 이미 수행한 A 대입의 rollback이 아니다. 수정 설계는 먼저 새 쌍 (7, 3)을 독립적으로 구성하고, 모든 읽기와 게시가 같은 gate를 사용하는 조건 아래 한 번에 완성 쌍을 게시한다. 그 뒤 gate 밖에서 알림을 호출한다. 쌍의 내부 값은 이후 수정하지 않는다는 소유 계약도 필요하다.

이 설계에서 알림 실패는 잔액 이동의 취소를 뜻하지 않는다. 이동을 이미 반영한 뒤 알림이 실패했음을 별도로 보고해야 한다. 외부 효과까지 원자적으로 되돌려야 한다면 더 큰 업무 프로토콜이 필요하며 이 작은 메모리 gate만으로 보장하지 않는다. 실제 은행·스레드·콜백 실행은 하지 않았다.

한 줄처럼 보이는 처리도 나뉜다

좌석 수를 읽고 양수인지 검사한 뒤 하나 줄이는 예약은 여러 단계다. 자체 모형에서 좌석이 1개이고 A와 B가 각각 1을 읽은 뒤 성공으로 처리하면 실제 자리 하나에 성공 기록 둘을 만들 수 있다.

이 단원은 종이에서 읽기·판단·쓰기 순서를 정한 경쟁 반례다. 실제 CPU의 모든 명령이나 C#의 모든 실행 순서를 관찰한 것은 아니다. 빠른 실행 한 번이 정상이라고 경쟁 가능성이 없다고 판단하지 않는다.

조건과 갱신을 같은 구간에 둔다

전용의 같은 잠금 객체 gate를 모든 관련 경로에서 사용하고 검사와 감소를 하나의 lock 구간에 둔다. A가 먼저 잠금을 잡고 1을 0으로 바꾼 뒤 B가 진입하면 B는 0을 보고 실패한다.

검사만 잠금 안에서 하고 감소를 밖에서 하면 두 작업이 검사 사이를 통과하는 문제가 남는다. 각 요청이 서로 다른 new object를 잠금으로 쓰는 것도 같은 공유 상태를 보호하지 못한다. 잠금은 모든 갱신 경로가 따르는 공통 계약이어야 한다.

짧은 구간과 실패 경로

lock은 정상 종료뿐 아니라 예외로 구간을 나가도 잠금을 해제하도록 구성된다. 그렇다고 이미 수정한 여러 값을 자동으로 이전 상태로 돌리는 데이터 트랜잭션은 아니다. 변경 순서와 불변 조건도 정해야 한다.

잠금을 잡은 채 오래 걸리는 외부 작업을 수행하면 다른 요청을 막을 수 있다. lock 본문에는 await를 쓸 수 없으므로 비동기 외부 작업과 짧은 상태 확정을 나누고 필요한 재검사를 계획한다. 실제 예약·네트워크·컴파일은 수행하지 않았다.

중간 과정을 따라가는 예제

좌석 1개에서 A와 B가 읽기·검사·남은 수 쓰기를 수행한다. 각각 읽은 값에서 1을 빼서 쓴다고 정한다. 무잠금 일정과 공통 gate의 전체 구간 잠금을 비교한다.

  1. 무잠금 일정: A가 1을 읽고 B도 1을 읽는다. 둘 다 양수 검사에 통과한다.

  2. A가 0을 쓰고 B도 0을 쓴다. 남은 수는 0이지만 성공 기록은 2개다.

  3. 전체 구간 잠금 일정: A가 1을 읽고 0으로 감소해 성공한 뒤 해제한다.

  4. B는 그 뒤 0을 읽어 실패한다. 성공 기록은 1개다.

무잠금 반례는 남은 수 0·성공 2개, 같은 gate로 전체 구간을 보호하면 이 일정에서 남은 수 0·성공 1개다.

안전한 사전 갱신 두 번이면 값 계산 함수도 두 번만 호출될까?

앞 본문은 GetOrAdd의 값 생성 함수가 중복 실행될 수 있다고 설명했다. 새 입력은 이미 key K에 정수 10이 있는 ConcurrentDictionary이며 두 호출 A와 B가 AddOrUpdate의 갱신 함수로 old + 1을 사용한다. 새 손모형의 순서를 고정한다. A가 10을 읽어 11을 계산하지만 아직 반영하지 않는다. B도 10에서 11을 계산하고 자기 갱신을 반영한다. A가 낡은 계산을 반영하려 할 때 재시도가 필요해 현재 11을 읽고 12를 계산하여 반영한다.

이 허용된 재시도 이력에서는 사전 값이 10 → 11 → 12로 변하며 업무 갱신은 두 번이다. 하지만 사용자 갱신 함수는 A의 첫 계산, B의 계산, A의 재계산으로 세 번 호출된다. 함수 안에서 외부 청구를 수행하면 함수 호출 수를 업무 수로 착각할 수 있다. 공식 계약은 위 이력이 모든 실행에서 반드시 나온다고 보장하지 않지만 갱신 함수의 여러 실행과 잠금 밖 호출을 허용한다.

따라서 갱신 함수는 부작용 없는 값 계산으로 설계하고 업무 효과에는 별도 식별자·중복 처리 계약을 둔다. 갱신에 사용한 old를 수정하는 가변 객체라면 재시도가 원래 객체를 이미 훼손할 수 있다. 여기의 old는 불변 정수이므로 그런 별칭 변화가 없다는 조건을 명시했다.

사전의 내부 슬롯 안전성과 값 객체의 내부 안전성도 다르다. K에 List<int> 참조를 저장했다고 해서 서로 다른 호출의 List.Add가 자동으로 같은 보호를 받지는 않는다. 사전은 정수·불변 값의 교체나 자체 보호를 갖춘 객체를 저장할 수 있지만 모든 가변 대상의 쓰기를 대신 직렬화하지 않는다. 새 라이브러리 실행은 하지 않았다.

안전성의 범위를 정한다

일반 List나 Dictionary를 여러 스레드가 동시에 수정할 때는 별도의 동기화 계약이 필요하다. ConcurrentQueue 같은 컬렉션은 동시 사용을 위한 개별 연산을 제공한다. 자료 구조 이름에 안전이 붙어도 주변 코드의 모든 판단이 자동 원자화되지는 않는다.

자체 큐 [7]에서 A가 Count가 양수라고 확인한 뒤 B가 7을 먼저 꺼낼 수 있다. A가 나중에 꺼내는 시도는 실패할 수 있다. 실패를 반환하는 TryDequeue의 결과를 검사해야 한다.

관찰 대신 시도 결과를 판단한다

큐가 비어 있을 가능성을 정상 상태로 취급하고 TryDequeue가 true일 때만 반환 항목을 처리한다. false이면 대기·종료·다른 작업 중 계약에 맞는 선택을 한다. 실패 때의 out 값을 정상 항목으로 처리하지 않는다.

이 자체 일정에서는 B의 성공 항목 7이 한 번 처리되고 A는 실패 분기로 간다. A와 B 중 누가 먼저 성공할지는 일정을 별도로 주지 않으면 확정할 수 없다. Count는 미래의 예약권이 아니다.

사전 안과 함수 밖의 경계

ConcurrentDictionary는 TryAdd·TryUpdate처럼 조건을 포함한 연산을 제공한다. 키가 없음을 확인하고 별도의 추가를 하는 두 호출은 하나의 독점 계약이 아니다. 원하는 조건에 맞는 단일 연산과 반환값을 사용한다.

GetOrAdd나 AddOrUpdate에 넘긴 함수는 내부 잠금 밖에서 실행될 수 있다. 자체 일정에서 두 함수가 각각 값을 계산했어도 사전에 채택되는 값은 하나일 수 있다. 함수 안의 결제·알림을 정확히 한 번 수행한다고 기대하지 말고 중복 가능한 계산과 외부 부작용을 분리한다.

허가를 얻지 못한 작업의 finally가 왜 활성 상한을 깨뜨릴까?

앞 본문은 두 허가로 독립 작업을 제한했다. 새 사례는 초기값과 최대값이 모두 2인 SemaphoreSlim이다. A와 B가 허가를 하나씩 얻어 활성이고 CurrentCount는 0이다. C는 시간 제한이 있는 WaitAsync를 호출했지만 false로 완료되어 허가를 얻지 못했다. 잘못된 finally가 C에서도 Release를 호출하면 CurrentCount가 1이 된다.

이 순간 A/B가 아직 허가를 소유하므로 활성 두 개와 남은 허가 하나의 합은 3이다. 새 D가 허가를 얻으면 활성 세 개가 된다. 최대값 2는 반환된 카운트가 최대값을 넘는지 검사하는 조건일 뿐, 누가 앞서 얻었는지 자동으로 증명하지 않는다. C의 잘못된 반환 시점에는 카운트 0에서 1로 늘어나므로 그 즉시 최대 초과 예외가 반드시 발생한다고 주장할 수 없다.

정상 설계는 기다림이 true로 완료된 뒤에만 획득 사실을 기록하고, 그 작업의 실행 범위를 try/finally로 둘러 한 번 반환한다. 기다림이 false이거나 취소 예외로 끝나면 얻지 않은 허가를 반환하지 않는다. 작업 본문이 예외를 던져도 실제 획득 뒤라면 finally로 반환한다. 이 소유 장부와 업무 결과 장부는 별도다.

활성 상한만 맞춰도 대기 작업을 무제한 생성할 수 있다. 별도 가상 모델에서 대기 항목 하나의 관리 비용을 64바이트로 정하고 10000개를 한 번에 만들어 보관하면 관리 비용은 640000바이트다. 창 크기 4에서 생성/보관을 제한하면 이 비용 항목은 256바이트다. 입력·결과·실제 Task 객체·작업 버퍼는 제외한 자체 비용 항목이며 실제 .NET 메모리 측정이 아니다. SemaphoreSlim은 FIFO를 보장하지 않아 처리 순서 요구는 별도로 설계한다.

기다릴 작업들을 묶는다

WhenAll은 제공한 작업들의 완료를 나타내는 Task를 만든다. 그것만으로 작업들을 새로 생성하거나 동시 실행 수를 제한하지 않는다. 이미 시작한 작업들이 언제 끝나는지와 결과를 어떻게 받는지를 나누어 설명한다.

자체 목록 [A, B, C]의 결과가 각각 2, 4, 6이고 완료는 B → C → A라고 정하자. 모두 정상 완료한 Task<T>의 WhenAll 결과 배열은 제공한 순서 [2, 4, 6]이다. 완료 순서대로 정렬하는 함수는 아니다.

작업 수의 별도 계약

실행 구간에 동시에 진입할 수 있는 수를 SemaphoreSlim의 허가 수로 제한하는 모형을 쓸 수 있다. 허가를 획득한 뒤 실행하고, 획득에 성공한 경로는 finally에서 정확히 한 번 Release한다.

WaitAsync의 취소나 실패로 획득하지 못한 경로에서 무조건 Release하면 허가 계약이 깨진다. 또한 작업 구간 수를 제한해도 대기 Task를 무한히 생성하는 설계의 메모리 문제까지 해결하지 않는다. 큰 입력은 작업 생성량 자체도 제한할 수 있어야 한다.

시간과 상태를 가정해 계산한다

자체 비용 모형에서 A/B/C/D가 각각 3/2/4/1초 걸리고 제한이 2개라고 하자. 대기 순서 A → B → C → D, 진입·전환 비용 0, 작업 간 간섭 없음으로 정하면 A/B가 0초에 시작한다.

B가 2초에 끝나 C가 2~6초, A가 3초에 끝나 D가 3~4초에 실행되어 전체 완료는 6초다. 실제 SemaphoreSlim은 대기 순서의 FIFO를 보장하는 스케줄러로 설명하지 않는다. 실패한 작업이 있으면 WhenAll의 결합 상태는 실패이며, 실패가 없고 취소가 있으면 취소다.

작업 A가 B를 기다리고 B도 A를 기다리면 시간이 지나기만 해도 풀릴까?

준비 개념과 학습 목표

준비 개념

  • 잠금

  • await와 대기

  • UI 실행 경로

학습 목표

  • 순환 대기를 화살표로 설명한다.

  • 단일 실행 경로의 동기 대기와 continuation을 구별한다.

  • 공유 수정 없이 결과를 모으는 대안을 제시한다.

await로 스레드를 비워도 자원 의존 고리는 남을 수 있을까?

앞 본문은 UI 스레드에서 Result로 기다리면 같은 UI 문맥으로 돌아와야 할 continuation이 막힐 수 있다고 설명했다. 새 사례는 용량 하나의 비동기 허가 S다. 요청 U가 S를 얻고 작업 W를 시작한 뒤 W를 await한다. W도 완료 전에 같은 S를 얻어야 한다. U는 W가 끝난 뒤 finally에서 S를 반환할 계획이다.

스레드를 막지 않는 await라도 U는 S를 아직 소유한다. 의존은 U가 W 완료를 기다리고, W는 S를 기다리며, S는 U가 반환해야 사용할 수 있다는 고리다. U의 스레드가 비어 다른 일을 처리할 수 있다는 사실은 S를 반환했다는 뜻이 아니다. 문맥 포착을 생략하는 ConfigureAwait(false)도 이 자원 소유 관계를 제거하지 않는다.

수정 정책은 보호 구간에서 입력 snapshot만 만들고 S를 반환한 뒤 W를 기다린다. W는 필요한 S를 얻어 처리하고 반환할 수 있다. 그러나 기다리는 동안 원래 상태가 바뀔 수 있으므로 결과 게시 전에 버전 조건을 재검증한다. 새 상태 (값 10, 버전 4)에서 계산 후보 12를 만들고 기다리는 동안 다른 요청이 (20, 5)를 게시했다면 버전 4를 기대한 결과는 거절한다. 값만 보고 무조건 12를 게시하면 새 20을 잃는다.

UI 문맥 고리와 S 소유 고리는 원인이 다르다. 문맥 포착을 피하는 수정은 해당 문맥 의존을 제거할 수 있지만 UI 접근 자체가 필요한 코드에 무조건 적용하는 해결책은 아니다. 애플리케이션 문맥/자원/업무 버전 조건을 각각 확인해야 한다. 실제 UI·Task·경쟁 실행은 하지 않았다.

보유한 것과 기다리는 것을 그린다

자체 일정에서 A는 잠금 X를 갖고 Y를 기다리며 B는 Y를 갖고 X를 기다린다. 둘 다 다른 잠금을 얻기 전 자기 잠금을 놓지 않고 취소·외부 해제도 없다고 정하면 진행할 수 없는 순환 대기다.

두 잠금이 필요하면 모든 경로가 X 다음 Y 같은 공통 획득 순서를 따르는 방법을 검토한다. 한 경로만 순서를 바꿔도 계약이 깨진다. 이 방법은 두 잠금 모형의 순환을 막는 조건이지 모든 종류의 교착을 자동 증명한 것은 아니다.

UI 경로를 막으면 돌아올 곳이 없다

자체 단일 UI 실행 경로 U에서 비동기 작업을 시작하고 아직 완료되지 않은 Task의 Result를 동기로 기다린다고 하자. 그 작업의 남은 continuation이 U에서 실행되어야 완료되는 조건이면 U는 완료를 기다리고 완료는 U의 실행을 기다린다.

await로 UI 경로를 반환하면 필요한 남은 동작을 실행할 기회가 생긴다. 모든 Result가 언제나 교착이라는 말은 아니며 완료 상태·실행 context 조건이 중요하다. ConfigureAwait나 Task.Run 하나를 모든 교착의 자동 해결로 선언하지 않는다.

공유 누적을 줄이는 설계

각 작업이 공유 total에 값을 더하면 작은 코드에도 경쟁이 생길 수 있다. 작업이 자기 결과를 반환하고 모든 정상 결과가 모인 뒤 한 경로에서 합산하는 대안을 사용하면 그 공유 수정 구간을 줄일 수 있다.

  4. ④ U가 S를 반환한 뒤 W를 기다려야 이 자원 고리가 제거된다. 현재 버전 5가 기대 버전 4와 달라 후보 12는 거절하고 상태 (20, 5)를 보존한다.
