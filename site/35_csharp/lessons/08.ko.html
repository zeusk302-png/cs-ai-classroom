IEnumerable·IEnumerator

값을 만드는 방법과 지금 몇 번째를 읽는지는 같은 객체일까?

두 변수가 가리키는 열거자는 서로 다른 읽기 위치를 가질까?

앞 본문의 두 GetEnumerator 호출은 배열을 읽는 서로 다른 열거자를 얻었다. 이제 같은 열거자를 e와 alias 두 변수에 저장한다. 자체 읽기 대상은 변경하지 않는 [10,20,30]이며 e가 한 번 MoveNext하면 Current는 10이다. alias가 MoveNext하면 같은 열거자의 위치가 이동하므로 e.Current도 20이다. 변수 이름 두 개와 상태 객체 두 개를 구별해야 한다.

Current 읽기는 다음 항목을 요구하는 작업이 아니다. 유효한 위치에서 Current를 두 번 읽으면 같은 현재 항목을 얻는다. 반면 MoveNext를 두 번 호출하면 두 항목을 지나간다. 첫 MoveNext 전과 false를 반환한 뒤의 Current는 계약상 사용할 수 있는 값이 아니다. 0이라는 값이 들어 있다는 사실과 false라는 종료 신호도 분리한다.

IEnumerable라는 인터페이스만으로 모든 구현이 독립 재생 가능한 것은 아니다. 아래 비교는 배열에서 얻은 독립 열거자와 같은 열거자 별칭의 두 정책을 명시한다. 같은 장치 커서를 공유하는 별도 구현의 반복 가능성은 그 구현 계약을 읽어야 한다. Reset 지원을 가정하지 않으며 수동으로 얻은 열거자의 정리 책임도 없애지 않는다. 실제 C# 열거는 수행하지 않았다.

원천과 진행 위치

IEnumerable<T>는 GetEnumerator로 열거자를 얻는 원천 역할이다. IEnumerator<T>는 한 번의 순회에서 현재 위치를 진행시키는 역할이며 MoveNext와 Current를 제공한다. 목록 전체를 이미 저장한 경우도, 값을 필요할 때 생성하는 경우도 이 공통 인터페이스로 읽을 수 있다.

새 열거자는 보통 첫 원소 이전에 있다. MoveNext가 true일 때에만 이번 Current를 읽는다. 첫 이동 전이나 종료 false 뒤 Current의 값에 기대지 않는다. 모든 IEnumerable이 반복 가능하거나 스냅샷을 제공한다고 인터페이스만으로 보장하지는 않는다.

이동 성공과 값 읽기

MoveNext는 다음 값이 존재하는지 bool로 알리고 위치를 이동한다. Current는 그 이동에서 준비된 값을 읽는 역할이다. Current를 두 번 읽는 것을 두 번 이동으로 계산하면 안 된다. 구체 구현이 getter에서 어떤 부작용을 갖는지는 별도 계약이다.

자체 순수 배열 [4,7]의 열거자를 가정하면 이동 결과 true,true,false와 두 Current 값4,7이 나온다. false는 숫자0이 마지막 원소라는 뜻이 아니라 끝이라는 상태다. 값0이 실제 원소라면 true와 함께0을 읽을 수 있다.

using var e = values.GetEnumerator();
while (e.MoveNext()) {
    var x = e.Current;
}

foreach의 자원 경계

foreach는 원천에서 열거자를 얻고 반복 이동·Current 읽기를 수행한다. 필요한 disposal을 finally 경계에서 처리하므로 break로 그만둬도 열거자 자원 정리가 가능하다. generic IEnumerator<T>는 IDisposable과 연결된다.

언어의 foreach는 배열이나 GetEnumerator 패턴 등도 지원하므로 모든 경우가 동일한 인터페이스 호출 형태라는 완전한 명세는 아니다. 이 단원에서는 IEnumerable<int>/IEnumerator<int> 동기 경로만 다룬다. 비동기 원천은 IAsyncEnumerable<T>와 await foreach라는 별도 계약이다.

  3. e1의 둘째 이동 true는7을 준비한다.

yield와 상태기계

함수가 값을 하나 반환했는데 다음 호출은 왜 중간에서 이어질까?

준비 개념과 학습 목표

준비 개념

  • 함수 호출과 지역 변수

  • 열거자 MoveNext

  • 자원 정리

학습 목표

  • yield 전후 실행 위치와 지역 상태를 추적한다.

  • 조기 종료와 finally의 차이를 설명한다.

입력 오류를 즉시 알려야 하는 함수 안에 yield를 넣으면 언제 실패할까?

iterator 메서드 Late(n)는 본문 맨 앞에서 n<0이면 ArgumentOutOfRangeException을 던지고, 그렇지 않으면 yield return n을 한다고 하자. Late(-1) 호출 자체는 iterator 본문을 실행하지 않으므로 그 검사도 연기된다. 첫 MoveNext가 검사를 실행하며 예외를 낸다. 문장 위치가 맨 앞이라는 사실과 호출 시 실행이라는 사실은 같지 않다.

즉시 검사가 필요한 자체 Early(n)는 yield가 없는 일반 함수다. 먼저 n을 검사하고 정상일 때만 별도 iterator Core(n)를 반환한다. 이 구조에서 Early(-1)은 일반 함수 호출에서 실패한다. Core의 본문과 자원 사용은 여전히 열거 시점에 시작한다. 아래 단계는 호출/MoveNext/Dispose를 분리한 손모형이며 생성된 상태기계의 실제 필드 이름을 주장하지 않는다.

자체 iterator Resource에는 try 안에서 로그 open, yield return 1, 로그 resume, 예외 E가 있고 finally에서 close를 기록한다. 첫 값 뒤 foreach에서 break하면 Dispose 경로로 close는 실행되지만 resume과 E는 실행하지 않는다. 다시 MoveNext를 요구하면 resume 후 E와 close가 발생한다. 처음부터 열거하지 않은 경우 open 자체를 실행하지 않았으므로 close 로그도 없다.

멈추는 반환과 끝내는 반환

iterator의 yield return은 값을 하나 제공하고 실행을 일시 중단한다. 다음 MoveNext에서 그 yield 바로 다음 문장부터 재개한다. yield break 또는 본체 끝에 도달하면 열거가 종료된다. 일반 return으로 목록 전체를 반환하는 함수와는 다른 흐름이다.

컴파일러는 실행 위치·현재 값·살아 있는 지역 변수를 보존하는 상태기계로 이 동작을 구현할 수 있다. 실제 생성 클래스 이름이나 정수 상태 번호는 구현 세부이므로 교재의 시작/첫 yield/종료 상태가 실제 bytecode 관측 결과라는 뜻은 아니다.

지역 값이 이어지는 상태

아래 함수의 x는 첫 이동에서2로 초기화되고2를 제공한다. 다음 이동은 x+=3을 실행해5를 제공한다. 같은 열거자가 이어질 때 지역 x가 보존된다. 다른 새 열거자에서는 다시 자기 x=2로 시작한다.

본체 안 print나 예외도 소비 시점까지 미뤄질 수 있다. iterator를 반환하는 바깥 일반 함수에서 실행한 검사와 iterator 본체의 검사는 시점이 다르다. 여기 예제는 직접 yield 본체이며 호출만 했을 때 안쪽 이벤트가 시작되지 않는다.

IEnumerable<int> Items() {
    int x = 2;
    yield return x;
    x += 3;
    yield return x;
}

중단 동안 자원이 살아 있다

using으로 얻은 자원은 yield에서 중단됐다고 즉시 정리되지 않는다. 이어 실행하는 데 필요할 수 있기 때문이다. 본체의 종료나 열거자의 Dispose에서 관련 finally가 실행되어 정리한다.

foreach의 break는 열거자를 정리하는 경로를 사용한다. 하지만 열거자를 수동으로 얻어 버려 놓고 Dispose하지 않으면 같은 정리 보장을 즉시 주장할 수 없다. yield 다음의 일반 문장이 조기 Dispose에서도 꼭 실행되는 것은 아니며 finally와 구별한다.

같은 열거 중 조건을 바꾸면 결과는 어느 순간의 자료를 나타낼까?

자체 지연 iterator Above(data,()=>limit)는 고정 배열 [2,4,6]을 앞에서부터 읽고 각 항목을 검사할 때 현재 limit보다 크면 yield한다. 배열은 바꾸지 않지만 limit는 바꿀 수 있다. limit=3으로 첫 값 4를 얻은 뒤 limit=7로 바꾸면 남은 6은 탈락한다. 결과 [4]는 처음 조건의 전체 결과 [4,6]도, 마지막 조건의 전체 결과 []도 아니다.

반복하는 계산을 만드는 것과 하나의 관찰 결과를 보존하는 것은 다르다. 매번 새 열거자는 매번 당시 limit를 읽어 다시 검사한다. 조건을 고정하고 싶으면 iterator를 만들기 전에 정수 fixedLimit를 복사하고 이후 그 복사 변수를 변경하지 않는 계약을 둔다. ToList는 호출 중 실제로 전체 계산을 요구하므로 실패하거나 끝나지 않을 수도 있다.

ToList가 반환한 리스트가 객체 내부까지 복제하는 것은 아니다. 자체 Box A.Value=2, B.Value=4를 담은 배열을 ToList로 모으면 목록에는 A와 B의 같은 참조가 있다. 이후 A.Value=9이면 모은 목록의 첫 객체도 9를 읽는다. 숫자를 보존하려면 그 시점에 Value를 읽어 int 목록을 만들고, 입력 갱신/동시 관찰 정책도 따로 명시한다. 아래는 단일 스레드의 지정 사건만 다룬다.

계산법과 계산 결과

지연 실행은 결과를 요구할 때 작업을 수행하는 방식이다. iterator 본체를 호출해 얻은 IEnumerable은 흔히 계산법을 담고 값 전체를 아직 만들지 않는다. 여러 번 열거하면 본체를 여러 번 실행할 수 있다.

지연이라는 말이 자동 캐시를 뜻하지 않는다. 두 순회가 같은 원천 상태를 보았는지, 시간·외부 입력·부작용이 달라졌는지 확인한다. 반복 불가능한 원천이나 custom 캐시도 있어 모든 IEnumerable에 같은 반복 규칙을 강제할 수는 없다.

원본 참조를 나중에 읽기

아래 Twice는 배열 객체를 받아 각 원소를 소비 시점에 읽는다. 변수 이름 data를 새 배열로 재대입한 경우와 전달한 기존 배열의 원소를 바꾼 경우가 다르다. 인자 배열 참조와 실제 원소 상태를 분리한다.

이 예제는 순회 중에는 원천을 바꾸지 않고 순회 사이에만 바꾼다. 동시 변경을 포함하면 별도 정책이 필요하다. List의 fail-fast, 배열 변경 관측, 원격 스트림의 변경은 동일 계약이 아니므로 일반 예측으로 합치지 않는다.

IEnumerable<int> Twice(int[] source) {
    foreach (int x in source) yield return 2*x;
}

100만 줄을 다 읽기 전에 앞의 두 유효 값만 받을 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 열거자

  • 조건 필터

  • 누적 합

학습 목표

  • 필터·변환·조기 소비의 원천 처리량을 계산한다.

  • streaming과 모든 연산의 상수공간 보장을 구별한다.

출력 두 개만 필요하면 입력도 두 개만 읽으면 될까?

자체 필터는 [1,3,5,6,8,10]을 순서대로 검사하고 짝수만 반환한다. 소비자는 두 번째 반환 즉시 중단하며 미리 읽기를 하지 않는다. 첫 출력 6을 위해 입력 네 개를 읽고, 둘째 출력 8을 위해 하나를 더 읽어야 한다. 출력 2개와 입력 검사 5개는 다른 분모다. 마지막 10은 이 경로에서 읽지 않는다.

무한 홀수 입력을 같은 필터에 연결하면 출력 하나를 요구한 첫 MoveNext조차 끝나지 않을 수 있다. 출력 수 제한은 검사 수 제한이 아니다. 자체 검사 예산 b=3을 두면 처음 세 항목 1,3,5를 검사한 뒤 예산 종료로 멈추고 출력은 0개다. 입력 종료와 예산 종료를 별도 상태로 보고해야 필요한 결과를 다 얻었다는 오해를 피한다.

상수 크기 처리 상태라는 말도 연산 종류에 달려 있다. 인접한 같은 값만 한 번 내보내는 Adjacent는 직전 값 하나를 기억하면 된다. 전체 중복을 없애는 Global은 지금까지 본 서로 다른 값을 기억해야 한다. [A,A,B,A]에서 Adjacent 출력 [A,B,A]와 Global 출력 [A,B]는 다른 계약이다. 아래 항목 검사/기억 수는 논리 모형이며 실제 파일·네트워크 버퍼나 메모리 바이트를 측정한 수가 아니다.

  • 필터와 조기 중단의 비용

    입력 검사 수와 실제 반환 수를 별도로 센다.

  • 다음 출력 요청의 작업

    MoveNext 한 번이 여러 입력을 내부 소비할 수 있다.

한 값씩 연결하는 경로

streaming은 원천 값을 순차적으로 받아 필요한 만큼 처리하는 흐름이다. 필터는 조건을 만족하는 값만 다음 단계로 보내고 변환은 그 값을 새 값으로 바꾼다. 다음 결과 하나를 내기 위해 원천 여러 개를 읽을 수도 있다.

소비자가 결과 두 개만 요구하면 그 두 결과를 만들 만큼만 원천을 진행하는 교육 iterator를 설계할 수 있다. 그러나 요청 결과 수2와 입력 소비 수2는 같지 않을 수 있다. 파일·네트워크 원천은 자원 수명과 오류·취소도 함께 관리해야 한다.

조기 종료와 처리량

원천 [3,−1,4,8,2]에서 짝수만 골라 두 배를 만든다고 하자. 첫 출력8은3/−1/4를 검사한 뒤 나온다. 둘째16은 다음8에서 나온다. 그때 소비자가 break하면 뒤2는 이 자체 흐름에서 읽지 않는다.

원천 iterator가 한 값씩 제공하고 불필요한 lookahead가 없다는 조건이다. 버퍼를 미리 읽는 입출력 계층의 바이트 처리량까지 동일 수치라고 할 수는 없다. 코드 수준 원소 평가와 OS·네트워크 실제 읽기를 구별한다.

기억하는 양을 따로 계산하기

이 필터와 변환은 현재 값과 몇 개의 상태만 필요해 전체 입력을 저장하지 않는다. 누적합도 하나의 합 상태로 진행할 수 있다. 모든 streaming 연산이 그런 것은 아니다. 전체 정렬이나 모든 고유값 기억은 입력량에 따라 저장공간이 늘 수 있다.

무한 원천에서 조건을 만족하는 값이 없으면 필터의 첫 출력도 끝나지 않을 수 있다. 지연만으로 응답 기한이 생기지 않는다. 실제 서비스는 한도·취소·timeout·자원 정리를 설계하며 여기서는 유한 종이 목록과 확정 검사 비용만 사용한다.

위 자체 원천 [3,−1,4,8,2]에서 EvenTwice의 첫 두 결과만 foreach로 받고 break한다. 원천 검사 수·변환 수·출력과 남은 상태를 구하라. 불필요한 lookahead는 없다.

  1. 3은 홀수라 버리고 −1도 짝수가 아니라 버린다.

  2. 4가 첫 짝수라 2×4=8을 제공한다. 이때 검사3회·변환1회다.

  3. 다음8은 2×8=16으로 둘째 결과다. 검사4회·변환2회다.

  4. 소비가 끝나므로 원천2는 읽지 않는다. foreach의 열거자 정리 경로를 사용한다.

예상 출력8/16, 입력 검사4회·변환2회이며 마지막2는 이 코드 경로에서 미소비다.

인접 중복과 전체 중복

새 [A,A,B,A]에서 Adjacent와 Global의 출력과 기억할 정보를 비교하라.

  1. Adjacent는 두 번째 A만 바로 앞 A와 같아 생략한다.

  2. Global은 마지막 A도 이미 본 값이므로 생략한다.

Adjacent는 [A,B,A]이고 직전 값 한 개를 기억한다. Global은 [A,B]이고 이 입력에서 서로 다른 값 A,B 두 개를 기억한다.

다른 문제에 적용하기

가상 미리보기는 원본 [1,3,5,6,8,10]을 바꾸지 않고 각 검사 때 현재 limit보다 큰 짝수만 반환한다. 처음 limit=3이다. 소비자는 첫 값 6을 받은 즉시 limit=9로 바꾸고 두 번째 값까지 요청한다. 선읽기는 없으며 iterator 본문은 처음 시작에 open, finally에 close를 기록한다. (1) 반환과 전체 검사 수 및 두 번째 값 뒤 즉시 Dispose한 로그를 구하라. (2) 매번 새 원본/iterator에서 fixedLimit=3을 복사하고 전체를 ToList로 정상 완료한 경우를 비교하라. (3) 매번 새 원본에서 검사 예산 3을 적용하면 결과와 종료 사유는? (4) published=[99]를 유지하며 후보 계산이 첫 값 뒤 실패할 수도 있을 때 공개 정책과 보존 범위를 설계하라. 각 비교는 독립 초기 상태이며 실서비스나 파일을 실행하지 않는다.

풀이와 답 확인

  1. 첫 조건 3에서 1,3,5가 탈락하고 6을 반환하여 누적 검사 4회다. 조건을 9로 바꾸면 8이 탈락하고 10이 통과한다. 두 값은 [6,10]이며 총 검사 6회다.

  2. 두 번째 값 뒤 추가 MoveNext 없이 Dispose하므로 finally의 close를 실행한다. 본문의 별도 재개 로그가 없다는 자체 계약에서 로그는 [open,close]다.

  3. 고정 조건 3의 전체 계산은 [6,8,10]이며 검사 6회다. ToList가 정상 완료한 int 목록을 보존한다.

  4. 검사 예산 3의 독립 경로는 1,3,5만 검사하므로 출력 []이며 입력 끝이 아니라 예산 소진이다.

  5. 새 candidate를 완성한 뒤 published=candidate를 수행한다. 실패하면 기존 [99]를 유지하지만 open/close나 외부 생산 효과까지 취소된다고 주장하지 않는다.
