소단원 8.1

IEnumerable·IEnumerator

값을 만드는 방법과 지금 몇 번째를 읽는지는 같은 객체일까?

준비 개념과 학습 목표

준비 개념

  • 인터페이스

  • 목록과 반복문

  • 객체 상태

학습 목표

  • 열거 가능한 원천과 열거자의 역할을 구별한다.

  • MoveNext의 반환과 Current를 순서대로 추적한다.

원천과 진행 위치

IEnumerable<T>는 GetEnumerator로 열거자를 얻는 원천 역할이다. IEnumerator<T>는 한 번의 순회에서 현재 위치를 진행시키는 역할이며 MoveNext와 Current를 제공한다. 목록 전체를 이미 저장한 경우도, 값을 필요할 때 생성하는 경우도 이 공통 인터페이스로 읽을 수 있다.

새 열거자는 보통 첫 원소 이전에 있다. MoveNext가 true일 때에만 이번 Current를 읽는다. 첫 이동 전이나 종료 false 뒤 Current의 값에 기대지 않는다. 모든 IEnumerable이 반복 가능하거나 스냅샷을 제공한다고 인터페이스만으로 보장하지는 않는다.

이동 성공과 값 읽기

MoveNext는 다음 값이 존재하는지 bool로 알리고 위치를 이동한다. Current는 그 이동에서 준비된 값을 읽는 역할이다. Current를 두 번 읽는 것을 두 번 이동으로 계산하면 안 된다. 구체 구현이 getter에서 어떤 부작용을 갖는지는 별도 계약이다.

자체 순수 배열 [4,7]의 열거자를 가정하면 이동 결과 true,true,false와 두 Current 값4,7이 나온다. false는 숫자0이 마지막 원소라는 뜻이 아니라 끝이라는 상태다. 값0이 실제 원소라면 true와 함께0을 읽을 수 있다.

using var e = values.GetEnumerator();
while (e.MoveNext()) {
    var x = e.Current;
}

foreach의 자원 경계

foreach는 원천에서 열거자를 얻고 반복 이동·Current 읽기를 수행한다. 필요한 disposal을 finally 경계에서 처리하므로 break로 그만둬도 열거자 자원 정리가 가능하다. generic IEnumerator<T>는 IDisposable과 연결된다.

언어의 foreach는 배열이나 GetEnumerator 패턴 등도 지원하므로 모든 경우가 동일한 인터페이스 호출 형태라는 완전한 명세는 아니다. 이 단원에서는 IEnumerable<int>/IEnumerator<int> 동기 경로만 다룬다. 비동기 원천은 IAsyncEnumerable<T>와 await foreach라는 별도 계약이다.

중간 과정을 따라가는 예제

자체 고정 원천 [4,7]에서 독립 열거자 e1/e2를 얻는다. e1.MoveNext(), e1.Current 두 번, e2.MoveNext(), e1.MoveNext(), e1.MoveNext()를 추적하라. Current는 유효 위치에서 순수하게 읽는다고 정한다.

  1. e1의 첫 이동은 true, Current는4다. 같은 위치에서 두 번 읽어도4/4이며 추가 이동은 없다.

  2. e2는 독립 첫 위치라 첫 이동 true, Current4다.

  3. e1의 둘째 이동 true는7을 준비한다.

  4. e1의 셋째 이동은false이고 이후 Current를 유효 값으로 읽지 않는다.

e1 값4,4 다음7; e2 첫 값4; e1 최종 이동false다. 열거자마다 위치가 독립인 자체 원천 조건이다.

힌트 보기

풀이 보기

오해와 반례

IEnumerable은 항상 모든 값을 저장한 재사용 가능한 목록이다.

값을 필요할 때 생성하거나 외부 입력을 한 번만 읽는 원천도 가능하다. 이 인터페이스는 열거 경로이며 저장·반복·스냅샷을 모두 보장하지 않는다.

소단원 8.2

yield와 상태기계

함수가 값을 하나 반환했는데 다음 호출은 왜 중간에서 이어질까?

준비 개념과 학습 목표

준비 개념

  • 함수 호출과 지역 변수

  • 열거자 MoveNext

  • 자원 정리

학습 목표

  • yield 전후 실행 위치와 지역 상태를 추적한다.

  • 조기 종료와 finally의 차이를 설명한다.

멈추는 반환과 끝내는 반환

iterator의 yield return은 값을 하나 제공하고 실행을 일시 중단한다. 다음 MoveNext에서 그 yield 바로 다음 문장부터 재개한다. yield break 또는 본체 끝에 도달하면 열거가 종료된다. 일반 return으로 목록 전체를 반환하는 함수와는 다른 흐름이다.

컴파일러는 실행 위치·현재 값·살아 있는 지역 변수를 보존하는 상태기계로 이 동작을 구현할 수 있다. 실제 생성 클래스 이름이나 정수 상태 번호는 구현 세부이므로 교재의 시작/첫 yield/종료 상태가 실제 bytecode 관측 결과라는 뜻은 아니다.

지역 값이 이어지는 상태

아래 함수의 x는 첫 이동에서2로 초기화되고2를 제공한다. 다음 이동은 x+=3을 실행해5를 제공한다. 같은 열거자가 이어질 때 지역 x가 보존된다. 다른 새 열거자에서는 다시 자기 x=2로 시작한다.

본체 안 print나 예외도 소비 시점까지 미뤄질 수 있다. iterator를 반환하는 바깥 일반 함수에서 실행한 검사와 iterator 본체의 검사는 시점이 다르다. 여기 예제는 직접 yield 본체이며 호출만 했을 때 안쪽 이벤트가 시작되지 않는다.

IEnumerable<int> Items() {
    int x = 2;
    yield return x;
    x += 3;
    yield return x;
}

중단 동안 자원이 살아 있다

using으로 얻은 자원은 yield에서 중단됐다고 즉시 정리되지 않는다. 이어 실행하는 데 필요할 수 있기 때문이다. 본체의 종료나 열거자의 Dispose에서 관련 finally가 실행되어 정리한다.

foreach의 break는 열거자를 정리하는 경로를 사용한다. 하지만 열거자를 수동으로 얻어 버려 놓고 Dispose하지 않으면 같은 정리 보장을 즉시 주장할 수 없다. yield 다음의 일반 문장이 조기 Dispose에서도 꼭 실행되는 것은 아니며 finally와 구별한다.

중간 과정을 따라가는 예제

자체 Items 본체 시작을start, 첫 yield 뒤를middle, 둘째 yield 뒤를end 이벤트로 표시한다. 호출 후 GetEnumerator, 세 번 MoveNext의 값과 이벤트를 추적하라.

  1. 호출과 GetEnumerator만으로 본체 start를 실행하지 않는다.

  2. 첫 MoveNext는start, x=2, yield2에서 중단하여true다.

  3. 둘째는middle과x=5, yield5에서true다.

  4. 셋째는end에 도달하고 끝으로false다.

순서: 첫 이동 start/값2, 둘째 middle/값5, 셋째 end/false. 실제 출력 실행이 아니다.

힌트 보기

풀이 보기

오해와 반례

yield return을 만나면 함수의 자원과 모든 지역 변수는 즉시 사라진다.

다음 이동에서x+=3을 수행하려면x=2와 재개 위치가 보존되어야 한다. 자원은 종료/Dispose의 finally 경계에서 정리한다.

소단원 8.3

지연 실행·반복 평가

질문을 적은 뒤 원본 값을 바꾸면 답은 적을 때 값일까 읽을 때 값일까?

준비 개념과 학습 목표

준비 개념

  • iterator

  • 배열 변경

  • 구체화 목록

학습 목표

  • 반복 평가와 캐시를 구별한다.

  • 원천 변경이 지연 결과에 미치는 영향을 추론한다.

계산법과 계산 결과

지연 실행은 결과를 요구할 때 작업을 수행하는 방식이다. iterator 본체를 호출해 얻은 IEnumerable은 흔히 계산법을 담고 값 전체를 아직 만들지 않는다. 여러 번 열거하면 본체를 여러 번 실행할 수 있다.

지연이라는 말이 자동 캐시를 뜻하지 않는다. 두 순회가 같은 원천 상태를 보았는지, 시간·외부 입력·부작용이 달라졌는지 확인한다. 반복 불가능한 원천이나 custom 캐시도 있어 모든 IEnumerable에 같은 반복 규칙을 강제할 수는 없다.

원본 참조를 나중에 읽기

아래 Twice는 배열 객체를 받아 각 원소를 소비 시점에 읽는다. 변수 이름 data를 새 배열로 재대입한 경우와 전달한 기존 배열의 원소를 바꾼 경우가 다르다. 인자 배열 참조와 실제 원소 상태를 분리한다.

이 예제는 순회 중에는 원천을 바꾸지 않고 순회 사이에만 바꾼다. 동시 변경을 포함하면 별도 정책이 필요하다. List의 fail-fast, 배열 변경 관측, 원격 스트림의 변경은 동일 계약이 아니므로 일반 예측으로 합치지 않는다.

IEnumerable<int> Twice(int[] source) {
    foreach (int x in source) yield return 2*x;
}

구체화가 만드는 경계

ToList 같은 구체화는 그 시점에 전체를 열거해 값을 저장한다. 저장한 정수 결과를 이후 읽는 일은 원천 iterator를 다시 실행하는 일과 다르다. 다만 참조 원소라면 목록 저장이 깊은 복사라는 보장은 없으며 객체 내부 변경은 공유될 수 있다.

무한 원천이나 매우 큰 원천을 전부 구체화하려 하면 끝나지 않거나 메모리 문제가 생길 수 있다. 필요한 범위만 소비하고 작업 횟수와 저장공간을 구분한다. 여기서는 유한 두 정수 배열과 순수 두 배 변환만 가정한다.

중간 과정을 따라가는 예제

자체 data=[1,2], q=Twice(data)다. q를 만들고 data[0]=3으로 바꾼 후 끝까지 순회한다. data[1]=4로 바꾸고 q를 다시 순회한다. 둘째 결과를 별도 int 목록 saved에 저장하고 data[0]=9로 바꾸면saved와q는?

  1. q 생성만으로 원소 변환을 수행하지 않는다. 첫 순회는[3,2]를 읽어[6,4]다.

  2. 둘째 순회는[3,4]를 읽어[6,8]이다. 자동 결과 캐시가 아니다.

  3. saved는 둘째 정수 결과[6,8]을 저장한다.

  4. data가[9,4]가 되면saved는[6,8] 그대로, 새 q순회는[18,8]을 예상한다.

첫[6,4], 둘째[6,8], 이후saved[6,8]과q[18,8]이다. 순회 중 변경은 없다.

소단원 8.4

streaming 데이터 처리

100만 줄을 다 읽기 전에 앞의 두 유효 값만 받을 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 열거자

  • 조건 필터

  • 누적 합

학습 목표

  • 필터·변환·조기 소비의 원천 처리량을 계산한다.

  • streaming과 모든 연산의 상수공간 보장을 구별한다.

한 값씩 연결하는 경로

streaming은 원천 값을 순차적으로 받아 필요한 만큼 처리하는 흐름이다. 필터는 조건을 만족하는 값만 다음 단계로 보내고 변환은 그 값을 새 값으로 바꾼다. 다음 결과 하나를 내기 위해 원천 여러 개를 읽을 수도 있다.

소비자가 결과 두 개만 요구하면 그 두 결과를 만들 만큼만 원천을 진행하는 교육 iterator를 설계할 수 있다. 그러나 요청 결과 수2와 입력 소비 수2는 같지 않을 수 있다. 파일·네트워크 원천은 자원 수명과 오류·취소도 함께 관리해야 한다.

조기 종료와 처리량

원천 [3,−1,4,8,2]에서 짝수만 골라 두 배를 만든다고 하자. 첫 출력8은3/−1/4를 검사한 뒤 나온다. 둘째16은 다음8에서 나온다. 그때 소비자가 break하면 뒤2는 이 자체 흐름에서 읽지 않는다.

원천 iterator가 한 값씩 제공하고 불필요한 lookahead가 없다는 조건이다. 버퍼를 미리 읽는 입출력 계층의 바이트 처리량까지 동일 수치라고 할 수는 없다. 코드 수준 원소 평가와 OS·네트워크 실제 읽기를 구별한다.

기억하는 양을 따로 계산하기

이 필터와 변환은 현재 값과 몇 개의 상태만 필요해 전체 입력을 저장하지 않는다. 누적합도 하나의 합 상태로 진행할 수 있다. 모든 streaming 연산이 그런 것은 아니다. 전체 정렬이나 모든 고유값 기억은 입력량에 따라 저장공간이 늘 수 있다.

무한 원천에서 조건을 만족하는 값이 없으면 필터의 첫 출력도 끝나지 않을 수 있다. 지연만으로 응답 기한이 생기지 않는다. 실제 서비스는 한도·취소·timeout·자원 정리를 설계하며 여기서는 유한 종이 목록과 확정 검사 비용만 사용한다.

IEnumerable<int> EvenTwice(IEnumerable<int> src) {
    foreach (int x in src)
        if (x % 2 == 0) yield return 2*x;
}

중간 과정을 따라가는 예제

위 자체 원천 [3,−1,4,8,2]에서 EvenTwice의 첫 두 결과만 foreach로 받고 break한다. 원천 검사 수·변환 수·출력과 남은 상태를 구하라. 불필요한 lookahead는 없다.

  1. 3은 홀수라 버리고 −1도 짝수가 아니라 버린다.

  2. 4가 첫 짝수라 2×4=8을 제공한다. 이때 검사3회·변환1회다.

  3. 다음8은 2×8=16으로 둘째 결과다. 검사4회·변환2회다.

  4. 소비가 끝나므로 원천2는 읽지 않는다. foreach의 열거자 정리 경로를 사용한다.

예상 출력8/16, 입력 검사4회·변환2회이며 마지막2는 이 코드 경로에서 미소비다.

종이와 본문으로 직접 해보기

첫 세 결과를 모두 받으면 검사/변환 수와 합은? 무한한 홀수 원천에서 첫 짝수를 기다리는 필터는 언제 끝나는가?

힌트 보기

마지막2까지 읽어4를 추가한다. 종료나 한도가 없는 무한 원천 조건을 확인한다.

풀이 보기

전체 출력8/16/4, 검사5회·변환3회, 합28이다. 무한 홀수 원천에서는 짝수 결과가 없어 첫 출력을 위한 진행이 끝나지 않을 수 있다. timeout은 이 iterator에 자동 추가되지 않는다.

오해와 반례

streaming이면 입력 크기와 무관하게 모든 처리가 상수 메모리와 정해진 시간에 끝난다.

모든 고유값을 저장하면 종류 수만큼 메모리가 필요하고 무한 홀수의 짝수 필터는 출력을 못 낼 수 있다. 연산과 입력 가정을 확인해야 한다.

한 단계 더
