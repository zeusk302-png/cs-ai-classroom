소단원 4.1

constructor와 access modifier

객체가 만들어지는 순간부터 유효한 점수를 갖게 하려면 어디에서 검사해야 할까?

준비 개념과 학습 목표

준비 개념

  • 클래스는 타입 정의, 인스턴스는 그 정의에 따라 만든 객체다. 같은 클래스로 서로 다른 객체를 만들 수 있다.

  • assembly는 여러 .cs 파일을 컴파일하여 만든 .dll이나 .exe의 경계다. 소스 폴더와 동일한 말이 아니다.

  • 정수 점수는0..100이라는 자체 교육 규칙을 사용한다. 실제 성적이나 학생 정보를 저장하지 않는다.

학습 목표

  • 생성자의 초기화와 접근 제한을 구분한다.

  • 유효 생성과 실패 생성, 객체 별칭을 종이로 추적한다.

생성자의 약속

인스턴스 생성자는 new로 객체를 만들 때 초기 상태를 정하는 멤버다. 타입과 같은 이름을 쓰고 반환 타입을 적지 않는다. 클래스가 어떤 생성자도 선언하지 않으면 일반적인 비정적 클래스에는 매개변수 없는 생성자가 제공되지만, 인자를 받는 생성자를 직접 선언하면 그것만으로 매개변수 없는 생성자가 추가되지는 않는다. 초기화 방식과 호출할 생성자를 명확히 적는다.

여기서는 Score(int initial)가0≤initial≤100을 검사하여 유효한 경우에만 값을 저장한다고 정한다. 범위를 벗어나면 예외를 던지고 정상적으로 생성된 객체를 반환하지 않는다. 이는 메모리가 할당된 적이 전혀 없다는 주장과 다르다. 생성 중 자기 참조를 외부에 공개하거나 검증 전에 외부 파일을 바꾸지 않는 단순 모형을 사용한다.

어느 코드가 멤버를 쓸 수 있는가

public은 포함 타입이 허용하는 범위에서 외부 코드에 멤버를 공개한다. private은 같은 클래스 내부에서, internal은 같은 assembly에서 접근하도록 제한한다. protected는 파생 클래스 문맥을 포함한다. namespace에 직접 선언한 class의 기본 접근은 internal이고 class의 일반 멤버 기본 접근은 private이다. 모든 선언의 기본값이 같다고 암기하지 않는다.

private 필드를 두어 외부가 점수를 바로 덮어쓰지 못하게 할 수 있다. 접근 제한은 프로그램 코드의 사용 범위를 정하는 언어 규칙이며 웹 로그인 권한이나 암호화를 대신하지 않는다. internal에는 명시적으로 지정한 friend assembly 등 예외가 있고 protected 접근에도 정적 타입 조건이 있으므로 상세 상속 접근은 별도 단원에서 확인한다.

객체와 변수의 이름을 분리하기

class 변수 대입은 보통 객체 전체를 복제하지 않고 참조를 복사한다. a가 유효한 Score 객체를 가리킬 때 b=a라면 두 변수는 같은 객체를 가리킨다. 생성자에서 검사한 상태가 유지되려면 이후 허용된 메서드도 규칙을 지켜야 한다. 생성자가 한 번 올바르게 실행되었다는 사실만으로 모든 후속 변화가 안전해지지는 않는다.

아래 교육 코드는 명시적 필드와 생성자, 읽기 전용 property만 사용한다. 상속·직렬화·reflection·동시 변경은 분석하지 않는다. C# 문법상 기대 결과와 범위 검사 순서는 종이로 읽었으며 컴파일러나 런타임으로 실제 확인한 결과가 아니다.

public sealed class Score
{
    private readonly int points;
    public Score(int initial)
    {
        if (initial < 0 || initial > 100)
            throw new System.ArgumentOutOfRangeException(nameof(initial));
        points = initial;
    }
    public int Points => points;
}

중간 과정을 따라가는 예제

위 Score 정의에서 a=new Score(80), b=a, c=new Score(80)를 순서대로 고려하라. new Score(101)와 new Score()는 같은 실패인가? 외부 코드가 points에 직접 대입할 수 있는지도 설명하라.

  1. a의 인자80은 가드를 통과하여 points80인 객체 A를 가리킨다.

  2. b=a는 같은 객체 A의 참조를 복사한다. c는 새 객체 C를 가리키며 값은80이어도 객체는 A와 다르다.

  3. new Score(101)는 존재하는 생성자를 호출하지만 범위 검사에서 예외를 던지는 실행 시점의 실패다.

  4. new Score()는 이 정의에 매개변수 없는 생성자가 없어 컴파일 단계에서 거절될 것으로 예상한다. 외부 points 대입도 private 접근 제한에 걸린다. 이 판정은 실제 컴파일 결과가 아니다.

a와 b는 같은 객체, c는 별도 객체다. 101의 값 검증과 인자 없는 호출의 형식 검증을 구별한다.

종이와 본문으로 직접 해보기

new Score(0), new Score(100), new Score(-1)의 정상 생성 여부를 적어라. 타입을 namespace에 class Hidden { public int X; }로 선언했을 때 다른 assembly가 X를 쓸 수 있다고 단정할 수 있는가?

힌트 보기

양끝0과100은 포함된다. public 멤버의 접근은 포함 타입의 접근 범위를 넘어가지 않는다.

풀이 보기

0과100은 정상 생성,−1은 예외를 예상한다. Hidden은 namespace 직접 선언에서 기본 internal이므로 외부 assembly는 보통 타입 자체에 접근할 수 없다. public X만 보고 누구나 쓴다고 결론 내리지 않는다. friend assembly 등 별도 허용 조건은 이 활동에 없다.

오해와 반례

생성자만 검사하면 public 필드도 항상 유효하다.

생성자가80을 저장한 뒤 public points에−1을 대입할 수 있게 하면 규칙이 깨진다. 초기 검사와 이후 변경 경계를 함께 설계해야 한다.

소단원 4.2

property·indexer

대괄호나 점으로 값을 읽는 문법이 단순한 메모리 읽기만 뜻할까?

준비 개념과 학습 목표

준비 개념

  • 필드는 저장 위치, property는 get/set 등의 접근자 동작을 제공하는 멤버다.

  • 인덱스0부터 시작하는 길이3 배열의 유효 위치는0,1,2다.

  • 할당 오른쪽의 값은 setter 안에서 value로 받을 수 있다.

학습 목표

  • property와 indexer의 접근자·계산·검증을 설명한다.

  • 인덱스/값 두 검사를 통과한 변경만 추적한다.

property가 제공하는 경계

property는 필드처럼 읽거나 쓰는 문법을 제공하지만 접근자는 코드다. 자동 property의 get/set은 숨은 저장 필드를 제공한다. 반대로 int Doubled => points*2처럼 계산하는 property는 그 결과를 별도 필드에 저장하지 않아도 된다. 읽을 때 계산·예외·외부 상태 조회가 생길 수 있으므로 점 문법을 비용0과 같은 뜻으로 보지 않는다.

public int Count { get; private set; }는 외부가 읽되 변경은 클래스 내부에서 수행하는 예다. private set도 내부에서는 생성 후 바꿀 수 있으므로 불변이라는 뜻이 아니다. 검증이 필요한 setter에서는 먼저 범위를 확인하고 성공한 경우에만 필드에 대입한다. 자동 get/set 문법 자체는0..100 규칙을 검사하지 않는다.

indexer는 인자가 있는 접근

indexer는 this[int i]처럼 선언하여 객체를 obj[i]로 다루게 한다. get은 해당 값을 돌려주고 set은 새 value를 처리한다. 인덱스는 반드시 정수일 필요가 없고 문자열 키나 여러 인자를 사용할 수도 있다. 어떤 키를 허용하고 누락을 어떻게 처리할지는 타입의 계약이다.

C#에는 자동 property와 똑같은 자동 저장 indexer가 없다. 내부 배열·목록·사전·계산 등 저장과 접근을 직접 구현해야 한다. 여기의 ScoreList는 길이3인 private 배열을 갖고0≤i<3과0≤value≤100을 요구한다. 잘못된 입력에서는 예외를 던지기 전에 배열을 바꾸지 않는 순차 모형을 선택한다.

같은 모양의 호출을 실제 약속으로 읽기

아래에서 Count는 길이만 읽는 property이고 list[1]은 indexer다. 두 문법 모두 클래스의 내부 표현을 감출 수 있다. 이후 배열을 다른 저장 방식으로 바꾸더라도 인덱스 규칙과 오류 동작 같은 공개 약속을 유지해야 한다. 문법만 같고 오류 처리나 순서가 달라지면 같은 API 계약이라고 할 수 없다.

indexer에서 직접 배열 참조를 반환하는 대신 정수 하나를 돌려주면 호출자가 배열 전체를 몰래 바꾸는 통로를 줄인다. 이 코드에는 동시성·외부 데이터 저장이 없고 생성된 세 원소는0으로 초기화된다. 예외 종류와 상태 변화는 종이 판정이며 실제 C# 실행을 하지 않았다.

public sealed class ScoreList
{
    private readonly int[] items = new int[3];
    public int Count => items.Length;
    public int this[int i]
    {
        get { CheckIndex(i); return items[i]; }
        set
        {
            CheckIndex(i);
            if (value < 0 || value > 100)
                throw new System.ArgumentOutOfRangeException(nameof(value));
            items[i] = value;
        }
    }
    private static void CheckIndex(int i)
    {
        if (i < 0 || i >= 3)
            throw new System.ArgumentOutOfRangeException(nameof(i));
    }
}

중간 과정을 따라가는 예제

새 ScoreList에서 list[1]=70, list[3]=80, list[0]=101을 각각 독립 요청으로 처리하며 실패 뒤에도 다음 요청을 계속한다고 정한다. Count와 최종 배열을 구하라.

  1. 새 배열은[0,0,0]이고 Count는3이다.

  2. i=1과 value70이 모두 범위 안이라[0,70,0]이 된다.

  3. i=3은 유효 위치0..2 밖이라 인덱스 검사에서 예외를 예상하고 배열을 유지한다.

  4. i=0은 유효하나 value101은 범위 밖이라 예외를 예상하고 배열을 유지한다. 최종[0,70,0], Count3이다. 실제 프로그램에서 예외를 잡지 않으면 다음 문장으로 계속되지 않을 수 있어 요청별 계속 조건을 명시했다.

두 거절 요청은 상태를 바꾸지 않는다. 최종[0,70,0]이다.

종이와 본문으로 직접 해보기

같은 모형에서 list[-1]=−1의 어떤 검사가 먼저 실패하는가? list[2]=100 후 list[2]와 Count를 적고, computed property Twice => items[2]*2의 값을 구하라.

힌트 보기

setter는 인덱스를 먼저 검사한다. Count는 저장한 점수와 무관하게 배열 길이다.

풀이 보기

−1 인덱스가 먼저 거절된다. list[2]=100이 성공하면 해당 읽기100, Count3, Twice200이다. Twice는 다른 값의 계산이며 setter의 점수 범위를 새로운 계산 결과에 자동으로 적용하지 않는다.

오해와 반례

get만 있는 property가 반환하면 내부 객체도 모두 불변이다.

get이 int[] 참조를 반환하면 외부가 배열 원소를 바꿀 수 있다. setter가 없다는 것과 참조한 객체를 수정할 수 없다는 것은 다르다. 현재 예제는 원소 정수를 반환하여 그 통로를 제공하지 않는다.

소단원 4.3

init·record와 값 의미

두 record가 같다는 말은 같은 객체라는 뜻일까, 안쪽 배열까지 복사했다는 뜻일까?

준비 개념과 학습 목표

준비 개념

  • 참조 동등성은 같은 객체 여부, 값 동등성은 타입이 정한 값의 같음이다.

  • C#9 이상에서 init와 record class를 사용할 수 있다. 이 단원은 최신 field·required 기능을 코드에 요구하지 않는다.

  • 배열 원소는 변경 가능하고 배열 참조 대입은 원소 전체 복사가 아니다.

학습 목표

  • init 제한과 깊은 불변성을 구분한다.

  • record의 동등성·with·공유 참조를 추적한다.

초기화 뒤 대입을 막는 init

init 접근자는 생성/초기화가 허용된 문맥에서 값을 정하고 일반 외부 코드의 후속 대입을 막는다. public int Points { get; init; }는 new 객체 초기화의 Points=80과 생성 후 Points=81을 다르게 취급한다. 그러나 init 자체는 값 범위나 초기화 필수 조건을 만들지 않는다. 생략하면 기본값일 수 있고 유효성 검사가 필요하면 직접 구현해야 한다.

init은 property가 참조하는 객체의 내부까지 얼리지 않는다. 배열을 담은 init property는 나중에 다른 배열로 교체하는 외부 대입을 제한해도 기존 배열 원소는 바뀔 수 있다. 따라서 “참조를 다시 지정할 수 없다”와 “도달 가능한 자료 전체가 변하지 않는다”를 구분한다. reflection 등 우회 기법을 제외한 일반 언어 사용을 설명한다.

record는 어떤 같음을 생성하는가

record만 쓰면 record class인 참조 타입이다. 컴파일러는 동등성·해시·출력·복사 관련 멤버를 제공하지만 class의 참조 대입 성질은 남는다. 여기의 명시적 위치 record Pair(int X,int Y)는 같은 실제 타입과 X/Y 값이 같으면 ==로 동등하다고 판단하며 ReferenceEquals는 별도 질문이다. 사용자가 동등성을 변경한 타입은 별도로 검사해야 한다.

record struct는 값 타입으로 대입 시 데이터를 복사하며 위치 property가 기본적으로 읽기/쓰기일 수 있다. record class의 위치 property 기본 init과 같다고 일반화하지 않는다. 문자열/정수처럼 자신의 동등성이 명확한 멤버와 배열처럼 참조 동등성을 쓰는 멤버가 record 비교에 미치는 영향도 다르다. 모든 중첩 컬렉션을 원소별로 비교한다는 뜻이 아니다.

with는 복사 후 지정한 값의 변경

record class의 with는 기존 객체를 복사하여 지정한 property를 바꾼 새 record를 만든다. 기본 복사는 얕은 복사이므로 참조 멤버는 같은 배열을 가리킬 수 있다. 원본의 정수 Points를 바꾸지 않았다는 것과 공유 배열을 통해 원본이 관찰하는 내용까지 변하지 않는다는 것은 다르다. 아래 기록은 실제 개인 정보를 쓰지 않는 점수·태그 교육 예제다.

public record Sheet(int Points,string[] Tags)에서 배열 동등성은 기본적으로 배열 참조를 비교한다. 별도 배열 두 개의 내용이 같아도 같은 배열이라는 보장은 없다. hash 기반 자료구조의 키에 변경 가능한 값 의미를 넣으면 주의가 필요하며 실제 해시 충돌/버킷 관리는 후속 단원에서 다룬다. 이 예는 컴파일·실행 없이 정의를 종이로 따라간다. 아래는 C# 9 이상 콘솔 프로그램의 최상위 문장 예다. 실행 문장이 먼저 오고 record 타입 선언은 그 뒤에 둔다. 실제 컴파일은 수행하지 않았다.

var a = new Sheet(80, new[] { "A" });
var b = a with { Points = 90 };
var c = a with { };
b.Tags[0] = "B";

public record Sheet(int Points, string[] Tags);

종이와 본문으로 직접 해보기

힌트 보기

배열의 내용과 배열 참조의 같음을 구분한다. 첫 대입은 property 자체, 둘째는 참조한 배열 원소다.

풀이 보기

d의 배열은 T와 다른 배열이므로 기본 동등성의 a==d는 false다. 생성 후 일반 외부 코드의 Points 대입은 init 제한으로 컴파일 거절을 예상한다. 배열 원소 변경은 허용되어 T의 첫 값이 C가 될 수 있다. 그러므로 Sheet 전체가 깊이 불변이라고 부르면 틀린다.

오해와 반례

record의 값 동등성은 배열을 항상 원소별로 비교하고 with는 깊은 복사다.

a와d는 같은 태그 내용에도 다른 배열 참조 때문에 동등하지 않다. 반면 a와b는 별도 record인데 같은 배열 변경을 함께 관찰한다. 비교 정책과 복사 깊이를 각각 확인해야 한다.

소단원 4.4

encapsulation과 invariant

private 필드에 유효한 수를 넣었다면 객체의 규칙은 저절로 지켜질까?

준비 개념과 학습 목표

준비 개념

  • 불변식은 유효한 공개 관찰 시점마다 성립해야 하는 상태의 조건이다.

  • 이 예의 capacity는 고정10, used는 사용 중인 자리 수다.

  • 순차 호출과 실패 시 상태 보존을 가정한다. 실제 공유 서비스의 동시 호출은 별도다.

학습 목표

  • 생성과 공개 변경의 불변식 유지 조건을 증명한다.

  • 정보 은닉·별칭·예외·동시성의 경계를 구분한다.

숨기는 것은 규칙을 지킬 통로다

캡슐화는 표현과 동작의 경계를 정하여 외부 코드가 내부 규칙을 직접 깨는 통로를 제한한다. private이라는 단어 자체가 올바른 알고리즘을 만들어 주지는 않는다. 공개 Reserve(n) 메서드가 검증 없이 used를 늘리면 내부 필드가 private이어도 정원이 넘친다. 어떤 공개 연산이 어떤 상태 변화를 허용하는지 설명해야 한다.

정원 모형의 불변식을0≤used≤capacity=10으로 정한다. 생성자는 used=0을 만들고 성공 예약은 양수 n이 남은 자리 이하일 때만 used+n으로 바꾼다. 취소는 양수 n이 used 이하일 때만 used−n으로 바꾼다. 실패 요청은 false를 반환하고 기존 used를 보존한다. 이 정책은 특정 학사 서비스의 실제 예약 규칙이 아니다.

한 연산씩 불변식을 보존하기

예약 전0≤used≤10이고0<n≤10−used이면0≤used+n≤10이다. 취소 전0<n≤used이면0≤used−n≤10이다. 실패에서는 값을 안 바꾸므로 이전 불변식이 유지된다. 초기 상태와 모든 공개 변경을 검사하면 순차로 어떤 길이의 호출을 해도 공개 경계에서 규칙이 유지된다는 귀납 논증을 만들 수 있다.

아래 코드는 n을 더하기 전에 n≤capacity−used를 비교한다. 유효 used의 차이는0..10이라 안전하고, 임의의 큰 양수 n을 먼저 used+n으로 더하지 않아 int 넘침 위험을 피한다. 입력 검사를 조건 앞부분에서 해도 실제 실행 환경의 예외·메모리 실패·외부 효과까지 자동으로 처리하는 일반 트랜잭션은 아니다.

보호한 범위를 넘겨 말하지 않기

생성 후 공개 관찰에서는 Used만 읽고 Reserve/Cancel로 바꾸게 한다. 내부 배열이나 변경 가능한 객체를 그대로 반환한다면 외부 별칭으로 규칙을 깨는 통로가 다시 생길 수 있다. 표시용 복사본·읽기 API가 어떤 깊이까지 보호하는지 검토한다. 현재 모형은 정수 하나여서 참조한 컬렉션의 깊은 복사 문제는 없다.

검사와 갱신은 단일 스레드에서 순서대로 실행한다고 정한다. 두 스레드가 used8을 읽고 각각2의 예약 검사를 동시에 통과하는 상황에는 이 순차 증명을 그대로 적용할 수 없다. 락/원자적 연산/트랜잭션 등으로 전체 검사와 갱신 경계를 보호할지는 동시성 계약이다. 학생용 코드 실행이나 실제 예약 요청은 하지 않는다.

public sealed class Capacity
{
    private readonly int capacity = 10;
    private int used = 0;
    public int Used => used;
    public bool Reserve(int n)
    {
        if (n <= 0 || n > capacity - used) return false;
        used += n;
        return true;
    }
    public bool Cancel(int n)
    {
        if (n <= 0 || n > used) return false;
        used -= n;
        return true;
    }
}

중간 과정을 따라가는 예제

새 Capacity에서 Reserve(6),Reserve(5),Cancel(2),Reserve(6),Cancel(11)을 순차 호출한다. 각 결과와 최종 Used, 불변식을 검토하라.

  1. 초기 used0에서 Reserve6은 남은10 이하라 true, used6이다.

  2. Reserve5는 남은4보다 커 false이고 used6을 유지한다. Cancel2는 사용6 이하라 true, used4다.

  3. Reserve6은 남은6과 같아 true, used10이다. Cancel11은 사용10보다 커 false, used10을 유지한다.

  4. 결과 true/false/true/true/false, 공개 상태0/6/6/4/10/10은 모두0..10이다. 가드와 상태 보존을 각 단계에서 확인한다.

최종 Used10이며 성공3개·거절2개다. private의 이름 대신 연산별 조건으로 유지 근거를 보였다.

종이와 본문으로 직접 해보기

초기 used9에서 Reserve(0),Reserve(int.MaxValue),Cancel(9)을 종이로 추적하라. 검사를 먼저 used+n>10으로 바꾸면 큰 n에 어떤 문제가 생길 수 있는가?

힌트 보기

현재 코드는 차10−used와 n을 먼저 비교한다. 큰 양수를 더한 int 결과의 넘침 정책은 checked 여부에 따라 다를 수 있다.

풀이 보기

0과 MaxValue는 각각 양수 조건/남은1 조건에서 false이고 used9를 보존한다. Cancel9는 true로 used0이다. used+n을 먼저 계산하면 int 넘침으로 예외나 wrap 등 모드별 결과를 만나 검증 의도가 깨질 수 있다. 수학적 정수 부등식과 유한 int 연산을 구분해야 한다.

오해와 반례

캡슐화는 private를 붙이는 것이므로 동시성도 자동으로 안전하다.

두 요청이 같은 남은 자리를 동시에 보고 각각 성공할 수 있다. 접근 제한은 여러 호출의 원자성을 제공하지 않는다. 현재 귀납은 순차 가정에서만 유효하다.
