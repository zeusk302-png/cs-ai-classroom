소단원 5.1

virtual·override·abstract

같은 객체를 두 가지 타입의 변수로 부르면 결과가 항상 같을까?

준비 개념과 학습 목표

준비 개념

  • 변수의 선언 타입과 실제 객체 타입은 다를 수 있다.

  • 메서드 시그니처는 이름과 매개변수 정보를 포함한다.

  • base는 기반 클래스의 구현을 지정해 부를 때 사용한다.

학습 목표

  • 가상 호출과 이름 숨김을 구별한다.

  • 추상 멤버의 구현 의무를 설명한다.

  • 참조 타입·실제 타입·선택된 본문을 표로 추적한다.

실제 객체 타입을 알면 오버로드 선택까지 모두 바뀔까?

앞 본문의 Read는 가상 슬롯이 하나였다. 새 모형은 두 선택을 나눈다. B는 public virtual int F(object x) => 10을 선언하고 D : B는 public override int F(object x) => 20 및 public int F(string x) => 30을 선언한다. d는 새 D 객체이고 B b = d다. 호출 식의 정적 타입과 인수의 정적 타입으로 적용할 시그니처를 고른 뒤, 선택한 멤버가 virtual이면 그 슬롯의 실제 객체 구현을 고른다. 이는 C#의 일반 정적 호출 모형이며 dynamic은 사용하지 않는다.

b.F("x")에서는 B 시야의 F(object)가 선택되고 실제 객체 D의 override가 20을 반환한다. d.F("x")에서는 더 적합한 string 인수의 F(string)이 30을 반환한다. d.F((object)"x")에서는 object 인수가 F(object)를 선택하므로 20이다. 같은 문자열 객체를 넘겨도 인수 식의 정적 타입이 후보 선택에 영향을 준다. 타입 변환은 같은 객체를 보는 경로를 바꿀 수 있으며 객체의 실제 클래스 자체를 교체하지 않는다.

가상 본문 선택이 맞아도 생성 시점의 상태 계약은 아직 준비되지 않을 수 있다. 별도 InitBase 생성자가 Seen = Read()를 실행하고 Read를 virtual로 선언한다고 하자. InitDerived는 초기화 식 없는 int value 필드를 갖고 자신의 생성자 본문에서만 value = 9를 실행하며 override Read는 value를 반환한다. 기반 생성자가 호출하는 Read도 InitDerived의 본문이다. 그때 파생 생성자 본문은 아직 실행되지 않아 value는 기본값 0이고 Seen은 0이 된다. 정상 생성 종료 뒤 Read는 9다.

이 생성 예제는 불안정한 설계의 손추적이며 권장 초기화 절차가 아니다. 필드 초기화 식에 값을 옮기면 특정 값이 달라질 수 있지만 임의의 파생 클래스 초기화 의존성 전체를 해결하지 못한다. 생성자에서는 재정의 가능한 호출을 제거하고, 필요한 내부 검증은 파생 구현을 호출하지 않는 방식으로 설계한다. 실제 analyzer·컴파일러·CLR은 실행하지 않았다.

먼저 확인할 개념
  • 역할별 호출 경로

    클래스와 역할 참조가 같은 객체의 다른 경로임을 연결한다.

  • 선택 전에 아는 타입 정보

    generic 본문도 선언된 타입 정보로 연산을 확인한다.

1. 확장을 허용하는 virtual

C#에서 보통의 클래스 메서드는 기본적으로 non-virtual이다. 기반 클래스가 virtual로 확장을 허용하고 파생 클래스가 override로 같은 가상 슬롯의 구현을 바꾸면, 기반 타입의 참조로도 실제 객체의 재정의된 본문을 호출한다. 이 선택은 변수 이름이 아니라 객체의 실제 타입에 달려 있다.

반면 new 수정자는 접근 가능한 기반 멤버를 숨긴다는 의도를 표시한다. 아래 Tag처럼 non-virtual 멤버를 숨기면 b.Tag와 d.Tag는 서로 다른 본문을 선택한다. new가 객체를 새로 만든다는 뜻은 아니다. 이 단원의 new 수정자와 new LoudMeter()라는 생성 표현은 위치와 역할이 다르다.

2. 두 개의 호출 경로를 읽기

다음은 C# 8 이상 콘솔 프로젝트의 단일 Program.cs에 둘 수 있도록 Main과 모든 클래스를 포함한 자체 예제다. 실제 컴파일러나 CLR로 실행하지 않았다. 출력 설명은 언어 규칙에 따른 종이 추적이며 설치·실행 성공의 증거가 아니다.

b와 d는 같은 LoudMeter 객체를 가리킨다. b.Read()는 override된 Read를 선택하고, 그 내부 base.Read()는 Meter의 본문 6 을 얻는다. 여기에 2 를 더해 8 을 반환한다. b.Tag()는 Meter.Tag, d.Tag()는 LoudMeter.Tag를 선택한다. 변수의 타입을 바꾸는 형변환이 객체 자체를 기반 객체로 바꾸지는 않는다.

using System;
class Meter {
    public virtual int Read() { return 6; }
    public string Tag() { return "base"; }
}
class LoudMeter : Meter {
    public override int Read() { return base.Read() + 2; }
    public new string Tag() { return "loud"; }
}
class Program {
    static void Main() {
        LoudMeter d = new LoudMeter();
        Meter b = d;
        Console.WriteLine(b.Read());
        Console.WriteLine(b.Tag());
        Console.WriteLine(d.Tag());
    }
}

3. abstract는 아직 채워야 할 의무

abstract 클래스는 직접 new로 만들 수 없다. 상태, 생성자, 완성된 보통 메서드와 virtual 메서드를 포함할 수 있고, 본문 없는 abstract 멤버도 선언할 수 있다. 비추상 파생 클래스가 되려면 상속받은 추상 멤버를 적합한 override로 구현해야 한다. 추상 메서드는 확장 가능한 의무이므로 virtual을 함께 붙여 표시하지 않는다.

예를 들어 abstract Sensor가 public abstract int Read();를 선언하면 concrete SensorImpl의 public override int Read(){return 11;}은 의무를 채운다. 단지 Read라는 보통 메서드를 새로 선언해 숨기는 방법으로 추상 의무를 대신하지 않는다. 반대로 구현을 미룬 파생 클래스는 스스로 abstract로 남을 수 있다. 접근성·매개변수 등 언어 조건과 실제 값의 계약 모두 별도로 확인해야 한다.

오버로드 행은 하나의 d를 공유하지만 상태 효과 없는 F다. Init 행은 별도 생성 사례이며 초기화 식 없는 필드라는 조건을 유지한다. 선택한 시그니처와 실제 실행 본문을 서로 다른 칸에 기록한다.

중간 과정을 따라가는 예제

본문의 b.Read(), b.Tag(), d.Tag() 순서로 출력 값을 종이에서 구하라. 변수의 선언 타입도 함께 적어라.

  1. d의 선언 타입은 LoudMeter이며 만들어진 객체도 LoudMeter다.

  2. b에 d를 대입해도 객체는 변하지 않으며 b의 선언 타입만 Meter다.

  3. Read는 virtual 슬롯이므로 LoudMeter.Read를 선택하고 base.Read()의 6 에 2 를 더한다.

  4. Tag는 숨김 대상인 non-virtual 메서드다. b에는 Meter.Tag, d에는 LoudMeter.Tag를 선택한다.

  5. 각 반환 값을 순서대로 적으면 8, base, loud이다.

예상 출력은 세 줄 8 / base / loud이다. 실제 출력 캡처는 아니다.

조건을 바꾸어 비교하기

객체가 같아도 시그니처가 다르다

b.F("x")와 d.F("x")를 비교하라.

  1. b의 정적 타입 B에는 이번 F(object) 슬롯만 보인다.

  2. object로 변환 가능한 문자열을 그 슬롯에 전달하고 D의 override를 실행한다.

  3. d의 시야에서는 string 인수에 맞는 F(string)을 선택한다.

b 경로는 20, d 경로는 30이다.

비교할 점

앞 본문의 숨김과 별도로 오버로드 선택 단계를 추가한다.

재정의가 생성 완료를 기다려 주지는 않는다

InitDerived를 정상 생성할 때 Seen과 생성 후 Read 값을 구하라.

  1. 기반 생성자가 먼저 Read를 호출할 때 파생 생성자 본문은 미실행이다.

  2. override가 기본값 0을 읽어 Seen에 저장한다.

  3. 파생 생성자 본문이 value를 9로 바꾼 뒤 Read는 9를 반환한다.

Seen은 0이고 생성 후 Read는 9다.

비교할 점

잘못된 슬롯 선택이 아니라 올바른 슬롯에서 아직 준비되지 않은 상태를 읽은 문제다.

종이와 본문으로 직접 해보기

예제의 b.Read() 대신 ((Meter)d).Read()를 쓸 때와 d.Tag() 대신 ((Meter)d).Tag()를 쓸 때 값을 구하라. 별도로 abstract Read를 구현하지 않은 비추상 클래스가 적합한지 판정하라.

힌트 보기

가상 슬롯은 그대로이고 non-virtual 이름 찾기는 표현식의 정적 타입을 따른다. 추상 의무는 객체를 만들기 전에 언어 차원에서 확인한다.

풀이 보기

((Meter)d).Read()는 8, ((Meter)d).Tag()는 base다. 객체는 계속 LoudMeter다. 추상 Read를 구현하지 않은 비추상 클래스는 적합하지 않다. 그 클래스를 abstract로 남기거나 적합한 override를 제공해야 한다.

오해와 반례

C#에서는 같은 이름의 파생 메서드를 쓰면 자동으로 재정의된다.

기반 멤버의 virtual/abstract 여부와 파생 선언의 override가 필요하다. Tag의 new 숨김은 반례다. b와 d가 같은 객체를 참조해도 Tag의 결과가 달라진다. 언어적으로 override가 맞더라도 약속한 값이나 부작용이 틀리면 행동 계약을 위반한다.

자기점검

Meter b=new LoudMeter()에서 b.Read()는 어느 본문을 선택하는가?

답과 이유 보기

LoudMeter.Read다.

virtual 슬롯의 실제 객체 구현을 고르고 그 안의 base 호출은 Meter 본문을 선택한다.

new Tag가 override Tag와 같은 의미인가?

답과 이유 보기

아니다.

new는 숨김을 명시하며 본문 예제에서는 정적 참조 타입에 따라 선택이 달라진다.

abstract 클래스는 완성된 메서드를 포함할 수 있는가?

답과 이유 보기

그렇다.

직접 생성 금지와 모든 멤버에 본문이 없다는 주장은 다르다. 공통 구현과 구현 의무를 함께 둘 수 있다.

연습 3 · 직접 만들어 보기

상속 확장을 유지하면서 기반 생성자의 재정의 가능한 호출을 제거하는 경계를 설계하라.

힌트 1

초기 내부 상태 검사는 파생 Read를 요구하지 않도록 한다.

힌트 2

생성 이후 호출자가 관찰하는 Read 계약은 별도로 남긴다.

풀이와 답 확인

  1. 기반 생성자는 자신이 직접 받은 값과 내부 비가상 검증만 사용한다.

  2. 파생 생성자는 자신의 상태를 완성한다.

  3. 정상 생성 이후 공개 가상 호출의 계약을 확인한다.

생성 준비와 가상 관찰을 분리하고 생성 중 this를 외부에 공개하지 않는다.

흔한 오답에서 다시 생각하기

가상 호출을 try/catch로 감싸면 아직 초기화되지 않은 상태도 정상이다.

예외를 삼키는 것은 파생 상태의 준비 완료를 보장하지 않는다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

D의 F(object)가 −1을 반환하도록 바뀌었다. B의 공개 계약은 모든 반환값이 0 이상이다. 호출 적합성과 행동 적합성은?

힌트 1

override 시그니처는 그대로다.

힌트 2

−1은 별도로 정한 값 계약을 위반한다.

풀이와 답 확인

  2. b.F("x")도 새 본문의 −1을 받는다.

interface와 composition

보고서 객체가 프린터의 자식이어야 인쇄를 부탁할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • interface는 호출 가능한 역할을 선언한다.

  • 필드에 다른 객체의 참조를 보관할 수 있다.

  • 계약에는 입력·출력과 부작용이 포함된다.

학습 목표

  • interface 구현과 클래스 상속을 구별한다.

  • 합성 객체의 위임 흐름과 책임을 추적한다.

  • 명시적 구현의 접근 경로를 설명한다.

역할을 분리하면 하나의 객체 안 상태도 따로 생길까?

앞 본문의 Device는 명시적 역할 구현만 있었다. 새 Device는 public int Level() => 3, int IFast.Level() => 8, int IQuiet.Level() => 2를 동시에 갖고 두 interface를 선언해 구현한다. d.Level(), ((IFast)d).Level(), ((IQuiet)d).Level()은 각각 서로 다른 경로다. 명시적 구현에는 접근 수정자를 붙이지 않는다. 같은 d를 바라보며 반환 경로를 분리한 것이지 세 장치가 생긴 것이 아니다.

상태를 가진 변형에서는 Device에 정수 calls 하나를 두고 세 본문 모두 반환 전에 calls를 1 증가시킨다고 정한다. 처음 calls가 0일 때 세 경로를 순서대로 한 번씩 부르면 반환은 3, 8, 2이고 calls는 3이다. 어느 경로의 호출이든 같은 객체의 필드를 변경한다. interface가 달라도 별도 상태라는 주장은 이 공유 필드로 반박한다.

합성 부품의 성공과 예외도 같은 방식으로 계약을 적는다. 새 Writer.Write(text)는 목록에 text를 추가한 뒤 실패 예외를 던질 수 있다고 정한다. Reporter는 앞 본문과 같이 "report:"를 붙여 한 번 위임한다. 첫 Publish("A")가 추가 후 예외이면 목록에는 이미 report:A가 있다. Reporter가 무조건 한 번 재시도하고 그때 성공하면 같은 항목이 두 번 남는다. 호출자에게 실패했다는 사실과 부품의 효과가 없다는 결론은 다르다.

정확히 한 번의 업무 효과가 필요하다면 요청 ID와 효과/기록의 원자적 처리, 보존 기간 및 실패 후 조회 범위를 부품 계약에 넣어야 한다. 이 보강은 그러한 서비스를 구현하지 않는다. 공유 Writer의 종료 권한과 순서·동시성도 생성자 전달만으로 정해지지 않는다. 아래 사례는 순차이고 공유 부품을 임의 종료하지 않는다.

먼저 확인할 개념
  • 실제 객체와 선택 경로

    호출 경로를 바꾸어도 같은 객체라는 점을 연결한다.

1. 역할을 약속하고 부품을 보유하기

IWriter라는 interface가 void Write(string text)를 요구한다고 하자. 클래스는 이 역할을 implements라는 별도 키워드 없이 선언부의 : IWriter로 구현할 수 있다. 보통의 암시적 구현은 적합한 public 인스턴스 메서드를 제공한다. 클래스 이름이나 우연히 같은 메서드 이름만 있다고 interface 구현 관계가 생기는 것은 아니다.

Reporter가 IWriter 필드 writer를 가지고 생성자에서 전달받아 저장하면 보고서의 출력 부품을 합성한 것이다. Reporter가 프린터의 하위 클래스라는 뜻은 아니다. 합성은 다른 객체를 부품으로 참조해 사용하는 설계다. 이 참조가 배타적 소유인지 공유인지, null 허용 여부와 수명 종료 책임은 설계 계약으로 따로 정해야 한다.

2. 호출을 넘기는 지점의 책임

자체 종이 모형에서 Reporter.Publish(s)는 먼저 문자열 "report:"와 s를 이어 붙이고 writer.Write에 정확히 한 번 전달한다. MemoryWriter는 전달 문자열을 순서대로 저장한다. s="sun", 그다음 "rain"이면 기록은 ["report:sun", "report:rain"]이다. 파일이나 네트워크의 실제 저장은 수행하지 않았다.

생성자는 null writer를 거부한다고 명시한다. Publish는 null이 아닌 s만 허용하고, 이 단원의 MemoryWriter는 성공하며 예외를 던지지 않는다고 가정한다. 실제 writer가 예외를 던지면 Reporter가 전달·변환·재시도 중 무엇을 보장하는지 정해야 한다. 재시도를 무조건 추가하면 정확히 한 번이라는 출력 계약이 깨질 수 있다. interface를 받아 결합을 줄였다고 오류 책임까지 없어지지 않는다.

3. 같은 이름을 역할별로 분리하기

IFast와 IQuiet가 모두 int Level()을 선언한다고 하자. 장치 클래스가 public int Level(){return 3;} 하나를 제공하면 두 역할은 그 구현을 공유할 수 있다. 반대로 int IFast.Level(){return 8;}과 int IQuiet.Level(){return 2;}라는 명시적 구현을 별도로 제공하면 해당 interface 참조를 통해 각 구현을 부른다. 이 선언에는 public 같은 접근 수정자를 붙이지 않는다.

명시적 구현만 있는 Device 객체 d에서 d.Level()을 직접 호출하는 경로는 제공되지 않는다. ((IFast)d).Level()은 8 이고 ((IQuiet)d).Level()은 2 다. 여기의 형변환은 같은 장치를 서로 다른 역할로 보는 것이다. 두 interface가 각각 요구한 후행 조건도 별도로 지켜야 한다. 기본 interface 구현 등 최신 기능의 모든 규칙을 이 간단한 사례로 일반화하지 않는다.

소단원 5.3

generic constraint

T라고만 적은 타입으로 왜 원하는 메서드를 마음대로 부를 수 없을까?

준비 개념과 학습 목표

준비 개념

  • generic은 타입을 매개변수로 받아 재사용한다.

  • 컴파일러는 선언된 계약을 기준으로 호출을 확인한다.

  • public 매개변수 없는 생성자와 private 생성자는 다르다.

학습 목표

  • where 제약이 허용하는 연산을 연결한다.

  • 제약의 교집합과 선언 순서를 확인한다.

  • 형식 제약과 값의 의미 보장을 구별한다.

같은 interface 연산인데 원래 struct와 복사본 중 어느 쪽이 바뀔까?

새 ICounter는 void Inc()와 int Value { get; }를 요구한다. Counter struct는 정수 n을 저장하고 Inc는 n을 1 늘리며 Value는 n을 반환한다고 정한다. 모든 시작 값은 1이며 넘침 범위는 사용하지 않는다. BumpCopy<T>(T x) where T : ICounter는 x.Inc()를 한 번 실행한다. BumpRef<T>(ref T x) where T : ICounter는 같은 본문을 실행한다. interface 제약은 Inc 호출을 허용하지만 값 매개변수와 ref 매개변수의 저장 대상 차이를 없애지 않는다.

Counter c의 Value가 1일 때 BumpCopy(c)는 복사된 매개변수의 n만 2로 바꿔 원래 c는 1이다. 별도 초기 c에서 BumpRef(ref c)는 원래 저장소를 사용하여 c를 2로 바꾼다. 이 예제는 각 호출이 지정된 작은 struct 상태를 변경한다는 손추적이다. 실제 JIT의 할당 여부·명령 수·속도 차이를 측정하지 않았다.

별도 시작에서 ICounter box = c는 Counter 값의 boxing 복사다. box.Inc() 뒤 box.Value는 2이고 원래 c.Value는 1이다. Counter back = (Counter)box는 box의 현재 값을 복사해 back.Value가 2다. back.Inc() 뒤 back은 3이지만 box는 2다. 역할 변환이 언제나 원래 변수 자체의 별칭을 만든다고 생각하면 복사 경계 두 곳을 놓친다.

생성과 호출 능력도 분리한다. 이미 받은 x.Inc()만 필요한 두 함수에는 new()가 필요 없다. 자체 Seed class가 ICounter를 구현하지만 public 매개변수 없는 생성자가 없다면 이 두 함수에 정상 Seed 객체를 전달하는 것은 제약상 가능하다. 반면 new T()를 사용하는 Factory에는 생성 능력이 추가로 필요하다. 타입 제약은 Inc의 의미가 양수 증가인지, 객체가 null인지, 어느 외부 상태를 바꾸는지까지 자동 검증하지 않는다.

먼저 확인할 개념
  • 역할 참조의 상태

    참조 객체의 상태 공유와 값 타입 boxing 복사를 비교한다.

  • boxing과 분산의 다른 경계

    개별 값 변환을 generic 참조 변환으로 확대하지 않는다.

1. T에 관해 알 수 있는 사실

제약 없는 T는 특정 Score 메서드나 public 생성자를 보장하지 않는다. 호출자가 우연히 그런 타입을 넣을 예정이라고 생각해도 generic 본문은 그 약속을 선언해야 한다. where T : IScore는 T가 그 interface를 구현한다는 사실을 제공하여 item.Score() 호출을 허용한다.

where T : class, IScore, new()는 참조 타입·IScore 구현·public 매개변수 없는 생성자라는 조건을 함께 요구한다. 마지막 new() 덕분에 new T()를 쓸 수 있다. 제약은 또는가 아니라 동시에 만족할 교집합이다. 이름이 같은 Score를 가진 클래스라도 IScore 구현 선언이 없으면 이 제약을 만족하지 않는다.

2. 각 줄이 요구하는 능력

아래 자체 프로그램은 C# 8 이상 콘솔 문맥이며 nullable 주석을 사용하지 않는 단순 예제다. 컴파일하거나 실행하지 않았다. FreshScore<Rookie>()에 Rookie를 대입한다고 종이에서 읽으면 Rookie는 참조 타입이고 IScore를 구현하며 public Rookie()를 갖는다. new T()는 새로운 Rookie를 만들고 Score는 7 을 반환한다.

IScore 제약만 두고 new T()를 유지하면 public 기본 생성자 보장이 부족하다. 반대로 new()만 두고 Score()를 호출하면 Score의 존재가 보장되지 않는다. 제약을 줄이는 것은 좋은 일반화일 수 있지만 본문이 필요한 연산을 지원하는 조건까지 제거해서는 안 된다.

using System;
interface IScore { int Score(); }
class Rookie : IScore {
    public Rookie() { }
    public int Score() { return 7; }
}
class Factory {
    public static int FreshScore<T>() where T : class, IScore, new() {
        T item = new T();
        return item.Score();
    }
}
class Program {
    static void Main() { Console.WriteLine(Factory.FreshScore<Rookie>()); }
}

3. 배제 관계와 값 계약

기본 class/struct 같은 종류 제약은 정해진 위치와 배제 관계가 있다. 이 예제의 class는 앞, interface는 중간, new()는 뒤에 적는다. struct 제약은 비 nullable 값 타입을 요구하며 생성 조건을 포함하므로 struct와 new()를 함께 적지 않는다. 최신 allows ref struct 등 부가 기능의 규칙은 여기서 다루지 않는다.

제약이 IScore라고 해도 Score 반환값이 항상 양수라는 뜻은 아니다. 그것은 별도의 interface 의미 계약과 구현 검토가 필요하다. 또한 nullable 문맥의 class/notnull 주석은 런타임 null 검사와 다르다. notnull 위반은 해당 문맥에서 경고일 수 있으며, 제약 이름만으로 모든 null 입력이 예외로 거부된다고 주장하면 안 된다. 실제 입력 검사는 필요 지점의 구현 정책이다.

  1. Rookie는 class 조건을 만족한다.

  2. Rookie는 IScore와 public 기본 생성자도 만족하므로 세 조건의 교집합 안에 있다.

소단원 5.4

variance와 타입 계약

개를 내주는 상자를 동물 상자로 볼 수 있는데, 동물을 받는 창구는 왜 반대 방향으로 바꿀까?

준비 개념과 학습 목표

준비 개념

  • Dog와 Cat은 Animal의 하위 클래스라고 가정한다.

  • 입력은 호출자가 넘기는 값, 출력은 호출자가 받는 값이다.

  • 같은 객체를 다른 참조 타입으로 보는 것이 새 객체 생성은 아니다.

학습 목표

  • out 공변과 in 반공변의 안전 방향을 설명한다.

  • 불변 generic 및 값 타입의 제한을 구별한다.

  • 간단한 입력·출력 반례로 부적합 변환을 판단한다.

입력과 출력의 화살표가 동시에 바뀌어도 안전할까?

Dog와 Cat은 각각 Animal의 별개 하위 클래스다. 새 함수 f는 Animal을 받고 Dog를 반환하는 Func<Animal,Dog>다. 이를 Func<Dog,Animal> g로 보면 g 호출자는 Dog만 전달하며 반환을 Animal로 다룬다. f는 Dog도 받을 수 있고 반환 Dog도 Animal이므로 입력 반공변과 출력 공변 조건을 동시에 만족한다. 새 변환은 함수의 내부 알고리즘이나 의미 계약을 고치는 작업이 아니다.

역방향은 일반적으로 안전하지 않다. Dog만 받는 함수에 Cat을 보낼 수 없으며 Animal 반환 함수가 Cat을 줄 수도 있어 Dog 반환을 보장하지 못한다. 자체 h가 Dog를 받고 Cat 객체를 Animal로 반환한다고 정하면 Func<Dog,Animal>로는 정상이다. h를 Func<Animal,Dog>로 일반 변환한다고 가정하는 순간 입력과 출력 양쪽에서 반례가 생긴다. 명시 cast 성공이나 실제 예외는 시험하지 않았다.

읽기 시야도 객체 복제를 뜻하지 않는다. list는 Dog 객체 D1 하나를 담은 List<Dog>이고 IEnumerable<Animal> view = list로 본다고 하자. 같은 list에 Dog D2를 추가한 뒤 열거하면 현재 두 객체를 볼 수 있다. view 자체에는 Add가 없지만 원래 list의 외부 갱신을 차단하지 않는다. 열거 도중 변경의 예외 규칙까지 이 단순 순차 모형으로 주장하지 않는다.

값 타입 boxing은 별도 원소 변환이다. IProducer<int>에서 얻은 정수 하나를 object 변수에 저장할 수 있다는 사실로 그 생산자 참조를 IProducer<object>로 분산 변환할 수 있다고 결론 내리지 않는다. 새 어댑터가 Get마다 원래 생산자를 한 번 부르고 결과 정수를 boxing하여 object로 반환하는 설계는 별도 객체·호출·null·예외 계약을 가진다. 변환 불가와 어댑터 구성 불가를 같은 뜻으로 쓰지 않는다.

먼저 확인할 개념
  • 정적 시야와 실제 구현

    경로 변환으로 원래 본문과 의미가 자동 수정되지 않는다.

  • 값 복사와 boxing 경계

    개별 원소 변환과 generic 타입 변환을 구별한다.

1. 내주는 값의 공변성

단순 interface IProducer<out T> { T Get(); }를 생각하자. Dog를 내주는 IProducer<Dog>를 IProducer<Animal>로 보면 호출자는 Get 결과를 Animal로 다룬다. 모든 Dog가 Animal이므로 안전하다. 이 방향을 공변성이라 부른다. Dog에서 Animal이라는 타입 인수 방향과 interface 변환 방향이 일치한다.

반대는 일반적으로 안전하지 않다. 동물 생산자가 Cat을 돌려줄 수 있는데 이를 개 생산자로 보게 허용하면 호출자는 Dog라고 믿고 Cat을 받는다. out은 아무 위치에 T를 넣어도 된다는 표시가 아니다. 단순 예제에서는 반환 위치에 쓰고 입력 매개변수 T를 추가하면 분산 안전성 규칙과 충돌한다. 중첩 generic 위치는 별도 규칙을 분석해야 한다.

2. 받는 값의 반공변성

IConsumer<in T> { void Put(T item); }에서 모든 Animal을 처리하는 창구는 Dog도 처리한다. 따라서 IConsumer<Animal>을 IConsumer<Dog>로 사용할 수 있다. Dog만 받겠다고 약속한 호출자가 실제로 Dog를 넘기면 더 넓은 Animal 처리자가 받아도 안전하다. 이 방향은 타입 인수 관계와 반대이므로 반공변성이다.

Dog만 받는 처리자를 Animal 처리자로 보는 역방향은 안전하지 않다. Animal 호출자는 Cat을 넣을 수 있기 때문이다. in은 단순 입력 위치에 쓰며, 반환 T를 추가하면 이 단순 선언의 분산 조건을 위반한다. 계약이 허용하는 값의 집합을 그려 보면 화살표를 외우지 않아도 판단할 수 있다.

3. 모든 generic이 분산되는 것은 아니다

C#의 분산 선언은 generic interface와 delegate의 타입 매개변수에 적용한다. 보통 class List<T>는 불변이다. List<Dog>를 List<Animal>로 그대로 대입하도록 허용하면 후자를 통해 Cat을 추가해 원래 개 목록의 타입 안전성을 깰 수 있다. 읽기용 IEnumerable<Dog>를 IEnumerable<Animal>로 보는 별도 interface 경로와 List 자체의 변환을 혼동하지 않는다.

분산에 따른 변환은 참조 타입 인수에 적용한다. int가 object로 boxing될 수 있다고 IProducer<int>가 IProducer<object>로 분산 변환되는 것은 아니다. 개별 원소 boxing과 이미 구성된 generic 참조의 변환은 다르다. 배열 공변성과 가상 메서드의 공변 반환도 별도 기능이며, 이 단원의 in/out 타입 매개변수 규칙으로 한꺼번에 판단하지 않는다.
