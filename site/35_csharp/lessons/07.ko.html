소단원 7.1

delegate와 callback

계산 함수를 인수로 보내면 호출받는 쪽은 무엇을 알아야 할까?

준비 개념과 학습 목표

준비 개념

  • delegate는 호출 가능한 메서드와 대상을 담는 타입이다.

  • callback은 다른 코드에 전달해 그 코드가 호출하도록 한 행동이다.

  • void는 반환 값이 없다는 뜻이다. multicast delegate는 여러 메서드를 순서대로 호출하는 호출 목록을 가진다.

학습 목표

  • 입력/반환 계약을 읽는다.

  • 함수 전달과 즉시 호출을 구분한다.

  • 호출 목록의 순서를 추적한다.

두 함수를 더한 delegate는 앞 결과를 다음 입력으로 보내는 계산 사슬일까?

앞 본문의 ApplyTwice는 f(f(v))라는 명시적인 합성이다. 반면 자체 Func<int,int> F=x=>x+1, G=x=>2*x를 결합한 F+G는 두 함수에 같은 입력을 전달한다. 입력 3에서 F의 결과는 4, G의 결과는 6이며 정상 호출의 반환은 마지막 결과 6이다. G(F(3))의 결과 8과 다르다. 호출 목록을 결합하는 기호와 수학적 함수 합성을 같은 연산으로 읽지 않는다.

호출 목록과 호출 대상의 상태도 구별한다. Action a=H; Action old=a; a+=J라는 순차 선언에서 old는 H만 담는 기존 목록이다. 결합이 old의 내부 목록을 H,J로 바꾸지 않는다. 다만 H가 같은 대상 객체의 변경 가능한 필드를 읽으면 old 호출의 효과도 현재 필드에 따라 달라질 수 있다. 목록 불변성과 대상 상태 불변성은 서로 다른 계약이다.

이 보강은 같은 스레드의 작은 정수 입력과 정상 반환을 먼저 가정한다. callback을 저장하는 단계와 호출하는 단계는 분리하며, 호출 중 예외는 앞에서 이미 발생한 효과를 자동 취소하지 않는다. 직접 각 항목을 호출하며 예외를 처리하는 정책은 일반 multicast 호출과 별도다. 실제 C# 번역·실행 또는 비동기 작업은 수행하지 않았다.

먼저 확인할 개념
  • 함수 전달과 순서 호출

    앞 본문의 ApplyTwice를 일반 호출 목록과 비교한다.

  • 등록 목록과 해제

    같은 handler 목록의 복사와 변경을 구별한다.

함수를 호출할 약속

Func<int,int>는 int 입력 하나에서 int 결과를 얻는 호출 계약이다. f=x=>x+2를 전달하면 받는 코드는 f(3)으로5를 얻을 수 있다. Action<int>는 int를 받아 행동하지만 반환 값은 void다.

모든 메서드가 서로 대체되는 것은 아니다. 입력 개수·타입·참조 전달 방식·반환 계약이 호환되어야 한다. 같은 모양의 사용자 delegate 타입 두 개도 이름이 다른 별도 타입일 수 있어 변수끼리 아무 변환 없이 교환할 수 있다고 단정하지 않는다.

전달과 실행 사이

ApplyTwice(v,f)를 f(f(v))로 정의하면 f를 두 번 호출한다. 인수로 lambda를 만드는 시점과 본문이 실제 호출되는 시점은 다르다. API가 저장했다가 나중에 호출하면 수명·취소 조건도 필요하다.

callback이라는 단어만으로 비동기 실행이나 새 스레드를 뜻하지 않는다. 이 예의 ApplyTwice는 같은 스레드에서 순서대로 호출한다. 실제 타이밍은 호출하는 API 계약에 따라 달라진다.

여러 행동과 실패

Action 두 개를 A+B로 결합하면 호출 목록은 A 다음 B다. A에서 처리하지 않은 예외가 나면 일반 multicast 호출은 B를 이어 호출하지 않는다. 모두 실행해야 하는 정책이면 별도 오류 처리가 필요하다.

반환 값이 있는 multicast는 정상 호출 시 마지막 호출 결과를 반환한다. 앞 결과들을 자동 합산하지 않는다. 아래는 안전한 작은 정수·void 행동의 종이 추적이며 실제 컴파일과 스레드를 실행하지 않았다.

소단원 7.2

lambda capture

lambda를 만들 때의 숫자와 나중에 호출할 때의 숫자는 같을까?

준비 개념과 학습 목표

준비 개념

  • capture는 바깥 변수를 lambda가 사용할 수 있게 하는 관계다.

  • 변수의 현재 값을 읽는 것과 생성 시 복사한 값을 읽는 것은 다르다.

학습 목표

  • 공유 변수 상태를 추적한다.

  • 루프별 별도 변수를 설명한다.

  • static lambda의 범위를 구분한다.

참조 변수의 사진을 찍으면 그 객체의 필드 값도 사진으로 고정될까?

자체 Box는 변경 가능한 int Value 하나를 가진 참조 객체다. a=Box(2) 뒤 saved=a; frozen=a.Value; live=()=>a.Value; pinned=()=>saved.Value; number=()=>frozen을 만든다. saved는 객체 A의 참조 복사이고 frozen은 정수 2의 값 복사다. a.Value=7이면 live와 pinned는 모두 7을 읽지만 number는 2다. 참조를 복사한 것과 객체 내용을 복사한 것은 다르다.

그 뒤 a=Box(9)로 참조 변수를 새 객체 B에 연결하면 live는 9, pinned는 아직 A의 값 7, number는 2를 읽는다. pinned가 캡처한 saved도 변수다. saved까지 B로 재대입하면 pinned의 결과가 바뀐다. 이 사례에서는 saved와 frozen을 이후 변경하지 않는다는 명시 조건으로 비교한다.

독립 상태를 만들려면 선언이 어느 실행마다 새 변수인지 확인한다. 자체 factory는 호출마다 새 int n=0을 만들고 inc=()=>++n과 read=()=>n을 한 쌍으로 반환한다. 같은 쌍 내부는 n 하나를 공유하지만 서로 다른 factory 호출은 다른 n을 갖는다. static lambda의 캡처 금지는 이 독립 상태 정책이나 순수성을 자동으로 대신하지 않는다. 실제 closure 객체 배치·할당 수·스레드 동작은 측정하지 않는다.

먼저 확인할 개념
  • 변수 캡처와 생성 시점

    앞 본문의 offset과 for 변수 수를 객체 참조/값 복사로 확장한다.

  • 도달 가능한 캡처 사슬

    변수 연결이 객체 수명에 남기는 경로를 함께 읽는다.

값 사진 대신 변수 연결

int offset=2; Func<int,int> f=x=>x+offset; 뒤 offset=5라면 f(3)은8이다. 캡처한 것은 offset이라는 변수이며 초기 숫자2를 영원히 고정한 사진이 아니다.

두 lambda가 같은 변수 n을 사용하면 한쪽의 변경을 다른 쪽이 관찰한다. 캡처가 자동 스레드 안전이나 값 불변을 주지 않는다. 이 단원은 순차 호출과 살아 있는 delegate를 가정한다.

루프의 변수 수 세기

for의 같은 i 변수를 여러 lambda가 참조하고 루프 종료 후 호출하면 모두 최종 i를 읽을 수 있다. 자체 for(i=0;i<3;i++)에서 세 저장 함수 ()=>i는 종료 후 모두3이다.

본문마다 int copy=i를 새로 만들고 ()=>copy를 저장하면 서로 다른 세 변수의0,1,2를 보존한다. foreach의 반복 변수 규칙은 언어 버전에 따른 별도 사항이라 이 for 사례를 무조건 모든 루프에 적용하지 않는다.

수명과 불필요한 캡처

바깥 블록이 끝나도 살아 있는 delegate가 사용하는 캡처 변수는 필요할 동안 유지될 수 있다. 대형 객체를 캡처하면 도달 가능 관계도 길어질 수 있다. 블록 종료를 곧 수거 완료로 읽지 않는다.

C#9부터 static lambda는 바깥 지역 변수나 인스턴스 상태를 캡처하지 못하게 한다. 자기 인수·지역 변수 및 허용되는 static 멤버/상수는 사용할 수 있다. static이라는 표기만으로 순수 함수나 모든 할당0을 보장하지 않는다.

event 구독·해제

같은 handler를 두 번 등록하고 한 번 빼면 몇 번 호출될까?

준비 개념과 학습 목표

준비 개념

  • publisher는 사건을 발행하고 subscriber는 handler를 등록한다.

  • 이 예는 기본 field-like event이며 custom add/remove와 동시 실행은 제외한다.

학습 목표

  • +=와−=의 의미를 추적한다.

  • 해제할 delegate를 보관한다.

  • 발행 권한과 구독 권한을 구분한다.

발행 중 한 handler를 빼면 이미 시작한 발행의 남은 목록도 즉시 바뀔까?

자체 publisher는 기본 field-like event Action을 사용하고 발행 시작에서 snap=Changed를 지역 변수로 얻은 뒤 snap?.Invoke()를 호출한다. 처음 목록은 [H,J]다. H는 자신의 호출 중 Changed에서 J를 빼고 K를 더한다. 현재 저장 목록은 [H,K]가 되지만 이미 얻은 snap은 [H,J]다. 따라서 첫 발행은 H,J를 호출하고 다음 발행은 H,K를 호출한다. 이 예의 H는 매 호출마다 같은 변경을 수행하므로 두 번째 뒤 현재 목록은 [H,K,K]가 된다.

이것은 새 스레드가 없어도 생기는 재진입 효과다. 발행 중 H가 다시 발행을 호출한다면 안쪽 발행은 그 시점의 현재 목록을 얻고 바깥 발행은 자신의 목록을 계속한다. 여기서는 무한 재진입을 피하려고 H가 딱 한 번만 중첩 발행하도록 별도 guard를 둔다. 일반 event 선언만으로 중복 등록 금지·업무 단위 취소·재진입 금지가 생기지 않는다.

해제할 delegate의 동일성과 등록 횟수도 별개다. 같은 인스턴스 메서드 H를 두 번 추가하면 −=H 한 번은 한 일치를 제거한다. 의도한 한 번 활성화를 보장하려면 자체 active 상태와 저장 handler를 사용해 중복 Activate를 생략하고 성공한 등록의 해제 책임을 기록한다. 아래 정책은 순차·정상 add/remove이며 실패 주입·custom accessor·동시 변경은 시험하지 않았다.

event Action? Changed를 선언한 클래스 밖에서는 Changed에 +=나−=를 사용할 수 있지만 직접 Invoke하거나 전체 값을 대입하는 것은 허용되지 않는다. 발행자는 자신의 변경 시점을 정해 내부에서 호출한다.

같은 인스턴스의 같은 메서드H를 두 번 더하면 호출 목록에H가 두 번 들어간다. H를 한 번 빼면 마지막 일치 항목 하나가 제거되어 한 번의H가 남는다. 서로 다른 대상의 같은 이름 메서드는 같은 handler라고 취급하지 않는다.

소단원 7.4

event lifetime과 메모리 누수

화면을 닫았는데 오래 사는 publisher가 화면을 붙잡을 수 있을까?

준비 개념과 학습 목표

준비 개념

  • GC는 도달 가능한 객체를 수거 대상으로 보지 않는다.

  • 이 예는 일반 strong-reference handler와 살아 있는 장기 publisher를 가정한다.

  • root는 GC가 탐색을 시작하는 정적 필드·스택 등의 참조 출발점이다. 1MiB는 2^20바이트다.

학습 목표

  • 참조 경로를 그린다.

  • 논리 종료와 수거 가능을 구분한다.

  • 해제 후 남은 참조를 확인한다.

여러 페이지가 같은 자료를 공유하면 등록 횟수만큼 메모리가 늘어날까?

자체 자료 그래프에서 장기 publisher P는 세 페이지 A/B/C의 인스턴스 handler를 참조한다. A와 B는 같은 버퍼 X(4 MiB)를, C는 별도 버퍼 Y(2 MiB)를 참조한다. 추가 root cache는 B를 참조한다. 버퍼 노드의 서로 다른 ID를 한 번씩 세면 자료 합은 6 MiB다. 페이지별 크기를 더한 4+4+2=10 MiB는 X를 두 번 세므로 실제 자료 그래프의 합과 다르다. 헤더·delegate·페이지 객체의 크기는 이 자체 계산에서 제외한다.

A와 B 구독을 모두 제거해도 root cache→B→X 경로가 남아 X는 여전히 도달 가능하다. 이후 cache에서 B를 제거하고 진행 중 호출·다른 root가 없다는 조건이면 X가 수거 가능해지고 P→C→Y의 2 MiB만 남는다. 같은 페이지 A를 두 번 등록했다면 제거 한 번으로는 해당 대상 경로가 남는다는 앞 소단원의 횟수 규칙도 함께 점검해야 한다.

닫힘·Dispose·구독 해제·수거 가능·실제 GC 완료는 구분해 기록한다. 외부 root 없는 publisher와 subscriber의 주기는 상호 참조만으로 영원히 유지되는 것이 아니다. 반대로 저장한 snapshot delegate를 root 작업 목록이 붙잡으면 현재 event가 비어도 snapshot→subscriber 경로가 남는다. 아래는 명시한 그래프의 도달성 계산이며 CLR 배치·profiler·실제 수거 시점·운영 메모리를 측정하지 않았다.

먼저 확인할 개념
  • root 경로와 수거 가능성

    앞 본문의 단순 10개 자료 합을 공유 노드/여러 root로 확장한다.

  • 중복 구독과 해제 책임

    경로를 끊으려면 남은 호출 항목과 별도 저장 목록도 확인한다.

도달 가능한 참조 사슬

root→publisher→event delegate→subscriber를 그리자. 인스턴스 handler는 대상 subscriber를 참조하므로 화면을 닫아도 publisher가 살아 있고 등록이 남으면 subscriber가 도달 가능하다. 더 이상 필요 없는 유지가 누수가 될 수 있다.

GC가 있다는 사실이 불필요한 참조를 없애 주는 것은 아니다. 이벤트가 항상 누수라는 주장도 틀리다. publisher와 subscriber 모두 다른 root에서 도달 불가능해지면 서로 참조하는 주기도 수거 가능할 수 있다.

해제와 수거는 다른 사건

같은 handler를−=로 제거해 경로를 끊는 것이 해결의 한 방법이다. 하지만 다른 목록이나 캡처가 subscriber를 참조하면 아직 도달 가능하다. Dispose라는 이름의 메서드를 호출했다고 GC수거가 즉시 완료됐다는 뜻도 아니다.

익명 lambda가 this나 대형 자료를 캡처하면 delegate→closure→자료라는 경로도 생긴다. 실제 해제 책임과 구독 기간을 명시하고 필요 없는 캡처를 줄이자. weak-event 방식은 참조 정책·실패/수명 계약이 다른 설계라 자동 대체로 단정하지 않는다.
