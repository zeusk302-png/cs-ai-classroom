소단원 1.1

SDK·project·build·run

소스 파일을 저장했는데 실행 결과가 그대로라면 무엇이 아직 바뀌지 않은 것일까?

준비 개념과 학습 목표

준비 개념

  • 변수는 값에 이름을 붙인 것이다. int a=2에서 a의 값은2이며 a+b는 두 값을 더한 식이다.
  • 함수는 인수를 받아 정해진 일을 수행하는 단위다. Add(2,3)은 인수2와3을 전달하고 결과를 돌려받는 호출이다.
  • 파일은 저장된 내용의 묶음, 폴더는 파일을 조직하는 위치다. 소스와 빌드 산출물은 서로 다른 파일임을 구별하자.

학습 목표

  • SDK와 런타임의 책임을 구분한다.
  • project 설정에서 build와 run의 관계를 추적한다.
  • 소스 변경과 실행한 산출물의 버전을 구별한다.

언어·도구·실행환경의 다른 책임

C#은 프로그램을 표현하는 언어이고 .NET은 런타임·라이브러리·도구 등을 포함하는 개발 플랫폼이다. SDK는 소스를 빌드하는 데 필요한 컴파일러와 CLI 등의 개발 도구를 제공한다. 런타임은 이미 만들어진 관리 프로그램을 실행하는 쪽이다. 실행만 하는 컴퓨터가 항상 전체 SDK를 필요로 하는 것은 아니다.

이 단원은 SDK8.0.204, C#12, net8.0 콘솔 프로젝트로 예를 고정한다. 이는 최신 버전 추천이 아니라 확인한 예의 조건이다. 설치 없이 프로젝트 카드를 읽고 실행 흐름을 종이로 추적할 수 있다.

프로젝트는 빌드의 입력을 모은 계약

SDK 스타일 .csproj는 출력 종류와 대상 프레임워크 등의 설정을 적는 XML 파일이다. 여기서는 Exe가 진입점을 가진 프로그램임을, net8.0이 대상 API 범위를 지정함을 뜻한다. 기본 SDK 규칙은 프로젝트 폴더의 .cs 파일을 포함하지만 그 규칙을 설정으로 변경할 수 있다.

빌드는 소스와 설정, 참조를 이용해 산출물을 만든다. 복원(restore)은 의존성 정보를 해결하고 빌드에 필요한 자산을 준비하는 과정이다. 코드 오류로 빌드가 실패했는데 이전 산출물이 남아 있다면 그것은 새 코드의 성공 증거가 아니다.

<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net8.0</TargetFramework>
    <LangVersion>12.0</LangVersion>
  </PropertyGroup>
</Project>

빌드 뒤 무엇을 실행하는가

dotnet run은 보통 프로젝트를 빌드한 뒤 실행하며 필요한 복원도 암묵적으로 수행한다. --no-build는 다시 빌드하지 않는 선택이므로 기존 결과를 실행한다. -- 뒤의 값은 프로그램 인수로 전달한다. 소스를 읽는 것과 그 소스의 최신 결과를 실행하는 것은 별개다.

우리 Add는 작은 int 두 개를 더한다. Main은 프로그램의 시작 메서드다. 실제 격리 예제는 아래 두 출력에 더해 타입·이름 정보도 출력한다. 산출물의 Debug/net8.0 위치와 실행 인수를 기록하면 어느 코드가 실행되었는지 확인하기 쉽다.

using System;
class Program {
    static int Add(int a, int b) { return a+b; }
    static void Main(string[] args) {
        Console.WriteLine(Add(2,3));
        Console.WriteLine(args.Length);
    }
}

중간 과정을 따라가는 예제

빌드가 성공한 예제를 alpha beta 두 인수로 실행한다. int 합은 표현범위 안이며 args는 두 문자열을 가진 배열이다.

  1. Main 시작 시 args.Length=2.
  2. Add에 a=2,b=3 전달. a+b=5를 반환.
  3. WriteLine이5를 출력하고 다음 줄에2를 출력.
  4. 소스를 Add(2,7)로 고쳐도 --no-build로 이전 산출물을 실행하면 이전5가 나올 수 있다.

새 빌드의 기본 출력은5와2다. 변경한 소스의 결과9는 새 빌드 성공 후 기대한다.

종이와 본문으로 직접 해보기

소스 카드S1(Add2,3), 산출물B1(5), 소스 카드S2(Add2,7)를 그려라. S2 저장→빌드 실패→B1 실행과 S2 저장→빌드 성공→B2 실행 결과를 적어라.

풀이 보기

오해와 반례

run은 항상 방금 편집한 소스를 실행한다.

--no-build로 이전 파일을 실행하는 반례가 있다. 일반 run도 빌드 실패면 새 실행이 성공했다고 볼 수 없다. IDE 버튼의 동작은 설정에 따라 확인해야 한다.

소단원 1.2

CIL·CLR·CTS

C#과 다른 언어가 같은 int 값을 주고받으려면 어떤 공통 약속이 필요할까?

준비 개념과 학습 목표

준비 개념

  • 타입은 어떤 값과 연산을 허용하는지 정한다. 정수2와 문자열"2"는 표기가 비슷해도 같은 타입이 아니다.
  • 번역은 한 표현을 다른 표현으로 바꾸는 과정이다. 종이 계산의 의미와 계산을 실행할 명령을 구별하자.
  • 스택은 나중에 넣은 값을 먼저 꺼내는 칸들의 묶음이다. [2,3]에서 맨 오른쪽3을 먼저 꺼낸다고 약속한다.

학습 목표

  • CIL과 메타데이터를 기계명령과 구분한다.
  • CLR 실행 과정과 CTS 공통 타입 규칙을 설명한다.
  • 설명용 CIL 추적과 실제 컴파일 산출물을 구별한다.

중간 표현과 실행을 잇는 단계

일반적인 관리 C# 빌드는 언어 소스를 CIL(Common Intermediate Language)과 메타데이터가 담긴 assembly로 만든다. CIL은 특정 CPU의 기계명령과 구별되는 중간 명령이고 메타데이터는 타입·멤버·참조 등의 구조 정보를 제공한다. 이 구조 덕분에 런타임이 코드와 타입 관계를 다룰 수 있다.

CLR(Common Language Runtime)은 관리 실행을 지원하며 메모리 관리·예외 처리 등 서비스를 제공한다. 흔한 JIT 경로에서는 필요한 메서드의 CIL을 목표 CPU 기계코드로 컴파일한다. JIT 시점과 최적화는 구현에 따라 달라진다. 미리 컴파일하는 AOT 경로도 있으므로 모든 .NET 배포가 실행 때만 번역한다고 단정하지 않는다.

서로 다른 언어가 공유하는 타입 약속

CTS(Common Type System)는 런타임에서 타입을 선언·사용·관리하는 공통 규칙이다. C#의 int는 System.Int32의 별칭이다. 소스 키워드가 다르더라도 같은 공통 타입에 대응하면 언어 경계를 넘는 API를 설계할 수 있다. 단지 비트수가 같다는 이유만으로 모든 언어 타입이 자동 호환되는 것은 아니다.

공통 타입 체계가 있어도 각 언어가 모든 기능을 똑같이 노출하지는 않는다. CTS와 언어 문법을 구분하고, 여러 언어가 이용할 API에는 접근성과 언어별 기능 범위를 검토해야 한다. 값/참조 타입의 자세한 복사 의미는 다음 단원에서 다룬다.

스택을 이용한 합의 의미 추적

교육용 CIL 형태에서 ldarg.0은 첫 인수, ldarg.1은 둘째 인수를 평가 스택에 올린다. add는 두 피연산자를 꺼내 합을 올리고 ret는 반환한다. 여기서는 두 int의 작은 합으로 오버플로가 없다고 제한한다.

아래는 Add의 의미를 설명하는 최소 형태다. 실제 Debug 컴파일은 임시 지역 변수·분기·nop 등을 더 가질 수 있다. 본문에서는 역어셈블을 하지 않았으므로 이 네 줄이 실제 파일의 완전한 바이트열이라고 주장하지 않는다.

// 의미 설명용 CIL 형태
ldarg.0
ldarg.1
add
ret

중간 과정을 따라가는 예제

인수(2,3), 빈 평가 스택으로 설명용 네 명령을 추적한다.

  1. ldarg.0 뒤[2].
  2. ldarg.1 뒤[2,3].
  3. add는3과2를 꺼내 합5를 넣어[5].
  4. ret가5를 호출자에게 반환. 타입 비교 typeof(int)==typeof(System.Int32)는 실제 예제에서True.

오해와 반례

CIL이므로 어떤 CPU·OS에서도 아무 조건 없이 실행된다.

호환 런타임·배포 방식·사용 API와 네이티브 의존성이 필요하다. 특정 OS의 네이티브 라이브러리를 호출하는 프로그램은 중간언어를 썼다고 모든 환경에서 실행되지 않는다.

소단원 1.3

assembly·namespace

같은 폴더에 넣은 클래스는 반드시 같은 namespace와 assembly에 속할까?

준비 개념과 학습 목표

준비 개념

  • 클래스는 값과 메서드의 구조를 정의하는 타입이다. School.Lesson.Program처럼 앞 이름까지 쓰면 어떤 Program인지 구별하기 쉽다.
  • 동일한 짧은 이름을 두 사람이 사용할 수 있다. 학교 이름을 붙여 동명이인을 구별하는 것과 이름의 묶음을 연결해 보자.
  • 의존은 다른 기능을 사용하려면 그 기능을 제공하는 대상이 필요하다는 관계다. 이름을 아는 것과 실제 코드를 갖는 것은 다르다.

학습 목표

  • 이름의 조직과 배포/참조 단위를 구분한다.
  • using과 assembly 참조의 책임을 설명한다.
  • namespace·파일·assembly의 대응이 일대일이 아님을 보인다.

namespace는 타입 이름을 조직한다

namespace는 타입 이름을 조직하고 이름 충돌을 다루는 논리적 공간이다. namespace School.Lesson 안의 Program의 완전한 이름은 School.Lesson.Program이다. using School.Lesson은 적절한 범위에서 Program이라는 짧은 이름을 사용할 수 있도록 돕는다. 파일을 내려받거나 assembly를 자동으로 추가하는 명령은 아니다.

namespace의 점은 이름 계층을 표현하지만 반드시 폴더 경로가 같은 것은 아니다. 서로 다른 파일에서 같은 namespace를 이어 선언할 수 있다. 파일을 옮겼다는 이유만으로 명시된 namespace 이름이 자동으로 바뀌는 언어 규칙도 없다.

assembly는 코드와 정보를 묶는 단위

assembly는 코드·타입 메타데이터·참조 정보 등을 묶는 .NET의 배포·참조 단위다. 관리 실행파일이나 DLL은 assembly가 될 수 있고 DLL이라는 확장자만으로 네이티브/관리 파일을 구별할 수는 없다. 보통의 이 예는 Lesson.dll이라는 단일 파일 assembly로 빌드된다.

한 assembly에 여러 namespace의 타입이 들어갈 수 있고 한 namespace의 타입이 여러 assembly에 나뉠 수도 있다. 외부 타입을 사용하려면 해당 assembly가 빌드에서 참조되고 타입과 멤버의 접근성도 허용되어야 한다. 이름이 정확한 것만으로 private/internal 접근 제한이 없어지지 않는다.

이름 찾기와 코드 제공을 따로 확인한다

School.Lesson.MathTools.Add를 호출하려면 먼저 타입 이름을 해석하고 접근 가능한 메서드를 찾으며 필요한 코드 참조도 준비한다. using은 이름 표기를 줄이는 데 관여한다. 프로젝트 참조는 다른 프로젝트의 산출물을 사용할 관계를 선언한다. 서로 다른 문제를 같은 해결책으로 처리하면 빌드 오류를 이해하기 어렵다.

실제 예제는 School.Lesson이라는 namespace를 두고 AssemblyName을 Lesson으로 지정했다. 런타임에 typeof(Program).Namespace와 Assembly.GetName().Name을 출력해 두 이름이 다름을 확인했다. 아래 표기는 이 실행 예제의 핵심 발췌다.

namespace School.Lesson {
    public static class MathTools {
        public static int Add(int a,int b) { return a+b; }
    }
}
// namespace 이름: School.Lesson
// project AssemblyName: Lesson

중간 과정을 따라가는 예제

Program 타입이 School.Lesson에 선언되고 프로젝트 AssemblyName은 Lesson이다. reflection으로 두 이름을 출력한다.

  1. typeof(Program)은 해당 타입의 정보를 가리킨다.
  2. Namespace 값은 School.Lesson.
  3. Assembly를 얻어 GetName().Name을 읽으면 Lesson.
  4. namespace 이름과 assembly 이름이 다른데도 정상 빌드와 실행이 성공.

실제 출력은 School.Lesson, Lesson이다. 논리 이름 공간과 코드 묶음은 다른 분류다.

소단원 1.4

target framework와 dependency

SDK를 바꿨는데 프로젝트의 net8.0은 그대로라면 사용할 API도 자동으로 모두 바뀔까?

준비 개념과 학습 목표

준비 개념

  • 계약은 서로 맞추어야 할 요구와 약속이다. 부품의 규격이 맞아야 연결된다는 비유를 API 사용 조건에 적용하자.
  • 그래프는 대상을 점, 의존 관계를 화살표로 표시한 것이다. 앱→라이브러리는 앱이 라이브러리 기능을 사용한다는 뜻이다.
  • 버전은 변경된 대상의 구분이다. 개발 도구의 버전과 실행 환경의 버전은 서로 다른 대상을 나타낼 수 있다.

학습 목표

  • SDK·TFM·언어버전·런타임 버전을 구별한다.
  • 프레임워크와 프로젝트/패키지 의존성 호환 조건을 설명한다.
  • 빌드 성공과 배포 환경의 실행 성공을 구별한다.

대상 프레임워크는 사용할 API 계약

Target Framework Moniker(TFM)는 프로젝트가 대상으로 삼는 프레임워크를 표시한다. net8.0 프로젝트는 해당 API 계약을 기준으로 빌드된다. 특정 OS 기능을 포함하는 net8.0-windows 같은 표기는 플랫폼 조건도 드러낸다. TFM은 컴파일한 CPU 명령의 개수나 SDK의 정확한 패치 번호를 뜻하지 않는다.

SDK는 빌드 도구 선택, LangVersion은 C# 문법 선택, TFM은 대상 API 계약이다. 이 예는 SDK8.0.204/C#12/net8.0을 명시한다. 지원하는 SDK라면 다른 대상도 빌드할 수 있으므로 세 값을 같은 숫자로 묶어 생각하지 않는다.

의존성을 해결하는 일과 실행할 수 있는 일

ProjectReference는 다른 프로젝트에 대한 의존, PackageReference는 패키지 의존을 선언한다. 복원은 적합한 자산과 의존 그래프를 해결한다. 자신의 TFM에서 사용할 수 없는 라이브러리 API를 참조했다고 using 하나로 호환성이 생기지는 않는다. 호환 여부는 대상과 제공 자산을 확인해야 한다.

framework-dependent 앱은 실행 컴퓨터의 호환 공유 런타임이 필요하다. self-contained 배포는 런타임을 함께 제공하지만 OS·CPU·네이티브 의존 조건까지 사라지지 않는다. SDK를 고정하는 global.json은 런타임의 정확한 패치 선택을 직접 고정하는 파일이 아니다.

종이 호환표와 실제 확인의 차이

이번 예제는 추가 패키지 없이 net8.0의 기본 참조를 사용한다. 프로젝트 안의 NuGet.Config는 외부 패키지 소스를 비워 놓고 설치된 참조팩으로 복원·빌드했다. 온라인 패키지 다운로드나 모든 패키지 호환성을 시험한 기록이 아니다.

라이브러리가 net9.0 자산만 제공하고 앱이 net8.0이면 그 높은 API 계약을 낮은 대상으로 사용하지 못하는 조건을 따져야 한다. 반대로 net8.0 자산을 지원하는 앱이 사용한다고 해서 모든 OS별 기능이 어디서나 되는 것은 아니다. API 호환과 플랫폼 조건을 별도 열로 적는다.

// 예제의 서로 다른 선택
SDK: 8.0.204 (global.json)
Language: C#12 (LangVersion)
Target API: net8.0 (TargetFramework)
Dependency: 기본 프레임워크, 추가 패키지 없음

중간 과정을 따라가는 예제

앱A는 net8.0, 라이브러리B는 net8.0 자산, C는 net9.0 자산만 제공한다고 가정한다. 플랫폼별 기능과 추가 패키지는 제외한다.

  1. A→B는 동일 대상 API 범위로 참조 가능성을 검토할 수 있다.
  2. A→C는 C가 요구하는 더 높은 프레임워크 API를 A가 보장하지 못한다.
  3. A를 지원하는 SDK로 빌드하는 문제와 배포 컴퓨터의 런타임 조건은 분리한다.
  4. 실제 자체 예제A는 외부 패키지 없이 net8.0 빌드·실행 성공을 확인했다. B/C 참조 실험은 하지 않았다.

A→B의 호환 가능성과 A→C의 높은 대상 제약을 구별한다. 이 예의 실제 성공을 모든 의존성 조합으로 확대하지 않는다.

종이와 본문으로 직접 해보기

오해와 반례

빌드가 성공하면 모든 컴퓨터에서 바로 실행된다.

배포 컴퓨터에 필요한 런타임이 없거나 OS 전용 의존성이 맞지 않으면 실패할 수 있다. 빌드 성공은 지정된 참조와 언어 규칙 통과이며 모든 실행 환경의 보증이 아니다.
