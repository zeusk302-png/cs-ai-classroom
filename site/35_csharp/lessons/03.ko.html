소단원 3.1

overload·optional argument

같은 Add 이름을 여러 번 선언하면 실행 중 아무 메서드나 고를까?

준비 개념과 학습 목표

준비 개념

  • 메서드는 이름·매개변수·본문·반환형을 가진 호출 가능한 멤버다. 호출 인자는 호출자가 제공하는 식이고 매개변수는 선언의 이름이다.
  • int는 32비트 정수이고 long은 64비트 정수다. 정수 리터럴 3은 int이며 3L은 long이다. int에서 long으로 암시적 변환이 가능하지만 반대는 일반적으로 명시적 변환이 필요하다.
  • 자가진단: Add(5)에서 5는 인자이고 선언 int Add(int x,int step=2)의 x와 step은 매개변수다.

학습 목표

  • 정적 호출의 후보와 더 나은 변환을 구별한다.
  • 이름 인자와 생략 기본값의 계약을 설명한다.
  • 기본값 변경과 호출자 재컴파일의 경계를 판단한다.

이름이 같아도 서명은 다르다

오버로드는 같은 이름에 서로 다른 매개변수 서명의 메서드를 제공한다. 반환형만 int에서 long으로 바꾸는 것으로 같은 매개변수 메서드를 두 개 선언할 수는 없다. 호출자는 인자 수·타입·변환과 이름 인자에 따라 적용 가능한 후보를 찾는다. 이 단원은 일반적인 정적 호출만 다루며 dynamic·가상 메서드 재정의의 실행시 선택과 구별한다.

Pick(int)와 Pick(long)에서 Pick(3)은 int에 대한 항등 변환을 선택하고 Pick(3L)은 long에 대한 항등 변환을 선택한다. 작은 수라는 실제 크기만 보고 선택하지 않는다. long 변수에 3이 들어 있어도 선언된 타입이 long이면 long 후보가 선택된다. 이 두 후보의 비교를 모든 오버로드에 대한 단순 숫자 순위 규칙으로 일반화하지 않는다.

생략과 이름은 호출 계약이다

Add(int x,int step=2)에서 x는 필수이고 step은 선택 매개변수다. Add(5)는 step=2를 전달하는 호출이며 Add(step:4,x:5)는 이름으로 위치를 연결한다. 명시 인자 식의 평가는 호출에 적힌 순서로 진행하므로 이름으로 순서를 바꾸었다고 선언 순서로 부작용을 평가하지 않는다. 예제에는 부작용 있는 인자를 쓰지 않는다.

기본값은 허용된 상수식·값 타입 초기화/default 규칙을 따라야 한다. 런타임 입력을 받는 임의 식을 기본값에 둘 수 없다. nullable 타입이라는 사실도 생략 가능성을 만들지 않는다. 정적으로 컴파일된 일반 호출의 생략 인자는 호출자가 본 선언의 기본값으로 전달되므로 라이브러리 기본값만 2에서 4로 바꿔도 기존 호출자 바이너리에 저장된 2가 자동 4가 되지 않는다. 이 설명은 dynamic/COM 호출을 대상으로 하지 않는다.

짧은 호출도 모호할 수 있다

기본 인자를 가진 후보가 여러 개면 생략한 부분까지 포함해 하나가 언제나 결정되는 것이 아니다. M(int x=0)와 M(string x="")만 있으면 M()은 두 후보 모두 적용 가능하고 어느 명시 인자 변환도 더 낫지 않아 모호하다. 이 변형은 컴파일 오류 조건의 종이 분석이며 실행 출력이 없다.

Add는 checked 덧셈을 사용한다. 수학적 합이 int 표현범위 안이면 그 합을 반환하고 범위를 벗어나면 OverflowException이 발생한다. 5+2와 5+4는 정상 범위다. 같은 인터페이스 이름이 선택 규칙·실패 조건·기본값을 모두 숨기는 것은 아니므로 문서에 세 가지를 함께 적는다.

중간 과정을 따라가는 예제

아래 정상 코드의 후보 선택과 두 합을 추적한다.

  1. 3은 int이므로 Pick(int)를, 3L은 long이므로 Pick(long)를 선택한다.
  2. Add(5)는 x=5이고 생략된 step=2다.
  3. Add(step:4,x:5)는 이름을 연결하여 x=5,step=4다.
  4. checked의 두 합 7과 9는 표현 가능하므로 두 줄 int long / 7 9를 출력한다.

실제 stdout은 int long 7 9 이다.

풀이 보기

10과 8이다. M()은 두 후보가 적용 가능하지만 더 나은 후보가 없어 모호한 컴파일 오류다. 오류 출력은 예측하지 않는다.

오해와 반례

기본값은 메서드 안에서 매번 읽으므로 라이브러리만 바꾸면 모든 기존 호출도 바뀐다.

일반 정적 호출에서는 생략 기본값이 호출에 전달된다. 기존 호출자와 새로 컴파일한 호출자의 기본값이 달라질 수 있으므로 공개 API 변경을 호환성 관점에서 검토한다.

한 단계 더

심화: 정상 Add의 사후조건 r=x+step은 int.MinValue≤x+step≤int.MaxValue라는 수학 정수 조건 아래 성립한다. checked는 이 조건이 깨지면 다른 정수로 성공하는 대신 예외를 낸다. 공개 기본값은 호출자 계약의 일부이므로 v1 호출자·v2 호출자·v2 라이브러리를 표로 나누어 각각 전달되는 step을 기록한다. 현재 실행은 두 정상 합만 확인했고 버전이 다른 라이브러리 교체 실험은 하지 않았다.

소단원 3.2

ref·out·in

상자 속 값을 바꾸는 것과 상자 안의 객체를 바꾸는 것은 같은가?

준비 개념과 학습 목표

준비 개념

  • int 변수 상자는 정수 값을 보관한다. 클래스 변수는 객체 참조를 보관하므로 상자의 참조 재대입과 객체 필드 수정이 다르다.
  • 값 전달은 인자의 값을 매개변수에 복사한다. 복사한 클래스 참조도 같은 객체를 가리킬 수 있다. ref 전달은 호출자의 변수 위치를 참조하는 별도의 계약이다.
  • 자가진단: b.Value=9는 객체를 수정하지만 b=new Box()는 그 변수의 참조를 바꾼다.

학습 목표

  • ref/out/in의 초기화·쓰기·정상 반환 조건을 구별한다.
  • Try 패턴의 bool과 out 결과 계약을 함께 읽는다.
  • 읽기 전용 참조와 깊은 불변성을 구분한다.

호출자의 위치를 빌리는 ref

ref int x는 호출자의 이미 초기화한 int 변수 위치를 읽고 쓸 수 있게 한다. Bump(ref a)가 x에 4를 쓰면 a가 4가 된다. 선언과 호출에 ref가 필요하며 보통 속성 값이나 상수는 직접 참조 가능한 변수 위치가 아니므로 ref 인자로 전달할 수 없다. 참조의 유효 범위를 지키도록 컴파일러가 수명 규칙도 검사한다.

기본 클래스 값 전달에서 객체 필드가 바뀌는 사실을 ref라고 부르면 안 된다. 참조 값을 복사해도 같은 객체의 필드는 수정할 수 있지만 매개변수 재대입으로 호출자의 변수 위치는 바뀌지 않는다. ref 클래스 매개변수는 그 호출자 위치 자체까지 재대입할 수 있다는 점에서 더 강하다.

out은 정상 반환의 대입 의무다

out int half는 호출 전에 초기화하지 않아도 전달할 수 있지만 메서드는 정상 반환하는 모든 경로에서 half를 확정 대입해야 한다. TryEven은 먼저 0을 쓰고 홀수면 false, 짝수면 x/2를 쓰고 true를 반환한다. 따라서 false일 때도 결과는 정의된 0이다. 일반 Try API의 false 결과가 언제나 사용 가능하다는 뜻은 아니므로 해당 계약을 읽는다.

이 예제의 사후조건은 true이면 x가 짝수이고 2×half=x, false이면 x가 홀수이고 half=0이다. 수학 정수로 기술한 조건이며 C# int x/2는 여기서 안전하다. 예외로 빠져나간 경로는 정상 반환의 out 보장으로 덮지 않는다. bool만 검사하지 않고 out만 해석하면 false의 0을 짝수 입력 성공으로 오인할 수 있다.

in의 읽기 전용 경계

in int x는 매개변수를 통한 쓰기를 금지한다. 호출에 in을 명시하면 참조 가능한 위치와 맞는 타입이 요구된다. 호출에 in을 생략한 경우에는 리터럴·변환·속성 값 등을 임시 변수로 만들어 읽기 전용 참조로 전달할 수 있다. 이 단원의 Read(in a)는 직접 int 위치를 전달한다.

in Box b는 b의 참조를 재대입하지 못하게 하지만 b가 가리키는 객체의 가변 Value 필드를 9로 바꾸는 것은 허용한다. 따라서 in이 깊은 불변성·스레드 안전·성능 향상을 증명하지 않는다. ref/out/in만 서로 바꾼 동일 매개변수 목록으로 오버로드할 수 없고 값 전달과 참조 전달의 오버로드는 별도 규칙이 있다. 여기서는 동기 일반 메서드만 사용한다.

중간 과정을 따라가는 예제

Bump,TryEven,Read,Mutate의 호출자 상태를 네 단계로 추적한다.

  1. a=3에서 Bump가 같은 위치에 4를 기록한다. checked 증가가 이 값에서는 성공한다.
  2. TryEven(4,out half)는 0을 쓴 뒤 짝수 분기에서 2를 쓰고 true를 반환한다. Read(in a)는 4를 읽는다.
  3. TryEven(5,out half)는 0을 쓰고 홀수 분기에서 false를 반환한다.
  4. Value=4인 Box의 읽기 전용 참조 b를 전달해 객체 필드를 9로 바꾼다.

실제 세 줄은 4 True 2 4 / False 0 / 9다.

오해와 반례

out은 성공할 때만 쓰면 되고 in은 객체 전체를 얼린다.

out은 false를 포함한 모든 정상 반환 경로에서 대입해야 한다. in은 해당 참조를 통한 위치 쓰기를 제한하며 가리키는 가변 객체까지 불변으로 만들지 않는다.

한 단계 더

심화: TryEven의 두 분기는 int의 짝수/홀수 경우를 모두 나눈다. 짝수이면 나눗셈의 나머지가 0이어서 수학적 2×half=x이고 홀수이면 먼저 기록한 0을 보존한다. 초기화와 정상 반환 의무를 검토하면 모든 반환 경로의 결과가 정의됨을 보일 수 있다. Bump는 a<int.MaxValue라는 충분조건에서 정상 증가하며 최댓값 실패 변형은 실행하지 않았다. 별칭으로 같은 위치를 여러 인자에 전달하거나 동시에 수정하면 별도 순서·동기화 계약이 필요하다.

소단원 3.3

expression-bodied member

화살표 한 줄이면 상태도 바뀌지 않는 함수일까?

준비 개념과 학습 목표

준비 개념

  • 식은 평가되어 값을 만들거나 부작용을 일으킨다. 문장은 실행 흐름과 대입을 기술한다. 함수 반환과 Console 출력은 별도 사건이다.
  • 속성은 obj.P라는 접근 문법을 가지지만 getter가 코드를 실행할 수 있다. 필드의 저장 값을 읽는 것과 계산형 속성을 평가하는 것을 구분한다.
  • 자가진단: ++count는 count를 먼저 1 증가시키고 그 새 값을 만든다. count=0은 0을 기록하는 대입식이다.

학습 목표

  • 값 반환·void의 화살표 본문 규칙을 구분한다.
  • 속성의 반복 평가와 상태변화를 추적한다.
  • 표현의 짧음과 순수성·종료·오류 조건을 구별한다.

본문을 줄이는 문법

T M()=>expr;는 반환 값이 expr인 메서드의 짧은 본문 표기다. expr의 결과는 T로 암시적으로 변환 가능해야 한다. 예제 Twice(int x)=>checked(2*x)는 return checked(2*x);를 가진 블록으로 풀어 읽을 수 있다. 문법이 짧아도 입력·반환형과 checked의 실패 조건이 없어지지 않는다.

void M()=>expr;에서는 호출·대입·증가처럼 허용되는 문장식이어야 하고 그 결과 값은 버린다. Reset()=>count=0;은 대입식이어서 유효하지만 void M()=>1+2;는 단순 덧셈식이라 유효한 void 본문이 아니다. 실패 선언은 종이 판정이며 컴파일 실행의 정답 근거로 쓰지 않았다.

계산형 getter는 매번 실행된다

Next=>checked(++count)는 저장된 자동 속성이 아니라 getter 본문이다. c.Next를 한 번 읽을 때 count를 증가시키고 그 새 값을 반환한다. 초기 count=0에서 두 접근은 1,2다. 두 번째가 첫 번째 계산의 캐시를 읽는다고 가정하면 결과를 틀린다.

Reset은 count를 0으로 바꾼다. 이후 Next는 1이고 Twice(3)는 6이다. Twice는 count를 사용하지 않아 이 예제의 객체 상태 변화와 독립이다. 모든 속성을 부작용 없이 설계해야 한다는 문법 규칙은 없지만 값 조회처럼 보이는 API의 부작용은 클라이언트가 놀라지 않도록 문서화·설계해야 한다.

화살표와 수학 함수는 다르다

같은 => 기호는 람다의 인자와 본문 사이에도 사용된다. 이미 이름과 반환형을 선언한 멤버의 본문과 익명 함수를 만드는 표현은 문맥으로 구별한다. Next는 상태를 바꾸므로 같은 객체에 같은 접근을 반복해도 값이 달라지고 참조 투명하다고 할 수 없다.

Twice는 -1073741824≤x≤1073741823인 int 입력에서 수학적 2x를 정상 반환한다. 이 범위 밖에서는 checked 곱셈이 예외를 낸다. Next도 count<int.MaxValue일 때만 정상 증가한다. 여기서는 세 정상 증가만 실행했으며 예외·동시 접근·성능·자동 메모화에 대한 실행 근거는 없다.

중간 과정을 따라가는 예제

Counter의 네 가지 접근을 실제 코드 순서대로 추적한다.

  1. 새 Counter의 count는 int 기본값 0이다. 첫 Next는 1을 기록하고 1을 반환한다.
  2. 두 번째 Next는 count=1에서 2를 기록하여 첫 줄 1 2가 된다.
  3. Reset이 count를 0으로 바꾼 뒤 Next는 1을 기록한다.
  4. Twice(3)는 count를 바꾸지 않고 6을 반환해 두 번째 줄 1 6이 된다.

실제 stdout은 1 2 1 6 이다.

종이와 본문으로 직접 해보기

새 c에서 c.Next,c.Twice(4),c.Next,c.Reset(),c.Next 순서를 표로 추적한다. void F()=>2*3;도 판정한다.

힌트 보기

반환 값 열과 count 열을 분리한다. Reset은 반환 값이 없는 대입이다.

풀이 보기

반환은 1,8,2,없음,1이고 count는 1,1,2,0,1이다. void F의 곱셈은 문장식이 아니므로 해당 선언은 유효하지 않다.

오해와 반례

화살표 속성은 한 번만 계산되므로 두 접근이 같은 값을 준다.

계산형 getter는 접근할 때마다 실행된다. ++count가 있는 Next가 1과 2를 반환하는 것이 반례다. 짧은 표기가 캐시나 순수성을 보장하지 않는다.

자기점검

답과 이유 보기

Twice는 x만 사용하며 count에 대입하지 않는다.

Reset의 대입식 결과 0이 호출자에게 반환되는가?

답과 이유 보기

아니다.

void 멤버의 문장식 결과는 버리고 상태만 바꾼다.

Twice(int.MaxValue)가 정상 정수 결과를 보장하는가?

답과 이유 보기

아니다.

checked의 표현범위 밖 곱셈은 예외이며 정상 계약의 범위 밖이다.

한 단계 더

심화: reset 없이 count=0에서 k번 순차 정상 Next를 호출하고 0≤k≤int.MaxValue인 정수 k라면 귀납으로 최종 count=k다. 초기 0이고 각 호출은 이전값+1을 기록하기 때문이다. 다른 쓰기·동시 호출이 있으면 귀납의 전제가 깨진다. Twice의 값 계산은 범위 안에서 블록 return과 동일하지만 이 동등성이 임의 화살표 멤버를 순수 수학 함수로 만드는 것은 아니다.

소단원 3.4

문자열·pattern matching

문자열을 붙였는데 별칭의 글자는 왜 바뀌지 않을까? null과 빈 글자는 같은가?

준비 개념과 학습 목표

준비 개념

  • string 변수는 문자열 객체 참조를 가진다. null은 대상 문자열 객체가 없는 참조이고 ""는 길이 0인 실제 문자열 객체다.
  • 패턴은 입력 값이 어떤 형태·타입·조건을 만족하는지 검사한다. switch 식은 맞는 가지의 결과 값을 선택한다.
  • 자가진단: int 0은 값이 있는 정수다. null과도 빈 문자열과도 다른 경우로 분류한다.

학습 목표

  • 문자열 불변성과 변수 재대입을 추적한다.
  • null·타입·속성·guard 패턴의 경계를 설명한다.
  • UTF-16 길이와 보이는 글자 수를 구별한다.

객체의 불변성과 참조 재대입

string 객체의 내용은 생성 후 바꿀 수 없다. a="A";b=a;a+="B";는 a에 붙인 결과 "AB"의 참조를 새로 대입하고 b는 원래 "A"를 보존한다. 원래 객체가 별칭 b를 통해 남아 있으므로 이 코드로 원래 문자열의 즉시 수거를 주장할 수도 없다.

불변성은 string 변수에 다른 참조를 대입할 수 없다는 뜻이 아니다. null에서는 Length 접근이 정상 문자열 읽기가 아니지만 빈 문자열은 객체가 있으므로 Length가 0이다. nullable 주석 string?와 object?는 정적 경고 분석을 돕고 런타임에서 null을 자동 차단하거나 모든 입력을 검증하지 않는다.

형태와 조건으로 분류한다

Classify의 첫 가지는 null을 missing으로 분류한다. string {Length:0}은 null이 아닌 string의 길이 0을 empty로 분류하고 다음 string 패턴은 양의 길이 문자열과 변수 s를 연결한다. 속성 패턴은 먼저 null이 아닌 대상이 있어야 맞으므로 이 형태로 null.Length를 무조건 평가하는 코드를 쓰지 않는다.

int n when n>=0은 int 타입 확인과 guard 조건을 모두 만족해야 count 결과를 만든다. -1은 이 guard를 통과하지 않아 마지막 _에서 other가 된다. switch 식은 먼저 맞는 arm의 결과를 선택하며 마지막 _가 null을 포함한 나머지 입력을 덮는다. 이 분류기는 외부 텍스트 숫자를 int로 파싱하거나 업무 의미를 검증하는 함수가 아니다.

Length의 단위와 패턴의 한계

String.Length는 UTF-16 Char 코드 단위 수다. ASCII hi는 2이고 U+1F600 한 코드 포인트는 서로게이트 쌍 두 단위로 표현되어 예제 길이가 2다. 따라서 Length>0은 비어 있지 않다는 검사는 가능하지만 사용자에게 보이는 글자 수나 UTF-8 바이트 수를 측정하지 않는다. 결합 문자와 이모지의 표시 단위는 별도 텍스트 규칙이 필요하다.

x is null은 사용자 정의 == 연산자를 호출하지 않는 null 패턴 검사다. 형태가 맞는다는 사실도 순수성·안전성·종료를 자동 증명하지 않는다. 사용자 정의 속성 getter는 부작용이나 예외가 있을 수 있으므로 이 예제의 표준 string.Length와 임의 객체의 속성을 구분한다. 현재 코드는 C#12로 컴파일한 네 가지 오래 지원된 패턴 형태만 사용한다.

중간 과정을 따라가는 예제

문자열 별칭과 Classify의 다섯 입력 및 이모지 길이를 추적한다.

  1. a와 b가 같은 "A"를 가리킨 뒤 a 재대입으로 AB A를 출력한다.
  2. null은 missing,빈 문자열은 empty,hi는 길이 2여서 text:2다.
  3. -1은 int이지만 guard에 실패해 other이고 0은 count:0이다.
  4. U+1F600은 UTF-16 두 단위여서 마지막 출력 2다. 이 출력은 화면 글자 수의 측정이 아니다.

실제 줄은 AB A / missing / empty / text:2 / other / count:0 / 2다.

종이와 본문으로 직접 해보기

Classify("A"),Classify(7),Classify(7L)를 종이로 분류하고 a="X";b=a;a+="Y" 뒤 b를 적는다.

힌트 보기

값 7과 타입long을 구분한다. 별칭 b를 새 참조로 재대입한 명령은 없다.

풀이 보기

text:1,count:7,other다. 7L은 long이어서 int 패턴에 맞지 않는다. b는 X를 보존하고 a는 XY다.

오해와 반례

Length는 글자 수이고 string이 불변이면 a+="B"는 불가능하다.

Length는 UTF-16 코드 단위 수이며 U+1F600의 길이 2가 반례다. 불변 객체를 수정하지 않고 변수 a에 결합 결과를 재대입하는 것은 가능하다.

자기점검

Classify(null)이 empty인가?

답과 이유 보기

missing이다.

null과 길이 0인 문자열 객체는 다르고 첫 arm이 null을 처리한다.

Classify(-1)이 count:-1인가?

답과 이유 보기

other다.

int guard n>=0이 실패한다.

object? 주석이 런타임 null 입력을 막는가?

답과 이유 보기

아니다.

nullable 주석은 주로 정적 분석 정보이며 실제 null 가지 처리는 별도로 작성했다.

한 단계 더

심화: 입력을 null,빈 string,양의 길이 string,비음수 int,나머지의 다섯 집합으로 나눈다. string.Length는 비음수이고 string과 int는 서로 다른 타입이므로 이 분류들은 서로 겹치지 않으며 마지막 집합을 앞 네 집합의 여집합으로 두면 모든 object? 값을 덮는다. 따라서 각 정상 입력에 한 결과가 선택된다. 이는 외부 파싱·업무 유효성·시간 복잡도·사용자 문자 단위의 정확성을 보장하는 증명은 아니다.
