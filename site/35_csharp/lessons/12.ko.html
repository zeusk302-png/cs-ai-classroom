바이트 조각의 끝이 문자나 문서의 끝일까?

앞 본문에서 B나의 UTF-8 바이트는 42 EB 82 98이고 C# 문자열 길이는 2였다. 새 입력은 첫 조각 42 EB와 둘째 조각 82 98로 나뉜다. EB는 나의 첫 바이트여서 아직 두 바이트가 더 필요하다. 조각마다 독립 문자열로 디코딩하면 첫 조각 끝과 둘째 조각 시작을 모두 잘못된 문자열로 볼 수 있다. 읽기 반환 경계와 문자 경계가 일치한다는 전제가 없기 때문이다.

새 규약은 UTF8Encoding(false,true)에서 얻은 같은 Decoder를 사용하며 충분한 문자 출력 공간을 확보한다. 첫 조각에서 flush=false로 읽으면 B를 내보내고 미완성 EB를 다음 조각을 위해 보관한다. 둘째 조각 뒤 실제 문서 끝에서 flush=true이면 나를 완성한다. 새 독립 입력 EB 82만 있고 실제 EOF라면 마지막 바이트가 없어 엄격 디코더의 오류 경로다. 실제 Decoder를 실행한 결과가 아니라 UTF-8 구조와 상태 계약을 손추적한 예측이다.

문자열 생성 뒤에도 JSON 문법과 업무 검증은 별도다. 새 자체 schema는 이름이 정확히 version과 Score인 두 속성만 한 번씩 허용하고 둘 다 정수 토큰이어야 한다. version은 1, Score는 0부터 100까지다. 대소문자가 다른 이름·중복 이름·추가 속성·문자열 숫자를 거절한다. JSON object의 모든 속성을 열거하여 검증한 후보만 현재 상태에 한 번 게시한다. 기본 deserializer 옵션이 이 정책을 자동 수행한다는 주장은 아니다.

예를 들어 현재 점수 40에서 {"version":1,"Score":8,"Score":90}은 문법으로 읽을 수 있어도 자체 중복 금지 정책에서는 거절하여 현재 점수 40을 보존한다. 먼저 첫 Score를 현재 상태에 쓰고 나중 오류를 발견하는 방식은 실패 보존 계약을 깨뜨린다. 문자열 디코딩 상태와 업무 후보 상태 모두 중간 정보를 보존하지만 무엇을 언제 공개하는지는 각 단계의 다른 계약이다.

자료를 흘리는 Stream

Stream은 순서 있는 바이트를 읽고 쓰는 통로다. FileStream은 파일을, MemoryStream은 메모리를 바탕으로 같은 추상화를 사용한다. 모든 스트림이 읽기·쓰기·임의 위치 이동을 전부 지원하는 것은 아니므로 CanRead, CanWrite, CanSeek를 확인한다.

StreamReader와 StreamWriter는 인코딩 규칙을 이용해 바이트와 문자를 바꾼다. Buffering은 전달 효율을 돕고 encoding은 글자의 뜻을 결정한다. 이름이 text.txt여도 내용의 인코딩이 자동으로 결정되지 않는다. 읽기 실패와 잘못된 데이터는 별도의 오류로 처리하고 열린 자원은 정해진 범위에서 닫는다.

문자 수와 파일 크기는 다르다

B나 나 같은 글자는 문자열에서는 글자 표현이지만 UTF-8 저장 시 다른 바이트 수를 쓴다. BOM과 줄바꿈이 없는 B나는 42 EB 82 98 네 바이트다. C# string.Length는 UTF-16 코드 단위 수라 이 예제는 2지만 모든 눈에 보이는 글자 수를 그대로 세는 함수는 아니다.

문자셋·BOM 유무·줄바꿈 규칙을 함께 약속하면 다른 프로그램도 같은 뜻으로 읽기 쉽다. UTF-8 글자를 중간 바이트에서 자르면 정상 문자 하나를 깨뜨릴 수 있다. 스트림을 작은 조각으로 읽을 때 문자 디코더가 미완성 글자를 이어 처리해야 하며 매 바이트를 문자로 강제 변환하는 방법은 피한다.

객체를 교환 형태로 바꾸기

JSON 직렬화는 객체의 정해진 멤버를 JSON 값으로 표현하는 과정이다. System.Text.Json의 기본 옵션은 public properties를 포함하고 일반 fields는 제외한다. Score가 public 속성이고 Secret이 일반 public field인 객체라면 기본 결과에 Score는 나타나지만 Secret은 같은 이유로 자동 포함되지 않는다.

Serialize는 문자열을, SerializeToUtf8Bytes는 UTF-8 바이트를 얻는 선택이다. 기본 encoder는 비 ASCII 글자를 escape할 수 있으므로 사람이 보이는 한글과 파일에 직접 적힌 한글은 다를 수 있다. 파싱과 업무 범위 검증은 별개이고, 저장할 멤버·이름·버전·옵션을 명시해야 출력 형식을 안정적으로 교환한다.

  2. 총 1+3=4바이트이며 이 예제의 Length는 2다.

  3. 기본 public property 포함 규칙으로 Score를 포함한다.

  4. 일반 field인 Secret은 기본 제외하며 옵션을 바꾸면 결과가 달라질 수 있다.

연습 1 · 값과 상태 예측

새 입력 42 EB 82에서 실제 EOF가 왔다. 엄격 디코더로 전체 문서를 성공했다고 게시할 수 있는가?

힌트 1

EB 82 뒤 필요한 마지막 바이트 수를 센다.

힌트 2

마지막 flush는 미완성 상태를 다음 문서로 넘기지 않는다.

풀이와 답 확인

  1. B는 해독할 수 있지만 나의 마지막 바이트가 없다.

  2. 진짜 EOF의 최종 flush에서 실패하여 전체 문서 성공으로 게시하지 않는다.

부분 B가 있어도 전체 문서는 실패다.

B 하나를 읽었으니 나머지를 무시하고 성공이다.

연습 2 · 오류 찾아 고치기

각 읽기마다 새 Decoder를 만들고 flush=true를 쓴다. 원래 두 조각의 오류 원인을 고쳐라.

힌트 1

첫 조각의 EB가 이어질 상태를 표시한다.

힌트 2

읽기 끝과 실제 EOF를 구별한다.

풀이와 답 확인

  1. 첫 조각 끝을 문서 끝으로 잘못 선언하여 미완성 EB를 거절한다.

  2. 같은 문서의 Decoder 상태를 유지하고 중간에는 flush=false, 실제 끝에서만 최종 flush를 한다.

다른 독립 문서에는 새 상태를 쓰되 같은 문서의 조각 사이에는 상태를 보존한다.

파일을 기다리는 동안 버튼을 다시 누를 수 있게 하려면 무엇을 바꿔야 할까?

늦게 끝난 옛 요청이 새 화면을 덮어써도 될까?

앞 본문은 기다리는 동안 UI가 다른 일을 할 수 있다는 점을 다뤘다. 새 자체 화면 계약은 가장 최근에 시작한 요청의 성공 결과만 게시하는 것이다. 단일 UI 사건 순서에서 A를 시각 0에 시작하여 generation 1로 기록하고 B를 시각 10에 시작하여 generation 2로 올린다. B는 시각 30에 payload 20으로 끝나고 A는 시각 80에 payload 10으로 끝난다. 수치는 가상 밀리초이며 CPU 처리 지연은 0으로 두었다.

완료마다 무조건 화면에 쓰면 30에 20을 썼다가 80에 옛 10으로 되돌아간다. 요청이 시작할 때 자기 generation을 저장하고, 완료 후 게시 전에 현재 generation과 일치하는지 확인하면 B의 2는 허용되고 A의 1은 거절된다. 비교와 게시가 같은 UI 사건 안에서 원자적으로 진행된다는 자체 전제가 필요하다. 여러 스레드가 그 사이에 새 요청을 넣을 수 있는 구현까지 이 종이 표로 인증하지 않는다.

A에 취소를 요청하는 것은 유용할 수 있지만 완료/중단 보장은 아니다. 취소 요청 뒤 A가 여전히 성공 결과를 반환하는 사건도 이 화면 정책에서 안전하게 걸러야 한다. 또한 최신 B가 실패하면 옛 A의 성공을 자동 게시하는 것이 아니라 이전 화면을 유지하고 B의 실패를 보고하도록 여기서 정책을 고정한다. 자동 fallback이 필요하면 다른 요구로 명시한다.

기다리는 시간과 계산하는 시간을 나눈다

파일이나 네트워크는 결과가 올 때까지 시간이 걸릴 수 있다. UI 스레드가 동기 호출 안에서 막혀 있으면 다른 입력을 처리하지 못할 수 있다. 비동기 I/O는 결과를 기다리는 동안 제어를 돌려 다른 독립 작업을 처리할 기회를 주는 구조다. 기다릴 일이 없거나 이미 완료된 Task라면 await에서 실제로 중단하지 않을 수도 있다.

async라는 단어를 함수에 붙인다고 계산이 자동으로 다른 스레드로 이동하지 않는다. 오래 걸리는 CPU 반복문은 여전히 실행 스레드를 점유할 수 있다. I/O 대기와 CPU 계산을 구별하고, 비동기를 도입하는 목적이 응답성인지 처리량인지 먼저 적는다.

Task는 결과 자체가 아니라 완료 상태를 추적한다

Task<string>은 문자열 결과를 나중에 얻을 작업을 나타낸다. 호출 직후 Task를 받았다는 사실은 파일 내용이 준비됐다는 뜻이 아니다. await는 완료된 결과를 얻거나 실패를 관찰하며, 진행 중일 때는 함수의 남은 부분을 이어 실행할 수 있도록 보존하고 caller로 제어를 돌린다.

본문의 의존 관계는 읽기 요청 → 읽기 완료 → 읽은 내용 해석 순서다. 제목 미리 표시처럼 결과와 무관한 일은 기다리는 사이 할 수 있지만, 내용 길이 계산은 결과가 있어야 한다. Result나 Wait로 동기적으로 막으면 응답성을 다시 잃고 특정 문맥에서 교착 위험도 생길 수 있어 비동기 호출 체인에서 await를 이어 쓰는 이유가 있다.

실패와 자원 수명도 완료를 기다린다

파일을 읽는 작업이 진행 중인데 스트림을 먼저 닫으면 후속 작업이 사용할 자원이 사라진다. 요청을 시작한 범위는 실제 완료나 실패를 관찰한 뒤 자원을 정리하도록 설계한다. 비동기 함수의 예외는 Task를 통해 전달될 수 있으므로 결과를 얻는 await 주위에서 오류를 처리한다.

취소 요청은 협조를 구하는 신호이지 이미 완료된 파일 쓰기를 되돌리는 버튼이 아니다. API가 취소를 지원하는지와 완료 상태를 확인하고 화면의 취소 표시와 저장 상태를 혼동하지 않는다. 이 수업의 시간은 가상 일정이며 비동기 API가 파일 장치를 더 빠르게 만든다는 측정 결과가 아니다.

attribute를 읽기만 해도 생성자가 실행될 수 있을까?

앞 본문의 메뉴 선택은 public 메서드의 metadata를 걸러 정렬하는 단계였다. 새 자체 OrderAttribute 생성자는 실행될 때 static calls를 1 증가시키며 입력 정수를 그대로 저장한다. 메서드 P에는 Order(2), Q에는 Order(1)을 적었다. calls는 처음 0이다. 특성 인스턴스를 생성하여 값을 읽는 GetCustomAttributes 계열과 선언된 인수를 표현하는 CustomAttributeData는 같은 종류의 관찰이 아니다.

CustomAttributeData로 두 선언의 constructor argument를 읽는 자체 경로는 특성 생성자를 호출하여 의미를 계산하는 경로가 아니므로 calls는 0인 상태로 두 값 2와 1을 얻는다. 별도 경로에서 두 특성 인스턴스를 각각 한 번 생성하면 calls는 2다. 실제 API는 조회 반복마다 어떤 캐싱이 있는지 이 표로 보장하지 않으므로 반복 호출 횟수는 별도 실측으로 남긴다. 특성 생성자가 인수를 변환하면 metadata의 선언값과 생성 후 property 값도 다를 수 있다.

새 메뉴 계약은 선택 후보의 public·instance·매개변수 없음·void 반환을 모두 검사하고, Order가 정확히 하나이며 선택 후보끼리 Order 값이 중복되지 않을 때만 전체 메뉴를 게시한다. P/Q가 모두 조건을 만족하면 Q,P 순서다. R이 public이지만 인수 하나를 받으면 후보에서 제외한다. Q와 P의 Order가 둘 다 1인 별도 변형은 전체 검증 실패로 이전 메뉴를 보존한다. 우연한 reflection 열거 순서로 동률을 해결하지 않는다.

코드에 붙이는 설명 정보

attribute는 타입·멤버·어셈블리 같은 선언에 메타데이터를 붙인다. []로 표시하며 인자에 설명값을 넣을 수 있다. 실제 클래스 이름 LessonAttribute를 사용 위치에서 Lesson으로 줄이는 관례가 있지만 모든 메서드 이름을 대괄호로 적으면 attribute가 되는 것은 아니다. 적용 대상도 해당 attribute의 규칙에 맞아야 한다.

사용자 정의 표식을 붙이는 것만으로 모든 원하는 행동이 자동 실행되지는 않는다. 컴파일러나 프레임워크가 특별히 이해하는 표식도 있고, 수업에서 만드는 LessonAttribute처럼 이를 읽는 소비 코드를 따로 작성해야 하는 것도 있다. 표식이 데이터를 설명하는 단계와 정책이 행동을 결정하는 단계를 나눈다.

Reflection은 프로그램 구조를 조회한다

Type과 reflection API로 타입 이름, 메서드와 속성, attribute 등의 정보를 조사할 수 있다. 이미 가진 객체의 GetType이나 알려진 타입의 typeof로 출발한다. 조회만 하면 메서드의 업무 본문을 실행한 것이 아니고, Invoke로 실제 호출하면 별도의 실행과 부작용이 생길 수 있다.

문자열로 이름을 찾을 때 오타·같은 이름의 여러 오버로드·접근 범위 때문에 원하는 멤버를 못 찾을 수 있다. 어떤 이름과 매개변수, 접근 수준을 허용할지 명시하고 조회 실패를 검사한다. 외부 입력으로 임의의 타입과 메서드를 호출하도록 내버려 두지 않고 의도한 후보만 사용한다.

메타데이터를 소비하는 규칙을 적는다

가상 강의 메뉴는 Lesson 표식이 붙은 public parameterless 메서드만 선택하고 표식의 Order 숫자로 정렬한다고 하자. 이 세 조건을 읽는 메뉴 생성기가 있어야 목록이 만들어진다. 이름순과 Order순은 다르며 reflection이 돌려주는 나열 순서를 강의 순서라고 믿지 않는다.

문자 수와 native 버퍼의 바이트 용량은 같을까?

앞 본문은 metadata token을 주소와 구별했다. 새 두 모듈 M/N에 같은 숫자 token 0x06000009가 있어도 서로 다른 MethodDef를 가리킬 수 있다. token은 모듈과 함께 metadata 요소를 식별한다. 라이브러리 이름·export 이름·호출 규약·정수 폭·문자 인코딩은 native 호출의 다른 계약이며 token 숫자만으로 export를 찾거나 ABI를 인증할 수 없다.

새 가상 native API는 UTF-8 문자열을 쓰며 마지막 NUL을 포함한 필요 바이트 수를 먼저 알려준다. 입력 B나의 payload는 42 EB 82 98로 4바이트고 끝 00을 포함하면 5바이트다. capacity가 5 이상이면 한 번에 전체를 기록하고 성공, 작으면 아무 바이트도 바꾸지 않고 필요량 5를 알린다는 자체 계약이다. C# Length 2에 1을 더해 3바이트만 확보하는 계산은 틀린다. 이 API는 실제 OS 함수가 아니며 어떤 P/Invoke 옵션이 자동으로 이 두 단계 계약을 제공한다는 뜻도 아니다.

native가 함수 반환 뒤 버퍼 주소를 보관하는 별도 비동기 계약에서는 주소 안정성과 소유권 기간을 함께 보장해야 한다. 가상 native 사용 기간은 시각 2부터 terminal 9까지다. 포인터 주소가 고정돼 있어도 owner가 6에 버퍼를 다른 작업으로 돌려주면 8의 사용은 계약 위반이다. 호출이 반환했다는 사건이나 취소 요청만으로 native 접근 종료를 추론하지 않는다. 실제 pinning·unmanaged allocation·completion API 선택은 별도 구현 검토이며 여기서는 손수명 표만 구성한다.

Metadata는 실행 코드를 설명한다

관리 어셈블리는 타입 이름, 접근 수준, 메서드의 인자와 반환형, 참조와 attribute 같은 메타데이터를 포함한다. CIL은 실행할 명령을 표현하고 metadata는 그 명령이 가리키는 타입·멤버를 설명한다. 정보와 동작은 관련되지만 같은 부분이 아니다.

metadata token은 모듈 안의 특정 테이블 행을 가리키는 식별값이다. 상위 한 바이트는 테이블 종류, 하위 세 바이트는 행 번호다. 메서드의 메모리 주소나 전 세계에서 영구 고정된 ID라고 생각하면 안 된다. 다른 모듈이나 다시 빌드한 결과에서 같은 수가 같은 메서드를 뜻한다는 보장이 없다.

관리 영역 밖으로 나가는 P/Invoke

P/Invoke는 관리 코드에서 native 라이브러리의 함수·구조체와 통신하는 기술이다. DllImport extern 선언과 현대 .NET의 LibraryImport partial 기반 생성은 native 함수를 호출할 연결 정보를 제공하는 방식이다. 여기서는 실제 라이브러리 호출을 하지 않고 경계 계약을 종이로 읽는다.

C# 쪽 이름만 맞추는 것으로 부족하다. 실제 라이브러리 파일, export 이름, 프로세스 아키텍처, 호출 규약, 인자와 반환 자료형이 맞아야 한다. Windows DLL 이름을 Linux에서 그대로 찾거나 32비트 라이브러리를 64비트 프로세스에 무작정 넣으면 안 된다. 라이브러리가 없거나 함수가 없다는 오류를 별도로 진단한다.

Marshalling은 표현과 수명의 약속이다

문자열 인코딩, 배열 길이, 구조체 배치, bool과 정수 폭은 경계를 넘을 때 표현을 맞추어야 한다. native 함수가 문자열을 호출 동안만 사용하는지 나중에도 포인터를 보관하는지도 중요하다. GC가 관리하는 객체 수명과 native 코드가 기대하는 포인터 수명은 자동으로 모든 상황에서 일치하지 않는다.

가상 native 계약이 signed32 Add(signed32,signed32)이며 두 입력의 합이 signed32 범위 안이면 같은 폭의 관리 정수로 결과를 해석할 수 있다. 이것은 임의의 실제 라이브러리 ABI를 선언한 것이 아니다. 실제 함수 문서를 먼저 확인하고 필요하면 오류 코드와 자원 해제 규칙까지 함께 선언한다.

native 표현은 문자 수가 아닌 바이트와 NUL을 센다. 모듈 식별/주소 안정/사용 기간은 서로 다른 조건이다.

풀이와 답 확인

  1. ① 첫 출력은 B이며 EB를 보관한다. 둘째는 나를 완성하여 B나다. EB 82만의 최종 flush는 실패다. 중복 JSON은 전체 거절하여 현재 점수 40을 보존한다.

  2. ② 30에는 B의 번호 2가 현재와 같아 20을 게시한다. 80에는 A의 번호 1이 낡아 거절하므로 최종 화면 20이다.

  3. ③ 선언 인수는 P 2/Q 1이며 생성자 실행 없이 calls 0, 각 한 번 생성 경로는 calls 2다. 메뉴는 Q,P다. 독립 동률 변형은 이전 메뉴를 유지한다. 업무 메서드는 어느 경로에서도 실행하지 않았다.

  4. ④ 같은 token 숫자라도 M/N의 요소는 다를 수 있다. B나 payload 4바이트와 NUL 1의 합은 5이므로 capacity 4는 무변경 실패다. 반환 6은 native 사용 2–9와 겹쳐 주소 안정 여부와 무관하게 lease 위반이다.

문자 조각·전체 문서·후보 수용·최신 요청·특성 생성·모듈 식별·native 표현과 사용 종료를 각각의 조건으로 확인한다. 일부 값이나 초기 반환의 관찰로 모든 경계를 성공으로 확대하지 않는다.

해결한 뒤 점검할 것

  • 중간/최종 flush의 상태와 엄격 실패·점수 40 보존을 설명한다.

  • 현재 번호와 요청 시작 번호를 비교하고 30/80 화면을 각각 구한다.

  • 선언 조회와 생성 효과 및 후보 검증/업무 호출을 구별한다.

  • 모듈 범위·필요 5바이트·capacity 4 실패·반환 6/terminal 9의 수명 조건을 확인하고 실제 학생 미수행을 유지한다.
