소단원 6.1

List·Dictionary·HashSet

좋아하는 책 세 권을 적는 것과 책별 대출 수를 적는 것은 같은 자료구조일까?

준비 개념과 학습 목표

준비 개념

  • List는 위치로 원소를 찾는 목록이다.
  • Dictionary는 키에서 값을 찾는 대응이다.
  • HashSet은 중복 없는 값의 집합이다.

학습 목표

  • 순서·중복·키 대응의 요구로 컬렉션을 선택한다.
  • 각 Count와 수정 동작을 종이에 추적한다.
  • 키·집합 비교자와 순서의 한계를 설명한다.

목록은 위치와 반복을 보존하기

자체 방문 기록 [3,1,3]에는 방문 순서와 같은 장소 재방문이 의미 있다. List<int>는 인덱스0·1·2로 각 방문을 구별하고 중복3을 허용한다. Count는 서로 다른 값 수가 아니라 원소 수이므로3이다. 인덱스2를 읽으면 세 번째 방문3이다.

List를 집합으로 바꾸면 반복 기록이 사라진다. 반대로 존재하는 장소를 한 번씩만 모으는 문제라면 HashSet<int>로1과3을 담는 것이 자연스럽다. 같은 입력도 문제의 의미에 따라 자료구조 선택이 달라진다.

키에서 값으로 찾는 대응

자체 Dictionary<string,int>는 red→2, blue→1을 담는다. red의 값을5로 설정하면 새 키를 더하지 않고 기존 키의 값을 바꾸므로 Count는2다. Add로 기존 red를 다시 추가하는 것과 인덱서로 red의 값을 설정하는 것은 계약이 다르다. 중복 Add는 예외이며 덮어쓰기와 혼동하지 않는다.

키의 유일성은 선택한 동등성 비교자에 따른다. 값2를 여러 키가 공유하는 것은 허용되며 키만 중복될 수 없다. 없는 키의 조회는 안전한 TryGetValue 등으로 실패를 처리할 수 있다. 키의 해시에 영향을 주는 값을 저장 중 바꾸지 않는다.

집합 연산과 관측 순서

HashSet의 {1,3}과 {3,4}의 합집합은 {1,3,4}, 교집합은 {3}이다. 중괄호 표기는 내용만 설명하며 실제 순회가1,3,4라는 계약을 주장하지 않는다. HashSet은 정렬 목록이 아니다. Dictionary의 열거 순서에도 의존하지 말고 화면 정렬이 필요하면 별도 정렬 기준을 정한다.

컬렉션의 Count가 같아도 의미가 같지는 않다. List [1,3]과 [3,1]은 순서를 구별하는 문제에서 다르지만 집합 내용은 같다. Dictionary를 순회하면 키와 값의 쌍을 받는다. 본문에 쓴 순서는 종이 설명용이며 실행 관찰이 아니다.

using System.Collections.Generic;
var visits = new List<int> { 3, 1, 3 };
var counts = new Dictionary<string,int> { ["red"] = 2, ["blue"] = 1 };
counts["red"] = 5;
var places = new HashSet<int>(visits);

중간 과정을 따라가는 예제

위 자체 코드의 visits.Count, counts.Count, counts["red"], places.Count를 구하고 places.Add(3) 후 집합 크기를 예측하라.

  1. visits에는 위치가 세 개이므로 Count=3이다. 중복3도 원소 하나로 센다.
  2. counts는 red·blue 두 키다. red 값의 변경 뒤에도 Count=2이고 red의 값은5다.
  3. places는 입력3,1,3에서 마지막3이 기존3과 같아 두 값만 담는다.
  4. places.Add(3)은 기존 값이라 새로 더하지 않아 false를 반환하고 Count=2를 유지한다.

각 값은3,2,5,2이며 Add(3) 뒤에도 집합 크기는2다. 실제 실행하지 않은 예상 동작이다.

종이와 본문으로 직접 해보기

List에4를 추가하고 HashSet에도4를 추가하라. Dictionary에는 green→5를 새 키로 추가한다. 각 Count와 값5인 키 수를 써라.

힌트 보기

목록의 원소 수, 집합의 서로 다른 값 수, 대응의 서로 다른 키 수를 따로 센다.

풀이 보기

List는4개, HashSet은 {1,3,4} 세 값, Dictionary는 red·blue·green 세 키다. 값5는 red와 green 두 키가 공유한다. 값 중복은 금지하지 않았다.

오해와 반례

Dictionary는 값도 모두 달라야 한다.

red→5와 green→5는 서로 다른 키이므로 함께 저장할 수 있다. 키의 동등성으로 중복을 판정하며 값 유일성은 별도 업무 규칙이다.

자기점검

답과 이유 보기

반복 원소도 위치마다 센다.

기존 키를 Add하면 자동 덮어쓰는가?

답과 이유 보기

중복 Add는 예외다.

값 설정 인덱서와 계약이 다르다.

HashSet 순회가 정렬순인가?

답과 이유 보기

그렇게 보장되지 않는다.

집합 내용과 화면 정렬을 구분한다.

한 단계 더

도서 대출 기록에서 대출 순서·책별 횟수·대출한 책의 존재를 동시에 묻는다면 세 모델을 어떻게 함께 유지할지 종이에 설계해 보자. 수정할 때 서로 모순되지 않도록 규칙을 적는다.

소단원 6.2

equality·hash 계약

Cat과 cat을 같은 이름으로 처리할지 누가 결정할까?

준비 개념과 학습 목표

준비 개념

  • 동등성은 두 값을 같다고 보는 규칙이다.
  • 해시 값은 후보를 빠르게 찾도록 돕는다.
  • 비교자는 컬렉션 생성 때 선택할 수 있다.

학습 목표

  • 같은 값과 같은 해시의 방향을 설명한다.
  • 문자열 비교 정책에 따른 집합 결과를 계산한다.
  • 가변 키와 영구 ID 오해를 반례로 교정한다.

동등성 규칙은 명시적으로 고르기

자체 사용자 표지 Cat·cat·Dog를 생각하자. StringComparer.Ordinal은 대소문자를 구별하므로 세 값이고 OrdinalIgnoreCase는 이 ASCII 예제에서 Cat과 cat을 같다고 보아 두 값이다. 어느 정책이 맞는지는 사용자 이름의 계약에 달렸다. 자연어 이름 정렬이나 모든 언어의 문자를 같은 식으로 바꾼다는 주장으로 확대하지 않는다.

HashSet은 생성자에 넘긴 IEqualityComparer<T>로 동등성과 해시를 함께 처리한다. 한 컬렉션은 Cat과 cat을 같다고 보고 다른 저장 규칙은 다르게 보면 식별 의미가 어긋날 수 있다. 입력·저장·조회가 같은 정책을 따라야 한다.

해시 계약의 한 방향

Equals로 같은 값이라면 같은 비교자의 GetHashCode도 같아야 한다. 반대 방향은 성립하지 않는다. 자체 설명용 정수 표지의 해시를 h(id)=id%10으로 정하면11과21은 모두1이지만 id 전체를 비교할 때는 다르다. 충돌을 동등성 비교로 구분하면 두 값 모두 집합에 남을 수 있다.

이 자체 식은 원리를 보여 주는 예시이며 실제 문자열 비교자의 해시 숫자를 예측하지 않는다. 해시만으로 사용자를 식별하거나 DB에 영구 ID로 저장하지 않는다. 실행·플랫폼·구현에 따라 값이 달라질 수 있고 서로 다른 값이 충돌할 수 있다.

저장 중인 키와 변경

Dictionary나 HashSet이 저장할 때 계산한 위치에 키를 두었다고 하자. 키의 동등성·해시 관련 필드가 바뀌면 다음 조회는 다른 위치로 갈 수 있다. 이 때문에 해당 필드를 불변으로 만들거나 정해진 제거·재삽입 절차를 사용한다. 컬렉션 안의 키를 제멋대로 수정하는 것만으로 저장 구조가 자동 재배치된다고 가정하지 않는다.

사용자 정의 값 타입은 Equals·GetHashCode와 필요한 IEquatable<T> 동작을 같은 규칙으로 유지한다. equals라는 말은 여기서 개념 설명이고 C#의 메서드 표기는 Equals다. 연산자 ==를 재정의했는지도 별도 계약이므로 ==와 Equals가 언제나 같다고 단정하지 않는다.

using System;
using System.Collections.Generic;
var exact = new HashSet<string>(StringComparer.Ordinal) { "Cat", "cat", "Dog" };
var folded = new HashSet<string>(StringComparer.OrdinalIgnoreCase) { "Cat", "cat", "Dog" };

중간 과정을 따라가는 예제

위 두 집합의 크기를 구하라. 별도 정수 표지 집합은 id 동등성과 h(id)=id%10을 사용한다. 11,21,11을 넣었을 때 크기는?

  1. Ordinal에서는 Cat·cat이 다르고 Dog도 달라 exact.Count=3이다.
  2. OrdinalIgnoreCase에서 Cat과 cat은 같은 값이고 Dog는 달라 folded.Count=2다.
  3. 정수11의 해시는1이고21의 해시도1이다. id 전체 비교는 다르므로 두 값이 저장된다.
  4. 마지막11은 앞11과 동등하고 같은 해시라 새 값이 아니다. 정수 집합 크기는2다.

문자열 집합은3과2, 정수 표지 집합은2다. 해시 충돌과 동등성은 별도 판단이다.

종이와 본문으로 직접 해보기

두 문자열 집합에 CAT을 추가하면 각 크기는? 정수 표지 집합에31을 추가하면?

힌트 보기

ASCII 대소문자 규칙과 전체 id 비교를 적용하라.

풀이 보기

Ordinal은 CAT이 새 값이라4다. OrdinalIgnoreCase는 기존 Cat과 같아2다. 31도 해시1이지만11·21과 다른 ID라 정수 집합은3이 된다.

오해와 반례

GetHashCode가 같으면 영구적으로 같은 사용자다.

자체 h(11)=h(21)=1이지만 서로 다른 표지다. 기본 해시도 영구 식별자가 아니므로 별도 ID를 설계하고 해시를 보관·통신용 ID로 사용하지 않는다.

자기점검

Equals=true인데 해시가 다른 비교자는 올바른가?

답과 이유 보기

올바르지 않다.

동등 값의 동일 해시 조건을 위반한다.

11·21의 해시가 같으면 하나만 저장해야 하는가?

답과 이유 보기

아니다.

전체 값 비교가 다르면 충돌을 구분한다.

OrdinalIgnoreCase가 모든 자연어 이름의 적절한 정책인가?

답과 이유 보기

그렇게 단정할 수 없다.

언어와 업무 의미에 맞는 별도 정책 검토가 필요하다.

한 단계 더

표지 이름은 바뀌어도 사용자 ID는 유지되는 모델을 설계해 보자. 동등성을 이름으로 정의했을 때와 ID로 정의했을 때 수정 영향이 어떻게 다른지 추적한다.

소단원 6.3

IEnumerable와 순회

목록을 한꺼번에 받는 것과 다음 값을 하나씩 받는 것은 어떻게 다를까?

준비 개념과 학습 목표

준비 개념

  • 순회는 원소를 하나씩 방문하는 과정이다.
  • IEnumerator는 현재 위치를 가진 순회자다.
  • 인터페이스는 제공하는 연산의 계약이다.

학습 목표

  • 순회 가능성과 인덱스·Count의 차이를 설명한다.
  • yield와 MoveNext의 진행을 추적한다.
  • 반복 순회 비용과 자료 변경 조건을 구분한다.

순회할 수 있다는 최소 약속

IEnumerable<T>는 GetEnumerator로 IEnumerator<T>를 제공한다. 순회자는 MoveNext로 다음 원소가 있는지 확인하고 성공했을 때 Current를 읽는다. foreach는 이런 진행을 간편하게 표현하고 필요한 정리를 수행한다. 현재 원소가 아직 없거나 끝난 시점에 Current를 유효 값으로 가정하지 않는다.

이 인터페이스 자체는 인덱서나 Count를 요구하지 않는다. List처럼 추가 기능이 있는 구현도 있지만 파일 읽기나 계산된 수열처럼 다음 원소를 구하는 데 일이 필요한 구현도 있다. LINQ 확장 메서드 Count가 보인다고 모든 IEnumerable의 원소 수를 O(1)에 얻는다는 뜻은 아니다.

요청 때 다음 값을 계산하기

아래 자체 iterator는1,4,9를 순서대로 제공한다. Squares()를 호출해 IEnumerable을 얻는 것과 본문을 끝까지 실행하는 것은 다르다. 순회를 시작해 다음 값을 요청할 때 i=1의 yield까지 진행하고, 다음 요청에서는 보류한 지점 다음에서 반복을 계속한다.

종이에 i와 제공값을 두 열로 적으면1→1, 2→4, 3→9를 볼 수 있다. 네 번째 MoveNext 요청에서는 i=4가 되어 조건이 false라 종료한다. yield return은 반복 전체를 끝내는 일반 return과 달리 원소 하나를 제공하고 다음 진행을 보류한다.

using System.Collections.Generic;
static IEnumerable<int> Squares() {
    for (int i=1; i<=3; i++) {
        yield return i*i;
    }
}

몇 번 순회하는지 세기

아무 부작용 없이 자체 Squares를 새 foreach로 두 번 순회하면 각 순회마다1,4,9를 계산한다. 결과를 저장해 재사용하려면 목록으로 구체화하는 별도 선택을 할 수 있지만 메모리를 쓰고 생성 시점도 달라진다. 모든 IEnumerable이 같은 결과를 반복 제공한다고 보장되지는 않는다. 외부 입력·시간·상태에 의존하는 구현은 관측이 달라질 수 있다.

순회 중 원본 자료를 수정해도 되는지도 구체 구현의 계약을 읽어야 한다. 단순히 IEnumerable이라는 타입만 보고 안전하다고 판단하지 않는다. 무한 수열은 끝까지 센다는 연산이 끝나지 않을 수 있다. 인터페이스의 편리함과 실제 작업량·수명 조건을 함께 검토한다.

중간 과정을 따라가는 예제

자체 Squares의 순회자가 MoveNext를 네 번 요청한다. 각 반환값과 유효할 때 Current, 세 원소의 합을 구하라.

  1. 첫 요청은 i=1에서 true, Current=1이다. 합은0+1=1이다.
  2. 두 번째는 i=2에서 true, Current=4다. 합은1+4=5다.
  3. 세 번째는 i=3에서 true, Current=9다. 합은5+9=14다.
  4. 네 번째는 i=4에서 종료해 false다. 이때 Current로 새 원소를 읽지 않는다.

MoveNext 결과는 true,true,true,false이고 유효 원소는1,4,9, 합은14다. 종이상의 예상 진행이다.

각 순회를 처음부터 새로 시작하여 앞 두 원소만 읽고 중단하는 작업을 두 번 한다. 전체 제공 원소 수와 합을 구하라.

힌트 보기

첫 두 값은1·4이고 두 번째 작업도 같은 순수 iterator를 새로 시작한다.

풀이 보기

오해와 반례

IEnumerable이면 모든 값이 이미 메모리에 있고 Count와 인덱스가 항상 빠르다.

자체 Squares는 요청할 때 값을 계산하며 인터페이스에는 Count·인덱서가 없다. 파일·무한 수열 같은 구현에서는 끝까지 순회 자체가 비싸거나 종료하지 않을 수 있다.

소단원 6.4

collection API와 복잡도

인덱스로 읽기와 값으로 찾기는 같은 비용일까?

준비 개념과 학습 목표

준비 개념

  • n은 현재 원소 수다.
  • O(n)은 입력 크기에 비례하는 증가를 표현한다.
  • 비교와 이동 횟수는 실제 실행 시간과 구별한다.

학습 목표

  • 구체 연산과 자료구조를 함께 비용으로 판단한다.
  • 삭제 후 이동과 선형 탐색을 계산한다.
  • 해시 분포·확장·인터페이스의 조건을 명시한다.

연산 이름이 비용을 정한다

List<T>의 유효 인덱스 읽기·설정은 O(1)이다. 하지만 특정 값을 찾는 Contains는 위치가 알려져 있지 않아 원소를 차례로 비교한다. 이 자체 비용 모델은 원소 동등성 비교 한 번을 상수 비용으로 가정한다. 문자열이나 큰 값의 비교 비용이 늘면 그 비용도 곱해서 검토해야 한다.

List는 필요하면 내부 배열을 확장한다. 끝에 더한다는 말만으로 매번 같은 시간이 걸린다고 단정하지 않는다. 공간이 충분한 삽입과 확장·복사가 필요한 삽입을 나누어 본다. Count는 실제 원소 수이며 Capacity는 준비된 저장 공간 수라 서로 다를 수 있다.

중간 삭제가 이동을 만드는 이유

List의 RemoveAt(i)는 뒤쪽 원소를 앞으로 한 칸씩 옮겨 순서를 유지한다. 현재 n개에서 유효 i를 지우면 뒤 원소 n-i-1개를 옮기는 배열 모델이다. 그 외 검사·Count 갱신 같은 상수 작업도 있어 복잡도는 O(n-i), 최악 O(n)으로 설명할 수 있다.

n=5에서 i=1을 지우면 원래 인덱스2·3·4가1·2·3으로 이동한다. 값 검색 Remove(value)는 먼저 찾는 비용도 있다. 마지막 인덱스 삭제는 뒤 원소 이동이0이지만 상수 작업이 남는다. 이동0을 전체 비용0으로 혼동하지 않는다.

빠른 조회의 조건과 실제 측정

Dictionary 키 조회는 해시 분포가 적절하고 해시·동등성 비용을 상수로 보는 상황에서 매우 빠르게 사용할 수 있다. 충돌이 많이 몰리거나 키 처리 비용이 크면 모든 경우 O(1)이라고 보장하지 않는다. HashSet도 중복 없는 조회라는 요구와 비교자 품질을 함께 검토한다.

한 번의 인덱스 조회·한 번의 값 찾기·전체 순회는 다른 작업이다. 이 절의 비교 횟수와 이동 횟수는 정의한 종이 모델로 계산하며 밀리초 성능을 측정한 결과가 아니다. 큰 n에 대한 선택은 처리 요구와 메모리, 정렬 유지 비용 및 실제 조건에서의 측정을 함께 고려한다.

중간 과정을 따라가는 예제

목록 [2,4,6,8,10]에서 왼쪽부터 값을 비교하는 선형 탐색 모델을 쓴다. Contains(8), Contains(7)의 비교 횟수와 원래 목록 RemoveAt(1)의 이동 수를 구하라.

  1. 8과2,4,6,8을 차례로 비교하므로 성공 비교까지4회다.
  2. 7은 다섯 원소 어디에도 없어2·4·6·8·10과5회 비교한다.
  3. 원래 n=5,i=1이므로 뒤 원소 이동은5-1-1=3회다. 6→인덱스1,8→2,10→3이다.
  4. 삭제 뒤 목록은 [2,6,8,10], Count=4다. 위 탐색은 삭제 전 목록을 기준으로 했다.

비교4회·5회, 이동3회다. 실제 구현 명령 수나 실행 시간과 같다고 주장하지 않는다.

종이와 본문으로 직접 해보기

삭제 후 목록 [2,6,8,10]에서 맨 마지막 원소를 RemoveAt(3)로 지운다. 이동 수와 Count를 구하고 Contains(10)을 선형 탐색하라.

풀이 보기

오해와 반례

collection이면 조회는 언제나 O(1)이다.

List의 값 찾기는 최대 n번 비교하고 IEnumerable 순회는 원소마다 작업한다. Dictionary도 해시·충돌·키 처리 조건이 있다. 자료구조 이름과 구체 연산을 함께 적어야 한다.
