unit test·mock의 경계

가짜 저장소를 사용한 시험이 통과하면 실제 서버도 정상일까?

준비 개념과 학습 목표

준비 개념

  • interface와 메서드

  • 예외

  • 기대값 비교

학습 목표

  • 계약에서 정상·실패·경계 시험을 고른다.

  • 테스트 대역의 역할과 실제 연결 시험의 범위를 구별한다.

  • 결과와 필요한 상호작용을 각각 확인한다.

통과한 두 시험이 서로 같은 대역 객체를 사용해도 독립적인가?

앞 본문의 Buy는 양의 수량에서 한 번 저장하고 true를 반환하며 수량 0에서는 저장 없이 false를 반환한다. 새 시험 설계는 실제 저장소 대신 수량과 저장 호출을 기록하는 대역을 사용한다. 첫 시험은 수량 1에서 시작하고, 둘째 시험은 수량 0에서 시작해야 한다. 두 시험 모두 자기 초기 상태를 직접 구성해야 순서가 바뀌어도 같은 약속을 검사할 수 있다.

잘못된 설계는 첫 시험에서 사용한 대역을 둘째 시험에서도 재사용하고 Value만 0으로 바꾼다. 첫 시험 뒤 Saves는 1이고 Last는 0이다. 둘째 Buy가 실제로 저장하지 않아도 누적 Saves와 Last는 그대로 남는다. 둘째 시험이 Saves == 1만 검사하면 이전 시험의 저장을 현재 시험의 저장으로 오해한다. 반대로 원래 거부 계약의 Saves == 0을 검사하면 올바른 Buy가 실패했다고 오해한다.

새 대역을 만드는 수정은 입력만 아니라 관찰 이력도 초기화한다. 정상 거부 시험의 마지막 저장값은 null이며 저장 호출 수는 0이다. 반환값·호출 수·마지막 인수는 다른 관찰이다. 반환값이 false라는 사실만 검사하면 거부 뒤 불필요하게 Save(0)을 호출하는 변형을 발견하지 못한다.

예외의 경계도 명시한다. 자체 Save 실패 대역 S는 호출을 기록한 뒤 E를 던지고 Value는 변경하지 않는다. 별도 대역 T는 호출을 기록하고 Value를 변경한 뒤 E를 던진다. Buy는 E를 잡지 않으므로 둘 다 정상 bool 반환이 없다. 하지만 S와 T의 상태는 다르다. 이것은 두 대역에 부여한 계약의 차이이며 실제 저장소의 장애 원자성을 증명하지 않는다.

시험할 약속부터 정한다

자체 재고 계약은 읽은 수량이 1 이상이면 한 개를 빼서 저장하고 true를 반환한다. 수량이 0이면 저장하지 않고 false를 반환한다. 데이터베이스 연결 없이도 이 조건과 저장 호출을 따져 볼 수 있다. 준비, 동작, 검증을 나누면 어떤 입력과 기대값을 비교했는지 보인다.

아래 코드는 설명을 위한 작은 테스트 대역이다. Check가 실패하면 예외를 던진다. 외부 시험 프레임워크를 설치하지 않아도 종이 위에서 호출 순서와 상태를 읽을 수 있다. 실제 실행한 결과는 이 원고에 없다.

대역의 이름보다 통제하는 역할을 본다

미리 정한 값을 반환하는 역할을 여기서는 stub, 저장 횟수와 인자를 기록하는 역할을 spy라고 부른다. mock이라는 말은 상호작용 검증 대역을 가리키기도 하고 대역 전체를 느슨하게 부르기도 한다. 자료마다 용어가 달라서 실제로 무엇을 반환하고 무엇을 검증하는지 함께 적는다.

이 예제는 하나의 객체가 반환값과 호출 기록을 모두 제공한다. 호출 횟수만 확인하면 틀린 저장값을 놓칠 수 있고 반환값만 확인하면 저장 누락을 놓칠 수 있다. 계약에 필요한 결과와 상호작용을 확인하되 의미 없는 내부 호출까지 고정하지 않는다.

단위 시험의 증거를 넓혀 말하지 않는다

대역은 실제 저장소의 연결, 트랜잭션, 권한, 동시 구매를 검증하지 않는다. 여러 구매자가 동시에 같은 수량을 읽는 문제는 이 단일 호출 모형 밖이다. 실제 서비스에서는 원자적 갱신이나 트랜잭션 계약과 통합 시험을 따로 설계한다.

코드가 실행된 줄의 비율인 coverage가 높아도 기대값이 약하면 오류를 놓친다. 항상 true를 반환하는 구현을 잡을 시험이 있는지, 저장값을 0으로 고정한 구현을 잡을 시험이 있는지 반례를 만들어 본다. 빠르고 반복 가능한 단위 시험과 실제 연결 시험은 각자의 목적이 있다.

중간 과정을 따라가는 예제

다음 자체 코드에서 초기 수량 1과 0의 반환값, 저장 횟수, 마지막 저장값을 추적한다. 

using System;
interface IStock { int Read(); void Save(int value); }
sealed class StockDouble : IStock
{
    public int Value;
    public int Saves;
    public int? Last;
    public int Read() => Value;
    public void Save(int value) { Saves++; Last = value; Value = value; }
}
static class Demo
{
    static bool Buy(IStock stock)
    {
        int n = stock.Read();
        if (n < 1) return false;
        stock.Save(n - 1);
        return true;
    }
    static void Check(bool ok)
    {
        if (!ok) throw new Exception("check failed");
    }
    static void Main()
    {
        var one = new StockDouble { Value = 1 };
        Check(Buy(one) && one.Saves == 1 && one.Last == 0);
        var zero = new StockDouble { Value = 0 };
        Check(!Buy(zero) && zero.Saves == 0 && zero.Last == null);
    }
}

  1. one은 1을 읽고 조건을 지나 0을 저장한다. Saves는 1, Last는 0, 반환값은 true다.

  2. zero는 0을 읽고 바로 false를 반환한다. 저장하지 않아 Saves는 0이고 Last는 null이다.

  3. 두 Check 조건은 손으로 추적하면 true다. 성공할 때 출력하는 문장은 없으며 실제 C# 실행 결과를 기록한 것은 아니다.

수량 1은 true/1/0, 수량 0은 false/0/null이다. 실제 저장소나 동시 구매의 성공을 뜻하지 않는다.

조건을 바꾸어 비교하기

남은 이력이 거부 시험을 오염시킨다

성공 시험 뒤 Value만 0으로 바꾸어 거부 시험을 실행한다. 누적 Saves와 이번 호출의 저장 수를 나누어 적어라.

  1. 첫 성공에서 저장 이력 한 번이 생겼다.

  2. 둘째 Buy는 저장하지 않지만 이력을 지우지 않으므로 누적 값은 1이다.

누적 저장 수는 1이고 둘째 호출의 저장 수는 0이다.

수량 3에서 S와 T를 별도 사용한다. 두 Buy의 정상 반환과 실패 뒤 수량을 구하라.

  1. 둘 다 Save 인수 2를 계산하고 E가 밖으로 전파된다.

패키지 버전 하나를 적었는데 왜 두 그래프가 서로 다른 결론을 낼까?

앞 본문은 최저 적용 가능 버전과 floating 버전을 구별했다. 새 예시는 안정 버전만 있는 가상 feed이며 P의 후보가 2.2.0과 2.3.0이다. PackageReference의 Version="2.2.0"은 최솟값을 포함하는 요구이고 Version="[2.2.0]"은 정확 버전 요구다. 2.2.0이 사라지면 첫 요구는 2.3.0으로 만족할 수 있지만 둘째는 만족할 수 없다. 버전 목록은 실제 패키지나 추천이 아니다.

새 앱은 A와 B를 직접 참조하고, A는 P >= 2.2.0, B는 P >= 2.3.0을 요구한다. 앱이 P를 직접 참조하지 않는 이 cousin 경로에서는 두 조건을 모두 만족하는 최저 후보 2.3.0을 고른다. 앱이 P 2.2.0을 직접 참조하는 별도 경로에서는 direct-dependency-wins 규칙으로 더 낮은 직접 버전이 선택될 수 있으며 downgrade 진단을 확인해야 한다. 낮은 버전 선택과 모든 간접 조건 충족은 같은 말이 아니다.

여기서는 downgrade를 릴리스 차단 대상으로 삼는 자체 정책을 둔다. 실제 SDK가 경고를 오류로 처리하는 설정도 별도 기록해야 한다. 규칙이 버전을 선택했다는 이유로 A/B의 API 호환성 시험이나 진단 검토를 생략하지 않는다. 직접 버전을 2.3.0으로 높이는 수정은 이 작은 수치 조건을 만족하지만 모든 실행 동작을 증명하지 않는다.

잠금 파일도 요구 변경을 숨기는 도구가 아니다. 현재 앱 요구의 닫힘이 P 2.2.0으로 잠겨 있는데 요구를 P >= 2.3.0으로 바꾸면 locked mode는 낡은 잠금을 그대로 성공이라고 만들지 않고 실패한다. 승인한 변경 뒤 별도 재평가로 새 잠금을 만들고 검토해야 한다. 라이브러리 자신의 잠금과 소비 앱의 최종 닫힘, 동일 닫힘과 실제 패키지 확보 성공도 각각 다르다.

요청을 실제 그래프로 바꾼다

PackageReference 방식에서 restore는 직접·간접 의존성을 해석한다. 최저 적용 가능 버전, floating version, 직접 의존성 우선, 서로 다른 간접 경로의 조건 같은 규칙이 작용한다. 요구 조건이 맞지 않으면 오류나 경고가 생길 수 있어서 최종 그래프와 진단을 읽는다.

가상 범위 >=2.1.0에 2.2.0과 2.3.0이 있다면 최저 적용 가능 규칙의 결과는 2.2.0이다. floating 6.0.*은 그 범위에서 가장 높은 일치 버전을 고른다. 모든 요청을 최신 버전 선택이라고 뭉뚱그리지 않는다. 정확 버전 요청이 없으면 다른 버전으로 바꾸는 정책과도 구별한다.

변경을 잠금 기록과 비교한다

RestorePackagesWithLockFile을 true로 설정하면 packages.lock.json으로 해석한 의존성 닫힘을 기록할 수 있다. dotnet restore --locked-mode는 잠금 내용을 그대로 만족시키거나 실패하게 해서 예상치 못한 갱신을 드러낸다. 프로젝트 요구를 바꾼 뒤 일반 restore는 잠금을 다시 평가하고 갱신할 수 있다.

project.assets.json은 빌드가 사용하는 생성 결과이며 packages.lock.json과 역할이 다르다. 앱의 잠금을 버전 관리하고 입력 변경을 검토한다. SDK가 제공하는 암묵적 참조도 영향을 줄 수 있으므로 SDK 선택 정책도 함께 다룬다. 잠금 파일 하나를 모든 빌드 환경의 완전한 증거로 취급하지 않는다.

라이브러리와 앱의 책임이 다르다

재사용 라이브러리의 잠금 파일이 그 라이브러리를 소비하는 앱의 전체 그래프를 고정하지는 않는다. 앱은 다른 의존성과 함께 다시 해석하기 때문이다. 버전 충돌과 직접 의존성 우선 때문에 API 호환성 문제가 생길 수 있어 실제 시험이 필요하다.

이론 활동에서는 좌표, 요청 범위, 가능한 버전, 선택 이유를 표에 적는다. 실제 작업에서는 restore 진단, 변경된 잠금, 패키지 출처와 정책을 확인한다. 여기의 버전 목록은 계산을 위한 가상 자료이며 실제 NuGet 패키지의 존재·안전성 추천이 아니다.

각 설정값이 정수이고 범위 안인데 묶음 설정은 왜 실패할까?

앞 본문은 공급자가 같은 키를 덮어쓰는 순서를 설명했다. 새 입력은 JSON → 환경 → CLI의 고정 순서다. JSON은 Delay = 4, Timeout = 10을 제공하고 환경은 Delay = 8만 제공하며 CLI는 Timeout = 6만 제공한다. 최종 Delay는 8이고 Timeout은 6이다. 각 값을 1 이상 20 이하 정수로 읽는 검사는 통과하지만 업무 규칙 Delay < Timeout에는 실패한다.

마지막 공급자의 객체 하나를 통째로 골랐다고 생각하면 이 혼합을 놓친다. 실제 우선순위는 같은 키에 대한 값이며 CLI에 없는 Delay는 앞 공급자의 값이 남는다. 최종 설정을 먼저 모은 뒤 각 값의 형·범위와 값 사이의 관계를 검사해야 한다. 실패하면 서비스 시작을 거부한다는 자체 정책을 둔다. 낮은 우선순위 값으로 조용히 돌아가는 정책은 사용하지 않는다.

별도 CLI에서 Timeout 문자열이 빈 값이면 키가 없는 경우와 다르다. 키가 없으면 JSON의 10이 남아 Delay 8과 관계를 만족한다. 빈 문자열이 명시되면 이 과제의 정수 파싱은 실패하고 시작을 거부한다. 이 규약은 명시된 파싱 단계의 정책이지 모든 바인딩 API가 동일하게 행동한다는 주장이 아니다.

로그는 실패한 설정의 모든 원문을 공개하기보다 문제의 키와 사유, 안전한 상관 ID를 기록한다. 특히 토큰이나 비밀번호를 진단에 그대로 쓰지 않는 자체 최소 공개 정책을 둔다. 구조화 메시지는 자리 이름과 인수의 순서를 맞추어야 하며 저장된 로그의 수와 시작 성공 여부도 별도 기록한다. 두 번 실패 로그를 남겼다고 시작 시도를 두 번 성공한 것은 아니다.

설정 공급자를 순서대로 겹친다

configuration은 파일, 환경 변수, 실행 인자 같은 입력을 공통 키로 읽는 구조다. 같은 키에는 나중에 추가한 공급자의 값이 우선한다. 표준 Host 기본 구성에서는 명령행 인자가 환경 변수와 JSON 설정보다 우선하지만 직접 공급자를 추가하거나 순서를 바꾸면 그 구성을 다시 확인한다.

자체 모형은 JSON, 환경 변수, CLI 순서로 공급자를 추가한다고 명시한다. TimeoutSeconds에 30, 20, 10이 각각 있으면 최종 값은 10이다. 마지막 공급자에 그 키가 없으면 앞의 해당 값이 남는다. 프로그램이 사용한 실제 설정의 출처를 확인해야 오래된 파일만 읽고 원인을 단정하지 않는다.

숫자로 읽혔다고 유효한 정책은 아니다

문자열을 int로 변환할 수 있는지와 서비스가 허용하는 범위인지는 다르다. 자체 시간 제한 계약을 1부터 60초로 정하면 -5는 정수 변환이 가능해도 계약 위반이다. 잘못된 입력을 묵시적으로 성공 처리할지 실패로 알릴지 정책을 정하고 시험한다.

CLI 인자는 실행하는 사람이 쉽게 바꾸는 입력이다. 이론 활동에서는 특정 비밀값을 넣지 않고 키와 가상값만 사용한다. 실제 앱의 관리자 권한·비밀 저장 방식·배포 환경은 설정 계층만으로 검증되지 않는다. 오류 메시지에 비밀 전체를 그대로 복사하지 않는다.

메시지 템플릿과 값은 순서로 연결한다

ILogger의 메시지 템플릿은 이름 있는 자리와 값을 함께 기록한다. LogInformation("User {UserId} bought {Count}", userId, count)에서는 첫 인자가 첫 자리, 둘째 인자가 둘째 자리에 연결된다. 인자 변수 이름을 찾아서 자동으로 맞추는 방식이 아니다.

로그 수준과 event ID, 예외 출력은 공급자의 설정과 기능에 영향을 받는다. 구조화된 필드가 모든 저장소에서 같은 모습으로 보인다고 단정하지 않는다. 이벤트를 진단할 때 사용자 비밀 대신 필요한 식별·결과·시간 같은 최소 정보를 고른다. 로그가 있다는 사실만으로 행위의 성공이나 개인정보 처리가 검증되지는 않는다.

앞 본문은 기능 결과와 산출물 바이트를 별도 비교했다. 새 릴리스 장부는 소스 ID, SDK, 잠금 ID, TFM, RID, configuration과 산출물 집합을 빌드 입력 및 결과로 기록한다. 두 가상 실행 X/Y는 같은 DLL 바이트 h를 사용하지만 외부 설정 Limit이 각각 4와 7이다. 입력 5를 Limit 이하일 때 수용하는 업무에서는 X가 거부하고 Y가 수용한다. DLL 해시가 같아도 실행 입력은 다르다.

반대로 두 가상 DLL의 해시 h와 j가 다르지만 지정한 입력 3과 5의 결과가 같을 수도 있다. 유한한 두 시험의 기능 일치는 바이트 동일성이나 모든 입력의 등가성 증명이 아니다. 비교 보고서는 무엇의 바이트를 비교했는지, 어떤 환경과 입력에서 어떤 기능을 검사했는지를 따로 적어야 한다. 여기의 해시는 가상 식별자이며 실제 파일을 계산하지 않았다.

빌드 생략도 입력 동일성을 검증하는 명령이 아니다. 가상 옛 산출물 장부는 소스 S1, Debug, win-x64이고 새 계획은 소스 S2, Release, linux-x64다. --no-build로 새 입력을 적었다고 S2를 새로 컴파일하지 않는다. 호환 산출물이 없으면 실패할 수 있고 오래된 파일을 쓰는 경로에서는 새 소스의 증거가 아니다. 현재 계획의 빌드가 수행되었는지와 생략 옵션을 함께 기록한다.

이 활동의 제안 순서는 명시 SDK와 현재 요구를 고정하고 locked restore를 검증한 뒤 같은 입력으로 --no-restore publish를 수행하는 것이다. SDK 선택은 실행 runtime 선택과 다르고 framework-dependent/self-contained 및 RID도 명시한다. 성공한 공개나 새 환경 실행은 아직 없으며 가상 장부 분석을 실제 배포의 성공으로 기록하지 않는다.

재현의 기준과 입력을 먼저 적는다

재현은 같은 기능 시험 결과인지, 같은 패키지 그래프인지, 같은 산출물 바이트인지 기준을 명시해야 한다. 소스 commit, SDK, 의존성 잠금, 설정, 대상 runtime identifier, 빌드 옵션, 생성 파일과 시간 정보도 영향을 줄 수 있다. 소스가 같다는 한 조건만으로 바이트 일치를 선언하지 않는다.

global.json은 .NET SDK 선택 정책을 정하며 앱이 실행할 runtime 버전을 그대로 고정하는 파일은 아니다. version은 전체 SDK 버전이며 rollForward: disable은 정확히 그 버전을 요구한다. 지정 SDK가 설치되지 않은 실패를 다른 SDK를 사용한 성공으로 기록하지 않는다.

publish와 실행 환경을 구별한다

dotnet publish는 컴파일하고 실행에 필요한 의존성 및 runtime 설정 파일과 산출물을 폴더에 모은다. framework-dependent 방식은 대상 환경의 호환되는 .NET runtime을 요구한다. self-contained 방식은 runtime을 포함하지만 운영체제의 모든 의존성과 모든 장비 호환성을 자동 보장하지 않는다.

SDK와 대상 framework에 따라 기본 동작이 달라질 수 있으므로 이 활동은 --self-contained 또는 --no-self-contained와 RID를 명시한다. --no-build는 --no-restore도 뜻한다. 이전 산출물과 다른 입력으로 명령을 실행하면 오래된 파일을 포장할 수 있어 어떤 빌드 결과를 썼는지 확인한다.

공개 전에 실제 증거를 구분한다

제안 명령은 프로젝트가 존재하는 폴더에서 dotnet restore --locked-mode를 수행하고 dotnet publish -c Release -r win-x64 --no-self-contained -o ../artifacts/price를 수행하는 흐름이다. publish가 다시 restore를 할 수 있으므로 실제 절차에서는 잠금 강제 정책을 유지하거나 동일 입력의 restore 뒤 --no-restore를 명시한다. 출력 폴더는 프로젝트 밖에 두어 반복 포장 시 산출물을 입력으로 다시 포함하는 문제를 피한다.

명령의 성공, 산출물 목록, 해시, 별도 환경의 시작과 기능 시험을 각각 기록한다. 여기서는 프로젝트 생성·SDK 설치·restore·publish·해시 비교·새 환경 실행을 하지 않았다. 두 번 빌드하는 계획과 실제 두 산출물을 비교한 결과는 다르며 미수행 단계는 남겨 둔다.

CLI 키 부재와 빈 값은 별도 비교다. ④ DLL h의 Limit 4/7에서 입력 5를 비교하고, 옛 S1 산출물에 새 S2 계획의 --no-build를 적용한 보고를 감사하라. 각 질문은 명시한 초기 상태에서 별도 시작하며 실제 도구·학생 실행은 요구하지 않는다.

힌트 1

① 이전 이력과 이번 효과를 구별하고 Save의 실패 지점을 표시한다. ② cousin 조건 교집합과 direct-dependency-wins의 진단을 분리한다.

힌트 2

③ 키별 마지막 값을 고른 뒤 값 사이의 관계를 검사한다. ④ DLL의 비교 범위와 실행 입력, 새 빌드 수행 여부를 별도 장부에 적는다.

풀이와 답 확인

  1. ① 누적 Saves는 1이지만 둘째 저장은 0회다. 새 거부 대역에서는 Saves 0, Last null이다. 수량 3의 S는 E 뒤 Value 3이고 T는 Value 2이며 둘 다 정상 bool 반환이 없다.

  2. ② P 직접 참조가 없으면 공통 문턱을 만족하는 2.3.0이다. 직접 2.2.0은 더 낮은 선택과 downgrade 진단을 만들 수 있으며 자체 정책이 차단한다. 요구를 2.3.0으로 변경한 뒤 낡은 잠금의 locked restore는 실패한다.

  3. ③ 최종 Delay는 8이고 Timeout은 6이다. 두 값은 개별 범위에 있지만 관계가 실패하여 시작을 거부한다. CLI 키를 생략하면 Timeout 10으로 수용 가능하며 빈 값을 명시하면 이 과제의 파싱이 실패한다.

  4. ④ DLL h가 같아도 Limit 4에서는 입력 5를 거부하고 Limit 7에서는 수용한다. --no-build는 S2 컴파일을 수행하지 않으므로 최신 소스의 빌드 증거가 없다.

시험별 입력·이력, 패키지 선택·진단·잠금 일치, 설정 형·범위·관계, 산출물 바이트·실행 입력·빌드 수행을 각 장부로 구별한다. 실제 C#/restore/publish/서비스/학생 시험은 미수행이다.
