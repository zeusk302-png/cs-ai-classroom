exception flow·filter

예외를 던지면 바로 다음 줄은 실행될까?

정리가 상태를 바꾸는데 바깥 filter는 정리 전 값을 볼까?

앞 본문에서 when과 catch 안 if의 판단 시점이 달랐다. 새 순차 모형은 ready=true에서 시작한다. Inner는 T를 기록하고 원래 예외 E를 던진다. Inner의 finally는 Z를 기록하고 ready=false로 바꾼다. 바깥 catch의 filter는 현재 ready 값을 F:true 또는 F:false로 기록한 뒤 그 값을 반환한다. 강제 종료와 정리 실패는 제외한다.

예외 E의 handler 탐색에서 바깥 filter가 먼저 ready=true를 읽는다. 따라서 기록은 T,F:true,Z,H다. H는 선택된 바깥 handler의 기록이다. handler 본문에서 ready를 읽으면 이미 false다. filter에서 본 값과 본문에서 본 값이 다른 이유는 동시 실행이 아니라 두 단계 사이의 내부 finally다.

별도 모형의 첫 filter는 G를 기록하고 hits를 1 증가시킨 뒤 false를 반환한다. 다음 catch가 B를 기록하면 첫 catch 본문은 실행되지 않지만 G와 hits 변경은 남는다. filter 평가 중 일반 예외 X를 던지는 변형에서도 해당 filter는 false로 취급되어 원래 E의 다음 handler를 찾는다. 이는 filter에 새 실패 처리/업무 변경을 맡겨도 좋다는 뜻이 아니다.

실패하면 돌아갈 길을 찾는다

throw 뒤의 같은 정상 경로는 진행하지 않는다. 현재 try의 catch를 위에서부터 찾아 예외 타입과 filter 조건이 맞는 곳으로 제어를 옮긴다. 해당 범위에서 처리할 곳이 없으면 호출자 방향으로 탐색한다. 예외 하나를 잡는다고 모든 catch가 차례로 실행되지는 않는다.

구체 타입 처리와 일반 처리를 배치할 때 도달 가능성을 따진다. 예외가 예상됐다고 무조건 삼키면 호출자는 성공으로 오인할 수 있다. 처리한 결과나 전파 조건을 계약에 밝혀 둔다.

조건은 탐색할 때 평가한다

when filter는 이 catch가 담당할지 결정하는 Boolean 식이다. matching handler를 찾는 탐색 단계에서 평가되어, 그 handler로 이동하기 위한 stack unwinding보다 앞선다. catch 안 if에서 다시 throw하는 방식과 시점이 다르다.

filter에서 상태를 바꾸면 뒤의 탐색에도 영향이 남을 수 있어 짧고 부작용이 적은 판단을 권한다. 정리용 finally는 일반적인 return·정상 종료·예외 전파 때 실행되지만 프로세스 강제 종료까지 무조건 보장하는 장치는 아니다.

흐름을 종이에 적는다

아래 조각은 using System이 있는 C# 메서드 본문을 가정한다. 의도적으로 예외를 던지는 교육 사례이며 실행하지 않았다. n이 양수일 때 F handler, 그렇지 않을 때 B handler가 선택된다.

catch에서 같은 예외를 재전파하려면 throw;가 원래 stack trace를 보존하는 방식이다. throw ex;와 혼동하지 않는다. finally에서 새 예외를 던지면 원래 문제 진단을 흐릴 수 있으므로 정리 실패 정책도 필요하다.

int n = -1;
try { Console.Write("T"); throw new InvalidOperationException(); }
catch (InvalidOperationException) when (n > 0) { Console.Write("F"); }
catch (InvalidOperationException) { Console.Write("B"); }
finally { Console.Write("Z"); }

조건을 바꾸어 비교하기

같은 Boolean을 서로 다른 시점에 읽는다

위 모형에서 바깥 filter 대신 filter 없는 catch 안 if(ready)로 H 또는 B를 고르면 어떻게 달라지는가?

  1. filter 없는 handler를 선택한 뒤 먼저 Inner의 finally가 ready를 false로 만든다.

  2. catch 본문의 if는 false를 읽어 B를 기록한다.

새 기록은 T,Z,B다. 원래 filter 모형의 T,F:true,Z,H와 다르다.

재시도 수를 제한해도 마감과 중복 효과가 자동 지켜질까?

새 직렬 시간 모형은 최대 시도 3회, 각 호출의 최대 시간 30 ms, 실패 뒤 대기 40 ms와 80 ms, 절대 마감 150 ms다. 시작 시각은 0이고 다음 호출을 시작하기 전에 대기와 호출의 전체 최악 시간을 합쳐 마감 이하인지 검사한다. 시간은 교육 모형이며 타이머·네트워크를 실행하지 않는다.

첫 호출은 0–30 ms, 첫 대기는 30–70 ms, 둘째 호출은 70–100 ms다. 다음 대기와 셋째 호출의 완료 예정은 100+80+30=210 ms라 마감을 넘는다. 정책은 둘째 실패 시각 100 ms에 더 시도하지 않고 중단한다. 단순히 시도 횟수만 검사하면 셋째는 180–210 ms에 실행하여 마감을 위반한다.

별도 계층 모형은 바깥 최대 3시도, 각 바깥 시도 안쪽 최대 2시도다. 모든 안쪽 호출이 실패하고 각각 10 ms이며 한 안쪽 대기는 5 ms다. 바깥 대기는 20 ms와 40 ms, 다른 비용은 없다. 실제 최하위 호출은 6회이고 총 시간은 3×(10+5+10)+20+40=135 ms다. 이 경우 시도 수를 3+2로 더하는 정책은 요청 수를 잘못 센다.

자체 포인트 원장은 초기 40이며 요청 R이 10을 차감한다. 처리와 R 결과 기록이 하나의 원자 업무이고 기록이 아직 보존되어 있으면 첫 수행 뒤 응답 손실·같은 R 재시도는 잔액 30을 유지하며 기존 결과를 돌려준다. 중복 기록 없이 차감하면 잔액 20이 된다. R 기록을 삭제한 뒤 다시 오는 요청을 새 업무로 처리하는 정책도 20이므로 보존 기간과 재시도 범위를 함께 정해야 한다.

메서드 계약에는 정상 결과뿐 아니라 잘못된 입력·권한 부족·일시 연결 실패·취소가 어떻게 나타나는지도 필요하다. 도메인의 예상 실패는 결과 값으로, 호출 전제 위반은 예외로 설계할 수 있다. 어느 방식이든 호출자가 구분할 정보와 부작용 상태를 보존한다.

기다리면 고쳐질 것인가

연결 혼잡 같은 일시 오류에는 제한된 재시도가 도움이 되지만 형식이 틀린 입력을 그대로 반복하면 보통 해결되지 않는다. 취소 요청은 사용자 의도이므로 일반 일시 장애처럼 계속 반복하지 않는다. 총 deadline과 서비스 권고 지연도 확인한다.

준비 개념과 학습 목표

준비 개념

  • null

  • 분기

학습 목표

  • string와 string? 의도를 구별한다.

  • nullable context와 API 계약을 설명한다.

helper가 true를 반환하면 어떤 값이 null이 아니라고 약속하는가?

앞 본문은 선언과 현재 null-state를 구별했다. 새 순차 helper는 Present([NotNullWhen(true)] string? value)이고 구현은 value is not null이다. true는 전달된 인수의 값이 null이 아니라는 사후 조건을 분석기에 전달한다. false이면 null이라고 하는 반대 방향까지 속성 하나가 일반적으로 보장하지는 않는다.

별도 NonBlank helper의 구현은 !string.IsNullOrWhiteSpace(value)이고 같은 NotNullWhen(true)를 붙인다. null, 빈 문자열, 공백 하나는 모두 false이며 cat은 true다. false의 이유는 셋이 다르므로 출력 Boolean만으로 누락/빈 값/공백을 다시 구별할 수 없다. true이면 null이 아니지만 false이면 반드시 null이라는 추론은 틀린다.

현재 문맥은 #nullable enable이며 System.Diagnostics.CodeAnalysis를 사용한다. 선언된 사후 조건은 구현과 일치해야 한다. Lies([NotNullWhen(true)] string? value)가 무조건 true를 반환하는 변형은 null에서도 true여서 호출자가 value.Length를 읽을 때 실패한다. 컴파일러가 관련 구현 경고를 낼 수 있더라도 경고를 무시해 만든 실행의 런타임 검사를 속성이 자동 추가하는 것은 아니다.

독립 과제마다 입력을 새로 시작한다. 지역 input을 한 번 저장하여 검사하면 검사한 그 참조값을 다음 줄에서 사용한다. 속성은 모든 다른 변수·같은 객체의 다른 필드·미래 getter 호출까지 null이 아니라고 선언하는 전역 약속이 아니다. 새로운 C# 컴파일과 분석 진단은 실제 수행하지 않았다.

선택 여부를 선언한다

nullable annotation context에서 string은 null을 받지 않으려는 의도, string?은 null 가능성을 표현한다. 두 표기는 별개의 CLR 문자열 클래스를 만들지 않으며 자동 검사 코드를 추가하지도 않는다. 정적 분석에 전달하는 계약 정보다.

값 형식 int?가 Nullable<int>로 표현되는 것과 reference annotation은 다르다. 과거 라이브러리처럼 정보가 없는 oblivious 경계도 있어 단순 물음표 개수로 전체 안전성을 판단하지 않는다.

분기마다 알고 있는 사실

분석기는 값 할당과 검사에 따라 not-null 또는 maybe-null 상태를 추적한다. nullable 변수여도 non-null 리터럴을 넣은 직후에는 직접 사용을 경고하지 않을 수 있다. 반대로 non-null 선언에 null을 넣으면 의도 위반 경고가 생긴다.

지역 변수의 if 검사는 안쪽 흐름에 근거가 된다. 다른 메서드의 내부를 마음대로 추론하는 것은 아니므로 검사 helper는 NotNullWhen 같은 적절한 속성으로 관계를 전달할 수 있다. 속성도 구현이 계약을 지켜야 유용하다.

없음을 처리하는 작은 함수

다음은 #nullable enable 문맥의 C# 클래스 안 정적 메서드 조각이다. null은 길이 0으로 취급한다는 이 함수만의 계약을 정했다. 비어 있는 문자열도 길이 0이므로 두 경우가 동일 결과를 낸다.

원래 뜻이 다른데 편의를 위해 null을 빈 문자열로 바꾸면 정보가 사라질 수 있다. API가 누락과 빈 입력을 구별해야 하는지는 먼저 결정한다. 이 예제는 소스의 분기와 예상 값을 종이로 추적하며 컴파일은 하지 않았다.

{
    if (text is null) return 0;

한 번 확인한 property를 다시 읽어도 같은 참조가 나올까?

자체 Source.Name getter는 첫 읽기에 cat, 둘째 읽기에 null을 반환한다. 동시 변경 없이도 getter가 호출 횟수에 따라 상태를 바꾼다. source.Name is not null을 확인하고 다시 source.Name!.Length를 읽으면 검사한 값은 cat이지만 사용한 값은 null이다. 두 읽기를 같은 사실로 합치는 가정이 잘못됐다.

지역 saved=source.Name으로 딱 한 번 읽고 saved is null이면 거절, 아니면 saved.Length를 쓰는 변형은 cat의 길이 3을 얻는다. 이후 source.Name의 변화는 지역 참조 saved를 다시 null로 대입하는 것과 다르다. 이 순차 모형의 지역 참조 안전성만 보장하며 객체의 모든 불변식·외부 서비스 일관성까지 보장하지 않는다.

새 string[2]는 슬롯 두 개의 런타임 초기값이 null이다. 원소 타입을 string으로 썼다는 의도가 배열의 요소를 실제 문자열로 채우지는 않는다. values[0]=cat만 수행하면 첫 슬롯은 길이 3이지만 둘째 슬롯의 values[1]!.Length는 실패한다. 주어진 작은 배열의 실제 초기화 범위와 각 슬롯의 검사를 별도로 확인한다.

실패를 정상 길이로 숨기는 것과 존재 여부를 보존하는 것은 다르다. null 조건부 Length에 ?? -1을 쓰면 null은 −1, 빈 문자열은 0, cat은 3이다. 이 자체 표식에서 음수가 누락을 구별하지만 이름의 모든 도메인 유효성은 따로 판단한다. 경고 없는 코드라는 주장과 런타임 입력/조회 횟수의 근거를 분리한다.

  • 후위 !와 런타임 값

분석을 억제하는 약속

후위 !는 앞 표현식을 not-null로 취급하라고 분석기에 말하는 null-forgiving 연산자다. null을 문자열로 바꾸거나 조건 검사를 수행하지 않는다. 앞에 붙이는 Boolean 부정 !와 쓰는 위치도 다르다.

확실한 불변식이 분석기에 보이지 않을 때 사용할 수 있지만 근거가 틀리면 런타임 실패는 그대로다. 외부 데이터·옛 라이브러리·reflection 경계에서 non-null 의도를 배반할 수 있어 입력 검증이 필요하다.

경고 정책과 실행 정책

nullable 경고를 오류로 취급하는 빌드 설정이면 경고가 빌드를 막을 수 있다. 이는 프로젝트 정책이며 언어가 non-null 참조를 런타임에서 새 타입으로 강제하는 것이 아니다. 억제나 정보 부족으로 경고 없는 잘못된 프로그램도 만들 수 있다.

비어 있는 문자열의 Length는 0이고 null 참조의 Length는 객체가 필요해 NullReferenceException을 일으킨다. 둘을 같은 값으로 생각하면 진단과 복구 모두 흐려진다.

다른 문제에 적용하기

네 독립 계약을 감사하라. (1) ready=true에서 Inner가 T 기록 후 E를 던지고 finally가 Z 기록 후 ready=false로 만든다. 바깥 filter는 F와 현재 ready를 기록해 그 값을 반환하며 선택 handler는 H를 기록한다. filter 선택과 H 내부 ready를 구한다. 별도 hits=0의 첫 filter는 G 기록과 hits++ 후 X를 던지고 다음 catch가 원래 E를 B로 처리한다. (2) 최대 3회/각 30 ms/대기 40·80 ms/마감 150 ms이며 다음 대기+최악 호출 완료가 마감 이하일 때만 승인한다. 둘째 실패 뒤의 시도 수와 중단 시각을 구한다. 별도 원장 40에서 R 차감 10과 결과 기록을 원자적으로 보존한 뒤 응답 손실·같은 R 재시도가 있다. 잔액을 구한다. (3) NonBlank는 null/빈 문자열/공백을 false로, cat을 true로 반환하며 NotNullWhen(true)가 있다. false에서 누락을 단정하는 논리를 반박한다. (4) 새 Source.Name은 첫 cat/둘째 null이다. 반복 조회 계획과 지역 saved 한 번 조회 계획의 결과를 비교한다. 각 항목은 별도 초기 상태의 순차 손모형이며 실제 C#/네트워크/학생 실행은 없다.

힌트 1

handler 탐색과 내부 정리의 시간 순서를 분리하고 filter가 false여도 이전 효과를 지우지 않는다.

힌트 2

다음 전체 완료 예산·원자 결과 기록·속성의 논리 방향·실제 조회 횟수를 각각 검사한다.

풀이와 답 확인

  1. (1) T,F:true,Z,H이며 H에서 ready는 false다. 별도 filter 예외는 false 취급이라 원래 E가 B로 처리되고 기록 G,B와 hits=1이 남는다.

  2. (2) 둘째 실패는 100 ms다. 다음 완료 예정 210 ms가 마감 150 ms를 넘어 더 대기/시도하지 않는다. 시도 2회/재시도 1회다. 별도 원자 R 기록이 보존되므로 잔액은 30을 유지한다.

  3. (3) false는 null/빈 값/공백 세 경우여서 null을 단정하지 못한다. true의 인수 not-null 사후 조건과 도메인 분류를 구별한다.

  4. (4) 반복 계획은 둘째 null의 Length에서 실패한다. 한 번 저장 계획은 saved=cat의 길이 3이다. 각 계획은 새 Source에서 시작하며 !는 두 번째 값을 바꾸지 않는다.

탐색/정리의 T,F:true,Z,H와 별도 G,B·hits 1, 보수적 중단 100 ms와 원장 30, false의 정보 손실, 반복 실패 대 저장 길이 3을 각 계약의 근거로 설명한다.

해결한 뒤 점검할 것

  • filter가 본 ready와 handler가 본 ready를 서로 다른 시점으로 설명한다.

  • filter 예외와 finally 예외의 서로 다른 규칙을 구별한다.

  • 마감 승인식·시도/재시도 수·원자 R 기록의 보존을 적는다.

  • NotNullWhen의 단방향 조건과 getter 평가 횟수를 확인하고 실제 실행/학생 미수행을 유지한다.
