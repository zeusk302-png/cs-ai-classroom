소단원 11.1

GC와 관리 메모리

두 객체가 서로 가리키면 아무도 쓰지 않아도 영원히 남을까?

준비 개념과 학습 목표

준비 개념

  • 객체와 참조

  • 화살표 그래프

학습 목표

  • root에서 도달 가능한 객체를 찾는다

  • 참조 개수와 도달 가능성을 구별한다

  • 수집 가능 상태와 실제 회수 시점을 분리한다

지역 변수를 비워도 오래 사는 발행자가 구독자를 붙잡을까?

앞 본문에서는 root에서 따라갈 수 있는 객체를 셌다. 새 그림에는 static root가 가리키는 발행자 P, P의 이벤트 delegate D, D가 가리키는 구독자 S, S의 buffer B가 있다. 참조 간선은 P→D→S→B이고 S→P도 있다. 명시한 가상 크기는 P가 8, D가 8, S가 16, B가 32바이트다. 다른 root·finalizer·약한 참조는 제외한 종이 그래프다.

구독자 지역 변수 s를 null로 바꾸어도 static root에서 P,D,S,B까지 모두 도달하므로 도달 크기는 64바이트다. 순환이 있다는 이유도, null을 썼다는 이유도 단독 회수 판정이 아니다. 저장해 둔 정확한 이벤트 handler를 -=로 제거하고 다른 참조가 없으면 P만 도달하며 D,S,B의 합 56바이트는 이 제한 모형에서 회수 후보다. 실제 회수 시각이나 프로세스 메모리 감소는 계산하지 않았다.

정리의 효과와 객체의 도달성도 다르다. S.Dispose가 buffer 사용을 종료하지만 이벤트 구독을 제거하지 않는 자체 변형에서는 이벤트 간선이 남아 S도 도달한다. Dispose가 managed 객체를 GC에서 즉시 없애는 연산이라고 해석하지 않는다. 이름 없는 lambda를 새로 써서 제거하기보다 가입 시 handler를 저장하거나 같은 대상/메서드의 handler를 정확히 제거하는 계약이 필요하다.

출발점에서 화살표를 따라간다

GC는 관리 객체의 메모리를 자동으로 관리한다. root는 프로그램이 계속 사용할 수 있는 참조의 출발점이다. root에서 객체 참조를 따라 도달하는 객체를 찾으면 외부에서 사용할 수 없는 객체를 구별할 수 있다.

이 단원의 그래프는 주어진 root만 있는 정지 상태의 교육 모형이다. 실제 CLR의 root에는 스택·레지스터·정적 데이터 등이 있고 JIT는 참조가 살아 있는 구간을 결정한다. 소스 변수의 중괄호 범위만으로 정확한 GC 시각을 예측하지 않는다.

순환 자체가 생존 이유는 아니다

A가 B를 가리키고 B가 A를 가리키더라도 root에서 둘로 가는 경로가 없다면 일반 관리 객체는 수집 대상이 될 수 있다. 서로 참조한다는 사실과 프로그램에서 도달한다는 사실은 다르다.

관리 참조를 계속 정적 캐시에 보관하면 사용 의도가 끝나도 도달 가능성이 유지될 수 있다. GC가 존재한다고 모든 불필요한 저장이 자동으로 제거되지는 않는다. 캐시 정책과 참조 유지 범위를 설계해야 한다.

언제 회수하는지는 별도다

수집 가능이라는 분류는 즉시 메모리가 반환됐다는 관측이 아니다. CLR은 할당과 메모리 압력 등 조건에 따라 수집한다. 세대는 오래 살아남은 객체와 짧게 사는 객체를 다루는 전략이며 특정 시간표를 약속하지 않는다.

여기서는 finalizer·weak reference·pinning을 제외하고 표에 정한 가상 바이트만 더한다. 실제 객체 header와 정렬·힙 segment·프로세스 사용량을 측정한 계산이 아니다. 관리 메모리 회수와 파일 handle 정리도 서로 다른 작업이다.

조건을 바꾸어 비교하기

지역 참조와 발행자의 참조를 따로 지운다

s=null 뒤에 P의 이벤트를 정확히 제거하는 전후 도달 집합을 구하라.

  1. null은 지역 변수의 간선만 없앤다. static→P→D→S→B 경로는 남는다.

  2. handler 제거 뒤 D를 보관한 다른 root도 없다는 조건에서 P의 다음 간선이 사라진다.

도달 크기는 64에서 8바이트로 줄며 새 회수 후보는 56바이트다.

순환도 root가 없으면 후보가 된다

새 독립 상태에서 s=null이고 static P 참조도 null이다. 네 객체 사이 간선은 그대로지만 다른 root는 없다.

  1. 시작 root 집합이 비어 네 객체 어느 것도 도달하지 못한다.

  2. S→P 순환은 객체 내부에서만 이어지며 root 경로를 새로 만들지 않는다.

64바이트 전체가 제한 모형의 회수 후보다. 실제 GC 완료를 뜻하지 않는다.

연습 1 · 값과 상태 예측

정확 handler를 제거했지만 별도 static saved가 S를 보관한다. 원래 S→P와 S→B는 남는다. D는 다른 참조가 없다. 도달 집합과 후보는?

힌트 1

두 root P와 saved를 모두 출발점으로 삼는다.

힌트 2

P에서 D로 가던 간선은 제거됐다.

풀이와 답 확인

  1. P,S,B는 도달하여 크기는 8+16+32=56바이트다.

  2. D의 8바이트만 회수 후보다.

도달 크기는 56바이트, 회수 후보는 D의 8바이트다.

handler 제거만 하면 S/B도 언제나 후보다.

saved라는 별도 root 경로가 S/B를 보유한다. 모든 보유 경로를 감사한다.

연습 2 · 오류 찾아 고치기

S.Dispose만 호출하고 s=null로 바꿨으므로 이벤트 참조도 자동 사라졌다고 했다. Dispose 구현은 이벤트를 건드리지 않는다.

힌트 1

호출 이름이 아니라 구현 효과를 적는다.

힌트 2

P의 이벤트 목록을 다시 그린다.

풀이와 답 확인

  1. P→D→S→B는 그대로다.

  2. 사용 종료와 이벤트 구독 제거를 별도 계약으로 구현하거나 owner가 제거해야 한다.

Dispose가 이벤트를 자동 해제하는 보편 규칙은 없다.

흔한 오답에서 다시 생각하기

IDisposable이면 GC가 모든 외부 참조를 자동 지운다.

GC는 도달성을 추적하며 IDisposable이라는 타입이 보유 간선을 모두 제거하지 않는다.

연습 3 · 직접 만들어 보기

구독 생성과 종료를 쌍으로 관리하라. 가입 시 handler를 하나 보관하고 종료 뒤 추가 이벤트 호출이 없어야 하는 순차 계약이다.

힌트 1

구독 때 사용한 delegate를 보관한다.

힌트 2

종료 때 구독 제거와 보관 참조 해제를 나눈다.

풀이와 답 확인

  1. handler를 저장하고 P.Event+=handler로 한 번 등록한다.

  2. 종료에서 P.Event-=handler를 수행하고 불필요한 handler/S 참조도 놓는다. 반복 종료는 이 자체 owner가 중복 작업하지 않도록 상태를 기록한다.

정확한 구독 관계를 제거한 뒤 모든 다른 root를 확인한다. 동시 이벤트 진행까지 이 순차 모형으로 증명하지 않는다.

흔한 오답에서 다시 생각하기

같은 모양의 새 lambda를 -=에 쓰면 언제나 가입 항목이다.

별도의 익명 함수가 같은 delegate라고 보장하지 않는다. 가입 때의 handler를 저장한다.

두 번째 자원 생성이 실패하면 아직 만들지 못한 객체도 Dispose할까?

앞 본문은 정상 생성된 A/B의 역순 정리를 추적했다. 새 중첩 using은 먼저 A를 정상 취득하여 acquire-A를 기록하고, 안쪽에서 B를 취득하려다 acquire-B를 기록한 뒤 예외 E로 실패한다. 실패한 B 생성은 호출자에게 객체를 반환하지 않았다. A.Dispose는 dispose-A를 기록하고 정상 완료한다. 강제 종료와 비동기는 제외한다.

using은 취득 뒤 사용을 try/finally로 감싼다. 그러므로 B 취득이 실패하면 B의 using 정리 구간은 시작하지 못하며 호출자의 dispose-B 기록은 없다. 이미 정상 취득한 A의 바깥 finally는 수행한다. 기록은 acquire-A,acquire-B,dispose-A이며 E가 전파된다. B 생성 내부에서 임시 자원을 취득했다면 그 실패 정리는 B 생성 코드의 별도 책임이지 이 using이 자동 대체하지 않는다.

별도 정상 A/B 취득 후 본문이 return 7을 계산해도 정리 성공이 필요하다. B.Dispose가 dispose-B를 기록하고 예외 C를 던지며 A.Dispose가 정상 완료하는 변형이면 기록은 dispose-B,dispose-A이고 반환 7은 완료되지 않는다. using이 정리를 시도하도록 만드는 것과 모든 정리 성공·업무 결과 성공을 보장하는 것은 다르다.

정리를 호출하는 계약

IDisposable은 Dispose를 통해 정리하는 계약이다. 파일 handle 같은 자원이나 소유한 다른 disposable 객체의 정리를 연결할 수 있다. Dispose가 객체의 관리 메모리를 즉시 지우는 명령은 아니다.

자원을 생성해 소유하는 코드가 정리 책임을 지는 것이 일반적이다. 다른 코드에서 잠시 빌린 자원은 합의 없이 닫지 않는다. API의 ownership 설명을 읽어 생성·이전·대여를 구별한다.

scope를 빠져나갈 때 정리한다

using 블록은 확보한 자원을 블록 종료 때 정리한다. 블록 안에서 예외가 발생하거나 return해도 try/finally와 같은 정리 경로가 있다. using 선언은 선언한 scope가 끝날 때 정리한다.

여러 자원을 확보하면 뒤에 선언한 자원부터 정리한다. 이 예제는 생성과 Dispose가 모두 성공하는 정상적 환경을 가정한다. 프로세스 강제 종료나 Dispose 자체 예외까지 모든 작업 성공을 약속하는 문장이 아니다.

반복 정리와 async는 따로 설계한다

잘 설계한 Dispose는 반복 호출로 자원을 두 번 해제하지 않도록 멱등성을 갖는다. 이미 정리했는지 상태를 기록하고 후속 호출은 추가 효과 없이 끝내는 패턴이 있다. using이 모든 사용자 정의 타입의 결함을 대신 수정해 주지는 않는다.

비동기 정리가 필요한 IAsyncDisposable에는 await using을 사용한다. using 지시문으로 namespace를 가져오는 문법과 using으로 자원 수명을 정하는 문법도 서로 구별한다. dispose 뒤 객체를 계속 사용해도 된다는 보장은 없다.

같은 native 자원 번호를 가진 두 wrapper는 서로의 정리를 알까?

앞 본문에서 finalizer는 예측 가능한 마감 수단이 아니었다. 새 자체 자원 장부는 열린 native token H 하나와 owner W 하나를 둔다. W의 순차 Dispose는 열린 상태일 때 H를 닫고 closed=true를 기록하며 반복 호출은 아무 동작도 하지 않는다. alias a와 b가 같은 W 객체를 가리키면 두 경로의 Dispose 호출은 같은 closed 상태를 본다.

별도 잘못된 설계는 같은 H 번호를 가진 서로 다른 owner W1/W2를 만든다. 각각 자신의 closed=false로 시작하며 서로 독립된 상태다. W1.Dispose 뒤 W2.Dispose는 자기 상태만 보고 두 번째 close를 시도한다. 같은 owner의 반복 Dispose를 안전하게 만든다고 서로 다른 owner의 중복 소유까지 자동 해결되지는 않는다. 실제 OS의 번호 재사용·오류 반환·두 번째 close 결과는 이 장부 모형에서 예측하지 않는다.

올바른 자원 종류에 맞는 SafeHandle을 하나의 소유 표현으로 두고 소비자는 빌린 접근 기간을 지켜야 한다. raw 값만 복사해 새 owner를 만드는 것은 소유권 이동 증거가 아니다. 직접 finalizer가 필요한 고급 구현에서도 부분 초기화와 이미 닫힌 상태를 고려하며, managed 필드의 다른 finalizer 순서나 UI 스레드를 기대하지 않는다. 여기서는 SafeHandle의 실제 네이티브 호출을 실행하지 않았다.

wrapper와 외부 자원을 구별한다

관리 객체가 운영체제 handle을 감싸고 있어도 GC가 그 handle의 고유 해제 절차를 모두 아는 것은 아니다. 관리 wrapper의 메모리와 외부 자원의 사용 가능 상태는 따로 기록한다.

정상 사용이 끝난 자원은 Dispose로 정리하는 경로를 제공한다. 직접 handle을 관리할 필요가 있다면 올바른 해제 함수를 연결한 SafeHandle 대안을 먼저 검토한다. handle 숫자를 임의의 메모리 주소처럼 쓰지 않는다.

마지막 정리는 시간표가 아니다

finalizer는 직접 소유한 비관리 자원을 위한 마지막 정리 경로로 사용할 수 있지만 언제 실행되는지 정해져 있지 않다. 두 객체의 finalizer 순서와 실행 thread도 기대하지 않는다. 실행이 완료되지 않거나 실행 기회가 없을 수 있다.

따라서 finalizer가 10ms 안에 실행된다고 가정해 자원 한도를 관리하면 안 된다. C#에서는 ~TypeName 문법으로 finalizer를 작성하며 Object.Finalize를 직접 override하는 방식은 쓰지 않는다. 일반 관리 객체만 보관하는 타입에 무조건 추가하지 않는다.

명시 정리 후 중복 경로를 막는다

dispose pattern은 명시 경로와 finalizer 경로를 분리한다. Dispose(true)는 소유한 disposable 구성요소의 정리도 연결할 수 있고 finalizer의 false 경로는 다른 관리 객체의 정리 순서에 의존하지 않도록 한다.

명시 정리 후 GC.SuppressFinalize로 해당 객체의 finalization을 억제하는 일반 패턴이 있다. SafeHandle이 정리를 맡으면 바깥 wrapper가 직접 finalizer를 추가하지 않아도 된다. 어느 경로든 이중 해제 방지와 정확한 소유권은 필요하다.

겹친 부분 범위의 복사와 저장된 view의 사용 권리는 같은 문제일까?

앞 본문에서 view는 원본 일부를 함께 보았다. 새 배열 a=[1,2,3,4,5]에서 source=a.AsSpan(0,4), destination=a.AsSpan(1,4)다. source.CopyTo(destination)는 겹침을 지원하여 원래 네 값 1,2,3,4를 옮기므로 a=[1,1,2,3,4]다. 복사 API의 계약을 같은 방향의 손수 루프와 혼동하지 않는다.

별도 같은 초기 배열에서 i=0부터 3까지 a[i+1]=a[i]를 순서대로 수행하면 첫 덮어쓴 값을 다음 단계가 다시 읽는다. 상태는 [1,1,3,4,5], [1,1,1,4,5], [1,1,1,1,5], [1,1,1,1,1]로 변한다. 거꾸로 i=3부터 0까지 옮기면 [1,1,2,3,4]를 보존한다. 범위 길이 검사와 겹침 방향은 다른 조건이며 CopyTo의 겹침 규약은 동시 쓰기 안전의 보장이 아니다.

다른 자체 풀 일정에는 owner O가 buffer를 빌리고 t=2에 Memory view m을 Task 소비자에게 넘긴다. 소비자는 t=9에 terminal 상태가 되고 그 뒤 사용하지 않는 계약이다. O가 t=6에 반환하고 풀의 새 owner가 t=7에 내용을 99로 쓰면 옛 m이 객체로 남아 있어도 t=8에 읽을 권리는 없다. 배열을 GC가 보존하는 것과 풀의 사용 권리를 보존하는 것은 다르다. 정상 owner는 terminal 확인 및 다른 소비 종료 뒤 반환한다.

부분 범위를 가리키는 view

Span<T>는 연속 메모리 범위를 가리키며 부분 범위의 요소를 처리할 수 있다. view를 만들었다고 원소 전체를 복사한 새 배열이 생기는 것은 아니다. 원본 배열의 부분 view에서 쓰면 같은 원본 요소가 바뀐다.

ReadOnlySpan은 그 view를 통해 쓰지 못하게 하는 의미다. 다른 참조로 원본을 수정하는 상황까지 원본이 영원히 불변이라고 보장하지 않는다. 이 예제는 한 소비자만 순서대로 접근하여 경쟁을 제외한다.

view 저장 제한과 buffer 위치는 다르다

Span은 ref struct라 관리 heap으로 탈출하는 사용에 제한이 있다. 일반 class 필드나 boxing·lambda capture에 넣지 않는다. Span이 heap 배열을 볼 수 있으므로 Span 제한을 원본 데이터가 반드시 stack이라는 뜻으로 해석하지 않는다.

Memory<T>는 관리 heap에 저장할 수 있어 비동기 API에 전달할 때 사용할 수 있다. C# 13부터 async 안의 일부 구간에서 ref struct를 허용하지만, await와 같은 블록에서는 ref struct 변수를 사용할 수 없다. 모든 async 함수에서 Span을 무조건 금지하는 과거 설명으로 일반화하지 말고, 사용하는 언어 버전과 블록·수명 규칙을 확인한다.

저장할 수 있어도 수명 책임은 있다

owner는 buffer 수명을 관리하고 consumer는 허용된 lease 동안 읽거나 쓴다. Memory를 값으로 복사해 보관해도 owner의 수명이 자동으로 늘어나는 소유권 계약이 생기지는 않는다. 풀로 반환한 buffer를 뒤 작업이 계속 사용하면 새 사용자의 데이터와 충돌할 수 있다.

동기 소비는 메서드 반환 때 lease가 끝나고 Task 반환 소비는 Task가 완료·실패·취소 상태에 이른 뒤 계속 사용하지 않는다. owner는 소비가 끝나기 전에 Dispose하거나 반환하지 않는다. 배열 view와 pool 소유권 예제는 서로 다른 조건으로 명시한다.
