소단원 1.1

역할과 책임

셋이 모두 “앱 담당”이면 누가 마지막으로 확인해야 할까?

준비 개념과 학습 목표

준비 개념

  • 산출물은 작업 뒤 다른 사람이 확인할 수 있는 결과다. 화면 설계도·소스 파일·검토 기록이 예다.

  • 권한은 어떤 결정을 할 수 있는 범위이고 책임은 맡은 결과를 설명하고 미완료를 알릴 의무다.

  • 의존성은 한 작업이 다른 작업의 결과를 필요로 하는 관계다. 문제 형식이 정해져야 채점 화면을 만들 수 있다.

학습 목표

  • 수행·검토·결정·연락 역할을 산출물별로 구분한다.

  • 권한과 의존성을 포함해 역할 누락을 찾는다.

직함보다 결과와 행동을 먼저 적는다

가상 세 사람 민·서·준이 퀴즈 앱을 만든다. “민은 개발”만 쓰면 화면 오류를 누가 고치고 누가 받아들일지 알기 어렵다. 역할은 특정 결과에 대해 수행할 행동의 묶음이다. 작업 수행자는 만들고, 검토자는 기준과 비교하며, 결정자는 허용된 범위의 승인이나 변경을 정한다. 연락 창구는 필요한 정보를 전달한다. 한 사람이 여러 역할을 맡을 수 있지만 역할들이 같은 뜻은 아니다.

책임을 맡겼다면 필요한 권한·정보·시간도 연결해야 한다. 서에게 문제 품질 책임을 주면서 정답표를 볼 수 없게 하면 확인이 불가능하다. 검토를 요청한 사람이 자동으로 최종 결정자가 되는 것도 아니다. 이 예에서는 산출물마다 결정자 한 명을 지정하되 다른 사람의 반론과 전문 검토를 받아야 한다고 합의한다. 모든 팀이 반드시 한 명의 결정자를 가져야 한다는 보편 규칙은 아니다.

경계에는 전달할 계약이 필요하다

민이 화면, 서가 문제와 정답, 준이 검토를 맡는다면 “문제 목록 완성”의 형식도 정해야 한다. 여기서는 문제 ID, 질문, 선택지 네 개, 정답 번호를 표 한 행으로 전달한다. 민은 정답 번호가 1–4인지 확인하고, 준은 선택지와 정답의 내용이 일치하는지 따로 확인한다. 형식 검사와 내용 검토를 서로 떠넘기지 않는다.

작업표의 각 행에는 결과·수행자·검토자·결정자·필요 입력·기한을 적는다. 필요한 입력의 제공자가 비어 있으면 맡은 사람이 있어도 시작할 수 없다. 수정 요청은 누가 무엇을 언제 바꿀지 새 행이나 변경 기록으로 연결한다. “누군가 알아서”라는 표현은 책임이 정의되었다는 근거가 아니다.

책임 분담은 잘못을 한 사람에게 몰아주는 표가 아니다

검토자는 오류가 있을 수 있다는 전제로 결과를 비교한다. 검토에서 오류를 발견하면 재작업 경로를 사용하고, 발견하지 못했다면 검토 기준과 자료의 부족도 돌아본다. 구현자의 실수 가능성과 팀의 검토 체계 문제는 함께 존재할 수 있다. 작업표만으로 모든 도덕적·법적 책임이 결정되지는 않는다.

독립 검토가 필요한 중요한 산출물은 수행자와 검토자를 다르게 둘 수 있다. 혼자 작업한다면 이를 독립 검토라고 부르지 말고 자기 검토로 표시한다. 사람이 빠졌을 때는 대체자를 기록하고 정보에 접근할 수 있게 인수인계한다. 명단만 바꾸고 이전 결정을 전달하지 않으면 같은 역할이어도 같은 일을 할 수 없다.

중간 과정을 따라가는 예제

가상 퀴즈 앱의 문제 표는 서가 작성하고 준이 검토하며 민이 정해진 형식으로 구현한다. 정답 내용 승인자는 서다. 문제 3의 정답 번호가 5로 전달되었다. 각 역할의 다음 행동을 추적하라.

  1. 민은 1–4 형식 조건 위반을 발견하고 승인된 값처럼 사용하지 않는다.

  2. 서에게 문제 ID와 위반 조건을 기록하여 수정 요청한다.

  3. 서는 정답 내용을 확인해 번호 2로 수정하고 변경 이유를 적는다.

  4. 준은 수정한 표의 질문·선택지·번호 2가 일치하는지 검토한다. 서의 승인 뒤 민이 새 표를 구현한다.

수행·검토·내용 결정·구현을 구분했다. “개발 담당이니 알아서 고쳐라”로 정답의 전문 결정을 넘기지 않는다.

공동 목표와 완료 기준

“거의 다 됐다”를 세 사람이 같은 뜻으로 이해할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 목표는 이루려는 결과를 설명하는 문장이다. 작업 목록은 목표를 위해 할 행동이며 둘은 다르다.

  • 조건은 참인지 확인할 수 있는 약속이다. P∧Q는 P와 Q가 모두 참이어야 한다는 뜻이다.

  • 증거는 조건을 확인하는 자료다. 화면 캡처는 보이는 상태의 증거지만 모든 입력이 옳다는 증명은 아니다.

학습 목표

  • 사용자 목표·산출물·완료 조건·확인 증거를 연결한다.

  • 범위 변경과 일부 조건 통과를 전체 완료와 구분한다.

공동 목표는 무엇을 만들지보다 누구의 문제를 풀지 말한다

가상 목표를 “학습자가 다섯 문제를 풀고 틀린 문제의 이유를 확인한다”로 정한다. 화면 세 개 제작은 작업량이고 이 목표의 사용 결과는 아니다. 목표에는 대상·행동·사용 상황을 적어 팀원들이 다른 성공을 상상하지 않도록 한다. 시험 성적 향상은 이 예에서 측정하지 않으므로 앱 기능 완료만으로 성적 효과가 검증됐다고 말하지 않는다.

범위도 적는다. 이 첫 버전은 고정 다섯 문제, 오프라인, 개인 연습만 다룬다. 계정·반별 순위·실제 학습자 성과 측정은 포함하지 않는다. 범위 밖의 제안을 무조건 나쁜 아이디어로 판단하는 것이 아니라 현재 목표와 기한에서 별도 결정한다.

완료 기준은 판정할 수 있는 조건과 근거다

완료 조건 C1은 다섯 문제를 각각 한 번 제출 가능, C2는 고정 정답표로 채점 정확, C3는 틀린 답에 설명 표시, C4는 새로 시작 시 점수 초기화라고 합의하자. 전체 완료 D=C1∧C2∧C3∧C4다. C1–C3만 확인했다면 확인된 범위의 완료이지 D는 확인되지 않았다. 알 수 없음은 거짓으로 확정할 수 없지만 승인에 필요한 증거가 없다는 뜻이다.

각 조건 옆에 누가 어떤 입력으로 확인할지 적는다. 고정 정답표와 실제 반환값의 비교는 채점 근거이고 “보기 좋다”는 그 조건의 근거가 아니다. 실행 전 예상값, 실제 실행 기록, 독립 검토, 학습자 관찰은 서로 다른 근거다. 여기의 활동 표는 가상 확인 결과이므로 실제 실행 기록으로 사용할 수 없다.

기준 변경은 버전과 재확인 범위를 남긴다

기준을 작업 뒤 임의로 낮추면 “완료”의 뜻이 바뀐다. 설명 표시를 제외하려면 목표에 미치는 영향·동의한 결정자·새 버전의 조건을 기록한다. 새로운 C3를 충족했다고 옛 C3도 충족한 것은 아니다. 반대로 목표에 필요 없는 장식 요구가 끝없이 추가되면 완료할 수 없으므로 추가 기준의 근거도 검토한다.

조건이 모두 통과해도 기준 밖의 오류가 없다는 보장은 아니다. 입력 범위나 운영 조건을 바꾸면 다시 확인해야 한다. 좁은 기능 완료를 신뢰성·보안·교육 효과 전체로 확대하지 않는 것이 팀의 정확한 상태 공유다.

중간 과정을 따라가는 예제

가상 확인 표에서 C1,C2,C3는 참, C4는 새 시작 후 이전 점수 3이 남아 거짓이다. D=C1∧C2∧C3∧C4를 판정하고 다음 작업을 정하라.

  1. 확인 표의 네 조건과 증거를 읽는다.

  2. C4의 요구는 초기 점수 0이고 관측값은 3이므로 불일치다.

  3. 참∧참∧참∧거짓=거짓이므로 전체 완료라고 승인하지 않는다.

  4. 점수 초기화를 수정한 뒤 C4를 재확인하고 관련 채점/시작 흐름도 변경 영향에 맞게 확인한다.

확인된 세 조건과 미충족 한 조건을 함께 보고한다. 가상 값은 실제 앱 시험 결과가 아니다.

소단원 1.3

연락·응답·기록 규칙

채팅에서 “네”라고 답한 것은 검토를 끝냈다는 뜻일까?

준비 개념과 학습 목표

준비 개념

  • 응답은 요청을 받았거나 다음 행동을 알려 주는 메시지다. 작업 완료와 같은 사건이 아니다.

  • 시간대는 시각의 기준이다. 14시라는 숫자만으로 상대의 동일 순간을 지정할 수 없으므로 날짜와 기준을 함께 적는다.

  • 결정 기록은 선택·이유·담당·시점·미결 사항을 나중에도 확인할 수 있게 남기는 자료다.

학습 목표

  • 수신 확인·예정·완료·승인을 구분한다.

  • 연락 기한·기록 위치·응답 부재 때 경로를 자기완결 규칙으로 작성한다.

메시지의 상태를 이름 붙여 혼동을 줄인다

가상 팀은 요청에 작업 ID, 원하는 행동, 필요한 자료, 기한을 넣는다. 받는 사람은 “받음”, “검토 예정”, “수정 필요”, “검토 완료”를 구분해 쓴다. 읽음 표시나 이모지만으로 내용 검토와 승인까지 추론하지 않는다. 완료 응답에는 확인한 버전과 범위가 있어야 다른 파일에 대한 승인으로 오해하지 않는다.

모든 연락을 즉시 처리하라는 규칙은 집중 시간을 끊고 지속하기 어렵다. 팀의 실제 가능 시간을 고려해 응답 가능한 창을 합의한다. 이 예에서는 평일 13–17시 KST에 요청을 확인하고 그 창의 누적 2시간 안에 수신/예정을 알린다. 이는 자체 사례의 규칙이고 법률이나 실제 회사 정책이 아니다.

응답 지연과 완료 지연은 다른 경로로 다룬다

화요일 14시 요청이면 같은 날 16시까지 첫 응답을 기대한다. 16시 요청이면 화요일 17시까지 1시간, 수요일 13–14시의 1시간을 더해 수요일 14시가 기한이다. 응답 창 밖의 시간은 세지 않는다고 명시했기 때문이다. 첫 응답은 목요일 완료 예정처럼 별도 완료 시각을 알릴 수 있다. 응답 기한을 충족했다고 실제 검토가 끝났다고 기록하지 않는다.

기한이 지나도 응답이 없으면 정해진 대체 연락 창구에 작업 ID와 미응답 사실을 전달한다. 상대가 게으르거나 작업을 거부했다고 확정하지 않는다. 휴식·장애·메시지 누락 등 이유는 아직 모른다. 긴급 안전 문제가 있는 업무는 별도 경로가 필요하나 이 학습 앱의 일반 요청 규칙을 그대로 응급 대응에 쓰지 않는다.

대화 뒤에는 하나의 확인 가능한 결정 기록을 남긴다

채팅과 회의가 여러 곳에서 일어나도 최종 기준은 팀이 접근할 수 있는 결정 문서에 기록한다. 항목은 ID, 결정 내용, 근거, 반론/미결, 담당, 기한, 적용 버전이다. 파일 이름만 적으면 이후 수정된 내용을 구별하기 어려우므로 문서 버전이나 변경 ID도 연결한다. 접근 권한과 필요한 개인정보만 포함하는 기록 범위를 함께 정한다.

“문제 3을 삭제하자”는 제안과 “버전 v2에서 문제 3 삭제를 승인했다”는 결정을 구별한다. 회의 후 기록을 참가자에게 확인받고 수정된 결정은 옛 기록을 몰래 지우기보다 대체한 이유를 남긴다. 문서 작성 자체가 합의를 만들어 주는 것은 아니며 권한 있는 사람이 결정했는지와 이견 처리 경로도 확인한다.

중간 과정을 따라가는 예제

가상 규칙은 평일 13–17시 KST의 누적 2시간 내 첫 응답이다. 화요일 16시 요청에 수요일 13시 30분 “받음, 목요일 15시 검토 예정”이 왔다. 응답 기한과 완료 상태를 구하라.

  1. 화요일 16–17시가 응답 창 1시간이다.

  2. 남은 1시간은 수요일 13–14시이므로 첫 응답 기한은 수요일 14시다.

  3. 수요일 13시 30분은 창 내 누적 1.5시간이므로 첫 응답 기한을 지켰다.

  4. 목요일 15시는 검토 예정이며 현재 검토 완료나 승인의 증거는 없다.

첫 응답은 기한 내, 검토는 예정 상태다. 이 시간들은 가상이며 메시지를 실제 발송하거나 관찰하지 않았다.

오해와 반례

메시지가 많고 모두 읽었으면 결정 기록은 필요 없다.

서로 다른 대화에서 두 기준을 승인했다고 생각할 수 있다. 메시지 수가 아니라 적용 버전·결정 권한·근거가 재확인 가능한지 살핀다.
