소단원 8.1

검토 질문과 체크 기준

검사 네 칸에 체크하면 모든 버그가 사라진 것일까?

준비 개념과 학습 목표

준비 개념

  • 조건문

  • 요구사항

  • 예상과 관측

학습 목표

  • 요구에 연결된 검토 질문을 만든다.

  • PASS/FAIL/미수행을 구별한다.

검토 항목이 많아져도 빠진 요구는 그대로 남을까요?

앞 본문은 PASS, FAIL, 미수행을 근거 방법과 함께 기록합니다. 새 자체 계약은 정수 x가 0 이상 6 이하이면 ACCEPT를 반환하고 accepted를 1 늘리며, 그 밖에는 ERROR를 반환하고 accepted를 보존합니다. accepted의 초기값은 0입니다. 반환과 상태가 모두 계약의 일부입니다.

요구 R1은 허용 범위의 반환, R2는 범위 밖 반환, R3은 성공 때의 카운터 증가, R4는 실패 때의 카운터 보존, R5는 실제 UI 관측입니다. 검토 카드 C1부터 C4까지는 입력 2의 반환 ACCEPT만 각각 종이로 확인합니다. 같은 요구를 반복한 카드 수와 서로 다른 요구에 연결된 수를 구별합니다.

별도 오류 모형 K는 반환 범위를 올바르게 판정하지만 모든 호출에서 accepted를 1 늘립니다. 입력 −1의 반환 ERROR만 보면 오류를 놓칩니다. 실제 실행은 하지 않았으며 아래 PASS는 고정된 종이 사례의 판정입니다.

무엇을 만족해야 하는지

검토는 변경된 코드나 문서가 요구를 만족하는지 근거로 확인하는 활동이다. 먼저 누가 어떤 입력에서 어떤 결과를 기대하는지 적는다. 문서의 약속과 코드 분기, 변경된 사용법도 함께 봐야 한다.

체크 기준은 질문을 작게 만든다. 정상 입력/경계 입력/오류 처리/문서 일치 같은 관점을 변경의 성격에 맞게 고른다. 모든 변경에 같은 긴 목록을 무조건 적용하기보다 영향받는 조건을 분명히 한다.

읽기와 실행의 역할

읽어서 발견한 분기 오류는 실행하지 않아도 설명할 수 있다. 반대로 실제 UI 모양이나 장비 동작을 보지 않았으면 읽기만으로 관측 완료라고 쓰지 않는다. 동시성 문제는 단순 실행 성공만으로 부재를 증명하기 어려워 사건 순서를 생각해야 한다.

테스트도 그 자체를 검토한다. 잘못된 구현에서도 통과하는 비교식이면 녹색 표시는 유용한 증거가 아니다. 체크 결과의 근거가 읽기·종이 추적·실제 실행 중 무엇인지 함께 적어야 다른 검토자가 의미를 이해한다.

상태를 분리한 종이 표

이 활동의 PASS는 명시한 종이 사례를 만족한다는 뜻이며 실제 제품 전체의 검증 완료가 아니다. FAIL은 기준에 어긋나는 구체 사례가 있다는 뜻이고 미수행은 아직 확인하지 않은 상태다. 미수행을 실패나 성공으로 바꾸어 세지 않는다.

의견을 필수 요구·개선 제안·질문으로 구별하면 수정 우선순위가 선명하다. 문서가 0 허용이라고 쓰는데 코드가 0 거절이면 이는 취향이 아니라 약속의 불일치다. 코드 검토와 설명 검토를 같은 변경 묶음에 연결한다.

중간 과정을 따라가는 예제

자체 약속: 정수 x≥0이면 x+1, 음수면 오류다. 실제 분기는 x>0이면 x+1, 그 밖은 오류다. 기준 A는 x=2→3, B는 x=0→1, C는 x=−1→오류, D는 실제 UI 관찰이다. 코드 읽기와 종이 추적만 수행했다.

  1. A는 2>0이므로 3으로 PASS다.

  2. B는 0>0이 거짓이라 오류로 가므로 기대한 1과 달라 FAIL이다.

  3. C는 −1>0이 거짓이라 오류로 PASS다. D는 실제 관찰을 하지 않았으므로 미수행이다.

PASS 2 / FAIL 1 / 미수행 1이다. 이 네 기준에서 실제 실행 완료는 0이며 B의 경계 반례를 수정 요청으로 적는다.

조건을 바꾸어 비교하기

네 카드와 한 요구를 따로 셉니다

C1부터 C4까지 가상으로 모두 PASS입니다. 카드 통과율과 요구 연결 비율을 계산하세요.

  1. 카드 통과율은 4/4 = 100%입니다.

  2. 서로 다른 요구는 R1 하나이므로 요구 연결 비율은 1/5 = 20%입니다.

  3. R3과 R4의 카운터 동작 및 R5의 실제 UI는 이 표로 확인되지 않습니다.

카드 통과율 100%와 요구 연결 비율 20%를 함께 표시합니다.

비교할 점

이는 코드 coverage나 제품 전체의 실제 통과율이 아닙니다.

올바른 반환이 상태 오류를 가립니다

오류 모형 K에서 초기 accepted = 0에 입력 −1을 한 번 줍니다. 독립 기대 상태와 종이 결과를 비교하세요.

  1. 계약의 기대는 반환 ERROR와 accepted = 0입니다.

  2. K의 반환은 ERROR지만 accepted는 1이 됩니다.

  3. 반환 검사만 PASS이고 실패 상태 보존 R4는 FAIL입니다.

실패 카운터가 0에서 1로 바뀌는 반례를 별도 필수 검토 항목으로 남깁니다.

비교할 점

K에서 나온 1을 기대값으로 복사하면 같은 오류를 검출하지 못합니다.

연습 1 · 값과 상태 예측

네 기존 카드에 C5 하나를 추가해 입력 −1의 반환을 종이로 확인합니다. 다섯 카드 모두 PASS라면 두 비율은?

힌트 1

서로 다른 연결 요구는 R1과 R2입니다.

힌트 2

전체 요구는 다섯 개입니다.

풀이와 답 확인

  1. 카드 통과율은 5/5 = 100%입니다.

  2. 요구 연결 비율은 2/5 = 40%입니다.

카드 통과율은 100%, 요구 연결 비율은 40%입니다.

다섯 카드이므로 다섯 요구를 모두 확인했다.

연습 2 · 오류 찾아 고치기

K의 반환 ERROR만 보고 실패 무부작용도 PASS라고 썼습니다. 초기 accepted = 0에서 입력 7을 줍니다.

힌트 1

7은 상한 6을 넘습니다.

힌트 2

반환과 변경 상태를 각각 비교합니다.

풀이와 답 확인

  1. 계약은 ERROR를 반환하고 accepted = 0을 유지해야 합니다.

  2. K는 ERROR를 반환하지만 accepted를 1로 바꿉니다.

  3. 반환 PASS와 상태 FAIL을 각각 남깁니다.

입력 7에서도 실패 카운터 증가가 요구 R4를 위반합니다.

흔한 오답에서 다시 생각하기

ERROR 반환은 모든 상태 보존을 증명한다.

반환값의 뜻과 실제 부작용은 다른 관찰입니다.

연습 3 · 직접 만들어 보기

올바른 모형에서 초기 accepted = 0에 입력 0, 6, 7을 순서대로 처리합니다. 반환과 카운터를 함께 비교하는 카드를 구성하세요.

힌트 1

힌트 2

사실이 맞아도 어느 버전의 사실인지 없으면 수정 대상을 찾을 수 있을까요?

자체 normalize 규칙은 정수 x가 0 이상 8 이하이면 그대로 반환하고 그 밖에는 ERROR를 반환합니다. revA의 분기는 x < 0 또는 x >= 8이면 ERROR입니다. 따라서 상한 8만 잘못 거절합니다. revB에서는 x > 8로 교정합니다. 이 사례는 종이 분기이며 실제 프로그램을 실행하지 않았습니다.

피드백에는 대상 함수와 revision, 입력, 기대와 관찰, 계약 위반의 영향을 함께 씁니다. “revA의 상한 검사에서 입력 8을 ERROR로 추적했으며 계약의 반환 8과 다릅니다. 입력 8의 허용과 9의 거절을 함께 확인해 주세요”는 필수 오류를 구체화합니다.

별도 이름 변경은 의미가 명확한 현재 코드의 선택 제안으로 정합니다. UI 표시를 아직 보지 않았다면 질문으로 남깁니다. 필수 오류 해결, 선택 응답, 관측 대기는 서로 다른 완료 기준입니다. 개인의 능력을 평가하는 문장을 추가하지 않습니다.

변경된 대상을 가리키기

피드백은 작성자의 성격 대신 읽은 코드·문서의 특정 부분을 다룬다. 어떤 조건에서 무엇이 일어나고 왜 약속과 어긋나는지 적으면 수정 가능한 문제가 된다. “늘 잘못한다” 같은 사람 평가는 입력과 결과를 재현할 수 없게 한다.

위치가 중요하다. 파일 이름과 함수·문단·해당 revision을 남기면 이후 줄번호가 바뀌어도 대상을 찾기 쉽다. 실제로 실행하지 않은 반례라면 종이 추론이라는 사실을 함께 밝힌다.

이유와 심각도를 함께

필수 수정은 합의된 요구 위반이나 오류에 연결한다. 선택 제안은 현재 요구를 이미 만족하지만 더 읽기 쉽게 하는 대안이다. 질문은 요구나 상태를 아직 모르는 경우다. 세 종류를 섞으면 모든 사소한 취향이 배포 차단으로 보일 수 있다.

해결 방법을 무조건 대신 작성할 필요는 없다. 실패 조건과 필요한 결과를 설명하고 작성자가 방법을 고르게 하거나, 작은 예제에서 명확한 수정 방향을 제안한다. 제안도 더 좋은 대안이 있는지 논의할 수 있다.

다음 독자까지 이해시키기

설명이 검토 댓글 안에만 있으면 이후 코드 독자는 이유를 못 볼 수 있다. 복잡한 이름·분기를 명료화하거나 필요한 이유를 문서에 남겨 검토자의 이해를 공유한다. 모든 줄을 설명하는 주석을 늘리는 것과는 다르다.

필수 댓글을 전부 답해도 현재 변경 전체를 검토했다고 할 수 있을까요?

새 자체 enqueue 계약은 용량 2의 목록 q에 값을 넣는 것입니다. 길이가 2보다 작으면 뒤에 추가하고 OK, 꽉 차면 FULL이며 q를 보존합니다. rev1은 꽉 찬 경우에도 앞 값을 지우고 새 값을 넣으면서 FULL을 반환합니다. 필수 댓글 A는 이 실패 상태 손상입니다.

rev2는 꽉 찬 실패에서 q를 보존합니다. rev3은 빈 목록에 첫 값을 추가할 때 같은 값을 두 번 넣는 새 오류가 들어왔습니다. rev2의 두 경로 확인 기록도 rev3의 빈 분기 통과 근거가 아닙니다. 수정의 영향 범위와 현재 대상의 새 변경을 함께 읽어야 합니다.

변경 설명은 문제, 최종 행동, 근거 방법, 미확인 범위를 연결합니다. 실제 저장소 댓글이나 프로그램 실행은 수행하지 않습니다. 이전 실패/수정 기록을 보존하되 현행 설명의 본문을 옛 구현 이야기로 남겨두지 않습니다.

변경 묶음의 맥락

CL은 함께 검토하는 변경 묶음이다. 설명은 무엇이 왜 바뀌는지 보여주어 작성자를 모르는 미래 독자도 이해하게 한다. “수정” 한 단어만 적으면 어떤 입력과 동작이 달라졌는지 찾기 어렵다.

처음 문장은 구체적인 결과를 요약하고 본문은 문제 조건·해결 방식·필요한 한계를 덧붙인다. 작은 변경에도 경계 사례 하나와 검증 방법이 있으면 내용을 판단하기 쉽다. 코드가 하는 일과 그 선택의 이유는 별도 정보다.

댓글에 근거로 응답하기

의견을 이해 못 하면 조건과 기대를 질문한다. 동의하면 변경 위치와 확인 결과를 적고, 다른 대안을 고르면 장단점과 요구 충족 근거를 설명한다. 의견의 개수만 세기보다 핵심 필수 문제가 해결되었는지 확인한다.

“완료” 표시는 실제로 마친 범위에 맞춘다. 코드만 읽었는데 테스트 통과라고 쓰지 않는다. 아직 관측하지 않은 UI나 기능은 미수행으로 남기고 그 관측을 담당할 사람과 단계를 연결한다.

최종 코드에 맞게 설명 갱신

검토 중 접근 방식이 달라졌으면 최종 변경 설명을 고친다. 옛 구현의 설명이 남으면 미래 독자가 잘못된 전제에서 유지보수한다. 이전의 논쟁 전체를 복사할 필요는 없지만 남은 한계와 판단 근거는 알 수 있게 한다.

중간 과정을 따라가는 예제

rev1은 x>0만 허용하지만 약속은 x≥0이다. 필수 댓글 A는 0 경계, 선택 B는 이름, 질문 C는 실제 UI에 대한 의견이다. rev2는 x≥0으로 수정하고 이름을 유지한 이유를 설명하며 UI는 미관측이다. 변경 설명과 응답표를 작성한다.

  1. 설명 첫 줄에 “0 입력도 허용하도록 경계 검사를 수정한다.”라고 쓴다. 양수/0/음수의 기대도 첨부한다.

  2. A는 rev2의 위치와 종이 추적에서의 0 허용으로 해결하고, B는 선택 제안이며 현 이름의 뜻을 유지하는 근거를 응답한다.

  3. C는 실제 관찰 미수행으로 남긴다. “UI 테스트 통과”로 바꾸지 않는다.

    실제 전체 0–95행을 읽어 요구 기능·동시성 읽기·테스트 자체 검토·문서와 모든 줄/문맥의 범위를 확인했다. 새 카운터/목록과 비율은 자체 모형이다.

  • Google Engineering Practices — Review comments

    실제 전체 0–44행에서 대상 코드 중심·이유·방향 제안·심각도·코드 자체 명료화와 미래 독자 설명을 읽었다. 실제 피드백을 발송하지 않았다.

  • Google Engineering Practices — CL descriptions

    실제 전체 0–119행을 읽었다. 무엇/왜/맥락, 첫 줄과 본문, 검토 중 변경 뒤 최종 설명 갱신을 대조했다.

  • Google Engineering Practices — Handling comments

    실제 전체 0–38행을 읽었다. 불명확한 요청 확인·코드 자체 명료화·근거와 장단점의 협업을 확인했다. 회사 내부의 연락 권고를 실제 연락 수행으로 옮기지 않았다.

R1만 반복한 네 카드의 통과율은 4/4이고 요구 연결 비율은 1/5다. R2 카드를 추가하면 통과율은 5/5, 요구 연결 비율은 2/5다. 오류 K는 입력 −1과 7의 별도 초기 상태에서 ERROR를 반환하지만 accepted를 1로 바꾸므로 기대값 0을 위반한다. 올바른 모형에서 순차 입력 0 뒤 반환은 ACCEPT와 카운터 1, 입력 6 뒤는 ACCEPT와 카운터 2, 입력 7 뒤는 ERROR와 카운터 2다. R5를 보고에서 제외하면 연결 비율은 1/4지만 원래 요구 기준은 1/5다. revA는 입력 −1과 8과 9에서 ERROR, 입력 0에서 0을 반환한다. revB는 입력 −1과 9에서 ERROR, 입력 0에서 0, 입력 8에서 8을 반환한다. revB의 입력 7은 7을 반환한다. 꽉 찬 목록에서 rev1은 [B,C]로 바꾸지만 rev2는 [A,B]를 보존한다. rev3의 빈 목록 결과는 기대 [D]와 다른 [D,D]다. 올바른 rev2에서 A 요청과 B 요청은 각각 OK, C 요청은 FULL이며 최종 목록은 [A,B]다. rev4 가상 보고는 계획 네 기준 중 종이 세 기준을 모두 PASS로 확인했으므로 수행 범위 75%와 수행 통과율 100%다. UI는 미수행이다. 전이의 요구 연결 비율은 2/6이고 목록 최종 상태는 [A,B,C]다. 별도 가상 검토 표의 수행 범위는 3/4, 종이 통과율은 2/3다. 모든 값은 명시 계약에서 손으로 유도했으며 실제 실행이나 팀 결과로 제시하지 않는다.
