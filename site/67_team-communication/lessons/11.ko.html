소단원 11.1

설치·사용·문제 해결

처음 보는 도구의 안내만 읽고 준비부터 오류 복구까지 따라갈 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 파일과 저장 위치

  • 화면의 입력과 결과

  • 조건 분기

학습 목표

  • 준비 조건과 단계별 결과를 기록한다.

  • 오류 증상과 확인·복구를 연결한다.

  • 실제 확인된 안내와 가상 절차를 구별한다.

시작 전에 필요한 조건을 밝힌다

설치 안내는 제품과 문서 버전, 지원 환경, 필요한 권한과 준비 파일을 먼저 알려 준다. 이미 설치되어 있다는 가정을 숨기면 첫 단계부터 막힐 수 있다. 이 절의 도구는 종이로 설계한 가상 점수 요약 앱이며 실제 다운로드 링크나 설치 파일은 없다.

가상 앱 v1은 브라우저에서 열고 UTF-8 CSV를 선택한다는 계약을 둔다. UTF-8은 글자를 바이트로 표현하는 문자 인코딩 이름이고 CSV는 열을 쉼표로 구분하는 텍스트 형식이다. 필요한 개념 설명을 준비 목록과 연결한다.

행동과 확인 결과를 함께 쓴다

사용 절차는 준비→입력 선택→실행→결과 확인 순으로 적는다. 버튼의 정확한 이름과 어느 화면에서 행동하는지 쓰며 그 다음 어떤 결과가 나타나야 하는지 밝힌다. 예제 파일의 값과 기대 결과는 따로 제공한다.

가상 계약은 첫 행 score 헤더 다음에 정수 점수를 한 줄씩 받는다. 빈 데이터와 정수가 아닌 값은 계산하지 않고 오류로 표시한다. 문서에 넣은 기대 출력은 이 계약의 손 계산 결과이며 실제 앱을 실행해서 본 화면은 아니다.

복구를 검증 가능한 행동으로 쓴다

문제 해결은 오류 문구와 조건을 연결한다. score 열 없음이라면 헤더 철자와 파일 버전을 확인하고, 정수 아님이라면 안내된 데이터 행의 값을 확인한다. 이유 없이 재설치만 반복하도록 쓰지 않는다.

입력 파일을 수정할 때 원본을 보존하고 복사본을 사용한다. 복구 후 같은 예제를 다시 확인할 계획을 둔다. 계속 실패하면 버전·환경·재현 단계·기대/실제 결과를 보고하되 비밀번호나 개인 점수를 공개 보고서에 넣지 않는다.

중간 과정을 따라가는 예제

가상 입력은 헤더 score 뒤 데이터8,10,12다. 사용 안내에 넣을 기대 합계·평균과 확인 단계를 적어라.

  1. 헤더score와 데이터3개인지 확인한다.

  2. 합8+10+12=30, 평균30/3=10을 계산한다.

  3. 입력 선택→실행→결과에서 건수3/합30/평균10을 확인하도록 안내한다.

예상 결과는3/30/10이다. 이는 가상 계약의 손 계산이며 실제 화면 검증은 미수행이다.

종이와 본문으로 직접 해보기

10을 문자 ten으로 바꾸었을 때와 데이터 행을 모두 없앴을 때 문제 해결 항목을 적어라.

힌트 보기

오류 위치는 헤더를 제외한 데이터 행 번호로 정한다.

풀이 보기

ten은 데이터2행 정수 오류로 계산하지 않고 복사본의2행을10으로 고친 뒤 재확인한다. 데이터0개는 빈 입력 오류이며 평균0이라고 표시하지 않는다. 원본 파일은 남긴다.

오해와 반례

설치가 끝났으면 사용자 안내는 완성이다.

목표 작업과 결과 확인, 실패 시 복구가 남는다. 가상 앱의 설치 가능성을 확인하지 않았으므로 이 자료를 실제 설치 검증 완료라고 부를 수 없다.

실제 앱과 장치는 실행하지 않았다.

한 단계 더

가상 v2가 헤더를 score에서 points로 바꾸면 준비 파일·정상 절차·열 없음 오류·예제를 함께 갱신해야 한다. v1과 v2 안내를 섞으면 같은 파일이 다른 의미를 갖는다는 것을 표로 정리하라.

소단원 11.2

독자 수준과 접근성

전공자에게 익숙한 짧은 표현을 처음 온 학생도 이해할까?

준비 개념과 학습 목표

준비 개념

  • 문서 제목과 링크

  • 대상 독자

  • 키보드와 화면 읽기

학습 목표

  • 독자의 현재 지식을 구체적으로 가정한다.

  • 제목·링크·이미지의 의미를 글로 전달한다.

  • 내용 검토와 실제 접근성 검증을 분리한다.

나이와 직함만으로 지식을 판단하지 않는다

독자가 학교에 다니거나 개발자라는 이유만으로 모든 기술을 안다고 가정하지 않는다. 문서의 작업에 필요한 지식과 현재 아는 내용을 비교한다. 자체 교육 계획은 파일 선택은 알고 CSV·UTF-8·헤더는 모르는 독자를 가정한다. 이는 설계 가정이며 실제 조사 결과가 아니다.

처음 나온 용어에 뜻과 작은 예를 붙이고 준비 학습 링크를 제공한다. 쉬운 단어를 써도 기술 조건을 지우지 않는다. 다른 언어 독자를 위해 지역적 농담이나 관용구보다 뜻이 직접 드러나는 문장을 쓴다.

찾고 해석할 수 있는 구조를 만든다

설치 준비·첫 사용·오류 해결처럼 구역의 역할을 드러내는 제목을 사용한다. 큰 글자 모양만으로 제목을 흉내 내는 대신 실제 heading 구조를 사용해야 화면 읽기 도구도 탐색 의미를 얻는다. 문서 자체의 제목도 다른 페이지와 구별한다.

여기를 누르세요 대신 CSV 예제 파일 받기처럼 링크의 목적을 드러낸다. 기능을 설명하는 그림은 그 정보가 텍스트에도 전달되게 하고 장식 그림은 불필요한 설명을 늘리지 않는다. 그림의 대체텍스트는 파일 이름을 읽어 주는 것으로 충분하지 않을 수 있다.

색과 위치만으로 안내하지 않는다

오른쪽 빨간 버튼만 누르라는 문장은 화면 크기·언어·색 구분 방식이 달라지면 모호하다. 버튼 이름 실행을 쓰고 입력 위치와 결과를 함께 설명한다. 실제 제품이 키보드로 동작하는지는 문서의 표현만으로 확정할 수 없다.

자체 점검표는 제목 의미, 링크 의미, 입력/오류 설명, 그림 대체 정보 네 항목이다. 이 네 항목의 내용 점검을 통과해도 전체 접근성 표준 준수나 실제 보조기술 사용성을 증명하지 않는다. 렌더·키보드·화면 읽기 시험과 학습자 실험은 별도 수행이 필요하다.

중간 과정을 따라가는 예제

독자가 파일 선택은 알고 CSV/UTF-8/헤더는 모른다고 가정한다. 필요한 네 지식 항목 중 설명할 항목 수와, 여기를 눌러요 링크의 개선 문장을 제시하라.

  1. 작업에 필요한 항목은파일 선택/CSV/UTF-8/헤더 네 개다.

  2. 가정한 기존 항목은파일 선택 하나이므로 설명할 차이는3개다.

  3. 링크를 CSV 예제 파일 받기로 바꾸고 형식·내용을 옆에 설명한다.

설명할 항목은3개다. 실제 독자의 지식이 다르면 준비 설명의 범위도 다시 정한다.

종이와 본문으로 직접 해보기

자체 네 항목 점검에서 제목·링크·오류 안내는 확인했고 그림 대체 정보는 미확인이다. 항목 확인률과 다음 조치를 적어라.

힌트 보기

점검 항목 수는 보조기술 시험 수가 아니다.

풀이 보기

3/4=75%다. 그림이 전달하는 의미를 먼저 정하고 대체 정보가 이를 전달하는지 확인한다. 확인 후4/4라도 WCAG 전체 통과나 실제 도구 시험 완료로 표시하지 않는다.

오해와 반례

폰트가 크고 그림이 있으면 누구나 읽을 수 있다.

의미적 구조, 링크 목적, 대체 정보, 입력 설명과 실제 조작 조건도 필요하다. 시각적 모양만으로 다른 감각이나 도구의 사용을 보장할 수 없다.

자기점검

큰 글자만 쓰면 의미적 heading이 되는가?

답과 이유 보기

아니다.

구조 태그와 의미가 별도로 전달되어야 한다.

CSV를 안다고 가정해도 모든 독자가 아는가?

답과 이유 보기

아니다. 설계 가정이다.

실제 독자 지식은 확인과 피드백으로 갱신해야 한다.

자체 항목4/4이면 화면 읽기 실험도 통과했는가?

답과 이유 보기

아니다.

글 점검과 실제 렌더·도구 수행은 다른 검증이다.

한 단계 더

그림을 볼 수 없어도 헤더score와8/10/12 입력 예를 이해할 수 있게 같은 정보를 텍스트 표나 목록으로 작성하라. 장식용 그림과 작업에 필요한 정보 그림의 역할을 구별해 불필요한 대체 설명을 피한다.

  • W3C WAI — Writing for Web Accessibility

  • Google — Procedures

소단원 11.3

문서 유지 책임

제품 버튼이 바뀐 다음 누가 안내와 예제까지 다시 확인할까?

준비 개념과 학습 목표

준비 개념

  • 버전과 변경 기록

  • 역할과 검토

  • 집합

학습 목표

  • 문서 담당자와 검토·배포 책임을 정한다.

  • 변경된 기능이 영향을 주는 안내를 찾는다.

  • 검토 일자와 실제 검증 범위를 기록한다.

역할과 변경 신호를 정한다

문서 소유자는 제안과 오류를 받아 상태를 관리하는 담당이다. 제품의 기술 사실을 확인하는 검토자, 초보자의 표현을 살피는 검토자, 승인된 안내를 반영하는 담당의 책임도 정한다. 담당자가 모든 기술을 혼자 증명한다는 뜻은 아니다.

자체 계획은 버튼 이름 변경, 입력 형식 변경, 지원 환경 변경을 문서 검토 신호로 삼는다. 문서만 달력대로 보다가 제품 변경을 놓치지 않도록 기능 변경과 연결한다. 담당이 바뀌면 열린 항목과 근거를 넘긴다.

영향 집합에서 점검 대상을 찾는다

자체 페이지 D1 준비/D2 첫 사용/D3 오류/D4 참고를 둔다. 버튼 변경은{D2}, 헤더 변경은{D1,D2,D3}에 영향을 준다고 기록한다. 두 변경이 함께 있으면 중복 없이 합집합으로 범위를 정한다.

영향 표는 조사 출발점이며 표시된 페이지 밖에도 연결이나 검색 요약이 영향받을 수 있다. 예제 파일, 이미지, 기대 결과와 버전 표시까지 확인한다. 검토 범위를 좁혔다는 이유로 다른 관련 증거를 보지 않는 것은 위험하다.

정보를 받아 실제 확인으로 닫는다

보고 양식에 제품/문서 버전, 발생 위치, 재현 단계, 기대/실제 결과를 요청하면 담당자가 문제를 좁히기 쉽다. 구조화 양식이 채워졌다고 사실 확인이 끝난 것은 아니다. 개인정보와 비밀 키를 포함하지 않도록 안내한다.

자체 상태는 접수→재현 계획→수정→독립 확인→반영 확인으로 정한다. 마지막 검토 날짜만 새로 바꾸지 말고 어떤 버전과 절차를 실제 확인했는지 적는다. 이 자료는 가상 관리 계획이며 실제 앱 재현·외부 보고·배포는 수행하지 않았다.

중간 과정을 따라가는 예제

버튼 변경 영향{D2}, 헤더 변경 영향{D1,D2,D3}가 동시에 생겼다. 영향 범위와 D1/D2만 검토한 상태의 확인률을 계산하라.

  1. 합집합은{D1,D2,D3}으로3페이지다. D2를 두 번 세지 않는다.

  2. 확인된 것은D1/D2 두 페이지라2/3≈66.7%다.

  3. D3 오류 안내와 관련 예제의 헤더가 남아 있다. D4가 영향 없음이라는 가정도 실제로 검토해야 한다.

자체 표시 범위3개 중2개 확인이다. 검토 날짜를 모두 갱신해3개 확인으로 만들면 안 된다.
