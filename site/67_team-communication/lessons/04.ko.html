소단원 4.1

구조도와 데이터 흐름

상자 네 개를 그리면 프로그램이 어떻게 움직이는지까지 알 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 구조는 누가 어떤 책임을 맡는지, 흐름은 특정 상황에서 어떤 정보가 오가는지 설명한다.

  • 화살표가 의미하는 것이 호출·데이터·의존성 중 무엇인지 범례를 정해야 한다.

  • 아래 서버와 데이터베이스는 가상 서비스 구성이다. 실제 배포·접속·시간 측정은 하지 않았다.

학습 목표

  • 독자와 질문에 맞는 구조도의 범위를 정한다.

  • 성공과 실패 경로의 메시지·방향·책임을 설명한다.

  • 구조 그림과 실행 증거를 구분한다.

접수 응답을 받았다는 사실만으로 저장 완료라고 설명해도 될까요?

앞 본문의 동기 저장 흐름과 다른 자체 비동기 흐름을 만듭니다. 브라우저는 입력을 API에 보내고, API는 검증을 마친 뒤 큐에 작업을 넣습니다. 큐 접수 확인이 오면 API는 브라우저에 접수됨을 응답합니다. Worker는 큐의 작업을 나중에 받아 DB에 저장하고, 저장 완료 확인 뒤 별도 상태 조회에 완료를 공개합니다. 접수 응답과 저장 완료 응답은 의미와 사건 순서가 다릅니다.

모형은 시각 0 ms의 요청 한 건을 대상으로 합니다. API 검증은 3 ms에 끝나고 큐 접수는 5 ms, 브라우저의 접수 응답 수신은 6 ms, Worker 시작은 8 ms, DB 저장 완료 확인은 11 ms, 상태 조회의 완료 관측은 12 ms입니다. 이 값은 가상 사건 시각이며 실제 서버 실행이나 장치 저장의 내구성을 측정한 값이 아닙니다. 실패와 완료 통지 유실은 별도 경우로 설명합니다.

구조도는 책임의 지도를 만든다

학습 기록 서비스에서 사용자는 브라우저로 단원 완료를 요청하고, API 서버는 요청의 형식과 권한을 확인하며, 데이터베이스는 기록을 보관한다고 정하자. API는 다른 프로그램이 약속한 방식으로 요청할 수 있는 인터페이스다. 각 상자에는 이름만 아니라 하는 일을 적어야 처음 보는 사람이 저장 담당을 찾을 수 있다.

사용자와 외부 서비스를 보는 전체 그림, 실행되는 프로그램과 저장소를 보는 그림, 한 프로그램 내부의 구성 요소를 보는 그림은 질문이 다르다. C4의 container는 실행되는 애플리케이션이나 데이터 저장소라는 수준이며 반드시 Docker 컨테이너라는 뜻은 아니다. 모든 수준을 빠짐없이 그리기보다 현재 설명할 질문과 독자에 필요한 수준을 선택한다.

흐름도는 한 상황의 순서를 설명한다

가상의 단원 완료 요청은 1 브라우저→API 완료 요청, 2 API→DB 유효한 기록 저장, 3 DB→API 저장 확인, 4 API→브라우저 완료 응답으로 적을 수 있다. 요청과 응답은 방향이 다르므로 화살표 이름을 따로 적는다. 번호는 이 시나리오의 순서를 설명하고 모든 요청이 언제나 같은 시간에 실행된다고 보장하지 않는다.

이 모형에서는 입력이 잘못되면 API가 오류를 응답하고 DB 저장 단계로 가지 않는다. 저장 실패도 완료 성공으로 바꾸어 응답하지 않는다. 구조도에 선이 있다고 그 선을 모든 상황에서 사용하는 것은 아니며 성공·검증 실패·저장 실패 흐름을 나누면 그 조건이 드러난다. 개인의 실제 학습 정보 대신 가상 번호를 써서 설명한다.

독자가 혼자 읽을 수 있는 그림

제목에 서비스 이름과 설명 범위를 적고 상자의 종류와 책임, 선의 방향과 메시지, 약어의 뜻을 표시한다. 프로그램 사이의 관계에는 HTTP 같은 통신 약속도 필요에 따라 쓴다. 색만으로 정상·실패를 구별하면 흑백 출력이나 색 구별이 어려운 독자에게 의미가 사라지므로 글자와 선 모양을 함께 쓴다.

이 단원의 그림은 설계 의도이며 서버가 실제 존재하거나 보호 장치가 작동한다는 증거는 아니다. 실행 로그나 시험은 별도로 필요하다. 그림에 나온 네 단계 시간을 더하려면 단계가 순차이고 겹치지 않으며 각 시간에 중복 계상이 없다는 조건부터 확인한다. 병렬 작업이나 재시도가 있으면 같은 단순 합을 사용할 수 없다.

6 ms에 사용자가 본 접수 응답은 11 ms의 저장 확인보다 먼저입니다. 문서에는 사람·API·큐·Worker·DB의 책임과 각 화살표의 자료·목적을 명시합니다. 이 구조도만으로 실제 배포 대수나 복제·장애 내구성은 알 수 없습니다.

중간 과정을 따라가는 예제

가상 성공 흐름의 겹치지 않는 네 구간 시간이 요청 전달2ms, API 검증3ms, DB 저장5ms, 응답 전달2ms다. 순차 실행이라고 가정할 때 합계와, 검증 실패로 저장을 건너뛰는 흐름의 합계를 구하라. 실패 응답 전달도2ms로 가정한다.

  1. 성공 경로는 요청→검증→저장→응답이며 네 시간은 서로 겹치지 않는 구간으로 정의되었다.

  2. 성공 시간은 2+3+5+2=12ms다. 저장 확인 전달 등 추가 시간은 여기서5ms 구간에 포함했다고 가정한다.

  3. 검증 실패 경로는 요청2+검증3+실패 응답2이고 DB를 호출하지 않는다. 합은7ms다.

  4. 실패 경로가5ms 짧다는 계산은 실패가 더 좋은 서비스라는 뜻이 아니다. 완료라는 목적을 이루지 못했다.

  5. 이 숫자는 모형의 합산 결과다. 실제 응답 시간은 네트워크·동시 요청·재시도·측정 경계에 따라 달라져 실행 증거가 필요하다.

가정한 성공12ms, 검증 실패7ms. 저장 성공 전에는 완료 성공 응답을 보내지 않는다.

조건을 바꾸어 비교하기

두 응답의 경계를 따로 읽습니다

표의 접수 응답 지연, 저장 완료 시각, 완료 상태 관측 지연을 구하고, 사용자가 6 ms에 저장 완료로 표시하면 생기는 문제를 설명하세요.

  1. 요청 시각 0 ms부터 접수 응답 수신 6 ms까지의 지연은 6 ms입니다.

  2. 모형의 DB 저장 완료는 11 ms이고 상태 조회로 관측한 완료 지연은 12 ms입니다.

  3. 6 ms에는 저장 완료 사건이 아직 일어나지 않았으므로 접수됨과 완료를 같은 표시로 바꿀 수 없습니다.

접수 지연은 6 ms, 저장 완료 시각은 11 ms, 완료 관측 지연은 12 ms입니다. 각각 다른 계약의 경계입니다.

비교할 점

실제 DB의 내구성 정책이나 사용자의 실제 화면을 검증한 결과가 아니라 명시한 사건 모형의 판정입니다.

접수 후 실패 경로를 구조도에 남깁니다

별도 요청은 6 ms에 접수 응답을 받았지만 Worker가 9 ms에 실패하여 DB 쓰기는 전혀 수행하지 않았다고 정합니다. 어떤 상태와 화살표를 남겨야 하나요?

  1. 접수 응답의 성공은 그대로 과거 기록으로 보존합니다.

  2. Worker 실패 뒤 DB 쓰기 경로는 실행되지 않았다고 기록합니다.

  3. 상태 조회가 그 실패를 실제로 읽은 시각은 주어지지 않았으므로 사용자에게 실패가 이미 전달됐다고 쓰지 않습니다.

작업은 접수됐으나 저장은 미완료이고 Worker 실패가 발생했습니다. 실패 관측과 재시도 정책은 별도로 명시합니다.

비교할 점

9 ms 실패라는 추가 전제가 없는 단순 시간 초과만으로 저장 미수행을 확정하지 않습니다.

종이와 본문으로 직접 해보기

종이에 브라우저/API/DB 세 상자를 그려 성공 메시지 네 개와 검증 실패 메시지를 표시하라. DB 실패 때 API가 완료 성공을 보내는 화살표를 그려도 되는가? API가 DB에 직접 저장한다는 설계 조건이다.

힌트 보기

상자 이름 옆에 책임을 적고 요청/확인/응답을 구별한다. 실패는 같은 상자 사이의 다른 메시지일 수 있다.

풀이 보기

성공은 브라우저→API 요청, API→DB 저장, DB→API 확인, API→브라우저 성공이다. 검증 실패는 브라우저→API 요청 뒤 API→브라우저 오류이며 DB 화살표가 없다. DB 실패에서는 DB→API 실패, API→브라우저 저장 실패로 표시한다. DB가 실패했는데 성공 응답을 보내면 정한 완료 의미를 위반한다.

오해와 반례

구조도에서 두 상자가 연결되어 있으면 그 관계는 모든 요청에서 실행된다.

연결은 가능한 의존 관계나 정보 흐름을 설명한다. 검증 실패 요청이 DB를 건너뛰는 것이 반례다. 동적 그림에 조건과 메시지를 붙여 어느 시나리오를 설명하는지 밝혀야 한다.

연습 1 · 값과 상태 예측

정상 표에서 Worker 시작만 10 ms로 늦어집니다. Worker 시작부터 저장 확인까지는 3 ms, 저장 확인부터 상태 관측까지는 1 ms로 유지합니다. 접수와 두 완료 시각은?

힌트 1

접수 경로는 바뀌지 않았습니다.

힌트 2

늦어진 단계 뒤의 시각을 새 시작에서 계산합니다.

풀이와 답 확인

  1. 브라우저 접수 응답은 여전히 6 ms입니다.

  2. DB 저장 완료는 10+3=13 ms이고 상태 완료 관측은 14 ms입니다.

접수는 6 ms, 저장 완료는 13 ms, 완료 관측은 14 ms입니다.

연습 2 · 오류 찾아 고치기

그림의 화살표에 모두 성공이라고 쓰고 API·Worker·DB의 책임 설명을 생략했습니다. 접수와 완료를 구별할 최소 보완을 제안하세요.

힌트 1

누가 무엇을 확인하는지 화살표별로 씁니다.

힌트 2

정상 경로만으로 실패와 관측 범위를 숨기지 않습니다.

풀이와 답 확인

  1. API→큐는 작업 접수 요청, 큐→API는 접수 확인으로 이름 붙입니다.

  2. Worker→DB는 저장 요청, DB→Worker는 저장 확인으로 구별합니다.

  3. 브라우저 접수 응답과 완료 상태 조회에 각 의미·시각을 쓰고 실패 경로도 덧붙입니다.

구성 요소의 책임, 방향, 전달 자료와 확인 범위를 설명합니다.

대안과 선택 이유

점수가 가장 높은 대안을 고르면 항상 요구를 만족할까?

준비 개념과 학습 목표

준비 개념

  • 대안은 같은 문제를 푸는 서로 다른 방법이다. 비교 기준은 문제와 제약에서 나온다.

  • 필수 조건은 통과 여부를, 선호 기준은 통과한 후보의 장단점을 판단하는 데 쓴다.

  • 점수와 시간은 교육용 가정이며 기술의 실측 성능이나 가격표가 아니다.

학습 목표

  • 대안별 장점·손해·미확인 사항을 같은 기준으로 기록한다.

  • 필수 조건과 가중치 선호를 분리한다.

  • 환경이 달라질 때 선택을 재검토할 이유를 설명한다.

점수로 고른 대안이 필수 조건과 비용까지 충족할까요?

자체 대안 A의 운영 편의 점수는 4, 오프라인 기능 점수는 1입니다. B의 운영 편의 점수는 2, 오프라인 기능 점수는 5입니다. 점수는 클수록 좋고 운영 가중치를 w, 오프라인 가중치를 1−w로 두며 0≤w≤1입니다. 점수와 가중치는 가상 판단 입력입니다. 이 계산을 실제 사용자 설문이나 성능 실측으로 보고하지 않습니다.

필수 조건은 점수 합산 전에 적용합니다. 별도 용량은 A가 25명, B가 15명의 동시 사용을 지원한다고 이 문제에서 정합니다. 실제 동시 사용 시험은 하지 않았습니다. 비용 모형은 A의 초기 비용 8 U·월 비용 1 U, B의 초기 비용 2 U·월 비용 3 U이며 기간 t개월 동안 같은 기능 범위의 총비용을 비교합니다. 단위 U는 자체 비용 단위입니다.

선택하기 전에 문제와 제약을 적는다

학습 기록을 한 사람이 오프라인에서 수정하는 상황과 스무 사람이 동시에 수정하고 공유하는 상황은 다르다. 로컬 JSON 파일과 공유 서버 DB를 비교한다면 먼저 편집자 수, 동시 변경 처리, 오프라인 필요, 운영할 사람을 적는다. JSON은 데이터 표현 형식이지 동시 변경 충돌을 자동으로 해결하는 장치는 아니다.

이 모형의 A는 충돌 해결을 갖추지 않은 단일 편집 로컬 파일, B는 동시 편집 검사를 갖춘 공유 서비스라고 정의한다. 모든 파일 방식이 동시 편집을 못 한다거나 DB가 자동으로 충돌을 모두 해결한다는 일반 주장으로 확대하지 않는다. 현실의 후보는 구체적 구현과 시험을 확인해야 한다.

필수 조건 뒤에 선호를 비교한다

필수 동시 편집을 지원하지 못하는 후보는 유지보수가 쉬워도 현재 요구에 맞지 않는다. 통과 후보끼리 관리 편의·동기화·오프라인 대응을 비교할 수 있다. 가중 합은 중요도를 숫자로 드러내는 한 도구이며 점수가 주관적인 경우 그 근거와 불확실성을 함께 적어야 한다.

기준이 서로 겹치면 같은 장점을 두 번 셀 수 있다. 점수 범위의 뜻도 통일해야 한다. 여기서는 세 기준 모두1~5점이고 클수록 좋다고 가정한다. 응답 시간처럼 작을수록 좋은 원래 수치를 그대로 같은 방향으로 더하지 않는다. 필수 조건을 큰 벌점 하나로 감추기보다 통과 여부를 별도 표시한다.

조건·비용·불확실성을 함께 남긴다

선택 이유에는 좋은 점뿐 아니라 운영 부담과 포기한 기능을 적는다. 구축 기간과 매달 운영 시간이 다른 후보는 살펴보는 기간에 따라 총 시간이 달라진다. 이때 한 달이 몇 시간이라는 식의 실제 노동 조건을 정하지 않고 일·월을 바로 더해서는 안 된다. 아래는 둘 모두 작업일로 환산한 모형이다.

미확인 사항은 성능이 좋음처럼 확정하지 말고 예상·확인 방법·담당·판단 시점을 적는다. 요구가 한 명에서 스무 명으로 바뀌면 이전 선택이 당시 틀렸다는 결론보다 새 조건이 무엇을 바꾸는지 설명한다. 결정 이유를 남겨야 다음 사람이 같은 토론을 처음부터 반복하지 않고 변경의 영향을 검토할 수 있다.

중간 과정을 따라가는 예제

A 점수는 관리4/동기화1/오프라인5, B는3/5/1이다. 가중치0.5/0.3/0.2로 계산하되 필수 조건은 스무 명 동시 편집이며 이 모형에서는 B만 통과한다. 단순 최고 점수와 실제 선택을 비교하라.

  1. 가중치는0.5+0.3+0.2=1이고 점수는 모두 클수록 좋다는 동일 범위다.

  2. A는4×0.5+1×0.3+5×0.2=2+0.3+1=3.3이다.

  3. B는3×0.5+5×0.3+1×0.2=1.5+1.5+0.2=3.2다. 선호 합만 보면 A가0.1 높다.

  4. 그러나 A는 필수 조건을 통과하지 못한다. B만 통과하므로 이 모형의 적합 후보는 B다.

  5. B의 오프라인 점수1이라는 손해를 숨기지 않는다. 오프라인도 필수가 되면 B까지 탈락하므로 새 대안·조건 협의가 필요하다.

가중 합 A3.3/B3.2지만 필수 조건 적용 뒤 B를 선택한다. 어느 후보도 필수를 만족하지 않으면 선택을 억지로 확정하지 않는다.

조건을 바꾸어 비교하기

가중치의 선택 경계를 계산합니다

필수 조건은 없다고 정합니다. A와 B의 점수가 같은 w, w=0.7의 점수와 선호, w가 0.6부터 0.8까지 미확정일 때의 결론을 구하세요.

  1. 1+3w=5−3w에서 6w=4이므로 경계는 w=2/3입니다.

  2. w=0.7이면 A 점수는 3.1이고 B 점수는 2.9여서 A를 선호합니다.

  3. w=0.6이면 A가 2.8, B가 3.2이고 w=0.8이면 A가 3.4, B가 2.6입니다. 미확정 구간은 경계 양쪽을 포함합니다.

w=2/3에서는 동률이고 그보다 크면 A, 작으면 B를 선호합니다. 0.6≤w≤0.8만 알려지면 하나의 우승 대안을 확정할 수 없습니다.

동률의 선택 규칙과 미확정 가중치의 확인 절차는 이 점수식만으로 자동 정해지지 않습니다.

기간을 바꾸면 비용의 순서가 바뀝니다

기능 범위가 같고 다른 비용은 없다고 정합니다. t=2개월과 t=4개월의 비용, 동률 기간을 구하세요.

  1. A 총비용은 8+t, B 총비용은 2+3t입니다.

  2. t=2이면 A는 10 U, B는 8 U입니다. t=4이면 A는 12 U, B는 14 U입니다.

  3. 8+t=2+3t에서 t=3개월이며 두 비용은 11 U입니다.

2개월은 B가 싸고 4개월은 A가 쌉니다. 3개월은 동률입니다.

소단원 4.3

설계 결정 기록

예전 결정을 지우면 새 팀원이 변경 이유를 더 쉽게 알 수 있을까?

준비 개념과 학습 목표

준비 개념

  • ADR은 중요한 설계 결정과 맥락·이유·결과를 남기는 짧은 기록이다.

  • 제안·승인·거절·대체 상태는 구분하며 승인된 설계도 구현 완료와는 다르다.

  • 아래 번호와 팀 검토는 가상 종이 사례다. 실제 프로젝트 승인이나 파일 변경을 수행하지 않는다.

학습 목표

  • 중요한 결정의 맥락·대안·선택·손해를 적는다.

  • 제안과 승인, 과거 결정의 대체 관계를 추적한다.

  • 기록의 상태를 실제 구현·시험 증거와 구분한다.

최신 승인 결정과 지금 배포된 구현이 다르면 무엇을 현재라고 쓰나요?

자체 결정 원장에서는 ADR 21이 월요일 10시에 accepted 상태로 대안 A를 선택했습니다. ADR 22는 화요일 12시에 accepted 상태가 되어 대안 B를 선택하고 ADR 21을 superseded로 표시합니다. 화요일 13시의 배포 관찰 기록은 여전히 구현 A입니다. 승인된 결정과 현재 구현의 관찰은 서로 다른 상태입니다. 실제 회의·승인·배포를 수행한 것이 아니라 이 문제의 가상 자료입니다.

ADR 23은 화요일 14시에 대안 A 복귀를 proposed로 제안했으나 15시에 rejected 상태가 되었습니다. 거절된 제안이 현재 accepted 결정 ADR 22를 대체하지 않습니다. 결정 기록에는 선택·근거·불리한 결과와 참조를 남기고 과거 승인 내용을 새 선택으로 덮어쓰지 않습니다. accepted 또는 rejected 기록을 다시 쓰지 않고 바뀐 선택은 새 식별자와 관계로 남기는 원칙을 사용합니다.

먼저 확인할 개념
  • 설계 결정 기록

    앞 본문의 proposed·accepted·superseded·rejected 상태와 과거 결정 보존을 확인합니다.

  • 대안과 선택 이유

    선택의 조건과 불리한 결과를 결정의 근거에 함께 연결합니다.

무엇을 한 기록에 담는가

변수 이름 하나하나보다 저장 방식, 공개 인터페이스, 실패 처리처럼 구조와 주요 품질에 영향을 주는 결정을 기록한다. 제목과 번호로 무엇을 결정하는지 찾고, 맥락에는 제약과 충돌하는 요구를 적는다. 결정은 공유 저장을 사용한다처럼 팀이 채택하려는 구체적 행동으로 쓴다.

대안과 근거, 기대 이득, 운영 부담, 아직 모르는 점을 이어 적으면 이유를 평가할 수 있다. 특정 양식이 사고를 대신하지 않는다. 숫자와 성능 주장은 자료나 시험 기록을 연결해야 하고, 없으면 교육 모형·추정·미확인으로 표시한다. 짧은 기록은 이유를 생략하라는 뜻이 아니라 한 중요한 결정에 집중하라는 뜻이다.

제안 뒤 검토와 승인

제안된 기록은 검토 대상이며 채택한 결정이 아니다. 다른 사람이 먼저 읽고 불명확한 조건·손해·대안을 질문하면 작성자가 고치고 다시 검토한다. 거절했다면 이유를 남겨 같은 조건의 제안을 반복해 논의할 때 참고할 수 있다.

AWS의 절차는 승인 뒤 기록을 고쳐 과거 이유를 바꾸는 대신 새 결정을 제안하고 승인하면 이전 기록을 대체 상태로 표시한다. 이 단원은 그 절차를 교육 모형으로 사용한다. 실제 팀마다 규칙은 다를 수 있으므로 누가 승인하는지와 변경 절차를 합의해야 한다. 번호와 날짜, 참여자 표기도 허위 승인을 적는 용도로 사용하지 않는다.

이력과 구현 증거를 연결한다

ADR3이 로컬 저장을 승인하고 뒤에 동시 편집 요구가 생겼다면 ADR4에서 공유 저장 대안을 제안할 수 있다. ADR4가 제안 상태인 동안 ADR3을 대체했다고 표시하면 아직 승인하지 않은 변경을 채택한 것처럼 오해하게 한다. ADR4 승인 뒤 ADR3에 대체됨·대체 기록4를 연결하되 과거 맥락은 남긴다.

승인 기록은 그 선택을 채택했다는 의미이지 코드가 구현되어 시험을 통과했다는 의미는 아니다. 구현 작업과 시험 기록을 별도로 연결한다. 반대로 구현이 이미 변했는데 기록이 옛 상태라면 두 정보의 불일치를 발견하고 검토해야 한다. 설계 의도와 관찰한 결과를 함께 읽어야 현재 상태를 정확히 설명할 수 있다.

정상 비동기 요청의 접수 관측은 6 ms, 저장 확인은 11 ms, 완료 상태 관측은 12 ms다. A/B의 가중 점수는 1+3w와 5−3w이며 동률 경계는 w=2/3이다. w=0.7에서 A는 3.1, B는 2.9다. w=0.6에서는 A가 2.8, B가 3.2이고 w=0.8에서는 A가 3.4, B가 2.6이어서 미확정 구간에서 승자는 정해지지 않는다. 오프라인 최소 3이면 B만 후보이며 동시 사용 최소 20명까지 요구하면 두 후보 모두 탈락한다. 비용 A=8+t, B=2+3t는 t=3개월에 각 11 U로 같다. 기간이 2개월이면 A 비용은 10 U이고 B 비용은 8 U다. 기간이 4개월이면 A 비용은 12 U이고 B 비용은 14 U다. 변경 비용 2c를 A에 추가하면 경계는 t=3+c이며 c=2일 때 5개월이다. 이 별도 모형의 기간이 4개월이면 A 비용은 16 U이고 B 비용은 14 U다. 기간이 6개월이면 A 비용은 18 U이고 B 비용은 20 U다.
