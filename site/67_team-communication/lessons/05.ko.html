소단원 5.1

API 계약

한 팀이 만든 기능을 다른 팀이 구현 코드를 읽지 않고 사용할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 함수와 입력·반환값

  • 자료형과 조건

학습 목표

  • 호출자와 구현자의 책임을 선행/후행 조건으로 구별한다.

  • 변경이 기존 사용자의 약속을 깨는지 판정한다.

사용 경계의 약속

API는 다른 코드가 기능을 사용하는 접점이다. 네트워크 주소뿐 아니라 함수나 라이브러리의 공개 메서드도 API다. 계약은 이름·입력·출력에 더해 값의 의미, 허용 범위, 오류와 상태 변화의 약속을 기록한다. 점수라는 숫자만으로는 0~1 비율인지 0~100 백분율인지 알 수 없다.

계약이 있으면 호출 팀은 내부 계산 방식을 몰라도 약속을 바탕으로 사용하고 구현 팀은 그 약속을 지키며 내부를 바꿀 수 있다. 이런 독립성은 문서가 정확하고 실제 코드가 맞을 때 성립한다. 문서를 작성했다는 사실이 구현의 정확성을 증명하지 않는다. 여기서 계약은 교육용 기술 약속이지 법률 계약의 해석이 아니다.

선행 조건과 후행 조건

선행 조건은 호출 시에 만족해야 하는 조건이고, 후행 조건은 선행 조건을 만족한 호출이 끝났을 때 구현자가 지켜야 할 결과다. 자체 함수 passFlag(score)의 선행 조건을 0 이상 100 이하 정수로 정하고, 후행 조건을 score가 60 이상일 때 그리고 그때만 true라고 정할 수 있다. 반환 형식만 boolean이라고 쓰면 판정 기준이 빠진다.

선행 조건 밖의 행동을 약속하지 않은 내부 함수와, 외부 입력을 검증하여 오류를 반환하는 API는 다르다. 후자의 계약은 잘못된 형식·범위에도 구체적인 오류 행동을 정의해야 한다. 선행 조건이 없는 것처럼 쓰고 검증을 생략하면 서로 다른 기대가 생긴다. 입력을 수정하는지, 상태를 바꾸는지 역시 결과 약속에 포함한다.

변경의 호환성

계약을 유지하는 내부 알고리즘 교체는 사용자의 변경 없이 가능할 수 있다. 그러나 점수 기준을 60에서 70으로 바꾸면 반환 자료형이 같아도 행동이 달라진다. 기존 사용자는 65를 합격으로 처리했으므로 새 결과는 그 사용을 깨뜨린다. 호환성을 형식만으로 검사하면 이런 의미 변화를 놓친다.

기존 호출에 새 필수 인자를 추가하거나 필드 이름·단위를 바꾸면 소비자를 함께 검토해야 한다. 선택 인자 추가도 기존 기본 동작을 보존하는지 확인한다. 변경 이유·영향받는 사용처·전환 계획을 기록하고 양측이 합의한 새 계약을 배포 전에 검토한다. Google AIP의 구체 규칙은 Google API 설계 맥락이며 모든 시스템의 자동 판정 법칙은 아니다.

중간 과정을 따라가는 예제

자체 passFlag(score)는 정수 0~100, true⇔score≥60, 상태 변경 없음이다. 입력 59/60/65/100을 판정하고 새 구현의 기준 70이 기존 계약을 만족하는지 확인하라.

  1. 네 입력은 모두 정수이고 0~100 범위에 들어 선행 조건을 만족한다.

  2. 59는 60보다 작아 false다.

  3. 60·65·100은 모두 60 이상이므로 true다. 경계 60을 포함한다.

  4. 기준 70 구현은 65를 false로 반환하므로 기존 후행 조건과 모순이다.

  5. 기준 변경이 필요하면 기존 계약을 몰래 바꾸지 않고 새 약속과 소비자 전환을 검토한다.

기존 결과는 false/true/true/true다. 기준 70은 자료형이 같아도 기존 행동 계약을 깨뜨린다.

종이와 본문으로 직접 해보기

이 내부 함수의 선행 조건 밖인 -1, 60.5, null을 적고, 검증 API를 추가한다면 각 입력에 어떤 문서가 필요한지 써라.

힌트 보기

내부 함수에 없던 오류 보장을 추측하지 않는다. 외부 경계가 받아들이는 값과 오류를 별도로 정한다.

풀이 보기

세 입력은 모두 내부 함수의 선행 조건 밖이다. 그 함수의 반환값을 계약으로 추론할 수 없다. 자체 검증 API라면 -1은 RANGE_ERROR, 60.5와 null은 TYPE_ERROR로 정의하는 방식 등을 합의할 수 있다. 이것은 새로 설계한 행동이며 기존 함수가 이미 그렇게 작동한다는 주장이 아니다.

오해와 반례

반환 자료형이 같으면 API를 어떻게 바꿔도 호환된다.

boolean 형식을 유지해도 기준 60→70은 score=65의 결과를 바꾼다. 의미·단위·기본값·상태 변화까지 소비자가 의존하는 약속을 대조해야 한다.

소단원 5.2

입출력·오류·예제

정상 응답 예시 하나로 실패 상황의 행동도 알 수 있을까?

준비 개념과 학습 목표

준비 개념

  • API 계약

  • JSON 값의 종류

학습 목표

  • 입력 형식·범위와 성공/오류 응답을 모호함 없이 기록한다.

  • 예제로 경계·오류와 문서 일관성을 확인한다.

형식과 뜻을 함께 적기

자체 검증 API의 요청은 score 필드 하나를 가진 JSON 객체라고 정한다. score는 숫자 값이며 값이 정수이고 0~100이어야 한다. 따라서 문자열 "60"은 숫자 60과 다르고 null이나 필드 누락도 다르다. 이 모형에서는 숫자 60.0은 수학적으로 정수인 값이라 허용한다. 다른 시스템은 표현을 더 제한할 수 있어 문서에 써야 한다.

자체 예제의 판단 순서는 객체/필드/숫자 종류·정수 여부 확인, 범위 확인, 합격 계산이다. 추가 필드는 허용하지 않는다고 이 모형에 명시한다. 둘 이상의 오류가 있으면 먼저 형식 오류를 내도록 순서를 정한다. 값의 단위를 백분율 점수로 정의하고 성공 여부와 학습자 평가의 신뢰도를 혼동하지 않는다.

서로 구별되는 응답 만들기

자체 성공 응답은 kind="ok"와 passed boolean을 포함한다. 실패 응답은 kind="error"와 error_code, 설명 message를 포함하며 passed는 없다. 합격하지 못한 정상 평가인 passed=false와 입력 처리 실패를 다른 가지로 구별한다. 이 객체는 교육용 설계로 Google rpc.Status나 실제 HTTP 서버 응답의 표준 형식이라고 주장하지 않는다.

프로그램은 안정된 error_code로 행동을 결정하고 사람은 message를 읽어 입력을 고칠 수 있게 한다. 번역이나 문장 개선으로 메시지가 달라질 수 있으므로 메시지 문자열을 비교해 오류 종류를 결정하지 않는다. TYPE_ERROR는 형식을 고치고 RANGE_ERROR는 범위를 고쳐야 하며 같은 요청을 무작정 반복해도 문제가 해결되지 않는다.

예제는 규칙의 작은 검사점

문서에 정상값만 나열하면 경계나 오류에서 기대가 갈린다. 0/59/60/100, -1/101, 문자열과 null, 필드 누락 예제를 규칙과 연결한다. 예제가 모두 맞아도 모든 입력·보안·실행이 검증된 것은 아니다. 예제와 규칙이 충돌하면 하나를 임의로 믿기보다 계약을 고쳐 합의한다.

네트워크 시간 초과는 이 모형의 입력 오류와 별개의 전달 실패다. 서버가 처리했는지 모르는데 상태를 바꾸는 요청을 다시 보내면 중복 효과가 생길 수 있다. 재시도나 중복 방지의 보장은 별도 계약이 필요하다. 여기서는 상태를 바꾸지 않는 판정 모형의 입력·응답만 종이로 다루며 HTTP 요청을 보내지 않는다.

중간 과정을 따라가는 예제

자체 계약에 따라 {score:60}, {score:59}, {score:"60"}, {score:101}을 판정하라. 표시된 객체는 종이 표기이며 실제 전송 JSON이 아니다. kind와 핵심 필드를 적어라.

  1. 60은 숫자·정수·범위를 통과하므로 정상 가지로 간다.

  2. 60≥60이라 kind=ok, passed=true다.

  3. 59도 정상 입력이지만 60 미만이므로 kind=ok, passed=false다.

  4. 문자열 "60"은 숫자가 아니라 kind=error, error_code=TYPE_ERROR다. 자동 변환하지 않는다.

  5. 101은 숫자·정수지만 범위를 넘어 kind=error, error_code=RANGE_ERROR다. 오류 응답에는 passed가 없다.

차례로 ok/true, ok/false, error/TYPE_ERROR, error/RANGE_ERROR다. 합격 실패와 API 입력 오류는 다른 가지다.

종이와 본문으로 직접 해보기

필드 없는 객체, {score:null}, {score:60.5}, {score:60.0}, {score:60,extra:1}을 판정하라.

힌트 보기

숫자인지와 값이 정수인지 구별하고 추가 필드 정책을 적용한다.

풀이 보기

처음 세 입력은 TYPE_ERROR다. 60.0은 숫자 값이 정수 60이므로 ok/true다. 마지막은 추가 필드 금지 정책 때문에 TYPE_ERROR다. 이 정책은 자체 계약의 선택이며 모든 JSON API의 공통 규칙이 아니다.

오해와 반례

passed=false면 입력 처리에 실패한 것이므로 같은 요청을 다시 보내야 한다.

false는 정상 처리된 점수가 합격 기준보다 낮다는 의미다. 입력 오류는 error 가지로 표시된다. RANGE_ERROR도 같은 값 재전송으로 고쳐지지 않는다.

소단원 5.3

역할 간 의존성

서로 기다리는 팀도 계약을 정하면 병렬로 일할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • API 입력과 응답

  • 작업의 선행 관계

학습 목표

  • 제공자·소비자·검토자의 산출물과 책임을 정한다.

  • 모의 응답과 실제 통합 검증을 구별하고 변경 영향을 추적한다.

담당자보다 전달물을 먼저 정의하기

역할 간 의존성은 한 역할의 일을 끝내려면 다른 역할의 산출물이 필요한 관계다. 화면 팀은 응답 필드와 오류 뜻에 의존하고 서비스 팀은 입력 규칙에 의존한다. 담당자 이름만 배정하면 무엇을 언제 전달해야 하는지 빠진다. 산출물·소비자·완료 조건·검토할 사람을 함께 적는다.

자체 학교 프로젝트에서 계약 합의 작업 A, 서비스 구현 B, 화면 구현 C, 실제 통합 확인 D를 구분한다. A에서 입력·성공/오류 예제를 정하면 C는 그 예제의 모의 응답으로 화면 흐름을 먼저 준비할 수 있다. 모의 응답은 합의한 형식의 가짜 데이터이며 실제 서비스가 구현됐거나 통신이 성공했다는 증거가 아니다.

공유 경계의 변경을 양쪽에서 보기

응답의 passed를 success로 바꾸면 서비스만 고쳐서는 끝나지 않는다. 화면 소비자, 문서 예제, 검사 기준도 영향받는다. 변경 요청에 이유·이전/새 의미·사용처·전환 절차를 적고 양측이 확인한다. 이름이 같아도 단위나 기본값 변경은 의존성을 건드린다.

책임 경계에는 정상 결과뿐 아니라 오류를 누가 해석하고 어떤 화면을 보여 줄지도 들어간다. 입력 검증을 화면에만 맡기면 다른 호출자가 잘못된 값을 보낼 수 있다. 화면의 빠른 안내와 서비스의 경계 검증은 역할이 다르다. 문서 갱신 담당과 검토 기록 담당도 분명히 정한다.

기다림을 줄여도 통합 확인은 남는다

의존 작업의 순서와 시간을 적으면 어떤 일을 병렬로 시작할 수 있는지 보인다. 단순한 종이 모형에서는 각 역할에 전용 작업자가 있고 중단·수정·자원 경쟁이 없다고 가정한다. 실제 팀에서는 검토 지연이나 재작업이 생길 수 있으므로 계산을 납기 보장으로 말하지 않는다.

B와 C가 각각 끝나도 D에서는 실제 요청·응답·오류 흐름이 계약과 일치하는지 확인해야 한다. 모의 데이터만으로는 직렬화·통신·배포 차이를 못 찾을 수 있다. 실제 통합이 끝나기 전에 완료라고 보고하지 않는다. 이 수업의 일정과 역할 사례는 종이 계획이며 서버·화면·팀 작업을 수행한 기록이 아니다.

중간 과정을 따라가는 예제

전용 작업자가 있는 자체 모형에서 A 계약 합의 2시간, A 뒤 B 서비스 5시간과 C 모의 응답 기반 화면 3시간, B와 C 모두 뒤 D 통합 확인 1시간이다. 중단·재작업·경쟁이 없을 때 최단 완료 시간을 구하라.

  1. 시작 시각을 0으로 놓으면 A는 0~2시간이다.

  2. A가 끝난 2시간에 B와 C를 동시에 시작할 수 있다.

  3. B는 2+5=7시간, C는 2+3=5시간에 끝난다.

  4. D는 둘 다 완료되어야 하므로 max(7,5)=7시간에 시작한다.

  5. D 완료는 7+1=8시간이다. 모두 직렬로 하면 2+5+3+1=11시간이지만 이 모형은 병렬 작업을 허용한다.

모형 최단 완료는 8시간이다. 경로 A→B→D가 2+5+1=8시간으로 더 길며 실제 일정의 약속은 아니다.

종이와 본문으로 직접 해보기

C가 모의 응답을 쓸 수 없어 실제 B 완료 뒤에만 시작하도록 바뀌었다. 완료 시간을 다시 구하고, 모의 응답을 썼더라도 생략할 수 없는 확인을 적어라.

힌트 보기

새 의존 관계 A→B→C→D와 실제 통합의 의미를 확인한다.

풀이 보기

새 완료 시간은 2+5+3+1=11시간이다. 모의 응답을 허용한 기존 계획에서도 실제 서비스와 화면을 연결해 정상·오류 입력/응답이 계약과 맞는지 D에서 확인해야 한다. 이 활동은 그 실제 확인을 수행한 것이 아니다.

오해와 반례

팀별 구현이 끝나거나 모의 화면이 보이면 프로젝트 통합도 완료다.

모의 화면은 계약을 가정한 소비자 작업만 보여 준다. 실제 제공자가 그 형식과 의미를 지키며 연결되는지 통합 확인이 남는다. 양측 개별 완료와 전체 연결 완료를 분리해서 보고한다.
