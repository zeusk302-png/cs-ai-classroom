소단원 3.1

기능·품질 요구

“검색이 잘 되고 빠르면 된다”를 서로 같은 뜻으로 읽는 약속으로 바꿀 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 이해관계자는 결과에 관심이나 영향을 가진 사람·집단이다. 사용자 필요는 문제와 목적이고 요구는 제품이 제공할 동작·조건·제약을 구체화한 약속이다.

  • 기능 요구는 어떤 입력·사건에서 어떤 결과를 제공할지, 품질 요구는 그 동작의 성능·사용성·신뢰성 등 판단 조건을 적는다. 구분은 정리 도구이며 한 기능과 여러 품질 요구는 연결될 수 있다.

  • 식별자 R-F1 같은 이름은 요구를 안정적으로 가리키는 표식이다. 문서에서 이름만 붙이고 조건·근거·검증 방법을 비워 두면 합의가 완성되지 않는다.

학습 목표

  • 필요·기능·품질·설계 선택을 구별한다.

  • 입력 범위·정규화·빈 결과·성능 조건을 명시한다.

  • 정량 조건과 버전을 갖춘 작은 요구 표를 만든다.

검색 규칙의 적용 순서를 바꾸어도 같은 약속일까요?

앞 본문의 검색 약속을 새 자체 버전 N2로 확장합니다. N2는 제목과 검색어 모두에서 U+005F 밑줄을 U+0020 공백으로 바꾸고, 그 뒤 양끝 U+0020을 제거한 다음 ASCII A..Z만 소문자로 바꿉니다. 내부 공백은 합치지 않습니다. 이 순서를 포함한 정규화 결과로 부분 문자열을 찾습니다. 빈 검색어는 전체 목록을 반환하고 각 항목의 원래 ID·제목·링크·목록 순서를 보존합니다.

자체 목록의 ID 1은 제목 Py, ID 2는 제목 Py Basics, ID 3은 제목 PY입니다. 각 ID는 다른 강의이며 링크도 서로 다릅니다. 제목이 같은 정규화 결과가 되어도 항목을 합치지 않습니다. 원래 제목과 검색용 비교값은 다른 자료입니다. N2는 보편적인 다국어 검색 권장 규칙이 아니며 실제 제품이나 고객 합의가 아닌 종이 계약입니다.

먼저 확인할 개념
  • 기능·품질 요구

    앞 본문의 제한된 ASCII 정규화와 기능·품질·구현 선택 구분을 확인합니다.

  • 범위와 변경 관리

    규칙 N2가 원래 검색 규칙을 바꾸는 새 제안이라는 상태를 연결합니다.

필요를 동작과 조건으로 번역한다

가상 공개 강의의 필요는 “관심 있는 과목을 이름으로 찾고 싶다”다. R-F1은 과목 목록이 로드된 뒤 검색어에 포함되는 과목 제목과 연결을 표시한다는 제품 동작이다. “검색창이 있다”만 쓰면 입력이 언제 적용되는지, 제목과 소개 중 무엇을 검색하는지, 대소문자·공백·빈 검색은 어떻게 처리하는지 합의가 남는다.

작은 계약에서는 목록 순서를 유지하고 제목만 부분 문자열 검색한다. 검색어 앞뒤 U+0020 공백을 제거한 뒤 제목과 검색어의 ASCII A..Z만 a..z로 바꾸고 다른 문자는 그대로 둔다. 빈 검색어는 모든 과목을, 일치0개는 빈 결과 안내를 표시한다. 이는 전 세계 언어의 정렬·동의어·검색을 완성한 규칙이 아니라 이 단원에서 합의할 수 있는 제한 모형이다.

빠르다는 말에 환경과 분모를 붙인다

R-Q1을 “합의한 기준 환경에서 로컬 목록 로드가 끝난 뒤 미리 정한20개 입력 사례 중 최소95%는 마지막 입력 사건부터 결과 목록이 완전히 반영된 관측 지점까지200ms 이하”라고 적을 수 있다. 기준 환경은 브라우저/버전·기기·목록 크기·배경 작업·계측 방식과20개 사례 목록을 기록하며 그 정보가 미정이면 요구도 검증 준비 중이다.

이 조건은 모든 사례 최대200ms와 다르다. 20개에서95%는 최소19개이며 나머지1개가 더 오래 걸릴 수 있다. 실제 서비스를 위한 적절한 숫자인지 사용자의 필요·비용·환경을 검토해야 한다. 여기의95%/200ms는 자체 가상 약속이고 이미 측정한 성능이나 보편 권장 기준이 아니다.

구현 방법과 합의 상태를 구분한다

“React를 사용한다”는 일반 검색 기능의 결과보다 구현 선택에 가깝다. 팀이나 외부 인터페이스가 특정 기술을 반드시 요구하는 명시 제약이라면 따로 이유를 붙여 관리할 수 있다. 결과 요구에 불필요하게 코드를 넣으면 내부 구현을 바꿨을 때 약속도 부수게 된다. NASA와 MIT의 원칙을 참고하되 법·계약·대학 인증 요구를 받은 것으로 해석하지 않는다.

각 요구에 ID·문장·필요의 출처·조건·검증 연결·합의 상태를 둔다. 한 문장에 검색·번역·계정·다운로드를 모두 묶으면 어느 부분이 충족되었는지 판정하기 어렵다. 미정 값은 누가 무엇을 확인할지 남기고, 쓰인 문장을 팀이 승인한 문장으로 자동 바꾸지 않는다. 이 단원은 실제 고객과 합의하지 않은 가상 문서다.

중간 과정을 따라가는 예제

목록 [Python 입문,C 기초,선형대수]와 R-F1 규칙을 가정한다. 검색어 " PYTHON ",빈 문자열,"자료구조"의 결과를 구하라. "항상 빠르게 검색"을 품질 조건으로 분리하고,20건에서95%의 최소 개수를 구하라.

  1. " PYTHON "은 앞뒤 U+0020 제거 후PYTHON, ASCII 소문자화 후python이다. 제목의Python도python이어서 첫 과목만 일치한다.

  2. 빈 검색어는 계약상 전체3과목을 원래 순서대로 보여 준다. "자료구조"는 세 제목 어느 것에도 없어0개와 빈 결과 안내다.

  3. 기능 R-F1의 결과와 품질 R-Q1의200ms/20개/기준 환경/시작·끝 정의를 별도 ID로 적고 연결한다. 실제 측정 결과를 적지는 않는다.

  4. 20×0.95=19다. 측정 환경·20사례·관측 방법이 확정되지 않았다면 이 숫자만으로 검증 준비 완료가 아니다.

입력 결과는 첫 과목/전체3개/0개 안내이고 품질 기준은 최소19/20이다. 성능 환경과 계측 정의까지 합의해야 시험을 설계할 수 있다.

조건을 바꾸어 비교하기

순서가 다른 정규화를 구별합니다

원문 " _PY_ "를 N2로 처리하세요. 별도 잘못된 안 W는 양끝 제거, 밑줄 치환, ASCII 소문자화 순서입니다. 목록의 세 제목에는 밑줄이나 양끝 공백이 없습니다.

  1. N2는 밑줄 치환 뒤 양끝 공백을 모두 제거하여 py를 얻습니다.

  2. W는 먼저 양끝 공백만 제거해 _PY_를 얻고 이후 밑줄을 공백으로 바꾸어 " py "를 얻습니다. 이 안은 마지막에 공백을 다시 제거하지 않습니다.

  3. N2의 py는 세 제목에 모두 포함됩니다. W의 " py "는 세 비교 제목 어느 것에도 포함되지 않습니다.

N2는 ID 1·2·3을 원래 순서로 반환하고 W는 빈 결과를 반환합니다. 같은 단계 이름도 적용 순서가 결과를 바꿉니다.

비교할 점

앞 본문의 기존 규칙은 밑줄을 치환하지 않으므로 _py_로 비교하여 이 입력에서는 빈 결과입니다. 기존 결과를 새 N2 기대값으로 재사용하지 않습니다.

비교값이 같아도 항목 ID를 보존합니다

검색어 PY를 N2로 처리한 뒤 ID 1과 3의 정규화 제목이 같다는 이유로 하나를 삭제했습니다. 결과 요구와 충돌하는 내용을 쓰세요.

  1. 검색어 비교값은 py이며 세 강의가 모두 일치합니다.

  2. ID 1과 3의 비교 제목은 둘 다 py지만 ID와 링크가 다른 강의입니다.

  3. 결과는 세 항목과 세 링크를 보존해야 하며 제목 기준 중복 제거는 계약에 없는 변경입니다.

기대한 ID 목록은 [1,2,3]입니다. 한 강의를 지우면 찾을 수 있는 강의와 링크가 사라집니다.

비교할 점

표시 제목을 전부 py로 덮어쓰는 것도 비교용 정규화와 화면 표시를 혼동한 별도 오류입니다.

오해와 반례

기능 요구만 쓰면 품질은 자동으로 충족되고, 기술 이름을 쓰면 동작이 명확해진다.

검색 결과가 맞아도 갱신이 늦거나 키보드로 접근할 수 없을 수 있다. “React로 검색”도 공백·대소문자·빈 결과·시간 규칙을 정하지 않는다. 관찰 가능한 결과·조건과 설계 선택을 나누고 필요하면 명시 제약의 이유를 기록한다.

요구가 쓰여 있다는 것과, 그 요구가 충족되었다고 판정할 수 있다는 것은 어떻게 다를까?

준비 개념과 학습 목표

준비 개념

  • 수용 기준은 요구나 사용자 필요가 충족되었는지 판정할 관찰 가능한 결과 조건이다. 시험 사례는 그 조건을 구체 입력·기대 결과·절차로 펼친 것이다.

  • 추적은 요구 ID와 기준/시험/결과 기록의 연결이다. 연결이 있다는 사실과 실제로 시험에 통과했다는 사실은 다르다.

  • 평균과 임계값 이하 비율은 다른 통계다.20개 값 중18개가100ms,2개가500ms면 평균은140ms지만200ms 이하 비율은90%다.

학습 목표

  • 수용 기준에 준비 상태·입력 사건·기대 결과를 적는다.

  • 정답·비율·시간의 oracle과 근거를 별도로 정한다.

  • 미실행·실패·충족과 변경 버전을 구분한다.

누락된 한 기록이 수용 기준의 판정을 바꿀 수 있나요?

새 자체 시간 기준 Q2는 미리 지정한 서로 다른 25개 사례의 첫 시도를 대상으로 합니다. 동일 버전·환경·관측 방법에서 200 ms 이하인 사례가 최소 95%여야 합니다. 정수 통과 수는 25×0.95=23.75이므로 최소 24개입니다. 추가 재시도는 별도 기록으로 남기며 첫 시도의 판정을 덮어쓰지 않는다고 이 종이 문제에서 정합니다.

유효한 시간 기록이 없는 사례는 시간 초과가 확정된 제품 실패와 다릅니다. 분모 25는 유지하면서 확인된 통과 수와 미확정 수를 따로 적습니다. 미확정 기록이 가능한 두 값에서 모두 실패이면 기준 미충족을 논리적으로 확정할 수 있지만 실제 계측이 있었다는 주장은 할 수 없습니다. 아래 수치와 로그 상태는 자체 가상 자료입니다.

수치 기준은 계산 규칙까지 합의한다

R-Q1의 최소95%/20건/200ms 이하는 AC20에서19건 이상으로 펼친다. 시간 시작은 마지막 입력 사건을 관측한 순간, 끝은 해당 결과 목록이 완전히 갱신된 관측 지점이며 같은 시간축으로 차이를 잰다.100ms에서250ms까지면150ms다. 실행마다 버전·환경·입력·관측 방법을 남겨 비교할 수 있게 한다.

20건 중 끝나지 않은 건을 분모에서 빼면 실패를 숨겨 비율을 높일 수 있다. 이 기준은 미리 정한20건 전부를 분모에 넣고200ms를 넘기거나 미완료인 건은 시간 조건 미충족으로 센다고 정한다. 계측 자체가 무효하거나 로그가 없으면 제품 실패와 별도로 판단 불가/재시험을 기록하며 임의 성공으로 대체하지 않는다.

시험 표에는 요구R-F1→AC10/11/12→구체 사례와 기록 위치를 연결하고, 실행 전은 not_executed로 둔다. 기대 결과가 정해져 있다고 실제 결과를 채워 넣지 않는다. 실제로 다른 결과가 나왔으면 요구·기준·구현·자료 중 어디가 틀린지 확인하고 실패를 지워 완료 숫자만 맞추지 않는다.

중간 과정을 따라가는 예제

가상 로그20건 중18건100ms,2건500ms이고 모든 과목 결과는 맞았다. AC20은20건 중 최소19건이200ms 이하이다. 평균·임계 비율·AC20 판정을 구하고 실제 시험을 수행했다는 보고가 가능한지 판단하라.

  1. 총 시간은18×100+2×500=1800+1000=2800ms이며 평균은2800/20=140ms다.

  2. 200ms 이하인 것은18건이므로18/20=90%다. 평균140<=200과 다른 질문이다.

  3. AC20은19건 이상이 필요하여 가상 표에서는18건으로 미충족이다. 기능 결과의 일치로 이 품질 실패가 사라지지 않는다.

  4. 이 표는 자체 가상 입력이므로 실제 시험 성공/실패 로그라고 보고하지 않는다. "가상 표의 계산상 기준 미충족, 실제 계측은 미수행"으로 기록한다.

별도 25개 사례에서 기능 결과가 맞는 것은 24개, 시간 조건을 만족한 것도 24개입니다. 둘 다 만족한 사례는 최소 몇 개이고, 전체 성공을 최소 95%로 요구하면 반드시 통과하나요?

  1. 기능 집합 F와 시간 집합 T가 전체 25개 안에 있습니다.

  2. 교집합은 적어도 24+24−25=23개이며 최대 24개입니다.

  3. 기능만 맞는 사례 한 개와 시간만 맞는 사례 한 개가 서로 다르면 교집합 23개로 전체 성공 기준을 실패합니다.

평균200ms 이하이면95%가200ms 이하라는 수용 기준도 통과한다.

소단원 3.3

범위와 변경 관리

추가 요청 한 줄이 검색·시험·일정의 어떤 약속을 바꾸는지 어떻게 함께 볼까?

준비 개념과 학습 목표

준비 개념

  • 범위는 이번 버전에 포함/제외할 결과와 경계다. 기준선(baseline)은 합의해 식별한 문서·조건의 버전으로, 변경 논의의 출발점이다.

  • 변경 요청은 기존 요구에 대한 제안이다. 요청·검토·승인·구현·검증·적용 기록은 서로 다른 상태이며 제안이 곧 승인이라는 뜻은 아니다.

  • person-day는 사람 한 명의 하루 작업량 상당이라는 계획 단위다. 인원으로 나눈 값은 완벽 병렬 가정의 하한일 수 있으며 실제 완료 일정을 보장하지 않는다.

학습 목표

  • 포함/제외·기준선·요구 ID를 명시한다.

  • 변경의 결과·품질·시험·자료·일정 영향을 추적한다.

  • 승인과 구현/검증 완료를 구분해 이력을 유지한다.

작업량이 가용량에 맞으면 마감도 자동으로 맞을까요?

가상 CR8의 설계 A는 2일, 구현 B는 3일, 검토 C는 2일입니다. A가 끝나야 B를 시작하고 B가 끝나야 C를 시작합니다. 각 작업은 한 사람이 하루에 최대 1 person-day를 진행하며 분할하거나 여러 사람이 동시에 맡아 기간을 줄일 수 없습니다. 두 사람은 매일 각각 1 person-day의 가용량이 있고 마감은 시작 뒤 6작업일입니다.

기존 독립 작업 E는 5 person-day이며 다른 사람이 연속 5일 진행할 수 있습니다. 전체 작업량은 CR8의 7과 E의 5를 합친 12 person-day로 두 사람의 6일 총량 12에 맞습니다. 그러나 A→B→C의 직렬 경로는 7일입니다. 다음 표는 실제 인력이나 일정 관측이 아닌 자체 완전 가용 모형이며 승인 여부·구현 완료·검증 완료를 별도 상태로 둡니다.

바꿀 기준선을 먼저 함께 가리킨다

가상 v1은 제목 검색R-F1, 세 기능 기준AC10/11/12와 시간R-Q1/AC20을 포함하고 계정·검색 이력 저장·다른 기기 동기화는 제외한다. 이는 영구 금지가 아니라 이번 버전의 합의 범위다. “편리한 검색”만 있으면 저장 요청이 원래 포함인지 추가인지 서로 다르게 해석할 수 있다.

문서ID/버전/승인 상태를 남기고 어떤 요구·기준·자료 버전이 시험 보고서와 연결되는지 표시한다. 기록에 이전 문장을 덮어써 버리면 과거 시험이 어떤 약속을 판단했는지 잃는다. 현재 합의본과 과거본을 구별하되 사람이 실제 승인하지 않은 본문을 승인본이라고 쓰지 않는다. 본문 v1은 실제 프로젝트 합의가 아닌 종이 사례다.

요청의 영향을 결과에서 시험까지 펼친다

CR7은 "새로고침 뒤 같은 기기에서 마지막 검색어를 다시 보고 싶다"는 요청이다. 먼저 사용자 목표를 확인하고 저장 범위·보존 기간·다른 사용자/공유기기·저장 차단 시 결과를 정한다. 계정·클라우드 동기화를 요청한 것으로 자동 확대하지 않는다. 새 기능R-F3과 읽기/저장 실패의 기준, 관련 품질·개인정보·안내·회귀 시험을 검토한다.

가상 계획에서 기존 합의 작업6person-day, 전체 가능량10person-day라면 남은4다. 추가 설계2·구현3·시험1의 추정합6은 전체12가 되어2를 초과한다. 추정은 합리적 계획 자료이며 실제 구현 완료나 모든 위험 비용의 확정 측정이 아니다. 목표를 만족하는 다른 범위, 기간·자원 조정, 다음 버전 이월을 비교한 뒤 정한 권한자가 결정한다.

승인 후에도 구현과 검증 상태를 따로 추적한다

변경 표에는 요청ID·이유·기준선·영향 요구/기준·추정·결정/결정자·후속 작업·검증 증거를 기록한다. 승인되면 새 기준선을 식별하고 관련 문서와 시험 기대값을 갱신하며 영향을 받는 팀에 알린다. 승인됐다고 코드를 구현하거나 실제 시험이 끝난 것은 아니다. 작은 팀의 역할과 절차는 필요에 맞게 정하되 NASA의 정식 조직 절차를 수행했다고 부르지 않는다.

예를 들어 목록 제목 "C 기초"를 "C 언어 기초"로 바꾸면 표시 기대값과 검색 자료가 바뀐다. 옛 제목에만 맞춘 기준을 계속 통과했다고 표시하지 않고 새 목록 버전에서 영향을 검토한다. 글자 수정도 사용자의 검색 결과나 링크 식별자를 바꾸면 기능 영향이 있고, 문서 설명 오타처럼 결과가 안 바뀌는 수정과 구별해야 한다.

  1. 기존6에서 남은 가능량10-6=4person-day다. CR7 추정은2+3+1=6person-day다.

  2. 합은6+6=12로 가능10보다2person-day 초과한다. 기존 약속을 몰래 지우거나 시험1을0으로 바꿔 합계만 맞추지 않는다.

  3. 일 가용2person-day에서 완벽 병렬 하한은12/2=6작업일이다. 가용10은5일 상당이므로 같은 가정에서도1일 상당이 부족하며 의존성/검토 대기로 실제는 더 길 수 있다.
