소단원 12.1

가설·baseline·ablation

새 부품을 두 개 넣어 좋아졌다면 어느 부품 덕분이라고 말할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 정확도와 분모

  • 훈련·검증·평가 분리

  • 평균과 조건 비교

학습 목표

  • 검증 가능한 가설과 비교 기준을 적는다.

  • baseline과 ablation의 서로 다른 질문을 설명한다.

  • 조합 표에서 조건부 차이와 상호작용을 계산한다.

먼저 질문과 비교 기준을 고정한다

가설은 무엇이 어떤 조건에서 달라질지 확인 가능한 형태로 적는 예상이다. 예를 들어 같은 자료와 학습 예산에서 특징 A를 넣으면 정확도가 높아지는지 묻는다. 모든 자료와 모든 모델에서 우수하다는 주장과 이 한 조건의 질문은 범위가 다르다.

Baseline은 비교의 기준인 기존 방법이다. 약하게 설정한 기준을 이기는 것만으로 좋은 새 방법이라고 판단하기 어렵다. 자료 분할·입력 처리·평가 지표·탐색 예산을 맞추고 기준 방법도 합리적으로 설정한다. 평가 정답을 보고 계속 고른 결과는 독립 최종 평가로 부르지 않는다.

제거 실험의 조건을 밝힌다

Ablation은 제안 방법의 요소를 제거하거나 대체하여 그 조건에서 결과가 얼마나 달라지는지 보는 실험이다. AB에서 A를 빼면 B가 되므로 AB−B가 A의 조건부 차이다. baseline에서 A를 넣은 A−baseline과 같은 숫자라고 미리 가정하지 않는다.

두 요소가 함께 있을 때의 변화가 단독 변화의 합과 다르면 상호작용을 의심할 수 있다. 그러나 다른 하이퍼파라미터나 훈련 예산도 함께 바뀌었다면 그 차이를 요소 하나의 효과로 고립하지 못한다. 실제 인과 해석에는 실험 설계와 변동의 검토가 필요하다.

한 표의 차이를 보편 성질로 바꾸지 않는다

한 번의 실행에서 높은 수치를 얻었다고 모든 무작위 초기값에서도 높다고 할 수 없다. 여러 실행의 결과·평균·변동과 선택 규칙을 함께 보고한다. 오차막대가 표준편차인지 평균의 표준오차인지 신뢰구간인지도 적어야 읽는 사람이 같은 뜻으로 해석한다.

아래 표는 손으로 만든 정확도 표다. 실제 자료나 신경망 실행에서 얻은 결과가 아니다. 작은 자료에 과적합해 보는 디버깅은 코드의 일부 오류를 찾는 데 도움이 될 수 있지만 전체 방법의 일반화 성능을 증명하지 않는다.

중간 과정을 따라가는 예제

같은 조건이라고 가정한 가상 정확도는 baseline 70%, A 74%, B 73%, AB 78%다. 단독 변화, AB에서의 제거 차이와 상호작용 차이를 구하라.

  1. A 단독 변화는 74−70=4%p, B 단독 변화는 73−70=3%p다. %p는 두 백분율을 뺀 퍼센트포인트다.

  2. AB에서 A를 제거하면 B이므로 차이는 78−73=5%p다. B를 제거하면 A이므로 78−74=4%p다.

  3. 상호작용 차이는 78−74−73+70=1%p다. 이는 이 표의 산술이며 통계적으로 검증된 효과가 아니다.

A 단독 4%p, B 단독 3%p, A 제거 5%p, B 제거 4%p, 상호작용 1%p다.

종이와 본문으로 직접 해보기

AB만 77%로 바꾸면 두 제거 차이와 상호작용은 어떻게 되는가?

힌트 보기

AB−B, AB−A와 AB−A−B+baseline을 각각 계산한다.

풀이 보기

A 제거 차이는 4%p, B 제거 차이는 3%p, 상호작용은 77−74−73+70=0%p다. 한 표에서 합과 같다는 사실이 모든 조건의 독립성을 증명하지는 않는다.

오해와 반례

전체 방법이 좋아졌으므로 모든 부품이 각각 같은 만큼 기여했다.

조합과 제거의 조건부 차이가 다를 수 있다. 조건을 맞춘 표와 여러 실행의 변동을 보고 범위를 한정한다.

자기점검

AB에서 A를 뺀 비교 상대는?

답과 이유 보기

B다.

A의 존재만 바뀌는 비교를 의도한다.

78%와 70%의 차이는?

답과 이유 보기

8%p다.

백분율 값의 뺄셈이며 상대 증가율 8/70과 다르다.

평가 자료로 반복 선택한 뒤 독립 최종 평가라고 해도 되는가?

답과 이유 보기

그렇지 않다.

선택에 사용한 정보가 최종 평가로 유입된다.

가상 세 실행에서 A−baseline 차이가 −1, 2, 5%p면 평균은 2%p지만 한 실행은 낮다. 이 세 수만으로 유의성이나 신뢰구간을 선언하지 않는다. 같은 실행 조건을 짝지었는지와 무작위성·자료 표본의 변동 범위를 추가로 밝혀야 한다.

소단원 12.2

공정한 자원비교

마지막 학습은 짧지만 수백 번 탐색한 모델을 빠른 방법이라고 할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 시간과 비율

  • 학습 배치와 갱신

  • 훈련과 탐색 구분

학습 목표

  • 개별 실행과 전체 탐색 자원을 구별한다.

  • 같은 예산·품질에서 비교할 질문을 적는다.

  • 비동기 실행 시간과 실제 완료 시간을 구별한다.

자원의 범위와 단위를 정한다

계산 비용은 마지막 한 번의 학습 시간만을 뜻하지 않는다. 하이퍼파라미터 탐색·실패한 실행·예비 실험을 포함한 전체와 최종 선택된 실행을 나누어 적는다. 장치 종류와 수·메모리·시간·소프트웨어 조건이 달라지면 GPU 시간 수만으로 동일한 능력을 비교할 수 없다.

GPU 시간은 장치 수×사용 시간으로 계산하는 한 자원량이다. 두 장치를 한 시간 쓰면 2 GPU 시간이지만 벽시계 시간은 한 시간이다. 이 둘은 비용과 기다림이라는 다른 질문을 나타내며 장치 가격이나 전력의 실제 측정과도 다르다.

같은 질문에 맞는 비교를 한다

같은 계산 예산에서 품질을 비교하거나 같은 목표 품질까지 필요한 자원을 비교할 수 있다. 어느 질문인지 미리 정해야 한쪽에는 더 많은 탐색과 학습을 허용하고 숫자만 나란히 놓는 비교를 피할 수 있다. 데이터와 지표도 맞추어야 한다.

Epoch는 자료 전체를 한 번 훑는 기준이고 갱신 수와 항상 같지 않다. 자료 수·배치 크기·마지막 배치 처리·기울기 누적이 갱신 수를 바꾼다. 학습 시간뿐 아니라 배포 시 지연·처리량·메모리도 다른 목적이므로 하나의 승리라는 말로 합치지 않는다.

타이머가 잰 범위를 확인한다

GPU 호출은 CPU에 작업을 예약하고 완료 전에 돌아올 수 있다. 예약 시간만 재고 전체 연산이 빨라졌다고 말할 수 없다. 실제 측정에서는 필요한 동기화·초기 준비·반복·스레드 수·입력 크기 등을 밝혀야 한다.

아래는 가상 자원 장부와 정수 갱신 계산이다. 실제 GPU나 타이머를 실행하지 않았다. 반복 측정의 평균을 쓰더라도 분산과 측정 구간을 숨기지 않으며 준비 시간 포함 여부도 같은 규칙으로 적용한다.

중간 과정을 따라가는 예제

같은 종류의 장치를 쓴다고 가정한다. A는 탐색 8회마다 GPU 1개로 2시간, 별도의 최종 학습 1회는 GPU 2개로 3시간이다. B는 탐색 3회마다 GPU 1개로 3시간, 별도 최종 학습은 GPU 1개로 4시간이다. 탐색과 총 GPU 시간을 구하라.

  1. A 탐색은 8×1×2=16 GPU 시간, 최종은 2×3=6 GPU 시간이다. 총은 22 GPU 시간이다.

  2. B 탐색은 3×1×3=9 GPU 시간, 최종은 1×4=4 GPU 시간이다. 총은 13 GPU 시간이다.

  3. A 최종 벽시계는 3시간으로 B의 4시간보다 짧지만 총 GPU 시간은 A가 더 크다. 탐색 병렬 일정이 없으므로 총 벽시계 시간을 단정하지 않는다.

A 탐색/최종/총은 16/6/22, B는 9/4/13 GPU 시간이다.

종이와 본문으로 직접 해보기

표본 120개를 한 epoch 동안 각 한 번 쓰며 누적 없이 매 배치마다 갱신한다. 배치 크기 20과 30이면 각각 몇 번 갱신하는가?

힌트 보기

이 수는 모두 나누어떨어지므로 표본 수를 배치 크기로 나눈다.

풀이 보기

각각 120/20=6회, 120/30=4회다. 같은 한 epoch여도 갱신 수는 다르다. 이것만으로 어느 모델의 성능이 더 좋다고 판단하지 않는다.

오해와 반례

최종 학습 시간만 짧으면 탐색까지 포함한 비용도 낮다.

최종 실행과 탐색 전체 비용은 다르다. 장치 종류·수·시간과 실패한 탐색을 포함한 범위를 공개한다.

자기점검

GPU 4개를 2시간 쓴 자원량은?

답과 이유 보기

8 GPU 시간이다.

장치 수와 사용 시간을 곱한다.

8 GPU 시간이 벽시계 8시간이라는 뜻인가?

답과 이유 보기

아니다.

동시에 장치 4개를 쓰면 이 예에서는 벽시계 2시간이다.

비동기 GPU 예약만 잰 시간은 완료 시간과 같은가?

답과 이유 보기

일반적으로 아니다.

예약 반환 뒤 연산이 계속될 수 있다.

한 단계 더

가상 결과를 동일한 장치·평가 규약으로 얻었다고 가정하자. X: 정확도 80%·5 GPU 시간, Y: 82%·7 GPU 시간, Z: 79%·6 GPU 시간이라면 X는 Z보다 품질이 높고 자원이 낮다. X와 Y는 한쪽이 정확도, 다른 쪽이 자원에서 앞서므로 목표 없이 단일 순위를 강요하지 않는다. 실제 비용·전력 자료는 아니다.

무엇을 다시 확인했는지 밝힌다

재현 보고에는 대상 주장·자료 버전·분할·전처리·모델·학습 규칙·탐색·평가 지표와 환경을 적는다. 코드 공개는 중요한 경로지만 실행 의존성이나 자료가 부족하면 그 자체로 재현 성공을 보장하지 않는다. 결과 숫자뿐 아니라 어떤 질문을 확인하려 했는지가 필요하다.

원래 설정에 맞춘 반복과 일부 설정을 바꾼 변형 실험을 구별한다. 다른 분할이나 목표를 사용했다면 같은 지표 이름이어도 원래 조건을 그대로 확인한 것은 아니다. 비교할 수 있는 조건과 바뀐 조건을 숨기지 않는다.

미실행과 실행 결과를 나눈다

필수 자료를 받지 못해 학습을 시작하지 않았다면 환경이나 자료 확보가 막힌 상태다. 점수가 낮게 관측된 실패라고 적으면 안 된다. 실행한 경우에도 프로그램 오류·평가 조건 불일치·관측된 낮은 성능을 별도로 기록하고 확인된 원인과 가설을 나눈다.

Seed는 무작위 선택의 재현을 돕는 설정이지만 버전·플랫폼·CPU/GPU 차이를 모두 없애는 보장은 아니다. 결정적 연산 설정은 성능 비용을 가질 수도 있다. 관찰한 한 번의 불일치를 논문의 모든 주장이 거짓이라는 보편 결론으로 확대하지 않는다.

차이와 한계를 함께 보고한다

보고된 기준과 관측 수치의 차이를 적고 실행 수·변동·계산 예산·환경 차이를 덧붙인다. 작은 실행 수에서 평균만 나란히 놓고 통계적으로 차이가 확정됐다고 쓰지 않는다. 원문의 주장 범위와 자신의 확인 범위를 함께 적는다.

학습자에게는 아직 하지 않은 작업도 도움이 된다. 미확인 자료 버전, 실행하지 않은 모델, 다음 점검 항목을 명확히 남기면 후속 사람이 관측 사실과 예상 계획을 구별할 수 있다. 아래 기록은 가상 보고이며 실제 논문 재현 실패 사례가 아니다.

중간 과정을 따라가는 예제

가상 논문 기준은 정확도 80%다. 같은 평가 규약이라고 가정한 자체 가상 세 실행은 74%, 76%, 78%다. 평균과 기준 차이, 실행 범위를 적어라.

  1. 평균은 (74+76+78)/3=76%다. 최솟값/최댓값은 74%/78%다.

  2. 평균−기준은 76−80=−4%p다. 기준을 분모로 한 상대 차이는 −4/80=−5%다.

  3. 세 가상 실행 평균이 기준보다 낮다는 표의 사실과 환경/예산 조건 및 불확실성을 나누어 쓴다. 실제 관측이나 유의성 판단은 없다.

평균 76%, 범위 74–78%, 기준과 차이 −4%p, 상대 차이 −5%다. 이는 자체 가상 표다.

오해와 반례

같은 seed를 썼으니 다른 버전과 장치에서도 반드시 같은 결과다.

무작위 설정은 중요한 조건이지만 버전·플랫폼·비결정적 연산 차이까지 모두 보장하지 않는다. 환경과 실제 비교 범위를 기록한다.
