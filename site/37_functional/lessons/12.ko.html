소단원 12.1

작은 parser 또는 변환기

문자열에서 숫자만 뽑으면 올바른 입력 해석이 될까?

준비 개념과 학습 목표

준비 개념

  • 문자열

  • 순수 함수

  • 성공과 실패 값

학습 목표

  • 입력 문법과 범위를 정한다.

  • 실패 이유를 값으로 보존한다.

  • 해석과 변환 및 출력을 분리한다.

형식이 맞는 기록을 언제 중복으로 판정할까요?

명단에 이름이 보인다는 사실과 그 이름의 점수를 채택했다는 사실은 다르다. 실패한 입력까지 이름을 예약하면 뒤에 온 정상 수정 기록이 거절된다. 앞 본문의 점수 검증을 이름과 중복 정책까지 확장하되, 문자열의 해석과 명단의 상태 변경을 분리한다.

자체 입력은 문자열이며 전체 형식은 [A-Z]{1,2}:[0-9]{1,3}이다. 공백·소문자·부호·추가 콜론을 허용하지 않는다. 전체 형식 실패는 형식 오류, 숫자가 100보다 크면 범위 오류다. 값은 0부터 100까지다. 그 뒤에만 이미 채택한 이름인지 검사하여 중복 오류를 낸다. 정상 채택만 seen에 이름을 넣는다.

결과는 입력 위치와 함께 성공(name,score) 또는 오류(reason)로 기록한다. 위치는 1부터 센다. 부분 채택 정책은 오류를 모으며 나머지를 계속 처리한다. 이 정책은 오류 하나라도 있으면 전체 공개를 거절하는 별도 원자 배치 정책과 다르다. 아래 각 문제는 빈 seen에서 독립적으로 시작한다.

먼저 확인할 개념
  • 전체 문자열과 범위의 단계 검증

    숫자 변환 전에 형식을 확인하는 앞 본문을 이름이 포함된 기록으로 확장한다.

  • 정확성의 입력 범위와 오류 보고

    집계 값만 쓰지 않고 어느 위치가 어떤 이유로 실패했는지도 계약에 넣는다.

문법을 먼저 약속한다

parser는 입력 표현을 구조 있는 값으로 바꾸는 해석기다. 여기서는 점수 문자열 한 개를 받는다. ASCII 숫자 1개부터 3개로만 이루어지고 정수값이 0 이상 100 이하면 성공한다. 공백·부호·소수점은 허용하지 않는다. 따라서 007은 성공 7이지만 +7이나 7점은 실패다. 무엇이 올바른지는 구현 전에 이 계약이 정한다.

숫자를 찾아내는 search와 문자열 전체를 검사하는 fullmatch는 다르다. 7점에서 7만 발견하고 성공시키면 계약을 위반한다. Python의 [0-9]는 이 예제의 ASCII 숫자를 표현하고 {1,3}은 길이 범위를 나타낸다. 다른 언어권 숫자를 지원하려면 별도의 명시적 계약과 테스트를 추가한다.

실패도 정상적인 결과 값이다

parse_score는 성공이면 (True, 숫자), 실패이면 (False, 이유)를 반환한다. 문법 실패와 범위 실패를 구분하면 호출자가 안내를 결정할 수 있다. 성공 0은 실제 점수이므로 실패를 0으로 반환하면 두 뜻이 섞인다. 원래 입력을 수정하거나 출력하지 않는 계산 중심 함수를 만든다.

이 함수가 전혀 실패하지 않는다는 뜻은 아니다. 여기서는 문자열이라는 전제 아래 예상할 수 있는 입력 오류를 반환값으로 다룬다. 파일 읽기 실패나 메모리 부족까지 모두 이 결과로 해결했다고 주장하지 않는다. 외부 입출력은 별도 경계에서 처리한다.

import re

def parse_score(text):
    if re.fullmatch(r'[0-9]{1,3}', text) is None:
        return (False, '형식')
    value = int(text)
    if value > 100:
        return (False, '범위')
    return (True, value)

작은 변환을 연결한다

문자열 목록을 map으로 해석하면 각 위치에 대응하는 성공·실패 결과가 생긴다. 그 결과를 성공 값과 오류 위치로 나누고 성공 값만 집계할 수 있다. 단순히 실패 결과를 버리기보다 사용자에게 어느 입력을 다시 살펴볼지 알려주는 정보도 보존한다.

Python map은 즉시 완성된 목록이 아니라 iterator를 돌려준다. 같은 iterator를 이미 끝까지 소비한 뒤 다시 읽으면 결과가 없다. 작은 활동에서는 list로 한 번 저장해 재사용할 수 있지만 큰 입력의 메모리 비용은 뒤 소단원에서 따로 검토한다.

  1. 007은 문법이 맞고 7<=100이므로 성공 7이다.

  2. 7점은 전체 문법이 맞지 않아 형식 실패다. 101은 문법이 맞지만 범위 실패다.

조건을 바꾸어 비교하기

실패한 첫 기록이 정상 수정을 막지 않게 하기

A:101, A:7을 빈 seen에서 처리하라. 이름을 숫자 범위 검사 전에 넣는 변형과 비교하라.

  1. 정상 정책에서 첫 기록은 범위 오류이며 seen은 빈 집합으로 남는다.

  2. 둘째 기록은 성공(A,7)이고 seen은 {A}가 된다.

  3. 변형은 첫 실패 때 A를 예약하여 둘째 정상 기록까지 중복으로 거절한다. 실패의 상태 변경이 후속 결과를 바꾼다.

정상은 오류 하나와 성공 하나다. 실패 기록으로 seen을 바꾸면 정상 수정을 잃는다.

비교할 점

앞 본문의 단일 점수 판정에 실패 뒤 상태 보존이라는 후속 입력 조건을 추가한다.

부분 결과와 전체 공개 거절을 구별하기

표의 네 기록을 처리한 뒤 부분 채택 정책과 원자 배치 정책의 공개 결과를 비교하라. 원자 정책은 후보를 끝까지 검사하지만 오류가 있으면 기존 공개 명단을 그대로 둔다. 기존 명단은 빈 명단이다.

  1. 부분 채택은 A의 7과 B의 0을 공개하며 오류 위치는 2와 4다.

  2. 원자 정책은 동일한 후보 성공·오류 장부를 얻어도 오류가 있어 공개 명단을 빈 상태로 유지한다.

  3. 후보의 합계 7과 공개 합계 0은 각각 다른 상태의 값이다. 후보 7을 원자 정책의 공개 값이라고 보고하지 않는다.

부분 공개 합계는 7, 원자 공개 합계는 0이며 후보 검사 자체의 성공은 두 기록이다.

비교할 점

함수형 후보 구성은 공개 정책을 자동으로 결정하지 않는다. 공개 여부를 별도 계약으로 둔다.

연습 1 · 값과 상태 예측

빈 seen에서 C:000, C:+1, C:101, C:9의 결과와 seen 변화를 순서대로 적어라.

힌트 1

000은 세 자리 ASCII 숫자이며 값은 0이다.

힌트 2

전체 형식, 범위, 채택 이름 순으로 검사한다.

풀이와 답 확인

  1. 첫 기록은 성공(C,0)으로 seen이 {C}가 된다.

  2. 둘째는 부호 때문에 형식 오류, 셋째는 범위 오류, 넷째는 중복 오류다. 실패 때 seen은 {C}를 유지한다.

성공 1개와 형식·범위·중복 오류 각 1개이며 최종 seen은 {C}다.

0은 거짓이므로 첫 기록도 실패다.

성공 여부는 태그로 판단한다. 점수 0도 허용 범위의 정상 값이다.

연습 2 · 오류 찾아 고치기

부분 채택 집계기가 범위 오류를 성공 점수 100으로 복구한 뒤 60 이상을 두 배 하여 더한다. 입력 A:101, B:60의 정상 합과 잘못된 합을 비교하고 수정하라.

힌트 1

범위 오류는 점수가 아니다.

힌트 2

정상 성공 점수는 B의 60 하나다.

풀이와 답 확인

  1. 정상은 A를 오류 목록에 보존하고 B의 60만 선택하여 120을 얻는다.

  2. 변형은 오류를 100으로 바꾸어 200을 추가하므로 합계 320이다.

  3. 오류를 성공으로 바꾸지 말고 성공 태그인 점수만 선택한다. 오류 목록과 합계는 별도 결과다.

정상 합계는 120, 잘못된 합계는 320이다. 오류 태그를 유지한다.

흔한 오답에서 다시 생각하기

오류를 가장 큰 허용값으로 바꾸면 범위도 맞고 안전하다.

복구 값이 업무 조건을 통과해 가짜 기여를 만든다. 실패를 성공으로 재분류하는 정책은 별도 승인된 계약이 필요하다.

연습 3 · 직접 만들어 보기

같은 이름의 첫 정상 기록만 채택하는 처리기의 후보 상태와 한 단계 전이를 설계하라. 실패 입력은 이름을 예약하지 않으며 원본 문자열 목록은 변경하지 않는다.

힌트 1

seen, 채택 기록, 위치별 오류를 분리한다.

힌트 2

검증 통과 전에 후보 상태를 갱신하지 않는다.

풀이와 답 확인

  1. 후보 상태를 (seen,accepted,errors)로 두고 원본은 읽기만 한다.

  2. 전체 형식과 범위를 검사한 뒤 seen을 검사한다. 실패는 위치·이유를 errors에 추가하고 seen과 accepted를 유지한다.

  3. 성공은 seen에 이름을 넣고 accepted 끝에 이름·점수를 추가한다. 원자 공개가 필요하면 끝에서 errors의 빈 여부를 확인한다.

실패의 이름 예약을 막는 전이와 입력 순서의 성공·오류 장부를 명시한다.

흔한 오답에서 다시 생각하기

중복 여부만 먼저 검사하면 같은 정책이다.

이미 A를 채택한 뒤 A:101이 오면 범위와 중복 조건에 함께 걸린다. 검사 순서를 바꾸면 보고하는 첫 오류가 달라진다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

이름 장부를 성공 필터의 뒤에 두면 성공 점수 계산과 이름 중복 거절을 두 독립 순회로 나눌 수 있다고 주장한다. A:60, A:80에서 두 점수를 먼저 합산하는 방식의 오류를 설명하라.

힌트 1

두 기록 모두 단일 기록 검증은 통과한다.

힌트 2

단일 기록 성공과 배치에서 채택된 성공은 다른 단계다.

풀이와 답 확인

  1. 단일 검증 뒤 즉시 합산하면 120+160=280을 얻는다.

  2. 배치 정책은 첫 A만 채택하므로 두 배 합계는 120이고 둘째는 중복 오류다.

  3. seen을 포함한 순서 의존 채택 단계가 끝난 뒤 채택 점수만 집계하거나 한 단계에서 채택과 집계를 함께 수행한다.

같은 결과를 만드는 for와 map 중 어느 쪽이 항상 더 좋은가?

같은 합계가 나오면 처리 순서도 같을까요?

순수하고 종료하는 정수 함수만 쓰면 결과 값으로 루프와 파이프라인을 비교할 수 있다. 로그·예외가 들어가면 함수 호출의 시점과 순서도 관찰이다. 이 차이는 함수형이라는 이름으로 없어지지 않는다. 이번 사례는 실제 실행 대신 호출 장부를 손으로 구성한다.

입력 [60,61,80]에 술어 p는 p(x)를 로그에 남기고 x ≥ 60을 반환한다. 변환 f는 f(x)를 남기며 x가 61이면 예외 E를 발생시키고, 나머지는 2x를 반환한다. eager는 필터를 리스트로 완전히 만든 뒤 변환 리스트를 만든다. lazy는 filter와 map을 연결한 뒤 합계가 이를 소비한다. 둘 다 예외를 외부로 전파하며 정상 최종 합계를 반환하지 않는다.

순수한 별도 사례에서는 x ≥ 60인 값만 두 배 하여 더한다. 먼저 두 배 한다면 기준도 120 이상으로 바꾸어야 선택 집합이 같다. 하지만 제외될 값까지 변환하는 방식은 효과와 예외까지 같은 계약이 되는 것은 아니다.

먼저 확인할 개념
  • 접두 합계 불변식과 순수성 조건

    루프와 파이프라인의 값 동등성을 호출 순서까지 확대할 수 있는 조건을 확인한다.

  • 반복자 한 번 소비와 재사용

    두 결과 목록을 얻으려다 같은 반복자를 앞 순회에서 소진하는 오류를 연결한다.

비교 전에 같은 문제로 맞춘다

입력은 이미 검증된 정수 점수 목록이다. 60 이상만 통과 점수로 선택하고 각 값에2를 곱해 합한다. 이 소단원은 만점 제한 없이 변환 숫자를 합치는 가상 규칙이다. 한 해법만 파싱 오류를 무시하거나 값을100에 제한하면 같은 문제의 비교가 아니다.

명령형은 순회하며 조건을 확인하고 누적 변수 total을 갱신한다. 함수형 표현은 선택 filter, 변환 map, 집계 reduce의 관계를 드러낸다. 줄 수나 영어 함수 이름보다 조건과 결과가 계약을 만족하는지가 먼저다.

누적 변수의 의미를 추적한다

명령형 순회에서 k개 항목을 처리한 뒤 total은 그 접두 부분에서60 이상인 값의 두 배 합이다. 처음0이고 각 새 항목이60 이상이면 두 배를 더하므로 이 불변식이 유지된다. 마지막에는 전체 합이 된다. 지역 누적 변수 변경 자체가 잘못된 설계는 아니다.

reduce는 왼쪽부터 누적값과 새 값을 결합한다. 합의 initial을0으로 두면 빈 입력에서도 결과0이다. 순수한 계산과 정수 합을 쓰므로 여기서는 단계 연결과 명령형 순회의 결과가 같다. 뺄셈과 나눗셈에서는 순서나 괄호를 임의로 바꾸면 안 된다.

from functools import reduce

def imperative(scores):
    total = 0
    for score in scores:
        if score >= 60:
            total += 2 * score
    return total

def pipeline(scores):
    passed = filter(lambda x: x >= 60, scores)
    doubled = map(lambda x: 2 * x, passed)
    return reduce(lambda a, b: a + b, doubled, 0)

같은 숫자와 같은 행동은 다르다

단계 함수가 로그를 출력하거나 공유값을 바꾸면 연결·저장 방식에 따라 효과 순서가 달라질 수 있다. 모든 필터를 먼저 목록으로 만들면 조건 효과가 먼저 모이고 지연 iterator를 이어 소비하면 각 항목의 조건과 변환이 교차한다. 최종 합만 비교하면 이 차이를 놓친다.

효과가 없는 조건·변환과 명시적 입력값을 사용하면 분석 범위를 줄일 수 있다. 그래도 언어 구현, 데이터 크기, 팀의 읽기 경험이 선택에 영향을 준다. 기능적으로 같은 결과를 확인한 뒤 실제 측정이 필요하면 입력과 환경을 고정해서 수행한다.

합계만 남기는 스트림도 오류를 모두 반환하면 공간이 일정할까요?

합계를 하나의 정수로 축약하는 것과 출력 전체가 정수 하나인 것은 다르다. 이번 보고기는 성공 합계와 모든 오류 기록을 함께 반환한다. 입력이 잘못될수록 오류 목록이 커지므로 중간 성공 리스트를 없앤 뒤에도 전체 보존 공간은 입력 길이와 무관하지 않다.

자체 참조 칸 모형은 성공 중 60 이상인 기록 k개, 오류 m개를 쓴다. 정책 L은 선택 리스트 k칸과 변환 리스트 k칸을 동시에 유지하고 오류 목록 m칸을 반환까지 둔다. 정책 S는 선택·변환 리스트를 만들지 않고 합계 하나와 오류 목록 m칸만 둔다. 입력·seen·개별 객체·정수 비트·리스트 용량·헤더는 이 비교의 계수에서 제외하되 실제 보고에서는 제외 사실을 반드시 적는다.

기록마다 판정 1회, 선택된 기록마다 변환 1회와 누적 1회를 세는 추상 작업 모형을 별도로 둔다. 입력 n개에서 n+2k다. 문자열 길이·정규식 비용·이름 장부 접근·오류 저장 비용은 이 식의 단위에 포함하지 않는다. 같은 추상 작업 수가 실제 시간이나 메모리 바이트가 같다는 뜻은 아니다.

먼저 확인할 개념
  • 연산 횟수와 참조 수의 모형 경계

    앞 본문의 n+2k와 두 리스트 참조 수를 오류 출력이 있는 보고기로 확장한다.

  • 성공·실패 태그와 위치 보존

    오류를 출력에서 지우면 공간을 줄이는 대신 보고 계약 자체를 바꾼다.

비용은 무엇을 세는지부터 정한다

n개의 검증된 점수에 조건 검사를 한 번씩 하고 통과 k개에 두 배 연산과 누적을 한 번씩 한다. 연산별 단위 비용을 같다고 둔 추상 모델에서는 n+2k회다. 이 숫자는 Python 함수 호출, 메모리 할당, CPU와 입출력 비용을 모두 반영한 실제 시간은 아니다.

단계마다 새 목록을 저장하면 선택 목록k개와 변환 목록k개 등 중간 저장 공간이 늘어난다. iterator를 연결하고 합 하나만 남기면 이 예제의 중간 상태는 입력 저장을 제외해 일정 개수다. 최종 결과 자체가 목록이라면 그 출력 공간까지 없어지는 것은 아니다.

정확성의 작은 근거를 만든다

계약 표에는 정상 입력,60의 바로 아래/해당 값/바로 위, 빈 입력과 잘못된 문자열을 넣는다. 검증된 정수 집계와 앞 소단원 파서를 분리하면 어떤 층의 오류인지 설명하기 쉽다. 작은 예제 통과는 전 입력의 형식적 증명과 다르고 큰 입력에서의 자원 한계도 따로 확인한다.

종이 불변식과 테스트 결과는 다른 증거다. 직접 실행하지 않았다면 기대 결과만 작성하고 실행했다고 표시하지 않는다. 재현 가능한 보고는 구현 버전, 입력 계약, 예상값, 실제 실행 여부, 측정 조건과 남은 검증을 분리한다. 초보 독자도 결과 표를 따라갈 수 있게 쓴다.

효과를 경계에 모으고 선택 이유를 쓴다

파일 읽기와 오류 안내는 바깥 층이 맡고 중심 계산은 값과 결과로 연결하면 동일 입력을 종이에 재현하기 쉽다. 로그나 오류를 반환 데이터로 보존할 수도 있지만 실제 출력 시점과 저장 정책은 별도 선택이다. 모든 프로그램을 효과 없이 만들 수 있다는 주장이 아니다.

최종 보고에는 왜 이 문제에서 iterator 연결 또는 명령형 순회를 골랐는지와 어느 입력에서 비교했는지를 적는다. 손 계산으로는 비용 모형과 예상 정답을 말하고 실제 속도 우위는 측정 후에만 말한다. 사용자에게 읽기 어려운 짧은 표현을 무조건 좋은 설계라고 평가하지 않는다.
