소단원 5.1

lexical scope

함수를 만든 곳과 부른 곳에 같은 이름이 있으면 어느 값을 읽을까?

준비 개념과 학습 목표

준비 개념

  • let은 이름에 값을 묶는다.

  • 함수의 매개변수와 바깥 이름은 다르다.

  • 중첩된 범위에서 이름이 가려질 수 있다.

학습 목표

  • 정의 위치에 따른 이름 연결을 추적한다.

  • shadowing과 변경을 구별한다.

  • lexical과 dynamic 모형의 다른 결과를 설명한다.

같은 x를 매개변수로 쓰면 바깥 함수의 x도 바뀔까?

앞 본문은 정의할 때의 offset과 호출할 때의 offset을 구별했다. 여기서는 let x=6, let f=fun y->x+y, let g=fun x->f x, let x=20을 순서대로 둔 뒤 g 2를 계산한다. 이 식들은 중첩된 let의 설명용 나열이며 서로 다른 binding을 X1, X2, X3으로 표시한다. X1은 6, X2는 g의 매개변수, X3은 마지막 20이다. f 본문의 자유 x는 X1에 연결되고 g 본문의 x는 X2에 연결된다.

g 2는 자기 매개변수 X2를 2로 두고 f에 값 2를 전달한다. f는 자기 매개변수 y에 2를 받고 정의 환경의 X1에서 6을 읽어 8을 만든다. 호출 스택 가까이에 같은 철자 x가 있다고 f의 연결을 옮기지 않는다. 비교용 dynamic 모형에서는 g의 호출 환경에 있는 x=2를 f가 찾는다고 정하므로 결과는 4다. 이것은 OCaml 실행 결과가 아니라 범위 규칙을 바꾼 별도 종이 비교다.

매개변수 y를 z로 바꾸면서 그 매개변수에 연결된 사용만 함께 바꾸면 fun z->x+z로 같은 뜻을 보존한다. 그러나 fun x->x+x로 바꾸면 원래 자유 x까지 새 매개변수에 포획한다. 이름 변경의 안전 조건은 새 이름이 바깥 자유 이름을 가로채지 않는 것이다. 아래 각 예제·과제는 독립된 원래 식에서 시작하며 작은 정수와 순차 계산만 사용한다.

먼저 확인할 개념
  • 정의 환경과 shadowing

    이름의 철자 대신 선언별 연결을 추적한다.

  • 코드와 환경의 쌍

    f 호출은 g의 전체 환경을 대신 사용하지 않는다.

1. 이름이 연결되는 문맥

lexical scope는 프로그램의 문법적 중첩과 이름을 선언한 위치에 따라 그 이름이 가리키는 binding을 정하는 규칙이다. 함수 본문의 매개변수가 아닌 offset 같은 이름도 함수가 정의된 문맥에서 연결된다. 나중에 함수를 부르는 문맥에 같은 이름이 생겼다고 그 연결을 새로 선택하지 않는다.

OCaml의 let offset=40 은 예전 binding의 값을 40 으로 수정하는 명령이 아니다. 새 binding이 같은 이름을 가려 이후 그 범위에서 직접 offset을 쓰면 40 을 찾는다. 기존 함수가 연결한 offset=7 binding은 여전히 구별된다. 이름과 binding을 따로 번호 매겨 읽으면 같은 철자 때문에 생기는 혼동을 줄일 수 있다.

2. 정의한 곳의 이름을 표시하기

다음은 단일 .ml 파일에 둘 수 있는 자체 OCaml 예제다. 작은 정수만 사용하며 정수 범위를 넘는 계산은 없다. OCaml 컴파일러와 toplevel로 실제 실행하지 않았다. 예상 출력은 언어의 lexical 규칙을 종이에서 적용한 값이다.

첫 offset binding을 o1=7, 뒤 binding을 o2=40 으로 적는다. shift의 본문 x+offset에서 offset은 o1 에 연결된다. shift 3 을 호출할 때 x=3 이므로 3+7=10 이다. o2 가 생긴 뒤라고 3+40=43 을 계산하는 규칙은 이 OCaml 예제의 규칙이 아니다.

let result =
  let offset = 7 in
  let shift = fun x -> x + offset in
  let offset = 40 in
  shift 3

let () = Printf.printf "%d\n" result

3. 다른 범위 규칙과 비교하기

dynamic scope라는 별도 모형은 함수 적용 시점의 호출 환경에서 자유 이름을 찾는다. 같은 종이 식을 그 모형으로 계산하면 마지막 offset 40 을 찾아 43 을 얻을 수 있다. 이 비교는 OCaml이 43 을 반환한다는 주장도, 모든 언어가 lexical 규칙만 쓴다는 주장도 아니다. 구체 언어와 기능의 규칙을 확인해야 한다.

자유 이름은 함수 본문 안에서 그 함수의 매개변수나 내부 선언으로 묶이지 않은 이름이다. fun x -> x+offset에서 x는 매개변수로 묶이고 offset은 자유 이름이다. fun offset -> offset+1 이라면 그 offset은 새 매개변수에 묶인다. 일관된 이름 바꾸기는 의미를 유지할 수 있지만 자유 이름을 우연히 새 binding에 포획하도록 바꾸면 의미가 달라진다.

중간 과정을 따라가는 예제

본문 코드의 result를 계산하고, 호출 환경에서 자유 이름을 찾는 별도 dynamic 모형의 결과와 비교하라.

  1. 첫 let에서 offset의 binding o1 을 7 로 기록한다.

  2. shift 정의 시 본문의 자유 offset은 o1 에 연결되고 x는 매개변수로 남는다.

  3. 뒤 let은 새로운 o2=40 을 만들고 호출하는 범위의 이름을 가린다.

  4. lexical 적용은 함수의 연결 o1 과 x=3 을 사용하여 10 을 얻는다.

  5. 별도 dynamic 모형은 호출 환경 o2 를 찾아 43 을 얻는다. 두 모형을 실행 결과로 혼합하지 않는다.

OCaml lexical 결과 10, 별도 dynamic 종이 모형 43 이다. 실제 출력은 관찰하지 않았다.

조건을 바꾸어 비교하기

호출자 매개변수가 자유 이름을 대체하지 않는다

원래 식에서 g 2와 f 3, 마지막 직접 x를 계산하라. 비교 dynamic 모형의 g 2도 적어라.

  1. g 2는 f 2를 호출하고 lexical f는 6+2=8을 만든다.

  2. f 3은 정의 연결 X1의 6을 읽어 9다. 마지막 직접 x는 X3의 20이다.

  3. 비교 dynamic g 2에서는 호출 환경 x=2를 읽어 2+2=4다.

lexical g 2는 8, f 3은 9, 직접 x는 20이다. 별도 dynamic g 2는 4다.

비교할 점

호출자의 x와 마지막 바깥 x 중 무조건 최신 값을 고르는 설명은 선언 연결을 잃는다.

매개변수 이름 바꾸기가 포획을 만든다

f를 각각 fun z->x+z와 fun x->x+x로 바꾼 독립 대안에서 g 2를 비교하라.

  1. 첫 대안의 자유 x는 계속 X1이고 z는 인수 2라서 8이다.

  2. 둘째 대안에는 자유 x가 없어지고 두 x 모두 새 매개변수 2에 연결된다.

  3. 둘째 대안은 4다. 이름만 바꿨다고 생각했지만 자유 사용의 연결도 바뀌었다.

안전한 이름 변경은 8을 유지하지만 포획을 만든 변경은 4다.

비교할 점

계산값의 우연한 일치가 아니라 모든 해당 사용의 선언 연결이 보존되는지 확인한다.

종이와 본문으로 직접 해보기

shift를 fun offset -> offset+2 로 바꾸고 shift 3 을 호출하면 결과는? 바깥 7 과 40 중 하나를 더하는지 설명하라.

힌트 보기

본문 offset의 가장 가까운 선언은 함수 자신의 매개변수다.

풀이 보기

3+2=5 다. 그 offset은 자유 이름이 아니라 매개변수 binding이다. 바깥 o1/o2 를 읽지 않는다. 이름이 같아도 어떤 선언에 연결되었는지를 먼저 표시한다.

오해와 반례

가장 나중에 쓴 같은 이름의 값이 모든 기존 함수 안에서도 쓰인다.

shift는 정의된 환경의 offset 7 을 써 10 을 반환하는 반례다. 뒤 let40 은 shadowing이며 예전 불변 binding 수정이 아니다. mutable ref의 셀 변경은 다른 개념이고 다음 소단원에서 따로 다룬다.

연습 1 · 값과 상태 예측

g의 매개변수를 z로 바꾸어 fun z->f z로 정의한다. 나머지는 원래 식이다. g 2와 g 5를 예측하고 마지막 x=20이 미치는 영향을 설명하라.

힌트 1

f의 자유 x에서 연결 화살표를 먼저 그린다.

힌트 2

g의 새 z는 f에 전달할 값만 정한다.

풀이와 답 확인

  1. g 2는 f 2이므로 6+2=8이다.

  2. g 5는 f 5이므로 6+5=11이다.

  3. 뒤의 X3은 직접 이름 찾기에만 적용되고 f의 X1을 수정하지 않는다.

결과는 각각 8과 11이며 마지막 x의 새 binding은 영향을 주지 않는다.

흔한 오답에서 다시 생각하기

g를 부른 위치의 x가 20이므로 22와 25다.

그 결과는 f의 정의 연결을 버린 다른 규칙이다. X1에서 f 본문으로 향한 화살표를 복원한다.

연습 2 · 오류 찾아 고치기

잘못된 설명은 fun y->x+y의 y를 x로 바꾸어 fun x->x+x를 만들면서 의미를 보존했다고 한다. 어떤 사용이 달라졌으며 안전하게 고치려면?

힌트 1

함수 본문에서 자유 이름과 매개변수를 다른 색으로 표시한다.

힌트 2

바깥 x와 겹치지 않는 새 매개변수를 선택한다.

풀이와 답 확인

  1. 원래 첫 x는 바깥 X1이고 y만 함수 매개변수다.

  2. 수정 뒤 두 x가 모두 새 매개변수에 묶여 첫 x의 연결이 달라졌다.

  3. fun z->x+z로 쓰면 자유 x를 유지하고 y의 사용만 z로 바꾼다.

포획을 피하는 z 변경은 g 2의 8을 유지한다.

흔한 오답에서 다시 생각하기

본문에 같은 이름을 일관되게 쓰면 모든 변경은 안전하다.

철자 일관성에 더해 자유 이름의 포획이 없어야 한다. 선언별 사용을 바꿔야 한다.

연습 3 · 직접 만들어 보기

함수 h는 정의 바깥의 정수 x=6과 인수 y를 더한다. 호출자도 x라는 매개변수를 가져야 한다. 이름을 바꾸지 않고 lexical 선언 연결 표로 h와 호출자 k를 설계하고 k 5를 계산하라.

힌트 1

h는 fun y->x+y이고 k는 fun x->h x로 둘 수 있다.

힌트 2

서로 같은 철자의 두 x에 다른 선언 ID를 붙인다.

풀이와 답 확인

  1. 바깥 x를 X1, k의 매개변수를 K1로 표기한다. h의 자유 x는 X1에 연결한다.

  2. k 본문의 x는 K1에 연결되어 값 5를 h의 y로 전달한다.

  3. h는 X1의 6과 y의 5를 더한다.

k 5는 11이다. 같은 철자를 금지하지 않아도 선언 연결을 보존할 수 있다.

흔한 오답에서 다시 생각하기

서로 다른 함수가 x라는 이름을 쓰면 언제나 충돌한다.

범위 규칙은 각 사용의 선언을 구별한다. 이름의 중복 자체가 포획은 아니다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

원래 X1을 0으로 바꾸고 g 0을 계산하면 lexical과 비교 dynamic 모형 모두 0이다. 이 한 관찰로 두 규칙이 같다고 증명할 수 있는가? 구별 입력을 구성하라.

힌트 1

같은 결과와 같은 규칙은 다른 명제다.

힌트 2

바깥 값과 g 인수의 차이가 결과에 나타나게 한다.

풀이와 답 확인

  1. X1=0, 인수 0에서는 양쪽 모두 0+0이라 우연히 같다.

  2. 같은 X1=0에서 g 2를 쓰면 lexical은 0+2=2, dynamic은 2+2=4다.

  3. 한 입력의 일치는 모든 호출 환경에 관한 등식이 아니다.

g 2가 두 규칙을 구별한다. 한 결과만으로 환경 선택 규칙을 결정하지 않는다.

소단원 5.2

환경과 closure

바깥 함수가 끝난 뒤에도 반환된 함수는 어떻게 그때의 값을 사용할까?

준비 개념과 학습 목표

준비 개념

  • 자유 이름은 정의 환경에 연결된다.

  • 함수도 값으로 전달·반환할 수 있다.

  • ref는 변경 가능한 셀을 가리킨다.

학습 목표

  • 코드와 환경의 쌍으로 closure를 설명한다.

  • 반환된 함수의 독립 환경을 추적한다.

  • 불변 binding 보존과 mutable 셀 공유를 구별한다.

함수 두 개를 반환하면 상태도 두 개가 생길까?

앞 본문은 생성 호출마다 새 셀을 만들 때 카운터가 독립적이라고 설명했다. 새 factory는 호출마다 정수 셀 c=0을 하나 만들고 두 함수 inc와 read를 반환한다. inc()는 c에 1을 더한 뒤 새 값을 반환하고 read()는 변경 없이 현재 c를 반환한다. 한 쌍의 두 함수는 같은 셀을 포획한다. factory를 두 번 호출해 얻은 쌍 P와 Q 사이에는 셀이 공유되지 않는다.

P의 inc를 다른 이름 alias로 묶는 것은 factory를 다시 부르는 일이 아니다. alias()도 P의 기존 셀을 증가시킨다. 반면 P의 read()를 호출해 얻은 정수 snapshot은 그때의 내용 값이다. snapshot 자체는 이후 셀 변경을 따라 움직이지 않는다. 함수 값을 보존하는 이름과 함수 호출로 얻은 정수를 같은 방식으로 취급하지 않는다.

이것은 생성·증가·조회 순서를 명시한 순차 손모형이다. 모든 숫자는 범위 초과 없는 작은 정수이고 ref 할당 실패·동시 호출은 다루지 않는다. 코드와 최소한의 자유 연결이 필요하다는 의미를 설명하며, 특정 구현에서 몇 바이트 환경이 생기는지나 즉시 회수되는지는 주장하지 않는다. 각 문제의 P와 Q는 다시 새 셀에서 시작한다.

  • 반환 함수와 셀 공유

1. 함수가 들고 가는 문맥

closure는 함수의 코드와 자유 이름을 해석할 정의 환경을 함께 보존하는 개념이다. 함수가 매개변수만 읽으면 단순하지만, 반환된 함수가 바깥 매개변수 offset을 사용하면 해당 호출에서의 연결이 필요하다. 언어 구현은 이런 연결이 필요한 동안 사라지지 않도록 표현한다.

종이 표기로〈본문 x+offset,환경 offset→5〉처럼 적을 수 있다. 이것은 설명용 표기이며 OCaml 소스 문법이 아니다. 구현이 무조건 전체 환경을 통째로 복사한다거나 특정 메모리 주소를 항상 사용한다는 주장도 아니다. 최적화와 표현 방식은 달라도 lexical 의미를 보존해야 한다.

2. 같은 코드와 다른 환경

make_shift 5 와 make_shift 9 는 같은 구조의 함수 본문을 반환하지만 offset의 연결이 다르다. a 4 는 4+5=9, b 4 는 4+9=13 이다. make_shift를 호출하던 순간의 지역 이름 범위를 벗어났다는 이유로 offset이 undefined가 되지는 않는다. 필요한 환경이 반환 함수에 남아 있다.

다음은 OCaml 단일 .ml 파일용 자체 예제이며 실제 컴파일/실행하지 않았다. 첫 출력 예상은 9 13 이다. 이후 ref 예제의 cell은 하나의 셀이고 live는 그 셀 연결을 보존한다. 처음 내용 2 에서 live3 은 5, 내용 8 로 변경한 뒤 live3 은 11 이다. 출력 순서를 명시하려고 first,대입,second를 순차 let 정의로 분리했다.

let make_shift offset = fun x -> x + offset
let a = make_shift 5
let b = make_shift 9
let () = Printf.printf "%d %d\n" (a 4) (b 4)

let cell = ref 2
let live x = x + !cell
let first = live 3
let () = cell := 8
let second = live 3
let () = Printf.printf "%d %d\n" first second

3. 보존은 값의 영구 동결이 아니다

OCaml 이름 binding은 불변이지만 binding이 가리키는 ref 셀 내용은 변경할 수 있다. closure가 cell의 참조를 보존하면 같은 셀을 나중에 읽어 바뀐 내용을 관찰할 수 있다. 모든 자유 이름의 값을 함수 생성 때 깊은 복사로 얼린다고 설명하면 mutable 셀 사례를 틀리게 읽는다.

독립 카운터를 만들려면 카운터 생성 함수 호출마다 새로운 ref를 할당할 수 있다. 반대로 생성 함수 밖 ref 하나를 모든 함수가 읽으면 상태를 공유한다. 환경에 오래 남는 참조가 큰 객체의 수명을 늘릴 수도 있으며 공유 상태를 읽는 closure가 항상 순수 함수인 것은 아니다. 동시 호출은 이 순차 종이 예제의 보장에 포함되지 않는다.

읽기와 증가를 한 쌍의 환경으로 추적한다

소단원 5.3

currying·partial application

인수 세 개를 받는 함수를 한 개씩 넘기면 중간에 무엇이 남을까?

준비 개념과 학습 목표

준비 개념

  • 함수는 다른 함수를 결과로 반환할 수 있다.

  • 곱셈과 덧셈 순서를 안다.

  • tuple은 여러 값을 묶은 하나의 값이다.

학습 목표

  • 커리 함수의 중간 타입과 값을 추적한다.

  • 커링 변환과 부분 적용을 구별한다.

  • 인수 순서·효과 발생 시점의 조건을 설명한다.

부분 적용한 순간에 로그가 남아야 할까, 마지막 인수에서 남아야 할까?

앞 본문의 price는 순수한 units·rate·fee 계산이었다. 먼저 새 순수 식 subtract x y=x−y를 쓴다. subtract 10은 나머지 y를 받아 10−y를 계산하는 함수다. 10을 오른쪽 인수로 고정하려면 fun x->subtract x 10이 필요하다. 부분 적용은 비어 있는 임의 위치를 자동으로 채우는 표기가 아니다.

이제 순차 효과 모형 A는 첫 x 적용에서 로그 Create(x)를 남기고 fun y->x−y를 반환한다. 모형 B는 첫 x 적용에서는 로그를 남기지 않고, 반환 함수가 y를 받을 때 Use(x,y)를 남기고 x−y를 계산한다. 각각 x=10으로 얻은 함수를 y=3과 y=4에 순서대로 적용하면 값 7과 6은 같아도 로그의 시점과 횟수는 다르다. 이 모형의 순서는 별도 let과 순차 호출로 고정하며 OCaml의 모든 인수 식 평가 순서를 가정하지 않는다.

단순 uncurry로 A를 감싼 함수 U(x,y)=A x y는 호출마다 첫 적용도 다시 수행한다. U(10,3)과 U(10,4)는 Create 로그를 두 번 남긴다. 반면 A 10을 한 번만 부분 적용해 재사용하면 Create는 한 번이다. 함수 형태의 변환과 중간 함수 재사용 정책은 서로 다른 선택이다. 아래 각 대안은 새 빈 로그에서 독립적으로 시작하고 실제 언어 실행은 하지 않는다.

먼저 확인할 개념
  • 커리 타입과 인수 위치

    화살표의 남은 타입과 고정한 인수의 위치를 같이 적는다.

  • 중간 함수의 환경

    같은 x를 포획한 함수를 재사용하는 것과 새로 만드는 것을 구별한다.

1. 반환값이 다시 함수인 형태

커리 함수는 인수를 차례로 받고 중간 결과로 나머지를 받는 함수를 반환하는 형태다. price : int -> int -> int -> int는 int -> (int -> (int -> int))로 읽는다. 함수 적용 price 3 6 2 는 ((price 3)6)2 로 읽는다. 타입 화살표의 오른쪽 결합과 적용의 왼쪽 결합은 방향이 다르다.

tuple_price : int*int*int -> int는 세 정수를 묶은 tuple 하나를 받는다. tuple의 일부만 건네 자동으로 나머지 함수를 얻는 것은 이 타입의 호출 방식이 아니다. tuple 입력을 커리 형태로 감싸거나 반대로 감싸는 변환이 currying/uncurrying이다. 이미 주어진 함수에 일부 인수를 고정해 새 함수를 얻는 행동이 partial application이며 두 개념은 관련 있지만 동일한 질문은 아니다.

2. 무엇을 고정하고 무엇을 남기는가

자체 price는 units*rate+fee를 계산한다. price 3 은 units3 을 포획하고 rate와 fee를 기다리는 함수다. 여기에 6 을 적용한 six_each는 fee만 기다린다. six_each 2 는 3*6+2=20 이다. 중간 함수가 20 이라는 최종 숫자를 이미 반환했다고 말하면 타입과 값을 혼동한다.

다음 단일 OCaml .ml 파일 예제는 컴파일/실행하지 않았다. 작은 정수만 쓰며 overflow 없는 범위다. with_fee_two는 fixed_fee2 에서 fee2 를 먼저 고정한다. with_fee_two 3 6 도 20 이다. 원래 price에서 fee는 세 번째 인수이므로 price 2 라고만 쓰면 fee2 고정이 아니라 units2 고정이다. 고정할 위치를 맞추려고 wrapper의 인수 순서를 정했다.

let price units rate fee = units * rate + fee
let at_three = price 3
let six_each = at_three 6
let tuple_price (units, rate, fee) = units * rate + fee
let fixed_fee fee units rate = tuple_price (units, rate, fee)
let with_fee_two = fixed_fee 2
let () = Printf.printf "%d %d\n" (six_each 2) (with_fee_two 3 6)

3. 계산을 언제 하는지 명시하기

본문의 함수들은 순수하고 종료하므로 중간 적용의 설명을 값 등식으로 추적하기 쉽다. 하지만 함수 생성과 본문 실행을 항상 아무 비용도 없다고 주장하지 않는다. 또한 부작용을 가진 함수를 커리 형태로 다시 작성하면 효과가 바깥 적용에서 발생하는지, 모든 인수를 받은 뒤 발생하는지에 따라 관찰이 달라질 수 있다.

예를 들어 외부 로그를 한 줄 남기고 fun y -> x+y를 반환하는 모형은 첫 x 적용 시 로그를 남긴다. 로그를 안쪽 함수 본문에 두면 y를 적용할 때마다 남긴다. 따라서 같은 최종 합만으로 변환이 모든 맥락에서 동등하다고 결론 내리지 않는다. 부분 적용한 함수의 이름·인수순서·남은 타입을 함께 적으면 사용자가 무엇을 설정했는지 이해하기 쉽다.

price 3, at_three 6, six_each 2 의 중간 타입과 최종 값을 구하고 tuple_price(3,6,2)와 비교하라.

  1. price 타입은 int→int→int→int다.

  2. price 3 은 units 3 을 고정해 int→int→int 타입의 함수를 반환한다.

  3. at_three 6 은 rate 6 까지 고정하여 int→int 타입의 함수 six_each를 만든다.

  4. six_each 2 는 fee 2 를 받아 3*6+2=20 을 계산한다.

  5. tuple_price는한 tuple (3,6,2)을 받아 20 을 계산한다. 같은 결과지만 입력의 구조와 중간 적용 가능성이 다르다.

중간 타입 int→int→int, int→int, 최종 int 20 이다. tuple 입력도 20 이지만 price 3 과 같은 부분 적용 경로는 자동 제공하지 않는다.

조건을 바꾸어 비교하기

왼쪽 고정과 오른쪽 고정의 부호가 다르다

left=subtract 10과 right=fun x->subtract x 10을 만든다. 각각 입력 3의 결과와 타입을 적어라.

  1. subtract는 int→int→int다. left는 첫 인수를 10으로 고정한다.

  2. left 3은 10−3=7이다. right 3은 3−10=−7이다.

  3. 둘 다 int→int지만 어느 인수를 고정했는지 다르다.

left 3은 7, right 3은 −7이며 같은 함수 타입만으로 두 계약이 같지는 않다.

비교할 점

덧셈의 우연한 교환 성질 대신 뺄셈으로 인수 위치 차이를 드러낸다.

중간 함수 재사용과 tuple 호출을 비교한다

A 10을 한 번 만들어 y=3,4로 재사용하는 경우와 U(10,3), U(10,4)를 각각 호출하는 경우의 값과 로그를 비교하라.

  1. 재사용 대안은 첫 단계 A 10을 한 번만 수행한다.

  2. U는 매 호출마다 A 10과 다음 적용을 수행한다.

  3. 양쪽 값은 7과 6이지만 Create 횟수는 1과 2다.

동일한 두 정수 결과라도 생성 효과 관찰은 다르다.

다른 문제에 적용하기

순차 견적 모형의 공유 정수 셀 rate는 처음 4다. 세 factory는 모두 unit을 받고 int→int→int 함수를 반환한다. S는 factory 호출 때 r=!rate를 읽고, 그 뒤 units와 fee를 받아 units*r+fee를 계산한다. E는 factory에서는 읽지 않고 첫 units 적용에서 r=!rate를 읽어 보존한 뒤 fee를 기다린다. L은 factory와 units 단계에서는 읽지 않고 마지막 fee 적용에서 !rate를 읽는다. (1) rate=4에서 세 factory를 한 번씩 호출한다. (2) 같은 셀을 7로 바꾼 뒤 각 함수에 units=3을 적용한다. (3) 셀을 9로 바꾼 뒤 각 중간 함수에 fee=2를 적용한다. 각 결과와 읽기 시점, 단계별 남은 타입을 적어라. 이후 마지막 중간 함수들을 다시 fee=1로 호출하면 무엇인가? 마지막 let rate=ref 100으로 이름을 가리는 별도 변경을 그 재호출 직전에 추가하면 기존 세 함수의 연결이 바뀌는지도 설명하라. 작은 정수·순차 모형이며 실제 견적/언어/학생 실행은 없다. 세 설계 모두 마지막에는 units에 각 설계에서 읽은 rate 값을 곱하고 fee를 더한다.

힌트 1

읽기 동작은 셀의 참조를 포획하는 일과 다르다. S/E의 r은 읽어서 보존한 정수다.

힌트 2

세 단계의 남은 타입과 읽은 rate의 값을 각각 표기한다. 새로운 ref binding은 기존 셀의 내용 대입이 아니다.

풀이와 답 확인

  1. factory 뒤 세 함수의 타입은 int→int→int다. S만 이때 정수 4를 읽는다. E/L은 기존 rate 셀의 연결을 보존하지만 아직 내용을 읽지 않는다.

  2. units=3 적용 뒤 타입은 각각 int→int다. E는 이때 정수 7을 읽어 보존한다. S의 r은 4로 유지되고 L은 여전히 셀을 마지막에 읽도록 남긴다.

  3. fee=2 적용은 int를 반환한다. S는 3*4+2=14, E는 3*7+2=23, L은 현재 내용 9를 읽어 3*9+2=29다.

  4. 같은 중간 함수에 fee=1을 다시 적용하면 S는 13, E는 22, L은 28이다. L은 다시 셀을 읽지만 기존 내용은 9로 유지되어 있다.

  5. 재호출 직전에 let rate=ref 100으로 새 이름을 가려도 기존 함수가 포획한 연결은 옛 셀이다. S와 E의 정수도 그대로이고 L은 옛 셀의 9를 읽는다. S의 결과는 13, E의 결과는 22, L의 결과는 28로 유지된다. 새 binding과 옛 셀 내용에 100을 대입하는 일을 혼동하지 않는다.

첫 최종 결과는 S가 14, E가 23, L이 29다. fee를 1로 주는 재호출은 S가 13, E가 22, L이 28이다. factory, units 적용, fee 적용 단계의 읽기 시점과 보존 대상이 다르며 새 rate 이름의 shadowing은 기존 연결을 바꾸지 않는다.

해결한 뒤 점검할 것

  • 세 단계의 남은 타입과 정수 결과를 분리해 적는다.

  • S와 E가 보존한 정수와 L이 포획한 옛 셀을 구별하고 S의 14, E의 23, L의 29를 계산한다.

  • 재사용한 함수의 결과가 S는 13, E는 22, L은 28인 이유를 읽기 시점으로 설명한다.

  • 새 ref binding의 가리기와 같은 셀 내용 변경을 구별하고 실제 견적·학생 검증으로 확대하지 않는다.
