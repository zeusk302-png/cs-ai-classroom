소단원 2.1

product·sum type

스위치와 소리 높이를 함께 갖는 경우와 둘 중 하나만 갖는 경우는 값이 몇 개일까?

준비 개념과 학습 목표

준비 개념

  • 자료형은 허용 값의 구조를 정한다. lamp는 On 또는 Off, tone은 Low·Mid·High 중 하나다. 이 단원은 유한하고 정상 구성된 값만 세며 발산·예외를 값 개수에 넣지 않는다.

  • 순서쌍 (a,b)는 첫째와 둘째 성분을 함께 갖는다. 태그는 값이 어느 경우인지 나타내는 생성자 이름이다.

학습 목표

  • product와 태그 있는 sum의 구조를 구별한다.

  • 유한 경우의 수를 열거하고 곱·합 공식을 도출한다.

  • 생성자 패턴이 값을 분해하는 규칙을 설명한다.

없는 것은 목적지일까, 요청 전체일까?

앞 본문은 product의 모든 조합과 sum의 태그별 선택을 셌다. 새 유한 모형에서 A={Red,Blue}는 요청 소유자이고 B={1,2,3}은 목적지다. A×option B는 소유자가 항상 있고 목적지만 없을 수 있다. option(A×B)는 요청 전체가 없거나 소유자와 목적지가 함께 있다. 정상 값만 세며 예외·발산·물리 크기는 제외한다.

첫 구조에는 (Red,None)과 (Blue,None)이 서로 다른 값이다. 둘째 구조의 None에는 그 구별이 없다. 두 구조의 값 수는 각각 2×4=8과 1+2×3=7이다. 첫 구조에서 목적지가 없는 두 값을 모두 None으로 보내면 정보가 손실된다. 역변환에서 소유자를 임의로 골라도 원래 두 입력을 모두 복원하지 못한다.

반면 Local of A | Remote of (A×B)는 소유자를 두 경우 모두 보존한다. 이를 A×(LocalUnit | RemoteDest of B)로 바꾸면 Local a를 (a,LocalUnit), Remote(a,b)를 (a,RemoteDest b)로 보낸다. 역변환도 태그와 소유자를 함께 읽으므로 양방향 합성은 입력을 복원한다. 메모리 배치나 언어의 자동 타입 동일성을 주장하는 식은 아니다.

먼저 확인할 개념
  • 태그와 성분의 개수

    동일한 payload도 태그가 다르면 별도 값이라는 정의를 사용한다.

  • 구조 제약의 범위

    없음 상태에서 어떤 업무 정보를 보존할지 먼저 정한다.

둘 다 필요한 값: product

product A×B는 A의 값 하나와 B의 값 하나를 함께 갖는다. A={On,Off}, B={Low,Mid,High}이면 (On,Low),(On,Mid),(On,High),(Off,Low),(Off,Mid),(Off,High)의 6개다. 각 첫 선택마다 둘째 선택 3개가 붙으므로 2×3=6이다. 이 계산은 모든 조합이 허용된다는 조건이며 확률적 독립성 주장이 아니다. A나 B가 빈 집합이면 가능한 쌍이 하나도 없어 product의 크기는 0이다.

OCaml의 lamp * tone은 두 성분을 갖는 product다. 레코드는 성분에 이름을 붙인 product 형태로 이해할 수 있다. 업무가 On과 High 조합을 금지한다면 일반 product 자체는 그 규칙을 강제하지 않는다. 허용 부분집합의 검증이나 제한된 생성 경계가 필요하다.

어느 하나인 값: 태그 있는 sum

sum A+B는 Lamp a 또는 Tone b 중 하나를 갖는다. 값은 Lamp On,Lamp Off,Tone Low,Tone Mid,Tone High의 5개다. 생성자가 두 경우를 구별하므로 |A+B|=|A|+|B|다. 한 경우의 payload가 product일 수도 있지만 하나의 값은 하나의 생성자 경우에 속한다.

Left 1과 Right 1은 payload가 같아도 태그가 달라 다른 값이다. 일반 합집합은 겹치는 원소를 한 번 세지만 태그 있는 sum은 구별한다. 데이터 없는 생성자는 단일 선택 하나를 나타낸다. option A의 None과 Some a는 1+A 구조로, None은 숫자 0이나 빈 문자열과 같은 값이 아니다.

구조에서 연산까지

패턴 match는 값을 생성자별로 나누고 내부 값을 이름에 연결한다. Tone Mid는 Lamp 패턴과 맞지 않고 Tone Mid 패턴에 맞는다. 생성자 이름은 payload 타입이 같아도 경우를 구별한다. 여러 boolean이나 특별한 숫자 sentinel보다 경우마다 필요한 데이터를 드러낼 수 있다.

여기서는 닫힌 variant의 유한 예를 다룬다. OCaml도 예외·mutable 값·입출력을 허용하므로 algebraic type을 사용했다는 것만으로 순수성이나 총함수를 얻지 않는다. 구조가 모순된 값 일부를 배제하는 성질과 연산 전체의 실행 계약을 분리해야 한다.

중간 과정을 따라가는 예제

아래 코드에서 both/either의 값 수와 describe (Tone Mid)의 예상 출력은?

  1. both의 On 묶음 3개와 Off 묶음 3개를 열거하여 6개를 얻는다.

  2. either는 Lamp의 2개와 Tone의 3개를 합하여 5개다.

  3. Tone Mid는 두 Lamp 패턴과 Tone Low를 지나 네 번째 패턴에 일치한다.

  4. 선택된 문자열 mid를 출력한다. 이는 종이 예측이며 실제 OCaml 출력 관찰이 아니다.

product 6개, sum 5개, 예상 한 줄 출력 mid다. 값 개수는 메모리 크기와 다르다.

조건을 바꾸어 비교하기

실패한 역변환의 두 입력

(Red,None)과 (Blue,None)을 모두 None으로 보내고, 역변환은 None을 (Red,None)으로 보낸다. 두 왕복을 비교하라.

  1. 첫 입력은 None을 거쳐 (Red,None)으로 돌아온다.

  2. 둘째 입력도 (Red,None)으로 돌아와 Blue가 사라진다.

첫 왕복만 복원한다. 두 값을 합친 변환은 단사도 아니며 지정 역변환으로 양쪽을 복원할 수 없다.

비교할 점

값 수의 차이와 실제 충돌 입력을 함께 제시하면 잃은 정보가 드러난다.

빈 payload 타입의 경계

A가 빈 유한 집합이고 B에는 세 값이 있다. option(A×B)와 A×option B 및 LocalUnit+RemoteDest B의 크기를 구하라.

  1. A×B는 0개이므로 option(A×B)는 None 한 값이다.

  2. A×option B는 소유자를 고를 수 없어 0개다.

  3. 마지막 sum은 데이터 없는 LocalUnit 한 값과 목적지 세 값이다.

각각 1개, 0개, 4개다.

비교할 점

데이터 없는 생성자는 선택 하나지만 빈 타입을 payload로 요구하는 생성자는 정상 값을 만들 수 없다.

종이와 본문으로 직접 해보기

A={0,1}, B={0,1}에서 product, Left A+Right B, 일반 합집합의 값을 써라. option A도 세어라.

힌트 보기

숫자가 같아도 Left/Right 태그를 먼저 붙인다. None은 별도 한 값이다.

풀이 보기

product={(0,0),(0,1),(1,0),(1,1)}로 4개, sum={Left 0,Left 1,Right 0,Right 1}로 4개, 일반 합집합={0,1}로 2개다. option={None,Some 0,Some 1}로 3개다.

오해와 반례

sum은 모든 경우의 데이터를 동시에 담는다.

Lamp On에는 Tone payload가 없다. 동시에 저장하려면 lamp * tone을 쓴다. Pair of (lamp * tone) | Missing처럼 sum의 한 분기가 product를 담을 수는 있다. 경우의 선택과 그 경우 내부의 성분을 구별한다.

자기점검

Left 1과 Right 1은 같은 값인가?

답과 이유 보기

아니다.

태그 있는 sum은 생성자도 값의 일부로 구별한다.

|A|=3,|B|=2이고 모든 조합을 허용하면 product/sum 크기는?

답과 이유 보기

6과 5다.

각 첫 선택마다 둘째 선택 2개가 붙고 태그 있는 두 경우는 겹치지 않는다.

None과 Some 0은 같은가?

답과 이유 보기

다르다.

없음 생성자와 데이터 있는 생성자가 다르다.

설명 기준 확인

타입별 모든 정상 값에 정의한 두 변환의 합성이 입력을 복원하는지 확인한다.

한 단계 더

유한 집합에서 A×(B+C) ≅ (A×B)+(A×C)를 구성하자. (a,Left b)를 Left(a,b), (a,Right c)를 Right(a,c)로 보내고 태그를 보고 역변환한다. 두 변환을 합성하면 입력을 복원하므로 전단사다. ≅는 변환 가능한 구조라는 뜻이며 언어에서 타입이 자동 동일하거나 메모리 표현이 같다는 뜻은 아니다. 재귀·무한·발산 의미를 포함한 타입에는 별도 모형이 필요하다.

소단원 2.2

완전성과 중복패턴

모든 경우를 적었는데 Found 0 분기가 영원히 선택되지 않는 이유는 무엇일까?

준비 개념과 학습 목표

준비 개념

  • 패턴은 값의 구조를 검사하고 이름을 바인딩하는 모양이다. Found n은 내부 값을 새 이름 n에 연결한다. _는 어떤 값도 받아들이되 이름을 묶지 않는다.

  • when guard는 패턴 성공 뒤 검사하는 조건이다. 이 예는 위에서 아래로 검사하여 패턴과 guard가 처음 모두 성공한 분기를 고른다.

학습 목표

  • 완전성·분기 겹침·완전 가림을 구별한다.

  • guard와 순서가 선택에 미치는 영향을 추적한다.

  • 완전성에서 종료·무예외까지 결론 내릴 수 없는 이유를 설명한다.

값은 같아도 guard를 지나간 기록이 같을까?

새 classify는 Missing을 none으로 처리한다. Found n에서는 첫 guard g1이 G1을 기록하고 n>0을 반환한다. 첫 guard가 거짓이면 둘째 g2가 G2를 기록하고 n=0을 반환한다. 두 guard가 거짓이면 negative다. 각 호출은 새 빈 기록에서 독립적으로 시작하며 기록 추가·비교는 정상 종료한다고 가정한다.

Found 0은 G1을 기록한 뒤 거짓이므로 G2를 기록하고 zero를 고른다. Found 1은 G1만 기록하고 positive를 고른다. guard 순서를 바꾸어 0 검사부터 하면 반환은 같아도 0의 기록은 G2만 남는다. 구조적 완전성은 효과의 동일성을 보장하지 않는다.

g1이 0에서 G1을 기록한 뒤 E를 발생시키는 별도 변형에서는 false를 반환하지 않았다. 이 경우 나머지 분기로 재개하는 것이 아니라 E가 전파된다. 아래의 유한 도달 집합 계산은 guard가 정상 반환하는 모형에 한정한다.

먼저 확인할 개념
  • 첫 일치와 guard 재개

    false 뒤 다음 분기와 예외 전파를 구별한다.

  • 생성자와 payload 분해

    Missing에는 비교할 정수 payload가 없다.

완전성은 입력 범위를 덮는 성질

answer=Missing|Found of int의 모든 값 구조를 패턴 전체가 덮으면 exhaustive, 즉 완전하다. Missing과 Found _는 모든 경우를 덮는다. Missing만 있으면 Found 0이 누락 반례다. 매칭할 분기가 없으면 OCaml은 정상 결과 대신 Match_failure 예외를 낼 수 있다. 이 완전성의 정의역은 정상적으로 구성된 answer 값이다. 외부 입력 문자열이 올바른 variant로 파싱되는지와 업무상 유효한지는 별도로 검증한다.

Found n when n>0은 0과 음수를 덮지 않는다. 컴파일러는 임의 guard의 논리를 모두 증명하는 도구가 아니므로 나머지 구조를 명시하면 분명하다. good은 0·양수·남은 Found의 경우를 모두 처리한다. 정수 비교만 하는 이 예의 guard와 효과나 예외를 내는 일반 guard는 구별한다.

순서와 중복을 구별하기

Found _ 뒤의 Found 0은 아무 입력에도 선택되지 않는다. 0도 앞의 wildcard에 먼저 맞기 때문이다. 모든 값이 앞에서 처리되어 가려진 redundant 분기와 일부 겹치지만 남은 입력에는 도달하는 분기는 다르다. 순서를 바꾸면 결과가 바뀔 수 있다.

Found 0을 먼저 쓰고 Found _를 뒤에 쓰면 0은 특별 결과, 나머지는 일반 결과다. 같은 이름을 (x,x)처럼 한 패턴에 두 번 바인딩하여 같음을 검사하는 방식은 OCaml에서 허용되지 않는다. (x,y) when x=y로 서로 다른 이름을 바인딩하고 조건을 비교해야 한다.

완전해도 남는 계약

모든 구조를 덮어도 선택된 분기가 raise하거나 끝없는 재귀를 할 수 있다. 완전성은 선택할 경우가 있다는 성질이며 원하는 값을 반환하는 전체 정확성이 아니다. 각 결과의 의미·종료·예외·효과를 별도 확인해야 한다.

타입에 새 생성자를 추가하면 명시적 경우 나열은 누락을 드러내기 쉽다. 마지막 _는 새 경우도 옛 기본 정책으로 처리하여 의도 누락을 숨길 수 있다. wildcard가 언제나 잘못은 아니지만 새 경우에 맞는 기본 정책인지 확인해야 한다. 여기서는 문서와 종이 반례만 확인했고 실제 compiler 경고를 관찰한 것으로 쓰지 않는다.

중간 과정을 따라가는 예제

good (Found 0), good (Found (−2)), bad (Found 0)을 추적하고 bad의 완전성과 중복을 판정하라.

  1. good의 0 입력은 Missing에 실패한 뒤 Found 0에 맞아 zero다.

  2. -2는 0 패턴에 실패하고 양수 guard도 거짓이므로 마지막 Found _에서 negative다.

  3. bad의 0은 첫 Found _에서 some을 고르므로 뒤의 Found 0에 도달하지 않는다.

조건을 바꾸어 비교하기

순서 변경의 숨은 차이

0 검사 g2를 첫째로 바꾸고 양수 검사 g1을 둘째로 한다. Found 0과 Found 1을 원래 순서와 비교하라.

  1. 0은 새 첫 guard에서 끝나 zero와 [G2]다.

  2. 1은 G2를 기록하고 false 뒤 G1을 기록해 positive다.

Found 0의 반환은 zero, Found 1의 반환은 positive로 원래 순서와 같다. 새 기록은 0에서 [G2], 1에서 [G2,G1]이다.

비교할 점

guard를 순수 비교로 제한하면 이 기록 관찰은 없어지지만 그런 제한을 명시해야 한다.

일부 겹침과 완전 가림

정수 영역을 {−1,0,1}로 제한한다. Found n의 분기는 순서대로 n≥0→A, n≤0→B, _→C다. 도달 집합을 구하라.

  1. A는 {0,1}을 먼저 처리한다.

  2. B의 표면 집합은 {−1,0}이나 0은 앞에서 처리되어 실제로는 {−1}이다.

  3. 마지막 C에는 남은 입력이 없다.

도달 집합은 {0,1},{−1},∅다. B는 일부 겹치지만 도달하며 C는 완전히 가려진다.

비교할 점

입력 전체를 덮는 완전성과 각 분기가 선택되는지는 별도 질문이다.

종이와 본문으로 직접 해보기

flag=On|Off에서 순서 1은 _→1,On→2, 순서 2는 On→2,Off→1이다. 각 결과와 Pause 추가 후 누락 위험을 비교하라.

힌트 보기

값마다 처음 성공하는 분기를 찾고, 완전성과 올바른 정책을 나누어 판단한다.

풀이 보기

순서 1은 둘 다 1이며 On 분기가 가려진다. 순서 2는 On은 2, Off는 1이다. Pause 추가 뒤 순서 1은 새 값을 1로 조용히 처리하므로 정책 검토가 필요하고 순서 2는 Pause 분기를 추가해야 한다. 어느 결과가 업무상 맞는지는 계약에 달려 있다.

오해와 반례

완전성 경고가 없으면 함수가 모든 입력에서 성공적으로 끝난다.

모든 패턴을 덮고 각 분기에서 예외를 발생시키는 함수도 구조적으로 완전하다. match 선택과 정상 종료는 별개다. 경고 설정과 실제 컴파일을 확인하지 않고 성공 증거로 쓰는 것도 잘못이다.

준비 개념

  • 도메인은 프로그램이 다루는 업무 세계다. 가상 사례는 도서 하나의 대출 상태다. 회원ID는 문자열이며 등록 여부·외부 저장·동시성은 별도 조건이다.

  • 전이는 이전 상태와 요청을 받아 다음 상태나 거절을 만든다. 순수 전이 함수는 외부 저장을 바꾸지 않고 결과 값을 반환한다.

학습 목표

  • 잘못된 상태 조합을 product/sum으로 비교한다.

  • 구조 제약과 업무 검증의 범위를 구별한다.

  • 순수 전이와 외부 상태 적용을 분리한다.

예약 상태를 더하면 기존 대출 함수는 무엇을 다시 확인해야 할까?

새 모형의 등록회원은 U={u1,u2}이며 loan은 Available | Reserved of ID | Borrowed of ID다. 정상 업무 상태는 다섯 개다. status={free,reserved,borrowed}와 option U를 곱하면 아홉 개지만 free+회원 또는 reserved/borrowed+None의 네 조합은 허용하지 않는다.

reserve는 등록회원이 Available을 Reserved member로 바꾼다. 이미 Reserved이면 AlreadyReserved, Borrowed이면 AlreadyBorrowed로 거절한다. borrow는 Available 또는 같은 회원의 Reserved에서 Borrowed member로 바꾸고, 다른 회원의 Reserved이면 NotYours, 이미 Borrowed이면 AlreadyBorrowed로 거절한다. return_book은 Borrowed만 Available로 바꾸고 나머지는 NotBorrowed로 거절한다. 요청 회원 검증이 필요한 reserve/borrow는 먼저 member∈U를 검사하며 실패는 BadMember다. 모든 거절은 이전 상태를 유지한다.

순수 함수가 Updated를 만들면 호출자가 그 새 상태를 적용한다. 두 요청이 같은 Available을 동시에 읽으면 각각 성공을 계산할 수 있다. 순차 계약의 귀납 보존과 공유 저장의 원자 적용은 다른 조건이다. 예약을 취소하는 연산은 여기서 정의하지 않았으며 return_book을 취소로 확대하지 않는다.

필요한 경우에만 데이터 두기

boolean borrowed와 string option member를 함께 두면 false,None 및 true,Some ID 외에 false,Some ID와 true,None이라는 모순된 구조도 만들 수 있다. loan=Available|Borrowed of string은 Available에는 회원 payload가 없고 Borrowed에만 하나가 있어 이 두 구조적 모순을 배제한다.

배제한 모순의 범위를 정확히 말해야 한다. Borrowed ""나 미등록ID도 string 타입에는 맞는다. 등록·빈 문자열 금지·만료일 등은 검증, 숨긴 생성자, 검증된 ID 타입 또는 연산 계약으로 따로 강제해야 한다. 타입 구조와 현실의 사실 확인은 다르다.

전이를 값으로 만들기

borrow는 Available에서 Updated(Borrowed member), Borrowed에서 Rejected AlreadyBorrowed를 반환한다. return_book은 Borrowed에서 Updated Available, Available에서 Rejected NotBorrowed다. Updated와 Rejected는 다른 경우다. 거절에는 새 상태가 없으며 호출자는 이전 상태를 유지한다는 적용 계약을 명시한다.

함수는 저장이나 화면을 직접 바꾸지 않는다. 호출자가 Updated일 때 새 상태를 저장하고 거절 때 유지한다. 이 계산이 맞아도 저장 실패나 두 요청의 동시 관찰이면 실제 서비스가 달라진다. 상태 검사·저장의 원자성 및 실패·영속성 계약은 별도 구현 층에서 필요하다.

경우의 수와 변경의 경계

회원ID 집합 U가 유한하고 n개이면 loan의 상태 수는 1+n이다. Available 한 값과 회원마다 Borrowed 한 값이다. boolean×option U는 2(1+n)개로 그 중 n+1개만 의도한 조합이다. sum은 나머지 구조적 조합을 없애지만 여러 도서 사이 대출한도 관계까지 해결하지는 않는다.

Reserved 등 새 상태가 필요하면 필요한 payload와 허용 전이를 추가하고 모든 연산을 재검토한다. 목적은 실제 요구를 삭제하는 것이 아니라 유효한 경우에 필요한 정보만 담는 것이다. 기존 저장 데이터 migration과 API 고객의 호환성은 타입 선언 하나로 해결되지 않는다.

같은 이전 상태의 두 성공

u1과 u2가 Available 스냅샷으로 각각 borrow를 계산한다. 순수 결과와 순차 적용 결과를 비교하라.

  1. 두 독립 계산은 Updated Borrowed u1과 Updated Borrowed u2를 각각 낸다.

  2. u1 결과 적용 뒤 현재 상태에서 u2를 다시 계산하면 이미 Borrowed여서 거절된다.

같은 스냅샷의 두 성공은 순차 계약의 단일 대출을 보장하지 못한다.

(3) 새 loan을 Available로 시작해 reserve u2, borrow ghost, return_book, borrow u2를 순차 적용하라. ghost는 U 밖이고 회원 검증을 먼저 수행한다.

힌트 1

None이 지우는 범위와 guard의 정상 false/예외를 따로 확인한다.

힌트 2

거절에서 이전 상태를 유지하고 마지막 요청의 예약 소유자를 비교한다.

풀이와 답 확인

  1. 소유자 보존을 위해 A×option B를 고른다. (Blue,None)은 목적지가 없지만 Blue를 보존하며 전체 정상 값은 8개다. 밖의 option 모형은 7개이고 None에는 소유자가 없다.

  2. 원래 Found 0은 zero와 [G1,G2]다. 변형은 E와 [G1]이며 g2를 실행하지 않는다.

  3. reserve u2는 Reserved u2로 성공한다. borrow ghost는 BadMember로 거절하고 Reserved u2를 유지한다. return_book도 NotBorrowed로 거절하여 예약을 유지한다.

  4. 마지막 borrow u2는 같은 예약자이므로 Borrowed u2로 성공한다. 성공은 2회, 거절은 2회다. 이는 순차 종이 계약이며 실제 저장 성공 관찰이 아니다.

소유자 보존 구조는 8개 값의 A×option B다. guard 예외는 false 재개가 아니다. 예약 요청열은 성공/거절/거절/성공이며 최종 Borrowed u2다.

해결한 뒤 점검할 것

  • 태그·소유자·목적지의 보존과 None의 다른 범위를 설명한다.

  • 반환과 예외 및 G1/G2의 관찰을 구별하고 비교 초기 상태를 분리한다.

  • 등록 검증 우선·거절 보존·예약자 관계를 모두 적용하며 저장/동시성 보장으로 확대하지 않는다.
