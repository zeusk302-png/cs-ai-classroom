소단원 10.1

option·result

값이 없는 것과 계산이 실패한 것은 같은 상태일까?

준비 개념과 학습 목표

준비 개념

  • 대수적 자료형
  • 분기
  • 정수 나눗셈

학습 목표

  • option의 부재를 설명한다.
  • result의 성공/오류를 구별한다.
  • 합성에서 오류를 전파한다.

없음에도 이름을 준다

option은 값이 있으면 Some(value), 없으면 None인 선택을 표현한다. Some(0)은 유효한 0이며 None과 다르다. 임의 sentinel 0으로 부재를 표시하면 0이 실제 값일 때 구분이 사라진다.

없음의 이유까지 호출자에게 알려야 한다면 option만으로 부족할 수 있다. 예를 들어 검색 결과 부재와 권한 오류를 같게 처리할지 계약을 먼저 정한다. 이름은 언어별로 Option/Maybe 등 다르지만 이 절은 태그를 명시한 교육 표기를 쓴다.

실패 이유를 실어 보낸다

result는 성공 값 Ok(value) 또는 오류 Err(reason)를 담는다. 이 절의 checkedDivide(a,b)는 b=0이면 Err(ZeroDivisor), 아니면 정수 나눗셈 결과를 Ok에 넣는 자체 계약이다. 해당 입력 범위는 작은 정수로 제한해 overflow 등은 제외한다.

match로 모든 상태를 처리하거나 다음 단계로 Err를 전파한다. Result 반환은 성공을 보장하지 않고 오류를 값으로 다룰 기회를 준다. unwrap/expect처럼 결과를 강제로 꺼내는 연산은 실패를 다시 panic 등 다른 제어 흐름으로 바꿀 수 있다.

다음 계산을 언제 부를까

교육 bind는 Ok(v)이면 함수 g(v)를 부르고 Err(e)이면 g를 부르지 않고 같은 Err를 전달한다. map은 성공 값을 보통 값으로 변환하는 함수와, bind는 result를 반환하는 함수와 합성하는 차이를 가진다.

아래 표기는 실제 Rust 코드가 아닌 언어 중립 태그/흐름 모형이다. division과 후속 increment를 종이에 추적한다. 실패한 단계가 있더라도 이미 발생한 외부효과가 자동으로 취소된다는 뜻은 아니다.

중간 과정을 따라가는 예제

checkedDivide(12,3) 및 checkedDivide(12,0)의 결과에 bind(g)를 적용한다. g(v)=Ok(v+1)이다.

  1. 12/3=4이므로 첫 결과 Ok(4)다. g(4)를 불러 Ok(5)가 된다.
  2. 분모0은 나누지 않고 Err(ZeroDivisor)를 만든다.
  3. Err 경로는 g 호출0회이며 Err(ZeroDivisor)를 그대로 전달한다.

각각 Ok(5)·Err(ZeroDivisor)이며 g 호출은1·0회다.

소단원 10.2

예외와 효과구분

같은 결과를 두 번 반환해도 세상에 남기는 흔적은 같을까?

준비 개념과 학습 목표

준비 개념

  • 순수 함수
  • 예외 전파
  • 공유 상태

학습 목표

  • 반환/실패 제어/외부효과를 구별한다.
  • 순수한 result 계산을 설명한다.
  • 오류가 효과를 되돌리지 않음을 추적한다.

결과의 종류와 효과는 두 축이다

result로 실패를 표현하거나 예외로 제어를 이동하는 선택은 오류 전달 방식이다. 외부 파일 수정·콘솔 기록·공유 카운터 갱신은 관측 가능한 효과다. result 함수도 파일을 쓰면 효과가 있고, 실패 태그를 계산하는 순수 함수는 외부 상태를 바꾸지 않을 수 있다.

순수함수는 같은 입력에 같은 결과를 내며 관측 가능한 부작용이 없어야 한다. 항상 숫자7을 반환해도 매번 로그를 쓰면 순수하다는 결론은 나오지 않는다. referential transparency를 판단할 때 출력 버퍼도 관측에 포함한다.

실패가 앞선 효과를 지우지는 않는다

교육 단계 A가 counter를 증가시키고, B가 Err를 반환하면 전체 결과는 Err라도 counter는 이미 바뀌었다. 예외 catch도 과거 파일 쓰기나 결제를 저절로 rollback하지 않는다. 트랜잭션·보상·멱등 계약 같은 별도 장치가 필요하다.

명시적 오류 전파는 실패 경로를 읽기 쉽게 만들지만 부작용 제거를 자동 수행하는 기능이 아니다. 어떤 상태가 언제 바뀌는지 시간 순서 표를 함께 써야 부분 수행을 찾는다.

교체 가능성을 시험한다

아래 h(x)는 counter를1 올리고 Ok(x)를 반환하는 교육 모형이다. 한 스레드·초기 counter0·다른 접근 없음으로 정한다. h(7)을 상수 Ok(7)로 교체하면 결과만 같고 counter 관측은 달라진다.

예외를 result로 잡아 바꾸는 wrapper도 원인·취소·치명적 오류를 모두 같은 Err로 뭉개지 않게 설계한다. 예상 범위만 처리하며 실제 file/network·코드 실행은 이 활동에서 수행하지 않는다.

중간 과정을 따라가는 예제

counter0에서 h(7)을 두 번 호출한다. 다음 별도 실험에서 초기 counter0, A 증가1 후 B가 Err(Failed)를 반환한다.

  1. 첫 h는 counter1,Ok7이며 두 번째는 counter2,Ok7이다.
  2. h를 Ok7 상수로 두 번 대체하면 counter0으로 남아 관측이 다르다.
  3. 별도 A/B 순서의 마지막 result는 Err(Failed), counter1이다.

같은 Ok7 반환이 순수를 뜻하지 않는다. 실패 후에도 앞선 counter 효과1이 남는다.

B를 예외 throw로 바꾸고 wrapper가 Err로 잡으면 counter는 자동0으로 되돌아가나?

힌트 보기

풀이 보기

없다면 counter1 그대로다. 예외→Err 변환은 전달 형식만 바꾸며 상태 복구를 추가하지 않는다.

오해와 반례

반환 형식과 실제 효과를 분리해 본다. 파일·로그·공유 상태가 바뀌면 effect가 남는다.

소단원 10.3

순수핵심·입출력 경계

파일 없이도 계산 규칙을 검토하려면 어디를 나눠야 할까?

준비 개념과 학습 목표

준비 개념

  • 입력/출력
  • 불변 자료
  • 함수 합성

학습 목표

  • 순수 계산에 필요한 환경을 입력으로 준다.
  • IO 실패와 계산 실패를 구별한다.
  • 종이 테스트와 시스템 검증을 분리한다.

바깥에서 읽고 안에서 계산한다

프로그램의 바깥 경계가 파일·네트워크·시각을 읽어 값으로 준비하고, 핵심 함수는 그 값으로 새 결과를 계산하게 할 수 있다. 현재 시간을 핵심 안에서 몰래 읽기보다 명시 입력으로 주면 같은 사례를 다시 검토하기 쉽다.

출력 경계는 핵심이 반환한 결정을 실제 저장·전송한다. 핵심이 "결제하라"는 명령 값을 반환하는 것과 실제 결제를 수행하는 것은 다른 사건이다. 계산이 순수해도 경계의 재시도·중복·권한·동시성 문제는 남는다.

규칙과 경계 계약을 연결한다

교육 cart 핵심은 nonnegative 정수 가격·수량 목록을 받아 subtotal=sum(price×quantity)를 구한다. subtotal<1000이면 배송300, 그 이상이면 배송0인 자체 원 단위 계약이다. 예제는 작은 값이라 overflow를 제외한다.

잘못된 수량은 핵심의 Err(InvalidQuantity), 파일 접근 실패는 경계의 Err(ReadFailure)로 구별할 수 있다. 같은 파일이라고 생각해도 읽기 시점 내용이 바뀌면 핵심 입력이 달라진다. 순수함수의 반복 결과 약속은 동일 입력이라는 조건 위에 있다.

테스트의 증거 범위

설치 없이 입력 표·예상 subtotal·배송·총액을 적으면 조건 경계와 계산 규칙을 검토할 수 있다. 가격표를 읽는 부분은 대역 값을 넣어 테스트할 수 있지만 실제 parsing·저장·네트워크 복구 성공을 증명하지는 않는다.

파일을 한 번 읽어 불변 snapshot 값으로 핵심에 넘기면 계산 중 내용 변화를 분리하기 쉽다. 최종 저장 전에 다른 갱신이 있으면 버전/충돌 정책을 따로 확인한다. 본문은 실제 주문·IO·학습자 실험을 수행하지 않는다.

중간 과정을 따라가는 예제

품목 (가격100,수량2),(가격200,수량3)의 순수 cart 결과를 구하라. 위 배송규칙을 적용한다.

  1. subtotal=100×2+200×3=200+600=800원이다.
  2. 800<1000이므로 배송300원이다.
  3. 총액800+300=1100원이며 IO는 이 계산에 포함되지 않는다.

subtotal800·배송300·총액1100원이다.

힌트 보기

새 입력과 외부 저장 사건을 나눈다.

풀이 보기

오해와 반례

순수핵심의 테스트가 맞으면 실제 파일 저장과 결제까지 완료다.

계산 계약 검토와 IO의 실제 수행 증거는 다르다. 경계의 오류·중복·상태를 별도로 검증한다.
