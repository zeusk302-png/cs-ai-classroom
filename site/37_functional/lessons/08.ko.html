소단원 8.1

tail recursion

재귀 호출이 마지막 줄에 있다고 언제나 꼬리 재귀일까?

준비 개념과 학습 목표

준비 개념

  • 재귀와 기저 사례

  • 함수 반환

  • 누산기

학습 목표

  • 호출 뒤 남은 계산에서 tail 위치를 판단한다.

  • 누산기 불변식과 공간 가정을 설명한다.

숫자를 왼쪽부터 읽는 계산에서 곱셈을 앞으로 옮겨도 같은 값을 얻을까요?

자리표에 4, 1, 7을 순서대로 입력하면 417을 만든다. 자체 함수 parse의 입력은 유한한 십진 숫자 목록이며 모든 원소는 정수 0부터 9다. 빈 목록은 0으로 해석하고 선행 0도 허용한다. 정확한 정수 산술을 가정하며 실제 OCaml int의 범위 검사는 별도다.

원래 parse(d::rest)는 d×10^(length rest)+parse(rest)다. 오른쪽 재귀 결과를 얻은 뒤 덧셈이 남는다. 새 helper H(rest,acc)는 다음 숫자 d에서 H(tail,10×acc+d)를 부른다. acc는 이미 소비한 접두부의 숫자 값이며 최종 숫자와 동일한 순서로 자란다.

불변식은 acc×10^(length rest)+parse(rest)가 처음 입력의 값이라는 것이다. 남은 목록이 비면 acc를 반환한다. 반복해서 length와 거듭제곱을 구하는 원래 설계와 새 설계의 작업도 다르지만, 여기서는 우선 의미와 남은 반환 작업을 추적한다. 꼬리 최적화가 적용되는 경우의 helper 스택과 출력 정수 크기를 구별한다.

먼저 확인할 개념
  • tail recursion

    호출 뒤 남은 연산과 누산기 불변식으로 새 숫자 파서를 분석한다.

  • lazy evaluation과 stream

    필요한 접두부만 소비하는 다음 단계와 모든 숫자를 소비하는 현재 파서를 구별한다.

마지막 문장보다 마지막 작업

꼬리 위치의 호출은 그 결과를 얻은 뒤 현재 함수가 더 계산할 일이 없는 호출이다. n*fact(n−1)은 재귀 결과를 얻은 뒤 곱셈이 남아 있으므로 꼬리 호출이 아니다. return에 적혀 있다는 표면 위치와 실행해야 할 작업을 구별한다.

호출 뒤 남은 정보는 일반적으로 호출 스택에 보존된다. 꼬리 호출 최적화가 적용되면 더 사용할 정보가 없는 프레임을 재사용할 수 있다. 언어·컴파일러가 이를 지원하는지 확인해야 하며 모든 재귀나 모든 실행 환경에 상수 스택을 보장하지 않는다.

곱셈을 앞으로 옮기기

누산기 acc는 지금까지 모은 결과다. fact_aux n acc의 기저는 acc를 반환하고 재귀는 fact_aux (n−1) (n*acc)다. 곱셈을 호출 전에 수행하므로 재귀 결과 뒤에 남은 연산이 없다. 처음 acc=1을 넣으면 원래 팩토리얼의 기저1을 보존한다.

시작4라면 acc×n!=4!이라는 불변식을 본다. 상태(4,1)에서(3,4)로 바뀌어도1×4!=4×3!=24다. n≥0과 해당 값에서 정수 overflow가 없다는 전제를 둔다. 최적화로 스택을 줄여도 큰 정수의 표현 한계가 사라지지 않는다.

let rec fact_aux n acc =
  if n = 0 then acc
  else fact_aux (n-1) (n*acc)
let fact_tr n = fact_aux n 1

시간과 저장공간을 나누기

원래 방식과 누산기 방식 모두 n단계 곱셈으로 값이 계산된다. 최적화된 꼬리 호출에서 상수인 것은 해당 호출 스택의 성장이지 모든 프로그램 메모리나 실행 시간이 아니다. 결과 리스트나 큰 정수 자체는 입력에 따라 공간을 요구한다.

리스트를 acc 앞에 계속 붙이면 결과 순서가 뒤집힐 수 있다. 마지막 List.rev로 원래 순서를 복구하는 방법은 선형 시간과 결과 저장공간을 요구한다. 누산기를 추가했다는 사실만으로 함수의 의미가 유지되는 것은 아니므로 값·순서·불변식을 함께 대조한다.

acc의 값은 소비한 접두부에 해당한다. 각 행에서 남은 자릿수만큼 자리를 비우고 나머지를 더하면 417로 유지된다. 행 수와 살아 있는 호출 프레임 수는 같은 양이 아니다.

중간 과정을 따라가는 예제

자체 fact_aux로4!를 계산한다. n≥0, 정수 overflow 없음, 꼬리 호출 최적화 적용을 가정한다. 상태와 곱셈 수를 적고 최적화 없는 원래 fact의 살아 있는 호출 프레임 수도 기저 호출을 포함해 비교하라.

  1. (4,1)→(3,4)→(2,12)→(1,24)→(0,24)다.

  2. 각 상태 acc×n!는24로 유지되고 기저에서acc24를 반환한다.

  3. 곱셈은4/3/2/1의4회다.

  4. 원래 fact4는 fact3/2/1/0 결과를 기다려 최대5개 호출 프레임이 겹친다. 최적화된 helper는 프레임을 재사용한다. wrapper 등 고정 비용은 제외한다.

예상24, 곱셈4회. 원래 최대5프레임, 최적화 helper는 입력에 비례한 프레임 성장이 없다.

조건을 바꾸어 비교하기

자리 이동의 방향이 누산기 의미를 정한다

표의 입력에서 정상 갱신 10×acc+d와 오류 갱신 10×d+acc를 비교하라. 두 helper는 모두 마지막에 재귀를 호출한다.

  1. 정상 acc는 0에서 4, 41, 417로 바뀐다.

  2. 오류 acc는 0에서 40, 50, 120으로 바뀐다. 두 번째 단계는 10×1+40이고 마지막은 10×7+50이다.

  3. 두 함수 모두 호출 뒤 계산은 없지만 오류 함수는 접두부 숫자의 의미를 보존하지 않는다.

정상 결과는 417이고 오류 결과는 120이다. 꼬리 위치만으로 값 보존은 증명되지 않는다.

비교할 점

앞 본문의 곱셈 누산기와 달리 자릿수 갱신은 두 항의 역할을 교환할 수 없다.

길이와 자리 무게를 매번 다시 구하는 비용

길이 n의 입력에서 원래 parse가 각 단계마다 남은 목록의 length를 선형 순회하고 10의 거듭제곱도 지수만큼 곱해서 구한다. 새 H는 숫자당 한 번 자리 갱신한다. length가 방문하는 cons 수만 n=4에서 비교하라.

  1. 원래 length는 남은 길이 3, 2, 1, 0을 각각 읽는다. 방문 합은 6이다.

  2. 일반 방문 합은 n(n−1)/2다. 거듭제곱도 반복 구현이면 추가 이차 작업을 만든다.

  3. H는 전체 숫자 네 개를 각각 한 번 소비한다. helper 꼬리 최적화가 적용되면 프레임 성장은 입력 길이에 비례하지 않는다.

원래 length의 방문은 6회이며 새 H에는 length 순회가 없다. 고정 비용 정수 산술 모형에서 H의 자리 갱신은 n회다.

비교할 점

이는 지정한 구현의 작업 수다. 큰 정수 곱셈까지 상수 시간이라고 주장하거나 실제 속도 향상을 측정했다고 말하지 않는다.

[1]→[2,1]→[3,2,1]이다. 역순 결과에 List.rev를 적용하면 [1,2,3]을 복구한다. n=−1에서 수학 정수로 추적하면 −2,−3으로 내려가 기저0에 도달하지 않는다. 실제 OCaml의 유한 비트 정수와 overflow까지 같은 무한열이라고 일반화하지 말고 n≥0 전제를 검사한다.

연습 1 · 값과 상태 예측

새 독립 입력 [0,4,1]을 H([],acc) 기저와 초기 acc=0으로 처리하라. 각 acc와 결과, 자리 갱신 수를 구하라.

힌트 1

선행 0도 원소 하나로 소비한다.

힌트 2

갱신은 숫자마다 10×acc+d다.

풀이와 답 확인

  1. acc는 첫 숫자 뒤 0, 둘째 뒤 4, 셋째 뒤 41이다.

  2. 남은 목록이 비면 41을 반환한다. 갱신은 세 번이다.

결과는 41이며 갱신은 3회다. 출력에 선행 0의 자릿수 정보는 없다.

흔한 오답에서 다시 생각하기

선행 0이 있으므로 결과는 041이라는 별도 정수다.

정수 값과 문자열 자릿수는 다른 관찰이다. 길이를 보존하려면 별도 길이 또는 원문이 필요하다.

연습 2 · 오류 찾아 고치기

H의 빈 목록 기저를 0으로 두고 재귀 갱신은 그대로 유지했다. [4,1,7]의 최종 반환과 수정을 설명하라.

힌트 1

마지막 상태에서 acc가 어디에 있는지 보라.

힌트 2

기저에서 반환하지 않은 상태는 사라진다.

풀이와 답 확인

  1. 기저에 도달할 때 acc는 417이다.

  2. 그러나 함수는 항상 0을 반환하므로 어떤 접두부를 누적했는지 버린다.

  3. 기저를 acc 반환으로 고치고 초기 acc는 0으로 유지한다.

잘못된 반환은 0이며 기저 수정 후 417이다.

흔한 오답에서 다시 생각하기

초기 acc만 417로 두면 일반 파서가 고쳐진다.

초기 값에 한 사례의 정답을 넣으면 빈 입력과 다른 숫자 목록의 의미가 깨진다.

연습 3 · 직접 만들어 보기

숫자 값과 소비한 길이를 함께 반환하는 꼬리 helper를 설계하라. 빈 입력과 [0,4,1]의 결과도 적어라.

힌트 1

상태에 acc와 k를 함께 둔다.

힌트 2

한 숫자를 소비할 때 길이도 하나 늘린다.

풀이와 답 확인

  1. 초기 상태를 (acc,k)=(0,0)으로 둔다.

  2. 숫자 d마다 (10×acc+d,k+1)로 갱신하고 빈 목록에서 (acc,k)를 반환한다.

  3. 빈 입력은 (0,0), [0,4,1]은 (41,3)이다.

정수 값 41과 원래 자릿수 3을 분리해 보존한다.

흔한 오답에서 다시 생각하기

값이 같으면 길이도 같으므로 k가 필요 없다.

[4,1]과 [0,4,1]은 같은 값 41이지만 길이는 각각 2와 3이다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

자체 허용 범위를 0부터 M까지로 제한하는 H를 설계한다. M≥9, 현재 acc≥0, 숫자 d는 0..9다. 다음 값을 계산하기 전에 실패를 판정하는 조건과 M=99, acc=9, d=9 및 acc=10, d=0의 결과를 적어라.

힌트 1

10×acc+d≤M을 acc에 대한 조건으로 옮긴다.

힌트 2

검사 자체가 제한형의 곱셈 overflow를 일으키면 안 된다.

풀이와 답 확인

  1. 다음 값 허용 조건은 acc≤floor((M−d)/10)다. M≥9이므로 M−d는 음수가 아니다.

  2. M=99, d=9에서는 문턱이 9라서 acc=9를 허용하고 99가 된다.

  3. d=0에서는 문턱이 9라서 acc=10을 거절한다. 거절 시 이전 acc를 바꾸지 않는다.

경계 99는 허용하며 100은 계산·상태 변경 전에 거절한다.

흔한 오답에서 다시 생각하기

꼬리 최적화를 켜면 숫자 범위 검사도 불필요하다.

프레임 재사용은 자리 곱셈의 표현 범위를 확대하지 않는다.

꼬리 호출인지와 올바른 파서인지의 증명은 어떻게 다른가?

설명 기준 확인

호출 뒤 작업 유무는 스택 재사용 조건이고 접두부 불변식은 값 보존 조건이다. 오류 갱신도 꼬리 호출일 수 있다.

H의 상수 스택에서 무엇을 제외해야 하는가?

설명 기준 확인

꼬리 최적화 적용을 전제로 helper 프레임 성장만 비교한다. 입력 목록, 출력 정수와 큰 정수 산술의 공간·시간은 별도다.

한 단계 더

합·곱·리스트 역순의 누산기 불변식을 각각 적자. 부동소수점 덧셈은 연산 묶음을 바꾸면 반올림 결과가 달라질 수 있으므로 정수 결합법칙을 아무 수에 그대로 적용하지 않는다.

소단원 8.2

memoization

같은 작은 문제를 다시 풀지 않고 답을 기억하면 얼마나 줄어들까?

준비 개념과 학습 목표

준비 개념

  • 재귀 호출

  • 함수 입력과 결과

  • 표와 키

학습 목표

  • 캐시 miss/hit와 계산 수를 구별한다.

  • 완전한 키·재귀 경로·수명 조건을 설명한다.

남은 거리만 같으면 다음 행동의 선택 수도 같을까요?

계단에서 한 칸 또는 두 칸을 오르되 두 칸 이동을 연속해서 하지 않는 경로를 센다. 자체 W(r,b)의 r은 남은 거리이고 b는 바로 전 이동이 두 칸이었는지다. 거리 0이면 빈 후속 경로 한 개, 음수면 경로 0개다. 모든 계산은 정확 정수의 단일 순차 평가다.

r>0에서 한 칸 이동은 W(r−1,false)를 요구한다. b=false일 때만 두 칸 이동의 W(r−2,true)를 더한다. 따라서 같은 r이어도 b에 따라 서로 다른 문제다. 기저까지 포함해 키 (r,b)를 저장하는 정책을 쓰고, 재귀 호출도 같은 표를 통과한다.

표의 존재 확인과 결과의 진릿값은 다르다. 값 0은 계산을 끝내 얻은 답일 수 있다. 자료 버전이 바뀌거나 캐시 안에 가변 결과 객체를 저장하면 입력 키뿐 아니라 재사용 계약도 다시 확인해야 한다.

먼저 확인할 개념
  • memoization

    완전한 키와 재귀가 캐시 경로를 통과하는 조건을 새 경로 계산에 적용한다.

  • tail recursion

    재귀의 남은 거리 감소와 입력 범위 전제를 사용한다.

입력별 답을 기억하기

memoization은 함수 입력을 키로 결과를 저장하고 같은 키를 다시 요구하면 이전 결과를 사용한다. 같은 키가 항상 같은 의미의 결과를 요구한다는 전제가 필요하다. 외부 시간·설정·자료 버전에 의존하면 그 조건을 키에 포함하거나 캐시 무효화 정책을 정한다.

여기 자체 Fibonacci는 F0=0,F1=1,Fn=F(n−1)+F(n−2)다. 인용 Cornell의 두 기저가1인 정의와 다르므로 숫자를 복사하지 않는다. n≥0인 정수와 이 작은 예제의 overflow 없음, 단일 스레드 계산을 가정한다.

재귀도 같은 캐시를 거쳐야 한다

memo 함수가 호출 전에 표를 보고 없으면 자식 문제를 푼 뒤 저장한다. 재귀 호출도 이 memo 경로를 지나야 중복을 줄인다. 바깥 호출 한 번만 감싸고 원래 재귀는 그대로 두면 첫 큰 문제 안의 중복은 남을 수 있다.

캐시 hit도 함수 진입과 조회가 있는 요청이다. 계산이 새로 일어난 miss 수, 모든 호출 시도 수, 실제 덧셈 수는 다른 양이다. 아래 추적은 항상 n−1부터 푸는 평가 순서와 기저0/1도 저장하는 정책을 명시한다.

저장과 재사용의 비용

F4를 빈 캐시에서 계산하면 키0..4를 저장한다. 같은 캐시로 F5를 구하면 F4와F3을 바로 읽고 새 F5만 계산한다. 매 호출마다 새 캐시를 만들면 호출 사이의 재사용은 사라진다.

상수 비용 조회와 고정 크기 정수 연산 모형에서는 이 Fibonacci의 서로 다른 작은 문제 수가 선형이다. 실제 hash 비용·큰 정수 덧셈·캐시 크기·스레드 동기화는 별도다. 공간을 더 쓰는 대가와 입력 자료의 변화에서 잘못된 오래된 답을 읽는 위험도 고려한다.

memoF(n):
  if cache has n: return cache[n]
  if n < 2: value = n
  else: value = memoF(n-1) + memoF(n-2)
  cache[n] = value
  return value

중간 과정을 따라가는 예제

자체 F4를 빈 캐시에서 n−1 먼저 계산한다. 기저도 저장한다. 호출 시도 순서·miss/hit·덧셈 수를 구하고 원래 캐시 없는 T0=T1=1,Tn=1+T(n−1)+T(n−2)의 호출 수와 비교하라.

조건을 바꾸어 비교하기

같은 남은 거리의 두 상태가 충돌한다

W(2,false)를 먼저 계산해 r=2만 키로 2를 저장했다. 이어 W(2,true)를 같은 표에서 요구한다. 올바른 값과 잘못된 재사용을 비교하라.

  1. false 상태의 경로는 1,1과 2의 두 가지다.

  2. true 상태는 다음 두 칸 이동이 금지되어 1,1만 남는다.

  3. r만 키로 쓰면 이전 값 2를 반환하지만 정확한 값은 1이다.

키 (2,false)에는 2, 키 (2,true)에는 1을 저장해야 한다.

비교할 점

Fibonacci처럼 숫자 하나로 충분했던 상태와 직전 선택이 영향을 주는 상태를 구별한다.

답이 0인 키도 계산을 마친 키다

별도 함수 E(r)는 두 칸 이동만 허용하며 E(0)=1, E(r<0)=0, 양수에서는 E(r)=E(r−2)다. 빈 표에서 E(1)을 두 번 요구한다. 성공한 모든 기저도 저장하며 본체 진입 수를 비교하라.

  1. 첫 요청은 E(1)과 E(−1)의 본체를 각각 한 번 계산해 두 키에 0을 저장한다.

  2. 둘째 E(1)은 키 존재 검사로 hit를 확인해 본체를 계산하지 않는다.

  3. if cached_value 같은 진릿값 검사는 0을 부재로 오인해 두 본체를 다시 계산할 수 있다.

정상 표의 두 요청 전체 본체 계산은 2회다. 0을 miss로 보는 변형에서는 이 사례의 본체 계산이 4회다.

비교할 점

무해해 보이는 0 오인은 답만 비교하면 숨고 요청·hit·본체 장부에서 드러난다.

풀이와 답 확인

  2. 두 번째 동일 root 요청은 hit일 수 있지만 이것이 첫 요청 내부의 중복 제거를 증명하지는 않는다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

거리 n≥0에서 (r,b) 키를 쓰면 상태 수가 많아도 2(n+1) 이하라는 주장과 상수 메모리라는 주장을 구별하라. 음수 기저는 저장하지 않는 새 정책이며 정확 큰 정수 결과를 허용한다.

힌트 1

각 거리 0..n에 b 두 값뿐이다.

힌트 2

한 상태 값의 비트 수는 고정이라는 보장이 없다.

풀이와 답 확인

  1. 저장 가능한 키 수는 두 상태씩 최대 2(n+1)이며 실제 도달 상태는 이보다 작을 수 있다.

  2. 모든 결과를 유지하는 표는 입력에 비례해 항목 수가 증가한다.

  3. 큰 경로 수의 비트 길이와 덧셈 비용도 추가되므로 키 수의 선형 상한을 전체 바이트나 실제 시간의 상수 비용으로 읽지 않는다.

선형 키 상한은 성립하지만 상수 전체 메모리 주장은 성립하지 않는다.

동시에 재사용하려는 서로 다른 상태의 결과를 어디에 보관하는지 확인해야 한다.

소단원 8.3

lazy evaluation과 stream

끝이 없는 수열을 만들면서도 앞의 세 값만 읽을 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 함수 값

  • 재귀

  • memoization

  • take의 k는 비음수 정수라는 전제다. from/take의 작은 예제는 정수 표현 범위 안에서 계산하며 수학적 무한 수열과 유한 비트 OCaml int의 끝없는 증가를 동일시하지 않는다.

학습 목표

  • thunk 지연과 lazy 결과 기억을 구별한다.

  • 필요한 tail 수와 보존한 prefix 공간을 계산한다.

앞의 두 결과만 필요할 때 원본도 두 값만 읽으면 충분할까요?

자체 생산자 s는 1,2,3,…의 head와 memo lazy tail을 만든다. 정수 표현 범위를 넘기지 않는 작은 접두부만 추적한다. mapSquare는 현재 head를 즉시 제곱하고 다음 mapping을 lazy tail에 넣는다. 제곱 본체가 실행될 때마다 H를 하나 늘리는 관찰 장부를 둔다. 실제 부작용 코드 실행은 하지 않는다.

takeExact는 앞 본문의 자체 take처럼 k=1에서 tail을 강제하지 않는다. mapSquare(s)를 만들면 첫 제곱은 이미 끝났으며, takeExact의 요구가 추가 mapped node를 만든다. 같은 q를 보관하는 경우와 mapSquare(s)를 다시 호출해 새 q를 만드는 경우는 결과 기억의 정체성이 다르다.

filter는 조건을 만족하는 head를 찾을 때까지 원본 tail을 읽는다. 수락한 출력의 tail은 lazy로 미루며 다음 출력이 필요할 때만 다시 탐색한다. 출력 개수와 검사한 입력 개수는 같지 않을 수 있다. 아래 각 예제와 과제는 명시된 새 초기 상태에서 시작한다. 동시 force나 예외 캐시 규칙은 이 순차 성공 모형으로 일반화하지 않는다.

먼저 확인할 개념
  • lazy evaluation과 stream

    마지막 head에서 tail을 요구하지 않는 take와 lazy 결과 정체성을 그대로 사용한다.

  • memoization

    계산 결과를 어느 키 또는 어느 lazy 객체에 기억하는지 비교한다.

계산을 함수 안에 미루기

엄격한 평가에서 함수 인자는 보통 적용 전에 값으로 계산된다. 하지만 함수 값의 본체는 그 함수를 호출하기 전에는 실행되지 않는다. unit→value 형태의 thunk는 이 성질로 계산을 미루는 작은 함수다.

동일 thunk를 두 번 호출하면 본체가 두 번 실행될 수 있다. OCaml의 lazy e와 Lazy.force는 지연된 같은 값의 결과를 기억해 재사용한다. 지연과 캐시는 서로 다른 선택이고 C# iterator의 재순회 규칙과도 동일하지 않다.

tail을 지연하는 수열

자체 표현 Cons(head, lazy_tail)에서 현재 head만 있고 tail은 필요할 때 생성된다. from n은 head n과 lazy(from(n+1))를 만든다. 무한 수열을 처음부터 전부 완성하는 것이 아니라 유한 요구만큼 확장한다.

정확히 앞 k개만 읽는 자체 take는 k=0이면 빈 목록, k=1이면 현재 head만 반환하고 tail을 강제하지 않는다. k>1에서만 tail을 강제하고 k−1개를 이어 읽는다. 원저자 노트의 take는 마지막에도 tl을 호출하므로 추가 tail 요구가 있으며 아래 횟수에 그대로 쓰지 않는다.

type stream = Cons of int * stream Lazy.t
let rec from n = Cons(n, lazy (from (n+1)))
let rec take k (Cons(h,t)) =
  if k = 0 then []
  else if k = 1 then [h]
  else h :: take (k-1) (Lazy.force t)

남겨 둔 참조가 기억을 보존한다

앞 세 값을 계산한 뒤 루트 stream을 계속 참조하면 lazy tail의 결과들도 연결되어 보존될 수 있다. 읽은 값을 버리고 현재 위치만 진행하면 옛 노드가 더 이상 필요 없는 경우 회수할 수 있다. 실제 GC 시점은 별도다.

lazy가 모든 공간을 항상 상수로 만드는 것은 아니다. filter가 조건에 맞는 값을 찾기 위해 끝없이 진행하거나 큰 prefix가 보존될 수 있다. 부작용을 포함하면 강제 시점과 기억 정책이 관측 결과를 바꾸므로 순수 수열 계산과 구별한다.

tail을 요청하는 호출과 처음 본체를 실행하는 miss를 분리한다. 반복 take는 두 tail을 다시 요구하지만 기억한 결과를 읽는다. H는 mapSquare의 제곱 실행 횟수이며 take가 만든 출력 리스트의 cons 수를 뜻하지 않는다.

중간 과정을 따라가는 예제

자체 s=from 0과 위 take로 첫3개를 얻는다. 필요한 tail 강제 수와 결과는? 같은 s에서 다시 take3을 하면 새 tail 생성은? 각 lazy는 한 번 성공한 결과를 기억하며 다른 요구는 없다.

  1. s 생성은 head0과 아직 강제하지 않은 tail을 만든다.

  2. 첫 tail 강제로 head1 노드, 둘째 tail 강제로 head2 노드를 만든다.

  3. k=1의 head2에서는 tail을 강제하지 않고 끝내므로 총2 tail 강제다. 결과[0,1,2]다.

  4. 다시 take3은 같은 두 tail을 요구하지만 이미 결과가 기억되어 새 노드 생성은0이다.

첫 결과[0,1,2], 처음 tail 강제2회·새 노드2개, 반복 새 tail 생성0개다.

조건을 바꾸어 비교하기

같은 원본으로 새 mapping을 만들면 별도 캐시다

표에서 takeExact(3,q)를 마친 뒤 q를 유지한 채 q2=mapSquare(s)를 새로 만들고 takeExact(3,q2)를 요구한다. 원본 s의 이미 강제한 tail은 기억되어 있다.

  1. q2 생성에서 첫 head 제곱을 다시 실행해 H는 4가 된다.

  2. q2의 두 mapped tail도 새 객체이므로 다음 제곱 두 번이 추가된다.

  3. s의 tail 생성은 재사용해도 mapped 결과 1,4,9를 q에서 자동 가져오지는 않는다.

전체 H는 6이다. 두 mapping의 결과는 같지만 mapped lazy 객체의 정체성은 다르다.

같은 입력 값과 같은 지연 객체를 혼동하지 않는다.

filter와 take의 순서를 바꾸면 요구 범위가 달라진다

새 q에서 제곱 값이 4 이상인 것만 선택한다. (A) filter 후 takeExact로 두 결과를 얻는 방식과 (B) 먼저 q의 두 값을 takeExact하고 그 유한 목록을 filter하는 방식을 각각 새 H=0에서 비교하라.

  1. A는 제곱 1을 거절하고 4와 9를 받아 두 결과를 만든다. H는 3이다.

  2. B는 [1,4]까지만 만들고 목록에서 1을 거절하므로 [4] 하나만 남는다. H는 2다.

오해와 반례

lazy이면 모든 무한 수열 연산이 유한 시간·상수 메모리로 끝난다.

연습 1 · 값과 상태 예측

새 s와 H=0에서 q=mapSquare(s)를 생성한 다음 takeExact(0,q), takeExact(1,q)를 차례로 요구한다. 반환과 H를 적어라.

힌트 1

힌트 2

풀이와 답 확인

  1. q 생성으로 H는 1이다.

  2. takeExact(0,q)는 []를 반환하며 H는 1이다.

  3. takeExact(1,q)는 [1]을 반환하고 tail을 강제하지 않아 H는 1이다.

두 반환은 []와 [1]이며 최종 H는 1이다.

별도 Q는 head 제곱을 즉시 만들되 tail에는 기억하지 않는 thunk를 둔다. Q를 한 번 생성하고 takeExact(3,Q)를 두 번 요구할 때 제곱 실행 수를 구하라. 첫 head는 재사용하며 각 thunk 본체는 항상 새 mapped node를 만든다.

힌트 1

생성 시 head의 한 번을 먼저 센다.

힌트 2

각 take는 다음 두 head를 새로 계산한다.

풀이와 답 확인

  1. Q 생성에서 한 번 실행한다.

  2. 첫 take의 두 tail 본체에서 두 번, 둘째 take에서 같은 두 요구를 다시 계산해 두 번이다.

  3. 전체 제곱 실행은 1+2+2=5회다.

memo q의 3회와 달리 thunk Q는 전체 5회다.

결과 목록과 생산자 thunk는 다른 객체다. 목록을 다시 읽는 요구와 Q를 다시 순회하는 요구를 나눈다.

내 말로 설명하기

같은 수열 값을 가진 두 lazy root는 캐시를 공유하는가?

설명 기준 확인

별도로 만든 mapping의 lazy 객체는 자동 공유하지 않는다. 원본 tail 공유와 mapping 결과 공유를 구별한다.

filter에서 생산 가능성과 메모리 보존을 왜 따로 확인하는가?

설명 기준 확인

수락 값이 없으면 첫 결과를 만들지 못할 수 있고, root를 유지하면 이미 만든 tail도 도달 가능할 수 있다. 유한 take가 두 문제를 자동 해결하지 않는다.

한 단계 더

head를 유지한 탐색과 옛 head를 버리는 탐색의 도달 가능 객체 그림을 비교하자. 같은 lazy의 예외·동시 강제 규칙은 언어 명세로 추가 확인하고 실제 메모리 회수를 측정하지 않았으면 가능성과 관측을 구별한다.

다른 문제에 적용하기

행 번호를 읽는 작은 보고서 모형을 설계한다. (1) 입력 [0,4,1]을 값과 길이로 파싱하고 M=99 범위의 helper 검사 정책을 적는다. (2) V1 계단 규칙으로 W(4,false)와 W(2,true)를 같은 표에서 계산한 뒤 V2로 바꾼다. 완전한 키와 세 결과를 적는다. (3) 별도 새 s와 H=0에서 제곱 4 이상 두 값을 얻고 같은 mapped root로 같은 요구를 반복한다. filter 앞에 takeExact(2)를 옮긴 대안과 반환·제곱 실행 횟수를 비교한다. 각 부분은 독립 모형이며 실제 보고서 프로그램을 실행한 것이 아니다.

힌트 1

누산기에는 값과 길이가 있고 캐시 키에는 규칙과 직전 이동이 있다. 이름마다 의미를 분리한다.

힌트 2

지연 결과 두 개를 수락하려면 처음 거절한 제곱 값도 검사해야 한다. 반복은 같은 객체인지 확인한다.

풀이와 답 확인

  1. 파싱 상태는 (0,0), (0,1), (4,2), (41,3)이다. 각 자리 전 acc≤floor((99−d)/10)을 검사하고 모두 허용한다.

  2. V1의 두 값은 각각 4와 1이다. (V1,4,false)와 (V1,2,true)를 별도로 저장한다. V2의 (4,false)는 5이고 이전 키와 다르게 저장한다.

  3. filter 후 두 결과는 [4,9]이며 첫 요구까지 H는 3이다. 같은 root의 반복 요구는 추가 제곱 0회이므로 H는 3이다.

  4. take를 먼저 옮긴 독립 대안은 [1,4]에서 [4]만 남기며 H는 2다. 결과 계약을 만족하지 못하므로 낮은 작업 수만으로 채택하지 않는다.

파싱 결과는 값 41과 길이 3이다. 규칙별 캐시 값은 V1의 4와 1, V2의 5다. 정상 지연 보고는 [4,9]를 반복해도 H=3이며 순서 변경 대안은 [4]와 H=2다.

해결한 뒤 점검할 것

  • 각 접두부 값과 길이, 범위 검사 전에 사용하는 조건을 설명한다.

  • 두 boolean 상태와 두 규칙을 구별하는 캐시 키를 적고 V1의 두 값 4와 1, V2의 값 5에 이름을 붙인다.

  • 출력 개수와 실제 검사 입력 개수, 같은 lazy 객체의 재사용을 구별한다.

  • 모든 값은 손으로 계산한 예측이며 실제 언어·캐시·메모리·학습자 실행 미수행으로 남긴다.
