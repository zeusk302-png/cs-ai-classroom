소단원 1.1

shape와 broadcasting

두 예측과 두 정답을 빼는데 왜 오차가 네 개 생길 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 텐서는 여러 축을 가진 수의 배열이다. 스칼라의 shape는 (), 길이 3인 벡터는 (3,), 2행 3열 표는 (2,3)이다. shape는 각 축의 크기를 순서대로 적는다.

  • 미니복습: 행렬곱의 한 성분은 행과 열의 대응하는 수를 곱해 더한다. [1,2,3]·[1,0,1]=4이다. 원소별 곱은 같은 위치의 수끼리 곱하는 다른 연산이다.

  • 이 단원에서 B는 한 번에 처리하는 사례 수, d는 특징 수이다. 같은 shape라도 축이 사례인지 시간인지 채널인지 이름을 따로 명세해야 한다.

학습 목표

  • shape와 축의 의미를 함께 명세한다.

  • 방송 규칙을 뒤쪽 축부터 적용한다.

  • 행렬곱과 원소별 연산 및 손실의 의도치 않은 확장을 구분한다.

shape가 같으면 의도한 행에 더한 것일까?

두 사례의 두 특성을 담은 X=[[1,2],[3,4]]에서 행은 사례, 열은 특성이다. 사례별 보정값은 첫 사례에 10, 둘째 사례에 20이다. (2,) 벡터를 더하면 뒤쪽 열에 맞춰져 [[11,22],[13,24]]가 된다. 원하는 결과는 [[11,12],[23,24]]이므로 보정값을 (2,1) 열벡터로 배치해야 한다. 두 결과의 shape는 모두 (2,2)다. 사례 수와 특성 수가 우연히 같아서 크기 검사만으로 의미 오류가 드러나지 않는다.

축소 연산 뒤에도 같은 함정이 생긴다. 별도 X=[[1,3],[4,8]]의 행 평균은 2와 6이다. 평균을 (2,)로 남기면 X에서 뺄 때 [[−1,−3],[2,2]]가 된다. 각 행의 평균을 빼려면 평균 shape를 (2,1)로 유지해 [[−1,1],[−2,2]]를 얻어야 한다. 올바른 결과의 각 행 합은 0이다. 이 불변식은 shape 검사와 다른 내용 검사다.

여기서 배열 표기는 손으로 만든 수치 표다. 실제 tensor 연산은 실행하지 않았다. 차원 크기와 축 이름을 함께 기록하고, 사례 수와 특성 수가 다른 입력 및 배치 크기 1도 별도로 점검할 계획을 세운다. 크기가 다른 입력이 오류를 드러낼 수 있지만 모든 의미 오류를 자동 검출한다는 보장은 없다.

먼저 확인할 개념
  • 뒤쪽 차원의 broadcasting

    벡터의 마지막 축이 특성 축에 맞춰지는 규칙을 실제 앞 본문에서 확인한다.

  • 배치 축과 squeeze 경계

    축 이름을 유지하고 배치 크기 1에서 무분별한 squeeze가 배치 축을 없애는 경계를 사용한다.

축은 프로그램의 수학적 계약이다

입력 X의 shape (B, d)는 B개의 사례마다 d개 특징이 있다는 계약이다. W가 (d, k)이면 X@W는 (B, k)이며 각 출력은 특징 d개에 대한 가중합이다. 축을 바꾸어 (d, B)를 만들면 같은 수가 들어 있어도 다른 계산이 된다. 크기만 적고 의미를 생략하면 우연히 B=d일 때 오류가 숨을 수 있다.

예를 들어 X=[[1,2,3],[0,1,1]], W=[[1,0],[0,1],[1,1]]이면 X@W=[[4,5],[1,2]]이다. @는 내부 축의 크기 3이 일치해야 한다. X*W는 원소별 곱이며 여기서는 (2,3)과 (3,2)가 호환되지 않는다. 행렬곱을 broadcasting 규칙 하나만으로 설명해서는 안 된다.

broadcasting은 복사된 것처럼 대응시킨다

원소별 덧셈·뺄셈에서는 뒤쪽 축부터 두 크기가 같거나 한쪽이 1이면 호환된다. 부족한 앞쪽 축은 크기 1로 간주한다. (2,3)+(3,)은 (2,3)+(1,3)처럼 각 행에 같은 벡터를 더한다. (2,3)+(2,1)은 각 행마다 한 수를 세 열에 더한다. 이는 의미상 확장이지 반드시 메모리에 배열 전체를 복사한다는 뜻은 아니다.

(2,3)+(2,)은 마지막 축 3과 2가 모두 1이 아니므로 실패한다. scalar ()의 덧셈은 모든 원소에 적용된다. 크기 0인 축이 있는 빈 텐서는 양수 크기 사례와 구분해야 한다. 이 단원의 표는 모두 양수 크기 축을 사용한다. in-place 연산에는 왼쪽 저장 공간의 shape를 늘릴 수 없다는 추가 조건이 있다.

실행 성공이 의도한 손실을 뜻하지 않는다

예측 p=[1,3]의 shape (2,)와 정답 y=[[1],[3]]의 shape (2,1)를 빼면 결과는 [[0,2],[-2,0]]의 (2,2)이다. 각 사례와 자기 정답만 비교하려던 의도 대신 모든 조합을 비교했다. 제곱 평균은 2이며 같은 shape의 정답 [1,3]에 대한 올바른 평균 0과 다르다.

회귀가 사례당 출력 하나라는 계약이면 예측과 정답을 모두 (B,1)로 만들거나 모두 (B,)로 정하고 assert p.shape == y.shape를 둔다. 무조건 squeeze하면 B=1인 마지막 배치의 사례 축까지 없어질 수 있다. 축을 지정한 변환과 마지막 작은 배치 검사가 필요하다. 손실 함수가 허용하는 broadcasting도 과제의 의미와 따로 확인한다.

중간 과정을 따라가는 예제

위 X와 W에 편향 b=[1,−1]을 더해 Z=X@W+b를 계산하고 세 shape를 적어라.

  1. X는 (2,3), W는 (3,2)이므로 내부 축 3이 일치한다.

  2. 첫 행의 두 내적은 1+3=4, 2+3=5이다. 둘째 행은 1, 1+1=2이다.

  3. 행렬곱은 [[4,5],[1,2]]이다. b의 (2,)는 출력의 마지막 축 2와 맞고 앞축은 1로 확장된다.

  4. 각 행에 [1,−1]을 더하면 [[5,4],[2,1]]이다.

Z=[[5,4],[2,1]], shape (2,2)이다. 사례 축 B=2와 출력 축 k=2의 이름은 서로 다르다.

  1. (2,)는 뒤쪽 열 축에 맞춰진다.

행 합으로 중심화 오류를 찾는다

둘째 X에서 행 평균 2와 6을 두 shape로 빼고 각 행 합을 비교하라.

  1. 벡터를 빼면 첫 행 합은 −4, 둘째는 4다.

  2. 열벡터를 빼면 각 행의 두 편차가 상쇄된다.

의도한 행 중심화는 [[−1,1],[−2,2]]다.

비교할 점

전체 합은 잘못된 결과도 0이다. 전체 합만 검사하면 행별 오류를 가린다.

종이와 본문으로 직접 해보기

(2,3)+(3,), (2,3)+(2,), (2,3)+(2,1), (2,1)+(1,3)의 성공 여부와 결과 shape를 종이에 적어라.

힌트 보기

풀이 보기

순서대로 성공 (2,3), 실패, 성공 (2,3), 성공 (2,3)이다. 마지막은 행별 수와 열별 수의 모든 조합을 만든다. 성공한 조합도 문제의 의미가 맞는지 따로 확인한다.

오해와 반례

라이브러리가 오류를 내지 않았으니 예측과 정답을 제대로 비교했다.

p shape (2,), y shape (2,1)의 뺄셈은 실행되지만 네 조합을 만든다. 의도한 두 대응 쌍의 MSE는 0인데 방송된 MSE는 2이다. shape 검사에는 축 의미까지 포함해야 한다.

설명 기준 확인

크기 튜플뿐 아니라 사례·특성의 축 이름과 반복되는 보정값의 위치를 쓴다.

정방형 입력이 특별히 위험한 이유는?

설명 기준 확인

서로 다른 축의 크기가 같아 잘못된 브로드캐스팅도 shape 검사에 통과할 수 있다.

한 단계 더

방송된 정답 차이의 합은 B²개의 비교를 포함한다. 같은 shape의 올바른 손실은 B개 사례를 비교한다. 손실의 합을 평균으로 바꾸는 것만으로 이 의미 오류는 해결되지 않는다. 후속 자동미분 단원에서는 방송된 축의 기울기가 어떻게 합산되는지도 추적한다.

출처와 확인 범위

    뒤쪽 축부터 같은 크기 또는 크기 1인 축을 확장하는 규칙과 in-place 제약을 공식 문서에서 확인. 실제 보조 실행은 설치된 2.11.0+cu128의 CPU에서 수행하며 문서판과 구분한다.

소단원 1.2

배치와 데이터로더

5개 사례를 2개씩 처리할 때 마지막 1개를 버리면 평균 손실은 어떻게 달라질까?

준비 개념과 학습 목표

준비 개념

  • 데이터 한 사례는 (입력, 정답) 쌍이다. 배치는 여러 쌍을 같은 순서로 묶는다. 입력만 섞고 정답을 그대로 두면 대응이 깨진다.

  • 미니복습: 수 1,1,9의 평균은 11/3이다. 크기 2,2,1인 묶음들의 평균을 같은 비중으로 평균내면 원래 다섯 사례의 평균과 다를 수 있다.

  • 훈련·검증·시험 분리는 데이터로더를 만들기 전에 정한다. 섞기는 분리나 독립성 보장을 대신하지 않는다.

학습 목표

  • Dataset과 DataLoader의 역할을 구분한다.

  • 배치 크기와 drop_last에 따른 평가 분모를 계산한다.

  • 학습 루프의 기울기 초기화·평가 모드를 설명한다.

배치 평균을 더하면 어떤 대상의 평균인가?

패딩된 시퀀스의 목표를 유효 토큰 하나당 평균 손실로 정한다. 첫 배치의 두 사례에는 유효 토큰이 각각 1개와 3개이며 손실 합은 각각 2와 6이다. 둘째 배치의 한 사례에는 유효 토큰 8개와 손실 합 8이 있다. 전체 유효 토큰 손실은 16/12=4/3이다. 배치 평균 2와 1을 다시 같은 비중으로 평균하면 3/2라 다른 목적이 된다.

사례별 평균 손실은 2,2,1이다. 사례 하나당 같은 비중의 평균은 5/3으로 토큰 평균과도 다르다. 어느 것이 맞는지는 명세가 정한다. 패딩 칸의 손실이 0이어도 그 칸을 분모에 넣으면 유효 토큰 평균을 낮춘다. 분자와 분모는 같은 마스크와 같은 관측 범위를 사용해야 한다.

반복 추출에서는 처리 횟수와 고유 자료 개수도 다르다. 별도 세 ID 0,1,2의 고정 손실이 1,9,5이고 sampler가 0,0,2,2를 내보냈다고 하자. 네 번 처리했지만 고유 ID는 둘이고 ID 1은 빠졌다. 처리된 평균은 3, 전체 세 ID 평균은 5다. 같은 고정 손실 모형에서 평균 차이는 추출 범위 때문이며 모델 개선의 증거가 아니다.

먼저 확인할 개념
  • 배치 크기 가중 손실 집계

    배치별 합계와 개수를 누적하는 앞 본문의 분모 원리를 유효 토큰으로 확장한다.

  • sampler와 패딩 마스크

    반복 추출의 고유 ID와 collate의 패딩을 자료 개수 및 목적 단위와 구별한다.

사례를 얻는 규칙과 묶는 규칙을 나눈다

map-style Dataset은 인덱스로 사례를 가져오고 길이를 알려 주는 형태다. DataLoader는 sampler가 정한 인덱스를 사용하여 여러 사례를 가져오고 collate 함수로 묶는다. 기본 collate는 같은 크기 텐서를 새 배치 축으로 쌓고 입력과 정답의 대응을 보존한다. 길이가 서로 다른 문장은 별도 padding과 mask 계약이 필요하다.

iterable-style Dataset은 순서대로 사례를 내보내는 스트림이다. 인덱스가 있는 자료와 길이·중복·분할의 조건이 다르다. 이 단원의 계산은 길이 5의 map-style 자료, num_workers=0, 순차 sampler, batch_size=2에 한정한다. 여러 worker나 분산 sampler에 그대로 동일한 개수 보장을 적용하지 않는다.

마지막 배치와 평균의 분모를 확인한다

drop_last=False이면 배치 크기는 2,2,1이고 다섯 사례를 모두 처리한다. True이면 마지막 한 사례를 제외하여 2,2만 남는다. 훈련에서 일정 크기가 필요한 경우에는 이 선택을 명시할 수 있지만 시험 성능을 보고하면서 누락 사례를 숨기면 안 된다.

사례별 손실 [1,1,1,1,9]의 배치 평균은 1,1,9이다. 세 배치 평균의 단순 평균 11/3은 작은 마지막 배치를 과도하게 가중한다. 사례 평균은 (2·1+2·1+1·9)/5=13/5=2.6이다. 이 식은 배치 손실이 사례당 같은 가중 평균일 때 적용한다. 토큰 수나 mask 수가 다른 손실에는 실제 유효 항의 개수가 분모다.

배치 처리와 학습·평가의 상태를 분리한다

기본 훈련 순서는 optimizer.zero_grad(), 모델의 forward, loss 계산, loss.backward(), optimizer.step()이다. backward는 기울기를 누적하므로 이전 배치의 기울기를 사용할 의도가 없으면 초기화한다. forward는 예측을 만들고 step은 현재 기울기에 따라 매개변수를 바꾼다. 의도적 기울기 누적은 별도 손실 크기 조절과 갱신 주기를 요구한다.

평가에서는 model.eval()로 dropout·batch normalization 같은 모듈의 동작을 평가 모드로 바꾸고 torch.no_grad()로 기울기 그래프 작성을 끈다. 두 기능은 서로 다르며 eval만으로 기울기 기록을 끄지 않는다. 훈련 자료 섞기는 i.i.d. 훈련의 순서 효과를 줄일 수 있지만 시계열의 문맥이나 그룹 경계를 깨면 안 된다. 사용자 sampler에 복원추출이 있으면 한 epoch에 모든 사례가 정확히 한 번 나온다는 보장도 없다.

준비 개념과 학습 목표

준비 개념

  • device는 계산과 저장이 이뤄지는 CPU·가속기의 위치, dtype은 수를 저장하는 자료형이다. float32와 float64는 표현 가능한 정밀도가 다르다.

  • 미니복습: 무작위 수 생성기는 내부 상태에서 다음 값을 만든다. seed는 초기 상태를 정하지만 같은 상태 이후 어떤 순서로 몇 번 호출했는지도 결과에 영향을 준다.

  • 이 단원의 실제 확인은 작은 CPU 연산이다. 설치 패키지의 +cu128 표시는 배포 빌드 정보이며 여기서 GPU 계산을 검증했다는 뜻이 아니다.

학습 목표

  • 연산의 dtype·device 계약을 확인한다.

  • 정밀도에 따른 반올림 차이를 계산한다.

  • seed와 실행환경 기록의 역할 및 재현성 한계를 설명한다.

자료형 변환은 복사와 정보 복원을 보장할까?

gradient를 기록하지 않는 CPU float32 벡터 A=[4,7]을 가정한다. 같은 장치·자료형으로 copy=False인 to를 호출한 B는 공식 규약상 A 자체다. B의 첫 원소를 9로 바꾸면 A도 [9,7]이 된다. 반면 그 상태에서 float64로 바꿔 받은 C는 복사본이다. C의 첫 원소를 2로 바꾸면 C는 [2,7]이고 A는 [9,7]이다. to를 호출했다는 사실만으로 독립 소유권을 얻었다고 생각하면 안 된다.

형 변환은 이전 반올림도 되돌리지 않는다. 최근접 짝수 반올림의 IEEE binary32를 가정하면 정수 16777216과 16777217은 모두 float32 값 16777216으로 저장된다. 그 저장값을 float64로 넓혀도 두 값은 계속 같다. 원래 정수에서 float64로 직접 변환하면 두 정수를 구별할 수 있다. 식별 ID의 구별이 필요하다면 손실 전에 정수 원본을 보존해야 한다.

난수 소비도 상태의 소유권 문제다. 설명용 발생기가 차례로 2,5,7,1을 반환한다고 정한다. 이는 실제 PyTorch 난수 출력이 아니다. 시작 상태에서 모델이 첫 값을 받으면 2지만, 같은 발생기로 진단이 먼저 한 값을 소비하면 모델은 5를 받는다. 같은 초기 상태만 적고 소비 이력을 바꾸면 비교가 달라진다. 공식 문서 역시 seed만으로 다른 장치·버전의 완전 재현을 보장하지 않는다.

먼저 확인할 개념
  • to의 반환값과 자료형

    앞 본문의 변환 결과 사용과 float32 표현 간격에서 복사 여부 및 손실의 비가역성을 분석한다.

  • 난수 발생기와 실행 조건

    같은 초기화뿐 아니라 호출 순서와 발생기 소유권을 고정해야 하는 이유를 자체 유한 모형으로 설명한다.

변환은 명시적인 프로그램 단계다

torch.tensor의 dtype과 device를 적으면 입력 계약을 읽을 수 있다. .to(device=..., dtype=...)는 조건에 맞는 텐서를 반환하므로 반환값을 사용해야 한다. 이미 같은 조건이면 같은 객체를 돌려줄 수 있어 무조건 새로운 복사라고 해석하지 않는다. 모델의 매개변수와 buffer도 모델의 .to로 이동시킨다.

행렬곱에서는 대응하는 입력의 장치와 dtype이 호환되어야 한다. CPU float64 X와 float32 W의 @는 이 사례에서 dtype 오류를 낸다. 원소별 연산에는 자료형 승격 규칙이 있을 수 있으므로 모든 연산이 같은 규칙이라고 단정하지 않는다. 모델 이동은 일반적으로 optimizer를 구성하기 전에 하고, 입력 배치도 같은 장치의 계약에 맞춘다.

자료형은 오차와 허용 연산을 바꾼다

일반적인 IEEE float32의 유효 이진 정밀도는 24비트이다. 2²⁴=16777216 근처에서 위쪽 인접 표현값의 간격은 2이므로 1을 더한 중간값은 최근접 짝수 반올림으로 원래 수에 남는다. float64는 53비트 정밀도로 이 예의 16777217을 정확히 표현한다. 수가 작거나 크다고 모든 계산에서 같은 오차 비율을 갖는 것은 아니다.

정수 자료형의 인덱스와 실수 자료형의 특징은 용도가 다르다. 손실 함수마다 정답 자료형과 shape의 계약이 있으므로 숫자가 같다고 서로 교체할 수 없다. 낮은 정밀도의 언더플로·오버플로와 누적 순서도 결과를 바꾼다. 자료형을 높이면 이 예의 오차는 줄지만 모델 선택 오류나 데이터 누수는 해결하지 못한다.

재현성은 seed보다 넓은 실행 조건이다

torch.Generator(device="cpu").manual_seed(7)로 독립 생성기 두 개를 만들고 같은 환경에서 같은 rand 호출을 하면 해당 CPU 예에서는 같은 벡터를 얻는다. 한 생성기를 재사용하면 내부 상태가 진행한다. Python random, NumPy와 PyTorch의 난수원은 별개이므로 사용하는 원천마다 제어가 필요하다. 다중 worker의 초기화와 데이터로더 generator도 기록 대상이다.

공식 문서는 PyTorch 판·플랫폼·CPU/GPU 사이의 완전 재현성을 보장하지 않는다. seed 외에 입력, 호출 순서, 알고리즘의 결정성, 병렬 계산, 자료형, 라이브러리·드라이버 조건이 관련된다. 실제 기록에는 문서 2.14와 설치 2.11.0+cu128을 분리한다. 이 단원의 작은 CPU 확인은 전체 신경망 훈련, GPU, 다중 worker 또는 다른 기계의 재현성 검증으로 확대하지 않는다.

중간 과정을 따라가는 예제

a=16777216에 1을 더할 때 float32와 float64의 결과를 예측하고, 같은 seed의 독립 CPU 생성기 두 개로 난수를 뽑는 실험의 검증 범위를 적어라.

  1. a=2²⁴이고 float32 위쪽 간격은 2이다. 정확한 a+1은 두 표현값의 중간이다.

  2. 최근접 짝수 반올림은 이 경우 a를 선택하므로 float32 결과는 16777216이다.

  3. float64에서는 이 정수가 유효 정밀도 범위 안이므로 16777217이다.

  4. 동일 seed 생성기의 동일 호출을 같은 설치 환경에서 비교하면 이 실행의 난수 일치를 확인할 수 있다. 다른 장치나 판의 전체 학습 결과 일치까지 증명하지는 못한다.

float32: 16777216, float64: 16777217. 난수 확인은 기록된 CPU 환경과 호출에 한정한다.

A=[4,7]에서 B=A.to(dtype=float32,copy=False)를 얻어 B[0]을 9로 바꾼 뒤 float64 복사 C의 첫 값을 2로 바꾼다. 끝 값을 구하라.

  1. 같은 장치·자료형 조건에서 B는 A 자체다.

  2. float64 변환 C는 복사본이므로 그 뒤 변경은 A에 반영되지 않는다.

A와 B는 [9,7], C는 [2,7]이다.

  1. 진단이 없으면 모델은 첫 값 2를 받는다.

  2. 진단이 먼저 2를 받으면 모델은 두 번째 값 5를 받는다.

모델 값은 각각 2와 5다.

다른 문제에 적용하기

① X=[[1,3],[4,8]]의 행 평균을 (2,)로 빼는 결과와 (2,1)로 빼는 결과, 각 행 합 및 전체 평균 제곱 편차를 비교하라. ② 사례 A의 유효 토큰은 1개이고 손실 합은 2다. 사례 B의 유효 토큰은 3개이고 손실 합은 6이다. 사례 C의 유효 토큰은 8개이고 손실 합은 8이다. A와 B가 첫 배치, C가 둘째 배치일 때 토큰 평균·사례 평균·배치 평균의 평균을 구하라. ③ ID 0의 손실은 1, ID 1의 손실은 9, ID 2의 손실은 5다. 추출 순서 0,0,2,2의 처리 평균과 고유 개수·누락 ID를 보고하라. ④ 정수 16777216과 16777217을 최근접 짝수 IEEE binary32로 저장한 뒤 binary64로 넓혔을 때 구별 가능한지 설명하라. 별도로 설명용 발생기 순서 2,5,7,1에서 진단의 선행 한 번 소비가 모델 첫 값에 미치는 영향을 설명하라.

힌트 1

① 같은 shape의 두 결과라도 행별 합을 비교한다. ② 토큰·사례·배치 각각의 분모를 별도로 쓴다.

힌트 2

③ 추출된 네 손실을 더하고 ID의 집합을 센다. ④ 넓은 형에는 현재 저장값이 들어가며 발생기의 소비 위치는 상태다.

풀이와 답 확인

  1. 벡터 평균을 빼면 [[−1,−3],[2,2]]로 행 합은 −4와 4, 평균 제곱 편차는 9/2다. 열벡터 평균을 빼면 [[−1,1],[−2,2]]로 행 합은 모두 0, 평균 제곱 편차는 5/2다.

  2. 토큰 평균은 16/12=4/3이다. 사례 평균은 (2+2+1)/3=5/3이며 배치 평균의 평균은 (2+1)/2=3/2다.

  3. 처리 손실 합은 12, 처리 횟수는 4여서 평균 3이다. 고유 ID는 0과 2 두 개이며 ID 1이 누락된다. 전체 세 ID의 평균 5와 다른 범위다.

  4. 두 ID의 저장값과 넓힌 값은 모두 16777216이라 구별되지 않는다. 설명용 발생기에서 진단이 먼저 첫 값 2를 소비하면 모델은 5를 받으며, 진단이 없으면 2를 받는다. 독립 상태 발생기를 사용하면 이 모형의 진단 소비 영향을 끊는다.

행 중심화는 축 유지와 행별 불변식을 함께 확인한다. 세 평균은 토큰 4/3, 사례 5/3, 배치 3/2다. 반복 처리 평균 3의 고유 ID는 둘이며 ID 1이 빠졌다. 이미 좁은 형에서 충돌한 ID는 넓혀도 복원되지 않으며 같은 난수 초기 상태도 소비 이력이 달라지면 같은 모델 입력을 주지 않는다.

해결한 뒤 점검할 것

  • 축 이름·shape·각 행 불변식과 제곱 목적을 함께 설명한다.

  • 손실 합과 목적 단위의 분모를 일치시킨다.

  • 처리 횟수·고유 ID·전체 평가 범위를 구별한다.

  • 자료형 정밀도·복사 소유권·난수 상태를 나누고 손모형을 실측으로 주장하지 않는다.

보강 자료의 출처와 확인 범위
  • PyTorch Broadcasting semantics

    공식 본문 410–446행의 뒤쪽 축 정렬과 동일/1/없는 축 규칙을 실제 읽었다. 자체 정방형 축 오류와 행 중심화를 손추론했다.

  • PyTorch DataLoader

    공식 3782–3816/3940–3947/4395–4408행을 실제 읽었다. sampler·collate·패딩·drop_last·복원 추출을 확인했다. 자체 유효 토큰 목적의 세 분모는 손으로 계산했다.

  • PyTorch Tensor.to

    공식 854–878행의 조건 일치 self 반환·변환 복사·copy=True를 실제 읽었다. 새 실제 tensor를 만들거나 변경하지 않았다.

  • PyTorch Reproducibility

    공식 410–423행을 실제 읽어 버전·장치 한계와 같은 환경의 난수 소비를 확인했다. 설명용 2,5,7,1은 자체 유한 모형이며 PyTorch 출력이 아니다.

기본 세 소단원 전체와 같은 단원의 세 고유 선수 설명을 읽었다. 행·열 보정과 중심화의 네 결과 및 행 합·제곱 합을 손계산했다. 토큰·사례·배치의 세 평균과 반복 ID 평균·누락을 독립 단위로 계산했다. to의 조건별 객체 공유, 명시한 binary32 반올림 뒤 확장, 자체 유한 발생기의 소비 위치와 전체 전이를 손추론했다.
