소단원 7.1

서비스와 DB 경계

잔액을 빼는 함수와 더하는 함수는 각각 맞는데 이체가 실패하면 전체 잔액은 어떻게 될까?

준비 개념과 학습 목표

준비 개념

  • 함수와 상태 변화

  • 트랜잭션 기본 개념

  • DB는 자료를 저장·조회하는 데이터베이스다. fake는 실제 저장소를 흉내 낸 대체 객체이며 autocommit은 성공한 문장을 각각 확정하는 방식이다.

학습 목표

  • 단위 격리와 실제 연결 경계의 검사를 구별한다.

  • 성공·중간 실패·롤백의 관찰 상태를 설계한다.

시험 연결을 롤백하면 서비스의 다른 연결 커밋도 지워질까?

자체 DB 상태는 처음 빈 표다. 시험 준비 연결 F는 트랜잭션을 열었지만 새 행을 만들지 않는다. 서비스 연결 S가 두 행을 저장하고 자기 트랜잭션을 커밋한다. 마지막에 F를 롤백해도 S가 확정한 두 행은 남는다. 트랜잭션의 소유 연결과 경계를 표시하지 않으면 롤백 격리의 범위를 과장할 수 있다.

별도 같은 연결 모형에서 두 행을 넣고 커밋 전에 조회하면 자기 미확정 행을 볼 수 있다. 그때 개수 2가 맞아도 마지막 롤백 뒤 영구 상태는 0이다. 저장소의 재조회가 어느 연결·시점에서 이루어졌는지에 따라 시험이 묻는 질문이 달라진다.

원자성·영구 저장·클라이언트 응답 수신은 서로 다른 관찰이다. 커밋 뒤 응답을 잃으면 DB에 두 행이 남아도 요청자는 결과를 모를 수 있다. 재시도에서 중복 효과를 막는 계약은 트랜잭션 하나의 성공만으로 증명하지 않는다. 여기서는 단일 요청의 작은 연결 모형만 계산한다.

연결되는 경계에 계약이 있다

통합 테스트는 둘 이상의 구성 요소가 실제 연결됐을 때의 동작을 확인한다. 서비스→드라이버→DB 에서 SQL/자료형/제약/트랜잭션 경계는 함수 내부 계산만 검사해서 드러나지 않을 수 있다. fake DB 가 좋다고 실제 DB 계약도 같다고 가정하지 않는다.

우리 자체 이체 서비스는 A100/B20 에서 30 을 보내고 성공 시 A70/B50 을 만든다. 금액은 정수 단위이며 인증·동시 이체·과금 등을 생략한 단일 요청이다. 테스트 계획은 실제 사용하는 DB 버전·스키마·연결 설정도 적고 가상 상태표와 실행 결과를 구별한다.

트랜잭션의 범위를 확인한다

같은 DB 트랜잭션에서 두 갱신을 성공하면 COMMIT 하고 실패하면 ROLLBACK 한다. 차감 후 장애를 주입해 최종 잔액이 초기 상태로 돌아오는지를 검사할 수 있다. SQL 한 문장씩 자동 커밋되어 차감만 남는 모형과 구별한다.

DB ROLLBACK 이 이미 보낸 이메일이나 외부 HTTP 쓰기를 자동 취소하지 않는다. 다른 연결의 커밋도 같은 트랜잭션이라고 가정하면 안 된다. 여러 시스템의 부분 성공은 별도 조정/재시도/중복 처리 계약으로 설계하며 여기서 분산 원자성을 입증하지 않는다.

예상 상태와 관찰 지점을 선언한다

검사는 응답 코드뿐 아니라 DB 의 최종 상태도 본다. 성공 응답을 먼저 보내고 저장이 실패하면 클라이언트와 DB 가 모순될 수 있다. 장애 위치는 차감 전·차감 후·반영 후 응답 전처럼 나누고 각 위치의 기대 상태를 계약으로 적는다.

입력 오류는 변화를 만들기 전에 거절해야 한다. 같은 요청을 다시 보낸 경우 두 번 이체할지, 키로 중복을 막을지도 명시한다. 단순 합 보존만 검사하면 A60/B60 처럼 잘못된 두 잔액이 합 120 으로 통과할 수 있으므로 개별 계좌 값도 확인한다.

중간 과정을 따라가는 예제

A100/B20, 이체 30 에서 성공·차감 직후 실패(동일 트랜잭션 롤백)·각 문장 autocommit 실패 세 경우의 최종 잔액을 비교하라.

  1. 성공은 A100−30=70,B20+30=50 으로 합 120 이다.

  2. 같은 트랜잭션에서 A70 까지 갱신한 뒤 실패해 ROLLBACK 하면 A100/B20 으로 합 120 이다.

  3. 각 문장을 커밋해 차감 70 이 확정된 뒤 입금 실패면 A70/B20 으로 합 90 이다. 내부 함수의 두 계산이 맞아도 묶음 경계가 틀렸다.

원자 이체의 기대는 성공 70/50 또는 실패 100/20 이다. autocommit 실패 70/20 은 계약 위반이다.

준비 개념과 학습 목표

준비 개념

  • 소비자와 제공자의 버전 호환을 조건별로 계산한다.

필드 생략과 null이 둘 다 스키마에 맞아도 효과는 같을까?

자체 PATCH 계약에서 메모 필드는 선택 사항이며 값은 문자열 또는 null이다. 필드 생략은 기존 값을 유지, null은 지우기, 문자열은 대체로 정한다. 초기 메모가 “학습 중”일 때 {}, {memo:null}, {memo:"완료"}는 구조상 모두 허용해도 각각 유지·삭제·대체라는 다른 효과다.

구조만 통과하는 구현이 생략까지 지우기로 처리하면 {} 사례에서 계약을 어긴다. optional은 부재가 허용된다는 뜻이고 nullable은 null 값이 허용된다는 뜻이므로 별도로 정해야 한다. 이 PATCH 의미는 자체 서비스 계약이며 모든 API나 JSON Schema의 자동 동작으로 일반화하지 않는다.

소비자 계약은 제공자 상태를 설정하고 특정 요청의 응답과 필요한 효과를 확인한다. 예를 들어 동일 ID 조회라도 자료 존재/부재 상태가 다르면 기대 상태 코드가 달라진다. 새 enum 값 추가도 소비자가 모르는 값을 거절하는지에 따라 호환성이 달라질 수 있어 필드 추가 여부만으로 판단하지 않는다.

    모양 검사를 상태와 효과의 계약으로 연결한다.

  • 명세에서 기대 결과 만들기

    생략·삭제·대체의 정답을 구현에서 복사하지 않는다.

모양과 필수 조건을 명시한다

스키마는 데이터의 허용 구조를 적는다. JSON Schema 에서 properties 로 타입을 적는 것만으로 필수 필드가 되지 않으므로 required 를 함께 정한다. null 값과 필드 부재는 다르다. 추가 필드를 허용할지도 명시하며 JSON 문법 통과와 스키마 통과를 구별한다.

이 자체 응답은 id 가 양의 정수이고 amount 가 0 이상 정수다. C1 소비자는 id/amount 를 필수로 읽고 추가 필드를 무시한다. C2 소비자는 currency 문자열도 필수로 읽는다. 스키마는 이 소비자 동작의 일부이며 돈의 실제 정확성이나 권한까지 자동 보장하지 않는다.

계약은 메시지와 의미를 연결한다

API 계약에는 메서드·경로·헤더·상태·본문과 사전 상태/부작용도 포함될 수 있다. 소비자 테스트의 요청/응답 사례를 제공자에게 대조하는 방식은 실제 사용의 기대를 연결한다. 단독 제공자 스키마 검사만으로 소비자가 올바르게 호출한다는 증거는 되지 않는다.

GET /payments/7 에서 해당 ID 가 있는 상태의 200 응답과 없는 상태의 404 응답을 별도 사례로 적는다. 모든 숫자 응답이 스키마에 맞아도 ID8 의 데이터를 ID7 요청에 반환하면 의미가 틀린다. 어느 상태와 어떤 요청인지 함께 검증한다.

호환은 변화와 소비자 조건에 따른다

제공자 P1 은 {"id":7,"amount":120}, P2 는 여기에 "currency":"KRW"를 더한다. 추가 필드를 무시하는 C1 에는 모두 맞고 currency 필수 C2 에는 P1 이 부족하다. amount 를"120"으로 바꾸면 양쪽의 정수 기대가 깨진다.

추가 필드를 금지하는 엄격한 소비자는 P2 도 거절할 수 있다. 그러므로 추가는 언제나안전이라는 규칙 대신 실제 파서·스키마·의미를 본다. 계약 통과가 성능·권한·실제 네트워크·전체 사용자 흐름까지 통과했다는 뜻도 아니다.

소단원 7.3

환경과 test data

혼자 실행할 때 통과한 테스트가 앞의 테스트 뒤에서만 실패하면 입력 함수보다 무엇을 먼저 의심할까?

준비 개념과 학습 목표

준비 개념

  • 상태와 초기화

  • 시간과 식별자

  • fixture는 테스트 환경 준비와 정리 장치, scope는 공유 수명 범위, seed는 난수의 초기 설정이다.

학습 목표

  • 테스트의 준비·실행·정리와 환경을 기록한다.

  • 공유 상태·순서·병렬 실행의 오염을 추적한다.

생성 키를 격리해도 정리 조건이 넓으면 다른 시험을 지울까?

자체 합성 표에는 (R1,x)와 (R2,x) 두 행이 있고 복합키 (run_id,name)는 유일하다. R1의 정리가 WHERE name=x만 사용하면 두 행을 모두 지운다. 생성의 namespace가 맞아도 정리가 소유 범위를 지키지 않으면 다른 실행을 오염시킨다.

R1 정리 조건을 run_id=R1 AND name=x로 제한하면 R1 행만 지우고 R2 행은 남긴다. 이 조건에서도 권한·외부 자원·잔여 작업까지 자동 검증한 것은 아니다. 생성·관찰·정리 각각이 같은 소유 경계를 보존하는지 계획하고 실제 결과를 기록해야 한다.

준비 실패는 성공한 자원 생성의 경계도 중요하다. pytest의 yield 전 예외는 해당 yield 뒤 정리를 실행하지 않는다. 성공한 자원 획득 뒤 finalizer를 등록하면 이후 실패에도 그 등록된 정리가 실행 대상이지만, 실제 해제 성공이나 등록 이전 부분 생성 실패는 별도 확인해야 한다.

먼저 확인할 개념
  • 격리 영역과 고유키

    생성뿐 아니라 관찰과 삭제 조건까지 같은 실행 범위를 보존한다.

  • 정리 등록과 해제 성공

    등록된 호출과 실제 자원 해제 결과를 구별한다.

각 테스트의 출발 상태를 만든다

fixture 는 테스트에 필요한 환경과 자료를 준비하고 정리하는 장치다. 같은 코드라도 초기 DB 행·시계·시간대·언어·스키마 버전이 다르면 결과가 달라질 수 있다. 필요한 환경을 기록하고 테스트마다 기대하는 초기 상태를 명시한다.

우리 Tcreate 는 빈 격리 영역에 두 가상 레코드를 만들고 개수 2 를 기대한다. Tempty 는 자신의 빈 영역에서 0 을 기대한다. 같은 저장소를 쓴다는 이유로 이전 테스트의 행까지 포함하면 Tempty 의 실패가 기능 결함인지 준비 실패인지 구별하기 어려워진다.

정리의 실패 경로를 설계한다

준비→검사→정리의 모든 경로를 생각한다. pytest yield fixture 는 yield 뒤에 정리를 둘 수 있지만 해당 fixture 가 yield 전에 실패하면 그 뒤의 정리는 실행되지 않는다. 하나의 자원 생성과 짝인 정리를 작은 단위로 묶어 이미 만들어진 자원이 남지 않게 설계한다.

DB 트랜잭션 롤백으로 격리할 때도 서비스가 다른 연결로 커밋하거나 메일을 보내면 그 작업은 남을 수 있다. 세션 공유 fixture 로 속도를 얻으면 가변 상태를 공유하는지 확인한다. 테스트 실패 후 정리까지 실제로 검증했는지 별도로 기록한다.

동시성과 재현 정보를 남긴다

병렬 실행 R1/R2 는 같은 이름 x 를 만들 수 있다. 자체 고유키 (run_id,name)를 쓰면 (R1,x)/(R2,x)가 서로 다르지만 name 만 고유하면 충돌한다. namespace 는 테스트 영역을 구별하는 표식이며 실제 업무 고유 제약과 혼동하지 않는다.

가상 시계 1000/1100 의 차 100ms 를 검사하면 실제 벽시계 대기와 다르다. 난수 seed/초기 상태/버전 기록은 실패 재현을 돕지만 각 플랫폼·네트워크·동시 순서까지 자동 고정하지 않는다. 실제 사용자 개인 자료 대신 자체 합성 자료를 쓰고 환경 검증이 완료됐다고 허위 표시하지 않는다.

중간 과정을 따라가는 예제

공유 영역 초기 0 에서 Tcreate 가 2 행을 만들고 정리하지 않은 뒤 Tempty 가 개수 0 을 검사한다. 격리된 영역 또는 완전 정리가 있으면 각 결과는?

  1. 공유/정리 없음은 Tcreate 뒤 개수 2 로 자기 검사 통과다.

  2. Tempty 는 실제 2 를 보아 기대 0 과 달라 실패한다. 순서를 뒤집으면 Tempty 는 0 으로 먼저 통과하지만 오염 원인은 남는다.

  3. 각 테스트별 빈 영역이나 Tcreate 뒤 정리가 완료되면 Tempty 는 0 으로 통과한다. 테스트 순서 한 개의 통과는 격리 증명이 아니다.

두 테스트의 계약과 초기 상태를 맞춘다. 이 표는 실제 테스트 실행 로그가 아니다.
