소단원 4.1

fixture와 assertion

혼자 실행하면 통과하는 테스트가 다른 테스트 다음에는 실패하는 이유는 무엇일까?

준비 개념과 학습 목표

준비 개념

  • 테스트는 준비·동작·확인 단계를 구별한다.

  • 같은 가변 객체를 공유하면 앞의 변경이 뒤에 남을 수 있다.

  • 이 단원의 코드와 테스트 결과는 종이 판정이며 Python 실행을 하지 않았다.

학습 목표

  • fixture를 준비와 정리의 과정으로 설명한다.

  • 기대한 결과를 명시하는 assertion을 선택한다.

  • 테스트 사이 상태 누출과 준비 실패 시 정리를 추적한다.

매번 시작 상태를 만들기

fixture는 테스트 실행에 필요한 준비와 관련 정리다. 데이터 파일만을 뜻하지 않는다. 새 지갑 객체를 만들거나 임시 자원을 준비하고 종료 때 정리하는 것도 fixture다. 각 테스트가 어떤 초기 상태를 가정하는지 명시하고 앞선 테스트가 준비해 주리라고 기대하지 않는다.

Python unittest의 setUp은 각 테스트 메서드 전에 호출된다. 새 지갑을 매번 만들면 시작 잔액이 10으로 되돌아온다. 반대로 클래스나 모듈의 가변 객체를 그대로 공유하면 test A가 쓴 잔액을 test B가 읽을 수 있다. 격리는 순서를 바꿔도 개별 테스트의 뜻이 유지되는지 확인하는 기준이다.

무엇을 확인하는지 분명하게

assertion은 요구한 결과와 관찰 결과를 비교해 기대가 깨졌음을 드러낸다. 잔액이 7이어야 한다면 assertEqual(실제 잔액,7)을 쓰고 단지 객체가 존재하는지만 확인하지 않는다. 오류 입력에서는 특정 예외를 기대하는 assertRaises를 쓸 수 있다. 출력값·상태·예외·필수 상호작용 중 계약에 필요한 것을 고른다.

일반 Python assert 문은 최적화 옵션에서 생략될 수 있으므로 unittest의 전용 assertion 메서드와 구별한다. 테스트가 예외 없이 끝났다는 것만으로 결과가 올바른 것은 아니다. 한편 모든 내부 변수까지 고정하면 구현을 바꿀 때 의미 없는 실패가 늘 수 있으므로 외부에서 약속한 동작을 중심으로 확인하자.

실패해도 자원을 정리하기

setUp이 성공하면 테스트가 성공하거나 실패해도 tearDown이 실행된다. 하지만 setUp 자체가 예외로 끝나면 테스트 본문과 tearDown은 실행되지 않는다. 준비 중 자원을 얻은 뒤 다음 단계가 실패할 가능성이 있으면 자원 획득 직후 addCleanup으로 정리를 등록하는 방식이 유용하다.

등록한 cleanup은 뒤에 등록한 것부터 호출된다. 자원 A를 얻고 B를 얻은 경우 B 다음 A 순서로 정리하는 상황을 생각할 수 있다. 정리 과정도 실패할 수 있고 외부 서비스가 남긴 상태를 완벽히 복구한다는 보장은 없으므로 실제 자원의 종료 규칙을 확인해야 한다. 여기서는 파일이나 서버를 만들지 않고 순서만 종이로 추적한다.

중간 과정을 따라가는 예제

지갑 규칙은 시작 잔액 10, 출금 3이면 잔액에서 3을 뺀다. A와 B는 각각 출금 3 후 잔액 7을 확인한다. 매 테스트 새 지갑을 만드는 경우와 공유 지갑 하나를 A→B 순서로 사용하는 경우를 비교하라.

  1. 독립 fixture에서 A는 새 잔액 10을 받아 10−3=7을 확인하므로 종이 기대와 일치한다.

  2. B도 새 잔액 10으로 시작하여 10−3=7이 된다. A의 결과를 입력으로 받지 않는다.

  3. 공유 fixture에서는 A 뒤 잔액 7이 남는다.

  4. B가 같은 지갑에서 3을 출금하면 7−3=4다. 기대값 7과 실제 모형값 4가 다르므로 B가 실패해야 한다.

  5. 공유 상태 때문에 B의 의미가 A의 실행 여부에 의존한다. 실제 테스트 러너를 실행한 PASS/FAIL 기록이 아니라 이 입력에 대한 종이 판정이다.

독립 fixture에서는 각 결과 7이다. 공유 A→B에서는 7 뒤 4가 되어 B의 기대 7과 불일치한다.

종이와 본문으로 직접 해보기

setUp이 A를 얻고 cleanup(A)를 등록한 뒤 B를 얻고 cleanup(B)를 등록한다. 그 다음 예외가 나면 테스트 본문·tearDown·두 cleanup은 어떻게 되는가? 또 잔액 4인 상황에서 assertTrue(지갑 객체가 존재함)만 확인하면 오류를 잡는가?

힌트 보기

setup 실패 시 teardown과 등록된 cleanup의 규칙을 구별하라. 객체 존재와 잔액 계약은 다른 조건이다.

풀이 보기

본문과 tearDown은 실행되지 않으며 이미 등록된 cleanup(B), cleanup(A)가 역순으로 호출된다. 객체가 존재한다는 assertion만으로 잔액 4≠7 오류를 검출하지 못한다. 자원을 실제로 얻고 해제한 실험은 하지 않았다.

오해와 반례

fixture를 한 번 만들어 공유하면 준비 시간이 줄어드니 모든 단위테스트에 더 좋다.

공유 지갑에서는 A의 변경 때문에 B가 잔액 4를 읽는다. 가변 상태를 공유하면서 매 테스트 의미가 유지되려면 별도의 격리·초기화 규칙이 필요하다. 속도를 위해 기대 결과나 실패 시 정리를 없애서는 안 된다.

소단원 4.2

mock·stub·fake

인터넷에 연결하지 않고 주문 알림을 한 번만 보냈는지 확인하려면 무엇을 대신 둘 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 테스트 대상과 협력하는 가격 조회·저장·알림 등의 의존성을 구별한다.

  • 대역은 실제 의존성 대신 테스트에서 사용하는 객체나 함수다.

  • 용어는 팀마다 다를 수 있어 이 단원은 Fowler가 소개한 Meszaros 구분을 사용한다.

학습 목표

  • stub·fake·mock을 테스트에서 맡는 역할로 구별한다.

  • 반환값·최종 상태·필수 호출을 따로 확인한다.

  • 대역으로 통과한 결과와 실제 연동 검증의 범위를 구별한다.

답을 준비하는 stub과 동작하는 fake

stub은 필요한 요청에 미리 정한 답을 준다. 상품 A 가격을 요청하면 5를 반환하도록 만든 함수가 예다. 실제 가격 서버를 호출하지 않으면서 계산 코드에 일정한 입력을 넣는다. 반환값을 고정했다는 사실은 실제 서버의 형식이나 오류 응답이 같은지 검증했다는 뜻이 아니다.

fake는 테스트에 충분한 동작을 구현하되 운영 환경에는 맞지 않는 단순화가 있다. 메모리 사전에 재고를 저장하고 조회·차감을 실제 수행하는 재고 저장소를 만들 수 있다. 이 fake가 값 변경을 잘 처리해도 실제 데이터베이스의 잠금·격리·영속성·동시 장애를 그대로 흉내 냈다고 가정하지 않는다.

약속한 상호작용을 확인하는 mock

mock은 예상 호출에 관한 검증 역할을 가진 대역이다. 결제 승인 후 알림을 정확히 한 번, 상품 A와 수량 2로 요청해야 한다는 계약을 확인할 때 유용하다. Python unittest.mock은 호출 기록과 assert_called_once_with 같은 검사 도구를 제공한다. 다만 Mock이라는 클래스 이름만으로 언제나 이 역할이 정해지는 것은 아니다.

같은 Mock 객체를 반환값만 고정하는 stub 역할로도 쓸 수 있다. 호출을 기록만 하면 spy 역할로 이야기할 수 있다. 도구 이름보다 무엇을 준비했고 무엇을 검증했는지 적자. 요구하지 않은 내부 함수 호출 순서까지 고정하면 내부 구조를 개선한 뒤 동작은 같은데 테스트가 깨지는 문제가 생긴다.

경계의 실제 계약을 남기기

대역이 실제 API와 달라져 테스트가 잘못 통과할 수 있다. spec이나 autospec으로 허용 속성·호출 서명을 제한하면 일부 API 오용을 잡을 수 있지만 실제 서버의 인증·직렬화·타임아웃이나 DB 제약까지 보장하지는 않는다. 중요한 경계는 별도의 계약·통합 테스트가 필요하다.

의존성을 함수 인자로 전달하면 어느 협력자를 대체하는지 드러난다. patch를 쓰는 경우에는 원래 정의된 위치가 아니라 테스트 대상이 해당 이름을 조회하는 위치를 바꾸어야 할 수 있다. 대역은 결함을 숨기기 위해 모든 답을 성공으로 만드는 장치가 아니라 확인할 조건을 통제하는 도구다.

중간 과정을 따라가는 예제

자체 주문 모형은 상품 A 수량 2를 받는다. 가격 stub은 단가 5를 준다. 재고 fake는 A=4로 시작해 수량만큼 차감한다. 승인 성공 때 notify(A,2)를 정확히 한 번 요청한다. 금액·재고 상태·알림 검증 항목을 각각 구하라.

  1. 가격 stub이 단가 5를 주므로 계산 대상의 총액은 5×2=10이다. 가격 서버를 조회한 값이 아니다.

  2. 재고 fake의 시작 4에서 주문 2를 빼면 4−2=2다. 최종 상태 A=2를 확인한다.

  3. 승인 성공 분기에서 알림 협력자에게 notify(A,2)를 한 번 요청한다는 기대를 적는다.

  4. 호출 검사는 정확한 횟수 1과 인자 A,2를 모두 포함한다. 호출 한 번만 세고 잘못된 상품 B를 허용하면 계약을 놓친다.

  5. 총액 10, 재고 2, 필수 호출 한 번을 확인해도 실제 알림 서비스 전달 성공이나 DB 트랜잭션을 증명하지 못한다. 이 세 역할을 종이로 추적했으며 테스트 실행은 미수행이다.

금액 10, fake 재고 A=2, notify(A,2) 정확히 한 번을 각각 기대한다.

종이와 본문으로 직접 해보기

실제 단위테스트를 실행한 것이 아닌 호출 기록 카드가 [notify(A,2),notify(A,2)]일 때 기대를 판정하라. 승인 실패 분기에서는 재고를 차감하지 않고 알림도 요청하지 않는다고 정하면 시작 재고 4의 기대 상태와 횟수는 무엇인가?

힌트 보기

인자가 맞는지와 횟수가 맞는지를 따로 보라. 실패 분기의 계약은 성공 분기에서 가져오지 않는다.

풀이 보기

첫 기록은 인자는 맞아도 두 번 호출하여 정확히 한 번이라는 기대에 어긋난다. 승인 실패 모형의 기대는 재고 4 유지, 알림 횟수 0이다. 실패 분기의 호출 0과 상태 보존도 명시적으로 확인해야 한다.

오해와 반례

Mock 객체를 사용한 테스트가 통과하면 실제 서버와 데이터베이스 연동도 검증된다.

가격 5를 고정한 stub과 재고 사전 fake에는 실제 서버 응답이나 DB 잠금이 없다. notify 요청이 한 번 기록돼도 메시지 전달 성공은 별도다. 대역을 사용하는 단위 검증과 실제 경계 검증의 범위를 나누어 보고해야 한다.

소단원 4.3

결정성·빠른 피드백

시간 경계 테스트를 빨리 돌리려면 기다리는 시간을 줄이는 것만으로 충분할까?

준비 개념과 학습 목표

준비 개념

  • 같은 통제 입력에 같은 관찰 결과가 나오는 성질을 결정성이라 한다.

  • 실제 시계·난수·네트워크·공유 상태·스케줄링은 테스트 결과를 흔들 수 있다.

  • 아래 시간표는 가정한 작업 비용이며 실제 테스트 실행 시간 측정이 아니다.

학습 목표

  • 시계와 외부 의존성을 통제한 경계 검증을 설계한다.

  • 격리와 빠른 피드백이 연결되는 이유를 설명한다.

  • 재시도 통과와 원인 해결을 구별하고 실행 시간의 조건을 적는다.

실제 시간이 아니라 입력 경계를 확인하기

만료 규칙을 now>=expires_at이면 만료로 정하자. 시간을 함수 인자로 넣으면 만료 직전·정확한 경계·직후를 기다리지 않고 검사할 수 있다. now=119,120,121과 expires_at=120을 넣는 세 사례는 입력이 명확하다. 실제 시계에서 1초를 기다리면 스케줄링 지연 때문에 의도한 경계를 지나칠 수 있다.

시간 주입은 테스트 중 제어 지점을 만드는 방법이다. 실제 시스템의 시간대·단위·시계 종류가 맞는지 검증하는 일은 여전히 남는다. 날짜 문자열과 초 단위 정수를 섞으면 같은 120처럼 보여도 의미가 다를 수 있다. 이 예에서는 같은 기준의 정수 초만 사용하며 실제 인증이나 만료 서비스를 만들지 않는다.

반복할 수 있는 입력과 독립 상태

결정적인 테스트에는 입력뿐 아니라 초기 상태와 의존성의 응답도 통제되어야 한다. 앞선 테스트의 재고가 남거나 외부 서버가 그때그때 다른 답을 주면 결과가 흔들린다. 난수 시드를 고정하는 방법도 있지만 그 하나만으로 스레드 실행 순서·네트워크·시계·라이브러리 버전 차이까지 없애지는 못한다.

실패했다가 재실행하면 통과하는 flaky 테스트는 믿을 만한 신호를 약하게 만든다. 재시도해서 초록 표시를 얻는 것과 원인을 고치는 것은 다르다. 어떤 입력·시드·환경·순서에서 실패했는지 기록하고 공유 자원이나 경계·타임아웃 조건을 조사하자. 항상 성공만 반환하는 대역으로 실패 조건을 지우면 검출력을 잃는다.

빠름의 조건과 남은 확인

작은 격리 테스트는 외부 대기 비용을 줄이고 변경 직후 피드백을 주기 좋다. Google의 Test Sizes 글은 내부 분류의 접근 제약과 임의 순서 실행·격리를 설명한 역사적 자료다. 그 글의 시간 한도를 모든 프로젝트의 최신 표준으로 삼지 말고 우리 프로젝트의 자원·실행 비용을 측정해 목표를 정한다.

독립 테스트를 병렬 실행하면 기다림을 줄일 수 있지만 자원 경쟁·시작 비용·직렬 의존성이 있으면 단순한 최대값 계산과 달라진다. 검증 항목을 삭제해 빨라진 테스트와 같은 계약을 더 빠르게 확인하는 테스트도 구별하자. 단위테스트로 빠른 신호를 얻더라도 실제 통합·브라우저·장비 검증이 필요한 요구를 별도로 유지한다.

중간 과정을 따라가는 예제

is_expired(now,expiry)는 같은 기준 정수 초에서 now>=expiry를 반환한다고 정한다. expiry=120, now=119/120/121의 기대 결과를 구하라. 독립 테스트 세 개의 종이 비용이 2/3/5초이며 시작·자원 경쟁 비용이 없다면 순차 실행과 세 작업자 동시 시작 시간도 구하라.

  1. 119>=120은 거짓이므로 직전 입력은 미만료다.

  2. 120>=120은 참이므로 정확한 경계는 만료다. 규칙이 >라고 잘못 구현되면 이 사례가 오류를 드러낸다.

  3. 121>=120도 참이므로 직후 입력은 만료다.

  4. 순차 실행의 가정 시간은 2+3+5=10초다.

  5. 서로 독립이고 세 작업자가 동시에 시작하며 경쟁·시작 비용이 없다면 가장 늦게 끝나는 5초가 전체 완료 시점이다. 실제 측정이나 일반 병렬 속도 보장은 아니다.

결과는 False/True/True다. 제한된 시간 모형에서는 순차 10초, 세 작업자 동시 실행 5초다.

종이와 본문으로 직접 해보기

작업자가 두 명이라면 5초 테스트를 첫 작업자에, 2초 후 3초 테스트를 둘째 작업자에 배치해 전체 시간을 구하라. 모두 한 개의 재고 사전을 초기화 없이 공유할 때 이 병렬 시간만 보고 안전한 실행이라고 말할 수 있는가?

힌트 보기

둘째 작업자의 2+3과 첫 작업자의 5를 비교하라. 시간 계산의 독립성 가정이 실제 공유 상태에서 유지되는지 보라.

풀이 보기

정한 배치에서는 max(5,2+3)=5초다. 하지만 가변 사전을 공유하며 읽기·차감이 충돌하면 독립성 가정이 깨져 상태와 실행 순서에 따라 결과가 달라질 수 있다. 시간표 5초는 격리나 스레드 안전 검증 결과가 아니다.

오해와 반례

난수 시드를 고정하고 실패 테스트를 재시도해 통과하면 결정성과 품질이 확보된다.

시드를 고정해도 실제 시계나 공유 재고·스레드 순서가 달라질 수 있다. 120 경계에서 >와 >=를 잘못 쓰는 결함은 재시도로 고쳐지지 않는다. 통제한 입력과 격리·경계 기대를 확인하고 실패 원인을 조사해야 한다.
