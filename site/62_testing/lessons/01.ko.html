소단원 1.1

error·fault·failure

평균 함수에 결함이 있는데도 [0]을 넣으면 왜 정답처럼 보일까?

준비 개념과 학습 목표

준비 개념

  • 함수는 입력에 대응하는 출력이나 예외를 낸다. 계약은 허용 입력과 요구 결과를 정한 약속이다. 목록 길이는 원소 개수다. 산술평균은 비어 있지 않은 숫자 목록의 합을 개수로 나눈 값이다.

학습 목표

  • 이 단원 용어 문맥에서 사람의 오류·결함·실패를 구별한다

  • 결함 활성화와 관찰 가능한 실패를 구분한다

  • 기대값을 독립적으로 정하는 oracle의 역할을 설명한다

원인·산출물·관찰 결과는 다르다

여기서는 ISTQB4.0.1의 error를 사람이 한 실수, fault/defect를 코드·요구 문서 같은 산출물의 결함, failure를 요구한 동작과 다른 실행 결과로 쓴다. “개수에 1을 더해야 한다”는 작성자의 실수로 분모 n+1이 코드에 남고 평균이 다르게 나오면 세 층을 구분할 수 있다.

다른 분야의 error는 실행 중 잘못된 내부 상태나 수치 오차를 가리키기도 한다. error라는 영어 단어가 언제나 사람의 실수만 뜻한다고 일반화하지 않는다. 모든 실패 원인이 작성자의 실수라고 단정하지도 않는다. 환경 조건과 요구 자체의 문제도 조사해야 한다.

결함은 특정 입력에서 가려질 수 있다

이 예제의 계약은 비어 있지 않은 정수 목록을 받아 정확한 유리수 평균을 내는 것이다. buggy_mean은 분모를 n+1로 잘못 쓴다. [2,4]는 합 6, 길이 2이므로 요구값 3인데 실제 2가 된다. [0]은 0/1과 0/2가 모두 0이므로 같은 결함을 지나도 반환값만 보면 실패가 드러나지 않는다.

[-1,1]도 합이 0이라 결함이 가려진다. 분모 차이를 관찰할 수 있는 입력을 선택해야 한다. 이 함수만 분석하면 유효 입력에서 n≥1이므로 s/n=s/(n+1)의 필요충분조건은 합s=0이다. 통과 입력 몇 개가 모든 입력의 정확성 증명은 아니다.

from fractions import Fraction

def buggy_mean(values):
    # 이 예제의 입력은 비어 있지 않은 정수 목록이라고 가정한다.
    return Fraction(sum(values), len(values) + 1)

관찰에는 믿을 수 있는 판정 근거가 필요하다

테스트 oracle은 관찰 결과가 요구와 맞는지 판단하는 근거다. [2,4]의 기대값은 평균 정의로 독립 계산한 3이다. 결함 코드와 똑같이 sum/(n+1)을 기대값 생성에 쓰면 양쪽이 같은 잘못을 공유하여 테스트가 통과할 수 있다. 실행했다는 사실과 옳은 판정을 했다는 사실은 다르다.

코드를 읽어 분모가 계약과 다르다고 찾는 정적 검토는 프로그램을 실행하지 않아도 결함을 찾는다. 동적 테스트는 선택 입력으로 실행하여 결과를 관찰한다. 실패가 관찰되면 재현·원인 진단·수정·재확인을 연결해야 하며 관찰되지 않았다는 이유로 결함 없음이라고 쓰지 않는다.

중간 과정을 따라가는 예제

[0]과 [2,4]를 buggy_mean에 넣어 기대값·실제값을 비교하라.

  1. [0]:n=1,s=0,기대 0/1=0.

  2. 실제는 0/2=0으로 출력이 같아 실패가 관찰되지 않는다.

  3. [2,4]:n=2,s=6,기대 6/2=3.

  4. 실제 6/3=2이므로 평균 계약에 대한 실패가 드러난다.

결함은 두 실행 모두에 있지만 [0]은 반환값 차이를 가리고 [2,4]는 드러낸다. 본문 코드의 실제 Python 결과도 각각 0,2였다.

종이와 본문으로 직접 해보기

[-1,1]과 [3]의 기대값/결함값을 손으로 계산하고 결함을 더 잘 드러내는 입력을 고르라.

힌트 보기

합이 0인지 확인하고 분모는 각각n과n+1이다.

풀이 보기

[-1,1]은 0/2=0과 0/3=0, [3]은 3/1=3과 3/2=1.5이다. [3]이 반환값 차이를 드러낸다. Fraction은 1.5를 3/2라는 정확한 유리수로 표현한다.

오해와 반례

테스트 한 번이 통과하면 코드에는 결함이 없다.

[0] 통과는 분모 결함의 반례다. 관찰 입력과 oracle가 볼 수 있는 동작만 확인했으므로 다른 입력이나 다른 계약의 문제를 배제하지 못한다.

답과 이유 보기

한 단계 더

심화: n≥1에서 s/n=s/(n+1)을 양의 n(n+1)로 곱하면 s(n+1)=sn, 따라서 s=0이다. 이 작은 함수의 출력 차이가 없는 입력 조건을 증명했다. 이는 I/O·동시성·자원 부족이 있는 실제 제품 전체의 무결함 증명이 아니다.

소단원 1.2

검증과 확인

명세대로 평균을 계산하는 프로그램도 사용자의 성적 산정 방식에는 틀릴 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 요구는 원하는 동작의 조건이다. 명세는 입력·결과·예외를 구체적으로 적은 약속이다. 유리수는 정수의 비이며 분모가 0이면 정의되지 않는다. 예외는 함수가 정상 값을 반환하지 않고 정해진 실패 경로를 알리는 것이다.

학습 목표

  • 명시 요구의 충족과 실제 필요의 적합을 구별한다

  • 입력·예외·기대값을 포함한 테스트 계약을 쓴다

  • 관찰 범위와 미확인 사용자 요구를 기록한다

무엇과 대조하는지에 따라 질문이 달라진다

이 소단원은 verification을 명시된 요구 충족의 검증, validation을 의도한 사용자 필요와 사용맥락에 대한 확인으로 구별한다. 구현이 “모든 점수의 같은 가중치 평균”을 정확히 계산하는지와 실제 업무가 “평가별 가중치 평균”을 필요로 하는지는 다른 질문이다.

한국어 번역과 학문 분야에 따라 용어가 다를 수 있다. MIT 읽기 자료는 validation을 검증·코드리뷰·테스트를 포괄하는 뜻으로도 쓴다. 이 본문에서는 ISTQB의 요구/사용자 필요 구분을 사용하며 validation을 결함 수정 후 confirmation testing과 혼동하지 않는다.

테스트 계약에는 거절 동작도 넣는다

자체 mean의 명세는 Python 목록만 받고 원소는 type(x) is int인 정수여야 하며 bool은 제외한다. 비어 있지 않으면 Fraction으로 정확한 동일 가중치 평균을 반환한다. 목록이 아니거나 잘못된 원소는 TypeError, 정수 목록이 비면 ValueError다. 검사 순서는 목록 타입→원소 타입→빈 목록이다.

빈 입력에서 0을 반환할지 예외를 낼지는 평균 정의만으로 구현자가 몰래 정할 문제가 아니다. 이 예제는 명시적으로 예외를 정했다. None, [True], []를 서로 다른 계약 사례로 나누고 예외 발생 자체가 아니라 예상 예외 종류와 조건을 비교한다.

from fractions import Fraction

def mean(values):
    if type(values) is not list:
        raise TypeError('list required')
    if any(type(x) is not int for x in values):
        raise TypeError('integer required')
    if not values:
        raise ValueError('empty list')
    return Fraction(sum(values), len(values))

요구가 잘못되면 테스트도 잘못된 목표를 확인한다

가상 성적 [10,20]의 동일 가중 평균은 15다. 실제 요구가 가중치 1:3이라면 (10×1+20×3)/4=17.5다.15가 명세에 맞아도 그 업무 필요에는 맞지 않는다. 먼저 어느 정책이 필요한지 사용자와 문서 근거를 확인해야 한다. 이 가상 예에서 실제 학생 정책을 조사한 것은 아니다.

테스트를 잘 작성하면 선택한 요구의 충족 근거를 얻지만 요구 자체의 타당성을 자동 보장하지 않는다. 정상·빈·타입 경계로 input partition을 만들고 기대값을 명세에서 정한 뒤 사용자 업무·장치·사용 흐름은 별도로 확인한다. 사람 대상 확인을 수행하지 않았다면 미수행으로 남긴다.

중간 과정을 따라가는 예제

자체 mean의 [2,4], [], [True], None 결과와 가상 성적 [10,20]의 두 평균을 비교하라.

  1. [2,4]는 목록·정수·비어 있지 않음 조건을 만족하여 Fraction(6,2)=3.

  2. []는 타입 검사 후 빈 목록에서 ValueError. [True]는 bool이라 원소 검사에서 TypeError.

  3. None은 목록 검사에서 TypeError.

  4. [10,20] 동일 가중치는 15, 가중치 1:3은 70/4=17.5이며 요구 정책이 다르다.

코드 실행에서 3/ValueError/TypeError/TypeError를 확인했다. 성적 정책 예는 가상이며 실제 업무 적합성 검토가 아니다.

종이와 본문으로 직접 해보기

[3], [1,2], [1.0]의 명세 결과를 손으로 정하고 이 테스트만으로 실제 사용자 요구가 맞다고 말할 수 있는지 답하라.

힌트 보기

float1.0이 수치상 정수처럼 보여도 type 조건을 확인하라.

풀이 보기

[3]→3, [1,2]→3/2, [1.0]→TypeError다. 이 결과는 선택 명세를 대조하며 실제 요구 정책·사용맥락 타당성은 별도 근거가 필요하다.

오해와 반례

모든 명세 테스트를 통과하면 사용자 필요까지 충족한다.

동일 가중 평균 명세는 정확해도 가중 성적 요구에는 15 대신 17.5가 필요할 수 있다. 요구 충족과 요구 선택의 타당성을 분리한다.

소단원 1.3

위험과 테스트수준

자주 틀리는 사소한 표시와 드물지만 큰 손실을 만드는 계산 중 무엇을 먼저 확인할까?

준비 개념과 학습 목표

준비 개념

  • 위험은 불리한 사건이 생길 가능성과 영향을 함께 다루는 개념이다. 확률은 0부터 1 사이의 가능성 수치다. 기대손실은 같은 기준의 여러 경우를 확률로 가중한 평균 손실이다. 테스트 대상의 경계는 함수·연결·전체 제품처럼 검토할 범위를 정한다.

학습 목표

  • 위험 추정의 가정과 우선순위를 설명한다

  • 단위·통합·시스템·인수 검토의 질문을 구별한다

  • 테스트수준과 품질 유형을 혼동하지 않는다

우선순위에는 영향과 불확실성이 필요하다

가상 사건 A의 발생확률.01, 발생 시 손실 10000원, B의 확률.2와 손실 100원이라 하자. 미발생 손실 0, 같은 기간·사용량·금액 단위·고정 조건이라고 가정하면 기대손실은 A100원, B20원이다. 빈도만 보면 B가 크지만 이 기준으로는 A가 더 높다.

확률과 손실은 실제 근거가 필요하고 여기의 값은 가상이다. “낮음/높음”이나 1..5 순위 점수를 곱한 수는 실제 확률×금전 기대손실이 아니다. 심각한 피해·제약·추정 불확실성 때문에 기대금액만으로 우선순위를 정하지 않는 상황도 있다. 위험 분석은 테스트 깊이와 범위를 정하는 판단 자료다.

수준은 대상 경계와 질문을 정한다

단위/컴포넌트 테스트는 mean 같은 요소를 분리하여 확인한다. 컴포넌트 통합은 문자열 파서와 mean의 연결·전달 타입을 확인한다. 시스템 테스트는 전체 프로그램의 요구를, 시스템 통합은 외부 시스템과 연결을 확인한다. 인수 검토는 의도한 사용과 수용 조건을 다룬다.

ISTQB4.0.1의 이 다섯 수준을 참고하되 모든 프로젝트가 같은 순서의 다섯 별도 단계로 실행되어야 한다는 법칙은 아니다. mean([2,4])=3이라는 통과만으로 화면에서 입력한 “2,4”가 정확히 파싱되거나 외부 저장이 성공한다고 보장하지 않는다. 대역으로 대신한 외부 서비스는 실제 서비스 관찰과 구분한다.

무엇을 시험하는가와 어디를 시험하는가는 다르다

기능·성능·보안 같은 관심은 테스트 유형 또는 품질 질문이다. 단위·통합·시스템은 대상의 경계다. 성능을 시스템에서만, 기능을 단위에서만 본다는 분류는 틀리다. 예를 들어 파서 단위의 큰 입력 시간과 전체 화면의 응답시간은 서로 다른 경계의 성능 질문이다.

검토 계획에는 요구·대상 경계·입력·oracle·환경·기대결과·남은 범위를 적는다. 평균 프로그램의 단위 정상/빈 입력/타입 검토 뒤 파서 연결과 전체 사용 흐름으로 범위를 넓히되 실제 실행하지 않은 수준은 계획으로 남긴다. 통과 수를 모든 위험 제거의 증거로 바꾸지 않는다.

중간 과정을 따라가는 예제

가상 A(.01,10000원), B(.2,100원)의 기대손실을 구하고 평균 프로그램의 단위/통합 검토 질문을 하나씩 적어라.

  1. 같은 기간과 노출, 미발생 손실 0이라는 가정을 명시한다.

  2. A=.01×10000=100원, B=.2×100=20원.

  3. 단위 질문:mean([2,4])는 정확히 3을 반환하는가?

  4. 통합 질문:입력 “2,4”를 파서가 정수 목록[2,4]로 바꾸어 mean에 전달하는가? 실제 파서 실행은 하지 않았다.

가정한 기대손실 기준에서는 A를 먼저 다룰 이유가 있다. 단위 결과는 직접 확인했지만 파서/전체/외부/인수 검토는 계획이다.

종이와 본문으로 직접 해보기

C의 가상 확률.05, 조건부 손실 2000원이라면 기대손실을 계산하고 “전체 UI의 응답 1초 이하”의 수준과 관심을 분리하라.

힌트 보기

금액 기대값과 수준/유형을 별도 축으로 쓴다.

풀이 보기

C=.05×2000=100원. UI를 포함한 전체 제품 응답은 시스템 경계의 성능 질문이다.1초 기준은 가상 요구이며 실제 응답시간을 측정한 것은 아니다.

오해와 반례

단위 테스트가 모두 통과하면 통합·인수 테스트는 필요 없다.

파서가 쉼표를 잘못 처리하거나 실제 필요가 가중 평균이면 mean 단위 테스트는 통과해도 시스템 목표를 못 이룬다. 서로 다른 대상·연결·사용 목표의 근거를 확인해야 한다.
