소단원 10.1

lint·type·dataflow

프로그램을 실행하지 않고 무엇을 알 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 변수와 대입
  • 조건문
  • 함수의 입력·출력

학습 목표

  • lint·타입 검사·자료흐름 분석의 질문을 구분한다
  • 분기 합류에서 가능한 값 집합을 계산한다
  • 정적 검사와 실제 실행의 증거 범위를 구분한다

서로 다른 질문을 하는 검사

lint는 선택한 규칙에 따라 소스의 의심스러운 사용이나 스타일을 찾는다. 규칙과 설정이 다르면 결과도 달라진다. 타입 검사는 값에 허용된 연산과 함수의 입력·출력 타입 관계를 검사한다. 두 검사가 같은 도구 안에 있어도 묻는 질문을 구분하면 경고를 이해하기 쉽다.

정수 가격과 정수 수량을 받아 정수를 돌려주는 함수가 가격+수량을 반환한다고 하자. 타입은 맞아도 곱셈이 필요한 주문 총액 요구를 어긴다. 타입 검사 통과만으로 업무 계산이 맞다고 판단할 수 없다. mypy의 기본 설정에서는 타입 주석 없는 함수 본문을 모두 같은 수준으로 검사하지도 않는다.

자료가 지나간 길을 따라가기

자료흐름 분석은 제어 흐름 그래프의 각 지점에 사실을 붙인다. 여기서는 실행 가능한 정수 값의 집합만 기록하는 작은 분석을 사용한다. 분기 한쪽에서 x=2, 다른 쪽에서 x=5라면 합류 직후 가능한 값은 {2,5}이다. 이어 y=x+1이면 {3,6}을 얻는다.

여러 경로를 합칠 때 집합의 합집합을 쓰면 두 경로의 가능성을 보존한다. 반복문은 같은 지점에 새 사실이 돌아올 수 있어, 사실이 더 바뀌지 않는 고정점까지 계산하기도 한다. 실제 도구는 비용을 줄이려고 값의 범위를 근사하며, 그 과정에서 경로 사이의 관계를 잃을 수 있다.

경고와 실행을 연결하기

d의 가능한 값이 {0,2}이고 10/d가 이어지면 0으로 나눌 가능성을 조사해야 한다. 이 집합만으로 실제 입력이 반드시 0이라고 결론내릴 수는 없다. 앞 조건이 d=0인 경로를 정말 허용하는지 확인해야 한다.

정적 분석의 가정, 활성 규칙, 언어·도구 버전을 함께 남긴다. 테스트는 선택한 입력에서 실제 동작을 관찰하며 정적 분석과 보완 관계다. 본 단원의 집합 추적은 종이 계산이고, Ruff·mypy·Clang을 실행해 얻은 진단이 아니다.

중간 과정을 따라가는 예제

두 분기에서 x가 각각 2 또는 5가 된다. 합류 뒤 y=x+1, z=y*2를 계산한다. 정수 오버플로는 없는 모형에서 가능한 값 집합을 구하라.

  1. 합류에서 x={2,5}이다.
  2. 각 값에 1을 더해 y={3,6}이다.
  3. 각 값에 2를 곱해 z={6,12}이다.

z는 6 또는 12이다. 경로를 합쳐도 이 예에서는 정확한 값 집합을 유지한다.

종이와 본문으로 직접 해보기

다른 분기에서 x=1 또는 x=4로 바꾸고 y=x+1, z=y*2의 집합을 적어라. 타입이 모두 정수라는 사실만 알면 z의 두 값을 특정할 수 있는지도 설명하라.

힌트 보기

가능한 값을 하나씩 변환한 뒤 중복을 합친다. 타입과 값 집합은 다르다.

풀이 보기

x={1,4}, y={2,5}, z={4,10}이다. 정수 타입만으로는 4와 10이라는 두 값까지 특정할 수 없다.

오해와 반례

타입 검사를 통과하면 요구사항도 맞다.

정수 두 값을 더하는 잘못된 총액 함수도 정수 타입 관계는 만족할 수 있다. 요구의 연산, 경계와 상태를 리뷰하고 적절한 실행 테스트를 별도로 수행한다.

한 단계 더

두 분기의 (x,y)가 각각 (0,1), (1,0)이라고 하자. x+y는 실제로 항상 1이다. 각 변수 집합만 따로 합치면 x={0,1}, y={0,1}이 되어 합 {0,1,2}를 근사한다. 0과 2는 실제 쌍에 없으며, 관계를 버리면 경고의 정확성이 낮아질 수 있음을 설명해 보자.

소단원 10.2

경고의 정밀도

경고가 많으면 결함을 잘 찾는 도구일까?

준비 개념과 학습 목표

준비 개념

  • 분수와 백분율
  • 실제 결함과 경고의 구분

학습 목표

  • TP·FP·FN·TN을 구분한다
  • 정밀도와 재현율의 분모를 설명한다
  • 경고 억제의 근거와 측정 조건을 남긴다

정답 표와 경고 표를 나란히 놓기

학습 모형에서는 서로 다른 100개 검사 사례마다 실제 결함 유무가 별도로 확정되어 있다고 가정한다. 도구가 경고하고 실제 결함도 있으면 참양성 TP, 결함이 없는데 경고하면 거짓양성 FP이다. 실제 결함을 놓치면 거짓음성 FN, 결함 없이 경고도 없으면 참음성 TN이다.

단위가 사례인지 경고 메시지인지 먼저 정해야 한다. 한 결함에 중복 경고 세 개를 세면 결과가 달라진다. 여기서는 사례 하나당 경고 있음·없음 하나만 기록한다. 실무의 정답 표는 불완전할 수 있으므로 조사 방법과 미확정 사례도 별도로 기록한다.

정밀도와 재현율의 두 질문

정밀도 TP/(TP+FP)는 나온 경고 중 실제 결함의 비율이다. 재현율 TP/(TP+FN)은 실제 결함 중 찾은 비율이다. 전자는 경고를 읽는 비용, 후자는 놓친 결함을 생각하게 한다. 서로 다른 분모이므로 높은 정밀도 하나로 모든 결함 발견을 주장할 수 없다.

TP=8, FP=4, FN=2, TN=86이면 정밀도는 8/12=2/3, 재현율은 8/10=80%이다. 경고 중 오경고 비율은 4/12이고, 결함 없는 사례 중 경고 비율인 거짓양성률은 4/(4+86)=4/90이다. 두 비율을 같은 이름으로 부르지 않는다.

억제는 이유를 남기는 결정

경고를 읽고 입력 조건·경로·함수 계약을 확인한다. 실제 문제라면 수정과 회귀 검사를 연결한다. 잘못된 경고라면 도구가 모르는 조건을 적절한 주석·assert·구성으로 전달할 방법을 조사하고, 제한된 억제에는 이유와 재확인 조건을 남긴다. 분석기가 알아듣게 만들려고 실제 코드의 위험을 숨기면 안 된다.

설정을 더 좁혀 TP=6, FP=1이 되었고 실제 결함 10개는 그대로라면 FN=4이다. 정밀도 6/7은 높아져도 재현율은 60%로 낮아진다. 숫자는 자체 예시이며 특정 제품의 측정 결과가 아니다. 경고가 0개이면 이 정의의 정밀도 분모도 0이므로 자동으로 100%라고 적지 않는다.

중간 과정을 따라가는 예제

실제 결함 10개가 있는 100사례에서 12사례에 경고했고 그중 8개가 실제 결함이다. 혼동표와 두 비율을 구하라.

  1. TP=8, FP=12−8=4이다.
  2. FN=10−8=2, 결함 없는 90개 중 TN=90−4=86이다.
  3. 정밀도=8/12≈66.7%, 재현율=8/10=80%이다.

표의 합은 8+4+2+86=100이다. 정밀도와 재현율을 함께 보고한다.

종이와 본문으로 직접 해보기

같은 100사례·실제 결함 10개에 대해 새 설정이 7개 경고 중 실제 결함 6개를 찾았다. 네 칸과 비율, 기존 설정과의 차이를 계산하라.

힌트 보기

실제 결함 수와 전체 사례 수는 고정된다.

풀이 보기

TP=6, FP=1, FN=4, TN=89이다. 정밀도 6/7≈85.7%, 재현율 6/10=60%이다. 경고는 줄었지만 놓친 결함은 2개에서 4개로 늘었다.

오해와 반례

경고를 전부 끄면 품질 지표가 좋아진다.

경고 수는 0이어도 결함이 사라지지 않는다. 실제 결함 10개를 모두 놓치면 재현율은 0%이며 정밀도는 0분모다. 제품 품질과 대시보드의 조용함을 구분한다.

한 단계 더

정밀도가 같아도 심각한 결함과 사소한 경고의 구성은 다를 수 있다. 가상의 두 도구가 각각 TP=8, FP=4라고 할 때, 보안 결함을 누가 놓쳤는지 모르면 배포 판단을 내릴 수 없는 이유를 적어 보자. 수치 비교에는 사례 구성·도구 버전·규칙·정답 표도 필요하다.

소단원 10.3

코드리뷰와 결함분류

리뷰 댓글 다섯 개는 결함 다섯 개일까?

준비 개념과 학습 목표

준비 개념

  • 입력·조건·출력
  • 변경과 요구사항

학습 목표

  • 관찰·조건·영향·개선 요청을 연결한다
  • 결함 유형과 심각도를 구분한다
  • 중복 지적과 실제 검증 상태를 기록한다

변경이 해결해야 하는 문제부터 읽기

리뷰는 코드의 생김새만 보는 일이 아니다. 변경 목적과 사용자 요구를 읽고, 수정된 줄이 기존 문맥과 어떻게 연결되는지 확인한다. 기능과 경계 입력, 동시성, 복잡도, 적절한 테스트, 문서의 일치를 살핀다. 이해하기 어려운 부분은 추측으로 승인하지 않고 조건과 의도를 확인한다.

좋은 지적은 위치·조건·현재 동작·기대 동작을 연결한다. 예를 들어 “무료배송 조건이 상품 소계 1000 이상인데 소계가 아닌 배송비 포함 총액을 비교한다. 소계 700과 배송비 300일 때 무료로 오판한다”처럼 반례를 제시한다. 이 문장은 종이 추적이며 실제 실행 관찰이 아니다.

유형과 심각도를 다른 축으로 기록하기

여기서는 학습용으로 정확성, 동시성, 자원 수명, 보안, 유지보수성이라는 유형을 쓴다. 한 문제가 여러 유형에 걸칠 수 있다. 유형은 어떤 성질의 문제인지, 심각도는 어떤 조건에서 누구에게 얼마나 큰 영향을 주는지 묻는다. 보안이라는 이름만으로 항상 최고 심각도라고 자동 판정하지 않는다.

확정 결함, 조사 필요, 선택적 스타일 제안도 구분한다. 개인 취향에 따른 이름 변경은 실제 오류와 같은 배포 차단 근거가 아니다. 반대로 테스트 코드도 잘못된 답을 정답으로 검사할 수 있으므로 주장하려는 조건에서 깨지는지 확인해야 한다.

중복을 합치고 해결 증거를 연결하기

두 사람이 같은 배송 조건 오류를 지적했다면 댓글은 두 개지만 원인 결함은 하나로 관리할 수 있다. 고유 ID, 재현 조건, 요구 근거, 수정 담당, 상태, 검증 계획을 연결한다. 관련 댓글을 ID로 묶으면 중복 수가 발견 능력으로 잘못 계산되는 일을 줄인다.

수정 후 리뷰 의견이 해결되었는지 다시 확인한다. 코드 읽기, 종이 추적, 실제 테스트, 사용자 관찰은 각각 다른 증거다. UI의 실제 표시나 경쟁 상태 해결을 코드 읽기만으로 실험 완료라고 적지 않는다. 승인 범위와 남은 확인을 기록해야 다음 사람이 판단을 이어 갈 수 있다.

중간 과정을 따라가는 예제

댓글 R1·R2는 같은 무료배송 비교 오류 D1, R3은 파일 닫기 누락 D2, R4는 선택적 이름 제안, R5는 근거가 아직 없는 성능 의문이다. 확정 원인 결함 수와 조사 대상을 분리하라.

  1. R1·R2를 동일 조건·위치의 D1로 묶는다.
  2. R3은 자원 수명 결함 D2로 기록한다.
  3. R4는 선택 제안, R5는 조사 필요로 별도 둔다.

댓글은 5개, 확정 고유 결함은 2개다. R5는 측정 전 성능 결함으로 확정하지 않는다.

종이와 본문으로 직접 해보기

R6가 D2의 같은 닫기 누락을 다시 지적하고, R7이 요구 근거와 반례가 확인된 새로운 D3을 제시했다. 댓글·고유 결함 수와 R5 상태를 다시 적어라.

힌트 보기

같은 원인 ID를 중복 집계하지 않는다. 새 증거가 없는 항목의 상태는 그대로다.

풀이 보기

댓글은 7개, 확정 고유 결함은 D1·D2·D3의 3개다. R5는 여전히 조사 필요다. D3 유형·영향은 제공된 근거로 별도 분류한다.

오해와 반례

리뷰에서 승인했으므로 기기 실험과 모든 테스트도 통과했다.

승인은 지정한 검토 범위의 판단이다. 실제 실행을 하지 않았다면 실행 미수행으로 남기며, UI·성능·장비 같은 관찰이 필요한 항목은 별도 확인한다.
