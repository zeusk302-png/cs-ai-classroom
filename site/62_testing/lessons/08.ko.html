소단원 8.1

E2E 시나리오

버튼에 성공 메시지가 뜨는데 새로 고치면 저장한 과목이 사라진다면 테스트가 충분했을까?

준비 개념과 학습 목표

준비 개념

  • E2E 는 사용자 입력부터 연결된 시스템의 결과까지 끝에서 끝으로 보는 검사다.

  • 기대 결과를 판정하는 기준을 oracle 이라고 한다.

학습 목표

  • 경계와 실제/모형 의존성을 명시한다.

  • 초기 상태·행동·지속 결과의 검사표를 만든다.

연결 경로를 포함하되 범위를 이름 붙인다

단위 테스트가 저장 함수 하나의 계약을 검사한다면 E2E 는 로그인·선택·요청·저장·다시 조회 같은 연결을 검사할 수 있다. 실제 어느 서비스까지 포함했는지 적어야 결과의 범위를 해석할 수 있다.

외부 인증이나 결제 등을 모형 응답으로 바꿨다면 그 모형 계약 아래의 경로를 검사한 것이다. 외부 실제 서비스를 통과했다고 바꾸어 말하지 않는다. 모든 가능한 시스템 행동을 한 시나리오로 확인할 수도 없다.

행동과 관찰 가능한 결과를 연결한다

내부 함수명이 불렸다는 사실만으로 사용자가 목표를 이뤘다고 판단하지 않는다. 저장 완료 표시와 재조회에서의 존재처럼 요구사항의 결과를 검사한다. 검사 대상과 예상값을 먼저 정하면 잘못된 UI 성공을 놓치기 어렵다.

동적 화면에는 잠깐 기다린 뒤 즉시 판정하는 것보다 조건이 충족되는지 정해진 한도 안에서 기다리는 검사가 필요할 수 있다. 그러나 자동 대기가 부정확한 요구사항이나 잘못된 결과를 고쳐 주지는 않는다. 무엇을 기다리는지 적는다.

각 시험이 자기 자료로 시작한다

저장 목록에 예전 항목이 남아 있으면 이번 저장이 실패해도 조회만 보고 통과할 수 있다. 초기 자료를 고정하고 시험별 사용자·식별자를 분리하여 앞 시험이 만든 상태에 우연히 의존하지 않게 한다.

회귀 테스트는 변경 뒤 기존 계약이 깨졌는지 확인하는 목적이다. 경로가 길수록 실패 지점이 여러 곳일 수 있으므로 요청·응답·화면·자료의 관찰 근거를 모은다. 아래 표는 가상 결과이며 실제 자동 시험이나 서비스 요청은 보내지 않는다.

중간 과정을 따라가는 예제

자체 요구: 초기 빈 저장 목록에서 사용자가 과목 7 을 저장하면 완료 표시가 나타나고, 새로 고침 뒤 목록에 7 이 있어야 한다. 가상 실행 A 는 표시있음/재조회[7], B 는 표시있음/재조회[], C 는 표시없음/재조회[7]이다. 두 조건을 모두 요구한다.

  1. A 는 표시와 지속 결과를 모두 충족한다.

  2. B 는 완료 표시만 있으며 지속 저장 조건이 실패한다. UI 문구 하나만 검사하면 이 결함을 놓친다.

  3. C 는 저장됐지만 요구한 완료 표시가 없어 전체 계약을 충족하지 않는다. 조건 둘의 논리곱으로 판정한다.

A 만 전체 통과, B/C 는 각각 다른 조건 실패다. 가상 표의 1/3 을 실제 사이트 테스트 통과율로 발표하지 않는다.

소단원 8.2

visual·snapshot 한계

화면 사진이 예전과 같으면 버튼이 올바르게 저장한다고 결론 내릴 수 있을까?

준비 개념과 학습 목표

준비 개념

  • baseline 은 비교 기준으로 승인한 결과다.

  • visual 비교는 이미지 차이, snapshot 은 고정한 출력과의 차이를 찾는다.

학습 목표

  • 출력 차이와 동작 정확성을 구별한다.

  • 허용 오차·숨긴 영역·기준 갱신의 한계를 설명한다.

같음을 보는 질문의 범위를 적는다

visual 비교는 텍스트 잘림·위치 이동처럼 모습의 회귀를 찾는 데 도움을 준다. 하지만 화면이 같아도 클릭 뒤 요청이 나가지 않으면 저장 기능은 실패할 수 있다. 출력 검사와 동작 결과 검사를 함께 설계한다.

문자열 snapshot 은 정해진 시점의 내용·구조와 기준을 비교할 수 있다. 같은 문자열이 나왔다고 모든 중간 상태·권한·외부 효과가 같다는 뜻은 아니다. baseline 자체가 잘못된 결과일 가능성도 사람이 검토해야 한다.

비교 환경과 동적 자료를 통제한다

브라우저·운영체제·글꼴·표시 환경이 달라지면 제품 변경 없이 이미지 차이가 생길 수 있다. 같은 환경에서 기준과 실제를 준비하고 시간·랜덤 광고 같은 자료를 고정하거나 목적에 따라 숨긴다.

숨긴 영역은 비교의 증거에서 빠진다. 허용 픽셀 수를 크게 늘리면 사소한 차이뿐 아니라 의미 있는 결함도 통과할 수 있다. 도구가 쓰는 픽셀 차이 알고리즘과 아래 단순 색이 같음/다름 모형을 구별한다.

갱신은 새 결과의 승인이다

실패했으니 기준을 전부 덮어쓰면 무엇이 바뀌었는지 확인하지 못한다. 의도한 변경인지 차이를 읽고 요구사항에 맞을 때 새 기준을 승인한다. 두 번 같은 사진을 얻어 안정화했다고 그 사진이 올바르다고 증명되는 것은 아니다.

이 단원은 10 칸의 색을 직접 비교하여 다른 칸 수 d 를 세고 d≤허용치이면 비교 통과라는 자체 규칙을 쓴다. 실제 Playwright 의 maxDiffPixels 는 pixelmatch 가 판정한 차이 수에 적용되며 색 임계값·안티앨리어싱 규약까지 이 활동과 같다고 주장하지 않는다.

중간 과정을 따라가는 예제

자체 10 칸 기준은 모두 0 이다. 실제 A 는 2/8 번칸만 1, 실제 B 는 2/3/8 번칸이 1 이며 나머지 0 이다. d≤2 이면 비교 통과다. 클릭 동작은 이 표에 없다.

  1. A 의 서로 다른 칸은{2,8}로 d=2 다. 경계를 포함하는≤2 라 비교 통과다.

  2. B 는{2,3,8}로 d=3 이며 비교 실패다.

  3. A 의 통과는 10 칸 출력 규칙을 만족한다는 뜻이며 저장 동작 성공을 검사한 것이 아니다.

A 비교 통과/B 실패. 허용치 경계 2 와 기능 검증 범위를 구별한다.

종이와 본문으로 직접 해보기

B 의 3 번칸을 숨김 처리해 비교 대상에서 빼면 d 가 얼마인가? 허용치 2 에서 결과와 잃는 증거를 설명하라.

힌트 보기

숨긴 칸은 일치로 검사한 것이 아니라 검사하지 않는다.

풀이 보기

남은 차이는 2/8 번의 2 칸으로 비교 통과다. 그러나 3 번칸의 차이를 검출하는 증거를 잃는다. 그 칸이 중요한 경고이면 다른 검사가 필요하다.

오해와 반례

새 snapshot 을 만들면 결함도 해결된다.

B 를 새 기준으로 승인하면 다음 B 는 차이 0 이지만 원래 의도한 값 0 이라는 요구는 여전히 위반할 수 있다. 기준 갱신과 구현 수정은 다른 일이다.

자동 갱신 전에 의도한 문구 변경·잘림·환경 차이를 구분하는 검토표를 만든다. 핵심 경고 영역을 숨기는 선택이 허용되는지 기능/접근성의 별도 검사와 함께 판단한다.

소단원 8.3

flaky test와 유지비용

같은 코드인데 어떤 실행은 실패하고 재시도는 성공했다면 실패를 지워도 될까?

준비 개념과 학습 목표

준비 개념

  • flaky 는 같은 코드·시험 계약에서 성공과 실패가 섞여 나타나는 현상이다.

  • 재시도는 관찰 기회를 늘리며 원인을 자동 수정하지 않는다.

학습 목표

  • 지연·공유 상태·제품 경쟁을 구별한다.

  • 최초 실패와 최종 판정·추가 비용을 함께 기록한다.

실패를 발생시킨 조건을 찾는다

실패 원인은 고정 대기시간보다 느린 응답, 시험 사이 공유 자료, 환경 장애, 실제 제품의 경쟁 상태일 수 있다. 코드가 같다는 이유만으로 제품에 결함이 없다고 단정하지 않는다. 시간·자료·실행 순서·응답을 함께 기록한다.

예를 들어 100ms 뒤 확인하는 시험에서 완료 시간이 80ms 이면 통과,150ms 이면 실패한다. 완료 조건을 한도 안에서 기다리는 규약으로 바꾸면 타이밍 결함을 줄일 수 있지만 500ms 안에 완료해야 한다는 제품 요구가 깨지는 경우는 계속 드러내야 한다.

처음 결과와 재시도 결과를 나눈다

Playwright 는 첫 시도 성공을 passed, 처음 실패 후 재시도 성공을 flaky, 허용한 재시도까지 실패를 failed 로 구분한다. 재시도 횟수는 첫 시도에 더해지는 횟수이며 기본값 0 이면 재시도를 하지 않는다.

실패 후 새 worker 를 시작해도 외부 데이터베이스의 공유 상태가 자동 초기화된다고 가정하면 안 된다. 시험별 초기화와 고유 자료가 필요하다. 재시도가 성공할 때까지 반복하면 드문 실제 결함의 신호를 감출 수 있다.

유지 비용도 측정 목적이다

같은 실패를 여러 번 조사하면 수정 작업보다 신호 분류에 시간이 들 수 있다. 실행 시간·최초 실패 수·재시도 수·원인별 조사 시간을 분리해 기록하면 느린 검사와 불안정한 검사를 구별할 수 있다.

격리해 배포를 막지 않게 하는 정책은 해당 검사의 보호 범위를 줄이는 선택이다. 소유자·원인·복구 기한·대체 검사 없이 영구히 지우는 것이 해결은 아니다. 아래 비용은 가상 상수이며 실제 CI 의 측정값이나 현재 Google 통계가 아니다.

중간 과정을 따라가는 예제

자체 5 개 시험 각각 한 시도 비용 10 초다. 최초 결과는 성공,실패,성공,실패,성공이며 실패한 두 시험을 한 번씩 재시도한다. 둘째시험 재시도 성공, 넷째시험 재시도 실패다. 다른 준비 비용은 0 이다.

  1. 첫 시도 5 회 비용 50 초, 실패 2 개에 재시도 2 회 비용 20 초다.

  2. 총 7 회·70 초다. 최초 실패 비율은 2/5=40%다.

  3. 분류는 passed3/flaky1/failed1 이다. 재시도 이후 실패만 보면 1/5=20%지만 최초의 불안정 신호 40%와 같은 수치가 아니다.

7 회 70 초, passed3/flaky1/failed1 이다. 실제 수행 로그가 아닌 자체 가상 기록이다.

오해와 반례

재시도 성공은 제품이 정확하다는 증명이다.

실제 경쟁이 간헐적으로 발생해도 재시도 때 스케줄이 달라지면 성공할 수 있다. 시간·자료를 통제하고 원인을 조사해야 하며 실패 기록을 유지한다.
