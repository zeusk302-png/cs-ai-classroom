소단원 9.1

부하·stress·soak

잠깐 빠른 서버가 하루 내내 버틸지도 알 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 요청률과 시간

  • 가상 사용자

학습 목표

  • 검사 목적에 맞는 부하와 기간을 선택한다.

  • 가상 부하 표와 실제 측정을 구별한다.

서버가 느려졌을 때 시험이 보내는 요청도 줄어든다면 무엇을 놓칠까?

자체 닫힌 부하 모형은 사용자 열 명이 각각 응답을 받은 즉시 다음 요청을 보낸다. 한 명에게 동시에 요청 하나만 진행되며 생각 시간은 없고 응답 시간은 일정하다. 응답이 0.1 초라면 안정 상태의 요청률은 10/0.1=100 회/초지만 응답이 1 초가 되면 10 회/초다. 느려진 서버에 자동으로 더 적은 요청을 보내는 셈이다.

열린 부하 모형은 응답 완료와 별도로 시작 일정을 잡는다. 자체 장부에서 5 초 동안 초당 100개의 시작 슬롯을 계획하고 실제로 350 회만 시작해 300 회가 완료됐다고 하자. 시작하지 못한 150 회와 진행 중인 50 회는 다른 상태다. 미시작을 서버의 오류 응답으로 기록하면 시험기 병목과 서버 결과를 혼동한다.

여기서는 반복 하나가 요청 하나이고 초기 진행 요청은 없으며 취소·재시도도 없다고 정했다. 실제 도구의 반복에는 여러 요청이나 준비 시간이 포함될 수 있다. 부하 종류의 이름보다 시작 일정·실제 시작·완료·자원·정리 구간을 함께 남겨야 비교할 수 있다.

먼저 확인할 개념
  • 부하 종류와 요청량

    기본 요청률 장부에 응답 시간과 시작 일정의 의존성을 추가한다.

  • 최초와 최종 시도 장부

    반복·요청·재시도 횟수의 범위를 구별한다.

정상 부하와 높은 부하는 질문이 다르다

load 검사는 예상 정상 workload에서 지연·오류·처리량을 본다. stress는 정상보다 큰 부하에서 제한과 열화·복구를 확인하고 soak는 오랜 지속 부하에서 누적 누수나 시간에 따른 문제를 찾는다.

짧은 spike와 단계 증가 breakpoint도 다른 질문이다. 이름을 붙이기 전에 요청 종류·비율·데이터·생성 모델을 정하고 작은 smoke로 시나리오 자체를 확인한다.

사용자 수를 요청률로 바꾸어 믿지 않는다

가상 사용자 수가 같아도 생각 시간과 응답 지연에 따라 요청 수가 달라질 수 있다. 목표 arrival rate와 완료 throughput, 동시성은 별도 지표다.

부하 생성기의 CPU·연결·대역폭이 병목이면 목표 부하가 실제 시스템에 도착하지 않는다. 정상 workload와 stress 단계가 재현되었는지 생성 측 기록도 확인해야 한다.

시간과 중지 조건을 기록한다

검사에는 시작·증가·지속·회복 단계와 지연/오류 등 목표·중지 기준을 둔다. 높은 부하만 넣고 끝내면 부하를 내린 뒤 회복하는지도 알 수 없다.

소단원 9.2

지연분포와 throughput

평균이 100 ms 아래면 느리게 기다린 요청은 없을까?

준비 개념과 학습 목표

준비 개념

  • 평균과 정렬

  • 단위

학습 목표

  • 분위수 규약과 꼬리 지연을 구분한다.

  • 입력률·전체 완료률·성공 완료률을 따로 계산한다.

두 구간의 p95를 평균내면 합친 요청의 p95가 될까?

자체 p95 규칙은 오름차순 표본의 ceil(0.95×n)번째 값을 고른다. 순위는 1부터 세며 모든 도구가 같은 보간 규칙을 쓰는 것은 아니다. A의 표본 20개는 10 ms인 값 열아홉 개와 1000 ms인 값 하나다. 순위 19이므로 A의 p95는 10 ms다. B의 표본은 1000 ms 하나이므로 B의 p95는 1000 ms다.

두 구간 p95의 단순 평균은 505 ms지만 합친 표본 21개의 p95 순위는 ceil(19.95)=20이다. 합친 표에는 10 ms 열아홉 개 뒤로 1000 ms 두 개가 있으므로 합친 p95는 1000 ms다. 표본 수로 가중한 p95 평균 (20×10+1000)/21≈57.14 ms도 합친 p95가 아니다.

백분위수는 해당 분포의 순서를 나타내므로 일부 요약값만 평균해 합친 분포의 위치를 복원할 수 없다. 합치려면 원 표본이나 적절한 분포 자료와 정의가 필요하다. 응답 시간의 시작·종료와 실패 포함 범위도 기록한다. k6의 http_req_duration은 보내기·대기·받기 합이며 초기 DNS·연결 시간을 포함하지 않는다.

먼저 확인할 개념
  • 순위 기반 지연 분포

    기본 p95 계산에 구간 병합의 반례를 추가한다.

  • 분모와 비교 영역

    각 요약값이 어떤 표본 집합의 값인지 밝힌다.

측정 시작과 끝을 먼저 정한다

지연은 무엇을 시작과 끝으로 삼았는지에 따라 달라진다. 사용자 클릭부터 화면 표시까지와 서버 내부 처리 시간은 같은 지표가 아니다. k6 http_req_duration은 송신·대기·수신 합이며 초기 DNS/연결 시간을 제외한다.

실패·timeout도 결과 해석에 포함하고 endpoint·성공 여부·시간창을 분리한다. 성공한 빠른 요청만 골라 전체 체감 속도로 보고하면 실패를 숨길 수 있다.

평균과 꼬리는 다른 정보를 준다

정렬된 표본에서 p95는 대략 95%가 그 값 이하라는 요약이지만 계산 방법이 여럿이다. 아래는 nearest-rank, 순위 ceil(p×n), 1 부터 세는 규약을 명시한다. 작은 표본은 큰 집단의 안정된 꼬리를 확정하지 못한다.

평균은 총합/n이다. 한 개의 큰 값이 있어도 대다수 작은 값 때문에 평균이 낮을 수 있고, 구간별 p95의 평균이 전체 표본 p95라는 보장도 없다.

처리량의 분자를 명시한다

throughput은 관찰 시간당 완료 수다. 성공 완료만 세는 goodput과 오류까지 포함한 완료률을 따로 쓰고 단위를 건/초 등으로 표기한다. arrival rate는 유입률이라 대기열 증가 시 완료률과 다르다.

빠른 오류 응답만 늘어 전체 완료률이 높아졌다고 사용자 목적 달성이 좋아진 것은 아니다. 지연·실패율·성공 완료률을 함께 해석한다.

장애주입과 복구

서버가 다시 켜졌다는 것과 주문이 보존되었다는 것은 같을까?

준비 개념과 학습 목표

준비 개념

  • 정상 상태와 지표

  • 재시도와 중복

학습 목표

  • 가설·범위·중지 기준을 정의한다.

  • 복구 시간과 데이터 정확성을 함께 확인한다.

장애 주입을 멈췄다는 사실만으로 서비스와 자료가 복구됐을까?

자체 모형의 주입 시작은 10 초, 주입 중단은 15 초다. 응답 기준을 10 초 길이의 창마다 검사한 결과 [10,20)는 정상, [20,30)는 비정상, [30,40)는 정상, [40,50)는 정상이다. 모든 구간의 시각 단위는 초다. 복구 계약은 연속된 정상 창 두 개를 요구한다. 첫 정상 창이 끝난 20 초를 복구 완료 시점으로 기록할 수는 없다.

마지막 두 정상 창을 모두 관찰한 50 초가 이 모형의 첫 복구 확인 시점이다. 주입 시작을 기준으로 하면 40 초, 주입 중단을 기준으로 하면 35 초이며 어떤 기준을 쓰는지 밝혀야 한다. 표는 지정한 관찰 장부이고 실제 가용성이나 장애 실험의 결과가 아니다.

기능 응답과 자료 복구도 나눈다. 승인된 요청 식별 A,B,C가 각각 한 번 남아야 하는 계약에서 저장 결과 A,B,B는 개수 세 개로 같아도 C 누락과 B 중복이다. 실험 중단 조건은 피해를 제한하는 안전 경계이며 정상 응답·자료 일관성·해제 결과를 자동으로 증명하지 않는다.

정상 상태와 가설을 먼저 정한다

장애주입은 정한 오류를 제한한 환경에 넣어 예상 동작과 복구를 관찰하는 검사다. 먼저 정상 상태를 지연·오류·성공 기능 등으로 정의하고 어떤 장애가 어떤 영향을 줄 것인지 가설을 적는다.

대상·기간·영향 범위와 되돌릴 경로를 정한다. 아래는 실제 서버를 끄는 활동이 아니라 사건표를 계산하는 종이 모형이며 공개 서비스나 다른 사용자 시스템에 장애를 가하지 않는다.

중지 기준은 실험과 별도 감시한다

AWS FIS는 CloudWatch alarm으로 임계에 도달하면 실험을 중지하는 stop condition을 둔다. 문서에서 중지된 실험은 재개할 수 없으므로 새 실험과 구분한다.

실험 중지는 서비스 복구 완료의 증거가 아니다. 이미 생긴 오류·누락·중복과 진행 중 작업이 남을 수 있어 실제 영향과 정리 결과를 별도 확인해야 한다.

복구 기준은 시간과 정확성이다

프로세스 생존만이 아니라 기능이 다시 목표 상태를 만족하는 첫 시점을 정의한다. 시간창·연속 유지 조건이 있으면 그 조건도 포함하고 장애 감지/제거/복구를 다른 사건으로 기록한다.

재시도는 요청 ID 기반 중복 처리 정책을 검증한다. 같은 거래가 두 번 반영되거나 승인된 기록이 사라지면 서버가 응답해도 정확성 복구라고 볼 수 없다.

중간 과정을 따라가는 예제

가상 사건표에서 주입 시작 t=10 초, 실험 중지 t=15 초, 서비스 시작 t=20 초, 기능 응답 목표를 만족하는 첫 시각 t=25 초다. 데이터 기준은 승인 ID 각각을 중복 없이 보존하는 것이다. 승인 ID 집합은 {A,B,C}, 복구 저장 목록은 A,B,B다.

  1. 시작부터 기능 목표 만족까지 25−10=15 초다. 실험 중지 뒤에는 25−15=10 초이며 서비스 시작 20 초만으로 끝내면 기능 기준을 놓친다.

  2. 복구 목록의 고유 ID는 {A,B}라 C가 누락되고 B가 중복됐다. 목록 길이 3 만으로 승인 3 개 보존이라 판정할 수 없다.

  3. 기능 목표 시각을 25 초라고 주었어도 이 데이터 표는 정확성 기준을 위반한다. 전체 복구 통과라고 선언할 수 없다.

기능 사건 간 시간은 15 초/10 초지만 C 누락·B 중복으로 전체 복구 검사는 실패다. 25 초는 가상 기능 시각으로만 읽는다.

연습 1 · 값과 상태 예측

50 초의 복구 확인은 주입 시작 10 초와 중단 15 초에서 각각 얼마의 시간이 지난 뒤인가?

힌트 2

풀이와 답 확인

  1. 시작 기준은 50−10=40 초다.

  2. 중단 기준은 50−15=35 초다.

시작 기준 40 초, 중단 기준 35 초이며 자체 모형의 계산이다.

다른 문제에 적용하기

좋아 보이는 수치를 조건에 맞게 다시 읽기

사용자 열 명이 응답 뒤 즉시 다음 요청을 보내는 모형에서 일정 응답 시간 0.1 초와 1 초의 안정 상태 요청률을 구하라. A는 10 ms 표본 열아홉 개와 1000 ms 표본 하나, B는 1000 ms 표본 하나다. 합친 표본의 ceil(0.95n) 순위 p95를 계산하라. 연속 정상 창 두 개를 요구하는 계약에서 [10,20)부터 [40,50)까지 정상·비정상·정상·정상인 장부의 복구 확인 시각을 구하라. 구간 시각의 단위는 초다. 승인 식별 A,B,C 대비 저장 식별 A,B,B가 어긴 조건도 적어라.

힌트 1

단위·표본 수·순위·관찰 창을 각각 구한다.

힌트 2

완료·요약 평균·중단 명령으로 계약의 다른 조건을 대체하지 않는다.

풀이와 답 확인

  1. 생각 시간이 0인 자체 닫힌 모형의 요청률은 각각 100 회/초와 10 회/초다.

  2. 합친 표본 21개의 순위는 20이므로 p95는 1000 ms다.

  3. 연속된 정상 창 두 개는 50 초에 처음 확인된다.

  4. 자료 계약은 C 누락과 B 중복으로 실패한다.

모든 수치는 지정한 자체 모형의 계산이다. 실제 서버 용량·k6 부하·AWS 장애 주입·자료 복구나 학생 검증은 수행하지 않았다.

해결한 뒤 점검할 것

  • 닫힌 부하의 응답 의존성을 설명한다.

  • 병합 p95를 표본 분포로 계산한다.

  • 복구 확인에 정한 연속 창을 적용한다.

  • 자료의 개수와 식별별 계약을 구별한다.
