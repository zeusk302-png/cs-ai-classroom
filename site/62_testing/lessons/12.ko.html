소단원 12.1

재현 가능한 파이프라인

내 컴퓨터에서는 통과했는데 자동 검사에서는 왜 다를까?

준비 개념과 학습 목표

준비 개념

  • 테스트는 특정 입력·조건에서 기대 결과를 비교한다.

  • 버전은 코드와 도구 상태를 식별한다.

학습 목표

  • 코드·도구·자료·환경과 실행 결과를 연결한다.

  • 재실행의 범위와 원래 결과를 구별한다.

현재 코드로 시작한 CI가 이전 산출물만 검사할 수도 있을까?

자체 장부의 목표 소스는 H2다. 실행 R의 체크아웃은 H2지만 빌드 경로가 오래된 결과 P1을 복원했고 실제 검사는 H1에서 만든 P1만 검사했다고 정하자. 실행 이름 R과 목표 H2만으로 H2 산출물 P2의 검사가 완료됐다고 쓸 수 없다.

의존성 캐시의 정확한 key 적중도 지정한 경로의 캐시 복원 사실이다. 캐시 적중만으로 코드 빌드·테스트 성공이 생기지 않는다. 부분 key나 restore-keys로 다른 키의 자료를 복원했을 수도 있어 요청 키·실제 복원 키·설치와 빌드 단계의 결과를 함께 남긴다.

자체 식별 H1/H2와 P1/P2는 실제 해시가 아니라 서로 다른 소스와 산출물의 이름이다. 공개하려는 P2와 실제 검사 P1이 다르면 적용 범위를 재확인한다. 같은 파일 내용을 확인하는 절차도 기능 정답이나 사용자 검증을 자동 보장하지 않는다.

먼저 확인할 개념
  • 파이프라인의 실행 범위

    코드 이름에서 실제 소비한 산출물까지 추적한다.

  • 현재 검토 버전과 근거

    이전 버전의 근거를 새 산출물 전체로 복사하지 않는다.

CI도 구체적인 실행 환경이다

CI는 변경 등을 계기로 별도 실행 환경에서 검사를 반복하는 흐름이다. 내 컴퓨터의 성공과 다른 서버의 성공은 같은 관측이 아니다. 도구 버전·의존성·운영체제·언어 설정·시간대·환경 변수와 자료 경로가 다를 수 있다.

재현 가능한 기록에는 코드 식별자, 의존성 버전, 입력 자료, 실행 명령, 수집한 테스트 목록과 환경을 포함한다. 고정된 무작위 seed는 도움이 될 수 있지만 병렬 순서·외부 서버·실시간 시계까지 모두 고정하지는 않는다. 재현 조건과 남은 변동 조건을 구별한다.

단계마다 입력과 실패를 남긴다

설치→빌드→테스트→보고처럼 작업을 나누고 어떤 단계가 어떤 입력과 산출물을 쓰는지 연결한다. 설치 실패 뒤 테스트가 실행되지 않았다면 테스트가 실패했다고 바꿔 말하지 않는다. run에는 여러 job과 step이 있을 수 있어 실패한 단계의 로그를 확인한다.

순서가 있는 작업과 독립 병렬 작업은 시간이 다르다. 아래 시간선은 실패 없이 정해진 시간에 끝나는 자체 모형이며 실제 네트워크나 runner 대기 시간을 측정한 것이 아니다. 자동 검사 성공은 검사 대상 밖 행동까지 보장하지 않는다.

한 번 더 실행한 결과의 범위를 표시한다

부분 재실행은 일부 job만 다시 수행할 수 있다. 새 로그에 이전 성공 job이 없다고 삭제된 테스트로 단정하지 않고 실행 시도 번호와 범위를 확인한다. 재실행으로 통과했어도 첫 실패를 보존하고 원인이 코드·환경·테스트 중 어디에 있는지 조사한다.

결과 보고를 같은 코드와 산출물에 연결한다. 다른 버전을 재검사한 뒤 원래 실패가 해결되었다고 자동 판정하지 않는다. 검사를 건너뛰거나 실패 종료코드를 무시한 파이프라인의 녹색 표시는 기대한 검증을 의미하지 않을 수 있다.

중간 과정을 따라가는 예제

가상 파이프라인은 설치2분 뒤 단위 검사3분과 통합 검사5분이 병렬, 둘 다 끝난 뒤 보고1분이다. 총시간과 통합 검사만 재실행한 로그의 범위를 구하자.

  1. 설치 종료2분, 단위 검사 종료5분, 통합 검사 종료7분이다.

  2. 보고는7분에 시작해8분에 끝난다. 총시간2+max(3,5)+1=8분이다.

  3. 통합 검사만 재실행하면 그 로그는 통합 재실행 범위다. 단위 검사를 새로 실행했다는 증거는 아니다.

가상 총8분이다. 재실행 결과와 이전 실행 결과를 시도 번호·job별로 연결한다.

소단원 12.2

우선순위·root cause

가끔 실패하는 검사를 반복해서 통과시키면 결함이 사라졌을까?

준비 개념과 학습 목표

준비 개념

  • 관찰 증상은 원인과 다를 수 있다.

  • 재현 입력과 기대값을 나누어 적는다.

학습 목표

  • 결함 영향과 수정 순서를 구별한다.

  • 간헐 실패의 가설을 검증 가능한 조건으로 좁힌다.

A 뒤에 B가 실패한다는 사실만으로 A가 원인이라고 확정할까?

자체 초기 관찰은 A 뒤의 B가 실패하고 B 단독은 통과한다는 두 줄이다. 두 실행의 캐시 조건도 각각 있음과 없음이었다면 A 실행 여부와 캐시 상태가 함께 바뀌었다. 이 관찰만으로 어느 변수가 결과를 바꿨는지 분리하지 못한다.

두 변수를 따로 지정한 가상 비교 표에서는 A 없음/캐시 없음 통과, A 있음/캐시 없음 통과, A 없음/캐시 있음 실패, A 있음/캐시 있음 실패다. 이 표는 캐시 가설과 일치하고 A 유무 자체의 효과는 구별되지 않는다. 표는 실제 실험 결과가 아니라 조건을 분리하는 교육 모형이다.

실제 원인을 조사할 때는 초기 상태·입력·코드·캐시·순서·환경을 기록하고 후보 변수를 하나씩 바꿀 계획을 세운다. 가상 표만으로 캐시의 어떤 필드가 왜 문제인지까지 확정하지 않는다. 재실행 통과나 격리도 원인 교정과 구별한다.

먼저 확인할 개념
  • 순서 의존의 원인 가설

    함께 바뀐 조건을 따로 비교하는 표를 추가한다.

  • 초기 상태와 정리

    캐시·전역 상태의 초기 조건을 통제한다.

심각도와 우선순위는 다른 질문이다

심각도는 문제가 났을 때 영향이고 우선순위는 언제 무엇을 먼저 처리할지의 결정이다. 데이터 손실 한 건은 드문 화면 색 오류보다 중요할 수 있다. 빈도만 보고 순서를 정하지 않고 영향을 받는 기능·회복 가능성·우회 방법·배포 시점을 함께 고려한다.

간단한 수업 점수를 만들 수 있지만 점수가 서비스 정책을 대신하지는 않는다. 아래 영향×빈도 등급은 자체 순서 연습이다. 등급 숫자의 차이가 정확한 피해 크기나 발생 확률이라고 가정하지 않는다. 점수 동률이나 중요 예외를 따로 기록한다.

원인을 한 가설씩 좁힌다

root cause는 관찰한 실패를 만들어 낸 근본 원인을 찾으려는 분석이다. “테스트가 빨갛다”는 결과만으로 제품 코드를 원인으로 확정할 수 없다. 입력·의존 환경·이전 검사 잔여 상태·순서·시간 단정을 각각 후보로 검토한다.

예를 들어 A가 전역 목록에 값을 남기고 B가 빈 목록을 가정한다면 A→B와 B 단독 결과가 다를 수 있다. 정리 단계를 추가하는 후보를 만들고 같은 순서와 다른 순서에서 확인할 계획을 세운다. 환경을 깨끗하게 한 한 번의 통과만으로 모든 순서의 문제를 없앴다고 보장하지 않는다.

불안정 신호를 숨기지 않는다

flaky test는 때때로 통과하고 실패하는 검사다. 원인이 테스트일 수도 있고 제품의 경쟁 상태일 수도 있다. 재실행은 작업 흐름의 부담을 줄일 수 있지만 원인 수정과 같지 않다. 첫 실패·재실행 횟수·환경·최종 결과를 함께 남긴다.

격리한 검사는 정상 검증 범위에서 빠질 수 있다. 담당자·해결 계획과 빠진 위험을 기록하지 않고 영구적으로 제외하면 실제 결함을 놓칠 수 있다. 엄격한 시간 비교를 완화하는 것도 요구조건과 허용 오차를 이해한 뒤 결정해야 한다.

준비 개념과 학습 목표

준비 개념

  • 회귀는 변경 후 이전에 되던 행동이 깨지는 문제다.

  • 검사 수와 기능 중요도는 같지 않다.

학습 목표

  • 통과율·미수행·필수 차단 기준을 구별한다.

  • 수정 버전의 재현 검사와 회귀 범위를 보고한다.

필수 검사가 skip인데 실행 통과율이 100%이면 출시해도 될까?

자체 예정 검사는 120개다. 검사 본문을 수행한 80개는 모두 통과했고, 수집 후 건너뛴 20개와 수집되지 않아 미수행인 20개가 따로 있다. 이 장부의 실행 분모는 본문 수행 80개로 정의한다. 실행 통과율은 80/80=100%지만 예정 대비 통과율은 80/120=2/3≈66.7%다.

자체 출시 조건은 필수 저장 검사 C가 지정한 현재 산출물에서 실제 통과해야 한다. C가 skip 20개 안에 있다면 조건을 충족하지 않는다. 실패가 0개라는 요약이나 wrapper가 도구의 비정상 종료를 0으로 바꾼 표시만으로 필수 수행 근거를 만들 수 없다.

현재 pytest 공식 종료 문서는 수집 없음의 코드 5와 경고 한도 초과의 코드 6도 구별한다. 기존 기본 본문은 그대로 보존하고 현재 문서의 0부터 6까지 정의와 사용 버전·정책을 함께 확인한다. 도구 종료코드는 수행 범위를 읽는 한 근거이며 필수 검사 목록·skip·실제 산출물과 함께 판단한다.

먼저 확인할 개념
  • 릴리스 분모와 필수 조건

    skip과 수집되지 않은 미수행을 나누어 기록한다.

  • 검사한 산출물의 연결

    현재 공개 예정 산출물의 실제 검사 결과를 확인한다.

릴리스 기준을 먼저 명시한다

릴리스 판단은 총 통과율 한 숫자로 끝나지 않는다. 필수 기능 검사·미해결 결함·검증 환경·실제 공개 산출물의 연결을 기준으로 정한다. 아래 저장 검사 필수 통과 규칙은 자체 수업 정책이며 모든 프로젝트의 표준 정책이 아니다.

한 중요한 실패를 쉬운 검사 수백 개 추가로 희석하지 않는다. skip·미수행·수집 실패·중단은 실행 후 통과와 다르다. pytest의 종료코드5는 테스트 수집 없음이고0과 같은 뜻이 아니다. 실제 도구 버전과 전체 요약도 확인한다.

수정 확인과 회귀를 함께 기록한다

수정한 문제의 재현 입력이 새 버전에서 기대값으로 바뀌었는지 확인한다. 이어 관련된 정상 입력·경계 입력·연결 기능을 살펴 이전 동작의 파손을 찾는다. 검사 계획은 변경의 영향 범위에 맞추며 무관한 반복 횟수만 늘리는 것과 구별한다.

원래 실패 버전과 새 버전, 입력, 기대값, 결과 및 환경을 연결한다. “회귀 검사 완료”라고 쓸 때 실제로 어떤 검사들이 수행되었는지 목록을 남긴다. 전체 테스트 통과는 검사하지 않은 기능·환경까지 무결함이라는 증거가 아니다.

보고의 분모와 산출물을 보존한다

전체 예정 검사 수, 실행한 검사 수, 통과·실패·skip·미수행을 나누어 적는다. 실행 통과율과 예정 대비 통과율은 서로 다른 분모다. 표에서 어느 비율인지 이름을 붙이지 않으면 완료 범위가 과장될 수 있다.

검사한 패키지와 공개할 패키지가 달라지면 결과 적용 범위를 다시 확인한다. 실제 배포와 공개 접속 및 사용자 실험은 테스트 문서 작성만으로 수행되지 않는다. 보고는 알려진 사실·남은 위험·다음 확인을 전달하는 도구다.

중간 과정을 따라가는 예제

자체 릴리스 규칙은 저장 검사 반드시 통과다. 예정100개 중90개 실행되어89개 통과·저장 검사1개 실패,10개 미수행이다. 실행 통과율과 예정 대비 통과율, 릴리스 판정을 구하자.

  1. 실행 통과율89/90×100≈98.9%다.

  2. 예정 대비 통과율89/100=89%이고 미수행10/100=10%다.

  3. 저장 필수 검사 실패로 자체 기준에서는 차단이다. 높은 실행 통과율로 실패를 지울 수 없다.

약98.9% 실행 통과율, 예정 대비89% 통과, 미수행10개다. 자체 필수 저장 규칙 때문에 릴리스 불통과다.

목표 소스 H2인데 H1 산출물 P1만 검사했다면 P2 검사 상태를 적어라. A 있음/캐시 없음에서 통과, A 없음/캐시 있음에서 실패하는 자체 표에서 A의 필요·충분조건 여부를 적어라. 예정 120개, 본문 통과 80개, skip 20개, 미수집 20개이고 필수 C가 skip이면 두 통과율과 자체 출시 판정을 구하라.
