요구사항과 블록도

세 숫자를 더하는 회로도 시작과 완료 규칙이 필요할까?

준비 개념과 학습 목표

준비 개념

  • 이진수와 비트 폭

  • 레지스터

  • 상승 에지

학습 목표

  • 입력 범위와 합의 폭을 정한다.

  • 클록 에지별 입력 계약을 쓴다.

  • 블록도에 자료와 제어 신호를 구별한다.

세 값 설계를 다섯 값 설계로 바꾸면 어느 계약이 함께 바뀔까?

원래 단원은 unsigned 4비트 값 세 개를 합한다. 여기서는 별도의 수정 설계 N=5를 명시하여 다섯 번의 수신을 합한다. 시작 에지는 값을 받지 않고, RUN의 valid=1 에지만 수신하며, DONE에서는 ack를 기다리는 우선순위는 그대로다. 원래 설계를 몰래 다섯 값으로 해석하지 않는다.

최댓값은 5×15=75다. 6비트의 최댓값 63보다 크므로 정확한 합에는 7비트가 필요하다. 수신 개수 0부터 5까지는 3비트로 표현한다. 데이터 포트 value는 여전히 4비트다. 출력 폭·내부 합 폭·0 확장 폭을 함께 바꾸고 마지막 판정은 직전 개수가 4인지로 바꾼다.

동일한 입력값도 어디에서 수신했는지가 중요하다. start를 여러 에지 동안 1로 유지하면 RUN에서는 무시되지만 DONE의 ack로 IDLE에 돌아온 다음 에지에서는 또 시작할 수 있다. 회로가 자동으로 버튼의 새 누름을 구별하는 것이 아니다. 환경은 시작 에지와 승인 시점을 계약에 맞춰 제공해야 한다.

먼저 확인할 개념
  • 자리올림과 전체 합의 폭

    낮은 비트와 자리올림을 함께 보관하는 정수 등식을 적용한다.

  • 상태와 입력의 역할

    같은 입력도 현재 상태에 따라 다른 다음 상태를 만든다는 정의를 사용한다.

숫자의 범위와 성공 조건을 적는다

자체 작은 회로는 부호 없는 4비트 값 세 개를 받아 합을 내는 누산기다. 각 값은 0부터 15까지이며 최댓값은 45다. 5비트는 31까지만 표현하므로 합 레지스터와 result 출력은 6비트로 정한다.

포트는 clk, reset, start, valid, value[3:0], ack와 result[5:0], busy, done이다. valid는 현재 값이 유효하다는 표시다. 세 개를 받는 동안 값이 없는 에지는 개수에 넣지 않는다. 입력 범위·수신 횟수·출력 유효 시점을 함께 요구에 쓴다.

같은 에지에서 겹치는 요청을 정한다

모든 입력은 하나의 클록 영역에 있고 상승 에지 주변의 입력 타이밍 조건을 지킨다고 가정한다. reset은 1일 때 활성인 동기 리셋이며 모든 상태에서 가장 높은 우선순위다. 리셋 에지에서 상태는 IDLE, 합과 개수는 0이 된다.

IDLE에서 start가 1이면 합과 개수를 지우고 RUN으로 간다. 같은 에지의 valid는 받지 않는다. RUN에서는 valid가 1인 에지에서만 값을 받으며 start와 ack는 무시한다. 세 번째 수신 뒤 DONE으로 간다. DONE에서는 ack만 IDLE 복귀를 결정하고 start와 valid는 무시한다.

블록의 경계에 계약을 표시한다

자료 경로에는 값의 0 확장기·가산기·합/개수 레지스터·개수 비교기가 있다. 제어기는 상태와 valid 및 마지막 값 여부를 보고 지우기·저장 허용 신호를 낸다. 화살표에는 이름과 폭을 쓰고 공통 clk와 reset도 나타낸다.

busy는 RUN에서만 1이고 done은 DONE에서만 1이다. 결과는 done이 1일 때만 유효하다. DONE에서 ack와 start가 동시에 1이면 IDLE로만 가며 다시 시작하려면 다음 IDLE 에지에 start가 필요하다. IDLE의 합은 이전 결과를 유지할 수 있지만 유효한 새 결과라는 뜻은 아니다.

중간 과정을 따라가는 예제

초기 리셋 뒤 에지 0에 start와 valid가 함께 1이고 값은 9다. 에지 1/2/3에 valid가 1이고 값은 3/15/2다. 최종 합과 유효 시점을 구하라.

  1. 에지 0은 시작만 받아 RUN, 합 0, 개수 0이 된다. 값 9는 제외한다.

  2. 에지 1 뒤 합 3, 개수 1이다. 에지 2 뒤 합 18, 개수 2다.

  3. 에지 3 뒤 합 20, 개수 3, 상태 DONE이 된다. 이후 전파 지연을 거쳐 done이 1이며 result 20이 유효하다.

합은 20이다. 완료 출력은 세 번째 수신 에지 뒤 유효하며 시작 에지의 값은 합에 들어가지 않는다.

조건을 바꾸어 비교하기

모든 폭을 동시에 바꾸기

N=5의 입력이 모두 15다. 내부 합만 7비트로 바꾸고 result를 6비트로 두면?

  1. 정확한 내부 합은 75다.

  2. 6비트 출력이 낮은 비트만 내보내면 75 mod 64=11이다.

  3. 내부와 외부 출력 계약의 폭을 모두 7비트로 맞춰야 한다.

내부 계산의 정확성이 외부 전달의 정확성을 대신하지 않는다.

유지된 start와 새 작업

DONE에서 start=1,ack=1인 에지 뒤에도 start가 1이다. 다음 IDLE 에지의 동작은?

  1. DONE 에지는 IDLE로만 돌아간다.

  2. 그다음 에지의 현재 상태는 IDLE이고 start=1이다.

  3. 다시 합과 개수를 지우고 RUN으로 간다.

두 번째 시작을 막으려면 환경이 start를 낮추거나 별도의 사건 계약을 설계해야 한다.

마지막 값의 후보와 완료 결과를 어떻게 같은 에지에 맞출까?

N=5 수정 설계의 상태는 (state,k,A)다. RUN에서 이미 k개를 받은 합 A는 그 k개 값의 합이다. valid=0이면 모두 유지한다. valid=1이면 A_next=A+value,k_next=k+1이며 직전 k=4인 경우에 DONE으로 간다. 동기 reset은 이 모든 계산보다 우선한다.

마지막 에지에서 A_next를 계산했어도 출력 저장 칸을 따로 두고 옛 A를 복사하면 마지막 값이 빠질 수 있다. 결과를 합 레지스터의 새 값으로 읽거나 같은 후보 A+value를 저장하도록 계약을 맞춘다. 여기서는 별도 result 레지스터 없이 A를 출력하고 DONE일 때 유효하다고 정의한다.

불변식은 A≤15k와 0≤k≤5를 포함하지만 그 조건만으로 정확한 입력 합이라는 결론은 나오지 않는다. 잘못된 A=0도 많은 k에서 범위 조건을 통과한다. 범위·수신 개수·정확한 접두 합을 함께 확인하고 리셋으로 작업이 취소된 경계를 별도로 표시한다.

자료 경로는 계산과 저장을 맡는다

datapath는 자료 경로라는 뜻이다. 4비트 값을 앞에 0 두 개를 붙여 6비트로 확장하고 현재 합과 더한다. 합 레지스터의 입력 선택기는 0·현재 합·가산 결과 중 제어 신호가 지시한 값을 고른다.

개수는 0/1/2/3을 표현하는 2비트 레지스터다. 마지막 수신 판정은 에지 직전 개수가 2인지 비교한다. 가산기는 늘 후보 값을 계산할 수 있지만 저장 허용이 없으면 레지스터는 바뀌지 않는다. 계산된 후보와 저장된 결과를 구별한다.

제어기는 저장 시점과 상태를 결정한다

controller는 제어기다. IDLE에서 start를 받으면 지우기를 지시하고 RUN으로 간다. RUN에서 valid를 받으면 합 저장과 개수 증가를 지시한다. 직전 개수가 2이면 같은 에지에 세 번째 값을 저장하고 DONE으로 간다.

RUN에서 valid가 0이면 아무 값도 저장하지 않는다. DONE에서는 합과 개수를 유지하고 ack를 기다린다. done은 현재 상태가 DONE인지에만 의존하는 Moore 출력이다. 실제 레지스터 출력과 상태 해독기의 지연은 0이 아니므로 에지 바로 그 순간 안정한 값이라고 가정하지 않는다.

이전 값으로 동시 갱신을 설명한다

순차 갱신에서는 합의 다음 값과 개수의 다음 값을 에지 직전 값으로 계산한다. SystemVerilog의 nonblocking 대입을 사용할 때 앞 줄의 개수 증가가 뒤 줄의 비교에 즉시 반영된다고 생각하면 마지막 시점을 잘못 고를 수 있다.

RUN에서 k개를 받은 뒤에는 개수가 k이고 합은 그 k개 값의 합이라는 불변 조건을 둔다. k가 0/1/2인 동안 이를 유지하고 다음 valid 수신이 세 번째일 때 DONE에서 세 값의 합을 얻는다. 리셋은 진행 중 작업을 중단하므로 리셋 뒤에는 새 시작이 필요하다.

여러 경로의 시간 조건은 어떻게 한 주기와 skew에 모일까?

별도의 가상 두 경로 A와 B를 검사한다. A의 최대 지연과 setup 합은 4.6 ns, 최소 도착은 0.3 ns, hold는 0.4 ns다. B는 최대 합 5.2 ns, 최소 도착 0.7 ns, hold 0.2 ns다. 공통 skew가 0이고 주기가 5 ns면 A는 setup만 통과하고 B는 hold만 통과한다.

A를 수정한 소자가 최소 도착을 0.2 ns, 최대 합을 0.7 ns 늘린다고 가정하자. A의 새 최대 합은 5.3 ns, 최소 도착은 0.5 ns다. 두 경로 모두를 통과시키려면 skew 0에서 주기는 적어도 5.3 ns여야 한다. 가장 긴 경로 하나만 찾는 과정이 최소 경로의 hold 검사를 없애지 않는다.

단순 고정 모형에서 δ=target−source를 두 경로의 공통 클록 도착 차이로 둔다. setup은 δ≥max(5.3−T,5.2−T), hold는 δ≤min(0.5−0.4,0.7−0.2)=0.1 ns다. 실제 uncertainty·온도·입출력·다른 경로는 제외한다. 허용 구간의 존재를 따져 계산의 조건부 결론으로 기록한다.

하나의 클록과 skew 0을 가정한 레지스터 간 경로에서 최대 clock-to-Q 지연과 최대 조합 지연 및 setup의 합이 클록 주기 이하이어야 한다. 가상 수치 0.8 ns+3.2 ns+0.6 ns=4.6 ns를 사용한다.

주기가 5 ns이면 이 경로의 setup 여유는 0.4 ns다. 주기가 4 ns이면 −0.6 ns로 실패한다. 5 ns의 역수는 200 MHz지만 한 경로의 계산만으로 실제 회로가 200 MHz를 달성했다고 말할 수 없다. 다른 경로·입출력·클록 불확실성과 실제 도구 보고를 확인해야 한다.

너무 빨리 변하는 경로도 실패한다

같은 skew 0 모델에서 최소 clock-to-Q와 최소 조합 지연의 합은 hold 이상이어야 한다. 0.2 ns+0.1 ns=0.3 ns인데 hold가 0.4 ns면 0.1 ns가 부족하다. 클록 주기를 늘려도 같은 에지 뒤의 너무 빠른 변화는 해결되지 않는다.

가상 경로에 최소 0.2 ns의 지연을 더하면 최소 합은 0.5 ns가 된다. 다만 추가 소자가 최대 지연도 늘릴 수 있으므로 setup을 다시 계산해야 한다. FPGA에서는 일반 논리로 임의 지연을 만들기보다 도구의 제약·배치배선·타이밍 수정 결과를 검토한다.

예상표와 실행 기록이 같아 보이면 어떤 결론까지 낼 수 있을까?

N=5 수정 설계의 정확한 합 기준 모델은 수신값 다섯 개의 정수 합이다. 6비트로 잘라낸 DUT와 기준 모델을 함께 사용하면 최대 입력에서 둘 다 11을 내어 시험이 통과할 수 있다. 원래 계약은 75이므로 기준 모델의 독립성이 필요하다.

가상 보고서의 이름을 단계별로 읽자. 종이 전이표·유한 Python 정수 검사는 HDL 실행이 아니다. RTL 시뮬레이션 기록이 실제로 있더라도 그 코드와 자극의 기능 근거다. 실제 합성/배치배선/전체 정적 타이밍/보드 관찰에는 서로 다른 도구·버전·제약·관측 증거가 필요하다.

다섯 값의 조합 수는 16^5=1,048,576개다. 이 수를 계산한 것은 그만큼의 시험을 실행한 것이 아니다. 값 조합을 전수 확인해도 무제한 대기·리셋·ack/start 겹침의 모든 시간 흐름을 자동 검증하지 않는다. 완료 시점만 조건부 비교하면 완료가 전혀 없는 기계도 그 조건을 어기지 않을 수 있어 진행성 요구를 별도로 둔다.

같은 이름의 설계도 단계마다 다르다

종이에 그린 상태표는 설계 의도를 보여 준다. RTL 시뮬레이션은 실행한 코드와 입력 자극 아래의 동작을 보여 준다. 기대값을 잘못 쓴 testbench는 오류를 놓칠 수 있으므로 계약과 독립적인 참조 계산을 비교한다.

RTL 기능 시뮬레이션이 모든 물리 지연을 재현하는 것은 아니다. 합성 결과는 코드가 하드웨어 구조로 변환된 것이며 배치배선과 정적 타이밍 분석은 실제 자원과 경로 조건을 더 다룬다. 그 뒤 보드 실행은 연결·입력·클록 환경까지 포함한 관찰이다.

실제 실행을 주장하려면 환경을 남긴다

시뮬레이션 결과에는 도구와 버전·RTL 및 testbench 버전·입력·기대 출력·실패 수·파형 관찰 범위를 남긴다. FPGA 결과에는 장치/보드·클록·핀과 입출력 제약·리셋 방식·타이밍 보고·비트스트림 버전·실제 관측을 추가한다.

LED가 켜진 한 장면은 모든 값을 더했거나 모든 경로의 타이밍을 만족한다는 증거가 아니다. 어떤 입력과 시점에서 무슨 값을 읽었는지 기록한다. 버튼을 직접 사용했다면 동기화와 바운스 처리가 계약을 충족하는지도 확인한다.

이번 단원의 완료와 미수행을 분리한다

이번에는 세 값 누산기의 요구·포트·상태표·비트 폭을 정의하고 정상/대기/리셋 흐름과 가상 시간 조건을 손으로 확인했다. 실제 RTL 파일을 구현하거나 시뮬레이터를 실행한 결과는 제공하지 않는다.

합성·배치배선·타이밍 보고 생성·비트스트림 작성·보드 계측·학생 실험도 미수행이다. 이후 실습에서 각 단계가 실제로 끝나면 그 단계의 증거와 실패 조건을 추가한다. 자체 예제의 숫자와 실제 기기 성능 측정값을 섞지 않는다.

다른 문제에 적용하기

별도의 N=5 설계를 에지 0에서 시작한다. 이 시작 에지의 value=9와 valid=1은 수신에 포함하지 않는다. 에지 1에서 15를, 에지 2에서 0을 받고 에지 3에서는 대기한다. 에지 4, 5, 6에서는 각각 15를 받는다. 에지 7의 현재 상태는 DONE이며 ack=start=1이다. 에지 8에도 start=1이 유지된다고 하자. 각 수신 뒤 합과 완료 시점, 새 시작을 구하고 마지막에 옛 A를 결과 칸에 복사한 mutant와 비교하라. 수정된 시간 경로 A의 최대 합은 5.3 ns, 최소 도착은 0.5 ns, hold는 0.4 ns다. B의 최대 합은 5.2 ns, 최소 도착은 0.7 ns, hold는 0.2 ns다. T=5.2 ns에서 공통 δ의 허용 구간도 구하라. 실제 HDL과 보드를 실행했는지 구별하여 보고하라.

힌트 1

현재 상태에서만 수신하며 대기는 개수를 유지한다. 마지막 후보와 옛 저장 값을 나눈다.

힌트 2

setup은 δ의 하계, hold는 상계다. ack로 돌아온 다음 IDLE 에지의 start를 따로 처리한다.

풀이와 답 확인

  1. 에지 0 뒤에는 RUN이며 k=0, A=0이다. 에지 1 뒤에는 합이 15이고 k=1이다. 에지 2 뒤에도 합은 15이며 k=2다. 에지 3에서는 이 상태를 유지한다.

  2. 에지 4 뒤에는 합이 30이고 k=3이다. 에지 5 뒤에는 합이 45이고 k=4다. 에지 6 뒤에는 합이 60이고 k=5이며 DONE으로 간다. 정상 결과는 60이다. mutant의 별도 결과 칸은 옛 A=45를 내보내므로 마지막 수신값 15를 잃는다.

  3. 에지 7은 IDLE로만 돌아가고 기존 A=60은 유효한 새 결과가 아니다. 에지 8의 start는 새 회차를 시작하여 RUN/k=0/A=0이 된다.

  4. 시간 하계는 max(5.3−5.2,5.2−5.2)=0.1 ns이며 상계는 min(0.5−0.4,0.7−0.2)=0.1 ns다. 공통 δ=0.1 ns 한 점에서만 모형의 등호 조건이 맞는다.

  5. 이 결과는 선언한 이상적 상태와 가상 시간 산술이다. 아래 Python의 지정 모형 검사만 수행했고 실제 HDL·합성·타이밍 보고·보드·학습자 시험은 미수행이다.

정상 합은 60이고 마지막 옛 합을 복사한 mutant는 45다. 완료는 에지 6 뒤다. 에지 7은 IDLE 복귀이며 에지 8은 새 회차의 RUN/k=0/A=0 시작이다. 공통 δ의 허용 구간은 {0.1} ns이며 실제 변동에 대한 여유 증거는 없다. 실제 HDL/보드 실행은 미수행이다.
