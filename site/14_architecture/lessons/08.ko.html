소단원 8.1

forwarding·stall

아직 레지스터에 쓰지 않은 답을 다음 명령이 먼저 쓸 수 있을까?

준비 개념과 학습 목표

준비 개념

  • IF/ID/EX/MEM/WB

  • 레지스터 읽기·쓰기

학습 목표

  • 생성 시점과 필요 시점을 비교한다.

  • 우회 가능 여부와 stall을 구분한다.

명령에 같은 번호가 보이면 반드시 기다려야 할까?

hazard 판정은 비트의 번호 일치보다 명령의 의미를 먼저 확인한다. 자체 LOAD R1,[주소] 뒤 ADDI R2,R3,1은 즉시값 1을 사용하며 R1을 읽지 않는다. 즉시값을 source 레지스터 번호로 착각하면 가짜 stall이 생긴다.

반대로 STORE의 자료 레지스터는 목적지 쓰기가 아니라 읽기다. 자체 STORE [R4],R1은 주소 R4와 자료 R1을 읽는다. 이 보강에서는 store 자료를 EX 시작에서 받아 보관하는 경로만 있다고 정한다. LOAD 바로 뒤 이 STORE가 오면 본문 규약의 한 클록 대기가 필요하다.

상수 0 레지스터를 가진 자체 ISA에서는 그 목적지 쓰기를 일반 RAW 생산자로 세지 않는다. 하지만 LOAD의 목적지가 0이라는 이유로 메모리 접근이나 fault까지 없어지는 것은 아니다. 값 전달의 쓰기 후보 제외와 명령 전체의 효과를 나눈다. 실제 ISA 실행이 아닌 명시한 자체 연습 규약이다.

먼저 확인할 개념
  • 실제 writer와 소비 시점

    번호 일치에 쓰기 여부와 실제 읽기 의미를 더한다.

  • read/write 집합

    즉시값과 STORE 입력을 올바르게 분류한다.

값이 준비되는 경계를 찾는다

RAW 의존은 앞 명령이 쓸 값을 뒤 명령이 읽는 관계다. 이름이 같은지만 보지 말고 앞 명령이 실제로 쓰는지, 뒤 명령이 그 필드를 실제 입력으로 사용하는지 확인한다.

여기서는 단일 발행·순서 실행 IF/ID/EX/MEM/WB의 5 단계를 쓰며 ALU 값은 EX 끝, load 값은 MEM 끝에 준비된다고 정한다. EX 입력은 사이클 시작에 필요하고 단계 간 레지스터에서 EX로 우회할 수 있다.

준비된 최신 값은 우회한다

ALU 결과를 EX/MEM에서 다음 명령 EX 입력으로 주면 WB까지 기다릴 필요가 없다. 우회는 레지스터 파일에 쓰는 작업과 별도 경로다.

같은 레지스터를 여러 앞 명령이 쓰면 프로그램 순서상 가장 가까운 앞 명령을 고른다. 더 오래된 값이 준비되었다고 최신 아직 미준비 값을 건너뛰면 잘못된 결과가 된다.

아직 없는 값은 기다린다

load 바로 뒤 소비자의 EX가 load의 MEM과 같은 사이클이면 소비자 시작 때 데이터가 없다. 이 모델에서는 소비자를 한 사이클 멈추고 EX에 부작용 없는 bubble을 넣는다.

PC와 IF/ID는 유지하지만 앞의 load는 진행시켜야 한다. 모든 단계를 함께 얼리면 필요한 값도 만들어지지 않는다. 실물의 단계·메모리 지연이 달라지면 stall 수도 달라진다.

STORE 자료는 EX 시작에 필요하다고 별도로 정했다. MEM에서 자료를 받는 우회 경로를 추가한 설계는 이 표와 다른 모형이다.

중간 과정을 따라가는 예제

I1=load r1,[r0], I2=add r2,r1,r3 이다. I1 IF가 c1, r3=4, 읽은 메모리 값=7 이며 앞서 정한 우회 모델을 쓴다.

  1. I1 은 c1 IF, c2 ID, c3 EX, c4 MEM, c5 WB다. I2 는 c2 IF, c3 ID 뒤 원래 c4 EX가 필요하다.

  2. c4 시작에는 load 값이 없어 I2 를 ID에 유지하고 EX bubble을 둔다. c4 끝에 값 7 이 준비된다.

  3. I2 는 c5 EX에서 MEM/WB의 7 을 받아 7+4=11, c6 MEM, c7 WB로 r2 를 쓴다.

한 stall 뒤 r2=11 이고 두 명령 완료는 c7 이다. 이상적 두 명령의 c6 보다 한 사이클 길다.

조건을 바꾸어 비교하기

즉시값 1은 R1이 아니다

R3=8인 ADDI R2,R3,1의 입력과 결과를 구하라.

  1. 레지스터 입력은 R3의 8이다.

  2. 상수 1을 더한다.

R2=9이며 앞 LOAD R1의 자료를 기다리지 않는다.

비교할 점

인코딩 숫자와 실제 source 의미를 구별한다.

STORE는 자료도 읽는다

LOAD가 7을 읽고 R4=100인 뒤 STORE의 필요한 값을 구하라.

  1. 주소는 100이다.

  2. 자료 R1=7이 EX 시작에 필요하다.

한 대기 뒤 주소 100에 자료 7을 보관해 쓰는 모형이다.

비교할 점

일반 레지스터를 쓰지 않는 명령도 레지스터 값을 읽을 수 있다.

종이와 본문으로 직접 해보기

I1 을 add r1,r4,r5 로 바꾸고 r4=3,r5=4 면 I2 에 stall이 필요한가?

힌트 보기

I1 EX 끝과 I2 EX 시작을 나란히 놓는다.

풀이 보기

c3 끝의 7 을 c4 EX로 우회할 수 있어 stall이 없다. I2 는 c6 WB에서 11 을 쓴다.

오해와 반례

forwarding이 있으면 모든 의존에서 stall이 없어진다.

load 데이터는 필요한 시작 시점 뒤에 생긴다. 미래 값을 우회할 수는 없으므로 제시 모델의 load-use는 한 stall이 필요하다.

상수 0 레지스터 R0에 대한 앞 ALU 쓰기와 뒤 ADD R2,R0,R3가 있고 R3=8이다. 결과와 RAW 대기는?

힌트 1

힌트 2

소단원 8.2

분기와 flush

틀린 길로 가져온 명령은 이미 실행 목록에 있는데 어떻게 없앨까?

준비 개념과 학습 목표

준비 개념

  • 분기와 PC

  • 파이프라인 유효 비트

학습 목표

  • 분기 판단 시점과 잘못 가져온 수를 연결한다.

  • 추측 명령의 상태 변경을 억제한다.

틀린 경로의 대기 요청이 분기 전환을 막아도 될까?

본문의 flush는 분기보다 뒤의 잘못된 경로를 취소한다. 자체 제어 표에서 older 분기가 taken을 확정한 같은 경계에 younger 명령이 프런트엔드 hold를 요구할 수 있다고 정한다. 이 요청의 종류는 일반적인 앞쪽 대기 요청이며 특정 LOAD-use 검출 회로를 구현했다고 가정하지 않는다.

이 경우 취소되는 younger 요청을 그대로 보존하면서 PC도 hold하면 이미 정해진 올바른 목적지로 이동하지 못한다. 자체 우선순위는 유효한 older 분기의 전환과 younger 취소를 먼저 적용한 뒤 남는 유효 명령의 대기를 판단하는 것이다. 취소보다 앞선 정상 명령의 상태는 유지한다.

분기를 일찍 판단하면 오판 벌점은 줄 수 있지만 주기가 늘 수도 있다. 본문 분포의 장기 평균에서 늦은 설계 CPI=1.1, 주기 5ns면 5.5ns/명령이다. 이른 설계 CPI=1.05, 주기 5.6ns면 5.88ns/명령으로 느리다. 시작·종료 비용과 다른 hazard 상호작용은 이 자체 평균 비교에서 제외한다.

먼저 확인할 개념
  • younger 취소와 older 보존

    flush 범위가 프로그램 순서로 정해진다.

  • 보존하는 대기와 bubble

    기다리는 정상 명령과 취소된 명령을 구별한다.

다음 PC도 의존하는 값이다

분기 방향과 목적지가 알려지기 전에는 다음 명령을 확정할 수 없다. 여기서는 5 단계, EX 끝에서 판단, 순차 주소를 예상하며 branch delay slot은 없다고 정한다.

분기 피연산자의 RAW hazard도 처리해야 한다. 잘못 읽은 비교값으로 빠르게 분기하는 것은 올바른 해결이 아니다.

잘못된 경로는 무효로 만든다

taken이라고 EX 끝에 알게 되면 그때 ID와 IF에 있는 두 younger 명령은 잘못된 경로다. 유효 비트나 쓰기 제어를 막고 다음 사이클 IF를 목적지로 바꾼다.

flush는 이 younger 명령들을 취소하는 것이며 이미 앞선 older 명령의 정상 결과를 지우는 작업이 아니다. stall은 명령을 보존하며 기다리므로 둘을 구별한다.

판단이 늦을수록 낭비가 커진다

분기 판단을 더 뒤로 미루면 잘못 가져온 명령 수가 늘 수 있다. 실제 비용은 폭·예측·단계·동시 stall에 영향을 받는다.

아래 CPI는 긴 실행에서 독립된 오예측 비용만 더한 교육용 평균이다. 시작·종료 채우기 비용과 캐시·데이터 stall은 제외하며 실제 측정으로 보고하지 않는다.

준비 개념과 학습 목표

준비 개념

학습 목표

뒤 명령의 오류가 먼저 보이면 그 명령부터 처리할까?

자체 명령 순서에서 I1은 PC 100의 R1←R1+1, I2는 PC 104의 LOAD R2,[bad], I3는 PC 108의 불법 명령이다. 초기값은 R1이 4, R2가 9다. I3의 오류는 사건 시각 4에, I2의 메모리 fault는 사건 시각 6에 발견한다고 정한다. 이 시각은 실제 5단계 사이클 표를 구현한 것이 아니라 검출 순서를 비교하는 자체 사건 번호다.

정확한 재시작 가능 fault 경계를 만들려면 명령 순서상 가장 앞선 fault인 I2를 처리한다. 더 앞선 I1만 완료하여 R1은 5가 된다. I2의 R2 쓰기는 일어나지 않아 R2는 9다. I3는 정상 상태를 바꾸지 않는다. 본문의 fault PC 규약에 따라 104를 저장한다. 먼저 검출된 I3를 선택하는 것은 이 경계를 보장하지 못한다.

원인을 고친 뒤 PC 104부터 재시작하면 I1의 증가를 다시 하지 않는다. PC 100으로 잘못 돌아가면 이미 5인 R1을 6으로 늘려 결과가 달라진다. 반대로 I2가 정상 완료해 R2에 17을 쓴 별도 변형에서는 I3의 fault 경계에 R1이 5, R2가 17이어야 한다. fault 경계를 명령 순서와 확정 상태로 설명한다.

먼저 확인할 개념
  • 정확한 fault 경계

    이전 완료와 해당·이후의 정상 효과 억제를 나눈다.

  • younger 효과 취소

    먼저 검출됐어도 앞선 오류 뒤의 명령을 확정하지 않는다.

프로그램 순서의 경계를 만든다

정확한 예외는 명령 순서의 한 경계에서 상태가 설명되는 성질이다. 여기서 재시작 가능한 fault를 다루며 해당 명령 이전은 완료, 해당 및 이후는 정상 프로그램 상태를 변경하지 않은 것으로 정한다.

예외 처리용 PC·원인 레지스터 변화는 정상 명령의 결과와 구별한다. trap처럼 다음 명령을 가리키는 ISA 규약이나 비동기 interrupt 경계를 모든 fault와 같다고 단정하지 않는다.

검출이 먼저여도 처리 순서를 지킨다

older load의 메모리 오류가 younger add의 EX 오류보다 늦게 검출될 수 있다. 검출 시각만으로 먼저 핸들러에 가면 이전 명령 상태가 애매해진다.

각 명령의 PC·예외 정보·유효 여부를 함께 보관하고 순서대로 확정할 때 가장 먼저인 예외를 처리한다. younger 쓰기와 store 부작용도 확정 전에 억제해야 한다.

재시작은 원인을 고친 뒤 한다

주소 변환 fault라면 운영체제가 매핑을 고친 뒤 저장한 fault PC에서 다시 실행할 수 있다. 어떤 fault든 무조건 반복하면 해결된다는 뜻은 아니다.

순서 밖 실행에서도 계산과 commit을 나누는 reorder buffer 같은 방법이 가능하다. 모든 실제 처리기가 하나의 방법이나 모든 예외에 같은 정확성을 쓴다는 주장은 아니다.

소단원 8.4

명령별 의존 추적

같은 레지스터 이름을 여러 번 쓸 때 화살표를 어디로 이어야 할까?

준비 개념과 학습 목표

준비 개념

  • read/write 집합

  • RAW/WAR/WAW

학습 목표

  • 각 read에 최신 이전 writer를 연결한다.

  • 이름 의존과 실제 stall 조건을 구분한다.

이름을 나누면 필요한 값까지 사라질까?

본문의 I1:R1←R2+R3, I2:R4←R1+R5, I3:R1←R6+R7, I4:R8←R1+R4를 쓴다. R1의 두 쓰기에 새 이름 A와 B를 붙이면 I1:A←R2+R3, I2:C←A+R5, I3:B←R6+R7, I4:D←B+C가 된다. 같은 원래 R1이라도 I2는 A, I4는 B를 읽는다.

본문 수치로 A=5, C=9, B=11, D=20이다. 쓰기마다 이름을 구별하면 이전 R1 읽기와 뒤 R1 쓰기 사이의 이름 충돌, 두 R1 쓰기의 이름 충돌을 나눌 수 있다. 하지만 C는 여전히 A를, D는 B와 C를 필요로 한다. 세 RAW 값 의존은 사라지지 않는다.

이것은 무한한 이름을 쓸 수 있다는 자체 종이 변환이다. 실제 레지스터 수·할당·해제·commit·분기 복구는 구현하지 않았다. 모든 R1의 읽기를 마지막 이름 B로 한꺼번에 바꾸면 I2까지 11+4=15가 되어 D=26으로 틀린다. 이름 변환은 각 읽기의 당시 최신 정의를 유지해야 한다.

먼저 확인할 개념
  • 최신 정의와 RAW/WAR/WAW

    값을 전달하는 의존과 같은 이름의 충돌을 구별한다.

  • 최신 유효 writer 선택

    읽기마다 어느 앞선 정의가 필요한지 유지한다.

입력과 출력을 표로 적는다

I1: r1←r2+r3 은 r2/r3 을 읽고 r1 을 쓴다. store는 주소 계산 레지스터와 저장할 값 모두 읽지만 일반 목적 레지스터를 쓰지 않는다.

즉시값 필드를 레지스터 read라고 세면 가짜 의존이 생긴다. zero 레지스터와 쓰지 않는 명령도 ISA 의미에 따라 제외한다.

읽기는 가장 가까운 앞 쓰기를 따른다

같은 이름을 반복해 썼다면 각 read는 프로그램 순서의 최신 이전 정의에 연결한다. 그 사이 값을 다시 덮는 명령을 건너뛰어 더 오래된 writer와 연결하면 틀린 값이다.

RAW는 값 전달 의존이다. WAR는 이전 읽기보다 뒤 쓰기가 앞서면 안 되는 이름 의존, WAW는 두 쓰기의 마지막 값 순서 의존이다. 단순 순서 실행에서는 이 이름 관계가 모두 stall을 만들지는 않는다.

정적 화살표와 동적 시간을 분리한다

의존 그래프만으로 stall 횟수를 정할 수 없다. 결과 준비 단계, 소비 단계, 우회 경로와 메모리 응답을 함께 주어야 한다.

메모리는 두 주소가 같은지 판단해야 한다. 서로 다른 레지스터 이름으로 주소를 계산해도 같은 위치를 가리킬 수 있다. 여기서는 우선 레지스터 의존만 계산한다.

중간 과정을 따라가는 예제

I1:r1←r2+r3, I2:r4←r1+r5, I3:r1←r6+r7, I4:r8←r1+r4 이다. r2=2,r3=3,r5=4,r6=10,r7=1 이다.

  1. I2 의 r1 read는 I1 에 연결돼 r4=5+4=9 다.

  2. I4 의 r1 read는 I3 에, r4 read는 I2 에 연결된다. r1=11 로 바뀌어 r8=11+9=20 이다.

r4=9,r8=20 이다. I1→I4 의 r1 직접 RAW로 최신 I3 를 대신하면 안 된다.

  2. 서로 다른 출력 이름 A와 B는 같은 저장 이름을 덮지 않는다.

세 값 간선이 그대로 남는다.

모든 읽기를 마지막 버전으로 바꾸는 오류

I2가 A 대신 B를 읽도록 잘못 변환했다.

  1. B의 값은 11이므로 잘못 읽은 C는 11+4=15다.

  2. D는 B와 C의 합이므로 11+15=26이다.

원래 이름이 같아도 각 읽기의 원천 정의는 다르다.

  3. I1만 완료하여 R1은 5, R2는 9이고 fault PC는 104다. PC 100으로 돌아가면 R1이 6이 되어 같은 증가를 중복 적용한다.

의존·제어 우선순위·정확한 상태·이름 버전을 명시한 조건으로 설명한다. 자체 종이 모형이며 실제 CPU·ISA·OS·HDL·학습자 실험은 수행하지 않았다.

해결한 뒤 점검할 것

  • 즉시값과 STORE 입력을 구별한다.

  • 취소와 보존할 대기의 대상 순서를 설명한다.

  • 가장 앞선 fault와 완료 효과의 재실행 금지를 확인한다.

  • 이름 변환 뒤 남는 RAW와 각 읽기의 버전을 보존한다.
