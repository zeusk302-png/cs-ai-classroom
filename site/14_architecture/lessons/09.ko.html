instruction-level parallelism

지연 3클록의 장치가 매 클록 결과를 낼 수 있을까?

자체 장치는 연산을 시작한 클록을 포함해 세 번째 클록 끝에 결과를 낸다. 독립 연산을 시작할 수 있는 간격은 1클록이다. 네 독립 연산을 각각 클록 1, 2, 3, 4에 시작하면 결과는 각각 클록 3, 4, 5, 6의 끝에 나온다. 클록 1 시작부터 마지막 완료까지 6클록이 걸린다.

네 연산이 각자 앞 결과를 입력으로 쓰는 사슬이면 시작 클록은 각각 1, 4, 7, 10이고 완료 클록은 각각 3, 6, 9, 12의 끝이다. 장치가 독립 입력을 매 클록 받을 수 있어도 아직 앞 결과가 준비되지 않은 의존 연산을 그 간격으로 시작할 수는 없다.

같은 네 연산의 실행 구간 평균 처리율은 독립 작업열에서 4/6=2/3연산/클록, 의존 사슬에서 4/12=1/3연산/클록이다. 장치가 충분히 긴 독립 작업열을 처리할 때의 용량인 1연산/클록과 구별한다. 명령 공급·commit·메모리·분기 비용은 이 자체 일정에서 제외했다. 실제 CPU의 측정값은 아니다.

명령 사이의 데이터 흐름

instruction-level parallelism, ILP는 한 명령 흐름 안에서 독립 명령들이 겹쳐 실행될 기회를 말한다. 스레드를 여러 개 만드는 것과 다르다. 앞 명령의 결과를 읽는 RAW는 진짜 데이터 의존성이다. 이름만 같은 레지스터를 다시 쓰는 WAR/WAW와 구분해야 어떤 순서를 반드시 지킬지 알 수 있다.

지연과 처리율

latency는 한 연산 시작부터 결과 준비까지의 시간이고 throughput은 단위 시간에 완료할 수 있는 작업량이다. 파이프라인 장치는 결과가3cycle 뒤에 나오더라도 독립 연산을 매cycle 새로 시작할 수 있다. 그러나 같은 결과를 이어 사용하는 연산은 앞 결과가 필요하다. 넓은 실행기라도 의존 사슬의 길이는 없애지 못한다.

작은 계산 그래프

교육 모형에서 두 실행기가 있고 각 연산 지연1cycle, 자원/메모리/분기 지연은 없다고 정하자. A=a+b,B=c+d는 독립이라 같은 cycle에 시작할 수 있고 C=A×B는 둘의 결과가 준비된 다음 cycle에 시작한다. 실제 CPU의 명령 decode·issue·메모리 순서 비용은 이 모형에 들어 있지 않다. 손 계산 값은 실제 장치 속도가 아니라 의존성의 하한을 읽는 예다.

superscalar·out-of-order

앞의 긴 명령을 기다리는 동안 뒤의 독립 명령을 해도 될까?

먼저 끝난 뒤 명령은 언제 확정될까?

본문의 I1 LOAD는 클록 1에 시작해 클록 4의 끝에 완료한다. I2는 LOAD 결과를 읽는 1클록 ADD이고 I3는 독립적인 1클록 ADD다. 모두 대기 목록에 있으며 issue 폭은 1이고 LOAD와 ADD 장치는 겹쳐 사용할 수 있다. OoO에서 I3는 클록 2의 끝에, I2는 클록 5의 끝에 완료한다. 엄격한 in-order issue에서는 I2가 클록 5의 끝에, I3가 클록 6의 끝에 완료한다.

이 보강은 commit 규칙을 추가로 정한다. 결과가 끝난 다음 클록의 시작부터 프로그램 순서대로 한 명령씩 commit한다. OoO에서 I1·I2·I3의 commit은 각각 클록 5·6·7의 시작이다. in-order에서도 각각 클록 5·6·7의 시작이다. 마지막 실행 완료가 클록 5의 끝과 클록 6의 끝으로 다르더라도, 이 짧은 작업열의 전체 commit 시점은 같다.

OoO의 검색 범위도 조건이다. 미확정 명령 두 개만 담는 창이 I1과 I2로 가득 차면 독립적인 I3를 미리 볼 수 없다. 이 변형에서는 I1이 클록 5의 시작에 commit한 후, 클록 5의 끝에 I3를 대기 목록에 넣고 클록 6에 issue한다. 창 크기와 dispatch 경계를 바꾸면 일정도 달라진다. 실제 프로세서의 창이나 모든 구현의 commit 규약을 설명하는 표는 아니다.

먼저 확인할 개념
  • 완료와 commit의 구별

    임시 계산 완료와 순서에 따른 최종 반영을 나눈다.

  • retirement와 자원 회수

    앞 명령의 확정이 창과 저장 자원을 풀어 주는 조건을 확인한다.

폭과 순서는 다른 축

superscalar는 한 cycle에 여러 명령을 처리할 수 있는 폭을 가진 설계다. out-of-order는 프로그램상 앞 명령이 기다릴 때 준비된 뒤 명령을 먼저 실행하도록 일정을 정하는 방법이다. 넓지만 in-order일 수도 있고 한 번에 하나를 issue하지만 OoO일 수도 있다. 폭이 있어도 같은 실행 port나 데이터 의존 때문에 매번 최대 폭을 채우지는 못한다.

준비된 작업을 고르기

실행 대기 목록의 명령은 입력 값 준비와 기능 장치 사용 가능 조건을 함께 만족해야 한다. 아직 load 결과가 없는 add는 기다리지만 다른 레지스터만 쓰는 add는 앞서 실행할 수 있다. 실제 메모리 명령은 같은 주소의 이전 store와 관계를 추적해야 하므로 레지스터만 보면 독립으로 보이는 것과 다를 수 있다.

관찰되는 순서는 보존

완료 순서와 commit 순서는 다르다. 전형적 OoO는 여러 결과를 임시 보관하고 프로그램 순서대로 retire/commit하여 순차 의미와 예외 복구를 유지한다. 추측이 틀리면 잘못된 경로의 명령은 최종 상태에 반영하지 않는다. 이것은 cache를 포함한 모든 내부 흔적이 없어진다는 뜻은 아니다. 이 단원의 실행 시간표에는 front-end와 commit 지연을 제외한다.

register renaming·retirement

새 이름이 준비되면 옛 이름을 바로 재사용해도 될까?

자체 초기 매핑은 R1→p1, R2→p2, R3→p5이고 비어 있는 물리 이름은 p3/p4 두 개다. I1이 R1을 쓸 때 p3를 할당하고 I2가 R2를 쓸 때 p4를 할당하면 free list는 빈다. I3가 R3의 새 값을 쓰려면 빈 이름이 생길 때까지 rename을 기다린다.

이 자체 정책은 새 결과를 만드는 순간이 아니라 그 명령이 순서대로 commit하고 옛 이름을 요구하는 입력·복구가 없다고 확인한 뒤 옛 이름을 회수한다. I1 commit 후 p1을 회수할 수 있다는 조건이면 I3는 p1을 새 목적지로 사용할 수 있다. p3는 최신 R1 값의 장소여서 I1이 끝났다고 비는 이름이 아니다.

추측 매핑과 확정 매핑도 나눈다. I1의 R1=9가 p3로 이미 commit됐고 I2의 새 R2→p4는 아직 미확정인 상태에서 I2가 fault이면 확정 매핑 R1→p3/R2→p2로 돌아간다. 처음의 R1→p1로 무조건 돌아가면 앞서 확정한 I1까지 잃는다. 실제 회수·복구 정책은 구현마다 다르며 이 단원은 명시한 자체 표만 다룬다.

먼저 확인할 개념
  • 읽기 태그·free list·회수

    새 목적지와 아직 필요한 옛 저장소의 수명을 구별한다.

  • 순서 commit과 오류 경계

    확정한 older 상태와 취소할 younger 상태를 나눈다.

이름과 값의 세대

ISA 레지스터는 프로그램이 부르는 이름이고 물리 레지스터는 내부 저장 장소다. renaming은 각 쓰기에 새 물리 장소를 할당하여 같은 이름의 값 세대를 구분한다. 앞 명령이 읽을 옛 r1과 뒤 명령이 쓸 새 r1을 분리하면 WAR와 WAW의 이름 충돌을 제거할 수 있다. RAW는 새 장소에서도 필요한 생산자 결과를 기다린다.

읽기 대상을 먼저 잡기

명령을 프로그램 순서로 rename하면서 입력은 현재 매핑을 조회하고 목적지는 새 물리 레지스터에 연결한다. r1=r1+1은 입력으로 옛 r1을 잡은 뒤 목적지 매핑을 바꿔야 한다. 실제 프로세서는 free list·대기 태그·준비 비트 등으로 이를 구현한다. 이 단원은 물리 이름 p1,p2를 쓰는 단순 종이 모형이며 특정 제품의 레지스터 개수나 배치라고 주장하지 않는다.

확정과 복구

retirement는 앞 명령부터 결과와 예외를 확정하는 단계다. 아직 확정되지 않은 새 매핑만으로 실패 경로를 최종 상태로 남기면 안 된다. 예외나 분기 실패에 대비해 확정된 상태 또는 checkpoint에서 회복할 정보를 둔다. 옛 물리 저장소는 필요한 읽기와 복구 상태가 끝나기 전에 재사용하면 안 된다. free list가 고갈되면 rename이 멈출 수 있다.

예측기가 같은 칸을 공유하면 두 단순 분기도 틀릴까?

자체 2비트 카운터 상태를 0/1/2/3으로 두고 2 이상이면 taken(T), 미만이면 not-taken(N)을 예측한다. 실제 T 뒤에는 1을 더하되 3에서 멈추고, N 뒤에는 1을 빼되 0에서 멈춘다. 예측은 갱신 전 상태로 한다.

초기 상태 2에서 실제 N,N,T,T를 받으면 예측 T,N,N,N이고 세 번 틀린다. 최종 상태는 2다. 같은 입력열이라도 초기 상태 0에서는 예측 N,N,N,N으로 두 번 틀린다. 관측 창과 초기 학습 상태를 함께 적어야 한다.

두 분기 주소 A/B가 한 카운터 칸을 공유하는 자체 변형을 보자. A는 언제나 T, B는 언제나 N이며 순서는 A,B,A,B다. 초기 상태 1에서 공유하면 1↔2로 번갈아 바뀌어 네 번 모두 틀린다. 각각 별도 카운터를 초기 1로 두면 A의 첫 예측만 틀린다. 주소별 패턴이 단순해도 표의 충돌이 결과를 바꿀 수 있다. 실제 제품 예측기 구성이나 측정은 아니다.

예측으로 실행 경로 늘리기

분기는 다음에 가져올 명령 주소를 바꾼다. 결과를 기다리면 front-end가 멈추므로 CPU는 방향·목표를 예측해 가져오기를 이어 갈 수 있다. 맞으면 독립 작업을 일찍 준비하고 틀리면 잘못된 경로를 버리고 올바른 경로로 다시 시작한다. 예측기는 데이터와 과거 행동을 이용하지만 모든 입력을 완벽히 예측하지 못한다.

비율과 추가 cycle

단순 비용 모형은 CPI=기본CPI+명령당분기비율×오예측률×회당추가penalty다. penalty는 이 모형에서 기본비용에 더해지는cycle로 정의하고, 서로 겹치는 다른 stall은 없다고 가정한다. 실제 CPU에서는 overlap·fetch 대역·cache와 predictor 구성 때문에 이 선형식이 정확한 실측을 대신하지 못한다.

속도와 내부 효과의 경계

틀린 경로는 architectural 결과로 commit하지 않아도 cache 접근 등 내부 효과가 남을 수 있다. 따라서 성능 모델의 flush를 보안상 모든 흔적 삭제라고 해석하지 않는다. 무작위 데이터 분기·짧은 관측 창·패턴 변경에서는 정확도가 낮아질 수 있다. 분기 없는 계산으로 바꾸는 방법도 필요 없는 일을 추가할 수 있어 실행 시간과 기능을 함께 검증해야 한다.

다른 문제에 적용하기

값 준비·확정·이름 회수·예측 충돌

지연 3/시작 간격 1 장치의 독립 네 작업과 네 작업 사슬의 마지막 완료를 구하라. 본문 I1 LOAD/I2 의존 ADD/I3 독립 ADD에 commit 폭 1·다음 클록 시작 확정 규약을 적용하라. p3/p4 두 빈 이름을 소모한 뒤 I1 commit으로 어느 옛 이름을 회수하고 I2 fault에서 어느 확정 R1 매핑을 보존하는지 적어라. 초기 1의 공유 A(T)/B(N) 카운터와 분리 카운터의 A,B,A,B 오판 수를 비교하라.

힌트 1

결과 준비와 정상 상태 확정을 별도 경계로 적는다.

힌트 2

최신 확정 값의 장소와 예측 갱신 전 상태를 보존한다.

풀이와 답 확인

  1. 독립 연산 네 개의 마지막 완료는 클록 6의 끝이고, 의존 사슬 네 연산의 마지막 완료는 클록 12의 끝이다.

  2. OoO에서 I1은 클록 4의 끝, I2는 클록 5의 끝, I3는 클록 2의 끝에 실행을 완료한다. in-order에서 I1은 클록 4의 끝, I2는 클록 5의 끝, I3는 클록 6의 끝에 완료한다. 명령 순서대로 한 명령씩 확정하면 두 설계 모두 I1·I2·I3를 각각 클록 5·6·7의 시작에 commit한다.

  3. I1을 commit한 뒤 회수 조건을 만족하는 옛 p1을 회수한다. 최신 확정 R1 값의 장소인 p3는 유지한다. I2의 fault에서도 확정한 R1의 매핑은 p3다.

  4. 공유 카운터의 상태는 1과 2 사이를 번갈아 이동하며 네 번 모두 오판한다. 분리한 카운터에서는 A의 첫 예측만 틀려 오판이 한 번이다.

장치의 용량과 실제 준비, 실행과 확정, 값 장소의 수명, 예측기의 표 조건을 함께 설명한다. 자체 종이 모형이며 실제 CPU·예측기·학습자 실험은 미수행이다.

해결한 뒤 점검할 것

  • 독립 입력과 사슬의 완료 경계를 구별한다.

  • issue·완료·commit의 시간을 별도로 적는다.

  • 새 값의 장소를 free로 오인하지 않고 확정 경계로 복구한다.

  • 예측 전에 실제 방향을 쓰지 않으며 공유 조건을 기록한다.
