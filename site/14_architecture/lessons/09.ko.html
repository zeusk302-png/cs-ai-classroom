instruction-level parallelism

명령 사이의 데이터 흐름

instruction-level parallelism, ILP는 한 명령 흐름 안에서 독립 명령들이 겹쳐 실행될 기회를 말한다. 스레드를 여러 개 만드는 것과 다르다. 앞 명령의 결과를 읽는 RAW는 진짜 데이터 의존성이다. 이름만 같은 레지스터를 다시 쓰는 WAR/WAW와 구분해야 어떤 순서를 반드시 지킬지 알 수 있다.

지연과 처리율

latency는 한 연산 시작부터 결과 준비까지의 시간이고 throughput은 단위 시간에 완료할 수 있는 작업량이다. 파이프라인 장치는 결과가3cycle 뒤에 나오더라도 독립 연산을 매cycle 새로 시작할 수 있다. 그러나 같은 결과를 이어 사용하는 연산은 앞 결과가 필요하다. 넓은 실행기라도 의존 사슬의 길이는 없애지 못한다.

작은 계산 그래프

교육 모형에서 두 실행기가 있고 각 연산 지연1cycle, 자원/메모리/분기 지연은 없다고 정하자. A=a+b,B=c+d는 독립이라 같은 cycle에 시작할 수 있고 C=A×B는 둘의 결과가 준비된 다음 cycle에 시작한다. 실제 CPU의 명령 decode·issue·메모리 순서 비용은 이 모형에 들어 있지 않다. 손 계산 값은 실제 장치 속도가 아니라 의존성의 하한을 읽는 예다.

중간 과정을 따라가는 예제

A=a+b,B=c+d,C=A×B,D=C+e의1cycle 연산4개를 두 실행기로 처리한다. 입력은 처음부터 준비되며 결과는 cycle 끝에 나온다.

  1. cycle1 A와 B를 함께 수행한다.

  2. cycle2 C,cycle3 D를 수행한다.

  3. 직렬1실행기에서는4cycle이므로 이상 실행구간 비는4/3이다.

3cycle,4/3배. A/B→C→D의3단계 경로가 하한이다.

소단원 9.2

superscalar·out-of-order

앞의 긴 명령을 기다리는 동안 뒤의 독립 명령을 해도 될까?

준비 개념과 학습 목표

준비 개념

  • clock cycle과 지연

학습 목표

  • 폭과 순서는 다른 축 설명

폭과 순서는 다른 축

superscalar는 한 cycle에 여러 명령을 처리할 수 있는 폭을 가진 설계다. out-of-order는 프로그램상 앞 명령이 기다릴 때 준비된 뒤 명령을 먼저 실행하도록 일정을 정하는 방법이다. 넓지만 in-order일 수도 있고 한 번에 하나를 issue하지만 OoO일 수도 있다. 폭이 있어도 같은 실행 port나 데이터 의존 때문에 매번 최대 폭을 채우지는 못한다.

준비된 작업을 고르기

실행 대기 목록의 명령은 입력 값 준비와 기능 장치 사용 가능 조건을 함께 만족해야 한다. 아직 load 결과가 없는 add는 기다리지만 다른 레지스터만 쓰는 add는 앞서 실행할 수 있다. 실제 메모리 명령은 같은 주소의 이전 store와 관계를 추적해야 하므로 레지스터만 보면 독립으로 보이는 것과 다를 수 있다.

관찰되는 순서는 보존

완료 순서와 commit 순서는 다르다. 전형적 OoO는 여러 결과를 임시 보관하고 프로그램 순서대로 retire/commit하여 순차 의미와 예외 복구를 유지한다. 추측이 틀리면 잘못된 경로의 명령은 최종 상태에 반영하지 않는다. 이것은 cache를 포함한 모든 내부 흔적이 없어진다는 뜻은 아니다. 이 단원의 실행 시간표에는 front-end와 commit 지연을 제외한다.

중간 과정을 따라가는 예제

cycle 1에 I1 load가 시작해 cycle 4 끝에 결과가 나온다. I2는 I1 결과의 add, I3는 독립 add다. 두 add는 각각 1 cycle이고 이미 대기 목록에 있다. 두 비교 모형 모두 cycle당 최대 한 명령을 issue하며 load와 add 장치는 겹쳐 작동할 수 있다고 가정한다. 엄격한 in-order issue와 OoO를 비교하라.

  1. in-order에서는 I2가 준비될 때까지 뒤 I3의 시작도 막는다. I2는cycle5, I3는cycle6이다.

  2. OoO는 I3를cycle2에 끝낼 수 있고 I2는cycle5에 끝낸다.

  3. 전체 실행 완료는6 대5cycle이나 I3의 최종commit은 이전 명령 완료를 기다릴 수 있다.

실행 완료6cycle과5cycle. 모든 commit까지의 실제 CPU 시간 측정은 아니다.

종이와 본문으로 직접 해보기

I3도 I1의 load 결과를 읽도록 바꾸면 cycle2 실행이 가능한가?

힌트 보기

입력 준비 조건을 확인한다.

풀이 보기

불가능하다. I3도 cycle 4 끝까지 기다려야 한다. 예제의 issue 폭 1을 그대로 유지하면 I2를 cycle 5, I3를 cycle 6에 시작할 수 있다. 모형을 폭 2 및 충분한 add 장치로 바꾸면 두 add를 cycle 5에 함께 시작할 수 있다.

오해와 반례

OoO는 프로그램의 뜻까지 마음대로 바꾼다.

준비된 독립 계산을 먼저 하는 것이며 필요한 데이터·메모리 순서와 최종 관찰 가능한 의미를 유지해야 한다.

register renaming·retirement

같은 r1 이름을 다시 쓰는 두 계산을 어떻게 서로 다른 값으로 보존할까?

준비 개념과 학습 목표

준비 개념

  • 명령의 입력과 출력

  • clock cycle과 지연

  • 레지스터와 순차 의미

학습 목표

  • 이름과 값의 세대 설명

  • 읽기 대상을 먼저 잡기 설명

  • 확정과 복구 설명

이름과 값의 세대

ISA 레지스터는 프로그램이 부르는 이름이고 물리 레지스터는 내부 저장 장소다. renaming은 각 쓰기에 새 물리 장소를 할당하여 같은 이름의 값 세대를 구분한다. 앞 명령이 읽을 옛 r1과 뒤 명령이 쓸 새 r1을 분리하면 WAR와 WAW의 이름 충돌을 제거할 수 있다. RAW는 새 장소에서도 필요한 생산자 결과를 기다린다.

읽기 대상을 먼저 잡기

명령을 프로그램 순서로 rename하면서 입력은 현재 매핑을 조회하고 목적지는 새 물리 레지스터에 연결한다. r1=r1+1은 입력으로 옛 r1을 잡은 뒤 목적지 매핑을 바꿔야 한다. 실제 프로세서는 free list·대기 태그·준비 비트 등으로 이를 구현한다. 이 단원은 물리 이름 p1,p2를 쓰는 단순 종이 모형이며 특정 제품의 레지스터 개수나 배치라고 주장하지 않는다.

확정과 복구

retirement는 앞 명령부터 결과와 예외를 확정하는 단계다. 아직 확정되지 않은 새 매핑만으로 실패 경로를 최종 상태로 남기면 안 된다. 예외나 분기 실패에 대비해 확정된 상태 또는 checkpoint에서 회복할 정보를 둔다. 옛 물리 저장소는 필요한 읽기와 복구 상태가 끝나기 전에 재사용하면 안 된다. free list가 고갈되면 rename이 멈출 수 있다.

중간 과정을 따라가는 예제

초기 r1→p1(값5),r2→p2(값3). I1:r3=r1+r2; I2:r1=9; I3:r4=r1+r2. 새 목적지는 순서대로p3,p4,p5이다. 입력 태그와 값을 구하라.

  1. I1은p1,p2를 읽고p3에8을 만든다. r3→p3이다.

  2. I2는p4에9를 만들고 r1→p4로 바꾼다. I1은 이미 잡은p1을 계속 읽는다.

  3. I3은p4,p2를 읽고p5에12를 만든다. I2의값이 준비되어야 한다.

I1 입력p1/p2·결과8;I2 목적p4·값9;I3 입력p4/p2·결과12.

종이와 본문으로 직접 해보기

I2를 r1=r1+1로 바꾸면 입력·목적 태그와 I3 결과는?

힌트 보기

I2의읽기는 매핑 변경 전이다.

풀이 보기

I2 입력p1,목적p4이고값6이다. I3은p4/p2로6+3=9다. p4를 자기 입력으로 잘못 잡으면 순환 대기가 된다.

오해와 반례

renaming은 어떤 명령의 대기도 모두 없앤다.

I3은 I2의 실제값을 기다린다. 이름 충돌 해소는 생산자가 아직 만든 적 없는 값을 즉시 준비시키지 않는다.

답과 이유 보기

프로그램 순서의 실패 경계를 보존해야 한다.

한 단계 더

예측으로 실행 경로 늘리기

분기는 다음에 가져올 명령 주소를 바꾼다. 결과를 기다리면 front-end가 멈추므로 CPU는 방향·목표를 예측해 가져오기를 이어 갈 수 있다. 맞으면 독립 작업을 일찍 준비하고 틀리면 잘못된 경로를 버리고 올바른 경로로 다시 시작한다. 예측기는 데이터와 과거 행동을 이용하지만 모든 입력을 완벽히 예측하지 못한다.

비율과 추가 cycle

단순 비용 모형은 CPI=기본CPI+명령당분기비율×오예측률×회당추가penalty다. penalty는 이 모형에서 기본비용에 더해지는cycle로 정의하고, 서로 겹치는 다른 stall은 없다고 가정한다. 실제 CPU에서는 overlap·fetch 대역·cache와 predictor 구성 때문에 이 선형식이 정확한 실측을 대신하지 못한다.

속도와 내부 효과의 경계

틀린 경로는 architectural 결과로 commit하지 않아도 cache 접근 등 내부 효과가 남을 수 있다. 따라서 성능 모델의 flush를 보안상 모든 흔적 삭제라고 해석하지 않는다. 무작위 데이터 분기·짧은 관측 창·패턴 변경에서는 정확도가 낮아질 수 있다. 분기 없는 계산으로 바꾸는 방법도 필요 없는 일을 추가할 수 있어 실행 시간과 기능을 함께 검증해야 한다.

중간 과정을 따라가는 예제

가상1000명령,기본CPI1,분기200개,그중20개 오예측,추가penalty5cycle이다. 총cycle·CPI를 구하라.

  1. 분기율200/1000=.2,오예측률20/200=.1이다.

  2. 추가20×5=100cycle이다.

  3. 총1000+100=1100cycle,CPI1.1이다.

1100cycle,CPI1.1. 자체 비용 모형이며 특정 CPU 측정 아니다.

종이와 본문으로 직접 해보기

분기 수는 같고 오예측을 10개로 줄이면 총 cycle과 이전 대비 속도 비는?

힌트 보기

기본 1000 cycle은 그대로이고 추가 비용만 절반이다.

풀이 보기

추가 비용은 10×5=50 cycle, 총 1050 cycle이다. 이전 시간/새 시간=1100/1050=22/21≈1.048배이며 전체가 두 배 빨라지는 것은 아니다. 두 모형의 clock 주파수는 같다고 가정한다.

오해와 반례

오예측률이 절반이면 프로그램 전체 시간도 절반이다.

기본 비용은 그대로여서 이 예는 1100→1050 cycle뿐이다. penalty, 분기 비율, 다른 병목을 함께 본다.
