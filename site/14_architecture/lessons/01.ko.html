소단원 1.1

ISA·microarchitecture 구별

같은 명령을 이해하는 두 CPU가 서로 다른 속도와 내부 구조를 가져도 될까?

준비 개념과 학습 목표

준비 개념

  • 명령은 값을 다루는 규칙이고 데이터는 그 규칙의 대상이다.2와 3을 더하는 명령을 예로 든다.
  • 비트열은 공유된 규칙에 따라 의미를 가진다. 기계 명령도 인코딩 규칙이 필요하다.
  • 레지스터는 CPU가 명령에서 사용할 값을 보관하는 저장소라는 뜻을 복습한다.

학습 목표

  • ISA의 관찰 가능한 약속과 마이크로아키텍처의 구현 선택을 구별한다.
  • 실제 ISA 명세에 근거한 산술 명령을 종이로 추적한다.
  • ISA 호환성이 전체 프로그램·성능 호환성과 동일하지 않음을 설명한다.

ISA는 명령 실행의 외부 약속

명령어 집합 구조(ISA)는 소프트웨어가 사용할 명령의 인코딩과 의미, 레지스터 등 건축적으로 보이는 상태를 규정하는 인터페이스다. 명령이 어느 비트에 어떤 연산을 지정하는지와 실행 후 무엇이 바뀌는지가 포함된다. CPU가 명령을 몇 단계로 나누어 계산하는지는 보통 같은 규칙의 내부 구현 문제다.

예를 들어 RV32I의 ADD는 두 32비트 레지스터를 더해 결과의 아래 32비트를 목적 레지스터에 쓴다. 일반 산술 오버플로 예외는 만들지 않는다. 이 규칙은 정확한 32비트 비트 결과의 약속이며, 특정 CPU의 클록 수나 C 언어의 signed 연산 계약과는 구별한다. 이후 어셈블리에서는 명령 이름뿐 아니라 이런 세부 의미를 확인한다.

마이크로아키텍처는 약속을 실현하는 조직

마이크로아키텍처는 데이터패스·제어·파이프라인·캐시·실행 장치처럼 ISA를 구현하는 내부 조직이다. 같은 ADD를 한 긴 단계에서 끝내거나 여러 단계로 나누는 구현이 가능하다. 기능적으로 같은 결과를 내더라도 면적·전력·최대 주파수·처리량은 달라질 수 있다. 전기 회로가 실제로 이 약속을 수행하려면 논리 기능과 타이밍도 만족해야 한다.

외부에서 관찰되는 상태를 ISA처럼 유지하는 것이 호환성의 핵심이다. 내부 실행 순서가 달라도 ISA가 요구하는 결과와 메모리 순서·예외 규칙 등을 지켜야 한다. ‘마음대로 순서를 바꾸어도 된다’는 뜻은 아니다. 이 단원에서는 레지스터 산술의 순차 모형으로 출발하고, 복잡한 메모리 모델이나 정확한 예외는 후속 단원에서 다룬다.

실행 파일에는 더 많은 경계가 있다

같은 ISA라고 모든 실행 파일이 바로 동작하는 것은 아니다. 사용하는 ISA 확장, 운영체제, ABI, 파일 형식, 라이브러리 등도 맞아야 한다. ISA는 명령의 의미를 정하고 ABI는 함수 인수·반환·호출 규약 같은 소프트웨어 연결을 정한다. 하드웨어의 명령 호환성만으로 OS 서비스 호환성까지 증명할 수 없다.

성능도 ISA 이름만으로 알 수 없다. 같은 입력과 같은 일을 비교하면서 명령 수, 실제 사이클 수, 메모리 대기를 확인해야 한다. 소스 코드 한 줄과 기계 명령 한 개를 같게 세는 것도 오류다. 컴파일러가 여러 명령으로 번역하거나 상수로 접을 수 있기 때문이다. 이 과목은 하드웨어 조직, 컴퓨터시스템 과목은 번역·ABI·링킹의 프로그래머 관점에 초점을 둔다.

중간 과정을 따라가는 예제

RV32I의 x1=2,x2=3이고 x3의 기존 값은 관심 밖이다. add x3,x1,x2를 한 번 실행한 의미를 종이로 추적한다. 명령 주소·실제 CPU 사이클은 주어지지 않았다.

  1. 명세에서 ADD는 rs1과 rs2의 합 아래 XLEN 비트를 rd에 쓰는 것을 확인한다.
  2. rs1=x1의 2,rs2=x2의 3을 읽는다.
  3. 정확한 합 5는 32비트 안이므로 아래 32비트도 5다.
  4. 목적 x3=5가 된다. x1과x2의 값은 이 명령으로 바뀌지 않는다.

레지스터 결과 x3=5. 이 예는 공식 ISA 의미를 적용한 종이 추적이며 하드웨어·시뮬레이터 실행 관측이 아니다.

종이와 본문으로 직접 해보기

‘ADD의 아래 32비트 결과’, ‘캐시 크기’, ‘파이프라인 단계 수’, ‘함수 인수 전달 규약’을 ISA·마이크로아키텍처·ABI에 분류한다. 이어 x1=0xffffffff,x2=1의 ADD 결과를 비트 수준으로 예측하라.

힌트 보기

32비트 밖으로 넘어간 비트는 ADD 목적 결과에 들어가지 않는다. ISA에 없는 성능 조건을 더하지 않는다.

풀이 보기

순서대로 ISA, 마이크로아키텍처, 마이크로아키텍처, ABI다.0xffffffff+1=0x1_00000000이므로 아래 32비트 결과는 0이다. 이는 명령 의미이며 C의 signed 오버플로 일반 규칙을 추론하는 근거가 아니다.

오해와 반례

ISA가 같으면 내부 회로와 속도도 같고 모든 실행 파일이 호환된다.

같은 산술 결과를 내는 두 CPU도 캐시와 파이프라인이 달라 속도가 다를 수 있다. OS/ABI/확장 조건이 다른 실행 파일은 ISA 기반이 같아도 바로 실행되지 않을 수 있다. 호환성은 어느 경계의 약속을 비교하는지 명시해야 한다.

소단원 1.2

CPU 시간·CPI·클록

3GHz라는 숫자만 보면 2GHz보다 반드시 빠르다고 말할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 단위 관계 1GHz=10^9사이클/초를 읽는다.
  • 평균을 합/개수로 계산한다. 가중 평균은 항목 수가 다른 묶음을 합칠 때 쓴다.
  • 명령 개수·클록 사이클 수·시간을 다른 양으로 구별한다.

학습 목표

  • CPU 시간식을 차원으로 유도하고 단위를 검산한다.
  • 동적 명령 수와 평균 CPI를 정의한다.
  • 명령 혼합에 따른 가중 CPI와 두 CPU의 시간을 비교한다.

실행된 명령과 사용한 사이클

동적 명령 수 N은 특정 작업을 수행하며 실제로 실행한 명령의 수다. 프로그램에 적힌 서로 다른 명령 줄 수인 정적 개수와 다르다. 루프 안의 한 명령을 100번 실행하면 동적 개수에는 100이 들어간다. 어떤 카운터가 명령을 세는지, 취소된 추측 실행을 포함하는지 등 측정 정의도 정해야 한다. 이 단원은 완료된 명령과 그 작업에 대응하는 실행 사이클을 세는 모형이다.

평균 CPI는 총 사이클 수 C를 N으로 나눈 C/N이다. CPI는 명령마다 반드시 정수인 고정 지연이 아니라 이 작업 전체의 비율일 수 있다. 여러 명령을 겹쳐 완료하는 기계에서는 CPI가 1보다 작을 수 있다. 메모리나 분기 대기는 작업의 총 사이클에 반영되므로, 평균 CPI는 입력·명령 혼합·구현에 따라 바뀐다.

시간식과 차원 유도

N>0, f>0을 가정한다. 클록 주파수 f가 해당 실행 구간에서 일정하다면 주기τ=1/f이고 CPU 실행 시간 T=C/f다. CPI=C/N을 대입하면 T=N×CPI/f=N×CPI×τ다. 명령×(사이클/명령)/(사이클/초)=초가 되어 단위가 맞는다. 주파수와 주기를 뒤집지 않는 것이 중요하다.2GHz의 주기는 0.5ns다.

여기서 CPU 실행 시간의 모형은 I/O나 스케줄 대기를 포함한 모든 벽시계 시간과 같지 않다. 실제 도구의 사용자/커널 CPU 시간과 하드웨어 카운터 범위를 맞추어야 한다. 주파수가 실행 중 달라지거나 카운터가 다른 기준 클록을 사용하면 하나의 고정 f를 기계적으로 넣을 수 없다. 모형 입력인지 관측된 수치인지 표시한다.

CPI를 합칠 때는 명령 수로 가중하기

서로 겹치지 않는 비용을 각 종류의 명령에 배정한 단순 모형에서는 총 사이클=Σ Ni×CPIi이고 평균 CPI=Σ(Ni/N)×CPIi다.80개가 1사이클,20개가 4사이클이면 총 160사이클, 평균 1.6이다. 두 종류 CPI의 단순평균 2.5는 개수가 같지 않으므로 틀리다.

현대 파이프라인의 상호작용 비용을 각 종류에 깔끔히 분해하는 일은 쉽지 않다. 이 식은 가상 비용표의 계산이거나 정의가 맞는 계수 분석에 사용한다. 한 CPU의 단일 프로그램 CPI를 다른 입력·다른 CPU에서도 상수처럼 사용하지 않는다. 더 높은 주파수가 CPI 증가나 명령 수 차이로 상쇄되는지를 함께 비교한다.

중간 과정을 따라가는 예제

같은 작업의 동적 명령 수가 10^9개라고 가정한다. A는 평균 CPI 2, 2GHz이고 B는 평균 CPI 3, 3GHz다. 주파수는 일정하고 명령·사이클 정의가 같다.

  1. A 사이클 수=10^9×2=2×10^9.
  2. A 시간=(2×10^9)/(2×10^9사이클/초)=1초.
  3. B 사이클 수=10^9×3=3×10^9.
  4. B 시간=(3×10^9)/(3×10^9)=1초. 주기는 A0.5ns,B약 0.333ns다.

두 모형의 CPU 시간은 1초로 같다.3GHz가 더 높은 숫자라는 사실만으로 전체 속도를 판단할 수 없다.

종이와 본문으로 직접 해보기

100개 명령 중 80개 비용 1사이클,20개 비용 4사이클이라는 가상 순차 비용표를 만든다. 총 사이클·평균CPI·100MHz에서의 시간을 계산한다.

힌트 보기

종류 수가 아니라 명령 개수로 가중한다.1MHz=10^6사이클/초다.

풀이 보기

총 80×1+20×4=160사이클, 평균 160/100=1.6, 시간 160/(100×10^6)=1.6×10^-6초=1.6μs다. 실제CPU의 병렬 실행을 이 가상 개별 비용표로 관찰한 것은 아니다.

오해와 반례

클록 주파수가 1.5배이면 어떤 작업도 1.5배 빨라지고 CPI는 언제나 1이상이다.

예제의B는 주파수가 1.5배지만 CPI도 1.5배라 시간이 같다. 겹쳐서 명령을 완료하는 구현에서는 100사이클 동안 200명령을 완료하면 평균CPI0.5가 가능하다. 입력과 기계의 실행 조직을 고정해야 비교할 수 있다.

소단원 1.3

latency·throughput

공장에서 제품 하나는 60분 걸리는데 20분마다 제품이 나오는 일이 가능할까?

준비 개념과 학습 목표

준비 개념

  • 경과 시간과 단위 시간당 개수는 다른 양이다.
  • 여러 작업의 단계가 겹칠 수 있음을 시간표로 그린다.
  • 클록 주기가 한 사이클의 길이라는 것을 복습한다.

학습 목표

  • 한 작업의 지연과 정상 상태의 처리량을 구별한다.
  • 이상적 파이프라인의 시간표와 유한 작업의 완료 시간을 계산한다.
  • 병목·빈칸·오버헤드가 가정에 미치는 영향을 설명한다.

한 작업을 따라가는 질문과 전체 흐름의 질문

latency는 한 입력이 들어온 뒤 그 결과가 나올 때까지의 지연시간이다. throughput은 정한 관찰 구간의 완료 작업 수/시간이다. 같은 시스템에서도 한 작업을 빨리 끝내는 목표와 많은 작업을 끝내는 목표가 다를 수 있다. 서버의 한 요청 지연과 초당 완료 요청 수 역시 같은 지표가 아니다.

처리량이 지연의 역수인 것은 모든 작업을 하나씩 끝낸 뒤 다음 작업을 시작하는 등의 특별한 조건에서다. 작업을 겹치거나 병렬 장치를 쓰면 하나의 작업은 오래 걸려도 완료 간격이 짧아질 수 있다. 따라서 1/latency를 항상 처리량이라고 쓰면 안 된다. 유한 관찰 구간에는 시작 준비와 마지막 완료도 포함될 수 있다.

이상적 파이프라인의 계산

서로 다른 3단계가 각 1사이클을 사용하고 매사이클 새 작업을 받을 수 있는 가상 파이프라인을 정하자. 단계 간 저장과 모든 타이밍 비용을 포함한 클록 주기를 2ns로 가정한다. 작업 하나는 3사이클, 즉 6ns가 걸린다. 충분히 채워진 뒤에는 매 2ns마다 결과 하나가 나와 처리량 0.5개/ns다.

처음 비어 있을 때 N≥1개를 연속으로 넣으면 마지막 결과는(N+3-1)사이클에 나온다. 첫 결과까지 3사이클, 나머지N-1개는 한사이클씩 더 기다리기 때문이다. N=4이면 6사이클=12ns다. 전체 구간 평균 4/12개/ns와 정상 처리량 1/2개/ns는 같지 않다. 시작·끝 효과를 구분해야 한다.

더 많은 단계가 항상 더 좋은가

파이프라인 주기는 가장 느린 단계와 레지스터·설정 시간 등 오버헤드가 제한한다. 단계들이 2,3,1ns 걸리는데 한 클록으로 맞추려면 가장 긴 3ns만 봐도 하한이다. 실제 저장·클록 조건을 더해야 하므로 단순합 6ns를 3으로 나눈 2ns로 정할 수 없다. 작업 간 의존·자원 경쟁·분기 때문에 빈 사이클이 생기면 정상 처리량도 낮아진다.

지연과 처리량은 사용자의 목적에 따라 함께 평가한다. 한 번 결과를 기다리는 작업과 수백 개 입력을 이어 보내는 작업의 이득은 다를 수 있다. 이 첫 단원은 이상적 파이프라인 모형의 구별을 배우며 실제 CPU 해저드와 캐시는 후속 단원에서 분석한다. 공장 비유는 시간표를 돕지만 모든 CPU 명령이 동일한 고정 단계 시간을 갖는다는 주장으로 확장하지 않는다.

중간 과정을 따라가는 예제

3단계·주기 2ns·빈칸 없음인 가상 파이프라인에A,B,C,D를 시작부터 매사이클 한 개씩 넣는다. 시작은 t=0이다.

  1. 사이클 1[0,2): A단계 1. 사이클 2[2,4): A단계 2,B단계 1.
  2. 사이클 3[4,6): A단계 3,B단계 2,C단계 1. t=6ns에A완료.
  3. 사이클 4에B완료(t=8ns),사이클 5에C완료(t=10ns).
  4. 사이클 6에D완료(t=12ns). 각 작업 자체의 파이프라인 지연은 6ns다.

첫 결과 6ns, 마지막 12ns, 정상 완료 간격 2ns.4개 전체 평균 처리량은 4/12=1/3개/ns다.

오해와 반례

단계를 3개로 나누면 한 작업의 latency가 반드시 3분의 1이 된다.

한 작업은 여전히 모든 단계를 거친다. 이 가상 모형에서 6ns 지연은 매 2ns마다 결과를 내는 처리량과 공존한다. 단계 저장 오버헤드 때문에 지연은 늘 수도 있다. 파이프라인은 주로 여러 작업의 중첩을 통한 완료 간격을 개선한다.

소단원 1.4

Amdahl 법칙과 측정

프로그램의 일부를 무한히 빠르게 해도 전체 시간은 0이 될 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 부분 시간을 더하면 전체가 되는 순차 모형을 읽는다.
  • 비율p=부분/전체와 배속=이전시간/새시간을 계산한다.
  • 가상 수치의 예측과 실제 측정값을 구별한다.

학습 목표

  • Amdahl 식을 고정 작업량의 부분 시간에서 유도한다.
  • 개선 상한과 오버헤드가 있는 경우를 계산한다.
  • 동등한 결과와 통제 조건을 갖춘 측정 기록을 설계한다.

부분 개선의 배속을 유도하기

기존 시간 T>0 중 개선할 부분의 비율p를 0≤p≤1로 두고 그 부분의 속도를 s배로 바꾼다(s>0). 개선되지 않는 부분은(1-p)T, 개선 부분은pT/s이므로 새 시간은T((1-p)+p/s)다. 따라서 전체 배속S=1/((1-p)+p/s). 이 유도는 같은 작업량, 겹치지 않는 시간 분할, 다른 부분 비용 불변이라는 조건을 쓴다.

p는 개선 뒤가 아니라 기존 시간에서의 비율이다. p<1일 때 s를 크게 해도 남는(1-p)T 때문에 배속 상한은 1/(1-p)다. p=0이면 어떤 개선도 영향이 없고,p=1이면 이상적으로 전체가s배가 된다. 법칙은 임의 하드웨어에 모든 전제를 자동으로 보장하는 명령이 아니라 전제가 맞는 비용 모델의 결과다.

병렬화의 비용과 고정 문제의 조건

병렬 가능한 부분이p이고 n개 자원에서 이상적으로n배 빠르다고 두면s=n이다. 하지만 작업 분배·동기화·통신·자원 경쟁 비용을 추가해야 할 수 있다. 새 오버헤드가hT면 배속 분모에h를 더한다. 더 많은 코어가 항상 더 빠르다는 주장은 이 비용이 없거나 충분히 작은 경우에만 따라온다.

입력 크기를 늘려 코어를 더 활용하는 실험은 고정 작업량 비교와 다르다. 같은 식의p를 그대로 사용하면 질문을 섞는다. 또 캐시 변화로 개선하지 않은 부분의 비용까지 달라지면 단순모형과 실제 결과의 차이를 조사해야 한다. 모델과 다르다는 관찰을 감추지 않고 어느 전제가 달라졌는지 기록한다.

측정이 뒷받침해야 할 것

먼저 두 구현이 같은 입력에서 같은 명세의 결과를 내는지 확인한다. 일을 생략해 빨라졌다면 같은 작업의 개선이 아니다. 다음으로 하드웨어·OS·컴파일러·옵션·입력·스레드 수·캐시 준비 정책·시계와 구간을 적는다. CPU 시간과 벽시계 시간 중 목표에 맞는 지표를 정하고 여러 번 측정해 분포와 대표값을 보고한다.

가장 좋은 한 번만 비교하거나 한쪽만 준비 실행을 하면 결과가 편향될 수 있다. 평균과 중앙값은 다른 특성을 말하므로 반복값도 보관한다. 관측값·계산된배속·가정한분할을 각각 표시하면 재현 가능한 주장인지 검토할 수 있다. 이 단원의 표는 직접 만든 수치이며 실제 벤치마크 수행을 뜻하지 않는다.

중간 과정을 따라가는 예제

가상 작업은 기존 100ms이고 개선 부분 60ms다. 그 부분만 4배 빠르게 하고 나머지 40ms는 그대로다. 새 오버헤드는 우선 0이다.

  1. p=60/100=0.6,s=4.
  2. 개선부분=60/4=15ms,전체=40+15=55ms.
  3. 배속=100/55=20/11≈1.818.
  4. 무한히 빠른 부분의 한계는 40ms,상한 100/40=2.5배.
  5. 새 오버헤드 5ms가 생기면 전체 60ms,배속 100/60=5/3≈1.667이다.

4배 부분 개선은 전체 약 1.82배다. 5ms 오버헤드를 넣으면 약 1.67배이며, 수치는 가상 비용표의 계산이다.

종이와 본문으로 직접 해보기

p=0.9인 가상 고정 작업을 8코어에서 개선부분만 8배 빠르게 한다. 전체 배속과 무한 코어 한계를 구하라. 처리 결과가 기존과 다른데 시간이 줄었으면 같은 성능 개선이라고 보고할지도 적어라.

힌트 보기

분모(1-p)+p/8을 계산한다. 비교 전에 작업 명세가 같아야 한다.

풀이 보기

분모 0.1+0.9/8=0.2125,배속 80/17≈4.706. 무한한계 10배. 결과가 명세를 어기면 동일 작업의 올바른 성능 개선이 아니므로 정확성 실패와 시간 관측을 분리한다.

오해와 반례

코어 8개면 어떤 고정 프로그램도 8배 빠르고, 한 번 빨랐으면 개선이 확정된다.

p=0.9의 이상모형도약 4.71배이며 순차부분이 남는다. 실제는 오버헤드도 있다. 한 번의 값은 잡음·캐시·다른 작업 영향을 받으므로 반복과 조건 통제가 필요하다. 학습용 계산은 벤치마크 실행 검증과 구별한다.

자기점검

답과 이유 보기
