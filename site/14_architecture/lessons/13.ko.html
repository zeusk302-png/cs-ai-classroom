소단원 13.1

memory-mapped I/O

메모리 주소에 숫자를 쓰는 일이 어떻게 장치를 움직일까?

준비 개념과 학습 목표

준비 개념

  • 주소와 바이트

  • 비트 마스크

  • 읽기·쓰기

학습 목표

  • MMIO 주소와 RAM을 구별한다.

  • 레지스터의 폭·역할·부작용을 읽는다.

  • 쓰기 명령과 장치 완료를 구별한다.

주소가 가리키는 대상부터 확인하기

MMIO는 주소 공간의 일부를 장치 인터페이스로 해석한다. 같은 load/store 형태라도 RAM처럼 저장값을 되돌려 주는 계약은 아닐 수 있다. 실제 접근에는 운영체제의 매핑·전용 접근자와 장치 설명이 필요하다.

이 단원의 주소는 종이 모형이다. 숫자를 실제 포인터로 만들어 실행하지 않는다. 주소 표에서 대상·폭·허용 방향·읽기/쓰기 효과를 각각 찾아야 한다.

상태와 명령의 계약

가상 상태 비트 0은 준비, 비트 1은 오류라고 정의하자. 값 3이면 두 비트가 함께 켜졌다. 준비가 참이어도 오류가 있으므로 성공 조건에는 오류가 없다는 검사도 포함한다.

명령 레지스터에 시작을 쓰면 일을 요청한다. 완료까지 필요한 시간과 결과 상태는 별도 사건이다. 아래 예제의 비트 뜻은 실제 제품에 적용하지 않는다.

같은 주소를 두 번 읽는 경우

가상의 데이터 레지스터가 읽을 때 큐의 앞 값을 꺼내면 두 번 읽기의 결과가 다를 수 있다. 값을 확인하려고 한 추가 읽기가 실제 자료를 소비할 수 있으므로 관찰 자체의 부작용을 확인한다.

Linux 접근자의 폭·순서와 posted 쓰기 완료는 별도 계약이다. 실제 장치에서 같은 장치의 읽기로 쓰기를 확인하는 경우가 있어도 모든 주소를 안전한 확인용으로 선택할 수는 없다.

중간 과정을 따라가는 예제

자체 장치의 기준 주소는 0x8000이고 32비트 레지스터 STATUS/DATA/CMD의 오프셋은 0/4/8이다. STATUS=3, DATA의 큐는 [11,22], DATA 읽기는 앞 값을 소비한다. 주소와 안전한 관찰 순서를 계산하자.

  1. 세 주소는 0x8000/0x8004/0x8008이며 각각 4바이트 정렬이다.

  2. STATUS & 1=1, STATUS & 2=2다. 준비와 오류가 모두 표시되어 이 가상 성공 조건을 만족하지 않는다.

  3. DATA를 두 번 읽으면 11,22를 얻고 큐가 비어 버린다. 로그용 읽기도 소비한다는 계약을 빠뜨리면 안 된다.

  4. 오류 처리 후 시작 여부를 정해야 한다. CMD 쓰기 한 번으로 완료를 관찰했다고 보고하지 않는다.

상태 3은 준비와 오류의 동시 표시다. 주소·폭·부작용·완료 조건을 함께 읽는다.

종이와 본문으로 직접 해보기

기준 주소를 0x9000으로 바꾸고 STATUS=1, DATA=[7,9]라 하자. DATA/CMD 주소와 두 DATA 읽기의 결과는? STATUS를 읽는 것과 DATA를 읽는 것이 같은가?

힌트 보기

오프셋은 그대로 더한다. DATA만 큐 소비 효과가 있다고 정의했다.

풀이 보기

DATA=0x9004, CMD=0x9008이다. DATA 결과는 7 다음 9이고 큐는 빈다. STATUS의 읽기는 이 가상 계약에서 소비하지 않으므로 DATA 읽기로 바꾸면 안 된다.

오해와 반례

MMIO 값은 일반 변수처럼 원하는 만큼 읽어도 같은 효과다.

장치 레지스터는 읽기에도 상태 변화가 있을 수 있다. 폭·역할·부작용을 설명서로 확인한다.

읽기가 큐 앞 값을 소비한다.

소단원 13.2

polling·interrupt

준비됐는지 계속 물을까, 준비되면 알려 달라고 할까?

준비 개념과 학습 목표

준비 개념

  • 시간 구간

  • CPU 작업과 대기

  • 상태 검사

학습 목표

  • polling과 interrupt의 알림 경로를 구별한다.

  • 관찰 지연과 CPU 검사 비용을 계산한다.

  • 고정 비용 모형의 한계를 설명한다.

물어보는 방식과 알림 방식

Polling은 소프트웨어가 상태를 반복 확인하는 방식이다. Interrupt는 사건을 알리는 신호에 따라 처리 경로로 들어가는 방식이다. 완료 알림 뒤에도 상태·오류 확인과 필요한 처리가 남는다.

알림 방식과 자료 전송 방식은 다른 축이다. 인터럽트를 사용하면서 CPU가 자료를 복사할 수도 있고, DMA 완료를 polling할 수도 있다.

우리 시간표의 가정

검사를 t=0,2,4,… ms의 점에서 하고 검사 비용을 별도 CPU 사용량으로 합산하는 가상 모형을 정하자. 점검을 실제 길이를 가진 일정으로 다시 배치하지 않는 단순화다. 준비 시점이 두 점검 사이면 다음 점검에서 발견한다.

검사 한 번의 비용이 작아도 많은 검사를 합치면 커진다. 인터럽트도 처리 비용이 있으므로 빠른 장치에서 무조건 더 효율적이라는 결론을 내리지 않는다.

어떤 지연을 보고하는가

준비까지 시간, 준비 이후 발견 지연, 처리 완료 시각을 분리한다. 이 예제는 발견까지를 먼저 계산하고 데이터 후처리는 포함하지 않는다.

사건을 모아 알리는 방법은 알림 수를 줄이지만 먼저 끝난 작업을 더 기다리게 할 수 있다. 실제 선택에는 CPU 부하·요청률·지연 목표와 플랫폼 동작을 확인해야 한다.

중간 과정을 따라가는 예제

가상 장치가 t=7 ms에 준비된다. Polling은 t=0,2,4,6,8에 검사하며 한 번당 CPU 0.1 ms다. 인터럽트는 준비 후 알림 지연 0.2 ms, 처리 비용 0.4 ms라고 별도 정의한다. 비용과 시각을 비교하자.

  1. Polling은 t=8에서 처음 준비를 발견한다. 다섯 검사 CPU 비용은 0.5 ms, 준비 뒤 발견 지연은 1 ms다.

  2. 인터럽트는 t=7.2에 전달되고 처리 완료는 t=7.6이다. 지정한 CPU 처리 비용은 0.4 ms다.

  3. 8은 polling 발견 시각, 7.6은 인터럽트 처리 완료 시각이라 같은 단계 지표는 아니다. Polling 후처리 비용은 표에 없다고 표시한다.

  4. 비용 차이 0.1 ms는 이 가상 상수에서만 성립하며 실제 장치 측정 결과가 아니다.

두 방식의 단계와 CPU 비용을 별도로 보고한다. 같은 단계가 아닌 시각을 빠르기 순위로 단정하지 않는다.

종이와 본문으로 직접 해보기

별도 사건이 t=0.05에 준비된다. t=0과 t=0.1에 polling하고 한 번당 0.02 ms, 인터럽트 비용은 그대로 0.4 ms라고 하자. 발견 지연과 polling CPU 비용은? 이 표만으로 어느 방식의 실제 전체 시간이 짧은가?

힌트 보기

두 검사를 합산하되 준비 이후 지연은 0.1−0.05다.

풀이 보기

Polling CPU 비용은 0.04 ms, 발견 지연은 0.05 ms다. 인터럽트보다 이 모형의 CPU 비용은 낮지만 polling 후처리·스케줄링 전체 조건이 없어 실제 전체 시간 우열은 확정하지 않는다.

오해와 반례

인터럽트는 공짜라서 언제나 polling보다 좋다.

두 방식 모두 비용과 지연 조건이 있다. 짧은 작업의 가상 반례는 polling 검사 비용이 더 작을 수 있음을 보여 준다.

소단원 13.3

DMA와 버스

자료를 옮기는 동안 CPU는 다른 일을 할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 바이트와 전송률

  • CPU 주소

  • 설정과 완료

학습 목표

  • PIO와 DMA의 전송 주체를 구별한다.

  • 주소 매핑과 전송 비용을 분리한다.

  • 공유 버스와 작은 전송의 비용 반례를 계산한다.

전송을 맡기는 의미

DMA는 자료 이동을 DMA 엔진에 맡기는 방식이다. CPU는 설정과 완료 처리에 여전히 참여한다. 자료를 옮기는 CPU 작업이 줄어도 총 지연이 항상 줄어드는 것은 아니다.

버스와 메모리 자원은 공유될 수 있다. 다른 작업과 겹치는 정도를 확인하지 않고 DMA가 CPU 성능에 영향이 없다고 주장하지 않는다.

주소를 그대로 복사하지 않는다

CPU 가상 주소·물리 주소·장치의 DMA 주소는 구별한다. 매핑이 필요한 환경에서 CPU 포인터 숫자를 장치에 그대로 전달하면 원하는 버퍼가 아닐 수 있다.

Linux DMA API에는 방향·주소 범위·매핑 실패와 수명 조건이 있다. 아래 주소 연결은 자체 표이며 실제 매핑 호출 결과는 아니다.

비용 모형의 포함 범위

전송 바이트 수를 전송률로 나누면 모형의 이동 시간이 나온다. 설정·완료 비용, 공유 병목과 겹침 조건을 함께 적는다.

아래는 모든 단계를 직렬 합산하는 가정이다. 실제 비동기 겹침·추가 캐시 작업·할당·입출력 장치 내부 시간은 포함하지 않았으므로 실제 속도 보장으로 쓰지 않는다.

중간 과정을 따라가는 예제

자체 버퍼 4,096 B를 전송한다. PIO는 4 B당 CPU 0.02 μs가 들며 설정/완료 추가 비용은 이 모형에서 0이다. DMA는 CPU 설정 3 μs·완료 처리 1 μs, 전송률 512 B/μs다. CPU 가상 0x4000→물리 0xA000→DMA 0x2000이라는 매핑 표도 주어진다.

  1. PIO 전송은 4,096/4=1,024개이고 CPU 비용은 20.48 μs다. 직렬 모형에서 총 시간도 20.48 μs로 가정했다.

  2. DMA 이동은 4,096/512=8 μs다. CPU 비용은 3+1=4 μs이고 직렬 총 시간은 3+8+1=12 μs다.

  3. 장치에는 매핑 표의 DMA 주소 0x2000을 전달한다. CPU 가상 0x4000을 그대로 전달하지 않는다.

  4. CPU 비용 감소와 총 시간 감소는 별도 계산이다. 실제 시스템에서 이 값과 겹침 조건을 측정하지 않았다.

이 모형의 CPU 비용은 20.48 대 4 μs, 직렬 총 시간은 20.48 대 12 μs다. 장치는 DMA 주소를 사용한다.

종이와 본문으로 직접 해보기

같은 가정으로 64 B만 전송하면? 별도로 큰 전송의 버스를 다른 일이 절반씩 사용하여 DMA 유효 전송률을 256 B/μs로 정하면 4,096 B의 총 시간은?

힌트 보기

작은 전송은 PIO 16개, DMA 이동 64/512다. 공유 버스의 속도는 새 가정이다.

풀이 보기

64 B의 PIO CPU/총 시간은 16×0.02=0.32 μs이고 DMA CPU 4 μs·총 4.125 μs다. 작은 전송에서는 설정 비용이 지배한다. 별도 공유 버스 모형의 큰 전송은 이동 16 μs·총 20 μs다.

오해와 반례

DMA는 CPU가 전혀 관여하지 않으며 어떤 크기에서나 빠르다.

설정·완료 비용이 있고 작은 64 B 반례는 이 모형의 DMA 총 시간이 더 크다. 공유 전송 자원도 확인한다.

자기점검

매핑 표에서 장치에 줄 주소는?

답과 이유 보기

0x2000이다.

그 값이 지정된 DMA 주소다.

DMA CPU 비용은 12 μs인가?

답과 이유 보기

아니다. 4 μs다.

12에는 장치 이동 시간 8이 포함된다.

CPU 주소와 DMA 주소는 언제나 같은가?

답과 이유 보기

아니다.

플랫폼 매핑에 따라 다를 수 있다.

한 단계 더

가상 DMA 매핑 실패 상태를 추가해 시작하지 않음/대체 전송/오류 보고의 가능한 분기를 작성하자. 주소 반환값이 있다고 실패 검사 없이 시작하는 경로를 성공으로 표시하지 않는다.

소단원 13.4

장치·CPU의 동기화

완료 비트를 봤는데 왜 옛 자료가 보일 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 캐시와 메모리

  • 순서와 소유권

  • 완료 확인

학습 목표

  • 캐시 가시성·순서·소유권을 구별한다.

  • 버퍼의 인계와 재사용 상태를 추적한다.

  • coherent도 순서 계약이 필요함을 설명한다.

누가 버퍼를 사용하는가

CPU 소유일 때 내용을 준비하고, 장치로 인계한 뒤에는 장치 소유로 둔다. 완료를 확인하고 필요한 동기화 뒤 CPU가 다시 읽는다. 버퍼 수명과 사용 주체를 사건표로 추적하자.

매핑을 유지한 streaming 버퍼를 다시 사용할 때 Linux API의 CPU/장치 동기화 단계가 필요할 수 있다. 실제 방향·플랫폼 계약을 확인해야 하며 아래 표는 호출 처방이 아니다.

가시성과 순서의 차이

CPU가 쓴 새 내용이 장치에서 보이는가와, 데이터 준비가 유효 표시보다 먼저 보이는가는 다른 질문이다. Coherent 메모리도 필요한 순서 보장을 자동으로 모두 제공하는 것은 아니다.

가상 기술자가 버퍼 주소를 쓰고 나서 유효를 표시하려 한다. 장치가 유효부터 보고 옛 주소를 읽는 순서를 허용하면 잘못된 전송이 시작될 수 있다. 실제 플랫폼의 적절한 barrier와 접근 계약을 사용한다.

완료와 재사용을 따로 확인하기

완료 신호가 나타나도 실패 상태·전송 범위와 읽기 가시성을 확인해야 한다. 사용이 끝나기 전에 버퍼를 해제하거나 다른 요청으로 덮어쓰는 상태를 정상으로 취급하지 않는다.

종이 상태표는 문제 원인을 설명할 수 있지만 특정 장치에서 캐시 동작이나 메모리 순서를 실험한 증거가 아니다. 실제 장치 검증에는 드라이버/하드웨어 계약이 필요하다.

중간 과정을 따라가는 예제

가상 수신 버퍼에서 CPU 캐시는 [2,2], 장치가 접근하는 메모리는 [2,2]다. CPU가 장치에 인계하고 장치가 [7,9]를 쓴 뒤 완료를 표시했다. 이 비일관 캐시 모형에서 CPU용 동기화 전 읽기는 캐시를 사용하고, 동기화 후에는 새 값을 읽는다고 정의한다.

  1. 인계 뒤 장치 소유 동안 CPU가 버퍼를 덮어쓰지 않는다.

  2. 장치 완료 때 메모리는 [7,9]지만 가정한 CPU 캐시는 [2,2]라 이전 읽기 합은 4다.

  3. 완료 확인과 CPU용 동기화 뒤 [7,9]의 합은 16이다. 이것은 가시성 변화의 자체 모형이다.

  4. CPU 읽기가 끝난 뒤 필요한 장치 인계 단계를 거쳐 재사용한다. 완료 전에 해제하는 사건은 허용하지 않는다.

완료·가시성·소유권은 각각 확인한다. 가상 합은 동기화 전 4, 후 16이며 실제 캐시 실측이 아니다.

종이와 본문으로 직접 해보기

별도 coherent 기술자의 이전 주소는 100, 새 주소는 200이고 valid는 0이다. 주소 200 기록 A와 valid=1 기록 V를 하려 한다. 장치 관찰 V→이전 주소 100과 A→V→새 주소 200의 차이는? CPU/장치 동기화로 장치가 반드시 완료되는가?

힌트 보기

순서와 완료는 별도다. 유효 표시가 새 주소 준비보다 먼저 보이는 경우를 추적한다.

풀이 보기

V가 먼저 보이면 장치가 이전 주소 100을 사용할 수 있다. 새 주소 A가 먼저 보이고 그 뒤 V를 보도록 계약하면 지정한 200을 사용할 수 있다. 동기화 단계만으로 미완료 전송이 완료되는 것은 아니며 완료 사건을 따로 확인한다.

오해와 반례

coherent 메모리에서는 유효 비트를 먼저 써도 모든 순서와 버퍼 수명이 자동으로 맞는다.

캐시 가시성의 보장과 필드 순서·완료·버퍼 소유권은 별도다. 적절한 순서와 수명 계약을 유지한다.

자기점검

가상 동기화 전 합은 16인가?

답과 이유 보기

아니다. 4다.

CPU가 옛 캐시 [2,2]를 읽는다고 정의했다.

장치가 사용하는 중 CPU가 버퍼를 해제해도 되는가?

답과 이유 보기

안 된다.

전송 대상 수명이 유지되어야 한다.

CPU용 동기화가 완료 대기를 대신하는가?

답과 이유 보기

아니다.

전송 완료와 가시성 인계는 다른 단계다.

CPU 소유→장치 인계→장치 소유→완료 확인→CPU용 동기화→CPU 읽기라는 여섯 상태를 카드로 그리자. 완료 전 읽기·해제·동시 덮어쓰기 반례를 각각 끼워 넣고 위반 이유를 적는다.
