소단원 13.1

memory-mapped I/O

메모리 주소에 숫자를 쓰는 일이 어떻게 장치를 움직일까?

준비 개념과 학습 목표

준비 개념

  • 주소와 바이트

  • 비트 마스크

  • 읽기·쓰기

학습 목표

  • MMIO 주소와 RAM을 구별한다.

  • 레지스터의 폭·역할·부작용을 읽는다.

  • 쓰기 명령과 장치 완료를 구별한다.

장치 상태를 지우는 쓰기는 일반 변수의 대입과 같을까?

자체 장치의 32비트 STATUS는 bit 0이 완료, bit 1이 오류다. 이 레지스터는 읽기만으로 상태를 바꾸지 않는다. 쓰기는 write-one-to-clear, 즉 1을 쓴 비트의 현재 상태만 지우고 0을 쓴 비트는 유지한다고 별도로 정의한다. 실제 제품의 레지스터 의미가 아니다.

현재 STATUS가 3이면 완료와 오류가 모두 있다. 완료만 확인 처리하려면 마스크 1을 쓴다. 일반 변수처럼 읽은 3에서 bit 0을 뺀 2를 쓰면, 이 자체 계약에서는 오류를 지우고 완료를 남긴다. 값 자체의 대입과 비트별 확인 처리 의미가 반대가 될 수 있다.

처음 읽은 값이 1인데 쓰기 전에 오류 bit가 새로 켜져 현재 값이 3이 된 경우에도 마스크 1만 쓰면 새 오류를 보존한다. 현재 상태 전체를 다시 읽어 값 3을 쓰는 잘못된 경로는 관찰하지 않았던 오류까지 지운다. 접근 폭·순서·읽기 부작용과 posted 쓰기의 실제 도착도 각각 계약을 확인해야 한다.

주소가 가리키는 대상부터 확인하기

MMIO는 주소 공간의 일부를 장치 인터페이스로 해석한다. 같은 load/store 형태라도 RAM처럼 저장값을 되돌려 주는 계약은 아닐 수 있다. 실제 접근에는 운영체제의 매핑·전용 접근자와 장치 설명이 필요하다.

이 단원의 주소는 종이 모형이다. 숫자를 실제 포인터로 만들어 실행하지 않는다. 주소 표에서 대상·폭·허용 방향·읽기/쓰기 효과를 각각 찾아야 한다.

상태와 명령의 계약

가상 상태 비트 0은 준비, 비트 1은 오류라고 정의하자. 값 3이면 두 비트가 함께 켜졌다. 준비가 참이어도 오류가 있으므로 성공 조건에는 오류가 없다는 검사도 포함한다.

명령 레지스터에 시작을 쓰면 일을 요청한다. 완료까지 필요한 시간과 결과 상태는 별도 사건이다. 아래 예제의 비트 뜻은 실제 제품에 적용하지 않는다.

같은 주소를 두 번 읽는 경우

가상의 데이터 레지스터가 읽을 때 큐의 앞 값을 꺼내면 두 번 읽기의 결과가 다를 수 있다. 값을 확인하려고 한 추가 읽기가 실제 자료를 소비할 수 있으므로 관찰 자체의 부작용을 확인한다.

Linux 접근자의 폭·순서와 posted 쓰기 완료는 별도 계약이다. 실제 장치에서 같은 장치의 읽기로 쓰기를 확인하는 경우가 있어도 모든 주소를 안전한 확인용으로 선택할 수는 없다.

polling·interrupt

준비됐는지 계속 물을까, 준비되면 알려 달라고 할까?

준비 개념과 학습 목표

준비 개념

  • 시간 구간

  • CPU 작업과 대기

  • 상태 검사

학습 목표

  • 관찰 지연과 CPU 검사 비용을 계산한다.

알림 비용 때문에 실제 처리가 밀릴 수 있을까?

자체 CPU 예산에서 1초에 요청 10000개가 도착한다. 요청별 자료 처리 비용은 0.04ms, 인터럽트 진입의 고정 비용은 0.08ms다. 한 요청마다 인터럽트가 하나이면 자료 처리 400ms와 진입 800ms로 총 1200ms의 CPU 작업이 필요하다.

단일 CPU의 1초 예산은 1000ms다. 이 집계에서는 다른 일을 전혀 하지 않아도 1200ms의 작업을 같은 1초 안에 소화할 수 없다. 이는 정의한 비용 예산의 산술이며 실제 큐 길이·스케줄러·하드웨어를 측정한 결과는 아니다.

10개 요청을 한 알림으로 묶으면 알림 1000회에 진입 80ms, 자료 처리 400ms로 합계 480ms다. 그러나 묶음의 앞 요청은 기다린다. 같은 비용을 줄이는 방식에서도 지연 목표와 데이터 처리가 모두 필요한 이유를 확인한다.

물어보는 방식과 알림 방식

Polling은 소프트웨어가 상태를 반복 확인하는 방식이다. Interrupt는 사건을 알리는 신호에 따라 처리 경로로 들어가는 방식이다. 완료 알림 뒤에도 상태·오류 확인과 필요한 처리가 남는다.

알림 방식과 자료 전송 방식은 다른 축이다. 인터럽트를 사용하면서 CPU가 자료를 복사할 수도 있고, DMA 완료를 polling할 수도 있다.

우리 시간표의 가정

검사를 t=0,2,4,… ms의 점에서 하고 검사 비용을 별도 CPU 사용량으로 합산하는 가상 모형을 정하자. 점검을 실제 길이를 가진 일정으로 다시 배치하지 않는 단순화다. 준비 시점이 두 점검 사이면 다음 점검에서 발견한다.

검사 한 번의 비용이 작아도 많은 검사를 합치면 커진다. 인터럽트도 처리 비용이 있으므로 빠른 장치에서 무조건 더 효율적이라는 결론을 내리지 않는다.

어떤 지연을 보고하는가

준비까지 시간, 준비 이후 발견 지연, 처리 완료 시각을 분리한다. 이 예제는 발견까지를 먼저 계산하고 데이터 후처리는 포함하지 않는다.

매핑 전의 세 조각이 장치에는 두 조각으로 보일 수 있을까?

자체 scatter-gather 입력은 각 512바이트의 메모리 조각 세 개다. 매핑이 성공한 반환 장부는 장치 주소 0x2000의 길이 1024바이트와 주소 0x5000의 길이 512바이트, 총 두 항목이라고 정한다. 매핑 과정이 첫 두 조각을 장치가 볼 수 있는 연속 범위로 합친 사례다.

장치에 넘길 항목 수는 성공 반환값 2를 사용한다. Linux의 unmap과 해당 sync에 사용하는 원래 nents는 3이다. 목적이 다른 두 개수를 같은 변수 의미로 취급하면 장치 설정이나 매핑 수명 관리가 틀릴 수 있다. 실제 dma_map_sg를 호출한 결과가 아닌 교육용 반환 장부다.

세 입력 조각의 총 길이는 1536바이트로, 두 반환 범위의 길이 합 1024 + 512와 같다. CPU 가상 포인터를 장치 주소로 대체하지 않으며 방향과 장치 주소 제약도 별도로 확인한다. dma_map_sg가 실패해 0을 반환하면 성공한 항목이 없으므로 장치 시작을 성공 경로로 진행하지 않는다.

전송을 맡기는 의미

DMA는 자료 이동을 DMA 엔진에 맡기는 방식이다. CPU는 설정과 완료 처리에 여전히 참여한다. 자료를 옮기는 CPU 작업이 줄어도 총 지연이 항상 줄어드는 것은 아니다.

버스와 메모리 자원은 공유될 수 있다. 다른 작업과 겹치는 정도를 확인하지 않고 DMA가 CPU 성능에 영향이 없다고 주장하지 않는다.

주소를 그대로 복사하지 않는다

CPU 가상 주소·물리 주소·장치의 DMA 주소는 구별한다. 매핑이 필요한 환경에서 CPU 포인터 숫자를 장치에 그대로 전달하면 원하는 버퍼가 아닐 수 있다.

중간 과정을 따라가는 예제

자체 버퍼 4,096 B를 전송한다. PIO는 4 B당 CPU 0.02 μs가 들며 설정/완료 추가 비용은 이 모형에서 0이다. DMA는 CPU 설정 3 μs·완료 처리 1 μs, 전송률 512 B/μs다. CPU 가상 0x4000→물리 0xA000→DMA 0x2000이라는 매핑 표도 주어진다.

  1. PIO 전송은 4,096/4=1,024개이고 CPU 비용은 20.48 μs다. 직렬 모형에서 총 시간도 20.48 μs로 가정했다.

  2. DMA 이동은 4,096/512=8 μs다. CPU 비용은 3+1=4 μs이고 직렬 총 시간은 3+8+1=12 μs다.

  3. 장치에는 매핑 표의 DMA 주소 0x2000을 전달한다. CPU 가상 0x4000을 그대로 전달하지 않는다.

  4. CPU 비용 감소와 총 시간 감소는 별도 계산이다. 실제 시스템에서 이 값과 겹침 조건을 측정하지 않았다.

이 모형의 CPU 비용은 20.48 대 4 μs, 직렬 총 시간은 20.48 대 12 μs다. 장치는 DMA 주소를 사용한다.

timeout을 기록하면 장치도 버퍼 사용을 멈춘 것일까?

자체 요청 A는 식별자 7로 버퍼를 장치에 인계했다. 소프트웨어가 t = 5ms에 timeout을 기록하지만 장치는 t = 7ms에 늦게 값 20을 쓸 수 있다고 정한다. timeout은 소프트웨어의 기다림 결과이며 이 모형에서는 장치를 중지시키는 사건이 아니다.

잘못된 경로는 t = 5ms에 버퍼를 해제·재사용해 새 요청 B(식별자 8)의 초기 값 99를 넣는다. 늦은 A의 쓰기는 B의 데이터를 20으로 바꿔 손상한다. 나중에 A의 알림 식별자 7을 확인하고 무시해도 이미 발생한 DMA 쓰기를 되돌리지는 못한다.

안전한 정책에는 장치 계약에 따른 중지 또는 완료·접근 종료의 확인, 필요한 가시성 인계, 매핑 해제와 버퍼 재사용 순서가 있어야 한다. 식별자는 늦은 완료를 새 요청과 혼동하지 않게 하지만 수명을 혼자 보장하지 않는다. 실제 특정 장치의 취소 처방이 아니라 명시한 접근 가능성의 종이 모형이다.

먼저 확인할 개념

    요청 시작과 종료를 장치 계약으로 확인한다.

  • 가시성·순서·소유권

    CPU의 기다림 결과와 장치의 접근 가능성을 분리한다.

누가 버퍼를 사용하는가

CPU 소유일 때 내용을 준비하고, 장치로 인계한 뒤에는 장치 소유로 둔다. 완료를 확인하고 필요한 동기화 뒤 CPU가 다시 읽는다. 버퍼 수명과 사용 주체를 사건표로 추적하자.

매핑을 유지한 streaming 버퍼를 다시 사용할 때 Linux API의 CPU/장치 동기화 단계가 필요할 수 있다. 실제 방향·플랫폼 계약을 확인해야 하며 아래 표는 호출 처방이 아니다.

가시성과 순서의 차이

CPU가 쓴 새 내용이 장치에서 보이는가와, 데이터 준비가 유효 표시보다 먼저 보이는가는 다른 질문이다. Coherent 메모리도 필요한 순서 보장을 자동으로 모두 제공하는 것은 아니다.

장치가 읽는 전송 설명 구조를 descriptor(디스크립터)라고 부르자. 가상 디스크립터에 버퍼 주소를 쓰고 나서 유효를 표시하려 한다. 장치가 유효부터 보고 옛 주소를 읽는 순서를 허용하면 잘못된 전송이 시작될 수 있다. 실제 플랫폼의 적절한 barrier와 접근 계약을 사용한다.

완료와 재사용을 따로 확인하기

완료 신호가 나타나도 실패 상태·전송 범위와 읽기 가시성을 확인해야 한다. 사용이 끝나기 전에 버퍼를 해제하거나 다른 요청으로 덮어쓰는 상태를 정상으로 취급하지 않는다.

종이 상태표는 문제 원인을 설명할 수 있지만 특정 장치에서 캐시 동작이나 메모리 순서를 실험한 증거가 아니다. 실제 장치 검증에는 드라이버/하드웨어 계약이 필요하다.

다른 문제에 적용하기

장치 효과·CPU 예산·매핑 개수·버퍼 수명

자체 W1C STATUS의 현재 값이 3일 때 완료 bit만 지우는 마스크와 잘못 값 2를 쓴 결과를 구하라. 초당 요청 10000개, 요청당 알림 진입 0.08ms와 자료 처리 0.04ms에서 개별 알림과 열 요청 묶음 알림의 필요 CPU 작업량을 계산하라. 각 512바이트의 입력 세 조각이 DMA 범위 두 개로 매핑되면 장치 순회와 unmap에 사용할 개수를 분리하라. 요청 A7의 timeout이 5ms에 발생한 뒤 새 요청 B8로 재사용해 초기 값 99를 넣은 버퍼에 A가 7ms에 값 20을 쓰는 trace에서, 늦은 알림을 무시하는 것만으로 충분한지 설명하라.

힌트 1

쓴 비트의 효과와 비용이 발생하는 사건을 명시한다.

힌트 2

매핑 전후의 개수와 소프트웨어의 대기 결과 및 장치 접근 종료를 나눈다.

풀이와 답 확인

  1. 완료만 지울 때 마스크 1을 쓰면 상태 2가 남는다. 잘못 값 2를 쓰면 오류를 지워 상태 1이 남는다.

  2. 개별 알림은 800 + 400 = 1200ms, 열 요청 묶음 알림은 80 + 400 = 480ms의 필요 CPU 작업량이다.

  3. 총 길이는 1536바이트다. 장치 순회는 반환 count 2를, unmap은 원래 nents 3을 사용한다.

  4. B의 값 99가 옛 요청 A의 값 20으로 이미 손상될 수 있다. 식별자 검사는 알림 오인을 막지만, 장치 접근 종료의 확인·가시성 인계·매핑과 버퍼 수명 관리도 필요하다.

장치 계약과 자체 trace에서 효과·비용·주소 장부·사용 종료를 구별한다. 실제 MMIO·ISR·DMA·장치·학생 실험은 미수행이다.
