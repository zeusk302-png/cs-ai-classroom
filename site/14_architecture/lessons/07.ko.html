소단원 7.1

stage와 pipeline register

명령 여러 개가 겹쳐 계산되어도 서로의 값이 섞이지 않는 이유는?

준비 개념과 학습 목표

준비 개념

  • stage는 한 클록 구간에 수행하는 처리 단계다.
  • 레지스터는 클록 경계에서 값을 저장해 다음 단계에 넘긴다.
  • stall은 필요한 값이나 자원을 기다리는 정지, flush는 잘못된 경로 명령 취소, valid는 실제 명령인지 표시하는 유효 비트다.

학습 목표

  • 단계별 데이터와 제어 신호를 함께 추적한다.
  • 같은 작업의 피연산자를 맞추는 이유를 설명한다.

역할을 나누고 작업을 겹친다

교육용 5단계는 IF 명령 가져오기, ID 해석/레지스터 읽기, EX 연산/주소 계산, MEM 데이터 메모리, WB 결과 기록이다. 모든 명령이 모든 단계에서 실제 일을 하는 것은 아니지만 이 모형에서는 각 명령이 다섯 슬롯을 지나간다. 실제 CPU의 단계 수와 기능은 구현마다 다르다.

두 명령이 다른 단계에서 동시에 진행하면 회로를 더 자주 사용할 수 있다. 한 명령 자체가 여러 단계를 생략해 빨라지는 것과 겹쳐 처리하는 것은 다르다. 단계 이름만 외우기보다 어느 데이터가 다음 단계에서 필요한지 적는다.

데이터와 꼬리표가 함께 이동한다

IF/ID에는 명령 정보, ID/EX에는 피연산자와 목적 레지스터/제어 정보, EX/MEM에는 결과 또는 주소와 제어 정보 등이 저장된다. 결과 값만 넘기고 어느 명령의 어느 목적지인지 잃으면 WB에서 엉뚱한 곳을 쓸 수 있다.

클록 경계에서 모든 단계가 이전 저장값을 사용하고 다음 저장값을 동시에 갱신한다고 모델링한다. 소프트웨어 표를 위에서 아래로 갱신하며 방금 계산한 새 값을 같은 경계의 다른 단계가 즉시 읽게 하면 교육용 동기 회로 모형과 달라진다.

같은 작업의 두 입력을 맞춘다

회로 y=2x+z를 파이프라인화할 때 x 경로만 레지스터로 늦추면 이전 작업의 2x와 새 작업의 z를 섞을 수 있다. 동일 입력 묶음에 속한 값이 함께 만나도록 경로 지연을 맞춘다. acyclic 고정 파이프라인에서는 경로의 레지스터 수가 같은 규약이 이를 돕는다.

CPU는 stall/flush가 있어 단순 고정회로보다 복잡하다. valid 비트로 슬롯이 실제 명령인지 거품인지 표시하며, 기다릴 때 관련 레지스터의 enable을 제어한다. 경로 맞춤 원리를 CPU의 모든 제어 상황에 그대로 충분조건이라고 확대하지 않는다.

중간 과정을 따라가는 예제

두 단계 회로는 첫 단계에서 a=2x와 z를 각각 저장하고 둘째에서 y=a+z를 저장한다. 입력 작업1=(x1,z1)=(1,10), 작업2=(2,20), 초기 valid0이다. 경계마다 저장 묶음을 추적하라. z 경로 저장을 빠뜨리고 둘째에서 현재 z2를 쓰면 작업1의 값은?

  1. 경계1에 첫 단계 (a,z)=(2,10), valid1이며 출력은 아직 invalid다.
  2. 경계2에 첫 단계(4,20), 출력은 이전 묶음 2+10=12다.
  3. 경계3에 작업2 출력 4+20=24다.
  4. z를 저장하지 않고 작업2의 20과 결합하면 작업1 결과2+20=22로 틀린다.

정상 출력 12/24이며 꼬리표와 경로 저장이 없으면22처럼 다른 작업이 섞인다.

종이와 본문으로 직접 해보기

작업3=(3,30)을 연속 공급할 때 경계3의 첫 단계 값과 경계4 출력은? 첫 단계 데이터와 valid를 함께 적어라.

힌트 보기

출력은 같은 경계의 새 첫 단계가 아닌 이전 묶음을 읽는다.

풀이 보기

경계3의 첫 단계는(6,30),valid1이고 경계4 출력은6+30=36이다. 경계3 출력 24와 구별한다.

오해와 반례

레지스터는 값만 저장하면 되고 목적지 정보는 현재 명령에서 읽으면 된다.

앞 명령의 결과가 WB에 있을 때 현재 IF에는 뒤 명령이 있다. 목적지를 현재 명령에서 고르면 앞 결과를 뒤 명령의 레지스터에 써버릴 수 있으므로 제어 꼬리표도 함께 전달한다.

소단원 7.2

이상적인 처리율

명령 하나가5클록 걸리는데 매 클록 한 개가 끝날 수 있을까?

준비 개념과 학습 목표

준비 개념

  • latency는 한 작업의 시작부터 완료까지 시간이다.
  • throughput은 단위 시간에 완료하는 작업 수다.

학습 목표

  • 충전·비우기 비용을 포함한 유한 작업 시간을 구한다.
  • 최장 단계와 레지스터 비용으로 주기를 계산한다.

첫 결과와 이후 결과의 간격

hazard가 없고 매 클록 하나를 시작하는 k단계 파이프라인은 첫 결과가k클록 뒤 나온다. 이후에는 다른 작업들이 이미 뒤따르고 있으므로 매 클록 하나씩 끝날 수 있다. 단일 작업 latency와 정상 상태 결과 간격을 구별한다.

n개 작업을 빈 파이프라인에서 처리하면 k+n−1클록이다. 처음 채우는 비용 k−1이 유한 작업 평균 CPI에 들어간다. n이 매우 커질 때 평균이1에 가까워지지만 n 1이면 CPI=k다.

최장 단계가 발걸음을 정한다

각 단계가 같은 클록 경계에 맞춰야 하므로 주기는 가장 느린 단계의 조합 지연과 레지스터 오버헤드를 포함한다. 단계를 많이 나누어도 일부가 여전히 길면 나눈 수만큼 주기가 줄지 않는다.

레지스터 clock-to-Q와 setup 등을 합친 비용을 h라고 단순화하면 T=max(d_i)+h다. 이 식은 skew/hold/변동을 별도 검토하는 교육 모형이다. hold 제약을 이 최대 지연 식 하나로 해결했다고 말하지 않는다.

이상 speedup도 유한하다

직렬 한 작업의 시간이 합 지연인 비교 모형과 파이프라인 시간을 같은 조건에서 비교한다. 실제 single-cycle CPU와 회로 모형의 구체적인 레지스터 비용이 다를 수 있으므로 기준을 문제에 적는다.

균형 단계·오버헤드0·많은 독립 작업이면 k배에 가까운 이득을 얻을 수 있다. 빈 파이프라인과 짧은 작업열, 단계 불균형과 register overhead는 이득을 줄인다. 개별 작업 latency는 오히려 늘 수 있다.

중간 과정을 따라가는 예제

5단계 지연2/3/4/3/2ns, 각 클록의 합산 레지스터 overhead1ns이며 hazard가 없다. 직렬 기준은 한 작업 14ns이다. n=10의 파이프라인 시간과 throughput/latency/speedup을 구하라.

  1. T=max지연4+1=5ns다.
  2. 첫 작업 latency 5*5=25ns다.
  3. 10작업은5+10−1=14클록,70ns다. 직렬은140ns다.
  4. 유한 speedup140/70=2배, 정상 throughput1/5ns=2억작업/s다.

단일 latency 25ns는14ns보다 길지만10작업 총시간은70ns로 절반이다.

종이와 본문으로 직접 해보기

힌트 보기

n+4와 최장 지연을 각각 적용한다.

풀이 보기

오해와 반례

5단계면 명령 하나도 정확히5배 빨라진다.

예제의 단일 작업은 14→25ns로 느려진다. 여러 독립 작업을 겹치는 처리율 이득과 한 작업 latency를 구별해야 한다.

소단원 7.3

데이터·제어·구조 hazard

명령의 순서가 맞는데도 겹쳐 실행하면 틀릴 수 있는 이유는?

준비 개념과 학습 목표

준비 개념

  • hazard는 겹친 단계 진행이 요구되는 결과나 자원을 만족하지 못하는 상황이다.
  • 의존성은 명령 사이의 의미 관계이며 stall 여부는 구현에 달려 있다.
  • forwarding은 기록 전 결과의 우회 전달, younger는 앞 명령보다 나중에 시작한 뒤 명령을 뜻한다.

학습 목표

  • 세 hazard의 원인을 구별한다.
  • forwarding·stall·flush의 역할을 설명한다.

필요한 값이 아직 만들어지지 않았다

데이터 hazard의 대표는 앞 명령이 쓸 값을 뒤 명령이 먼저 읽으려는 read-after-write다. 레지스터에 최종 기록되기 전 결과를 우회 전달하는 forwarding은 일부 대기를 줄인다. 명령을 무조건 멈추는 대신 언제 값이 생기고 언제 필요한지 비교한다.

교육용 5단계에서는 ALU 결과가 EX 끝에 있고 다음 EX가 이를 받을 수 있지만 load 결과는 MEM 끝에 생긴다. 바로 뒤의 EX가 그보다 먼저 시작하면 forwarding이 있어도 load-use 대기를 한 클록 둘 수 있다. 실제 설계의 stage와 메모리 지연이 달라지면 필요한 stall 수가 바뀐다.

다음 명령의 주소를 아직 모른다

분기의 방향과 목적지를 알기 전에 뒤 명령을 fetch하면 잘못된 경로의 명령이 들어올 수 있다. 틀린 경로의 valid를 지워 효과를 내지 못하게 하는 것이 flush다. 단순히 PC만 바꾸고 이미 들어온 store를 계속 실행하면 잘못된 메모리를 쓸 수 있다.

branch prediction은 다음 경로를 예상해 기다림을 줄이지만 오판이면 이미 진행한 잘못된 작업을 버려야 한다. 예측 정확도와 오판 패널티는 별도 수치다. 모든 분기마다 같은 penalty를 더하거나 정확도가 높다는 이유로 검증을 생략하지 않는다.

같은 자원을 동시에 요구한다

단일 포트 메모리를 IF와 MEM이 동시에 요구하면 두 요청을 같은 클록에 처리하지 못하는 structural hazard가 생긴다. 자원을 복제하거나 포트를 늘리거나 한 요청을 늦추는 방식으로 해결할 수 있다.

stall은 명령을 기다리게 하며 bubble은 효과가 없는 슬롯이다. flush는 잘못된 명령을 취소한다. 데이터를 기다리는 올바른 명령을 취소하고 다음으로 넘어가는 방식은 의존성을 해결하지 못한다.

중간 과정을 따라가는 예제

교육 모형: ALU EX 끝 결과는 다음 EX로 forwarding, load는 MEM 끝 결과를 다음 클록 EX로만 전달한다. I1 load r1, I2 add r2=r1+1이다. I1 IF1/ID2/EX3/MEM4/WB5일 때 I2의 earliest EX를 구하라. 분기는 EX3 끝에 판정되고 다음 target IF는4에서 시작한다고 별도 가정한다.

  1. I2가 IF2/ID3이면 대기 없이는 EX4다.
  2. load 값은4 끝에 있으므로 EX4 시작에 쓸 수 없다.
  3. ID4에 기다리고 EX5/MEM6/WB7로 진행한다.
  4. 분기의 뒤 경로 IF2/ID3 명령과 IF3 명령은 두 younger 슬롯이므로 취소한다.

load-use는 이 규약에서1 stall, EX끝 분기 오판은 younger2개를 flush한다.

종이와 본문으로 직접 해보기

IF와 MEM이 하나의 단일 포트를 공유한다. I1 load의 MEM4와 I4의 예정 IF4가 충돌하면 둘 다 그대로 진행해도 되나? 분리된 instruction/data port이면?

힌트 보기

정해진 동시 처리 수를 확인한다.

풀이 보기

한 포트는 동시에 하나만 처리하므로 예를 들어 MEM4를 우선하고 IF를5로 미룬다. 분리 포트이면 이 원인의 충돌은 없지만 데이터/제어 hazard까지 없어진 것은 아니다.

오해와 반례

forwarding이면 모든 hazard가 사라진다.

load-use의 값은 아직 MEM이 끝나지 않았고, 잘못된 PC나 단일 포트 충돌도 데이터 전달만으로 해결되지 않는다. 각 자원/시점을 별도로 확인한다.

소단원 7.4

pipeline diagram

표에서 같은 ID가 두 칸 연속 나오면 명령을 두 번 해석한 것일까?

준비 개념과 학습 목표

준비 개념

  • 가로축은 클록, 세로축은 명령으로 timing diagram을 그린다.
  • ID*는 해당 명령을 유지하며 기다리는 슬롯이라는 표기다.

학습 목표

  • 단계 표와 의존 화살표를 함께 작성한다.
  • stall이 뒤 명령 진행과 전체 완료에 주는 영향을 계산한다.

표를 읽는 기준을 먼저 고정한다

첫 IF가 cycle 1, 매 cycle 끝에 stage register가 갱신된다고 정한다. 빈 칸은 그 명령이 아직 없거나 완료했다는 뜻이며 stage 자체가 CPU 전체에서 없다는 뜻은 아니다. 한 column에는 여러 명령이 서로 다른 stage를 차지한다.

stall 표기는 값이 필요한 시점에 못 움직여 같은 명령이 그 stage에 남아 있음을 나타낸다. 표시된 반복 ID를 새로운 명령처럼 세면 instruction count를 과대 계산한다. bubble은 별도의 무효 EX 슬롯으로 표시한다.

생산 시점에서 소비 시점으로 선을 긋는다

load MEM 끝에서 consumer EX 시작까지 화살표를 그려 전달 가능한지 확인한다. 숫자 레지스터가 같다는 것만 찾지 말고 실제 source operand인지, 값이 어느 명령의 최신 쓰기인지 함께 본다.

대기할 때 PC와 앞 IF/ID를 유지하고 앞의 producer는 계속 흘려보낸다. producer까지 계속 멈추면 필요한 값이 영원히 생기지 않는 설계가 된다. 무엇을 hold하고 어디에 bubble을 넣는지 구별한다.

전체 완료와 취소 슬롯을 구별한다

정상 명령 n개의 이상 완료는 n+4지만 실제 대기와 취소 때문에 늘어날 수 있다. 취소된 명령을 완료 수에 넣지 않고 실제 진행을 cycle별로 확인한다. 복수 stall의 겹침 여부를 모르면 단순히 각각을 더하지 않는다.

아래 모형은 단일 발행·순서 진행·분리 메모리·한 클록 load-use stall과 ALU forwarding을 명시한다. store operand 타이밍이나 multi-cycle unit은 제외한다. 다른 CPU의 diagram을 이 규약으로 읽을 수 있는지 먼저 확인한다.

중간 과정을 따라가는 예제

I1 load r1, I2 add r2=r1+1, I3 add r3=r2+2이다. 5단계·단일 발행·분리 메모리·load-use1 stall·ALU forwarding, I2가 ID4에 유지되는 동안 I3의 IF도 유지된다. 각 stage cycle과 마지막 WB를 구하라.

  1. I1은 IF1 ID2 EX3 MEM4 WB5다.
  2. I2는 IF2 ID3 ID*4 EX5 MEM6 WB7이다.
  3. I3는 IF3 IF*4 ID5 EX6 MEM7 WB8이다.
  4. I1 MEM4 끝→I2 EX5, I2 EX5 끝→I3 EX6 forwarding이 가능하다.

마지막 WB8이며 정상 3명령 이상7클록에 stall1이 추가됐다.

종이와 본문으로 직접 해보기

I1과 I2 사이에 r1/r2와 무관한 독립 ALU J를 넣는다. 순서 I1,J,I2,I3일 때 load-use stall이 필요한가? 마지막 WB는?

힌트 보기

I2의 IF3/ID4/EX5를 먼저 적는다.

풀이 보기

I1 MEM4 끝 후 I2 EX5라 대기가 없다. J는IF2..WB6,I2 IF3..WB7,I3 IF4..WB8이다. 정상 명령은4개로 늘고 마지막8클록은 같아도 유용한 독립 일을 하나 더 했다. 원래 순서 교체가 의미상 허용된다는 전제가 필요하다.

오해와 반례

표의 총 칸 수가 실행 클록 수다.

여러 명령의 칸은 같은 시간에 겹친다. 예제 3명령의 유효 단계15칸을 더해15클록이라 하면 잘못이다. 최종 완료 column8을 기준으로 elapsed cycles를 센다.
