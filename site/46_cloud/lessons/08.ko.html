소단원 8.1

autoscaling·health check

방문자가 몰리면 서버를 늘리는 일과 고장 난 서버를 빼는 일은 같은가?

준비 개념과 학습 목표

준비 개념

  • 비율과 올림

  • 복제본과 요청 처리

학습 목표

  • 수평 확장의 계산 가정을 말한다.

  • 준비·생존·시작 검사를 구분한다.

용량을 맞추는 피드백

autoscaling은 관측 부하에 맞춰 복제본 수를 조정하는 피드백 제어다. 수평 확장은 수를, 수직 확장은 한 복제본의 자원을 바꾼다. 현재 수 n, 평균 지표 c, 목표 t>0에서 기본 제안은 ceil(n·c/t)이다. 올림은 필요한 수를 정수로 만들기 위한 것이다.

CPU 이용률이 request 대비 백분율이면 분모는 장비 전체 용량과 다르다. 현실에서는 결측 지표, 준비되지 않은 복제본, 최소·최대 수, 허용 오차와 안정화 기간이 계산을 바꾼다. 제안 수가 곧 준비 완료 수는 아니다.

건강의 세 가지 질문

readiness는 지금 새 요청을 받아도 되는지 묻는다. 실패하면 보통 Service 트래픽 대상에서 제외하지만 그것만으로 컨테이너를 재시작하지 않는다. liveness는 프로세스가 회복 불가능하게 멈췄는지를 살피며 임계 실패에 재시작을 유발한다.

startup 검사를 설정하면 초기화 성공 전 생존·준비 검사를 미룬다. 준비 검사와 생존 검사를 혼동해 일시적 외부 DB 장애마다 모든 앱을 재시작하면 남은 서버에 부하가 몰릴 수 있다. 검사도 실제 처리 능력을 완전히 증명하지는 못한다.

지연과 진동을 읽기

확장은 계측·판단·배치·기동 시간을 거쳐 효과가 난다. 과도한 축소와 확장을 반복하지 않도록 안정화와 여유 용량을 둔다. 병목이 공유 DB이면 앱 수만 늘려 해결되지 않는다.

아래 식은 모든 기존 복제본의 지표가 있고 준비되어 있으며 허용 오차·정책 제한을 따로 고려하지 않는 종이 모델이다. 실제 클러스터를 생성하거나 측정하지 않는다.

중간 과정을 따라가는 예제

복제본 4개, 평균 CPU 이용률 75%, 목표 50%, 최대 5개다. 기본 제안과 제한 적용 수는?

  1. 75/50=1.5를 구한다.

  2. ceil(4·1.5)=6이다.

  3. 최대5를 적용해 요청 수는5다. 기동 전 실제 준비 수는 별개다.

기본 6개, 최대 제한 후 5개.

종이와 본문으로 직접 해보기

최대 제한 없이 평균35%, 목표50%, 현재4개일 때 기본 제안과 readiness 실패의 조치를 적자.

힌트 보기

올림과 재시작 여부를 각각 판단한다.

풀이 보기

ceil(4·0.7)=3개. readiness 실패 복제본은 새 트래픽에서 제외하며 생존 실패와 동일하게 재시작한다고 판단하지 않는다.

오해와 반례

자동 확장이 있으면 모든 부하 급증을 즉시 처리한다.

새 복제본 시작 지연과 공유 병목이 있다. 확장 제어는 순간 무한 용량이 아니므로 대기열·부하 제한·관측도 필요하다.

5개.

readiness 실패가 곧 재시작인가?

답과 이유 보기

아니다.

startup 검사는 무엇을 보호하나?

답과 이유 보기

느린 초기화 동안 성급한 생존·준비 검사를 미룬다.

설정된 startup 성공 전 두 검사를 실행하지 않는다.

한 단계 더

종이에 수요가 상승·하강하는 시간선을 그리고 새 복제본 준비까지 두 관측 주기가 걸린다고 가정하자. 식의 제안 수와 실제 준비 수를 두 줄로 기록하면 확장 지연을 볼 수 있다.

소단원 8.2

무상태·상태 서비스

로그인한 사람의 다음 요청이 다른 서버로 가도 장바구니가 보일까?

준비 개념과 학습 목표

준비 개념

  • 메모리와 영속 저장

  • 복제본과 요청 경로

학습 목표

  • 요청 처리 상태의 위치를 추적한다.

  • 앱 교체와 데이터 복구를 분리한다.

무상태가 뜻하는 경계

무상태 앱은 올바른 다음 요청 처리에 특정 인스턴스의 이전 요청 메모리가 필수인 구조를 피한다. 요청에 필요한 식별자를 넣고 지속 상태는 공유 저장소 등 명시된 경계에 둔다. 서비스 전체에 데이터가 없다는 뜻은 아니다.

캐시가 있어도 없어졌을 때 다시 만들 수 있고 정확성이 다른 저장소에 의존하면 교체 가능한 앱을 설계할 수 있다. 반면 유일한 장바구니가 앱 A 메모리에 있으면 A 장애나 요청 경로 변경으로 손실될 수 있다.

상태를 가진 역할의 수명

DB와 메시지 저장소는 데이터·복제 관계·역할 정체성이 중요하다. StatefulSet은 안정적 식별자와 저장소 연결을 관리하는 도구지만 DB 복제 프로토콜·충돌 해소를 대신 구현하지 않는다.

복제본 이름이 안정적이어도 그 볼륨이 장애영역에서 접근 불가능하면 복구가 필요하다. 앱을 많이 켜는 것과 데이터 복제본의 올바른 승격은 다르다. 삭제·축소가 곧 볼륨 삭제라고 가정하지 않는다.

재시도의 의미를 보존하기

응답이 유실되면 결제가 실패했는지 성공했는지 클라이언트가 모를 수 있다. 같은 요청 식별자로 이미 처리한 결과를 찾아 중복 부작용을 막는 멱등 처리를 설계한다. 원자적 기록·중복 방지가 가능한 저장소 계약이 필요하다.

종이 예제는 저장소가 성공한 변경과 요청 ID를 함께 원자적으로 기록하고 장애 없이 유지된다는 조건이다. 실제 결제나 분산 DB 구현 보장을 실험한 것은 아니다.

중간 과정을 따라가는 예제

잔액100의 계좌에서 요청 ID r7로30을 한 번 차감했다. 응답이 유실되어 다른 앱에 r7을 재전송한다. 기록을 공유할 때와 중복방지 없이 다시 차감할 때의 잔액은?

  1. 첫 성공 변경은100−30=70이며 r7 처리 결과를 함께 저장한다.

  2. 다른 앱은 r7이 완료된 것을 찾아 결과70을 돌려주며 새 차감을 하지 않는다.

  3. ID를 확인하지 않고 다시30을 차감하면70−30=40이다.

계약을 지킨 경우70, 무방비 중복 차감은40.

종이와 본문으로 직접 해보기

앱 A에만 장바구니2개 품목을 저장했다. 다음 요청이 B로 간다. 공유 저장소로 옮길 때 새로 고려할 문제 두 가지를 적자.

힌트 보기

상태가 없어지는 대신 저장소가 새로운 의존점이 된다.

풀이 보기

B가 공유된2개 품목을 읽도록 만들 수 있다. 저장소 가용성과 동시 변경·원자성, 접근 권한 등을 별도로 설계해야 한다.

오해와 반례

무상태로 바꾸면 저장소 장애도 사라진다.

앱의 교체를 쉽게 하는 대신 지속 상태의 위치와 계약을 명확히 한다. 공유 저장소 장애·일관성은 여전히 남는다.

자기점검

무상태 앱에도 캐시가 가능한가?

답과 이유 보기

가능하다.

캐시 소실이 정확한 지속 상태의 소실과 같지 않도록 설계한다.

StatefulSet이 DB 복제 알고리즘을 제공하나?

답과 이유 보기

그 자체로 제공하지 않는다.

식별·저장소 관리와 응용 데이터 복제는 다른 층이다.

다른 앱으로 재시도만 하면 중복 차감이 막히나?

답과 이유 보기

아니다.

공유된 요청 ID 처리와 변경의 원자적 계약이 필요하다.

한 단계 더

한 요청이 처리 중인 동안 같은 ID가 동시에 도착하는 그림을 그리자. 단순히 먼저 조회하고 나중에 기록하는 두 단계라면 둘 다 미처리로 볼 수 있다. 저장소의 원자적 중복 차단이 필요한 이유다.

출처와 확인 범위
  • Kubernetes: StatefulSets

    안정적인 식별자와 저장소 연결, Deployment와 차이 및 삭제·축소 시 볼륨 유지 기본 설명을 읽었다.

  • Azure Architecture: Retry pattern

    응답 손실 후 비멱등 작업 재시도의 중복 부작용과 멱등성 조건 본문을 실제 읽었다.

소단원 8.3

장애영역·복구 전략

서버 세 대가 같은 전원에 연결되어 있으면 세 대의 의미는 무엇일까?

준비 개념과 학습 목표

준비 개념

  • 복제와 백업

  • 시간 간격

학습 목표

  • 공통 원인 장애를 식별한다.

  • RTO·RPO와 복구 관측값을 구별한다.

같이 실패하는 경계

장애영역은 한 원인으로 함께 영향을 받는 자원 묶음이다. 호스트·랙·가용영역·지역처럼 범위를 나누어 볼 수 있다. 복제본을 다른 호스트에 두어도 같은 전력·네트워크·권한에 의존하면 더 큰 공통 실패가 남는다.

지역 분산은 거리·비용·복제 지연과 운영 복잡성을 늘린다. 영역 이름만 다르다고 모든 의존성이 독립인 것은 아니다. 복구 계획은 앱뿐 아니라 데이터, 설정, 비밀 접근, 경로 전환을 포함한다.

복원 시점과 서비스 중단 시간

RPO는 받아들일 수 있는 데이터 복구 시점의 손실 시간 목표, RTO는 서비스를 복구하기까지 허용 중단 시간 목표다. 실제 복구 지연과 마지막 복구 가능 데이터 시점은 실험·사건에서 관측할 값이다. 목표를 적었다고 달성한 것은 아니다.

백업 복원은 저장된 시점으로 돌아간다. pilot light는 핵심 상태를 유지하고 나머지를 켜며, warm standby는 축소 서비스를 준비하고, active/active는 여러 위치에서 처리한다. 선택은 데이터 계약과 비용에 달린다.

복제와 백업은 다른 질문

복제는 장애 시 계속 읽고 쓰게 도울 수 있지만 잘못된 삭제나 손상도 복제할 수 있다. 여러 시점의 별도 백업·복원 절차가 필요한 이유다.

아래는 순서대로 탐지·데이터 복원·앱 준비·경로 전환을 한다는 교육 일정이다. 실제 일부 작업은 겹칠 수 있다. 장비를 끊거나 계정을 만들지 않고 종이에 복구 계획을 점검한다.

중간 과정을 따라가는 예제

12:00 백업 이후 쓰기가 계속되다가 12:07 장애가 났다. 이후 백업은 없다. 탐지 2분·복원 8분·앱 준비 3분·경로 전환 1분이 순서대로 든다. RPO 목표 5분, RTO 목표 10분과 비교하자.

  1. 복구 가능한 시점은12:00, 사건과의 간격7분이다.

  2. 순차 중단시간은2+8+3+1=14분이다.

  3. 7>5,14>10이므로 두 목표 모두 이 일정에서 미달이다.

시점 손실 간격 7분·복구 14분, 두 목표 미달. 정확한 손실 건수는 쓰기 기록이 필요하다.

종이와 본문으로 직접 해보기

12:05까지 안전하게 복제된 데이터가 있고 장애는12:07이다. 복구 작업 합계가9분이면 같은 목표를 만족하나?

힌트 보기

목표와 가정된 관측 간격을 각각 비교한다.

풀이 보기

간격2분≤5, 중단9분≤10으로 이 가정에서는 만족한다. 다른 의존성이나 실제 실험의 성공은 증명하지 않는다.

오해와 반례
