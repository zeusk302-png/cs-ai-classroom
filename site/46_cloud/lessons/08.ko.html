autoscaling·health check

방문자가 몰리면 서버를 늘리는 일과 고장 난 서버를 빼는 일은 같은가?

준비 개념과 학습 목표

준비 개념

  • 비율과 올림

  • 복제본과 요청 처리

학습 목표

  • 수평 확장의 계산 가정을 말한다.

  • 준비·생존·시작 검사를 구분한다.

지표를 못 받은 복제본을 평균에서 빼면 확장 판단이 어떻게 달라질까요?

기본의 올림 식에 실제 문서의 결측 보정을 연결합니다. 아래 CPU request는 모든 Pod에서 같고 모든 Pod가 준비되어 있다고 정합니다. 알려진 지표의 평균으로 확장 방향을 먼저 판단하고, 증가 방향이면 결측 Pod에 목표 지표의 0%를 보수적으로 가정해 평균을 다시 계산합니다. 이 0은 실제 CPU가 0이라고 측정한 값이 아닙니다. 새 비율이 반대 방향이 되면 곧바로 축소하는 대신 이번 조정을 하지 않습니다. 허용 오차·안정화·최소/최대·변경률 정책은 별도 조건입니다.

여러 지표는 하나가 낮다고 다른 하나의 확장 요구를 취소하지 않습니다. 유효한 지표별 제안 중 큰 값을 선택하며, 일부 지표를 읽지 못하고 나머지가 축소를 제안하면 축소를 건너뜁니다. 아래는 문서 규칙을 적용하는 자체 숫자 예이며 클러스터 실행 결과가 아닙니다. 검사 주기도 자체 시간표로 명시하여 startup 성공과 readiness 수락을 같은 사건으로 섞지 않습니다.

용량을 맞추는 피드백

autoscaling은 관측 부하에 맞춰 복제본 수를 조정하는 피드백 제어다. 수평 확장은 수를, 수직 확장은 한 복제본의 자원을 바꾼다. 현재 수 n, 평균 지표 c, 목표 t>0에서 기본 제안은 ceil(n·c/t)이다. 올림은 필요한 수를 정수로 만들기 위한 것이다.

CPU 이용률이 request 대비 백분율이면 분모는 장비 전체 용량과 다르다. 현실에서는 결측 지표, 준비되지 않은 복제본, 최소·최대 수, 허용 오차와 안정화 기간이 계산을 바꾼다. 제안 수가 곧 준비 완료 수는 아니다.

건강의 세 가지 질문

readiness는 지금 새 요청을 받아도 되는지 묻는다. 실패하면 보통 Service 트래픽 대상에서 제외하지만 그것만으로 컨테이너를 재시작하지 않는다. liveness는 프로세스가 회복 불가능하게 멈췄는지를 살피며 임계 실패에 재시작을 유발한다.

startup 검사를 설정하면 초기화 성공 전 생존·준비 검사를 미룬다. 준비 검사와 생존 검사를 혼동해 일시적 외부 DB 장애마다 모든 앱을 재시작하면 남은 서버에 부하가 몰릴 수 있다. 검사도 실제 처리 능력을 완전히 증명하지는 못한다.

지연과 진동을 읽기

확장은 계측·판단·배치·기동 시간을 거쳐 효과가 난다. 과도한 축소와 확장을 반복하지 않도록 안정화와 여유 용량을 둔다. 병목이 공유 DB이면 앱 수만 늘려 해결되지 않는다.

결측을 무시한 10개와 보정한 8개

현재 Pod 6개 중 5개의 CPU 지표는 각각 80%, 하나는 결측이고 목표는 50%입니다. CPU request는 같고 모두 준비됐으며 다른 정책은 제외합니다. 초기 제안과 결측 보정 제안을 구하세요.

  1. 알려진 평균 80%의 비율은 80/50=1.6이고 초기 제안은 ceil(6×1.6)=10개입니다.

  2. 증가 방향이므로 결측 하나를 목표의 0%로 가정합니다. 보정 평균은 400/6=200/3%입니다.

  3. 보정 비율은 (200/3)/50=4/3이고 제안은 ceil(6×4/3)=8개입니다.

  4. 여전히 증가 방향이며 기본 0.1 허용 오차 바깥입니다. 다른 정책을 제외한 이 예에서는 8개를 제안합니다.

초기 제안 10개, 결측 보정 제안 8개입니다. 실제 준비 완료 수는 따로 확인합니다.

비교할 점

결측 Pod를 죽은 Pod로 제거하거나 실제 CPU가 0이라고 측정했다고 하지 않습니다. 서로 다른 request나 추가 정책을 적용하면 결과가 달라질 수 있습니다.

느린 초기화와 실패 임계값

자체 startup 검사는 10, 20, 30, …초에 즉시 판정하며 초기화는 65초에 완료됩니다. 처음 여섯 번은 실패입니다. 연속 실패 임계값 6과 7을 비교하세요. 종료 유예와 기동 재시도 시간은 제외합니다.

  1. 임계값 6에서는 10–60초의 여섯 실패로 60초에 재시작 조치를 유발합니다. 종료 유예를 제외한 조건에서 첫 시도의 65초 완료 전에 중단됩니다.

  2. 임계값 7에서는 60초까지의 여섯 실패가 아직 임계값에 못 미칩니다.

  3. 70초 검사 때는 이미 65초에 초기화가 끝났으므로 성공합니다.

  4. startup 성공 전에는 liveness/readiness 검사를 실행하지 않습니다. 성공 후 별도의 readiness 조건까지 충족해야 트래픽을 받습니다.

임계값 6은 60초에 재시작 조치를 유발하고, 임계값 7은 70초에 startup 검사에 성공합니다.

비교할 점

연습 1 · 값과 상태 예측

현재 Pod 4개 중 알려진 2개의 CPU 지표는 각각 80%, 결측은 2개이고 목표는 50%입니다. 모두 준비됐고 request가 같습니다. 원래 증가 제안과 보정 후 비율, 조정 여부를 쓰세요.

힌트 1

먼저 알려진 평균으로 방향을 정합니다.

힌트 2

보정할 때 결측 각각에 0을 넣어 네 개의 평균을 구합니다.

풀이와 답 확인

  1. 초기 제안은 ceil(4×80/50)=ceil(6.4)=7개입니다.

  2. 보정 평균은 (80+80+0+0)/4=40%, 비율은 0.8입니다.

  3. 증가에서 축소 방향으로 바뀌었으므로 이번 조정을 하지 않습니다.

보정 제안 ceil(4×0.8)=4이므로 CPU가 낮아졌다는 실제 관측이다.

보정값은 결측의 보수적 가정입니다. 방향 반전 규칙과 실제 관측값을 구분하세요.

힌트 1

조회 오류는 낮은 부하 측정값이 아닙니다.

힌트 2

여러 지표의 축소 제한 규칙을 확인합니다.

풀이와 답 확인

  1. 알 수 없는 지표를 0으로 대체하지 않습니다.

  2. 유효 지표는 축소를 제안하지만 다른 지표 오류가 있으므로 축소를 건너뜁니다.

  3. 지표 오류를 조사하고 유효한 관측으로 다시 판단합니다.

이 조건에서는 현재 4개를 유지하고 축소를 건너뜁니다.

지표를 읽지 못했다는 것은 해당 작업이 없다는 뜻이다.

관측 실패와 실제 값 0은 다릅니다. 지표 파이프라인의 실패를 부하가 줄었다는 근거로 쓰지 마세요.

연습 3 · 직접 만들어 보기

현재 Pod 4개에서 CPU 지표의 제안은 6개, 큐 지표의 제안은 8개이며 둘 다 유효합니다. 최대 7개인 자체 제한을 마지막에 적용하세요. 제안·요청·준비 수를 구별해 쓰세요.

힌트 1

지표별 제안 중 큰 값을 선택합니다.

힌트 2

새 Pod가 시작됐다는 추가 관측은 없습니다.

풀이와 답 확인

  1. 지표 통합 제안은 max(6,8)=8개입니다.

  2. 최대 7개 제한을 적용한 요청 수는 7개입니다.

  3. 실제 준비 수는 주어진 정보로 확정하지 못합니다.

통합 제안은 8개, 최대 제한 후 요청은 7개이며 준비 수는 추가 확인이 필요합니다.

흔한 오답에서 다시 생각하기

CPU와 큐는 다른 병목 신호입니다. 큰 제안을 선택하는 단계와 정책 제한 단계를 따로 표시하세요.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

초기화를 마친 앱의 DB만 잠시 불통입니다. 자체 readiness는 필수 DB 연결을 검사하고, liveness는 앱 자체의 진행 가능성을 검사하며 성공합니다. readiness가 실패 임계값에 도달하면 어떤 조치를 하는지 쓰고 모든 앱을 재시작하는 설계와 비교하세요.

힌트 1

외부 의존성 장애와 앱 자체의 회복 불가능한 정지를 구별합니다.

힌트 2

readiness 실패만으로 컨테이너를 재시작하지 않습니다.

풀이와 답 확인

  1. 필수 DB를 쓰는 새 요청을 받지 못하므로 Service의 트래픽 대상에서 제외합니다.

  2. liveness 검사는 성공하므로 이 검사 계약에서는 앱 재시작을 유발하지 않습니다.

  3. 모든 앱을 재시작하면 초기화 부하를 더할 수 있으며 DB 가용성을 자동 회복하는 것도 아닙니다.

복구 작업을 동시에 하면 중단 시간이 언제나 가장 짧은 작업과 같을까요?

기본 복구 시간 계산에 작업 사이의 의존 관계를 추가합니다. 장애 탐지에 2분이 걸리고, 그 뒤 데이터 복원 8분·앱 준비 3분·비밀 접근 준비 5분을 동시에 시작한다고 정합니다. 세 준비가 모두 끝나야 검증 2분과 경로 전환 1분을 순서대로 진행합니다. 중단 시간은 2+max(8,3,5)+2+1=13분입니다. 앱 준비를 데이터 복원 뒤에만 시작할 수 있다면 같은 작업 시간으로도 결과가 달라집니다. 숫자를 모두 더하거나 가장 짧은 작업을 고르는 대신 완료 조건까지의 가장 긴 경로를 찾습니다.

서비스를 복구하려면 여러 자료의 복구 시점도 서로 맞아야 합니다. 이 예에서는 DB가 12:00부터 12:05까지, 객체 자료가 12:00부터 12:03까지 매 분의 시점으로 복구 가능하고, 같은 시점의 조합이 일관됨을 확인했다고 가정합니다. 12:07에 장애가 나면 최신 공통 복구 시점 12:03과의 간격은 4분입니다. 실제 복원 시험을 수행한 결과는 아닙니다. 스냅샷 두 개만 있다면 그 사이 모든 시점으로 복구할 수 있다고 가정해서도 안 됩니다.

같이 실패하는 경계

장애영역은 한 원인으로 함께 영향을 받는 자원 묶음이다. 호스트·랙·가용영역·지역처럼 범위를 나누어 볼 수 있다. 복제본을 다른 호스트에 두어도 같은 전력·네트워크·권한에 의존하면 더 큰 공통 실패가 남는다.

지역 분산은 거리·비용·복제 지연과 운영 복잡성을 늘린다. 영역 이름만 다르다고 모든 의존성이 독립인 것은 아니다. 복구 계획은 앱뿐 아니라 데이터, 설정, 비밀 접근, 경로 전환을 포함한다.

복원 시점과 서비스 중단 시간

RPO는 받아들일 수 있는 데이터 복구 시점의 손실 시간 목표, RTO는 서비스를 복구하기까지 허용 중단 시간 목표다. 실제 복구 지연과 마지막 복구 가능 데이터 시점은 실험·사건에서 관측할 값이다. 목표를 적었다고 달성한 것은 아니다.

백업 복원은 저장된 시점으로 돌아간다. pilot light는 핵심 상태를 유지하고 나머지를 켜며, warm standby는 축소 서비스를 준비하고, active/active는 여러 위치에서 처리한다. 선택은 데이터 계약과 비용에 달린다.

복제와 백업은 다른 질문

복제는 장애 시 계속 읽고 쓰게 도울 수 있지만 잘못된 삭제나 손상도 복제할 수 있다. 여러 시점의 별도 백업·복원 절차가 필요한 이유다.

힌트 1

풀이와 답 확인

  3. 병렬 준비의 최대 시간이 5분이므로 전체 계획 시간은 2+5+2+1=10분입니다.
