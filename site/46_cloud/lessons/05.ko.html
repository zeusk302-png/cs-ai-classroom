소단원 5.1

가상 네트워크·서브넷

멀리 있는 가상 컴퓨터들도 같은 주소 공간 안에서 묶어 관리할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • IPv4는 32비트 주소다. CIDR의 /p는 앞 p비트를 공통 접두부로 사용한다.

  • VPC는 클라우드의 논리적 네트워크 영역이며 서브넷은 그 안의 더 작은 주소 범위다. 가용영역은 물리 장애를 구분하는 배치 범위다.

학습 목표

  • CIDR 범위를 나누고 포함·겹침을 판정한다.

  • 주소 범위·배치·인터넷 경로의 역할을 구별한다.

큰 주소 구역을 둘로 나누면 실제 배정할 수 있는 자리도 그대로일까요?

학교 전체의 사물함 번호를 반별로 나누듯 CIDR은 주소 범위를 일정한 비트 경계로 나눈다. 같은 주소 구역 안에 있다는 것과 독립 서브넷끼리 겹치지 않는다는 것은 다른 조건이다. 이번에는 /23을 /24로 나누고 중복·포함·예약을 함께 비교한다.

IPv4 전체 주소 수는 비트 수로 계산한다. 사용 가능 수는 별도 서비스 규칙을 적용한 값이다. 예약 계산에서는 AWS 일반 IPv4 서브넷의 첫 네 주소와 마지막 주소를 제외하는 조건을 사용하며 BYOIP 예외·다른 공급자·IPv6로 확대하지 않는다. 실제 자원은 배정하지 않았다.

먼저 확인할 개념
  • 가상 네트워크·서브넷

    CIDR의 자유 비트와 주소 범위·가용영역을 구별한다.

  • 보안그룹·라우팅·NAT

    주소 구역 안이라는 사실이 경로나 접근 허용을 대신하지 않음을 연결한다.

주소 공간을 잘라 이름을 붙인다

10.20.0.0/16은 앞 두 바이트가 10과 20인 주소 범위다. 이를 10.20.1.0/24,10.20.2.0/24처럼 나누면 각 범위의 마지막 바이트가 0..255다. 실제 자원이 사용할 주소는 해당 범위와 서비스 예약 규칙에 맞아야 한다.

/24의 전체 수는 2^(32−24)=256이다. 이를 그대로 가상 컴퓨터 256대의 사용 가능 수라고 말하지 않는다. 공급자가 일부 주소를 예약할 수 있고 이미 배정된 주소도 있기 때문이다. 여기서는 사용 가능 수가 아닌 전체 범위의 크기를 계산한다.

논리 주소와 물리 배치를 함께 적는다

가상 네트워크는 주소와 접속 정책을 논리적으로 표현한다. AWS의 서브넷은 한 가용영역 안에 있으며 영역을 가로지르지 않는다. 두 영역에 서비스를 배치하려면 각 영역의 서브넷과 그 사이 경로를 별도로 계획한다. 다른 공급자의 세부 제약은 해당 문서에서 확인해야 한다.

같은 VPC라는 사실은 모든 요청이 자동 성공한다는 뜻이 아니다. 경로·보안 정책·서버 수신 상태가 함께 맞아야 한다. 주소가 겹치는 별도 네트워크를 연결하면 목적지를 구분하기 어려울 수 있어 연결 전에 범위를 검사한다.

공개라는 이름의 조건을 살핀다

공개 서브넷과 비공개 서브넷의 구별은 숫자가 10으로 시작하는지보다 외부로 향하는 경로 설정과 연결 방식에 달린다. AWS의 공개 서브넷은 인터넷 게이트웨이로 직접 가는 경로를 갖는다. IPv4 자원 자체의 공인 주소와 허용 정책도 실제 인터넷 통신에 필요하다.

따라서 공개 경로가 있다고 모든 자원에 공인 주소가 자동 붙거나 모든 포트가 열리는 것은 아니다. 비공개 자원의 외부 시작 통신은 NAT 등 별도 경로로 계획할 수 있다. 이 단원은 종이 주소 지도이며 클라우드 콘솔을 설정한 결과가 아니다.

/23은 세 번째 바이트의 마지막 비트도 자유다. 시작 값 4는 2의 배수이며 세 번째 바이트 4와 5를 포함한다. 두 /24는 경계가 겹치지 않고 원래 범위를 모두 덮는다.

중간 과정을 따라가는 예제

VPC 10.20.0.0/16 안에서 A 10.20.1.0/24,B 10.20.2.0/24를 만든다. 각 전체 주소 수, 겹침 여부,10.20.1.200과 10.21.1.2의 포함을 판정하라.

  1. 각 /24에는 마지막 8비트가 자유라 256개다. 두 범위 전체는 512개다.

  2. A의 범위 10.20.1.0..255와 B의 10.20.2.0..255는 세 번째 바이트가 달라 겹치지 않는다.

  3. 10.20.1.200은 A와 VPC에 포함되며 B에는 없다.

  4. 10.21.1.2는 두 번째 바이트 21이 VPC 접두부 20과 달라 VPC 밖이다.

A,B는 겹치지 않는 256개 범위이며 전체 512개다. 사용 가능한 인스턴스 수와 구별한다.

조건을 바꾸어 비교하기

분할의 포함과 비중복

표의 /23을 두 /24로 나눌 때 총 주소 수와 10.20.5.9의 포함을 설명하라.

  1. 자유 비트는 각각 9개와 8개라 전체 수는 512개와 각 256개다.

  2. 두 /24의 세 번째 바이트는 4와 5로 다르다. 합계 256+256=512개다.

  3. 10.20.5.9는 두 번째 /24와 원래 /23에 속하며 첫 번째 /24에는 없다.

크기와 포함이 보존되면서 두 조각은 비중복이다. 자원 배정 가능 수를 뜻하지 않는다.

비교할 점

기본 /16 안의 /24 비교에서 /23의 한 비트를 실제 분할한다.

예약은 서브넷마다 적용

일반 AWS IPv4 조건에서 /23 하나와 /24 두 개의 미배정 사용 가능 주소 수를 비교하라. 다른 사용·추가 예약은 없다.

  1. 하나의 /23은 전체 512개에서 예약 5개를 빼면 507개다.

  2. 두 /24는 각각 256−5=251개로 합계 502개다.

  3. 전체 주소는 같지만 서브넷별 예약 횟수가 두 번이라 합계 사용 가능 수는 5개 적다.

507개와 502개다. 이 조건부 계산을 모든 클라우드·주소 반입 방식의 규칙으로 사용하지 않는다.

비교할 점

주소 전체 크기 보존과 예약 후 배정 가능 수를 비교한다.

오해와 반례

연습 1 · 값과 상태 예측

10.20.4.0/24를 10.20.4.0/26, 10.20.4.64/26, 10.20.4.128/26, 10.20.4.192/26으로 나눈다. 각 전체 수, 총수, 10.20.4.190의 소속을 구하라.

힌트 1

/26의 자유 비트는 6개다.

힌트 2

마지막 바이트의 구역 폭은 64다.

풀이와 답 확인

  1. 각 조각은 64개이고 합계는 256개다.

  2. 범위는 0..63, 64..127, 128..191, 192..255다.

  3. 190은 세 번째 조각에만 들어간다.

각 64개·총 256개이며 190은 10.20.4.128/26에 속한다.

흔한 오답에서 다시 생각하기

190은 마지막 조각의 시작 192와 비슷하니 마지막이다.

구역 경계는 유사한 숫자가 아니라 포함 부등식으로 판단한다.

연습 2 · 오류 찾아 고치기

서브넷 A=10.20.4.0/25, B=10.20.4.64/26을 비중복 두 구역이라고 썼다. 전체 범위를 비교해 고쳐라.

힌트 1

A의 끝은 마지막 바이트 127이다.

힌트 2

B의 64개 주소가 A 안에 들어가는지 확인한다.

풀이와 답 확인

  1. A는 0..127의 128개다.

  2. B는 64..127의 64개로 A 안에 포함된다.

  3. 합집합은 128개이며 단순 합 192개는 중복을 센다.

두 구역은 64개가 겹친다. 일반 AWS의 서로 다른 서브넷 생성 계획으로는 비중복 조건을 충족하지 못한다.

흔한 오답에서 다시 생각하기

접두부 길이가 다르므로 서로 겹치지 않는다.

길이가 달라도 짧은 접두부가 긴 범위를 포함할 수 있다.

연습 3 · 직접 만들어 보기

VPC 10.20.0.0/16 안에서 두 가용영역에 일반 AWS IPv4 서브넷을 하나씩 두려 한다. 각 서브넷에서 미배정 주소 최소 120개가 필요하다. /25 또는 /26 중 최소 크기의 비중복 두 CIDR과 영역 배정을 제시하라. 추가 예약·사용은 없다.

힌트 1

/25의 예약 후 수는 128−5다.

힌트 2

주소 구역과 가용영역 배정을 모두 적는다.

풀이와 답 확인

  1. /26은 64−5=59개라 요구에 부족하다. /25는 123개라 충분하다.

  2. 10.20.6.0/25를 영역 Z1, 10.20.6.128/25를 영역 Z2에 배정하는 계획을 쓴다.

  3. 두 범위는 0..127과 128..255로 비중복이고 VPC 안이다.

각 123개의 조건부 여유를 가진 두 /25 계획이다. 생성이나 실제 AZ 자원 배정은 수행하지 않았다.

흔한 오답에서 다시 생각하기

/26 전체 64개를 두 영역에 합쳐 128개라 충분하다.

요구는 각 서브넷의 120개이며 예약 후 수로 비교해야 한다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

일반 AWS IPv4 /28 하나에 주소 10개를 이미 배정했다. 다른 사용·추가 예약은 없다. 전체·예약 후·남은 미배정 수를 계산하라.

힌트 1

자유 비트는 4개다.

힌트 2

전체에서 예약을 빼고 기존 배정도 뺀다.

풀이와 답 확인

  1. 전체는 16개다. 예약 후 배정 가능한 범위는 11개다.

  2. 이미 배정한 10개를 빼면 1개가 남는다.

전체 16개, 예약 후 11개, 미배정 1개다. 실제 콘솔의 현재 여유를 조회한 값은 아니다.

흔한 오답에서 다시 생각하기

16−10=6개가 남는다.

예약된 다섯 주소까지 새 자원에 줄 수 있다고 계산했다.

서브넷 주소를 정하면 인터넷 접속도 완료되는가?

설명 기준 확인

아니다. 경로·주소 연결·허용 정책·상대 서비스는 별도 조건이다.

한 단계 더

A/24를 0..127과 128..255의 두 /25로 나눠 주소 지도를 그리자. 총 크기는 128+128=256으로 보존된다. IPv6는 128비트와 다른 공급자 예약 규칙을 사용하므로 IPv4의 사용 가능 수 공식을 그대로 적용하지 않는다.

소단원 5.2

보안그룹·라우팅·NAT

요청을 허용했는데도 목적지에 도달하지 않는다면 어느 표를 따로 읽어야 할까?

준비 개념과 학습 목표

준비 개념

  • 라우팅 표는 목적지 주소에 따른 다음 경로를 정한다. 보안그룹은 관련 자원의 허용 트래픽을 정한다.

  • NAT는 주소 변환이며 기본 경로0.0.0.0/0은 모든 IPv4 목적지와 일치한다. longest prefix는 일치하는 가장 긴 접두부 선택이다.

학습 목표

  • 경로 선택과 허용 여부를 분리해 추적한다.

  • 내부 시작 NAT 통신과 응답 경로를 설명한다.

가는 길과 출입 허가는 어느 순서로 확인해야 할까요?

주소 지도의 길은 목적지에 맞는 경로를 고르고, 출입 규칙은 특정 방향·프로토콜·포트의 트래픽을 허용한다. 여기서는 둘을 별도 표로 계산한다. 표에 경로가 있어도 서비스가 실제 실행 중인지는 알 수 없다.

NAT 예는 주소와 포트 대응을 기억하는 자체 추상 상태표다. 문서용 외부 주소만 사용한다. AWS 공개 NAT에서는 NAT의 private 주소 변환 뒤 인터넷 게이트웨이가 Elastic IP로 바꾸는 단계가 있으므로 아래 한 단계 표를 실제 AWS 내부 구현과 같은 것으로 부르지 않는다.

먼저 확인할 개념
  • 보안그룹·라우팅·NAT

    최장 접두부·stateful 응답·내부 시작 연결을 구별한다.

  • 가상 네트워크·서브넷

    목적지의 주소 범위 포함을 경로 비교에 사용한다.

목적지에 맞는 가장 구체적인 길

모형의 표는 10.20.0.0/16→local,10.30.0.0/16→peer,0.0.0.0/0→NAT다. 10.30.2.8은 /16과 /0에 모두 맞지만 /16이 더 구체적이라 peer를 선택한다. 기본 경로가 표에 있다고 내부 주소까지 NAT로 보내지는 않는다.

같은 길이 또는 같은 목적지의 여러 경로에는 별도 우선순위 규칙이 필요하다. 이 예제는 그런 동률이 없어 접두부 길이만 사용한다. 선택한 경로가 존재하는 것과 실제 상대 서버가 응답하는 것은 다른 확인이다.

방향·프로토콜·포트를 확인한다

보안그룹은 source 또는 destination, protocol과 port 같은 조건의 허용 규칙을 확인한다. AWS 보안그룹은 stateful이라 허용된 요청의 응답을 그 연결 상태에 따라 허용한다. 이 기능을 서브넷 전체의 ACL이나 라우팅 표와 같은 것으로 부르지 않는다.

모형에서는 웹 서버의 TCP 443을 특정 출발 범위에 허용한다고 정한다. TCP 22는 다른 규칙이 없으면 새 요청으로 허용되지 않는다. 허용된 TCP 443 응답이라고 해서 같은 출발자의 모든 새 포트 요청까지 허용되는 것은 아니다. 애플리케이션 로그인·권한은 네트워크 허용과 별개다.

내부 시작 연결의 주소를 바꾼다

공개 NAT 경로를 쓰는 비공개 IPv4 자원은 내부에서 외부 연결을 시작하고 응답을 되돌려 받을 수 있다. 실제 AWS 공개 NAT의 경로에는 공개 NAT의 위치와 인터넷 게이트웨이 연결도 필요하다. 이름만 NAT라고 적고 나머지 경로가 있다고 가정하지 않는다.

NAT 상태의 주소·포트 대응은 어느 내부 연결로 응답을 보낼지 기억한다. 외부가 임의로 새 연결을 시작하여 내부 자원에 들어오는 것과 다르다. NAT는 애플리케이션 인증이나 모든 보안 규칙을 대신하는 도구가 아니며 아래 숫자는 추상 주소 변환 표다.

중간 과정을 따라가는 예제

위 라우팅 표에서 목적지 10.20.9.9,10.30.2.8,203.0.113.9의 경로를 고르라. 별도 NAT 모형이 10.20.2.7:50000→198.51.100.5:61000으로 출발을 바꿨다면 대응 응답은 어디로 돌아오는가?

  1. 10.20.9.9는 local /16과 기본/0 중 local을 고른다.

  2. 10.30.2.8은peer /16을 고른다. 외부 203.0.113.9는 두 /16에 없어 기본 NAT다.

  3. 추상 NAT는 외부에 보이는 출발 198.51.100.5:61000과 내부 10.20.2.7:50000의 대응을 저장한다.

  4. 그 허용 연결의 응답은 대응을 이용하여 내부 10.20.2.7:50000으로 복원한다. 예제의 외부 두 범위는 문서용 주소이며 실제 인터넷 서비스를 만들지 않았다.

경로는 local/peer/NAT이며 응답 대상은 원래 내부 주소·포트다.

조건을 바꾸어 비교하기

겹치는 범위에서 긴 접두부

표에서 10.20.4.7, 10.20.5.7, 203.0.113.7의 선택을 구하라.

  1. 첫 목적지는 /24, /16, /0 모두 맞아 /24의 F를 선택한다.

  2. 두 번째는 /16과 /0만 맞아 local을 고른다.

  3. 세 번째는 /0만 맞아 NAT 경로다.

각각 F, local, NAT 경로다. F의 정상 동작이나 외부 연결 성공은 이 표로 검증되지 않았다.

비교할 점

기본 예제의 분리된 두 /16에 더 구체적인 내부 경로를 추가한다.

서로 다른 내부 연결의 응답 복원

추상 NAT는 A의 10.20.2.7:50000을 198.51.100.5:61000으로, B의 10.20.2.8:50000을 같은 외부 주소의 61001로 바꾼다. 두 연결은 같은 외부 서버로 향하며 표가 유효하다. 61001로 온 대응 응답은 어디로 복원되는가?

  1. 내부 출발 포트가 같아도 두 IP가 다르므로 별도 연결이다.

  2. 외부 대응 포트 61001은 B 행과 연결된다.

  3. 응답을 B의 10.20.2.8:50000으로 복원한다.

B로 복원한다. 유효한 대응 응답이라는 조건이 있으며 임의 새 외부 연결을 허용하는 표가 아니다.

오해와 반례

NAT를 추가하면 외부의 모든 새 요청을 내부 서버가 받을 수 있고 라우팅·보안규칙은 필요 없다.

공개 NAT의 내부 시작 연결·응답 복원과 외부 새 연결은 다르다. 경로 선택과 허용 규칙도 별도다. /16 내부 목적지는 기본 NAT보다 local 경로가 먼저 선택된다.

연습 1 · 값과 상태 예측

새 TCP 요청의 inbound 규칙은 10.20.4.0/25에서 오는 443만 허용하며 다른 허용 규칙은 없다. A=10.20.4.127→443, B=10.20.4.128→443, C=10.20.4.8→22를 판정하라. 별도 경로는 확보되어 있다.

힌트 1

/25의 마지막 바이트 범위는 0..127이다.

힌트 2

주소와 포트를 동시에 맞춘다.

풀이와 답 확인

  1. A는 범위와 포트가 모두 맞는다.

  2. B는 출발 주소 범위 밖이다.

  3. C는 출발 주소는 맞지만 포트가 다르다.

A만 해당 네트워크 규칙으로 허용된다. 앱 로그인이나 실제 응답 성공은 별도다.

같은 10.20.4 접두부이므로 B도 허용이다.

/25에는 마지막 바이트의 상위 비트 조건도 있다.

연습 2 · 오류 찾아 고치기

허용된 inbound TCP 443 연결의 응답이 나갔으므로 같은 출발자의 새 TCP 22 요청도 허용된다고 썼다. AWS 보안그룹의 stateful 성질로 설명을 고쳐라.

힌트 1

응답과 새 연결은 다른 트래픽이다.

힌트 2

stateful 응답 허용 범위를 원래 연결에 연결한다.

풀이와 답 확인

  1. 허용된 연결의 응답은 연결 상태에 따라 허용된다.

  2. 새 22 요청은 inbound 허용 규칙으로 별도 판정한다.

  3. 443 규칙만 있다면 새 22 요청은 그 규칙에 맞지 않는다.

원래 응답의 허용을 모든 새 포트의 허용으로 확대할 수 없다. 다른 ACL·경로·서버 조건은 이 문제에서 검사하지 않았다.

연습 3 · 직접 만들어 보기

비공개 IPv4 앱이 외부 문서 서버에 연결을 시작하도록 AWS 공개 NAT 경로 계획을 그려라. 앱에는 직접 공인 IP가 없다고 하며 비용·생성·실제 통신은 수행하지 않는다.

힌트 1

앱 서브넷의 기본 경로와 NAT 쪽 인터넷 경로를 따로 그린다.

힌트 2

반환 트래픽과 새 외부 연결을 구별한다.

풀이와 답 확인

  1. 앱 서브넷의 기본 경로를 공개 NAT 쪽으로 계획한다.

  2. 공개 NAT의 공개 서브넷·Elastic IP 및 인터넷 게이트웨이 경로를 계획에 표시한다.

  3. 앱의 출발 허용과 필요한 관련 정책을 확인 목록에 적는다.

  4. 유효 연결의 응답 복원 경로를 그리되 새 외부 시작 연결 허용을 주장하지 않는다.

앱→공개 NAT→인터넷 게이트웨이→외부 서버와 대응 응답의 계획이다. 각 실제 생성·상태 검사는 미수행이다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

NAT 대응 후보가 A와 B의 서로 다른 내부 연결을 같은 외부 주소·포트 및 동일한 외부 상대와 프로토콜로 동시에 표시한다. 반환 패킷에 A/B 식별 정보가 더 없다는 추상 모형에서 무엇이 부족한가?

힌트 1

밖에서 보이는 대응 키가 완전히 같은지 확인한다.

힌트 2

반환할 내부 대상이 유일해야 한다.

풀이와 답 확인

  1. 두 행의 외부 연결 키가 같아 반환 패킷은 두 행과 모두 맞는다.

  2. 추가 식별 정보가 없는 모형에서는 A와 B 중 유일한 대상이 정해지지 않는다.

  3. 다른 외부 포트 등 구별되는 대응을 배정하거나 해당 동시 대응을 허용하지 않는 정책이 필요하다.

응답 복원의 유일성 조건이 부족하다. 실제 NAT가 충돌 대응을 설치한다는 주장이나 제품 결함 증거가 아니다.

공개 NAT의 Elastic IP 변환을 누가 수행하는가?

설명 기준 확인

AWS 문서 조건에서는 NAT의 private 주소 변환과 인터넷 게이트웨이의 Elastic IP 변환을 나누어 설명한다.

한 단계 더

출발→허용 검사→경로→변환→외부→응답의 두 방향 화살표를 그리자. 실제 공급자의 주소 변환 단계와 프로토콜 예외는 문서로 따로 확인한다. 종이 표의 허용·주소 대응을 패킷 캡처나 클라우드 배포 검증으로 표시하지 않는다.

출처와 확인 범위
  • AWS VPC: Route priority

  • AWS VPC: Security groups

소단원 5.3

로드밸런싱·SDN

요청을 어느 서버로 보낼지 정하는 규칙과 패킷을 실제 전달하는 일을 나눌 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 로드밸런서는 받은 요청을 대상 서버에 나누는 구성요소다. listener는 받는 프로토콜·포트, health check는 대상의 상태 검사다.

  • SDN은 네트워크 제어 논리와 패킷 전달을 구분하는 설계다. flow의 match는 일치 조건, action은 그 패킷에 할 동작이다.

학습 목표

  • 자체 round robin 표와 장애 후 재배정을 계산한다.

  • 제어·전달 역할과 flow 규칙을 연결한다.

남은 요청을 다시 나누면 진행 중인 일까지 되돌릴까요?

요청을 보낼 후보 목록과 이미 배정한 작업의 상태는 다르다. 이 모형은 건강한 대상으로 새 요청을 round robin 배정하고, 후보가 바뀔 때 다음 순서를 명시한다. 실제 제품의 기본 알고리즘이나 장애 처리 결과를 재현한 표가 아니다.

flow 표에서는 match와 priority로 행을 골라 action을 적용한다. 규칙이 유효한 시간도 조건으로 쓴다. 컨트롤러와의 연결이 끊겼다는 사실만으로 기존 규칙의 만료·삭제·유지가 정해졌다고 보지 않는다. 아래 시간·비용·배정은 모두 자체 가상값이다.

먼저 확인할 개념
  • 로드밸런싱·SDN

    요청 수와 일량 및 제어·전달의 분리를 사용한다.

  • 보안그룹·라우팅·NAT

    flow priority와 경로 최장 접두부가 다른 선택 기준임을 연결한다.

요청 분산은 계산량 균등과 다르다

이 모형은 건강한 대상 A,B,C에 요청을 순서대로 한 번씩 보내는 round robin이다. 요청 6개면 각 2개다. 요청의 실제 실행량이 모두 같다는 가정은 없으므로 요청 수가 같다고 CPU 부하까지 같아지는 것은 아니다. 연결 유지나 세션·알고리즘 선택에 따라 다른 정책도 가능하다.

health check에 의해 대상으로 제외된 B는 다음 새 요청의 후보에서 뺀다고 정한다. 실제 검사에는 주기와 감지 지연이 있고 이미 처리 중인 요청의 결과는 따로다. 특정 공급자의 모든 대상 실패 예외나 기존 연결 처리를 이 작은 정책표로 설명했다고 주장하지 않는다.

규칙을 정하는 곳과 적용하는 곳

OpenFlow 예제에서 컨트롤러는 match·action 규칙을 설치하고 스위치는 표를 참조하여 패킷을 전달한다. 미일치 패킷을 컨트롤러에 보내는 Packet-In 등으로 새 규칙을 배울 수 있다. 모든 패킷이 반드시 컨트롤러를 왕복한다고 생각하지 않는다. 설치된 규칙에 맞는 패킷은 스위치에서 처리할 수 있다.

SDN이라는 말은 로드밸런서와 동의어가 아니다. 로드밸런싱 정책을 네트워크 제어로 구현할 수는 있지만 범위가 다르다. 논리적 제어 분리는 실제로 컨트롤러가 한 대만 있다는 뜻도 아니다. 아래는 작은 flow 표이며 실제 Ryu·스위치를 실행하지 않았다.

동률과 미일치 정책을 명시한다

flow 표의 높은 priority를 먼저 적용하는 자체 규칙을 쓰자. priority 10의 dst=B→port2와 priority 0의 모든 패킷→controller가 있다면 B 행이 먼저 선택된다. 경로표의 최장 접두부 규칙과 flow의 명시적 priority는 서로 다른 선택 기준이다.

컨트롤러·규칙 전파·상태 검사가 실패할 때 어떤 규칙이 남는지는 구현 정책에 달린다. 기존 규칙을 유지할지 닫을지까지 단어 SDN만으로 정할 수 없다. 제어 정책을 종이에 적는 것과 실제 지연·가용성·수신 결과를 검증하는 것을 구별한다.

연습 1 · 값과 상태 예측

건강한 A와 B에 A부터 요청 네 개를 round robin 배정한다. 비용은 순서대로 9,1,1,9 ms CPU이고 각 서버에서 직렬로 처리할 총 일량만 합친다. 대상별 요청 수와 CPU 일량을 계산하라.

힌트 1

배정은 A,B,A,B다.

힌트 2

각 대상의 첫·다음 비용을 합친다.

풀이와 답 확인

  1. A는 9+1=10 ms, B는 1+9=10 ms이며 각각 두 요청이다.

연습 3 · 직접 만들어 보기

힌트 1

구체 match는 B와 C를 나눈다.

힌트 2

풀이와 답 확인

  1. priority 10: dst=B→port2를 둔다.

  2. priority 10: dst=C→port3을 둔다.

  3. priority 0: any→controller를 둔다.

  4. D는 구체 행에 맞지 않아 controller를 선택한다.

any 행도 10이면 구체성이 자동 우선이다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

t=12초에 컨트롤러 연결이 끊기지만 설치 규칙과 스위치는 정상이라고 가정한다. 위 hard timeout 규칙은 15초부터 제거되고 기본 controller 행은 유지된다. 14초와 16초의 dst=B에 대해 표 선택과 최종 성공을 구별하라.

힌트 1

연결 단절과 이미 설치한 규칙의 유효성을 나눈다.

힌트 2

controller action 선택이 controller 수신 성공을 뜻하지 않는다.

풀이와 답 확인

  1. 14초에는 유효한 높은 행이 있어 port2 action을 선택한다.

  2. 16초에는 높은 행이 만료되어 controller action을 선택한다.

  3. 연결 단절 때문에 16초의 controller 수신은 이 조건으로 성공을 보장할 수 없다. 14초의 최종 목적지 수신도 별도 관찰이 없다.

선택은 port2와 controller로 다르다. 두 시각의 실제 목적지 성공은 측정하지 않았다.

다른 문제에 적용하기

온라인 수업 주소·연결·분산의 종이 설계

VPC 10.20.0.0/16 안에 Z1=10.20.6.0/25, Z2=10.20.6.128/25를 둔다. 일반 AWS IPv4 예약 규칙이며 각 서브넷에 주소 100개를 이미 배정했고 추가 예약은 없다. 남은 주소 수를 각각 구하라. 서버 inbound는 Z1 출발 TCP 443만 허용하고 다른 규칙은 없다. 필요한 경로가 확보된 새 요청 10.20.6.140→443을 판정하라. 별도 추상 NAT 표에서 내부 두 연결이 서로 다른 외부 포트 61000과 61001을 가지며 대응이 유효하다면 응답 복원의 근거는 무엇인가? 마지막으로 건강한 A,B에 A부터 네 요청을 보내고 CPU 비용은 6,2,6,2 ms다. 대상별 수와 일량을 비교하라. 실제 클라우드 설정은 수행하지 않는다.

힌트 1

각 /25의 전체 수에서 예약과 기존 배정을 뺀다.

힌트 2

출발 구역·새 요청 허용·NAT 대응·요청 일량을 다른 기준으로 판단한다.

풀이와 답 확인

  1. 각 /25는 128개이며 예약 5개와 기존 배정 100개를 빼면 각 23개가 남는다.

  2. 140은 Z2 범위라 Z1만 허용하는 inbound 규칙에 맞지 않는다.

  3. 외부 포트가 다르므로 같은 상대·프로토콜이라는 조건에서도 대응 키로 내부 연결을 구분할 수 있다.

  4. 배정은 A,B,A,B여서 각 두 요청이다. CPU 일량은 A가 12 ms, B가 4 ms다.

두 서브넷의 미배정 여유는 각각 23개다. 새 140→443 요청은 주어진 inbound 규칙으로 허용되지 않는다. 유효 NAT 표는 구별되는 외부 포트로 대응 응답을 원래 내부 연결에 복원한다. 요청 수는 각 2개지만 CPU 일량은 12 ms와 4 ms로 다르다. 실제 전달·로그인·완료시간은 확인하지 않았다.

해결한 뒤 점검할 것

  • 전체·예약·기존 배정 수를 구별한다.

  • /25 경계와 출발 주소 포함을 확인한다.

  • 대응 응답과 임의 새 외부 요청을 구별한다.

  • 요청 개수와 CPU 일량의 단위를 분리한다.
