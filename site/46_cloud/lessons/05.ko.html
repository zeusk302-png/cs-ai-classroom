소단원 5.1

가상 네트워크·서브넷

멀리 있는 가상 컴퓨터들도 같은 주소 공간 안에서 묶어 관리할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • IPv4는 32비트 주소다. CIDR의 /p는 앞 p비트를 공통 접두부로 사용한다.

  • VPC는 클라우드의 논리적 네트워크 영역이며 서브넷은 그 안의 더 작은 주소 범위다. 가용영역은 물리 장애를 구분하는 배치 범위다.

학습 목표

  • CIDR 범위를 나누고 포함·겹침을 판정한다.

  • 주소 범위·배치·인터넷 경로의 역할을 구별한다.

주소 공간을 잘라 이름을 붙인다

10.20.0.0/16은 앞 두 바이트가 10과 20인 주소 범위다. 이를 10.20.1.0/24,10.20.2.0/24처럼 나누면 각 범위의 마지막 바이트가 0..255다. 실제 자원이 사용할 주소는 해당 범위와 서비스 예약 규칙에 맞아야 한다.

/24의 전체 수는 2^(32−24)=256이다. 이를 그대로 가상 컴퓨터 256대의 사용 가능 수라고 말하지 않는다. 공급자가 일부 주소를 예약할 수 있고 이미 배정된 주소도 있기 때문이다. 여기서는 사용 가능 수가 아닌 전체 범위의 크기를 계산한다.

논리 주소와 물리 배치를 함께 적는다

가상 네트워크는 주소와 접속 정책을 논리적으로 표현한다. AWS의 서브넷은 한 가용영역 안에 있으며 영역을 가로지르지 않는다. 두 영역에 서비스를 배치하려면 각 영역의 서브넷과 그 사이 경로를 별도로 계획한다. 다른 공급자의 세부 제약은 해당 문서에서 확인해야 한다.

같은 VPC라는 사실은 모든 요청이 자동 성공한다는 뜻이 아니다. 경로·보안 정책·서버 수신 상태가 함께 맞아야 한다. 주소가 겹치는 별도 네트워크를 연결하면 목적지를 구분하기 어려울 수 있어 연결 전에 범위를 검사한다.

공개라는 이름의 조건을 살핀다

공개 서브넷과 비공개 서브넷의 구별은 숫자가 10으로 시작하는지보다 외부로 향하는 경로 설정과 연결 방식에 달린다. AWS의 공개 서브넷은 인터넷 게이트웨이로 직접 가는 경로를 갖는다. IPv4 자원 자체의 공인 주소와 허용 정책도 실제 인터넷 통신에 필요하다.

따라서 공개 경로가 있다고 모든 자원에 공인 주소가 자동 붙거나 모든 포트가 열리는 것은 아니다. 비공개 자원의 외부 시작 통신은 NAT 등 별도 경로로 계획할 수 있다. 이 단원은 종이 주소 지도이며 클라우드 콘솔을 설정한 결과가 아니다.

중간 과정을 따라가는 예제

VPC 10.20.0.0/16 안에서 A 10.20.1.0/24,B 10.20.2.0/24를 만든다. 각 전체 주소 수, 겹침 여부,10.20.1.200과 10.21.1.2의 포함을 판정하라.

  1. 각 /24에는 마지막 8비트가 자유라 256개다. 두 범위 전체는 512개다.

  2. A의 범위 10.20.1.0..255와 B의 10.20.2.0..255는 세 번째 바이트가 달라 겹치지 않는다.

  3. 10.20.1.200은 A와 VPC에 포함되며 B에는 없다.

  4. 10.21.1.2는 두 번째 바이트 21이 VPC 접두부 20과 달라 VPC 밖이다.

A,B는 겹치지 않는 256개 범위이며 전체 512개다. 사용 가능한 인스턴스 수와 구별한다.

종이와 본문으로 직접 해보기

10.20.1.128/25는 A와 겹치는가? 그 전체 주소 수와 첫·끝 주소를 적어라.

힌트 보기

마지막 바이트의 상위 1비트가 1인 범위를 찾는다.

풀이 보기

오해와 반례

서브넷이 공개이면 그 안 모든 컴퓨터가 누구에게나 모든 포트를 연다.

공개 경로는 접근의 한 조건이다. 공인 주소·보안 규칙·수신 서비스가 별도이며 /24 수 256도 실제 배정 가능 수를 뜻하지 않는다.

한 단계 더

A/24를 0..127과 128..255의 두 /25로 나눠 주소 지도를 그리자. 총 크기는 128+128=256으로 보존된다. IPv6는 128비트와 다른 공급자 예약 규칙을 사용하므로 IPv4의 사용 가능 수 공식을 그대로 적용하지 않는다.

소단원 5.2

보안그룹·라우팅·NAT

요청을 허용했는데도 목적지에 도달하지 않는다면 어느 표를 따로 읽어야 할까?

준비 개념과 학습 목표

준비 개념

  • 라우팅 표는 목적지 주소에 따른 다음 경로를 정한다. 보안그룹은 관련 자원의 허용 트래픽을 정한다.

  • NAT는 주소 변환이며 기본 경로0.0.0.0/0은 모든 IPv4 목적지와 일치한다. longest prefix는 일치하는 가장 긴 접두부 선택이다.

학습 목표

  • 경로 선택과 허용 여부를 분리해 추적한다.

  • 내부 시작 NAT 통신과 응답 경로를 설명한다.

목적지에 맞는 가장 구체적인 길

모형의 표는 10.20.0.0/16→local,10.30.0.0/16→peer,0.0.0.0/0→NAT다. 10.30.2.8은 /16과 /0에 모두 맞지만 /16이 더 구체적이라 peer를 선택한다. 기본 경로가 표에 있다고 내부 주소까지 NAT로 보내지는 않는다.

같은 길이 또는 같은 목적지의 여러 경로에는 별도 우선순위 규칙이 필요하다. 이 예제는 그런 동률이 없어 접두부 길이만 사용한다. 선택한 경로가 존재하는 것과 실제 상대 서버가 응답하는 것은 다른 확인이다.

방향·프로토콜·포트를 확인한다

보안그룹은 source 또는 destination, protocol과 port 같은 조건의 허용 규칙을 확인한다. AWS 보안그룹은 stateful이라 허용된 요청의 응답을 그 연결 상태에 따라 허용한다. 이 기능을 서브넷 전체의 ACL이나 라우팅 표와 같은 것으로 부르지 않는다.

모형에서는 웹 서버의 TCP 443을 특정 출발 범위에 허용한다고 정한다. TCP 22는 다른 규칙이 없으면 새 요청으로 허용되지 않는다. 허용된 TCP 443 응답이라고 해서 같은 출발자의 모든 새 포트 요청까지 허용되는 것은 아니다. 애플리케이션 로그인·권한은 네트워크 허용과 별개다.

내부 시작 연결의 주소를 바꾼다

공개 NAT 경로를 쓰는 비공개 IPv4 자원은 내부에서 외부 연결을 시작하고 응답을 되돌려 받을 수 있다. 실제 AWS 공개 NAT의 경로에는 공개 NAT의 위치와 인터넷 게이트웨이 연결도 필요하다. 이름만 NAT라고 적고 나머지 경로가 있다고 가정하지 않는다.

NAT 상태의 주소·포트 대응은 어느 내부 연결로 응답을 보낼지 기억한다. 외부가 임의로 새 연결을 시작하여 내부 자원에 들어오는 것과 다르다. NAT는 애플리케이션 인증이나 모든 보안 규칙을 대신하는 도구가 아니며 아래 숫자는 추상 주소 변환 표다.

중간 과정을 따라가는 예제

위 라우팅 표에서 목적지 10.20.9.9,10.30.2.8,203.0.113.9의 경로를 고르라. 별도 NAT 모형이 10.20.2.7:50000→198.51.100.5:61000으로 출발을 바꿨다면 대응 응답은 어디로 돌아오는가?

  1. 10.20.9.9는 local /16과 기본/0 중 local을 고른다.

  2. 10.30.2.8은peer /16을 고른다. 외부 203.0.113.9는 두 /16에 없어 기본 NAT다.

  3. 추상 NAT는 외부에 보이는 출발 198.51.100.5:61000과 내부 10.20.2.7:50000의 대응을 저장한다.

  4. 그 허용 연결의 응답은 대응을 이용하여 내부 10.20.2.7:50000으로 복원한다. 예제의 외부 두 범위는 문서용 주소이며 실제 인터넷 서비스를 만들지 않았다.

경로는 local/peer/NAT이며 응답 대상은 원래 내부 주소·포트다.

종이와 본문으로 직접 해보기

TCP 443을 10.20.1.0/24에서만 새 요청으로 허용하고 다른 inbound 허용 규칙은 없다고 하자.10.20.1.8→443,10.20.2.8→443,10.20.1.8→22를 판정하라. 경로는 모두 따로 확보되었다고 가정한다.

힌트 보기

출발 범위와 TCP 포트를 동시에 검사한다.

풀이 보기

첫 요청만 이 규칙으로 허용된다. 둘째는 출발 범위, 셋째는 포트가 다르다. 허용은 경로 확보를 전제한 네트워크 조건이며 서버 실제 응답 성공을 측정한 것이 아니다.

오해와 반례

NAT를 추가하면 외부의 모든 새 요청을 내부 서버가 받을 수 있고 라우팅·보안규칙은 필요 없다.

공개 NAT의 내부 시작 연결·응답 복원과 외부 새 연결은 다르다. 경로 선택과 허용 규칙도 별도다. /16 내부 목적지는 기본 NAT보다 local 경로가 먼저 선택된다.

소단원 5.3

로드밸런싱·SDN

요청을 어느 서버로 보낼지 정하는 규칙과 패킷을 실제 전달하는 일을 나눌 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 로드밸런서는 받은 요청을 대상 서버에 나누는 구성요소다. listener는 받는 프로토콜·포트, health check는 대상의 상태 검사다.

  • SDN은 네트워크 제어 논리와 패킷 전달을 구분하는 설계다. flow의 match는 일치 조건, action은 그 패킷에 할 동작이다.

학습 목표

  • 자체 round robin 표와 장애 후 재배정을 계산한다.

  • 제어·전달 역할과 flow 규칙을 연결한다.

요청 분산은 계산량 균등과 다르다

이 모형은 건강한 대상 A,B,C에 요청을 순서대로 한 번씩 보내는 round robin이다. 요청 6개면 각 2개다. 요청의 실제 실행량이 모두 같다는 가정은 없으므로 요청 수가 같다고 CPU 부하까지 같아지는 것은 아니다. 연결 유지나 세션·알고리즘 선택에 따라 다른 정책도 가능하다.

health check에 의해 대상으로 제외된 B는 다음 새 요청의 후보에서 뺀다고 정한다. 실제 검사에는 주기와 감지 지연이 있고 이미 처리 중인 요청의 결과는 따로다. 특정 공급자의 모든 대상 실패 예외나 기존 연결 처리를 이 작은 정책표로 설명했다고 주장하지 않는다.

규칙을 정하는 곳과 적용하는 곳

OpenFlow 예제에서 컨트롤러는 match·action 규칙을 설치하고 스위치는 표를 참조하여 패킷을 전달한다. 미일치 패킷을 컨트롤러에 보내는 Packet-In 등으로 새 규칙을 배울 수 있다. 모든 패킷이 반드시 컨트롤러를 왕복한다고 생각하지 않는다. 설치된 규칙에 맞는 패킷은 스위치에서 처리할 수 있다.

SDN이라는 말은 로드밸런서와 동의어가 아니다. 로드밸런싱 정책을 네트워크 제어로 구현할 수는 있지만 범위가 다르다. 논리적 제어 분리는 실제로 컨트롤러가 한 대만 있다는 뜻도 아니다. 아래는 작은 flow 표이며 실제 Ryu·스위치를 실행하지 않았다.

동률과 미일치 정책을 명시한다

flow 표의 높은 priority를 먼저 적용하는 자체 규칙을 쓰자. priority 10의 dst=B→port2와 priority 0의 모든 패킷→controller가 있다면 B 행이 먼저 선택된다. 경로표의 최장 접두부 규칙과 flow의 명시적 priority는 서로 다른 선택 기준이다.

컨트롤러·규칙 전파·상태 검사가 실패할 때 어떤 규칙이 남는지는 구현 정책에 달린다. 기존 규칙을 유지할지 닫을지까지 단어 SDN만으로 정할 수 없다. 제어 정책을 종이에 적는 것과 실제 지연·가용성·수신 결과를 검증하는 것을 구별한다.

중간 과정을 따라가는 예제

건강한 A,B,C에 round robin으로 1..6번 요청을 보내고,그 뒤 B를 제외하고 순서를 A부터 새로 시작하여 7..10을 보내라. 각 요청의 대상과 누적 개수를 구하라.

  1. 1..6은 A,B,C,A,B,C라 각 2개다.

  2. B 제외 후 7..10은 A,C,A,C다. 기존 요청은 다시 보내지 않는다.

  3. 누적 A4/B2/C4이며 새 요청 4개는 A2/C2다.

  4. 이 표는 B 장애 후 기존 두 요청의 성공 여부를 정하지 않으며 실제 부하균등도 측정하지 않았다.

누적 요청 수 A4/B2/C4다. 제외는 새 요청 후보만 바꾼다.

오해와 반례

요청을 같은 개수로 나누면 서버 부하도 같고 SDN에서는 모든 패킷이 컨트롤러를 통과한다.

A의 요청 하나가 100시간이고 C의 요청이 1시간이면 요청 수만 같아도 부하가 다르다. 설치된 flow 규칙과 맞는 패킷은 스위치에서 직접 전달할 수 있다. 두 주장을 각 반례로 구별한다.
