소단원 9.1

스케줄링·서비스 발견

Pod가 옮겨 다니는데 사용자는 어디로 접속할까?

준비 개념과 학습 목표

준비 개념

  • Pod는 하나 이상의 컨테이너를 묶는 실행 단위다.

  • CPU와 메모리는 서로 다른 자원이다.

학습 목표

  • 가능한 노드와 선호하는 노드를 구별한다.

  • 서비스 이름과 실제 Pod 주소의 관계를 설명한다.

점수가 가장 높은 노드가 메모리 조건을 못 맞춰도 선택될까요?

배치 가능한 후보를 남기는 filtering과 후보의 선호도를 비교하는 scoring을 단계별로 계산합니다. 아래 숫자는 자체 예입니다. 새 Pod의 request는 CPU 500m·메모리 384Mi이며 반드시 east 영역에 배치한다고 정합니다. 노드의 여유는 현재 사용량이 아니라 추가 request를 수용할 수 있는 양입니다. 다른 affinity·taint·볼륨 조건은 없다고 가정합니다. 높은 점수라도 필수 조건을 통과하지 못하면 후보가 아닙니다.

접속 후보도 주소를 단순히 세는 것으로 정해지지 않습니다. 기본 publishNotReadyAddresses=false에서는 serving이고 terminating이 아닌 조건이 ready를 요약합니다. 종료 중인 대상을 이용하는 프록시 예외는 별도로 봐야 합니다. 여러 EndpointSlice에 같은 주소가 잠시 중복될 수도 있으므로 전체 고유 접점을 만든 뒤 상태를 확인합니다. 아래 신규 요청 후보 모형은 종료 중 대상을 제외하며 실제 프록시의 모든 정책을 재현하지 않습니다.

먼저 확인할 개념
  • 스케줄링·서비스 발견

    기본 자원 판단에 필수 영역 조건과 선호 점수를 추가합니다.

  • autoscaling·health check

    확장 요청, 노드 배치, 준비된 트래픽 후보가 서로 다른 단계임을 연결합니다.

먼저 들어갈 수 있는 곳 찾기

kube-scheduler는 아직 노드가 정해지지 않은 Pod의 배치를 결정한다. filtering은 자원과 배치 조건 등을 만족하는 노드만 남긴다. 남는 노드가 없으면 그 순간에는 스케줄링할 수 없고, CPU가 많이 남는다는 이유만으로 메모리 부족을 무시하지 않는다.

여기서 자원 판단은 Pod의 requests와 노드의 할당 가능한 자원에 관한 것이다. 실제 사용량이 작아 보이는 것과 새 요청을 수용할 수 있는 것은 다르다. 실제 클러스터에는 affinity, taint, 볼륨 등의 조건도 있으므로 자원 두 개만 계산한 예제는 축소 모형이다.

가능한 후보 사이의 선택

scoring은 filtering을 통과한 후보의 선호도를 비교한다. 공식 문서는 설정된 점수 기준에 따라 높은 점수의 노드를 선택하고 최고점 동률이면 임의 선택한다고 설명한다. 가장 여유 있는 CPU 하나만 보는 규칙으로 일반화하지 않는다.

스케줄링과 컨테이너의 성공적 실행도 구별한다. 배치된 뒤 이미지 다운로드나 설정 오류로 실행이 실패할 수 있다. 배치가 실패하면 이벤트와 조건을 확인하고, 무작정 복제본 수를 늘리기보다 부족한 자원이 무엇인지 살핀다.

바뀌는 Pod 뒤의 안정적인 접점

일반 ClusterIP Service는 선택자와 맞는 Pod들의 EndpointSlice를 통해 접점을 제공한다. Pod의 IP가 바뀌어도 클라이언트는 서비스 이름을 사용할 수 있다. 일반 서비스 DNS는 ClusterIP를 가리키며 headless Service의 DNS 동작은 다르다.

접속 후보에는 readiness와 종료 상태도 영향을 준다. 아래 예제는 종료 중인 Pod가 없고 publishNotReadyAddresses가 false인 보통의 서비스를 가정한다. readiness는 트래픽을 받을 준비 상태이며, 이름이 조회된다는 사실만으로 모든 요청이 성공하는 것은 아니다.

중간 과정을 따라가는 예제

다른 배치 조건은 없다고 하자. 노드 A의 남은 요청 수용량은 CPU 750m·메모리 512Mi, B는 1500m·256Mi다. 새 Pod의 request는 500m·384Mi다. Service 선택자는 app=classroom이며 p1은 일치·Ready, p2는 일치·NotReady, p3은 다른 label·Ready다.

  1. A는 750≥500과 512≥384를 모두 만족한다. B는 CPU는 충분하지만 256<384이므로 탈락한다.

  2. A에 배치하면 남은 양은 250m·128Mi다. 같은 요청의 두 번째 Pod는 A에도 B에도 배치할 수 없다.

  3. 기본 readiness 조건에서 서비스의 준비된 후보는 p1 하나다. p2가 Ready가 되면 두 개이고 p3은 선택자 불일치로 제외된다.

첫 Pod는 A만 후보이며, 같은 크기의 두 번째 Pod는 현재 자원으로 배치할 수 없다. 기본 서비스의 준비된 후보 수는 1에서 2로 늘어난다.

조건을 바꾸어 비교하기

후보가 하나인 경우와 둘인 경우

표의 request 500m·384Mi를 먼저 배치하고, 별도 사례로 메모리 request만 192Mi로 바꾸세요. 새 사례의 자체 점수는 자원 점수 A=90·B=40, 분산 점수 A=20·B=80이며 가중치는 각각 1과 2입니다. 다른 점수는 없습니다.

  1. 원래 request에서는 A만 남습니다. B는 메모리, C는 필수 영역 조건에서 탈락합니다.

  2. 별도 사례의 192Mi request에서는 A와 B가 모두 후보이며 C는 여전히 탈락합니다.

  3. 자체 합산 점수는 A=90+2×20=130, B=40+2×80=200입니다.

  4. B를 선택합니다. 이 점수 식은 학습용 설정이며 기본 Kubernetes 점수 설정이라고 주장하지 않습니다.

원래 사례는 A, 메모리 192Mi와 자체 가중 점수 사례는 B입니다.

비교할 점

최고 CPU 여유나 단일 점수만 보지 않습니다. 첫 배치가 완료된 자원을 이어 쓰는 사례가 아니라 원래 표에서 독립적으로 비교하는 사례입니다.

주소가 세 행에 있어도 접점은 두 개

자체 Slice S1에는 e1=10.0.0.1:80과 e2=10.0.0.2:80, S2에는 e1이 다시 있습니다. e1은 serving=true·terminating=false, e2는 serving=true·terminating=true입니다. 주소와 포트·프로토콜로 중복을 합치고 종료 중 대상을 제외하는 신규 요청 후보 수를 구하세요. publishNotReadyAddresses=false입니다.

  1. 원시 행 수는 3이지만 e1 두 행은 같은 접점이므로 고유 접점은 2개입니다.

  2. e1은 serving이고 종료 중이 아니므로 ready=true입니다.

  3. e2는 serving이지만 종료 중이므로 기본 ready=false입니다.

  4. 자체 신규 요청 후보 집합은 {e1}입니다. 모든 접점이 종료 중일 때 일부 프록시가 serving인 종료 대상을 이용할 수 있는 예외는 이 집합 규칙과 별도입니다.

고유 접점 2개, 이 모형의 신규 요청 후보 1개입니다.

비교할 점

종료 중인 프로세스가 이미 처리하는 요청까지 즉시 사라졌다고 말하지 않습니다. 실제 EndpointSlice나 프록시를 실행한 결과도 아닙니다.

연습 1 · 값과 상태 예측

원래 표에서 A에 500m·384Mi Pod 하나를 배치합니다. 같은 필수 조건의 두 번째 Pod를 배치할 후보가 있나요? 다른 자원 변화는 없습니다.

힌트 1

첫 배치 후 A의 남은 request 수용량을 뺍니다.

힌트 2

B의 메모리와 C의 필수 영역 조건도 다시 확인합니다.

풀이와 답 확인

  1. A의 남은 양은 250m·128Mi입니다.

  2. A는 두 번째 요청을 만족하지 못하며 B는 256Mi로 메모리가 부족합니다.

  3. C는 west라 필수 east 조건을 만족하지 못합니다.

현재 조건에서는 두 번째 Pod의 후보가 없습니다.

흔한 오답에서 다시 생각하기

첫 Pod가 성공했으니 두 번째도 같은 노드에 들어간다.

자원 수용량은 첫 요청만큼 줄어듭니다. 반복할 때마다 현재 남은 양을 계산하세요.

연습 2 · 오류 찾아 고치기

B의 선호 점수가 999라며 원래 384Mi request를 B에 넣자고 합니다. filtering과 scoring 순서로 고치세요.

힌트 1

B의 남은 메모리는 256Mi입니다.

힌트 2

점수는 통과한 후보들 사이에서만 비교합니다.

풀이와 답 확인

  1. 256<384라 B는 filtering에서 탈락합니다.

  2. C도 필수 영역 조건에서 탈락합니다.

  3. A만 후보이므로 점수 999는 선택 근거가 되지 않습니다.

원래 조건의 배치 후보는 A입니다.

흔한 오답에서 다시 생각하기

높은 점수는 필수 조건을 무시할 권한이다.

점수는 선호도입니다. 불가능한 노드를 가능하게 바꾸지 않습니다.

연습 3 · 직접 만들어 보기

메모리 192Mi의 별도 사례에서 자원과 분산 점수의 가중치를 둘 다 1로 바꾸세요. A=90/20, B=40/80입니다. 새 합과 선택을 구하고, 가중치 변화의 의미를 설명하세요.

힌트 1

새 점수는 두 점수의 합입니다.

힌트 2

노드의 여유나 필수 조건은 바꾸지 않았습니다.

풀이와 답 확인

  1. A=90+20=110, B=40+80=120입니다.

  2. B가 여전히 높지만 점수 차이는 기존 70에서 10으로 줄어듭니다.

  3. 동일 후보 집합에서도 가중치를 바꾸면 선호 차이가 달라질 수 있습니다.

새 점수 A=110, B=120이며 B를 선택합니다.

흔한 오답에서 다시 생각하기

가중치를 바꾸면 B의 메모리 용량도 바뀐다.

점수 규칙과 실제 자원 조건은 별도 입력입니다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

e3은 serving=false·terminating=false입니다. publishNotReadyAddresses=true인 서비스에서 ready=true로 나타난다는 이유만으로 앱이 요청을 처리할 수 있다고 결론내려도 되나요?

힌트 1

문서의 ready 예외와 앱의 실제 serving 상태를 분리합니다.

힌트 2

트래픽 정책에 쓰이는 값이 업무 성공을 증명하지는 않습니다.

풀이와 답 확인

  1. 이 설정에서는 EndpointSlice ready가 항상 true인 예외가 있습니다.

  2. 그러나 주어진 e3의 serving은 false입니다.

  3. 따라서 준비되지 않은 주소를 게시한 설정과 앱의 업무 처리 가능성을 각각 확인해야 합니다.

ready=true만으로 e3의 업무 성공을 보장하지 못합니다.

흔한 오답에서 다시 생각하기

ready라는 이름이 true이면 모든 기능도 정상이다.

어떤 조건으로 true가 되었는지와 실제 앱 상태를 함께 보세요.

배포·롤링 업데이트

사용자가 보고 있는 강의 서비스를 꺼 버리지 않고 새 버전으로 바꿀 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 복제본 여러 개가 같은 역할을 수행할 수 있다.

  • Ready는 요청을 받을 준비 상태다.

학습 목표

  • Deployment의 원하는 상태와 실제 상태를 구별한다.

  • surge와 unavailable의 서로 다른 상한을 계산한다.

25%를 복제본 수로 바꿀 때 두 설정은 같은 방향으로 반올림할까요?

정수 설정을 백분율 설정으로 넓힙니다. maxSurge는 백분율 결과를 올리고 maxUnavailable은 내립니다. desired=5와 각각 25%이면 추가 수는 ceil(1.25)=2, 부족 허용 수는 floor(1.25)=1입니다. 이 설정의 최소 available은 4입니다. 종료 중 Pod는 추가 자원을 쓰며 남을 수 있으므로 replicas+surge를 모든 프로세스 수의 엄격한 상한으로 바꾸지 않습니다. 아래 순간 종료 계산은 별도 모형입니다.

Ready 직후 available로 세는지 여부도 설정에 달려 있습니다. minReadySeconds=10이면 새 Pod가 충돌 없이 Ready를 유지한 최소 10초가 필요합니다. 중간에 준비 상태를 잃으면 이 시간표에서는 연속 구간을 다시 셉니다. 진행 기한 초과는 상태로 보고되는 실패이며 Deployment가 자동으로 이전 버전으로 되돌아갔다는 증거가 아닙니다. 진단, 수정, 수동 롤백 또는 별도 상위 정책의 조치가 필요합니다.

  • 배포·롤링 업데이트

    기본의 정수 상한을 백분율 반올림과 연속 Ready 시간으로 확장합니다.

  • autoscaling·health check

    검사 성공, 준비 상태, available 조건의 차이를 연결합니다.

새 버전은 새 Pod 집합

Deployment는 원하는 복제본 수와 Pod 템플릿을 선언하고 ReplicaSet을 통해 이를 맞춘다. 이미지 등 Pod 템플릿을 바꾸면 새 ReplicaSet의 Pod를 늘리고 이전 집합을 줄이는 rollout을 할 수 있다. 이미 떠 있는 컨테이너 파일을 몰래 바꾸는 설명과는 다르다.

명령을 받아들였다는 사실과 rollout 완료는 같지 않다. 새 Pod가 이미지 오류나 readiness 실패로 준비되지 않으면 진행이 멈출 수 있다. 완료 여부를 복제본 상태와 rollout 상태로 확인해야 한다.

추가 수와 부족 수를 따로 제한

maxSurge는 원하는 복제본 수보다 추가로 만들 수 있는 양을 제어하고 maxUnavailable은 업데이트 중 사용할 수 없는 양을 제한한다. 아래에서는 정수 설정만 사용한다. desired=4, surge=1, unavailable=0이면 새 준비본을 확보하면서 이전 준비본을 줄이는 경로를 생각할 수 있다.

이 상한은 모든 프로세스가 항상 즉시 사라진다는 보장은 아니다. 공식 문서는 terminating Pod가 availableReplicas에 포함되지 않으며 종료 유예가 끝나기 전 총 Pod 수와 자원 사용량이 replicas+maxSurge보다 커질 수 있다고 명시한다. 예제의 순간 종료 가정을 현실의 엄격한 프로세스 수 상한으로 바꾸지 않는다.

가용성과 성공의 경계

준비된 복제본 수를 유지하더라도 애플리케이션의 모든 기능이 올바른 것은 아니다. 잘못된 API 호환성이나 데이터 변경은 별도 검토가 필요하다. readiness 조건 자체가 너무 느슨하면 숫자만 만족하는 위험도 있다.

surge Pod를 위한 자원 여유가 없고 unavailable=0이면 새 Pod가 준비되기 전에 옛 Pod를 줄일 수 없어 rollout이 정체될 수 있다. 용량 확보, 설정 조정, 실패 원인 수정 중 어떤 대응이 필요한지 원인을 먼저 확인한다.

중간 과정을 따라가는 예제

원하는 복제본은 4, maxSurge=1, maxUnavailable=0이다. 처음 옛 버전 4개가 모두 available이다. 새 Pod가 생성되면 다음 단계에 available이 되며 옛 Pod 삭제는 즉시 완료된다고 가정한다. 한 개씩 바꾸는 경로를 추적하자.

  1. 옛 4·새 0에서 새 1개를 생성하면 존재 5·available 4다. 새것이 available이 되면 available은 5다.

  2. 옛 1개를 삭제하면 옛 3·새 1·available 4다. 같은 생성→준비→삭제 순서를 세 번 더 반복한다.

  3. 안정 단계는 옛/새가 4/0, 3/1, 2/2, 1/3, 0/4다. 각 생성 직후 존재는 최대 5, available은 최소 4다.

이 가정의 경로는 준비본 최소 4를 유지하며 새 4개로 교체한다. 실제 종료 유예가 있는 총 프로세스 수의 엄격한 최대가 5라는 뜻은 아니다.

조건을 바꾸어 비교하기

다섯 복제본의 25% 계산

desired=5, surge=25%, unavailable=25%입니다. 각 정수 값과 최소 available을 구하세요. 별도 순간에 종료 중을 제외한 Pod 7개와 아직 자원을 쓰는 terminating Pod 2개가 있다면 총 존재 수는 얼마인가요?

  1. 5×0.25=1.25에서 surge는 올림하여 2개입니다.

  2. unavailable은 내림하여 1개이므로 최소 available은 5−1=4개입니다.

  3. 종료 중 제외 수의 구성 상한은 5+2=7개입니다.

  4. 주어진 순간의 총 존재 수는 7+2=9개입니다. 이 수치만으로 available이 7개라고 판단하지 않습니다.

surge 2, unavailable 1, 최소 available 4, 주어진 총 존재 수 9개입니다.

비교할 점

Pod 수와 실제 CPU·메모리 사용량은 다릅니다. 9개는 가정한 순간이며 실제 배포에서 측정하지 않았습니다.

준비 상태가 잠깐 끊기면

새 Pod가 20초에 Ready, 25초에 NotReady, 28초부터 다시 계속 Ready입니다. minReadySeconds=10이고 그 이후 충돌은 없습니다. desired=5·surge=1·unavailable=0, 옛 available 5개가 유지됩니다. 이 새 Pod를 available로 셀 계획 시점과 30초에 옛것을 삭제해도 되는지 판단하세요.

  1. 20초부터 25초까지는 5초만 Ready여서 10초 조건을 채우지 못합니다.

  2. 다시 Ready가 된 28초부터 연속 10초를 세면 38초입니다.

  4. 30초에 옛것 하나를 삭제하면 available은 4가 되어 최소 5 조건을 깨므로 이 경로에서는 삭제하지 않습니다.

계획상 새 available 시점은 38초이며 30초에 옛것을 삭제하지 않습니다.

소단원 9.3

자원 요청·제한·상태 저장

Pod를 다시 만들면 그 안에 저장한 숙제도 함께 사라질까?

준비 개념과 학습 목표

준비 개념

  • CPU와 메모리는 사용량과 용량을 가진다.

  • 프로그램의 실행 상태와 저장 데이터는 구별된다.

학습 목표

  • request와 limit의 역할을 구별한다.

  • StatefulSet의 정체성과 영구 볼륨의 수명을 설명한다.

초기화가 끝나면 자원을 덜 써도 처음 배치 기준은 작아질까요?

기본의 일반 컨테이너 request 합에 순차 실행하는 일반 init container를 추가합니다. 이 예에는 재시작형 sidecar init, Pod 수준 자원 설정, overhead가 없고 모든 CPU·메모리 request를 명시합니다. 일반 앱의 합과 init 각각의 최대를 자원별로 비교해 큰 값을 유효 request로 잡습니다. CPU 최대가 생기는 init과 메모리 최대가 생기는 init이 달라도 두 조건을 함께 만족해야 합니다. 초기화가 끝난 뒤 실제 사용량이 줄어드는 것은 배치 계산과 다른 질문입니다.

지속 저장의 삭제도 서로 다른 객체의 정책입니다. StatefulSet의 PVC retention은 claim을 남길지 정하며 PV reclaim은 claim이 해제된 뒤 볼륨을 어떻게 처리할지 정합니다. 아래는 두 retention 필드를 Retain으로 명시합니다. Pod가 사용 중인 claim의 삭제 요청은 보호 장치 때문에 즉시 제거되지 않을 수도 있습니다. 저장 정책을 검토하는 활동이며 실제 데이터 삭제는 수행하지 않습니다.

먼저 확인할 개념
  • 자원 요청·제한·상태 저장

    일반 컨테이너 합을 순차 init의 유효 request와 두 저장 정책으로 확장합니다.

  • 무상태·상태 서비스

    안정 이름, PVC 보존과 실제 데이터 복구 계약을 구분합니다.

요청은 배치의 기준

컨테이너 request는 스케줄러가 자원 수용 가능성을 판단하는 기준이다. 일반적인 Pod의 컨테이너 요청은 합산해 생각할 수 있다. 여기서는 일반 두 컨테이너만 있고 init container, Pod overhead 등 추가 조건이 없는 예제를 쓴다.

request는 사용량 계측값이 아니다. limit까지 여유가 허용되면 request보다 많이 사용할 수도 있다. 노드 전체 물리 용량과 Pod에 할당 가능한 양도 다르므로 운영체제 등이 쓰는 몫을 무시해서는 안 된다.

상한도 자원마다 다르게 작동

limit는 실행 중 자원 사용을 제한하는 설정이다. Linux의 CPU limit는 throttling으로 CPU 시간을 제한하고 메모리 limit는 OOM 처리에 의해 반응적으로 집행될 수 있다. CPU를 초과했다는 이유로 반드시 즉시 종료된다는 설명은 틀리다.

메모리 초과 역시 모든 순간을 완벽히 선제 차단하는 단순 벽으로 보지 않는다. 재시작과 실패 처리는 애플리케이션에 영향을 줄 수 있다. 예제의 수치만으로 실제 지연 시간이나 OOM 발생 시각을 확정하지 않는다.

정체성과 저장소는 별도 계약

StatefulSet은 순서와 고유한 Pod 정체성, 연결된 저장소를 다루는 데 사용한다. Pod가 재생성되어도 일관된 정체성과 저장소 연결이 필요한 응용에 유용하다. 이 기능 자체가 데이터베이스의 복제·일관성·백업 알고리즘을 대신한다는 의미는 아니다.

PersistentVolume과 claim의 수명도 살펴야 한다. Retain은 claim을 지운 뒤에도 볼륨과 데이터가 남아 관리자의 처리가 필요한 정책이고, 지원되는 Delete 정책은 볼륨 객체와 외부 저장 자산을 제거할 수 있다. StatefulSet 삭제 시 기본적으로 볼륨을 남기는 동작과 PV reclaim 정책을 한 규칙으로 섞지 않는다.

배치에 필요한 두 자원 조건

init 둘의 CPU를 더하면 1500m이지만 이 예의 순차 init 최대는 1000m입니다. CPU와 메모리는 각각 최대를 구합니다. 표의 유효 request는 하나의 시점에 두 init이 동시에 실행된다는 뜻이 아닙니다.

중간 과정을 따라가는 예제

일반 컨테이너 C1의 request는 250m·128Mi, C2는 500m·256Mi다. limit는 각각 CPU 500m·1000m, 메모리 256Mi·512Mi다. 별도 StatefulSet의 3개 Pod가 각자 10Gi claim을 요구한다. 추가 자원 항목은 없다고 가정한다.

  1. Pod request는 250+500=750m=0.75 core, 메모리는 128+256=384Mi다.

  2. 컨테이너별 limit를 합하면 CPU 1500m=1.5 core, 메모리 768Mi다. 합은 구성의 비교값이며 한 컨테이너가 다른 컨테이너의 limit를 마음대로 빌린다는 뜻은 아니다.

  3. 저장 요청 합은 3×10=30Gi다. 이는 세 claim의 요청량이며 실제 저장 장치의 물리 복제 수나 백업 용량을 계산한 값이 아니다.

배치 기준은 CPU 0.75 core·384Mi이며 limit 합은 1.5 core·768Mi다. claim 요청 합은 30Gi이고 복제·백업 보장은 별도다.

조건을 바꾸어 비교하기

앱만 보면 들어가지만 초기화가 크다면

일반 앱의 request 합은 750m·384Mi, init I1은 1000m·128Mi, I2는 500m·768Mi입니다. 남은 수용량이 900m·1024Mi인 노드에 이 Pod를 배치할 수 있나요? 다른 조건은 없으며 두 init은 일반 순차 init입니다.

  1. 앱 합만 비교하면 750≤900과 384≤1024로 들어갈 것처럼 보입니다.

  2. init의 자원별 최대는 CPU 1000m·메모리 768Mi입니다.

  3. 유효 request는 max(750,1000)=1000m, max(384,768)=768Mi입니다.

  4. 메모리는 충분하지만 900<1000으로 CPU 조건을 만족하지 못합니다.

이 노드는 유효 CPU request를 만족하지 못해 후보가 아닙니다.

비교할 점

실제 CPU 사용량이 작아 보인다고 초기화의 명시 request를 무시하지 않습니다. 새 스케줄러 실행 결과는 아닙니다.

claim을 남기는 정책과 claim 삭제 후 정책

세 Pod의 claim은 각각 10Gi이고 StatefulSet whenDeleted/whenScaled는 Retain입니다. StatefulSet 삭제 후 claim을 별도로 삭제하는 경우를 비교하세요. PV reclaim은 한 경우 Retain, 다른 경우 지원되는 Delete입니다. claim을 쓰는 Pod가 모두 종료되어 보호 대기가 끝났다고 가정합니다.

  1. StatefulSet의 명시 Retain 정책에서는 삭제만으로 claim을 자동 삭제하지 않습니다.

  2. claim을 별도로 삭제하면 PV reclaim 정책을 확인합니다.

  3. PV Retain이면 볼륨과 데이터가 남아 released 상태이며 곧바로 새 claim에 자동 재사용된다는 뜻은 아닙니다.

  4. 지원되는 PV Delete이면 PV 객체와 외부 저장 자산을 제거할 수 있습니다. 따라서 데이터 보존을 가정하면 안 됩니다.

StatefulSet 삭제에 따른 claim 유지와 별도 claim 삭제 뒤 PV 처리를 두 단계로 구분합니다.

비교할 점

세 claim의 요청 합 30Gi는 백업이나 동일 데이터의 세 사본을 뜻하지 않습니다. 이 비교에서는 실제 삭제를 하지 않았습니다.

종이와 본문으로 직접 해보기

C2의 request 메모리만 384Mi로 바꾸고 limit는 그대로 두자. 새 Pod 요청 합을 구하자. 또 사용하던 claim을 지웠을 때 Retain과 지원되는 Delete 정책의 차이를 설명하자.

힌트 보기

변경한 request만 다시 더하자. 데이터가 남는지와 자동으로 새 claim에 재사용되는지도 구별하자.

풀이 보기

CPU는 750m 그대로, 메모리는 128+384=512Mi다. Retain이면 볼륨은 released 상태와 함께 데이터가 남아 관리자가 회수 과정을 처리해야 하며 새 claim에 자동 재사용 가능하다는 뜻은 아니다. Delete는 지원되는 저장 플러그인에서 볼륨과 외부 자산을 제거하므로 데이터 보존을 가정하면 안 된다.

오해와 반례

StatefulSet이 있으면 저장 데이터의 복제와 백업은 자동으로 모두 해결된다.

안정적인 정체성과 저장소 연결은 응용의 데이터 복제나 복원 가능성을 증명하지 않는다. 3개의 10Gi claim도 30Gi의 요청일 뿐 동일 데이터의 안전한 사본 3개라는 근거가 아니다.
