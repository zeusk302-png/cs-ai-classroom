소단원 9.1

스케줄링·서비스 발견

Pod가 옮겨 다니는데 사용자는 어디로 접속할까?

준비 개념과 학습 목표

준비 개념

  • Pod는 하나 이상의 컨테이너를 묶는 실행 단위다.
  • CPU와 메모리는 서로 다른 자원이다.

학습 목표

  • 가능한 노드와 선호하는 노드를 구별한다.
  • 서비스 이름과 실제 Pod 주소의 관계를 설명한다.

먼저 들어갈 수 있는 곳 찾기

kube-scheduler는 아직 노드가 정해지지 않은 Pod의 배치를 결정한다. filtering은 자원과 배치 조건 등을 만족하는 노드만 남긴다. 남는 노드가 없으면 그 순간에는 스케줄링할 수 없고, CPU가 많이 남는다는 이유만으로 메모리 부족을 무시하지 않는다.

여기서 자원 판단은 Pod의 requests와 노드의 할당 가능한 자원에 관한 것이다. 실제 사용량이 작아 보이는 것과 새 요청을 수용할 수 있는 것은 다르다. 실제 클러스터에는 affinity, taint, 볼륨 등의 조건도 있으므로 자원 두 개만 계산한 예제는 축소 모형이다.

가능한 후보 사이의 선택

scoring은 filtering을 통과한 후보의 선호도를 비교한다. 공식 문서는 설정된 점수 기준에 따라 높은 점수의 노드를 선택하고 최고점 동률이면 임의 선택한다고 설명한다. 가장 여유 있는 CPU 하나만 보는 규칙으로 일반화하지 않는다.

스케줄링과 컨테이너의 성공적 실행도 구별한다. 배치된 뒤 이미지 다운로드나 설정 오류로 실행이 실패할 수 있다. 배치가 실패하면 이벤트와 조건을 확인하고, 무작정 복제본 수를 늘리기보다 부족한 자원이 무엇인지 살핀다.

바뀌는 Pod 뒤의 안정적인 접점

일반 ClusterIP Service는 선택자와 맞는 Pod들의 EndpointSlice를 통해 접점을 제공한다. Pod의 IP가 바뀌어도 클라이언트는 서비스 이름을 사용할 수 있다. 일반 서비스 DNS는 ClusterIP를 가리키며 headless Service의 DNS 동작은 다르다.

접속 후보에는 readiness와 종료 상태도 영향을 준다. 아래 예제는 종료 중인 Pod가 없고 publishNotReadyAddresses가 false인 보통의 서비스를 가정한다. readiness는 트래픽을 받을 준비 상태이며, 이름이 조회된다는 사실만으로 모든 요청이 성공하는 것은 아니다.

중간 과정을 따라가는 예제

다른 배치 조건은 없다고 하자. 노드 A의 남은 요청 수용량은 CPU 750m·메모리 512Mi, B는 1500m·256Mi다. 새 Pod의 request는 500m·384Mi다. Service 선택자는 app=classroom이며 p1은 일치·Ready, p2는 일치·NotReady, p3은 다른 label·Ready다.

  1. A는 750≥500과 512≥384를 모두 만족한다. B는 CPU는 충분하지만 256<384이므로 탈락한다.
  2. A에 배치하면 남은 양은 250m·128Mi다. 같은 요청의 두 번째 Pod는 A에도 B에도 배치할 수 없다.
  3. 기본 readiness 조건에서 서비스의 준비된 후보는 p1 하나다. p2가 Ready가 되면 두 개이고 p3은 선택자 불일치로 제외된다.

첫 Pod는 A만 후보이며, 같은 크기의 두 번째 Pod는 현재 자원으로 배치할 수 없다. 기본 서비스의 준비된 후보 수는 1에서 2로 늘어난다.

종이와 본문으로 직접 해보기

B의 남은 메모리만 512Mi로 늘려 보자. 두 노드가 후보가 되면 어느 노드가 반드시 선택된다고 말할 수 있는가? 또 namespace=school, cluster domain=cluster.local인 일반 서비스 learn의 DNS 이름을 적어 보자.

힌트 보기

가능 여부와 점수 선택을 나누고 서비스·namespace·도메인의 순서를 확인하자.

풀이 보기

A와 B가 모두 filtering을 통과하지만 점수 설정이 주어지지 않아 선택 노드는 확정할 수 없다. DNS 이름은 learn.school.svc.cluster.local이다. cluster.local은 이 활동에서 정한 도메인이며 모든 클러스터의 고정값은 아니다.

오해와 반례

서비스 DNS가 Pod의 현재 IP 하나를 그대로 저장한다.

일반 ClusterIP Service의 이름은 서비스 IP를 가리킨다. Pod 집합의 변경은 EndpointSlice 등으로 반영된다. headless 서비스는 다른 방식이므로 두 모델을 섞지 않는다.

자기점검

답과 이유 보기

1 core다.

m은 CPU의 천분의 일 단위다.

CPU가 충분한 B를 예제에서 제외한 이유는?

답과 이유 보기

메모리 request를 만족하지 못한다.

각 필요한 자원 조건을 함께 만족해야 한다.

p3이 Ready면 선택자 불일치를 무시하고 후보가 되는가?

답과 이유 보기

아니다.

readiness와 label 선택은 서로 다른 조건이다.

한 단계 더

종이에 Pod label, Ready, 종료 여부를 열로 나누어 표를 만들고 조건을 한 번에 하나씩 바꿔 후보 집합을 추적하자. publishNotReadyAddresses=true인 예외는 기본 readiness 판정과 따로 비교하자.

출처와 확인 범위

  • DNS for Services and Pods

    일반 Service의 이름 구성과 ClusterIP, headless의 차이를 읽었다.

  • EndpointSlices

    ready·serving·terminating 조건과 publishNotReadyAddresses 예외를 읽었다.

소단원 9.2

배포·롤링 업데이트

사용자가 보고 있는 강의 서비스를 꺼 버리지 않고 새 버전으로 바꿀 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 복제본 여러 개가 같은 역할을 수행할 수 있다.
  • Ready는 요청을 받을 준비 상태다.

학습 목표

  • Deployment의 원하는 상태와 실제 상태를 구별한다.
  • surge와 unavailable의 서로 다른 상한을 계산한다.

새 버전은 새 Pod 집합

Deployment는 원하는 복제본 수와 Pod 템플릿을 선언하고 ReplicaSet을 통해 이를 맞춘다. 이미지 등 Pod 템플릿을 바꾸면 새 ReplicaSet의 Pod를 늘리고 이전 집합을 줄이는 rollout을 할 수 있다. 이미 떠 있는 컨테이너 파일을 몰래 바꾸는 설명과는 다르다.

명령을 받아들였다는 사실과 rollout 완료는 같지 않다. 새 Pod가 이미지 오류나 readiness 실패로 준비되지 않으면 진행이 멈출 수 있다. 완료 여부를 복제본 상태와 rollout 상태로 확인해야 한다.

추가 수와 부족 수를 따로 제한

maxSurge는 원하는 복제본 수보다 추가로 만들 수 있는 양을 제어하고 maxUnavailable은 업데이트 중 사용할 수 없는 양을 제한한다. 아래에서는 정수 설정만 사용한다. desired=4, surge=1, unavailable=0이면 새 준비본을 확보하면서 이전 준비본을 줄이는 경로를 생각할 수 있다.

이 상한은 모든 프로세스가 항상 즉시 사라진다는 보장은 아니다. 공식 문서는 terminating Pod가 availableReplicas에 포함되지 않으며 종료 유예가 끝나기 전 총 Pod 수와 자원 사용량이 replicas+maxSurge보다 커질 수 있다고 명시한다. 예제의 순간 종료 가정을 현실의 엄격한 프로세스 수 상한으로 바꾸지 않는다.

가용성과 성공의 경계

준비된 복제본 수를 유지하더라도 애플리케이션의 모든 기능이 올바른 것은 아니다. 잘못된 API 호환성이나 데이터 변경은 별도 검토가 필요하다. readiness 조건 자체가 너무 느슨하면 숫자만 만족하는 위험도 있다.

surge Pod를 위한 자원 여유가 없고 unavailable=0이면 새 Pod가 준비되기 전에 옛 Pod를 줄일 수 없어 rollout이 정체될 수 있다. 용량 확보, 설정 조정, 실패 원인 수정 중 어떤 대응이 필요한지 원인을 먼저 확인한다.

중간 과정을 따라가는 예제

원하는 복제본은 4, maxSurge=1, maxUnavailable=0이다. 처음 옛 버전 4개가 모두 available이다. 새 Pod가 생성되면 다음 단계에 available이 되며 옛 Pod 삭제는 즉시 완료된다고 가정한다. 한 개씩 바꾸는 경로를 추적하자.

  1. 옛 4·새 0에서 새 1개를 생성하면 존재 5·available 4다. 새것이 available이 되면 available은 5다.
  2. 옛 1개를 삭제하면 옛 3·새 1·available 4다. 같은 생성→준비→삭제 순서를 세 번 더 반복한다.
  3. 안정 단계는 옛/새가 4/0, 3/1, 2/2, 1/3, 0/4다. 각 생성 직후 존재는 최대 5, available은 최소 4다.

이 가정의 경로는 준비본 최소 4를 유지하며 새 4개로 교체한다. 실제 종료 유예가 있는 총 프로세스 수의 엄격한 최대가 5라는 뜻은 아니다.

종이와 본문으로 직접 해보기

처음 옛 4개가 준비되어 있지만 다섯 번째 Pod를 수용할 자원이 없다고 하자. unavailable=0을 유지하면 이 경로의 어느 단계가 막히는가? 새 Pod가 계속 NotReady이면 무엇이 달라지는가?

힌트 보기

옛것을 먼저 줄이면 허용된 준비본 최소 수를 깨는지 확인하자.

풀이 보기

추가 Pod의 배치 또는 실행 단계가 막힌다. 준비본 4를 유지해야 하므로 새 준비본 없이 옛것을 먼저 하나 줄이는 경로는 조건을 어긴다. 새것이 NotReady인 경우에도 available이 늘지 않아 옛것을 줄이는 단계가 막힌다.

오해와 반례

롤링 업데이트면 어떤 종류의 장애든 무조건 무중단이다.

Pod 교체의 가용성 조건은 기능적 정확성이나 데이터 호환성을 증명하지 않는다. 준비 상태 판정, 여유 용량, 종료 처리와 애플리케이션 동작을 함께 검토해야 한다.

자기점검

예제의 새 Pod 생성 직후 available은 왜 5가 아닌가?

답과 이유 보기

새것이 아직 준비되지 않았기 때문이다.

존재 수와 available 수를 구별한다.

준비된 새것을 하나 확보한 뒤 옛것을 하나 없애면 available은?

답과 이유 보기

4다.

5−1=4이며 순간 종료 가정이다.

실제 종료 중 Pod까지 포함한 수가 5를 넘을 수 있는가?

답과 이유 보기

그럴 수 있다.

종료 유예 중 Pod가 남고 available 수에는 포함되지 않을 수 있다.

한 단계 더

각 시점의 옛 available, 새 available, 새 NotReady, terminating을 네 열로 기록해 보자. 숫자를 나누면 자원 사용량과 사용 가능 복제본 수가 다른 질문임을 볼 수 있다. 여기서는 실제 배포나 장애 실험을 하지 않았다.

소단원 9.3

자원 요청·제한·상태 저장

Pod를 다시 만들면 그 안에 저장한 숙제도 함께 사라질까?

준비 개념과 학습 목표

준비 개념

  • CPU와 메모리는 사용량과 용량을 가진다.
  • 프로그램의 실행 상태와 저장 데이터는 구별된다.

학습 목표

  • request와 limit의 역할을 구별한다.
  • StatefulSet의 정체성과 영구 볼륨의 수명을 설명한다.

요청은 배치의 기준

컨테이너 request는 스케줄러가 자원 수용 가능성을 판단하는 기준이다. 일반적인 Pod의 컨테이너 요청은 합산해 생각할 수 있다. 여기서는 일반 두 컨테이너만 있고 init container, Pod overhead 등 추가 조건이 없는 예제를 쓴다.

request는 사용량 계측값이 아니다. limit까지 여유가 허용되면 request보다 많이 사용할 수도 있다. 노드 전체 물리 용량과 Pod에 할당 가능한 양도 다르므로 운영체제 등이 쓰는 몫을 무시해서는 안 된다.

상한도 자원마다 다르게 작동

limit는 실행 중 자원 사용을 제한하는 설정이다. Linux의 CPU limit는 throttling으로 CPU 시간을 제한하고 메모리 limit는 OOM 처리에 의해 반응적으로 집행될 수 있다. CPU를 초과했다는 이유로 반드시 즉시 종료된다는 설명은 틀리다.

메모리 초과 역시 모든 순간을 완벽히 선제 차단하는 단순 벽으로 보지 않는다. 재시작과 실패 처리는 애플리케이션에 영향을 줄 수 있다. 예제의 수치만으로 실제 지연 시간이나 OOM 발생 시각을 확정하지 않는다.

정체성과 저장소는 별도 계약

StatefulSet은 순서와 고유한 Pod 정체성, 연결된 저장소를 다루는 데 사용한다. Pod가 재생성되어도 일관된 정체성과 저장소 연결이 필요한 응용에 유용하다. 이 기능 자체가 데이터베이스의 복제·일관성·백업 알고리즘을 대신한다는 의미는 아니다.

PersistentVolume과 claim의 수명도 살펴야 한다. Retain은 claim을 지운 뒤에도 볼륨과 데이터가 남아 관리자의 처리가 필요한 정책이고, 지원되는 Delete 정책은 볼륨 객체와 외부 저장 자산을 제거할 수 있다. StatefulSet 삭제 시 기본적으로 볼륨을 남기는 동작과 PV reclaim 정책을 한 규칙으로 섞지 않는다.

중간 과정을 따라가는 예제

일반 컨테이너 C1의 request는 250m·128Mi, C2는 500m·256Mi다. limit는 각각 CPU 500m·1000m, 메모리 256Mi·512Mi다. 별도 StatefulSet의 3개 Pod가 각자 10Gi claim을 요구한다. 추가 자원 항목은 없다고 가정한다.

  1. Pod request는 250+500=750m=0.75 core, 메모리는 128+256=384Mi다.
  2. 컨테이너별 limit를 합하면 CPU 1500m=1.5 core, 메모리 768Mi다. 합은 구성의 비교값이며 한 컨테이너가 다른 컨테이너의 limit를 마음대로 빌린다는 뜻은 아니다.
  3. 저장 요청 합은 3×10=30Gi다. 이는 세 claim의 요청량이며 실제 저장 장치의 물리 복제 수나 백업 용량을 계산한 값이 아니다.

배치 기준은 CPU 0.75 core·384Mi이며 limit 합은 1.5 core·768Mi다. claim 요청 합은 30Gi이고 복제·백업 보장은 별도다.

종이와 본문으로 직접 해보기

C2의 request 메모리만 384Mi로 바꾸고 limit는 그대로 두자. 새 Pod 요청 합을 구하자. 또 사용하던 claim을 지웠을 때 Retain과 지원되는 Delete 정책의 차이를 설명하자.

힌트 보기

변경한 request만 다시 더하자. 데이터가 남는지와 자동으로 새 claim에 재사용되는지도 구별하자.

풀이 보기

CPU는 750m 그대로, 메모리는 128+384=512Mi다. Retain이면 볼륨은 released 상태와 함께 데이터가 남아 관리자가 회수 과정을 처리해야 하며 새 claim에 자동 재사용 가능하다는 뜻은 아니다. Delete는 지원되는 저장 플러그인에서 볼륨과 외부 자산을 제거하므로 데이터 보존을 가정하면 안 된다.

오해와 반례

StatefulSet이 있으면 저장 데이터의 복제와 백업은 자동으로 모두 해결된다.

안정적인 정체성과 저장소 연결은 응용의 데이터 복제나 복원 가능성을 증명하지 않는다. 3개의 10Gi claim도 30Gi의 요청일 뿐 동일 데이터의 안전한 사본 3개라는 근거가 아니다.

한 단계 더

실행 단위, 고유 정체성, claim, 실제 저장 자산, 백업을 다섯 상자로 그려 보자. 삭제 화살표가 어느 상자까지 영향을 주는지 정책별로 표시하면 운영 중 데이터 보호 질문을 분리할 수 있다. 실제 클러스터나 볼륨 삭제는 수행하지 않았다.
