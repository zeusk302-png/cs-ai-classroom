소단원 6.1

블록·파일·객체 저장

같은 사진을 디스크 칸, 경로 이름, 객체 키로 보관하면 읽는 방법이 어떻게 달라질까?

준비 개념과 학습 목표

준비 개념

  • 바이트는 데이터의 단위이며 KiB =1024 바이트다.

  • 파일 경로는 디렉터리 안의 이름이고 블록 주소는 저장 단위의 번호다.

학습 목표

  • 세 저장 인터페이스의 책임을 구별한다.

  • 작은 부분 갱신과 객체 교체의 비용을 가정 아래 계산한다.

번호를 읽는 블록

블록 저장은 정해진 위치의 바이트 구간을 읽고 쓰는 인터페이스다. 운영 체제가 그 위에 파일 시스템을 만들 수 있다. 블록 장치가 자체적으로 사람에게 친숙한 폴더/ 권한/ 파일명을 모두 제공하는 것은 아니다. EBS 볼륨은 VM에 연결하는 대표 사례다.

파일의 일부를 고칠 때 어느 블록에 해당하는지 파일 시스템이 계산한다. 파일 시스템 메타데이터/ 로그/ 정렬에 따라 실제 쓰기량이 더 클 수 있다. 아래에서는 데이터 블록만 세어 인터페이스 차이를 보여 주고 실제 저장 장치 내부 쓰기 증폭은 계산에서 제외한다.

경로를 공유하는 파일

파일 저장은 디렉터리와 파일 경로, 파일 내용 읽기/ 쓰기 같은 인터페이스를 제공한다. 네트워크 파일 저장은 여러 컴퓨터가 같은 경로의 데이터를 볼 수 있게 한다. EFS의 NFS처럼 프로토콜과 공유 권한을 함께 고려한다.

파일을 동시에 고치는 문제는 공유 가능성만으로 해결되지 않는다. 파일 잠금·갱신 규약·클라이언트 캐시 조건이 필요할 수 있다. 여러 VM이 같은 블록 장치를 직접 연결하는 것도 공유 파일 시스템과 같은 뜻이 아니며 별도 동시성 설계 없이 일반 파일 시스템을 공유 쓰기하면 위험하다.

키로 찾는 객체

객체 저장에서는 키가 하나의 객체와 메타데이터를 가리킨다. 일반 S3 객체의 images/cat.jpg라는 키 안에 슬래시가 있어도 전통 파일 시스템의 디렉터리 inode와 같은 것으로 해석하지 않는다. 서비스의 버킷 종류와 API에 따라 기능이 다르다.

이 단원은 일반 객체 전체 교체 PUT 모형을 사용한다. GET으로 범위를 읽는 기능과 임의 바이트를 제자리 덮어 쓰는 파일 인터페이스는 다르다. 특정 서비스의 추가 부분 쓰기 기능을 모든 객체 저장의 공통 성질로 일반화하지 않고 API별로 확인한다.

중간 과정을 따라가는 예제

1 MiB 자료의 1024바이트를 바꾼다. 데이터 블록 4 KiB, 수정은 한 블록 안에 있다. 파일의 데이터 블록 1개 쓰기와 전체 객체 1 MiB 교체 PUT의 데이터 전송량을 비교하라. 메타데이터/ 복제/ 요청 헤더는 제외한다.

  1. 1 MiB =1048576 바이트,4 KiB =4096 바이트다.

  2. 블록 모형은 4096바이트 데이터 쓰기다.

  3. 전체 객체 교체는 1048576바이트를 보낸다.

  4. 비율1048576/4096=256이다.

자체 모형의 데이터량은 4 KiB 대 1 MiB,256 배다. 실제 서비스 총 비용/ 내부 쓰기량은 아니다.

힌트 보기

풀이 보기

오해와 반례

객체 키의 슬래시는 항상 POSIX 디렉터리를 뜻한다.

일반 객체 버킷에서는 이름의 문자/ 접두어다. rename/locking/ 부분 쓰기 의미를 파일 API와 같다고 가정하면 설계가 어긋난다.

한 단계 더

자료를 작은 객체 256개로 나누면 부분 갱신 전송량은 줄 수 있으나 요청 수와 다중 객체 일관성이 복잡해진다. 4 KiB 단위 객체 256개와 원본 1개의 목록·복구·갱신 책임을 표로 비교한다.

소단원 6.2

내구성·일관성·복제

데이터 복사본이 세 개 있으면 삭제 실수도 막고 모든 읽기가 최신일까?

준비 개념과 학습 목표

준비 개념

  • 내구성은 저장한 데이터가 손실되지 않는 성질, 가용성은 요청에 응답할 수 있는 성질이다.

  • 일관성은 여러 관측이 어떤 순서/ 규칙을 따르는지 정한다.

학습 목표

  • 세 성질을 분리해 장애와 읽기 사례를 설명한다.

  • 독립성 가정 아래 복제 손실 모형을 계산한다.

복사본과 장애 영역

복제는 데이터의 여러 복사본을 다른 장치/ 노드에 둔다. 한 장치가 망가져도 다른 복사본을 이용할 수 있다. 같은 전원/ 관리 실수/ 소프트웨어 오류를 공유하면 복사본의 장애는 독립이 아니므로 복사 개수만으로 손실 확률을 계산할 수 없다.

버전 보존/ 백업은 과거 상태로 돌아가는 별도 책임이다. 잘못된 삭제를 즉시 모든 복사본에 반영하는 복제는 삭제 실수를 그대로 확산시킨다. 내구성이 높아도 권한/ 네트워크 때문에 지금 읽을 수 없으면 가용성은 낮을 수 있다.

성공 응답 뒤의 관측

강한 read-after-write 일관성은 성공한 쓰기 응답 뒤 시작하는 읽기가 그 쓰기를 반영한다는 규약이다. 일반 S3 객체의 PUT/DELETE와 GET/LIST는 공식 문서가 이 성질을 명시한다. 복제 방식과 일관성 규약은 같은 축이 아니며 객체 저장이라고 항상 eventual인 것도 아니다.

서로 겹치는 쓰기는 시작/ 응답 시간이 다르게 관측될 수 있다. 단일 키의 원자적 갱신이면 읽기는 완전한 이전 또는 새 객체를 보며 일부 바이트가 섞인 객체를 보지 않는다. 여러 키를 한꺼번에 교체하는 거래 원자성이 따라오는 것은 아니다.

동기·비동기의 선택

동기 복제는 정한 복사본들의 확인을 기다려 성공 응답하는 식으로 구성할 수 있다. 기다리는 대상이 늘면 장애 시 응답 지연/ 불가가 생길 수 있다. 비동기 복제는 응답 뒤 복사가 진행되어 지연 구간에 원본 손실 시 최근 데이터가 사라질 수 있다. 이는 교육용 일반 모형이며 특정 AWS 내부 protocol 설명이 아니다.

독립 손실 모형은 분명한 기간과 복구 제외 조건을 둔다. 세 복사본이 그 기간에 각각 확률 p로 독립 영구 손실되고 하나라도 남으면 데이터가 유지된다고 가정할 때 전체 손실은 p³다. 복구 중 노출 시간/ 공통 장애를 포함한 실제 내구성 계산과 구별한다.

중간 과정을 따라가는 예제

자체 기간 모형에서 복사본 3개의 영구 손실 확률이 각각.02이고 독립이다. 복구는 없고 하나만 남아도 데이터가 유지된다. 전체 손실 확률과 최소 하나 손실 확률을 구하라.

  1. 전체 손실은.02³ =.000008이다.

  2. 확률을 퍼센트로 바꾸면.0008 %다.

  3. 모두 생존은.98³ =.941192다.

  4. 최소 하나 손실은 1 −.941192 =.058808,5.8808 %다.

전체 손실.0008 %와 하나 이상 손실 5.8808 %는 서로 다른 사건이다.

종이와 본문으로 직접 해보기

세 복사본이 같은 원인으로 함께 손실될 확률.02 인 모형으로 바꾸면 전체 손실은? 성공 PUT 뒤 GET/LIST와 다중 키 갱신도 구별하라.

힌트 보기

공통 사건의 확률을 세 번 곱하지 않는다.

풀이 보기

전체 손실.02 =2 %다. S3 객체 성공 PUT 뒤 시작한 GET/LIST는 새 상태를 반영하지만 두 키 교체가 하나의 원자적 거래로 되는 것은 아니다.

오해와 반례

복제는 백업이므로 현재 값을 잘못 덮어 써도 과거 값이 반드시 남는다.

버전/ 백업 없이 세 복사본을 같은 새 값으로 교체하면 과거 값은 없어진다. 복사본 수와 복구 가능한 과거 시점은 별도다.

소단원 6.3

접근 패턴과 비용

단가가 싼 저장 공간이 읽기 요청이 많은 서비스에서도 가장 쌀까?

준비 개념과 학습 목표

준비 개념

  • GB-month는 저장량과 기간의 과금 단위이고 요청 단가는 횟수에 곱한다.

  • 여기 단가와 GB 는 자체 가상 10진 모형이며 실제 업체 가격/ 세금/ 할인과 무관하다.

학습 목표

  • 저장·요청·반출/ 검색 비용을 나누어 계산한다.

  • 읽기 빈도 변화의 손익 분기점을 찾는다.

용량 외의 세는 것

총비용 모형은 용량비 +요청비 +조회한 데이터 비 +반출비 등으로 나눈다. 같은 100GB를 보관해도 작은 객체를 수 백만 번 읽는 경우와 큰 파일을 몇 번 순차 읽는 경우의 요청 횟수/ 전송량은 다르다. 보관 기간 최소 값과 최소객체 과금도 서비스별로 확인해야 한다.

이 예는 월 100GB를 계속 보관하고 조회량 DGB에 비례한 추가 비용만 고려한다. 요청비·반출·최소 기간·세금은 두 안에서 같거나 0으로 놓는다. 이렇게 고정한 조건을 바꾸면 결론도 다시 계산해야 한다.

빈도와 지연 요구

자주 읽는 자료는 캐시/ 배치 요청으로 비용을 줄일 수 있지만 캐시가 차지하는 용량과 최신성 관리도 책임이다. 순차 접근은 큰 요청으로 묶기 쉽고 무작위 작은 읽기는 요청 수와 지연이 중요한 경우가 많다. 접근 패턴은 저장 형태를 고르는 입력이다.

낮은 저장 단가의 archival 선택에는 복원대기/ 조회비 같은 조건이 붙을 수 있다. 비용만 작은 선택이 학습 웹 페이지의 지연 요구를 만족하는지는 별도 확인한다. 실제 측정 없이 특정 class가 항상 빠르다거나 최저비용이라고 결론 내리지 않는다.

분기점은 식으로 비교한다

안 A는 GB-month당.03 단위, 조회 GB당 0이고 안 B는.01 과.05다. 월 100GB면 CA =3,CB =1 +.05D다. 3 =1 +.05D에서 D =40이다. 이때 두 안 비용이 같고 그보다 많이 읽으면 A가 작다.

D는 보관 용량이 아니라 월 누적 조회량이다. 같은 파일을 여러 번 읽으면 D가 100GB보다 클 수 있다. 불확실한 조회량이면 D =0/20/100 같은 시나리오를 계산하고 지연/ 복원 조건도 나란히 둔다.

중간 과정을 따라가는 예제

위 가상 안에서 D =20GB와 100GB일 때 CA,CB를 계산하고 분기점을 구하라.

  1. CA =100×.03 =3이다.

  2. D20이면 CB =100×.01 +20×.05 =2다.

  3. D100이면 CB =1 +5 =6이다.

  4. 동일 비용 조건.05D =2로 D40이다.

D20에서는 B2<A3, D100에서는 A3<B6, D40에서는 둘 다 3이다.
