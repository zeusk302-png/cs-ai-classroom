소단원 1.1

IaaS·PaaS·SaaS

서버를 빌리는 것, 만든 앱을 배포하는 것, 완성된 앱을 쓰는 것은 같은 선택일까?

준비 개념과 학습 목표

준비 개념

  • 서버는 다른 프로그램의 요청에 응답하는 프로그램 또는 이를 실행하는 장치다. 네트워크는 장치 사이 데이터를 전달하며 파일은 이름 있는 데이터 저장 단위다.

  • 운영체제는 CPU·메모리·장치 사용을 관리한다. 런타임은 응용 코드를 실행하는 환경이고 응용은 사용자 기능을 제공한다.

  • 제공자와 고객의 경계: 어떤 층을 직접 설정·교체할 수 있는지와 어떤 기능을 요청해 쓰는지를 구분한다.

학습 목표

  • 세 모델을 고객에게 제공되는 능력과 통제 범위로 분류한다.

  • 서비스 모델과 배포 모델·상품 이름을 구분한다.

  • 작은 기능 요구에 필요한 운영 층을 표로 추적한다.

완성된 게시판을 쓰는 사람과 게시판 코드를 배포하는 사람은 같은 통제를 갖나요?

학교 게시판을 이용하는 학생, 게시판 프로그램을 만드는 동아리, 서버 운영 담당자는 서로 다른 작업을 한다. 클라우드 서비스도 화면이 웹이라는 이유로 하나로 묶기보다 고객이 무엇을 배포하고 바꿀 수 있는지 본다. 이번에는 기본 본문의 I/P/S 표에 요구 조건을 붙여 후보를 걸러 본다.

이 보강의 I는 고객이 게스트 OS와 자기 앱을 관리하고, P는 제공자의 지원 환경에서 자기 앱을 배포하며, S는 제공자 앱의 허용된 설정만 바꾼다는 가상 계약이다. 세 후보는 다른 요구가 없을 때 비교한다. 실제 상품의 가격·지원 언어·계약을 확인한 표가 아니며, 서비스 모델 이름 하나로 특정 상품 선택을 보장하지 않는다.

먼저 확인할 개념
  • IaaS·PaaS·SaaS

    제공 능력과 통제 범위로 세 모델을 분류한다.

  • 공유책임·서비스 모델

    일부 층을 맡겨도 고객 데이터와 설정 책임이 남는 이유를 연결한다.

구름이라는 이름보다 제공 능력을 본다

NIST의 클라우드 정의는 네트워크로 필요할 때 공유 자원을 제공받는 모형이다. 셀프서비스·넓은 네트워크 접근·자원 풀·빠른 탄력성·사용량 측정이라는 다섯 특성을 함께 본다. 단지 원격 컴퓨터라는 이유만으로 그 정의의 모든 특성을 만족한다고 단정하지 않는다.

서비스 모델은 고객에게 무엇을 제공하는지 구분한다. IaaS는 OS와 앱을 올릴 기본 계산·저장·네트워크 자원, PaaS는 지원 환경에 고객 앱을 배포하는 능력, SaaS는 제공자 앱을 사용하는 능력이다. 여기서 분류의 근거는 VM·웹·컨테이너라는 단어 하나가 아니다.

통제하는 층에 따라 작업이 달라진다

전형적인 IaaS 고객은 게스트 OS와 배포 앱을 관리한다. PaaS는 기반 OS를 직접 관리하지 않고 고객 앱과 허용된 호스팅 설정을 다룬다. SaaS는 제공자 앱을 사용하며 허용된 사용자 설정을 다룬다. 실제 서비스가 제공하는 세부 통제·책임은 문서와 계약에 따라 정해야 한다.

자체 수업용 표를 정하자. 기능은 게시판이며 데이터와 접근 권한은 고객이 관리한다. I에서는 고객 OS·런타임·앱, P에서는 제공자 OS·런타임과 고객 앱, S에서는 제공자 앱을 사용한다. 이 표는 모델 비교를 위한 가정으로, 모든 상품의 세부 기능을 대표하지 않는다.

배포 위치와 서비스 모델은 다른 축이다

Public/private/community/hybrid는 배포 모델의 구분이고 IaaS/PaaS/SaaS는 서비스 능력의 구분이다. 사설 클라우드에서도 SaaS 형태를 제공할 수 있으므로 public과 SaaS를 동의어로 쓰지 않는다. 같은 시스템 안에 여러 서비스 모델을 조합할 수도 있다.

더 많은 층을 맡기면 고객의 일부 유지보수 작업은 줄지만 앱 코드·데이터·계정·설정의 판단이 자동으로 없어지지 않는다. 선택은 필요한 통제, 기능 제약, 운영 능력과 비용을 함께 비교해야 한다. 설치 없는 책임표로 모델을 이해한 뒤 특정 상품은 공식 문서에서 다시 확인한다.

가상 조건확인할 능력 또는 상태결론의 범위

행마다 필수 요구를 먼저 적용한다. 만족한 후보 사이의 최선 선택은 비용·운영 능력 등의 추가 기준이 있어야 한다.

중간 과정을 따라가는 예제

위 가상 I/P/S 게시판에서 기반 OS 패치, 고객 앱 배포, 게시물 읽기 권한 설정을 누가 다루는지 표를 만들어라.

  1. I의 OS 패치는 고객, P/S의 기반 OS 패치는 제공자로 둔 계약을 읽는다.

  2. 자체 앱 배포는 I/P의 고객 작업이다. S는 제공자 앱 사용이므로 같은 앱 교체 능력을 가정하지 않는다.

  3. 게시물 읽기 권한은 세 경우 모두 고객이 허용 범위에서 설정한다.

I: 고객 OS·앱·권한. P: 제공자 OS/고객 앱·권한. S: 제공자 OS·앱/고객 권한 설정. 실제 상품 책임은 이 가상 표만으로 확정하지 않는다.

조건을 바꾸어 비교하기

지원 언어라는 조건을 한 번 더 적용

동아리는 자기 앱을 배포해야 한다. 가상 I는 언어 L과 M을 설치할 수 있고, P는 L만 지원하며, S는 자체 앱 배포를 제공하지 않는다. 앱이 M으로 작성되었고 다시 쓰지 않는다면 후보는?

  1. 자체 앱 배포 요구만 보면 I와 P가 남고 S가 제외된다.

  2. M 지원 요구를 추가하면 P도 제외된다.

  3. 가상 조건을 모두 만족하는 후보는 I다. 실제 운영 능력이나 다른 요구는 주어지지 않았다.

I만 두 요구를 만족한다. PaaS가 앱 배포를 제공한다는 일반 분류만으로 모든 언어를 지원한다고 결론 내릴 수 없다.

비교할 점

서비스 모델에서 실제 기능 제약으로 한 단계 더 내려간다.

전용 사용과 외부 위치를 다른 축으로 기록

서비스 X는 한 학교 조직만 전용으로 사용하며 제공자 시설에 있다. 고객은 제공자 게시판 앱의 설정만 사용한다. 서비스 Y는 일반 대중에게 제공되는 자원에서 고객이 OS와 자기 앱을 올린다. NIST의 서비스·배포 두 축으로 분류하라.

  1. X의 능력은 제공자 앱 사용이므로 SaaS다. 전용 조직 사용은 private 배포에 해당하며 제공자 시설이라는 이유로 public으로 바꾸지 않는다.

  2. Y의 능력은 기본 자원 위 OS와 앱 배포이므로 IaaS다. 일반 대중에게 제공되는 자원이라는 조건은 public 배포에 해당한다.

X는 private/SaaS이고 Y는 public/IaaS다. 문제는 각 구성의 클라우드 특성이 성립한다고 가정한다.

비교할 점

사설 배포를 학교 내부 건물과 동의어로 쓰지 않는다.

종이와 본문으로 직접 해보기

고객이 OS 버전을 직접 바꿔야 한다는 요구와, 제공자 앱의 사용자 설정만 바꾸면 된다는 요구를 각각 I/P/S 표와 비교하라.

힌트 보기

무엇을 사용할 수 있는지와 무엇을 통제할 수 있는지를 구분한다.

풀이 보기

가상 표에서는 직접 OS 변경 요구는 I만 충족한다. 제공자 앱 설정 사용은 S에 맞는다. 특정 상품에 필요한 기능이 실제 있는지는 별도 확인해야 한다.

오해와 반례

브라우저로 쓰는 모든 서비스는 SaaS이고 서버가 있는 서비스는 IaaS다.

브라우저 관리 화면으로 VM을 제어해도 제공 능력은 IaaS일 수 있다. 고객 앱을 실행하는 서버가 있다고 PaaS가 자동 IaaS가 되지 않는다.

연습 1 · 값과 상태 예측

가상 계약에서 I와 P 모두 언어 L의 자기 앱 배포가 가능하고, S는 제공자 앱만 쓴다. OS 직접 변경은 필요 없다. 필수 요구가 자기 앱 배포뿐이면 만족 후보를 모두 써라.

힌트 1

필요하지 않은 통제를 필수 조건에 추가하지 않는다.

힌트 2

자체 앱을 배포할 수 있는 두 후보를 찾는다.

풀이와 답 확인

  1. I와 P는 요구를 충족한다.

  2. S는 자체 앱 배포를 제공하지 않는다.

만족 후보는 I와 P다. 추가 기준이 없으므로 유일한 최선 후보를 고르지 않는다.

P가 덜 관리하므로 무조건 최선이다.

요구 만족과 최적 선택은 다르다. 비용이나 운영 제약이 주어져야 비교할 수 있다.

연습 2 · 오류 찾아 고치기

브라우저의 관리 화면에서 VM의 OS를 설치했으므로 SaaS라고 분류했다. 이 화면으로 고객이 기본 계산 자원에 OS와 앱을 올린다는 조건을 사용해 고쳐라.

힌트 1

접속 수단과 제공 능력을 구별한다.

힌트 2

고객이 바꾸는 층을 표시한다.

풀이와 답 확인

  1. 브라우저는 관리 화면의 접속 수단이다.

  2. 고객이 기본 자원에 OS와 앱을 배포하는 능력은 IaaS 분류에 맞는다.

주어진 능력은 IaaS다. 웹 화면 자체는 SaaS의 충분조건이 아니다.

흔한 오답에서 다시 생각하기

화면이 웹이면 앱 사용 서비스이므로 모두 SaaS다.

화면의 모양보다 고객에게 제공되는 통제와 배포 능력을 읽는다.

연습 3 · 직접 만들어 보기

같은 학교 프로젝트에 제공자 메일 앱 사용, 직접 OS 설정이 필요한 실험 서버, 지원 언어의 자체 수업 앱 배포가 각각 필요하다. 가상 I/P/S에서 각 역할에 맞는 모델을 배치하고 세 역할이 한 모델이어야 하는지 설명하라.

힌트 1

역할별 제공 능력을 따로 쓴다.

힌트 2

프로젝트 전체가 반드시 하나의 서비스 모델인 것은 아니다.

풀이와 답 확인

  1. 메일 앱 사용은 S, 직접 OS 설정은 I에 맞는다.

  2. 지원 언어의 자기 앱 배포는 P에 맞고 가상 I에서도 가능하다.

  3. 이 구성은 여러 모델을 조합할 수 있다.

S와 I 및 P 또는 I를 역할별로 조합한다. 실제 지원 기능은 각 서비스에서 확인해야 한다.

흔한 오답에서 다시 생각하기

프로젝트 이름이 하나면 모델도 하나로 통일한다.

분류 대상인 서비스 능력은 프로젝트 안에서 여러 종류로 나뉠 수 있다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

원격 서버 Z를 빌리려면 매번 담당자에게 메일을 보내 수동 승인을 기다려야 한다. 원격 접속이 된다는 사실만으로 NIST의 다섯 클라우드 특성을 모두 확인했다고 하는 주장을 평가하라.

힌트 1

네트워크 접근과 셀프서비스는 다른 특성이다.

힌트 2

제공자 사람의 개입 없이 자원을 마련하는 조건을 확인한다.

풀이와 답 확인

소단원 1.2

공유책임·서비스 모델

제공자가 서버를 패치해도 잘못 공개한 고객 파일까지 자동으로 보호될까?

준비 개념과 학습 목표

준비 개념

  • 자산은 보호할 데이터·계정·서비스다. 인증은 누구인지 확인하고 권한은 어떤 자산에 어떤 동작을 허용하는지 정한다.

  • 공유책임은 작업을 막연히 반씩 나눈다는 뜻이 아니다. 자산·층·작업·수행 주체·확인 증거를 지정한다.

  • 논리곱 A∧B는 두 조건이 모두 참이어야 참이다. 기반 보호와 고객 설정이 모두 필요할 수 있다.

학습 목표

  • 서비스별 책임의 경계를 공식 문서와 함께 정한다.

  • 제공자 수행·고객 설정·고객 검증을 분리한다.

  • 권한 사고를 책임표와 불변식으로 추적한다.

권한을 다 막은 표와 정확히 허용한 표는 같은 성공일까요?

교실 문을 모두 잠그면 원치 않는 방문은 줄어도 수업을 할 학생도 들어오지 못한다. 클라우드 권한에서도 과도한 허용이 없는 조건과 필요한 기능이 되는 조건을 나눈다. 정책 P는 원하는 허용 쌍의 집합이고 A는 현재 설정이 허용하는 쌍의 집합이다. 여기서는 요청 인증이 올바르고 다른 우회 경로가 없는 작은 모형만 계산한다.

설정의 책임, 작업을 수행한 기록, 실제 동작 확인은 다른 자료다. 제공자의 기반 패치 완료 기록은 고객의 파일 공개 설정을 확인한 기록을 대신하지 않는다. AWS와 Microsoft의 공식 설명에서도 기반 층과 고객의 데이터·설정·계정 판단을 나눈다. 아래 표는 자체 가상 운영표이며 법적 책임이나 실제 제품 계약 판정이 아니다.

먼저 확인할 개념
  • 공유책임·서비스 모델

    A⊆P와 P⊆A를 나누는 기본 권한 모형을 확인한다.

  • IaaS·PaaS·SaaS

    OS와 앱의 통제 범위를 책임 작업에 연결한다.

공유라는 말은 구체적인 분담을 요구한다

AWS 공식 설명에서 EC2 고객은 게스트 OS·설치 앱·보안그룹 설정을 관리한다. S3/DynamoDB처럼 더 추상화한 서비스에서도 데이터·IAM 권한·암호화 선택의 고객 책임이 남는다. 이것은 각 예시의 공식 분담이며 모든 관리형 저장소를 한 서비스 모델로 뭉뚱그릴 이유가 아니다.

Microsoft의 공식 모델 표 역시 데이터·설정·사용자와 기반 호스트/OS 항목의 분담을 구별한다. 따라서 정확한 표는 선택한 상품·지역·기능·설정·계약을 기준으로 만든다. 보호 기능 제공과 그 기능을 활성화·구성·감사하는 행위는 서로 다른 작업이다.

권한을 상태 모형으로 검사한다

가상 공유 저장소의 계약은 교사 계정만 성적 파일을 읽고 학생은 공개 자료만 읽는 것이다. 권한표는 교사:성적/자료 읽기, 학생:자료 읽기, 익명:없음으로 초기화한다. 제공자가 저장 기반을 패치해도 고객이 성적 파일에 익명 읽기 허용을 추가하면 계약이 깨진다.

주체 s, 자산 o의 실제 읽기 허용 집합 A와 정책 집합 P를 비교한다. 보호 목표는 모든 성공 읽기에 대해 (s, o)∈P이다. A⊆P면 허용 집합의 과도한 공개는 없지만 필요한 읽기가 되는지는 별도 P⊆A 조건이다. 권한 판단뿐 아니라 인증 우회·오래된 링크·캐시 등 실제 경로도 별도로 검사해야 한다.

운영 작업에도 확인 가능한 주체가 있다

수업용 책임표에는 기반 패치 제공자/앱 의존성 패치 고객/권한 설정 고객/백업 보존과 복원은 선택 서비스 계약에 따라 지정이라고 쓴다. 제공자 복제는 실수 삭제 이전 버전을 되찾는 고객 백업과 자동 동의어가 아니다. 복구 가능성을 원하면 보존 정책·복원 경로·검증 근거를 정한다.

공유 항목은 같은 작업을 두 번 맡긴다는 뜻일 수도 있지만 서로 다른 층의 유사 작업인 경우도 있다. 누가 수행하는지 외에 누가 확인하는지, 실패를 누가 관측하고 어떻게 대응하는지를 적어야 빈 책임이 드러난다. 문서를 읽은 사실은 해당 설정이 실제 배포되었다는 증거가 아니다.

정책과 현재 허용표를 서로 다른 방향으로 비교하기

포함 기호의 방향을 먼저 읽는다. 집합의 원소 개수가 같아도 서로 다른 허용 쌍이면 일치가 아니다.

중간 과정을 따라가는 예제

위 초기 권한표에서 고객이 성적 파일에 익명 읽기를 허용한다. 제공자의 기반 패치 성공이 정책 불변식을 유지하는지 판단하라.

  1. 정책 P에는 (익명, 성적)이 없다.

  2. 변경된 A에는 (익명, 성적)이 추가된다. 따라서 A⊆P가 아니다.

  3. 기반 패치 성공과 권한 설정 오류는 다른 층이며 패치가 이 허용을 자동 제거한다고 가정하지 않았다.

가상 정책 불변식은 깨진다. 익명 성공 읽기가 실제 발생했다는 관측은 없지만 허용 표에 정책 위반 경로가 생겼다.

조건을 바꾸어 비교하기

허용 개수는 같고 내용은 다르다

P={(교사,성적),(교사,자료),(학생,자료)}다. A={(교사,성적),(교사,자료),(익명,성적)}다. 과도한 허용과 누락을 각각 구하라.

  1. A에는 있으나 P에는 없는 쌍은 (익명,성적)이다.

  2. P에는 있으나 A에는 없는 쌍은 (학생,자료)이다.

  3. 두 집합은 각각 원소 3개지만 내용이 다르므로 어느 포함 조건도 만족하지 않는다.

과도한 허용 1개와 필요한 허용 누락 1개다. A⊆P와 P⊆A가 모두 실패한다.

기본 본문의 단일 추가·삭제를 동시에 일어난 서로 다른 오류로 합친다.

완료 기록이 없는 담당 항목

가상 운영표에서 기반 패치의 수행 담당은 제공자이며 제공자 완료 기록이 있다. 앱 의존성 패치의 수행 담당은 고객이지만 완료 기록은 없다. 파일 권한 점검의 수행 담당도 고객이며 설정 스냅샷은 있으나 실제 읽기 시험은 수행하지 않았다. 세 항목의 확인된 범위를 구분하라.

  1. 기반 패치는 문제에서 완료 기록이 주어진 항목이다.

  2. 앱 패치는 담당자만 정해졌으며 실제 완료 근거가 없다.

  3. 권한은 설정표를 읽을 수 있지만 실제 읽기 경로 시험은 미수행이다.

기반 완료 기록, 앱 완료 미확인, 권한 설정 확인 및 실제 읽기 미수행으로 각각 적는다.

소단원 1.3

이용조건·위험·비용 목표

시간당 가격이 낮으면 전체 비용도 항상 낮고 요구도 만족할까?

준비 개념과 학습 목표

준비 개념

  • 단가는 한 단위의 가격이고 사용량×단가는 해당 항목 비용이다. 시간·저장량·전송량을 서로 다른 단위로 센다.

  • 제약은 반드시 만족할 요구이고 목적은 가능한 후보 중 개선할 수치다. 싼 후보라도 필요한 복구·기능을 제공하지 못하면 제외한다.

  • 서비스 약정의 측정 범위와 우리 사용자의 전체 성공 경험은 같지 않을 수 있다. 제외 조건·집계 기간·대응 절차를 확인한다.

학습 목표

  • 가상 비용식의 단위·고정비·변동비·상한을 계산한다.

  • 이용조건과 서비스 수준의 확인 항목을 구체화한다.

  • 수치 목적과 위험·복구 요구를 구분해 후보를 비교한다.

평균 비용이 예산 안이면 모든 달 예산을 지킬까요?

같은 한 달 예산이라도 매달 지키는 상한과 여러 달의 평균 목표는 다르다. 큰 전송량이 가끔 발생하면 평균은 낮아도 특정 달의 비용은 높을 수 있다. 기본 본문의 자체 비용식 C=20+0.10h+0.02g+0.05e를 이어 쓰되, 실제 가격이나 청구서로 제시하지 않는다.

h는 계산 시간, g는 월간 저장 청구 단위, e는 과금 전송 GB다. 이 식의 비용단위는 자체 정의이며 세금·할인·요청 요금 등은 제외되어 있다. 허용 후보를 결정할 때는 예산, 복구 상한, 기능 요구를 먼저 확인한다. 공급자의 어떤 약정 범위와 사용자 전체 요청이 같은 사건인지도 따로 적는다.

먼저 확인할 개념
  • 이용조건·위험·비용 목표

    단위별 가상 비용과 예산·복구 제약을 확인한다.

  • 공유책임·서비스 모델

    설정과 앱 장애가 전체 서비스 목표에 남는 이유를 연결한다.

이용조건은 선택한 자료를 기준으로 읽는다

이 단원은 특정 상품 계약의 법률 해석이나 구매 권고를 제공하지 않는다. 사용할 서비스를 고르면 데이터 이용·보관/삭제·지역·접근·내보내기·지원 기능과 현재 공식 조건을 연결해 확인한다. 기능 소개와 계약의 적용 범위가 같다고 가정하지 않는다.

SLA는 서비스별 측정 범위·기간·제외 조건·신청 조건을 가진 약정이다. 자체 사용자 목표는 예를 들어 “수업 시간에 자료 요청 99% 성공, 복구 1시간 이내”처럼 별도로 정할 수 있다. 공급자 기반 가용성과 로그인·고객 앱·네트워크를 포함한 전체 요청 성공은 같은 사건이 아니다.

단위를 넣어 가상 총비용을 만든다

실제 가격이 아닌 자체 월 비용 모형 C=20+0.10h+0.02g+0.05e를 비용단위로 정한다. h는 그달 과금 계산 시간, g는 월간 저장량 청구 단위, e는 과금 전송 GB다. 저장 단가를 시간 단가처럼 곱하지 않는다. 세금·할인·계단 요금·요청 요금·환율·추가 저장 복제는 이 가상 식에 없다.

h=100, g=50, e=200이면 C=20+10+1+10=41이다. 계산 자원을 20시간 줄이면 2가 줄지만 전송이 100GB 늘면 5가 늘어 총 44가 된다. CPU 시간 최적화만으로 총비용 감소를 결론낼 수 없는 반례다. 실제 청구서는 상품별 요금 구조와 사용량 계측으로 별도 확인한다.

예산을 만족해도 기능과 위험을 따진다

동일한 g=50, h=100에서 월 예산 50을 요구하면 20+10+1+.05e≤50이므로 e≤380 GB다. 사용량이 그 상한을 넘지 않는다는 운영 조건이 필요하다. 예산 알림은 이미 발생한 비용을 자동 취소하는 상한 장치라고 가정하지 않는다.

후보 X는 비용41/복구시간 상한3시간, Y는 비용46/복구시간 상한 0.5시간이라는 가상 계약을 비교한다. 복구 1시간 이내가 필수이면 Y만 가능하다. 두 상한이 실제 모든 허용 장애에서 유효한지는 별도 근거가 필요하며 평균 복구시간으로 대신할 수 없다. 위험 사건·가능성·영향을 적고 남은 가정을 기록한다.

평균을 내기 전에 각 상태의 비용과 확률을 적는다. 가능한 최대 비용은 기대값과 다른 열에 둔다.

중간 과정을 따라가는 예제

가상 식 C=20+.10h+.02g+.05e에서 h=100, g=50, e=200의 비용과 h=80, g=50, e=300의 비용을 구하고 예산 50의 e 상한을 계산하라.

  1. 처음 비용20+10+1+10=41이다.

  2. 변경 비용20+8+1+15=44로3 증가한다.

  3. h=100, g=50을 고정하면31+.05e≤50, 따라서 e≤380이다.

41→44이며 전송 증가가 계산시간 절감을 넘는다. 고정한 가상 모형에서 예산 상한 전송량380GB다.

조건을 바꾸어 비교하기

평균은 낮아도 예산 초과는 남는다

h=100, g=50을 유지한다. 전송 e는 200 GB일 확률 3/4, 600 GB일 확률 1/4라는 자체 모형이다. 기대 비용과 예산 50의 초과 확률을 구하라.

  1. 두 비용은 41과 61이다.

  2. 기대 비용은 (3/4)×41+(1/4)×61=46이다.

  3. 61인 상태만 예산을 초과하므로 초과 확률은 1/4=25%다.

기대 비용 46과 예산 초과 확률 25%가 동시에 성립한다. 실제 사용량을 관측해 얻은 확률이 아니다.

비교할 점

기본 본문의 동일 확률 사례와 달리 평균이 예산 아래여도 초과가 남는 사례다.

기반 성공과 사용자 성공의 분모

가상 1,000개 요청에서 기반 서비스는 995개에 이용 가능했다. 그중 15개는 고객 앱 오류로 실패하고 나머지는 성공했다. 기반이 이용 불가한 5개도 최종 실패했다. 두 성공 비율을 같은 분모로 구하라.

  1. 기반 이용 가능 비율은 995/1000=99.5%다.

  2. 사용자 최종 성공 수는 995−15=980개다.

  3. 사용자 성공 비율은 980/1000=98%다. 같은 사건을 측정한 것이 아니다.

기반 이용 가능 99.5%와 최종 성공 98%다. 이 가상 요청비율은 실제 SLA의 가용 시간이나 약정 해석이 아니다.

다른 문제에 적용하기

동아리 수업 앱의 후보와 운영 근거 연결하기

동아리는 언어 L의 자기 앱을 배포하지만 OS 직접 변경은 필요 없다. 가상 I와 P는 L 배포를 제공하고 S는 제공자 앱만 쓴다. 두 배포 가능 후보의 조건은 I: 비용 44/복구 상한 2시간, P: 비용 48/복구 상한 0.75시간이다. 예산≤50과 복구≤1시간이 필수이고 상한의 장애 범위는 동일하다. 선택한 앱의 정책 P_set은 {(교사,성적),(교사,자료),(학생,자료)}인데 현재 허용 A_set은 {(교사,성적),(교사,자료),(익명,성적)}이다. 서비스 제공자는 기반 패치를 완료했지만 실제 읽기 시험은 수행하지 않았다. 허용 후보, 두 권한 오류, 필요한 수정과 확인 범위를 한 보고서에 적어라.

힌트 1

기능 요구와 비용·복구 제약을 차례로 적용한다.

힌트 2

과도한 허용과 필요한 허용 누락을 다른 집합 차이로 비교한다.

풀이와 답 확인

  1. 기능으로 I와 P가 남고 S는 제외된다. 복구 제약에서 I가 제외되어 P만 두 제약을 만족한다.

  2. A_set−P_set은 {(익명,성적)}이고 P_set−A_set은 {(학생,자료)}다.

  3. 익명 성적 읽기를 삭제하고 학생 자료 읽기를 추가하면 가상 표는 A_set=P_set이 된다.

  4. 제공자 기반 패치 완료는 주어진 별도 사실이다. 설정 수정의 실제 적용 및 읽기 경로 시험과 앱 의존성 등 남은 고객 작업은 따로 확인해야 한다. 실제 데이터 유출이나 실제 배포 성공은 이 표로 증명하지 않는다.

가상 후보 P를 선택한다. 권한표에는 과도한 허용 1개와 필요한 허용 누락 1개가 있으므로 각각 삭제와 추가가 필요하다. 수정 계획과 실제 적용·시험을 구분한다.

해결한 뒤 점검할 것

  • 서비스 능력과 필수 제약으로 후보를 걸러 낸다.

  • 동일 원소 수와 집합 내용 일치를 구별한다.

  • 두 권한 오류를 서로 다른 편집으로 복구한다.

  • 제공자 완료 기록과 고객 설정·실제 시험의 범위를 나눈다.
