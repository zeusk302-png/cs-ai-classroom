소단원 1.1

IaaS·PaaS·SaaS

서버를 빌리는 것, 만든 앱을 배포하는 것, 완성된 앱을 쓰는 것은 같은 선택일까?

준비 개념과 학습 목표

준비 개념

  • 서버는 다른 프로그램의 요청에 응답하는 프로그램 또는 이를 실행하는 장치다. 네트워크는 장치 사이 데이터를 전달하며 파일은 이름 있는 데이터 저장 단위다.
  • 운영체제는 CPU·메모리·장치 사용을 관리한다. 런타임은 응용 코드를 실행하는 환경이고 응용은 사용자 기능을 제공한다.
  • 제공자와 고객의 경계: 어떤 층을 직접 설정·교체할 수 있는지와 어떤 기능을 요청해 쓰는지를 구분한다.

학습 목표

  • 세 모델을 고객에게 제공되는 능력과 통제 범위로 분류한다.
  • 서비스 모델과 배포 모델·상품 이름을 구분한다.
  • 작은 기능 요구에 필요한 운영 층을 표로 추적한다.

구름이라는 이름보다 제공 능력을 본다

NIST의 클라우드 정의는 네트워크로 필요할 때 공유 자원을 제공받는 모형이다. 셀프서비스·넓은 네트워크 접근·자원 풀·빠른 탄력성·사용량 측정이라는 다섯 특성을 함께 본다. 단지 원격 컴퓨터라는 이유만으로 그 정의의 모든 특성을 만족한다고 단정하지 않는다.

서비스 모델은 고객에게 무엇을 제공하는지 구분한다. IaaS는 OS와 앱을 올릴 기본 계산·저장·네트워크 자원, PaaS는 지원 환경에 고객 앱을 배포하는 능력, SaaS는 제공자 앱을 사용하는 능력이다. 여기서 분류의 근거는 VM·웹·컨테이너라는 단어 하나가 아니다.

통제하는 층에 따라 작업이 달라진다

전형적인 IaaS 고객은 게스트 OS와 배포 앱을 관리한다. PaaS는 기반 OS를 직접 관리하지 않고 고객 앱과 허용된 호스팅 설정을 다룬다. SaaS는 제공자 앱을 사용하며 허용된 사용자 설정을 다룬다. 실제 서비스가 제공하는 세부 통제·책임은 문서와 계약에 따라 정해야 한다.

자체 수업용 표를 정하자. 기능은 게시판이며 데이터와 접근 권한은 고객이 관리한다. I에서는 고객 OS·런타임·앱, P에서는 제공자 OS·런타임과 고객 앱, S에서는 제공자 앱을 사용한다. 이 표는 모델 비교를 위한 가정으로, 모든 상품의 세부 기능을 대표하지 않는다.

배포 위치와 서비스 모델은 다른 축이다

Public/private/community/hybrid는 배포 모델의 구분이고 IaaS/PaaS/SaaS는 서비스 능력의 구분이다. 사설 클라우드에서도 SaaS 형태를 제공할 수 있으므로 public과 SaaS를 동의어로 쓰지 않는다. 같은 시스템 안에 여러 서비스 모델을 조합할 수도 있다.

더 많은 층을 맡기면 고객의 일부 유지보수 작업은 줄지만 앱 코드·데이터·계정·설정의 판단이 자동으로 없어지지 않는다. 선택은 필요한 통제, 기능 제약, 운영 능력과 비용을 함께 비교해야 한다. 설치 없는 책임표로 모델을 이해한 뒤 특정 상품은 공식 문서에서 다시 확인한다.

중간 과정을 따라가는 예제

위 가상 I/P/S 게시판에서 기반 OS 패치, 고객 앱 배포, 게시물 읽기 권한 설정을 누가 다루는지 표를 만들어라.

  1. I의 OS 패치는 고객, P/S의 기반 OS 패치는 제공자로 둔 계약을 읽는다.
  2. 자체 앱 배포는 I/P의 고객 작업이다. S는 제공자 앱 사용이므로 같은 앱 교체 능력을 가정하지 않는다.
  3. 게시물 읽기 권한은 세 경우 모두 고객이 허용 범위에서 설정한다.

I: 고객 OS·앱·권한. P: 제공자 OS/고객 앱·권한. S: 제공자 OS·앱/고객 권한 설정. 실제 상품 책임은 이 가상 표만으로 확정하지 않는다.

종이와 본문으로 직접 해보기

고객이 OS 버전을 직접 바꿔야 한다는 요구와, 제공자 앱의 사용자 설정만 바꾸면 된다는 요구를 각각 I/P/S 표와 비교하라.

힌트 보기

무엇을 사용할 수 있는지와 무엇을 통제할 수 있는지를 구분한다.

풀이 보기

가상 표에서는 직접 OS 변경 요구는 I만 충족한다. 제공자 앱 설정 사용은 S에 맞는다. 특정 상품에 필요한 기능이 실제 있는지는 별도 확인해야 한다.

오해와 반례

브라우저로 쓰는 모든 서비스는 SaaS이고 서버가 있는 서비스는 IaaS다.

브라우저 관리 화면으로 VM을 제어해도 제공 능력은 IaaS일 수 있다. 고객 앱을 실행하는 서버가 있다고 PaaS가 자동 IaaS가 되지 않는다.

소단원 1.2

공유책임·서비스 모델

제공자가 서버를 패치해도 잘못 공개한 고객 파일까지 자동으로 보호될까?

준비 개념과 학습 목표

준비 개념

  • 자산은 보호할 데이터·계정·서비스다. 인증은 누구인지 확인하고 권한은 어떤 자산에 어떤 동작을 허용하는지 정한다.
  • 공유책임은 작업을 막연히 반씩 나눈다는 뜻이 아니다. 자산·층·작업·수행 주체·확인 증거를 지정한다.
  • 논리곱 A∧B는 두 조건이 모두 참이어야 참이다. 기반 보호와 고객 설정이 모두 필요할 수 있다.

학습 목표

  • 서비스별 책임의 경계를 공식 문서와 함께 정한다.
  • 제공자 수행·고객 설정·고객 검증을 분리한다.
  • 권한 사고를 책임표와 불변식으로 추적한다.

공유라는 말은 구체적인 분담을 요구한다

AWS 공식 설명에서 EC2 고객은 게스트 OS·설치 앱·보안그룹 설정을 관리한다. S3/DynamoDB처럼 더 추상화한 서비스에서도 데이터·IAM 권한·암호화 선택의 고객 책임이 남는다. 이것은 각 예시의 공식 분담이며 모든 관리형 저장소를 한 서비스 모델로 뭉뚱그릴 이유가 아니다.

Microsoft의 공식 모델 표 역시 데이터·설정·사용자와 기반 호스트/OS 항목의 분담을 구별한다. 따라서 정확한 표는 선택한 상품·지역·기능·설정·계약을 기준으로 만든다. 보호 기능 제공과 그 기능을 활성화·구성·감사하는 행위는 서로 다른 작업이다.

권한을 상태 모형으로 검사한다

가상 공유 저장소의 계약은 교사 계정만 성적 파일을 읽고 학생은 공개 자료만 읽는 것이다. 권한표는 교사:성적/자료 읽기, 학생:자료 읽기, 익명:없음으로 초기화한다. 제공자가 저장 기반을 패치해도 고객이 성적 파일에 익명 읽기 허용을 추가하면 계약이 깨진다.

주체 s, 자산 o의 실제 읽기 허용 집합 A와 정책 집합 P를 비교한다. 보호 목표는 모든 성공 읽기에 대해 (s, o)∈P이다. A⊆P면 허용 집합의 과도한 공개는 없지만 필요한 읽기가 되는지는 별도 P⊆A 조건이다. 권한 판단뿐 아니라 인증 우회·오래된 링크·캐시 등 실제 경로도 별도로 검사해야 한다.

운영 작업에도 확인 가능한 주체가 있다

수업용 책임표에는 기반 패치 제공자/앱 의존성 패치 고객/권한 설정 고객/백업 보존과 복원은 선택 서비스 계약에 따라 지정이라고 쓴다. 제공자 복제는 실수 삭제 이전 버전을 되찾는 고객 백업과 자동 동의어가 아니다. 복구 가능성을 원하면 보존 정책·복원 경로·검증 근거를 정한다.

공유 항목은 같은 작업을 두 번 맡긴다는 뜻일 수도 있지만 서로 다른 층의 유사 작업인 경우도 있다. 누가 수행하는지 외에 누가 확인하는지, 실패를 누가 관측하고 어떻게 대응하는지를 적어야 빈 책임이 드러난다. 문서를 읽은 사실은 해당 설정이 실제 배포되었다는 증거가 아니다.

중간 과정을 따라가는 예제

위 초기 권한표에서 고객이 성적 파일에 익명 읽기를 허용한다. 제공자의 기반 패치 성공이 정책 불변식을 유지하는지 판단하라.

  1. 정책 P에는 (익명, 성적)이 없다.
  2. 변경된 A에는 (익명, 성적)이 추가된다. 따라서 A⊆P가 아니다.
  3. 기반 패치 성공과 권한 설정 오류는 다른 층이며 패치가 이 허용을 자동 제거한다고 가정하지 않았다.

가상 정책 불변식은 깨진다. 익명 성공 읽기가 실제 발생했다는 관측은 없지만 허용 표에 정책 위반 경로가 생겼다.

힌트 보기

과도한 허용과 필요한 허용의 누락을 별도로 비교한다.

풀이 보기

A⊆P는 유지될 수 있지만 (학생, 자료)∈P가 A에 없으므로 P⊆A는 실패한다. 보안 제한과 기능 가용성은 별도 조건이다.

오해와 반례

관리형 서비스의 제공자가 보안을 맡으므로 고객 설정은 중요하지 않다.

제공자 기반 보호가 정상이어도 가상 익명 성적 읽기 허용은 고객 정책을 깨뜨린다. 책임 층과 성공 읽기 경로를 명시해야 한다.

한 단계 더

읽기/쓰기/공유/삭제를 포함한 (주체, 자산, 동작) 정책으로 확장하라. 관리자가 읽기만 갖는 경우와 권한을 변경할 능력을 갖는 경우를 구분하면 이후의 상태 전이도 위협 모델에 포함해야 한다. 이 종이 표가 실제 IAM 구현의 모든 공격 경로를 검증하지는 않는다.

소단원 1.3

이용조건·위험·비용 목표

시간당 가격이 낮으면 전체 비용도 항상 낮고 요구도 만족할까?

준비 개념과 학습 목표

준비 개념

  • 단가는 한 단위의 가격이고 사용량×단가는 해당 항목 비용이다. 시간·저장량·전송량을 서로 다른 단위로 센다.
  • 제약은 반드시 만족할 요구이고 목적은 가능한 후보 중 개선할 수치다. 싼 후보라도 필요한 복구·기능을 제공하지 못하면 제외한다.
  • 서비스 약정의 측정 범위와 우리 사용자의 전체 성공 경험은 같지 않을 수 있다. 제외 조건·집계 기간·대응 절차를 확인한다.

학습 목표

  • 가상 비용식의 단위·고정비·변동비·상한을 계산한다.
  • 이용조건과 서비스 수준의 확인 항목을 구체화한다.
  • 수치 목적과 위험·복구 요구를 구분해 후보를 비교한다.

이용조건은 선택한 자료를 기준으로 읽는다

이 단원은 특정 상품 계약의 법률 해석이나 구매 권고를 제공하지 않는다. 사용할 서비스를 고르면 데이터 이용·보관/삭제·지역·접근·내보내기·지원 기능과 현재 공식 조건을 연결해 확인한다. 기능 소개와 계약의 적용 범위가 같다고 가정하지 않는다.

SLA는 서비스별 측정 범위·기간·제외 조건·신청 조건을 가진 약정이다. 자체 사용자 목표는 예를 들어 “수업 시간에 자료 요청 99% 성공, 복구 1시간 이내”처럼 별도로 정할 수 있다. 공급자 기반 가용성과 로그인·고객 앱·네트워크를 포함한 전체 요청 성공은 같은 사건이 아니다.

단위를 넣어 가상 총비용을 만든다

실제 가격이 아닌 자체 월 비용 모형 C=20+0.10h+0.02g+0.05e를 비용단위로 정한다. h는 그달 과금 계산 시간, g는 월간 저장량 청구 단위, e는 과금 전송 GB다. 저장 단가를 시간 단가처럼 곱하지 않는다. 세금·할인·계단 요금·요청 요금·환율·추가 저장 복제는 이 가상 식에 없다.

h=100, g=50, e=200이면 C=20+10+1+10=41이다. 계산 자원을 20시간 줄이면 2가 줄지만 전송이 100GB 늘면 5가 늘어 총 44가 된다. CPU 시간 최적화만으로 총비용 감소를 결론낼 수 없는 반례다. 실제 청구서는 상품별 요금 구조와 사용량 계측으로 별도 확인한다.

예산을 만족해도 기능과 위험을 따진다

동일한 g=50, h=100에서 월 예산 50을 요구하면 20+10+1+.05e≤50이므로 e≤380 GB다. 사용량이 그 상한을 넘지 않는다는 운영 조건이 필요하다. 예산 알림은 이미 발생한 비용을 자동 취소하는 상한 장치라고 가정하지 않는다.

후보 X는 비용41/복구시간 상한3시간, Y는 비용46/복구시간 상한 0.5시간이라는 가상 계약을 비교한다. 복구 1시간 이내가 필수이면 Y만 가능하다. 두 상한이 실제 모든 허용 장애에서 유효한지는 별도 근거가 필요하며 평균 복구시간으로 대신할 수 없다. 위험 사건·가능성·영향을 적고 남은 가정을 기록한다.

중간 과정을 따라가는 예제

가상 식 C=20+.10h+.02g+.05e에서 h=100, g=50, e=200의 비용과 h=80, g=50, e=300의 비용을 구하고 예산 50의 e 상한을 계산하라.

  1. 처음 비용20+10+1+10=41이다.
  2. 변경 비용20+8+1+15=44로3 증가한다.
  3. h=100, g=50을 고정하면31+.05e≤50, 따라서 e≤380이다.

41→44이며 전송 증가가 계산시간 절감을 넘는다. 고정한 가상 모형에서 예산 상한 전송량380GB다.

종이와 본문으로 직접 해보기

e=400으로 늘었을 때 비용을 구하라. X: 비용 41/복구 3시간, Y: 비용 46/복구 0.5시간에서 예산 50·복구 1시간 조건을 모두 만족하는 후보를 골라라.

힌트 보기

비용 목적을 비교하기 전에 두 제약을 각각 적용한다.

풀이 보기

C=31+20=51로 예산 위반이다. X/Y의 비용은 둘 다50 이하지만 복구 조건은 Y만 만족한다. 가상 상한이 타당하다는 전제에서 Y가 가능하다.

오해와 반례

최저 계산 단가와 SLA 숫자 하나면 가장 좋은 전체 서비스가 정해진다.

계산 비용 2 절감/전송 비용 5 증가의 총비용 반례와 싼 X의 복구 실패를 보라. 전체 요청 성공 범위와 약정 제외 조건도 별도이다.

한 단계 더

가상 사용량 e의 분포를 정하면 기대 비용과 예산 초과 확률을 따로 구할 수 있다. 기대 비용≤50은 모든 달 비용≤50과 다르다. 예를 들어 e=200/600이 각각 절반이면 기대 비용 51이지만 실제 비용41/61이고, 다른 분포에서는 기대가50보다 낮아도 큰 초과 사건이 남을 수 있다. 확률·상한·중단 정책의 목적을 구분하라.
