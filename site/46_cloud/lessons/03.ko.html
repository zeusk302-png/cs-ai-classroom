소단원 3.1

CPU·메모리·I/O 가상화

두 운영체제가 같은 컴퓨터를 자기 것처럼 쓰려면 무엇을 나누어야 할까?

준비 개념과 학습 목표

준비 개념

  • 프로그램의 명령은 CPU에서 실행된다. 레지스터·PC 같은 상태를 저장하면 다른 실행으로 전환할 수 있다.

  • 주소는 이름이고 프레임은 실제 저장 구역이다. 페이지 번호와 페이지 안 offset을 나누어 계산한다.

  • 게스트는 VM 안의 운영체제, 호스트는 그 VM을 제공하는 쪽이다. 가상 CPU 개수와 실제 동시 실행 코어 수는 구별한다.

학습 목표

  • CPU 실행과 특권 통제의 역할을 나눈다.

  • 두 단계 주소 변환을 계산한다.

  • 장치 모델·준가상화·장치 전달의 조건을 설명한다.

CPU를 실행하게 하면서 통제한다

VMM은 게스트 운영체제가 보게 될 CPU·메모리·장치를 제공하고 실제 자원 사용을 조정한다. vCPU는 게스트에 보이는 실행 단위이며 호스트의 실행 자원에 배정된다. vCPU가 여덟 개라도 실제 코어가 두 개면 여덟 개가 모두 같은 순간 전용 코어를 갖는다는 뜻은 아니다. 게스트 스케줄러와 호스트 스케줄러의 선택이 겹쳐 대기가 생길 수 있다.

지원되는 하드웨어 가상화에서는 많은 게스트 명령이 CPU에서 직접 실행되고 통제해야 할 사건에 VMM이 개입한다. 에뮬레이션은 명령과 장치의 동작을 소프트웨어로 구현하는 방법이다. 같은 명령 집합의 하드웨어 가속과 다른 명령 집합의 에뮬레이션을 구별한다. 역사적 trap-and-emulate 사례를 모든 syscall마다 동일한 VM exit가 생긴다는 주장으로 바꾸지 않는다.

게스트의 물리 주소도 한 번 더 번역한다

게스트 프로그램의 가상 주소를 게스트 OS가 게스트 물리 주소로 바꾼다. 그 주소가 어느 호스트 메모리에 연결되는지는 VMM과 하드웨어가 관리한다. 개념적으로 가상 페이지→게스트 물리 프레임→호스트 물리 프레임이라는 두 단계다. 각 매핑이 유효하고 접근 권한을 만족해야 읽기나 쓰기가 가능하다.

offset은 페이지 크기가 같은 이 작은 모형에서 두 단계 모두 보존된다. shadow table은 두 변환을 합친 매핑을 유지하는 방법이고, 하드웨어의 중첩 변환은 단계별 테이블을 지원하는 방법이다. TLB가 결과를 재사용하므로 매번 동일 개수의 테이블 메모리 접근이 발생한다고 단정하지 않는다. KVM API의 userspace 주소는 호스트 물리 주소 그 자체가 아니라 호스트 프로세스의 주소라는 점도 구별한다.

장치가 보여 주는 인터페이스와 실제 요청을 잇는다

에뮬레이션 장치는 게스트 드라이버가 아는 인터페이스의 읽기·쓰기를 받아 호스트의 파일·네트워크 같은 backend 작업으로 연결한다. VirtIO처럼 가상 환경을 고려한 인터페이스는 게스트와 제공자가 요청 정보를 나누어 일부 비용을 줄일 수 있다. 요청이 끝나면 게스트에 완료 통지가 필요하며 실제 저장장치 시간은 가상화만으로 없어지지 않는다.

장치 전달은 지원되는 장치를 게스트에 직접 배정해 장치 에뮬레이션 경로를 줄일 수 있지만 메모리 접근 격리, 장치 재설정, 공유 가능성 및 이동 제약을 따져야 한다. CPU 메모리 매핑만 보호한다고 DMA까지 자동 보호된다고 가정하지 않는다. KVM의 I/O/MMIO exit 정보는 처리 경로의 예이며 모든 I/O를 반드시 동일한 경로로 처리한다는 규칙은 아니다.

중간 과정을 따라가는 예제

페이지 크기 4096B, 가상 페이지 2의 offset 37이 게스트 프레임 7, 그 프레임이 호스트 프레임 11에 매핑된다. 접근은 유효하다. 두 주소를 계산하라. 또 한 물리 코어에서 A/B vCPU가 4ms씩 번갈아 실행하고 전환 비용이 0일 때 8ms 동안의 실행량은?

  1. 가상 주소는 2×4096+37=8229B다. offset 37은 페이지 범위 안이다.

  2. 게스트 물리 주소는 7×4096+37=28709B다. 이 숫자를 바로 호스트 주소로 쓰지 않는다.

  3. 호스트 물리 주소는 11×4096+37=45093B다. 동일한 offset과 다른 프레임 번호를 확인한다.

  4. 0..4ms A, 4..8ms B여서 각 4ms, 총 8ms CPU 실행이다. 두 vCPU가 각 8ms씩 실행한 총 16ms로 계산하지 않는다.

게스트 주소 28709B, 호스트 주소 45093B, A/B 실행 각 4ms다. 가상 자원 이름을 늘리는 것과 실제 처리량은 별개다.

오해와 반례

소단원 3.2

VM 이미지·격리

같은 출발 디스크에서 만든 두 VM의 변경은 서로에게 보일까?

준비 개념과 학습 목표

준비 개념

  • 디스크 이미지는 게스트 저장장치 내용을 담는 자료다. 실행 중 RAM이나 CPU 상태와 구별한다.

  • copy-on-write는 공유된 원본을 직접 바꾸지 않고 변경한 부분을 별도 위치에 기록하는 방법이다.

  • 격리는 어떤 주체가 어떤 자원에 접근할 수 있는지를 나누는 속성이다. 성능·네트워크·저장·비밀정보의 경계를 각각 따진다.

학습 목표

  • 이미지·디스크 snapshot·전체 VM snapshot을 구별한다.

  • 공유 base와 개별 overlay의 읽기·쓰기를 추적한다.

  • 데이터 격리와 완전한 보안 보장을 분리한다.

이미지 하나가 실행 전체를 담는 것은 아니다

부팅 가능한 디스크 이미지는 OS 파일·설정·응용 데이터 등의 저장 내용을 담을 수 있다. 가상 CPU 개수, 메모리 용량, 가상 장치와 네트워크 연결은 별도 실행 설정이다. 디스크 파일을 복사했다는 것만으로 현재 실행 중 프로그램의 레지스터·RAM·외부 서비스 상태까지 복사했다고 말하지 않는다.

전체 VM snapshot은 지원되는 범위에서 CPU·RAM·장치·디스크 상태를 함께 저장한다. 디스크 snapshot만으로는 그 범위가 다르다. 실행 중 DB가 디스크에 남기지 않은 변경이나 여러 디스크 사이의 쓰기 순서가 있으면 일관성 조건이 필요하다. 실제 도구의 지원 장치·snapshot 종류·정지/동기화 절차를 확인해야 한다.

공유 base와 개별 overlay에서 읽는다

두 VM이 변경하지 않는 base를 읽고 각자 overlay에 쓰도록 구성하면, 읽기는 우선 자신의 overlay에서 해당 블록을 찾고 없으면 base로 내려간다. A가 블록2를 바꿔도 B의 overlay와 불변 base를 바꾸지 않았다면 B는 원래 블록2를 본다. 이 구조는 원본 자체를 모든 VM이 동시에 쓰는 공유 디스크와 다르다.

논리 디스크 크기와 실제 저장 공간도 다르다. 빈 영역을 실제로 배정하지 않는 sparse 형식과 변경 블록 공유는 공간을 줄일 수 있지만 metadata·정렬·압축·중복·예약 정책에 따라 실제 사용량은 달라진다. overlay만 옮기고 필요한 backing image를 빠뜨리면 완전한 디스크 내용을 재구성하지 못할 수 있다.

격리 범위는 여러 층에 걸친다

게스트 메모리의 권한 매핑과 각 VM의 저장 연결을 분리하면 다른 VM의 자료를 직접 읽는 경로를 제한한다. 그러나 잘못 연결한 공유 폴더, 공통 관리자 자격, 공개 네트워크 서비스, 이미지에 넣은 비밀키는 이 경계를 우회할 수 있다. 격리를 설정한 각 경로와 권한을 구체적으로 적는다.

VM은 VMM·호스트와 자원을 공유하므로 구현 취약점과 cache·대역폭 경쟁 등의 영향 가능성이 남는다. 파일 변경이 분리된다는 검증을 모든 부채널과 성능 간섭의 제거로 확대하지 않는다. rollback은 과거 상태 복원이며 외부에서 이미 처리한 요청·보낸 이메일·타 시스템 변경을 자동 취소하지 않는다.

중간 과정을 따라가는 예제

불변 base의 블록0..3=[A,B,C,D]를 공유하고 XA={1:X}, XB={2:Y} overlay를 각 VM이 사용한다. 각 읽기 결과와 A가 블록2에 Z를 쓴 뒤 B의 결과를 구하라. 각 블록1MiB, metadata 없음인 공간 모형도 계산하라.

  1. A는 자신의 블록1 변경을 우선 읽어 [A,X,C,D]다. B는 블록2 변경을 우선 읽어 [A,B,Y,D]다.

  2. A가 쓰면 XA={1:X,2:Z}가 되며 base는 그대로다. A는 [A,X,Z,D]다.

  3. XB는 변하지 않아 B는 [A,B,Y,D]다. A의 Z가 B에 자동 전파되지 않는다.

  4. 처음 base4+XA1+XB1=6MiB, 추가 뒤 4+2+1=7MiB다. 두 완전 복사8MiB와 비교하는 metadata 없는 종이 모형이며 실제 파일 크기가 아니다.

각 VM은 자기 overlay가 우선이다. 변경 후 A=[A,X,Z,D], B=[A,B,Y,D], 모형 공간7MiB다.

종이와 본문으로 직접 해보기

힌트 보기

소단원 3.3

하이퍼바이저와 성능

직접 실행을 하는 VM도 왜 느려질 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 하이퍼바이저는 여러 게스트의 실행과 자원 연결을 통제하는 VMM이다. 구현은 호스트 kernel·userspace·장치 backend 여러 부분에 나뉠 수 있다.

  • 경과시간은 CPU 작업시간과 대기·I/O·다른 원인까지 포함한다. 같은 작업과 환경을 비교해야 느려짐을 계산할 수 있다.

  • 비율은 분모를 명시한다. VM 시간/기준 시간과 추가시간/기준 시간은 서로 다른 수치다.

학습 목표

  • 하이퍼바이저 구조와 실제 실행 경로를 연결한다.

  • 작업별 가상화 비용 모형을 계산한다.

  • 공정한 성능 비교와 병목 원인 추론의 한계를 설명한다.

분류 이름보다 실행 경로를 확인한다

하드웨어 위에서 직접 관리하는 구성과 호스트 OS 위에 제공되는 구성은 흔히 type1/type2로 분류된다. 하지만 실제 시스템은 kernel 가속과 userspace 장치 모델을 조합할 수 있어 단일 이름만으로 비용을 예측하기 어렵다. QEMU라는 프로그램 이름만으로 TCG인지 KVM 등의 가속인지 판단하지 않고 실행 설정과 지원 조건을 확인한다.

게스트는 가상 CPU를 실행하고 특정 사건에서 제공자 처리가 필요하다. 장치 요청 전달, 메모리 변환, 호스트 스케줄링, 저장과 네트워크 backend가 함께 시간에 영향을 준다. 게스트가 아무 일도 안 하면서 바쁘게 spin하면 호스트가 유용한 VM에 자원을 주기 어려운 정보 간극이 생길 수 있다. idle 통지 같은 협력 인터페이스는 이 간극을 줄이는 방법이다.

횟수와 한 번의 비용을 곱하는 작은 모형

겹침이 없는 단순 모형에서 Tvm=Tbase+Ne×ce+Tm+Ti+Tw로 적는다. Ne는 추가 개입 횟수, ce는 그때 평균 비용, Tm은 별도 주소 변환 비용, Ti는 별도 I/O 추가 비용, Tw는 호스트 대기다. 각 항은 기준 실행과 비교해 늘어난 부분만 넣으며 같은 VM exit를 여러 항에 중복 계산하지 않는다.

실제로는 cache·메모리·I/O가 겹치거나 다른 실행과 경쟁하고 일부 비용이 줄 수도 있다. 따라서 이 합식은 가정한 종이 모형이지 모든 성능을 설명하는 측정 법칙이 아니다. 개입 횟수가 같아도 장치 종류·batch 크기·cache 상태에 따라 ce가 달라질 수 있으며 직접 실행한다고 나머지 항이 0이 되지 않는다.

작업량과 분모를 고정해서 비교한다

같은 데이터·결과·동시 사용자·가상 CPU/실제 코어·메모리·저장·cache 상태에서 경과시간과 처리량을 기록한다. 짧은 요청은 평균뿐 아니라 분위수와 꼬리 지연도 중요하다. 호스트의 다른 작업, 전력/주파수 변화, warm-up, VM 생성 시간을 포함했는지를 기록해야 반복 비교가 가능하다.

많은 CPU 연산만 하는 workload와 I/O·동기화가 빈번한 workload의 느려짐은 다를 수 있다. 가상화 기능을 끄거나 바꾸는 비교 실험에서 여러 조건을 동시에 변경하면 단일 원인을 확정하기 어렵다. 이 단원의 숫자는 설계 비용의 종이 계산이며 실제 클라우드 공급자 성능·가격·보안 순위를 측정한 것이 아니다.

중간 과정을 따라가는 예제

같은 작업의 기준 경과시간은 100ms다. 겹침 없는 모형에서 추가 개입은 1000회×2μs, 추가 변환 3ms, I/O 추가 4ms, 호스트 대기 11ms다. 개입을 200회로 줄이고 대신 I/O 추가가 5ms가 되면 얼마나 달라지는가?

  1. 1000×2μs=2000μs=2ms다. 나머지는 추가 항이며 기준100ms에 이미 포함된 시간은 다시 더하지 않는다.

  2. 초기 Tvm=100+2+3+4+11=120ms다. 시간비1.2, 추가율20%, 같은 작업 처리량비100/120=5/6이다.

  3. 새 개입 항은 .4ms다. 새 Tvm=100+.4+3+5+11=119.4ms다.

  4. 초기 대비 .6ms 줄었고 시간 감소율 .6/120=.5%다. 개입 항 감소80%를 전체 실행80% 개선으로 읽지 않는다.

120→119.4ms, 전체 시간 감소 .5%다. 비용 한 항의 감소와 전체 효과를 구별한다.
