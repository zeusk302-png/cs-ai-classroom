소단원 3.1

CPU·메모리·I/O 가상화

두 운영체제가 같은 컴퓨터를 자기 것처럼 쓰려면 무엇을 나누어야 할까?

준비 개념과 학습 목표

준비 개념

  • 프로그램의 명령은 CPU에서 실행된다. 레지스터·PC 같은 상태를 저장하면 다른 실행으로 전환할 수 있다.

  • 주소는 이름이고 프레임은 실제 저장 구역이다. 페이지 번호와 페이지 안 offset을 나누어 계산한다.

  • 게스트는 VM 안의 운영체제, 호스트는 그 VM을 제공하는 쪽이다. 가상 CPU 개수와 실제 동시 실행 코어 수는 구별한다.

학습 목표

  • CPU 실행과 특권 통제의 역할을 나눈다.

  • 두 단계 주소 변환을 계산한다.

  • 장치 모델·준가상화·장치 전달의 조건을 설명한다.

같은 게스트 프레임 번호가 같은 실제 메모리를 뜻할까요?

아파트마다 301호라는 이름이 있어도 건물이 다르면 다른 집이다. VM의 게스트 물리 프레임도 VM별 이름이다. 기본 본문의 두 단계 변환에서 이번에는 게스트 두 개의 표와 읽기·쓰기 권한을 함께 추적한다. 모든 페이지는 4096바이트이고 offset은 0부터 4095까지다.

작은 모형에서 각 VM의 가상 페이지 변환 g 뒤에 그 VM의 게스트 프레임 변환 h를 적용한다. 두 단계 모두 존재하고 요청 동작이 각 단계 권한을 만족해야 한다. 주소 산술이 가능하다는 이유로 읽기나 쓰기를 허용하지 않는다. 실제 CPU 페이지 형식·TLB 동작·KVM 호출을 실행한 모형은 아니다.

먼저 확인할 개념
  • CPU·메모리·I/O 가상화

    가상 주소·게스트 주소·호스트 주소와 동일 offset의 두 단계 변환을 사용한다.

  • VM 이미지·격리

    이름 분리와 접근 경로·권한이라는 격리 조건을 연결한다.

CPU를 실행하게 하면서 통제한다

VMM은 게스트 운영체제가 보게 될 CPU·메모리·장치를 제공하고 실제 자원 사용을 조정한다. vCPU는 게스트에 보이는 실행 단위이며 호스트의 실행 자원에 배정된다. vCPU가 여덟 개라도 실제 코어가 두 개면 여덟 개가 모두 같은 순간 전용 코어를 갖는다는 뜻은 아니다. 게스트 스케줄러와 호스트 스케줄러의 선택이 겹쳐 대기가 생길 수 있다.

지원되는 하드웨어 가상화에서는 많은 게스트 명령이 CPU에서 직접 실행되고 통제해야 할 사건에 VMM이 개입한다. 에뮬레이션은 명령과 장치의 동작을 소프트웨어로 구현하는 방법이다. 같은 명령 집합의 하드웨어 가속과 다른 명령 집합의 에뮬레이션을 구별한다. 역사적 trap-and-emulate 사례를 모든 syscall마다 동일한 VM exit가 생긴다는 주장으로 바꾸지 않는다.

게스트의 물리 주소도 한 번 더 번역한다

게스트 프로그램의 가상 주소를 게스트 OS가 게스트 물리 주소로 바꾼다. 그 주소가 어느 호스트 메모리에 연결되는지는 VMM과 하드웨어가 관리한다. 개념적으로 가상 페이지→게스트 물리 프레임→호스트 물리 프레임이라는 두 단계다. 각 매핑이 유효하고 접근 권한을 만족해야 읽기나 쓰기가 가능하다.

offset은 페이지 크기가 같은 이 작은 모형에서 두 단계 모두 보존된다. shadow table은 두 변환을 합친 매핑을 유지하는 방법이고, 하드웨어의 중첩 변환은 단계별 테이블을 지원하는 방법이다. TLB가 결과를 재사용하므로 매번 동일 개수의 테이블 메모리 접근이 발생한다고 단정하지 않는다. KVM API의 userspace 주소는 호스트 물리 주소 그 자체가 아니라 호스트 프로세스의 주소라는 점도 구별한다.

장치가 보여 주는 인터페이스와 실제 요청을 잇는다

에뮬레이션 장치는 게스트 드라이버가 아는 인터페이스의 읽기·쓰기를 받아 호스트의 파일·네트워크 같은 backend 작업으로 연결한다. VirtIO처럼 가상 환경을 고려한 인터페이스는 게스트와 제공자가 요청 정보를 나누어 일부 비용을 줄일 수 있다. 요청이 끝나면 게스트에 완료 통지가 필요하며 실제 저장장치 시간은 가상화만으로 없어지지 않는다.

장치 전달은 지원되는 장치를 게스트에 직접 배정해 장치 에뮬레이션 경로를 줄일 수 있지만 메모리 접근 격리, 장치 재설정, 공유 가능성 및 이동 제약을 따져야 한다. CPU 메모리 매핑만 보호한다고 DMA까지 자동 보호된다고 가정하지 않는다. KVM의 I/O/MMIO exit 정보는 처리 경로의 예이며 모든 I/O를 반드시 동일한 경로로 처리한다는 규칙은 아니다.

중간 과정을 따라가는 예제

페이지 크기 4096B, 가상 페이지 2의 offset 37이 게스트 프레임 7, 그 프레임이 호스트 프레임 11에 매핑된다. 접근은 유효하다. 두 주소를 계산하라. 또 한 물리 코어에서 A/B vCPU가 4ms씩 번갈아 실행하고 전환 비용이 0일 때 8ms 동안의 실행량은?

  1. 가상 주소는 2×4096+37=8229B다. offset 37은 페이지 범위 안이다.

  2. 게스트 물리 주소는 7×4096+37=28709B다. 이 숫자를 바로 호스트 주소로 쓰지 않는다.

  3. 호스트 물리 주소는 11×4096+37=45093B다. 동일한 offset과 다른 프레임 번호를 확인한다.

  4. 0..4ms A, 4..8ms B여서 각 4ms, 총 8ms CPU 실행이다. 두 vCPU가 각 8ms씩 실행한 총 16ms로 계산하지 않는다.

게스트 주소 28709B, 호스트 주소 45093B, A/B 실행 각 4ms다. 가상 자원 이름을 늘리는 것과 실제 처리량은 별개다.

조건을 바꾸어 비교하기

주소와 허용 동작을 두 번 확인

표에서 offset 100의 A/B 읽기와 쓰기를 판단하고 게스트·호스트 주소를 구하라.

  1. 두 VM의 게스트 주소는 7×4096+100=28772바이트다.

  2. A의 호스트 주소는 11×4096+100=45156, B는 20×4096+100=82020바이트다.

  3. A 읽기는 두 단계에서 허용되나 쓰기는 호스트 단계가 막는다. B는 읽기·쓰기 모두 허용된다.

같은 게스트 주소 숫자와 다른 호스트 주소다. A 쓰기는 산술 결과가 있어도 완료할 수 없다.

비교할 점

기본 변환 예제에 VM별 표와 동작 권한을 더한다.

두 vCPU와 전환 시간

물리 코어 한 개에서 A는 0–3 ms 실행, 3–4 ms 전환, B는 4–7 ms 실행, 7–8 ms 전환한다. 겹침은 없다. 각 실행량과 전환 비중을 구하라.

  1. A와 B의 CPU 실행은 각 3 ms다.

  2. 전환은 총 2 ms이고 전체 구간은 8 ms다.

  3. 유용한 실행 합 6 ms와 전환 2 ms의 합이 전체 8 ms다. 전환 비중은 2/8=25%다.

A/B 각 3 ms, 전환 25%다. 각 VM이 8 ms씩 실행했다고 합산하지 않는다.

비교할 점

기본 전환 비용 0이라는 가정을 풀어 시간 예산을 추적한다.

연습 1 · 값과 상태 예측

표의 B에서 offset 4095로 읽는 호스트 주소와 offset 4096을 같은 페이지 안 위치로 사용할 수 있는지 답하라.

힌트 1

프레임 20의 시작 주소에 offset을 더한다.

힌트 2

offset 상한은 페이지 크기보다 1 작다.

풀이와 답 확인

  1. 20×4096+4095=86015바이트다.

  2. 4096은 다음 페이지 범위이므로 현재 페이지의 유효 offset이 아니다.

86015바이트다. offset 4096의 요청은 페이지 번호·매핑을 다시 나누어 검사해야 한다.

흔한 오답에서 다시 생각하기

프레임 20에 4096을 그냥 더해 접근한다.

그 결과는 다른 페이지 시작이다. 그 페이지의 변환·권한이 유효한지 주어지지 않았다.

연습 2 · 오류 찾아 고치기

A의 가상 페이지 2→게스트 프레임 7은 유효하지만 7의 호스트 매핑이 없다. 이전의 호스트 프레임 11을 임의로 재사용해 읽겠다는 풀이를 고쳐라.

힌트 1

각 단계 존재 여부를 차례로 검사한다.

힌트 2

사라진 매핑을 주소 계산으로 만들 수 없다.

풀이와 답 확인

  1. 첫 단계는 게스트 프레임 7을 준다.

  2. 두 번째 단계가 없으므로 읽기 완료를 결정할 호스트 주소를 제공하지 않는다.

  3. 예외·할당·오류 처리 경로는 실제 구현 계약을 확인해야 한다.

이 상태에서는 선언된 두 단계 읽기를 완료할 수 없다. 이전 숫자 11은 현재 유효 매핑의 증거가 아니다.

흔한 오답에서 다시 생각하기

예전 계산에서 11이었으니 아직 같은 주소다.

주소 변환 표는 상태다. 현재 존재하지 않는 매핑에 과거 값을 적용하지 않는다.

연습 3 · 직접 만들어 보기

A의 가상 페이지 2와 3이 각각 게스트 프레임 7과 8로 가고 두 프레임이 모두 호스트 프레임 11로 간다. 공유가 의도되고 권한이 허용된 모형이다. offset 5의 두 주소와 공유 여부를 표로 만들어라.

힌트 1

합성 h(g(VPN))을 두 가상 페이지에 적용한다.

힌트 2

다른 이름이 반드시 다른 실제 프레임이 되는 것은 아니다.

풀이와 답 확인

  1. 페이지 2: g(2)=7, h(7)=11이다. 페이지 3: g(3)=8, h(8)=11이다.

  2. 두 호스트 주소는 모두 11×4096+5=45061바이트다.

  3. 같은 물리 위치를 가리키는 별칭이다.

두 페이지 이름은 다르나 해당 offset의 실제 위치가 같다. 이 의도적 공유 사례를 모든 VM 간 공유로 일반화하지 않는다.

흔한 오답에서 다시 생각하기

다른 가상 페이지이므로 서로 다른 자료다.

합성 변환이 일대일이라는 조건은 주어지지 않았다. 마지막 프레임과 offset을 비교한다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

두 단계의 동작 허용 집합은 Rg={읽기,쓰기}, Rh={읽기}다. 허용 동작을 교집합으로 나타내고 합집합을 쓰면 왜 문제가 되는지 설명하라.

힌트 1

두 조건을 동시에 통과해야 한다.

힌트 2

한 단계만 허용하는 동작을 찾아라.

소단원 3.2

VM 이미지·격리

같은 출발 디스크에서 만든 두 VM의 변경은 서로에게 보일까?

준비 개념과 학습 목표

준비 개념

  • 디스크 이미지는 게스트 저장장치 내용을 담는 자료다. 실행 중 RAM이나 CPU 상태와 구별한다.

  • copy-on-write는 공유된 원본을 직접 바꾸지 않고 변경한 부분을 별도 위치에 기록하는 방법이다.

  • 격리는 어떤 주체가 어떤 자원에 접근할 수 있는지를 나누는 속성이다. 성능·네트워크·저장·비밀정보의 경계를 각각 따진다.

학습 목표

  • 이미지·디스크 snapshot·전체 VM snapshot을 구별한다.

  • 공유 base와 개별 overlay의 읽기·쓰기를 추적한다.

  • 데이터 격리와 완전한 보안 보장을 분리한다.

같은 블록을 두 번 고치면 overlay 공간도 두 배로 세나요?

투명 메모지를 원본 그림 위에 놓고 고친 부분만 읽는다고 생각해 보자. 이 보강은 불변 base와 한 VM의 현재 overlay라는 두 층을 사용한다. 각 블록 1 MiB이며 overlay는 현재 변경된 블록마다 한 항목을 갖고, 같은 블록 재쓰기는 해당 항목을 바꾼다고 선언한다.

이 단순 공간 모형은 이전 버전·메타데이터·실제 파일 배정 단위를 제외한다. snapshot을 별도로 보존하면 과거 변경 블록도 남을 수 있으므로 현재 항목 수만 세는 모형을 그대로 적용하지 않는다. rollback은 VM 안의 보존된 상태로 돌아가는 동작이며 이미 보낸 외부 메시지를 취소하지 않는다.

먼저 확인할 개념
  • VM 이미지·격리

    base와 overlay의 읽기 우선순위, 디스크와 전체 VM snapshot의 다른 범위를 사용한다.

  • CPU·메모리·I/O 가상화

    CPU·RAM·장치 상태가 디스크 저장 내용과 다르다는 자원 구분을 연결한다.

이미지 하나가 실행 전체를 담는 것은 아니다

부팅 가능한 디스크 이미지는 OS 파일·설정·응용 데이터 등의 저장 내용을 담을 수 있다. 가상 CPU 개수, 메모리 용량, 가상 장치와 네트워크 연결은 별도 실행 설정이다. 디스크 파일을 복사했다는 것만으로 현재 실행 중 프로그램의 레지스터·RAM·외부 서비스 상태까지 복사했다고 말하지 않는다.

전체 VM snapshot은 지원되는 범위에서 CPU·RAM·장치·디스크 상태를 함께 저장한다. 디스크 snapshot만으로는 그 범위가 다르다. 실행 중 DB가 디스크에 남기지 않은 변경이나 여러 디스크 사이의 쓰기 순서가 있으면 일관성 조건이 필요하다. 실제 도구의 지원 장치·snapshot 종류·정지/동기화 절차를 확인해야 한다.

공유 base와 개별 overlay에서 읽는다

두 VM이 변경하지 않는 base를 읽고 각자 overlay에 쓰도록 구성하면, 읽기는 우선 자신의 overlay에서 해당 블록을 찾고 없으면 base로 내려간다. A가 블록2를 바꿔도 B의 overlay와 불변 base를 바꾸지 않았다면 B는 원래 블록2를 본다. 이 구조는 원본 자체를 모든 VM이 동시에 쓰는 공유 디스크와 다르다.

논리 디스크 크기와 실제 저장 공간도 다르다. 빈 영역을 실제로 배정하지 않는 sparse 형식과 변경 블록 공유는 공간을 줄일 수 있지만 metadata·정렬·압축·중복·예약 정책에 따라 실제 사용량은 달라진다. overlay만 옮기고 필요한 backing image를 빠뜨리면 완전한 디스크 내용을 재구성하지 못할 수 있다.

격리 범위는 여러 층에 걸친다

게스트 메모리의 권한 매핑과 각 VM의 저장 연결을 분리하면 다른 VM의 자료를 직접 읽는 경로를 제한한다. 그러나 잘못 연결한 공유 폴더, 공통 관리자 자격, 공개 네트워크 서비스, 이미지에 넣은 비밀키는 이 경계를 우회할 수 있다. 격리를 설정한 각 경로와 권한을 구체적으로 적는다.

VM은 VMM·호스트와 자원을 공유하므로 구현 취약점과 cache·대역폭 경쟁 등의 영향 가능성이 남는다. 파일 변경이 분리된다는 검증을 모든 부채널과 성능 간섭의 제거로 확대하지 않는다. rollback은 과거 상태 복원이며 외부에서 이미 처리한 요청·보낸 이메일·타 시스템 변경을 자동 취소하지 않는다.

하이퍼바이저와 성능

직접 실행을 하는 VM도 왜 느려질 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 하이퍼바이저는 여러 게스트의 실행과 자원 연결을 통제하는 VMM이다. 구현은 호스트 kernel·userspace·장치 backend 여러 부분에 나뉠 수 있다.

  • 경과시간은 CPU 작업시간과 대기·I/O·다른 원인까지 포함한다. 같은 작업과 환경을 비교해야 느려짐을 계산할 수 있다.

  • 비율은 분모를 명시한다. VM 시간/기준 시간과 추가시간/기준 시간은 서로 다른 수치다.

학습 목표

  • 하이퍼바이저 구조와 실제 실행 경로를 연결한다.

  • 작업별 가상화 비용 모형을 계산한다.

  • 공정한 성능 비교와 병목 원인 추론의 한계를 설명한다.

개입을 묶어서 줄였는데 전체 시간이 오히려 늘 수 있나요?

여러 작은 택배를 한 번에 모아 보내면 접수 횟수는 줄어도 기다리는 시간이 늘 수 있다. 가상화에서도 호출·개입을 묶는 방법은 횟수와 한 번의 비용, 다른 추가 항을 동시에 바꿀 수 있다. 이번에는 기본 합식의 겹침 없음·추가 항만 계산이라는 조건을 유지한다.

가상 비교는 동일한 완료 작업의 기준 시간 100 ms다. 추가 개입 비용은 횟수 N과 평균 비용 c의 곱이고 주소 변환·I/O·대기는 서로 중복되지 않는 별도 추가 시간이다. 실제 하이퍼바이저 분류나 가속기 이름만으로 값이 정해지지 않으며, 아래 숫자는 benchmark 실행 결과가 아니다.

먼저 확인할 개념
  • 하이퍼바이저와 성능

    겹침 없는 추가 비용식과 같은 작업의 시간비·처리량비를 사용한다.

  • CPU·메모리·I/O 가상화

    직접 실행과 장치 처리·주소 변환이 함께 존재하는 경로를 연결한다.

분류 이름보다 실행 경로를 확인한다

하드웨어 위에서 직접 관리하는 구성과 호스트 OS 위에 제공되는 구성은 흔히 type1/type2로 분류된다. 하지만 실제 시스템은 kernel 가속과 userspace 장치 모델을 조합할 수 있어 단일 이름만으로 비용을 예측하기 어렵다. QEMU라는 프로그램 이름만으로 TCG인지 KVM 등의 가속인지 판단하지 않고 실행 설정과 지원 조건을 확인한다.

게스트는 가상 CPU를 실행하고 특정 사건에서 제공자 처리가 필요하다. 장치 요청 전달, 메모리 변환, 호스트 스케줄링, 저장과 네트워크 backend가 함께 시간에 영향을 준다. 게스트가 아무 일도 안 하면서 바쁘게 spin하면 호스트가 유용한 VM에 자원을 주기 어려운 정보 간극이 생길 수 있다. idle 통지 같은 협력 인터페이스는 이 간극을 줄이는 방법이다.

횟수와 한 번의 비용을 곱하는 작은 모형

겹침이 없는 단순 모형에서 Tvm=Tbase+Ne×ce+Tm+Ti+Tw로 적는다. Ne는 추가 개입 횟수, ce는 그때 평균 비용, Tm은 별도 주소 변환 비용, Ti는 별도 I/O 추가 비용, Tw는 호스트 대기다. 각 항은 기준 실행과 비교해 늘어난 부분만 넣으며 같은 VM exit를 여러 항에 중복 계산하지 않는다.

실제로는 cache·메모리·I/O가 겹치거나 다른 실행과 경쟁하고 일부 비용이 줄 수도 있다. 따라서 이 합식은 가정한 종이 모형이지 모든 성능을 설명하는 측정 법칙이 아니다. 개입 횟수가 같아도 장치 종류·batch 크기·cache 상태에 따라 ce가 달라질 수 있으며 직접 실행한다고 나머지 항이 0이 되지 않는다.

작업량과 분모를 고정해서 비교한다

같은 데이터·결과·동시 사용자·가상 CPU/실제 코어·메모리·저장·cache 상태에서 경과시간과 처리량을 기록한다. 짧은 요청은 평균뿐 아니라 분위수와 꼬리 지연도 중요하다. 호스트의 다른 작업, 전력/주파수 변화, warm-up, VM 생성 시간을 포함했는지를 기록해야 반복 비교가 가능하다.

많은 CPU 연산만 하는 workload와 I/O·동기화가 빈번한 workload의 느려짐은 다를 수 있다. 가상화 기능을 끄거나 바꾸는 비교 실험에서 여러 조건을 동시에 변경하면 단일 원인을 확정하기 어렵다. 이 단원의 숫자는 설계 비용의 종이 계산이며 실제 클라우드 공급자 성능·가격·보안 순위를 측정한 것이 아니다.

평균의 분모는 네 번이다.

풀이와 답 확인

  1. 합은 12 μs이며 평균은 12/4=3 μs다.

  2. 다른 부하의 비용 목록은 주어지지 않았다.

현재 네 개입의 총 12 μs, 평균 3 μs다. 다른 workload 평균까지 보장하지 않는다.

흔한 오답에서 다시 생각하기

가장 큰 값 7 μs가 평균이다.

평균은 합/개수다. 최대값은 다른 지표다.

연습 2 · 오류 찾아 고치기

기준 100 ms에는 이미 I/O 20 ms가 포함되어 있다. VM에서 늘어난 I/O만 4 ms이고 개입 2 ms, 변환 3 ms, 대기 11 ms가 추가다. 100+20+4+2+3+11=140 ms라고 한 식을 고쳐라.

힌트 1

기준에 포함된 부분을 한 번 더 더하지 않는다.

힌트 2

추가 항만 기준에 더한다.

풀이와 답 확인

  1. 기준 100 ms에 포함된 20 ms는 다시 더하지 않는다.

  2. 100+4+2+3+11=120 ms다.

120 ms다. 기준의 구성 항과 기준 대비 추가 항을 구별한다.

흔한 오답에서 다시 생각하기

모든 I/O 항목을 다 더하면 더 정확하다.

연습 3 · 직접 만들어 보기

실측이 아닌 가상 반복 기록이다. 동일 완료 작업의 기준 시간 목록은 [90,100,110] ms, VM 목록은 [110,120,190] ms다. 각 목록의 평균과 중앙값을 계산하고 평균 시간비와 중앙값 시간비를 함께 보고하라. 단일 느린 기록의 원인은 주어지지 않았다.

힌트 1

평균은 세 기록의 합을 3으로 나누고, 중앙값은 정렬한 가운데 기록이다.

힌트 2

시간비의 분모는 각각 대응하는 기준 지표다.

풀이와 답 확인

  1. 기준 시간의 평균은 300/3=100 ms, VM 시간의 평균은 420/3=140 ms다. 평균 시간비는 140/100=1.4다.

  2. 기준 시간의 중앙값은 100 ms, VM 시간의 중앙값은 120 ms다. 중앙값 시간비는 120/100=1.2다.

  3. VM의 190 ms 기록이 평균에 영향을 준다. 호스트 대기나 I/O 등 그 원인은 이 목록만으로 식별되지 않는다.

기준 평균 100 ms와 VM 평균 140 ms의 시간비는 1.4다. 기준 중앙값 100 ms와 VM 중앙값 120 ms의 시간비는 1.2다. 두 비율의 분모를 함께 보고한다. 가상 기록이며 실제 benchmark나 특정 가상화 경로의 원인 판정이 아니다.

흔한 오답에서 다시 생각하기

중앙값이 120 ms이니 평균도 120 ms이고 나머지는 무시한다.

VM 평균은 190 ms도 포함한 140 ms다. 평균과 중앙값은 다른 질문에 답하며, 제외 규칙 없이 기록을 임의로 지우지 않는다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

기준 시간 B>0, 고정 추가 E≥0인 T=B+E에서 추가 항 E 전체를 0으로 만들 때 속도 향상 배수와 시간 감소율을 유도하라.

힌트 1

향상 배수는 이전 시간/새 시간이다.

힌트 2

감소율의 분모는 이전 B+E다.

풀이와 답 확인

  1. 새 시간은 B다. 향상 배수는 (B+E)/B=1+E/B다.

  2. 시간 감소율은 E/(B+E)다.

  3. B=100,E=20이면 배수1.2와 감소율1/6≈16.667%다.

추가율 E/B=20%와 전체 시간 감소율 E/(B+E)≈16.667%는 다르다.

흔한 오답에서 다시 생각하기

추가율 20%니까 제거하면 이전보다 20% 줄어든다.

20%의 분모는 기준 100이다. 이전 전체 120을 분모로 다시 계산한다.

종이로 비용을 계산했으면 VM 성능 검증 완료인가?

공유 이미지에서 만든 두 VM의 변경과 시간

VM A와 VM B는 불변 base=[A,B,C,D]와 각자의 현재 overlay를 사용한다. A의 overlay={1:X}, B의 overlay={1:Y}다. 각 블록의 크기는 1 MiB이며 메타데이터와 과거 버전은 제외한다. 두 VM 모두 가상 페이지 2를 게스트 프레임 7로 변환한다. 다음 단계에서 A는 호스트 프레임 11, B는 호스트 프레임 20으로 변환한다. 페이지 크기는 4096바이트, offset은 100바이트이며 두 VM의 읽기 권한은 유효하다. A가 블록 1에 Z를 재쓴다. 같은 작업의 기준 시간은 100 ms다. A의 추가 비용은 개입 200회에 회당 5 μs, 주소 변환 3 ms, I/O 4 ms, 대기 2 ms이며 서로 겹치지 않는다. 두 VM의 블록 1 읽기 값, 두 호스트 주소, 총 저장 공간, A의 전체 시간과 기준 대비 추가율을 계산하라. snapshot 저장 범위는 A VM 내부이며 외부 수신함은 제외한다. 외부 메시지 발송 후 A의 snapshot을 되돌리면 그 메시지도 취소되는지 설명하라.

힌트 1

현재 overlay는 VM마다 다르며 재쓰기는 A의 항목만 대체한다.

힌트 2

주소·저장 공간·경과시간은 각각 다른 상태와 단위다.

풀이와 답 확인

  1. A의 블록 1은 Z, B의 블록 1은 Y다. base의 블록 1은 원래 문자 B로 유지된다.

  2. A의 호스트 주소는 11×4096+100=45156바이트, B의 호스트 주소는 20×4096+100=82020바이트다. 같은 게스트 프레임 번호가 같은 호스트 메모리를 뜻하지 않는다.

  3. 현재 저장 모형은 원본 4 MiB, A의 변경 항목 1 MiB, B의 변경 항목 1 MiB의 합인 6 MiB다. A의 재쓰기는 기존 항목을 대체한다.

  4. 개입 비용은 200×5 μs=1 ms다. 전체 시간은 100+1+3+4+2=110 ms, 기준 대비 추가율은 (110−100)/100=10%다.

  5. 외부 메시지는 저장 범위 밖이므로 VM rollback만으로 외부에서 완료된 발송을 취소하지 않는다.

A의 블록 1 읽기 값은 Z, B의 값은 Y다. 호스트 주소는 A가 45156바이트, B가 82020바이트다. 현재 저장 모형의 공간은 6 MiB이며, A의 전체 시간은 110 ms로 기준보다 10% 늘었다. 외부 메시지 취소는 별도 절차가 없으므로 보장되지 않는다. 모든 값은 가상 상태·비용 모형이며 실제 VM 실행 결과가 아니다.
