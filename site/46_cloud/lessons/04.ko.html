소단원 4.1

namespace·cgroup

서로 다른 방 번호를 쓰는 것과 전기 사용량을 제한하는 것은 같은 일일까?

준비 개념과 학습 목표

준비 개념

  • 프로세스와 운영체제 커널

  • CPU 시간과 경과시간

  • 이름 공간은 보이는 이름의 범위다

학습 목표

  • namespace의 보기 분리와 cgroup의 자원 제어를 구별한다

  • CPU quota를 시간 단위로 해석한다

이름은 분리했는데 같은 CPU 예산을 함께 쓰면 어떻게 되나요?

교실마다 같은 책상 번호를 쓴다는 것과 학교의 하루 전기 예산을 나누는 것은 다른 약속이다. namespace는 특정 자원의 보기를 분리하고 cgroup은 자원 제어를 담당한다. 이번에는 두 이름 공간에서 같은 번호를 쓰는 상황과 부모·자식 그룹의 CPU 상한을 함께 추적한다.

CPU 계산은 fair-class 작업의 이상적 bandwidth 모형이다. 모든 기간은 시작이 정렬된 100000 μs=100 ms, burst와 전환 비용은 0이고 다른 제한은 없다. 부모의 총 CPU 시간 상한과 각 자식 상한은 모두 적용한다. 이 가상 조건으로 허용 가능한 분배만 논하며 실제 배분이나 전용 코어·처리량을 보장하지 않는다.

먼저 확인할 개념
  • namespace·cgroup

    보기 분리와 자원 제어, CPU 시간과 벽시계 시간을 구별한다.

  • CPU·메모리·I/O 가상화

    가상 이름 개수가 물리 실행 자원을 늘리지 않는다는 시간 예산 원칙을 연결한다.

같은 이름을 다른 보기에서

Linux namespace는 특정 자원의 보기와 이름 범위를 나누는 장치다. PID·network·mount·user·UTS 등 각각 다루는 자원이 다르다. 두 네트워크 namespace에서 같은 포트 번호를 따로 쓸 수 있어도 호스트와 통신할 연결 규칙은 별도로 정해야 한다.

같은 Linux 컨테이너들의 프로세스는 대체로 같은 호스트 커널을 이용한다. 이름의 분리는 새로운 커널이나 물리 CPU를 만드는 기능이 아니다. mount 보기 분리도 실제 파일을 무조건 복제하지 않으므로 공유된 파일·권한·mount 설정을 함께 살핀다.

사용할 양을 제어하기

cgroup은 프로세스를 계층으로 묶고 CPU·메모리 등 자원 제어를 적용한다. namespace가 무엇을 볼지에 가깝다면 cgroup은 어떤 자원을 얼마나 쓸지에 가깝다. cgroup namespace는 cgroup 경로의 보기를 분리하는 종류로, 제한 자체와도 구별한다.

cgroup v2의 cpu.max는 MAX PERIOD 두 시간값을 μs로 표시한다. fair-class 스케줄러의 기본 bandwidth 모형에서 한 기간에 쓸 수 있는 총 CPU 시간 상한을 뜻한다. quota는 성능 보장이나 전용 코어 지정이 아니며 상위 cgroup 제한도 영향을 준다.

비율과 벽시계를 분리하기

MAX=50000, PERIOD=100000이면 기간 100 ms당 CPU 시간 50 ms라는 상한이다. 단일 실행 thread가 다른 방해 없이 계속 실행하면 일부 시간에 실행 후 throttle될 수 있다. 여러 코어에서 동시에 실행하는 thread들은 quota를 함께 소비한다.

cpu.weight는 경쟁할 때의 상대 배분에 관련된 값이고 cpu.max는 상한이다. 가중치 두 배가 항상 실제 처리량 두 배를 보장하지 않는다. 실행 가능 작업 수·다른 그룹·부모 한계·스케줄링 정책이 결과를 바꾸며 이 단원의 수는 실제 측정값이 아니다.

중간 과정을 따라가는 예제

자체 모형에서 그룹 quota는 60000 μs/100000 μs다. 두 thread가 두 코어에서 동시에 계속 실행하고 다른 방해·관리 비용·burst는 0이다. quota 비율과 소진까지 벽시계 시간을 계산하라.

  1. 한 기간은 100 ms, 총 CPU 허용량은 60 ms다.

  2. 비율 60000/100000=0.6은 코어 하나의 시간 비율 기준이다.

  3. 두 thread가 각 30 ms 실행하면 CPU 시간 합은 60 ms다. 두 코어에서 겹쳐 실행하므로 벽시계는 30 ms다.

  4. 이 이상 모형에서는 그 뒤 기간의 quota를 더 쓸 수 없다. 실제 스케줄러의 정확한 실행·재충전 시각과 처리량은 이 계산만으로 증명하지 않는다.

quota 비율 0.6, 두 코어 동시 실행 모형의 소진 벽시계 30 ms다. CPU 시간 60 ms와 경과시간 30 ms를 구별한다.

조건을 바꾸어 비교하기

부모 상한과 형제 경쟁

한 기간에 A와 B가 사용하는 CPU 시간이 각각 (50 ms, 50 ms), (50 ms, 20 ms), (35 ms, 35 ms)인 세 분배를 비교하라. 각 자식 상한은 50 ms이고 부모 상한은 70 ms다.

  1. 첫 분배는 각 자식 상한을 만족하지만 합계 100 ms가 부모 상한 70 ms를 넘는다.

  2. 두 번째는 합계 70 ms이고 각 자식의 사용량도 50 ms 이하이므로 상한을 만족한다.

  3. 세 번째도 합계 70 ms이고 각 사용량이 50 ms 이하이므로 상한을 만족한다.

첫 분배만 부모 상한 위반이다. 뒤의 두 분배가 가능 조건을 만족해도 실제 scheduler가 그중 하나를 선택한다는 증거는 아니다.

동시 실행과 quota 소진

한 그룹의 cpu.max 값은 "80000 100000"이다. 앞의 수는 허용 CPU 시간, 뒤의 수는 기간이며 단위는 μs다. 네 스레드가 서로 다른 네 코어에서 동시에 계속 실행하고 다른 비용은 없다고 가정한다. 예산 소진까지 총 CPU 시간과 벽시계 경과시간을 구하라.

  1. cpu.max의 기간은 100 ms이며 그 기간에 그룹 전체가 사용할 수 있는 CPU 시간의 합은 최대 80 ms입니다.

  2. 서로 다른 네 코어에서 스레드 네 개가 동시에 각각 20 ms를 사용하면 총 CPU 시간은 4×20=80 ms입니다.

  3. 이 이상 모형에서는 벽시계 20 ms 뒤 예산을 소진합니다. 남은 80 ms의 벽시계 시간 동안에는 해당 기간의 추가 quota가 없습니다.

총 CPU 시간 80 ms를 벽시계 경과시간 20 ms에 사용합니다. 실제 throttle 시각이나 burst·회계 구현을 측정한 값은 아닙니다.

연습 1 · 값과 상태 예측

부모의 CPU 상한은 60 ms이고, 자식 A와 B의 상한은 각각 50 ms입니다. A가 20 ms를 사용했다면 남은 기간에 B가 사용할 수 있는 CPU 시간의 상한은 얼마인가요? 각 기간은 시작이 정렬되어 있고 다른 사용량은 없다고 가정합니다.

힌트 1

부모의 남은 예산은 60 ms에서 A의 사용량 20 ms를 뺀 값입니다.

힌트 2

B 자신의 CPU 상한 50 ms도 함께 적용합니다.

풀이와 답 확인

  1. 부모의 남은 CPU 예산은 60−20=40 ms입니다.

  2. B의 상한 50 ms와 부모 잔여량 40 ms 중 작은 값은 40 ms입니다.

B가 남은 기간에 사용할 수 있는 CPU 시간의 상한은 40 ms입니다. 이 값은 반드시 배정된 최소 사용량을 뜻하지 않습니다.

흔한 오답에서 다시 생각하기

B의 자체 상한이 50 ms이므로 부모의 잔여량과 관계없이 50 ms를 사용할 수 있다.

부모 예산도 같은 시간 합을 제한한다.

두 network namespace가 각자의 포트8080을 쓴다. 이것만으로 CPU 사용을0.5코어로 제한했다고 설명했다. 기능을 구별해 고쳐라.

힌트 1

포트 번호의 보기와 CPU 시간은 다른 자원이다.

힌트 2

CPU 상한에는 별도의 controller 설정과 계층 조건이 필요하다.

풀이와 답 확인

  1. network namespace는 네트워크 장치·stack·포트 등의 보기를 구분한다.

  2. 포트8080이라는 이름만으로 CPU quota는 정해지지 않는다.

  3. 호스트 접근 연결 규칙도 이 보기 분리만으로 제공되지 않는다.

포트 보기 분리와 CPU 제한을 별도로 설명한다. 실제 컨테이너나 포트 연결을 실행한 것이 아니다.

이름 공간의 경계가 자원 예산을 대신하지 않는다.

연습 3 · 직접 만들어 보기

부모의 CPU 상한이 70 ms이고 두 자식의 상한이 각각 50 ms인 한 기간을 생각하자. A에는 최소 30 ms, B에는 최소 25 ms의 사용량이 필요하다. 필요량 합과 부모의 잔여량을 구한 뒤 상한을 만족하는 분배 한 가지를 작성하라. 이 연습은 스케줄러의 최소 보장 설정을 뜻하지 않는다.

힌트 1

A와 B의 최소 필요량 합은 55 ms입니다.

힌트 2

각 자식의 사용량은 50 ms 이하이고 두 사용량 합은 70 ms 이하인 분배를 고릅니다.

풀이와 답 확인

  1. 필요량 합은 30+25=55 ms이고 부모 상한 대비 잔여량은 15 ms다.

  2. A가 40 ms, B가 30 ms를 사용하면 각각의 필요량 이상이고 각 상한 50 ms 이하이며 합계도 70 ms다.

A에 40 ms, B에 30 ms를 두는 분배가 조건을 만족한다. quota 설정만으로 최소 필요량인 30 ms와 25 ms가 자동 확보되는 것은 아니다.

흔한 오답에서 다시 생각하기

최소 요구가 작으므로 A에 50 ms, B에 50 ms를 배정해도 된다.

두 자식이 각각 상한을 만족해도 합계 100 ms가 부모 상한 70 ms를 초과합니다. 부모의 조건도 함께 확인하세요.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

한 그룹의 cpu.max 값은 "150000 100000"으로, 기간 100 ms당 총 CPU 시간 상한은 150 ms다. 실행 가능한 스레드는 하나이고 단일 코어에서 실행된다. 한 기간의 최대 CPU 시간은 얼마인가? 네트워크·I/O·전환 비용은 없다.

힌트 1

그룹의 quota는 총 CPU 시간 150 ms이지만 한 기간의 벽시계 길이는 100 ms입니다.

힌트 2

한 thread는 두 코어에서 같은 순간 동시에 실행하지 않는다.

풀이와 답 확인

  1. 단일 스레드가 한 코어에서 기간 내내 실행해도 CPU 시간은 100 ms입니다.

  2. 그룹 상한 150 ms를 설정한다고 단일 스레드의 병렬 실행이 생기지는 않습니다.

한 기간에 가능한 CPU 시간은 최대 100 ms입니다. 이 단일 스레드 모형에서는 설정된 상한 150 ms를 모두 소비할 수 없습니다.

흔한 오답에서 다시 생각하기

quota가 코어 1.5개에 해당하면 단일 스레드도 CPU 시간 150 ms를 벽시계 100 ms 안에 쓸 수 있다.

허용 총 CPU 시간과 단일 thread의 물리 실행 가능한 시간이 다르다.

아니다. 상한 충족은 가능 조건이며 scheduler·실행 가능 작업·경쟁 등의 실제 기록은 없다.

최종 파일 목록이 같아도 저장된 계층과 빌드 입력이 같을까요?

사진 위에 덧붙인 스티커가 이전 그림을 가려도 종이 아래에는 이전 그림이 남는다. 이미지 계층도 최종 파일 보기와 저장된 변경 조각을 나눠 본다. 이번에는 같은 경로의 변경 순서, 이미 가진 계층에 따른 새 전송량, 고정한 기반 밖의 입력을 추적한다.

최종 보기와 저장된 조각

이미지는 기반 파일과 여러 파일 변경 계층을 묶은 실행 재료다. 아래 경로에 위 계층이 새 내용을 놓으면 최종 보기에서는 위 내용이 보인다. 실행 컨테이너의 쓰기 공간은 이미지 층 자체를 바꾸는 것과 구별한다.

계층을 재사용하면 공통 파일을 반복 저장하거나 전송할 필요를 줄일 수 있다. 그러나 최종 보기에서 경로가 삭제되었다고 아래 계층의 바이트가 모두 없어지는 것은 아니다. 아래에 비밀을 넣었다가 위에서 지우는 것을 안전한 비밀 제거 방법으로 삼지 않는다.

이름표가 가리키는 내용

Tag는 읽기 쉬운 이름표이고 시간이 지나 다른 이미지 내용을 가리킬 수 있다. Digest는 특정 내용을 식별하는 hash 기반 참조다. 같은 tag 문자열로 다시 빌드하면 기반 내용이 바뀔 수 있으며 digest를 기록하면 사용한 기반을 더 정확히 추적할 수 있다.

내용이 같은지 식별하는 것과 누가 만들었는지·어떤 과정으로 만들었는지·취약점이 있는지는 다른 질문이다. 신뢰할 출처와 빌드 입력, 의존 버전, 검토 기록을 함께 관리한다. 자체 예의 D1/D2는 설명용 기호이며 실제 유효 digest나 검증된 이미지를 뜻하지 않는다.

  1. 첫 이미지의 논리 합은 80+20+5=105 MB다.

  2. 둘째 이미지의 논리 합은 80+20+8=108 MB다.

  3. 두 논리 합을 단순 더하면 213 MB지만 공통 B/D를 두 번 센 것이다.

  4. 이 모형의 고유 저장은 80+20+5+8=113 MB다. 공유 절약량은 213−113=100 MB다.

수신자가 가진 조각에 따라 전송이 달라짐

이미지 X의 조각은 B(80 MB), D(20 MB), A(5 MB)이고, 이미지 Y의 조각은 B(80 MB), D(20 MB), E(8 MB)입니다. 수신자가 B만 가진 경우와 B·D·A를 가진 경우에 Y를 받기 위해 필요한 새 조각량을 비교하세요.

  1. B만 있으면 누락된 조각 D의 20 MB와 E의 8 MB를 더해 28 MB를 받습니다.

  2. B·D·A가 있으면 Y에 필요한 B와 D는 이미 있습니다. 누락된 E의 8 MB만 받습니다.

  3. A는 Y의 구성요소가 아니므로 수신자가 A를 가지고 있어도 E를 대신하지 못합니다.

새 조각량은 첫 수신자 상태에서 28 MB, 두 번째 상태에서 8 MB입니다. 압축 전송이나 registry의 실제 응답량을 측정한 결과는 아닙니다.

VM·컨테이너 비교

같은 앱을 감싸는 두 방식이 왜 다른 커널 경계를 가질까?

준비 개념과 학습 목표

준비 개념

학습 목표

학교마다 다른 커널이 꼭 필요하면 비용식의 최솟값만 고르면 될까요?

한 건물의 여러 방과 별도 건물은 공유하는 기반이 다르다. 전형적인 Linux 컨테이너들은 실행 host의 커널을 공유하고 VM은 guest 커널을 갖는다. VM 안에 여러 컨테이너를 두는 구성도 가능하다. 이번에는 커널 기능 요구를 먼저 확인한 다음 가상 메모리 비용을 비교한다.

앱당 100 MiB, VM당 guest 운영체제 부가량 200 MiB, 컨테이너당 부가량 10 MiB를 가정한다. 공통 호스트 비용은 제외하고 페이지 공유는 없다. 숫자만 낮은 후보라도 서로 다른 guest 커널을 요구하면 한 커널 공유 구성으로 충족하지 못한다. 실제 커널 버전이나 보안 강도를 비교한 자료는 아니다.

격리의 층을 먼저 그리기

전형적인 VM은 가상 하드웨어 위에서 guest 운영체제와 그 커널을 실행한다. 컨테이너는 프로세스와 사용자 파일 환경을 묶고 실행을 제공하는 Linux 커널을 공유한다. 실제 Docker Desktop처럼 Linux VM 안에서 Linux 컨테이너를 실행하는 조합도 있다.

VM 안의 컨테이너들이 공유하는 것은 그 VM의 Linux 커널일 수 있다. Windows 호스트에서 실행한다고 모든 Linux 컨테이너 프로세스가 Windows 커널 syscall을 바로 사용한다는 뜻은 아니다. 호스트·VM·guest·컨테이너 경계를 그림에 따로 표시한다.

이미지에 모든 하드웨어가 들어가지는 않는다

컨테이너 이미지에 사용자 라이브러리를 넣어도 실행 CPU ISA·커널 기능·GPU driver·외부 장치와의 조건을 없애지는 못한다. 같은 image라는 이유로 서로 다른 환경의 모든 동작·속도를 동일하게 보장할 수 없다.

VM은 guest kernel을 고를 수 있는 장점이 있지만 hypervisor·가상 장치·호스트 조건이 남는다. VM이면 어떤 장치도 자동 동작하거나 모든 공격이 불가능하다는 주장 역시 틀리다. 두 방식의 경계·권한·업데이트 범위를 구체적으로 비교한다.

숫자는 공통 조건에서 비교하기

프로세스별 app 메모리와 guest 커널 비용을 따로 세면 공유의 효과를 간단한 표로 볼 수 있다. 그러나 page 공유·cache·메모리 압력·runtime 부가 비용을 바꾸면 결과도 달라진다. 시작시간이나 처리량은 실제 측정 없이 특정 배수를 단정하지 않는다.

공유 커널은 여러 환경의 실행 기반이며 공통 장애나 취약점 영향 범위를 생각하게 한다. 별도 guest 경계는 구조가 다르지만 강도는 구체 설정과 구현에 달렸다. 여기 비교는 배포 권고나 실측이 아닌 명시한 구조·비용 모형이다.

자체 메모리 모형에서 앱은 각각 100 MiB, guest kernel/운영체제 부가는 VM당 200 MiB, 컨테이너 부가는 개당 10 MiB다. 호스트 공통 비용·page 공유는 제외한다. 앱3개를 각각 VM, 같은 Linux host의 컨테이너3개, 하나의 Linux VM 안 컨테이너3개로 비교하라.

  1. 각각 VM이면 3×(200+100)=900 MiB다.

  2. 같은 Linux host의 컨테이너면 3×(100+10)=330 MiB다. host 공통 kernel 비용은 제외했다.

  3. 한 Linux VM 안에서 컨테이너3개면 200+3×110=530 MiB다. VM 부가는 한 번 들어간다.

  4. 이 모형에서 컨테이너 호스트330과 VM별900의 차는570 MiB다. 실제 구현 수치는 가상 부가값과 같다고 주장하지 않는다.

자체 가정 아래 900/330/530 MiB다. 어느 커널 비용을 포함했는지 달라져 숫자를 직접 비교할 때 분모와 공통 제외를 확인한다.

필수 요구가 비용 최저 후보를 제외

두 앱이 서로 다른 guest 커널을 동시에 요구한다. 표의 세 후보를 필수 조건과 비용 순서로 비교하라.

  1. 한 VM 안 두 컨테이너는 커널 하나를 공유하므로 필수 요구에 실패한다.

  2. 별도 VM 두 개는 600 MiB이고, VM마다 컨테이너 하나를 두면 620 MiB다. 두 구성 모두 별도의 guest 커널 경계를 만들 수 있다.

  3. 이 비용 모형에서 요구를 만족하는 두 후보 중에는 600 MiB인 별도 VM 구성이 620 MiB인 구성보다 작습니다.

가상 비용 최소 적합 후보는 각각 별도 VM이다. 420 MiB 후보는 싸도 요구를 충족하지 않는다.

동일 앱 수에서 기능 제약을 비용 최적화보다 먼저 적용한다.

같은 커널인 여러 앱의 손익분기

모든 앱이 같은 Linux 커널을 사용할 수 있습니다. 앱 수를 양의 정수 n이라고 두면 앱마다 별도 VM을 사용하는 비용은 300n MiB이고, 한 VM 안의 컨테이너 구성 비용은 (200+110n) MiB입니다. 두 번째가 엄격히 작은 최소 n을 구하세요.

  1. 혼합 구성의 비용 (200+110n) MiB가 개별 VM 비용 300n MiB보다 작으려면 200 MiB<190n MiB여야 합니다.

  2. n>200/190=20/19≈1.0526이다.

  3. 양의 정수에서 최소 n은 2다. 앱 하나이면 혼합 구성은 310 MiB, 개별 VM은 300 MiB다. 앱 두 개이면 각각 420 MiB와 600 MiB로 순서가 바뀐다.

이 가상 비용 모형에서 혼합 구성이 엄격히 작은 최소 앱 수는 2개입니다. 실제 비용·성능·기능의 보편적인 손익분기를 뜻하지 않습니다.

세 앱 중 A/B는 같은 Linux 커널을 사용해도 되고 C는 다른 guest 커널이 필요하다. A/B를 한 VM 안 두 컨테이너, C를 별도 VM으로 배치하는 구조와 비용을 작성하라.

힌트 2

풀이와 답 확인

  1. A와 B의 한 VM 안 컨테이너 구성은 200+2×110=420 MiB입니다.

  2. C의 별도 VM 구성은 200+100=300 MiB입니다.

  3. 두 구성의 총 비용은 420+300=720 MiB이며, 두 VM이 별도의 guest 커널 경계를 제공합니다.

총 비용은 720 MiB이고 guest 커널 경계는 두 개입니다. 각 앱의 실제 호환성·장치·보안 검토는 수행하지 않았습니다.

다른 문제에 적용하기

수업 실행 환경의 이름·예산·입력 기록

두 수업 A와 B의 컨테이너가 서로 다른 network namespace에서 각각 포트 8080을 쓴다. 두 컨테이너는 같은 Linux VM의 guest 커널을 공유한다. 두 cgroup 자식의 CPU 상한은 각각 50 ms이고 부모 상한은 70 ms다. 기간은 시작이 정렬된 100 ms이며 burst와 다른 사용은 없다. A가 45 ms를 사용했을 때 B의 남은 CPU 상한을 구하라. 이미지 기반 D1과 크기 20 MB인 공통층을 수신자가 이미 가지고 있고, 크기 8 MB인 새 앱층 E만 없다. 새 조각량은 얼마인가? 기반 D1은 같아도 외부 패키지가 P1에서 P2로 달라졌다면 전체 입력 동일성을 증명할 수 있는가? 수업 B가 다른 guest 커널을 요구할 때 현재 배치가 적합한지도 판정하라.

힌트 1

부모 잔여예산과 B의 상한을 함께 적용한다.

힌트 2

포트 보기·CPU 제어·이미지 식별·커널 기능 요구는 각각 다른 조건이다.

풀이와 답 확인

  1. 부모의 남은 CPU 예산은 70−45=25 ms입니다. B 자신의 상한 50 ms와 함께 적용하면 B의 남은 상한은 min(25,50)=25 ms입니다. 실제 최소 배분을 보장하는 값은 아닙니다.

  2. 수신자는 필요한 공유층을 가지고 있으므로 누락된 새 앱 조각 E의 8 MB만 받으면 됩니다.

  3. 외부 패키지 버전은 P1에서 P2로 바뀌었습니다. 기반 식별자 D1이 같다는 사실만으로 전체 입력의 동일성을 증명할 수 없습니다.

  4. 두 namespace는 같은 VM 커널을 공유한다. 다른 guest 커널이 필요한 B의 요구는 현재 배치로 충족되지 않는다.

B의 남은 CPU 상한은 25 ms이고 새 조각량은 8 MB다. 외부 패키지가 다르므로 전체 입력 동일성을 증명하지 못한다. 현재 배치는 B의 다른 guest 커널 요구를 충족하지 못한다. 각자 포트 8080을 사용한다는 사실만으로 CPU 사용량 확보나 별도 커널이 제공되지는 않는다.
