소단원 11.1

MapReduce·shuffle

여러 컴퓨터의 구매 기록에서 상품별 총수량을 어떻게 합칠까?

준비 개념과 학습 목표

준비 개념

  • 키·값 쌍

  • 리스트와 합

  • 자료 분할

학습 목표

  • map 출력과 key별 reduce 입력을 구별한다.

  • shuffle의 역할·자료 쏠림·올바른 부분 결합을 설명한다.

평균을 올바르게 합쳤다면 중앙값도 지역 대표값만 합쳐 구할 수 있을까요?

기본 원고는 상품 수량의 지역 합과 전체 합을 비교하고, 평균을 구할 때 합과 개수를 함께 보내야 한다고 설명합니다. 이번에는 같은 자료 P0=[2,4], P1=[10]의 요약에 제곱 합도 추가합니다. 요약을 (개수, 합, 제곱 합)으로 쓰고 세 성분을 각각 더하면 전체 평균과 모집단 분산을 계산할 수 있습니다. 여기서 모집단 분산은 관측한 세 값 모두를 모집단으로 보고, 평균으로부터의 제곱 편차 합을 전체 개수 3으로 나누는 통계입니다. 표본 분산의 분모 2와 구별합니다.

모든 통계가 같은 방식으로 요약되지는 않습니다. 지역 중앙값 하나씩만 전달하면 각 지역의 개수뿐 아니라 값의 배치도 잃습니다. 또 최신 기록을 고르려면 도착 순서 대신 사건 시각과 동률 규칙을 명시해야 합니다. 아래 값과 비용은 자체 종이 모형입니다. 실제 MapReduce 작업을 실행하거나 부동소수점 수치 안정성을 검증한 결과는 아닙니다.

먼저 확인할 개념
  • MapReduce·shuffle

    기본 원고의 합·개수 요약을 확장하고, 중간 값의 도착 순서를 보장하지 않는 조건을 유지합니다.

  • Spark식 반복 처리

    큰 자료를 driver로 모두 모으기 전에 분산 요약할 수 있는지 살펴봅니다. 정확한 통계 요약은 가져올 결과의 크기를 줄이는 후보가 됩니다.

한 줄에서 중간 쌍을 만든다

MapReduce의 map은 입력 기록에서 중간 키·값 쌍을 만들고 reduce는 같은 키의 값들을 결합하는 모델이다. 입력을 여러 부분으로 나누어 map을 수행할 수 있다. 입력 키와 중간 키가 같은 종류일 필요는 없다. 이 본문은 원래 논문의 모델을 배우는 것이며 특정 클라우드 서비스의 최신 기능이나 가격을 주장하지 않는다.

구매 기록의 중간 키를 상품명, 값을 수량으로 정하면 같은 상품의 수량을 더할 수 있다. reduce를 쓴다고 어떤 통계가 자동으로 올바르게 나오지는 않는다. 키를 상품으로 할지 지점으로 할지, 취소 수량을 음수로 포함할지 등 데이터 의미를 먼저 정의해야 한다.

같은 키를 만나는 shuffle

같은 상품의 기록은 다른 입력 분할에 있을 수 있다. key별 결합 전에 같은 키를 담당하는 곳으로 중간 쌍을 재배치하는 단계를 shuffle이라고 이해한다. 다른 작업자 사이의 데이터 이동·직렬화·저장 비용이 들어갈 수 있으므로 map 계산의 속도만으로 전체 시간을 판단하지 않는다.

같은 키의 값을 묶는 일은 원래 기록 순서를 항상 그대로 보존하는 일과 다르다. 수량 합에는 순서가 중요하지 않지만 첫 번째 도착을 최신 기록으로 오해하는 집계에는 영향을 준다. 시간순 최신 값을 원하면 시간·동률 규칙을 값에 포함하여 별도로 정의한다.

결합 가능한 요약과 쏠림

수량 합은 부분 합들을 다시 더해 같은 결과를 얻을 수 있다. 이런 지역 요약은 이동할 쌍 수를 줄이는 후보가 된다. 평균을 지역 평균 하나로 바꾸면 각 부분의 자료 수가 달라 잘못될 수 있으므로 합과 개수를 함께 전달한다. 지역 결합은 구현이 실행하는 횟수에도 결과가 의존하지 않도록 연산 조건을 확인한다.

기록 대부분이 한 상품에 몰리면 담당 reducer의 부하가 크다. 작업자를 늘려도 한 hot key가 자동으로 균등하게 나뉘는 것은 아니다. 키를 나누어 부분 집계한 뒤 다시 합치는 설계는 결과 의미와 추가 단계를 함께 검토한다. 재시도되는 map 안에서 외부 계좌를 갱신하는 식의 부작용도 집계 자체와 구별해야 한다.

각 열을 별도로 더합니다. 평균은 S/n이고 모집단 분산은 Q/n−(S/n)²입니다. 이 작은 정수 예에서 식을 손계산하며, 실제 큰 수의 부동소수점 계산에는 상쇄 오차 등의 별도 검토가 필요합니다.

중간 과정을 따라가는 예제

자체 입력 분할 P0는 (연필,2),(공책,1),(연필,3), P1은 (공책,4),(지우개,2),(연필,1)이다. map은 상품·수량을 그대로 중간 쌍으로 내보낸다. 상품별 총수량을 추적하라.

  1. P0의 map 출력은 세 쌍이고 P1도 세 쌍이다. 전체 6쌍의 수량 합은 2+1+3+4+2+1=13이다.

  2. shuffle 이후 연필은 [2,3,1], 공책은 [1,4], 지우개는 [2]를 만난다. 괄호 안 순서는 풀이용이며 전역 도착 순서 보장으로 사용하지 않는다.

  3. reduce 합은 연필 6, 공책 5, 지우개 2다. 결과 총합 6+5+2=13으로 입력 총수량과 일치한다.

  4. P0에서 미리 연필 5·공책 1, P1에서 공책 4·지우개 2·연필 1로 합치면 5쌍만 보내도 같은 결과다. 이는 자체 지역 합 모형이다.

연필 6·공책 5·지우개 2다. 지역 합은 여기서 쌍 수 6→5를 줄인다.

조건을 바꾸어 비교하기

지역 요약으로 평균과 분산 구하기

표의 세 성분을 결합하여 전체 평균과 모집단 분산을 구하고, 세 원본 값의 제곱 편차로 검산하세요.

  1. 성분별 합은 n=3, S=16, Q=120입니다. 평균은 16/3입니다.

  2. 모집단 분산은 120/3−(16/3)²=40−256/9=104/9입니다.

  3. 세 값의 평균에 대한 편차는 −10/3, −4/3, 14/3입니다. 제곱 합은 (100+16+196)/9=104/3입니다.

  4. 제곱 편차 합 104/3을 전체 개수 3으로 나누면 104/9로 일치합니다.

평균은 16/3이고 모집단 분산은 104/9입니다.

비교할 점

평균들의 단순 평균이나 지역 분산들의 단순 평균을 사용하지 않습니다. 이 공식으로 모든 실제 데이터의 수치 안정성이 확보된다는 주장도 아닙니다.

지역 중앙값의 중앙값이 틀리는 경우

P0=[1,2,3], P1=[100]입니다. 짝수 개 자료의 중앙값은 가운데 두 값의 평균으로 정의합니다. 두 지역 중앙값의 중앙값과 전체 중앙값을 비교하세요.

  1. P0의 중앙값은 2이고 P1의 중앙값은 100입니다.

  2. 지역 대표값 두 개의 중앙값은 (2+100)/2=51입니다.

  3. 전체 정렬 자료는 [1,2,3,100]이며 가운데 두 값은 2와 3입니다.

  4. 전체 중앙값은 (2+3)/2=2.5입니다. 지역 중앙값 둘만으로 원본의 위치 관계를 복원하지 못했습니다.

지역 대표값의 중앙값은 51이지만 전체 중앙값은 2.5입니다.

비교할 점

이 반례는 지역 중앙값 하나만 전달하는 방법이 일반적으로 정확하지 않다는 뜻입니다. 분산 중앙값을 어떤 추가 자료나 알고리즘으로도 구할 수 없다는 뜻은 아닙니다.

풀이 보기

오해와 반례

작업자를 두 배 늘리면 shuffle도 필요 없고 항상 처리 시간은 반이 된다.

같은 키의 값이 나뉘어 있으면 결합에 필요한 자료 재배치가 남는다. 한 hot key·직렬화·통신·시작 overhead 등이 지배하면 worker 수 증가만으로 시간 반을 보장할 수 없다.

연습 1 · 값과 상태 예측

P0=[2,4], P1=[10]에서 합과 개수만 보냈습니다. 전체 평균은 구할 수 있나요? 제곱 합 없이 위의 분산 공식까지 계산할 수 있다고 단정해도 될까요?

힌트 1

평균에는 전체 합과 개수가 필요합니다.

힌트 2

Q가 없으면 서로 다른 값들이 같은 S와 n을 만들 수 있습니다.

풀이와 답 확인

  1. (S,n)=(16,3)에서 평균은 16/3입니다.

  2. 예를 들어 P0=[2,4]와 P0=[3,3]은 지역 합 6과 개수 2가 같습니다. 두 경우 모두 P1=[10]을 유지하면 전체 합 16과 개수 3도 같지만, 전체 제곱 합은 각각 120과 118입니다.

  3. 따라서 합과 개수만으로 이 두 자료의 분산을 구별할 수 없습니다.

평균은 16/3입니다. 합과 개수만으로 일반적인 분산까지 결정할 수는 없습니다.

연습 2 · 오류 찾아 고치기

전체 요약 (n,S,Q)=(3,16,120)에서 분산을 120/3−16/3으로 계산했습니다. 빠진 연산을 찾고 모집단 분산을 바로잡으세요.

힌트 1

분산 공식의 두 번째 항은 평균의 제곱입니다.

힌트 2

120/3은 제곱 값들의 평균입니다.

풀이와 답 확인

  1. 잘못된 식은 제곱 값의 평균에서 값의 평균을 그대로 뺍니다.

  2. 올바른 두 번째 항은 (16/3)²=256/9입니다.

  3. 따라서 분산은 40−256/9=104/9입니다.

평균의 제곱을 빼야 하므로 정답은 104/9입니다.

캐시 선언은 같아도 실제로 남은 분할 수가 다르면 재사용 비용은 어떻게 바뀔까요?

기본 원고의 전체 캐시 비용 모형은 3회차에서 30 대 17단위였습니다. 이번에는 다른 비용과 저장 정책을 명시한 자체 모형을 만듭니다. 불변 전처리를 분할 네 개에 각각 2단위씩 수행하고, 매 회차 새 계산에 2단위를 씁니다. 캐시에 넣는 분할마다 최초 저장 비용은 1단위, 이후 읽기 비용은 0.25단위입니다. 첫 회차는 전처리한 값을 바로 사용하므로 별도 캐시 읽기 비용을 더하지 않습니다.

일부 캐시 모형은 첫 회차에 정한 두 분할만 저장하며, 이후 캐시에서 빠진 분할은 다시 저장하지 않습니다. 저장된 분할은 손실이 명시된 경우를 제외하면 유지됩니다. 모든 비용은 작업량을 직렬로 더하는 교육용 단위이며 실제 클러스터의 벽시계 시간이나 Spark의 자동 배치·퇴출 정책을 예측하지 않습니다. 공식 문서의 부분 캐시와 재계산을 이해하기 위해 조건을 고정한 비교입니다.

계획과 실행의 시점을 나눈다

Spark RDD는 분할된 자료 집합에 변환을 연결하고 action에서 필요한 계산을 수행하는 추상화다. map으로 새 RDD를 정의했다는 사실과 그 값이 지금 모두 계산됐다는 사실을 구별한다. 이런 lazy 실행을 이해하면 실행하지 않은 코드에 결과가 나왔다고 표시하는 실수를 피할 수 있다.

예를 들어 숫자 [1,2,3,4]를 제곱하는 변환 뒤 count와 sum을 실행하면 count는 개수 4, sum은 제곱 합 30을 요구한다. 새로운 데이터 집합의 모든 값을 driver로 모아 보여 주는 collect는 자료가 작을 때만 감당 가능하며 큰 자료를 cluster에서 처리해 놓고 마지막에 driver 메모리를 넘기지 않도록 결과 범위를 정한다.

재사용할 중간값과 계산 이력

반복 action에 쓰는 중간 RDD를 persist 또는 cache하면 이미 계산한 partition을 재사용할 수 있다. 지정하는 것만으로 모든 partition이 즉시 채워지는 것은 아니며 처음 계산하는 action이 필요하다. 선택한 저장 수준·공간·partition 손실에 따라 재계산이나 디스크 접근이 생길 수 있다.

변환 이력은 손실된 partition을 만드는 데 활용될 수 있지만 모든 외부 상태를 자동 복구하거나 cache를 영구 백업으로 바꾸지는 않는다. 입력 자료의 유지와 함수의 일관된 의미가 필요하다. 비용이 비싼 같은 전처리를 반복할 때 무엇을 재사용할지 결정하고 자료가 바뀌면 이전 값을 쓸 수 있는지도 확인한다.

절약과 비용을 같은 가정에서 센다

캐시는 저장·관리 공간과 최초 저장 비용을 요구한다. 여러 번 재사용하면 초기 비용을 회수할 수 있지만 한 번만 쓰면 이득이 없거나 작을 수 있다. 실측 없이 일정 배수의 속도 향상을 주장하지 않고 계산·저장·읽기 비용을 가정해 비교한다.

반복 알고리즘도 각 회차에서 모델·조건에 따른 새 계산은 남는다. 불변 전처리 결과를 cache하는 것과 회차 결과를 그대로 재사용하는 것을 구별한다. 회차마다 값이 달라지는 계산을 생략하면 속도 비교 이전에 결과가 틀릴 수 있다.

중간 과정을 따라가는 예제

자체 비용 모형: 불변 자료 전처리 P는 8단위, 회차별 계산은 2단위다. 3회차를 수행한다. 캐시는 첫 전처리 뒤 저장 비용 1, 이후 회차마다 읽기 비용 1이며 자료 손실·공간 부족·다른 overhead는 없다.

  1. cache 없이 매회 P를 다시 수행하는 모형 비용은 3×(8+2)=30이다. 실제 Spark optimizer가 모든 경우 이 계획을 따르는 것은 아니다.

  2. 캐시 모형의 첫 회차는 전처리 8 + 저장 1 + 회차 계산 2 = 11단위다. 첫 사용에서는 이미 계산한 값으로 회차 계산을 하므로 별도 읽기 비용 1단위를 추가하지 않는다고 정한다.

  3. 두 번째와 세 번째 회차는 각각 읽기 1 + 새 회차 계산 2 = 3단위다. 전체는 11 + 3 + 3 = 17단위다.

기본 원고는 사건 시각과 처리 시각, 체크포인트와 외부 출력의 중복 방지를 구별했습니다. 이제 두 입력의 watermark를 따로 구합니다. 자체 창 정책은 [12:00,12:05) 상태를 전역 경계 W가 창 끝 12:05보다 클 때 폐기합니다. 입력 A의 최대 사건 시각은 12:12, B는 12:06이며 각각 허용 지연을 4분으로 정합니다. 두 경계의 최솟값과 최댓값을 선택하는 차이를 손으로 추적합니다. 이 단순 창 폐기 규칙은 실제 Spark의 모든 연산·출력 모드 규칙을 대신하지 않습니다.

출력도 서로 다른 두 저장소로 나뉠 수 있습니다. 한 저장소에서 결과와 적용 ID를 원자적으로 기록했다고 다른 저장소까지 자동으로 같은 트랜잭션이 되는 것은 아닙니다. 재시도 식별자는 해당 논리 배치를 계속 식별해야 하고, 별개 처리 흐름에서 같은 숫자가 나오면 이름공간을 구별해야 합니다. 아래 Q1/Q2와 저장소 L/R은 자체 모형의 이름이며 실제 query나 외부 출력을 실행한 기록이 아닙니다.

자료가 끝나지 않는 흐름

stream은 사건이 계속 들어오는 자료 흐름이다. 사건이 발생한 event time과 처리기가 받은 processing time은 다를 수 있다. 통신 지연과 재시도로 오래된 사건이 나중에 도착할 수 있으므로 도착 순서를 사건 시각의 순서로 가정하지 않는다.

시간 창은 사건들을 일정 구간에 묶어 계산한다. 모든 과거 사건을 무한히 기다리면 상태가 계속 커지므로 얼마나 늦은 자료를 고려할지 정책이 필요하다. watermark는 이런 상태 관리와 늦은 자료 처리에 쓰이는 경계이며 모든 사건이 그 시각 전에 도착했다는 절대적 물리 증거는 아니다.

진행 위치와 상태를 복구한다

checkpoint는 처리 진행 위치와 누적 상태 등을 장애 뒤 복구하는 데 사용한다. 입력을 다시 읽을 수 있어야 의미 있는 재처리가 가능하다. 처리기의 RAM 값만 있고 진행 위치를 저장하지 않았다면 같은 사건을 다시 더하거나 사건을 건너뛰는 문제가 생길 수 있다.

복구용 상태를 남긴다고 외부 출력이 자동으로 정확히 한 번만 생기는 것은 아니다. 예를 들어 출력한 직후 checkpoint 갱신 전 실패하면 그 입력을 다시 처리할 수 있다. Spark 문서도 sink별 보장과 foreachBatch 구현에 따른 차이를 설명한다. 내부 재시도와 외부 결과 중복 제거를 별도 계약으로 본다.

출력 계약과 상태 수명을 정한다

자체 출력 모형에서 사건 또는 batch의 고유 ID로 이미 적용한 결과를 기록하고 같은 ID의 재시도를 건너뛸 수 있다. 단, 결과 갱신과 적용 ID 저장을 원자적으로 수행해야 그 사이 실패에도 중복을 막는다. ID 저장만 먼저 하면 결과 누락, 결과만 먼저 하면 재적용 위험이 남는다.

체크포인트를 다른 source나 다른 상태 구조의 query에 무조건 재사용하지 않는다. 실제 라이브러리의 호환 규칙과 기록 보존 기간을 확인해야 한다. 중복 제거용 ID를 삭제한 뒤 매우 늦은 재시도가 오면 다시 적용될 수 있어 상태 수명도 요구사항에 포함한다.

두 출력 중 하나만 성공한 배치

논리 배치 (Q1,3)의 출력은 L과 R에 각각 +5입니다. 두 저장소의 초기 값은 12이며 각 저장소는 결과와 적용 ID (Q1,3)를 자체 DB 트랜잭션으로 원자 기록합니다. L은 적용해 17이 되었고 R은 적용 전 실패했습니다. 처리 체크포인트는 아직 이 배치를 확정하지 않았습니다. 재시도를 추적하세요.

  2. L에는 적용 ID가 있으므로 +5를 다시 더하지 않고 17을 유지합니다.

  3. R에는 적용 ID가 없으므로 +5와 ID를 함께 기록해 17이 됩니다.

  4. 두 출력 완료를 확인한 뒤 처리 진행을 확정하도록 설계합니다. 첫 장애부터 재시도 완료 전까지는 L=17, R=12인 중간 상태가 존재했습니다.

재시도 완료 후 L=17, R=17입니다. 두 저장소가 언제나 동시에 같은 값을 보인다는 보장은 없습니다.

풀이와 답 확인

연습 3 · 직접 만들어 보기

두 출력 예제에서 L은 원자 기록으로 17이지만 R은 +5 결과만 저장해 17이 되었고 적용 ID 기록 전에 실패했습니다. 복구 후 L과 R에서 ID 존재 여부로 재시도하면 어떤 값이 되나요?

힌트 1

R의 결과와 ID는 원자적으로 저장되지 않았습니다.

힌트 2

R에는 이전 적용 ID가 없다는 조건을 유지합니다.

풀이와 답 확인

  1. L은 적용 ID가 있어 17을 유지합니다.

  2. R에는 적용 ID가 없으므로 +5를 다시 적용하여 22가 됩니다.

  3. R에서도 결과 갱신과 안정된 적용 ID 기록을 하나의 트랜잭션으로 묶어야 이 중간 실패를 없앨 수 있습니다.

저장소 L의 값은 17을 유지하고 저장소 R의 값은 22가 됩니다. R의 결과와 적용 ID를 함께 원자 기록하는 조건이 빠졌기 때문입니다.
