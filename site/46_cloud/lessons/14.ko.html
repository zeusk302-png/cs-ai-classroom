부하·확장·장애 복구

사용자가 늘면 서버를 추가하는 것만으로 기다림이 바로 사라질까?

준비 개념

  • 처리 용량

  • 관찰과 제어

학습 목표

  • 용량 복구와 데이터 복구를 구별한다.

앱 사본을 늘려도 공유 DB가 처리할 수 있는 수는 그대로라면 어떻게 될까요?

기본 원고의 연속 시간 유체 모형을 유지합니다. 도착은 초당 120건, 앱 사본마다 처리 가능량은 초당 50건입니다. 여기에 공유 DB의 전체 처리 상한 130건/s를 추가하고 요청 하나마다 DB 작업 하나가 필요하다고 정합니다. 전체 완료 가능량은 min(앱 사본 수×50,130)입니다. 초기 큐는 0이고 대기 중 포기·오류·재시도는 없습니다.

두 앱으로 시작해 t=0에 세 앱을 요청하고 t=10초에 새 앱이 준비됩니다. 요청된 수와 준비된 수를 구별합니다. 공유 DB 조건은 실제 제품의 상한이 아니라 자체 가정입니다. 다른 예에서는 용량 변경 시각이나 재시도 규칙을 명시해 모형을 바꾸며 실제 요청별 응답 지연을 계산한 것처럼 보고하지 않습니다.

부하는 도착과 완료를 함께 본다

부하는 일정 시간에 들어오는 요청과 그 요청이 요구하는 작업으로 설명한다. 도착률만 같아도 짧은 읽기와 큰 계산의 비용은 다르다. 완료율·실패·대기·응답 지연을 함께 관찰해야 서비스가 실제로 처리하는 상태를 이해할 수 있다. 요청을 모두 거부하여 큐가 없는 상황을 정상 처리라고 부르지 않는다.

이 단원의 종이 모형은 매초 같은 작업 수가 도착하고 각 준비된 복제본이 매초 고정 수를 처리하며 큐에 제한·재시도·포기가 없는 가정이다. 실제 서비스는 작업 분포와 DB·네트워크 병목이 달라 용량이 복제본 수에 정확히 비례하지 않을 수 있다. 모형의 요청 수는 실제 장비 측정값이 아니다.

확장 지시와 준비된 용량은 다르다

수평 확장은 실행 사본 수를 늘리고 수직 확장은 사본에 배정하는 자원을 늘리는 방향이다. Kubernetes HPA는 관측 지표를 바탕으로 목표 사본 수를 주기적으로 조정한다. 새 사본을 요청했다고 즉시 배치·시작·준비가 모두 완료되지는 않는다. 필요한 노드 자원과 지표 수집도 별도 조건이다.

기본 지표 비율 식의 목표는 ceil(현재 사본 수×현재 지표/목표 지표)로 이해할 수 있지만 실제 HPA에는 허용 오차·준비되지 않은 사본·누락 지표·안정화와 정책이 있다. 이 단원의 단순 식만으로 실제 모든 제어 결과를 예측하지 않는다. CPU 이용률의 기준 자원 요청을 설정하지 않은 경우도 조사해야 한다.

장애 뒤 밀린 작업까지 회복한다

사본 하나가 중단되면 남은 준비 용량과 도착량의 차이를 다시 계산한다. 대체 사본이 준비되어도 그동안 쌓인 큐가 남을 수 있다. 도착량과 같은 용량으로 복귀하면 더 쌓이지 않을 뿐 기존 큐를 줄이지 못한다. 초과 용량이 있어야 이 단순 모형의 밀린 작업을 소진한다.

재시작으로 실행 사본 수를 회복하는 것과 저장 자료를 복구하는 것은 다르다. 결제처럼 외부 효과가 있는 요청의 재시도에는 중복 처리와 멱등성 계약도 필요하다. 실제 장애 시험은 대상과 범위가 정해진 별도 환경에서 해야 하며 본문에서는 사건표만 추적한다.

중간 과정을 따라가는 예제

자체 모형에서 초당 120개가 도착하고 준비된 사본 2개가 각각 초당 50개를 처리한다. t=0에 사본 3개로 늘리라고 지시했지만 새 사본은 t=10에 준비된다. 초기 큐는 0이며 [0,10)에는 용량 100개/s, 이후에는 150개/s다. 큐와 소진 시간을 계산하자.

  1. 앞 10초는 매초 120−100=20개가 밀리므로 t=10의 큐는 200개다.

  2. t=10 뒤 준비 용량은 150개/s이고 새 도착은 120개/s라 매초 30개만큼 큐를 줄일 수 있다.

  3. 연속 시간의 유체 모형에서는 200/30=20/3초 뒤 큐가 0이 된다. 따라서 t=50/3≈16.67초다. 정수 초 말에만 관찰하면 t=17에 처음 0으로 보인다.

확장 준비 시점 t=10에는 큐 200개가 남는다. 준비 완료와 큐 소진은 다른 사건이며 이 계산은 실제 요청별 지연 측정이 아니다.

조건을 바꾸어 비교하기

준비 완료와 밀린 큐 소진

위 조건에서 큐가 비는 시각을 기본의 DB 상한 없는 모형과 비교하세요.

  1. t=10까지 용량은 100건/s이므로 큐는 (120−100)×10=200건입니다.

  2. 이후 전체 가능량은 min(150,130)=130건/s이며 큐 감소량은 10건/s입니다.

  3. 남은 200건은 200/10=20초 뒤 비므로 전체 시각은 t=30초입니다.

  4. 기본 모형은 감소량 30건/s이므로 t=50/3초입니다.

DB 상한 모형은 t=30초에 비며 사본 준비 시각 t=10초와 다릅니다.

비교할 점

앱 사본 증가를 전체 용량의 동일 증가로 가정하지 않습니다.

복구 중 두 번째 용량 감소

별도 모형은 DB 상한이 없고 도착은 120건/s입니다. 초기 큐 0, 용량은 [0,10) 100건/s, [10,15) 150건/s, [15,20) 100건/s, 이후 150건/s입니다. 큐를 구하세요.

  1. t=10의 큐는 200건입니다.

  2. 다음 5초는 초당 30건 감소해 t=15의 큐는 50건입니다.

  3. 다음 5초는 초당 20건 증가해 t=20의 큐는 150건입니다.

  4. 이후 150/30=5초 뒤 t=25에서 비게 됩니다.

시작 뒤 10초에는 큐에 200건이 남습니다. 시작 뒤 15초에는 50건이 남고, 시작 뒤 20초에는 150건이 남습니다. 이후 초당 30건씩 줄어 시작 뒤 25초에 큐가 비게 됩니다.

비교할 점

새 준비 뒤에도 용량이 다시 감소할 수 있으며 각 구간의 경계 값을 다음 구간의 초기값으로 넘깁니다.

연습 1 · 값과 상태 예측

공유 DB 상한 130건/s, 도착 140건/s입니다. 앱 2개로 시작하고 t=10에 3개가 준비됩니다. t=10과 t=20의 큐를 구하고 더 늘리면 비는지 판단하세요.

힌트 1

초기 전체 용량은 100건/s입니다.

힌트 2

3개 이상에서도 DB 상한 130건/s입니다.

풀이와 답 확인

  1. 첫 10초 큐는 (140−100)×10=400건입니다.

  2. 다음 10초는 초당 10건 증가해 t=20의 큐는 500건입니다.

  3. 앱 수만 늘려도 전체 상한이 도착보다 작아 큐가 계속 증가합니다.

400건, 500건이며 앱 증설만으로 소진되지 않습니다.

흔한 오답에서 다시 생각하기

앱 3개면 용량 150이므로 큐가 줄어든다.

모든 요청이 쓰는 공유 DB의 130건/s 상한을 누락했습니다.

연습 2 · 오류 찾아 고치기

원래 요청→계층 A→계층 B→계층 C→DB인 자체 경로에서 A/B/C는 각각 하위 호출을 최대 3번 시도합니다. 모든 하위 시도는 실패하고 각 상위 시도마다 아래 계층의 시도 한도를 새로 사용합니다. 원래 100요청이 DB에 최대 300번만 도달한다는 보고를 고치세요.

힌트 1

계층별 시도는 더하기가 아니라 곱하기가 됩니다.

힌트 2

각 계층의 최대 시도에는 최초 시도가 포함됩니다.

풀이와 답 확인

  1. 원래 요청 하나의 DB 시도는 최대 3×3×3=27번입니다.

  2. 100요청이면 최대 2700번입니다.

  3. 오직 DB 바로 위 계층만 최대 3번 시도하고 위 계층은 재시도하지 않는 별도 조건이면 최대 300번입니다.

주어진 세 계층 조건은 최대 2700번이며 한 계층 재시도 조건의 300번과 다릅니다.

흔한 오답에서 다시 생각하기

계층이 세 개니 3+3+3=9번이다.

상위의 각 시도가 하위의 전체 시도를 다시 유발합니다. 실제 성공·취소가 있으면 최대보다 적을 수 있습니다.

연습 3 · 직접 만들어 보기

별도의 정수 초 모형에서 매초 120건을 큐에 넣고 최대 100건을 처리한 뒤 초 말의 대기를 최대 100건으로 제한해 초과분을 거부합니다. 초기 0이며 재시도·포기는 없습니다. 첫 10초의 완료·거부·남은 건수를 검산하세요.

힌트 1

매초 순증가는 제한에 도달하기 전 20건입니다.

힌트 2

입력=완료+거부+남은 큐로 확인합니다.

풀이와 답 확인

  1. 1–5초 말 큐는 20,40,60,80,100건이고 거부는 0입니다.

  2. 6–10초는 각각 처리 후 120건 중 20건을 거부해 큐 100을 유지합니다.

  3. 도착 1200건, 완료 1000건, 거부 100건, 남은 100건입니다.

1200=1000+100+100입니다. 큐 제한이 모든 요청의 성공을 뜻하지 않습니다.

흔한 오답에서 다시 생각하기

큐가 100으로 안정됐으니 1200건을 모두 처리했다.

거부 100건과 미완료 100건을 성공 완료에 넣지 마세요. 이 예의 초 말 제한을 다른 큐 정책에 일반화하지 않습니다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

기본의 DB 상한 없는 모형에서 준비 지연을 10초에서 5초로 줄입니다. 이후 용량 150건/s, 도착 120건/s일 때 큐 소진 시각을 구하세요. 종이 결과로 개별 응답 p95를 알 수 있나요?

힌트 1

t=5의 큐는 100건입니다.

힌트 2

준비 개념

  • 성공 기준

학습 목표

  • 가상 단가와 실제 가격 견적을 구별한다.

두 시간의 단위 비용을 단순 평균하면 전체 단위 비용이 될까요?

기본의 가상 단위 U와 유효 완료 기준을 유지합니다. 유효 완료는 올바르고 정한 지연 제한도 만족한 요청입니다. 같은 조건의 여러 관찰 구간을 합칠 때 총비용을 더하고 유효 완료도 더한 뒤 나눕니다. 이미 계산한 구간별 단위 비용을 단순 평균하면 구간마다 건수가 다를 때 다른 통계가 됩니다.

늦은 응답과 잘못된 응답은 겹칠 수 있습니다. 제외 집합의 합집합을 계산해야 유효 완료 분모를 정확히 구합니다. 아래의 두 구성은 같은 관찰 기간과 작업 조건으로 비교한다고 가정한 자체 표이며 실측 성능·실제 클라우드 단가가 아닙니다.

단가 대신 같은 기간의 전체 비용을 쓴다

사본당 시간 가격과 서비스 전체 비용은 다르다. 사본 수와 유지 시간을 곱한 컴퓨팅 비용에 저장·네트워크 전송·요청·로드밸런서·로그 등 적용되는 항목을 더한다. 어떤 항목을 포함하거나 제외했는지 적어야 비교가 재현된다. 실제 가격은 지역·제품·계약·과금 단위·시점에 따라 확인한다.

이 단원은 학습용 비용 단위 U를 사용하며 어떤 회사의 실제 가격·견적도 아니다. 공공 가격표에 전송과 별도 자원 항목이 있다는 사실을 확인하되 오래된 숫자나 무료 한도를 모든 계정에 일반화하지 않는다. 세금·할인·운영 인건비의 포함 여부도 실제 비교에서는 명시한다.

유효 성능의 계약을 먼저 정한다

유효 완료는 올바른 답이며 정해 둔 응답 제한도 만족하는 요청이라고 이 표에서 정의한다. 성공 응답을 반환했지만 너무 늦은 요청과 오답은 이 분모에서 제외한다. 전체 시도·유효 완료·제외 이유를 함께 적는다. 이 정의는 자체 비교 계약이고 모든 서비스가 같은 지표를 사용하지는 않는다.

같은 한 시간 비용 C와 유효 완료 N이 있으면 C/N은 U/건이고 N/C는 건/U다. 더 작은 C/N과 더 큰 N/C가 같은 효율 방향을 나타낸다. N=0이면 나눗셈으로 유한한 단위 성공 비용을 보고하지 않는다. 처리율 건/s와 비용 U/건을 혼동하지 않는다.

효율 개선은 품질 조건과 함께 읽는다

비용을 줄였지만 응답 지연·정확성 기준을 바꾸었다면 같은 서비스 수준의 개선이라고 말하기 어렵다. 자료량·요청 조합·측정 기간·성공 기준을 고정하고 반복 실험의 변동을 기록한다. 적은 표본의 우연한 성공과 실제 지속 가능한 용량을 구별한다.

자원 수를 늘려 단위 비용이 내려가더라도 총비용과 예산은 커질 수 있다. 효율과 지출 한도는 다른 결정 기준이다. 가상 표에서는 산술 비교를 할 수 있지만 실측 없는 공급자 추천이나 실제 예상 청구액 확정으로 확장하지 않는다.

로컬 환경은 유용한 다른 범위의 실험이다

선택적으로 로컬 클러스터를 사용하면 API 객체·사본·준비 상태 등의 동작을 조사할 수 있다. Kubernetes의 kind는 로컬 컨테이너 기반 실행을 위해 Docker 또는 Podman이 필요하고 minikube도 개인 컴퓨터의 학습 환경을 제공한다. 설치 요구·메모리·권한·버전은 실제 장치에서 확인해야 한다.

한 컴퓨터의 여러 사본은 여러 독립 물리 서버나 지역과 같은 장애 격리가 아니다. 로컬 API 동작을 확인해도 클라우드 요금·지역 지연·관리형 서비스 계약·실제 가용 영역 장애는 확인하지 못한다. 필요한 지표 구성 없이 로컬 설치만으로 HPA 시험 완료라고 하지 않는다. 본문은 로컬 설치도 수행하지 않았다.

유료 실험에는 지출과 정리의 증거가 필요하다

선택 유료 실습 계획에는 계정 소유자 승인·대상 자원·상한 사본 수·시간·비용 항목·중단/정리 절차를 구체적으로 적는다. 무료 범위가 있어도 적용 조건을 확인해야 하며 남은 디스크·IP·로드밸런서·로그 등의 항목을 조사한다. 실행 사본 중지 하나가 모든 청구 항목 제거를 의미하지 않는다.
