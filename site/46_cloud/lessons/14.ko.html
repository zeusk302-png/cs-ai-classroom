소단원 14.1

부하·확장·장애 복구

사용자가 늘면 서버를 추가하는 것만으로 기다림이 바로 사라질까?

준비 개념과 학습 목표

준비 개념

  • 요청과 큐

  • 처리 용량

  • 관찰과 제어

학습 목표

  • 도착량·처리 용량·밀린 요청을 구별한다.

  • 확장 결정과 준비 완료 사이의 지연을 추적한다.

  • 용량 복구와 데이터 복구를 구별한다.

부하는 도착과 완료를 함께 본다

부하는 일정 시간에 들어오는 요청과 그 요청이 요구하는 작업으로 설명한다. 도착률만 같아도 짧은 읽기와 큰 계산의 비용은 다르다. 완료율·실패·대기·응답 지연을 함께 관찰해야 서비스가 실제로 처리하는 상태를 이해할 수 있다. 요청을 모두 거부하여 큐가 없는 상황을 정상 처리라고 부르지 않는다.

이 단원의 종이 모형은 매초 같은 작업 수가 도착하고 각 준비된 복제본이 매초 고정 수를 처리하며 큐에 제한·재시도·포기가 없는 가정이다. 실제 서비스는 작업 분포와 DB·네트워크 병목이 달라 용량이 복제본 수에 정확히 비례하지 않을 수 있다. 모형의 요청 수는 실제 장비 측정값이 아니다.

확장 지시와 준비된 용량은 다르다

수평 확장은 실행 사본 수를 늘리고 수직 확장은 사본에 배정하는 자원을 늘리는 방향이다. Kubernetes HPA는 관측 지표를 바탕으로 목표 사본 수를 주기적으로 조정한다. 새 사본을 요청했다고 즉시 배치·시작·준비가 모두 완료되지는 않는다. 필요한 노드 자원과 지표 수집도 별도 조건이다.

기본 지표 비율 식의 목표는 ceil(현재 사본 수×현재 지표/목표 지표)로 이해할 수 있지만 실제 HPA에는 허용 오차·준비되지 않은 사본·누락 지표·안정화와 정책이 있다. 이 단원의 단순 식만으로 실제 모든 제어 결과를 예측하지 않는다. CPU 이용률의 기준 자원 요청을 설정하지 않은 경우도 조사해야 한다.

장애 뒤 밀린 작업까지 회복한다

사본 하나가 중단되면 남은 준비 용량과 도착량의 차이를 다시 계산한다. 대체 사본이 준비되어도 그동안 쌓인 큐가 남을 수 있다. 도착량과 같은 용량으로 복귀하면 더 쌓이지 않을 뿐 기존 큐를 줄이지 못한다. 초과 용량이 있어야 이 단순 모형의 밀린 작업을 소진한다.

재시작으로 실행 사본 수를 회복하는 것과 저장 자료를 복구하는 것은 다르다. 결제처럼 외부 효과가 있는 요청의 재시도에는 중복 처리와 멱등성 계약도 필요하다. 실제 장애 시험은 대상과 범위가 정해진 별도 환경에서 해야 하며 본문에서는 사건표만 추적한다.

중간 과정을 따라가는 예제

자체 모형에서 초당 120개가 도착하고 준비된 사본 2개가 각각 초당 50개를 처리한다. t=0에 사본 3개로 늘리라고 지시했지만 새 사본은 t=10에 준비된다. 초기 큐는 0이며 [0,10)에는 용량 100개/s, 이후에는 150개/s다. 큐와 소진 시간을 계산하자.

  1. 앞 10초는 매초 120−100=20개가 밀리므로 t=10의 큐는 200개다.

  2. t=10 뒤 준비 용량은 150개/s이고 새 도착은 120개/s라 매초 30개만큼 큐를 줄일 수 있다.

  3. 연속 시간의 유체 모형에서는 200/30=20/3초 뒤 큐가 0이 된다. 따라서 t=50/3≈16.67초다. 정수 초 말에만 관찰하면 t=17에 처음 0으로 보인다.

확장 준비 시점 t=10에는 큐 200개가 남는다. 준비 완료와 큐 소진은 다른 사건이며 이 계산은 실제 요청별 지연 측정이 아니다.

종이와 본문으로 직접 해보기

별도 장애 모형에서 t=0에 사본 3개 중 하나가 사라져 10초 동안 용량 100개/s가 되고 도착은 120개/s다. 대체 후 용량을 120개/s로만 복구하면 큐 200개가 언제 사라질까? 기본 식에서 사본 2개·지표 80·목표 50의 목표 수는?

힌트 보기

큐를 줄이는 속도는 용량−도착량이다. 기본 식은 올림한다.

풀이 보기

복구 용량 120과 도착 120의 차이는 0이라 이 가정에서는 큐 200개가 줄지 않는다. 기본 식은 ceil(2×80/50)=ceil(3.2)=4개다. 실제 HPA 결정은 다른 정책·지표 조건까지 필요하다.

오해와 반례

목표 사본 수를 늘린 순간부터 모든 용량과 자료가 복구된다.

배치·시작·준비 지연과 밀린 요청, 저장 자료·외부 효과의 복구를 각각 확인해야 한다.

자기점검

용량과 도착이 모두 120개/s면 기존 큐는 줄어드는가?

답과 이유 보기

이 모형에서는 줄지 않는다.

소진 여유 용량이 0이다.

ceil(3.2)를 사본 3개로 해석하는가?

답과 이유 보기

아니다. 4개다.

올림은 작은 정수 내림과 다르다.

사본 재시작 성공이 결제 중복 없음의 증거인가?

답과 이유 보기

아니다.

소단원 14.2

성능당 비용 비교

시간당 가격이 낮은 서버가 성공한 요청 한 건에도 더 저렴할까?

준비 개념과 학습 목표

준비 개념

  • 같은 관찰 구간

  • 성공 기준

  • 비용 합계와 단위

학습 목표

  • 총비용과 유효 완료 수로 단위 비용을 계산한다.

  • 지연·실패 기준을 만족하는 성능만 비교한다.

  • 가상 단가와 실제 가격 견적을 구별한다.

단가 대신 같은 기간의 전체 비용을 쓴다

사본당 시간 가격과 서비스 전체 비용은 다르다. 사본 수와 유지 시간을 곱한 컴퓨팅 비용에 저장·네트워크 전송·요청·로드밸런서·로그 등 적용되는 항목을 더한다. 어떤 항목을 포함하거나 제외했는지 적어야 비교가 재현된다. 실제 가격은 지역·제품·계약·과금 단위·시점에 따라 확인한다.

이 단원은 학습용 비용 단위 U를 사용하며 어떤 회사의 실제 가격·견적도 아니다. 공공 가격표에 전송과 별도 자원 항목이 있다는 사실을 확인하되 오래된 숫자나 무료 한도를 모든 계정에 일반화하지 않는다. 세금·할인·운영 인건비의 포함 여부도 실제 비교에서는 명시한다.

유효 성능의 계약을 먼저 정한다

유효 완료는 올바른 답이며 정해 둔 응답 제한도 만족하는 요청이라고 이 표에서 정의한다. 성공 응답을 반환했지만 너무 늦은 요청과 오답은 이 분모에서 제외한다. 전체 시도·유효 완료·제외 이유를 함께 적는다. 이 정의는 자체 비교 계약이고 모든 서비스가 같은 지표를 사용하지는 않는다.

같은 한 시간 비용 C와 유효 완료 N이 있으면 C/N은 U/건이고 N/C는 건/U다. 더 작은 C/N과 더 큰 N/C가 같은 효율 방향을 나타낸다. N=0이면 나눗셈으로 유한한 단위 성공 비용을 보고하지 않는다. 처리율 건/s와 비용 U/건을 혼동하지 않는다.

효율 개선은 품질 조건과 함께 읽는다

비용을 줄였지만 응답 지연·정확성 기준을 바꾸었다면 같은 서비스 수준의 개선이라고 말하기 어렵다. 자료량·요청 조합·측정 기간·성공 기준을 고정하고 반복 실험의 변동을 기록한다. 적은 표본의 우연한 성공과 실제 지속 가능한 용량을 구별한다.

자원 수를 늘려 단위 비용이 내려가더라도 총비용과 예산은 커질 수 있다. 효율과 지출 한도는 다른 결정 기준이다. 가상 표에서는 산술 비교를 할 수 있지만 실측 없는 공급자 추천이나 실제 예상 청구액 확정으로 확장하지 않는다.

중간 과정을 따라가는 예제

같은 한 시간의 가상 구성 A는 컴퓨팅 6 U·기타 3 U·유효 완료 9,000건이고 B는 컴퓨팅 8 U·기타 4 U·유효 완료 15,000건이다. 동일한 정확성/지연 기준을 썼다고 가정한다. 총비용과 유효 완료 1,000건당 비용을 비교하자.

  1. A 총비용은 6+3=9 U이고 B는 8+4=12 U다. B의 전체 지출이 3 U 더 크다.

  2. A는 9/9,000×1,000=1 U/1,000건, B는 12/15,000×1,000=0.8 U/1,000건이다.

  3. 단위 비용 감소율은 (1−0.8)/1=20%다. 역수 효율은 A 1,000건/U에서 B 1,250건/U로 25% 증가한다. 감소율과 역수 증가율은 다르다.

B는 가상 단위 유효 완료 비용이 20% 낮지만 총비용은 12 U로 더 크다. 실제 요금이나 성능 측정 결과는 아니다.

종이와 본문으로 직접 해보기

B의 전체 완료는 여전히 15,000건이지만 늦거나 틀린 답 5,000건을 제외해야 한다면 유효 완료 1,000건당 비용은? A보다 효율적인가?

힌트 보기

분모를 15,000−5,000으로 바꾼다.

풀이 보기

유효 완료는 10,000건이고 12/10,000×1,000=1.2 U다. A의 1 U보다 높으므로 같은 유효 기준에서는 A보다 비용 효율이 낮다.

오해와 반례

전체 완료 건수가 많으면 유효 완료당 비용도 반드시 작다.

전체 비용과 정확성/지연 기준을 만족하는 건수를 함께 계산한다. 제외 5,000건 반례에서는 B가 더 비싸다.

자기점검

B의 단위 비용 20% 감소가 총지출 20% 감소인가?

답과 이유 보기

아니다.

총비용은 9 U에서 12 U로 증가했다.

비용당 효율의 역수 증가율은?

답과 이유 보기

25%다.

(1,250−1,000)/1,000=0.25다.

유효 완료 0건일 때 C/0을 유한한 성공 비용으로 적는가?

답과 이유 보기

적지 않는다.

이 나눗셈은 정의되지 않고 성공 비용 추정 근거가 없다.

  • 예산 알림과 즉시 지출 차단을 구별한다.

  • 계획·실행·정리 확인을 각각 기록한다.

먼저 설치 없는 사건표로 시작한다

종이 모형은 사본 수·준비 시간·도착량·큐·비용을 직접 바꾸어 인과를 탐색할 수 있다. 첫 소단원의 큐 계산은 계정·결제·장비 없이 가능하다. 이 모형이 실제 스케줄러·네트워크·저장 장애를 관찰한 증거는 아니지만 가정과 예상의 관계를 이해하는 데 유용하다.

학습 보고는 예상과 관찰을 별도 열에 두고 실행하지 않은 활동의 관찰은 비워 둔다. 실제 출처 읽기와 산술 검산을 실제 클러스터 실행으로 바꾸어 적지 않는다. 초중고 학습자도 이 이론 경로만으로 참여할 수 있고 유료 실습은 필수 조건이 아니다.

로컬 환경은 유용한 다른 범위의 실험이다

선택적으로 로컬 클러스터를 사용하면 API 객체·사본·준비 상태 등의 동작을 조사할 수 있다. Kubernetes의 kind는 로컬 컨테이너 기반 실행을 위해 Docker 또는 Podman이 필요하고 minikube도 개인 컴퓨터의 학습 환경을 제공한다. 설치 요구·메모리·권한·버전은 실제 장치에서 확인해야 한다.

한 컴퓨터의 여러 사본은 여러 독립 물리 서버나 지역과 같은 장애 격리가 아니다. 로컬 API 동작을 확인해도 클라우드 요금·지역 지연·관리형 서비스 계약·실제 가용 영역 장애는 확인하지 못한다. 필요한 지표 구성 없이 로컬 설치만으로 HPA 시험 완료라고 하지 않는다. 본문은 로컬 설치도 수행하지 않았다.

유료 실험에는 지출과 정리의 증거가 필요하다

선택 유료 실습 계획에는 계정 소유자 승인·대상 자원·상한 사본 수·시간·비용 항목·중단/정리 절차를 구체적으로 적는다. 무료 범위가 있어도 적용 조건을 확인해야 하며 남은 디스크·IP·로드밸런서·로그 등의 항목을 조사한다. 실행 사본 중지 하나가 모든 청구 항목 제거를 의미하지 않는다.

AWS Budgets는 비용과 사용량을 추적하고 알림·행동을 구성할 수 있지만 비용 반영과 알림에 지연이 있다. 알림만 설정했다고 지정 금액에서 모든 사용이 즉시 끊긴다고 가정하지 않는다. 자원 정리는 실제 목록·삭제/종료 상태와 청구 범위를 확인한 증거로 보고하며 계획 문서 체크 표시만으로 완료하지 않는다.

중간 과정을 따라가는 예제

자체 계획표에 종이 P·로컬 L·유료 C 세 활동이 있다. 실제로 P의 계산만 수행했고 L/C는 실행하지 않았다. 한 별도 가상 청구표는 컴퓨팅 4 U·잔여 저장 2 U·잔여 IP 1 U다. 컴퓨팅만 중지한 뒤 남은 항목과 본문 실제 실행 범위를 적자.

  1. 본문 활동에서 실제로 수행한 것은 종이 계산 P다. 로컬 L과 유료 C의 예상 결과를 관찰 결과로 적지 않는다.

  2. 가상 청구표의 전체는 4+2+1=7 U다. 컴퓨팅 항목을 제거한 뒤도 2+1=3 U의 저장/IP 항목이 남는다고 가정했다.

  3. 종이상 남은 항목 계산과 실제 자원 정리는 다르다. 실제 자원을 만들지 않았으므로 실제 삭제·요금 종료를 확인했다는 주장도 하지 않는다.

가상 남은 비용 항목은 3 U이고 실제 완료는 종이 계산뿐이다. 실제 클러스터·청구·정리는 미수행이다.

종이와 본문으로 직접 해보기

가상의 비용이 8 U일 때 예산 알림 기준은 10 U인데, 알림 도착 전에 4 U가 추가되고 알림 이후 1 U가 더 들었다고 하자. 알림 도착/이후 총액과 기준 초과를 계산하고 알림이 즉시 상한이라는 주장이 맞는지 설명하자.

힌트 보기

알림 도착 시점까지 8+4를 계산한다. 알림 자체와 사용 중단은 다른 사건이다.

풀이 보기

알림 도착 때 12 U로 기준보다 2 U 높고 이후에는 13 U로 3 U 높다. 이 가상 표에서 알림은 즉시 상한이 아니다. 실제 AWS 지연 시간·실제 비용을 측정한 결과는 아니다.

오해와 반례

로컬 모형 성공과 예산 알림 설정만 있으면 유료 운영 검증도 끝났다.

로컬과 유료 환경의 증거 범위가 다르고 알림 반영 지연이 있다. 실제 운영·비용·정리 검증을 별도 수행해야 한다.
