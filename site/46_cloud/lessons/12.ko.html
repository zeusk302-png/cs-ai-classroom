평균은 빨라 보이는데 일부 호출은 여전히 느리다면 무엇을 함께 봐야 할까요?

기본 원고의 초기화 300 ms와 처리기 40 ms를 유지합니다. 대기·통신을 제외한 자체 호출 모형에서 새 환경 C는 340 ms, 재사용 W는 40 ms입니다. 이번에는 호출 20개의 평균과 p95를 비교합니다. p95는 이 문제에서 시간을 오름차순으로 정렬한 뒤 ceil(0.95×20)=19번째 값을 택하는 최근접 순위 방식으로 정의합니다. 보간 방식으로 계산한 백분위수와 다를 수 있습니다.

이벤트의 중복도 식별자만 읽고 끝내지 않습니다. 자체 계약에서 같은 이벤트 ID는 같은 정규화 업무 내용과 연결되어야 합니다. ID가 같은데 금액이 달라진 요청은 기록한 내용과 충돌하므로 거부합니다. 결과와 ID·내용 기록은 같은 DB에서 원자적으로 저장하고 외부 메일은 그 경계에 자동 포함되지 않는다고 정합니다. 호출 통계와 업무 상태는 종이 모형이며 실제 Lambda의 지연·중복률을 측정하지 않습니다.

이벤트가 실행을 요청하는 경계

서버리스에서는 서버가 사라지는 것이 아니라 인프라 관리의 상당 부분을 제공자가 맡는다. 함수 방식은 사진 업로드처럼 발생한 일을 입력으로 받아 정해진 처리기를 실행하는 형태다. 이벤트 생산자, 전달 경로, 처리 함수, 결과 저장소를 네 칸으로 그려 보면 한 함수가 전체 시스템을 대신하지 않는다는 점이 보인다.

이벤트가 접수되었다는 응답과 업무 처리가 끝났다는 응답은 구별해야 한다. 동기 호출은 호출자가 결과를 기다리는 형태이고, 비동기 호출은 접수 뒤 별도로 실행될 수 있다. 실패 처리와 재시도는 호출 방식 및 이벤트 연결의 계약에 따라 다르므로 문서에서 확인해야 한다.

초기화와 일시적인 실행 환경

일반적인 on-demand Lambda 실행 환경은 처리기를 실행하기 전에 런타임과 정적 코드를 초기화한다. 새 환경의 준비 시간이 요청 지연에 더해지는 상황을 cold start라고 부른다. 기존 환경을 재사용하는 warm 실행에서는 같은 준비를 반복하지 않을 수 있지만 다음 요청의 재사용을 보장하지는 않는다.

환경 안의 변수나 임시 파일은 캐시로 활용할 수 있어도 영구적인 업무 기록으로 믿으면 안 된다. 환경이 교체되면 그 기록에 의존한 결과가 달라질 수 있기 때문이다. 초기화 의존성을 줄이거나 미리 준비하는 방식을 검토할 때도 운영 비용과 적용 조건을 함께 확인해야 한다.

재시도 가능한 입력과 한 번의 업무 효과

Lambda 비동기 호출은 오류 처리 과정에서 재시도될 수 있고, 오류가 없더라도 중복 이벤트를 받을 수 있다. 같은 주문에 같은 포인트를 다시 더하면 실행은 성공해도 업무 결과는 틀린다. 멱등성은 같은 요청을 반복해도 의도한 업무 효과가 추가로 반복되지 않도록 만드는 성질이다.

아래 종이 모형에서는 처리 식별자 확인·업무 값 갱신·처리 기록 저장을 하나의 원자적인 동작으로 가정한다. 확인 뒤 기록 전에 다른 실행이 끼어들거나 실패할 수 있는 실제 프로그램에서는 단순한 메모리 집합만으로 충분하지 않다. 외부 호출까지 포함한 전체 효과에는 별도의 중복 방지 계약이 필요하다. 실패한 이벤트를 모으는 목적지와 재처리 정책도 설계의 일부다.

평균은 전체 합을 20으로 나누고 p95는 명시한 19번째 값을 읽습니다. 첫 행의 p95가 40 ms라고 해도 최대 호출 340 ms가 사라지는 것은 아닙니다. 이 20개 표본을 실제 서비스 전체 트래픽의 보장으로 사용하지 않습니다.

중간 과정을 따라가는 예제

가상 함수의 초기화는 300 ms, 처리기는 40 ms다. 대기·통신 시간은 0으로 단순화한다. 네 호출은 새 환경 C, 재사용 W, W, 새 환경 C 순이다. 별도로 초기 포인트 0에 이벤트 E1(+5), E1(+5)의 중복, E2(+3)가 순서대로 온다. 같은 식별자는 같은 업무 요청이며 원자적 중복 방지를 가정한다.

  1. C의 시간은 300+40=340 ms이고 W의 시간은 40 ms다. 네 시간은 340, 40, 40, 340 ms다.

  2. 합계는 760 ms, 평균은 760/4=190 ms, 최대는 340 ms다. 이 네 관찰의 평균이 모든 실제 트래픽의 지연을 대표하지는 않는다.

  3. 중복 방지 없이 포인트를 더하면 0→5→10→13이다. E1이 이미 처리되었으면 두 번째 효과를 생략하여 0→5→5→8이 된다.

가상 평균 190 ms, 최대 340 ms다. 포인트의 의도한 값은 8이며 단순 반복 갱신의 13과 다르다. 모든 호출 시간과 이벤트는 자체 가정이며 실제 측정이 아니다.

조건을 바꾸어 비교하기

cold 호출 하나와 둘 비교

표의 두 구성을 손계산하여 평균·p95·최댓값을 비교하세요.

  1. C 1회는 340+19×40=1100 ms이므로 평균은 55 ms입니다.

  2. C 1회 구성의 19번째는 40 ms, 최대는 340 ms입니다.

  3. C 2회는 2×340+18×40=1400 ms이므로 평균은 70 ms입니다.

  4. C 2회 구성의 19번째와 최대는 모두 340 ms입니다.

cold 호출이 한 번인 구성의 평균은 55 ms이고 p95는 40 ms입니다. cold 호출이 두 번인 구성의 평균은 70 ms이고 p95는 340 ms입니다. 두 구성의 최댓값은 모두 340 ms입니다.

비교할 점

같은 초기화 시간에서도 cold 비율과 표본 구성에 따라 통계가 달라집니다. 실제 함수의 p95나 cold 비율을 예측한 값이 아닙니다.

같은 ID에 다른 내용이 들어오기

초기 포인트는 0입니다. E1(+5)을 원자 저장한 뒤 같은 E1(+5)이 재시도되고, 이어 E1(+8)이 옵니다. 자체 계약은 ID와 정규화 내용을 함께 기록하며 같은 ID의 내용 충돌을 거부합니다. 상태를 추적하세요.

  1. 첫 E1(+5)은 포인트 5와 기록 (E1,+5)을 함께 저장합니다.

  2. 두 번째 E1(+5)은 기록 내용과 같으므로 결과를 재사용하고 효과를 반복하지 않습니다.

  3. E1(+8)은 같은 ID의 저장 내용 +5와 다르므로 충돌로 거부합니다.

  4. 거부는 +8을 적용했다는 성공 응답과 다릅니다. 최종 포인트는 5입니다.

최종 포인트는 5이고 E1(+8)은 내용 충돌로 거부합니다.

비교할 점

이 충돌 정책은 자체 애플리케이션 계약입니다. AWS가 임의 이벤트의 업무 금액 충돌을 자동으로 검사한다는 뜻은 아닙니다.

오해와 반례

함수가 성공하면 동일 이벤트가 다시 오지 않으며 함수 내부 변수에 처리 기록을 두면 충분하다.

성공 후에도 가능한 중복 전달과 실행 환경 교체를 생각해야 한다. 로컬 변수가 초기화되면 E1을 다시 처리할 수 있다. 업무 데이터와 중복 식별자를 함께 원자적으로 관리하는 조건을 확인해야 하며 외부 효과는 추가 계약이 필요하다.

연습 1 · 값과 상태 예측

초기화만 100 ms로 바꾸고 C 2회·W 18회를 유지합니다. 자체 20회 표본의 평균·p95·최댓값을 구하세요.

힌트 1

C=100+40 ms입니다.

힌트 2

정렬된 19번째와 20번째는 C입니다.

풀이와 답 확인

  1. C는 140 ms입니다. 전체 합은 2×140+18×40=1000 ms입니다.

  2. 평균은 1000/20=50 ms입니다.

  3. p95와 최대는 모두 140 ms입니다.

평균 50 ms, p95 140 ms, 최대 140 ms입니다.

힌트 1

힌트 2

20번째 호출의 시간을 확인합니다.

풀이와 답 확인

  1. 19개 호출은 40 ms이지만 나머지 한 호출은 340 ms입니다.

  2. 명시한 p95는 40 ms이고 최대는 340 ms로 서로 다릅니다.

  3. p95 하나로 모든 호출의 지연 상한을 보장할 수 없습니다.

한 호출은 340 ms입니다. p95는 이 표본의 순위 통계이며 전체 호출의 상한이 아닙니다.

힌트 1

힌트 2

포인트와 중복 기록이 서로 다른 수명을 가집니다.

풀이와 답 확인

  2. 포인트 5에 +5를 적용하면 10이 됩니다.

  3. 영구 DB의 포인트와 안정 ID·내용 기록을 원자적으로 관리하고 동시 처리의 유일성·경합 조건도 정해야 합니다.

잘못된 결과는 10입니다. 일시적 환경 메모리를 업무 중복 기록의 유일한 근거로 사용하지 않습니다.

실행 중인 처리기 수는 줄었는데 연결은 여전히 부족하다면 무엇을 세어야 할까요?

기본 원고의 DB 연결 한도 12개와 다른 작업의 점유 4개를 유지합니다. 기본 계산은 실행 중인 처리기 하나가 연결 두 개를 점유할 때 동시 실행 상한이 4개였습니다. 새 자체 모형에서는 환경마다 최대 두 연결을 미리 열고, 호출이 끝나도 그 환경의 연결을 닫지 않습니다. 따라서 실행 중인 처리기 수가 아닌 살아 있는 환경의 열린 연결 수를 세어야 합니다. 실제 Lambda나 DB가 언제나 이 정책을 쓴다는 뜻은 아닙니다.

자원 조건을 만족해도 데이터 권한은 별도로 확인합니다. 아래 자체 정책은 네트워크 허용, DB 인증, SELECT 또는 UPDATE 권한을 서로 다른 칸으로 기록합니다. 인스턴스를 변경하는 관리 권한은 이 표의 SELECT 권한을 자동으로 추가하지 않습니다. 제공자가 맡는 인프라 운영과 고객의 연결·권한·업무 정확성 책임을 구별하는 연습입니다.

먼저 확인할 개념
  • 관리형 데이터·컴퓨팅

    기본의 연결 한도와 서비스 관리/데이터 접근 권한 구분을 환경 수명과 단계별 정책으로 확장합니다.

  • 함수·이벤트·cold start

    재사용 환경의 연결과 일시적 상태가 호출 하나보다 오래 남을 수 있다는 조건을 연결합니다.

관리 작업과 데이터 의미는 다른 책임

관리형 데이터 서비스는 데이터베이스를 운영하는 여러 작업을 대신 수행한다. RDS에서는 기반 인프라와 운영 작업의 책임이 고객 직접 운영과 달라진다. 그러나 애플리케이션의 정확한 결과와 쿼리·스키마 설계까지 제공자가 대신 결정하지는 않는다. 잘못 작성한 조건은 관리형 데이터베이스에서도 잘못된 행을 바꿀 수 있다.

백업 기능이 제공된다는 사실과 우리의 데이터가 필요한 시점으로 복구된다는 사실도 구별한다. 보존 정책, 복구 목표, 실제 복원 후 데이터 확인을 따로 점검해야 한다. 가용성을 위한 복제본과 실수 이전 상태를 되찾는 백업은 목적이 다르다.

서비스 설정 권한과 데이터 권한

RDS 공식 문서는 인프라 보호와 고객의 보안 설정을 나누고, DB 인스턴스를 생성·변경하는 관리 권한과 DB 안에 로그인하는 권한을 구별한다. 네트워크 연결을 허용했다고 모든 데이터 작업을 허용한 것도 아니다. 연결, 인증, 업무 권한을 순서대로 확인하면 실패 위치를 설명하기 쉽다.

이 단원의 종이 정책에서는 보고서 계정은 조회만, 운영 계정은 서비스 설정 변경만 허용한다. 실제 제품에서 이 역할들이 자동으로 같은 경계를 갖는다는 뜻은 아니다. 계정별 서비스 정책과 데이터베이스 권한을 명시해 대조하는 연습이다.

관리형 컴퓨팅도 애플리케이션의 자원이 필요하다

함수 이외에 컨테이너를 실행하는 관리형 컴퓨팅도 있다. Fargate는 서버 클러스터 관리 부담을 줄이지만 고객은 컨테이너, CPU와 메모리 요구, 네트워크 및 IAM 설정을 준비한다. 지원되는 실행 계약을 확인해야 하며 모든 VM 기능을 그대로 사용할 수 있다고 가정하지 않는다.

처리기 수를 늘릴 때 다른 구성 요소가 같은 속도로 확장되는지도 확인한다. 아래 예제에서는 처리기 하나가 DB 연결 두 개를 점유한다고 가정한다. 처리기를 늘려도 연결 한도가 충분하지 않으면 모든 처리기가 동시에 원하는 연결을 얻지 못한다. 이 계산은 자원 수의 상한만 보여 주며 쿼리 처리량이나 지연을 예측하지 않는다.

중간 과정을 따라가는 예제

자체 서비스 A의 DB 연결 한도는 12개다. 다른 작업이 4개를 항상 점유하고, 처리기 하나는 실행 중 2개를 점유한다. 연결 공유·대기·자동 확장은 없다고 가정한다. 처리기 3개와 5개를 동시에 실행할 수 있는지 판단하자. 자체 정책에서 보고서 R은 SELECT만, 운영 O는 인스턴스 설정 변경만 허용한다.

  1. 처리기에 남는 연결은 12−4=8개다. 모든 처리기가 각 2개를 동시에 확보할 수 있는 최대 수는 floor(8/2)=4개다.

  2. 3개는 4+3×2=10개로 한도 이내다. 5개는 4+5×2=14개로 한도를 2개 넘으므로 가정한 동시 확보가 불가능하다. 실제로 기다릴지 실패할지는 추가 계약이다.

  3. R의 SELECT는 허용하고 UPDATE는 거부한다. O의 인스턴스 설정 변경은 허용하지만 이 정책만으로 SELECT 권한을 얻지는 않는다.

종이 모형의 동시 처리기 상한은 4개다. 3개는 자원 조건을 만족하고 5개는 만족하지 않는다. 관리형 서비스라는 이름과 데이터 접근 권한은 별개다.

조건을 바꾸어 비교하기

유휴 환경의 연결을 포함하기

다른 작업이 네 연결을 점유하고 있습니다. 환경 다섯 개를 유지하면서 각 환경이 연결 두 개를 열고, 호출 종료 뒤에도 유지하도록 계획했습니다. DB 한도는 12개이고 실제 호출을 실행하려는 환경은 하나뿐입니다. 계획한 전체 연결 요구와 부족량을 구하세요. 한도를 넘는 14개가 실제로 이미 열렸다고 가정하지 않습니다.

  1. 환경의 열린 연결 요구는 5×2=10개입니다.

  2. 다른 작업의 4개까지 더하면 총 요구는 14개입니다.

  3. 한도 12보다 2개 많으므로 모든 요구를 동시에 충족할 수 없습니다.

  4. 실행 환경 하나만 세어 4+2=6개라고 계산하면 유휴 환경에 남은 연결을 누락합니다.

총 요구 14개로 2개가 부족합니다. 기다림·실패·연결 회수 방식은 추가 계약입니다.

비교할 점

이 수치는 실제 연결 풀이 관측된 결과가 아닙니다. 실행 중이 아닌 환경도 열린 연결을 유지한다는 명시한 모형 조건에서만 성립합니다.

같은 개수의 처리기라도 요구량은 다름

처리기 A는 연결 3개, B는 1개, C는 2개를 필요로 합니다. 다른 작업 4개를 제외하면 가용 연결은 8개입니다. A 2개+B 2개, A 3개, C 4개의 동시 요구를 비교하세요.

  1. A 2개+B 2개는 2×3+2×1=8개로 가용량과 같습니다.

  2. A 3개는 3×3=9개로 가용량보다 1개 많습니다.

  3. C 4개는 4×2=8개로 가용량과 같습니다.

같은 코드와 이벤트를 다른 클라우드에 옮기면 비용과 동작도 그대로 같을까?

같은 사건을 처리해도 재시도 수나 사용량이 달라지면 이전 비용 판단은 유지될까요?

기본 원고의 가상 단가를 유지합니다. A는 실행 요청당 1점, GB-second당 2점, 월 부대비 20점입니다. B는 요청당 0.8점, GB-second당 3점, 월 부대비 40점입니다. 각 과금 실행은 0.5 GB를 0.2초 사용하므로 0.1 GB-second입니다. 무료 구간과 반올림은 없다고 정합니다. n을 월 과금 실행 횟수로 두면 A=1.2n+20, B=1.1n+40입니다. 이 자체 점수는 실제 가격이나 구매 권고가 아닙니다.

이벤트 형식의 공통화와 업무 의미의 이식은 나누어 봅니다. CloudEvents의 source와 id는 서로 다른 사건을 구별하는 범위이며 봉투가 같다고 data의 업무 스키마가 자동으로 같아지지는 않습니다. 아래 어댑터는 두 입력의 서로 다른 필드명을 내부 점수로 바꾸되, 원래 source/id 쌍은 보존합니다. 내용을 바꾼 같은 식별자의 충돌 정책과 중복 방지의 원자성은 자체 애플리케이션에서 따로 정의합니다.

  • 함수·이벤트·cold start

    업무 이벤트 수와 재시도를 포함한 함수 실행 수가 다를 수 있음을 비용 계산에 연결합니다.

옮길 대상을 네 층으로 나누기

프로그램의 계산 부분은 그대로 사용해도 이벤트 입력, 저장소 API, 인증, 배포 설정을 바꾸어야 할 수 있다. 이식성은 어느 층을 얼마나 수정해 옮길 수 있는지에 관한 성질이다. 공급자 종속성은 특정 API나 운영 기능에 기대어 변경 비용이 커지는 상황으로 이해하자. 기능을 이용하는 이득과 변경 비용을 함께 비교해야 한다.

자체 설계에서는 계산 핵심에 공급자의 요청 객체를 바로 넣지 않고 내부 입력으로 바꾸는 어댑터를 둔다. 그렇다고 모든 차이가 없어지지는 않는다. 재시도·순서·트랜잭션·권한·제한 시간과 데이터 이전을 확인해야 같은 업무 의미를 유지할 수 있다.

공통 이벤트 형식의 도움과 경계

CloudEvents는 이벤트의 공통 표현을 정하는 공급자 중립 규격이다. 1.0.2의 필수 속성은 id, source, specversion, type이며 specversion 값은 1.0이다. 서로 다른 이벤트의 식별에서는 source와 id를 함께 보며, 같은 쌍으로 재전송된 이벤트는 중복으로 판단할 수 있다.

공통 봉투에 담아도 data 안의 업무 스키마는 별도로 정의해야 한다. 이 규격을 쓴다는 사실만으로 모든 플랫폼에서 전달 횟수·순서·인증·DB 기능이 같아지지 않는다. 종이 비교 표에 이벤트 형식과 운영 의미를 다른 행으로 적으면 무엇을 실제로 옮겼는지 분명해진다.

요청 수와 자원 시간에 단가를 곱하기

요금은 서비스와 실행 방식마다 다르다. Lambda Functions의 공식 요금 설명에서는 요청과 GB-seconds 같은 항목을 구별하며 미리 준비하는 방식의 별도 항목도 있다. 실제 청구는 지역, 실행 방식, 반올림과 무료 구간 등 계약을 확인해야 한다. 여기서는 구조를 연습하기 위해 실제 통화가 아닌 가상 비용점만 사용한다.

단순 모형의 자원 시간은 호출 수×호출당 할당 GB×호출당 과금 초다. 같은 호출 수도 실행 시간이 늘거나 할당량이 커지면 달라진다. 로그·저장·전송·실패한 재시도와 전환 작업의 비용까지 비교 범위를 적어야 한다. 일부 항목만 싼 것을 전체 시스템이 더 싸다고 해석하지 않는다.

중간 과정을 따라가는 예제

자체 한 달 모형에서 실행 100회, 할당량 0.5 GB, 호출당 과금 시간 0.2초다. 무료 구간·반올림은 없다고 가정한다. A는 요청당 1점, GB-second당 2점, 부대비 20점이다. B는 요청당 0.8점, GB-second당 3점, 부대비 40점이다. B로 옮기는 일회 비용은 50점이며 두 달 동안 같은 사용량이라고 가정한다.

  1. 자원 시간은 100×0.5×0.2=10 GB-seconds다. A의 한 달 비용은 100×1+10×2+20=140점이다.

  2. B의 한 달 비용은 100×0.8+10×3+40=150점이다. 요청 단가는 낮아도 포함한 월 총액은 더 크다.

  3. 두 달 A는 2×140=280점이다. B는 50+2×150=350점이다. 같은 이벤트 형식을 사용할 수 있어도 이 계산에서 전환 비용을 없애지는 못한다.

가상 두 달 비용은 A 280점, B 350점이며 차이는 70점이다. 실제 제품 가격이나 구매 권고가 아니고, 명시한 항목과 사용량에서만 성립한다.

조건을 바꾸어 비교하기

사용량에 따라 월 손익이 바뀜

두 서비스의 월액이 같은 n과, n=300일 때 일회 전환비 50점을 회수하여 B가 엄격히 더 저렴해지는 최소 정수 개월을 구하세요.

  1. 월액 차이는 A−B=0.1n−20입니다. 같음은 n=200입니다.

  2. n=300이면 A=380점, B=370점으로 월 절감은 10점입니다.

  3. k개월 A는 380k, 전환한 B는 50+370k입니다.

  4. B가 작으려면 50<10k이므로 k>5입니다. 5개월은 같고 6개월부터 작습니다.

월액 같음은 n=200입니다. n=300 조건에서는 6개월부터 B가 작습니다.

업무 이벤트 100개와 과금 실행 140회

고유 업무 이벤트는 100개지만 재시도로 총 과금 실행이 140회입니다. 모든 실행이 각각 0.5 GB·0.2초를 사용한다고 정합니다. A/B의 월액과 의도한 업무 효과 횟수를 구하세요. 안정된 업무 ID의 원자적 중복 방지가 있다고 가정합니다.

  1. 과금 실행의 자원 시간은 140×0.5×0.2=14 GB-seconds입니다.

  2. A는 140+14×2+20=188점입니다.

  3. B는 140×0.8+14×3+40=194점입니다.

  4. 100개 고유 이벤트의 업무 효과를 각각 한 번 적용하더라도 실행 비용은 명시한 140회 기준으로 계산합니다.

가상 월액은 A 188점, B 194점입니다. 의도한 업무 효과는 100개이며 실행 140회와 다릅니다.

실제 재시도의 과금 여부와 처리 시간은 계약에 따라 확인해야 합니다. 이 예에서는 모든 140회를 같은 과금 실행으로 명시했습니다.

종이와 본문으로 직접 해보기

B의 부대비만 월 10점으로 줄어든 별도 시나리오를 계산하자. 일회 전환비 50점과 같은 사용량을 유지할 때 두 달·세 달의 총액을 비교하자. 같은 id E1이 source S1과 S2에서 각각 왔다면 무조건 하나의 중복으로 합쳐도 되는지도 판단하자.

힌트 보기

변경 후 B 월액을 먼저 구하고, 매월 절감액과 일회 비용을 비교한다. 이벤트 식별의 범위는 source+id다.

풀이 보기

B의 변경 월액은 80+30+10=120점이며 A보다 월 20점 작다. 두 달 B는 50+240=290점으로 A 280점보다 10점 크다. 세 달 B는 50+360=410점으로 A 420점보다 10점 작다. 수학적 같음은 50/20=2.5개월이나 정수 개월 비교에서는 세 달부터 작다. S1/E1과 S2/E1은 쌍이 다르므로 같은 id라는 이유만으로 중복으로 합치지 않는다.

오해와 반례

표준 이벤트와 컨테이너를 사용하면 공급자 변경이 무료이고 요청 단가가 싼 서비스가 전체적으로 가장 싸다.

표준화는 특정 형식이나 포장을 돕지만 데이터 이전·권한·운영 계약의 차이는 남을 수 있다. 원래 예제에서 B의 요청 단가는 낮지만 부대비를 포함한 월액이 더 크다. 전환 작업과 비교 기간을 빼면 판단이 달라질 수 있다.

힌트 2

풀이와 답 확인

    실제 REQUIRED Attributes의 id/source 유일성 범위·specversion 값 1.0·type 및 datacontenttype의 업무 자료 형식 범위를 읽었다. points/score의 내부 의미와 동일 식별자 내용 충돌은 자체 스키마·정책이며 규격의 자동 업무 변환이 아니다.
