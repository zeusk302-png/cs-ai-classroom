선언적 구성·IaC

서버 만들기 순서를 적는 것과 필요한 서버 상태를 적는 것은 어떻게 다를까?

준비 개념과 학습 목표

준비 개념

  • 설정 파일

  • 버전 관리

  • 자원의 식별자

학습 목표

  • 희망 상태·관측 상태·관리 state를 구분한다.

  • 계획과 적용을 나누고 자원 의존성을 읽는다.

선언적 적용 도중 하나만 실패하면 성공한 자원도 모두 사라질까요?

기본 의존 그래프에 두 선행 조건과 부분 실패를 추가합니다. 자체 예의 네트워크 N은 2분, 권한 I는 4분이며 서로 독립입니다. 서버 S는 둘이 끝나야 시작해 3분, 설정 C는 S 뒤 1분입니다. 작업 자원이 충분하고 실패·재시도·API 대기가 없을 때 계획 시간은 max(2,4)+3+1=8분입니다. 파일 줄 순서의 합 10분이나 가장 짧은 선행 작업 2분으로 판단하지 않습니다.

Terraform plan은 변경 제안이며 적용이 아닙니다. 저장하지 않은 예비 계획을 검토한 뒤 현실이 달라지면 최종 계획의 효과도 달라질 수 있습니다. apply가 부분 실패하면 자동으로 전체 롤백하지 않으므로 성공한 변경, 관리 state와 실제 객체를 다시 확인합니다. state locking 역시 backend가 지원해야 하며 같은 state의 동시 기록을 막는 기능입니다. 모든 원격 업무를 원자적 거래로 바꾸는 기능이 아닙니다.

원하는 결과를 자료로 표현한다

IaC(infrastructure as code)는 서버·네트워크·접근 규칙 등의 구성을 버전 관리 가능한 텍스트로 표현해 검토와 자동화를 돕는 방법이다. 선언적 구성은 어떤 상태를 원하는지 적고 도구가 지원하는 범위에서 현재 상태와의 차이를 계획한다. 모든 자동화가 선언적이라는 뜻은 아니며 명령 순서를 적는 스크립트도 IaC 작업에 함께 쓰일 수 있다.

가상 구성을 네트워크 N, 서버 S, S가 N을 사용한다는 참조로 표현해 보자. 먼저 필요한 참조를 만족한 뒤 서버를 생성해야 한다. 파일에 먼저 적힌 줄이 무조건 먼저 실행되는 것은 아니다. Terraform은 구성의 참조에서 의존성을 파악하고 provider를 통해 실제 서비스 API를 사용한다.

구성·state·현실은 서로 다른 기록이다

구성은 목표를 담고 state는 도구가 관리하는 자원과 원격 객체의 대응을 기록한다. 현실은 서비스에 실제로 존재하는 객체와 현재 속성이다. 사람이 콘솔에서 값을 바꾸면 구성과 state가 그대로인 채 현실만 달라질 수 있다. 도구를 다시 실행한다고 이 세 기록이 항상 같은 의미라는 전제를 세우면 안 된다.

동일 목표를 반복 적용할 때 추가 변경이 없는 수렴을 기대하지만 이것은 도구와 자원의 계약에 달려 있다. 매번 변하는 값이나 외부 변경, 교체가 필요한 속성, 실행 중 실패 때문에 변경이 다시 생길 수 있다. 선언적이라는 이름만으로 모든 명령의 재시도가 무해하거나 전체 변경이 원자적으로 완료되는 것은 아니다.

형식 검증·계획·적용의 역할

형식과 참조를 검증하는 단계는 문법과 내부 모순을 찾는다. 계획 단계는 생성·변경·삭제와 자원 교체를 보여 주고 적용은 실제 API 호출을 수행한다. 검증이 성공했다고 운영 기능이 동작하거나 삭제 계획이 적절하다는 증거는 아니다. 변경 대상과 의존성을 계획에서 확인한다.

실행 환경과 provider 버전도 기록해야 같은 텍스트의 뜻을 재현하기 쉽다. Terraform의 dependency lockfile은 선택된 provider 버전을 기록하는 사례다. 동시에 여러 작업이 같은 관리 상태를 갱신하지 않도록 실행을 조정하고, 일부 성공 뒤 실패했을 때는 실제 상태를 다시 관측한 뒤 후속 계획을 세운다.

중간 과정을 따라가는 예제

종이 모델에서 목표 자원은 N 네트워크, A/B 서버이며 두 서버는 N에 의존한다. 실제 관리 자원은 N/A뿐이고 설정도 이미 목표와 같다. 네트워크 생성 시간2분, 서버 생성 각3분이며 서버 둘은 독립이면 병렬 가능하다고 가정한다.

  1. 현재 N과 A는 목표와 같고 B만 없다. 이번 변경 계획은 B 생성1개이며 N/A를 새로 만드는 계획은 아니다.

  2. 완전히 빈 상태에서라면 N을0–2분에 만든다. A/B는 N 뒤2–5분에 병렬 생성할 수 있다. 총5분이다.

  3. 서버를 순차로 만들면2+3+3=8분이다. 병렬5분은 서비스 제약과 비용을 무시한 가상 모델이다.

  4. 현재 상태에서 B만 만들면3분이다. 적용 후 세 자원이 목표와 같고 외부 변화가 없으면 다음 계획은 변경0개다.

차이 기반 계획은 B만 생성한다. 의존 그래프와 가상 시간 모델을 이용하면 빈 상태의 병렬 경로5분과 현재 상태3분을 구별한다.

조건을 바꾸어 비교하기

짧은 작업만 줄이면 전체도 줄까요?

표의 N을 2분에서 1분으로 줄이고, I는 4분, S는 3분, C는 1분으로 유지합니다. 별도 사례에서는 I를 4분에서 2분으로 줄이고 N은 2분으로 유지합니다. 두 계획 시간을 비교하세요.

  1. N만 줄이면 max(1,4)+3+1=8분입니다.

  2. I가 여전히 선행 조건의 긴 경로여서 전체 시간은 줄지 않습니다.

  3. I를 2분으로 줄인 별도 사례에서는 max(2,2)+3+1=6분입니다.

  4. 작업 시간을 줄인 효과는 어느 필수 경로가 가장 긴지에 따라 달라집니다.

N만 줄인 계획 8분, I를 2분으로 줄인 별도 계획 6분입니다.

비교할 점

변경한 시간은 자체 입력입니다. 도구의 자동 최적화나 실제 서비스 속도 향상을 입증한 결과가 아닙니다.

하나 성공하고 하나 실패한 뒤 다시 보기

이미 N이 존재하며 목표는 N/A/B입니다. A와 B의 생성은 독립입니다. apply에서 A 생성이 성공하고 그 변경은 state에 기록됐지만 B는 생성 전에 실패했습니다. 다른 원격 변화가 없고 재시도 전 관측도 N/A 존재·B 부재를 확인했다고 정합니다. 다음 차이 기반 계획은?

  1. 실패했다는 한 줄로 성공한 A가 자동 삭제됐다고 판단하지 않습니다.

  2. 확인한 state와 실제 객체에는 N과 A가 남습니다.

  3. 목표 자원 중 현재 현실에 없는 것은 B 하나입니다. 이 예의 생성 계약 아래 다음 계획은 B 생성입니다.

  4. B 실패 원인을 해결한 뒤 최종 계획을 검토합니다. 처음의 전체 생성 계획을 그대로 재실행했다고 가정하지 않습니다.

주어진 관측과 계약에서 다음 계획은 B 생성 1개입니다.

비교할 점

provider가 원격 객체를 만들었지만 state 기록 전에 실패한 다른 사례라면 결과가 달라질 수 있습니다. 이 예는 그 모호함을 제외한 명시 조건입니다.

종이와 본문으로 직접 해보기

목표 N/A/B에서 실제 N/A/B/C가 있다. C는 이 구성의 관리 자원이며 목표에서 제거됐다고 가정한다. 단순 모델의 차이를 쓰라. C가 관리 대상이 아닌 외부 자원일 때와 비교하라.

풀이 보기

관리 대상 C를 목표에서 제거한 단순 모델은 C 삭제1개를 계획한다. C가 외부 비관리 자원이면 이 목표만으로 C를 삭제한다고 단정할 수 없다. 실제 삭제/보존은 도구와 lifecycle 계약을 확인한다.

오해와 반례

선언적 구성은 상태가 틀려도 반복 적용하면 모든 자원을 안전하게 복원한다.

교체·삭제와 부분 실패가 생길 수 있다. 계획과 실제 상태를 확인하며 관리 경계·보존 조건·자원별 재시도 의미를 따져야 한다.

새 버전이 먼저 공개되고 옛 배포가 나중에 끝나면 마지막 화면은 어느 버전일까요?

기본 파이프라인의 검사와 배포 의존성을 실패 사례에 적용합니다. build가 성공해도 unit과 content 중 하나가 실패하면 둘을 needs로 요구하는 deploy는 기본 성공 조건에서 건너뜁니다. always()를 붙이면 의존 작업의 성공 여부와 무관하게 후속 job을 실행할 수 있으므로 정리·보고 job의 조건을 운영 배포와 섞지 않습니다. 여기의 결과는 문서 규칙에 따른 종이 추적이며 새 Actions workflow를 실행한 관측이 아닙니다.

같은 환경의 두 배포도 공유 자원을 갱신합니다. 자체 덮어쓰기 모형에서 구버전 A는 0분 시작·8분 완료, 신버전 B는 1분 시작·4분 완료이고 각 완료가 곧 공개 포인터의 쓰기라고 정합니다. 4분에는 B가 보이지만 8분에는 A가 덮습니다. concurrency group은 동시 실행을 제어하지만 workflow의 발생 순서가 곧 적용 순서라는 보장은 아닙니다. 최신 버전만 허용하는 별도 원자적 조건을 설계하려면 판정과 공개 갱신을 함께 보호해야 합니다.

자동화 파이프라인은 단계 사이 계약이다

CI(continuous integration)는 변경을 자주 통합하고 빌드·검사를 자동 수행해 문제를 빨리 찾는 흐름이다. CD는 자료에 따라 continuous delivery 또는 continuous deployment를 뜻하므로 의미를 명시한다. 여기서는 delivery를 검증된 변경을 배포 가능한 상태로 준비하는 과정, deployment를 정한 조건에 따라 실제 배포하는 과정으로 구분한다.

GitHub Actions의 workflow는 이벤트로 시작하고 job은 runner에서 step을 실행한다. job 사이 의존성이 없으면 병렬 실행될 수 있다. 배포가 검사 성공을 기다려야 한다면 그 의존 관계를 명시해야 한다. 자동화 파일이 있다는 사실만으로 실패한 검사 뒤 배포가 차단된다고 보장되지 않는다.

검사한 산출물의 신원을 유지한다

빌드 결과에 커밋 식별자와 산출물 해시를 기록하면 무엇을 검사했는지 추적할 수 있다. 검사를 마친 뒤 운영 단계에서 다시 빌드하면 의존성이나 시간별 생성 내용 때문에 다른 파일이 될 수 있다. 동일 산출물을 환경 사이에 이동하는 설계는 검사 대상과 배포 대상의 대응을 명확하게 한다.

환경은 개발·검증·운영처럼 다른 설정과 접근 권한을 갖는 배포 대상을 뜻한다. 프로그램 파일이 같아도 연결 주소·기능 설정·비밀 값이 다르면 동작이 다를 수 있다. 따라서 산출물 해시와 함께 환경 설정 버전, 데이터 호환성도 확인한다. 같은 해시는 설정과 실제 사용자 결과까지 같다는 증거는 아니다.

배포 완료와 이용 가능을 확인한다

파이프라인 성공은 그 파이프라인에서 실행한 단계가 성공했다는 뜻이다. 실제 주소에 새 버전이 노출되는지, 필요한 자료가 열리는지 별도로 확인한다. 캐시나 잘못된 경로 때문에 이전 버전이 보일 수 있다. 공개 버전 메타데이터를 조회해 기대한 산출물 식별자와 대조하는 방법을 사용할 수 있다.

환경 보호 조건은 승인·허용 브랜치·준비 상태 검사 등을 배포 단계에 붙이는 정책이다. GitHub environment를 참조하는 job은 그 환경의 설정을 사용하며 보호 조건이 있으면 통과 후 진행한다. 실패 시 이전 산출물로 되돌리는 절차도 준비하되 데이터 형식 변경은 파일만 되돌린다고 복구되지 않을 수 있다.

관리 기록을 현실에 맞추는 것과 현실을 목표로 돌리는 것은 같은 작업일까요?

목표·state·현실을 여러 자원에 나누어 표시합니다. 아래 자체 모형에서 A의 연결 제한은 목표와 처음 state에 각각 100으로 기록됐고, 현실은 150입니다. B는 목표와 state에 존재했지만 원격에서 삭제됐습니다. 외부 비관리 자원 C도 존재합니다. 완전하고 정확한 관측을 refresh-only로 기록하면 A의 state는 150이 되고, B의 관리 대응은 부재를 반영합니다. 원격 A의 제한은 여전히 150이고 B는 부재이며 목표도 그대로입니다. 이후 일반 계획은 지원되는 수정·생성 계약에서 A를 100으로 변경하고 B를 만들 수 있습니다. C는 이 관리 경계에 없으므로 존재만 보고 자동 삭제한다고 가정하지 않습니다.

비밀을 숨긴 화면과 저장되지 않는 값도 다릅니다. sensitive는 CLI와 UI 표시를 가리지만 state와 plan에는 남을 수 있고 output의 raw/json 출력은 평문을 보여줄 수 있습니다. ephemeral은 지원 버전·provider·허용 참조 문맥에서 저장을 피하는 별도 기능입니다. 아무 자원 속성이나 root output에 자유롭게 넣는 이름표가 아닙니다. 아래 문서는 실값 대신 TOKEN_PLACEHOLDER만 쓰며 실제 비밀을 조회하거나 출력하지 않습니다.

설정과 비밀은 같은 공개 파일에 넣지 않는다

기능 토글이나 공개 서비스 주소는 설정이지만 인증 토큰과 비밀번호는 접근 권한을 주는 비밀이다. 환경별 값은 프로그램과 분리해 관리할 수 있지만 환경 변수라는 전달 형식 자체가 암호화를 의미하지는 않는다. 읽을 수 있는 프로세스·로그·산출물의 범위를 함께 확인한다.

GitHub Actions는 secret 저장소의 값을 필요한 step의 입력이나 환경 변수로 전달할 수 있다. 비밀을 출력하는 로그를 만들지 않고 필요한 작업에만 권한을 준다. 미설정 secret이 빈 문자열일 수 있으므로 빈 값을 정상 인증 값으로 간주하지 않는다. Base64는 표현 변환이며 공개된 문자열을 숨기는 암호화 수단이 아니다.

표시를 가리는 것과 저장하지 않는 것은 다르다

Terraform에서 sensitive 표시는 CLI에 값을 가리는 기능이지만 해당 값이 state와 plan 파일에 남을 수 있다. 누구나 읽는 저장소에 이런 파일을 올리면 화면에서 숨긴 값도 노출될 수 있다. 실제 값을 넣지 않은 예제 설정과 비밀을 담은 실행 상태를 구분한다.

저장 방지 기능도 도구 버전과 provider의 지원 범위에 따라 다르다. 문서의 ephemeral과 write-only는 특정 조건에서 저장을 피하는 선택지이지 모든 기존 비밀이 자동 제거된다는 뜻이 아니다. 비밀이 유출됐다면 파일 한 줄을 지우는 것과 권한을 폐기·교체하는 일을 구분한다. 기록과 이미 배포한 산출물에 남았는지도 확인한다.

드리프트는 세 기록의 차이에서 찾는다

drift는 도구 밖에서 변경된 현실과 구성 또는 관리 상태의 차이다. 목표 서버 수2, 관리 state2, 현실3이라면 외부에서 하나가 추가됐을 가능성이 있다. 하지만 그 추가 서버가 같은 관리 대상인지 확인해야 삭제 계획을 판단할 수 있다. 관측된 차이는 자동 복구 결정을 대신하지 않는다.

Terraform refresh-only는 현실에 맞춰 state를 갱신하는 계획/적용이며 원격 객체를 목표 구성으로 바꾸는 동작이 아니다. 외부 변경이 의도됐다면 목표 구성에도 반영하거나 관리 경계를 조정하고, 의도되지 않았다면 실제 변경 계획을 검토해 목표로 복원한다. state만 현실에 맞춘 뒤 구성은 그대로 두면 다음 일반 계획이 다시 차이를 만들 수 있다.

  1. 표시를 숨겼지만 일반 sensitive 값은 state와 plan에 남을 수 있습니다.

  3. ephemeral 사용에는 Terraform 버전, provider 지원과 허용 참조 문맥이 필요합니다.

  4. 지원되는 write-only 등 전달 경로와 저장되지 않는 범위, 기존 저장 기록을 따로 확인합니다.

sensitive 화면만으로 plan을 공개하지 않습니다. ephemeral도 지원과 참조 범위를 확인합니다.
