소단원 7.1

분산 파일시스템

큰 파일을 여러 컴퓨터에 나누어 두면 파일 이름은 누가 기억할까?

준비 개념과 학습 목표

준비 개념

  • 파일과 디렉터리

  • 바이트와 MiB

학습 목표

  • 메타데이터와 블록 데이터 경로를 구분한다.

  • 부분 블록과 복제 저장량을 계산한다.

전체 파일이 아니라 블록 경계를 걸친 일부만 읽으면 무엇을 세어야 할까요?

기본 원고의 300 MiB 파일은 길이가 각각 128 MiB, 128 MiB, 44 MiB인 블록 세 개로 나뉩니다. 파일 시작을 오프셋 0으로 놓고 범위를 [시작, 끝)으로 표시합니다. MiB 단위로 첫 블록은 [0, 128), 둘째는 [128, 256), 셋째는 [256, 300)입니다. 오프셋 120 MiB부터 20 MiB를 요청하면 끝은 140 MiB입니다. 첫 블록에서 8 MiB, 둘째에서 12 MiB를 읽으므로 접촉한 블록 수는 2개이고 요청한 페이로드는 20 MiB입니다. 이 범위 계산은 실제 HDFS의 네트워크·체크섬·미리 읽기 비용을 측정한 결과가 아닙니다.

복사본 수를 확인한 다음, 함께 실패하는 영역을 배치표에서 지워 봅니다. 노드 A와 B는 랙 R1, C는 랙 R2, D는 랙 R3에 있다고 정합니다. 기본 원고의 배치인 B1=A/B/C, B2=A/C/D, B3=B/C/D를 유지합니다. 랙 R1 장애로 A와 B가 동시에 사라져도 모든 블록에는 다른 랙의 복사본이 남습니다. 파일을 읽을 수 있는지와 목표 복제 수 3을 회복하는 데 필요한 추가 용량은 별도로 계산합니다. 이 자체 배치를 HDFS가 언제나 세 랙에 복사본을 하나씩 두는 정책으로 일반화하지 않습니다.

먼저 확인할 개념
  • 분산 파일시스템

    기본의 블록 길이와 A/B/C/D 배치를 범위·랙 장애 분석에 그대로 사용합니다.

  • 내구성·일관성·복제

    복사본의 생존과 최신성·백업의 역할을 구분합니다.

안내소와 창고의 역할

분산 파일시스템은 하나의 파일을 여러 저장 노드에 나누어 보관한다. HDFS에서는 NameNode가 이름·권한·블록 위치 같은 메타데이터를 관리하고 DataNode가 실제 블록을 보관한다.

읽는 클라이언트는 위치 안내를 받은 뒤 저장 노드에서 데이터를 받는다. 안내소에 파일 전체가 들어 있다고 생각하면 데이터 이동 경로를 잘못 그리게 된다.

블록과 복제는 다른 나눔이다

블록은 긴 파일을 자르는 단위이고 복제는 같은 조각을 여러 위치에 두는 일이다. 마지막 조각은 블록 최대 크기보다 작을 수 있으므로 실제 페이로드와 최대 수용량을 구별한다.

복제 위치는 장애의 범위와 연결된다. 같은 랙의 두 복사본은 그 랙 장애를 함께 겪을 수 있다. 아래 배치는 설명용이며 HDFS 기본 정책을 모든 복사본의 서로 다른 랙 배치로 일반화하지 않는다.

살아 있는 복사본에서 복구한다

노드 장애가 나면 남은 복사본으로 읽고 부족한 복제 수를 복구할 수 있다. 체크섬은 손상 감지를 돕지만 사라진 내용을 아무것도 없이 만드는 기술은 아니다.

복제는 실수로 삭제한 과거 버전을 항상 보존하는 백업과 다르다. 삭제·손상·전체 장애의 범위를 따져 별도의 복구 정책을 세워야 한다.

각 행의 추가량은 실제 블록 길이에 부족한 사본 수를 곱한 값입니다. 생존 페이로드 472 MiB는 중복 사본까지 포함한 저장량입니다. 서로 다른 원본 정보가 472 MiB라는 뜻은 아니며 파일의 논리 길이는 여전히 300 MiB입니다.

중간 과정을 따라가는 예제

파일 300 MiB를 최대 128 MiB 블록으로 자르고 각 블록을 3 개씩 저장한다. B1 은 A/B/C, B2 는 A/C/D, B3 는 B/C/D에 둔다. 메타데이터·체크섬·패딩 비용은 제외한다. C만 고장 나면 무엇이 남는가?

  1. 300=128+128+44 이므로 블록은 3 개다.

  2. 페이로드 복제량은 3×300=900 MiB다. 마지막 블록까지 128 MiB로 세는 1152 MiB는 이 모델의 실제 페이로드가 아니다.

  3. C를 지우면 B1 은 A/B, B2 는 A/D, B3 는 B/D에 남는다. 모두 읽을 수 있고 복제 수를 3 으로 되돌리려면 128+128+44=300 MiB를 추가로 복사한다.

블록 3 개, 복제 페이로드 900 MiB다. C 장애 후 각 블록 2 개씩 남으며 적절한 대상 노드와 용량이 있으면 300 MiB를 추가 복사한다.

조건을 바꾸어 비교하기

블록 경계를 넘는 짧은 읽기

오프셋 120 MiB부터 길이 20 MiB를 읽습니다. 자체 모형에서 요청한 바이트만 읽는 정책과 접촉한 블록 전체를 읽는 별도 정책의 페이로드를 비교하세요.

  1. 요청 구간은 [120, 140) MiB입니다. B1과 겹친 길이는 128−120=8 MiB입니다.

  2. B2와 겹친 길이는 140−128=12 MiB이며 B3와는 겹치지 않습니다.

  3. 요청 범위만 읽는 정책의 페이로드는 8+12=20 MiB입니다.

  4. 접촉한 두 블록 전체를 읽는 별도 정책의 페이로드는 128+128=256 MiB입니다. 두 정책의 접촉 블록 수는 모두 2개입니다.

접촉 블록은 2개입니다. 요청 범위만 읽으면 20 MiB이고, 두 블록 전체를 읽는 별도 정책에서는 256 MiB입니다.

비교할 점

실제 HDFS가 항상 256 MiB를 전송한다는 주장은 아닙니다. 비용을 계산할 때 단위와 읽기 정책을 먼저 명시하는 연습입니다.

읽을 수 있지만 복제 목표에는 못 미침

랙 R1의 노드 A와 B가 고장났습니다. 새 노드 E와 F는 충분한 용량을 갖고, 각 노드는 같은 블록의 사본을 최대 하나씩 수용한다고 가정합니다. 목표 복제 수 3을 회복할 배치와 추가 저장량을 구하세요.

  1. B1은 C만 남고 B2와 B3는 C/D가 남으므로 세 블록 모두 읽을 수 있습니다.

  2. B1의 새 사본을 E/F에, B2의 새 사본을 E에, B3의 새 사본을 F에 배치합니다.

  3. E의 추가 저장량은 128+128=256 MiB이고 F는 128+44=172 MiB입니다.

  4. 추가 저장량의 합은 428 MiB입니다. 생존 페이로드 472 MiB에 이를 더하면 복제 페이로드가 900 MiB로 회복됩니다.

E에 256 MiB, F에 172 MiB를 추가 저장하며 합계는 428 MiB입니다.

비교할 점

통신 헤더·체크섬·복구 시간·배치 정책의 추가 조건은 제외했습니다. 동일 노드에 같은 블록 사본 둘을 놓아 복제 수를 채우지 않습니다.

오해와 반례

복제 3 개면 어떤 랙 장애도 반드시 견딘다.

각 블록의 실제 배치에 따라 다르다. 세 복사본 모두 같은 장애 영역에 놓이면 그 영역 장애로 전부 사라질 수 있다.

연습 1 · 값과 상태 예측

[256, 300) MiB 범위를 읽습니다. 접촉 블록 수와 요청 길이를 구하세요. 끝점 300 MiB는 포함하나요?

힌트 1

반열린 구간은 왼쪽만 포함합니다.

힌트 2

셋째 블록의 실제 길이를 사용합니다.

풀이와 답 확인

  1. 해당 구간은 B3의 범위와 정확히 같습니다.

  2. 길이는 300−256=44 MiB이고 접촉 블록은 1개입니다.

  3. 끝점 300 MiB는 포함하지 않으므로 파일 끝을 넘지 않습니다.

접촉 블록은 1개이고 요청 길이는 44 MiB입니다. 끝점 300 MiB는 포함하지 않습니다.

흔한 오답에서 다시 생각하기

최대 블록 크기가 128 MiB이므로 요청 길이도 128 MiB이다.

최대 수용량과 실제 저장한 길이는 다릅니다. 구간의 끝에서 시작을 빼세요.

연습 2 · 오류 찾아 고치기

랙 R1 장애 후 복구량을 128 MiB×4사본=512 MiB로 계산했습니다. 어떤 블록에서 과대 계산했고 차이는 얼마인가요?

힌트 1

B3의 사본은 하나가 부족합니다.

힌트 2

B3의 실제 길이는 44 MiB입니다.

풀이와 답 확인

  1. B1의 추가 사본 2개는 256 MiB이고 B2의 추가 사본 1개는 128 MiB입니다.

  2. B3의 추가 사본 1개는 44 MiB이므로 합계는 428 MiB입니다.

  3. 512−428=84 MiB입니다. B3의 길이를 44 MiB 대신 128 MiB로 사용한 차이입니다.

B3에서 84 MiB를 과대 계산했습니다. 정확한 복구량은 428 MiB입니다.

흔한 오답에서 다시 생각하기

복제 수가 3이면 마지막 블록도 무조건 128 MiB로 저장한다.

이 모형은 패딩·메타데이터를 제외한 실제 페이로드입니다. 마지막 조각의 길이를 유지하세요.

연습 3 · 직접 만들어 보기

기본 배치에서 C와 D가 고장난 뒤, 복구 전에 B도 고장났습니다. B1/B2/B3의 생존 노드를 기록하고 전체 파일을 읽을 수 있는지 판정하세요.

힌트 1

장애 노드를 각 블록의 목록에서 지웁니다.

힌트 2

어느 한 블록이라도 사본이 0개이면 이 사본들만으로 전체 파일을 복원할 수 없습니다.

풀이와 답 확인

  1. B1의 A/B/C에서 B/C를 지우면 A가 남습니다.

  2. B2의 A/C/D에서는 A가 남습니다.

  3. B3의 B/C/D에서는 아무 노드도 남지 않습니다.

  4. 첫 256 MiB의 조각은 남지만 B3의 44 MiB가 없어 이 사본들만으로 전체 파일을 읽을 수 없습니다.

생존 노드는 B1=A, B2=A, B3=없음입니다. 전체 300 MiB 파일은 불완전합니다.

흔한 오답에서 다시 생각하기

남은 두 블록과 체크섬으로 없어진 44 MiB를 만들어 내면 된다.

체크섬은 손상 감지를 돕지만 없어진 임의 내용을 창조하지 못합니다. 별도 복구 자료의 존재를 추가로 확인해야 합니다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

각 노드가 별도의 장애 영역에 있고 한 시점의 장애 확률이 서로 독립이며 각각 0.1이라고 가정합니다. B1의 A/B/C 사본이 모두 실패할 확률을 구하세요. 이어서 세 노드가 장애 확률 0.1인 한 영역의 장애를 공유하는 별도 모형과 비교하세요.

힌트 1

독립이라는 조건이 곱셈에 필요합니다.

힌트 2

공유 영역 모형에서는 그 영역의 장애 확률 자체를 0.1로 정합니다.

풀이와 답 확인

  1. 별도의 독립 장애에서는 세 노드가 모두 실패할 확률이 0.1³=0.001입니다.

  2. 공유 영역에서는 한 장애 사건이 세 사본을 동시에 없애므로 확률은 0.1입니다.

  3. 두 값은 100배 차이지만 실제 장비 장애율을 측정한 결과는 아닙니다.

독립 장애 모형의 확률은 0.001이고 공유 영역 장애 모형은 0.1입니다.

흔한 오답에서 다시 생각하기

사본이 3개라는 숫자만으로 전멸 확률은 언제나 0.001이다.

같은 영역의 실패 사건들은 독립이 아닙니다. 실제 배치와 공통 원인을 먼저 정의하세요.

파티션 하나를 늘렸는데 기존 키 몇 개가 위치를 바꿀까요?

기본 원고의 자체 나머지 배치 h4(id)=id mod 4를 h5(id)=id mod 5로 바꿉니다. 파티션 번호가 유지되면 같은 목적지에 남는다고 가정합니다. 키 1부터 8 중 1/2/3은 번호가 유지되고 4부터 8은 이동합니다. 파티션을 한 개 늘린다는 수와 이동하는 키 수는 다릅니다. 이 단순 모형은 DynamoDB의 내부 해시나 실제 서비스의 확장 절차를 구현한 것이 아닙니다.

학생 1부터 8의 초당 요청 수를 각각 2, 3, 4, 1, 80, 3, 5, 2회로 정합니다. 레코드 크기가 같아도 h4의 파티션별 요청 부하는 3, 82, 6, 9회/초로 달라집니다. 인기 키 5의 요청 80회를 네 보조 키에 각각 20회씩 나누면 열점을 완화할 수 있습니다. 다만 학생 5의 전체 자료를 모으려면 네 키를 조회해야 하며 여러 키를 갱신할 때의 의미도 정해야 합니다. 저장 키 수, 쓰기 분산, 한 학생의 전체 조회 비용을 함께 살펴봅니다.

모델은 질문에 맞춘다

키·값 모델은 키 하나로 값을 찾는 데 초점을 두고 문서 모델은 관련 필드를 묶어 표현한다. 넓은 열 계열 모델 등 다른 형태도 있으며 NoSQL이라는 이름만으로 모두 같은 기능을 가정할 수 없다.

학생별 프로필 조회와 성적 범위 검색은 서로 다른 질문이다. 저장 형태뿐 아니라 어떤 키로 묶고 정렬하는지가 필요한 접근을 결정한다. NoSQL을 스키마나 트랜잭션이 전혀 없는 저장소라고 정의하지 않는다.

파티션은 책임을 나누고 복제는 사본을 둔다

파티셔닝은 서로 다른 데이터 부분을 나누어 맡기는 일이다. 복제는 동일 부분의 사본을 여러 곳에 둔다. 파티션마다 복제본을 두는 구성도 가능하므로 둘은 양자택일이 아니다.

DynamoDB는 partition key를 내부 해시에 이용하고 같은 키의 sort key로 범위 조회를 지원한다. 실제 물리 분할은 서비스가 관리한다. 아래 단순 나머지 함수가 서비스의 실제 배치 규칙이라는 뜻은 아니다.

균등한 개수와 균등한 부하는 다르다

키 수가 비슷해도 인기 있는 키 하나에 요청이 몰리면 열점이 생긴다. 장비를 늘려도 한 키의 처리 한계와 접근 제약이 남을 수 있다.

분할 수를 바꾸면 위치가 바뀌는 키가 있다. 이때 데이터 이동과 전환 중 조회 규칙을 함께 설계해야 한다. 단순 해시 분할은 숫자가 가까운 키들을 같은 범위에 모으지 않는다.

빠른 복사본과 나중에 처리할 쪽지는 어떤 실수를 만들까?

준비 개념과 학습 목표

준비 개념

  • 데이터베이스 갱신

학습 목표

캐시 항목이 다시 생겼다는 이유만으로 오래된 응답을 채워도 될까요?

기본 원고의 캐시 무효화 경합에 두 번째 조회를 추가합니다. 첫 조회 R1이 시작된 뒤 무효화를 관측하고, 새 조회 R2가 새 대기 항목을 만든 상황을 생각해 봅니다. 이후 오래된 R1의 응답이 도착하면 항목의 존재만 검사해서는 부족합니다. 이 자체 설계는 키별 세대 번호와 요청 토큰을 기록하고 응답 토큰이 현재 대기 토큰과 일치할 때만 값을 채웁니다. 이미 관측한 무효화를 반영하는 규칙이며, 무효화가 아직 도착하지 않은 모든 순간의 최신성을 보장하지는 않습니다.

메시지 큐에서도 식별 번호의 범위를 확인해야 합니다. RabbitMQ의 delivery tag는 전달받은 채널 안의 식별자이며 업무 중복을 막는 안정된 메시지 ID와는 계약이 다릅니다. 여러 전달을 한꺼번에 승인하면 지정 번호 이하의 미승인 전달도 포함됩니다. 그 사이에 아직 처리하지 않은 일이 있다면 잘못 승인할 수 있습니다. 아래 번호와 시간표는 자체 종이 모형이며 실제 브로커 실행 기록은 아닙니다.

먼저 확인할 개념
  • 캐시·메시지 큐

    기본 원고의 무효화 경합과 DB의 원자적 중복 기록을 요청 토큰 및 전달 승인 범위로 확장합니다.

  • 내구성·일관성·복제

    복사본이 존재한다는 사실과 최신성 판정을 구별합니다.

캐시는 원본에서 유도한 복사본이다

캐시가 적중하면 느린 원본 조회를 줄일 수 있다. 하지만 만료 시간 TTL 안에 원본이 바뀌면 복사본이 오래된 값을 줄 수 있다. TTL은 일정 시간 동안 최신 값이라는 증명이 아니다.

무효화 메시지를 써도 이전 조회 응답이 늦게 도착해 다시 오래된 값을 채우는 경합을 살펴야 한다. 연결 손실과 재접속 때의 캐시 처리 규칙까지 정해야 한다.

큐는 생산과 소비의 시점을 분리한다

메시지 큐는 생산자가 보낸 일을 소비자가 나중에 꺼내 처리하게 한다. 도착이 처리보다 빠르면 대기열이 증가하므로 큐 자체가 처리 능력을 무한히 늘리지는 않는다.

발행자 확인은 브로커의 수신 책임에 관한 것이고 소비자 승인은 전달 처리에 관한 것이다. 둘 중 하나를 다른 쪽의 업무 완료 증거로 사용하면 안 된다.

재전달을 업무와 함께 설계한다

업무를 저장한 뒤 승인 전에 연결이 끊어지면 미승인 메시지가 재전달될 수 있다. 같은 메시지를 다시 실행해도 업무 효과가 중복되지 않도록 메시지 식별자와 처리 기록을 고려한다.

같은 데이터베이스 안에서 처리 기록과 잔액 변경을 하나의 트랜잭션으로 묶는 예를 생각하자. 외부 결제나 이메일까지 그 트랜잭션에 자동 포함되지는 않으므로 별도의 중복 방지 계약이 필요하다.

  3. 일곱째 초에는 2+5=7개만 완료할 일이 있어 최대 능력 8개 중 한 개분은 사용되지 않습니다.

20개가 쌓인 뒤 7초에 0개가 됩니다. 마지막 실제 완료는 7개입니다.

흔한 오답에서 다시 생각하기

20−7×3=−1이므로 미완료는 −1개이다.

미완료 개수는 음수가 될 수 없습니다. 최대 처리 능력과 실제 완료를 구분하며 이 모형을 실제 확률 대기 시간으로 대신하지 않습니다.

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

처리 완료 5/7/8만 승인한 뒤 채널이 닫혔습니다. 6은 미승인입니다. 재전달 때 delivery tag가 새 숫자라도 어떤 기록을 기준으로 업무 효과를 판정해야 하나요?

  2. 새 전달 번호가 아니라 안정된 업무 메시지 ID를 조회합니다.

  3. 업무 효과와 기록이 이미 원자적으로 저장되었다면 재실행을 건너뛰고, 아직 없으면 원자적으로 처리합니다.
