소단원 7.1

routing·middleware

같은 URL에 GET과 POST가 오면 같은 일을 해야 할까?

준비 개념과 학습 목표

준비 개념

  • HTTP 요청과 응답

  • 함수 호출 순서

  • route는 메서드·경로에 맞춘 처리 규칙, middleware는 요청 중간 처리 함수다. next는 다음 처리기로 흐름을 넘긴다.

학습 목표

  • 메서드와 경로로 담당 함수를 고른다.

  • middleware의 진행과 종료를 추적한다.

접수 창구에서 번호표를 받았다고 책 수정까지 허락받은 걸까?

번호표 발급, 신원 확인, 책 수정 권한 확인, 저장은 서로 다른 단계다. 여기서는 Express의 등록 순서 모형을 사용한다. request-id → auth → parse → validate → permission → save 순서이며 각 실패는 응답을 끝내고 뒤 단계를 호출하지 않는다고 정한다. 모든 요청이 JSON 객체를 보내는 PUT /books/7 사례다.

auth 성공은 이 책을 수정할 권한까지 뜻하지 않는다. 파싱 단계가 본문 객체를 만들고, validate는 title/pages 규칙을 검사하며, permission이 소유자를 확인한다. 이 순서와 상태코드는 연습용 API 계약이다. 실제 서버·인증 장치·HTTP 요청을 실행한 결과가 아니다.

먼저 확인할 개념
  • 요청과 응답의 경계

    하나의 요청이 어느 응답에서 종료되는지 먼저 찾는다.

  • 네트워크 실패와 응답 처리

    서버가 보낸 결과와 클라이언트가 결과를 읽었는지의 차이를 구별한다.

routing은 요청의 담당자를 고른다

routing은 요청의 메서드와 경로를 보고 처리 함수를 연결하는 일이다. GET /books/7은 책 조회, POST /books는 새 책 생성처럼 계약을 나눈다. Express의 /books/:id에서 id는 경로에서 추출하는 값이고 /books/7?lang=ko의 lang은 별도 질의 문자열이다.

경로 변수는 입력이다. 문자열 "7"을 받았다는 사실이 정수 변환·존재·접근 권한까지 보장하지 않는다. 먼저 모양과 범위를 검증하고 실제 자원을 찾는 단계를 구분한다. 라우트 등록만으로 인증이나 권한 검사가 생기지 않는다.

middleware는 공통 처리의 연결이다

middleware는 요청·응답 객체와 다음 처리로 넘기는 함수를 받는다. 요청 식별자 생성, 인증, 입력 파싱처럼 여러 라우트가 공유하는 일을 연결한다. 여기서는 Express의 등록 순서에 따라 실행되는 모형을 쓴다. 다른 프레임워크의 감싸는 호출 구조와 자동으로 같다고 가정하지 않는다.

응답을 끝냈다면 더 진행하지 않는 분기를 만들고, 응답을 끝내지 않았다면 next로 다음 처리에 넘긴다. 둘 다 하지 않으면 요청이 응답 없이 대기할 수 있다. next 자체가 성공 응답을 보내는 것은 아니다.

실행 순서를 사건표로 읽는다

이 예제는 request-id→auth→route 순서다. auth는 자격이 있으면 next를 호출하고 없으면 401 응답을 끝낸다는 자체 계약이다. HTTP 401에는 적용 가능한 인증 challenge인 WWW-Authenticate 헤더도 보내야 한다. 식별자는 어느 분기의 로그도 묶어 준다.

로그 middleware가 진입 때 남기는 기록은 최종 성공 여부와 다르다. 최종 상태와 소요 시간은 응답 완료 시점에 별도로 기록하도록 설계한다. 이 수업의 사건표는 서버를 실행한 로그가 아니라 손으로 적은 논리 추적이다.

중간 과정을 따라가는 예제

GET /books/7?lang=ko가 위 세 처리로 들어온다. 인증 성공과 실패 각각의 호출 순서를 적어라.

  1. request-id가 r1을 부여하고 next한다.

  2. 성공에서는 auth가 통과시키고 route가 id="7",lang="ko"를 읽어 200 응답을 종료한다.

  3. 실패에서는 auth가 401과 WWW-Authenticate를 보내 종료하며 route는 호출하지 않는다.

성공은 request-id/auth/route, 실패는 request-id/auth에서 종료한다.

조건을 바꾸어 비교하기

인증만 하면 남의 책도 고칠 수 있다는 오류

인증된 사용자 민수가 pages=12,title="봄"을 보내지만 책 7의 소유자는 수아다. 표의 순서를 유지한다.

  1. auth와 parse, validate까지 통과한다.

  2. permission에서 소유자 조건이 맞지 않는다.

  3. 403 응답을 끝내며 save를 호출하지 않는다.

request-id/auth/parse/validate/permission에서 종료한다. 책 7의 소유자는 바뀌지 않는다.

비교할 점

입력 타입이 맞는지와 누가 바꿀 수 있는지는 별도 질문이다.

처리를 넘긴 뒤에도 현재 함수는 계속될 수 있다

보통 함수 문장으로 next(); audit("after")를 썼다. next가 뒤의 동기 handler를 호출하고 그 handler가 응답을 끝낸 뒤 반환하며, 예외는 없다고 정했다.

  1. 현재 함수가 next를 호출한다.

  2. 뒤 handler가 응답을 끝내고 호출자에게 반환한다.

  3. 현재 함수의 audit("after") 문장은 여전히 실행된다. 이 로그는 두 번째 응답을 보내는 문장이 아니다.

응답 종료가 모든 JavaScript 함수 문장을 자동으로 중단시키지는 않는다. 해당 분기의 실행을 끝내려면 return 등 제어 흐름도 설계한다.

REST와 JSON

JSON을 주고받으면 모두 REST일까?

준비 개념과 학습 목표

준비 개념

  • HTTP 메서드

  • 객체와 배열

  • HTTP는 요청과 응답의 통신 규칙이며 JSON은 값을 문자로 표현하는 형식이다. URI는 자원의 식별자이고 멱등성은 반복의 의도된 최종 효과가 같은 성질이다.

학습 목표

  • 자원과 표현을 구별한다.

  • JSON 문법과 API 의미 계약을 구별한다.

신청 완료 화면을 못 봤다면 신청이 없었던 걸까?

생성 요청을 서버가 저장한 뒤 응답이 끊길 수 있다. 화면에서 결과를 못 읽었다는 사실은 생성이 없었다는 증거가 아니다. 아래 사건표는 첫 저장이 완료됐다고 아는 관찰자와 결과를 못 받은 클라이언트의 지식을 나눈다. 통신 실험을 실제 수행하지 않았다.

별도 중복 키가 없는 생성 POST와 같은 표현으로 교체하는 PUT을 비교한다. JSON 표현 형식을 쓴다는 사실만으로 전체 REST 제약이나 자동 중복 방지를 얻지 않는다. 중복 키는 도입한다면 범위·본문 일치·보관 기간·동시 요청 처리 규칙까지 별도 계약이 필요하다.

먼저 확인할 개념
  • 비동기 실패를 해석하기

    abort와 응답 읽기 실패를 서버 처리 취소로 오해하지 않는다.

  • 메서드와 HTTP 응답

    표현 조회와 자원 변경 요청을 서로 다른 의미로 읽는다.

자원은 식별하고 표현은 전달한다

/books/7은 자원을 식별하는 URI이고 {"id":7,"title":"봄"}은 그 자원의 한 JSON 표현이다. GET은 현재 표현을 조회하고 POST는 대상 자원의 계약에 맞는 처리를 요청한다. 여기서는 POST /books가 새 책을 만든다는 자체 API 계약이다.

REST는 클라이언트·서버 분리, stateless, 캐시, 계층과 uniform interface 등의 제약을 갖는 아키텍처 스타일이다. JSON은 표현 형식 하나다. 이 단원의 작은 HTTP JSON API는 핵심 원리 연습이며 hypermedia를 포함한 전체 REST 준수를 증명한 것은 아니다.

메서드의 효과와 재요청

PUT /books/7에 같은 전체 표현을 반복 적용하면 의도한 최종 자원 상태가 한 번 적용과 같도록 설계한다. 이를 멱등성이라 한다. 반복 요청마다 접근 로그가 추가되어도 자원에 대한 의도 효과와 구별한다. 응답 코드까지 매번 같아야 한다는 뜻은 아니다.

POST 생성은 자동 멱등성이 없다. 응답을 놓친 뒤 같은 생성 요청을 다시 보내면 두 책을 만들 수 있다. 별도 요청 키와 중복 처리 계약이 없다면 무조건 재시도하지 않는다. GET으로 삭제나 결제를 요청하는 계약은 안전한 조회 메서드의 의미를 깨뜨린다.

JSON은 문법, 스키마는 의미다

JSON 값은 객체·배열·문자열·숫자·true·false·null이다. 객체 이름은 큰따옴표 문자열이며 undefined와 NaN은 JSON 값이 아니다. 객체의 중복 이름은 파서마다 다르게 처리할 수 있으므로 상호운용 가능한 API에서는 피하고 중복 처리 정책을 명시한다.

{"pages":"12"}는 문법상 JSON이지만 pages를 1..1000 정수로 받는 이 API에서는 타입이 맞지 않는다. {"pages":12}는 타입·범위 검사에 통과한다. JSON 파싱 성공, 필드 검증 성공, 권한 승인, 실제 저장 성공은 각각 다른 단계다.

계약이 실제 구현됐는지 필요

PUT의 의도 상태가 같아도 두 접근 로그나 서로 다른 응답 코드가 생길 수 있다. 마지막 행은 이 수업이 설계한 추가 계약이며 HTTP가 모든 POST에 자동 제공하는 기능이 아니다.

중간 과정을 따라가는 예제

비어 있는 저장소에서 POST /books를 두 번 보내 각각 새 id를 만든다. 별도로 PUT /books/7의 같은 표현을 두 번 적용한다.

  1. POST 첫 성공은 id7을 만들고 201 Location:/books/7을 보낸다고 정한다.

  2. 중복키 계약이 없는 두 번째 POST는 id8을 만들어 책이2개다.

  3. PUT 두 번은 id7의 같은 표현으로 교체하여 해당 자원의 최종 상태가 같으며 두 접근로그가 있어도 멱등효과와 모순되지 않는다.

POST는 예제에서2개 생성, 동일 PUT의 의도한 최종 id7 상태는1회와 같다.

조건을 바꾸어 비교하기

DELETE의 다른 응답과 같은 최종 효과

책 7이 존재했다. 첫 DELETE /books/7은 제거하고 204, 다음 같은 DELETE는 현재 없다는 자체 정책으로 404를 응답한다. 두 처리 모두 다른 책을 바꾸지 않는다.

  1. 첫 요청 뒤 책 7은 없다.

  2. 두 번째 뒤에도 책 7은 없다.

  3. 204와 404의 차이는 이 서버가 정한 응답 정책이다.

의도한 최종 상태는 둘 다 책 7 없음이어서 다른 응답 코드만으로 멱등성이 깨졌다고 할 수 없다.

비교할 점

응답 문자열 동일성과 자원 효과 동일성을 구별한다.

JSON 문법과 정수 계약을 따로 검사한다

pages는 1..1000 정수다. JSON 값 12.0, "12", null, 0, 12.5를 값의 수학적 정수 여부로 검증하는 계약을 둔다. 문자열을 숫자로 자동 변환하지 않는다.

  1. 다섯 값 모두 JSON 문법에 속한다.

  2. 12.0은 숫자 값 12로 정수 조건을 만족한다.

  3. 문자열 "12"와 null은 타입 실패, 0은 범위 실패, 12.5는 정수 조건 실패다.

이 계약의 통과는 12.0뿐이다. 문법 파싱 성공을 필드 통과와 구별한다.

비교할 점

소수점 표기가 보인다는 이유만으로 값 12를 반드시 비정수로 분류하지 않는다. 어떤 정수 검증 계약인지 명시한다.

종이와 본문으로 직접 해보기

{"pages":"12"}, {"pages":0}, {"pages":12}를 자체 pages 계약으로 분류하라.

힌트 보기

풀이 보기

오해와 반례

JSON API는 모두 REST이고 멱등 요청은 같은 응답을 낸다.

JSON은 형식일 뿐 REST 전체 제약을 뜻하지 않는다. 멱등성은 의도한 서버 효과의 동일성이므로 응답이나 로그까지 동일할 필요는 없다.

오류 번호를 알면 무엇부터 고쳐야 하는지도 알 수 있을까?

같은 실패라도 입력 문법, 필드 의미, 권한, 현재 버전, 저장 장치의 단계가 다르다. 이 자체 API는 400/422/403/409/412/500을 아래 계약으로 구분한다. 모든 API가 같은 세부 분류를 쓴다는 주장은 아니다. 클라이언트에는 고칠 수 있는 설명과 비민감 요청 식별자를 준다.

version 필드 검사와 If-Match 헤더 검사는 서로 다른 계약이다. 이 표는 일반 검사와 권한을 통과한 기존 책의 수정에서 비교하며, 이미 처리된 재요청의 예외나 다른 헤더 조건은 제외한다. 시간도 같은 가상 서버 시계로만 뺀다. 실제 HTTP·저장·로그 시스템의 실행 증거는 아니다.

경계에서 형태와 의미를 검증한다

서버는 클라이언트의 검증을 믿지 않고 입력 크기와 미디어 타입을 확인하고 안전하게 파싱한 뒤 허용 필드·타입·범위를 검증한다. 이 API에서는 JSON 객체 title은 빈 문자열이 아니고 pages는 1..1000 정수라는 계약을 둔다. 입력은 저장 전에 검증한다.

입력 검증과 인증·권한·출력 인코딩은 별개다. pages가 유효해도 다른 사람의 책을 수정할 권한을 주지 않는다. 날짜 두 개가 각각 유효해도 시작이 종료 뒤인 경우처럼 필드 간 의미 조건도 검사해야 한다.

오류 종류를 상태코드로 전달한다

이 자체 계약은 잘못된 JSON 문법에400, 문법은 맞지만 pages범위 실패에422를 쓴다. 없는 책 조회는404, 현재 버전 충돌은409, 예상치 못한 저장 장애는500이다. 실제 API가 입력 오류에400을 일괄 쓰는 정책도 있으므로 문서화된 계약을 읽는다.

401은 유효한 인증 정보가 없다는 뜻이며 challenge 헤더가 필요하다. 403은 이해했지만 거절한 요청이며 항상 로그인 문제만을 뜻하지 않는다. 클라이언트에는 수정 가능한 오류와 요청 식별자를 주고 내부 스택·연결 문자열을 그대로 보내지 않는다.

요청과 결과를 연결하는 로그

로그에는 요청 식별자, 시각, 메서드, 정규화한 경로, 결과 코드, 처리 시간과 실패 범주를 기록한다. 토큰·비밀번호·민감한 본문을 통째로 기록하는 대신 필요한 요약을 남긴다. 사용자 입력의 줄바꿈도 인코딩하거나 정리하여 가짜 로그 줄이 생기지 않게 한다.

로그는 진단 증거이며 성공 응답 자체나 완벽한 감사 증명이 아니다. 요청 식별자는 여러 내부 사건을 연결하지만 접근 제한·보존 정책·실제 기록 실패 처리도 설계해야 한다. 여기서는 가상 시간표이며 서버 측정 결과가 아니다.

책 7의 현재 version 3/strong ETag "v3"다. 모두 같은 서버 시계의 가상 사건이며 일반 검사와 권한은 별도 명시한 경우에 통과한다. A: 자격 없음과 깨진 JSON, B: 자격 있음/title="봄"/pages=0, C: 유효 필드·권한·본문 version 3/If-Match:"v2", D: 유효 변경 요청의 저장 완료와 200 응답 생성 뒤 클라이언트가 응답을 못 읽음. 등록 순서와 401/422/412 계약으로 종료 단계·저장 여부·클라이언트 다음 행동을 적어라. D가 중복키 없는 생성 POST였다면 무조건 재시도의 위험도 비교하라. A의 시작 100/끝 106 ms, B의 시작 200/끝 209 ms로 완료 차이를 계산하고 비밀 없는 진단 필드를 제안하라.

힌트 1

A는 auth에서 종료한다. B는 필드 범위, C는 header 조건 실패다. D는 서버 관찰과 클라이언트 지식이 다르다.

힌트 2

같은 서버 시계만 빼고 token/password는 요청 식별자와 구별한다.

풀이와 답 확인

  1. A는 request-id/auth에서 401과 challenge로 종료하고 parse/save를 호출하지 않는다. B는 validate에서 422로 종료하며 save하지 않는다.

  2. C는 이 사례의 If-Match 조건 실패 412이며 책 7을 덮어쓰지 않는다. 현재 표현·태그 재조회와 변경 병합을 안내한다.

  3. D는 관찰자에게 저장 성공이 알려졌지만 응답을 못 읽은 클라이언트는 그 관찰 없이 저장 성공 여부를 확정하지 못한다. 같은 PUT의 의도 효과와 중복키 없는 생성 POST의 중복 위험을 나눈다.

  4. A의 완료 차이는 6 ms, B의 완료 차이는 9 ms다. 실제 HTTP 성능 측정 결과로 표시하지 않는다.

  5. request-id/method/정규화 경로/status/실패 범주/완료 관찰이 있는 같은 시계의 차이를 요약하고 비밀·민감한 본문 원문·가짜 개행을 제외하거나 안전하게 인코딩한다.

A: 401/저장 없음/6 ms, B: 422/저장 없음/9 ms, C: 412/덮어쓰기 없음, D: 서버 저장 완료와 클라이언트 결과 불명을 분리한다. 생성 POST의 재시도는 별도 중복 방지 계약 없으면 추가 생성을 일으킬 수 있다.

해결한 뒤 점검할 것

  • 도달하지 않은 검사에 오류 판정을 붙이지 않는다.

  • 입력·권한·조건부 변경·저장·응답 읽기를 다른 단계로 적는다.

  • 재요청의 의도 효과와 추가 생성 위험을 구별한다.

  • 가상 시간 차이와 실제 측정 증거를 구분한다.

  • 진단 식별자와 인증 비밀을 구별한다.
