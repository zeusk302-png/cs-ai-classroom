소단원 10.1

XSS·CSRF

로그인한 친구의 브라우저가 왜 친구 뜻과 다른 일을 할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • HTML 텍스트와 태그

  • 쿠키와 로그인 세션

학습 목표

  • 데이터가 실행 문맥에 들어가는 XSS 경계를 설명한다.

  • 쿠키 인증 요청과 사용자 의도를 구별해 CSRF 방어를 고른다.

데이터와 실행의 경계

XSS는 신뢰하지 않은 내용이 페이지의 실행 가능한 문맥으로 해석되는 문제다. 댓글에 적힌 문장을 보여 주려 했는데 브라우저가 태그나 스크립트로 해석하면 작성자의 데이터가 페이지 권한으로 동작할 수 있다. 저장형·반사형·DOM 기반이라는 이름보다 입력이 어디에서 어떤 해석기로 가는지 먼저 추적한다.

일반 div의 textContent에 원문을 넣으면 텍스트 노드로 다뤄진다. innerHTML로 HTML 문법을 해석시키는 일과 다르다. HTML 본문·속성·URL·JavaScript에는 서로 다른 문맥 규칙이 있으므로 한 가지 수동 치환을 모든 위치에 적용하지 않는다. script 요소의 textContent까지 안전한 일반 텍스트 위치로 생각하면 안 된다.

인증과 의도는 다르다

CSRF는 브라우저가 갖고 있는 인증 정보를 이용해 사용자가 의도하지 않은 상태 변경 요청을 보내게 하는 문제다. 피해 페이지 안에서 공격 코드를 실행시키는 XSS와 출발점이 다르지만 같은 서비스에 함께 존재할 수 있다. 로그인 쿠키가 붙었다는 사실만으로 사용자가 그 요청을 승인했다고 결론내리지 않는다.

유지 관리되는 프레임워크의 CSRF 보호를 설정하고 서버가 세션에 결합한 예측 불가능한 토큰을 검증하게 한다. 토큰 누락·불일치는 변경 전에 거절한다. 토큰은 권한 검사를 대신하지 않으며 GET으로 상태를 바꾸는 설계도 고쳐야 한다. 실서비스 토큰을 URL·로그에 기록하지 않는다.

서로 다른 방어를 연결하기

댓글 표시에는 문맥에 맞는 텍스트 처리, 계정 변경에는 CSRF 및 인증·권한 검사가 필요하다. 방어 이름만 체크하는 대신 표시 경로와 변경 경로를 별도로 그려야 한다. 아래는 공격 사이트를 만들지 않고 문자열과 가상의 서버 규칙을 종이에서 따라가는 활동이다.

이 수업은 일반 div 텍스트와 세션별 토큰 검증이라는 제한된 모형이다. 실제 서비스에는 쿠키 SameSite, Origin 검사, CSP 등 다른 조건도 존재한다. CSRF 토큰이 있다고 XSS가 없어지는 것은 아니며 실제 보안 시험도 수행하지 않았다.

중간 과정을 따라가는 예제

문자열 <b>안녕</b>를 일반 div의 textContent로 표시한다. 가상 변경 API는 로그인과 유효 토큰을 모두 요구한다. 로그인은 참이고 토큰이 없으면 각각 어떻게 되나?

  1. div에는 원문을 텍스트로 넣으므로 b 태그를 생성하지 않는다.

  2. 변경 허용 조건 참 AND 거짓은 거짓이다.

  3. 변경 전에 거절하고 화면 표시와 서버 변경의 판정을 따로 기록한다.

화면에는 <b>안녕</b>라는 글자 자체가 보이고 변경 요청은 거절된다.

종이와 본문으로 직접 해보기

같은 세션의 유효 토큰은 있지만 해당 자료의 수정 권한이 없을 때 승인 가능한가? 일반 div에 2 < 3을 textContent로 넣으면?

힌트 보기

토큰 검증 뒤에도 권한 검사가 남는다. 텍스트 위치는 HTML 파싱과 구별한다.

풀이 보기

수정 권한이 없어 거절해야 한다. div는 2 < 3이라는 텍스트를 보여 준다. 미리 &lt;로 바꿀 필요가 없다.

오해와 반례

CSRF 토큰을 달면 댓글 XSS도 해결된다.

토큰은 상태 변경 요청의 위조 방어다. 댓글이 실행 가능한 문맥으로 들어가는 경로는 별도이고 XSS가 토큰을 읽을 수도 있다.

소단원 10.2

입력검증과 injection

숫자 범위를 검사하는 일과 명령을 데이터로 다루는 일은 왜 둘 다 필요할까?

준비 개념과 학습 목표

준비 개념

  • 문자열 연결

  • SQL의 조건식

학습 목표

  • 허용 입력 범위와 명령/데이터 분리를 구별한다.

  • 값 바인딩과 동적 식별자 선택의 경계를 설명한다.

입력의 의미를 검사하기

입력검증은 서비스가 허용하는 값인지 확인하는 일이다. 수량이 정수 1..20이어야 하면 0·21·소수·누락은 각각 이유를 갖고 거절한다. 클라이언트 화면 검사는 사용자를 돕지만 직접 요청을 보내는 클라이언트도 있으므로 서버에서 동일한 계약을 확인한다.

문자열이 허용되는 자유 입력이라고 해서 명령 문법에 그대로 이어 붙여도 된다는 뜻은 아니다. 유효한 사람 이름에도 작은따옴표가 있을 수 있다. 모든 문장 부호를 삭제하면 정상 데이터를 망가뜨리고 다른 문맥의 공격도 놓칠 수 있다.

질의 구조를 먼저 정하기

SQL 값을 바인딩하는 API는 질의 구조를 미리 정한 뒤 입력을 값으로 전달한다. 물음표 ?를 매개변수로 사용하는 가상의 질의 SELECT name FROM users WHERE name = ?에서 입력은 이름 값 하나다. 실제 드라이버의 placeholder 문법은 다를 수 있으므로 이 문장은 실행 코드가 아닌 계약 표시다.

열 이름이나 정렬 방향은 값 placeholder로 임의 대체할 수 있다고 가정하지 않는다. 사용자 선택을 서버가 미리 정의한 age/name 같은 식별자와 ASC/DESC에 대응시키는 방식이 필요하다. 파라미터 바인딩을 한 뒤 다시 문자열 SQL로 재구성하면 처음의 경계를 잃는다.

다른 경계도 남는다

SQL injection 방어가 XSS·권한 누락·업무 오류까지 자동 해결하지는 않는다. 쿼리 결과를 HTML로 표시할 때 출력 문맥을 다시 확인한다. DB 계정도 필요한 권한만 가져야 실수의 영향이 줄어든다.

아래 작은 표는 실제 DB 접속 없이 값 비교를 수행하는 교육 모델이다. 이름은 문자열 전체 일치로 비교하며 SQL 패턴 매칭이나 대소문자 정규화는 생략한다. 안전성의 전부를 증명하는 시험이 아니라 명령과 값의 차이를 관찰한다.

중간 과정을 따라가는 예제

교육 표의 이름은 [민수,지아]다. 고정된 name = ? 조건의 값으로 민수를 바인딩하면? 이어 문자 OR가 포함된 원문 민수 OR 지아를 값 하나로 바인딩하면?

  1. 첫 값 민수는 첫 행과 전체 일치한다.

  2. 두 번째 입력 전체 문자열은 두 행 어느 이름과도 같지 않다.

  3. OR 글자가 값 내부에 있다고 질의의 OR 연산자로 바뀌지 않는다.

첫 질의는 민수 1행, 두 번째는 0행이다.

종이와 본문으로 직접 해보기

수량은 정수 1..20이고 정렬 선택은 newest 또는 name만 허용한다. 요청 (수량21,정렬name)과 (수량2,정렬unknown)을 판정하자.

힌트 보기

숫자 범위와 정렬 allow-list를 각각 검사한다.

풀이 보기

첫 요청은 수량 범위 밖, 두 번째는 정렬 목록 밖으로 거절한다. 입력을 임의 SQL에 이어 붙여 해결하지 않는다.

오해와 반례

입력검증을 통과하면 SQL을 문자열로 연결해도 안전하다.

업무상 유효한 값에도 SQL 특수 문자가 존재한다. 값 바인딩을 유지하며 식별자 선택은 별도 allow-list로 제한한다.

답과 이유 보기

그렇게 가정하면 안 된다.

한 단계 더

허용 수량 0/1/20/21과 이름 빈 문자열을 표로 적자. 숫자 경계와 이름의 업무 규칙을 정한 뒤 SQL 값 전달 단계는 그 규칙과 별도로 유지한다.

소단원 10.3

CORS·비밀관리

브라우저에서 읽지 못한 응답은 서버에 요청조차 안 갔다는 뜻일까?

준비 개념과 학습 목표

준비 개념

  • HTTP 요청과 응답

  • URL의 scheme·host·port

학습 목표

  • CORS의 브라우저 응답 접근과 서버 인증을 구별한다.

  • 공개 클라이언트에 들어간 비밀의 노출과 폐기 절차를 설명한다.

origin과 응답 접근

origin은 scheme·host·port의 조합이다. 경로가 다르다고 다른 origin이 되는 것은 아니지만 같은 host라도 포트나 scheme이 다르면 다를 수 있다. CORS는 서버의 헤더를 근거로 브라우저가 다른 origin 응답을 페이지 코드에 공개할지 결정하는 규칙이다.

일부 요청은 preflight로 실제 요청 전 허용 조건을 묻지만 모든 요청이 그렇지는 않다. 단순 요청은 먼저 전달되고 응답 읽기만 막힐 수 있다. 따라서 CORS 오류를 서버의 부작용 부재나 인증·CSRF 방어의 증명으로 사용하지 않는다. 브라우저 밖의 클라이언트는 별도 서버 인증이 필요하다.

자격 증명의 조건

자격 증명을 포함하는 cross-origin fetch에는 서버가 정확한 허용 origin과 Access-Control-Allow-Credentials: true를 제공해야 응답 접근 조건을 만족한다. Allow-Origin: *는 이 경우 사용할 수 없다. 브라우저의 쿠키 정책이 추가로 전송을 제한할 수 있어 헤더 둘만 맞다고 모든 환경의 로그인 성공이 보장되지는 않는다.

허용 목록의 origin을 정확하게 비교하고 응답이 origin별로 달라지면 캐시의 Vary: Origin도 고려한다. 임의 요청 Origin을 그대로 반사해 모든 신뢰를 주지 않는다. 이 단원 표는 simple GET의 응답 공개 조건만 따로 계산한다.

클라이언트 공개물과 자격 증명

웹 페이지의 JavaScript 번들이나 모바일 앱에 배포한 문자열은 사용자가 읽을 수 있다고 보고 설계한다. 환경 변수 이름이나 난독화는 클라이언트에 이미 들어간 서버 비밀을 비공개로 만들지 않는다. 공개 식별자는 공개 식별자로, 실제 권한 있는 비밀은 제한된 서버에서 사용하도록 나눈다.

비밀이 유출되면 저장소에서 글자를 지우는 것만으로 이미 복사된 키는 폐기되지 않는다. 공급자의 폐기·회전과 권한 축소, 사용 이력 확인이 필요하다. 아래 K1/K2는 실제 키가 아닌 상태표의 이름이며 계정이나 비밀을 만들지 않는다.

중간 과정을 따라가는 예제

페이지 origin은 https://learn.example다. 쿠키 포함 simple GET의 응답 A는 Allow-Origin:*와 Allow-Credentials:true, B는 Allow-Origin:https://learn.example와 Allow-Credentials:true다. 다른 쿠키 정책은 만족했다고 가정하고 페이지의 읽기를 판정하자.

  1. A의 wildcard는 자격 증명 요청 응답 공개 조건과 맞지 않는다.

  2. B는 명시 origin이 페이지와 같고 자격 증명 허용이 참이다.

  3. 이미 전달된 simple GET 여부와 응답 읽기 여부를 구별한다.

A 응답은 페이지 읽기 차단, B는 이 CORS 조건에서 읽기 허용. 서버 인증 성공이나 부작용 부재를 뜻하지 않는다.

종이와 본문으로 직접 해보기

공개 번들에 있던 K1을 파일에서 지우고 K2로 바꿨지만 서비스는 K1도 여전히 유효하게 둔다. 누군가 복사한 K1을 못 쓰게 된 것인가?

힌트 보기

파일 상태와 서비스의 키 유효 상태를 두 열로 적는다.

풀이 보기

아니다. 서비스에서 K1을 폐기·만료시키기 전까지 복사본이 사용될 수 있다. K2의 안전한 전달과 기존 의존 작업 확인도 필요하다.

오해와 반례

CORS를 닫아 놓으면 서버 API의 인증은 필요 없다.

CORS는 브라우저 페이지의 응답 접근 규칙이다. 다른 클라이언트 요청은 서버에서 인증·권한을 검증해야 한다.

자기점검

https://a.example/x와 /y는 같은 origin인가?

답과 이유 보기

같다.

경로는 origin 구성요소가 아니다.

https://a.example:443과 https://a.example:8443은?

답과 이유 보기

다르다.

유효 포트가 다르다.

클라이언트 번들 환경 변수는 서버 비밀 보관소인가?

답과 이유 보기

아니다.

배포 결과에 포함된 값은 수신자가 볼 수 있다.
