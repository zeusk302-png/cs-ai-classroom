소단원 10.1

XSS·CSRF

로그인한 친구의 브라우저가 왜 친구 뜻과 다른 일을 할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • HTML 텍스트와 태그

  • 쿠키와 로그인 세션

학습 목표

  • 데이터가 실행 문맥에 들어가는 XSS 경계를 설명한다.

  • 쿠키 인증 요청과 사용자 의도를 구별해 CSRF 방어를 고른다.

태그를 글자로 보여 주는 창과 태그를 작동시키는 창은 같은 창일까?

자체 댓글 입력은 <em>반가워</em>다. 일반 div에 원문을 textContent로 넣는 경로와 HTML 파서로 넣는 경로를 구별한다. 서비스가 서식 있는 HTML을 의도적으로 허용한다면 텍스트 표시와 다른 요구이며, 허용 요소 정책과 유지되는 sanitizer를 사용해야 한다.

계정 변경 요청은 또 다른 경계다. 아래 자체 서버 조건은 유효 세션 AND 그 세션에 맞는 토큰 AND 해당 작업 권한이다. 표시용 A토큰/B토큰은 실제 보안 토큰이 아니다. 모든 예는 종이 해석이며 실제 DOM·sanitizer·공격·HTTP 코드는 실행하지 않았다.

  • 일반 요소의 텍스트 표시

    텍스트 내용과 HTML 구조가 어느 위치에서 나뉘는지 본다.

  • 유효 로그인과 자원별 권한

    토큰 일치만으로 변경 작업 권한을 생략하지 않는다.

데이터와 실행의 경계

XSS는 신뢰하지 않은 내용이 페이지의 실행 가능한 문맥으로 해석되는 문제다. 댓글에 적힌 문장을 보여 주려 했는데 브라우저가 태그나 스크립트로 해석하면 작성자의 데이터가 페이지 권한으로 동작할 수 있다. 저장형·반사형·DOM 기반이라는 이름보다 입력이 어디에서 어떤 해석기로 가는지 먼저 추적한다.

일반 div의 textContent에 원문을 넣으면 텍스트 노드로 다뤄진다. innerHTML로 HTML 문법을 해석시키는 일과 다르다. HTML 본문·속성·URL·JavaScript에는 서로 다른 문맥 규칙이 있으므로 한 가지 수동 치환을 모든 위치에 적용하지 않는다. script 요소의 textContent까지 안전한 일반 텍스트 위치로 생각하면 안 된다.

인증과 의도는 다르다

CSRF는 브라우저가 갖고 있는 인증 정보를 이용해 사용자가 의도하지 않은 상태 변경 요청을 보내게 하는 문제다. 피해 페이지 안에서 공격 코드를 실행시키는 XSS와 출발점이 다르지만 같은 서비스에 함께 존재할 수 있다. 로그인 쿠키가 붙었다는 사실만으로 사용자가 그 요청을 승인했다고 결론내리지 않는다.

유지 관리되는 프레임워크의 CSRF 보호를 설정하고 서버가 세션에 결합한 예측 불가능한 토큰을 검증하게 한다. 토큰 누락·불일치는 변경 전에 거절한다. 토큰은 권한 검사를 대신하지 않으며 GET으로 상태를 바꾸는 설계도 고쳐야 한다. 실서비스 토큰을 URL·로그에 기록하지 않는다.

서로 다른 방어를 연결하기

댓글 표시에는 문맥에 맞는 텍스트 처리, 계정 변경에는 CSRF 및 인증·권한 검사가 필요하다. 방어 이름만 체크하는 대신 표시 경로와 변경 경로를 별도로 그려야 한다. 아래는 공격 사이트를 만들지 않고 문자열과 가상의 서버 규칙을 종이에서 따라가는 활동이다.

이 수업은 일반 div 텍스트와 세션별 토큰 검증이라는 제한된 모형이다. 실제 서비스에는 쿠키 SameSite, Origin 검사, CSP 등 다른 조건도 존재한다. CSRF 토큰이 있다고 XSS가 없어지는 것은 아니며 실제 보안 시험도 수행하지 않았다.

sanitizer 행은 실제 도구 출력이 아니라 별도 확인이 필요한 경로다. 토큰은 현재 세션의 서버 값과 비교하며 다른 사용자에게 맞는 토큰을 이 세션에서 허용하지 않는다. XSS 없는 전체 사이트라는 주장을 이 표로 증명하지 않는다.

중간 과정을 따라가는 예제

문자열 <b>안녕</b>를 일반 div의 textContent로 표시한다. 가상 변경 API는 로그인과 유효 토큰을 모두 요구한다. 로그인은 참이고 토큰이 없으면 각각 어떻게 되나?

  1. div에는 원문을 텍스트로 넣으므로 b 태그를 생성하지 않는다.

  2. 변경 허용 조건 참 AND 거짓은 거짓이다.

  3. 변경 전에 거절하고 화면 표시와 서버 변경의 판정을 따로 기록한다.

화면에는 <b>안녕</b>라는 글자 자체가 보이고 변경 요청은 거절된다.

조건을 바꾸어 비교하기

미리 HTML 치환하면 텍스트 요구도 바뀐다

사용자 원문은 2 < 3이다. 개발자가 이를 2 &lt; 3으로 먼저 바꾼 뒤 일반 div의 textContent에 넣는다고 가정한다. 원문을 직접 넣는 경로와 표시 글자를 비교하라.

  1. textContent는 HTML 엔티티를 파싱해 다시 원문으로 바꾸는 경로가 아니다.

  2. 직접 원문을 넣으면 2 < 3이라는 글자다.

  3. 미리 치환한 문자열을 넣으면 2 &lt; 3이라는 글자가 된다.

일반 텍스트 sink의 계약에 맞게 원문을 넣고 수동 HTML 치환을 덧붙이지 않는다. 실제 브라우저 렌더 시험은 미수행이다.

비교할 점

인코딩을 한 번 더 하면 항상 같은 화면에 더 안전하다는 추정을 비교한다.

토큰이 맞아도 권한은 남는다

A세션은 민이고 현재 세션 토큰 A토큰이 맞는다. 문서 소유자는 서이며 민에게 수정 권한은 없다. 변경 요청의 세 조건을 계산하라.

  1. 세션 유효는 True다.

  2. 세션 토큰 일치는 True다.

  3. 수정 권한은 False라 AND 결과는 False다.

변경 전에 거부한다. 세션 토큰 검사는 자원 소유 관계를 만들지 않는다.

비교할 점

요청 위조 방어와 개별 작업 허용을 서로 다른 조건으로 둔다.

종이와 본문으로 직접 해보기

힌트 보기

토큰 검증 뒤에도 권한 검사가 남는다. 텍스트 위치는 HTML 파싱과 구별한다.

풀이 보기

수정 권한이 없어 거절해야 한다. div는 2 < 3이라는 텍스트를 보여 준다. 미리 &lt;로 바꿀 필요가 없다.

오해와 반례

CSRF 토큰을 달면 댓글 XSS도 해결된다.

토큰은 상태 변경 요청의 위조 방어다. 댓글이 실행 가능한 문맥으로 들어가는 경로는 별도이고 XSS가 토큰을 읽을 수도 있다.

입력검증과 injection

숫자 범위를 검사하는 일과 명령을 데이터로 다루는 일은 왜 둘 다 필요할까?

준비 개념과 학습 목표

준비 개념

  • 문자열 연결

  • SQL의 조건식

학습 목표

  • 허용 입력 범위와 명령/데이터 분리를 구별한다.

  • 값 바인딩과 동적 식별자 선택의 경계를 설명한다.

작은따옴표가 들어간 사람 이름을 없애야 안전한 이름이 될까?

자체 업무 규칙은 이름 O'Neil을 허용한다. 따옴표를 지워 ONeil로 만들면 요구한 이름을 바꾸는 것이다. 의미 검증은 허용된 데이터인지 묻고, 질의 값 바인딩은 명령 구조와 데이터를 분리한다. 이후 결과를 화면에 표시할 때는 출력 문맥이 새로 생긴다.

이번 질의 모형은 고정 구조 WHERE name = 값이며 문자열 전체 일치다. SQL 패턴·대소문자·정규화는 생략한다. ?는 가상 값 자리 표시이고 실제 드라이버 문법/DB는 실행하지 않았다. 식별자와 방향은 서버에 미리 정의한 조각만 선택한다.

먼저 확인할 개념
  • 업무 입력 계약

    수량 형과 범위 검사가 질의 구조 분리와 다른 조건임을 본다.

  • 같은 시각의 정렬 키

    사용자 정렬 선택을 고정된 열·동점 규칙에 대응시킨다.

입력의 의미를 검사하기

입력검증은 서비스가 허용하는 값인지 확인하는 일이다. 수량이 정수 1..20이어야 하면 0·21·소수·누락은 각각 이유를 갖고 거절한다. 클라이언트 화면 검사는 사용자를 돕지만 직접 요청을 보내는 클라이언트도 있으므로 서버에서 동일한 계약을 확인한다.

문자열이 허용되는 자유 입력이라고 해서 명령 문법에 그대로 이어 붙여도 된다는 뜻은 아니다. 유효한 사람 이름에도 작은따옴표가 있을 수 있다. 모든 문장 부호를 삭제하면 정상 데이터를 망가뜨리고 다른 문맥의 공격도 놓칠 수 있다.

질의 구조를 먼저 정하기

SQL 값을 바인딩하는 API는 질의 구조를 미리 정한 뒤 입력을 값으로 전달한다. 물음표 ?를 매개변수로 사용하는 가상의 질의 SELECT name FROM users WHERE name = ?에서 입력은 이름 값 하나다. 실제 드라이버의 placeholder 문법은 다를 수 있으므로 이 문장은 실행 코드가 아닌 계약 표시다.

열 이름이나 정렬 방향은 값 placeholder로 임의 대체할 수 있다고 가정하지 않는다. 사용자 선택을 서버가 미리 정의한 age/name 같은 식별자와 ASC/DESC에 대응시키는 방식이 필요하다. 파라미터 바인딩을 한 뒤 다시 문자열 SQL로 재구성하면 처음의 경계를 잃는다.

다른 경계도 남는다

SQL injection 방어가 XSS·권한 누락·업무 오류까지 자동 해결하지는 않는다. 쿼리 결과를 HTML로 표시할 때 출력 문맥을 다시 확인한다. DB 계정도 필요한 권한만 가져야 실수의 영향이 줄어든다.

아래 작은 표는 실제 DB 접속 없이 값 비교를 수행하는 교육 모델이다. 이름은 문자열 전체 일치로 비교하며 SQL 패턴 매칭이나 대소문자 정규화는 생략한다. 안전성의 전부를 증명하는 시험이 아니라 명령과 값의 차이를 관찰한다.

응답이 안 보였는데 서버 장부는 바뀔 수 있을까?

페이지 origin은 https://learn.example, API는 https://api.example다. 자체 실험 표에서 단순 POST는 text/plain 본문이며 추가 비허용 헤더·스트리밍·업로드 리스너는 없다. 브라우저가 요청을 전달하고 서버가 변경을 했다고 명시해도 CORS 응답 공개 조건이 실패하면 페이지 코드는 결과를 읽지 못할 수 있다.

별도 사례는 캐시된 preflight 허용이 없고 JSON POST 전에 OPTIONS가 거부된다. 두 사례를 같은 오류 이름으로 뭉치지 않는다. 실제 브라우저·네트워크·API·키 폐기 시험은 하지 않았으며 응답 공개와 서버 효과를 종이에서 분리한다.

    관찰 실패만으로 명령 효과 없음을 단정하지 않는다.

  • 쿠키 전달 조건

    credentials 설정과 브라우저 쿠키 조건도 CORS 헤더와 별도로 본다.

origin과 응답 접근

origin은 scheme·host·port의 조합이다. 경로가 다르다고 다른 origin이 되는 것은 아니지만 같은 host라도 포트나 scheme이 다르면 다를 수 있다. CORS는 서버의 헤더를 근거로 브라우저가 다른 origin 응답을 페이지 코드에 공개할지 결정하는 규칙이다.

일부 요청은 preflight로 실제 요청 전 허용 조건을 묻지만 모든 요청이 그렇지는 않다. 단순 요청은 먼저 전달되고 응답 읽기만 막힐 수 있다. 따라서 CORS 오류를 서버의 부작용 부재나 인증·CSRF 방어의 증명으로 사용하지 않는다. 브라우저 밖의 클라이언트는 별도 서버 인증이 필요하다.

자격 증명의 조건

자격 증명을 포함하는 cross-origin fetch에는 서버가 정확한 허용 origin과 Access-Control-Allow-Credentials: true를 제공해야 응답 접근 조건을 만족한다. Allow-Origin: *는 이 경우 사용할 수 없다. 브라우저의 쿠키 정책이 추가로 전송을 제한할 수 있어 헤더 둘만 맞다고 모든 환경의 로그인 성공이 보장되지는 않는다.

허용 목록의 origin을 정확하게 비교하고 응답이 origin별로 달라지면 캐시의 Vary: Origin도 고려한다. 임의 요청 Origin을 그대로 반사해 모든 신뢰를 주지 않는다. 이 단원 표는 simple GET의 응답 공개 조건만 따로 계산한다.

클라이언트 공개물과 자격 증명

웹 페이지의 JavaScript 번들이나 모바일 앱에 배포한 문자열은 사용자가 읽을 수 있다고 보고 설계한다. 환경 변수 이름이나 난독화는 클라이언트에 이미 들어간 서버 비밀을 비공개로 만들지 않는다. 공개 식별자는 공개 식별자로, 실제 권한 있는 비밀은 제한된 서버에서 사용하도록 나눈다.

비밀이 유출되면 저장소에서 글자를 지우는 것만으로 이미 복사된 키는 폐기되지 않는다. 공급자의 폐기·회전과 권한 축소, 사용 이력 확인이 필요하다. 아래 K1/K2는 실제 키가 아닌 상태표의 이름이며 계정이나 비밀을 만들지 않는다.

페이지 origin은 https://learn.example다. 쿠키 포함 simple GET의 응답 A는 Allow-Origin:*와 Allow-Credentials:true, B는 Allow-Origin:https://learn.example와 Allow-Credentials:true다. 다른 쿠키 정책은 만족했다고 가정하고 페이지의 읽기를 판정하자.

  1. A의 wildcard는 자격 증명 요청 응답 공개 조건과 맞지 않는다.

  2. B는 명시 origin이 페이지와 같고 자격 증명 허용이 참이다.

  3. 이미 전달된 simple GET 여부와 응답 읽기 여부를 구별한다.

A 응답은 페이지 읽기 차단, B는 이 CORS 조건에서 읽기 허용. 서버 인증 성공이나 부작용 부재를 뜻하지 않는다.

저장 없음으로 단정해 재시도하지 않는다. 실제 주문 API를 호출한 기록은 아니다.

다른 문제에 적용하기

댓글 원문 <em>반가워</em>를 일반 div에 글자 그대로 보여 주고 이름 O'Neil은 업무상 허용한다. 두 입력을 각각 표시/SQL 값 전달할 계획과 정렬 unknown 거부를 적어라. 별도 A세션의 유효 토큰은 A토큰인데 B토큰이 제출됐다. 변경 허용을 판정하라. 마지막으로 text/plain 단순 POST의 주문 저장은 완료됐지만 ACAO 누락으로 응답 읽기가 실패한 자체 사례다. 같은 POST 자동 재요청의 중복 위험을 설명하라. 노출된 권한 있는 키 K1은 현재 번들에서만 제거됐고 공급자 유효 상태는 그대로다. 어떤 완료 주장이 아직 불가능한가?

힌트 1

표시의 해석 문맥과 SQL의 데이터 값을 별도 경계로 둔다. 토큰은 현재 세션과 비교한다.

힌트 2

응답 관찰 실패가 저장을 취소하는지, 파일 삭제가 공급자 자격을 무효화하는지 따로 묻는다.

풀이와 답 확인

  1. 일반 div textContent에는 댓글 원문을 넣어 em 요소를 만들지 않는다. script 위치로 옮기지 않는다.

  2. 허용 이름은 따옴표를 지워 바꾸지 않고 고정 질의의 값으로 바인딩한다. unknown 정렬은 고정 목록 밖이라 질의 구성 전에 거부한다.

  3. A세션 값 A토큰과 B토큰은 불일치하므로 변경 전 거부한다. 맞는 토큰이어도 자원 인가는 따로 필요하다.

  4. 주문 저장은 완료됐다는 주어진 조건이다. 읽기 실패는 취소가 아니며 중복 방지 계약 없는 재요청은 추가 주문 위험이 있다.

  5. K1의 이미 받은 사본과 공급자 유효 상태는 파일 삭제로 없어지지 않는다. 공급자 폐기와 새 전달/의존 작업 검사를 계획해야 한다. 실제 DOM/SQL/HTTP/키 폐기/학생 시험은 미수행이다.

텍스트 문맥/SQL 값 결박/정렬 목록/세션 토큰을 분리하고, CORS 실패와 키 파일 삭제를 서버 효과·폐기 완료로 확대하지 않는다.

해결한 뒤 점검할 것

  • 일반 텍스트 표시와 HTML 해석을 구분한다.

  • 허용 데이터 보존과 값 바인딩을 연결한다.

  • 세션에 맞는 토큰과 권한을 각각 검사한다.

  • 응답 관찰과 저장 효과를 나눈다.

  • 파일 상태와 공급자 키 유효 상태 및 미수행 시험을 구별한다.

보강 자료의 출처와 확인 범위
  • OWASP XSS Prevention

    229–242 프레임워크 우회,291–358 문맥·정화 이후 변경·safe sinks 본문을 읽었다. div와script 및 표시 글자 비교는 제한된 자체 모형이다.

  • OWASP CSRF Prevention

    281–320 GET 변경 금지·프레임워크 보호·토큰 수명/세션 결합·불일치 거부·URL/로그 금지를 실제 읽었다.

  • OWASP SQL Injection Prevention

    254–300의 값 결박과 추상 계층 경계,333–335의 식별자/방향 allow-list 및399–401의 검증된 값도 문자열 SQL 안전을 보장하지 않음을 읽었다.

  • MDN CORS

    308–312 preflight 순서,428–494 credentials/추가 쿠키 정책/응답 접근과 wildcard 제한을 실제 읽었다. 본 요청/변경 여부는 선언한 자체 모형이다.

  • OWASP Secrets Management

    438–463 비밀 수명주기와 폐기,748–768 노출 범위/기록/의존관계 및782–794 노출 후 실제 폐기·회전·파일 정리 범위를 실제 읽었다.
