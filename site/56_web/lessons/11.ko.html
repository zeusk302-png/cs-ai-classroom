소단원 11.1

unit·integration·E2E

가격 계산은 맞는데 예약 버튼을 누르면 왜 실패할까?

준비 개념과 학습 목표

준비 개념

  • 함수와 반환값

  • 브라우저·서버·저장소

학습 목표

  • 검사 범위와 기대값을 명시한다

  • 세 검사 수준의 관측을 구분한다

  • 통과 범위 밖의 실패를 찾는다

연습 경기 점수와 실제 경기 점수를 같은 줄에 적어도 될까?

자체 예약 요구는 요청 ID r1을 재전송해도 예약이 한 건인 것이다. 버튼을 눌렀다는 관측, 성공 표시, 서버가 저장한 행 수는 서로 다른 값이다. 이 단원은 가상의 관측표를 판정하며 실제 예약 앱·저장소·Playwright를 실행한 결과가 아니다.

테스트 대역은 정한 응답을 줄 수 있지만 실제 저장소의 필수 필드·오류·중복 방지까지 자동 증명하지 않는다. 각 검사에 환경, 사전 상태, 입력, 기대, 관측과 바꾼 구성 요소를 적자. 실제 결제·메일 대역도 범위를 분명히 표시한다.

먼저 확인할 개념
  • 저장 뒤 응답 실패와 재시도

    같은 요청 ID의 효과가 언제 확정됐는지 검사 범위를 정한다.

  • 객체 변경과 거래 확정

    화면 성공과 저장소의 확정 행을 다른 관측으로 둔다.

작은 규칙부터 분리한다

unit 검사는 정한 작은 단위를 주변에서 격리해 입력과 출력을 확인한다. 예를 들어 할인 계산에 정수 원 가격을 주고 결과를 확인한다. 어떤 단위를 unit이라고 부르는지는 팀의 경계 정의도 필요하며 파일 하나와 반드시 같지는 않다.

외부 저장소를 대역으로 바꾸면 규칙을 빠르고 반복 가능하게 검사할 수 있다. 하지만 대역이 진짜 저장소의 필드 형식이나 실패 동작과 다르면 연결 오류를 놓칠 수 있다. 무엇을 대체했는지 검사 기록에 적는다.

연결과 사용자 여정을 넓힌다

integration은 실제로 연결한 둘 이상의 구성 요소가 주고받는 값을 검사한다. API와 저장소가 같은 필드명·단위로 대화하는지, 실패를 적절히 처리하는지 볼 수 있다. 브라우저를 생략한 API 통과는 버튼과 화면 동작의 증거가 아니다.

이 교재의 E2E는 합의한 테스트 환경에서 브라우저의 사용자 조작부터 서버와 저장 결과·화면까지 지정 흐름을 확인하는 뜻이다. 모든 외부 결제나 이메일까지 실제 사용하는지는 따로 명시한다. 환경이 넓어질수록 지연·데이터 초기화·실패 원인 관리가 더 필요하다.

기대와 관측을 분리한다

검사마다 입력·사전 상태·기대·실제 관측을 남긴다. 단순 버튼 클릭 발생보다 저장된 상태와 화면의 최종 내용을 확인하는 것이 업무 요구에 가깝다. 실패 요청 뒤 중복 저장이 생기지 않는지도 중요한 경계다.

자동 검사와 수동 탐색은 보완 관계다. 중요한 규칙은 빠른 검사로 반복하고 대표 사용자 흐름·접근성·시각 변화는 필요한 관측을 더한다. 이 단원의 흐름 표는 실제 앱을 실행한 결과가 아닌 종이 분석이다.

E2E라는 이름만으로 모든 외부 서비스와 실제 DB가 포함됐다고 가정하지 않는다. 여기서 B의 관측은 주어진 표이고 직접 실행한 증거가 아니다. 통과 범위와 미확인 범위를 함께 읽는다.

중간 과정을 따라가는 예제

가상 예약 규칙: 가격≥1000이면100원을 할인하고, API는 total이라는 정수 필드를 저장한다. UI가 price1200을 받았지만 amount1100을 보낸다. 각 검사 범위를 판정하라.

  1. unit에서1200−100=1100을 얻어 계산 규칙은 통과할 수 있다.

  2. API/저장소 integration에서 올바른 {total:1100}을 보내면 저장1100으로 통과할 수 있다.

  3. 브라우저 흐름은 UI가 amount를 보내 필수total이 없어 거절된다. 앞 검사들은 실제UI 변환을 포함하지 않았다.

unit/integration의 지정 사례 통과와 E2E 흐름 실패는 모순이 아니다. 잘못 연결한 필드가 원인인 자체 표다.

조건을 바꾸어 비교하기

시간을 기다리는 것과 결과를 확인하는 것

자체 시간표에서 클릭 후 0 ms에는 저장 중, 300 ms에 테스트 DB 저장, 700 ms에 화면 완료다. 500 ms 고정 대기 뒤 화면 완료를 한 번만 읽는 검사와 완료 조건을 2000 ms까지 관측하는 계획을 비교하라.

  1. 500 ms는 이 표에서 화면 완료 전이라 실패할 수 있다.

  2. 완료 상태를 기다리는 계획은 이 표의 700 ms에 기대 조건을 확인할 수 있다.

  3. 완료 문구와 DB 한 행을 별도로 확인하며 2000 ms를 넘는 경우는 실패로 남긴다.

고정 시간 경과를 업무 성공으로 치환하지 않는다. 재시도 assertion도 실제 저장의 증거를 대신하지 않는다.

비교할 점

대기 길이를 무작정 늘리는 것과 명시한 최종 조건을 관측하는 것을 비교한다.

앞 검사 잔여 데이터의 거짓 성공

검사 A가 r1 예약을 남겼다. 검사 B는 r1을 새로 만드는 요구인데 시작 DB에 r1이 이미 있다. B 뒤 한 건이 있다는 이유만으로 새 생성 동작이 성공했다고 할 수 있는가?

  1. B 전 상태의 이미 한 건을 기록한다.

  2. B 후 한 건은 전후 차이가 없다.

  3. 검사별 새 ID·격리 데이터 또는 명시 초기 상태를 준비하고 실제 생성 결과를 확인한다.

잔여 데이터만으로 새 생성 성공을 판단하지 않는다. 중복 요청 테스트라면 의도적으로 같은 ID를 쓰는 별도 계약이 필요하다.

비교할 점

테스트끼리 독립할 요구와 한 테스트 안의 재전송 상태 유지 요구를 나눈다.

연습 1 · 값과 상태 예측

버튼 클릭과 성공 문구는 관측했지만 DB는 대역이었다. 요구가 실제 테스트 DB 한 행일 때 저장 검사를 완료라고 표시할 수 있는가?

힌트 1

대역으로 바꾼 경계를 본다.

힌트 2

관측한 문구와 실제 DB 결과를 나눈다.

풀이와 답 확인

  1. UI 성공 문구는 관측했다고 적는다.

  2. 실제 테스트 DB 한 행은 미확인이다.

요구 전체 완료로 표시하지 않는다. 실제 환경 시험은 아직 없다.

흔한 오답에서 다시 생각하기

화면이 성공이므로 어떤 저장소에도 한 행 있다.

대역이 반환한 응답을 실제 저장 결과로 확대하지 않는다.

연습 2 · 오류 찾아 고치기

UI와 API 모두 total 필드를 잘못 amount로 바꿨고 DB 대역도 amount를 받도록 함께 수정했다. 검사 통과가 원래 total 계약을 증명한다고 한다. 무엇을 대조해야 하는가?

힌트 1

검사 기대가 구현과 같이 잘못 바뀌었는지 본다.

힌트 2

독립된 업무/API 계약을 기준으로 둔다.

풀이와 답 확인

  1. 원래 계약의 total 필드와 실제 API/DB 스키마를 대조한다.

  2. 대역이 그 계약의 필수 필드·실패 조건을 반영하는지 확인한다.

  3. 잘못 동기화한 기대만 통과한 상태를 성공 증거로 삼지 않는다.

기대값은 검증할 구현의 오답을 그대로 복제하지 않아야 한다.

연습 3 · 직접 만들어 보기

같은 r1 재전송 요구에 대해 최초 저장 뒤 응답 유실·재전송·실제 행 수·화면을 포함한 검사 계획을 만들라. 결제는 대역이다.

힌트 1

재전송 전 서버 저장 상태를 둔다.

힌트 2

최종 행과 표시가 각각 기대를 만족하는지 본다.

풀이와 답 확인

  1. 격리 초기 DB에 r1이 없음을 정한다.

  2. 첫 저장 완료 뒤 응답 유실을 주입하는 경계를 정한다.

  3. 같은 r1을 재전송해 기존 결과를 얻고 DB 한 행 / 화면 1100을 확인한다.

  4. 대역 결제와 실제 결제 완료 미확인을 기록한다.

중복 방지 계약을 포함한 계획이다. 실제 실패 주입·DB·브라우저 실행은 미수행이다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

unit 문장 커버리지 100%라는 기록만 있다. 할인 가격 999 / 1000 경계의 값과 입력 형 거부가 모두 맞다고 증명할 수 있는가?

힌트 1

문장이 실행됨과 값 관계 검사 여부를 나눈다.

힌트 2

실제 기대·입력 집합을 확인한다.

풀이와 답 확인

  1. 실행된 문장 비율만으로 적절한 기대 검사와 모든 경계가 포함됐는지 모른다.

  2. 999 → 999, 1000 → 900 및 명시 형 오류 같은 사례를 추가 대조한다.

  3. 연결·UI·외부 서비스 범위는 별도로 유지한다.

커버리지 수치와 계약 검사 범위를 같은 값으로 읽지 않는다. 실제 커버리지 도구 실행은 미수행이다.

한 단계 더

동일 요청ID 두 번 전송에서 저장은 한 건이어야 한다는 자체 요구를 추가하자. 첫 요청 후 응답이 사라진 상황을 표로 그려 재시도와 중복 저장을 구별하라. 멱등성 검사는 어떤 수준에서도 범위를 정해 수행할 수 있고 E2E라는 이름만으로 이 요구가 포함되지는 않는다.

마우스 없이 검색하고 오류를 고칠 수 있을까?

준비 개념과 학습 목표

준비 개념

  • HTML 입력과 버튼

  • 분수와 비율

학습 목표

  • 키보드·이름·오류의 점검을 설계한다

  • 대비의 명시조건을 계산한다

  • 부분 점검과 전체 적합성을 구별한다

문에 도달하는 것과 문을 열고 다시 나오는 것은 같은 검사일까?

가상 키보드 관측에서 입력·검색 버튼·결과 링크까지 초점이 이동한다. 버튼 Enter가 아무 동작을 하지 않고 펼친 창에서 초점이 빠져나오지 못한다면 도달만의 성공은 전체 조작 성공이 아니다. 단원 표는 실제 브라우저·보조기기 관측이 아닌 주어진 상황이다.

이름·조작·초점·확대·오류 복구·대비를 나누어 질문한다. 대비 예는 이미 계산된 상대휘도와 SC1.4.3 예외가 아닌 일반 본문이라는 전제를 쓴다. RGB 숫자나 화면 캡처 밝기를 상대휘도로 직접 대입하지 않는다.

먼저 확인할 개념
  • HTML 이름과 폼 의미

    입력 설명과 명시 label 연결을 점검할 기준을 둔다.

  • 검증 오류와 입력 복구

조작과 의미를 함께 본다

키보드로 필요한 컨트롤에 도달하고 작동하며 빠져나올 수 있는지 본다. 현재 초점을 눈으로 확인할 수 있는지도 별도 질문이다. 클릭 가능한 모양만 보고 키보드 조작이 된다고 추정하지 않는다.

입력에는 무엇을 넣는지 알 수 있는 이름과 필요한 형식 안내를 제공한다. label의 for와 입력 id를 일치시키는 연결은 한 방법이며 다른 접근 가능한 이름 방법도 있다. 색만으로 필수나 오류를 표현하면 색을 구별하기 어려운 사람에게 정보가 빠질 수 있다.

읽기와 오류 복구를 확인한다

일반 본문 문자에 대한 대비 기준 예제는 WCAG SC1.4.3의 예외에 해당하지 않는 문자로 한정하고4.5:1을 비교한다. 이미 구한 상대휘도 L1≥L2에 대해 대비는(L1+0.05)/(L2+0.05)다. RGB 숫자를 상대휘도처럼 바로 대입하지 않는다.

대비가 맞아도 확대 시 내용이 잘리거나 키보드 초점이 사라지면 다른 장벽이 남는다. 빈 필수 입력의 오류가 어디인지와 어떻게 고칠지를 텍스트로 알려 주는지 살핀다. 자동 검사 결과만으로 의미 있는 대체 텍스트나 실제 과제 수행을 모두 확인할 수 없다.

관측 범위를 기록한다

WAI Easy Checks는 빠른 첫 평가이며 일부 항목 통과가 완전한 접근성 보장은 아니다. 실제 점검 기록에는 페이지/상태/입력 방법·문제 재현·기대·관측을 적고 아직 수행하지 않은 사용자나 보조기기 검사는 미수행으로 남긴다.

아래 예제는 제공된 HTML 관계와 가상 관측표로 판정한다. 실제 브라우저·스크린리더·사용자 실험을 하지 않는다. 학습자는 종이에서 무엇을 검사해야 할지 먼저 설계한 뒤 별도 환경에서 관측을 추가할 수 있다.

중간 과정을 따라가는 예제

가상 폼은 label for=q와 input id=query를 쓰며 다른 이름 제공 방법이 없다. Tab 경로는입력→버튼이고 둘 다 보이는 초점이 있다. 일반본문의 상대휘도는 밝은0.8/어두운0.1이다. 항목별 판정하라.

  1. for=q와id=query가 달라 이 label은 연결되지 않는다. 다른 이름 방법이 없다는 전제로 이름 문제를 기록한다.

  2. 주어진 키보드 도달/초점 표는 그 두 항목만 통과다. 실제 기능 실행이나 빠져나오기 여부는 이 표에 없어 미상이다.

  3. 대비는(.8+.05)/(.1+.05)=.85/.15=17/3≈5.667로4.5이상이다.

이름 연결 문제1개·주어진 도달/초점 통과·본문 대비 통과다. 전체 적합성 판정은 하지 않는다.

대비 경계에 작은 차이가 있다

일반 본문에서 밝은 색의 상대휘도는 0.8, 어두운 색은 0.14다. 0.85/0.19를 계산해 대비가 4.5 이상인지 판단하라. 어두운 색의 상대휘도를 0.13으로 바꾼 경우도 비교하라.

  1. 0.14에서는 85/19≈4.473684로 4.5 미만이다.

  2. 0.13에서는 0.85/0.18=85/18≈4.722222로 4.5 이상이다.

  3. 표시 반올림으로 실패를 통과로 바꾸지 않는다.

0.14는 실패, 0.13은 이 일반 본문 대비 조건을 통과한다. 실제 CSS 색을 측정한 것은 아니다.

빠른 방문이 많으면 느린 방문은 평균 뒤에 숨겨도 될까?

자체 표본에서 요청 80개의 시간은 각각 5 ms이고, 나머지 20개는 각각 105 ms다. 평균 25 ms라는 결과와 느린 요청 20개는 함께 존재한다. 다음 계산은 주어진 표본의 요약이며 실제 사용자 Web Vitals나 장치 성능을 측정한 것은 아니다.

캐시의 언어 구분과 fresh 여부는 시간 요약과 다른 조건이다. 아래는 HTTP 캐시가 Vary와 freshness 정책을 따른다는 모형으로 한정한다. 브라우저 history 복원·service worker·CDN 설정·인증 상태의 실제 동작은 별도로 시험해야 한다.

어느 환경의 어떤 시간을 잰다

실험실 관측은 장치·네트워크·입력을 통제해 원인을 비교하기 쉽고 실제 사용자 관측은 다양한 환경의 경험을 담는다. 둘은 목적이 다르다. 응답 시간만 짧아도 주 콘텐츠 표시·사용자 입력 반응·배치 안정성이 나쁠 수 있다.

Web Vitals의 LCP/INP/CLS는 각각 로딩·반응·시각 안정성과 관련한 구별된 관측이다. 특정한 한 요청의 서버 시간만으로 이 지표들을 계산했다고 주장하지 않는다. 아래 가상 시간은 요청 처리 모형이며 사이트 품질 인증 결과가 아니다.

저장과 재사용은 다르다

여기서는 HTTP private cache가 Cache-Control을 지키는 상황만 본다. max-age는응답의freshness lifetime이고 현재 age가 그보다 작으면 조건에 맞게 재사용할 수 있다. age에는 앞선 공유캐시 체류시간 같은 정보가 포함될 수 있어 단순히 내 컴퓨터 저장 이후만 뜻하지 않는다.

no-cache는 저장 자체 금지가 아니라 재사용 전 검증을 요구한다. no-store는 저장하지 말라는 지시다. ETag와 If-None-Match로 검증해 같으면304로 기존 본문을 쓸 수 있고 달라지면200의 새 본문을 받는다. 브라우저 history 복원·service worker 자체 정책은 현재 모형 밖이다.

빠름과 최신성을 함께 관측한다

캐시 hit는 원본 통신을 줄일 수 있지만fresh 허용기간 중 원본이 바뀌면 저장된 응답을 재사용할 수 있다. 개인화·언어별 응답은 적절한 구별과 정책이 필요하다. 원본이 Accept-Language로응답을 바꾸는 경우 Vary 같은 선언이 캐시 선택에 관여한다.

성능 비교에는 캐시 상태·요청 수·버전·시간 정의를 함께 기록한다. warm표본만 보고 처음 방문의cold경험을 대표한다고 하지 않는다. 실패율이나 최신성 검사도 별도로 필요하며 빠른 오답 화면은 성공적인 사용자 경험이 아니다.

중간 과정을 따라가는 예제

가상 캐시 응답의 max-age는 60초, current age는 45초이고 원본 버전은 v2로 바뀌었다. 저장된 응답의 ETag는 v1이다. age가 60초일 때 통상 재사용을 위해 검증하며 원본 ETag v2를 받는 상황을 추적하라. stale 사용 예외와 reload/history 복원은 없다.

  1. age 45<60이므로 fresh 여유는 15초다. 별도 검증 지시가 없으면 저장된 v1을 재사용할 수 있어 원본의 v2 발행을 즉시 알아내지는 못한다.

  2. age 60은 fresh 조건 age<60을 만족하지 않는다. If-None-Match v1로 원본에 검증을 요청한다.

  3. 원본 ETag v2가 달라 200과 새 본문 v2를 받는다. 같았다면 304를 받고 기존 본문을 재사용한다.

age 45에서는 fresh 응답 v1의 재사용이 가능하고, age 60에서는 검증 뒤 200과 v2를 받는다. 정의한 종이 추적이며 실제 HTTP 관측 결과는 아니다.

조건을 바꾸어 비교하기

느린 표본을 제외한 개선 주장

모형 A의 요청 100개는 80×5 ms+20×105 ms다. 모형 B는 80×5 ms만 남기고 느린 요청 20개를 제외해 평균 5 ms를 보고했다. 같은 요청 100개의 경험이 개선됐다고 할 수 있는가?

  1. A의 평균은 2500/100=25 ms다.

  2. B는 분모가 80인 부분집합의 평균 5 ms다.

  3. 느린 요청 20개를 개선한 값이 없으므로 같은 모집단의 개선 증거가 아니다.

표본 제외와 성능 개선을 구별한다. 실제 사용자나 실험 측정은 아니다.

비교할 점

숫자만 작아진 보고와 같은 조건의 관측 비교를 나눈다.

정한 백분위 계산 규칙을 먼저 적는다

자체 요청 시간 8개를 오름차순으로 놓으면 [5, 5, 5, 5, 5, 5, 105, 105] ms다. 이 연습에서 p75는 nearest-rank 규칙으로 ceil(0.75×n)번째 값이다. 평균과 p75를 구하라.

  1. 합은 6×5+2×105=240이고, 평균은 30 ms다.

  2. ceil(0.75×8)=6이므로 여섯 번째 값 5 ms가 p75다.

  3. 최댓값 105 ms와 느린 요청 2개는 남는다. 이 요청 표본의 p75는 실제 INP·LCP·CLS를 계산한 것이 아니다.

평균 30 ms, p75는 5 ms, 최댓값은 105 ms다. 백분위 값 하나가 모든 방문의 속도를 보장하지 않는다.

힌트 보기

풀이 보기

전체 평균은 (80×5+20×105)/100=(400+2100)/100=25ms, cold 평균은 105ms다. no-cache는 저장을 허용하지만 재사용 전에 검증을 요구한다. 저장을 금지하는 no-store와 다르다.

오해와 반례

cache hit가 많으면 모든 사용자에게 새 버전과 좋은 응답 품질이 보장된다.

fresh v1의 재사용과 cold 요청의 105ms가 반례다. 캐시 빈도·최신성·사용자 환경·로딩·입력 반응·시각 안정성 관측은 서로 대체하지 않는다.

예약 r1 검사의 DB는 대역이고 브라우저는 성공 문구를 보였다고 주어진다. 실제 테스트 DB 한 행 요구의 완료 여부와 추가할 검사 경계를 적어라. 가상 폼은 Tab 도달·초점만 확인됐고 Enter 실행·오류 복구는 미상이다. 일반 본문 상대휘도 0.8/0.14의 대비도 판정하라. 가상 요청 표본은 80×5 ms+20×105 ms이며 느린 20개를 빼고 평균 5 ms라 보고했다. 전체 평균과 비교의 의미를 적어라. 마지막 /u는 언어별 응답인데 ko 본문만 URL 키에 저장됐다. en 요청을 올바르게 구별할 정책과 stale ko 응답의 동일 ETag 조건부 GET 결과를 적어라.

힌트 1

대역·실제 저장, 도달·실행을 각각 나눈다. 대비는 .85/.19를 반올림 전에 비교한다.

힌트 2

평균의 분모와 Vary의 선택 기준을 확인한다. 304에는 새 본문이 없다.

풀이와 답 확인

  1. 대역 환경의 UI 문구는 주어진 관측이나 실제 테스트 DB 한 행은 미확인이다. 연결 DB와 격리 사전 상태·행 수·화면을 추가 검사 계획에 둔다.

  2. Tab 도달·초점은 주어진 성공, Enter·오류 복구는 미상이다. 대비 85/19≈4.473684<4.5이므로 실패다.

  3. 전체 평균은 (400+2100)/100=25 ms다. 80개만의 5 ms는 부분집합 보고이고 같은 요청 100개의 개선을 증명하지 않는다.

  4. Vary: Accept-Language로 변형 구분을 알리고 실제 캐시 선택을 검사하는 계획을 둔다. 언어 구분이 개인화 보호 전체를 대체하지 않는다.

  5. 선택된 stale ko 표현의 ETag가 같으면 조건부 GET 304와 기존 본문 재사용이다. 실제 DB·브라우저·보조기기·색·캐시·성능·학생 실험은 미수행이다.

대역 범위 밖 DB 미확인·기능 미상·대비 실패·전체 평균 25 ms/부분 5 ms 구별·언어 변형 구분·304 기존 본문이다.
