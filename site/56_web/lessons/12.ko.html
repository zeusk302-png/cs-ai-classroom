환경설정과 HTTPS

내 컴퓨터에서 열리는 링크가 공개 주소에서도 같은 곳을 가리킬까?

준비 개념과 학습 목표

준비 개념

  • URL

  • 브라우저와 서버

  • 정적 파일

학습 목표

  • 공개 base 경로와 개발 경로를 구별한다.

  • 클라이언트 설정과 비밀을 구별한다.

  • HTTPS 보장 범위를 설명한다.

주소 끝의 / 하나가 그림의 위치를 바꿀 수 있을까?

가상 공개 사이트의 경로는 https://learn.example/class/다. URL 해석은 문자열을 뒤에 붙이는 일이 아니다. 이 연습에서는 HTML base 요소나 리다이렉트가 없고, 문서 URL이 기준 주소라고 정한다. /class/와 /class는 마지막 / 뒤의 현재 디렉터리가 달라 같은 상대 주소가 다른 위치로 간다.

파일 목록과 요청한 절대 주소를 짝지어 보자. HTTPS는 전달 중의 연결을 보호하지만 받은 JavaScript를 방문자가 읽는 것을 막지 않는다. 이 단원은 가상 파일 목록과 응답표로 판단하며 실제 인증서·브라우저·배포 설정 검사를 수행한 기록은 아니다.

먼저 확인할 개념
  • 요청 URL과 응답

    정적 파일의 경로 해석과 HTTP 응답 관측을 구별한다.

  • CORS와 공개 비밀

    받은 파일 속 비밀과 요청 읽기 허가를 다른 문제로 본다.

배포 환경은 경로의 일부다

개발 중 localhost는 그 주소를 여는 사람 자신의 컴퓨터를 가리킨다. 공개 페이지 안의 API 주소가 localhost로 남으면 방문자는 작성자의 서버에 연결하지 못한다. 공개 도메인, 프로젝트 하위 경로, API endpoint, 빌드 설정을 배포 전에 명시한다. 정적 호스팅은 서버 프로그램을 자동 실행해 주는 서비스와 다르다.

GitHub Pages의 project site는 기본적으로 계정 도메인 아래 저장소 이름 경로를 사용한다. 예제 사이트 주소가 https://learn.example/class/이고 HTML이 /class/lessons/one.html에 있다면 상대 경로와 /로 시작하는 루트 경로가 다르게 해석된다. 로컬 루트에서 우연히 통과한 경로는 하위 경로 배포에서 다시 확인한다.

브라우저에 보낸 설정은 공개 정보다

정적 JavaScript에 넣은 endpoint나 언어 설정은 사용자가 다운로드해 볼 수 있다. 빌드 때 환경 변수를 문자열로 바꾸어 넣어도 결과 파일에 비밀이 포함되면 공개된 것이다. 사용자에게 보내는 공개 설정과 서버에서만 쓰는 권한 비밀을 분리한다. 비밀이 필요한 작업은 적절히 보호한 서버 경계가 필요하다.

페이지를 처음 보이게 만드는 것과 데이터 요청이 성공하는 것은 별도다. HTML200이어도 잘못된 API 주소, 허가되지 않은 요청, 오래된 캐시나 실패한 JSON 해석 때문에 본문이 없을 수 있다. 개발 도구의 network 요청과 화면 결과를 연결해 어느 단계가 실패했는지 확인하는 절차를 만든다.

HTTPS는 연결을 보호한다

HTTPS는 HTTP를 TLS로 보호해 전송 중 내용의 기밀성과 무결성 및 서버 신원 확인을 제공한다. 올바른 도메인의 인증서를 확인하고 브라우저 경고를 무시하지 않는다. HTTPS가 있다고 콘텐츠 사실성, 접근 권한, 입력 검증과 서버 저장 보안까지 모두 검증된 것은 아니다.

주 문서가 HTTPS라도 script나 스타일 등을 HTTP로 요청하면 mixed content다. 브라우저는 자원 종류에 따라 HTTPS로 업그레이드하거나 차단할 수 있으므로 실제 요청 결과를 확인한다. 모든 자원 주소를 HTTPS로 맞추고 공개 인증서와 경로 및 상태 코드를 점검한다.

  1. 현재 디렉터리는 /class/lessons/다. ../는 한 단계 위 /class/로 이동한다.

  2. 상대 대상은 https://learn.example/class/assets/app.js다.

  3. /assets/app.js는 도메인 루트에서 시작해 https://learn.example/assets/app.js다. 실제 파일이 전자에만 있으면 후자는 실패할 수 있다.

두 주소가 다르며 project 하위 경로를 검증해야 한다.

조건을 바꾸어 비교하기

뒤의 슬래시를 포함해 계산하기

https://learn.example/class와 https://learn.example/class/에서 각각 ./assets/app.js를 해석하라. 리다이렉트와 base 요소는 없다.

  1. 첫 주소의 마지막 / 뒤는 class다. 현재 디렉터리는 /라서 /assets/app.js가 된다.

  2. 둘째 주소는 /class/ 디렉터리 안이므로 /class/assets/app.js가 된다.

  3. 실제 서버가 /class를 /class/로 리다이렉트한다면 최종 문서 URL을 다시 기준으로 삼는다.

주어진 조건에서는 서로 다른 주소다. 실제 리다이렉트 존재 여부는 미확인이다.

200인데 데이터는 아직 없다

가상 표에서 HTML은 200이고 app.js도 200이다. API 주소는 http://localhost:9000/items이며 방문자는 다른 컴퓨터다. API 연결은 실패했다고 주어진다. 서버에 과목이 0개라는 결론이 맞는가?

  1. localhost는 이 방문자의 컴퓨터를 가리킨다.

  2. API 요청 실패는 서버의 성공한 빈 목록 응답이 아니다.

  3. 공개 API 주소·HTTPS·권한·응답 해석을 확인하는 계획을 세우고 자료를 불러오지 못했다고 표시한다.

홈과 스크립트 전달 성공, API 실패, 목록 내용 미확인을 함께 기록한다.

풀이와 답 확인

  2. 두 번째 ..는 /다.

연습 2 · 오류 찾아 고치기

공개 JavaScript 파일에 서버 권한 키가 들어 있다. 파일은 HTTPS로만 전송되므로 방문자가 그 키를 알아낼 수 없다는 설명을 고쳐라.

힌트 1

전송 중 제삼자와 파일을 받은 방문자를 나눈다.

힌트 2

권한 키가 있어야 할 경계를 찾는다.

풀이와 답 확인

  1. 방문자는 받은 파일 내용을 볼 수 있다.

  2. 키 노출이 확인됐다면 복사본도 고려해 발급 기관에서 폐기·교체하는 대응을 계획한다.

  3. 권한 비밀은 공개 결과물에서 제거하고 필요한 기능을 보호한 서버 경계로 옮긴다.

HTTPS가 공개 결과물 속 비밀을 숨기지는 않는다. 실제 키 폐기나 서버 변경은 수행하지 않았다.

흔한 오답에서 다시 생각하기

키를 난독화하거나 파일 이름만 바꾸면 이미 복사된 키도 폐기된다.

표현 변경과 발급 기관의 권한 취소는 다른 사건이다.

연습 3 · 직접 만들어 보기

공개 하위 경로 /class/에 홈·수업·CSS·그림·JSON이 있다. 기준 URL, 상대 참조, 기대 절대 주소, 응답, 내용 확인을 포함한 첫 점검표를 설계하라.

힌트 1

수업 안의 자원은 홈과 기준 디렉터리가 다르다.

힌트 2

상태 코드와 필요한 내용 확인을 다른 칸으로 둔다.

풀이와 답 확인

  1. 홈 /class/index.html과 수업 /class/lessons/one.html을 각각 행으로 둔다.

  2. 수업의 ../assets/style.css와 ../data/catalog.json의 절대 주소를 계산한다.

  3. 파일 목록과 예상 MIME·본문을 적는다.

  4. 실제 요청 상태와 내용·버전 관측 칸은 아직 미수행으로 둔다.

수업의 두 참조는 /class/assets/style.css와 /class/data/catalog.json이다. 실제 요청 검사 계획이다.

흔한 오답에서 다시 생각하기

각 참조가 쓰이는 문서의 기준 URL이 필요하다.

주 문서와 하위 자원을 나눈다.

검사한 도시락과 배달한 도시락이 같은 것인지 어떻게 알까?

가상 릴리스 H는 파일 묶음의 이름이다. 원본 커밋 c1에서 검사한 산출물 H와 같은 c1을 다른 설정으로 다시 빌드한 J는 같다고 가정하지 않는다. 검사는 어떤 파일 목록과 해시, 설정에 관한 것이었는지 적는다. 아래 H·J는 실제 해시 문자열이 아니라 서로 다른 묶음을 나타내는 기호다.

배포 작업 성공, 공개 manifest 버전, 필요한 파일 내용과 기능은 다른 관측이다. 새 파일 복원도 데이터·서버 설정·방문자의 저장 자료를 과거 상태로 자동 복원하지 않는다. 산출물 전달을 직렬화하는 정책과 되돌릴 호환성을 함께 계획한다.

같은 산출물을 연결한다

CI는 변경을 통합할 때 빌드와 검사를 반복해 결함을 빨리 찾는 절차다. CD는 검증된 변경을 배포 가능하게 준비하거나 정책에 따라 실제 환경에 배포하는 과정이다. workflow에는 여러 job과 step이 있으며 배포가 어떤 검사 성공에 종속되는지 명시한다. 검사 실패가 있어도 독립 job으로 배포가 계속되는 설계는 원한 기준을 만족하지 않을 수 있다.

검사한 산출물 H와 공개 산출물 H를 연결해야 한다. 같은 원본 커밋이어도 의존성이나 설정이 달라 재빌드 결과 J가 생기면 H에 대한 검사 기록만으로 J를 검증했다고 할 수 없다. 릴리스에는 원본 버전, 공개 파일 목록과 해시, 검사 결과를 묶어 기록한다.

배포 완료와 공개 완료를 나눈다

자동 작업의 성공은 지정한 단계가 성공했다는 증거다. 잘못된 폴더를 올리거나 CDN과 브라우저가 이전 파일을 보관하면 사용자가 새 내용을 못 볼 수 있다. 공개 주소를 열어 릴리스 표시와 파일 내용, 주요 흐름을 확인해야 최신 릴리스를 확인했다고 말할 수 있다.

배포 후 점검은 예상 릴리스 H와 관측 릴리스가 일치하는지, HTML과 자원 및 데이터가 잘 조합되는지를 본다. 일부 요청만200이고 다른 요청404인 경우 전체를 성공이라 하지 않는다. 점검 실패 시 원인을 기록하고 공개 확인 상태를 미완료로 유지한다.

되돌릴 수 있는 대상부터 정한다

rollback은 문제 릴리스에서 이전에 검증된 산출물로 되돌리는 대응이다. 정적 사이트는 이전 파일 묶음을 복원하고 공개 버전을 다시 확인할 수 있다. 코드 파일만 복원해도 서버 데이터, 브라우저 저장 형식이나 외부 설정이 자동으로 옛 상태로 돌아오는 것은 아니다.

예전 코드가 새 데이터 형식을 이해하지 못하면 파일 rollback이 또 다른 오류를 만들 수 있다. 변경 전 호환성, 백업과 복원 범위, 되돌린 뒤 확인할 흐름을 준비한다. 사고 대응에서 임의 삭제로 이전 증거를 없애기보다 릴리스 기록과 문제 원인을 보존한다.

중간 과정을 따라가는 예제

build3분 뒤 검사2분, 배포1분, 공개 점검2분이 순서대로 돈다. 점검에서 기대H 대신 이전G가 보인다. 시간과 완료 상태를 판단하라.

  1. 3+2+1=6분에 배포 작업은 끝난다.

  2. 공개 점검까지3+2+1+2=8분이다.

  3. G≠H이므로 최신 공개 확인은 실패다. 자동 작업 성공만으로 학습자 공개 완료라고 기록하지 않는다.

8분 후 최신 공개 확인 미완료다. 실제 배포 폴더·캐시·릴리스 대상 등을 조사한다.

조건을 바꾸어 비교하기

동일 커밋의 다른 산출물

H는 설정 API=/api/v1로 빌드해 검사했다. 같은 c1에서 API=/api/v2로 J를 빌드하고 H 검사 보고만 첨부했다. 어떤 연결이 빠졌는가?

  1. API 설정이 바뀌어 J의 결과 파일이 H와 다르다고 주어진다.

  2. H 검사는 J의 v2 요청 계약을 검사하지 않았다.

  3. J를 기준으로 필요한 검사를 수행하거나 검사한 H 자체를 배포할 정책을 정한다.

커밋 같음만으로 산출물 검사 이전을 주장하지 않는다. 실제 빌드·검사는 미수행이다.

비교할 점

원본 버전과 배포 결과물의 동일성은 다른 관계다.

파일 되돌리기 뒤의 남은 형식

G는 데이터 v1만 읽고 H는 v2만 읽는다. H 배포 때 서버 데이터를 v2로 바꾸고, 문제 뒤 파일만 G로 되돌렸다. 저장 데이터는 그대로 v2다. 복구인가?

  1. 파일은 G지만 데이터는 v2다.

  2. 주어진 G의 읽기 조건에 맞지 않는다.

  3. v2를 읽는 수정 코드 또는 검증한 데이터 복원·호환 전략을 선택하고 실제 흐름을 확인해야 한다.

파일 복원 사건은 있었지만 서비스 복구는 보장되지 않는다. 실제 데이터 복원은 미수행이다.

연습 1 · 값과 상태 예측

H를 공개하려 한다. 배포 job은 성공이고 manifest는 H지만 필수 수업 파일은 이전 G다. 릴리스 기준은 필수 파일 모두 H 일치다. 완료인가?

힌트 1

기준의 모든 파일 조건을 읽는다.

힌트 2

버전 하나와 파일 묶음 일치를 나눈다.

풀이와 답 확인

  1. manifest는 H라는 관측이다.

  2. 필수 수업 G는 기준과 다르다.

  3. 최신 공개 완료를 미완료로 기록한다.

지정 기준 미달이다. 실제 공개 사이트 검사 결과가 아니라 가상 표의 판정이다.

묶음 안 파일별 관측이 필요하다.

연습 2 · 오류 찾아 고치기

가상 배포 A(H)가 오래 걸리고 뒤에 시작한 B(J)가 먼저 끝난다. 마지막에 A가 덮어써 H가 공개됐다. 시작 순서만으로 최신 J를 보장한다는 주장을 고쳐라.

힌트 1

시작 시각과 마지막 쓰기 시각을 나눈다.

힌트 2

동일 공개 대상의 동시에 쓰는 경계를 확인한다.

풀이와 답 확인

  1. B 완료 후 A 완료라는 관측에서 마지막 공개값은 H다.

  2. 공개 대상별 배포를 한 번에 하나로 제한하는 계획을 세운다.

  3. 선택된 최종 릴리스와 공개 관측을 다시 연결한다.

직렬화 정책과 최종 버전 확인이 필요하다. 특정 큐의 순서를 가정하거나 실제 동시 배포를 실행하지 않았다.

작업 소요 시간이 달라 완료 순서가 바뀔 수 있다.

가상 점검은 처음 방문·검색·직접 링크·키보드·오류 복구라는 서로 다른 길을 다룬다. 목록에 없는 경로를 성공이라고 채우지 않는다. 검색 결과 없음은 성공한 검색의 빈 결과이고, 요청 실패는 검색 결과 자체를 모르는 상태다. 두 경우의 안내와 다음 행동은 달라야 한다.

자동 검사와 개발자의 시나리오 점검, 실제 학생 수행은 분모가 다르다. 통과율에는 어떤 항목을 포함했는지 적고 핵심 실패를 평균 뒤에 숨기지 않는다. 아래는 가상 보고를 읽는 연습이며 학생·보조기기·실사용 운영을 직접 관측한 것은 아니다.

사용자의 목적을 따라간다

공개 강의 사이트의 목표 흐름은 홈에서 과목 찾기, 소단원 읽기, 연습문제 답 확인, 이전 화면으로 돌아가기일 수 있다. 각 단계의 링크와 버튼뿐 아니라 표시된 과목, 정답 내용과 뒤로 가기 결과도 확인한다. 사이트 첫 화면200은 이 전체 흐름의 증거가 아니다.

직접 소단원 URL로 들어오기, 새로 고침, 검색 결과 없음, 존재하지 않는 과목처럼 처음부터 홈을 거치지 않는 길도 살핀다. 오류 화면은 무엇이 실패했고 어디로 돌아갈 수 있는지 알려야 한다. 네트워크 실패 때 빈 화면이나 끝없는 로딩을 정상이라고 표시하지 않는다.

다양한 접근 방법을 포함한다

키보드만으로 과목 링크와 정답 버튼을 이동·실행할 수 있는지, 포커스가 보이는지, 화면 확대에서 내용이 겹치지 않는지 점검한다. 그림 핵심 정보는 텍스트 대안으로 제공한다. 화면낭독 도구와 실제 사용자 피드백은 자동 검사가 찾지 못하는 흐름을 드러낼 수 있다.

자동 접근성 점수만으로 모든 사람이 사용할 수 있다고 결론내리지 않는다. 좁은 화면, 느린 연결, 쉬운 표현과 일관된 탐색도 사용에 영향을 준다. 실제 검증한 브라우저·입력 방식·환경과 남은 대상들을 공개 문서에 구분해 적는다.

운영 점검의 빈도는 변경과 장애 영향에 맞춰 정한다. 링크 오류와 오래된 데이터, 주요 자원 실패 및 이용자 신고를 원인과 연결한다. 로그는 필요한 범위로 수집하고 민감 정보를 무작정 저장하지 않는다. 이 소단원의 종이 활동은 실제 학습자 실험을 대신하지 않는다.
