소단원 8.1

ORM과 SQL 연결

객체의 이름을 바꾸면 언제 데이터베이스의 행이 바뀔까?

준비 개념과 학습 목표

준비 개념

  • 객체의 속성

  • 테이블의 행과 기본키

  • 트랜잭션은 변경 묶음

학습 목표

  • 객체·세션·행 상태를 분리한다.

  • flush 와 commit·rollback 을 사건표로 설명한다.

연습장에 쓴 새 이름과 공식 명부에 확정된 이름은 언제 같아질까?

하나의 열린 거래에서 User7.name의 확정 값은 "봄"이고, 세션의 유효 객체를 "여름"으로 바꾼다. 객체 속성, 거래 안 SQL 변경, 확정 행을 세 칸으로 나누자. 아래는 SQLAlchemy 2.0의 기본 세션 동작을 따르는 종이 모형이다. 실제 ORM이나 데이터베이스를 실행한 기록은 아니다.

flush와 commit을 구별하면 화면에서 성공을 알릴 시점도 바뀐다. rollback이나 실패 복구는 세션 객체의 수명까지 다룬다. 이 연습은 하나의 연결, driver autocommit 없는 정상 DB 트랜잭션, 다른 writer 없음으로 제한한다. 외부 메일 송신은 DB 행과 같은 취소 묶음이 아니다.

  • 객체의 참조와 변경

    객체 이름의 동일성과 행의 기본키 동일성을 별도로 그린다.

  • 저장 실패와 응답 관찰

    SQL 변경 이후 응답 실패만으로 저장이 없었다고 단정하지 않는다.

객체에 행의 주소를 연결한다

ORM 은 객체와 관계형 테이블 사이의 매핑이다. User 객체의 id 가 기본키 열, name 이 문자열 열에 연결된다. 객체에 속성이 있다는 사실만으로 파일에 저장된 것은 아니다. 메모리의 객체, 세션의 변경 관리, 데이터베이스의 행을 세 칸으로 그린다.

SQLAlchemy 의 Session 은 작업 단위를 관리한다. 새 객체를 add 하면 세션에 pending 상태로 등록한다. 그다음 flush 가 INSERT 를 보내며, 이때 발생한 변경은 아직 열린 트랜잭션 안에 있다. 아래 모형은 하나의 세션과 하나의 연결에 한정한다.

보내기와 확정은 다른 경계다

flush 는 쌓인 변경을 SQL 로 데이터베이스에 보낸다. commit 은 트랜잭션을 확정하며 필요하면 먼저 flush 한다. flush 성공 뒤에도 rollback 하면 그 거래의 행 변경은 취소될 수 있다. flush 를 저장 완료 알림으로 사용하는 것은 경계를 혼동한다.

조회 전에 autoflush 가 발생할 수 있어 SELECT 한 번에 UPDATE 도 먼저 실행될 수 있다. 세션 밖 다른 거래의 관측에는 격리 수준이 관련된다. 자기 거래에서 변경이 보인다는 사실을 모든 사용자에게 확정됐다는 뜻으로 해석하지 않는다.

같은 행과 같은 객체의 범위를 정한다

identity map 은 하나의 세션에서 같은 기본키로 관리되는 객체의 동일성을 맞춘다. 이미 유효하게 로드된 User 7 을 session.get 으로 다시 찾으면 같은 객체를 받을 수 있다. 다른 세션까지 하나의 객체를 공유하는 전역 캐시는 아니다.

기본 설정에서 commit 은 객체 속성을 만료시킬 수 있고 rollback 도 만료와 재조회에 영향을 준다. 이후 속성 접근이 SELECT 를 유발하거나 닫힌 세션에서는 실패할 수 있다. 또한 관계 목록을 반복 접근하면 여러 SQL 이 나갈 수 있으므로 객체 코드만 보고 쿼리 수를 확정하지 않는다.

둘째 행은 SQL을 보내는 조회를 아직 호출하지 않았다는 조건이다. 셋째 행은 dirty가 없어져도 commit이 아니라는 점을 보여 준다. 만료 속성의 재조회는 연결 가능한 세션과 새 거래라는 조건이 필요하다.

중간 과정을 따라가는 예제

자체 단일 세션 모형에서 DB 의 User7.name="봄"이다. get 으로 a 를 읽고 같은 유효 세션에서 get7 으로 b 를 읽는다. a.name="여름", flush, rollback 후 새 거래에서 이름을 다시 읽는다. 별도 동시 writer 는 없다.

  1. 두 조회는 같은 관리 행을 가리키므로 a 와 b 는 같은 객체다. 두 객체를 새로 생성한 경우와 다르다.

  2. 속성 대입 직후 메모리 이름은 여름이며 변경 대상으로 관리된다.

  3. flush 는 UPDATE 를 열린 거래에 보낸다. 자기 거래에서 여름을 볼 수 있지만 commit 은 아직 없다.

  4. rollback 뒤 재조회하면 원래 행 이름 봄을 읽는다. 기존 참조가 남아 있다는 사실이 여름의 영구 보존을 뜻하지 않는다.

같은 세션의 a/b 는 동일하며 flush 뒤에도 취소 가능하다. 가정한 재조회 결과는 봄이다.

조건을 바꾸어 비교하기

autoflush를 끄면 commit도 안 보내는가

User7의 유효 객체를 여름으로 바꾸고 autoflush=False인 세션에서 ORM SELECT를 실행했다. 그 뒤 commit한다. 명시 flush와 다른 변경은 없다.

  1. 이 SELECT 앞의 자동 flush는 비활성화됐다.

  2. 객체의 아직 유효한 속성과 DB에서 별도 열 조회한 값이 다를 수 있다.

  3. commit 경계에서는 남은 변경을 flush하고 확정한다.

autoflush 설정을 commit의 pending 변경 처리까지 막는 기능으로 해석하지 않는다.

비교할 점

쿼리 반환을 기존 객체로 볼 때 identity map이 유효 속성을 보존하는 조건도 있어, 모든 조회가 자동으로 객체를 새 값으로 덮는다고 단정하지 않는다.

실패한 flush 뒤 같은 세션을 다시 쓰기

새 행 INSERT의 제약 위반으로 flush가 실패했다. DB 거래가 이미 rollback됐다고 해서 같은 Session으로 곧바로 새 SQL을 보내려 한다.

  1. 실패한 flush는 세션을 정상 사용 가능한 상태로 남기지 않는다.

  2. 같은 세션을 계속 쓸 때 명시 Session.rollback을 호출한다.

  3. 버리기로 했으면 닫고 별도 새 세션의 복구 계약을 따른다.

DB 측 취소와 Session의 복구 책임을 구분한다. 실제 제약 위반 코드를 실행한 결과는 아니다.

실패가 있었는데도 오류를 감추고 성공 안내를 보내는 경로를 별도로 막는다.

소단원 8.2

schema migration

열 하나를 지우는 버전 변경을 되돌리면 지웠던 값도 되살아날까?

준비 개념과 학습 목표

준비 개념

  • schema 는 테이블·열·제약의구조

  • 버전은이력의상태

  • NULL 은값부재

학습 목표

  • 구조와 데이터 변경을 순서대로 추적한다.

  • 자동 생성·downgrade 의 범위와 데이터 손실을 구별한다.

낡은 공책의 제목 칸을 지웠다가 다시 그리면 글자도 돌아올까?

열 구조 복원과 데이터 복구는 다르다. 자체 구조 A에는 id/name, B에는 nickname nullable 추가, C에는 값을 채운 뒤 NOT NULL 설정이라고 하자. 기존 행 name이 봄/NULL/달인 세 행이다. 단순히 name을 nickname으로 복사하면 NULL도 옮겨진다.

버전 연결을 따라 어떤 변경이 적용됐는지 추적하고, 업무상 의미를 정한 뒤 비어 있는 값을 채운다. 빈 문자열을 무조건 넣는 것과 올바른 값 결정은 다르다. DB별 DDL 원자성·잠금·실제 백업 복원은 이 종이 계산으로 확인되지 않는다.

먼저 확인할 개념
  • 필드 타입과 업무 의미

    구조 규칙을 만족해도 업무상 올바른 자료인지 별도 확인한다.

  • 객체와 행 변경 경계

    코드 필드 수정과 저장 구조에 실제 변경을 적용한 것을 나눈다.

이전 구조에서 다음 구조로 가는 길

migration 은 저장된 데이터와 구조를 특정 버전에서 다음 버전으로 옮기는 절차다. 소스 모델의 필드를 고쳤다는 사실과 운영 DB 가 그 구조로 바뀌었다는 사실은 다르다. 현재 DB 버전, 다음 변경, 앱의 기대 구조를 함께 기록한다.

Alembic revision 은 이력의 식별자이며 down_revision 으로 앞 변경과 연결한다. 한 갈래의 A→B→C 모형에서는 A 에서 C 로 갈 때 B 와 C 를 순서대로 적용한다. 실제 이력은 분기할 수 있으므로 파일이름 정렬만으로 모든 순서를 정하지 않는다.

기존 행에도 새 규칙을 적용한다

기존 행이 있는 테이블에 NOT NULL 열을 단순 추가하면 각 기존 행의 값을 어떻게 채울지 문제가 생긴다. 교육 전략은 먼저 nullable 열을 추가하고 값을 채운 뒤 남은 NULL 이 없는지 검사하고 NOT NULL 제약을 넣는 순서다. SQL 실행 시간과 잠금·DB 별 DDL 규약은 별도 확인한다.

자동생성은 코드의 메타데이터와 DB 구조 차이를 이용해 후보를 만든다. 열 이름 변경이 삭제/추가로 나타날 수 있으므로 의도한 rename 인지 검토해야 한다. 구조가 같아졌다고 업무상의 올바른 데이터 변환도 자동 증명되는 것은 아니다.

구조 복원과 데이터 복구를 구별한다

downgrade 함수를 작성하면 이전 구조로 가는 경로를 만들 수 있다. 그러나 값을 가진 열을 DROP 한 뒤 다시 빈 열을 ADD 한다고 원래 값이 복원되지 않는다. 되돌릴 수 있는 변경과 복구 자료가 필요한 변경을 따로 적는다.

실제 배포에서는 구 버전 앱과 신 버전 앱이 잠시 함께 있을 수 있다. 새 열 추가→양쪽 호환→데이터 이행→구열 제거와 같은 자체 단계 전략을 설계할 수 있다. 원자적 DDL 지원여부·백업 복원·중간 실패 대응을 실제 확인하지 않았다면 성공 배포로 표시하지 않는다.

마지막 행은 실제 DB 성공 로그가 아니라 성공을 가정한 모델이다. name=NULL에서 nickname=별로 바꾸는 규칙은 이 과제에서 결정한 업무 정책이며 자동 도구가 의미를 찾아준 것은 아니다.

중간 과정을 따라가는 예제

자체 A 의 행 (id, name)=(1, 봄),(2, 달)이다. B 는 nickname nullable 추가, name 으로 채우기, NULL 없음 검사 후 NOT NULL 설정이다. C 는 nickname 삭제다. A→C 와 C→B 의구조 및 데이터를 추적하라. C→B 는 새 nullable 열만 복원한다고 가정한다.

  1. A→B 에서각기 nickname=NULL 인열을 만든 뒤봄/달로 채운다. NULL 개수는 0 이어서명시한 제약 검사를 통과한다.

  2. B 의 행은(1, 봄, 봄),(2, 달, 달)이다.

  3. C 에서 nickname 열과 값이 제거돼 원래 2 열만남는다.

  4. C→B 구조 복원만으로는 nickname=NULL/NULL 이다. 원래 봄/달 값과 NOT NULL 제약까지 자동 복원됐다고 말할 수 없다.

upgrade B 와 C 를 2 회적용한다. 삭제 뒤 빈 열 복원은 데이터 복구가 아니며 추가 이행/복구 설계가 필요하다.

조건을 바꾸어 비교하기

파일 이름보다 앞 버전 연결을 따라간다

자체 선형 이력은 A→B→C이고 down_revision이 그 순서를 지정한다. 파일명은 300_A.py, 100_B.py, 200_C.py다. 현재 DB A에서 C로 갈 순서는?

  1. 이름의 숫자 순서가 이력 연결을 대체하지 않는다.

  2. B의 앞 버전은 A, C의 앞 버전은 B다.

  3. 현재 A에서 B를 적용한 뒤 C를 적용한다.

B 다음 C, 두 변경을 적용한다. 실제 분기 이력에는 별도 경로 결정이 필요하다.

비교할 점

디렉터리 정렬과 변경 의존 관계를 같은 규칙으로 취급하지 않는다.

값 복원을 주장할 근거가 없다

열 nickname에 봄/별/달이 저장돼 있었다. 열을 DROP한 뒤 같은 이름의 nullable 열을 ADD했다. 다른 복구 자료가 없다.

  1. DROP 뒤 세 값을 읽을 열이 없다.

  2. ADD는 빈 열 구조를 만든다.

  3. 새 열의 NULL/NULL/NULL로 원래 값 복구를 주장하지 않는다.

구조 재생성만으로 데이터 복원이나 NOT NULL 보장을 얻지 못한다.

비교할 점

현재 다른 열에서 비슷한 값을 추측할 수 있다는 것과 과거 정확한 값 복원은 별개다.

지난 페이지의 마지막 줄 번호와 마지막 글의 정렬 키는 왜 다를까?

페이지를 넘기는 사이 앞의 행이 추가·삭제되면 순번이 움직인다. 자체 첫 정렬은 (time,id) 내림차순 [(10,50),(10,40),(9,30),(9,20)]이고 페이지 크기는 2다. 두 열은 NULL 없고 id는 유일하다. 각 요청은 새 snapshot을 읽는다.

키 cursor는 (10,40)보다 뒤라는 비교 조건이며 고정 페이지 번호가 아니다. 아래 결과는 새 snapshot과 정렬 키 변경을 명시한 종이 계산이다. 실제 SQL·PostgreSQL 격리·HTTP cursor 기능을 실행한 기록은 아니다.

먼저 확인할 개념
  • 목록 표시와 원본 상태

    현재 목록의 위치와 항목 id를 서로 다른 기준으로 쓴다.

  • 같은 요청과 의도 효과

    읽기·변경·재요청의 관찰 범위를 나누어 상태를 추적한다.

여러 변경을 하나의 결과로 묶는다

잔액 A50/B10 에서 20 을 보낼 때 A30 을 쓴 뒤 B30 을 써야 합 60 이 유지된다. 두 문장을 하나의 DB 트랜잭션에 넣으면 중간 실패 시 rollback 할 수 있다. 웹에서 두 요청을 보냈다는 사실만으로 하나의 DB 거래가 되지는 않는다.

원자성은 관련 변경의 확정 묶음이다. 읽기 격리는 동시 다른 거래의 변경을 어느 시점에 볼지 정한다. PostgreSQL Read Committed 에서 연속 SELECT 는 각 문장 시작 snapshot 을 쓰므로 같은 거래 안이라도 사이 다른 commit 을 다르게 볼 수 있다.

페이지의 순서를 완전히 고정한다

페이지는 전체 결과의 일부다. ORDER BY created_at DESC 만 쓰면 같은 시각의 행이 동점이다. id 까지 내림차순으로 붙여 유일 순서를 만들 수 있다. 정렬을 안 하면 현재 눈에 보이는 우연한 순서로 다음 페이지를 계산할 수 없다.

OFFSET2 LIMIT2 는 현재 정렬 결과에서 2 행을 건너뛴 뒤 2 행을 읽는다. 앞에 새 행이 삽입되면 그 위치가 밀려 지난 행이 두 번째 페이지에 다시 나올 수 있다. 유일 정렬은 한 snapshot 의 순서를 정할 뿐 페이지 사이 데이터를 고정하지 않는다.

마지막 키 뒤로 이동한다

cursor 방식은 마지막 행의 정렬 키를 기억해 그 키보다 뒤인 행을 읽는다. 내림차순 (created_at,id)의 마지막이 (9,40)이면 created_at<9 또는 (created_at=9 그리고 id<40)을 조건으로 사용한다. 두 열의 방향과 NULL 정책을 명시한다.

keyset 은 앞에 새 행이 추가되어도 지난 행을 위치만으로 다시 읽는 문제를 줄인다. 그러나 정렬 키가 수정되거나 행이 삭제될 수 있고 모든 페이지가 동일 snapshot 이라는 보장은 없다. Repeatable Read 를 유지하는 DB 거래의 범위와 HTTP cursor 의 수명은 다르다.

중간 과정을 따라가는 예제

자체 모든 created_at 이 10 이며 id 내림차순 [50,40,30,20]이다. 첫 페이지 LIMIT2 뒤 새 id60 이 commit 된다. 다음 페이지 OFFSET2/LIMIT2 와 cursor 조건 id<40/LIMIT2 를 계산하라. 키는불변이고각 요청은 새 snapshot 이다.

  1. 첫 페이지는[50,40], cursor40 이다.

  2. 삽입 뒤 새 순서는[60,50,40,30,20]이다.

조건을 바꾸어 비교하기

같은 시각에서도 id로 뒤를 정한다

cursor는 (9,40), 후보는 (9,50), (9,30), (8,80), (10,10)이다. 두 열 내림차순이고 NULL은 없다.

  1. time<9인 후보 또는 time=9이고 id<40인 후보를 고른다.

  2. (9,30),(8,80)을 선택한다.

  3. 선택된 두 행의 정렬은 (9,30) 다음 (8,80)이다.

포함 id는 30,80이다. id만 비교하면 뒤의 다른 시각 행을 잘못 빼거나 앞 행을 넣을 수 있다.

비교할 점

여러 열의 정렬 방향과 동점 조건을 논리식으로 연결한다.

거래 원자성과 연속 읽기 snapshot

잔액 A의 잔액 50 / B의 잔액 10을 한 거래에서 20을 이체해 A의 잔액 30 / B의 잔액 30으로 commit했다. 읽는 거래는 PostgreSQL Read Committed에서 일반 SELECT 두 번을 하고 이체 commit은 두 SELECT 사이에 끝났다. 다른 변경은 없다.

  1. 첫 SELECT는 이체 commit 전의 A의 잔액 50 / B의 잔액 10을 읽는다.

  2. 두 번째 SELECT는 commit 뒤의 A의 잔액 30 / B의 잔액 30을 읽는다.

  3. 같은 읽는 거래라도 문장마다 snapshot이 달라질 수 있다.

각 snapshot의 합은 60이며 두 결과가 다를 수 있다. 미확정 중간 A의 잔액 30 / B의 잔액 10을 읽는다는 결론은 아니다.

다른 문제에 적용하기

새 nickname 열이 nullable인 세 행 name=(봄,NULL,달)을 이행한다. 복사 뒤 NULL 검사를 하고 행 2의 결정된 값 별을 채운 뒤 NOT NULL을 적용한다는 자체 계획이다. 열을 나중에 삭제하고 빈 열만 다시 추가한 경우 원래 값의 복구 여부도 비교하라. 별도 요청에서 유효한 User7.name = 봄을 여름으로 바꾸고 flush 뒤 rollback했다. 다른 writer 없이 새 거래에서 읽는 이름과 성공 안내 시점을 판단하라. 마지막으로 첫 feed 페이지 id [50,40] 뒤 새 (11,60)이 추가됐다. 다음 offset2/cursor(10,40) 결과와 이때의 snapshot 보장 범위를 설명하라.

힌트 1

구조·값·제약을 세 칸으로 적고 NULL 개수를 센다. ORM의 flush/commit/rollback을 다른 경계로 둔다.

힌트 2

feed 순서는 앞에 60이 추가됐지만 cursor는 위치 2가 아니라 키 조건이다.

풀이와 답 확인

  1. 복사 뒤 nickname은 봄/NULL/달, NULL이 1행이므로 중단한다. 별을 채운 뒤 0행을 재검사하고 제약 적용 성공을 가정한다.

  2. 삭제 후 ADD만 하면 NULL/NULL/NULL로 원래 봄/별/달의 복구가 아니다. 복구 자료와 실제 시험이 필요하다.

  3. flush는 열린 거래의 여름 변경이며 rollback 뒤 새 재조회는 봄이다. flush 직후 영구 성공 안내는 시점이 잘못됐다.

  4. 새 feed 순서는 60/50/40/30/20, offset2는 40/30, cursor 뒤는 30/20이다.

  5. 키 불변·새 snapshot이라는 모형이며 전체 HTTP 페이지의 고정 snapshot을 증명하지 않는다. 실제 ORM/DDL/DB 격리/학생 시험은 미수행이다.

NULL 1행 → 정책에 따른 채움 → NULL 0행 검사, 빈 열 복원≠과거 값 복구, rollback 뒤 봄, offset[40,30]/cursor[30,20]이다.
