소단원 2.1

문서와 semantic 요소

굵고 큰 글씨를 제목처럼 보여 주면 문서에도 제목이 생긴 것일까?

준비 개념과 학습 목표

준비 개념

  • HTML은 문서의 구조와 의미를 나타내는 텍스트 표기다. <h1>과 </h1>처럼 시작·끝 태그가 요소를 감싸며, 속성은 lang="ko"처럼 추가 정보를 붙인다.

  • 부모 요소는 안에 자식 요소를 담는다. DOM은 브라우저가 해석한 문서 객체 구조이며 원본 문자열과 개념이 다르다. CSS는 주로 표현을 조정하고 HTML의 의미를 자동으로 대신하지 않는다.

학습 목표

  • 문서 계층과 화면 모양을 구별한다.

  • main/nav/article/section/heading을 콘텐츠 목적에 맞게 선택한다.

  • 예제의 구조와 fragment 대상 연결을 추적한다.

같은 색의 상자가 세 개 있어도, 문서에서는 서로 다른 역할일까?

신문을 읽을 때 기사 제목과 광고 제목을 글자 크기만으로 판단하지 않는다. 문서의 관계와 목적을 먼저 본다. HTML에서도 독립된 기사, 기사 속 주제, 색을 칠할 상자를 각각 판단해야 한다. 아래의 메뉴와 우주 관찰 기록은 자체 가상 콘텐츠다.

“별자리 관찰 기록” 전체를 하나의 독립 글로 나누어 배포할 수 있고, 그 안의 “준비”와 “관찰 결과”는 하위 주제라고 정하자. 본문 제목을 h1, 두 하위 제목을 h2로 계획한다. 배경색만 주는 바깥 상자는 제목 계층에 새 주제를 추가하지 않는다. 표의 선택은 이 콘텐츠 조건에 대한 설계안이며 모든 웹사이트를 같은 구조로 강제하는 규칙은 아니다.

먼저 확인할 개념
  • 입력·처리·출력의 구분

    HTML 문자열과 이를 해석한 구조, 표시 결과를 서로 다른 단계로 읽는다.

  • 다운로드와 실행 관찰

    소스의 의도와 실제 브라우저 관찰이 다른 증거임을 기억한다.

문서는 읽을 순서와 의미를 갖는다

HTML을 그림 배치 명령으로만 보면 큰 글씨·상자 모양을 고르는 데서 멈추기 쉽다. 문서는 제목, 본문, 목록, 링크처럼 정보의 관계도 전달한다. h1은 제목 계층을, ul/li는 목록을 나타낸다. p를 크게 꾸몄다고 h1의 의미가 생기지 않는다. 반대로 h1을 작게 보이도록 꾸며도 요소의 제목 의미를 없애는 것은 아니다.

예제는 UTF-8 한국어 문서이며 lang="ko"는 주된 언어를 알린다. title은 문서 제목으로, 본문 h1은 읽는 콘텐츠의 제목으로 사용한다. 둘을 알맞게 쓰되 동일 역할이라고 혼동하지 않는다. 잘못된 중첩을 브라우저가 복구할 수 있어도 의도한 구조가 그대로 만들어진다는 보장은 없으므로 맞는 구조로 작성한다.

의미에 맞는 영역 선택

main은 이 페이지의 주된 콘텐츠, nav는 주요 탐색 링크 묶음이다. 독립적으로 재사용할 수 있는 강의 안내 전체를 article로 묶고, 목표·준비물 같은 주제별 묶음을 section으로 나눴다. 제목 h1 아래 두 h2가 같은 수준의 주제를 나타낸다. 모든 링크 집합이 반드시 nav일 필요는 없고, 모든 박스가 article일 필요도 없다.

시각적인 간격이나 JavaScript 묶음만 필요하면 div 같은 일반 컨테이너를 사용할 수 있다. section은 의미 있는 주제 묶음을 위해 고른다. header/footer의 문맥은 위치에 따라 달라질 수 있으며 모든 header가 페이지 전체의 동일 landmark라고 일반화하지 않는다. 예제는 페이지 수준의 header/footer와 하나의 main으로 단순화했다.

소스·파싱·표현을 분리해 확인하기

문서의 예상 계층은 body 아래 header,nav,main,footer이고 main 아래 article, 그 아래 제목과 두 section이다. href="#goals"는 같은 문서의 id="goals" 대상을 가리킨다. 이는 서버에 새 fragment 문자열을 보내는 규칙이 아니며 첫 단원의 URL 조건과 연결된다. 실제 스크롤·focus 동작은 브라우저 구현과 대상 조건을 확인해야 한다.

의미 요소는 접근성 정보의 기반이지만 그것만으로 완전한 접근성을 보장하지 않는다. 제목 설명의 명확함·링크 목적·focus 표시·콘텐츠 순서를 함께 검토해야 한다. 여기서는 소스를 따라 구조를 읽는 종이 활동이며 실제 렌더링·보조기술의 읽기 결과는 관찰하지 않았다.

독립 글과 모양 상자를 나눈다

  1. 새 묶음이 교재 차례의 주제인지 묻는다.

  2. 목적은 둥근 배경을 적용할 컨테이너뿐이다.

  3. 이 조건이면 div를 고르고 article의 내용 의미는 유지한다.

연습 1 · 값과 상태 예측

h1 관찰 기록 아래 준비 h2, 도구 h3, 결과 h2 순서가 있다. 도구가 속한 주제와 결과의 수준을 설명하라.

힌트 1

제목 수준을 들여쓰기로 옮긴다.

힌트 2

낮은 하위 묶음에서 상위 수준으로 돌아오는 경우를 본다.

풀이와 답 확인

  1. 준비 h2 안에 도구 h3를 들여쓴다.

  2. 결과 h2는 준비와 같은 수준의 새 주제다.

도구는 준비의 하위 주제이고 결과는 준비의 형제 주제다.

흔한 오답에서 다시 생각하기

h3 뒤에는 언제나 h4만 와야 한다.

하위 주제를 끝내고 상위 주제로 돌아갈 수 있다. 이 경우 h2 복귀는 새 하위 수준을 건너뛰는 것과 다르다.

연습 2 · 오류 찾아 고치기

제목 “실험 결과”가 p 요소인데 CSS로 크게 보인다. 제목 목록에서 찾기 쉽게 만들려면 무엇을 고치고 무엇을 유지할 수 있는가?

힌트 1

현재 요소가 제목 의미를 갖는지 본다.

힌트 2

계층 수준과 글씨 크기를 다른 선택으로 둔다.

풀이와 답 확인

  1. 문맥상 결과는 실험 h1의 하위 주제라고 정한다.

  2. p를 h2로 바꾸고 필요한 표현은 CSS로 정한다.

적절한 제목 요소와 명확한 제목 내용으로 수정한다. 크기 조정은 별도다.

굵게 표시됐으므로 제목 의미도 이미 있다.

보이는 속성과 문서에서 전달하는 역할을 나누어 적어라.

“빵 굽기” 문서에 재료와 순서라는 두 주제, 재료 세 개, 순서 세 단계가 있다. 요소와 계층을 글로 설계하라.

힌트 1

순서를 바꾸면 뜻이 달라지는 목록을 찾는다.

힌트 2

전체 문서와 그 안의 두 주제 수준을 구별한다.

풀이와 답 확인

  1. 독립 레시피를 article 후보로 두고 빵 굽기를 h1로 둔다.

  2. 재료와 순서는 각각 h2를 가진 section 후보로 둔다.

  3. 재료 세 항목은 ul/li, 단계 세 항목은 ol/li로 정한다.

독립 글·두 하위 주제·순서 있는 목록과 없는 목록을 구별한 설계면 된다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

한 과목 소개 페이지의 제목들을 모았더니 “소개”, “설명”, “기타”만 있다. 요소 수준은 맞지만 탐색 목적이 모호하다. 내용을 바탕으로 더 나은 제목 후보와 확인 계획을 적어라.

힌트 1

제목만 읽고 다음 내용의 질문을 예상할 수 있는지 본다.

힌트 2

글자 수를 늘리는 것보다 구체적인 목적이 중요하다.

풀이와 답 확인

  1. 실제 묶음 내용이 목표, 준비물, 신청 조건이라고 가정한다.

  2. “배우는 내용”, “시작 전에 준비할 것”, “신청 조건” 같은 후보를 만든다.

  3. 제목만으로 내용 위치를 찾을 수 있는지 관찰할 계획을 적는다.

소단원 2.2

폼과 검증

인원 입력칸이 1~3만 받으면 서버도 잘못된 인원을 받을 수 없는 것일까?

준비 개념과 학습 목표

준비 개념

  • 폼은 여러 control의 값을 제출하는 구조다. id는 문서 안 연결 대상, name은 제출 데이터의 키이며 둘은 같은 역할이 아니다. 여기서 입력값은 control의 현재 값이다. 이 예의 text/number input에서 DOM의 .value는 현재 값을 읽고, HTML에 적는 value 속성은 기본값을 지정한다. 사용자가 편집한 현재 값과 기본값은 다를 수 있다.

  • 검증은 허용 형식·범위·업무 조건을 판정한다. 브라우저의 client 검증과 서버의 신뢰 경계 검증은 서로 다른 위치에서 수행한다.

학습 목표

  • label/id와 제출 name/value를 구별한다.

  • required·min/max·step의 의미를 주어진 값에 적용한다.

  • 클라이언트 제약을 우회하는 입력에도 서버 검증이 필요한 이유를 설명한다.

화면에서 고른 과목 두 개가 서버에 도착할 때 하나의 값으로 합쳐질까?

설문지의 같은 질문에서 선택을 두 개 표시하는 상황을 생각하자. 전송 항목도 이름 하나가 값 여러 개와 짝지어질 수 있다. 화면 위치, label 연결, 제출 항목 이름은 다른 역할을 맡는다. 아래는 실제 신청 서비스 없이 entry list를 종이에 만드는 활동이다.

기본 인원 폼에서 나아가, 체크된 과목만 제출하는 목록과 step의 기준을 바꿔 본다. 수정되지 않은 유효한 정적 HTML, 명시된 현재 값, form 관련 이벤트로 값을 바꾸지 않는 조건을 가정한다. 이름·현재 값·체크 여부·disabled를 각각 표에 적고 포함 여부를 판정한다.

먼저 확인할 개념
  • 문서 구조와 연결 관계

    요소 관계를 화면 위치와 구별하여 label과 input 연결을 찾는다.

  • 요청 대상과 응답

    제출 항목 구성과 실제 서버 응답을 같은 성공 단계로 취급하지 않는다.

입력 목적과 연결을 명시하기

label의 for="count"는 input의 id="count"와 연결된다. label은 입력 목적을 보여 주며 설명 count-help는 aria-describedby로 추가 연결한다. placeholder만 두고 목적 설명을 없애면 입력 후 안내가 사라질 수 있어 충분한 대체가 아니다. 예제에는 목적과 허용 범위를 항상 읽을 수 있게 두었다.

name="count"는 제출 항목 이름이다. id만 있고 name이 없는 일반 텍스트 입력은 이 예의 제출 데이터에 포함되지 않는다. disabled control도 제출 항목 구성에서 제외된다. 사용자 편집 가능성·검증 대상·전송 항목은 구별해야 한다. 동일 name의 여러 값도 가능하므로 서버가 항상 키 하나당 값 하나만 온다고 가정해서는 안 된다.

브라우저 제약은 무엇을 뜻하는가

number는 수량처럼 숫자 연산 의미가 있는 입력에 사용한다. required는 빈 값을 허용하지 않으며 min=1,max=3은 범위, step=1은 여기서 기준 1부터 정수 간격을 정한다. 파싱 가능한 값 1,2,3은 조건에 맞고 0은 최소 위반,4는 최대 위반,2.5는 step 위반이다. 문자 입력의 처리 UI와 오류 문구는 브라우저마다 달라질 수 있어 고정하지 않는다.

정상 사용자 제출 경로에서 검증이 활성화된 conforming browser를 가정한다. novalidate 같은 우회 설정이나 validation을 거치지 않는 호출·직접 HTTP 요청은 별도다. 숫자처럼 보이는 우편번호나 회원ID는 선행 0과 식별 의미가 중요할 수 있어 number를 자동 선택하지 않는다. 예제의 인원 수와 식별자를 분리한다.

서버가 다시 검사하고 결과를 설명하기

method="post"와 기본 encoding의 이 단순 폼은 제출 항목을 요청 본문에 인코딩하도록 정한다. POST 자체가 암호화나 저장 성공을 보장하지는 않는다. action="/enroll"은 설명용 경로로 실제 서버를 구현하거나 요청하지 않았다. 브라우저 검증 성공은 사용자가 올바른 값을 입력하도록 돕는 조건이지 공격자가 같은 경로로만 요청한다는 근거가 아니다.

서버는 count 항목의 개수·허용 숫자 형식·정수성·범위를 재검사하고, 남은 좌석과 권한 같은 업무 조건도 검사해야 한다. 폼이 3까지 허용해도 잔여 좌석 1이면 신청 3을 거절할 수 있다. 오류는 어느 필드에서 무엇을 고칠지 텍스트로 알리고 기존 입력을 보존하는 설계가 필요하다. 같은 입력을 다시 제출했을 때 중복 처리·원자 저장은 다음 API 계약으로 연결한다.

접근 가능한 구조

마우스 없이 읽어도 제목과 링크 목적을 구별하고 본문으로 이동할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 키보드 focus는 현재 키 입력을 받을 요소를 가리키는 상태다. 선택 표시나 마우스 위치와 같지 않다. DOM 순서는 파싱한 문서 객체 트리의 순서이며 원본 문자열 자체의 순서와 동일한 개념은 아니다. 이 예제처럼 단순하고 올바르게 중첩된 정적 문서에서는 소스를 따라 의도한 요소 순서를 읽을 수 있다. CSS 화면 배치와는 달라질 수 있다.

  • 보조기술은 의미·이름·관계를 사용해 콘텐츠를 전달할 수 있다. 접근성은 여러 환경의 사용자에게 기능과 정보를 이용 가능하게 만드는 목표이며 태그 하나의 존재로 판정하지 않는다.

학습 목표

  • 제목·영역·링크 이름으로 구조를 읽는다.

  • 기본 HTML 상호작용과 focus의 역할을 설명한다.

  • 정적 검사와 실제 키보드·보조기술·사용자 시험의 증거를 구별한다.

버튼의 이름이 맞으면, 실제로 그 행동을 끝낼 수 있다는 뜻일까?

엘리베이터 버튼에 층수가 쓰여 있다는 사실과 실제로 그 층에 도착한다는 결과를 나누어 생각하자. 웹에서도 역할·이름·입력 방식·관찰 결과를 각각 확인한다. “선택 초기화”라는 버튼 이름만 있고 로직이 없다면 기능을 완료한 것이 아니다.

이번 활동은 가상 점검 기록을 분류하는 이론 연습이다. HTML 정적 연결, 키보드 조작, 보조기술 정보, 실제 사용자 경험을 서로 다른 증거로 적는다. 원고를 쓴 사람이 실제로 학습자 관찰이나 전체 접근성 평가를 수행했다고 표시하지 않는다.

먼저 확인할 개념
  • 의미 있는 요소와 제목

    제목 계층과 영역의 의미를 기능 점검표의 첫 칸으로 연결한다.

  • 입력 목적과 값의 계약

    입력 이름·설명과 검증 결과를 사용자에게 전달해야 한다.

구조와 이름으로 탐색 가능하게 하기

주 제목 h1과 하위 h2는 콘텐츠의 논리 관계를 나타낸다. 제목 단계를 불필요하게 건너뛰지 않고 내용에 맞는 수준을 선택한다. 시각적으로 작게 보이고 싶다는 이유로 h4를 고르는 것은 의미 계층과 모양을 혼동한다. nav의 이름은 여러 탐색 영역을 구별하는 데 도움을 주며 main은 본문의 영역을 나타낸다.

링크 텍스트 "강의 이용 안내 읽기"는 "여기"보다 목적이 분명하다. 같은 이름의 서로 다른 행동이 반복되면 주변 문맥 없이 구별하기 어렵다. 사진·도표가 추가된다면 목적에 맞는 대체 텍스트도 필요하지만 이번 작은 문서는 이미지를 쓰지 않는다. 언어·제목·의미 있는 목록과 영역은 서로 보완한다.

기본 동작을 먼저 사용하고 focus를 보이게 하기

이동에는 href가 있는 a, 동작에는 button을 사용한다. div에 click handler만 붙이면 키보드 활성화·focus·역할·이름을 추가 설계해야 한다. native 요소도 기능 자체를 구현해 주는 것은 아니다. 예제의 초기화 버튼은 역할과 이름만 갖고 초기화 로직은 없어 실제 기능 완료라고 부를 수 없다.

양의 tabindex로 순서를 억지 재배열하면 문서 읽기 순서와 키보드 순서가 갈라질 수 있다. 예제의 main tabindex=-1은 일반 Tab 순서에 추가하지 않되 focus 대상으로 삼을 수 있게 둔 것이다. 첫 skip 링크는 본문 ID를 대상으로 한다. focus-visible 스타일은 선택 위치를 표시하려는 설계이며 실제 기기에서 표시·이동이 적절한지는 시험해야 한다. 음의 tabindex는 일반 순차 탐색에서 제외하려는 저자의 의도를 나타내지만 사용자 에이전트는 플랫폼 관례나 키보드만 쓰는 사용자를 위해 그 선호를 무시할 수 있다. 아래 종이 예제는 이 예외가 적용되지 않는 일반 순차 탐색을 가정한다.

증거의 수준을 구별하기

소스에서 id 중복·label 연결·제목 계층·link/button 역할을 확인할 수 있다. 정적 검사로 빠진 관계 일부를 찾을 수 있지만 실제 keyboard trap·동적 갱신 안내·화면 확대·contrast·보조기술 이름을 전부 보장하지는 않는다. 브라우저와 운영체제·보조기술 버전 및 입력 방식이 결과에 영향을 줄 수 있다.

종이 활동에서는 문서 순서와 의도한 순서를 비교하고 기능 미구현을 발견한다. 실제 시험 단계에는 키보드만으로 기능 완료, 확대 및 reflow, focus 가시성, 스크린리더의 이름·역할·오류 안내를 기록해야 한다. 그 결과와 학습자·장애 사용자 피드백은 또 별개 증거다. 이번 집필에서 이 시험들을 수행하거나 WCAG 전체 적합성을 인증하지 않았다.

중간 과정을 따라가는 예제

예제의 제목·영역·focus 가능한 기본 요소를 소스에서 찾아라. 표시된 버튼이 동작을 완성했는지도 판단하라. 일반 native 순차 focus를 문서 순서로 따르는 환경을 이론 가정한다.

  1. 제목은 열린 강의 목록 h1과 신청 안내 h2다. nav는 과목이라는 이름을 갖고 main의 ID는 main이다.

  2. 문서의 링크 순서는 본문으로 이동,Python,웹,강의 이용 안내 읽기이며 이후 버튼 선택 초기화가 있다.

  3. main은 tabindex=-1이므로 일반 Tab 순서에는 추가되지 않는다. skip 링크의 대상 역할과 일반 Tab 정류장을 구별한다.

  4. 버튼은 type=button이므로 form 제출 버튼이 아니며 handler도 없다. 초기화 기능은 미구현이다. 실제 Tab·스크린리더 이동은 관찰하지 않았다.

소스로 확인 가능한 의도는 제목 계층·이름 있는 탐색·skip 대상·native control이다. 기능 완료 및 실제 접근성은 별도 시험이 필요하다.

링크를 목적별 "강의 안내 읽기"·"신청 조건 읽기"·"도움말 읽기"로 바꾼다. 신청 동작은 button과 실제 handler/오류 처리로 구현하고 native 키보드 동작을 유지한다. outline 제거 뒤 대체 focus 표시가 있는지 실제 키보드 환경에서 검사해야 한다. 문구와 요소 개선만으로 기능 시험을 마쳤다고 하지 않는다.

오해와 반례

ARIA role을 붙이면 기본 요소 선택이나 키보드 코드를 고민할 필요가 없다.

div에 role="button"만 붙여도 자동으로 키보드 focus와 Enter/Space 동작이 모두 생기는 것은 아니다. 기본 button을 쓰는 것이 필요한 역할과 기본 동작을 함께 제공하기 쉽다. ARIA는 의미 전달이며 기능 구현과 시험을 대체하지 않는다.

    공식 본문 explicit/implicit label과 control purpose를 실제 읽었다. for와 id 연결 및 버튼의 label 관계를 확인했다. 자체 폼을 보조기술로 실행한 기록은 없다.

    공식 본문의 required/입력 형식 안내 및 사용자 오류 식별·피드백 설명을 실제 읽었다. 클라이언트 경험과 서버 검증을 구별하며 실제 사용자 시험을 한 것으로 표시하지 않는다.

  • WHATWG HTML Living Standard — The tabindex attribute

    독립 검토자가 음의 tabindex의 focus 가능성과 일반 순차 탐색 제외 의도, 사용자 에이전트가 플랫폼/키보드 전용 사용자에 따라 선호를 무시할 수 있는 본문을 실제 읽었다. 실제 Tab 동작은 미시험.

  • W3C WAI APG — Button Pattern

    독립 검토자가 button과 link의 행동 구분, 키보드 Enter/Space, 이름/role/description 요구를 실제 읽었다. role 지정만으로 구현을 완료했다는 주장은 없으며 예제 실제 동작은 미시험.

  • WHATWG DOM Standard — Trees

    독립 검토자가 tree order의 preorder depth-first 및 parent/ordered children 정의를 실제 읽었다. 소스 문자열과 DOM 구조를 구분하는 설명을 보완했다.

다른 문제에 적용하기

가상 별 관찰 신청 페이지를 종이로 설계하라. 독립 안내 글에 준비·신청 조건 두 주제가 있다. 두 과목 선택은 각각 고유 id/label과 같은 name=topic을 가진 체크박스이며 value=sky, value=moon이다. 두 항목을 모두 체크했고 정수 인원은 min=2,max=8,step=2,required인 number 입력의 현재 값 6이다. 서버의 잔여 좌석은 4라고 정했다. 문서 계층, 제출 목록, 브라우저 제약, 업무 승인, 키보드 점검 계획을 구별하여 적어라. 실제 요청은 보내지 않는다.
