소단원 9.1

암호저장

서비스는 로그인 암호를 어떻게 확인하면서 원래 문자열을 보관하지 않을까?

준비 개념과 학습 목표

준비 개념

  • 문자열

  • 함수와 비교

학습 목표

  • 암호 전용 해시와 일반 빠른 해시를 구별한다.

  • salt·비밀·비용 설정의 역할을 설명한다.

자물쇠 확인표를 새 방식으로 바꾸려면 이전 확인표만 다시 계산하면 될까?

해시 레코드는 암호를 복구하는 보관함이 아니다. 자체 로그인 계획에서 verify(후보, 기존 레코드)가 성공한 때에만 그 후보를 현재 암호라고 확인한다. 이때 최신 정책으로 새 레코드를 만들 수 있다. 저장 문자열을 후보 대신 다시 해시하면 사용자가 입력하는 원래 암호와 다른 입력을 처리한다.

아래 표의 구/신 표시는 특정 라이브러리 설정이 아니라 정책 구분이다. 실제 암호 함수·서버 부하·비밀 저장소는 실행하지 않았다. 무작위 salt와 별도 pepper, 알고리즘 설정과 로그인 시도 제한을 서로 다른 조건으로 그리자.

먼저 확인할 개념
  • 암호 검증과 사용자 식별

    성공한 검증을 뒤의 사용자 식별 단계와 연결한다.

  • 저장 확정과 응답 실패

    새 레코드 계산과 DB에 확정된 레코드를 다른 사건으로 기록한다.

검증용 값과 복원용 값을 구별한다

로그인 서비스는 암호를 다시 보여 줄 필요보다 제출한 후보가 맞는지 확인할 필요가 있다. 검증된 라이브러리의 암호 전용 해시를 저장하고 verify 연산을 쓴다. 암호화는 키로 원문 복원이 가능한 다른 요구이며 평문이나 빠른 SHA-256 한 번을 암호 저장 설계로 쓰지 않는다.

salt는 사용자별 계산을 나눈다

무작위의 서로 다른 salt는 같은 후보 암호에 대해서도 사용자마다 별도 계산이 필요하게 한다. salt는 비밀 키가 아니며 저장한 해시와 함께 보관할 수 있다. pepper를 쓴다면 DB와 분리한 비밀 관리가 추가로 필요하다. salt 자체가 짧고 예측 가능한 암호를 강하게 바꾸지는 않는다.

비용은 운영 조건과 함께 설정한다

Argon2id 같은 적응형 함수에는 메모리·반복 비용이 있다. 공식 최소 구성과 현재 라이브러리를 확인하고 실제 서버에서 지연·부하를 측정해야 한다. 알고리즘·설정·salt 정보도 보존해 로그인 시 갱신할 수 있게 한다. 아래 단위는 해시 함수의 실제 속도가 아니라 종이 작업량이다.

원래 후보의 정상 재해시와 다름

성공 판단과 저장 성공은 별도다. 정책 갱신을 요구해 새 저장이 실패했다면 실제 상태와 로그인 허용 여부는 서비스의 실패 정책으로 정해야 한다. 이 표는 그 실패를 자동 성공으로 취급하지 않는다.

중간 과정을 따라가는 예제

서로 다른 salt의 검증 레코드가 3 개다. 자체 모델에서 후보 하나와 레코드 하나의 계산은 5 작업 단위다. 두 후보를 세 레코드 모두에 비교하면 작업량은? 병렬·조기 종료는 없다.

  1. 후보/레코드 쌍은 2×3=6 개다.

  2. 각 쌍의 salt를 반영한 별도 계산을 하므로 6×5=30 단위다.

  3. 암호의 추측 성공 여부나 실제 초 단위 속도는 이 조건으로 알 수 없다.

30 작업 단위다. salt는 공통 후보 계산 하나로 전 레코드를 비교하는 지름길을 줄인다.

조건을 바꾸어 비교하기

맞지 않는 후보로 갱신하지 않기

기존 레코드가 구 정책이다. 후보 A의 verify는 False, 후보 B는 True라고 주어진다. 두 요청은 각각 별도이며 다른 변경은 없다. 어떤 후보가 정상 갱신 입력인가?

  1. A는 기존 암호와 일치하지 않아 현재 암호로 확인되지 않았다.

  2. B는 verify 성공으로 현재 암호를 확인했다.

  3. 갱신은 B를 최신 정책의 입력으로 쓰며 salt 관리는 검증된 라이브러리 계약을 따른다.

B만 정상 갱신 입력이다. 새 레코드의 DB 확정 여부는 별도로 확인한다.

비교할 점

알고리즘 이름이 오래됐다는 사실과 제출 후보의 정당성을 같은 판단으로 취급하지 않는다.

서버 동시 로그인 비용은 종이 예산

자체 예산 모형에서 작업 한 개가 메모리 20 MiB를 계속 점유하고 동시에 8개가 실행된다. 다른 소비를 무시한 작업 메모리와, 허용 예산 120 MiB 안의 최대 동시 개수는?

  1. 8×20=160 MiB다.

  2. 120÷20=6이므로 이 모형의 최대 개수는 6이다.

  3. 실제 Argon2id 메모리 설정·런타임 부가 메모리·큐 대기·지연은 별도 측정이 필요하다.

160 MiB와 6개다. 실제 서비스 용량이나 권장 파라미터를 측정한 값은 아니다.

비교할 점

암호 하나의 비용을 올리는 것과 동시에 여러 요청을 감당하는 것을 서로 다른 축으로 계산한다.

한 후보씩 다시 계산해 비교하는 공격은 여전히 가능하다. salt·비용·암호 품질과 온라인 시도 제한은 다른 방어 요소다.

연습 1 · 값과 상태 예측

같은 암호를 쓰는 두 사용자에게 서로 다른 salt를 쓴다. 저장 문자열이 다르다는 이유만으로 두 사용자의 암호도 반드시 다르다고 판단할 수 있는가?

힌트 1

암호 외 입력을 확인한다.

힌트 2

비교할 후보를 사용자별 salt와 함께 검증한다.

풀이와 답 확인

  1. salt가 다르므로 같은 후보도 다른 레코드 계산에 쓰인다.

  2. 서로 다른 저장값을 평문 암호의 서로 다름 증명으로 해석하지 않는다.

저장값의 차이만으로 원래 암호가 다르다고 결론 내릴 수 없다.

흔한 오답에서 다시 생각하기

해시 문자열이 다르면 입력 암호도 항상 다르다.

사용자별 salt와 알고리즘 설정도 입력 조건이다.

연습 2 · 오류 찾아 고치기

로그인 후보가 실패했지만 개발자가 정책 갱신이라며 그 후보를 최신 방식으로 저장했다. 이후 진짜 사용자가 로그인하지 못한다. 어느 판단을 먼저 고쳐야 하는가?

힌트 1

정책 낡음과 후보 일치를 분리한다.

힌트 2

실패한 후보를 현재 암호로 인정했는지 본다.

풀이와 답 확인

  1. verify 성공 여부를 먼저 확인한다.

  2. 실패 후보는 기존 레코드를 대체하지 않는다.

  3. 성공 후보의 갱신도 실제 저장 성공과 별도로 기록한다.

실패 후보로 계정 암호를 바꾸는 경로를 제거한다.

흔한 오답에서 다시 생각하기

비용이 높아졌으니 잘못된 후보도 안전하다.

비용은 추측 계산 부담이며 후보의 정당성 검사가 아니다.

연습 3 · 직접 만들어 보기

원래 암호나 pepper를 공개 로그에 남기지 않고 갱신 성공을 관찰할 항목을 설계하라. 자체 모형은 비밀값을 제외하고 이벤트 ID·정책 이름 구/신·검증 결과·변경 필요 여부·새 레코드 저장 결과의 상태 항목을 허용한다.

힌트 1

정책 변화와 비밀값을 나눈다.

힌트 2

계산 완료와 저장 확정도 구분한다.

풀이와 답 확인

  1. 이벤트 ID, 검증 성공/실패, 정책 변경 필요 여부를 기록한다.

  2. 새 레코드 저장 확정/실패를 별도 결과로 둔다.

  3. 평문 후보·pepper·전체 세션 ID를 기록 항목에 넣지 않는다.

정책 전환의 상태를 관찰하되 인증 비밀을 로그로 복제하지 않는다. 실제 로깅 시험은 미수행이다.

문제 재현을 위해 모든 후보와 비밀을 로그에 저장한다.

상태 증거와 인증 비밀 노출을 같은 요구로 취급하지 마라.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

힌트 1

힌트 2

풀이와 답 확인

  2. 나머지는 기존 레코드이며 별도 만료·재설정 정책이 필요할 수 있다.

로그인 기반 이행만으로 미접속 계정의 완료를 주장하지 않는다.

도서관 출입표를 새로 받았는데 이전 표도 계속 통하면 무엇이 바뀐 걸까?

자체 서버 표에서 a는 익명 세션, 로그인 후 b는 민의 세션이다. 로그인 시 b를 발급하면서 a를 민으로 바꾸어 계속 허용하지 않는다고 정한다. 문자 a/b는 실제 비밀이 아니라 흐름을 보여 주는 표식이다. ID는 검증된 프레임워크의 예측 불가능한 값이어야 한다.

브라우저 쿠키 저장, 요청에 표식 전달, 서버의 유효 세션 조회를 세 사건으로 나눈다. HttpOnly는 문서 스크립트의 직접 읽기를 막는 속성이고 요청 수행 자체를 막는 속성이 아니다. 아래는 동일 호스트 HTTPS 요청 모형이며 실제 브라우저·서버·공격 실험을 수행하지 않았다.

먼저 확인할 개념
  • HTTP 요청과 응답 경계

    Set-Cookie 응답과 Cookie 요청을 다른 방향으로 읽는다.

  • 후속 요청의 상태 갱신

    화면의 로그인 표시와 서버의 실제 유효 상태를 나눈다.

쿠키는 전달 수단이다

브라우저가 응답의 Set-Cookie를 저장하고 조건에 맞는 요청에 Cookie를 보낸다. 이 소단원은 불투명한 세션 ID를 쿠키에 넣고 사용자·상태는 서버의 레코드에서 찾는 모델이다. 모든 쿠키가 로그인 세션은 아니며 쿠키 자체에 암호를 넣을 필요도 없다.

표식의 보호는 여러 조건이다

Secure는 HTTPS 전달을, HttpOnly는 DOM 스크립트의 쿠키 읽기 차단을, SameSite는 사이트 간 전달 조건을 다룬다. HttpOnly여도 브라우저는 요청에 쿠키를 보낼 수 있어 XSS로 수행되는 모든 작업을 막지는 않는다. SameSite도 별도 CSRF 방어를 대체한다고 단정하지 않는다.

서버 상태를 종료해야 한다

로그인이나 권한 상승 때 세션 ID를 갱신하고 이전 ID의 유효성을 관리한다. 로그아웃은 브라우저 표식 정리와 서버 레코드 무효화를 연결한다. 탭·브라우저 닫힘을 유일 종료 신호로 믿지 않는다. 아래 sA/sB는 표시용 이름이며 실제 ID는 예측 불가능하게 생성한다.

  1. 표에서 sA를 찾으면 민이라는 결과를 얻는다.

  2. 로그아웃으로 sA의 서버 레코드를 무효화한다.

  3. 이후 같은 쿠키가 도착해도 유효 레코드가 없어 로그인 세션으로 받아들이지 않는다.

처음에는 민의 세션, 로그아웃 후에는 무효다. 쿠키 보유와 유효 세션은 다르다.

HttpOnly를 읽지 못해도 요청은 가능하다

같은 출처의 스크립트가 실행 중이고 sid에 HttpOnly가 있다. 스크립트는 document.cookie로 sid 값을 읽지 못한다. 허용 조건의 같은 출처 요청을 실행할 때 세션 전달 가능성도 없다고 결론내려도 되는가?

  1. 직접 값을 읽는 동작과 브라우저가 요청에 붙이는 동작을 나눈다.

  2. HttpOnly 쿠키도 JavaScript가 시작한 요청에 전달될 수 있다.

  3. 서버 권한 검사·XSS 예방·CSRF 정책은 별도다.

직접 읽기 차단만으로 모든 세션 요청을 불가능하다고 결론 낼 수 없다. 실제 XSS 실행은 하지 않았다.

소단원 9.3

접근권한과 만료

로그인했으면 다른 사람의 모든 문서도 읽어도 될까?

준비 개념과 학습 목표

준비 개념

  • 인증

  • 논리 AND

학습 목표

  • 인증과 자원별 권한 검사를 구별한다.

  • idle·absolute 만료 경계를 계산한다.

출입증이 살아 있고 문서가 보이면 수정도 할 수 있을까?

자체 정책에서 민은 문서 d1의 소유자로 읽기·수정이 가능하고, 서는 그 문서의 공유 독자로 읽기만 가능하다. d2는 서의 비공개 문서다. 서버가 보관한 관계와 요청 작업을 함께 판단한다. 요청자가 owner=민이라고 보내도 그 문자열이 서버 관계를 바꾸지는 않는다.

시간은 모두 서버의 같은 분 단위 시계다. 유효 조건은 t−last<5 그리고 t−created<20이며 경계와 같으면 만료다. 이 단원의 추가 정책은 성공한 보호 요청만 last를 갱신한다. 거부 요청이나 상태만 확인하는 poll은 갱신하지 않는다. 이는 모든 서비스의 표준 시간값이 아닌 자체 계약이다.

먼저 확인할 개념
  • 서버 입력 검사와 권한 검사

    형식이 올바른 요청도 자원 권한에서 실패할 수 있다.

  • DB에서 확정된 소유 관계

    요청자가 보낸 이름과 서버 저장 관계를 다른 신뢰 근거로 둔다.

누구인지와 무엇을 할지는 별도다

인증은 사용자 식별을, 인가는 요청한 자원과 작업의 허용을 결정한다. 소유자·관계·역할 등 정책에 필요한 속성을 서버에서 확인한다. 버튼을 감추는 화면 처리는 직접 HTTP 요청의 권한 검사를 대신하지 않는다.

기본 거부와 요청별 검사를 사용한다

허용 근거가 없는 요청은 거부하며 자원 ID를 찾은 뒤 사용자와 작업을 함께 검사한다. 읽기·수정·삭제는 다른 허용일 수 있다. 클라이언트가 보낸 소유자 이름을 믿기보다 서버가 저장한 소유권을 사용한다.

시간 제한도 서버의 계약이다

idle 만료는 마지막 유효 활동 이후, absolute 만료는 최초 생성 이후의 최대 시간을 정한다. 요청마다 서버 시간으로 둘을 확인한다. 경계의 포함 여부를 명시하고 만료면 새 인증을 요구한다. 권한 회수와 세션 종료는 무제한 토큰 보유만으로 피할 수 없어야 한다.

기본 거부

표의 허용은 유효 세션과 선언한 정책을 전제로 한다. URL을 알고 있다는 사실이나 화면 버튼의 존재는 행의 허용 근거가 아니다. 실제 서버에서 모든 경로를 시험한 기록은 아니다.

중간 과정을 따라가는 예제

자체 규칙은 t−last<5 분 AND t−created<20 분이며 같으면 만료다. created=0, last=12인 세션으로 t=16에 민 소유 문서를 민이 읽는다. 별도 같은 상태 t=17과 t=20을 판단하라. 권한 규칙은 소유자만 읽기다.

  1. t=16은 idle 4<5, absolute 16<20이고 소유자가 같아 허용한다.

  2. 별도 t=17은 idle 5라 만료다. t=20은 absolute 20이라 만료이며 idle도 실패한다.

  3. t=16 요청이 실제 성공하면 last를 16으로 갱신한다. 별도 시간 질문과 한 실행의 후속 요청을 섞지 않는다.

고정 상태를 각각 비교하면 t=16 허용, t=17/t=20 만료다.

조건을 바꾸어 비교하기

읽기 성공이 수정 허용을 만들지 않는다

서의 세션은 시간 조건을 만족한다. 서가 d1을 읽은 뒤 수정 요청의 owner=민 필드를 보내 소유자 행처럼 처리해 달라고 한다. 어떤 근거로 결정해야 하는가?

  1. 서의 식별은 서버 세션에서 얻는다.

  2. d1의 소유자는 민, 서는 공유 독자라는 서버 관계를 읽는다.

  3. 읽기만 허용하고 수정은 거부한다. 제출 owner로 관계를 바꾸지 않는다.

서의 수정은 거부다. 별도 관계 변경 권한 정책도 이 문제에는 없다.

비교할 점

한 작업의 허용과 다른 작업의 허용, 클라이언트 주장과 서버 관계를 나눈다.

거부 요청은 idle 시계를 되돌리지 않는다

created=0,last=12인 민의 세션으로 t=16에 d2 읽기를 요청했다. 세션 시간은 유효하지만 관계가 없어 거부된다. 이후 t=17에 d1 읽기를 요청한다. 다른 활동은 없다.

  1. t=16은 4<5,16<20이지만 d2 권한이 없다.

  2. 거부이므로 이 자체 정책에서 last는 12 그대로다.

  3. t=17은 5<5가 거짓이어서 세션 만료다.

두 요청 모두 보호 작업을 허용하지 않으며 둘째는 idle 만료다.

비교할 점

권한에서 실패한 요청을 활동 갱신으로 셀지 정하지 않은 채 숫자만 계산하지 않는다.

연습 1 · 값과 상태 예측

created=0,last=16이며 다른 활동 없이 t=19에서 허용된 읽기가 성공해 last=19로 바뀌었다. t=20에서 idle이 1분이니 세션도 유효한가?

힌트 1

absolute 기준은 created다.

힌트 2

두 조건을 AND로 계산한다.

풀이와 답 확인

  1. idle은 1<5다.

  2. absolute는 20<20이 거짓이다.

absolute 만료이므로 유효하지 않다.

흔한 오답에서 다시 생각하기

방금 읽었으니 생성 시각도 19로 자동 바뀐다.

이 계약에서 활동 갱신은 last만 바꾸고 created를 초기화하지 않는다.

연습 2 · 오류 찾아 고치기

권한 검사를 로그인 때 한 번만 했다. 뒤에 서의 d1 공유 읽기 관계를 서버에서 회수했는데 옛 화면은 계속 열려 있다. 새 읽기 요청은 어떻게 판단해야 하는가?

힌트 1

지금 요청의 서버 관계를 본다.

힌트 2

옛 화면의 표시가 현재 정책을 대신하는지 본다.

풀이와 답 확인

  1. 새 요청에서 현재 유효 세션과 관계를 다시 검사한다.

  2. 회수된 관계로는 새 읽기를 거부한다.

  3. 이미 전달된 내용이나 이미 진행 중인 작업의 회수를 이 검사로 보장하지 않는다.

현재 자원별 검사로 새 요청을 거부한다. 실제 권한 캐시 무효화나 동시 요청 시험은 미수행이다.

흔한 오답에서 다시 생각하기

로그인 때 허용했으니 세션이 끝날 때까지 항상 허용이다.

현재 정책이 바뀐 사건을 무시한 판단이다.

연습 3 · 직접 만들어 보기

문서 d1의 민 소유자/서 공유 독자 정책에 대한 성공·실패 검사표를 제안하라. 로그인 성공만 검사한 표에서 빠진 행을 찾는다.

힌트 1

사용자×자원×작업을 조합한다.

힌트 2

만료와 허용 근거 없음도 넣는다.

풀이와 답 확인

  1. 민 d1 읽기/수정 허용과 서 d1 읽기 허용을 넣는다.

  2. 서 d1 수정, 민 d2 읽기, 정책 없는 자원은 거부로 둔다.

  3. 같은 허용 행도 만료 세션이면 거부하는 경계를 추가한다.

인가 조합과 시간 경계를 포함한 계획이다. 이 표를 실제 HTTP 테스트로 실행한 것은 아니다.

흔한 오답에서 다시 생각하기

두 사용자가 로그인되므로 모든 행을 성공으로 둔다.

인증 성공은 자원과 작업의 허용을 자동 부여하지 않는다.

클라이언트 타이머가 3분 남았다고 보이지만 서버는 absolute 만료로 거부했다. 클라이언트 시계를 늦춰 요청하면 서버 계약도 연장되는가?

힌트 1

시간 판정의 권위가 어디인지 확인한다.

힌트 2

화면 안내와 서버 판단을 나눈다.

풀이와 답 확인

  2. 클라이언트 시계 변경은 그 계약을 연장하지 않는다.

화면의 남은 시간은 권한 증거가 아니다. 실제 시계 차이나 복구 UI 시험은 미수행이다.

안내 표시와 권한 결정은 다른 상태이다.

다른 문제에 적용하기

자체 서비스의 구 정책 암호 레코드를 후보 A는 검증 실패, 후보 B는 성공한다. 정상 재해시에 쓸 후보와 실패 후보로 저장해선 안 되는 이유를 적어라. B 로그인 성공 시 익명 a를 폐기하고 민의 b를 만든다. 쿠키는 지원 브라우저의 HTTPS __Host-sid=b; Secure; HttpOnly; SameSite=Strict; Path=/ 이며 실제 ID 대신 표시용 b다. 로그아웃 서버 무효화 완료 뒤 다른 사본의 b로 새 보호 요청이 오면? 별도 독립 시간 사례는 created=0,last=12, t=16에 민의 d2 읽기가 권한 거부되고 t=17에 d1 읽기를 요청한다. 성공한 보호 요청만 last를 갱신하며 idle<5,absolute<20이다. 마지막 별도 서버 상태 last=19,created=0,t=20의 판단과 Path가 서버 권한 검사를 대신하는지도 설명하라.

힌트 1

후보 확인·새 레코드 계산·저장 확정을 세 사건으로 둔다. 표식 보유와 서버 유효성을 나눈다.

힌트 2

권한 거부는 이 정책에서 last를 갱신하지 않는다. 시간의 두 부등식을 각각 계산한다.

풀이와 답 확인

  1. 정상 재해시 후보는 B이며 A는 현재 암호로 확인되지 않아 교체에 쓰지 않는다. 실제 새 저장 성공은 별도 확인한다.

  2. 로그인 ID 갱신은 b 발급과 a 무효화를 함께 한다. 서버 로그아웃이 완료된 뒤의 새 b 요청은 유효 세션으로 허용하지 않는다.

  3. 독립 시간 사례 t=16은 시간은 유효하지만 d2 권한 거부라 last=12 유지다. t=17은 idle=5여서 만료다.

  4. 별도 last=19,t=20은 idle=1이어도 absolute=20이라 만료다. 클라이언트 시계나 쿠키 수명은 서버 계약을 연장하지 않는다.

  5. Path는 쿠키 전달 범위이며 자원별 인가 검사와 다르다. 실제 암호 라이브러리·HTTP·브라우저·경쟁 요청·학생 시험은 미수행이다.

B 검증 후 정책 갱신, a 무효/b 발급, 로그아웃 뒤 새 b 거부, 거부 뒤 last12와 t17 idle 만료, t20 absolute 만료다.

해결한 뒤 점검할 것

  • 검증 실패 후보와 정상 갱신 후보를 구별한다.

  • 새 ID 발급과 옛 ID 무효화를 함께 설명한다.

  • 서버 유효성과 남은 쿠키 사본을 구별한다.

  • 권한 거부의 last 정책과 두 만료 경계를 계산한다.

  • 범위 속성·인가·실제 실행 증거의 차이를 설명한다.
