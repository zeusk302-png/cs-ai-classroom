소단원 9.1

암호저장

서비스는 로그인 암호를 어떻게 확인하면서 원래 문자열을 보관하지 않을까?

준비 개념과 학습 목표

준비 개념

  • 문자열
  • 함수와 비교

학습 목표

  • 암호 전용 해시와 일반 빠른 해시를 구별한다.
  • salt·비밀·비용 설정의 역할을 설명한다.

검증용 값과 복원용 값을 구별한다

로그인 서비스는 암호를 다시 보여 줄 필요보다 제출한 후보가 맞는지 확인할 필요가 있다. 검증된 라이브러리의 암호 전용 해시를 저장하고 verify 연산을 쓴다. 암호화는 키로 원문 복원이 가능한 다른 요구이며 평문이나 빠른 SHA-256 한 번을 암호 저장 설계로 쓰지 않는다.

salt는 사용자별 계산을 나눈다

무작위의 서로 다른 salt는 같은 후보 암호에 대해서도 사용자마다 별도 계산이 필요하게 한다. salt는 비밀 키가 아니며 저장한 해시와 함께 보관할 수 있다. pepper를 쓴다면 DB와 분리한 비밀 관리가 추가로 필요하다. salt 자체가 짧고 예측 가능한 암호를 강하게 바꾸지는 않는다.

비용은 운영 조건과 함께 설정한다

Argon2id 같은 적응형 함수에는 메모리·반복 비용이 있다. 공식 최소 구성과 현재 라이브러리를 확인하고 실제 서버에서 지연·부하를 측정해야 한다. 알고리즘·설정·salt 정보도 보존해 로그인 시 갱신할 수 있게 한다. 아래 단위는 해시 함수의 실제 속도가 아니라 종이 작업량이다.

중간 과정을 따라가는 예제

서로 다른 salt의 검증 레코드가 3 개다. 자체 모델에서 후보 하나와 레코드 하나의 계산은 5 작업 단위다. 두 후보를 세 레코드 모두에 비교하면 작업량은? 병렬·조기 종료는 없다.

  1. 후보/레코드 쌍은 2×3=6 개다.
  2. 각 쌍의 salt를 반영한 별도 계산을 하므로 6×5=30 단위다.
  3. 암호의 추측 성공 여부나 실제 초 단위 속도는 이 조건으로 알 수 없다.

30 작업 단위다. salt는 공통 후보 계산 하나로 전 레코드를 비교하는 지름길을 줄인다.

힌트 보기

쌍 수부터 센다.

풀이 보기

4×3×5=60 단위다. 메모리·동시성 실측은 아니다.

오해와 반례

salt만 넣으면 어떤 암호도 추측할 수 없다.

한 후보씩 다시 계산해 비교하는 공격은 여전히 가능하다. salt·비용·암호 품질과 온라인 시도 제한은 다른 방어 요소다.

소단원 9.2

cookie·session

브라우저의 작은 표식은 서버가 기억하는 로그인 상태와 어떻게 이어질까?

준비 개념과 학습 목표

준비 개념

  • HTTP 요청
  • 서버와 브라우저

학습 목표

  • 쿠키 전달과 서버 세션 저장을 구별한다.
  • 쿠키 속성과 로그아웃의 경계를 설명한다.

쿠키는 전달 수단이다

브라우저가 응답의 Set-Cookie를 저장하고 조건에 맞는 요청에 Cookie를 보낸다. 이 소단원은 불투명한 세션 ID를 쿠키에 넣고 사용자·상태는 서버의 레코드에서 찾는 모델이다. 모든 쿠키가 로그인 세션은 아니며 쿠키 자체에 암호를 넣을 필요도 없다.

표식의 보호는 여러 조건이다

Secure는 HTTPS 전달을, HttpOnly는 DOM 스크립트의 쿠키 읽기 차단을, SameSite는 사이트 간 전달 조건을 다룬다. HttpOnly여도 브라우저는 요청에 쿠키를 보낼 수 있어 XSS로 수행되는 모든 작업을 막지는 않는다. SameSite도 별도 CSRF 방어를 대체한다고 단정하지 않는다.

서버 상태를 종료해야 한다

로그인이나 권한 상승 때 세션 ID를 갱신하고 이전 ID의 유효성을 관리한다. 로그아웃은 브라우저 표식 정리와 서버 레코드 무효화를 연결한다. 탭·브라우저 닫힘을 유일 종료 신호로 믿지 않는다. 아래 sA/sB는 표시용 이름이며 실제 ID는 예측 불가능하게 생성한다.

중간 과정을 따라가는 예제

자체 서버 표에 sA→사용자 민이 있고 sB는 없다. 민의 브라우저가 sA를 보내면 로그인으로 해석한다. 로그아웃으로 서버 sA를 지운 뒤 남아 있던 다른 탭이 sA를 다시 보내면?

  1. 표에서 sA를 찾으면 민이라는 결과를 얻는다.
  2. 로그아웃으로 sA의 서버 레코드를 무효화한다.
  3. 이후 같은 쿠키가 도착해도 유효 레코드가 없어 로그인 세션으로 받아들이지 않는다.

처음에는 민의 세션, 로그아웃 후에는 무효다. 쿠키 보유와 유효 세션은 다르다.

종이와 본문으로 직접 해보기

쿠키만 지우고 서버 레코드를 남기면 다른 곳에 남은 sA는?

힌트 보기

서버가 무엇을 검사하는지 본다.

풀이 보기

다른 유효 조건이 유지된다면 남은 sA가 아직 허용될 수 있다. 서버 무효화가 필요하다.

오해와 반례

HttpOnly면 세션을 통한 모든 악성 요청이 불가능하다.

쿠키를 직접 읽지 못해도 페이지의 악성 스크립트가 요청을 수행할 수 있다. 속성 하나를 전체 공격 방어로 확대하지 않는다.

답과 이유 보기

남은 ID를 무효로 판단해야 한다.

닫힌 탭이 항상 서버 로그아웃을 보장하나?

답과 이유 보기

아니다.

종료 신호는 신뢰할 수 없다.

한 단계 더

두 탭과 서버 표를 그려 ID 전달과 무효화 화살표를 나누자.

소단원 9.3

접근권한과 만료

로그인했으면 다른 사람의 모든 문서도 읽어도 될까?

준비 개념과 학습 목표

준비 개념

  • 인증
  • 논리 AND

학습 목표

  • 인증과 자원별 권한 검사를 구별한다.
  • idle·absolute 만료 경계를 계산한다.

누구인지와 무엇을 할지는 별도다

인증은 사용자 식별을, 인가는 요청한 자원과 작업의 허용을 결정한다. 소유자·관계·역할 등 정책에 필요한 속성을 서버에서 확인한다. 버튼을 감추는 화면 처리는 직접 HTTP 요청의 권한 검사를 대신하지 않는다.

기본 거부와 요청별 검사를 사용한다

허용 근거가 없는 요청은 거부하며 자원 ID를 찾은 뒤 사용자와 작업을 함께 검사한다. 읽기·수정·삭제는 다른 허용일 수 있다. 클라이언트가 보낸 소유자 이름을 믿기보다 서버가 저장한 소유권을 사용한다.

시간 제한도 서버의 계약이다

idle 만료는 마지막 유효 활동 이후, absolute 만료는 최초 생성 이후의 최대 시간을 정한다. 요청마다 서버 시간으로 둘을 확인한다. 경계의 포함 여부를 명시하고 만료면 새 인증을 요구한다. 권한 회수와 세션 종료는 무제한 토큰 보유만으로 피할 수 없어야 한다.

중간 과정을 따라가는 예제

자체 규칙은 t−last<5 분 AND t−created<20 분이며 같으면 만료다. created=0, last=12인 세션으로 t=16에 민 소유 문서를 민이 읽는다. 별도 같은 상태 t=17과 t=20을 판단하라. 권한 규칙은 소유자만 읽기다.

  1. t=16은 idle 4<5, absolute 16<20이고 소유자가 같아 허용한다.
  2. 별도 t=17은 idle 5라 만료다. t=20은 absolute 20이라 만료이며 idle도 실패한다.
  3. t=16 요청이 실제 성공하면 last를 16으로 갱신한다. 별도 시간 질문과 한 실행의 후속 요청을 섞지 않는다.

고정 상태를 각각 비교하면 t=16 허용, t=17/t=20 만료다.

종이와 본문으로 직접 해보기

t=16 성공 뒤 last=16인 실제 후속 t=19와 t=20은?

힌트 보기

absolute 기준은 생성 시각 0에서 계속 센다.

풀이 보기

t=19는 idle 3/absolute 19로 유효다. t=20은 idle 4여도 absolute 20으로 만료다.

오해와 반례

로그인 사용자면 문서 번호를 알기만 해도 읽을 수 있다.

유효한 민의 세션이라도 서 소유 문서는 이 정책에서 거부된다. ID 지식은 소유권 증명이 아니다.
