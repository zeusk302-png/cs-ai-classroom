소단원 6.1

컴포넌트와 상태분리

과목 카드와 상세 설명이 서로 다른 과목을 표시하면 어디부터 고칠까?

준비 개념과 학습 목표

준비 개념

  • 컴포넌트는 화면의 책임을 나누는 단위다.
  • props는 부모가 자식에게 전달하는 입력이다.
  • 상태는 시간에 따라 달라지는 화면의 기억이다.

학습 목표

  • 공유 상태의 소유자를 정한다.
  • 파생 값과 저장할 상태를 구분한다.
  • 사용자 이벤트의 전달 경로를 종이에 추적한다.

책임과 공유 범위를 먼저 나누기

자체 강의 탐색 화면을 CourseExplorer 부모, CourseList 목록, CourseDetail 상세로 나눈다. 목록은 카드와 선택 요청, 상세는 선택 과목의 설명을 맡는다. 두 자식이 같은 선택을 보여야 하므로 selectedId의 소유자는 공통 부모다. 자식은 받은 값을 표시하고 선택 이벤트를 부모에게 전달한다.

모든 상태를 무조건 최상단에 두지는 않는다. 상세 내부의 설명 접기처럼 다른 컴포넌트가 필요 없는 상태는 가까운 곳에 둘 수 있다. 공유 여부와 책임을 기준으로 위치를 정한다. 컴포넌트를 나누었다는 사실만으로 데이터 일치가 자동 보장되지는 않는다.

같은 사실을 두 번 저장하지 않기

자체 목록은 [{id:1,title:"C"},{id:2,title:"선형대수"},{id:3,title:"Python"}]이다. selectedId만 저장하고 selectedCourse는 목록에서 같은 ID를 찾아 계산한다. 선택 객체까지 별도 상태로 저장하면 제목 변경 때 목록은 새 이름인데 상세는 옛 이름인 모순이 생길 수 있다.

검색 문자열 query는 입력으로 저장하지만 visibleCourses와 그 개수는 현재 목록·query로부터 계산한다. 예제는 제목 포함 검색, 대소문자 구별, ID 유일이라는 조건을 사용한다. 선택 과목이 검색 결과에서 사라져도 전체 목록에 있으면 상세를 유지하는 정책을 명시한다. 필터와 선택의 관계는 제품 정책이다.

이벤트에서 새 화면까지 연결하기

사용자가 2번 카드를 누르면 자식은 onSelect(2)를 요청한다. 부모가 selectedId를 2로 바꾼 뒤 다음 화면 계산에서 상세 과목은 선형대수가 된다. 자식이 부모의 props를 직접 수정하는 방식으로 생각하지 않는다. 아래는 실제 React 실행 대신 책임 전달을 나타내는 의사코드다.

자체 초기 선택 1과 검색 빈 문자열에서 C 상세와 세 카드가 나온다. query를 "선형"으로 바꾸면 목록은 2번 한 개지만 정책에 따라 상세는 여전히 1번 C다. 이어 2번 선택 이벤트를 처리하면 목록과 상세가 2번을 가리킨다. 데이터 흐름과 표시 정책을 함께 추적한다.

state = {selectedId: 1, query: ""}
visible = courses.filter(title includes state.query)
selected = courses.find(id == state.selectedId)
CourseList(visible, onSelect = id => updateSelectedId(id))
CourseDetail(selected)  // 책임 설명용 의사코드

중간 과정을 따라가는 예제

위 목록에서 초기 selectedId=1, query=""이다. query="선형" 입력 후 2번 선택 이벤트까지 목록 개수와 상세를 추적하라.

  1. 초기 빈 문자열은 세 제목에 포함되므로 개수 3, 상세 C다.
  2. query="선형"이면 제목에 포함되는 것은 2번뿐이라 개수 1이다. 아직 selectedId=1이므로 상세 C다.
  3. onSelect(2)로 부모 선택이 2가 되면 전체 목록에서 2번을 찾아 상세 선형대수를 표시한다. 개수는 계속 1이다.

(3,C) → (1,C) → (1,선형대수)다. 검색이 선택을 자동 변경하지 않는 자체 정책을 적용했다.

풀이 보기

오해와 반례

컴포넌트마다 같은 선택 상태를 복사해 두면 항상 편하고 정확하다.

서로 다른 복사본을 한쪽만 바꾸면 목록 2번·상세 1번 같은 모순이 가능하다. 공통 소유자와 전달 경로를 정하고 계산 가능한 값은 파생한다.

소단원 6.2

라우팅과 폼

뒤로 가기와 새로고침에서도 사용자가 보던 과목을 찾을 수 있을까?

준비 개념과 학습 목표

준비 개념

  • URL은 사용자가 공유하거나 다시 방문할 주소다.
  • 라우팅은 주소를 화면의 의미에 연결한다.
  • 폼은 입력 항목·제약·제출 동작을 가진다.

학습 목표

  • 경로와 화면 상태의 연결을 설명한다.
  • push와 replace의 방문 기록 차이를 추적한다.
  • 폼 제약과 서버의 검증 책임을 구분한다.

주소를 화면 의미에 연결하기

자체 주소 /courses는 목록, /courses/7은 ID7 상세라는 규칙을 둔다. 라우터는 경로를 해석해 필요한 화면과 데이터를 정한다. 주소가 바뀌었다고 없는 과목이 생기는 것은 아니므로 ID 존재 여부도 확인한다. URL의 화면 의미와 비공개 권한 확인은 서로 다른 책임이다.

이 절은 같은 출처에서 해당 주소를 처리할 수 있는 앱을 가정한다. History API가 서버 파일이나 경로 처리를 만들어 주지는 않는다. 주소를 직접 입력하거나 새로고침하는 경우에도 서버가 문서를 제공할 수 있도록 배포 방식에 맞는 구성이 필요하다. 이 강의의 공개 사이트를 실제로 변경한 예제가 아니다.

새 방문과 현재 방문 교체 구분하기

pushState는 새 방문 항목을 추가하고 replaceState는 현재 항목을 바꾼다. 화면 변경을 앱에서 수행하면서 주소와 저장할 상태를 함께 관리한다. 사용자가 뒤로·앞으로 이동할 때 popstate의 상태로 화면을 복원할 수 있다. 초기 항목에도 복원에 필요한 상태를 설정하는 이유를 생각해 보자.

자체 방문 기록 [/courses,/courses/7,/courses/8]의 현재 위치는 마지막이다. 뒤로 한 번이면 /courses/7이다. 그 항목을 replace로 /courses/7?view=summary로 바꾸면 전체 항목 수는 3이다. 이 상태에서 앞으로 이동하면 원래 다음 항목 /courses/8로 간다. replace는 새 항목 추가와 다르다.

폼은 항목과 오류 회복을 함께 설계하기

자체 신청 폼에는 이름과 학점이 있다. 이름은 required, 학점은 type=number·required·min=1·max=5·step=1로 정한다. 값이 비었는지, 숫자인지, 범위 안 정수인지 각각 확인한다. 이름표와 수정할 문제를 알려 주어 사용자가 입력을 고칠 수 있게 한다.

클라이언트 검사는 빠른 피드백을 주지만 요청을 직접 보낼 수 있는 사용자를 막는 보안 보장은 아니다. 서버는 같은 입력 조건과 신청 권한을 다시 검사해야 한다. 브라우저가 통과시킨 값이라고 신뢰하지 않는다. 아래 종이 판정은 제약의 의미를 보는 것이며 폼 제출·서버 구현은 실제 수행하지 않았다.

<label for="credits">학점</label>
<input id="credits" name="credits" type="number"
       required min="1" max="5" step="1">

중간 과정을 따라가는 예제

자체 방문 3항목에서 뒤로·현재 항목 replace·앞으로를 추적하라. 이름="민", 학점=6인 신청은 명시한 폼 조건을 통과하는가?

  1. 마지막 /courses/8에서 뒤로 이동하면 현재 /courses/7이다.
  2. 현재 항목을 /courses/7?view=summary로 교체해도 길이는 3이다. 앞으로 이동할 다음은 /courses/8이다.
  3. 이름은 비어 있지 않지만 학점 6은 max=5를 넘는다. 전체 입력 조건은 실패하며 1~5의 정수로 수정해야 한다.

현재 주소는 7→7?view=summary→8, 항목 수는 3을 유지한다. 학점 6은 범위 실패다.

종이와 본문으로 직접 해보기

이름을 채우고 학점을 3.5 또는 3으로 입력한 두 경우를 비교하라. 클라이언트 검사 없이 학점=99인 요청을 보내면 서버는 무엇을 해야 하는가?

힌트 보기

범위와 step=1을 따로 확인한다. 클라이언트 통과 여부가 서버 신뢰 근거는 아니다.

풀이 보기

3.5는 1~5 안이지만 1에서 정수 간격 1로 떨어지지 않아 step 조건에 맞지 않는다. 3은 해당 조건을 통과한다. 서버는 직접 받은 99를 독립 검증해 거절하고 권한도 검사해야 한다.

오해와 반례

replaceState는 pushState처럼 방문 항목을 하나 더 만든다.

replace는 현재 항목만 교체한다. 예제에서 항목 수가 3인 채 앞으로 8번에 갈 수 있는 것이 반례다. 새 항목 추가와 현재 항목 수정의 목적을 구분한다.

한 단계 더

검색어가 바뀔 때마다 push하는 경우와 현재 검색 항목을 replace하는 경우의 뒤로 가기 경험을 비교하라. 북마크할 정보와 한시적인 폼 오류 메시지를 URL에 담는 것이 각각 적절한지도 생각한다.

소단원 6.3

로딩·빈결과·실패

아무 카드도 없을 때 기다리는 중인지 결과가 없는지 실패했는지 알 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 비동기 요청은 응답을 기다리는 동안 화면을 계속 표시할 수 있다.
  • HTTP 상태와 자료 내용은 서로 다른 정보다.
  • 같은 요청 화면에서도 여러 상태가 시간에 따라 이어진다.

학습 목표

  • 대기·성공·빈 성공·실패를 구분한다.
  • HTTP 실패와 네트워크 실패의 차이를 설명한다.
  • 늦게 도착한 옛 응답을 걸러 낼 조건을 추적한다.

화면에 의미 있는 상태를 이름 붙이기

자체 화면 상태는 idle(아직 요청 안 함), loading(기다리는 중), success(items), error(message)로 둔다. success 안에서 items가 빈 배열이면 정상적으로 검색했지만 결과가 없다는 안내를 표시한다. 초기 빈 배열 하나만으로 요청 전·대기·빈 성공·실패를 모두 판단할 수 없다.

실패 화면에는 무슨 요청이 실패했는지와 다시 시도할 방법을 준다. loading과 error가 동시에 참인 두 불리언 대신 의미가 분명한 상태를 선택하면 모순을 줄일 수 있다. 예제는 이전 결과를 숨기는 단순 정책이다. 이전 결과를 유지하는 화면은 갱신 중이라는 별도 표현이 필요하다.

전송과 응답 내용을 각각 확인하기

fetch는 네트워크 오류 등에서 거절될 수 있지만 404 같은 HTTP 오류 응답을 받으면 Response로 이행할 수 있다. 따라서 응답을 받은 뒤 response.ok를 확인하고, 성공으로 인정한 응답의 JSON 읽기도 기다린다. JSON 파싱 실패도 자료를 정상 사용한 성공으로 취급하지 않는다.

자체 모형은 서버 계약이 성공 응답에서 items 배열을 준다고 가정한다. 200과 items=[]는 빈 성공, 404는 실패, 네트워크 거절도 실패다. 상태 코드가 200이라고 내용 구조까지 자동 증명되지는 않으므로 배열 등 기대 형식 확인도 필요하다. 실제 서버 호출 없이 조건을 종이에 판정한다.

요청의 시작 순서와 도착 순서 구분하기

사용자가 검색 A 다음 B를 시작했는데 B 응답이 먼저 오고 A가 나중에 올 수 있다. 자체 요청 번호 1·2 중 최신 번호를 2로 저장하고, 응답을 적용할 때 번호가 최신과 같은지 검사한다. 옛 응답 1이 새 검색 B의 화면을 덮지 않게 하는 조건이다.

성공뿐 아니라 실패 처리에도 같은 검사를 적용해야 한다. 옛 A가 늦게 실패했다고 현재 B 성공을 오류로 바꾸지 않는다. 취소는 비용을 줄일 수 있지만 이 예제는 취소 API를 구현하거나 모든 경합을 해결했다고 주장하지 않는다. 번호 비교와 상태 전이만 분석하는 의사코드다.

latest = latest + 1
mine = latest
state = loading
try:
    response = await request(query)
    if not response.ok: fail("HTTP 실패")
    items = await readAndValidateItems(response)
    if mine == latest: state = success(items)
catch error:
    if mine == latest: state = error(error.message)
// 실행한 코드가 아닌 요청 번호 모형

중간 과정을 따라가는 예제

A 요청 번호1 후 B 번호2를 시작한다. B는 200과 [선형대수]를 먼저 반환하고 A는 늦게 200과 []를 반환한다. 최종 화면을 구하라.

  1. A 시작에서 latest=1, loading이다. B 시작에서 latest=2, loading이다.
  2. B 성공 처리에서 mine=2=latest라 success([선형대수])를 적용한다.
  3. A는 mine=1≠latest2라 빈 응답을 적용하지 않는다. B의 한 결과를 유지한다.

최종은 B의 성공 결과 선형대수 한 개다. 빈 결과 A가 마지막에 도착했어도 최신 요청은 아니다.

풀이 보기

200과 []는 success의 빈 결과 안내, 404는 error다. 어느 경우든 최신3에서 옛 번호1 실패는 적용하지 않아 C 상태를 유지한다.

오해와 반례

fetch가 정상 이행했으면 HTTP 요청은 모두 성공이다.

404도 응답 객체로 이행할 수 있으므로 ok 검사가 필요하다. 또 200의 JSON 읽기나 형식 확인이 실패하면 화면 자료 성공과 다르다.
