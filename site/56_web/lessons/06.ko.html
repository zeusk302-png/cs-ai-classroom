소단원 6.1

컴포넌트와 상태분리

과목 카드와 상세 설명이 서로 다른 과목을 표시하면 어디부터 고칠까?

준비 개념과 학습 목표

준비 개념

  • 컴포넌트는 화면의 책임을 나누는 단위다.

  • props는 부모가 자식에게 전달하는 입력이다.

  • 상태는 시간에 따라 달라지는 화면의 기억이다.

학습 목표

  • 공유 상태의 소유자를 정한다.

  • 파생 값과 저장할 상태를 구분한다.

  • 사용자 이벤트의 전달 경로를 종이에 추적한다.

도서관 목록에서 책을 지웠는데 대출 창에는 여전히 그 책이 보인다면, 어떤 기억이 남았을까?

선택 ID를 기억하는 것과 선택한 객체 전체를 따로 기억하는 것은 다른 설계다. 이번 모형은 ID가 유일한 과목 목록에서 selectedId와 query만 저장하고 선택 객체·필터 목록·개수를 현재 자료로부터 계산한다. 실제 React를 실행한 예제가 아닌 상태 책임의 종이 추적이다.

삭제 정책도 명시해야 한다. 이 보강에서는 선택 ID가 전체 목록에 없으면 상세에 “선택한 과목이 없습니다”를 표시한다. 저장된 selectedId는 다음 선택까지 그대로 둘 수 있지만, 존재하지 않는 ID로 가짜 상세 객체를 만들지는 않는다. 검색에서 숨은 과목과 목록에서 삭제된 과목을 구별한다.

먼저 확인할 개념
  • 원본 상태와 표시

    저장할 사실과 화면에서 계산한 값을 분리한다.

  • 객체 공유와 복사

    예전 객체 복사본과 최신 목록 객체의 차이를 설명한다.

책임과 공유 범위를 먼저 나누기

자체 강의 탐색 화면을 CourseExplorer 부모, CourseList 목록, CourseDetail 상세로 나눈다. 목록은 카드와 선택 요청, 상세는 선택 과목의 설명을 맡는다. 두 자식이 같은 선택을 보여야 하므로 selectedId의 소유자는 공통 부모다. 자식은 받은 값을 표시하고 선택 이벤트를 부모에게 전달한다.

모든 상태를 무조건 최상단에 두지는 않는다. 상세 내부의 설명 접기처럼 다른 컴포넌트가 필요 없는 상태는 가까운 곳에 둘 수 있다. 공유 여부와 책임을 기준으로 위치를 정한다. 컴포넌트를 나누었다는 사실만으로 데이터 일치가 자동 보장되지는 않는다.

같은 사실을 두 번 저장하지 않기

자체 목록은 [{id:1,title:"C"},{id:2,title:"선형대수"},{id:3,title:"Python"}]이다. selectedId만 저장하고 selectedCourse는 목록에서 같은 ID를 찾아 계산한다. 선택 객체까지 별도 상태로 저장하면 제목 변경 때 목록은 새 이름인데 상세는 옛 이름인 모순이 생길 수 있다.

검색 문자열 query는 입력으로 저장하지만 visibleCourses와 그 개수는 현재 목록·query로부터 계산한다. 예제는 제목 포함 검색, 대소문자 구별, ID 유일이라는 조건을 사용한다. 선택 과목이 검색 결과에서 사라져도 전체 목록에 있으면 상세를 유지하는 정책을 명시한다. 필터와 선택의 관계는 제품 정책이다.

이벤트에서 새 화면까지 연결하기

사용자가 2번 카드를 누르면 자식은 onSelect(2)를 요청한다. 부모가 selectedId를 2로 바꾼 뒤 다음 화면 계산에서 상세 과목은 선형대수가 된다. 자식이 부모의 props를 직접 수정하는 방식으로 생각하지 않는다. 아래는 실제 React 실행 대신 책임 전달을 나타내는 의사코드다.

자체 초기 선택 1과 검색 빈 문자열에서 C 상세와 세 카드가 나온다. query를 "선형"으로 바꾸면 목록은 2번 한 개지만 정책에 따라 상세는 여전히 1번 C다. 이어 2번 선택 이벤트를 처리하면 목록과 상세가 2번을 가리킨다. 데이터 흐름과 표시 정책을 함께 추적한다.

state = {selectedId: 1, query: ""}
visible = courses.filter(title includes state.query)
selected = courses.find(id == state.selectedId)
CourseList(visible, onSelect = id => updateSelectedId(id))
CourseDetail(selected)  // 책임 설명용 의사코드

검색 결과에 없다는 사실은 전체 자료에 없다는 사실과 다르다. 삭제 행에서 저장된 ID 3과 찾기 결과 없음이 함께 존재할 수 있다. 안내의 문구와 재선택 방법을 정하는 것까지 제품의 정책이다.

중간 과정을 따라가는 예제

위 목록에서 초기 selectedId=1, query=""이다. query="선형" 입력 후 2번 선택 이벤트까지 목록 개수와 상세를 추적하라.

  1. 초기 빈 문자열은 세 제목에 포함되므로 개수 3, 상세 C다.

  2. query="선형"이면 제목에 포함되는 것은 2번뿐이라 개수 1이다. 아직 selectedId=1이므로 상세 C다.

  3. onSelect(2)로 부모 선택이 2가 되면 전체 목록에서 2번을 찾아 상세 선형대수를 표시한다. 개수는 계속 1이다.

(3,C) → (1,C) → (1,선형대수)다. 검색이 선택을 자동 변경하지 않는 자체 정책을 적용했다.

조건을 바꾸어 비교하기

필터 개수를 별도로 저장한 오류

query=선형일 때 visibleCount를 1로 따로 저장했다. ID4 제목 선형회귀를 전체 목록에 추가하고 count 갱신을 잊었다.

  1. 현재 필터는 ID2와 ID4를 선택한다.

  2. 현재 자료에서 계산한 개수는 2다.

  3. 별도 count=1은 같은 사실의 오래된 복사본이다.

파생 개수 2와 저장 count 1이 모순된다. 목록과 query에서 개수를 계산하는 설계를 택한다.

비교할 점

선택 객체 중복뿐 아니라 결과 개수도 같은 동기화 부담이 생긴다.

공유할 기억과 가까이 둘 기억

목록과 상세가 selectedId를 공유하지만 상세 안의 설명 펼침은 목록이 사용하지 않는다. 필터와 상관없이 상세 펼침은 해당 상세가 유지되는 동안 기억한다고 정했다.

  1. selectedId는 두 표시의 공통 책임이다.

  2. 설명 펼침은 상세만 사용하는 별도 기억이다.

  3. 공통 부모의 선택과 상세 내부의 펼침을 분리한다.

공유 선택은 가까운 공통 부모에, 상세 전용 펼침은 상세 책임에 둘 수 있다.

비교할 점

모든 상태를 한곳으로 옮긴다는 규칙 대신 공유 범위와 수명 정책을 적용한다.

종이와 본문으로 직접 해보기

선택 3번에서 목록의 Python 제목을 Python 기초로 바꾼다. 선택 ID 방식과 별도 선택 객체 복사 방식의 차이를 적어라.

힌트 보기

같은 ID로 최신 목록을 찾는지, 예전 객체를 따로 보관하는지 비교한다.

풀이 보기

ID 방식은 최신 목록에서 3번을 찾아 Python 기초를 표시한다. 예전 객체 복사 상태를 따로 갱신하지 않으면 상세는 Python이라는 옛 이름일 수 있다. 중복 상태의 동기화 부담이다.

오해와 반례

컴포넌트마다 같은 선택 상태를 복사해 두면 항상 편하고 정확하다.

서로 다른 복사본을 한쪽만 바꾸면 목록 2번·상세 1번 같은 모순이 가능하다. 공통 소유자와 전달 경로를 정하고 계산 가능한 값은 파생한다.

연습 1 · 값과 상태 예측

표의 ID3 삭제 뒤 query를 빈 문자열로 바꿨다. 목록 개수와 상세를 구하라. 선택 ID는 자동 변경하지 않는다.

힌트 1

전체 자료에 남은 ID를 센다.

힌트 2

선택 3이 존재하는지 다시 찾는다.

풀이와 답 확인

  1. ID1과 ID2가 모두 보인다.

  2. ID3은 없어 상세 찾기가 실패한다.

목록 2개, 선택 없음 안내다.

흔한 오답에서 다시 생각하기

빈 검색이면 삭제한 과목도 복구된다.

검색은 현재 자료의 표시 조건이며 삭제 취소 기능이 아니다.

연습 2 · 오류 찾아 고치기

자식 목록은 자기 selectedId를 2로 바꾸고 상세는 자기 selectedId=1을 유지한다. “둘 다 상태이므로 자동 일치한다”는 설명을 고쳐라.

힌트 1

같은 사실을 어디에 몇 번 저장했는지 찾는다.

힌트 2

onSelect 요청의 도착 지점을 그린다.

풀이와 답 확인

  1. 독립 복사본이라 한쪽 변경이 다른 쪽을 자동 변경하지 않는다.

  2. 공통 소유자에 선택 요청을 전달한다.

  3. 두 자식은 같은 최신 선택을 입력으로 받는다.

선택의 공통 소유자와 전달 경로를 정해야 한다.

이름이 같은 것과 같은 상태의 소유자를 공유하는 것을 구분하라.

연습 3 · 직접 만들어 보기

선택된 ID가 삭제되면 자동으로 첫 남은 과목을 선택하는 다른 정책을 제안하라. 자료가 전부 비었을 때도 정하라.

힌트 1

남은 목록의 첫 항목이 있는지 확인한다.

힌트 2

빈 목록의 선택 값 표현을 별도로 둔다.

풀이와 답 확인

  1. 삭제 후 선택 ID가 없으면 남은 첫 ID로 재선택한다.

  2. 목록이 비면 null 등 명시한 선택 없음 값으로 둔다.

  3. 상세는 그 정책에 따른 현재 선택만 표시한다.

첫 과목 재선택과 완전히 빈 자료의 선택 없음 정책을 함께 제시한다.

빈 배열에서는 첫 항목이 없다는 경계를 포함하라.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

ID가 중복된 목록 [2 선형대수, 2 선형회귀]에서 find로 ID2를 선택했다. 이 보강의 유일 ID 전제로 두 과목을 정확히 구별했다고 말할 수 있는가?

힌트 1

선택 ID의 정보량을 본다.

힌트 2

find가 두 후보를 구별할 조건을 찾는다.

풀이와 답 확인

  1. 두 과목이 같은 ID를 사용해 선택 정보가 모호하다.

  2. find 결과는 앞의 일치 항목일 수 있지만 의도한 과목 식별이 보장되지 않는다.

  3. 자료의 고유 ID 계약을 검증하거나 구별 가능한 키를 정한다.

이전 유일 ID 전제가 깨졌다. 자료 계약을 먼저 고쳐야 한다.

find가 있으니 데이터 중복도 자동 해결된다.

검색 연산과 자료 식별 계약을 다른 책임으로 검사하라.

소단원 6.2

라우팅과 폼

뒤로 가기와 새로고침에서도 사용자가 보던 과목을 찾을 수 있을까?

준비 개념과 학습 목표

준비 개념

  • URL은 사용자가 공유하거나 다시 방문할 주소다.

  • 라우팅은 주소를 화면의 의미에 연결한다.

  • 폼은 입력 항목·제약·제출 동작을 가진다.

학습 목표

  • 경로와 화면 상태의 연결을 설명한다.

  • push와 replace의 방문 기록 차이를 추적한다.

  • 폼 제약과 서버의 검증 책임을 구분한다.

지난 페이지로 돌아간 자리에서 새 페이지로 갔다면, 원래 앞으로 가던 길은 남아 있을까?

방문 기록을 배열과 현재 위치로 단순화하면 push와 replace의 차이가 드러난다. 아래는 앱 내부 방문 세 개만 고려하는 종이 모형이다. 다른 문서·iframe·브라우저 전체 history.length를 이 작은 배열과 같다고 주장하지 않는다.

처음 [/courses, /courses/7, /courses/8]의 현재 위치는 마지막이다. 뒤로 간 자리에서 push로 /courses/9를 추가하면 이 모형의 앞으로 갈 가지 /courses/8은 새 방문으로 교체된다. 주소 변경과 앱의 표시 갱신, 서버의 직접 방문 지원은 각각 구현해야 하는 책임이다.

먼저 확인할 개념
  • URL과 상대 경로

    주소가 나타내는 자료와 경로 해석을 분리한다.

  • 폼 제약과 서버 계약

    브라우저 입력 조건만으로 서버의 허용을 보장하지 않는다.

주소를 화면 의미에 연결하기

자체 주소 /courses는 목록, /courses/7은 ID7 상세라는 규칙을 둔다. 라우터는 경로를 해석해 필요한 화면과 데이터를 정한다. 주소가 바뀌었다고 없는 과목이 생기는 것은 아니므로 ID 존재 여부도 확인한다. URL의 화면 의미와 비공개 권한 확인은 서로 다른 책임이다.

이 절은 같은 출처에서 해당 주소를 처리할 수 있는 앱을 가정한다. History API가 서버 파일이나 경로 처리를 만들어 주지는 않는다. 주소를 직접 입력하거나 새로고침하는 경우에도 서버가 문서를 제공할 수 있도록 배포 방식에 맞는 구성이 필요하다. 이 강의의 공개 사이트를 실제로 변경한 예제가 아니다.

새 방문과 현재 방문 교체 구분하기

pushState는 새 방문 항목을 추가하고 replaceState는 현재 항목을 바꾼다. 화면 변경을 앱에서 수행하면서 주소와 저장할 상태를 함께 관리한다. 사용자가 뒤로·앞으로 이동할 때 popstate의 상태로 화면을 복원할 수 있다. 초기 항목에도 복원에 필요한 상태를 설정하는 이유를 생각해 보자.

자체 방문 기록 [/courses,/courses/7,/courses/8]의 현재 위치는 마지막이다. 뒤로 한 번이면 /courses/7이다. 그 항목을 replace로 /courses/7?view=summary로 바꾸면 전체 항목 수는 3이다. 이 상태에서 앞으로 이동하면 원래 다음 항목 /courses/8로 간다. replace는 새 항목 추가와 다르다.

폼은 항목과 오류 회복을 함께 설계하기

자체 신청 폼에는 이름과 학점이 있다. 이름은 required, 학점은 type=number·required·min=1·max=5·step=1로 정한다. 값이 비었는지, 숫자인지, 범위 안 정수인지 각각 확인한다. 이름표와 수정할 문제를 알려 주어 사용자가 입력을 고칠 수 있게 한다.

클라이언트 검사는 빠른 피드백을 주지만 요청을 직접 보낼 수 있는 사용자를 막는 보안 보장은 아니다. 서버는 같은 입력 조건과 신청 권한을 다시 검사해야 한다. 브라우저가 통과시킨 값이라고 신뢰하지 않는다. 아래 종이 판정은 제약의 의미를 보는 것이며 폼 제출·서버 구현은 실제 수행하지 않았다.

주소만 바꾼 화면

앱이 pushState로 주소 /courses/9를 만들었지만 표시 자료는 ID7을 계속 사용한다. push 호출 자체가 앱의 렌더 함수나 popstate를 자동 호출한다고 가정했다.

  1. 주소/방문 변경과 화면 자료 선택을 분리한다.

  2. push 자체에만 화면 갱신을 맡긴 가정을 제거한다.

  3. 새 방문 경로와 뒤로 이동 복원 경로에서 같은 라우트 해석을 호출하도록 설계한다.

주소 9와 상세 7의 모순을 앱에서 고쳐야 한다. 실제 History API 실험은 수행하지 않았다.

비교할 점

뒤로 이동의 복원 이벤트와 직접 push 시점의 화면 갱신을 같은 자동 효과로 생각하지 않는다.

required를 통과하는 공백 이름

신청 이름은 type=text, required이며 값 " "다. 서버의 새 정책은 trim한 이름 길이가 1 이상이어야 한다. 학점은 범위 안 정수 3이다.

  1. required의 빈 문자열 검사와 공백 제거 정책을 구분한다.

  2. 공백만 있는 이름은 원래 입력 문자열이 비어 있지 않다.

  3. 서버 정책의 trim 후에는 빈 문자열이라 거절한다.

학점은 통과해도 새 이름 정책은 실패한다. 이름의 실제 의미 조건을 서버에서 검증한다.

소단원 6.3

로딩·빈결과·실패

아무 카드도 없을 때 기다리는 중인지 결과가 없는지 실패했는지 알 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 비동기 요청은 응답을 기다리는 동안 화면을 계속 표시할 수 있다.

  • HTTP 상태와 자료 내용은 서로 다른 정보다.

  • 같은 요청 화면에서도 여러 상태가 시간에 따라 이어진다.

학습 목표

  • 대기·성공·빈 성공·실패를 구분한다.

  • HTTP 실패와 네트워크 실패의 차이를 설명한다.

  • 늦게 도착한 옛 응답을 걸러 낼 조건을 추적한다.

카드가 없는 화면에서 사용자가 기다릴지, 검색어를 바꿀지, 다시 시도할지 어떻게 알까?

빈 배열 하나로 요청의 의미를 정하지 않는다. 이 보강은 idle, loading, success(items), error(message)의 한 상태를 사용하고 loading 중 이전 결과는 숨긴다. success([])는 오류가 아니라 검색 결과가 없는 정상 완료다.

상태 안내는 시각 문구뿐 아니라 사용자에게 전달되는 방식도 설계해야 한다. 검색 완료 개수 같은 간단한 갱신 안내는 작업의 focus를 빼앗지 않고 전달할 방법을 검토한다. role이나 속성을 적었다고 실제 보조기술 동작이나 전체 접근성 적합성을 시험한 것으로 표시하지 않는다.

먼저 확인할 개념
  • 최신 요청과 마지막 정리

    새 요청의 상태를 오래된 완료가 바꾸지 않도록 번호를 확인한다.

  • 요소 역할과 동작

    읽을 안내와 실행할 재시도 버튼의 책임을 분리한다.

화면에 의미 있는 상태를 이름 붙이기

자체 화면 상태는 idle(아직 요청 안 함), loading(기다리는 중), success(items), error(message)로 둔다. success 안에서 items가 빈 배열이면 정상적으로 검색했지만 결과가 없다는 안내를 표시한다. 초기 빈 배열 하나만으로 요청 전·대기·빈 성공·실패를 모두 판단할 수 없다.

실패 화면에는 무슨 요청이 실패했는지와 다시 시도할 방법을 준다. loading과 error가 동시에 참인 두 불리언 대신 의미가 분명한 상태를 선택하면 모순을 줄일 수 있다. 예제는 이전 결과를 숨기는 단순 정책이다. 이전 결과를 유지하는 화면은 갱신 중이라는 별도 표현이 필요하다.

전송과 응답 내용을 각각 확인하기

fetch는 네트워크 오류 등에서 거절될 수 있지만 404 같은 HTTP 오류 응답을 받으면 Response로 이행할 수 있다. 따라서 응답을 받은 뒤 response.ok를 확인하고, 성공으로 인정한 응답의 JSON 읽기도 기다린다. JSON 파싱 실패도 자료를 정상 사용한 성공으로 취급하지 않는다.

자체 모형은 서버 계약이 성공 응답에서 items 배열을 준다고 가정한다. 200과 items=[]는 빈 성공, 404는 실패, 네트워크 거절도 실패다. 상태 코드가 200이라고 내용 구조까지 자동 증명되지는 않으므로 배열 등 기대 형식 확인도 필요하다. 실제 서버 호출 없이 조건을 종이에 판정한다.

요청의 시작 순서와 도착 순서 구분하기

사용자가 검색 A 다음 B를 시작했는데 B 응답이 먼저 오고 A가 나중에 올 수 있다. 자체 요청 번호 1·2 중 최신 번호를 2로 저장하고, 응답을 적용할 때 번호가 최신과 같은지 검사한다. 옛 응답 1이 새 검색 B의 화면을 덮지 않게 하는 조건이다.

성공뿐 아니라 실패 처리에도 같은 검사를 적용해야 한다. 옛 A가 늦게 실패했다고 현재 B 성공을 오류로 바꾸지 않는다. 취소는 비용을 줄일 수 있지만 이 예제는 취소 API를 구현하거나 모든 경합을 해결했다고 주장하지 않는다. 번호 비교와 상태 전이만 분석하는 의사코드다.

latest = latest + 1
mine = latest
state = loading
try:
    response = await request(query)
    if not response.ok: fail("HTTP 실패")
    items = await readAndValidateItems(response)
    if mine == latest: state = success(items)
catch error:
    if mine == latest: state = error(error.message)
// 실행한 코드가 아닌 요청 번호 모형

재시도

loading에서 예전 결과를 숨기는 정책을 유지한다. 이전 결과를 남기는 제품이라면 갱신 중과 오래된 결과라는 추가 의미를 명시해야 한다. 카드가 없는 세 행은 사용자에게 다른 행동을 안내한다.

중간 과정을 따라가는 예제

A 요청 번호1 후 B 번호2를 시작한다. B는 200과 [선형대수]를 먼저 반환하고 A는 늦게 200과 []를 반환한다. 최종 화면을 구하라.

  1. A 시작에서 latest=1, loading이다. B 시작에서 latest=2, loading이다.

  2. B 성공 처리에서 mine=2=latest라 success([선형대수])를 적용한다.

  3. A는 mine=1≠latest2라 빈 응답을 적용하지 않는다. B의 한 결과를 유지한다.

최종은 B의 성공 결과 선형대수 한 개다. 빈 결과 A가 마지막에 도착했어도 최신 요청은 아니다.

조건을 바꾸어 비교하기

빈 성공을 오류로 바꾼 안내

최신 요청이 200과 유효한 items=[]를 반환했다. 화면은 “서버 실패, 계속 재시도”만 보여 준다.

  1. HTTP와 배열 계약이 성공했다.

  2. 자료 개수 0은 이 검색의 정상 결과다.

  3. 검색어 변경 같은 다음 행동을 안내한다.

success([])의 빈 결과 안내로 고친다. 실제 검색 조건 실패를 서버 오류로 단정하지 않는다.

비교할 점

빈 화면의 모양이 같아도 상태의 원인과 회복 행동이 다르다.

재시도에서 예전 실패가 도착한다

최신 번호 5가 실패한 뒤 사용자가 재시도 6을 시작했다. 6이 유효한 한 결과로 성공하고, 그 뒤 더 오래된 4가 실패한다. 번호 정책은 모든 성공/오류 경로에 적용된다.

  1. 5의 실패는 당시 최신 상태로 표시된다.

  2. 6 시작에서 loading으로 바뀌고 성공에서 한 결과를 보인다.

  3. 4의 늦은 실패는 최신 6과 다르므로 버린다.

최종은 6의 한 결과 성공이다. 과거 오류를 최신 화면에 다시 표시하지 않는다.

다른 문제에 적용하기

과목 목록은 ID1 C, ID2 선형대수, ID3 Python이다. selectedId=3, query=선형이며 필터에서 숨은 선택은 유지한다. 먼저 ID3을 삭제하고, 남은 ID2를 선택한다. 앱 방문 모형은 [목록,ID2,ID3]에서 마지막이 현재이며 뒤로 이동해 ID2 자리에서 push ID1을 한다. 자료 요청 1은 이전 검색이고 새 검색 2를 시작한다. 2는 200과 유효한 items=[]로 먼저 완료하고 1은 뒤늦게 실패한다. 모든 완료는 최신 번호일 때만 반영하며 loading에서는 이전 결과를 숨긴다. 삭제/재선택 뒤 상세, 방문 기록과 현재 위치, 최종 요청 상태 및 사용자에게 줄 다음 행동을 하나의 추적표로 적어라. 화면 선택, 방문 기록, 요청 상태가 자동으로 서로 일치한다고 가정하지 말고 각각의 계약을 사용한다.

선택 과목의 존재와 검색 결과 포함을 별도 확인한다.

힌트 2

새 push는 옛 앞 가지를 바꾸며 최신 빈 성공은 오류가 아니다.

풀이와 답 확인

  1. ID3 삭제 뒤 상세는 선택 없음이고 필터에는 ID2만 남는다.

  2. ID2 선택 뒤 상세는 선형대수다.

  3. 방문에서 뒤로 ID2 후 push ID1이면 [목록,ID2,ID1], 현재 ID1이다.

  4. 이 주소 방문과 별도 과목 선택을 자동 동기화했다고 정하지 않았으므로 앞 단계의 selectedId=2를 임의로 1로 바꾸지 않는다. 실제 앱은 동기화 정책을 구현해야 한다.

  5. 요청 2의 유효한 빈 배열은 success([])이며 옛 1 실패는 버린다.

  6. 검색 결과 없음과 검색어 변경 안내를 제시한다.

상세는 삭제 직후 선택 없음→ID2 재선택 뒤 선형대수, 방문은 [목록,ID2,ID1]에서 ID1, 요청은 success([])다. 주소와 선택의 불일치를 확인하고 실제 앱의 라우트 동기화 책임을 추가로 설계한다.
