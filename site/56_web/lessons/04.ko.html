소단원 4.1

객체·모듈·함수

같은 점수 객체를 두 이름으로 부르면 점수가 두 개 생길까?

준비 개념과 학습 목표

준비 개념

  • 속성은 객체의 이름과 값의 연결이다. 객체 안의 함수 속성은 메서드로 사용할 수 있다.
  • 함수 값과 호출 결과는 다르다. f 를 전달하는 것과 f()를 실행하는 것을 구별한다.
  • const 는 변수의 다른 값 재대입을 막는다. 그 변수가 가리키는 객체의 모든 속성이 자동 불변이라는 뜻은 아니다.

학습 목표

  • 객체 참조 공유와 별도 객체의 차이를 추적한다.
  • export/import 로 공개 함수와 파일 범위를 연결한다.

값이 같은 객체와 같은 객체는 다르다

const a={points:40}, b=a 이면 b 는 같은 객체를 가리킨다. b.points=70 은 새 점수 객체를 만드는 것이 아니라 공유 객체의 속성을 바꾸므로 a.points 도 70 이다. 반면 c={points:70}은 내용은 같아 보여도 별도로 만든 객체다. a===b 는 참, a===c 는 거짓으로 객체 정체성을 비교한다.

const 로 a 를 선언해도 a.points=70 은 허용될 수 있다. a={points:80}처럼 변수 자체를 재대입하는 것과 구별한다. 얕은 복사는 바깥 객체만 새로 만들고 안쪽 객체를 공유할 수 있다. 이 단원은 단순 own data property 만 있는 객체로 제한하므로 getter·prototype·Proxy 의 별도 동작을 복사 예에 섞지 않는다.

함수에 필요한 자료를 전달한다

function addScore(s,n){return s.points+n;}은 객체 s 를 읽고 합을 반환한다. 객체를 읽기만 하는 함수와 s.points+=n 처럼 변경하는 함수는 다른 계약이다. 호출자는 n 이 점수의 증가인지 대체값인지, 입력 유효 범위와 반환 형식을 확인해야 한다. 객체 참조를 인자로 전달한 뒤 함수가 속성을 바꾸면 바깥 관찰도 바뀔 수 있다.

메서드 호출 s.show()의 this 와 함수만 꺼내 호출하는 방식의 this 는 항상 같지 않다. 처음에는 입력을 명시한 일반 함수를 사용해 의존을 드러낼 수 있다. 이 예제의 Number 는 작은 정수로 제한하여 안전한 정수 범위·반올림·문자열 덧셈 문제가 없다. 실제 사용자 입력 문자열은 검증과 변환을 별도로 해야 한다.

모듈은 공개 이름과 범위를 정한다

별도 score.js 에서 export function total(s){return s.points;}를 선언하고 main.js 가 import {total} from "./score.js"로 받는 구성을 생각한다. total 은 해당 모듈이 공개한 이름이며 같은 이름의 private 보조 함수까지 전부 전역으로 퍼지는 것은 아니다. 상대 URL 은 가져오는 파일의 위치와 연결되어 옮길 때 경로를 확인한다.

브라우저에서는 script type="module"로 불러오고 JavaScript MIME·서버/URL·CORS 조건을 맞춰야 한다. module 은 기본 strict mode 이며 일반 module script 는 자동으로 지연된다. imported binding 을 받는 쪽에서 재대입할 수 없다고 해서 내보낸 객체 속성까지 자동 변경 불가인 것은 아니다. 아래는 두 파일을 구별한 설명 코드이며 파일 로드나 브라우저 실행을 수행한 결과가 아니다.

// score.js
export function total(s) { return s.points; }
// main.js (별도 파일)
import { total } from "./score.js";
const a = { points: 40, meta: { label: "A" } };
const b = a;
const c = { points: a.points, meta: a.meta };
b.points = 70;
c.meta.label = "B";

중간 과정을 따라가는 예제

위 두 파일의 main.js 문장 순서만 종이로 추적하라. a/b/c 의 points 와 meta.label, a===b/a===c, total(c)를 구하라. 두 모듈 로드가 성공한다는 조건을 가정한다.

  1. 처음 a 와 b 는 같은 객체다. c 는 별도 바깥 객체이며 points40 을 복사하고 meta 는 같은 안쪽 객체를 가리킨다.
  2. b.points=70 뒤 a.points=b.points=70 이다. c.points 는 독립 숫자 속성이므로 40 으로 남는다.
  3. c.meta.label="B"는 공유 meta 를 변경해 a/b/c 모두 label B 를 본다. 바깥 복사만으로 깊은 독립을 얻지 못했다.
  4. a===b 는 참, a===c 는 거짓이다. total(c)는 c.points 를 읽어 40 을 반환한다. 모듈 함수가 호출될 때 입력 c 를 사용한다.

points 는 70/70/40, label 은 모두 B, 비교는참/거짓, total(c)=40 이다. 예상 종이 결과다.

종이와 본문으로 직접 해보기

d={points:a.points,meta:{label:a.meta.label}}를 위 마지막 상태에서 만든 뒤 d.meta.label="D"로 바꾼다. a 의 label 과 d 의 points 는? main.js 에서 imported total 을 다른 함수로 재대입할 수 있는가?

힌트 보기

이번에는 meta 도 새 객체인지 화살표를 그린다. imported binding 과 객체 속성의 변경을 구분한다.

풀이 보기

a.meta.label 은 B 로 남고 d.points 는 70 이다. d 의 meta 를 새로 만들었기 때문이다. import 한 total binding 은 가져오는 쪽에서 재대입할 수 없다. export 된 값이 객체일 때 속성 변경 가능성과는 별개다.

오해와 반례

객체 속성이 모두 같은 숫자/글자면 ===도 반드시 참이다.

새로 만든 {points:70} 두 객체는 별도 정체성이므로 ===는 거짓이다. 필요한 값 동등성은 점수 등 비교할 필드와 중첩 구조의 규칙을 별도로 정해야 한다.

소단원 4.2

DOM과 이벤트

버튼을 누르기 전에 함수를 등록하는 것과 지금 실행하는 것은 어떻게 다를까?

준비 개념과 학습 목표

준비 개념

  • DOM 은 문서를 node 와 element 의 트리로 다루는 Web API 다. JavaScript 언어 자체의 일부와 구별한다.
  • querySelector 는 유효한 CSS selector 의 첫 일치 element 를 찾으며 없으면 null 이다.
  • 이벤트 handler 는 특정 사건 때 호출할 함수다. 등록 함수의 반환값과 사건 처리 결과는 별개다.

학습 목표

  • 선택 실패와 callback 등록/호출의 차이를 설명한다.
  • 동일 함수 객체의 등록·제거 및 once 를 사건열로 추적한다.

문서에서 대상을 찾고 존재를 확인한다

document.querySelector("#add")는 id add 인 첫 element 를 돌려준다. element 가 없으면 null 이며 그 상태에서 addEventListener 를 호출하면 정상 등록이 아니다. 잘못된 CSS selector 자체는 null 대신 SyntaxError 를 일으킬 수 있어 존재 실패와 문법 실패도 구별한다. HTML 파싱 전 코드가 실행되는지, selector 가 실제 구조에 맞는지 확인한다.

HTML 문자열과 실제 DOM 트리는 공백 text node 등을 포함해 차이가 날 수 있다. DOM 은 내용·구조를 바꾸는 인터페이스이며 화면의 실제 paint 시간과 같은 개념은 아니다. 브라우저 밖 JavaScript 런타임이 자동으로 같은 document 객체를 제공한다고 가정하지 않는다.

함수 객체를 등록하고 같은 객체로 제거한다

button.addEventListener("click", onClick)은 onClick 함수 값을 등록한다. onClick()를 인자로 쓰면 지금 호출한 반환값을 넘기므로 보통 원하는 등록이 아니다. 같은 target/type/callback/capture 의 등록을 반복해도 같은 listener 가 중복되지 않는다. 반면 코드 모양이 같은 익명 함수를 매번 새로 만들면 서로 다른 함수 객체가 등록될 수 있다.

removeEventListener 에 등록 당시의 함수 객체와 맞는 capture 를 전달해야 한다. 새 익명 함수로 같은 본문을 적어도 이전 함수와 동일하지 않다. once:true 는 등록 후 첫 전달 때 최대 한 번 호출하고 제거하는 선택이다. 이 단원의 trace 는 예외·재등록·다른 listener 와 default action 이 없다고 제한한다.

이벤트 반응과 기본 동작은 분리한다

클릭, 키 입력, form submit 처럼 사건마다 등록할 이름과 대상이 다르다. submit handler 에서 preventDefault 를 호출하는 것은 취소 가능한 기본 제출 동작을 막는 것이며 모든 이벤트 전파나 다른 handler 를 자동 제거하는 것은 아니다. stopPropagation 은 전파 경로와 관련되며 같은 단어로 취급하지 않는다. passive listener 에서는 preventDefault 를 할 수 없다는 계약도 확인한다.

작은 입력 검사가 모든 악의적 입력을 막지는 않는다. textContent 는 값을 텍스트로 넣고 innerHTML 은 HTML 구문을 해석하므로 사용자 글자를 표시할 때 의도에 맞는 API 를 택한다. textContent 를 부모에 지정하면 기존 자식들이 교체되므로 그 아래 버튼과 연결된 구조도 사라질 수 있다. 예제는 화면 조작을 실제 수행하지 않는 사건 모형이다.

중간 과정을 따라가는 예제

존재하는 버튼의 click listener 로 inc 를 같은 capture=false 로 두 번 등록한다. inc 는 count 를 1 증가시킨다. 별도로 once:true 인 bonus 는 count 를 10 증가시킨다. 초기 count0 에서 click 두 번, inc 제거, click 한 번의 count 를 추적하라. listener 가 처리 도중 등록/제거되거나 예외를 내지 않는다.

  1. 같은 inc 함수 객체의 반복 등록은 동일 listener이므로 지속 listener는 한 개다. bonus는 다른 함수 객체이며 once다.
  2. 첫 click은 inc의 +1과 bonus의 +10을 반영하여 count=11이다. bonus는 제거된다. 합계는 두 순서 어느 경우에도 동일하다.
  3. 둘째 click은 inc만 남아 count=12다. 같은 함수를 두 번 적었다고 +2하지 않는다.
  4. 같은 inc와 capture=false로 제거한 뒤 셋째 click은 이 모형에 handler가 없어 count=12로 남는다. 실제 기본 동작은 모형에서 제외했다.

count0→11→12→12 다. 함수 객체의 동일성과 once 수명을 함께 추적한 예상 결과다.

종이와 본문으로 직접 해보기

inc 대신 서로 다른 익명 함수 두 개가 각각 count를 1 증가시키도록 등록되었다. 초기 0에서 click 한 번의 결과는? 없는 #missing에 querySelector한 결과도 적어라.

힌트 보기

같은 본문과 같은 함수 객체는 다르다. 선택하는 문자열은 유효 CSS selector 라고 가정한다.

풀이 보기

각각 한 번 호출되어 count=2다. #missing은 일치 element가 없으므로 null이다. null일 때 등록을 진행하지 않는 경로를 두어야 한다. 새 익명 함수를 removeEventListener에 넘겨도 기존 둘이 자동 제거되지 않는다.

오해와 반례

preventDefault 는 같은 사건의 모든 listener 호출을 막는다.

기본 form 제출을 취소해도 별도 등록된 로그 listener는 호출될 수 있다. 전파 중단과 기본 동작 취소는 서로 다르고 passive/취소 가능 조건도 확인해야 한다.

소단원 4.3

상태와 렌더링

숫자 변수를 바꾸었는데 화면 글자가 옛값이라면 어떤 연결이 빠졌을까?

준비 개념과 학습 목표

준비 개념

  • 상태는 프로그램이 기억하는 자료이며 DOM 표시는 그 상태의 한 표현이다.
  • render는 이 단원에서 상태를 읽어 정해진 DOM 속성을 갱신하는 함수다.
  • 동기 순차 모형에서는 한 handler 가 끝난 뒤 다음 handler 가 시작한다. 비동기 작업과 framework 스케줄링은 별도 계약이다.

학습 목표

  • 상태 전이와 표시 갱신을 분리하고 연결한다.
  • 같은 상태의 반복 render와 중복 listener 등록의 차이를 설명한다.

한 가지 자료에서 표시를 계산한다

count 를 별도 let 변수로 기억하고 render 가 output.textContent=String(count)로 표시하도록 한다. +1 버튼은 count 를 바꾼 뒤 render 를 호출한다. 화면 글자를 직접 읽어 다시 숫자로 해석하는 곳과 count 를 읽는 곳이 섞이면 공백·번역·오류 메시지 때문에 서로 다른 기준이 생길 수 있다. 상태의 원본을 정하고 표시는 거기서 유도한다.

count=2 를 대입해도 JavaScript 가 모든 DOM 과 자동으로 연결해 주지 않는다. render 를 호출하거나 이를 관리하는 library 의 규칙을 사용해야 한다. DOM 변경이 곧 사용자에게 paint 완료라는 보장도 아니다. 이 단원의 확인은 상태와 textContent 의 논리적 값이며 실제 화면의 시각 측정이 아니다.

전이 규칙과 오류 조건을 먼저 적는다

자체 counter 모형은 0≤count≤3 이다. ADD 는 count<3 일 때 1 을 더하고 그 외에는 유지한다. RESET 은 0 으로 설정한다. reducer(state,action)가 새 상태를 정하고 render 가 이를 읽으면 예제·활동에서 UI 없이 전이를 계산할 수 있다. 알 수 없는 action 은 유지한다고 명시한다.

다른 사건이 이전 상태를 어떻게 읽는지 확인한다. plain JavaScript 의 동기 변수 갱신과 React useState 의 render snapshot 은 다르다. React 에서는 한 render 의 handler 가 본 state 값이 setter 직후 바뀌지 않는다. 이 사실을 모든 JavaScript 변수에도 적용하면 안 된다. 본문 예제는 React 를 쓰지 않는 명시 동기 모형이다.

표시 갱신에 다른 효과를 섞지 않는다

같은 count 에서 render 를 반복하면 같은 textContent 를 쓰도록 만든다. 반면 render 마다 새 익명 click listener 를 등록하면 상태 표시는 같아도 다음 클릭의 효과가 배가될 수 있다. 초기 연결과 표시 갱신을 분리하고 listener 의 수명을 따로 관리한다. 사용자 요청을 전송하는 효과도 render 가 호출될 때마다 반복할지 계약을 분리한다.

textContent 를 쓰기만 하는 render 는 지정 대상의 기존 자식을 교체한다. output 전용 영역을 택하고 입력 버튼 전체 부모를 무심코 덮어쓰지 않는다. 복잡한 UI 에서는 부분 갱신·안정적인 항목 식별·focus 보존이 중요하지만 이 모형으로 그 기능이 자동 보장되는 것은 아니다. 네트워크 재시도·서버 저장·브라우저 측정은 실행하지 않았다.

// output element가 존재하고 DOM 연결이 끝났다는 설명 조건
let count = 0;
function reduce(s, action) {
  if (action === "RESET") return 0;
  if (action === "ADD" && s < 3) return s + 1;
  return s;
}
function render(output) { output.textContent = String(count); }
function dispatch(action, output) {
  count = reduce(count, action);
  render(output);
}

중간 과정을 따라가는 예제

초기 count 0 에서 render 한 뒤 ADD, ADD, ADD, ADD, RESET, ADD 를 순서대로 dispatch 한다. 다른 이벤트와 예외는 없고 output 이 존재한다. 상태와 textContent 를 계산하라.

  1. 초기 render 뒤 상태 0/표시 "0"이다. 첫 ADD 뒤 1/"1", 둘째 ADD 뒤 2/"2"다.
  2. 셋째 ADD 뒤 3/"3"이다. 범위의 상한 3 에 이른다.
  3. 넷째 ADD 는 s<3 이 거짓이라 상태 3 을 유지하고 render 도 "3"을 쓴다. 누락된 render 가 아니라 정책상 유지다.
  4. RESET 뒤 0/"0", 마지막 ADD 뒤 1/"1"이다. 각 dispatch 는 전이 뒤 표시를 동기 갱신하지만 실제 paint 시점은 계산하지 않았다.

최종 count=1/표시 "1"이며 상태 열은 0→1→2→3→3→0→1이다.

직접 대입 후 상태 3/표시 "2"로 어긋난다. render 두 번 뒤 둘 다 3/"3"이며 count 를 증가시키지 않는다. UNKNOWN 을 dispatch 하면 reduce 가 3 을 유지하고 render 도 "3"을 쓴다. 이 순차 모형은 자동 저장이나 화면 관측의 증거가 아니다.

오해와 반례

render 가 여러 번 실행될 수 있으니 그 안에 매번 새 listener 를 붙여도 안전하다.

새 함수 객체 listener 가 두 개 남으면 한 click 에서 ADD 를 두 번 처리할 수 있다. count 0 의 상한 3 모형에서는 한 click 으로 2 가 될 수 있어 원래 한 click 한 증가 약속을 어긴다. render 의 같은 표시와 다음 사건의 효과는 분리해야 한다.

초기 0≤s≤3 에서 RESET/ADD/UNKNOWN 각 경우가 같은 불변식을 보존함을 증명하라. 비동기 응답이 A 요청 뒤 B 요청을 보내고 B 가 먼저 도착하면 화면이 오래된 A 로 덮이지 않도록 request ID/version 등 별도 규칙이 필요하다. 이 심화는 문제 제기이며 실제 race 재현이나 framework 실행 검증이 아니다.
