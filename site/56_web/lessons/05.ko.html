소단원 5.1

event loop

타이머를 0밀리초로 설정했는데 왜 뒤에 적은 문장이 먼저 나타날까요?

준비 개념과 학습 목표

준비 개념

  • 함수 호출 스택은 아직 끝나지 않은 호출의 목록이다.

  • 콜백은 지금 직접 호출하거나 나중에 호스트가 호출하도록 등록할 수 있다.

  • 이 단원은 다른 코드가 개입하지 않는 브라우저의 한 Window agent를 가정한다.

학습 목표

  • 동기 구간과 task·microtask를 분리해 순서를 추적한다.

  • 0밀리초 타이머와 실제 실행 시각을 구별한다.

  • 긴 계산과 microtask의 과도한 연쇄가 응답성을 낮추는 이유를 설명한다.

실행하는 코드와 기다리는 작업

검색 버튼을 누르면 요청을 시작하고 화면은 계속 사용 가능해야 한다. 실행 중인 JavaScript 함수는 스택에 올라가며, 일반적인 한 agent의 동기 구간은 다른 callback이 임의의 문장 사이에 끼어들어 실행하지 않는다. 이를 run-to-completion의 직관으로 이해하자. await를 포함한 함수는 중간에 재개 구간으로 나뉘므로 함수 전체가 한 번에 끝난다는 뜻은 아니다.

브라우저는 네트워크와 타이머 같은 대기 작업을 관리한다. 나중에 callback을 실행할 수 있는 작업을 큐에 등록하고 event loop가 실행 기회를 조정한다. 비동기는 기다리는 동안 다른 일을 할 수 있다는 뜻이며 JavaScript의 모든 계산이 자동으로 여러 CPU에서 동시에 실행된다는 뜻은 아니다. Worker는 별도 agent를 사용하는 다른 주제다.

두 종류의 대기 줄

이 단원에서 타이머 callback은 task, 이미 이행된 Promise의 then callback과 queueMicrotask callback은 microtask로 추적한다. 현재 스크립트가 동기 구간을 마치면 microtask checkpoint에서 큐가 빌 때까지 오래된 항목부터 처리한다. 그 안에서 추가한 microtask도 같은 checkpoint의 처리 대상이 된다.

실제 HTML에는 여러 task source와 task queue가 있다. 따라서 모든 사용자 입력·네트워크·타이머가 하나의 전역 FIFO에 있다는 그림은 정확하지 않다. 아래처럼 다른 개입이 없는 자체 예제에서는 현재 스크립트의 동기 문장, 등록한 microtask, 타이머 순서만 판단한다. Node.js 등의 호스트에 이 모형을 그대로 적용하지 않는다.

// 브라우저의 일반 script에서 한 번 실행하는 자체 예제. 실제 실행 미수행.
console.log("A");
setTimeout(() => console.log("T"), 0);
Promise.resolve().then(() => {
  console.log("B");
  queueMicrotask(() => console.log("C"));
});
console.log("D");

실행 순서와 화면 갱신의 간격

타이머의 0은 지금 스택을 중단하고 즉시 실행하라는 명령이 아니다. 대기 시간이 지나도 현재 작업과 checkpoint가 끝나야 실행 기회를 얻는다. 기기 부하와 브라우저 정책 때문에 정확한 시각은 이 코드만으로 보장하지 않는다. 예제의 예상 로그 순서는 A,D,B,C,T이지만 각 로그 사이의 밀리초 차이는 계산하지 않는다.

계산이 오래 걸리는 동기 구간은 같은 agent의 입력 처리 기회를 지연시킨다. microtask가 계속 자기 자신을 등록해 큐가 비지 않는 경우도 다음 task로 넘어가기 어렵다. 화면 그리기는 매 callback 뒤에 반드시 일어나지 않고 별도의 rendering opportunity와 조건에 따른다. 작은 작업으로 나누는 방법을 선택할 때 단순히 Promise로 포장하는 것만으로 화면 갱신이 보장된다고 생각하지 말자.

중간 과정을 따라가는 예제

다른 스크립트·입력·예외가 없는 위 브라우저 script의 로그 순서를 종이로 구하라. B 실행 직전과 직후 microtask 큐도 적어라.

  1. 현재 script에서 A를 기록하고 타이머 T를 예약한다. T는 지금 실행되지 않는다.

  2. Promise.resolve()는 이행된 promise를 만들고 then의 B callback을 microtask로 등록한다.

  3. 동기 구간을 계속하여 D를 기록한다. B 실행 직전 큐는 [B]다.

  4. checkpoint에서 B를 꺼내 B를 기록하고 C를 등록한다. B 실행 직후 대기 큐는 [C]다.

  5. C를 실행하고 큐가 빈 후 타이머 task가 실행 가능한 기회를 얻으면 T를 기록한다.

예상 로그 A,D,B,C,T. 큐 상태는 [B]에서 [C], 그 뒤 []이다. 실제 브라우저 로그나 시간 측정 결과가 아니다.

종이와 본문으로 직접 해보기

같은 조건에서 B 안의 queueMicrotask 대신 setTimeout으로 C를 예약한다. 원래 T와 새 C는 같은 Window의 타이머 task source이고 둘 다 실행 가능해진 뒤 순서대로 처리된다고 가정한다. 로그와 checkpoint의 차이를 설명하라.

힌트 보기

원래 T의 타이머 예약이 C의 예약보다 앞이다. C가 이제 microtask 큐에 들어가지 않는다는 점을 표시하라.

풀이 보기

A,D,B 다음 checkpoint는 비게 된다. 가정한 타이머 처리에서는 먼저 예약된 T가 먼저 실행되고 뒤에 C가 실행되어 A,D,B,T,C다. 이는 명시한 타이머 조건의 결과다. 서로 다른 task source의 모든 작업 순서를 이 한 예제로 단정할 수 없다.

오해와 반례

Promise.then으로 큰 계산을 옮기면 화면은 반드시 즉시 반응한다.

then callback의 계산 자체도 해당 agent에서 동기 실행된다. microtask로 옮긴 백만 번 반복은 여전히 입력 처리를 오래 지연시킬 수 있다. 또한 무한한 microtask 연쇄는 task 진행을 막는 반례다. 대기와 계산량을 따로 분석해야 한다.

소단원 5.2

promise·async

함수가 결과 대신 Promise를 돌려준다는 것은 어떤 약속일까요?

준비 개념과 학습 목표

준비 개념

  • 값 7과 나중에 7로 이행될 Promise는 서로 다른 대상이다.

  • 오류를 throw하면 가장 가까운 적용 가능한 오류 처리로 전달된다.

  • 앞 소단원의 동기 구간과 microtask 순서를 사용한다.

학습 목표

  • pending·fulfilled·rejected와 handler의 역할을 설명한다.

  • async 함수의 첫 await 전후 구간을 추적한다.

  • 반환한 값과 promise, 오류 처리 연결을 구별한다.

결과의 상태를 나타내는 객체

Promise는 진행 중인 비동기 작업의 최종 결과 또는 실패를 받을 수 있는 객체다. pending은 아직 이행이나 거부로 정해지지 않은 상태, fulfilled는 결과 값이 정해진 상태, rejected는 실패 이유가 정해진 상태다. 결과를 기다리는 then과 catch는 새로운 promise를 반환하여 다음 처리를 연결한다. Promise 자체가 네트워크 요청을 만드는 것은 아니다.

new Promise에 전달한 executor는 생성할 때 동기로 호출된다. 반면 이미 이행된 promise에 등록한 then handler도 지금 문장 사이에서 직접 실행되지 않고 나중에 실행된다. resolve에 다른 promise를 전달하면 그 결과를 따라가며 아직 pending일 수 있다. resolved라는 말과 fulfilled를 언제나 같은 상태로 외우지 말자. 무거운 계산을 executor에 넣으면 생성 시점부터 막힐 수 있다.

await는 현재 함수의 후속 구간을 기다리게 한다

async 함수 호출은 promise를 돌려준다. 첫 await까지는 호출 과정에서 동기적으로 진행하며, await 이후 구간은 기다린 값이 준비된 뒤 나중에 재개한다. await가 현재 agent의 모든 코드를 멈추는 것은 아니다. 아래 f의 반환 7은 호출 시 곧바로 얻는 숫자 7이 아니라 p의 최종 이행 값이다.

자체 예제는 정상적인 내장 Promise와 다른 개입이 없는 브라우저 script를 가정한다. 먼저 A를 기록한 뒤 f에 들어가 F를 기록한다. await 뒤의 G는 바로 기록되지 않으므로 호출자는 B까지 진행한다. 재개된 f가 G를 기록하고 7을 반환한 뒤 p에 등록한 handler가 7을 기록한다.

// 브라우저 script 문맥. 종이 예상 결과만 제시한다.
async function f() {
  console.log("F");
  const value = await Promise.resolve(5);
  console.log("G");
  return value + 2;
}
console.log("A");
const p = f();
console.log("B");
p.then(value => console.log(value));

값과 실패를 다음 단계로 전달한다

then handler에서 return 8을 하면 그 then이 반환한 promise는 8로 이행한다. return을 빠뜨리면 해당 handler의 정상 반환 값은 undefined다. handler가 throw하면 다음 promise는 거부된다. catch가 값을 정상 반환하면 실패를 처리한 이후의 promise는 그 값으로 이행할 수 있으므로 실패가 영원히 거부 상태로만 흐르는 것은 아니다.

async 함수 안에서 await한 거부는 해당 위치에서 던져지는 오류처럼 try/catch로 처리할 수 있다. 다만 시작한 모든 비동기 작업이 그 try/catch와 연결되어야 한다. 별도로 시작하고 반환하거나 await하지 않은 promise의 실패가 자동으로 연결되지는 않는다. 여러 독립 작업은 Promise.all 또는 allSettled로 함께 연결할 수 있지만 all이 거부되었다고 다른 작업이 자동으로 취소되는 것은 아니다.

중간 과정을 따라가는 예제

위 f 예제의 로그 순서와 p의 최종 값을 구하라. 첫 await 직후 호출자의 위치도 적어라.

  1. A를 기록하고 f를 호출한다. f 내부는 await 전까지 동기로 진행하므로 F가 두 번째다.

  2. Promise.resolve(5)는 5로 이행된 promise다. await는 f의 후속 구간을 나중에 재개하도록 하고 호출자에게 p를 돌려준다.

  3. 호출자는 B를 기록하고 p에 then handler를 등록한다. 이때 G나 7은 아직 기록하지 않았다.

  4. f가 재개되면 value=5로 G를 기록하고 5+2=7을 반환하여 p를 이행시킨다.

  5. 그 뒤 p의 handler가 7을 기록한다.

예상 로그 A,F,B,G,7이고 p의 이행 값은 숫자 7이다. 함수 호출의 반환 객체 p와 그 최종 값을 구별한다.

종이와 본문으로 직접 해보기

종이로 Promise.resolve(4).then(x => x * 3).then(() => { throw new Error("bad"); }).catch(() => 9).then(x => x + 1)의 각 단계 상태와 최종 값을 적어라. 마지막 promise에는 관찰 handler를 붙일 수 있다고 가정한다.

힌트 보기

처음 4는 다음 단계에서 12다. throw 단계는 거부이고 catch의 정상 반환으로 다시 이행된다.

풀이 보기

첫 값 4→첫 then의 이행 값 12→두 번째 then의 거부 이유 Error("bad")→catch의 이행 값 9→마지막 then의 이행 값 10이다. 마지막 promise가 10으로 이행할 뿐 코드에 console.log가 없으므로 자동으로 10을 화면에 찍지는 않는다.

오해와 반례

async를 함수 앞에 붙이면 함수의 모든 문장이 나중에 실행되고 오류도 자동으로 사라진다.

f의 F는 첫 await 전 동기로 기록되는 반례다. 또한 catch하지 않은 throw는 반환 promise의 거부로 전달되며 적절한 처리가 필요하다. await 없이 별도 작업을 시작했다면 그 실패가 현재 호출의 성공과 별개일 수도 있다.

자기점검

async 함수가 return 3을 하면 호출자가 숫자 3을 직접 받는가?

답과 이유 보기

3으로 이행할 promise를 받는다.

async 호출의 반환 형식과 그 최종 결과 값은 다르다.

executor 안의 긴 반복은 생성 시점에 막을 수 있는가?

소단원 5.3

fetch와 오류·취소

서버가 404를 답했는데 catch가 실행되지 않는 이유는 무엇일까요?

준비 개념과 학습 목표

준비 개념

  • HTTP 상태와 응답 본문은 서로 다른 정보다.

  • JSON은 데이터 문법이며 JavaScript 객체의 원하는 필드를 보장하지 않는다.

  • await와 try/catch 및 Promise의 이행·거부를 구별한다.

학습 목표

  • 네트워크 실패·HTTP 실패·본문 파싱·형식 검사를 구별한다.

  • AbortController의 signal을 요청에 연결한다.

  • 취소와 오래된 결과 방지를 서로 다른 장치로 설명한다.

응답을 받았다고 자료가 올바른 것은 아니다

fetch(url)은 요청의 응답을 나타내는 promise를 반환한다. 네트워크 실패 같은 경우는 거부될 수 있지만 HTTP 404나 500 응답은 Response로 정상 이행할 수 있다. 응답의 ok는 200~299 상태인지를 나타낸다. 따라서 원하는 정책이 성공 상태만 받아들이는 것이라면 명시적으로 ok를 확인한다. 응답 헤더가 왔어도 본문 전체가 아직 도착하지 않았을 수 있다.

아래는 브라우저의 같은 출처 JSON endpoint가 {title: 문자열}을 준다는 자체 계약을 읽는 함수 정의다. 실제 서버나 요청을 제공하거나 실행하지 않는다. fetch의 응답을 기다린 뒤 HTTP 조건을 확인하고, json()으로 본문을 비동기적으로 읽어 파싱하며, 마지막으로 title의 자료형을 검사한다. 유효한 JSON 숫자 7도 이 계약에서는 실패다.

// 브라우저에서 사용하는 함수 정의. 실제 요청·서버·코드 실행 미수행.
async function loadTitle(url, signal) {
  const response = await fetch(url, { signal });
  if (!response.ok) throw new Error("HTTP " + response.status);
  const data = await response.json();
  if (data === null || typeof data !== "object" ||
      typeof data.title !== "string") {
    throw new TypeError("Expected an object with a string title");
  }
  return data.title;
}

어디에서 실패했는지 구별한다

status=404이면 위 함수는 HTTP 오류를 던져 본문 파싱 단계로 넘어가지 않는다. status=200이어도 본문이 깨진 JSON이면 json()에서 실패한다. JSON {"title":17}은 파싱은 성공하지만 자체 자료형 검사에서 실패한다. 상태 204처럼 성공 범위지만 본문이 없는 응답도 이 JSON 계약에는 그대로 맞지 않는다. 오류 메시지와 화면의 안내는 이러한 원인을 구별할 수 있어야 한다.

응답 body는 소비되는 stream이다. 같은 Response에서 json()을 두 번 호출해 두 개의 독립 사본을 얻는 것으로 생각하지 말자. 서로 다른 출처 요청에는 CORS 조건도 적용되며 no-cors를 쓰면 일반적으로 opaque 응답의 내용을 읽을 수 없다. 이 설정을 권한 우회 수단처럼 사용하지 않는다. 유효한 자료를 받은 뒤에도 화면에 넣을 때 HTML로 해석하지 않는 안전한 표시 방법을 선택해야 한다.

취소와 최신 요청의 결과 선택

AbortController를 만들고 controller.signal을 fetch 옵션에 연결한 뒤 controller.abort()를 호출하면 해당 신호를 따르는 요청·본문 읽기가 취소될 수 있다. 기본 abort의 실패는 AbortError로 처리할 수 있다. 이미 취소한 signal을 다음 요청에 재사용하지 않고 새 controller를 만든다. abort가 서버에서 이미 수행된 변경을 되돌려 주는 것은 아니다.

검색어를 바꾸면 예전 요청이 늦게 도착해 새 결과를 덮어쓸 수 있다. 요청마다 증가하는 번호를 부여하고, 결과나 오류를 화면에 반영하기 직전 그 번호가 현재 최신인지 검사하면 오래된 결과를 버릴 수 있다. 취소는 낭비를 줄이는 시도이고 번호 검사는 어떤 결과를 표시할지 정하는 정책이다. 이미 끝난 요청이나 취소를 따르지 않는 후속 처리도 있으므로 두 장치를 구별한다. 페이지를 떠날 때의 정리와 개인정보를 URL·로그에 남기지 않는 정책은 별도 설계가 필요하다.

중간 과정을 따라가는 예제

loadTitle에 같은 출처의 가상 응답 네 개를 넣는다고 가정하라: A=404 및 {"title":"없음"}, B=200 및 깨진 JSON, C=200 및 {"title":17}, D=200 및 {"title":"행렬"}. 각 실패 위치나 최종 결과를 종이로 판정하라.

  1. A의 fetch는 Response로 이행할 수 있지만 ok=false이므로 HTTP 404 오류를 던진다. title 내용은 읽지 않는다.

  2. B는 ok=true라 본문 단계로 간다. JSON 문법이 깨졌으므로 json()의 promise가 거부되어 함수도 거부된다.

  3. C는 파싱에 성공한다. 그러나 title은 number라서 TypeError를 던지고 함수는 거부된다.

  4. D는 HTTP·파싱·계약 검사를 통과한다. title 문자열을 반환하여 함수의 promise가 "행렬"로 이행한다.

A는 상태 검사, B는 파싱, C는 자료형 검사에서 실패하며 D만 "행렬"을 결과로 얻는다. 이는 가상 응답의 종이 판정이며 요청을 실행하지 않았다.

종이와 본문으로 직접 해보기

요청 1은 검색어 "수", 요청 2는 "수학"이다. 최신 번호는 2다. 2가 먼저 결과 "새 목록"을 주고 1이 나중에 "옛 목록"을 준다. 아무 검사 없이 반영할 때와 현재 번호 검사 후 반영할 때 최종 화면을 비교하라. 1의 취소가 실제로 성공했는지는 가정하지 않는다.

힌트 보기

완료 순서와 시작 번호는 다르다. 화면에 쓰기 직전에 완료 요청의 번호를 최신 2와 비교한다.

풀이 보기

검사 없이 쓰면 새 목록을 먼저 표시한 뒤 옛 목록으로 덮어 최종 옛 목록이다. 번호 검사에서는 2=2인 결과만 반영하고 1≠2인 결과를 버려 최종 새 목록이다. 오래된 오류도 같은 검사로 거르면 현재 검색의 성공 화면을 예전 오류로 바꾸지 않는다.

오해와 반례

abort만 호출하면 서버의 모든 작업이 취소되고 예전 결과가 화면에 나올 가능성도 완전히 없어진다.

서버가 이미 저장한 주문은 클라이언트 신호로 자동 취소되지 않는 반례다. 취소 시점 전에 끝난 처리와 이후의 별도 작업도 있을 수 있다. 요청 취소·화면 반영 정책·서버의 변경 취소 절차는 각각 명시해야 한다.
