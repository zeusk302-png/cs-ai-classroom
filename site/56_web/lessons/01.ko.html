소단원 1.1

URL·request·response

주소의 #intro와 ?topic=web은 서버에 똑같이 전달될까?

준비 개념과 학습 목표

준비 개념

  • 텍스트는 문자들의 순서다. 파일은 저장된 데이터 묶음이며 URL은 그 파일 자체가 아니라 자원에 접근하는 주소 표현이다. 메시지는 보내는 쪽과 받는 쪽이 약속한 구조의 데이터다.

학습 목표

  • URL 구성요소를 구분한다

  • GET 요청과 상태·헤더·본문의 역할을 추적한다

  • 주소 fragment와 서버 요청 대상의 차이를 설명한다

교재의 다음 장 링크를 눌렀는데, 왜 같은 파일 이름이 다른 주소가 될까?

도서관에서 “옆 칸”을 말하려면 지금 선 칸을 알아야 한다. 웹의 상대 주소도 기준 주소와 함께 읽는다. 주소의 경로와 서버가 하는 일은 별개다. 아래는 DNS·캐시·실제 파일 제공을 가정하지 않은 주소 해석 문제이며, 모든 example 도메인은 설명용이다.

기준을 https://study.example/chapters/start.html로 정하자. next.html은 마지막 경로 조각 start.html을 바꾼 /chapters/next.html로 간다. /next.html처럼 처음에 /를 적으면 호스트의 루트 경로에서 출발한다. 이번 예제에는 HTML base 요소나 자바스크립트로 기준을 바꾸는 동작이 없다. 주소를 맞게 해석해도 서버에 자원이 있는지는 응답으로 따로 확인한다.

먼저 확인할 개념
  • 입력·처리·출력

    주소 입력을 해석하는 처리와 서버가 돌려주는 응답을 분리한다.

  • 응용 메시지와 계층

    HTTP 메시지의 의미를 패킷 전달이나 링크 전송과 같은 것으로 취급하지 않는다.

주소를 분해하면 질문이 보인다

https://learn.example:8443/lesson?topic=web#intro에서 https는 scheme, learn.example은 host, 8443은 명시한 port, /lesson은 path, topic=web은 query, intro는 fragment다. port는 한 호스트의 통신 끝점을 구별하는 번호다. example 도메인은 설명용이며 이 주소에 실제 요청하지 않았다.

query를 어떤 검색 조건으로 해석할지는 서버의 응용 규칙이다. path가 반드시 디스크의 같은 이름 파일을 뜻하지는 않는다. 서버가 계산으로 응답을 만들 수 있기 때문이다. fragment는 자원 안의 위치를 가리키는 클라이언트 쪽 정보이고 HTTP 요청 대상으로 보내지 않는다.

요청과 응답은 역할이 다른 메시지다

GET은 대상 자원의 현재 표현을 얻으려는 메서드다. HTTP/1.1의 개념 예제는 GET /lesson?topic=web HTTP/1.1 요청 줄과 Host 헤더다. 안전한 메서드라는 규약은 사용자가 상태 변경을 요청하지 않는다는 의미이며 서버가 접근 로그를 남기는 것까지 금지한다는 뜻이 아니다.

응답에는 상태코드, 헤더, 선택적인 본문이 있다. 200은 해당 요청의 성공을, 404는 서버가 대상 자원의 현재 표현을 찾지 못했거나 공개하지 않음을 나타낸다. Content-Type은 본문을 해석할 종류를 알려준다. 200도 응용에서 원하는 답을 받았다는 보증은 아니므로 본문과 계약을 함께 확인해야 한다.

GET /lesson?topic=web HTTP/1.1
Host: learn.example:8443

HTTP/1.1 200 OK
Content-Type: text/html

<h1>Lesson</h1>

웹 한 화면에도 요청은 여러 개다

HTML 문서는 링크나 CSS·이미지·스크립트 주소를 포함할 수 있다. 브라우저는 문서를 해석하면서 필요한 추가 자원을 요청할 수 있고 이미 보유한 캐시를 사용할 수도 있다. 한 번 클릭했다는 사실에서 네트워크 요청이 정확히 한 개였다고 결론낼 수 없다.

여기서는 DNS·TLS·중간 캐시를 생략한 로컬 HTTP/1.1 사례를 사용한다. HTTP는 응용 계층의 메시지 의미를 정의하며 인터넷 전체와 같은 대상이 아니다. HTTP/2·3도 요청/응답 의미를 사용하지만 위의 문자 요청 줄을 그대로 전송하는 프로토콜이라고 설명하면 안 된다.

같은 기준 주소에서 네 링크를 해석하기
링크 표현해석된 경로·queryfragment서버 대상에 포함되는 부분

next.html?mode=read#quiz

quiz

/chapters/next.html?mode=read

/next.html?mode=read#quiz

/next.html?mode=read

quiz

/next.html?mode=read

../index.html#courses

/index.html

courses

/index.html

#top

/chapters/start.html

top

같은 문서의 클라이언트 위치 변경; 새 요청 수는 이 표에서 세지 않음

각 행은 기준 https://study.example/chapters/start.html에 대한 독립적인 해석이다. 순서대로 이동하면서 기준을 갱신한 표가 아니다. “서버 대상”은 일반 GET을 보내는 경우의 path와 query이며, fragment는 포함하지 않는다. 같은 문서 위치 이동에서 새 네트워크 요청이 있다고 자동 가정하지 않는다.

중간 과정을 따라가는 예제

가상 주소 http://127.0.0.1:8000/lesson?topic=web#intro에 대해 서버가 /lesson은 HTML 200, /style.css는 CSS 200, 나머지는 404로 정했다고 하자. 문서와 CSS, /missing의 세 요청을 추적하라.

  1. scheme=http, host=127.0.0.1, port=8000, path=/lesson, query=topic=web, fragment=intro로 분해한다.

  2. 첫 서버 요청 대상은 /lesson?topic=web이다. #intro를 붙이지 않는다.

  3. 문서 응답의 200·text/html·본문을 따로 읽는다. CSS를 요청하면 /style.css의 200·text/css를 읽는다.

  4. /missing 응답은 404다. 응답 자체가 도착했으므로 연결 실패와 구별한다.

요청 대상은 세 개이며 상태는 200,200,404다. 실제 검증에서는 임시 포트 50849를 사용했고 같은 상태 및 fragment 제외를 관찰했다. 8000은 종이 예제의 가정값이다.

조건을 바꾸어 비교하기

파일 이름이 같아도 경로가 다르다

서버가 /chapters/next.html은 200, /next.html은 404를 반환한다고 정했다. 기준 문서의 next.html과 /next.html 링크 결과를 비교하라.

  1. 첫 링크는 기준의 /chapters/ 디렉터리를 사용한다.

  2. 두 번째 링크는 앞의 / 때문에 /next.html로 간다.

  3. 가정한 서버 계약에 따라 응답은 각각 200과 404다.

첫 링크만 지정한 자원의 성공 응답을 받는다. 404도 HTTP 응답이다.

비교할 점

기본 예제의 자원 세 개 추적에서 나아가, 같은 이름의 상대 주소를 연결하는 규칙 자체를 진단한다.

서버 조건과 문서 내부 위치를 따로 설계한다

/atlas?view=map#legend와 /atlas?view=map#routes를 일반 GET 요청 대상으로 분해하라.

  1. 두 주소의 경로는 /atlas, query는 view=map으로 같다.

  2. fragment만 legend와 routes로 다르며 GET 대상에서는 제외한다.

  3. 서버는 두 대상 표현만으로 원하는 내부 위치를 구별할 수 없다.

두 대상은 /atlas?view=map으로 같다. 화면의 내부 이동 목적은 다르다.

비교할 점

주소 문자열의 차이가 언제나 서버 입력의 차이는 아니다. 그렇다고 브라우저나 스크립트가 fragment를 읽을 수 없다는 뜻은 아니다.

종이와 본문으로 직접 해보기

https://learn.example/a?q=2#part와 https://learn.example/a?q=3#part의 구성요소를 적고, 서버 요청 대상에서 달라지는 부분을 표시하라.

힌트 보기

물음표 뒤와 # 뒤를 분리하라. HTTPS 기본 포트는 443이다.

풀이 보기

두 주소의 scheme/host/기본 포트/path/fragment는 같고 query만 q=2와 q=3으로 다르다. 서버 요청 대상은 /a?q=2와 /a?q=3이다. fragment part는 두 요청 모두 제외한다.

오해와 반례

404는 인터넷이 끊겼다는 뜻이다.

반례는 정상 연결된 서버가 없는 경로에 404를 반환하는 경우다. 연결 실패에는 HTTP 상태가 아예 없을 수 있다. 진단은 연결 여부, HTTP 상태, 응용 본문 순서로 증거를 구분해야 한다.

자기점검

fragment intro는 위 HTTP 요청 대상에 포함되는가?

답과 이유 보기

아니다.

fragment는 클라이언트의 자원 내부 위치 정보이며 HTTP 요청 URI에 포함하지 않는다.

Content-Type: text/css는 상태코드인가?

답과 이유 보기

아니다. 응답 헤더다.

상태코드는 성공/오류의 의미를, 이 헤더는 본문의 형식을 설명한다.

동일한 path면 query가 달라도 응답이 같아야 하는가?

답과 이유 보기

아니다.

서버의 응용 규칙이 query를 사용해 다른 표현을 만들 수 있다.

스스로 풀어보기

먼저 답과 이유를 적고, 필요한 만큼 힌트를 한 단계씩 열어 보세요.

연습 1 · 값과 상태 예측

기준 https://study.example/chapters/start.html에서 ../lab.html?q=1#task를 해석하고 일반 GET 대상을 적어라.

힌트 1

..는 기준의 chapters 디렉터리 밖으로 한 단계 이동한다.

힌트 2

fragment를 분리하고 query는 남긴다.

풀이와 답 확인

  1. 경로는 /lab.html이다.

  2. query q=1과 fragment task를 구별한다.

해석한 주소는 https://study.example/lab.html?q=1#task, 대상은 /lab.html?q=1이다.

흔한 오답에서 다시 생각하기

/chapters/lab.html#task를 요청한다.

상위 디렉터리 이동과 fragment 제외를 모두 놓쳤다. 표의 ../index.html 행으로 돌아가라.

연습 2 · 오류 찾아 고치기

현재 기준은 /chapters/start.html인데 서버의 정답 자원은 /assets/theme.css다. href="assets/theme.css"가 /chapters/assets/theme.css로 해석됐다. 루트 기준 링크로 고쳐라.

힌트 1

주소의 첫 문자를 확인하라.

힌트 2

호스트 루트에서 시작하는 /를 사용한다.

풀이와 답 확인

  1. 기존 표현은 기준 디렉터리에 붙는다.

  2. href="/assets/theme.css"로 경로를 지정하면 이 가정의 대상과 일치한다.

이 서버의 루트 배치에서는 /assets/theme.css다. 프로젝트가 하위 경로에 배포된다면 배치 기준을 다시 정해야 한다.

흔한 오답에서 다시 생각하기

서버 파일을 아무 곳에 복사하면 상대 주소가 자동 수정된다.

링크 해석은 배치한 파일을 검색해서 추측하지 않는다. 주소 계약과 배포 경로를 먼저 맞춰라.

연습 3 · 직접 만들어 보기

서버가 과목에 따라 내용을 선택하고 브라우저가 해당 본문의 연습 위치로 이동해야 한다. /lesson 자원에 subject=python과 fragment practice를 사용한 주소를 설계하라.

힌트 1

서버 선택 조건과 내부 위치를 다른 칸에 둔다.

힌트 2

? 뒤에는 subject=python, # 뒤에는 practice를 둔다.

풀이와 답 확인

  1. 서버 선택은 응용이 query를 해석한다는 계약을 둔다.

  2. fragment practice에 대응하는 문서 앵커도 있어야 한다.

https://study.example/lesson?subject=python#practice다. 서버가 subject를 지원하고 문서에 practice 앵커가 있다는 조건이 필요하다.

흔한 오답에서 다시 생각하기

/lesson#subject=python&practice만 쓰면 서버가 과목을 고른다.

fragment는 일반 HTTP 대상에서 빠진다. 서버에 필요한 값을 query나 정한 요청 데이터로 전달해야 한다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

세 URL /atlas?view=map#a, /atlas?view=map#b, /atlas?view=list#a의 서버 대상 종류 수를 세고, 그 수가 실제 요청 횟수와 같은지도 설명하라.

힌트 1

대상 문자열의 서로 다른 값들을 집합으로 적는다.

힌트 2

이동·캐시·호출 횟수 정보는 주어지지 않았다.

풀이와 답 확인

  1. 앞의 두 대상은 /atlas?view=map이다.

  2. 세 번째는 /atlas?view=list여서 대상 종류는 두 개다.

  3. 새 요청이 몇 번 일어나는지는 별도의 실행 기록이 필요하다.

대상 종류는 2개다. 실제 요청 횟수는 이 주소 목록만으로 정할 수 없다.

흔한 오답에서 다시 생각하기

주소 세 개이므로 네트워크 요청도 반드시 세 번이다.

가능한 대상의 수와 실제 사건 수를 구별하라. 같은 문서 이동이나 캐시, 반복 호출의 조건을 추가로 관찰해야 한다.

내 말로 설명하기

상대 주소의 답을 적기 전에 어떤 조건을 적어야 하는가?

설명 기준 확인

기준 URL과 기준을 바꾸는 요소가 있는지 적고, 각 문제의 이동이 독립적인지 연속인지 구별할 수 있다.

서버 대상이 같으면 화면도 같다는 결론을 내릴 수 있는가?

설명 기준 확인

fragment와 브라우저 상태가 다를 수 있음을 설명하고 서버가 받는 입력과 클라이언트 표시를 나눌 수 있다.

한 단계 더

심화: GET의 안전성과 멱등성을 구분하라. 안전성은 요청 의미가 읽기라는 조건이고, 멱등성은 동일 요청을 반복했을 때 의도된 서버 효과가 한 번과 같다는 조건이다. 응답 시각이나 로그 개수가 같다는 주장은 아니다. 실제 API의 계약과 캐시 정책은 별도 확인해야 한다.

출처와 확인 범위
  • RFC 9110 HTTP Semantics

    본문의 요청/응답 의미, URI fragment 제외, GET, 상태코드, origin 관련 절을 확인. HTTP/1.1 표기 예제를 HTTP/2·3의 바이트 형식으로 일반화하지 않음.

  • WHATWG URL Standard

    URL 구성요소 및 http/https 기본 포트와 origin 규칙 본문 확인. 본문 예제는 단순 ASCII http(s) URL에 한정.

소단원 1.2

브라우저·서버·origin

같은 컴퓨터의 다른 포트에서 실행되는 두 페이지는 같은 origin일까?

준비 개념과 학습 목표

준비 개념

  • 프로그램은 규칙을 실행하는 절차다. 클라이언트는 요청을 시작하는 역할, 서버는 요청을 받아 응답하는 역할이다. 한 컴퓨터가 두 역할을 모두 실행할 수 있다.

학습 목표

  • 브라우저와 서버의 실행 위치를 구분한다

  • 단순 http(s) URL의 origin을 비교한다

  • cross-origin 전송과 응답 읽기 권한을 구별한다

같은 학교의 웹페이지와 자료 서버는 같은 컴퓨터에 있어도 한 출입구일까?

컴퓨터 한 대라는 물리적 사실과 브라우저가 구별하는 출처 경계는 다르다. 학교 페이지를 study.example, 이미지 서버를 media.study.example로 정하면 같은 장비에서 응답해도 호스트 이름이 다른 두 출처다. 이번 계산은 일반 http(s) URL과 기본 origin만 다루며 특별한 sandbox나 domain 변경을 사용하지 않는다.

또한 어떤 데이터를 화면에 보여주는 것, 다른 출처에 요청을 보내는 것, 그 응답을 자바스크립트로 읽는 것은 별도의 질문이다. 경계를 판단할 때 “다른 origin이라서 모든 작업이 금지된다”라는 한 문장으로 묶지 말고, 지금하려는 동작과 서버 정책을 함께 적는다.

먼저 확인할 개념
  • 주소와 서버 대상

    origin 비교에서 경로·query·fragment와 scheme·host·port를 혼동하지 않는다.

  • 분해한 작업의 계약

    요청 전송, 응답 읽기, 사용자 권한 확인을 다른 책임으로 분해한다.

실행하는 쪽에 따라 보이는 정보가 다르다

브라우저는 받은 HTML로 문서 구조를 만들고 CSS로 표현을 결정하며 JavaScript를 실행할 수 있다. 서버는 저장소 조회나 계산을 통해 응답을 만들 수 있다. HTML에 써서 브라우저에 보낸 비밀은 사용자가 볼 수 있으므로 서버 비밀로 취급할 수 없다.

브라우저가 서버 데이터베이스에 직접 접근해야 웹이라는 뜻은 아니다. 보통 서버 API가 권한과 입력을 검사하고 저장소를 다룬다. JavaScript를 사용한다는 사실도 실행 위치를 정하지 않는다. 브라우저와 서버 양쪽에 JavaScript 실행 환경이 있을 수 있다.

origin은 실행 주체를 구별하는 경계다

기본 domain 변경이 없는 단순 http(s) 예제의 origin 비교는 정규화된 scheme, host, port를 사용한다. https://learn.example/a와 https://learn.example:443/b는 같은 origin이다. path·query·fragment는 이 비교에 들어가지 않는다. https와 http, 다른 host, 다른 유효 port 중 하나라도 다르면 다른 origin이다.

HTML 표준에는 opaque origin도 있다. 일부 sandbox 문서나 특별 URL의 origin을 단순 세 문자열 공식으로 처리하면 안 된다. 이 단원은 일반 http(s) 주소의 기본 origin만 계산하며 document.domain 변경을 쓰지 않는다. 같은 서버 IP로 연결되더라도 다른 host 이름은 이 비교에서 같아지지 않는다.

보안 정책은 읽기와 보내기를 구별한다

동일 origin 정책은 다른 origin의 문서와 데이터에 대한 접근을 제한하는 브라우저의 중요한 경계다. 그러나 cross-origin 이미지 표시나 링크 이동처럼 허용되는 동작도 있다. 다른 origin이면 어떤 네트워크 바이트도 전송할 수 없다는 규칙은 아니다.

브라우저의 fetch로 cross-origin 응답을 스크립트가 읽으려면 보통 서버의 적절한 CORS 응답이 필요하다. 요청 형태에 따라 사전 요청이 생기거나 응답 읽기가 차단되어도 일부 실제 요청은 서버에 도착할 수 있다. CORS를 사용자 로그인·권한 검사와 동일시하면 안 된다. 서버는 브라우저 이외의 클라이언트 요청도 받으므로 자체 인증·권한 계약이 필요하다.

scheme 변경

443이라는 숫자만 맞추어도 http와 https가 같은 origin이 되지 않는다. 경로 /answers가 다른 것은 origin 분리도 사용자 권한 검사도 아니다. 실제 자원 접근 권한은 서버의 별도 계약으로 확인한다.

중간 과정을 따라가는 예제

기준 https://learn.example/a와 B=https://learn.example:443/b?q=1, C=http://learn.example/a, D=https://learn.example:8443/a를 비교하라.

  1. 기준의 유효 scheme/host/port는 https,learn.example,443이다.

  2. B의 명시 포트 443은 HTTPS 기본 포트와 같으므로 동일 origin이다.

  3. C는 http와 기본 포트 80이라 기준과 다르다.

  4. D는 port=8443이므로 기준과 다르다.

B만 같은 origin이다. 이 결과는 주소 규칙의 종이 추적이며 실제 브라우저 CORS 실험이 아니다.

조건을 바꾸어 비교하기

해답을 접는 것과 접근을 막는 것은 다르다

공개 HTML에 해답을 넣고 details를 접었다. 학생에게 아직 해답을 보이지 않게 한 화면이 해답 접근 권한도 제한하는가?

  1. details는 사용자가 열 수 있는 표시 장치다.

  2. 서버가 해답 내용을 HTML로 이미 보냈다는 조건을 확인한다.

  3. 시험 정답처럼 전송하면 안 되는 정보는 서버의 별도 권한 처리 대상이다.

접힌 해답은 선택 읽기 기능이다. 공개 HTML에 보낸 해답의 비밀성은 보장하지 않는다.

비교할 점

기본 예제의 서버와 브라우저 실행 위치 구분을 실제 교육 페이지 설계 판단에 연결한다.

전송 기록과 읽기 실패를 함께 해석한다

가상 서버 로그에는 다른 origin에서 보낸 GET /public.json 도착 기록이 있다. 브라우저 스크립트에서는 CORS 읽기 실패가 기록됐다. 두 기록은 모순인가?

  1. 서버 로그는 이 GET 도착을 지지한다.

  2. 브라우저 실패는 스크립트가 응답 데이터를 읽지 못한 관찰이다.

  3. 전송 여부와 읽기 허용 여부를 다른 칸에 적으면 두 기록을 함께 설명할 수 있다.

모순이 아니다. 이 가상 사례에서는 요청은 도착했고 스크립트의 읽기는 실패했다.

비교할 점

다른 종류의 모든 요청도 반드시 전송된다는 일반화는 하지 않는다. 사전 요청이 필요한 경우 등은 별도 규칙이다.

종이와 본문으로 직접 해보기

http://localhost:8000/a, http://localhost:8000/b, http://127.0.0.1:8000/a, http://localhost:8001/a의 origin을 첫 주소와 비교하라.

힌트 보기

호스트명이 같다는 조건을 IP 연결 결과와 혼동하지 말라.

풀이 보기

두 번째만 첫 주소와 같은 origin이다. 세 번째는 host가 localhost와 127.0.0.1로 다르고 네 번째는 port가 다르다. 실제로 같은 컴퓨터로 연결되어도 비교 결과는 바뀌지 않는다.

오해와 반례

서버가 CORS를 허용하면 사용자 권한 검사도 끝난다.

공개 CORS API에도 관리자 전용 작업은 별도 권한 검사가 필요하다. CORS는 브라우저 스크립트의 cross-origin 접근 허용 조건이고 사용자에게 작업 권한을 부여하는 인증 체계가 아니다.

한 단계 더

심화: 서버에 부작용이 있는 요청을 보내는 공격과 응답 데이터를 읽는 공격을 나누어 생각하라. same-origin/CORS만으로 모든 요청 부작용을 방지할 수 없으므로 CSRF 방어·쿠키 정책·서버 권한 확인이 별도 과제다. 여기서는 구체 보안 설정의 적합성 검증을 수행하지 않았다.

출처와 확인 범위
  • WHATWG HTML: Origins

    tuple origin의 scheme/host/port 및 opaque origin 본문 확인. domain 필드는 기본 null인 예제만 사용.

  • WHATWG URL Standard

    URL 구성요소 및 http/https 기본 포트와 origin 규칙 본문 확인. 본문 예제는 단순 ASCII http(s) URL에 한정.

  • RFC 9110 HTTP Semantics

    본문의 요청/응답 의미, URI fragment 제외, GET, 상태코드, origin 관련 절을 확인. HTTP/1.1 표기 예제를 HTTP/2·3의 바이트 형식으로 일반화하지 않음.

  • WHATWG Fetch: CORS protocol

    독립 검토자가 CORS3.3의 opt-in cross-origin 응답 공유와 preflight 조건을 직접 확인. 브라우저 실행은 수행하지 않음.

소단원 1.3

개발자도구와 요청관찰

화면이 하얗게 보이면 어떤 기록부터 읽어 원인을 좁힐 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 관찰은 실제로 얻은 기록이고 가설은 그 기록을 설명하려는 추측이다. 상태코드는 응답의 의미를 나타내며 본문과 실행 오류는 별도 정보다. 요청 시간은 조건에 따라 변하는 측정값이다.

학습 목표

  • Network 기록에서 주소·메서드·상태·본문을 연결한다

  • 관찰된 사실과 원인 추정을 분리한다

  • 캐시와 기록 시점을 포함해 재현 조건을 적는다

요청 세 개의 시간이 40, 12, 20ms라면 페이지는 72ms 뒤 준비될까?

시간표에서 한 사람이 차례로 하는 일과 여러 사람이 동시에 하는 일을 다르게 계산하듯, 요청 시간도 시작·끝을 함께 봐야 한다. 여기서는 가상 관찰표로 추론한다. 숫자는 실제 사이트 성능 측정값이 아니며 렌더링 완료나 모든 사용자의 체감 시간을 뜻하지 않는다.

Network는 다운로드 관찰의 도구다. 상태·본문·요청 유발 원인을 연결하고, 기록을 시작한 시점과 필터를 적어야 증거 범위를 이해할 수 있다. 이번 가상 표는 문서가 완료된 뒤 CSS와 JavaScript 요청을 동시에 시작한다는 단순 일정으로 고정한다.

먼저 확인할 개념
  • 응답의 상태·본문

    200과 404, 본문 종류를 실행 오류와 구별해 읽는다.

  • 지연과 처리율

    측정 구간과 포함 범위를 명시하고 겹치는 작업의 시간을 무조건 더하지 않는다.

기록을 시작한 시점이 증거 범위를 정한다

Chrome DevTools Network 패널은 요청 목록을 기록한다. 선택 활동으로 패널을 먼저 열고 기록을 켠 뒤 새로고침하면 문서와 하위 자원을 확인할 수 있다. 이미 끝난 요청이 반드시 뒤늦게 모두 복원되는 것은 아니므로 언제 기록을 시작했는지 적는다. 이 활동은 선택 사항이며 본문의 표만으로도 연습할 수 있다.

각 행에서 URL·메서드·상태를 보고 요청을 선택해 Headers와 Response를 읽는다. Initiator는 무엇이 요청을 유발했는지, Timing은 단계별 시간 정보를 제공한다. 화면의 오류 문구와 서버 응답 본문이 같다고 가정하지 않고 서로 대조한다.

실제로 관찰한 세 요청

작성자는 Python 클라이언트로 로컬 서버에 세 GET을 명시적으로 보냈다. 기록은 /lesson?topic=web 200 text/html, /style.css 200 text/css, /missing 404 text/plain이다. 첫 클라이언트 URL에는 #intro가 있었으나 서버 로그에는 없었다. 이것은 실제 HTTP 클라이언트·서버 관찰이다.

HTML 본문에 CSS 링크가 들어 있었지만 Python 클라이언트가 HTML을 렌더링한 것은 아니다. CSS 요청도 코드에서 따로 보냈다. 따라서 이 로그를 브라우저의 자동 하위 자원 로딩이나 Chrome 화면 캡처라고 부르면 증거 범위를 넘는다. 실제 로그는 verification/batch04/http-report.json에 보존했다.

진단은 가장 작은 주장부터 한다

404 행은 해당 서버 응답을 받았다는 사실을 지지한다. 왜 경로가 잘못되었는지, 인증 정책이 숨겼는지까지는 그 행만으로 결정되지 않는다. 200 CSS에도 문법 문제나 적용 우선순위 문제가 있을 수 있다. Network로 다운로드 사실을 확인한 다음 문서·스타일·콘솔 관찰을 추가한다.

캐시를 사용한 새로고침과 캐시를 비활성화한 측정은 조건이 다르다. 브라우저·버전·시각·캐시 설정·네트워크 조건을 함께 적어야 시간 비교가 의미 있다. 한 번의 로컬 측정으로 모든 사용자의 성능을 단정할 수 없으며 이 단원은 성능 수치를 주장하지 않는다.

가상 Network 표: document /lesson 200 HTML, stylesheet /style.css 404 text/plain, script /main.js 200 JavaScript. 문서는 보이지만 색이 기대와 다르다. 확인 순서를 써라.

  2. 스타일시트 요청 404를 기록하고 실제 URL과 링크의 상대경로 해석을 대조한다.

  3. 서버에 /style.css가 제공되는지 확인한다. 이것은 404의 원인 후보를 검증하는 다음 단계다.

  4. 스타일 요청이 200으로 바뀐 뒤에도 색이 다르면 스타일 규칙과 적용 우선순위를 확인한다.

필터 뒤에 보이는 행 수

전체 로그에 document 1행, stylesheet 1행, script 1행, image 2행이 있다. CSS 필터에서 1행만 보였다. 전체 요청 수를 1로 기록해도 되는가?

  1. 가상 전체 로그의 행 수는 1+1+1+2=5다.

  2. CSS 필터는 전체 기록 중 일부만 보여 준다.

  3. 기록 시점과 필터를 적고 전체 목록으로 확인한다.

이 가상 로그에는 5행, CSS 필터에는 1행이다. 하나의 화면 표시가 전체 기록의 크기는 아니다.

비교할 점

기본 예제의 개별 요청 진단을 관찰 범위와 표본 선택의 오류로 확대한다.

다운로드와 실행을 분리한다

Network에는 /ui.js 200이 있고 Console에는 실행 중 TypeError가 있다는 가상 기록이다. 서버가 자바스크립트를 실행해서 성공한 것인가?

  1. 200은 해당 요청의 HTTP 성공 관찰이다.

  2. Console의 실행 중 오류는 브라우저 실행에 대한 별도 관찰이다.

  3. 받은 본문과 오류 위치, 재현 입력을 연결할 후속 계획을 적는다.

다운로드 성공과 실행 실패는 함께 일어날 수 있다. 200만으로 실행 성공을 주장하지 않는다.

비교할 점

기본 CSS 404와 달리 다운로드 이후 단계에서 실패하는 경우다. 실제 오류 원인은 두 행만으로 확정하지 않는다.

연습 2 · 오류 찾아 고치기

페이지 로딩이 끝난 뒤 Network를 열어 빈 목록을 보고 “요청이 없었다”고 보고했다. 보고 문장을 고쳐라.

힌트 1

힌트 2

풀이와 답 확인

  1. 현재 목록은 도구를 연 뒤 관찰한 범위가 비었다는 사실만 적는다.

  2. 기록을 켜고 조건을 적은 뒤 새로고침하여 새 사건을 관찰할 계획을 세운다.

이 기록만으로 이전 요청이 없었다고 결론낼 수 없다. 재관찰은 아직 하지 않았다고 표시한다.

빈 목록이면 서버가 동작하지 않은 것이다.

관찰 부재와 사건 부재는 다른 주장이다. 시작 시점이라는 조건부터 보완하라.

힌트 2

available의 의미는 응용 계약에서 확인한다.

풀이와 답 확인

  1. HTTP 200과 JSON 본문의 available=false를 관찰로 적는다.

  2. 사용 가능한 항목이 없는 것인지 오류인지 아직 계약을 모른다고 적는다.

  3. 응용 명세와 요청 조건을 확인할 계획을 적는다.

상태와 본문을 둘 다 기록하고 업무 성공·원인을 확정하지 않는 메모면 된다.

200이므로 available을 확인하지 않아도 성공이다.

응용 결과를 확인해야 사용자의 목적 달성 여부를 판단할 수 있다. 본문을 별도 증거로 읽어라.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

가상 실험 A에서는 캐시를 켜고 요청 평균 8ms, B에서는 캐시를 끄고 평균 30ms였다. “서버 코드 변경만으로 22ms 개선됐다”라는 결론을 평가하고 비교 계획을 설계하라.

힌트 1

A와 B에서 동시에 달라진 조건을 적는다.

힌트 2

코드 비교에서는 캐시 등 다른 조건을 맞추고 반복값을 보관한다.

풀이와 답 확인

  1. 캐시 조건이 달라 코드 효과와 섞여 있다.

  2. 각 코드 버전에 같은 캐시 정책·입력·환경·관찰 구간을 적용하는 계획을 만든다.

  3. 반복값과 퍼짐을 함께 보고 계획과 실제 결과를 구별한다.

8과 30의 차이는 22ms지만 그 원인을 코드에만 귀속할 수 없다. 새 비교는 미수행이다.

흔한 오답에서 다시 생각하기

평균 차이가 계산되면 원인도 증명된다.

산술 차이와 원인 추론은 다른 단계다. 통제하지 않은 조건을 찾아라.

다른 문제에 적용하기

자체 가상 교재 기준 URL은 https://study.example/chapters/start.html이다. next.html?level=beginner#practice 링크를 클릭했다. 서버는 /chapters/next.html?level=beginner에 200 HTML을, 이 HTML의 href="theme.css"가 해석한 /chapters/theme.css에 404를 응답했다. 문서는 보이지만 색이 기본값이다. URL 분해, origin 비교, 확정 가능한 두 사실, 아직 모르는 원인, 다음 확인 순서를 한 장의 진단 메모로 작성하라.

힌트 1

주소 해석표에서 기준 디렉터리와 fragment를 구별한다.

힌트 2

상태 404는 원인 후보를 찾을 단서이며 파일 누락을 이미 증명한 것은 아니다.

풀이와 답 확인

  1. 이동 주소는 https://study.example/chapters/next.html?level=beginner#practice이고 문서 GET 대상에는 fragment가 없다.

  2. 문서와 CSS의 일반 origin은 https/study.example/443으로 같다.

  3. 문서 200과 CSS 404 응답을 사실로 적는다. CSS를 받을 수 없었다는 단서가 있으나 올바른 링크, 실제 서버 배치 또는 공개 정책 중 어느 것이 원인인지는 추가 확인이 필요하다.

  4. 원문 href와 해석된 URL, 서버의 자원 제공 계약을 먼저 대조한다. 수정 뒤 상태·본문과 실제 스타일 적용을 다시 관찰할 계획을 적되 아직 수행하지 않았다고 표시한다.

주소와 출처, HTTP 사실, 원인 가설, 재관찰 계획을 구별한 메모가 답이다. origin이 같다는 사실은 자원 존재나 스타일 적용 성공을 보장하지 않는다.

  • 문서·스타일 요청의 origin이 같다고 판단했는가?

  • HTTP 재관찰 뒤 실제 스타일 적용까지 확인할 계획과 미수행 상태를 적었는가?

보강 자료의 출처와 확인 범위
  • RFC 9110: HTTP Semantics

    7.1의 target URI/fragment 제외, Host와 요청 대상 및 응답 의미를 실제 읽었다. 새 링크와 가상 응답은 자체 작성이며 HTTP/1.1 표기를 모든 버전의 바이트로 일반화하지 않는다.

  • WHATWG URL Standard

    4장의 URL 구성요소·상대 주소와 기준의 예, 4.2 기본 포트 표를 실제 읽었다. 자체 ASCII http(s) 예제만 쓰며 다른 scheme/opaque origin을 이 계산으로 일반화하지 않는다.

  • WHATWG Fetch: CORS protocol

    3.3의 응답 공유/opt-in 및 preflight 절을 실제 읽었다. 가상 GET 도착과 응답 읽기를 분리하며 실제 CORS 성공이나 보안 설정 적합성을 주장하지 않는다.

  • Chrome DevTools: Inspect network activity

    기록 시작/새로고침, Status·Initiator·Time, Headers·Response·Timing 및 캐시 비교 안내를 실제 읽었다. 새 가상 일정·필터·진단 문제는 자체 작성이며 DevTools 실측으로 표시하지 않는다.

모든 상대 주소는 기준 디렉터리를 표시하여 직접 해석했다. 표의 기본 포트와 origin 네 행, 세 대상 종류 2, 로그 행 5, 가상 시간 구간 60/20ms와 평균 차이 22ms를 손으로 계산했다. 전이의 두 경로와 origin을 같은 규칙으로 대조했다.

not_executed: 이 보강의 네트워크·CORS·DevTools·캐시·브라우저 실행 문제는 자체 가상 기록과 종이 추론이다. v1의 이전 HTTP 실험 기록과 혼동하지 않는다.
