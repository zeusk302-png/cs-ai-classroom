소단원 12.1

CI와 품질 게이트

검사 한 개가 초록색이면 바로 모든 사용자에게 공개해도 될까?

준비 개념과 학습 목표

준비 개념

  • 버전관리의 커밋
  • 단위시험과 통합시험
  • 의존성 그래프

학습 목표

  • CI의 반복 통합과 검사 조건을 설명한다.
  • job의 의존성과 가상 소요시간을 추적한다.
  • 통과한 범위와 검증하지 않은 범위를 구분한다.

작은 변경을 자주 통합하고 확인하기

CI는 팀의 변경을 자주 통합하고 자동 빌드와 검사를 통해 문제를 빠르게 찾는 활동이다. 버튼 하나나 특정 제품 이름만으로 성립하는 것은 아니다. 오래 따로 작업한 뒤 큰 충돌을 한번에 합치는 습관은 검사 도구가 있어도 통합 위험을 키울 수 있다.

자동 작업에는 시작 조건, 고정 소스 버전, 실행 환경, 검사, 산출물, 결과 기록이 필요하다. GitHub Actions에서는 workflow 안에 job과 step을 구성하고 needs로 job 의존성을 나타낼 수 있다. 아래는 도구를 실행하지 않는 종이 그래프다.

품질 게이트는 구체적인 수용 조건

게이트는 다음 단계로 넘어가기 전 충족할 조건이다. 빌드 성공, 필수 시험 통과, 형식 검사, 알려진 보안 문제 처리와 같은 조건을 서비스 맥락에 맞게 정한다. 가상의 규칙에서 필수 A, B가 모두 통과해야 하는데 A만 통과했다면 전체 통과가 아니다.

초록색 표시는 실행한 검사에서 실패가 없었다는 증거다. 사용자 이해, 접근성, 실기기, 운영 부하를 검사하지 않았다면 그 범위까지 입증하지 못한다. flaky 시험의 재시도 성공도 원인을 숨기지 않도록 첫 실패와 재시도를 함께 기록한다.

병렬 실행에도 선행 조건이 있다

가상 파이프라인은 build 뒤 unit/lint가 독립 병렬이고 둘 다 성공하면 package를 만든다. unit이 실패했는데 package가 의존성 없이 실행되면 게이트 설계를 어긴다. 작업을 나란히 배치한 그림과 실제로 병렬 자원이 확보됐다는 것은 다르다.

실제 시간에는 큐 대기·checkout·캐시·전송이 추가된다. 아래 숫자는 그런 비용 0, 충분한 runner, 각 job의 고정 시간을 가정한다. 임계 경로를 종이에 계산하는 것과 실제 CI 성능 측정 보고를 구별한다.

중간 과정을 따라가는 예제

build 2분 뒤 unit 5분과 lint 1분이 병렬이다. 두 성공 뒤 package 2분, 그 뒤 deploy 1분이다. 큐·전송 비용이 0이고 자원이 충분할 때 완료 시간과 unit 실패 시 가능한 단계를 구하라.

  1. build는 0–2분, unit은 2–7분, lint는 2–3분이다.
  2. 두 검사 완료는 max(7,3)=7분이므로 package는 7–9분, deploy는 9–10분이다.
  3. unit 실패면 두 성공 조건을 못 채우므로 package와 deploy를 진행하지 않는다.

가상 완료 시간은 10분이다. 모두 직렬이면 2+5+1+2+1=11분이다. 실제 성능이 1분 개선되었다고 실측한 것은 아니다.

종이와 본문으로 직접 해보기

unit을 3분으로 줄인 같은 가정의 시간과 lint가 실패했는데 unit이 통과한 경우 배포 여부를 판단하라.

힌트 보기

두 검사의 최댓값과 AND 게이트를 각각 확인한다.

풀이 보기

2+max(3,1)+2+1=8분이다. lint도 필수이므로 실패 시 배포할 수 없다. unit 단독 통과로 게이트를 대체하지 않는다.

오해와 반례

모든 자동 검사가 통과하면 모든 환경·모든 사용자에게도 오류가 없다.

검사하지 않은 기기나 실사용 입력에서 문제가 날 수 있다. 시험 목록·버전·환경·결과와 미수행 범위를 남겨 증거를 한정한다.

소단원 12.2

자동 배포·환경 설정

똑같은 파일을 올렸는데 테스트 서버와 공개 서버에서 다른 결과가 나오는 이유는 무엇일까?

준비 개념과 학습 목표

준비 개념

  • CI 산출물
  • 설정값과 비밀값
  • 개발·시험·운영 환경

학습 목표

  • 빌드한 산출물의 동일성과 환경 설정을 나눠 기록한다.
  • 환경 보호 규칙과 최소 권한을 설명한다.
  • 설정 오류와 코드 오류를 구별한다.

배포할 것을 한 번 정하고 추적하기

소스 커밋만 같아도 도구나 의존성 버전이 달라지면 산출물이 달라질 수 있다. 빌드 환경과 입력을 고정하고 산출물 식별자를 남긴다. 시험한 파일을 운영에 승격하면 운영 단계에서 몰래 다시 빌드한 파일과의 차이를 줄일 수 있다.

산출물의 내용 해시와 릴리스 기록은 어떤 파일을 사용했는지 찾는 근거다. 해시만 있다고 누가 만들었는지 인증하거나 그 파일이 안전하다는 것은 아니다. 배포 후 실제 서비스가 가리키는 식별자도 확인한다.

코드와 설정과 비밀의 각 책임

같은 코드는 시험 API와 운영 API에 다른 주소로 연결할 수 있다. 주소·기능 플래그·제한값의 환경 차이를 검토하고 설정 버전도 기록한다. 잘못된 주소가 들어가면 프로그램 파일이 맞아도 잘못된 서비스에 접속한다.

인증 토큰은 공개 소스·공개 빌드 산출물·로그에 적지 않는다. 특히 브라우저에 전달하는 정적 파일에 들어간 값은 방문자가 읽을 수 있으므로 비밀 저장소에서 가져왔다는 이유로 숨겨지지 않는다. 서버 측 사용과 공개 클라이언트 설정을 구별한다.

자동화의 권한과 사전 확인

배포 job은 배포 대상·허용 버전·필요 권한을 가져야 한다. 환경 보호 규칙이나 승인 단계가 있으면 통과 후에만 해당 환경 secret에 접근하도록 구성할 수 있다. 어떤 서비스에 어떤 게이트를 둘지는 위험과 팀 규칙에 따른 선택이다.

아래 종이 기록은 승인·설정 검사·대상 확인을 각각 표시한다. 세 조건 중 하나가 실패하면 중단한다. 자동화 파일을 작성했다는 사실과 실제 자격 증명·환경·네트워크에서 배포를 수행했다는 사실을 같게 보고하지 않는다.

중간 과정을 따라가는 예제

가상 산출물 A17을 시험 완료했다. 운영 배포 기록은 artifact=A17, config=C4, target=prod인데 C4의 API 주소가 test다. 승인도 완료했다. 코드 동일성·설정·대상 게이트를 판단하라.

  1. 시험 산출물과 배포 산출물은 A17로 같다. 실제 내용 해시가 아닌 교육 식별자다.
  2. target은 prod지만 config C4는 test 주소여서 운영 주소 검사에 실패한다.
  3. 승인 완료와 산출물 일치는 설정 실패를 상쇄하지 않으므로 배포를 보류하고 설정을 수정·검증한다.

산출물과 대상은 의도와 일치하지만 설정 게이트에 실패한다. 설정 수정 후 같은 산출물과 새 설정 버전의 조합을 다시 검사한다.

종이와 본문으로 직접 해보기

힌트 보기

검사한 바이트와 배포한 바이트의 연결, 방문자가 받는 파일을 각각 확인한다.

풀이 보기

A18을 시험했다는 증거가 없으므로 A17 검증을 자동 승계하지 않는다. HTML 토큰은 방문자에게 전달되므로 비밀이 아니다. 비밀을 필요로 하는 작업은 적절한 서버 측 경계를 설계해야 한다.

오해와 반례

환경 secret에서 꺼낸 값이면 HTML에 넣어도 계속 비밀이다.

HTML 응답의 문자열은 사용자가 볼 수 있다. 저장할 때 비밀 관리와 배포 후 공개 범위는 별개다. 키 노출이 있었다면 삭제만으로 끝내지 않고 회수·교체 등 실제 영향을 확인해야 한다.

소단원 12.3

릴리스·롤백·관측

새 버전을 되돌렸다는 로그만 있으면 사용자의 문제가 해결됐다고 볼 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 배포 산출물 식별
  • 오류율과 비율
  • 데이터와 설정

학습 목표

  • 릴리스 기록과 사용자 관측을 연결한다.
  • 가상의 canary 비율과 중단 조건을 계산한다.
  • 롤백의 데이터 호환성과 재확인을 설명한다.

릴리스는 변경 내용과 증거를 묶는다

릴리스에는 버전, 변경 내용, 산출물·설정, 검사, 배포 대상, 알려진 제약을 남긴다. 일부 사용자에게 새 버전을 적용하는 canary는 영향을 제한하며 관측할 수 있지만, 다양한 사용자군 전체를 한 번에 대표한다는 보장은 없다.

어떤 관측값을 언제 얼마나 모아 확대·중단할지 미리 정한다. 오류율·지연·핵심 사용 흐름과 관측 누락을 함께 본다. 아래 100요청 표는 설명을 위한 가상 표이며 실제 서비스 실험이 아니다.

비율의 분자와 분모를 확인하기

오류 10건이라는 숫자만으로 서비스 상태를 판단할 수 없다. 요청 100개 중 10건과 10000개 중 10건은 다른 비율이다. canary와 기존 그룹의 같은 기간·정의·분모를 확인하고 전체 평균이 작은 그룹의 악화를 가리는지도 본다.

자체 규칙은 canary 오류율이 2%를 초과하면 중단한다. 이 임계값을 모든 서비스의 보편적 기준으로 권고하지 않는다. 작은 표본의 우연·사용자 구성 차이·기존 오류 원인까지 분석하지 않은 단순 판정이다.

되돌릴 수 있는 범위를 미리 검토하기

롤백은 이전 코드나 설정을 다시 활성화하는 조치다. 새 코드가 저장한 데이터 형식을 옛 코드가 읽을 수 없다면 코드 교체만으로 복구되지 않는다. 스키마 변경·외부 알림·사용자 작업과 같이 되돌리기 어려운 효과를 구분하고 호환성이나 복구 경로를 준비한다.

실행 명령 성공만으로 복구 완료라고 하지 않는다. 실제 버전·설정과 사용자 핵심 흐름, 오류 관측을 다시 확인한다. 복구 시간을 계산할 때 탐지·결정·교체·검증 중 어디부터 어디까지인지 명시한다.

중간 과정을 따라가는 예제

가상 canary 100요청 중 오류 5건, 기존 900요청 중 오류 9건이다. canary 오류율 > 2%이면 중단하는 계약이다. 전체 오류율과 그룹별 비율을 계산하라. 탐지 14:00, 결정 14:03, 교체 완료 14:07, 사용자 검증 14:10이다.

  1. canary는 5/100=5%, 기존은 9/900=1%다. 전체는 14/1000=1.4%다.
  2. 전체 1.4%가 작아도 canary의 5% > 2%이므로 중단한다.
  3. 탐지부터 검증까지 10분, 결정부터 교체까지 4분이다. 시간 구간이 서로 다르다.

중단 대상은 canary다. 이 표만으로 원인이나 유의성을 확정하지 않는다. 가상 복구 구간은 탐지부터 검증까지 10분이며 실측이 아니다.

풀이 보기

2/100=2%는 초과가 아니므로 이 한 규칙만으로 중단하지 않는다. 다른 게이트나 분석이 있으면 별도다. 옛 코드는 name 없는 새 자료를 읽지 못할 수 있어 호환 변환·복구 등을 준비해야 한다.

오해와 반례

옛 코드만 다시 올리면 새 코드의 모든 영향이 자동으로 사라진다.

이미 보낸 알림은 회수되지 않을 수 있고 저장 형식도 남는다. 코드·설정·데이터·외부 효과별 복구 가능성과 확인 절차를 분리해야 한다.
