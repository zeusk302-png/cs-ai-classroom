소단원 12.1

CI와 품질 게이트

검사 한 개가 초록색이면 바로 모든 사용자에게 공개해도 될까?

준비 개념과 학습 목표

준비 개념

  • 버전관리의 커밋

  • 단위시험과 통합시험

  • 의존성 그래프

학습 목표

  • CI의 반복 통합과 검사 조건을 설명한다.

  • job의 의존성과 가상 소요시간을 추적한다.

  • 통과한 범위와 검증하지 않은 범위를 구분한다.

완료 보고서를 항상 만들면서 실패한 산출물의 배포는 어떻게 막는가?

학교 실습 서버의 새 종이 파이프라인은 build 뒤 unit과 schema 검사를 실행한다. 배포의 수용 조건은 둘 다 성공이다. 그러나 실패를 설명하는 report는 실패하더라도 필요하다. 실패 후에도 실행할 작업과 실패 후에는 실행하면 안 되는 작업을 같은 조건으로 묶으면 한쪽 목적을 잃는다.

GitHub의 needs는 기본적으로 앞 job의 성공을 요구하며 실패·skip은 후속 의존 job도 skip시킨다. always() 조건으로 완료 보고서를 실행할 수 있지만 그것은 성공 게이트를 대신하지 않는다. 여기서는 report를 항상 실행하되 deploy는 필수 두 검사 결과가 success인지 별도로 확인하는 설계다. 실제 workflow를 생성하거나 실행한 것은 아니다.

새 고정 시간은 build 2분, unit 4분, schema 3분, report 1분, deploy 2분이다. 충분한 runner에서는 두 검사를 병렬로 하고 report와 deploy도 조건을 만족하면 병렬로 한다. 한 runner 비교에서는 build→unit→schema→report→deploy 순서를 지정하며 큐 외 추가 비용은 0이다.

작은 변경을 자주 통합하고 확인하기

CI는 팀의 변경을 자주 통합하고 자동 빌드와 검사를 통해 문제를 빠르게 찾는 활동이다. 버튼 하나나 특정 제품 이름만으로 성립하는 것은 아니다. 오래 따로 작업한 뒤 큰 충돌을 한번에 합치는 습관은 검사 도구가 있어도 통합 위험을 키울 수 있다.

자동 작업에는 시작 조건, 고정 소스 버전, 실행 환경, 검사, 산출물, 결과 기록이 필요하다. GitHub Actions에서는 workflow 안에 job과 step을 구성하고 needs로 job 의존성을 나타낼 수 있다. 아래는 도구를 실행하지 않는 종이 그래프다.

품질 게이트는 구체적인 수용 조건

게이트는 다음 단계로 넘어가기 전 충족할 조건이다. 빌드 성공, 필수 시험 통과, 형식 검사, 알려진 보안 문제 처리와 같은 조건을 서비스 맥락에 맞게 정한다. 가상의 규칙에서 필수 A, B가 모두 통과해야 하는데 A만 통과했다면 전체 통과가 아니다.

초록색 표시는 실행한 검사에서 실패가 없었다는 증거다. 사용자 이해, 접근성, 실기기, 운영 부하를 검사하지 않았다면 그 범위까지 입증하지 못한다. flaky 시험의 재시도 성공도 원인을 숨기지 않도록 첫 실패와 재시도를 함께 기록한다.

병렬 실행에도 선행 조건이 있다

가상 파이프라인은 build 뒤 unit/lint가 독립 병렬이고 둘 다 성공하면 package를 만든다. unit이 실패했는데 package가 의존성 없이 실행되면 게이트 설계를 어긴다. 작업을 나란히 배치한 그림과 실제로 병렬 자원이 확보됐다는 것은 다르다.

실제 시간에는 큐 대기·checkout·캐시·전송이 추가된다. 아래 숫자는 그런 비용 0, 충분한 runner, 각 job의 고정 시간을 가정한다. 임계 경로를 종이에 계산하는 것과 실제 CI 성능 측정 보고를 구별한다.

각 행은 독립적인 초기 상태에서 시작한다. 첫 두 행에서 build는 0–2분, unit은 2–6분, schema는 2–5분이다. report 완료와 deploy 완료는 서로 다른 사건이고 실패 행에 배포 완료 시각을 만들어 넣지 않는다.

중간 과정을 따라가는 예제

build 2분 뒤 unit 5분과 lint 1분이 병렬이다. 두 성공 뒤 package 2분, 그 뒤 deploy 1분이다. 큐·전송 비용이 0이고 자원이 충분할 때 완료 시간과 unit 실패 시 가능한 단계를 구하라.

  1. build는 0–2분, unit은 2–7분, lint는 2–3분이다.

  2. 두 검사 완료는 max(7,3)=7분이므로 package는 7–9분, deploy는 9–10분이다.

  3. unit 실패면 두 성공 조건을 못 채우므로 package와 deploy를 진행하지 않는다.

가상 완료 시간은 10분이다. 모두 직렬이면 2+5+1+2+1=11분이다. 실제 성능이 1분 개선되었다고 실측한 것은 아니다.

조건을 바꾸어 비교하기

실패를 기록하는 job과 공개하는 job의 분리

unit이 6분에 실패하고 schema가 5분에 성공했다. report에만 always()를 둔다. 누가 실행되는가?

  1. 두 선행 job이 끝나는 시각은 6분이다. report는 성공 여부와 무관하게 6분에 시작한다.

  2. deploy의 성공 AND는 거짓이므로 시작하지 않는다. 보고서는 7분에 끝난다.

보고서 생성 성공은 실패한 unit을 성공으로 바꾸지 않는다.

비교할 점

base의 성공 경로 시간만 계산하는 것에서 실패 경로의 증거 보존으로 확장한다.

자원 수를 생략하면 임계 경로가 실측처럼 보인다

모두 성공하며 runner를 충분한 경우와 한 개의 지정 순서로 비교하라.

  1. 병렬 경우 build 2 + max(4,3) + max(1,2) = 8분이다.

  2. 한 runner에서는 2+4+3+1+2 = 12분이다.

같은 DAG와 고정 작업 시간이라도 자원·순서 전제가 전체 시간에 영향을 준다.

비교할 점

실제 큐·전송·설치 시간은 추가로 관찰해야 한다.

종이와 본문으로 직접 해보기

unit을 3분으로 줄인 같은 가정의 시간과 lint가 실패했는데 unit이 통과한 경우 배포 여부를 판단하라.

힌트 보기

두 검사의 최댓값과 AND 게이트를 각각 확인한다.

풀이 보기

2+max(3,1)+2+1=8분이다. lint도 필수이므로 실패 시 배포할 수 없다. unit 단독 통과로 게이트를 대체하지 않는다.

오해와 반례

모든 자동 검사가 통과하면 모든 환경·모든 사용자에게도 오류가 없다.

검사하지 않은 기기나 실사용 입력에서 문제가 날 수 있다. 시험 목록·버전·환경·결과와 미수행 범위를 남겨 증거를 한정한다.

스스로 풀어보기

먼저 답과 이유를 적고, 필요한 만큼 힌트를 한 단계씩 열어 보세요.

연습 1 · 값과 상태 예측

충분한 runner에서 schema가 5분에 실패하고 unit이 6분에 성공하면 report와 deploy는?

힌트 1

필수 검사 결과는 서로 다른 두 값이다.

힌트 2

늦은 완료는 6분이며 AND는 거짓이다.

풀이와 답 확인

  1. report는 6–7분에 실행한다.

  2. deploy는 필수 schema 실패 때문에 실행하지 않는다.

보고 완료는 7분, 배포는 미실행이다.

흔한 오답에서 다시 생각하기

unit이 더 오래 걸리고 성공했으므로 실패를 덮는다.

완료 시각의 최댓값은 대기 조건이며 성공 판정의 우선순위가 아니다.

연습 2 · 오류 찾아 고치기

실패한 unit의 step에 continue-on-error를 넣어 job을 성공 표시하고 deploy에 success 조건만 두었다. 필수 시험 실패 차단이라는 자체 정책을 어떻게 보존할까?

힌트 1

허용된 실패와 필수 실패를 구분한다.

힌트 2

원래 검사 결과와 최종 job 상태가 같다고 가정하지 않는다.

풀이와 답 확인

  1. 필수 검사에는 실패를 성공 처리하는 허용을 제거하거나 원래 결과를 보존해 명시적으로 검사한다.

  2. report의 실패 시 실행과 deploy의 필수 성공 게이트는 분리한다.

정책이 필수로 지정한 실패가 공개 경로를 통과하지 못하게 한다.

흔한 오답에서 다시 생각하기

최종 초록색이면 원래 실패 로그를 삭제한다.

도구의 실패 허용은 시험의 논리적 수용 조건을 자동 만족시키지 않는다.

연습 3 · 직접 만들어 보기

unit=success, schema=skipped, report=success인 기록을 배포 여부 표에 추가하고 이유를 써라.

힌트 1

success와 skipped는 같은 값이 아니다.

힌트 2

report는 필수 두 검사 중 어느 것도 대체하지 않는다.

풀이와 답 확인

  1. 필수 schema가 수행되어 성공했다는 증거가 없다.

  2. 배포 조건 success AND success는 거짓이다.

배포를 진행하지 않고 schema skip의 원인을 확인한다.

흔한 오답에서 다시 생각하기

failure가 없으니 모두 성공이다.

미수행·skip과 성공을 구별해야 검사 범위가 사라지지 않는다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

충분한 runner에서 unit 시간을 u≥0분으로 바꾸고 나머지 시간은 고정한다. 성공 경로 완료 식과 unit만 줄여도 개선이 멈추는 구간을 구하라.

힌트 1

검사 단계는 max(u,3)이다.

힌트 2

뒤 report와 deploy는 병렬이며 더 긴 것은 2분이다.

풀이와 답 확인

  1. 완료 시간 T(u)=2+max(u,3)+2다.

  2. u≤3이면 T=7분으로 schema 경로가 하한을 만든다. u>3이면 T=u+4다.

u를 4에서 3으로 줄이면 8→7분, 3에서 2로 줄여도 7분이다.

흔한 오답에서 다시 생각하기

unit을 1분 줄이면 언제나 전체도 1분 줄어든다.

다른 필수 경로가 더 길면 그 경로가 끝 시각을 결정한다.

내 말로 설명하기

always()는 배포 승인인가?

설명 기준 확인

아니다. 성공과 무관하게 실행할 job을 정하는 조건이다.

시간과 게이트의 서로 다른 계산은?

설명 기준 확인

시간은 의존·자원·최댓값, 수용은 필수 결과의 논리 조건이다.

한 단계 더

시험이 처음 실패하고 재시도에서 통과한 기록을 추가하자. 최종 status와 첫 실패 로그를 둘 다 보존하고 원인이 재현되었는지 기록한다. 무조건 재시도하여 초록색만 남기는 정책의 문제를 토론하자.

가변 이름이 같은 산출물을 가리킨다는 보장을 줄까?

새 종이 레지스트리에는 가변 이름 candidate와 불변 식별자 H1/H2가 있다. H1/H2는 교육용 이름이며 실제 해시가 아니다. 10:00에는 candidate→H1이고 H1을 시험했다. 10:05에 candidate→H2로 바뀌고 10:06에 candidate를 조회해 배포하면 H2를 받는다. 문자열 candidate를 보존한 것과 시험한 바이트를 보존한 것은 다르다.

배포 기록의 핵심은 시험 증거가 가리키는 산출물·설정·대상 조합이다. 이 과제의 검증 키는 (artifact, config, target)이다. (H1,C1,stage)의 시험을 (H1,C2,prod)에 자동 승계하지 않는다. 코드가 같다는 증거는 설정 의미와 대상 권한까지 보증하지 않는다.

GitHub 환경 보호는 해당 환경 job과 secret 접근 전에 규칙을 적용한다. 환경 이름을 적었다는 이유로 보호 규칙이 이미 설치된 것은 아니다. 공식 문서는 workflow가 없는 환경 이름을 참조해 새 환경을 만들면 일부 경우 규칙·secret이 없을 수 있음을 설명한다. 여기서는 계정 설정을 변경하지 않고 기록의 전제만 대조한다.

배포할 것을 한 번 정하고 추적하기

소스 커밋만 같아도 도구나 의존성 버전이 달라지면 산출물이 달라질 수 있다. 빌드 환경과 입력을 고정하고 산출물 식별자를 남긴다. 시험한 파일을 운영에 승격하면 운영 단계에서 몰래 다시 빌드한 파일과의 차이를 줄일 수 있다.

산출물의 내용 해시와 릴리스 기록은 어떤 파일을 사용했는지 찾는 근거다. 해시만 있다고 누가 만들었는지 인증하거나 그 파일이 안전하다는 것은 아니다. 배포 후 실제 서비스가 가리키는 식별자도 확인한다.

코드와 설정과 비밀의 각 책임

같은 코드는 시험 API와 운영 API에 다른 주소로 연결할 수 있다. 주소·기능 플래그·제한값의 환경 차이를 검토하고 설정 버전도 기록한다. 잘못된 주소가 들어가면 프로그램 파일이 맞아도 잘못된 서비스에 접속한다.

인증 토큰은 공개 소스·공개 빌드 산출물·로그에 적지 않는다. 특히 브라우저에 전달하는 정적 파일에 들어간 값은 방문자가 읽을 수 있으므로 비밀 저장소에서 가져왔다는 이유로 숨겨지지 않는다. 서버 측 사용과 공개 클라이언트 설정을 구별한다.

자동화의 권한과 사전 확인

배포 job은 배포 대상·허용 버전·필요 권한을 가져야 한다. 환경 보호 규칙이나 승인 단계가 있으면 통과 후에만 해당 환경 secret에 접근하도록 구성할 수 있다. 어떤 서비스에 어떤 게이트를 둘지는 위험과 팀 규칙에 따른 선택이다.

아래 종이 기록은 승인·설정 검사·대상 확인을 각각 표시한다. 세 조건 중 하나가 실패하면 중단한다. 자동화 파일을 작성했다는 사실과 실제 자격 증명·환경·네트워크에서 배포를 수행했다는 사실을 같게 보고하지 않는다.

중간 과정을 따라가는 예제

가상 산출물 A17을 시험 완료했다. 운영 배포 기록은 artifact=A17, config=C4, target=prod인데 C4의 API 주소가 test다. 승인도 완료했다. 코드 동일성·설정·대상 게이트를 판단하라.

  1. 시험 산출물과 배포 산출물은 A17로 같다. 실제 내용 해시가 아닌 교육 식별자다.

  2. target은 prod지만 config C4는 test 주소여서 운영 주소 검사에 실패한다.

  3. 승인 완료와 산출물 일치는 설정 실패를 상쇄하지 않으므로 배포를 보류하고 설정을 수정·검증한다.

산출물과 대상은 의도와 일치하지만 설정 게이트에 실패한다. 설정 수정 후 같은 산출물과 새 설정 버전의 조합을 다시 검사한다.

새 합성 관측에는 easy와 hard 요청 종류가 있다. 기존 버전은 easy 990건 중 오류 10건, hard 10건 중 오류 5건이다. canary는 easy 10건 중 오류 0건, hard 90건 중 오류 40건이다. canary는 종류별 비율이 낮지만 전체 비율은 훨씬 높다. 요청 종류의 비중이 서로 다르기 때문이다.

두 버전의 동일 목표 비중을 easy/hard 각각 절반으로 정한 비교도 별도로 계산한다. 이것은 관찰된 전체율을 수정해 지우는 일이 아니라 목적이 다른 가중 비교다. 고정 표는 무작위 배정·인과효과·통계적 유의성이나 실제 서비스의 대표성을 입증하지 않는다.

관측 누락도 분모를 바꾼다. 별도 합성 canary 100요청 중 상태를 아는 80요청에 오류 4건, 나머지 20건의 상태는 모른다. 확인된 비율 4/80과 전체 가능한 오류 범위 4/100–24/100을 구분해야 한다. 현재 코드 되돌리기는 이미 저장한 새 스키마나 외부 알림을 자동 복원하지 않는다.

릴리스는 변경 내용과 증거를 묶는다

릴리스에는 버전, 변경 내용, 산출물·설정, 검사, 배포 대상, 알려진 제약을 남긴다. 일부 사용자에게 새 버전을 적용하는 canary는 영향을 제한하며 관측할 수 있지만, 다양한 사용자군 전체를 한 번에 대표한다는 보장은 없다.

어떤 관측값을 언제 얼마나 모아 확대·중단할지 미리 정한다. 오류율·지연·핵심 사용 흐름과 관측 누락을 함께 본다. 아래 100요청 표는 설명을 위한 가상 표이며 실제 서비스 실험이 아니다.

비율의 분자와 분모를 확인하기

오류 10건이라는 숫자만으로 서비스 상태를 판단할 수 없다. 요청 100개 중 10건과 10000개 중 10건은 다른 비율이다. canary와 기존 그룹의 같은 기간·정의·분모를 확인하고 전체 평균이 작은 그룹의 악화를 가리는지도 본다.

자체 규칙은 canary 오류율이 2%를 초과하면 중단한다. 이 임계값을 모든 서비스의 보편적 기준으로 권고하지 않는다. 작은 표본의 우연·사용자 구성 차이·기존 오류 원인까지 분석하지 않은 단순 판정이다.

되돌릴 수 있는 범위를 미리 검토하기

롤백은 이전 코드나 설정을 다시 활성화하는 조치다. 새 코드가 저장한 데이터 형식을 옛 코드가 읽을 수 없다면 코드 교체만으로 복구되지 않는다. 스키마 변경·외부 알림·사용자 작업과 같이 되돌리기 어려운 효과를 구분하고 호환성이나 복구 경로를 준비한다.

실행 명령 성공만으로 복구 완료라고 하지 않는다. 실제 버전·설정과 사용자 핵심 흐름, 오류 관측을 다시 확인한다. 복구 시간을 계산할 때 탐지·결정·교체·검증 중 어디부터 어디까지인지 명시한다.

새 릴리스의 build 2분 뒤 unit 4분과 schema 3분을 충분한 runner로 실행한다. unit은 실패, schema는 성공이다. report 1분은 항상 실행하고 deploy 2분은 필수 두 성공을 요구한다. 실행 여부와 끝 시각을 구하라. 별도 산출물 기록에서는 10:00에 candidate→H1을 (H1,C1,stage)로 시험했고 10:05에 candidate→H2다. 10:06 요청은 candidate/C2/prod다. 증거 일치 여부와 보완할 기록을 작성하라. 관측은 이 단원의 easy/hard 표와 별도 누락 표를 사용한다. 목표 절반 가중율·확인된율·전체 범위 및 >10% 계약 판정의 확정 가능성을 구하라. 마지막으로 14:00 탐지부터 14:12 사용자 검증까지 코드와 데이터 복구 상태를 기록하라.

힌트 1

완료 보고의 조건과 공개의 성공 게이트를 분리하고 가변 이름을 사건 시점의 불변 식별자로 해석한다.

힌트 2

종류별·전체·목표 가중·확인된 표의 분모를 따로 쓰고 겹친 시간 구간을 더하지 않는다.

풀이와 답 확인

  1. unit은 2–6분, schema는 2–5분이다. report는 6–7분이며 deploy는 필수 실패로 미실행이다.

  2. 10:06 candidate는 H2다. 기존 시험 키 (H1,C1,stage)와 요청 키 (H2,C2,prod)는 세 요소가 다르므로 증거를 자동 승계하지 않는다. 불변 산출물·설정·대상·승인·실제 활성 상태를 연결해 기록한다.

  3. 종류별 canary 오류율은 모두 낮지만 전체 기존 1.5%와 canary 40%는 비중 차이로 다르다. 절반 목표에서는 기존 101/396 ≈25.51%, canary 2/9 ≈22.22%다.

  4. 별도 누락 표의 확인된율은 5%, 전체 범위는 4–24%다. 미확인 오류가 6건/7건인 두 경우가 >10% 판정을 갈라 아직 확정하지 못한다.

  5. 14:05 코드 교체, 14:09 데이터 호환, 14:12 사용자 검증은 별도 상태다. 탐지부터 사용자 검증까지는 12분이며 코드 교체까지만 센 5분과 합산하지 않는다.

실행·수용·바이트 동일성·구성 일치·관측 분모·복구 끝점을 하나의 초록색 표시로 합치지 않는다. 모든 시간과 관측은 자체 합성 사례이며 실제 CI/배포/서비스/사용자 실험은 미수행이다.

해결한 뒤 점검할 것

  • 실패 후 report 실행과 deploy 차단을 각각 설명한다.

  • 사건 시점의 산출물과 정확한 검증 조합을 복원한다.

  • 전체율과 목표 가중율이 다른 이유 및 누락의 가능한 범위를 계산한다.

  • 롤백의 코드·데이터·사용자 상태와 실제 미수행을 구분한다.

전체 원본과 새 조건을 손검산했다. 파이프라인 성공 경로 충분 runner 8분/단일 지정 순서 12분, 실패 후 보고 7분 및 배포 미실행이다. T(u)=4+max(u,3)의 하한 7분을 확인했다. 가변 candidate의 10:06 값 H2와 세 요소 검증 키의 불일치를 추적했다. 종류별 1/99·1/2 대 0·4/9, 전체 15/1000·40/100, 목표 절반 101/396·2/9를 계산했다. 별도 확인된 4/80=5%와 전체 4–24%, 미확인 오류 6/7건의 경계 10/11%를 대조했다. 시각 구간 5/12/3/4/3분 및 전이 전체를 손유도했다.
