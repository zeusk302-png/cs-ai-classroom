소단원 6.1

API 계약과 오류 규약

버튼을 눌렀는데 실패했다. 사용자는 입력을 바꿔야 할까, 기다려야 할까?

준비 개념과 학습 목표

준비 개념

  • API는 다른 프로그램이 사용하는 인터페이스다.

  • 요청에는 입력, 응답에는 결과나 오류가 담긴다.

  • 정수 범위와 조건문을 종이에 검사할 수 있다.

학습 목표

  • 허용 입력·결과·오류를 함께 계약으로 작성한다.

  • HTTP 상태와 프로그램용 오류 코드를 구분한다.

  • 재시도와 멱등성의 적용 조건을 설명한다.

입력부터 결과까지 약속하기

학교의 가상 사물함 API를 설계해 보자. PUT /lockers/7/settings의 입력은 정수 온도 target이며 허용 범위는 10~30이다. 성공하면 현재 설정을 돌려주고 target 밖의 필드는 이 예제에서 거부한다. 주소·타입·범위·권한·성공 결과까지 명시해야 호출자가 구현자의 생각을 추측하지 않는다. 온도 단위는 섭씨라는 사실도 계약에 넣는다.

HTTP를 사용한다고 모든 API가 같은 동작을 갖는 것은 아니다. 이 자체 예제는 이미 존재하는 사물함 설정을 변경하는 동기 작업이다. 신규 자원 생성이나 비동기 작업이라면 성공 상태와 결과 위치를 따로 정해야 한다. 202 Accepted는 접수 사실이며 작업 완료를 보장하는 신호로 쓰지 않는다.

오류는 고치는 행동과 연결하기

이 예제는 target=9에 400과 코드 TARGET_OUT_OF_RANGE를, 인증·권한 확인 후 존재하지 않는 사물함에는 404를, 점검 중이라 변경할 수 없는 상태에는 409와 LOCKER_UNAVAILABLE을 돌려주기로 정한다. 이는 이 서비스의 설계 결정이며 모든 서비스가 같은 코드를 쓰도록 강제하는 보편 규칙은 아니다. 오류 본문에는 안전한 설명과 추적용 requestId를 넣고 비밀번호·내부 경로·전체 예외 스택을 내보내지 않는다.

사용자에게 보여줄 한국어 문구와 클라이언트가 분기할 안정된 코드를 구분한다. 번역 때문에 문장이 달라져도 TARGET_OUT_OF_RANGE를 보고 입력을 수정할 수 있다. 반면 서버 내부 장애는 같은 요청을 반복한다고 반드시 해결되지 않는다. 재시도 허용 여부·횟수·대기 규칙을 계약이나 운영 정책으로 정해야 한다.

같은 요청을 두 번 보내는 경우

PUT으로 target=20을 두 번 설정하면 최종 설정 상태가 한 번 수행한 경우와 같도록 설계한다. 이 성질이 멱등성이다. 응답의 시각이나 로그까지 동일해야 한다는 뜻은 아니다. 이 예제는 설정 저장과 별도로 매 호출마다 요금을 청구하는 일을 하지 않는다.

POST /reservations처럼 새 예약을 만드는 요청을 응답 유실 뒤 그대로 보내면 예약 두 건이 생길 수 있다. 멱등성 키를 쓰려면 키의 유효 기간·동일 입력 검사·중복 처리의 원자성을 함께 정의해야 한다. 키 이름을 추가한 것만으로 중복 방지 구현이 완성된 것은 아니다. 여기서는 종이상의 계약을 설계하며 실제 서버는 실행하지 않는다.

중간 과정을 따라가는 예제

사물함 7은 존재하고 사용자는 권한이 있다. 초기 target=18, 점검 중 아님이다. target=9, 20, 20 순서로 PUT 요청하면 상태와 저장 값은?

  1. 9는 10≤target≤30을 만족하지 않아 400/TARGET_OUT_OF_RANGE이며 저장 값 18을 유지한다.

  2. 20은 범위 안이고 점검 중도 아니므로 200과 저장 값 20이다.

  3. 다시 20을 보내도 200이고 저장 값은 20이다. 두 번째 성공이 새 사물함을 생성하지 않는다.

상태는 400, 200, 200; 최종 설정은 20이다. 성공 요청 두 번과 한 번의 최종 설정이 같다.

종이와 본문으로 직접 해보기

종이에 target=10, 30, 31과 점검 중 target=20의 결과를 적어라. 모든 대상과 권한은 유효하다. 입력 검사를 먼저 수행한다.

힌트 보기

범위의 양 끝을 포함하고, 범위가 맞으면 상태 충돌을 검사한다.

풀이 보기

10과 30은 각 200으로 저장한다. 31은 400으로 저장하지 않는다. 점검 중 20은 409/LOCKER_UNAVAILABLE이며 기존 설정을 유지한다. 이 순서와 유지 조건도 계약에 적는다.

오해와 반례

성공이 아닌 응답은 모두 같은 문구로 표시하면 충분하다.

입력 범위 오류 400은 값을 고쳐야 하고 상태 충돌 409는 상태 변화를 기다려야 할 수 있다. 같은 문구만 있으면 호출자가 적절한 행동을 고르기 어렵다. 서버 상세 정보를 무제한 공개하는 것도 해결책이 아니다.

자기점검

target=10은 유효한가?

답과 이유 보기

유효하다.

10~30을 양 끝 포함 범위로 계약했다.

202를 받으면 예약 완료로 표시해도 되는가?

답과 이유 보기

접수만으로 완료를 단정할 수 없다.

비동기 작업의 별도 완료 상태를 확인해야 한다.

PUT 멱등성은 모든 응답 본문이 같다는 뜻인가?

답과 이유 보기

아니다.

반복 요청의 의도한 자원 상태 효과가 동일하다는 뜻이다.

소단원 6.2

데이터 모델과 경계

학습자의 이름을 보여 주려고 비밀번호 저장 정보까지 보내야 할까?

준비 개념과 학습 목표

준비 개념

  • 개체는 구별 가능한 대상이고 관계는 개체 사이의 연결이다.

  • 식별자는 이름이 바뀌어도 같은 대상을 가리키도록 설계한다.

  • 불변조건은 허용된 상태가 계속 만족해야 하는 조건이다.

학습 목표

  • 개체와 관계를 요청·저장·응답 모델에 연결한다.

  • 중복과 참조 규칙을 문장으로 정의한다.

  • 내부 표현과 외부 표현의 경계를 설명한다.

학습 세계를 모델로 옮기기

자체 예제로 User(id, displayName), Course(id, title), Enrollment(userId, courseId)를 정한다. 한 사용자는 여러 과목을 듣고 한 과목에는 여러 사용자가 있으므로 Enrollment는 다대다 관계를 표현한다. 같은 사용자·같은 과목의 수강 관계는 한 번만 허용하며 두 ID는 실제 존재하는 대상을 참조해야 한다.

표를 세 개로 나누었다는 사실만으로 규칙이 지켜지지는 않는다. 생성·삭제·변경이 모두 중복 금지와 참조 규칙을 보존해야 한다. 사용자를 삭제할 때 수강 관계도 지울지, 삭제를 막을지 먼저 정한다. 실습에서는 삭제를 막는 정책을 사용한다. 동시 요청의 안전성은 별도의 트랜잭션·제약 구현으로 확인해야 한다.

입력과 저장과 응답을 구분하기

수강 신청 입력은 courseId 하나여도 서버는 로그인한 사용자의 ID를 신뢰된 인증 문맥에서 얻어야 한다. 입력으로 받은 임의 userId를 그대로 믿으면 다른 사람의 수강 내역을 바꾸는 문제가 생긴다. 이는 인증 구현을 완료했다는 주장이 아니라 경계를 어디에 두어야 하는지 보여 주는 설계 예이다.

외부 CourseSummary는 id·title·enrolledCount만 제공하고 내부 관리 메모는 포함하지 않도록 명시한다. 저장 테이블을 응답으로 그대로 노출하면 내부 열 이름을 바꾸는 일과 외부 API 변경이 붙어 버린다. 별도의 변환이 조금 늘어도 저장 구조를 바꿀 여지를 확보하고 노출할 필드를 검토할 수 있다.

경계를 넘는 참조와 규칙

메모리 안에서도 내부 수강 목록을 직접 돌려주면 호출자가 검사 없이 항목을 추가할 수 있다. private 필드라도 가변 목록의 참조를 외부에 내보내면 중복 금지 규칙이 깨질 수 있다. 복사본이나 제한된 읽기 인터페이스를 선택할 때는 원소 자체가 가변인지도 확인한다.

불변조건을 초기 생성에서 만족시키고 모든 공개 변경 연산에서 유지하며 내부 표현 노출을 막아야 한다. 데이터베이스 제약과 서비스 검사가 서로 대신한다는 식으로 단정하지 않는다. 서비스는 이해 가능한 오류를, 저장 계층은 최종 무결성 보존을 담당하도록 설계할 수 있다.

중간 과정을 따라가는 예제

User={U1,U2,U3}, Course={C1,C2}, Enrollment={(U1,C1),(U1,C2),(U2,C1),(U3,C2)}이다. C1 수강자 수를 구하고 (U2,C1), (U4,C2)의 추가를 판단하라.

  1. C1을 가진 관계는 (U1,C1), (U2,C1)이므로 enrolledCount=2다.

  2. (U2,C1)은 기존 관계와 같은 ID 쌍이므로 중복 금지에 걸린다.

  3. U4가 User에 없으므로 (U4,C2)는 참조 규칙을 어긴다. 두 추가를 거절하면 관계 수는 4다.

C1은 2명이며 두 요청을 모두 거절한다. 총 관계는 4개로 유지된다.

종이와 본문으로 직접 해보기

(U2,C2)를 추가한 뒤 U2 삭제 요청을 받았다. 수강 관계가 있는 사용자는 삭제를 막는 정책이다. 각 단계의 관계 수와 삭제 결과를 써라.

힌트 보기

두 ID가 존재하고 그 쌍이 처음인지 검사한다. 삭제 판단은 추가 후 상태를 사용한다.

풀이 보기

(U2,C2)는 유효하므로 관계가 5개가 된다. U2에는 C1·C2 수강 관계가 남아 있어 삭제를 거절하고 사용자 3명과 관계 5개를 유지한다.

오해와 반례

필드를 private으로 만들면 내부 가변 목록을 그대로 반환해도 안전하다.

외부 코드가 반환받은 목록에 (U4,C2)를 넣으면 private 필드를 직접 대입하지 않아도 내부 상태가 바뀐다. 참조 노출을 막거나 복사·변경 검사를 제공해야 한다.

소단원 6.3

호환성과 버전

새 기능을 넣었는데 어제의 학습 앱이 갑자기 멈춘다면 무엇을 바꾼 걸까?

준비 개념과 학습 목표

준비 개념

  • 클라이언트는 API 계약에 따라 입력을 보내고 응답을 읽는다.

  • 선택 필드는 생략될 수 있고 필수 필드는 반드시 있어야 한다.

  • 버전은 어떤 계약을 사용할지 구별하는 표지다.

학습 목표

  • 소스·전송·의미 호환성을 구분한다.

  • 필드 추가·삭제·이름 변경의 영향을 구체적 클라이언트로 판단한다.

  • 버전 전환의 공존·안내·검증 계획을 작성한다.

무엇이 계속 작동해야 하는가

자체 학습 API v1은 {id:7,title:"별"}를 돌려준다. C1은 id·title을 읽고 모르는 필드는 무시한다. C2는 응답 필드가 정확히 두 개여야 한다고 검사한다. 두 클라이언트의 해석 규칙이 다르므로 description을 추가했을 때 결과도 다르다. 추가라는 단어만으로 안전을 판정하지 말고 허용된 계약과 실제 소비자를 확인한다.

호환성에는 프로그램이 다시 컴파일되는지, 주고받은 데이터를 읽는지, 성공 의미가 유지되는지가 포함된다. 응답 형식이 같아도 이전에 전체 목록을 주던 API가 설명 없이 앞의 20개만 주면 사용자는 나머지가 없다고 오해할 수 있다. 자료형과 이름만 검사하는 회귀 확인으로 이 의미 변화를 놓칠 수 있다.

추가·이름 변경·타입 변경

요청에 새 필수 locale을 요구하면 예전 앱의 생략 요청은 실패한다. 선택 locale의 생략 시 이전 언어를 유지하면 영향을 줄일 수 있다. 응답의 title을 name으로 바꾸는 것은 기존 title을 없애고 다른 필드를 더하는 일이라 title을 읽던 C1이 실패한다. 과도기에는 둘을 제공하되 의미와 충돌 규칙을 정할 수 있다.

id를 정수에서 문자열로 바꾸면 겉으로 "7"이 같은 값처럼 보여도 정수만 받는 클라이언트가 실패한다. 새 열거값을 추가할 때도 알 수 없는 값의 처리 규칙을 확인한다. 이 예제에서 C2의 엄격한 필드 검사는 description 추가에 실패하므로 실제 이용 중이라면 별도 수정·전환이나 v2 공존이 필요하다.

버전 표지와 이행 절차

v2라는 경로를 만들면 두 계약을 구별할 수 있지만 v1이 실제로 계속 동작하는지는 별도 문제다. 지원 기간과 변경 안내, C1·C2 같은 대표 구버전 요청·응답 확인, 실패 때 되돌리는 절차를 계획한다. 같은 DB를 쓰더라도 v1 표현으로 변환할 수 있는지 확인해야 한다.

주·부·패치 번호의 호환성 정책은 프로젝트에서 정해 공개한다. 숫자를 올렸다는 사실이 자동으로 검증 증거가 되지는 않는다. 구버전 소비자에게 더 엄격한 입력이나 다른 기본 정렬을 적용하는지도 검사한다. 여기서는 계획과 종이 클라이언트 검사만 수행하며 실제 배포 호환 테스트는 하지 않았다.

중간 과정을 따라가는 예제

C1은 알 수 없는 필드를 무시하고 title을 문자열로 요구한다. C2는 id·title 두 필드만 요구한다. A=description 추가, B=title 삭제 후 name 추가, C=title을 정수로 변경이다. 호환 여부는?

  1. A: C1은 id·title을 정상 읽고 description을 무시하므로 성공한다. C2는 세 필드라는 이유로 거절한다.

  2. B: 두 클라이언트 모두 필수 title이 없어 거절한다.

  3. C: 두 클라이언트 모두 title의 문자열 조건을 위반해 거절한다.

A는 C1만 통과하고 B·C는 둘 다 실패한다. 호환성은 명시한 소비자 조건에 따라 판단한다.

종이와 본문으로 직접 해보기

새 요청 선택 필드 limit를 추가한다. 생략하면 이전처럼 전체 목록을 주는 정책 D와 생략해도 20개만 주는 E를 비교하라. 기존 앱은 반환 목록을 전부라고 가정한다.

힌트 보기

기존 앱이 필드를 보내지 않을 때의 관측 결과를 비교한다.

풀이 보기

D는 생략 요청의 이전 동작을 유지한다. E는 21개 이상 있을 때 앱이 20개를 전체라고 오해하므로 의미 호환성이 깨진다. 원래 페이지 계약이 없었다는 조건 때문에 결과가 달라진다.

오해와 반례

선택 필드 추가는 항상 호환이다.

C2는 알 수 없는 응답 필드를 거절한다. 요청 선택 필드도 생략 기본값이 바뀌면 기존 의미가 달라진다. 소비자가 따르는 계약과 기본 동작을 확인해야 한다.
