소단원 9.1

동치분할·경계값

가능한 입력이 수없이 많으면 무엇부터 시험할까?

준비 개념과 학습 목표

준비 개념

  • 조건식

  • 요구사항과 기대 결과

학습 목표

  • 입력 공간을 명세 기준으로 분할한다.

  • 경계 바로 전·경계·바로 후의 기대 결과를 만든다.

입력 하나씩의 경계를 모두 지나도 두 입력의 관계가 빠질 수 있을까?

새 배송 견적 계약은 이미 정수인 개별 무게 w와 상자 수 n을 받는다. 1 ≤ w ≤ 10, 1 ≤ n ≤ 4이고 총 무게 w × n ≤ 10이어야 한다. 어느 조건이든 위반하면 오류다. 유효하면 총 무게가 5 이하일 때 요금 4, 5보다 클 때 요금 7을 반환한다. 단위는 자체 무게 단위와 자체 요금 단위이며 문자열·실수 변환과 유한 정수 overflow는 이 수학 정수 모형 밖이다.

w = 5, n = 2는 각 범위 안이며 총 무게 10으로 유효하다. w = 6, n = 2도 각 범위 안이지만 총 무게 12라 오류다. 각 입력을 따로 분할한 뒤 대표 하나씩을 조합한다고 관계 조건이 자동으로 검증되지는 않는다. w × n = 10이라는 경계와 총 무게 5의 요금 경계를 별도로 읽어야 한다.

예상 결과는 명세의 조건 순서에서 독립적으로 만든다. 오류를 먼저 판정하지 않고 무게만 보고 요금 7을 반환하는 변형은 대표 정상 입력에서 통과할 수 있다. 대표값은 효율적인 후보이고 전체 영역의 동등성 증명이 아니다. 새 견적 구현이나 테스트 도구를 실행하지 않고 아래 표와 반례를 종이로 설계한다.

먼저 확인할 개념
  • 명세의 분할과 경계 이웃

    개별 범위와 입력 사이 관계의 경계를 따로 고른다.

  • 지나간 분기와 옳은 기대값

    정상 대표 통과를 모든 조합의 증명으로 확대하지 않는다.

비슷한 행동을 기대하는 영역으로 나누기

시험은 입력마다 올바른 결과가 무엇인지 판단할 기준이 필요하다. 정수 점수 0~100을 받고 60 이상이면 합격이라는 명세를 보자. 범위 밖과 범위 안, 범위 안의 불합격과 합격 영역을 나누면 대표 사례를 고를 이유가 생긴다.

동치분할은 영역 안의 모든 입력을 증명상 같다고 선언하는 일이 아니다. 명세에서 비슷한 행동을 기대하는 후보 영역을 정해 시험 효율을 높이는 설계다. 다른 오류 원인이 있으면 분할을 더 세분화해야 한다.

경계에서 비교 연산자를 시험하기

<와≤, >와≥의 혼동은 영역 경계에서 드러난다. 정수 입력이라면 59,60,61처럼 경계의 이웃을 고른다. 유효 범위 끝인 0과 100에도 전후 사례−1,1 및 99,101을 고려한다.

연속 실수 입력의 바로 옆값은 정수의±1과 다르다. 자료형, 반올림, NaN 같은 특별값의 허용 여부를 명세에서 확인해야 한다. 여기서는 입력이 이미 정수라는 조건을 두고 문자열 변환 문제는 분리한다.

기대 결과는 구현 복제가 아니다

시험의 기대값을 현재 코드의 식을 그대로 복사해 만들면 같은 버그를 반복할 수 있다. 합격 기준은 독립적으로 명세에서 읽고, 각 입력을 왜 선택했는지 적는다. 구현이 x>60이라면 60 사례가 명세 위반을 찾아낸다.

대표 사례와 경계 사례를 조합한 뒤 누락된 업무 규칙을 검토한다. 정상 경로만 통과했다고 범위 검증이나 형식 변환, 외부 장애 경로까지 확인한 것은 아니다. 시험 범위와 아직 다루지 않은 조건을 기록한다.

중간 과정을 따라가는 예제

정수 score만 받는다. 0≤score≤100이면 60 이상 합격, 그 미만 불합격이고 범위 밖은 입력 오류다. −1,0,59,60,61,100,101의 기대 결과를 적어라.

  4. 100은 유효 상한이며 합격이다.

조건을 바꾸어 비교하기

요금 경계와 허용 경계는 다르다

n = 1을 고정하고 w = 4, 5, 6, 10, 11의 기대값을 구하라.

  1. 4와 5는 총 무게 5 이하라 요금 4, 6과 10은 유효한 큰 총 무게라 요금 7이다.

  2. 11은 개별 무게와 총 무게 상한을 위반하므로 요금 계산 대신 오류다.

순서대로 요금 4, 4, 7, 7, 오류다.

비교할 점

5의 전환은 요금 전환이고 10의 전환은 성공/오류 전환이다.

개별 범위는 맞지만 관계가 틀리다

n = 2를 고정하고 w = 4, 5, 6을 비교하라.

  1. 총 무게는 각각 8, 10, 12다. 세 무게와 n은 모두 개별 범위 안이다.

  2. 앞 두 입력은 요금 7이고 마지막 입력은 관계 조건 위반으로 오류다.

개별 범위 시험만으로 w = 6, n = 2의 오류 기대값을 대신할 수 없다.

비교할 점

관계 경계의 이웃을 추가해 검사 누락을 드러낸다.

연습 1 · 값과 상태 예측

독립 입력 (w,n) = (2,2), (3,2), (2,4), (3,4)의 기대 결과를 적어라.

힌트 1

총 무게를 먼저 각각 계산한다.

힌트 2

요금 기준보다 유효 관계 조건이 먼저다.

풀이와 답 확인

  1. 총 무게는 4, 6, 8, 12다.

  2. 첫 입력은 요금 4, 둘째와 셋째는 요금 7, 마지막은 오류다.

요금 4, 요금 7, 요금 7, 오류다.

흔한 오답에서 다시 생각하기

모든 입력이 개별 범위 안이므로 전부 요금을 반환한다.

총 무게 상한이라는 두 입력의 관계를 검사해야 한다.

연습 2 · 오류 찾아 고치기

변형은 개별 범위만 검사하고 총 무게가 5 이하이면 4, 아니면 7을 반환한다. (1,1)과 (6,1)만 통과했다. 반례와 정상 회귀를 구성하라.

힌트 1

각 범위는 만족하되 곱이 10보다 큰 입력을 고른다.

힌트 2

경계 안의 곱 10도 성공으로 남겨야 한다.

풀이와 답 확인

  1. (6,2)는 총 무게 12라 오류가 명세인데 변형은 7을 반환한다.

  2. (5,2)는 총 무게 10이라 요금 7을 유지해야 한다.

오류 반례 (6,2)와 정상 회귀 (5,2)를 함께 확인한다. 실제 구현 실행은 미수행이다.

흔한 오답에서 다시 생각하기

곱이 큰 모든 입력을 거절하면 모든 정상 요구도 맞는다.

개별 범위와 정확 허용 경계 10을 함께 보존해야 한다.

연습 3 · 직접 만들어 보기

n = 2에서 관계 상한과 요금 경계의 두 쌍을 고르고 왜 바로 옆 정수 곱을 모두 만들 수 없는지 설명하라.

힌트 1

관계 상한에는 w = 5와 6을 쓴다.

힌트 2

n = 2이면 가능한 총 무게는 짝수다.

풀이와 답 확인

  1. 상한 비교는 (5,2)의 총 무게 10 성공과 (6,2)의 12 오류다.

  2. 요금 비교는 (2,2)의 4와 (3,2)의 6이다. 이 고정 n에서는 총 무게 5나 11을 만들 수 없다.

입력 좌표의 이웃과 계산된 곱의 이웃은 같지 않다. n = 1에서 총 무게 5/6과 10/11을 추가로 다룬다.

흔한 오답에서 다시 생각하기

모든 n에서 총 무게 9/10/11을 같은 방법으로 고르면 된다.

정수 곱의 도달 가능한 값은 고정 n에 따라 달라진다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

개별 범위 안 입력은 10 × 4 = 40쌍이다. 관계까지 유효한 입력 수와 요금 4인 입력 수를 구하라. 유한 전수 확인 계획이 전체 파서 안전을 증명하는가?

힌트 1

각 n마다 w의 상한은 min(10, floor(10/n))이다.

힌트 2

낮은 요금의 w 상한은 floor(5/n)이다.

풀이와 답 확인

  1. 유효 수는 n = 1,2,3,4에서 각각 10, 5, 3, 2로 합 20이다.

  2. 낮은 요금 수는 각각 5, 2, 1, 1로 합 9이며 높은 요금은 11쌍이다.

40쌍 중 유효 20쌍, 요금 4는 9쌍, 요금 7은 11쌍이다. 전수 계획을 실제 실행하거나 범위 밖/변환 단계까지 확인한 것은 아니다.

흔한 오답에서 다시 생각하기

40쌍만 모두 맞으면 어떤 문자열과 서비스 입력도 안전하다.

한정한 이미 정수인 영역과 실제 변환·외부 서비스 계약은 다르다.

  • 독립된 시험 상태와 정리 책임을 설계한다.

반환값이 같은 대역 호출이 한 번과 두 번이면 같은 시험일까?

새 주문 계약은 양의 정수 수량 n을 받고 price()를 한 번 호출해 반환 가격 5를 얻는다. 가격 조회가 성공하면 total = 5n을 계산하고 notify(total)을 정확히 한 번 요청한다. notify가 정상 반환하면 total을 반환하고 실패하면 그 오류를 전달한다. 가격 조회가 실패하면 notify를 호출하지 않는다. 오류 전달이 이미 일어난 외부 효과를 되돌렸다는 뜻은 아니다.

순수 호출 장부에서 notify는 매번 성공한다고 정하고 n = 2를 사용하자. 정상은 가격 호출 1회, 알림 인자 [10], 반환 10이다. 알림을 두 번 호출하는 변형은 인자 [10,10]과 같은 반환 10을 만든다. 마지막 인자만 검사하면 중복을 놓치지만 정확 한 번 조건은 이를 구별한다. 여기서 장부는 unittest.mock의 실제 실행 출력이 아니다.

fixture도 객체의 이름보다 상태와 수명이 중요하다. 두 시험이 같은 가변 목록을 받으면 첫 시험이 추가한 항목을 둘째가 볼 수 있다. 준비 단계에서 자원 A를 만든 뒤 B 준비가 실패하고 yield에 도달하지 못한 통합 fixture는 yield 뒤 정리를 기대할 수 없다. 성공한 자원마다 정리 책임을 먼저 확보하거나 성공/실패 경로를 분리한다. 실패한 생성은 자원을 남기지 않고 정리 자체는 성공한다는 추가 가정을 아래 모형에 명시한다.

먼저 확인할 개념
  • 대역의 응답과 호출 계약

    반환과 호출 횟수·인자 및 실제 외부 효과를 별도로 관찰한다.

  • 실패 조건의 독립 기대 결과

    대역의 실패가 발생하는 위치마다 다음 호출과 상태를 정한다.

의존성을 통제하는 두 목적

외부 결제·메일·시각 서비스가 늘 실제로 실행되어야 한다면 작은 함수의 시험도 느리고 불안정해진다. 시험용 대역을 주입하면 특정 응답을 고정하거나 실패를 재현할 수 있다. 여기서는 정해진 응답을 공급하는 역할을 stub, 호출 횟수와 인자 계약을 확인하는 역할을 mock이라고 구별한다.

도구의 클래스 이름이 이 역할을 딱 하나만 수행한다는 뜻은 아니다. Python Mock 객체도 return_value로 응답을 주면서 assert_called_once_with로 상호작용을 검증할 수 있다. 용어와 도구 기능을 구분한다.

시험마다 준비할 상태를 정하기

fixture는 시험이 필요한 데이터·객체·환경을 준비하고 필요하면 정리하는 구성이다. 빈 장바구니를 매 시험에 새로 만들면 앞 시험이 남긴 상품 때문에 다음 시험이 영향을 받는 일을 줄인다. 넓은 범위의 공유 fixture는 속도와 상태 격리 사이의 선택이다.

임시 파일이나 연결처럼 정리가 필요한 자원은 성공·실패 경로에서도 정리 책임을 정한다. pytest의 yield fixture는 yield 앞에서 준비하고 뒤에서 정리하는 패턴을 제공한다. 준비 자체가 중간에 실패하는 상황도 고려해야 한다.

대역의 통과와 실제 연결의 통과는 다르다

상품 주문 함수가 가격 조회 stub을 통해 100을 받고 수량 2의 총액 200을 계산한다고 하자. mail mock에 send("확인",200)을 한 번 요구하면 메시지 호출 계약을 시험할 수 있다. 실제 메일 서버 로그인이나 배달 결과는 아직 확인하지 않았다.

대역이 실제 API와 다른 응답을 주면 시험이 틀린 가정을 강화할 수 있다. 단위 시험과 실제 구현을 연결한 통합 시험을 구별하고, 내부 함수 호출 순서를 과도하게 고정하여 정당한 리팩터링을 어렵게 만들지 않는다.

같은 마지막 인자와 다른 횟수

  1. 두 경로의 마지막 인자는 모두 10이라 마지막 인자만 확인하면 둘 다 맞는다.

  2. 총 호출 수는 1과 2이므로 정확 한 번 조건은 정상만 맞는다.

비교할 점

결과와 효과의 총 횟수는 다른 관찰이다.

yield 전에 멈춘 준비

통합 fixture가 A 생성 성공→B 생성 실패→yield 미도달이면 yield 뒤 A 정리를 기대할 수 있나? B 실패는 자원을 만들지 않는다고 정한다.

  1. 이 fixture의 yield 뒤 정리 코드는 실행 단계에 도달하지 못한다. A 정리가 별도로 등록되지 않았다면 남는다.

  2. A를 독립 fixture로 준비해 성공적으로 yield한 뒤 B fixture가 실패하게 나누면 pytest는 이미 성공한 A의 정리를 시도한다.

첫 계획은 A 누수 가능성이 있고 분리 계획은 성공한 A의 정리 책임을 확보한다. 정리 자체의 실패까지 자동 해결한다는 뜻은 아니다.

비교할 점

  2. price 실패는 계산 완료와 알림이 없고 조회 오류를 전달한다. notify 실패는 total 15를 계산하고 한 번 시도한 뒤 알림 오류를 전달한다.

연습 2 · 오류 찾아 고치기

T1은 shared 목록에 A를 추가하고 T2는 빈 목록을 기대한다. 두 시험에 같은 목록을 반환하는 fixture를 썼다. 실행 순서와 수정 계획을 설명하라.

힌트 1

T1 다음 T2이면 이전 항목 A가 남는다.

힌트 2

시험당 새 객체와 동일 객체 내용 초기화를 구별한다.

풀이와 답 확인

  1. T1→T2는 T2가 [A]를 보아 빈 목록 기대와 충돌한다. T2→T1에서는 T2 시작이 빈 목록일 수 있어 순서에 따라 숨겨진다.

  2. 두 시험 각각에 새 빈 목록과 새 호출 장부를 제공한다. 단순 이름 재대입이 다른 참조의 옛 객체까지 바꾸는 것은 아니다.

공유 상태의 순서 의존을 제거하는 준비 계획을 구성한다. 실제 pytest 실행은 하지 않았다.

연습 3 · 직접 만들어 보기

A/B 두 자원 준비의 성공·실패 및 정리 계획을 설계하라. 각 생성 실패는 자원 없음, 성공한 자원의 정리는 성공한다고 가정한다.

힌트 1

A의 성공 뒤 B 준비 전에 A 정리 책임이 존재해야 한다.

힌트 2

둘 다 성공한 뒤에는 B를 먼저, A를 나중에 정리한다.

풀이와 답 확인

  1. A 생성 실패면 정리 대상이 없다. A 성공/B 실패면 A를 정리한다.

  2. 둘 다 성공이면 사용 후 B→A로 정리한다. pytest에서는 각 성공한 생성/정리를 별도 yield fixture에 묶거나 성공 뒤 finalizer를 등록하는 방법을 계획할 수 있다.

소유한 자원만 각각 한 번 정리한다. 실제 생성·삭제·finalizer는 실행하지 않았다.

실패 전에 finalizer부터 등록하면 존재하지 않는 자원도 항상 지울 수 있다.

정리할 자원을 실제 소유했는지 먼저 확인해야 한다.

  • 문장과 분기 커버리지의 분모를 구별한다.

  • 높은 수치와 실제 요구 충족의 차이를 설명한다.

각 조건의 참과 거짓을 모두 봤는데 두 조건이 동시에 참인 입력은 빠질 수 있을까?

자체 함수는 입력 A/B 두 불리언을 각각 별도 if에서 관찰 로그로 기록한 뒤, 정확히 하나만 참이면 True를 반환한다. 명세 결과는 XOR다. 첫 if는 A가 참이면 AT, 거짓이면 AF를 기록하고 둘째 if는 B에 따라 BT 또는 BF를 기록한다. 반환은 한 단계다. 구현·도구별 실제 실행 가능 줄과 분모 대신 이 종이 모형의 일곱 문장과 네 방향을 직접 정의한다.

문장은 첫 조건 평가 C1, AT 기록, AF 기록, 둘째 조건 평가 C2, BT 기록, BF 기록, 반환 R의 일곱 개다. 방향은 C1의 참/거짓과 C2의 참/거짓, 총 네 개다. 시험 (True,False)와 (False,True)를 합치면 일곱 문장과 네 방향을 모두 지나지만 (True,True)와 (False,False)는 한 번도 사용하지 않았다. 서로 다른 각 분기의 방향을 합친 값은 입력 조합의 목록이 아니다.

XOR를 OR로 잘못 구현해도 두 시험의 반환은 모두 True여서 같은 기대값으로 통과할 수 있다. 동시에 참인 입력의 명세 반환 False와 변형 반환 True가 차이를 만든다. 커버리지는 빠진 위치의 단서이고 기대값의 독립성·조합 선택을 대체하지 않는다. 여기서는 함수나 coverage.py를 실행한 보고가 아닌 손으로 정의한 방문 집합이다.

먼저 확인할 개념
  • 문장·방향의 서로 다른 분모

    방향 합집합과 입력 조합을 별도 장부로 기록한다.

  • 독립 명세의 기대 결과

    OR 구현을 기대값에도 복제하지 않는다.

어느 부분을 실행했는지 세기

문장 커버리지는 지정한 실행 가능 문장 중 시험이 지나간 문장의 비율이다. 분기 커버리지는 조건에서 가능한 방향 중 지나간 방향의 비율을 다룬다. 어떤 줄을 지났는지와 어떤 결과가 옳았는지는 다른 정보다.

실제 도구마다 제외 문장, 보고 분모, 줄 단위 분기 계산이 다를 수 있다. 이 소단원은 직접 정한 문장 4개와 if의 방향 2개를 세는 작은 모델이다. 도구의 최종 합산 비율이라고 주장하지 않는다.

한 번의 실행이 두 분기를 채우지는 않는다

다음 의사 코드에서 amount>0이면charge=amount, 아니면charge=0으로 둔다. return이 양쪽 뒤에 있어도 양수 시험 하나는 참 방향만 지났다. 거짓 방향 시험을 추가해야 두 방향을 확인한다.

문장 집합은 S1:조건 평가,S2:참 대입,S3:거짓 대입,S4:반환의 네 개로 정의한다. amount=2는 S1,S2,S4를 지나므로 3/4다. amount=0을 추가하면 S3도 지나 네 문장을 모두 채운다.

if amount > 0:       # S1
    charge = amount  # S2
else:
    charge = 0       # S3
return charge        # S4

빠진 요구와 약한 기대값을 찾기

모든 분기를 지났더라도 charge를 잘못 계산하거나 반환값을 확인하지 않으면 버그를 놓칠 수 있다. 입력 종류의 조합, 반복 횟수, 순서, 외부 실패처럼 분기 비율만으로 알 수 없는 조건도 많다.

커버리지는 빠진 실행 영역을 찾는 지도처럼 사용한다. 미실행 부분의 이유를 살피고 명세 기준의 기대값, 경계, 오류 경로, 필요하면 변이 시험과 속성 시험을 함께 고려한다. 수치를 올리기 위해 중요한 코드까지 제외하면 보고의 의미를 바꾼다.

  2. 참 방향만 지나므로 분기 1/2=50%다.

  3. T2가 거짓 방향 S3를 실행하여 합집합은 네 문장이다.

  4. 두 시험 합산의 문장은 4/4=100%, 분기는 2/2=100%다.

T1만 75%/50%, 둘을 합치면 100%/100%다. 이것은 정한 모형의 실행 영역 비율이다.

자체 배송 계약의 (w,n) = (5,2), (6,2), (0,2)를 독립 판단하라. 견적 성공 뒤 notify(요금)을 한 번 요청하고 알림 실패는 전달한다고 추가한다. 각 입력은 새 호출 장부에서 시작하며 알림 대역은 성공한다. 배송 개별 범위와 곱 상한을 먼저 판단하고, 정상 견적에서만 알림 횟수와 인자를 기록한다.

힌트 2

성공한 준비의 소유권과 yield 도달을 나눈다. XOR 기대값을 OR 구현에서 복사하지 않는다.

풀이와 답 확인

  1. (5,2)는 총 무게 10으로 요금 7이고 알림 인자 [7] 한 번이다. (6,2)는 총 무게 12, (0,2)는 무게 범위 위반으로 오류이며 알림을 요청하지 않는다.

  2. 정상과 중복 변형의 반환 요금 7 및 마지막 인자 7은 같지만 총 횟수는 1과 2다. 정확 한 번 조건은 중복을 구별한다. 대역 시도는 실제 배달 확인이 아니다.

  3. 통합 fixture의 yield 뒤 정리만 기다리면 A가 남을 수 있다. 성공한 A를 별도 fixture로 yield하거나 성공 뒤 정리 책임을 등록하여 B 실패에도 A 정리를 수행하도록 계획한다.

  4. TF/FT의 XOR와 OR 반환은 둘 다 True라 해당 변형을 놓친다. TT를 추가해 독립 False 기대와 OR의 True를 구별한다. 문장/방향의 비율은 이미 100%지만 조합은 2/4에서 3/4가 된다.

배송 결과는 요금 7/오류/오류이며 정상의 알림 한 번과 중복 두 번을 분리한다. A의 성공 뒤 정리 책임을 확보하고 TT의 독립 XOR 기대 False로 OR 변형을 구별한다. 실제 서비스·도구·자원 생성/삭제·학생 실행은 미수행이다.

해결한 뒤 점검할 것

  • 개별 입력 범위와 두 입력의 관계 및 정상 요금을 분리한다.

  • 반환/마지막 인자와 호출 횟수 및 실제 배달을 구별한다.

  • yield 이전 실패와 이미 성공한 A의 정리 책임을 명시한다.

  • 문장·방향·조합의 세 분모를 그대로 유지한다.

  • 추가 입력의 기대값을 독립 명세에서 만들고 계획과 실제 실행을 구별한다.
