소단원 2.1

반복·애자일·계획 중심 비교

한 달 뒤에 완성품을 처음 보여주는 것과 매주 일부를 보여주는 것 중 어느 쪽이 틀린 요구를 빨리 찾을까?

준비 개념과 학습 목표

준비 개념

  • 요구는 사용자가 원하는 관찰 가능한 결과다. 예: 대출한 책 목록을 표시한다. 구현 작업인 파일 작성과 구별한다.

  • 반복은 같은 종류의 활동을 다시 수행하는 것, 증가분은 기존 기능 위에 사용 가능한 기능을 더하는 것이다. 같은 화면을 개선만 하면 반복적이지만 기능 증가가 없을 수 있다.

  • 가정과 증거를 구별한다. 예상 수정시간은 추정이고 실제 사용자 시험 결과와 다르다. 종이 사례의 비용은 실제 팀 생산성을 측정한 값이 아니다.

학습 목표

  • 반복·점진·애자일·계획 중심의 서로 다른 축을 비교한다.

  • 불확실성과 검증 비용에 맞춰 피드백 시점을 선택한다.

  • 문서와 변경 통제도 애자일 과정에서 필요한 이유를 설명한다.

활동을 다시 하는 것과 기능을 늘리는 것

프로세스는 요구를 파악하고 설계·구현·검증·운영을 이어 가는 활동과 결정 규칙이다. 반복적 과정은 결과를 보고 요구나 설계를 다시 고친다. 점진적 과정은 사용 가능한 부분을 늘린다. 매회 같은 프로토타입을 고치는 반복과 대출조회 후 반납 기능을 추가하는 증가분은 다르며 두 특성을 함께 가질 수 있다.

계획 중심은 범위·산출물·책임·승인 기준을 미리 상세히 정하는 정도가 큰 접근이다. 단계가 있다는 사실만으로 피드백이 금지되지 않는다. 이 단원은 모든 계획 중심 개발을 되돌아갈 수 없는 폭포수와 동일시하지 않으며 반복을 한다는 사실만으로 애자일이라고 판정하지 않는다.

가치와 운영 규칙을 연결하기

애자일은 변화에 대한 학습과 사람들의 협력, 가치 있는 결과의 자주 확인을 중시하는 가치와 원칙이다. 선언은 계획·문서·계약의 가치를 부정하지 않는다. 변경의 효과와 안전·접근성 같은 품질 기준을 기록해야 협력자가 같은 사실을 바탕으로 결정할 수 있다.

Scrum은 이러한 접근에 쓰일 수 있는 특정 프레임워크다. 2020 가이드의 Sprint는 한 달 이하이며 목표와 완료 기준을 사용한다. 본문의 일주일 피드백 사례는 가능한 자체 설계이지 모든 애자일 팀이 반드시 Scrum 또는 주간 Sprint를 사용해야 한다는 뜻이 아니다.

선택에는 조건과 비용이 있다

요구가 불확실하면 작은 결과를 일찍 확인해 잘못된 해석을 줄일 수 있다. 반면 외부 장비 승인에 시간이 오래 걸리거나 여러 팀이 고정 인터페이스에 의존하면 사전 합의와 추적 가능한 문서가 중요하다. 같은 프로젝트에서 불변 인터페이스를 계획하고 화면을 반복 개선할 수 있다. 두 접근의 이름만으로 우열을 증명하지 못한다.

가상 수정 비용을 C=k×m+r로 잡자. k는 잘못된 해석에 의존한 작업 수, m은 각 작업 수정시간, r은 검토시간이다. 이 모형은 독립·동일한 수정 비용을 가정하며 코드 간 상호작용, 작업 중단 비용을 생략한다. 일찍 발견해 k가 줄어도 검토 횟수가 늘면 비용이 생기므로 피드백을 무료라고 말할 수 없다.

중간 과정을 따라가는 예제

가상 도서 앱에서 잘못 해석한 대출기간 규칙을 작업당2시간으로 수정한다. 마지막 검토는 의존 작업6개 이후, 조기 검토는2개 이후다. 두 경우 검토1회는1시간이며 발견 후 남은 작업은 올바르게 한다. 해당 오류의 수정+검토 비용을 비교하라.

  1. 마지막 발견은 k=6,m=2,r=1이므로 C=6×2+1=13시간이다.

  2. 조기 발견은 k=2로 C=2×2+1=5시간이다.

  3. 이 오류의 비용 차이는13−5=8시간이다. 원래 기능 구현시간은 이 계산에 포함하지 않았다.

  4. 조기 검토를 추가로4회 했다면 같은 비용 모형에서4시간이 더해져 총9시간, 마지막 검토13시간 대비4시간 절감이다. 실제 작업시간 측정이나 사용자 실험은 아니다.

가정 아래 오류 처리 비용은13시간 대5시간, 추가 검토4회까지 세면13시간 대9시간이다. 불확실성·검토 비용·의존 작업 수를 확인해야 선택 근거가 된다.

종이와 본문으로 직접 해보기

각 작업 수정이1시간이고 마지막 발견 k=3, 조기 k=1이다. 조기 방식에만 추가 검토가3회, 각1시간이면 두 방식의 비용을 비교하라. 공통 마지막/발견 검토1시간을 포함한다.

힌트 보기

조기 방식의 추가 검토도 r에 더한다.

풀이 보기

마지막3×1+1=4시간, 조기1×1+1+3=5시간이다. 이 가정에서는 조기가1시간 더 든다. 앞 사례의 절감은 일반 법칙이 아니라 특정 의존 작업 수와 검토 비용에 따른 결과다.

오해와 반례

애자일은 계획과 문서를 없애고 변경을 언제나 즉시 넣는 방식이다.

공통 인터페이스를 문서 없이 바꾸면 다른 팀이 같은 이름을 다른 뜻으로 해석할 수 있다. 변화 대응에는 영향·기준·일정의 재합의가 필요하다. Scrum에서도 목표를 해치지 않는 범위 협의가 있어 변경 무제한이라는 결론은 나오지 않는다.

한 단계 더

심화: 마지막/조기 의존 작업 수를 kₗ,kₑ, 공통 수정 비용을 m, 추가 조기 검토 비용을 Δr라 두면 조기가 싼 조건은 (kₗ−kₑ)m>Δr다. 등호이면 비용은 같다. 수정 비용이 작업별로 다르면 단순 곱 대신 실제 영향을 받는 작업의 비용 합으로 바꾸어야 한다. 이 비교는 가치·안전성·지연에 대한 최종 판단까지 자동으로 결정하지 않는다.

소단원 2.2

역할·일정·위험

두 사람이 있으면 세 작업의 기간을 언제나 절반으로 줄일 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 역할은 맡은 책임의 종류이고 사람은 책임을 수행하는 주체다. 한 사람이 여러 역할을 할 수 있으며 역할 이름만으로 권한이 정해지지 않는다.

  • 의존성 A→B는 A의 합의된 완료 결과가 있어야 B를 시작할 수 있다는 뜻이다. 작업시간과 달력기간을 구별한다.

  • 확률 p와 손실 c의 곱 pc는 단순한 기대손실이다. p가 가상 추정이면 결과도 추정이며 낮은 확률의 큰 피해를 무시하는 허가가 아니다.

학습 목표

  • 결정·구현·검토 책임과 완료 근거를 연결한다.

  • 의존성과 자원 제약으로 일정의 하한과 가능한 계획을 구한다.

  • 위험·현재 이슈·가정 및 완화의 비용을 분리한다.

사람을 나누기 전에 책임을 명시한다

가상 팀에서는 요구 우선순위 결정자, 구현 담당자, 독립 검토자를 기록하고 누가 어떤 근거로 결정을 확정할지 합의한다. 구현자가 자기 코드를 확인하는 것과 다른 사람이 요구와 대조하는 것은 다른 증거다. 독립 검토는 다른 관점의 오류 발견 기회를 주지만 무오류를 보장하지 않는다.

Scrum 2020은 Product Owner·Developers·Scrum Master의 책임을 구분한다. 이 역할 이름을 모든 회사의 직급이나 승인 체계로 일반화하지 않는다. 본문 가상 팀의 역할 표는 특정 조직 규정이 아니며 요구 수용·실행 검산·독립 검토·사용자 시험을 서로 다른 작업으로 취급한다.

일정은 합이 아니라 의존 경로와 자원을 본다

작업을 정점, 선행 관계를 화살표로 둔 비순환 그래프에서, 각 작업의 시작 가능 시각은 선행 작업들의 완료 시각 중 최댓값이다. 작업 길이가 d일 때 완료는 시작+d다. 자원이 충분한 고정 기간 모형에서는 가장 긴 선행 경로가 프로젝트 기간의 하한이다. 순환 의존성이면 이 모형에서 시작 불가능한 교착을 먼저 풀어야 한다.

총 작업량 W를 양의 정수 p명의 동일 작업자에게 배분한다 해도 기간은 W/p보다 짧을 수 없다. 여기에 의존 경로 길이 L을 합쳐 max(W/p,L)가 하한이다. 두 하한을 만족하는 실제 배치가 항상 존재하는 것은 아니다. 전문성·동시 작업 불가·검토 대기·고정시간 여부를 별도로 정한다.

위험은 미래의 불확실한 사건이다

위험은 아직 일어나지 않은 사건이 목표에 영향을 줄 가능성이다. 이미 검토 환경이 고장난 것은 현재 이슈다. 위험 기록에는 사건·가능성의 근거·영향·담당자·완화·재평가 시점을 둔다. 확률과 영향 값을 알 수 없으면 임의 수치를 정밀한 사실처럼 표시하지 말고 미확인 조건을 적는다.

단순 기대비용 모형은 완화 비용 v와 완화 전후의 pc를 비교한다. 이는 금액으로 환산 가능하고 확률 추정이 유효한 가정에서의 의사결정 보조다. 사람이 다치는 위험·권리·법적 요구 같은 제약을 낮은 기대값 하나로 교환할 수 없다. 일정 여유는 무엇이 늦어질 때 얼마나 흡수하는지 경로와 함께 기록한다.

중간 과정을 따라가는 예제

가상 팀 작업 A 요구합의2일, B 구현3일, C 검토1일, D 설명작성2일이다. A→B→C와 A→D가 있고 작업자는2명, 모두 같은 자격을 갖추며 작업은 중단 없이 한 사람이 전담한다. 이 모형의 기간과 위험 완화 비용을 구하라. 오류 재작업 위험은 p=0.3,c=10시간, 추가 검토 v=1시간 후 p=0.1이다.

  1. 작업량 W=2+3+1+2=8인일, W/2=4일이다. 경로 A→B→C는6일, A→D는4일이므로 하한6일이다.

  2. A를0~2일 한 사람이 수행한 뒤, B를2~5일, D를 다른 사람이2~4일 수행할 수 있다.

  3. C는 B 후5~6일에 수행한다. 계획6일은 하한과 같아 이 고정 모형에서 최적이다. 검토가 구현과 독립되어야 한다면 D 담당자가 C를 맡을 수 있다.

  4. 위험 기대손실은0.3×10=3시간. 완화 후 총기대비용은1+0.1×10=2시간으로 가정상1시간 감소한다. 이 가상 위험시간을 일 단위 작업 그래프에 자동 합산하지 않는다.

프로젝트6일의 가능한 배치가 있다. 위험 완화는 해당 가상 모형에서 기대비용3→2시간이며 실제 발생 빈도나 성능 관찰이 아니다.

종이와 본문으로 직접 해보기

같은 네 작업을 작업자1명만 수행한다면 최소 기간을 구하라. 위험 완화가 v=3시간이고 p=0.1로 바뀌는 경우 기대비용도 비교하라.

힌트 보기

작업을 동시에 하지 못하면 모든 기간을 더한다. 완화 비용을 빼먹지 않는다.

풀이 보기

A,B,C,D를 선행 조건에 맞게 순서 배치하면8일이고 작업량 때문에 더 짧을 수 없다. 완화 후3+0.1×10=4시간은 원래3시간보다1시간 크다. 비용 기준만 보면 이 완화가 낫다고 말할 수 없지만 다른 제약과 피해 분포도 검토한다.

오해와 반례

위험의 기대손실이 작으면 안전하고, 사람을 늘리면 일정도 비례해 단축된다.

A→B→C의6일 의존 경로는 작업자를 늘려도 각 고정 작업을 쪼개지 않는 한 그대로다. 낮은 확률의 큰 피해와 항상 작은 피해는 같은 기대값이어도 허용성이 다르다. 평균 숫자만으로 책임이나 안전을 결정하지 않는다.

소단원 2.3

이슈·변경 관리

요청이 “추가 기능 하나”라고 불려도, 기존 시험과 데이터에 영향을 주면 무엇을 먼저 기록해야 할까?

준비 개념과 학습 목표

준비 개념

  • 이슈는 해결할 질문·버그·작업을 추적하는 기록이다. 원인 추정과 재현 가능한 관찰을 분리한다.

  • 기준선은 비교할 특정 버전의 요구·코드·시험이다. 파일 이름만 같아도 내용이 바뀌면 같은 기준선이 아니다.

  • 회귀 시험은 변경 후 이전에 맞던 동작이 깨졌는지 확인하는 시험이다. 시험 통과가 모든 가능한 입력의 증명은 아니다.

학습 목표

  • 재현 조건·수용 기준·담당자·근거를 갖춘 이슈를 쓴다.

  • 변경 영향과 승인 근거를 기준선에서 새 버전까지 추적한다.

  • 닫힌 이슈·코드 병합·요구 검증을 서로 구별한다.

불만을 검증 가능한 기록으로 바꾸기

“대출 화면이 이상하다”보다 “v1에서 회원A가 이미3권을 빌린 상태로 네 번째 대출을 시도하면 성공이 표시됨, 요구R1은 동시3권까지”가 재현에 유용하다. 이슈는 버전·입력·절차·관찰·기대 결과·환경을 기록하고 개인정보는 필요한 가상 값으로 대체한다. 구현 결함인지 요구의 변경인지 아직 모르면 미확인 질문으로 남긴다.

GitHub Issues는 작업과 버그를 기록하고 담당자·의존 관계·PR을 연결하는 도구 예다. 종이 표에도 같은 논리 구조를 쓸 수 있다. 실제 GitHub 계정이나 외부에 이슈를 게시하는 일이 이 단원의 필수 활동은 아니다.

영향 분석과 변경 결정

변경은 기존 기준선의 어떤 요구를 어떤 이유로 바꾸는지 명시하고, 연관 설계·코드·자료·시험·운영을 찾는다. R1의 한도를3→5로 바꾸면 UI 숫자만이 아니라 서버 검사·기존 수용 시험·이용 안내가 영향을 받는다. 바뀌지 않는 접근권한 같은 요구도 회귀 대상으로 확인한다.

승인은 권한 있는 가상 역할이 근거를 보고 수용·보류·거절을 정하는 결정이다. 보류는 요청이 틀렸다는 판정이 아니라 추가 조건이나 자원이 필요하다는 뜻일 수 있다. 긴급 변경도 영향을 숨기지 않고 적용 범위와 후속 확인을 기록한다. 실제 조직의 승인 의무를 이 예제로 주장하지 않는다.

상태와 증거를 같이 갱신한다

자체 이슈 상태를 제안→분석→승인→구현→검증→종료로 두고 각 전이의 근거를 붙일 수 있다. 되돌아갈 수 없는 일방향 과정은 아니다. 검증에서 요구 불일치가 발견되면 구현 상태로 재개하고, 요구 자체가 불명확하면 분석으로 돌아간다. 승인되지 않은 요청은 보류/거절로 기록한다.

PR 병합이나 자동 닫기는 도구 사건이고 요구 만족 증거와 다르다. 재현 입력·기대 결과·실제 시험 결과·검토 버전을 기록해야 종료 판단을 다시 살필 수 있다. 계산 검산·독립 문서 검토·사용자 시험은 서로 다른 질문에 답하는 증거이므로 한 항목의 통과로 나머지를 완료 표시하지 않는다.

중간 과정을 따라가는 예제

가상 도서 서비스 v1 요구R1은 한 사람당 동시3권 이하이다. 요청C7은5권으로 확대하자는 것. 유지할 요구R2는 다른 사람의 대출 조회를 거부하는 것이다. 코드가 아직 없는 종이 검토에서 변경 영향과 종료 기준을 작성하라.

  1. v1/R1/R2를 기준선으로 쓰고 C7은 기존 요구 위반 버그가 아니라 R1 변경 제안이라고 분류한다.

  2. 한도 저장값·서버 신규대출 검사·화면 안내·시험 경계에 대한 영향 목록을 쓴다. 4권과5권까지 성공을 허용하고6번째 시도는 거부하는 새 기준을 명시한다.

  3. R2의 권한 거부는 유지하므로 다른 사람의 조회를 회귀 사례로 둔다. 기존 “4번째 거부” 시험은 새 요구와 충돌하므로 의도적인 수정으로 기록한다.

  4. 결정자 승인 후 v2 요구·구현 버전·6번째 거부와 R2 시험 결과·검토자를 연결해야 종료한다. 지금은 분석 문서만 만들었으므로 구현/실행검증/종료를 완료로 표시하지 않는다.

C7에 기준선·수용 기준·영향·승인·예정 시험을 연결한다. 종이 분석은 실행된 코드나 실제 사용자 시험의 증거가 아니다.

종이와 본문으로 직접 해보기

상태가 승인→구현인 이슈에서 병합 후 “빈 목록이면 화면이 멈춤”이라는 가상 검토 의견이 나왔다. 종료시키지 않고 어떤 기록/상태를 써야 할까? 빈 목록 수용 기준은 정상적인 “0권” 표시이다.

오해와 반례

이슈가 닫히거나 PR이 병합되면 요구를 만족했고 사용자 검증도 끝났다.

커밋 메시지로 이슈가 자동 닫혀도 여섯 번째 대출이 허용되는 오류가 남을 수 있다. 닫힘은 기록 상태이며 실제 시험 결과·수용 기준·버전의 연결을 확인해야 한다. 자동화 자체와 검증의 타당성은 별도다.
