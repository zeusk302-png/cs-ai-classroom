소단원 4.1

유스케이스·사용자 스토리

“학생이 답안을 제출한다”라는 한 줄만으로 개발자와 검토자가 같은 기능을 만들 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 액터는 시스템 밖에서 상호작용하는 역할이다. 학생·채점자 역할을 실제 사람 한 명과 구분한다.

  • 경계는 이번 시스템이 맡을 일을 나누는 선이다. 아래 모형은 한 답안의 제출 기록만 다루고 계정·실제 성적 서비스는 만들지 않는다.

  • 전제는 시작 조건, 사후 조건은 성공·실패 뒤 보장할 상태다.

학습 목표

  • 스토리의 역할·목표·이유와 유스케이스의 성공/대안 흐름을 작성한다.

  • 수용 기준을 구체 입력과 관찰 결과로 연결하며 구현·사용자 검증과 구분한다.

제출됐다는 응답 하나로 어느 내용이 접수됐는지도 알 수 있을까?

원본의 제출 목표를 다른 질문으로 확장한다. 자체 새 계약에서는 한 시도의 초안 내용과 이미 접수한 내용의 스냅샷을 구별한다. 학생의 목표는 제출 여부뿐 아니라 접수된 내용이 자신이 의도한 내용인지 확인하는 것이다. 이 목표에서 제출 후 수정 가능 여부나 마감 시각은 자동 결정되지 않으므로 이 보강은 수정 불가라는 정책을 명시한다.

새 순차 모형의 Draft는 원문 raw만 가지며 접수 스냅샷 snap은 없음이다. submit을 허용하면 그 시점의 raw를 그대로 snap에 복사하고 Submitted로 바꾼다. Submitted의 재제출은 이미 접수한 snap을 확인하도록 알리고 바꾸지 않는다. edit은 Draft에서만 가능하다. raw와 snap은 교육용 문자열 값이며 실제 저장·파일 복제·서버 구현을 수행하지 않았다.

빈 내용의 판정에는 정책 버전을 쓴다. v1은 raw의 길이가 0이면 거절한다. v2는 양끝의 U+0020만 제거한 문자열의 길이가 0이면 거절하지만, 성공 접수할 snap은 제거 전 원문 그대로다. 탭·개행·전각 공백까지 같은 정책이라고 확대하지 않는다. 허용 여부 계산과 보관값 변환은 별도 약속이므로 하나의 trim이라는 말로 묶지 않는다.

사용자 목표의 짧은 출발점

사용자 스토리는 누가 무엇을 원하며 왜 필요한지를 짧게 표현하여 논의를 시작한다. “학생으로서 답안을 제출하고 싶다. 내가 제출했는지 확인하기 위해서다”처럼 역할·활동·목표를 함께 적는다. 이 문장은 사용자 가치를 설명하지만 빈 답안·중복 클릭·변경 허용 범위까지 모두 정하지는 않는다. 양식의 세 문장을 썼다는 사실만으로 완전한 명세가 되지 않는다.

스토리의 역할은 시스템 외부에서 보는 행동 역할이다. 한 사람이 학생 역할과 채점자 역할을 각각 수행할 수도 있지만 권한 조건은 역할별로 정해야 한다. 내부 데이터베이스를 액터로 적는 것처럼 경계를 흐리면 구현 부품과 외부 상호작용자가 섞인다. 외부 서비스가 이번 경계 밖에서 통신한다면 별도 액터로 볼 수 있으므로 무엇을 포함했는지 먼저 정의한다.

흐름과 분기까지 풀어 적기

유스케이스는 목표를 이루는 시스템·액터 상호작용을 조금 더 풀어 적는다. 여기의 작은 작성 틀은 이름, 주 액터, 시작 전제, 시작 사건, 정상 흐름, 대안 흐름, 사후 조건이다. 정확한 문서 양식은 조직마다 다르며 이 틀이 유일한 표준은 아니다. 중요한 것은 단계가 내부 구현 순서를 강제하기보다 외부 행동과 약속을 설명하도록 하는 것이다.

정상 흐름만 적으면 실패 상황에서 데이터가 바뀌는지 알 수 없다. 초안 답안 제출에서 빈 답안을 거절한다면 초안 상태와 기존 내용이 그대로 남는지, 어떤 메시지가 보이는지 정해야 한다. 제출 후 다시 제출했을 때 새 기록을 만드는지 기존 제출을 알려주는지도 별도 선택이다. 이 단원은 아래 예에서 기존 제출을 보존하고 이미 제출되었다고 알리는 정책을 명시한다.

수용 기준과 확인 증거

수용 기준은 스토리의 목표가 충족되었다고 확인할 관찰 가능한 결과다. 주어진 상태에서 사건을 주었을 때 어떤 결과와 상태를 얻는지 적으면 시험 사례로 연결하기 쉽다. “제출 버튼이 예쁘다”보다 “빈 답안을 초안에서 제출하면 거절 메시지를 표시하고 제출 기록은0개”가 판정하기 쉽다. 사용성 목표는 없어지는 것이 아니라 어떤 사용자·과제·측정으로 검토할지 별도로 구체화한다.

기준을 문서에 적거나 시험 입력을 준비한 상태와 실제 시험을 통과한 상태는 다르다. 종이 모형이 자기 약속에 맞는다는 것은 구현·네트워크·학생 이해도까지 확인했다는 뜻이 아니다. 목표를 만족하는 다른 구현이 가능하다면 버튼 클릭 내부 함수·특정 DB 쿼리를 계약에 불필요하게 고정하지 않는 편이 변경 논의를 돕는다.

중간 과정을 따라가는 예제

가상 답안 모형은 상태 Draft/Submitted, 내용은 문자열, 한 답안에 제출 기록은 최대1개다. Draft에서 내용이 빈 문자열이 아니면 제출 성공, 빈 문자열이면 거절하고 그대로다. Submitted에서 다시 제출하면 상태·기록을 유지하며 이미 제출됨을 알린다. 스토리와 세 수용 사례를 작성하라. 공백만 있는 문자열은 여기서는 비어 있지 않은 것으로 정한다.

  1. 스토리는 “학생으로서 답안을 제출하고 제출 상태를 확인하고 싶다. 채점 요청이 접수되었는지 알기 위해서다”다. 역할·행동·목표를 분리한다.

  2. 초기Draft/내용"풀이A"/기록0에서 제출하면 Submitted/기록1과 성공 표시를 기대한다. 정상 흐름의 사후 조건이다.

  3. 초기Draft/내용""/기록0에서 제출하면 Draft/기록0와 빈 답안 거절을 기대한다. 실패에서도 내용과 기록을 바꾸지 않는다.

  4. 초기Submitted/기록1에서 재제출하면 Submitted/기록1과 이미 제출됨을 기대한다. 이는 새 기록2개를 만드는 동작과 다르다. 아직 실제 서비스 시험은 아니다.

한 스토리에 성공·빈 답안·재제출 세 사례를 연결한다. 문서상 기준 수3개와 구현 시험 통과 수를 혼동하지 않는다.

  1. v1의 길이 검사는 3이므로 성공해 Submitted가 되고 원문 공백 세 개를 snap에 둔다.

오해와 반례

사용자 스토리 한 줄이면 모든 대안 흐름이 자동 결정된다.

“제출하고 싶다”는 문장에 공백·재제출·저장 실패의 규칙은 없다. 같은 스토리를 읽고 두 개발자가 기록1개 유지와 매번 새 기록을 각각 구현할 수 있다. 대안 흐름과 수용 기준을 합의해야 차이를 줄인다.

답안·학생·문제를 그린 그림과 초안→제출→채점의 그림은 어떤 다른 질문에 답할까?

준비 개념과 학습 목표

준비 개념

  • 도메인 개념은 다루는 세계의 대상이다. 학생 역할, 문제, 답안 시도를 구분한다.

  • 상태는 현재 상황, 사건은 들어오는 요청, 가드는 그 전이가 가능한 불리언 조건이다.

  • 0≤s≤100인 정수 점수와 문자열 내용, 제출 상태를 준비한다. 실제 학생 자료는 사용하지 않는다.

학습 목표

  • 개념 관계·상태 전이·행동 순서 모델의 관점을 구분한다.

  • 사건/가드/효과로 답안 전이를 추적하고 불변식을 검토한다.

상태가 Graded이고 점수가 있으면 어느 접수 내용을 채점했는지도 맞을까?

구조 모델에서 한 Attempt는 학생 역할 하나와 문제 하나에 연결되고, 접수 내용 snap 및 점수 score를 가진다고 하자. 상태 모델은 Draft/Submitted/Graded 중 하나를 고른다. 두 모델이 같은 이름을 쓰더라도 상태·속성이 맞아야 한다. 새 모형의 불변식은 Draft이면 snap과 score가 모두 없음, Submitted이면 snap이 있고 score는 없음, Graded이면 snap과 유효 정수 score가 모두 있다는 것이다.

이 보강의 사건은 한 번에 하나씩 원자 처리한다. Draft의 edit은 raw를 바꾸고, 허용된 submit은 raw의 스냅샷과 Submitted를 함께 만든다. grade는 Submitted에서만, 권한 있는 채점 역할과 0…100 정수 점수일 때 snap을 보존하고 Graded/score를 함께 만든다. 나머지 사건은 명시적으로 거절하고 모든 필드를 보존한다. 자료 관계가 있다는 사실은 채점 권한이 있다는 뜻이 아니다.

부분 효과를 허용하면 상태 그림만의 논증이 깨질 수 있다. 예를 들어 score=80을 먼저 쓰고 상태 갱신에 실패해 Submitted가 남으면 Submitted⇒score 없음을 위반한다. 상태부터 Graded로 바꾸고 점수 저장 전에 실패해도 반대 불변식을 위반한다. 여기서는 둘을 원자적 전이로 정했으며, 실제 데이터베이스 트랜잭션이나 장애 복구가 이를 구현했다는 증거는 없다.

  • 접수 내용과 변경 허용 범위

개념과 관계를 먼저 정하기

도메인 모델은 중요한 개념과 관계를 이해하려는 설명이다. 한 답안 시도는 문제 하나와 학생 역할 하나에 속한다고 정할 수 있다. 한 문제에는 여러 시도가, 한 학생 역할에는 여러 시도가 연결될 수 있다. 이것은 이번 교육 모형의 다중성이다. 실제 시스템이 익명 제출을 허용하거나 한 시도에 여러 문제가 들어가면 관계가 달라지므로 이름만 보고 영원한 규칙이라 생각하지 않는다.

개념의 이름과 의미를 용어집에 적으면 같은 “답안”이 내용 문자열인지 제출 시도인지 혼동하는 일을 줄인다. 개념 모델의 상자를 실제 프로그램 클래스나 DB 테이블 하나와 반드시 일대일 대응시키지는 않는다. 구현에서는 성능·저장·권한 때문에 여러 구조로 표현할 수 있다. 관계가 있다고 즉시 모든 데이터를 공개 조회할 권한이 생기는 것도 아니다.

상태와 전이의 작은 계약

이 단원에서는 한 시도를 Draft/Submitted/Graded 중 정확히 하나로 두며, 사건은 한 번에 하나씩 원자적으로 처리한다고 가정한다. 초기 Draft에서 edit(text)는 내용을 바꾼다. submit은 내용 길이>0일 때 Submitted가 되고, Submitted에서 grade(score,actor)는 actor가 채점 권한 역할이며 score가 0..100 정수일 때 Graded가 되어 점수를 저장한다. 그 밖 사건이나 실패한 가드는 거절하며 상태·내용·점수를 바꾸지 않는다.

가드는 미래에 수행될 일이 아니라 현재 상태와 사건 입력에서 확인하는 조건이다. 전이가 수행될 때 저장하는 점수는 효과다. “채점자면 된다”만 적으면 소수점·범위 밖 점수·Draft 채점이 허용되는지 알 수 없다. 같은 상태·사건에 서로 겹치는 가드의 두 전이가 가능하면 선택 정책이나 우선순위를 정의해야 한다. 이 모형에는 그런 충돌을 만들지 않는다.

관점이 다른 모형을 맞추기

상태 모델은 같은 사건이 현재 상태에 따라 어떻게 달라지는지 답한다. 행동이나 활동 흐름은 작업을 어떤 단계와 분기로 수행하는지, 상호작용 흐름은 역할과 시스템 사이 어떤 메시지가 오가는지 답할 수 있다. 개념 관계 모델에는 제출의 시간 순서를 담지 않고, 전이표만으로 개념의 모든 관계가 표현되는 것도 아니다. 서로 보완하는 모형의 이름을 함께 적는다.

예를 들어 “Graded이면 유효한 정수 점수가 있다”는 불변식을 전이표와 저장 속성에 같이 검토한다. Draft/Submitted는 아직 점수 없음으로 초기화하고, 오직 유효 grade만 Graded와 점수를 함께 만든다면 이 불변식을 유지한다. 이것은 단순한 단일 시도·순차 사건 모형의 증명이다. DB 실패·동시 요청·재전송·실제 권한 인증까지 해결한 구현 증거는 아니다.

준비 개념과 학습 목표

준비 개념

  • 고정 ID는 문서가 바뀌어도 항목을 찾는 이름이다. R은 요구사항, M은 모델 요소, T는 시험 사례로 쓴다.

  • 추적 링크는 두 항목의 근거 있는 관련성이다. 같은 단어가 있다는 이유만으로 유효한 링크가 되지는 않는다.

  • 비율에는 분모의 의미를 적는다. 연결된 요구3개/전체 요구3개와 실제 통과한 시험 수는 별개다.

학습 목표

  • 요구→모델→시험의 연결을 양방향으로 검토하고 변경 영향을 추적한다.

  • 모호한 문장을 조건·입력·관찰 범위로 고치면서 연결률과 충족 여부를 구분한다.

허용 출력이 둘이면 명세 오류일까, 구현 선택일까?

자체 조회 계약 F는 이미 접수한 기록 목록에서 내용이 같은 기록의 ID 하나를 반환한다고 정한다. ID는 목록에서 서로 다르고 내용이 일치하는 기록이 적어도 하나 있다는 전제다. 목록 [(a,x),(b,y),(c,x)]의 x 조회는 a와 c 둘 다 허용된다. 이것은 답을 합의하지 못한 공백이 아니라 허용 집합을 명시한 선택이다. 실행마다 무작위로 답해야 한다는 뜻도 아니다.

계약 G는 같은 입력 전제에서 목록 위치가 가장 앞선 일치 ID를 반환한다. 이 목록의 허용 집합은 {a}이고 G는 F보다 출력 약속을 강화한다. F만을 약속한 부품을 G의 호출자에 그대로 대입하면 c를 반환하는 부품에서 호출자 기대가 깨진다. 반대로 G를 만족하는 부품은 F가 허용한 어느 일치 ID 하나라는 약속도 만족한다.

추적 표에는 요구 ID뿐 아니라 정책 버전·입력·허용 출력 집합·보존 상태·실행 상태를 적는다. v1 길이 검사에서 v2 U+0020 판정으로 바꿀 때 공백 세 개의 기대는 성공에서 거절로 바뀌지만 원문 " x " 접수값은 그대로다. 링크 존재, 입력 범위 커버리지, 실제 실행, 결과 판정을 서로 다른 장부로 관리해야 변경 영향과 남은 조건을 설명할 수 있다.

양방향의 질문

추적성은 요구가 어떤 모델·설계·확인 항목에 배정되었는지 알 수 있게 한다. 요구에서 시험으로 따라가면 빠진 확인 범위를 질문하고, 시험에서 요구로 거슬러 가면 그 시험의 목적과 승인된 근거를 질문한다. 연결이 있는 것과 그 연결이 내용을 충분히 다루는 것은 별개다. 부모 요구를 반복한 문장을 붙인다고 더 구체적인 검증 조건이 생기지는 않는다.

목록에 없는 내부 안전 조건을 시험했다고 무조건 불필요한 것은 아니다. 파생 요구·설계 불변식·회귀 시험의 목적으로 정당화될 수 있다. 반대로 근거 없이 새 기능을 넣으면 승인 범위가 늘어날 수 있다. 출처·버전·변경 담당자와 연결 이유를 확인하고, 불명확한 부분을 미확인으로 남기는 것이 단어 일치 검색보다 중요하다.

모호함과 허용된 선택

“학생에게 점수를 빨리 보여 준다”에는 누구의 점수인지, 어떤 사건부터 시간을 재는지, 언제 표시가 끝난 것인지, 오류 상태를 어떻게 다루는지가 없다. 예컨대 유효한 채점이 완료된 후 현재 시도의 화면에서 점수80이 보여야 한다는 내용과 시간 목표를 나눌 수 있다. 시간 조건에는 환경·데이터·시작과 끝의 관측·표본 수·허용 기준을 함께 정해야 한다.

모든 선택을 하나로 고정해야만 좋은 명세인 것은 아니다. “일치하는 항목 하나의 ID를 반환한다”가 의도된 약속이면 여러 유효한 ID를 허용할 수 있다. “첫 번째”를 누락하여 혼동이 생긴 상황과 의도적으로 여러 답을 허용한 상황을 구분한다. 허용 집합이 명확한 명세는 구현자에게 선택을 줄 수 있으며 사용자가 그 선택을 임의로 가정하면 안 된다.

변경과 증거 상태

  2. Submitted의 edit("y")는 거절된다. grade100은 허용되어 Graded/score100이 된다. Graded의 grade0은 이 모형에 성공 전이가 없어 거절된다.

  3. 최종 raw와 snap은 모두 " x ", 상태는 Graded, score는100이다. 거절은 첫 submit·edit y·마지막grade의 세 개다. snap 존재와 유효 정수 점수를 함께 확인한다.

  4. 별도 F의 허용 집합은 {z,a}, G의 허용 집합은 {z}다. F에서 a만 기대하면 허용 결과 z를 잘못 실패로 판정한다.

  5. 네 사례가 각각 요구에 연결돼도 실행은0개이고 계획 대비 실행률0/4다. 계획이나 손논증을 구현·학생 시험 PASS로 표시하지 않는다.

허용 가드·효과·상태 관계·oracle을 서로 다른 조건으로 검토한다. 도달 상태의 종이 논증과 실제 저장·인증·사용자 검증은 구별하며 실제 구현 및 학생 실험은 미수행이다.
