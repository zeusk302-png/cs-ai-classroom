소단원 8.1

브랜치·병합·릴리스

각자 고친 코드를 합치면 항상 새 병합 커밋이 생길까?

준비 개념과 학습 목표

준비 개념

  • 파일 변경

  • 버전 이력

  • 그래프의 경로

학습 목표

  • 조상 관계에서 병합 종류를 판단한다.

  • 릴리스 이름·소스 revision·산출물을 구별한다.

파일이 옛 상태로 돌아가면 이력에서도 그 변경이 사라졌을까?

자체 이력은 부모에서 자식 방향으로 A → B → C다. A는 feature = off와 limit = 3, B는 feature만 on으로 바꾸고 C는 limit만 5로 바꾼다. C 위에서 B의 변경을 되돌리는 새 R을 기록하면 상태는 feature = off, limit = 5가 된다. 서로 독립인 두 필드를 가정하므로 충돌 없는 역변경을 손으로 정할 수 있다. 실제 Git 명령이나 저장소 변경은 하지 않는다.

R의 부모는 C이고 B도 여전히 R의 조상이다. 이 상태에서 B를 다시 병합하면 이력에는 이미 B가 포함돼 있어 같은 변경을 새로 가져오지 않는다. off라는 현재 값과 B가 이력에 있다는 사실은 모순이 아니다. 반대로 이후 실제로 on을 다시 도입하는 새 D를 R 위에 만들면 D는 새로운 변경이며 R에서 D로 기본 fast-forward할 수 있다.

이력 되돌리기와 운영 되돌리기도 나눈다. 소스 C에서 산출물 hC를 만들었다는 기록, 소스 R에서 hR을 만들었다는 기록, 실제 제공 중인 산출물이 무엇인지는 별도 장부다. 현재 공개 산출물이 hC라는 관찰이라면 소스 이름이 R로 이동했어도 제공 상태가 되돌아갔다고 선언하지 않는다. 산출물 식별·검증 범위와 실제 제공 확인을 함께 연결해야 한다.

먼저 확인할 개념
  • 조상 관계와 이동 가능한 이름

    현재 값과 이미 포함된 이력의 관계를 분리한다.

  • 검토 대상 revision

    되돌림과 재도입도 새 검토 대상임을 확인한다.

변경 이력의 점과 이름

커밋은 프로젝트의 기록된 상태와 부모 이력에 연결된 점으로 생각할 수 있다. 브랜치는 특정 커밋을 가리키는 이름이고 새 커밋을 만들면 그 이름이 앞으로 이동한다. 같은 이름 main이 오늘과 내일 다른 커밋을 가리킬 수 있다.

이력 그림에서 화살표를 부모에서 자식으로 그린다고 정하자. A→B이고 A→C라면 B와 C는 A에서 갈라진 작업이다. 실제 Git 객체는 부모를 기록하므로 이 교육 그림의 화살표 방향과 내부 저장 방향을 구별한다. 파일 복사 두 개만으로 모든 이력 정보를 설명할 수 없다.

앞으로 이동과 세 버전 비교

현재 B가 D의 조상이고 D로 병합하는 기본 fast-forward 상황에서는 브랜치 이름을 D로 옮길 수 있다. 갈라진 두 끝 B와 C를 합칠 때는 공통 조상 A와 두 끝을 비교하는 3-way가 필요하며 보통 두 부모 B,C를 가진 새 M을 만든다.

같은 줄을 다르게 고치면 충돌이 날 수 있다. 충돌 표시를 지우고 한쪽을 선택하는 작업만으로 기능이 옳다는 증명은 되지 않는다. 자동 병합이 성공해도 두 변경이 의미상 충돌할 수 있으므로 계약·테스트·리뷰가 필요하다. 정책의 --no-ff 등 선택은 기본 모형과 별도다.

누구에게 무엇을 내보내는가

릴리스는 사용자에게 제공하는 특정 결과와 그 기록이다. 브랜치 이름, 버전 태그, 소스 커밋, 빌드 산출물의 해시와 검증 상태를 함께 연결하면 어느 코드를 배포했는지 찾기 쉽다. 태그 이름도 권한과 명령에 따라 이동할 수 있으므로 이름만을 불변 증거로 삼지 않는다.

병합 완료와 실제 공개 배포 완료는 다른 단계다. 이 활동은 종이 이력과 가상 파일을 합치며 저장소 변경·명령 실행·서비스 배포는 하지 않는다. 실제 릴리스에서는 선택한 커밋에서 나온 산출물과 공개 서비스의 일치를 별도 확인한다.

새 재도입

표의 R은 C 전체를 A로 덮어쓰지 않는다. 이력에서 B가 사라지는 것도 아니다. D는 이미 존재한 B 이름을 재사용한 것이 아니라 새 변경을 기록한 점이다.

중간 과정을 따라가는 예제

자체 이력은 A→B와 A→C다. A의 파일은 두 줄 a=1,b=1, B는 a=2,b=1, C는 a=1,b=3이다. 서로 다른 줄은 결합할 수 있다고 가정한다. M의 파일과 부모, B→D인 별도 상황의 fast-forward를 추론하라.

  1. 공통 조상 A에서 B는 a만 1→2, C는 b만 1→3으로 바꿨다.

  2. 각 독립 변경을 결합해 M의 파일을 a=2,b=3으로 정한다. 두 끝 B,C를 부모로 기록한다.

  3. B와 C 중 한쪽이 다른 쪽의 조상이 아니므로 이 기본 상황은 단순 이름 이동으로 합치지 않는다.

  4. 별도 B→D 상황에서는 B가 D의 조상이다. 기본 fast-forward는 현재 이름을 D로 옮기며 새 M을 만들 필요가 없다.

가상 M은 a=2,b=3, 부모 B와 C다. 별도 B→D는 기본 fast-forward 가능하다.

조건을 바꾸어 비교하기

되돌린 상태와 남은 조상

C 위에서 B 효과를 역변경한 R을 만들고 B 재병합을 판단하라.

  1. feature만 off가 되고 C의 limit 5는 보존된다.

  2. B는 A → B → C → R 경로의 조상이다.

R은 off/5이며 B를 다시 병합해도 새 on 변경을 가져오지 않는다.

비교할 점

상태를 되돌리는 새 커밋과 이력 제거는 다르다.

새 소스와 옛 제공 산출물

소스 이름은 R을 가리키고 빌드 기록에 R/hR이 있지만 실제 제공 관찰은 hC다. 무엇을 완료라 기록할까?

  1. 소스 역변경과 hR 빌드 기록의 존재를 각각 기록한다.

  2. 실제 제공 산출물이 hR로 바뀌었다는 관찰은 없고 현재 hC라는 관찰이 있다.

공개 되돌림 완료라고 기록하지 않는다. 실제 제공 확인은 별도이며 여기서는 종이 장부만 검토한다.

비교할 점

빌드 기록의 존재와 제공 확인을 같은 증거로 쓰지 않는다.

종이와 본문으로 직접 해보기

같은 A의 a=1을 B는2, C는4로 바꾸었다. 자동으로 하나를 정할 수 있는가? 릴리스 이름 v1이 M을 가리킨 뒤 D로 이동하면 같은 이름만 적은 기록의 한계는?

힌트 보기

동일 줄의 상충 변경과 이름이 가리키는 커밋을 분리한다. 기능 계약이 없는 상태다.

풀이 보기

상충 변경은 기능 계약 없이 정답을 자동 선택할 수 없다. 어느 값을 채택했는지 이유와 검증을 남겨야 한다. v1 이름만 기록하면 M과 D 중 실제 제공한 소스를 구별하지 못하므로 커밋·산출물 해시를 함께 기록한다.

오해와 반례

병합이 성공하면 릴리스 기능도 자동으로 올바르다.

두 다른 파일의 함수 이름과 호출 이름을 각 브랜치가 따로 바꾸면 줄 충돌은 없어도 연결이 깨질 수 있다. 이력 병합과 기능 검증을 구별한다.

먼저 답과 이유를 적고, 필요한 만큼 힌트를 한 단계씩 열어 보세요.

연습 1 · 값과 상태 예측

독립 R 상태에서 새 D가 feature만 on으로 바꾼다. R에서 D 병합과 R 위에서 옛 B 병합의 상태를 각각 예측하라.

힌트 1

D는 R의 자식이다.

힌트 2

B는 R의 조상이다.

풀이와 답 확인

  1. D로 기본 fast-forward하면 on/5가 된다.

  2. 옛 B 병합은 이미 포함된 이력이라 R의 off/5를 유지한다.

새 D는 on/5, 옛 B 병합은 off/5다.

흔한 오답에서 다시 생각하기

두 경우 모두 on 변경이므로 결과가 같다.

변경 효과와 커밋의 조상 관계를 함께 읽는다.

연습 2 · 오류 찾아 고치기

R을 만들 때 C 전체를 A 파일로 덮어써 off/3으로 만들고 B만 되돌렸다고 했다. 차이를 고쳐라.

힌트 1

C의 limit 변경은 B와 별도다.

힌트 2

역변경의 범위를 필드별로 적는다.

풀이와 답 확인

  1. B의 효과는 feature를 켠 것이므로 역효과는 feature를 끄는 것이다.

  2. limit 5를 3으로 바꾸면 C의 별도 변경까지 취소한 다른 작업이다.

요구한 결과는 off/5다. 실제 충돌과 실행 영향은 추가 검토 대상이다.

흔한 오답에서 다시 생각하기

옛 상태 하나를 쓰면 특정 변경도 정확히 되돌아간다.

전체 상태 교체와 특정 변경 역효과는 범위가 다르다.

연습 3 · 직접 만들어 보기

릴리스 되돌림 검토 카드에 최소 네 연결을 설계하라. 서명과 배포를 실제 수행한 것은 아니다.

힌트 1

이름만 적으면 이동 뒤 의미가 바뀐다.

힌트 2

소스·산출물·검사·제공 관찰을 연결한다.

풀이와 답 확인

  1. 대상 소스 커밋 R과 지정 산출물 식별 hR 및 생성 입력을 기록한다.

  2. 검사 대상과 범위/미수행을 기록하고 실제 제공 산출물의 관찰을 그 식별에 연결한다.

소스, 지정 산출물, 검사 근거, 제공 관찰을 각각 연결한다. 해시 일치만으로 기능·보안을 인증하지 않는다.

흔한 오답에서 다시 생각하기

태그 이름 하나가 모든 연결을 대신한다.

이름은 포인터이며 산출물 생성과 실제 제공을 자동 증명하지 않는다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

두 부모인 병합 커밋 M의 되돌림을 한 부모의 단순 커밋과 같은 역변경이라 할 수 있나? 새 수치 예측 없이 필요한 조건을 적어라.

힌트 1

어느 부모와 비교한 변경인지 정해야 한다.

힌트 2

이력의 조상 관계는 되돌림 뒤에도 남는다.

풀이와 답 확인

  1. mainline으로 삼을 부모를 정해 그 부모와 비교한 역변경을 해석한다.

  2. 이후 병합이 가져올 새 변경 범위도 조상 관계와 되돌린 효과를 나누어 검토한다.

부모 선택과 후속 이력의 의미가 필요하다. 실제 merge revert를 실행하지 않았다.

흔한 오답에서 다시 생각하기

병합 되돌림은 부모가 하나인 변경과 언제나 같다.

부모별 차이가 서로 다를 수 있으므로 비교 기준이 없으면 역효과를 정의하지 못한다.

한 단계 더

세 버전 비교표에 삭제·이름 변경·기능 계약을 추가하자. 자동 도구의 충돌 없음과 사람의 기능 검토를 두 칸으로 기록한다. 서명 태그나 보호 규칙을 설계할 때도 실제 설정 여부를 관측과 분리한다.

코딩 규칙과 리뷰

정렬과 이름을 예쁘게 고치면 경계 조건 오류도 해결될까?

준비 개념과 학습 목표

준비 개념

  • 함수 계약

  • 조건문

  • 검증 입력

학습 목표

  • 기능 오류와 스타일 제안을 구별한다.

  • 검토 근거를 현재 변경 revision에 연결한다.

본체 한 줄만 읽은 승인으로 호출된 검사 함수까지 확인했을까?

자체 단일 스레드 예약 계약은 양의 정수 q만 받는다. 남은 수 remaining이 q 이상이면 remaining에서 q를 빼고 성공 번호 next를 하나 증가시켜 반환한다. 거절하면 두 상태를 모두 보존한다. 성공 번호는 정확 정수 모형이며 실제 유한 정수의 상한 처리는 별도다. 본체가 validate(q)를 호출할 때 검토자는 호출된 함수의 현재 뜻도 읽어야 한다.

revision H1의 validate는 q > 0이다. H2에서 도우미만 q >= 0으로 바뀌면 본체가 같아도 q = 0이 성공하여 remaining은 그대로인데 next가 증가한다. 0 요청 성공은 남은 수가 음수가 되지 않는 불변식만으로 발견하지 못한다. 실패의 상태 보존과 양수만 성공한다는 전체 계약까지 확인해야 한다.

검토 기록에는 H1에서 읽은 범위와 H2에서 달라진 도우미를 명시한다. 포맷 검사, 작은 종이 반례, 전체 변경 독립 검토, 실제 사용자 시험의 성격을 분리한다. 이 보강의 표는 직접 실행 출력이 아닌 손추적이다. 검토 지침을 특정 팀의 강제 규칙이나 모든 지역의 법적 요구로 일반화하지 않는다.

먼저 확인할 개념
  • 계약과 revision별 검토 범위

    도우미 변경과 본체 관찰을 연결한다.

  • 내용이 바뀌는 이력의 점

    같은 이름과 다른 현재 내용을 구별한다.

공동 규칙이 줄이는 비용

코딩 규칙은 이름·형식·주석 등의 일관성을 정해 팀이 코드를 읽는 비용을 줄인다. 규칙의 목적과 적용 범위를 합의하면 작성자마다 다른 취향을 다시 논쟁할 필요가 줄어든다. 의미 없는 긴 이름이나 과한 주석이 항상 더 좋다는 규칙은 아니다.

공식 스타일 규칙과 개인 선호를 구별한다. Google의 공개 리뷰 지침은 공식 스타일을 기준으로 보고 개인 선호를 Nit로 표시할 수 있다고 설명한다. 이는 해당 조직 지침이며 모든 프로젝트가 같은 승인 정책을 반드시 써야 한다는 법이나 표준은 아니다.

기능을 작은 반례로 검토하기

리뷰는 설계·기능·복잡도·테스트·이름·주석·문서와 주변 문맥을 함께 읽는 작업이다. 함수 계약이 금액이 100 이상이면 10을 뺀다고 정했다면 >100과 >=100은 다른 기능이다. 포맷 검사 통과는 이 차이를 검사하지 못한다.

경계 바로 아래·경계·바로 위 입력을 나란히 놓고 기대 결과와 코드 결과를 비교한다. 발견한 문제는 위치·조건·관측 또는 종이 추론·수정 방향을 구체적으로 적는다. 근거 없는 전면 재작성 요청보다 반례 하나가 기능 문제를 더 분명히 보여준다.

검토한 버전과 바뀐 버전

리뷰 기록은 어느 revision의 어떤 범위를 읽었는지 연결해야 한다. 검토 뒤 코드가 바뀌면 예전 승인이 새 변경까지 읽었다는 뜻이 아니다. 변경 영향에 맞춰 다시 검토하고 빌드·테스트 결과도 현재 변경과 연결한다.

자동 검사, 독립 사람 리뷰, 실제 사용자 실험은 서로 다른 증거다. 검토자가 전부 읽지 않은 범위는 그렇게 기록한다. 문서와 테스트 변경도 제품 행동에 영향을 줄 수 있으므로 코드 줄만 보고 전체 변경을 검토 완료했다고 단정하지 않는다.

int price(int total) {
    return total > 100 ? total - 10 : total;
}

중간 과정을 따라가는 예제

자체 계약은 음수가 아닌 정수 total에 대해 100 이상이면10을 빼고 그 미만이면 그대로 반환한다. 위 코드의 입력99/100/101 결과와 계약 결과를 비교하라. 음수 처리 정책은 이 함수의 전제 바깥이다.

  1. 99>100은 거짓이어서 코드99, 계약도99다.

  2. 100>100은 거짓이어서 코드100이지만 계약100−10=90이다. 경계에서 오류를 발견한다.

  3. 101>100은 참이어서 코드91, 계약도91이다.

  4. >를 >=로 바꾸면 이 세 입력의 계약 결과99/90/91을 만족한다. 세 점 검사만으로 모든 다른 요구를 증명하지는 않는다.

오류 반례 total=100: 기대90, 코드 예상100. 조건 >=100이 이 경계 계약에 맞는다.

조건을 바꾸어 비교하기

남은 수는 같지만 성공 번호가 다르다

초기 remaining = 3, next = 10에서 H1/H2의 q = 0을 비교하라.

  1. H1은 validate에서 거절해 두 상태를 보존한다.

  2. H2는 수량 3 >= 0도 참이라 성공 번호 10을 반환하고 next를 11로 바꾼다.

remaining은 두 경우 모두 3이지만 반환 판정과 next는 다르다.

비교할 점

한 상태 필드만 비교하면 실패 계약의 차이를 놓친다.

양수 통과도 성공을 보장하지 않는다

H1에서 q = 4를 요청하고 q = 2의 성공과 비교하라.

  1. 4는 양수지만 remaining 3보다 커 본체에서 거절한다.

  2. 2는 양수이며 수량 조건도 만족해 remaining 1, next 11이 된다.

validate와 수량 검사의 실패 위치가 다르며 거절은 두 상태를 보존한다.

연습 1 · 값과 상태 예측

  2. 둘째는 번호 11을 반환해 remaining 1, next 12가 되고 마지막은 부족 거절해 이를 보존한다.

연습 2 · 오류 찾아 고치기

테스트가 remaining >= 0만 확인하며 H2의 q = 0 성공을 허용했다. 더 강한 확인을 구성하라.

힌트 1

힌트 2

거절에는 반환과 두 상태를 함께 확인한다.

풀이와 답 확인

  1. q = 0에 거절을 기대하고 remaining 3, next 10의 보존을 확인한다.

  2. q = 2의 성공과 q = 4의 거절도 별도로 확인해 모든 요청을 거절하는 수정이 통과하지 않게 한다.

기능 반례와 정상 회귀를 함께 둔다. 실제 테스트 실행은 하지 않았다.

강한 테스트는 모든 요청이 실패하는지만 보면 된다.

정상 성공 계약을 없애는 수정도 검출해야 한다.

힌트 2

헤더를 먼저 준비하기만 하면 새 내용도 빌드에 반영될까?

자체 빌드 그래프에서 G는 생성 헤더를 만드는 2초 작업이고, G 뒤 A는 3초 컴파일, B는 5초 컴파일이다. A와 B 모두 뒤 L은 1초 연결이다. 작업 두 개를 동시에 수행할 수 있고 다른 비용이 없으면 G가 0…2초, A가 2…5초, B가 2…7초, L이 7…8초다. 한 작업만 가능하면 합계 11초다. 이는 실제 빌드 측정이 아니다.

GNU make의 normal prerequisite는 선행 순서와 변경 시 재빌드 관계를 함께 가진다. order-only는 순서는 보장하지만 그 대상의 시각이 바뀌었다는 이유만으로 산출물을 다시 만들지는 않는다. 출력 디렉터리는 생성이 선행돼야 하지만 내부 파일 추가마다 모든 객체를 다시 만들 필요가 없을 수 있다. 내용에 영향을 주는 헤더를 같은 방식으로 제외하면 낡은 객체를 재사용할 수 있다.

별도 작은 매크로 모형에서 헤더 h1은 K = 2, h2는 K = 3을 정하고 A의 관찰값은 2K다. A 소스가 같아도 결과는 4와 6으로 달라져야 한다. 캐시 키가 소스·도구·옵션만 포함하고 헤더를 빠뜨리면 h2에서도 옛 결과 4를 재사용할 수 있다. 기록된 입력의 동일성과 지정 산출물의 바이트 재현, 기능 정확성을 서로 다른 검토 질문으로 유지한다.

소스에서 산출물로 가는 단계

빌드는 소스와 도구·옵션·의존 파일을 사용해 목적 파일, 실행 파일, 패키지 같은 산출물을 만드는 과정이다. 단순 복사·생성 코드·컴파일·연결 등 여러 단계가 있다. 단계 사이 화살표는 선행 결과가 필요하다는 뜻으로 그린다.

A가 준비된 뒤 B와 C를 만들고 둘 다 준비된 뒤 D를 만드는 그래프는 독립 가지를 보여준다. 병렬 자원이 충분한 시간과 한 작업만 가능한 시간을 구별한다. 그래프만 보고 네트워크·캐시·자원 경쟁을 포함한 실측 시간을 주장하지 않는다.

요구 버전과 선택된 버전

의존성은 직접 사용하는 라이브러리뿐 아니라 그 라이브러리의 의존성도 포함한다. 요구 구간의 교집합을 만족하는 버전이 있어야 한 환경의 단일 선택이 가능하다. 선언 파일의 느슨한 구간과 실제 고정된 해석 결과를 구별한다.

버전이 맞아도 플랫폼, 선택 기능, ABI, 실행 데이터 등 다른 조건이 충돌할 수 있다. 고정 목록은 중요한 기록이지만 모든 호환성을 증명하지 않는다. 빌드 도구·컴파일 옵션·환경 변수도 입력인데 기록에서 빼면 원인을 놓치기 쉽다.

재현 가능한 바이트의 조건

Reproducible Builds의 정의는 같은 소스·빌드 환경·지침으로 다른 사람이 지정 산출물을 바이트 단위로 동일하게 만들 수 있다는 것이다. 어떤 산출물을 비교하는지 먼저 정해야 한다. 모든 로그 파일까지 무조건 동일해야 한다는 뜻은 아니다.

동일 도구 버전만으로 충분하지 않다. 자체 산출물에 현재 시각을 넣으면 같은 소스도 다른 바이트가 된다. 무작위 값·절대 경로 같은 입력도 영향을 줄 수 있다. 해시 비교는 바이트 결과를 연결하는 증거지만 프로그램이 올바르다는 기능 증명은 아니다.

연습 1 · 값과 상태 예측

G의 내용 변경은 A와 B 모두에 영향을 준다. 새 관찰 구간의 시각 0에서 G를 다시 만드는 작업부터 시작할 때, 두 작업 자원과 단일 자원의 완료 시간을 구하라.

힌트 1

힌트 2

풀이와 답 확인

  1. 두 작업 자원에서 G가 0…2, A/B가 2…5와 2…7, L이 7…8이다.

  2. 단일 자원에서는 의존 순서로 모든 작업을 수행해 2 + 3 + 5 + 1 = 11초다.

8초 대 11초이며 네 작업을 모두 재실행한다.

  2. 캐시 키에도 실제 사용한 헤더 내용 등 관련 입력을 포함하고 누락된 옛 결과를 정상으로 승인하지 않는다.

동일한 지정 산출물 바이트를 두 번 얻었다고 가정한다. 헤더 h1을 양쪽에서 실수로 사용했고 요구는 h2였다. 재현과 요구 만족을 판단하라.

A(off,3) → B(on,3) → C(on,5)에서 B 효과만 역변경한 R을 만들고 옛 B 재병합과 새 D(R의 자식, on/5) 병합을 비교한다. 예약 H2의 초기 remaining = 3, next = 10에서 q = 0,2,2를 순서대로 처리하고 H1의 양수 계약에 대한 반례를 적는다. 빌드 G2 → A3/B5 → L1은 두 작업 자원으로 새 시각 0에서 수행한다. 별도 h 변경은 A만 영향 주고 G/B 캐시가 유효하다. 전체 처음 시간과 h 변경 재실행 시간을 계산하고, h1의 K = 2 결과를 h2의 K = 3에서도 재사용한 키의 결함 및 바이트 비교 미수행을 기록하라.

힌트 1

되돌린 상태와 조상을 나누고 예약의 성공 번호까지 관찰한다.

힌트 2

빌드의 순서·무효화·재현 비교를 별개 조건으로 계산한다.

풀이와 답 확인

  1. R은 off/5이며 옛 B는 이미 조상이라 새 기능을 가져오지 않는다. 새 D로 기본 fast-forward하면 on/5다. 실제 제공 상태는 별도 확인한다.

  2. H2는 0 요청에 번호 10을 반환해 next 11이 되고 다음 2 요청에 번호 11을 반환해 remaining 1, next 12가 된다. 마지막 2는 부족 거절해 상태를 보존한다. 0 성공이 양수만 성공한다는 계약의 반례다.

  3. 전체 처음 병렬 시간은 2 + max(3,5) + 1 = 8초다. h만 바뀌고 다른 결과가 유효하면 A/L의 재실행은 3 + 1 = 4초다.

  4. h2의 기대 값은 6이지만 헤더를 제외한 키는 옛 값 4를 재사용할 수 있다. 키의 실제 입력 범위를 수정하고 실제 독립 빌드/바이트 비교는 미수행으로 둔다.

이력 포함, 검토 대상 현재 의미, 빌드 입력과 결과를 각 장부에서 연결한다. 실제 Git·서비스·예약·make·빌드·바이트 비교·학생 수행은 하지 않았다.

해결한 뒤 점검할 것

  • off/5와 B의 조상 관계가 동시에 성립함을 설명한다.

  • H2의 세 요청에서 판정·remaining·next를 모두 추적한다.

  • 새 구간 8초와 선택 재실행 4초를 같은 기준으로 계산한다.

  • 헤더 누락 반례 4 대 6과 normal/order-only의 의미를 구별한다.

  • 검토 계획과 실제 빌드·제공·학습자 수행을 구별한다.
