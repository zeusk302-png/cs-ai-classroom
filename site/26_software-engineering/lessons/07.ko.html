소단원 7.1

책임 분배와 의존성

점수를 계산하는 객체가 화면 색과 파일 이름까지 알아야 할까?

준비 개념과 학습 목표

준비 개념

  • 책임은 객체가 알고 수행해야 할 일이다.

  • 의존성은 다른 요소의 계약이나 구현에 기대는 관계다.

학습 목표

  • 책임을 문장으로 나눈다.

  • 호출 방향과 계약을 적는다.

  • 공개 배열로 불변식이 깨지는 반례를 찾는다.

점수가 모두 허용 범위 안이면 평균의 캐시도 올바를까?

자체 ScoreBook은 점수 목록과 합계 sum을 함께 가진다. 표현 불변식은 각 점수가 정수 0…100이라는 조건과 sum이 목록의 합이라는 관계를 모두 포함한다. 초기 목록 [60,80]과 sum = 140에서 외부가 첫 점수를 70으로 바꾸면 두 점수는 여전히 유효하지만 합은 150으로 바뀐다. 캐시 140을 그대로 쓰는 평균은 70이고 올바른 평균은 75다.

책임을 분리한다는 것은 검사의 주인도 분명하게 둔다는 뜻이다. replace(index,score)는 위치와 점수를 먼저 확인하고 새 목록과 새 합계의 계산을 준비한 뒤 함께 반영한다는 자체 단일 스레드 계약을 갖는다. 실패에서는 목록과 sum 모두 보존한다. 실제 원자적 구현이나 예외 안전성을 수행한 증거는 아니며, 어떤 구현이 계약을 만족할지는 별도 검토한다.

조회는 불변 정수 값의 독립 목록을 반환한다고 정한다. 반환 목록을 바꾸어도 내부 목록을 바꾸지 않는다. 여기서는 점수가 정수 값이라 원소 내부의 가변 객체 공유가 없다. 점수 대신 가변 Record를 반환하는 변형이라면 바깥 목록 복사만으로는 충분하지 않다. View와 Repository는 표현 필드를 직접 고치지 않고 좁은 계산·조회 계약에 의존한다.

먼저 확인할 개념
  • 점수 불변식과 책임의 주인

    단일 점수의 범위에서 목록·합계의 관계로 검사를 확장한다.

  • 구조 변경의 관찰 보존

    새 캐시를 추가해도 평균과 실패 상태를 보존해야 한다.

데이터와 규칙의 주인

자체 성적 연습에서 ScoreBook은 0..100 점수를 보관하고 평균을 구한다. GradeView는 평균을 받아 표시한다. 파일 입출력은 ScoreRepository에 둔다. 이 분리는 가능한 한 설계이며 모든 프로그램의 유일 정답이 아니다.

책임 이름만 나눠도 내부 배열을 밖에 그대로 공개하면 외부가 -10을 넣어 규칙을 우회할 수 있다. addScore가 범위를 검사하고 조회가 수정 권한을 주지 않는 계약인지 확인한다. 객체 수보다 규칙을 지킬 수 있는 협력이 중요하다.

누가 누구를 아는가

View가 ScoreBook의 average() 계약을 호출한다면 View→ScoreBook 의존 화살표를 그린다. 저장 함수가 클래스 내부 필드 이름과 화면 문구까지 읽으면 구현 변경의 영향 범위가 커진다. 인터페이스는 필요한 요청을 좁히는 방법이다.

인터페이스 사용만으로 모든 결합이 없어지지 않는다. 반환 단위가 점수인지 비율인지, 빈 목록은 어떤 결과인지도 계약에 포함한다. 서로 다른 클래스가 이름만 같은 메서드를 가져도 의미가 다르면 안전한 교체가 아니다.

변경 사례로 경계를 평가하기

표시를 80.0에서 80점으로 바꾸는 요구는 View 책임이다. 범위 상한을 바꾸는 요구는 ScoreBook 계약에 영향을 준다. 저장 형식을 바꾸면 Repository를 검토한다. 실제 의존 관계가 이 범위를 지키는지 확인한다.

과도하게 쪼개면 작은 변경을 따라 여러 파일을 읽어야 한다. 초보자는 먼저 세 책임과 한 호출 경로를 종이에 적자. 아래는 가상 설계이며 성능·개발 시간·실제 협업 효과를 측정한 결과가 아니다.

거절·두 상태 보존

둘째와 셋째 행은 초기 상태에서 각각 시작한다. 마지막 행은 셋째 뒤의 요청이다. 범위와 합계 관계를 별도 기준으로 읽고 평균은 실제 실행 출력이 아닌 계약의 계산이다.

중간 과정을 따라가는 예제

점수60,80,100을 저장해 평균을 표시한다. 책임과 결과를 구하라.

  1. ScoreBook이 세 유효 점수를 보관한다.

  2. 합계240, 개수3, 평균240/3=80이다.

  3. View는 계약 결과80을 80점으로 표시한다.

  4. Repository는 저장/읽기 책임이며 표시 문구를 결정하지 않는다.

평균80, 계산은 Book·문구는 View·저장은 Repository다.

조건을 바꾸어 비교하기

범위가 맞아도 관계가 틀린다

초기 [60,80], sum = 140의 공유 목록 첫 값만 70으로 바꾼다. 범위와 평균을 비교하라.

  1. 70과 80은 모두 범위 안이다.

  2. 실제 합은 150인데 캐시 합은 140이다.

범위는 맞고 sum 관계는 틀리다. 캐시 평균 70 대 실제 평균 75다.

비교할 점

한 불변식의 통과로 다른 관계까지 통과했다고 선언하지 않는다.

성공과 실패의 두 필드

초기 상태에서 replace(0,70), replace(1,101)을 순서대로 요청한다.

  1. 첫 요청은 새 합 140−60+70=150을 목록 변경과 함께 반영한다.

  2. 둘째의 101은 범위 밖이라 변경 전에 거절한다.

최종 [70,80], sum = 150, 평균 75다.

비교할 점

실패에서 점수만 보존하고 sum을 먼저 늘리는 구현은 같은 계약이 아니다.

소단원 7.2

대표 설계 패턴

같은 정렬 요청에 서로 다른 알고리즘을 교체하려면 어떻게 할까?

준비 개념과 학습 목표

준비 개념

  • 패턴은 반복 문제의 의도·협력·결과를 설명한 설계 경험이다.

  • Strategy는 알고리즘 교체, Observer는 변경 알림, Adapter는 인터페이스 연결이라는 서로 다른 목적을 갖는다.

학습 목표

  • 의도에 맞는 패턴을 고른다.

  • 세 패턴의 협력 경로를 추적한다.

  • 패턴이 해결하지 않는 조건을 명시한다.

알림 중 새 변경이 일어나면 각 관찰자는 어느 버전을 보았을까?

Observer의 관계와 전달 계약을 나눈다. 자체 Book의 첫 변경은 값 70과 revision 1을 확정하고 등록 순서 [A,B]를 복사한다. A의 알림 처리 중 새 변경 값 80이 들어온다. 즉시 재진입 전달을 허용하면 revision 2의 A,B 전달이 revision 1의 B보다 먼저 일어날 수 있다. B의 이벤트 순서가 2,1로 뒤집힌다.

별도 안전 정책 Q는 알림 중 들어온 변경 요청을 FIFO 큐에 넣고 현재 알림 묶음이 끝난 뒤 처리한다. 이벤트는 확정 당시의 불변 (revision,value) 값을 담는다. 처음 A1, B1을 전달한 뒤 둘째 변경을 반영하여 A2, B2를 전달한다. 각 A는 revision 1에서만 새 요청 하나를 만든다고 정해 무한 생성은 배제한다. 단일 스레드라는 조건도 동시성 안전의 증명으로 확대하지 않는다.

등록 목록은 변경 시작 때 복사하고 관찰자 실패는 기록하되 나머지를 계속 전달한다는 자체 정책을 둔다. A가 전달 중 B를 해제해도 현재 복사 목록의 B는 호출하고 다음 변경부터 제외한다. Strategy의 계산 교체나 Adapter의 단위 연결은 이 전달 규약을 자동 정하지 않는다. 이름보다 버전·등록·실패·재진입의 관찰을 설계한다.

먼저 확인할 개념
  • Observer의 등록·순서·재진입 조건

    알림 관계와 전달 시점의 별도 약속을 읽는다.

  • 상태를 변경하는 책임

    Book이 변경을 확정하고 관찰자는 전달된 값을 소비하도록 나눈다.

Strategy로 바뀌는 규칙을 분리하기

자체 배송비 예에서 주문 객체는 quote(weight)를 제공하는 전략에 계산을 맡긴다. 일반 전략은1000+200w, 빠른 전략은2000+300w다. w는 양의 정수 kg이며 금액 단위는 원이라는 계약을 정한다.

고객이 전략을 선택하면 주문 객체의 나머지 동작을 유지하면서 계산 규칙을 교체할 수 있다. 입력 범위·반올림·실패 조건이 다르면 공통 계약을 먼저 정해야 한다. 패턴 이름이 계약 차이를 자동 해결하지 않는다.

Observer는 알림의 책임을 나누기

점수가 바뀌면 Book이 등록된 관찰자에게 변경을 알리고 View가 다시 조회하는 설계를 생각하자. 누가 변경을 소유하고 누가 화면을 갱신하는지 분리한다. 등록·해제와 같은 이벤트의 중복 처리 정책도 적는다.

자동으로 모든 UI가 최신이거나 스레드 안전하다는 보장은 없다. 관찰자 호출 순서·실패 처리·재진입은 구현 계약이다. 이 예는 단일 스레드에서 등록 순서로 각 관찰자를 한 번 호출하는 자체 모형이다.

Adapter는 기존 요청을 맞추기

새 계약 readCelsius()에 기존 센서 readFahrenheit()를 연결하려면 변환 책임을 어댑터에 둔다. C=(F−32)×5/9이고 실제 센서와 네트워크는 이 활동에서 사용하지 않는다. 단위와 오류도 함께 연결해야 한다.

이름만 바꿔서 화씨 값을 그대로 섭씨로 반환하면 계약 위반이다. Strategy의 알고리즘 교체와 Adapter의 계약 연결, Observer의 알림은 의도가 다르다. 하나의 시스템에서 함께 쓸 수도 있지만 문제마다 필요한 이유를 설명한다.

A1이 변경 요청 하나를 발생시키는 독립 두 정책
정책전달 순서B가 받은 revision마지막 Book

즉시 재진입

2,1

revision 2 / 값 80

Q: 현재 묶음 뒤 FIFO

이벤트는 revision과 값의 불변 복사다. 호출 중 현재 Book을 다시 읽는 값과 전달 이벤트 값을 같은 것으로 보지 않는다. A1만 요청을 생성하고 A2는 생성하지 않는 유한 모형이다.

  2. B1은 뒤에 도착했어도 revision 1의 값 70이다.

소단원 7.3

과잉 추상화와 대안

한 줄 계산을 위해 여덟 클래스를 만들어야 할까?

준비 개념과 학습 목표

준비 개념

  • 추상화는 중요한 계약을 남기고 세부를 숨긴다.

  • 추가 계층은 교체 가능성과 이해·유지 비용을 함께 만든다.

학습 목표

  • 실제 변경 요구를 찾는다.

  • 함수·조건문·패턴 대안을 비교한다.

  • 리팩터링의 행동 보존 범위를 명시한다.

객체를 함수로 바꾸면서 상태를 지우면 같은 전략일까?

새 가상 요금 전략은 호출마다 쓴 쿠폰 수 c를 갖는다. 첫 두 유효 요청에 500원, 이후에는 1000원을 반환하고 성공한 요청마다 c를 늘린다. 입력 w는 양의 정수이고 잘못된 입력에서는 요금 계산과 c 증가를 하지 않는다. w가 같아도 이 전략은 호출 이력에 따라 달라진다. 같은 수식만 옮기는 순수 함수와 계약이 다르다.

객체 대신 함수를 전달하는 설계도 상태를 유지할 수 있다. 새 함수가 같은 쿠폰 상태를 캡처하고 같은 순서로 검사를 수행하면 객체 여부만으로 결과가 달라지지 않는다. 반대로 함수가 매번 새 c = 0을 만들면 세 요청 모두 500원이 된다. 호출자 두 명이 상태를 공유하는지 각자 갖는지와 리셋 시점도 외부 관찰이다.

현재 요구가 첫 두 쿠폰의 공동 사용이라면 공유 상태의 주인과 갱신 계약이 필요하다. 순수 요금 하나만 필요할 때 추가 계층이 주는 이점은 별도다. 객체 개수나 패턴 수로 품질을 판정하지 않고 실제 변경 이유와 상태·오류·수명 장부를 비교한다. 새 구현의 메모리 비용·속도·개발 시간은 측정하지 않았다.

먼저 확인할 개념
  • 함수와 전략 객체의 대안

    동일 공식 외에 상태·수명·오류의 보존 조건을 검토한다.

  • Strategy의 공통 요청 계약

    교체 가능한 요청이 성공·거절과 상태 효과까지 포함하는지 확인한다.

변경 이유 없이 계층을 늘리지 않기

단일 요금1000+200w만 있고 교체 요구가 없다면 한 함수로 시작할 수 있다. 앞으로 모든 운송수단이 나올 것이라는 추측만으로 여러 추상 팩토리를 만드는 것은 비용이다. 실제 변경 사례와 테스트 가능한 계약을 먼저 적는다.

패턴 원문도 유연성에 필요한 추가 간접 계층이 복잡도와 성능 비용을 만들 수 있다고 설명한다. 이는 패턴을 절대 쓰지 말라는 뜻이 아니다. 현재 요구·예상 변경의 근거·언어 기능을 비교하라는 뜻이다.

간단한 대안도 계약으로 평가하기

종류가 일반과 빠른 둘뿐이면 작은 조건문이 읽기 쉬울 수 있다. 종류가 자주 늘고 독립적인 상태·협업이 생기면 Strategy가 유리할 수 있다. 코드 줄 수나 패턴 수 하나만으로 결론내리지 않는다.

함수 전달은 계산을 교체할 수 있지만 필요한 수명·상태·복수 연산 계약이 있으면 별도 설계가 필요하다. 공통 인터페이스를 너무 넓게 만들면 각 구현이 쓸모없는 연산까지 제공해야 한다. 현재 사용 경로를 추적해서 필요한 최소 요청을 찾는다.

변경 전후의 관찰 결과 확인하기

두 요금 계산을 함수에서 전략 객체로 옮길 때 유효 입력의 요금·오류·부작용 약속을 보존해야 한다. 구현 구조를 바꾸면서 가격 정책까지 몰래 바꾸면 행동 보존 리팩터링이라고 부를 수 없다.

다른 문제에 적용하기

서로 독립인 세 모형을 검토하라. Book의 초기 목록 [60,80]과 sum = 140에서 replace(0,70), replace(1,101)을 순서대로 요청한다. Observer Q는 첫 변경 value = 70/revision = 1의 [A,B] 복사 목록을 가진다. A1은 B를 해제하고 value = 80의 새 요청 하나를 큐에 넣으며 A2는 아무 요청도 하지 않는다. 호출 순서와 마지막 상태를 구하라. 쿠폰 전략은 초기 c = 0에서 두 호출자가 A,B,A,B 순서로 유효 요청을 보내며 같은 상태를 공유한다. 요금 합과 각자 상태를 가진 변형의 차이를 적어라.

힌트 1

실패 보존은 목록과 sum을 함께 확인하며 해제는 다음 복사 목록부터 적용한다.

힌트 2

FIFO 묶음 종료와 상태 공유의 범위를 별도 장부로 추적한다.

풀이와 답 확인

  1. Book은 첫 요청 후 [70,80], sum = 150이고 둘째는 거절해 같은 상태와 평균 75를 보존한다.

  2. Q는 A1,B1을 전달한 뒤 둘째 변경을 확정하고 A2만 전달한다. 마지막 Book은 revision 2/값 80이고 B는 revision 1만 받는다.

  3. 공유 쿠폰은 500,500,1000,1000으로 합계 3000원, 최종 c = 4다.

  4. 각자 쿠폰은 네 요청 모두 500원으로 합계 2000원이며 A와 B의 c는 각각 2다. 공유 변경은 단순 구조 리팩터링과 다르다.

불변식 관계·알림 시점·상태 소유라는 다른 경계를 나눠 판단한다. 실제 객체·UI·스레드·큐·성능·학생 실행은 미수행이다.

해결한 뒤 점검할 것

  • Book의 실패에서 두 표현 필드를 모두 보존한다.

  • 현재 복사 목록과 다음 구독 목록을 구별해 세 호출을 기록한다.

  • Q의 FIFO와 revision별 불변 값을 구별한다.

  • 공유/각자 쿠폰의 요금과 성공 상태를 각각 계산한다.
