소단원 13.1

위협 모델과 보안 요구

수정 버튼을 감추면 다른 학생의 노트를 수정할 수 없을까?

준비 개념과 학습 목표

준비 개념

  • 클라이언트와 서버

  • 인증과 권한

  • 요구사항과 시험

학습 목표

  • 자산과 신뢰 경계를 표시한다.

  • 위협을 검증 가능한 요구로 바꾼다.

  • 모형의 가정과 미검증 범위를 구별한다.

노트 내용이 그대로여도 권한이 바뀌면 이전 허용을 재사용할 수 있는가?

새 가상 노트 N은 소유자 A, 내용 v1, 공개 여부 public이다. 읽기는 공개이거나 현재 소유자일 때 허용하고, 수정은 현재 소유자에게만 허용한다. 확인된 사용자는 서버에서 얻으며 요청 본문의 owner 값은 이 판단에 쓰지 않는다. 삭제 규칙은 없으므로 기본 거절한다. 이는 앞 본문의 단일 요청 정책을 시간에 따라 바뀌는 자산으로 확장한 설계다.

시각 0에서 B의 공개 읽기를 허용하고 답을 캐시했다. 시각 1에서 A가 N을 private으로 바꾼다. 내용 v1이 같아도 시각 2의 B 읽기는 거절해야 한다. 이 과제는 캐시 hit도 새 읽기 요청이며 현재 읽기 정책을 적용한다는 계약이다. 콘텐츠 버전만으로 캐시 안전을 판정하면 권한 변경을 놓친다.

또 다른 경계는 권한 검사와 수정 사이의 소유자 변경이다. 현재 소유자가 A인지 검사한 뒤 소유권이 B로 이동하면 오래된 허용으로 쓰지 않도록 검사와 갱신을 하나의 원자적 조건부 작업으로 묶는 설계를 요구한다. 이 설계가 실제 서버에 구현됐다는 뜻은 아니다. 동시성 제어·캐시 무효화·우회 경로는 구현과 별도 시험이 필요하다.

먼저 확인할 개념
  • 사용자·객체·행동별 권한

    인증 결과와 저장된 자산 속성을 근거로 현재 요청을 평가한다.

  • 오래된 상태와 사용자 영향

    자료를 반환할 수 있는 상태와 사용자에게 허용된 상태를 나눈다.

무엇을 보호하고 누구를 신뢰할까

위협 모델은 서비스 구조, 지킬 자산, 잘못될 수 있는 상황, 대응과 확인 방법을 함께 기록한다. 학교 노트 서비스에서는 노트의 내용과 소유자 정보가 자산이다. 읽기 공개와 수정 공개는 서로 다른 요구다.

브라우저에서 온 소유자 번호나 역할을 그대로 믿으면 사용자가 바꾼 입력이 판단 근거가 된다. 서버가 확인한 사용자와 저장된 노트 소유자를 비교하는 경계를 그려보자. 모든 위협을 한 번에 찾았다고 단정하지 않고 기능 변경 때 가정을 다시 확인한다.

인증된 사용자도 권한이 다르다

인증은 누구인지 확인하는 과정이고 인가는 특정 자료에 특정 행동을 허용할지 결정하는 과정이다. 로그인한 학생이 있다는 사실만으로 모든 노트의 수정 권한이 생기지 않는다. 명시적으로 허용한 규칙이 없으면 거절하는 정책을 정한다.

화면의 숨김 버튼은 탐색을 도와도 서버의 권한 검사를 대신하지 못한다. 자체 요구는 '수정 요청마다 서버에서 로그인 사용자와 대상 노트 소유자를 비교하고 다르면 내용을 바꾸지 않는다'다. 수정과 삭제 같은 각 경로에 적용 여부를 확인한다.

좋은 요구는 반례로 점검할 수 있다

시험 표에는 요청자, 대상, 행동, 기대 결과, 실제 결과를 따로 적는다. 자기 노트 수정 허용만 시험하면 다른 사람 노트 수정 거절을 빠뜨릴 수 있다. 거절 때 원래 자료가 그대로인지도 수용 조건에 넣는다.

아래 활동은 가상 정책을 종이에 평가한다. 실제 사이트에 요청을 보내거나 침투 시험을 하는 것이 아니다. 이 표를 맞혔다고 서비스가 안전하다고 인증하지 않는다. 로그에는 원인 조사에 필요한 식별 정보를 남기되 노트의 비공개 본문 전체를 무조건 복사하지 않는다.

중간 과정을 따라가는 예제

자체 서비스 정책은 공개 노트 읽기는 누구나 허용, 수정은 로그인한 소유자만 허용이다. 노트 N의 소유자는 A다. 익명 읽기, A 수정, B 수정의 기대 결과를 구하라.

  1. 익명 읽기는 공개 읽기 정책에 의해 허용한다.

  2. A 수정은 로그인과 소유자 일치가 모두 참이므로 허용한다.

  3. B 수정은 로그인했어도 소유자가 달라 거절하고 N의 내용을 유지한다.

허용·허용·거절이다. 화면 버튼 표시 여부는 이 판정의 근거가 아니다. 실제 권한 검사는 수행하지 않았다.

조건을 바꾸어 비교하기

내용 버전이 같아도 공개 권한은 같지 않다

B가 시각 0의 응답을 캐시했고 시각 2에 같은 주소를 읽는다. 콘텐츠 v1만 검사하는 캐시와 현재 권한 검사 뒤 응답하는 캐시를 비교하라.

  1. v1 일치는 내용 변경 여부만 말한다. 현재 public은 거짓이고 B는 소유자 A와 다르다.

  2. 현재 권한을 검사하면 B 요청은 거절하고 비공개 내용을 반환하지 않는다.

권한 변경을 반영하지 않는 캐시 경로는 정책 위반이다. 이미 합법적으로 받은 과거 사본까지 원격 삭제했다는 결론은 아니다.

비교할 점

과거 사본 보유와 서버의 새 응답 허용을 구별한다.

검사와 사용 사이의 소유권 변경

A 수정의 검사 때 owner=A다. 검사 뒤 owner=B로 바뀌고 그 다음 내용 v2를 저장하려 한다. 정책은 저장 순간에도 현재 소유자 일치를 요구한다.

  1. 분리 검사는 옛 참을 갖고 있어 v2를 잘못 저장할 수 있다.

  2. 원자 작업의 조건 owner=A를 저장 순간 다시 평가하면 거짓이므로 v1을 유지한다.

이 가상 일정에서는 갱신 거절과 v1 보존이 수용 조건이다.

비교할 점

매 요청 검사만 언급하고 검사/변경의 일관성 경계를 생략하는 설계를 보완한다.

종이와 본문으로 직접 해보기

A가 보낸 요청 본문에 owner='B'가 있고 대상 N의 저장된 소유자는 A다. 서버가 요청의 owner만 믿어야 할까? 정책에 삭제 규칙을 추가하지 않았다면 B 삭제 요청은 어떻게 처리할까?

힌트 보기

서버가 확인한 사용자, 저장된 소유자, 명시적인 행동 허용 규칙을 각각 찾아보자.

풀이 보기

요청의 owner를 권한 근거로 믿지 않는다. 저장된 소유자와 확인된 사용자로 평가한다. 삭제는 명시적 허용 규칙이 없으므로 기본 거절하며 새 기능을 만들 때 별도 요구와 시험을 추가한다.

오해와 반례

로그인한 사람은 서비스의 모든 자료를 수정해도 된다.

인증과 인가는 다르다. B는 로그인했어도 A의 노트를 수정할 권한이 없다. 객체별 행동 권한을 서버에서 검증해야 한다.

연습 1 · 값과 상태 예측

시각 2의 A 읽기, B 읽기, B가 owner=A를 본문에 넣은 수정, A 삭제의 결과를 이름별로 적어라.

힌트 1

읽기와 수정 규칙은 다르다.

힌트 2

본문의 owner와 정의하지 않은 행동은 허용 근거가 아니다.

풀이와 답 확인

  1. A 읽기는 현재 소유자라 허용, B 읽기는 private이므로 거절이다.

  2. B 수정은 확인된 B가 소유자와 달라 거절하고 A 삭제는 규칙이 없어 거절한다.

허용되는 것은 A 읽기 하나다. 거절된 요청은 내용과 소유자를 바꾸지 않는다.

흔한 오답에서 다시 생각하기

A가 소유자이므로 모든 행동을 허용한다.

허용은 행동별 명시 규칙에 따르며 삭제 규칙을 자동 생성하지 않는다.

연습 2 · 오류 찾아 고치기

비공개 노트의 본문을 권한 검사 전에 로그에 복사하고 응답만 거절했다. 보호 자산이 로그까지 포함된다면 무엇을 고칠까?

힌트 1

거절 응답은 이미 발생한 부작용을 되돌리지 않는다.

힌트 2

조사에 필요한 요청 식별과 비공개 본문을 구별한다.

풀이와 답 확인

  1. 권한 검사 전 비공개 전체 본문 복사를 제거하고 최소 조사 정보만 기록하는 요구를 둔다.

  2. 로그 접근 권한·보존·삭제와 실제 기록 경로도 별도 시험한다.

응답 거절과 민감 본문 유출 방지는 서로 다른 수용 조건이다.

흔한 오답에서 다시 생각하기

사용자에게 거절했으므로 로그 내용은 안전하다.

응답 경로 밖 저장도 같은 보호 자산을 복제할 수 있다.

연습 3 · 직접 만들어 보기

현재 owner와 요청자 일치를 원자적으로 확인해 내용을 바꾸는 종이 작업의 성공/실패 사후 조건을 써라.

힌트 1

검사와 변경 사이에 다른 소유권 변경을 끼우지 않는다.

힌트 2

실패 때 내용뿐 아니라 owner도 보존한다.

풀이와 답 확인

  1. 성공은 현재 owner=확인된 요청자일 때만 새 내용 저장이다.

  2. 불일치는 저장하지 않고 이전 내용과 owner를 그대로 둔다.

원자 경계를 명시하고 허용된 관리 소유권 변경과 노트 수정 작업을 분리한다.

흔한 오답에서 다시 생각하기

검사를 한 번 했으면 앞으로의 모든 요청도 허용한다.

허용 판단의 상태와 사건 시점이 달라진다.

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

힌트 2

과제에 원격 사본 회수 기능이 있는가?

풀이와 답 확인

  2. B의 과거 사본 삭제를 수행하는 기능은 정의하거나 실행하지 않았다.

접근 철회와 기존 사본 회수를 같은 보증으로 적지 않는다.

보호 경계 밖에 이미 전달된 자료의 수명은 별도 통제가 필요하다.

시작하지 못한 요청을 제외하면 지연 목표를 만족했다고 말할 수 있는가?

새 유지 구간은 10초이고 시작 예정 요청은 100개다. 발생기 제약으로 실제 시작은 80개이며 20개는 시작되지 않았다. 시작한 80개는 성공 76개와 timeout 4개다. 예정 수, 시작 수, 성공 수는 서로 다른 분모다. timeout 기준은 500ms이며 timeout은 실제 완료 응답을 관측하지 못한 상태다.

성공 76개의 가상 지연은 50ms 72개와 300ms 4개다. 성공 요청만 nearest-rank p95를 계산하면 ceil(0.95×76)=73번째인 300ms다. timeout에 가상 완료 시각을 붙여 전체 실제 지연처럼 보고하면 안 된다. 대신 시작부터 400ms 안에 성공했다는 별도 목표는 76/80으로 판단할 수 있다.

비용 모형도 별도다. 서버가 한 초에 제공할 수 있는 CPU 예산을 1000ms라고 가정하고 읽기 한 건은 1ms, 저장 한 건은 9ms가 필요하다고 정한다. 같은 초당 요청 수라도 구성 비율에 따라 CPU 요구량이 다르다. 이 표는 용량의 필요 조건을 계산하며 실제 지연·큐·처리율을 측정하지 않는다.

먼저 확인할 개념
  • 목표의 분모와 지연 순위

    성공 응답·실패·미시작 요청을 각각의 계약으로 평가한다.

  • 실패 관찰과 실제 상태

    timeout이 완료된 실패 응답이나 서버 부작용 부재인지 구별한다.

어떤 사용을 얼마나 오래 흉내 낼까

부하 시험은 사용자 행동과 요청량을 정한 환경에서 재현해 응답과 자원 사용을 확인하는 활동이다. 동시 사용자 수와 초당 요청 수는 같은 숫자가 아니다. 사용자가 생각하는 시간, 여러 요청, 응답을 기다리는 방식이 요청량에 영향을 준다.

읽기만 하는 시험과 읽기·저장·검색이 섞인 시험은 비용이 다를 수 있다. 버전, 자료 크기, 캐시 상태, 요청 종류의 비율, 증가 구간과 유지 구간을 기록한다. 평균적인 부하와 그보다 높은 부하에서 한계를 보는 시험도 구분한다.

목표는 측정 규칙까지 포함한다

자체 계약을 '유지 구간에서 초당 30개 요청을 시작하고 실패율 1% 이하'로 정했다고 하자. 실패율의 분모는 그 구간에서 시작한 전체 요청이며 시간 초과를 실패에 포함한다. 실패 요청을 표에서 지우면 좋은 결과처럼 보일 수 있다.

응답시간은 시작과 끝의 정의, 대상 요청, 시간 초과 처리, 백분위 방법을 정한다. 여기서는 별도 가상 성공 요청 20개의 nearest-rank 방식으로 p95를 계산한다. 정렬 후 ceil(0.95×20)=19번째를 택한다. 이 방법을 모든 도구의 기본 보간 방식으로 단정하지 않는다.

환경과 부하 발생기도 결과에 영향을 준다

실제 시험에서는 부하 발생기가 목표 요청량을 만들었는지 확인해야 한다. 요청을 기다린 뒤 다음 것을 만드는 방식은 서비스가 느려질수록 유입도 줄어들 수 있다. 정해진 시작률을 의도해도 자원이 부족하면 실행하지 못한 작업이 생길 수 있다.

증가 구간과 안정 유지 구간을 섞어 하나의 평균으로 보고하지 않는다. 자원 사용, 실패, 긴 응답, 실제 시작률을 함께 본다. 아래 값은 설명을 위해 만든 표이며 k6나 서비스에 부하를 발생시키지 않았다.

중간 과정을 따라가는 예제

가상 유지 구간 10초에 요청 300개를 시작하고 성공 294개, 실패 6개다. 실패 목표는 1% 이하이다. 별도 성공 응답 20개 표는 100ms가 18개, 300ms가 1개, 900ms가 1개다. nearest-rank p95 목표는 250ms 이하이다.

  1. 시작률은 300/10 = 초당 30개 요청, 성공 처리율은 294/10 = 초당 29.4개 요청이다. 실패율은 6/300 = 2%다.

  2. 별도 지연 표의 평균은 (18×100+300+900)/20=150ms다.

  3. 정렬한 19번째는 300ms, 20번째는 900ms다. p95 = 300ms, p99 = 900ms이며 두 목표를 각각 판단한다.

실패율은 2% > 1%, 별도 표 p95는 300ms > 250ms로 둘 다 불충족이다. 평균 150ms만으로 통과시키지 않는다. 20개 표는 성공 요청 294개 전체의 측정 결과가 아니다.

조건을 바꾸어 비교하기

같은 결과에 서로 다른 성공률이 붙는다

성공 지연 p95, 시작 요청 중 400ms 안 성공한 비율, 예정 요청 중 같은 조건을 만족한 비율을 구하라.

  1. 성공 표 순위 73은 300ms다. 모든 성공 76개는 400ms 안이다.

  2. 시작 기준은 76/80=95%, 예정 기준은 76/100=76%다.

성공 p95가 좋아도 예정 부하 실현과 전체 사용자 목표를 자동 만족시키지 않는다.

백업과 재시도가 있어도 같은 장애를 모두 복구할 수 있는가?

새 자체 기록은 시각 0의 백업에 N 내용 x가 있고 시각 2에 저장 y가 확정된다. 시각 4에 잘못된 삭제가 확정되며 복제본도 삭제를 받아들인다. 시각 6에 장애를 탐지한다. 복제본 존재는 삭제 전 상태 보존과 다르다. 시각 2의 정상 로그까지만 재생할 수 있는 독립 백업/로그가 있다는 조건에서 y를 복원할 수 있다.

또 다른 실패는 저장 y가 완료됐는데 응답이 끊겨 호출자가 성공을 모르는 경우다. 재시도마다 새 사건으로 저장하면 부작용이 늘 수 있다. 여기서는 동일 요청 ID와 결과를 부작용과 함께 원자적으로 남겨 재시도를 같은 결과로 처리하는 설계를 둔다. 기록이 삭제되거나 ID가 달라지면 이 약속의 적용 범위도 끝난다.

회복 시간의 새 계획은 탐지 6분, 백업 읽기 8분, 로그 재생 11분, 자료 검사 13분, 사용자 확인 16분이다. 장애 시작은 5분이라고 정한다. RTO는 시작 5부터 확인 16까지이고 탐지부터만 센 값과 다르다. 이 시간과 로그는 가상 계획이며 실제 복원 시험·장애 주입을 수행하지 않았다.

  • 보호 자산과 검증 요구

부분 실패의 영향을 먼저 적는다

실패 모드는 부품 이름만 나열하는 것이 아니라 사용자에게 어떤 일이 생기는지 설명한다. 저장소가 응답하지 않을 때 오래된 캐시로 읽기를 제공할 수는 있어도 새 저장을 완료했다고 표시해서는 안 된다. 최신성이 중요한 작업에는 오래된 자료의 시점과 제한을 알려야 한다.

대응에는 시간 제한, 요청 제한, 기능 축소, 재시도와 복구가 있다. 재시도는 추가 부하를 만들고 이전 작업의 성공 여부가 불명확할 때 중복 부작용을 낼 수 있다. 무조건 반복보다 전체 시간과 횟수, 중복 처리 정책을 정한다.

손실 허용 시점과 복구 시간은 다르다

복구 시점 목표 RPO는 얼마나 최근의 자료까지 잃을 수 있는지를 시간으로 표현하는 요구다. 복구 시간 목표 RTO는 서비스 복구까지 허용하는 시간을 표현한다. 시작과 종료 조건을 정해야 실제 기록과 비교할 수 있다.

아래 자체 가정에서 백업은 정확히 14:00 상태를 담고 로그나 추가 복제본은 없다. 14:08 실패하면 그 이후 8분 구간의 변경이 백업에 없다. 8분은 변경 구간이지 8분 분량의 자료가 반드시 실제로 쓰였거나 손실됐다는 측정은 아니다.

복원 뒤 사용 가능한지 확인한다

백업은 만들기, 보관하기, 읽기, 자료 검증, 서비스에 연결하기까지 여러 단계에서 실패할 수 있다. 복구 계획은 권한과 암호화 키, 호환 버전, 자원과 담당자를 포함한다. 복사 완료 메시지만으로 실제 사용자 복구를 확정하지 않는다.

독립된 시험 환경에서 복원을 연습하고 핵심 자료와 사용자 흐름을 확인하는 증거가 필요하다. 실제로 연습하지 않았다면 미수행으로 남긴다. 캐시만 돌아온 경우, 자료 복원만 끝난 경우, 사용자가 확인된 경우를 서로 다른 상태로 적는다.

자체 노트 서비스에서 저장소 실패, 캐시 실패, 백업 읽기 실패 각각에 대해 사용자 영향·감지·대응·복구 종료 조건을 써보자. 실제 장애를 발생시키지 않고 계획으로 남긴다.

다른 문제에 적용하기

새 노트 N은 시각 0에 public/owner A/내용 v1이고 B가 읽어 캐시했다. 시각 1에 private으로 바꾸고 시각 2에 B가 캐시 읽기를 요청한다. 새 응답 정책과 과거 사본의 범위를 구별하라. 성능은 예정 100/시작 80/성공 76/timeout 4 및 성공 지연 50ms 72개·300ms 4개 표를 사용해 p95와 400ms 안 성공 비율 두 분모를 구하라. CPU 비용 읽기 1ms·저장 9ms, 200건/s에서 80% 예산 조건의 저장 비중을 계산하라. 별도 복구 표에서 정상 시각 2의 y, 삭제 시각 4, 장애 5/탐지 6/사용자 확인 16을 사용해 필요한 로그 범위와 RTO를 적어라. ID R의 원자 완료 기록이 유지된 세 번 시도와 기록 삭제 뒤의 보증을 구분하라.

힌트 1

서버의 현재 권한과 외부의 옛 사본, 성공 지연과 시작/예정 분모를 따로 기록한다.

힌트 2

자원 조건은 비용 가중식으로 풀고 복구는 정상 사건 범위와 정확한 종료점, 중복 방지는 기록 수명으로 판정한다.

풀이와 답 확인

  1. B의 새 읽기는 private이며 소유자가 달라 거절한다. 과거 합법 사본까지 삭제했다는 보증은 없다.

  2. 성공 p95는 73번째인 300ms다. 400ms 안 성공은 시작 기준 76/80=95%, 예정 기준 76/100=76%다.

  3. 200(1+8p)≤800에서 0≤p≤3/8, 최대 저장 비중 37.5%다. 이는 CPU 모형 조건이며 실제 지연은 미검증이다.

  4. 백업 x에 정상 시각 2까지 로그를 재생해 y를 얻고 잘못된 시각 4의 삭제는 제외한다. RTO는 16−5=11분이고 탐지부터의 10분과 다르다.

  5. R 기록이 원자 효과와 함께 유지되면 세 번 시도/한 번 효과다. 기록 삭제 뒤 동일 문자열만으로 기존 완료를 판정하지 못하므로 늦은 요청 정책이 필요하다.

권한 변경·부하 실현·관측 지연·CPU 예산·정상 복원 범위·효과 기록의 수명을 연결한다. 모든 표와 시간은 자체 가상 계약이며 실제 보안/부하/복구/사용자 시험을 수행하지 않았다.

해결한 뒤 점검할 것

  • 새 요청 거절과 과거 사본 회수의 다른 경계를 설명한다.

  • p95 순위와 시작/예정 두 성공 비율의 분모를 보존한다.

  • 저장 비중의 부등식과 실제 성능 미검증을 구별한다.

  • 정상 로그 범위·복구 종료점·중복 결과 기록의 수명 조건을 기록한다.
