소단원 5.1

계층·서비스·이벤트 구조

같은 제출 기능을 세 가지 구조로 나누면 무엇을 기다리고 무엇을 따로 바꿀 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 함수와 모듈
  • 요청과 응답
  • 메시지와 상태

학습 목표

  • 논리 계층과 물리 배치를 구별한다.
  • 서비스와 이벤트를 책임·통신·배포의 관점으로 설명한다.
  • 접수 응답과 업무 완료의 차이를 시간선에서 찾는다.

1. 책임을 나누는 계층

아키텍처는 구성 요소와 그 관계, 지켜야 할 제약을 설명한다. 학습 과제 제출 시스템에 화면, 제출 규칙, 저장 접근이라는 세 논리 계층을 정해 보자. 화면은 입력과 결과 표시를 맡고, 제출 규칙은 마감과 재제출 정책을 결정하며, 저장 접근은 자료를 읽고 쓴다. 화면이 저장 형식의 세부를 직접 바꾸게 두면 책임 경계가 흐려진다.

논리 계층이 세 개라는 사실은 서버가 세 대라는 뜻이 아니다. 한 프로세스 안에 세 모듈을 둘 수도 있고 물리적으로 나눌 수도 있다. 닫힌 계층은 바로 아래 계층만 사용하도록 하고 열린 계층은 아래 여러 계층을 사용할 수 있게 한다. 어느 규칙인지 명시하지 않고 화살표가 아래를 향한다는 이유만으로 모든 우회 호출을 허용해서는 안 된다. 실제 네트워크 분리는 지연과 장애 경계를 추가한다.

2. 서비스 경계와 배포

서비스 구조에서는 제출 관리와 채점처럼 업무 책임을 나누고 정해진 인터페이스로 통신하게 할 수 있다. 독립 배포를 목표로 하는 마이크로서비스에서는 내부 저장 형식도 소유 서비스의 책임으로 두어 다른 서비스가 몰래 테이블 구조에 의존하는 일을 줄인다. 모든 작은 함수가 서비스가 되는 것도 아니고 서버 수가 많다는 사실만으로 마이크로서비스가 되는 것도 아니다.

예를 들어 제출 서비스가 정상이어도 채점 서비스가 멈추면 동기식 채점 완료 응답은 실패할 수 있다. 장애 격리는 경계를 그리는 것만으로 완성되지 않고 호출자의 시간 제한, 오류 처리, 복구 정책이 필요하다. 하나의 서비스 내부에는 다시 계층 구조를 둘 수 있으므로 계층과 서비스는 반드시 서로 배타적인 대안이 아니다. 무엇을 별도로 배포하고 무엇을 공유하는지 그림에 적어야 한다.

3. 이벤트와 접수 상태

이벤트 구조에서는 제출 접수라는 사실을 기록하여 채널을 통해 채점·알림 소비자에게 전달한다. 발행자는 모든 소비자의 실행 완료를 직접 기다리지 않을 수 있다. 다만 메시지 형식과 의미에 대한 계약은 남는다. 전송 방식에 따라 중복이나 순서 뒤바뀜이 가능하므로 업무 식별자, 처리 기록, 상태 전이 조건을 설계해야 한다.

접수됨과 채점 완료를 사용자 화면에서 구분하자. 이 종이 모형에서는 접수 자료와 이벤트가 안전하게 보존되었다는 가정을 두고 접수 응답을 보낸다. 실제 구현의 데이터 저장과 이벤트 발행 사이 장애 창은 별도 검증이 필요하다. 비동기 채널을 쓴다고 메시지 소실이 자동으로 사라지거나 최종 완료 시간이 항상 짧아지지는 않는다. 추적 ID와 실패 상태도 사용자가 확인할 수 있어야 한다.

중간 과정을 따라가는 예제

자체 시간 모형이다. 입력 검사 2초, 제출 보존 3초, 채점 5초이며 단계 사이 전달·대기 비용은 0이다. 동기 방식은 세 단계를 마친 뒤 응답한다. 비동기 방식은 앞 두 단계가 끝나면 접수 응답하고 채점은 그 뒤 시작한다. 두 응답과 완료 시점을 비교하라.

  1. 시작 시각을 0초로 두고 입력 검사가 끝나는 시각 2초를 표시한다.
  2. 제출 보존은 2초부터 5초까지이며 이 모형에서는 제출과 이벤트가 함께 안전하게 기록됐다고 가정한다.
  3. 동기 방식은 채점이 5초부터 10초까지 이어진 뒤 10초에 완료 응답을 보낸다.
  4. 비동기 방식은 5초에 접수 응답을 보내고 채점은 10초에 끝난다. 응답 내용이 완료라는 뜻은 아니다.
  5. 0 비용 가정을 제거하여 큐 대기 4초를 더하면 비동기 완료는 14초가 되지만 접수 응답은 여전히 이 모형에서 5초이다.

동기 완료 응답은 10초, 비동기 접수 응답은 5초이며 큐 대기 없는 비동기 완료는 10초이다. 대기 4초가 있으면 완료는 14초이다. 이는 가정한 시간선의 계산이며 실측 성능이 아니다.

종이와 본문으로 직접 해보기

검사 1초, 보존 2초, 큐 대기 6초, 채점 4초인 비동기 시간선을 그려라. 같은 제출 이벤트가 두 번 온 경우 채점 결과를 두 번 추가하는 소비자와 제출 ID별 결과 하나를 보존하는 소비자의 차이도 적어라.

힌트 보기

접수 응답은 보존 직후, 완료는 큐 대기와 채점 이후이다. 중복 이벤트의 효과와 중복 수신 자체를 구별한다.

풀이 보기

접수는 3초, 채점 시작은 9초, 완료는 13초이다. 무조건 추가하면 결과가 두 개 생길 수 있다. 같은 ID의 처리를 원자적으로 판정하고 결과 하나를 유지하는 정책이면 중복 효과를 막을 수 있다. 단순히 먼저 조회한 뒤 추가하는 두 단계만으로 동시 처리에 안전하다고 단정하지 않는다.

오해와 반례

이벤트를 쓰면 접수 응답이 곧 모든 소비자의 완료를 보장한다.

5초에 접수하고 10초 또는 14초에 채점을 마치는 시간선이 반례이다. 이벤트 전달·보존·중복 처리·관찰 가능성의 조건을 별도로 정해야 한다. 접수 응답을 완료처럼 표시하면 사용자가 아직 처리되지 않은 작업을 끝난 것으로 오해한다.

한 단계 더

한 서비스 내부의 세 논리 계층, 제출 이벤트 채널, 두 소비자와 각각의 저장소를 한 그림에 그려 보자. 화살표마다 동기 요청인지 이벤트 전달인지 표시하고 접수 자료가 남았는데 이벤트가 발행되지 않은 장애를 추가한다. 상태를 복구하는 방법을 설명할 수 있어야 구조 선택을 이해했다고 할 수 있다. 실제 브로커·데이터베이스 실행은 이 단원에서 수행하지 않았다.

소단원 5.2

결합도·응집도

파일을 잘게 나누었는데도 작은 수정이 왜 여러 곳으로 퍼질까?

준비 개념과 학습 목표

준비 개념

  • 모듈과 인터페이스
  • 의존 화살표
  • 저장 자료와 자료 형식

학습 목표

  • 모듈 내부 책임과 모듈 사이 의존성을 구별한다.
  • 변경의 영향이 퍼지는 조건을 추적한다.
  • 파일 수나 화살표 수만으로 품질을 판정하지 않는다.

1. 안쪽 관계와 바깥 관계

응집도는 한 모듈 안의 작업이 얼마나 관련된 책임을 이루는지 보는 관점이다. 수강 등록 모듈에 좌석 확인, 중복 등록 방지, 등록 취소가 함께 있다면 등록이라는 책임을 설명할 수 있다. 여기에 이미지 압축과 음악 재생을 이름 없이 함께 넣는다면 왜 한 모듈인지 설명하기 어렵다. 같은 파일에 있다는 사실이 의미 있는 관계를 만들지는 않는다.

결합도는 모듈 사이의 의존 정도와 성격을 보는 관점이다. 함수 호출만 아니라 공유 자료 형식, 실행 순서, 다른 서비스의 가용성도 관계가 될 수 있다. 낮은 결합도를 추구해도 협력에 필요한 계약까지 없앨 수는 없다. 무조건 함수를 한 줄씩 쪼개면 내부 책임은 작아 보이지만 조립 관계가 복잡해질 수 있으므로 이해 가능한 책임 경계와 변경 조건을 함께 봐야 한다.

2. 정보 은닉과 변경 영향

화면 A가 등록 정책 B를 호출하고 B가 저장 모듈 C를 호출하는 그래프 A→B→C를 그려 보자. C 내부의 저장 자료를 바꾸더라도 C의 공개 계약을 보존하면 B가 그 내부를 모르는 한 코드를 바꾸지 않을 수 있다. 반면 C의 공개 반환 형식을 바꾸면 B가 그 형식을 사용하는 부분은 수정해야 할 수 있다. 단순히 직접 화살표가 없다는 이유로 A의 영향까지 무조건 0이라고 할 수 없다.

B가 새 C 형식을 내부에서 변환하고 기존 등록 결과 계약을 유지하면 A는 그 변화를 몰라도 된다. 그러나 B의 공개 계약까지 바꾸면 A도 수정 대상이다. 정보 은닉은 변경 가능한 결정을 경계 뒤에 숨기고 약속한 외부 의미를 보존하는 방법이다. 인터페이스 문서에는 이름과 타입뿐 아니라 오류·단위·순서·성공 조건을 적어야 사용자의 숨은 가정을 찾을 수 있다.

3. 숨은 결합과 지표의 한계

A가 B를 거치지 않고 C의 내부 테이블을 읽으면 직접 호출을 하지 않아도 자료 형식에 결합된다. 이벤트 소비자가 발행자의 내부 필드 이름을 그대로 믿는 경우에도 스키마 결합이 생긴다. 비동기 메시지는 동시에 살아 있어야 하는 시간 의존성을 줄일 수 있지만 계약 버전, 재처리, 진단 책임을 추가한다. 어느 차원의 결합이 달라졌는지 구체적으로 적어야 한다.

그래프의 간선 수는 연결을 빠뜨리지 않았는지 점검하는 데 쓸 수 있지만 품질 점수 자체는 아니다. 필수 등록 정책 호출 한 개와 내부 저장 필드 수십 개를 읽는 접근 한 개를 모두 간선 하나로 세면 강도와 변경 위험이 가려진다. 이 단원의 활동은 자체 작은 그래프의 영향을 추적하는 것이며 실제 프로젝트의 변경 비용이나 결함 수를 측정했다고 주장하지 않는다.

중간 과정을 따라가는 예제

초기 그래프는 A→B, B→C 두 의존이며 A는 B의 등록 결과 계약만 안다. C가 내부 배열을 다른 저장 방식으로 바꾸는 경우와 공개 반환 형식을 바꾸는 경우를 비교한다. 후자의 경우 B가 외부 계약을 보존하는 변환을 제공한다고 가정한다.

  1. 노드 A,B,C 세 개와 직접 의존 간선 두 개를 적는다. 화살표는 왼쪽 모듈이 오른쪽 모듈을 사용한다는 뜻이다.
  2. C 내부 변경은 공개 의미가 같고 B가 내부를 보지 않는 조건이면 C 안에 숨길 수 있다. B와 A의 코드 변경은 필수가 아니다.
  3. C 공개 반환 형식 변경은 B의 C 사용 지점에 영향을 준다. C와 B의 수정·검증을 계획한다.
  4. B가 형식 변환을 하고 기존 결과와 오류 계약을 유지하면 A 코드는 바꿀 필요가 없다는 조건부 결론을 낸다.
  5. A가 C 내부를 직접 읽는 새 간선 A→C를 추가하면 직접 의존은 세 개가 된다. 이 경우 C 내부 변경도 A에 영향을 줄 수 있어 앞의 은닉 조건이 깨진다.

직접 간선은 처음 2개, 우회 접근 추가 후 3개이다. 내부 변경의 차단과 A의 변경 불필요 결론은 계약 보존·내부 접근 금지라는 조건에 의존한다. 간선 수만으로 두 설계의 전체 품질을 단정하지 않는다.

종이와 본문으로 직접 해보기

A→B, B→C, C→A를 그려 순환을 찾고, C→A를 없애되 C가 필요한 설정을 매개변수로 받게 바꾸는 대안을 적어라. 등록·취소·이미지 압축 세 작업을 어떤 책임으로 묶을지 이유와 함께 적어라.

힌트 보기

A에서 화살표를 따라 다시 A로 돌아오는 경로를 찾는다. 의존 제거가 필요한 정보를 없애는 일인지 전달 방식을 바꾸는 일인지 구분한다.

풀이 보기

A→B→C→A가 순환이다. C가 A의 내부 상태를 읽는 대신 명시적인 설정 값을 받도록 설계하면 직접 역방향 접근을 없애는 대안이 된다. 값의 형식 계약은 남는다. 등록과 취소는 같은 등록 책임에 묶고 이미지 압축은 독립 책임으로 분리할 수 있으나 실제 요구에 따라 경계를 설명해야 한다.

소단원 5.3

품질 속성의 트레이드오프

빠른 응답과 최신 정보와 실패 복구를 모두 같은 방법으로 얻을 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 응답 시간
  • 캐시와 재시도
  • 백분율과 시간 단위

학습 목표

  • 품질 목표를 관찰 조건과 수치로 표현한다.
  • 한 선택의 이득과 비용을 같은 시나리오에서 비교한다.
  • 종이 예산과 실제 서비스 보장을 구별한다.

1. 좋다는 말을 관찰 가능한 목표로

빠르다, 안전하다, 바꾸기 쉽다는 말만으로는 대안을 비교하기 어렵다. 어떤 사용자가 어떤 상황에서 무엇을 요청하고, 어느 부분이 어떻게 반응하며, 무엇을 측정할지 정해야 한다. 예를 들어 평상시 공개 공지 읽기 요청의 95%가 200ms 안에 응답한다는 목표는 대상·상황·관찰 비율과 시간을 가진다. 모든 요청의 최대 시간이 200ms라는 목표와는 다르다.

품질 시나리오는 입력 사건, 운영 상황, 대상, 기대 반응과 측정 기준을 구체화한다. 아키텍처 분석에서는 하나의 결정이 여러 품질 목표에 주는 영향을 찾는다. 이 활동은 CMU SEI의 품질 목표와 시나리오 분석 관점을 참고한 입문 종이 연습이다. 이해관계자 회의와 정식 평가 절차를 수행한 것이 아니므로 ATAM 평가 완료나 실제 시스템 품질 인증으로 기록하지 않는다.

2. 캐시의 지연과 신선도

공지 내용을 캐시에 두면 반복 읽기의 저장소 부담과 응답 시간을 줄일 가능성이 있지만 오래된 내용을 읽을 수 있다. 고정 만료 시간 30초를 마지막 적재 시점부터 계산하고, 만료 후에는 새 데이터를 읽기 전까지 옛 내용을 제공하지 않는 자체 모형을 정하자. 원본은 즉시 최신이며 갱신 읽기는 최대 5초이고 동시 갱신 경합은 없다고 가정한다. 추가로 만료 시각에 즉시 새 요청이 도착해 갱신을 시작하고 그 요청에 응답한다고 가정한다. 원본 변경은 적재 직후 한 번만 일어나며 갱신 중 추가 변경은 없다. 이 도착 조건은 자체 계산을 위한 가정이며 일반 Cache-aside가 요청을 자동 생성한다는 뜻이 아니다.

적재 직후 원본이 바뀌면 기존 내용이 제공될 수 있는 기간은 거의 30초이다. 만료 후 새 읽기를 기다리는 최대 5초를 더하면 새 값을 응답받는 시점은 변경 후 최대 약 35초이다. 이 둘은 오래된 내용의 제공 기간과 새 값의 응답 대기라는 다른 측정이다. 접근 때마다 만료를 연장하거나 원본 복제 지연이 있거나 오래된 값을 계속 제공하는 정책이면 이 경계를 그대로 사용할 수 없다. 만료 뒤 첫 요청이 도착하기까지 w초를 더 기다린다면 새 응답 시점은 변경 후 약 30+w+5초이다. w의 상한을 정하지 않으면 변경 시점부터 새 응답까지의 유한 상한도 보장되지 않는다.

3. 재시도와 가용성 예산

실패한 요청을 다시 시도하면 일시 장애에서 성공할 기회를 늘릴 수 있지만 기다림과 부하가 늘어난다. 최대 3회 시도, 시도별 상한 2초, 시도 사이 대기 1초 두 번인 모형에서는 최대 8초이다. 추가 네트워크·큐 비용을 모두 시도 상한에 포함했다는 가정이 필요하다. 응답만 유실된 변경 요청을 재시도하면 같은 업무가 두 번 실행될 수 있으므로 멱등 처리 조건도 분석한다.

30일 연속 관찰 기간에 시간 기준 가용성 목표 99.9%를 정하면 허용 불가용 시간은 30×24×60×0.001=43.2분이다. 요청 성공률 99.9%와 같은 계산이라고 단정할 수 없고 계획 점검 제외 등 분모 규칙도 확인해야 한다. 복제나 재시도 하나를 추가했다고 목표 달성을 증명한 것도 아니다. 정책, 비용, 복구 능력, 보안과 관찰 가능성을 같은 대안표에서 검토한 뒤 실제 측정이 필요하다.

중간 과정을 따라가는 예제

공지 캐시는 고정 30초 만료, 갱신 읽기 최대 5초이며 앞서 명시한 원본·경합 조건을 만족한다. 재시도는 3회×2초와 사이 대기 두 번×1초이다. 30일 시간 가용성 목표는 99.9%이다. 각 예산과 한계를 계산하라. 캐시의 만료 시각에 새 요청이 즉시 도착하여 갱신을 시작하고, 원본은 적재 직후 한 번 바뀐 뒤 유지된다고 가정한다.

  1. 캐시 적재 시각을 0초, 원본 변경을 그 직후로 놓는다. 만료는 적재 후 30초이며 접근으로 연장하지 않는다.
  2. 이전 내용은 만료 전 거의 30초까지 제공될 수 있다. 만료 뒤에는 옛 내용 제공을 멈추고 새 읽기를 기다린다.
  3. 만료 시각 30초에 새 요청이 즉시 도착해 갱신을 시작하고 새 읽기가 5초 걸리면 새 응답은 약 35초이다. 이는 35초 동안 옛 내용을 계속 제공한다는 뜻이 아니다. 요청 도착이 늦어지면 새 응답 시점도 그만큼 늦어진다.
  4. 재시도 상한은 3×2+2×1=8초이다. 3회 시도는 첫 시도와 재시도 2회를 포함한다.
  5. 관찰 분모는 30×24×60=43200분이고 불가용 몫 0.1%=0.001을 곱하면 43.2분이다. 시간 기준 목표의 종이 예산임을 표시한다.

옛 값 제공 기간은 최대 약 30초, 새 응답까지는 최대 약 35초, 재시도 정책 상한은 8초, 시간 기준 불가용 예산은 43.2분이다. 조건을 바꾸면 경계도 달라지고 실제 달성 여부는 아직 측정하지 않았다. 새 응답의 35초 경계에는 만료 시 즉시 요청 도착·갱신 시작과 이후 원본 불변 조건이 필요하다.

종이와 본문으로 직접 해보기

만료를 10초, 갱신 읽기를 2초로 바꾸면 두 신선도 관련 시간을 구하라. 2회 시도×3초와 사이 대기 2초의 상한도 구하라. 목표를 99.95%로 높일 때 같은 30일 시간 분모의 불가용 예산을 계산하라. 이 활동에서도 원본은 적재 직후 한 번 바뀌고 유지되며, 만료 시각에 새 요청이 즉시 도착해 갱신을 시작한다고 가정한다.

힌트 보기

오래된 값 제공과 새 응답 대기를 따로 쓴다. 99.95%의 남은 비율은 0.05%=0.0005이다.

풀이 보기

옛 값은 거의 10초까지, 새 응답은 약 12초까지이다. 시도 상한은 2×3+1×2=8초이다. 불가용 예산은 43200×0.0005=21.6분이다. 수치가 더 엄격해졌다는 사실만으로 구현이 그 목표를 만족하는 것은 아니다. 12초 경계는 위의 즉시 요청 도착 조건 아래 값이며 후속 요청 대기 시간의 상한을 모르면 변경 후 새 응답 시점도 제한할 수 없다.

오해와 반례

캐시와 재시도를 많이 넣으면 모든 품질이 동시에 좋아진다.

캐시에는 신선도와 접근 권한 자료 노출의 위험이 있고 재시도에는 지연·부하·중복 효과가 있다. 같은 요청에서 8초를 기다리도록 한 정책은 짧은 응답 목표와 충돌할 수 있다. 선택의 이득뿐 아니라 조건과 손해, 검증 방법을 기록해야 한다.

만료 시 즉시 새 요청이 도착하여 갱신을 시작하는 모형에서 원본 변경 직후부터 새 응답까지의 상한이다.

만료 후 옛 값 제공을 중지하므로 옛 값 제공 기간은 약 30초이다. 새 응답의 35초에는 즉시 요청 도착·5초 갱신 상한이 필요하며 요청이 늦으면 응답도 늦어진다.

한 단계 더

공개 공지와 좌석 예약에 같은 캐시 정책을 적용해도 되는지 두 시나리오를 쓰자. 공개 공지는 짧은 오래됨을 허용할 수 있지만 예약의 중복 판매 방지는 별도 원자적 판단이 필요하다. 요청별 최악 시간과 백분위 지연, 시간 가용성과 요청 성공률을 서로 다른 열에 기록하면 숫자 하나로 시스템을 좋다고 단정하는 실수를 줄일 수 있다. 실제 부하·장애·캐시 실험은 미수행이다.
