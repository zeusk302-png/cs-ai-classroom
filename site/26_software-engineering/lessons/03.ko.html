소단원 3.1

이해관계자와 인터뷰

예약 버튼을 빨리 만들면 도서관 사람들의 문제가 해결될까?

준비 개념과 학습 목표

준비 개념

  • 이해관계자는 시스템 사용·운영·개발·승인 또는 영향과 관계된 사람/집단이다. 직접 버튼을 누르는 이용자만 포함하지 않는다.
  • 요구 도출은 필요한 결과와 제약을 찾아 명시하는 과정이다. 인터뷰 발언, 작성자의 해석, 합의한 요구는 같은 종류의 증거가 아니다.
  • 자가진단: 이용자·사서·운영 담당 세 역할을 종이에 적고 각자 필요한 결과를 하나씩 상상한다. 아래는 실제 사람을 면담하지 않은 가상 사례다.

학습 목표

  • 역할·영향·승인 책임을 나눈 이해관계자 지도를 만든다.
  • 중립 질문과 구체 사건을 통해 모호한 필요를 분석한다.
  • 발언→해석→확인 질문→후보 요구의 근거를 추적한다.

누가 어떤 결과를 필요로 하는가

가상 작은 도서관에서 이용자는 헛걸음을 줄이고, 사서는 중복 예약을 피하며, 운영 담당은 장애 중에도 예약 상태를 설명하고 싶다. 승인자는 우선순위와 예산을 정할 수 있지만 모든 이용 경험을 대신 말해 주지는 못한다. 생애주기별 역할·사용 맥락·정보 접근·영향을 표로 적으면 버튼 사용자만 봤을 때 빠지는 요구를 찾을 수 있다.

이용자 한 명의 발언이 모든 이용자의 실제 행동을 대표한다고 추정하지 않는다. 사례는 전부 자기완결 가상 발언이며 모집·동의·녹음·실제조사를 수행하지 않았다. 실제 연구를 계획할 때는 참여 동의와 필요한 기록의 취급 조건을 정해야 하지만 여기서는 특정 법률 준수 판정이나 기관 규정을 주장하지 않는다.

해결책 제안 뒤의 문제를 묻는다

가상 발언 U1: 알림 버튼을 크게 해 주세요를 곧바로 큰 버튼 요구로 승인하지 않는다. 언제 어떤 결과를 놓쳤는지, 지난 예약을 어떻게 확인했는지 묻는다. 가상 추가 정보 U2: 통신이 끊긴 뒤 접수가 되었는지 몰라 다시 눌렀다가 중복 예약이 됐어요를 얻었다고 문제지에 주면, 상태 확인과 중복 방지가 더 직접적인 필요 후보다.

중립 질문은 최근 예약에서 어떤 순서로 확인했나요처럼 답을 강요하지 않는다. 큰 버튼이면 해결되죠는 미리 답을 정하고 두 문제를 섞는 질문이다. 발언은 원래 의미와 맥락을 보존하고 해석을 별도 열에 적는다. 연구자의 추측을 인용문이나 실제 관찰로 꾸미지 않는다.

분석과 재확인의 연결

후보 N1: 재시도 뒤 같은 예약 여부를 확인하고 싶다를 만들고, R1: 같은 이용자·책·활성 예약에 중복 결과를 만들지 않는다라는 구체 요구를 검토할 수 있다. 그러나 책 단위인지 개별 복본 단위인지, 취소 뒤 새 예약은 허용되는지, 동시 요청과 실패 복구는 무엇인지 아직 질문이 남는다. 이 질문들이 답해질 때까지 후보·미정 상태를 유지한다.

원 발언 ID→필요 ID→요구 ID→수용 기준 ID를 잇는 추적표를 만든다. 이해관계자에게 해석과 예외를 다시 확인하고 충돌을 기록해야 합의 여부를 알 수 있다. 인터뷰 횟수 자체는 요구 완전성 증명이 아니며, 다수의 선호로 데이터 손실·접근 권한 같은 제약을 자동 지울 수 없다.

중간 과정을 따라가는 예제

가상 U1 큰 알림 버튼, U2 통신 실패 뒤 재예약, 사서 S1 같은 사람이 같은 책을 두 번 잡아요를 자료로 받고 후보 요구와 확인 질문을 도출한다.

  1. U1은 해결책 제안이다. 큰 버튼이라는 설계안과 결과를 놓친다는 문제 추정을 따로 적는다.
  2. U2와 S1을 연결해 중복 활성 예약이라는 문제 후보를 만든다. 실제조사 증거가 아니라 문제에서 준 정보다.
  3. N1 상태 확인, R1 중복 방지 후보를 적고 이용자·책·활성의 정의를 확인 질문으로 남긴다.
  4. 취소 뒤 재예약과 동시 실패 상황을 묻는 질문을 붙이고 아직 승인 전임을 표기한다. U1만으로 버튼 크기를 확정하지 않는다.

문제 후보는 접수 상태 불명확과 중복 활성 예약이다. 상태 확인·중복 방지 후보와 식별/취소/동시성 질문을 도출했으나 실제 면담·승인 완료로 표시하지 않는다.

종이와 본문으로 직접 해보기

가상 관리자 A1: 보고서를 많이 주세요, 직원 E1: 지난 예약 취소 이유를 알아야 해요를 받았다. 중립 후속 질문 두 개와 후보 필요 하나, 아직 확인하지 못한 항목 하나를 적는다.

풀이 보기

예: 최근 어떤 결정을 위해 어떤 기록을 찾았나요? 취소 사유는 누가 기록하고 누가 확인해야 하나요? 후보는 결정에 필요한 취소 사유 확인이다. 기록 항목·열람권한·실제 필요빈도는 미확인이다. 보고서 개수만 늘리면 필요를 충족한다고 보장되지 않는다.

오해와 반례

요청을 가장 많이 말하는 고객 한 명의 말을 적으면 요구가 완성된다.

운영·지원·직접 이용자·승인 역할이 다르면 놓치는 제약이 있다. 버튼 제안과 재시도 중복 문제의 차이도 반례다. 발언 수는 대표성·일관성·실현가능성의 증명이 아니다.

소단원 3.2

기능·비기능 요구

예약이 되기만 하면 느리거나 중복되어도 요구를 만족한 걸까?

준비 개념과 학습 목표

준비 개념

  • 기능 요구는 어떤 조건에서 시스템이 무엇을 해야 하는지 정한다. 품질 요구는 그 행동의 성능·신뢰성 등 정도와 제약을 정한다. 분류 명칭보다 내용과 검증 조건이 중요하다.
  • 밀리초 ms는1/1000초다. 시간 측정에는 시작/끝 사건과 부하·환경이 필요하다. 서버 처리와 이용자 화면 완료는 다른 구간이다.
  • 자가진단: 예약 성공이라는 결과와 500ms 이내라는 시간 조건은 서로 다른 질문이다. 하나가 참이어도 다른 하나는 거짓일 수 있다.

학습 목표

  • 행동 요구·품질 요구·설계 제약을 맥락에 맞게 구별한다.
  • 전제·결과·시간·분모를 측정 가능하게 적는다.
  • 기능 성공과 성능 또는 권한 조건의 독립 반례를 만든다.

무엇과 얼마나 잘을 함께 적는다

가상 R1은 인증된 이용자가 이용 가능한 책에 예약을 요청하면 정확히 한 활성 예약ID를 반환한다는 행동이다. 가상 Q1은 정한 환경의 유효 요청100개 중 적어도95개가500ms 이내에 올바른 결과를 얻는다는 정도다. 기능 요구만 적으면 시간·실패·중복 처리 기대를 추측하게 되고 품질 요구만 적으면 빠르지만 틀린 결과를 성공으로 셀 수 있다.

기능/비기능은 프로젝트에서 쓰는 분류다. 비권한 요청 거절은 보안 품질을 위한 구체 기능일 수도 있어 상호배타적인 두 바구니라고 단정하지 않는다. PostgreSQL 사용처럼 구현 선택을 명시한 항목은 설계 제약이며 결과 중심 요구와 구별한다. 정당한 외부 제약이면 기록하지만 사용자 제안만으로 필수 구현으로 확정하지 않는다.

조건과 관측 경계를 고정한다

Q1의 자체 시험 명세는 같은 서버 구성·고정1000책 데이터·단일클라이언트의 직렬100유효요청·각각 고유 예약조건, 클라이언트가 요청을 보낸 시각부터 올바른 결과 수신까지의 구간으로 정한다. 재시도는 하지 않고 오류·시간초과는 느린 실패로 분모에 포함한다. 네트워크 포함 구간이라 서버 처리시간만으로 대체하지 않는다. 실제 시험은 수행하지 않은 요구 예시다.

≤500ms 경계는500을 포함하고95/100은 포함형 적어도95%다. 모든 요청의 평균≤500ms와 같지 않다.100개 중94개가100ms,6개가1000ms이면 평균154ms여도95% 조건은 실패다. 반대로95개가500ms,5개가10000ms이면95% 조건은 통과하지만 평균975ms다. 유한 표본 통과는 모든 미래 부하의 분포 보장이 아니다.

사전조건과 실패도 요구이다

R1의 이용 가능·인증됨·중복 없음 같은 정상 전제와, 이미 활성 예약이 있을 때 기존ID를 반환하는 재시도 규칙, 없는책/권한없음/내부실패 때 상태를 바꾸지 않는 요구를 따로 적는다. 분모에서 실패를 지워 성공만 세면 Q1을 유리하게 바꿔 버린다. 예약식별 범위와 동시에 일어난 사건의 정렬/원자성은 별도 합의가 필요하다.

기능 정확성은 입력·출력·변경된 상태를 검사하고 시간 품질은 같은 올바른 결과의 관측시간을 검사한다. 요구의 측정 가능성은 그 수치가 필요한지를 증명하지 않는다.500ms와95%는 가상 이해관계자가 검토할 후보이며 접근성·복구·부하환경도 아직 별도 요구가 될 수 있다. 공개 NASA 체크리스트를 적용한 예시이지 유료 품질분류 표준 준수 판정이 아니다.

중간 과정을 따라가는 예제

Q1에서 올바른 결과100개 중94개가400ms,1개가500ms,5개가900ms라는 가상 시험표를 준다. 모든 결과의 기능값은 맞다고 가정하고 시간 수용 여부를 계산한다.

  1. 분모는 정한100개 요청이며 누락·중복행이 없다고 가정한다. 성공한 것만 다시 뽑는 분모를 쓰지 않는다.
  2. ≤500ms인 결과는94+1=95개다. 정확히500ms인 한 개도 포함한다.
  3. 비율95/100=95%이므로 적어도95% 조건은 통과한다. 평균은 (94×400+500+5×900)/100=426ms다.
  4. 평균426은 추가 계산일 뿐 판정 기준은95%다. 표는 가상이며 실제 앱·네트워크 성능 측정이 아니다.

가상 표는 Q1을 통과한다. 기능 올바름은 문제의 별도 전제이고 미래 부하나 모든 이용자 경험을 검증한 결과가 아니다.

종이와 본문으로 직접 해보기

가상 표 A:99개100ms+1개10000ms, B:94개100ms+6개1000ms를 비교한다. Q1의 비율과 평균을 구하고 두 기준이 같은지 판단한다.

풀이 보기

오해와 반례

비기능 요구는 빠르고 안전하게 같은 말로 두고 기능 테스트만 통과하면 된다.

94%/154ms 반례는 시간 기준 선택에 따라 판정이 달라짐을 보인다. 빠르다는 표현에 구간·부하·실패·분모·경계를 정의해야 하며 올바른 예약 결과와 시간 조건을 각각 확인한다.

소단원 3.3

범위와 수용 기준

모든 테스트가 초록색이면 이번 버전의 약속을 전부 지킨 걸까?

준비 개념과 학습 목표

준비 개념

  • 범위는 어떤 결과·기능·환경을 이번 작업에 포함하고 제외하는지 정한다. 제외는 영원히 불필요하다는 뜻이 아니라 이번 합의의 경계다.
  • 수용 기준은 요구를 만족했다고 판정할 관측 조건이다. 요구ID와 시험/분석ID를 연결하되 시험 개수와 요구충족을 혼동하지 않는다.
  • 자가진단: 예약 생성·조회는 이번에 포함하고 결제는 제외한다고 종이에 경계를 그린다. 생성이 조회와 연결되는 것은 포함 범위 안의 계약이다.

학습 목표

  • 포함/제외·가정·의존·변경의 경계를 명시한다.
  • 상태·행동·관측결과로 수용 기준을 만든다.
  • 추적 커버리지·사례 통과·전체 정확성과 필요확인을 구별한다.

범위는 시스템의 약속을 고정한다

가상 버전 V1의 포함은 책 식별자 조회·인증 이용자의 예약 생성/취소·자기 예약 상태 조회이고, 제외는 결제·배송·외부도서관 연계다. 인증 서비스를 외부에서 제공받는다는 의존을 적되 예약 접근권한 검사를 누가 책임지는지는 별도 지정한다. 외부 의존이 있다는 이유로 잘못된 인증정보 수용을 자동 제외하지 않는다.

대상은 하나의 책ID에 대한 활성 예약이며 실제 복본 배정은 제외한다는 가정을 쓴다. 책ID나 활성의 정의가 바뀌면 생성·중복·조회 기준의 의미도 바뀐다. 고정한 요구 버전과 변경 이유/영향/승인 상태를 함께 기록해야 나중에 기준을 몰래 완화해 통과시키는 일을 피할 수 있다.

상태와 결과를 모두 관측한다

가상 AC1: 인증된 이용자 u에게 책 b의 활성 예약이 없고 b가 예약 가능한 상태일 때 생성 요청을 완료하면 예약ID r 하나가 반환되고, 자기 목록에는 (r,u,b,active)가 정확히 한 건 나타난다. AC2: 같은 u,b의 활성 예약이 이미 있으면 같은 r을 돌려주고 활성 건수를 늘리지 않는다. 각 문장은 입력·이전 상태·행동·결과·상태변화를 포함한다.

실패/취소에도 기준을 둔다. 권한 없는 이용자가 남의 예약을 조회하면 정한 거절 결과를 주고 상태는 변하지 않는다. 취소를 완료한 예약은 active가 아니며 다음 생성은 새ID를 얻는다. 동시 요청과 영속성은 이 순차 모형의 사례만으로 보장하지 않으므로 별도 요구/시험으로 남긴다. 정상 하나만 시험해 모든 예외를 확인했다고 쓰지 않는다.

수용의 증거 범위

자체 순차 종이 모형에서 초기 활성0→첫생성1→재시도1→취소0→새생성1을 추적하면 AC1/AC2의 기대 상태를 볼 수 있다. 반환 문자열 success만 검사하면 중복2건을 만드는 구현도 통과할 수 있으므로 결과ID와 상태 건수를 함께 관측해야 한다. ID를 바꾸어 재시도 반환을 비교하기 어렵게 하지 않는다.

고정된 유한 수용 사례가 통과하면 그 사례에 대한 증거를 얻는다. 무한 입력·고장·동시성·미래환경의 정확성 증명이나 실제 이용자 필요 적합성 확인은 아니다. 요구에 맞는지 검증하는 일과 그 요구가 필요한 결과를 정의했는지 확인하는 일을 분리한다. 계산 검산·독립 문서검토·실제 사용자시험은 서로 다른 근거다.

중간 과정을 따라가는 예제

가상 상태표에서 u,b의 활성예약이 없다. 생성은 새 r1, 같은조건 재시도는 r1, 취소는 r1을 inactive, 다시생성은 새 r2로 정한다. 순차 사건 네 개를 추적한다.

  1. 첫 생성은 r1을 반환하고 active(r1)=참, 활성 건수1이다. AC1의 결과와 상태가 일치한다.
  2. 재시도는 r1을 반환하고 새건을 만들지 않는다. 건수1 유지가 AC2의 핵심이다.
  3. 취소 뒤 r1은 inactive, 활성 건수0이다. 이력이 남아도 활성 예약과 구별한다.
  4. 다시 생성은 r2를 반환하고 활성1이다. r2≠r1을 새ID 계약으로 요구한다. 이력은 r1,r2 두 건이지만 활성은 한 건이다.

반환 r1,r1,취소확인,r2; 활성 건수1,1,0,1이다. 이는 자체 종이 수용모형으로 실제DB/서비스/영속성/동시성 시험이 아니다.

종이와 본문으로 직접 해보기

잘못된 구현이 첫생성 r1/재시도 r2를 반환하고 둘 다 active로 남긴다. 결과에 success만 표시하면 통과할 수 있는가? AC2를 검사할 두 관측값을 적는다. 결제 기능의 부재는 V1 실패인가?

풀이 보기
