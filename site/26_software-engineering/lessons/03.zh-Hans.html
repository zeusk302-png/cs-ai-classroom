小节 3.1

利益相关者与访谈

尽快做出预约按钮，就能解决图书馆里人们的问题吗？

预备知识与学习目标

预备知识

  • 利益相关者是与系统的使用、运营、开发、批准或影响有关的个人或群体，并不限于直接点击按钮的用户。
  • 需求获取是发现并明确所需结果及约束的过程。访谈发言、作者的解释和已经达成共识的需求，并不是同一种证据。
  • 自我检查：在纸上写出读者、图书馆员和运营负责人三个角色，分别想象他们需要的一个结果。下面是假想案例，没有访谈真实的人。

学习目标

  • 区分角色、影响和批准责任，绘制利益相关者地图。
  • 通过中立问题和具体事件分析模糊的需要。
  • 追溯发言→解释→确认问题→候选需求的依据。

谁需要什么结果

在一个假想的小图书馆中，读者希望减少白跑一趟，图书馆员希望避免重复预约，运营负责人希望在故障期间也能解释预约状态。批准者可以决定优先级和预算，却不能替所有人描述使用体验。按生命周期列出角色、使用情境、信息访问和影响，可以找出只关注按钮使用者时遗漏的需求。

不要推断一个读者的发言代表所有读者的实际行为。这里的发言都是自足的假想资料，没有进行招募、征得同意、录音或真实调查。规划实际研究时，应确定参与同意以及必要记录的处理条件；本课不声称判定了某项法律合规或机构规定。

追问解决方案背后的问题

假想发言 U1：“请把通知按钮做大一些。”不能立刻据此批准“大按钮”需求。应询问何时错过了什么结果，以及上次如何确认预约。如果题目补充假想信息 U2：“断网后，我不知道请求是否已受理，于是又点了一次，结果重复预约了。”那么状态确认和防止重复就是更直接的候选需要。

“最近一次预约，你按什么顺序确认？”是不会强迫回答的中立问题。“按钮变大就能解决，对吧？”则预设答案，并混合了两个问题。保留发言的原意和情境，把解释写在单独一栏。不要把研究者的猜测伪装成引语或实际观察。

连接分析与再次确认

可以提出候选 N1：“重试后希望确认是不是同一笔预约”，并审查具体候选要求 R1：“同一读者、同一本书的有效预约不产生重复结果”。但仍需确认是按书目还是按实体复本区分、取消后能否重新预约、并发请求和失败恢复如何处理。在这些问题得到回答之前，保持候选或未定状态。

建立原始发言 ID→需要 ID→要求 ID→验收标准 ID 的追溯表。向利益相关者再次确认解释和例外，并记录冲突，才能确定是否达成共识。访谈次数本身不能证明需求完整；多数人的偏好也不能自动取消数据丢失、访问权限等约束。

逐步推导的例题

题目给出假想资料 U1“大通知按钮”、U2“通信失败后再次预约”和图书馆员 S1“同一个人把同一本书预约了两次”。推导候选要求及确认问题。

  1. U1 是解决方案建议。把“大按钮”设计方案和“错过结果”的问题推测分开记录。
  2. 连接 U2 与 S1，提出“重复有效预约”的候选问题。这是题目给出的信息，不是真实调查证据。
  3. 记录 N1 状态确认、R1 防止重复两个候选，并留下关于读者、书和有效状态定义的确认问题。
  4. 补充取消后重新预约、并发失败情境的问题，并标明尚未批准。不能仅凭 U1 决定按钮大小。

候选问题是受理状态不明确和重复有效预约。已提出状态确认、防止重复的候选，以及标识、取消和并发相关问题，但不能标记为完成了真实访谈或批准。

用纸笔和正文动手试一试

得到假想发言：管理员 A1“请给我很多报表”、员工 E1“我需要知道过去预约取消的原因”。写出两个中立追问、一个候选需要和一个尚未确认的项目。

查看提示

从用途、阅读者和决策展开“很多”的含义；另行询问原因信息由谁生成、由谁查看。

查看解答

例如：“最近为了作出什么决定，你查找过哪些记录？”“取消原因应由谁记录、由谁确认？”候选需要是查看决策所需的取消原因。记录项目、查看权限和实际需要频率仍未确认。单纯增加报表数量不能保证满足需要。

常见误解与反例

只要记录最常提出要求的一位客户的话，需求就完整了。

运营、支持、直接使用和批准角色不同，约束就可能被遗漏。按钮建议与重试导致重复预约之间的差异也是反例。发言数量不能证明代表性、一致性或可实现性。

检查理解

可以把假想访谈发言记录为真实用户观察吗？

查看答案与理由

不可以。

资料的生成方式和证据范围会因此改变。

“按钮大一些就更方便，对吧？”是中立问题吗？

查看答案与理由

不是。

它诱导接受解决方案和肯定回答，应另行询问过去的事件及目的。

如果候选 R1 的取消例外尚未确定，可以写成已批准要求吗？

查看答案与理由

不可以。

必须确认并追溯解释、例外和批准状态。

进一步探索

进阶：设有限需要集合 N、要求集合 R，以及追溯关系 T⊆N×R。如果每个 n 都关联某个 r，则形式上的需要覆盖率是 100%。然而，某个 r 可能只是名义上关联，却不真正满足 n 所需结果；这个反例说明关系的全性并不足以保证语义满足。必须审查关联理由、条件和结果。反过来，未关联的要求也可能具有风险应对或外部约束等新依据，应确认依据类型，而不是直接删除。

小节 3.2

功能需求与非功能需求

只要能预约，即使很慢或重复预约，也算满足需求吗？

预备知识与学习目标

预备知识

  • 功能需求规定系统在什么条件下应当做什么。质量需求规定行为的性能、可靠性等程度及约束。内容和验证条件比分类型名称更重要。
  • 毫秒 ms 是 1/1000 秒。时间测量必须规定开始和结束事件、负载及环境。服务器处理与用户界面完成是不同的时间区间。
  • 自我检查：“预约成功”的结果和“500 ms 以内”的时间条件是两个不同问题。一个可以为真，另一个仍为假。

学习目标

  • 根据情境区分行为需求、质量需求和设计约束。
  • 以可测量的方式写明前提、结果、时间和分母。
  • 构造功能成功与性能或权限条件独立的反例。

同时写明做什么以及做到什么程度

假想 R1 的行为是：经过认证的读者请求预约一本可预约的书时，返回恰好一个有效预约 ID。假想 Q1 规定：在约定环境中的 100 个有效请求里，至少 95 个在 500 ms 内得到正确结果。只写功能要求会让人猜测时间、失败和重复处理的预期；只写质量要求可能把快速但错误的结果计作成功。

功能与非功能是项目采用的分类。拒绝无权限请求也可能是实现安全质量目标的具体功能，因此不能断言两类互斥。指定使用 PostgreSQL 等实现选择属于设计约束，要与结果导向要求区分。合理的外部约束应记录，但不能仅凭用户建议确定必选实现。

固定条件与观察边界

Q1 的自定测试规格为：相同服务器配置、固定 1000 本书的数据、单一客户端串行发出 100 个有效请求，每个请求有独特预约条件；测量从客户端发送请求到收到正确结果的区间。不重试，错误和超时作为缓慢失败计入分母。由于该区间包含网络，不能用服务器处理时间替代。这只是需求示例，没有进行实际测试。

≤500 ms 包含 500，至少 95/100 包含恰好 95%。它不等于所有请求的平均时间≤500 ms。若 94 个请求为 100 ms、6 个为 1000 ms，平均虽为 154 ms，95% 条件仍失败。若 95 个为 500 ms、5 个为 10000 ms，95% 条件通过，但平均为 975 ms。有限样本通过不能保证所有未来负载的分布。

前提和失败同样属于需求

分别写明 R1 的正常前提，如可预约、已认证、没有重复；已有有效预约时返回原 ID 的重试规则；以及书不存在、无权限或内部失败时不改变状态的要求。若从分母删除失败，只计成功，就有利地改变了 Q1。预约标识范围以及并发事件的排序和原子性，需要另行达成共识。

功能正确性检查输入、输出和改变后的状态；时间质量检查同一正确结果的观察时间。可测量并不证明这些数值确有必要。500 ms 和 95% 是供假想利益相关者审查的候选；无障碍、恢复和负载环境也可能需要另行规定。这是应用 NASA 公开检查表的示例，不是对付费质量分类标准的合规判定。

逐步推导的例题

给出 Q1 的假想测试表：100 个正确结果中，94 个用时 400 ms、1 个 500 ms、5 个 900 ms。假设所有结果的功能值正确，计算时间验收是否通过。

  1. 分母是约定的 100 个请求，假设没有缺失或重复行。不能重新选取仅成功结果作为分母。
  2. ≤500 ms 的结果有 94+1=95 个。恰好 500 ms 的一个也计入。
  3. 95/100=95%，因此通过至少 95% 的条件。平均为 (94×400+500+5×900)/100=426 ms。
  4. 平均 426 只是额外计算；判定标准是 95%。这是假想表，不是实际应用或网络性能测量。

假想表通过 Q1。功能正确是题目的独立前提；它不是对未来负载或所有用户体验的验证结果。

用纸笔和正文动手试一试

比较假想表 A：99 个 100 ms 加 1 个 10000 ms；B：94 个 100 ms 加 6 个 1000 ms。计算 Q1 的比例和平均时间，判断两个标准是否相同。

查看提示

把快速请求数量和所有时间之和写在不同列。

查看解答

A 的比例为 99%，通过，平均 199 ms。B 为 94%，失败，平均 154 ms。即使 B 的平均更小，95% 条件仍失败。两标准不等价，也不能把样本测试通过变成对实际总体的保证。

常见误解与反例

非功能需求可以只写成“快速、安全”，通过功能测试就够了。

94%/154 ms 的反例表明，选择不同时间标准会改变判定。必须为“快速”定义区间、负载、失败、分母和边界，并分别确认正确预约结果及时间条件。

检查理解

在 Q1 中，500 ms 是否计入快速请求？

查看答案与理由

计入。

标准定义为≤500 ms。

“拒绝无权限请求”的要求一定不是功能需求吗？

查看答案与理由

不是。它也可以分类为实现安全目标的功能。

分类可因情境和层次重叠，但行为与验证必须明确。

只保留成功结果作为分母、删除错误，Q1 仍相同吗？

查看答案与理由

不相同。

这改变了错误也计入原定 100 个有效请求分母的契约。

进一步探索

进阶：若在有效输入集合 D 上同时要求功能谓词 F 和纯时间谓词 Q_time，则验收谓词为 F∧Q_time。正确但缓慢的实现可以使 F 真、Q_time 假；快速返回错误 ID 的实现可以使 F 假、Q_time 真。只检查一个不是满足结合要求的充分条件。正文的 Q1 还包含正确结果条件，因此快速错误也必须计为失败。应区分这个结合的 Q1 与只看时间的 Q_time。假想表的谓词评估不是对真实时间分布的拟合或产品认证。

小节 3.3

范围与验收标准

所有测试都显示绿色，就表示兑现了这个版本的全部承诺吗？

预备知识与学习目标

预备知识

  • 范围规定本次工作包含和排除哪些结果、功能和环境。排除不表示永远不需要，只表示本次约定的边界。
  • 验收标准是判定需求已满足的观察条件。连接要求 ID 与测试或分析 ID，但不要混淆测试数量与要求满足。
  • 自我检查：在纸上画出边界，本次包括创建和查询预约，不包括付款。创建与查询之间的连接是范围内的契约。

学习目标

  • 明确包含、排除、假设、依赖和变更的边界。
  • 用状态、行为及观察结果制定验收标准。
  • 区分追溯覆盖率、案例通过、整体正确性及对需要的确认。

范围固定系统的承诺

假想版本 V1 包含书 ID 查询、已认证读者的预约创建和取消、本人预约状态查询；排除付款、配送和其他图书馆集成。记录认证服务由外部提供的依赖，同时另行指定谁负责预约访问权限检查。不能因为存在外部依赖，就自动排除接受错误认证信息的问题。

明确假设：对象是同一书 ID 的有效预约，实际复本分配不在范围内。书 ID 或有效状态定义改变，创建、防重复和查询标准的含义也会改变。记录固定需求版本、变更理由、影响及批准状态，才能避免后来偷偷放宽标准来使其通过。

同时观察状态与结果

假想 AC1：已认证读者 u 对书 b 没有有效预约，且 b 可预约时，创建请求完成后返回一个预约 ID r，本人列表中恰好出现一条 (r,u,b,active)。AC2：同一 u,b 已有有效预约时，返回同一个 r，不增加有效记录数。每句话都包含输入、之前状态、行为、结果及状态改变。

还应为失败和取消制定标准。无权限的读者查询他人预约时，返回约定拒绝结果且状态不变。已完成取消的预约不再 active，下一次创建获得新 ID。本顺序模型的案例不能保证并发请求及持久性，需另行列为要求和测试。不能只测试一个正常情况，就写成确认了所有例外。

验收证据的范围

在自定顺序纸面模型中，追踪初始有效数 0→首次创建 1→重试 1→取消 0→再次创建 1，就能看到 AC1/AC2 的预期状态。如果只检查返回字符串 success，一个产生两条重复记录的实现也可能通过；必须同时观察结果 ID 和状态记录数。不要通过改变 ID 来让重试返回值难以比较。

固定的有限验收案例通过，就获得了针对这些案例的证据。它不是对无限输入、故障、并发、未来环境的正确性证明，也不是对实际用户需要适合性的确认。区分“是否符合要求”的验证与“要求是否定义了所需结果”的确认。计算核算、独立文档审查和真实用户测试是不同证据。

逐步推导的例题

假想状态表中 u,b 没有有效预约。规定首次创建获得新 r1，相同条件重试返回 r1，取消使 r1 inactive，再创建获得新 r2。追踪四个顺序事件。

  1. 首次创建返回 r1，active(r1)=真，有效数为 1。AC1 的结果和状态一致。
  2. 重试返回 r1，不创建新记录。保持记录数 1 是 AC2 的关键。
  3. 取消后 r1 为 inactive，有效数为 0。即使保留历史，也要与有效预约区分。
  4. 再次创建返回 r2，有效数为 1。新 ID 契约要求 r2≠r1。历史有 r1,r2 两条，但有效预约只有一条。

返回 r1、r1、取消确认、r2；有效数为 1、1、0、1。这是自定纸面验收模型，不是实际数据库、服务、持久性或并发测试。

用纸笔和正文动手试一试

错误实现首次创建返回 r1，重试返回 r2，并把两者都保留为 active。如果结果只显示 success，是否可能通过？写出检查 AC2 的两个观察值。缺少付款功能是否使 V1 失败？

查看提示

状态数量和 ID 相同性不同于成功字符串。把排除范围与要求对照。

查看解答

只看 success 可能错误地通过。检查返回 ID 与已有 r1 相同、有效记录数保持 1，就能发现违反。付款在 V1 中明确排除，因此单纯缺少付款不违反 V1 要求。如果新增需求把它纳入，则改变版本后再评估。

常见误解与反例

100 个测试通过，就验证了全部要求和实际使用目的。

若 100 个都只看正常创建，就会遗漏重试重复或权限失败。检查范围、追溯和观察值，并记录通过案例的范围。实际用户测试必须另行进行；这里没有进行。

检查理解

重试后有两条有效记录，只要 success 就满足 AC2 吗？

查看答案与理由

不满足。

标准同时要求相同 ID 和记录数不变。

取消历史保留，有效记录数就一定为 1 吗？

查看答案与理由

不是。

历史存在与 active 状态是不同条件。

新增付款要求后，旧 V1 测试通过就验证了新范围吗？

查看答案与理由

没有。

必须重新审查改变后的要求、标准和测试之间的连接。

进一步探索

进阶：设有限要求集合 R、案例集合 T，以及连接关系 C⊆R×T。每条要求都有案例关联时，连接覆盖率为 100%。但若案例不能真正判别该要求，或案例输入只覆盖一部分，就不能推出整体满足。AC2 中只检查 success 的判定器就是反例。更强的论证必须证明输入划分覆盖要求的所有情况，并且每个划分内的推广成立。在顺序预约状态模型中，可以用归纳证明每个读者-书对的有效数为 0 或 1，且每个定义的转移都保持该性质；但这不会自动赋予实际并发数据库实现原子性。
