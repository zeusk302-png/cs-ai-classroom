소단원 10.1

테스트 계층과 계약

화면 버튼이 눌리는 것과 사용자가 원하는 일이 완성되는 것은 같은 검사일까?

준비 개념과 학습 목표

준비 개념

  • 요구사항에 예상 행동을 적을 수 있다.
  • 여러 함수와 저장소가 하나의 시스템을 구성한다.

학습 목표

  • 검사 대상과 목적에 맞게 테스트 수준을 구분한다.
  • 입력·예상 결과·환경으로 검토 가능한 계약 사례를 만든다.

검사 범위의 크기

단위 테스트는 작은 컴포넌트를 분리해 검사한다. 컴포넌트 통합 테스트는 부품 사이 형식과 호출 상호작용을 살핀다. 전체 시스템 테스트는 여러 부품이 만드는 기능과 품질을 시스템 명세에 대조한다.

다른 시스템이나 외부 서비스와의 연결은 시스템 통합의 관심사다. 테스트 수준은 코드 파일의 개수만으로 결정하지 않는다. 무엇을 대상으로 어떤 결함을 찾으려는지와 환경을 함께 적는다.

계약에서 예상 결과로

수용 테스트는 사용자의 실제 필요와 합의한 수용 기준을 만족하는지 판단하는 활동이다. 자동 검사 결과는 일부 기준의 증거가 될 수 있지만 사용자가 이해하고 업무를 수행하는지 관찰한 증거와 같지는 않다.

장바구니 가격 함수는 계산 계약, 저장 API는 저장/읽기 계약, 사용자 구매 흐름은 다른 계약을 가진다. 입력·사전 상태·예상 결과·실패 조건을 정하면 결과가 틀렸을 때 어느 약속을 어겼는지 찾기 쉽다.

비율보다 위험과 증거

작은 테스트는 대개 빠르고 원인을 좁히기 쉽지만 실제 연결과 전체 흐름을 대신하지 못한다. 모든 문제를 넓은 E2E 검사 하나로 다루면 실패 원인을 찾기 어려울 수 있다. 어떤 경계에서 무엇을 확인할지 정한다.

테스트가 설계됨, 실행됨, 통과함, 차단됨은 다른 상태다. 아래 가상 사례는 수준을 분류하는 활동일 뿐 테스트 실행 기록이 아니다. 수준들이 실제 개발에서 시간상 겹칠 수도 있다.

중간 과정을 따라가는 예제

가상 쇼핑 앱의 검사 A는 배송비 함수만, B는 주문 서비스와 DB 저장/읽기, C는 화면 주문부터 영수증, D는 초보 사용자의 합의된 구매 과업을 본다. 각 주 관심사를 분류하라.

  1. A는 계산 부품을 분리해 단위 계약을 본다.
  2. B는 서비스와 저장소 상호작용으로 통합 계약을 본다.
  3. C는 구성된 앱의 전체 흐름으로 시스템 수준의 E2E 검사다.
  4. D는 대표 사용자와 수용 기준의 검증이며 C의 자동 성공으로 대체되지 않는다.

A 단위, B 통합, C 시스템/E2E, D 사용자 수용의 관심사다. 실제 시험을 한 것은 아니다.

힌트 보기

경계값과 바로 양쪽을 고르자.

풀이 보기

각각 3000·0·0원이다. 경계가 ≥임을 드러내며 이 세 사례는 단위 계산 계약의 일부를 검사한다.

오해와 반례

단위 테스트가 모두 통과하면 사용자 수용도 통과다.

연결·전체 흐름·업무 적합성과 사용자가 이해한 행동은 더 넓은 증거를 요구한다. 한 수준의 통과만으로 다른 수준을 추정 완료하지 않는다.

답과 이유 보기

계획과 관찰 증거는 다른 상태다.

한 단계 더

소단원 10.2

E2E·회귀·사용자 검증

고친 기능이 정상이어도 원래 잘되던 기능이 깨질 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 수정 전후 버전이 다르다.
  • 전체 사용자 흐름에는 여러 의존성이 있다.

학습 목표

  • E2E 범위와 환경 가정을 명시한다.
  • 수정 확인·회귀·사용자 검증 증거를 분리한다.

끝에서 끝까지의 시나리오

E2E는 정한 시작에서 끝까지 실제 연결된 흐름을 살피는 접근이다. 로그인→상품 선택→주문 저장→영수증 같은 경로에 입력과 최종 관찰 조건을 적는다. 어떤 외부 서비스를 대체했는지도 범위에 포함한다.

자동 E2E는 화면과 시스템 결과를 확인할 수 있지만 사용자의 사고 과정을 직접 관찰하지는 않는다. 환경·버전·테스트 데이터가 달라지면 원인도 달라질 수 있어 재현 가능한 출발 상태가 필요하다.

수정 확인과 주변 영향

수정 확인은 원래 실패했던 사례가 고쳐졌는지 다시 검사한다. 회귀 검사는 변경이 기존 다른 행동을 해치지 않았는지 살핀다. 두 목적이 겹치는 사례가 있어도 증거의 질문을 구별하면 빠뜨린 경로를 찾기 쉽다.

회귀 범위는 바뀐 코드와 공유 계약을 따라 정한다. 배송비 경계 수정은 일반 주문 계산과 쿠폰을 함께 쓰는 흐름에도 영향을 줄 수 있다. 무관한 테스트를 무조건 반복하거나 하나의 재현 사례만 검사하는 극단을 피한다.

사용자가 실제로 성공했는가

대표 사용자의 과업을 관찰할 때는 성공 조건, 안내 여부, 중단 이유를 정해 기록한다. 사용자가 누른 경로와 이해한 결과는 자동 시나리오가 예상한 경로와 다를 수 있다. 사용자 검증을 계획한 사실은 수행 증거가 아니다.

예제의 관찰 결과는 모두 가상 자료다. 실제 초중고 학생이나 구매 사용자를 실험했다고 표시하지 않는다. 자동 검사와 사용자 관찰을 함께 보아도 선택한 표본 밖의 모든 사용자 성공을 보장하지는 않는다.

중간 과정을 따라가는 예제

가상 수정 v2의 기록은 다음과 같다. 원래 오류인 20000원 배송비 사례는 성공, 25000원 주문도 성공, 쿠폰 적용 영수증은 실패, 사용자 과업은 미실시다. 무엇을 완료라고 보고할까?

  1. 원래 오류 재현 사례가 성공했으므로 해당 수정 확인의 성공 기록이다.
  2. 25000원 사례는 검사한 일반 주문 회귀 범위의 성공이다.
  3. 쿠폰 영수증 회귀 실패가 있어 전체 회귀 통과는 아니다.
  4. 사용자 과업은 미실시이므로 수용 완료로 표시하지 않는다.

수정 확인은 성공했지만 쿠폰 회귀 실패와 사용자 미수행이 남는다. 네 기록은 실제 프로젝트 실행 결과가 아닌 가정 자료다.

힌트 보기

차단을 실행 성공으로 세지 말자.

풀이 보기

오해와 반례

회귀 테스트와 사용자 검증은 같은 이름의 활동이다.

회귀는 변경의 부정적 영향을 확인하는 목적이다. 사용자 검증은 사용자의 필요와 수행을 관찰하는 목적이며 자동 테스트만으로 실제 관찰을 수행했다고 할 수 없다.

소단원 10.3

결함 분류와 재현

“안 돼요”를 다른 사람이 다시 확인할 수 있는 기록으로 바꾸려면 무엇을 적어야 할까?

준비 개념과 학습 목표

준비 개념

  • 예상값과 관찰값을 구별한다.
  • 결함의 영향과 처리 순서는 다를 수 있다.

학습 목표

  • 최소 재현과 환경 정보를 포함한 보고를 만든다.
  • 관찰·원인 가설·심각도·우선순위를 구별한다.

같은 출발 상태로 재현하기

결함 보고에는 대상 버전과 환경, 초기 데이터, 입력 순서, 예상 결과와 실제 결과가 필요하다. 재현에 필요 없는 개인정보는 넣지 않고 대신 동일 조건을 만드는 가상 자료를 쓸 수 있다.

최소 재현은 실패를 보존하면서 불필요한 단계와 데이터를 줄이는 과정이다. 간헐적 실패가 사라졌다면 해결됐다고 단정하지 말고 재현 빈도와 변경한 조건을 기록한다. 시간·동시 작업처럼 중요한 조건을 먼저 지우지 않는다.

영향과 급함을 나누기

심각도는 사용자나 요구사항에 미치는 영향의 크기를 나타낸다. 우선순위는 업무 위험·범위·시점 등을 고려한 처리 순서다. 둘의 분류 기준을 팀이 정하고 보고자가 절대적인 숫자 체계로 가정하지 않는다.

데이터 손실은 큰 영향일 수 있고 공개 행사 화면의 작은 오타는 영향이 작아도 행사 전에 빨리 처리할 수 있다. 관찰한 이상이 코드 결함인지 잘못된 기대값인지 설정 문제인지 분석 전에는 원인 가설로 구별한다.

보고에서 닫힘까지

접수→분석→수정→재확인→닫힘은 한 예시 흐름이며 실제 팀 정책을 따른다. 중복·재현 불가·수정 보류도 이유와 상태를 기록한다. 수정했다고 적는 것과 재현 사례가 정상임을 확인한 것은 다르다.

로그나 화면 증거에는 관련 시각·식별자를 포함하면 추적이 쉽다. 비밀 토큰과 개인 내용은 공개 보고에 노출하지 않는다. 예제의 원인과 결과는 가정 기록이며 실제 서비스 오류를 관찰한 주장이 아니다.

중간 과정을 따라가는 예제

가상 v2.1 배송비 함수의 계약은 주문액≥20000이면 무료다. 내부 조건은 >20000이라고 주어졌고, 19999·20000·20001을 손으로 평가한다. 결함 기록을 작성하라.

  1. 계약 기대값은 차례로 3000·0·0원이다.
  2. 주어진 > 조건의 가상 실제값은 3000·3000·0원이다.
  3. 차이는 20000원 한 경계에서만 드러난다.
  4. 최소 기록: v2.1, 초기 주문액 20000원, 계산 요청, 기대 0원, 주어진 코드 모형 결과 3000원. 코드 조건은 주어진 근거이고 실제 서비스 관찰은 아니다.

20000원 경계 불일치를 재현하는 종이 보고다. 19999와 20001 비교가 경계 문제임을 좁힌다.

풀이 보기

항상이라고 하면 안 된다. 관찰 빈도는 3/10=30%다. 버전·환경·데이터·순서·시각과 성공한 7회의 조건 차이를 기록해야 원인을 좁힐 수 있다.

오해와 반례

우선순위가 높으면 항상 심각도도 가장 높다.

행사 직전 오타는 빨리 처리할 수 있지만 데이터 손실과 같은 영향 등급은 아닐 수 있다. 영향과 일정상 처리 순서를 별도 기준으로 기록한다.
