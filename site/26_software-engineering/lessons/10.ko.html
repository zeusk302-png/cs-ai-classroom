소단원 10.1

테스트 계층과 계약

화면 버튼이 눌리는 것과 사용자가 원하는 일이 완성되는 것은 같은 검사일까?

준비 개념과 학습 목표

준비 개념

  • 요구사항에 예상 행동을 적을 수 있다.

  • 여러 함수와 저장소가 하나의 시스템을 구성한다.

학습 목표

  • 검사 대상과 목적에 맞게 테스트 수준을 구분한다.

  • 입력·예상 결과·환경으로 검토 가능한 계약 사례를 만든다.

서로 맞는 부품 두 개를 연결했는데 금액이 백 배가 될 수 있을까?

새 견적 서비스는 소수점 없는 자체 금액 단위를 쓴다. 화면 입력의 정수 가격 p는 큰 단위이고 수량 n은 양의 정수다. 경계 계약은 요청의 amount_minor가 100×p×n인 작은 단위 정수여야 한다고 정한다. 저장소는 받은 amount_minor를 그대로 저장한다. p=3, n=2이면 기대 저장값은 600이다. 화면이 잘못하여 6을 보내도 저장소 자체 계약만 보면 6을 정확히 저장했을 수 있다.

단위 성공을 이어 붙여도 연결 계약의 단위 변환은 저절로 검사되지 않는다. 화면 대역은 임의 요청에 OK를 돌려주고 저장소 단위 시험은 600을 직접 넣어 읽었다면 둘 다 정상일 수 있다. 두 모듈을 연결한 시험에서 실제 전송 필드와 저장값을 같은 요청 식별자로 대조해야 변환 누락을 찾는다. 이 표의 실제라는 말은 설계상 관찰할 경계를 뜻하며 지금 실행한 서비스 증거가 아니다.

응답 200이나 성공 문구만 보는 시스템 시험도 저장된 금액을 확인하지 않으면 같은 결함을 놓친다. 수용 과업에는 사용자가 예상 금액을 이해하는지라는 별도 기준이 있다. 통합 범위의 가상 오류를 모든 저장소 구현 결함으로 진단하거나 자동 시스템 통과를 사용자 수용 완료로 보고하지 않는다. 모든 새 시험은 계획과 종이 계약 대조다.

검사 범위의 크기

단위 테스트는 작은 컴포넌트를 분리해 검사한다. 컴포넌트 통합 테스트는 부품 사이 형식과 호출 상호작용을 살핀다. 전체 시스템 테스트는 여러 부품이 만드는 기능과 품질을 시스템 명세에 대조한다.

다른 시스템이나 외부 서비스와의 연결은 시스템 통합의 관심사다. 테스트 수준은 코드 파일의 개수만으로 결정하지 않는다. 무엇을 대상으로 어떤 결함을 찾으려는지와 환경을 함께 적는다.

계약에서 예상 결과로

수용 테스트는 사용자의 실제 필요와 합의한 수용 기준을 만족하는지 판단하는 활동이다. 자동 검사 결과는 일부 기준의 증거가 될 수 있지만 사용자가 이해하고 업무를 수행하는지 관찰한 증거와 같지는 않다.

장바구니 가격 함수는 계산 계약, 저장 API는 저장/읽기 계약, 사용자 구매 흐름은 다른 계약을 가진다. 입력·사전 상태·예상 결과·실패 조건을 정하면 결과가 틀렸을 때 어느 약속을 어겼는지 찾기 쉽다.

비율보다 위험과 증거

작은 테스트는 대개 빠르고 원인을 좁히기 쉽지만 실제 연결과 전체 흐름을 대신하지 못한다. 모든 문제를 넓은 E2E 검사 하나로 다루면 실패 원인을 찾기 어려울 수 있다. 어떤 경계에서 무엇을 확인할지 정한다.

테스트가 설계됨, 실행됨, 통과함, 차단됨은 다른 상태다. 아래 가상 사례는 수준을 분류하는 활동일 뿐 테스트 실행 기록이 아니다. 수준들이 실제 개발에서 시간상 겹칠 수도 있다.

기대600과 불일치

같은 요청을 식별하고 명세의 100배 변환을 기대값에 사용한다. 개별 단위 사례는 서로 독립된 시작 상태이며 저장600 시험이 화면 요청6의 기록을 덮어 수정한 것은 아니다.

중간 과정을 따라가는 예제

가상 쇼핑 앱의 검사 A는 배송비 함수만, B는 주문 서비스와 DB 저장/읽기, C는 화면 주문부터 영수증, D는 초보 사용자의 합의된 구매 과업을 본다. 각 주 관심사를 분류하라.

  1. A는 계산 부품을 분리해 단위 계약을 본다.

  2. B는 서비스와 저장소 상호작용으로 통합 계약을 본다.

  3. C는 구성된 앱의 전체 흐름으로 시스템 수준의 E2E 검사다.

  4. D는 대표 사용자와 수용 기준의 검증이며 C의 자동 성공으로 대체되지 않는다.

A 단위, B 통합, C 시스템/E2E, D 사용자 수용의 관심사다. 실제 시험을 한 것은 아니다.

조건을 바꾸어 비교하기

저장소가 맞아도 연결이 틀린다

잘못된 전송 6을 저장소가 정확히 6으로 보존했다. 저장소의 복사 계약과 전체 금액 계약을 판정하라.

  1. 받은 정수를 그대로 저장하는 저장소 계약은 이 사례에서 맞는다.

  2. 전체 경계 계약은 100×3×2=600을 요구하므로 화면→저장 경계는 틀렸다.

저장 정확성의 성공과 연결 단위의 실패가 동시에 가능하다.

비교할 점

한 통합 실패만으로 모든 부품이 틀렸다고 진단하지 않는다.

응답 검사와 읽기 검사의 관찰 범위

정상과 변형 모두 응답 OK다. p=4,n=1에서 응답만 검사와 저장 읽기를 비교하라.

  1. 독립 기대 저장값은 100×4×1=400이다.

  2. 정상은 400을 저장하고 변형은 4를 저장하지만 응답 문구는 동일하다.

응답만 보면 구별하지 못한다. 같은 요청의 저장값을 대조하면 정상 400과 변형 4를 구별한다.

비교할 점

관찰 추가는 실제 저장소와 조회 경로를 시험 범위에 포함한다.

종이와 본문으로 직접 해보기

배송비 함수가 주문액 20000원 이상이면 0원, 미만이면 3000원이다. 19999·20000·20001의 예상값을 적어라.

힌트 보기

경계값과 바로 양쪽을 고르자.

풀이 보기

각각 3000·0·0원이다. 경계가 ≥임을 드러내며 이 세 사례는 단위 계산 계약의 일부를 검사한다.

오해와 반례

단위 테스트가 모두 통과하면 사용자 수용도 통과다.

연결·전체 흐름·업무 적합성과 사용자가 이해한 행동은 더 넓은 증거를 요구한다. 한 수준의 통과만으로 다른 수준을 추정 완료하지 않는다.

연습 1 · 값과 상태 예측

정상 변환에서 (p,n)=(1,3)과(5,2)의 저장 기대값을 구하라. 저장소에 이미 작은 단위 300을 직접 입력한 단위 시험에도 100을 다시 곱할까?

힌트 1

화면 경계와 저장소 경계의 입력 단위가 다르다.

힌트 2

p×n은 큰 단위 금액이고 amount_minor는 이미 작은 단위다.

풀이와 답 확인

  1. 화면 입력의 기대 저장값은 첫 입력에서 300, 둘째 입력에서 1000이다.

  2. 저장소 직접 입력 300은 300 그대로 보존한다.

첫 화면 입력은 300, 둘째 화면 입력은 1000을 저장해야 한다. 저장소에 작은 단위 300을 직접 넣은 사례는 300을 보존한다.

흔한 오답에서 다시 생각하기

필드 이름과 관계없이 모든 가격은 저장할 때100배다.

변환 책임은 경계 계약에 있으며 같은 값을 두 번 변환하면 안 된다.

연습 2 · 오류 찾아 고치기

화면 대역이 모든 요청에 OK를 반환해 변환 누락을 놓쳤다. 대역 시험과 실제 연결 시험에 각각 관찰 하나를 추가하라.

힌트 1

대역에는 전송 인자도 보인다.

힌트 2

실제 연결에는 저장 후 읽을 식별자가 필요하다.

풀이와 답 확인

  1. 대역 시험에는 전송 인자 amount_minor가 600이어야 한다는 정확 조건을 추가한다.

  2. 별도 연결 시험에서 요청 ID와 저장값 600을 조회해 매칭한다.

인자 확인은 화면 계약의 증거이고 실제 연결은 저장소의 형식/보존까지 더 넓게 검사한다.

흔한 오답에서 다시 생각하기

대역이600을 승인하면 모든 실제 저장소 연결도 이미 확인됐다.

대역은 실제 스키마/연결/저장 동작을 실행하지 않는다.

연습 3 · 직접 만들어 보기

새 할인 정책이 경계 계약을 바꿀 때 단위·통합·시스템·수용의 증거 장부를 구성하라. 실제 사용자는 모집하지 않는다.

힌트 1

각 행에 입력 단위와 독립 기대 결과를 쓴다.

힌트 2

자동 상태와 사용자 이해의 기준을 분리한다.

풀이와 답 확인

  1. 계산 부품에는 할인 산술,연결에는 필드/단위,시스템에는 같은 주문의 화면과 저장 일치,수용에는 합의 과업과 개입 기록을 적는다.

  2. 각 검사 버전/초기 상태/대체 의존성/실행 여부를 붙이고 아직 모두 계획이라고 표시한다.

파일 개수 대신 대상 계약과 환경으로 수준을 설명한다.

흔한 오답에서 다시 생각하기

같은 경계 사례를 여러 수준에 적으면 네 활동을 모두 수행했다.

계획의 배치와 실제 관찰은 별개다.

연습 4 · 선택 심화

저장값600은 맞지만 화면이 작은 단위를 큰 단위로 그대로 표시해600이라고 보인다. 연결 저장 성공으로 전체 요구를 승인할 수 있나?

E2E·회귀·사용자 검증

고친 기능이 정상이어도 원래 잘되던 기능이 깨질 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 수정 전후 버전이 다르다.

  • 전체 사용자 흐름에는 여러 의존성이 있다.

학습 목표

  • E2E 범위와 환경 가정을 명시한다.

  • 수정 확인·회귀·사용자 검증 증거를 분리한다.

재시도해서 녹색이 됐으면 첫 실패는 없어졌을까?

자체 여섯 E2E 사례 A–F의 가상 장부를 사용한다. A/B는 첫 시도 통과, C는 첫 실패 뒤 재시도 통과, D는 두 시도 실패, E는 환경 차단으로 시도 없음, F는 첫 시도 통과다. 계획 사례 수는 6, 실행된 서로 다른 사례는5, 총 시도는7이다. 사례 수와 시도 수는 다른 분모다. 이 장부는 실제 브라우저 실행 결과가 아니다.

Playwright의 분류처럼 첫 시도 통과와 재시도 통과를 구별하면 첫 통과3개, 재시도 통과1개, 끝까지 실패1개가 된다. 재시도 통과는 첫 실패의 원인 제거 증명이 아니다. 실패 후 새 worker가 생성돼도 서버의 외부 상태가 자동 초기화된다는 계약을 추정하지 않는다. 사례마다 독립 주문 ID와 시작 상태를 설계하고 첫 실패 trace도 보존할 계획을 세운다.

검사 조건을 반복 관찰하는 assertion과 전체 테스트 재실행은 또 다른 반복이다. 아래 자체 상태 타임라인에서 화면은0초에 pending,2초에 done이 되고 계속 done이다. 1초의 즉시 비교는 pending을 얻지만 0/1/2/3초에 관찰하고3초까지 done을 기다리는 지정 검사라면2초에 조건을 찾는다. 이는 공식 도구의 고정 polling 간격을 주장하는 예가 아니라 단순 관찰 모형이다. 대기가 성공해도 같은 주문 ID·정확 결과인지 확인해야 한다.

먼저 확인할 개념
  • 실행/통과/차단의 분모

    다른 사례 수와 재시도 횟수를 구별한다.

  • 자동 검사의 증거 범위

    시스템 관찰을 실제 사용자 성공으로 확대하지 않는다.

끝에서 끝까지의 시나리오

E2E는 정한 시작에서 끝까지 실제 연결된 흐름을 살피는 접근이다. 로그인→상품 선택→주문 저장→영수증 같은 경로에 입력과 최종 관찰 조건을 적는다. 어떤 외부 서비스를 대체했는지도 범위에 포함한다.

자동 E2E는 화면과 시스템 결과를 확인할 수 있지만 사용자의 사고 과정을 직접 관찰하지는 않는다. 환경·버전·테스트 데이터가 달라지면 원인도 달라질 수 있어 재현 가능한 출발 상태가 필요하다.

수정 확인과 주변 영향

수정 확인은 원래 실패했던 사례가 고쳐졌는지 다시 검사한다. 회귀 검사는 변경이 기존 다른 행동을 해치지 않았는지 살핀다. 두 목적이 겹치는 사례가 있어도 증거의 질문을 구별하면 빠뜨린 경로를 찾기 쉽다.

회귀 범위는 바뀐 코드와 공유 계약을 따라 정한다. 배송비 경계 수정은 일반 주문 계산과 쿠폰을 함께 쓰는 흐름에도 영향을 줄 수 있다. 무관한 테스트를 무조건 반복하거나 하나의 재현 사례만 검사하는 극단을 피한다.

사용자가 실제로 성공했는가

대표 사용자의 과업을 관찰할 때는 성공 조건, 안내 여부, 중단 이유를 정해 기록한다. 사용자가 누른 경로와 이해한 결과는 자동 시나리오가 예상한 경로와 다를 수 있다. 사용자 검증을 계획한 사실은 수행 증거가 아니다.

예제의 관찰 결과는 모두 가상 자료다. 실제 초중고 학생이나 구매 사용자를 실험했다고 표시하지 않는다. 자동 검사와 사용자 관찰을 함께 보아도 선택한 표본 밖의 모든 사용자 성공을 보장하지는 않는다.

“안 돼요”를 다른 사람이 다시 확인할 수 있는 기록으로 바꾸려면 무엇을 적어야 할까?

학습 목표

두 번 제출해야만 실패한다면 한 번만 남기는 최소화가 성공일까?

새 예약 종이 모형에서 초기 좌석은1,성공 예약 수는0이다. 정상 계약은 좌석 확인과 차감·예약 기록을 나뉘지 않는 한 승인 사건으로 처리해 성공 한 개만 허용한다. 잘못된 구현은 읽기와 쓰기를 분리한다. A/B가 각각1을 읽고 각각 자신의 읽은 값에서1을 빼0을 저장하면 최종 좌석은0이지만 두 예약 성공을 기록한다. 좌석이 음수가 아니라는 검사만으로 중복 성공을 놓친다.

실패 재현 장부는 초기 좌석1과 A읽기→B읽기→A저장/성공→B저장/성공이라는 순서를 포함한다. B를 지우면 A만 성공하고,읽기/승인을 직렬로 바꾸면 B는0을 보고 거절한다. 실패가 사라진 최소 후보는 원래 결함의 해결 증거가 아니라 필수 겹침 조건을 제거한 후보일 수 있다. 여기서는 스레드·DB·API를 실행하지 않고 지정 사건을 추적한다.

영향은 초과 예약이고 코드 원인은 원자성 누락이라는 가설을 둘 수 있지만 실제 서비스의 잠금 결함으로 확정하지 않는다. 두 버전의 모형·같은 초기 상태·계약·관찰을 함께 기록해야 수정 확인과 회귀를 연결할 수 있다. 공개 보고에는 실제 개인정보 대신 가상 ID A/B와 필요한 시각·사건만 둔다. 로그의 마지막 좌석0과 성공 수2는 서로 다른 관찰이며 재시도/동시 요청을 구별하는 자료도 필요하다.

같은 출발 상태로 재현하기

결함 보고에는 대상 버전과 환경, 초기 데이터, 입력 순서, 예상 결과와 실제 결과가 필요하다. 재현에 필요 없는 개인정보는 넣지 않고 대신 동일 조건을 만드는 가상 자료를 쓸 수 있다.

최소 재현은 실패를 보존하면서 불필요한 단계와 데이터를 줄이는 과정이다. 간헐적 실패가 사라졌다면 해결됐다고 단정하지 말고 재현 빈도와 변경한 조건을 기록한다. 시간·동시 작업처럼 중요한 조건을 먼저 지우지 않는다.

영향과 급함을 나누기

심각도는 사용자나 요구사항에 미치는 영향의 크기를 나타낸다. 우선순위는 업무 위험·범위·시점 등을 고려한 처리 순서다. 둘의 분류 기준을 팀이 정하고 보고자가 절대적인 숫자 체계로 가정하지 않는다.

데이터 손실은 큰 영향일 수 있고 공개 행사 화면의 작은 오타는 영향이 작아도 행사 전에 빨리 처리할 수 있다. 관찰한 이상이 코드 결함인지 잘못된 기대값인지 설정 문제인지 분석 전에는 원인 가설로 구별한다.

보고에서 닫힘까지

접수→분석→수정→재확인→닫힘은 한 예시 흐름이며 실제 팀 정책을 따른다. 중복·재현 불가·수정 보류도 이유와 상태를 기록한다. 수정했다고 적는 것과 재현 사례가 정상임을 확인한 것은 다르다.

로그나 화면 증거에는 관련 시각·식별자를 포함하면 추적이 쉽다. 비밀 토큰과 개인 내용은 공개 보고에 노출하지 않는다. 예제의 원인과 결과는 가정 기록이며 실제 서비스 오류를 관찰한 주장이 아니다.

중간 과정을 따라가는 예제

가상 v2.1 배송비 함수의 계약은 주문액≥20000이면 무료다. 내부 조건은 >20000이라고 주어졌고, 19999·20000·20001을 손으로 평가한다. 결함 기록을 작성하라.

  1. 계약 기대값은 차례로 3000·0·0원이다.

  2. 주어진 > 조건의 가상 실제값은 3000·3000·0원이다.

  3. 차이는 20000원 한 경계에서만 드러난다.

  4. 최소 기록: v2.1, 초기 주문액 20000원, 계산 요청, 기대 0원, 주어진 코드 모형 결과 3000원. 코드 조건은 주어진 근거이고 실제 서비스 관찰은 아니다.

20000원 경계 불일치를 재현하는 종이 보고다. 19999와 20001 비교가 경계 문제임을 좁힌다.

연습 1 · 값과 상태 예측

초기 좌석이 2이고 세 요청 A/B/C가 모두 2를 읽은 뒤 각각 1을 저장하고 성공을 기록하는 동일 변형이면 최종 상태는?

힌트 1

각 쓰기는 현재값이 아닌 자신이 읽은 값 2에서 계산한다.

힌트 2

초기 용량과 성공 수를 함께 본다.

풀이와 답 확인

  1. 좌석은 각 쓰기 뒤 1이므로 최종 값도 1이다.

  2. 성공 수 3은 초기 용량 2를 넘으며 남은 좌석과의 보존 관계도 틀리다.

최종 좌석은 1이고 성공 수는 3이다. 남음과 성공의 합 4는 초기 좌석 2와 맞지 않는다.

흔한 오답에서 다시 생각하기

최종 좌석이 1개 남았으니 실패는 없다.

최종 표시 한 개로 모든 업무 효과를 검사하지 못한다.

연습 2 · 오류 찾아 고치기

보고서가 A/B 식별자와 순서를 지우고 좌석 0만 남겨 재현에서 실패가 없다고 닫았다. 수정할 기록은?

힌트 1

중복과 겹침을 구별할 식별자가 필요하다.

힌트 2

기대 성공 수 1과 관찰 성공 수 2를 다시 적는다.

풀이와 답 확인

  1. 가상 두 요청 ID, 초기 좌석 1, 두 읽기가 두 승인보다 앞선 순서, 예약 성공 장부를 복원한다.

  2. 모형상 기대 성공 수 1과 관찰 성공 수 2를 기록하고 원인 가설을 실제 결함 확정과 분리한다.

필수 조건이 사라진 재현 불가를 수정 확인 통과로 처리하지 않는다.

연습 3 · 직접 만들어 보기

정상 승인 모형으로 바꾼 뒤 확인과 회귀의 네 계획을 설계하라.

힌트 1

원래 초기 좌석 1에서 두 요청이 겹치는 사례를 남긴다.

힌트 2

빈 좌석과 정상 용량 2도 살핀다.

풀이와 답 확인

  1. 초기 좌석 1에서 두 요청이 겹치면 성공 1개, 거절 1개, 남은 좌석 0을 확인한다.

  2. 초기 좌석 1의 한 요청은 성공 1개와 남음 0, 초기 좌석 0의 한 요청은 거절과 성공 0개, 초기 좌석 2의 두 승인은 성공 2개와 남음 0이라는 회귀를 계획한다.

상태 변경과 기록이 한 승인이라는 모형 계약으로 예상한다. 실제 서비스 검사는 미수행이다.

초기 좌석 0에서 모두 거절하는 수정이면 모든 회귀도 통과한다.

정상 용량에서 승인해야 하는 성공 계약이 남는다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

합성 동일 환경의 10시도 중 겹침 순서가 3번이고 그 3번만 반례를 보였다. 실패율을 모든 요청의 30%라고 보고할 수 있나?

힌트 1

시도 장부와 요청 장부의 분모가 다르다.

힌트 2

관찰하지 않은 새 환경에는 일반화하지 않는다.

풀이와 답 확인

  1. 관찰된 시도 10개에서 실패 3개, 즉 3/10=30%라고 적는다.

  2. 관찰된 겹침 3개 내의 실패 3/3=100%는 조건부율이다. 시도별 요청 수와 환경이 없으면 전체 요청 실패율은 계산하지 않는다.

두 비율은 합성 관찰 장부의 서로 다른 조건이다. 실제 빈도 측정이 아니다.

분모와 조건을 버리면 관찰 범위를 과장한다.

모든 사례는 독립 초기 상태다. 큰 단위 p=3, n=2를 작은 단위 amount_minor로 저장하는 계약에서 정상 값 600과 변형 값 6이 모두 OK 응답을 받으면 어떤 경계 검사가 필요한가? 가상 A–F 장부에서 계획 사례 6개, 실행 사례 5개, 전체 시도 7개와 최종 성공 사례 4개를 각 분모로 보고하라. 초기 좌석 1에서 A/B가 모두 1을 읽고 각각 0을 저장하고 성공을 기록하는 변형의 최종 좌석과 성공 수를 정상 승인과 대조하라. B를 삭제한 후보를 수정 증거로 인정할 수 있는지도 답하라. 실제 서비스·브라우저·사용자 시험은 실행하지 않는다.

힌트 1

응답 문구와 같은 요청의 저장 금액을 비교하고 사례 수와 시도 수를 나눈다.

힌트 2

초기 용량과 성공 수의 관계를 확인하고 재현 최소화에도 겹침 조건을 남긴다.

풀이와 답 확인

  1. 100×3×2=600을 독립 기대값으로 만든다. 전송 amount_minor와 같은 주문 ID의 저장값을 확인하여 변형 6을 구별한다. 저장소 직접 입력에는 다시 100을 곱하지 않는다.

  2. 실행률은 5/6≈83.33%, 계획 대비 성공은 4/6≈66.67%, 실행 사례 대비 성공은 4/5=80%, 성공 시도 비율은 4/7≈57.14%다. 첫 통과 3개와 재시도 통과 1개를 별도로 보존한다.

  3. 분리 변형의 좌석은 0이고 성공 수는 2라서 초기 용량 1을 초과한다. 정상 원자 승인 모형은 성공 1개, 거절 1개, 좌석 0이다.

  4. B를 지운 후보는 좌석 0, 성공 수 1로 실패가 사라진다. 그러나 두 요청의 겹침 조건도 제거했으므로 원래 구현의 수정 통과 증거가 아니다.

연결 금액·재시도 장부·업무 효과 수와 겹침을 서로 다른 증거로 기록한다. 모두 자체 종이 모형이며 실제 통합/E2E/수용 시험 완료가 아니다.

해결한 뒤 점검할 것

  • 입력 단위와 저장 기대값 및 대역 범위를 명시한다.

  • 사례·시도의 분모와 첫 실패 이력을 보존한다.

  • 마지막 좌석과 성공 업무 수의 관계를 판정한다.

  • 최소 후보의 실패 보존과 실제 수정 확인을 구별한다.
