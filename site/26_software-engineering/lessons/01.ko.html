소단원 1.1

개발 생명주기

도서 대출 버튼이 한 번 작동하면 개발은 끝났다고 할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 프로그램 목적은 누구의 어떤 문제를 해결하는지 적는 것이다. 예: 이용자가 책의 대출 상태를 확인한다.

  • 요구는 만족해야 할 조건, 구현은 그 조건을 만족하도록 만든 코드와 설정이다.

  • 자가진단: '대출하면 재고가 1 줄어든다'와 '검토한 설계 문서'는 각각 동작 요구와 개발 산출물이다.

학습 목표

  • 생명주기를 생성부터 운영·변경·폐기까지의 활동으로 설명한다.

  • 요구·설계·구현·검증·운영 사이의 피드백을 추적한다.

  • 활동 종류와 활동을 배치하는 프로세스 모델을 구분한다.

실행파일을 되돌렸는데 새 데이터가 남아 있다면 정말 복구된 것일까?

원본 대출 앱의 정책 변경을 저장 형식의 변화까지 확장한다. 자체 v1은 대출마다 due_day 정수만 읽고, v2는 due_day와 policy_version을 읽는다고 정한다. v2가 새 필드를 추가하되 due_day도 보존하고, v1은 모르는 필드를 무시하는 입력 계약이면 새 레코드를 v1도 읽을 수 있다. 반대로 v2가 due_day를 지우고 문자열 due_date만 쓰면 v1 실행파일 복구만으로 읽기 계약을 복원하지 못한다. 실제 데이터베이스 마이그레이션을 수행한 사례가 아니다.

따라서 변경 카드는 요구뿐 아니라 데이터 형식, 읽기·쓰기 계약, 변환, 이전 버전 복귀 조건에 이어진다. 점진 변경의 자체 계획은 먼저 두 형식을 읽는 코드를 준비하고, 새 쓰기를 적용하며, 기존 자료를 변환하고, 이전 읽기 의존이 없다는 증거를 확인한 뒤 옛 필드를 없애는 순서다. 이 순서만 적었다고 운영 중 동시 쓰기나 실패 복구가 검증된 것은 아니다.

폐기도 생명주기 활동이다. 가상 알림 서비스가 새 요청을 중단했어도 이미 접수한 요청 세 개가 남았다면 접수 중단과 처리 종료는 다른 시점이다. 각 요청을 완료·취소·이관 중 하나로 처리하고, 보존할 자료와 접속 권한 종료를 확인하는 계획이 필요하다. 실제 법률상 보존 기간은 이 단원에서 정하지 않으며 사용자 필요와 적용 정책을 확인하는 별도 판단으로 둔다.

먼저 확인할 개념
  • 변경 영향과 연결된 활동

    신규 기능·저장 자료·운영 책임을 연결한다.

  • 버전과 증거 범위

    계획한 복귀와 실제 복귀 성공을 구별한다.

생명주기는 코드 작성보다 넓다

소프트웨어 생명주기는 필요를 이해하고 제품을 만들며 운영·변경하고 사용을 끝내는 동안 수행하는 활동의 흐름이다. 요구 분석은 어떤 문제와 조건을 해결할지 정하고, 설계는 책임·데이터·인터페이스를 정하며, 구현은 이를 코드와 설정으로 만든다. 시험과 검토는 산출물이 요구와 사용 목적에 맞는지 증거를 만든다.

운영에서는 실제 환경의 실패·사용 방식·변경 필요를 관찰한다. 유지보수는 결함 수정뿐 아니라 요구 변화와 환경 변화에 적응하는 활동을 포함한다. 도서 대출 앱의 정책이 바뀌면 요구·설계·코드·시험·운영 설명을 함께 다시 확인해야 한다. 개발을 '일단 실행파일 만들기'로만 정의하면 이 책임을 놓친다.

활동 목록과 수행 순서는 다른 질문이다

요구→설계→구현→시험을 한 번만 수행하고 끝내는 것이 모든 프로젝트의 유일한 과정은 아니다. 계획 중심 방식은 단계와 검토 시점을 상대적으로 명확히 두고, 반복 방식은 작은 기능을 여러 번 요구·설계·구현·검증한다. 어느 방식에서도 요구의 타당성과 변경 결과를 확인할 책임은 사라지지 않는다.

선택은 위험·변경 가능성·팀 규모·운영 제약에 따라 달라진다. 초기에 사용자 화면을 종이로 검토하면 실제 데이터베이스를 만들기 전에 오해를 발견할 수 있다. 반대로 데이터 손실 위험이 큰 변경은 짧은 반복이라는 이유로 복구 설계와 충분한 검증을 생략해서는 안 된다. 여기의 설명은 공개 교육·NASA 자료에서 활동 개념을 확인한 것이며 특정 ISO 생명주기 표준의 조항 준수를 인증하지 않는다.

변경은 연결된 산출물에 영향을 준다

예를 들어 대출 기간을 모든 사용자 14일에서 학생 14일·교사 28일로 바꾸면 사용자 종류와 만료일 계산 계약이 추가된다. 설계의 정책 책임을 확인하고 코드의 조건을 수정하며 두 종류와 경계 날짜의 시험을 만든다. 운영 중 기존 대출에 소급 적용할지 정하지 않으면 같은 새 코드도 현장에서 혼란을 만들 수 있다.

이처럼 요구의 식별자와 관련 설계·구현·시험을 연결하는 것을 추적성이라고 한다. 변경 영향은 코드 줄뿐 아니라 저장 데이터, 안내문, 배포·롤백 절차까지 포함할 수 있다. 모든 변경에 무조건 같은 분량의 문서를 만들기보다 위험과 재현에 필요한 내용을 구체적으로 남긴다.

자동 복원 아님

코드와 데이터 상태의 공동 확인

가능이라는 표시는 명시한 읽기 계약의 손판정이다. 실제 파일 복구·배포·호환성 시험 통과를 뜻하지 않는다. 자료 복원이 가능한지도 변환의 정보 보존 조건으로 따로 확인한다.

중간 과정을 따라가는 예제

도서 앱의 정책을 '모두 14일'에서 '학생 14일, 교사 28일'로 바꾼다. 기존 대출은 원래 만료일을 유지한다고 가정한다. 필요한 활동을 네 단계로 분해하라.

  1. 요구: 학생/교사 분류와 신규 대출만 새 정책 적용을 명시한다.

  2. 설계: 대출 시점의 만료일을 저장하고 정책 계산 책임을 한 곳에 둔다.

  3. 구현·검증: 신규 학생 14일, 신규 교사 28일, 기존 대출 불변 사례를 만든다.

  4. 운영: 변경 시각·버전·안내와 실패 시 이전 버전으로 돌아갈 조건을 기록한다.

성공 조건은 새 버튼 실행뿐 아니라 신규 규칙·기존 데이터 유지·운영 안내의 일관성이다. 이 단계는 가상 설계이며 실제 앱 배포는 하지 않았다.

조건을 바꾸어 비교하기

필드를 추가한 변경과 교체한 변경

v1은 due_day 필수/추가 필드 무시다. v2 레코드 A={due_day:30,policy_version:2}와 B={due_date:"day30"}의 v1 복귀를 비교하라.

  1. A에는 v1이 요구하는 due_day가 있다.

  2. B에는 due_day가 없으므로 이전 실행파일만으로는 입력 계약을 만족하지 못한다.

A는 지정 계약상 읽기 가능, B는 불가다. 실제 호환성 검증은 미수행이다.

비교할 점

원본 정책 값 변경과 달리 저장 형식의 복귀 책임을 추가한다.

접수 중단과 종료 완료의 차이

가상 서비스가 새 접수를 막았지만 접수된 Q1/Q2/Q3 중 Q1만 완료했다. 종료 보고에 무엇이 남는가?

  1. 신규 접수는 0이지만 미처리 요청은 두 개다.

  2. Q2와 Q3의 완료·취소·이관 및 통지 상태를 확인해야 한다.

접수 중단 완료와 기존 요청 처리 종료 미완료를 따로 보고한다.

비교할 점

사용 종료를 하나의 버튼 상태로 축약하지 않는다.

종이와 본문으로 직접 해보기

종이에 요구·설계·코드·시험·운영 카드 다섯 장을 놓는다. '교사 기간을 21일로 다시 변경' 카드에서 영향을 받는 카드로 화살표를 그리고 변경 후 확인할 사례 하나를 각 카드에 적어라.

힌트 보기

기존 대출 소급 여부가 먼저 정해져야 시험 기대값을 정할 수 있다.

풀이 보기

요구의 기간을 21일로 바꾸고 설계의 정책 계산 책임, 코드의 새 상수/규칙, 신규 교사 만료일 시험, 운영 안내를 확인한다. 기존 대출 비소급 조건은 그대로 유지되는지 함께 대조한다.

오해와 반례

애자일이나 반복 개발이면 요구와 문서와 시험이 필요 없다.

반복 개발에서도 새 교사 대출의 기간과 기존 데이터 처리 조건을 합의하지 않으면 기대값이 없다. 작은 산출물을 자주 갱신할 수 있지만 요구 계약과 검증 책임이 없어지는 것은 아니다.

연습 1 · 값과 상태 예측

v1이 추가 필드도 오류로 거절하는 엄격 입력 계약이었다면 A 레코드도 같은 결론인가?

힌트 1

추가 필드 무시 전제가 바뀌었다.

힌트 2

필수 필드 존재와 전체 스키마 허용은 다르다.

풀이와 답 확인

  1. due_day는 있지만 policy_version이 금지된 추가 필드다.

  2. 이 v1 계약에서는 A도 거절된다.

A도 읽기 불가다. 호환성은 소비자의 정확한 계약에 달려 있다.

흔한 오답에서 다시 생각하기

필수 필드가 있으면 모든 이전 프로그램이 자동으로 읽는다.

추가 필드 허용 여부를 확인해야 한다.

연습 2 · 오류 찾아 고치기

변경 계획에 새 화면과 코드만 갱신하고 기존 대출을 소급할지 정하지 않았다. 기대값을 고쳐라.

힌트 1

변경 대상의 시간 범위를 정한다.

힌트 2

기존 레코드와 신규 레코드를 별도 집합으로 둔다.

풀이와 답 확인

  1. 비소급이면 기존 due_day는 유지하고 새 접수에만 새 정책을 적용한다.

  2. 소급이면 대상·변환·통지·복구를 정의한 뒤 해당 기대값을 만든다.

소급 여부 합의 전 기존 자료 기대값은 미정이다.

흔한 오답에서 다시 생각하기

새 정책 숫자를 알면 기존 레코드도 당연히 바뀐다.

정책 값과 적용 대상은 다른 요구다.

연습 3 · 직접 만들어 보기

점진 저장 변경을 위한 요구→읽기→쓰기→변환→복귀 카드와 확인 항목을 설계하라.

힌트 1

각 카드의 선행 조건을 적는다.

힌트 2

복귀 코드가 읽을 실제 자료를 표시한다.

풀이와 답 확인

준비 개념과 학습 목표

준비 개념

  • 기능은 시스템이 무엇을 하는지, 품질은 정해진 조건에서 얼마나 잘 하는지 묻는다.

  • 백분위 같은 통계 용어 대신 먼저 10개의 관측값 중 조건을 만족한 개수를 세어 보자.

  • 미니복습: 즉시 2시간을 아껴도 이후 변경마다 1시간이 더 들면 네 번 변경에서 총 4시간이 더 든다.

학습 목표

  • 기능·성능·접근성·변경 용이성 요구를 조건과 측정으로 표현한다.

  • 기술부채의 미래 변경 비용을 가정과 함께 비교한다.

  • 품질 상충과 비용·위험 판단을 설명한다.

빠른 요청 수를 늘렸는데 최신 결과 수는 줄었다면 개선이라고 할까?

자체 검색 품질 기준은 같은 가상 요청 네 개에서 응답 1초 이하이면서 최신 재고와 일치한 요청을 세는 것이다. 캐시 없는 A의 시간은 [0.8,0.9,1.1,1.2]초이고 결과는 모두 최신이다. 캐시 B의 시간은 [0.4,0.4,0.5,0.5]초지만 둘째·넷째 결과가 낡았다. 시간만 보면 A는 2개, B는 4개 통과다. 최신성까지 동시에 만족한 요청은 둘 다 2개다. 실제 측정이 아니라 품질 상충의 분모를 고정한 가상 표다.

빠른 요청 수와 최신 요청 수를 더하여 통합 성공 수로 쓰면 같은 요청을 중복 센다. 조건의 교집합을 요청 ID별로 평가해야 한다. 실제 사용자는 낡은 재고라도 참고 검색에는 허용할 수 있고 확정 대출에는 금지할 수 있으므로 허용 조건을 목적별로 합의해야 한다. 이 표만으로 실제 운영 성능이나 장애율을 추정하지 않는다.

기술부채의 비용도 미래 작업 종류에 따라 다르다. 자체 개선 비용은 지금 6시간이고, 정책 변경 한 번의 추가 부담을 2시간, 문구 변경 한 번의 추가 부담을 0.25시간 줄인다고 정한다. 이후 정책 변경 두 번과 문구 변경 네 번이면 절약은 5시간으로 즉시 개선 비용보다 작다. 정책 변경이 세 번이면 절약은 7시간이다. 횟수와 단가가 가정일 때 손익 결과도 조건부이며 위험 영향이 동일하다는 가정을 별도로 검토한다.

먼저 확인할 개념
  • 시나리오별 품질과 부채 비용

    품질 조건을 정하고 미래 변경 비용을 비교하는 기본 계산을 먼저 확인한다.

  • 분모와 가상 관측

    실제 실행 자료가 아닌 표의 판정 범위를 명시한다.

품질은 이름보다 시나리오와 기준이 중요하다

기능 요구 '사용자가 책을 검색한다'와 품질 요구 '정해진 부하에서 검색 응답의 대부분이 목표 시간 안에 끝난다'는 연결되지만 다른 질문이다. 성능·신뢰성·접근성·보안·변경 용이성 같은 속성은 이해관계자와 환경에 따라 중요도가 다르다. 여기의 목록은 교육용 예이며 ISO의 완전한 품질분류표를 재현하거나 준수 판정을 하는 것이 아니다.

'빠르고 편하다'만으로는 평가할 수 없다. 누가 어떤 자극을 어떤 환경에서 주고, 시스템이 어떻게 응답하며, 어떤 측정 기준을 만족해야 하는지 적는다. 예를 들어 '고정된 시험 데이터와 10개 요청에서 최소 9개가 1초 안에 완료'는 작은 실습의 기준이다. 이를 실제 운영의 90백분위 전체 성능 보장으로 확대하지 않는다.

품질 속성은 서로 영향을 준다

도서 검색 결과를 캐시에 저장하면 응답 시간을 줄일 수 있지만 최신 재고와의 일치 조건을 따로 해결해야 한다. 더 많은 인증 확인은 보안상 유용할 수 있지만 사용 경로와 성능에 영향을 준다. 한 속성을 개선했다고 다른 속성까지 자동으로 좋아졌다는 뜻은 아니다.

접근성은 마우스 없이 검색과 결과 확인을 수행할 수 있는지처럼 구체적 경로로 점검한다. 변경 용이성은 대출 기간 변경 때 수정되는 정책 위치와 시험 범위를 통해 논할 수 있다. 정상 계산 하나의 성공은 이런 품질 증거를 모두 대신하지 못한다.

기술부채는 장래 작업 부담을 드러내는 비유이다

기술부채는 현재 설계·구현의 선택이나 미완성 상태가 미래 변경·검증에 추가 부담을 주는 상황을 설명하는 비유이다. 의식적인 일정 선택일 수도 있고 나중에 발견한 구조적 문제일 수도 있다. 모든 버그나 모든 오래된 코드가 같은 종류·크기의 부채는 아니다.

예를 들어 같은 정책을 세 파일에 복사하면 첫 구현은 빠르지만 변경마다 세 군데의 동기화와 회귀 검증 비용이 든다. 책임 위치를 하나로 모으는 정리는 비용을 줄일 수 있으나 즉시 비용과 변경 계획, 결함 위험을 함께 따져야 한다. 금융처럼 고정 이율로 증가한다고 가정하지 말고 부채 항목·발생 이유·영향·개선 비용·미루는 조건을 기록한다.

중간 과정을 따라가는 예제

정책 중복 구현 A는 처음 2시간, 변경마다 1.5시간 추가가 든다. 단일 정책 구현 B는 처음 5시간, 변경마다 0.5시간이 든다. 그 외 비용은 같다는 가상 가정에서 네 번 변경과 손익 경계를 비교한다.

  1. A의 네 변경 총비용은 2+4*1.5=8시간이다.

  2. B의 네 변경 총비용은 5+4*0.5=7시간이다.

  3. 일반 변경 횟수 n에 대해 A-B=(2+1.5n)-(5+0.5n)=n-3이다.

  4. n=3이면 모두 6.5시간, n>3이면 이 단순 비용 모형에서 B가 적다.

네 번이면 B가 1시간 적다. 실제 예측에는 변경 횟수·학습 비용·오류 위험·불확실성이 추가되므로 이 계산만으로 모든 프로젝트의 결정을 고정하지 않는다.

원본 하나의 시간 기준에서 두 품질의 교집합으로 확장한다.

다른 종류의 변경이 손익을 바꿈

개선 6시간, 정책당 절약 2시간, 문구당 절약 0.25시간이다. 정책 두 번/문구 네 번과 정책 세 번/문구 네 번을 비교하라.

  1. 첫 경우 절약은 2×2+4×0.25=5시간이다.

  2. 둘째는 3×2+4×0.25=7시간이다.

첫 경우 비용이 1시간 더 크고, 둘째는 절약이 1시간 더 크다. 다른 위험·비용은 같다는 자체 가정이다.

오해와 반례

기술부채는 무조건 즉시 없애야 하고 오래된 코드일수록 반드시 크다.

한 번만 쓸 실험의 정리 비용이 이득보다 클 수 있고 안정된 오래된 코드가 변경 부담을 거의 주지 않을 수도 있다. 변경 계획·위험·비용을 명시해 판단하며 부채라는 이름만으로 결론 내리지 않는다.

소단원 1.3

공학적 증거와 산출물

시험 계획서가 있다는 사실만으로 시험에 통과했다고 말해도 될까?

준비 개념과 학습 목표

준비 개념

  • 주장은 사실이라고 말하는 내용이며 증거는 그 주장을 뒷받침하는 관측·계산·검토 기록이다.

  • 예상값은 실행 전 정한 결과이고 관측값은 실제 확인한 결과이다.

  • 자가진단: '20개 시험을 할 계획'과 '20개를 실행해 18개 통과'는 서로 다른 증거 상태이다.

학습 목표

  • 요구·설계·코드·시험 계획·실행 기록의 역할을 구분한다.

  • 명세 적합성 확인과 실제 사용 목적 확인을 연결한다.

  • 증거의 버전·환경·입력·범위·미수행 상태를 기록한다.

같은 이름의 보고서를 다시 사용하면 새 버전의 통과도 증명될까?

자체 시험 증거의 식별자는 파일명 하나가 아니라 대상 내용 해시, 요구 버전, 입력 집합, 실행 설정, 도구 버전과 실제 방법의 묶음이다. 가상 L1은 내용 H1, 요구 R1, 설정 cache=off에서 Q1/Q2를 실행해 둘 다 통과한 기록이다. 새 코드 H2로 바뀌었거나 설정만 cache=on으로 바뀌면 L1이 해당 조합의 실행 통과를 직접 보여 주지 않는다. 분석으로 영향이 없다고 판단할 수는 있지만 그것도 별도 분석 증거로 기록해야 한다.

증거의 연결은 내용 검토를 필요로 한다. 요구 R2는 최신 재고를 보여 주는 것이지만 시험 T2가 결과에 책 제목이 들어 있는지만 확인한다면 R2→T2 링크가 있어도 최신성을 검사하지 않는다. 가상 낡은 재고 0과 현재 재고 1 모두 제목을 포함할 수 있어 같은 시험 결과를 낸다. 추적표의 연결률 100%와 요구의 검증 충분성은 다른 주장이다.

부정 결과와 미수행도 기록한다. 계획 Q1/Q2/Q3에서 Q1 통과, Q2 실패, Q3 미수행이라면 실행 집합 통과는 1/2, 계획 대비 확인 통과는 1/3이다. Q2 코드를 수정했다고 Q2가 통과로 바뀌지는 않는다. 실제 사용자 목적 확인은 이 예제에서 전부 미수행이며 분석·종이 기대값·실행·사용자 관찰의 방법을 서로 바꾸어 부르지 않는다.

먼저 확인할 개념
  • 주장과 증거의 버전·범위

    대상·환경·방법이 바뀌면 증거 해석도 다시 확인한다.

  • 요구와 산출물의 추적성

    링크 존재와 시험 내용의 일치를 분리한다.

산출물은 주장마다 역할이 다르다

산출물은 요구 문서, 설계 모델, 소스, 빌드 결과, 시험 계획, 실행 로그, 검토 의견처럼 개발 활동의 결과이다. 시험 계획은 앞으로 무엇을 확인할지 보여 주고 실행 기록은 실제로 무엇을 확인했는지 보여 준다. 코드가 존재하는 증거와 코드가 특정 조건에서 정확히 실행된 증거는 같지 않다.

빌드 결과는 어떤 소스를 어떤 도구와 설정으로 처리했는지 연결해야 한다. 검토 의견도 파일·버전·검토 기준이 있어야 해석할 수 있다. 문서 개수나 로그 분량이 많다는 사실만으로 품질이 높다는 결론을 내리지 않는다. 필요한 주장을 뒷받침하는지와 누락된 조건이 무엇인지가 핵심이다.

검증과 사용 목적의 타당성을 구분한다

검증(verification)은 산출물이 정한 요구·명세에 부합하는지 확인하는 활동으로 설명할 수 있다. 확인에는 시험뿐 아니라 분석·검토·검사도 포함된다. 타당성 확인(validation)은 의도한 사용과 사용자의 필요를 만족하는지 확인하는 질문이다. 둘은 관련되지만 같은 시험 하나로 언제나 끝나는 것은 아니다.

예를 들어 명세가 교사 기간 28일이라고 정했다면 날짜 계산을 대조할 수 있다. 하지만 실제 도서관의 교사 대출 정책이 21일이었다면 28일을 정확히 구현했어도 목적과 어긋난다. 사용자·운영 환경을 검토하는 근거가 추가로 필요하다. NASA 공개자료의 구분을 교육용으로 설명하며 특정 인증·표준 적합성 심사를 수행했다고 주장하지 않는다.

증거를 범위에 맞게 해석한다

시험 결과에는 요구 식별자, 소스/산출물 버전, 환경, 입력, 기대값, 관측값, 판정과 실패 재현 조건을 적는다. 일부 시험만 수행했다면 완료 수와 미수행 수를 분리한다. 손계산과 코드 실행, 실제 사용자 검토는 서로 다른 방법이므로 방법도 표시한다.

같은 파일명이어도 내용이 바뀌면 과거 로그를 새 버전의 통과 증거로 쓸 수 없다. 시험 모두 통과했다는 말은 정의한 시험 집합과 조건에서의 사실이며 모든 입력의 무결함 증명이 아니다. 출처·원시 로그·재현 명령을 연결하면 다른 사람이 주장 범위를 검토할 수 있다.

중간 과정을 따라가는 예제

가상 대출 계산 시험 20개를 계획했다. 버전 v1에서 12개를 실행해 10개 통과, 2개 실패, 8개는 미수행이다. 이후 코드만 v2로 바꾸고 재실행하지 않았다. 올바른 보고는?

  1. 계획 수 20과 실행 수 12를 나누어 적는다.

  2. 실행한 집합의 통과 비율은 10/12이며 전체 계획 대비 확인된 통과는 10/20이다.

  3. 두 비율은 각각 다른 분모이므로 하나로 혼동하지 않는다.

  4. 모든 기록은 v1에 대한 것이다. v2는 아직 검증 기록이 없다.

v1: 20개 계획, 12개 실행, 10개 통과·2개 실패·8개 미수행. v2: 재검증 미수행. 소스 변경 자체를 결함 해결의 실행 증거로 표시하지 않는다.

조건을 바꾸어 비교하기

코드가 같아도 설정이 달라짐

내용 H1은 그대로지만 cache=off에서 on으로 바뀌었다. off 통과 로그를 on 실행 성공으로 재표기할 수 있나?

  1. 대상 해시는 같아도 실행 조건은 다르다.

  2. 설정 영향 분석이나 on 실행 증거가 별도로 필요하다.

직접 on 실행 통과 증거로 재표기하지 않는다.

비교할 점

원본의 v1/v2 변경을 환경 조건 차이까지 확장한다.

링크는 있지만 검사 내용이 다름

R2 최신 재고와 T2 제목 포함을 연결했다. 낡은 재고 0/현재 1이 같은 제목을 내는 반례를 구성하라.

  1. 두 출력 모두 제목 검사에는 통과할 수 있다.

  2. 재고 0인 출력은 최신성 요구를 어긴다.

연결 존재만으로 R2 검증을 주장할 수 없다. 최신성 비교 기준을 추가해야 한다.

풀이 보기

각각 요구 문서, 빌드 로그, 입력/출력 기록, 사용자 검토 기록이 직접 연결된다. 사용자 검토가 없으면 정상 출력만으로 목적 검토 완료를 말할 수 없고, 실행 기록이 없으면 시험 계획으로 통과를 말할 수 없다.

오해와 반례

계획서와 코드 수정이 있으면 모든 검증도 완료된 셈이다.

v2 코드가 있어도 v1의 실행 로그는 v2의 결과를 보여 주지 않는다. 계획·구현·실행·사용자 검토 각각에 상태와 증거를 연결해야 한다.

연습 1 · 값과 상태 예측

가상 세 시험의 상태가 통과/실패/미수행이면 실행 통과 비율과 계획 대비 확인 통과 비율은?

힌트 2

풀이와 답 확인

  1. 실행 집합은 1/2=50%다.

  2. 계획 대비 확인 통과는 1/3≈33.33%다.

미수행 한 개를 별도로 유지한다. 실제 시험 실행은 없다.

실패를 고칠 계획이 있으니 3/3이다.

다른 문제에 적용하기

코드·자료 복귀와 공동 품질·증거 승인

각 사례는 독립인 가상 상황이다. v1은 due_day 필수/추가 필드 무시 계약이다. v2가 due_date 문자열만 남긴 뒤 실행파일만 v1으로 복귀하면 읽기 가능 여부와 필요한 활동을 적어라. 본문 네 요청의 캐시 B에서 공동 시간/최신성 통과를 구하고 Q2 최신성만 수정한 변형을 비교하라. 개선 비용 6시간·정책당 절약 2시간·문구당 0.25시간에서 정책 두 번/문구 네 번을 평가하라. 계획 시험 세 개에서 통과/실패/미수행의 두 분모를 보고하고 H1/cache off 로그가 H2/cache on 직접 실행 성공을 증명하는지 판단하라. 실제 운영·실행·사용자 검토는 수행하지 않는다.

힌트 1

요구·데이터·버전·설정·실제 방법을 각각 이름 붙인다.

힌트 2

공동 품질은 교집합, 비용은 변경 종류별 합, 통과 비율은 집합별 분모로 계산한다.

풀이와 답 확인

  1. due_day가 없어 v1 읽기 계약을 만족하지 못한다. 코드 복귀뿐 아니라 자료 복원과 호환성·실패 복구의 별도 계획/증거가 필요하다.

  2. B의 공동 통과는 Q1/Q3의 2/4=50%다. Q2 최신성만 고친 가상 변형은 Q1/Q2/Q3의 3/4=75%다.

  3. 절약은 정책 4시간+문구 1시간=5시간이므로 개선 비용이 1시간 더 크다. 위험과 미래 횟수는 별도 가정이다.

  4. 실행 집합 통과는 1/2, 계획 대비 확인 통과는 1/3이고 미수행은 한 개다. H1/off 기록은 H2/on의 직접 실행 성공 증거가 아니며 분석도 실행 사실로 바꾸지 않는다.

자료 복귀 미완료·공동 품질 50%와 가상 수정 후 75%·시간 비용상 개선 1시간 추가·실행 50%와 계획 대비 약 33.33%·현재 조합 실행 증거 없음으로 이름별 상태를 보고한다.

해결한 뒤 점검할 것

  • 실행파일 복귀와 저장 자료 계약을 분리한다.

  • 같은 요청의 두 품질 조건을 교집합으로 센다.

  • 미래 변경 종류와 비용 가정의 한계를 보존한다.

  • 두 분모·미수행·대상과 설정 범위·분석/실행 방법을 구별한다.
