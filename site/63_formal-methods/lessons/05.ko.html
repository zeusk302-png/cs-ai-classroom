소단원 5.1

Hoare triple

몇 번 입력해 잘 나왔다는 사실과 모든 조건부 입력에 대한 약속은 같을까?

준비 개념과 학습 목표

준비 개념

  • 상태는 변수 이름을 값에 연결한 표다. assertion은 상태에서 참/ 거짓인 논리식이다.

  • {P} C {Q}에서 P는 시작의 사전조건,Q는 끝의 사후조건이다. 본 자체 예제는 오버플로 없는 수학적 정수의 순차 명령이며 원문 Imp nat와 구별한다.

학습 목표

  • 명시한 정의와 적용 조건을 설명한다.

  • 자체 예제를 단계별로 풀고 반례의 원인을 찾는다.

모든 조건부 시작 상태를 양화하기

유효한 triple은 P를 만족하는 모든 시작 상태에서 C가 종료하면 끝 상태에 Q가 성립한다는 뜻이다. 한 입력의 관측이나 원하는 출력만 쓰는 문서와 다르다. P가 불필요하게 좁으면 매우 적은 상황만 보장한다.

변수 이름은 같아도 P의 x 는 전 상태,Q의 x는 후 상태다. 증가 명령 후 값은 다른 시점이다. 원래 값을 기억하려면 변하지 않는 논리 상수 n을 쓰거나 old(x) 표기 의미를 별도로 정의해야 한다.

부분 정확성과 종료 분리하기

이 논리의 부분 정확성은 종료한 경우를 보장한다. 무한히 도는 명령은 종료 상태가 없어 어떤 Q에 대해서도 이 정의에 반례를 내지 않는다. 이것을 서비스가 응답했다거나 실행에 성공했다는 뜻으로 해석하지 않는다.

전체 정확성은 종료까지 추가로 보장한다. 아래 대입 명령은 이 추상 의미에서 종료하지만 반복문 전체의 종료 증명을 자동으로 얻지는 않는다. 시간 제한· 예외· 동시성도 현재 단순 언어에서 제외한다.

반례와 공허한 참

triple을 깨려면 P가 참인 시작을 찾고 명령이 종료한 뒤 Q가 거짓인 것을 보여야 한다. P 밖 입력의 실패만으로 조건부 계약을 반박하지 않는다.

P =False이면 만족하는 시작 상태가 없어 triple은 공허하게 참이다. 논리적으로 유효해도 사용할 수 있는 입력이 없으므로 유용한 계약인지 별도로 보자. 실제 증명기나 프로그램 실행 검증은 수행하지 않았다.

중간 과정을 따라가는 예제

{x ≥0} x:=x +3 {x ≥3}의 유효성을 설명하고 사후조건을 x>3으로 바꾸면 반례를 찾으라.

  1. 시작 값을 n ≥0으로 두면 종료 값은 n +3이다.

  2. n +3 ≥3이라 모든 허용 시작에서 첫 Q가 참이다.

  3. x>3은 n =0을 선택하면 종료 값 3에서 거짓이다.

  4. 이 반례의 시작 0은 P에 속하고 명령은 종료하므로 수정 triple이 무효다.

≥3 계약은 유효,>3 계약은 시작 0의 반례로 무효다.

종이와 본문으로 직접 해보기

{x ≥2} x:=x +3 {x ≥5}와 {False} skip {x =100}을 판정하라.

힌트 보기

허용 시작의 집합과 종료 값을 따로 적는다.

풀이 보기

첫 계약은 n ≥2 →n +3 ≥5로 유효다. 둘째는 허용 시작이 없어 공허하게 유효이며 100을 실제로 만든다는 뜻이 아니다.

오해와 반례

부분 정확성이면 모든 명령이 끝나고 원하는 출력이 실제 생성된다.

while true do skip은 끝나지 않아 부분 triple의 종료 사후조건을 깨지 않지만 응답을 보장하지 않는다. False 사전조건도 실제 출력 증거가 아니다.

소단원 5.2

할당·합성·조건규칙

원하는 마지막 값을 거꾸로 따라가면 필요한 시작 조건을 찾을 수 있을까?

준비 개념과 학습 목표

준비 개념

  • :=는 값 갱신이고 =는 논리의 같음이다. Q[x ←e]는 Q에 등장하는 자유 변수 x를 식 e로 대체한 논리식이다.

  • ∧는 둘 다 참,¬ 는 부정이다. 본문은 부작용 없는 식/ 무한정밀 정수/ 순차 대입의 추상 언어다.

학습 목표

  • 명시한 정의와 적용 조건을 설명한다.

  • 자체 예제를 단계별로 풀고 반례의 원인을 찾는다.

할당은 사후조건에서 역으로 치환하기

할당 규칙은{Q[x ←e]} x:=e {Q}다. 시작 시 e의 값을 후 x에 넣으므로 사후조건 x의 자리를 e로 바꾼 식이 시작에서 참이면 된다. 명령문 왼쪽 x를 없애라는 뜻이 아니다.

사후조건 x ≤12와 x:=x +2이면 치환은 x +2 ≤12, 즉 x ≤10이다. 사후조건에만 있는 다른 변수는 대입으로 바뀌지 않는다. 식에 부작용이나 포인터 별칭이 있으면 현재 규칙의 상태 모형을 그대로 사용할 수 없다.

합성에서 중간 조건 연결하기

{P} C1 {M}과{M} C2 {Q}를 보이면{P} C1;C2 {Q}다. C1의 후 상태와 C2의 전 상태가 동일한 중간 조건 M으로 연결된다. 마지막 명령부터 역 치환하면 필요한 M을 찾기 쉽다.

x:=x +2;y:=3 *x 뒤 y ≤18을 원하면 두 번째 앞 M은 3 *x ≤18, 즉 x ≤6이다. 첫 번째 앞 P는 x +2 ≤6, 즉 x ≤4다. 각 단계의 x 시점을 섞으면 잘못된 조건이 나온다.

분기마다 조건을 더 하기

if b then C1 else C2에서는 P ∧b로 첫 가지,P ∧¬b로 둘째 가지를 증명하고 공통 Q를 만든다. 한 가지의 성공을 다른 가지까지 일반화하지 않는다.

if x ≥0 then y:=x else y:=−x 는 수학적 정수에서 y ≥0을 보장한다. 첫 가지 x ≥0, 둘째 x<0이므로 −x>0이다. 음수 최솟값을 부호 반전하는 기계 정수 오버플로는 현재 추상 조건 밖이다.

중간 과정을 따라가는 예제

x:=x +2;y:=3 *x의 사후조건 y ≤18에 필요한 사전조건과 시작 x =4의 중간/ 끝 값을 구하라.

  1. y 자리에 3 *x를 넣어 중간 조건 3 *x ≤18을 얻는다.

  2. 양수 3으로 나눠 x ≤6이다.

  3. 그 x에 x +2를 넣으면 x +2 ≤6, 즉 시작 x ≤4다.

  4. 시작 4는 중간 x6/ 끝 y 18로 경계를 만족한다. 시작 5는 x7/y21로 실패한다.

사전 x ≤4, 시작 4 →x6 →y18이다.

종이와 본문으로 직접 해보기

if x ≥0 then y:=x else y:=−x에서 x =−3과 x =0을 추적하고 두 가지 증명 조건을 적어라.

힌트 보기

둘째 조건은 x ≥0의 부정이다.

풀이 보기

−3은 else로 y3,0은 then으로 y0이다. then은 P ∧x ≥0,else는 P ∧x<0이고 둘 다 y ≥0을 보장한다.

오해와 반례

대입 순서를 뒤집어도 같은 합성 증명과 출력이다.

y:=3 *x;x:=x +2이면 시작 4의 y는 12다. 명령 순서와 중간 조건이 바뀌므로 원래 y18의 추적과 같지 않다.

소단원 5.3

사전·사후조건

조건을 더 강하게 쓰면 언제나 더 좋은 API 계약일까?

준비 개념과 학습 목표

준비 개념

  • 강한 조건은 허용 상태가 더 적다. P 강 ⇒P약이면P강을 만족하는 모든 상태가 P 약에도 속한다.

  • old(n)은 시작 시 n 값을 보존한 논리 표기이며 실행 변수가 아니다. 아래 reserve는 종이에서 정의한 추상 연산이다.

학습 목표

  • 명시한 정의와 적용 조건을 설명한다.

  • 자체 예제를 단계별로 풀고 반례의 원인을 찾는다.

호출자와 제공자의 약속

사전조건은 호출자가 충족할 조건, 사후조건은 제공자가 그 시작 조건하에 반환 시 지킬 조건이다. n ≥0인 개수에 하나 더 하는 연산의 Q를 n =old(n)+1로 쓰면 단지 양수보다 정확한 증가 관계가 남는다.

사전조건을 n ≥5로 강화하면 제공자는 처리할 입력이 줄지만 호출자는 더 제약 받는다. 사후조건을 n ≥1로 약화하면 증명하기 쉽지만 정확히 하나 추가됐는지는 알 수 없다. 계약의 강약은 입력/ 출력에서 서로 다른 효과를 낸다.

결과 규칙의 함의 방향

이미{P} C {Q}라면 P ′⇒P와 Q ⇒Q ′를 이용해{P ′} C {Q ′}를 얻는다. 시작은 더 강한 조건으로 좁히고 끝은 더 약한 조건으로 넓힌다. 반대 방향은 추가 증명 없이 안 된다.

n ≥0에서 증가 후 n ≥1이면 n ≥2인 시작으로 좁히고 끝 n ≥0으로 약화할 수 있다. 그런데 사전 n ≥−1로 넓히면서 끝 n ≥1을 유지하면 시작 −1 →0의 반례가 생긴다.

변경 범위와 실패도 계약에 넣기

reserve의 추상 상태(n,limit)에 0 ≤n<limit을 요구하고 성공 후 n ′=n +1,limit ′=limit로 정하면 어느 값이 유지되는지도 보인다. n ≤limit만으로 같은 성공을 약속하면 경계 n =limit에서 한도 초과다.

실제 API에는 실패시 상태· 예외· 동시 호출· 기계 범위도 필요할 수 있다. 현재는 정의한 순차 성공 연산의 조건만 본다. 문서의 계약이 적혀 있다고 구현의 증명· 실행 시험까지 완료됐다는 뜻은 아니다.

중간 과정을 따라가는 예제

reserve가 0 ≤n<limit에서 n ′=n +1,limit ′=limit로 끝난다. 시작(2,4),(4,4)의 허용 여부와 결과 보장을 구하라.

  1. (2,4)는 0 ≤2<4라 허용된다.

  2. 후상태는(3,4),n ′≤limit ′도 참이다.

  3. (4,4)는 4<4가 거짓이라 사전조건 밖이다. 반환이나 거절을 원 계약만으로 결정할 수 없다.

  4. 이를 무조건 증가시키면(5,4)가 되어 한도 조건을 깨므로 ≤로 사전조건을 바꾸려면 실패 계약 등 추가 설계가 필요하다.

허용(2,4)→(3,4);(4,4)는 계약 밖이다.

종이와 본문으로 직접 해보기

n:=n +1 의 원계약{n ≥0}{n ≥1}에서 새 사전 n ≥3/ 새후 n ≥0은 허용되는가? 사전 n ≥−1은?

힌트 보기

새 사전 ⇒원 사전, 원 후 ⇒새후를 각각 검사한다.

풀이 보기

n ≥3 ⇒n ≥0과 n ≥1 ⇒n ≥0 라 앞 변경은 유효하다. n ≥−1은 원사전을 함의하지 않고 −1 →0에서 원 후 실패다.

오해와 반례

사전조건 밖이면 함수가 반드시 예외로 거절하며 문서만으로 정확성이 증명된다.

원 계약은 조건 밖 동작을 정하지 않는다. 필요하면 거절/ 실패 조건을 추가해야 하고 구현 대조· 증명· 시험은 별도다.
