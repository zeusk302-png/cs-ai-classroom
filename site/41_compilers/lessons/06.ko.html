소단원 6.1

범위·선언·사용 연결

이름이 같은 두 x 는 반드시 같은 변수일까?

준비 개념과 학습 목표

준비 개념

  • 선언은 이름을 새 대상에 연결하고 사용은 그 연결을 찾는다.

  • lexical scope는 코드의 중첩 위치를 기준으로 이름을 찾는 정적 범위다.

학습 목표

  • 사용 위치를 선언 ID에 연결한다.

  • 차폐와 실행 중 값 변경을 구별한다.

문자열 이름에서 선언 대상으로

문법이 맞는 use x도 x의 선언이 없으면 의미 분석에서 오류가 될 수 있다. 컴파일러는 사용 노드마다 어떤 선언을 가리키는지 연결해 이후 타입 검사와 코드 생성에 사용한다. 같은 철자라도 서로 다른 선언이면 별개의 대상이다.

이 단원 자체 언어는 중첩 블록, 순차 선언, 단일 변수 이름 공간을 가진다. 선언은 초기화식의 이름을 먼저 해석한 뒤 현재 블록에 추가한다. 안쪽 블록의 같은 이름은 바깥 이름을 차폐할 수 있지만 같은 블록의 중복 선언은 금지한다. 모든 C/Java 언어의 규칙으로 일반화하지 않는다.

안쪽에서 바깥으로 찾는다

사용 위치에서 가장 안쪽의 현재 보이는 선언을 찾고 없으면 둘러싼 블록으로 나간다. 내부 x가 보이는 구간에서는 바깥 x도 존재하지만 평범한 x 사용은 내부 선언에 연결된다. 블록을 나오면 내부 선언의 범위가 끝나 바깥 연결이 다시 보인다.

이는 실행 호출 스택에서 가장 최근 값을 찾는 동적 범위와 다른 기준이다. 함수와 클로저를 포함하는 언어라면 함수가 작성된 환경과 값의 생존 기간을 따로 다뤄야 한다. 여기서는 함수 호출을 제외해 선언 연결에 집중한다.

연결 정보와 값 정보를 나눈다

심볼 기록에는 선언 ID· 타입· 위치· 범위 같은 정보가 있을 수 있다. 실행 중 정수 값이 5에서 8로 바뀌어도 해당 사용이 참조하는 선언 ID가 바뀌는 것은 아니다. 이름 해석과 값을 계산하는 실행은 서로 다른 작업이다.

오류 보고에는 사용 위치와 관련 선언 위치를 함께 남기면 이유를 설명하기 쉽다. 범위 밖 이름과 초기화 전에 읽는 문제도 구별해야 한다. 이 자체 예에서는 선언의 초기화식 처리 규칙을 명시하며 모든 definite assignment 분석을 구현했다고 주장하지 않는다.

중간 과정을 따라가는 예제

모형 코드: let x =2[D1]; {use x[U1]; let x =x +1[D2]; use x[U2];} use x[U3]. 각 use와 D2의 초기화식 x 를 선언 ID에 연결하라.

  1. 처음 D1을 바깥 블록에 등록한다.

  2. 안쪽 블록의 U1 시점에는 내부 x가 없어 D1을 찾는다.

  3. D2 초기화식은 등록 전 해석하므로 x는 D1이다. 값 계산 직관은 2 +1 =3이다.

  4. D2를 안쪽에 등록한 뒤 U2는 D2에 연결된다.

  5. 블록 종료 후 D2가 보이지 않아 U3는 D1이다. D1의 값은 이 모형에서 2로 남는다.

U1 →D1, 초기화식 x →D1,U2 →D2,U3 →D1이다.

종이와 본문으로 직접 해보기

예제 안쪽 블록에서 D2 선언 뒤, U2 앞에 {let y =x; use y;}를 넣고 그 새 블록 바깥에서 use y를 적으면 각 연결은? U2 전에 x =8이라는 대입을 넣으면 D1/D2 중 어느 대상이 바뀌는가?

힌트 보기

새 y는 그 블록에서만 보인다. x 대입은 현재 가장 안쪽 연결을 따른다.

풀이 보기

y 초기화의 x 는 그 위치에 보이는 D2, 내부 use y는 새 y 선언이다. 블록 밖 use y는 해당 선언을 찾지 못한다. U2 전에 x =8이면 D2의 값만 바뀌며 D1 연결이나 값 2를 바꾸지 않는다.

오해와 반례

변수 이름이 같으면 하나의 표에 덮어 쓰고 블록을 나와도 그 값이 남는다.

D2는 D1을 차폐할 뿐 삭제하지 않는다. 블록 뒤 U3가 D1로 돌아오므로 단일 덮어쓰기 후 복원 없는 구조는 이 범위 규칙을 구현하지 못한다.

자기점검

U1은 어느 선언인가?

답과 이유 보기

D1이다.

그 시점 D2가 아직 등록되지 않았다.

U2는 D1인가?

답과 이유 보기

D2다.

가장 안쪽에 등록된 같은 이름을 찾는다.

블록 종료 후 D2가 사용 가능한가?

답과 이유 보기

아니다.

정한 lexical 범위가 종료되어 U3는 바깥 D1로 연결된다.

한 단계 더

안쪽 변수 이름을 z로 일관되게 바꾸고 모든 연결 ID를 유지할 수 있는지 살펴보자. 바꾸는 이름이 주변의 다른 선언과 충돌하면 포획이 생길 수 있으므로 철자 교체만으로 의미 보존을 단정하지 않는다.

소단원 6.2

심볼 테이블 구조

블록을 나오면서 가려졌던 이름을 어떻게 되살릴까?

준비 개념과 학습 목표

준비 개념

  • 맵은 이름을 심볼 기록으로 대응시키는 자료 구조다.

  • 스택은 마지막에 넣은 범위를 먼저 제거하며 해시 충돌은 서로 다른 이름이 같은 버킷을 쓰는 경우다.

학습 목표

  • 범위별 맵 스택의 lookup/push/pop을 추적한다.

  • 해시 예상 비용과 범위 깊이를 구별한다.

맵 하나보다 범위의 층이 필요하다

심볼 테이블을 바깥에서 안쪽 순서의 맵 스택으로 구현하자. 블록 진입 때 빈 맵을 push하고 현재 범위 선언을 top에 넣는다. use는 top부터 아래로 찾으며 블록 종료 때 top을 pop한다. 차폐는 서로 다른 맵에 같은 이름이 존재하도록 허용한다.

현재 맵에만 찾는 lookupCurrent와 모든 범위를 찾는 lookup은 다른 작업이다. 중복 선언 검사는 전자로, 일반 이름 사용은 후자로 할 수 있다. 해시 버킷이 같다는 이유로 두 이름을 같은 심볼로 취급하지 않고 실제 키도 비교한다.

찾는 비용에 깊이가 들어간다

각 맵의 해시 조회를 예상 O(1)로 볼 조건이면 d개 범위를 모두 찾는 실패는 예상 O(d)다. 가장 안쪽 성공은 맵 한 번, 바깥 끝 성공은 d 번이다. 해시가 항상 최악 O(1)이라는 뜻은 아니고 충돌 처리 및 분포 조건이 필요하다.

빈 맵 push와 top 참조 제거는 단순 모형에서 O(1)이지만 메모리 해제 비용은 별도다. 불변 균형 트리를 사용하면 확장한 새 환경을 만들고 이전 환경을 유지할 수도 있다. 자료 구조 선택은 저장해야 할 환경 버전과 실제 언어 정책에 따라 달라진다.

다른 구조도 복원 정보를 보존해야 한다

단일 해시 테이블에 이름별 바인딩 스택과 변경 로그를 두는 방법도 있다. 새 선언을 앞에 추가하고 범위 진입 marker까지 변경을 기록한다. 나올 때 이번 범위 변경만 되돌리면 가려졌던 바깥 기록이 다시 보인다.

로그 구조의 종료 비용은 그 범위에 추가한 k 개 바인딩 수에 비례할 수 있다. 모든 종료가 단독 O(1)이라고 하면 잘못이다. 그러나 추가와 제거를 전체로 보면 각 바인딩이 한 번씩 처리되어 분할 상환 관점이 가능하다. 아래 활동은 먼저 이해하기 쉬운 맵 스택을 사용한다.

중간 과정을 따라가는 예제

아래에서 위로 G ={a:D1},B ={b:D2},C ={a:D3,c:D4}인 3 맵 스택이다. a,b,z를 찾을 때 방문 맵 수와 결과를 구하라.

  1. a는 C에서 바로 D3를 찾으므로 1 맵이다.

  2. b는 C에 없어 B의 D2를 찾으므로 2 맵이다.

  3. z는 C/B/G 모두에 없어 3 맵 실패다.

  4. C를 pop하면 스택G/B이며 a는 B 실패/G의 D1로 2 맵, c는 2 맵을 찾고 실패한다.

처음 a →D3/1,b →D2/2,z 실패/3이며 C 종료 후 a →D1/2다.

종이와 본문으로 직접 해보기

C에 b:D5를 추가한 뒤 b를 찾고 C를 pop한 뒤 다시 찾으라. 서로 다른 a와 b가 같은 해시 버킷 번호를 얻으면 중복 선언인가?

힌트 보기

이름별 실제 키와 범위별 맵을 구별한다.

풀이 보기

추가 후 b는 C의 D5를 1 맵에서 찾고 pop 후 B의 D2를 1 맵에서 찾는다. a/b의 버킷 충돌은 다른 이름이므로 중복 선언이 아니며 충돌 체인에서 키를 구별한다.

오해와 반례

해시 맵을 쓰면 이름 찾기는 범위 수와 무관하게 항상 한 번이다.

3 층 예의 z는 3개 맵을 조사하고 실패한다. 개별 예상 O(1) 맵 조회와 전체 깊이 O(d)는 다르며 단일 맵 +로그는 다른 구조다.

자기점검

처음 b의 방문 맵 수는?

답과 이유 보기

2개다.

C 실패 후 B 성공이다.

현재 범위 중복 검사를 바깥까지 확장하면 허용한 차폐를 잘못 막을 수 있는가?

답과 이유 보기

그렇다.

바깥에만 같은 이름이 있는 것은 자체 언어에서 허용한다.

k 개 선언 로그를 되돌리는 실제 pop 작업은?

답과 이유 보기

O(k)다.

각 추가 기록을 제거해야 하며 전체 분할 상환 비용과 단일 호출 비용은 다르다.

한 단계 더

심볼 기록을 AST에 ID로 연결한 뒤 범위를 pop해도 기록 본체가 필요한지 생각하자. 검색 맵 제거와 기록 수명은 분리해야 한다. 실제 메모리 관리 구현은 미수행이며 이 설명은 필요한 소유권 정책을 설계하는 질문이다.

소단원 6.3

미정의·중복 선언 진단

닫는 괄호가 모두 맞아도 프로그램의 이름은 잘못될 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 미정의 사용은 보이는 환경에 이름이 없는 경우다.

  • 자체 언어는 같은 범위 중복을 금지하고 내부 범위 차폐를 허용하며 초기화식은 새 이름 등록 전에 해석한다.

학습 목표

  • 사용 위치와 기존 선언 위치를 포함해 진단한다.

  • 진단 이후 환경을 보존해 불필요한 후속 오류를 줄인다.

오류의 종류와 기준을 적는다

use q가 문법적으로 올바른 토큰과 AST를 만들어도 현재 보이는 q가 없으면 미정의 사용이다. 중복 선언은 동일 범위의 이름 정책을 위반하는 새 선언이며 다른 블록의 차폐와는 구별된다. 한 규칙을 모든 언어의 overloading·namespace에 그대로 적용하지 않는다.

오류에는 파일/ 행/ 열과 문제 이름을 적고 중복이면 이전 선언 위치도 제시한다. x와 X를 다른 이름으로 보는 이 예제에서는 대소문자 변경이 의도인지 판단하지 않고 명시한 이름 비교를 따른다. 비슷한 철자를 제안하는 기능도 실제 의미 분석을 대체하지 않는다.

진단 뒤에도 무엇을 유지할지 정한다

중복 선언을 발견했을 때 기존 기록을 그대로 남기는 복구 정책을 정하자. 그러면 뒤의 use x는 첫 유효 선언에 연결할 수 있다. 새 기록으로 덮어 쓴다면 원래 타입 정보가 바뀌어 파생 오류가 생길 수 있으므로 복구 선택을 기록한다.

미정의 사용은 오류 표시를 가진 AST 노드로 남겨 다른 독립 오류를 계속 찾을 수 있다. 여기서는 미정의 사용이 임의의 정상 선언을 만들어 주지 않는다고 정한다. 실제 컴파일러의 오류 타입 전파와 최적화 억제는 추가 정책이며 아래 결과는 종이 진단 표다.

등록 시점은 초기화식의 해석을 바꾼다

순차 선언 언어에서 let q =q +1을 만나면 등록 전 보이는 q를 먼저 찾는다. 바깥 q가 있으면 그것을 읽고, 없으면 미정의다. 선언을 미리 등록하고 미초기화 상태를 검사하는 언어에서는 다른 진단이 가능하므로 용어를 혼용하지 않는다.

함수들의 상호 참조는 헤더를 먼저 수집한 뒤 본문을 검사하는 별도 설계로 해결할 수 있다. 그렇다고 모든 지역 변수 선언을 앞당겨 보이게 해야 하는 것은 아니다. 언어가 무엇을 허용하는지 먼저 정하고 심볼 테이블의 순회를 맞춘다.

중간 과정을 따라가는 예제

모형의 행: 1 let x =1[D1]; 2 let x =2[D2]; 3 {let x =3[D3];use y;} 4 use x; 5 use z. 같은 범위 중복은 거부하고 기존 기록 유지다. 오류와 행 4 연결을 구하라.

  1. 행 1 D1을 등록한다.

  2. 행 2 현재 맵에 x가 있어 중복 오류다. 행 1을 관련 위치로 붙이고 D1을 유지한다.

  3. 행 3 새 범위의 D3은 허용된 차폐다. use y는 안쪽과 바깥 모두 없어 미정의 오류다.

  4. 블록을 나온 행 4 use x는 D1에 연결되어 추가 이름 오류가 없다.

  5. 행 5 z도 없어 미정의 오류다. 총 3 오류며 차폐 D3을 오류로 세지 않는다.

오류는 행 2 중복/ 행 3 y 미정의/ 행 5 z 미정의의 3개이고 행 4 →D1이다.

종이와 본문으로 직접 해보기

행 3의 use y를 use x로 고치고 행 5를 use X로 고치면? 빈 환경에서 let q =q +1의 초기화식은? 바깥 q가 있으면?

힌트 보기

x와 X는 다른 이름이다. 초기화식은 등록 전에 조사한다.

풀이 보기

행 3 use x는 D3으로 정상이고 행 5 X는 대소문자 구별로 여전히 미정의다. 남는 오류는 행 2/ 행 5의 2개다. 빈 환경의 q 초기화는 미정의이며 바깥 q가 있으면 그 기록을 읽은 뒤 새 q를 등록할 수 있다.

오해와 반례

같은 철자의 모든 선언은 중복이고 미정의 오류 뒤에는 같은 이름을 자동 등록하면 된다.

D3은 별도 범위라 허용된다. 오류 사용을 정상 선언으로 등록하면 다음 사용을 부당하게 정상으로 판단할 수 있으므로 정한 복구와 언어 정책을 따른다.

한 단계 더

미정의 이름 두 번을 하나의 오류로 합칠지 각 위치에서 보고할지 정책을 정해 보자. 실제 프로그램 의미가 잘못된 위치를 놓치지 않되 첫 오류의 파생 메시지가 지나치게 늘지 않도록 원인 연결을 남긴다. 이 단원은 특정 컴파일러의 실제 출력 로그를 제공하지 않는다.
