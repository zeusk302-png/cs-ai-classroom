소단원 13.1

간섭 그래프·할당·spill

이름이 다른 모든 변수에 서로 다른 레지스터가 필요할까?

준비 개념과 학습 목표

준비 개념

  • live 변수 분석

  • 무방향 그래프

  • 명령의 읽기·쓰기

학습 목표

  • live 값과 간섭을 연결한다.

  • 주어진 그래프의 합법적 색칠을 검사한다.

  • spill 후 재분석과 기계 제약을 설명한다.

저장해야 할 값의 생존 구간

어떤 지점의 현재 값이 다시 덮어써지기 전에 이후 경로에서 읽힐 수 있으면 그 값은 live다. 단순히 변수가 한 번 선언됐다는 사실과 다르다. 서로 독립적으로 보존해야 하는 live 값에 같은 레지스터를 할당하면 한 값을 덮어 다른 값을 잃을 수 있다.

간섭 그래프의 정점은 이 분석에서 사용하는 값·임시변수이고 간선은 함께 할당하면 안 되는 관계다. 정의와 live-out의 관계, 복사 명령의 처리 및 실제 기계 제약을 반영해 만든다. 아래 활동은 이미 정확히 만들어졌다고 가정한 간섭 그래프의 색칠 연습이다.

색을 레지스터로 해석한다

간선으로 연결한 두 정점은 서로 다른 색을 써야 한다. k개 사용 가능한 레지스터를 k색으로 나타내면 색칠은 충돌 없는 배정을 표현한다. 간선이 없는 두 정점은 같은 레지스터를 재사용할 수 있지만 모든 실제 명령 제약이 이미 그래프에 반영됐다는 전제가 필요하다.

가상 네 정점 a,b,c,d와 간선 ab,bc,cd,da는 a,c를 R1에, b,d를 R2에 두어 색칠할 수 있다. 첫 제거 단계에서 차수<2인 정점이 없다는 이유만으로 이 그래프가 2색 불가능하다고 결론 내리지 않는다. 단순 휴리스틱의 실패와 해의 부재는 다르다.

공간을 넘치면 코드를 다시 쓴다

spill은 레지스터에 계속 두기 어려운 값을 스택 슬롯 등 메모리로 옮기는 것이다. 읽기 전에 load, 필요한 계산 후 store와 짧은 생존 임시값을 도입할 수 있다. 원래 간섭 정점을 지우는 작업만으로 실행 가능한 프로그램이 완성되는 것이 아니다.

변환한 명령에 대해 liveness와 할당을 다시 점검한다. 호출에서 파괴되는 레지스터·고정 결과 레지스터·프레임 슬롯·명령별 피연산자 제약도 있다. spill의 메모리 접근과 코드 크기 비용은 경로 빈도·기계에 달려 있으므로 작은 그래프만으로 실제 실행 시간 개선을 보장하지 않는다.

중간 과정을 따라가는 예제

자체 간섭 그래프의 간선은 ab,bc,cd,da다. 사용 가능한 R1,R2로 배정하라. 간선 ac를 추가하면 어떻게 바뀌는가?

  1. a=R1,b=R2,c=R1,d=R2로 둔다.

  2. 네 기존 간선의 양 끝이 서로 달라 모두 합법이다.

  3. ac를 추가하면 a,b,c가 삼각형이다. 두 색이면 a와 c가 같아질 수밖에 없어 ac 조건을 위반한다.

  4. 삼각형 때문에 2색은 불가능하고 세 색이면 a=R1,b=R2,c=R3,d=R2로 배정할 수 있다. 실제 2레지스터 코드라면 spill 등 변환과 재분석이 필요하다.

처음에는 두 레지스터 재사용이 가능하며, ac 추가 그래프는 최소 세 색이다.

종이와 본문으로 직접 해보기

값 v를 메모리 슬롯 S에 spill했다고 가정한다. 가상 누산 명령 v←v+w를 load t←S, t←t+w, store S←t로 바꾸고 S=7,w=4를 추적하라.

힌트 보기

t는 원래 v의 값을 먼저 읽는다. 마지막 값이 메모리에 저장되는지 본다.

풀이 보기

load 후 t=7, 덧셈 후 t=11, store 후 S=11이다. 원래 v 결과 11과 일치한다. 이는 가상 명령의 의미 계산이고 특정 CPU 어셈블리 실행이 아니다. t와 w를 실제로 배정할 수 있는지도 별도로 확인한다.

오해와 반례

간섭 그래프에서 정점 하나를 지우면 spill 구현이 끝난다.

그 값의 저장·읽기·갱신을 보존할 명령과 슬롯이 필요하다. 새 임시값의 간섭을 다시 분석해야 한다.

소단원 13.2

가비지 수집 기초

서로 참조하는 두 객체라도 프로그램에서 찾아갈 길이 없다면 어떨까?

준비 개념과 학습 목표

준비 개념

  • 방향 그래프와 도달 가능성

  • 힙과 스택

  • 메모리 수명

학습 목표

  • 루트에서 도달 가능한 객체를 표시한다.

  • mark/sweep과 단순 참조 계수의 차이를 설명한다.

  • 수집과 실제 메모리 반환·자원 종료를 구분한다.

루트에서 따라갈 수 있는 길

기초 tracing GC 모델은 스택·전역 등에서 런타임이 확인한 루트를 출발점으로 포인터를 따라간다. 객체에 다른 객체의 포인터가 있다는 사실만으로 프로그램에서 도달 가능하다고 말하지 않는다. 출발점에서 그 참조까지 가는 경로가 있어야 한다.

이 단원은 강한 포인터만 있는 정지된 유한 그래프를 가정한다. 약한 참조·finalizer·동시 변경 등 복잡한 런타임 정책은 제외한다. 도달 가능한 객체라도 실제 이후 코드가 다시 쓰지 않을 수 있어 tracing 도달성과 미래 사용 예측은 같은 개념이 아니다.

표시한 뒤 나머지를 회수한다

mark는 루트에서 탐색하며 방문 객체를 표시한다. 같은 객체를 다시 방문하지 않게 표시하면 순환도 끝낼 수 있다. sweep은 할당된 객체 목록에서 표시되지 않은 객체 공간을 재사용 가능하게 만든다. 정확한 루트와 포인터 정보가 중요하다.

단순 참조 계수만으로는 외부 루트가 사라진 순환의 계수가 0이 되지 않을 수 있다. tracing은 루트에서 경로가 없음을 확인해 그 순환을 회수할 수 있다. 반대로 살아 있는 객체를 잘못 회수하면 안전성이 깨진다. 현재 GC 구현 모두가 같은 알고리즘이라고 일반화하지 않는다.

회수 뒤에도 남는 운영 비용

GC에는 탐색 비용·추가 메타데이터·일시 정지·메모리 여유 공간 등 비용이 있다. 비이동 수집 뒤에는 빈 공간이 흩어질 수 있고, 이동·압축 수집은 객체 주소와 참조 갱신 문제를 해결해야 한다. 기초 그림을 실행 성능 예측으로 바로 바꾸지 않는다.

힙 내부 재사용 가능과 운영체제에 메모리 페이지를 반환하는 일은 별도 정책이다. 도달 가능 객체를 계속 보유하면 GC가 있어도 메모리가 증가할 수 있다. 파일·소켓 등 외부 자원의 제때 종료는 해당 API의 수명 규칙으로 관리하며 GC 그림만으로 보장하지 않는다.

중간 과정을 따라가는 예제

자체 객체 A=16,B=24,C=8,D=8,E=32바이트다. A→B,B→A,C→D,D→C이며 E는 간선이 없다. 루트는 A뿐이다. mark/sweep에서 유지·회수되는 객체와 바이트 수는?

  1. 루트 A를 표시하고 A→B로 B를 표시한다. B→A는 이미 표시한 객체로 돌아가 끝난다.

  2. C,D 순환과 E는 루트에서 갈 수 없다.

  3. 총 크기는 16+24+8+8+32=88바이트, 유지 A+B는 40바이트다.

  4. 회수 가능 C+D+E는 48바이트다. 메타데이터·정렬·페이지·수집기 공간을 제외한 가상 객체 크기 합계다.

A,B 40바이트를 유지하고 C,D,E 48바이트를 회수 가능하게 한다.

종이와 본문으로 직접 해보기

루트에 E도 추가하면 유지·회수 합은? 다음에 모든 루트를 제거하고 객체 간선은 그대로면 단순 참조 계수는 A/B와 C/D의 계수를 0으로 만들까?

힌트 보기

루트에서 도달성을 다시 구하고 순환의 내부 incoming 포인터를 세어 본다.

풀이 보기

A,B,E는 72바이트 유지하고 C,D는 16바이트 회수 가능하다. 모든 루트를 제거하면 tracing 모델에서는 다섯 객체 모두 도달 불가능하다. 단순 참조 계수에서는 A/B와 C/D가 각각 서로의 포인터 하나를 받아 계수 1이 남으므로 별도 순환 처리가 없으면 회수하지 못한다.

오해와 반례

GC가 있으면 살아 있는 객체를 무한히 보유해도 메모리가 줄어든다.

루트에서 도달 가능한 객체는 이 모델에서 유지한다. 계속 참조를 쌓는 구조는 GC가 있어도 메모리를 소비한다.

소단원 13.3

코드 크기·속도 비교

파일이 작아졌다는 사실만으로 실행도 빨라졌다고 말할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 비율과 단위

  • 중앙값

  • 프로그램의 관측 결과

학습 목표

  • 비교 대상 크기·시간을 정의한다.

  • 정확성을 먼저 확인하고 가상 자료를 해석한다.

  • 제약 아래 후보를 비교하고 실제 실험과 구분한다.

어느 크기와 어느 시간을 비교할지

소스 글자 수, 기계어 코드 섹션, 전체 실행 파일, 메모리 사용량은 다른 크기다. 이 단원 표는 가상 코드 섹션 바이트와 같은 입력 1회 처리 시간 ns를 비교한다. 측정 대상을 섞으면 비율이 의미를 잃는다.

Clang 공식 안내에서 O3는 속도를 위한 더 큰 코드가 생길 수 있고 Os/Oz는 크기 감소를 지향한다. 옵션 이름만으로 모든 프로그램의 실제 크기·속도를 정할 수는 없다. 아래 후보 A/B는 특정 옵션의 결과라는 이름을 붙이지 않는다.

같은 일을 하는 코드인지 먼저

비교 전 입력 범위와 출력·부수 효과·오류 동작 등의 계약을 정한다. 같은 결과를 계산하지 않거나 정의되지 않은 동작에 의존하는 코드는 작은 시간 숫자만으로 더 좋은 구현이라고 결론 내리지 않는다.

실제 비교 계획은 컴파일러 버전·대상 CPU·옵션·라이브러리·입력·환경·타이밍 경계를 기록한다. 반복값과 요약 방법을 남기며 초기화·캐시·입출력 등 조건을 구분한다. 여기서는 실제 컴파일·어셈블리·벤치마크를 실행하지 않는다.

목표를 명시하고 후보를 고른다

속도 개선 비율은 기준 시간/후보 시간으로 정의한 speedup과 (기준−후보)/기준으로 정의한 시간 감소율을 구분한다. 바이트 감소율도 자기 기준을 쓴다. 시간과 크기를 바로 더해 단위 없는 점수라고 부르지 않는다.

자체 조건 코드 크기≤850바이트, 시간≤100ns 아래에 후보가 들어오는지 따로 검사한다. 더 작은 후보가 시간 제한을 넘으면 이 조건의 해가 아니다. 조건이 바뀌면 선택도 바뀔 수 있다. 성능 표는 합성 계산용이며 실제 장치 보장값이 아니다.

중간 과정을 따라가는 예제

자체 합성 기준 1000바이트/120ns, 후보 A 800바이트/90ns, 후보 B 700바이트/150ns다. 코드≤850바이트·시간≤100ns 조건에 맞는 후보와 A의 비율을 구하라.

  1. A는 800≤850,90≤100으로 두 조건을 만족한다. B는 크기만 만족하고 150>100이다.

  2. A의 크기 감소율은 (1000−800)/1000=20%다.

  3. A의 시간 감소율은 (120−90)/120=25%, speedup은 120/90=4/3이다.

  4. B는 30% 작지만 시간은 기준보다 25% 증가한다. 더 작다는 사실만으로 더 빠르다고 판단하지 않는다.

이 합성 제약에서는 A만 적합하다. A는 20% 작고 시간은 25% 줄었으며 speedup은 약 1.333배다.

종이와 본문으로 직접 해보기

합성 A 반복 시간 88/90/92 ns와 B 145/150/155 ns의 중앙값은? 시간 제한만 160 ns로 바꾸면 크기 조건까지 통과하는 후보는?

힌트 보기

정렬된 세 값의 가운데를 사용하고 두 조건을 재검사한다.

풀이 보기

중앙값은 A 90 ns, B 150 ns다. 크기≤850바이트와 시간≤160 ns이면 두 후보 모두 적합하다. 더 작은 것을 우선하면 B, 더 빠른 것을 우선하면 A이므로 추가 목적을 적어야 한다. 합성 반복값을 실제 벤치마크 실행으로 표시하지 않는다.

오해와 반례

최적화 옵션이 크면 언제나 작고 빠르며 결과도 같은 방식으로 유지된다.

옵션별 목표·언어 의미의 허용 범위·프로그램·기계에 따라 다르다. 관측 동작을 바꿀 수 있는 설정은 계약을 먼저 확인하고 검증한다.
