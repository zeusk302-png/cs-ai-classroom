소단원 3.1

CFG·AST·모호성

똑같은 8−3−1을 읽었는데 두 답이 나오는 것은 계산 실수일까?

준비 개념과 학습 목표

준비 개념

  • 토큰은 숫자·식별자·연산자처럼 lexer가 분류한 입력 단위다. num 토큰의 값 8과 토큰 종류 num을 구분한다.

  • 트리의 뿌리·자식·잎, 재귀적으로 식을 만드는 구조를 준비한다.

  • 문법의 ε는 빈 토큰열이며 규칙의 |는 여러 대안을 뜻한다.

학습 목표

  • CFG의 유도·파스트리·AST를 구별하고 모호성 반례를 만든다.

  • 구문을 만족하는 것과 변수·타입·실행의 의미가 맞는 것을 분리한다.

서로 다른 다섯 트리에서 같은 값이 두 번 나오면 구조도 같은가?

기본 E→E−E | num에 숫자 네 개를 준다. 정수 연산은 수학적 뺄셈이며 고정 폭 오버플로, 부작용, 평가 시각은 포함하지 않는다. num−num−num−num의 잎 순서를 고정하고 이항 노드의 묶임만 바꾼다. 괄호 표기는 입력에 없는 트리 설명용이다.

뿌리의 왼쪽 잎 수를 1, 2, 3으로 나누면 구조 개수는 각각 2, 1, 2다. 이 분할은 모든 순서 보존 이항 트리를 빠짐없이 세면서 중복하지 않는 방법이다. 결과값을 집합으로 만들면 서로 다른 구조의 같은 값을 합쳐 버린다.

AST가 단순 수치 결과보다 풍부한 이유를 별도 조건문에서도 확인한다. if p then if q then a else b에는 else가 안쪽 또는 바깥쪽에 붙는 두 구조가 있다. 이번 관찰 규약은 실행된 출력 a/b의 목록이고 조건이 거짓인 else 없는 if는 아무것도 출력하지 않는다. 이는 특정 실제 언어 실행이 아닌 작은 의미 모형이다.

먼저 확인할 개념
  • 트리와 유도 순서

    왼쪽/오른쪽 전개가 같은 트리일 수 있고 모호성은 다른 트리의 존재임을 사용한다.

  • 결합 방향과 AST

    같은 잎 순서를 유지해도 묶임과 값을 바꿀 수 있어 의미 보존을 별도로 검사한다.

문법은 생성 규칙이다

CFG를 G=(N,Σ,P,S)로 둔다. N은 비단말, Σ는 단말 토큰 종류이며 둘은 서로 겹치지 않는다. 시작 S∈N, 생성규칙 P의 왼쪽은 비단말 하나이고 오른쪽은 단말·비단말의 유한 열(ε 포함)이다. A→γ는 어떤 주변 토큰열 안에서도 A를 γ로 바꿀 수 있다는 뜻이다.

S에서 규칙을 유한 번 적용하여 단말만 남는 토큰열 w를 만들면 w∈L(G)다. 파서는 입력을 새로 생성하는 대신 그 입력이 이런 구조로 유도되는지 찾는다. 이름 x가 선언되었는지나 0으로 나누는지는 E→E/E 같은 구조 규칙만으로 보통 결정하지 않고 이후 의미 검사·실행 규칙과 연결한다.

유도 순서와 트리

파스트리는 규칙 적용의 부모·자식 구조를 보존하고 잎을 왼쪽부터 읽으면 입력 토큰열이 된다. 왼쪽 비단말을 먼저 전개한 유도와 오른쪽을 먼저 전개한 유도는 같은 트리를 만들 수 있다. 따라서 유도 단계 순서가 다르다는 사실 하나만으로 문법이 모호하다고 판정하면 안 된다.

문법이 모호하다는 것은 어떤 하나의 토큰열에 서로 다른 파스트리가 적어도 둘 존재한다는 뜻이다. E→E−E | num에서는 num−num−num의 뿌리를 첫 번째 − 또는 두 번째 −에 놓을 수 있다. 산술 해석을 붙이면 8−(3−1)=6과 (8−3)−1=4로 달라져 문제를 드러낸다.

AST는 필요한 구조를 남긴다

AST는 이후 의미 검사와 변환에 필요한 연산·피연산자 구조를 표현한다. Num(8), Sub(left,right) 같은 노드를 쓴다. 모든 문법 비단말과 구두점을 별도 AST 노드로 남길 필요는 없다. 괄호는 AST에서 별도 노드가 없어도 자식 구조를 결정하므로 효과는 보존되어야 한다.

예를 들어 (8−3)−1의 AST는 Sub(Sub(Num(8),Num(3)),Num(1))이다. 소스 위치는 오류 메시지에 유용하여 AST에 부가 정보로 보존할 수 있고, 원문 그대로 다시 인쇄하는 도구는 주석·공백까지 보존하는 구체 구문 표현도 필요할 수 있다. AST에서 구두점을 생략한다는 말은 원문 편집 정보를 모두 버려도 된다는 일반 규칙이 아니다.

서로 다른 다섯 트리에서 같은 값이 두 번 나오면 구조도 같은가?
입력 또는 정책중간 구조 또는 상태관찰 결과

((20−6)−3)−1

뿌리 왼쪽에 잎 세 개

값은 10

(20−(6−3))−1

뿌리 왼쪽에 잎 세 개

값은 16

(20−6)−(3−1)

뿌리 양쪽에 잎 두 개씩

값은 12

20−((6−3)−1)

뿌리 오른쪽에 잎 세 개

값은 18

20−(6−(3−1))

뿌리 오른쪽에 잎 세 개

값은 16

표의 다섯 행은 입력의 다섯 복사본이 아니라 한 토큰열의 다섯 구조다. 값 집합 {10,12,16,18}은 네 원소여도 트리 개수는 다섯이다. 숫자 순서를 바꾸는 순열은 이 표에 포함하지 않는다.

중간 과정을 따라가는 예제

E→E−E | (E) | num인 문법에서 8−3−1의 두 구조와 값을 구하고, (8−3)−1에서 괄호가 AST에 미치는 영향을 설명하라.

  1. 왼쪽 결합 트리는 뿌리 E→E−E의 왼쪽 E에 다시 E→E−E를 적용한 구조다. 묶임 (E−E)−E의 괄호는 트리 설명용이며 입력에 괄호 토큰을 추가하는 유도 단계가 아니다.

  2. 잎을 num 값 8,3,1로 채우면 Sub(Sub(8,3),1)이고 8−3=5,5−1=4다.

  3. 오른쪽 구조는 Sub(8,Sub(3,1))이고 3−1=2,8−2=6이다. 둘 다 잎 순서 8,−,3,−,1을 유지한다.

  4. 괄호가 실제 입력에 있는 (8−3)−1은 내부 E를 먼저 묶어 왼쪽 AST를 강제한다. 괄호 노드를 없애더라도 Sub의 중첩을 바꾸면 의미 보존에 실패한다.

같은 무괄호 입력은 값 4 또는 6인 두 트리를 갖는다. (8−3)−1의 AST는 왼쪽 구조이며 괄호 효과가 자식 관계에 남는다.

조건을 바꾸어 비교하기

값으로 트리를 식별할 수 없다

표의 두 값 16이 같은 AST인지 판단하고 각 중간 값을 써라.

  1. 둘째 트리에서는 6−3=3, 20−3=17, 17−1=16이다.

  2. 다섯째 트리에서는 3−1=2, 6−2=4, 20−4=16이다.

  3. 둘째 뿌리의 오른쪽은 Num(1)이고 다섯째 뿌리의 오른쪽은 Sub(6,Sub(3,1))이므로 서로 다르다.

두 트리는 수치 결과만 같고 자식 구조는 다르다.

비교할 점

기본의 4/6처럼 값이 달라야만 모호성이 드러나는 것은 아니다.

가까운 else와 바깥 else의 관찰

if p then if q then a else b에서 p=false,q=false일 때와 p=true,q=false일 때 두 구조를 비교하라.

  1. 안쪽 연결은 If(p,If(q,a,b),없음), 바깥 연결은 If(p,If(q,a,없음),b)다.

  2. p=false이면 안쪽 연결은 아무 출력도 없고 바깥 연결은 b를 출력한다. q는 평가하지 않는다.

  3. p=true,q=false이면 안쪽 연결은 b를 출력하고 바깥 연결은 아무 출력도 없다.

같은 토큰열에서 두 조건 조합 모두 구조 차이를 관찰할 수 있다.

비교할 점

구문 자체와 가까운 if 연결 정책, 실제 실행 증거를 분리한다.

종이와 본문으로 직접 해보기

E→E+E | num 문법으로 2+5의 왼쪽 우선 유도와 오른쪽 우선 유도를 쓰라. 두 유도가 문법 모호성의 증거인지, 2+5+7에서는 어떤 증거를 쓸 수 있는지 판단하라.

힌트 보기

E⇒E+E 이후 어느 E를 먼저 num으로 바꾸는지와 최종 트리의 뿌리·자식 관계를 분리한다.

풀이 보기

왼쪽 우선 E⇒E+E⇒num+E⇒num+num, 오른쪽 우선 E⇒E+E⇒E+num⇒num+num이다. 둘은 같은 두 자식 트리라 이것만으로 모호성 증거가 아니다. 2+5+7에는 Add(Add(2,5),7)과 Add(2,Add(5,7))의 서로 다른 트리가 있다. 덧셈 값이 둘 다 14라도 트리 구조가 달라 모호성은 존재한다.

오해와 반례

두 트리가 같은 수치 결과를 내면 문법은 모호하지 않다.

2+5+7의 두 결합은 같은 14여도 트리는 다르다. 모호성은 수치 결과가 아니라 문법적 구조의 유일성에 관한 성질이다. 반대로 왼쪽·오른쪽 유도가 다르더라도 같은 트리이면 그 차이만으로 모호성은 아니다.

연습 1 · 값과 상태 예측

각 행의 결과를 먼저 읽는다.

힌트 2

힌트 1

힌트 2

  2. 둘 다 Sub(20,6) 하나다. 문법의 모호성 증인에는 표의 네 숫자 또는 세 숫자의 다른 묶임을 쓴다.

힌트 1

힌트 2

풀이와 답 확인

  2. 괄호 자체의 노드는 없어도 6과 3의 Sub가 안쪽 오른쪽 자식이라는 관계를 유지한다.

구두점 삭제가 묶임 삭제의 허가는 아니다. 값 10으로 바뀌는 반례가 있다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

순서가 고정된 숫자 다섯 개의 모든 이항 뺄셈 트리 개수를 뿌리 분할로 구하라. 일반 입력의 비모호성을 이 유한 계산이 보장하는가?

힌트 1

잎 한 개의 구조 수는 1이다.

힌트 2

잎 네 개의 구조 수 5, 세 개 2, 두 개 1을 사용한다.

풀이와 답 확인

  1. 뿌리 분할 1+4,2+3,3+2,4+1의 개수는 1·5,1·2,2·1,5·1이다.

  2. 합은 14다. 분할별 잎 수가 다르고 자식 트리 선택이 독립이라 중복하지 않는다.

  3. 이는 이 문법의 특정 길이 구조 계산이며 모든 문자열의 비모호성 증명이 아니다.

다섯 잎의 트리는 14개다. 유한 예시로 전역 비모호성을 인증할 수 없다.

흔한 오답에서 다시 생각하기

준비 개념과 학습 목표

준비 개념

  • 좌재귀 A→Aα는 입력 소비 전에 A를 재호출하게 만들 수 있다.

  • 문법 변형은 생성 토큰열의 보존과 AST 의미 보존을 각각 검사한다.

학습 목표

  • 좌재귀 제거·좌인수분해의 목적과 적용 한계를 설명한다.

곱셈 우선순위를 고쳤어도 지수의 결합 방향은 남아 있지 않을까?

이번 소단원의 새 문법은 E→T R, R→−T R|ε, T→P U, U→*P U|ε, P→num V|(E)V, V→^P|ε다. 단항 부호는 없고 num은 비음수 정수 토큰이다. 지수는 자연수 지수로 해석하며 예제는 0^0을 사용하지 않는다. ^는 *보다 높고 오른쪽 결합, −와 *의 AST는 왼쪽 누적한다.

P는 앞의 원자와 뒤의 V를 읽어 V가 ^P이면 Pow(atom,nextP)를 반환한다. 다음 P가 지수 사슬 전체를 먼저 구성하므로 2^3^2는 Pow(2,Pow(3,2))다. E와 T는 꼬리 트리가 오른쪽으로 길어져도 AST를 왼쪽에 누적한다. 한 문법 안에서도 같은 누적 행동을 모든 연산에 쓰면 안 된다.

좌인수분해의 다른 사례는 S→A ;, A→id B, B→(E)|=E|ε다. id만 쓰는 문장도 허용하지만 ε 선택은 B 뒤의 ;에서만 한다. 새 표는 이 시작 기호의 FOLLOW를 기준으로 정의하며 식 내부 문법의 FOLLOW와 섞지 않는다.

  • 꼬리 문법과 AST 누적

  • 괄호 효과의 자식 관계

    지수 사슬과 괄호가 없어져도 서로 다른 Pow 자식 구조를 보존한다.

연산 층을 구분하기

정수 계산의 예로 E→E−T | T, T→T*F | F, F→num | (E)를 둔다. E는 낮은 우선순위 뺄셈, T는 곱셈, F는 숫자 또는 명시적 괄호를 표현한다. 괄호 없이 E가 T 아래로 들어가는 규칙이 없어 곱셈보다 뺄셈을 먼저 묶는 트리를 막는다.

E→E−T의 왼쪽 E 재귀는 같은 층 뺄셈을 왼쪽으로 묶는다. 10−4−2는 (10−4)−2다. 오른쪽 재귀 E→T−E | T는 10−(4−2)를 표현한다. 우선순위와 결합성을 따로 명세하지 않으면 파서의 우연한 선택이 언어 의미를 대신한다.

좌재귀 제거와 AST 보존

단순 예측 재귀하강에서는 E가 입력을 소비하기 전에 E를 부르므로 직접 좌재귀가 문제다. 위 문법을 E→T R, R→−T R | ε, T→F U, U→*F U | ε로 바꿀 수 있다. F는 그대로 둔다. 반복하는 토큰열은 같지만 R,U의 꼬리 재귀 트리가 원래 왼쪽 연산 AST를 저절로 만들어주지는 않는다.

AST는 먼저 첫 T를 acc로 두고 다음 −T마다 acc=Sub(acc,nextT)로 왼쪽 누적하여 만든다. 곱셈도 같은 방식이다. 직접 좌재귀 제거는 모든 LL(1) 문제를 자동으로 없애지 않으며 간접 좌재귀·nullable·FIRST/FOLLOW 충돌도 검사해야 한다. LR 계열은 좌재귀를 처리할 수 있어 모든 파서에서 좌재귀 문법이 잘못인 것은 아니다.

공통 접두사를 미루기

A→id ( E ) | id = E처럼 대안의 첫 토큰이 같은 경우 한 토큰만 보고 선택할 수 없다. A→id B, B→( E ) | = E로 좌인수분해하면 id를 읽은 뒤 다음 토큰 ( 또는 =로 결정한다. 이 변형은 접두사를 공유하는 선택 위치를 뒤로 미루며 연산 결합성 문제와는 별개다.

LL(1) 표는 대안의 시작 토큰 FIRST와 빈열 가능성, 뒤따르는 토큰 FOLLOW를 함께 사용한다. 예를 들어 R→−T R | ε에서 −이면 반복하고 적절한 FOLLOW(E), 여기서는 ) 또는 입력 끝에서 빈 꼬리를 고른다. 아무 토큰에서나 ε를 고르면 잘못된 입력을 조용히 통과시킬 수 있다. 괄호 예측이 가능해도 닫는 괄호의 실제 일치는 검사해야 한다.

윗 세 행은 수학적 정수 연산이고 아래 네 행은 별도 문장 문법의 한 토큰 선택이다. 지수의 오른쪽 AST와 곱셈·뺄셈의 왼쪽 AST를 동시에 확인한다. EOF는 필수 세미콜론을 대체하지 않는다.

중간 과정을 따라가는 예제

E→T R,R→−T R|ε,T→F U,U→*F U|ε,F→num|(E)를 사용하고 −는 왼쪽 누적 AST를 만든다. 10−4−2*3의 AST와 값을 단계별로 구하라.

  1. 첫 T는 F의 10이고 뒤가 −여서 U는 빈 꼬리다. acc=Num(10)으로 시작한다.

  2. 첫 − 뒤 T는 4다. 다음 토큰이 −라 곱셈 꼬리가 끝나고 acc=Sub(10,4)가 된다.

  3. 다음 − 뒤 T는 2*3을 읽어 Mul(2,3)으로 만든다. 입력 끝에서 U,R의 빈 꼬리를 허용한다.

  4. 최종 AST는 Sub(Sub(10,4),Mul(2,3))다. 10−4=6,2*3=6,6−6=0이다. 오른쪽 누적하면 10−(4−6)=12여서 잘못된 결합 의미가 된다.

왼쪽 누적과 곱셈 우선순위를 보존한 AST의 값은 0이다.

18−2^3^2*2−4의 값과 잘못된 지수 누적의 값을 구하라.

  1. 올바른 지수는 3²=9, 2⁹=512이며 곱셈은 1024다.

구문 오류와 복구

첫 오타에서 멈추지 않고 다음 문장의 오류까지 찾으려면 무엇을 버려야 할까?

준비 개념과 학습 목표

준비 개념

  • 토큰 위치와 기대 토큰, 입력 끝 EOF 표시를 준비한다.

  • 정상 AST 노드와 ErrorStmt 같은 오류 표시 노드를 구분한다.

  • 복구는 사용자의 의도를 증명하는 일이 아니라 다음 분석 지점을 찾는 정책이다.

학습 목표

  • 오류 검출 지점·발생 원인·복구 지점을 구별한다.

  • 단순 동기화 정책의 진행·EOF·블록 경계 조건을 종이로 추적한다.

괄호 안의 세미콜론에서 동기화하면 다음 정상 문장을 보존할 수 있을까?

기본 문장 S→id=E;와 숫자·+·괄호 식을 유지한다. 입력 위치는 0부터 세는 토큰 인덱스다. 기본 정책 B는 오류 뒤 처음 ;를 소비한다. 비교 정책 D는 오류가 난 문장의 이미 열린 괄호 깊이를 이어받고, 건너뛰는 (에서 +1, )에서 양수 깊이를 −1로 바꾸며 깊이 0의 ;만 소비하여 동기화한다.

D에서도 현재 블록의 }는 깊이와 관계없이 소비하지 않고 문장 단계를 끝내 상위 블록 분석기에 남긴다. EOF는 즉시 종료한다. 이 언어의 식에는 블록이 없으며 건너뛰는 {는 일반 오류 토큰이다. 정책 D는 소스의 의도를 복구하는 것이 아니라 정해진 경계까지 버리는 모형이다.

건너뛰는 정상/오류 토큰은 한 번씩 소비한다. }에서 소비가 없으면 반드시 현재 호출이 끝나고 상위가 처리한다. 오류 노드를 반환하고 같은 위치에서 같은 문장 호출을 반복하면 이 진행 보장이 깨진다. 진단 수·보존한 정상 문장 수·종료 여부를 분리해 평가한다.

오류를 어디서 알아차리는가

예측표의 비어 있는 칸이나 기대 단말과 실제 토큰의 불일치에서 구문 오류를 검출한다. x=3+;에서는 + 뒤 피연산자를 기다리다가 ;에서 오류를 알 수 있다. 검출 위치는 누락이 드러난 지점이며 실제 원인이 그 토큰 자체라고 확정되는 것은 아니다.

진단에는 소스 범위, 실제 토큰, 그 파서 상태에서 가능한 기대 범주를 함께 기록한다. 피연산자가 필요하다는 설명은 전체 문법을 나열하는 것보다 다음 행동을 이해하기 쉽다. 예상 기대 집합도 현재 문법·파서 상태에 의존한다. 선언되지 않은 이름이나 타입 불일치는 토큰 순서가 유효해도 이후 단계에서 보고될 수 있다.

단순 문장 단위 동기화

작은 언어의 문장 S→id = E ;, 식 E는 숫자와 +, 괄호로 만든다고 하자. 문장 내부 구문 오류가 나면 해당 문장의 부분 AST를 버리고 ;, 현재 블록의 }, EOF 중 하나까지 토큰을 건너뛴다. ;는 소비하고 ErrorStmt를 반환한다. }는 블록 분석기에 남겨 그 분석기가 소비하며 EOF에서는 더 읽지 않고 종료한다. 이는 설명을 위해 정한 panic-mode 정책이다.

정상 문장까지 건너뛸 수 있고 여러 오류가 한 진단으로 합쳐질 수 있다. 특히 누락된 ; 때문에 다음 문장 토큰까지 버릴 수 있다. 이 정책은 괄호 깊이나 중첩된 블록을 정교하게 추적하지 않으므로 범용 언어의 최적 복구가 아니다. 실제 파서의 오류 토큰·스택 되감기·몇 토큰의 성공 여부 검사 등과 구체 정책을 구별한다.

분석을 계속해도 성공은 아니다

복구한 AST에는 정상 문장과 ErrorStmt가 함께 있을 수 있다. 이후 의미 검사에서는 오류 노드를 정상 값으로 취급하지 않아 불필요한 추가 오류를 줄인다. 복구 성공은 입력 전체가 문법에 맞거나 프로그램을 안전하게 실행할 수 있다는 뜻이 아니다. 최종 진단 상태에 오류가 있음을 유지한다.

반복이 반드시 진행하도록 소비 또는 호출 단계 종료가 필요하다. ;를 찾았는데 소비하지 않고 같은 문장 분석을 재호출하면 같은 오류가 반복된다. }를 남길 때는 상위 블록 분석기로 복귀하여 소비하게 한다. EOF를 찾을 때까지 무조건 scan하면 EOF에서 무한 반복할 수 있으므로 명시적으로 멈춘다. 복구 경로에도 유한 입력 종료의 증명이 필요하다.

}는 블록 분석기가 소비하고 y의 처리 여부는 바깥 문맥에 달려 있다.

흔한 오답에서 다시 생각하기

깊이가 1이라 }도 건너뛰고 같은 블록에서 y를 읽는다.

이 정책은 }를 즉시 상위 경계로 정했다. 괄호 깊이로 블록 경계를 삼키지 않는다.

연습 2 · 오류 찾아 고치기

복구에서 }를 소비하지 않고 ErrorStmt를 반환한 뒤 같은 문장 함수를 같은 위치에서 재호출한다. 진행 오류를 고쳐라.

힌트 1

입력 위치가 바뀌지 않았다.

힌트 2

소비하지 않는 분기에는 호출 종료와 상위 소유권이 필요하다.

풀이와 답 확인

  1. 현재 문장 목록의 반복을 끝내 상위 블록 함수로 복귀한다.

  2. 상위 블록 함수가 }를 소비하고 종료한다. EOF라면 전체 입력 분석을 종료한다.

소비하지 않는 분기에는 해당 단계의 종료/상위 처리를 명시한다.

흔한 오답에서 다시 생각하기

ErrorStmt를 만들었으므로 입력이 진행했다.

노드 추가는 토큰 소비가 아니다. 위치와 호출 단계를 함께 추적한다.

연습 3 · 직접 만들어 보기

D의 복구 장부를 깊이 1에서 시작하는 토큰열 ; num ) ; id = num ; EOF에 대해 구성하라.

힌트 1

처음 ;에서는 깊이가 아직 1이다.

힌트 2

)를 소비한 뒤 깊이가 0으로 내려간다.

풀이와 답 확인

  1. 첫 ;와 num을 소비한다. )를 소비해 깊이는 0이다.

  2. 다음 ;를 소비하고 ErrorStmt를 반환한다. id에서 정상 문장을 시작해 Assign을 만들고 EOF에서 종료한다.

복구 소비는 앞 네 토큰이며 뒤 네 토큰은 정상 문장이다.

흔한 오답에서 다시 생각하기

첫 ;에서 동기화하고 num을 새 문장으로 인식한다.

그것은 B 정책이다. D에서는 기존 괄호 깊이를 이어받아 검사한다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

유한 입력에서 D의 종료를 증명하고 복구 품질 인증과 구별하라. 문장 진입까지 이미 소비한 토큰도 고려하라.

힌트 1

일반 복구 반복에서 남은 토큰 수는 줄어든다.

힌트 2

}와 EOF는 반복 대신 단계 종료를 선택한다.

풀이와 답 확인

  1. 일반 토큰과 깊이 0의 ;는 소비하여 남은 유한 토큰 수를 줄인다.

  2. }에서는 현재 문장 호출이 종료되고 상위가 소비한다. EOF에서는 더 호출하지 않는다.

  3. 이미 소비한 접두사를 되돌리지 않고 같은 경계에서 문장 재호출을 금지하면 전체 처리도 진행한다.

  4. 종료는 정상 문장 보존이나 정확한 진단 수를 보장하지 않는다. 미닫힌 괄호 사례가 반례다.

유한 토큰 소비와 경계의 단계 종료로 종료를 보인다. 품질은 별도 장부로 평가한다.

흔한 오답에서 다시 생각하기

모든 복구 반복에서 무조건 토큰을 소비해야 한다.

} 소유권을 상위에 남기는 계약도 종료와 결합하면 가능하다. 단순 소비만이 유일한 진행 방법은 아니다.

한 단계 더

복구의 진행을 세 경우로 검증하라. ; 발견 시 소비하여 입력 위치가 증가한다. } 발견 시 소비는 상위 블록 단계가 맡고 현재 단계는 끝난다. EOF 발견 시 전체 분석을 끝낸다. 건너뛰는 일반 토큰도 매번 하나 소비한다. 이 약속이 없는 복구는 동일 입력 위치에서 되풀이될 수 있다. 더 나은 복구를 평가하려면 정확한 진단·후속 정상 구조 보존·종료성을 별도로 확인해야 하며, 실제 IDE나 생성기 실행 없이 그 품질을 검증했다고 주장하지 않는다.

다른 문제에 적용하기

가상 설정 언어의 문장은 id=E;이며 E/T/P와 지수·곱셈·뺄셈 정책은 보강 2번과 같다. 입력 a=18−2^3^2*2−4; b=(1−); c=3^2^2;를 분석하라. b의 오류 당시 깊이는 1이다. 복구 정책 D를 적용하고 정상 AST/값·검출 토큰·소비 경계·최종 오류 상태를 작성하라. 지수를 잘못 왼쪽 결합하면 a/c에서 어떤 비교 결과가 나오는지도 밝히라.

힌트 1

a의 ^는 오른쪽 자식으로, −는 왼쪽 acc로 조립한다. c의 같은 값은 구조 인증을 대신하지 않는다.

힌트 2

b에서는 − 뒤 )가 나타나 피연산자 기대가 실패한다. D는 그 )를 소비해 깊이를 0으로 내린 다음 ;를 소비한다.

풀이와 답 확인

  1. a의 지수 AST는 Pow(2,Pow(3,2))이며 값은 512다. 곱은 1024이고 왼쪽 뺄셈은 18−1024−4=−1010이다. Assign(a,Sub(Sub(18,Mul(Pow(2,Pow(3,2)),2)),4))를 보존한다.

  2. b에서 1− 뒤의 )가 검출 토큰이다. 깊이 1을 이어받아 )를 소비한 뒤 깊이를 0으로 바꾸고 다음 ;를 소비한다. 부분 대입 AST를 버리고 ErrorStmt 한 개와 진단 한 개를 남긴다.

  3. c는 Pow(3,Pow(2,2))로 값 81인 정상 Assign이다. EOF에서 종료하고 목록 [Assign(a,...),ErrorStmt,Assign(c,...)]를 유지한다.

  4. 지수를 잘못 왼쪽 조립하면 a는 −114로 달라진다. c는 Pow(Pow(3,2),2)여도 값 81이 같으므로 c의 값만 검사해서는 오류를 찾지 못한다.

  5. 정상 대입 두 개와 오류 노드 한 개가 존재해도 전체 입력의 구문 정상 판정은 거부한다. 복구 종료는 실행 허가나 사용자의 의도 복원 증거가 아니다.

a의 정상 값은 −1010, c의 정상 값은 81이다. b는 )에서 오류를 검출해 닫는 괄호와 뒤 세미콜론을 소비하고 ErrorStmt로 남긴다. 진단은 한 개이며 입력 전체는 오류 상태다. 잘못된 지수 묶임은 a의 −114로 검출되지만 c의 값 81에서는 숨으므로 AST 구조도 확인한다.

해결한 뒤 점검할 것

  • 지수의 오른쪽 자식과 뺄셈의 왼쪽 누적을 명시하고 a의 중간값 512/1024 및 최종 −1010을 맞춘다.

  • b의 검출 위치와 실제 원인을 구별하고 기존 깊이 1→0 및 ; 소비 경계를 기록한다.

  • 정상 c와 ErrorStmt를 구별하고 진단 한 개 및 EOF 종료·전체 오류 상태를 유지한다.

  • a의 −114 대 −1010과 c의 같은 값 81/다른 AST를 사용해 결과값만의 인증 한계를 설명한다.
