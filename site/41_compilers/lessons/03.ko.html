소단원 3.1

CFG·AST·모호성

똑같은 8−3−1을 읽었는데 두 답이 나오는 것은 계산 실수일까?

준비 개념과 학습 목표

준비 개념

  • 토큰은 숫자·식별자·연산자처럼 lexer가 분류한 입력 단위다. num 토큰의 값 8과 토큰 종류 num을 구분한다.

  • 트리의 뿌리·자식·잎, 재귀적으로 식을 만드는 구조를 준비한다.

  • 문법의 ε는 빈 토큰열이며 규칙의 |는 여러 대안을 뜻한다.

학습 목표

  • CFG의 유도·파스트리·AST를 구별하고 모호성 반례를 만든다.

  • 구문을 만족하는 것과 변수·타입·실행의 의미가 맞는 것을 분리한다.

문법은 생성 규칙이다

CFG를 G=(N,Σ,P,S)로 둔다. N은 비단말, Σ는 단말 토큰 종류이며 둘은 서로 겹치지 않는다. 시작 S∈N, 생성규칙 P의 왼쪽은 비단말 하나이고 오른쪽은 단말·비단말의 유한 열(ε 포함)이다. A→γ는 어떤 주변 토큰열 안에서도 A를 γ로 바꿀 수 있다는 뜻이다.

S에서 규칙을 유한 번 적용하여 단말만 남는 토큰열 w를 만들면 w∈L(G)다. 파서는 입력을 새로 생성하는 대신 그 입력이 이런 구조로 유도되는지 찾는다. 이름 x가 선언되었는지나 0으로 나누는지는 E→E/E 같은 구조 규칙만으로 보통 결정하지 않고 이후 의미 검사·실행 규칙과 연결한다.

유도 순서와 트리

파스트리는 규칙 적용의 부모·자식 구조를 보존하고 잎을 왼쪽부터 읽으면 입력 토큰열이 된다. 왼쪽 비단말을 먼저 전개한 유도와 오른쪽을 먼저 전개한 유도는 같은 트리를 만들 수 있다. 따라서 유도 단계 순서가 다르다는 사실 하나만으로 문법이 모호하다고 판정하면 안 된다.

문법이 모호하다는 것은 어떤 하나의 토큰열에 서로 다른 파스트리가 적어도 둘 존재한다는 뜻이다. E→E−E | num에서는 num−num−num의 뿌리를 첫 번째 − 또는 두 번째 −에 놓을 수 있다. 산술 해석을 붙이면 8−(3−1)=6과 (8−3)−1=4로 달라져 문제를 드러낸다.

AST는 필요한 구조를 남긴다

AST는 이후 의미 검사와 변환에 필요한 연산·피연산자 구조를 표현한다. Num(8), Sub(left,right) 같은 노드를 쓴다. 모든 문법 비단말과 구두점을 별도 AST 노드로 남길 필요는 없다. 괄호는 AST에서 별도 노드가 없어도 자식 구조를 결정하므로 효과는 보존되어야 한다.

예를 들어 (8−3)−1의 AST는 Sub(Sub(Num(8),Num(3)),Num(1))이다. 소스 위치는 오류 메시지에 유용하여 AST에 부가 정보로 보존할 수 있고, 원문 그대로 다시 인쇄하는 도구는 주석·공백까지 보존하는 구체 구문 표현도 필요할 수 있다. AST에서 구두점을 생략한다는 말은 원문 편집 정보를 모두 버려도 된다는 일반 규칙이 아니다.

중간 과정을 따라가는 예제

E→E−E | (E) | num인 문법에서 8−3−1의 두 구조와 값을 구하고, (8−3)−1에서 괄호가 AST에 미치는 영향을 설명하라.

  1. 왼쪽 결합 트리는 뿌리 E→E−E의 왼쪽 E에 다시 E→E−E를 적용한 구조다. 묶임 (E−E)−E의 괄호는 트리 설명용이며 입력에 괄호 토큰을 추가하는 유도 단계가 아니다.

  2. 잎을 num 값 8,3,1로 채우면 Sub(Sub(8,3),1)이고 8−3=5,5−1=4다.

  3. 오른쪽 구조는 Sub(8,Sub(3,1))이고 3−1=2,8−2=6이다. 둘 다 잎 순서 8,−,3,−,1을 유지한다.

  4. 괄호가 실제 입력에 있는 (8−3)−1은 내부 E를 먼저 묶어 왼쪽 AST를 강제한다. 괄호 노드를 없애더라도 Sub의 중첩을 바꾸면 의미 보존에 실패한다.

같은 무괄호 입력은 값 4 또는 6인 두 트리를 갖는다. (8−3)−1의 AST는 왼쪽 구조이며 괄호 효과가 자식 관계에 남는다.

종이와 본문으로 직접 해보기

E→E+E | num 문법으로 2+5의 왼쪽 우선 유도와 오른쪽 우선 유도를 쓰라. 두 유도가 문법 모호성의 증거인지, 2+5+7에서는 어떤 증거를 쓸 수 있는지 판단하라.

힌트 보기

E⇒E+E 이후 어느 E를 먼저 num으로 바꾸는지와 최종 트리의 뿌리·자식 관계를 분리한다.

풀이 보기

왼쪽 우선 E⇒E+E⇒num+E⇒num+num, 오른쪽 우선 E⇒E+E⇒E+num⇒num+num이다. 둘은 같은 두 자식 트리라 이것만으로 모호성 증거가 아니다. 2+5+7에는 Add(Add(2,5),7)과 Add(2,Add(5,7))의 서로 다른 트리가 있다. 덧셈 값이 둘 다 14라도 트리 구조가 달라 모호성은 존재한다.

오해와 반례

두 트리가 같은 수치 결과를 내면 문법은 모호하지 않다.

2+5+7의 두 결합은 같은 14여도 트리는 다르다. 모호성은 수치 결과가 아니라 문법적 구조의 유일성에 관한 성질이다. 반대로 왼쪽·오른쪽 유도가 다르더라도 같은 트리이면 그 차이만으로 모호성은 아니다.

한 단계 더

모호성을 증명하려면 하나의 문자열과 두 서로 다른 트리면 충분하지만, 몇 개 문자열에서 유일한 트리를 찾았다고 모든 문자열이 비모호하다고 증명되지는 않는다. 왼쪽 우선 유도는 트리 하나를 정하면 전개 순서가 고정되므로 서로 다른 왼쪽 우선 유도 둘을 구하는 것도 모호성 증거다. 연산의 실제 평가 순서·부작용은 AST 묶임뿐 아니라 언어의 의미 규칙도 함께 확인해야 한다.

소단원 3.2

문법 변형과 우선순위

파서를 위해 문법을 바꾸면 10−4−2의 뜻까지 달라져도 될까?

준비 개념과 학습 목표

준비 개념

  • 우선순위는 다른 연산의 묶임, 결합성은 같은 층의 연속 연산 묶임을 뜻한다.

  • 좌재귀 A→Aα는 입력 소비 전에 A를 재호출하게 만들 수 있다.

  • 문법 변형은 생성 토큰열의 보존과 AST 의미 보존을 각각 검사한다.

학습 목표

  • 우선순위 층과 결합 방향을 문법·AST에서 표현한다.

  • 좌재귀 제거·좌인수분해의 목적과 적용 한계를 설명한다.

연산 층을 구분하기

정수 계산의 예로 E→E−T | T, T→T*F | F, F→num | (E)를 둔다. E는 낮은 우선순위 뺄셈, T는 곱셈, F는 숫자 또는 명시적 괄호를 표현한다. 괄호 없이 E가 T 아래로 들어가는 규칙이 없어 곱셈보다 뺄셈을 먼저 묶는 트리를 막는다.

E→E−T의 왼쪽 E 재귀는 같은 층 뺄셈을 왼쪽으로 묶는다. 10−4−2는 (10−4)−2다. 오른쪽 재귀 E→T−E | T는 10−(4−2)를 표현한다. 우선순위와 결합성을 따로 명세하지 않으면 파서의 우연한 선택이 언어 의미를 대신한다.

좌재귀 제거와 AST 보존

단순 예측 재귀하강에서는 E가 입력을 소비하기 전에 E를 부르므로 직접 좌재귀가 문제다. 위 문법을 E→T R, R→−T R | ε, T→F U, U→*F U | ε로 바꿀 수 있다. F는 그대로 둔다. 반복하는 토큰열은 같지만 R,U의 꼬리 재귀 트리가 원래 왼쪽 연산 AST를 저절로 만들어주지는 않는다.

AST는 먼저 첫 T를 acc로 두고 다음 −T마다 acc=Sub(acc,nextT)로 왼쪽 누적하여 만든다. 곱셈도 같은 방식이다. 직접 좌재귀 제거는 모든 LL(1) 문제를 자동으로 없애지 않으며 간접 좌재귀·nullable·FIRST/FOLLOW 충돌도 검사해야 한다. LR 계열은 좌재귀를 처리할 수 있어 모든 파서에서 좌재귀 문법이 잘못인 것은 아니다.

공통 접두사를 미루기

A→id ( E ) | id = E처럼 대안의 첫 토큰이 같은 경우 한 토큰만 보고 선택할 수 없다. A→id B, B→( E ) | = E로 좌인수분해하면 id를 읽은 뒤 다음 토큰 ( 또는 =로 결정한다. 이 변형은 접두사를 공유하는 선택 위치를 뒤로 미루며 연산 결합성 문제와는 별개다.

LL(1) 표는 대안의 시작 토큰 FIRST와 빈열 가능성, 뒤따르는 토큰 FOLLOW를 함께 사용한다. 예를 들어 R→−T R | ε에서 −이면 반복하고 적절한 FOLLOW(E), 여기서는 ) 또는 입력 끝에서 빈 꼬리를 고른다. 아무 토큰에서나 ε를 고르면 잘못된 입력을 조용히 통과시킬 수 있다. 괄호 예측이 가능해도 닫는 괄호의 실제 일치는 검사해야 한다.

중간 과정을 따라가는 예제

E→T R,R→−T R|ε,T→F U,U→*F U|ε,F→num|(E)를 사용하고 −는 왼쪽 누적 AST를 만든다. 10−4−2*3의 AST와 값을 단계별로 구하라.

  1. 첫 T는 F의 10이고 뒤가 −여서 U는 빈 꼬리다. acc=Num(10)으로 시작한다.

  2. 첫 − 뒤 T는 4다. 다음 토큰이 −라 곱셈 꼬리가 끝나고 acc=Sub(10,4)가 된다.

  3. 다음 − 뒤 T는 2*3을 읽어 Mul(2,3)으로 만든다. 입력 끝에서 U,R의 빈 꼬리를 허용한다.

  4. 최종 AST는 Sub(Sub(10,4),Mul(2,3))다. 10−4=6,2*3=6,6−6=0이다. 오른쪽 누적하면 10−(4−6)=12여서 잘못된 결합 의미가 된다.

왼쪽 누적과 곱셈 우선순위를 보존한 AST의 값은 0이다.

종이와 본문으로 직접 해보기

같은 문법과 정책으로 10−4−2와 10−(4−2)를 계산하라. A→id(E)|id=E의 공통 접두사를 분해하고, id 다음 토큰 num을 만나면 어느 대안인지 판단하라.

힌트 보기

무괄호는 첫 T부터 왼쪽 누적한다. 괄호는 F 안에서 새로운 E를 만든다. B의 FIRST는 (와 = 두 가지다.

풀이 보기

10−4−2는 Sub(Sub(10,4),2)=4, 10−(4−2)는 Sub(10,Sub(4,2))=8이다. A→id B,B→(E)|=E로 바꾸며 id 다음 num은 어느 대안의 시작도 아니라 구문 오류다. 좌인수분해가 잘못된 토큰을 새로운 허용 구문으로 바꾸는 것은 아니다.

오해와 반례

문법이 같은 토큰열을 생성하면 AST와 프로그램 뜻도 자동으로 같다.

10−4−2는 왼쪽 AST에서 4, 오른쪽 AST에서 8이다. 좌재귀 제거 뒤에도 왼쪽 누적 행동을 명시해야 한다. 언어 동치와 의미 보존은 별도 의무이며 단순 구조 변경을 안전한 최적화라고 부를 수 없다.

이미 읽은 왼쪽 결과를 새 노드의 왼쪽 자식으로 보존한다.

한 단계 더

반복 k회 뒤 acc가 처음 k+1개 항의 왼쪽 결합 AST라는 불변식을 증명하라. 0회에서는 첫 항 자체다. k회가 맞다고 가정하면 새 항을 Sub(acc,next)의 오른쪽에 붙여 k+1회의 왼쪽 묶임을 얻는다. 지수 연산처럼 오른쪽 결합이 명세인 경우에는 이 누적을 그대로 쓰면 안 된다. 같은 우선순위 표라도 단항 연산·괄호·오류 토큰을 포함한 경계 사례를 별도로 확인해야 한다.

소단원 3.3

구문 오류와 복구

첫 오타에서 멈추지 않고 다음 문장의 오류까지 찾으려면 무엇을 버려야 할까?

준비 개념과 학습 목표

준비 개념

  • 토큰 위치와 기대 토큰, 입력 끝 EOF 표시를 준비한다.

  • 정상 AST 노드와 ErrorStmt 같은 오류 표시 노드를 구분한다.

  • 복구는 사용자의 의도를 증명하는 일이 아니라 다음 분석 지점을 찾는 정책이다.

학습 목표

  • 오류 검출 지점·발생 원인·복구 지점을 구별한다.

  • 단순 동기화 정책의 진행·EOF·블록 경계 조건을 종이로 추적한다.

오류를 어디서 알아차리는가

예측표의 비어 있는 칸이나 기대 단말과 실제 토큰의 불일치에서 구문 오류를 검출한다. x=3+;에서는 + 뒤 피연산자를 기다리다가 ;에서 오류를 알 수 있다. 검출 위치는 누락이 드러난 지점이며 실제 원인이 그 토큰 자체라고 확정되는 것은 아니다.

진단에는 소스 범위, 실제 토큰, 그 파서 상태에서 가능한 기대 범주를 함께 기록한다. 피연산자가 필요하다는 설명은 전체 문법을 나열하는 것보다 다음 행동을 이해하기 쉽다. 예상 기대 집합도 현재 문법·파서 상태에 의존한다. 선언되지 않은 이름이나 타입 불일치는 토큰 순서가 유효해도 이후 단계에서 보고될 수 있다.

단순 문장 단위 동기화

작은 언어의 문장 S→id = E ;, 식 E는 숫자와 +, 괄호로 만든다고 하자. 문장 내부 구문 오류가 나면 해당 문장의 부분 AST를 버리고 ;, 현재 블록의 }, EOF 중 하나까지 토큰을 건너뛴다. ;는 소비하고 ErrorStmt를 반환한다. }는 블록 분석기에 남겨 그 분석기가 소비하며 EOF에서는 더 읽지 않고 종료한다. 이는 설명을 위해 정한 panic-mode 정책이다.

정상 문장까지 건너뛸 수 있고 여러 오류가 한 진단으로 합쳐질 수 있다. 특히 누락된 ; 때문에 다음 문장 토큰까지 버릴 수 있다. 이 정책은 괄호 깊이나 중첩된 블록을 정교하게 추적하지 않으므로 범용 언어의 최적 복구가 아니다. 실제 파서의 오류 토큰·스택 되감기·몇 토큰의 성공 여부 검사 등과 구체 정책을 구별한다.

분석을 계속해도 성공은 아니다

복구한 AST에는 정상 문장과 ErrorStmt가 함께 있을 수 있다. 이후 의미 검사에서는 오류 노드를 정상 값으로 취급하지 않아 불필요한 추가 오류를 줄인다. 복구 성공은 입력 전체가 문법에 맞거나 프로그램을 안전하게 실행할 수 있다는 뜻이 아니다. 최종 진단 상태에 오류가 있음을 유지한다.

반복이 반드시 진행하도록 소비 또는 호출 단계 종료가 필요하다. ;를 찾았는데 소비하지 않고 같은 문장 분석을 재호출하면 같은 오류가 반복된다. }를 남길 때는 상위 블록 분석기로 복귀하여 소비하게 한다. EOF를 찾을 때까지 무조건 scan하면 EOF에서 무한 반복할 수 있으므로 명시적으로 멈춘다. 복구 경로에도 유한 입력 종료의 증명이 필요하다.

중간 과정을 따라가는 예제

S→id=E;에서 숫자 식은 num과 +만 사용한다. 문장 단위 복구는 ;까지 버리고 ;를 소비하며 EOF에서는 종료한다. 입력 x=3+; y=4; z=;의 토큰 순서와 결과 AST를 추적하라.

  1. x=3+까지 읽고 피연산자를 기대하지만 다음은 ;다. 그 위치에 피연산자 필요 진단을 기록한다.

  2. 첫 ;가 바로 동기화 토큰이므로 소비하고 x 문장을 ErrorStmt로 둔다. y 토큰에서 새 문장을 시작한다.

  3. y=4;는 정상이며 Assign(y,Num(4))를 만든다. z= 뒤 ;에서 다시 피연산자 누락을 검출한다.

  4. 마지막 ;를 소비하여 z는 ErrorStmt, EOF에서 종료한다. AST 목록은 [ErrorStmt,Assign(y,4),ErrorStmt]이고 진단 2개가 남는다. 오류 노드를 0값 대입으로 바꾸지 않는다.

중간 y 문장을 보존하며 두 오류를 보고한다. 분석 종료와 프로그램 정상 판정은 다르다.

종이와 본문으로 직접 해보기

같은 정책에서 x=3 y=4; z=5;를 추적하라. 또 블록 안에서 x=3+ }를 만나면 }를 누가 처리해야 하는가?

힌트 보기

x=3 뒤 +나 ;가 아닌 y가 와서 문장 끝 기대가 어긋난다. 첫 ;까지 복구가 버리는 범위를 표시한다.

풀이 보기

x 문장의 오류 검출 토큰은 y다. 첫 ;까지 y=4도 건너뛰고 ;를 소비하여 첫 문장 전체는 ErrorStmt가 된다. z=5;는 정상으로 남는다. 따라서 y가 올바른 별도 문장일 가능성이 있어도 단순 복구는 보존하지 못한다. x=3+ }에서는 }를 소비하지 않은 채 문장 오류를 반환하고, 상위 블록 분석기가 }를 소비하여 블록을 끝낸다. EOF이면 종료하며 없는 토큰을 계속 찾지 않는다.

오해와 반례

오류 뒤 끝까지 읽었다면 프로그램이 고쳐진 것이다.

ErrorStmt와 진단이 남은 AST는 일부 구조를 분석했을 뿐이다. 사용자가 원한 피연산자가 무엇인지 알 수 없다. x=3 y=4; 예에서 단순 복구가 정상 후보 y까지 버리는 것은 복구의 한계를 보여주며 진단 개수도 실제 오타 수와 같다고 보장하지 않는다.

한 단계 더

복구의 진행을 세 경우로 검증하라. ; 발견 시 소비하여 입력 위치가 증가한다. } 발견 시 소비는 상위 블록 단계가 맡고 현재 단계는 끝난다. EOF 발견 시 전체 분석을 끝낸다. 건너뛰는 일반 토큰도 매번 하나 소비한다. 이 약속이 없는 복구는 동일 입력 위치에서 되풀이될 수 있다. 더 나은 복구를 평가하려면 정확한 진단·후속 정상 구조 보존·종료성을 별도로 확인해야 하며, 실제 IDE나 생성기 실행 없이 그 품질을 검증했다고 주장하지 않는다.
