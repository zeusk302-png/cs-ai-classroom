소단원 8.1

활성 레코드와 ABI

재귀 함수가 같은 이름의 변수를 여러 번 만들 때 어디에 구분해 놓을까?

준비 개념과 학습 목표

준비 개념

  • 함수 호출은 인자를 받고 결과와 제어를 돌려준다.

  • 레지스터와 메모리는 값을 담는 장소다.

학습 목표

  • 호출마다 필요한 상태와 복귀를 설명한다.

  • 명시된 ABI에서 인자·반환·보존 규칙을 추적한다.

혼합 인자의 두 번째 정수는 왜 RDX에 들어가지 않을까?

일반 Windows x64 원형 함수 f(Int a, Double b, Int c, Float d, Int e)를 새로 둔다. 각각 2, 3.5, 5, 7.0, 11을 전달한다. 위치는 타입별로 압축해서 세지 않는다. 첫 위치의 정수는 RCX, 두 번째 위치의 Double은 XMM1, 세 번째 위치의 정수는 R8, 네 번째 위치의 Float는 XMM3이며 다섯 번째 정수는 스택이다. varargs와 특별 호출 규약은 이 사례에서 제외한다.

주소 추적은 호출 직전 준비 이전 RSP=0x1000에서 시작한다. 호출자는 shadow space 32바이트, 다섯 번째 인자 슬롯 8바이트, 정렬 여유 8바이트를 위해 48바이트를 빼서 RSP=0x0FD0을 만든다. 호출 명령이 8바이트 복귀 주소를 추가한 뒤 피호출자 진입 RSP는 0x0FC8이다. 이때 shadow space는 RSP+8부터, 다섯 번째 인자는 RSP+40인 0x0FF0부터다. 이 명시한 배치가 모든 컴파일러의 전체 프레임이라는 주장은 아니다.

복귀 주소는 다음 실행 위치이고 RAX나 XMM0의 반환 값은 데이터다. 호출 전 RAX의 값 9를 호출 뒤에도 쓰려면 volatile 보존을 따로 마련한다. R12를 보존 위치로 골랐다면 그 R12를 바꾸는 현재 함수도 자신의 호출자에게 원래 R12를 복원할 의무가 있다. 저장 책임은 어느 호출의 경계인지 함께 적는다.

먼저 확인할 개념
  • 인자 위치와 volatile 보존 약속

    혼합 인자를 타입별로 압축하지 않고 호출 전후 살아 있는 값을 구별한다.

  • 교육 객체의 this와 실행 위치

    객체 주소라는 데이터 인자와 복귀 코드 위치를 혼동하지 않는다.

호출 한 번의 상태

활성 레코드는 진행 중인 함수 호출의 인자·지역 값·저장 레지스터·복귀 위치 등 필요한 상태를 조직하는 개념이다. 재귀 호출은 같은 코드여도 서로 다른 호출 상태를 가진다. 모든 상태가 반드시 스택 한 덩어리에 실제 존재하는 것은 아니며 레지스터와 최적화로 사라지는 값도 있다.

호출 스택은 마지막 호출이 먼저 끝나는 중첩 수명에 적합하다. f가 g를 부르면 g가 반환한 뒤 f의 남은 동작을 진행한다. 반환 주소와 반환 값은 하나는 실행 위치, 다른 하나는 계산 결과이므로 구분한다.

ABI는 양쪽의 약속

Application Binary Interface는 기계 코드 수준에서 인자 전달·반환·레지스터 보존·정렬 등을 맞추는 약속이다. 함수 이름과 인자 수가 같아도 호출 규칙이 다르면 서로의 값을 잘못 읽을 수 있다. 플랫폼·컴파일러·특수 호출 규약별 조건을 적어야 한다.

공식 Windows x64의 일반 정수 인자는 첫 네 위치 RCX,RDX,R8,R9를 사용하고 이후는 스택이다. 호출자는 네 레지스터 인자용32바이트 shadow space를 준비한다. 부동소수 인자는 위치에 맞는 XMM을 쓰므로 정수 전용 예제 규칙을 그대로 확대하지 않는다.

호출 전후 살아 있어야 할 값

호출로 바뀔 수 있는 volatile 레지스터 값이 뒤에서도 필요하면 호출자 쪽에서 적절히 보존해야 한다. 보존 약속이 있는 nonvolatile 레지스터를 변경하는 피호출자는 원상 복구 책임이 있다. 한쪽만 모든 레지스터를 항상 저장한다는 규칙이 아니다.

스택 정렬·복귀 주소·shadow space·추가 인자·지역값을 함께 고려해 프레임을 만든다. 이론상 몇 바이트 인자가 필요한지 계산한 것과 실제 컴파일러의 프레임 크기를 관찰한 것은 다르다. 본문은 실제 어셈블리 실행을 하지 않는다.

피호출자의 RAX 결과와 구별

주소 열은 호출 전 기준과 진입 후 기준을 분리한다. 40은 shadow의 크기가 아니라 복귀 주소 8과 shadow 32를 더한 오프셋이다. 저장량 48도 실제 관찰한 최적 프레임 크기가 아니다.

중간 과정을 따라가는 예제

Windows x64 일반 규약으로 정수 f(2,3,5,7,11)를 호출한다고 하자. f는 다섯 수를 더해64비트 정수로 반환한다. 인자 위치와 결과를 구하라.

  1. 첫 번째2는 RCX, 두 번째3은 RDX, 세 번째5는 R8, 네 번째7은 R9다.

  2. 다섯 번째11은 추가 스택 인자 영역에 둔다. 호출자는32바이트 shadow space도 별도로 예약한다.

  3. 합은2+3+5+7+11=28이며64비트 정수 반환 규칙에 따라 RAX의 결과로 받는다.

  4. 32바이트와 추가 인자 슬롯 외에도 정렬·복귀 주소 등이 있어 이를 전체 프레임 크기라고 부르지 않는다.

인자는 네 정수 레지스터와 추가 스택 슬롯, 반환은 RAX의28이다. 실제 컴파일/실행 결과가 아니라 명시 ABI의 종이 추적이다.

조건을 바꾸어 비교하기

타입별 압축 배치가 조용히 값을 바꾼다

호출자가 c=5를 RDX에 넣고 R8에는 이전 값 99를 남겼다. 계약대로 R8에서 c를 읽는 피호출자는 무엇을 받는가?

  1. 세 번째 인자 위치의 일반 정수 슬롯은 R8이다.

  2. 계약대로 읽은 c는 99이며 RDX의 5는 c 전달을 대신하지 않는다.

정한 상태에서 c는 99다. 실제 기계 실행 결과가 아니라 슬롯 계약의 반례다.

비교할 점

같은 인자 수와 같은 함수 이름만으로 ABI 일치가 성립하지 않는다.

값을 보호한 함수도 자기 보존 책임이 있다

현재 함수 F의 호출자에게 받은 R12는 41이다. F가 호출 전 RAX=9를 R12에 옮기고 G를 호출한다. G는 계약대로 R12를 유지하고 RAX=18을 반환한다. F는 무엇을 보존·복원할까?

  1. F는 먼저 원래 R12=41을 안전한 저장소에 둔다. G 뒤 R12=9를 읽어 원래 RAX의 필요한 값을 얻는다.

  2. F가 반환하기 전에 R12를 41로 복원한다. G의 반환 데이터 18과 F가 보존한 데이터 9는 다르다.

9를 잃지 않으면서 원래 R12=41도 호출 경계에서 복원한다.

비교할 점

G의 보존 약속은 F가 자기 호출자의 R12를 덮어도 된다는 허가가 아니다.

종이와 본문으로 직접 해보기

첫 네 정수 인자만 있고 함수가 한 번 더 호출한다면 호출 전의 RCX 값을 반환 뒤에도 필요로 할 때 무엇을 고려할까?

인자 수와 레지스터 보존 약속은 다른 문제다.

RCX는 volatile이라 내부 호출이 바꿀 수 있다. 필요한 값은 스택이나 적절한 보존 위치에 저장해야 한다. 추가 인자가 없더라도 shadow space 약속은 지킨다.

연습 1 · 값과 상태 예측

명시한 f 호출의 진입 RSP와 다섯 번째 인자 주소를 구하고, f가 세 정수 a+c+e만 더해 Int를 반환하면 결과 위치와 값을 적어라.

힌트 1

준비 48바이트와 call의 8바이트를 순서대로 뺀다.

힌트 2

Int 결과는 부동소수 인자 유무와 별개다.

풀이와 답 확인

  1. 진입 RSP는 0x0FC8이고 다섯 번째 인자 주소는 0x0FC8+40=0x0FF0이다.

  2. 정수 합은 2+5+11=18이고 64비트 이내 정수 결과는 RAX다.

진입 0x0FC8, 인자 주소 0x0FF0, RAX의 값 18이다.

흔한 오답에서 다시 생각하기

부동소수 인자가 있으니 모든 결과는 XMM0이다.

반환 타입과 인자의 타입 혼합은 별도 계약이다.

연습 2 · 오류 찾아 고치기

진입 RSP+32인 0x0FE8에 다섯 번째 인자를 썼다. 왜 잘못된가? 이 배치에서 주소를 고쳐라.

힌트 1

진입 RSP에는 복귀 주소가 있다.

힌트 2

shadow space의 마지막 슬롯까지 먼저 센다.

풀이와 답 확인

  1. 진입 RSP+8부터 32바이트 shadow space가 차지하므로 +32는 그 마지막 슬롯 시작이다.

  2. 다섯 번째 인자는 +40인 0x0FF0으로 옮긴다.

복귀 주소를 포함한 진입 기준을 사용해 +40으로 고친다.

흔한 오답에서 다시 생각하기

shadow가 32바이트라 어떤 기준에서도 +32다.

call 전 RSP와 진입 RSP는 8바이트 다르다.

연습 3 · 직접 만들어 보기

F가 RAX=9를 G 뒤에도 사용할 때 R12를 쓰지 않고 스택의 별도 안전한 지역 슬롯으로 보호하는 사건 순서를 작성하라. 슬롯은 G의 shadow 영역과 겹치지 않으며 필요한 정렬·프레임 공간은 준비했다고 가정한다.

힌트 1

G가 사용하는 shadow는 F의 보존 슬롯이 아니다.

힌트 2

저장·호출·복원 순서를 적는다.

풀이와 답 확인

  1. G 호출 전에 별도 지역 슬롯에 9를 저장한다.

  2. G 반환 뒤 해당 슬롯에서 9를 읽는다. G의 RAX 결과가 필요하면 그것도 읽기 전에 별도로 보존한다.

유효한 별도 슬롯의 저장과 복원이 호출을 감싼다.

흔한 오답에서 다시 생각하기

G의 shadow에 저장하면 G가 절대로 쓰지 않는다.

shadow는 피호출자가 인자 저장 등에 사용할 수 있도록 제공한 공간이다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

일반 원형 f의 두 번째 Double 3.5를 XMM1에만 전달하는 조건을 varargs 호출로 바꾸면 무엇이 추가되는가? 값 변환과 전체 프레임을 실제 측정한 것으로 주장하지 말라.

힌트 1

일반 원형과 varargs의 규칙을 분리한다.

힌트 2

두 번째 위치의 일반 정수 레지스터는 RDX다.

풀이와 답 확인

  1. 해당 부동소수 값의 표현을 XMM1뿐 아니라 대응하는 RDX에도 중복 전달하는 규약을 적용한다.

  2. 두 번째 인자 위치는 유지하고 다른 shadow/스택 규칙도 함께 준수한다.

varargs 조건에서 XMM1과 RDX의 대응 전달을 추가한다. 실제 레지스터 비트나 실행은 관찰하지 않았다.

흔한 오답에서 다시 생각하기

varargs에서는 부동소수 값이 오직 스택에만 있다.

공식 규약은 첫 네 위치의 대응 레지스터 중복을 요구한다.

스택·힙·클로저

바깥 함수가 끝난 뒤에도 안쪽 함수가 바깥 값을 기억하려면 무엇이 남아 있어야 할까?

준비 개념과 학습 목표

준비 개념

  • 렉시컬 범위는 소스의 둘러싼 정의를 따른다.

  • 수명은 저장된 값에 유효하게 접근할 수 있는 기간이다.

학습 목표

  • 클로저의 코드와 환경을 분리한다.

  • 탈출하는 값의 수명과 저장 위치를 설명한다.

공유 카운터의 클로저를 복사하면 왜 갱신이 갈라질까?

교육 언어의 makeCounter(2)는 같은 환경 E의 변경 가능한 n을 참조하는 inc와 read를 반환한다. inc는 n을 1 증가시켜 반환하고 read는 현재 n을 반환한다. 바깥 호출이 끝난 뒤 inc, read, inc를 순서대로 호출하면 3, 3, 4다. 각 클로저에 n=2를 독립 복사하면 첫 inc 뒤 read는 2여서 공유 참조 의미를 깨뜨린다. 이 언어 모델은 실제 C++·JavaScript의 캡처 문법이 아니다.

다른 makeCounter(10)의 환경 F는 E와 별개다. 같은 read 코드 주소라도 환경 포인터가 다르면 10을 읽는다. 호출자의 지역 n=99가 있어도 렉시컬 환경의 E.n을 읽는 의미는 바뀌지 않는다. 클로저 코드만 비교해 함수값이나 상태를 같은 것으로 합치면 안 된다.

바이트 장부는 자체 모델로 클로저 한 개를 16바이트, 공유 환경 한 개를 24바이트로 정한다. 두 클로저와 한 환경은 56바이트다. 같은 변경 변수를 각 환경에 복사한 두 환경은 80바이트이며 크기뿐 아니라 결과도 다르다. 이 값은 실제 allocator의 헤더·정렬·GC 비용을 포함하지 않는다. read를 전역 보관하면 그 환경의 수명은 바깥 반환보다 길다. 반환 문장이 없더라도 전역 저장으로 탈출할 수 있다.

  • 호출 상태의 수명과 복귀

스택 수명과 힙 수명

스택은 호출 중첩과 함께 생성·해제할 수 있는 임시 상태에 적합하다. 함수가 반환하면 그 호출의 스택 저장 공간을 계속 유효하다고 가정할 수 없다. 힙은 호출 하나보다 오래 살아야 하는 객체를 배치할 수 있는 공간이며 해제/회수 규칙이 필요하다.

지역변수라는 문법이 스택 배치를 확정하지는 않는다. 값은 레지스터·스택·힙에 놓이거나 최적화로 없어진다. 중요한 것은 프로그램의 관찰 가능한 동작과 유효 수명을 보존하는 것이다.

코드만으로 부족한 함수값

클로저는 실행할 코드와 그 코드의 자유변수를 찾을 환경을 함께 담는다. makeAdder(n)가 x↦x+n을 반환하면 같은 코드라도 n=3과 n=8의 환경이 달라 다른 함수값이다. 호출은 개념적으로 code(environment,x)로 바꿀 수 있다.

환경은 값 복사 또는 공유 참조 등 언어의 캡처 의미를 따라야 한다. 여러 클로저가 같은 변경 가능한 변수를 공유한다면 독립 복사로 바꾸면 서로의 갱신을 못 보게 된다. 클로저가 있다는 사실만으로 복사/참조 정책이 정해지는 것은 아니다.

탈출 분석과 유효성

함수 결과로 반환되거나 더 오래 사는 저장소에 넣은 클로저는 바깥 호출 뒤에도 쓰일 수 있다. 캡처한 환경을 이미 끝난 스택 칸에만 남겨 두면 잘못된 접근이 된다. 이런 수명을 힙이나 적절한 다른 전략으로 보존한다.

탈출하지 않고 바깥 함수가 진행 중일 때만 호출하는 클로저는 환경을 스택에 둘 수도 있다. 최적화가 안전하다고 증명할 때의 선택이며 모든 클로저가 반드시 힙을 쓴다는 법칙은 아니다. 회수도 도달성/소유권 등 언어 런타임의 정책에 따르므로 함수 반환과 동일하지 않다.

불변 n을 값으로 캡처하는 교육 모델에서 f=makeAdder(3), g=makeAdder(8)를 만들고 바깥 호출이 둘 다 끝난 뒤 f(5),g(5)를 계산하라.

공유와 복사의 관찰 가능한 차이

inc와 read가 같은 E를 참조할 때와 각각 초기 n=2를 복사할 때 inc, read, inc의 반환을 비교하라.

  1. 공유에서는 E의 n이 2→3→3→4라서 반환은 3, 3, 4다.

  2. 독립 복사에서는 inc 환경만 2→3→4이고 read 환경은 2이므로 반환은 3, 2, 4다.

가운데 결과가 3 대 2로 달라 독립 복사는 이 공유 계약을 보존하지 않는다.

소단원 8.3

객체 배치와 동적 호출

같은 메서드 이름으로 부르는데 서로 다른 객체가 다른 코드를 실행하는 까닭은 무엇일까?

준비 개념과 학습 목표

준비 개념

  • 객체는 필드 상태와 동작을 함께 설명한다.

  • 정적 타입과 실행 시 실제 타입은 다를 수 있다.

학습 목표

  • 배치·정렬·패딩을 명시된 모델에서 계산한다.

  • 가상 테이블을 통한 동적 호출을 추적한다.

기반 부분을 가리키는 주소를 전체 객체로 읽으면 무엇이 어긋날까?

새 교육 배치 A는 vptr의 크기와 정렬을 각각 8바이트로, flag의 크기와 정렬을 각각 1바이트로 정한다. d의 크기와 정렬은 각각 8바이트이며 x의 크기와 정렬은 각각 4바이트다. 필드는 vptr, flag, d, x 순서로 놓아 각각의 시작 오프셋은 0, 8, 16, 24바이트다. 마지막 필드의 끝은 28바이트이고 객체 정렬 8바이트에 맞춘 전체 크기는 32바이트다. flag와 d 사이 패딩은 7바이트이며 끝 패딩은 4바이트다. 순서를 vptr, d, x, flag로 바꾼 별도 교육 배치 B에서는 각 필드의 시작 오프셋이 각각 0, 8, 16, 20바이트이며 전체 크기는 24바이트다. 언어에서 필드 재배치가 허용된다는 주장이 아니라 서로 다른 명시 배치를 비교한다.

별도 다중 부분 객체 M은 전체 크기 32바이트, 전체 시작 주소 1000, 보조 기반 B 부분 시작 1016, 전체 기준 x 오프셋 24와 값 7을 갖는다. B 부분의 가상 슬롯은 D의 메서드로 가기 전에 this에서 16을 빼는 조정 루틴을 지정한다. 메서드는 전체 기준 this+24를 읽고 10을 더한다. 따라서 B 포인터 1016→전체 this 1000→필드 주소 1024→결과 17이다. 이 주소 모델은 앞의 배치 A/B와도 독립이다.

조정을 생략해 1016+24=1040을 읽으면 정한 32바이트 객체 범위 밖이다. 그 위치의 값을 임의로 7이나 0으로 정해 오답 결과를 계산하지 않는다. 메서드 선택이 맞아도 this의 의미가 틀리면 호출 계약은 실패한다. 반대로 테이블 주소만 같다고 객체의 필드 상태도 같은 것은 아니다. 원시 메모리에는 포인터와 패딩도 있으므로 값 직렬화와 그대로 전송하는 일을 구별한다.

먼저 확인할 개념
  • 필드 정렬·가상 표·this 조정

    전체 객체 주소와 기반 부분 주소를 분리하고 모델 범위를 유지한다.

  • ABI 전달 약속과 반환 데이터

    메서드 주소 선택과 this 인자의 위치·의미를 함께 맞춘다.

객체도 바이트 배치가 필요하다

컴파일러는 필드·기반 클래스 부분·런타임 정보 등을 규약에 맞는 위치에 둔다. 자료형 정렬 때문에 빈 패딩 바이트가 생길 수 있다. 선언한 필드 크기 합만으로 전체 객체 크기를 확정할 수 없다.

언어 의미와 ABI 구현은 구별한다. 모든 언어가 객체마다 가상 테이블 포인터 하나를 두는 것은 아니며, C++도 상속 형태와 ABI에 따라 배치가 복잡하다. 아래 계산은 실제 특정 컴파일러 관찰이 아닌 명시한 교육 모델이다.

실제 타입으로 동작 고르기

교육 모델에서 객체 첫 칸 vptr은 해당 실제 타입의 함수 테이블을 가리킨다. 호출자는 정해진 슬롯을 읽어 함수 주소를 얻고 객체 주소를 this 인자로 넘긴다. 기반 참조여도 객체가 파생 타입이면 재정의된 슬롯의 함수가 선택된다.

정적 호출은 호출할 함수가 컴파일 시 결정되는 방식이다. 동적 호출도 컴파일러가 실제 타입을 증명하면 직접 호출로 바꿀 수 있으므로 모든 소스 가상 호출이 실행 때 간접 분기를 쓴다고 단정하지 않는다.

서로 다른 배치의 연결

다중 상속에서는 기반 부분을 가리키는 포인터가 전체 객체 시작과 다를 수 있다. 이때 메서드가 기대하는 this로 조정하는 경로가 필요하다. 공식 ABI는 테이블·보조 테이블·조정 루틴을 상세히 정한다.

객체 메모리를 다른 실행 환경에 원시 바이트로 보내면 포인터·정렬·ABI가 맞지 않을 수 있다. 저장/통신에는 값 의미를 표현하는 직렬화 규칙을 따로 정의한다. 교육 배치의 오프셋을 모든 언어의 표준으로 사용하지 않는다.

교육 ABI는 vptr8바이트/정렬8, 필드 x,y는 각4바이트/정렬4, flag는1바이트/정렬1이다. 선언 순서대로 놓고 객체 정렬8로 끝을 맞춘다. 객체의 vptr은 Derived 표, slot0은 x+10을 반환하는 메서드다. x=7인 호출을 추적하라.

  1. vptr은0~7, x는8~11, y는12~15, flag는16에 놓인다.

  2. 다음 빈 위치17을8의 배수24로 올려 끝 패딩17~23의7바이트를 둔다.

  3. 기반 참조로slot0을 호출해도 현재 vptr의 Derived 함수 주소를 읽는다.

조건을 바꾸어 비교하기

필드 합과 실제 정렬 장부가 다르다

배치 A/B의 필드 크기 합은 모두 21바이트다. 두 전체 크기와 패딩을 구하라.

  1. A는 flag 뒤 7바이트와 끝 4바이트를 더해 21+11=32바이트다.

  2. B는 끝 21을 24로 올려 끝 패딩 3바이트를 더한다.

필드 합은 같지만 명시한 전체 크기는 32와 24바이트다.

비교할 점

배치를 바꾸는 권한·외부 ABI·관찰 가능 오프셋을 따지기 전에 실제 객체 최적화로 주장하지 않는다.

올바른 함수 주소에도 잘못된 this가 전달될 수 있다

M의 B 슬롯에서 D 메서드 주소를 맞게 찾았지만 조정 없이 this=1016을 전달했다. 정상 경로와 비교하라.

  1. 정상 경로는 16을 빼서 1000을 전달하고 x 주소 1024의 7을 읽어 17을 얻는다.

  2. 잘못된 경로는 x 주소를 1040으로 계산해 정한 객체 밖을 가리킨다.

잘못된 호출의 숫자 결과는 지정하지 않는다. 실제 위험한 메모리 실행도 수행하지 않았다.

동일 이름 메서드와 다른 실제 타입 두 객체를 그리고 표의slot0만 달라지는 상황을 추적하라. 다중 상속 this 조정은 다음 심화 주제로 남기고 단일 포인터 모델의 범위를 명시한다.

다른 문제에 적용하기

세 계약을 하나의 감사 장부로 연결하라. ① 일반 원형 f(Int,Double,Int,Float,Int)에 2, 3.5, 5, 7.0, 11을 전달하는 위치와 진입 RSP=0x0FC8에서 다섯째 인자 주소를 적어라. f는 정수 셋의 합만 Int로 반환한다. ② E.n=2를 공유하는 inc/read에 inc, read, inc를 호출한 뒤 다른 F.n=10의 read와 비교하라. 두 E 클로저/한 환경의 장부는 16+16+24바이트다. ③ 전체 크기 32바이트, 전체 시작 1000, 보조 B 시작 1016인 M에서 D 슬롯은 this를 −16 조정하고 전체 기준 +24의 x=7에 10을 더한다. 정상 경로와 조정 누락을 비교하라. 실제 ABI·클로저·C++ 실행이나 학생 실험은 하지 않는다.

힌트 1

① 타입별 개수가 아니라 전체 인자 위치를 센다. call의 복귀 주소 8바이트와 shadow 32바이트를 진입 기준에서 합친다.

힌트 2

② 갱신을 보는 환경은 코드 주소와 별도다. ③ 함수 주소가 맞아도 this 기준은 먼저 고쳐야 한다.

풀이와 답 확인

  1. ① RCX=2, XMM1=3.5, R8=5, XMM3=7.0이며 다섯째 11은 진입 기준 +40인 0x0FF0에 있다. 정수 반환은 RAX의 18이다.

  2. ② E의 호출 반환은 3, 3, 4이고 F의 read는 10이다. 두 E 클로저와 환경의 명시 장부는 56바이트이며 환경 독립 복사로 가운데 값을 2로 바꾸면 공유 의미를 깨뜨린다.

  3. ③ 정상은 1016→1000→1024에서 7을 읽어 17을 반환한다. 조정 없이 1040을 읽는 경로는 정한 [1000,1032) 밖이며 숫자 결과를 지정하지 않는다.

인자 위치·반환 데이터·환경 공유·유효 수명·this 조정을 서로 다른 계약으로 확인한다. 정수 반환은 18이다. E의 세 반환은 3, 3, 4이고 F의 read 반환은 10이다. 정상 객체 호출의 반환은 17이며 잘못된 범위 접근의 값은 미지정이다.

해결한 뒤 점검할 것

  • 다섯 인자 각각의 위치를 명시한다. 다섯째 인자는 진입 스택 주소에서 40바이트 뒤인 0x0FF0에 있으며 Int 반환 값은 18임을 확인한다.

  • 환경 E의 inc, read, inc 호출 반환은 순서대로 3, 3, 4임을 계산한다. 별도 환경 F의 read 반환은 10이며 두 E 클로저와 공유 환경의 장부 합은 56바이트임을 확인한다.

  • this의 부분 기준과 전체 기준을 구분하고 정상 주소 1024와 잘못된 1040의 범위를 확인한다.

  • 실제 호출/메모리/GC/컴파일러/언어 UB/학생 실행은 미수행으로 유지한다.

기본 전체와 새 세 진입 설명·표·여섯 비교 예제·12과제·전이의 모든 수치를 손유도했다. 혼합 인자의 첫째 정수는 RCX, 둘째 Double은 XMM1, 셋째 정수는 R8, 넷째 Float는 XMM3로 전달된다. 다섯째 인자 주소는 0x0FF0이다. 호출 전 예약량은 48바이트, 복귀 주소 크기는 8바이트이며 진입 주소에서 다섯째 인자까지의 거리는 40바이트다. 정수 합 반환은 18이다. R12의 들어온 값 41과 호출 중 값 9를 구별하고 복원을 확인했다. 환경 E의 inc, read, inc 반환은 각각 3, 3, 4이며 F의 read 반환은 10이다. 공유 환경 장부는 56바이트, 별도 환경 장부는 80바이트다. 불변 환경의 도달 장부는 예제의 해당 시점에서 128바이트와 24바이트로 나뉘며 전역 루트가 남는 예외를 확인했다. 교육 배치 A의 전체 크기는 32바이트이고 패딩 합은 11바이트다. 배치 B의 전체 크기는 24바이트이고 패딩 합은 3바이트다. A 배열의 둘째 객체 시작은 2032이며 flag, d, x 주소는 각각 2040, 2048, 2056이다. this 조정 뒤 필드 주소 1024에서 값 7을 읽어 17을 반환한다. 별도 객체에서는 필드 주소 3008에서 값 6을 읽어 12를 반환한다. 범위 밖 주소 1040의 결과는 미지정으로 유지했다. 같은 08의 세 기본 설명 전체와 여섯 HTML 의미 앵커를 읽고 확인했다.
