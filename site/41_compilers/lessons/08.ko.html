소단원 8.1

활성 레코드와 ABI

재귀 함수가 같은 이름의 변수를 여러 번 만들 때 어디에 구분해 놓을까?

준비 개념과 학습 목표

준비 개념

  • 함수 호출은 인자를 받고 결과와 제어를 돌려준다.
  • 레지스터와 메모리는 값을 담는 장소다.

학습 목표

  • 호출마다 필요한 상태와 복귀를 설명한다.
  • 명시된 ABI에서 인자·반환·보존 규칙을 추적한다.

호출 한 번의 상태

활성 레코드는 진행 중인 함수 호출의 인자·지역 값·저장 레지스터·복귀 위치 등 필요한 상태를 조직하는 개념이다. 재귀 호출은 같은 코드여도 서로 다른 호출 상태를 가진다. 모든 상태가 반드시 스택 한 덩어리에 실제 존재하는 것은 아니며 레지스터와 최적화로 사라지는 값도 있다.

호출 스택은 마지막 호출이 먼저 끝나는 중첩 수명에 적합하다. f가 g를 부르면 g가 반환한 뒤 f의 남은 동작을 진행한다. 반환 주소와 반환 값은 하나는 실행 위치, 다른 하나는 계산 결과이므로 구분한다.

ABI는 양쪽의 약속

Application Binary Interface는 기계 코드 수준에서 인자 전달·반환·레지스터 보존·정렬 등을 맞추는 약속이다. 함수 이름과 인자 수가 같아도 호출 규칙이 다르면 서로의 값을 잘못 읽을 수 있다. 플랫폼·컴파일러·특수 호출 규약별 조건을 적어야 한다.

공식 Windows x64의 일반 정수 인자는 첫 네 위치 RCX,RDX,R8,R9를 사용하고 이후는 스택이다. 호출자는 네 레지스터 인자용32바이트 shadow space를 준비한다. 부동소수 인자는 위치에 맞는 XMM을 쓰므로 정수 전용 예제 규칙을 그대로 확대하지 않는다.

호출 전후 살아 있어야 할 값

호출로 바뀔 수 있는 volatile 레지스터 값이 뒤에서도 필요하면 호출자 쪽에서 적절히 보존해야 한다. 보존 약속이 있는 nonvolatile 레지스터를 변경하는 피호출자는 원상 복구 책임이 있다. 한쪽만 모든 레지스터를 항상 저장한다는 규칙이 아니다.

스택 정렬·복귀 주소·shadow space·추가 인자·지역값을 함께 고려해 프레임을 만든다. 이론상 몇 바이트 인자가 필요한지 계산한 것과 실제 컴파일러의 프레임 크기를 관찰한 것은 다르다. 본문은 실제 어셈블리 실행을 하지 않는다.

중간 과정을 따라가는 예제

Windows x64 일반 규약으로 정수 f(2,3,5,7,11)를 호출한다고 하자. f는 다섯 수를 더해64비트 정수로 반환한다. 인자 위치와 결과를 구하라.

  1. 첫 번째2는 RCX, 두 번째3은 RDX, 세 번째5는 R8, 네 번째7은 R9다.
  2. 다섯 번째11은 추가 스택 인자 영역에 둔다. 호출자는32바이트 shadow space도 별도로 예약한다.
  3. 합은2+3+5+7+11=28이며64비트 정수 반환 규칙에 따라 RAX의 결과로 받는다.
  4. 32바이트와 추가 인자 슬롯 외에도 정렬·복귀 주소 등이 있어 이를 전체 프레임 크기라고 부르지 않는다.

인자는 네 정수 레지스터와 추가 스택 슬롯, 반환은 RAX의28이다. 실제 컴파일/실행 결과가 아니라 명시 ABI의 종이 추적이다.

힌트 보기

풀이 보기

레지스터 배치·임시값·저장 상태·정렬·최적화가 더해지거나 사라진다. 필요한 논리 상태와 실제 프레임 배치를 나누어 봐야 한다.

소단원 8.2

스택·힙·클로저

바깥 함수가 끝난 뒤에도 안쪽 함수가 바깥 값을 기억하려면 무엇이 남아 있어야 할까?

준비 개념과 학습 목표

준비 개념

  • 렉시컬 범위는 소스의 둘러싼 정의를 따른다.
  • 수명은 저장된 값에 유효하게 접근할 수 있는 기간이다.

학습 목표

  • 클로저의 코드와 환경을 분리한다.
  • 탈출하는 값의 수명과 저장 위치를 설명한다.

스택 수명과 힙 수명

스택은 호출 중첩과 함께 생성·해제할 수 있는 임시 상태에 적합하다. 함수가 반환하면 그 호출의 스택 저장 공간을 계속 유효하다고 가정할 수 없다. 힙은 호출 하나보다 오래 살아야 하는 객체를 배치할 수 있는 공간이며 해제/회수 규칙이 필요하다.

지역변수라는 문법이 스택 배치를 확정하지는 않는다. 값은 레지스터·스택·힙에 놓이거나 최적화로 없어진다. 중요한 것은 프로그램의 관찰 가능한 동작과 유효 수명을 보존하는 것이다.

코드만으로 부족한 함수값

클로저는 실행할 코드와 그 코드의 자유변수를 찾을 환경을 함께 담는다. makeAdder(n)가 x↦x+n을 반환하면 같은 코드라도 n=3과 n=8의 환경이 달라 다른 함수값이다. 호출은 개념적으로 code(environment,x)로 바꿀 수 있다.

환경은 값 복사 또는 공유 참조 등 언어의 캡처 의미를 따라야 한다. 여러 클로저가 같은 변경 가능한 변수를 공유한다면 독립 복사로 바꾸면 서로의 갱신을 못 보게 된다. 클로저가 있다는 사실만으로 복사/참조 정책이 정해지는 것은 아니다.

탈출 분석과 유효성

함수 결과로 반환되거나 더 오래 사는 저장소에 넣은 클로저는 바깥 호출 뒤에도 쓰일 수 있다. 캡처한 환경을 이미 끝난 스택 칸에만 남겨 두면 잘못된 접근이 된다. 이런 수명을 힙이나 적절한 다른 전략으로 보존한다.

탈출하지 않고 바깥 함수가 진행 중일 때만 호출하는 클로저는 환경을 스택에 둘 수도 있다. 최적화가 안전하다고 증명할 때의 선택이며 모든 클로저가 반드시 힙을 쓴다는 법칙은 아니다. 회수도 도달성/소유권 등 언어 런타임의 정책에 따르므로 함수 반환과 동일하지 않다.

중간 과정을 따라가는 예제

불변 n을 값으로 캡처하는 교육 모델에서 f=makeAdder(3), g=makeAdder(8)를 만들고 바깥 호출이 둘 다 끝난 뒤 f(5),g(5)를 계산하라.

  1. 두 클로저의 코드 add(env,x)는 같지만 환경 Ef.n=3, Eg.n=8은 별개다.
  2. 바깥 makeAdder가 반환해도 두 환경은 f/g가 사용하는 동안 유효해야 한다.
  3. f(5)=5+3=8, g(5)=5+8=13이다.
  4. 두 함수값을 같은 코드 주소만으로 표현하면 어떤 n을 쓸지 구분할 수 없다.

결과8과13이며 코드 공유와 환경 분리가 동시에 가능하다.

종이와 본문으로 직접 해보기

공유 참조 캡처 모델에서 환경 n=3을 두 클로저가 참조하다 하나가 n=4로 바꾸었다. 다른 클로저가5+n을 계산하면?

힌트 보기

복사 모델과 다른 가정을 먼저 기록한다.

풀이 보기

같은 환경을 참조하므로5+4=9다. 값 복사 캡처였으면 원래3이 남을 수 있어 정책을 혼합하면 안 된다.

오해와 반례

함수 반환 때 모든 지역 값은 반드시 없어져야 한다.

탈출 환경처럼 계속 관찰되는 값의 유효 수명은 더 길다. 소스 범위를 벗어났다는 사실과 런타임 저장소가 회수되었다는 사실은 다르다.

답과 이유 보기

소단원 8.3

객체 배치와 동적 호출

같은 메서드 이름으로 부르는데 서로 다른 객체가 다른 코드를 실행하는 까닭은 무엇일까?

준비 개념과 학습 목표

준비 개념

  • 객체는 필드 상태와 동작을 함께 설명한다.
  • 정적 타입과 실행 시 실제 타입은 다를 수 있다.

학습 목표

  • 배치·정렬·패딩을 명시된 모델에서 계산한다.
  • 가상 테이블을 통한 동적 호출을 추적한다.

객체도 바이트 배치가 필요하다

컴파일러는 필드·기반 클래스 부분·런타임 정보 등을 규약에 맞는 위치에 둔다. 자료형 정렬 때문에 빈 패딩 바이트가 생길 수 있다. 선언한 필드 크기 합만으로 전체 객체 크기를 확정할 수 없다.

언어 의미와 ABI 구현은 구별한다. 모든 언어가 객체마다 가상 테이블 포인터 하나를 두는 것은 아니며, C++도 상속 형태와 ABI에 따라 배치가 복잡하다. 아래 계산은 실제 특정 컴파일러 관찰이 아닌 명시한 교육 모델이다.

실제 타입으로 동작 고르기

교육 모델에서 객체 첫 칸 vptr은 해당 실제 타입의 함수 테이블을 가리킨다. 호출자는 정해진 슬롯을 읽어 함수 주소를 얻고 객체 주소를 this 인자로 넘긴다. 기반 참조여도 객체가 파생 타입이면 재정의된 슬롯의 함수가 선택된다.

정적 호출은 호출할 함수가 컴파일 시 결정되는 방식이다. 동적 호출도 컴파일러가 실제 타입을 증명하면 직접 호출로 바꿀 수 있으므로 모든 소스 가상 호출이 실행 때 간접 분기를 쓴다고 단정하지 않는다.

서로 다른 배치의 연결

다중 상속에서는 기반 부분을 가리키는 포인터가 전체 객체 시작과 다를 수 있다. 이때 메서드가 기대하는 this로 조정하는 경로가 필요하다. 공식 ABI는 테이블·보조 테이블·조정 루틴을 상세히 정한다.

객체 메모리를 다른 실행 환경에 원시 바이트로 보내면 포인터·정렬·ABI가 맞지 않을 수 있다. 저장/통신에는 값 의미를 표현하는 직렬화 규칙을 따로 정의한다. 교육 배치의 오프셋을 모든 언어의 표준으로 사용하지 않는다.

중간 과정을 따라가는 예제

교육 ABI는 vptr8바이트/정렬8, 필드 x,y는 각4바이트/정렬4, flag는1바이트/정렬1이다. 선언 순서대로 놓고 객체 정렬8로 끝을 맞춘다. 객체의 vptr은 Derived 표, slot0은 x+10을 반환하는 메서드다. x=7인 호출을 추적하라.

  1. vptr은0~7, x는8~11, y는12~15, flag는16에 놓인다.
  2. 다음 빈 위치17을8의 배수24로 올려 끝 패딩17~23의7바이트를 둔다.
  3. 기반 참조로slot0을 호출해도 현재 vptr의 Derived 함수 주소를 읽는다.
  4. this가 이 객체를 가리켜 x=7을 읽으므로 결과는17이다.

모델 객체 크기24바이트, flag 오프셋16, 동적 호출 결과17이다. 실제 sizeof나 어셈블리 실행을 관찰한 결과는 아니다.

오해와 반례

소스 필드 합이 객체 크기이며 기반 참조는 항상 기반 메서드만 호출한다.

패딩·런타임 필드가 더해질 수 있고 가상 호출은 실제 타입의 재정의로 갈 수 있다. 가상 여부와 명시 ABI 모델을 확인해야 한다.
