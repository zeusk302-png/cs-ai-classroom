소단원 14.1

파이프라인 통합

문법 분석기가 만든 나무를 실행까지 어떻게 연결할까?

준비 개념과 학습 목표

준비 개념

  • 토큰과 AST

  • 타입 검사

  • 스택과 후위 순회

학습 목표

  • 작은 언어의 단계별 계약을 연결한다.

  • 스택 명령의 연산 순서를 추적한다.

  • 설계 완료와 실제 구현 완료를 구별한다.

작게 정의한 언어부터 끝까지 연결한다

자체 언어는 print 뒤에 정수 산술식 하나와 세미콜론이 오는 프로그램이다. 정수 리터럴·덧셈·뺄셈·곱셈·괄호를 지원하고 나눗셈·변수·입력·반복은 제외한다. 정수는 수학적 정수로 정의하고 음수 결과도 허용한다.

곱셈이 덧셈/뺄셈보다 우선하고 같은 우선순위는 왼쪽 결합이다. 괄호는 순서를 바꾼다. 음수 리터럴과 단항 마이너스는 이번 문법에 없으며 0−3처럼 이항 뺄셈으로 음수를 만든다. 지원하지 않는 기능은 우연히 통과시키지 않고 오류로 다룬다.

단계마다 자료와 오류 계약을 정한다

어휘 분석은 위치가 붙은 토큰을 만들고 지원하지 않는 문자는 어휘 오류로 멈춘다. 구문 분석은 토큰을 AST로 바꾸고 마지막 세미콜론과 입력 끝까지 확인한다. 의미 검사에서는 print 대상과 모든 연산자가 정수식을 사용한다는 조건을 확인한다.

이 언어에는 변수나 다른 타입이 없으므로 의미 검사 범위도 작다. 이후 AST의 후위 순회로 명령을 만들고 명령 검증을 거쳐 실행기로 보낸다. 앞 단계 실패 시 부분 AST나 불완전 명령을 정상 실행하지 않는다. 모든 오류에 단계·위치·이유를 연결한다.

명령과 실행기의 의미를 맞춘다

자체 목표 명령 PUSH n은 정수를 스택에 넣는다. ADD/SUB/MUL은 오른쪽 피연산자 r을 먼저 꺼내고 왼쪽 l을 다음에 꺼내 l+r/l−r/l×r을 넣는다. PRINT는 하나를 꺼내 출력한다. 스택은 처음 비어 있고 정상 종료 때도 비어 있어야 한다.

정수 AST 하나의 생성 명령은 스택 높이를 정확히 1 늘린다. 이항식은 왼쪽 명령·오른쪽 명령·연산 명령 순이다. 두 값이 없는 연산과 빈 스택의 PRINT는 잘못된 목표 프로그램이다. 여기서 완성하는 것은 통합 설계와 종이 추적이며 실제 컴파일러 구현 완료를 주장하지 않는다.

중간 과정을 따라가는 예제

print 2 + 3 * (4 - 1);의 AST 구조와 목표 명령, 출력을 구하라.

  1. AST는 Print(Add(2,Mul(3,Sub(4,1))))이다. 곱셈과 괄호의 구조를 먼저 보존한다.

  2. 생성 명령은 PUSH 2; PUSH 3; PUSH 4; PUSH 1; SUB; MUL; ADD; PRINT다.

  3. 스택은 [2]→[2,3]→[2,3,4]→[2,3,4,1]→[2,3,3]→[2,9]→[11]→[]이다. SUB는 4−1이며 역순 1−4가 아니다.

출력은 11이다. 목표 실행과 AST 의미 계산 2+3×(4−1)이 일치한다.

종이와 본문으로 직접 해보기

힌트 보기

왼쪽 결합과 스택에 쌓인 왼쪽/오른쪽 값을 확인한다.

풀이 보기

AST는 Sub(Sub(8,3),2)이므로 출력 3이다. PUSH 8/PUSH 3/SUB에서 r=3,l=8을 사용해야 5가 된다. 순서를 뒤집으면 −5가 되어 언어 의미를 위반한다.

각 단계가 따로 동작하면 연결한 컴파일러도 자동으로 올바르다.

토큰 위치·AST 구조·정수 규약·명령 피연산자 순서·오류 전달의 계약이 맞아야 한다. 통합 추적과 종단 간 검사가 필요하다.

소단원 14.2

차등·회귀·오류 테스트

출력이 예전과 같으면 정답인 것도 보장될까?

준비 개념과 학습 목표

준비 개념

  • 독립 기대값

  • 오류 단계

  • 프로그램 의미

학습 목표

  • 차등 비교와 회귀 검사를 구별한다.

  • 정상/오류 입력의 기대 결과를 정한다.

  • 공유 결함과 잘못 저장한 기대값의 한계를 설명한다.

비교할 관측 의미를 정한다

차등 테스트는 같은 입력을 서로 다른 구현이나 경로에 넣고 결과를 비교한다. 자체 언어에서는 AST의 직접 의미 계산과 생성 명령의 실행 결과를 비교할 수 있다. stdout의 값·종료 여부·오류 단계처럼 무엇을 비교할지 명시한다.

두 경로가 같은 잘못된 AST를 공유하면 parser의 오류를 함께 놓칠 수 있다. 따라서 일부 입력은 문법과 의미에서 독립적으로 계산한 기대값도 비교한다. 실제 다른 구현의 정수 넘침이나 오류 규약이 다르면 불일치가 곧 컴파일러 결함이라고 단정할 수 없다.

기존 실패를 회귀 검사로 남긴다

회귀 테스트는 수정 뒤 이미 확인한 동작이 다시 깨지는지 검사한다. SUB 역순 오류가 있었다면 print 4−1;의 기대값 3을 고정하여 다시 검사한다. 정상 결과뿐 아니라 잘못된 입력의 오류도 남긴다.

스냅샷 방식은 입력과 출력 파일 쌍을 저장해 변경을 비교한다. 출력이 달라지면 의도한 변경인지 사람이 검토한다. 저장 버튼으로 새 출력을 무조건 기대값으로 받아들이면 잘못된 결과를 정상으로 고정할 수 있다. 오류 메시지 형식 변경과 의미 변경을 구별한다.

단계별 오류와 경계를 검사한다

print 2 + ;는 피연산자 누락의 구문 오류, print @;는 지원하지 않는 문자의 어휘 오류다. print (2+3;는 닫는 괄호 누락의 구문 오류다. 정상 문 뒤 추가 토큰도 입력 끝 검사에서 거절한다.

빈 입력·0·큰 리터럴·중첩 괄호·결합/우선순위·음수 결과를 계획에 넣는다. 반복과 나눗셈은 지원하지 않으므로 그것들의 실행 성능이나 0 나눗셈 처리를 검증했다고 쓰지 않는다. 설계한 검사 목록과 실제 통과 로그를 별도 상태로 기록한다.

중간 과정을 따라가는 예제

네 검사 입력 print 4-1;, print 8-3-2;, print 2+;, print @;에 독립 기대 결과와 오류 단계를 적어라.

  1. 4−1의 정상 출력은 3이다. 8−3−2는 왼쪽 결합으로 3이며 오른쪽 결합 7과 다르다.

  2. 2+ 뒤 바로 세미콜론이 오면 식의 오른쪽 항이 없으므로 구문 오류다. 정상 명령을 실행하지 않는다.

  3. @는 토큰 규약에 없으므로 어휘 오류다. parser 단계의 정상 AST를 만들었다고 처리하지 않는다.

앞 둘은 출력 3, 뒤 둘은 각각 구문 오류·어휘 오류다. 위치와 메시지는 실제 구현 전에 계약으로 정한다.

종이와 본문으로 직접 해보기

힌트 보기

언어는 왼쪽 결합이며 두 경로가 같은 AST를 사용할 수 있다.

풀이 보기

오른쪽 결합 AST를 공유한 parser 오류를 놓친다. 독립 의미 기대값 3과 비교해야 한다. 두 구현 일치는 필요한 관찰일 수 있지만 모든 의미의 정답 증명은 아니다.

오해와 반례

스냅샷이 달라지면 새 결과를 저장하면 검증이 끝난다.

변경된 의미가 정당한지 검토해야 한다. 결함 출력을 저장하면 회귀 검사 자체가 결함을 요구하는 상태가 된다.

실행 결과·성능·설계 보고

명령 수가 줄었다는 사실과 실제 실행이 빨라졌다는 사실은 같은가?

준비 개념과 학습 목표

준비 개념

  • 컴파일과 실행

  • 평균과 비율

  • 측정과 가정

학습 목표

  • 기능 결과와 성능 주장의 근거를 분리한다.

  • 컴파일 비용과 반복 실행의 총 비용을 계산한다.

  • 설계 범위·실패·재현 조건을 보고한다.

실행 결과에는 버전과 입력이 필요하다

실제 보고는 언어 문법과 의미·지원 범위·파이프라인·코드 버전·도구 환경·실행 입력·기대 출력·관측 결과·실패를 연결한다. 어느 단계가 설계뿐이고 어느 단계가 구현/실행됐는지 명시한다.

이번 단원은 print 하나의 정수식 언어와 스택 목표의 통합 설계다. 종이 추적에서 출력 11과 3을 확인했지만 실제 컴파일러 바이너리를 실행하지 않았다. 지원하지 않는 반복·변수·나눗셈을 포함하는 범용 컴파일러를 완성했다고 표현하지 않는다.

비용의 경계를 먼저 정한다

명령 수 감소는 설계나 코드 관찰이며 시간 단축은 측정이 필요하다. 같은 입력·기기·버전·워밍업·반복 규칙에서 비교하고 시간 단위를 남긴다. 컴파일 비용을 제외한 실행 시간과 컴파일을 포함한 총 시간은 다른 질문이다.

가상 모델에서 기본 컴파일 20 ms, 최적화 컴파일 40 ms, 둘의 한 번 시작 비용 10 ms, 실행당 기본 2 ms·최적화 1 ms라고 정하자. 한 번 컴파일하고 실행기를 한 번 시작하여 N회 같은 연산을 수행하는 모델의 총 비용은 30+2N과 50+N ms다. 이 수치는 실제 측정값이 아니다.

결과와 한계를 같이 보고한다

N=1이면 기본 32 ms, 최적화 51 ms여서 이 모델에서는 최적화가 느리다. N=100이면 기본 230 ms, 최적화 150 ms다. 실행 본체만의 2배와 총 비용의 230/150=23/15배는 다르다.

손익분기는 30+2N=50+N에서 N=20이다. N>20에서 최적화 총 비용이 작다. 실제 시스템의 시작 비용이 매 실행마다 붙거나 입력이 달라지면 모델을 바꿔야 한다. 실제 측정·실험 수행 없이 이 가정의 결과를 보편 성능으로 보고하지 않는다.

중간 과정을 따라가는 예제

위 가상 비용 모델의 N=1/20/100 총 시간을 계산하고 N=100의 총 시간 비율을 구하라.

  1. N=1: 기본 30+2=32 ms, 최적화 50+1=51 ms다.

  2. N=20: 기본과 최적화 모두 70 ms다. N=100: 기본 230 ms, 최적화 150 ms다.

  3. 기본/최적화 총 시간은 230/150=23/15≈1.533이다. 실행당 본체만의 2/1=2와 구별한다.

가정 아래 20회에서 동률이고 100회 총 시간 비율은 23/15다. 실제 컴파일러 성능 측정은 미수행이다.

종이와 본문으로 직접 해보기

시작 비용 10 ms가 N회마다 붙는 방식으로 바뀌면 총 비용 식과 손익분기는 어떻게 바뀌는가?

힌트 보기

컴파일 한 번과 시작/실행 N번의 비용을 분리한다.

풀이 보기

기본 20+12N, 최적화 40+11N ms다. 동률은 여전히 N=20이지만 N=100 시간은 1220/1140 ms로 비율이 달라진다. 공통 시작 비용도 전체 비율에 영향을 준다.

오해와 반례

최적화 명령이 적으면 어떤 사용 상황에서도 총 시간이 절반이다.

컴파일·시작·실행·입력과 하드웨어 비용을 모두 고려해야 한다. 명령 수만으로 실제 시간이나 전체 배율을 확정할 수 없다.
