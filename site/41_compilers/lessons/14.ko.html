파이프라인 통합

문법 분석기가 만든 나무를 실행까지 어떻게 연결할까?

준비 개념과 학습 목표

준비 개념

  • 타입 검사

  • 스택과 후위 순회

학습 목표

  • 스택 명령의 연산 순서를 추적한다.

  • 설계 완료와 실제 구현 완료를 구별한다.

스택 높이가 맞으면 출력 숫자도 맞을까?

기본의 작은 언어를 그대로 사용한다. 프로그램은 print 식; 하나와 EOF이며 리터럴은 음이 아닌 정수다. 이항 +,−,*와 괄호만 허용하고 곱셈의 우선순위가 더 높다. 덧셈·뺄셈은 왼쪽 결합이다. 결과는 음수가 될 수 있는 수학적 무한 정수로 해석한다. 이는 C 정수의 overflow나 UB를 실행해 관찰한 언어가 아니다.

새 입력 print 9-(4-1)*2;의 AST는 Print(Sub(9,Mul(Sub(4,1),2)))다. 올바른 후위 코드는 PUSH 9; PUSH 4; PUSH 1; SUB; PUSH 2; MUL; SUB; PRINT다. SUB는 먼저 오른쪽 값 r을 pop하고 다음 왼쪽 값 l을 pop하여 l−r을 push한다. 스택 높이와 값의 대응을 동시에 추적해야 한다.

SUB를 r−l로 구현해도 pop 두 번과 push 한 번이라는 높이 효과는 같다. 같은 코드의 올바른 출력은 3이지만 이 오류 구현은 −15를 출력한다. 높이 불변식은 underflow와 잔여 값에 대한 검사이며 산술 의미의 증명까지 대신하지 않는다. 작은 단계마다 다른 계약을 연결하고 각 계약의 관찰 대상을 이름으로 적는다.

먼저 확인할 개념
  • 식의 구조와 스택 계약

    AST의 결합 순서와 오른쪽 먼저 pop하는 명령 의미를 함께 적용한다.

  • 독립 기대값 검사

    높이만 같거나 두 실행 경로가 같은 오류를 공유할 때 별도 기대값이 필요하다.

작게 정의한 언어부터 끝까지 연결한다

자체 언어는 print 뒤에 정수 산술식 하나와 세미콜론이 오는 프로그램이다. 정수 리터럴·덧셈·뺄셈·곱셈·괄호를 지원하고 나눗셈·변수·입력·반복은 제외한다. 정수는 수학적 정수로 정의하고 음수 결과도 허용한다.

곱셈이 덧셈/뺄셈보다 우선하고 같은 우선순위는 왼쪽 결합이다. 괄호는 순서를 바꾼다. 음수 리터럴과 단항 마이너스는 이번 문법에 없으며 0−3처럼 이항 뺄셈으로 음수를 만든다. 지원하지 않는 기능은 우연히 통과시키지 않고 오류로 다룬다.

단계마다 자료와 오류 계약을 정한다

어휘 분석은 위치가 붙은 토큰을 만들고 지원하지 않는 문자는 어휘 오류로 멈춘다. 구문 분석은 토큰을 AST로 바꾸고 마지막 세미콜론과 입력 끝까지 확인한다. 의미 검사에서는 print 대상과 모든 연산자가 정수식을 사용한다는 조건을 확인한다.

이 언어에는 변수나 다른 타입이 없으므로 의미 검사 범위도 작다. 이후 AST의 후위 순회로 명령을 만들고 명령 검증을 거쳐 실행기로 보낸다. 앞 단계 실패 시 부분 AST나 불완전 명령을 정상 실행하지 않는다. 모든 오류에 단계·위치·이유를 연결한다.

명령과 실행기의 의미를 맞춘다

자체 목표 명령 PUSH n은 정수를 스택에 넣는다. ADD/SUB/MUL은 오른쪽 피연산자 r을 먼저 꺼내고 왼쪽 l을 다음에 꺼내 l+r/l−r/l×r을 넣는다. PRINT는 하나를 꺼내 출력한다. 스택은 처음 비어 있고 정상 종료 때도 비어 있어야 한다.

정수 AST 하나의 생성 명령은 스택 높이를 정확히 1 늘린다. 이항식은 왼쪽 명령·오른쪽 명령·연산 명령 순이다. 두 값이 없는 연산과 빈 스택의 PRINT는 잘못된 목표 프로그램이다. 여기서 완성하는 것은 통합 설계와 종이 추적이며 실제 컴파일러 구현 완료를 주장하지 않는다.

잘못된 SUB 두 번

[9,−3]→[9,−6]→[−15]→[]

높이는 같지만 출력은 다름

각 대괄호는 아래부터 위까지의 값 순서다. MUL 직전에는 높이가 3이며 표의 해당 행은 MUL까지 마친 상태다. 출력과 높이를 별도 열로 검사한다. 입력은 먼저 전체 lexing을 완료한 뒤 parsing·검증·실행하는 자체 정책을 사용하며 오류가 있으면 PRINT를 전혀 실행하지 않는다.

중간 과정을 따라가는 예제

print 2 + 3 * (4 - 1);의 AST 구조와 목표 명령, 출력을 구하라.

  1. AST는 Print(Add(2,Mul(3,Sub(4,1))))이다. 곱셈과 괄호의 구조를 먼저 보존한다.

  2. 생성 명령은 PUSH 2; PUSH 3; PUSH 4; PUSH 1; SUB; MUL; ADD; PRINT다.

  3. 스택은 [2]→[2,3]→[2,3,4]→[2,3,4,1]→[2,3,3]→[2,9]→[11]→[]이다. SUB는 4−1이며 역순 1−4가 아니다.

출력은 11이다. 목표 실행과 AST 의미 계산 2+3×(4−1)이 일치한다.

조건을 바꾸어 비교하기

같은 높이 열을 가진 두 SUB 구현

새 입력의 정상 구현과 r−l 오류 구현을 끝까지 비교하라. 최대 스택 높이와 최종 출력은?

  1. 정상 값은 내부 SUB 뒤 3, MUL 뒤 6, 바깥 SUB 뒤 3이다. 출력 뒤 스택은 비고 최대 높이는 3이다.

  2. 오류 값은 내부에서 1−4=−3, MUL 뒤 −6, 바깥에서 −6−9=−15다. 높이 열은 1,2,3,2,3,2,1,0으로 두 구현에서 같다.

높이 검사 둘 다 통과하지만 출력 3과 −15가 달라 의미 검사는 실패한다.

비교할 점

기본의 정상 추적에 높이 효과를 보존하는 새 오류 구현을 붙여 검사별 보장 범위를 분리한다.

실행 전에 오류를 차단하는 계약

print 1; 2를 입력받으면 앞의 print를 먼저 실행하고 뒤의 오류를 보고해도 이 단원의 정책을 지키는가?

  1. print 식; 뒤에 EOF가 와야 한다. 뒤의 2가 남아 있으므로 전체 프로그램 parsing에 실패한다.

  2. 이 자체 정책은 전체 lexing/parsing/검증 성공 뒤에만 실행한다. 따라서 정상 출력 1을 먼저 내는 증분 실행은 같은 계약이 아니다.

오류를 반환하고 출력은 비어 있어야 한다.

연습 1 · 값과 상태 예측

print 9-(4-1)*2;의 정상 코드에서 PUSH 2 직후의 스택과 높이, 이후 출력과 최대 높이를 예측하라.

힌트 1

내부 SUB는 오른쪽 1과 왼쪽 4를 제거한다.

힌트 2

PUSH 2 직후와 MUL 직후를 같은 시점으로 쓰지 않는다.

풀이와 답 확인

  1. 내부 SUB 뒤 [9,3]이며 PUSH 2 직후 [9,3,2]라 높이는 3이다.

  2. MUL 뒤 [9,6], SUB 뒤 [3], PRINT 뒤 []이며 출력은 3이고 최대 높이는 3이다.

PUSH 2 직후 높이 3, 출력 3, 최대 높이 3이다.

흔한 오답에서 다시 생각하기

PUSH 2 직후 스택은 [9,6]이다.

그 상태는 MUL까지 실행한 뒤다. 관찰하는 명령 경계를 명시해야 한다.

연습 2 · 오류 찾아 고치기

SUB 구현이 오른쪽 pop r과 왼쪽 pop l 뒤 r−l을 push한다. 높이 검사만 통과한 보고를 수정하고 이 입력의 최초 값 불일치를 적어라.

힌트 1

첫 SUB는 4와 1을 처리한다.

힌트 2

높이 효과와 숫자 의미는 다른 불변식이다.

풀이와 답 확인

  1. 첫 SUB의 정상 결과 3 대신 −3이 생기는 시점이 최초 값 불일치다. 높이는 두 경우 모두 2다.

  2. push 값을 l−r로 바꾸고 모든 SUB 경계의 값과 마지막 출력 3을 다시 대조할 계획을 적는다. 이 계획을 실제 시험 완료로 기록하지 않는다.

최초 오류는 내부 SUB의 값이며 pop 순서에 맞춘 l−r이 복구식이다.

흔한 오답에서 다시 생각하기

마지막 PRINT만 고치면 높이 검사도 의미 검사도 해결된다.

잘못된 산술이 중간에 전파되므로 출력 형식 변경은 의미를 복구하지 못한다.

연습 3 · 직접 만들어 보기

print 12-5-3;의 올바른 AST와 후위 코드, 각 명령 뒤 높이와 값을 직접 구성하라.

힌트 1

두 뺄셈은 왼쪽 결합이다.

힌트 2

첫 SUB 결과를 두 번째 SUB의 왼쪽 값으로 쓴다.

풀이와 답 확인

  1. AST는 Print(Sub(Sub(12,5),3))다. 코드는 PUSH 12; PUSH 5; SUB; PUSH 3; SUB; PRINT다.

  2. 스택은 [12],[12,5],[7],[7,3],[4],[]로 변하고 높이는 1,2,1,2,1,0이다. 출력은 4이고 최대 높이는 2다.

왼쪽 결합 AST와 출력 4 및 빈 종료 스택을 함께 구성한다.

흔한 오답에서 다시 생각하기

AST는 Sub(12,Sub(5,3))이며 출력 10이다.

그것은 오른쪽 결합으로 문법 계약을 바꾼 결과다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

왼쪽 식을 먼저 계산하는 생성 규칙에서 식의 최대 추가 스택 높이 H를 재귀식으로 쓰고 새 입력의 H를 구하라. 식 평가 시작 아래의 기존 값은 건드리지 않는다고 가정한다.

힌트 1

리터럴은 값 하나를 추가한다.

힌트 2

오른쪽 식을 계산할 때 왼쪽 결과 한 개가 이미 남는다.

풀이와 답 확인

  1. H(리터럴)=1이고 H(l op r)=max(H(l),1+H(r))다. op 뒤에는 값 한 개만 추가되어 있다.

  2. H(Sub(4,1))=2, H(Mul(Sub(4,1),2))=2이므로 바깥 Sub의 H는 max(1,1+2)=3이다. 오른쪽 먼저 계산하도록 바꾸면 SUB의 값 순서도 함께 고쳐야 하며 현재 명령 집합에는 SWAP이 없다.

규칙의 최대 높이는 3이며 평가 순서 변경은 산술 계약까지 다시 설계해야 한다.

흔한 오답에서 다시 생각하기

H(l op r)는 항상 H(l)+H(r)다.

왼쪽의 임시 전체를 끝까지 남기는 것이 아니라 평가 뒤 결과 하나만 남긴다.

두 경로가 같은 출력을 내도 문법이 잘못될 수 있을까?

차등 검사는 비교 경로의 독립성이 있어야 해석하기 쉽다. 파서가 print 12-5-3;을 잘못된 오른쪽 결합 AST로 만들고 AST 해석기와 코드 생성기가 그 AST를 공유하면 둘 다 10을 낼 수 있다. 두 결과의 일치는 공유된 파서의 문법 계약을 인증하지 않는다. 문자열과 문법에서 별도로 얻은 기대값 4와 AST 구조를 함께 비교한다.

오류를 시험할 때에는 값만 아니라 단계·위치·출력 유무를 명시한다. 이 보강의 위치는 ASCII 문자에 대한 0기반 인덱스다. 전체 lexer 성공 뒤 parser를 호출하는 정책이므로 print @;은 @ 위치 6에서 lexical 오류다. print 7+;은 ; 위치 8에서 식이 필요한 syntax 오류이고 print 1; 2는 위치 9의 남는 토큰으로 EOF 검사를 실패한다.

snapshot에는 정상 출력과 오류 관찰을 구별해 기록한다. 새 예상 파일을 저장했다는 사실은 정확한 답을 검토했다는 사실과 다르다. 동일한 출력 텍스트에 성공/실패 상태를 붙여 비교하는 테스트 계약을 먼저 정한다. 아래 장부는 실행 결과가 아니라 사람이 구성한 기대값·후보 관찰의 가상 표다.

비교할 관측 의미를 정한다

차등 테스트는 같은 입력을 서로 다른 구현이나 경로에 넣고 결과를 비교한다. 자체 언어에서는 AST의 직접 의미 계산과 생성 명령의 실행 결과를 비교할 수 있다. stdout의 값·종료 여부·오류 단계처럼 무엇을 비교할지 명시한다.

두 경로가 같은 잘못된 AST를 공유하면 parser의 오류를 함께 놓칠 수 있다. 따라서 일부 입력은 문법과 의미에서 독립적으로 계산한 기대값도 비교한다. 실제 다른 구현의 정수 넘침이나 오류 규약이 다르면 불일치가 곧 컴파일러 결함이라고 단정할 수 없다.

기존 실패를 회귀 검사로 남긴다

회귀 테스트는 수정 뒤 이미 확인한 동작이 다시 깨지는지 검사한다. SUB 역순 오류가 있었다면 print 4−1;의 기대값 3을 고정하여 다시 검사한다. 정상 결과뿐 아니라 잘못된 입력의 오류도 남긴다.

스냅샷 방식은 입력과 출력 파일 쌍을 저장해 변경을 비교한다. 출력이 달라지면 의도한 변경인지 사람이 검토한다. 저장 버튼으로 새 출력을 무조건 기대값으로 받아들이면 잘못된 결과를 정상으로 고정할 수 있다. 오류 메시지 형식 변경과 의미 변경을 구별한다.

단계별 오류와 경계를 검사한다

print 2 + ;는 피연산자 누락의 구문 오류, print @;는 지원하지 않는 문자의 어휘 오류다. print (2+3;는 닫는 괄호 누락의 구문 오류다. 정상 문 뒤 추가 토큰도 입력 끝 검사에서 거절한다.

건당 빠른 코드가 빌드를 자주 바꾸어도 전체 비용을 줄일까?

새 합성 비용 모형의 기준 B는 빌드당 12 ms와 실행 본문당 3 ms, 후보 O는 빌드당 30 ms와 본문당 1 ms다. 두 후보 모두 프로세스 시작당 4 ms다. K번 빌드, P번 프로세스 시작, N번 본문 실행을 서로 다른 사건 수로 정의하며 같은 사건 장부를 두 후보에 적용한다. 실패·재시도·대기·I/O 비용은 이 모형에서 제외한다.

총 시간은 B=12K+4P+3N,O=30K+4P+N ms다. O−B=18K−2N이므로 O가 엄격히 빠른 조건은 N>9K다. 프로세스 수가 두 후보에서 같다는 가정 아래 공통 4P가 비교식에서 사라진다. 실제 빌드·benchmark를 수행한 표가 아니며 이름 B/O도 실제 옵션에 연결하지 않는다.

재사용은 숫자뿐 아니라 캐시의 의미 계약에 영향을 준다. 예를 들어 같은 소스라도 목표 명령의 SUB 규약이 바뀌면 생성 코드의 요구가 달라진다. 캐시 키는 소스만 아니라 언어·대상 의미·사용한 옵션 등 산출물에 영향을 주는 입력을 구별해야 한다. 키의 해시는 정확성의 독립 증명이 아니라 특정 입력 장부를 식별하는 수단이다.

실행 결과에는 버전과 입력이 필요하다

실제 보고는 언어 문법과 의미·지원 범위·파이프라인·코드 버전·도구 환경·실행 입력·기대 출력·관측 결과·실패를 연결한다. 어느 단계가 설계뿐이고 어느 단계가 구현/실행됐는지 명시한다.

이번 단원은 print 하나의 정수식 언어와 스택 목표의 통합 설계다. 종이 추적에서 출력 11과 3을 확인했지만 실제 컴파일러 바이너리를 실행하지 않았다. 지원하지 않는 반복·변수·나눗셈을 포함하는 범용 컴파일러를 완성했다고 표현하지 않는다.

비용의 경계를 먼저 정한다

명령 수 감소는 설계나 코드 관찰이며 시간 단축은 측정이 필요하다. 같은 입력·기기·버전·워밍업·반복 규칙에서 비교하고 시간 단위를 남긴다. 컴파일 비용을 제외한 실행 시간과 컴파일을 포함한 총 시간은 다른 질문이다.

가상 모델에서 기본 컴파일 20 ms, 최적화 컴파일 40 ms, 둘의 한 번 시작 비용 10 ms, 실행당 기본 2 ms·최적화 1 ms라고 정하자. 한 번 컴파일하고 실행기를 한 번 시작하여 N회 같은 연산을 수행하는 모델의 총 비용은 30+2N과 50+N ms다. 이 수치는 실제 측정값이 아니다.

결과와 한계를 같이 보고한다

N=1이면 기본 32 ms, 최적화 51 ms여서 이 모델에서는 최적화가 느리다. N=100이면 기본 230 ms, 최적화 150 ms다. 실행 본체만의 2배와 총 비용의 230/150=23/15배는 다르다.

손익분기는 30+2N=50+N에서 N=20이다. N>20에서 최적화 총 비용이 작다. 실제 시스템의 시작 비용이 매 실행마다 붙거나 입력이 달라지면 모델을 바꿔야 한다. 실제 측정·실험 수행 없이 이 가정의 결과를 보편 성능으로 보고하지 않는다.

다른 문제에 적용하기

작은 언어의 새 입력 print 12-5-3;을 통합 감사하라. ① 왼쪽 결합 AST와 코드, 스택 값/높이를 구성하라. ② 잘못된 오른쪽 결합 AST를 공유한 해석기·생성기가 모두 10을 냈을 때 차등 일치와 문법 실패를 구별하라. print 1; 2의 오류 위치와 출력 정책도 적어라. ③ 합성 비용 B=12K+4P+3N,O=30K+4P+N ms에서 K=2,P=2를 고정하고 N=12,18,24의 순위·시간을 구하라. ④ 전체 검증 성공 뒤 실행하며 캐시 입력에는 대상 의미 판본도 포함한다는 승인 조건을 작성하라. 실제 실행을 수행했다고 기록하지 않는다.

힌트 1

왼쪽 결합 코드는 첫 SUB 결과 7을 다음 SUB의 왼쪽 값으로 쓴다. EOF 검사에서 남는 2의 0기반 위치는 9다.

힌트 2

비용 차이는 18K−2N이며 K=2에서 동률은 N=18이다. 차등 비교의 공유 입력과 독립 기대값을 구별한다.

풀이와 답 확인

  1. 정상 AST는 Print(Sub(Sub(12,5),3))이며 코드 PUSH 12; PUSH 5; SUB; PUSH 3; SUB; PRINT의 스택은 [12],[12,5],[7],[7,3],[4],[]다. 높이는 1,2,1,2,1,0으로 최대 2이며 출력은 4다.

  2. 공유된 잘못된 AST Sub(12,Sub(5,3))의 두 결과 10은 차등 일치일 뿐 왼쪽 결합 계약에서는 실패다. 독립 기대값 4와 구조 검사를 추가한다. print 1; 2는 위치 9의 남는 토큰으로 EOF 요구를 실패하며 전체 검증 후 실행 정책에서 출력하지 않는다.

  3. K=2, P=2를 유지할 때 N=12이면 B의 총 시간은 68 ms이고 O의 총 시간은 80 ms라 B가 빠르다. N=18이면 둘 다 86 ms다. N=24이면 B의 총 시간은 104 ms이고 O의 총 시간은 92 ms라 O가 빠르다. 이 고정 K의 엄격한 O 이득은 정수 N≥19다.

  4. 문법·오류 관찰·대상 명령 의미·캐시 입력 식별을 각각 검사할 계획을 둔다. 합성 비용의 좋은 순위나 빈 종료 스택만으로 의미 실패를 승인하지 않는다. 실제 컴파일·시험·benchmark와 학생 수행은 별도 미수행으로 남긴다.

정상 출력은 4이며 최대 스택 높이는 2다. 공유 오류의 두 출력 10은 문법 검사를 실패한다. 남는 토큰의 위치는 9이고 오류 출력은 없다. K=2, P=2에서 N=12일 때 B의 총 시간은 68 ms이고 O의 총 시간은 80 ms다. N=18에서는 두 후보 모두 86 ms이며 N=24에서는 B가 104 ms이고 O가 92 ms다. 동일 P의 엄격한 O 이득 조건은 N>9K다.

해결한 뒤 점검할 것

  • AST의 왼쪽 결합·두 SUB 값·여섯 높이·출력 4를 모두 제시한다.

  • 공유 AST 차등 일치와 독립 문법 기대값을 구별하고 위치 9·빈 오류 출력을 확인한다.

  • 세 N의 두 총 시간을 각각 계산하고 동률과 엄격한 이득을 구별한다.

  • 대상 의미 판본을 캐시 입력으로 식별하며 손모형과 실제 실행/학생 미수행의 범위를 보존한다.
