소단원 1.1

프런트엔드·중간표현·백엔드

a+2*3을 읽을 때 왜 덧셈보다 곱셈을 먼저 묶어야 할까?

준비 개념과 학습 목표

준비 개념

  • 토큰은 글자 흐름에서 의미 있는 단위로 나눈 조각이다. a, +, 2, *, 3은 이 예에서 다섯 토큰이다.

  • 트리는 뿌리에서 자식으로 가지를 나누는 구조다. 연산자 노드는 계산을, 잎은 수나 변수 이름을 나타낸다.

  • 실행은 정한 규칙에 따라 상태를 바꾸거나 값을 얻는 것이다. 환경 ρ는 변수 이름에 값 하나를 대응시킨 표로, ρ(a)=4라고 쓰면 a의 값은 4다.

학습 목표

  • 프런트엔드·IR·백엔드의 입력과 책임을 설명한다.

  • 같은 표현식을 토큰·AST·중간코드·가상 명령으로 추적한다.

  • 단계의 올바른 출력과 진단이 필요한 입력을 구별한다.

토큰과 트리에서 스택 코드까지 뜻이 같다는 것을 무엇으로 확인할까?

기본의 순수 정수 언어에 빼기 −를 명시적으로 추가한 새 모형을 사용한다. 곱셈은 덧셈·뺄셈보다 우선하고 같은 우선순위는 왼쪽부터 묶는다. 리터럴은 비음수 정수이고 결과는 수학적 정수다. 모든 이름은 환경에서 정의된다. 기본 언어에 없던 빼기를 기존 문법이라고 부르지 않는다.

새 스택 기계에서 PUSH n과 LOAD a는 값을 오른쪽 끝에 넣는다. 이항 명령은 먼저 오른쪽 값 r, 이어 왼쪽 값 l을 꺼내 l op r을 넣는다. RETURN은 정확히 한 값이 있을 때 그 값을 반환한다. 정수 폭·실제 CPU·메모리 비용은 이 모형 밖이다.

표면 식, AST와 연산 의존 관계를 따로 남기면 괄호를 잃은 파서와 순서를 잃은 백엔드를 구분할 수 있다. 정상적인 스택 높이와 맞는 결과값은 별개다. 덧셈만 시험하면 피연산자 뒤집힘이 가려지므로 비가환 연산도 비교하자.

먼저 확인할 개념
  • AST와 임시 코드의 의존 관계

    기본 우선순위와 상수 접기 과정을 새 빼기와 스택 명령에 연결한다.

  • 단계 시험과 독립 예상값

    정상 형식과 전체 의미의 다른 시험을 새 단계 장부에서 구분한다.

프런트엔드는 문자열을 구조와 의미로 바꾼다

컴파일러는 한 언어의 프로그램을 다른 표현으로 번역하는 프로그램이다. 이 단원의 작은 언어는 비음수 정수 리터럴, 변수 이름, +, *, 괄호로 만든 표현식이다. 값은 수학적 정수이며 변수는 환경에 미리 정의되어 있다. 공백은 토큰 사이에서만 무시하고 곱셈은 덧셈보다 우선한다. 이 조건을 먼저 정해야 어떤 트리가 올바른지 판단할 수 있다.

프런트엔드는 글자를 토큰으로 나누는 어휘 분석, 문법 구조를 만드는 구문 분석, 이름·타입 등 의미 조건을 검사하는 단계를 담당한다. a+2*3의 AST는 Add(Var(a), Mul(Int(2), Int(3)))다. a+*3처럼 문법에 맞지 않거나 환경에 없는 이름을 사용하는 입력은 정상 번역 결과와 별도의 진단으로 처리한다. 문법이 맞다는 사실만으로 모든 의미 조건이 맞지는 않는다.

중간표현은 표면 문법과 특정 기계를 분리한다

중간표현(IR)은 이후 분석과 변환에 사용할 프로그램 표현이다. AST도 중간 표현의 한 종류지만 이 예는 임시 이름을 가진 세 주소 코드로 한 번 더 낮춘다. t1=mul 2,3; t2=add a, t1; return t2라고 적으면 각 계산과 의존관계를 명확히 볼 수 있다. 임시 이름은 계산 결과를 한 번 붙잡는 이름이며 소스의 줄 번호와 동일하지 않다.

곱셈의 두 입력이 상수이므로 정수 의미 아래 t1=6으로 접을 수 있다. 그 뒤 t2=add a,6으로 단순화한다. 이 변환은 상수 계산을 미리 하는 것이지 모든 프로그램을 실행하여 결과를 미리 아는 것은 아니다. 실제 IR에는 타입·분기·메모리·예외·호출 등 더 많은 정보가 필요하고 언어 의미를 잃지 않아야 한다.

백엔드는 목표 기계의 규칙으로 낮춘다

백엔드는 IR의 연산을 목표 기계 명령에 대응시키고 필요한 저장 위치나 레지스터를 배정한다. 자체 가상 기계에서는 LOAD R0, a가 환경의 a를 R0에 읽고 ADDI R0,6이 R0에 6을 더하고 RETURN R0이 값을 반환한다고 정한다. 이 절의 R0은 수학적 정수를 담으며 실제 CPU의 비트 폭·메모리·명령 인코딩을 모델링하지 않는다.

프런트엔드를 여러 소스 언어에 만들고 IR 아래에 여러 목표 백엔드를 붙이는 구성이 가능하다. 그렇다고 IR 하나가 모든 언어의 성질을 자동 보존하거나 모든 기계에서 같은 비용을 갖는 것은 아니다. 목표가 유한 비트 정수를 사용하면 표현 범위·오버플로 규칙을 연결해야 한다. 어셈블·링크·로딩은 실행까지 이어지는 별도 단계일 수 있다.

// 자체 가상 명령; 실제 ISA 또는 LLVM 실행 결과가 아님
LOAD R0, a
ADDI R0, 6
RETURN R0
토큰과 트리에서 스택 코드까지 뜻이 같다는 것을 무엇으로 확인할까?
단계 또는 사건표현 또는 상태해석

식

a−(2+3)*b

a=20, b=2

AST

Sub(a, Mul(Add(2,3),b))

뺄셈 오른쪽은 전체 곱

임시 코드

t1=2+3; t2=t1*b; t3=a−t2

결과는 10

스택 변화

[20]→[20,2]→[20,2,3]→[20,5]→[20,5,2]→[20,10]→[10]

먼저 꺼낸 10은 오른쪽 값

접은 코드

LOAD a; PUSH 5; LOAD b; MUL; SUB; RETURN

상수 덧셈만 없어짐

스택의 오른쪽 끝이 top이다. 각 산술 명령의 두 pop 순서와 AST 자식 순서를 대조한다. 최종 높이 1만으로 원식과 같은 값이라고 결론내리지 않는다.

중간 과정을 따라가는 예제

작은 순수 정수 표현식 a+2*3, 환경 ρ(a)=4를 토큰·AST·세 주소 코드·상수 접기·가상 명령으로 변환하라. +와*는 수학적 정수 연산이다.

  1. 토큰은 ID(a), PLUS, INT(2), STAR, INT(3).

  2. 곱셈 우선순위로 AST는 Add(Var(a), Mul(Int(2), Int(3))).

  3. IR은 t1=mul 2,3; t2=add a, t1; return t2. t1=6으로 접어 return add(a,6)으로 만든다.

  4. 가상 LOAD로 R0=4, ADDI로 R0=10, RETURN으로 10을 반환한다고 종이 추적한다.

예상 반환값은 10이다. 잘못 (a+2)*3으로 묶으면 18이 되어 소스 의미가 바뀐다. 실제 컴파일러 실행 결과는 아니다.

조건을 바꾸어 비교하기

괄호 손실은 어느 단계에서 드러나는가?

위 식에서 괄호를 지워 a−2+3*b로 번역했다. 같은 환경의 두 값과 AST를 비교하라.

  1. 원식은 20−(2+3)×2=10이다.

  2. 괄호를 지운 식의 AST는 Add(Sub(a,2),Mul(3,b))다.

  3. 잘못된 식은 (20−2)+6=24다.

10과 24의 차이는 스택 구현 전에 AST에서 이미 발생했다.

비교할 점

형식상 올바른 IR도 잘못된 AST의 뜻을 정확히 구현할 수 있다.

같은 높이의 반대 뺄셈

PUSH 9; PUSH 4; SUB; RETURN을 올바른 pop 계약과 잘못된 계약으로 비교하라.

  1. 올바른 계약에서 r=4, l=9이므로 5를 넣는다.

  2. 첫 pop을 왼쪽이라고 오해하면 4−9=−5를 넣는다.

  3. 두 구현 모두 산술 뒤 높이는 1이며 RETURN 형식도 통과한다.

형식 검사는 두 값을 구분하지 못하지만 명세 예상값 5는 오류를 드러낸다.

비교할 점

ADD와 MUL만 사용하는 시험은 이 특정 순서 오류를 가릴 수 있다.

종이와 본문으로 직접 해보기

(a+2)*3을 같은 환경 a=4로 토큰·트리·임시 코드로 옮기고, a+2*3과 비교하라.

힌트 보기

괄호 안 Add가 Mul의 자식이 된다. 상수만 있는 서브트리와 변수에 의존하는 서브트리를 구별하라.

풀이 보기

AST는 Mul(Add(Var(a), Int(2)), Int(3)). t1=add a,2; t2=mul t1,3; return t2이며 a=4에서 6→18이다. a+2*3은 10이므로 괄호를 단순히 지우면 안 된다.

오해와 반례

컴파일러는 소스 한 줄마다 기계어 한 줄을 만든다.

하나의 식이 여러 임시 연산으로 나뉘고 상수 곱셈은 없어질 수 있다. 줄과 명령의 개수 대응 대신 의미를 보존하는 구조와 단계별 규칙을 확인한다.

연습 1 · 값과 상태 예측

a=12, b=3에서 a−(2+3)*b의 값과 접은 스택 코드의 최대 높이를 예측하라.

힌트 1

5*b를 먼저 계산한다.

힌트 2

접은 코드는 LOAD a, PUSH 5, LOAD b, MUL, SUB다.

풀이와 답 확인

  1. 값은 12−15=−3이다.

  2. 접은 코드의 높이는 1,2,3,2,1이므로 최대 3이다.

  3. 접기 전 코드의 최대 높이는 표와 같이 3으로 동일하다.

명령 수 감소가 최대 스택 높이 감소를 보장하지 않는다.

흔한 오답에서 다시 생각하기

상수 접기를 하면 저장 피크도 반드시 줄어든다.

실제로 동시에 쌓이는 값을 추적하라. 이 두 코드는 명령 수가 달라도 높이 피크가 같다.

연습 2 · 오류 찾아 고치기

같은 우선순위의 9−4−2를 오른쪽부터 묶어 7이라 반환했다. AST와 값으로 고쳐라.

힌트 1

새 규약은 같은 우선순위를 왼쪽부터 묶는다.

힌트 2

Sub(Sub(9,4),2)를 계산한다.

풀이와 답 확인

  1. 올바른 트리는 Sub(Sub(9,4),2)이고 값은 3이다.

  2. 잘못된 Sub(9,Sub(4,2))는 7이다.

우선순위만 같게 설정하고 결합 방향을 빠뜨리면 의미가 달라진다.

흔한 오답에서 다시 생각하기

우선순위 표가 있으면 결합 방향은 아무렇게나 해도 된다.

동률 연산의 결합 방향도 문법 계약에 포함해야 한다.

연습 3 · 직접 만들어 보기

(a−2)*(b+1)을 위한 스택 코드를 만들고 a=7, b=2에서 추적하라.

힌트 1

왼쪽 서브트리를 완성한 값을 남긴다.

힌트 2

오른쪽 계산 중 왼쪽 값이 사라지지 않아야 한다.

풀이와 답 확인

  1. LOAD a; PUSH 2; SUB; LOAD b; PUSH 1; ADD; MUL; RETURN을 만든다.

  2. 스택은 [7]→[7,2]→[5]→[5,2]→[5,2,1]→[5,3]→[15]로 바뀐다.

  3. 최대 높이는 3이고 반환값은 15다.

임시값 수명과 pop 순서를 함께 보존했다.

왼쪽 결과 5는 최종 MUL까지 살아 있어야 한다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

순수 정수 모형에서 a*(b+c)를 a*b+a*c로 전개하면 저장과 연산이 같은가? 왼쪽부터 생성하는 스택 코드로 비교하라.

힌트 1

값 보존은 분배법칙이다.

힌트 2

전개식에서는 a를 두 번 읽는다.

풀이와 답 확인

  1. 원식은 LOAD a; LOAD b; LOAD c; ADD; MUL로 최대 높이 3, 산술 2회, 변수 읽기 3회다.

  2. 전개식은 LOAD a; LOAD b; MUL; LOAD a; LOAD c; MUL; ADD로 최대 높이 3, 산술 3회, 변수 읽기 4회다.

  3. 모든 정수 a,b,c에서 값은 같지만 이 가상 비용은 다르다.

의미 보존과 비용 개선은 서로 다른 주장이다.

같은 값을 주는 변환이면 언제나 더 빠르다.

준비 개념과 학습 목표

같은 최종 비트가 나오면 중간 오버플로와 출력도 없애도 될까?

새 세 규약을 나란히 둔다. Z는 수학적 정수다. U4는 0부터 15까지의 대표값을 사용하며 +와 *의 각 결과를 mod 16으로 만든다. T4는 같은 대표값을 가지지만 각 연산의 수학적 결과가 15를 넘으면 즉시 오류로 종료한다. T4의 오류는 자체 언어가 명시한 관찰이며 C의 UB나 LLVM poison이 아니다.

식 (x+1)*0은 Z와 U4에서 값을 0으로 바꿀 수 있다. 그러나 T4에서 x=15이면 첫 덧셈이 오류여서 0을 반환하지 않는다. 최종 값만 보고 중간 정의역이나 오류를 삭제하면 의미 보존 계약이 달라진다.

별도 효과 언어에서는 emit()이 문자 X를 출력하고 1을 반환하며 식의 자식을 왼쪽부터 평가한다. 관찰은 출력 문자열과 반환값 또는 오류다. 이런 효과를 가진 e에 대해 e+e를 2*e로 바꾸면 값이 같더라도 평가 횟수와 출력이 달라진다. 순수 언어의 대수 규칙을 조건 없이 가져오지 않는다.

번역의 계약은 관찰을 보존한다

결정론적이고 종료하는 작은 순수 언어에서 의미 ⟦e⟧ρ는 환경 ρ에서 식 e의 정수 값이다. 컴파일 결과 C(e)가 가상 기계에서 같은 환경의 값을 반환해야 한다는 것이 의미 보존 계약이다. 예를 들어 ⟦a+2*3⟧ρ=ρ(a)+6이므로 상수 접기는 변수 a의 모든 정수 값에서 같은 결과를 갖는다. a=4 하나의 통과만을 근거로 쓰지 않는다.

일반 언어에는 허용된 여러 동작이나 외부 상호작용이 있을 수 있다. 그때는 소스가 허용하는 관찰 동작 안에 목표 동작이 들어가는 정제 관계를 사용할 수 있다. 정의되지 않은 동작(UB)은 소스 명세가 결과를 요구하지 않는 경우이며, 이를 특정 랩어라운드 결과나 반드시 발생하는 오류 메시지로 해석하지 않는다. 컴파일러가 정의된 프로그램까지 마음대로 바꿔도 된다는 뜻은 아니다.

정수의 종류부터 구분한다

수학적 정수에서 x+1>x는 모든 정수 x에 참이다. 8비트 unsigned 랩어라운드에서 x=255이면 x+1=0이고 비교는 거짓이다. 따라서 그 모형에서 비교를 항상 true로 바꾸면 잘못이다. C의 정수 승격도 실제 표현식 타입에 영향을 주므로 이 8비트 모형을 C의 unsigned char 식과 동일하게 취급하지 않는다.

기본 C 규칙의 부호 있는 정수 연산은 결과가 해당 타입 범위를 넘으면 UB다. 예를 들어 int가 32비트이고 최대값이 2147483647인 구현을 가정하면 그 값에 1을 더하는 것은 정의된 랩어라운드 예가 아니다. C의 x+1>x를 true로 바꾸는 변환을 판단할 때는 x+1이 정의된 입력의 범위를 기준으로 한다. 명시적 랩어라운드 옵션·언어 타입·확장 규칙을 쓴다면 계약이 달라진다.

값이 같아도 효과나 오류가 달라질 수 있다

이 절의 순수 정수 언어에서 e는 항상 값을 주고 부수효과가 없으므로 0*e를 0으로 바꾸는 근거를 쓸 수 있다. 하지만 e가 파일에 한 줄을 쓰거나 오류를 발생시키는 일반 언어라면 e의 평가를 삭제하는 것이 관찰을 바꿀 수 있다. 예외·I/O·메모리 접근·평가 순서·종료도 최적화 전제에 포함해야 한다.

부동소수점 덧셈은 반올림 때문에 수학적 실수처럼 결합법칙을 무조건 쓰지 못한다. 예를 들어 자체 십진 두 유효숫자 모형에서 각 덧셈 결과를 반올림하면 (1000+−1000)+1은 1, 1000+(−1000+1)은 0이다. 뒤 괄호의 −999를 −1000으로 반올림하기 때문이다. 이 가상 모형은 IEEE 실험 결과가 아니라 정수 대수 규칙을 다른 연산으로 옮길 때의 반례다.

중간 과정을 따라가는 예제

의미를 두 모형으로 비교하라. 모형 Z는 모든 수학적 정수, 모형 U8은 0..255에서 덧셈을 mod256으로 하고 비교는 그 대표값의 보통 순서로 한다. 식 (x+1)>x를 항상 true로 바꾸는 것이 허용되는가?

  1. Z에서 모든 x에 대해 x+1−x=1>0이므로 원식은 true다.

  2. U8에서 x=254이면 255>254라 true다.

  3. U8에서 x=255이면(255+1) mod256=0이므로 0>255는 false다.

  4. 항상 true로 바꾸는 변환은 Z에서는 의미를 보존하지만 U8에서는 x=255 반례로 실패한다.

연산 규칙에 따라 결론이 달라진다. U8 반례를 C signed overflow의 정의된 실행으로 부르지 않는다.

준비 개념과 학습 목표

준비 개념

독립처럼 보이는 두 실행기가 같은 잘못된 파서를 쓰면 무엇을 놓칠까?

새 오류 가설은 파서가 모든 이항 연산을 같은 우선순위로 왼쪽부터 묶는 것이다. AST 해석기와 스택 번역기가 이 파서를 공유하면 두 결과가 같은 잘못된 값으로 일치할 수 있다. 비교 경로가 둘이라는 사실과 오류 원인이 독립이라는 사실을 구분하자.

기본 작은 언어의 +와 *만 사용하는 명세 예상값을 손으로 만든다. 식 2+3*4의 정답은 14다. 공유 파서는 (2+3)*4로 묶어 20을 주고 두 경로 모두 20이라 서로만 비교하면 통과한다. 반면 2*3+4는 잘못된 파서도 우연히 10을 주어 이 입력 하나는 결함을 드러내지 않는다.

어휘·구문·이름·IR 형식·번역 의미·관찰 효과는 별도 시험 축이다. 실패 입력에는 임의 숫자를 요구하지 않고 진단 범주를 기록한다. 아래 모든 표는 설계한 예상값이며 실제 실행 로그나 커버리지 측정이 아니다.

  • 토큰·문법·이름 검사

세 언어와 실행 환경을 먼저 표시한다

작은 식 언어의 컴파일러를 Python으로 작성해 가상 명령을 출력한다면 소스 언어는 식 언어, 구현 언어는 Python, 목표는 가상 명령이다. Python 문법이 입력 언어의 문법이라는 뜻은 아니다. 컴파일러를 실행하는 호스트와 출력 프로그램이 실행될 타깃도 다를 수 있다. 이 단원은 실제 구현 설치를 필수로 하지 않고 명세와 테스트를 종이로 설계한다.

도구는 lexer/parser 생성기, IR 라이브러리, 어셈블러, 링커, 테스트 실행기 등 역할이 다르다. LLVM을 연결했다고 이름 해석이나 타입 규칙까지 자동으로 구현한 것은 아니다. 또한 구현 언어의 정수·문자열 규칙을 소스 의미로 실수로 가져오지 않도록 소스 규칙을 명시해야 한다. 호스트 정수가 큰 값을 담아도 목표 레지스터가 같은 범위라는 보장은 없다.

각 단계의 계약과 끝까지의 관찰을 시험한다

작은 언어의 명세는 INT/ID/+/*/괄호 토큰, 곱셈 우선, 괄호와 왼쪽 묶임, 수학적 정수 연산, 모든 이름의 환경 정의를 포함한다. 어휘 시험은 토큰, 구문 시험은 AST, 이름 시험은 잘못된 입력의 진단을 대조한다. IR가 잘 형성되었다는 검사와 실행 결과가 맞다는 검사는 서로 다른 검사다. 원인이 어디인지 찾기 위해 중간 구조를 남긴다.

전체 시험은 같은 식과 환경에 대해 직접 AST 의미와 번역한 가상 명령의 결과를 비교할 수 있다. 직접 의미 계산기를 독립하게 만들지 않고 둘이 같은 잘못된 parser를 공유하면 같은 오류로 일치할 수 있다. 따라서 명세에서 손으로 얻은 우선순위·경계·잘못된 입력 사례도 필요하다. 최적화 전후의 값 비교도 둘 다 잘못되었을 가능성을 배제하지 않는다.

통과한 시험의 범위를 정확하게 말한다

회귀 시험은 발견한 오류를 재현하는 작은 입력을 남겨 수정 뒤 다시 깨지는 것을 찾는 것이다. a+2*3을 (a+2)*3으로 잘못 묶은 오류에는 a=4의 예상 10이 유용하고, 괄호 입력은 예상 18을 별도로 둔다. 무작위 생성 식을 많이 비교하는 차등 시험은 추가 반례를 찾는 데 도움이 되지만 유한 통과를 모든 길이의 증명으로 바꾸지 않는다.

자기 컴파일은 구현 경로와 많은 입력을 거치는 중요한 점검일 수 있지만 올바름의 완전한 증명은 아니다. 같은 버그를 포함한 컴파일러가 자기 소스를 안정적으로 번역할 수 있다. 버전·호스트·타깃·옵션·입력·기대 결과·실제 결과와 실행 여부를 기록해야 재현할 수 있다. 이 문서의 테스트 표는 설계된 예상값이며 실제 LLVM 시험 로그가 아니다.

중간 과정을 따라가는 예제

이 작은 순수 정수 언어의 종이 테스트 표를 작성하라. 입력 a+2*3와(a+2)*3의 a=4, 입력 2*(3+4), 문법 오류 a+*3, 정의되지 않은 이름 b+1을 검사한다. 환경은 a만 정의되어 있다.

  1. a+2*3은 Add(a, Mul(2,3))와 예상값 10을 적는다.

  2. (a+2)*3은 Mul(Add(a,2),3)와 예상값 18을 적는다.

  3. 2*(3+4)는 Mul(2, Add(3,4))와 예상값 14를 적는다.

  4. a+*3은 구문 진단이며, b+1은 문법에 맞지만 이름 진단이다. 오류 입력에는 임의 숫자 정답을 요구하지 않는다.

정상값 10/18/14와 서로 다른 두 진단이 테스트 기준이다. 모두 실행하지 않은 예상 결과다.

차등 일치의 가짜 통과

2+3*4의 공유 AST 해석기와 백엔드가 모두 20을 준다. 독립 명세 기준으로 판단하라.

  1. 명세는 곱셈 3*4를 먼저 계산하므로 14다.

  2. 공유 AST는 Mul(Add(2,3),4)이고 해석기는 20을 준다.

  3. 그 AST의 올바른 백엔드도 20을 주어 두 경로의 비교는 일치한다.

일치는 이 둘의 공유 결함을 배제하지 못한다.

비교할 점

백엔드가 공유 AST의 뜻을 보존했다는 사실과 소스 뜻을 보존했다는 사실이 다르다.

검증기와 의미 oracle의 다른 경계

위 잘못된 AST의 코드 PUSH 2; PUSH 3; ADD; PUSH 4; MUL; RETURN의 높이와 결과를 구하라.

  1. 높이는 1,2,1,2,1이며 마지막 RETURN 전 하나다.

  2. 스택의 부족이나 잔여 값 오류는 없다.

  3. 반환값은 20이어서 명세 14와 다르다.

형식 검증기는 정상 코드를 받아도 의미 oracle은 실패를 보고한다.

비교할 점

형식 검증 통과를 명세 의미 보존의 증명으로 바꾸지 않는다.

종이와 본문으로 직접 해보기

잘못된 파서가 +의 우선순위를 *보다 높게 정한다고 하자. a=4에서 a+2*3과 2*3+4가 각각 오류를 드러내는지 판단하라. 이어 이 잘못된 파서도 우연히 통과하는 단일 연산 식 하나를 추가하고 예상값을 적어라.

힌트 보기

첫 식의 잘못된 AST는 Mul(Add(a,2),3)이다. 둘째는 잘못 덧셈을 묶으면 Mul(2, Add(3,4))가 된다.

풀이 보기

첫 식은 18≠정답 10, 둘째는 14≠정답 10으로 모두 반례다. 우연히 통과하는 입력으로 2+3 또는 2*3을 추가하면 연산 종류가 하나라 우선순위 오류가 드러나지 않는다. 통과 입력만 많이 모으면 같은 결함을 놓칠 수 있다.

오해와 반례

정상 입력 몇 개의 출력이 맞으면 lexer·parser·최적화·백엔드가 전부 증명되었다.

2+3은 올바르지만 a+2*3은 잘못 번역하는 parser가 반례다. 명세의 분기와 진단·타입·경계를 포함한 시험이 필요하며 유한 시험과 전체 의미 보존 증명은 구분한다.

다른 문제에 적용하기

공유 파서와 효과 삭제를 따로 감사한다

새 보고서가 기본 식 2+3*4에서 공유 파서의 AST 해석기와 스택 번역기 모두 20을 주어 통과했다고 했다. 같은 보고서는 자체 T4에서 x=15의 (x+1)*0→0과 왼쪽부터 평가하는 효과 언어의 f()+g()→g()+f()도 반환값이 같아 통과라 했다. f는 A를 출력하고 2를, g는 B를 출력하고 3을 반환한다. 각 항목의 명세 예상 관찰, 실패 단계, 새 회귀 기준을 만들라. 실제 LLVM/Clang/학생 시험이 수행됐는지도 구분하라.

힌트 1

첫 식은 기본 우선순위에서 14이며 두 경로의 공유 AST부터 확인한다.

힌트 2

T4의 오류와 출력 순서도 관찰이다. 정상 값만 비교하지 않는다.

풀이와 답 확인

  1. 첫 식의 명세 AST는 Add(2,Mul(3,4))이고 정답은 14다. 공유 AST Mul(Add(2,3),4)의 두 경로 값 20은 파서 오류를 가린다.

  2. T4 원식은 15+1에서 오류로 종료하지만 변환식은 0을 반환한다. x=14에서는 둘 다 0이라는 통과도 별도로 남긴다.

  3. 효과 언어의 원식은 (출력 AB, 반환 5), 교환식은 (출력 BA, 반환 5)여서 관찰이 다르다.

  4. 회귀 기준은 독립 예상값 14, T4의 x=15 오류/x=14 정상 0, 그리고 출력 AB와 반환 5다. 오류 입력에 임의 숫자를 정답으로 요구하지 않는다.

  5. 이것은 명시 규약의 손계산 시험 설계다. 실제 compiler/IR/명령/학생 실행과 전체 입력의 구현 증명은 수행하지 않았다.

공유 우선순위 결함, 중간 오류 삭제, 효과 순서 변경이 각각 실패 원인이다. 명세 값과 진단·출력을 독립으로 적어 세 시험 축을 구분한다.
