소단원 4.1

읽기·쓰기·위치 이동

파일에서 읽을 다음 바이트는 누가 기억할까?

준비 개념과 학습 목표

준비 개념

  • 바이트와 길이

  • 0부터 시작하는 위치

  • 함수 반환값

학습 목표

  • 요청량과 처리량을 구별한다.

  • 읽기·쓰기 이후 오프셋을 추적한다.

  • seek만으로 파일 길이가 늘지 않음을 설명한다.

파일 내용과 현재 위치

일반 파일을 바이트의 줄로 보고 첫 바이트의 위치를 0이라 하자. 길이 6인 파일의 바이트 위치는 0부터 5까지이며 위치 6은 끝 바로 다음이다. 현재 오프셋은 다음 읽기나 쓰기를 시작할 위치다. 여기서는 동시 접근이 없는 한 열린 파일, 일반 파일의 성공 호출, O_APPEND가 없는 조건을 사용한다.

read(fd,buf,n)은 최대 n바이트를 요청한다. 성공 반환 k가 실제 받은 바이트 수이며 오프셋은 k만큼 증가한다. 양수 요청에서 반환 0은 파일 끝을 만났음을 나타낸다. 오류는 -1과 오류 정보로 구분한다. 요청량보다 작은 성공 반환도 가능하므로 요청 n으로 위치를 갱신하면 아직 읽지 않은 영역을 건너뛸 수 있다.

쓰기와 위치 이동

write 역시 반환한 실제 처리량만큼 위치를 옮긴다. 중간 위치에 쓰면 기존 바이트를 덮어쓰며 뒤 내용을 자동으로 밀어내지 않는다. 요청을 모두 처리하지 못했으면 남은 부분을 적절히 재시도해야 한다. 예제에서는 write가 요청량을 모두 처리한다는 별도 종이 가정을 두지만 실제 API의 항상 전량 처리 보장은 아니다.

lseek의 SEEK_SET은 시작 기준, SEEK_CUR은 현재 기준, SEEK_END는 길이 기준으로 위치를 계산한다. 새 위치가 음수이면 이 일반 파일 모형에서는 유효하지 않다. 파이프처럼 위치 이동을 지원하지 않는 대상도 있다. seek 성공 자체는 데이터를 읽거나 쓰지 않는다.

끝 바깥과 공유 상태

파일 끝을 넘어 seek할 수 있지만 위치만 바꾸는 동안 길이는 그대로다. 그 뒤 새 위치에 쓰면 파일이 늘며 중간 공백 영역을 읽을 때 0바이트 값이 나온다. 이것은 실제로 0값인 바이트가 있다는 뜻이며 read가 0개를 반환하는 EOF와 다르다. 물리적으로 같은 수의 저장 블록이 반드시 할당되는지는 파일시스템에 달려 있다.

파일 디스크립터 번호와 열린 파일 설명은 구별한다. 일부 복제된 디스크립터는 같은 오프셋을 공유하지만 파일을 별도로 열면 서로 다른 오프셋을 가질 수 있다. 또한 O_APPEND 쓰기는 일반적인 현재 위치 덮어쓰기와 달리 쓰기 전에 끝으로 위치를 맞춘다. 여기의 계산 결과는 이러한 조건을 바꾸면 다시 계산해야 한다.

중간 과정을 따라가는 예제

초기 바이트는 ABCDEF, 길이 6, 위치 0이다. 오류 없이 read(3), seek(-1,CUR), write(XY), seek(0,SET), read(10)을 순서대로 수행한다. read는 요청량과 남은 길이 중 작은 양을 받고 write는 두 바이트를 전량 처리한다.

  1. read(3)은 ABC를 받고 위치를 0+3=3으로 만든다.

  2. seek(-1,CUR)은 3−1=2로 위치를 옮기며 내용과 길이는 그대로다.

  3. write(XY)는 위치 2의 C, 위치 3의 D를 덮어쓴다. 내용은 ABXYEF, 위치는 4, 길이는 6이다.

  4. seek(0,SET)으로 위치 0이 된다. read(10)은 남은 6바이트 ABXYEF를 받아 6을 반환하고 위치는 6이다. 다음 양수 read는 0을 반환한다.

최종 내용 ABXYEF, 길이 6, 위치 6이다. 마지막 요청량 10은 실제 반환량 6과 다르다.

종이와 본문으로 직접 해보기

초기 ABCDEF를 새로 사용한다. seek(8,SET) 직후 길이를 적고, 한 바이트 Z를 전량 쓰고 길이·위치를 적어라. 위치 6부터 3바이트 읽었을 때의 바이트 값도 종이에 표시하라.

힌트 보기

길이는 마지막 저장된 바이트 위치+1이다. 위치 6과 7은 문자 0이 아닌 값 0인 바이트로 그려라.

풀이 보기

seek 직후 길이는 여전히 6이다. 위치 8에 Z를 쓰면 길이 9, 위치 9가 된다. 위치 6부터 읽는 3바이트는 [0값,0값,Z]이며 반환량은 3이다. 0값 바이트를 읽은 것이 EOF 반환 0과 혼동되지 않도록 구별한다.

오해와 반례

seek로 멀리 가는 순간 파일 길이가 늘어난다.

길이 6에서 위치 8로 이동해도 쓰기 전 길이는 6이다. 위치 변경과 데이터 확장은 다른 연산이다. 끝 밖의 쓰기 뒤에야 길이가 9가 된다.

자기점검

read가 5를 요청하고 2를 반환하면 위치는 얼마나 증가하는가?

답과 이유 보기

2만큼이다.

실제로 읽은 양을 반영한다.

XY를 위치 2에 쓰면 C와 D가 뒤로 밀리는가?

답과 이유 보기

일반 덮어쓰기에서는 아니다.

바이트 2와 3이 교체되며 삽입 연산이 아니다.

길이 6, 위치 4에서 seek(-2,END)의 새 위치는?

답과 이유 보기

4다.

끝 기준 6−2이며 현재 위치는 이 계산 기준에 들어가지 않는다.

한 단계 더

read와 write의 짧은 성공 반환을 가정한 추적표를 만들어 보라. 요청 5가 2+3으로 완료되려면 버퍼의 다음 시작 위치도 실제 반환 2만큼 옮겨야 한다. 실제 시스템 구현에서는 오류·신호·동시 접근까지 별도로 다룬다.

소단원 4.2

페이지 캐시·버퍼 풀

한 번 읽은 페이지를 다시 읽을 때 저장장치까지 가야 할까?

준비 개념과 학습 목표

준비 개념

  • 페이지와 메모리

  • 집합·순서

  • 파일 읽기

학습 목표

  • OS 캐시와 DB 버퍼 풀을 구별한다.

  • hit·miss·dirty·pin의 뜻을 구별한다.

  • 명시한 교체 정책의 사건열을 계산한다.

서로 다른 계층의 보관소

OS의 페이지 캐시는 일반적인 파일 읽기와 쓰기에서 데이터를 메모리에 보관한다. 동일 데이터가 캐시에 있으면 반복 접근이 저장장치 읽기로 바로 이어지지 않을 수 있다. Linux 문서는 일반 read/write/mmap이 이 경로를 거치며 O_DIRECT 같은 우회 방식도 있다고 설명한다. 모든 파일 접근이 예외 없이 같은 캐시 경로를 가진다고 말할 수는 없다.

DB 버퍼 풀은 DBMS가 자기 페이지를 관리하는 메모리 영역이다. frame은 페이지를 담는 슬롯이며 page ID로 어떤 페이지가 들어 있는지 찾는다. OS 페이지와 DB 페이지의 크기가 반드시 같지는 않다. DB 버퍼 풀의 miss가 OS 캐시에서는 hit일 수도 있어 두 계층의 miss 수와 물리 저장장치 읽기 수를 동일시하면 안 된다.

변경됨과 사용 중은 다른 상태

dirty는 메모리 페이지가 하위 계층으로 아직 반영되지 않은 변경을 가졌음을 뜻한다. pin count는 현재 그 페이지를 사용하며 교체되지 않게 잡아 둔 요청자의 수를 추적한다. 읽기만 한 페이지는 clean이어도 pin될 수 있고, 수정한 뒤 사용을 끝낸 페이지는 dirty이면서 unpinned일 수 있다. 둘은 서로 다른 질문에 답한다.

교체할 때에는 사용 중인 pinned 페이지를 피하고, dirty 페이지의 필요한 쓰기 처리를 해야 한다. 모든 frame이 pin되어 있으면 단순히 가장 오래된 것을 빼는 대신 대기·실패 등 구현 정책이 필요하다. DB의 write-back도 지속성 완료와 같다고 자동으로 결론 내리지 않는다. 하위 OS 캐시에 넘어갔을 가능성이 있다.

정책을 정해야 수를 셀 수 있다

이 절의 LRU 종이 모형은 요청 때마다 해당 페이지를 가장 최근 사용으로 갱신하고 요청 직후 unpin한다. 가득 찼을 때 가장 오래 사용하지 않은 페이지를 교체한다. 모든 페이지는 clean, 처음에는 비어 있고 미리 읽기와 백그라운드 동작은 없다고 정한다. 실제 강의·제품에서 마지막 unpin 시점을 사용하기도 하므로 정책의 갱신 시점을 명시해야 한다.

hit는 요청 페이지가 풀에 이미 있는 사건이며 hit rate=hit 수/전체 요청 수다. 작은 풀보다 큰 작업 집합을 반복 순회하면 최근 사용 정책도 계속 miss가 날 수 있다. 좋은 정책이 모든 접근 패턴에서 최선이라는 보장은 없고, 페이지 요청 수·하위 읽기 수·측정 시간은 서로 다른 지표다.

중간 과정을 따라가는 예제

위의 LRU 모형에서 frame 2개, 페이지 요청 A,B,A,C,A,B를 추적하라. 매 단계의 가장 오래된→가장 최근 순서와 hit/miss를 적어라.

  1. A는 miss로 [A], B도 miss로 [A,B]가 된다. 아직 교체는 없다.

  2. A는 hit이다. A를 최근으로 옮겨 [B,A]가 된다.

  3. C는 miss이다. 가장 오래된 B를 제거하여 [A,C]가 된다.

  4. A는 hit로 [C,A], 마지막 B는 miss로 C를 제거하여 [A,B]다. 총 hit 2, miss 4, 요청 6이다.

hit rate는 2/6=1/3, 최종 풀은 [A,B]다. 이 모형의 miss 4를 실제 장치 읽기 4회라고 주장하지 않는다.

종이와 본문으로 직접 해보기

같은 두 frame으로 A,B,C,A,B,C를 추적하라. 이어 A,B가 둘 다 pin된 상태에서 C를 요청한다면 LRU만으로 교체가 가능한지 설명하라.

힌트 보기

매번 가장 오래된 페이지를 지우되 pin 조건을 만족하는 교체 후보가 있는지 먼저 확인한다.

풀이 보기

처음 A와 B를 넣고 C가 A를, 다음 A가 B를, B가 C를, C가 A를 제거한다. 여섯 요청 모두 miss다. A와 B 모두 pin된 별도 상태에서는 교체 가능한 frame이 없어 LRU로 아무 페이지나 제거할 수 없다. 대기나 실패 같은 다음 동작은 별도 정책이다.

오해와 반례

dirty는 페이지가 인기 있다는 표시다.

읽기 요청이 매우 많아도 수정하지 않았다면 clean일 수 있다. 한 번 수정하고 다시 읽지 않아도 dirty일 수 있다. 인기도·최근 사용·현재 pin과 변경 여부를 서로 구별해야 한다.

자기점검

답과 이유 보기

아니다.

clean이면서 pin된 페이지를 교체해도 되는가?

답과 이유 보기

이 모형에서는 안 된다.

변경 여부와 관계없이 현재 사용자가 잡고 있기 때문이다.

hit2, 요청6의 hit rate는?

한 단계 더

같은 사건열에서 frame을 3개로 늘려 결과를 비교하라. A,B,C,A,B,C는 최초 세 miss 후 세 hit로 1/2다. 이어 dirty 페이지의 하위 쓰기와 OS 캐시 동기화를 상태표의 서로 다른 열로 추가해 보라.

flush·fsync·쓰기 증폭

화면에서 파일을 다시 읽을 수 있으면 전원을 꺼도 안전할까?

준비 개념과 학습 목표

준비 개념

  • 사용자 메모리와 OS

  • 쓰기 반환값

  • 페이지와 바이트

학습 목표

  • 버퍼 비우기의 대상 계층을 명시한다.

  • 가시성과 지속성·원자성을 구별한다.

  • 쓰기 증폭의 분자·분모를 설정한다.

flush라는 말의 범위

프로그램의 출력 버퍼, OS 페이지 캐시, 장치의 휘발성 캐시는 서로 다른 계층이다. 출력 fflush는 C 라이브러리의 사용자 버퍼를 아래 쓰기 경로로 보내는 연산이다. 성공했다고 물리적 지속 저장까지 끝났다고 해석하면 안 된다. 다른 라이브러리의 flush도 대상과 보장은 해당 문서를 읽어 판단해야 한다.

성공한 write의 데이터는 일반적으로 이후 읽기에서 보일 수 있지만 지속성이 같은 말은 아니다. 사용자가 다시 읽었다는 관찰은 캐시에서 최신 값을 읽었을 가능성도 포함한다. 예제는 background write가 없다는 자체 모형으로 상태 이동을 보여 주며 실제 OS가 정확히 그 순간까지 기다린다고 주장하지 않는다.

동기화의 보장과 경계

Linux fsync는 지정한 파일의 변경 데이터와 관련 메타데이터를 지속 저장 장치로 동기화하고 장치의 완료 보고를 기다린다. 반환 오류도 검사해야 한다. 사용자 출력 버퍼가 남아 있다면 아직 커널에 보내지 않은 내용은 파일의 fsync만으로 처리되지 않는다. 그러므로 해당 스트림의 출력 flush를 성공시킨 뒤 적절한 파일 디스크립터로 fsync하는 순서를 구별한다.

파일 fsync가 포함 디렉터리의 이름 변경·새 항목까지 반드시 지속시킨다는 뜻은 아니다. Linux 문서는 디렉터리에 대한 별도 fsync가 필요할 수 있음을 명시한다. 또한 여러 파일의 업데이트를 하나의 원자적 거래로 만드는 일은 별도 복구 프로토콜이다. fsync 하나만으로 중간 고장에 대한 전체 거래의 원자성을 얻었다고 말하지 않는다.

쓰기 증폭의 단위를 정하기

쓰기 증폭은 선택한 하위 계층의 실제 쓰기 바이트 수를 애플리케이션의 논리적 변경 바이트 수로 나눈 비율로 정의한다. 어떤 계층을 재는지, 중복 갱신을 분모에 세는지, 저널·메타데이터·SSD 내부 복사를 분자에 넣는지 명시해야 비교할 수 있다. 한 바이트 수정이 더 큰 페이지 쓰기로 이어지면 비율이 1보다 커질 수 있다.

같은 페이지의 여러 갱신을 모아 한 번 쓰면 이 모형의 하위 쓰기량을 줄일 수 있다. 그러나 중간 갱신의 지속성을 즉시 보장해야 한다면 모으기만 할 수는 없다. 저널이나 복구 로그도 필요한 안전성을 위한 추가 쓰기이며, 높은 비율만 보고 불필요하다고 판단하지 않는다. 페이지 크기와 장치 쓰기 단위는 예제의 가정이지 모든 장비의 규격이 아니다.

중간 과정을 따라가는 예제

자체 모형에서 앱은 같은 4096바이트 페이지의 서로 다른 64바이트 영역 두 개를 수정한다. 논리 변경량은 128바이트다. 정책 P는 각 수정 뒤 전체 페이지를 하위 계층에 한 번씩 쓰고, 정책 B는 둘을 모아 한 번 쓴다. 저널·메타데이터·장치 내부 복사·백그라운드 쓰기는 제외한다. 비율과 상태 단계를 계산하라.

  1. 논리 변경량은 서로 다른 두 영역 64+64=128바이트다. 최종 변경량과 누적 변경량이 이 예제에서는 같다.

  2. P의 하위 쓰기는 4096×2=8192바이트이므로 증폭은 8192/128=64다.

  3. B의 하위 쓰기는 4096바이트이므로 증폭은 4096/128=32다. 쓰기 횟수와 바이트 비율은 별도 지표다.

  4. 앱 출력 버퍼에만 있다면 아래 계층에는 아직 보내지지 않았다. 출력 flush 뒤 커널에 보낸 상태와 fsync 성공 뒤의 지속성 완료 상태를 구분한다. 이 사건열의 byte 수 계산은 장치 실행 결과가 아니다.

명시한 하위 페이지 쓰기 계층의 증폭은 P=64, B=32다. 정책 B는 쓰기량을 절반으로 줄이지만 첫 수정 직후의 지속성을 이 모형에서 제공하지 않는다.

종이와 본문으로 직접 해보기

논리 변경량 128을 유지하되 정책 B에 4096바이트의 저널 쓰기 한 번을 추가한다고 정하라. 비율을 구하고 출력 flush 없이 fsync부터 호출한 경우 앱 버퍼 내용의 운명을 설명하라.

힌트 보기

분자는 DB 페이지와 저널의 합이다. fsync가 처리할 수 있는 파일 상태에 사용자 버퍼가 이미 들어갔는지 따져라.

풀이 보기

하위 쓰기량은 DB4096+저널4096=8192바이트이며 비율은 64다. 이는 본 활동이 정한 최소 종이 비용으로 실제 SQLite 거래 비용을 예측한 값이 아니다. 앱 버퍼를 보내지 않고 fsync하면 그 버퍼 내용은 커널의 파일 변경분에 아직 들어 있지 않아 해당 내용의 지속성이 확보됐다고 말할 수 없다.

오해와 반례

flush나 fsync 성공은 여러 파일 변경 전체의 원자성을 자동 보장한다.

A 파일을 먼저 지속시키고 B 파일을 변경하기 전에 중단되면 A만 새 상태인 중간 상태가 가능하다. 개별 파일의 지속성 동기화와 여러 변경의 전부 또는 전무 복구는 다른 요구다.
