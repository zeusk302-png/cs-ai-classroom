소단원 10.1

append-only와 정리

공책에 수정할 때마다 새 줄을 쓰면 마지막 정답은 쉽지만 오래된 줄은 어떻게 치울까?

준비 개념과 학습 목표

준비 개념

  • 키·값

  • 순서와 최신 버전

  • 바이트 크기

학습 목표

  • 추가 기록과 제자리 갱신을 구별한다.

  • 최신 값과 삭제 표식을 추적한다.

  • 정리 시 버전·복구·공간 조건을 설명한다.

수정도 새 기록으로 남기기

append-only는 이 모형에서 기존 기록을 덮지 않고 뒤에 새 기록을 붙이는 방식이다. 키 A의 값을 바꾸면 A의 새 값과 순서를 기록한다. 읽을 때는 같은 키의 유효한 최신 기록을 선택한다. 옛 기록은 파일에 남을 수 있어 논리 데이터와 물리 바이트가 다르다.

삭제도 지워졌다는 표식인 tombstone을 새 기록으로 남길 수 있다. 이전 값을 찾았더라도 더 최신 삭제 표식이 있으면 현재 조회는 없음이다. 이 절은 모든 기록의 전역 순서가 알려지고 스냅샷 독자가 없는 작은 자체 모형을 다룬다.

살아 있는 기록만 새 파일로 옮기기

정리 과정에서는 필요한 기록을 읽고 새 파일에 보존할 기록을 쓴다. 모든 오래된 기록을 한 번에 다시 볼 수 있고 과거 읽기·복구 요구가 없다면 현재 값만 남긴 뒤 이전 파일을 제거할 수 있다. 원본을 먼저 삭제하고 새 파일을 쓰다가 실패하는 순서는 안전한 교체가 아니다.

삭제 표식을 버려도 되는지는 옛 값이 다른 파일에 남아 있는지를 포함해 판단한다. 표식을 지웠는데 다른 계층에서 오래된 값이 발견되면 삭제된 키가 되살아날 수 있다. 스냅샷이 과거 버전을 읽는 시스템에서는 최신 값만 남기는 정책도 충분하지 않다.

추가 기록이 곧 영속성은 아니다

메모리나 운영체제 버퍼에 기록했다는 사실과 장애 후 디스크에서 복구할 수 있다는 사실은 다르다. 실제 저장 엔진은 로그 동기화, 파일 설치와 메타데이터 기록, 복구 규칙을 정한다. append-only라는 형식 자체가 모든 쓰기의 장애 내구성을 보장하지 않는다.

RocksDB의 WAL은 memtable 변경을 복구하는 로그이며 선택적으로 비활성화할 수 있다. 동기화 여부도 쓰기 옵션에 달린다. 이 절의 단일 로그 정리 모형은 WAL과 SST의 정확한 수명이나 실제 장애 복구를 구현했다고 주장하지 않는다.

중간 과정을 따라가는 예제

전역 순서대로 A=1, B=2, A=3, delete B, C=4, A=5가 있다. 각 기록은 삭제 표식도 포함해 20바이트다. 모든 관련 기록을 한 번에 정리하고 과거 독자·다른 파일·복구 의존성이 없다고 가정한다. 현재 값과 정리 크기를 구하라.

  1. A의 가장 최신 기록은 여섯 번째 A=5다. B의 최신 기록은 네 번째 삭제 표식이므로 현재 없다. C의 최신 기록은 C=4다.

  2. 입력은 6×20=120바이트다. 모든 관련 옛 기록이 함께 제거되는 조건이므로 삭제 B의 표식도 버릴 수 있다.

  3. 새 파일은 A=5와 C=4의 2×20=40바이트다. 새 파일이 설치되기 전 입력과 출력이 함께 존재하면 120+40=160바이트를 쓴다.

현재 A=5, C=4이며 B는 없다. 정리 후 40바이트, 원본과 출력 공존 시 160바이트다. 파일 헤더·인덱스·여유 공간은 이 모형에서 제외한다.

종이와 본문으로 직접 해보기

최신 두 기록을 40바이트로 복사했는데 별도 오래된 파일에 B=2가 남아 있다고 바꾸자. 삭제 표식을 버리면 생기는 문제와 표식까지 20바이트로 보존할 때 출력 크기는?

힌트 보기

정리 범위 밖의 옛 값을 막는 표식이 필요한지 먼저 판단한다.

풀이 보기

B의 삭제 표식을 버리면 남은 B=2를 최신 남은 값으로 잘못 반환할 수 있다. 표식까지 보존한 출력은 A=5, C=4, delete B의 60바이트다. 이 조건에서는 40바이트 정리가 안전하지 않다.

오해와 반례

맨 뒤에만 쓰면 정리나 복구 조건 없이 항상 빠르고 안전하다.

추가 쓰기로 생긴 옛 버전이 공간과 읽기 비용을 늘린다. 정리는 추가 읽기·쓰기를 만들며 실제 내구성에는 동기화와 복구 규칙이 필요하다. 과거 독자나 다른 파일이 있다면 더 많은 기록을 보존해야 한다.

자기점검

원래 로그에서 B의 현재 값은 2인가?

답과 이유 보기

아니다. 없음이다.

B의 더 최신 기록이 삭제 표식이다.

정리 후40바이트이면 최대 공존 공간도40인가?

답과 이유 보기

이 모형에서는160바이트다.

입력120을 아직 제거하지 않은 시점에 출력40이 함께 있다.

스냅샷이 A=3 시점을 읽는다면 A=5만 보존해도 되는가?

답과 이유 보기

그렇게 일반화할 수 없다.

과거 시점에 필요한 버전까지 보존할 조건이 추가된다.

한 단계 더

각 기록을 32바이트로 바꾸면 입력192, 출력64, 공존256바이트다. 기록 수는 그대로6과2다. 최신 값의 선택 규칙은 바이트 크기가 바뀌어도 달라지지 않는다.

소단원 10.2

LSM의 메모리·디스크 계층

한 곳에 최신 값이 모두 없다면 작은 정렬 공책 여러 권에서 어떻게 찾을까?

준비 개념과 학습 목표

준비 개념

  • 정렬·병합

  • 키의 최신 기록

  • 메모리와 저장 장치

학습 목표

  • memtable·WAL·SST의 역할을 구별한다.

  • 여러 계층에서 버전과 tombstone을 선택한다.

  • flush와 compaction을 구분한다.

새 쓰기는 메모리에서 모이기

LSM 구조에서는 쓰기를 메모리 구조에 모으고 정렬된 파일로 내보내며 여러 파일을 병합한다. RocksDB의 기본 구성에는 memtable, SST 파일, WAL이 있다. memtable은 현재 메모리 변경을 담고 WAL은 설정에 따라 복구에 사용되는 순차 로그다. 둘은 같은 객체가 아니다.

가득 찬 memtable을 파일로 내보내는 flush와 기존 파일들을 합치는 compaction은 서로 다른 일이다. flush했다고 모든 옛 버전이 모든 계층에서 사라지는 것은 아니다. 아래에서는 키·값·전역 순서가 명시되어 최신 읽기를 종이로 추적한다.

겹치는 파일과 정렬된 범위

레벨 방식에서 L0에는 flush된 파일들이 있고 키 범위가 겹칠 수 있다. L1 이후의 각 레벨은 일반적으로 키 범위로 나뉜 하나의 정렬 run이다. 모든 LSM 구현이 같은 레벨 정책을 쓰는 것은 아니며 이 설명은 레벨 병합 방식의 큰 틀이다.

찾는 키가 여러 파일에 있으면 현재 조회는 유효한 최신 버전이 결정한다. 최신 tombstone은 옛 값을 반환하지 못하게 한다. 파일 범위와 인덱스는 후보를 줄이지만 오래된 후보에서 값이 있다는 것만으로 바로 정답이 되지는 않는다.

병합으로 읽기와 공간 비용 조절하기

병합은 관련 정렬 파일을 함께 읽어 순서대로 새 파일을 만든다. 레벨 방식에서는 다음 레벨의 겹치는 범위도 병합 대상으로 고려한다. 중복·옛 버전을 제거할 수 있지만 스냅샷이나 정리 밖의 옛 값에 필요한 삭제 표식까지 무조건 버리지는 않는다.

파일을 설치한 메타데이터와 기존 독자의 수명도 관리한다. 새 파일의 작성과 이전 파일 삭제를 같은 순간의 단순 덮어쓰기라고 보지 말자. 계층 수나 겹침이 읽기 비용에 영향을 주고 이를 줄이는 병합에는 쓰기 비용이 든다.

중간 과정을 따라가는 예제

memtable에는 (A,9,seq5),(C,delete,seq6)이 있다. L0에는 (A,7,seq3),(B,8,seq4), L1에는 (A,2,seq1),(C,6,seq2)가 있다. 모두 현재 조회 대상이며 스냅샷은 없다. A/B/C를 조회하고 전체 관련 파일·메모리를 한 정렬 run으로 합칠 때 남길 현재 기록을 구하라.

  1. A 후보 seq1/3/5 중 가장 큰5의 값9를 고른다. B는 seq4의 값8이다.

  2. C는 seq2의 값6보다 seq6 삭제가 최신이므로 없음이다.

  3. 모든 관련 버전을 포함한 전체 병합과 과거 의존성 없음이라는 가정에서는 정렬 출력 A=9, B=8만 남길 수 있다.

A=9, B=8, C 없음이다. 전체 병합 출력은 A/B 두 키이며 seq가 아닌 키 순서로 정렬한다.

종이와 본문으로 직접 해보기

memtable만 새 SST로 flush하고 기존 파일은 그대로 둔다면 새 파일 내용은? C 삭제 표식을 빼도 되는가? 이어 snapshot seq4 조회의 A와 C도 구하라.

힌트 보기

flush 범위는 모든 옛 파일이 아니다. 스냅샷은 지정 seq 이하의 최신 버전을 고른다.

풀이 보기

새 SST에는 A=9(seq5), C삭제(seq6)가 들어가며 키 순서 A/C다. C=6이 L1에 남아서 표식을 빼면 안 된다. snapshot seq4에서는 A seq3의7, C seq2의6이다. 전체 최신 상태만으로 이 과거 조회를 대체할 수 없다.

오해와 반례

flush는 전체 병합과 같아서 최신 값만 있으면 모든 옛 파일을 삭제해도 된다.

flush는 특정 메모리 내용을 내보내는 작업이다. L1의 C=6과 snapshot seq4 같은 의존성이 있으면 최신 출력만으로 충분하지 않다. WAL의 복구 필요성과 파일 설치 조건도 별도로 확인한다.

자기점검

답과 이유 보기

아니다. seq5의9다.

전역 순서로 최신 유효 버전을 고른다.

L0 파일들의 키 범위는 반드시 겹치지 않는가?

답과 이유 보기

레벨 방식에서도 겹칠 수 있다.

flush로 나온 파일은 여러 시점의 같은 키를 포함할 수 있다.

snapshot seq4에서 최신 전체 삭제 seq6을 적용하는가?

답과 이유 보기

아니다. 이 모형에서는 seq4 이하만 본다.

C seq2 값6은 해당 과거 시점에 아직 삭제되지 않았다.

한 단계 더

새 memtable에 (B,10,seq7)을 추가하면 현재 B=10이고 snapshot seq4에서는 여전히 B=8이다. 파일이 어느 계층에 있느냐만 보지 말고 버전의 가시성 조건을 먼저 판단하라.

바이트 압축과 버전 정리는 다른 일

바이트 압축은 데이터 표현을 더 적은 바이트로 저장하는 기법이다. compaction은 파일·버전을 병합해 구조를 정리하는 작업이다. 옛 기록을 남긴 채 압축만 할 수 있고 파일을 병합해도 바이트 압축을 쓰지 않을 수 있다.

RocksDB SST에서는 데이터와 인덱스 블록에 압축을 적용할 수 있으며 필터 블록은 압축하지 않는다. 압축은 공간과 I/O를 줄일 수 있지만 압축·복원에 CPU 비용이 든다. 아래 압축 크기는 주어진 가상 수치이며 실제 파일을 압축해서 얻은 측정값이 아니다.

없는 키를 먼저 배제하는 비트 배열

표준 Bloom filter는 처음0인 배열에 삽입할 키의 여러 해시 위치를1로 만든다. 조회 시 같은 위치 중 하나라도0이면 그 집합에 없다고 말할 수 있다. 모두1이면 있을 수 있다는 뜻이며 원래 데이터에서 다시 확인한다.

정상적으로 삽입한 집합·같은 해시·비트 손상 없음이라는 조건에서 거짓 음성은 없다. 서로 다른 키가 비트를 공유해 거짓 양성은 생긴다. 기본 필터에서 삭제하려고 한 비트를0으로 만들면 다른 키가 공유한 표시도 지워질 수 있다. SST를 병합할 때는 새 집합에 맞는 필터를 다시 만드는 방식도 사용된다.

증폭은 무엇을 얼마나 세는가

쓰기 증폭은 정한 기간·계층에서 기록한 바이트를 애플리케이션 논리 쓰기 바이트로 나눈 값으로 정의할 수 있다. WAL을 포함하는지, 압축 전후인지, 장치 내부 쓰기를 세는지 반드시 적는다. 정의가 다른 숫자를 그대로 비교하면 안 된다.

공간 증폭은 정한 시점의 물리 공간을 필요한 논리 데이터 크기로 나눌 수 있다. 읽기 증폭도 후보 파일·실제 데이터 블록·바이트 등 측정 단위를 정해야 한다. 아래는 작은 후보 파일과 바이트 모델을 선언한다. Bloom filter가 줄이는 것은 불필요한 후보 데이터 확인이며 실제 키의 존재 여부를 대신 결정하지 않는다.

중간 과정을 따라가는 예제

8비트 배열의 위치는0~7이다. 자체 고정 해시 표에서 A는{1,4}, B는{4,6}, 없는 키 C는{1,6}, 없는 키 D는{2,4}에 대응한다. A/B만 넣고 네 키를 검사하라. 한편 논리 쓰기1000바이트, WAL1000, 최초SST1000, 병합출력2000이면 WAL 포함·제외 쓰기 증폭은?

  1. 삽입 뒤1인 비트 위치는{1,4,6}이고 나머지는0이다. A/B의 두 비트는 모두1이므로 실제 데이터 확인 후 있음이다.

  2. C도 두 비트가1이어서 있을 수 있다고 나오지만 실제 집합에는 없다. D는 위치2가0이므로 없다.

  3. WAL 포함 물리 쓰기는1000+1000+2000=4000이고 논리1000으로 나누면4다. WAL 제외는3000/1000=3이다. 압축·헤더·장치 내부 쓰기는 제외한다.

C가 거짓 양성이고 D는 확실히 없음이다. 선언한 바이트 범위의 쓰기 증폭은 WAL 포함4, 제외3이다.

힌트 보기

B도4를 사용한다. 거짓 양성률의 분모는 없는 키 조회 수다. 전체 파일에 메타정보도 더한다.

풀이 보기

B의4가0이 되어 실제 있는 B를 없다고 할 수 있는 오류가 생긴다. 원래 배열에서 없는 두 키 중 C 하나만 양성이므로 이 두 질의의 관측률은1/2이다. 전체600바이트이고600/1100=6/11이다. 데이터 블록만의1/2 압축비와 전체 비율을 구별한다.

오해와 반례

Bloom filter가 양성이면 키가 확실히 있고 압축을 켜면 모든 증폭이 자동으로 절반이다.

없는 C도 양성이다. 실제 키를 확인해야 한다. 필터·메타정보는 가정대로 그대로100바이트이고 병합 빈도·WAL·CPU 비용도 압축비 한 개로 결정되지 않는다.

한 단계 더

없는 키를 찾을 때 후보 파일3개가 있고 각 필터 응답이 없음/가능/없음이라고 주어진다면 데이터 파일 확인은1개다. 캐시된 필터 읽기 자체·인덱스·메모리 비용은0이라는 가정을 별도로 둔다. 필터가 없을 때 후보3개 대비1/3이지만 실제 장치 I/O가 반드시 정확히1/3이라는 측정 결과는 아니다.
