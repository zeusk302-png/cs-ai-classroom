소단원 3.1

고정·가변길이 레코드

학생 이름이 짧거나 길어져도 파일의 다음 학생 위치를 바로 알 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 레코드는 한 자료 항목의 여러 필드 묶음이다. 필드는 식별자·상태·이름 등 각 값이고 스키마는 타입과 배열 규칙을 정한다.

  • 여기서 길이는 바이트 수다. 이름 8 바이트 제한이 여덟 글자 제한이라는 뜻은 아니며 문자 인코딩은 다음 소단원에서 확인한다.

  • floor(a/b)는 나머지를 버린 몫이다. 페이지 안에 레코드가 나뉘어 걸치지 않는다는 가정을 두면 수용량 계산에 이 몫을 쓴다.

학습 목표

  • 고정 길이의 위치 계산과 여유 공간을 설명한다.

  • 가변 길이의 경계 메타데이터 비용을 포함한다.

  • NULL·빈 값·예약 공간과 포맷 조건을 구분한다.

평균 길이로 두 개가 들어간다고 해도 긴 두 개가 함께 들어갈까?

자체 페이지는 64바이트, 헤더는 8바이트, 레코드별 슬롯은 4바이트다. 자료 길이가 8바이트인 짧은 레코드 두 개와 32바이트인 긴 레코드 두 개가 있다. 네 자료 길이의 평균은 20바이트다. 평균과 슬롯을 더한 24바이트로 계산하면 페이지당 floor(56/24) = 2개다. 그러나 긴 두 개의 실제 공간은 2 × (32 + 4) = 72바이트여서 헤더를 제외한 56바이트를 넘는다.

짧은 레코드와 긴 레코드를 한 페이지씩 짝지으면 각 페이지 사용량은 8 + 4 + 4 + 8 + 32 = 56바이트라 네 개를 두 페이지에 담는다. 반면 길이 8,8,32,32 순서로 현재 페이지에 최대한 넣으면 첫 페이지는 짧은 두 개로 32바이트를 사용한다. 남은 32바이트에는 다음 긴 레코드의 자료 32와 슬롯 4를 합한 36바이트가 들어가지 않는다. 두 번째 페이지에는 긴 레코드 하나가 들어가지만 다음 긴 레코드를 더하면 80바이트로 넘치므로 세 번째 페이지를 연다. 이 비교는 레코드를 쪼개지 않고 앞 페이지에 남은 공간으로 다시 돌아가지 않는 순차 포장 정책을 정한 것이다. 평균 길이는 입력의 전체 요약이며 배치 순서와 특정 페이지의 수용 보장이 아니다.

별도 고정 칸 모형에서는 같은 64바이트 페이지와 8바이트 헤더에 자료 칸 하나가 7바이트이고 슬롯은 없다. 점유 상태를 칸당 한 비트로 기록하는 bitmap은 ceil(n/8)바이트가 필요하다. 최대 칸 수는 7n + ceil(n/8) ≤ 56을 만족해야 한다. n = 8이면 56 + 1 = 57로 넘치고 n = 7이면 49 + 1 = 50으로 들어간다. 점유 비트도 저장 공간을 차지한다. 실제 DB의 표준 형식을 구현한 계산이 아니다.

모든 칸의 크기가 같은 모형

고정 길이 레코드는 같은 포맷의 각 항목이 같은 바이트 수를 차지한다. id4 바이트, 상태 1 바이트, 이름 예약 8 바이트로 정한 자체 포맷이면 길이 R=13 이다. 이름이 2 바이트라도 칸은 8 바이트를 차지하고 남은 6 바이트는 지정된 padding 규칙으로 채운다. 별도 정렬 패딩·null bitmap·길이표를 넣으면 R도 바뀌므로 “정수는 항상 4, 구조체는 필드합” 같은 기기 독립 결론은 내리지 않는다.

파일의 자료 시작 위치 H와 0 부터 센 레코드 번호 i가 알려지고 모두 연속 배치라면 시작 offset=H+iR다. 세 번째는 i=2 이지 3 이 아니다. 삭제로 빈 자리를 허용하면 i는 살아 있는 항목 순서가 아니라 물리 칸 번호일 수 있다. 첫 항목을 삭제했다고 세 번째 칸이 두 번째 칸으로 자동 이동하는 것은 아니며 packed/unpacked 정책을 정해야 한다. 일정 칸의 사물함 비유는 접근 계산을 돕지만 살아 있는 자료 수와 총 칸 수를 혼동할 수 있다.

내용 길이만큼 저장하려면 경계가 필요하다

가변 길이는 이름 등 필드의 실제 길이에 따라 레코드 크기가 달라질 수 있다. 순서대로 나열하기만 하면 다음 항목 경계를 모르므로 전체 길이, 필드별 길이, offset 목록 또는 구분자와 escape 같은 규칙이 필요하다. 여기서는 id4, 상태 1, 이름 바이트 길이 1, 실제 이름 L바이트로 R=6+L을 정한다. 한 바이트 길이는 0..255 만 표현하므로 더 긴 이름은 거부하거나 포맷을 바꿔야 한다.

필드별 offset을 넣는 다른 설계는 필요한 가변 필드 시작점을 더 빨리 찾는 대신 메타데이터를 저장한다. 빈 문자열의 길이 0 과 값 없음(NULL)은 별도 상태 비트로 구분할 수 있고, 구분 비트를 추가했다면 크기 계산에도 넣는다. 같은 내용이라도 메타데이터를 생략한 형식과 포함한 형식의 수용량은 다르다. 가변 길이가 언제나 작거나 언제나 빠른 것이 아니라 실제 분포와 경계 정보 비용에 따라 달라진다.

페이지 수용량에는 모든 비용을 넣는다

크기 P인 가상 페이지에 헤더 H, 항목당 슬롯 s, 고정 레코드 R이 있으면 n(R+s)+H<=P를 만족해야 하며 최대 n=floor((P-H)/(R+s))이다. 슬롯 없는 연속 포맷이면 s=0 이지만 해당 포맷에서 주소 안정성·삭제를 어떻게 처리하는지 별도로 봐야 한다. 가변 레코드는 각각 R_i를 합쳐 H+ns+sum R_i<=P로 검사한다. 평균 길이로 구한 값은 특정 페이지에 긴 항목들이 모일 때의 보장이 아니다.

실제 DB는 정렬·페이지 특수 영역·압축·큰 값의 외부 저장을 사용할 수 있다. 이 단원 예제는 레코드가 페이지를 가로지르지 않고 추가 패딩도 없다는 종이 모형이다. 실제 파일 크기와 이 수치가 같다고 주장하지 않는다. 자료 해석의 형식, 페이지 안 배치, 파일의 여러 페이지 조직은 서로 연결되지만 다른 층이므로 문제마다 어느 층의 헤더를 세는지 먼저 적는다.

중간 과정을 따라가는 예제

P=64,H=8,슬롯 s=4,추가 패딩 없이 레코드는 페이지 안에만 둔다. 고정 형식 R=13 인 경우 최대 개수를 구하라. 가변 형식 R=6+L로 이름 바이트 길이가 2,5,3 인 세 레코드를 넣을 때 크기와 남은 공간을 구하라.

  1. 고정은 한 항목에 13+4=17 바이트다. (64-8)/17=56/17 의 몫 3 이며 네 항목은 68+8=76 으로 넘친다.

  2. 고정 세 항목의 사용량은 헤더 8+슬롯 12+자료 39=59 이며 남은 5 바이트다.

  3. 가변 세 레코드 길이는 8,11,9 이며 합 28 이다. 이름 길이 인수는 이미 바이트 수이므로 글자 수를 다시 대입하지 않는다.

  4. 가변 사용량은 8+12+28=48, 남은 16 이다. 이 세 입력에서는 고정보다 11 바이트 덜 쓰지만 모든 길이 분포에서 그렇다는 뜻은 아니다.

고정 최대 3 개/남은 5 바이트, 주어진 가변 3 개/남은 16 바이트다. 메타데이터와 실제 길이를 함께 합했다.

별도 7바이트 고정 칸에서 bitmap까지 포함한 최대 칸 수는?

  2. 7칸은 자료 49와 bitmap 1로 50바이트다. 칸 수가 증가하면 필요한 공간은 감소하지 않는다.

오해와 반례

가변 길이는 고정 길이보다 무조건 공간을 적게 쓰고 모든 항목의 위치도 곱셈으로 구할 수 있다.

고정 이름 예약 8 바이트와 가변 길이표 1 바이트를 비교하면 이름 8 바이트를 가변으로 저장할 때 오히려 1 바이트가 더 든다. 가변 레코드 순서 i까지 직접 찾아가려면 앞 길이 합 또는 디렉터리 정보가 필요하고 iR 곱셈만 쓸 수 없다. 속도·공간의 조건을 분리한다.

힌트 1

첫 페이지의 실제 여유와 다음 긴 레코드의 자료·슬롯 비용을 비교한다.

힌트 2

첫 페이지를 떠난 뒤에는 그 페이지로 되돌아가지 않는다.

소단원 3.2

필드 인코딩과 직렬화

같은 바이트를 다른 컴퓨터가 읽으면 왜 다른 숫자나 이름으로 보일까?

준비 개념과 학습 목표

준비 개념

  • 직렬화는 구조화한 값을 정한 바이트나 텍스트 형식으로 바꾸는 일이고 역직렬화는 규칙에 따라 읽는 일이다. 변환 규칙 없이 메모리를 복사하는 것과 구분한다.

  • 16 진수 한 자리는 4 비트다. 한 바이트 0x02 는 2,0x01 은 1 이고 두 바이트 큰 자리 우선이면 0x0201=2×256+1=513 이다.

  • UTF-8 은 유니코드 코드포인트를 1..4 바이트로 표현한다. 코드포인트 수·사용자가 보는 글자 수·바이트 수는 일반적으로 같은 개념이 아니다.

학습 목표

  • 타입·크기·바이트 순서·문자 인코딩을 포맷에 명시한다.

  • 길이표를 바탕으로 자료 경계를 검증한다.

  • NULL·버전·텍스트 형식의 의미 규칙을 구분한다.

길이 검사에 통과한 바이트가 반드시 올바른 이름일까?

앞 본문의 version1 형식은 version 1바이트, id 2바이트 big endian, present 1바이트, nameLength 1바이트, 이름 UTF-8 순이다. 자체 입력 01 00 01 01 02 C0 80은 선언한 이름 길이 2와 실제 이름 바이트 수 2가 맞는다. 하지만 C0 80은 유효한 UTF-8이 아니다. 길이 경계 검사와 문자 해석 검사는 다른 단계다. 이 입력을 NUL의 정상 표현으로 받지 않는다.

별도 입력 01 00 01 00 01 41은 이름 바이트 A가 유효하고 길이도 1이다. 그러나 present = 0이면 nameLength = 0이어야 한다는 자체 형식 계약을 위반한다. 길이·UTF-8·존재 상태·version·id 범위를 각각 검사해야 한다. 구문 하나에 통과한 사실을 완전한 응용 값으로 인정한 사실로 바꾸지 않는다.

경계 산술도 폭을 확인한다. 자체 8비트 unsigned 산술에서 pos = 250, L = 10, 끝 N = 255를 계산하면 pos + L의 수학적 값 260이 모듈로 256에 따라 4로 돌아간다. 4 ≤ 255만 검사하면 잘못 통과한다. 먼저 0 ≤ pos ≤ N을 확인하고 L ≤ N − pos를 비교하면 10 ≤ 5가 거짓이라 거부한다. 실제 파서나 C 구현을 실행한 결과가 아닌 지정한 unsigned 모형의 반례다.

숫자의 값과 메모리 배치는 다르다

정수 513 을 2 바이트 unsigned로 저장할 때 큰 자리 우선(big endian)은 02 01, 작은 자리 우선(little endian)은 01 02 다. 받는 쪽이 순서를 반대로 해석하면 02 01 을 1×256+2=258 로 읽는다. “정수”라는 타입 이름만으로 부호·폭·순서가 결정되지 않는다. 범위를 0..65535 로 정하면 음수와 65536 은 이 필드에 그대로 넣을 수 없으며 거부나 다른 표현을 정해야 한다.

C 구조체를 그대로 파일에 복사하면 기기별 크기·padding·정렬·포인터·바이트 순서의 문제가 남는다. 주소 포인터는 다른 실행의 같은 자료를 뜻하지 않고 padding은 논리적 필드값이 아니다. 포맷은 필드별 크기와 해석, 순서와 길이를 정하고 범위를 검사해야 한다. 이 단원의 자체 바이트 모형은 실행한 C 구조체 덤프가 아니며 숫자 손계산으로 만든 예상 배열이다.

문자를 바이트 경계에 맞게 읽기

UTF-8 에서 ASCII A(U+0041)는 41 한 바이트다. 가(U+AC00)는 3 바이트 형태 1110xxxx 10xxxxxx 10xxxxxx로 코드포인트 비트를 분배하여 EA B0 80 이 된다. 따라서 A가의 코드포인트는 2 개지만 길이는 4 바이트다. 길이표에는 여기서 반드시 인코딩한 바이트 수를 쓴다. 3 바이트 제한에 맞춘다고 A가의 앞 3 바이트 41 EA B0 만 잘라내면 마지막 문자가 불완전하므로 그대로 유효 문자열로 볼 수 없다.

유효 UTF-8 검사와 애플리케이션 문자열 정책은 구별된다. 잘못된 시퀀스, 과도한 길이, 필드 경계 침범을 확인하고, 정상 문자열이어도 이름으로 허용하는지의 의미 규칙은 따로 정한다. 빈 문자열은 유효 길이 0 값이며 NULL은 값 부재다. 단순 ASCII 예제에서 둘을 합쳐 설명하면 한국어·중국어·일본어처럼 바이트 수가 다른 자료에서 오류가 드러난다. 문자 인코딩을 지정해도 날짜 단위·시간대·금액 단위 같은 의미는 자동으로 정해지지 않는다.

형식 버전과 의미의 계약

자체 바이너리 포맷을 version1 바이트,id2 바이트 big endian,present1 바이트,nameLength1 바이트,UTF-8 이름 순으로 정하자. present=0 이면 nameLength=0 이어야 하며 이름은 없음이다. present=1 이면 길이 0 도 허용해 빈 이름을 나타낸다. version이 알 수 없는 값이면 이 규칙으로 추측해 파싱하지 않는다. 길이가 남은 자료보다 길면 잘린 레코드로 보고 완전한 값으로 해석하지 않는다. 길이가 적당해도 아직 UTF-8 유효성 검사와 응용 검사가 남는다.

JSON 같은 텍스트 직렬화는 문자열·숫자·객체·배열 등 구문을 정한다. 넓게 교환하는 JSON은 UTF-8 을 사용하며 객체 이름을 중복시키면 구현마다 처리 차이가 생길 수 있다. 그러나 JSON이라는 이름만으로 id 범위, 이름의 필수성, 날짜 형식, 버전 호환이 정해지지는 않는다. 바이트 표현이 서로 달라도 같은 값일 수 있고 객체 멤버 순서에 의미를 의존하지 않는 규칙이 필요하다. 이 자료는 JSON이 모든 언어의 임의 정밀 숫자를 그대로 보존한다고 주장하지 않는다.

소단원 3.3

슬롯 페이지와 삭제 표시

페이지 안의 레코드를 이동해도 밖에서 같은 자료를 찾아가게 하려면 무엇을 고정해야 할까?

준비 개념과 학습 목표

준비 개념

  • 페이지는 정한 크기의 자료 묶음이며 여기서는 byte offset을 0 부터 센다. [a,b)의 길이는 b-a이고 경계 b는 포함하지 않는다.

  • 슬롯은 레코드의 시작 위치·길이·상태를 저장하는 디렉터리 항목이다. 레코드의 내용 자체와 슬롯 항목의 공간을 함께 센다.

  • 삭제 표시는 논리적으로 읽지 않는 상태이고 공간 정리는 배치를 바꾸는 작업이다. 삭제만으로 원래 바이트가 덮어써졌다고 생각하지 않는다.

학습 목표

  • 슬롯 번호를 통해 위치와 내용 주소를 분리한다.

  • 삭제 후 전체 여유와 연속 여유를 구별한다.

  • 압축 정리·번호 재사용·보안 삭제의 한계를 설명한다.

각 슬롯이 페이지 안에 있어도 레코드끼리 겹칠 수 있을까?

자체 120바이트 페이지에서 헤더와 슬롯 영역은 [0,20)이다. live 슬롯 A는 [80,100), B는 [90,110)을 가리키고 길이는 각각 20바이트다. 둘 다 페이지 안에 있고 관리 영역과도 겹치지 않는다. 그런데 두 자료는 [90,100)의 10바이트를 함께 사용한다. 개별 범위 검사만으로는 자료끼리의 겹침을 발견하지 못한다.

슬롯 길이 합은 40바이트이고 관리 영역 20을 더해도 60바이트라 페이지 크기 120보다 작다. 이 총량 검사를 통과해도 서로 독립된 레코드 A와 B를 보존하는 올바른 배치가 아니다. 자료 범위 안에서 B의 값을 바꾸면 A의 일부도 바뀔 수 있다. 이 모형에서는 의도적인 데이터 공유를 허용하지 않으므로 live 구간은 서로 겹치지 않아야 한다.

B를 [100,120)으로 수정하고 현재 슬롯도 함께 갱신하면 A와 B는 경계 100만 맞닿는다. 반열린 구간에서는 그 경계가 A에 포함되지 않아 두 구간은 겹치지 않는다. 관리 영역 20·자료 40·빈 구간 [20,80)의 60을 합하면 120이다. 이런 정상 상태 검사는 이동 도중 독자·로그·전원 장애의 안전성이나 보안 삭제를 시험한 결과가 아니다. 삭제된 바이트나 오래된 슬롯 참조의 수명은 따로 관리한다.

먼저 확인할 개념
  • 슬롯·반열린 구간·불변식

    범위·서로 겹치지 않음·관리 영역과 비용 합을 함께 확인한다.

  • 레코드 위치와 ID 수명

    현재 위치와 옛 참조의 유효 수명을 구별한다.

두 방향으로 자라는 페이지 모형

슬롯 페이지는 고정 헤더와 슬롯 목록을 한쪽에, 가변 레코드를 반대쪽에 두고 가운데 빈 구간을 관리할 수 있다. 이 소단원의 자체 모형은 헤더 8 바이트, 슬롯 하나 4 바이트로 위치·길이·live 상태를 표현할 수 있다고 가정하고 추가 패딩이 없다. 슬롯은 0 부터 번호를 매긴다. 아래 크기는 PostgreSQL의 실제 헤더 24 바이트 등을 복제한 것이 아니며 어느 DB에서도 같은 숫자라는 뜻이 아니다.

외부 참조를 (페이지번호,슬롯번호)로 만들면 레코드가 페이지 안에서 이동해도 슬롯의 위치·길이 정보를 갱신해 다시 찾을 수 있다. 다만 슬롯이 유지되는 동안의 주소 간접화 성질이다. 실제 PostgreSQL CTID가 영구 업무 식별자라는 뜻은 아니며 버전 갱신·페이지 이동·슬롯 해제 및 재사용은 추가 규칙이 필요하다. 도서관 검색표의 책 위치를 고치는 비유에서는 검색표 번호를 다른 책에 재사용할 때의 혼동도 설명해야 한다.

삭제와 조각난 여유 공간

가상 삭제는 해당 슬롯을 dead로 표시하고 조회에서 제외한다. 즉시 자료를 이동하지 않는 정책이면 삭제된 바이트 구간은 빈 조각이 되지만 가운데 연속 여유는 그대로다. 전체 가용 바이트가 새 레코드보다 많아도 하나의 연속 구간이 작으면 그 자리에는 삽입할 수 없다. 슬롯이 새로 필요하면 자료 길이에 슬롯 비용도 더해야 한다. 살아 있는 레코드 수와 유지하는 슬롯 수는 삭제 뒤 같지 않을 수 있다.

페이지 정리(compaction)는 살아 있는 내용을 한쪽으로 모아 빈 조각을 큰 연속 구간으로 합치고 움직인 레코드의 슬롯 offset을 갱신한다. 이 단원은 dead 슬롯을 보존하고 새 삽입마다 끝에 슬롯을 추가하는 정책으로 계산한다. dead 슬롯 재사용 정책을 택하면 슬롯 공간 계산과 외부 참조 안전성도 바뀐다. 재사용된 번호를 오래된 참조가 잘못 읽는 문제는 세대 번호나 유효성 조건 등 별도의 설계로 다뤄야 한다.

논리적 삭제와 실제 시스템의 범위

삭제 표시를 지웠다고 이전 내용이 물리 바이트에서 사라지는 것은 아니다. 슬롯만 dead로 바꾼 직후에는 원래 레코드 바이트가 그대로 남는 것이 직접 반례다. compaction도 새 배치로 복사했을 뿐 페이지의 옛 영역·로그·백업·저장장치의 이전 버전에 대한 보안 삭제를 증명하지 않는다. 이 단원은 자료 배치와 참조를 설명하며 실제 포렌식 회수나 장치 삭제 실험을 수행하지 않는다.

실제 DB의 동시 읽기·트랜잭션·MVCC·로그 복구는 언제 자료를 보이지 않게 하고 언제 공간을 회수할지에 영향을 준다. 단순 dead 상태 하나를 모든 DB의 삭제 구현과 같게 놓으면 이전 버전을 읽는 트랜잭션을 설명할 수 없다. 여기서는 단일 순차 모형에서 레코드 조회를 제외하고 공간을 정리하는 논리만 공부한다. 파일 전체의 페이지 재배치, 레코드가 페이지보다 큰 경우, 원자적 갱신은 이후 단원과 연결한다.

  3. 정리하여 A[108,120),C[90,108)로 놓고 슬롯 2 의 위치를 90 으로 갱신한다. 슬롯 1 은 dead로 유지한다. 연속 여유[20,90)=70 이다.

풀이와 답 확인
