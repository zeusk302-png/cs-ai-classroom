소단원 12.1

역색인·포스팅 리스트

검색어가 나온 문서를 찾으려면 매번 모든 파일을 읽어야 할까?

준비 개념과 학습 목표

준비 개념

  • 문서와 고유 번호

  • 집합과 AND·OR

  • 정렬

학습 목표

  • 문서에서 단어로 보는 방향과 역색인의 방향을 구별한다.

  • 포스팅 리스트와 문서 빈도를 구성한다.

  • 단어 존재와 위치·순위·원문 저장을 구별한다.

찾는 방향을 뒤집는다

문서 저장은 보통 문서 번호에서 내용을 찾는다. 역색인은 단어에서 그 단어가 나타난 문서 번호 목록으로 간다. 사전에서 단어의 목록 위치와 길이 등을 찾고 포스팅 리스트를 조회하면 검색 때 모든 원문을 다시 읽는 일을 줄일 수 있다.

docID는 해당 색인 안의 문서 식별자다. 운영체제 inode나 파일 오프셋, 사용자가 보는 URL과 자동으로 같은 번호가 아니다. 실제 시스템에서 색인 재구성이나 세그먼트 병합이 내부 docID를 바꿀 수 있으므로 외부 식별자와 연결할 정책이 필요하다.

같은 규칙으로 단어를 만든다

본문에서 검색 단위를 얻는 토큰화와 표기를 맞추는 정규화를 먼저 정한다. 이 예제는 이미 공백으로 분리한 한국어 단어를 그대로 사용한다. 실제 한국어 조사·복합어, 영어 대소문자·구두점은 더 정교한 처리가 필요하다.

같은 문서에서 같은 단어가 여러 번 나오더라도 단순 존재 목록에는 docID를 한 번만 넣는다. 문서 빈도 df는 단어가 나온 문서 수이며 전체 발생 횟수와 다르다. 빈도와 위치가 필요한 검색은 추가 정보를 저장한다.

존재 검색과 문장 검색은 다르다

AND는 양쪽 목록의 교집합, OR는 합집합으로 문서를 선택할 수 있다. 각 목록은 공통 순서의 docID로 정렬해야 두 포인터 처리에 사용할 수 있다. 결과의 docID 순서가 관련성 순위와 같은 것은 아니다.

단어가 둘 다 있다는 정보만으로 바로 옆 순서의 구문이 있는지 확인할 수 없다. 구문 검색에는 위치 정보나 원문 확인이 필요하다. 삭제·업데이트된 문서의 표시와 원문 버전도 맞춰야 검색 목록과 사용자 내용이 어긋나지 않는다.

중간 과정을 따라가는 예제

자체 문서 5는 “자료 구조”, 130은 “검색”, 131은 “자료 검색”, 400은 “파일 검색”이다. 공백으로 분리한 단어의 존재 역색인과 자료 AND 검색, 자료 OR 검색을 구하라.

  1. 자료의 목록은 [5, 131], 구조는 [5], 검색은 [130, 131, 400], 파일은 [400]이다.

  2. 자료의 df는 2, 검색의 df는 3이다. 문서 번호가 400까지 있다고 문서가 400개인 것은 아니며 이 컬렉션에는 네 문서가 있다.

  3. 자료 AND 검색의 결과는 [131]이고 OR의 결과는 [5, 130, 131, 400]이다. 목록 번호로 원문 저장 위치를 따로 찾아 내용을 표시한다.

단어 → 정렬된 docID 목록을 구성한다. AND는 문서 131만 선택하고 OR는 네 문서 모두 선택한다.

소단원 12.2

압축과 교집합

문서 번호를 압축하면 정렬 목록의 교집합도 그대로 구할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 정렬된 정수 목록

  • 2진수와 바이트

  • 누적합

학습 목표

  • 차이 저장과 가변 바이트를 해독한다.

  • 정렬된 두 목록의 교집합을 추적한다.

  • 압축 공간과 해독·탐색 비용을 구별한다.

번호 대신 차이를 저장한다

정렬된 docID 목록의 첫 값을 저장하고 이후에는 직전 번호와의 차이를 저장한다. [5, 130, 131, 400]은 [5, 125, 1, 269]로 된다. 첫 docID와 누적합으로 원래 목록을 정확히 복원할 수 있다.

차이가 작아도 모든 값을 같은 4바이트 정수로 저장하면 공간이 자동 줄지 않는다. 작은 값은 짧게 쓰는 가변 길이 부호가 필요하다. 드문 단어의 큰 간격은 길게 저장될 수 있고 사전·목록 길이·블록 정보도 전체 저장 비용에 더해진다.

가변 바이트의 규약을 명시한다

여기서는 한 바이트의 아래 7비트를 값의 조각으로 쓰고 마지막 바이트의 상위 비트를 1로 한다. 높은 자리 조각부터 기록한다. 다른 varint 방식은 상위 비트나 자리 순서가 다르므로 형식 이름만 보고 섞어 읽지 않는다.

269 = 2 × 128 + 13이므로 조각 2와 13을 쓰고 마지막 13에 128을 더해 [2, 141]을 저장한다. 인코딩 경계가 있어야 다음 값을 분리한다. 마지막 표시 없이 끝난 스트림은 잘린 입력으로 거부한다. 이 구현은 교육용이며 손상 탐지용 체크섬·버전 헤더를 제공하지 않는다.

복원한 순서로 두 포인터를 움직인다

두 정렬·중복 없는 목록에서 현재 번호가 같으면 결과에 넣고 둘 다 전진한다. 다르면 작은 번호 쪽만 전진한다. 작은 번호는 반대쪽의 현재 번호나 이후 큰 번호와 같아질 수 없으므로 버려도 된다. 한 목록이 끝나면 교집합을 종료한다.

길이가 m과 n이면 포인터가 앞으로만 가서 이 방식의 비교 시간은 O(m + n)이다. 이 결과가 디스크 해독·목록 조회·모든 검색 질의의 비용까지 없앤다는 뜻은 아니다. 압축 목록의 임의 지점부터 시작하려면 누적 docID와 바이트 위치 등 건너뛰기 정보를 추가로 둘 수 있다.

표준 라이브러리로 작은 형식 확인하기

아래 코드를 postings.py로 저장하고 python postings.py로 실행하면 자체 정수 목록의 차이 저장·복원·교집합을 확인한다. 파일이나 네트워크 입력을 읽지 않고 Python 표준 기능만 사용한다.

encode_number는 7비트씩 나누고 decode_numbers는 128배 누적한다. 실제로 큰 목록 전체를 한 번에 복원하지 않는 스트리밍 방식도 있지만 이 코드는 과정을 보이려고 전체를 복원한다. 압축 검색 엔진이나 속도 측정 구현이 아니다.

def encode_number(n):
    if not isinstance(n, int) or n < 0:
        raise ValueError("nonnegative integer required")
    parts = [n % 128]
    n //= 128
    while n:
        parts.insert(0, n % 128)
        n //= 128
    parts[-1] |= 128  # final byte has high bit 1
    return bytes(parts)

def decode_numbers(data):
    result = []
    value = 0
    pending = False
    for byte in data:
        value = 128 * value + (byte & 127)
        pending = True
        if byte & 128:
            result.append(value)
            value = 0
            pending = False
    if pending:
        raise ValueError("truncated number")
    return result

def intersect(a, b):
    # Inputs must be sorted and contain no duplicate IDs.
    i = j = 0
    result = []
    while i < len(a) and j < len(b):
        if a[i] == b[j]:
            result.append(a[i])
            i += 1
            j += 1
        elif a[i] < b[j]:
            i += 1
        else:
            j += 1
    return result

ids = [5, 130, 131, 400]
gaps = [ids[0]] + [ids[i] - ids[i - 1] for i in range(1, len(ids))]
data = b"".join(encode_number(n) for n in gaps)
restored = []
total = 0
for gap in decode_numbers(data):
    total += gap
    restored.append(total)
print(gaps)
print(list(data), len(data))
print(restored)
print(intersect(restored, [1, 5, 131, 300, 400]))

중간 과정을 따라가는 예제

코드의 A = [5, 130, 131, 400]을 차이와 가변 바이트로 저장하고 B = [1, 5, 131, 300, 400]과 교집합을 구하라. 32비트 고정 정수와 목록 본문 크기만 비교하라.

  1. 차이는 [5, 125, 1, 269]다. 가변 바이트는 [133, 253, 129, 2, 141]이며 다섯 바이트다.

  2. 누적 해독은 5 → 130 → 131 → 400이다. 고정 32비트 정수 네 개는 16바이트이므로 이 자체 목록 본문에서는 11바이트 감소다. 사전·헤더는 제외했다.

  3. 교집합 비교쌍은 (5,1), (5,5), (130,131), (131,131), (400,300), (400,400)이다. 일치 결과는 [5, 131, 400]이다.

  4. 예상 네 출력은 차이 목록, 바이트 목록과 길이 5, 복원 목록, 교집합이다. 압축률과 실행 시간이 항상 함께 좋아진다고 결론내리지 않는다.

가변 바이트 본문은 5바이트, 원래 목록은 정확히 복원된다. 교집합 결과는 [5, 131, 400]이다.

같은 고정 너비로 쓰면 저장량이 유지되고 큰 간격·메타데이터·해독 비용도 있다. 본문 5바이트 결과는 특정 네 번호와 형식의 계산이며 실제 속도나 모든 자료의 압축률 보장이 아니다.

소단원 12.3

텍스트·문서 저장 배치

검색으로 얻은 docID만 있으면 원문 바이트를 바로 표시할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • docID와 오프셋

  • UTF-8 바이트

  • 블록과 정렬

학습 목표

  • 색인과 문서 원문 저장의 역할을 나눈다.

  • 바이트 오프셋·길이·블록 범위를 계산한다.

  • 갱신과 압축 묶음이 검색 후 접근에 미치는 조건을 설명한다.

검색 목록과 표시할 원문을 연결한다

역색인의 포스팅은 검색 조건을 만족하는 문서 번호를 준다. 사용자에게 보여 줄 제목·본문·주소는 별도 저장 필드나 문서 저장소에서 찾아야 한다. docID → 원문 위치·길이의 대응표를 둘 수 있으며 실제 구조에서는 세그먼트와 버전도 필요하다.

색인에 위치나 빈도가 있다고 원문 서식과 원래 모든 문자를 복원할 수 있는 것은 아니다. 정규화하며 버린 정보와 색인하지 않은 내용이 있기 때문이다. 원문을 저장할지 원래 파일을 다시 읽을지, 접근 권한을 어떻게 적용할지 정해야 한다.

문자 개수와 파일 바이트를 나눈다

UTF-8에서는 문자마다 바이트 수가 다를 수 있다. 이 예제의 한글 음절은 각각 3바이트이고 공백은 1바이트다. “자료 구조”는 표시 문자 다섯 개지만 13바이트다. 일반적인 모든 Unicode 문자가 3바이트라는 규칙은 아니다.

파일 위치는 바이트 단위로 계산한다. 자체 배치는 원문 UTF-8 바이트를 구분자 없이 연결하고 대응표가 각 길이를 가진다. 실제 레코드 형식은 헤더·길이·체크섬·압축 등 추가 정보가 있어 이 단순 오프셋과 다르다.

묶음 저장과 갱신의 비용을 본다

문서를 압축 묶음으로 저장하면 같은 표현을 활용할 수 있지만 문서 하나를 얻기 위해 묶음 일부를 해독해야 할 수 있다. Lucene의 특정 저장 필드 형식은 문서 블록 데이터와 docID·디스크 위치의 별도 색인을 사용한다. 이 단원의 16바이트 무압축 모형은 실제 Lucene 형식이 아니다.

중간 문서를 길게 바꾸면 단순 연결 배치의 뒤쪽 오프셋이 달라진다. 별도 레코드·추가 기록·재작성·세그먼트 병합 등 여러 정책이 가능하다. 원문이 바뀌었는데 오래된 역색인이나 위치표를 쓰면 잘못된 검색과 표시가 생길 수 있으므로 일치하는 공개 버전을 정한다.

중간 과정을 따라가는 예제

첫 소단원의 문서를 docID 순서 5/130/131/400으로 구분자 없이 UTF-8 연결한다. 내용은 “자료 구조”/“검색”/“자료 검색”/“파일 검색”이다. 블록 16바이트, 시작 위치 0인 모형에서 길이·시작·걸치는 블록을 구하라.

  1. 각 바이트 길이는 13, 6, 13, 13이다. 시작은 0, 13, 19, 32이며 끝 다음 위치는 45다. docID 값과 시작 위치는 서로 다른 숫자다.

  2. 문서 5의 범위는 [0,13), 130은 [13,19), 131은 [19,32), 400은 [32,45)다. 끝 다음 위치는 해당 문서에 포함하지 않는다.

  3. 블록 번호는 바이트 위치를 16으로 나눈 몫이다. 문서 5는 블록 0, 130은 블록 0과 1, 131은 블록 1, 400은 블록 2에 걸친다.

  4. 문서 130은 문자 두 개여도 블록 경계를 넘는다. 원문 조회는 시작 13에서 여섯 바이트를 읽고 올바르게 UTF-8 해독한다. 블록 읽기의 실제 I/O 횟수는 캐시 등의 조건을 더 봐야 한다.

총 원문은 45바이트다. 문서 130의 시작 13·길이 6·두 블록 걸침은 문자 개수만으로 판단할 수 없다.

오해와 반례

검색용 토큰을 모두 저장했으므로 원문의 바이트와 서식도 항상 그대로 복원된다.

색인은 정규화·중복 병합·정보 제외를 할 수 있다. 원문 복원을 요구한다면 원본이나 저장 필드를 별도로 보존하고 그 버전과 docID 연결을 관리한다.
