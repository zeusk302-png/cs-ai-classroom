역색인·포스팅 리스트

검색어가 나온 문서를 찾으려면 매번 모든 파일을 읽어야 할까?

준비 개념과 학습 목표

준비 개념

  • 문서와 고유 번호

  • 집합과 AND·OR

  • 정렬

학습 목표

  • 문서에서 단어로 보는 방향과 역색인의 방향을 구별한다.

  • 포스팅 리스트와 문서 빈도를 구성한다.

  • 단어 존재와 위치·순위·원문 저장을 구별한다.

같은 두 단어가 있는데 순서가 다르면 구문 검색에서도 같은 문서일까?

기본 네 문서에서 131을 “자료 자료 검색”으로 바꾸고 문서 200 “검색 후 자료”를 추가한다. 위치는 공백 토큰의 1부터 시작하는 순번이다. 자료의 문서 목록은 [5,131,200], 검색은 [130,131,200,400]이다. 문서 131에서 자료는 위치 1,2이고 검색은 3이다. 문서 200에서는 자료 3, 검색 1이다. 자료의 문서 빈도는 3, 컬렉션 전체 발생 횟수는 1+2+1=4로 서로 다르다.

자료 AND 검색은 두 문서 131,200을 고르지만 순서 있는 인접 구문 “자료 검색”은 검색 위치가 자료 위치보다 정확히 1 큰 경우를 찾아 131만 고른다. “자료 자료 검색”은 시작 위치 p의 자료, p+1의 자료, p+2의 검색을 모두 요구한다. 동일 단어의 목록을 한 번 읽을 수 있어도 질의 안의 두 등장 위치 조건을 하나로 지워서는 안 된다.

NOT의 기준도 컬렉션을 명시해야 한다. 문서 200이 삭제된 공개 상태의 살아 있는 문서 집합은 U={5,130,131,400}이다. 옛 물리 목록에 200이 아직 있어도 최종 결과는 U와 교차시킨다. NOT 검색은 U에서 검색 목록을 뺀 {5}다. docID 최대 400이라는 이유로 1..400을 우주집합으로 쓰면 존재하지 않는 번호를 결과로 만든다. 실제 접근 권한을 적용하는 시스템이라면 허용된 문서 집합과 일치하는 조회 범위를 별도로 관리해야 한다.

먼저 확인할 개념
  • 문서 빈도·존재 목록·위치

    같은 문서의 반복과 인접 순서 조건을 구별한다.

  • 원문·색인 버전과 공개 상태

    삭제된 문서나 옛 내용이 결과에 나타나지 않도록 조회 버전을 맞춘다.

찾는 방향을 뒤집는다

문서 저장은 보통 문서 번호에서 내용을 찾는다. 역색인은 단어에서 그 단어가 나타난 문서 번호 목록으로 간다. 사전에서 단어의 목록 위치와 길이 등을 찾고 포스팅 리스트를 조회하면 검색 때 모든 원문을 다시 읽는 일을 줄일 수 있다.

docID는 해당 색인 안의 문서 식별자다. 운영체제 inode나 파일 오프셋, 사용자가 보는 URL과 자동으로 같은 번호가 아니다. 실제 시스템에서 색인 재구성이나 세그먼트 병합이 내부 docID를 바꿀 수 있으므로 외부 식별자와 연결할 정책이 필요하다.

같은 규칙으로 단어를 만든다

본문에서 검색 단위를 얻는 토큰화와 표기를 맞추는 정규화를 먼저 정한다. 이 예제는 이미 공백으로 분리한 한국어 단어를 그대로 사용한다. 실제 한국어 조사·복합어, 영어 대소문자·구두점은 더 정교한 처리가 필요하다.

같은 문서에서 같은 단어가 여러 번 나오더라도 단순 존재 목록에는 docID를 한 번만 넣는다. 문서 빈도 df는 단어가 나온 문서 수이며 전체 발생 횟수와 다르다. 빈도와 위치가 필요한 검색은 추가 정보를 저장한다.

존재 검색과 문장 검색은 다르다

AND는 양쪽 목록의 교집합, OR는 합집합으로 문서를 선택할 수 있다. 각 목록은 공통 순서의 docID로 정렬해야 두 포인터 처리에 사용할 수 있다. 결과의 docID 순서가 관련성 순위와 같은 것은 아니다.

단어가 둘 다 있다는 정보만으로 바로 옆 순서의 구문이 있는지 확인할 수 없다. 구문 검색에는 위치 정보나 원문 확인이 필요하다. 삭제·업데이트된 문서의 표시와 원문 버전도 맞춰야 검색 목록과 사용자 내용이 어긋나지 않는다.

중간 과정을 따라가는 예제

자체 문서 5는 “자료 구조”, 130은 “검색”, 131은 “자료 검색”, 400은 “파일 검색”이다. 공백으로 분리한 단어의 존재 역색인과 자료 AND 검색, 자료 OR 검색을 구하라.

  1. 자료의 목록은 [5, 131], 구조는 [5], 검색은 [130, 131, 400], 파일은 [400]이다.

  2. 자료의 df는 2, 검색의 df는 3이다. 문서 번호가 400까지 있다고 문서가 400개인 것은 아니며 이 컬렉션에는 네 문서가 있다.

  3. 자료 AND 검색의 결과는 [131]이고 OR의 결과는 [5, 130, 131, 400]이다. 목록 번호로 원문 저장 위치를 따로 찾아 내용을 표시한다.

단어 → 정렬된 docID 목록을 구성한다. AND는 문서 131만 선택하고 OR는 네 문서 모두 선택한다.

조건을 바꾸어 비교하기

AND와 인접 구문의 차이

문서 131과 200이 자료·검색 두 목록에 있다. 인접 구문 “자료 검색”의 결과는?

  1. 131의 자료 위치 2와 검색 위치 3은 차이 1이다.

  2. 200의 자료 위치 3 뒤 위치 4에 검색은 없다.

AND는 [131,200], 인접 구문은 [131]이다.

비교할 점

단어 존재 집합만으로 구문의 순서와 간격을 복원할 수 없다.

삭제 후 NOT의 범위

200 삭제 후 살아 있는 U={5,130,131,400}이다. NOT 검색과 자료 AND 검색의 살아 있는 결과는?

  1. 검색의 살아 있는 목록은 [130,131,400]이다.

  2. NOT은 U에서 이 목록을 빼고, AND에서 삭제된 200을 제외한다.

NOT 검색은 [5], AND는 [131]이다.

물리 포스팅의 옛 항목과 현재 공개 문서 집합은 다를 수 있다.

연습 1 · 값과 상태 예측

수정·추가 직후 삭제 전 자료의 df와 전체 발생 횟수는? 문서 131의 자료를 세 번으로 늘리면?

힌트 1

자료가 나오는 문서는 5,131,200 세 개다.

힌트 2

같은 문서 안의 반복은 df를 더 늘리지 않는다.

풀이와 답 확인

  1. 현재 df=3, 전체 발생 횟수=4다.

  2. 131의 자료가 세 번이면 df=3 그대로, 전체 발생 횟수=5다.

문서 수와 토큰 발생 횟수를 따로 기록한다.

흔한 오답에서 다시 생각하기

자료가 두 번 있는 131은 df에 두 번 센다.

연습 2 · 오류 찾아 고치기

“자료 자료 검색” 질의를 중복 단어를 지워 “자료 검색”의 존재 AND로 바꿨다. 왜 틀렸나?

힌트 1

반복된 자료는 서로 다른 위치 p와 p+1에 있어야 한다.

힌트 2

검색은 p+2 위치에 있어야 한다.

풀이와 답 확인

  1. 131의 위치 1,2,3은 원래 구문을 만족한다.

  2. 200은 단어가 함께 있어도 연속 위치 조건을 만족하지 않는다.

질의의 반복과 순서 조건을 보존해야 한다.

흔한 오답에서 다시 생각하기

질의 안의 같은 단어는 언제나 의미 없이 중복이다.

구문에서는 같은 단어의 여러 연속 등장 자체가 조건이다.

연습 3 · 직접 만들어 보기

두 단어의 위치 목록으로 구문 “자료 검색”을 판정할 조건을 쓰고, 131 자료=[1,2]/검색=[3], 200 자료=[3]/검색=[1]에 적용하라.

힌트 2

  2. 200에서는 p=3 뒤 검색 4가 없어 탈락한다.

압축 바이트의 중간에서 시작하면 숫자가 해독돼도 원래 docID일까?

기본 목록 [5,130,131,400]의 간격은 [5,125,1,269], 바이트는 [133,253,129,2,141]이다. 바이트 오프셋 3부터 읽으면 마지막 간격 269의 시작 [2,141]이다. 여기서 이전 docID가 131이라는 기준값을 함께 알면 131+269=400을 복원한다. 기준 없이 0부터 더하면 269가 되어 원래 docID를 얻지 못한다.

오프셋 4의 바이트 [141]도 마지막 비트가 1이라 숫자 13으로 정상 해독된다. 그러나 그 바이트는 원래 269의 두 번째 조각이라 숫자 시작점이 아니다. 이전 docID 131을 알고 있어도 144를 만들어 틀린다. 마지막 비트는 숫자의 종료를 알릴 뿐 임의 바이트가 숫자의 시작이라는 증거는 아니다. 건너뛰기 체크포인트에는 같은 스트림 버전의 숫자 시작 오프셋과 그 직전 누적 docID를 함께 둔다.

기본 decoder는 0을 정수로 해독할 수 있어도 엄격 증가·중복 없는 docID 목록에는 첫 항목 이후 0 간격을 허용하지 않는다. [5,5]의 간격 [5,0]과 바이트 [133,128]은 숫자 해독에는 성공하지만 포스팅 계약을 어긴다. 첫 docID를 0으로 허용하는 별도 규칙에서는 [0,5]의 첫 0은 유효하다. 또 32비트 최댓값 4294967295는 7비트 조각 [15,127,127,127,127]로 마지막 표시를 더해 [15,127,127,127,255]의 5바이트다. 단일 고정 32비트 4바이트보다 커질 수 있다.

번호 대신 차이를 저장한다

정렬된 docID 목록의 첫 값을 저장하고 이후에는 직전 번호와의 차이를 저장한다. [5, 130, 131, 400]은 [5, 125, 1, 269]로 된다. 첫 docID와 누적합으로 원래 목록을 정확히 복원할 수 있다.

차이가 작아도 모든 값을 같은 4바이트 정수로 저장하면 공간이 자동 줄지 않는다. 작은 값은 짧게 쓰는 가변 길이 부호가 필요하다. 드문 단어의 큰 간격은 길게 저장될 수 있고 사전·목록 길이·블록 정보도 전체 저장 비용에 더해진다.

가변 바이트의 규약을 명시한다

여기서는 한 바이트의 아래 7비트를 값의 조각으로 쓰고 마지막 바이트의 상위 비트를 1로 한다. 높은 자리 조각부터 기록한다. 다른 varint 방식은 상위 비트나 자리 순서가 다르므로 형식 이름만 보고 섞어 읽지 않는다.

269 = 2 × 128 + 13이므로 조각 2와 13을 쓰고 마지막 13에 128을 더해 [2, 141]을 저장한다. 인코딩 경계가 있어야 다음 값을 분리한다. 마지막 표시 없이 끝난 스트림은 잘린 입력으로 거부한다. 이 구현은 교육용이며 손상 탐지용 체크섬·버전 헤더를 제공하지 않는다.

복원한 순서로 두 포인터를 움직인다

두 정렬·중복 없는 목록에서 현재 번호가 같으면 결과에 넣고 둘 다 전진한다. 다르면 작은 번호 쪽만 전진한다. 작은 번호는 반대쪽의 현재 번호나 이후 큰 번호와 같아질 수 없으므로 버려도 된다. 한 목록이 끝나면 교집합을 종료한다.

길이가 m과 n이면 포인터가 앞으로만 가서 이 방식의 비교 시간은 O(m + n)이다. 이 결과가 디스크 해독·목록 조회·모든 검색 질의의 비용까지 없앤다는 뜻은 아니다. 압축 목록의 임의 지점부터 시작하려면 누적 docID와 바이트 위치 등 건너뛰기 정보를 추가로 둘 수 있다.

표준 라이브러리로 작은 형식 확인하기

아래 코드를 postings.py로 저장하고 python postings.py로 실행하면 자체 정수 목록의 차이 저장·복원·교집합을 확인한다. 파일이나 네트워크 입력을 읽지 않고 Python 표준 기능만 사용한다.

encode_number는 7비트씩 나누고 decode_numbers는 128배 누적한다. 실제로 큰 목록 전체를 한 번에 복원하지 않는 스트리밍 방식도 있지만 이 코드는 과정을 보이려고 전체를 복원한다. 압축 검색 엔진이나 속도 측정 구현이 아니다.

def encode_number(n):
    if not isinstance(n, int) or n < 0:
        raise ValueError("nonnegative integer required")
    parts = [n % 128]
    n //= 128
    while n:
        parts.insert(0, n % 128)
        n //= 128
    parts[-1] |= 128  # final byte has high bit 1
    return bytes(parts)

def decode_numbers(data):
    result = []
    value = 0
    pending = False
    for byte in data:
        value = 128 * value + (byte & 127)
        pending = True
        if byte & 128:
            result.append(value)
            value = 0
            pending = False
    if pending:
        raise ValueError("truncated number")
    return result

def intersect(a, b):
    # Inputs must be sorted and contain no duplicate IDs.
    i = j = 0
    result = []
    while i < len(a) and j < len(b):
        if a[i] == b[j]:
            result.append(a[i])
            i += 1
            j += 1
        elif a[i] < b[j]:
            i += 1
        else:
            j += 1
    return result

ids = [5, 130, 131, 400]
gaps = [ids[0]] + [ids[i] - ids[i - 1] for i in range(1, len(ids))]
data = b"".join(encode_number(n) for n in gaps)
restored = []
total = 0
for gap in decode_numbers(data):
    total += gap
    restored.append(total)
print(gaps)
print(list(data), len(data))
print(restored)
print(intersect(restored, [1, 5, 131, 300, 400]))

블록 순서로 묶어 읽고도 검색 결과의 순위를 유지할 수 있을까?

이 소단원은 기본 원문의 수정 전 네 문서 배치를 사용한다. docID 5/130/131/400의 바이트 범위는 [0,13)/[13,19)/[19,32)/[32,45)이고 블록은 16바이트다. 첫 소단원의 수정 문서·추가 200은 이 별도 저장 모형에 적용하지 않는다. 검색 결과 순위가 [400,130,131,5]라고 정하면 필요한 블록 방문 순서는 [2,0,1,1,0]이다. 130은 두 블록에 걸쳐 각각의 바이트 조각을 합쳐야 한다.

캐시가 비어 있고 블록 프레임이 하나뿐이면 이 순서의 읽기 실패는 2,0,1,0에서 네 번이고 가운데 연속된 1은 재사용한다. 별도 결과 바이트를 충분히 보관하는 계획은 필요한 블록 0,1,2를 각 한 번 읽어 세 번으로 줄일 수 있다. 각 요청의 원래 순위 번호를 함께 저장하고 대응 문서의 바이트 조각을 모아 [400,130,131,5] 순서로 되돌린다. 같은 블록에 있는 서로 다른 문서를 하나의 문서로 합치면 안 된다.

두 프레임을 가진 LRU 캐시를 같은 방문 순서에 쓰면 2,0,1의 처음 세 번만 실패하고 뒤 1,0은 모두 남아 있어 재사용한다. 이 조건에서는 묶음 계획이 읽기 수를 더 줄인다고 주장하지 않는다. 기본 활동처럼 130이 “빠른 검색”으로 길어지면 새 131은 [26,39)이다. 옛 시작 19는 새 130의 공백 위치이고 “검색”은 20에서 시작한다. 옛 길이 13만 읽으면 다음 문서 일부까지 섞인다. UTF-8 해독에 성공해도 올바른 원문 경계라는 증거는 아니다.

검색 목록과 표시할 원문을 연결한다

역색인의 포스팅은 검색 조건을 만족하는 문서 번호를 준다. 사용자에게 보여 줄 제목·본문·주소는 별도 저장 필드나 문서 저장소에서 찾아야 한다. docID → 원문 위치·길이의 대응표를 둘 수 있으며 실제 구조에서는 세그먼트와 버전도 필요하다.

색인에 위치나 빈도가 있다고 원문 서식과 원래 모든 문자를 복원할 수 있는 것은 아니다. 정규화하며 버린 정보와 색인하지 않은 내용이 있기 때문이다. 원문을 저장할지 원래 파일을 다시 읽을지, 접근 권한을 어떻게 적용할지 정해야 한다.

문자 개수와 파일 바이트를 나눈다

UTF-8에서는 문자마다 바이트 수가 다를 수 있다. 이 예제의 한글 음절은 각각 3바이트이고 공백은 1바이트다. “자료 구조”는 표시 문자 다섯 개지만 13바이트다. 일반적인 모든 Unicode 문자가 3바이트라는 규칙은 아니다.

파일 위치는 바이트 단위로 계산한다. 자체 배치는 원문 UTF-8 바이트를 구분자 없이 연결하고 대응표가 각 길이를 가진다. 실제 레코드 형식은 헤더·길이·체크섬·압축 등 추가 정보가 있어 이 단순 오프셋과 다르다.

묶음 저장과 갱신의 비용을 본다

문서를 압축 묶음으로 저장하면 같은 표현을 활용할 수 있지만 문서 하나를 얻기 위해 묶음 일부를 해독해야 할 수 있다. Lucene의 특정 저장 필드 형식은 문서 블록 데이터와 docID·디스크 위치의 별도 색인을 사용한다. 이 단원의 16바이트 무압축 모형은 실제 Lucene 형식이 아니다.

중간 문서를 길게 바꾸면 단순 연결 배치의 뒤쪽 오프셋이 달라진다. 별도 레코드·추가 기록·재작성·세그먼트 병합 등 여러 정책이 가능하다. 원문이 바뀌었는데 오래된 역색인이나 위치표를 쓰면 잘못된 검색과 표시가 생길 수 있으므로 일치하는 공개 버전을 정한다.

끝 다음 위치인 39 대신 마지막 포함 위치인 38을 블록 계산에 사용한다.

풀이와 답 확인

  1. 26//16=1이고 38//16=2이므로 새 문서는 블록 1과 블록 2에 걸친다.

  2. 옛 문서는 위치 19..31을 차지했으므로 블록 1 하나에 있었다.

다른 문제에 적용하기

구문·압축 재시작·원문 순위를 연결

수정 문서 131 “자료 자료 검색”, 추가 문서 200 “검색 후 자료”와 기본 문서 5, 130, 400에 대해 “자료 AND 검색”과 인접 구문 “자료 검색”의 결과를 비교하라. 문서 200을 삭제한 뒤 살아 있는 문서 집합에서 NOT 검색을 구하라. 별도 VB 스트림 [133,253,129,2,141]에서 시작 오프셋 3과 직전 docID 131을 사용해 마지막 번호를 복원하고, 잘못된 오프셋 4의 결과도 설명하라. docID 목록 [5,5]를 간격 [5,0]으로 바꾸면 숫자는 해독할 수 있는데도 포스팅으로 거부해야 하는 이유를 써라. 별도 수정 전 원문 배치에서 순위 [400,130,131,5]에 필요한 블록 방문 순서는 [2,0,1,1,0]이다. 캐시가 비어 있을 때 한 프레임과 두 프레임 LRU의 읽기 수를 비교하라. 필요한 블록을 각각 한 번 읽은 뒤 원래 순위를 보존하는 계획도 설명하라.

힌트 1

존재·인접 위치·살아 있는 문서 범위를 나누고 압축 숫자의 시작 경계와 기준값을 함께 확인한다.

힌트 2

원문 배치는 수정 전 별도 모형이다. 캐시의 퇴출과 원래 순위 번호 및 문서별 바이트 범위를 추적한다.

풀이와 답 확인

  1. 자료 AND 검색의 결과는 [131,200]이다. 인접 구문은 위치 2→3에 해당하는 문서 131만 만족한다. 문서 200을 삭제하면 살아 있는 집합은 {5,130,131,400}이다. 여기서 검색을 포함한 [130,131,400]을 빼면 NOT 검색의 결과는 [5]다.

  2. 오프셋 3부터 읽은 [2,141]은 간격 269로 해독된다. 직전 docID 131에 더하면 400이다. 잘못된 오프셋 4부터 읽은 [141]은 13으로 해독되어 144라는 잘못된 번호를 만든다.

  3. docID 목록 [5,5]에 대응하는 간격 [5,0]은 숫자로 해독할 수 있다. 그러나 뒤 간격이 0이므로 엄격하게 증가하고 중복이 없어야 하는 포스팅의 조건을 어긴다.

  4. 한 프레임에서는 블록 2, 블록 0, 첫 번째 블록 1, 마지막 블록 0의 네 요청이 읽기 실패다. 두 프레임 LRU에서는 처음 블록 2, 0, 1의 세 요청만 읽기 실패다.

  5. 블록 0, 1, 2를 각각 한 번 읽고 문서 130의 두 조각을 합친다. 각 요청에 저장한 원래 순위에 따라 문서 400, 130, 131, 5를 표시한다. 이 계획에는 결과 바이트를 따로 보관할 충분한 공간이 필요하다.

새 구문·재시작·캐시 활동은 손추적한 자체 모형이다. 기본 본문의 기존 Python 실행 증거는 보존하지만 이번 보강에서 새 코드나 검색 서버·Lucene·실제 파일 I/O·학생 실험을 실행하지 않았다.

해결한 뒤 점검할 것

  • 문서 존재와 인접 위치 조건 및 NOT 범위를 구별한다.

  • VB 숫자 시작·누적 기준·포스팅 계약을 함께 검사한다.

  • 캐시 프레임 수에 맞는 실제 방문 실패를 계산한다.

  • 문서의 모든 바이트와 원래 검색 순위를 보존한다.
