페이지 손상·체크섬

파일이 열렸다는 사실만으로 안의 페이지가 온전하다고 말할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 바이트와 페이지

  • 나머지 계산

  • 오류 검출과 복구의 차이

학습 목표

  • 체크섬의 계산·비교 절차를 설명한다.

  • 검출 실패의 작은 반례를 만든다.

  • 손상·최신성·업무 정확성을 구별한다.

옛 버전과 그 체크섬이 함께 돌아오면 버전 필드를 보호해도 최신임을 알까?

새 자체 규약은 페이지 ID와 버전도 한 바이트씩 보호 범위에 넣고, 체크섬은 (ID+버전+데이터 두 바이트) mod 256으로 정한다. 기대하는 현재 페이지는 ID 1, 버전 2, 데이터 (20,40)이라 체크섬 63이다. 이전 버전 1의 같은 데이터와 체크섬 62가 함께 돌아오면 내부 계산은 62로 통과한다. 외부에서 기대한 버전 2와 읽은 버전 1을 비교해야 오래된 페이지임을 알 수 있다.

다른 ID 2, 버전 2, 데이터 (20,40)의 페이지와 유효 체크섬 64를 위치 1에서 읽어도 그 페이지 내부 계산은 맞다. 요청한 페이지 ID 1과 읽은 ID 2의 불일치를 별도로 검사해야 한다. 보호 범위에 신원 필드를 넣는 것과 그 신원이 기대한 대상인지 판단하는 것은 다른 단계다. 이 규약은 PostgreSQL 실제 체크섬 알고리즘이나 디스크 페이지 형식이 아니다.

ID 1·버전 2에서 데이터가 (40,20)으로 서로 바뀌거나 (21,39)로 바뀌어도 합은 60이어서 체크섬 63으로 통과한다. 데이터를 두 역할에 배치한 업무 규칙은 순서나 각 값을 따로 검사할 수 있다. 검출 실패의 모든 원본을 체크섬 값 하나로 복원하지 못한다. 장애 대응에서는 읽은 원본 증거와 검증된 복구 자료를 보존하고 어떤 검사에서 무엇이 확인됐는지를 구분한다.

먼저 확인할 개념
  • 보호 범위·충돌·최신성

    체크섬 필드와 외부 기대 상태를 서로 다른 검사로 구별한다.

  • 복구 근거와 일관된 버전

    유효한 바이트와 갱신 완료 상태를 같은 증거로 취급하지 않는다.

페이지를 읽었다고 내용이 맞는 것은 아니다

페이지는 파일의 일정 구간을 묶어 저장하고 읽는 단위다. 매체 오류·전송 오류·부분 쓰기 등으로 바이트가 예상과 달라질 수 있다. 체크섬은 정해진 바이트에서 요약값을 계산해 저장하고 읽을 때 다시 계산하여 비교하는 검출 장치다. 무엇을 계산 범위에 넣는지, 체크섬 필드는 계산 때 어떻게 처리하는지 규약이 필요하다.

PostgreSQL 18 문서는 데이터 페이지의 체크섬 검증을 설명하지만 내부 자료구조와 임시 파일까지 모두 보호한다고 하지 않는다. 여기의 작은 합산 규칙은 개념을 보이기 위한 자체 모형이며 PostgreSQL 체크섬 구현이나 실제 페이지 형식이 아니다.

같은 요약값이 같은 내용을 보장하지 않는다

이 수업에서는 두 데이터 바이트의 합을 256으로 나눈 나머지를 체크섬으로 삼는다. 저장할 때 (20,40)의 체크섬은 60이다. 한 바이트만 21로 바뀌면 61이 되어 비교에서 실패한다. 반면 (21,39)는 다른 내용인데도 합이 60이어서 통과한다. 서로 다른 내용이 같은 요약값을 갖는 충돌을 직접 볼 수 있다.

실제 체크섬은 이런 단순 합보다 오류 검출 특성이 좋도록 설계되지만 모든 가능한 변경을 무조건 검출하는 장치는 아니다. 특히 공격자가 데이터와 체크섬을 함께 고칠 수 있는 환경에서 단순 체크섬은 작성자 인증 수단이 아니다. 인증이 목적이면 신뢰할 키나 서명 등 별도 설계가 필요하다.

검출·복구·최신성은 각각 질문이다

검증 실패는 해당 페이지를 그대로 신뢰하면 안 된다는 신호다. 실패한 체크섬만으로 원래 바이트를 일반적으로 복원할 수 없다. 검증된 백업·복제본·로그 등 복구 근거가 있어야 하며 원본 증거를 남기고 절차에 따라 복구해야 한다. 설치 없이 여기서는 값의 판정만 연습한다.

오래된 페이지와 그에 맞는 체크섬이 함께 돌아와도 검증은 통과할 수 있다. 따라서 최신 버전인지, 업무 규칙을 지키는지도 별도 검사한다. 두 계좌 합이 기대값인지 같은 논리 검사는 체크섬의 바이트 검증과 서로 보완한다.

모든 행의 저장 체크섬은 그 행의 전체 보호 데이터와 일치한다고 정한다. 체크섬 통과 뒤에도 원하는 신원·최신 버전·업무 값을 확인한다.

중간 과정을 따라가는 예제

가상 페이지의 보호 데이터는 두 바이트다. 저장값은 (20,40), 체크섬은 합 mod 256이다. 읽은 후보 A=(21,40), B=(21,39), C=(20,40)를 판정하라. 저장된 체크섬 60은 바뀌지 않았다고 가정한다.

  1. 저장 체크섬은 (20+40) mod 256=60이다.

  2. A의 계산값은 61이므로 60과 달라 검증 실패다.

  3. B의 계산값은 60으로 통과하지만 저장한 두 바이트와 같지 않다. 이것이 충돌 반례다.

  4. C는 60으로 통과하고 바이트도 원본과 같다. 다만 이 비교만으로 페이지가 최신 버전이거나 업무상 올바르다고 증명하지 않는다.

A는 실패, B/C는 통과다. 통과와 원본 동일성은 구별한다. B가 무조건 정상이라고 보고하면 안 된다.

오해와 반례

체크섬이 통과하면 최신·정상 페이지이고 실패하면 체크섬으로 원래 내용을 복구할 수 있다.

B는 내용이 달라도 통과한다. 오래된 내용과 맞는 체크섬도 통과할 수 있다. 실패 시 원래 내용을 알아내려면 별도 복구 자료가 필요하며 체크섬 값 자체가 백업은 아니다.

각 로그의 재생이 멱등적이면 여러 로그의 순서도 아무렇게나 바꿔도 될까?

자체 초기 상태에서 P와 Q는 각각 10이다. T1의 결과는 P=20, Q=20이고 뒤의 T2의 결과는 P=30, Q=30이다. 둘의 완전한 로그와 commit이 순서대로 지속 저장됐다고 정한다. 원위치에는 T1의 P=20, Q=20을 반영한 뒤 T2의 P=30만 설치했으므로 장애 후 P는 30, Q는 20이다. 복구는 남은 두 로그를 T1 다음 T2 순서로 재생해 최종 P=30, Q=30을 얻는다. 각 결과 대입이 멱등적이라는 사실은 다른 트랜잭션의 적용 순서가 무관하다는 뜻이 아니다.

T2를 먼저 적용하면 P와 Q가 각각 30이지만 T1을 나중에 적용하면 각각 20으로 돌아가 최신 commit 결과를 잃는다. P=Q 관계와 페이지 체크섬이 모두 맞아도 최신 버전 요구에는 실패할 수 있다. 같은 순서의 전체 재생을 다시 시작하면 마지막 T2가 P=30, Q=30을 복원한다. 복구 중간의 P=20, Q=20을 일반 독자에게 최종 상태로 공개하지 않는다. 이 모형에서는 복구 완료 전에 독자 접근을 허용하지 않는다고 정한다.

원위치의 P=30, Q=30이 지속 저장되고 검증된 checkpoint가 T2까지 반영 완료라고 기록된 별도 상태에서는 그 경계 이전의 T1과 T2를 재생 대상에서 제외한다. T2 로그만 지운 뒤 T1을 여전히 미반영 로그로 취급하면 P와 Q를 각각 20으로 되돌릴 수 있다. checkpoint 경계와 로그 재사용 상태를 일치시켜야 한다. 이것은 완료 순번을 관리하는 자체 종이 정책이며 실제 ext4의 revocation이나 저널 복구 전체를 구현한 것은 아니다.

요청한 쓰기와 남은 쓰기는 다르다

메모리에서 두 값을 바꿨다고 저장 장치의 두 위치가 동시에 바뀌는 것은 아니다. 프로그램이 호출한 순서와 장애 뒤 남은 순서도 저장 버퍼·장치 동작 때문에 같다고 가정할 수 없다. 지속성 보장을 위한 동기화와 오류 확인이 필요한 이유다.

이 절의 자체 모형은 P와 Q가 같은 버전 값이어야 한다는 계약이다. 초기에는 둘 다 10이고 목표는 둘 다 20이다. P만 20으로 바뀐 상태는 각각의 값이 정상적으로 읽혀도 두 값의 관계가 깨진다. 페이지별 체크섬 통과와 여러 페이지의 갱신 일관성은 다른 검사다.

원위치보다 먼저 복구 근거를 남긴다

저널 방식은 예정된 변경을 로그에 남기고 유효한 commit을 지속 저장한 뒤 원위치에 반영할 수 있게 한다. 장애 뒤에는 완성된 기록을 근거로 필요한 갱신을 재생한다. 이 모형의 로그에는 P=20,Q=20이라는 결과값과 commit이 있으며 로그의 완전성·체크섬도 검증한다고 가정한다.

commit이 없거나 기록 검증이 실패하면 이 모형에서는 재생하지 않는다. 원위치 쓰기는 유효 commit의 지속 저장 후에만 시작한다. 로그 데이터보다 commit만 먼저 남도록 두면 복구 자료가 없는 완료 표시가 생기므로 쓰기 순서 보장이 중요하다. 실제 ext4는 모드에 따라 저널 보호 범위가 다르며 모든 응용 데이터가 기본적으로 저널에 들어가는 것은 아니다.

재생 도중의 장애도 고려한다

로그의 결과를 P=20,Q=20으로 다시 설치하면 첫 재생에서 P만 쓰고 중단했어도 다음 재생에서 둘을 20으로 만들 수 있다. 반면 P에 10을 더하라는 절차를 무조건 반복하면 같은 로그가 중복 적용되어 30이 될 수 있다. 반복의 효과를 명시해야 한다.

기록을 재사용하거나 지우는 시점도 중요하다. 이 모형에서는 모든 원위치 결과가 지속 저장되었다는 확인 전에는 복구에 필요한 로그를 지우지 않는다. 실제 저널의 트랜잭션 ID·회수·재생 정책은 더 복잡하다. 아래 표는 데이터와 메타데이터를 모두 기록하는 자체 종이 모형이다.

원자적으로 저장한 두 사용자의 변경도 모두 보존된다는 뜻일까?

자체 config의 현재 버전은7이다. A와 B는 같은 버전7을 읽고 각자 N1과 N2를 완성했다. B가 먼저 N2/버전8을 원자 교체하고 A가 뒤에 N1/버전8을 무조건 원자 교체하면 최종 이름은 N1이다. 두 파일은 각각 완전하고 각 이름 전환도 원자적이지만 B의 변경이 사라진다. 원자성은 여러 편집의 합쳐짐이나 충돌 해결을 뜻하지 않는다.

A가 교체 직전에 버전7인지 확인해도 확인과 교체 사이에 B가 N2/8을 설치할 수 있으면 같은 문제가 남는다. 자체 해결 계획은 모든 쓰기자가 같은 잠금 규칙에 협력하고, 같은 보호 구간에서 현재 버전을 다시 읽어 기대 버전과 비교한 뒤 교체한다. A가 기대7인데 현재8이면 충돌을 보고하고 교체하지 않는다. 잠금의 실제 범위·실패·재시작 및 비협력 쓰기자를 다룬 구현은 이 종이 계획에서 수행하지 않았다.

지속성 결과도 별도로 보고한다. 새 내용과 이름 교체는 성공했지만 부모 디렉터리 동기화가 실패했다면 현재 이름은 새 파일이어도 최종 장애 지속성은 확인되지 않았다. 기본 본문의 O/N 허용 복구는 자체 모형의 조건이다. 오류가 났다는 이유로 교체가 없었다고 기록하거나 옛 O를 자동으로 덮어 되돌리면 현재 새 데이터나 다른 작성자의 변경까지 훼손할 수 있다. 확인된 단계와 현재 관찰, 미확정 지속성 및 재검증 계획을 따로 남긴다.

완성한 다음 이름을 바꾼다

기존 파일을 열어 앞부분부터 덮어쓰면 중간 장애에 새 앞부분과 옛 뒷부분이 섞일 수 있다. 대안은 별도 임시 파일에 새 내용을 완성하고 검증한 뒤 기존 이름이 새 파일을 가리키도록 바꾸는 방식이다. 임시 파일은 목적지와 같은 파일시스템에 두는 것이 교체 동작의 조건을 관리하기 쉽다.

Python os.replace는 목적지 파일을 교체하고 성공 시 원자적인 이름 변경을 설명한다. 서로 다른 파일시스템에서는 실패할 수 있다. 원자적이라는 말은 이름 전환을 반쯤 관찰하지 않는다는 계약이지 모든 바이트와 디렉터리 변경이 정전 뒤 영원히 남는다는 뜻이 아니다.

내용과 이름을 따로 지속 저장한다

버퍼링된 Python 파일에서는 flush로 언어 수준 버퍼를 넘기고 fsync 같은 저장 동기화를 수행해야 한다. flush만으로 정전 지속성을 주장하지 않는다. Linux fsync 문서는 파일 동기화가 디렉터리의 이름 항목까지 반드시 저장하는 것은 아니며 디렉터리의 별도 동기화가 필요함을 설명한다.

종이 절차는 새 파일의 쓰기·검증·동기화 성공, 파일 닫기, 이름 교체 성공, 부모 디렉터리 동기화 성공을 구별한다. 이것은 Linux 계열의 개념 절차이며 Windows에서 같은 디렉터리 동기화 코드를 그대로 지원한다고 가정하지 않는다. 저장 장치와 파일시스템의 실제 보장, 각 오류, 권한·동시 쓰기까지 별도로 확인해야 한다.

확인된 단계까지만 결과를 말한다

교체 성공 뒤 살아 있는 프로세스에서 새 이름을 읽는 결과와 재시작 뒤 복구된 결과는 별도다. 부모 디렉터리 동기화가 아직 확인되지 않았다면 새 이름이 정전 뒤 남았다고 단정하지 않는다. 불확정 상태를 실패로 숨기거나 성공으로 과장하지 않고 기록하는 것이 복구 계획에 도움이 된다.

임시 파일을 정리할 때도 작업 중인 다른 쓰기나 복구 근거를 삭제하지 않도록 소유권과 완료 여부를 확인한다. 이 수업은 실제 파일을 바꾸지 않고 사건 표만 작성한다. 백업·동시 편집 충돌·파일 메타데이터 보존을 모두 해결한 저장 라이브러리 구현이 아니다.

  2. 교체 성공 후 현재 config는 N이다. 이름 전환은 원자적이라고 가정해 중간 이름을 관찰하지 않는다.

  3. 정전 뒤 모형은 O 또는 N을 허용한다. 부모 디렉터리의 지속 저장을 아직 확인하지 않았으므로 N 하나로 확정할 수 없다.

  4. 이 O/N 규칙은 자체 복구 모형이다. 모든 실제 파일시스템이 같은 결과 집합을 보장한다는 주장이 아니다.
