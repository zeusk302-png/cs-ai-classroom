소단원 14.1

레코드 관리자와 페이지 API

책의 한 문장을 옮겨도 책갈피가 같은 문장을 가리키게 만들 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 바이트 오프셋과 반열린 구간

  • 고정 크기 페이지

  • 슬롯과 레코드 ID

  • 메모리와 영속 저장소의 구분

학습 목표

  • 페이지 관리자와 레코드 관리자의 책임을 구분한다.

  • 작은 슬롯 페이지의 공간 조건을 계산한다.

  • 삭제 후 낡은 식별자가 다른 레코드를 가리키는 문제를 설명한다.

페이지를 가져오는 일과 내용을 읽는 일

페이지 API는 페이지 ID로 고정 크기 블록을 가져오거나 새 블록을 만들고, 변경 여부를 기록하는 층이다. 레코드 API는 그 블록 안에서 insert, read, update, delete를 수행하는 층이다. 예를 들어 페이지 7을 가져오는 것과 그 안의 슬롯 2가 뜻하는 학생 기록을 읽는 것은 서로 다른 작업이다. 파일의 헤더 유무와 페이지 배치 규칙에 따라 실제 파일 오프셋도 달라진다.

단순 파일에 헤더가 없고 모든 페이지가 64바이트라면 페이지 번호 0부터의 오프셋은 64×번호다. 그러나 이 계산을 모든 저장 형식에 적용하면 안 된다. 데이터베이스 페이지 크기와 운영체제 페이지 크기도 반드시 같은 것은 아니다. 프로그램에서 정한 파일 형식의 버전, 정수 바이트 순서, 길이 제한을 먼저 문서화한다.

슬롯 배열은 움직이는 내용에 붙인 이름표

이번 종이 모형의 페이지는 64바이트, 헤더는 앞의 8바이트, 슬롯 하나는 4바이트다. 슬롯 배열은 앞에서 자라고 데이터는 뒤에서 자란다. 두 영역의 경계 사이가 연속된 빈 공간이다. 슬롯은 레코드의 현재 위치와 길이를 가리킨다. 압축으로 레코드를 옮겨도 슬롯 번호를 유지하면 외부의 (페이지 ID, 슬롯 번호)는 그대로다.

새 슬롯과 새 레코드를 만들 때는 레코드 길이뿐 아니라 슬롯 4바이트도 필요하다. 삭제로 생긴 구멍들의 합이 충분해도 한 덩어리로 이어진 공간이 부족할 수 있다. 이때 살아 있는 레코드를 뒤쪽에 다시 모으고 슬롯의 오프셋을 함께 갱신하는 압축을 수행한다. 데이터만 옮기고 슬롯을 바꾸지 않는 것은 레코드를 망가뜨리는 오류다.

식별자와 메모리 수명을 계약으로 적기

슬롯 1을 삭제한 뒤 그 자리에 다른 사람의 기록을 넣으면 과거의 식별자가 새 사람을 가리킬 수 있다. 학습용 API에서는 삭제된 식별자를 무효 처리하고 세대 번호까지 포함한 (페이지, 슬롯, 세대)를 사용하는 방법을 생각할 수 있다. 세대가 다르면 오래된 요청을 거부한다. 실제 설계에서는 세대의 표현 범위와 순환 정책도 정해야 한다.

버퍼 풀은 메모리에 있는 페이지 사본을 frame에 담는다. pin은 사용하는 동안 교체되지 않도록 참조를 유지하는 개념이고, dirty는 사본이 변경되었다는 표시다. 이들은 영속성 보장을 대신하지 않는다. 학습용 계약은 fetch→pin→읽기/변경→dirty 표시→unpin 순서를 명시하고, 모든 frame이 pin된 경우의 실패 또는 대기 정책을 따로 정한다.

중간 과정을 따라가는 예제

64바이트 페이지에 헤더 8바이트와 슬롯당 4바이트를 쓴다. A는 12바이트, B는 16바이트다. A와 B를 넣은 뒤 A를 삭제한다. C 20바이트를 새 슬롯으로 넣을 수 있는지 계산하라. 삭제 슬롯은 재사용하지 않고 보존한다.

  1. A와 B 삽입 후 슬롯은 2개다. 앞 경계는 8+2×4=16, 데이터는 A [52,64), B [36,52)에 있으므로 뒤 경계는 36이다. 연속 빈 공간은 20바이트다.

  2. A를 삭제해도 슬롯 2개와 B의 위치를 유지한다. [52,64)의 12바이트 구멍이 생기지만 [16,36)의 연속 공간은 여전히 20바이트다. 새 C에는 데이터 20+새 슬롯 4=24바이트가 필요하므로 바로 넣을 수 없다.

  3. B를 [48,64)로 옮기고 해당 슬롯 오프셋을 48로 바꾼다. 앞 경계 16, 뒤 경계 48이라 32바이트가 연속으로 빈다.

  4. C를 [28,48)에 넣고 슬롯 3을 만들면 앞 경계는 20, 뒤 경계는 28이다. 빈 공간 8바이트가 남는다. B의 슬롯 번호는 바뀌지 않는다.

압축 후 삽입할 수 있다. 삭제 슬롯을 보존한 이 규약에서 최종 연속 여유는 8바이트다. 다른 슬롯 재사용 규약이라면 계산과 식별자 정책을 함께 바꿔야 한다.

종이와 본문으로 직접 해보기

위 최종 상태에서 D 5바이트를 새 슬롯으로 넣는 요청을 승인할 수 있는가? B를 이동하면서 슬롯 오프셋을 갱신하지 않으면 어떤 바이트 구간을 잘못 읽는가?

힌트 보기

새 슬롯 비용을 더하고 B의 이전 오프셋 36을 기억하라.

풀이 보기

D에는 5+4=9바이트가 필요하지만 8바이트밖에 없어 거부하거나 다른 페이지를 고른다. B의 낡은 슬롯은 [36,52)를 읽는다. 그 중 [36,48)는 C의 일부이고 [48,52)는 B의 일부이므로 두 레코드가 섞인다.

오해와 반례

총 빈 바이트가 충분하면 어떤 레코드든 바로 넣을 수 있다.

구멍과 연속 빈 공간, 슬롯 비용을 구분해야 한다. A 삭제 직후 총 데이터용 구멍과 중앙 여유는 32바이트지만 중앙 20바이트만으로 C와 새 슬롯을 넣을 수 없다. 압축 또는 다른 페이지 선택이 필요하다.

한 단계 더

페이지 헤더에 형식 버전, 유효 범위, checksum을 넣는 종이 설계를 그려 보자. checksum은 일부 손상을 탐지하는 근거이며 삭제 식별자의 재사용이나 트랜잭션 원자성을 해결하지 않는다. 실제 파일 프로그램을 만들 경우 잘못된 길이·경계 밖 슬롯을 거부하는 검사부터 추가한다.

소단원 14.2

B+트리·해시 성능 비교

한 사람의 번호 찾기와 일정 범위의 번호 찾기에 같은 색인을 써도 될까?

준비 개념과 학습 목표

준비 개념

  • 동등 검색과 범위 검색

  • B+트리 리프와 연결

  • 해시 버킷과 충돌

  • 논리 접근과 실제 I/O

학습 목표

  • 같은 데이터와 결과 조건으로 두 접근 방법을 비교한다.

  • 콜드/웜 캐시에서 페이지 읽기 계수를 계산한다.

  • 충돌과 범위 검색이 해시의 장점을 바꾸는 이유를 설명한다.

비교의 질문을 고정한다

B+트리는 키 순서를 이용해 검색 경로를 찾고 리프 사이를 이어 범위를 읽는다. 해시는 키로 버킷을 골라 동등 검색을 수행한다. 평균적으로 유리한 해시 동등 검색도 충돌 분포와 페이지 용량에 의존한다. 정렬된 범위를 그대로 제공하는 구조가 아니므로 범위 검색에서는 추가 구조가 없으면 관련될 수 있는 모든 버킷을 확인한다.

공정한 비교는 동일한 키, 값, 중복 규약, 결과 집합, 삽입 상태를 먼저 고정한다. 색인에 값 자체가 들어 있는지, 값은 별도 heap 페이지에 있는지도 적는다. 별도 레코드 페이지를 읽는 비용을 한 구조에서만 제외하면 결과가 왜곡된다. 아래 예제는 두 구조 모두 리프 또는 버킷에 값이 직접 들어 있는 작은 모형이다.

작은 트리와 버킷 배치를 함께 그린다

키는 10,20,30,40,50,60이다. B+트리는 루트의 구분 키 30과 50으로 세 리프 [10,20], [30,40], [50,60]을 고른다. 경계 키와 같으면 오른쪽으로 가는 규약이다. 리프들은 낮은 키에서 높은 키 순서로 연결되어 있다. 동등 검색에는 루트 1회와 선택 리프 1회가 필요하다.

해시는 h(k)=(k/10) mod 3으로 버킷 0=[30,60], 1=[10,40], 2=[20,50]을 만든다. 정수 10의 배수만 쓰는 이 자체 예제에서 버킷 페이지는 각각 한 장이다. 40의 동등 검색은 버킷 1 한 장으로 끝난다. 반면 20 이상 50 이하 범위는 세 버킷을 모두 보고 조건에 맞는 네 항목을 골라야 한다.

접근 횟수와 성능 주장을 구분한다

이 모형의 콜드 캐시에서는 첫 접근마다 페이지 읽기 miss 하나로 센다. 트리의 40 검색은 2회, 해시는 1회다. 20≤k≤50의 트리 검색은 루트와 리프 세 장으로 4회, 해시는 버킷 세 장으로 3회다. 따라서 작은 예제에서 트리가 범위 검색에 항상 더 적은 페이지를 읽는다고 단정할 수 없다. 데이터가 커져도 필요한 범위가 좁을 때 순서 구조의 장점이 커진다.

루트가 캐시에 있고 다른 페이지가 콜드이면 트리 읽기는 동등 1회, 해당 범위 3회다. 동일 상태를 두 실험에 적용하고 논리 fetch와 버퍼 miss를 따로 센다. 실제 시간에는 CPU 비교, 캐시 정책, 동시성, 장치 지연도 작용한다. 페이지 수로부터 측정하지 않은 밀리초나 배속을 만들어 내지 않는다. 삽입 분할과 overflow까지 비교하려면 쓰기와 공간도 별도 지표로 기록한다.

중간 과정을 따라가는 예제

설명에 있는 트리와 해시로 key=40과 20≤key≤50을 찾는다. 값은 색인 안에 있고 캐시는 처음 비었다. 결과와 읽기 페이지 목록을 비교하라.

  1. 트리의 40 검색은 루트에서 30≤40<50을 선택한다. [30,40] 리프에서 값 40을 찾는다. 루트와 중간 리프 두 장이다.

  2. 해시의 40 검색은 (40/10) mod 3=1이다. 버킷 1=[10,40]을 읽어 40을 찾는다. 한 장이다.

  3. 트리의 범위는 루트에서 20이 있는 첫 리프로 간다. 20을 취한 뒤 연결로 다음 리프의 30,40과 마지막 리프의 50을 취한다. 60은 조건 밖이다. 루트와 세 리프, 총 네 장이다.

  4. 해시의 범위는 버킷 0,1,2를 읽고 20,30,40,50을 선택한다. 세 장이며 반환 순서를 정렬하려면 별도 작업이 필요하다.

동등 검색 결과는 둘 다 {40}, 범위의 집합 결과는 둘 다 {20,30,40,50}이다. 콜드 읽기 계수는 트리 2/4, 해시 1/3이다. 이 결과는 지정한 작은 배치에 한정된다.

종이와 본문으로 직접 해보기

버킷 용량을 2개로 하고 h(k)=k mod 3으로 10,20,30,40,50,60을 넣었다. 이 배치와 h(k)=k mod 10으로 바꾼 배치에서 60 동등 검색의 읽기 수를 비교하라. overflow는 삽입 순서대로 연결하며 디렉터리는 메모리에 있다고 가정한다.

힌트 보기

mod 10이면 여섯 키가 모두 버킷 0에 모인다. 페이지마다 두 키를 담는다.

풀이 보기

mod 3에서는 0=[30,60], 1=[10,40], 2=[20,50]이라 60은 버킷 0 한 장에서 찾는다. mod 10에서는 [10,20]→[30,40]→[50,60] 세 장을 순서대로 읽어 60을 찾는다. 충돌이 집중되면 동일 검색도 세 장으로 늘어난다.

오해와 반례

해시의 평균 O(1)이므로 디스크에서 언제나 한 번 읽는다.

O(1)은 가정이 있는 평균 연산 증가율이며 특정 페이지 수를 보장하지 않는다. 본문 mod 10 예제는 overflow 세 장을 읽는다. 디렉터리, 별도 레코드 페이지와 캐시 상태가 추가 비용을 만들 수도 있다.

자기점검

두 구조가 같은 네 키를 반환했지만 순서가 다르면 어떤 검사가 필요한가?

답과 이유 보기

명세가 집합 반환인지 정렬 반환인지 확인한다.

집합 계약이면 같은 결과지만 정렬 계약이면 해시 결과 정렬을 포함한 구현과 비용이 필요하다.

트리의 루트만 웜 캐시이면 범위 검색의 miss는 몇 회인가?

답과 이유 보기

3회다.

루트의 논리 접근은 있지만 읽기 miss는 없고 세 리프의 첫 접근만 miss다.

root가 캐시에 있는 경우 예제의 tree 범위 20–50 읽기 페이지 수는?

소단원 14.3

장애·재시작·I/O 계수 검증

저장했다고 답한 직후 전원이 꺼져도 그 답을 믿을 수 있게 하려면 무엇을 남겨야 할까?

준비 개념과 학습 목표

준비 개념

  • 트랜잭션 원자성과 지속성

  • WAL과 LSN

  • 메모리 변경과 영속 쓰기의 차이

  • 논리 I/O 계수의 범위

학습 목표

  • 단순 redo 모형의 영속 로그와 응답 순서를 설명한다.

  • 장애 시점별 허용 결과와 반복 redo를 추적한다.

  • 페이지 fetch, read miss, write, sync 계수를 구분한다.

먼저 작은 장애 모형을 선언한다

연습 저장소는 단일 트랜잭션 T만 동시에 허용하고, 미커밋 변경 페이지를 영속 저장소에 내보내지 않는다. 로그 레코드와 페이지 쓰기는 모형에서 원자적이며 sync를 마친 데이터는 장애 후 남는다고 가정한다. 실제 장치의 torn write나 거짓 완료 응답은 다루지 않는다. 이 가정들을 빼고 아래 순서만 적용하면 완전한 복구 구현이라고 부를 수 없다.

T는 A를 5에서 9로 바꾼다. 영속 로그에 LSN 10의 after-image A=9와 LSN 11의 COMMIT을 기록하고 로그 sync를 완료한 뒤 성공을 응답한다. 변경 페이지의 pageLSN은 10이다. 페이지를 쓰기 전 해당 변경 로그가 영속 저장소에 있어야 하는 것이 WAL 순서다. 이 단순 no-steal 모형은 미커밋 페이지 undo가 불필요하지만 실제 ARIES의 steal 모형에는 undo와 그 복구도 필요하다.

장애 시점과 반복 복구를 추적한다

로그 sync 이전에 장애가 나면 성공 응답이 없으므로 새 값의 지속성을 약속하지 않는다. 연습에서는 영속 COMMIT이 없으면 T를 적용하지 않는다. COMMIT이 영속화되었으나 아직 페이지를 쓰지 못했으면 복구가 A=9를 redo한다. 성공 응답을 받은 뒤 장애가 나도 이 로그 때문에 A=9가 복구되어야 한다. 응답 직전 장애에서는 요청자가 결과를 모를 수 있지만 그 불확실성과 서버의 커밋 여부는 별개다.

redo는 기록된 값과 pageLSN으로 반복 적용을 판단한다. 페이지의 pageLSN이 10보다 작으면 A=9를 쓰고 pageLSN=10으로 만든다. 이미 10 이상이면 같은 기록을 다시 적용하지 않는다. add 4 같은 연산을 무조건 다시 수행하면 복구 두 번 후 13이 되어 잘못이다. 실제 여러 트랜잭션 복구에는 커밋만 골라 재생하는 것 이상의 분석·redo·undo 순서가 필요하므로 이 한 트랜잭션 연습을 일반화하지 않는다.

검증 표에 결과와 계수의 경계를 함께 적는다

기능 검사는 정상 재시작, COMMIT 직전/직후, 페이지 쓰기 전/후, 복구 도중 재장애를 포함한다. 각 지점에서 허용 결과를 먼저 적고 조회 결과와 비교한다. 잘못된 헤더 길이나 checksum도 정상 결과로 통과시키지 않는다. 예제 파일을 실제 쓰지 않은 상태에서는 종이 상태 검증이며 실제 장애 시험 완료로 기록하지 않는다.

I/O 표는 논리 fetch 요청 수, 버퍼 read miss, 페이지 write, 로그 쓰기, sync 호출을 나눈다. 같은 fetch가 캐시에서 끝날 수 있고 sync 한 번은 페이지 읽기 한 번이 아니다. OS 캐시와 장치 내부 처리 때문에 프로그램 계수와 물리 장치 I/O도 다를 수 있다. 정확성 검사가 실패한 빠른 결과는 유효한 속도 개선으로 채택하지 않는다. 반복 실험에서는 같은 초기 데이터와 캐시 정책, 동일 결과 명세를 고정한다.

중간 과정을 따라가는 예제

초기 영속 페이지는 A=5, pageLSN=0이다. T의 로그 UPDATE(10,A=9), COMMIT(11)을 sync한 뒤 페이지 쓰기 전 장애가 났다. 복구 후 다시 복구한다. 별도로 빈 2-frame LRU 버퍼에서 페이지 요청 [1,2,1,3,2]를 읽기 전용으로 수행할 때 fetch와 read miss를 세라. 각 요청 후 즉시 unpin한다.

  1. 영속 COMMIT 11이 있고 페이지의 0<10이므로 복구는 A=9, pageLSN=10을 적용한다. 실제 영속 쓰기까지 완료한 뒤 재장애라고 가정한다.

  2. 두 번째 복구에서는 10≤pageLSN이므로 해당 redo를 건너뛴다. A는 9다. 같은 add 4를 두 번 계산하는 13과 다르다.

  3. LRU 요청 1은 miss, 요청 2도 miss다. 요청 1은 hit이며 2가 가장 오래된 페이지가 된다.

  4. 요청 3은 miss이고 2를 내보낸다. 마지막 요청 2도 miss이며 1을 내보낸다. fetch는 5, read miss는 4, hit는 1이다. 읽기 전용이라 dirty 페이지 쓰기는 0이다.

복구 반복 후 A=9가 유지된다. 독립 읽기 모형에서는 fetch 5/read miss 4/hit 1/page write 0이다. 로그 sync·복구 쓰기 계수와 독립 읽기 실험의 계수를 섞지 않는다.

종이와 본문으로 직접 해보기

COMMIT이 영속화되기 전에 장애가 나면 T를 적용하는가? 3-frame 빈 LRU 버퍼로 같은 [1,2,1,3,2]를 읽으면 miss는 얼마인가?

힌트 보기

연습 모형은 미커밋 데이터 페이지를 내보내지 않는다. 세 페이지 모두 보관할 수 있는지 확인하라.

풀이 보기

영속 COMMIT이 없으므로 T를 적용하지 않고 A=5를 유지한다. UPDATE만 남아도 커밋한 것으로 판단하지 않는다. 3-frame에서는 1,2,3의 첫 접근만 miss이므로 miss 3, hit 2, fetch 5다.

오해와 반례

한 번 재시작했을 때 값이 맞으면 장애 복구 검증이 끝난다.

응답·로그·페이지 쓰기의 경계와 복구 중 재장애가 빠져 있다. 특히 add 연산의 무조건 재생은 한 번 맞고 두 번째 틀릴 수 있다. 본문의 원자 쓰기 가정도 실제 시스템에서 별도로 검증해야 한다.

자기점검

pageLSN=20인 페이지에 LSN 10 redo를 적용하는가?

답과 이유 보기

이 순서 모형에서는 적용하지 않는다.

그 페이지에 이미 해당 변경 이후의 기록이 반영되었다고 해석하므로 과거 after-image로 덮어쓰지 않는다.

프로그램의 read miss 4가 장치의 물리 읽기 4를 증명하는가?

답과 이유 보기

아니다.

정한 버퍼 모형의 계수이며 OS 캐시와 장치 처리의 실제 계수는 따로 측정해야 한다.

commit 응답 전에 장애가 나면 클라이언트는 항상 실패로 재시도해도 되는가?

답과 이유 보기

아니다. 커밋됐지만 응답이 유실됐을 수 있다.

내구 상태와 응답 관찰은 별개이며 요청 식별자·결과 확인 같은 재시도 계약을 검토해야 한다.

한 단계 더

장애 지점, 영속 로그, 영속 pageLSN, 응답 여부, 재시작 결과를 다섯 열로 적어 보자. 이후 여러 트랜잭션과 미커밋 페이지 쓰기를 허용할 때 왜 undo와 복구 로그가 필요한지 앞 단원과 연결한다. 실제 fsync·파일 쓰기·장애 주입은 환경을 준비한 다음 수행할 확장 과제다.
