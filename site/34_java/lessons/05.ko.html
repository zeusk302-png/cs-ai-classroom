소단원 5.1

override와 dispatch

같은 변수 타입으로 부르는 메서드가 왜 다른 결과를 낼까?

준비 개념과 학습 목표

준비 개념

  • 클래스와 인스턴스

  • 메서드의 매개변수 타입

  • 참조 변수

학습 목표

  • overload 선택과 override 구현 선택을 나눈다.

  • 상위 타입 참조와 실제 객체 타입을 함께 추적한다.

  • static·private·super를 일반 동적 호출과 구별한다.

1. 호출을 두 단계로 읽기

Java에서 호출문에 맞는 메서드 선언을 고르는 단계와 실제 객체의 구현을 찾는 단계는 구별된다. 먼저 컴파일 시점에는 참조와 인자의 정적 타입, 접근 범위와 매개변수 목록을 사용한다. 이름이 같지만 매개변수 목록이 다른 overload는 이 단계에서 선택한다. 그 뒤 일반 인스턴스 호출은 실제 대상 객체의 클래스에서 override된 구현을 찾는다.

Base b = new Extra()라면 b의 정적 타입은 Base이고 대상 객체는 Extra이다. Extra가 Base의 public int value()를 정확히 override했다면 b.value()는 Extra의 구현을 사용하는 것으로 추적한다. 참조를 Base로 바꾸어 부르는 cast는 객체를 Base로 새로 만들지도 않고 override를 취소하지도 않는다. 여기서는 null이 아닌 객체와 일관되게 작성된 클래스들을 가정한다.

2. 선언 조건과 구별할 호출

Override는 같은 이름만으로 성립하지 않는다. 이 단원의 비제네릭 예에서는 같은 매개변수 목록을 가지며 반환 타입과 접근 범위, checked exception 조건도 맞아야 한다. public 메서드를 private으로 좁힐 수 없고 checked exception을 더 넓게 선언할 수도 없다. @Override를 붙이면 의도한 override가 성립하지 않는 선언을 컴파일러가 지적하도록 할 수 있다.

Static 메서드는 객체의 실행 타입으로 override하지 않고 선언 타입에 따라 선택되는 hiding 규칙을 쓴다. 혼동을 피하려면 Base.label()처럼 클래스 이름으로 호출하자. Private 메서드는 기술적인 의미에서 override되지 않으며 final 메서드는 override를 금지한다. Extra 구현 안에서 super.value()를 부르는 것은 상위 구현을 명시적으로 사용하는 특별한 호출이다.

3. 표로 계산하는 자체 예제

Base.value()는 4 를 반환하고 Extra.value()는 super.value()+3 을 반환한다고 하자. Base b = new Extra()에서 b.value()는 Extra로 가서 4+3=7 이 된다. Extra를 Base로 cast한 참조에서도 일반 value() 호출은 7 이다. 이 결과는 객체의 구현 선택과 super의 상위 구현 사용을 모두 추적해야 설명된다.

Base.label()은 "B", Extra.label()은 "E"를 반환하는 static 메서드라고 따로 정한다. 이 경우 클래스 이름에 따라 각각 B와 E가 된다. int value(int x)를 Extra에 추가하는 것은 매개변수 없는 value()의 override가 아니다. 실제 컴파일러 실행은 하지 않았으므로 아래 완전한 콘솔 코드의 결과는 공식 규칙에 따른 종이 예상으로 기록한다.

class Base {
  public int value() { return 4; }
  public static String label() { return "B"; }
}
class Extra extends Base {
  @Override public int value() { return super.value() + 3; }
  public static String label() { return "E"; }
}
public class Main {
  public static void main(String[] args) {
    Base b = new Extra();
    System.out.println(b.value());
    System.out.println(((Base)b).value());
    System.out.println(Base.label() + Extra.label());
  }
}

중간 과정을 따라가는 예제

Main.java에 적는 앞의 자체 코드에서 세 출력 줄을 종이로 예측하고, value() 호출마다 정적 타입과 실행 타입을 적어라.

  1. b는 Base 타입 변수이지만 생성한 대상은 Extra 하나이다. value()의 접근 가능한 선언을 Base에서 확인한다.

  2. 일반 인스턴스 호출은 실제 Extra의 value()로 연결된다. Extra 내부 super.value()는 Base 구현의 4 를 반환한다.

  3. 3 을 더해 첫 줄 7 을 얻는다. cast는 같은 Extra 객체 참조의 정적 타입을 확인할 뿐 객체를 바꾸지 않는다.

  4. 두 번째 일반 호출도 Extra 구현을 사용하므로 7 이다. static label은 Base와 Extra를 명시해서 B와 E를 얻는다.

  5. 세 줄은 7,7,BE이다. 파일·클래스·main의 문맥은 명시했지만 javac/java 실행 확인은 수행하지 않았다.

예상 출력은 각 줄에 7, 7, BE이다. 실제 실행 로그가 아니라 호출 규칙의 종이 추적이다.

종이와 본문으로 직접 해보기

Extra.value()를 super.value()*2 로 바꾸면 b.value()와 ((Base)b).value()를 구하라. Base에 value(Number n), value(Integer n)가 있다고 가정하고 Number n=Integer.valueOf(2)로 호출할 때 어떤 매개변수 선언을 선택하는지 적어라.

힌트 보기

반환식만 바꾸면 4×2 가 된다. overload는 인자 변수 n의 정적 타입으로 선택하며 객체의 런타임 숫자 클래스만 보고 고르지 않는다.

풀이 보기

두 value() 결과는 모두 8 이다. b.value(n)의 overload는 Number 매개변수를 선택한다. 선택한 시그니처의 구현이 하위 클래스에서 override되었는지는 다음 동적 선택 단계의 질문이다.

오해와 반례

상위 타입으로 cast하면 모든 호출은 상위 클래스 구현으로 돌아간다.

같은 Extra 객체를 Base로 cast한 두 번째 value()도 7 이라는 반례가 있다. 일반 인스턴스 호출의 override와 super 호출, static hiding, overload의 정적 선택을 따로 구별해야 한다.

자기점검

value(int x)는 value()의 override인가?

답과 이유 보기

이 예에서는 아니다.

매개변수 목록이 달라 overload이며 매개변수 없는 선언을 대체하지 않는다.

public을 private으로 줄인 override는 허용되는가?

답과 이유 보기

허용되지 않는다.

원래 공용 호출자의 접근 가능성을 줄이는 선언은 JLS override 요구를 만족하지 않는다.

같은 Extra 객체의 참조를 Base로 바꾸면 객체도 새로 만들어지는가?

답과 이유 보기

아니다.

참조의 정적 타입과 대상 객체의 클래스는 다른 정보다.

한 단계 더

Base 배열에 new Base()와 new Extra()를 넣고 value()를 순서대로 부르면 4 와 7 을 예상할 수 있다. 이 방식으로 공통 호출과 다른 구현을 연결한다. 이후에는 생성자 안에서 override 가능한 메서드를 부르는 경우처럼 상태 초기화 순서가 추가되는 문제를 별도로 검토해야 한다. 여기서는 객체 초기화·JVM 최적화·성능을 측정하지 않았다.

소단원 5.2

abstract class·interface

공통 상태를 나누는 일과 공통 역할을 약속하는 일은 어떻게 다를까?

준비 개념과 학습 목표

준비 개념

  • 인스턴스 상태

  • 메서드 선언과 본문

  • 클래스의 extends

학습 목표

  • 추상 클래스의 상태·생성자와 미구현 메서드를 설명한다.

  • interface 구현의 공용 계약을 읽는다.

  • 다중 역할과 클래스 단일 상속을 구별한다.

1. 완성되지 않은 공통 골격

Abstract class는 직접 인스턴스화할 수 없는 클래스이며 공통 상태, 생성자, 구현된 메서드와 abstract 메서드를 함께 둘 수 있다. 추상 메서드는 본문을 제공하지 않고 구현 의무를 남긴다. 구체 클래스가 그 의무를 충족하면 그 클래스의 객체를 만들 수 있으며 상위 추상 클래스의 초기화도 실행된다는 의미를 가진다.

예를 들어 AbstractMeter가 private final int start를 보존하고 start()로 읽으며 abstract int read()를 선언한다고 하자. OffsetMeter는 start()+5 로 read를 구현할 수 있다. AbstractMeter에 변수가 있다는 사실이 모든 하위 클래스에 직접 필드 변경 권한을 주지는 않는다. 공통 불변식을 유지하도록 접근 경계를 설계해야 한다.

2. 역할을 약속하는 interface

Interface Readable에 int read()를 본문 없이 선언하면 이 선언은 공용 추상 인스턴스 메서드이다. 구현 클래스의 read는 public이어야 한다. 역할 타입 Readable 변수에 다른 구현 객체를 담으면 같은 계약으로 읽을 수 있다. 컴파일러가 메서드 타입을 확인해도 단위나 값의 의미까지 자동으로 검사하지는 않는다.

Interface는 각 객체의 변경 가능한 인스턴스 필드를 선언하는 장소가 아니다. 인터페이스 필드는 public static final이며 클래스의 객체별 저장 상태와 구별한다. 현대 Java interface에 default/static/private 구현이 있을 수 있으므로 본문이 절대 없다고 외우면 안 된다. 이 단원 기본 예제는 Java8 의 abstract와 default 수준만 사용하며 다른 기능의 도입 시기를 실행 환경처럼 주장하지 않는다.

3. 상속 수와 설계 선택

Java 클래스는 클래스 상위를 하나만 extends하지만 여러 interface를 implements할 수 있다. 동일 객체가 읽기 역할과 이름 표시 역할을 모두 제공할 수 있다는 뜻이다. 추상 클래스도 interface를 구현하면서 일부 메서드 의무를 다음 구체 클래스에 남길 수 있다. 모든 인터페이스 의무가 무조건 한 클래스의 새 본문에 있어야 하는 것은 아니고 적절한 상속 구현도 사용할 수 있다.

공통 상태와 초기화·확장 규칙을 긴밀하게 공유할 때 추상 클래스 골격이 도움이 된다. 여러 독립 구현에 같은 역할 계약을 주려면 interface가 자연스러운 경계가 될 수 있다. 어느 쪽이 항상 더 좋은지는 정해져 있지 않다. 코드 재사용, 대체 가능한 동작, 저장 상태 노출, 클래스 상속 한도와 변경 영향을 함께 검토한다.

중간 과정을 따라가는 예제

Readable은 public int read()를 약속한다. AbstractMeter는 start=7 을 보존하고 read가 abstract이다. OffsetMeter는 AbstractMeter를 extends하고 Readable을 implements하며 public read()에서 start()+5 를 반환한다. Readable r=new OffsetMeter(7)의 값을 추적한다.

  1. Readable 변수는 역할 계약을 보고 read()를 호출할 수 있다. 클래스 필드나 임의의 추가 메서드가 역할 타입에 자동으로 보이는 것은 아니다.

  2. OffsetMeter(7)는 상위 초기화로 start=7 을 보존한다. start가 private이면 start() 같은 공개한 접근 메서드로 읽는다.

  3. OffsetMeter의 read 구현은 public이고 정수 반환 타입을 맞춰 추상 의무를 충족하는 것으로 모델링한다.

  4. 호출은 OffsetMeter.read로 가서 7+5=12 를 반환한다.

  5. new AbstractMeter(7)는 추상 클래스를 직접 만들려는 선언이므로 허용되지 않는 종이 판정이다. 실제 소스 생성이나 컴파일은 수행하지 않았다.

역할을 통한 읽기 값은 12 이다. 추상 골격의 상태 초기화와 구체 구현의 의무 충족을 모두 따져야 하며 interface 자체에 start 저장 슬롯을 넣었다는 뜻은 아니다.

종이와 본문으로 직접 해보기

또 다른 구체 구현 TwiceMeter가 start()*2 를 반환하면 start=7 에서 결과를 구하라. Readable 외에 Named의 String name()도 구현할 때 public 이름 메서드가 필요한 이유와 클래스 두 개를 extends하려는 경우를 분류하라.

힌트 보기

두 역할의 공용 의무와 클래스 상속 개수를 각각 체크한다. 같은 객체가 두 역할을 제공하는 것과 클래스 상위를 둘 갖는 것을 구별한다.

풀이 보기

TwiceMeter의 값은 14 이다. Named도 공용 name 계약을 구현해야 하므로 적절한 public 메서드가 필요하다. 여러 interface 구현은 가능하지만 Java 클래스 상위 두 개를 extends하는 선언은 허용되지 않는다.

오해와 반례

Interface에는 모든 상태와 구현이 없고 abstract class에는 반드시 abstract 메서드가 있다.

Interface에는 static final 필드와 default 등의 구현이 있을 수 있다. Abstract class는 추상 메서드가 없어도 abstract로 선언하여 직접 생성을 막을 수 있다. 기본 역할과 객체별 상태를 구별하는 설명이 이 단순 암기보다 정확하다.

자기점검

상속계층과 대체 가능성

하위 클래스가 타입 검사에 통과했는데도 기존 호출자가 왜 망가질까?

준비 개념과 학습 목표

준비 개념

  • 전제조건과 결과 보장

  • 상위 타입 변수

  • 상태 불변식

학습 목표

  • 명목 상속과 행동 대체가능성을 구별한다.

  • 전제 강화와 결과 약화의 반례를 찾는다.

  • 공용 계약과 특정 구현의 확장 약속을 나눈다.

1. 호출자가 믿을 수 있는 것

클래스 계층에서 extends를 선언하면 언어의 타입 관계가 생긴다. 행동 대체가능성은 더 강한 요구로, 상위 타입의 계약을 믿고 올바르게 작성한 호출자가 하위 객체로 바꾸어도 그 계약을 잃지 않는다는 뜻이다. 컴파일러가 메서드 선언을 확인했다고 모든 동작 약속까지 검증한 것은 아니다.

공용 계약은 모든 구현에 대해 호출자가 믿을 수 있는 조건이다. 특정 상위 구현이 내부적으로 어떤 보조 메서드를 몇 번 부르는지는 확장자를 위한 별도 약속일 수 있다. 그 내부 순서를 의존하면서도 문서화하지 않으면 상위 구현의 작은 변경이 하위 동작을 깨뜨릴 수 있다. 공용 약속과 재정의 가능한 골격의 약속을 따로 쓰는 이유다.

2. 입력은 더 요구하지 않고 결과는 덜 주지 않기

상위 Clock의 next(n)이 n∈{0,1,2,3}를 입력으로 허용하고 결과 n+1 을 약속한다고 하자. 하위 구현이 n≥2 만 처리하겠다고 새 전제를 요구하면 기존 호출자의 합법적 n=1 을 거부한다. 이것은 전제 강화의 반례이다. 하위 구현이 -1 도 처리하는 것은 기존 입력을 그대로 처리한다는 조건 아래 전제 완화가 될 수 있다.

결과 조건도 원래 합법 입력에 대해 유지해야 한다. 결과를 n 이상 아무 수로 바꾸면 n+1 이라는 원래 정확한 보장을 잃는다. 전제를 넓혀도 원래 입력에서 보장을 약하게 해서는 안전한 대체라고 말할 수 없다. 이 조건은 단순 반환 숫자뿐 아니라 예외와 상태 변경, 객체 불변식, 관찰 가능한 연산 이력까지 포함하여 검토해야 한다.

3. 실패 계약과 불변식

잔액이 음수가 되지 않는 객체에서 출금 실패가 잔액을 바꾸지 않는다고 약속했다면 하위 구현도 그 약속을 지켜야 한다. 먼저 잔액을 차감한 뒤 실패를 반환하면 반환 타입은 boolean으로 같아도 상태 계약은 다르다. 타입 문법에 보이지 않는 계약 위반을 입력·이전 상태·결과·다음 상태 표로 찾을 수 있다.

Java override의 checked exception·접근·반환 타입 제한은 일부 형식 조건을 검사한다. 문서의 정상 종료나 오류 의미까지 자동으로 검증하는 것은 아니다. 상위 계약에서 실패를 명시적으로 허용했다면 실패 반환 자체가 위반은 아니며, 어느 입력에 어떤 실패와 효과를 약속했는지 먼저 읽어야 한다. 더 빠르다는 주장도 실측 근거 없이 행동 계약의 증명처럼 쓰지 않는다.

중간 과정을 따라가는 예제

기본 next의 입력은 {0,1,2,3}, 결과는 n+1 이다. 후보 A는 {2,3}만 받아 n+1 을 돌려주고, 후보 B는 {-1,0,1,2,3}에서 n+1 을 돌려주며, 후보 C는 원래 입력에서 n을 돌려준다. 종이 계약 기준으로 판정하라.

  1. 상위 계약에서 합법인 입력 집합 P={0,1,2,3}을 먼저 적는다. 출력 조건은 각 n에서 정확히 n+1 이다.

  2. A에는 0 과 1 이 빠져 있다. n=1 호출이 상위에는 합법이지만 A에는 불법이므로 전제 강화로 탈락한다.

  3. B의 입력 집합은 P를 포함한다. 원래 입력 각각의 출력은 1,2,3,4 로 상위와 같으므로 이 숫자 계약은 보존한다.

  4. C는 입력을 받아도 n=0 에서 결과 0 을 주어 상위의 1 과 다르다. 결과 보장 위반으로 탈락한다.

  5. B의 통과는 여기 명시한 순수 숫자 계약에 대한 판정이다. 실제 상태·예외·수명·이력 약속이 있으면 그것까지 검토해야 전체 대체가능성을 말할 수 있다.

A와 C는 반례가 있고 B는 명시한 숫자 계약을 보존한다. 실제 프로그램 전체에 대한 대체가능성 시험이나 형식 증명을 수행한 것은 아니다.

종이와 본문으로 직접 해보기

잔액 5 에서 withdraw(7)는 false이고 잔액을 5 로 유지한다고 상위 계약에 적혀 있다. 하위 구현이 false와 잔액-2 를 남기는 경우를 표로 판정하라. next의 결과 조건을 원래부터 n보다 큰 정수라고 정했다면 n+2 구현은 어떠한가?

힌트 보기

실패의 반환값과 이후 상태를 두 열에 적는다. 원래 보장이 정확한 값인지 가능한 값의 집합인지 먼저 확인한다.

풀이 보기

false는 같지만 잔액-2 는 실패 시 불변 상태와 음수 금지 불변식을 위반한다. 반대로 결과가 처음부터 n보다 크기만 하면 n+2 는 그 숫자 결과 조건을 만족한다. 계약을 n+1 에서 바꾸어 놓고 같은 판단을 반복하면 안 된다.

오해와 반례

extends와 @Override를 적으면 행동 대체가능성이 모두 증명된다.

n=1 을 거부하는 A나 false와 함께 잔액을-2 로 바꾸는 구현도 형식만 맞출 수 있다. 타입 관계와 선언 검사는 입력·결과·상태·이력의 의미 검토를 대신하지 않는다.

소단원 5.4

default method와 설계 선택

두 역할이 같은 기본 구현을 주면 어느 것을 따라야 할까?

준비 개념과 학습 목표

준비 개념

  • interface의 추상 메서드

  • override

  • 클래스와 interface 계층

학습 목표

  • default 구현의 적용과 우선순위를 종이 판정한다.

  • 무관한 두 default 충돌을 명시적으로 해결한다.

  • 문법 충돌 해결과 의미 계약 만족을 구별한다.

1. 역할에 기본 구현 더하기

Default method는 interface에 있는 인스턴스 구현이며 구현 클래스가 적절한 자기 구현을 제공하지 않을 때 사용할 수 있다. Java8 부터 제공되는 이 기본 기능으로 공통 동작을 표현할 수 있다. 다만 객체별 변경 상태를 interface 필드에 저장하는 수단은 아니고 구현 객체가 제공하는 메서드를 통해 동작할 수도 있다.

예를 들어 BaseRole의 default int level()이 1 이고 ChildRole extends BaseRole이 level을 2 로 override한다면 ChildRole을 구현한 객체에는 더 구체적인 ChildRole 구현을 적용한다. 같은 기본 선언을 여러 경로로 물려받는 일 자체와 서로 다른 기본 선언이 경쟁하는 일은 구별해야 한다. 상속 화살표와 실제 메서드 선언의 위치를 함께 표시하면 판단이 쉬워진다.

2. 클래스 구현과 충돌

클래스 계층에 적절한 public concrete level 구현이 이미 있으면 interface default보다 클래스 구현이 우선한다. 그러나 상위 클래스가 abstract level을 남겼다면 default만으로 그 구체 클래스 의무가 자동 해결된다고 단정하면 안 된다. 추상 클래스 계층의 의무와 interface의 기본 구현 조건을 별도로 확인한다. 이 단원은 단순 비제네릭 동일 시그니처만 비교한다.

무관한 Left와 Right가 각각 default level을 1 과 4 로 제공한다면 둘을 implements하는 클래스는 충돌을 자기 override로 해결해야 한다. 첫 번째로 적힌 interface가 자동 승리하는 규칙은 아니다. 직접 상위 interface의 기본 구현을 명시할 때 Left.super.level() 같은 특별한 표기를 쓸 수 있다. 여기서는 직접 implements하는 무관한 두 interface를 사용하여 복잡한 간접 경로 호출을 피한다.

3. 합쳐도 약속은 검토하기

Resolved가 public level()에서 Left.super.level()+Right.super.level()을 반환한다면 숫자는 1+4=5 이다. 이는 문법적인 충돌을 명시적으로 해결하는 자체 예제이다. 실제 소스와 main을 적을 수 있지만 컴파일러를 실행하지 않았으므로 규칙에 따른 종이 예상만 기록한다.

숫자를 더할 수 있다는 것이 두 역할의 의미 계약도 모두 지킨다는 증거는 아니다. Left의 level이 반드시 1 이라고 문서에 약속했다면 5 는 그 계약을 깨뜨린다. 기본 구현의 선택뿐 아니라 공용 약속의 호환성을 확인해야 한다. 새 default 추가는 기존 계층과 충돌을 만들 수도 있으므로 모든 interface 변화가 무조건 안전한 진화라고 설명하지 않는다.

interface Left { default int level() { return 1; } }
interface Right { default int level() { return 4; } }
class Resolved implements Left, Right {
  @Override public int level() {
    return Left.super.level() + Right.super.level();
  }
}
public class Main {
  public static void main(String[] args) {
    Left x = new Resolved();
    System.out.println(x.level());
  }
}

중간 과정을 따라가는 예제

위 Main.java 자체 예제에서 level 호출을 추적한다. 이어 자기 override를 제거한 경우와 public concrete level=9 인 상위 클래스를 extends하는 경우를 분류하라.

  1. Left 참조 x의 실제 객체는 Resolved이고 자기 public override가 있으므로 그 구현을 선택한다.

  2. Left.super.level()은 직접 상위 Left의 기본 구현 1 을 사용하고 Right.super.level()은 Right의 4 를 사용한다.

  3. 1+4=5 이므로 main 출력의 종이 예상은 5 이다. 클래스 자기 구현이 충돌을 해결한 상태다.

  4. Resolved의 override를 없애고 다른 상위 구현도 없으면 무관한 두 기본 구현이 경쟁하여 선언을 허용하지 않는 것으로 판정한다.

  5. 대신 상위 클래스에 적절한 public concrete level=9 가 있고 자기 override가 없으면 클래스 구현을 사용하여 9 가 된다. 실제 컴파일 성공·실패 로그는 미수행이다.

자기 합산 구현은 5, 구현 없는 무관한 default 둘은 충돌, 적절한 구체 상위 클래스 구현이 있는 경우는 9 이다. 형식 선택 규칙과 역할 의미는 별도 검토 대상이다.

종이와 본문으로 직접 해보기

BaseRole default1, ChildRole extends BaseRole의 override2, OnlyChild implements ChildRole이며 자기 구현은 없다. 반환값을 구하라. BaseRole이 1 만 반환한다고 공용 계약에 명시했을 때 ChildRole의 2 가 문법상 허용되어도 무슨 문제가 생기는지 적어라.

풀이 보기

OnlyChild의 종이 반환값은 2 이다. 그러나 BaseRole 공용 계약이 정확히 1 을 약속했다면 2 는 행동 대체가능성 위반이다. 문법의 override 가능성과 의미 계약의 보존은 같은 검사가 아니다.

오해와 반례

두 default가 충돌하면 implements에 먼저 적은 interface가 선택되고 그것으로 계약도 해결된다.

무관한 Left와 Right의 동일 level default는 순서만으로 선택되지 않는다. 명시적 override로 충돌을 해결해도 합산 5 가 정확한 1 의 계약을 깨뜨릴 수 있다. 구조적 선택과 의미 호환성을 각각 검사한다.

인터페이스 추가 구현 없이 공통 보조 동작을 제공할 수 있는 장점과 새 충돌·의미 의존성의 비용을 표로 적자. 충돌 그림에는 부모 역할, 자식 역할, 실제 선언과 클래스 구현을 따로 표시한다. 간접 상위의 Interface.super 호출, Object 메서드와 같은 특수 경우는 JLS의 추가 제한이 있으므로 이 직접 상위 예제의 규칙만으로 일반화하지 않는다.
