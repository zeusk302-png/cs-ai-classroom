소단원 3.1

메서드·overload

같은 이름의 메서드를 부르는데 왜 다른 본체로 들어갈까?

준비 개념과 학습 목표

준비 개념

  • 메서드 선언은 이름·매개변수·반환 타입·본체를 정한다. 인수는 호출 쪽 식이고 매개변수는 호출마다 새로 생기는 지역 변수다.

  • int는 원시 정수 타입이고 Integer는 그 값을 감싸는 참조 타입이다. int에서 long으로의 확장과 int에서 Integer로의 boxing은 다른 변환이다.

학습 목표

  • 선언과 호출, return과 출력의 역할을 구별한다.

  • 단순 overload를 정적 인수 타입으로 선택한다.

  • boxing보다 먼저 적용되는 호출 단계를 설명한다.

메서드 본체에 들어가지 않았는데 앞 인수의 효과가 남을 수 있는가?

앞 본문은 kind와 pick의 서명을 정적 타입으로 골랐다. 새 모형은 선택한 서명과 실행한 인수 평가를 다른 장부에 적는다. static int combine(int x,int y)는 본체 진입 때 로그에 B를 붙이고 10*x+y를 반환한다. static int mark(int v)는 로그에 M을 붙인 뒤 v를 반환한다. static int fail()은 로그에 F를 붙인 뒤 IllegalArgumentException을 던진다. 로그는 순차 문자열 사건을 표기한 종이 장부이며 실제 외부 출력이 아니다.

combine(mark(2),fail())는 첫 인수의 mark가 끝나고 둘째 fail에 도착한다. 둘째가 예외를 던지면 combine 본체는 시작하지 않아 B가 없다. 그러나 앞 M은 자동 취소되지 않는다. fail()과 mark(2)의 위치를 바꾸면 F 뒤에서 평가가 중단돼 M도 없다. 예외 때문에 정상 반환이 없다는 사실을 앞 효과가 전혀 없었다는 사실로 바꾸지 않는다.

기존 pick(Object)/pick(String)에는 여전히 정적 선택이 적용된다. 인수 평가 순서를 이해했다고 실행 객체에 따라 overload를 재선택할 수는 없다. 아래 모형의 모든 정상 숫자 계산은 int 범위 안이고 메모리·연결 오류는 제외한다. 각 예제·연습은 빈 로그에서 독립적으로 시작한다.

먼저 확인할 개념
  • overload의 정적 서명 선택

    인수 평가와 실행 본체 진입을 서명 선택과 분리한다.

  • 매개변수 값의 생성

    정상 인수 값이 모여야 새 호출의 매개변수에 전달된다.

메서드에 계약 붙이기

static 메서드는 클래스 이름으로 호출할 수 있고 이 예제처럼 같은 클래스 안에서는 이름으로 호출한다. 반환 타입 String은 결과가 문자열 참조값이라는 뜻이다. return은 현재 호출을 끝내고 값을 전달하며 println은 화면 출력이라는 효과를 만든다. 둘을 같은 동작이라고 부르면 호출 결과를 조합할 수 없다.

입력 타입만으로 모든 업무 조건을 표현하지는 않는다. 수량 메서드에 int를 넘길 수 있어도 음수 금지 같은 사전조건은 별도로 검사하거나 문서화해야 한다. 반환 타입이 있는 메서드는 정상 완료 경로에서 값을 반환해야 하며 무한 반복/예외 경로와 정상 return을 구별한다.

오버로드는 이름 공유와 정적 선택

overload는 같은 이름으로 구별되는 매개변수 서명을 제공한다. 여기서는 제네릭 없는 단순 서명만 다룬다. 반환 타입만 다르게 만든 같은 인수 서명 두 개는 overload로 구별할 수 없다. 호출 위치에서 인수 식의 정적 타입과 적용 가능한 변환을 보고 선택한다.

고정 인수 개수의 엄격 호출 단계에서는 boxing/unboxing을 사용하지 않는다. kind(int 값)에는 int→long 확장으로 kind(long)이 적용되어 이후 boxing 단계의 kind(Integer)까지 가지 않는다. 반면 Integer 식은 kind(Integer)에 바로 맞는다. 숫자 값이 같다는 사실은 정적 타입 차이를 없애지 않는다.

실행 객체 타입과 혼동하지 않기

Object text="cat"에서 pick(text)의 인수 정적 타입은 Object이므로 pick(Object)가 선택된다. (String)text는 식 타입을 바꾸어 pick(String)을 고르게 한다. 실제 객체가 String이라는 이유만으로 모든 overload가 실행 시 다시 선택되는 것은 아니다.

이 예제의 pick들은 static이며 상속 overriding을 사용하지 않는다. 인스턴스 메서드 overriding은 컴파일 때 정한 서명 뒤 실행 객체 클래스에 따른 본체 선택과 관련되어 다른 단계다. 아래 네 출력은 Java SE11 규칙으로 선택했고 실제 JDK11 실행으로도 확인했다.

public class Methods03 {
    static String kind(long x) { return "long"; }
    static String kind(Integer x) { return "Integer"; }
    static String pick(Object x) { return "Object"; }
    static String pick(String x) { return "String"; }
    public static void main(String[] args) {
        int n=3; Integer boxed=3; Object text="cat";
        System.out.println(kind(n));
        System.out.println(kind(boxed));
        System.out.println(pick(text));
        System.out.println(pick((String)text));
    }
}

M/F는 인수 평가가 만든 효과이고 B는 combine 본체의 효과다. 위 두 예외 행은 같은 예외 종류라도 로그가 달라 호출 전체의 관찰이 같지 않다. 마지막 행은 앞 본문의 static pick 선언을 사용한다.

중간 과정을 따라가는 예제

아래 완전 소스의 네 호출에서 선택한 서명과 출력을 추적하라.

  1. n은 int라 kind(long)이 엄격 호출 단계에서 적용되어 long을 반환한다.

  2. boxed는 Integer라 kind(Integer)를 직접 선택하여 Integer를 반환한다.

  3. text 식은 Object라 pick(Object)가 Object를 반환한다.

  4. (String)text는 String 식이고 실제 객체도 호환되어 pick(String)이 String을 반환한다.

실제 stdout 네 줄은 long, Integer, Object, String이다.

조건을 바꾸어 비교하기

뒤 인수 실패가 앞 효과를 지우지 않는다

combine(mark(2),fail())의 평가와 반환을 단계별로 적어라.

  1. mark(2)가 M을 기록하고 첫 인수 값 2를 만든다.

  2. fail()이 F를 기록한 뒤 예외로 끝나 정상 둘째 값과 combine 진입이 없다.

로그는 MF이고 정상 결과 27 또는 0을 반환하지 않는다. B는 없다.

비교할 점

서명이 선택됐음과 본체가 실행됐음은 다른 단계다.

참조 정적 타입과 명시 변환

앞 본문의 pick(Object)/pick(String)에서 Object s="cat"이다. pick(s), pick((String)s), pick(null)을 독립 비교하라.

  1. s 식의 타입은 Object이고 변환 식은 String이다.

  2. null은 두 참조 매개변수에 적용 가능하지만 String이 더 구체적이다.

선택은 각각 Object, String, String이다. 같은 실제 문자열 대상만으로 첫 선택이 바뀌지 않는다.

비교할 점

실행 로그의 순서를 검사하는 일과 정적 overload 선택은 서로 다른 검토다.

종이와 본문으로 직접 해보기

pick(null)은 위 Object/String 둘 중 무엇을 고르는가? 서로 상속 관계가 없는 String과 Integer 두 매개변수 overload에 null을 넘기면?

힌트 보기

null은 참조 타입에 대입 가능하지만 가장 구체적인 적용 서명이 필요한가를 본다.

풀이 보기

위 pick(null)은 더 구체적인 String을 고른다. String/Integer만 있으면 둘 다 적용 가능하고 더 구체적인 한쪽이 없어 모호한 호출 컴파일 오류다. 이 추가 컴파일 반례는 종이 분석이며 실행하지 않았다.

오해와 반례

실행 객체가 String이면 pick(Object 식)도 항상 String overload다.

실제 소스의 Object text 호출은 Object다. overload의 정적 선택과 overriding의 실행 선택을 구별해야 한다.

연습 1 · 값과 상태 예측

combine(mark(3),mark(1))과 combine(fail(),mark(3))을 각각 빈 로그에서 추적하라.

힌트 1

정상 호출은 왼쪽·오른쪽 인수가 끝난 뒤 본체다.

힌트 2

첫 실패 뒤 오른쪽은 평가되지 않는다.

풀이와 답 확인

  1. 첫 계획은 M/M/B를 기록하고 10*3+1=31을 반환한다.

  2. 둘째는 F만 기록하고 combine 본체와 mark(3)은 수행되지 않는다.

정상 로그 MMB와 값 31, 실패 로그 F와 예외다. 실제 Java 실행은 미수행이다.

흔한 오답에서 다시 생각하기

예외 호출도 두 인수 식이 먼저 모두 실행돼 FM이다.

왼쪽의 abrupt completion은 오른쪽 인수 평가를 중단한다.

연습 2 · 오류 찾아 고치기

보고가 “combine 본체가 미진입이므로 요청에는 효과가 없었다”라고 썼다. MF 사례에 맞춰 수정하라.

힌트 1

효과 주체를 인수와 본체로 나눈다.

힌트 2

앞 효과의 자동 롤백이 문서화됐는지 확인한다.

풀이와 답 확인

  1. 본체 B는 없지만 mark와 fail이 남긴 MF는 있다.

  2. 요청 실패와 외부 효과 취소를 별도로 기록하고 입력 평가가 효과를 만들지 않도록 설계하거나 별도 보상 계약을 둔다.

본체 미진입만으로 호출 전체 무효과를 증명하지 않는다.

흔한 오답에서 다시 생각하기

예외를 catch하면 앞 로그도 사라진다.

catch의 제어 복구는 이미 수행한 쓰기의 자동 역연산이 아니다.

연습 3 · 직접 만들어 보기

인수 검증이 실패하면 업무 로그를 그대로 보존하는 combine 호출 계획을 구성하라. 검증은 문자열을 읽기만 하고 mark는 업무 기록을 만드는 것으로 정한다.

힌트 1

효과 있는 mark를 검증 전에 호출하지 않는다.

힌트 2

두 값이 모두 준비된 정상 갈래에서 기록한다.

풀이와 답 확인

  1. 두 입력의 문법·범위를 읽기만 하는 단계에서 모두 검사하고 성공 후보 값 x/y를 만든다.

  2. 모두 성공한 뒤에만 mark 및 combine을 수행한다. 검증 실패는 이전 업무 로그를 보존한다.

읽기 검증·값 생성과 업무 효과 단계를 나눈다. 이후 효과 단계의 임의 실패까지 원자적으로 취소한다고 주장하지 않는다.

흔한 오답에서 다시 생각하기

검증 함수를 오른쪽 인수로 옮기면 앞 mark의 효과도 보호된다.

오른쪽 실패 전 왼쪽 효과가 먼저 남는 MF 반례를 다시 적용한다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

기존 Object/String pick에 pick(Integer)를 추가한 뒤 기존 소스의 pick(null)을 다시 번역한다. 결과가 그대로 String인가?

힌트 1

null은 Integer에도 적용 가능하다.

힌트 2

String과 Integer 사이에 더 구체적인 방향이 있는가?

풀이와 답 확인

  1. String과 Integer 모두 적용 가능하고 서로 하위 타입 관계가 없다.

  2. 둘 사이의 가장 구체적인 하나를 정할 수 없어 호출은 모호한 번역 오류다.

API에 overload를 추가하는 일이 기존 소스의 번역 가능성을 바꿀 수 있다. 실제 재컴파일은 미수행이다.

흔한 오답에서 다시 생각하기

새 overload는 옛 호출에 영향을 주지 않는 무조건적 확장이다.

정적 선택 후보 집합이 달라지므로 null 경계 입력을 포함해 검토한다.

내 말로 설명하기

정상 인수 두 개를 얻기 전에 본체를 실행하는가?

설명 기준 확인

이 고정 인수 호출에서는 먼저 왼쪽부터 인수를 평가하며 실패하면 본체로 넘어가지 않는다.

본체가 미진입이면 로그도 반드시 비어 있는가?

설명 기준 확인

아니다. 앞 인수 평가에서 효과가 생겼을 수 있다.

한 단계 더

새 overload 추가가 기존 소스의 재컴파일 선택을 바꿀 수 있음을 생각하자. null, 확장, boxing, varargs를 모두 고려하면 이름만 같다고 동등한 API가 아니다. 이 단원은 단순 고정 인수와 static 호출을 중심으로 설명했으며 제네릭 추론·가변 인수 전체 선택 규칙은 JLS의 추가 조건을 읽어야 한다.

소단원 3.2

값 전달과 참조값

배열 값이 바뀌는데도 왜 Java는 값 전달이라고 할까?

준비 개념과 학습 목표

준비 개념

  • 변수는 값을 저장하는 칸이며 배열 객체는 여러 원소를 저장하는 별도 객체다. 참조값은 객체를 가리키거나 null인 값이다.

  • a[0]=7은 가리킨 배열의 원소를 바꾸고 a=new int[]{8}은 변수 a의 참조값을 바꾼다. 두 대입의 대상이 다르다.

학습 목표

  • 매개변수의 값 복사를 그린다.

  • 참조 재대입과 객체 변경의 효과를 구별한다.

  • 공유 객체의 사전조건을 명시한다.

두 매개변수가 같은 배열이면 교환 계획은 무엇을 교환하는가?

앞 본문의 change는 매개변수를 재대입해도 호출자 변수는 유지된다는 사례였다. 새 swapRefs(int[] x,int[] y)의 본체는 int[] t=x; x=y; y=t;다. 이 절차는 새 지역 참조 칸을 교환하며 호출자 a와 b의 칸을 교환하지 않는다. swapFirst의 본체 int t=x[0]; x[0]=y[0]; y[0]=t;는 참조값을 통해 실제 배열 정수 저장을 바꾼다. 입력은 비null·길이 1 이상이며 단일 스레드다.

서로 다른 A=[2], B=[9]를 넘기면 swapFirst는 두 정수 값을 교환한다. 같은 A를 두 인수로 넘기면 t에 옛 2를 보관하고 같은 칸을 다시 읽고 쓰므로 A는 2를 유지한다. 반면 moveFirst라는 잘못된 합치기 계획 x[0]+=y[0]; y[0]=0;는 같은 객체에서 첫 값을 두 배로 만든 뒤 그 칸을 0으로 지워 결과가 다르다. 업무에서 두 대상이 반드시 달라야 한다면 참조 정체성의 전제를 명시하거나 먼저 거절한다.

새 부분 실패 모형 writeThenCheck는 x[0]=7을 먼저 수행한 뒤 y가 null이면 거절한다. y 검사를 뒤에 둔 사실은 앞 변경을 취소하지 않는다. 실패 시 x 보존을 요구한다면 두 입력의 전체 접근 조건을 쓰기 전에 검사해야 한다. 할당 실패·동시 변경·일반 거래 롤백 구현은 이 작은 순차 조건에 포함하지 않는다.

먼저 확인할 개념
  • 값 전달과 공유 객체 효과

    지역 참조 교환과 호출자 객체 변경을 분리한다.

  • 메서드의 전제·반환·효과

    정상 사전조건과 실패 보존을 본체 계약으로 적는다.

원시값도 참조값도 복사된다

호출은 인수 값을 계산하여 새 매개변수 칸에 넣는다. int x=3을 넘기면 숫자 3을 복사한다. 배열 변수 a를 넘기면 배열을 가리키는 참조값을 복사한다. 호출자 변수 칸 자체에 대한 별칭을 전달하는 것은 아니다.

복사된 참조값 둘은 같은 객체를 가리킬 수 있다. 따라서 메서드가 매개변수 참조로 배열 원소를 바꾸면 호출자도 같은 원소 변경을 관찰한다. 값 전달이라는 말은 객체 전체를 깊은 복사한다거나 외부 효과가 없다는 뜻이 아니다.

변수 칸과 객체 칸 그리기

change 안의 x=9는 새 지역 매개변수 칸만 바꾼다. a[0]=7은 두 참조가 공유한 기존 배열 원소를 바꾼다. 이후 a=new int[]{8}은 메서드 안의 a만 다른 배열로 이동시켜 호출자의 a에는 영향을 주지 않는다.

새 배열에 a[0]=10을 하면 새 배열만 바뀐다. 이 메서드에는 입력 배열이 null이 아니고 길이가 최소 1이라는 사전조건이 필요하다. null이나 빈 배열에서 같은 호출이 정상 완료한다는 주장을 하지 않으며 해당 예외 경로를 성공 증거로 삼지 않는다.

효과를 계약으로 기록하기

정상 종료 후 호출자의 원시 x는 유지되고 전달했던 배열의 0번 칸은 7이다. 다른 원소가 있다면 이 예제 메서드는 그 원소를 쓰지 않는다. 반환이 void라는 사실은 효과가 없다는 뜻이 아니므로 사후조건에 객체 변경을 적는다.

배열의 변경을 원치 않는 API에서는 필요한 내용을 복사하거나 읽기 계약을 지켜야 한다. final int[] a는 변수의 재대입을 막지만 a[0] 수정을 막지 않는다. 공유 배열에 동시에 접근한다면 이 순차 추적 외에 동기화와 가시성 조건이 추가된다.

public class Values03 {
    static void change(int x, int[] a) {
        x=9;
        a[0]=7;
        a=new int[]{8};
        a[0]=10;
    }
    public static void main(String[] args) {
        int x=3; int[] a={4};
        change(x,a);
        System.out.println(x+" "+a[0]);
    }
}

조건을 바꾸어 비교하기

지역 참조 교환과 대상 정수 교환

A=[2], B=[9]인 새 상태에서 swapRefs와 swapFirst를 각각 계획한다.

  1. swapRefs의 t/x/y는 호출 내부 칸이라 호출자 a/b는 그대로다.

  2. swapFirst는 t=2, A[0]=9, B[0]=2를 순서대로 쓴다.

첫 계획의 대상 값은 2/9를 유지하고 둘째는 A가 9, B가 2다. 호출자 참조는 둘 다 유지한다.

비교할 점

값 전달은 객체 수정 금지가 아니라 새 매개변수 칸의 독립성을 뜻한다.

검사보다 앞선 쓰기가 거절 뒤 남는다

새 A=[2], y=null에서 writeThenCheck(x,y)는 x[0]=7 후 y의 부재를 검사해 거절한다. 실패 시 A 보존 계약과 비교하라.

  1. 첫 쓰기는 유효 x의 A[0]을 7로 바꾼다.

  2. 그 뒤 y 부재 거절은 그 정수의 이전 값 2를 자동 복구하지 않는다.

계획은 실패하면서 A=[7]을 남겨 보존 계약을 위반한다. 먼저 두 입력의 존재·길이를 읽기 검사해야 한다.

소단원 3.3

String의 불변성

문자열을 바꿨는데 이전 이름이 그대로 남는 것은 왜일까?

준비 개념과 학습 목표

준비 개념

  • String 변수의 값은 문자열 객체의 참조값이다. 변수 재대입과 그 객체 내부 변경을 구별한다.

  • Java char는 UTF-16 코드 단위다. 보조 평면의 코드 포인트는 두 char의 surrogate pair로 표현될 수 있다.

학습 목표

  • 불변 객체와 변경 가능한 참조 변수를 구별한다.

  • 문자열 내용 비교와 참조 비교를 구별한다.

  • 코드 단위·코드 포인트·사용자가 보는 글자를 분리한다.

코드 포인트 두 개를 남기면 UTF-16 인덱스도 항상 2인가?

앞 본문의 웃는 얼굴 U+1F600은 두 char로 표현됐다. 새 문자열은 A, U+1F600, B를 연결한 s다. UTF-16 코드 단위의 순서는 0041/D83D/DE00/0042로 길이 4이고, 전체 코드 포인트 수는 3이다. substring(0,2)는 A와 높은 surrogate D83D만 남겨 원래 보조 문자 표현을 나눈다. 먼저 두 코드 포인트를 남기려면 끝 char 인덱스가 3이어야 한다.

offsetByCodePoints(0,2)는 이 s에서 char 끝 인덱스 3을 구한다. 그 인덱스로 substring(0,3)을 만들면 A와 완전한 보조 문자를 남긴다. 그러나 “두 코드 포인트”는 일반적인 “사용자가 보는 글자 두 개”와 같은 계약이 아니다. e와 결합 acute U+0301은 char 두 개·코드 포인트 두 개이며 이 단원은 화면 글자 분할이나 정규화를 실제 수행하지 않는다.

String은 불변이지만 변수의 재대입은 가능하다. cut=substring(...)는 원본 s의 값을 바꾸지 않는다. 불변 객체끼리 같은 내용을 만들었다는 사실도 반드시 같은 참조라는 뜻은 아니다. 특히 처리 결과의 참조 재사용 여부에 기대지 않고 문자열 내용 계약은 equals로 비교한다. null과 빈 문자열의 비교 정책은 별도다.

먼저 확인할 개념
  • UTF-16·substring·불변 문자열

    끝 인덱스의 단위와 원본 보존을 연결한다.

  • 참조값 복사

    문자열 결과를 새 지역에 대입해도 호출자 참조 칸은 독립이다.

객체 불변성과 변수 재대입

String 객체의 문자열 값은 만들어진 뒤 바뀌지 않는다. replace 같은 처리 결과를 변수에 다시 넣어도 원래 객체가 수정되는 것은 아니다. 다른 변수 alias가 원래 객체를 가리키고 있으면 원래 cat를 유지한다.

반면 s라는 변수를 다른 참조값으로 재대입할 수 있으므로 String s의 내용이 바뀌었다는 일상 표현을 엄밀하게 풀어야 한다. final String s는 s 재대입을 막는다. String 자체의 불변성과 final 변수의 제한은 별개의 근거다.

같음의 두 질문

==는 두 참조값이 같은 객체를 가리키는지 묻는다. equals는 문자열 내용을 비교한다. new String("cat")로 만든 객체는 alias가 가리킨 cat 객체와 구별되므로 ==는 false지만 내용 비교는 true다. 문자열 리터럴 공유로 ==가 우연히 참인 예제를 일반 비교 규칙으로 삼지 않는다.

null 참조에서 인스턴스 메서드를 호출하면 NullPointerException이 날 수 있다. 허용된 null을 함께 비교하는 설계라면 Objects.equals 등 계약이 있는 방법을 쓰거나 먼저 null을 검사한다. null과 빈 문자열은 다른 상태다.

길이의 단위 정하기

String.length()는 char 코드 단위 수다. 예제의 U+1F600은 유효한 두 surrogate를 사용하므로 length=2이고 전체 구간의 codePointCount=1이다. 이것이 화면 폭이나 사용자가 보는 글자 수가 1이라는 모든 경우의 법칙을 만들지는 않는다.

substring의 끝 인덱스는 제외되며 char 경계를 사용한다. surrogate pair 사이를 자르면 코드 포인트의 표현을 나눌 수 있다. 사용자 글자 단위 편집은 결합 문자·이모지 묶음까지 고려해야 하며 codePointCount만으로 모든 grapheme cluster를 센다고 설명하지 않는다.

준비 개념과 학습 목표

준비 개념

  • 문법 검사는 허용 문자열 모양을 확인하고 의미 검사는 업무 값의 범위를 확인한다. 이 단원은 수량 0…100만 허용한다.

빈 필드를 버린 뒤에는 원래 레코드의 형식을 증명할 수 있는가?

앞 본문의 수량 quantity는 ASCII 숫자 1..3개와 값 0..100을 요구했다. 새 기록은 id,quantity,note의 정확히 세 필드이며 id는 대문자 ASCII 한 글자, note는 비어도 되지만 쉼표는 허용하지 않는 자체 간단 형식이다. 따옴표·escape·일반 CSV는 다루지 않는다. null 원자료는 거절하고 trim하지 않는다. 쉼표 split의 limit=-1로 끝 빈 필드를 보존한 뒤 필드 수와 각각의 입력 계약을 검사한다.

원자료 A,007,은 세 필드 A/007/빈 note로 수용할 수 있다. 기본 split은 끝 빈 필드를 버려 두 필드만 남기므로 의도한 note 존재를 놓친다. 반대로 limit=3은 A,007,x,y를 마지막 필드 x,y로 합쳐 길이 3으로 만들 수 있다. 필드 개수만 검사하면 금지한 추가 구분자를 숨기므로 음수 limit와 정확 세 필드 조건을 함께 사용한다.

검증한 수량 값 7은 원자료 007과 다르다. quantity가 같으면 같은 품목 키라는 새 업무 정책을 정하면 007/7/0007의 관계를 검토해야 한다. 0007은 네 자리여서 먼저 문법에서 거절한다. 007과 7은 서로 다른 원자료이지만 같은 키 7이다. 원자료 보존·값 변환·중복 정책을 따로 기록하며 키 충돌 시 거절하거나 합칠지 명시한다. 아래 새 장부는 중복을 거절하고 기존 기록을 보존한다.

API의 문법과 업무의 문법

Integer.parseInt는 선택 부호 등을 포함하는 정수 문자열을 다루지만 우리 수량 계약은 null 금지, ASCII 숫자 1…3개, 부호/공백 금지, 값 0…100이다. API가 +7을 읽을 수 있어도 업무가 허용할 필요는 없다. 허용 입력 언어를 먼저 적으면 유니코드 숫자나 공백을 우연히 받아들이는 문제를 피할 수 있다.

raw 문자열을 곧바로 trim하여 버리면 앞 공백이 있었는지 확인할 수 없어진다. 계약이 공백 무시라면 원자료와 처리값을 분리하고 그 규칙을 기록한다. 이 예제는 trim하지 않으며 " 7"을 거절한다. 입력 검증은 출처 인증이나 모든 보안 요구를 대신하지 않는다.

단락 평가와 범위 보장

text==null || !text.matches(...)는 null일 때 오른쪽 메서드를 부르지 않는다. 문법을 통과한 길이≤3 ASCII 십진수는 0…999이므로 int 범위에 항상 들어간다. 이 조건 아래 parseInt의 표현 범위 실패를 별도 정상 경로로 기대할 필요가 없다.

그 뒤 n>100이면 업무 범위에서 거절한다. 007은 문법상 허용하고 값 7로 해석하는 정책이다. 문자열 길이만 확인하고 임의 긴 수나 문자를 parseInt에 넣는 일반 코드에서는 NumberFormatException을 명시적으로 처리해야 하며 이 작은 증명의 조건을 확대하면 안 된다.

필드와 오류도 데이터다

split의 첫 인수는 단순 문자 집합이 아니라 정규식이다. A,,를 쉼표로 나눌 때 limit=-1을 두면 뒤 빈 필드도 유지하여 세 필드가 된다. 기본 limit=0은 끝의 빈 필드를 버리므로 자료의 빈 값이 의미 있을 때 계약을 바꿀 수 있다. 이 예제는 따옴표/이스케이프가 있는 일반 CSV 파서가 아니다.

아래 완전 소스는 고정된 아홉 입력과 split 한 사례를 실행한다. catch는 우리가 명시적으로 던진 syntax/range 거절을 보고한다. 예외 관찰은 실패 입력을 정상 성공값으로 취급했다는 뜻이 아니며 실제 사용자 입력·대량 공격·교실 실험을 수행했다는 증거도 아니다.

public class Parse03 {
    static int quantity(String text) {
        if(text==null || !text.matches("[0-9]{1,3}"))
            throw new IllegalArgumentException("syntax");
        int n=Integer.parseInt(text);
        if(n>100) throw new IllegalArgumentException("range");
        return n;
    }
    public static void main(String[] args) {
        String[] tests={"0","007","100","101","+7"," 7","12x","",null};

            try { System.out.println(String.valueOf(text)+": "+quantity(text)); }
            catch(IllegalArgumentException e) {
                System.out.println(String.valueOf(text)+": rejected "+e.getMessage());
            }
        }
        System.out.println("split="+"A,,".split(",",-1).length);
    }
}

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

허용된 한 자리부터 세 자리 ASCII 숫자 문자열의 서로 다른 표현이 같은 정수로 모이는 경우를 0과 7에서 나열하라. 문법상 0000은 포함하지 않는다.

풀이와 답 확인

변환은 이 입력 언어에서 일대일이 아니다. 원자료의 유일성과 정수 키의 유일성은 서로 다른 정책이다.

힌트 1

문법 수용과 정수 키 충돌은 다른 단계다. 앞 mark 효과는 뒤 fail 예외가 자동 취소하지 않는다.

힌트 2

코드 포인트 이동으로 char 끝 인덱스를 구한다. 새 매개변수의 참조 재대입과 호출자 대입을 구별한다.

풀이와 답 확인

  1. 음수 limit split은 A/007/빈 note의 세 필드를 보존한다. quantity는 문법을 통과하여 값 7이지만 기존 정수 키 7과 충돌하므로 최종 레코드 처리는 중복 거절이다. 원자료 007을 기존 문자열 7과 다른 내용으로 보존할 수 있어도 키 충돌은 사라지지 않는다.

  2. P에서 quantity는 정상 7을 반환하고 mark가 M을 기록한다. 둘째 fail은 F를 기록한 뒤 예외를 던지므로 로그는 MF이며 combine 본체 B와 정상 반환은 없다. P는 업무 로그 보존을 만족하지 않는다.

  3. 읽기만 하는 전체 필드/수량 검사와 정수 키 중복 검사를 모두 먼저 수행한다. 현재 키는 중복이므로 mark/commit 없이 거절하여 기존 기록과 빈 업무 로그를 보존한다. 이후 효과 단계의 임의 실패까지 일반 거래 원자성을 구현한 것은 아니다.

  4. label의 코드 단위는 0041/D83D/DE00/0042다. offsetByCodePoints(0,2)는 끝 3을 주며 substring(0,3)은 A와 완전한 U+1F600으로 코드 단위 수 3·코드 포인트 수 2다. label 원본은 그대로다.

  5. 메서드 매개변수 note의 재대입은 호출자 변수 칸을 바꾸지 않는다. 새 String 결과를 반환하는 메서드의 정상 반환을 호출자 note=처리결과처럼 명시 대입해야 한다. 원래 참조를 가진 alias는 원래 불변 문자열을 유지한다.

raw는 형식/수량을 통과하지만 정수 키 중복으로 거절된다. P는 MF 효과와 예외를 남긴다. 전체 읽기 검증·중복 확인 뒤 효과를 두면 현재 요청은 기존 장부와 빈 로그를 보존한다. 앞 두 코드 포인트의 끝 char 인덱스는 3이며 반환 문자열을 호출자가 명시 대입한다.
