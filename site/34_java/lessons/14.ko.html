바깥 배열을 복사했는데 안쪽 자료도 독립적일까?

앞 본문에서 변수 칸의 재대입과 배열 원소 변경을 나누었다. 이제 두 단계 참조를 그린다. a는 바깥 배열 O1을 가리키고 O1의 두 원소는 각각 안쪽 배열 R1과 R2를 가리킨다. R1의 내용은 [1], R2의 내용은 [2]다. 바깥 참조 원소만 복사하여 b가 새 O2를 가리키게 하면 O1과 O2는 다르지만 두 바깥 배열의 원소가 가리키는 R1과 R2는 여전히 같다. 이는 자체 얕은 복사 계약이다.

같은 초기 상태에서 b[0][0] = 9는 공유 R1의 내용을 바꾸므로 a[0][0]도 9다. 반면 b[0] = new int[]{7}은 O2의 첫 참조 원소를 새 R3로 바꾸며 O1의 첫 참조는 R1에 남는다. 원소의 타입이 참조인 배열에서는 바깥 원소 변경과 더 안쪽 원소 변경을 따로 표시해야 한다.

프레임의 지역 변수 슬롯에 참조 값을 복사하는 것과 대상 객체를 복제하는 것도 다르다. JVM 규격은 추상 실행 영역을 정하지만 실제 프레임을 어떤 물리 공간에 배치하는지까지 이 그림으로 확정하지 않는다. O1 같은 이름은 실제 주소가 아니다. 각 예제와 연습은 명시한 초기 그래프에서 독립적으로 시작한다.

칸의 값과 대상의 내용

참조는 객체 자체가 아니라 객체를 가리키는 값이다. 자체 그림에서 배열 객체를 O1이라고 부르자. a와 b가 O1을 가리키면 서로 다른 변수 칸으로 같은 대상에 접근한다. O1은 설명용 이름이며 실제 주소나 출력 문자열이 아니다.

배열 내용 변경과 변수의 참조 변경은 다른 동작이다. b[0] = 9는 O1의 원소를 바꾸지만 b = null은 b 칸의 참조만 없앤다. a가 여전히 O1을 가리킬 수 있다. null은 빈 배열도 원소 0도 아니다.

호출마다 따로 추적하는 프레임

JVM의 추상 모델에서 스레드마다 호출 프레임을 담는 스택이 있고 객체와 배열의 저장 공간은 공유 힙에서 할당한다. 프레임에는 지역 변수와 계산 중간값이 있다. 이것은 역할 설명이며 실제 기계의 주소 배치를 그려 확정한 것이 아니다.

메서드가 호출되면 새 프레임을, 끝나면 프레임 제거를 생각하면 된다. 지역 참조 값이 사라져도 다른 참조로 연결된 객체는 남을 수 있다. 힙에 있는 객체를 두 스레드가 공유한다고 해서 그 객체의 수정이 자동으로 안전해지는 것은 아니다.

참조 값도 값으로 전달한다

자체 메서드 change(int[] p)가 먼저 p[0] = 7을 수행하고 이어 p = new int[]{5}를 수행한다고 하자. 호출자의 a가 가진 참조 값을 매개변수 p에 복사하므로 첫 수정은 같은 배열에 도달한다.

두 번째 대입은 p가 새 배열 O2를 가리키게 한다. 호출자의 a 칸은 바뀌지 않는다. 따라서 이 메서드를 a = new int[]{1}로 호출한 뒤 a[0]은 7이라는 예상 결과를 얻는다. Java 컴파일·실행은 수행하지 않았고 참조 그림으로 추적했다.

얕은 복사 뒤 b의 안쪽 원소를 고치면서 a를 보존하려는 설계다. 어디서 독립 복제가 빠졌는가?

힌트 2

풀이와 답 확인

  1. 바깥 참조 복사만으로는 R1/R2가 공유된다.

  2. 변경 대상 안쪽 배열을 독립 생성하여 연결하고 자료 원소도 복사해야 한다.

O2가 새 객체이므로 모든 안쪽 대상도 새 객체다.

한 경로를 지웠는데 왜 큰 자료가 아직 도달 가능할까?

강한 참조만 있는 새 자체 그래프에서 루트 X → A → C, 루트 Y → B → C로 둔다. A/B/C의 가상 크기는 각각 10/20/80단위다. C에 도달하는 경로가 둘이므로 X만 없애도 Y → B → C가 남는다. 전체 110단위에서 X 제거 뒤 도달 집합은 B와 C, 합 100단위이고 A 10단위만 후보다. 특수 참조·finalization과 동시 변경은 이 종이 모형에서 제외한다.

객체를 지우는 동작보다 어떤 루트와 경로를 없애는지 먼저 기록한다. X가 A를 계속 가리키는데 A → C만 끊었다면 A는 남고 C는 다른 Y 경로 때문에 남는다. Y 경로도 없애야 C가 후보가 된다. 후보 크기, 현재 도달 크기, 생성한 전체 크기는 서로 다른 분모다.

복제 중 최대 공존 공간도 마지막 상태의 공간과 다르다. 별도 교체 모형에서 루트가 크기 60단위인 옛 자료를 가리키고 새 자료 90단위를 전부 만든 후 루트를 교체한다면 전환 중 두 자료가 함께 도달 가능하여 150단위다. 교체 뒤에는 새 자료 90단위만 도달하지만 옛 자료 60단위가 즉시 운영체제로 반환된다는 보장은 없다. 수치는 실제 객체 크기나 GC 측정값이 아니다.

사용 가능한 경로를 따라간다

GC는 동적 메모리의 관리를 맡는다. 이해를 위해 살아 있는 실행 상태와 정적 참조 등에서 출발하는 강한 참조의 도달 관계를 단순 그림으로 사용한다. 아래 활동은 weak reference·finalization 같은 특수 참조를 제외한다.

자체 그림에서 시작점 R → A, A → B, B → A이며 C → C라고 하자. R에서 A와 B에 도달하지만 C에는 도달하지 못한다. 서로 참조하는가보다 사용 가능한 시작점과 연결되는가를 묻는다.

회수 후보와 회수 시점

위 단순 모형에서 C는 회수 후보이고 A와 B는 아직 사용 가능한 집합에 남는다. R → A 연결을 없애고 다른 출발 경로가 없다고 가정하면 A와 B도 도달 불가능해진다. 순환 참조 자체가 영구 보존 이유는 아니다.

후보라는 말은 지금 즉시 회수되어 운영체제의 메모리 수치가 내려간다는 보장이 아니다. 회수된 공간을 JVM 내부에서 재사용할 수도 있다. 사용 중인 자료를 더 이상 필요 없다고 판단해도 정적 목록에 참조를 계속 넣으면 도달 경로는 남는다.

자동 관리에도 비용과 책임이 남는다

수집기는 실행 비용을 사용하고 종류와 환경에 따라 동작이 달라질 수 있다. 특정 알고리즘을 모든 JVM의 필수 규칙으로 설명하지 않는다. 평균 처리량과 멈춤 시간의 목표도 같지 않다.

자체 교육 모형에서 A, B, C의 크기를 각각 10, 20, 30단위로 정하면 처음 도달 가능한 크기는 30단위이고 후보는 30단위다. 이는 실제 Java 객체 크기가 아니다. 파일 같은 외부 자원의 종료 책임까지 이 숫자 그림으로 해결하지 않는다.

요청한 로더가 다른 것과 정의한 로더가 다른 것은 같은가?

앞 본문은 이름과 정의 로더의 쌍으로 클래스 정체성을 설명했다. 새 사례에서는 L1과 L2가 demo.Box 요청을 모두 L0에 위임하고 L0가 한 번 정의한 같은 Class를 반환한다. 요청을 시작한 로더는 둘이지만 정의 로더는 L0 하나다. 반대로 L1/L2가 각각 직접 정의하면 이름이 같아도 정의 쌍이 다르다. 각 상황은 독립적이며 실제 사용자 로더를 구현하지 않는다.

초기화가 필요한 사용인지도 따로 판정한다. Parent가 비상수 static int value = seed()를 선언하고 Child가 이를 상속한다고 하자. seed는 7을 반환하며 초기 상태에서 두 클래스는 초기화되지 않았다. Child.value를 읽는 행위는 필드를 실제 선언한 Parent의 초기화를 요구한다. 이 읽기 자체가 Child의 초기화를 요구하는 것은 아니다. Parent의 static final int LIMIT = 3 같은 상수 변수 사용도 그 사용만으로 Parent 초기화를 요구하지 않는다.

초기화 실패는 정상 완료와 다른 상태다. 별도 Bad 클래스의 정적 초기화가 RuntimeException을 던지고 포장 객체 생성은 성공한다고 정한다. 최초 요청은 ExceptionInInitializerError로 실패하고 같은 정의의 Bad는 오류 상태가 된다. 이후 능동 사용은 NoClassDefFoundError로 실패하며 단순히 같은 클래스를 다시 읽는다고 초기화 식이 재시도되지 않는다. Error 자체 발생, 할당 실패, 별도 정의 로더의 새 클래스는 이 계약과 구별한다.

로딩은 이름에 해당하는 클래스의 표현을 찾아 JVM에 정의하는 과정이고 링킹은 실행 상태에 연결하는 과정이다. 클래스 파일의 존재만으로 원하는 모든 의존성과 실행 조건이 맞는다고 판단하지 않는다.

하나의 클래스 정체성은 이진 이름과 정의한 로더를 함께 고려한다. 이름이 같은 파일이라는 이유만으로 서로 다른 정의 로더의 타입이 항상 같은 타입이라고 보지 않는다. 아래 종이 활동은 사용자 정의 로더를 실제로 구현하지 않는다.

준비와 초기화의 값을 나눈다

링킹에는 구조 검증·준비와 심볼 참조의 해결이 관련된다. 준비에서는 정적 필드를 만들고 기본값을 둔다. 자체 클래스 Box에 static int count = seed();가 있고 seed()는 부작용 없이 7을 반환한다고 정하자.

count는 준비 단계에서 0으로 시작하고 클래스 초기화에서 식을 실행한 뒤 7이 된다. 이것은 상수 속성의 별도 규칙을 가진 static final 상수 예제가 아니다. 해결을 모두 한꺼번에 미리 끝내야 한다고 단정하지 않는다.

초기화 뒤 사용과 실패

Box를 처음 능동적으로 사용하는 동작이 정상 초기화를 일으켰고 다른 수정이 없다고 가정하자. count를 읽으면 7이고 다음 읽기도 7이다. 이미 정상 초기화된 같은 클래스의 식을 읽을 때마다 다시 실행하지 않는다.

로딩 실패와 초기화 실행 실패는 다른 단계다. 오류가 생기면 파일 경로만 볼 것이 아니라 의존성·접근 조건·초기화 코드와 오류 원인을 함께 살핀다. 이 단원은 자기 참조 초기화와 다중 스레드 초기화의 모든 세부 규칙을 단순화해 대체하지 않는다.

준비 개념과 학습 목표

  • 도달 가능한 참조

  • 파일 종료

  • 의도하지 않은 참조 유지와 외부 자원 누수를 구별한다.

논리적으로 비웠다는 말이 참조 제거와 자원 종료까지 뜻할까?

자체 큐의 slots는 세 참조 슬롯을 가진 배열이고 논리 count는 1이다. 첫 슬롯에 현재 자료 A, 둘째와 셋째 슬롯에 완료한 옛 자료 B/C가 남았다고 하자. 큐 객체가 세 슬롯 모두에 강한 참조를 갖는 동안 count만 0으로 바꾸어도 A/B/C의 도달 경로는 사라지지 않는다. 이후 사용하지 않는 슬롯을 null로 정리하는 계약과 논리 원소 수를 감소시키는 계약은 별도로 점검한다.

단순한 보관 장부와 실제 누수 진단을 구별한다. 아래 그래프는 다른 참조가 없고 A/B/C의 가상 내용 크기가 4/6/8단위라는 조건이다. count를 0으로만 바꾼 뒤 도달 내용은 여전히 18단위다. 세 슬롯을 모두 null로 바꾸면 자료 18단위가 후보가 되지만 큐 배열 자체의 공간은 이 계산에서 제외했다. 실제 작업 부하·관찰 시점·도구 없이 이 숫자를 JVM 측정이라고 표시하지 않는다.

자원도 생성 완료 여부를 따라 종료해야 한다. try-with-resources에서 A 생성은 성공하고 B 생성이 오류 E로 실패하면 본문에 진입하지 않고 이미 생성한 A만 닫는다. A.close가 별도 오류 F로 실패하면 주 오류 E에 F가 suppressed로 붙는다. B는 성공적으로 생성된 자원 목록에 없다. 두 자원이 정상 생성되고 본문이 정상 종료한 다른 사례에서 B.close 오류 F 뒤 A.close 오류 G가 생기면 첫 종료 오류 F가 주 오류이고 G가 suppressed로 붙는다. 모두 서로 다른 오류 객체와 suppression 활성 조건의 손모형이다.

조건이 같은 관찰을 비교한다

메모리 사용이 잠깐 늘었다는 사실만으로 누수를 확정하지 않는다. 처리 중인 작업량·캐시·힙 설정·측정 지점을 함께 남겨야 한다. 메모리 부족 오류도 필요한 용량이 작게 설정된 경우와 참조 보관 오류를 나누어 조사한다.

자체 가상 기록에서 같은 부하와 같은 관찰 시점의 남은 자료 크기가 20, 25, 30 MiB라면 증가 폭은 매번 5 MiB다. 이 표는 실제 GC 뒤 측정값이 아니며 원인 증명이 아니다. 보관 목록과 필요성을 확인할 단서다.

객체의 필요와 연결 경로를 조사한다

처리한 요청을 정적 history 목록에 무한히 보관하면 요청이 끝나도 목록에서 참조 경로가 남을 수 있다. 기록이 정말 필요한지, 보관 기간과 상한이 있는지 먼저 계약을 정한다.

자체 모형에서 요청마다 더 이상 필요 없는 기록 2 KiB를 목록에 하나씩 남기면 100회에 기록 내용만 200 KiB가 추가된다. 객체 머리말·목록 자체 공간은 제외한 계산이다. 10개만 보관하는 계약이면 정상 관리 시 내용 상한은 20 KiB지만 정책 구현과 실제 측정은 별도로 확인한다.

외부 자원의 종료 경로

파일의 자원 종료와 객체 메모리 회수는 같은 계약이 아니다. 종료 책임이 있는 AutoCloseable 자원은 try-with-resources 같은 명시적인 종료 구조로 정상 경로와 예외 경로를 다룬다.

자체 가상 자원 A 다음 B를 선언해 둘 다 정상 생성됐고 본문에서 오류 E가 발생한 뒤 B 종료에서 오류 F가 발생했다고 하자. 종료 시도 순서는 B 다음 A이며 본문 오류 E가 주 오류, 종료 오류 F가 suppressed 정보로 붙는 경우를 추적한다. 실제 파일·소켓·종료 실패는 일으키지 않았다.

  1. 누적 내용 크기는 100 × 2 = 200 KiB다.

  2. 상한 10개 정책을 정확히 구현한 다른 모형은 10 × 2 = 20 KiB다.

  4. 보관이 필요한 정상 기록인지 의도하지 않은 유지인지 요구 계약을 확인한다.

내용 누적은 200 KiB이며 제한 모형의 내용 상한은 20 KiB다. 실제 누수 확정과 측정 성공은 별도다.

풀이와 답 확인

  2. X 제거 뒤 B/C의 도달 합은 100단위이고 A 10단위가 후보다. 두 루트를 남기고 C로 향한 두 연결만 지우면 A/B 30단위가 도달하고 C 80단위는 후보가 된다. 별도 교체의 도달 피크는 60+90 = 150단위이며 최종 도달 90단위만으로 성공이나 실제 힙을 판정하지 않는다.

  3. 위임한 두 결과는 (demo.Box,L0)로 같다. 각 직접 정의는 (demo.Box,L1)/(demo.Box,L2)로 다르다. Child.value는 선언자 Parent의 초기화를 요구하여 값 7을 읽고 그 사용만으로 Child 초기화를 요구하지 않는다. Bad 최초는 EIIE, 같은 정의의 이후 사용은 NCDFE다.

  4. count만 0으로 바꾸면 18단위 모두 도달한다. 세 슬롯을 비워도 history로 B 6단위는 남고 A/C 12단위만 후보다. B 생성 실패에서는 본문 미진입/A만 close 시도, 주 오류 E와 suppressed F를 기록한다.

a의 두 값은 9와 2이고 b의 두 값은 9와 7이다. 두 배열은 R1만 공유한다. X를 제거하면 도달 크기는 100단위이고 후보 크기는 10단위다.
