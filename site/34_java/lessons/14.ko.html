소단원 14.1

heap·stack·reference

같은 배열을 가리키는 두 변수 중 하나만 바꾸면 다른 변수에서 무엇이 보일까?

준비 개념과 학습 목표

준비 개념

  • 배열

  • 메서드 호출

  • 변수 대입

학습 목표

  • 참조 값과 대상 객체를 구별한다.

  • 메서드 프레임과 공유 힙의 역할을 설명한다.

  • 참조 전달 뒤 재대입과 객체 수정을 추적한다.

칸의 값과 대상의 내용

참조는 객체 자체가 아니라 객체를 가리키는 값이다. 자체 그림에서 배열 객체를 O1이라고 부르자. a와 b가 O1을 가리키면 서로 다른 변수 칸으로 같은 대상에 접근한다. O1은 설명용 이름이며 실제 주소나 출력 문자열이 아니다.

배열 내용 변경과 변수의 참조 변경은 다른 동작이다. b[0] = 9는 O1의 원소를 바꾸지만 b = null은 b 칸의 참조만 없앤다. a가 여전히 O1을 가리킬 수 있다. null은 빈 배열도 원소 0도 아니다.

호출마다 따로 추적하는 프레임

JVM의 추상 모델에서 스레드마다 호출 프레임을 담는 스택이 있고 객체와 배열의 저장 공간은 공유 힙에서 할당한다. 프레임에는 지역 변수와 계산 중간값이 있다. 이것은 역할 설명이며 실제 기계의 주소 배치를 그려 확정한 것이 아니다.

메서드가 호출되면 새 프레임을, 끝나면 프레임 제거를 생각하면 된다. 지역 참조 값이 사라져도 다른 참조로 연결된 객체는 남을 수 있다. 힙에 있는 객체를 두 스레드가 공유한다고 해서 그 객체의 수정이 자동으로 안전해지는 것은 아니다.

참조 값도 값으로 전달한다

자체 메서드 change(int[] p)가 먼저 p[0] = 7을 수행하고 이어 p = new int[]{5}를 수행한다고 하자. 호출자의 a가 가진 참조 값을 매개변수 p에 복사하므로 첫 수정은 같은 배열에 도달한다.

두 번째 대입은 p가 새 배열 O2를 가리키게 한다. 호출자의 a 칸은 바뀌지 않는다. 따라서 이 메서드를 a = new int[]{1}로 호출한 뒤 a[0]은 7이라는 예상 결과를 얻는다. Java 컴파일·실행은 수행하지 않았고 참조 그림으로 추적했다.

중간 과정을 따라가는 예제

a가 내용 [1]인 O1을 가리킨다. change의 p는 a의 참조 값을 받아 p[0] = 7, p = new int[]{5}를 순서대로 수행하고 반환한다. 호출 뒤 a의 값을 추적한다.

  1. 시작할 때 a → O1, p → O1이다.

  2. 첫 대입 뒤 O1의 내용은 [7]이다.

  3. 새 배열 대입 뒤 p → O2이며 O2의 내용은 [5]다. a → O1은 유지된다.

  4. 반환으로 p의 프레임은 끝나지만 a가 가리키는 O1의 내용은 [7]이다.

a[0]의 예상 값은 7이다. 매개변수 재대입은 호출자의 변수 칸을 바꾸지 않는다.

종이와 본문으로 직접 해보기

a → O1, b → O1이고 O1의 내용은 [2]다. b[0] = 8 뒤 b = null을 수행하면 a[0]과 b의 참조는 무엇인가?

힌트 보기

원소 대입의 대상과 변수 대입의 대상을 따로 그린다.

풀이 보기

O1의 내용은 [8]이므로 a[0]은 8이다. b의 값은 null이다. a가 O1을 가리키므로 b의 참조를 없앤 것만으로 O1이 즉시 없어졌다고 할 수 없다.

오해와 반례

Java가 참조를 전달하므로 매개변수를 재대입하면 호출자의 변수도 재대입된다.

전달되는 것은 참조 값의 복사본이다. 같은 객체 수정은 보이지만 매개변수 칸의 재대입은 호출자 칸을 바꾸지 않는다.

자기점검

a와 b가 같은 배열을 가리킬 때 변수 칸도 같은가?

서로 다른 칸일 수 있다.

같은 대상 참조와 같은 변수는 구별한다.

null에 원소 [0]이 있는가?

답과 이유 보기

없다.

null은 객체를 가리키지 않는 참조 값이다.

호출 프레임 종료가 모든 대상 객체의 즉시 제거인가?

답과 이유 보기

아니다.

다른 경로의 참조가 남을 수 있다.

소단원 14.2

garbage collection의 역할

서로 연결된 객체가 아무 곳에서도 사용되지 않을 때 두 객체가 서로를 붙잡고 있으면 어떻게 생각해야 할까?

준비 개념과 학습 목표

준비 개념

  • 참조 그림

  • 연결 경로

  • 메모리 할당

학습 목표

  • 도달 가능한 객체와 회수 후보를 그림에서 구별한다.

  • 고립된 순환 참조를 추적한다.

  • 회수 가능성과 즉시 회수 보장을 구별한다.

사용 가능한 경로를 따라간다

GC는 동적 메모리의 관리를 맡는다. 이해를 위해 살아 있는 실행 상태와 정적 참조 등에서 출발하는 강한 참조의 도달 관계를 단순 그림으로 사용한다. 아래 활동은 weak reference·finalization 같은 특수 참조를 제외한다.

자체 그림에서 시작점 R → A, A → B, B → A이며 C → C라고 하자. R에서 A와 B에 도달하지만 C에는 도달하지 못한다. 서로 참조하는가보다 사용 가능한 시작점과 연결되는가를 묻는다.

회수 후보와 회수 시점

위 단순 모형에서 C는 회수 후보이고 A와 B는 아직 사용 가능한 집합에 남는다. R → A 연결을 없애고 다른 출발 경로가 없다고 가정하면 A와 B도 도달 불가능해진다. 순환 참조 자체가 영구 보존 이유는 아니다.

후보라는 말은 지금 즉시 회수되어 운영체제의 메모리 수치가 내려간다는 보장이 아니다. 회수된 공간을 JVM 내부에서 재사용할 수도 있다. 사용 중인 자료를 더 이상 필요 없다고 판단해도 정적 목록에 참조를 계속 넣으면 도달 경로는 남는다.

자동 관리에도 비용과 책임이 남는다

수집기는 실행 비용을 사용하고 종류와 환경에 따라 동작이 달라질 수 있다. 특정 알고리즘을 모든 JVM의 필수 규칙으로 설명하지 않는다. 평균 처리량과 멈춤 시간의 목표도 같지 않다.

자체 교육 모형에서 A, B, C의 크기를 각각 10, 20, 30단위로 정하면 처음 도달 가능한 크기는 30단위이고 후보는 30단위다. 이는 실제 Java 객체 크기가 아니다. 파일 같은 외부 자원의 종료 책임까지 이 숫자 그림으로 해결하지 않는다.

중간 과정을 따라가는 예제

강한 참조만 있는 자체 그래프 R → A, A → B, B → A, C → C를 사용한다. A/B/C의 가상 크기는 10/20/30단위이고 다른 시작점은 없다. R의 연결 제거 전후를 비교한다.

  1. 제거 전 R에서 A와 B에 도달하므로 10 + 20 = 30단위가 도달 가능하다.

  2. C는 고립된 순환이므로 30단위가 회수 후보다.

  3. R → A를 제거하면 어떤 시작점에서도 A/B/C에 도달하지 못한다.

  4. 이때 후보 크기는 10 + 20 + 30 = 60단위지만 실제 회수 시점이나 운영체제 반환량은 주어지지 않았다.

단순 모형의 후보는 30단위에서 60단위로 바뀐다. 즉시 60단위가 운영체제로 반환됐다는 뜻은 아니다.

종이와 본문으로 직접 해보기

R → A를 제거했지만 정적 목록 S → B가 남았다. 도달 가능한 객체와 후보 크기를 다시 구하라.

힌트 보기

B에서 A로 가는 연결을 잊지 않는다.

풀이 보기

S에서 B와 A에 도달하므로 A/B는 30단위가 도달 가능하다. C만 후보여서 후보 크기는 30단위다. 목록에서 참조를 제거해야 하는지 프로그램의 실제 필요를 확인한다.

오해와 반례

GC가 있으므로 필요 없는 객체를 목록에 계속 넣어도 메모리는 늘지 않는다.

목록이 강하게 참조하는 객체는 도달 경로가 남는다. 의도하지 않은 보관을 GC가 애플리케이션 대신 판별해 모두 지운다고 보장하지 않는다.

자기점검

고립된 A ↔ B 순환이면 반드시 영원히 남는가?

답과 이유 보기

아니다.

후보 60단위이면 운영체제 반환 60단위인가?

답과 이유 보기

알 수 없다.

시점과 내부 재사용·반환 정책은 별도다.

S → B가 있으면 A에도 도달하는가?

답과 이유 보기

그렇다.

B → A 경로가 있다.

한 단계 더

C의 가상 크기를 40단위로 바꾸면 전체 크기는 70단위, S → B가 남은 경우 후보 크기는 40단위다. 이 산술 변화를 실제 GC 지연 시간 증가로 곧바로 바꾸지 말라.

소단원 14.3

class loading 입문

클래스 파일을 찾았다는 사실은 정적 초기화 코드까지 모두 실행했다는 뜻일까?

준비 개념과 학습 목표

준비 개념

  • 클래스와 인스턴스

  • 정적 필드

  • 초기값

학습 목표

  • 로딩·링킹·초기화를 구별한다.

  • 준비 단계의 기본값과 초기화 식을 추적한다.

  • 이름과 정의 로더를 함께 고려한다.

실행에 필요한 정의를 찾는다

로딩은 이름에 해당하는 클래스의 표현을 찾아 JVM에 정의하는 과정이고 링킹은 실행 상태에 연결하는 과정이다. 클래스 파일의 존재만으로 원하는 모든 의존성과 실행 조건이 맞는다고 판단하지 않는다.

하나의 클래스 정체성은 이진 이름과 정의한 로더를 함께 고려한다. 이름이 같은 파일이라는 이유만으로 서로 다른 정의 로더의 타입이 항상 같은 타입이라고 보지 않는다. 아래 종이 활동은 사용자 정의 로더를 실제로 구현하지 않는다.

준비와 초기화의 값을 나눈다

링킹에는 구조 검증·준비와 심볼 참조의 해결이 관련된다. 준비에서는 정적 필드를 만들고 기본값을 둔다. 자체 클래스 Box에 static int count = seed();가 있고 seed()는 부작용 없이 7을 반환한다고 정하자.

count는 준비 단계에서 0으로 시작하고 클래스 초기화에서 식을 실행한 뒤 7이 된다. 이것은 상수 속성의 별도 규칙을 가진 static final 상수 예제가 아니다. 해결을 모두 한꺼번에 미리 끝내야 한다고 단정하지 않는다.

초기화 뒤 사용과 실패

Box를 처음 능동적으로 사용하는 동작이 정상 초기화를 일으켰고 다른 수정이 없다고 가정하자. count를 읽으면 7이고 다음 읽기도 7이다. 이미 정상 초기화된 같은 클래스의 식을 읽을 때마다 다시 실행하지 않는다.

로딩 실패와 초기화 실행 실패는 다른 단계다. 오류가 생기면 파일 경로만 볼 것이 아니라 의존성·접근 조건·초기화 코드와 오류 원인을 함께 살핀다. 이 단원은 자기 참조 초기화와 다중 스레드 초기화의 모든 세부 규칙을 단순화해 대체하지 않는다.

중간 과정을 따라가는 예제

자체 Box의 count는 static int count = seed();이고 seed()는 항상 7을 반환한다. 정상 준비와 초기화 이후 다른 대입은 없다. 준비 직후 및 초기화 이후 두 번 읽는 값을 정한다.

  1. 준비 단계에서 int 정적 필드의 기본값은 0이다.

  2. 초기화 단계에서 seed()를 실행해 7을 대입한다.

  3. 정상 초기화가 끝난 같은 클래스의 count를 두 번 읽으면 7, 7이다.

  4. 읽기마다 초기화 식을 반복 실행하는 모형은 사용하지 않는다.

상태는 준비의 0 → 정상 초기화의 7이며 두 읽기의 예상 값은 7과 7이다.

소단원 14.4

측정·메모리 누수·resource leak

메모리 그래프가 한 번 올라간 것과 계속 필요 없는 자료가 남는 것은 어떻게 구별할까?

준비 개념과 학습 목표

준비 개념

  • 도달 가능한 참조

  • 파일 종료

  • 비교 실험

학습 목표

  • 단일 사용량과 같은 조건의 추세를 구별한다.

  • 의도하지 않은 참조 유지와 외부 자원 누수를 구별한다.

  • 자원 종료의 정상·예외 경로를 점검한다.

조건이 같은 관찰을 비교한다

메모리 사용이 잠깐 늘었다는 사실만으로 누수를 확정하지 않는다. 처리 중인 작업량·캐시·힙 설정·측정 지점을 함께 남겨야 한다. 메모리 부족 오류도 필요한 용량이 작게 설정된 경우와 참조 보관 오류를 나누어 조사한다.

자체 가상 기록에서 같은 부하와 같은 관찰 시점의 남은 자료 크기가 20, 25, 30 MiB라면 증가 폭은 매번 5 MiB다. 이 표는 실제 GC 뒤 측정값이 아니며 원인 증명이 아니다. 보관 목록과 필요성을 확인할 단서다.

객체의 필요와 연결 경로를 조사한다

처리한 요청을 정적 history 목록에 무한히 보관하면 요청이 끝나도 목록에서 참조 경로가 남을 수 있다. 기록이 정말 필요한지, 보관 기간과 상한이 있는지 먼저 계약을 정한다.

자체 모형에서 요청마다 더 이상 필요 없는 기록 2 KiB를 목록에 하나씩 남기면 100회에 기록 내용만 200 KiB가 추가된다. 객체 머리말·목록 자체 공간은 제외한 계산이다. 10개만 보관하는 계약이면 정상 관리 시 내용 상한은 20 KiB지만 정책 구현과 실제 측정은 별도로 확인한다.

외부 자원의 종료 경로

파일의 자원 종료와 객체 메모리 회수는 같은 계약이 아니다. 종료 책임이 있는 AutoCloseable 자원은 try-with-resources 같은 명시적인 종료 구조로 정상 경로와 예외 경로를 다룬다.

자체 가상 자원 A 다음 B를 선언해 둘 다 정상 생성됐고 본문에서 오류 E가 발생한 뒤 B 종료에서 오류 F가 발생했다고 하자. 종료 시도 순서는 B 다음 A이며 본문 오류 E가 주 오류, 종료 오류 F가 suppressed 정보로 붙는 경우를 추적한다. 실제 파일·소켓·종료 실패는 일으키지 않았다.

중간 과정을 따라가는 예제

자체 가상 목록에 매 요청마다 불필요한 기록 내용 2 KiB를 추가한다. 제거가 없고 100회를 처리한다. 목록·객체의 부가 공간은 제외한다.

  1. 누적 내용 크기는 100 × 2 = 200 KiB다.

  2. 상한 10개 정책을 정확히 구현한 다른 모형은 10 × 2 = 20 KiB다.

  3. 실제 사용량에는 제외한 부가 공간이 있으므로 200 KiB를 JVM의 전체 힙 값이라고 부르지 않는다.

  4. 보관이 필요한 정상 기록인지 의도하지 않은 유지인지 요구 계약을 확인한다.

내용 누적은 200 KiB이며 제한 모형의 내용 상한은 20 KiB다. 실제 누수 확정과 측정 성공은 별도다.

종이와 본문으로 직접 해보기

같은 부하의 가상 자료가 20, 25, 30 MiB다. 두 증가 폭을 구하라. A 다음 B 자원을 생성한 try-with-resources의 본문 오류 E와 B 종료 오류 F가 있으면 종료 시도 순서와 주 오류를 설명하라.

힌트 보기

추세는 인접 값의 차이다. 자원은 선언 순서의 역순으로 종료한다.

풀이 보기

증가 폭은 25 − 20 = 5 MiB와 30 − 25 = 5 MiB다. 종료 시도는 B 다음 A다. 두 자원이 정상 생성되고 A 종료가 정상이라는 예제 조건에서 주 오류는 E이고 F는 suppressed 오류다. 이 가상 기록만으로 실제 누수를 확정하지 않는다.

오해와 반례

GC가 객체를 관리하니 파일 종료와 목록의 보관 정책도 자동으로 해결한다.

도달 가능한 불필요한 기록은 유지될 수 있고 파일 종료는 별도 자원 계약이다. 요구에 맞는 보관 정책과 정상·예외 종료 경로를 직접 점검한다.
