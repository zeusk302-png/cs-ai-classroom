소단원 7.1

checked·unchecked exception

컴파일러가 예외 처리를 요구하면 예외도 컴파일 중 발생하는 걸까?

준비 개념과 학습 목표

준비 개념

  • throw는 예외를 던지고 throws는 가능한 예외 계약을 선언한다.

  • Throwable 아래 Exception과 Error가 있으며 RuntimeException은 Exception의 하위다.

학습 목표

  • checked/unchecked를 계층으로 구분한다.

  • 잡기와 선언을 비교한다.

  • 컴파일 검사를 실제 발생과 구분한다.

실제 구현이 예외를 던지지 않아도 호출자는 처리 의무를 가질까?

앞 본문은 checked 예외에 catch 또는 throws가 필요하다고 설명했다. 이제 구현의 실제 몸체와 호출 지점에서 보이는 선언을 분리한다. 자체 Reader 인터페이스의 read()는 throws IOException을 선언하고, NoThrows 구현은 예외를 던지지 않는 몸체와 throws 없는 선언으로 재정의한다고 정한다. Reader r = new NoThrows()의 r.read() 호출은 여전히 Reader의 선언으로 checked 예외 분석을 받는다. 실제 실행에서 예외가 없다는 예측이 정적 처리 의무를 지우지 않는다.

재정의는 checked 예외의 허용 범위를 좁힐 수 있지만 넓힐 수 없다. IOException의 하위형 FileNotFoundException만 선언하는 구현과 아무 checked 예외도 선언하지 않는 구현은 이 조건에 맞는다. Exception을 선언하거나 별도의 SQLException을 선언하면 Reader 계약보다 넓거나 다른 checked 예외를 추가한다. 이 설명은 예외 선언 조건을 비교한 것이며 실제 javac 실행이나 전체 코드의 컴파일 성공을 검증한 것은 아니다.

같은 선언으로 받아들이는 호출자에게 구현을 바꿀 수 있게 하려면 정상 결과 계약도 지켜야 한다. 예외를 던지지 않고 임의의 기본값을 반환하는 것이 모든 read 요구를 만족한다는 결론은 나오지 않는다. 선언 적합성, 예외 발생, 업무 복구를 서로 다른 질문으로 읽는다. 아래 모든 문항은 각 문항의 별도 선언과 초기 상태에서 시작한다.

먼저 확인할 개념
  • checked와 unchecked의 분류

    재정의에서 제한되는 checked 예외 범위를 판정한다.

  • 호출 경로와 전파

    호출자가 보는 선언과 실제 전파가 일어나는 사건을 분리한다.

발생 시점과 검사 대상

checked는 메서드 본문에서 밖으로 나갈 수 있는 예외에 catch나 throws 계약을 요구하는 정적 규칙을 가리킨다. 예외 객체가 실제로 던져지는 것은 실행 중이다. checked 예외가 컴파일러 안에서 발생한다는 뜻이 아니다.

RuntimeException 계열과 Error 계열은 unchecked다. 그 밖의 Throwable 계열은 checked다. IOException은 checked, NullPointerException은 RuntimeException 계열, OutOfMemoryError는 Error 계열이다. catch(Exception)는 Error까지 포함하지 않는다.

선언과 처리는 다른 행동

read()가 IOException을 내보낼 수 있다면 호출 메서드는 적절한 catch로 처리하거나 throws IOException 같은 계약으로 전파해야 한다. throws를 적어도 읽기를 재시도하거나 사용자에게 복구 방법을 제공한 것은 아니다.

unchecked는 선언 의무에서 제외되지만 문서화·입력 검증·대응이 불필요하다는 뜻은 아니다. 인수 오류와 복구 불가능한 상태를 무작정 같은 값으로 바꾸면 정상 결과를 오해할 수 있다.

계층을 근거로 판단하기

자체 MissingScore extends Exception은 RuntimeException 하위가 아니므로 checked다. BadScore extends RuntimeException은 unchecked다. 이름에 Error라는 단어가 있느냐보다 실제 상속 관계를 확인한다.

아래는 세 예외의 분류와 계약을 종이에 확인한다. 실제 컴파일·파일 읽기·메모리 고갈을 수행하지 않았다. 특히 Error를 만들려고 장비 메모리를 소진하는 활동을 요구하지 않는다.

조건을 바꾸어 비교하기

참조의 선언형이 바꾸는 처리 의무

NoThrows n과 Reader r은 같은 NoThrows 객체를 가리킨다. NoThrows.read에는 throws가 없고 Reader.read에는 throws IOException이 있다. 두 호출 표현의 의무를 비교한다.

  1. n.read()는 NoThrows의 선언으로 분석하여 이 호출에서 IOException 처리 의무가 없다.

  2. r.read()는 Reader의 선언으로 분석하여 IOException을 catch하거나 바깥 메서드에 선언해야 한다.

같은 객체라도 호출 표현의 선언형에 따라 checked 예외 처리 의무가 다르다.

비교할 점

몸체가 이번에 정상 반환한다는 사실과 정적 분석은 다른 층이다.

예외를 좁히는 후보와 넓히는 후보

Reader.read throws IOException에 대해 F는 FileNotFoundException, E는 Exception을 선언한다.

  1. FileNotFoundException은 IOException의 하위형이므로 기존 호출자의 IOException 처리 안에 들어간다.

  2. Exception은 더 넓어서 기존 호출자의 IOException 처리로 다 감당되지 않는다.

F의 예외 선언은 허용하고 E는 이 조건을 위반한다.

허용된 F도 정상 결과와 실제 예외 상황을 별도로 검토해야 한다.

전파·복구·오류 계약

예외를 잡고0을 반환하면 복구한 걸까?

준비 개념과 학습 목표

준비 개념

  • 예외는 현재 호출의 정상 흐름을 중단한다.

  • 복구는 계약에 맞는 상태나 결과를 다시 제공하는 행동이다.

학습 목표

  • 호출 사슬을 따라간다.

  • 재던짐과 원인 보존을 설명한다.

  • 정상 값과 실패 표시를 구분한다.

반환할 값이 정해졌는데 finally가 상태를 바꾸면 무엇을 받는가?

앞 본문의 전파 경로에서 예외는 정상 반환을 중단했다. 새로 반환이 진행 중인 순간을 들여다보자. return 표현은 먼저 값을 평가하고, 그 메서드를 벗어나기 전에 관련 finally를 실행한다. 자체 지역 변수 x가 2이고 try에서 return x를 평가한 뒤 finally에서 x를 9로 바꾸고 정상 종료하면 호출자는 이미 평가한 정수 값 2를 받는다.

별도 Box의 value가 2이고 try에서 return box로 참조 값을 평가한 뒤 finally에서 box.value를 9로 바꾸면 호출자가 받는 것은 같은 Box 참조다. 그 객체의 현재 value는 9다. 정수 값의 복사와 객체 참조 값의 복사 모두 반환 값을 평가하지만, 후자는 객체 내부의 후속 변경을 보게 한다. 반환 전 객체 snapshot을 만든다는 계약은 자동으로 생기지 않는다.

finally 자체가 return 또는 throw로 비정상 종료하면 앞서 보류된 반환이나 예외를 대체할 수 있다. try의 throw P 뒤 finally의 throw Q는 Q가 최종 예외이며 P가 자동으로 suppressed에 보관된다고 보장하지 않는다. 이는 try-with-resources의 특별한 억제 예외 규칙과 구별해야 한다. 아래 P/Q는 서로 다른 일반 예외 객체이고 별도 원인 연결이나 억제 추가는 하지 않는다. 모두 손추적이다.

먼저 확인할 개념
  • 예외 전파와 정상 경로의 중단

    보류된 반환·예외와 최종 완료 이유를 비교한다.

  • 주 예외와 억제 예외

    일반 finally의 대체와 자원 정리 규칙을 혼합하지 않는다.

호출 사슬에서 처리자를 찾기

load→read→open의 가상 호출에서 open이 IOException을 던진다. read에 맞는 catch가 없으면 read도 정상 반환하지 않고 바깥으로 전파한다. load의 catch가 이를 처리하면 catch 뒤의 허용된 흐름으로 간다.

예외 발생 지점 다음 문장으로 돌아가 실패했던 연산을 자동 재개하지 않는다. 이미 수행한 부작용도 자동 취소되지 않는다. 저장 후 다음 연산이 실패하면 앞서 저장한 기록은 별도 복구 정책 없이 사라지지 않는다.

복구 능력이 있는 경계

설정 파일 없음에 대해 명시된 기본 설정을 쓰는 정책은 가능한 복구다. 필수 성적 파일의 실패를 평균0으로 바꾸면 실제0점과 실패를 구별하기 어렵다. 정상 반환·실패 반환·예외라는 계약을 먼저 정한다.

다른 예외로 감싸는 경우 원인을 보존할 수 있다. 예를 들어 도메인 LoadFailure(message,cause)를 사용하되 원문 경로나 민감한 내용을 공개 오류 메시지에 그대로 노출하지 않는다. 감싸기는 성공으로 바꾸는 행동이 아니다.

재시도에는 추가 조건이 필요하기

잠깐의 읽기 실패를 재시도할 수 있어도 횟수·대기·취소·중복 부작용을 정해야 한다. 결제를 이미 처리했는지 모르는 실패에 무조건 다시 요청하면 이중 처리 가능성이 있다. 예외 타입 하나만으로 재시도 안전을 단정하지 않는다.

소단원 7.3

try-with-resources

읽기와 close가 둘 다 실패하면 어떤 예외가 남을까?

준비 개념과 학습 목표

준비 개념

  • AutoCloseable은 close 계약을 제공한다.

  • suppressed는 주 예외에 붙이는 추가 실패이고 cause와 역할이 다르다.

학습 목표

  • 초기화·close 순서를 추적한다.

  • primary와 suppressed를 구분한다.

  • 초기화 실패 경로를 설명한다.

자원 변수 두 개가 같은 객체면 close도 한 번인가?

앞 본문의 try-with-resources는 선언한 자원을 역순으로 닫았다. 자원 객체의 고유 개수와 자원 변수의 개수를 나누어 보자. 자체 R 객체를 a와 b 두 자원 변수에 넣고 둘 다 정상 초기화했다고 정한다. b 다음 a 순서로 close 호출이 두 번 일어난다. 같은 참조라는 이유만으로 언어가 중복 정리를 제거하지 않는다.

AutoCloseable은 close가 반드시 멱등적이라고 요구하지 않는다. 새 R은 처음 close에서 closed를 true로 바꾸고 정상 반환하며, 이미 closed면 별도 예외 Q를 던진다고 정한다. 본문에서 return 5를 평가했어도 b의 첫 close는 정상, a의 둘째 close는 Q여서 호출자가 5 대신 Q를 받는다. 일반적인 설계에서는 불필요한 중복 소유를 피하고 구체 close 규약을 확인해야 한다.

초기화 도중 실패도 소유권 경계다. 새 Wrapper 생성자가 내부 H를 얻고 다음 검사에서 X를 던지면 Wrapper 자원 변수가 정상 초기화되지 않았다. try-with-resources는 그 Wrapper의 close를 호출할 수 없다. 생성자 안에서 H를 정리하거나 완성된 소유 객체로 책임을 넘기는 별도 계획이 필요하다. 억제 정보가 비활성인 예외 객체는 정리 실패가 있어도 억제 목록이 비어 있을 수 있으므로 빈 목록만으로 정리 성공을 증명하지 않는다.

먼저 확인할 개념
  • 초기화와 역순 close

  • 최종 실패와 전파

    몸체 정상 반환과 close 실패가 합쳐진 최종 결과를 계산한다.

왼쪽 초기화와 역순 닫기

try(A a=openA(); B b=openB())에서 A 다음 B를 초기화한다. 둘 다 성공해 본문이 끝나면 B 다음 A의 close를 호출한다. 자원 타입은 AutoCloseable을 구현해야 한다.

B 초기화가 실패하면 성공한 A는 닫지만 B 본문 변수는 성공적으로 마련되지 않았다. try 본문도 실행하지 않는다. null 자원은 close를 호출하지 않는다. close 호출이 있었다고 자원 해제 자체가 반드시 성공했다고 단정하지 않는다.

먼저 나온 실패를 보존하기

본문이 P를 던지고 B.close가 Q, A.close가 R을 던지는 가상 경로를 보자. 서로 다른 일반 예외 객체이고 suppression은 활성이라고 가정한다. 주 예외는 P이고 추가 실패 Q,R은 P의 suppressed 목록에 붙는다.

본문이 정상 종료했는데 B.close가 Q를 던지면 Q가 주 예외다. 이어 A.close의 R은 Q에 붙는다. 한 close가 실패했다고 다른 자원의 close를 건너뛰지 않는 규칙이 중요하다. cause와 suppressed를 서로 바꿔 읽지 않는다.

catch가 보는 것은 정리 후 결과

확장 try-with-resources의 catch는 초기화·본문·자동 닫기까지 포함한 결과를 처리한다. 읽기는 성공했어도 close 실패로 정상 완료하지 못할 수 있다. 자원이 닫혔다는 성공 기록과 처리 성공 기록을 함부로 동일시하지 않는다.

아래 이름 P,Q,R은 메시지나 실제 파일이 아닌 종이 사건표다. 실제 파일을 열거나 Java 코드를 실행하지 않았다. 안전한 자원 클래스의 close가 어떤 실패와 상태를 약속하는지도 구현별로 확인해야 한다.

준비 개념과 학습 목표

준비 개념

  • 로그는 관찰 기록이고 예외 처리를 대신하지 않는다.

  • 사건 ID는 같은 요청의 기록을 연결하기 위한 자체 식별자다.

학습 목표

  • 중복 로그와 실패 수를 구분한다.

  • 원인·추가 예외·상태를 기록한다.

  • 로그 출력 조건과 민감 정보 범위를 확인한다.

오류 로그 두 줄은 실패한 요청 두 개를 뜻하는가?

앞 본문은 한 요청 K7이 여러 계층에 로그를 남겨도 요청 수는 하나라고 설명했다. 이제 재시도와 최종 결과를 나누어 보자. 자체 요청 R은 첫 시도 R1이 실패하고 둘째 R2가 성공한다. 요청 S는 한 시도 S1이 실패하여 최종 실패한다. 시도는 총 세 개, 실패 시도는 두 개, 요청은 두 개, 최종 실패 요청은 한 개다. 실패 시도 비율 2/3과 최종 요청 실패 비율 1/2는 서로 다른 분모다.

R1과 S1의 각 실패를 세 계층이 각각 한 줄 기록하면 실패 로그는 여섯 줄이다. 여섯 줄을 여섯 실패 시도나 여섯 실패 요청으로 세지 않는다. 요청 id, 시도 id, 최종 결과 표시를 구별해 집계한다. cause와 suppressed로 연결된 진단 사건도 같은 업무 실패의 원인·정리 정보일 수 있어 별도 요청으로 자동 계산하지 않는다.

로그 메시지의 계산 자체도 효과를 가질 수 있다. Java Logger의 eager 문자열은 메서드 호출 전에 계산되므로 FINER가 비활성이어도 build()가 호출될 수 있다. Supplier 방식은 해당 수준이 활성일 때 메시지를 얻는 조건을 사용한다. 자체 build는 호출마다 calls를 1 증가시키고 문자열을 만든다고 정한다. disabled 수준에서 eager 한 번은 calls=1, Supplier 한 번은 calls=0이다. 메시지를 기록할지에 업무 상태 변경을 맡기면 설정에 따라 업무 결과까지 달라질 수 있으므로 진단과 업무를 분리한다.

출력 API와 실제 저장은 다르기

Logger는 레벨·필터·핸들러 설정을 거쳐 기록을 내보낸다. log 호출이 있었다고 외부 파일에 실제 저장됐다는 증거는 아니다. Throwable을 받는 API는 예외 정보를 별도 속성으로 전달해 형식기가 처리할 수 있다.

e.getMessage() 한 줄만 기록하면 원인·스택·suppressed를 놓칠 수 있다. 필요한 진단 정보를 보존하되 암호·토큰·개인 자료·불필요한 전체 파일 경로는 기록/공개 범위에 맞춰 제외하거나 마스킹한다. 이 마스킹 정책은 자체 설계이며 Logger가 자동 적용해 주지 않는다.

  2. 정수 반환 값은 먼저 평가한 2다. Box 반환은 같은 참조여서 호출자가 관측하는 value는 9다. 정상 finally는 보류된 완료 이유를 유지하지만 객체 snapshot을 만들지 않는다.
