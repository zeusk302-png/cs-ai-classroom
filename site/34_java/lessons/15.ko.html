소단원 15.1

dependency와 Maven·Gradle

import가 성공한 라이브러리가 실행 환경에도 자동으로 들어 있을까?

준비 개념과 학습 목표

준비 개념

  • package와 import

  • 컴파일·실행

  • 라이브러리 버전

학습 목표

  • 의존성의 식별·버전·범위를 적는다.

  • Maven phase와 Gradle task를 구별한다.

  • 직접·간접 의존성과 해석 결과를 읽는다.

파일 이름 대신 사용 조건을 기록한다

dependency는 코드가 사용하는 외부 API와 그 구현이다. 프로젝트 문서에 좌표·버전·repository·사용 범위를 적고 실제로 선택된 버전도 확인한다. import 문장은 자료형의 이름을 해석하는 코드이며 파일 다운로드나 runtime 배포의 완성 증거가 아니다.

직접 추가한 라이브러리가 또 다른 라이브러리를 요구하면 간접 의존성이 생긴다. 같은 artifact의 서로 다른 버전이 보이면 빌드 도구의 해석 규칙과 최종 그래프를 확인한다. 최신 숫자를 무조건 선택한다고 가정하지 않는다.

도구마다 작업 구조가 다르다

Maven의 기본 lifecycle은 phase가 순서대로 진행된다. 일반 jar 프로젝트에서 test는 단위 시험, package는 포장, install은 로컬 repository 설치, deploy는 원격 repository 공유 역할이다. phase에 연결된 plugin goal과 시험 생략 설정도 결과에 영향을 준다.

Gradle Java plugin은 compileJava, test, jar 같은 task와 그 의존 관계를 구성한다. implementation은 본 프로그램, testImplementation은 테스트의 컴파일·실행 요구를 담는 범위다. runtimeOnly와 compileOnly의 역할도 다르다. Maven의 scope와 Gradle configuration은 이름만 바꾼 동일한 시스템으로 보지 않는다.

선언과 실제 선택을 대조한다

Maven은 관리 조건이 없는 단순 충돌에서 의존 경로가 가까운 버전을 선택하며 같은 깊이이면 먼저 선언된 쪽이 선택된다. dependencyManagement나 직접 선언으로 조건을 바꿀 수 있다. 이 규칙을 모든 도구에 일반화하지 않는다.

빌드 결과에는 compiler/JDK와 plugin 버전, 선택된 의존성, 실제 명령·시험 결과를 남긴다. 외부 패키지의 라이선스와 배포 조건도 따로 확인한다. 이 절은 설치나 원격 업로드 없이 작은 가상 그래프를 읽는 활동이다.

중간 과정을 따라가는 예제

관리 설정이 없는 자체 Maven 그래프에서 App→L→X 1.0, App→M→N→X 2.0이다. 어느 X가 가까운가? App→X 2.0을 직접 추가하면 어떻게 바뀌는가?

  1. App에서 L을 거친 X 1.0까지 간선 2개, M과 N을 거친 X 2.0까지 3개다. 가까운 경로의 버전은 1.0이다.

  2. App의 직접 X 2.0은 깊이 1이다. 같은 artifact의 이 단순 조건에서는 직접 선언의 2.0이 더 가깝다.

  3. 선택된 2.0이 L과 호환된다는 결론은 별도다. API·동작·시험 결과를 확인해야 한다.

  4. 제안 확인 방법은 해당 Maven 프로젝트의 dependency tree를 읽는 것이다. 여기서는 repository 접근이나 실제 resolve를 실행하지 않았다.

단순 그래프의 최초 선택은 1.0, 직접 선언 추가 후는 2.0이다. 큰 버전 숫자 때문이 아니라 경로의 가까움 때문이다.

소단원 15.2

unit test와 fixture

테스트가 실행되는 순서를 바꾸면 결과도 바뀌어도 될까?

준비 개념과 학습 목표

준비 개념

  • 메서드와 예외

  • 객체 상태

  • 기대값 비교

학습 목표

  • 계약에서 정상·경계·예외 시험을 만든다.

  • fixture와 테스트 사이 상태를 점검한다.

  • 단위 시험과 외부 서비스 시험의 증거 범위를 구별한다.

작은 할인 계약으로 시작한다

자체 Price.pay는 음이 아닌 int 구매액을 받고 1000 이상이면 100을 뺀다. 음수는 IllegalArgumentException이다. 기대값은 구현을 실행하기 전에 이 계약으로 계산한다. 999, 1000, 1001의 경계와 음수·0을 함께 고른다.

JUnit Jupiter의 assertEquals는 기대값과 실제값을 비교하고 assertThrows는 지정한 예외 발생을 확인한다. 정상 입력만 시험하면 실패 처리의 약속을 놓친다. 기대식을 구현의 잘못된 조건에서 복사하지 않는다.

fixture는 시작 상태의 약속

fixture는 시험이 시작할 때 필요한 객체·입력·환경이다. Jupiter의 기본 per-method는 메서드마다 테스트 클래스 인스턴스를 새로 만든다. PER_CLASS를 쓰거나 기본 설정을 바꾸면 같은 인스턴스를 공유하므로 상태를 적절히 재설정해야 한다.

새 테스트 객체가 생겨도 static 변수, 파일, 데이터베이스와 외부 서비스가 자동 초기화되는 것은 아니다. Price는 상태 없는 정적 계산이므로 아래 시험은 공유 가변 fixture를 필요로 하지 않는다. 다른 시험에서는 시작 상태와 정리의 책임을 적는다.

무엇을 실행했는지 남긴다

테스트 코드의 존재, 실행 발견, 성공한 assertion과 실제 외부 서비스 검증은 구별한다. 시험이 한 개도 발견되지 않았는데 build 성공만 보고 검증 완료라고 적지 않는다. 실패·성공 개수와 실행 환경을 확인한다.

여기서 확인한 JUnit 6.1.3 문서는 runtime에 Java 17 이상을 요구한다. 프로젝트에 선택한 JUnit API·engine·runner와 JDK 조건을 맞춰야 실제로 실행할 수 있다. 이 강의는 작은 시험 코드와 손 추적이며 JUnit 실행은 미수행이다.

중간 과정을 따라가는 예제

다음 자체 함수와 테스트를 읽고 예상 결과 및 >=를 >로 바꾼 오류를 판정하라.

  1. src/main/java/lesson/price/Price.java: 

    package lesson.price;
public final class Price {
    private Price() {}
    public static int pay(int amount) {
        if (amount < 0) throw new IllegalArgumentException("negative amount");
        return amount >= 1000 ? amount - 100 : amount;
    }
}

  2. src/test/java/lesson/price/PriceTest.java: 

    package lesson.price;
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.*;
class PriceTest {
    @Test void boundary() {
        assertEquals(999, Price.pay(999));
        assertEquals(900, Price.pay(1000));
        assertEquals(901, Price.pay(1001));
    }
    @Test void zero() { assertEquals(0, Price.pay(0)); }
    @Test void negative() {
        assertThrows(IllegalArgumentException.class, () -> Price.pay(-1));
    }
}

  3. 독립 기대는 999→999, 1000→900, 1001→901, 0→0이다. -1은 첫 조건에서 예외여서 정상 반환에 도달하지 않는다.

  4. > 변이는 1000에서 1000을 내므로 boundary의 두 번째 assertion에서 실패를 예상한다. 정상 코드의 세 메서드 통과는 이론 예상이며 실제 JUnit 결과가 아니다.

기준과 같은 구매액을 포함하는 시험이 비교 오류를 찾는다. 정상·0·음수 세 종류의 계약을 확인한다.

종이와 본문으로 직접 해보기

공유 가상 counter = 0에서 시험 A가 +1 후 1을 기대하고 B가 +2 후 2를 기대한다. 재설정 없이 A→B와 B→A의 값을 구하고 fixture를 개선하라.

힌트 보기

한 시험의 끝 상태가 다음 시험의 시작 상태가 되는지 본다.

풀이 보기

A→B는 1 뒤 3이라 B의 기대 2에 실패한다. B→A는 2 뒤 3이라 A의 기대 1에 실패한다. 각 시험의 counter를 독립 생성하거나 명시적으로 시작값 0으로 재설정한다. 외부 공유 상태는 별도 관리한다.

오해와 반례

메서드마다 새 테스트 객체가 생기면 모든 공유 자원도 초기화된다.

static·파일·외부 서비스 상태는 새 객체 생성만으로 초기화되지 않는다. 시험의 fixture와 정리 계약을 따로 적는다.

소단원 15.3

API 문서·package 구조

메서드 이름과 반환형만 읽어도 실패 조건과 수정 여부를 알 수 있을까?

준비 개념과 학습 목표

준비 개념

  • package 이름

  • public 메서드

  • 예외

학습 목표

  • package와 파일 구조를 맞춘다.

  • API 문서에 입력·반환·예외 계약을 적는다.

  • 문서 생성과 내용 정확성을 구별한다.

호출자가 찾는 이름

Price의 완전한 이름은 lesson.price.Price다. 관례적인 source root src/main/java 아래 lesson/price/Price.java에 둔다. 테스트는 src/test/java 아래 같은 package로 배치한다. 출력 class root와 source root는 다른 역할이다.

package 이름의 점은 디렉터리 계층으로 대응시켜 도구가 찾기 쉽게 만든다. 하위 package가 이름상 포함된다고 부모 package의 접근 권한을 자동 공유하는 것은 아니다. 이름 구조와 public·package-private 같은 접근 제어를 구별한다.

사용 계약을 주석으로 남긴다

pay의 문서에는 구매액이 음이 아닌 int이며 금액 단위는 이 가상 예제의 원, 1000 이상에서 100 할인, 그 외 원값, 음수 예외라고 적는다. 시간·파일·네트워크 부작용을 수행하지 않는 함수임도 알릴 수 있다. 사용자에게 중요한 약속을 우선한다.

Javadoc은 선언과 문서 주석을 읽어 HTML API 자료를 만든다. @param은 입력, @return은 결과, @throws는 실패 계약을 설명한다. 본문이 실제 구현과 일치하는지는 저자와 검토자의 책임이며 생성 도구가 모든 의미를 증명하지 않는다.

문서와 코드가 함께 바뀐다

할인 기준을 2000으로 바꾸면 코드와 API 설명, 기대값 시험을 함께 갱신한다. 새 이름이나 예외 정책을 공개하면 기존 소비자에게 영향이 있는지 확인한다. 문서가 생성됐다는 사실과 이전 API와 호환된다는 사실은 별도다.

Javadoc의 문서 생성·DocLint와 HTML 확인을 통해 흔한 형식 문제를 찾을 수 있지만 실제 사용자 이해까지 검증했다고 쓰지 않는다. 여기서는 주석의 계약과 코드·시험을 이론으로 대조하고 HTML 생성은 하지 않았다.

중간 과정을 따라가는 예제

앞 Price.pay 선언 바로 앞에 다음 문서를 둔다. 입력 1000과 -1의 계약이 코드와 맞는지 확인하라.

  1. 문서 주석: 

    /**
 * Computes payment for the lesson's whole-won amount.
 * @param amount non-negative purchase amount
 * @return amount minus 100 when amount is at least 1000; otherwise amount
 * @throws IllegalArgumentException when amount is negative
 */

  2. 1000은 at least 1000에 포함되므로 반환 900이다. 코드의 >=와 맞는다.

  3. -1은 negative 조건이므로 IllegalArgumentException이다. 할인 계산으로 넘어가거나 음수 지불액을 정상 반환하지 않는다.

  4. 이 주석은 Price.pay 바로 앞에 붙인다. 제안 생성 명령은 javadoc -d docs src/main/java/lesson/price/Price.java이며 미실행이다.

문서의 경계·반환·실패 계약은 자체 코드와 맞는다. HTML 생성과 학습자 이해는 아직 확인하지 않았다.

종이와 본문으로 직접 해보기

힌트 보기

구현·계약·시험의 세 위치를 대조한다.

풀이 보기

새 계약은 1000→1000, 2000→1900이다. 문서가 여전히 1000부터 할인한다고 말하면 호출자는 1000→900을 기대해 실제와 다르다. 문서와 기존 boundary 시험도 갱신한다.

오해와 반례

Javadoc 생성이 성공하면 API 설명의 내용까지 맞다.

생성과 형식 검사는 계약의 의미나 구현 일치를 모두 증명하지 않는다. 기대값과 실패 조건을 따로 대조한다.

소단원 15.4

실행 가능한 배포와 재현성

JAR 파일을 만들었다는 사실과 다른 컴퓨터에서 앱이 실행된다는 사실은 같을까?

준비 개념과 학습 목표

준비 개념

  • main과 package

  • class 파일

  • 빌드 환경

학습 목표

  • 일반 JAR와 실행 진입점을 구별한다.

  • runtime·의존성·설정의 배포 조건을 적는다.

  • 재빌드 절차와 바이트 일치·운영 검증을 구별한다.

실행 시작점을 명시한다

일반 JAR는 클래스와 자원을 묶는 archive이며 모든 JAR가 java -jar로 시작되는 것은 아니다. 자체 Main은 public static void main(String[] args)를 진입점으로 가진다. 실행 JAR에서는 Main-Class와 실제 클래스 경로를 맞춘다.

jar 도구는 archive 생성과 목록 확인을 제공한다. 클래스가 포장됐다는 것만으로 모든 외부 라이브러리와 필요한 runtime이 함께 들어간다고 보지 않는다. 이 자체 프로그램은 외부 runtime 패키지 없이 JDK 표준과 Price만 사용한다.

빌드 조건과 runtime 조건

프로젝트에 compile JDK, target release, 실행 JDK, 운영체제, 명령, 설정과 파일 위치를 적는다. javac --release 17을 쓴 예제라면 Java 17 목표로 컴파일하고 그에 맞는 runtime을 제안한다. 실제 JDK 설치와 실행 결과는 별도 확인 대상이다.

시험용 JUnit 파일을 production 산출물에 넣는 것과 앱의 runtime 요구는 다른 선택이다. 뒤 예제는 main source 두 파일만 직접 컴파일해 JAR를 만들도록 제안한다. 이 경로는 JUnit을 실행하지 않으므로 앞 시험이 실제 통과한 증거가 아니다.

검증 단계를 기록한다

소스 revision·도구 버전·의존성·빌드 옵션과 명령은 절차 재현의 입력이다. 소스에서 다시 만들기, 새 환경에서 실행하기, 테스트하기, JAR hash가 같은지 비교하기를 따로 기록한다. 같은 revision만으로 같은 바이트를 자동 보장하지 않는다.

Maven deploy의 원격 artifact 공유와 앱 서버의 실제 운영 배포를 구별한다. 여기서는 로컬 JAR 실행 계획만 제안하며 원격 repository나 서버에 업로드하지 않는다. 생성물의 시각·경로·압축·도구 차이는 바이트 비교의 추가 조건이다.

중간 과정을 따라가는 예제

앞 Price와 다음 Main으로 기대 출력과 각 제안 명령의 목적을 읽어라.

  1. src/main/java/lesson/price/Main.java: 

    package lesson.price;
public final class Main {
    public static void main(String[] args) {
        System.out.println(Price.pay(1000));
    }
}

  2. 제안 compile: javac --release 17 -d out src/main/java/lesson/price/Price.java src/main/java/lesson/price/Main.java. out 아래 lesson/price의 class 파일이 생기는 구성을 목표로 한다. 사용하는 javac가 목표 release 17을 지원하는지 help로 확인한다.

  3. 제안 archive는 out의 클래스 계층을 포함하고 진입점을 지정한다. 다음 블록의 마지막 점 하나는 포함할 파일 집합이다. 

    jar --create --file price.jar --main-class lesson.price.Main -C out .
java -jar price.jar

  4. 정상 기대 출력은 900이다. 실제 compiler·jar·java 명령과 새 환경 실행은 미수행이며 성공 로그를 만들지 않았다.

compile은 class 생성, jar는 진입점을 포함한 포장, java -jar는 실행이다. 출력 900은 계약에서 계산한 예상이다.

종이와 본문으로 직접 해보기

가상 기록에 r8 소스·JDK X·Debug 빌드와 r8 소스·JDK Y·다른 옵션 빌드가 있다. 같은 revision이므로 hash와 실행 결과까지 같다고 해도 되는가? 필요한 확인 두 가지를 적어라.

힌트 보기

입력 기록, 산출물 비교, 실제 실행을 구별한다.

풀이 보기

자동으로 결론 내릴 수 없다. 실제 도구·옵션을 맞춰 재빌드한 결과와 hash 비교, 또는 필요한 runtime에서의 실제 실행·시험을 확인한다. 버전과 명령 기록만으로 확인 결과를 대체하지 않는다.

오해와 반례

JAR가 생성됐으니 모든 머신의 운영 배포까지 끝났다.

진입점·runtime·의존성·설정과 실제 실행을 확인해야 한다. 로컬 포장과 운영 배포의 증거는 별도다.
