소단원 15.1

dependency와 Maven·Gradle

import가 성공한 라이브러리가 실행 환경에도 자동으로 들어 있을까?

준비 개념과 학습 목표

준비 개념

  • package와 import

  • 컴파일·실행

  • 라이브러리 버전

학습 목표

  • 의존성의 식별·버전·범위를 적는다.

  • Maven phase와 Gradle task를 구별한다.

  • 직접·간접 의존성과 해석 결과를 읽는다.

같은 깊이의 두 버전을 선언하는 순서도 결과를 바꿀까?

앞 본문은 Maven 경로 길이의 차이를 비교했다. 새 자체 그래프는 App의 직접 의존성을 A, B 순서로 선언하고 A → X 1, B → X 2로 둔다. X는 같은 좌표의 artifact이며 범위·제외·관리 설정은 없고 두 경로는 모두 깊이 2다. 이 단순 조건에서는 먼저 선언한 A 쪽의 X 1이 선택된다. B, A 순서로 바꾸면 X 2가 선택된다. 숫자의 크기와 선언 순서의 역할을 분리해야 한다.

dependencyManagement는 사용할 때의 버전 등을 관리하는 설정이다. X 3을 관리 표에 적었다는 사실만으로 X를 새 의존성으로 추가했다고 결론내릴 수 없다. 실제 dependencies의 직접 또는 간접 경로를 먼저 찾는다. plugin의 의존성 관리와도 범위가 다르다. 한 경로에서 X를 제외해도 다른 경로가 남는다면 X 자체가 그래프에서 완전히 사라졌다고 단정할 수 없다.

Gradle Java plugin의 compileOnly와 runtimeOnly는 컴파일·실행의 서로 다른 목록에 참여한다. 새 사례에서 프로그램 소스가 외부 P의 자료형을 직접 쓰는데 P를 runtimeOnly에만 두면 해당 선언만으로 컴파일 목록을 충족하지 못한다. P를 compileOnly에만 두면 실행 목록 포함은 보장하지 못한다. 이 판단은 도구가 외부 라이브러리를 자동 포장한다는 주장과도 다르다. 모든 예제는 별도 초기 그래프에서 시작하고 실제 resolve와 다운로드는 하지 않는다.

먼저 확인할 개념
  • 의존성 경로와 사용 범위

    같은 깊이의 순서와 관리 표의 역할을 비교한다.

  • 포장과 실제 실행 조건

    컴파일에 보이는 라이브러리와 실행에 제공할 라이브러리를 나눈다.

파일 이름 대신 사용 조건을 기록한다

dependency는 코드가 사용하는 외부 API와 그 구현이다. 프로젝트 문서에 좌표·버전·repository·사용 범위를 적고 실제로 선택된 버전도 확인한다. import 문장은 자료형의 이름을 해석하는 코드이며 파일 다운로드나 runtime 배포의 완성 증거가 아니다.

직접 추가한 라이브러리가 또 다른 라이브러리를 요구하면 간접 의존성이 생긴다. 같은 artifact의 서로 다른 버전이 보이면 빌드 도구의 해석 규칙과 최종 그래프를 확인한다. 최신 숫자를 무조건 선택한다고 가정하지 않는다.

도구마다 작업 구조가 다르다

Maven의 기본 lifecycle은 phase가 순서대로 진행된다. 일반 jar 프로젝트에서 test는 단위 시험, package는 포장, install은 로컬 repository 설치, deploy는 원격 repository 공유 역할이다. phase에 연결된 plugin goal과 시험 생략 설정도 결과에 영향을 준다.

Gradle Java plugin은 compileJava, test, jar 같은 task와 그 의존 관계를 구성한다. implementation은 본 프로그램, testImplementation은 테스트의 컴파일·실행 요구를 담는 범위다. runtimeOnly와 compileOnly의 역할도 다르다. Maven의 scope와 Gradle configuration은 이름만 바꾼 동일한 시스템으로 보지 않는다.

선언과 실제 선택을 대조한다

Maven은 관리 조건이 없는 단순 충돌에서 의존 경로가 가까운 버전을 선택하며 같은 깊이이면 먼저 선언된 쪽이 선택된다. dependencyManagement나 직접 선언으로 조건을 바꿀 수 있다. 이 규칙을 모든 도구에 일반화하지 않는다.

빌드 결과에는 compiler/JDK와 plugin 버전, 선택된 의존성, 실제 명령·시험 결과를 남긴다. 외부 패키지의 라이선스와 배포 조건도 따로 확인한다. 이 절은 설치나 원격 업로드 없이 작은 가상 그래프를 읽는 활동이다.

중간 과정을 따라가는 예제

관리 설정이 없는 자체 Maven 그래프에서 App→L→X 1.0, App→M→N→X 2.0이다. 어느 X가 가까운가? App→X 2.0을 직접 추가하면 어떻게 바뀌는가?

  1. App에서 L을 거친 X 1.0까지 간선 2개, M과 N을 거친 X 2.0까지 3개다. 가까운 경로의 버전은 1.0이다.

  2. App의 직접 X 2.0은 깊이 1이다. 같은 artifact의 이 단순 조건에서는 직접 선언의 2.0이 더 가깝다.

  3. 선택된 2.0이 L과 호환된다는 결론은 별도다. API·동작·시험 결과를 확인해야 한다.

  4. 제안 확인 방법은 해당 Maven 프로젝트의 dependency tree를 읽는 것이다. 여기서는 repository 접근이나 실제 resolve를 실행하지 않았다.

단순 그래프의 최초 선택은 1.0, 직접 선언 추가 후는 2.0이다. 큰 버전 숫자 때문이 아니라 경로의 가까움 때문이다.

App → A → X 1과 App → B → X 2다. A, B 선언과 B, A 선언의 선택을 각각 구하라.

  1. 두 X 경로의 간선 수는 모두 2다.

  2. 가까움으로 동점을 해소할 수 없으므로 각각 먼저 선언된 경로를 읽는다.

A, B에서는 X 1, B, A에서는 X 2다. 호환성은 따로 검토해야 한다.

관리 표와 실제 경로를 별도로 읽는다

별도 프로젝트가 X 3을 dependencyManagement에만 적고 X로 가는 직접·간접 경로는 전혀 없다. X가 새로 추가되는가?

  1. 관리 표는 실제 dependencies 경로와 다르다.

  2. 사용할 대상의 버전을 관리하는 것과 사용 경로를 만드는 것을 구별한다.

연습 1 · 값과 상태 예측

A, B 순서의 초기 그래프에서 A 쪽 X를 제외한다. B → X 2는 남는다. 관리 설정은 없다. X의 부재를 보고해도 되는가?

힌트 1

제외가 적용된 경로와 남은 경로를 따로 그린다.

힌트 2

B에서 X로 가는 경로를 따라간다.

풀이와 답 확인

  1. A 경로는 없어지지만 B 경로는 살아 있다.

  2. 단순 그래프에서는 X 2가 남으며 X 전체 부재라고 보고하면 틀리다.

X 2가 남는다. 제외 한 곳과 전체 그래프 제거를 구별한다.

흔한 오답에서 다시 생각하기

제외 선언이 하나 있으므로 X는 어디서도 쓰이지 않는다.

제외는 적용 경로를 확인해야 하며 남은 간접 경로가 결과를 바꾼다.

힌트 1

compileClasspath에 포함되는 configuration을 확인한다.

힌트 2

runtimeOnly의 이름보다 실제 역할을 읽는다.

풀이와 답 확인

  1. 이 선언은 실행 목록에 참여하고 컴파일 목록에는 포함되지 않는다.

  2. 소스 컴파일 요구를 만족하는 선언과 실제 실행의 라이브러리 제공을 함께 검토해야 한다.

runtimeOnly만으로 직접 P 타입 사용의 컴파일 요구가 해결되지는 않는다.

힌트 2

  2. 해석된 그래프에서 X 3 선택을 확인하고 A/B가 해당 API·동작과 호환되는지 별도 시험한다. 실제 수행 전에는 결과를 미수행으로 둔다.

직접 선언, 최종 그래프 확인, 호환 시험이라는 세 책임을 적는다.

직접 선언을 적으면 A/B 호환 시험도 통과한 셈이다.

선택 규칙은 라이브러리 사용 코드의 동작 정확성을 증명하지 않는다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

동일 프로젝트에서 Maven package phase를 호출하는 계획과 jar plugin goal만 직접 호출하는 계획이 있다. 두 계획이 이전 시험 phase를 거쳤다고 똑같이 기록해도 되는가?

힌트 1

phase 호출은 그 앞 phase까지 진행하는 구조다.

힌트 2

직접 goal 호출과 시험 생략 설정을 구별한다.

풀이와 답 확인

  1. package phase의 lifecycle 연결은 앞 phase를 포함하지만 시험 설정과 실제 결과를 확인해야 한다.

  2. plugin goal을 직접 실행한 사실만으로 그 앞 모든 phase가 실행됐다고 쓰지 않는다.

호출 방식·연결·설정·실제 시험 결과를 각각 기록한다. 포장 파일 존재만으로 시험을 증명하지 않는다.

준비 개념과 학습 목표

  • 객체 상태

학습 목표

새 테스트 인스턴스에서도 실패 뒤의 상태를 확인해야 할까?

자체 순차 지갑은 balance라는 음이 아닌 잔액을 가진다. withdraw(k)는 1 ≤ k ≤ balance이면 잔액에서 k를 빼고 true를 반환하며 그 외 입력이면 false를 반환하고 잔액을 보존한다. 실제 금융 코드가 아니라 실패 보존을 시험하는 작은 계약이다. 초기 잔액 5에서 k = 2는 true와 잔액 3, k = 6은 false와 잔액 5여야 한다. 두 호출은 각각 새 지갑에서 시작한다.

잘못된 구현이 먼저 잔액에서 k를 뺀 뒤 음수인지 검사하면 k = 6에서 false를 반환하더라도 잔액은 −1로 훼손된다. 반환값만 시험하면 이 결함을 놓친다. 정상 출력, 실패 출력, 실패 뒤 상태를 모두 계약에서 독립 계산한다. 기대값을 잘못된 구현의 같은 식으로 만들면 두 값이 같이 틀려도 시험이 지나갈 수 있다.

JUnit의 기본 PER_METHOD는 테스트 클래스 인스턴스의 수명을 정하지만 static 상태까지 자동 재설정하지 않는다. 별도 손모형에서 static calls = 0이고 각각 새 테스트 인스턴스인 A/B가 calls를 1 증가시킨 뒤 1을 기대한다면 첫 시험만 맞고 다음 시험은 2를 본다. 상태 없는 순수 함수 시험, 새 지갑 시험, 공유 static 상태 시험의 fixture 책임은 다르다. 실제 시험 발견 수와 수행 수, 성공 수를 확인하지 않았다면 파일 존재를 통과 수로 바꾸지 않는다.

먼저 확인할 개념
  • 기대값과 fixture 시작 상태

    반환값뿐 아니라 실패 후 상태와 공유 정적 상태를 확인한다.

  • 실패 계약의 문서화

    시험의 기대 상태를 호출자에게 약속한 문장에서 계산한다.

작은 할인 계약으로 시작한다

자체 Price.pay는 음이 아닌 int 구매액을 받고 1000 이상이면 100을 뺀다. 음수는 IllegalArgumentException이다. 기대값은 구현을 실행하기 전에 이 계약으로 계산한다. 999, 1000, 1001의 경계와 음수·0을 함께 고른다.

JUnit Jupiter의 assertEquals는 기대값과 실제값을 비교하고 assertThrows는 지정한 예외 발생을 확인한다. 정상 입력만 시험하면 실패 처리의 약속을 놓친다. 기대식을 구현의 잘못된 조건에서 복사하지 않는다.

fixture는 시작 상태의 약속

fixture는 시험이 시작할 때 필요한 객체·입력·환경이다. Jupiter의 기본 per-method는 메서드마다 테스트 클래스 인스턴스를 새로 만든다. PER_CLASS를 쓰거나 기본 설정을 바꾸면 같은 인스턴스를 공유하므로 상태를 적절히 재설정해야 한다.

새 테스트 객체가 생겨도 static 변수, 파일, 데이터베이스와 외부 서비스가 자동 초기화되는 것은 아니다. Price는 상태 없는 정적 계산이므로 아래 시험은 공유 가변 fixture를 필요로 하지 않는다. 다른 시험에서는 시작 상태와 정리의 책임을 적는다.

무엇을 실행했는지 남긴다

테스트 코드의 존재, 실행 발견, 성공한 assertion과 실제 외부 서비스 검증은 구별한다. 시험이 한 개도 발견되지 않았는데 build 성공만 보고 검증 완료라고 적지 않는다. 실패·성공 개수와 실행 환경을 확인한다.

여기서 확인한 JUnit 6.1.3 문서는 runtime에 Java 17 이상을 요구한다. 프로젝트에 선택한 JUnit API·engine·runner와 JDK 조건을 맞춰야 실제로 실행할 수 있다. 이 강의는 작은 시험 코드와 손 추적이며 JUnit 실행은 미수행이다.

  2. src/test/java/lesson/price/PriceTest.java: 

    package lesson.price;
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.*;
class PriceTest {
    @Test void boundary() {
        assertEquals(999, Price.pay(999));
        assertEquals(900, Price.pay(1000));
        assertEquals(901, Price.pay(1001));
    }
    @Test void zero() { assertEquals(0, Price.pay(0)); }
    @Test void negative() {
        assertThrows(IllegalArgumentException.class, () -> Price.pay(-1));

  4. > 변이는 1000에서 1000을 내므로 boundary의 두 번째 assertion에서 실패를 예상한다. 정상 코드의 세 메서드 통과는 이론 예상이며 실제 JUnit 결과가 아니다.

  2. B의 인스턴스는 새것이지만 같은 static calls는 1에서 2가 된다.

같은 메서드 서명을 유지해도 약속한 동작이 바뀔 수 있을까?

자체 순차 예약 객체의 available은 남은 자리 수다. reserve(count)는 1 ≤ count ≤ available이면 count만큼 차감하고 차감 뒤 남은 자리 수를 반환한다. 범위 밖이면 IllegalArgumentException을 던지고 available을 보존한다. 한 자리의 단위는 사람 한 명이며 금액·시간이 아니다. 초기 available = 5에서 count = 2의 반환은 3이다. 실제 동시 예약이나 영구 저장은 이 계약에서 제외한다.

호출자는 int reserve(int count)라는 서명만으로 반환값이 예약한 수인지, 예약 뒤 잔여 수인지, 성공 여부 코드인지 알 수 없다. 문서에는 입력 단위와 허용 경계, 반환 의미, 수정하는 상태, 예외와 실패 보존을 써야 한다. @param/@return/@throws 태그와 본문 효과 설명을 연결하되 문서 생성 성공을 내용의 정확성 증명으로 쓰지 않는다.

같은 서명에서 반환을 잔여 수가 아닌 예약한 수로 바꾸면 count = 2의 관찰은 3에서 2로 달라진다. 파일을 찾는 데 성공하거나 이전 호출 코드가 링크된다는 사실만으로 동작 계약이 보존되는 것은 아니다. 여기서는 일반적인 모든 바이너리 호환 조건을 증명하지 않고 특정 입력의 동작 변화만 비교한다. 각 예제는 새 초기 상태에서 시작한다. package의 이름 계층도 하위 package에 부모의 비공개 접근을 자동 제공하는 계약이 아니다.

호출자가 찾는 이름

Price의 완전한 이름은 lesson.price.Price다. 관례적인 source root src/main/java 아래 lesson/price/Price.java에 둔다. 테스트는 src/test/java 아래 같은 package로 배치한다. 출력 class root와 source root는 다른 역할이다.

package 이름의 점은 디렉터리 계층으로 대응시켜 도구가 찾기 쉽게 만든다. 하위 package가 이름상 포함된다고 부모 package의 접근 권한을 자동 공유하는 것은 아니다. 이름 구조와 public·package-private 같은 접근 제어를 구별한다.

사용 계약을 주석으로 남긴다

pay의 문서에는 구매액이 음이 아닌 int이며 금액 단위는 이 가상 예제의 원, 1000 이상에서 100 할인, 그 외 원값, 음수 예외라고 적는다. 시간·파일·네트워크 부작용을 수행하지 않는 함수임도 알릴 수 있다. 사용자에게 중요한 약속을 우선한다.

Javadoc은 선언과 문서 주석을 읽어 HTML API 자료를 만든다. @param은 입력, @return은 결과, @throws는 실패 계약을 설명한다. 본문이 실제 구현과 일치하는지는 저자와 검토자의 책임이며 생성 도구가 모든 의미를 증명하지 않는다.

문서와 코드가 함께 바뀐다

할인 기준을 2000으로 바꾸면 코드와 API 설명, 기대값 시험을 함께 갱신한다. 새 이름이나 예외 정책을 공개하면 기존 소비자에게 영향이 있는지 확인한다. 문서가 생성됐다는 사실과 이전 API와 호환된다는 사실은 별도다.

Javadoc의 문서 생성·DocLint와 HTML 확인을 통해 흔한 형식 문제를 찾을 수 있지만 실제 사용자 이해까지 검증했다고 쓰지 않는다. 여기서는 주석의 계약과 코드·시험을 이론으로 대조하고 HTML 생성은 하지 않았다.

준비 개념과 학습 목표

준비 개념

  • main과 package

  • class 파일

  • 빌드 환경

학습 목표

  • 일반 JAR와 실행 진입점을 구별한다.

클래스 바이트가 같으면 JAR 바이트도 반드시 같을까?

자체 앱의 완전한 이름은 school.Main이며 외부 libs/util.jar의 util.Helper를 실행 중 사용한다. 일반 포장 계획에서 out/school/Main.class만 app.jar 안의 school/Main.class로 포함하고 Main-Class를 school.Main으로 지정했다. 파일이 포함되는 위치와 실행에서 필요한 외부 라이브러리 제공은 따로 점검한다. 클래스 파일을 app.jar의 out/school/Main.class로 넣으면 source/output root를 archive entry의 일부로 잘못 포함한 것이다.

별도 두 포장 기록이 같은 클래스·자원 바이트를 포함해도 항목의 저장 시각 같은 archive 메타데이터가 다르면 전체 바이트는 달라질 수 있다. JAR 도구의 --date는 해당 시각을 지정하는 방법이지만 입력 순서·도구·압축·자원 등 모든 변동을 혼자 통제한다고 주장하지 않는다. 기록을 맞추는 계획과 실제 재빌드/hash 비교를 분리한다.

일반 -jar 실행에서 다른 class path 설정이 무시되는 조건을 주의한다. 외부 util.jar를 -cp에 적고 동시에 -jar app.jar를 쓰는 것으로 실행 요구가 해결됐다고 단정하지 않는다. 별도 class 방식으로 main 이름과 앱·외부 JAR의 classpath를 제공하거나 올바른 manifest Class-Path 등 명시 배포 설계를 선택해야 한다. 여기서는 설치·명령·네트워크 업로드를 수행하지 않는다. --release로 앱을 목표 버전에 맞추는 설정도 이미 만든 외부 의존성의 class 바이트를 자동으로 다시 번역하는 작업이 아니다.

실행 시작점을 명시한다

일반 JAR는 클래스와 자원을 묶는 archive이며 모든 JAR가 java -jar로 시작되는 것은 아니다. 자체 Main은 public static void main(String[] args)를 진입점으로 가진다. 실행 JAR에서는 Main-Class와 실제 클래스 경로를 맞춘다.

jar 도구는 archive 생성과 목록 확인을 제공한다. 클래스가 포장됐다는 것만으로 모든 외부 라이브러리와 필요한 runtime이 함께 들어간다고 보지 않는다. 이 자체 프로그램은 외부 runtime 패키지 없이 JDK 표준과 Price만 사용한다.

빌드 조건과 runtime 조건

프로젝트에 compile JDK, target release, 실행 JDK, 운영체제, 명령, 설정과 파일 위치를 적는다. javac --release 17을 쓴 예제라면 Java 17 목표로 컴파일하고 그에 맞는 runtime을 제안한다. 실제 JDK 설치와 실행 결과는 별도 확인 대상이다.

시험용 JUnit 파일을 production 산출물에 넣는 것과 앱의 runtime 요구는 다른 선택이다. 뒤 예제는 main source 두 파일만 직접 컴파일해 JAR를 만들도록 제안한다. 이 경로는 JUnit을 실행하지 않으므로 앞 시험이 실제 통과한 증거가 아니다.

검증 단계를 기록한다

소스 revision·도구 버전·의존성·빌드 옵션과 명령은 절차 재현의 입력이다. 소스에서 다시 만들기, 새 환경에서 실행하기, 테스트하기, JAR hash가 같은지 비교하기를 따로 기록한다. 같은 revision만으로 같은 바이트를 자동 보장하지 않는다.

Maven deploy의 원격 artifact 공유와 앱 서버의 실제 운영 배포를 구별한다. 여기서는 로컬 JAR 실행 계획만 제안하며 원격 repository나 서버에 업로드하지 않는다. 생성물의 시각·경로·압축·도구 차이는 바이트 비교의 추가 조건이다.

(2) 각 시험은 새 잔액 5에서 시작한다. withdraw는 1 ≤ k ≤ balance만 true와 차감, 그 외 false와 보존이다. k = 6에서 반환 false만 확인한 시험을 보완하라. 별도 static calls는 0에서 A/B가 각각 증가 후 1을 기대한다. (3) 다른 예약 객체의 available은 5이고 reserve(2)는 잔여를 반환하며 reserve(6)는 예외와 보존이다. 문서에 반환은 예약 수라고 적혀 있다. 수정 계약과 두 기대를 적어라. (4) school.Main은 util.Helper를 필요로 하지만 app.jar에는 school/Main.class만 있고 외부 파일과 manifest 경로가 없다. class 내용은 같은 두 JAR의 저장 시각은 다르다. 의존성·동일 바이트·실제 실행의 현재 판정을 각각 적어라. 모든 graph/시험/예약 비교는 명시한 별도 초기 상태이며 실제 도구·학생 실행은 미수행이다.

힌트 1

Maven 남은 경로, 지갑 종료 상태, 예약 반환 의미를 각 장부에서 확인한다.

힌트 2

static 공유 상태와 새 인스턴스, 클래스 내용과 전체 archive, 포장과 runtime 제공을 따로 기록한다.

풀이와 답 확인

  1. 원래 같은 깊이의 A 먼저 선언은 X 1이다. A 쪽 제외 후 B → X 2가 남으므로 X 2다. 호환 시험은 아직 없다.

  2. withdraw(6)의 정상 기대는 false와 잔액 5다. 반환만 확인하면 먼저 차감해 −1을 남기는 결함을 놓치므로 상태 보존 비교를 추가한다. static calls는 A 뒤 1, B 뒤 2이며 두 새 시험 인스턴스만으로 초기화되지 않는다.

  3. reserve(2)는 반환 3과 available 3, 별도 reserve(6)는 예외와 available 5다. 반환 문서는 예약한 count가 아닌 차감 후 잔여 자리 수로 고치고 예외 시 보존을 적는다.

  4. util.Helper 제공이 빠졌으므로 포장만으로 runtime 요구 충족을 보고할 수 없다. 동일 class 내용도 시각 메타데이터가 다르다는 가정하에 전체 archive 바이트는 다르다. 실제 hash 비교·빌드·시험·실행은 미수행이며 이론 판정과 구별한다.

원래 선택은 X 1이고 한 경로 제외 뒤에는 X 2다. 지갑의 거절은 false와 잔액 5를 함께 확인하며 static calls는 첫 시험 뒤 1, 둘째 시험 뒤 2다. reserve(2)는 3을 반환하고 available도 3이다. 별도 reserve(6)는 예외가 발생하고 available은 5로 유지된다. 외부 의존성 제공이 빠지고 archive 시각 필드가 달라 내용 동일성만으로 전체 바이트 동일성을 주장하지 않는다. 실제 검사 결과는 아직 없다.

해결한 뒤 점검할 것

  • 동일 깊이의 선언 순서와 한 경로 제외 후 남은 X를 정확히 설명한다.

  • 지갑의 반환 및 실패 보존과 static fixture 공유를 별도 관찰로 설계한다.

  • 예약 문서에 단위·수용 범위·잔여 반환·예외와 상태 보존을 포함한다.

  • 포장 entry·외부 의존성·메타데이터·실제 hash 비교·실행을 서로 다른 증거로 적는다.

  • 새 Java/빌드/시험/포장/실행/학생 관찰을 완료한 것처럼 기록하지 않는다.
