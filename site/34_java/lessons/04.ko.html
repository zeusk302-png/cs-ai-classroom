소단원 4.1

constructor·접근제어

객체의 첫 상태를 누가 검사하고 외부는 무엇을 바꿀 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 클래스는 객체의 필드와 행동을 정의하는 타입이다. new Span(2,5)는 생성자에 값을 전달해 새 인스턴스를 초기화한다.

  • this.low는 현재 객체의 필드이고 매개변수 low는 호출의 지역 값이다. ≤를 만족하는 닫힌 정수 구간은 양끝 값을 포함한다.

학습 목표

  • 생성자와 일반 메서드를 구별한다.

  • 접근제어와 의미적 입력 검사를 분리한다.

  • 정상 생성 직후의 불변조건을 설명한다.

new 식이 실패하면 생성 중에 저장한 다른 상태도 모두 원상복구될까?

앞 본문의 Span은 검사한 뒤 필드를 저장하고 this를 외부에 넘기지 않았다. 새 비교 모형은 private int low,high와 static Span leaked를 가진다. 나쁜 생성자는 low를 저장하고 leaked=this를 실행한 뒤 low>high면 예외를 던지며, 정상 갈래에서만 high를 저장한다. high의 별도 초기식은 없다. 각 사례는 leaked가 null인 독립 시작이고 다른 스레드·할당 실패는 제외한다.

new Span(7,3)이 정상 값을 주지 않아도 leaked에는 부분 객체의 참조가 남는다. 인스턴스 int 필드의 처음 값 0에서 low만 7로 바뀌었으므로 이 참조로 관찰하는 상태는 low 7, high 0이다. private는 생성자 자신이 참조를 공개하는 것을 막지 않는다. 정상 객체만 외부에 존재한다는 원래 불변조건 증명의 전제가 깨진다.

대안은 두 인수를 읽기만 하여 검사하고, 유효하면 두 필드를 저장한 뒤 필요한 공개를 수행한다. 이는 지정한 순차 모형의 실패 보존 계획이다. 생성자 접근제어·정상 new 반환·외부 장부 변화는 각각 별도 계약이며 일반 동시 공개 안전성을 시험한 것이 아니다.

생성은 초기 상태의 계약

생성자는 클래스 이름과 같고 반환 타입을 쓰지 않는다. Java11에서 생성자 호출은 new 또는 다른 생성자의 this/super 호출 문법과 관계되며 일반 메서드처럼 객체에 대고 반복 호출하는 초기화 메서드가 아니다. void Span(...)라고 쓰면 생성자가 아닌 반환형 void의 메서드 선언이다.

아래 Span의 정상 생성 사전조건은 low≤high다. 위반이면 IllegalArgumentException을 던지고 new 식은 정상 결과를 돌려주지 않는다. 완전한 예제는 정상 생성만 실행했으며 잘못된 생성자의 예외 경로는 종이로 설명한다. 초기화 실패에서 부분 객체를 외부에 누출하지 않는 이 구현 조건을 유지한다.

선언하지 않을 때와 직접 선언할 때

일반 클래스에 생성자 선언이 하나도 없으면 컴파일러가 기본 생성자를 암묵적으로 선언한다. 직접 Span(int,int)를 선언하면 별도의 Span()가 자동 추가되지 않는다. 무인수 생성자가 필요하면 유효한 기본 상태와 함께 명시적으로 설계해야 한다.

이 단원은 단순한 정적 중첩 클래스 예제다. Java11의 생성자 본문에서 명시적인 this(...) 또는 super(...) 호출은 첫 문장에 놓이며 this 호출 사슬이 순환해서는 안 된다. 기본 생성자도 상위 클래스의 적합한 무인수 생성자를 호출할 수 있어야 한다.

접근 가능성과 올바른 상태

private 필드는 예제의 바깥 클라이언트에게 직접 쓰기를 제공하지 않는다. 정확한 private 접근 범위는 그 선언을 둘러싼 최상위 타입의 본문까지 포함하므로 단순히 한 객체만 접근 가능하다는 뜻은 아니다. 같은 클래스의 메서드는 다른 인스턴스의 private 필드도 접근할 수 있다.

접근제어가 없는 클래스 멤버·생성자는 package 접근이며 protected는 같은 패키지 또는 추가 조건을 만족하는 하위 클래스 접근이다. public 멤버도 타입과 모듈의 접근 조건을 무시하지 않는다. 예제에서는 같은 소스의 클라이언트가 공개 contains만 사용하고 low/high를 직접 변경하는 코드를 실행하지 않는다.

public class ConstructorDemo {
    static final class Span {
        private final int low, high;
        public Span(int low, int high) {
            if (low > high) throw new IllegalArgumentException("low > high");
            this.low=low; this.high=high;
        }
        public boolean contains(int x) { return low<=x && x<=high; }
    }
    public static void main(String[] args) {
        Span s=new Span(2,5);
        System.out.println(s.contains(2)+" "+s.contains(6));
    }
}

첫 행의 high 0은 전달한 인수 3을 저장한 값이 아니다. 초기 필드 값과 실행한 대입을 구별하여 예외가 발생한 정확한 지점을 읽는다.

중간 과정을 따라가는 예제

Span(2,5)의 정상 생성과 contains(2), contains(6)를 추적하라.

  1. 2≤5이므로 생성자의 검사에서 예외를 던지지 않는다.

  2. this.low=2,this.high=5를 저장하여 low≤high가 성립한다.

  3. contains(2)는 2≤2와 2≤5가 모두 참이다.

  4. contains(6)는 2≤6이 참이지만 6≤5가 거짓이다.

실제 JDK11 stdout은 true false와 줄바꿈이다. 소스와 출력 해시는 별도 실행 기록에 있다.

조건을 바꾸어 비교하기

실패한 new와 남은 부분 객체

나쁜 생성자에 (7,3)을 전달하여 세 사건과 외부 장부를 적어라.

  1. low=7을 저장한다. high는 기본 값 0이다.

  2. leaked=this로 참조를 공개한 뒤 7>3을 검사하여 예외로 끝난다.

정상 new 결과는 없지만 leaked가 가리키는 상태는 (7,0)이다.

비교할 점

정상 반환의 부재가 이미 수행한 대입의 취소를 뜻하지 않는다.

호출 경로와 유효 기본 상태

유일한 Span(int,int) 생성자가 있는 클래스에 무인수 생성자를 추가하려 한다. this(0,0) 위임과 void Span() 메서드를 비교하라.

  1. 명시 Span(){this(0,0);}는 같은 클래스 생성자를 첫 문장에서 호출한다.

  2. void Span()은 반환 타입이 있는 일반 메서드로 new Span()의 생성자를 제공하지 않는다.

위임한 정상 상태는 닫힌 구간 [0,0]이다. 일반 메서드만 추가해도 무인수 생성자가 자동 생기지는 않는다.

비교할 점

유효한 상태 선택과 언어의 생성자 문법을 함께 검사한다.

종이와 본문으로 직접 해보기

Span(7,3)과 Span(4,4)의 정상 생성 여부와 후자의 contains(4)를 종이로 판단하라.

힌트 보기

빈 길이처럼 보여도 양끝이 같은 닫힌 구간의 한 정수는 포함된다.

풀이 보기

7>3은 검사 실패라 정상 객체 결과를 주지 않는다. 4≤4는 성공하고 contains(4)=true다. 이 변형 생성은 실행하지 않았다.

오해와 반례

클래스가 public이면 어느 생성자나 호출 가능하다.

생성자 접근제어는 별도로 검사한다. public 클래스에 private 생성자만 제공하면 해당 접근 범위 밖에서 직접 new를 할 수 없다. 타입 접근도 모듈 조건과 함께 읽어야 한다.

연습 1 · 값과 상태 예측

나쁜 생성자 (0,−1)은 leaked의 두 필드를 어떻게 남기는가?

힌트 1

힌트 2

풀이와 답 확인

  2. 0>−1로 실패하여 high는 기본 값 0이다.

한 단계 더

정상 생성자는 low≤high를 검사한 뒤 두 값을 저장한다. 정상 결과 객체에서 두 final int 필드를 이후 대입할 수 없고 contains는 읽기만 하므로 각 호출 전후 low≤high가 보존된다. 생성자에서 this를 외부 콜백에 넘기거나 검사를 생략하면 이 짧은 초기화 증명의 전제가 바뀐다. 접근 제한과 필드 final을 결합하더라도 생성 중 객체 누출과 동시 공개 문제를 자동 해결했다고 확대하지 않는다.

instance·static

두 물건의 횟수는 따로 세는데 만들어진 총수는 왜 함께 셀까?

준비 개념과 학습 목표

준비 개념

  • 객체 참조 변수 a,b가 다른 new 결과를 가리키면 서로 다른 인스턴스다. 같은 객체를 가리키는 참조 둘은 별도 객체를 만들지 않는다.

  • static 필드는 클래스와 관계되는 상태다. 이 예제는 새 JVM 실행에서 해당 Counter 클래스 하나와 단일 스레드 순차 호출만 사용한다.

학습 목표

  • 인스턴스 필드와 클래스 필드의 상태를 구별한다.

  • static 메서드가 객체를 필요로 하는 경우를 설명한다.

  • 공통 상태의 동시성·범위 한계를 명시한다.

static 호출 앞에 객체 식을 쓰면 그 식의 효과도 사라질까?

앞 본문의 Counter.createdCount는 static이고 tick은 instance 메서드다. 새 순차 모형은 이미 초기화한 클래스 C에 static int total=5와 static int read(){return total;}을 둔다. static C probe()는 로그에 P를 추가하고 null을 반환한다. probe().read()는 probe 식을 평가하지만 read에 수신 객체를 제공하지 않는다. null 결과를 버리고 static read를 호출하므로 정상 값은 5이고 로그는 P다.

C.read()처럼 타입 이름을 쓰면 불필요한 probe 효과가 없다. C x=null; x.read()도 클래스의 static 호출이라 null 역참조 호출과 같지 않다. 반대로 같은 C가 instance int local(){return 8;}을 선언한 상태의 x.local()은 수신 참조 null 때문에 NullPointerException이다. 서로 다른 호출은 각각 빈 로그와 동일한 초기 total에서 독립 비교한다.

이 결과는 인스턴스 표기로 static을 쓰라는 권장이 아니다. 클래스 이름 호출은 범위를 읽기 쉽게 한다. total 하나라는 언어 규칙도 총 생성 성공 수·동시 갱신·전역 JVM 상태를 자동 정의하지 않는다. 아래 숫자와 로그는 새 Java를 실행하지 않은 손모형이다.

먼저 확인할 개념
  • static 상태와 수신 객체

    클래스의 공통 칸과 인스턴스 메서드의 this를 나눈다.

  • 생성 실패와 효과

    static 계수의 증가 위치가 실패 계약에 영향을 준다.

각 객체의 상자와 공통 상자

Counter의 local은 각 new마다 별도이며 a의 tick이 b.local에 대입하지 않는다. created는 같은 Counter 클래스 정의에 속한 필드 하나여서 두 생성자가 같은 값을 증가시킨다. 따라서 객체 도식에는 local 두 상자와 created 한 상자를 그린다.

전 세계 모든 JVM이나 모든 클래스 로더에 하나인 전역 수라고 일반화하지 않는다. 다른 JVM 또는 다른 로더가 정의한 클래스의 상태와 이 예제의 한 클래스 상태는 별개다. created는 생성 완료·실패·소멸과 관련된 정확한 설계를 필요로 하며 여기서는 정상 생성 횟수 두 번만 다룬다.

메서드의 수신 객체

a.tick()은 a가 가리킨 객체를 현재 this로 사용한다. static createdCount()에는 그와 같은 암묵적인 this가 없으므로 객체의 local을 직접 읽을 수 없다. static 메서드가 매개변수로 명시적 객체 참조를 받아 그 객체 메서드를 호출하는 것은 별개의 정상 사용이다.

Counter.createdCount()처럼 클래스 이름으로 호출하면 공통 상태 접근 의도가 드러난다. static 멤버를 인스턴스 이름으로 쓸 수 있는 경우도 있지만 그것을 인스턴스별 저장이라고 해석하지 말자. C의 함수 내부 static 지역 변수와 Java의 클래스 필드 규칙을 그대로 대응시키지 않는다.

공유가 안전을 뜻하지 않는다

예제의 ++created와 ++local은 정확히 작은 값 범위에서 실행되어 정수 표현 문제가 없다. 일반적으로 Java int 증가가 수학적 무한 정수를 표현하는 것은 아니며 overflow 후 래핑될 수 있으므로 ID 유일성 정책이라면 범위를 별도로 관리해야 한다.

static은 원자적 증가나 동기화를 지정하지 않는다. 여러 스레드가 동시에 읽고 증가하면 순차 상태표로 증명한 생성 횟수 결과를 그대로 보장할 수 없다. volatile을 붙이는 것만으로 복합 ++를 원자화하는 것도 아니다. 이 단원은 스레드 실행이나 ID 서비스 검증을 수행하지 않았다.

public class StaticDemo {
    static final class Counter {
        private int local=0;
        private static int created=0;
        Counter() { ++created; }
        void tick() { ++local; }
        int value() { return local; }
        static int createdCount() { return created; }
    }
    public static void main(String[] args) {
        Counter a=new Counter(), b=new Counter();
        a.tick(); a.tick(); b.tick();
        System.out.println(a.value()+" "+b.value()+" "+Counter.createdCount());
    }
}

소단원 4.3

불변조건·encapsulation

필드를 숨기기만 하면 잘못된 상태가 사라질까?

준비 개념과 학습 목표

준비 개념

  • 불변조건은 허용되는 객체 상태에 늘 성립해야 하는 술어다. 재고의 정수 count,capacity에 대해 0≤count≤capacity를 사용한다.

  • 캡슐화는 표현과 변경 경로를 인터페이스 뒤에서 관리하는 설계다. 불변조건이 보존되는 객체도 count가 바뀌므로 불변 객체와 같지 않다.

학습 목표

  • 생성·변경·실패의 상태 계약을 쓴다.

  • 표현 범위를 지키는 검사 순서를 설명한다.

  • final 참조와 깊은 불변성을 구별한다.

배열의 바깥 참조만 복사하면 중첩된 상태도 보호될까?

앞 본문의 Snapshot은 int[]라 원소가 정수 값이다. 새 얕은 보관 모형은 int[][] source를 source.clone()하여 private final int[][] data에 저장하고 values()도 data.clone()을 반환한다. source의 두 칸은 같은 행 R={2,5}를 가리킨다. 바깥 배열을 새로 만들었어도 두 원소는 모두 원래 R을 참조한다.

source[0][0]=9는 R을 바꾸므로 내부 두 행의 첫 값도 9다. 반면 source[0]=new int[]{7,8}은 source의 바깥 칸만 바꾸므로 내부 첫 칸은 여전히 R이다. 반환 바깥 복사 out[1][1]=6도 내부 R의 둘째 값을 6으로 만든다. final과 두 번의 바깥 clone만으로 깊은 값 보존을 증명하지 않는다.

각 행을 독립 clone하여 보관하면 값 별칭은 끊을 수 있지만 원본이 같은 행을 두 번 썼다는 공유 관계도 끊는다. 계약이 정수 값 행렬만인지 행 정체성 관계까지 보존하는지 먼저 정한다. 아래 깊은 복사 대안은 비null 바깥 배열과 비null 행, 동시 변경 없음, 필요한 할당 성공을 전제로 하며 실제 메모리 실행은 하지 않았다.

먼저 확인할 개념
  • primitive 복사와 final 참조

    한 단계 복사가 충분했던 타입 전제를 바꿔 읽는다.

  • 객체별 상태와 참조 별칭

    바깥 배열의 칸과 공유 행 객체를 다른 상자로 그린다.

정상 경계에서 보장하는 상태

Stock 생성자는 capacity≥0와 0≤count≤capacity를 검사한다. take는 n<0 또는 n>count면 false를 반환하고 상태를 바꾸지 않는다. 허용된 n에만 count-=n을 수행하므로 새 count도 0 이상이다. put은 남은 여유와 요청을 비교하여 상한을 지킨다.

put에서 count+n>capacity를 먼저 계산하면 int 덧셈이 overflow되어 잘못된 비교가 될 수 있다. 이미 불변조건이 참이면 capacity-count는 0…Integer.MAX_VALUE 안이므로 n>capacity-count 비교로 검사하고, 허용된 n에만 count+n을 계산해 표현 범위와 불변조건을 동시에 지킨다.

private과 검사 없는 setter

private은 직접 필드 쓰기 경로를 제한하지만 public void setCount(int x){count=x;}처럼 검사 없는 메서드를 열면 count=-1 상태를 만들 수 있다. getter/setter를 모든 필드에 붙이는 것이 캡슐화의 완료 기준은 아니다. 사용자가 해야 하는 일과 상태 계약에 맞는 동작을 제공해야 한다.

Stock은 변경 가능한 객체이며 불변조건이 유지되는 객체다. Snapshot은 저장한 배열의 값이 외부 변경으로 달라지지 않게 만들려는 별도 예다. private final int[] 필드는 배열 참조의 재대입을 막지만 그 배열 원소의 변경을 자동으로 막지 않는다.

외부 별칭을 차단하기

Snapshot은 입력 int[]를 clone하여 외부 원본 배열과 다른 배열을 보관하고 반환 때도 clone한다. 따라서 입력이나 결과 배열을 수정해도 내부 배열 원소는 그대로다. int 원소에는 중첩된 수정 가능한 객체 참조가 없어서 한 단계 복사로 이 예제의 값 보존 조건을 충족한다.

객체 참조 배열이나 중첩 목록을 같은 방식으로 얕게 복사하면 원소 객체의 별칭이 남을 수 있다. 방어적 복사는 필요한 깊이와 타입 계약을 명시해야 한다. 예제의 입력은 null이 아니며 동시 변경·반사로 private 우회·직렬화 우회 같은 별도 경로를 시험하지 않았다.

public class InvariantDemo {
    static final class Stock {
        private final int capacity;
        private int count;
        Stock(int capacity,int count) {
            if(capacity<0 || count<0 || count>capacity) throw new IllegalArgumentException();
            this.capacity=capacity; this.count=count;
        }
        boolean take(int n) {
            if(n<0 || n>count) return false;
            count-=n; return true;
        }
        boolean put(int n) {
            if(n<0 || n>capacity-count) return false;
            count+=n; return true;
        }
        int count() { return count; }
    }
    static final class Snapshot {
        private final int[] data;
        Snapshot(int[] source) { data=source.clone(); }
        int[] values() { return data.clone(); }
    }
    public static void main(String[] args) {
        Stock s=new Stock(5,4);
        boolean a=s.take(3), b=s.put(5);
        int[] input={1,2}; Snapshot snap=new Snapshot(input);
        input[0]=9; int[] output=snap.values(); output[1]=8;
        System.out.println(a+" "+b+" "+s.count()+" "+snap.values()[0]+" "+snap.values()[1]);
    }
}

값 복사와 공유 관계 복사

독립 시작 R={2,5}, source={R,R}에서 행마다 따로 clone한 deep={U,V}를 만들었다. U/V는 다른 새 행이다.

  2. deep[0][0]=9는 U만 바꾸므로 V 첫 값은 2다.

준비 개념과 학습 목표

준비 개념

  • 합성은 객체가 다른 객체를 구성 요소로 사용하여 작업을 수행하는 설계다. 이 코드의 필드 참조는 자동으로 독점 소유권을 증명하지 않는다.

  • 재고 감소는 변경이며 영수증의 수량·금액은 생성 뒤 고정 값이다. 본문의 화폐 단위는 가상 요금 단위이고 실제 결제 규정이 아니다.

학습 목표

  • 협력 객체의 각 계약을 분리한다.

  • 성공·실패의 상태 변화 순서를 추적한다.

재고 감소 뒤 보고 실패를 null로 바꾸면 거절한 주문이 되는가?

앞 Checkout은 영수증을 준비한 뒤 take를 호출하고 이후에는 반환만 했다. 새 잘못된 확장은 take 성공 뒤 audit(receipt)를 호출하고 audit 예외를 catch하여 null을 반환한다. audit은 이 모형에서 외부 장부 A를 남긴 뒤 예외를 던질 수 있다고 지정한다. 초기 재고는 4, 가격은 10, 요청은 3이다. 동일한 주문에 자동 재시도 효과를 추가하기 전에 실패 반환의 의미부터 검사한다.

역할을 계약으로 나누기

Stock은 남은 수량과 take의 비음수/충분 재고 검사를 책임진다. Receipt는 수량과 총액을 고정한다. Checkout은 요청 수량과 가격 계약을 검사한 뒤 두 역할을 연결한다. 세 클래스로 나누었다는 숫자 자체보다 각 변경의 근거와 실패 결과가 어디에 있는지 설명할 수 있어야 한다.

합성은 상속의 is-a 관계를 자동 요구하지 않는다. Checkout이 Stock을 사용한다고 Checkout이 Stock의 모든 동작을 대신 제공하는 하위 타입이라는 뜻은 아니다. 또한 생성자에 받은 Stock 참조를 보관하므로 다른 클라이언트가 같은 재고를 사용할 가능성을 없앴다고 주장하지 않는다.

검사하고 준비한 뒤 변경하기

buy의 허용 요청은 0≤n≤1000이고 가격은 생성 때 0≤price≤1000으로 제한한다. Receipt의 총액 n*price는 최대 1,000,000이므로 Java int에서 표현 가능하다. 음수 수량이나 범위 밖 요청에는 null을 반환하며 stock.take를 호출하지 않는다.

아래 코드는 재고를 줄이기 전에 proposed 영수증을 정상 생성한다. 생성자 검증이나 메모리 할당 실패가 재고 감소보다 먼저 발생하도록 순서를 정한 것이다. 재고가 부족하면 준비한 객체를 반환하지 않고 null을 돌려주며 재고도 보존한다. 실제 저장·결제·네트워크 성공을 원자적으로 보장하는 코드는 아니다.

성공과 실세계 실패의 경계

단일 스레드에서 Stock.take가 예외 없이 자신의 계약을 지키고 다른 개입이 없으면 buy 성공은 재고를 n 감소시키고 해당 수량·총액의 Receipt를 반환한다. 실패 null은 이 함수가 재고를 감소시키지 않았다는 계약이다. 호출자는 null 여부를 검사하거나 성공이 증명된 경우에만 영수증 메서드를 호출해야 한다.

서로 다른 주문이 동시에 같은 Stock을 사용하면 검사·감소 전체의 보호가 필요하다. 실제 DB 이력 기록과 재고 변경, 외부 결제까지 묶으면 원자성·격리·중복 요청·실패 복구의 추가 계약을 세워야 한다. 객체 역할 분리와 이번 네 소스 실행만으로 그 시스템이 검증되었다고 보고하지 않는다.

public class CompositionDemo {
    static final class Stock {
        private int count;
        Stock(int count) {
            if(count<0) throw new IllegalArgumentException();
            this.count=count;
        }
        boolean take(int n) {
            if(n<0 || n>count) return false;
            count-=n; return true;
        }
        int remaining() { return count; }
    }
    static final class Receipt {
        private final int units,total;
        Receipt(int units,int price) {
            if(units<0 || units>1000 || price<0 || price>1000) throw new IllegalArgumentException();
            this.units=units; this.total=units*price;
        }
        int units() { return units; }
        int total() { return total; }
    }
    static final class Checkout {
        private final Stock stock;
        private final int price;
        Checkout(Stock stock,int price) {
            if(stock==null || price<0 || price>1000) throw new IllegalArgumentException();
            this.stock=stock; this.price=price;
        }
        Receipt buy(int n) {
            if(n<0 || n>1000) return null;
            Receipt proposed=new Receipt(n,price);
            if(!stock.take(n)) return null;
            return proposed;
        }
    }
    public static void main(String[] args) {
        Stock stock=new Stock(4); Checkout shop=new Checkout(stock,10);
        Receipt r=shop.buy(3);
        System.out.println(r.units()+" "+r.total()+" "+stock.remaining());
    }
}
