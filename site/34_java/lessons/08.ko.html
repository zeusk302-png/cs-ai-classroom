generic class·method

Object 상자에서 꺼낼 때마다 강제 형변환해야 할까?

준비 개념과 학습 목표

준비 개념

  • String·Integer

  • 정적 타입 검사

학습 목표

  • 타입 매개변수와 타입 인자를 구별한다.

  • generic class 와 method 의 타입 범위를 추적한다.

값을 그대로 돌려줘도 호출에서 선택한 타입은 같을까?

앞 본문의 same은 전달한 참조를 그대로 반환했다. 새 자체 메서드 id는 static <U> U id(U x) { return x; }다. id의 몸체는 값 변환을 하지 않지만 명시한 타입 인자는 호출 표현의 정적 타입을 정한다. String a = id("go")의 간단한 문맥과 Object b = Util.<Object>id("go")를 비교하면 둘 다 같은 문자열 참조를 반환할 수 있지만 첫 결과의 정적 타입은 String, 둘째 명시 호출의 결과 타입은 Object다.

정적 결과 타입 Object가 실제 객체를 Object라는 새 객체로 바꾸는 것은 아니다. b.length()는 Object에 그런 메서드가 선언되지 않아 그 표현의 타입 조건을 만족하지 못한다. 문자열 참조라는 별도 정보로 안전한 검사·변환을 설계하는 일은 다른 단계다. generic이 호출마다 런타임 클래스를 새로 만드는 것으로 설명하지 않는다.

클래스와 메서드의 타입 매개변수도 별개다. 자체 Holder<T>는 T value를 보관하고 인스턴스 메서드 <U> U echo(U x)는 x만 반환한다. Holder<String> h가 value="keep"를 보관할 때 h.<Integer>echo(4)는 Integer 결과 4를 반환할 수 있으며 저장 value의 String 계약을 바꾸지 않는다. 클래스 T와 메서드 U의 자리·필드 효과를 이름별로 추적한다. 아래 모든 사례는 손으로 소스 조건을 판단하며 javac/JVM 실행은 미수행이다.

상자의 내용 타입을 약속하기

class Box<T>의 T 는 타입 매개변수이고 Box<String>의 String 은 구체 타입 인자다. 상자에 넣고 꺼내는 메서드의 T 자리가 함께 String 으로 해석되어 잘못된 타입을 일찍 검사한다. 변수 이름 T 가 특별한 예약어인 것은 아니다.

기본 타입 int 를 Box<int>로 직접 지정할 수는 없다. Box<Integer>와 boxing 을 사용한다. generic 은 참조가 null 이 아니라는 약속까지 자동으로 만들지 않는다. Box<String>에 null 을 넣는 일은 타입 자체로 거절하지 않으므로 별도 계약이 필요하다.

class Box<T> {
  private T value;
  void set(T x) { value = x; }
  T get() { return value; }
}

메서드만의 타입 자리

static <T> T same(T x)처럼 반환 타입 앞 <T>는 메서드가 자기 타입 매개변수를 선언한다. 클래스가 generic 이 아니어도 generic method 를 정의할 수 있다. 클래스 T 와 메서드 T 는 같은 철자라도 선언 범위가 다를 수 있으므로 초보 예제에서는 이름을 구별한다.

호출의 인자와 문맥에서 타입 인자를 추론하거나 명시할 수 있다. same("hi")를 String 으로 읽는 간단한 경우와 서로 다른 인자의 공통 타입 추론은 복잡도가 다르다. 여기서는 단일 인자와 명시한 문맥만 사용하고 모든 호출이 첫 인자의 정확한 런타임 클래스로 정해진다고 일반화하지 않는다.

static <U> U same(U x) { return x; }

타입 안전성의 범위

Box<String> b = new Box<>();에서 diamond <>는 문맥에 따라 타입 인자를 추론한다. b.set("hi")는 맞고 b.set(7)는 String 자리와 Integer 가 맞지 않아 컴파일 시 거절될 것으로 추론한다. 원래 get 의 결과 타입은 String 이다.

raw type 과 unchecked 형변환을 섞으면 generic 의 정적 보장을 우회할 수 있다. 따라서 generic 이름만 보인다고 모든 프로그램이 안전한 것은 아니다. 여기 예제는 raw 사용·반사·동시 변경을 제외하고 소스 타입만 종이로 판단하며 javac 를 실제 실행하지 않는다.

Box<String> b = new Box<>();
b.set("hi");
String s = b.get();

각 행은 명시한 선언의 별도 호출이다. echo는 필드 쓰기를 하지 않는 몸체이므로 결과를 반환해도 value를 바꾸지 않는다. 타입 인자·정적 타입·객체 값·상태 효과를 각 열로 읽는다.

중간 과정을 따라가는 예제

위 자체 Box<String>에 "hi"를 넣고 꺼낸다. b.set(7), Box<int>, Box<Integer>에7 넣기를 각각 판정하고 same("go")의 결과를 추론하라.

  1. b 의 T 는 String 이므로 set 의 인자와 get 의 결과가 String 이다. 값은 "hi"다.

  2. b.set(7)는 boxed Integer 를 String 자리에 넣어 타입 불일치다.

  3. Box<int>는 기본 타입 인자라 거절된다. Box<Integer>에7 은 boxing 을 통해 허용된다.

  4. same("go")의 이 단순 문맥에서는 U=String, 결과 값 "go"와 타입 String 을 얻는다.

예상 "hi":String, 두 잘못된 소스는 거절, Integer 상자에는7 을 넣을 수 있다. same 결과는"go":String 이다.

조건을 바꾸어 비교하기

명시한 Object 결과와 문자열 객체

Util.<Object>id("go") 결과를 Object b에 대입했다. b.length()의 소스 조건과 실제 객체 종류를 비교한다.

  1. U가 Object여서 반환 표현의 정적 타입은 Object다.

  2. 입력 String 참조는 그대로 반환되지만 Object 선언에는 length가 없다.

b.length()는 현재 표현의 타입 조건을 만족하지 않는다. 객체가 문자열일 수 있다는 사실과 다르다.

비교할 점

실제 문자열을 새 Object 객체로 복사했다는 설명은 틀리다.

클래스의 T를 바꾸지 않는 메서드 U

Holder<String> h의 value가 "keep"이고 echo는 전달 참조만 반환한다. h.<Integer>echo(4) 뒤 get의 결과를 비교한다.

  1. 메서드 U는 Integer여서 echo의 결과는 boxed 4다.

  2. 필드 value의 타입은 클래스 T=String이고 몸체에 필드 쓰기가 없어 "keep"를 유지한다.

echo 결과는 Integer 4, get 결과는 String "keep"다.

비교할 점

메서드 타입 선택이 클래스 인자를 재설정하지 않는다.

종이와 본문으로 직접 해보기

Box<Integer> n 에9 를 넣고 꺼내 int x 에 대입하면 값은? Box<String>에 null 을 넣고 get().length()를 호출하면 타입 검사와 실행 안전성은 어떻게 다른가?

힌트 보기

Integer 의 unboxing 과 null 참조에 대한 메서드 호출을 구별한다. 동시 변경은 없다.

풀이 보기

9 를 꺼내 unboxing 하면 x=9 다. null 저장과 length() 호출은 소스 타입이 String 이라 검사 가능하지만 실제 그 참조가 null 이면 호출에서 NullPointerException 이 예상된다. 실제 실행 관측은 아니다.

오해와 반례

generic 타입이 붙으면 null 이나 모든 실행 예외도 막는다.

Box<String>에 null 을 넣는 소스는 타입 자체가 막지 않는다. null 에서 length()를 호출하는 안전성은 별도 계약이다.

연습 1 · 값과 상태 예측

힌트 2

풀이와 답 확인

  2. value에 대입하지 않으므로 저장 값은 "keep"다.

연습 2 · 오류 찾아 고치기

Util.<Object>id("go")가 String을 Object로 변환하여 문자열 정보를 삭제했다고 했다. 고쳐라.

힌트 1

id는 참조를 그대로 반환한다.

힌트 2

정적 타입과 실제 객체 종류를 별도로 적는다.

풀이와 답 확인

  1. 명시 U=Object는 결과의 정적 타입을 Object로 만든다.

  2. 실제 입력 String 객체는 바뀌지 않는다. 단지 그 표현으로 사용 가능한 메서드가 Object 계약에 따른다.

타입 정보의 정적 관점과 객체의 실제 값·정체성을 분리한다.

흔한 오답에서 다시 생각하기

모든 generic 호출은 타입 인자마다 새 객체를 만든다.

새 객체를 만드는 명령이 없는 id 몸체에서 그 효과를 추론할 수 없다.

힌트 2

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

힌트 1

힌트 2

풀이와 답 확인

  1. 명시 결과는 Object이고 o의 선언도 Object다.

  2. 현재 정적 타입 그대로는 Integer unboxing 대입 근거가 없어 적절한 타입 확인·변환 또는 처음부터 Integer 결과 문맥이 필요하다.

실제 Integer일 수 있어도 Object에서 int로 이 대입을 자동 허용하지 않는다.

boxing이 한 번 있었으므로 모든 Object가 int로 변환된다.

Object는 문자열 등도 담을 수 있어 정적 변환 규약을 생략할 수 없다.

원소 타입을 모르는 목록 안의 두 칸은 바꿀 수 있을까?

앞 본문의 extends는 임의 새 Integer를 모르는 목록에 넣지 못하게 했다. 그러나 같은 목록에서 읽은 두 값을 다시 그 목록의 두 칸으로 옮기는 것은 원소 종류를 새로 만들지 않는다. List<?>를 받아 내부 <T> helper(List<T> xs)에 넘기면 한 번 포획한 미지의 원소 타입을 T로 이름 붙여 get과 set의 관계를 유지할 수 있다. 이는 unknown을 Object로 바꾸어 모든 쓰기를 허용하는 raw 우회가 아니다.

새 helper의 절차는 T saved=xs.get(0), xs.set(0,xs.get(1)), xs.set(1,saved)다. 목록 길이 2 이상·set 지원·단일 스레드·호출 중 예외 없음이라는 실행 전제를 둔다. ["A","B"]를 ["B","A"]로 바꾸며 null이 실제 원소인 [null,"B"]도 ["B",null]로 옮긴다. helper의 타입 조건만으로 길이·수정 가능성·전체 실패 보존을 보장하지 않는다.

두 서로 다른 List<? extends Number>는 각기 다른 포획 타입을 가질 수 있다. Integer 목록 [2]와 Double 목록 [1.5]의 첫 칸을 교환하려는 계획은 같은 Number 상한만으로 안전하지 않다. 하나의 목록 내부 교환과 서로 다른 목록 사이의 교환을 구별하고, 실제 공통 타입 관계를 갖는 API를 따로 설계한다.

이름 있는 매개변수의 상한

<T extends Number>는 T 가 Number 또는 그 하위 타입이라는 제한이다. n.doubleValue()처럼 상한이 보장하는 메서드를 쓸 수 있다. 단순 T 만 알 때는 Number 전용 메서드를 안전하게 호출할 근거가 없다.

extends 라는 단어는 여기의 타입 경계를 표현한다. 클래스 선언의 상속과 문맥을 구별하고 interface 경계에도 같은 bound 문법을 쓸 수 있다는 점을 기억한다. null 은 참조 타입의 값이므로 bound 가 non-null 을 보장하지 않는다. 아래 twice 는 n 이 null 이 아니라는 전제다.

static <T extends Number> double twice(T n) {
  return 2 * n.doubleValue();
}

상한 wildcard 에서 읽기

List<? extends Number>는 원소의 정확한 타입은 모르지만 Number 이하임을 안다는 뜻이다. List<Integer>, List<Double>, List<Number>를 받을 수 있으며 꺼낸 값을 Number 로 읽는다. List<Object>는 Object 가 Number 보다 넓어서 이 관계에 맞지 않는다.

이 변수로 임의 Integer 를 add 할 수는 없다. 실제 목록이 List<Double>일 수 있기 때문이다. null 추가·clear·remove 가능성은 별개이고 실제 목록 구현이 수정을 허용하는지도 별개다. 읽기 역할이 편리하다는 말을 엄밀한 불변 객체 보장으로 바꾸지 않는다.

하한 wildcard 에서 넣기

List<? super Integer>는 정확한 원소 타입이 Integer 또는 그 상위 타입인 목록이다. List<Integer>, List<Number>, List<Object>를 받을 수 있고 Integer 값을 넣는 것은 타입상 안전하다. Double 은 임의로 넣을 수 없다. 실제 목록이 Integer 전용일 수 있기 때문이다.

꺼낸 값은 Object 로 읽을 수 있지만 언제나 Integer 라고 할 수는 없다. List<Number>에 기존 Double 이 들어 있었을 수 있다. 상한·하한 모두 어떤 리스트인지 모르기 때문에 가능한 모든 후보에서 안전한 연산만 허용한다.

List<? extends Number> in;
List<? super Integer> out;

같은 PECS 타입이 append와 자리 덮어쓰기의 차이도 알려 주나?

앞 본문의 자체 copy는 dst.add로 원소를 뒤에 추가했다. Collections.copy는 비슷한 extends/super 타입 관계를 갖지만 원본과 같은 인덱스에 set하여 덮어쓰고, 대상의 현재 size가 원본 size 이상이어야 한다. capacity를 넉넉히 예약했어도 size가 0인 ArrayList에는 기존 인덱스가 없다. 타입 관계와 실제 동작·크기 전제를 API별로 읽는다.

src=Integer [2,3], dst=Number [9.5,8.5,7.5]라는 서로 다른 수정 가능한 목록에서 자체 append는 [9.5,8.5,7.5,2,3], Collections.copy의 명시 계약은 [2,3,7.5]다. src가 제공하고 dst가 소비하는 T 관계는 모두 맞지만 효과는 다르다. Collections.copy의 인수 순서는 dest, src이며 앞 자체 함수의 src, dst 순서와도 다르다.

generic 목록은 null을 배제하지 않는다. 별도 자체 절차는 Integer 목록을 차례로 읽어 int로 unbox하여 제곱 값을 dst에 append한다. src=[2,null,3], dst=[9]이고 첫 append는 성공한다고 정하면 4를 추가한 뒤 null unbox에서 실패하여 dst=[9,4]가 남는다. 이는 실패 시 원본 대상 보존 계약을 만족하지 않는다. 후보 목록에서 검증·계산을 끝내고 그 후보 참조를 단일 스레드의 단일 상태 필드에 게시하는 별도 설계는 이 검증 실패의 부분 효과를 피할 수 있다.

먼저 확인할 개념
  • 입력 extends·출력 super와 실행 전제

    같은 타입 관계로도 API의 효과·별칭·수정 계약이 달라진다.

  • null과 unboxing의 한계

    Integer 목록이라는 선언만으로 모든 원소의 non-null을 보장하지 않는다.

컨테이너의 타입 관계

Java 의 List<Integer>는 List<Number>의 서브타입이 아니다. 이런 타입 인자 관계를 불공변이라고 부른다. Integer 자체의 상속 관계를 컨테이너에 그대로 옮기면 Number 목록을 통해 Double 을 Integer 목록에 넣는 문제가 생긴다.

List<? extends Number>처럼 wildcard 로 필요한 범위를 표현한다. Java 배열의 공변 관계와 런타임 저장 검사는 별도 방식이다. 배열과 generic 목록이 동일 규칙을 사용한다고 생각하면 컴파일 결과를 잘못 예측한다.

생산자와 소비자 관점

PECS 는 Producer Extends, Consumer Super 의 기억법이다. 우리 코드에 T 값을 제공하는 src 는 List<? extends T>, T 값을 받아 저장하는 dst 는 List<? super T>로 표현한다. 기준은 데이터가 코드로 들어오고 나가는 역할이며 변수 이름만으로 정하지 않는다.

읽고 쓰기 모두 정확한 같은 타입을 요구하면 List<T> 같은 표현이 필요할 수 있다. PECS 가 모든 API 설계를 자동 해결하지는 않는다. 반환 wildcard 는 호출자에게 다루기 어려운 타입을 줄 수 있으므로 실제 API 의 역할과 관계를 먼저 설계한다.

static <T> void copy(
    List<? extends T> src, List<? super T> dst) {
  for (T x : src) dst.add(x);
}

타입 조건과 실행 조건

Integer 입력에서 Number 출력으로 복사하려면 Integer≤T≤Number 를 만족해야 한다. T=Integer 또는 Number 를 선택할 수 있다. Double 입력에서 Integer 출력은 Double≤T≤Integer 를 만족할 수 없어 허용되지 않는다.

위 foreach 예제는 서로 다른 src/dst, 수정 가능한 dst, 순회 중 src 변경 없음이라는 실행 조건을 둔다. 같은 목록을 src 와 dst 로 넘겨 순회 중 크기를 늘리면 반복 계약을 깨뜨릴 수 있다. 컴파일 가능함과 모든 실행 조건이 충족됨을 구별한다.

앞 본문의 raw List는 Integer를 넣은 뒤 String 읽기 cast에서 지연 실패했다. 검사 보장은 두 전제를 요구한다. view를 만들기 전에 잘못된 원소가 없고, 이후 접근도 모두 view를 통과해야 한다. 원본 L의 raw 별칭 B를 남겨 B.add(7)을 하면 view의 삽입 검사 경계를 건너뛴다. V는 같은 원본의 view이므로 오염 원소를 정상 String으로 바꾸어 주지 않는다. 외부 접근 경로·소유권 설계도 타입 검사만큼 중요하다.

검사 view는 null을 모든 참조 타입의 값으로 취급하며 원본이 null을 허용하면 view도 허용한다. String.class 검사는 문자열의 길이·업무 식별자 규약을 검사하지 않으며 구조 불변성이나 깊은 복사를 보장하지 않는다. 새 타입 불일치 감시와 기존 데이터 검증·non-null·내용 정책·다중 스레드 안전을 각각 적는다.

소스의 타입을 소거하기

Java 컴파일러는 generic 타입 매개변수를 경계로 바꾸며 경계가 없으면 Object 로 소거한다. 필요한 위치에 cast 를 넣고 상속의 다형성을 유지하기 위해 bridge 메서드를 생성할 수 있다. Number 경계의 T 와 무경계 T 는 소거 결과가 다르다.

Box<String>과 Box<Integer>라는 두 소스 타입 인자만으로 별도 런타임 클래스를 만들지는 않는다. 그렇다고 클래스 파일에 모든 generic 관련 메타데이터가 사라진다는 뜻은 아니다. 소거된 런타임 검사와 선언 메타데이터의 범위를 구별한다.

검사할 수 없는 구체 인자

new T()나 new T[]처럼 정확한 타입 인자 객체를 직접 만드는 표현은 일반적으로 이 generic 문맥에서 허용되지 않는다. List<String> 같은 구체 인자를 instanceof 로 직접 구분할 수도 없다. List<?>처럼 실행 중 표현 가능한 타입의 검사는 별도다.

print(List<String>)과 print(List<Integer>)만 다른 두 overload 는 소거 뒤 같은 List 매개변수 형태가 되어 이름 충돌을 일으킨다. 메서드 이름·매개변수 설계를 바꾸어 역할을 구별해야 한다. 오래된 튜토리얼의 반사 생성 API 를 최신 권장 방식이라고 그대로 제시하지 않는다.

raw List 는 타입 인자 없는 사용이다. List<String>을 raw 이름으로 참조하고 Integer7 을 넣으면 unchecked 경고를 통해 정적 보장을 우회할 수 있다. 저장 시 generic 인자를 자동 검증하는 것이라고 기대하면 안 된다.

add/set·size/capacity·기존 상태/별도 후보·view/원본 별칭을 각각 다른 열로 기록한다.

풀이와 답 확인

  1. 명시 id 결과의 정적 타입은 Object지만 실제 String 참조는 그대로다. echo의 결과는 Integer 4이며 Holder의 저장 값은 String "keep"로 유지된다.

  2. 정상 helper는 saved=A 뒤 [B,B]를 거쳐 [B,A]다. saved 없이 현재 get(0)을 쓰면 [B,B]가 남는다. Integer/Double의 서로 다른 포획 타입을 같은 Number 상한만으로 교환할 수 없다.

  3. append는 [9.5,8.5,7.5,2,3], Collections.copy는 [2,3,7.5]다. 별도 null 입력의 직접 제곱 append는 실패 후 [9,4]로 부분 효과를 남긴다. 별도 후보에서 검증 실패하면 state는 [9]를 유지하며 후보를 게시하지 않는다.

  4. raw V의 Integer 7은 삽입 경계에서 거절되어 L=[]다. raw B는 view를 우회하여 오염 가능성이 있어 전체 view 통과 전제를 깨뜨린다. null 허용과 빈 String의 클래스 적합은 업무 non-null/길이 정책을 대신하지 않는다.

타입 선택은 객체 변환이 아니고 포획은 원자성이 아니다. 복사의 add/set 효과와 실패 보존·검사 view의 접근 경로를 별도 계약으로 설명해야 한다.

해결한 뒤 점검할 것

  • 명시 Object 결과와 실제 String, Holder 저장과 echo 결과를 이름별로 구별한다.

  • 정상 swap의 saved 및 [B,B] 중간 상태·서로 다른 포획 반례를 적는다.

  • 두 복사의 크기/내용과 null 실패의 직접 [9,4]/후보 미게시 state [9]를 구분한다.

  • view 검사와 원본 우회·null/빈 문자열의 추가 계약을 나누고 Java·학생 미수행을 유지한다.
