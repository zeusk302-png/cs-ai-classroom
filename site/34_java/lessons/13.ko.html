일꾼이 기다리는 동안 그 일꾼이 맡을 다음 일을 누가 실행할까?

앞 본문은 task와 이를 실행하는 worker를 구별했다. 새 자체 모형에서는 고정 worker 하나와 FIFO 대기열을 쓴다. 실행 중인 outer 작업이 같은 executor에 inner 작업을 제출한 뒤 inner의 Future.get으로 기다린다. inner가 정상 종료하면 outer도 종료하지만 현재 유일한 worker는 outer가 차지한다. 외부 취소·중단·추가 worker가 없다는 조건에서 inner는 대기열에 남고 outer는 풀리지 않는다. 이 상황에는 서로 다른 monitor 두 개가 필요하지 않다. 작업의 의존 관계와 실행 자원 수가 맞지 않는 것이 원인이다.

worker 둘로 바꾸어 outer가 하나뿐이라면 다른 worker가 inner를 실행할 수 있다. 그러나 outer 작업 둘이 각각 worker 하나씩 차지하고 자신의 inner를 기다리면 다시 같은 문제가 생긴다. worker 수를 한 번 늘렸다는 사실은 모든 의존 구조의 진행 보장이 아니다. 설계에서는 의존 작업을 순서대로 직접 계산하거나 기다리는 조정자를 해당 작은 풀 밖에 두는 방법을 검토한다. 실제 스케줄러의 실행 순서나 무제한 진전을 측정한 것은 아니다.

Future의 반환 값도 제출 방식에 따라 다르다. Runnable은 반환 값을 갖지 않는다. submit(runnable, "OK")는 작업이 정상 완료되면 미리 정한 문자열 OK를 결과로 제공한다. Runnable 안에서 지역 계산 2+3을 했다는 이유로 이 Future가 정수 5를 반환하지 않는다. 계산 결과가 필요하면 Callable의 반환 계약으로 표현한다. 실패하면 정상 결과 대신 ExecutionException 등의 상태를 따로 처리한다.

할 일과 실행 정책 나누기

task는 실행할 작업이다. Runnable은 반환값 없이 수행할 일을, Callable<T>는 결과 T와 예외를 가진 작업을 나타낸다. Thread는 실행 흐름이며 executor는 제출한 작업을 어떤 방식으로 실행할지 맡는 인터페이스다.

작업 하나에 새 thread 하나를 반드시 만들어야 하는 것은 아니다. 일꾼을 재사용하거나 다른 실행 정책을 쓸 수 있다. 그래서 작업 코드와 자원·일정 관리의 책임을 나눈다. 사용한 executor의 규칙을 모르고 동시 실행 수나 순서를 보장하면 안 된다.

메서드를 부르는 것과 새 실행 흐름 시작하기

new Thread(task)는 thread 객체를 만들고 start()는 실행을 스케줄한다. 단순히 task.run()을 부르면 호출한 흐름에서 일반 메서드처럼 실행한다. start 직후 작업이 언제 시작하거나 끝날지는 별도 문제다.

ExecutorService.submit은 작업을 제출하고 결과를 추적하는 Future를 돌려준다. 제출했다는 사실과 성공 결과를 얻었다는 사실을 나누어 기록한다. 생성·제출 순서와 완료 순서도 같다고 가정하지 않는다.

동시 작업에도 자원과 종료가 필요하다

두 작업이 겹쳐 진행되는 동시성과 같은 순간 여러 코어에서 수행되는 병렬성은 구별한다. virtual thread도 CPU 계산이 자동으로 더 빨라지는 기술은 아니다. 코드가 쓸 공유 자료는 별도 안전 설계가 필요하다.

아래 일정은 충분한 독립 작업, 지정한 일꾼 수, 시작 비용 0과 FIFO 배정을 가정한 종이 모델이다. 실제 executor의 모든 완료 순서를 규정하는 예제가 아니다. 사용을 마치면 종료 요청과 종료 확인 책임도 둔다.

각 행은 독립적인 초기 상태다. 첫 세 행에서 자원을 차지한 작업은 기다린다고 worker를 자동 반환하지 않는다. 마지막 행의 OK는 작업 내부 산술의 값이 아니라 submit의 지정 결과다.

중간 과정을 따라가는 예제

자체 모델에서 일꾼 2개가 t = 0에 A(4ms)와 B(2ms)를 시작한다. C(3ms)는 B가 끝나면 시작한다. 작업들은 독립적이며 전환 비용은 0이다. 완료 순서와 총 시간을 구하라.

  1. A는 0–4ms, B는 0–2ms에 수행된다.

  2. B의 일꾼이 C를 2–5ms에 수행한다.

  3. 완료 순서는 B, A, C이며 전체는 5ms다. 한 일꾼이면 4 + 2 + 3 = 9ms다.

자체 일정은 5ms이고 직렬 일정은 9ms다. 일꾼 2개가 실제 두 코어를 사용했다거나 Java 성능을 측정했다는 뜻은 아니다.

조건을 바꾸어 비교하기

작업 그래프는 짧지만 진행은 멈춘다

worker 하나에서 outer가 같은 풀의 inner를 제출하고 get 대기한다. 외부 개입 없이 두 작업의 종료를 판정하라.

  1. outer가 worker를 차지한 상태에서 inner가 대기열에 들어간다.

  2. outer의 종료에는 inner의 완료가 필요하지만 inner의 시작에는 worker가 필요하다.

두 작업 모두 정상 완료에 도달하지 못하는 자체 일정이다.

단순 병렬 시간 합산보다 의존과 점유를 먼저 검사한다.

  1. Runnable은 계산 값을 반환하는 인터페이스가 아니다.

  2. submit(Runnable, result)의 정상 완료 값은 지정한 result다.

문자열 OK다. 계산 값 5가 필요하면 Callable의 반환으로 설계한다.

힌트 보기

풀이 보기

C는 4ms에 시작하여 7ms에 완료하므로 전체는 7ms다. task.run() 직접 호출은 현재 흐름에서 메서드를 실행하며 새 thread 시작이 아니다.

오해와 반례

submit이 반환하면 계산 결과도 준비됐다.

Future는 진행과 결과를 추적한다. 작업이 아직 대기하거나 실행 중이면 get은 기다릴 수 있다. 등록과 완료를 구별한다.

앞 본문은 count++ 전체를 같은 monitor로 보호했다. 새 객체는 left+right=10이라는 관계를 유지하며 초기 상태는 left=4, right=6이다. writer는 같은 monitor 안에서 두 필드를 left=7, right=3으로 함께 바꾼다. reader의 getLeft와 getRight도 각각 같은 monitor를 잠그지만 두 메서드 호출 사이에 writer가 들어갈 수 있다. reader가 left=4를 얻고 writer 변경 뒤 right=3을 얻으면 읽은 쌍의 합은 7이다. 어느 한 시점의 객체 상태도 합 7이 아니지만 관찰을 둘로 나누면 관계가 깨진다.

같은 monitor를 한 번 잡고 두 값을 함께 복사하는 snapshot은 이 자체 계약에서 이전 쌍 (4,6) 또는 새 쌍 (7,3)을 반환한다. lock을 붙였는지뿐 아니라 보호할 단위가 한 필드인지, 여러 필드의 관계인지 적어야 한다. writer와 snapshot의 모든 관련 경로가 실제로 동일한 monitor를 사용한다는 전제가 필요하다.

monitor의 정체성도 중요하다. 인스턴스 synchronized 메서드는 해당 this를 잠그고 static synchronized 메서드는 해당 Class 객체를 잠근다. 이름이 같은 메서드라도 서로 다른 인스턴스나 Class와 this는 같은 lock이 아니다. 같은 스레드가 같은 monitor를 다시 얻는 재진입은 허용된다. 재진입은 다른 monitor 순서의 교착이나 혼합 snapshot을 자동으로 해결하지 않는다.

count++는 현재 값을 읽고 1을 더해 다시 쓰는 복합 동작이다. 두 작업이 이전 값을 각각 읽으면 하나의 증가가 덮일 수 있다. race condition은 일정에 따라 업무 결과가 달라지는 상황을 가리키며 data race의 명세 조건과 구별해서 설명한다.

아래 표는 Java int 필드의 초기 값 0에서 가능한 단순 읽기/쓰기 끼어들기다. 동기화 없는 모든 실행 결과를 이 표 하나로 열거하지 않는다. 실제 명세는 가시성과 순서까지 고려하며 반복 실행에서 특정 실패가 안 나왔다고 안전을 증명하지 않는다.

하나의 경계를 같은 잠금으로 지킨다

synchronized(lock) 몸체에서는 같은 객체의 모니터를 한 thread만 보유한다. 모든 count 접근을 같은 lock으로 보호하면 증가의 읽기부터 쓰기까지 다른 증가가 끼어들지 않게 할 수 있다. 한 잠금을 사용하는 규칙을 모든 경로가 지켜야 한다.

각 호출이 new Object()를 lock으로 만들면 서로 다른 모니터라 경쟁을 막지 못한다. 또한 getter만 잠그거나 읽기와 쓰기를 서로 다른 잠금으로 보호하면 하나의 불변식 경계가 깨진다. 객체 소유와 공유 경로를 먼저 확인한다.

자료의 불변식과 진행 조건도 검사한다

잠금은 원하는 자료 조건을 스스로 정해 주지 않는다. 잔액이 0 이상이어야 한다면 검사와 감소가 같은 임계 구역에 있어야 한다. 검사 때 잠갔다가 풀고 나중에 감소하면 다른 작업이 그 사이 값을 바꿀 수 있다.

여러 잠금을 함께 쓸 때는 공통 획득 순서를 정해 교착 가능성을 줄인다. 한 task가 L을 잡고 M을 기다리고 다른 task가 M을 잡고 L을 기다리면 서로 진행하지 못한다. 상호배제와 완료 가능성은 별도 질문이다.

학습 목표

  • 전이로 자료 게시의 조건을 설명한다.

  • sleep과 시간이 동기화가 아님을 구별한다.

한 번 공개한 값을 다음 회차에 바꾸려면 무엇을 더 기다려야 할까?

앞 본문의 data=42 뒤 volatile ready=true는 나중에 그 공개를 읽은 reader에게 앞의 data 쓰기를 연결했다. 새 모형은 한 producer와 한 consumer가 같은 슬롯을 두 회차 사용한다. plain payload와 volatile ready를 쓰고 초기 ready=false다. producer가 payload=11 뒤 ready=true를 쓰면 consumer가 그 true를 읽은 뒤 첫 payload를 읽을 수 있다. 하지만 producer가 소비 완료를 기다리지 않고 payload=22로 덮어쓰면, 첫 payload 읽기와 새 쓰기는 별도로 충돌할 수 있다. 첫 공개의 가시성은 다음 회차의 슬롯 소유권을 주지 않는다.

한 슬롯 자체 프로토콜에서는 producer가 ready=false를 관찰한 경우에만 payload를 쓰고 true로 공개한다. consumer는 true를 관찰한 뒤 payload를 지역 값으로 복사하고 false를 써서 소비 완료를 알린다. producer는 그 false를 관찰한 뒤에만 다음 payload를 쓴다. 따라서 producer→consumer의 공개뿐 아니라 consumer→producer의 역방향 연결이 필요하다. 초기 false는 첫 생산을 허용하는 초기 조건이지 이전 회차 소비 증거가 아니다.

이 설명은 정확히 한 producer·한 consumer·한 슬롯과 정해진 쓰기 역할의 교육용 계약이다. volatile flag의 읽기/쓰기만으로 다중 producer의 조건 검사와 예약이 원자적으로 합쳐지지 않는다. 한 reader가 true를 봤다는 사실을 임의 가변 객체의 이후 모든 쓰기에 확대하지도 않는다. 실제 Java 코드·spin 대기·스케줄링 진전·성능을 실행한 것은 아니다.

    다중 생산자의 검사/쓰기 전체는 flag 하나로 보호되지 않음을 연결한다.

보이는 값에는 언어의 규칙이 있다

happens-before는 한 동작의 효과가 다른 동작에 보이도록 하는 명세상의 순서 관계다. 벽시계가 조금 지났다는 기록 자체와 같지 않다. 공유 변수의 충돌 접근이 이 관계로 정렬되지 않으면 data race가 생긴다.

같은 thread의 프로그램 순서와 언어가 정한 동기화 간선을 연결한다. 서로 이어진 관계는 전이된다. 종이 시간선의 왼쪽에 있다고 무조건 서로 다른 thread의 간선을 그리면 안 된다.

자료를 게시할 때 간선을 연결한다

자체 예제의 공유 int data는 0, volatile boolean ready는 false다. 작성자는 data = 42 다음 ready = true를 쓴다. 독자는 ready를 읽어 true를 확인한 뒤 data를 읽는다. ready를 쓰는 다른 thread도 data를 바꾸는 후속 쓰기도 없다는 가정이다.

data 쓰기 → ready 쓰기 → 그 쓰기의 true를 읽은 ready 읽기 → data 읽기가 이어져 data의 42를 읽을 근거가 된다. ready의 false를 읽었다면 data를 사용하는 조건을 만족하지 않는다. volatile을 모든 객체 상태의 자동 잠금으로 해석하지 않는다.

다른 연결과 없는 연결을 구분한다

같은 모니터를 풀고 뒤에 다시 잡는 접근, thread start 이전과 시작된 thread, thread 종료와 성공한 join의 관계도 근거가 된다. ExecutorService는 제출 전 동작→task→Future.get으로 결과를 얻는 흐름의 메모리 효과를 명시한다.

sleep이나 yield에는 이러한 동기화 의미가 없다. 1초 기다렸다는 사실로 게시 조건을 대신하지 않는다. 가시성·원자성·공정한 일정·성능은 서로 다른 문제여서 올바른 게시만으로 복합 증가나 빠른 응답까지 보장하지 않는다.

각 대기에 같은 제한을 주면 전체 제한도 지켜질까?

앞 본문은 timeout이 작업 취소가 아님을 설명했다. 새 모형의 전체 결과 마감은 시작 0 ms부터 10 ms다. Future A는 7 ms에 끝나고 B는 13 ms에 끝난다고 가정한다. A.get에 10 ms를 주어 7 ms에 정상 반환한 뒤 B.get에도 새 10 ms를 주면 전체 13 ms까지 기다려 B를 얻을 수 있다. 두 호출 각각의 제한을 지켜도 전체 마감 10 ms는 넘는다.

같은 절대 마감을 공유하면 A 뒤 남은 시간은 10−7=3 ms다. B가 13 ms에 끝난다는 고정 모형에서 B의 남은 대기는 10 ms 시점에 timeout이다. 실제 코드에서는 같은 단조 시간 기준으로 남은 시간을 다시 계산하고 0 이하이면 새 대기를 시작하지 않는다. 여기의 시각은 가상 모형이며 정확한 실제 복귀 시각·timer 정밀도·JVM 스케줄링을 보장하지 않는다. timeout 뒤 B가 계속 실행 중인지, 취소 요청을 보냈는지, 실제 종료했는지는 각각 별도 장부다.

shutdown은 새 작업 수용을 끝내고 이미 제출한 작업을 계속 처리하는 계약이다. shutdownNow는 시작 전 기다리던 작업들을 돌려주고 실행 중 작업 중단을 시도하지만 즉시 모두 끝났다고 보장하지 않는다. 반환된 대기 작업 목록과 이미 얻은 Future들의 상태도 자동으로 같은 장부라고 보지 않는다. 보유한 Future마다 취소와 완료/실패 상태를 확인하는 종료 정책이 필요하다. Future.isDone은 정상 성공만이 아니라 예외 완료·취소도 포함한다.

완료에는 성공 이외의 상태도 있다

Future.get은 결과를 기다려 정상 값을 얻거나 작업 예외를 ExecutionException으로 전달한다. 취소되면 CancellationException, 기다리는 호출자가 인터럽트되면 InterruptedException을 구별한다. isDone=true는 정상 결과만 뜻하지 않는다.

timed get은 최대 기다리는 시간을 제한한다. 시간이 지나 TimeoutException이 났다는 사실만으로 작업을 취소하지 않는다. 원인·남은 작업·자원 소유를 확인하고 계속 기다릴지, 취소를 요청할지 정책을 정한다.

취소 요청을 실행 코드가 받아들여야 한다

cancel(true)는 실행 thread를 알 수 있는 구현에서 인터럽트로 멈추기를 시도할 수 있다. 실행 코드가 인터럽트에 반응하지 않으면 실제 계산은 계속될 수 있다. Future의 취소 상태와 계산 thread의 실제 종료는 별개로 확인한다.

기다림의 InterruptedException을 무시하며 루프를 계속하는 코드는 종료 정책을 깨뜨릴 수 있다. 전파하거나 필요한 정리 뒤 적절히 종료하고, 상위 계층이 상태를 필요로 하면 인터럽트 상태 보존 방식을 검토한다. 이미 수행한 외부 저장을 취소가 자동으로 되돌리지는 않는다.

executor도 마지막 책임이 남는다

shutdown은 새 작업을 거절하고 기존 작업의 실행을 허용하는 종료 요청이다. 호출 자체는 기존 작업 종료를 기다리지 않는다. awaitTermination은 정한 시간 동안 종료를 기다리고 종료 여부를 반환한다.

shutdownNow는 대기 작업을 시작하지 않게 하고 실행 작업을 멈추려 시도한다. 응답하지 않는 작업의 강제 종료 보장이 아니다. 소유한 자원이 실제로 더 이상 사용되지 않는 시점과 실패 처리까지 확인해야 종료 완료라 기록할 수 있다.

다른 문제에 적용하기

네 독립 장부를 작성하라. (1) 고정 worker 둘에서 outer 둘이 각각 같은 풀에 자신의 inner를 제출하고 get 대기하며 inner 자체는 더 기다리지 않는다. 자유 worker와 정상 완료 가능성을 판정하라. (4) 서로 독립적인 Future A/B가 시작 0 ms부터 7/13 ms에 정상 종료하는 가상 일정에서 전체 마감은 10 ms다. 순서대로 새 timeout 10 ms를 주는 방식과 공통 마감 방식의 결과를 비교하고, B의 timeout 뒤 자동 취소 여부를 적어라. 실제 Java·서비스·학생 실행은 요구하지 않는다.

작업 의존/worker 점유, 실제 객체 상태/독립 관찰, 첫 공개/다음 회차 소유를 서로 다른 장부에 적는다.

힌트 2

A 결과 뒤 새 대기 직전 시각을 가상 7 ms라고 두고 남은 예산을 계산한다. timeout과 취소는 각각 이름 붙인다.

풀이와 답 확인

  1. worker 둘은 모두 outer에 점유되고 inner 둘은 큐에 남는다. 지정된 외부 개입 없는 상황에서는 inner의 시작이 막혀 정상 완료로 진행하지 못한다.

  2. 개별 getter 일정의 관찰 쌍은 (4,3)이고 합은 7이다. writer와 동일 monitor로 두 값을 함께 복사한 snapshot은 (4,6) 또는 (7,3)으로 합 10을 유지한다.

  3. 잘못된 early false는 producer에게 다음 쓰기를 허가하므로 consumer의 읽기 전 22의 덮어쓰기가 가능하다. true를 관찰한 consumer는 먼저 자료를 지역으로 복사하고 그 뒤 false를 써야 한다. producer는 그 확인 뒤에만 다음 값을 쓴다.

  4. 새 timeout 방식의 A는 7 ms에 끝나고 B는 새 허용 끝 17 ms보다 이른 13 ms에 끝나 전체 마감 10 ms를 넘는다. 공통 마감 방식의 남은 예산은 3 ms이고 가상 10 ms에서 B 결과 대기가 timeout이다. get timeout 자체는 B를 취소하지 않는다.

자유 worker는 0개이고 inner 둘은 시작하지 못한다. 별도 getter 관찰은 (4,3), 합 7이며 snapshot 합은 10이다. 슬롯 소비의 자료 복사가 재사용 확인 false보다 먼저 와야 한다. 새 제한 반복은 전체 13 ms, 공통 마감은 가상 10 ms의 B timeout이며 자동 취소는 아니다.
