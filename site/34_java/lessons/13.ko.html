소단원 13.1

thread·executor·task

해야 할 일과 그 일을 실행하는 일꾼은 같은 것일까?

준비 개념과 학습 목표

준비 개념

  • 메서드와 람다
  • 예외
  • 시간선

학습 목표

  • task와 실행 주체를 구별한다.
  • start/run과 submit/get의 차이를 설명한다.
  • 가정한 작업 일정과 실제 실행을 분리한다.

할 일과 실행 정책 나누기

task는 실행할 작업이다. Runnable은 반환값 없이 수행할 일을, Callable<T>는 결과 T와 예외를 가진 작업을 나타낸다. Thread는 실행 흐름이며 executor는 제출한 작업을 어떤 방식으로 실행할지 맡는 인터페이스다.

작업 하나에 새 thread 하나를 반드시 만들어야 하는 것은 아니다. 일꾼을 재사용하거나 다른 실행 정책을 쓸 수 있다. 그래서 작업 코드와 자원·일정 관리의 책임을 나눈다. 사용한 executor의 규칙을 모르고 동시 실행 수나 순서를 보장하면 안 된다.

메서드를 부르는 것과 새 실행 흐름 시작하기

new Thread(task)는 thread 객체를 만들고 start()는 실행을 스케줄한다. 단순히 task.run()을 부르면 호출한 흐름에서 일반 메서드처럼 실행한다. start 직후 작업이 언제 시작하거나 끝날지는 별도 문제다.

ExecutorService.submit은 작업을 제출하고 결과를 추적하는 Future를 돌려준다. 제출했다는 사실과 성공 결과를 얻었다는 사실을 나누어 기록한다. 생성·제출 순서와 완료 순서도 같다고 가정하지 않는다.

동시 작업에도 자원과 종료가 필요하다

두 작업이 겹쳐 진행되는 동시성과 같은 순간 여러 코어에서 수행되는 병렬성은 구별한다. virtual thread도 CPU 계산이 자동으로 더 빨라지는 기술은 아니다. 코드가 쓸 공유 자료는 별도 안전 설계가 필요하다.

아래 일정은 충분한 독립 작업, 지정한 일꾼 수, 시작 비용0과 FIFO 배정을 가정한 종이 모델이다. 실제 executor의 모든 완료 순서를 규정하는 예제가 아니다. 사용을 마치면 종료 요청과 종료 확인 책임도 둔다.

중간 과정을 따라가는 예제

자체 모델에서 일꾼2개가 t=0에 A4ms와 B2ms를 시작한다. C3ms는 B가 끝나면 시작한다. 작업들은 독립적이며 전환 비용0이다. 완료 순서와 총 시간을 구하라.

  1. A는0–4ms,B는0–2ms다.
  2. B의 일꾼이 C를2–5ms에 수행한다.
  3. 완료는B,A,C이며 전체는5ms다. 한 일꾼이면4+2+3=9ms다.

자체 일정5ms와 직렬9ms다. 일꾼2개가 실제 두 코어를 사용했다거나 Java 성능을 측정했다는 뜻은 아니다.

종이와 본문으로 직접 해보기

같은 모델에서 C가 A의 결과를 필요로 하여 A 완료 뒤에만 시작할 수 있으면 총 시간은? run() 직접 호출이 새 thread를 시작하는지도 판단하라.

힌트 보기

C의 선행 작업과 start의 역할을 각각 본다.

풀이 보기

C는4–7ms에 시작·완료하므로 전체7ms다. task.run() 직접 호출은 현재 흐름에서 메서드를 실행하며 새 thread 시작이 아니다.

오해와 반례

submit이 반환하면 계산 결과도 준비됐다.

Future는 진행과 결과를 추적한다. 작업이 아직 대기하거나 실행 중이면 get은 기다릴 수 있다. 등록과 완료를 구별한다.

소단원 13.2

race·synchronization

두 사람이 동시에 숫자에 1을 더했는데 왜 하나만 늘어날 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 필드와 객체
  • 읽기·계산·쓰기
  • 조건과 불변식

학습 목표

  • 복합 연산의 경쟁을 추적한다.
  • 같은 모니터의 임계 구역을 설명한다.
  • 잠금 누락과 잘못된 잠금 대상을 찾는다.

한 줄이 하나의 원자 작업은 아니다

count++는 현재 값을 읽고1을 더해 다시 쓰는 복합 동작이다. 두 작업이 이전 값을 각각 읽으면 하나의 증가가 덮일 수 있다. race condition은 일정에 따라 업무 결과가 달라지는 상황을 가리키며 data race의 명세 조건과 구별해서 설명한다.

아래 표는 Java int 필드 초기0의 가능한 단순 읽기/쓰기 끼어들기다. 동기화 없는 모든 실행 결과를 이 표 하나로 열거하지 않는다. 실제 명세는 가시성과 순서까지 고려하며 반복 실행에서 특정 실패가 안 나왔다고 안전을 증명하지 않는다.

하나의 경계를 같은 잠금으로 지킨다

synchronized(lock) 몸체에서는 같은 객체의 모니터를 한 thread만 보유한다. 모든 count 접근을 같은 lock으로 보호하면 증가의 읽기부터 쓰기까지 다른 증가가 끼어들지 않게 할 수 있다. 한 잠금을 사용하는 규칙을 모든 경로가 지켜야 한다.

각 호출이 new Object()를 lock으로 만들면 서로 다른 모니터라 경쟁을 막지 못한다. 또한 getter만 잠그거나 읽기와 쓰기를 서로 다른 잠금으로 보호하면 하나의 불변식 경계가 깨진다. 객체 소유와 공유 경로를 먼저 확인한다.

자료의 불변식과 진행 조건도 검사한다

잠금은 원하는 자료 조건을 스스로 정해주지 않는다. 잔액이0 이상이어야 한다면 검사와 감소가 같은 임계 구역에 있어야 한다. 검사 때 잠갔다가 풀고 나중에 감소하면 다른 작업이 그 사이 값을 바꿀 수 있다.

여러 잠금을 함께 쓸 때는 공통 획득 순서를 정해 교착 가능성을 줄인다. 한 task가 L을 잡고 M을 기다리고 다른 task가 M을 잡고 L을 기다리면 서로 진행하지 못한다. 상호배제와 완료 가능성은 별도 질문이다.

중간 과정을 따라가는 예제

int count=0이다. A와B가 각1회 증가한다. 가상 일정 A읽기0,B읽기0,A쓰기1,B쓰기1을 추적하고 같은 lock으로 각 증가 전체를 보호한 일정과 비교하라.

  1. A와B의 지역 계산값은 각각1이다.
  2. 첫쓰기 뒤 count1,둘째쓰기 뒤에도 count1로 한 증가가 사라진다.
  3. 같은 lock으로 A전체 뒤B전체를 실행하면0→1→2다. B뒤A도2다.

가상 경쟁 일정은1, 제대로 보호하고 두 작업 종료를 확인한 결과는2다. 모든 접근이 같은 잠금 규칙을 지킨다는 조건이 중요하다.

종이와 본문으로 직접 해보기

잔여 좌석1을 A와B가 잠금 없이 각각 읽어 '남았다'고 판정한 뒤0을 저장하고 각각 예약 성공을 알린다. 남은 숫자와 성공 수는? 각자 다른 lock을 쓰면 해결되는가?

힌트 보기

숫자 결과와 업무 불변식을 따로 센다.

풀이 보기

숫자는0이지만 성공2로 좌석1을 초과한다. 서로 다른 lock은 함께 배제하지 않는다. 같은 잠금 안에서 확인·감소·결과 결정을 한 덩어리로 처리하면 성공1/거절1이다.

오해와 반례

공유 필드를 volatile로만 바꾸면 count++ 전체가 원자적이다.

volatile은 접근의 가시성·순서에 관한 규칙을 주지만 증가의 읽기와 쓰기를 하나로 묶지 않는다. 위 두 읽기 뒤 두 쓰기 일정은 volatile에서도 가능하다.

한 단계 더

L→M 공통 순서를 사용하면 M을 보유한 채 L을 기다리는 반대 경로가 사라지는지 그려보자. 이를 모든 종류의 대기·외부 호출 교착까지 해결했다는 주장으로 확대하지 않는다.

소단원 13.3

visibility와 happens-before

자료를 먼저 썼다는 벽시계 기록만 있으면 다른 thread가 새 값을 읽을까?

준비 개념과 학습 목표

준비 개념

  • 프로그램 순서
  • 공유 필드
  • volatile과 모니터

학습 목표

  • happens-before 간선을 그린다.
  • 전이로 자료 게시의 조건을 설명한다.
  • sleep과 시간이 동기화가 아님을 구별한다.

보이는 값에는 언어의 규칙이 있다

happens-before는 한 동작의 효과가 다른 동작에 보이도록 하는 명세상의 순서 관계다. 벽시계가 조금 지났다는 기록 자체와 같지 않다. 공유 변수의 충돌 접근이 이 관계로 정렬되지 않으면 data race가 생긴다.

같은 thread의 프로그램 순서와 언어가 정한 동기화 간선을 연결한다. 서로 이어진 관계는 전이된다. 종이 시간선의 왼쪽에 있다고 무조건 서로 다른 thread의 간선을 그리면 안 된다.

자료를 게시할 때 간선을 연결한다

자체 예제의 공유 int data는0,volatile boolean ready는false다. 작성자는 data=42 다음 ready=true를 쓴다. 독자는 ready를 읽어 true를 확인한 뒤 data를 읽는다. ready를 쓰는 다른 thread도 data를 바꾸는 후속 쓰기도 없다는 가정이다.

data쓰기→ready쓰기→그 쓰기의 true를 읽은 ready읽기→data읽기가 이어져 data42를 읽을 근거가 된다. readyfalse를 읽었다면 data를 사용하는 조건을 만족하지 않는다. volatile을 모든 객체 상태의 자동 잠금으로 해석하지 않는다.

다른 연결과 없는 연결을 구분한다

같은 모니터를 풀고 뒤에 다시 잡는 접근, thread start 이전과 시작된 thread, thread 종료와 성공한 join의 관계도 근거가 된다. ExecutorService는 제출 전 동작→task→Future.get으로 결과를 얻는 흐름의 메모리 효과를 명시한다.

sleep이나 yield에는 이러한 동기화 의미가 없다.1초 기다렸다는 사실로 게시 조건을 대신하지 않는다. 가시성·원자성·공정한 일정·성능은 서로 다른 문제여서 올바른 게시만으로 복합 증가나 빠른 응답까지 보장하지 않는다.

중간 과정을 따라가는 예제

data=0,volatile ready=false로 시작한다. 작성자 W1:data=42,W2:ready=true;독자 R1:ready가true임을 읽음,R2:data읽기다. 다른 쓰기는 없다. 간선과 R2의 값을 구하라.

  1. 작성자 프로그램 순서로W1→W2다.
  2. volatile의 연결로W2→R1,독자 프로그램 순서로R1→R2다.
  3. 전이로W1→R2가 되어R2는42를 읽는다. 실제 게시 코드 실행 없이 관계를 적용한다.

세 간선과 전이로42다. ready를 일반 boolean으로 바꾸면 같은 가시성 근거를 그대로 적용할 수 없다.

종이와 본문으로 직접 해보기

작업 제출 전에 공유 int x=7을 쓰고 task가 x를 읽어2를 곱해 반환한다. 이후 다른 쓰기가 없고 Future.get이 정상 결과를 반환하면 값은? get 대신 sleep만 한 뒤 task의 일반 필드를 읽는 것도 같은 근거인가?

힌트 보기

submission→task→get과 sleep 규칙을 구별한다.

풀이 보기

task는7을 읽고14를 계산하며 정상 get 결과는14다. sleep에는 동기화 의미가 없어 일반 필드의 게시 근거를 대신하지 않는다.

오해와 반례

happens-before가 있으면 두 thread가 절대 겹쳐 실행되지 않는다.

소단원 13.4

future·취소·종료

기다리기 시간이 끝났다면 실제 작업도 멈춘 것일까?

준비 개념과 학습 목표

준비 개념

  • Future와 예외
  • 인터럽트
  • 자원 정리

학습 목표

  • 정상·예외·취소 결과를 구별한다.
  • timeout과 작업 취소를 분리한다.
  • 종료 요청과 종료 확인의 차이를 추적한다.

완료에는 성공 이외의 상태도 있다

Future.get은 결과를 기다려 정상 값을 얻거나 작업 예외를 ExecutionException으로 전달한다. 취소되면 CancellationException, 기다리는 호출자가 인터럽트되면 InterruptedException을 구별한다. isDone=true는 정상 결과만 뜻하지 않는다.

timed get은 최대 기다리는 시간을 제한한다. 시간이 지나 TimeoutException이 났다는 사실만으로 작업을 취소하지 않는다. 원인·남은 작업·자원 소유를 확인하고 계속 기다릴지, 취소를 요청할지 정책을 정한다.

취소 요청을 실행 코드가 받아들여야 한다

cancel(true)는 실행 thread를 알 수 있는 구현에서 인터럽트로 멈추기를 시도할 수 있다. 실행 코드가 인터럽트에 반응하지 않으면 실제 계산은 계속될 수 있다. Future의 취소 상태와 계산 thread의 실제 종료는 별개로 확인한다.

기다림의 InterruptedException을 무시하며 루프를 계속하는 코드는 종료 정책을 깨뜨릴 수 있다. 전파하거나 필요한 정리 뒤 적절히 종료하고, 상위 계층이 상태를 필요로 하면 인터럽트 상태 보존 방식을 검토한다. 이미 수행한 외부 저장을 취소가 자동으로 되돌리지는 않는다.

executor도 마지막 책임이 남는다

shutdown은 새 작업을 거절하고 기존 작업의 실행을 허용하는 종료 요청이다. 호출 자체는 기존 작업 종료를 기다리지 않는다. awaitTermination은 정한 시간 동안 종료를 기다리고 종료 여부를 반환한다.

shutdownNow는 대기 작업을 시작하지 않게 하고 실행 작업을 멈추려 시도한다. 응답하지 않는 작업의 강제 종료 보장이 아니다. 소유한 자원이 실제로 더 이상 사용되지 않는 시점과 실패 처리까지 확인해야 종료 완료라 기록할 수 있다.

중간 과정을 따라가는 예제

가상 작업A는0ms에 시작해8ms에 끝나고 다른 취소 요청은 없다. 호출자는0ms부터 timed get(3ms)를 한다. 종료 요청은4ms,awaitTermination은4ms부터2ms 기다린다. 호출·작업·executor 상태를 추적하라.

  1. 3ms에 timed get은TimeoutException으로 기다림을 끝낸다. A는 계속 실행해8ms에 끝난다.
  2. 4ms의shutdown 뒤 새 작업은 거절하지만 기존 A는 계속된다.
  3. 6ms의awaitTermination 종료 시점에는 A가 실행 중이므로false다.8ms 뒤 모든 작업과 executor가 종료된 조건에서 다시 확인하면true다.

기다림 시간 초과3ms와 실제 완료8ms는 다르다. 종료 요청4ms와 확인false6ms도 구별한다. 시간은 실제 API 실험이 아닌 자체 일정이다.

풀이 보기

오해와 반례

Future가 취소되면 이미 완료한 파일 저장도 자동 복원된다.

결과 상태와 외부 부작용은 다르다. 취소 전에 저장이 확정됐을 수 있어 업무 수준에서 중복·복구 정책을 따로 둬야 한다.
