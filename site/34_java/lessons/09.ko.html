조회 결과 null은 아직 등록하지 않았다는 뜻일까?

앞 본문은 Map의 같은 키 재등록이 연결 값을 교체함을 보였다. 새 점수 장부 scores는 null 값을 허용하는 HashMap<String,Integer>이며 키 "A"는 등록됐지만 점수 미확정이라 null에 연결하고, "B"는 아직 등록하지 않았다고 정한다. scores.get("A")와 get("B")는 모두 null이지만 containsKey("A")는 true, containsKey("B")는 false다. 반환 값 하나로 등록 여부와 점수 확정을 모두 판단하면 서로 다른 업무 상태를 합쳐 버린다.

점수 미확정이 정상 상태라면 존재 여부와 값의 의미를 따로 문서화한다. 또는 null을 금지하고 Pending/Scored처럼 별도 상태를 설계할 수도 있다. 특정 구현이 null을 허용하는 조건과 업무가 null에 부여한 뜻은 별개다. 단일 스레드의 안정된 장부라는 전제를 두며 containsKey와 get 두 호출이 모든 동시 변경에 대해 하나의 원자적 관찰이라는 주장을 하지 않는다.

처리 대기의 실패도 반환값을 해석해야 한다. 새 자체 FIFO 용량 2 모형은 null 항목을 금지하고 가득 차면 offer가 false로 거절한다. 초기 [A,B]에 C를 offer하면 내용은 그대로이고, A를 poll한 뒤 C를 다시 offer하면 [B,C]다. 이는 특정 Queue 구현의 실제 용량이나 실행 결과가 아닌 명시한 자체 상태 모형이다. 승인 기록을 먼저 남긴 뒤 offer의 false를 무시하면 기록과 실제 대기가 어긋난다.

순서와 유일성의 질문을 먼저 정하기

List는 위치 순서를 가진 요소 모음이고 보통 중복을 허용한다. 출석 기록 [민,서,민]에서는 같은 이름의 두 방문이 각 위치에 남는다. Set은 equals 기준의 중복 없이 포함 여부를 다루며 방문 학생의 종류만 필요할 때 알맞다.

Set이라는 인터페이스만으로 순회가 정렬 순서나 입력 순서라고 보장되지 않는다. 순서가 중요하면 구현의 계약을 선택해야 한다. null 허용과 변경 가능 여부도 개별 구현에서 확인한다.

키와 처리 대기를 구별하기

Map은 키마다 연결된 값을 보관한다. 같은 키에 새 값을 put하면 기존 연결을 교체하므로 학생별 현재 점수에 맞다. Map은 Collection을 직접 상속하는 요소 모음이 아니며 키·값·entry를 각각 순회한다.

Queue는 처리할 요소를 기다리게 하는 인터페이스다. 보통 FIFO지만 우선순위 큐 등 다른 순서도 있어 구현 계약이 필요하다. 비어 있을 때 poll은 null, remove는 예외라는 차이를 알고 정상적인 빈 상태에는 적절한 API를 사용한다.

역할을 인터페이스로 표현하기

변수 선언을 List<String>처럼 역할 인터페이스로 두면 호출자가 필요한 기능을 드러낼 수 있다. 구현은 ArrayList,HashSet,HashMap,ArrayDeque처럼 선택한다. 선택한 구현의 순서·성능·null·동시성 조건은 사라지지 않는다.

같은 데이터도 질문에 따라 네 형태로 보관할 수 있다. 모든 자료를 한 컨테이너에 밀어 넣기보다 중복 기록인지 현재 연결인지 대기 작업인지 요구를 먼저 적으면 API 선택이 쉬워진다.

  3. Map의 민 연결 70이 90으로 바뀌어 키 2 개, 민 90/서 80이다.

범위를 지우면 복사한 목록도 함께 지워질까?

앞 본문은 subList의 set이 원본 칸에 반영됨을 보였다. 새 원본 b는 수정 가능한 ArrayList<Integer> [10,20,30,40,50]다. v=b.subList(1,4)를 만들면 v는 [20,30,40]이고, c=new ArrayList<>(v)는 그 세 Integer 참조를 담는 별도 목록이다. v.clear()를 지원되는 view 경로로 수행하면 원본에서 해당 구간이 제거되어 b=[10,50], v=[]가 되지만 c=[20,30,40]는 유지한다.

구간 삭제는 원본 바깥에서 임의로 구조를 바꾸는 것과 다르다. v를 통해 지원된 변경은 API가 제공하는 범위 작업이다. 별도 대안에서 b.add(60)을 직접 수행한 뒤 기존 v를 계속 읽으면 기존 view의 의미가 정의되지 않는 조건에 들어간다. 실제 어떤 예외가 언제 나오는지를 성공 증거로 쓰지 말고, 새 view 생성 또는 독립 목록 선택으로 계약을 다시 확보한다.

Iterator.remove도 삭제할 대상을 가진 상태 기계다. 새 ArrayList [A,B,C]의 iterator가 next로 A를 반환한 뒤 한 번 remove하면 목록은 [B,C]다. next를 새로 수행하지 않고 두 번째 remove를 하면 IllegalStateException 조건이다. 지원 여부도 별개이며 모든 Iterator가 remove를 구현한다고 가정하지 않는다. 아래 모든 목록 변경과 예외는 실제 JVM 호출 없는 계약 손추적이다.

먼저 확인할 개념
  • backed view와 컨테이너 복사

    구간을 통한 구조 변경과 독립 저장 목록의 차이를 추적한다.

  • 위치 순서와 삭제의 대상

    원소 값과 현재 인덱스, 순회가 마지막 반환한 요소를 구별한다.

순회가 보는 계약 읽기

iteration은 요소를 하나씩 방문하는 작업이다. for-each는 Iterator 기반의 순회를 간편하게 표현한다. 순회 도중 원본을 직접 구조 변경하면 일반 ArrayList 등의 iterator는 ConcurrentModificationException을 감지할 수 있다. 모든 동시 오류를 반드시 감지하는 보장으로 사용하지 않는다.

지원되는 iterator.remove는 마지막 반환 요소를 계약에 따라 제거하는 방법이다. 제거를 지원하지 않는 iterator도 있으므로 모든 모음에 통한다고 가정하지 않는다. 여러 스레드의 공유 접근은 이 예외만 기다리지 말고 동기화와 동시성 구현으로 설계해야 한다.

view는 원본 일부를 보는 창이다

list.subList(from,to)는 from 포함,to 제외 구간의 view다. 새 독립 저장 컨테이너로 값들을 복사했다는 뜻이 아니다. 원본과 view의 비구조 변경은 서로 반영된다. 예제의 set은 크기를 바꾸지 않으므로 원본에도 나타난다.

원본을 view를 통하지 않고 구조 변경하면 subList의 의미가 정의되지 않을 수 있다. 창의 범위와 원본의 구조가 함께 움직이기 때문이다. 안전하게 독립 목록이 필요하면 새 ArrayList<>(view) 같은 컨테이너 복사를 고려한다.

컨테이너 복사도 요소 복제는 아니다

new ArrayList<>(view)는 새 목록 컨테이너를 만들지만 요소 객체 참조는 그대로 복사한다. 문자열처럼 불변 요소를 쓰는 예제에서는 독립 set의 차이가 분명하지만 요소 내부를 바꿀 수 있다면 그 객체 변경은 둘에서 보일 수 있다.

Map의 keySet/values/entrySet도 원본과 연결된 view다. 변경 지원 여부와 반영 범위를 API에서 확인해야 한다. 이름을 copy라고 붙이는 것으로 깊은 복사가 되는 것은 아니다.

소단원 9.3

hash·ordered 구조

키를 빠르게 찾는 것과 정렬해서 보여 주는 것은 같은 요구일까?

준비 개념과 학습 목표

준비 개념

  • equals와 hashCode

  • 키와 값

학습 목표

  • 해시의 동일성 계약과 순서 계약을 구별한다.

  • 정렬 비교가 키 동일성을 결정하는 경우를 설명한다.

정렬 비교의 동점이 실제 키를 지워 버릴 수 있을까?

앞 본문의 길이 Comparator는 서로 다른 문자열을 하나의 키로 취급했다. 새 입력 연결은 ("aa",1), ("bb",2), ("c",3)이다. 문자열 equals를 쓰는 HashMap에는 세 연결을 유지하지만 길이만 비교하는 TreeMap은 aa와 bb를 비교 0으로 보아 하나의 연결 값이 2로 교체되며 총 두 연결이다. 순서 문제를 고치려다 저장 동일성 자체를 바꾼 것이다. HashMap의 실제 순회 순서는 여기서 예측하지 않는다.

문자열 전체를 키로 유지하면서 길이별 표시가 필요하면 비교를 길이 우선, 같은 길이에서는 문자열 자연 순서로 정할 수 있다. 새 비교의 0은 같은 문자열에만 생기므로 세 연결을 유지하고 표시 순서는 c, aa, bb다. 반대로 업무가 길이별 통계라면 길이 정수를 명시 키로 삼고 개수 등을 집계하는 Map<Integer,...>을 설계하는 편이 목적을 드러낸다. 서로 다른 문제를 같은 비교기로 해결했다고 주장하지 않는다.

연결된 keySet도 원본 Map의 변경 경로다. 별도 수정 가능한 장부 m={A:1,B:2}에서 live=m.keySet(), saved=new HashSet<>(live)를 만든 뒤 live.remove("A")를 수행하면 m에는 B만 남고 saved에는 A/B가 남는다. keySet.add("C")는 값을 제공하지 않아 이 view가 지원하지 않는 작업이다. 키 집합 복사와 live view의 수명·순서·변경 지원을 구별한다.

먼저 확인할 개념
  • 비교 0과 Map의 키 동일성

    정렬 요구가 equals와 다른 연결 병합을 만들지 확인한다.

  • Map의 연결된 collection view

    keySet의 제거 반영과 독립 집합 복사를 나눈다.

해시는 후보를 좁히고 동일성은 구별한다

HashMap은 해시로 후보 위치를 찾아 키의 동일성 계약과 함께 연결을 관리한다. 같은 키로 판단되는 객체는 같은 hashCode를 가져야 한다. 반대로 해시가 같다는 이유만으로 같은 키라고 결론내릴 수는 없으며 서로 다른 키의 충돌이 가능하다.

키를 넣은 뒤 equals나 hashCode에 영향을 주는 값을 바꾸면 찾기 규칙이 깨질 수 있다. 불변 키를 쓰거나 필요한 변경에서 제거·재삽입 규칙을 설계한다. 실제 버킷 배치는 구현 세부이므로 예제의 작은 해시표와 혼동하지 않는다.

빠른 조회와 표시 순서를 따로 선택하기

HashMap은 순회 순서를 보장하지 않는다. 정렬된 키가 필요하면 TreeMap의 자연 순서 또는 Comparator를 선택한다. 삽입 순서를 유지하는 LinkedHashMap 같은 다른 요구도 있으며 순서라는 단어만으로 정렬과 삽입 순서를 섞지 않는다.

TreeMap은 비교 결과가 0인 키를 같은 것으로 취급한다. Map의 일반 계약과 맞추려면 정렬 비교가 equals와 일관되어야 한다. 길이만 비교하는 문자열 Comparator는 "ab"와 "cd"를 같은 키로 취급하여 연결을 교체할 수 있다.

조회 비용의 조건까지 읽기

HashMap의 get/put 상수시간 성능은 해시가 적절히 분산된다는 조건을 가진다. 순회에는 크기뿐 아니라 용량도 영향을 준다. 충돌이 심한 입력에서 같은 비용을 보장한다고 일반화하지 않는다.

TreeMap의 기본 키 연산은 log(n) 비용을 보장하지만 비교 자체의 비용도 실제 전체 시간에 포함된다. 정렬 범위 조회가 필요한지, 값 표시만 한 번 정렬하면 되는지에 따라 구조 선택이 달라질 수 있다.

변경할 수 없는 목록을 받으면 안의 학생 객체도 영원히 그대로일까?

준비 개념과 학습 목표

준비 개념

  • 참조와 가변 객체

학습 목표

평균적으로 싸다는 설명이 공간 피크와 깊은 불변성도 보장할까?

앞 본문의 상각 O(1)은 한 append의 지연이 항상 작다는 약속이 아니다. 새 자체 배열 모형은 초기 용량 1, 빈 상태에서 시작해 가득 찬 때 용량을 두 배로 늘린다. 확장에서는 옛 활성 참조를 모두 복사하고 새 배열 완성 뒤 옛 배열을 해제하며, append는 한 칸 쓰기 비용으로 센다. 다섯 번 append의 복사 수는 0,1,2,0,4로 총 7이고 새 값 쓰기 5를 더한 총 비용은 12칸 작업이다. 이는 Java ArrayList의 실제 성장 비율이 아니라 자체 분석 모형이다.

다섯 번째 append의 확장은 옛 4칸과 새 8칸이 동시에 살아 있어 피크 12칸이다. 이때까지 생성한 배열 용량의 누적 합 1+2+4+8=15칸과 최종 용량 8칸은 다른 수다. 실제 바이트·객체 헤더·GC 회수 시각·할당 실패·실시간 지연은 측정하지 않았다. ArrayList 문서는 구체 성장 정책을 약속하지 않으므로 이 숫자를 라이브러리 성능 결과로 쓰지 않는다.

새 깊이 모형의 Box p는 value=7이며 src=[p]다. u=Collections.unmodifiableList(src)와 frozen=List.copyOf(src)를 만든 뒤 src에 새 Box(3)를 추가하면 u는 두 요소, frozen은 한 요소다. 이어 p.value=9로 바꾸면 두 목록의 첫 요소는 모두 9를 보인다. frozen은 원본의 칸 추가와 분리됐지만 동일 가변 요소의 상태까지 복제하지 않았다. 각 Box의 값만 불변 Integer로 추출해 별도 copyOf하는 설계는 값 스냅샷과 다른 계약을 만든다.

List.copyOf는 null 원소를 거절한다. 현재 published=[7]라는 정상 목록을 보관하고 candidate=[9,null]의 copyOf가 실패하면, 결과 참조를 얻은 성공에만 published를 바꾸는 계획에서는 기존 [7]을 유지한다. 후보 원본부터 현재 상태로 게시해 버린 계획과 비교한다. 이 단원은 순차 메모리의 손모형이며 실제 Java/JVM/할당/계측/학생 실행은 미수행이다.

먼저 확인할 개념
  • 상각 비용과 변경 불가 목록의 범위

    전체 작업 비용·한 번의 피크·컨테이너 제한·요소 상태를 서로 다른 장부에 둔다.

  • 컨테이너 복사와 요소 공유

    copyOf가 별도 요소 객체를 자동 생성하지 않는 이유를 확인한다.

무슨 연산을 얼마나 자주 하는지 묻기

ArrayList의 인덱스 get은 상수시간이고 뒤에 add하는 비용은 상각 상수시간이다. 상각은 긴 연산열의 총비용을 평균적으로 나누는 분석이며 매번 동일 시간으로 끝난다는 실시간 보장이 아니다. 중간 삽입은 뒤의 요소를 옮길 수 있어 선형 비용이다.

자료형의 이름 대신 조회·추가·순회·범위 검색 등 실제 연산의 횟수를 적는다. Big-O는 증가율을 설명하며 실제 지연은 요소 크기, 메모리, 구현과 입력에 달렸다. 작은 모음에서는 이론의 차이만으로 실측 순위를 단정하지 않는다.

변경 불가 창과 변경 불가 복사 구별하기

Collections.unmodifiableList(base)는 원본을 읽는 변경 불가 view다. 그 view를 통해 add/set을 하면 예외지만 원본이 다른 경로로 바뀌면 view에도 보인다. List.copyOf(base)는 주어진 요소를 담는 변경 불가 목록으로 원본의 나중 구조 변경을 반영하지 않는다.

List.of와 copyOf는 null을 허용하지 않는다. 이 예제는 Java 10 이상 기본 API 범위이며 실제 확인은 Java SE 25 문서로 했다. 목록을 변경할 수 없는 성질과 외부 원본의 변화가 없는 성질을 따로 생각하자.

깊은 불변성은 요소까지 확인해야 한다

변경 불가 목록 안의 요소가 가변 객체라면 그 객체의 필드를 바꾸어 관찰 값이 달라질 수 있다. List.copyOf도 요소 객체를 깊게 복제하지 않는다. 진짜 깊은 불변 구조가 필요하면 요소 자체의 불변성이나 복사 전략을 함께 설계한다.

안전한 공유와 변경 불가 목록은 관련되지만 자동으로 모든 스레드 공개나 복합 작업 동기화를 보장하지 않는다. 버전 스냅샷, 수명, 공개 규칙을 실제 사용 맥락에서 확인한다.
