소단원 10.1

functional interface

함수 하나를 변수에 담으려면 Java는 어떤 타입 약속을 요구할까?

준비 개념과 학습 목표

준비 개념

  • interface의 추상 메서드와 default 메서드를 구별한다.

  • 입력 int와 반환 int를 읽을 수 있다.

학습 목표

  • 함수형 인터페이스의 단일 논리 추상 메서드를 판별한다.

  • lambda의 목표 타입과 호출 계약을 설명한다.

같은 한 줄 몸체를 쓰면 어떤 함수형 변수에도 넣을 수 있을까?

앞 본문의 IntOp는 int 입력과 int 반환을 약속했다. 새 두 목표 타입은 Function<String,Integer>와 Consumer<String>이다. String 변수 s를 받아 s.length()를 쓰는 식 lambda는 전자에서 길이를 반환할 수 있고 후자에서도 메서드 호출 식의 결과를 버리는 형태로 사용할 수 있다. 이 예제의 s는 비null ASCII 문자열이라고 정한다. 함수형이라는 말만으로 반환 의미가 같아지는 것은 아니다.

몸체를 블록으로 바꾸면 return 여부를 명시해야 한다. s -> { s.length(); }는 정상적으로 끝나는 void 블록이며 Consumer의 소비 계약에는 맞지만 Function의 Integer 반환을 만들지 못한다. s -> { return s.length(); }는 값을 돌려주는 블록이며 Function에는 맞지만 Consumer의 void 계약에는 맞지 않는다. 목표 타입, 입력 개수, 몸체의 반환 경로를 함께 검사한다. 실제 javac 진단을 수집한 것이 아닌 JLS 규칙에 따른 판별이다.

단일 추상 계약도 선언 줄 수만 세면 놓친다. 새 비sealed 인터페이스 A와 B가 각각 int run(int x)를 선언하고 C가 둘을 상속하면 호환되는 같은 시그니처가 하나의 논리 호출 계약을 만들 수 있다. C에 boolean equals(Object other)를 추상 선언해도 Object의 public 인스턴스 메서드 제외 규칙을 적용한다. 반대로 int undo(int x)를 추가하면 다른 호출 약속이 생긴다. 반환 타입이 충돌하는 불법 상속을 정상 단일 계약이라고 우기지는 않는다.

먼저 확인할 개념
  • 목표 타입과 논리 추상 계약

    함수형 정의와 반환 조건을 한 줄 코드의 외형 대신 호출 계약으로 확인한다.

  • 함수 호출의 관찰 결과

    값을 버리는 소비와 변환 결과 전달의 차이를 후속 단계와 연결한다.

한 가지 호출 약속

Java 함수형 인터페이스는 비sealed 인터페이스이며 하나의 논리적 추상 메서드 계약을 가진다. 단순 예에서는 추상 메서드 하나를 선언한다. Object의 public 인스턴스 메서드에 대응하는 선언은 계산에서 제외하는 등의 규칙이 있다.

상속된 동일 시그니처의 호환되는 메서드들이 하나의 논리 계약을 만들 수도 있다. 소스 선언 줄 수를 무조건 세는 방식은 일반 정의가 아니다. 서로 다른 추상 호출 두 개가 있으면 이 단순 lambda 목표 타입으로 사용할 수 없다.

타입이 몸체를 해석한다

IntOp의 apply(int)→int를 목표로 삼으면 x->x+2의 x와 결과는 그 계약에 맞춰 검사한다. 함수형 값 f를 만드는 것과 f.apply(3)를 호출하는 것은 별개다. 인터페이스가 결과의 의미까지 자동 증명하지는 않는다.

@FunctionalInterface는 의도를 표시하고 조건을 어기면 컴파일 오류를 요구한다. 주석이 없어도 규칙을 만족하면 함수형이다. default·static 메서드가 있다는 이유만으로 추상 메서드 수가 늘지는 않는다.

함수형은 순수함의 이름이 아니다

아래 인터페이스 조각은 자체 작성이다. default twice는 같은 apply를 두 번 호출하므로 상태를 바꾸는 구현을 넘기면 결과가 호출 순서에 따라 달라질 수 있다. 함수형 인터페이스는 호출 모양이지 부수효과 금지 장치가 아니다.

API에는 Predicate의 조건 판정, Consumer의 소비, Function의 변환 같은 역할별 타입이 있다. 필요한 입력과 반환을 기준으로 골라야 한다. 예제 조각의 컴파일·실행은 수행하지 않았다.

@FunctionalInterface
interface IntOp {
  int apply(int x);
  default int twice(int x) { return apply(apply(x)); }
}
// 메서드 안에서 사용할 조각
IntOp plus2 = x -> x + 2;

메서드 이름을 변수에 연결하는 순간 그 메서드도 호출될까?

준비 개념과 학습 목표

준비 개념

  • 함수형 인터페이스의 목표 타입을 안다.

  • 인스턴스 메서드의 수신 객체를 안다.

학습 목표

  • lambda와 메서드 참조의 호출 모양을 대응한다.

  • 값 생성 시점과 호출 시점을 구별한다.

필드를 다른 객체로 바꾸면 저장한 메서드 참조도 따라갈까?

앞 본문은 메서드 참조 생성과 메서드 호출을 구별했다. 새 Box는 int value와 int read(){return value;}를 가지며 Holder는 Box current 필드를 가진다. 지역 변수 h는 재대입하지 않는 Holder이고 h.current는 처음 Box A(value 4)다. IntSupplier bound = h.current::read;와 IntSupplier late = () -> h.current.read();를 만들면 bound는 생성 순간 평가한 A를 수신 객체로 보존하고 late는 호출할 때 h.current를 읽는다.

그 뒤 h.current를 Box B(value 9)로 교체하고 A.value를 6으로 바꾸면 bound 호출은 A의 현재 값 6, late 호출은 B의 현재 값 9를 반환한다. bound가 저장한 것은 A의 주소 역할을 하는 참조이지 생성 때 읽은 정수 4가 아니다. 두 방식 모두 read 몸체는 함수형 호출 때 수행한다. 이 모형은 단일 스레드이고 생성·필드 변경·호출을 명시 순서대로 적용한다.

null 시점도 구별한다. 별도 초기 상태에서 h.current=null이면 h.current::read의 생성은 NullPointerException으로 끝난다. () -> h.current.read()는 이 null 필드를 그 시점에 역참조하지 않으므로 생성 뒤 h.current를 정상 A로 바꾸고 호출할 수 있다. 생성 자체의 할당 실패 등 다른 오류는 이 손모형에서 제외한다. 나중에도 null이면 late의 호출에서 예외가 발생한다.

동작을 뒤에 호출하도록 담기

lambda는 인자와 몸체로 동작을 표현한다. 메서드 참조는 이미 존재하는 메서드나 생성자를 호출할 수 있는 함수형 값을 표현한다. 둘 다 목표 타입과 맞아야 하며 표현식을 만드는 순간 그 몸체나 참조 메서드를 바로 호출하는 것은 아니다.

호출할 때 인터페이스의 추상 메서드가 몸체를 수행한다. 메서드 참조의 왼쪽 수신 표현식은 참조 생성 시 평가될 수 있으므로 아무 표현식이나 lambda와 평가 시점까지 같다고 주장하면 안 된다.

정적 호출과 수신 객체

Math::abs 같은 정적 메서드 참조는 함수 입력을 정적 호출의 인자로 전달한다. String::length처럼 타입 이름으로 인스턴스 메서드를 쓰면 함수의 첫 인자가 수신 객체가 된다. "hello"::length는 수신 객체를 이미 정했으므로 길이를 물을 때 입력이 필요 없다.

오버로드가 있으면 목표 타입의 인자와 반환이 후보 선택에 영향을 준다. 같은 메서드 이름이 있으니 무조건 연결된다고 보지 않는다. null 수신 객체·예외·형 변환도 메서드 계약의 일부다.

소단원 10.3

capture와 effectively final

바깥 변수는 다시 대입할 수 없는데 그 변수가 가리킨 배열은 바꿀 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 지역 변수와 객체 필드를 구분한다.

  • 참조와 객체 내용은 별개다.

학습 목표

  • 지역 변수 캡처의 final 조건을 판별한다.

  • 참조 재대입 제한과 객체 내용 변경을 구별한다.

매번 만든 지역 복사는 반복 횟수마다 다른 값을 기억할까?

앞 본문은 offset 고정과 배열 요소 변경을 나눴다. 새 단일 스레드 반복에서 공유 int[] box={10}을 한 번 만들고, i가 0부터 2까지 바뀔 때마다 int current=i를 새로 선언한다. 각 IntSupplier는 () -> current + box[0]이다. 반복 뒤 box[0]=20으로 바꾸고 세 함수를 호출한다. 첫 함수의 current는 0, 둘째는 1, 셋째는 2다. 공유 요소는 모두 호출 시점의 값 20이므로 첫 반환은 20, 둘째는 21, 셋째는 22다. 함수 생성 때 box[0]의 값 10을 자동 복사하지 않는다.

각 반복의 current는 그 반복에서 선언한 별도 지역 변수이며 다시 대입하지 않는다. 증가하는 기본 for의 i 자체를 캡처하면 effectively final 규칙에 맞지 않는다. 반면 box 참조를 재대입하지 않는다는 조건은 box[0]을 바꾸지 못하게 하는 규칙이 아니다. 함수 목록을 만들었다고 다음 호출의 공유 상태 접근이 스레드 안전해지는 것도 아니다.

정수 snapshot이 필요하면 반복 안에서 int saved=box[0]도 읽고 () -> current+saved를 저장한다. 새 독립 대안은 box의 요소가 여전히 10인 상태에서 세 함수를 만든다. 이후 요소를 20으로 바꾸어도 첫 반환은 10, 둘째는 11, 셋째는 12다. 첫 모형을 수행한 뒤의 값 20을 이어받는 비교가 아니다. 값 snapshot은 가변 객체 그래프의 깊은 복제와 다르다. 모든 대안의 초기 상태를 명시하여 판별한다.

  • 나중 호출과 현재 객체 관찰

    저장한 동작이 언제 배열 내용을 읽는지 추적한다.

바깥 지역 변수를 읽기

lambda가 자기 안에서 선언하지 않은 바깥 지역 변수·매개변수를 사용하면 final 또는 effectively final이어야 한다. effectively final은 final을 쓰지 않았지만 규칙상 다시 대입·증감하지 않은 변수다. 읽기 전에 definite assignment도 필요하다.

lambda 선언 뒤에 지역 변수를 증가시키는 경우도 조건을 어긴다. 먼저 lambda를 만들었으니 이후 변경은 괜찮다는 시간 순서의 해석은 잘못이다. 규칙은 코드 전체의 관련 대입을 고려한다.

고정된 참조와 가변 내용

지역 배열 참조 box를 다른 배열로 재대입하지 않으면 effectively final일 수 있다. 그러나 box[0]을 바꾸는 것은 box 변수에 새 참조를 대입하는 일이 아니다. 배열 내용이 바뀌면 lambda가 다음 호출 때 읽는 내용도 달라질 수 있다.

이 차이 때문에 캡처가 허용된다고 스레드 안전하거나 불변 데이터가 된 것은 아니다. 필드 사용에는 지역 변수 캡처와 다른 규칙이 적용되지만 공유 상태의 동기화와 의미는 여전히 별도 검토한다.

값과 상태의 종이 추적

아래는 같은 메서드 블록 안의 자체 작성 조각이다. offset은 3으로 유지되고 box 변수도 재대입하지 않는다. f는 offset과 배열의 현재 요소를 읽는다. 배열 내용을 5로 바꾸는 줄은 캡처 조건과 구별된다.

offset++을 추가하거나 box=new int[]{5}로 box를 재대입하면 관련 지역 변수의 effectively final 조건이 깨진다. 오류 여부는 표준으로 판별한 예상이며 실제 javac를 실행한 결과는 아니다.

소단원 10.4

함수 합성과 side effect

두 함수를 같은 순서로 묶지 않으면 답도 같을까?

준비 개념과 학습 목표

준비 개념

  • 함수 입력과 반환을 이어 전달할 수 있다.

  • 부수효과는 결과 외의 상태 변화다.

학습 목표

  • andThen과 compose의 순서를 계산한다.

  • 부수효과와 예외가 합성의 관찰 결과에 미치는 영향을 설명한다.

조건 순서를 바꾸면 실패도 기록도 같을까?

앞 본문은 Function 합성의 순서와 예외 전 효과를 다뤘다. 새 비null Integer 입력을 검사하는 Predicate<Integer> positive는 x>0이며 check는 호출마다 log에 x를 추가한 뒤 x가 홀수인지 반환한다. 단일 스레드이고 log는 초기 빈 수정 가능 목록이다. positive.and(check).test(0)는 앞 false 때문에 check를 호출하지 않아 false/빈 log다. check.and(positive).test(0)는 먼저 0을 기록한 뒤 false로 끝나 false/[0]이다. 반환이 같아도 효과는 다르다.

Predicate의 and/or는 단락 평가를 약속한다. 앞 false이면 and의 뒤는 생략하고 앞 true이면 or의 뒤는 생략한다. 이는 Function.andThen처럼 앞 반환을 뒤 입력에 넘기는 변환 합성과 다른 계약이다. 앞 판정이 예외로 끝나면 뒤는 호출되지 않는다. 다른 predicate가 null인 채 합성 객체를 만드는 경우의 NPE와 test 중 예외도 구별한다. 이번 모형의 입력은 비null이며 계산 값은 작은 정수에 한정한다.

새 변환 f는 log에 F를 추가하고 x<0이면 IllegalArgumentException, 그 외 x+1을 반환한다. g는 log에 G를 추가한 뒤 2x를 반환한다. 각각 빈 log에서 f.andThen(g).apply(-1)는 F만 남기고 실패하며, f.compose(g).apply(-1)는 G 뒤 F를 남기고 실패한다. 예외 전달이 앞 효과를 취소하지 않는다. 로깅까지 포함한 원자 성공이 필요하면 후보 데이터를 먼저 계산하고 성공 후 게시하는 별도 정책을 설계해야 한다. 외부 파일·다른 객체까지 무조건 되돌릴 수 있다고 주장하지 않는다.

먼저 확인할 개념
  • 합성 순서와 이미 발생한 효과

    반환·예외·로그의 세 관찰을 분리한다.

  • 호출 모양과 업무 의미

    Predicate라는 타입만으로 순수성이나 실패 보존을 증명하지 않는다.

함수 출력이 다음 입력으로

Function<T,R>는 T를 받아 R로 바꾸는 apply 계약을 제공한다. f.andThen(g)는 먼저 f 다음 g, f.compose(g)는 먼저 g 다음 f다. 앞 출력 타입이 뒤 입력에 맞아야 합성할 수 있다.

합성 순서를 바꾸면 같은 함수들이라도 결과가 달라질 수 있다. identity는 받은 값을 그대로 반환하는 함수다. API가 정한 합성 순서는 임의의 병렬 실행 순서를 뜻하지 않는다.

결과 외에 남는 변화

순수 함수는 같은 입력과 정한 의미에서 같은 결과를 내고 외부 상태를 바꾸지 않는 동작으로 생각할 수 있다. 그러나 Java Function 타입이 이것을 검사하거나 강제하지 않는다. 로그·카운터·파일 쓰기를 몸체에서 수행할 수도 있다.

호출 횟수와 순서를 바꾸면 부수효과도 달라진다. 재시도나 캐시를 적용할 때 반환값만 같다는 이유로 모든 관찰 의미가 같다고 보면 안 된다. 공유 카운터의 동시 증가는 별도 동기화 문제다.

예외와 합성 경계

f가 정상 결과를 만들지 못하고 예외를 던지면 andThen의 g는 그 결과로 실행되지 않는다. 합성 API는 호출 중 예외를 호출자에게 전달한다. f가 예외 전 수행한 부수효과를 자동으로 되돌려 주는 트랜잭션은 아니다.

아래 자체 조각은 작은 정수 4에 한정해 overflow나 null을 제외한다. Function<Integer,Integer>의 박싱과 합성 형식은 API에 맞추되 실제 실행은 하지 않았다.

// 메서드 내부 조각
Function<Integer,Integer> f = x -> x + 2;
Function<Integer,Integer> g = x -> x * 3;
int a = f.andThen(g).apply(4);
int b = f.compose(g).apply(4);
