소단원 6.1

equals·hashCode 계약

같은 좌표 두 개를 집합에 넣었는데 둘 다 남아 있다면 무엇을 확인할까?

준비 개념과 학습 목표

준비 개념

  • 객체와 그 객체를 가리키는 참조는 구별한다.

  • 해시는 후보 위치를 고르는 정수이며 고유 번호가 아니다.

  • 조건문과 정수 곱셈을 추적할 수 있다.

학습 목표

  • equals의 관계 조건을 적용한다.

  • 같은 값이면 같은 해시여야 하는 이유를 설명한다.

  • 충돌과 가변 키의 위험을 구분한다.

어떤 값을 같다고 볼 것인가

자체 Key는 두 정수 x·y가 모두 같을 때만 같은 값으로 정한다. (2,3)과 다른 객체 (2,3)은 equals로 같지만 (2,4)는 다르다. equals는 null이 아닌 대상 사이에서 반사성·대칭성·추이성을 만족해야 하고 관련 값이 변하지 않는 동안 결과가 일관되어야 한다. null과의 비교는 false다.

최종 클래스와 final 정수 필드를 사용하면 상속 때문에 서로 다른 비교 규칙이 섞이거나 키 값이 바뀌는 문제를 줄인다. 타입 검사 뒤 x·y를 비교하는 순서를 읽자. instanceof는 null에도 false이므로 아래 코드에서는 null 필드 접근을 하지 않는다. 이는 정적 추적용 자체 코드이며 실제 컴파일 결과는 아니다.

final class Key {
    private final int x, y;
    Key(int x, int y) { this.x=x; this.y=y; }
    @Override public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Key other)) return false;
        return x == other.x && y == other.y;
    }
    @Override public int hashCode() { return 31*x+y; }
}

해시는 비교를 대신하지 않는다

자체 해시식 31x+y로 (2,3)은 65, (1,34)도 65다. 값은 다르지만 해시는 같아서 충돌한다. 이것은 계약 위반이 아니다. 해시가 같은 후보들을 최종 equals로 구분해야 한다. 반대로 같은 (2,3)인데 두 객체의 해시가 다르면 해시 컬렉션이 다른 후보 위치만 확인해 동등 객체를 놓칠 수 있다.

위 해시식은 이해용이며 모든 키에서 충돌을 없애는 식은 아니다. Java int 계산은 범위를 넘으면 정해진 정수 연산 규칙으로 값이 달라질 수 있지만 같은 x·y에는 같은 결과를 내므로 동등성 계약은 유지한다. 여기서 쓰는 작은 입력은 범위를 넘지 않는다. 기본 해시나 자동 record 해시를 영구 ID로 저장하지 않는다.

집합에 들어 있는 동안 유지할 조건

해시 집합에 키를 넣은 뒤 해시에 쓰는 x를 변경하면 저장할 때의 위치와 찾을 때의 위치가 달라질 수 있다. 키를 잃어버린 것처럼 보일 수 있으므로 이 예제는 final 필드로 변경을 막는다. 변경이 꼭 필요하면 기존 키를 정상적으로 제거한 뒤 새 값을 가진 객체를 삽입하는 정책 등을 검토한다.

equals만 재정의하고 Object의 hashCode를 그대로 쓰는 것은 해시 계약을 보장하지 않는다. hashCode도 함께 값 기준으로 작성하고 같은 값·다른 값·충돌·null의 예를 점검한다. 계산 점검은 구현을 모든 런타임에서 실행했다는 주장과 구별한다.

중간 과정을 따라가는 예제

A=Key(2,3), B=Key(2,3), C=Key(1,34)를 순서대로 HashSet에 넣는다. 필드는 final이고 위 equals·hashCode를 사용한다. 결과를 종이로 예측하라.

  1. A: 31×2+3=65이며 새 값이어서 원소 하나를 만든다.

  2. B: 해시65 뒤 A와 두 필드를 비교해 equals=true이므로 새 값을 더하지 않는다.

  3. C: 31×1+34=65지만 A와 x가 달라 equals=false다. 충돌을 구별해 두 번째 값을 저장한다.

집합 크기는 2이며 값은 (2,3)과 (1,34)다. 이는 API 계약에 따른 예상이며 실제 실행 출력이 아니다.

종이와 본문으로 직접 해보기

D=(0,65), E=(2,3)의 해시와 A와의 동등성을 계산하라. D를 같은 집합에 넣으면 크기는?

힌트 보기

31x+y를 먼저 계산하고 필드 비교는 별도로 한다.

풀이 보기

D의 해시는65지만 A와 x가 달라 다르므로 크기3이 된다. E의 해시는65이고 A와 두 필드가 같아 추가되지 않는다. 해시가 같은 세 값을 구분한다.

오해와 반례

해시65가 같으면 같은 객체다.

(2,3), (1,34), (0,65)는 모두65지만 필드가 다르다. 해시는 후보 선택에 쓰며 고유 ID나 최종 동등성 판정이 아니다.

자기점검

A.equals(null)은?

답과 이유 보기

false다.

타입 검사가 통과하지 않는다.

동등 객체의 해시는 달라도 되는가?

답과 이유 보기

안 된다.

같은 값이면 같은 해시라는 계약을 만족해야 한다.

서로 다른 값의 같은 해시는 오류인가?

답과 이유 보기

그 사실만으로 오류가 아니다.

충돌을 equals로 구별할 수 있다.

한 단계 더

상속으로 색이 있는 좌표를 추가했을 때 부모는 x·y만, 자식은 색까지 비교하면 대칭성·추이성이 어떻게 깨질 수 있는지 세 객체를 그려라. 최종 값 타입의 장점을 연결해 보자.

소단원 6.2

identity와 value equality

내용이 같은 메모 두 장은 한 장의 메모일까?

준비 개념과 학습 목표

준비 개념

  • 참조 변수는 객체를 가리킨다.

  • 새 객체 생성과 기존 참조 대입은 다르다.

  • equals는 클래스가 정의하는 동등성을 따른다.

학습 목표

  • 동일 참조와 같은 값의 질문을 구분한다.

  • 별칭과 새 객체의 비교를 추적한다.

  • null과 기본 Object.equals의 조건을 설명한다.

동일한 대상을 가리키는가

참조형 변수에서 ==는 두 값이 같은 객체를 가리키는지 또는 둘 다 null인지 묻는다. a를 b에 대입하면 객체를 복제하지 않고 같은 객체를 가리키는 별칭을 만든다. 그림에서는 변수 두 개에서 하나의 상자로 화살표를 그린다.

new로 각각 만든 String 객체는 문자가 같아도 두 상자다. 문자열 리터럴의 재사용 최적화 사례에 기대면 구분이 흐려지므로 아래에서는 new String을 명시한다. 기본 Object.equals는 참조 동일성을 사용하지만 String은 내용 동등성으로 재정의한다.

같은 내용이라는 질문

a.equals(c)는 두 String의 문자 내용이 같은지 묻는다. 반면 사용자 정의 클래스가 equals를 재정의하지 않았다면 같은 필드 값을 담았다는 이유만으로 같아지지 않는다. 값 동등성은 객체의 모습이 아니라 클래스의 계약을 읽고 결정한다.

배열 역시 기본 equals가 원소를 순서대로 비교한다고 가정하면 안 된다. 배열 원소를 비교하려면 별도의 배열 비교 규칙을 선택해야 한다. 좌표처럼 값이 중요한 대상과 잠금 객체처럼 동일 인스턴스가 중요한 대상은 질문이 다르다. 한 기준을 모든 곳에 강제로 적용하지 않는다.

null과 호출 대상

null에는 메서드를 호출할 객체가 없으므로 null인 변수에 equals를 호출하면 정상적인 false 결과를 얻는 것이 아니라 NullPointerException이 발생한다. 먼저 null인지 검사한 뒤 호출하는 조건문을 쓰면 된다. null==null은 참조 비교에서 true다.

동등성 판단을 코드에 넣기 전에 참조형인지 기본형인지 확인한다. 이 절에서 ==의 설명은 참조형 비교에 대한 것이다. int의 ==는 정수 값 비교다. 박싱된 정수의 캐시나 문자열 풀을 내용 비교 규칙으로 외우지 말고 계약에 맞는 연산을 선택한다.

String a = new String("달");
String b = a;
String c = new String("달");
String n = null;
boolean sameObject = (a == b);
boolean sameValue = a.equals(c);
boolean safe = (n != null && n.equals(a));

중간 과정을 따라가는 예제

위 자체 코드에서 a==b, a==c, a.equals(c), safe를 순서대로 종이로 예측하라.

  1. a는 첫 String 상자, b는 같은 상자의 별칭이므로 a==b는 true다.

  2. c는 두 번째 새 String 상자이므로 a==c는 false다.

  3. 두 상자의 문자 내용이 달이므로 a.equals(c)는 true다.

  4. n!=null은 false다. &&는 뒤를 평가하지 않으므로 n.equals(a)를 호출하지 않아 safe=false다.

true, false, true, false다. 마지막 경우는 단락 평가로 null 호출을 피한 예상 동작이다.

종이와 본문으로 직접 해보기

c의 참조를 b에 대입한다. a==b와 b.equals(a)를 다시 구하라. a 자체를 바꾼 것인지 설명하라.

힌트 보기

변수 b의 화살표만 옮긴다. String 상자 두 개의 내용은 그대로다.

풀이 보기

b가 c 상자를 가리켜 a==b는 false다. 두 String의 문자 내용은 같아 b.equals(a)는 true다. a가 가리키는 객체나 그 내용은 바뀌지 않았다.

오해와 반례

equals는 언제나 객체의 모든 필드를 자동 비교한다.

재정의하지 않은 일반 클래스는 Object의 참조 기준을 물려받는다. 클래스가 선택한 값 규칙을 확인해야 하며 배열도 내용 비교를 자동 제공한다고 가정하지 않는다.

소단원 6.3

Comparable·Comparator

성적순과 이름순을 모두 쓰려면 객체의 같은 값 기준도 바꿔야 할까?

준비 개념과 학습 목표

준비 개념

  • 정렬은 두 값의 앞뒤 관계를 정한다.

  • 음수·0·양수는 비교 결과의 부호다.

  • 동등성과 정렬은 구분하지만 일관성을 검토해야 한다.

학습 목표

  • 자연 순서와 외부 비교자를 구분한다.

  • 동점의 추가 비교 기준을 적용한다.

  • 정렬 집합의 compare=0 처리와 정수 뺄셈 위험을 설명한다.

자연 순서와 여러 화면의 순서

Comparable의 compareTo는 그 타입의 자연 순서를 정한다. Comparator는 별도 객체나 함수로 순서를 제공하므로 같은 학생을 이름순·점수순으로 표시할 수 있다. compare 결과는 음수·0·양수의 뜻을 읽으며 정확히 -1·0·1만 반환한다고 요구하지 않는다.

비교는 부호의 반대 관계와 추이성을 만족해야 한다. a<b이고 b<c인데 c<a인 순환 비교는 정렬에 쓸 수 없다. int 비교에 a-b를 사용하면 큰 양수에서 음수를 빼는 경우 넘침 때문에 부호가 틀릴 수 있으므로 Integer.compare 같은 비교 연산을 사용한다.

동점이면 다음 키로 넘어가기

자체 Student는 id와 score를 가진 record로 정의하고, 점수 오름차순 다음 ID 오름차순으로 비교한다. 첫 점수가 다르면 ID는 볼 필요가 없고 점수가 같으면 ID를 비교한다. 이는 두 기준을 더하는 것이 아니라 첫 기준이 0일 때만 다음 기준으로 결정하는 사전식 비교다.

아래 비교자는 두 구성값이 모두 같을 때만0이므로 이 Student의 자동 equals와 일치한다. record 선언과 Comparator 사용은 Java 25 기준의 자체 예시이며 실행하지 않았다. 점수만 비교하는 다른 비교자는 화면 정렬에 쓸 수 있지만 정렬 집합에서 별도 문제가 생길 수 있다.

import java.util.Comparator;
record Student(int id, int score) {}
Comparator<Student> byScoreThenId =
    Comparator.comparingInt(Student::score)
              .thenComparingInt(Student::id);

0으로 비교되는 값과 집합

TreeSet과 같은 정렬 집합은 비교 결과0인 값을 같은 정렬 키로 다룬다. (id1,score80)과 (id2,score80)를 점수만 비교하면0이므로 두 학생이 별도 값이어도 한 항목만 남을 수 있다. 점수 다음 ID를 쓰면 구분할 수 있다.

Comparable의 equals 일관성은 강하게 권장되는 조건이다. 모든 표준 타입에서 무조건 동일하다고 외우지 않는다. 정렬 기준과 값 기준이 달라야 하는 업무도 있으므로 계약을 문서화하고 자료구조가 어떤 기준을 사용하는지 확인한다. 이 예제는 null 학생을 허용하지 않는 것으로 정한다.

중간 과정을 따라가는 예제

A=(id2,score80), B=(id1,score80), C=(id3,score70)를 byScoreThenId로 정렬하고, 점수만 비교하는 TreeSet의 예상 크기를 구하라.

  1. C는70이고 A·B는80이므로 C가 먼저다.

  2. A와 B의 점수 비교는0이어서 ID를 비교한다. 1<2이므로 B가 A보다 먼저다.

  3. 점수만 쓰는 TreeSet에 A 다음 B를 넣으면 B는 A와 비교0이므로 새 항목이 되지 않는다. C는70이어서 별도 항목이 된다.

정렬 순서는 C,B,A이며 점수만 비교한 집합의 크기는2다. 복합 비교 집합은 세 값을 구별한다.

종이와 본문으로 직접 해보기

D=(id4,score80)를 추가하면 점수만 비교하는 집합과 복합 비교 집합의 크기는 각각 얼마인가?

힌트 보기

D가 기존80점과0으로 비교되는지, ID까지 비교할 때0인지 나누어 본다.

풀이 보기

점수만 쓰면80이 이미 있어2를 유지한다. 복합 비교에서는 id4가 id1·id2와 달라 새 원소가 되고4가 된다. 비교자의0이 집합 의미에 영향을 준다.

오해와 반례

정렬할 때 점수가 같다는 말은 두 학생 객체가 같은 값이라는 뜻이다.

id1·id2가 달라도 점수 비교는0이다. Student의 값 동등성은 두 필드 모두 비교하므로 false다. 정렬 집합에서는 이 차이를 명시적으로 처리해야 한다.

소단원 6.4

enum·record와 불변 데이터

필드에 final이 붙으면 그 안의 목록도 절대 변하지 않을까?

준비 개념과 학습 목표

준비 개념

  • enum은 선언된 선택지를 타입으로 표현한다.

  • 불변 객체는 생성 후 나타내는 값이 바뀌지 않는다.

  • 참조를 바꾸는 일과 참조 대상의 내용을 바꾸는 일은 다르다.

학습 목표

  • 유한한 상태를 enum으로 표현한다.

  • record의 자동 동등성과 얕은 불변성을 구분한다.

  • 가변 구성값의 방어 복사 조건을 설명한다.

유한한 선택지를 타입으로 만들기

자체 enum LessonState { READY, READING, DONE }는 세 상태를 정의한다. 임의 문자열 "DNOE"가 정상 상태로 들어오는 실수를 줄일 수 있다. enum 상수는 선언된 인스턴스를 가리키며 사용자가 new LessonState로 별도 상수를 만드는 방식은 허용되지 않는다.

상태 타입은 전이 규칙까지 자동 구현하지 않는다. READY에서 DONE으로 건너뛰어도 되는지, 완료 후 READING으로 돌아가는지는 서비스가 정할 정책이다. 이름·선언 순서를 저장 값으로 쓰면 이후 변경 영향을 고려해야 한다. enum에 가변 필드를 넣을 수도 있으므로 enum이라는 단어만으로 모든 내부 데이터가 불변이라고 단정하지 않는다.

값 묶음과 얕은 불변성

record Point(int x,int y)는 구성 필드와 접근자, 값 기준 equals·hashCode 등을 제공한다. int 구성값은 생성 후 바뀌지 않으며 Point(2,3) 두 개는 같은 값이다. 자동 해시의 정확한 숫자 생성식은 계약에서 정하지 않으므로 특정 숫자를 예상 출력으로 외우지 않는다.

record Notebook(java.util.List<String> tags)는 목록 참조를 final로 보관하지만 목록 자체가 가변이면 내부 내용이 바뀔 수 있다. 이것이 얕은 불변성과 깊은 불변성의 차이다. 같은 가변 목록을 외부에서 수정하면 record의 관측 값과 동등성·해시에 영향을 줄 수 있으므로 해시 키로 쓰는 경우 특히 주의한다.

복사와 원소의 조건

자체 Tags record의 간결 생성자에서 names=List.copyOf(names)로 저장하면 입력 목록 구조를 나중에 바꾸어도 저장된 목록에는 반영되지 않는다. copyOf는 null 목록과 null 원소를 거절한다. 이 예제는 String 원소라 원소 자체도 불변이지만 가변 원소를 담으면 구조를 복사한 것만으로 깊은 불변성이 생기지 않는다.

복사가 항상 새 인스턴스를 만들 것이라는 가정도 필요하지 않다. 이미 적합한 비수정 목록은 재사용될 수 있다. 중요한 계약은 원본 구조 변경의 영향과 수정 허용 여부다. 아래 코드는 Java 25의 자체 설명용이며 컴파일·실행하지 않았다.

import java.util.List;
enum LessonState { READY, READING, DONE }
record Point(int x, int y) {}
record Tags(List<String> names) {
    Tags { names = List.copyOf(names); }
}

중간 과정을 따라가는 예제

가변 입력 목록 L=["수학","코딩"]으로 Tags를 만든 뒤 L에 "그림"을 추가한다. Tags.names의 원소와 Point(2,3) 두 객체의 equals 결과를 예측하라.

  1. 생성자에서 현재 두 문자열을 가진 비수정 목록 표현을 확보한다. 입력 L의 구조 변경과 분리된다.

  2. L에 그림을 더하면 L은 세 원소지만 Tags.names는 수학·코딩 두 원소다.

  3. Point 두 객체는 같은 record 타입이며 x=2·y=3이 같으므로 equals=true다. 해시 값도 같아야 하지만 정확한 숫자를 지정하지 않는다.

L의 길이는3, Tags.names의 길이는2, Point 동등성은 true다. 실제 실행 결과가 아닌 계약 기반 추적이다.

종이와 본문으로 직접 해보기

방어 복사 없이 record Raw(List<String> names)로 L을 보관했다면 같은 L 추가 후 길이는? List.copyOf 입력에 null 원소가 있으면?

힌트 보기

참조 대상이 공유되는지와 copyOf의 금지 조건을 분리한다.

풀이 보기

Raw.names는 같은 L을 가리키므로 길이3을 관측한다. null 원소를 가진 목록은 copyOf가 NullPointerException으로 거절한다. 이것은 자동 입력 정화가 아니다.

오해와 반례

record는 모든 구성값을 깊게 복사해 완전히 불변으로 만든다.

가변 List 참조를 그대로 구성값에 넣으면 외부 add가 관측된다. 방어 복사는 직접 설계해야 하고 가변 원소도 별도 처리해야 한다.

자기점검

enum 선언이 상태 전이를 자동 제한하는가?

답과 이유 보기

아니다.

전이 정책은 별도의 조건으로 작성한다.

record의 List 참조 final은 List.add를 막는가?

답과 이유 보기

참조 재대입과 대상 변경은 다르다.

답과 이유 보기

허용하지 않는다.

문서의 사전 조건이며 예외로 거절한다.

한 단계 더

원소가 가변 메모 객체라면 List.copyOf 이후 메모의 text 변경을 그림으로 추적하라. 원소까지 불변 타입으로 만들거나 별도 복사하는 두 대안을 비교해 보자.
