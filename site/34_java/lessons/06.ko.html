equals·hashCode 계약

같은 좌표 두 개를 집합에 넣었는데 둘 다 남아 있다면 무엇을 확인할까?

준비 개념과 학습 목표

준비 개념

  • 객체와 그 객체를 가리키는 참조는 구별한다.

  • 해시는 후보 위치를 고르는 정수이며 고유 번호가 아니다.

  • 조건문과 정수 곱셈을 추적할 수 있다.

학습 목표

  • equals의 관계 조건을 적용한다.

  • 같은 값이면 같은 해시여야 하는 이유를 설명한다.

  • 충돌과 가변 키의 위험을 구분한다.

가까운 두 측정값을 같은 키로 취급하면 중복 제거 순서가 바뀌는가?

앞 본문의 좌표 equals는 두 정수의 정확한 일치를 사용했다. 새 자체 Near 값은 정수 v를 담고, 두 값의 차이 절댓값이 1 이하면 같다고 하는 후보 규칙을 검토한다. 차이 계산은 long으로 확장하여 작은 예제뿐 아니라 int 끝에서도 뺄셈 overflow를 피한다고 정한다. 모든 값의 해시는 0으로 둔다. 해시가 같다는 필요조건은 충족하지만 동등 관계 자체가 적합한지는 별도 질문이다.

A의 값은 0, B는 1, C는 2다. A와 B, B와 C는 가까우나 A와 C는 가깝지 않다. 따라서 후보 규칙은 추이성을 잃는다. 각 새 값을 지금까지 보존한 대표들과만 비교하는 자체 선형 중복 제거 모형에서는 B를 먼저 넣으면 A와 C가 모두 제거되어 대표 하나가 남고, A를 먼저 넣으면 B만 제거되고 C가 남는다. 이 결과는 실제 HashSet의 내부 실행을 주장하는 것이 아니라 비동등 관계를 대표 분할에 사용한 논리 문제를 드러낸다.

가변 키도 다른 실패 경로를 만든다. 별도 자체 버킷 모형은 크기 5이고 key의 비음수 정수 v를 h(v)=v로 해시하여 v mod 5 위치에 저장한다. K의 v가 2일 때 버킷 2에 넣은 뒤 v를 7로 바꾸면 위치는 다시 2지만 저장 때의 값 의미는 바뀐다. v를 3으로 바꾸면 찾는 위치도 3으로 달라진다. 아래 모든 모형은 단일 스레드 손추적이며 실제 Java·해시 컬렉션 실행은 미수행이다.

어떤 값을 같다고 볼 것인가

자체 Key는 두 정수 x·y가 모두 같을 때만 같은 값으로 정한다. (2,3)과 다른 객체 (2,3)은 equals로 같지만 (2,4)는 다르다. equals는 null이 아닌 대상 사이에서 반사성·대칭성·추이성을 만족해야 하고 관련 값이 변하지 않는 동안 결과가 일관되어야 한다. null과의 비교는 false다.

최종 클래스와 final 정수 필드를 사용하면 상속 때문에 서로 다른 비교 규칙이 섞이거나 키 값이 바뀌는 문제를 줄인다. 타입 검사 뒤 x·y를 비교하는 순서를 읽자. instanceof는 null에도 false이므로 아래 코드에서는 null 필드 접근을 하지 않는다. 이는 정적 추적용 자체 코드이며 실제 컴파일 결과는 아니다.

final class Key {
    private final int x, y;
    Key(int x, int y) { this.x=x; this.y=y; }
    @Override public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Key other)) return false;
        return x == other.x && y == other.y;
    }
    @Override public int hashCode() { return 31*x+y; }
}

해시는 비교를 대신하지 않는다

자체 해시식 31x+y로 (2,3)은 65, (1,34)도 65다. 값은 다르지만 해시는 같아서 충돌한다. 이것은 계약 위반이 아니다. 해시가 같은 후보들을 최종 equals로 구분해야 한다. 반대로 같은 (2,3)인데 두 객체의 해시가 다르면 해시 컬렉션이 다른 후보 위치만 확인해 동등 객체를 놓칠 수 있다.

위 해시식은 이해용이며 모든 키에서 충돌을 없애는 식은 아니다. Java int 계산은 범위를 넘으면 정해진 정수 연산 규칙으로 값이 달라질 수 있지만 같은 x·y에는 같은 결과를 내므로 동등성 계약은 유지한다. 여기서 쓰는 작은 입력은 범위를 넘지 않는다. 기본 해시나 자동 record 해시를 영구 ID로 저장하지 않는다.

집합에 들어 있는 동안 유지할 조건

해시 집합에 키를 넣은 뒤 해시에 쓰는 x를 변경하면 저장할 때의 위치와 찾을 때의 위치가 달라질 수 있다. 키를 잃어버린 것처럼 보일 수 있으므로 이 예제는 final 필드로 변경을 막는다. 변경이 꼭 필요하면 기존 키를 정상적으로 제거한 뒤 새 값을 가진 객체를 삽입하는 정책 등을 검토한다.

equals만 재정의하고 Object의 hashCode를 그대로 쓰는 것은 해시 계약을 보장하지 않는다. hashCode도 함께 값 기준으로 작성하고 같은 값·다른 값·충돌·null의 예를 점검한다. 계산 점검은 구현을 모든 런타임에서 실행했다는 주장과 구별한다.

위치가 우연히 같아도 값 변경은 별도 문제

identity와 value equality

내용이 같은 메모 두 장은 한 장의 메모일까?

준비 개념과 학습 목표

준비 개념

  • 참조 변수는 객체를 가리킨다.

  • 새 객체 생성과 기존 참조 대입은 다르다.

  • equals는 클래스가 정의하는 동등성을 따른다.

학습 목표

  • 동일 참조와 같은 값의 질문을 구분한다.

  • 별칭과 새 객체의 비교를 추적한다.

  • null과 기본 Object.equals의 조건을 설명한다.

내용이 같은 두 신청서와 같은 신청서의 재전송을 어떻게 구별할까?

앞 본문은 새 String 두 개와 같은 참조의 별칭을 구별했다. 새 Ticket은 final id와 final amount를 가진 불변 값이고 두 필드가 같을 때 equals라고 정한다. A는 (id 7, amount 20)의 새 객체, B는 A의 별칭, C는 같은 두 필드의 별도 새 객체, D는 (7,21)의 별도 객체다. 참조 정체성, 전체 값, id만 쓰는 업무 중복 기준은 세 관계다.

A와 C는 같은 값이지만 객체는 다르다. A와 D는 같은 업무 id지만 금액이 달라 전체 값은 다르다. 재전송 처리에서 id가 같으면 무조건 성공으로 반환하는 정책은 금액 충돌을 숨길 수 있다. 자체 원장 모형은 최초 id에 요청 금액과 결과를 함께 기록하고, 같은 id/같은 금액의 반복만 기록 결과를 반환하며 같은 id/다른 금액은 충돌로 거절한다고 정한다. 실제 원자 저장·서비스·네트워크 실행을 한 것은 아니다.

배열의 다른 비교도 이어 보자. 독립 int 배열 U={3,5}, V={3,5}, W=U로 정한다. U와 V의 ==와 기본 equals는 false지만 순서별 두 정수 비교는 true다. W를 통해 첫 칸을 9로 바꾸면 U와 W는 {9,5}, V는 {3,5}다. 비교하려는 관찰을 먼저 정한 뒤 복사·별칭·값 변화를 추적한다. 아래 과제와 표는 각각 명시된 초기 상태에서 독립 시작한다.

먼저 확인할 개념
  • 참조 동일성과 값 동등성

    객체 그림과 클래스의 값 계약을 각각 적용한다.

  • equals가 선택한 필드

    id만의 업무 기준과 두 필드의 equals를 혼합하지 않는다.

동일한 대상을 가리키는가

참조형 변수에서 ==는 두 값이 같은 객체를 가리키는지 또는 둘 다 null인지 묻는다. a를 b에 대입하면 객체를 복제하지 않고 같은 객체를 가리키는 별칭을 만든다. 그림에서는 변수 두 개에서 하나의 상자로 화살표를 그린다.

new로 각각 만든 String 객체는 문자가 같아도 두 상자다. 문자열 리터럴의 재사용 최적화 사례에 기대면 구분이 흐려지므로 아래에서는 new String을 명시한다. 기본 Object.equals는 참조 동일성을 사용하지만 String은 내용 동등성으로 재정의한다.

같은 내용이라는 질문

a.equals(c)는 두 String의 문자 내용이 같은지 묻는다. 반면 사용자 정의 클래스가 equals를 재정의하지 않았다면 같은 필드 값을 담았다는 이유만으로 같아지지 않는다. 값 동등성은 객체의 모습이 아니라 클래스의 계약을 읽고 결정한다.

배열 역시 기본 equals가 원소를 순서대로 비교한다고 가정하면 안 된다. 배열 원소를 비교하려면 별도의 배열 비교 규칙을 선택해야 한다. 좌표처럼 값이 중요한 대상과 잠금 객체처럼 동일 인스턴스가 중요한 대상은 질문이 다르다. 한 기준을 모든 곳에 강제로 적용하지 않는다.

null과 호출 대상

null에는 메서드를 호출할 객체가 없으므로 null인 변수에 equals를 호출하면 정상적인 false 결과를 얻는 것이 아니라 NullPointerException이 발생한다. 먼저 null인지 검사한 뒤 호출하는 조건문을 쓰면 된다. null==null은 참조 비교에서 true다.

동등성 판단을 코드에 넣기 전에 참조형인지 기본형인지 확인한다. 이 절에서 ==의 설명은 참조형 비교에 대한 것이다. int의 ==는 정수 값 비교다. 박싱된 정수의 캐시나 문자열 풀을 내용 비교 규칙으로 외우지 말고 계약에 맞는 연산을 선택한다.

  • 자연 순서와 외부 비교자를 구분한다.

  • 동점의 추가 비교 기준을 적용한다.

  • 정렬 집합의 compare=0 처리와 정수 뺄셈 위험을 설명한다.

두 값이 비교에서 0이면 다른 모든 값과의 앞뒤도 같아야 할까?

앞 본문은 점수 다음 ID의 사전식 비교를 사용했다. 새 잘못된 비교 후보는 정수 a와 b의 차이 절댓값이 1 이하면 0, 그렇지 않으면 Integer.compare(a,b)를 반환한다고 정한다. long 차이로 overflow는 막았다고 해도 순서 계약이 자동으로 생기지 않는다. a=0과 b=1은 0으로 비교되지만 z=2에 대해 0은 앞, 1은 동점이라고 나오기 때문이다.

Comparator의 0은 정렬 과정에서 서로 교체할 수 있는 묶음을 의미한다. 같은 묶음의 두 값이 z에 대한 부호를 다르게 주면 묶음 자체에 일관된 위치를 정할 수 없다. 이 결함은 compare를 뺄셈으로 구현하지 않는다고 해서 해결되지 않는다. 또 화면 정렬과 정렬 집합의 중복 의미를 분리해야 한다. 점수만 비교하는 유효한 비교자는 동점 ID들을 0으로 묶을 수 있지만 그 기준의 TreeSet은 ID별 집합을 구현하지 않는다.

별도 Row는 ID 1/2/3과 점수 80/80/70의 불변 값이다. 목표 화면은 점수 내림차순, 동점 ID 오름차순이다. 점수 비교만 reversed한 뒤 ID 기준을 연결하면 1,2,3 순서다. 점수 오름차순 다음 ID 오름차순을 먼저 연결하고 전체 reversed하면 2,1,3 순서로 동점 ID까지 뒤집힌다. 두 후보는 각자 같은 새 세 값을 입력으로 사용하며 실제 정렬·TreeSet·Java 실행은 하지 않았다.

자연 순서와 여러 화면의 순서

Comparable의 compareTo는 그 타입의 자연 순서를 정한다. Comparator는 별도 객체나 함수로 순서를 제공하므로 같은 학생을 이름순·점수순으로 표시할 수 있다. compare 결과는 음수·0·양수의 뜻을 읽으며 정확히 -1·0·1만 반환한다고 요구하지 않는다.

비교는 부호의 반대 관계와 추이성을 만족해야 한다. a<b이고 b<c인데 c<a인 순환 비교는 정렬에 쓸 수 없다. int 비교에 a-b를 사용하면 큰 양수에서 음수를 빼는 경우 넘침 때문에 부호가 틀릴 수 있으므로 Integer.compare 같은 비교 연산을 사용한다.

동점이면 다음 키로 넘어가기

자체 Student는 id와 score를 가진 record로 정의하고, 점수 오름차순 다음 ID 오름차순으로 비교한다. 첫 점수가 다르면 ID는 볼 필요가 없고 점수가 같으면 ID를 비교한다. 이는 두 기준을 더하는 것이 아니라 첫 기준이 0일 때만 다음 기준으로 결정하는 사전식 비교다.

아래 비교자는 두 구성값이 모두 같을 때만0이므로 이 Student의 자동 equals와 일치한다. record 선언과 Comparator 사용은 Java 25 기준의 자체 예시이며 실행하지 않았다. 점수만 비교하는 다른 비교자는 화면 정렬에 쓸 수 있지만 정렬 집합에서 별도 문제가 생길 수 있다.

import java.util.Comparator;
record Student(int id, int score) {}
Comparator<Student> byScoreThenId =
    Comparator.comparingInt(Student::score)
              .thenComparingInt(Student::id);

0으로 비교되는 값과 집합

TreeSet과 같은 정렬 집합은 비교 결과0인 값을 같은 정렬 키로 다룬다. (id1,score80)과 (id2,score80)를 점수만 비교하면0이므로 두 학생이 별도 값이어도 한 항목만 남을 수 있다. 점수 다음 ID를 쓰면 구분할 수 있다.

Comparable의 equals 일관성은 강하게 권장되는 조건이다. 모든 표준 타입에서 무조건 동일하다고 외우지 않는다. 정렬 기준과 값 기준이 달라야 하는 업무도 있으므로 계약을 문서화하고 자료구조가 어떤 기준을 사용하는지 확인한다. 이 예제는 null 학생을 허용하지 않는 것으로 정한다.

Comparator의 0 묶음 조건 위반

0으로 비교한 두 값은 임의 z와 비교한 부호도 같아야 한다. 앞 두 값의 쌍만 확인하거나 음수/양수 반대성만 점검해서는 세 번째 값에서 드러나는 이 결함을 찾지 못한다.

중간 과정을 따라가는 예제

  1. C는70이고 A·B는80이므로 C가 먼저다.

  2. A와 B의 점수 비교는0이어서 ID를 비교한다. 1<2이므로 B가 A보다 먼저다.

  3. 점수만 쓰는 TreeSet에 A 다음 B를 넣으면 B는 A와 비교0이므로 새 항목이 되지 않는다. C는70이어서 별도 항목이 된다.

배열을 방어 복사한 record는 배열 내용의 값 타입이 자동으로 되는가?

앞 본문은 List.copyOf로 목록 구조를 보호했다. 새 Raw record는 int[] values 한 구성값과 자동 equals를 가진다. 별도 두 배열 A={2,4}, B={2,4}로 만든 두 Raw는 배열 내용이 같아도 구성값 배열의 기본 equals가 참조 기준이므로 서로 equals=false다. 같은 A를 담은 두 Raw는 equals=true지만 A[0]=9 쓰기를 함께 관측한다. record의 final 참조, 저장 내용 보존, 값 동등성은 세 의무다.

새 Defensive record의 생성자가 입력 배열을 clone하고 accessor도 저장 배열의 clone을 반환한다고 하자. 자동 equals를 그대로 두면 외부 변경은 격리되지만 각 저장 배열은 별도 객체다. 이때 accessor 값으로 다시 생성한 copy조차 별도 배열을 담아 원래 record와 자동 equals가 false일 수 있다. 이는 record의 접근자-생성자 복원 동등성 의무를 위반하는 설계다. 방어 복사를 추가한 것만으로 모든 record 계약을 해결하지 못한다.

이 단원은 정수 내용의 값 타입이 목표이므로 Values(List<Integer> items)로 바꾸어 입력을 List.copyOf로 보관하는 계획을 선택한다. Integer는 불변이고 목록 순서·원소 값이 비교된다. 생성자는 null 목록/원소를 거절한다. copyOf가 새 목록 정체성을 만들 것인지는 요구하지 않는다. enum도 같은 방식으로 타입과 정책을 나눈다. 자체 READY→READING→DONE만 허용하는 전이표를 명시해야 READY→DONE 건너뛰기를 거절할 수 있고 선언 순서 번호만 검사하는 정책은 충분하지 않다. 모두 실제 Java·record·상태 서비스 실행 없는 손설계다.

유한한 선택지를 타입으로 만들기

자체 enum LessonState { READY, READING, DONE }는 세 상태를 정의한다. 임의 문자열 "DNOE"가 정상 상태로 들어오는 실수를 줄일 수 있다. enum 상수는 선언된 인스턴스를 가리키며 사용자가 new LessonState로 별도 상수를 만드는 방식은 허용되지 않는다.

상태 타입은 전이 규칙까지 자동 구현하지 않는다. READY에서 DONE으로 건너뛰어도 되는지, 완료 후 READING으로 돌아가는지는 서비스가 정할 정책이다. 이름·선언 순서를 저장 값으로 쓰면 이후 변경 영향을 고려해야 한다. enum에 가변 필드를 넣을 수도 있으므로 enum이라는 단어만으로 모든 내부 데이터가 불변이라고 단정하지 않는다.

값 묶음과 얕은 불변성

record Point(int x,int y)는 구성 필드와 접근자, 값 기준 equals·hashCode 등을 제공한다. int 구성값은 생성 후 바뀌지 않으며 Point(2,3) 두 개는 같은 값이다. 자동 해시의 정확한 숫자 생성식은 계약에서 정하지 않으므로 특정 숫자를 예상 출력으로 외우지 않는다.

record Notebook(java.util.List<String> tags)는 목록 참조를 final로 보관하지만 목록 자체가 가변이면 내부 내용이 바뀔 수 있다. 이것이 얕은 불변성과 깊은 불변성의 차이다. 같은 가변 목록을 외부에서 수정하면 record의 관측 값과 동등성·해시에 영향을 줄 수 있으므로 해시 키로 쓰는 경우 특히 주의한다.

복사와 원소의 조건

자체 Tags record의 간결 생성자에서 names=List.copyOf(names)로 저장하면 입력 목록 구조를 나중에 바꾸어도 저장된 목록에는 반영되지 않는다. copyOf는 null 목록과 null 원소를 거절한다. 이 예제는 String 원소라 원소 자체도 불변이지만 가변 원소를 담으면 구조를 복사한 것만으로 깊은 불변성이 생기지 않는다.

복사가 항상 새 인스턴스를 만들 것이라는 가정도 필요하지 않다. 이미 적합한 비수정 목록은 재사용될 수 있다. 중요한 계약은 원본 구조 변경의 영향과 수정 허용 여부다. 아래 코드는 Java 25의 자체 설명용이며 컴파일·실행하지 않았다.

방어 복사와 복원 계약의 충돌

입력 A={2,4}로 Defensive d를 생성한다. d.values()가 clone C를 반환하고 new Defensive(C)가 다시 clone D를 저장한다. 자동 equals를 유지한다.

  1. d의 내부 배열과 C, copy의 D는 서로 다른 배열 객체지만 모두 {2,4}다.

  2. 자동 record equals는 배열 구성값의 참조 동등성을 보므로 내부 배열과 D가 다르다.

d.equals(copy)는 false이며 접근자로 다시 생성한 복원 동등성 의무를 위반한다.

각 부분은 서로 독립인 새 상태에서 시작하는 단일 스레드 손모형이다. (1) Near의 대표 절차에 B=1, A=0, C=2 순서와 A=0, B=1, C=2 순서를 넣고 최종 대표를 비교한다. (2) 자체 업무 원장에 id 7/금액 20/결과 OK7이 있다. 별도 새 Ticket C(7,20)와 D(7,21)의 요청을 각각 판정한다. (3) Row 1/80, 2/80, 3/70의 화면 목표인 점수 내림차순/ID 오름차순과 복합 오름차순 전체 reversed를 비교한다. (4) Defensive의 clone 생성자/clone accessor/자동 equals로 접근자 값을 재생성한 copy와 원본의 동등성을 판정하고, 불변 Integer 목록을 가진 Values 대안을 비교한다. 실제 Java 구현이나 실행을 요구하지 않는다.

힌트 1

같음이라는 이름 대신 Near 관계, 객체 정체성, 전체 Ticket 값, 업무 id, Comparator의 0을 각각 적는다.

힌트 2

역순의 적용 범위를 확인하고 배열 clone의 새 정체성과 불변 목록의 값 비교·복원 의무를 구별한다.

풀이와 답 확인

  1. B 먼저이면 A와 C 모두 B에 가까워 대표 B 하나다. A 먼저이면 B가 제거되지만 C는 A와 달라 대표 A/C 두 개다. 관계의 추이성 위반이 순서 의존을 만든다.

  2. C는 객체가 새로워도 원장의 금액 20과 일치하여 효과 없이 OK7을 재사용한다. D는 id만 같고 금액 21이 달라 충돌 거절하고 기존 기록을 보존한다.

  3. 목표 순서는 ID 1,2,3이다. 복합 오름차순은 3,1,2여서 전체 reversed는 2,1,3이다. 첫 점수 기준만 뒤집어야 동점 ID 오름차순을 보존한다.

  4. Defensive 원본 저장 배열과 재생성한 copy 저장 배열은 서로 다른 객체여서 자동 equals가 false이고 복원 의무에 실패한다. Values는 List.copyOf와 불변 Integer 원소 및 순서 내용 비교로 같은 내용의 재생성을 equals=true로 판정한다. 복사 결과 목록의 정체성은 요구하지 않는다.

같음의 목적과 표현 규약을 각각 적으면 대표 수 1/2, 반복 승인/충돌, ID 순서 1·2·3/2·1·3, Defensive 복원 false/Values 복원 true를 동시에 설명할 수 있다.

해결한 뒤 점검할 것

  • Near의 세 쌍 비교와 두 입력 순서의 대표를 이름별로 적고 실제 HashSet 실행으로 확대하지 않는다.

  • 원장의 id 일치와 금액 일치를 나누어 C 반복 승인/D 충돌 및 기존 기록 보존을 설명한다.

  • 전체 reversed가 동점 ID도 뒤집는 이유를 두 최종 순서로 보인다.

  • 배열 정체성과 목록 내용·Integer 불변성을 나누어 복원 동등성과 실제 Java/학생 미수행을 명시한다.
