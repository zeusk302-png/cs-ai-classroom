pipeline·lazy evaluation

filter를 적는 순간 리스트에서 원소가 바로 지워질까?

준비 개념과 학습 목표

준비 개념

  • 리스트와 람다 함수

  • 참/거짓 조건

학습 목표

  • source·중간·최종 단계의 역할을 구별한다

  • lazy와 단락 종료가 관측에 주는 한계를 설명한다

  • stream의 한 번 소비와 원본 저장소를 나눈다

첫 세 입력과 첫 세 통과 결과는 같은 목록일까?

앞 본문은 lazy한 처리 계획과 원본 목록을 구별했다. 새 source는 순서 있는 비null 정수 목록 [−2,5,−1,4,3]이며 모든 비교는 각자 새 stream에서 시작한다. P는 limit(3) 뒤 양수 filter, Q는 양수 filter 뒤 limit(3)이다. P는 처음 세 입력만 후보로 두어 [5]를 남기지만 Q는 전체 입력에서 처음 세 양수 [5,4,3]을 남긴다. limit의 수가 같아도 어느 단계의 원소를 세는지에 따라 요구가 달라진다.

정렬도 위치에 영향을 받는다. 전체 source를 오름차순 sorted한 뒤 limit(2)하면 [−2,−1]이고, 먼저 limit(2)한 뒤 sorted하면 [−2,5]다. 정렬 앞에 있는 limit는 정렬이 보는 후보 집합을 줄인다. 정렬 뒤 limit는 전체 집합의 작은 값들을 요구한다. 이는 유한 값 의미의 비교이며 두 구현의 실제 메모리 사용이나 비교 횟수를 측정한 것이 아니다.

무한 source에 대한 종료도 최종 결과 길이만으로 결정하지 않는다. 증가하는 0,1,2,…에서 limit(3) 뒤 sorted는 유한 [0,1,2]를 정렬하는 의미를 갖는다. sorted 뒤 limit(3)는 전체 무한 입력의 정렬을 먼저 요구하므로 일반 stream 정렬에서 정상 종료를 기대할 수 없다. 최종 연산이 없으면 둘 다 아직 소비를 요구하지 않은 계획이다. peek나 map의 부수효과를 정확한 방문 장부로 쓰는 설계는 피한다.

먼저 확인할 개념
  • lazy와 stateful 중간 단계

    결과 요구와 입력 전체가 필요한 정렬의 경계를 함께 확인한다.

  • 연산의 순서와 조건 대상

    원소를 먼저 자르는 것과 통과 결과를 자르는 것을 다른 계약으로 읽는다.

데이터와 처리 계획은 다르다

stream은 원소를 담아 둔 리스트 그 자체가 아니라 원소를 처리하는 흐름이다. source에서 시작해 중간 연산을 붙이고 최종 연산으로 결과를 요구한다. filter와 map은 중간 단계이며 reduce나 collect는 결과를 만드는 최종 단계다.

filter 조건을 썼다고 source 리스트에서 탈락한 원소를 지우지 않는다. 이 단원은 null 없는 유한 List<Integer>, 순수 람다, 처리 도중 원본을 바꾸지 않는 경우를 사용한다. 원본 변경·무한 생성·외부 I/O 수명은 조건을 따로 확인한다.

필요할 때 처리한다

중간 연산을 붙이는 것은 lazy한 처리 계획을 구성하는 일이다. 최종 결과를 요구할 때 순회가 시작된다. findFirst처럼 필요한 답이 정해지면 뒤 원소를 모두 처리할 필요가 없는 연산이 있다.

손 추적의 값 흐름은 반환값을 이해하기 위한 표다. 구현은 결과에 영향을 주지 않는 단계를 생략할 수 있어 람다 호출 수와 println 출력 순서를 부수효과로 의존하지 않는다. peek 뒤 count에서 원소 수를 바로 알 수 있는 경우가 대표적이다.

소비 후에는 새 흐름을 만든다

최종 연산에 사용한 stream은 소비된 것으로 취급한다. 같은 stream 변수를 다시 순회하는 계획을 세우지 말고 원본에서 새 stream을 만든다. 원본 List를 재사용하는 것과 동일 stream을 재사용하는 것은 다르다.

정렬 같은 상태 있는 중간 연산은 전체 입력을 먼저 볼 필요가 있을 수 있다. lazy라는 말이 모든 처리를 반드시 원소 하나씩만 즉시 내놓는다는 뜻은 아니다. 무한 source에 sorted를 먼저 붙이면 뒤 limit만으로 종료를 기대할 수 없다.

각 행은 같은 source에서 새 stream을 만든 독립 대안이다. 중간 처리 목록은 손으로 값 의미를 설명하기 위한 것이며 실제 라이브러리가 해당 임시 목록을 할당했다는 뜻이 아니다. 음수 기호와 탈락 여부를 먼저 확인한 뒤 각 limit가 세는 위치를 읽는다.

중간 과정을 따라가는 예제

source=[1,2,3,4,5]에서 순차 stream.filter(x→x%2==0).map(x→x*10).findFirst()의 값을 손 추적하라. 이는 코드 실행이나 람다 호출 횟수 보장이 아닌 값 의미 추적이다.

  1. 1은 짝수 조건에서 탈락한다. 첫 통과 값은 2다.

  2. 2를 10배로 바꾸면 20이다. 순서 있는 source의 첫 결과는 20이다.

  3. findFirst는 Optional<Integer>로 20을 감싼 값을 반환한다. 모든 source를 미리 리스트로 변환해야 하는 것은 아니다.

Optional의 값은 20이다. 중간 단계 구성만으로 처리한 출력은 없으며 source는 그대로다.

앞 본문은 reduce의 항등원과 결합성을 강조했다. 새 입력 [2,4,12]를 교육용 부분 [2,4]와 [12]로 나누면 평균은 각각 3과 12다. 두 평균의 단순 평균 7.5는 전체 평균 6이 아니다. 앞 부분에 원소가 둘, 뒤 부분에 하나 있다는 분모 정보를 버렸기 때문이다. 평균 하나 대신 합계와 개수의 쌍을 부분 결과로 보존한다.

새 불변 쌍 (sum,count)의 항등값은 (0,0), 원소 x의 쌍은 (x,1), 두 쌍의 병합은 각 성분의 덧셈이다. 지정 입력에서 첫 부분 (6,2)와 둘째 (12,1)을 합치면 (18,3)이고 마지막에 18/3=6이다. 모든 합계와 개수가 선택한 정수형 범위 안이라는 전제를 둔다. 평균 나눗셈은 count>0에서만 수행하고 빈 입력은 평균 부재로 남긴다. count 0을 평균 0이라는 관측으로 바꾸지 않는다.

서로 다른 accumulator와 combiner를 쓰는 세 인자 reduce에는 항등원·결합성 외에 호환 조건도 필요하다. 이번 과제의 잘못된 조합은 accumulator가 (s,c)에 원소 x를 반영하여 (s+x,c+1)을 만들지만, combiner는 두 부분 결과를 (s1+s2,max(c1,c2))로 합치는 것이다. u=(6,2), x=12에서 직접 반영하면 (18,3)이다. 반면 항등값 (0,0)에 x를 반영한 (12,1)을 u와 병합하면 (18,2)이므로 API의 호환식 combiner(u,accumulator(identity,x))=accumulator(u,x)가 실패한다. 합계에 2x를 더하는 accumulator와 부분 합계를 더하는 combiner라는 조합 자체는 이 호환식의 반례가 아니다. 한 원소를 어느 경로로 반영해도 같은 표현이 되도록 정의해야 한다. 여기서는 불변 쌍을 만드는 수학적 설계만 하고 구현 코드를 실행하지 않았다.

남길 것과 바꿀 것을 나눈다

filter는 각 원소에 조건을 적용해 통과한 원소만 남긴다. map은 각 원소를 함수 반환값으로 바꾼다. 원소 타입도 달라질 수 있다. reduce는 여러 값을 결합해 결과를 축적하는 최종 연산이다.

입력 순서와 단계별 값을 표에 적으면 다른 이름의 연산을 하나로 착각하지 않는다. 이 예제의 int 값은 작고 오버플로가 없으며 함수는 외부 상태를 변경하지 않는다. 실제 언어의 정수 한도와 실수 오차는 별도 조건이다.

조건이 어느 값을 보는지 확인한다

filter가 map보다 앞이면 원래 값을 검사한다. map 뒤 filter면 변환한 값이 검사 대상이다. 예컨대 x>3은 원래3을 제외하지만 3을 두 배로 만든 뒤 검사하면6을 포함한다.

순서를 바꾸어도 같은 결과가 되는 경우는 있지만 모든 경우가 그런 것은 아니다. 함수와 조건의 관계를 증명하거나 반례로 판단한다. 더 짧은 표현이라는 이유만으로 의미가 보존됐다고 결론 내리지 않는다.

결합에는 규칙이 있다

reduce(0, Integer::sum)은0을 항등값으로 사용한다. 빈 흐름에서는0이고 덧셈 결합의 의미를 유지한다. 항등값 없는 reduce는 결과 부재를 Optional로 표현한다. 임의의 시작값은 병렬 파티션마다 반복될 수 있으므로 항등원으로 사용할 수 없다.

결합 함수는 묶음을 다르게 나눠도 결과가 같은 결합성을 만족해야 한다. 뺄셈은 일반적으로 그렇지 않다. reduce를 순차 왼쪽 루프로 이해한 손 표가 실제 병렬 실행의 허용조건을 대신하지 않는다.

양수가 없는 부서의 키를 없앨까, 빈 그룹으로 남길까?

앞 본문은 groupingBy 앞에서 filter하면 탈락한 키가 생기지 않는다고 설명했다. 새 비null 기록은 (부서,값)의 순서 있는 [(A,2),(B,−1),(A,4),(C,0),(B,3)]이다. 양수만 먼저 걸러 부서별 리스트를 만들면 A→[2,4], B→[3]이며 C 키는 없다. 전체 부서가 존재했다는 사실까지 결과에 남겨야 한다면 같은 요구가 아니다.

전체 기록을 부서로 groupingBy한 뒤 downstream filtering으로 양수만 누적하면 기록이 존재한 C의 그룹을 빈 결과로 남길 수 있다. 여기서는 각 그룹에서 값만 모으는 mapping과 toList를 결합한다고 정해 A→[2,4], B→[3], C→[]라는 값 관계를 얻는다. source에 없는 D 부서는 이 방식으로도 자동 생성되지 않는다. 키의 존재, 빈 그룹, source 전체에 없는 키를 세 가지로 나눈다.

키 충돌 정책도 별도다. toMap의 두 인자 형태로 부서→값을 만들면 A와 B의 반복 키 때문에 정상 완성 대신 IllegalStateException이 발생한다. 값을 합치는 merge를 명시하면 전체 입력에서 A→6, B→2, C→0이라는 다른 집계가 된다. grouping의 리스트를 자동 합계로 해석하지 않는다. 기본 Map의 키 반복 순서와 반환 컨테이너의 수정 가능성은 여전히 별도 계약이다.

먼저 확인할 개념
  • 앞 filter와 그룹 키 부재

    새 downstream filtering의 빈 그룹 보존과 비교한다.

  • 남기는 원소와 집계 값

    리스트/합계/개수라는 서로 다른 결과 의미를 구별한다.

모으는 전략을 지정한다

collect는 결과 컨테이너에 원소를 모으는 최종 연산이다. Collector는 생성·누적·병합·마무리 전략을 담아 재사용하게 한다. 병렬일 때 각 부분 결과를 분리해 만들고 올바르게 병합할 수 있다.

toList라는 이름만 보고 모든 API의 반환 계약을 같게 생각하지 않는다. Stream.toList는 수정 불가 List를 반환하지만 Collectors.toList는 구체 타입이나 수정 가능성을 보장하지 않는다. 필요한 컨테이너 계약은 문서나 명시한 factory로 정한다.

키를 정한 뒤 그룹을 처리한다

groupingBy의 classifier는 원소를 어느 키에 둘지 정한다. 기본은 키마다 해당 원소 List를 모은다. downstream에 counting을 주면 각 그룹의 원소 수가 Long 값이 된다. Map<String,List<T>>처럼 표기된 타입과 Map<Integer,Long> 같은 집계 결과를 구별한다.

기본 groupingBy의 Map 키 순서를 출력 순서로 약속하지 않는다. 결과를 보여줄 때 키순 정렬을 별도로 선택하거나 mapFactory를 지정한다. 여기서는 사전형의 키→값 관계만 정답으로 적어 실제 toString 순서를 주장하지 않는다.

그룹 밖으로 사라지는 키도 있다

앞 filter에서 모든 원소가 탈락한 키는 기본 groupingBy 결과에 생기지 않는다. 기존 가능한 키 전체를 미리 채워 넣었다는 가정을 추가하지 않는다. 빈 source의 기본 그룹 결과도 빈 Map이다.

groupingBy 자체는 concurrent collector가 아니다. 병렬에서도 부분 Map을 병합해 사용할 수 있지만 하나의 Map을 모든 스레드가 마음대로 동시에 수정하는 것과 다르다. 결과 List의 thread safety까지 자동 보장한다고 해석하지 않는다.

소단원 11.4

parallel stream의 조건

작은 합계 계산에 parallel을 붙이면 반드시 빨라질까?

준비 개념과 학습 목표

준비 개념

  • reduce의 항등원과 결합성

  • 동시에 공유 값을 바꾸는 위험

학습 목표

  • 병렬 파티션과 병합 조건을 설명한다

  • 공유 가변 부수효과와 순수 집계를 구별한다

  • 계산 의미·순서·성능 측정을 분리한다

수집기의 supplier가 같은 목록을 돌려주어도 병렬 부분이 분리될까?

앞 본문은 외부 공유 ArrayList 대신 부분 컨테이너와 올바른 병합을 권했다. 새 collect 계획이 supplier에서 항상 하나의 saved 목록을 반환한다면 supplier라는 이름만으로 분리되지 않는다. 두 교육 파티션 P=[1], Q=[2]의 컨테이너가 같은 S를 가리키면 축적부터 공유하고 병합에서 S.addAll(S)라는 자기 병합까지 생긴다. 이 잘못된 계획을 실제 병렬 실행의 특정 결과로 약속하지 않는다.

올바른 mutable collect 설계는 supplier 호출마다 새 빈 컨테이너를 만들고, 각 부분에서만 누적한 뒤 두 부분을 정해진 병합으로 합친다. P의 독립 LP=[1], Q의 LQ=[2]를 LP.addAll(LQ)로 합치면 [1,2]다. 순서 있는 목록 집계와 다른 입력/공유 효과를 구별한다. 값 reduce에 하나의 수정 가능 identity를 넣어 계속 바꾸는 방식은 이 fresh 공급 계약을 대신하지 못한다.

성능은 의미 검사 뒤에 별도 묻는다. 자체 가상 비용 모델을 Tseq(n)=2n, Tpar(n)=30+n으로 둔다. 단위는 임의 시간 단위이고 균등 분할·총 오버헤드 30을 가정한다. n=20에서는 40 대 50이라 병렬 모델이 느리며 n=60에서는 120 대 90이다. 두 값이 같은 n=30 경계와 n>30의 모델상 우세는 특정 CPU/JDK의 측정 결과가 아니다. ordered limit나 비균등 작업은 이 식의 전제를 바꾼다.

먼저 확인할 개념
  • 부분 결과 격리와 성능 분리

    결과의 안전성과 실제 시간 검증을 다른 게이트로 둔다.

  • 수집 전략과 반환 컨테이너

    supplier·누적·병합의 역할을 구체적인 객체 정체성으로 확인한다.

나누기와 합치기가 맞아야 한다

병렬 stream은 여러 부분의 처리를 나누어 병합할 수 있다. 순수 필터와 변환, 올바른 reduce는 이런 조합에 맞는다. source를 처리 중 바꾸지 않고 함수가 변화하는 공유 상태에 의존하지 않도록 한다.

항등원·결합성은 장식이 아니다. 파티션 수에 따라 초기값을 더 넣거나 병합 순서를 바꾸어 결과가 달라지면 올바른 집계 계약을 만족하지 않는다. 단순 덧셈 예제는 작은 int 값으로 오버플로 문제를 제외한다.

결과를 모으고 공유 상태는 피한다

외부 합계 변수에 여러 thread가 읽기→더하기→쓰기를 하면 갱신을 잃을 수 있다. 결과를 reduce/collect로 표현하여 라이브러리가 부분 결과를 올바르게 합치게 한다. 외부 ArrayList에 parallel forEach로 무조건 add하는 설계도 안전하지 않다.

forEach는 병렬 source의 만남 순서를 보장하지 않는다. forEachOrdered는 정의된 만남 순서에 맞는 최종 action을 제공하지만 모든 mapper 실행이 한 thread에서 그 순서대로 된다는 약속은 아니다. 결과 순서와 내부 평가 순서를 분리한다.

빨라짐은 별도 관측이다

분할·스케줄·병합에도 비용이 든다. 데이터 크기, source의 분할 특성, 각 원소의 계산량, 상태 있는 단계, 장비를 같이 확인해야 한다. parallel이라는 표시만으로 elapsed time 감소를 확정하지 않는다.

교육용 부분합 표는 실제 JDK의 분할 순서나 thread 수 관측이 아니다. 성능 검증을 추가할 때 정확한 결과와 조건을 먼저 확인한 뒤 실제 입력·JDK·장비·반복 측정 범위를 기록한다. 이 단원에서는 시간 측정을 하지 않았다.
