소단원 11.1

pipeline·lazy evaluation

filter를 적는 순간 리스트에서 원소가 바로 지워질까?

준비 개념과 학습 목표

준비 개념

  • 리스트와 람다 함수

  • 참/거짓 조건

학습 목표

  • source·중간·최종 단계의 역할을 구별한다

  • lazy와 단락 종료가 관측에 주는 한계를 설명한다

  • stream의 한 번 소비와 원본 저장소를 나눈다

데이터와 처리 계획은 다르다

stream은 원소를 담아 둔 리스트 그 자체가 아니라 원소를 처리하는 흐름이다. source에서 시작해 중간 연산을 붙이고 최종 연산으로 결과를 요구한다. filter와 map은 중간 단계이며 reduce나 collect는 결과를 만드는 최종 단계다.

filter 조건을 썼다고 source 리스트에서 탈락한 원소를 지우지 않는다. 이 단원은 null 없는 유한 List<Integer>, 순수 람다, 처리 도중 원본을 바꾸지 않는 경우를 사용한다. 원본 변경·무한 생성·외부 I/O 수명은 조건을 따로 확인한다.

필요할 때 처리한다

중간 연산을 붙이는 것은 lazy한 처리 계획을 구성하는 일이다. 최종 결과를 요구할 때 순회가 시작된다. findFirst처럼 필요한 답이 정해지면 뒤 원소를 모두 처리할 필요가 없는 연산이 있다.

손 추적의 값 흐름은 반환값을 이해하기 위한 표다. 구현은 결과에 영향을 주지 않는 단계를 생략할 수 있어 람다 호출 수와 println 출력 순서를 부수효과로 의존하지 않는다. peek 뒤 count에서 원소 수를 바로 알 수 있는 경우가 대표적이다.

소비 후에는 새 흐름을 만든다

최종 연산에 사용한 stream은 소비된 것으로 취급한다. 같은 stream 변수를 다시 순회하는 계획을 세우지 말고 원본에서 새 stream을 만든다. 원본 List를 재사용하는 것과 동일 stream을 재사용하는 것은 다르다.

정렬 같은 상태 있는 중간 연산은 전체 입력을 먼저 볼 필요가 있을 수 있다. lazy라는 말이 모든 처리를 반드시 원소 하나씩만 즉시 내놓는다는 뜻은 아니다. 무한 source에 sorted를 먼저 붙이면 뒤 limit만으로 종료를 기대할 수 없다.

중간 과정을 따라가는 예제

source=[1,2,3,4,5]에서 순차 stream.filter(x→x%2==0).map(x→x*10).findFirst()의 값을 손 추적하라. 이는 코드 실행이나 람다 호출 횟수 보장이 아닌 값 의미 추적이다.

  1. 1은 짝수 조건에서 탈락한다. 첫 통과 값은 2다.

  2. 2를 10배로 바꾸면 20이다. 순서 있는 source의 첫 결과는 20이다.

  3. findFirst는 Optional<Integer>로 20을 감싼 값을 반환한다. 모든 source를 미리 리스트로 변환해야 하는 것은 아니다.

Optional의 값은 20이다. 중간 단계 구성만으로 처리한 출력은 없으며 source는 그대로다.

힌트 보기

풀이 보기

오해와 반례

lazy라면 최종 연산이 있어도 반드시 모든 람다를 입력마다 한 번씩 호출한다.

최종 결과에 필요한 처리와 실제 구현 호출 횟수는 다르다. 단락 종료·연산 생략 가능성이 있으므로 부수효과 로그를 정확한 작업수 계약으로 사용하지 않는다.

소단원 11.2

map·filter·reduce

걸러내기와 값 바꾸기의 순서를 바꾸면 같은 합계가 나올까?

준비 개념과 학습 목표

준비 개념

  • 함수와 조건식

  • 덧셈의 항등원0

학습 목표

  • 각 연산의 입력/출력 원소 의미를 추적한다

  • 파이프라인 순서가 조건의 대상 값을 바꿈을 설명한다

  • reduce의 항등원·결합 조건과 빈 경우를 확인한다

남길 것과 바꿀 것을 나눈다

filter는 각 원소에 조건을 적용해 통과한 원소만 남긴다. map은 각 원소를 함수 반환값으로 바꾼다. 원소 타입도 달라질 수 있다. reduce는 여러 값을 결합해 결과를 축적하는 최종 연산이다.

입력 순서와 단계별 값을 표에 적으면 다른 이름의 연산을 하나로 착각하지 않는다. 이 예제의 int 값은 작고 오버플로가 없으며 함수는 외부 상태를 변경하지 않는다. 실제 언어의 정수 한도와 실수 오차는 별도 조건이다.

조건이 어느 값을 보는지 확인한다

filter가 map보다 앞이면 원래 값을 검사한다. map 뒤 filter면 변환한 값이 검사 대상이다. 예컨대 x>3은 원래3을 제외하지만 3을 두 배로 만든 뒤 검사하면6을 포함한다.

순서를 바꾸어도 같은 결과가 되는 경우는 있지만 모든 경우가 그런 것은 아니다. 함수와 조건의 관계를 증명하거나 반례로 판단한다. 더 짧은 표현이라는 이유만으로 의미가 보존됐다고 결론 내리지 않는다.

결합에는 규칙이 있다

reduce(0, Integer::sum)은0을 항등값으로 사용한다. 빈 흐름에서는0이고 덧셈 결합의 의미를 유지한다. 항등값 없는 reduce는 결과 부재를 Optional로 표현한다. 임의의 시작값은 병렬 파티션마다 반복될 수 있으므로 항등원으로 사용할 수 없다.

결합 함수는 묶음을 다르게 나눠도 결과가 같은 결합성을 만족해야 한다. 뺄셈은 일반적으로 그렇지 않다. reduce를 순차 왼쪽 루프로 이해한 손 표가 실제 병렬 실행의 허용조건을 대신하지 않는다.

중간 과정을 따라가는 예제

입력=[1,2,3,4], filter(x→x>2), map(x→x*x), reduce(0, Integer::sum)의 결과를 계산하라.

  1. filter 통과 값은 3, 4다.

  2. map 제곱은 9, 16이다.

  3. 항등값 0부터 0+9=9, 9+16=25다. 이 작은 값에는 int 오버플로가 없다.

결과는 25이며 source의 원소를 제곱으로 바꿔 저장한 것은 아니다.

종이와 본문으로 직접 해보기

입력=[1,2,3]에서 filter(x→x>3) 뒤 map(x→2*x)의 리스트와, map 뒤 같은 filter의 리스트를 비교하라.

힌트 보기

필터가 검사하는 값이 원래 입력인지 변환 결과인지 구별한다.

풀이 보기

앞 필터는 통과 값이 없어 []다. 먼저 map하면 [2,4,6], 뒤 필터는 [4,6]이다. 순서 변경은 의미를 바꾼다.

오해와 반례

reduce는 임의 이항 연산을 순차/병렬 모두 같은 결과로 만든다.

결합성·항등원 및 상태 조건을 지켜야 한다. (10−3)−2=5지만10−(3−2)=9이므로 뺄셈은 묶음 변경에 안전하지 않다.

한 단계 더

덧셈에 시작값10을 넣어 reduce(10,Integer::sum)로 [1,2,3]의 단순 왼쪽 표를 만들면16이다. 그러나 두 파티션에10을 각각 넣고 합치면(10+1)+(10+2+3)=26이 된다. 10은 덧셈의 항등원이 아니므로 이러한 reduce 사용은 계약을 위반한다. 순차/병렬 어느 결과를 정답 API보장이라고 주장하지 않는다.

소단원 11.3

collector와 grouping

같은 길이의 단어를 묶고 각 묶음 개수를 동시에 셀 수 있을까?

준비 개념과 학습 목표

준비 개념

  • Map의 키와 값

  • 문자열과 리스트

학습 목표

  • collect의 결과 수집 전략을 설명한다

  • 분류키와 그룹 안의 downstream 처리를 구별한다

  • 결과 컨테이너의 순서·수정 가능성을 확인한다

모으는 전략을 지정한다

collect는 결과 컨테이너에 원소를 모으는 최종 연산이다. Collector는 생성·누적·병합·마무리 전략을 담아 재사용하게 한다. 병렬일 때 각 부분 결과를 분리해 만들고 올바르게 병합할 수 있다.

toList라는 이름만 보고 모든 API의 반환 계약을 같게 생각하지 않는다. Stream.toList는 수정 불가 List를 반환하지만 Collectors.toList는 구체 타입이나 수정 가능성을 보장하지 않는다. 필요한 컨테이너 계약은 문서나 명시한 factory로 정한다.

키를 정한 뒤 그룹을 처리한다

groupingBy의 classifier는 원소를 어느 키에 둘지 정한다. 기본은 키마다 해당 원소 List를 모은다. downstream에 counting을 주면 각 그룹의 원소 수가 Long 값이 된다. Map<String,List<T>>처럼 표기된 타입과 Map<Integer,Long> 같은 집계 결과를 구별한다.

기본 groupingBy의 Map 키 순서를 출력 순서로 약속하지 않는다. 결과를 보여줄 때 키순 정렬을 별도로 선택하거나 mapFactory를 지정한다. 여기서는 사전형의 키→값 관계만 정답으로 적어 실제 toString 순서를 주장하지 않는다.

그룹 밖으로 사라지는 키도 있다

앞 filter에서 모든 원소가 탈락한 키는 기본 groupingBy 결과에 생기지 않는다. 기존 가능한 키 전체를 미리 채워 넣었다는 가정을 추가하지 않는다. 빈 source의 기본 그룹 결과도 빈 Map이다.

groupingBy 자체는 concurrent collector가 아니다. 병렬에서도 부분 Map을 병합해 사용할 수 있지만 하나의 Map을 모든 스레드가 마음대로 동시에 수정하는 것과 다르다. 결과 List의 thread safety까지 자동 보장한다고 해석하지 않는다.

중간 과정을 따라가는 예제

null 없는 ASCII 단어 List.of("cat","dog","a","ox","cat")를 stream.collect(Collectors.groupingBy(String::length,Collectors.counting()))로 모으는 값 의미를 추적하라. ASCII라 Java length가 여기서 문자 수와 같다.

  1. 길이 3에 cat, dog, cat의 세 원소를 분류한다. 중복 cat도 별도 입력 원소다.

  2. 길이 1에 a 한 개, 길이 2에 ox 한 개다.

  3. downstream counting 결과는 길이 1→1L, 2→1L, 3→3L이다. Map 키 순서와 출력 포맷은 고정하지 않는다.

키→Long 관계 {1→1L,2→1L,3→3L}이다. 중복 제거 결과가 아니다.

종이와 본문으로 직접 해보기

같은 source를 먼저 length>1로 filter한 뒤 같은 그룹 count를 구하라. 기본 groupingBy만 쓰면 각 그룹의 List는?

힌트 보기

길이1의 a가 source흐름에서 탈락했으므로 키가 남는지 확인한다.

풀이 보기

count는 2→1L, 3→3L이고 1 키는 없다. 기본 그룹 List는 2→[ox], 3→[cat,dog,cat]이다. 원본 List의 순서 있는 순차 흐름을 따른다.

오해와 반례

groupingBy 결과 Map의 키는 기본으로 숫자 오름차순이다.

소단원 11.4

parallel stream의 조건

작은 합계 계산에 parallel을 붙이면 반드시 빨라질까?

준비 개념과 학습 목표

준비 개념

  • reduce의 항등원과 결합성

  • 동시에 공유 값을 바꾸는 위험

학습 목표

  • 병렬 파티션과 병합 조건을 설명한다

  • 공유 가변 부수효과와 순수 집계를 구별한다

  • 계산 의미·순서·성능 측정을 분리한다

나누기와 합치기가 맞아야 한다

병렬 stream은 여러 부분의 처리를 나누어 병합할 수 있다. 순수 필터와 변환, 올바른 reduce는 이런 조합에 맞는다. source를 처리 중 바꾸지 않고 함수가 변화하는 공유 상태에 의존하지 않도록 한다.

항등원·결합성은 장식이 아니다. 파티션 수에 따라 초기값을 더 넣거나 병합 순서를 바꾸어 결과가 달라지면 올바른 집계 계약을 만족하지 않는다. 단순 덧셈 예제는 작은 int 값으로 오버플로 문제를 제외한다.

결과를 모으고 공유 상태는 피한다

외부 합계 변수에 여러 thread가 읽기→더하기→쓰기를 하면 갱신을 잃을 수 있다. 결과를 reduce/collect로 표현하여 라이브러리가 부분 결과를 올바르게 합치게 한다. 외부 ArrayList에 parallel forEach로 무조건 add하는 설계도 안전하지 않다.

forEach는 병렬 source의 만남 순서를 보장하지 않는다. forEachOrdered는 정의된 만남 순서에 맞는 최종 action을 제공하지만 모든 mapper 실행이 한 thread에서 그 순서대로 된다는 약속은 아니다. 결과 순서와 내부 평가 순서를 분리한다.

빨라짐은 별도 관측이다

분할·스케줄·병합에도 비용이 든다. 데이터 크기, source의 분할 특성, 각 원소의 계산량, 상태 있는 단계, 장비를 같이 확인해야 한다. parallel이라는 표시만으로 elapsed time 감소를 확정하지 않는다.

교육용 부분합 표는 실제 JDK의 분할 순서나 thread 수 관측이 아니다. 성능 검증을 추가할 때 정확한 결과와 조건을 먼저 확인한 뒤 실제 입력·JDK·장비·반복 측정 범위를 기록한다. 이 단원에서는 시간 측정을 하지 않았다.

중간 과정을 따라가는 예제

입력 [1,2,3,4]의 합을 항등원 0과 덧셈으로 계산한다. 교육 분할은 [1,2]와 [3,4] 두 부분이다. 부분합과 병합을 계산하고 전체와 비교하라.

  1. 첫 부분은 0+1+2=3, 둘째는 0+3+4=7이다.

  2. 두 결과를 3+7=10으로 병합한다.

  3. 전체 0+1+2+3+4=10과 같다. 다른 분할 [1]/[2,3,4]도 1+9=10으로 같은 의미다.

합은 10이며 실제 두 thread로 실행했다는 결과는 아니다.

두 번째 쓰기가 첫 결과를 덮는지 확인한다.

마지막 값은 2로 올바른 합 3을 잃는다. 이는 공유 갱신 경쟁의 자체 시간선이며 특정 실행을 재현한 기록은 아니다. 순수 부분합 1, 2를 합치면 3이다.

오해와 반례

parallelStream이면 결과와 로그 순서와 실행 시간이 모두 순차와 같다.

올바른 집계 의미와 만남 순서, 내부 평가·부수효과 순서, elapsed time은 다른 계약이다. forEach 순서 비보장과 공유 갱신 값 2의 반례 및 분할 비용을 구별한다.

한 단계 더

실수 덧셈은 표현 오차로 수학적 결합성처럼 행동하지 않을 수 있다. 같은 분할 순서가 항상 보장되지 않으면 반올림 결과 차이도 별도 검토한다. 정확한 금액과 근사 과학 계산의 허용 오차 계약을 구별하고 정수 예제의 동일 결과를 모든 실수 집계로 일반화하지 않는다.
