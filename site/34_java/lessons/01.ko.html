소단원 1.1

source·bytecode·JVM

Hello.java를 복사하는 것과 Hello.class를 복사하는 것은 무엇이 다를까?

준비 개념과 학습 목표

준비 개념

  • 파일은 이름이 있는 저장 내용이다. 텍스트 소스와 실행용 산출물은 내용 종류가 다르다.

  • 함수는 입력을 받아 정해진 동작을 실행한다. Java의 메서드는 클래스 안에 선언하는 함수 역할의 구성이다.

  • 자가진단: int x=2의 x는 정수 값 2를 가진 변수이며 x+3의 계산 결과는 5이다.

학습 목표

  • Java 소스·컴파일러·class 파일·JVM의 역할을 연결한다.

  • bytecode를 특정 CPU의 기계어와 구분한다.

  • 실행기 구현 방식과 프로그램 의미의 차이를 설명한다.

소스를 고쳤는데 화면의 값이 그대로라면 무엇을 실행했는가?

앞 본문의 Hello는 x가 2인 소스를 번역한 뒤 5를 출력했다. 새 종이 모형에서는 S0가 그 소스의 식별자이며, S0에서 만든 class 묶음 C0를 별도 폴더 old에 보존한다. S1에서는 x를 7로 바꾸었지만 아직 번역하지 않았다. 클래스 실행 명령이 읽는 대상은 지정 경로의 산출물이지 편집기에 열린 소스가 아니다.

같은 프로그램 이름이 있어도 소스의 현재 상태, 번역한 입력, 실행한 산출물을 각각 연결해야 한다. S1에서 새 산출물 C1을 정상 생성해 new 폴더에 보관했다는 가정을 추가하면 C1의 예측은 10이다. 이것은 새 빌드·실행을 실제 수행한 기록이 아니라 버전별 입력과 결과를 추적하는 모형이다.

Java SE 11의 단일 소스 실행은 별도의 경로다. 기존 S1 파일을 런처에 전달하면 메모리 안에서 번역해 시작 클래스를 실행한다. 아래 비교에서는 그 모드의 응용 classpath를 해당 이름의 class가 없는 empty 폴더로 명시한다. 같은 이름의 기존 class가 응용 classpath에 있으면 이 모드는 오류 조건이므로 오래된 class 실행과 임의로 혼합하지 않는다.

사람이 읽는 소스와 번역 산출물

Java 소스는 .java 파일에 저장하는 텍스트이다. Java SE 11의 javac는 이 텍스트의 문법·이름·타입 조건을 확인하고 class 파일을 만든다. class 파일에는 JVM이 해석할 바이트코드뿐 아니라 클래스 이름·메서드·상수 등 실행에 필요한 구조 정보도 포함된다.

따라서 .class를 단순한 글자 파일이나 'CPU가 직접 실행하는 exe와 완전히 같은 것'으로 설명하면 틀리다. 또 하나의 소스 파일에서 중첩 클래스 등을 선언하면 class 산출물이 여럿 나올 수 있다. 이 첫 예제는 public 클래스 하나만 가진 소스로 단순화한다.

JVM은 규정된 실행 환경이다

JVM(Java Virtual Machine)은 class 형식과 명령 등의 실행 규칙을 정의한 가상머신이다. 실제 JVM 구현은 운영체제·CPU에 맞게 제공된다. Java 런처가 시작 클래스를 찾고 필요한 클래스를 로딩·연결·초기화한 뒤 이 버전의 진입 메서드를 호출한다.

JVM 구현은 바이트코드를 해석하거나 실행 중 기계어로 컴파일하는 JIT 같은 전략을 사용할 수 있다. 어떤 방식이든 언어와 VM의 실행 규칙을 지키는 범위에서 구현한다. 'Java는 전혀 컴파일하지 않는다'거나 'javac가 모든 실행을 끝낸다'는 두 주장 모두 컴파일 단계와 실행 단계를 혼동한다.

JDK와 표준 라이브러리의 관계

JDK는 Java 개발에 쓰는 도구와 런타임을 제공하는 개발 키트이다. javac는 번역 도구이고 java는 JVM을 시작하는 런처이며 System.out.println은 표준 라이브러리의 출력 기능을 사용하는 호출이다. 이 역할들은 서로 연결되지만 하나의 동일한 프로그램이 아니다.

이 단원은 Java SE 11의 전통적인 클래스 기반 진입 형식을 사용한다. 최신 버전의 간략화된 소스 문법이나 프리뷰 기능을 섞지 않는다. 설치는 종이 활동의 필수가 아니며 코드·바이트코드·실행 화살표를 따라가면서 기본 결과를 예측할 수 있다.

public class Hello {
    public static void main(String[] args) {
        int x = 2;
        System.out.println(x + 3);
    }
}

중간 과정을 따라가는 예제

위 코드를 Hello.java로 저장하고 javac로 번역한 뒤 Hello 클래스를 실행한다고 가정한다. 파일과 값의 흐름을 추적하라.

  1. Hello.java는 public 클래스 Hello의 선언과 main 몸통을 가진 소스이다.

  2. 이 작은 파일은 javac 성공 시 Hello.class를 만드는 것으로 예상한다.

  3. java 런처가 Hello를 시작 클래스로 지정하면 JVM이 main을 호출한다.

  4. x=2 후 x+3=5를 계산하고 println이 5와 환경의 줄 종료를 표시한다.

예상 출력은 한 줄 5이다. 번역 성공은 main의 덧셈이 실제로 실행됐다는 증거가 아니므로 실행 단계 기록을 따로 둔다.

조건을 바꾸어 비교하기

현재 소스와 실행 산출물의 연결이 끊긴다

S1의 x는 7이다. C0는 바뀌지 않았고 java -cp old Hello를 계획했다. 새 결과가 10일 것이라는 주장을 판단하라.

  1. old 안의 Hello.class는 S0에서 만든 C0다.

  2. C0가 가진 계산은 2 + 3이므로 예측 줄 내용은 5다.

S1의 계산을 검토한 사실은 C0가 새로 번역됐다는 근거가 아니다.

비교할 점

경로 오류가 없어도 잘못된 버전의 정상 실행을 선택할 수 있다.

소스 실행의 전제 하나가 달라진다

S1.java의 시작 클래스는 Hello다. 계획 A는 java -cp empty S1.java이며 empty에는 Hello.class가 없다. 계획 B는 java -cp old S1.java이고 old에는 C0의 Hello.class가 있다. 다른 의존성·문법 문제는 없다.

  1. A는 단일 소스 모드로 S1을 번역해 10을 예측한다.

  2. B에는 시작 클래스와 같은 이름의 class가 응용 classpath에 있어 이 모드의 오류 조건이다.

B를 오래된 5 또는 새 10의 정상 출력이라고 단정하지 않는다.

비교할 점

소스 모드는 클래스 실행 명령에 .java만 붙이는 무조건적 대체가 아니다.

종이와 본문으로 직접 해보기

종이에 Hello.java, javac, Hello.class, java/JVM, 출력5 카드를 놓고 처리 순서로 연결하라. println 호출을 제거하면 산출물과 화면 중 무엇이 달라지는지도 적어라.

힌트 보기

소스와 번역 산출물은 객체, 도구는 처리 단계이다.

풀이 보기

Hello.java→javac→Hello.class→java/JVM→5 순서이다. 출력 호출을 제거해도 유효한 프로그램은 class로 번역될 수 있지만 화면의 5 출력은 없어질 것이다.

오해와 반례

Java는 인터프리터 언어이므로 .class는 필요 없고 컴파일도 없다.

이 명시적 javac 경로는 소스를 class로 번역한 뒤 JVM에서 실행한다. Java 11의 소스 파일 직접 실행 모드도 내부 번역을 수행하는 별도 도구 모드이며 언어 전체가 단일 구현 전략만 갖는다고 분류할 수 없다.

연습 1 · 값과 상태 예측

C1을 생성한 후 S2에서 x를 9로 편집했다. C1은 그대로다. java -cp new Hello의 줄 내용과 S2를 올바르게 소스 실행한 경우의 줄 내용을 예측하라.

힌트 1

산출물의 입력 식별자는 S1이다.

힌트 2

각 입력의 x에 3을 더한다.

풀이와 답 확인

  1. C1은 x가 7인 S1에서 번역돼 줄 내용 10을 예측한다.

  2. S2의 정상 소스 실행은 9 + 3으로 12를 예측한다.

클래스 실행은 10, S2 소스 실행은 12다. 실제 실행한 값은 아니다.

편집기에서 9가 보이므로 두 실행 모두 12다.

편집은 선택한 class 파일을 자동 수정하지 않는다.

연습 2 · 오류 찾아 고치기

기록에 “S1을 확인했고 출력 5가 나왔으므로 S1의 덧셈이 틀렸다”만 적었다. 확인할 연결과 수정할 보고는?

힌트 1

명령·classpath·실행 산출물 식별자를 찾는다.

힌트 2

예측과 실제 관찰이라는 상태도 구별한다.

풀이와 답 확인

  1. S1 확인과 실제 선택한 class의 입력 버전이 같은지 조사한다.

  2. C0를 선택했다면 S0 산출물의 결과이며, 현재 종이 모형에서는 실행 미수행이라고 표시한다.

소스 식별자 → 번역 입력 → 산출물 → 실행 명령을 이어 기록한다.

흔한 오답에서 다시 생각하기

덧셈 상수를 바꾸면 어떤 산출물을 실행해도 새 결과가 된다.

원인을 확인하지 않고 소스를 바꾸면 잘못된 버전 선택이 계속 남는다.

S1을 검증하려는 빌드·실행 계획을 구성하라. old의 C0를 비교 자료로 보존하고 new의 산출물을 구분해야 한다.

힌트 1

입력과 출력 폴더를 이름 붙인다.

힌트 2

빌드 성공 확인 뒤 실행 단계를 연결한다.

풀이와 답 확인

  1. S1 입력, javac 제품·버전·명령과 new 출력 폴더를 기록하고 성공 여부를 확인하는 게이트를 둔다.

  2. 성공한 산출물의 식별자를 기록한 뒤 java의 버전·new classpath·Hello 이름·예측 10과 실제 관찰 칸을 나눈다.

현재 계획의 실제 관찰은 미수행이다. old의 C0를 새 산출물로 표시하지 않는다.

흔한 오답에서 다시 생각하기

new라는 폴더 이름만 붙이면 그 안 파일이 S1에서 만들어졌음이 증명된다.

이름은 추적 단서이며 입력과 생성 성공의 기록이 필요하다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

소단원 1.2

compile·run·classpath

컴파일은 성공했는데 실행기가 클래스를 찾지 못하면 무엇을 바꿔야 할까?

준비 개념과 학습 목표

준비 개념

  • 작업폴더는 상대경로의 기준 위치이다. .\src\Hello.java는 그 아래 src 폴더의 파일이다.

  • 클래스 이름 Hello와 파일 이름 Hello.class를 구분한다.

  • 진단: out\Hello.class가 있을 때 out 폴더가 탐색 기준이면 Hello를 찾을 수 있다.

학습 목표

  • javac 입력 경로와 java 실행 클래스 이름을 구분한다.

  • -d 산출물 위치와 -cp 검색 경로를 연결한다.

  • 소스 오류·클래스 탐색 오류·실행 오류를 단계별로 구분한다.

번역 경로와 실행 경로가 서로 다르면 어느 파일을 찾는가?

앞 본문은 -d out과 -cp out의 역할을 나누었다. 새 가상 작업폴더 P에는 src, build, lib가 있다. src의 school.Report는 helper.Tool을 사용하며 lib/helper/Tool.class가 그 의존성을 제공한다. 두 클래스의 패키지 이름은 각각 school과 helper다. 소스 파일 탐색과 모듈 기능은 제외하고 명시한 classpath의 class만 사용한다.

javac의 -d build는 생성 산출물의 위치다. 번역할 때 필요한 Tool의 경로를 자동으로 뜻하지 않는다. 번역 계획에 -cp lib를 주고 Report 소스를 읽으면 Report의 결과는 build/school/Report.class에 놓인다. 실행에는 Report와 Tool 모두 찾을 루트가 필요하므로 Windows의 명시적 경로 목록은 build;lib다. 문서의 명령은 토큰과 cwd가 명시된 종이 계획이며 실제 셸을 호출하지 않는다.

상대 경로를 썼다면 작업폴더도 입력 조건이다. P에서의 build는 P/build이고 P/src에서의 build는 P/src/build다. 파일이 존재한다는 관찰만으로 어느 상대 경로가 그 파일을 가리키는지 정해지지 않는다. 표의 탐색 실패는 교육용 파일 목록과 클래스 실행의 경로 조건을 따른 판단이며 특정 오류 문구를 강제하지 않는다.

먼저 확인할 개념
  • 출력 폴더와 classpath

    -d와 번역·실행 시 -cp를 각각 다른 선택으로 읽는다.

  • 한정 이름과 경로 루트

    school.Report와 helper.Tool을 각 루트의 패키지 경로로 찾는다.

compile은 파일을 받고 run은 클래스를 고른다

예제 작업폴더 아래 src\Hello.java와 출력 폴더 out을 둔다. javac -encoding UTF-8 --release 11 -d out src\Hello.java는 소스 파일을 읽어 Java SE 11 기준으로 번역하고 결과를 out에 둔다. out은 미리 만들어 두었다고 가정한다. 이때 아직 main은 실행하지 않는다.

다음 java -cp out Hello는 클래스 탐색 경로에 out을 지정하고 Hello 클래스를 실행한다. 이 클래스 실행 형식에서는 Hello.java나 Hello.class라는 파일명을 인자로 주지 않는다. Java 11의 java Hello.java는 별도의 단일 소스 파일 실행 모드이며 두 형식을 혼합하지 않는다.

classpath는 시작 클래스와 의존성을 찾는 기준이다

classpath는 사용자가 제공한 클래스를 찾는 디렉터리와 JAR 등의 목록이다. 단순 unnamed package의 Hello.class가 out 바로 아래에 있으면 -cp out으로 찾는다. 다음 소단원처럼 이름이 school.Hello이면 out\school\Hello.class를 찾도록 루트 out을 지정해야 한다.

명령에 -cp를 쓰면 CLASSPATH 환경변수의 값보다 그 명령의 지정값이 우선한다. 아무 지정도 없는 경우의 기본 경로는 환경 조건에 의존하므로 재현 예제는 -cp를 명시한다. Windows의 여러 경로 구분은 ;, Unix 계열은 :이며 첫 실습은 한 경로만 사용해 차이를 줄인다.

오류 단계에 따라 고칠 대상이 다르다

소스의 타입 오류는 javac 진단으로 확인한다. 번역된 파일이 있어도 -cp의 루트를 잘못 주거나 이름을 잘못 쓰면 java가 시작 클래스를 찾지 못한다. 정상 로딩 후 main이 실행되다가 발생한 예외는 또 다른 단계이다. 정확한 오류 메시지 문구는 구현·버전·언어 설정에 따라 달라질 수 있다.

예를 들어 out\Hello.class만 있는데 -cp wrong Hello를 쓰면 탐색 경로부터 확인한다. 이 문제를 고치려고 덧셈 식을 수정할 필요는 없다. 반대로 main 안의 잘못된 계산은 경로를 고쳐도 그대로 남는다. 빌드 명령과 실행 명령·위치를 분리해 기록하면 오류 원인을 좁힐 수 있다.

java -cp out Hello

중간 과정을 따라가는 예제

src\Hello.java는 앞 소단원의 코드이고 javac가 out\Hello.class를 생성했다고 가정한다. java -cp out Hello와 java -cp missing Hello를 비교하라. missing에는 해당 class가 없다.

  1. 첫 명령의 탐색 루트 out에서 Hello.class를 찾는다.

  2. main을 실행하면 예상값 5가 표시된다.

  3. 두 번째 명령은 missing 안에서 시작 클래스를 찾지 못한다.

  4. 두 번째 경우는 main 진입 전 실패이므로 덧셈이나 출력의 실행 결과 5가 없다.

올바른 경로의 예상 출력은 5. 잘못된 경로는 클래스 탐색 실패이며 출력 계산 단계까지 도달하지 않는다.

출력 위치만으로 의존성 경로를 해결하지 못한다

P에서 javac -d build src/school/Report.java만 계획했다. CLASSPATH는 설정하지 않았고 cwd 아래 helper/Tool.class도 없다. Tool은 P/lib/helper/Tool.class에만 있다.

  1. 번역의 기본 사용자 classpath는 현재 폴더라 lib 아래 Tool을 지정하지 않았다.

  2. -d build는 출력 위치이므로 의존성을 찾으려면 번역 경로 -cp lib를 추가한다.

가정한 입력은 Tool을 찾지 못한다. 폴더 build를 만드는 조치만으로 의존성이 생기지 않는다.

소단원 1.3

package와 entry point

class 파일은 있는데 school.Hello와 Hello를 왜 다른 이름으로 볼까?

준비 개념과 학습 목표

준비 개념

  • 이름 공간은 같은 짧은 이름을 조직하는 범위이다. 학교1의 교실과 학교2의 교실을 구분하는 전체 주소를 생각하라.

  • 메서드는 클래스 안의 동작이며 인자 배열은 여러 문자열을 순서대로 담는다.

  • 자가진단: 문자열 배열 길이가 2이면 유효한 인덱스는 0,1이다.

학습 목표

  • package 선언과 한정 클래스 이름의 관계를 설명한다.

  • Java SE 11 진입 메서드의 public·static·void·String[] 역할을 구분한다.

  • 런처 옵션과 main에 전달하는 인자를 따로 추적한다.

-cp라는 문자열도 프로그램 데이터가 될 수 있는가?

앞 본문은 클래스 이름 뒤 인자를 args로 받았다. 새 Report의 main은 args.length와 첫 문자열을 각각 출력하되, 길이가 0이면 첫 값 대신 NONE을 출력하는 계약이다. 일반 main(int x)도 따로 있다고 가정한다. 이름이 같아도 런처가 표준 진입점 대신 정수 인자 메서드를 골라 주지 않는다.

이 소단원은 셸이 토큰을 만든 뒤 java에 전달한 목록을 입력으로 삼는다. java, -cp, build;lib, school.Report, -cp, cache라는 여섯 토큰이라면 앞의 -cp는 런처 옵션이고 뒤의 -cp는 첫 프로그램 문자열이다. 특정 셸의 공백·인용을 검증하지 않고 이미 확정한 토큰을 추적하는 활동이다.

package school;의 선언과 클래스 이름 Report는 school.Report라는 이름을 만든다. 파일을 lab라는 폴더로 옮긴다는 편집만으로 lab.Report가 되지 않는다. 번역의 출력 경로와 이름을 확인한 뒤 main의 데이터 계약을 계산해야 탐색 실패와 실행한 데이터 결과를 혼동하지 않는다.

먼저 확인할 개념
  • main의 문자열 배열 계약

    Java SE 11 진입 형태와 길이 검사 뒤 첫 값을 읽는 조건을 사용한다.

  • 런처 옵션과 실행 대상

    클래스 이름 앞의 경로 옵션과 뒤의 프로그램 데이터를 나눈다.

package는 타입 이름의 일부가 된다

소스의 package school;은 Hello 클래스를 school 패키지에 속하게 한다. 이 클래스의 한정 이름은 school.Hello이다. 같은 Hello 짧은 이름도 다른 패키지에 있으면 다른 타입을 가리킬 수 있다. 파일이 우연히 school 폴더에 있다는 것만으로 package 선언이 생기는 것은 아니다.

javac -d out을 사용하면 패키지 이름에 대응하는 하위 경로 out\school\Hello.class를 만든다. 소스는 보통 src\school\Hello.java처럼 조직하지만 중요한 것은 선언·이름·빌드 설정의 일치이다. public 최상위 클래스 Hello의 소스 파일은 이 javac 예제에서 Hello.java 이름을 사용한다.

entry point는 실행기가 호출할 계약이다

이 Java SE 11 예제의 진입점은 public static void main(String[] args)이다. public은 런처가 접근할 수 있는 형태, static은 Hello 객체를 먼저 만들지 않고 클래스의 메서드를 호출하는 형태, void는 호출 결과값을 반환하지 않는 형태를 뜻한다. main이라는 이름과 문자열 배열 매개변수도 이 전통적 실행 계약의 일부이다.

모든 main이라는 메서드가 진입점이 되는 것은 아니다. 인자를 int로 바꾸거나 static을 제거하면 일반 메서드로는 번역될 수 있어도 이 실행 계약을 만족하지 못한다. 최신 Java의 별도 진입 형식을 이 버전의 규칙과 혼합해서 설명하지 않는다.

프로그램 인자는 클래스 이름 뒤에 온다

java -cp out school.Hello A B에서 -cp out은 런처 옵션이고 school.Hello는 시작 클래스이다. 뒤의 A,B가 main의 args에 문자열로 들어간다. args.length는 2이며 args[0]은 "A"이다. 파일 입력이나 표준 입력과 달리 실행 명령에서 미리 전달하는 값이다.

args.length가 0일 때 args[0]을 읽으면 배열 경계 밖 접근이다. 이 예제는 첫 값을 읽지 않고 길이만 출력하므로 인자가 없어도 계산을 설명할 수 있다. 클래스 이름 변경, package 변경, 배열 인자 사용을 분리해서 추적하면 이름 문제와 데이터 문제를 구분할 수 있다.

package school;
public class Hello {
    public static void main(String[] args) {
        System.out.println(args.length);
    }
}

조건을 바꾸어 비교하기

옵션처럼 보이는 문자열이 진입점 뒤에 있다

java -cp build;lib school.Report -cp cache라는 토큰 목록을 전달한다. Report는 정상 클래스이며 위 main 계약을 가진다. 두 출력 줄은?

  1. 시작 클래스까지가 런처의 선택이고 뒤 -cp와 cache는 main의 데이터다.

  2. args의 길이는 2이고 첫 값은 문자열 -cp다.

줄 내용은 2와 -cp다. 뒤 문자열은 classpath를 cache로 바꾸지 않는다.

비교할 점

동일 문자열의 역할은 위치와 파싱 계약으로 결정된다.

같은 이름의 일반 메서드는 런처 계약을 대체하지 못한다

후보 R에는 public static void main(int x)만 있고 후보 S에는 public static void main(String[] args)가 있다. 각 클래스는 정상 번역됐다고 가정한다. S에 한 토큰 7을 전달한다.

  1. R의 정수 main은 Java SE 11 전통적 진입 계약이 아니다. 번역 성공과 런처 진입 가능은 다르다.

  2. S의 인자는 정수 7이 아니라 문자열 7 하나이며 길이 1과 첫 값 7을 출력한다.

R은 지정 진입 계약을 만족하지 않고 S의 두 줄 내용은 1과 7이다.

비교할 점

데이터의 모양만으로 런처가 overload를 선택하거나 숫자로 파싱하지 않는다.

준비 개념

class의 버전 숫자만 맞으면 실행 전체가 증명되는가?

앞 본문은 Java SE 11 산출물의 major 값 55와 실행 환경 기록을 연결했다. 새 활동은 실제 파일을 열지 않고 가상 여덟 바이트 CA FE BA BE 00 00 00 37을 읽는다. 네 바이트 형식 표식 뒤 minor와 major가 각각 두 바이트이며 큰 쪽 바이트가 앞에 온다. 따라서 minor는 0, major는 16진수 37, 즉 십진수 55다.

표식과 버전은 형식 검사의 일부다. 여덟 바이트 뒤에 상수 풀·이름·메서드 등의 필수 구조가 없다면 전체 정상 class로 주장할 수 없다. 또한 main 산출물의 major가 55라는 사실은 외부 의존성·네이티브 기능·파일 권한·작업폴더까지 맞췄다는 뜻이 아니다. --release 11의 공개 API 번역 기준과 런타임 환경을 따로 기록한다.

출력 비교도 관찰 계약이 필요하다. 숫자 5와 줄바꿈을 출력하는 경우를 줄 내용 비교로 볼 수도 있고 정확 바이트 비교로 볼 수도 있다. 아래 모형은 인코딩을 ASCII 호환 UTF-8로 고정하고 줄바꿈을 LF 또는 CRLF로 가정한다. 논리적 한 줄이 같아도 바이트 수는 2와 3으로 다르며 실제 플랫폼의 바이트를 측정한 결과는 아니다.

호환성은 여러 조건을 가진다

Java 언어판은 어떤 구문·규칙을 사용할지 정하고 JDK 버전은 도구와 API의 집합을 제공한다. class 파일도 버전 필드를 가지므로 새 대상 버전으로 번역한 산출물을 더 오래된 JVM이 받아들이지 못할 수 있다. 이때 UnsupportedClassVersionError는 계산식 오류와 다른 호환성 단서이다.

--release 11은 해당 javac가 지원하는 Java SE 11 기준의 소스·class 대상 및 공개 API 집합으로 번역하는 선택이다. 이것만으로 별도 외부 라이브러리의 모든 버전이나 네이티브 연동, 운영체제 환경까지 검증하는 것은 아니다. 단순히 -target만 낮추는 것과 API 기준까지 맞추는 문제를 구분한다.

플랫폼 독립성에도 관찰 환경이 있다

호환 JVM과 필요한 라이브러리가 있으면 같은 class의 실행 의미를 여러 플랫폼에 가져갈 수 있다. 그러나 파일 경로·권한·기본 문자 인코딩·줄 종료·로케일·시간대·외부 서비스는 결과에 영향을 줄 수 있다. '언제 어디서나 아무 조건 없이 같은 화면과 바이트'라는 보장은 아니다.

소스가 UTF-8이면 javac -encoding UTF-8로 읽는 조건을 명시한다. 출력 println의 줄 종료는 환경에 맞춰 달라질 수 있으므로 첫 예제의 비교는 줄 내용 5와 2를 기준으로 한다. 플랫폼별 줄바꿈 바이트가 달라도 논리적 줄 내용이 같을 수 있다.

기록은 산출물과 실행 조건을 이어 준다

빌드 기록에는 소스 식별자, 파일 위치, 작업폴더, javac의 실제 제품·버전, 언어 기준, 문자 인코딩, 명령, 산출물 위치와 성공/진단을 적는다. 실행 기록에는 java 제품·버전, classpath, 시작 클래스, 인자, 실제 출력·오류·종료 상태를 적는다. java -version과 javac -version을 각각 확인해야 도구 불일치를 찾을 수 있다.

기록하지 않은 환경을 나중에 기억으로 채운 수치는 관측 증거가 아니다. 이 단원의 검증은 실제 가능한 간단한 예제와 경로 반례만 확인하며 모든 JVM·플랫폼·라이브러리의 호환성 검증으로 확대하지 않는다. 설치 없는 학습자는 같은 칸을 만들어 예측과 not_executed를 기록하면 된다.

다른 문제에 적용하기

새 후보를 선택하는 명령과 관찰 계약을 연결한다

가상 P의 S0 산출물 C0는 old/school/Report.class에 있고 프로그램은 인자 길이와 첫 값을 출력한다. S1 소스는 같은 계약으로 번역한 C1을 build/school/Report.class에 생성했다고 가정한다. C1은 helper.Tool도 사용하며 그 class는 lib/helper/Tool.class에만 있다. 번역·실행은 Java SE 11 기준이며 추가 의존성·입력 예외는 없다고 가정한다. 실제 명령 수행은 하지 않았다. (1) P에서 CLASSPATH=lib인 상태의 java -cp build school.Report -cp cache 토큰 목록이 Tool 경로를 갖는지 판단하고 필요한 경로를 고쳐 두 줄 내용을 예측하라. (2) 같은 명령을 P/src에서 계획할 때 경로 루트를 고쳐라. (3) C1의 가상 헤더 CA FE BA BE 00 00 00 37을 읽고 무엇이 아직 입증되지 않았는지 적어라. (4) 두 줄을 UTF-8 LF로 기록한다는 가상 계약의 전체 바이트 수와 CRLF 계약의 수를 비교하라. 입력 토큰은 이미 확정됐으며 셸의 실제 토큰화 실험을 요구하지 않는다.

힌트 1

명시 classpath가 환경변수를 대체한다. 클래스 이름 뒤 -cp는 프로그램의 첫 인자다. cwd 뒤에 상대 루트를 붙여 본다.

힌트 2

정상 경로 계획의 두 줄 내용은 길이와 첫 문자열이다. 두 줄 각각에 종료 바이트가 붙으며 헤더는 전체 class의 일부다.

풀이와 답 확인

  1. -cp build는 CLASSPATH=lib를 자동 합치지 않는다. P에서는 -cp build;lib로 두 루트를 지정한 뒤 school.Report를 선택한다.

  2. 프로그램 인자는 문자열 -cp와 cache 두 개다. 정상 실행의 예측 줄 내용은 2와 -cp이며 뒤 -cp는 런처 경로 옵션이 아니다.

  3. P/src에서는 -cp ../build;../lib로 P의 두 루트를 지정한다. C0의 old 폴더를 선택하지 않으며 C1 식별자를 빌드 입력 S1과 연결한다.

  4. 헤더는 표식 일치, minor 0, major 55다. 전체 class 유효성·의존성·환경·실제 실행은 헤더만으로 입증되지 않는다.

  5. UTF-8 LF 계약은 첫 줄의 숫자 2 한 바이트와 LF 한 바이트, 둘째 줄 -cp 세 바이트와 LF 한 바이트로 총 6바이트다. CRLF는 각 종료가 두 바이트라 총 8바이트다.

  6. 명령·cwd·산출물·예상 논리 줄·예상 바이트·실제 결과 칸을 분리하고 실제 빌드/실행/바이트 검증은 미수행으로 기록한다.

후보 C1과 두 의존성 루트를 선택한 계획의 줄 내용은 2와 -cp다. 헤더 major 55는 일부 버전 조건이며, 가상 LF/CRLF 바이트 수는 6/8이다. 실제 호환 실행 완료라는 주장은 하지 않는다.

해결한 뒤 점검할 것

  • P와 P/src에서 서로 같은 두 루트를 지정하며 명시 옵션의 환경변수 대체 관계를 설명한다.

  • 런처 경로 옵션과 인자 문자열 -cp를 구별하고 길이·첫 값을 이름 붙인다.

  • 소스 S1·선택 C1의 관계와 헤더 검사의 한계를 기록한다.

  • 두 줄의 내용 비교와 6/8바이트 계약을 구별하며 실제 미수행 상태를 유지한다.
