경로 글자를 정리하면 같은 파일을 가리킨다는 뜻일까?

앞 본문은 Path의 주소 표현과 실제 읽기를 구별했다. 새 예제는 UNIX 형태의 경로를 쓰는 자체 고정 파일시스템 모형이다. /work/link는 /other/sub를 가리키는 디렉터리 심볼릭 링크이며 /other/note와 /work/note는 서로 다른 기존 파일이다. 경로 /work/link/../note를 실제 링크와 부모 순서대로 해석하면 /other/note다. 반면 문자 구성 요소만 normalize하여 link/..를 제거하면 /work/note다. 문법상 간소화가 파일 정체성을 보존한다고 단정할 수 없다.

Path.startsWith는 문자열의 글자 접두어 검사가 아니라 경로 구성 요소 비교다. 같은 모형에서 /work/notes/a는 /work/notes 아래인 문자 경로지만 /work/notes-old/a는 그렇지 않다. 문자열 startsWith("/work/notes")는 둘을 혼동할 수 있다. 그러나 올바른 Path 비교도 그 사이 존재하는 링크나 검사 뒤 경로 교체를 해결하지 않으므로 보안 경계를 완성하는 단일 검사는 아니다. 실제 권한·경쟁 방지 코드를 구현한 것은 아니다.

내용 인코딩에서도 같은 표시와 같은 바이트는 다르다. 새 문자열 A😀와 LF는 코드 포인트 세 개지만 Java UTF-16 코드 단위는 1+2+1=4개, 표준 UTF-8은 1+4+1=6바이트다. 이 예제의 얼굴 문자는 U+1F600이며 바이트 F0 9F 98 80을 쓴다. 이를 UTF-8 두 조각 [41,F0,9F]와 [98,80,0A]로 전달하면 첫 조각 끝이 문자 중간이다. 매 조각을 독립 파일처럼 종료 처리하지 않고 남은 바이트를 보존하여 다음 조각과 이어 해석한다.

주소를 표현하는 Path

Path는 파일을 찾기 위한 주소 표현이다. 주소를 만들었다고 파일을 만들거나 내용을 읽은 것은 아니다. Files는 그 주소에 대해 읽기·쓰기 같은 동작을 제공한다. 상대 주소 data/notes.txt는 실행 환경의 기준 디렉터리에 영향을 받으므로 소스 파일이 있는 폴더와 같다고 단정하지 않는다.

Path.of("data", "notes.txt")처럼 구성 요소로 경로를 만들면 플랫폼의 구분자를 직접 이어 붙이는 부담을 줄인다. toAbsolutePath는 기본 파일시스템 디렉터리를 이용해 절대 주소를 얻지만 파일 존재 확인은 아니다. 실제로 열 때 발생하는 IOException을 처리하고, 문제가 생기면 기준 디렉터리와 실제 주소를 함께 확인한다.

바이트에 문자 의미를 붙이는 인코딩

문자열은 글자에 대한 표현이고 파일에는 바이트가 저장된다. 인코딩은 글자를 바이트로 바꾸는 규칙, 디코딩은 그 반대다. UTF-8에서 영어 A는 1바이트, 한글 가는 3바이트다. 글자 수를 그대로 파일 크기라고 생각하면 한글이나 이모지가 포함된 파일에서 틀린다.

Files.readString(path, StandardCharsets.UTF_8)는 명시한 UTF-8 규칙으로 읽는다. charset을 생략한 readString도 UTF-8이지만 명시하면 외부 파일과의 약속을 드러내기 쉽다. 잘못된 바이트가 들어 있으면 이 API는 IOException을 낼 수 있다. 깨진 글자를 무조건 지우는 대신 저장한 쪽의 인코딩부터 확인한다.

작은 파일과 큰 파일의 읽기 선택

readString은 전체 텍스트를 하나의 문자열로 얻어 작은 설정 파일에 편리하다. 거대한 로그에 같은 방법을 쓰면 전체 내용을 위한 메모리가 필요하다. newBufferedReader는 읽는 동안 바이트를 문자로 해석하며 필요한 부분부터 처리할 수 있다. 한 줄 처리만으로 충분한 파일인지, 줄 사이 상태가 필요한 형식인지도 구별한다.

이 소단원은 실제 파일을 만들지 않고 바이트 표를 계산한다. 확장 연습에서는 작업용 작은 파일과 명시한 인코딩부터 사용하고, 열린 Reader는 try-with-resources로 닫는다. 파일이 없는 경우와 글자 규칙이 맞지 않는 경우는 원인이 다르므로 같은 빈 문자열로 감추지 않는다.

풀이와 답 확인

레코드 읽기 실패가 버퍼를 원래대로 돌려줄까?

앞 본문의 readInt는 완전한 네 바이트 정수와 EOF를 구별했다. 새 장부는 readFully로 네 바이트 배열을 채우는 경우다. 시작 버퍼는 [9,9,9,9]이고 원본에는 [0,0,1]만 남아 있다. 일부가 버퍼로 옮겨진 뒤 EOFException이 날 수 있으므로 호출 실패를 버퍼 무변경으로 읽지 않는다. 세 바이트만 있는 입력에서 258 같은 정상 정수 값을 반환했다고 보고할 근거도 없다.

업무 상태를 보존하려면 읽기용 후보 저장소와 공개된 업무 값을 분리한다. 앞에서 공개한 값이 7이라면 새 후보 배열로 네 바이트를 모은 뒤 형식·범위를 검증한 경우에만 새 값으로 교체한다. 실패하면 공개 값은 7로 유지할 수 있지만 입력 스트림은 이미 일부 소비됐을 수 있다. 후보 공개 원자성과 스트림 되감기는 서로 다른 계약이다. 임의 IOException 뒤 입력 위치를 일반적으로 추정하지 않는다.

readUTF의 두 바이트 길이 접두부는 Java String.length()가 아니라 modified UTF-8 내용 바이트 수다. 새 문자열 A와 NUL은 UTF-16 두 단위이며 표준 UTF-8 바이트는 41 00이다. DataOutput 규약의 modified UTF-8에서는 NUL을 C0 80으로 표현하므로 내용은 41 C0 80 세 바이트이고 접두부는 00 03이다. 표준 UTF-8 자료에 접두부만 붙이는 방법은 송신 규약의 modified UTF-8 인코딩을 대신하지 않는다.

바이트를 모으는 버퍼

버퍼는 원 입력에서 여러 바이트를 받아 메모리에 잠시 보관하고 요청에 공급한다. 읽기 호출마다 외부 장치에 접근하는 부담을 줄일 수 있지만, 바이트 자체의 의미를 바꾸지 않는다. BufferedInputStream과 DataInputStream을 겹치면 버퍼링과 정수 해석을 각각 담당하게 할 수 있다.

감싼 뒤에는 원 입력 스트림을 따로 읽지 않는다. 버퍼가 미리 가져온 바이트와 원 스트림 위치가 어긋나면 자료를 건너뛴 것처럼 보일 수 있다. 읽은 바이트는 한 경로로 소비하고 끝나면 가장 바깥 자원을 닫아 생명주기를 관리한다.

바이트 순서가 정수의 자리값을 정한다

DataInput.readInt는 먼저 읽은 바이트를 높은 자리로 하는 4바이트 정수 규칙을 사용한다. 각 바이트를 0에서 255까지의 값으로 보면 a×2^24+b×2^16+c×2^8+d의 비트 배치다. 00 00 01 02는 0+0+256+2라서 258이다.

파일을 쓴 쪽이 little-endian이었다면 같은 네 바이트를 반대로 자리 배치해 33,619,968로 해석할 수 있다. readInt가 파일의 규칙을 알아서 추정하지 않는다. signed int의 범위와 상위 비트도 별도 약속이며 여기 예제는 양수 범위다. 텍스트 숫자 "258"과 이 이진 정수 표현은 전혀 다른 바이트다.

읽기 반환 개수와 레코드 완전성

배열로 읽을 때 요청한 길이는 최대량이며 실제 읽은 수를 반환한다. 반환 수가 3이면 앞의 세 바이트만 새 자료이고 나머지는 유효한 새 자료라고 사용할 수 없다. 입력 끝은 일반 byte read에서 -1로 표현된다. 짧게 읽었다고 곧바로 손상이라고 판단하지 말고 필요한 길이를 반복해서 채우는 절차가 필요하다.

반면 readInt는 네 바이트를 요구한다. 끝까지 세 바이트만 남아 있으면 EOFException이며 마지막 한 바이트를 0으로 보충한 값이 아니다. 정수 레코드 앞에 길이나 버전을 함께 정의하면 잘못된 파일을 진단하기 쉽다. DataInput.readUTF의 modified UTF-8는 일반 UTF-8 텍스트 파일 읽기와 같지 않다는 점도 기억한다.

앞 본문의 CSV 인용 규칙을 실제 경계 문제로 확장한다. 새 입력은 id,note라는 헤더 뒤에 7,"a와 CRLF와 b"를 하나의 인용 필드로 담고, 다음 기록은 8, 뒤에서 끝난다. 이 설명에서 CRLF는 문자 네 개가 아니라 실제 두 제어문자다. 파일의 물리적 줄 경계는 인용 필드 안에도 있으므로 readLine 한 번의 결과를 CSV 기록 하나라고 인증하지 않는다. 인용 상태를 유지한 형식 해석 뒤 첫 데이터 기록은 [7, a+CRLF+b], 둘째는 [8, 빈 문자열]이라는 두 필드를 갖는다. 빈 마지막 필드와 필드 부재도 다르다.

형식이 맞아도 업무 의미는 별도다. RFC 4180에서 공백은 필드 일부이므로 id 필드의 " 7"을 무조건 7로 바꾸는 규칙은 CSV 자체가 아니라 업무 정규화 정책이다. 새 계약에서는 id를 ASCII 숫자로만 구성한 문자열로 허용하고 선행 공백을 거절한다. 빈 note는 허용하지만 누락된 note는 거절한다. 형식 단계가 공백과 빈 필드를 먼저 지워 버리면 다음 검증 단계는 원본의 차이를 판정할 수 없다.

JSON에서도 표기와 논리적 이름을 구별한다. 자체 엄격 정책은 중복 객체 이름을 거절한다. {"a":1,"\u0061":2}의 두 이름은 이스케이프 해석 뒤 모두 a이므로 원시 토큰 글자만 비교하면 충돌을 놓친다. RFC 8259가 모든 구현에 같은 중복 처리 결과를 보장한 것은 아니다. 별도 외부 정수 ID 9007199254740993은 문법적으로 유효한 수지만 binary64만 쓰는 수신기가 모든 해당 정수를 정확히 보존한다는 보장은 없다. 이 과제에서는 정확 정수 표현 또는 숫자 문자열을 검증해 보존하고, 실제 라이브러리를 실행했다고 주장하지 않는다.

CSV는 쉼표만 자르는 형식이 아니다

CSV는 행과 필드로 표를 표현하지만 필드 안에도 쉼표가 들어갈 수 있다. RFC 4180은 널리 쓰이는 규칙을 설명하는 정보 제공 문서이며 구현마다 차이가 있으므로 실제 교환 규칙을 먼저 정한다. 이 수업은 UTF-8, 헤더 유무 명시, 같은 필드 수, 인용된 필드의 쉼표·줄바꿈을 처리하는 약속을 사용한다.

큰따옴표로 감싼 필드 안의 쉼표는 필드 경계가 아니다. 안에 큰따옴표 자체를 넣을 때는 두 번 써서 표현한다. 인용 안의 줄바꿈은 레코드를 바로 끝내지 않으므로 readLine 한 번이 CSV 레코드 한 개라고 단정하면 안 된다. split(",")만 사용한 방법은 이 규칙을 다루지 못한다.

JSON은 구조와 값의 종류를 함께 보낸다

JSON 객체는 문자열 이름에 값을 연결하고 배열은 순서대로 값을 담는다. 값에는 숫자·문자열·참과 거짓·null·객체·배열이 있다. {"id":7,"active":true}의 7은 숫자이고 true는 논리값이다. {"id":"7"}은 숫자 모양 문자열이며 수신 규칙 없이 같은 자료형이라고 합치지 않는다.

한 객체에서 이름을 반복하면 파서마다 마지막 값만 남기거나 오류를 낼 수 있으므로 중복을 피하고 수신 정책도 정한다. CSV의 7은 필드 텍스트라서 숫자로 바꾸는 검증이 추가로 필요하다. Java 프로그램에서는 선택한 CSV·JSON 파서의 의존성·버전·설정을 확인해야 하며 여기서는 설치 없이 규칙만 손으로 추적한다.

파싱 이후에도 뜻을 확인한다

파싱은 문법에 맞는 텍스트를 구조로 바꾸는 단계다. 문법에 맞는 {"age":-3}도 나이 규칙에는 맞지 않을 수 있다. 필요한 필드, 자료형, 범위를 업무 검증에서 따로 확인한다. 필드 누락과 명시적 null도 계약에 따라 의미가 다르므로 무조건 0으로 치환하지 않는다.

문자열을 코드로 실행해 JSON을 읽는 방법은 피하고 자료 전용 파서를 사용한다. UTF-8 교환과 인용 처리도 먼저 적용해야 이후 검증이 정확하다. 읽기 실패·문법 실패·업무 검증 실패를 구별해 어느 단계에서 고쳐야 할지 학습자가 알 수 있도록 기록한다.

앞 본문의 크기·버전·범위 검증을 한 묶음의 공개 계약으로 연결한다. 자체 입력은 형식 버전 2와 단위 points를 사용하고 값 목록 [40,70,−1]을 담는다. 각 값은 0 이상 100 이하이며 목록 전체가 통과해야 공개 총합을 교체한다. 이전 공개 총합은 9다. 앞 두 값을 즉시 더한 구현은 공개 값을 49,119로 바꾼 뒤 마지막 오류를 발견한다. 새 후보 방식은 내부 후보 합을 40,110으로 계산하지만 마지막 오류에서 후보를 폐기하여 공개 값 9를 유지한다. 이 비교는 직접 정한 원자 업무 공개 정책이며 파일 읽기나 네트워크 소비의 롤백 보장이 아니다.

형식 버전과 업무 데이터 수정 번호는 서로 다른 이름을 써야 한다. formatVersion=2는 points 필드를 요구하는 해석 규약이고 revision=8은 이미 공개된 업무 묶음의 수정 번호다. 새 입력의 formatVersion=2가 맞더라도 expectedRevision=7이면 현재 revision 8에 대한 수정 요구를 거절한다. 후보 검증 뒤 공개 시점에 수정 번호를 다시 비교하는 계약을 정한다. 실제 스레드·저장소를 구현한 것은 아니며 검사와 공개가 떨어진 구현을 이 종이 계약의 원자 단계라고 주장하지 않는다.

한도는 단위와 포함 구간을 정해야 한다. 새 규약은 수신 UTF-8 바이트 전체를 최대 12바이트, 해석된 중첩 깊이는 최상위 객체를 1로 세어 최대 2로 제한한다. 읽기 조각 길이 7과 6은 각각 작아도 전체 13바이트로 한도를 넘는다. {"a":{"b":0}}의 두 객체 깊이는 2이고 {"a":{"b":{"c":0}}}은 3이다. 크기 검사는 내용의 허용 범위와 별도며 이 짧은 한도는 교육용 정책이다. 깊이 계산도 실제 라이브러리의 내장 정의라고 일반화하지 않는다.

읽기 전에 허용량을 정한다

외부 데이터는 보내는 쪽과 받는 쪽의 가정이 다를 수 있다. 예를 들어 학습용 점수 파일의 허용량을 1,000바이트, 최대 중첩 깊이를 5로 정할 수 있다. 이 숫자는 JSON 표준의 고정 제한이 아니라 우리 프로그램의 정책이다. 크기만 작아도 과도한 중첩이나 잘못된 타입이 있을 수 있다.

자료를 전부 메모리에 올린 뒤에야 크기를 재면 할당 부담이 이미 발생한다. 스트림에서 읽은 바이트 수를 누적해 한도를 넘으면 중단하는 정책을 생각해 보자. 파일 크기 사전 조회만으로도 충분하다고 단정하지 않는다. 조회 이후 변경될 수 있으므로 실제 읽기에도 한도와 오류 처리가 필요하다.

version은 파일 구조의 약속이다

프로그램 출시 번호와 데이터 형식 version은 역할이 다르다. 프로그램이 여러 과거 형식을 읽을 수 있으며 기능을 고쳤어도 저장 구조는 그대로일 수 있다. 여기에서는 version 1은 score 정수 0–100을 points 단위로 저장하고, version 2는 같은 score와 unit:"points"를 명시한다고 약속한다.

version 1을 읽을 때 내부 구조에 unit을 points로 채우는 변환은 옛 약속에 근거한다. version 2에서 unit이 없으면 필수 필드 누락으로 거절한다. 알지 못하는 version 3을 최신 형식처럼 추측하지 않는다. 원본을 보존하고 지원하지 않는 형식이라는 메시지를 낸다. 값의 의미가 바뀌는 변환은 이름 추가보다 더 신중해야 한다.

우리 수업의 정책은 정의하지 않은 필드를 거절하는 것이다. 실제 서비스는 선택 필드를 무시하도록 정할 수도 있지만 그 선택을 문서화하고 재저장 때 자료를 잃을 가능성까지 고려해야 한다. 변환에 실패하면 원본을 덮어쓰지 않는다. 이 소단원은 문자 데이터의 직렬화 약속을 다루며 Java 객체의 임의 역직렬화를 실행하는 실습은 하지 않는다.

UNIX 링크 모형 /work/link→/other/sub에서 원래 /work/link/../note와 normalize 결과의 대상 파일을 비교하라. 다음 기록은 modified UTF-8 문자열 A와 NUL이며 두 바이트 내용 길이 접두부를 정확히 적어라. 별도 CSV 입력 8,와 8을 두 필드 계약으로 검사하고 JSON 객체의 이름 a와 \u0061을 엄격 중복 거절 정책으로 검사하라. 마지막 묶음은 formatVersion=2, unit=points, expectedRevision=8이며 현재 revision=8과 공개 총합 9에서 시작한다. 값은 [40,70,−1]이다. 즉시 누적 방식과 전체 후보 교체 방식의 공개 결과를 비교하라. 별도 같은 형식의 유효 목록 [40,70]은 교체 성공 뒤 revision을 9로 증가시키며, 이어 expectedRevision=8인 재처리를 거절한다. 모든 계산은 손모형이고 파일·Java·수신·학생 실행을 하지 않는다.

힌트 1

경로 이름 정리/실제 링크 해석, 문자열 내용 바이트/전체 레코드 길이를 각각 분리한다.

힌트 2

빈 필드와 부재, 해석된 이름 충돌, 후보 값과 공개 값, 형식 버전과 수정 번호를 각각 따로 장부에 적는다.

풀이와 답 확인

  1. 원래 경로는 링크를 따라 /other/sub의 부모 /other에서 note를 찾는다. 대상은 /other/note다. normalize 결과 /work/note는 다른 지정 파일이다.

  2. A와 NUL의 modified UTF-8 내용은 41 C0 80의 3바이트이므로 접두부는 00 03이고 전체는 5바이트다.

  3. CSV 8,는 빈 note가 존재해 허용되지만 8은 note가 없어 거절한다. JSON 두 이름은 모두 a로 해석되어 자체 중복 정책에서 거절한다.

  4. 잘못된 즉시 누적은 공개 값을 9→49→119로 바꾼 뒤 마지막 오류를 발견한다. 후보 교체는 내부 합 40→110 뒤 오류에서 폐기하므로 공개 총합 9와 revision 8을 유지한다.

  5. 독립 유효 목록 [40,70]의 전체 교체는 공개 총합 110과 revision 9를 함께 만든다. 이후 예상 수정 번호 8의 재처리는 현재 9와 불일치해 상태 110/9를 보존한다. 실제 저장소 원자 구현이나 스트림 되감기를 검증한 결과는 아니다.

두 경로 대상은 /other/note와 /work/note다. modified UTF-8 접두부는 00 03이고 전체는 5바이트다. CSV의 빈 note는 허용하지만 부재는 거절하며 JSON 이름은 논리적으로 중복이다. 실패 묶음의 즉시 방식은 공개 총합 119를 남기지만 후보 방식은 총합 9와 revision 8을 유지한다. 독립 유효 교체는 총합 110과 revision 9를 만들고 낡은 재처리는 이를 유지한다.
