소단원 13.1

페이지와 B+트리의 역할

책의 목차를 찾는 일과 실제 내용이 있는 쪽을 읽는 일은 같은가?

준비 개념과 학습 목표

준비 개념

  • 행과 열

  • 정렬된 키

  • 바이트와 페이지

학습 목표

  • 저장 페이지와 논리 행을 구별한다.

  • B+트리 내부와 잎의 역할을 설명한다.

  • 자체 페이지/트리 표에서 검색 경로를 추적한다.

필요한 열이 모두 색인에 있어도 heap을 읽을 수 있을까?

PostgreSQL B-tree에 검색 키 x와 INCLUDE 값 y가 있고 질의는 x 조건으로 y만 요구한다고 하자. 필요한 값이 색인에 있어도 현재 스냅샷에서 행이 보이는지 확인해야 한다. 관련 heap 페이지의 all-visible 비트가 없으면 가시성을 확인하기 위해 heap을 방문한다. 값의 충족과 가시성의 충족은 다른 조건이다.

가상 후보 8개 중 6개는 all-visible 페이지, 2개는 그렇지 않은 페이지에 있다고 하자. 후보마다 가시성 확인을 생각하면 2개는 heap 확인이 필요할 수 있다. 이것을 서로 다른 물리 디스크 읽기 2회라고 바꾸면 안 된다. 두 후보가 같은 페이지에 있거나 페이지가 버퍼에 있을 수 있다.

INCLUDE는 검색 키와 역할이 다르다. UNIQUE(x) INCLUDE(y)는 x의 유일성을 검사하며 (x,y) 쌍의 유일성을 검사하는 정의가 아니다. 넓은 y를 넣으면 색인 공간과 유지 비용도 바뀐다. 이 활동은 색인을 만들지 않고 조건표로 검토한다.

  • MVCC의 가시성

한 행과 한 페이지는 다르다

데이터베이스는 여러 행을 페이지라는 저장 단위에 묶어 관리할 수 있다. 페이지에는 행 내용 외에도 헤더·행 위치 표시·빈 공간 등이 들어간다. 따라서 페이지 크기를 순수 열 데이터 길이로 나눈 값이 실제 수용 행 수와 항상 같지는 않다.

PostgreSQL의 일반적인 heap 페이지는 헤더와 항목 위치 정보, 빈 공간, 항목 내용을 갖는다. 표준적인 빌드의 페이지 크기가 보통 8 kB라고 해서 모든 DB 엔진이나 모든 설정이 같다고 일반화하지 않는다. 아래 256바이트 페이지는 실제 PostgreSQL 페이지가 아닌 자체 산술 모형이다.

내부는 길 안내, 잎은 항목 찾기

B+트리의 내부 노드는 구분 키와 자식 연결로 검색 방향을 안내한다. 실제 색인 항목은 잎에서 확인한다. 내부에 같은 숫자가 나타났다고 해당 행을 찾았다고 끝내지 않는다. 전형적인 균형 모형에서는 모든 잎이 같은 깊이에 있다.

잎의 값이 행 위치일 수도 있고 행 데이터 자체일 수도 있어 저장 방식에 따라 후속 읽기가 달라진다. 이 단원은 잎에 행 위치를 둔 모형으로 한정한다. 잎을 순서대로 연결하면 시작 키를 찾고 범위 항목을 이어 읽을 수 있다. 논리적인 색인 키 순서가 heap 행의 물리 저장 순서를 자동으로 바꾸는 것은 아니다.

공간과 변경에도 비용이 있다

색인은 검색을 돕는 별도 구조라 공간을 사용하고 삽입·삭제·키 변경 시 유지가 필요하다. 페이지가 가득 찬 뒤 새 항목이 들어오면 분할 등이 발생할 수 있다. 색인을 여러 개 만들면 모든 질의가 무조건 빨라진다는 결론은 성립하지 않는다.

루트부터 잎까지 내려가는 페이지 수와 실제 디스크 읽기 횟수도 다를 수 있다. 버퍼에 이미 페이지가 있으면 논리 접근을 해도 디스크 읽기가 추가되지 않을 수 있다. 아래는 모두 캐시가 비어 있고 각 접근을 한 번의 모형 읽기로 세는 제한된 가정이다.

중간 과정을 따라가는 예제

자체 페이지는 256 B, 헤더는 16 B, 행 내용은 36 B, 각 행 위치 표시는 4 B이며 추가 정렬/여유는 없다고 가정한다. 별도 B+트리 루트 R의 구분 키는 20이다. 키<20은 잎 L=[5,12], 키≥20은 잎 M=[20,25,31]로 간다. 잎 값은 행 위치이고 키 25의 행은 heap 페이지 H7에 있다. 수용 행 수와 키 25의 읽기 경로를 구하자.

  1. 사용 공간은 256−16=240 B이고 행 하나마다 36+4=40 B다. 최대 floor(240/40)=6행이다.

  2. 25≥20이므로 R에서 M으로 간다. M에서 25의 항목과 행 위치를 확인한다.

  3. 색인 페이지는 R/M 두 개다. 실제 행 내용까지 요구하면 H7을 추가해 세 페이지를 읽는 모형이다. 내부 구분 키만으로 행 내용을 얻지 않는다.

자체 수용량은 6행, 색인 경로는 R→M, 내용 읽기까지 R→M→H7의 3페이지다. 실제 엔진 계측은 아니다.

조건을 바꾸어 비교하기

후보 확인과 물리 읽기를 나눈다

후보 8개 중 6개는 all-visible 페이지, 2개는 그렇지 않은 페이지에 있다. 2개가 같은 heap 페이지에 있으며 그 페이지는 버퍼에 있다고 가정한다.

  1. 2개 후보는 heap 가시성 확인이 필요하다.

  2. 같은 페이지의 접근과 버퍼 상태를 따로 본다.

가시성 확인 필요 후보 2개라는 사실로 물리 디스크 읽기 2회를 결론 내리지 않는다.

비교할 점

후보·heap 페이지·디스크 읽기는 다른 단위다.

INCLUDE가 유일 키를 늘리지 않는다

UNIQUE(x) INCLUDE(y)에 (x=1,y=A)와 (x=1,y=B)를 넣을 수 있는가?

  1. 유일성의 검색 키는 x다.

  2. 두 행의 x가 모두 1이다.

둘째는 x 유일 조건과 충돌한다. (x,y) 쌍이 다르다는 점으로 허용되지 않는다.

비교할 점

종이와 본문으로 직접 해보기

키 12의 행이 H2에 있다면 내용 조회 경로는? 범위 12≤key≤25를 찾는 모형에서 L→M 잎 연결을 사용해 반환 키를 적자. 헤더가 24 B로 늘어도 같은 6행을 넣을 수 있는가?

힌트 보기

키 12는 왼쪽이며 범위는 두 잎을 걸친다. 6행 공간과 남은 공간을 비교한다.

풀이 보기

내용 경로는 R→L→H2다. 범위의 반환 키는 12/20/25이며 31은 상한 밖이다. 헤더 24 B면 남은 232 B라 6행의 240 B를 넣을 수 없고 최대 5행이다.

오해와 반례

색인에 키가 있으니 heap을 읽을 필요가 없고 모든 행은 키 순서로 저장된다.

본문 모형의 잎 값은 행 위치라 필요한 내용은 heap에서 읽는다. 물리 배치와 색인 순서는 별도다. 다른 저장/covering 방식은 그 조건을 따로 확인한다.

복합 키의 뒤 열 조건은 항상 하나의 작은 연속 구간일까?

(a,b) 사전식 순서의 자체 키 목록을 (1,1),(1,3),(1,8),(2,1),(2,3),(2,8)로 두자. a=1 AND b≥3은 첫 a 묶음의 연속 구간 두 항목이다. b=3만 묻는 결과는 두 a 묶음에 흩어진다. 논리 결과가 두 개라는 사실과 하나의 짧은 연속 탐색 구간이라는 사실은 다르다.

PostgreSQL 18에서는 선두 열 조건이 없어도 복합 B-tree를 사용할 수 있고 유리하면 skip scan으로 선두 값별 반복 탐색을 할 수 있다. 따라서 선두 열 없으면 색인 사용이 절대 불가능하다는 규칙은 틀리다. 선두 서로 다른 값의 수와 분포·비용에 따라 계획 선택이 달라진다.

자체 비용 모형은 시작 탐색은 1U, 검사 항목당 비용은 1U다. 전부 한 번 훑으면 1+6=7U, a=1과 a=2 각각에서 b=3을 찾는 가상 두 탐색은 2×1+2×1=4U다. 실제 PostgreSQL 비용식이나 skip scan 실행시간이 아니다. 키 수와 중복 분포가 바뀌면 모형 결론도 다시 계산한다.

사용할 수 있는 색인인가

색인 구조는 지원하는 연산이 다르다. PostgreSQL B-tree는 정렬 가능한 자료의 동등/범위 조건에 사용할 수 있고 hash 색인은 단순 동등 비교를 다룬다. 조건과 연산자/키/자료형이 색인 계약에 맞는지 먼저 확인한다.

지원할 수 있다는 뜻은 계획기가 반드시 그 색인을 고른다는 뜻이 아니다. 읽을 행의 양·페이지 배치·비용 설정·통계·정렬 요구 등이 선택에 영향을 준다. SQL 결과의 논리적 의미와 결과를 얻는 접근 경로를 나누어 생각한다.

행 개수 대신 페이지 접근을 세어 본다

색인에서 행 위치를 찾았어도 heap 페이지를 읽을 수 있다. 같은 페이지의 여러 행을 묶어 읽으면 행 개수만큼 서로 다른 페이지를 읽는 것과 비용이 다르다. 무작위 위치와 연속 페이지의 접근 비용을 같은 상수로 두는 것도 특정 모형의 가정이다.

본문 비용 단위 U는 가상의 상대 단위이며 실제 시간이나 PostgreSQL의 기본 비용값이 아니다. 모두 캐시가 비었다고 하고 서로 다른 heap 페이지마다 비용을 한 번만 센다. 실제 계획기에는 CPU 검사·가시성·캐시·bitmap 처리 등의 항목이 추가되어 이 식을 그대로 사용하지 않을 수 있다.

많이 고르면 순차 스캔도 합리적이다

색인이 적은 후보만 찾아 주면 적은 페이지로 답을 얻을 수 있다. 대부분의 행이 조건을 만족하거나 여러 페이지에 퍼져 있으면 색인 탐색 뒤 비싼 heap 접근을 많이 해야 한다. 전체를 차례로 읽고 필터하는 쪽이 유리한 반례가 생긴다.

통과 행 수를 전체 행 수로 나눈 선택도와 heap 페이지 분포는 다른 정보다. 같은 수의 행이 한 페이지에 모였는지 여러 페이지에 흩어졌는지에 따라 비용이 달라진다. 읽기 개선과 색인 유지의 쓰기 비용도 따로 보고한다. 이 예제는 읽기 선택만 비교한다.

중간 과정을 따라가는 예제

자체 테이블은 heap 100페이지다. 전체 순차 스캔은 페이지당 1 U로 100 U다. 색인 시작 경로 비용은 고정 3 U이고 이후 서로 다른 heap 페이지 하나당 4 U다. A 질의는 2페이지, B 질의는 30페이지의 행을 요구한다. 추가 CPU/색인 범위 비용은 0이라고 단순화했다. 어느 경로가 비용상 낮은가?

  1. 색인 모형 비용은 3+4k U다. A는 k=2라 11 U로 100 U보다 작다.

  2. B는 k=30이라 123 U로 100 U보다 크다. 이 모형에서는 순차 스캔이 낮다.

  3. 색인 비용이 순차와 같거나 작으려면 3+4k≤100, 즉 k≤24.25다. 정수 페이지 수에서는 24까지이며 k=25면 103 U다.

가상 A는 색인 11 U, B는 순차 100 U를 고른다. 경계 k=24/25는 99/103 U다. 실제 DB 계획이나 실행시간 결과가 아니다.

평균을 반복 수로 곱해도 모든 관찰 항목을 같은 방식으로 더할까?

자체 계획표의 반복 노드가 평균 출력 3행, 평균 필터 제거 2행, loops=4라고 하자. 이 모형에서 출력은 12행, 필터에서 제거한 후보는 8행이다. 두 항목을 합하면 해당 노드가 그 필터에서 고려한 후보 20개를 설명할 수 있지만 전체 테이블 행 20개라고 일반화하지 않는다.

PostgreSQL 18의 Index Searches는 노드의 전체 loops에 걸친 탐색 횟수로 표시된다. 평균 actual rows와 달리 그 횟수를 loops로 다시 곱하면 중복 계산이다. 모든 숫자의 집계 단위를 먼저 읽어야 한다. 여기의 숫자는 실제 EXPLAIN에서 얻은 값이 아닌 자체 계획표다.

통계 객체를 만드는 것과 데이터를 수집하는 것도 다르다. CREATE STATISTICS는 관심 열을 정의하고 실제 수집은 ANALYZE가 한다. dependencies 통계가 있어도 충돌하는 상수 조합의 결과 0이나 모든 범위 조건을 자동 정확히 추정하지 못한다. 표본 통계와 업무 제약의 증명을 구별한다.

실행 전 계획과 실행 후 관찰

PostgreSQL의 일반 EXPLAIN은 계획과 추정값을 보여 준다. EXPLAIN ANALYZE는 질의를 실제 실행하고 노드별 관찰을 덧붙인다. 따라서 데이터를 바꾸는 질의에 ANALYZE 옵션을 붙이면 변경도 실제 일어난다. 본문 활동은 종이 표를 읽으며 어느 SQL도 실행하지 않는다.

계획의 cost는 상대 비용 단위이고 actual time은 밀리초다. rows 추정은 해당 노드가 출력할 행 수이며 검사한 모든 행 수와 같지 않을 수 있다. 필터나 상위 노드의 제한도 확인한다. 추정 표에 actual 열이 없는 경우 실제 실행값을 만들어 넣지 않는다.

반복 노드와 포함 비용

상위 계획 노드의 비용은 하위 비용을 포함한다. 트리의 모든 cost를 더하면 같은 일을 중복해서 세는 오류가 생길 수 있다. 노드 단위와 전체 질의 단위를 먼저 구별한다.

반복 실행 노드의 actual rows와 actual time은 실행 한 번당 평균으로 표시되며 loops는 반복 수다. 노드 전체 관찰 합을 보려면 평균에 반복 수를 곱한다. 하지만 포함 관계가 있는 부모/자식 시간 합을 전체 시간으로 무조건 더하지 않는다. 서버 관찰 시간과 클라이언트 변환/전송까지의 전체 시간도 다를 수 있다.

통계는 데이터 전체의 영구 진실이 아니다

계획기는 테이블 크기와 값 분포 등의 통계를 사용해 결과 행 수와 비용을 추정한다. PostgreSQL 통계는 변경 뒤 오래될 수 있고 ANALYZE로 갱신해도 표본 기반 근사다. 실제 값이 특정 구간에 몰리거나 조건들이 연관되어 있으면 단순 독립 가정이 부정확할 수 있다.

추정/관찰 차이를 찾았으면 데이터 분포·통계 시점·질의 조건·측정 환경을 함께 살핀다. 통계 갱신이나 색인 추가가 반드시 모든 오차를 없앤다고 단정하지 않는다. 전후 계획과 같은 결과 계약의 관찰을 비교하며 실제 실행하지 않은 대안은 계획/가정으로 남긴다.

중간 과정을 따라가는 예제

자체 가상 표의 반복 노드 P는 추정 rows=2, 관찰 actual rows=5, loops=4, 한 번당 평균 actual time 총값 0.3 ms다. 상위 노드 계획 cost 총값은 80 U이며 하위 P cost는 30 U라고 가정한다. P의 전체 출력/노드 시간과 잘못된 비용 합을 구별하자.

  1. P 관찰 총 출력은 5×4=20행이다. 같은 네 번을 기준으로 추정 출력 2×4=8행과 비교하면 실제/추정은 20/8=2.5배다.

  2. P에서 소비한 총 관찰 시간은 0.3×4=1.2 ms다. 이 값은 전체 질의나 네트워크 왕복 시간이 아니다.

  3. 상위 cost 80은 하위 30을 포함하므로 80+30=110 U를 전체 계획 비용이라고 하지 않는다. cost 80 U를 80 ms로 바꾸지도 않는다.

자체 가상 P의 총 출력 20행, 노드 시간 1.2 ms, 추정 대비 2.5배다. 전체 cost는 주어진 상위 80 U다. 실제 EXPLAIN 실행 결과가 아니다.

다른 문제에 적용하기

포함·탐색·관찰 단위를 분리하여 읽기

UNIQUE(x) INCLUDE(y)의 유일 조건과 Index Only Scan의 가시성 확인을 설명하라. 여섯 사전식 키에서 b=3 결과와 전체 7U/반복 4U 모형을 대조하라. 반복당 평균 출력 3행·제거 2행·loops=4·전체 Index Searches=5의 합계를 구하고 통계 정의와 수집을 나눠라.

힌트 1

값 포함·가시성·유일 키는 서로 다르다.

힌트 2

각 계획 항목의 평균 또는 전체 단위를 확인한다.

풀이와 답 확인

  1. 유일성은 x에 적용하고 all-visible이 아니면 필요한 값이 색인에 있어도 heap 가시성 확인이 필요하다.

  2. b=3의 결과는 (1,3),(2,3)이다. 지정한 전체 스캔은 시작 1U+검사 6U=7U이고 두 묶음의 반복 탐색은 시작 2U+후보 검사 2U=4U다. 이 비용은 가상 모형이며 서버 계측이 아니다.

  3. 반복당 평균 출력 3행에 4회 반복을 곱하면 출력 12행이다. 필터 제거도 2×4=8행이므로 해당 필터의 후보 합은 20개다. Index Searches는 이미 전체 반복의 합계 5회이므로 다시 loops로 곱하지 않는다.

  4. CREATE STATISTICS 정의와 ANALYZE 수집을 구별하며 통계를 제약·정확한 영구 진실로 쓰지 않는다.

색인 지원·실제 선택·가시성·집계 단위·통계 수집을 따로 확인한다. 실제 PostgreSQL 계획·성능·학습자 실험은 수행하지 않았다.

해결한 뒤 점검할 것

  • INCLUDE와 유일 키를 나눈다.

  • 가시성 확인과 물리 디스크 읽기를 구별한다.

  • 선두 조건 없는 색인을 절대 불가능이라고 쓰지 않는다.

  • 평균과 전체 횟수를 구별하고 실측을 만들지 않는다.
