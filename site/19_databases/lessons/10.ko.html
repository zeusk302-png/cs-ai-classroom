소단원 10.1

파라미터 질의

이름에 따옴표가 들어 있어도 검색 조건이 데이터로 유지되게 하려면?

준비 개념과 학습 목표

준비 개념

  • SELECT와 WHERE

  • 문자열과 튜플

  • 열과 행

학습 목표

  • 질의 구조와 값을 분리한다.

  • placeholder 개수와 인자 순서를 맞춘다.

  • 값 바인딩과 식별자 선택을 구별한다.

값으로 바인딩한 %도 언제나 보통 문자로 비교될까?

이름 A%, AB, O'Neil이 각각 ID 1, 2, 3에 저장되어 있다고 하자. name=?에 A%를 바인딩하면 정확한 이름 A%인 ID 1만 선택한다. name LIKE ?에 같은 값을 바인딩하면 패턴 A%가 되어 ID 1과 2를 선택한다. 바인딩은 SQL 구조와 입력 값을 분리하지만 LIKE 연산자가 그 값에 적용하는 패턴 의미까지 지우지는 않는다.

문자열의 따옴표와 패턴의 특수 문자는 역할이 다르다. O'Neil을 등호 조건에 바인딩하면 하나의 이름 데이터로 처리한다. %를 글자 그대로 찾고 싶다면 등호 비교가 맞는지 먼저 판단하고, LIKE가 필요한 질문이면 정한 ESCAPE 문자와 패턴 치환을 별도로 설계한다.

qmark의 인자 개수 검사와 named의 키 검사는 같은 정책이 아니다. sqlite3의 두 ?에는 두 값이 정확히 필요하지만 named 사전에는 필요한 키가 모두 있어야 하며 추가 키는 무시한다. 따라서 추가 키가 있다는 사실만으로 원하는 조건이 자동 추가되지는 않는다. 순서가 틀렸지만 개수는 맞는 인자는 오류 없이 엉뚱한 조건을 만들 수 있다.

  • 파라미터의 역할

    자리표시자가 값과 구조를 분리하는 범위를 확인한다.

질의의 문장과 빈칸의 값

파라미터 질의는 SQL 구조를 먼저 정하고 바뀌는 값은 별도 인자로 전달한다. sqlite3에서는 SELECT ... WHERE name = ?와 값 시퀀스를 execute에 각각 넘긴다. 사용자 입력을 문자열 더하기나 포매팅으로 SQL 문장에 끼워 넣는 방식과 구별한다.

이름 O'Neil처럼 따옴표가 들어간 문자열도 값으로 전달하면 문자열 데이터의 일부로 취급된다. 바인딩은 그 값을 SQL 연산자나 문장 구조로 재해석하도록 허용하는 방식이 아니다. 그렇다고 권한 검사, 업무 규칙 검증, 모든 동적 SQL의 안전성이 자동 해결되는 것은 아니다.

위치와 이름을 정확히 맞춘다

sqlite3의 ? 스타일은 placeholder 수와 같은 길이의 시퀀스가 필요하다. 두 빈칸이면 두 값을 순서대로 넘긴다. 한 값 튜플은 (value,)처럼 쉼표가 필요하며 (value)는 단지 괄호로 감싼 값이다. named 스타일은 :name 같은 자리와 해당 키가 있는 사전을 사용한다.

드라이버마다 표기법은 다르다. Psycopg의 %s는 Python 문자열 포매팅을 직접 적용하라는 뜻이 아니라 execute가 처리하는 자리표시자다. placeholder를 따옴표로 감싸면 안 된다. 본문은 sqlite3의 ?를 예시로 사용하고 다른 드라이버의 표기를 섞지 않는다.

테이블 이름은 값 칸이 아니다

파라미터는 질의의 값에 적용한다. SELECT * FROM ?의 ?에 테이블 이름을 넣는 방식으로 구조를 바꿀 수 없다. 선택 가능한 테이블이나 정렬 열은 사전에 허용한 목록에서 고르거나 해당 드라이버의 안전한 식별자 합성 기능을 사용한다.

값 조건을 올바르게 바인딩했어도 다른 부분을 사용자 문자열로 이어 붙이면 위험이 남는다. LIMIT 같은 값, 정렬 방향 같은 구문, 열 이름 같은 식별자의 역할을 따로 구별해야 한다. 안전성은 빈칸 하나뿐 아니라 전체 질의 구성과 권한까지 검토한다.

따옴표도 이름 데이터

이 세 입력과 질의는 Python 3.12.7·SQLite 3.45.3 메모리 DB에서 실제 확인했다. 다른 DB나 모든 문자열의 비교·대소문자 정책을 검증한 것은 아니다.

중간 과정을 따라가는 예제

자체 표 students(id,name,score)의 행은 (1,Ara,80),(2,Ara,65),(3,Bo,90)이다. SELECT id FROM students WHERE name = ? AND score >= ? ORDER BY id에 (Ara,70)을 바인딩한 결과를 종이로 구하라.

  1. 첫 빈칸은 name에 Ara, 둘째는 score의 하한70을 연결한다. SQL 구조는 그대로다.

  2. id1은 이름 일치·80≥70로 통과한다. id2는65<70로 제외, id3은 이름 불일치로 제외한다.

  3. ORDER BY id에 따라 남은 id1 하나를 반환한다. 실제 Python 조회 모양을 가정하면 [(1,)]이다.

예상 결과는 id1 하나다. [(1,)]은 이 표와 질의의 예상 Python 행 표현이며 실제 실행 출력은 아니다.

조건을 바꾸어 비교하기

구조 분리와 패턴 의미를 구별한다

ID 1의 이름은 A%, ID 2의 이름은 AB다. name=?와 name LIKE ?에 각각 A%를 바인딩하라.

  1. 등호는 이름 전체가 A%인지 비교한다.

  2. LIKE의 %는 0개 이상 문자와 일치한다.

등호는 ID 1만, LIKE는 ID 1과 2를 선택한다. 둘 다 값을 별도 인자로 전달했지만 질문이 다르다.

비교할 점

LIKE의 와일드카드 해석은 입력이 SQL 구문으로 삽입된 현상과 다르다.

named 추가 키는 조건이 아니다

SELECT id FROM names WHERE name=:name에 {name:AB,unused:99}를 넘긴다. unused가 필터로 추가되는가?

  1. 문장에는 :name만 있다.

  2. 필요한 name 키는 있고 unused는 추가 키다.

sqlite3에서는 ID 2를 반환하고 unused를 무시한다. 이 사례도 메모리 DB에서 확인했다.

비교할 점

사전에 키가 있다는 것과 질의에 그 조건이 있다는 것은 다르다.

풀이 보기

(Ara,65)는 id1과2를 반환한다. (Ara,)는 두 빈칸에 하나만 전달해 sqlite3의 ProgrammingError 대상이다. O'Neil은 하나의 이름 값이며 일치 행이 없으면 빈 결과다. SQL 따옴표를 손으로 붙이지 않는다.

오해와 반례

파라미터 질의는 테이블·열 이름까지 모두 ?로 바꾼다.

?는 값 자리다. 테이블 이름을 ?에 바인딩하는 것으로 SQL 구조를 선택할 수 없다. 허용 목록 또는 안전한 식별자 합성이 별도로 필요하다.

연결·트랜잭션 범위

송금의 첫 변경만 저장되고 두 번째는 실패하면 어떻게 될까?

준비 개념과 학습 목표

준비 개념

  • UPDATE

  • commit과 rollback

  • 예외 처리

학습 목표

  • 연결 수명과 트랜잭션 수명을 구별한다.

  • 업무 단위를 하나의 트랜잭션으로 묶는다.

  • 실패 시 rollback과 자원 반납을 설명한다.

예외를 잡았는데 왜 실패한 송금의 출금만 저장될까?

Python sqlite3에서 autocommit=False를 명시하고 A=100,B=40을 시작 상태로 둔다. with con 안에서 A를 30 출금한 뒤 입금 전에 ValueError가 난다. 예외가 블록 밖으로 나가면 문맥 관리자가 rollback하여 A=100,B=40이 유지된다.

그 예외를 with 블록 안의 except에서 잡고 정상 종료해 버리면 문맥 관리자는 밖으로 전달된 예외를 보지 못한다. 성공한 것으로 종료하여 출금만 commit할 수 있다. 실제 메모리 DB의 지정 사례에서는 A=70,B=40이 남았다. 예외를 처리했다는 사실과 업무 변경을 되돌렸다는 사실은 같지 않다.

실패를 알리는 예외가 트랜잭션 범위 밖에서 잡히도록 구성하거나 필요한 rollback과 재전달 정책을 명확히 한다. 검토한 사례는 DB 문장 오류가 아니라 출금 뒤의 Python 예외다. 드라이버와 오류 종류에 따라 DB 상태가 다를 수 있어 다른 제품에 그대로 일반화하지 않는다. with con 뒤 연결은 열려 있고 자원 close는 별도로 수행한다.

연결은 통로이고 트랜잭션은 변경 묶음

연결은 프로그램이 DB에 명령을 보내고 결과를 받는 통로다. 커서는 실행과 결과 읽기 상태를 관리한다. 트랜잭션은 관련 명령들의 변경을 확정하거나 되돌리는 범위다. 연결 하나에서 시간에 따라 여러 트랜잭션을 수행할 수 있어 두 수명이 같다고 가정하면 안 된다.

송금처럼 출금과 입금이 함께 성공해야 하는 업무는 둘을 같은 트랜잭션에 둔다. 원자성은 완료된 업무 전체를 남기거나 실패한 묶음을 되돌리는 성질이다. 외부 메일 발송 같은 DB 밖 효과까지 DB rollback이 자동 취소하지는 않는다.

자동 커밋 설정은 명시적으로 읽는다

Python sqlite3에서 autocommit=False를 명시하면 PEP249 방식으로 트랜잭션을 관리하고 commit/rollback을 사용한다. autocommit=True의 SQLite 자동 커밋 모드에서는 그 메서드가 같은 역할을 하지 않는다. 기본값과 legacy 동작에 기대지 말고 사용하는 버전과 설정을 확인한다.

sqlite3의 with con은 열린 트랜잭션을 정상 종료 시 commit하고 처리되지 않은 예외 또는 commit 실패 시 rollback하는 문맥이다. 이 문맥 자체가 연결을 닫는 것은 아니다. close는 별도 자원 정리이며 성공 업무를 확정하는 commit의 대체 명령으로 생각하지 않는다.

짧고 분명한 업무 범위

트랜잭션 안에서 사용자의 응답을 오래 기다리면 잠금이나 자원을 오래 점유할 수 있다. 검증 가능한 입력은 먼저 확인하고 DB 변경이 필요한 범위를 분명히 둔다. 실제 동시 접근에서는 격리 수준과 제약을 따로 검토하며 원자성만으로 모든 경쟁이 사라지지 않는다.

SQLAlchemy에서는 Session이 작업 중 연결을 빌리고 트랜잭션 종료 시 풀에 돌려준다. Session.begin 문맥의 성공/실패 처리와 Session.close의 수명을 구별한다. 같은 상태ful Session을 동시 작업자들이 무조건 공유하지 말고 작업별 트랜잭션과 세션 범위를 설계한다.

중간 과정을 따라가는 예제

다른 거래가 없는 자체 표에서 A잔액100,B잔액40이다. 하나의 트랜잭션으로 A에서30 출금하고 B에30 입금한다. 두 UPDATE가 대상 한 행씩 성공하고 commit도 성공한다고 가정하라. 입금 전에 예외가 나서 전체 rollback한 경우도 비교하라.

  1. 정상 경로의 임시 값은 A100−30=70,B40+30=70이다. 총합140은 유지된다.

  2. 두 변경 뒤 commit 성공하면 저장된 값은70/70이다.

  3. 출금 뒤 입금 전 예외가 나고 rollback 성공하면 출금도 되돌려 저장 값은100/40이다.

성공은70/70, 전체 실패는100/40이다. 종이 트랜잭션 모형이며 장애 복구나 동시 거래를 실제 실행한 결과가 아니다.

한 질의와 두 질의 중 언제나 한 질의가 더 적은 일을 할까?

부모 20명에게 각 자식 10개가 있다. 한 조인 질의는 원시 200행에서 부모 정보도 10번씩 반복한다. 두 질의로 부모 20행과 자식 200행을 따로 읽으면 총 행 수는 220이지만 넓은 부모 정보를 반복하지 않는다. 질의 수, 행 수, 전송 필드 크기는 서로 다른 지표다.

계산을 위해 부모 필드 1000바이트, 자식 필드 20바이트라는 가상 크기를 정하자. 조인은 200×1020=204000바이트, 별도 조회는 20×1000+200×20=24000바이트다. 프로토콜·키 중복·압축·실행 비용은 제외한 모형이다. 이 숫자는 실제 ORM·DB 성능 실측이 아니다.

미리 로딩하는 전략도 항상 두 질의라는 보장은 없다. 검토한 SQLAlchemy selectin 문서는 한 번에 최대 500개 부모 키의 묶음을 설명한다. 부모 1100개를 한 주 질의로 읽고 한 관계를 그 크기 묶음으로 읽는 모형이라면 자식 질의가 세 개여서 총 네 개다. 설정·여러 관계·스트리밍 등 다른 조건에서는 개수가 달라질 수 있다.

객체의 연결과 행의 연결

ORM은 프로그램 객체의 속성과 관계를 테이블 열·키·질의와 대응시키는 도구다. 객체는 다른 객체를 직접 참조할 수 있지만 관계형 DB는 키 값과 조인으로 관계를 나타낸다. 객체의 동일성과 DB 기본키의 동일성, 메모리 수명과 트랜잭션 수명도 그대로 같은 개념은 아니다.

이 차이를 임피던스 불일치라 부른다. 객체 모델을 편하게 다루도록 매핑해도 제약·조인·정렬·NULL·중복·동시성 등 관계형 의미가 사라지지 않는다. ORM을 쓴다는 이유로 SQL을 이해할 필요가 없어지는 것은 아니다.

세션에 있는 객체와 저장된 값

SQLAlchemy Session은 identity map으로 같은 기본키의 객체를 관리하고 변경 내용을 unit of work로 추적한다. flush는 pending 변경을 DB 트랜잭션에 반영하지만 commit과 같지 않다. rollback하면 그 트랜잭션의 변경을 되돌릴 수 있다.

identity map은 모든 질의 결과를 저장하는 query cache가 아니다. 일반 조건 질의는 SQL을 보내고 반환 기본키를 기존 객체와 연결할 수 있다. 객체를 메모리에 가지고 있다는 사실만으로 다른 트랜잭션이 바꾼 최신 값을 항상 본다는 보장은 없으며 expire/refresh와 격리 수준을 이해해야 한다.

관계 속성의 접근도 질의일 수 있다

아직 불러오지 않은 관계를 처음 접근할 때 SQL이 나가는 지연 로딩이 있다. 부모 N개를 한 질의로 읽은 뒤 각 부모의 별도 컬렉션을 하나씩 질의하면 총 N+1개다. 이 단원의 산술은 모든 컬렉션이 미로딩 상태이고 각 접근이 한 질의를 만든다는 조건을 둔다.

미리 관계를 로딩하면 질의 수를 줄일 수 있지만 항상 한 질의가 가장 빠르다는 뜻은 아니다. 조인 결과가 부모를 반복할 수 있고 대량 결과는 전송·메모리 비용이 늘어난다. 단순 many-to-one에서 대상이 identity map에 이미 있으면 추가 SQL이 없는 예외도 있으므로 모든 관계 접근을 무조건 한 질의로 세지 않는다.

  2. 두 질의 전략은1+1=2개, 비용2×5=10ms다. 두 번째 질의가 모든 자식을 가져온다고 명시했다.

  3. 차이는10ms다. 실제 DB 처리·네트워크·행 수는 제외했으므로 실측 성능 결론이 아니다.

자체 고정 비용 모형에서20ms 대10ms다. ORM의 모든 쿼리가 이 숫자나 개수로 동작한다는 주장이 아니다.
