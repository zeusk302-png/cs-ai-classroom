소단원 12.1

커밋·로그·체크포인트

사용자에게 저장됐다고 응답했는데 데이터 페이지는 아직 옛값이어도 될까?

준비 개념과 학습 목표

준비 개념

  • 트랜잭션과 원자성

  • 메모리와 영속 저장장치

  • 커밋과 장애

학습 목표

  • WAL 순서와 커밋 응답의 약속을 설명한다.

  • 로그 재생과 미완료 거래의 처리 대상을 구별한다.

  • 체크포인트를 백업과 구별한다.

페이지보다 로그를 먼저 남긴다

WAL은 변경 내용을 데이터 파일에 반영하기 전에 그 변경을 설명하는 로그를 영속화하는 규칙이다. 커밋 때 모든 데이터 페이지를 즉시 쓰지 않아도 필요한 로그가 남으면 장애 뒤 변경을 다시 적용할 수 있다. 로그를 메모리 버퍼에 적은 것과 영속 저장장치에 flush한 것을 구별한다.

PostgreSQL의 정상 동기 커밋은 성공 응답 전에 해당 WAL 영속화를 기다린다. 비동기 커밋은 성공 응답 뒤 최근 거래가 crash에서 사라질 수 있는 다른 약속이다. fsync를 끄는 것은 별도 설정이며 데이터 손실 위험을 같은 방식으로 해석하지 않는다. 이 단원에서 실제 서버 설정을 바꾸지는 않는다.

복구된 논리 상태에는 거래 경계가 필요하다

잔액 A에서 B로 이동할 때 A 감소만 보이는 상태를 완료 거래로 인정하면 안 된다. 로그에는 변경뿐 아니라 거래와 완료 여부를 판단할 정보가 필요하다. 복구 엔진은 재생과 거래 가시성 규칙을 함께 이용하여 미완료 거래를 완료 거래처럼 보이지 않게 한다.

아래 표는 완료한 거래의 논리 결과를 추적하는 단순 모형이다. 실제 PostgreSQL WAL은 SQL 문장을 그대로 줄줄이 재실행하는 텍스트가 아니다. 엔진에 따라 물리 REDO, UNDO, 가시성 관리 방식이 다르므로 미완료 기록은 언제나 물리적으로 재생하지 않는다고 일반화하지 않는다.

체크포인트는 되돌아갈 기준을 정리한다

체크포인트는 필요한 페이지 반영과 복구 시작 위치를 정리하여 이후 REDO 작업량을 줄이는 기준이다. 같은 장치 안의 체크포인트만으로 장치 전체 손실에서 되살릴 독립 사본이 생기지 않는다. 저장장치 장애에는 따로 확보한 백업·로그 사본이 필요하다.

체크포인트가 완료됐다는 이유만으로 모든 과거 WAL을 지우는 결론도 내리지 않는다. 백업·시점 복구·복제 등에 필요한 보존 범위가 남을 수 있다. 설치 없이 노트에 거래, 페이지 상태, 로그 영속 여부, 사용자 응답의 네 열을 만들어 시간 순서를 추적하자.

중간 과정을 따라가는 예제

가상 모형의 시작 잔액은 A = 100, B = 50이다. T1은 20을 이동하여 커밋하고 관련 로그가 영속화됐지만 페이지는 옛값이다. 이어 T2는 10을 이동하려 A 감소 기록만 남기고 커밋 전에 장애가 났다. 정상 복구 뒤 보이는 논리 상태는?

  1. 완료 T1의 결과는 A = 80, B = 70이며 합계 150이다. 페이지가 아직 100과 50이어도 영속 로그로 완료 결과를 반영할 근거가 있다.

  2. T2가 완료되지 않았으므로 A = 70, B = 70을 정상 완료 상태로 노출하지 않는다. 합계 140은 거래 중간 상태다.

  3. 이 모형에서 복구 뒤 보이는 상태는 T1만 완료한 A = 80, B = 70이다. 실제 엔진의 페이지 재생과 미완료 거래 가시성 구현은 별도다.

  4. 영속화 전에 비동기로 승인한 T1이라면 같은 보존 결론을 그대로 쓰지 못한다. 문제는 동기 완료 로그가 남았다는 가정을 명시했다.

복구 논리 결과는 A = 80, B = 70, 합계 150이다. 이 값은 가상 거래표 계산이며 실제 crash 복구 결과가 아니다.

한 단계 더

동기와 비동기 승인에 각각 성공 응답·로그 flush·장애 시점을 표시한 그림을 그리자. 사용자에게 약속하는 보존 범위와 실제 설정을 맞추고, 종이 순서표를 실측 지연·장애 실험으로 표시하지 않는다.

출처와 확인 범위
  • PostgreSQL 18 — Write-Ahead Logging

    실제 §28.3의 데이터 페이지보다 로그를 먼저 영속화하는 규칙과 REDO·기본 백업/WAL 연결을 읽었다. 자체 잔액 표는 서버 WAL 형식이나 복구 엔진 재현이 아니다.

  • PostgreSQL 18 — Asynchronous Commit

    실제 §28.4의 성공 응답 전 동기 로그 flush 및 비동기 승인·최근 손실·fsync off와 다른 의미를 읽었다. 설정 변경과 실제 crash 실험은 하지 않았다.

  • PostgreSQL 18 — WAL Configuration

    실제 §28.5의 체크포인트·REDO 시작·WAL 보존과 archive_timeout 및 체크포인트의 서로 다른 역할을 읽었다. 기본값 튜닝을 추천하지 않으며 자체 상태 표를 구성했다.

백업과 시점 복구

백업 이후 잘못된 삭제가 일어났다면 어느 지점까지 되살릴까?

준비 개념과 학습 목표

준비 개념

  • 백업 사본

  • 로그 순서와 커밋

  • 시간과 복구 목표

학습 목표

  • 논리 백업과 물리 기본 백업의 복구 범위를 구별한다.

  • 기본 사본과 연속 로그의 의존성을 확인한다.

  • 목표 시점·타임라인·검증 단계를 계획한다.

복구 방법에 맞는 사본을 고른다

SQL dump는 테이블·객체를 논리적으로 다시 만들 자료다. 물리 기본 백업은 데이터 파일 수준의 기반이다. PostgreSQL PITR은 적합한 물리 기본 사본에 연속 WAL을 재생하는 방식이며 pg_dump 파일에 WAL을 붙여 그대로 PITR하는 방식이 아니다.

실행 중인 파일을 아무 규칙 없이 복사했다고 복구 가능한 백업이 되지는 않는다. 도구·일관성 절차·필요한 로그·서버 버전 등 조건을 함께 확인한다. 여기서는 실제 서버 명령 대신 필요한 구성 목록과 시간표를 만드는 이론 활동을 한다.

목표까지 이어지는 기록이 필요하다

기본 백업의 시작부터 필요한 WAL과 목표까지의 기록이 이어져야 한다. 중간 기록이 빠지면 뒤의 최신 파일이 있어도 빈 부분을 건너뛰어 정확한 상태를 주장하지 못한다. 아카이브 지연은 현재 커밋 기록이 외부 사본에 아직 없을 수 있다는 뜻이다.

기본 백업이 끝난 뒤의 목표를 선택한다. 잘못된 삭제 전의 시점으로 멈추려면 그 삭제보다 앞선 유효 목표를 정하고 포함·제외 및 거래 완료 기준을 도구 설정과 맞춘다. 이후 새 이력은 이전 이력과 구별하며 필요한 timeline history도 보존한다.

복원한 뒤 목표 상태를 확인한다

새 시험 환경에 복원하여 정상 기동·내용·권한·연결 등을 확인하고 목표 거래가 어디까지 포함됐는지 대조한다. 백업 파일이 있다는 사실, 복원 명령이 끝났다는 사실, 학습 서비스가 사용할 데이터가 맞다는 사실은 각각 별도 확인이다.

원래 손상 자료나 잘못된 삭제 기록은 원인 확인에 필요할 수 있으므로 시험 대상과 원본을 구별한다. 이 활동에는 사용 중인 데이터 디렉터리를 지우거나 덮어쓰는 실행 단계가 없다. 종이에 사본 목록·로그 범위·목표·기대 행을 작성하면 설치 없이 핵심을 이해할 수 있다.

중간 과정을 따라가는 예제

기본 백업은 09:00에 시작해 09:05에 끝났다. 기준 잔액 A/B는 80/70이며 09:20의 T2에서 10을 이동해 커밋, 09:30의 T3에서 다시 10을 이동해 커밋했다. 09:37에 잘못된 전체 삭제가 커밋됐다. 필요한 연속 WAL이 모두 있다면 09:35를 목표로 한 논리 결과는?

  1. 기반 잔액 80/70에서 T2를 적용하면 70/80이다. T3까지 적용하면 60/90이다.

  2. 09:35는 기본 백업 종료 09:05 이후이고 잘못된 삭제 09:37 이전이다. 문제의 거래 시점과 목표가 같지 않아 경계 포함 모호성도 없다.

  3. 목표 결과는 A = 60, B = 90, 두 잔액 합계 150이다. 삭제까지 최신 재생하면 이 목표와 다른 결과가 된다.

  4. 09:20과 09:30 사이 필요한 WAL 일부가 없다면 최신 파일만으로 60/90을 복구했다고 주장하지 못한다. 실제 도구 복원은 실행하지 않았다.

09:35의 목표 상태는 A = 60, B = 90이다. 기반·연속 기록·정확한 목표가 모두 필요한 가상 예제다.

종이와 본문으로 직접 해보기

09:25 이전 완료 거래와 백업 종료 시점을 따로 본다.

풀이 보기

오해와 반례

최신 WAL 파일 하나와 아무 dump 파일이 있으면 원하는 모든 시점으로 복구한다.

적합한 물리 기반과 시작부터 목표까지 필요한 연속 기록·이력 정보가 있어야 한다. 논리 dump와 물리 WAL 재생의 복구 방법을 혼합하지 않는다.

09:25와 09:35의 기대 행을 나란히 적고 실제 시험 복원에서 어떤 조회로 구별할지 정하자. 오래된 파일처럼 보이더라도 다른 사본의 기반·연속 로그·타임라인에 필요한지 먼저 확인해야 한다.

소단원 12.3

복구 목표와 데이터 검증

데이터베이스가 켜졌다는 것과 복구 목표를 달성했다는 것은 같을까?

준비 개념과 학습 목표

준비 개념

  • 시간 차이

  • 테이블과 키·관계

  • 기대한 상태와 관측 근거

학습 목표

  • RTO와 RPO를 별도 목표로 계산한다.

  • 복구 후 구조·데이터·서비스 검증을 구분한다.

  • 계획·가상 계산·실제 훈련 결과를 따로 보고한다.

중단 시간과 잃을 수 있는 시간은 다르다

RTO는 서비스 중단부터 복구까지 허용하는 최대 시간 목표다. RPO는 손실을 허용하는 데이터 시점의 간격 목표다. RTO가 20분이라는 말은 데이터 20분을 잃어도 된다는 뜻이 아니다. 업무에서 허용하는 중단과 손실을 각각 정한다.

의존 서비스·설정·권한이 준비되지 않아 사용자 요청을 처리하지 못하면 DB 기동 시간만으로 서비스 복구 시간을 대신할 수 없다. 목표는 요구이며 실제 달성은 훈련·사고에서 기록한 결과다. 백업 주기만 보고 RPO를 보장하지 않고 성공한 사본과 실제 복구 가능 지점도 확인한다.

파일 검사와 데이터 의미를 함께 본다

pg_verifybackup은 manifest와 파일·체크섬·필요 WAL 등의 여러 오류를 찾지만 서버가 복원되어 올바른 자료를 제공한다는 모든 조건을 증명하지 못한다. 시험 복원과 내용 확인이 따로 필요하다. 검사 도구가 통과했는지와 실제 시험이 수행됐는지를 구별해 기록한다.

테이블 개수·행 개수·키 중복·참조 관계·대표 조회·목표 거래의 포함 여부를 확인한다. 행 수 하나만 같아도 행 값이 바뀌었을 수 있다. 합계도 오류가 상쇄될 수 있어 업무별 핵심 값과 관계를 함께 대조한다. 아래 데이터는 자체 가상 표로 실제 서버에 저장하지 않았다.

판정 기준을 먼저 정한다

가상 품목 표는 (id, 수량, 단가)가 (1,3,10), (2,2,20), (3,1,5)다. 목표 행은 세 개이고 금액 합계는 75다. 복구 후 (2,5,20)으로 바뀌었다면 행 수는 같지만 목표 상태가 아니다. 무엇을 비교했는지 공개해야 행 수만 본 검사를 전체 검증으로 오해하지 않는다.

노트에 목표 RTO/RPO, 장애 시각, 실제 사용 가능한 데이터 시점, 서비스 복구 시각, 검증 조회와 결과의 열을 만든다. 실제 장비 실험이 없으면 모든 시간과 표는 가상 계산으로 표시한다. 다음 훈련에서 수집할 증거와 현재 수행 여부를 함께 적는다.

중간 과정을 따라가는 예제

가상 목표 RTO는 20분, RPO는 5분이다. 서비스는 09:40에 중단되고 복구 가능한 마지막 데이터는 09:36, 서비스 사용 가능은 10:02다. 두 목표의 충족 여부를 구하라. 가상 품목 표에서 id 2의 수량이 5로 복구됐다면 행 수와 금액 합계를 비교하라.

  1. 중단부터 사용 가능까지 22분이므로 RTO 20분을 2분 초과한다.

  2. 장애 시점과 마지막 복구 데이터의 간격은 4분이므로 이 가상 모형에서는 RPO 5분 이내다. RPO를 충족해도 RTO 실패가 사라지지 않는다.

  3. 정상 금액은 3 × 10 + 2 × 20 + 1 × 5 = 75다. 잘못된 결과는 3 × 10 + 5 × 20 + 1 × 5 = 135다.

  4. 두 표 모두 세 행이지만 금액은 60만큼 다르다. 서비스가 시작돼도 기대 데이터와 맞지 않으면 내용 검증이 실패한 것이다.

가상 시간표에서 RTO는 실패, RPO는 충족이다. 품목 표는 행 수만으로 통과할 수 없고 금액 135는 기대 75와 다르다.

종이와 본문으로 직접 해보기

서비스 사용 가능 시각을 09:58로 바꾸고 마지막 복구 데이터를 09:30으로 바꾸면 각 목표는? 행 수와 합계가 모두 같으면 모든 값과 관계의 정확성을 증명한 것인가?

힌트 보기

두 시간 차이는 각각 장애 시각을 기준으로 계산한다. 같은 합계인 다른 값도 구성할 수 있다.

풀이 보기

중단 18분은 RTO 이내지만 데이터 간격 10분은 RPO를 넘는다. 행 수와 합계는 일부 검사일 뿐 모든 키·값·관계의 정확성을 증명하지 않는다.

오해와 반례

백업 검사가 성공했고 DB가 시작됐으므로 RTO/RPO와 모든 데이터 검증도 성공했다.

파일 검사·시험 복원·내용·서비스 사용과 시간 목표는 각각 다른 근거가 필요하다. 수행하지 않은 단계는 미수행으로 기록하고 가상 시간을 실제 결과로 보고하지 않는다.
