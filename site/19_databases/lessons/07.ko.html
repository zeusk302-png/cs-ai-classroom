소단원 7.1

DDL과 제약 선언

수량이 음수인 주문이나 없는 상품을 가리키는 주문을 저장해도 될까?

준비 개념과 학습 목표

준비 개념

  • DDL은 테이블 등 구조를 선언하는 명령이다.

  • NULL은 알려진 수가 아니라 부재/미상 표지다.

학습 목표

  • 키·참조·값 제약을 선언한다.

  • NULL과 제약의 적용 범위를 설명한다.

형식과 의미를 함께 선언한다

정수 타입은 수량이 정수임을 표현하지만 음수를 막지는 않는다. CHECK(qty>0)를 붙이면 그 행의 값이 양수인지 검사한다. NOT NULL은 값 부재를 금지한다. 업무 규칙에 맞는 두 조건을 함께 선언해야 알려진 양수만 받는다.

PostgreSQL CHECK는 식이 true 또는 NULL이면 통과한다. 따라서 CHECK(qty>0)만으로 NULL을 금지할 수 없다. 서로 다른 행의 합계를 일반 CHECK에 넣어 계속 보장하려는 접근도 지원 범위와 맞지 않으며 별도 제약/설계가 필요하다.

행의 이름표와 참조 연결

PRIMARY KEY는 한 컬럼 또는 컬럼 조합의 값이 유일하고 NULL이 아니도록 한다. FOREIGN KEY는 비NULL 참조 값이 참조 대상의 키에 있어야 함을 요구한다. 참조 컬럼에도 NOT NULL을 붙여야 선택이 아니라 필수 연결이 된다.

UNIQUE(a,b)는 각 컬럼의 단독 유일성이 아니라 조합의 유일성이다. PostgreSQL의 기본 UNIQUE는 NULL들을 서로 같게 취급하지 않으며 NULLS NOT DISTINCT를 선택할 수 있다. 이 부분은 제품/규약을 명시하여 외운다.

삭제 정책도 관계의 일부다

부모를 삭제하면 자식이 없는 부모를 가리키지 않도록 정책이 필요하다. RESTRICT는 참조되는 부모 삭제를 막고 CASCADE는 해당 부모를 참조하는 자식 행도 삭제한다. 편하다는 이유만으로 업무 기록까지 자동 삭제하도록 정하지 않는다.

제약 선언은 응용 코드의 입력 검사와 별도로 DB 상태를 보호한다. 기본값도 제약을 위반하면 실패하며 기존 자료에 새 제약을 추가할 때도 자료를 확인해야 한다. 아래는 즉시 검사·트리거 없는 작은 모형의 종이 판정이다.

중간 과정을 따라가는 예제

상품 Product의 id가 1,2다. 빈 Order에 id PRIMARY KEY, pid NOT NULL REFERENCES Product(id), qty integer NOT NULL CHECK(qty>0)를 둔다. 순서대로 후보 (10,1,2),(11,9,1),(12,2,NULL),(10,2,3),(13,2,−1)을 각각 별도 문장으로 삽입 시도하며 실패 문장은 상태를 바꾸지 않는다고 가정하라. 각 시도는 독립된 자동 커밋 문장으로 가정하며 하나의 명시적 트랜잭션에서 오류 후 계속하는 실험은 아니다. Order는 종이 표의 이름이며 실제 SQL에서 이 이름을 쓸 때는 예약어 충돌을 피할 식별자 표기가 필요하다.

  1. 첫 (10,1,2)는 유일키·부모 존재·양수라 통과한다.

  2. (11,9,1)은 pid 9 부모가 없어 실패, (12,2,NULL)은 NOT NULL 위반이다.

  3. 둘째 id10은 기존 키 중복, qty −1은 CHECK false이므로 실패한다.

최종 Order는 (10,1,2)만 있다. 각 실패를 제약 종류별로 설명할 수 있다.

종이와 본문으로 직접 해보기

CHECK(qty>0)만 있는 테이블에 NULL과 0을 판정한다. 별도 UNIQUE(a,b)에 (1,1),(1,2),(1,1)을 순서대로 넣으면 어느 것이 중복인가?

힌트 보기

CHECK의 NULL과 false를 구별하고 조합 전체를 비교한다.

풀이 보기

NULL의 비교는 NULL이라 CHECK 통과, 0은 false라 실패다. 조합 첫 두 행은 다르므로 통과, 셋째 (1,1)은 첫 행과 같아 실패한다.

오해와 반례

외래키를 선언하면 NULL 참조도 자동 금지한다.

기본 단일 컬럼 외래키에서 NULL은 부모 매칭을 요구하지 않는다. 필수 부모면 별도 NOT NULL을 선언한다. 복합키의 MATCH 규약까지 한 규칙으로 일반화하지 않는다.

답과 이유 보기

키는 유일성과 NOT NULL을 요구한다.

답과 이유 보기

통과할 수 있다.

식이 NULL이어도 CHECK를 만족한다.

RESTRICT로 상품 1을 삭제하면?

답과 이유 보기

현재 예제에서 실패한다.

Order의 pid 1 참조가 남아 있다.

한 단계 더

같은 자료에서 ON DELETE CASCADE를 선택하고 상품 1을 삭제하면 자식 (10,1,2)도 사라진다. 규칙 변경의 의미를 데이터 보존 목적과 함께 설명한다. 실제 테이블은 삭제하지 않는다.

소단원 7.2

INSERT·UPDATE·DELETE

조건 한 줄을 빠뜨리면 어느 행까지 바뀔까?

준비 개념과 학습 목표

준비 개념

  • INSERT는 새 행, UPDATE는 기존 행 값, DELETE는 행 자체를 바꾼다.

  • WHERE는 true인 행을 대상으로 고른다.

학습 목표

  • 각 문장의 대상과 결과 표를 구한다.

  • 연속 문장에서 앞 변경이 뒤 조건에 미치는 영향을 추적한다.

새 행에 컬럼 이름을 붙인다

INSERT INTO T(id,qty) VALUES (...)처럼 컬럼명을 명시하면 테이블 정의의 컬럼 순서를 암묵적으로 의존하지 않는다. 생략 컬럼은 지정된 default를 쓰거나 default가 없으면 NULL이 된다. 그 값도 제약을 통과해야 한다.

여러 행 VALUES나 SELECT 결과를 삽입할 수도 있다. 여기서는 각 문장을 순서대로 수행하는 단일 사용자 모형으로 제한한다. 실제 동시 트랜잭션에서 다른 사용자의 변경 가시성은 격리 규약을 추가로 확인한다.

기존 값에서 새 값을 계산한다

UPDATE T SET qty=qty+1 WHERE ...는 대상 행의 기존 qty에서 새 qty를 계산한다. WHERE를 만족하는 행은 0개일 수도 여러 개일 수도 있으며 대상 0개는 일반적으로 오류가 아니다. 키 조건만 정확히 일치하면 한 행을 식별할 수 있다.

WHERE를 생략하면 모든 행이 대상이다. 식을 갱신하는 SET의 =는 대입이고 WHERE의 =는 비교다. 두 표를 그려 먼저 대상 id를 표시하고 다음에 새 값을 계산하면 선택 조건과 변경 내용을 혼동하지 않는다.

삭제는 컬럼을 비우는 작업이 아니다

DELETE는 선택한 전체 행을 제거하고 테이블 구조는 남긴다. 값 하나를 NULL로 바꾸려면 UPDATE를 쓰며 NOT NULL 제약 여부도 확인한다. DELETE FROM T에 WHERE가 없으면 모든 행을 삭제한다.

아래 종이 활동은 실제 DB에 명령을 보내지 않는다. 실제 변경 전에는 요구사항과 대상 행을 확인해야 하며 제약·참조 정책·트랜잭션이 성공 여부에 영향을 준다. 본문의 행 수 계산은 트리거와 동시 변경이 없는 전제다.

중간 과정을 따라가는 예제

T(id PRIMARY KEY,qty integer NOT NULL CHECK(qty>=0),tag text DEFAULT 'new')의 시작 행 (1,2,old),(2,5,old)이다. INSERT INTO T(id,qty) VALUES(3,0); UPDATE T SET qty=qty+2 WHERE qty<3; DELETE FROM T WHERE qty>=5를 순서대로 종이 수행하라.

  1. 삽입 뒤 (3,0,new)가 더해져 3행이다.

  2. UPDATE 대상은 기존 qty 2의 id 1과 0의 id 3이다. 표는 (1,4,old),(2,5,old),(3,2,new)가 된다.

  3. DELETE는 id2만 제거한다. 앞 문장의 바뀐 qty를 기준으로 조건을 검사한다.

최종 (1,4,old),(3,2,new) 두 행이다. 삽입 1행/갱신 2행/삭제 1행이다.

종이와 본문으로 직접 해보기

같은 초기 두 행으로 다시 시작한다. UPDATE T SET qty=qty*2; DELETE FROM T WHERE qty<5;를 계산하고 마지막 DELETE FROM T;의 효과를 설명하라.

힌트 보기

첫 UPDATE에는 WHERE가 없다. 뒤 문장은 변경된 4와 10을 본다.

풀이 보기

먼저 id1 qty 4/id2 qty 10, 조건 삭제는 id1 한 행을 제거하여 id2만 남긴다. 마지막 조건 없는 DELETE는 id2도 제거해 빈 테이블이지만 구조는 남는다.

오해와 반례

WHERE가 있으면 항상 한 행만 바뀐다.

예제 qty<3은 두 행을 선택했다. id99 조건은 0행이다. 조건의 존재와 유일한 키로 특정 행을 식별하는 것은 다르다.

한 단계 더

최종 두 행에 UPDATE T SET qty=−1을 시도하면 CHECK를 위반한다. 단일 문장의 원자성 아래 일부 성공 행만 남기는 결과로 상상하지 말고 문장 실패와 트랜잭션의 후속 처리 정책을 구별한다. 실행 결과는 미수행이다.

소단원 7.3

뷰와 갱신 가능성

필터로 보이는 화면의 값을 바꾸면 원래 표도 바뀔까?

준비 개념과 학습 목표

준비 개념

  • 일반 뷰는 SELECT 정의를 저장한 이름이며 독립 복제 표와 다르다.

  • 집계는 여러 원래 행을 하나의 결과로 요약한다.

학습 목표

  • 단순 뷰의 갱신을 원래 행에 대응시킨다.

  • 자동 갱신 조건과 CHECK OPTION을 구별한다.

저장된 질문으로 테이블을 바라본다

CREATE VIEW V AS SELECT ...는 조회 정의를 이름으로 재사용한다. 일반 뷰는 생성 시 모든 결과를 복사해 고정하지 않으므로 기초 테이블 값이 바뀌면 다음 조회 결과도 바뀔 수 있다. materialized view는 별도 저장/새로고침 규약이다.

뷰는 관심 컬럼이나 행을 보이게 하는 인터페이스가 될 수 있다. 그러나 뷰라는 이름만으로 접근 보안이 완성되지는 않는다. 권한과 제품의 security 관련 옵션은 별도로 설계하며 이 단원은 행 대응에 집중한다.

단순 행 대응은 자동 변경할 수 있다

PostgreSQL의 자동 갱신 뷰는 하나의 테이블/갱신 가능 뷰를 FROM으로 사용하고 최상위 DISTINCT·GROUP BY·집계 등 제한 조건을 만족해야 한다. 단순 원래 컬럼은 갱신 가능하지만 price*2처럼 계산한 컬럼은 읽기 전용일 수 있다.

WHERE로 선택된 행은 갱신 뒤 조건을 벗어나 뷰에서 사라질 수 있다. WITH CHECK OPTION을 붙이면 INSERT/UPDATE 등이 뷰에 보이지 않을 새 행을 만드는 것을 막는다. 같은 테이블에 직접 한 변경까지 뷰 조건이 전역 제약처럼 막는 것은 아니다.

요약 행은 역방향이 모호하다

두 상품 가격의 평균이10일 때 평균을12로 바꾸는 방법은 여러 가지다. 각 가격에2를 더하거나 한 가격에4를 더할 수 있다. 그래서 집계 뷰는 기본적으로 자동 갱신 조건에 맞지 않는다.

특수 규칙이나 INSTEAD OF trigger로 변경 의미를 정의할 수 있지만 그것은 응용 설계의 선택이다. 읽기 가능한 SELECT라고 모두 INSERT/UPDATE/DELETE를 자동 지원한다고 결론 내리지 않는다. 아래는 권한 충분·트리거 없는 제품 규약이다.

중간 과정을 따라가는 예제

P(id PRIMARY KEY,price numeric NOT NULL CHECK(price>=0))에 (1,8),(2,12)가 있다. V AS SELECT id,price FROM P WHERE price<10. UPDATE V SET price=11 WHERE id=1을 CHECK OPTION 없이 할 때와 WITH CHECK OPTION 있을 때 각각 초기 상태로 비교하라.

  1. 처음 V는 (1,8)만 보인다. CHECK OPTION을 생략한 상황에서 갱신은 기초 P의 id1을 11로 바꾼다.

  2. P는 (1,11),(2,12), V는 빈 결과다. 행을 삭제한 것이 아니라 필터 밖으로 바꿨다.

  3. CHECK OPTION이면 새 price 11은 price<10을 만족하지 않아 갱신 실패, P와V는 처음대로 남는다.

보호 없으면 원래 행 11로 변경·뷰에서 사라짐, 보호 있으면 문장 실패다.

종이와 본문으로 직접 해보기

초기 P로 돌아간다. W AS SELECT id,price,price*2 AS double_price FROM P를 생각한다. id2 price를 9로 바꿀 때와 double_price를 18로 대입할 때의 자동 갱신 가능성을 판단하라.

힌트 보기

원래 컬럼과 계산 결과 컬럼은 다르다.

풀이 보기

price는 단순 원래 컬럼이라 갱신할 수 있고 P의 id2가 9로 되어 조회 double_price 18이다. double_price 자체 대입은 읽기 전용 계산 컬럼이므로 자동 갱신되지 않는다.

오해와 반례

CHECK OPTION이 기초 테이블의 모든 행을 뷰 조건에 묶는다.

처음 P의 id2 price 12도 존재할 수 있다. 해당 뷰를 통한 변경의 새 결과를 제한하는 것이며 기초 테이블 직접 변경의 전역 CHECK와 구별한다.

자기점검

보호 없는 예제의 id1은 삭제됐나?

답과 이유 보기

아니다.

P에 11로 남지만 V 필터를 벗어났다.

평균 가격 뷰는 기본 자동 갱신인가?

답과 이유 보기

아니다.

집계 결과는 여러 원래 행에 대응하고 자동 조건에서 제외된다.

계산 double_price를 직접 대입할 수 있나?

답과 이유 보기

기본 자동 갱신으로는 안 된다.

단순 기초 컬럼 참조가 아니므로 읽기 전용이다.

한 단계 더

같은 테이블의 SUM(price)를 새로운 값으로 바꾸라는 요구에 가능한 원래 표 두 개를 구성하라. 예를 들어 합 24는(12,12)와(8,16) 모두 만들 수 있어 별도 변경 정책이 필요한 이유를 설명한다.
