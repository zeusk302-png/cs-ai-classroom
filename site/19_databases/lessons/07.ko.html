소단원 7.1

DDL과 제약 선언

수량이 음수인 주문이나 없는 상품을 가리키는 주문을 저장해도 될까?

준비 개념과 학습 목표

준비 개념

  • DDL은 테이블 등 구조를 선언하는 명령이다.

  • NULL은 알려진 수가 아니라 부재/미상 표지다.

학습 목표

  • 키·참조·값 제약을 선언한다.

  • NULL과 제약의 적용 범위를 설명한다.

새 규칙을 선언하면 어제 저장한 잘못된 값도 고쳐질까?

재고 표에 상품 A의 수량 NULL, B의 수량 −2, C의 수량 5가 있다고 하자. 이 표에는 아직 수량 제약이 없다. DEFAULT 1을 새로 설정해도 기존 세 값은 그대로다. 기본값은 값을 생략하는 이후 삽입에 쓰는 선택 규칙이며 기존 기록을 수정하는 명령이 아니다.

새로운 일반 CHECK(qty > 0)를 추가하려면 기존 값도 그 조건을 만족해야 한다. B의 −2 때문에 추가가 실패한다. A의 NULL은 비교 결과가 UNKNOWN이므로 이 CHECK만으로 거부되지 않는다. 수량이 알려져 있으며 양수여야 한다면 NOT NULL과 양수 CHECK가 모두 필요하다.

기존 값을 올바르게 보정하려면 실제 업무에서 그 값이 무엇이어야 하는지 먼저 알아야 한다. NULL과 음수를 모두 임의로 1로 바꾸면 형식 규칙은 만족해도 실제 재고를 잘못 기록할 수 있다. 변경 전 위반 행과 보정 근거를 확인하고, 값을 수정한 뒤 규칙을 추가하는 순서를 구별한다. 여기서는 일반 제약 추가를 다루며 검사 유예 등 별도 옵션은 가정하지 않는다.

먼저 확인할 개념
  • 제약이 보장하는 사실

    형식상 허용과 실제 업무 사실의 정확성을 나눈다.

  • NULL의 비교 결과

    양수 CHECK 하나가 미상 값을 배제하지 않는 이유를 읽는다.

형식과 의미를 함께 선언한다

정수 타입은 수량이 정수임을 표현하지만 음수를 막지는 않는다. CHECK(qty>0)를 붙이면 그 행의 값이 양수인지 검사한다. NOT NULL은 값 부재를 금지한다. 업무 규칙에 맞는 두 조건을 함께 선언해야 알려진 양수만 받는다.

PostgreSQL CHECK는 식이 true 또는 NULL이면 통과한다. 따라서 CHECK(qty>0)만으로 NULL을 금지할 수 없다. 서로 다른 행의 합계를 일반 CHECK에 넣어 계속 보장하려는 접근도 지원 범위와 맞지 않으며 별도 제약/설계가 필요하다.

행의 이름표와 참조 연결

PRIMARY KEY는 한 컬럼 또는 컬럼 조합의 값이 유일하고 NULL이 아니도록 한다. FOREIGN KEY는 비NULL 참조 값이 참조 대상의 키에 있어야 함을 요구한다. 참조 컬럼에도 NOT NULL을 붙여야 선택이 아니라 필수 연결이 된다.

UNIQUE(a,b)는 각 컬럼의 단독 유일성이 아니라 조합의 유일성이다. PostgreSQL의 기본 UNIQUE는 NULL들을 서로 같게 취급하지 않으며 NULLS NOT DISTINCT를 선택할 수 있다. 이 부분은 제품/규약을 명시하여 외운다.

삭제 정책도 관계의 일부다

부모를 삭제하면 자식이 없는 부모를 가리키지 않도록 정책이 필요하다. RESTRICT는 참조되는 부모 삭제를 막고 CASCADE는 해당 부모를 참조하는 자식 행도 삭제한다. 편하다는 이유만으로 업무 기록까지 자동 삭제하도록 정하지 않는다.

제약 선언은 응용 코드의 입력 검사와 별도로 DB 상태를 보호한다. 기본값도 제약을 위반하면 실패하며 기존 자료에 새 제약을 추가할 때도 자료를 확인해야 한다. 아래는 즉시 검사·트리거 없는 작은 모형의 종이 판정이다.

각 행은 원래 상태에서 별도로 시도한다. 실패한 제약이 이미 설치된 것으로 계산하지 않는다. 새 열에 기본값을 붙여 추가하는 경우와 기존 열의 기본값만 바꾸는 경우도 구별한다.

중간 과정을 따라가는 예제

상품 Product의 id가 1,2다. 빈 Order에 id PRIMARY KEY, pid NOT NULL REFERENCES Product(id), qty integer NOT NULL CHECK(qty>0)를 둔다. 순서대로 후보 (10,1,2),(11,9,1),(12,2,NULL),(10,2,3),(13,2,−1)을 각각 별도 문장으로 삽입 시도하며 실패 문장은 상태를 바꾸지 않는다고 가정하라. 각 시도는 독립된 자동 커밋 문장으로 가정하며 하나의 명시적 트랜잭션에서 오류 후 계속하는 실험은 아니다. Order는 종이 표의 이름이며 실제 SQL에서 이 이름을 쓸 때는 예약어 충돌을 피할 식별자 표기가 필요하다.

  1. 첫 (10,1,2)는 유일키·부모 존재·양수라 통과한다.

  2. (11,9,1)은 pid 9 부모가 없어 실패, (12,2,NULL)은 NOT NULL 위반이다.

  3. 둘째 id10은 기존 키 중복, qty −1은 CHECK false이므로 실패한다.

최종 Order는 (10,1,2)만 있다. 각 실패를 제약 종류별로 설명할 수 있다.

조건을 바꾸어 비교하기

기본값을 바꾼 뒤 두 삽입

기존 A의 qty는 NULL이다. DEFAULT 1을 정하고 새 D는 qty를 생략, 새 E는 qty에 NULL을 명시한다. 제약은 아직 없다.

  1. 기존 A는 기본값 설정의 수정 대상이 아니다.

  2. D의 생략한 값은 기본값 1이다. E의 명시한 NULL은 그대로다.

A는 NULL, D는 1, E는 NULL이다.

비교할 점

기본값은 모든 NULL을 자동 치환하는 규칙이 아니다.

위반 행을 단계적으로 처리한다

A=NULL, B=−2, C=5다. 실제 조사로 A=3, B=2가 확인되었다. 양의 필수 수량을 만들려면?

  1. 업무 근거에 따라 A를 3, B를 2로 수정한다.

  2. 세 값 3,2,5에 대해 NOT NULL과 CHECK(qty > 0)를 추가한다.

두 규칙의 기존 데이터 검사에 모두 통과한다.

비교할 점

제약 추가는 사실 조사나 데이터 보정을 대신하지 않는다.

종이와 본문으로 직접 해보기

CHECK(qty>0)만 있는 테이블에 NULL과 0을 판정한다. 별도 UNIQUE(a,b)에 (1,1),(1,2),(1,1)을 순서대로 넣으면 어느 것이 중복인가?

힌트 보기

CHECK의 NULL과 false를 구별하고 조합 전체를 비교한다.

풀이 보기

NULL의 비교는 NULL이라 CHECK 통과, 0은 false라 실패다. 조합 첫 두 행은 다르므로 통과, 셋째 (1,1)은 첫 행과 같아 실패한다.

오해와 반례

외래키를 선언하면 NULL 참조도 자동 금지한다.

기본 단일 컬럼 외래키에서 NULL은 부모 매칭을 요구하지 않는다. 필수 부모면 별도 NOT NULL을 선언한다. 복합키의 MATCH 규약까지 한 규칙으로 일반화하지 않는다.

소단원 7.2

INSERT·UPDATE·DELETE

조건 한 줄을 빠뜨리면 어느 행까지 바뀔까?

준비 개념과 학습 목표

준비 개념

  • INSERT는 새 행, UPDATE는 기존 행 값, DELETE는 행 자체를 바꾼다.

  • WHERE는 true인 행을 대상으로 고른다.

학습 목표

  • 각 문장의 대상과 결과 표를 구한다.

  • 연속 문장에서 앞 변경이 뒤 조건에 미치는 영향을 추적한다.

명령에 오류가 없으면 주문 처리도 성공한 것일까?

상품 P의 재고가 4일 때 6개를 요청한다고 하자. id=P AND stock>=6을 조건으로 stock=stock−6을 갱신하면 대상이 0행이다. SQL 명령 자체에는 오류가 없어도 주문에 필요한 재고 차감은 이루어지지 않았다. 영향을 받은 행과 반환 결과를 확인해야 업무 결과를 알 수 있다.

한 UPDATE의 여러 대입식은 각 행의 갱신 전 값을 참조한다. a=2,b=9에서 SET a=b,b=a를 적용하면 a=9,b=2가 된다. 일반 프로그램에서 두 대입을 순서대로 실행하여 두 값이 모두 9가 되는 추적과 구별한다. 여기서는 트리거나 다른 자동 계산이 없는 단순한 표를 가정한다.

여러 행을 넣는 한 INSERT에서 즉시 CHECK 위반이 발생하면 그 문장의 삽입을 일부만 확정하지 않는다. 반면 각각 별도 자동 커밋 문장으로 먼저 성공한 삽입은 이후 다른 문장이 실패해도 이미 확정된 상태다. 명시적 트랜잭션 블록이 오류로 중단된 경우에는 전체 ROLLBACK 또는 오류 전 저장점으로의 ROLLBACK TO 등으로 복구해야 한다.

먼저 확인할 개념
  • 트랜잭션의 경계

    여러 업무 단계를 하나로 묶는 경우와 별도 확정을 나눈다.

  • 조건에 따른 행 선택

    조건 통과 행이 없을 수 있으며 성공 여부와 대상 수를 나눈다.

새 행에 컬럼 이름을 붙인다

INSERT INTO T(id,qty) VALUES (...)처럼 컬럼명을 명시하면 테이블 정의의 컬럼 순서를 암묵적으로 의존하지 않는다. 생략 컬럼은 지정된 default를 쓰거나 default가 없으면 NULL이 된다. 그 값도 제약을 통과해야 한다.

여러 행 VALUES나 SELECT 결과를 삽입할 수도 있다. 여기서는 각 문장을 순서대로 수행하는 단일 사용자 모형으로 제한한다. 실제 동시 트랜잭션에서 다른 사용자의 변경 가시성은 격리 규약을 추가로 확인한다.

기존 값에서 새 값을 계산한다

UPDATE T SET qty=qty+1 WHERE ...는 대상 행의 기존 qty에서 새 qty를 계산한다. WHERE를 만족하는 행은 0개일 수도 여러 개일 수도 있으며 대상 0개는 일반적으로 오류가 아니다. 키 조건만 정확히 일치하면 한 행을 식별할 수 있다.

WHERE를 생략하면 모든 행이 대상이다. 식을 갱신하는 SET의 =는 대입이고 WHERE의 =는 비교다. 두 표를 그려 먼저 대상 id를 표시하고 다음에 새 값을 계산하면 선택 조건과 변경 내용을 혼동하지 않는다.

삭제는 컬럼을 비우는 작업이 아니다

DELETE는 선택한 전체 행을 제거하고 테이블 구조는 남긴다. 값 하나를 NULL로 바꾸려면 UPDATE를 쓰며 NOT NULL 제약 여부도 확인한다. DELETE FROM T에 WHERE가 없으면 모든 행을 삭제한다.

아래 종이 활동은 실제 DB에 명령을 보내지 않는다. 실제 변경 전에는 요구사항과 대상 행을 확인해야 하며 제약·참조 정책·트랜잭션이 성공 여부에 영향을 준다. 본문의 행 수 계산은 트리거와 동시 변경이 없는 전제다.

중간 과정을 따라가는 예제

T(id PRIMARY KEY,qty integer NOT NULL CHECK(qty>=0),tag text DEFAULT 'new')의 시작 행 (1,2,old),(2,5,old)이다. INSERT INTO T(id,qty) VALUES(3,0); UPDATE T SET qty=qty+2 WHERE qty<3; DELETE FROM T WHERE qty>=5를 순서대로 종이 수행하라.

  1. 삽입 뒤 (3,0,new)가 더해져 3행이다.

  2. UPDATE 대상은 기존 qty 2의 id 1과 0의 id 3이다. 표는 (1,4,old),(2,5,old),(3,2,new)가 된다.

  3. DELETE는 id2만 제거한다. 앞 문장의 바뀐 qty를 기준으로 조건을 검사한다.

최종 (1,4,old),(3,2,new) 두 행이다. 삽입 1행/갱신 2행/삭제 1행이다.

비교할 점

문장의 대입 목록을 순차 프로그램처럼 추적하면 b=9라는 오답이 된다.

하나의 실패 문장과 별도 확정

qty > 0 제약이 있는 빈 표에 한 INSERT로 (A,2),(B,−1)을 넣는 경우와 별도 자동 커밋 INSERT 두 개로 넣는 경우를 비교하라.

  1. 한 문장은 B의 위반 때문에 전체 삽입이 실패한다.

  2. 별도 문장은 A의 성공이 확정된 뒤 B의 문장만 실패한다.

한 문장은 두 행 모두 없고, 별도 자동 커밋 문장에서는 A만 남는다.

비교할 점

처음 행을 먼저 처리했을 것이라는 추측으로 부분 확정을 결론 내리지 않는다.

소단원 7.3

뷰와 갱신 가능성

필터로 보이는 화면의 값을 바꾸면 원래 표도 바뀔까?

준비 개념과 학습 목표

준비 개념

  • 일반 뷰는 SELECT 정의를 저장한 이름이며 독립 복제 표와 다르다.

  • 집계는 여러 원래 행을 하나의 결과로 요약한다.

학습 목표

  • 단순 뷰의 갱신을 원래 행에 대응시킨다.

  • 자동 갱신 조건과 CHECK OPTION을 구별한다.

뷰의 검사 옵션은 아래 표의 모든 수정까지 막을까?

기본 표 P의 가격이 6인 상품 하나를 생각하자. V는 price<10인 상품을 보여 주고, W는 V에서 price>0인 상품만 보여 준다. V에는 검사 옵션이 없다. W를 통한 가격 12 수정은 W의 직접 조건 price>0은 만족하지만 V의 조건 price<10은 벗어난다.

W에 LOCAL CHECK OPTION을 두면 이 모형에서 직접 조건만 검사하여 12 수정을 허용한다. CASCADED CHECK OPTION이면 아래 V의 조건까지 검사하여 거부한다. 둘 모두 자동 갱신 가능한 단순 뷰이며 트리거나 규칙은 없다고 가정한다. V 자체가 검사 옵션을 가진 경우에는 LOCAL 비교 결과가 달라질 수 있다.

검사 옵션은 정한 뷰를 통한 변경의 새 행을 검사하는 규칙이다. 아래 기본 표에 직접 쓰는 권한이 있는 사람이 기본 표를 수정할 때 그 뷰의 조건을 전역 제약처럼 적용하지 않는다. 계산 열이나 집계 뷰의 갱신 가능성도 별도다. 숫자가 보인다는 사실만으로 그 숫자의 변경을 원본 어느 행에 어떻게 배분할지 정해지지는 않는다.

먼저 확인할 개념
  • 뷰의 기본 의미

    뷰 조건, 기본 표의 값, 자동 갱신 가능한 열을 나눈다.

  • 제약과 변경 경로

    표의 제약과 특정 뷰 변경에 대한 검사를 구별한다.

저장된 질문으로 테이블을 바라본다

CREATE VIEW V AS SELECT ...는 조회 정의를 이름으로 재사용한다. 일반 뷰는 생성 시 모든 결과를 복사해 고정하지 않으므로 기초 테이블 값이 바뀌면 다음 조회 결과도 바뀔 수 있다. materialized view는 별도 저장/새로고침 규약이다.

뷰는 관심 컬럼이나 행을 보이게 하는 인터페이스가 될 수 있다. 그러나 뷰라는 이름만으로 접근 보안이 완성되지는 않는다. 권한과 제품의 security 관련 옵션은 별도로 설계하며 이 단원은 행 대응에 집중한다.

단순 행 대응은 자동 변경할 수 있다

PostgreSQL의 자동 갱신 뷰는 하나의 테이블/갱신 가능 뷰를 FROM으로 사용하고 최상위 DISTINCT·GROUP BY·집계 등 제한 조건을 만족해야 한다. 단순 원래 컬럼은 갱신 가능하지만 price*2처럼 계산한 컬럼은 읽기 전용일 수 있다.

WHERE로 선택된 행은 갱신 뒤 조건을 벗어나 뷰에서 사라질 수 있다. WITH CHECK OPTION을 붙이면 INSERT/UPDATE 등이 뷰에 보이지 않을 새 행을 만드는 것을 막는다. 같은 테이블에 직접 한 변경까지 뷰 조건이 전역 제약처럼 막는 것은 아니다.

요약 행은 역방향이 모호하다

두 상품 가격의 평균이10일 때 평균을12로 바꾸는 방법은 여러 가지다. 각 가격에2를 더하거나 한 가격에4를 더할 수 있다. 그래서 집계 뷰는 기본적으로 자동 갱신 조건에 맞지 않는다.

특수 규칙이나 INSTEAD OF trigger로 변경 의미를 정의할 수 있지만 그것은 응용 설계의 선택이다. 읽기 가능한 SELECT라고 모두 INSERT/UPDATE/DELETE를 자동 지원한다고 결론 내리지 않는다. 아래는 권한 충분·트리거 없는 제품 규약이다.

두 겹 뷰에서 검사 범위를 비교한다
경로새 가격검사 범위결과

W LOCAL 경유

12

price>0

허용, V/W에서 행이 안 보임

W CASCADED 경유

12

price>0 및 price<10

거부, 가격 6 유지

권한 있는 기본 표 직접 수정

기본 표 제약

뷰 검사 옵션으로 거부하지 않음

각 경로는 가격 6에서 따로 시작한다. 기본 표에는 가격 범위 제약이 없고 V에는 검사 옵션이 없다. INSERT/UPDATE 권한이나 보안 정책을 실제 운영에서 검증했다는 의미는 아니다.

중간 과정을 따라가는 예제

P(id PRIMARY KEY,price numeric NOT NULL CHECK(price>=0))에 (1,8),(2,12)가 있다. V AS SELECT id,price FROM P WHERE price<10. UPDATE V SET price=11 WHERE id=1을 CHECK OPTION 없이 할 때와 WITH CHECK OPTION 있을 때 각각 초기 상태로 비교하라.

  1. 처음 V는 (1,8)만 보인다. CHECK OPTION을 생략한 상황에서 갱신은 기초 P의 id1을 11로 바꾼다.

  2. P는 (1,11),(2,12), V는 빈 결과다. 행을 삭제한 것이 아니라 필터 밖으로 바꿨다.

  3. CHECK OPTION이면 새 price 11은 price<10을 만족하지 않아 갱신 실패, P와V는 처음대로 남는다.

보호 없으면 원래 행 11로 변경·뷰에서 사라짐, 보호 있으면 문장 실패다.

조건을 바꾸어 비교하기

LOCAL과 CASCADED의 경계

V는 price<10, W는 V에서 price>0이다. V에 검사 옵션이 없다. W를 통해 가격 6을 12로 바꾸라.

  1. 12는 W의 직접 조건 price>0을 만족한다.

  2. 12는 아래 V의 price<10을 만족하지 않는다.

LOCAL이면 허용되어 뷰에서 사라지고, CASCADED이면 거부되어 6이 유지된다.

비교할 점

아래 뷰에도 검사 옵션이 있는지 반드시 명시해야 비교가 결정된다.

읽을 수 있는 열과 바꿀 수 있는 열

단순 뷰가 id,price,price*2 AS doubled를 보여 준다. 기본 가격은 6이다. doubled=20 대입은 자동 지원되는가?

  1. doubled는 기본 열의 직접 참조가 아니라 계산식이다.

  2. 기본 price를 7로 수정하면 조회 계산은 14가 된다.

doubled에 직접 대입하는 자동 갱신은 지원되지 않는다. price 직접 열의 수정 가능성과 구별한다.

비교할 점

계산 결과를 자동 역변환한다는 규칙은 없으며 임의 트리거 구현도 가정하지 않는다.

종이와 본문으로 직접 해보기

초기 P로 돌아간다. W AS SELECT id,price,price*2 AS double_price FROM P를 생각한다. id2 price를 9로 바꿀 때와 double_price를 18로 대입할 때의 자동 갱신 가능성을 판단하라.

힌트 보기

원래 컬럼과 계산 결과 컬럼은 다르다.

풀이 보기

price는 단순 원래 컬럼이라 갱신할 수 있고 P의 id2가 9로 되어 조회 double_price 18이다. double_price 자체 대입은 읽기 전용 계산 컬럼이므로 자동 갱신되지 않는다.

오해와 반례

CHECK OPTION이 기초 테이블의 모든 행을 뷰 조건에 묶는다.

처음 P의 id2 price 12도 존재할 수 있다. 해당 뷰를 통한 변경의 새 결과를 제한하는 것이며 기초 테이블 직접 변경의 전역 CHECK와 구별한다.

연습 1 · 값과 상태 예측

힌트 2

  1. −1은 직접 조건을 만족하지 않는다.

연습 2 · 오류 찾아 고치기

W CASCADED를 두었으므로 권한 있는 사람이 P를 직접 수정해 가격 12를 넣는 것도 뷰 검사로 막힌다고 했다.

힌트 1

  1. P 직접 수정은 W를 통한 변경이 아니다.

뷰 검사 옵션만으로 그 직접 수정을 거부하지 않는다. 필요하면 기본 표 제약과 쓰기 권한을 별도로 설계한다.

뷰 검사 옵션은 같은 기본 표의 모든 쓰기에 적용되는 전역 제약이다.

연습 3 · 직접 만들어 보기

0<price<10 범위를 기본 표 직접 쓰기에서도 요구하려 한다. 필수 가격이라는 조건까지 적어라.

힌트 1

뷰 조건만으로는 직접 쓰기를 제한하지 않는다.

힌트 2

NULL은 CHECK의 FALSE가 아니다.

풀이와 답 확인

  1. 기본 표에 price NOT NULL을 요구한다.

  2. CHECK(price>0 AND price<10)를 기본 표에 둔다.

  3. 기존 값도 새 규칙을 만족하는지 확인한다.

필수 가격과 표의 범위 제약을 함께 선언한다. 뷰 표시나 접근 권한은 추가로 정한다.

대상 경로와 NULL 정책은 각각 별도 조건이다.

두 상품 가격이 6과 8이고 합계 뷰가 14를 보여 준다. 합계 20으로 자동 수정하려면 원본 가격은 하나로 결정되는가?

힌트 2

풀이와 답 확인

  1. 6+14=20이고 10+10=20도 가능하다.

하나로 결정되지 않는다. 집계 뷰는 이 단순 자동 갱신 조건을 충족하지 않으며 별도 업무 배분 정책이 필요하다.

다른 문제에 적용하기

재고 변경 보고서의 세 가지 경계

기존 재고는 상품 A가 NULL, 상품 B가 −2, 상품 C가 5다. DEFAULT 1을 설정한 결과와 양수 필수 제약 추가의 실패 원인을 구별하라. 별도 상품 P의 재고 4에서 6개 차감을 조건부 UPDATE로 요청한 결과를 적어라. 가격 6인 상품의 V(price<10), W(V에서 price>0)에 대해 LOCAL/CASCADED 경유 가격 12 변경을 비교하라. V에는 검사 옵션이 없고 기본 가격 제약도 없다.

힌트 1

기존 값, 이후 생략 값, 현재 행의 조건을 나눈다.

힌트 2

명령 오류와 갱신 행 수, 뷰 변경 경로를 따로 추적한다.

풀이와 답 확인

  1. DEFAULT 설정 후에도 기존 재고는 상품 A가 NULL, 상품 B가 −2, 상품 C가 5다. NOT NULL은 A 때문에, 양수 CHECK는 B 때문에 일반 추가가 실패한다.

  2. P는 stock>=6에 맞지 않아 갱신 0행이고 재고 4가 유지된다.

  3. W LOCAL은 직접 양수 조건을 만족한 12를 허용하여 뷰에서 행이 사라진다.

  4. W CASCADED는 아래 price<10 위반을 거부하여 가격 6을 유지한다.

변경의 성공은 기존 데이터, 명령 경계, 갱신 대상, 변경 경로를 함께 정의해야 판정할 수 있다. 이는 문서 규칙과 작은 표의 손추적이며 실제 SQL 실행은 아니다.

해결한 뒤 점검할 것

  • DEFAULT와 기존 UPDATE를 구별한다.

  • NULL과 음수를 막는 두 규칙을 나눈다.

  • 갱신 0행을 차감 성공으로 보고하지 않는다.

  • 아래 뷰 검사 옵션과 직접 쓰기 경로를 명시한다.
