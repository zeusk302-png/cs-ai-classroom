소단원 5.1

SELECT·필터·정렬

점수표에서 80점 이상인 학생 이름만, 높은 점수부터 보고 싶다면 어떤 질문을 해야 할까?

준비 개념과 학습 목표

준비 개념

  • 아래 Score(id integer,name text,score integer) 표를 가정한다. 행 (1,민,80),(2,하,95),(3,준,80),(4,솔,NULL)이다.

  • SELECT는 값을 조회한다. 이 단원 예제는 표를 바꾸는 UPDATE/DELETE를 사용하지 않는다. SQL 의미는 PostgreSQL 18 기준이다.

학습 목표

  • FROM·WHERE·SELECT·ORDER BY의 역할을 한 표에 연결한다.

  • 동률과 NULL을 포함한 원하는 순서를 명시한다.

질문을 네 부분으로 쓴다

FROM Score는 입력 표, WHERE score>=80은 남길 행의 조건, SELECT id,name,score는 보여 줄 열, ORDER BY score DESC,id ASC는 정렬 기준이다. 설명을 위한 논리적 사고 순서는 입력→조건 검사→출력 식→정렬이다. 실제 엔진이 물리적으로 반드시 이 순서로 표를 복사한다는 뜻은 아니다. 질의 최적화는 같은 결과를 유지하며 다른 실행 방법을 사용할 수 있다.

WHERE에서 조건이 참인 행만 남긴다. NULL은 점수가 미상이라는 표식이라 score>=80이 참이 되지 않아 솔은 여기서 제외된다. 출력할 열 이름을 직접 적으면 필요한 정보를 분명히 할 수 있다. SELECT *는 모든 열을 뜻하지만 표의 열이 늘었을 때 출력 구조도 바뀔 수 있다.

순서를 계약에 넣는다

ORDER BY를 생략하면 저장·삽입 순서가 출력 순서라는 보장은 없다. DESC는 내림차순, ASC는 오름차순이며 각 열에 따로 적용된다. 점수가 같으면 id가 작은 행을 먼저 두겠다는 두 번째 기준을 쓴다. 모든 정렬 기준이 같은 두 행의 서로 순서는 아직 정하지 않은 것이다.

PostgreSQL의 DESC는 기본 NULLS FIRST라 미상 점수가 앞에 올 수 있다. 미상을 뒤에 두고 싶으면 score DESC NULLS LAST라고 직접 쓴다. NULL은 큰 점수를 받은 사람이 아니라 값이 없는 행이다. 문자 순서는 언어·콜레이션 설정에 영향을 받을 수 있어 이 예제는 숫자 id를 동률 기준으로 삼는다.

SELECT id, name, score
FROM Score
WHERE score >= 80
ORDER BY score DESC, id ASC;

출력 이름과 조건의 이름

SELECT score+5 AS adjusted는 계산 결과에 이름을 준다. 출력 별칭 adjusted는 ORDER BY adjusted에서 사용할 수 있지만 같은 SELECT의 WHERE에서 출력 별칭으로 쓰는 것은 허용하지 않는다. 이때 WHERE score+5>=85처럼 원래 식을 쓰거나 바깥 질의를 설계한다. 식에 이름을 주는 일은 입력 열을 수정하는 일이 아니다.

필터 없는 모든 행을 정렬할 때는 NULL 처리를 따로 선택한다. 어떤 행이 보이지 않는지 궁금하면 조건 하나씩 참·거짓·미상을 써 보는 방식이 디버깅에 도움이 된다. NULL을 0으로 보는 것은 데이터 의미를 바꾸는 결정이므로 자동으로 가정하지 않는다.

중간 과정을 따라가는 예제

주어진 Score에서 본문의 score>=80 질의를 판정하고, 필터 없이 score DESC NULLS LAST,id ASC 정렬도 써라.

  1. 조건 결과는 id1 참,id2 참,id3 참,id4 미상이다. true인 1,2,3만 남는다.

  2. 점수95인 id2 하가 먼저이며 점수80 동률 id1 민,id3 준 순서다.

  3. 필터 없이는 같은 세 행 뒤에 NULL인 id4 솔이 온다. NULLS LAST를 명시했기 때문이다.

  4. SELECT 이름만 출력하도록 바꾸어도 필터·정렬 기준으로 score/id를 쓸 수 있다. 이 예제는 DISTINCT 없는 단일 표 조회다.

필터 출력 (2,하,95),(1,민,80),(3,준,80). 필터 없는 NULLS LAST 출력에는 마지막 (4,솔,NULL)이 추가된다.

종이와 본문으로 직접 해보기

WHERE score<90, ORDER BY id DESC이면 어떤 행이 어떤 순서로 나오는가? score+5 AS adjusted도 계산하라.

힌트 보기

미상과 비교한 결과를 true로 취급하지 말고, 남은 id를 큰 순으로 놓는다.

풀이 보기

id1과 id3만 조건이 참이다. 출력 순서는 id3 준의 adjusted85, id1 민의 adjusted85다. id2는95라 거짓이고 id4는 미상이라 제외된다.

오해와 반례

표에 보이는 순서나 입력한 순서대로 결과가 항상 나오고 DESC는 모든 열에 적용된다.

명시 ORDER BY 없는 순서는 계약이 아니다. ORDER BY score DESC,id는 score만 내림차순이고 id는 기본 오름차순이다. 두 행80의 id1/3은 이 차이를 직접 보여 준다.

자기점검

답과 이유 보기

둘 다 남기지 않는다.

true만 필터를 통과한다.

답과 이유 보기

ORDER BY score DESC,id ASC다.

두 번째 기준은 첫 번째 기준이 같은 행에 적용된다.

AS adjusted가 입력 score 값을 바꾸는가?

답과 이유 보기

아니다.

조회 결과의 열 이름을 붙인 것이다.

한 단계 더

화면에서 상위 2명을 보여 주려면 LIMIT 2를 추가할 수 있다. 하지만 정렬에 점수만 쓰면 동률 경계에서 어떤 사람을 포함할지 불명확할 수 있다. 고유 id 같은 마지막 기준을 정하면 반복 조회의 의도를 분명하게 할 수 있다. 이 단원에서는 동시 데이터 변경과 페이지네이션의 별도 문제까지 해결했다고 주장하지 않는다.

소단원 5.2

집합·중복·NULL 처리

같은 점수가 두 번 나온 것은 오류일까, 서로 다른 두 학생의 정보일까?

준비 개념과 학습 목표

준비 개념

  • SQL의 일반 조회 결과는 중복 행을 허용한다. 수학 집합은 같은 원소의 반복을 별도로 세지 않는다.

  • Score id1=80,id2=95,id3=80,id4=NULL을 사용한다. NULL은 0이나 문자열 null과 다르다.

학습 목표

  • DISTINCT와 ALL의 의미를 출력 열 조합으로 판단한다.

  • NULL 비교와 NULL 검사를 분리하고 3값 조건을 추적한다.

어떤 값의 중복을 없애는가

SELECT score FROM Score는 80,95,80,NULL의 네 행을 얻는다. SELECT DISTINCT score는80,95,NULL의 세 종류다. 반면 SELECT DISTINCT id,score는 id가 서로 달라 네 행이다. 중복 판정은 선택한 모든 열의 조합을 기준으로 한다. 점수만 고르면 누가 같은 점수였는지 구별할 정보는 사라진다.

DISTINCT는 NULL끼리를 중복 제거에서 같은 것으로 취급한다. 따라서 NULL이 여러 행이어도 NULL 한 종류만 남는다. 이 규칙은 NULL=NULL이라는 일반 비교가 참이라는 뜻이 아니다. 중복 제거 규칙과 미상 값에 대한 조건식 규칙은 목적이 달라 구분해야 한다.

집합 연산과 행 수

UNION은 두 결과를 합치고 중복을 제거한다. UNION ALL은 중복을 그대로 합친다. 열 개수가 같고 해당 열의 자료형이 호환되어야 한다. 뒤 표가 반드시 뒤에 출력된다는 순서는 UNION이 보장하지 않으므로 정렬이 필요하면 합친 결과에 ORDER BY를 붙인다.

두 조회를 X=[80,80,NULL], Y=[80,95,NULL]로 두면 UNION ALL은 여섯 행이며 UNION은80,95,NULL의 세 종류다. INTERSECT는 공통 종류80,NULL, EXCEPT에서 X−Y는 비어 있다. 여기서 종류 표기는 순서를 주장하지 않는다. ALL 변형의 중복 개수 계산은 별도로 공부할 수 있다.

SELECT DISTINCT score FROM Score;
SELECT id, name FROM Score WHERE score IS NULL;
SELECT id, name FROM Score WHERE score IS NOT NULL;

미상에 대한 질문을 바꾼다

score=NULL이나 score<>NULL은 NULL 미상 결과를 주므로 원하는 NULL 행을 필터로 찾지 못한다. IS NULL은 값이 미상 표식인지 검사하여 true/false를 준다. NULL끼리도 값의 동등성처럼 비교해야 하는 별도 상황에는 IS NOT DISTINCT FROM이 있다. 이를 일반 등호와 같은 것으로 혼동하지 않는다.

3값 논리에서 미상을 U라 쓰면 NOT U=U, true AND U=U, false AND U=false, true OR U=true, false OR U=U다. WHERE에는 true만 남는 규칙을 마지막에 적용한다. 예를 들어 score>=90 OR score IS NULL은95인 행과 NULL인 행을 모두 남기는 명시적 정책이다.

중간 과정을 따라가는 예제

X/Y의 UNION과 UNION ALL의 행 수를 구하고 Score에서 score=NULL, score IS NULL, score>=90 OR score IS NULL의 출력 id를 구하라.

  1. UNION ALL은 X3+Y3=6행이다. 80 세 번,95 한 번,NULL 두 번이다.

  2. UNION은 반복을 지워80,95,NULL의3종류다.

  3. score=NULL은 모든 행에서 미상이라 출력0행이다. IS NULL은 id4만 참이다.

  4. score>=90 OR score IS NULL은 id2에서 true OR false=true, id4에서 U OR true=true라2와4를 남긴다.

집합 합침3종류, 중복 합침6행. 세 필터 출력은 각각 없음/4/2와4다. ORDER BY 없으므로 id2와4의 출력 순서는 지정하지 않는다.

종이와 본문으로 직접 해보기

다섯 번째 행의 점수도 NULL로 추가했다. DISTINCT score의 종류 수와 IS NULL의 행 수를 구하고 NOT(score>=90)의 출력 id를 적어라.

힌트 보기

중복 제거의 NULL 한 종류와 NULL 조건의 두 실제 행을 구별한다.

풀이 보기

DISTINCT score는 여전히80,95,NULL의3종류다. IS NULL은 id4와5의2행이다. NOT(score>=90)은 id1/3만 true이며 두 NULL행의 NOT U는U라 제외된다.

오해와 반례

NULL은 0이므로 NULL=NULL도 참이고 DISTINCT는 SELECT의 행을 모두 같은 수로 유지한다.

미상 점수와 실제0점은 다르다. NULL=NULL의 일반 비교는U다. DISTINCT score는 id 정보를 출력하지 않아 점수80의 두 행을 합치지만 DISTINCT id,score는 고유id를 포함해 합치지 않는다.

= NULL은 true가 아닌 미상이다.

답과 이유 보기

전자는 이미 거짓인 조건, 후자는 이미 참인 조건이 전체 판정을 결정한다.

한 단계 더

연습으로 (score>=90) IS NOT TRUE를 판정하라. 80인 두 행은 false여서 통과하고 NULL인 행은U여서도 통과한다. 이것은 NOT(score>=90)의80 두 행만 통과하는 결과와 다르다. 미상도 포함할지 정책을 먼저 쓰면 구문 선택이 명확해진다.

소단원 5.3

자료형과 식

7을 2로 나누는 같은 기호가 왜 3 또는 3.5가 될까?

준비 개념과 학습 목표

준비 개념

  • SQL 열과 식에는 자료형이 있다. PostgreSQL 18의 integer·numeric·text를 사용한다.

  • 기호의 의미는 자료형에 따라 정해진다. 입력 숫자를 글자로 쓴 것과 정수 값은 같은 표현이 아니다.

학습 목표

  • 형과 명시적 변환을 확인한 뒤 식의 값을 계산한다.

  • 가상 출력 열과 저장된 값을 구별한다.

값을 읽기 전에 형을 읽는다

PostgreSQL에서 정수끼리의 나눗셈은 소수 부분을0쪽으로 버린다. 7/2는3, −7/2는−3이다. numeric 값7.0을 나누면3.5다. 원하는 의미가 평균이나 비율이라면 한 피연산자를 명시적으로 numeric으로 바꿀 수 있다. 다른 DB의 형 추론과 나눗셈 규칙이 같다고 가정하지 않는다.

CAST(7 AS numeric)/2는 나눗셈 전에 형을 바꾸지만 CAST(7/2 AS numeric)는 이미 정수 나눗셈으로3이 된 뒤 형만 바꿔3으로 남는다. 형 변환을 어디에서 했는지도 계산 순서의 일부다. 정밀 소수 numeric과 근사 부동소수 real/double precision은 저장 의미가 다르다.

한 행씩 만드는 식

읽을 표 Item(id integer,qty integer,price numeric)를 (1,3,12.50),(2,2,8.00)으로 정하자. SELECT qty*price AS subtotal은 각 행의 수량과 단가를 곱하여37.50과16.00의 가상 출력 열을 만든다. 저장된 qty/price는 바뀌지 않으며 AS는 출력 이름이다.

괄호는 의도를 드러낸다. 수량이2이고 추가분이3이라면 (qty+3)*price와 qty+3*price는 다르다. 전자는 수량 합을 먼저 곱하고 후자는 곱셈이 먼저다. 수량 단위와 화폐 단위를 섞어 더하는 식이 업무 의미까지 맞는지도 별도로 검토한다. SQL이 식을 계산한다고 해서 모델이 타당하다는 뜻은 아니다.

SELECT CAST(7 AS numeric)/2 AS ratio;
SELECT id, qty*price AS subtotal
FROM Item
ORDER BY id;

NULL과 표시 정책

산술 입력이 NULL이면 이 단원의 덧셈·곱셈 식도 NULL이다. 아직 수량을 모르는 행의 qty*price가0매출이라는 뜻은 아니다. COALESCE(qty,0)는 NULL을0으로 대체하는 별도 정책이며 미상과 실제0을 구분할 필요가 있다면 원래 NULL을 보존한다.

문자 리터럴은 작은따옴표를 사용하여 예를 들어 SELECT '7' AS label은 텍스트 표시를 만든다. 이를 정수 계산에 쓰려면 CAST('7' AS integer)처럼 의도를 밝힐 수 있다. 'seven'을 integer로 변환할 수 있다고 가정하면 안 된다. 숫자처럼 보이는 이름·우편번호도 선행0을 보존해야 한다면 문자로 모델링한다.

중간 과정을 따라가는 예제

7/2, CAST(7 AS numeric)/2, CAST(7/2 AS numeric), −7/2를 비교하고 두 Item행 subtotal을 구하라.

  1. 정수7/정수2=3이고 −7/2=−3이다. 소수부분을0쪽으로 버리므로 −4가 아니다.

  2. 나눗셈 전 CAST는7numeric/2=3.5다. 나눗셈 후 CAST는3을numeric으로 바꿔3이다.

  3. Item1은3×12.50=37.50, Item2는2×8.00=16.00이다.

  4. 이 계산은 행별 결과다. 합53.50을 얻는 집계는 뒤 단원의 별도 질의로 다룬다. 출력 소수 표시 자릿수는 클라이언트가 달리 보여 줄 수 있다.

값은3/3.5/3/−3, 행별subtotal37.50/16.00이다. 본문은 SQL 실행 로그가 아니다.

종이와 본문으로 직접 해보기

qty=2,price=4.50에서 (qty+3)*price와 qty+3*price를 계산하라. qty=NULL일 때 qty*price와 COALESCE(qty,0)*price의 의미를 비교하라.

괄호와 곱셈 우선순위를 따르며 NULL 대체는 별도 정책이다.

풀이 보기

오해와 반례

숫자를 나눈 뒤 형을 바꾸면 소수 부분이 되살아나고 SELECT 식은 원본 값을 갱신한다.

정수 나눗셈이 버린 소수 부분은 사후 CAST로 돌아오지 않는다. 예제의3을numeric으로 바꾸어도3이다. SELECT qty*price는 결과 열을 계산하며 UPDATE와 같은 저장 변경이 아니다.

한 단계 더

이름에 숫자가 들어 있어도 학번 같은 식별자는 덧셈 대상이 아니다. 예를 들어 '0012'를integer로 변환하면 값12가 되어 표시상의 선행0 정보가 사라진다. 각 열을 정할 때 무엇을 계산하고 무엇을 보존할지 적어 보자. 결제의 반올림 규칙·통화별 최소 단위는 이 단원 산술만으로 확정하지 않는다.
