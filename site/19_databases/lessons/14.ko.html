역할·최소권한

책의 재고를 조회하는 프로그램에 회원 주소를 지울 권한까지 필요할까?

준비 개념과 학습 목표

준비 개념

  • 표와 열

  • SELECT와 UPDATE

  • 참과 거짓

학습 목표

  • 열 권한과 행 정책의 차이를 설명한다

  • 허용 시험과 거부 시험을 함께 설계한다

업무에서 권한을 거꾸로 도출하기

최소권한은 맡은 일을 수행하는 데 필요한 접근만 주는 설계 원칙이다. 먼저 누가 어떤 자원에서 어떤 행동을 해야 하는지 쓴다. 조회 화면, 반납 처리, 구조 변경은 다른 업무이므로 같은 관리자 계정을 공유할 이유가 줄어든다. 역할은 이 업무별 권한 묶음이다. 사용자 인증이 성공했다는 사실만으로 모든 자료를 열람할 수 있다는 결론은 나오지 않는다.

실제 PostgreSQL 18은 GRANT와 REVOKE로 객체 권한을 관리한다. 열 단위 권한도 가능하며 기존 값을 조건이나 계산에 사용하는 UPDATE에는 SELECT 권한도 필요할 수 있다. 아래 예제는 이미 연결과 스키마 접근이 가능하고 추가 권한 경로가 없다는 자체 모형이다. 실제 설치에서는 소유자, 상속, PUBLIC, 함수와 뷰를 통한 경로까지 따로 조사해야 한다.

열과 행은 다른 축이다

열 제한은 어떤 종류의 정보를 읽는지를 정한다. 행 제한은 같은 표 안에서 누구의 자료를 읽는지를 정한다. 예를 들어 반별 대출 표에서 담당 반의 책 이름만 보도록 하려면 두 축을 함께 생각한다. SELECT 권한만 있어도 모든 행이 업무상 적절한 것은 아니다.

PostgreSQL의 행 보안은 일반 객체 권한에 더해 적용된다. 활성화한 표에 적용 정책이 없으면 일반 사용자는 기본적으로 행을 볼 수 없다. 소유자는 보통 우회하며 superuser와 BYPASSRLS 역할은 우회한다. 따라서 관리자 계정으로 성공한 시험을 일반 사용자의 경계 시험으로 대신하면 안 된다. 이 단원은 설정을 실제로 바꾸지 않고 조건을 종이로 판정한다.

성공뿐 아니라 거부를 확인하기

허용 시험은 정상 업무가 막히지 않는지 확인한다. 거부 시험은 다른 열, 다른 반, 삭제, 구조 변경과 같은 업무 밖 접근이 막히는지 확인한다. 권한을 줄였다는 변경 기록과 실제 거부 결과는 다른 증거이다. 배포 뒤 역할이 다른 경로로 권한을 얻으면 과거의 시험을 다시 확인해야 한다.

요청이 거부되어도 자료가 일부 바뀌지 않아야 한다는 조건을 별도로 세운다. 한 서비스가 여러 사람을 대신해 DB에 접속한다면 DB 역할 이름만으로 최종 사용자가 누구인지 알 수 없다. 응용 계층의 인증과 권한 검사를 DB의 경계와 연결해서 설계해야 한다.

중간 과정을 따라가는 예제

자체 대출 표는 id·반·책·상태·연락처 열을 가진다. 조회 역할 R은 id·반·책·상태만 SELECT한다. 처리 역할 W는 이 네 열의 SELECT와 상태의 UPDATE만 가진다. 둘은 소유자·superuser가 아니며 다른 권한 경로가 없다. 행 정책은 담당 반 A의 기존 행과 변경 후 행만 허용한다. 요청 ① R이 A반 책 조회, ② R이 A반 연락처 조회, ③ W가 A반 상태 변경, ④ W가 B반 상태 변경, ⑤ W가 A반 행 삭제를 판정하라.

  1. ①은 책 열 SELECT와 A반 행 조건을 모두 만족하므로 허용한다.

  2. ②는 행 조건이 맞아도 연락처 열 SELECT가 없어 거부한다.

  3. ③은 조건에 쓰는 id·반의 SELECT와 상태 UPDATE가 있고 변경 후에도 A반이므로 허용한다.

  4. ④는 열 권한이 있어도 B반 행 조건을 만족하지 않아 대상 행을 처리하지 못한다. ⑤는 DELETE 권한이 없다.

정책상 허용은 ①·③ 두 요청, 비허용은 ②·④·⑤ 세 요청이다. 실제 DB 오류 문구나 영향 행 수를 실행한 결과가 아니라 명시한 모형의 판정이다.

종이와 본문으로 직접 해보기

W의 업무에 반 이동은 없다. 상태 변경을 위해 UPDATE ALL을 주자는 제안과 상태 열만 주자는 제안을 비교하라. 추가로 R이 A반 자료와 B반 자료를 각각 요청하는 두 시험을 작성하라.

개인정보·데이터 품질

준비 개념과 학습 목표

준비 개념

  • NULL

  • CHECK와 기본키

  • 개수와 비율

학습 목표

  • 업무에 필요한 데이터와 불필요한 식별 정보를 구별한다

  • 제약 통과와 실제 사실의 정확성을 구별한다

수집 목적과 노출 범위를 함께 적기

개인정보는 표의 한 열에만 머물지 않는다. 조회 결과, 내려받은 파일, 로그, 백업으로 복제될 수 있다. 도서별 대출 횟수를 세는 업무라면 연락처 원문을 매 조회 기록에 덧붙일 필요가 있는지 먼저 질문한다. 필요한 목적·접근 대상·유지 기간·삭제 경로를 자료 흐름과 함께 정한다. 이 종이 설계는 실제 제도나 법률 준수를 인증하지 않는다.

이름을 임의 번호로 바꾸어도 원래 사람과 연결하는 표가 남으면 연결 가능성이 남는다. 합계로 바꾼 작은 집단도 다른 자료와 결합해 추론될 수 있다. 표시 이름을 감췄다는 사실과 익명성이 보장됐다는 주장을 구별한다. 연습에는 실제 사람의 자료 대신 가상 표를 사용한다.

DB 제약은 품질의 일부를 자동화한다

제약은 자료가 정한 형식을 위반하지 않도록 돕는다. 기본키는 식별자 중복과 NULL을 막고, 외래키는 연결 대상을 확인하며, CHECK는 값 조건을 검사한다. 그러나 입력한 반 이름이 실제 반인지, 측정값이 실제로 정확한지는 별도 근거가 필요하다. 형식상 유효한 거짓 정보도 제약을 통과할 수 있다.

PostgreSQL에서 CHECK의 결과가 NULL이면 위반으로 거부되지 않는다. 따라서 CHECK(횟수 >= 0)만으로 누락된 횟수를 막았다고 해석하면 안 된다. 누락을 금지하려면 NOT NULL 같은 조건을 별도로 결합한다. 모르는 값이 0과 같다는 가정으로 채우면 총계의 의미도 달라진다.

지표는 행과 조건을 고정해서 계산한다

완전성은 필요한 값이 있는지, 일관성은 서로 맞는지, 정확성은 사실과 일치하는지를 다른 질문으로 본다. 오류 셀 수와 오류 행 수는 다르다. 한 행에 두 문제가 있어도 오류 행은 하나다. 제외한 행을 분모에서 빼는 순간 비율의 대상이 달라지므로 원래 입력 전체와 사용 가능한 자료를 함께 기록한다.

OWASP는 로그에 비밀번호·토큰·민감한 개인 자료를 직접 남기지 않도록 안내한다. 감사에 필요하다는 이유로 원본 내용을 모두 복제하면 노출 범위가 커진다. 가상 요청 식별자, 대상 종류, 성공 여부처럼 목적에 맞는 요약을 고려하고 로그 자체의 접근도 제한한다.

중간 과정을 따라가는 예제

가상 네 행은 A:(id=1, 횟수=2), B:(id=2, 횟수=NULL), C:(id=2, 횟수=-1), D:(id=4, 횟수=0)이다. NULL 금지·횟수 0 이상·id 중복 금지를 품질 목표로 삼는다. 품질 검사는 기존 표의 진단이며 삽입 순서의 DB 결과를 뜻하지 않는다. 모든 중복 그룹의 행을 표시하는 규칙으로 문제 행과 중복률을 구하라.

  1. 누락 횟수는 B 한 행이며 1/4 = 25%다. 음수 횟수는 C 한 행으로 역시 25%다.

  2. id=2인 B와 C 모두 중복 그룹에 속한다. 중복 그룹 소속 행 비율은 2/4 = 50%다. 추가 복제 행 수를 세는 다른 지표는 1개이며 혼용하지 않는다.

  3. 문제 행의 합집합은 B와 C 두 행이다. 조건별 문제 행 수 1+1+2=4를 오류 행 4개로 해석하지 않는다.

  4. A와 D 두 행만 모든 진단 조건을 만족한다. 그 합계는 2+0=2다. 원래 네 행은 누락이 있고 음수도 있으므로 이 값을 원래 전체의 신뢰할 만한 총계라고 부르지 않는다.

목표를 모두 만족한 행은 2/4 = 50%, 문제 행도 50%다. 진단 규칙과 분모를 기록하고 원자료를 근거 없이 자동 수정하지 않는다.

종이와 본문으로 직접 해보기

B의 NULL을 0으로 바꾼 후보 표를 평가하라. 중복 id는 그대로다. CHECK(횟수 >= 0)만 있는 경우와 NOT NULL도 있는 경우, 원래 B가 들어올 때의 차이를 설명하라.

풀이 보기

임의 0 채움은 누락 표시만 없애며 중복 B·C와 음수 C는 남아 목표 통과 행은 여전히 A·D 두 행이다. 실제 횟수가 0이었다는 증거는 생기지 않는다. 원래 NULL은 CHECK만으로 거부되지 않지만 NOT NULL이 있으면 거부된다. 이것은 해당 조건의 판정이며 전체 스키마의 실제 삽입 실행은 아니다.

오해와 반례

누락을 0으로 채우고 이름을 지우면 품질과 개인정보 문제를 모두 해결했다.

0은 실제 수량 주장이라서 누락을 감출 수 있다. 연결 가능한 번호와 원본·로그·백업도 남을 수 있다. 품질 근거와 노출 경로를 따로 확인한다.

이 설계에서는 남기지 않는다.

진단 목적에 비밀번호 원문이 필요하지 않고 비밀의 복제 경로를 만든다.

한 단계 더

가상 표에 측정 시각과 출처를 추가해 최근성·근거 여부를 따로 진단하라. 어떤 오류를 자동으로 거부하고 어떤 의심 값을 사람의 확인으로 보낼지 설명한다. 실제 개인정보를 수집하는 활동은 하지 않는다.

스키마 변경과 감사

열 이름 하나를 바꾸면 예전 프로그램도 계속 작동할까?

준비 개념과 학습 목표

준비 개념

  • 스키마

  • 트랜잭션

  • 변경 기록

학습 목표

  • 프로그램 버전과 표 구조의 호환 조건을 적는다

  • 확장·이행·정리의 순서를 자체 사례로 추적한다

  • 요청·DDL 종료·커밋·감사 기록의 차이를 설명한다

자료 구조도 사용자를 가진 인터페이스다

스키마 변경은 새 프로그램뿐 아니라 기존 프로그램, 보고서와 배치 작업에 영향을 준다. 열을 없애거나 뜻을 바꾸면 SQL 문장이 실행되더라도 결과 해석이 달라질 수 있다. 누가 어떤 열을 읽고 쓰는지 목록을 만든 뒤 변경 전후 계약을 비교한다.

자체 이행 전략으로 새 열을 먼저 추가하고 기존 값에서 의미를 보존해 채우며, 새 프로그램이 새 열을 사용하도록 바꾼 뒤 오래된 사용자가 없다는 근거를 확인하고 구열을 정리할 수 있다. 두 열을 유지하는 기간에는 모든 쓰기 경로의 동기화 조건도 필요하다. 순서만 적었다고 동시 변경이나 장애 문제가 자동 해결되지는 않는다.

자료 검증과 운영 영향을 따로 확인하기

새 제약을 추가할 때는 과거 행도 조건에 맞는지 확인한다. PostgreSQL 18의 NOT VALID는 지원되는 제약에서 과거 자료 검사를 미루지만 새 삽입·갱신의 검사는 적용한다. 과거 자료 전체가 통과했다는 결론은 이후 검증이 성공해야 얻는다. 모든 종류의 제약에 같은 옵션을 쓸 수 있는 것은 아니다.

ALTER TABLE의 잠금과 자료 재작성 여부는 구체적 동작에 따라 다르다. 작은 가상 표에서 계산이 맞는 것과 실제 큰 표에서 서비스가 버티는 것은 다른 검증이다. 시험에는 실패 시 중단 조건, 복구 자료, 이전 버전과의 호환, 실제 잠금·지연 관찰을 추가한다. 여기서는 실제 DB 변경을 수행하지 않는다.

감사는 결과와 신뢰 범위를 기록한다

감사 기록에는 누가 어떤 변경 식별자와 대상에 어떤 동작을 요청했고 어떤 결과를 얻었는지를 남긴다. 요청 로그는 성공 증거가 아니다. PostgreSQL의 ddl_command_end는 DDL 이후이지만 트랜잭션 커밋 전이다. 그 뒤 롤백되면 변경이 확정됐다고 말할 수 없다. 사건 트리거는 지원 사건의 관찰 수단이며 모든 자료 읽기와 실패·공유 객체 변경을 빠짐없이 기록하는 장치로 일반화하지 않는다.

로그 작성자와 삭제 가능한 관리자를 구별하고 누락·변조를 어떻게 탐지할지 정한다. 감사를 위해 비밀이나 모든 행 원문을 무조건 남기지 않는다. 변경 버전, 대상, 검사 요약, 요청·완료 상태와 필요한 연결 식별자를 목적에 맞게 남긴다. 실제 보관 정책과 운영 시험 없이 감사 완성을 선언하지 않는다.

중간 과정을 따라가는 예제

자체 표의 기존 amount 값은 id 1·2·3 순서로 12·0·7이다. v1은 amount만 읽고 쓴다. v2는 cents를 읽고 쓴다. 새 뜻은 cents=100×amount다. 설치 없이 다음 상태를 추적한다: A는 구열만 존재, B는 새열 추가 후 모두 채웠고 모든 쓰기가 두 열을 같은 뜻으로 원자 갱신, C는 v1 사용자가 없다는 근거를 확인해 구열 제거. 각 상태의 읽기 호환성과 값 검산을 판단하라.

  1. A에서 v1은 amount를 읽지만 cents가 없는 v2는 계약을 만족하지 못한다.

  2. B에서 cents는 1200·0·700이며 합은 1900이다. v1·v2 모두 각자 열을 읽을 수 있다. 두 열 관계가 이후 쓰기에도 유지된다는 가정이 필요하다.

  3. B에서 id 1을 amount=15로 바꾸면 같은 원자 갱신의 cents=1500이어야 한다. 합은 1500+0+700=2200이다. amount만 바꾸면 이행 불변식이 깨진다.

  4. C는 cents만 있으므로 v2는 읽을 수 있고 v1은 실패한다. 구열 제거는 이전 프로그램이 남지 않았다는 근거 뒤에 수행한다.

읽기 호환은 A에서 v1만, B에서 둘 다, C에서 v2만이다. 가상 값·원자 이중 쓰기 가정을 검산한 것이며 실제 무중단 이행 성공을 뜻하지 않는다.

종이와 본문으로 직접 해보기

변경 M7의 가상 사건은 요청 10:00, DDL 종료 10:02, 롤백 10:03이다. 변경 M8은 요청 10:04, DDL 종료 10:05, 커밋 확인 10:06이다. 종료 사건만 센 보고서는 성공 2개라고 한다. 확정 변경 수와 보고서의 문제를 설명하고 B에서 v1이 남았는데 구열을 먼저 지우는 반례를 적어라.

힌트 보기

종료 이벤트 시점과 트랜잭션 확정은 다르다.

풀이 보기

명시된 이력에서 확정 변경은 M8 한 개다. M7은 종료 뒤 롤백되어 확정되지 않았다. 사건 2개를 성공 2개로 바꾸는 분모·상태 해석이 잘못됐다. B에서 구열을 없애면 v1의 amount 읽기와 쓰기가 계약을 만족하지 못한다. 실제 프로그램 실행이나 감사 수집 시험은 아니다.

오해와 반례

DDL 종료 로그가 있으면 스키마 변경은 커밋됐고 감사도 완전하다.

종료 뒤 롤백 가능성이 있다. 수집 범위·실패 기록·누락·변조와 커밋 상태를 확인해야 한다. 하나의 관찰 수단을 모든 사건의 완전한 증거로 삼지 않는다.

자기점검

과거 행 검사 없이 제약을 추가했다면 모든 과거 행이 유효한가?

답과 이유 보기

그 결론은 아직 없다.

검사를 미룬 자료는 별도 검증 성공이 필요하다.

B에서 id 3을 amount=8로 바꿀 때 cents=700을 유지해도 되는가?

답과 이유 보기

안 된다. cents=800이어야 한다.

자체 계약 cents=100×amount를 보존해야 한다.

C에서 v1의 성공을 기대할 수 있는가?

답과 이유 보기

아니다.

v1이 요구하는 구열이 제거됐다. 버전 퇴역 근거가 먼저 필요하다.

새열 채우기 도중 중단되면 어떤 행이 완료됐는지 확인하는 가상 체크 목록을 설계하라. 완료 표시만 있고 값 불변식이 틀린 경우도 넣는다. 실제 이행 시간과 잠금 위험은 실행하지 않았으므로 숫자로 단정하지 않는다.
