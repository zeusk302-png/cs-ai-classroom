소단원 1.1

파일 처리의 한계

같은 학생의 연락처가 세 수강 명단에 복사되어 있다면 하나만 고쳤을 때 무엇이 진짜 정보일까?

준비 개념과 학습 목표

준비 개념

  • 파일은 이름으로 찾을 수 있는 저장 데이터다. CSV는 행과 구분자로 값을 표현하는 텍스트 형식이지만 관계·권한·거래 규칙을 자동 제공하지 않는다.

  • 표는 같은 속성 열을 가진 행의 모음이다. 식별자는 이름이 같은 사람도 구별하도록 부여한 값이며 이번 예에서는 학번이 학생을 유일하게 구별한다.

  • 트랜잭션은 하나의 논리적 작업으로 함께 성공하거나 취소되어야 하는 데이터 연산 묶음이다. 원자성은 그 묶음의 일부만 완료된 상태가 결과로 남지 않도록 하는 성질이다.

학습 목표

  • 파일 저장과 데이터 관리 책임을 구별한다.

  • 중복·무결성·동시 갱신·장애 문제를 작은 상태 추적으로 설명한다.

  • DBMS를 쓴다고 응용 규칙이 자동 결정되는 것은 아님을 설명한다.

도서 두 권을 한 번에 빌린다고 했는데 한 권만 기록되면 성공한 것일까?

대출 가능 도서 A,B와 회원 M을 종이에 적자. 업무 규칙은 두 권 묶음 신청이면 둘 다 대출하거나 둘 다 대출하지 않는 것이다. A의 대출을 기록한 뒤 B가 이미 대출 중임을 발견하면 A 기록도 취소해야 한다. 파일 형식의 정확성, 도서 ID의 유일성, 묶음 작업의 원자성은 각각 다른 관리 책임이다.

파일을 두 개로 나누면 공통 사실의 중복을 줄일 수 있지만 관계가 저절로 강제되지는 않는다. 도서(A,제목),(B,제목)와 대출(M,A)를 나눠도 없는 도서 Z의 대출 행이 들어갈 수 있다. 도서 ID 유일성·대출의 참조·동시에 한 도서를 둘에게 주지 않는 규칙·취소의 범위를 따로 정해야 한다. DBMS는 이런 규칙을 표현하고 강제할 수단을 제공하지만 어떤 규칙이 업무에 맞는지는 설계자가 결정한다.

실패 시점도 구별한다. 확정 전에 두 번째 변경이 실패하면 전체 묶음의 취소가 필요하다. 반면 정상 확정 뒤 다른 사람이 같은 도서를 신청했을 때에는 현재 대출 상태에 따라 거절해야 한다. 종이 상태의 일부 변경을 지웠다는 계산은 저장장치 정전 복구나 여러 사용자의 실제 경쟁 시험을 했다는 증거가 아니다.

먼저 확인할 개념

  • 불변량과 규칙

    같은 도서의 중복 사용을 막는 조건을 모든 전이에 적용한다.

1. 저장한 데이터와 관리하는 소프트웨어

데이터베이스는 일정한 의미와 관계를 가진 데이터 모음이고 DBMS는 그 데이터의 정의·조회·갱신·권한·동시 작업·복구를 관리하는 소프트웨어다. DBMS도 내부적으로 파일을 사용할 수 있다. 따라서 “파일이냐 DB냐”의 차이는 파일 존재 여부가 아니라 누가 공통 관리 규칙을 제공하는가에 있다.

행을 읽고 쉼표로 나누는 프로그램만으로 학생 명단을 처리할 수도 있다. 작은 읽기 전용 목록이라면 충분할 수 있다. 하지만 여러 프로그램이 같은 데이터와 규칙을 공유하면 각 프로그램에 파싱·검증·잠금·복구를 중복 구현하는 부담이 늘어난다. 어떤 규모에서 DBMS가 필요하다는 고정 숫자보다 작업·실패·공유 요구사항을 먼저 본다.

2. 복사된 사실과 끊어진 관계

수강 행마다 학번·이름·연락처·과목을 저장하면 학생 한 명의 사실이 여러 번 복사된다. 연락처 일부만 수정하면 같은 학번에 두 연락처가 남는 갱신 이상이 생긴다. 마지막 수강 행을 지우면서 학생 연락처도 함께 사라지면 삭제 이상이며, 수강하지 않는 학생을 저장할 자리가 없으면 삽입 이상이다.

학생(학번,이름,연락처)과 수강(학번,과목)을 분리하면 연락처를 한 곳에 저장할 수 있다. 그러나 두 파일로 나누기만 해서는 존재하지 않는 학번의 수강 행이 사라지지 않는다. 학번 유일성, 수강의 학번이 학생에 존재해야 한다는 참조 규칙, 학생 삭제 정책을 명시하고 강제할 책임이 남는다. 분해의 일반 조건은 이후 정규화 단원에서 다룬다.

3. 동시에 고치거나 중간에 멈출 때

잔여 좌석 1을 두 요청 A,B가 모두 읽고 각각 0을 쓰면 두 사람을 받아 놓고 좌석 표시는 0이 될 수 있다. 올바른 데이터 형식만으로 이 경쟁을 막지 못한다. 읽기·판단·쓰기 전체를 적절한 동시성 제어 아래 처리해야 한다. 무조건 트랜잭션으로 묶었다는 말만으로 모든 격리 이상이 사라지는 것은 아니며 격리 수준과 연산 패턴을 정해야 한다.

계좌 두 개를 10씩 이체하는 논리 작업에서 출금 뒤 중단되어 입금이 사라지면 합계가 변한다. DBMS의 원자성·복구 지원은 이런 일부 변경을 관리한다. 실제 보장은 제품 설정과 저장장치·장애 모델에도 의존한다. 스키마 제약과 올바른 트랜잭션을 선언하지 않으면 DBMS가 사용자의 의도를 알아서 추론하지 않는다.

  1. 기존 파일의 첫 행만 고치면 S1의 연락처가 수학 행에서는 010-C, 논리 행에서는 010-A가 된다.

  2. 학생 표를 (S1,민아,010-C),(S2,준,010-B)로 만든다. 수강 표는 (S1,수학),(S1,논리),(S2,수학)으로 연락처를 빼고 학번 연결을 남긴다.

  3. 수학 수강생 연락처 요청은 수강에서 과목=수학인 S1,S2를 고르고 학생 표의 같은 학번을 연결한다.

  4. 학생마다 유일한 학번이고 수강 학번이 학생에 존재한다고 가정했으므로 연락처 두 개를 얻는다.

수학 명단은 S1의 010-C와 S2의 010-B다. 연락처 수정은 학생 행 하나지만 참조 규칙은 두 표 사이에 계속 필요하다.

  2. 이번 변경은 A의 기록뿐이며 B=N은 이전부터 있었다.

A는 없음으로 돌아가고 B=N은 유지한다.

오해와 반례

DBMS만 설치하면 중복과 잘못된 데이터가 자동으로 사라진다.

DBMS가 있어도 학번 유일 제약을 선언하지 않으면 같은 학번 행을 넣을 수 있는 설계가 된다. 한 학생을 연락처별로 복사하는 스키마도 그대로 존재할 수 있다. DBMS는 규칙을 구현할 수단을 주지만 올바른 모델·제약·거래 경계는 설계자가 정한다.

준비 개념과 학습 목표

준비 개념

  • 스키마는 행의 속성·타입·관계·제약을 정한 구조 설명이고 인스턴스는 특정 시점의 실제 데이터다. 같은 스키마에 서로 다른 인스턴스가 들어갈 수 있다.

  • 질의는 원하는 데이터를 요청하는 표현이다. 뷰는 기본 데이터에서 정의한 질의 결과를 이름 있는 인터페이스로 제공하는 방식이다.

  • 매핑은 한 계층의 표현을 다른 계층의 표현으로 연결하는 규칙이다. 데이터 독립성은 하위 표현이 바뀌어도 그 위의 약속을 유지할 수 있는 성질이다.

학습 목표

예전 화면을 유지했다는 증거는 열 이름이 같다는 것뿐일까?

회원 기본 표에 M1,M2,M3의 ID와 이름이 있고 연락 표에 M1의 연락 두 개, M2는 없음, M3는 하나 있다고 하자. 기존 화면의 약속이 회원당 정확히 한 행이면 두 표의 내부 조인은 M1 두 행·M3 한 행을 만든다. 총 세 행이라는 수는 같지만 M2를 잃고 M1을 중복해 기존 인터페이스와 다르다.

외부 인터페이스는 열 이름만이 아니라 행의 대상·중복·누락값·단위·순서와 권한 같은 의미를 포함한다. 연락처가 없는 회원도 표시한다면 외부 조인을 고려할 수 있지만 M1의 두 연락처는 여전히 정책이 필요하다. 기본 연락을 하나 고르는 명시 규칙 또는 여러 연락처를 보여 주는 새 인터페이스를 정해야 한다. 단순히 첫 행을 고르면 정렬 약속이 없을 때 결과가 달라질 수 있다.

물리적 독립성은 논리 값과 질의 의미를 유지하면서 인덱스나 저장 배치를 바꿀 수 있는 성질이다. 논리적 독립성은 개념 구조의 변경을 매핑으로 흡수하는 성질이다. 연락 두 개를 허용하는 새 개념은 화면의 기존 한 행 계약을 유지할 조건이 필요하다. 반응 시간과 실행 계획까지 같은 것은 이 독립성의 약속이 아니다.

1. 같은 데이터의 세 설명

외부 스키마는 특정 사용자나 응용이 보는 형태다. 개념 스키마는 데이터베이스 전체의 논리 구조와 제약이고 내부 스키마는 파일·페이지·인덱스 등 저장 표현이다. 예를 들어 공개 명단은 (학번,이름)만 보이고 개념 구조에는 연락처까지 있으며 내부에서는 학번 인덱스로 행을 찾을 수 있다. 데이터 세 벌이 항상 따로 존재한다는 뜻은 아니다.

이 세 스키마는 데이터 표현 수준을 나눈 설계 관점이다. 브라우저·응용 서버·DB 서버의 네트워크 3계층과 혼동하지 않는다. 실제 DBMS는 파서·계획기·실행기·저장 관리자·트랜잭션 관리자 등을 협력시키며 세 스키마를 완전히 분리한 세 프로세스로 실행할 필요도 없다.

2. 물리적 독립성은 어떤 약속을 보존할까

학생 행이 파일의 어느 위치에 있는지 응용이 직접 기억하면 행 이동마다 응용을 고쳐야 한다. 학번과 논리 열 이름으로 질의하고 저장 접근을 DBMS에 맡기면 순차 저장에서 인덱스 저장으로 바꾸어도 같은 조건·같은 데이터에 대해 같은 의미의 결과를 얻을 수 있다. 이것이 물리적 데이터 독립성의 목표다.

독립성이 시간·읽은 페이지 수·실행 계획까지 같다는 뜻은 아니다. 인덱스 추가는 오히려 그런 비용을 바꾸려는 작업이다. 또한 SQL의 ORDER BY 없는 결과에는 행 순서 보장이 없다. 저장 구조 변경 후 화면 순서가 달라도 원래 순서를 요구하지 않은 질의의 결과 계약이 깨진 것은 아니다. 필요한 표시 순서를 명시해야 한다.

3. 논리적 독립성과 인터페이스의 한계

학생(학번,이름,연락처)을 학생기본(학번,이름)과 학생연락(학번,연락처)으로 나누더라도 기존 뷰가 같은 열과 값을 제공하도록 매핑을 바꾸면 기존 조회 응용을 유지할 수 있다. 각 학번의 연락처가 정확히 하나 존재한다는 조건이 있어야 단순 연결이 기존 행을 빠뜨리거나 늘리지 않는다. 논리적 데이터 독립성은 개념 스키마 변화의 영향을 외부 인터페이스에서 흡수하는 성질이다.

모든 변경이 자동 흡수되는 것은 아니다. 이름 열을 삭제하여 복원할 정보가 없거나 연락처 의미를 다른 단위로 바꾸면 호환 뷰만으로 같은 의미를 보장할 수 없다. 조회 뷰가 읽기 호환을 제공해도 갱신 가능성·권한·오류 계약은 별도로 검토해야 한다. 이 단원은 논리적 경계에 집중하고 인덱스·복구 엔진 구현은 뒤 과목에서 다룬다.

관계형·비관계형 모델 비교

학생의 수강 과목을 표의 연결로 저장할까, 학생 문서 안의 목록으로 저장할까?

준비 개념과 학습 목표

준비 개념

  • 데이터 모델은 어떤 구조·관계·제약·연산으로 데이터를 표현할지 정하는 개념 집합이다. 스키마는 특정 데이터에 적용한 그 구조의 설명이다.

  • 집합은 같은 원소의 중복과 순서를 구별하지 않는다. 관계모델의 릴레이션은 속성 값으로 이루어진 튜플의 집합이며 SQL 표의 동작과 완전히 같지는 않다.

  • 문서는 이름 있는 필드와 중첩된 값·목록을 담는 단위다. 키-값 모델은 키로 값을 찾고 그래프 모델은 노드와 간선의 연결을 직접 표현한다.

학습 목표

  • 관계·문서·키-값·그래프 모델을 같은 정보로 비교한다.

  • 관계의 수학적 집합과 SQL의 중복·NULL·순서 동작을 구별한다.

  • 모델 선택을 조회·변경·제약·일관성 요구에 연결한다.

복사된 가격이 다르면 항상 잘못 저장한 것일까?

현재 상품 P의 가격을 120으로 저장하고 주문 O1에는 주문 당시 가격 100, O2에는 당시 가격 120을 기록하자. 주문 가격은 과거 계약의 사실이고 상품 가격은 현재 판매 조건이다. 두 값이 다르다는 이유로 O1을 120으로 고치면 오히려 과거 계약을 바꾼다. 중복처럼 보이는 값도 어떤 시점의 사실인지 먼저 정한다.

반대로 주문 화면에 현재 상품명을 보여 주기로 약속했는데 상품명을 주문마다 복사하면 이름 변경 때 여러 곳의 갱신 책임이 생긴다. 주문 당시 이름을 보존하는 정책이라면 변경하지 않는 것이 맞다. 관계형 표에도 과거 가격을 주문 행에 담을 수 있고 문서형에도 현재 상품 ID를 참조할 수 있다. 모델 이름보다 읽기·변경·기록 보존의 의미가 먼저다.

주문 문서 안의 품목 묶음은 주문 한 개를 함께 읽기 편할 수 있지만 모든 주문의 재고 변경까지 그 문서 하나의 원자 변경으로 처리되는 것은 아니다. 상품 공통 재고와 여러 주문이 다른 문서라면 여러 대상의 작업 경계를 따로 설계한다. 단일 문서 원자성 지원을 시스템 전체 모든 변경의 원자성으로 확대하지 않는다.

먼저 확인할 개념
  • 데이터 모델의 기본 비교

    관계·문서·참조의 표현 선택을 읽기와 변경 요구에 연결한다.

  • 상태와 기록할 정보

    현재 상태와 과거 사건의 정보가 다른 목적을 갖는다는 점을 확인한다.

1. 관계형 모델은 표 모양 이상이다

관계형 모델은 이름 있는 속성과 각 속성의 값 범위, 튜플의 집합 및 그 관계에 수행하는 연산을 중심으로 데이터를 표현한다. 학생과 과목과 수강 관계를 나누어 식별자로 연결하면 한 과목의 제목을 한 곳에서 관리하고 새로운 조합 질의를 만들기 쉽다. 관계모델의 구조·무결성·조작 개념을 함께 본다.

수학적 릴레이션의 동일 튜플은 하나이고 행 순서는 없다. SQL은 기본적으로 중복 행을 다루며 NULL과 세 값 논리도 사용한다. 키 제약과 DISTINCT, ORDER BY 등을 어떻게 선언하느냐에 따라 동작이 달라진다. “표이므로 줄 번호가 학생 식별자” 또는 “SQL은 항상 수학적 집합”이라고 생각하면 설계와 결과를 잘못 이해할 수 있다. 여기서 NULL은 값이 없거나 알려지지 않았음을 나타내는 표지다. 일반 비교에서 NULL과의 비교는 true/false 대신 unknown이 될 수 있다. NULL=0이나 NULL=빈 문자열이라는 뜻은 아니며 IS NULL 같은 검사를 별도로 쓴다.

2. 비관계형은 하나의 고정 모델이 아니다

문서 모델은 학생 한 문서에 수강 과목 목록을 넣는 식으로 함께 읽는 정보를 가까이 묶을 수 있다. 키-값 모델은 student:S1 같은 키에 값을 대응시켜 알려진 키 조회를 표현한다. 그래프 모델은 학생 노드와 과목 노드를 수강 간선으로 연결해 연결 경로 탐색을 표현할 수 있다. NoSQL이라는 이름만으로 이들의 연산·제약·저장 구현이 같아지지는 않는다.

문서 안에 과목 제목까지 복사하면 학생 한 명의 상세 화면을 읽기 편하지만 제목 변경을 여러 문서에 반영할 수 있다. 과목 ID만 참조하면 복사를 줄이는 대신 과목 조회와 연결 책임이 생긴다. 문서의 유연한 필드도 스키마 설계가 필요 없다는 뜻은 아니다. 응용이 필요한 필드·타입과 제품의 스키마 검증을 정해야 한다.

3. 질문의 모양과 변경의 약속으로 고른다

모든 학생의 공통 과목 통계처럼 다양한 연결·집계 질의가 중요한지, 학생별 묶음을 주로 읽는지, 그래프의 다단계 경로를 주로 묻는지 요구를 적는다. 독립적인 사실의 중복, 한 변경이 영향을 주는 범위, 필요한 제약을 비교한다. 정답은 데이터가 크다는 한 문장만으로 정해지지 않는다.

모델 이름만으로 ACID 지원·분산 확장·속도·장애 보장을 단정할 수 없다. 문서 DB에도 트랜잭션 기능을 제공하는 제품이 있고 관계형 DB도 분산 배치될 수 있다. 구체적인 지원과 비용은 제품·연산·설정·업무 부하에 따라 확인해야 한다. 이 단원은 종이 데이터 모델의 의미 비교이며 제품 성능 경쟁이나 설치 실습이 아니다.
