소단원 8.1

CTE·재귀 질의

질의 안에서 이름을 붙인 중간 결과가 자기 자신을 쓸 수 있을까?

준비 개념과 학습 목표

준비 개념

  • SELECT·WHERE

  • UNION ALL

학습 목표

  • CTE의 범위를 설명한다.

  • 재귀 질의의 초기·반복·종료를 추적한다.

CTE는 질의 안의 이름이다

WITH는 복잡한 질의를 여러 이름 있는 중간 결과로 나눈다. CTE 이름은 해당 문장 안에서 사용하며 영구 테이블 생성과 다르다. 앞에서 정의한 CTE를 뒤의 CTE나 주 질의가 참조할 수 있다.

CTE를 썼다고 항상 별도 임시 저장이나 속도 향상을 보장하지 않는다. PostgreSQL은 조건에 따라 비재귀·부작용 없는 CTE를 주 질의와 합칠 수 있고 MATERIALIZED 선택은 별도 비용을 가진다.

초기 행 뒤에 반복 행을 붙인다

WITH RECURSIVE의 비재귀 항이 처음 working table을 만든다. 재귀 항은 그 단계 working table에서 다음 행을 만들고 그것을 다음 working table로 바꾼다. 비면 끝난다.

UNION ALL은 중복을 보존한다. UNION은 이전 출력과 중복되는 전체 행을 제거한다. id가 같아도 depth가 늘면 서로 다른 전체 행이라 순환 방지에 실패할 수 있다.

종료와 정렬은 별도다

숫자 상한이나 경로의 방문 여부 등 종료 조건을 설계한다. 그래프 순환에는 경로 기록이나 CYCLE을 고려한다. 부모 LIMIT만으로 무한 재귀를 안전하게 처리한다고 일반화하면 안 된다.

결과 표시 순서는 최종 ORDER BY로 정한다. 재귀 평가가 어떤 순서로 내부 방문하는지와 출력 정렬은 별개다.

중간 과정을 따라가는 예제

PostgreSQL 의미로 WITH RECURSIVE t(n) AS (VALUES (1) UNION ALL SELECT n+1 FROM t WHERE n<4) SELECT n FROM t ORDER BY n; 의 행을 종이에 구하자.

  1. 초기 working table은 {1}이고 결과에 1을 넣는다.

  2. 다음 단계는 {2},{3},{4}이며 각각 결과에 추가한다.

  3. {4}에서는 n<4가 거짓이라 다음 집합이 비고 종료한다. 최종 정렬은 1,2,3,4다.

결과 네 행과 합 10이다. 이는 실제 DB 실행 결과 기록이 아닌 의미론 손계산이다.

출력에 증가하는 depth가 있으면 전체 행이 계속 새로워 중복 제거만으로 끝나지 않을 수 있다.

소단원 8.2

윈도 함수

전체 합계를 각 행 옆에 써도 원래 행은 남을까?

준비 개념과 학습 목표

준비 개념

  • GROUP BY

  • 정렬과 동률

학습 목표

  • 집계와 윈도의 행 수를 구분한다.

  • partition·frame·최종 정렬을 구별한다.

윈도는 원래 행을 보존한다

SUM(v) OVER (...)는 관련 행을 보고 계산하되 각 행의 정체성을 남긴다. GROUP BY의 그룹별 한 행으로 압축하는 집계와 다르다. PARTITION BY는 계산 집단을 정한다. 생략하면 전체가 한 집단이다.

OVER 안 ORDER BY는 윈도 계산 순서다. 화면의 최종 순서까지 보장하지 않으므로 주 질의 ORDER BY가 별도로 필요하다.

ROWS와 기본 frame의 차이

누적 합을 행별로 하려면 유일한 정렬 키와 ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW를 명시할 수 있다. 각 위치까지의 행을 포함한다.

PostgreSQL에서 ORDER BY가 있는 기본 frame은 현재 값과 같은 peer도 포함한다. 동률 점수만 정렬하면 두 동률 행이 같은 누적 합을 받는 경우가 있다. row_number의 동률 내부 번호는 보조 키 없이는 확정되지 않는다.

계산 뒤 필터는 바깥에서 한다

윈도는 FROM/WHERE/GROUP BY/HAVING 결과를 본다. 먼저 WHERE로 제거한 행은 윈도에 보이지 않는다. 계산된 row_number를 같은 수준 WHERE에서 바로 쓸 수는 없다.

CTE나 서브질의에서 윈도 값을 만든 뒤 바깥 WHERE에서 rn<=2처럼 필터한다. 원본에서 먼저 필터하는 것과 계산 후 필터하는 것은 다른 의미다.

중간 과정을 따라가는 예제

같은 반의 id/점수는 (1,10),(2,10),(3,20)이다. ORDER BY score,id의 ROWS 누적 합과 ORDER BY score만 쓰는 기본 frame 합을 구하자.

  1. 유일 키 (score,id)의 ROWS 누적은 10,20,40이다.

  2. score만 정렬한 기본 frame에서 점수 10의 peer 두 행은 함께 포함돼 둘 다 합 20을 받는다. 점수 20 행은 합 40이다.

  3. SUM(score) OVER ()는 정렬 없이 전체를 대상으로 하므로 세 행 모두 40이다.

ROWS 누적 합은 id 순서로 10/20/40, peer 기본 frame 합은 20/20/40, 전체 합은 각 행에 40이다. 행 수는 모두 3이다.

힌트 보기

풀이 보기

id 3의 한 행만 남고 합 20이다. 전체 합 40을 계산한 뒤 바깥에서 id 3만 고르는 것과 다르다.

오해와 반례

OVER 안 ORDER BY면 최종 표시 순서도 확정된다.

계산 순서와 결과 표시 순서는 별개다. 최종 SELECT에 ORDER BY를 명시해야 한다.

소단원 8.3

분석 질의와 결과 검산

총액이 두 배가 되면 매출 증가일까, 조인 중복일까?

준비 개념과 학습 목표

준비 개념

  • LEFT JOIN

  • NULL·COUNT

학습 목표

  • 집계 단위와 조인 배수를 확인한다.

  • NULL과 가중 평균을 검산한다.

한 행이 무엇인지 먼저 정한다

주문마다 한 행인 orders와 주문 항목마다 한 행인 lines를 결합하면 주문 총액이 항목 수만큼 반복된다. 주문 단위 금액을 그대로 합산하면 조인 배수에 따라 과대 합계가 나온다.

항목 금액을 합할지 주문 금액을 합할지 목표를 정하고 그 단위에서 먼저 집계한다. SUM(DISTINCT amount)는 서로 다른 주문의 우연히 같은 금액을 제거할 수 있어 일반적인 해결이 아니다.

NULL을 0과 구별한다

COUNT(*)는 행 수, COUNT(amount)는 non-null 금액 행 수다. AVG와 SUM도 non-null 값을 본다. 관측되지 않은 금액을 자동으로 0이라고 해석하면 평균 분모가 바뀐다.

빈 입력의 SUM은 PostgreSQL에서 NULL이다. COALESCE로 0을 표시하는 것은 보고서의 별도 정책이며 원래 관측이 존재했다는 증명이 아니다. LEFT JOIN에는 매칭 없는 부모도 남아 COUNT(*)와 자식 id 개수가 다를 수 있다.

그룹 평균을 그대로 평균내지 않는다

집단 크기가 다르면 집단 평균의 단순 평균은 전체 관측 평균과 다르다. 전체 합을 전체 non-null 수로 나누거나 집단 평균을 관측 수로 가중한다.

원본 행 수, non-null 수, 그룹별 합, 전체 합을 나란히 검산하면 오류 위치를 찾기 쉽다. 필터의 시간 범위·통화·중복 id까지 확인해야 실제 보고서 의미가 정해진다.

중간 과정을 따라가는 예제

금액은 반 A의 10,20과 반 B의 30,NULL이다. 실제 관측 전체 평균을 구하자. 별도로 주문 X=100에 항목 2개, Y=50에 항목 1개를 조인한 합도 검산하자.

  1. 금액 행은 4개, non-null 금액은 3개, 합은 60이다. AVG는 60/3=20이고 A 평균은 15, B 평균은 30이다.

  2. 그룹 평균의 단순 평균은 (15+30)/2=22.5다. 관측 수로 가중하면 (15×2+30×1)/3=20이다.

  3. 조인 후 주문 금액은 100,100,50으로 합은 250이다. 주문 단위 원래 합은 150이므로 항목 중복을 제거한 단위에서 합해야 한다.

전체 관측 평균 20, 잘못된 그룹 평균 22.5, 잘못된 조인 합 250과 올바른 주문 합 150이다.

풀이 보기

오해와 반례

SUM(DISTINCT 주문금액)이면 모든 조인 중복이 안전하게 해결된다.

서로 다른 두 주문이 모두 100이면 올바른 합 200이나 DISTINCT 합은 100이 된다. 주문 id 단위로 먼저 묶어야 한다.
