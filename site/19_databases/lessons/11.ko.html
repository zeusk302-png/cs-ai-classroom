소단원 11.1

ACID와 실행 이력

포인트를 옮기는 두 문장 중 하나만 성공하면 전체 포인트는 어디로 갈까?

준비 개념과 학습 목표

준비 개념

  • UPDATE와 SELECT

  • 키와 제약조건

  • commit과 rollback

학습 목표

  • ACID의 책임과 조건을 구별한다.

  • 읽기·쓰기·종료를 실행 이력으로 기록한다.

  • 직렬 실행과 직렬가능성을 구분한다.

충돌 그래프에 사이클이 없으면 실패 복구까지 안전할까?

실행 이력의 r1(X)는 거래 T1의 읽기, w1(X)는 쓰기, c1은 확정, a1은 취소를 뜻한다. 단일 버전의 추상 모형에서 w1(X), r2(X), c2, a1을 보자. T2가 T1의 미확정 값을 읽고 먼저 확정했다. 충돌 간선은 T1→T2뿐이지만 T1이 취소되면 이미 확정한 T2가 의존한 값은 사라진다.

충돌 직렬 가능성은 연산 순서의 성질이며 복구 가능성은 읽은 값의 생산 거래와 확정 순서까지 살핀다. 이 미확정 읽기 모형은 PostgreSQL의 실제 허용 이력이라는 뜻이 아니다. PostgreSQL에서는 Read Uncommitted를 지정해도 Read Committed로 동작하여 이런 더티 읽기를 허용하지 않는다.

반대로 충돌 그래프에 사이클이 있다고 모든 종류의 직렬 가능성이 사라지는 것도 아니다. 값을 읽지 않고 쓰는 blind write 모형에서는 충돌 기준보다 넓은 뷰 직렬 가능성이 있다. 최종 값 하나가 우연히 같다는 주장만으로 충분하지 않으며 최초 값 읽기, 어떤 쓰기를 읽었는지, 최종 쓰기 거래를 함께 대조한다.

여러 단계의 완료를 하나로 묶는다

트랜잭션은 관련된 데이터베이스 작업의 완료 단위다. Atomicity는 전부 반영되거나 중단되어 전부 취소되는 성질이다. Consistency는 작업 전후에 선언한 제약과 업무 불변식을 지키는 것이다. DB가 모르는 업무 규칙까지 자동으로 추측해서 고치는 것은 아니다.

Isolation은 동시 작업이 서로 어떤 상태를 볼 수 있는지의 보장이다. 모든 격리 수준이 직렬 실행과 같은 결과를 제공하지는 않는다. Durability는 성공적으로 확정한 효과의 보존이다. 저장장치·복구 및 설정의 보장 범위도 확인한다. PostgreSQL의 비동기 commit 설정은 성공 응답 뒤 최근 효과가 장애로 사라질 수 있어 기본 동기 commit과 구별한다.

BEGIN만 쓰는 것보다 경계가 중요하다

명시 BEGIN 뒤 필요한 작업을 수행하고 모두 만족하면 COMMIT한다. 실패나 규칙 위반이면 ROLLBACK한다. SQL 문장이 성공했다는 사실과 업무 작업 전체를 성공적으로 commit했다는 사실은 다르다. 예상한 행이 실제 갱신되었는지와 제약을 확인하는 흐름도 필요하다.

PostgreSQL에서는 BEGIN 없이도 각 문장에 암묵적 트랜잭션이 붙는다. 그러나 두 UPDATE가 각각 commit되면 두 문장을 하나의 원자적 이체로 묶은 것이 아니다. 데이터베이스 rollback이 이미 발송한 이메일이나 다른 외부 서비스 요청을 자동으로 되돌리지도 않는다. 외부 효과의 연계는 별도 설계 주제다.

실행 이력은 명령의 끼어듦을 기록한다

읽기 r1(A), 쓰기 w1(A), 확정 c1, 중단 a1처럼 트랜잭션 번호를 붙여 실행 순서를 적으면 어느 값에서 계산했는지 볼 수 있다. 직렬 실행은 한 트랜잭션이 끝난 뒤 다음 것을 시작한다. 직렬가능 실행은 명령이 끼어들어도 허용된 관측과 최종 효과가 어떤 직렬 순서와 같은 실행이다.

같은 객체에 접근하는 서로 다른 트랜잭션의 두 동작 중 하나 이상이 쓰기면 충돌을 생각한다. 앞선 충돌에서 뒤 작업으로 화살표를 그리는 충돌 그래프는 충돌 직렬가능성의 검사다. 고리가 없으면 위상 순서가 있고, 고리가 있으면 그 검사에 실패한다. 이 검사는 commit/abort와 복구 안전성을 전부 대신하지 않는다.

추상 이력을 서로 다른 기준으로 읽는다
이력충돌 간선별도 확인판정

w1(X),r2(X),c2,a1

T1→T2

T2가 취소한 T1의 값을 읽고 확정

충돌 직렬 가능하나 복구 불가능

w1(X=1),w2(X=2),w1(X=3)

T1→T2와 T2→T1

읽기 없음, 최종 쓰기는 T1

충돌 직렬 불가, 뷰 기준은 별도

단일 버전 이론 모형이다. 쓰기 값과 읽기 의존성을 명시하며 PostgreSQL 실행 결과로 해석하지 않는다.

중간 과정을 따라가는 예제

초기 포인트 A=50, B=20이다. T1이 A에서10을 빼고 B에10을 더하는 이체를 수행한다. T2는 합계를 조회한다. 초기 값은 가상 정수이고 기존 두 행은 존재한다고 하자.

  1. 정상 완료 목표는 A=40, B=30이며 합은70이다.

  2. T1 안의 중간 상태에서 A40/B20이라도 아직 확정되지 않은 변화 전체를 다른 일반 조회가 이체 완료 상태처럼 봐서는 안 된다.

  3. 두 문장을 묶어 commit하면 새 확정값은40/30, rollback하면50/20이다.

  4. 반대로 첫 UPDATE만 별도로 commit하고 둘째가 실패하면40/20 합60이 남는다. 문장별 트랜잭션은 업무 전체 원자성을 제공하지 않는다.

  5. T2가 두 개의 별도 SELECT를 실행하면 낮은 격리에서는 이체 전 A50과 이체 후 B30을 섞어 합80으로 볼 수도 있다. 이는 미확정값을 본 것이 아니라 서로 다른 확정 스냅숏을 섞은 것이다.

업무 이체는 하나의 완료 단위로 묶어야 한다. 원자성만으로 모든 다중 문장 조회의 일관된 시점을 보장하지 않는다.

조건을 바꾸어 비교하기

직렬 순서와 복구 조건을 나눈다

w1(X),r2(X),c2,a1의 충돌 그래프와 확정 의존성을 구하라.

  1. 다른 거래의 같은 X에서 쓰기와 읽기가 충돌한다.

  2. 간선 T1→T2는 사이클이 없다.

  3. T2는 T1의 값을 읽었지만 T1보다 먼저 확정했고 T1은 취소했다.

충돌 직렬 가능성과 복구 불가능성이 함께 나타나는 추상 이력이다.

비교할 점

그래프의 비순환성만 검사하면 취소된 값의 의존성을 놓친다.

blind write의 뷰 기준을 확인한다

w1(X=1),w2(X=2),w1(X=3)을 직렬 T2→T1과 비교하라.

  1. 앞선 w1과 w2는 T1→T2, w2와 뒤 w1은 T2→T1을 만든다.

  2. 읽기 연산이 없어 읽기 출처 조건은 없다.

  3. 직렬 T2→T1에서도 최종 쓰기 거래는 T1이다.

충돌 직렬 가능하지 않지만 이 읽기 없는 이력은 T2→T1과 뷰 동등하다.

비교할 점

충돌 기준의 실패와 모든 직렬 가능성의 실패를 같은 말로 쓰지 않는다.

종이와 본문으로 직접 해보기

초기 X=10이고 T1은X에2를 더한다. T2는X를3배 한다. 직렬 T1→T2와 T2→T1의 결과를 구하라.

힌트 보기

각 작업은 앞 작업의 최종값을 읽고 갱신한다고 둔다.

풀이 보기

T1→T2는(10+2)×3=36, T2→T1은10×3+2=32다. 직렬가능 결과가 항상 하나의 값이라는 뜻은 아니다. 어떤 직렬 순서와 일치하는지가 중요하다.

오해와 반례

트랜잭션을 사용하면 모든 업무 규칙과 외부 동작까지 자동으로 맞는다.

잘못된 금액을 올바르게 commit하는 프로그램도 만들 수 있다. 필요한 제약·업무 검증·격리 수준을 정해야 하며 이메일 같은 외부 효과는 DB rollback의 대상이 아니다.

연습 1 · 값과 상태 예측

w1(X),r2(X),c1,c2는 앞선 복구 불가능 이력과 무엇이 다른가?

힌트 1

누가 누구의 값을 읽는지 유지한다.

힌트 2

생산 거래의 확정이 소비 거래 확정보다 앞서는지 본다.

풀이와 답 확인

  1. T2는 여전히 미확정 값을 읽었다.

  2. 하지만 c1이 c2보다 먼저 온다.

복구 가능하지만 연쇄 취소를 피하는 이력은 아니다. 더티 읽기가 없다는 뜻도 아니다.

흔한 오답에서 다시 생각하기

복구 가능하면 언제나 미확정 읽기가 없다.

확정 순서 조건과 미확정 값을 읽지 않는 조건은 다르다.

연습 2 · 오류 찾아 고치기

사이클이 없는 그래프를 근거로 c2,a1 이후 T2의 값을 안전하다고 했다.

힌트 1

간선은 확정 순서를 대신하지 않는다.

힌트 2

T2가 읽은 값의 생산 거래를 찾는다.

풀이와 답 확인

  1. T2가 읽은 쓰기 T1은 취소되었다.

복구 조건을 추가로 검사해야 한다. 이 추상 이력을 PostgreSQL 실제 재현이라고 기록하지 않는다.

흔한 오답에서 다시 생각하기

읽기 출처는 결과 숫자만 같으면 무시해도 된다.

다른 값을 읽었을 때 업무 결정과 후속 쓰기도 바뀔 수 있다.

연습 3 · 직접 만들어 보기

읽기 의존성 T1→T2가 있는 이력에서 복구 가능 조건과 연쇄 취소 방지 조건을 각각 적어라.

힌트 1

생산 거래 확정과 소비 거래 확정을 비교한다.

힌트 2

소비 거래의 읽기 시점도 따로 본다.

풀이와 답 확인

  1. 복구 가능성은 T2 확정 전에 T1의 확정을 요구한다.

  2. 연쇄 취소 방지는 T2가 T1의 값을 읽기 전에 T1의 확정을 요구한다.

두 조건의 시간 경계가 다르며 뒤 조건이 더 강하다.

흔한 오답에서 다시 생각하기

c1이 c2 앞이면 r2도 c1 뒤였다고 자동 결론 난다.

확정 순서만으로 앞선 읽기 시점을 바꿀 수 없다.

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

두 번 읽었는데 값이 바뀌었다면 DB가 잘못된 것일까, 선택한 규칙일까?

준비 개념과 학습 목표

  • write skew와 재시도 필요성을 설명한다.

반복 가능한 스냅샷이면 자신의 변경도 안 보일까?

PostgreSQL Repeatable Read는 다른 거래의 나중 확정을 같은 거래의 후속 질의에 자동 반영하지 않는다. 그러나 자신의 앞선 변경은 본다. 처음 X=10,Y=20을 읽은 T1이 X를 11로 바꾸고 그 사이 T2가 Y=30을 확정해도 T1은 X=11,Y=20을 읽을 수 있다. 다른 거래의 가시성과 자신의 변경 가시성을 나눠야 한다.

여러 거래가 서로 다른 행을 바꾸더라도 전체 조건을 깨뜨릴 수 있다. 방 R의 예약이 0개인지 각자 같은 스냅샷에서 확인하고 서로 다른 예약 ID를 넣는 두 거래는 같은 행 갱신 충돌이 없을 수 있다. 예약 ID의 유일성만으로 방·날짜의 독점 예약을 보장하지 않는다.

Serializable은 성공하여 확정한 거래들이 직렬 실행과 맞도록 감시하지만 성공을 모두 보장하지 않는다. serialization failure가 나면 읽기와 업무 결정을 포함한 거래 전체를 새 거래로 재시도한다. 이전 판단을 그대로 들고 마지막 INSERT만 반복하는 것은 새 상태에서 조건을 다시 검사하는 재시도와 다르다.

무엇이 달라졌는지를 분류한다

dirty read는 다른 작업의 미확정 변경을 읽는 것이다. nonrepeatable read는 같은 행을 다시 읽었을 때 다른 작업의 commit 때문에 값이 달라지는 현상이다. phantom read는 같은 조건 조회를 반복했는데 조건에 맞는 행 집합이 바뀌는 현상이다.

serialization anomaly는 성공적으로 확정된 작업들을 어떤 직렬 순서로 놓아도 관측과 효과가 일치하지 않는 경우다. 같은 행 재조회가 안정적이라고 모든 업무 규칙이 안전해지는 것은 아니다. 서로 다른 행을 각각 쓰는 작업의 읽기 의존성도 살펴야 한다.

표준의 이름과 구현의 스냅숏을 함께 본다

SQL 격리 이름은 최소 보호 수준을 나타내며 제품이 더 강한 보호를 줄 수 있다. PostgreSQL18의 Read Uncommitted는 Read Committed처럼 동작해 dirty read를 허용하지 않는다. PostgreSQL Read Committed의 일반 SELECT는 문장 시작 시 확정 상태와 자기 트랜잭션의 앞선 변경을 본다.

PostgreSQL Repeatable Read는 첫 비트랜잭션 제어 문장이 만든 스냅숏을 유지한다. 다른 작업의 이후 commit 때문에 같은 일반 조회 결과가 바뀌지 않고 phantom도 막는다. 하지만 직렬가능 이상은 남을 수 있다. 이 이름만 보고 다른 DB의 Repeatable Read 구현까지 동일하다고 가정하면 안 된다.

같은 스냅숏을 읽어도 서로 다른 행을 쓸 수 있다

당직자 두 명이 모두 근무 중이고 적어도 한 명은 남아야 한다고 하자. 각각 다른 사람이 남아 있다고 읽고 자기 행만 휴무로 바꾸면 같은 스냅숏에서도 둘 다 떠나는 write skew가 생길 수 있다. 동일 행 쓰기 충돌만 막는 것으로 충분하지 않다.

PostgreSQL Serializable은 읽기/쓰기 의존성을 감시해 직렬 순서와 맞지 않는 확정 조합을 막는다. 충돌이면 일부 작업을 serialization failure로 중단할 수 있어 애플리케이션은 전체 트랜잭션을 처음부터 다시 실행해야 한다. 중단된 결과를 확정값처럼 사용자에게 발표하거나 마지막 UPDATE만 반복하는 방식은 원래 판정을 다시 수행하지 않는다.

중간 과정을 따라가는 예제

당직 행 A=true,B=true다. T1은 두 행을 읽어 B가true면 A=false로 쓴다. T2는 두 행을 읽어 A가true면 B=false로 쓴다. 같은 초기 스냅숏을 읽고 다른 행에 쓰며 PostgreSQL Repeatable Read로 실행하는 이론 일정이다.

  1. T1은 B=true라 A를 false로 바꾸기로 결정한다.

  2. T2는 같은 초기 A=true라 B를 false로 바꾸기로 결정한다.

  3. 서로 다른 행을 쓰므로 이 일정은 둘 다 commit될 수 있고 결과false/false가 된다.

  4. 직렬 T1→T2에서는 T2가 A=false를 읽어 B를 유지한다. 직렬 T2→T1에서는 T1이 B=false를 읽어 A를 유지한다.

  5. 따라서 둘 다false 결과는 두 직렬 순서 모두와 맞지 않는다. Serializable로 같은 의존성 일정이면 이 조합의 모두 성공을 막고 재시도가 필요하다.

안정된 스냅숏에도 업무 불변식이 깨지는 write skew다. 두 직렬 순서에서는 각각 한 명이 남는다.

조회 결과가 0행이면 앞으로 들어올 행도 잠겼을까?

PostgreSQL의 SELECT FOR UPDATE는 선택한 기존 행을 잠근다. Read Committed에서 방·날짜의 예약을 조회했는데 0행이면 잠글 예약 행도 없다. 그 질의만으로 다른 거래의 같은 조건 INSERT를 막았다고 생각하면 안 된다. 존재하는 행 잠금과 아직 없는 업무 대상의 보호는 다르다.

대기열에서 SKIP LOCKED는 지금 잠글 수 없는 행을 건너뛴다. A가 가장 오래된 작업이고 다른 거래가 A를 잠갔으며 B는 잠기지 않았다면 B를 가져올 수 있다. 모든 후보가 잠겼다면 빈 결과여도 미완료 작업이 없다는 뜻은 아니다. 일반 조회의 완전한 결과나 엄격한 선입선출 보장으로 사용하지 않는다.

잠금의 수명도 종류별로 다르다. 거래 수준 advisory lock은 거래 끝에 해제되지만 세션 수준 advisory lock은 rollback만으로 해제되지 않는다. advisory lock은 참여 코드가 같은 규약을 사용해야 효과가 있다. 행 잠금·업무 유일 조건·세션 잠금의 경계를 명시해 복구 경로를 설계한다.

스냅숏은 보이는 버전을 고른다

MVCC는 여러 버전과 트랜잭션의 가시성 규칙으로 읽을 값을 결정한다. 일반 SELECT는 단순히 현재 물리 메모리에 가장 최근 기록된 값을 읽는 것이 아니다. PostgreSQL18에서 일반 읽기와 행 쓰기는 버전 관점에서 서로를 막지 않을 수 있다.

그래도 잠금이 전혀 없다는 뜻은 아니다. 행을 쓰는 작업끼리는 충돌할 수 있고 SELECT FOR UPDATE는 명시적으로 행을 잠근다. DROP/TRUNCATE 같은 ACCESS EXCLUSIVE 테이블잠금은 일반 SELECT도 막는다. MVCC의 읽기/쓰기 장점을 모든 종류의 명령에 대한 무대기 보장으로 확대하지 않는다.

읽은 값을 오래 들고 있다가 덮어쓰지 않는다

stock=5를 두 작업자가 일반 SELECT로 읽고 각각4를 계산해 UPDATE stock=4를 보내면 낮은 격리에서 낡은 계산이 덮어써 최종4가 될 수 있다. 행 업데이트 자체에 잠금이 있어도 외부에서 계산한 옛 값의 의미까지 DB가 보정하는 것은 아니다.

PostgreSQL Read Committed에서 UPDATE stock=stock-1 WHERE stock>0는 동시 갱신을 기다린 뒤 새로운 행 버전의 조건과 연산을 적용한다. 두 요청이 모두 성공하면5→4→3이다. 영향을 받은 행 수가0이면 조건이 맞지 않아 갱신되지 않은 것이므로 성공한 예약으로 처리하면 안 된다. 이것은 특정 단일행 조건 갱신의 설명이며 여러 행의 복잡한 업무 규칙까지 해결하는 공식은 아니다.

잠금은 끝날 때까지의 약속이다

SELECT FOR UPDATE는 조회한 행의 충돌 갱신·잠금을 트랜잭션이 끝날 때까지 기다리게 한다. Read Committed에서는 기다린 작업이 앞 작업 commit 뒤 갱신된 버전을 읽고 잠글 수 있다. Repeatable Read나 Serializable에서는 스냅숏 이후 변경된 행을 잠그려다 실패할 수 있어 격리 규칙도 확인한다.

여러 행을 잠그는 작업들이 서로 반대 순서를 쓰면 교착할 수 있다. PostgreSQL은 교착을 탐지해 관련 트랜잭션 하나를 중단하지만 어느 것이 중단될지에 의존해서는 안 된다. 같은 객체 순서, 짧은 트랜잭션, 전체 재시도 설계를 사용한다. 사용자가 버튼을 누를 때까지 열린 트랜잭션을 오래 잡는 방식은 다른 작업을 계속 기다리게 할 수 있다.

중간 과정을 따라가는 예제

PostgreSQL18 Read Committed, stock=5인 한 행이다. T1이 SELECT FOR UPDATE로5를 읽어 잠근 뒤 stock=4로 갱신한다. T2도 같은 행에 SELECT FOR UPDATE를 시도한다. T1이 먼저 commit한 뒤 T2가 새 값을 읽어1을 빼고 commit한다. 다른 작업은 없다.

  1. T1이 행을 잠그므로 T2의 충돌 잠금 요청은 기다린다.

  2. T1의 4가 commit되면 T2는 새 버전 4를 잠그고 읽는다.

  3. T2가 새 4에서 1을 빼어 3을 쓰고 commit한다. 최종 stock=3이다.

  4. T1의 행잠금 동안 다른 일반 SELECT는 테이블의 배타적 잠금이 별도로 없는 경우 확정 옛버전5를 읽을 수 있다. FOR UPDATE와 일반 SELECT는 다르다.

잠금 아래에서 확인하고 갱신하면 이 일정은5→4→3이다. 일반 읽기는 미확정4를 읽는 대신 가시적인 버전을 본다.

조건을 바꾸어 비교하기

없는 행 조회는 독점권이 아니다

T1과 T2가 같은 방·날짜에서 FOR UPDATE를 실행해 각각 0행을 받았다. 업무 유일 조건은 없다.

  1. 반환된 기존 예약 행이 없다.

  2. 같은 조건으로 이후 INSERT할 가능성을 구별한다.

그 조회만으로 서로의 INSERT가 금지되었다고 결론 낼 수 없다.

  • 빈 조회가 보호하지 않는 대상을 밝힌다.

  • 실제 실행하지 않은 동시 거래를 검증했다고 쓰지 않는다.

  • PostgreSQL 18 — Transaction Isolation

    실제 23–68,90–104,109–148행의 RU=RC·문장별 스냅샷·자신의 변경·Repeatable Read·전체 거래 재시도와 Serializable 중간 결과의 범위를 읽었다. 지정 이론 이력이며 서버 실행은 없다.

  • PostgreSQL 18 — Explicit Locking

    실제 29–151행의 테이블·반환 행 잠금·교착·advisory 세션 및 거래 수명을 읽었다. 없는 행의 미래 INSERT와 세션 잠금 rollback 경계를 수동 대조했다.

  • PostgreSQL 18 — SELECT Locking Clause

    실제 384–430행의 행 잠금·NOWAIT/SKIP LOCKED·일반 조회 부적합·테이블 잠금 적용 제외·LIMIT·순서 주의를 읽었다. 대기열 A/B 예는 지정 수동 모형이고 실제 소비자 실행은 없다.
