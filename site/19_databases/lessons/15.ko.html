소단원 15.1

요구사항·ER·SQL 연결

한 학생이 여러 강좌를 듣는 표에서 이름을 매번 복사하지 않으려면 어떻게 나눌까?

준비 개념과 학습 목표

준비 개념

  • 엔터티와 관계

  • PK·FK

  • 다대다 연결 테이블

  • NULL과 CHECK

학습 목표

  • 요구 문장을 엔터티·키·제약으로 변환한다.

  • 자체 등록 스키마의 보장 범위를 설명한다.

  • 조회 결과와 저장된 파생값을 구분한다.

등록 행이 중복되지 않아도 남은 자리 계산이 틀릴 수 있을까?

정원 3인 강좌에 학습자 L1만 등록되어 있고 남은 자리는 2다. L1의 재시도에서 남은 자리를 먼저 1로 줄인 다음 등록 INSERT를 ON CONFLICT DO NOTHING으로 건너뛰고 전체를 확정하면 등록은 여전히 1명인데 남은 자리는 1이다. 복합 기본키가 중복을 막아도 앞선 감소를 자동 되돌리는 것은 아니다.

등록의 업무 식별자인 (learner_id,offering_id)와 요청 식별자인 request_key를 구별한다. 같은 신청의 재전송인지, 취소 뒤의 새 신청인지, 다른 내용을 같은 키로 보낸 오류인지 판단하려면 요청의 의미와 상태를 함께 정한다. 키 문자열만 존재한다고 그 규약이 구현된 것은 아니다.

정원 일치의 명세는 remaining=capacity−활성 등록 수다. 어떤 코드 경로가 카운터를 바꾸는지와 변경한 실제 등록 수를 같이 읽는다. 이 활동은 작은 상태표이며 실제 SQL·네트워크·경쟁 실행은 하지 않았다.

먼저 확인할 개념
  • ER·제약과 파생 카운터

    등록 키와 여러 행의 일치 조건을 나눈다.

  • UPDATE의 대상 행 수

    명령 오류 없이 대상이 0행일 수 있다는 본문 설명을 실제 변경 확인의 출발점으로 삼는다. RETURNING은 이 보강에서 별도로 다룬다.

서비스 규칙을 먼저 읽는다

자체 응용은 학습자와 개설 강좌, 등록 관계를 관리한다. 한 학습자는 여러 개설 강좌에 등록할 수 있고 한 강좌도 여러 학습자를 받는다. 같은 학습자가 같은 개설 강좌에 두 번 등록하는 것은 금지한다. 제목이 같아도 서로 다른 개설 강좌일 수 있으므로 title이 아니라 ID로 식별한다. 실제 사람의 개인정보 대신 연습용 ID와 표시 이름만 사용한다.

ER에서 learners와 offerings는 각각 독립 엔터티이며 enrollments는 두 ID를 연결하는 다대다 관계다. 학습자 이름을 등록 행마다 복사하면 이름 변경과 불일치가 발생한다. 개설 강좌의 capacity와 remaining은 운영 규칙의 값이며, 단순한 제목 목록과 등록 이력은 역할이 다르다. 삭제는 참조된 학습자·강좌를 곧바로 지우지 않고 거부하는 연습 정책이다.

SQL 제약이 보장하는 것

learners.id와 offerings.id는 PK이며 등록 테이블의 복합 PK는 동일 쌍 중복을 막는다. PK는 NULL도 허용하지 않으므로 두 FK 열의 NULL 등록을 따로 허용하는 스키마가 아니다. FK는 실제 존재하는 엔터티만 등록하도록 하고 ON DELETE RESTRICT는 참조가 남은 삭제를 거부한다. CHECK와 NOT NULL은 서로 다른 조건이다.

capacity>0과 0≤remaining≤capacity는 같은 행 안의 규칙이다. PostgreSQL CHECK는 NULL 결과로 필수 값 부재를 막지 못할 수 있어 NOT NULL도 둔다. 그러나 remaining=capacity−등록수라는 여러 행의 일치 조건을 이 CHECK가 보장하지는 않는다. 등록과 remaining 변경을 같은 트랜잭션·일관된 쓰기 경로로 처리하고 별도 일치 검사도 설계해야 한다.

조회와 검증을 함께 설계한다

기본 조회는 학습자 ID의 등록 강좌 제목과 강좌별 등록 수다. 조인할 키를 ER의 관계와 연결하고 동명 학습자·동명 강좌를 이름으로 합치지 않는다. 등록이 0개인 강좌도 보여야 하면 offerings에서 시작하는 LEFT JOIN을 사용하고, 없는 등록에 대해 COUNT(*) 대신 등록 키의 COUNT를 써야 한다.

아래 코드는 설치 없이 읽는 설계 예시다. 실제 SQL 엔진에서 생성·조회하지 않았으므로 실행 통과 자료가 아니다. 스키마·샘플 행·예상 결과·제약 실패 목록을 같이 기록하고 이후 실제 DB 확장에서는 dump/restore와 migration까지 확인한다.

CREATE TABLE learners (
  id integer PRIMARY KEY,
  display_name text NOT NULL
);
CREATE TABLE offerings (
  id integer PRIMARY KEY,
  title text NOT NULL,
  capacity integer NOT NULL CHECK (capacity > 0),
  remaining integer NOT NULL,
  CHECK (remaining >= 0 AND remaining <= capacity)
);
CREATE TABLE enrollments (
  learner_id integer REFERENCES learners(id) ON DELETE RESTRICT,
  offering_id integer REFERENCES offerings(id) ON DELETE RESTRICT,
  PRIMARY KEY (learner_id, offering_id)
);

중간 과정을 따라가는 예제

학습자는 1=하늘, 2=바다다. 개설 강좌 10은 capacity 2/remaining 0, 강좌 20은 capacity 3/remaining 2다. 등록 쌍은 (1,10),(2,10),(1,20)이다. 등록 수·불변식·중복 요청을 검사하라.

  1. 강좌 10의 등록 수는 2, 강좌 20은 1이다. 개설 ID로 세며 제목이 같은지 여부는 관계없다.

  2. 강좌 10은 2−2=0, 강좌 20은 3−1=2라 remaining과 맞다.

  3. (1,10)을 또 INSERT하면 복합 PK 중복으로 거부해야 한다. 학습자 99를 등록하면 FK 대상 부재로 거부해야 한다.

  4. 등록 (1,20)을 삭제했는데 remaining을 2로 그대로 두면 올바른 값 3과 어긋난다. 행 CHECK는 2≤3을 만족하므로 이 오류를 혼자 잡지 못한다.

개별 행 제약과 여러 행 일치 조건은 다르다. 정상 등록 수는 2/1이며 삭제와 남은 수 갱신은 같은 원자적 경로가 필요하다.

조건을 바꾸어 비교하기

DO NOTHING은 앞선 감소를 취소하지 않는다

표의 마지막 상태와 기대 remaining을 구하라.

  1. 등록 INSERT는 새 행을 만들지 않았다.

  2. 정원 3에서 활성 등록 수 1을 뺀다.

기대 remaining은 2인데 저장값은 1로 한 자리 부족하다.

비교할 점

중복 금지의 성공과 거래 전체 업무 일치의 성공은 다르다.

취소 후 새 신청을 구별한다

R1은 L1의 신청 성공 결과를 보존한다. 이후 L1이 취소했다. 같은 R1을 새 신청에 재사용하면 과거 응답과 현재 등록이 같은 뜻일까?

  1. 과거 신청 결과와 현재 활성 등록은 다른 시간의 사실이다.

  2. 새 신청은 새 업무 의도다.

같은 뜻이 아니다. 재전송과 새 의도를 구별하는 요청 키·상태·보존 규약이 필요하다.

비교할 점

옛 결과의 재생이 현재 상태의 재생성이라는 뜻은 아니다.

종이와 본문으로 직접 해보기

등록 없는 강좌 30(capacity 4/remaining 4)를 추가했다. LEFT JOIN에서 강좌별 COUNT(*)와 COUNT(enrollments.learner_id)는 어떤 차이가 나는가?

힌트 보기

일치하는 등록이 없어도 LEFT JOIN은 NULL 쪽을 붙인 한 행을 남긴다.

풀이 보기

강좌 30의 COUNT(*)는 조인 결과 행 1을 세어 1이다. 등록 키 COUNT는 NULL을 제외하므로 0이다. 등록 수로는 0을 사용해야 capacity−count=4와 일치한다.

오해와 반례

CHECK로 remaining 범위를 검사하면 모든 등록 수 일치가 보장된다.

범위 안의 잘못된 값 2도 통과할 수 있다. 위 삭제 후 remaining은 3이어야 한다. 등록 행 수와 파생 카운터의 일치는 별도 트랜잭션 계약이다.

무결성·동시성 테스트

마지막 한 자리를 두 사람이 동시에 신청하면 모두 성공이라고 말해도 될까?

준비 개념과 학습 목표

준비 개념

  • 트랜잭션 원자성

  • 조건부 UPDATE와 반환 행

  • 동시 실행 이력

  • 중복 등록과 rollback

학습 목표

  • 읽은 값을 그대로 덮어쓰는 결함을 추적한다.

  • 조건부 갱신과 등록을 한 트랜잭션으로 묶는다.

  • 실제 동시 시험과 순차 상태 검산을 구별한다.

성공 응답을 잃은 요청은 반드시 실패한 요청일까?

서버가 등록과 자리 감소를 확정했지만 응답이 끊겼다고 하자. 클라이언트의 시간 초과는 결과를 모른다는 뜻이며 확정 실패를 증명하지 않는다. 같은 의도의 요청 키로 결과를 확인하고 이미 확정한 변경을 새로 수행하지 않는 규약을 정한다.

멱등 처리의 구체적 약속은 API마다 다르다. 참고한 Stripe API v1은 실행이 시작된 첫 결과를 같은 키 재시도에 돌려주며 500 결과도 저장할 수 있고 키 보존·내용 대조 조건이 있다. API v2와 같은 규칙이라고 일반화하지 않는다. 여기서는 결제 API를 호출하지 않고 등록 응용의 자체 규약을 설계한다.

취소에도 실제 변경 확인이 필요하다. 등록을 삭제한 행이 한 개일 때만 자리를 한 개 되돌려야 한다. 같은 취소가 재시도되어 DELETE의 반환이 0행이면 자리를 다시 증가시키지 않는다. 등록 삭제와 카운터 갱신은 같은 거래 범위로 묶는다.

먼저 확인할 개념
  • 동시 신청과 실패 경로

    응답·확정·재시도의 상태를 나눈다.

  • 응용 예외와 거래 범위

    응답 문자열과 DB 확정 결과의 차이를 확인한다.

읽기 검사만으로는 예약되지 않는다

remaining=1을 X와 Y가 각각 읽어 모두 자리가 있다고 판단할 수 있다. 두 프로그램이 자기 계산 1−1=0을 덮어쓴 뒤 서로 다른 등록 행을 넣으면 등록은 2명인데 remaining은 0이다. 0≤remaining≤capacity라는 한 행 제약은 통과해도 정원 1이라는 응용 계약은 깨진다.

해결 설계는 자리를 확보하는 조건부 갱신과 등록 행 삽입을 같은 트랜잭션에 묶는다. 예를 들어 UPDATE offerings SET remaining=remaining−1 WHERE id=10 AND remaining>0 RETURNING id를 실행하고 반환 행이 있을 때만 INSERT한다. 0행이면 신청 실패다. 이미 읽은 값을 앱에서 계산하여 SET remaining=0으로 쓰는 방식과 다르다. 성공 응답은 COMMIT 성공 이후로 제한한다.

실패 경로도 원자적으로 되돌린다

등록 INSERT가 복합 PK 중복이나 FK 오류로 실패하면 앞의 감소를 포함한 전체 트랜잭션을 ROLLBACK한다. 감소만 커밋하거나 오류를 무시하면 자리가 새로 생기거나 사라지는 불일치가 생긴다. 취소도 실제 삭제한 등록이 있을 때만 remaining을 증가시켜야 하며 같은 트랜잭션으로 처리한다.

PostgreSQL Read Committed의 조건부 UPDATE는 같은 행의 동시 변경을 기다린 뒤 갱신된 버전의 WHERE 조건을 다시 확인한다. 여기서는 한 강좌 행의 단순 조건을 이용한 계약이다. 여러 강좌 또는 다른 행 조건을 조합하면 별도의 잠금 순서·격리 설계가 필요하다. Serializable이나 deadlock 오류의 재시도는 전체 트랜잭션을 명세대로 다시 수행해야 한다.

시나리오별 예상 상태를 먼저 적는다

검사 목록은 정상 신청, 마지막 자리 경쟁, 동일 학습자 중복, 존재하지 않는 ID, INSERT 중 오류, COMMIT 뒤 응답 유실과 재시도를 포함한다. 테스트마다 capacity, 등록 집합, remaining, 반환 결과를 대조한다. 응답 유실은 실제 커밋 여부가 불명인 상황이므로 단순 실패로 단정하지 않고 동일 신청의 결과를 확인하는 정책을 설계한다.

실제 DB 세션 둘의 동시 실행과 순차 상태 모형은 다른 증거다. 아래 연습은 잠금·조건 재평가가 적용된 순서를 종이로 추적한다. 실제 시험에서는 장벽으로 경쟁 시작점을 정하고 반복 이력을 남겨야 한다. 모든 쓰기 경로가 이 계약을 사용해야 일치가 유지되며 수동 INSERT 같은 우회 경로도 권한과 검증으로 다룬다.

중간 과정을 따라가는 예제

강좌 10의 capacity=1, remaining=1이고 등록은 없다. X와 Y는 서로 다른 학습자다. X가 먼저 조건부 UPDATE를 수행하고 INSERT·COMMIT한다. Y가 대기한 뒤 같은 UPDATE를 계속한다. 결과를 추적하라.

  1. X의 remaining>0은 참이다. 감소 후 0이 되고 반환 행이 1개다. X의 등록을 INSERT하고 COMMIT하면 등록 수 1/remaining 0이다.

  2. Y는 X가 커밋한 갱신 행에서 remaining>0을 다시 확인한다. 0>0은 거짓이므로 갱신 0행이다.

  3. Y는 INSERT하지 않고 정원 없음 결과를 반환한다. 최종 등록 수는 1로 capacity와 같다.

  4. 별도 반례에서 X의 INSERT가 오류라면 전체 ROLLBACK하여 remaining=1, 등록 없음으로 돌아간다. 이후 Y가 자리를 확보할 수 있다.

X만 성공한다. 최종 1명/남은 0이며 X가 rollback했으면 0명/남은 1이다. 실제 동시 DB 결과는 아직 미측정이다.

단일 문서의 원자성만 있으면 모든 등록 규칙이 자동 유지될까?

가상 강좌 문서에는 remaining=2와 learners=[]가 있다. 같은 학습자 L1의 재시도에서 $addToSet으로 배열 중복만 막고 $inc로 remaining을 매번 줄이면 두 호출 후 learners=[L1], remaining=0이 될 수 있다. 각 쓰기가 원자적이어도 업무 불변식은 자동으로 생기지 않는다.

개념 대안은 같은 문서의 기대 조건에 remaining>0과 L1의 미등록을 포함하고 한 갱신으로 배열 추가와 자리 감소를 묶는 것이다. 두 번째 호출은 변경 후 조건을 만족하지 않아 새 자리 소비를 하지 않도록 설계한다. 정확한 연산자·배열 조건·검증·제품 지원을 실제로 확인해야 하며 이 단원은 상태 모형만 제시한다.

가상 읽기 모형에서 강좌가 10개이고 문서마다 학습자별 화면을 위해 확인할 등록자가 20명이라면 전체 확인은 200항목이다. 학습자별 참조 조회를 따로 구성하면 다른 경로와 유지 비용이 생긴다. 문서 수나 검사 항목 수를 실제 응답시간으로 바꾸지 않고 조회·원자 범위·복구를 함께 비교한다.

먼저 확인할 개념
  • 관계형·문서형의 변경 경계

    원자 문서와 여러 문서의 일치 조건을 구별한다.

  • COUNT와 집계 대상

    행 수와 고유 대상 수를 구별하는 집계 설명을 확인하고, 배열의 고유 학습자 수와 카운터를 별도로 대조한다.

요구하는 읽기와 쓰기의 경계를 적는다

현재 응용은 학습자별 강좌 목록, 강좌별 등록자, 중복 금지와 정원 보장이 필요하다. 관계형 모델은 관계를 FK·복합 PK와 조인으로 직접 표현하고 같은 트랜잭션의 변경을 묶을 수 있다. 강좌 문서에 등록자 배열을 넣으면 강좌 한 건 조회가 단순해질 수 있지만 학습자별 목록이나 등록자의 여러 강좌를 조회하는 요구도 함께 생각해야 한다.

어느 제품이 무조건 빠르다는 비교를 하지 않는다. 자료량·분포·색인·쿼리·운영 환경을 고정한 실제 측정이 필요하다. 설계 선택은 먼저 필요한 원자성 단위, 조회 경로, 중복 허용 범위, 스키마 변경과 오류 복구를 표로 비교한다. 관계형도 비정규화할 수 있고 문서형도 스키마와 제약을 설계해야 한다.

원자성이 닿는 범위를 확인한다

MongoDB 단일 문서 쓰기는 원자적이지만 서로 다른 문서의 변경 전체가 자동으로 하나의 원자 작업이 되는 것은 아니다. 강좌 문서에 남은 자리와 등록자들을 같이 보관하고 기대 조건을 포함한 한 갱신으로 변경하는 설계라면 한 문서의 경계를 활용할 수 있다. 그러나 정확한 조건·중복 방지·크기 증가와 동시 갱신을 별도로 설계해야 한다.

학습자 문서와 강좌 문서 모두에 등록을 복사하는 설계는 여러 문서를 수정한다. 한쪽만 성공하면 양쪽 목록이 다르다. 해당 제품의 여러 문서 트랜잭션이나 보상·재조정 정책을 선택하고 오류 상태를 명세에 포함한다. NoSQL에 트랜잭션이 없다는 단정과 모든 쓰기가 자동 분산 트랜잭션이라는 단정은 둘 다 틀리다. 실제 배치와 제품의 지원 조건을 확인한다.

선택 보고에는 대안과 검증되지 않은 칸을 남긴다

자체 학습용 요구에서는 관계형의 FK·복합 PK와 트랜잭션을 직접 가르칠 수 있어 앞 스키마를 기본 선택으로 삼는다. 이는 제품별 실측 우열의 결론이 아니라 모델과 요구의 연결이다. 문서형 대안은 한 강좌의 작은 aggregate를 중심으로 읽는 요구에서 검토할 수 있지만 양방향 조회와 다중 문서 일치를 해결해야 한다.

설계 보고는 명세, 원자 변경 범위, 색인과 조회, 중복·삭제 정책, 장애 복구, migration, 측정 미수행을 적는다. 정원·등록 일치 테스트를 저장소가 바뀌어도 같은 응용 명세로 실행해야 비교가 의미 있다. 운영 데이터의 수집 범위와 권한도 스키마 설계에 포함하지만 실제 개인정보·법률 검증을 했다는 주장으로 확장하지 않는다.

지정 모형에서 일치

실제 MongoDB 문법·드라이버·배열 연산 실행은 아니다. 단일 문서 원자성과 조건 재확인 문서를 읽고 구성한 자체 모형이다.

중간 과정을 따라가는 예제

자체 대안에서 learner L1 문서의 offeringIds와 offering C1 문서의 learnerIds에 등록을 중복 저장한다. L1에는 C1을 썼고 C1 갱신 전에 오류가 났다. 현재 상태와 허용 정책을 설명하라.

  1. 초기 두 목록은 비어 있다. 첫 쓰기 후 L1.offeringIds=[C1]이고 C1.learnerIds=[]다.

  2. 학습자 화면은 등록되었다고 보지만 강좌 화면에서는 L1이 없다. 단일 문서 쓰기 각각이 원자적이어도 두 문서 전체는 일치하지 않는다.

  3. 모든 변경이 하나의 여러 문서 트랜잭션 안에서 커밋되도록 설계하면 오류 시 둘 다 이전 상태로 rollback하는 정책을 사용할 수 있다. 실제 지원·구현 조건은 제품 문서를 확인한다.

  4. 별도의 단계·보상 방식이라면 중간 pending 상태를 사용자에게 어떻게 보이는지와 재시도·재조정·중복 방지를 명세로 정한다. 첫 쓰기만 보고 최종 성공을 응답하지 않는다.

현재 중복 목록은 불일치다. 문서형이라는 이름이 문제를 해결하지 않으며 원자 범위 또는 명시적인 복구 정책이 필요하다.

한 단계 더

두 후보 설계의 조회 경로·원자성 경계·중복·복구·측정 상태를 한 표로 작성하자. 필요 보장을 놓치지 않은 뒤 실제 작은 데이터에서 성능과 기능을 비교하는 확장 과제를 계획한다.

출처와 확인 범위
  • MongoDB Atomicity and Transactions

    실제 single-document 원자성, 조건 필터, $inc, multi-document 비원자성/트랜잭션, 모델링 비용 본문을 읽었다.

    실제 CHECK/NULL, NOT NULL, UNIQUE, PK, FK와 삭제 정책 본문을 읽었다. 자체 강좌 등록 스키마에 적용했다.

정원 3인 강좌에 L1 한 명이 등록되어 있고 remaining=2다. 남은 자리를 먼저 감소시킨 뒤 중복 INSERT를 건너뛰고 확정한 결과를 구하라. 성공 응답을 잃은 경우와 취소를 두 번 보낸 경우에 필요한 상태 확인 규약을 적어라. 정원 2인 문서에서 같은 L1의 배열 중복만 막고 매번 자리를 감소시키는 정책과, 미등록 조건을 포함한 원자 갱신 모형을 비교하라.

힌트 1

실제 등록의 변화와 카운터의 변화를 따로 센다.

힌트 2

응답의 관찰, 요청의 의미, 변경 후의 조건을 각각 확인한다.

풀이와 답 확인

  1. 중복 등록은 추가되지 않아 활성 등록은 한 명이다. 저장 remaining=1은 기대값 2보다 1 작다.

  2. 응답 유실은 결과 미상으로 두고 같은 키와 같은 내용에 대응하는 확정 결과를 확인한다.

  3. 취소는 실제 삭제가 1행일 때만 자리를 증가시키고, 재시도의 삭제가 0행이면 증가시키지 않는다.

  4. 문서의 배열만 중복 방지하면 remaining=0이 되어 틀린다. 미등록 조건과 자리 조건을 포함한 지정 모형은 첫 호출 후 remaining=1을 유지한다.
