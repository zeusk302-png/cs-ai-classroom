소단원 7.1

정적·동적 타입 구분

문자와 숫자를 더하는 문제는 실행 전에 찾을 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 타입은 값에 허용된 연산을 분류한다.

  • 검사 시점과 타입 이름을 직접 쓰는지 여부는 다른 문제다.

학습 목표

  • 검사 시점을 구분한다.

  • 실행 경로와 검사 범위를 비교한다.

  • 타입 추론을 동적 타입과 혼동하지 않는다.

조건을 바꿔도 실행하지 않은 가지의 타입은 사라질까?

원본의 자체 Int/Bool 언어는 정적 if에서 조건의 타입이 Bool이고 두 결과의 타입이 같아야 한다고 요구한다. 프로그램은 flag:Bool을 받아 if flag then 10 else true를 계산한다. flag가 true인 동적 실행에서는 정수 10, false인 실행에서는 Bool 값 true를 얻는다. 각 실행이 정상 값으로 끝나도 전체 식에 하나의 결과 타입을 부여하는 정적 규칙은 이 식을 거부한다. 동적 오류가 반드시 있어야 정적 거부가 가능한 것은 아니다.

반대로 if flag then 10 else 1+true는 flag가 true이면 10을 얻지만 false이면 Int와 Bool을 더하는 연산 오류에 도달한다. 이 작은 언어의 +는 정수 두 개만 받으며 자동 변환을 하지 않는다. 첫 프로그램의 두 정상 결과 타입 차이와 둘째 프로그램의 선택 경로 오류를 별도 이유로 기록한다. 시험 성공 수만 적으면 어떤 경로와 어떤 계약을 검사했는지 사라진다.

타입 표기가 없는 let n=4 in n+1을 정적 검사하면 n의 타입은 Int이고 전체 식도 Int라고 계산한다. 이는 값을 먼저 실행하여 얻은 태그가 아니라 규칙에서 도출한 분류다. 이 검사기가 값의 요구사항까지 검증하지는 않는다. 입력 n:Int의 산술식 n+1은 음수 입력에도 정수를 만들지만 결과가 항상 양수라는 별도 요구는 만족하지 않는다. 아래 평가는 모두 종이 모형이며 실제 검사기·언어 실행·학생 시험은 미수행이다.

먼저 확인할 개념
  • 검사 시점과 모든 분기

    정적 거부와 실제 선택 경로 결과를 서로 다른 관찰로 읽는다.

  • if와 덧셈의 타입 전제

    전체 판단을 조건과 두 분기 각각의 근거로 나눈다.

값 계산과 타입 계산

자체 작은 언어에서 정수 덧셈은 정수 두 개만 받는다. 2+3은 값 5를 계산하지만 타입 검사는 Int와 Int로 결과 Int를 판단한다. 정적 검사는 실행 전 프로그램에 규칙을 적용한다.

동적 검사는 실행 중 실제 값의 종류를 확인한다. 2+true는 이 언어에서 타입 오류다. 모든 언어의 +가 같은 규칙은 아니다. 문자열 결합·자동 변환이 있는 언어에는 해당 언어 규칙을 확인해야 한다.

선택하지 않은 분기도 검사하기

if true then 2 else false를 보자. 이 작은 정적 언어의 if는 조건 Bool, 양쪽 결과 같은 타입을 요구하므로 Int와 Bool의 차이를 거부한다. 실행 경로만 보면 2를 얻어도 규칙을 만족하지 않는다.

선택한 분기만 평가하는 자체 동적 모형에서는 이 실행이 2로 끝난다. 다른 입력에서 실패할 수 있는 코드를 한 번 성공한 실행으로 안전하다고 결론내리지 않는다. 정적 검사도 언어가 정한 분석이며 모든 요구사항을 증명하는 장치는 아니다.

추론과 검사 시점은 별개

let x=2 in x+3에 타입 표기를 생략해도 정적 검사기는 x:Int를 알아낼 수 있다. 이를 타입 추론이라고 한다. 표기를 안 썼다는 사실만으로 동적 언어라고 부르지 않는다.

한 언어가 정적·동적 기능을 함께 제공할 수도 있다. 초보자는 언어 이름 암기보다 해당 표현식의 검사 규칙과 시점을 적자. 아래는 작은 모형의 종이 추적이고 실제 컴파일 결과가 아니다.

각 행의 true/false는 독립 입력이며 한 실행이 두 가지를 모두 평가하지 않는다. P는 두 실행이 모두 정상이어도 현재 정적 규칙을 어긴다. Q는 실제 오류가 있는 입력도 제시하므로 같은 거부라는 말에 다른 근거를 붙인다.

중간 과정을 따라가는 예제

동적 모형과 정적 모형에서 if true then 2 else false를 비교하라.

  1. 정적 검사는 true:Bool, 2:Int, false:Bool를 구한다.

  2. 두 분기 타입 Int와 Bool이 달라 if 규칙에 실패한다.

  3. 동적 모형은 조건 true를 평가하고 then의 2만 평가한다.

  4. 이 동적 실행의 결과는 2이며 다른 프로그램의 안전성을 보장하지 않는다.

정적 거부, 주어진 동적 실행은 2다.

조건을 바꾸어 비교하기

정적 거부와 실제 오류가 일대일 대응하지 않는다

P의 두 입력을 모두 실행해 정상 값이었다. 이를 근거로 정적 검사기의 거부가 구현 결함이라고 판단해도 될까?

  1. 현재 if 규칙은 단일 결과 타입 T를 요구한다. then 분기는 Int, else 분기는 Bool이므로 같은 T가 없다.

  2. 동적 결과인 정수 10과 Bool 값 true는 서로 다른 타입이다. 정적 거부는 지정 규칙과 모순되는 구현 증거가 아니다. 합 타입을 도입한다면 언어 규칙을 변경하는 것이다.

거부는 지정 규칙에 맞다. 동적 정상 두 결과와 정적 단일 타입 요구를 구별한다.

비교할 점

다른 언어의 union/자동변환 규칙을 현재 언어에 가져오지 않는다.

선택 가지를 늘려 시험해도 규칙 근거는 남는다

Q에서 flag가 true인 입력을 열 번 시험하여 모두 10을 얻었다. false 입력을 한 번 추가하면 무엇을 새로 알까?

  1. 기존 열 번은 같은 정상 then 가지를 반복했다. else의 1+true는 평가하지 않았다.

  2. false 입력에서는 1의 타입이 Int이고 true의 타입이 Bool이므로 +의 전제를 만족하지 않는다. 정적 검사는 입력값을 실행하지 않고도 그 전제 실패를 찾는다.

동적 열 번 성공은 모든 경로의 보증이 아니다. false 입력의 실패 이유는 분기 결과 불일치에 앞선 덧셈 타입 전제다.

연습 1 · 값과 상태 예측

R에서 flag가 true인 경우와 false인 경우의 결과 및 전체 타입을 구하라. 이어 flag를 정수 1로 바꾼 입력은 현재 계약을 만족하는가?

힌트 1

두 분기의 타입은 모두 Int다.

힌트 2

정수 1을 참으로 취급하는 규칙은 없다.

풀이와 답 확인

  1. true 입력의 결과는 10, false 입력의 결과는 3이며 R의 타입은 Int다.

  2. flag의 타입이 Int인 입력은 조건이 Bool이어야 한다는 계약을 어긴다. 현재 동적 평가도 Bool 조건을 요구한다.

정상 true 입력은 10, 정상 false 입력은 3을 반환하며 전체 타입은 Int다. 정수 조건의 거부는 별도 결과다.

흔한 오답에서 다시 생각하기

1은 다른 언어에서 참이므로 여기서도 자동 허용한다.

해당 작은 언어의 조건 규칙을 먼저 확인한다.

연습 2 · 오류 찾아 고치기

P를 고치기 위해 else의 true를 정수 1로 바꾸었다. 이를 요구사항도 보존한 수정이라고 말할 수 있을까?

힌트 1

타입 규칙 통과와 원래 결과 의미는 다른 검사다.

힌트 2

false 입력에서 관찰한 Bool 값 true와 정수 1은 다른 값이다.

풀이와 답 확인

  1. 변형은 두 분기의 타입이 Int라서 정적 검사를 통과한다.

  2. false 입력의 결과가 Bool 값 true에서 정수 1로 바뀐다. 따라서 기존 동적 관찰 전체를 보존했다고 할 수 없다.

타입 오류 해결 후보지만 사용자 결과 계약의 변경을 별도로 승인/설계해야 한다.

흔한 오답에서 다시 생각하기

정적 타입을 맞춘 수정은 모든 원래 동작을 보존한다.

형 분류 일치가 값과 결과 종류의 동일성을 증명하지 않는다.

연습 3 · 직접 만들어 보기

입력 n:Int에서 양수를 반환해야 한다. n+1 대신 if n<0 then 1 else n+1을 구성하고 n이 −2인 경우와 0인 경우의 결과 및 타입을 확인하라. <는 Int 두 개를 받아 Bool을 반환하며 정확 정수만 쓴다.

힌트 1

조건의 타입과 두 반환 분기를 각각 검사한다.

힌트 2

음수 분기와 비음수 분기의 양수 근거를 나눈다.

풀이와 답 확인

  1. n<0의 타입은 Bool이고 1과 n+1의 타입은 Int이므로 전체 타입은 Int다.

  2. n이 −2이면 결과는 1이고 n이 0이어도 결과는 1이다. 일반적으로 음수 입력에는 1을 반환하고 비음수 입력에는 n+1≥1을 반환하므로 양수 요구도 별도 논증으로 만족한다.

정적 Int와 별도 양수 증명을 함께 제시한다.

흔한 오답에서 다시 생각하기

전체 타입이 Int라는 사실만으로 양수 요구가 이미 증명된다.

원래 식 n+1은 n이 −2일 때 −1을 반환하므로 양수 요구의 반례다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

정적 if가 조건을 true 상수로 보더라도 두 분기를 검사하는 현재 규칙과, 선택 가지 타입만 허용하는 새 규칙의 차이를 설명하라. 새 규칙 전체 안전성이 자동 증명되는가?

힌트 1

현재 규칙은 값 분석을 전제로 하지 않는다.

힌트 2

검사 규칙 변경은 평가 규칙과 모든 문맥에 대한 새 증명이 필요하다.

풀이와 답 확인

  1. 현재 규칙은 if true then 10 else false를 Int와 Bool의 불일치로 거부한다. 선택 가지를 허용하는 언어를 별도로 설계할 수는 있다.

  2. 상수가 나중에 입력으로 바뀌는 문맥이나 형 변환 등 새 규칙 전체를 검토해야 한다. 한 상수 예제가 성공해도 기존 안전성 정리를 그대로 적용할 수 없다.

모형의 규칙과 증명 범위를 명시하며 실제 구현 검증으로 확대하지 않는다.

선택 가지 최적화 한 예가 성공하면 모든 새 타입 규칙도 안전하다.

전체 정리는 모든 평가/타입 규칙의 조합을 다룬다.

소단원 7.2

타입 규칙과 오류

규칙을 한 줄씩 적용하면 오류가 난 자리를 찾을 수 있을까?

준비 개념과 학습 목표

준비 개념

  • Γ는 변수 이름과 타입을 묶은 환경이다.

  • Γ⊢e:Int는 환경 Γ에서 식 e의 타입이 Int라는 판단이다.

학습 목표

  • 타입 판단을 읽는다.

  • 덧셈·if·let 규칙을 적용한다.

  • 값 오류와 타입 오류를 구분한다.

새 x의 초기값을 검사할 때 아직 보이는 x는 어느 것일까?

이 보강의 let은 비재귀적이다. let x=e1 in e2에서 e1은 기존 환경 Γ로 검사하고, 얻은 타입을 몸체 e2의 환경 맨 앞에 추가한다. 내부 let이 끝나면 바깥 환경이 유지된다. Γ={x:Int}에서 let x=(x<5) in if x then 1 else 0의 초기식은 바깥 x:Int를 사용하여 Bool이 되고, 몸체의 x는 새 Bool 바인딩을 사용한다. 같은 이름이 있어도 검사 위치마다 다른 근거다.

잘못된 검사기가 새 x:Bool을 초기식에도 미리 넣으면 x<5의 x가 Bool이 되어 정당한 식을 거부할 수 있다. 반대로 몸체에 바깥 x:Int만 쓰면 조건 x를 거부한다. 환경은 값을 저장하는 실행 환경이 아니라 이름과 타입의 대응이다. 실제 평가에서 바깥 x가 4이면 결과는 1, x가 8이면 결과는 0이지만 전체 타입은 두 경우 모두 Int다.

함수 적용 규칙도 모든 전제를 확인한다. 자체 단순 타입은 Int, Bool과 유한한 화살표 타입 A→B뿐이다. Γ={f:Int→Bool,g:Bool→Int}에서 g(f(3))는 Int지만 f(g(3))는 g의 인수 3:Int가 Bool과 다르므로 거부한다. 함수 이름이 존재한다는 사실이나 최종 원하는 타입부터 적는 것만으로 중간 전제를 생략할 수 없다. 아래 자기 적용은 다형성·재귀 타입 없는 이 명시적 모형에 한정한다.

먼저 확인할 개념
  • 타입 환경과 let 검사

    초기식/몸체에서 확장 환경을 적용할 범위를 구별한다.

  • 타입 계산과 값 계산

    이름-타입 장부와 실제 정수/Bool 값을 다른 열로 관리한다.

잎부터 큰 식으로 올라가기

정수 상수는 Int, true와 false는 Bool이다. 변수 x는 Γ에 적힌 타입을 사용한다. x가 없으면 이 작은 검사기는 이름을 해결할 수 없다. +는 양쪽 Int를 확인한 뒤 결과 Int를 만든다.

Γ={x:Int}에서 x+2는 x:Int와 2:Int라는 두 근거를 가진다. 결과를 먼저 원하는 타입으로 적고 근거를 맞추지 않는다. 규칙의 전제들이 모두 성립해야 결론을 얻는다.

범위와 분기 조건

let x=3 in x+4에서는 3:Int를 확인하고 몸체를 Γ,x:Int에서 검사한다. 몸체 x+4:Int이므로 전체도 Int다. 이 환경 확장은 let의 몸체에 적용하며 모든 곳의 x를 바꾸라는 뜻이 아니다.

if c then a else b는 c:Bool과 a:T,b:T를 요구한다. if 1 then 2 else 3은 두 분기가 Int라도 조건이 Int여서 실패한다. 참처럼 취급하는 숫자 규칙을 다른 언어에서 가져오지 않는다.

오류 메시지의 한계

let x=true in x+4는 이름이 존재하지만 타입이 맞지 않는다. 이름 없음과 연산 타입 불일치를 따로 기록하면 원인을 찾기 쉽다. 검사기가 처음 발견한 위치가 개발자가 의도한 수정 위치와 항상 같지는 않다.

타입을 맞춰도 3−4=-1이 목적에 맞는지는 별도 요구사항이다. 아래는 정확 정수와 단순 타입만 사용하는 자체 연습이다. 오버플로·변환·오버로딩은 이 작은 규칙에 포함하지 않는다.

바깥 4 유지

초기식의 x와 몸체의 x는 서로 다른 바인딩이다. 값 열은 바깥 x가 4인 독립 입력의 설명이며 검사기에 숫자 4를 실행하여 타입을 얻은 것이 아니다. 환경을 한 전역 사전에서 영구 덮어쓰는 구현으로 오인하지 않는다.

중간 과정을 따라가는 예제

let x=3 in if x<5 then x+4 else 0을 검사하라. <는 Int 두 개에서 Bool이다.

  1. 3:Int이므로 몸체 환경에 x:Int를 추가한다.

  2. x<5는 Int,Int에서 Bool이다.

  3. x+4:Int이고 0:Int이므로 if:Int이다.

  4. 전체:Int이며 값 추적은 x=3, 조건 true, 3+4=7이다.

타입 Int, 값 7이다.

조건을 바꾸어 비교하기

초기식과 몸체의 같은 이름에 다른 타입이 있다

Γ={x:Int}에서 let x=(x<5) in if x then 1 else 0을 검사하라. 바깥 x가 4인 입력과 8인 입력의 값도 각각 구하라.

  1. 초기식에서는 x:Int와 5:Int를 비교하여 Bool을 얻는다. 몸체의 새 x는 Bool이고 두 분기는 Int이므로 전체 타입은 Int다.

  2. 바깥 x가 4이면 새 x는 true여서 몸체 결과는 1이다. 바깥 x가 8이면 새 x는 false여서 결과는 0이다. let 밖의 x값은 수정하지 않는다.

두 입력 모두 전체 타입은 Int다. 바깥 x가 4인 입력의 결과는 1이고, 8인 입력의 결과는 0이다.

비교할 점

변수 이름 하나를 모든 범위의 동일 바인딩으로 취급하면 잘못된다.

함수의 중간 결과도 다음 입력 계약이다

Γ={f:Int→Bool,g:Bool→Int}에서 g(f(3))와 f(g(3))를 검사한다.

  1. f(3)는 Int 입력에 맞아 Bool이고 g는 그 Bool을 받아 Int를 반환한다.

  2. 역순에서 먼저 g(3)는 Bool 입력에 Int 3을 주므로 실패한다. 바깥 f의 타입으로 이를 복구하지 않는다.

정방향은 Int, 역방향은 인수 타입 오류다. 함수의 실제 값은 정의하지 않았으므로 정수 결과값은 말하지 않는다.

비교할 점

타입표만으로 구체적 함수 반환값을 예측하지 않는다.

소단원 7.3

타입 안전성의 의미

타입이 맞으면 프로그램이 반드시 종료하고 답도 맞을까?

준비 개념과 학습 목표

준비 개념

  • 작은 단계 e→e′는 계산 한 번이다.

  • stuck은 값도 아니고 다음 규칙도 적용할 수 없는 상태다.

학습 목표

  • progress와 preservation을 설명한다.

  • 안전성과 종료를 구분한다.

  • 정리의 언어 범위를 명시한다.

보존을 깨는 검사기와 계산값을 틀리는 평가기는 같은 실패일까?

타입 안전성은 타입 규칙과 계산 규칙의 짝에 대한 주장이다. 현재 정수 덧셈만 있는 언어에서 새 검사기 A가 Int+Bool도 Int라고 허용하면 5+true를 승인한다. 두 피연산자는 이미 값이지만 정수 덧셈 규칙을 적용할 수 없어 값도 아닌 막힌 식이다. 이 반례는 progress 실패를 직접 보이며 실제 컴파일러 시험 결과가 아닌 자체 잘못된 규칙의 논증이다.

검사기 B는 if 조건 Bool과 then 타입만 보고 else를 무시한다고 하자. B는 if false then 1 else true를 Int로 분류한다. 정상 평가 규칙으로 한 단계 가면 true:Bool이다. 초기식이 진행하는 사실만 확인하면 문제를 놓친다. 이 한 전이는 preservation을 깨며 현재 예에서 다음 값 true도 정상 완료이므로 막힘 반례와 다르다.

반면 정상 타입 검사와 정상 값 분류를 유지하고 덧셈 평가를 잘못 구현하여 Int끼리 합 대신 왼쪽 값만 돌려주면 2+3이 2:Int가 된다. 정수 분류 보존과 다음 단계 존재만으로 원래 덧셈 요구값 5가 증명되지는 않는다. 재귀 loop:Int가 자기 호출로 매번 진행하는 별도 확장은 끝나지 않을 수 있다. 값·막힘·무한 진행·명시된 오류 결과를 구분하고 안전성 정리 밖의 요구사항이나 입출력 성공을 추가 보장하지 않는다.

진행과 보존을 함께 보기

닫힌 잘 타입된 식에 대해 progress는 값이거나 다음 계산 단계가 있음을 말한다. preservation은 e:T이고 e→e′이면 e′도 T라는 약속이다. 각각 진행 가능성과 타입 보존을 다룬다.

2+(3+4)는 Int이며 안쪽을 계산한 2+7도 Int다. 이어 9:Int라는 값에 도달한다. 이 과정은 한 예이고 모든 식의 정리 증명 자체는 아니다. 정리는 언어의 모든 규칙을 대상으로 따로 증명한다.

멈춤과 실패를 구분하기

2+true는 이 작은 언어에서 값이 아니며 정수 덧셈 규칙도 적용할 수 없다. 타입 검사가 거부하는 stuck 반례다. 정상 값 9에서 다음 단계가 없는 것은 완료라서 stuck이 아니다.

지원하는 예외가 있는 언어는 예외를 결과나 전파 단계로 정의할 수 있다. 안전성을 말할 때 어떤 실패를 제외하는지 의미론을 확인한다. 배열 범위 오류나 입출력 실패를 모든 정적 타입 검사가 없앤다고 주장하지 않는다.

안전성과 유용성의 경계

재귀를 추가한 언어에서 정수 함수 loop():Int가 계속 자기 자신을 부르면 매 단계가 정의되어도 종료하지 않을 수 있다. 타입 안전은 일반적으로 종료 정리가 아니다. 원하는 합을 잘못 계산한 정수 결과도 타입은 맞을 수 있다.

정리 밖의 외부 호출·불안전 기능·구현 오류까지 자동 보장하지 않는다. 모형의 연산·변환·메모리 규칙을 명시해야 한다. 우리의 종이 예제는 실제 언어 전체나 컴파일러 구현을 검증했다는 증거가 아니다.

다른 문제에 적용하기

자체 Int/Bool 언어에서 네 검사를 조립하라. P=if flag then 10 else true와 Q=if flag then 10 else 1+true를 flag의 두 Bool 입력으로 비교하고 현재 정적 거부의 서로 다른 이유를 적는다. Γ={x:Int}에서 비재귀 let x=(x<5) in if x then 1 else 0의 초기식과 몸체 환경을 구하고, 바깥 x가 4인 입력과 8인 입력의 결과를 각각 적는다. Γ={f:Int→Bool,g:Bool→Int}에서 g(f(3))의 타입을 도출한다. 마지막으로 검사기 A의 5+true, 검사기 B의 if false then 1 else true, 평가기 C의 2+3이 각각 어떤 명제를 어기는지 설명하라. A/B/C는 독립 변형이며 실제 검사기나 언어 실행은 하지 않는다.

힌트 1

P의 분기 결과 종류와 Q의 else 연산 전제를 분리한다. 비재귀 초기식은 기존 Γ, 몸체는 새 바인딩을 쓴다.

힌트 2

A는 다음 규칙 존재, B는 한 전이의 타입, C는 연산의 기대값을 각각 비교한다.

풀이와 답 확인

  1. P의 두 동적 값은 10:Int와 true:Bool이며 정적 거부는 분기 타입 차이다. Q는 true 입력에서 10, false 입력에서 연산 오류이며 정적 거부는 Int+Bool이다.

  2. let 초기식은 바깥 x:Int를 사용하여 비교 결과 Bool을 얻는다. 몸체에는 새 x:Bool을 사용하며 두 분기의 타입이 Int라서 전체도 Int다. 바깥 x가 4인 독립 입력은 1, x가 8인 입력은 0을 반환한다. 바깥 바인딩은 유지된다.

  3. f(3):Bool을 g의 Bool 입력에 넣어 g(f(3)):Int다. 함수 정의가 없으므로 구체적인 정수 반환값은 지정하지 않는다.

  4. A는 5+true를 승인하지만 식이 막혀 progress가 실패한다. B는 초기 Int로 분류한 식이 Bool 값 true로 진행하므로 preservation이 실패한다. C의 2+3→2:Int는 타입 분류를 보존하지만 기대값 5와 달라 연산 명세를 어긴다.

정적 전제와 실제 선택 경로, 범위별 타입 환경, 함수 적용 전제, 안전성 두 명제와 값 정확성을 구별해 판정한다. 실제 컴파일러/평가기/학생 시험은 미수행이다.

해결한 뒤 점검할 것

  • P의 정상 두 종류와 Q의 잘못된 연산을 다른 거부 근거로 쓴다.

  • let 초기식과 몸체의 x를 각각 Int/Bool로 표시하고 범위 종료를 설명한다.

  • 중간 f(3):Bool과 최종 Int를 전제로 도출한다.

  • A/B/C를 progress/preservation/연산 명세에 대응시키고 실제 언어 전체 검증으로 확대하지 않는다.
