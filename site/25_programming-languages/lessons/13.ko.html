소단원 13.1

공유 상태·메시지 전달

두 작업자가 같은 기록장을 쓰는 것과 한 사람에게 요청서를 보내는 것은 어떻게 다를까?

준비 개념과 학습 목표

준비 개념

  • 상태와 참조

  • 동시성과 순서

  • 소유권

학습 목표

  • 공유 상태와 메시지 중심 설계를 비교한다.

  • 잠금의 보호 범위와 메시지 소유권을 표시한다.

  • 동기화와 처리 완료의 차이를 설명한다.

요청서를 보낸 뒤 원래 목록을 바꾸면 받는 사람은 어떤 내용을 읽을까?

자체 순차 우편함 모형에서 발신자는 목록 A=[2,4]를 만든다. 참조 전달은 우편함에 A의 주소를 보관하고, 스냅샷 전달은 그 순간의 두 정수로 새 목록 B=[2,4]를 만들어 보관한다. 두 방식 모두 발신 이후에 수신자가 읽는 일정이다. 발신자가 A[0]=9로 바꾸면 참조 메시지의 합은 13, 스냅샷 메시지의 합은 6이다. 실제 언어의 데이터 경쟁을 실행한 사례가 아니라 별칭의 차이를 보이는 명시적 순서다.

Rust의 String 소유권 이전 예제는 발신 이후 이전 변수를 다시 사용하는 것을 거절한다. 이것은 임의 채널이 깊은 복사를 해 준다는 규칙과 다르다. 우리 우편함도 참조 공유·복사·독점 이전 중 하나를 계약으로 선택해야 한다. 중첩 가변 객체를 얕게 복사하면 겉 목록만 새로 만들어도 내부 공유가 남는다.

자체 상태 소유자는 논리 요청 Q(+6)을 반영하고 Q→6이라는 완료 기록을 같은 중단 없는 단계에 남긴 뒤 응답을 보낸다. 응답만 유실되면 호출자는 완료를 모르지만 상태는 이미 6이다. 같은 Q를 재시도하면 기록된 응답을 다시 주고 상태를 바꾸지 않는다. 새 번호 Q2로 재시도하면 새 요청으로 반영되어 12다. 실제 장애 내구성은 정의하지 않았으므로 프로세스 재시작의 정확히 한 번 보장으로 확대하지 않는다.

공유 상태는 함께 지켜야 하는 규칙을 만든다

공유 상태 방식에서는 여러 작업자가 같은 저장소를 읽거나 바꾼다. 올바른 갱신에는 잠금이나 원자 연산 등 해당 언어가 정한 동기화가 필요하다. 상태를 읽는 경로와 쓰는 경로가 서로 다른 규칙을 쓰면 불변조건이 깨질 수 있다.

이 단원의 추상 일정에서 합계 읽기·1 더하기·쓰기를 두 작업자가 각각 수행할 때 둘 다 0을 읽고 1을 쓰면 마지막 값은 1이다. 이것은 위험을 설명하는 단계 모형이다. C/C++의 비원자적 데이터 경쟁처럼 언어에서 정의되지 않는 경우를 이 표의 실제 출력으로 예측하지 않는다.

메시지로 상태의 주인을 모으기

한 작업자가 합계를 소유하고 다른 작업자는 증가 요청을 메시지로 보낼 수 있다. 소유자는 요청을 하나씩 처리한다. 상태 변경의 책임이 한곳에 모여 읽기·수정 범위를 이해하기 쉬워지지만 큐 용량, 대기, 종료, 오류 처리라는 새 계약이 필요하다.

Rust의 소유권을 이전하는 send 예제에서는 보낸 String을 이전 소유자가 다시 쓰지 못한다. 모든 언어와 모든 메시지 API가 자료를 복사하거나 소유권을 독점적으로 넘기는 것은 아니다. 메시지에 공유 객체의 참조를 담으면 수신자 밖에도 변경 주체가 남을 수 있으므로 실제 타입과 API를 확인한다.

보낸 것과 반영한 것의 시점을 구분하기

메시지 전송 성공이 수신 작업자의 업무 완료를 항상 뜻하지는 않는다. 필요하면 요청 번호와 완료 응답을 정해 반영 여부를 확인한다. Go에서는 채널 send와 해당 receive 완료 사이의 동기화 관계가 명시되지만 업무의 다음 명령이 완료됐다는 보장까지 자동으로 따라오지 않는다.

공유 잠금도 모든 순서를 보장하는 도구는 아니다. 어느 요청이 먼저 잠금을 얻을지, 공정하게 선택되는지는 별도 규칙이다. 공유 상태와 메시지는 경쟁·교착·누락 등의 책임 위치를 다르게 만들며 어느 쪽이든 오류와 종료를 설계해야 한다.

중간 과정을 따라가는 예제

합계 소유자의 초기값은 0이다. 요청 A(+1), B(+1)를 각 한 번만 받아 순서대로 처리하고 완료 응답을 보낸다고 가정한다. 같은 두 증가를 하나의 잠금 안에서 각각 처리하는 방식과 비교하라.

  1. 메시지 소유자는 A 처리로 0→1, B 처리로 1→2를 만든다.

  2. B→A 순서라도 두 요청이 정확히 한 번 처리되면 0→1→2다.

  3. 공유 상태도 읽기·더하기·쓰기를 각 임계 구역 안에 묶으면 두 갱신이 직렬화된다.

  4. 최종값은 둘 다 2지만 상태 변경 주체와 완료 확인 방법은 다르다.

이 모형의 최종값은 2다. 메시지 복제나 누락이 없는 조건과 잠금 아래의 전체 갱신 조건을 각각 확인해야 한다.

조건을 바꾸어 비교하기

얕은 복사의 내부 공유

A=[[2],4]를 겉 목록만 복사한 B를 보낸 뒤 A[0][0]=9로 바꾼다. 수신자가 B[0][0]+B[1]을 구하면?

  1. A와 B는 다른 겉 목록이지만 첫 내부 목록은 같다.

  2. 내부 쓰기로 B에서도 9를 읽어 4를 더한다.

합은 13이다. 내부 정수 값을 별도로 복사한 스냅샷이면 6이다.

비교할 점

새 겉 객체라는 조건만으로 독립 자료를 보장하지 않는다.

완료한 요청의 응답만 사라짐

합계 0에서 Q(+6)을 반영하고 기록한 뒤 응답을 잃는다. 같은 Q와 새 Q2를 각각 재시도하는 별도 경우를 비교하라.

  1. 같은 Q는 기록된 6을 반환하며 다시 더하지 않는다.

  2. Q2는 새 논리 요청이므로 6을 더한다.

같은 Q의 상태는 6, 새 Q2의 상태는 12다.

비교할 점

호출자 미확인과 소유자 미실행을 같은 상태로 쓰지 않는다.

종이와 본문으로 직접 해보기

A가 한 번 더 중복 전달되어 A, A, B를 모두 처리한다면 합계는? 요청 번호로 A의 재처리를 막는다면?

힌트 보기

각 메시지가 가진 논리 요청을 구별한다.

풀이 보기

중복을 모두 처리하면 0→1→2→3이다. 이미 처리한 A를 건너뛰는 계약이라면 두 논리 요청만 반영되어 2다. 실제 네트워크나 메시지 API가 중복을 만들었다는 관찰은 아니다.

오해와 반례

메시지 전달을 쓰면 모든 공유 상태와 경쟁이 사라진다.

메시지 안에 공유 참조를 넣거나 여러 작업자가 같은 외부 파일을 바꾸면 공유 효과가 남는다. 소유권, 전달 규칙, 중복과 완료 계약을 검토해야 한다.

연습 1 · 값과 상태 예측

새 A=[2,4]의 스냅샷 B를 보낸 뒤 A에 7을 덧붙인다. 수신 B의 길이와 합은?

힌트 1

B는 두 정수를 새 목록으로 복사했다.

힌트 2

A의 크기 변경은 B를 바꾸지 않는다.

풀이와 답 확인

  1. A는 [2,4,7]이지만 B는 [2,4]다.

B의 길이는 2이고 합은 6이다.

흔한 오답에서 다시 생각하기

발신 뒤 A의 합 13이 수신 결과다.

수신자가 읽는 보관 대상을 먼저 표시한다.

연습 2 · 오류 찾아 고치기

Q의 완료 여부를 먼저 검사하고 나중에 효과를 반영하는 두 소유자가 있다. 둘 다 기록 없음으로 판단한 뒤 각각 +6을 실행한다. 번호가 있으므로 중복은 막히나?

힌트 1

검사와 반영의 공동 보호 범위를 본다.

힌트 2

초기 합계 0에서 실제 반영 횟수를 센다.

풀이와 답 확인

  1. 두 검사가 모두 통과하면 효과는 두 번이다.

  2. 검사·효과·완료 기록을 하나의 직렬 계약에 둬야 한다.

합계는 12다. 번호 존재만으로 중복 억제되지 않는다.

흔한 오답에서 다시 생각하기

요청 번호만 같으면 어느 구현에서도 한 번만 실행된다.

번호 검사와 효과 관계의 원자성을 따로 설계한다.

연습 3 · 직접 만들어 보기

응답 유실 뒤 같은 요청을 안전하게 조회할 종이 상태표를 설계하라.

힌트 1

상태 반영과 호출자 지식을 나눈다.

힌트 2

기록의 보존 기간과 같은 번호의 다른 내용도 적는다.

풀이와 답 확인

  1. 요청 ID, 입력 내용, 미처리/처리 중/완료, 결과, 호출자 확인을 적는다.

  2. 동일 ID 다른 내용은 거절하고 완료 기록 만료 뒤 재시도의 정책을 정의한다.

기록 유효 범위 안에서만 같은 논리 요청을 재사용한다. 실제 저장 내구성 시험은 미수행이다.

흔한 오답에서 다시 생각하기

완료 기록은 지워도 같은 번호의 재시도가 항상 안전하다.

만료 후 중복 여부를 알 수 없는 상태를 계약에 포함한다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

합계 6과 Q 완료 기록을 유지하던 소유자가 재시작하여 기록만 잃었다. Q 재시도를 새 요청처럼 반영하면?

힌트 1

상태는 6이지만 기록은 비었다.

힌트 2

내구성을 정의하지 않은 원 모형 밖이다.

풀이와 답 확인

  1. 다시 +6을 반영하면 상태는 12다.

  2. 상태와 기록을 함께 보존·복구하는 별도 계약이 필요하다.

이 가정에서 12다. 기존 순차 중복 억제를 장애 보장으로 확대할 수 없다.

비동기와 코루틴 개요

기다리는 동안 다른 일을 하는 프로그램은 반드시 여러 CPU에서 동시에 실행될까?

준비 개념과 학습 목표

준비 개념

  • 함수 실행 상태

  • 대기와 실행

  • 호출 스택

학습 목표

  • 코루틴의 일시 중단과 재개를 설명한다.

  • 동시성과 병렬성을 구분한다.

  • 협력적 일정의 공유 상태 위험을 추적한다.

한 자리만 남았는데 두 코루틴이 모두 가능하다고 읽으면 어떻게 될까?

자체 한 이벤트 루프의 초기 free=1이다. A와 B는 free>0 검사 후 중단 가능한 승인 대기를 하고, 성공 응답을 받으면 현재 free에서 1을 뺀다. 일정은 A 검사 통과, B 검사 통과, A 재개 감소, B 재개 감소다. 같은 순간 실행되는 작업은 하나지만 free는 1→0→−1이 되어 두 예약을 허용한다. 원본의 옛 합계 덮어쓰기와 달리 현재 값 감소여도 검사 조건이 낡으면 불변식이 깨진다.

별도 예약 설계는 검사와 free 감소를 중단 없는 한 단계로 수행한 뒤 승인 대기를 한다. A가 먼저 예약하면 free=0이고 B는 거절된다. A 승인이 실패하면 A의 예약 토큰을 정확히 한 번 반환해 free=1로 복구한다. 이를 실제 금융 승인이나 모든 취소 경로의 구현으로 주장하지 않는다. 각 예약 토큰의 소유자와 상태 전이가 필요하다.

비동기 결과의 귀속도 관리해야 한다. 자체 A는 값 10, B는 값 20을 만들며 B가 먼저 끝난다. 완료 순서 목록 [20,10]을 시작 순서 [A,B]에 그대로 붙이면 A=20/B=10으로 잘못 연결한다. 결과에 요청 ID를 붙여 B→20/A→10으로 보관하면 시작 순서와 완료 순서가 달라도 값의 주인은 보존된다.

먼저 확인할 개념
  • 중단 전후 공유 상태

    검사 뒤 await에서 조건이 달라질 수 있다.

  • 상태 주인과 완료 응답

    예약 토큰·결과 ID의 책임 위치를 명시한다.

멈춘 자리의 상태를 보관하기

코루틴은 실행을 일시 중단했다가 지역 상태와 이어서 실행할 위치를 유지하며 재개할 수 있는 실행 단위다. async 함수의 호출과 실제 실행을 시작하는 방법은 언어마다 다르므로 일반 함수 호출과 같다고 가정하지 않는다.

Python asyncio에서는 코루틴 객체를 await하거나 Task로 스케줄링하는 흐름을 구분한다. 이 소단원은 실제 API 코드를 실행하는 대신 명시한 추상 일정으로 생각한다. await라는 글자가 항상 다른 작업으로 양보를 강제하는 것도 아니다. 이미 완료된 결과라면 중단 없이 이어질 수 있다.

대기 중에 다른 일을 할 수 있게 하기

Python asyncio 이벤트 루프는 한 번에 한 Task를 실행하는 협력적 일정을 쓴다. Task가 Future 완료를 기다려 중단되면 다른 Task나 콜백, I/O 처리를 진행할 수 있다. 한 코어에서도 여러 작업의 진행을 겹치는 동시성이 가능하다.

CPU 계산을 오래 수행하며 양보하지 않는 작업은 같은 루프의 다른 작업을 지연시킬 수 있다. async를 붙인다고 계산이 자동으로 여러 코어에서 병렬화되는 것은 아니다. 별도의 스레드·프로세스·실행기가 있으면 또 다른 규칙을 검토해야 한다.

await 사이에는 상태가 바뀔 수 있다

한 루프에서 한 Task만 실행해도 검사와 사용 사이에 대기가 있으면 다른 Task가 상태를 바꿀 수 있다. 읽기 직후 await하고 나중에 옛 값으로 쓰면 논리적 갱신 손실이 가능하다. 비동기 잠금이나 상태 소유자의 메시지 처리가 필요할 수 있다.

동기화 구간을 작게 만들되 보호할 불변조건 전체를 포함해야 한다. 모든 await를 같은 위험으로 단정하기보다 어떤 지점이 실제로 중단 가능한지 계약을 확인한다. 아래 추적은 두 대기가 모두 중단되고 일정이 주어진 경우다.

자체 부모 P가 연결 C를 소유하고 자녀 작업 K에게 범위 안에서만 빌려 준다. 사건은 K가 C를 사용하다 대기, P가 K 취소를 요청, K가 정리, K 종료 확인, P가 C를 닫기다. 취소 요청 직후 C를 닫으면 아직 종료하지 않은 K가 나중에 C를 사용하거나 정리하려고 할 수 있다. 종료 확인과 자원 수명을 함께 묶어야 한다.

이 모형에서 K 정리는 성공하고 추가 취소되지 않으며 유한 시간에 종료한다고 가정한다. 확인 전 보유 C는 1개, 확인 후 P가 닫으면 0개다. 실제 asyncio TaskGroup은 범위 종료 때 모든 작업을 기다리는 도구이며, 일반 create_task로 분리한 작업은 별도로 수명을 관리해야 한다. 작업이 영원히 끝나지 않으면 기다림도 완료되지 않을 수 있다.

자원 반환은 외부 효과의 롤백이 아니다. K가 이미 알림 E를 보낸 후 취소돼 C를 닫아도 E는 기록에 남는다. 별도 보상 E취소를 보내는 계약이라면 기록은 [E,E취소]이며 빈 기록과 다르다. 다른 관찰자가 E를 먼저 읽었을 가능성도 사라지지 않는다. 자동 정리의 범위와 업무 효과 보상의 범위를 따로 명시한다.

값 밖으로 나가는 변화도 효과다

같은 입력으로 값을 계산하는 것 외에 파일을 쓰거나 공유 상태를 바꾸거나 메시지를 보내는 일은 외부에 영향을 주는 효과다. 출력값만 같다고 두 프로그램의 동작이 같다고 볼 수 없다. 메시지 전송의 횟수나 파일 변화도 관찰 대상이 될 수 있다.

일부 언어와 타입 체계는 특정 효과를 표현하고 제한하지만, 이 단원은 그런 모든 체계의 형식을 정의하지 않는다. 먼저 함수 계약에 바꾸는 상태, 소유하는 자원, 실패와 취소가 밖으로 알려지는 방법을 적는다.

범위와 정리 책임을 연결하기

Rust의 MutexGuard는 범위를 벗어날 때 Drop으로 잠금을 해제하는 설계를 보여 준다. Python의 with/contextmanager는 획득한 자원을 yield로 제공하고 finally에서 해제하는 형태를 지원한다. 각 언어의 규칙이 정리를 묶는 지점을 만들지만 모든 비정상 종료를 다 해결한다는 뜻은 아니다.

비동기 해제는 기다림이 필요할 수 있어 async with 등의 별도 경로를 사용한다. 정리 함수 자체도 실패하거나 다시 취소될 수 있으므로 라이브러리 계약을 확인해야 한다. 프로세스 강제 종료에서도 모든 finally와 Drop이 반드시 실행된다고 보장하지 않는다.

취소 요청과 작업 수명을 관리하기

asyncio 취소는 다음 기회에 CancelledError로 알려질 수 있으며 정리용 try/finally를 권한다. 취소를 잡았다면 보통 정리 뒤 다시 전파하여 호출자가 완료·실패·취소를 구별하게 한다. 요청을 보냈다는 것과 모든 하위 작업이 끝나 자원을 정리했다는 것은 다른 상태다.

TaskGroup은 생성한 작업들을 범위 종료 시 기다리는 구조를 제공한다. 자체 설계에서는 자원 대여 개수, 반환 개수, 남은 개수를 추적하고 하위 작업의 종료 확인 전에 사용 중인 자원을 없애지 않는다. 정리 책임과 효과의 되돌림은 또 다르다. 연결을 닫았다고 이미 전송한 메시지가 취소되지는 않는다.

중간 과정을 따라가는 예제

추상 작업은 연결 두 개를 순서대로 얻고 작업 중 취소된다. 두 연결 획득은 성공했으며 정리 함수가 실패하거나 추가 취소되지 않아 둘 다 한 번씩 반환한다고 가정한다.

  1. 첫 획득 후 보유 수는 1, 둘째 후 2다.

  2. 작업 취소가 알려져 정상 결과를 만들지 않고 정리 경로에 들어간다.

  3. 둘째 연결 반환 후 보유 수1, 첫 연결 반환 후0이다.

  4. 정리 완료 뒤 취소 사실을 호출자에게 전달한다.

보유 수는 0→1→2→1→0이다. 이것은 명시한 정리 성공 조건의 종이 추적이며 실제 연결·취소 시험은 아니다.

각 사례는 새 상태에서 시작한다. A=[[2],4]의 겉 복사 B를 보낸 뒤 A[0][0]=9이면 수신 합을 구하라. 합계 0에서 Q(+6)를 반영·기록하고 응답을 잃은 뒤 같은 Q를 재시도한다. 별도 free=1 예약 설계에서 A 예약, B 거절, A 승인 실패 뒤 같은 토큰에 취소 알림도 온다. free를 구하라. 부모가 C를 소유하고 자녀 K가 빌릴 때 취소 요청·정리·종료 확인·반환 순서를 적고, 이미 보낸 E와 보상 E취소의 기록을 적어라.

힌트 1

겉 객체와 내부 객체, 논리 요청 ID와 반환 토큰의 정체성을 따로 표시한다.

힌트 2

요청/종료 확인/자원 반환/외부 알림을 다른 사건으로 적는다.

풀이와 답 확인

  1. A와 B의 내부 목록은 같으므로 수신 합은 9+4=13이다. 깊이 독립인 정수 스냅샷과 다르다.

  2. Q의 완료 기록을 재사용하므로 합계는 6이고 재시도가 다시 더하지 않는다. 기록 보존 범위 밖의 재시작은 이 결론 밖이다.

  3. A 예약으로 free=0, B는 미예약이다. A 실패의 유효 토큰 한 번 반환으로 free=1이며 뒤 취소 알림의 중복 반환은 없다.

  4. K 취소 요청 뒤 정리와 종료 확인을 기다리고 P가 C를 반환한다. 성공 가정의 C 보유 수는 1→0이다. 알림 기록은 [E,E취소]이며 빈 기록이 아니다.

공유 자료, 요청 효과, 예약 소유, 자녀 수명과 알림 이력을 서로 다른 장부로 유지한다. 실제 Rust/Python 동시 프로그램·서비스·학생 실험은 수행하지 않았다.

해결한 뒤 점검할 것

  • 내부 별칭으로 합 13을 설명한다.

  • 동일 Q의 재시도와 새 요청·기록 유실을 구별한다.

  • 실패와 취소 알림 두 개에도 하나의 예약만 반환하여 free=1을 유지한다.

  • 종료 확인 전 C 반환을 금지하고 보상 기록의 두 사건을 보존한다.
