소단원 12.1

스트림·메모이제이션

끝없이 이어지는 수열을 끝까지 만들지 않고 앞의 네 값만 얻을 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 함수 호출

  • 리스트와 재귀

  • 순수함수와 부작용

학습 목표

  • 지연된 계산과 저장된 값을 구별한다.

  • 요청한 스트림 접두부만 추적한다.

  • 캐시의 키·메모리·환경 조건을 설명한다.

지연한 계산을 공유하면 결과 값뿐 아니라 어느 상태가 공유될까?

원본의 정수 스트림을 확장하여 자체 순차 모형 S를 만든다. 0부터 시작하는 노드 i의 값은 i의 제곱이다. 각 노드의 값은 처음 요구할 때 한 번만 계산하여 저장하고, 꼬리를 따라가면 필요한 다음 노드를 연결한다. 노드를 건너뛰어 접근해도 중간 노드의 값 자체는 요구하지 않으면 계산하지 않는다. 같은 S를 두 소비자가 공유하면 값 저장 칸도 공유한다. 별도 생성한 S와 U는 값이 같지만 저장 칸과 계산 이력은 별개다.

처음 빈 S에서 A가 위치 2를 읽고 B가 위치 0을 읽은 뒤 A가 위치 2를 다시 읽는다. 계산된 값의 위치 집합은 {2}, {0,2}, {0,2}이고 반환은 4, 0, 4다. 노드 0부터 2까지 연결했다는 것과 세 값 모두 계산했다는 것은 다르다. 여기서는 노드 연결 비용·바이트 수·실제 Racket 내부 구조를 측정하지 않고 명시한 값 계산 횟수만 센다. Racket의 stream-cons도 값과 꼬리의 지연을 구별하므로 실제 API의 계약을 먼저 읽는다.

또 다른 문제는 캐시가 가변 객체를 돌려주는 경우다. 자체 make(n)는 호출할 때마다 새로운 한 칸 상자 [n]을 만들기로 약속한다. 결과를 그대로 캐시하면 첫 make(3)의 상자 A를 호출자가 [9]로 바꾼 뒤 둘째 호출도 같은 A를 받아 9를 본다. 숫자 3을 키로 삼는 것이 가능하더라도 새 객체 약속과 독립성은 깨진다. 불변 값 재사용, 매번 복사한 결과, 새 객체 생성 중 어느 계약을 택할지 먼저 결정해야 한다.

먼저 확인할 개념
  • 요구 시 평가와 결과 저장

    꼬리 연결과 값 계산을 따로 추적한다.

  • 관찰 가능한 객체 관계

    같은 값과 같은 가변 객체를 구별한다.

필요할 때 계산하기

스트림은 첫 값과 그 뒤를 얻는 규칙으로 순서 있는 자료를 다룰 수 있다. 무한 수열의 규칙을 유한하게 적을 수 있지만, 모든 값을 유한 시간에 목록으로 만들 수 있다는 뜻은 아니다. 앞에서 요구한 만큼만 관찰하면 이후 계산을 미룰 수 있다.

여기서는 S(n)의 첫 값이 n이고 다음은 S(n+1)인 자연수 스트림을 쓴다. S(0)부터 각 값에 2를 곱한 지연 스트림에서 처음 네 값을 요청하면 0, 2, 4, 6만 필요하다. 모든 API가 같은 평가 시점을 쓰는 것은 아니므로 생성·첫 값 요청·다음 값 요청을 구분한다.

미루기와 기억하기는 서로 다른 선택

지연은 언제 실행할지, 메모이제이션은 같은 계산 결과를 다시 쓸지를 다룬다. 호출할 때마다 재계산하는 지연 thunk도 있고, 한 번 강제한 결과를 기억하는 promise도 있다. Racket stream-cons의 기본 첫 식은 요청될 때 한 번 평가되지만 이를 모든 iterator의 보장으로 일반화하지 않는다.

함수 캐시는 보통 인수로 만든 키와 결과의 쌍을 저장한다. 입력이 같은데 전역 설정이 바뀌어 결과가 달라질 수 있으면 키가 충분하지 않다. 캐시는 결과뿐 아니라 인수·반환 객체를 살아 있게 할 수 있으므로 저장 크기와 무효화도 설계해야 한다.

같은 입력을 재사용해도 되는 조건

다음의 종이 캐시는 무제한 크기·단일 스레드·정확한 정수 인수·순수한 f(n)=n²을 가정한다. 요청 순서 2, 3, 2, 4, 3에서 키를 찾고 없는 경우에만 제곱을 계산한다. 이는 실제 라이브러리의 병렬 중복 호출이나 LRU 퇴출을 제외한 모형이다.

시간·난수·출력 효과가 있는 함수에 이 규칙을 붙이면 관찰 가능한 호출 횟수나 결과가 바뀐다. Python lru_cache는 hashable 인수를 요구하며 부작용 함수나 매번 새 가변 객체를 만들어야 하는 함수에는 적합하지 않음을 문서화한다. 스트림 객체 자체를 무조건 캐시해서 공유하는 것도 별도 문제다.

처음 S와 U는 모두 새로 생성한 모형이다. 마지막 열은 값 표현식의 실행 수이며 꼬리 연결 수나 물리 메모리 크기가 아니다. 반복 요구의 공유 범위는 스트림 객체별이다.

중간 과정을 따라가는 예제

f(n)=n²의 빈 무제한 캐시에 2,3,2,4,3을 순서대로 요청하라. 각 요청의 반환값·hit/miss·실제 제곱 횟수를 구하라.

  1. 2는 miss여서 4를 저장하고, 3은 miss여서 9를 저장한다.

  2. 다시 2는 hit로 4를 읽는다. 4는 miss여서 16을 저장한다.

  3. 마지막 3은 hit로 9를 읽는다. 요청 5개 중 miss 3회, hit 2회다.

반환값은 4, 9, 4, 16, 9이고 제곱 계산은 3회다. 최종 키는 2, 3, 4로 항목 3개다. 캐시 조회 비용이 없다고 실측한 것은 아니다.

조건을 바꾸어 비교하기

같은 값의 독립 계산과 공유 계산

A와 B가 각각 위치 2를 읽을 때 같은 S를 쓰는 경우와 새 S/U를 나누는 경우를 비교하라.

  1. 같은 S의 첫 요구만 위치 2 값을 계산한다. 둘째 요구는 저장된 4를 읽는다.

  2. 서로 다른 S와 U에서는 각자의 위치 2를 한 번씩 계산한다.

반환은 둘 다 4와 4지만 값 계산 수는 공유 1회, 독립 2회다.

비교할 점

같은 정수 결과에서 계산 이력과 저장 공유를 역추론하지 않는다.

새 상자 약속을 깨뜨리는 재사용

빈 캐시에서 make(3)을 A로 받고 A[0]=9로 바꾼 뒤 같은 키를 다시 요청한다. 원래 생성 함수와 결과 재사용 캐시를 비교하라.

  1. 원래 함수는 둘째 호출에서 새 B=[3]을 만든다. A와 B는 다른 상자다.

  2. 캐시는 둘째 호출에서 A를 그대로 반환하여 내용 9와 같은 객체 정체성을 보인다.

원래 둘째 결과는 별도 [3], 캐시 결과는 같은 [9]다. 새 객체 생성 계약을 보존하지 못한다.

비교할 점

해시 가능한 키 조건은 결과의 독립성 조건을 대신하지 않는다.

종이와 본문으로 직접 해보기

S(n)에서 n=1부터 시작해 각 값을 제곱한 스트림의 앞 3개를 적어라. 별도로 f(n)=n+offset을 n만 키로 저장하고 offset=10에서 f(2)를 캐시한 뒤 offset=20으로 바꾸면 어떤 오류가 생기는가?

힌트 보기

스트림의 필요한 인덱스만 쓴다. 입력 인수 밖에서 결과에 영향을 주는 값도 확인한다.

풀이 보기

앞 3개는 1, 4, 9이며 이후 값은 필요하지 않다. 첫 f(2)=12를 저장했으므로 offset=20에서 같은 키 2를 찾으면 12가 나온다. 현재 계약의 22와 다르다. offset을 키에 포함하거나 설정 변경 시 무효화해야 한다.

오해와 반례

지연 스트림이면 무한한 자료 전체도 목록으로 즉시 바꿀 수 있다.

끝이 없는 스트림을 끝까지 목록화하려면 끝에 도달해야 하므로 종료하지 않는다. 앞 4개를 요청하는 종료 문제와 전체 목록화 문제를 구별한다. 지연 자체가 메모리 사용 0이나 모든 함수의 자동 캐싱을 뜻하지 않는다.

연습 1 · 값과 상태 예측

표의 마지막 사건 뒤 B가 S의 위치 1을 읽고 A가 S의 위치 0을 읽는다. 반환과 두 스트림의 누적 값 계산 수는?

힌트 1

위치 1은 연결됐어도 아직 값을 요구하지 않았다.

힌트 2

위치 0은 S에서 이미 계산했다.

풀이와 답 확인

  1. 위치 1은 1을 계산하여 S의 위치 집합이 {0,1,2}가 된다.

  2. 위치 0은 0을 재사용한다. U의 계산 집합은 {2}로 유지한다.

반환은 1과 0, S는 3회·U는 1회로 합계 4회다.

연결과 값 강제를 따로 정의한 모형을 읽는다.

연습 2 · 오류 찾아 고치기

make가 새 상자를 약속하는데 캐시 결과 A를 매번 그대로 반환한다. 반환 직후 내용만 3으로 되돌리면 고쳐지나?

힌트 1

다른 호출자가 이전 A를 계속 보관할 수 있다.

힌트 2

정체성과 독립 쓰기도 관찰할 수 있다.

풀이와 답 확인

  1. 내용 복구는 이전 호출자의 A까지 바꾸는 효과를 만든다.

  2. 매번 새 상자를 만들어 반환하거나 불변 결과만 재사용하도록 계약을 바꾼다.

내용 초기화만으로 고치지 못한다. 새 객체 약속이면 별도 상자가 필요하다.

연습 3 · 직접 만들어 보기

키가 (문서 ID, 버전)인 자체 순차 캐시를 설계하라. 같은 ID의 버전 1과 2에 다른 내용이 있으며, 버전마다 내용은 불변이다.

힌트 1

동일 키가 동일 의미를 나타내야 한다.

힌트 2

버전 변경과 오래된 항목 정리는 다른 문제다.

풀이와 답 확인

  1. (ID,1)과 (ID,2)를 다른 키로 저장하여 현재 버전을 명시한 요청이 현재 결과를 찾게 한다.

  2. 오래된 버전을 보존하거나 제거하는 공간 정책을 정하되, 제거하면 필요한 요청을 다시 계산한다.

버전별 의미를 분리하고 실제 변경된 내용을 같은 버전으로 덮어쓰지 않는 전제가 필요하다.

매크로와 위생성 입문

코드 조각을 붙여 넣었는데 우연히 같은 변수 이름 때문에 결과가 바뀔 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 렉시컬 범위

  • 변수 바인딩

  • 함수와 식 평가

학습 목표

  • 매크로의 구문 확장과 함수 호출을 구별한다.

  • 변수 포획을 범위표로 추적한다.

  • 위생성과 중복 평가를 따로 점검한다.

이름을 안전하게 만들었는데도 조건부 실행을 망칠 수 있을까?

자체 의사언어는 왼쪽부터 순차 평가하며 if는 선택한 가지 하나만 실행한다. let의 초기값을 먼저 평가한 뒤 새 지역 이름이 본문에서 유효해진다. when-value(c,e)의 계약은 c를 한 번 평가하고 참일 때만 e를 한 번 평가하여 반환하며, 거짓이면 0을 반환하는 것이다. c와 e는 부작용이나 예외를 가질 수 있다. 이 계약은 원본 twice의 단순 중복 제거보다 실행 위치를 더 제한한다.

좋은 전개는 if c then (let fresh=e in fresh) else 0이다. fresh는 사용 위치의 이름과 겹치지 않게 결합한다. 잘못된 전개 let fresh=e in (if c then fresh else 0)는 e를 조건보다 먼저 실행한다. 이름을 잘 골랐어도 c=false이고 e가 예외를 내면 원래의 정상 반환 0이 사라진다. 위생성과 평가 횟수, 평가 위치는 서로 다른 검토 항목이다.

또한 임시 변수 이름만 바꾸면 정의 측의 다른 이름까지 안전해지는 것은 아니다. 자체 inc(e) 템플릿은 정의 위치의 정수 add와 상수 1을 사용하여 add(e,1)을 뜻한다고 정한다. 사용 위치가 add를 뺄셈으로 다시 결합했다면 문자열 치환은 그 이름에 포획되어 5 대신 3을 만들 수 있다. 정의 위치의 add 결합을 보존하는 위생적 전개는 4를 입력했을 때 5다. 이는 실제 Racket의 문법 결합 보존을 참고한 손모형이며 별도 매크로 구현을 실행하지 않았다.

먼저 확인할 개념
  • 문법 이름의 결합과 평가 횟수

    새 이름과 정의 위치의 연산 결합을 함께 검사한다.

  • 예외와 효과를 포함한 관찰

    정상 결과만 아니라 조건부 미실행도 보존한다.

실행할 값보다 먼저 구문을 변환하기

매크로는 구문 패턴을 보고 새로운 구문을 만든다. 함수처럼 인수값을 모두 계산한 뒤 본문을 실행하는 모델과는 단계가 다르다. 조건부 실행이나 바인딩 같은 새로운 문법을 표현할 수 있지만, 자동으로 더 빠르거나 더 안전한 것은 아니다.

아래 twice(e)→e+e는 설명용 구문 변환이다. 특정 언어의 매크로 정의 문법은 아니며, e를 텍스트 문자열로 다룬다고 실제 위생적 매크로 시스템을 설명하지 않는다. 변수의 이름·바인딩과 평가횟수를 살펴보는 종이 모형이다.

같은 철자와 같은 바인딩은 다르다

외부 변수 temp=4, y=9를 바꾸는 의도에서 임시 저장도 temp라는 이름으로 도입하면 안쪽 temp가 외부 temp를 가릴 수 있다. 순진한 확장 let temp=외부 temp in {temp=y; y=temp}는 안쪽 temp만 바꾸어 외부 temp=4, y=9를 그대로 남긴다.

새 바인딩 fresh에 외부 temp의 값 4를 저장한 뒤 외부 temp=y, y=fresh를 하면 4와 9가 9와 4로 바뀐다. 실제 위생적 시스템은 단지 긴 문자열 이름으로 충돌 확률을 낮추는 것을 넘어 도입 식별자와 사용 위치의 렉시컬 문맥을 구별한다. Racket 패턴 매크로가 이런 범위 보존을 제공한다.

이름이 안전해도 실행횟수는 따로 본다

위생성은 의도치 않은 식별자 포획을 막는 성질이지 부작용을 없애는 성질이 아니다. twice(next())를 next()+next()로 확장하면 next가 두 번 호출된다. fresh 변수를 도입해도 식을 두 번 썼으면 두 번 평가할 수 있다.

한 번만 평가하는 의도는 let fresh=e in fresh+fresh처럼 입력식을 한 번 묶는 규칙으로 표현할 수 있다. 여기서는 next가 현재 정수를 반환한 후 1 증가하고 덧셈은 좌→우로 평가하는 자체 모형을 사용한다. 호출 횟수·반환값·최종 상태를 동시에 비교한다.

참 가지 횟수 위반

fail은 호출하면 즉시 예외다. next는 아래 예제의 자체 상태 함수다. 각 행은 독립 초기 상태에서 평가하며 표의 두 입력 조건도 별개의 사례다. 신선한 변수 이름만으로 세 전개가 같은 의미가 되지는 않는다.

중간 과정을 따라가는 예제

counter=1이고 next()는 현재 값 반환 후 counter를 1 증가시킨다. 좌→우 평가에서 twice(next())를 next()+next()로 바꾼 A와 let fresh=next() in fresh+fresh인 B를 각각 초기 상태 1에서 추적하라.

  1. A의 첫 호출은 1을 반환하고 counter=2가 된다. 두 번째는 2를 반환하고 counter=3이 된다. 합은 3이다.

  2. B는 next 1회로 fresh=1, counter=2가 된다. fresh+fresh=2다.

  3. 두 규칙의 호출 횟수 2와 1, 반환값 3과 2, 최종 counter 값 3과 2가 모두 다르다.

A는 3을 반환하고 counter=3이며, B는 2를 반환하고 counter=2다. 둘 중 맞는 규칙은 매크로가 약속한 평가 횟수에 따라 정해야 한다.

조건을 바꾸어 비교하기

선택되지 않은 표현식의 예외

c=false이며 e=fail()이다. 좋은 전개와 바깥 let 전개를 비교하라.

  1. 좋은 전개는 조건 false를 읽어 else의 0을 반환한다.

  2. 바깥 let은 fail()을 먼저 평가하여 예외로 중단한다. 조건조차 읽지 못한다.

정상 0과 예외는 다른 관찰이므로 바깥 이동은 실패다.

비교할 점

평가 횟수를 한 번으로 만들었다는 사실만으로 조건부 실행을 보존하지 못한다.

정의 측 연산의 이름도 포획된다

inc(4)의 정의 측 add는 덧셈이다. 사용 위치의 add는 뺄셈으로 결합되어 있다. 두 전개의 값을 비교하라.

  1. 문자열 치환으로 나온 add(4,1)가 사용 측 결합을 따르면 4−1이다.

  2. 정의 측 결합을 보존하는 전개는 정수 덧셈 4+1이다.

잘못된 전개는 3, 결합 보존 전개는 5다.

비교할 점

임시 이름 외에 템플릿에서 도입한 연산 이름의 결합도 검사한다.

종이와 본문으로 직접 해보기

외부 temp=7, y=11을 바꾸려 한다. 안쪽 temp를 도입한 순진한 확장과 fresh를 도입한 범위 보존 확장 각각 최종 외부 두 값을 적어라.

힌트 보기

let의 초기 값에서는 바깥 temp를 읽고, 이후 안쪽 temp 참조는 안쪽 바인딩을 가리킨다고 가정한다.

풀이 보기

순진한 확장은 안쪽 temp가 7→11, y가 11→11이므로 외부 temp=7, y=11이다. fresh에 7을 저장하고 외부 temp=11, y=7로 바꾸는 확장의 결과는 11, 7이다. 같은 철자에 선을 긋고 어느 바인딩인지 표시하면 차이를 볼 수 있다.

오해와 반례

위생적인 매크로이면 부작용이 있는 인수도 항상 한 번만 평가한다.

이름 포획 방지와 입력식의 반복 평가는 별개다. 이름을 안전하게 처리해도 next()+next()에는 호출이 두 개 남는다. 의도한 횟수는 확장 결과의 식과 제어 흐름에서 확인해야 한다.

연습 1 · 값과 상태 예측

각각 새 상태 n=4에서 next는 현재 n을 반환하고 n을 1 늘린다. c=true일 때 좋은 when-value 전개와 e+e 전개의 반환·끝 상태는?

힌트 1

좋은 전개는 next를 한 번 실행한다.

힌트 2

e+e는 왼쪽 next 뒤 오른쪽 next를 실행한다.

풀이와 답 확인

  1. 좋은 전개는 값 4를 반환하고 n=5다.

  2. 중복 전개는 4+5=9를 반환하고 n=6이다.

각각 반환 4·끝 상태 5와 반환 9·끝 상태 6이다.

흔한 오답에서 다시 생각하기

위생적 이름이 있으니 e+e도 한 번만 실행된다.

위생성은 복제한 표현식의 실행 횟수를 없애지 않는다.

연습 2 · 오류 찾아 고치기

when-value를 일반 즉시 평가 함수 when-value(c,e)로 바꾸면 같은 계약이라고 했다. c=false이며 두 번째 인수가 fail()인 사례로 고쳐라.

힌트 1

즉시 평가 함수는 호출 전 인수를 평가한다.

힌트 2

함수 본문이 거짓 가지를 고르기 전에 무슨 일이 일어나는지 본다.

풀이와 답 확인

  1. fail() 인수 평가가 예외를 내면 함수 본문에 도착하지 못한다.

  2. e를 지연한 thunk로 전달하여 조건이 참일 때만 호출하거나 문법 형태를 유지한다.

일반 값 인수 함수로 단순 치환할 수 없다.

흔한 오답에서 다시 생각하기

함수 안에 if가 있으면 인수도 자동으로 지연된다.

함수 호출 규칙과 본문 안의 가지 규칙은 별개다.

연습 3 · 직접 만들어 보기

c도 효과를 가질 수 있을 때 when-value의 안전한 전개를 독립적으로 설계하라. 사용 측에는 fresh라는 변수도 있다.

힌트 1

조건을 한 번만 실행하고 e를 참 가지 안에 둔다.

힌트 2

도입한 이름은 사용 측 결합과 분리한다.

풀이와 답 확인

  1. 정의 측 if 결합으로 c를 한 번 검사한다.

  2. 참 가지 안에서 사용 측에 포획되지 않는 새 이름에 e를 한 번 저장한 뒤 그 값을 반환하고 거짓 가지는 0이다.

조건 한 번·선택된 e 한 번·결합 보존 세 조건을 모두 명시한다.

흔한 오답에서 다시 생각하기

c를 검사한 뒤 디버그 기록을 위해 c를 다시 호출해도 같다.

c의 두 번째 효과나 다른 값은 계약에 없는 실행이다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

조건 함수는 호출 시 기록 C를 남기고 false를 반환한다. e는 기록 E를 남기고 8을 반환한다. 좋은 전개와 바깥 let 전개의 기록 순서를 비교하라.

힌트 1

좋은 전개는 조건부터 실행한다.

힌트 2

바깥 let은 값 e를 먼저 얻는다.

풀이와 답 확인

  1. 좋은 전개의 기록은 C 하나이며 반환 0이다.

  2. 바깥 전개는 E,C 순서이고 반환도 0이다.

값 0이 같아도 기록 C와 E,C가 달라 등가가 아니다.

최종 정수가 같으면 매크로 전개도 같다.

등가성·리팩터링

계산 결과가 한 번 같았다는 이유만으로 프로그램을 바꿔도 된다고 말할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 순수함수와 상태

  • 평가 순서

  • 예외와 조건 분기

학습 목표

  • 관찰 가능한 행동의 범위를 먼저 정한다.

  • 순수식 변환의 조건과 반례를 든다.

  • 증명·반례·회귀시험의 역할을 구별한다.

같은 숫자를 만드는 두 계산이 객체와 실패까지 같을까?

이번 관찰 계약은 정상 반환 값뿐 아니라 예외 여부·순서 있는 기록·반환 참조 사이의 동일성·호출 뒤 가변 상태를 포함한다. 시간과 메모리 비용은 이 단원에서 비교하지 않는다. 자체 make(3)는 부작용 기록 없이 새 상자 [3]을 정상 생성하며 할당 실패는 이 제한된 모형에서 제외한다. A는 (make(3),make(3)) 두 결과를 반환하고 B는 let t=make(3) in (t,t)다. 반환한 두 칸의 초기 숫자는 같아도 A의 상자는 서로 다르고 B의 두 참조는 같은 상자다.

호출자가 첫 상자를 [8]로 고친 뒤 둘째 상자 내용을 읽으면 A는 3, B는 8이다. 입력과 출력 숫자에 대한 순수 계산이라는 설명만으로 가변 결과의 새 객체 계약을 지울 수 없다. 반대로 고정 불변 정수 f(3)=3을 두 번 읽는 것을 한 값으로 재사용하는 모형에서는 이 쓰기 관찰 자체가 없다. 어느 결과와 어떤 문맥을 허용하는지 범위를 먼저 적어야 한다.

조건의 교환도 안전성 검사가 필요하다. Java int의 x!=0 && 10/x>1은 x=0이면 오른쪽을 생략하여 false다. 순서를 바꾼 10/x>1 && x!=0은 0으로 나누는 예외다. 정수 나눗셈과 단락 평가의 실제 규정을 참고하며 여기서는 x=0,2,10만 손추적한다. 대수식처럼 두 조건을 교환하는 리팩터링은 왼쪽이 오른쪽의 실행 전제를 보장할 때 틀릴 수 있다.

먼저 확인할 개념
  • 반환·효과·예외의 등가성

    객체 관계와 호출 뒤 문맥을 관찰에 추가한다.

  • 가변 결과를 재사용하는 캐시

    결과 저장과 표현식 공유의 같은 위험을 비교한다.

관찰할 것이 무엇인지 먼저 약속하기

프로그램 등가성은 정한 관찰과 허용한 문맥에서 구별할 수 없는지를 묻는다. 반환값만 볼지, 출력 순서·예외·최종 상태·종료 여부를 포함할지 명시해야 한다. 실행시간을 관찰에서 제외한 의미 보존과 같은 속도 보장은 별개다.

리팩터링은 외부 행동을 보존하면서 내부 구조를 바꾸는 작업이다. 그 외부 행동을 정하지 않으면 반복 읽기를 캐시로 바꾸거나 연산을 재배치한 뒤 무엇을 유지했는지 판단하기 어렵다. 여러 입력의 시험 통과는 근거가 되지만 모든 문맥의 등가성 증명은 아니다.

순수한 계산에서의 대수적 근거

자체 언어의 정확한 정수, 종료하는 순수 함수 f, 동일한 고정 인수 x를 가정하면 f(x)+f(x)를 let t=f(x) in t+t로 바꿔도 값은 같다. f가 항상 v를 반환하므로 두 식의 결과는 v+v라는 일반적 설명이 가능하다. 새 변수 t의 바인딩이 기존 이름을 포획하지 않아야 한다.

정확한 수학정수 조건을 실제 float나 임의 언어의 예외/오버플로 규칙으로 옮기면 안 된다. Java 규격도 식 재배치는 값과 관측효과를 보존해야 하며 부동소수점의 재결합을 무조건 허용하지 않는다. 어떤 자료형과 평가 규칙을 썼는지가 근거의 일부다.

반례를 찾고 행동표를 만들기

next가 상태를 바꾸는 앞 소단원 모형에서는 반복 호출을 하나로 줄이면 결과와 최종상태가 달라진다. 출력 효과만 있는 f도 값을 같게 돌려주면서 로그 두 줄을 한 줄로 줄일 수 있다. 공통부분식이라는 모양만으로 재사용을 정당화하지 않는다.

if flag then 1 else 실패식을 flag*1+(1-flag)*실패식처럼 양쪽 계산식으로 바꾸면 선택되지 않았던 실패식도 평가할 수 있다. 정상·경계·예외·부작용·비종료 경로를 행동표에 적고 변경 가정에 맞는 시험을 골라야 한다. 실제 수행한 시험과 제안한 회귀시험을 구별한다.

중간 과정을 따라가는 예제

정확한 정수의 순수 함수 f(x)=x²+1이고 x=3이다. A=f(x)+f(x), B=let t=f(x) in t+t의 반환값을 비교하라. 별도의 함수 g는 호출마다 "읽음" 한 줄을 출력하고 5를 반환한다. g()+g()와 let t=g() in t+t도 반환값과 출력을 비교하라.

  1. f(3)=9+1=10이므로 A는 10+10=20, B는 t=10을 저장한 뒤 t+t=20이다.

  2. 일반 x에도 f(x)=v라는 고정값으로 두 결과 v+v를 설명한다.

  3. g 두 호출과 한 호출의 반환값은 모두 10이다. 그러나 출력은 두 줄과 한 줄이므로 출력 포함 관찰에서 다르다.

순수 f 변환은 명시한 관찰에서 같은 20이다. g 변환은 반환값만 같고 출력 행동이 달라 리팩터링의 행동 보존 조건을 충족하지 않는다.

조건을 바꾸어 비교하기

공통 표현식 저장의 가변 결과 반례

A와 B의 두 반환에서 첫 상자의 내용을 8로 바꾸고 둘째 내용을 읽어라.

  1. A는 별도 상자 두 개라 첫 쓰기가 둘째에 닿지 않는다.

  2. B는 같은 t 참조를 두 번 담아 첫 쓰기가 둘째 읽기에도 보인다.

둘째 읽기는 A에서 3, B에서 8이다.

등가성 반례는 변환식 내부가 아니라 허용된 호출자 문맥에서도 나타난다.

보호 조건을 뒤로 옮긴 실패

Java int x=0에서 x!=0 && 10/x>1을 뒤집어라.

  2. 뒤집은 식은 10/0부터 평가하여 ArithmeticException으로 중단한다.

원래 false, 변환 후 예외라 계약을 보존하지 않는다.

비교할 점

정상 입력 일부에서 같은 값인 것은 전체 입력의 등가 증명이 아니다.

선택되지 않은 가지의 평가 여부와 실패시 정상 반환 여부를 기록한다.

풀이 보기

fail이 예외를 던진다면 원본은 7을 반환하지만 변경은 조건 선택 전 예외가 나므로 다르다. f(0)=1→합 2, f(-2)=5→합 10으로 A/B는 같다. 이 두 시험만으로 모든 함수의 캐싱 안전성을 증명하지는 않는다.

다른 문제에 적용하기

공유·선택·후속 문맥을 함께 검토하기

새 S에서 위치 2, 위치 0, 위치 2를 순서대로 요구하고 별도 U에서 위치 2를 요구한다. 값 계산 집합과 합계 계산 수를 적어라. c=false이며 e=fail()일 때 좋은 when-value와 바깥 let을 비교하고, 사용 측 add가 뺄셈인 inc(4)의 문자열 치환/결합 보존 결과를 구별하라. 각각 새로 시작한 두 상자 설계 A/B에서 첫 상자에 8을 쓴 뒤 둘째 값을 읽는다. 마지막으로 Java int x=0,2,10에서 보호식과 뒤집은 식을 비교하여 통합 변환 제안을 판정하라.

힌트 1

같은 스트림의 저장 칸, 별도 스트림의 저장 칸, 상자의 참조 관계를 따로 그린다.

힌트 2

조건 이전 평가·정의 측 이름·정수 나눗셈의 첫 실패 사건을 기록한다.

풀이와 답 확인

  1. S의 계산 집합은 {2}, {0,2}, {0,2}이고 반환은 4,0,4다. U는 {2}에서 4를 반환하므로 두 스트림 합계 값 계산 수는 3회다.

  2. 좋은 when-value는 fail을 실행하지 않고 0이다. 바깥 let은 예외다. inc(4)는 사용 측 뺄셈으로 포획되면 3, 정의 측 덧셈 보존이면 5다.

  3. 상자 A의 둘째 읽기는 3, B의 둘째 읽기는 8이다. 초기 두 숫자가 같았어도 별칭 관찰이 다르다.

  4. 보호식/뒤집은 식은 x=2에서 true/true, x=10에서 false/false, x=0에서 false/예외다. 결과 공유·바깥 이동·이름 치환·조건 교환을 한꺼번에 승인할 수 없다. 실제 Racket/Java/캐시 구현/학생 실행은 수행하지 않았다.

요구한 계산만 저장하는 공유는 모형의 계약과 맞지만, 가변 결과 공유·조건 밖 평가·정의 측 이름 포획·보호 조건 교환은 각각 별도의 관찰 반례가 있다.

해결한 뒤 점검할 것

  • 연결된 노드 수와 계산된 값 수를 구별하고 합계 3회를 설명한다.

  • 위생성과 조건부 실행을 별개로 검사하여 0/예외 및 3/5를 기록한다.

  • 호출자 쓰기 문맥에서 둘째 상자 값 3/8의 이유를 설명한다.

  • 정상 두 입력의 일치와 0의 반례를 구별하며 실제 학생 미수행을 유지한다.
