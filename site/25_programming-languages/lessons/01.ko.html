소단원 1.1

구문·의미·실행모형

두 언어에서 똑같이 1+2라고 쓰면 더 큰 코드에서도 뜻이 항상 같을까?

준비 개념과 학습 목표

준비 개념

  • 식은 값을 계산하는 코드이며 1+2는 기본 덧셈 예이다. 문장은 대입·반복처럼 동작을 지정한다.

  • 타입은 값의 종류와 허용되는 연산을 구분한다. 숫자 2와 문자열 '2'를 각각 상자에 적어 구별하라.

  • 자가진단: (1+2)*3은 9이다. 괄호 없는 1+2*3은 곱셈을 먼저 하여 7이다.

학습 목표

  • 구문·정적 의미·동적 의미의 질문을 구분한다.

  • 피연산자 타입과 평가 순서로 같은 + 표기의 의미를 설명한다.

  • 언어 의미와 인터프리터/JIT 같은 구현 방식을 구분한다.

반환값이 같으면 중간에 한 일도 같은가?

원본의 Java SE 11 문자열 + 비교를 관찰 기록까지 확장한다. 별도의 작은 메서드 f는 로그 끝에 F를 붙이고 int 2를 반환하며 g는 G를 붙이고 int 3을 반환한다. 로그는 호출 전 빈 문자열이고 두 메서드는 순차 호출에서 정상 종료한다. f()+g()와 g()+f()는 둘 다 int 5지만 로그는 FG와 GF다. 여기서 로그는 종이 사건표이며 화면·파일에 실제 쓴 기록이 아니다.

구문 구조, 실행 시 평가 순서, 관찰 계약을 따로 적는다. 덧셈의 교환 법칙이 값 2와 3에는 적용되어도 부작용이 있는 두 호출을 교환할 근거가 되지는 않는다. 별도 실패 사례의 f는 F를 기록한 뒤 예외를 던진다고 정한다. Java 이항식의 왼쪽 평가가 급격히 끝나면 오른쪽은 평가하지 않는다. JIT가 있다는 이유로 G를 먼저 기록해도 된다고 해석하지 않는다.

  • 인자 평가와 본문 진입

    본문을 시작하지 않았어도 앞선 평가 효과가 남는 상황을 연결한다.

구문은 형태를, 의미는 해석을 정한다

구문(syntax)은 어떤 코드 형태가 언어에서 허용되는지 정하는 규칙이다. 1 + 처럼 피연산자가 빠진 형태는 표현식을 완성하지 못한다. 정적 의미는 실행 전 이름·타입·사용 조건을 검사하는 층이다. Java SE 11에서 int n="two";는 형태를 읽을 수 있어도 문자열을 int에 대입하는 타입 조건을 만족하지 않는다.

동적 의미는 유효한 코드의 실행 상태와 결과를 규정한다. 정수 두 개의 합, 문자열 연결, 예외 발생, 저장 상태 변화가 이에 포함된다. 정적 검사를 통과했다는 것이 0으로 나누는 등 모든 실행 오류가 없어졌다는 뜻은 아니다. 언어를 비교할 때 '문법이 비슷하다'는 주장과 '같은 상태에서 같은 결과를 낸다'는 주장을 나누어 적는다.

타입과 괄호가 +의 해석을 바꾼다

Java SE 11의 +는 두 숫자에 대해서는 숫자 덧셈이며 한쪽이 문자열이면 문자열 연결을 수행한다. +는 좌결합이므로 1+2+"3"은 (1+2)+"3"으로 해석되어 문자열 "33"이 된다. "1"+2+3은 ("1"+2)+3이며 문자열 "123"이다. 서로 다른 중간 타입이 나중의 연산도 바꾼다.

Python 3.12에서 1+2는 3이고 "1"+"2"는 "12"지만 "1"+2는 이 내장 타입 조합에서 TypeError이다. Java의 문자열 변환을 Python에 그대로 가져오면 잘못된 예측을 만든다. 사용자 정의 연산자나 특별한 객체를 추가할 수도 있으므로 현재 비교 범위는 내장 int·str 및 Java int·String의 작은 값으로 한정한다.

Java SE 11 식: 1 + 2 + "3"        // 값은 문자열 "33"
Java SE 11 식: "1" + 2 + 3        // 값은 문자열 "123"
Python 3.12 식: "1" + 2           # TypeError 예상

실행모형과 구현을 분리한다

의미를 설명할 때 상태 σ는 이름과 현재 값의 대응이라고 단순화할 수 있다. 대입 x=x+1은 현재 σ에서 x의 값을 읽고 새 값을 계산한 뒤 다음 상태를 만든다. 이런 단계별 모형은 컴퓨터를 실행하지 않고도 결과를 논증하게 한다. 실제 객체·저장소와 별칭이 필요하면 더 정밀한 모형으로 확장한다.

컴파일, 해석, 바이트코드, JIT는 프로그램을 실행하는 구현 전략이다. 한 언어가 반드시 하나의 전략만 사용하는 것은 아니다. JVM 구현은 해석과 JIT를 함께 사용할 수 있지만 Java의 + 규칙을 임의로 바꾸어서는 안 된다. 성능 비교에는 동일 문제·입력·구현·버전·측정 조건을 추가해야 하며 이 첫 단원의 의미 비교를 속도 순위로 바꾸지 않는다.

좌결합 구조·중간 타입 차이

각 행은 독립 초기 상태에서 출발한다. 예외 행의 F는 성공 반환의 증거가 아니다. 마지막 행은 정수와 문자열의 정해진 작은 값이며 실제 Java 실행을 수행하지 않았다.

중간 과정을 따라가는 예제

Java SE 11에서 문자열이 포함된 1+2+"4"와 "1"+(2+4)의 값을 타입과 함께 추적한다.

  1. 첫 식은 (1+2)+"4"이다. 1과 2는 int이므로 중간값 3이다.

  2. 3과 "4"의 +는 문자열 연결로 문자열 "34"가 된다.

  3. 둘째 식은 괄호 안 2+4=6을 먼저 계산한다.

  4. "1"과 6을 연결하여 문자열 "16"이 된다.

각각 String 값 "34", "16"이다. 화면 결과만 적기보다 중간 타입과 결합 구조를 함께 적어야 근거가 드러난다.

조건을 바꾸어 비교하기

값 관찰과 효과 관찰의 두 판정

정상 f()+g()를 g()+f()로 바꾼다. 결과 타입·값만 보는 시험과 로그 순서도 보는 시험의 판정을 나누어라.

  1. 두 식의 덧셈 입력 값은 2와 3이므로 결과는 int 5다.

  2. 첫 식은 F 뒤 G, 둘째는 G 뒤 F를 기록한다.

값 관찰에는 같은 결과지만 값과 로그를 함께 관찰하는 계약에는 다르다. 두 시험의 성공은 서로 다른 사실이다.

비교할 점

base의 출력 예측에 관찰 가능한 부작용을 더하여 동등성 조건을 드러낸다.

괄호와 예외의 층을 나누기

독립적으로 Java 2+3+"4", 2+(3+"4")를 계산하고, 예외 f()+g()가 합계 5를 보장하는지 판단하라.

  1. 첫 식은 정수 5를 만든 뒤 "4"를 연결하고 둘째는 "34"를 먼저 만든다.

  2. 예외 f는 정상 값 2를 반환하지 않으며 g도 평가하지 않는다.

두 문자열은 "54"와 "234"다. 실패 식은 반환값 없이 F와 예외를 남기므로 합계 5를 약속하지 않는다.

비교할 점

괄호로 바뀌는 중간 타입과 실행 중단으로 사라지는 값은 서로 다른 이유다.

종이와 본문으로 직접 해보기

종이에 Java SE 11 식 2+3+"0", 2+(3+"0"), Python 3.12 식 "2"+"3"을 적어 괄호 구조·중간 타입·최종값을 표시하라.

힌트 보기

Java에서 String이 등장한 +는 연결이며 Python의 두 문자열도 연결이다.

풀이 보기

Java 첫 식 (2+3)+"0"은 5→"50". 둘째 식 3+"0"은 "30", 이어 2+"30"은 "230". Python 식은 문자열 "23"이다.

오해와 반례

연산자 모양과 숫자 모양이 같으면 언어 사이 의미도 같다.

Java "1"+2는 "12"를 만들지만 Python 내장 str과 int 사이 같은 식은 TypeError이다. 타입·변환 규칙·결합 구조를 확인해야 의미를 비교할 수 있다.

연습 1 · 값과 상태 예측

f가 F를 기록하고 예외를 던지는 새 사례에서 g()+f()의 로그와 반환 여부를 예측하라.

힌트 1

왼쪽 g가 정상 끝나는지 먼저 본다.

힌트 2

풀이와 답 확인

  1. g가 G를 기록하고 3을 반환한다.

  2. f가 F를 기록한 뒤 예외로 식을 끝낸다.

로그는 GF이며 덧셈 결과는 반환되지 않는다.

연습 2 · 오류 찾아 고치기

최적화 설명이 “정수 +는 교환 가능하므로 함수 호출도 무조건 교환한다”라고 한다. 반례와 빠진 조건을 고쳐라.

힌트 1

힌트 2

풀이와 답 확인

  2. 교환을 논하려면 부작용·예외·종료와 허용 관찰을 확인해야 한다.

순수 값의 식과 효과가 있는 호출의 변환을 분리한다.

한 값 결과가 상태와 예외 계약을 증명하지 않는다.

힌트 1

힌트 2

의미나 로그를 임의 변경할 권한 또는 이 프로그램의 실측 속도 순위는 결론 낼 수 없다.

한 단계 더

두 프로그램의 동등성을 논하려면 관찰 가능한 것부터 정하라. 반환값만 볼지 출력·예외·종료 여부까지 볼지에 따라 판정이 다르다. 1+2를 3으로 바꾸는 순수 정수 식은 이 조건에서 같은 값이지만 부작용이 있는 함수를 평가 순서 없이 재배치하면 동등성을 보장하지 못한다.

추상화와 표현력

같은 일을 더 짧게 적으면 언제나 더 강한 언어일까?

준비 개념과 학습 목표

준비 개념

  • 함수는 입력과 반환의 계약을 가진다. 예: square(x)는 x*x를 반환한다.

  • 목록 [1,2,3]은 순서 있는 세 값이다. 반복문은 각 값을 차례로 처리할 수 있다.

  • 자가진단: [1,2,3]의 제곱 목록은 [1,4,9]이다. 원래 목록 길이와 결과 길이는 모두 3이다.

학습 목표

  • 반복되는 처리와 변경 가능한 요소를 분리해 함수 추상화를 설명한다.

  • 고차 함수의 입력 계약과 결과를 추적한다.

  • 계산 가능성·표현 편의·성능을 서로 다른 비교 기준으로 둔다.

중간 리스트를 없애면 같은 추상화일까?

Python 3.12의 작은 유한 리스트 xs=[1,2]를 순서대로 처리한다. f(x)는 F와 x를 로그에 적고 x+1을 반환하며 g(y)는 G와 y를 적고 2*y를 반환한다. 별도 방식 E는 mid=list(map(f,xs))를 완성한 뒤 out=list(map(g,mid))를 완성한다. 방식 P는 out=list(map(g,map(f,xs)))처럼 두 반복자를 연결하여 끝까지 소비한다. 입력은 처리 중 변경하지 않고 메모리 실패·동시성은 이 모형에서 제외한다.

E와 P의 out은 [4,6]으로 같지만 E의 로그는 F1,F2,G2,G3이며 P는 F1,G2,F2,G3다. Python map은 완성 리스트가 아닌 반복자를 반환하므로 괄호 두 겹이 중간 리스트 한 개를 자동 만드는 것은 아니다. 순수하고 종료하는 함수에서는 원소별 합성 값으로 결과를 논증할 수 있지만 로그·오류가 관찰되면 함수 호출의 배치도 계약이다. 짧아진 코드는 계산 가능성이나 실측 속도의 우열을 바로 정하지 않는다.

추상화는 필요한 계약을 드러내고 세부를 묶는다

추상화는 복잡한 구현을 다 기억하지 않고도 사용할 수 있도록 핵심 개념과 인터페이스를 드러내는 일이다. square(3)이 9를 반환한다는 계약을 알면 호출자는 곱셈 코드의 위치를 몰라도 사용할 수 있다. 하지만 값의 범위, 부작용, 오류 조건처럼 올바른 사용에 필요한 사실까지 숨기는 것은 좋은 추상화가 아니다.

같은 목록의 원소별 처리를 반복해서 쓰면 변하는 요소는 원소 처리 함수이고 고정 부분은 목록 순회라는 것을 찾을 수 있다. 고정 패턴을 모으고 변하는 부분을 매개변수로 주면 하나의 구조를 여러 문제에 적용한다. 추상화의 가치는 글자 수뿐 아니라 계약의 명확성과 변경 영향을 줄이는 데 있다.

함수를 데이터처럼 전달하는 고차 함수

고차 함수는 함수를 인자로 받거나 함수 값을 반환하는 함수이다. map이라는 개념적 연산은 목록 xs와 변환 함수 f를 받아 [f(x) for x in xs]에 해당하는 결과를 만든다. 이를 종이에서 함수 카드 f와 원소 카드 세 장으로 추적할 수 있다.

이 단원의 Python 3.12 코드는 list(map(square,xs))처럼 결과를 list로 모은다. Python의 map 자체는 바로 완성된 리스트를 반환하지 않고 반복자를 반환하므로 list가 소비하는 단계까지 명시한다. 여기서 f는 정수→정수이며 원래 목록을 변경하지 않는 함수라는 조건을 둔다.

def square(x):
    return x * x
xs = [1, 2, 3]
ys = list(map(square, xs))
print(ys)

표현력에는 여러 질문이 있다

계산 가능성의 표현력은 어떤 함수를 계산할 수 있느냐는 질문이다. 작성 편의의 표현력은 같은 문제를 얼마나 자연스럽고 국소적으로 적는지 묻는다. 타입 체계의 표현력은 어떤 계약을 코드에 표현하고 검사할 수 있는지 묻는다. 서로 다른 질문을 단순한 코드 길이 점수 하나로 합치면 비교가 흐려진다.

반복문으로도 위 제곱 목록을 계산할 수 있으므로 map이 있다는 사실만으로 새로운 수학적 함수를 반드시 계산 가능하게 한 것은 아니다. 유한 메모리를 가진 실제 기계와 무한 자원을 가정하는 계산 모형도 구분한다. 더 짧은 표기가 반드시 더 빠른 구현이나 더 적은 메모리를 뜻하지 않으며 결과를 만드는 방식과 구현 비용을 따로 분석해야 한다.

표는 동일 입력을 각 방식의 새 빈 로그에서 처리한 정상 경로다. P의 실제 내부 버퍼 크기나 특정 interpreter의 속도를 이 네 행에서 측정한 것은 아니다.

중간 과정을 따라가는 예제

목록 [2,4,5]에 함수 f(x)=x+1을 적용하는 개념적 map을 종이로 계산한다. 함수 호출 횟수와 결과 순서를 적는다.

  1. 첫 원소 2에 f를 적용하여 3을 만든다.

  2. 두 번째 4에 f를 적용하여 5를 만든다.

  3. 세 번째 5에 f를 적용하여 6을 만든다.

  4. 이 개념적 목록 변환은 원래 순서에 맞춰 [3,5,6]을 반환하며 함수 적용은 세 번이다.

결과 [3,5,6], 입력·출력 길이 3. f의 계산이 종료하고 부작용이 없다는 조건에서 원소별 값을 독립적으로 설명할 수 있다.

조건을 바꾸어 비교하기

완성 리스트와 연결된 반복자

E와 P의 결과 및 호출 로그를 계산하고 같은 반환값 관찰과 전체 효과 관찰을 나누어라.

  1. f(1)=2, f(2)=3이며 g(2)=4, g(3)=6이다.

  2. E는 f 두 번 뒤 g 두 번, P는 항목마다 f 뒤 g다.

둘 다 [4,6]이지만 로그는 F1,F2,G2,G3 대 F1,G2,F2,G3다.

비교할 점

base의 순수 map 합성에서 빠져 있던 지연 소비 시점과 효과를 비교한다.

중간 단계 실패가 앞선 호출을 바꾼다

새 변형의 g는 G와 y를 기록한 뒤 y=2이면 ValueError를 던진다. E와 P를 각각 새 로그에서 계산한다.

  1. E는 mid [2,3]을 완성한 다음 g(2)에서 실패한다.

  2. P는 첫 f(1) 다음 g(2)에서 실패하여 f(2)를 호출하지 않는다.

E 로그는 F1,F2,G2이고 P는 F1,G2다. 둘 다 정상 out을 얻지 못하지만 수행한 f 호출 수는 2와 1이다.

비교할 점

같은 예외 이름도 그 이전 상태의 동등성을 보장하지 않는다.

힌트 보기

풀이 보기

같은 반복자의 진행 상태를 이어받는다. 새 입력·새 반복자를 만들었다는 전제가 없으면 재시작하지 않는다.

한 단계 더

순수하고 종료하는 f,g에 대해서 두 번 변환하는 map(g,map(f,xs))와 한 번의 map(x→g(f(x)),xs)을 원소별로 비교하라. 각 결과 원소는 g(f(x))로 같지만 중간 자료구조·지연 평가·부작용이 달라지면 실행 관찰의 동등성은 추가 조건을 요구한다.

언어 기능과 라이브러리 구분

새 수학 함수를 설치했다고 Python 문법 자체가 바뀌는 것일까?

준비 개념과 학습 목표

준비 개념

  • 함수 호출 f(값)은 이미 정의된 기능을 사용한다. import는 모듈의 이름을 현재 코드에서 사용할 수 있게 하는 문장이다.

  • 문법은 허용되는 코드 형태이고 라이브러리는 재사용 가능한 구현과 인터페이스의 묶음이다.

  • 미니복습: math.sqrt(9)는 제곱근 기능을 호출하는 표기이며 괄호는 일반적인 호출 문법이다.

학습 목표

  • 구문·평가 규칙·표준 라이브러리·외부 도구의 역할을 분류한다.

  • import와 함수 계약을 통해 라이브러리 사용을 추적한다.

  • 코드 모양만으로 언어와 라이브러리의 경계를 단정하지 않는다.

함수 이름을 바꾸면 문법을 고친 것일까?

이름과 기능의 경계를 작은 버전 계약으로 확인한다. 가상 모듈 calc의 v1 함수 shift(x)는 int x에 1을 더한 int를 반환하고, v2는 2를 더한다. 같은 호출 표기 calc.shift(3)은 두 버전에서 4와 5다. 함수 이름과 괄호가 같아도 라이브러리 계약은 달라질 수 있다. 이 모듈은 실제 설치물이 아닌 자체 인터페이스 모형이다.

또 다른 자체 타입 Pair는 두 int 좌표를 가진다. 같은 타입의 두 객체에 대한 __add__는 좌표별 합의 새 Pair를 반환하며 원본 두 객체는 변경하지 않는다고 명시한다. Pair(1,2)+Pair(3,4)는 Pair(4,6)이다. + 문법은 Python이 이미 정의한 연산자 규칙이고 좌표 합 구현은 타입 제공자의 계약이다. 현재 같은 타입 비교만 다루며 다른 타입·상속·reflected 우선순위의 전체 절차를 단순화하여 단정하지 않는다.

문법 기능과 제공되는 함수

if와 함수 정의 같은 구조의 허용 형태는 언어 구문과 의미 규칙에 해당한다. Python math.sqrt는 math 모듈이 제공하는 함수이며 이를 호출하는 괄호·인자 표기는 일반적인 함수 호출 문법이다. 새로운 라이브러리 함수를 가져와도 언어가 없던 문법을 자동으로 허용하게 되지는 않는다.

표준 라이브러리는 언어 또는 플랫폼과 함께 정의·제공되는 재사용 기능이다. 외부 패키지는 별도 프로젝트의 기능과 배포물을 사용한다. 두 종류 모두 버전·계약·오류 조건을 확인해야 한다. 표준이라는 말이 언제나 내장 구문 또는 모든 Python 구현에서 동일한 내부 코드라는 뜻은 아니다.

모듈은 이름과 의존성을 관리한다

import math 후 math.sqrt(9)를 쓰면 math라는 모듈 이름을 통해 sqrt를 찾는다. 이 코드에는 모듈 탐색·가져오기, 속성 조회, 함수 호출이 참여한다. 결과는 이 예제에서 실수 3.0이다. math.sqrt(-1)는 실수 영역의 계약을 벗어나 ValueError를 일으키므로 함수 이름을 아는 것만으로 모든 입력을 사용할 수 있지는 않다.

모듈화는 구현을 묶고 외부 계약을 정하는 추상화이다. 언어 자체의 모듈 규칙과 모듈 안에 들어가는 수학 기능은 구분한다. 설치나 경로 변경으로 모듈을 찾을 수 없는 문제, 정상 모듈을 호출했지만 잘못된 입력으로 실패하는 문제도 다른 층이다.

import math
value = math.sqrt(9)
print(value)

경계가 겹치는 경우도 조건을 밝힌다

일부 언어에서는 연산자 오버로딩·매크로·확장 체계로 라이브러리가 언어처럼 보이는 표기를 제공할 수 있다. Python의 +가 사용자 객체의 특수 메서드와 연결되는 것도 언어 규칙과 객체 구현이 함께 작동하는 예이다. 따라서 '괄호가 있으니 무조건 외부 라이브러리' 같은 판정은 정확하지 않다.

비교할 때 문법을 누가 정의하는지, 평가 시 무엇을 호출하는지, 배포·버전 의존성이 무엇인지 따로 묻는다. 코드를 빌드하는 도구와 편집기의 자동완성도 언어 의미 자체와 다르다. 기능을 제거해도 문법은 남는지, 기능이 필요한 프로그램만 실패하는지 생각하면 역할을 분리할 수 있다.

유효 호출 문법·함수 영역 실패

첫 두 행은 명시적으로 서로 다른 가상 버전을 선택한 별도 환경이다. 실제 import 경로 변경·패키지 설치·객체 실행을 수행하지 않았다. 네 번째 행은 공식 CPython 설명의 예외 조건이며 새 실행 증거가 아니다.

중간 과정을 따라가는 예제

Python 3.12에서 import math; value=math.sqrt(9); print(value)를 단계별로 추적한다. 입력을 -1로 바꾸면 실패 층은 무엇인가?

  1. import가 math 모듈을 사용 가능한 이름으로 연결한다.

  2. math.sqrt라는 함수에 정수 9를 전달한다.

  3. 제곱근 계약에 따라 값 3.0을 반환하여 value에 연결한다.

  4. -1을 넣은 변형은 호출 문법은 유효하지만 함수의 실수 영역 조건에서 ValueError가 발생한다.

정상 예상 출력 3.0. 변형의 문제는 괄호나 import 문법이 아니라 호출된 기능의 입력 계약이다.

조건을 바꾸어 비교하기

같은 API 모양과 다른 정책

v1 shift(3)을 쓴 기존 기대 4를 v2에도 그대로 적용할 수 있는가? 입력/반환 타입이 같다는 이유를 평가하라.

  1. v1의 값 계약은 x+1이며 v2는 x+2다.

  2. 타입 int→int는 같지만 정상 값이 달라진다.

기대 4는 v2에서 5와 불일치한다. 타입·이름 일치만으로 의미 호환성을 증명하지 않는다.

새 연산자 표기와 새 문법을 나누기

좌표별 Pair 합과 math.sqrt(-1.0)의 실패를 문법·선택 규칙·제공 기능으로 분류하라.

  1. +와 함수 호출 괄호는 기존 언어 표기다.

  2. Pair 좌표 합은 __add__ 구현 계약이며 sqrt의 실패는 입력 영역이다.

Pair 합은 언어 확장 지점을 구현한 기능이고 sqrt 실패는 함수 영역 조건이다. 둘 다 설치 후 새로운 구문을 발명했다는 결론은 아니다.

다른 문제에 적용하기

언어 간 센서 변환 어댑터의 관찰 계약

자체 센서 입력 [1,2]를 f(x)=x+1, g(y)=2*y로 변환한다. f는 Fx, g는 Gy를 각 호출 전에 로그에 붙이며 정상 종료한다. E는 list(map(f,xs))를 완성한 뒤 list(map(g,mid))를 완성하고 P는 list(map(g,map(f,xs)))를 완성한다. 각 비교는 새 입력과 새 빈 로그에서 시작한다. Java 결과 포맷은 out의 첫째·둘째 int 값 a,b에 대해 a+b+"!"이며 Python 포맷 어댑터는 str(a)+str(b)+"!"로 계획했다. 필요한 공개 계약은 변환 결과 [4,6], 로그 순서 F1,F2,G2,G3, 포맷 "10!"다. E/P와 두 포맷이 각각 계약을 만족하는지 계산하고, Python 쪽 교정을 설계하라. 실제 코드/로그/Java/Python 실행·센서 수집·학생 실험은 수행하지 않는다.

힌트 1

최종 값과 호출 순서를 별도 열로 만든다.

힌트 2

Java +의 중간 타입과 Python 문자열 변환 위치를 비교한다.

풀이와 답 확인

  1. E의 mid는 [2,3], out은 [4,6]이고 로그는 F1,F2,G2,G3다. P의 out도 [4,6]이지만 로그는 F1,G2,F2,G3여서 공개 효과 계약을 어긴다.

  2. Java는 a+b가 int 10인 뒤 "!"를 연결하여 "10!"를 만든다. Python의 계획 어댑터는 "4"+"6"+"!"로 "46!"이므로 포맷 계약에 맞지 않는다.

  3. Python에서는 먼저 정수 a+b를 계산한 뒤 str(a+b)+"!"로 변환하면 "10!"다. 로그 계약을 보존하려면 E의 완성 단계 순서를 유지한다.

  4. 순수 함수라는 새 계약으로 로그를 숨기려면 계약 변경을 먼저 승인하고 별도 값 동등성을 논해야 한다. 현재 공개 로그를 구현 편의로 지울 수 없다.

E는 값과 로그 계약을 만족하고 P는 값만 만족한다. Java 포맷은 "10!"이며 초기 Python 포맷은 "46!"로 실패한다. Python 정수 합 뒤 문자열 변환과 E 순서를 함께 유지하면 이 제한된 정상 입력의 세 관찰이 맞는다. 언어 의미와 어댑터 구현·속도·일반 입력 검증은 별도다.

해결한 뒤 점검할 것

  • 값 [4,6]과 두 로그 순서를 각기 이름 붙여 적는다.

  • Java int 10→String "10!"와 Python String "46!"의 중간 타입을 구별한다.

  • 교정 포맷과 기존 공개 로그를 모두 유지하는 설계를 제시한다.

  • 손추적과 실제 실행·학생 시험을 구별하고 전체 입력 동등성으로 확대하지 않는다.
