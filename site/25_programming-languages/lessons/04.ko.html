소단원 4.1

값·이름·필요에 의한 호출

함수가 인수를 두 번 사용하면 계산도 두 번 해야 할까?

준비 개념과 학습 목표

준비 개념

  • 함수 f(x)=x+x는 인수에 이름 x를 붙이고 몸체를 계산한다. 인수 식 2+3과 값5를 구분한다.

  • 이 단원 첫 모형의 정수는 수학적 정수이고 +는 두 값을 요구한다. 입출력·상태 변경·예외는 없는 순수 모형이다.

  • λx.e는 x를 받는 함수, (λx.e)a는 적용이다. 치환은 자유로 나타난 x만 바꾸며 다른 이름을 붙잡지 않아야 한다.

학습 목표

  • CBV·CBN·CBNeed의 인수 계산 시점과 공유 차이를 종이로 추적한다.

  • 미사용 인수의 발산과 이름 포획 반례로 적용 조건을 설명한다.

같은 식을 두 번 적으면 필요 호출도 계산을 한 번만 할까?

이 소단원의 순수 모형은 수학적 정수, 정상 덧셈·곱셈과 명시한 함수만 사용한다. f(x)=x+x에 인수 E=(2+3)*(4+1)을 전달한다. E의 값은 25이며 산술 연산은 덧셈 두 번과 곱셈 한 번이다. 값 호출은 E를 먼저 계산하여 25를 전달하고, 이름 호출은 본문의 x를 E로 바꾸어 필요할 때마다 다시 계산한다. 필요 호출은 x라는 한 바인딩에 지연 계산과 완료 값을 두어 첫 요구 뒤 25를 공유한다. 함수 호출·치환·공유 조회 비용은 아래 산술 횟수에 넣지 않는다.

f(E)는 세 방식 모두 50이지만 산술 횟수는 값 호출 4회, 이름 호출 7회, 필요 호출 4회다. 반면 pair(x,y)=x+y의 pair(E,E)는 서로 다른 두 인수 바인딩을 만든다. 필요 호출에서도 두 바인딩이 각각 E를 계산하므로 7회다. 동일한 문자열 식이라고 자동으로 전역 메모 표에 합쳐지는 것이 아니다. 별도 let t=E in pair(t,t)를 공유 바인딩으로 정의하면 E의 완료 값을 두 위치에서 읽어 4회로 줄어든다.

이 공유는 순수 계산의 결과를 다시 쓰는 규칙이다. 사용하지 않는 인수는 이름·필요 호출에서 평가하지 않을 수 있어 종료 여부도 값 호출과 달라진다. 다음 소단원의 상태를 바꾸는 tick에는 순수 계산의 비용 등가를 그대로 적용하지 않는다. 실제 Haskell 실행이나 메모리 사용량 측정은 요구하지 않는다.

값을 먼저 전달하기

값에 의한 호출 CBV에서는 인수를 값으로 평가한 다음 몸체에서 그 값을 사용한다. f(2+3)이면 인수5를 얻어 f의 몸체5+5를 계산한다. 몸체에서 x를 두 번 사용해도 인수의 2+3을 두 번 계산하는 것은 아니다. 다만 값 전달을 객체 전체의 깊은 복사와 같은 말로 쓰면 안 된다. 어떤 값이 전달되고 공유되는지는 해당 언어의 별도 규칙이다.

값에 의한 호출이라는 말만으로 여러 인수의 좌우 평가 순서가 모두 정해지는 것도 아니다. 함수 적용과 인수 평가 사이의 원칙을 정한 뒤 구체적인 순서 규칙을 명시해야 한다. 여기서는 함수 자체가 이미 값인 단일 인수 적용을 쓰며, 산술 피연산자는 왼쪽부터 필요한 값을 계산하도록 정한다.

계산을 미루기와 결과 공유

이름에 의한 호출 CBN에서는 인수 식을 먼저 값으로 만들지 않고 몸체의 필요한 위치에 지연된 계산을 연결한다. x+x에서 x 값이 각각 필요하면 2+3을 두 번 계산할 수 있다. 몸체가 인수를 사용하지 않으면 그 인수는 계산되지 않는다. 구현은 단순 문자열 복사일 필요가 없으며 호출한 쪽 환경을 보존한 thunk 같은 표현을 사용할 수 있다.

필요에 의한 호출 CBNeed는 계산을 미루고 첫 요구에서 얻은 결과를 같은 바인딩의 후속 요구가 공유하게 한다. 처음 x를 읽을 때5를 얻어 저장하고 다음 x는 그5를 사용한다. 캐시는 해당 인수 바인딩에 속하며, 세상의 모든 같은 철자 x 또는 같은 모양2+3을 하나로 묶는 전역 캐시가 아니다. 이 작은 설명은 단일 스레드의 정상 종료 순수 계산을 대상으로 한다.

전략의 조건과 종료

Ω=(λz.z z)(λz.z z)라고 쓰자. 이 식은 β 축약을 하면 다시 자기 자신이 되어 계속 계산할 수 있다. (λx.7) Ω에서 CBV는 인수를 먼저 계산하려다 결과를 얻지 못한다. CBN과 CBNeed는 몸체7이 인수를 요구하지 않으므로7을 반환할 수 있다. 어떤 전략을 써도 같은 시간에 같은 결과라는 말은 이 반례에서 성립하지 않는다.

치환에서는 이름 포획을 피해야 한다. (λx.λy.x) y의 인수 y는 자유 이름이다. 그대로 바꾸어 λy.y를 만들면 자유 y가 몸체의 매개변수에 잡혀 원래 의미가 바뀐다. 안쪽 이름을 새 이름 z로 바꾸고 λz.y를 얻어야 한다. 이 예는 자유 y의 값을 환경이 제공하거나 열린 식의 변환을 논의하는 상황이다. 닫힌 완성 프로그램이라는 전제를 몰래 붙이지 않는다.

중간 과정을 따라가는 예제

순수 모형에서 f(x)=x+x, 입력 f(2+3)를 CBV/CBN/CBNeed로 계산하라. 비용은 실제 시간 대신 산술 +를 계산한 횟수만 센다. 적용·thunk 생성·조회 비용은 세지 않는다.

  1. CBV: 인수2+3을 한 번 계산해5다. 몸체5+5를 한 번 계산해10이다. 센 + 계산은2회다.

  2. CBN: 몸체의 두 요구는 (2+3)+(2+3)이다. 왼쪽5, 오른쪽5, 마지막 합10으로 + 계산3회다.

  3. CBNeed: x 바인딩에 미계산2+3을 저장한다. 첫 요구에서5를 계산해 저장하고 둘째 요구는 저장5를 사용한다. 마지막 합10으로 + 계산2회다.

  4. 세 결과는10이다. 이것은 선택한 원시 연산 비용의 차이이며 CBNeed가 실제 장치에서 항상 더 빠르다는 측정 결과가 아니다.

결과10은 같지만 + 계산 횟수는 CBV2·CBN3·CBNeed2다. 공유 단위는 한 인수 바인딩이다.

안 쓰는 인수의 발산을 피한다

k(x)=7이고 Ω는 한 단계마다 자기 자신으로 돌아가는 비종료 식이다. k(Ω)를 세 규칙으로 비교한다.

  1. 값 호출은 먼저 Ω를 값으로 만들려 하므로 본문 7에 도달하지 않는다.

  2. 이름 호출은 x가 본문에 없어서 Ω를 요구하지 않는다. 필요 호출도 x의 지연 계산을 강제하지 않는다.

값 호출은 발산하고 이름·필요 호출은 7이다.

비교할 점

값 차이가 아니라 종료 차이다. 실제 무한 반복은 실행하지 않는다.

서로 다른 바인딩을 같은 메모로 착각한다

필요 호출의 pair(E,E)와 let t=E in pair(t,t)를 비교하라. let도 같은 필요 호출 규칙으로 지연 바인딩을 만든다.

  1. 첫 표현의 x와 y는 별도 지연 계산이므로 각각 E의 산술 3회를 수행한다.

  2. 둘째 표현은 x와 y가 같은 t를 요구한다. t의 E 계산 3회 뒤 완료 값 25를 공유한다.

  3. 본문 x+y의 덧셈 1회는 두 경우 모두 남는다.

첫 표현은 7회, 둘째 표현은 4회이고 값은 둘 다 50이다.

비교할 점

필요 호출은 바인딩별 공유이며 임의 동일 식 탐지 최적화가 아니다.

종이와 본문으로 직접 해보기

풀이 보기

CBV는 인수1회+몸체2회=3회, CBN은 인수3회+몸체2회=5회, CBNeed는 첫 인수1회+몸체2회=3회이며 결과15다. 미사용 Ω에는 CBV가 발산하고 CBN/CBNeed는9를 얻는다. 이 종료 차이는 인수를 미루는 전략과 전체 계산 종료의 관계를 보여준다.

오해와 반례

필요에 의한 호출은 같은 모양의 식을 프로그램 전체에서 반드시 한 번만 계산한다.

f(2+3)와 별도 호출 f(2+3)는 서로 다른 인수 바인딩이다. 전역 공유를 정한 별도 최적화가 없다면 첫 호출의 캐시를 둘째 호출이 자동 사용하지 않는다. 부작용이나 예외가 들어가면 공유가 관찰 결과에 영향을 줄 수 있어 언어 계약을 추가해야 한다.

소단계·대단계 의미 입문

계산 결과가25라는 것과25까지 어떤 길을 거쳤는지를 어떻게 다르게 적을까?

준비 개념과 학습 목표

준비 개념

  • e는 식, v는 이미 계산이 끝난 값이다. 여기서는 정수와 true/false가 값이다.

  • e→e′는 한 전이, e→*e′는0회 이상 전이, e⇓v는 유한한 대단계 유도로 얻는 최종 값이다.

  • let x=a in b는 x 바인딩을 만들어 b를 계산한다. 이 모형에서는 a를 값으로 만든 뒤 포획 없는 치환을 한다.

학습 목표

  • 값과 문맥 규칙을 명시하여 작은 평가열과 대단계 유도 나무를 만든다.

  • 유한 결과 부재만으로 발산과 stuck을 구분할 수 없는 이유를 설명한다.

두 번 줄여도 답이 안 나왔다는 관찰은 발산의 증명일까?

본문의 작은 언어에서 정수와 Bool은 값이고 +와 *는 두 정수에만 정의한다. 왼쪽 피연산자부터 줄이고 if는 조건을 값으로 만든 뒤 선택한 한 분기만 남긴다. let x=v in body는 값 v를 자유로운 x 자리에 치환하는 한 단계다. 한 단계 화살표는 규칙 한 번이고 여러 단계 화살표는 0번 이상이다. 실제 인터프리터 실행을 흉내 낸 종이 규칙이며 문자열 Python 코드를 그대로 실행하는 문법이 아니다.

if true then (1+2)*(3+4) else (2+true)는 분기 선택, 왼쪽 덧셈, 오른쪽 덧셈, 곱셈의 네 단계를 거쳐 21이다. 선택하지 않은 오류 분기는 평가하지 않는다. 같은 식에 단계 예산 2만 허용하면 3*(3+4)가 남고 다음 규칙이 있어 아직 결과를 모르는 중간 상태다. 예산 초과를 stuck이나 발산으로 판정하면 유한하지만 긴 정상 계산을 잘못 분류한다.

작은 단계가 없고 이미 값이면 정상 완료다. 작은 단계가 없는데 값도 아니면 stuck이다. 2+true가 그런 예다. Ω→Ω→…는 단계가 계속 있어 발산한다. 정상 결과만 기록하는 대단계 관계에 결론이 없는 사실만으로 stuck과 발산을 구별할 수 없으며, 유한 관찰 예산으로 일반 발산을 결정할 수도 없다.

먼저 확인할 개념
  • 작은 단계와 대단계

    하나의 결과와 중간 경로 관찰을 나눈다.

  • 실패 이후 정상 경로 생략

    실제 Python 예외와 작은 언어 stuck은 같은 개념이 아니지만 정상 완료와 실패를 분리하는 관점을 연결한다.

한 단계의 선택

정수 n과 산술 e1+e2, e1*e2, let, if를 가진 작은 모형을 쓰자. 산술은 수학적 정수 연산이고 오버플로는 없다. 왼쪽 피연산자가 전이할 수 있으면 왼쪽을 한 번 전이한다. 왼쪽이 값일 때만 오른쪽을 전이한다. 두 정수 값이 준비되면 연산 결과로 바꾼다. 이 세 경우를 구분해야 같은 식에서 다음 단계가 무엇인지 정해진다.

let은 바인딩 식을 먼저 전이하고 값이 되면 몸체의 해당 자유 변수를 값으로 치환한다. if는 조건을 먼저 평가하고 true면 첫 분기, false면 둘째 분기만 남긴다. 이 규칙의 한 단계는 언어 모형의 단위다. 실제 CPU 명령 한 개, 벽시계 시간1초 또는 소스 코드 한 줄과 같다고 해석하지 않는다.

결과를 직접 연결하기

대단계에서는 숫자 n⇓n이고 산술 양쪽 e1⇓n1, e2⇓n2가 유도되면 e1+e2⇓n1+n2를 유도한다. 여러 전이의 중간 식 대신 전제들의 유도 나무로 결과를 설명한다. 전제를 가정 없이 건너뛰는 것이 아니라 각각 정상 평가된다는 근거가 필요하다. let도 바인딩 결과를 얻고 치환한 몸체를 평가해야 결론을 얻는다.

작은 순수 모형에서 맞게 정한 두 의미가 e→*v와 e⇓v를 같은 정상 결과로 연결하도록 증명할 수 있다. 하지만 소단계가 한 번 존재한다는 것과 최종값까지 유한하게 갈 수 있다는 것은 다르다. v는 더 전이하지 않으면서도 v→*v가 참이고 v⇓v가 참이다. 별표 관계에0단계가 포함된다는 점을 빼먹지 않는다.

멈춤과 성공은 다르다

잘못된 식2+true를 추가로 허용하되 +는 정수 두 개에만 정의한다고 하자. 양쪽이 값이지만 적용할 규칙이 없고 전체 식은 값이 아니므로 stuck 상태다. 반면 Ω를 지원하는 함수 모형은 Ω→Ω→…처럼 계속 전이하여 정상값을 얻지 못한다. 이 두 경우 모두 정상 결과 대단계 e⇓v가 없지만 실패 양상은 다르다.

이 한계는 정상 종료 결과만 기록하는 유한 대단계 관계에 관한 설명이다. 오류 결과를 포함하거나 무한 유도를 다루도록 확장한 다른 대단계 의미까지 불가능하다고 결론 내리지 않는다. 값이 아닌 모든 식이 전이할 수 있다는 progress 주장도 위2+true 같은 식을 허용하면 자동 성립하지 않는다. 적절한 타입과 규칙의 조건을 확인해야 한다.

소단원 4.3

평가 순서와 부작용

덧셈의 양쪽이 같은 함수를 호출해도 어느 쪽부터 읽는지가 답을 바꿀까?

준비 개념과 학습 목표

준비 개념

  • 상태 σ는 이름과 현재 값의 대응이다. ⟨e,σ⟩로 식과 상태를 같이 적는다.

  • 부작용은 값 외에 상태 변경·입출력처럼 관찰 가능한 변화다. 같은 값이 나와도 로그가 달라질 수 있다.

  • 우선순위는 식의 묶임, 평가 순서는 자식 식을 실제 계산하는 순서다. 괄호만으로 모든 언어의 자식 순서가 정해지는 것은 아니다.

학습 목표

  • 명시한 상태 모형에서 순서별 결과·마지막 상태를 추적한다.

  • 단락 평가·지연 공유·우선순위와 평가 순서의 차이를 반례로 설명한다.

계산 결과가 같아도 로그 순서는 다른 프로그램일까?

이번 종이 모형은 공유 정수 c와 로그 L을 상태로 둔다. tick()은 현재 c를 반환하고 c를 1 늘린다. log(tag,v)는 L 끝에 tag를 붙이고 v를 반환한다. 각 문제는 명시한 초기 상태에서 독립적으로 시작한다. 식의 의미를 결과 값만으로 보지 않고 (결과,c,L)의 관찰로 정한다. 예외나 자원 고갈·동시성은 이 모형에 포함하지 않는다.

log(A,2)+log(B,3)는 양쪽 평가 순서에서 결과 5와 같은 c를 얻지만 L은 AB 또는 BA다. 반면 tick()+tick()은 c=0에서 어느 쪽 먼저든 값 1과 최종 c=2를 얻는다. 교환이 한 예제의 전체 관찰을 유지하는 것과 모든 효과식에 안전하다는 정리는 다르다. tick()-tick()은 왼쪽 먼저 −1, 오른쪽 먼저 1로 값까지 달라진다.

조건부 평가도 상태를 바꾼다. if tick()==0 then tick() else 9는 c=0에서 조건이 0을 읽고 c=1이 된 뒤 선택한 분기가 1을 반환하여 c=2다. 원래 조건을 두 번 실행하는 변형은 같은 상태를 읽지 않는다. Python에서는 표현식을 왼쪽부터 평가하고 and/or는 필요한 쪽만 평가하지만 이 식 전체는 Python 프로그램 실행 결과가 아닌 자체 규칙 추적이다.

먼저 확인할 개념
  • 효과가 있는 평가 순서

    값·최종 상태·로그를 각각 관찰한다.

  • 값 0과 상태 표지의 구별

    0을 읽었다는 결과와 다음 상태 및 단락 조건을 혼동하지 않는다.

값과 상태를 함께 따라가기

자체 모형의 tick()은 카운터c의 이전 값을 반환하고 c를1증가시킨다. 초기c=0에서 한 번 호출하면 값0·상태1이다. 같은 문자열 tick()도 다른 시점에 평가되면 현재 상태가 달라 결과가 달라질 수 있다. 따라서 식만 지우며 숫자를 계산하면 어느 호출이 어느 상태를 읽었는지 놓친다.

산술 피연산자를 왼쪽부터 끝내는 정책과 오른쪽부터 끝내는 정책을 각각 가정해 비교한다. 이것은 하나의 실제 언어가 두 정책을 마음대로 갖는다는 설명이 아니다. 특정 언어·버전의 보장에 관한 질문은 그 언어 참조를 읽어야 한다. Python 공식 참조는 표현식의 왼쪽에서 오른쪽 평가를 명시하지만 여기의 tick 표는 가상의 상태 의미를 종이로 비교하는 활동이다.

묶임과 실행 순서를 구분하기

a()+10*b()는 우선순위에 따라 Add(a(),Mul(10,b()))로 묶인다. 그렇다고 곱셈 기호가 먼저 보인다는 이유로 b 호출이 항상 a보다 먼저 실행되는 것은 아니다. 평가 규칙이 전체 왼쪽 자식을 먼저 계산하면 a를 호출하고 오른쪽 곱셈 자식을 계산한다. 괄호는 트리 구조를 정하며 자식 방문 정책은 따로 정한다.

반대로 logA()가 값2를 주고 A를 기록하고 logB()가 값4를 주고 B를 기록한다면 logA()+3*logB()는 양 정책에서 값14여도 로그AB 또는BA가 될 수 있다. 프로그램의 관찰을 결과 숫자로만 정의하면 이 차이를 놓친다. 비교하려는 관찰 범위에 값·상태·출력·예외 순서 중 무엇이 포함되는지 먼저 적는다.

건너뛰기와 공유도 효과에 관여한다

불리언 and를 왼쪽이 false이면 오른쪽을 평가하지 않는 단락 연산으로 정하면 false and tickPositive()는 카운터를 바꾸지 않는다. 모든 인수를 먼저 평가하는 일반 함수 andFn(false,tickPositive())와는 다를 수 있다. 단락 연산의 구문·규칙을 함수 호출의 CBV와 같은 것으로 취급하지 않는다.

부작용 인수에는 CBN과 CBNeed의 중복/공유 차이가 값에도 드러난다. f(x)=x+x에 tick()을 넘기고 덧셈이 왼쪽 요구부터 진행한다고 정하면 CBN은 두 번의 상태 변화를 낼 수 있고 CBNeed는 첫 결과를 공유한다. 순수 정상 계산에서 성립한 동치나 비용 비교를 상태 변경 모형에 조건 없이 옮기지 않는다. 실제 지연 언어의 효과·예외·재진입 정책은 별도 계약이다.

중간 과정을 따라가는 예제

초기c=0, tick()은 이전c를 반환하고c를1증가시킨다. tick()+10*tick()의 왼쪽 우선 정책과 오른쪽 우선 정책 결과·마지막c를 구하라. 정수 곱셈·덧셈은 상태를 바꾸지 않는다.

  1. 왼쪽 우선에서 첫 tick은0을 반환하고c=1이다. 오른쪽 곱셈의 tick은1을 반환하고c=2가 된다.

  2. 따라서 왼쪽값0과 오른쪽값10*1=10을 더해 결과10, 마지막c=2다.

  3. 오른쪽 우선에서는 곱셈 안 tick이 먼저0을 반환해c=1, 오른쪽값0이다. 이어 왼쪽 tick이1을 반환해c=2다.

  4. 마지막 결과는1+0=1이며c=2다. 동일 최종 상태만 비교하면 값10/1의 차이를 놓친다. 실제 코드 출력이 아니라 명시한 정책의 종이 결과다.

왼쪽 우선은(값10,c2), 오른쪽 우선은(값1,c2)다. 부작용과 상태 읽기 때문에 순서가 관찰 값에 영향을 준다.

같은 합을 전체 등가로 확대한다

log(A,2)+log(B,3)를 두 순서에서 비교하라.

  1. 왼쪽 먼저는 A를 기록한 뒤 B를 기록한다.

  2. 오른쪽 먼저는 B를 기록한 뒤 A를 기록한다.

  3. 덧셈은 두 경우 모두 2+3=5다.

관찰 로그가 다르므로 주어진 (값,c,L) 계약에서 등가가 아니다.

숫자 반환만 보던 순수 모형의 관찰 범위를 확장했다.

조건을 재사용하는 대신 다시 실행한다

원래 if tick()==0 then tick() else 9와 변형 if tick()==0 then (if tick()==0 then tick() else 9) else 9를 각 c=0에서 추적한다.

  1. 원래는 첫 tick이 0을 반환하고 c=1, then의 tick이 1을 반환하고 c=2다.

  2. 변형의 안쪽 조건 tick은 1을 반환하고 c=2라 조건이 거짓이다.

  3. 변형은 9를 반환하며 세 번째 tick은 실행하지 않는다.

원래 값 1/c=2, 변형 값 9/c=2다.

종이와 본문으로 직접 해보기

힌트 보기

인수가 함수 시작 전에 값이 되는지, 요구마다 실행되는지, 첫 정상 결과가 공유되는지 나누어라.

풀이 보기

CBV는 tick을 한 번 실행해0을 전달하고0+0=0,c=1이다. CBN은 첫 요구0/c1, 둘째 요구1/c2여서 결과1,c=2다. CBNeed는 첫 요구0/c1을 저장해둘째도0이므로 결과0,c=1이다. 별도 초기 상태에서 false and tickPositive()는 오른쪽을 건너뛰어 false,c=0이다.

오해와 반례

값에 의한 호출이면 부작용이 있는 두 인수의 계산 순서도 모든 언어에서 왼쪽 우선이다.

CBV는 적용 전에 인수를 값으로 만든다는 원칙이지만 그 인수끼리의 순서는 별도 규칙이다. 또한 로그A/B의 값이 같아도 관찰 로그가 달라질 수 있다. 실제 언어의 미규정 순서를 관측한 한 실행의 순서로 고정하지 않는다. C의 동일 객체에 대한 순서 없는 변경 같은 경우는 UB 조건도 별도로 검토해야 하므로 이 활동을 C 실행 예로 옮기지 않는다.
