소단원 14.1

환경·클로저·저장소 구현

함수 안의 이름은 함수가 만들어진 곳과 호출된 곳 중 어디서 찾을까?

준비 개념과 학습 목표

준비 개념

  • 사전과 연결 구조

  • 정적 범위

  • 가변 상태와 별칭

학습 목표

  • 이름의 연결과 저장된 값의 변경을 두 표로 추적한다.

  • 클로저의 정의 환경을 사용하는 호출 절차를 구성한다.

학습용 언어의 실행 규칙을 정한다

이 소단원은 실제 제품 언어 전체를 구현하는 대신 작은 언어를 설계한다. 정수, 변수, 덧셈, let, 함수, 호출을 먼저 지원하고 나중에 가변 셀을 추가한다. 호출은 인자를 먼저 값으로 계산하는 방식이며 범위는 정적 범위다. 이 두 선택을 바꾸면 결과도 바뀔 수 있다.

환경 E는 이름을 값에 연결하는 표다. let의 본문을 계산할 때 새 연결을 앞에 추가하며 기존 환경을 덮어 고치지 않는다. 같은 이름이 두 번 나타나면 가까운 연결을 찾는다. 함수는 매개변수·본문·정의 환경의 묶음인 클로저로 저장한다.

호출은 정의 환경에서 시작한다

함수 호출을 구현하는 자체 의사 절차는 다음과 같다. 현재 환경에서 함수식을 계산해 클로저를 얻고 인자식을 계산한다. 클로저가 보관한 환경에 매개변수 연결을 추가한 다음 본문을 계산한다. 호출자의 다른 지역 이름을 본문에 몰래 넣지 않는다.

환경을 공유하려면 프레임을 변경하지 않는 규칙이나 별도 범위 해석 장치가 필요하다. let을 나중에 추가하면서 동일 사전을 계속 수정하면 앞서 만든 함수가 보게 될 범위까지 바뀔 수 있다. 아래 표에서는 환경 프레임을 불변으로 유지한다.

가변 셀은 주소와 값을 분리한다

이제 자체 모형에 새 셀·셀 읽기·셀 쓰기를 넣자. E는 이름을 위치 ℓ에 연결하고 저장소 S는 위치를 현재 값에 연결한다. ℓ은 교육용 식별자이며 실제 기계 주소가 아니다. 이름이 같은 위치를 가리키면 한쪽의 쓰기가 다른 쪽의 읽기에 보인다.

클로저가 보관한 환경이 불변이어도 그 환경이 가리킨 셀은 바뀔 수 있다. 환경을 붙잡는다는 말이 모든 값을 깊게 복사한다는 뜻은 아니다. 셀의 수명을 유지하는 메모리 관리가 따로 필요하며 이 소단원은 해제기나 garbage collector를 실제 구현하지 않는다.

중간 과정을 따라가는 예제

자체 정적 범위 언어에서 let x=4 in let f=(fun y -> x+y) in let x=9 in f(3)의 결과를 구하라. 이어 셀 a와 b가 같은 ℓ7을 가리키고 S[ℓ7]=4인 상태에서 b에 9를 쓰고 a를 읽어라.

  1. f는 매개변수 y, 본문 x+y, 정의 환경 {x:4}를 저장한다.

  2. 호출자의 환경에는 x:9가 있지만 본문은 정의 환경을 확장한 {y:3,x:4}에서 계산한다.

  3. 4+3=7이다. 호출자의 x를 참조하는 잘못된 동적 범위 구현이라면 9+3=12가 된다.

  4. 셀 예제는 E[a]=E[b]=ℓ7이다. b를 통한 쓰기는 S[ℓ7]을 9로 바꾸므로 a의 읽기도 9다.

정적 범위 함수의 결과는 7, 공유 셀의 읽기는 9다. 새 x 연결과 기존 셀 변경을 구별한다.

종이와 본문으로 직접 해보기

서로 다른 셀 a→ℓ1, b→ℓ2의 초기값이 모두 4다. b에 9를 쓴 뒤 a+b를 구하라. 이어 c가 a의 위치를 별칭으로 받고 c에 6을 썼을 때 a+b를 다시 구하라.

힌트 보기

E의 위치와 S의 값을 따로 적고 쓰기마다 어느 S 항목만 바뀌는지 표시한다.

풀이 보기

첫 쓰기 뒤 S[ℓ1]=4, S[ℓ2]=9이므로 합은 13이다. c→ℓ1에 6을 쓰면 a도 6을 읽어 합 15다. 값이 처음에 같다는 이유로 두 셀이 같은 위치인 것은 아니다.

오해와 반례

클로저는 정의 시점의 모든 값을 복사하므로 공유 셀의 변경도 볼 수 없다.

불변 연결과 가변 셀의 현재 값을 분리해야 한다. 정의 환경이 보관한 위치가 여전히 같은 셀을 가리키면 이후 쓰기를 읽을 수 있다. 값 포획·위치 포획은 언어의 별도 규칙이다.

자기점검

함수 본문에 호출자의 x=9를 자동 연결하는가?

답과 이유 보기

이 소단원의 정적 범위 모형에서는 아니다.

클로저의 정의 환경에 매개변수를 추가한다.

E[a]=E[b]가 같은 위치라면 b의 쓰기를 a가 읽는가?

답과 이유 보기

그렇다.

두 이름이 같은 저장소 항목을 조회한다.

두 셀의 초기값이 4이면 두 위치도 같은가?

답과 이유 보기

아니다.

값의 같음과 위치의 같음은 별개다.

한 단계 더

가변 셀을 새로 만드는 함수 make(초기값)를 종이에 설계하라. make(0)를 두 번 호출하면 서로 다른 셀이어야 한다. 첫 카운터를 두 번, 둘째를 한 번 증가시킨 결과는 2와 1이다. 반대로 한 전역 셀을 모두 공유하는 설계는 3을 공유하므로 계약과 다르다. 실제 인터프리터·메모리 관리 구현은 다음 프로젝트에서 별도로 검증한다.

소단원 14.2

타입 검사기와 진단

식을 실행하지 않고도 2+true의 잘못된 조합을 찾아낼 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 문법 트리

  • 정수와 불리언

  • 함수의 재귀

학습 목표

  • 작은 타입 규칙을 트리 순회 검사 절차로 바꾼다.

  • 실행 환경과 타입 환경을 구별하고 위치가 있는 오류를 설명한다.

작은 규칙을 먼저 명시한다

자체 언어 T에서는 정수 타입 Int와 불리언 Bool만 다룬다. 정수 상수는 Int, true와 false는 Bool이다. 덧셈은 두 피연산자가 Int일 때만 Int이며 비교 <=는 두 Int를 받아 Bool을 만든다. Python의 bool이 int의 서브타입인 동작을 이 언어에 가져오지 않는다.

타입 환경 Γ는 이름을 타입에 연결한다. 실행 환경이 x의 값 7을 담는다면 Γ는 x가 Int임을 담는다. 둘은 목적이 다르다. 변수 검사에서는 Γ의 연결을 찾고 이름이 없으면 정의되지 않은 이름의 오류를 낸다.

트리를 안쪽부터 검사한다

let x=e1 in e2에서는 e1의 타입 t1을 구하고 Γ에 x:t1을 추가한 환경으로 e2를 검사한다. let 전체 타입은 e2의 타입이다. 덧셈에서는 좌우 타입을 검사하고 하나라도 Bool이면 Int와의 불일치를 보고한다.

if의 조건은 Bool이어야 하며 이 자체 언어에서 양쪽 가지의 타입은 같아야 한다. 정적 검사는 실행 때 선택되지 않을 가지도 검사한다. 조건이 true라는 이유만으로 반대 가지의 타입 오류를 무시하지 않는다. 최적화 뒤 검사하는 다른 도구의 규칙과 혼동하지 않는다.

진단도 언어 도구의 인터페이스다

같은 오류라도 '실패' 한 단어만 출력하면 사용자는 어디를 고칠지 알기 어렵다. 자체 검사기는 토큰 범위를 트리 노드에 보관하고 연산 이름, 필요한 타입, 발견한 타입, 위치를 보고하도록 설계한다. 이 소단원의 위치는 편집기 구현 대신 표현식 경로로 표시한다.

타입 검사를 통과했다고 모든 업무 요구나 자원 조건을 만족하는 것은 아니다. 정수 범위·예외·종료 보장은 언어 규칙과 실행 모델에 따라 따로 다뤄야 한다. 진행과 타입 보존 같은 성질도 그 규칙에 대한 증명이 있어야 하며 몇 개의 시험 성공으로 증명됐다고 기록하지 않는다.

중간 과정을 따라가는 예제

자체 언어 T에서 let n=7 in if n<=10 then n+2 else 0을 검사하라. else를 false로 바꾸거나 n+true로 바꾸었을 때의 오류도 구하라.

  1. 7은 Int이므로 본문 환경은 Γ={n:Int}이다.

  2. n<=10은 Int 두 개를 비교해 Bool이다. 조건의 요구를 만족한다.

  3. n+2와 0은 모두 Int이므로 if와 let 전체가 Int다. 실행을 손으로 추적하면 true 가지에서 9다.

  4. else false는 Bool이어서 가지 Int/Bool 불일치다. n+true는 then/add/right 경로에서 필요한 Int 대신 Bool을 발견한다.

원래 식은 Int이다. 수정 두 경우는 각각 가지 불일치와 덧셈 오른쪽 타입 불일치이며 오류 경로가 다르다.

종이와 본문으로 직접 해보기

if true then 1 else false와 let x=false in x<=3을 검사하라. 첫 식의 false 가지가 실행되지 않는다는 이유로 검사를 생략해도 되는가?

힌트 보기

if의 조건과 양쪽 가지 규칙, 비교의 두 Int 규칙을 각각 적용한다.

풀이 보기

첫 식은 가지 Int/Bool 불일치다. 이 정적 검사 계약에서는 선택되지 않을 가지도 검사한다. 둘째는 x가 Bool이어서 비교의 왼쪽에 필요한 Int를 만족하지 못한다. 구문이 문법에 맞는 것과 타입 규칙 통과는 다르다.

오해와 반례

타입 검사를 통과한 프로그램은 요구사항·성능·종료까지 정확하다.

이 검사기는 표현식의 타입 조합을 다룬다. 같은 Int 결과라도 9를 반환해야 하는 요구에 8을 반환할 수 있고, 다른 언어의 반복이나 자원 제한은 추가 문제다. 주장하는 보장 범위를 규칙과 증거에 맞춰 제한한다.

자기점검

Γ[x]에 실행값 7을 저장하는가?

답과 이유 보기

아니다. 타입 Int를 저장한다.

정적 환경과 동적 환경은 목적이 다르다.

자체 T에서 true+2를 Int로 허용하는가?

답과 이유 보기

허용하지 않는다.

Bool을 Int로 자동 변환하는 규칙을 넣지 않았다.

타입 오류 진단에 기대한 타입과 실제 타입을 함께 적는 이유는?

답과 이유 보기

잘못된 조합과 수정 지점을 분명히 하기 위해서다.

위치만으로는 어떤 조건을 위반했는지 알기 어렵다.

한 단계 더

성공 사례 7+2, 7<=2, let z=2 in z+1과 실패 사례 7+false, 미정의 z, if 1 then 2 else 3을 표로 만들어라. 예상 타입은 Int/Bool/Int이며 실패 원인은 덧셈·이름·조건이다. 실제 검사기 실행은 미수행이고 이 표는 구현 후 대조할 자체 시험 계획이다.

소단원 14.3

여러 패러다임으로 같은 문제 비교

반복문과 객체와 함수 조합으로 같은 합을 구하면 무엇을 비교해야 할까?

준비 개념과 학습 목표

준비 개념

  • 반복문과 누적값

  • 객체와 메서드

  • filter·map·fold

학습 목표

  • 같은 입력·출력 계약으로 세 설계를 비교한다.

  • 결과·효과·비용·오류 처리를 분리하여 보고한다.

비교 전에 계약을 고정한다

자체 문제는 유한 정수 목록에서 짝수만 고르고 각 수의 제곱 합을 계산하는 것이다. 입력은 이 단원에서는 유효한 정수 목록으로 제한하고 음수도 허용한다. 빈 목록의 결과는 0, 입력 목록은 변경하지 않는다. 산술은 예제 범위 안에서 오버플로가 없다고 가정한다.

같은 문제라고 해도 한 구현이 음수를 버리고 다른 구현이 음수를 포함하면 공정한 비교가 아니다. 오류 입력을 거절할지 변환할지도 계약에 적어야 한다. 이 단원에서는 문자열이 섞인 입력을 유효 사례로 처리하지 않는다.

세 가지 설계의 중간 상태를 추적한다

명령형 설계는 total을 0으로 시작하고 각 원소에서 짝수이면 total에 x*x를 더한다. 객체 설계는 새 집계 객체의 내부 total을 0으로 시작한 뒤 같은 원소들을 add 메서드로 전달한다. 재사용 가능한 객체라면 누적을 유지할지 초기화할지 별도 약속이 필요하다.

함수 조합 설계는 filter(even), map(square), fold(add,0)의 순서다. 리스트를 모두 만드는 구현과 지연 스트림을 소비하는 구현은 중간 저장량이 다르다. 함수 이름이 같다고 모든 언어에서 평가 순서·메모리 동작까지 같다고 가정하지 않는다.

결과 외에 관찰할 항목을 정한다

세 방식이 같은 값을 반환해도 입력 변경, 전역 상태, 로그 출력이 다르면 관찰 가능한 효과가 다를 수 있다. 자체 비교표는 결과와 입력 보존, 검사 횟수, 곱셈 횟수, 중간 값 보관을 따로 기록한다. 읽기 쉬움은 실제 독자에게 평가받지 않았으면 설계 판단으로 남긴다.

지연 처리는 모든 항목을 즉시 만들지 않는 장점이 있지만 한 번 소비된 반복자나 공유 객체를 다시 쓰는 문제가 있다. 같은 목록을 한 번 처리하는 계약과 여러 번 처리하는 계약을 구별하자. 비용 표는 자체 연산 모형이며 실행 시간이나 실제 할당량을 측정한 자료가 아니다.

중간 과정을 따라가는 예제

입력 [-2,1,2,3,4]를 새 상태에서 세 방식으로 처리한다. 짝수 여부 검사와 제곱 곱셈 횟수, total의 변화를 구하라.

  1. 짝수 원소는 -2,2,4다. 음수 -2도 2로 나눈 나머지가 0이므로 포함한다.

  2. 제곱은 4,4,16이며 합은 24다. 명령형과 새 객체의 total은 원소별로 0→4→4→8→8→24로 변한다.

  3. 조건 검사는 입력 5개에 대해 5번이며 제곱 곱셈은 채택된 3개에서 3번이다. fold가 0부터 각 제곱을 더하는 모형에서는 덧셈도 3번이다.

  4. 즉시 리스트 모형은 선택 목록 3개와 제곱 목록 3개를 만들 수 있다. 지연 모형은 이 두 목록 전체를 만들지 않아도 되지만 입력 목록 자체나 실제 라이브러리의 비용이 사라지는 것은 아니다.

세 결과는 24다. 자체 연산 모형의 조건 검사 5번·곱셈 3번을 실제 속도 측정으로 해석하지 않는다.

종이와 본문으로 직접 해보기

빈 입력과 [-3,-2,0,2]의 결과를 구하라. total을 보존하는 객체에 [2,4]를 두 번 전달하면 한 번만 처리한 계약과 어떻게 다른가?

힌트 보기

0도 짝수이며 제곱은 0이다. 객체를 새로 만들었는지 같은 객체를 재사용했는지 표시한다.

풀이 보기

빈 입력은 초기값 0이다. 두 번째 입력은 4+0+4=8이다. [2,4]의 한 번 결과는 4+16=20이고 같은 객체에 다시 누적하면 40이 된다. 독립 호출마다 20을 기대한다면 새 객체나 명시적 초기화가 필요하다.

오해와 반례

함수형 표기라면 다른 표기보다 자동으로 빠르고 효과도 전혀 없다.

표기만으로 성능이나 순수성이 결정되지 않는다. 전달한 함수가 로그를 출력할 수도 있고 중간 리스트를 만들 수도 있다. 결과 계약·효과·실제 비용을 각각 확인해야 한다.
