소단원 14.1

환경·클로저·저장소 구현

함수 안의 이름은 함수가 만들어진 곳과 호출된 곳 중 어디서 찾을까?

준비 개념과 학습 목표

준비 개념

  • 사전과 연결 구조

  • 정적 범위

  • 가변 상태와 별칭

학습 목표

  • 이름의 연결과 저장된 값의 변경을 두 표로 추적한다.

  • 클로저의 정의 환경을 사용하는 호출 절차를 구성한다.

새 이름표를 붙일 때 오른쪽 식의 같은 이름은 옛 이름표를 읽을까?

원본의 작은 언어를 유지하며 let은 비재귀 바인딩이라고 정한다. 자체 초기 환경 E0에는 x→7이 있다. let x=x+1 in ...의 오른쪽 x+1을 E0에서 먼저 구하면 8이다. 그 뒤 새 환경 E1에 x→8을 둔다. 처음부터 새 x를 찾도록 하면 아직 값이 없는 자기 참조가 된다. 계산 결과를 저장하기 전과 후의 환경을 나누는 일이 변수 이름을 해석하는 실제 규칙이다.

E1에서 f=(fun y -> x+y)를 만들고 바깥 몸체에 새 x→20을 바인딩한 뒤 f(2)를 호출한다고 하자. 불변 값 환경을 보관한 클로저는 정의 때의 x 값 8을 읽어 10을 낸다. 호출 때의 x 값 20을 사용하면 22다. 이것은 실제 OCaml 프로그램 실행 결과가 아니라 원본의 어휘적 작은 언어를 손으로 해석한 사례다.

별도 가변 저장소 확장에서는 환경의 x가 값 자체 대신 위치 ℓ을 가리킨다. f가 x→ℓ을 보관하고 처음 S(ℓ)=8이었더라도 이후 같은 위치에 11을 쓰면 f(2)는 13이다. 어휘적 범위는 어느 이름표/위치를 참조하는지 결정하며 값이 항상 생성 때로 고정된다는 뜻은 아니다. 함수가 밖으로 반환돼도 필요한 환경과 위치의 수명은 유지돼야 한다.

학습용 언어의 실행 규칙을 정한다

이 소단원은 실제 제품 언어 전체를 구현하는 대신 작은 언어를 설계한다. 정수, 변수, 덧셈, let, 함수, 호출을 먼저 지원하고 나중에 가변 셀을 추가한다. 호출은 인자를 먼저 값으로 계산하는 방식이며 범위는 정적 범위다. 이 두 선택을 바꾸면 결과도 바뀔 수 있다.

환경 E는 이름을 값에 연결하는 표다. let의 본문을 계산할 때 새 연결을 앞에 추가하며 기존 환경을 덮어 고치지 않는다. 같은 이름이 두 번 나타나면 가까운 연결을 찾는다. 함수는 매개변수·본문·정의 환경의 묶음인 클로저로 저장한다.

호출은 정의 환경에서 시작한다

함수 호출을 구현하는 자체 의사 절차는 다음과 같다. 현재 환경에서 함수식을 계산해 클로저를 얻고 인자식을 계산한다. 클로저가 보관한 환경에 매개변수 연결을 추가한 다음 본문을 계산한다. 호출자의 다른 지역 이름을 본문에 몰래 넣지 않는다.

환경을 공유하려면 프레임을 변경하지 않는 규칙이나 별도 범위 해석 장치가 필요하다. let을 나중에 추가하면서 동일 사전을 계속 수정하면 앞서 만든 함수가 보게 될 범위까지 바뀔 수 있다. 아래 표에서는 환경 프레임을 불변으로 유지한다.

가변 셀은 주소와 값을 분리한다

이제 자체 모형에 새 셀·셀 읽기·셀 쓰기를 넣자. E는 이름을 위치 ℓ에 연결하고 저장소 S는 위치를 현재 값에 연결한다. ℓ은 교육용 식별자이며 실제 기계 주소가 아니다. 이름이 같은 위치를 가리키면 한쪽의 쓰기가 다른 쪽의 읽기에 보인다.

클로저가 보관한 환경이 불변이어도 그 환경이 가리킨 셀은 바뀔 수 있다. 환경을 붙잡는다는 말이 모든 값을 깊게 복사한다는 뜻은 아니다. 셀의 수명을 유지하는 메모리 관리가 따로 필요하며 이 소단원은 해제기나 garbage collector를 실제 구현하지 않는다.

각 행의 환경은 이름표 묶음이다. 새 바인딩은 이전 환경을 파괴하지 않는다고 정하며 마지막 행에서 E2를 사용하는 오류를 찾는다. 별도 위치 모형의 저장소 쓰기는 이 표의 값 바인딩 교체와 다르다.

중간 과정을 따라가는 예제

자체 정적 범위 언어에서 let x=4 in let f=(fun y -> x+y) in let x=9 in f(3)의 결과를 구하라. 이어 셀 a와 b가 같은 ℓ7을 가리키고 S[ℓ7]=4인 상태에서 b에 9를 쓰고 a를 읽어라.

  1. f는 매개변수 y, 본문 x+y, 정의 환경 {x:4}를 저장한다.

  2. 호출자의 환경에는 x:9가 있지만 본문은 정의 환경을 확장한 {y:3,x:4}에서 계산한다.

  3. 4+3=7이다. 호출자의 x를 참조하는 잘못된 동적 범위 구현이라면 9+3=12가 된다.

  4. 셀 예제는 E[a]=E[b]=ℓ7이다. b를 통한 쓰기는 S[ℓ7]을 9로 바꾸므로 a의 읽기도 9다.

정적 범위 함수의 결과는 7, 공유 셀의 읽기는 9다. 새 x 연결과 기존 셀 변경을 구별한다.

조건을 바꾸어 비교하기

초기식의 이름이 아직 새 이름은 아님

E0={x→7}에서 let x=x+1 in x+x를 구한다. 처음부터 새 x를 사용하는 구현과 비교하라.

  1. 오른쪽 초기식은 E0에서 7+1=8이다.

  2. 몸체는 새 x 값 8을 두 번 읽는다.

정상 결과는 16이다. 새 바인딩을 초기식 전에 활성화하면 비재귀 let 규칙을 어긴다.

비교할 점

원본의 단순 값 저장을 초기식의 범위 경계까지 확장한다.

위치 포획과 값 복사는 다른 계약

각각 새 상태에서 값 x=8을 포획한 f와 위치 x→ℓ/S(ℓ)=8을 포획한 g를 만든다. 값 모형에는 바깥 x=11을 새 바인딩하고, 위치 모형에는 S(ℓ)=11을 쓴 뒤 두 함수에 2를 전달한다.

  1. f의 보관 환경은 값 8을 유지한다.

  2. g는 같은 ℓ의 현재 값 11을 읽는다.

f(2)는 10, g(2)는 13이다. 두 경우 모두 정의된 이름 관계를 사용한다.

비교할 점

어휘적 범위와 가변 값의 시간 변화를 분리한다.

종이와 본문으로 직접 해보기

서로 다른 셀 a→ℓ1, b→ℓ2의 초기값이 모두 4다. b에 9를 쓴 뒤 a+b를 구하라. 이어 c가 a의 위치를 별칭으로 받고 c에 6을 썼을 때 a+b를 다시 구하라.

힌트 보기

E의 위치와 S의 값을 따로 적고 쓰기마다 어느 S 항목만 바뀌는지 표시한다.

풀이 보기

첫 쓰기 뒤 S[ℓ1]=4, S[ℓ2]=9이므로 합은 13이다. c→ℓ1에 6을 쓰면 a도 6을 읽어 합 15다. 값이 처음에 같다는 이유로 두 셀이 같은 위치인 것은 아니다.

오해와 반례

클로저는 정의 시점의 모든 값을 복사하므로 공유 셀의 변경도 볼 수 없다.

불변 연결과 가변 셀의 현재 값을 분리해야 한다. 정의 환경이 보관한 위치가 여전히 같은 셀을 가리키면 이후 쓰기를 읽을 수 있다. 값 포획·위치 포획은 언어의 별도 규칙이다.

연습 1 · 값과 상태 예측

E0={x→7}의 let x=x+1 in (let f=fun y -> x+y in (let x=20 in f(2)))를 손추적하라.

힌트 1

초기식은 E0에서 평가한다.

힌트 2

f의 보관 환경은 바깥 마지막 x 바인딩보다 먼저 만들어진다.

풀이와 답 확인

  1. 초기식 결과 8을 E1의 x에 둔다.

  2. f 몸체는 x 값 8과 y 값 2를 더한다.

결과는 10이다. 마지막 바깥 x 값 20은 f의 정의 환경을 바꾸지 않는다.

흔한 오답에서 다시 생각하기

항상 가장 최근 x를 찾아 22를 낸다.

어휘적 클로저의 환경을 호출 환경으로 교체한 오류다.

연습 2 · 오류 찾아 고치기

위치 모형에서 x→ℓ을 포획한 함수를 값 8의 복사로 바꾸어 최적화했다. 이후 S(ℓ)=11 쓰기가 허용된다면 보존되는가?

힌트 1

위치의 후속 쓰기가 관찰되는지 본다.

힌트 2

같은 인수 2로 두 결과를 비교한다.

풀이와 답 확인

  1. 원래는 현재 11을 읽어 13을 낸다.

  2. 값 복사는 8을 읽어 10을 낸다.

후속 쓰기가 허용되는 이 계약에서는 보존되지 않는다.

흔한 오답에서 다시 생각하기

이름 x가 같으니 값을 복사해도 같다.

같은 위치와 이전 값은 다른 자료다.

연습 3 · 직접 만들어 보기

밖으로 반환할 클로저를 위한 이름·값/위치·수명 장부를 독립 설계하라.

힌트 1

함수 코드와 필요한 자유 변수 관계를 적는다.

힌트 2

호출 종료 뒤에도 살아야 하는 자료를 표시한다.

풀이와 답 확인

  1. 각 클로저의 매개변수, 몸체, 정의 환경을 적는다.

  2. 값 포획인지 위치 포획인지와 해당 환경/저장소의 유지 책임을 명시한다.

필요한 관계가 사라지지 않도록 보존하는 설계다. 실제 힙 배치나 회수 구현은 요구하지 않는다.

한 단계 더

가변 셀을 새로 만드는 함수 make(초기값)를 종이에 설계하라. make(0)를 두 번 호출하면 서로 다른 셀이어야 한다. 첫 카운터를 두 번, 둘째를 한 번 증가시킨 결과는 2와 1이다. 반대로 한 전역 셀을 모두 공유하는 설계는 3을 공유하므로 계약과 다르다. 실제 인터프리터·메모리 관리 구현은 다음 프로젝트에서 별도로 검증한다.

타입 검사기와 진단

식을 실행하지 않고도 2+true의 잘못된 조합을 찾아낼 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 문법 트리

  • 정수와 불리언

  • 함수의 재귀

학습 목표

  • 작은 타입 규칙을 트리 순회 검사 절차로 바꾼다.

  • 실행 환경과 타입 환경을 구별하고 위치가 있는 오류를 설명한다.

실행에서 안 갈 분기의 타입 오류를 지우면 같은 언어를 구현한 것일까?

원본 작은 언어는 TInt와 TBool을 구별하고 +는 두 TInt만 받는다. 타입 검사는 값을 계산하는 일이 아니라 정적 환경 Γ와 구문으로 허용 여부를 결정한다. 자체 Γ0={x:TInt}에서 let x=(x<=3) in if x then 8 else 9를 검사하면 초기식 타입은 TBool, 몸체의 새 x 타입도 TBool이고 전체 타입은 TInt다. 동적 환경의 옛 x 값이 2라면 실행 결과는 8이지만 타입 검사에는 2라는 값이 필요하지 않다.

if true then 8 else false는 실행하면 정수 분기만 선택하더라도 원본 검사기는 두 분기의 타입 차이를 거절한다. 타입 검사 전에 상수 true의 다른 분기를 지워 버리면 이 프로그램을 받아들이게 된다. 실행 값만 우연히 같다고 해서 원본의 프로그램 수용/거절 계약까지 같다고 할 수 없다. 타입 검사 뒤 이미 통과한 식을 최적화하는 단계와 검사 전에 언어의 허용 범위를 바꾸는 단계를 나눠야 한다.

오류 메시지의 우선순위도 명세로 둔다. 새 진단 정책은 조건을 먼저 검사하고, 조건 타입이 Bool이 아니면 즉시 condition 경로 오류를 보고한다. 그렇지 않으면 then을 검사한 뒤 else를 검사하고 두 타입을 비교한다. 따라서 if 1 then unknown else false의 첫 진단은 condition의 Bool 요구다. 이 우선순위는 자체 검사기 설계이며 모든 실제 OCaml 구현의 메시지나 검사 순서를 주장하지 않는다.

먼저 확인할 개념
  • Γ와 if의 두 분기 타입

    값 평가와 프로그램 수용 여부를 구별한다.

  • 초기식 뒤 환경 확장

    정적 let에서도 먼저 기존 환경으로 초기식을 검사한다.

작은 규칙을 먼저 명시한다

자체 언어 T에서는 정수 타입 Int와 불리언 Bool만 다룬다. 정수 상수는 Int, true와 false는 Bool이다. 덧셈은 두 피연산자가 Int일 때만 Int이며 비교 <=는 두 Int를 받아 Bool을 만든다. Python의 bool이 int의 서브타입인 동작을 이 언어에 가져오지 않는다.

타입 환경 Γ는 이름을 타입에 연결한다. 실행 환경이 x의 값 7을 담는다면 Γ는 x가 Int임을 담는다. 둘은 목적이 다르다. 변수 검사에서는 Γ의 연결을 찾고 이름이 없으면 정의되지 않은 이름의 오류를 낸다.

트리를 안쪽부터 검사한다

let x=e1 in e2에서는 e1의 타입 t1을 구하고 Γ에 x:t1을 추가한 환경으로 e2를 검사한다. let 전체 타입은 e2의 타입이다. 덧셈에서는 좌우 타입을 검사하고 하나라도 Bool이면 Int와의 불일치를 보고한다.

if의 조건은 Bool이어야 하며 이 자체 언어에서 양쪽 가지의 타입은 같아야 한다. 정적 검사는 실행 때 선택되지 않을 가지도 검사한다. 조건이 true라는 이유만으로 반대 가지의 타입 오류를 무시하지 않는다. 최적화 뒤 검사하는 다른 도구의 규칙과 혼동하지 않는다.

진단도 언어 도구의 인터페이스다

같은 오류라도 '실패' 한 단어만 출력하면 사용자는 어디를 고칠지 알기 어렵다. 자체 검사기는 토큰 범위를 트리 노드에 보관하고 연산 이름, 필요한 타입, 발견한 타입, 위치를 보고하도록 설계한다. 이 소단원의 위치는 편집기 구현 대신 표현식 경로로 표시한다.

타입 검사를 통과했다고 모든 업무 요구나 자원 조건을 만족하는 것은 아니다. 정수 범위·예외·종료 보장은 언어 규칙과 실행 모델에 따라 따로 다뤄야 한다. 진행과 타입 보존 같은 성질도 그 규칙에 대한 증명이 있어야 하며 몇 개의 시험 성공으로 증명됐다고 기록하지 않는다.

표의 타입 이름은 실제 값 2나 true가 아니다. 새 환경은 몸체에만 적용되고 초기식에서 새 x:TBool을 먼저 사용하면 <=의 왼쪽을 잘못 검사하게 된다.

중간 과정을 따라가는 예제

자체 언어 T에서 let n=7 in if n<=10 then n+2 else 0을 검사하라. else를 false로 바꾸거나 n+true로 바꾸었을 때의 오류도 구하라.

  1. 7은 Int이므로 본문 환경은 Γ={n:Int}이다.

  2. n<=10은 Int 두 개를 비교해 Bool이다. 조건의 요구를 만족한다.

  3. n+2와 0은 모두 Int이므로 if와 let 전체가 Int다. 실행을 손으로 추적하면 true 가지에서 9다.

  4. else false는 Bool이어서 가지 Int/Bool 불일치다. n+true는 then/add/right 경로에서 필요한 Int 대신 Bool을 발견한다.

원래 식은 Int이다. 수정 두 경우는 각각 가지 불일치와 덧셈 오른쪽 타입 불일치이며 오류 경로가 다르다.

환경 확장의 잘못된 시점

Γ0={x:TInt}에서 let x=(x<=3) in if x then 8 else 9를 검사한다. 새 x:TBool을 초기식 전에 설치하면?

  1. 정상 초기식은 TInt<=TInt로 TBool이다.

  2. 잘못된 순서에서는 TBool<=TInt처럼 읽어 정상 프로그램을 거절한다.

정상 전체 타입은 TInt다. 초기식 검사가 끝난 뒤 몸체 환경을 확장한다.

비교할 점

결과 타입만 비교하지 않고 규칙 적용 시점을 검사한다.

상수 분기 삭제가 수용 계약을 바꿈

if true then 8 else false를 검사하는 원본과, 검사 전에 else를 지우는 변형을 비교하라.

  1. 원본은 TInt와 TBool 분기 차이를 거절한다.

  2. 삭제한 변형은 8만 남아 TInt로 수용한다.

실행 분기 예측과 별개로 수용/거절 결과가 다르다.

비교할 점

종이와 본문으로 직접 해보기

if true then 1 else false와 let x=false in x<=3을 검사하라. 첫 식의 false 가지가 실행되지 않는다는 이유로 검사를 생략해도 되는가?

힌트 보기

if의 조건과 양쪽 가지 규칙, 비교의 두 Int 규칙을 각각 적용한다.

풀이 보기

첫 식은 가지 Int/Bool 불일치다. 이 정적 검사 계약에서는 선택되지 않을 가지도 검사한다. 둘째는 x가 Bool이어서 비교의 왼쪽에 필요한 Int를 만족하지 못한다. 구문이 문법에 맞는 것과 타입 규칙 통과는 다르다.

오해와 반례

타입 검사를 통과한 프로그램은 요구사항·성능·종료까지 정확하다.

이 검사기는 표현식의 타입 조합을 다룬다. 같은 Int 결과라도 9를 반환해야 하는 요구에 8을 반환할 수 있고, 다른 언어의 반복이나 자원 제한은 추가 문제다. 주장하는 보장 범위를 규칙과 증거에 맞춰 제한한다.

filter와 map의 순서를 바꾸어도 실패까지 같을까?

원본의 짝수 제곱 합은 유한 정수 목록에서 순수 계산을 비교한다. 여기서는 경계를 드러내는 별도 변환 계약을 둔다. 입력 [2,0,4]에서 P(x)는 x!=0, G(x)는 1/x이며 0에는 정의되지 않는다. 먼저 P로 거른 뒤 G를 적용하면 1/2과 1/4을 더해 3/4이다. G부터 모든 입력에 적용하면 두 번째 값 0에서 실패한다. 이 자체 수학 모형의 실패는 실제 Python 예외 출력 관찰이 아니다.

같은 유효 입력에서 반환 값이 맞아도 관찰 계약은 다를 수 있다. 별도 G는 호출할 때 받은 입력을 로그에 적고 나서 역수를 계산한다고 정한다. filter 뒤 G의 로그는 [2,4], G 먼저의 실패 로그는 [2,0]이다. 실패 전에 남은 효과까지 비교해야 한다. 양쪽 변환을 바꾸려면 제거될 입력에서도 G가 정의되고, 필터의 의미가 변환 뒤에도 대응하며, 비교할 효과 순서까지 보존되는 조건이 필요하다.

자료의 재사용도 패러다임 이름만으로 결정되지 않는다. [2,4]에서 제곱을 차례로 내는 한 번짜리 반복자 I를 합하면 20이며 I는 소진된다. 같은 I를 다시 합하면 빈 합 0이다. 원본 목록으로 매번 새 반복자를 만들면 각각 20을 얻는다. 실제 라이브러리 실행이나 속도 측정은 하지 않고 입력 소유·소비 상태를 명시한 손모형으로 비교한다.

비교 전에 계약을 고정한다

자체 문제는 유한 정수 목록에서 짝수만 고르고 각 수의 제곱 합을 계산하는 것이다. 입력은 이 단원에서는 유효한 정수 목록으로 제한하고 음수도 허용한다. 빈 목록의 결과는 0, 입력 목록은 변경하지 않는다. 산술은 예제 범위 안에서 오버플로가 없다고 가정한다.

같은 문제라고 해도 한 구현이 음수를 버리고 다른 구현이 음수를 포함하면 공정한 비교가 아니다. 오류 입력을 거절할지 변환할지도 계약에 적어야 한다. 이 단원에서는 문자열이 섞인 입력을 유효 사례로 처리하지 않는다.

세 가지 설계의 중간 상태를 추적한다

명령형 설계는 total을 0으로 시작하고 각 원소에서 짝수이면 total에 x*x를 더한다. 객체 설계는 새 집계 객체의 내부 total을 0으로 시작한 뒤 같은 원소들을 add 메서드로 전달한다. 재사용 가능한 객체라면 누적을 유지할지 초기화할지 별도 약속이 필요하다.

함수 조합 설계는 filter(even), map(square), fold(add,0)의 순서다. 리스트를 모두 만드는 구현과 지연 스트림을 소비하는 구현은 중간 저장량이 다르다. 함수 이름이 같다고 모든 언어에서 평가 순서·메모리 동작까지 같다고 가정하지 않는다.

결과 외에 관찰할 항목을 정한다

세 방식이 같은 값을 반환해도 입력 변경, 전역 상태, 로그 출력이 다르면 관찰 가능한 효과가 다를 수 있다. 자체 비교표는 결과와 입력 보존, 검사 횟수, 곱셈 횟수, 중간 값 보관을 따로 기록한다. 읽기 쉬움은 실제 독자에게 평가받지 않았으면 설계 판단으로 남긴다.

지연 처리는 모든 항목을 즉시 만들지 않는 장점이 있지만 한 번 소비된 반복자나 공유 객체를 다시 쓰는 문제가 있다. 같은 목록을 한 번 처리하는 계약과 여러 번 처리하는 계약을 구별하자. 비용 표는 자체 연산 모형이며 실행 시간이나 실제 할당량을 측정한 자료가 아니다.

Γ0={x:TInt}에서 let x=(x<=3) in if x then 8 else 9의 타입을 적고, if true then 8 else false의 수용 여부를 검사 전 else 삭제 변형과 비교하라. 새 [2,0,4]에서 로그를 남기는 P-후-G와 G-먼저의 결과/실패/로그를 비교하고 새 제곱 반복자 I의 두 합을 적어라. 모든 표현은 본문 자체 모형이며 실제 구현 실행을 요구하지 않는다.

힌트 1

환경의 값과 저장소 위치, Γ의 타입을 서로 다른 칸에 기록한다.

힌트 2

반환 값·수용 여부·실패 이력·반복자 소비를 하나의 숫자로 합치지 않는다.

풀이와 답 확인

  1. 초기식은 E0에서 8을 낸다. f는 E1의 값 8을 포획하여 f(2)=10이다. g는 같은 위치의 현재 값 11을 읽어 g(2)=13이다.

  2. 정적 초기식 x<=3은 TBool이고 몸체 x도 TBool이다. 두 분기가 TInt라 전체는 TInt다. if true then 8 else false는 원래 거절되지만 검사 전 else 삭제 변형은 수용하여 계약이 다르다.

  3. P-후-G는 0을 제거해 합 3/4와 로그 [2,4]를 낸다. G-먼저는 0에서 실패하고 정상 합은 없으며 로그 [2,0]을 남긴다.

  4. 제곱 반복자 I는 2,4에서 4,16을 내어 첫 합 20이고 소진된다. 같은 I의 둘째 합은 0이다.

값/위치 클로저 10/13, 정적 전체 타입 TInt, 원래 분기 검사 거절/삭제 변형 수용, 역수 정상 합 3/4 또는 실패와 서로 다른 로그, 동일 반복자 합 20/0을 이름별 장부로 구별한다.
