小節 3.1

レキシカルスコープと動的スコープ

fのxは、fを定義した場所で探すのか、それとも今fを呼び出した側で探すのか？

準備する概念と学習目標

準備する概念

  • 名前の束縛は名前と対象を結び付ける。同じ綴りxが異なる束縛を指すこともある。スコープはコードのどの部分で束縛を使えるかを決める。
  • 関数呼び出しは実行中の出来事であり、関数定義のコード上の位置とは異なる。gがfを呼び出しても、fの定義がgの中へ移るわけではない。
  • 準備確認：外側のx=10とgのローカルx=20を二つの箱に描く。名前だけが同じで、束縛は異なる。

学習目標

  • 定義のコード構造とアクティブな呼び出し構造を区別する。
  • 同じモデルでレキシカル/動的な検索規則を対照する。
  • 束縛の選択と現在値・型・動的ディスパッチを区別する。

束縛を選ぶ基準

レキシカルスコープは名前が使われるコードの入れ子構造から束縛を決める。自由変数はその関数のパラメータやローカル宣言に束縛されていない名前である。fが外側のxを使い、gが独自のxを持つ場合、gからfを呼んでもfの束縛をgのxに変えない。ただし、束縛の値までコンパイル時に固定するという意味ではない。

下のPython 3.12ではfのxはモジュールの束縛、gのxはgのローカル束縛である。Pythonの検索は任意の呼び出し元のローカルをたどらない。global/nonlocal・クラス・注釈スコープには別の規則があり、LEGBの四文字だけでは全てのケースを完全には説明できない。ここではモジュールと通常の関数だけを扱う。

動的スコープを別に定義する

独自の動的モデルでは現在の関数のローカル名を先に探し、なければ現在アクティブな呼び出し元フレームを順にたどり、最後にグローバルを探す。グローバルx=10、f()=x、g()はローカルx=20を置いてからf()という構造では、直接のfは10、gが呼ぶfは20を返す。これはPythonを動的スコープモードで実行したという主張ではない。

ローカルx=30を持つhが直接fを呼ぶと、動的モデルは30を選ぶ。レキシカルなfの定義環境は呼び出し元の挿入で変わらない。引数の実行時型によりメソッドを選ぶ動的ディスパッチや、Pythonが動的型付け言語であることは、動的な名前のスコープと異なる概念である。

選んだ束縛の値は変わり得る

レキシカルな検索でも、選んだ束縛が可変なら後で別の値を読むことがある。Pythonのモジュールxを10から40へ再束縛すると、fは同じモジュール束縛から現在の40を読む。OCamlの新しいlet xは、以前の束縛の変更ではなく、新しい束縛によるシャドーイングの場合がある。言語の代入規則を確認せず結果だけを移してはいけない。

紙上で定義環境の矢印と呼び出し元の矢印を別の色にする。レキシカルな呼び出しフレームは関数が保持した定義環境を親に結び、独自の動的モデルはアクティブな呼び出し元環境を結ぶ。完全なPython例が実際に実行するのは前者だけで、動的結果は定義した規則から手で導く。

x = 10
def f():
    return x
def g():
    x = 20
    return f()
print(f(), g())

途中の過程をたどる例題

グローバルx=10、f()はxを返し、g()はローカルx=20を置いてf()を呼ぶ。Pythonと独自の動的モデルで二つの呼び出し結果を求める。

  1. モジュールGにはx=10とf,gがある。fはGで定義され、gの中にはない。
  2. 直接呼んだfのローカルにはxがないので、両モデルともGの10を見つける。
  3. gのローカルには20がある。Pythonのfはモジュールの10、独自の動的fは呼び出し元gの20を見つける。
  4. Pythonのprintは10 10である。動的モデルの結果10,20は実際のPython標準出力ではない。

過去に実行したCPython 3.12.7の実際の標準出力は10 10と改行である。動的モデルの10,20は紙上結果である。

紙と本文で試してみよう

G:x=4、f()=x、gはローカルx=7の後にf、hはローカルx=9の後にgというモデルを描く。直接のfとhの戻り値を二つの検索規則で求める。

ヒントを見る

hがgを呼ぶと、gのローカルxも新しく作られる。動的検索も最も近いアクティブな束縛から探す。

解答を見る

レキシカルなfはGで定義されるので、直接f=4,h=4。動的では直接f=4、h→g→fでは近いgの7が先に見つかり、hの9は選ばれない。結果は4,7である。

よくある誤解と反例

動的型付け言語は呼び出し元の変数を探し、レキシカルスコープは値を永久に固定する。

Pythonは動的型付けでも、fはgの20を読まない。モジュールxの再束縛によりfの値は変わり得る。束縛の選択と値・型・メソッドの選択は別の軸である。

理解を確かめる

レキシカルな自由変数検索の基準は？

答えと理由を見る

定義のコードの入れ子環境である。

アクティブな呼び出し元と定義環境は異なる関係である。

動的h→g→fでgにxがあれば、hのxを選ぶか？

答えと理由を見る

いいえ。gのxが先である。

最も近いアクティブな束縛で止まると定義したからである。

レキシカルな関数は常に同じ値を返すか？

答えと理由を見る

いいえ。

選んだ束縛やオブジェクトが変わることも、入力が異なることもある。

もう一歩先へ

発展：fのコード・定義環境・引数・共有ストアを維持して呼び出し元のローカルフレームだけを変えると、レキシカルな自由変数検索の束縛は維持される。検索経路にその呼び出し元を含めないためである。全ての関数結果が不変という定理ではない。共有状態の変化・例外・発散・引数の違いには別の前提が必要である。動的モデルでは新たな呼び出し元のxが経路に入る反例により、この束縛不変性が崩れる。

小節 3.2

束縛と環境モデル

aを別のリストに結び直したのに、なぜbは以前のリストを見続けるのか？

準備する概念と学習目標

準備する概念

  • 環境は名前を解釈する束縛の構造、フレームは一段の名前表である。フレームは親環境を持てる。独自モデルでは一つのフレーム内に同じ名前を二度置かない。
  • 名前の再束縛は名前が指す対象を変え、リスト要素の変更は共有オブジェクトの内部を変える。名前の格納場所とオブジェクトを分けて描く。
  • 準備確認：a,bからO1へ二本の矢印を描き、aだけをO2へ移す。bはO1に残る。

学習目標

  • 環境ρとストアσを区別する。
  • 束縛・再代入・エイリアスを追跡する。
  • 新しい呼び出しフレームと定義環境の接続を説明する。

環境とストアの二つの表

独自の可変モデルでは環境ρは名前→格納位置ℓの有限表、ストアσは位置→現在値の表である。lookupは現在フレームに名前があれば位置を返し、なければ親を探す。最後までなければunboundである。名前の読み出しは、見つかった位置のσ値を読む。値には整数や別オブジェクトを指す参照も含められる。

新しい宣言は現在フレームに新しい位置を結び、初期値を格納する。再代入は選んだ位置の値を変える。重複宣言の許可や初期化前の読み出しは実際の言語ごとに違うため、このモデルをPython全体の仕様とは呼ばない。Pythonの名前はオブジェクトを参照し、矢印図はその再束縛と共有の効果に対応するモデルである。

名前の位置とオブジェクトのエイリアス

a=[1]; b=aではa,bが同じリストO1への参照を持つ。a=[9]は新たなO2を作り、aだけをO2へ結ぶ。b[0]=2はbを新リストへ再束縛する文ではなく、O1内部を変える。最終的にa=[9],b=[2]となる。同じオブジェクト参照を持つことは、二つの名前の再代入も連動することを意味しない。

抽象位置ℓa,ℓbとリスト要素の格納を分ける。二つの位置は異なるが、最初の格納値は同じO1参照である。O1の要素変更はO1を見る別の名前からも観察できる。名前の綴りが同じ、あるいは同じ環境内にあるというだけで、同じオブジェクトを参照するとは限らない。

関数と新たなフレーム

レキシカルな関数値は⟨パラメータ,本体,定義環境⟩というクロージャである。呼び出しは引数を評価した値を新たなパラメータ位置に入れたフレームを作り、その親をクロージャ環境へ結ぶ。別の呼び出しは新しいローカルフレームを持つが、捕捉したオブジェクトを共有し得る。オブジェクト参照を引数値として渡せば、呼び出し側と関数が同じオブジェクトを見る場合がある。

モデルは抽象的意味を説明し、実際のメモリがこの辞書形式で実装されるとか、全ての名前が実際のアドレスを持つとは主張しない。実装は保持する環境を減らしたり最適化したりできる。単一の逐次実行・有効で生存中のオブジェクト・定義された検索を仮定する。並行変更・低水準ポインタ・実際の割り当て失敗は別の条件である。

a = [1]
b = a
a = [9]
b[0] = 2
print(a, b)

途中の過程をたどる例題

Python例のa,bと二つのリストO1,O2を描き、再束縛と要素変更を追跡する。

  1. a=[1]でO1を作りaを結ぶ。O1の最初の値は1である。
  2. b=aは同じO1参照をbに結ぶ。別の名前が同じリストを見る。
  3. a=[9]はO2を作り、aだけを変える。bはO1に残る。
  4. b[0]=2はO1の要素を変える。aはO2の[9]、bはO1の[2]を見る。

過去に実行したCPython 3.12.7の実際の標準出力は[9] [2]と改行である。実際のアドレスや抽象位置の数値は測定していない。

紙と本文で試してみよう

ρでx→ℓ1,y→ℓ2、σでℓ1→O,ℓ2→O、O=[5]とする。xを新しいP=[8]へ再代入し、O[0]=6に変えるとx,yは？

ヒントを見る

二つの名前位置と二つのリストオブジェクトを別々に描く。Oの変更はℓ2の参照を変えない。

解答を見る

ℓ1の値はP参照なのでx=[8]。ℓ2はO参照を保ちy=[6]。オブジェクト変更前はy=[5]であり、xの再代入だけではyはPへ変わらない。

よくある誤解と反例

名前を値へ一度置換すれば、代入やオブジェクト共有も説明できる。

可変状態では同じ名前の現在値が変わる。aの再束縛とb[0]の変更は別の場所を変えるので、機械的な値置換ではエイリアスの効果を失う。純粋で不変な式の置換論証と区別する。

理解を確かめる

独自のρとσは何を結ぶか？

答えと理由を見る

名前→位置、位置→現在値である。

現在値にオブジェクト参照も含められるモデルである。

b=a後、aを新リストに変えるとbも再束縛されるか？

答えと理由を見る

いいえ。

名前の束縛は別々なので、bには以前のオブジェクト参照が残る。

レキシカルな呼び出しフレームの親は？

答えと理由を見る

クロージャに保存された定義環境である。

アクティブな呼び出し元環境を常に親とする動的モデルとは異なる。

もう一歩先へ

発展：有限で循環のない親リンクでは、lookupはフレームの深さを一つずつ減らして終了する。現在フレームの最初の一致がない場合だけ親を探す規則についての帰納法から、最も近い束縛の一意性を得る。σだけを変えρと親を維持すると、検索位置は同じだが読んだ現在値は変わり得る。不変の環境と可変ストアを許す言語の前提を混同しない。

小節 3.3

シャドーイング・寿命・キャプチャ

makeが終わったのに、なぜincは以前のxを増やし続けられるのか？

準備する概念と学習目標

準備する概念

  • シャドーイングとは、内側の同名の束縛が外側の束縛より先に選ばれる現象である。外側オブジェクトの削除とは異なる。
  • スコープは名前を使用できるコード区間、寿命は実行時間中に対象が生きている期間である。二つの軸は同じではない。
  • 準備確認：makeのxから返されたincへ線を引く。makeの終了と捕捉した状態の消滅を分ける。

学習目標

  • シャドーイング・再代入・オブジェクト変更を区別する。
  • 捕捉した状態と呼び出し実行の終了を分ける。
  • 後の時点での値の検索と定義時の値保存の条件を対照する。

シャドーイングは削除ではない

内側フレームがxを導入すると、その区間の検索は内側のxで止まる。外側環境では元のxを再び見つける。同名宣言を許す位置は実際の言語により違うので、全ての入れ子ブロックに同じ宣言を書いてもコンパイルできるとは仮定しない。Pythonのfor/ifは通常、新たなローカル関数スコープを作らない。

incのnonlocal xは、incに新たなローカルxを作らず、最も近い外側関数の束縛を使うというPython 3.12の宣言である。これを外してx+=1を書くと、xはincのローカル名と判定され、まだ値がない状態で読み出してエラーが生じ得る。このエラー変形は正常例の証拠として実行していない。

呼び出し後も必要な捕捉状態

make(3)はxに対応する捕捉状態とincを作る。incがその状態を参照し続けると、Pythonは後の呼び出しでもその束縛を使えるようにする。makeの実行終了で、必要な全状態が直ちに消えるわけではない。反対に、Cの自動配列のアドレスを返すように、言語が寿命を延長しない参照は危険である。

make(10)は別の状態を作る。c=make(3),d=make(10)ではcの繰り返し呼び出し同士が状態を共有し、dは別である。実際のヒープ/スタックのアドレスや回収時点は測定していない。自由変数の値を生成時にコピーするのか、位置やオブジェクトを共有するのかは、言語とキャプチャ構文に応じて明示する必要がある。

後の時点での検索と変数捕獲を避ける改名

Pythonのループで同じ外側iを参照するlambdaを作り、ループ後に呼ぶと、全てが最終iを見る場合がある。レキシカルスコープは各反復値のコピーを意味しないためである。lambda i=i: iは各関数定義時にデフォルト引数を評価して数値を保存する別の方法である。可変オブジェクトをデフォルト引数に保存すると参照共有になり得るので、深いコピーとは異なる。

束縛した名前を変えるには、結び付く使用箇所も変え、別の自由変数を捕獲してはいけない。lambda x: x+yをlambda y: y+yへ変えると、外側の自由なyを隠して意味を変える。以下は整数start・逐次呼び出し・Pythonの任意精度整数という条件で正常な状態変化を追跡する完全な例である。

def make(start):
    x = start
    def inc():
        nonlocal x
        x += 1
        return x
    return inc
c = make(3)
d = make(10)
print(c(), c(), d(), c())

途中の過程をたどる例題

c=make(3),d=make(10)の後、c(),c(),d(),c()を左から計算する。

  1. C.x=3とD.x=10を別の箱に描く。本体は同じでも環境は異なる。
  2. 最初のcはC.x=4と戻り値4、次のcはC.x=5と戻り値5を作る。
  3. dはD.x=11と戻り値11を作り、C.x=5を変えない。
  4. 最後のcはC.x=6と戻り値6を作る。Pythonではprintの実引数式は左から評価される。

過去に実行したCPython 3.12.7の実際の標準出力は4 5 11 6と改行である。共有はcとdの間ではなく、各クロージャの繰り返し呼び出し間に起こる。

紙と本文で試してみよう

C.x=0のcとD.x=5のdにc(),d(),c(),d()を適用する。lambda x: x+yのxをzまたはyへ変える意味も比較する。

ヒントを見る

戻り値とC,Dの最終状態を一緒に書く。自由なyがそのまま残るか調べる。

解答を見る

戻り値は1,6,2,7、最終C.x=2,D.x=7。他の名前と衝突しない文脈のlambda z: z+yは束縛構造を保持する。lambda y: y+yは自由なyを捕獲するので、一般には別の関数である。

よくある誤解と反例

レキシカルなクロージャは生成時に必ず値をコピーし、関数終了時に捕捉状態も消える。

Pythonのnonlocalカウンタは同じ捕捉状態を変えて4,5,6を返す。OCamlの新たなletによるシャドーイング、可変配列の共有、C++の値/参照キャプチャも規則が異なる。コードのスコープとオブジェクトの寿命を分け、何を保持するかを確認する。

理解を確かめる

同じinc本体ならc,dも同じ状態か？

答えと理由を見る

いいえ。

各make呼び出しは異なる捕捉環境を作る。

nonlocalなしでx+=1を書くと、外側の変更が自動で保証されるか？

答えと理由を見る

いいえ。

ローカル名の判定により、初期値を読むエラーが起こり得る。

lambda x: x+yのxをyに変えても常に同じか？

答えと理由を見る

いいえ。

元の自由なyをパラメータが捕獲し、束縛構造が変わる。

もう一歩先へ

発展：start=sの一つのクロージャだけを非負整数k≥0回、逐次に正常呼び出しし、外からxを変えなければ、帰納法により呼び出し後x=s+kである。初期値はsで毎回ちょうど1増えるからである。別のmakeは別の位置なので影響しない。これは副作用がないという意味ではなく、定義された状態変化の契約である。固定幅整数・並行呼び出し・例外を導入するなら、表現範囲・原子性・完了条件を新たに立てる必要がある。変数捕獲を避ける改名と値のスナップショットは異なる変換である。
