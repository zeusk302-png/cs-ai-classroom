소단원 11.1

동적 디스패치

변수의 타입이 Animal인데 안에 Cat이 있으면 어떤 sound가 호출될까?

준비 개념과 학습 목표

준비 개념

  • 객체와 메서드
  • 변수의 선언 타입

학습 목표

  • 정적 타입과 런타임 객체 타입을 구별한다
  • 재정의한 인스턴스 메서드의 선택을 추적한다
  • 오버로딩과 디스패치의 단계를 구별한다

변수의 설명과 실제 대상은 다르다

Animal a = new Cat()에서 변수 a의 선언 타입은 Animal이고 가리키는 객체의 실제 클래스는 Cat이다. 선언 타입은 그 위치에서 어떤 멤버 호출이 허용되는지 판단하는 데 쓰인다. Cat에만 있는 멤버가 자동으로 Animal 변수에 노출되는 것은 아니다.

동적 디스패치는 적절한 인스턴스 메서드의 구현을 실제 대상 객체에 따라 선택하는 과정이다. Java의 일반 virtual 호출에서 재정의된 메서드를 찾을 때 실제 클래스부터 시작한다. 모든 언어의 모든 함수 호출에 같은 규칙이 적용된다고 일반화하지 않는다.

재정의와 오버로딩을 나눈다

재정의는 상위 메서드와 맞는 선언을 하위 클래스에서 구현하는 것이다. sound()를 Cat에서 재정의하면 Animal 변수로 호출하더라도 Cat의 구현이 선택된다. 오버로딩은 이름은 같지만 인수 타입 등이 다른 여러 후보 선언을 두는 것이다.

Java에서는 호출 후보의 시그니처 선택에 정적 타입이 관여한 뒤 선택한 인스턴스 메서드의 재정의 구현을 런타임에 찾는다. 실제 객체가 Cat이라는 이유로 다른 오버로드까지 전부 런타임에 다시 고르는 것은 아니다. 같은 이름이라는 정보만으로 결과를 결정하지 않는다.

예외와 특별한 호출도 있다

아래는 같은 패키지에서 접근 가능한 비private 인스턴스 메서드의 작은 예다. static 호출은 이 재정의 디스패치 규칙과 다르고 super 호출은 지정한 상위 구현을 사용하는 별도 문맥이다. private 등 세부 규칙도 문서에서 확인한다.

null은 메서드를 받을 객체가 아니다. Java에서 null 대상의 인스턴스 호출은 NullPointerException을 일으킨다. 객체의 저장 주소나 클래스 이름을 출력해 봤다는 관찰은 여기서 수행하지 않았으며 아래 결과는 선언과 호출 규칙의 손 추적이다.

중간 과정을 따라가는 예제

아래 선언 뒤 Animal a=new Cat(); Animal b=new Dog(); Animal c=new Animal();의 sound() 반환을 추적하라. 

class Animal {
    String sound() { return "unknown"; }
}
class Cat extends Animal {
    @Override String sound() { return "meow"; }
}
class Dog extends Animal {
    @Override String sound() { return "woof"; }
}
  1. a의 선언 타입은 Animal이지만 실제 Cat에서 재정의 sound를 찾아 meow를 반환한다.
  2. b는 Dog의 sound를 찾아 woof다.
  3. c는 Animal의 sound를 사용해 unknown이다.

순서대로 meow, woof, unknown이다. 직접 실행한 출력은 아니다.

종이와 본문으로 직접 해보기

Cat은 위처럼 sound만 재정의한다. Animal x=new Cat(); 다음 x=new Dog(); 후 두 호출의 결과를 비교하라. null을 넣으면?

힌트 보기

각 호출 시 참조의 현재 대상을 확인한다.

풀이 보기

대입 전 meow, Dog 대입 후 woof다. null 대상에서 sound 호출은 NullPointerException이 예상된다.

오해와 반례

동적 디스패치는 실제 타입으로 모든 오버로드를 다시 고르는 것이다.

정적 후보/시그니처 선택과 선택된 인스턴스 메서드의 런타임 재정의 탐색은 별도 단계다.

자기점검

Animal a=new Cat()의 선언 타입은?

답과 이유 보기

Animal.

왼쪽 변수 선언의 타입이다.

a.sound()의 작은 예제 반환은?

답과 이유 보기

meow.

실제 Cat이 인스턴스 메서드를 재정의했다.

null에 sound를 호출하면 unknown인가?

답과 이유 보기

아니다.

호출 대상 객체가 없어 NullPointerException이 예상된다.

한 단계 더

void show(Animal a)와 void show(Cat c)가 있고 Animal a=new Cat()로 show(a)를 호출한다고 가정하라. 정적 인수 타입 Animal로 Animal 오버로드를 선택한다. 그 본문 안의 a.sound()는 Cat의 meow를 사용할 수 있다. 두 단계의 선택을 따로 적어 같은 런타임 객체로도 질문이 다름을 설명하라.

출처와 확인 범위
  • Java Language Specification §15.12.4.4

    static/super/virtual/interface 호출 모드, null 수신자, 실제 런타임 클래스에서 시작하는 재정의 메서드 탐색 본문을 실제 읽었다. 예제는 Java의 단순 비private 인스턴스 메서드이며 특수 MethodHandle 규칙을 적용하지 않는다.

소단원 11.2

상속·위임·믹스인

기능을 빌려 쓰려면 반드시 같은 가족의 하위 클래스를 만들어야 할까?

준비 개념과 학습 목표

준비 개념

  • 객체 안의 다른 객체 참조
  • 메서드 호출과 인터페이스

학습 목표

  • 상속·위임·믹스인의 재사용 경로를 구별한다
  • 재사용과 하위타입 계약을 나누어 판단한다
  • 조합 순서와 상태 공유 조건을 밝힌다

상속은 구현과 관계를 함께 만든다

상속은 상위의 멤버와 구현을 이어받아 하위 클래스를 만드는 장치다. 많은 언어에서는 상속 선언이 하위타입 관계도 만든다. 그러나 코드를 조금 재사용하려고 상속했다는 동기만으로 상위 계약을 실제로 잘 지킨다고 보장되지는 않는다.

상위의 변경이 하위의 가정에 영향을 줄 수 있으므로 어떤 메서드를 재정의할 수 있고 어떤 불변식을 지켜야 하는지 확인한다. 내부 구현을 무조건 직접 만지는 하위 클래스는 작은 상위 변경에도 깨질 수 있다. 실제 위험은 특정 계약과 변경으로 판단한다.

위임은 다른 객체에 요청을 보낸다

위임에서는 객체가 협력 객체를 보관하고 작업을 그 객체에 전달한다. 예컨대 Notifier가 Formatter를 가지고 format(message)를 호출한다. Formatter를 바꾸어 행동을 선택하는 방식은 Notifier가 Formatter의 하위클래스일 필요가 없다.

단순한 전달만으로 위임 대상의 모든 멤버가 자동 공개되는 것은 아니다. Notifier가 어떤 인터페이스를 구현하고 어떤 메서드를 전달하는지 작성해야 한다. 협력 객체를 공유하면 그 객체의 가변 상태도 공유될 수 있으므로 복사·공유·교체 정책을 정한다.

믹스인은 기능 조각을 합친다

믹스인은 클래스에 기능 조각을 결합하는 장치다. Scala의 trait은 추상 요구와 구현을 제공하여 다른 클래스와 조합할 수 있다. 한 슈퍼클래스와 여러 믹스인을 합치는 예가 있지만 모든 언어의 믹스인이 동일한 문법과 의미를 갖지는 않는다.

두 조각이 같은 이름을 제공하거나 상위 호출을 이어 쓰면 조합 순서와 충돌 해소 규칙을 알아야 한다. 여기서는 언어 규칙 전체 대신 prefix 기능과 upper 기능을 순서대로 적용하는 자체 순수 메시지 모형을 정의한다. 순서 효과와 실제 Scala 선형화를 혼동하지 않는다.

중간 과정을 따라가는 예제

자체 메시지 변환은 prefix(s)="note: "+s, upper(s)=ASCII 소문자만 대문자로 바꾸기다. 원문 "hi"에 upper(prefix(s))와 prefix(upper(s))를 비교하라. 상속·위임·믹스인 중 구현 방식이 값만으로 결정되는가?

  1. prefix("hi")는 "note: hi"이고 upper를 적용하면 "NOTE: HI"다.
  2. upper("hi")는 "HI"이고 prefix를 적용하면 "note: HI"다.
  3. 순서가 결과를 바꾼다. 두 함수를 객체 상속·협력객체 위임·기능조각 조합으로 연결하는 방식은 별도 설계다.

두 결과는 NOTE: HI와 note: HI로 다르며 문자열 결과만으로 재사용 방식이 결정되지 않는다.

힌트 보기

같은 객체 공유이며 각 호출은 현재 prefix+메시지라는 자체 규칙이다.

풀이 보기

둘 다 warn: hi다. 위임이 자동으로 복사 상태를 만든 것은 아니다. 별도 Formatter를 만들면 공유 여부가 달라진다.

오해와 반례

위임으로 기능을 쓰면 위임 대상의 하위타입이 된다.

협력 객체를 보유하는 관계와 하위타입 관계는 다르다. 필요한 인터페이스 구현과 외부 계약을 따로 정한다.

자기점검

답과 이유 보기

Scala 클래스는 여러 trait을 믹스인할 수 있는가?

그렇다.

공식 예제의 한 슈퍼클래스와 여러 믹스인 조합을 따른다.

upper와 prefix 순서는 항상 같은가?

한 단계 더

formatter 교체를 허용할 때 null·실패·변환 규칙 변경을 Notifier 계약에 어떻게 노출할지 정하라. 소문자 그대로 보존한다는 외부 약속이 있다면 upper formatter로 교체하는 것만으로 계약을 위반할 수 있다. 재사용 장치가 바뀌어도 관찰 가능한 약속을 확인한다.

소단원 11.3

서브타입·변성

Cat이 Animal이면 Cat을 담는 상자도 Animal 상자로 취급해도 될까?

준비 개념과 학습 목표

준비 개념

  • 타입 매개변수
  • 함수의 입력과 반환

학습 목표

  • 하위타입 관계의 대체 방향을 설명한다
  • 생산·소비·읽기쓰기의 변성 차이를 추적한다
  • 타입 검사와 행동 계약의 차이를 이해한다

대체 가능한 방향을 적는다

S<:T는 S를 T가 요구되는 곳에 사용할 수 있는 하위타입 방향을 표시한다. Cat<:Animal이면 Animal 입력에 Cat을 전달하는 방향이 자연스럽다. 타입 시스템이 허용하는 대체와 메서드가 실제 행동 약속을 지키는지는 서로 다른 검토 대상이다.

같은 메서드 이름을 가지고 있다고 모든 언어가 자동 하위타입으로 인정하지 않는다. 명시적인 선언을 요구하는 명목적 타입과 구조를 비교하는 타입 체계가 있다. 이 소단원의 Cat/Animal 관계는 명시적으로 주어졌다고 가정한다.

만드는 것과 받는 것은 반대다

Producer<T>는 T를 반환만 하고 Consumer<T>는 T를 받기만 하는 자체 인터페이스라고 두자. Cat 생산자는 항상 Animal을 생산한다는 요구를 만족하므로 공변이면 Producer<Cat><:Producer<Animal>이다.

Animal을 모두 처리하는 소비자는 Cat도 처리하므로 반공변이면 Consumer<Animal><:Consumer<Cat>이다. 반대로 Cat만 처리하는 소비자에게 Dog를 맡길 수는 없다. 선언된 타입 매개변수의 사용 위치가 해당 변성을 지키는지는 언어의 규칙으로 검사한다.

읽고 쓰는 상자는 단순 공변이 아니다

Box<Cat>을 Box<Animal>로 허용한다면 Animal 상자 참조를 통해 Dog를 넣고 원래 Cat 상자 참조로 읽는 반례가 생긴다. 같은 가변 저장소를 공유한 조건이 핵심이며 자동 복사 상자로 가정하지 않는다.

Scala의 기본 불변 타입 매개변수와 Java의 일반 제네릭 상자는 이 단순 대체를 허용하지 않는다. 읽기 전용 인터페이스 등 제한된 관점을 설계하면 다른 대체가 가능할 수 있다. 함수 타입은 일반적인 안전 대체에서 입력 반공변·출력 공변 방향을 따르되 언어별 표기와 예외를 확인한다.

중간 과정을 따라가는 예제

Cat<:Animal, Dog<:Animal이고 Producer는 반환만, Consumer는 입력만 제공한다. 두 대체 Producer<Cat>→Producer<Animal>, Consumer<Animal>→Consumer<Cat>를 추적하고 반대 방향의 반례를 제시하라.

  1. Cat 반환값은 Animal이므로 첫 대체는 출력 약속을 만족한다. Animal 생산자→Cat 생산자는 Dog를 반환할 수 있어 실패한다.
  2. 모든 Animal 입력을 처리하는 소비자는 Cat도 처리한다. Cat 소비자→Animal 소비자는 Dog 입력에서 실패한다.
  3. 관계는 자체 공변/반공변 인터페이스의 정의로 판단하며 모든 일반 제네릭 클래스가 자동 이 관계를 갖는다는 뜻이 아니다.

생산은 정방향, 소비는 역방향이다. 반대 방향에는 Dog가 반례다.

오해와 반례

S<:T이면 모든 G에 대해 G<S><:G<T>다.

그 관계는 G가 공변일 때의 방향이다. 입력 위치·가변 쓰기·언어 규칙에 따라 반공변이나 불변이 필요하다.

한 단계 더

Cat<:Animal에서 함수 Animal→Cat은 Cat→Animal이 요구되는 곳에 안전하게 제공할 수 있다. 제공 함수는 요구 입력 Cat을 받고 요구 출력 Animal보다 구체적인 Cat을 낸다. 반대 대체는 Dog 입력을 받지 못하거나 Dog 출력을 Cat으로 약속할 수 없어 실패한다. 입력·출력 화살표를 따로 적어 검산하라.
