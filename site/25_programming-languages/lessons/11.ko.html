소단원 11.1

동적 디스패치

변수의 타입이 Animal인데 안에 Cat이 있으면 어떤 sound가 호출될까?

준비 개념과 학습 목표

준비 개념

  • 객체와 메서드

  • 변수의 선언 타입

학습 목표

  • 정적 타입과 런타임 객체 타입을 구별한다

  • 재정의한 인스턴스 메서드의 선택을 추적한다

  • 오버로딩과 디스패치의 단계를 구별한다

같은 문자열 객체를 전달했는데 다른 본문이 선택되는 이유는 무엇일까?

원본 sound 예제는 인수가 없어 재정의 단계만 보였다. 이번 Java 예제는 같은 패키지의 접근 가능한 비private 인스턴스 메서드이며 Base에 render(Object)와 render(String)가 있고 각각 "base-object", "base-string"을 반환한다. Sub extends Base는 render(Object)만 재정의하여 "sub-object"를 반환한다. generic·varargs·boxing·특수 호출은 없다. Base b=new Sub(), String s="x", Object o=s로 두고 각 문제는 이 선언에서 독립적으로 시작한다.

b.render(s)는 String 인수에 적용 가능한 두 후보 중 더 구체적인 render(String)를 정적으로 선택한다. Sub가 그 시그니처를 재정의하지 않았으므로 Base의 "base-string"이다. b.render(o)는 인수 표현식의 정적 타입 Object로 render(Object)를 선택하고 실제 Sub의 재정의 본문에서 "sub-object"를 얻는다. s와 o가 같은 문자열 객체를 가리킨다는 사실은 두 선택 단계를 하나로 합치지 못한다.

실제 객체에 대한 정확한 지식과 호출 위치에서 쓰는 타입은 다르다. render(Object)의 매개변수 이름을 String처럼 부르거나 실제 인수 클래스가 String이라고 하여 render(String)를 다시 고르는 규칙은 Java의 이 예제에 없다. 결과 문자열만 기록하지 말고 선택한 시그니처·수신자 클래스·실행 본문을 함께 적으면 잘못된 일반화를 찾아낼 수 있다. Java 컴파일과 실행은 수행하지 않았다.

먼저 확인할 개념
  • 정적 후보와 재정의 탐색

    인수가 있는 경우 두 단계를 구별한다.

  • 정적 대체 방향

    표현식 타입이 실제 클래스와 다를 수 있다.

변수의 설명과 실제 대상은 다르다

Animal a = new Cat()에서 변수 a의 선언 타입은 Animal이고 가리키는 객체의 실제 클래스는 Cat이다. 선언 타입은 그 위치에서 어떤 멤버 호출이 허용되는지 판단하는 데 쓰인다. Cat에만 있는 멤버가 자동으로 Animal 변수에 노출되는 것은 아니다.

동적 디스패치는 적절한 인스턴스 메서드의 구현을 실제 대상 객체에 따라 선택하는 과정이다. Java의 일반 virtual 호출에서 재정의된 메서드를 찾을 때 실제 클래스부터 시작한다. 모든 언어의 모든 함수 호출에 같은 규칙이 적용된다고 일반화하지 않는다.

재정의와 오버로딩을 나눈다

재정의는 상위 메서드와 맞는 선언을 하위 클래스에서 구현하는 것이다. sound()를 Cat에서 재정의하면 Animal 변수로 호출하더라도 Cat의 구현이 선택된다. 오버로딩은 이름은 같지만 인수 타입 등이 다른 여러 후보 선언을 두는 것이다.

Java에서는 호출 후보의 시그니처 선택에 정적 타입이 관여한 뒤 선택한 인스턴스 메서드의 재정의 구현을 런타임에 찾는다. 실제 객체가 Cat이라는 이유로 다른 오버로드까지 전부 런타임에 다시 고르는 것은 아니다. 같은 이름이라는 정보만으로 결과를 결정하지 않는다.

예외와 특별한 호출도 있다

아래는 같은 패키지에서 접근 가능한 비private 인스턴스 메서드의 작은 예다. static 호출은 이 재정의 디스패치 규칙과 다르고 super 호출은 지정한 상위 구현을 사용하는 별도 문맥이다. private 등 세부 규칙도 문서에서 확인한다.

null은 메서드를 받을 객체가 아니다. Java에서 null 대상의 인스턴스 호출은 NullPointerException을 일으킨다. 객체의 저장 주소나 클래스 이름을 출력해 봤다는 관찰은 여기서 수행하지 않았으며 아래 결과는 선언과 호출 규칙의 손 추적이다.

수신자는 네 행 모두 같은 Sub 객체다. 마지막 cast는 o가 실제 String을 가리키는 이 선언에서만 성공한다고 추적한다. 메서드 이름이 같아도 시그니처가 다른 두 연산이다.

중간 과정을 따라가는 예제

아래 선언 뒤 Animal a=new Cat(); Animal b=new Dog(); Animal c=new Animal();의 sound() 반환을 추적하라. 

class Animal {
    String sound() { return "unknown"; }
}
class Cat extends Animal {
    @Override String sound() { return "meow"; }
}
class Dog extends Animal {
    @Override String sound() { return "woof"; }
}

  1. a의 선언 타입은 Animal이지만 실제 Cat에서 재정의 sound를 찾아 meow를 반환한다.

  2. b는 Dog의 sound를 찾아 woof다.

  3. c는 Animal의 sound를 사용해 unknown이다.

순서대로 meow, woof, unknown이다. 직접 실행한 출력은 아니다.

조건을 바꾸어 비교하기

인수 객체를 바꾸지 않고 선택을 바꾼다

s와 o에 대한 두 호출의 결과 및 별칭 관계를 설명하라.

  1. s와 o는 같은 "x" 객체의 참조이며 변환이나 복사는 없다.

  2. 정적 String은 String 후보를, 정적 Object는 Object 후보를 선택한다. 선택 뒤 재정의를 각각 찾는다.

s 호출은 base-string, o 호출은 sub-object다. 인수 객체가 같다는 이유로 결과가 같지는 않다.

비교할 점

오버로드 선택과 수신자 디스패치를 별개 열에 기록한다.

재정의를 추가한 뒤 남는 차이

Sub에 render(String)를 추가 재정의하여 "sub-string"을 반환하도록 한 별도 설계를 추적하라.

  1. 정적 시그니처는 여전히 s에 String, o에 Object다.

  2. 새 Sub는 두 시그니처 모두 재정의했다.

s 호출은 sub-string, o 호출은 sub-object다. 두 본문이 Sub에 있다는 이유로 같은 시그니처가 되지는 않는다.

비교할 점

원래 설계와 변경 설계의 선언을 섞지 않는다.

종이와 본문으로 직접 해보기

Cat은 위처럼 sound만 재정의한다. Animal x=new Cat(); 다음 x=new Dog(); 후 두 호출의 결과를 비교하라. null을 넣으면?

힌트 보기

각 호출 시 참조의 현재 대상을 확인한다.

풀이 보기

대입 전 meow, Dog 대입 후 woof다. null 대상에서 sound 호출은 NullPointerException이 예상된다.

스스로 풀어보기

먼저 답과 이유를 적고, 필요한 만큼 힌트를 한 단계씩 열어 보세요.

연습 1 · 값과 상태 예측

원래 선언에서 b.render(null)은 어떤 후보와 본문을 선택하나?

힌트 1

null 인수는 참조형 String과 Object 양쪽에 적용된다.

힌트 2

이 둘 중 String이 더 구체적이며 수신자 b는 null이 아니다.

풀이와 답 확인

  1. render(String)를 선택한다.

  2. Sub는 그 선언을 재정의하지 않아 Base 본문이다.

base-string이다. 이 본문은 인수를 역참조하지 않으므로 null 인수만으로 예외가 생기지 않는다.

흔한 오답에서 다시 생각하기

null이 있으면 모든 메서드 호출이 NullPointerException이다.

null 수신자와 null 인수는 다르다.

연습 2 · 오류 찾아 고치기

o의 실제 클래스가 String이므로 b.render(o)는 base-string이라고 했다. 어느 단계를 고칠까?

힌트 1

인수 표현식 o의 선언을 읽는다.

힌트 2

런타임 탐색은 정적으로 선택된 시그니처를 유지한다.

풀이와 답 확인

  1. o는 Object 타입이므로 render(Object)를 선택한다.

  2. 실제 Sub가 그 시그니처를 재정의했다.

sub-object로 교정한다.

흔한 오답에서 다시 생각하기

수신자와 인수 모두의 실제 클래스에 대해 전체 오버로드를 다시 고른다.

이 예제는 다중 디스패치 언어의 규칙이 아니다.

연습 3 · 직접 만들어 보기

원래 두 결과를 검토하는 추적 장부를 설계하라. null 수신자도 별도 행으로 넣어라.

힌트 1

시그니처와 구현 클래스 칸을 나눈다.

힌트 2

수신자 null에서는 실행 본문을 찾을 실제 객체가 없다.

풀이와 답 확인

  1. s 행은 String/Base/base-string, o 행은 Object/Sub/sub-object로 기록한다.

  2. Base z=null에서 z.render(s)는 정적으로 String 후보를 고르지만 런타임 수신자 null에서 예외이며 정상 반환 문자열은 없다.

정상 반환과 예외를 별도 결과 종류로 쓴다.

흔한 오답에서 다시 생각하기

정적 후보가 있으면 항상 그 본문을 실행한다.

유효한 인스턴스 수신자라는 런타임 조건도 필요하다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

원래 Sub의 별도 메서드에서 super.render(o)를 호출하면 재정의 Sub.render(Object)가 다시 선택되나?

힌트 1

super는 일반 virtual 수신자 호출과 다르다.

힌트 2

인수 o는 Object 타입이다.

풀이와 답 확인

  1. 상위의 render(Object)를 선택한다.

  2. super 호출은 이 Sub 재정의를 우회하여 Base 본문을 사용한다.

base-object다. b.render(o)의 sub-object와 구별한다.

흔한 오답에서 다시 생각하기

실제 객체가 Sub이면 super도 무조건 Sub 본문이다.

super 호출 모드는 지정 상위 본문을 사용한다.

내 말로 설명하기

같은 인수 객체가 같은 오버로드를 뜻하나?

설명 기준 확인

호출 위치의 정적 표현식 타입이 달라 다른 시그니처가 선택될 수 있다.

null 인수와 null 수신자는 같은가?

설명 기준 확인

인수가 null이어도 본문 계약상 가능할 수 있지만 null 인스턴스 수신자는 호출을 받을 객체가 없다.

한 단계 더

void show(Animal a)와 void show(Cat c)가 있고 Animal a=new Cat()로 show(a)를 호출한다고 가정하라. 정적 인수 타입 Animal로 Animal 오버로드를 선택한다. 그 본문 안의 a.sound()는 Cat의 meow를 사용할 수 있다. 두 단계의 선택을 따로 적어 같은 런타임 객체로도 질문이 다름을 설명하라.

출처와 확인 범위
  • Java Language Specification §15.12.4.4

    static/super/virtual/interface 호출 모드, null 수신자, 실제 런타임 클래스에서 시작하는 재정의 메서드 탐색 본문을 실제 읽었다. 예제는 Java의 단순 비private 인스턴스 메서드이며 특수 MethodHandle 규칙을 적용하지 않는다.

  • Java Language Specification §15.12.1–15.12.2 — Compile-time method selection

    정적 선언 타입의 탐색과 접근 가능·적용 가능한 후보 중 가장 구체적인 시그니처를 선택한 뒤 런타임 디스패치에 사용한다는 실제 본문을 읽었다. 자체 show(Animal)/show(Cat)의 정적 선택 근거를 보강한다.

상속에서 쓰던 내부 호출을 위임으로 옮기면 어느 객체의 hook이 실행될까?

새 Java 모형의 Sender.send(s)는 this.decorate(s)를 반환하고 Sender.decorate(s)는 "base:"+s다. Special extends Sender는 decorate(s)를 "special:"+s로 재정의한다. Special 객체에서 상속된 send를 호출해도 this는 그 Special 객체이므로 내부 decorate는 Special의 재정의를 사용한다. 선언은 같은 패키지의 접근 가능한 비private 인스턴스 메서드다.

별도 Wrapper는 Sender helper를 필드에 보관한다. Wrapper에도 decorate(s)가 있어 "wrapper:"+s를 반환하지만 send(s)의 본문을 helper.send(s)로 작성했다. helper가 평범한 Sender라면 그 내부 this는 helper이며 Wrapper가 아니다. 결과는 "base:x"다. Wrapper의 메서드 이름이 같다고 다른 객체의 내부 호출 대상이 바뀌지 않는다. helper가 Special이면 "special:x"로 바뀌지만 역시 Wrapper.decorate의 실행은 아니다.

위임의 계약에는 상태의 공유·교체도 포함한다. 자체 순차 Formatter는 prefix 문자열을 보관하고 format(s)=prefix+s로 정한다. W1과 W2가 같은 Formatter F를 쓰면 F.prefix 변경은 둘의 다음 결과를 함께 바꾼다. W1.helper를 새 Formatter G로 교체하면 이후 F 변경은 W2에만 보인다. 두 협력 객체를 보관하는 설계와 실제 Scala trait 조합의 선형화 규칙은 다르며 여기서는 어느 언어의 자동 복사나 자동 전달도 가정하지 않는다.

상속은 구현과 관계를 함께 만든다

상속은 상위의 멤버와 구현을 이어받아 하위 클래스를 만드는 장치다. 많은 언어에서는 상속 선언이 하위타입 관계도 만든다. 그러나 코드를 조금 재사용하려고 상속했다는 동기만으로 상위 계약을 실제로 잘 지킨다고 보장되지는 않는다.

상위의 변경이 하위의 가정에 영향을 줄 수 있으므로 어떤 메서드를 재정의할 수 있고 어떤 불변식을 지켜야 하는지 확인한다. 내부 구현을 무조건 직접 만지는 하위 클래스는 작은 상위 변경에도 깨질 수 있다. 실제 위험은 특정 계약과 변경으로 판단한다.

위임은 다른 객체에 요청을 보낸다

위임에서는 객체가 협력 객체를 보관하고 작업을 그 객체에 전달한다. 예컨대 Notifier가 Formatter를 가지고 format(message)를 호출한다. Formatter를 바꾸어 행동을 선택하는 방식은 Notifier가 Formatter의 하위클래스일 필요가 없다.

단순한 전달만으로 위임 대상의 모든 멤버가 자동 공개되는 것은 아니다. Notifier가 어떤 인터페이스를 구현하고 어떤 메서드를 전달하는지 작성해야 한다. 협력 객체를 공유하면 그 객체의 가변 상태도 공유될 수 있으므로 복사·공유·교체 정책을 정한다.

믹스인은 기능 조각을 합친다

믹스인은 클래스에 기능 조각을 결합하는 장치다. Scala의 trait은 추상 요구와 구현을 제공하여 다른 클래스와 조합할 수 있다. 한 슈퍼클래스와 여러 믹스인을 합치는 예가 있지만 모든 언어의 믹스인이 동일한 문법과 의미를 갖지는 않는다.

두 조각이 같은 이름을 제공하거나 상위 호출을 이어 쓰면 조합 순서와 충돌 해소 규칙을 알아야 한다. 여기서는 언어 규칙 전체 대신 prefix 기능과 upper 기능을 순서대로 적용하는 자체 순수 메시지 모형을 정의한다. 순서 효과와 실제 Scala 선형화를 혼동하지 않는다.

준비 개념

  • 함수의 입력과 반환

  • 생산·소비·읽기쓰기의 변성 차이를 추적한다

  • 타입 검사와 행동 계약의 차이를 이해한다

읽기 관점은 넓힐 수 있어도 같은 저장소의 쓰기 권한도 넓힐 수 있을까?

Cat<:Animal, Dog<:Animal이며 서로 Cat과 Dog 사이의 관계는 없다고 둔다. 자체 Read<T>는 get():T만 제공하고 Write<T>는 put(T)만 제공한다. Cat을 보장하는 저장소의 Read<Cat> 관점을 Read<Animal>로 제공하면 반환 Cat이 Animal이므로 안전한 방향이다. 이것은 안쪽 Cat 객체 자체를 복제하거나 immutable로 바꾸었다는 뜻은 아니다. 관점이 제공하는 연산만 제한한다.

같은 Cat 저장소의 Write<Cat>를 Write<Animal>로 넓히면 Dog를 넣는 요청이 생겨 Cat 읽기 약속을 깨뜨린다. 입력만 받는 관점은 반대 방향이다. 모든 Animal을 받는 Write<Animal>을 Cat만 요청하는 Write<Cat> 자리에 제공할 수 있다. 읽기 관점의 공변성과 쓰기 관점의 반공변성을 각각 인정해도 두 관점을 합친 가변 Box를 공변으로 만들 수는 없다. 언어마다 선언·사용 위치의 검사 규칙을 확인한다.

타입 관계와 업무 행동도 별도다. 자체 잔액 계약의 take(k)는 정수 balance≥0 및 0≤k≤balance에서 성공하고 잔액을 이전 balance−k로 만들어 반환한다. 허용 범위 밖 요청은 거절하며 상태를 보존한다. 명목상 같은 인터페이스를 구현하더라도 k≤5만 성공하는 Limited나 추가 수수료 1을 빼는 Fee는 이 계약의 대체가 아니다. 각각 허용 입력을 줄이거나 성공 후 약속을 바꾼다. 모든 정수는 수학적 모형이며 실제 언어 overflow·예외·동시 결제는 검증하지 않았다.

먼저 확인할 개념

대체 가능한 방향을 적는다

S<:T는 S를 T가 요구되는 곳에 사용할 수 있는 하위타입 방향을 표시한다. Cat<:Animal이면 Animal 입력에 Cat을 전달하는 방향이 자연스럽다. 타입 시스템이 허용하는 대체와 메서드가 실제 행동 약속을 지키는지는 서로 다른 검토 대상이다.

같은 메서드 이름을 가지고 있다고 모든 언어가 자동 하위타입으로 인정하지 않는다. 명시적인 선언을 요구하는 명목적 타입과 구조를 비교하는 타입 체계가 있다. 이 소단원의 Cat/Animal 관계는 명시적으로 주어졌다고 가정한다.

만드는 것과 받는 것은 반대다

Producer<T>는 T를 반환만 하고 Consumer<T>는 T를 받기만 하는 자체 인터페이스라고 두자. Cat 생산자는 항상 Animal을 생산한다는 요구를 만족하므로 공변이면 Producer<Cat><:Producer<Animal>이다.

Animal을 모두 처리하는 소비자는 Cat도 처리하므로 반공변이면 Consumer<Animal><:Consumer<Cat>이다. 반대로 Cat만 처리하는 소비자에게 Dog를 맡길 수는 없다. 선언된 타입 매개변수의 사용 위치가 해당 변성을 지키는지는 언어의 규칙으로 검사한다.

읽고 쓰는 상자는 단순 공변이 아니다

Box<Cat>을 Box<Animal>로 허용한다면 Animal 상자 참조를 통해 Dog를 넣고 원래 Cat 상자 참조로 읽는 반례가 생긴다. 같은 가변 저장소를 공유한 조건이 핵심이며 자동 복사 상자로 가정하지 않는다.

Scala의 기본 불변 타입 매개변수와 Java의 일반 제네릭 상자는 이 단순 대체를 허용하지 않는다. 읽기 전용 인터페이스 등 제한된 관점을 설계하면 다른 대체가 가능할 수 있다. 함수 타입은 일반적인 안전 대체에서 입력 반공변·출력 공변 방향을 따르되 언어별 표기와 예외를 확인한다.
