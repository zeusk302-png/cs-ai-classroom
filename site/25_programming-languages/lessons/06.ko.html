소단원 6.1

재귀적 데이터형

상자 안에 같은 종류의 상자가 들어가면 데이터는 어디서 끝날까?

준비 개념과 학습 목표

준비 개념

  • OCaml에서 variant는 생성자 이름별로 여러 형태를 나눈 타입이다.

  • Leaf와 Node는 아래에서 직접 선언하는 생성자이며 함수 호출 이름과 구별한다.

  • 예제는 유한·비순환 트리와 작은 int 값을 가정하고 실제 실행하지 않았다.

학습 목표

  • 기저 형태와 재귀 형태를 분리한다.

  • 생성자에 실린 값의 타입을 읽는다.

  • 불변 구조 공유와 깊은 불변성을 구별한다.

그림에 잎이 네 번 보이면 서로 다른 잎 객체도 네 개일까?

같은 불변 하위 값을 여러 곳에서 사용해도 읽기 결과는 안전하게 공유할 수 있다. 그러나 펼친 트리의 출현 수와 공유 그래프의 서로 다른 객체 수는 다른 질문이다. 이 보강은 원본 tree = Leaf of int | Node of tree * tree를 그대로 쓰고, 종이 객체 모형에서 각 생성자 조립에 새 객체 하나를 부여한다. 정수나 컴파일러 헤더의 바이트 수는 세지 않는다. 기존 이름으로 묶는 일은 새로운 생성자 조립이 아니다.

객체 A=Leaf 4, B=Leaf 7, C=Node(A,B), D=Node(C,C)를 이 순서로 조립한다. D를 화살표대로 펼치면 C가 두 번, A와 B가 각각 두 번 나타나 생성자 출현은 7개다. 서로 다른 종이 객체는 A/B/C/D의 4개다. 잎 출현은 4개이고 합은 22이며, 같은 C를 두 번 방문하는 일반 구조적 sum도 호출 7번을 한다. 공유가 있다는 사실만으로 이 함수가 자동 메모화되는 것은 아니다.

지속적 갱신은 기존 D를 바꾸는 대신 지정 경로의 새 구조를 만든다. D의 왼쪽 C 안에서 오른쪽 B만 Leaf 9로 바꾸면 E=Leaf 9, F=Node(A,E), G=Node(F,C)를 조립한다. 오른쪽 C와 그 A/B는 그대로 공유한다. G의 합은 24지만 D의 합은 여전히 22다. 구조가 불변이어도 payload를 int ref로 바꾼 별도 자료형에서는 참조 대상 변경이 공유 경로에 모두 보일 수 있다. 아래 예제들은 각각 지정 초기값에서 독립 시작하며 실제 OCaml·할당·학생 실행은 없다.

먼저 확인할 개념
  • 재귀 생성자와 유한 구조

    펼친 생성자 출현과 공유된 하위 값의 구별에서 출발한다.

  • 구조를 따라 합을 구하는 재귀

    공유 화살표를 따라 반복 방문하는 함수의 호출 수와 결과를 함께 읽는다.

끝나는 형태와 확장하는 형태

type tree = Leaf of int | Node of tree * tree는 잎 하나 또는 두 하위 트리를 묶은 노드라는 자체 자료형이다. Leaf는 더 작은 tree를 요구하지 않아 조립의 출발점이 된다. Node는 이미 만들어진 tree 두 개를 받으므로 여러 단계로 큰 구조를 만들 수 있다.

재귀적이라는 말은 매 값이 무한히 커야 한다는 뜻이 아니다. 아래 t는 Leaf 2, Leaf 5, Leaf 1을 유한하게 조합했다. 이 단원은 유한 비순환 값을 대상으로 크기와 종료를 논증하며 무한 스트림·순환 그래프를 같은 조건으로 다루지 않는다.

type tree = Leaf of int | Node of tree * tree
let left = Leaf 2
let right = Node (Leaf 5, Leaf 1)
let t = Node (left, right)
let t2 = Node (left, Leaf 9)
(* OCaml 교육용 정의, 실제 실행하지 않음 *)

값과 타입을 다른 층에서 읽기

Node의 두 인수는 둘 다 tree이며 int 두 개를 직접 넣는 Node(2,3)은 이 선언에 맞는 tree 조립이 아니다. Leaf가 int를 tree로 감싼 뒤 Node(Leaf 2,Leaf 3)로 묶는다. 타입 이름 tree는 값 하나의 이름이 아니라 허용되는 형태의 규칙이다.

t의 루트 1개, 오른쪽 내부 Node 1개, 잎 3개를 그림으로 나누면 전체 생성자 출현 수는 5개다. 저장된 숫자의 합 8과 생성자 수 5는 서로 다른 관찰이다. 구현 메모리 바이트 수는 컴파일러·표현 조건을 모르므로 이 숫자만으로 단정하지 않는다.

새 구조와 원래 구조

t2는 left를 이용해 새 Node를 만드는 정의이며 left나 t를 제자리에서 수정하는 명령이 아니다. 같은 불변 하위 구조를 여러 값이 공유해도 읽기 결과를 서로 덮어쓰지 않는다. 그림에서는 공유 화살표를 쓰거나 두 번 펼쳐 그릴 수 있지만 논리적 출현 수와 실제 할당 수는 구별해야 한다.

불변 컨테이너라고 모든 안쪽 대상이 깊게 불변인 것은 아니다. payload, 즉 안에 저장한 내용이 변경 가능한(mutable) 참조라면 참조 대상의 상태 변화가 있을 수 있다. 지금 tree의 payload는 int이고 변경 명령을 사용하지 않아 순수한 유한 구조에 집중한다.

도달 객체 열은 이름 정체성의 집합이며 같은 A를 중복 세지 않는다. 펼친 열은 경로별 출현을 세므로 C가 D 아래 두 번 나온다. D와 G를 모두 보존할 때의 합집합 7개를 한 루트 G의 도달 6개와 구별한다.

중간 과정을 따라가는 예제

t의 생성자 출현 수·잎 개수·저장 정수 합을 구하고 t2를 정의한 뒤 t가 바뀌는지 설명하라.

  1. t의 루트는 Node이며 왼쪽 Leaf 2, 오른쪽 Node를 가진다.

  2. 오른쪽 Node의 두 자식은 Leaf 5와 Leaf 1이다.

  3. Node 2개와 Leaf 3개로 출현 수 5, 잎 수 3이다.

  4. 잎의 정수 합은 2+5+1=8이다.

  5. t2 조립은 새 값을 정의하며 t의 구조나 정수 합을 바꾸지 않는다.

t는 생성자 출현 5·잎 3·합 8이다. t2는 출현 3·잎 2·합 11이며 t의 합 8은 유지된다.

조건을 바꾸어 비교하기

공유는 방문 횟수를 자동으로 줄이지 않는다

D=Node(C,C)에서 원본 sum을 적용하고 종이 객체 수·출현 수·함수 호출 수를 비교한다.

  1. C 방문마다 Node 한 번과 두 Leaf 두 번으로 세 호출이다. D 루트의 한 호출 뒤 C를 왼쪽/오른쪽에서 각각 방문한다.

  2. 호출 수는 1+3+3=7, 값은 11+11=22다. 객체 정체성은 A/B/C/D 네 개이며 이 수는 호출 수가 아니다.

객체 4개, 출현/호출 7개, 잎 출현 4개, sum 22다.

비교할 점

공유 데이터 표현과 계산 결과 캐시는 별도 규약이다.

같은 B가 보여도 하나의 경로만 바꾼다

D의 왼쪽-오른쪽 경로를 Leaf 9로 바꾸어 G를 만든다. 원래 D와 오른쪽 C의 결과도 설명한다.

  1. 해당 경로의 B를 덮어쓰지 않고 E를 새로 만든다. E와 기존 A를 묶은 F, F와 기존 C를 묶은 G를 만든다.

  2. F의 합은 4+9=13이고 기존 C의 합은 11이다. G는 24다. 기존 D는 C를 두 번 가리키므로 22를 유지한다.

새 조립 객체는 E/F/G 세 개이고 G 도달 객체는 여섯 개다. D와 G를 함께 보존하면 일곱 개다.

비교할 점

값이 같다는 비교와 객체 정체성·갱신 경로를 따로 정한다.

종이와 본문으로 직접 해보기

u=Node(t,Leaf 4)의 펼친 그림에서 생성자 수·잎 수·합을 구하라. 실제 메모리 할당 수라고 주장할 수 있는지도 적어라.

힌트 보기

기존 t의 수에 새 루트와 새 Leaf를 더한다.

풀이 보기

펼친 구조의 생성자 수는 5+1+1=7, 잎은 3+1=4, 합은 8+4=12다. t의 공유 표현 여부에 따라 실제 할당을 세는 기준은 달라질 수 있으므로 7을 메모리 할당 개수라고 단정하지 않는다.

오해와 반례

재귀 타입의 값은 언제나 끝없이 자기 자신을 포함한다.

Leaf 2 자체는 tree이며 더 작은 tree가 필요 없다. 유한 조립 t도 끝나는 잎이 있다. 기저 형태와 유한 값 전제를 함께 읽어야 한다.

스스로 풀어보기

먼저 답과 이유를 적고, 필요한 만큼 힌트를 한 단계씩 열어 보세요.

연습 1 · 값과 상태 예측

K=Node(D,D)를 새로 조립한다. 서로 다른 도달 객체, 펼친 출현, 잎 출현, 일반 sum 호출 및 합을 구하라.

힌트 1

객체 D를 두 번 만들지 않았다.

힌트 2

펼친 두 D와 새 루트를 합친다.

풀이와 답 확인

  1. 도달 집합은 A/B/C/D/K의 다섯 개다. 출현은 1+7+7=15이고 잎은 4+4=8이다.

  2. 일반 sum 호출은 15번, 합은 22+22=44다.

도달 5개, 출현/호출 15개, 잎 8개, 합 44다.

흔한 오답에서 다시 생각하기

도달 객체가 다섯 개이므로 sum 호출도 다섯 번이다.

함수는 별도 방문 캐시 없이 각 자식 경로에 재귀 호출한다.

연습 2 · 오류 찾아 고치기

갱신자가 D의 왼쪽-오른쪽 값만 9로 바꾸려다가 공유 B 자체를 덮어쓰겠다고 했다. 현재 int payload의 불변 자료형에서 무엇이 잘못이고, 별도 mutable leaf 모형에서는 어떤 결과가 생길까?

힌트 1

현재 자료형에는 B를 제자리 갱신하는 연산이 없다.

힌트 2

별도 가변 B라면 D의 두 경로 모두 같은 대상이다.

풀이와 답 확인

  1. 불변 자료형은 E/F/G의 경로 복사를 사용해야 한다. 기존 D를 바꾸지 않는다.

  2. 별도 가변 객체 모형에서 B의 payload를 9로 덮어쓰면 C의 합이 13, D의 합이 26으로 바뀐다. 이는 왼쪽 경로만 변경한 G의 합 24와 다르다.

현재 계약에서는 새 G의 합이 24이고 옛 D의 합이 22다. 별도 가변 모형에서 D의 합이 26이 되는 결과를 같은 갱신으로 취급하지 않는다.

흔한 오답에서 다시 생각하기

공유 B를 고치면 원하는 한 경로만 달라진다.

공유 정체성 때문에 다른 경로도 같은 B를 관찰한다.

연습 3 · 직접 만들어 보기

유효 경로의 지정 잎을 바꾸는 순수 replace를 설계하라. 경로는 Left/Right의 목록이며 빈 경로는 현재 값이 Leaf일 때만 유효하다. D의 오른쪽-왼쪽을 Leaf 1로 바꾼 H의 새 객체 수와 합을 적어라.

힌트 1

유효 경로만 받는 계약을 먼저 적는다.

힌트 2

선택하지 않은 형제는 기존 값을 그대로 공유한다.

풀이와 답 확인

  1. Leaf와 빈 경로에서는 새 Leaf 1을 반환한다. Node와 Left/Right에서는 해당 자식에 replace를 적용하고 기존 다른 자식과 새 Node를 묶는다. 부적합한 경로는 별도 오류로 정의한다.

  2. 새 Leaf 1, 오른쪽 Node(새 Leaf 1,B), 새 루트 H를 만든다. H의 합은 기존 왼쪽11+새 오른쪽8=19다.

새 조립 세 개, H의 합 19, 기존 D의 합 22가 유지된다.

흔한 오답에서 다시 생각하기

경로를 따라 모든 자식을 깊은 복사해야 한다.

불변 구조에서는 선택하지 않은 형제의 공유를 보존할 수 있다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

기존 루트가 유지되고 깊이 d의 유효 잎 경로 하나를 갱신하는 종이 생성자 모형에서 새 객체 수를 증명하라. 같은 정수로 바꾸는 경우도 포함한다.

힌트 1

여기서는 동등값 갱신을 생략하는 최적화가 없다.

힌트 2

각 경로 Node마다 새 Node 하나가 필요하다.

풀이와 답 확인

  1. 깊이 0이면 새 Leaf 하나이므로 1이다. 깊이 d+1이면 자식 경로에서 d+1개를 만들고 부모 Node 하나를 더해 d+2개다.

  2. 따라서 새 조립은 d+1개다. 값이 같아도 현재 명시한 알고리즘은 새 객체를 만들며 실제 컴파일러 할당 제거·GC를 측정하지 않는다.

구조 경로 길이에 대한 귀납으로 d+1을 얻는다. 전체 도달 객체 수나 실제 바이트 수는 이 식과 다르다.

소단원 6.2

패턴 매칭과 구조적 재귀

잎과 가지가 다른데 하나의 함수가 어떻게 둘을 빠짐없이 읽을까?

준비 개념과 학습 목표

준비 개념

  • tree는 Leaf of int 또는 Node of tree * tree다.

  • 패턴 매칭은 값 형태에 맞는 분기를 고르고 그 안의 값을 이름에 연결한다.

  • 구조적 재귀는 입력의 실제 하위 구조에 재귀 호출하는 설계다.

학습 목표

  • 분기와 바인딩을 단계별로 추적한다.

  • 구조 크기의 감소로 유한 트리 재귀 종료를 설명한다.

  • 합과 높이의 기저·결합 규칙을 구별한다.

기저 분기가 있어도 Neg를 없애지 않는 재귀는 끝날까?

이제 자체 식 자료형 expr = Num of int | Neg of expr | Add of expr * expr를 사용한다. 유한·비순환 식만 입력이고 정수 계산은 범위 안의 정확 계산이다. eval(Num n)=n, eval(Neg a)=−eval(a), eval(Add(a,b))=eval(a)+eval(b)로 정의한다. 생성자마다 요구하는 자식 수가 달라 하나의 함수에서 일치 분기와 크기 감소를 함께 확인해야 한다.

새 E=Add(Neg(Num 3), Add(Num 3, Num 2))의 값은 2다. 같은 Num 3 값이 두 번 나타나도 노드 역할을 지우지 않는다. 전체 출현 수는 6개이고 eval 호출도 6번이며 간선 기준 높이는 2다. 설명의 왼쪽 전개는 종이 일정이다. 순수한 정확 계산의 값 대응으로만 사용하며 OCaml 일반 식의 실제 좌우 평가 순서를 주장하지 않는다.

분기를 모두 덮는 것과 올바른 뜻을 계산하는 것은 다르다. Num 분기 뒤 _ -> 0을 넣으면 Neg/Add가 모두 처리되어도 의미가 틀리며, 새 Mul을 추가해도 이 와일드카드가 누락을 가릴 수 있다. Neg a 분기에서 eval(Neg a)를 다시 호출하면 호출 입력의 출현 수가 줄지 않는다. Num 기저가 있다는 사실이 이 반복의 종료를 증명하지 않는다. 아래 모든 문항은 앞 문항의 잘못된 수정을 이어받지 않는 독립 비교다.

먼저 확인할 개념
  • 패턴 일치와 크기 감소

    첫 분기 선택과 구조적 재귀의 종료 조건을 새 생성자에 적용한다.

  • 생성자별 인수의 자료형

    Num/Neg/Add의 서로 다른 자식 수와 뜻을 선언에 맞춘다.

모양을 읽으며 이름 붙이기

match t with Leaf n -> n | Node(l,r) -> ...에서 Leaf 5는 첫 분기에 맞고 n=5를 얻는다. Node 값은 둘째 분기에 맞으며 l과 r은 그 노드의 왼쪽·오른쪽 tree에 연결된다. 변수 이름은 이미 존재하는 하위 값의 이름이지 제자리 수정 명령이 아니다.

여러 패턴이 맞을 수 있으면 첫 일치 분기가 선택된다. 맨 앞의 _는 모든 값을 잡으므로 뒤의 구체적 패턴을 가릴 수 있다. 모든 생성자를 명시하면 자료형을 확장했을 때 누락을 알아차리기 쉽다. 경고의 실제 출력은 이 단원에서 실행해 관측하지 않았다.

작아지는 입력으로 설계하기

sum의 Leaf 분기는 잎의 정수를 반환한다. Node 분기는 두 실제 자식에 sum을 적용하고 합친다. height는 Leaf를 0으로 두고 Node에서 1+max(자식 높이)를 쓰므로 잎 수나 합과 다른 측정이다. 이 높이는 루트에서 잎까지의 최대 간선 수라는 정의를 먼저 고정했다.

유한 비순환 트리에서 각 자식의 생성자 출현 수는 부모 전체보다 작다. Leaf가 기저 분기로 끝나므로 이런 호출은 종료 논증을 갖는다. Node 분기에서 sum t를 그대로 다시 호출하면 입력이 작아지지 않아 이 논증을 사용할 수 없다.

type tree = Leaf of int | Node of tree * tree
let rec sum t =
  match t with
  | Leaf n -> n
  | Node (l, r) -> sum l + sum r
let rec height t =
  match t with
  | Leaf _ -> 0
  | Node (l, r) -> 1 + max (height l) (height r)
let t = Node (Leaf 2, Node (Leaf 5, Leaf 1))

계산이 돌아오는 길

sum t는 먼저 하위 결과를 구한 뒤 그 결과를 더하는 규칙이다. 순수한 이 예제에서는 왼쪽·오른쪽 계산 순서가 숫자 합을 바꾸지 않지만 OCaml의 모든 식에 임의의 좌우 평가 순서를 가정해 부작용 순서를 주장하지 않는다. 풀이의 순서는 설명용으로 정한 전개다.

호출 수와 실행 시간도 다르다. 이 정의에서 각 생성자 출현마다 sum 호출 한 번이 있으므로 펼친 트리의 출현 5개에 대해 호출 5번을 세지만 실제 장비 시간을 얻은 것은 아니다. 아주 깊은 구조의 호출 스택 문제는 종료 가능성과 별도다.

소단원 6.3

꼬리재귀·누산기

재귀 호출 뒤 할 일이 남아 있으면 어떤 기억이 필요할까?

준비 개념과 학습 목표

준비 개념

  • 리스트 []는 빈 값이고 x::xs는 첫 원소와 나머지 리스트다.

  • 누산기는 지금까지 처리한 결과를 다음 호출의 인수로 넘기는 값이다.

  • 작은 int 리스트와 순수 덧셈을 가정한다. 실제 OCaml 실행·스택 측정은 미수행이다.

학습 목표

  • 재귀 뒤 남은 연산으로 꼬리 위치를 판정한다.

  • 누산기의 의미를 불변관계로 설명한다.

  • 스택 공간·결과 저장 공간·시간을 구별한다.

더하기를 빼기로 바꾸면 같은 누산기 변환도 맞을까?

순수한 정확 덧셈에서는 처리한 합과 남은 합을 묶어 누산기 불변식을 만들었다. 그러나 재귀 뒤 남은 연산을 지울 때는 결합법칙과 원소 순서가 바뀌는지 확인해야 한다. 자체 rightSub([])=0, rightSub(x::xs)=x−rightSub(xs)를 보자. 목록 [8,3,1]에서는 8−(3−(1−0))=6이다. go(acc,x::xs)=go(acc−x,xs), go(acc,[])=acc에 초기0을 주면 −12이므로 단순히 연산자를 바꾸는 꼬리 변환은 실패한다.

올바른 대안은 부호 sign을 상태에 더한다. 시작 (acc,sign)=(0,+1)이고 x 처리 후 (acc+sign×x,−sign)으로 갱신한다. 첫 원소에는 +, 다음에는 −, 다음에는 +가 붙어 rightSub의 전개와 같은 교대 합을 만든다. 불변식은 acc+sign×rightSub(rest)=rightSub(원래 목록)이다. 정확 정수와 유한 목록에서 이 식의 보존을 증명하고 빈 목록의 acc를 답으로 삼는다.

결과 목록을 만드는 꼬리 함수는 호출 스택 이외의 저장을 요구한다. 자체 map의 결과 순서를 보존하려면 왼쪽부터 f(x)를 계산하여 revAcc 앞에 넣은 뒤 마지막에 한 번 뒤집을 수 있다. f(x)=10x와 [1,2,3]에서는 revAcc가 [10], [20,10], [30,20,10]으로 자라며 최종 [10,20,30]이다. 두 cons 기반 새 리스트를 모두 살아 있게 두는 종이 피크는 2n개 칸이고, 중간 칸을 회수하는 실제 GC 피크는 이 값으로 확정하지 않는다. 꼬리 위치·반환 순서·새 cons 누적 수·실제 시간과 메모리를 서로 다른 관찰로 둔다.

반환 뒤 남는 덧셈

plain_sum의 x+plain_sum xs는 자식 호출의 결과를 받은 뒤 x를 더해야 한다. 따라서 재귀 호출이 함수의 마지막 완료 작업이 아니다. x를 기억한 여러 호출의 복귀가 필요하다는 그림으로 읽을 수 있다. 반면 go의 마지막 식 go(acc+x) xs는 그 호출 결과를 그대로 돌려준다.

꼬리재귀는 함수 끝 줄에 호출 이름이 보인다는 뜻보다 호출 반환 뒤 남은 계산이 없는지를 묻는다. 1+go ...는 호출이 끝에 있어 보여도 덧셈이 남는다. 조건 분기가 있는 함수는 각 재귀 호출의 위치를 따로 확인한다.

let rec plain_sum xs =
  match xs with
  | [] -> 0
  | x :: rest -> x + plain_sum rest
let rec go acc xs =
  match xs with
  | [] -> acc
  | x :: rest -> go (acc + x) rest
let tail_sum xs = go 0 xs
(* 예상 값은 종이 추적, 실제 OCaml 실행하지 않음 *)

누산기에서 잃지 않아야 할 뜻

go(acc,rest)의 관계는 acc+남은 원소 합=처음 리스트 전체 합이다. 처음 acc=0이며 전체 리스트가 남아 있어 성립한다. 첫 x를 처리하면 acc에 x를 더하고 나머지에서 x를 제거하므로 같은 합을 유지한다. 빈 리스트에 도달하면 남은 합 0이라 acc가 전체 답이다.

누산기 초기값을 아무 수나 고르면 다른 문제를 푼다. go 10 [3;-1;4]는 합만 반환하는 tail_sum과 달리 10을 더한 16이다. 누산기를 설명하지 않고 코드 모양만 바꾸면 잘못된 초기값이나 원소 순서 역전을 놓치기 쉽다.

공간 효율의 조건과 한계

OCaml의 꼬리 호출 구현을 활용하는 설계는 깊은 비꼬리 재귀가 보관하는 복귀 정보를 줄일 수 있다. 이 예제는 길이 n에 대해 원소를 한 번씩 처리하므로 두 방식 모두 n에 비례하는 작업을 한다. 꼬리재귀라는 이유만으로 실제 실행 시간이 무조건 더 빠르다고 말하지 않는다.

리스트를 누산기에 앞붙여 만드는 reverse 설계는 호출 스택을 줄여도 결과 리스트 n개 원소의 저장 공간이 필요하다. 스택 공간이 줄었다는 주장과 총 메모리 O(1) 주장은 다르다. 이 단원은 실행 환경의 최적화 여부·실제 시간·메모리 수치를 관측하지 않았다.

중간 과정을 따라가는 예제

  1. 오른쪽 결합의 값은 8 − (3 − 1) = 6이다. 초기 acc가 0인 왼쪽 연속 빼기의 값은 −8, −11, −12 순으로 바뀐다.

f(x) = 10x이고 입력은 [1,2,3]이다. revAcc와 마지막 뒤집기 및 새 cons의 누적 수를 세라.

  2. 뒤집기에도 새 cons를 쓰는 자체 모형에서는 첫 단계에 3개, 둘째 단계에 3개를 만들어 누적 6개가 된다. 원래 입력의 3개 칸은 새 cons 수에 포함하지 않는다.

풀이와 답 확인

  1. 입력이 비면 revAcc를 새 cons 기반 reverse로 뒤집어 반환한다. x::rest면 y=f(x)를 한 번 구해 y::revAcc와 rest로 꼬리 호출한다.

  2. 빈 목록의 결과는 []이고 콜백 호출은 0회, 새 cons는 0개다. 길이가 n이면 콜백 호출은 n회이고 두 단계의 새 cons 누적 수는 2n개이며 입력을 변경하지 않는다.

접두 역순 불변식으로 최종 정순을 보존한다. 새 cons 누적 수와 실제 메모리 피크는 분리한다.

마지막 reverse에서 f를 다시 호출해도 콜백n회다.

그렇게 하면 호출2n회이고 임의 f에서는 원래 의미마저 달라질 수 있다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

교대 누산기의 불변식 acc+sign×rightSub(rest)=원래 답을 한 단계와 기저에서 증명하라. 그 뒤 1+go(...)가 꼬리 호출인지 판정하라.

힌트 1

rightSub(x::xs)=x−rightSub(xs)를 대입한다.

힌트 2

호출 결과 뒤 덧셈이 남는지 묻는다.

풀이와 답 확인

  1. 갱신 뒤 식은 (acc + sign × x) + (−sign) × rightSub(xs) = acc + sign × (x − rightSub(xs))이므로 원래 식과 같다. 남은 목록이 비면 rightSub의 값이 0이므로 acc가 답이다.

  2. 1 + go(...)에서는 go가 돌아온 뒤 1을 더해야 하므로 해당 호출은 꼬리 위치가 아니다.

유한 입력/정확 연산에서 불변식을 유지한다. 소스 줄 끝에 호출이 보인다는 이유로 꼬리라고 판정하지 않는다.
