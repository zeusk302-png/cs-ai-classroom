Subtopic 3.1

Lexical and dynamic scope

Does f find x where f was defined, or in whoever is calling f now?

Preparation and learning goals

Preparation

  • A name binding connects a name with a target. The same spelling x can refer to different bindings. Scope determines which parts of the code can use a binding.
  • A function call is an event during execution, distinct from the code location of a function definition. Calling f from g does not move f’s definition inside g.
  • Readiness check: draw outer x=10 and g’s local x=20 as two boxes. Their names match, but their bindings differ.

Learning goals

  • Distinguish the code structure of definitions from the structure of active calls.
  • Compare lexical and dynamic lookup rules in the same model.
  • Distinguish binding selection from current values, types and dynamic dispatch.

What selects a binding?

Lexical scope selects a binding using the nesting structure of the code where the name is used. A free variable is a name not bound by that function’s parameters or local declarations. If f uses an outer x and g has its own x, calling f from g does not change f’s binding to g’s x. This does not mean the binding’s value is fixed at compile time.

In the Python 3.12 example below, f’s x is a module binding, while g’s x is local to g. Python lookup does not follow arbitrary callers’ local variables. global/nonlocal, classes and annotation scopes have additional rules, so the four letters LEGB do not completely explain every case. Here we cover only modules and ordinary functions.

Define dynamic scope separately

The original dynamic model first searches the current function’s local names; if absent, it follows currently active caller frames in order, finally searching globals. With global x=10, f()=x, and g() declaring local x=20 then calling f(), direct f returns 10 and f called by g returns 20. This does not claim that Python was run in a dynamic-scope mode.

If h with local x=30 directly calls f, the dynamic model chooses 30. Inserting a caller does not change lexical f’s definition environment. Dynamic dispatch, which chooses methods using the runtime types of arguments, and Python’s dynamic typing are different concepts from dynamic name scope.

A selected binding’s value may change

Even lexical lookup can read a different later value when the selected binding is mutable. Rebinding Python’s module x from 10 to 40 makes f read current value 40 from the same module binding. A new OCaml let x may instead shadow an earlier binding with a new one, rather than modifying it. Do not copy results across languages without their assignment rules.

On paper, use different colors for definition-environment arrows and caller arrows. A lexical call frame links its parent to the definition environment retained by the function; the original dynamic model links to the active caller environment. Only the former is actually run in the complete Python example; the dynamic results are derived by hand from the stated rules.

x = 10
def f():
    return x
def g():
    x = 20
    return f()
print(f(), g())

A worked example, step by step

Global x=10; f() returns x; g() declares local x=20 and calls f(). Find the results of both calls in Python and in the original dynamic model.

  1. Module G contains x=10 and f,g. f is defined in G, not inside g.
  2. A direct call to f has no local x, so both models find 10 in G.
  3. g has local 20. Python’s f finds the module’s 10; dynamic-model f finds its caller g’s 20.
  4. Python prints 10 10. The dynamic-model results 10,20 are not actual Python stdout.

Actual historical CPython 3.12.7 stdout is 10 10 followed by a newline. The dynamic-model results 10,20 are paper results.

Try it with paper and the lesson

Draw a model with G:x=4, f()=x, g declaring local x=7 then calling f, and h declaring local x=9 then calling g. Find direct f’s return and h’s return under both lookup rules.

Show hint

Calling g from h also creates g’s local x. Dynamic lookup searches the nearest active binding first.

Show solution

Lexical f is defined in G, so direct f=4 and h=4. Under dynamic scope direct f=4; in h→g→f, g’s nearer 7 is found before h’s 9. The results are 4,7.

Misconception and counterexample

Dynamically typed languages search callers’ variables, and lexical scope fixes values forever.

Although Python is dynamically typed, f does not read g’s 20. Rebinding module x can change f’s result. Binding selection, values, types and method selection are different axes.

Check your understanding

What determines lexical lookup of a free variable?

Show answer and reasoning

The definition’s environment of code nesting.

The active caller and the definition environment are different relationships.

In dynamic h→g→f, does lookup choose h’s x if g has an x?

Show answer and reasoning

No. g’s x comes first.

The model stops at the nearest active binding.

Does a lexical function always return the same value?

Show answer and reasoning

No.

Its selected binding or object may change, or its inputs may differ.

Explore further

Extension: if f’s code, definition environment, arguments and shared store stay fixed while only its caller’s local frame changes, lexical free-variable lookup retains the same binding. Its lookup path does not include that caller. This is not a theorem that all function results are invariant. Changes to shared state, exceptions, divergence and differing arguments require separate premises. In the dynamic model, a new caller’s x entering the lookup path gives a counterexample to this binding-invariance property.

Subtopic 3.2

Bindings and the environment model

After a is connected to a different list, why does b still see the earlier list?

Preparation and learning goals

Preparation

  • An environment is a structure of bindings used to interpret names; a frame is one level of the name table. A frame may have a parent environment. The original model does not put the same name twice within one frame.
  • Rebinding a name changes its target; modifying a list element changes the inside of a shared object. Draw name-storage locations and objects separately.
  • Readiness check: draw arrows from a and b to O1, then move only a’s arrow to O2. b remains connected to O1.

Learning goals

  • Distinguish environment ρ from store σ.
  • Trace bindings, reassignment and aliases.
  • Explain a new call frame’s connection to the definition environment.

Two tables: environment and store

In the original mutable model, environment ρ is a finite table from names to storage locations ℓ, and store σ maps locations to current values. lookup returns a location if the current frame contains the name, otherwise it searches the parent. If no frame contains it, the result is unbound. Reading a name reads σ at the located position. Values may include integers or references to separate objects.

A new declaration connects a new location in the current frame and stores an initial value. Reassignment changes the value at the selected location. Real languages differ on duplicate declarations and reads before initialization, so this model is not the complete Python specification. Python names refer to objects; the arrow diagram is a corresponding model of rebinding and sharing effects.

Name locations and object aliases

After a=[1]; b=a, both a and b hold references to the same list O1. a=[9] creates new O2 and connects only a to O2. b[0]=2 does not rebind b to a new list; it changes the inside of O1. Finally a=[9], b=[2]. Sharing an object reference does not mean reassignment of one name also reassigns the other.

Separate abstract locations ℓa,ℓb from list-element storage. The locations differ, although their initially stored values are the same reference to O1. Changing an element of O1 is observable through other names viewing O1. Names with the same spelling or in the same environment need not refer to the same object.

Functions and new frames

A lexical function value is a closure ⟨parameters,body,definition environment⟩. A call evaluates arguments and creates a frame with their values in new parameter locations, linking its parent to the closure environment. Different calls have new local frames but may share captured objects. Passing an object reference as an argument value can let caller and function view the same object.

The model explains abstract meaning; it does not claim that actual memory is implemented as this dictionary or that every name has an actual address. Implementations can retain reduced environments or optimize them. Assume single sequential execution, valid live objects and defined lookup. Concurrent changes, low-level pointers and actual allocation failures require separate conditions.

a = [1]
b = a
a = [9]
b[0] = 2
print(a, b)

A worked example, step by step

Draw a,b and lists O1,O2 in the Python example and trace rebinding and element mutation.

  1. a=[1] creates O1 and connects a to it. O1’s first value is 1.
  2. b=a connects b to the same O1 reference. Different names view the same list.
  3. a=[9] creates O2 and changes only a. b remains connected to O1.
  4. b[0]=2 changes an O1 element. a sees O2’s [9], and b sees O1’s [2].

Actual historical CPython 3.12.7 stdout is [9] [2] followed by a newline. Neither actual addresses nor numeric abstract locations were measured.

Try it with paper and the lesson

Let ρ map x→ℓ1,y→ℓ2; let σ map ℓ1→O,ℓ2→O, with O=[5]. Reassign x to new P=[8] and then set O[0]=6. What do x and y see?

Show hint

Draw the two name locations and two list objects separately. Changing O does not change ℓ2’s reference.

Show solution

ℓ1 contains a reference to P, so x=[8]. ℓ2 retains its reference to O, so y=[6]. Before the object mutation y=[5]; reassigning x alone does not make y refer to P.

Misconception and counterexample

Substituting a name with a value once also explains assignment and object sharing.

In mutable state, a name’s current value can change. Rebinding a and modifying b[0] change different places, so mechanical value substitution loses aliasing effects. Distinguish this from substitution arguments for pure immutable expressions.

Check your understanding

What do ρ and σ map in the original model?

Show answer and reasoning

Names to locations, and locations to current values.

This model allows object references among current values.

After b=a, does reassigning a to a new list also rebind b?

Show answer and reasoning

No.

The name bindings are separate, so b retains the reference to the earlier object.

What is the parent of a lexical call frame?

Show answer and reasoning

The definition environment stored in the closure.

This differs from the dynamic model that always uses the active caller’s environment as parent.

Explore further

Extension: with finite acyclic parent links, lookup reduces frame depth by one at each step and terminates. Induction on the rule that searches the parent only when the current frame has no first match yields uniqueness of the nearest binding. Changing only σ while retaining ρ and its parents leaves the lookup location unchanged, but its current value may change. Do not mix the premises of immutable environments with those of languages allowing mutable stores.

Subtopic 3.3

Shadowing, lifetime and capture

After make has finished, why can inc still keep increasing its earlier x?

Preparation and learning goals

Preparation

  • Shadowing occurs when an inner name is selected before an outer binding with the same name. It differs from deleting the outer object.
  • Scope is the code region where a name can be used; lifetime is the period during execution in which a target remains alive. These axes differ.
  • Readiness check: draw a line from make’s x to the returned inc. Separate the end of make’s execution from the disappearance of captured state.

Learning goals

  • Distinguish shadowing, reassignment and object mutation.
  • Separate captured state from completion of a call’s execution.
  • Compare the conditions for late lookup and storing values at definition time.

Shadowing is not deletion

When an inner frame introduces x, lookup in that region stops at the inner x. In the outer environment it finds the original x again. Languages differ on where declarations with the same name are allowed; do not assume matching declarations in every nested block will compile. Python for/if statements do not generally create a new local function scope.

Python 3.12 nonlocal x in inc declares use of the nearest enclosing function binding rather than introducing a new local x in inc. Omitting it while writing x+=1 can make x a local name in inc, causing an error when it is read before having a value. The error variation was not run as evidence for the normal example.

Captured state needed after a call

make(3) creates captured state corresponding to x and an inc function. If inc keeps referring to that state, Python keeps the binding usable for later calls. Finishing make’s execution does not immediately destroy all required state. By contrast, a reference for which the language does not extend lifetime, such as returning the address of a C automatic array, is dangerous.

make(10) creates separate state. With c=make(3),d=make(10), repeated calls to c share state with one another, while d is separate. Actual heap/stack addresses and collection times were not measured. Whether creation copies free-variable values or shares locations or objects must be stated according to language and capture syntax.

Late lookup and capture-avoiding renaming

Python lambdas created in a loop that refer to the same outer i may all see its final value when called after the loop. Lexical scope does not mean copying every iteration’s value. lambda i=i: i is a separate technique: evaluating the default argument at each function definition stores a numeric value. A mutable object stored as a default may share a reference rather than being deeply copied.

Renaming a bound name also requires renaming its bound uses without capturing another free variable. Changing lambda x: x+y to lambda y: y+y shadows the outer free y and changes meaning. Below is a complete normal-state example assuming integer start, sequential calls and Python’s arbitrary-precision integers.

def make(start):
    x = start
    def inc():
        nonlocal x
        x += 1
        return x
    return inc
c = make(3)
d = make(10)
print(c(), c(), d(), c())

A worked example, step by step

After c=make(3),d=make(10), evaluate c(),c(),d(),c() from left to right.

  1. Draw separate boxes C.x=3 and D.x=10. Bodies match, but environments differ.
  2. The first c produces C.x=4 and return 4; the next produces C.x=5 and return 5.
  3. d produces D.x=11 and return 11, without changing C.x=5.
  4. The final c produces C.x=6 and return 6. Python evaluates print’s argument expressions from left to right.

Actual historical CPython 3.12.7 stdout is 4 5 11 6 followed by a newline. State is shared among repeated calls to each closure, rather than between c and d.

Try it with paper and the lesson

For c with C.x=0 and d with D.x=5, apply c(),d(),c(),d(). Also compare renaming x in lambda x: x+y to z or to y.

Show hint

Write both the return values and final C,D states. Check whether free y remains free.

Show solution

Returns are 1,6,2,7; final C.x=2,D.x=7. In a context without conflicting names, lambda z: z+y preserves the binding structure. lambda y: y+y captures free y and is generally a different function.

Misconception and counterexample

Lexical closures always copy values at creation, and captured state disappears when the function finishes.

The Python nonlocal counter changes the same captured state, returning 4,5,6. Shadowing by a new OCaml let, sharing a mutable array, and C++ value/reference capture also have different rules. Separate code scope from object lifetime and check what is retained.

Check your understanding

If c and d have the same inc body, do they have the same state?

Show answer and reasoning

No.

Each make call creates a different captured environment.

Without nonlocal, does x+=1 automatically guarantee modification of the outer x?

Show answer and reasoning

No.

Classifying it as a local name can cause a read-before-initialization error.

Does renaming x to y in lambda x: x+y always preserve meaning?

Show answer and reasoning

No.

The parameter captures the formerly free y, changing the binding structure.

Explore further

Extension: starting from s, call one closure normally and sequentially k≥0 times without changing x externally. Induction gives x=s+k after the calls: initially s, then exactly one increment each time. Another make has a separate location and does not affect it. This is a contract for defined state change, not absence of side effects. Fixed-width integers, concurrent calls or exceptions require new representation-range, atomicity and completion conditions. Capture-avoiding renaming and taking a value snapshot are different transformations.
