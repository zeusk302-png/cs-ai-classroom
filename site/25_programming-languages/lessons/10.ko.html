소단원 10.1

시그니처·구현 경계

다른 사람이 만든 상자를 내부를 열지 않고도 사용할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 함수의 입력과 결과 타입을 읽을 수 있다.

  • 목록과 마지막에 넣은 값을 먼저 꺼내는 스택을 안다.

학습 목표

  • 타입 시그니처와 행동 계약을 구별한다.

  • 구현을 숨긴 추상 타입의 사용 가능 범위를 판단한다.

내부 목록에 같은 값이 두 번 있어도 외부 집합은 같은가?

원본의 불변 스택은 꺼내는 순서로 계약을 관찰했다. 이번에는 정수 집합을 empty, add(x,s), contains(x,s), size(s)로만 관찰하는 자체 불변 모형을 쓴다. add는 원본을 바꾸지 않고 x를 포함한 집합을 반환하며 중복 추가는 논리 집합을 바꾸지 않는다. 모든 정수를 허용하고 실행 시간·객체 주소·내부 순서·할당 실패는 공개 관찰에서 제외한다. 각 문제는 별도 초기 상태에서 시작한다.

구현 A는 add 때 무조건 앞에 붙인 목록을 쓰고, 추상 함수 AF_A는 목록에 등장하는 서로 다른 정수의 집합이다. A의 size는 목록 길이가 아니라 서로 다른 값의 수를 센다. 구현 B는 중복 없는 정렬 목록을 쓰며 AF_B도 그 값의 집합이다. 두 표현이 다르더라도 AF_A(a)=AF_B(b)이면 공개 논리 값이 같다. 이 관계는 단순히 목록 길이가 같은 관계가 아니다.

empty에서 2, 5, 2를 추가하면 A의 내부는 [2,5,2], B는 [2,5]일 수 있다. size는 둘 다 2이고 contains(2)는 참이다. A가 size를 length로 바꾸면 타입은 여전히 맞아도 결과 3으로 계약을 위반한다. 반대로 공개 enumerate가 추가되면 반환 순서·중복 정책을 새로 정해야 한다. 옛 관찰 관계만으로 넓어진 인터페이스의 교체 가능성을 확정하지 않는다.

먼저 확인할 개념
  • 타입과 행동 계약

    같은 함수 타입만으로 size의 뜻을 보장하지 못한다.

  • 공개 연산의 시퀀스

    표현을 읽는 대신 연산 결과를 비교한다.

사용자가 알아야 할 약속

모듈은 관련 타입과 연산을 하나의 경계로 묶는다. 시그니처는 그 경계 밖에서 쓸 이름과 타입을 정한다. 사용자는 제공된 연산으로 값을 만들고 관찰하며 내부 자료구조에 직접 의존하지 않는다.

타입 목록만으로 결과의 뜻은 정해지지 않는다. pop이 가장 최근 값을 꺼내는지 가장 오래된 값을 꺼내는지, 빈 경우 어떤 예외인지도 계약에 적어야 한다. 타입 검사는 그 의미를 자동 증명하지 않는다.

같은 약속의 다른 구현

추상 자료형은 배열이나 연결 목록 이름으로 정의하기보다 관찰 가능한 연산의 뜻으로 정의한다. 스택의 empty·push·pop을 지키면 내부를 바꾸어도 사용자의 논리적 결과를 유지할 수 있다.

교체가 가능한 범위는 계약에 달려 있다. 시간 복잡도·반환 객체의 공유·예외 종류를 보장했다면 그것도 지켜야 한다. 결과값만 같아도 모든 계약이 같다고 단정하지 않는다.

SML의 숨겨진 타입

아래는 정수용 불변 스택의 자체 작성 SML 조각이다. :>는 외부에서 STACK의 type stack만 보이게 하는 opaque ascription이다. 내부 int list 정의와 추가 helper가 외부 연산으로 자동 공개되지는 않는다.

외부에서 IntStack.empty를 만들고 push와 pop을 적용할 수 있다. 그러나 추상 stack을 목록처럼 직접 분해할 수는 없다. 이 예제는 push가 기존 스택을 바꾸지 않고 새 스택을 반환하는 계약이다. 컴파일은 수행하지 않았다.

signature STACK = sig
  type stack
  exception Empty
  val empty : stack
  val push : int * stack -> stack
  val pop : stack -> int * stack
end
structure IntStack :> STACK = struct
  type stack = int list
  exception Empty
  val empty = []
  fun push (x,s) = x::s
  fun pop [] = raise Empty
    | pop (x::xs) = (x,xs)
end

행은 각 구현의 독립 empty에서 같은 입력 시퀀스를 적용한다. 내부 열은 구현자 설명이며 외부 호출자가 목록 분해를 사용할 수 있다는 뜻이 아니다. 마지막 행은 목록 길이가 아니라 AF의 원소 수로 size를 정한다.

중간 과정을 따라가는 예제

s0=empty, s1=push(4,s0), s2=push(9,s1), pop(s2) 후 얻은 남은 스택을 다시 pop한다. 불변 스택 계약으로 값을 추적하라.

  1. s0의 논리 내용은 빈 순서다.

  2. s1의 위쪽 값은 4, s2의 위쪽 값은 9이고 그 아래 4다.

  3. 첫 pop은 (9,s1에 해당하는 스택), 다음 pop은 (4,빈 스택)이다.

  4. 기존 s0·s1·s2는 각 연산으로 바뀌지 않는다.

꺼낸 값 순서는 9,4다. 내부 목록을 관찰하지 않아도 계약만으로 결정한다.

조건을 바꾸어 비교하기

중복 표현과 관찰 관계

위 네 행에서 A의 size를 length로 바꾼 변형을 원래 A/B와 비교하라.

  1. 세 번째 추가 전까지 size 0,1,2는 모두 일치한다.

  2. 마지막 A 목록 길이는 3이지만 서로 다른 값은 2와 5 두 개다.

변형은 마지막 공개 size가 3이고 계약 결과는 2다. 처음 세 관찰의 일치만으로 변형을 승인할 수 없다.

비교할 점

타입 불일치가 아닌 행동 계약 위반이다.

같은 크기와 같은 집합의 차이

A=[2,5,2], B=[2,7]은 둘 다 size 2다. 공개 관찰 하나로 구별하라.

  1. contains(5,A)는 true다.

  2. contains(5,B)는 false다. AF의 두 집합이 다르다.

size만 같은 관계는 표현 대응 관계로 충분하지 않다.

비교할 점

관찰 하나를 통과하는 것과 모든 계약 관찰의 일치를 구별한다.

종이와 본문으로 직접 해보기

pop(empty)의 행동을 적지 않은 같은 타입 시그니처 두 구현이 서로 교체 가능하다고 확정할 수 있을까?

힌트 보기

타입 모양과 빈 입력의 의미를 나누어 보자.

풀이 보기

확정할 수 없다. 빈 입력을 허용할지, Empty 예외를 던질지 등의 계약이 필요하다. 본문 STACK 구현은 Empty로 명시한다.

오해와 반례

타입 시그니처가 같으면 프로그램의 의미도 모두 같다.

같은 pop 타입으로 FIFO 구현과 LIFO 구현을 만들 수 있지만 스택 계약은 후자다. 타입과 별도로 값·예외·상태 변화를 검토해야 한다.

연습 1 · 값과 상태 예측

s1=add(2,empty), s2=add(5,s1), s3=add(2,s2)에서 size(s1), size(s3), contains(5,s1)을 예측하라.

힌트 1

add는 기존 s를 바꾸지 않는다.

힌트 2

새 값 s3과 이전 값 s1을 각각 관찰한다.

풀이와 답 확인

  1. s1의 AF는 {2}, s3의 AF는 {2,5}다.

결과는 1, 2, false다.

흔한 오답에서 다시 생각하기

s1도 나중에 5를 추가했으니 contains는 true다.

불변 반환 계약에서는 새 s2가 만들어지고 s1의 논리 값은 유지된다.

연습 2 · 오류 찾아 고치기

A의 size=length 변형을 검사한 테스트는 2와 5를 한 번씩만 추가했다. 결함을 드러내는 가장 짧은 입력을 설계하라.

힌트 1

중복 없는 입력에서는 길이가 집합 크기와 같다.

힌트 2

동일 값 두 번을 추가한다.

풀이와 답 확인

  1. empty에 2를 두 번 추가한다. A 목록은 [2,2]다.

계약 size는 1인데 변형은 2다.

흔한 오답에서 다시 생각하기

정렬하지 않았으므로 size가 틀렸다.

순서가 아니라 중복을 세는 방법이 오류다. 정렬해도 length는 2다.

연습 3 · 직접 만들어 보기

두 구현을 교체하기 위한 대응 관계와 한 add의 보존 의무를 적어라.

힌트 1

관계는 AF의 동일성으로 정의한다.

힌트 2

같은 x를 넣은 뒤에도 관계를 유지해야 한다.

풀이와 답 확인

  1. R(a,b)는 AF_A(a)=AF_B(b)다.

  2. 각 empty가 ∅를 나타내고, add 뒤 두 AF가 모두 기존 집합∪{x}가 되어야 한다. contains와 size는 그 AF에 맞아야 한다.

초기 대응·연산 후 대응·공개 관찰 일치를 따로 논증한다. 이는 실제 구현 실행 증거가 아니다.

흔한 오답에서 다시 생각하기

R을 내부 길이 동일성으로 정의한다.

허용된 A의 중복 때문에 길이는 달라도 같은 집합일 수 있다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

enumerate : set→int list를 공개하고 A가 [2,5,2], B가 [2,5]를 그대로 반환한다. 옛 관계만으로 교체 가능한가?

힌트 1

새 관찰에 순서와 중복이 생긴다.

힌트 2

기존 집합의 AF는 이 두 정책을 말하지 않는다.

풀이와 답 확인

  1. 새 계약을 서로 다른 원소를 오름차순으로 반환한다고 정하면 A의 직접 반환은 위반이다.

  2. 순서를 지정하지 않더라도 중복 허용 여부와 리스트 관찰의 의미를 정해야 한다.

새 관찰까지 만족하는지 다시 논증해야 한다.

흔한 오답에서 다시 생각하기

추상 타입만 유지하면 공개 연산 추가는 아무 영향이 없다.

관찰이 넓어져 옛 구현 차이가 외부에 드러날 수 있다.

준비 개념과 학습 목표

준비 개념

  • 참조 두 개가 같은 가변 객체를 가리킬 수 있다.

  • 불변식은 허용 상태를 정하는 조건이다.

학습 목표

  • 정보 은닉이 보호하는 설계 결정을 설명한다.

  • 가변 참조 노출과 표현 불변식 위반을 추적한다.

목록만 복사한 장부의 합계가 왜 갑자기 틀릴까?

자체 가변 장부는 레코드마다 정수 amount를 담고 rows 목록과 캐시 total을 갖는다. 표현 불변식은 모든 amount가 0 이상이고 total이 현재 rows의 amount 합과 같다는 것이다. 초기 두 레코드는 r1.amount=4, r2.amount=6이고 total=10이다. 이름 r1/r2는 객체 정체성이다. 실제 언어 코드·정수 overflow·동시 접근·할당 실패는 이 모형에서 제외한다.

생성자가 외부 목록만 새로 복사하면 목록 객체는 달라져도 그 안의 r1/r2는 공유한다. 외부에서 r1.amount=9로 쓰면 내부 합은 15인데 캐시 total은 10이다. 값이 모두 비음수여도 관계 불변식이 깨진다. getter가 목록을 복사해도 같은 레코드를 담으면 똑같은 노출이 생긴다. 필드 private와 바깥 목록 복사는 도달 가능한 가변 객체 전체를 보호한다는 증거가 아니다.

이 작은 레코드는 amount라는 정수 필드 하나만 갖는다. 입력에서 새 레코드로 복사하고 출력에서는 불변 정수 쌍 (4,6)을 반환하면 외부 요소 변경 경로를 끊을 수 있다. 객체가 더 깊은 참조를 담으면 이 복사 수준을 다시 논증해야 한다. 출력이 snapshot인지 live view인지도 계약이다. snapshot을 받은 뒤 모듈이 내부 값 하나를 8로 바꾸면 예전 snapshot은 (4,6)이며 최신 total은 14다.

먼저 확인할 개념
  • 표현 노출과 복사 깊이

    목록과 내부 요소의 별칭을 각각 추적한다.

  • 교체 가능한 관찰의 범위

    snapshot/live view도 공개 의미에 포함한다.

변경되는 결정을 경계 안으로

정보 은닉은 사용자가 알아야 할 계약과 구현자가 바꿀 수 있는 결정을 나누는 원칙이다. 배열 길이·정렬 방식·캐시 같은 선택을 공개 계약에 불필요하게 묶지 않으면 구현 변경의 영향을 줄일 수 있다.

소스 코드를 비밀로 보관한다는 뜻은 아니다. 오픈소스여도 사용자는 내부 구조가 아니라 공개 연산에 의존할 수 있다. 프로그램 설계상의 은닉과 공격자에 대한 비밀 보호는 다른 목표다.

불변식과 추상 의미

정수 점수 상자의 허용 상태를 0≤score≤100으로 정할 수 있다. 생성과 수정 연산은 이 조건을 확립하고 보존해야 한다. 외부에서 내부 저장소를 임의로 바꾸게 두면 검사 경로를 우회할 수 있다.

추상 함수는 허용된 내부 표현이 어떤 논리 값인지 설명한다. 예컨대 내부 배열 [80]을 점수 80으로 읽는다. 조건과 해석을 문서에 적으면 잘못된 저장 상태와 잘못된 관찰 결과를 구별하기 쉽다.

private를 넘는 별칭

상자가 외부 배열을 그대로 저장하거나 getter가 내부 배열 참조를 그대로 반환하면 외부 코드와 별칭을 공유한다. 필드 접근은 private여도 배열 요소는 외부 참조로 바뀔 수 있다.

이 예제의 한 칸 int 배열은 입력과 출력에서 새 배열로 복사하면 요소 공유를 끊을 수 있다. 일반 객체가 중첩되어 있으면 얕은 복사만으로 내부 가변 요소의 별칭까지 사라지지는 않는다. 복사 비용과 허용 공유 계약도 고려한다.

모듈 조합과 테스트

각 부품이 맞게 움직여도 연결한 기계가 틀릴 수 있는 이유는 무엇일까?

준비 개념과 학습 목표

준비 개념

  • 선행조건과 후행조건을 구별한다.

  • 공개 연산을 조합해 사용 결과를 관찰한다.

학습 목표

  • 모듈 사이 값과 실패 계약의 호환성을 확인한다.

  • 구현에 의존하지 않는 연산 시퀀스 테스트를 설계한다.

단위를 바꾼 뒤 반올림하면 경계 판정도 보존될까?

자체 센서 A는 Result 형태로 Ok(c) 또는 Err를 반환한다. c는 정확한 유리수 섭씨이며 정상 범위는 −10≤c≤40이다. 소비자 B는 정확한 화씨 입력 −100≤f≤150을 받고 f≥68이면 warm, 아니면 cold를 반환한다. 어댑터는 Ok에서 f=9c/5+32로 변환하고 Err에서는 B를 호출하지 않고 Err를 전파한다. 실제 센서·부동소수점·반올림·네트워크 실행은 제외한다.

정상 후행 범위는 14≤f≤104라 B의 입력 범위에 포함된다. 타입이 숫자라는 사실만으로 이 포함 관계를 알 수는 없다. 또 변환 뒤 정수 올림을 추가하면 정상 범위 포함은 그대로인데 warm 경계가 달라질 수 있다. c=199/10에서는 f=3391/50=67.82라 정확 경로는 cold지만 올림 68은 warm이다. 계약이 정확 판정을 요구할 때 양자화 어댑터는 대체 구현이 아니다.

스텁이 언제나 Ok(20)만 내면 정확 어댑터·그릇된 올림·Err를 0°C로 바꾸는 오류가 모두 같은 warm을 보일 수 있다. 정상 값, 경계 바로 아래, 범위 끝점, 실패 경로를 공개 계약에서 각각 나눈다. 기대 결과를 시험 대상의 같은 변환 함수를 다시 호출해 만들면 동일 결함이 숨을 수 있다. 독립 수식과 요구의 부등식으로 기대값을 유도해야 한다.

    타입 이외의 값 조건도 경계 계약에 남긴다.

앞의 결과가 뒤의 입력이 된다

모듈 A의 결과를 모듈 B에 전달하려면 타입뿐 아니라 B가 요구하는 값 조건을 만족해야 한다. 숫자 double 하나라도 Celsius와 Fahrenheit의 뜻이 다르면 연결 결과가 틀린다. 단위와 실패 처리도 인터페이스의 일부다.

A의 후행조건이 B의 선행조건을 충족하는지 확인한다. A가 실패할 수 있다면 B에 임의의 기본값을 보내기보다 실패 계약을 처리하는 흐름을 설계한다. 연결 책임을 한 모듈 탓으로 단정하지 않는다.

연산들을 함께 시험하기

추상 자료형의 공개 생성·수정·관찰 연산을 조합하면 계약을 검토할 수 있다. 불변 스택은 empty→push→pop의 관찰값을 비교하고 빈 실패를 따로 검사한다. 내부 배열 슬롯이나 목록 길이를 읽는 검사는 표현 교체에 불필요하게 묶일 수 있다.

블랙박스 계약 테스트와 내부 불변식 검사는 목적이 다르다. 구현자는 내부 허용 상태를 확인할 수 있지만 외부 사용 계약의 결과를 확인하는 테스트도 필요하다. 몇 사례를 통과했다고 모든 입력의 정당성을 증명한 것은 아니다.

대체 모듈과 실제 연결

빠른 가짜 모듈은 정해진 결과나 실패를 제공해 호출자의 선택을 검토하기 좋다. 그러나 가짜가 실제 시간·형식·오류를 정확히 재현한다고 보장하지 않는다. 같은 계약 테스트를 실제 구현에도 적용하고 연결 자체를 별도로 확인한다.

의존성을 명시적으로 전달하면 시험용 모듈을 바꾸기 쉽다. 스텁의 성공만으로 실제 파일·네트워크 연결까지 완료됐다고 보고하지 않는다. 본문의 연결은 종이 모형이며 실제 통합 실행을 하지 않았다.

실패와 cold를 혼동

마지막 행은 올림 자체의 필연적 행동이 아니라 별도 실패 대체 변형이다. 두 결함을 구별한다. 화씨는 정확 유리수이며 정수 올림의 67.82→68이 경계 분기를 바꾼다.

중간 과정을 따라가는 예제

A는 20°C를 반환한다. B는 Fahrenheit 입력이 68 이상이면 warm을 반환한다. 변환 모듈 F=9C/5+32를 넣은 경우와 수치 20을 직접 전달한 경우를 비교하라.

  1. A의 숫자는 섭씨 단위다. B의 선행 의미는 화씨다.

  2. 변환하면 9×20/5+32=68°F다.

  3. 68≥68이므로 변환 경로의 결과는 warm이다.

  4. 변환 없이 20°F로 해석하면 20<68로 cold다. 타입만 같아도 의미가 어긋난다.

정상 연결은 68°F와 warm이다. 잘못된 연결은 cold를 만들어 낸다.
