행·열·PAX

같은 표를 어떤 순서로 놓느냐에 따라 읽는 양이 달라질까?

준비 개념과 학습 목표

준비 개념

  • 표의 행과 열

  • 페이지는 묶어서 옮기는 단위

  • 논리적 표와 물리 저장

학습 목표

  • NSM·DSM·PAX 배치를 그림으로 구분한다

  • 한 행 조회와 한 열 스캔의 비용을 조건별로 비교한다

한 열만 읽는 일과 한 학생의 기록을 읽는 일에 같은 배치가 좋을까요?

표를 화면에 행과 열로 그리는 방식과 저장 장치에 놓는 방식은 다릅니다. 행 저장은 같은 행의 값을 가까이 놓고, 열 저장은 같은 열의 값을 가까이 놓습니다. 한 행의 모든 값을 찾는 요청인지 여러 행의 한 열을 읽는 요청인지에 따라 필요한 페이지 수가 달라집니다.

PAX는 페이지 또는 정해진 행 그룹 안에서 열별 조각을 두는 배치입니다. 이 단원에서는 한 페이지가 네 행을 담는 작은 모형으로 고정합니다. 페이지 안의 열 값이 붙어 있다는 사실을 전체 표의 그 열이 한 페이지에 모였다는 뜻으로 읽으면 안 됩니다.

표의 의미와 배치

논리적 표는 행마다 여러 속성이 있는 관계다. 그 속성을 저장 장치에 반드시 행 순서로 놓아야 한다는 뜻은 아니다. 행 저장 NSM은 한 tuple의 값들을 가까이 두며, 열 저장 DSM은 같은 속성의 값들을 모아 둔다.

한 학생의 모든 값을 읽는 요청과 모든 학생의 한 점수만 합하는 요청은 필요한 범위가 다르다. 어느 배치가 좋은지 판단할 때 읽는 열 수·행 수·갱신 빈도를 먼저 적는다. SQL 표의 모양만 보고 저장 구조를 단정하지 않는다.

열끼리 묶되 같은 행을 잃지 않기

열 저장에서는 같은 행의 값들을 다시 연결할 위치나 ID 규칙이 필요하다. 각 열을 독립적으로 정렬하고 원래 대응을 버리면 점수와 학생이 뒤섞인다. 동일 순서의 위치나 명시적 식별자를 유지해야 한다.

PAX는 행을 그룹으로 나누고 각 그룹 내부에서 열별 조각을 둔다. 원래 페이지 내부의 PAX와 더 큰 row group 형식의 일반화를 구별한다. 전체 표의 한 열을 단일 연속 영역에 둔 DSM과 페이지마다 작은 열 조각을 둔 모형은 읽는 페이지 수가 같지 않을 수 있다.

페이지와 필요한 값의 바이트

한 열의 값만 실제 계산에 필요해도 장치가 전체 페이지를 읽으면 다른 열의 바이트도 함께 이동한다. PAX가 그룹 내부의 연속 접근을 돕는 것과 디스크 페이지를 한 개만 읽는 것은 다른 주장이다.

아래 예는 페이지 48 byte·각 값 4 byte·header/slot/NULL/정렬/압축/인덱스 없음이라는 작은 종이 모형이다. 실제 DB 페이지 크기나 저장량을 나타내지 않는다. 캐시가 빈 상태에서 필요한 물리 페이지를 한 번씩 읽는다고 정한다.

20행·4열 A/B/C/D의 각 값은 4바이트입니다. 페이지는 64바이트이며 헤더·슬롯·NULL·압축·정렬 메타데이터는 제외합니다.

캐시는 비어 있고 주소는 이미 알고 있으며 필요한 물리 페이지를 한 번씩 읽습니다. DSM의 각 열은 자기 전용 페이지에서 시작하므로 마지막 페이지의 남은 공간을 다른 열과 공유하지 않습니다.

중간 과정을 따라가는 예제

12 행·3 열 A/B/C, 각 값 4 byte를 페이지 48 byte에 저장한다. NSM은 행 단위, DSM은 열별 전용 페이지, PAX는 페이지마다 4 행의 A조각/B조각/C조각을 둔다. A 전체 스캔과 주소를 이미 아는 한 행의3 열 조회에서 페이지 수를 구하라.

  1. 한 행은3×4=12 byte여서 NSM 페이지당4 행, 전체 3 페이지다. A 전체 스캔은3 페이지144 byte를 옮긴다.

  2. DSM에서 A열 12×4=48 byte는1 페이지다. A 전체 스캔1 페이지 48 byte, 세 열 전체 저장은3 페이지다.

  3. PAX 각 페이지에는 A값 4개16 byte와 B/C 각16 byte가 있다. A 전체 스캔은3 페이지지만 계산에 쓰는 A바이트는48이다.

  4. 한 행의 주소를 안다면 NSM/PAX는 해당 1 페이지, DSM은 각 열에서1개씩 총3 페이지다. 페이지 단위 읽기·열별 전용 배치·빈 캐시 조건을 사용했다.

A 스캔 NSM 3/DSM 1/PAX 3 페이지, 한 행3 열 조회 NSM1/DSM 3/PAX 1 페이지다. PAX의 값 접근 이점과 페이지 수 감소를 같은 수로 말하지 않는다.

조건을 바꾸어 비교하기

논리적 바이트와 페이지 이동량을 분리합니다

표의 모형에서 A 열 전체의 논리적 값 바이트와 각 배치가 실제 옮기는 페이지 바이트를 구하세요. 두 열 A/B 전체 읽기도 비교하세요.

  1. 한 행은 4×4=16바이트이므로 NSM과 PAX는 페이지당 네 행, 전체 다섯 페이지입니다.

  2. A의 논리적 값은 20×4=80바이트입니다. DSM은 64바이트 페이지 두 개가 필요하며 마지막 페이지에서 16바이트만 값입니다.

  3. A 읽기에서 NSM·PAX는 다섯 페이지 320바이트, DSM은 두 페이지 128바이트를 옮깁니다. A/B 두 열이면 DSM은 네 페이지입니다.

A의 필요한 값은 모두 80바이트로 같지만 옮기는 양은 NSM 320, DSM 128, PAX 320바이트입니다. A/B 두 열은 NSM 5, DSM 4, PAX 5페이지입니다.

비교할 점

PAX에서 A의 계산 대상이 80바이트라는 사실은 디스크에서 80바이트만 읽었다는 뜻이 아닙니다. 이 모형의 이동 단위는 전체 페이지입니다.

질의 비중을 바꾸면 배치 선택이 달라집니다

요청의 80%는 A/B 두 열 전체 읽기이고 20%는 주소를 아는 한 행의 네 열 읽기입니다. 표의 비용으로 요청당 평균 페이지 수를 구하세요. 이어 전체 읽기 비중을 60%로 바꿔 보세요.

  1. 80% 혼합에서 NSM과 PAX는 0.8×5+0.2×1=4.2페이지입니다. DSM은 0.8×4+0.2×4=4페이지입니다.

  2. 60% 혼합에서 NSM과 PAX는 0.6×5+0.4×1=3.4페이지입니다. DSM은 0.6×4+0.4×4=4페이지입니다.

  3. 주소 탐색·CPU·갱신 비용을 제외한 같은 모형의 요청 비중만 바꿨습니다.

80% 혼합에서는 DSM의 평균 4가 NSM·PAX의 4.2보다 작습니다. 60% 혼합에서는 NSM·PAX의 3.4가 DSM의 4보다 작습니다.

비교할 점

배치 이름만으로 언제나 더 빠른 것을 고를 수 없습니다. 이 비교도 페이지 수 비교이며 실제 시간의 측정 결과가 아닙니다.

종이와 본문으로 직접 해보기

A와 B 두 열 전체를 읽을 때 페이지 수를 구하고, DSM의 A만 정렬해 같은 위치의 B와 연결하는 것이 왜 잘못인지 두 행 (A,B)=(2,10),(1,20)으로 보여라.

힌트 보기

같은 페이지는 한 번만 읽는다. 원래 행 대응을 먼저 적는다.

풀이 보기

NSM 3/PAX 3/DSM 2 페이지다. A만[1,2]로 정렬하고 B=[10,20]을 그대로 두면 (1,10),(2,20)이 되어 원래 (1,20),(2,10)과 다르다. 공동 순열이나 행 ID 대응을 유지해야 한다.

오해와 반례

PAX는 전체 표의 모든 동일 열을 한 페이지에 모으므로 언제나 DSM과 페이지 수가 같다.

PAX의 열 조각은 그룹 내부에 있다. 자체3 페이지 모형의 A 스캔은3 페이지이며 DSM의1 페이지와 다르다. 실제 그룹·페이지·압축·cache 조건에 따라 비용은 달라진다.

연습 1 · 값과 상태 예측

같은 조건에서 행 수를 21로 늘립니다. 각 배치의 A 전체 읽기와 한 행의 네 열 읽기 페이지 수를 구하세요.

힌트 1

한 행은 여전히 16바이트입니다.

힌트 2

나머지 한 행 때문에 필요한 페이지를 올림합니다.

풀이와 답 확인

  1. NSM·PAX는 21행을 네 행씩 담으므로 여섯 페이지입니다.

  2. DSM의 한 열은 84바이트로 두 페이지이며 네 열은 전용 배치에서 여덟 페이지입니다.

  3. 주소를 아는 한 행은 NSM·PAX 한 페이지, DSM 네 페이지입니다.

A 전체는 NSM 6, DSM 2, PAX 6페이지이며 한 행 전체는 1, 4, 1페이지입니다.

흔한 오답에서 다시 생각하기

한 행 추가는 작으므로 NSM도 다섯 페이지입니다.

다섯 페이지는 20행을 담습니다. 남은 한 행이 다음 페이지를 필요로 한다는 경계를 놓쳤습니다.

연습 2 · 오류 찾아 고치기

행 ID 0,1,2에 A=[30,10,20], B=[3,1,2]가 대응합니다. A만 정렬한 [10,20,30]을 B의 같은 위치와 연결합니다. 잘못된 결과와 올바른 B 순서를 구하세요.

힌트 1

A 정렬 뒤 원래 행 ID의 순서를 적습니다.

힌트 2

다른 열은 그 원래 ID로 찾아야 합니다.

풀이와 답 확인

  1. A 정렬의 원래 ID 순서는 1,2,0입니다.

  2. B를 그대로 붙이면 (10,3),(20,1),(30,2)로 잘못 연결됩니다.

  3. 같은 ID를 따르면 B는 1,2,3입니다.

정렬 뒤 올바른 행은 (10,1),(20,2),(30,3)입니다. 공동 순열이나 ID 대응을 유지해야 합니다.

흔한 오답에서 다시 생각하기

두 열 모두 길이가 세 개이므로 위치로 붙이면 맞습니다.

길이가 같은 것은 행의 대응이 같은 것을 보장하지 않습니다. 독립 정렬은 대응을 바꿉니다.

연습 3 · 직접 만들어 보기

별도 네 PAX 페이지의 A값 범위는 P0=[2,9], P1=[10,19], P2=[20,29], P3=[30,49]입니다. 각 범위는 현재 데이터를 안전하게 포함하고 미리 메모리에 있습니다. A≥25 질의에서 버릴 페이지와 읽어 확인할 페이지를 구성하세요. P2의 실제 값이 [20,21,24,29]이면 반환할 A값도 구하세요. 모든 A값은 NULL이 아닌 정수라고 정합니다.

힌트 1

최댓값이 25보다 작은 페이지만 안전하게 버릴 수 있습니다.

힌트 2

범위가 겹친다는 사실만으로 모든 행이 조건을 만족하지는 않습니다.

풀이와 답 확인

  1. P0와 P1은 최댓값이 25보다 작아서 버립니다.

  2. P2와 P3은 후보로 남겨 실제 값을 검사합니다.

  3. P2에서는 29만 조건을 만족합니다. P3는 주어진 최솟값 30 이상이므로 해당 페이지의 A값은 모두 조건에 맞지만 다른 출력 열의 값을 읽는 일은 남습니다.

P0·P1을 버리고 P2·P3를 읽습니다. P2에서 반환할 A값은 29입니다. 범위로 페이지를 거르는 일과 행별 조건 검사를 구별합니다.

흔한 오답에서 다시 생각하기

P2의 최대 29가 조건을 만족하므로 P2의 모든 값을 반환합니다.

최댓값 하나가 맞아도 나머지 행이 맞는 것은 아닙니다. 페이지 후보 선택 뒤 실제 행을 검사해야 합니다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

P1의 실제 A값 하나가 19에서 60으로 바뀌었는데 최대값 메타데이터는 19로 남았습니다. A≥50 질의가 이 메타데이터로 P1을 버렸습니다. 오류와 보수적인 수정 방법을 설명하세요.

힌트 1

변경 뒤에도 메타데이터가 현재 값을 포함하는지 봅니다.

힌트 2

정확한 범위를 모를 때 버리지 않는 선택이 가능합니다.

풀이와 답 확인

  1. 실제 60이 저장된 최대 19 밖에 있으므로 해당 통계는 안전한 경계가 아닙니다.

  2. 질의가 페이지를 버리면 조건을 만족하는 60을 놓칩니다.

  3. 현재 버전에 맞는 범위를 갱신해 최대를 최소 60으로 잡거나, 통계가 유효해질 때까지 해당 페이지를 버리지 않습니다.

P1을 읽어 검사해야 합니다. 안전한 통계는 현재 질의가 보는 데이터와 일치하거나 그 값을 보수적으로 포함해야 합니다.

통계는 참고 정보이므로 오래되어도 결과는 같습니다.

통계를 페이지 제외의 근거로 쓰면 정확성 조건이 됩니다. 너무 좁은 오래된 범위는 정답 행을 없애 버립니다.

준비 개념과 학습 목표

준비 개념

  • 비트와 바이트

  • 코드와 원래 값의 대응

학습 목표

  • 사전·bit packing·RLE 비용을 계산한다

짧은 코드는 숫자 크기와 원래 값의 순서를 모두 보존할까요?

사전은 원래 값과 코드를 연결하는 표입니다. 같은 코드가 같은 값을 뜻하려면 같은 사전을 기준으로 읽어야 합니다. 코드가 짧다는 사실은 코드 번호의 순서가 원래 값의 순서와 같다는 뜻이 아닙니다.

비트 포장은 고정폭 코드들을 빈틈 없이 넣는 모형입니다. 아래 계산은 사전·코드·헤더를 명시해 더하되 실제 Parquet의 바이트 형식은 구현하지 않습니다. 실제 형식에는 비트 폭, 반복 구간, 페이지와 NULL 상태 등 별도의 정보가 있습니다.

먼저 확인할 개념
  • 가변길이·압축·삭제

    코드 외에 사전·삭제 상태의 저장 비용도 필요한 이유를 연결합니다.

  • 압축과 교집합

    압축 상태의 연산과 원래 의미를 복원하는 조건을 이어서 봅니다.

되돌릴 수 있는 코드

사전 인코딩은 원래 값과 짧은 코드를 일대일로 대응시켜 코드와 사전을 함께 보관한다. 같은 값이 반복되면 이득이 생길 수 있으나 사전·코드·위치·NULL 메타데이터까지 비용에 넣어야 한다. 이 단원의 압축은 원래 값을 정확히 복원하는 무손실이다.

서로 다른 값 3개를 0/1/2로 표시하면 고정폭2 bit면 충분하다. 코드가 4개가 되면 여전히2 bit,5개면 3 bit가 필요하다. 값 하나뿐인 특수 경우에는 개수와 값이 다른 곳에 있으면0 bit/항목 모형도 가능하지만 모든 형식이 그런 표현을 쓰는 것은 아니다.

반복의 구조와 비용

RLE는 연속 반복을 값과 횟수의 쌍 등으로 표시한다. 같은 값의 총 등장 횟수가 많아도 서로 떨어져 있으면 run이 많아져 이득이 작다. 본 예는 시작 위치를 별도 저장하지 않고 앞 run의 길이를 누적하는 쌍 모형이다.

사전 코드 번호가 원래 문자열·숫자의 순서와 같다는 보장은 없다. 동등 비교는 해당 값을 같은 사전에서 찾은 코드와 비교할 수 있으나 범위 비교는 순서 보존 여부를 확인한다. 다른 사전의 같은 번호를 바로 같다고 비교하면 안 된다.

늦게 복원하고 행을 연결하기

먼저 조건 열에서 해당 코드나 값으로 필터를 계산하고 살아남은 행 위치를 기록할 수 있다. 그 뒤 결과에 필요한 다른 열의 그 위치만 읽거나 복원한다. 필요 없는 행의 모든 값을 미리 펼치는 것을 줄이는 방식이 late materialization의 한 흐름이다.

항상 코드를 그대로 모든 연산에 넣을 수 있는 것은 아니다. 합계나 범위 연산에 원래 수치의 의미가 필요할 수 있다. 행 위치 정렬·결과 합치기·선택률이 높은 요청의 비용도 남으며 일반 압축 블록 전체를 풀어야 하는 형식은 같은 이점을 주지 않을 수 있다.

아홉 값·세 종류의 사전 모형입니다. 원래 값과 사전 항목은 각각 4바이트, 헤더는 2바이트입니다.

중간 과정을 따라가는 예제

12개 값이 세 종류이며 원래 값과 사전의 각 값은4 byte다. 코드 0/1/2를2 bit로 빈틈 없이 포장하고 다른 메타데이터는 제외한다. 저장량을 구하라. 별도 6 값 [7,7,7,2,2,7]을 값 4 byte+횟수 4 byte의 RLE쌍으로 바꾸어라.

  1. 원래 12값은12×4=48 byte다. 사전은3×4=12 byte다.

  2. 코드 12×2=24 bit=3 byte다. 사전과 합쳐15 byte다.

  3. RLE는 (7,3),(2,2),(7,1) 세 쌍이다. 쌍당8 byte여서24 byte다.

  4. 6 값 원래 크기도6×4=24 byte여서 이 RLE 모형에서는 줄지 않는다.12값이 모두7이면 한 쌍 8 byte 대 원래 48 byte다.

사전+포장 코드 15 byte 대 원래 48 byte다. 여섯 값 RLE는24 byte로 동일하고 긴 단일 run은 이득이 있다. 예제 overhead 제외를 실제 파일 압축률로 일반화하지 않는다.

조건을 바꾸어 비교하기

값 종류가 늘 때 비트 폭의 경계를 넘습니다

표의 아홉 값에서 종류가 세 개, 네 개, 다섯 개일 때 각각의 전체 저장량을 구하세요. 동일한 2바이트 헤더를 유지합니다.

  1. 세 종류는 두 비트 코드이며 18비트는 3바이트입니다. 전체는 12+3+2=17바이트입니다.

  2. 네 종류도 두 비트면 충분합니다. 전체는 16+3+2=21바이트입니다.

  3. 다섯 종류는 세 비트가 필요해 27비트를 4바이트에 담습니다. 전체는 20+4+2=26바이트입니다.

전체 크기는 각각 17·21·26바이트입니다. 네 종류에서 다섯 종류로 늘 때 사전 항목뿐 아니라 코드 폭도 늘어납니다.

비교할 점

값 종류만 늘고 행 수가 같다고 코드 영역의 크기가 항상 같은 것은 아닙니다. 두 비트가 표현할 네 가지 경계를 확인해야 합니다.

선택한 행만 금액을 복원합니다

색 사전은 0=red, 1=blue, 2=green이고 색 코드가 [0,2,1,0,2,0]입니다. 같은 행의 금액은 [5,8,13,21,34,55]입니다. red 행의 금액 합을 구하세요. 각 금액은 행별로 독립 복원할 수 있다고 정합니다.

  1. red는 이 사전에서 코드 0입니다. 살아남는 원래 행 위치는 0,3,5입니다.

  2. 해당 금액만 복원하면 5,21,55입니다. 합은 81입니다.

  3. 색 코드의 번호 비교로 문자열 범위를 비교하지 않습니다. 예를 들어 blue<red는 문자열 순서에서 참이지만 코드 1<0은 거짓입니다.

red 행 금액 합은 81이며 이 모형에서는 금액 복원 항목이 여섯 개에서 세 개로 줄었습니다. 실제 복원 시간이나 페이지 읽기 수의 동일한 절반 감소를 뜻하지는 않습니다.

비교할 점

필터가 남긴 위치를 버리면 다른 열에서 해당 행을 정확히 찾을 수 없습니다. 또한 금액 연산에는 원래 금액의 의미가 필요합니다.

종이와 본문으로 직접 해보기

조건열 코드 [0,1,0,2], 사전 0=red/1=blue/2=green, 금액열[10,20,30,40]이다. red 행만 금액 합을 내고 코드 순서로 blue<red를 비교해도 되는지 설명하라.

연습 1 · 값과 상태 예측

부호 없는 실제 값 [31,32]를 기준값 없이 같은 고정 비트 폭으로 저장합니다. 필요한 최소 비트 폭과 두 값을 빈틈 없이 담은 바이트 수를 구하세요. 별도 기준값 31을 4바이트 저장하고 차이 [0,1]만 포장하면 총 몇 바이트인가요?

힌트 1

다섯 비트는 0부터 31까지 표현합니다.

힌트 2

기준값도 전체 저장량에 더해야 합니다.

풀이와 답 확인

  1. 32를 포함하므로 직접 포장은 여섯 비트씩입니다. 두 값은 12비트로 2바이트입니다.

  2. 차이는 한 비트씩이라 2비트를 1바이트에 담습니다.

  3. 기준값 4바이트를 더하면 5바이트입니다.

직접 포장은 6비트 폭·2바이트이고 기준값 방식은 5바이트입니다. 이 짧은 사례에서는 기준값 방식이 더 큽니다. 기타 헤더는 두 모형 모두 제외했습니다.

흔한 오답에서 다시 생각하기

최대값 32는 다섯 비트면 되고 기준값은 무료입니다.

다섯 비트의 최대는 31입니다. 기준값 저장 비용도 빠뜨리면 작은 표의 손익을 잘못 판단합니다.

힌트 1

코드를 해석하는 사전의 정체를 확인합니다.

힌트 2

공통 사전을 만들지 않은 경우 원래 값을 비교할 수 있습니다.

풀이와 답 확인

  2. 원래 값 기준으로 둘은 다릅니다.

  3. 같은 사전으로 다시 인코딩하거나 사전 간 의미 대응을 만든 뒤 비교합니다. 단순 코드 번호 비교를 하지 않습니다.

두 값은 다릅니다. 동일 코드 비교는 코드가 같은 의미를 갖는 공통 사전 조건에서만 사용할 수 있습니다.

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

열 [NULL,0,NULL,0]에서 NULL은 값 영역에 저장하지 않습니다. 유효 여부를 한 비트씩 포장하고 유효 값 두 개는 각각 한 바이트로 저장합니다. 기타 헤더는 없습니다. 두 영역과 전체 크기, 비교 값이 0인 행 위치를 구성하세요.

힌트 1

힌트 2

값 0과 NULL은 다른 상태입니다.

풀이와 답 확인

  1. 유효 비트는 [0,1,0,1]이며 네 비트를 한 바이트에 담습니다.

  2. 값 영역은 [0,0]으로 2바이트입니다.

  3. 전체는 3바이트입니다. 유효한 원래 위치 1과 3이 값 0인 행입니다.

유효 정보 1바이트와 값 2바이트를 합해 3바이트이며 값 0인 행은 위치 1·3입니다. 이 비트맵은 자체 형식이며 Parquet의 실제 definition level 인코딩과 같다고 주장하지 않습니다.

NULL도 0으로 읽으면 네 행 모두 값 0입니다.

NULL 여부를 버리면 원래 의미를 복원할 수 없습니다. 값 영역에서 빠진 항목과 숫자 0을 구별할 메타데이터가 필요합니다.

반으로 줄인 저장량이 처리 시간도 반으로 만들까요?

저장량과 읽기 수와 처리 시간은 서로 다른 지표입니다. 압축은 읽는 양을 줄여도 복원 CPU 비용을 늘릴 수 있습니다. 필요한 값만 늦게 복원할 수 있는지, 이미 캐시에 있는지에 따라서도 손익이 바뀝니다.

작은 값 갱신도 페이지나 압축 블록의 읽기와 재쓰기를 유발할 수 있습니다. 아래는 로그·인덱스·복제·장치 증폭을 제외한 정책 모형입니다. 총 이동량에 읽기를 포함했는지, 쓰기만 셌는지 분자와 분모를 분명히 밝힙니다.

먼저 확인할 개념
  • 캐시·직접 I/O·동시성

    캐시 경로에 따라 읽기 비용이 달라지는 조건을 연결합니다.

  • 교체정책·prefetch

    직렬 합과 읽기·계산의 겹침을 서로 다른 일정으로 구별합니다.

작업량과 시간은 다른 단위

저장량 byte, 읽는 페이지 수, CPU 계산 시간, 실제 응답 시간은 서로 다른 지표다. 압축으로 옮기는 양을 줄여도 복원에 계산이 필요하다. 반대로 압축 상태에서 필터를 처리하면 복원하지 않는 이득도 생길 수 있다.

전체 작업이 메모리에 이미 있거나 다른 연산이 지배적이면 디스크 읽기 절감의 효과가 작을 수 있다. 응답 시간은 cache·병렬 겹침·요청 크기·동시 사용자·스케줄러에 달린다. 아래는 겹침 없이 I/O 후 CPU가 실행되는 자체 직렬 모형이다.

작은 갱신이 만지는 범위

한 값 4 byte를 바꾸는 논리 요청이 물리 장치에 항상4 byte만 쓰는 것은 아니다. 페이지·압축 블록·로그·인덱스·복제 규칙이 더 큰 범위를 다루게 할 수 있다. 열 배치도 단일 값 갱신을 항상 가장 싸게 만드는 구조는 아니다.

아래 쓰기 예는 차가운48 byte 압축 블록을 한 번 읽고 한 번 다시 쓰는 정책을 일부러 정한다. 로그·인덱스·복제·파일시스템·장치 증폭은 제외한다. 실제 DBMS는 patch·delta·캐시·batch 등의 다른 정책을 쓸 수 있어 이 수를 일반적 측정값으로 쓰지 않는다.

비교할 조건을 동일하게

저장 형식 비교는 같은 데이터·질의·결과·정확성 조건에서 해야 한다. 필터 선택률이 낮으면 늦은 복원이 유리할 수 있고 거의 모든 행을 다시 연결하면 비용이 늘 수 있다. 읽기 중심/갱신 중심에 따라 설계 목표가 다르다.

측정하려면 warm/cold cache, 읽은 바이트, 처리 행 수, CPU와 wall time, 압축/복원 및 갱신 비용을 구별해 기록한다. 평균만으로 최악 지연을 주장하지 않는다. 이 원고는 실제 데이터베이스나 벤치마크 프로그램을 실행하지 않았다.

중간 과정을 따라가는 예제

직렬 종이 scan에서 비압축은3 페이지×2 ms I/O와 CPU 1 ms, 압축은1 페이지×2 ms와 복원 포함 CPU 3 ms다. 시간을 비교하라. 별도 정책에서 논리 4 byte 갱신마다 압축블록 48 byte를 읽고48 byte를 쓴다면 옮긴 총량과 비율은?

  1. 비압축 I/O6 ms에 CPU 1 ms를 더해7 ms다.

  2. 압축 I/O2 ms에 CPU 3 ms를 더해5 ms다. 시간비는7/5=1.4이며 I/O 페이지의3배 감소와 다르다.

  3. 블록 갱신은 읽기 48+쓰기 48=96 byte를 옮긴다. 논리 4 byte 대비 총 이동비는96/4=24다.

  4. 물리 쓰기만의 비율은48/4=12다. 읽기까지 포함한24와 구별한다. 이는 지정한 정책이며 실제 로그/장치 비용은 포함하지 않는다.

scan 시간7/5 ms, 이 모형의 속도비1.4다. 블록 총 이동96 byte·논리 대비24, 쓰기만48 byte·비율12다. 지표의 분모를 명시한다.

조건을 바꾸어 비교하기

차가운 읽기와 따뜻한 읽기를 섞습니다

표의 차가운 읽기 비중이 80%이고 따뜻한 읽기가 20%일 때 평균 시간을 구하세요. 이어 두 형식의 평균이 같아지는 차가운 비중을 구하세요.

  1. 비압축 평균은 0.8×10+0.2×2=8.4ms입니다.

  2. 압축 평균은 0.8×9+0.2×5=8.2ms입니다.

  3. 차가운 비중을 p라고 하면 비압축은 2+8p, 압축은 5+4p입니다. 두 값이 같으려면 4p=3이므로 p=0.75입니다.

차가운 비중 80%에서 압축은 평균 8.2ms로 비압축 8.4ms보다 0.2ms 짧습니다. 경계는 75%입니다. 그보다 작으면 이 조건에서는 비압축이 유리합니다.

비교할 점

차가운 경우 10ms와 9ms만 비교해 모든 요청에서 압축이 빠르다고 결론내릴 수 없습니다. 따뜻한 경로의 복원 비용도 가중해야 합니다.

같은 블록의 갱신을 묶습니다

빈 캐시에서 논리적 4바이트 값을 바꿀 때마다 해당 64바이트 블록을 한 번 읽고 한 번 쓰며 다음 요청에는 보관하지 않습니다. 같은 블록의 두 값 변경을 각각 처리한 경우와 한 번에 묶어 처리한 경우를 비교하세요. 두 변경의 논리적 총량은 8바이트입니다.

  1. 각각 처리하면 읽기 128바이트와 쓰기 128바이트로 총 256바이트입니다.

  2. 한 번에 묶으면 한 블록 읽기 64바이트와 쓰기 64바이트로 총 128바이트입니다.

  3. 논리 8바이트에 대한 총 이동 비율은 32와 16이며 쓰기만의 비율은 16과 8입니다.

따로 처리하면 총 256바이트·쓰기 128바이트이고 묶으면 총 128바이트·쓰기 64바이트입니다. 같은 블록·지정 캐시 정책이라는 조건에서 묶기의 이득이 생깁니다.

비교할 점

서로 다른 블록의 변경까지 한 블록 읽기와 쓰기로 줄일 수는 없습니다. 로그·장치 비용을 제외한 비율을 전체 시스템 증폭률로 발표해서도 안 됩니다.

풀이와 답 확인

  1. 비압축 평균은 0.5×10+0.5×2=6ms입니다.

  2. 압축 평균은 0.5×9+0.5×5=7ms입니다.

  3. 차가운 비중이 경계 아래이므로 비압축 쪽이 작습니다.

비압축 6ms, 압축 7ms이며 이 모형에서는 비압축이 평균 1ms 빠릅니다.

흔한 오답에서 다시 생각하기

압축은 페이지 수가 절반이니 평균도 3ms입니다.

CPU와 캐시 상태를 빠뜨렸습니다. 페이지 수 감소를 전체 시간에 그대로 곱할 수 없습니다.

연습 2 · 오류 찾아 고치기

비압축 경로는 차가운 캐시에서 10ms, 압축 경로는 따뜻한 캐시에서 5ms를 비교해 압축 덕분에 두 배 빨라졌다고 발표합니다. 비교의 문제와 같은 조건의 수치를 구하세요.

힌트 1

형식과 캐시 상태가 동시에 바뀌었습니다.

힌트 2

같은 캐시 상태끼리 표의 값을 비교합니다.

풀이와 답 확인

  1. 차가운 조건끼리는 비압축 10ms와 압축 9ms입니다.

  2. 따뜻한 조건끼리는 비압축 2ms와 압축 5ms입니다.

  3. 10과 5의 차이는 형식 효과와 캐시 효과가 섞여 있어 압축만의 효과로 분리할 수 없습니다.

압축만으로 두 배 빨라졌다는 결론은 이 비교에서 나오지 않습니다. 같은 결과·질의·캐시 조건을 맞춰 다시 비교해야 합니다.

흔한 오답에서 다시 생각하기

결과가 같으면 캐시 상태는 비교 조건에 넣지 않아도 됩니다.

같은 결과를 낸다는 것은 정확성 조건입니다. 형식의 성능 차이를 설명하려면 다른 비용 조건도 맞춰야 합니다.

연습 3 · 직접 만들어 보기

서로 다른 두 64바이트 블록에서 각각 4바이트 값을 하나 바꿉니다. 두 변경을 한 요청으로 묶어도 각 블록을 한 번 읽고 한 번 쓴다고 정합니다. 논리 총량 대비 총 이동과 쓰기 비율을 구하세요.

힌트 1

블록 두 개의 읽기와 쓰기를 따로 셉니다.

힌트 2

분모는 두 값 합계인 8바이트입니다.

풀이와 답 확인

  1. 읽기는 2×64=128바이트이고 쓰기도 128바이트입니다.

  2. 총 이동은 256바이트입니다.

  3. 총 이동 비율은 256/8=32이고 쓰기 비율은 128/8=16입니다.

총 이동 256바이트·비율 32, 쓰기 128바이트·비율 16입니다. 묶어도 블록 수가 줄지 않아 앞의 같은 블록 사례와 다릅니다.

흔한 오답에서 다시 생각하기

요청이 하나이므로 반드시 읽기 64·쓰기 64입니다.

요청의 개수와 건드리는 블록의 개수는 다릅니다. 두 블록을 처리하는 정책을 적용해야 합니다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

압축 읽기 한 페이지의 I/O는 2ms이고 그 페이지 CPU는 2.5ms입니다. 페이지 두 개를 읽기 담당 하나와 계산 담당 하나가 겹쳐 처리할 수 있고 버퍼는 충분합니다. 각 구간과 종료 시각을 구하고 표의 직렬 9ms와 비교하세요.

힌트 1

각 계산은 자기 페이지 읽기가 끝난 뒤 시작합니다.

힌트 2

전체 I/O와 CPU의 최댓값만 취하면 시작 준비 시간을 빠뜨릴 수 있습니다.

풀이와 답 확인

  1. 읽기는 [0,2), [2,4)입니다.

  2. 첫 계산은 [2,4.5), 둘째 계산은 [4.5,7)입니다.

  3. 직렬 합 4+5=9ms보다 이 일정은 2ms 짧습니다.

이 별도 파이프라인 모형의 종료는 7ms입니다. max(4,5)=5ms는 첫 페이지 준비와 마지막 계산의 경계를 빠뜨린 값입니다. 실제 겹침을 측정한 결과는 아닙니다.

흔한 오답에서 다시 생각하기

I/O 4ms와 CPU 5ms가 겹치면 반드시 5ms에 끝납니다.

처음에는 계산할 페이지가 없습니다. 각 페이지의 준비 시각을 지키는 일정으로 확인해야 합니다.

내 말로 설명하기

평균 시간이 작으면 모든 요청도 더 빠른가요?

설명 기준 확인

아닙니다. 차가운·따뜻한 경로 중 어느 쪽이 늘어났는지와 각 요청의 지연을 따로 봐야 합니다. 평균 하나로 모든 요청의 개선을 보장할 수 없습니다.

총 이동 비율 32와 쓰기 비율 16은 서로 모순인가요?

설명 기준 확인

아닙니다. 총 이동은 읽기와 쓰기를 함께 세고 쓰기 비율은 쓰기만 셉니다. 같은 논리 8바이트를 분모로 삼아도 분자가 다릅니다.

한 단계 더

CPU 6 ms인 압축 scan에서 I/O와 CPU가 완벽히 겹친다는 별도 이상모형을 만든다면 max(2,6)=6 ms가 된다. 실제 겹침 가능성을 측정하지 않은 상태에서 직렬8과 이상적6 중 하나를 실제 성능으로 보고하지 않는다.
