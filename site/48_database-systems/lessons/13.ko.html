소단원 13.1

WAL·LSN·체크포인트

저장 버튼 뒤에도 자료 페이지가 디스크에 없을 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 메모리와 영속 저장

  • 트랜잭션 commit

  • 로그 순서

학습 목표

  • WAL의 로그 선행 조건과 commit 조건을 구별한다.

  • pageLSN과 영속 로그 경계로 페이지 기록 가능성을 판정한다.

  • 체크포인트와 전체 백업의 역할을 구별한다.

같은 순간에 P는 저장할 수 있고 Q는 저장할 수 없을까요?

로그 번호는 증가하는 자체 정수 LSN입니다. 영속 로그는 중간이 비지 않은 연속 구간이고 flushedLSN은 그 끝입니다. 메모리 페이지 P의 pageLSN은 20, Q는 40이며 로그 영속 경계는 30입니다. 두 페이지의 로그 선행 조건을 따로 검사해야 합니다.

이 모형은 온전한 페이지와 로그, 정확한 저장 완료를 전제합니다. 동기 commit 기록의 LSN이 50이면 성공 응답 전 로그 50까지 영속화합니다. 페이지 저장 허용, commit 성공 허용, 응답 도착을 서로 다른 사건으로 기록합니다. PostgreSQL의 제품별 체크포인트와 자체 fuzzy 체크포인트 모형도 구분합니다.

먼저 확인할 개념
  • pin·dirty·eviction

    페이지 교체 전에 로그 선행 조건을 검사하는 이유를 연결합니다.

  • 직렬가능성·복구가능성

    commit과 다른 거래에 공개된 효과의 복구 조건을 구별합니다.

로그를 먼저 남기는 이유

메모리의 자료 페이지는 프로그램 종료 때 사라질 수 있다. 변경을 복구할 수 있는 로그가 먼저 영속 저장되어야 그 변경을 담은 자료 페이지를 저장할 수 있다는 순서가 WAL이다. 메모리 로그 버퍼에 글을 적는 것과 장애 뒤 남을 영속 저장 완료는 다르다.

STEAL은 아직 commit하지 않은 변경 페이지도 저장할 수 있는 정책이고 NO-FORCE는 commit 때 모든 자료 페이지를 즉시 저장하도록 강제하지 않는 정책이다. 두 정책을 함께 지원하는 전형적 ARIES 설계에서는 미완료 효과의 undo와 완료 효과의 redo가 필요하다. 모든 DB가 같은 복구 알고리즘을 쓰지는 않는다.

LSN은 기록의 순서를 연결한다

LSN은 로그 위치·순서를 식별하는 표지다. 이 단원은 작은 증가 정수로 표시하며 실제 제품은 WAL 바이트 위치 등 다른 표현을 쓴다. pageLSN은 그 페이지에 적용된 마지막 로그 표지, flushedLSN은 이 종이 모형에서 연속 영속화된 로그의 끝이다.

pageLSN≤flushedLSN이면 해당 페이지 변경의 로그가 영속화되어 있다는 선행 조건을 만족한다. 이 부등식만으로 모든 저장 장치의 원자 쓰기·오류 복구를 증명하지는 않는다. 동기 commit 계약에서는 commit 기록까지 로그를 영속화한 뒤 성공을 알리고 자료 페이지는 이후 기록해도 된다. 비동기 commit 계약은 성공 시점의 보장이 다르다.

체크포인트는 복구 출발점을 관리한다

체크포인트는 복구에 필요한 상태와 로그 출발점을 관리해 다시 조사할 범위를 줄인다. 중간 상태를 기록하며 실행을 계속하는 fuzzy checkpoint도 있어 그 이름만으로 모든 트랜잭션 완료나 모든 자료 페이지 최신화를 가정하지 않는다. ARIES에서는 활성 트랜잭션·더티 페이지 등의 정보가 중요하다.

PostgreSQL의 체크포인트와 redo 시작점은 그 제품의 계약으로 읽는다. 체크포인트가 있다는 이유로 로그를 임의 삭제하지 않는다. 백업·복제·아카이브 등의 보존 요구가 따로 남을 수 있고, 저장 장치 전체 손실에는 별도 백업과 복구 자료가 필요하다.

필요한 LSN 이하의 기록이 모두 영속화되어야 합니다. P의 조건이 만족됐다고 Q나 commit 조건도 만족한 것은 아닙니다. 이 표는 로그 선행 조건만 판단하며 저장 장치 전체 안전성을 증명하지 않습니다.

중간 과정을 따라가는 예제

자체 한 페이지 P의 값은 10이다. 로그 10은 T1이 P를 10→15로 바꾼 기록이고 메모리 pageLSN=10이다. 로그 20은 T1 commit이다. 현재 연속 영속 로그는 10까지다. P 기록과 동기 commit 성공 통지는 각각 가능한가?

  1. P의 pageLSN 10≤flushedLSN 10이므로 로그 선행 조건은 만족한다. T1이 아직 commit 기록을 영속화하지 않아도 STEAL 정책은 이 페이지 저장을 허용할 수 있다.

  2. 동기 commit 성공은 commit 로그 20까지 영속화되어야 하므로 현재 경계 10으로는 알리지 않는다.

  3. 로그를 20까지 영속화하면 동기 commit 성공 조건을 만족한다. 자료 P가 아직 디스크에서 10이어도 저장된 변경 로그로 15를 redo할 수 있다는 설계다.

페이지 기록의 WAL 조건과 commit 성공 통지 조건은 각각 10과 20이라는 다른 경계다. 자료 페이지 최신화가 commit의 필수 동작인 것은 아니다.

조건을 바꾸어 비교하기

경계를 한 번 더 옮깁니다

로그를 40까지 영속화했습니다. P 저장, Q 저장, commit LSN 50의 성공 응답을 다시 판정하세요.

  1. P는 20≤40이므로 선행 조건을 만족합니다.

  2. Q는 40≤40이므로 이제 선행 조건을 만족합니다.

  3. commit 기록 50은 경계 40보다 뒤이므로 성공 응답은 아직 허용되지 않습니다.

두 페이지의 선행 조건은 만족하지만 동기 commit 성공 응답 조건은 남아 있습니다.

비교할 점

페이지의 마지막 변경과 commit 기록의 번호를 같은 것으로 가정하지 않습니다.

세 성공 응답을 한 번에 기다립니다

별도 자체 저장 모형에서 commit LSN 20, 40, 60의 요청 도착 시각은 각각 1 ms, 2 ms, 3 ms입니다. 한 번의 그룹 flush가 시각 4 ms에 로그 60까지 영속화합니다. 그때 각 응답을 알리며 통신 지연은 없습니다. 요청별 지연을 구하세요.

  1. 로그 60까지 연속 영속화하면 세 commit 기록이 모두 포함됩니다.

  2. 첫 요청의 지연은 4−1=3 ms이고 둘째는 4−2=2 ms입니다.

  3. 셋째 지연은 4−3=1 ms이며 평균은 (3+2+1)/3=2 ms입니다.

요청별 지연은 순서대로 3 ms, 2 ms, 1 ms이며 평균은 2 ms입니다.

비교할 점

한 번의 flush가 여러 commit을 포함할 수 있다는 것과 모든 요청의 지연이 같다는 것은 다릅니다.

종이와 본문으로 직접 해보기

새 로그 30이 P를 15→18로 바꾸었고 메모리 pageLSN=30, flushedLSN=20이다. 페이지 기록 가능성을 판정하고 로그 30까지 영속화한 뒤 어떻게 달라지는지 설명하자.

힌트 보기

페이지에 포함된 변경 표지와 영속 로그 끝을 비교한다.

풀이 보기

처음에는 30>20이라 P를 저장하면 안 된다. 로그 30까지 영속화한 뒤 30≤30으로 선행 조건을 만족한다. 이것은 새 트랜잭션의 commit 완료 여부와는 별도다.

오해와 반례

체크포인트를 한 번 만들면 이전 로그는 모두 삭제해도 된다.

복구 출발점 외 백업·복제·아카이브·활성 상태의 보존 요구를 확인한다. 실제 제품의 관리 절차 없이 로그를 지우지 않는다.

연습 1 · 값과 상태 예측

처음 경계 30에서 다른 변경 로그 60이 P에 적용되어 메모리 pageLSN이 60이 됐습니다. Q의 pageLSN은 40입니다. 경계를 50까지 영속화한 뒤 두 페이지 저장 조건과 commit 50의 응답 조건을 판정하세요.

힌트 1

P의 이전 pageLSN 20을 재사용하지 않습니다.

힌트 2

세 요구를 각각 경계 50과 비교합니다.

풀이와 답 확인

  1. P는 60>50이라 아직 저장하면 안 됩니다.

  2. Q는 40≤50이므로 선행 조건을 만족합니다.

  3. commit 50은 영속 경계에 포함됩니다.

P의 저장 선행 조건만 불만족이며 Q 저장과 commit 50의 성공 응답 조건은 만족합니다.

흔한 오답에서 다시 생각하기

commit이 됐으니 모든 더티 페이지를 지금 저장할 수 있다.

commit 조건과 나중 변경을 포함하는 페이지의 WAL 조건을 따로 검사합니다.

연습 2 · 오류 찾아 고치기

메모리 로그 버퍼에는 LSN 70까지 있지만 실제 영속 경계는 50입니다. pageLSN 60인 P를 저장할 수 있다고 판단한 문장을 고치세요.

힌트 1

버퍼 작성과 영속 완료를 구별합니다.

힌트 2

장애 뒤 남는 경계는 50입니다.

풀이와 답 확인

  1. 판정 기준을 메모리 끝 70에서 영속 경계 50으로 바꿉니다.

  2. 60>50이므로 먼저 로그 60까지의 영속화를 완료해야 합니다.

현재는 P를 저장할 수 없습니다. 로그 60까지 영속화한 뒤에 선행 조건을 다시 검사합니다.

흔한 오답에서 다시 생각하기

로그 문자열이 버퍼에 있으면 WAL 조건을 만족한다.

전원 손실로 사라질 수 있는 메모리 기록을 영속 기록으로 세지 않습니다.

연습 3 · 직접 만들어 보기

자체 fuzzy 체크포인트는 LSN 60에서 시작하여 90에서 끝났습니다. 더티 페이지 표에는 P의 recLSN 20, Q의 recLSN 40이 있습니다. 이 모형의 후보 redo 탐색 시작은 두 recLSN의 최솟값으로 정합니다. 시작점과 60부터만 읽겠다는 안을 비교하세요.

힌트 1

체크포인트 시작과 첫 미저장 변경을 구별합니다.

힌트 2

여기서는 min(20,40)을 사용합니다.

풀이와 답 확인

  1. 후보 탐색 시작은 LSN 20입니다.

  2. 60부터만 읽으면 아직 더티 상태인 페이지의 더 이른 변경 기록을 놓칠 수 있습니다.

  3. 실제 ARIES에는 표 재구성 및 페이지별 redo 검사가 추가됩니다.

자체 후보 시작점은 20이며 체크포인트 시작 60으로 임의 대체하지 않습니다.

흔한 오답에서 다시 생각하기

fuzzy 체크포인트가 끝났으니 이전 모든 페이지 변경이 저장됐다.

실행을 계속하는 fuzzy 모형은 그런 전면 최신화 조건을 두지 않았습니다. PostgreSQL 체크포인트의 제품 계약과도 구분합니다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

앞 모형의 redo 보존 요구는 LSN 20부터이고 별도 백업 복구 보존 요구는 10부터입니다. 보존 요구만 보아 버릴 수 없는 전체 구간의 시작을 구하세요. 실제 파일·세그먼트 삭제 허용은 판단하지 않습니다.

힌트 1

두 용도 중 더 이른 기록을 요구하는 쪽을 확인합니다.

힌트 2

물리 세그먼트 경계와 다른 보존 계약은 별도입니다.

풀이와 답 확인

  1. 두 요구의 합집합은 LSN 10부터입니다.

  2. redo에만 필요 없는 10부터 20 미만도 백업 복구 때문에 필요합니다.

이 지정 모형의 보존 시작은 LSN 10입니다. 실제 로그 삭제를 승인한 결과는 아닙니다.

흔한 오답에서 다시 생각하기

현재 redo 시작 20 이전은 언제나 쓸모없다.

백업·복제 등 다른 소비자가 요구하는 구간을 함께 확인해야 합니다.

준비 개념과 학습 목표

준비 개념

학습 목표

  • 완료와 미완료 변경을 한 페이지 예제로 추적한다.

  • CLR과 undoNext가 재장애에 필요한 이유를 설명한다.

Q를 되돌리는 도중 다시 꺼지면 P는 어디서부터 되돌릴까요?

두 페이지 자체 로그를 사용합니다. T1은 P를 10에서 15로 바꾼 뒤 commit합니다. 이후 T2가 P를 15에서 19로, Q를 7에서 9로 바꾸지만 commit하지 못합니다. T2의 두 변경은 prevLSN으로 연결되며 다른 거래의 후속 변경은 없습니다.

복구는 필요한 이력을 redo한 뒤 미완료 T2의 변경을 역순으로 undo합니다. Q의 보상 기록 CLR 50은 Q를 7로 복원하는 정보와 다음 undo 대상 30을 담습니다. CLR 자체는 undo하지 않습니다. ABORT·END 등 전체 관리 레코드와 DPT 처리를 생략한 값 추적 모형이며 실제 ARIES 전체 구현이라고 부르지 않습니다.

먼저 확인할 개념
  • WAL·LSN·체크포인트

    CLR을 포함한 페이지 저장에도 로그 선행 조건을 적용합니다.

  • 직렬가능성·복구가능성

    완료된 앞 거래의 값과 미완료 뒤 거래의 효과를 분리합니다.

분석하고 기록된 이력을 다시 적용한다

ARIES 복구는 analysis로 복구에 필요한 트랜잭션과 페이지 상태를 파악하고 redo로 기록된 이력을 재구성한 뒤 undo로 미완료 트랜잭션 효과를 제거하는 흐름이다. redo를 완료 트랜잭션만 다시 실행하는 절차라고 단순화하면 history 반복과 다르다.

이미 페이지에 적용된 로그를 또 더하지 않도록 pageLSN 같은 상태를 활용한다. 실제 ARIES는 더티 페이지 표와 recLSN 등 추가 조건으로 필요한 redo를 정한다. 여기서는 로그가 모두 관련 있는 한 페이지이며 초기점이 알려진 자체 모형만 계산한다. SQL 문장을 그대로 다시 제출하는 작업과도 다르다.

미완료 효과는 역순으로 제거한다

이 단원은 같은 자료를 바꾼 두 트랜잭션이 적절한 순서로 실행되어 commit된 앞선 값이 뒤 미완료 트랜잭션의 이전 값이 되는 상황이다. 미완료 변경의 before 값으로 되돌리고 완료된 변경은 남긴다. 다른 트랜잭션의 후속 변경이 섞인 임의 이력을 무조건 before 값으로 덮는 알고리즘을 일반화하지 않는다.

한 트랜잭션의 이전 로그를 연결하는 prevLSN을 따라 되돌릴 대상을 찾을 수 있다. redo와 undo는 자료 변경을 복구하는 작업이고 사용자에게 응답이 도착했는지는 별도 사건이다. durable commit이 있어도 성공 응답이 유실되면 사용자는 결과를 알 수 없을 수 있다.

되돌린 동작도 기록한다

undo가 수행한 보상을 CLR이라는 로그로 기록하고 다음 되돌릴 위치를 undoNext로 남긴다. CLR은 redo 가능한 보상이며 다시 undo하는 기록이 아니다. 복구 도중 다시 장애가 나도 보상 기록과 페이지 적용 상태를 이용해 이미 되돌린 동작을 구별한다.

이 원리는 무조건 한 번만 실행된다는 외부 효과 계약이 아니다. 로그 원자성·영속화 순서·페이지 복구 조건을 충족하는 DB 설계가 전제다. 실제 ARIES 구현과 검사 없는 종이 모형을 구별하고 로그가 없거나 손상된 경우의 복구 가능성을 여기서 보장하지 않는다.

중간 과정을 따라가는 예제

자체 로그는 10: T1, P 10→15, 20: T1 commit, 30: T2, P 15→19다. T2 commit은 없고 세 로그는 영속화되어 있다. 장애 시 디스크 P는 15/pageLSN 10이다. 모든 기록이 이 페이지에 관련된 모형에서 redo·undo를 추적하자.

  1. analysis는 T1 완료와 T2 미완료를 구별한다. 실제 전체 트랜잭션 표 처리를 축약한 자체 사례다.

  2. redo에서 로그 10은 디스크 pageLSN 10≥로그 LSN 10이라 이미 적용된 것으로 건너뛴다. 로그 30은 pageLSN 10보다 뒤여서 P 19/pageLSN 30으로 적용한다. 미완료 T2 기록도 이력 반복에 포함된다.

  3. undo는 T2 변경을 되돌려 P 15로 만들고 자체 CLR 40에 P 15로 복원·undoNext 없음을 기록한다. 이 CLR이 WAL 조건에 맞게 영속화되고 페이지에 적용된 뒤 해당 페이지의 pageLSN은 40이다.

최종 P 15다. redo 직후의 19와 undo 완료의 15를 구별하며 T1 완료 변경은 남는다.

조건을 바꾸어 비교하기

두 페이지의 redo와 역순 undo

표의 로그와 디스크에서 redo와 undo의 중간 값을 쓰세요. Q 보상은 CLR 50, P 보상은 CLR 60입니다. 각 CLR은 페이지 저장 전에 영속화합니다.

  1. P의 pageLSN 30은 로그 10과 30을 이미 적용한 상태이므로 두 UPDATE를 재적용하지 않습니다.

  2. Q의 pageLSN 0은 40보다 작으므로 redo 뒤 Q=9/pageLSN 40입니다.

  3. 먼저 Q의 변경 40을 undo하여 Q=7/pageLSN 50으로 만들고 CLR 50의 undoNext를 30으로 정합니다.

  4. 다음 P의 변경 30을 undo하여 P=15/pageLSN 60으로 만들고 CLR 60의 undoNext는 없습니다.

redo 뒤 값은 P=19, Q=9이며 undo 완료 뒤에는 P=15, Q=7입니다.

비교할 점

로그 40이 미완료 거래의 변경이라고 redo에서 제외하는 방식과 다릅니다.

보상 로그만 남고 보상 페이지는 아직 없습니다

CLR 50은 영속화됐지만 Q 보상 페이지를 저장하기 전에 다시 장애가 났습니다. 디스크는 P=19/pageLSN 30, Q=9/pageLSN 40입니다. CLR 50에는 Q를 7로 복원하고 undoNext=30이라는 정보가 있습니다. 다시 복구하세요.

  1. Q의 pageLSN 40<50이므로 CLR 50을 redo하여 Q=7/pageLSN 50으로 만듭니다.

  2. T2의 다음 undo 대상은 CLR 50의 undoNext 30입니다. UPDATE 40을 다시 undo하는 경로로 가지 않습니다.

  3. P의 변경 30을 보상하여 P=15로 만들고 새로운 CLR 60을 기록합니다.

재복구 최종 값은 P=15, Q=7입니다. 영속 CLR을 이용해 남은 undo 위치를 이어갑니다.

비교할 점

재장애가 있었다고 처음부터 모든 보상을 중복 수행하는 것으로 일반화하지 않습니다.

소단원 13.3

crash injection과 복구 검증

재시작이 성공했으면 모든 완료 자료가 복구되었다고 말할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 시험 기대와 관찰

  • 영속/휘발 상태

  • 복구 결과 비교

학습 목표

  • 장애 지점별 영속 증거와 기대 결과를 작성한다.

  • 페이지 값·완료 상태·재장애를 함께 검증한다.

  • 종이 예측과 실제 장애 시험을 구별한다.

성공 응답을 못 받으면 commit도 없었다고 판단해도 될까요?

앞 소단원의 두 페이지와 온전한 로그 계약을 그대로 사용해 복구 중 재장애 지점을 바꿉니다. 각 행은 서로 독립인 종이 예상입니다. 프로세스 생존만 확인하는 대신 완료 T1의 P=15와 미완료 T2 제거 뒤 Q=7을 함께 확인합니다.

영속 commit과 응답 도착은 별개입니다. 실제 시험을 수행하지 않은 표는 예상으로 남깁니다. 응답 유실 예제는 별도 업무 원장의 중복 요청 문제이며 WAL redo와 사용자 요청 재전송을 같은 연산으로 취급하지 않습니다.

먼저 확인할 개념
  • redo·undo·ARIES 개요

    재장애 시점별 CLR과 남은 undo 대상을 먼저 추적합니다.

  • 병렬 실행·취소

    요청 송신·응답 관찰·이미 완료된 결과를 구별합니다.

장애 지점을 사건 사이에 둔다

crash injection은 정해 둔 실행 지점에서 실패를 일으켜 복구 결과를 조사하는 시험 방법이다. 실제 DB 프로세스 종료·장치 장애·로그 손상은 서로 다른 실패이고, 현재 사용하는 운영 서비스에서 임의로 수행하는 활동이 아니다. 이 단원은 가상 로그와 페이지 사건표로만 접근한다.

시험 전에 초기 자료·로그 영속 경계·페이지 저장 상태·동기 commit 계약·완료 판정·기대 결과를 고정한다. 메모리 버퍼를 영속 로그로 착각하면 복구 예측이 달라진다. 실제 시험에서는 재현 가능한 별도 허가 환경과 원본 보존·복구 절차가 필요하다.

프로세스 생존과 데이터 조건을 나눈다

재시작됐다는 사실과 기대 값이 복구됐다는 사실은 다른 증거다. 완료 변경 유지·미완료 변경 제거·중복 redo 방지·복구 중 재장애·자료 간 제약을 따로 확인한다. 기본 예제 한 개의 성공은 모든 장애 유형을 포함하지 않는다.

이 종이 모형은 완전한 로그 레코드와 온전한 페이지를 전제하며 로그 손상·부분 페이지 쓰기·장치 동기화 실패는 제외한다. 실제 엔진은 별도의 보호와 조건을 가진다. 실행하지 않은 실패 주입은 계획 또는 예상 결과로 보고하고 실제 통과로 표시하지 않는다.

기록과 판정의 분모를 보존한다

계획 세 개·수행 두 개·통과 한 개라면 수행률은 2/3이고 수행 시험 통과율은 1/2다. 두 비율의 분모를 섞지 않는다. 기대 값이 틀린 시험은 실행 성공을 복구 성공으로 바꾸지 않고 원인을 조사한다.

보고에는 제품/설정 버전·대상·주입 지점·영속 로그와 페이지 증거·관찰·기대·미수행 범위·후속 조치를 담는다. 종이 사례의 개수는 실제 시스템 신뢰도를 측정한 결과가 아니다. 백업 복원이나 운영 안전성은 또 별도의 증거가 필요하다.

중간 과정을 따라가는 예제

초기 P 10인 자체 모형에서 T1 변경 로그 10은 10→15, commit 로그는 20이다. A는 로그 10만 영속·디스크 P 10, B는 로그 20까지 영속·디스크 P 10, C는 로그 20까지 영속·디스크 P 15/LSN 10에서 장애가 난다고 하자. A에는 commit 성공 통지가 없으며 모든 로그는 온전하다. 복구 최종 값은?

  1. A는 영속 commit이 없어 미완료다. 이력 redo로 15를 만들더라도 undo 뒤 10으로 돌아간다.

  2. B는 durable commit이 있고 페이지는 옛 10이므로 redo로 15를 복원한다.

  3. C는 이미 로그 10이 적용된 15라 그 변경 redo는 건너뛰고 최종 15를 유지한다. 15에 5를 또 더해 20을 만드는 것은 잘못된 중복 적용이다.

종이 예상은 A 10·B 15·C 15다. 실제 장애를 주입하거나 DB에서 관찰한 결과는 아니다.

조건을 바꾸어 비교하기

최종 값은 같아도 재시작 경로가 다릅니다

사례 A와 B의 처음 Q 보상 처리 경로를 비교하세요. 두 사례 모두 디스크 Q는 9/pageLSN 40입니다.

  1. A에는 영속 CLR이 없으므로 Q UPDATE 40을 undo하고 CLR을 새로 기록합니다.

  2. B에는 영속 CLR 50이 있으므로 이를 redo하여 Q를 7로 복원합니다.

  3. B의 다음 원래 undo 대상은 30이므로 Q UPDATE 40을 다시 보상하지 않습니다.

A는 UPDATE 40의 undo이고 B는 CLR 50의 redo입니다. 이후 둘 다 P를 15로 복원합니다.

비교할 점

최종 Q=7이라는 사실만으로 어떤 복구 경로를 탔는지 알 수는 없습니다.

응답 유실 뒤 같은 요청을 보냅니다

별도 업무 원장 초기 잔액은 100입니다. 요청 id=R7의 +20이 동기 commit됐지만 응답이 유실됩니다. 같은 R7을 다시 전송합니다. 중복 방지가 없는 처리와 요청 id 및 결과를 잔액과 같은 거래에 저장하는 중복 방지 계약을 비교하세요. 다른 요청은 없습니다.

  1. 첫 완료 거래 뒤 잔액은 120입니다. 응답 유실은 이 commit을 없애지 않습니다.

  2. 중복 방지가 없고 재전송을 새 업무로 처리하면 다시 +20하여 140이 됩니다.

  3. 중복 방지 계약은 이미 완료된 R7과 결과를 확인하여 추가 증가 없이 기존 결과 120을 반환합니다.

중복 방지가 없는 재실행은 잔액 140을 만들 수 있고 지정한 요청 id 계약은 잔액 120을 유지합니다.

비교할 점

이것은 업무 요청 중복 처리 조건이며 페이지 pageLSN의 중복 redo 방지와 같은 장치가 아닙니다.

풀이 보기
