소단원 6.1

latch crabbing·optimistic traversal

리프에 숫자를 하나 넣을 때 왜 조상 페이지를 잠시 잡고 있을까?

준비 개념과 학습 목표

준비 개념

  • B+tree는 내부 경계 키로 리프를 찾고 리프에 정렬 키를 저장한다.

  • latch는 짧은 구조 변경 보호,transaction lock은 논리 격리와 관련된 별도 책임이다.

학습 목표

  • 안전한 자식에서 조상 latch를 풀 수 있는 이유를 설명한다.

  • optimistic 실패와 pessimistic 재시작을 손으로 추적한다.

같은 빈자리를 두 작업이 동시에 봤다면 나중에 얻은 쓰기 보호 아래에서도 안전할까요?

작업 전에 관찰한 페이지와 수정할 때의 페이지는 다른 상태일 수 있습니다. 두 작업이 같은 빈자리를 보고도 첫 작업의 삽입 뒤에는 둘째 작업의 여유가 달라집니다. 수정 권한을 얻은 뒤 현재 상태를 다시 확인해야 합니다.

이 모형은 비루트 잎에 최소 두 키·최대 세 키를 둡니다. 삽입 안전은 새 키를 넣어도 넘치지 않는 조건이고 삭제 안전은 한 키를 지워도 부족하지 않은 조건입니다. 안전하다는 표시는 작업과 현재 상태에 따라 달라집니다. 정확한 첫 키를 부모에 늘 복사하는 정책 등 추가 갱신 책임이 있으면 점유율 조건만으로 전체 안전성을 판단하지 않습니다.

먼저 확인할 개념
  • 분할·병합·복구

    잎의 넘침과 부족이 부모 변경으로 이어지는 이유를 연결합니다.

  • 세마포어·조건변수·모니터

    관찰과 수정 사이에 다른 작업이 끼어들 수 있는 조건을 사용합니다.

부모에서 자식으로 건넌다

latch crabbing은 부모를 잡고 자식을 잡은 뒤 조건에 따라 부모를 놓는 과정이다. 읽기는 자식의 포인터/ 구조가 안전하게 확보된 후 부모를 놓는다. 수정은 자식이 split/merge/redistribution 없이 작업을 끝낼 수 있는지 확인한다.

여기서는 리프 최대 키 3, 비루트 최소 2라는 자체 모형을 쓴다. 새키 삽입은 현재 2개 이하면 안전, 삭제는 현재 3개일 때 안전하다. root의 별도 최소 규칙과 중복 키 갱신은 이 모형에서 제외한다. 실제 tree가 max/min을 정하는 방법과 다르므로 숫자만 일반화하지 않는다.

변경이 위로 올라갈 수 있다

리프가 가득 찬 경우 새 키 삽입은 4개가 되어 split 하고 새 자식 경계를 부모에 반영한다. 조상 변경이 가능하므로 필요한 조상 write latch를 보존하거나 재시작해야 한다. 빈 칸이 남는 리프라면 이 변경이 조상으로 전파되지 않는다.

안전 조건은 작업에 따라 다르다. 현재 2개 리프는 삽입 후 3으로 안전하지만 삭제 후 1로 불안전하다. safe라는 라벨을 페이지의 영구 속성처럼 저장해 어떤 작업에도 쓰면 틀린다.

낙관적 경로와 재확인

optimistic 방식은 split/merge가 드물다고 가정해 상위 경로를 shared latch 로 따라가고 리프 수정 시 조건을 확인한다. 리프가 불안전하면 현재 latch를 정리하고 write 경로로 처음부터 재시작하는 규약을 쓸 수 있다. CMU 노트의 개선 protocol이 이 구조다.

read →write 전환 동안 페이지가 변할 수 있으면 예전 관측을 그대로 신뢰하지 않고 안전한 전환 방법/ 재확인이 필요하다. optimistic이라는 말은 latch 없이 임의 포인터를 읽어도 된다는 뜻이 아니다. 아래 사례는 다른 writer가 없는 상태에서 safe 판정을 종이 추적한다.

중간 과정을 따라가는 예제

리프L[2,4]와 M[8,10,12],max3/min2다. L에 3을 삽입할 때와 M에 9를 삽입할 때 optimistic safe 여부를 판단하라. M은 불안전이면 재시작 후 정렬 4 키를 2개씩 split한다.

  1. L의 현재 키 수 2로 새 키 후[2,3,4]3개다. safe이므로 리프 수정으로 끝낸다.

  2. M의 현재 키 수 3으로 9 삽입 후 4개가 된다. unsafe다.

  3. optimistic 경로의 latch를 정리하고 조상 write 경로로 재시작한다.

  4. 자체 split 결과[8,9]/[10,12], 오른쪽 최소 10을 부모 분리 경계로 넣는다.

L은 safe, M은 unsafe·재시작/split/ 부모 경계 10 갱신이 필요하다.

조건을 바꾸어 비교하기

둘째 쓰기에서 안전 판정을 다시 합니다

비루트 잎 L=[11,22]에 A가 15를, B가 18을 넣으려 합니다. 두 작업은 처음 키 수 2를 관찰했습니다. A가 먼저 write latch를 얻어 삽입하고 풀었습니다. B가 그 뒤 write latch를 얻습니다.

  1. A가 보호된 상태에서 확인한 키 수는 2입니다. 15 삽입 뒤 [11,15,22]로 세 키가 됩니다.

  2. B는 예전 두 키라는 관찰을 폐기하고 현재 세 키를 봅니다. 18을 넣으면 네 개라 점유율 안전하지 않습니다.

  3. 이 낙관적 경로는 latch를 정리하고 필요한 조상 write 보호를 포함하는 경로로 재시작합니다. 다른 변경이 없으면 [11,15,18,22]를 둘씩 나눕니다.

최종 두 잎은 [11,15]와 [18,22]이며 새 부모 경계 사본은 18입니다. B는 예전 안전 판정으로 리프만 바꾸면 안 됩니다.

비교할 점

두 작업의 초기 관찰이 같아도 수정 시점의 실제 상태가 같지는 않습니다. write latch 획득 자체도 오래된 안전 판단을 새 판단으로 바꾸어 주지는 않습니다.

읽기 권한을 붙잡은 채 쓰기를 기다립니다

A와 B가 같은 잎의 read latch를 함께 잡았습니다. write latch는 다른 read 보유자가 없어야 얻습니다. 두 작업은 자기 read latch를 유지한 채 write 획득이 끝날 때까지 기다립니다. 별도 원자적 승격 기능은 없다고 정합니다.

  1. A의 write 획득은 B의 read 해제를 기다립니다.

  2. B의 write 획득은 A의 read 해제를 기다립니다.

  3. 둘 다 write 획득 전에는 read를 풀지 않으므로 서로 기다리는 순환이 생깁니다.

이 승격 방식은 교착할 수 있습니다. read를 놓고 보호된 write 경로로 재시도하며 페이지 위치·버전·점유율을 다시 확인하거나, 실제로 정의된 안전한 승격 규약이 필요합니다.

비교할 점

read latch를 write 이름으로 바꾸는 표기만으로 권한이 바뀌지는 않습니다. 보호를 놓는 전환에서는 그 사이의 다른 쓰기도 고려해야 합니다.

종이와 본문으로 직접 해보기

L[2,4]에서 2 삭제와 M[8,10,12]에서 8 삭제는 safe인가?

힌트 보기

오해와 반례

latch가 있으니 전체 transaction의 serializable 격리도 보장된다.

짧은 페이지 구조 보호가 끝나면 latch는 풀린다. 이후 다른 transaction의 논리 값/ 범위 삽입 관측을 제어하는 격리 protocol은 별도다.

연습 1 · 값과 상태 예측

비루트 잎 [20,30,40]에서 30을 삭제할 때와 [20,40]에서 20을 삭제할 때 점유율 안전 여부를 구하세요. 추가 부모 메타데이터 갱신은 없는 모형입니다.

힌트 1

삭제 후 두 키 이상인지 확인합니다.

힌트 2

삽입의 빈자리 조건을 삭제에 그대로 쓰지 않습니다.

풀이와 답 확인

  1. 세 키에서 30을 지우면 [20,40]으로 두 키가 남습니다.

  2. 두 키에서 20을 지우면 [40] 한 키만 남습니다.

첫 삭제는 점유율 안전하고 둘째 삭제는 부족 상태라 안전하지 않습니다. 다른 갱신 책임이 있는 실제 구현의 전체 안전성까지 증명한 것은 아닙니다.

실제로 수정할 페이지의 최신 키 수를 기준으로 합니다.

한 번 안전한 페이지는 이후 모든 작업에도 안전합니다.

안전성은 작업 종류와 수정 시점의 상태에 달립니다. 앞선 쓰기가 이미 빈자리를 사용했습니다.

연습 3 · 직접 만들어 보기

루트 R, 내부 I, 잎 L로 내려가 새 키를 넣는 기본 경로를 구성하세요. 각 자식의 write latch를 얻은 뒤 그 자식 이하의 삽입이 분할을 위로 전파하지 않는다고 확인되면 조상 latch를 놓는 규약입니다. 자식 latch를 얻기 전에 부모를 놓지 않습니다.

힌트 1

경로 확보와 안전 판단의 순서를 분리합니다.

힌트 2

마지막 잎이 안전하면 앞의 보호를 계속 들고 있을 필요가 없습니다.

풀이와 답 확인

  1. R을 잡고 I의 write latch를 얻습니다. I가 주어진 의미에서 안전하면 R을 놓습니다.

  2. I를 잡은 상태에서 L의 write latch를 얻습니다. L이 안전하면 남아 있는 조상 latch를 놓습니다.

  3. L의 보호 아래 최신 키와 점유율을 확인해 삽입하고 L을 놓습니다.

  4. 불안전한 자식에서는 필요한 조상 보호를 유지하고 구현의 분할 규약을 따릅니다.

부모 확보→자식 확보→해당 작업의 안전 확인→필요 없는 조상 해제 순서입니다. 포인터 수명과 안전 판정을 별도 보장 없이 건너뛰면 안 됩니다.

조상은 비용만 늘리므로 자식 포인터 숫자만 읽고 바로 놓습니다.

자식의 보호와 수명이 아직 확보되지 않은 틈에서 구조 변경이 일어날 수 있습니다. 정한 획득 순서를 지켜야 합니다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

A가 관찰한 잎 번호 7이 보호를 놓은 사이 삭제되고 다른 잎으로 재사용되었습니다. 다시 번호 7을 pin했으니 예전 경로와 키 수를 쓴다고 합니다. 재시작에 필요한 확인을 설명하세요.

힌트 1

같은 페이지 번호가 같은 논리적 잎을 뜻하는지 확인합니다.

힌트 2

숫자 하나보다 페이지의 현재 경로와 세대가 필요할 수 있습니다.

풀이와 답 확인

  1. 현재 루트·경계·유효 링크로 목표 키의 잎을 다시 찾습니다.

  2. 재사용을 구별하는 실제 수명 또는 세대 규약에 따라 페이지 정체를 확인합니다.

  3. 보호된 현재 페이지에서 키와 점유율을 다시 검사합니다.

옆 리프로 넘어가는 순간 분할/ 합병이 일어나면 누락과 교착을 어떻게 막을까?

준비 개념과 학습 목표

준비 개념

  • 리프의 다음 포인터는 정렬 순서로 스캔을 이어 준다.

  • 교착은 서로 상대가 잡은 자원을 기다려 아무도 진행하지 못하는 상태다.

학습 목표

  • 구조 안전과 snapshot 관측을 구별한다.

  • sibling no-wait 와 재시작의 중복 방지를 추적한다.

스캔이 재시도할 때 마지막 키 하나만 기억하면 충분할까요?

옆 잎으로 넘어갈 때 상대 작업이 필요한 latch를 잡고 있을 수 있습니다. 이 모형의 no-wait는 즉시 얻지 못하면 보유한 latch를 놓고 재시도하는 규칙입니다. 서로 붙잡고 기다리는 경로를 끊지만 성공·공정성·한 시점의 데이터 관측까지 자동으로 보장하지 않습니다.

재개 커서는 이미 확정한 결과 뒤를 나타냅니다. 중복 키가 있으면 키 하나만으로 위치를 구분할 수 없습니다. 아래는 (키, 레코드 ID)의 사전식 순서, 곧 키를 먼저 비교하고 같은 키 안에서 ID를 비교하는 전체 순서를 사용합니다.

옆으로 움직이는 경쟁

검색은 root에서 아래로 내려가지만 range scan은 옆 리프로 움직인다. merge/delete가 다른 순서로 인접 리프를 잡으면 일관된 top-down 규칙만으로는 충분하지 않다. S가 L을 잡고 R을 기다리는 동안 D가 R을 잡고 L 을 기다리면 교착이다.

no-wait sibling 획득은 다음 latch를 즉시 얻지 못하면 자기가 잡은 latch를 풀고 작업을 재시작하는 규약이다. release 시점/ 어느 키부터 재개하는지/ 재시도 한도는 명확해야 한다. 실패를 무조건 정상 완료로 반환하면 부분 결과가 된다.

포인터의 수명과 누락

split이 기존 리프의 오른쪽 포인터를 바꾸거나 merge가 페이지를 제거하면 예전 포인터를 무보호로 쓰는 코드는 해제된 메모리에 접근할 수 있다. latch/ 핀/ 수명 관리와 적절한 구조 protocol이 필요하다. 이 본문은 B-link 구현 전체가 아닌 일반 문제와 종이 규약을 다룬다.

재개 시 마지막으로 확정 출력한 고유 키보다 큰 키부터 seek 하면 이미 출력한 키의 중복을 피할 수 있다. 중복 키가 허용되는 tree에서는 키만으로 위치를 구별할 수 없어 record-id 등의 총 순서가 필요하다. 이동 중 새 삽입까지 모두 포함하는 snapshot 보장은 이 규칙만으로 생기지 않는다.

관측 시점은 별도 규약

페이지 latch는 물리 자료 구조의 soundness를 보호한다. 두 리프를 서로 다른 시간에 읽으면 그 사이 생긴 삽입이 보이거나 안 보일 수 있다. 특정 시점 자료 전체를 보는 snapshot과 serializable 범위 보호에는 MVCC/ 논리범위 lock 등 별도 protocol이 필요하다.

소단원 6.3

Bloom filter와 선택성

비트 몇 개만 보고 자료가 없다고 판단해도 괜찮을까?

준비 개념과 학습 목표

준비 개념

  • 집합 membership은 키가 들어 있는지 묻는다. false positive는 없는 데 가능하다고 답하는 것이다.

  • 선택성 s는 전체 점 조회 중 실제로 키가 있는 비율이다. FP 확률 p의 분모는 없는 키 질의다.

학습 목표

  • 음성/ 양성 답의 다른 의미를 설명한다.

  • 작은 필터와 조회 비용을 조건부 확률로 계산한다.

오탐률 25%와 조회 양성률 40%는 동시에 맞을 수 있을까요?

Bloom 필터에서 어느 조회 비트 하나라도 0이면 해당 집합에 없다고 판단할 수 있습니다. 모든 비트가 1이면 있을 수 있다는 후보이므로 원자료를 확인합니다. 이 음성 보장은 같은 버전의 키 집합과 해시, 올바른 삽입 정보가 유지되는 조건에서만 사용합니다.

오탐률의 분모는 없는 키의 조회입니다. 실제 있는 키의 조회도 원자료를 확인하므로 전체 확인 비율에는 참양성과 거짓양성을 모두 더합니다. 필터 자체의 비용과 저장 집합 범위도 손익에 포함해야 합니다.

먼저 확인할 개념
  • 압축·Bloom filter·증폭

    필터의 후보 판정과 저장 계층의 추가 확인 비용을 연결합니다.

  • 캐시·직접 I/O·동시성

    조건부 비율과 전체 경로 평균의 분모를 구별하는 계산을 사용합니다.

없는 것과 있을 수 있는 것

일반 Bloom filter는 m 비트를 0으로 두고 삽입 키의 k개 해시 위치를 1로 설정한다. 조회위치 하나라도 0이면 그 키는 없다. 모두 1이면 있을 수 있으므로 원자료를 확인한다. 여기서는 삽입만 하는 정확한 필터와 같은 해시/ 버전 사용을 가정한다.

다른 키가 같은 비트를 켜서 양성 답을 만들 수 있다. 비트만 보면 어떤 키가 켰는지 구별할 수 없다. 키 삭제 시 비트를 무조건 0으로 하면 다른 키의 유일한 비트를 꺼서 false negative를 만들 수 있다. counting filter 등은 별도 설계다.

작은 종이 필터

8비트 index0..7, h1(x)=x mod8,h2(x)=(x +3) mod8로 정한다. 키 1은1/4, 키 4는4/7을 켜 1 인 위치는{1,4,7}이다. 키 2의2/5는 0이라 없고 키 9의1/4는 모두 1이라 가능하나 실제로 없다.

이 해시는 교육용으로 작고 독립 균등 가정을 만족하지 않는다. 이 세 비트 모형에 표준 큰 필터 근사식을 그대로 적용해 실제 FP율이라고 하지 않는다. 실제 RocksDB의 hash/cacheline/SST 형식과 같은 구현도 아니다.

선택성과 비용

점 조회 중 실제 키 비중 s는 반드시 원자료 확인이 필요하고 없는 키 중 p만 false positive로 추가 확인한다. 따라서 확인 비율 s +(1 −s)p다. p가 모든 질의 중 오류율이 아니라는 분모를 꼭 적는다.

필터 비용 F와 원자료 확인 비용 C를 가상 상수로 두면 총 평균은 F +[s +(1 −s)p]C다. 필터를 안 쓰면 C다. 필터 성능은 p뿐 아니라 선택성/ 캐시/ 읽기 비용에 달렸다. whole-key 필터의 point lookup과 prefix 필터의 seek를 같은 성능 규약으로 해석하지 않는다.

  2. 현재 실제 자료에는 7이 있으므로 거짓음성입니다.

  3. 새 집합에 맞는 필터를 만들거나 새 키가 있는 별도 계층을 먼저 확인하는 등 버전·조회 범위를 맞추어야 합니다.

힌트 1

① 현재 잎 상태로 다시 검사합니다. ② 키가 같으면 ID를 비교합니다.

힌트 2

③ 없는 조회의 분모와 전체 조회의 분모를 따로 씁니다.

풀이와 답 확인

  1. ① A 삽입 뒤 잎은 [6,9,12]로 세 키입니다. B의 새 키는 넘침을 만들므로 불안전합니다. 보호된 경로로 재시작해 [6,9,10,12]를 [6,9]와 [10,12]로 나누고 경계 10을 복사합니다.

  2. ② 쌍 커서 뒤의 결과는 (10,3),(12,1)입니다.

  3. ③ 없는 키 조회는 80개이므로 오탐률은 10/80=12.5%입니다. 원자료 확인은 30/100=30%이고 평균은 2+0.3×20=8U입니다.

  4. 실제 latch·스캔·RocksDB 필터 코드를 실행한 결과가 아니라 주어진 규약의 손모형입니다.

① B 삽입은 현재 불안전하며 분할 잎은 [6,9]와 [10,12], 부모 경계는 10입니다. ② 재개 결과는 (10,3),(12,1)입니다. ③ 조건부 오탐률은 12.5%, 전체 확인 비율은 30%, 평균은 8U입니다.
