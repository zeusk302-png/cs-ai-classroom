소단원 8.1

iterator·materialization

검색 결과를 한 개씩 건네면 전체를 배열로 만든 뒤 건네는 것과 무엇이 달라질까?

준비 개념과 학습 목표

준비 개념

  • 행과 필터

  • 함수 호출과 종료

학습 목표

  • Next 호출과 데이터 이동을 추적한다.

  • 전체 중간 결과와 blocking을 구별한다.

첫 결과가 숫자 0이면 종료한 것인가요?

자료 값과 제어 상태를 분리합니다. 여기서 Next의 결과는 Row(값), Done, Failure(이유) 중 하나입니다. 숫자 0이나 SQL NULL이 있는 행도 Row에 담을 수 있으며 종료를 뜻하지 않습니다. 필터는 Row가 조건을 통과할 때까지 자식에게 다시 요청합니다.

아래는 읽기 전용 고정 목록과 단일 흐름의 자체 계약입니다. Done 이후에는 다시 요청하지 않습니다. LIMIT으로 요청을 멈춘 뒤에도 열린 연산자를 닫고 소유한 자원을 한 번 정리해야 합니다. 정렬 같은 blocking 연산자는 행 하나를 반환하는 인터페이스여도 전체 입력 상태가 필요할 수 있습니다.

먼저 확인할 개념
  • 파서·최적화·실행·저장 계층

    논리 결과와 실제 호출 경로를 분리해서 읽습니다.

  • 외부정렬·aggregation

    전체 입력을 알아야 첫 정렬 결과를 정할 수 있는 경계를 확인합니다.

행을 당겨오는 계약

질의 실행기는 계획의 연산자를 연결한다. iterator 모델의 Next는 다음 행 하나 또는 종료 표시를 반환한다. 부모가 자식에 요청하고 자식이 필요한 만큼 아래 연산자에 요청하는 pull 구조다.

필터의 Next 한 번이 자식 Next 한 번과 같은 것은 아니다. 거절되는 행은 계속 읽다가 통과 행을 반환한다. 종료 표시는 데이터베이스 행의 NULL 값과 혼동하지 말고 별도 제어 상태로 이해한다.

전체 결과를 만드는 경계

materialization 모델은 한 연산자의 입력을 처리해 그 출력 전체를 중간 결과로 만든 뒤 다음 단계에 넘긴다. 결과가 작으면 호출이 줄 수 있지만 큰 중간 결과는 메모리·디스크 공간이 필요하다.

iterator도 정렬처럼 전체 입력을 알아야 첫 결과를 정할 수 있는 blocking 연산자를 포함할 수 있다. 한 행 인터페이스가 모든 연산자의 메모리를 한 행으로 제한하는 것은 아니다. 메모리 초과 시 외부 저장을 쓰는 구현도 있다.

요구한 만큼만 읽는 경우

순서가 입력 순서로 정해진 비blocking 필터 뒤 LIMIT을 두면 필요한 결과를 얻은 뒤 요청을 멈출 수 있다. 정렬 뒤 최솟값 하나를 요구하면 추가 인덱스 등이 없는 경우 전체를 봐야 한다.

다음 예는 순차 행 목록, SQL NULL 없는 양의 정수, 인덱스·병렬성·LIMIT 전달 최적화 없는 단순 모델이다. 실제 DB의 측정 결과가 아니라 호출 계약을 종이로 비교한다.

입력은 [0,1,2,3,4,5]이고 짝수 필터 뒤 LIMIT 2가 있습니다. 행 순서는 입력 순서입니다.

중간 과정을 따라가는 예제

입력[1,2,3,4,5], 짝수 필터에서 첫 결과 두 개만 받고 멈춘다. iterator의 Scan.Next 호출 수와 전체 materialization 결과는?

  1. 첫 Filter.Next는1을 거절하고2를 반환해 Scan.Next2회다.

  2. 다음 호출은3을 거절하고4를 반환해 추가2회다.

  3. LIMIT이 멈추므로5와종료 표시는 읽지 않아 총4회다. 전체 materialization은5행을 보고[2,4]를 만든다.

iterator는Scan.Next4회, 전체 방식은5행 검사 후[2,4].

조건을 바꾸어 비교하기

한 필터 호출 안에 여러 자식 호출이 있습니다

표의 LIMIT을 제거하고 입력 종료까지 읽습니다. Scan.Next와 Filter.Next 호출 수를 각각 구하세요.

  1. 첫 출력 0은 자식 호출 한 번이고 두 번째 출력 2는 추가 두 번입니다.

  2. 세 번째 출력 4도 값 3을 거절한 뒤 추가 두 번입니다.

  3. 네 번째 필터 호출은 값 5를 거절하고 Done을 받아 끝납니다. 자식의 데이터 호출 여섯 번과 Done 한 번을 합합니다.

Scan.Next는 7회, Filter.Next는 4회이며 결과는 [0,2,4]입니다. LIMIT 2에서는 Scan.Next가 3회였습니다.

비교할 점

필터가 행을 거절해도 자식은 앞으로 진행했습니다. 출력 행 수만큼만 Scan.Next를 불렀다고 세지 않습니다.

최솟값 하나도 전체 입력을 요구할 수 있습니다

입력 [9,4,1]에 전체 오름차순 정렬 뒤 LIMIT 1이 있습니다. 인덱스·정렬된 입력 보장·부분 정렬 최적화는 없습니다. 첫 정렬 출력을 위해 필요한 자식 호출을 구하세요.

  1. 9를 읽은 순간 뒤에 더 작은 값이 있는지 아직 모릅니다.

  2. 4와 1을 읽은 뒤에도 입력 끝을 확인해야 합니다.

  3. 세 Row와 Done을 받아 전체가 [1,4,9] 순서임을 결정하고 Row(1)을 냅니다.

첫 출력까지 자식 호출은 4회입니다. 출력 인터페이스가 한 행이라고 입력도 한 행만 읽는 것은 아닙니다.

비교할 점

최솟값만 추적해 큰 정렬 상태를 줄이는 별도 방식도 모든 입력을 확인합니다. 메모리 절감과 조기 입력 종료는 서로 다른 주장입니다.

종이와 본문으로 직접 해보기

오해와 반례

iterator를 쓰면 정렬도 항상 첫 입력 즉시 첫 결과를 낸다.

일반 정렬은 나중에 더 작은 값이 올 수 있어 전체 입력을 알아야 한다. 인터페이스와 blocking 성질은 구별한다.

먼저 답과 이유를 적고, 필요한 만큼 힌트를 한 단계씩 열어 보세요.

연습 1 · 값과 상태 예측

표의 필터 조건을 x>10으로 바꾸고 LIMIT 1을 둡니다. 해당 목록에 통과 행이 없을 때 호출 수와 결과를 구하세요.

힌트 1

통과 행을 찾지 못해도 입력 끝까지 확인해야 합니다.

힌트 2

정상 Done과 Failure를 구별합니다.

풀이와 답 확인

  1. 여섯 Row를 모두 거절합니다.

  2. 일곱 번째 Scan.Next가 Done을 반환합니다.

  3. 필터의 첫 호출이 Done을 반환하며 결과는 빈 목록입니다.

Scan.Next는 7회이고 Filter.Next는 1회입니다. 입력을 정상적으로 모두 확인한 빈 결과입니다.

흔한 오답에서 다시 생각하기

LIMIT이 1이므로 Scan.Next도 한 번입니다.

LIMIT은 통과 결과의 최대 개수입니다. 거절된 입력 행 수를 제한하지 않습니다.

연습 2 · 오류 찾아 고치기

짝수 필터 뒤 LIMIT 3에서 입력 [0,1,2,3,4,5]를 읽지만 값 4를 읽으려는 자식 호출이 Failure(I/O)입니다. 이미 부모가 받은 결과는 [0,2]입니다. 프로그램이 이를 완료된 두 행 결과로 표시했습니다. 고치세요.

힌트 1

원래 계약은 최대 세 결과를 얻거나 정상 입력 종료를 확인하는 것입니다.

힌트 2

Failure는 정상 Done이 아닙니다.

풀이와 답 확인

  1. 0과 2를 얻은 뒤 값 3을 거절하고 다음 자식에서 오류를 받습니다.

  2. 필터는 오류를 위로 전달하며 Done으로 바꾸지 않습니다.

  3. 이미 전달한 두 행은 미완료 결과로 표시합니다. 원자적인 목록 반환 API라면 임시 목록을 버리고 실패를 반환합니다.

이 질의는 실패 또는 미완료입니다. [0,2]를 정상 완료 결과로 표시할 수 없습니다. 부분 결과 허용 여부를 API 계약에 명시합니다.

흔한 오답에서 다시 생각하기

두 결과가 맞으니 실패를 무시해도 됩니다.

나머지 입력의 결과를 아직 확인하지 못했습니다. 올바른 앞부분과 완료된 전체는 다릅니다.

연습 3 · 직접 만들어 보기

Scan.Open은 한 핸들을 확보하고 Scan.Close는 그 핸들을 해제합니다. LIMIT 2가 첫 두 출력 뒤 요청을 멈춥니다. Open·Next·Close의 소유 규약을 만들고 중복 Close 방지 조건을 쓰세요.

힌트 1

정상 Done 없이 멈추는 경로도 포함합니다.

힌트 2

이미 닫힌 상태에서는 실제 해제를 다시 하지 않습니다.

풀이와 답 확인

  1. Open 성공 후 핸들 소유 상태를 표시합니다.

  2. LIMIT 충족·Done·Failure 중 어떤 종료 경로에서도 소유자가 Close를 호출합니다.

  3. Close는 소유 상태를 한 번 닫힘으로 바꾸고 실제 핸들을 한 번만 해제합니다. 이후 중복 요청은 해제하지 않습니다.

조기 중단에도 한 번 정리합니다. 다른 흐름이 핸들을 사용 중인 실제 구현이라면 종료·사용 완료 확인이 추가로 필요합니다.

흔한 오답에서 다시 생각하기

Done을 받지 않았으므로 핸들은 계속 열어 둡니다.

LIMIT으로 더 읽지 않는 경로에도 자원 수명을 끝낼 책임이 있습니다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

Next는 같은 한 칸 버퍼의 주소를 빌려 주고 그 주소는 다음 Next 전까지만 유효합니다. 처음 값 2, 다음 값 4가 같은 버퍼에 들어갑니다. 두 주소를 그대로 모아 나중에 읽는 경우와 두 값을 즉시 복사하는 경우를 비교하세요.

힌트 1

첫 주소가 별도 저장 공간인지 확인합니다.

힌트 2

다음 호출이 버퍼를 덮어쓰는 계약입니다.

풀이와 답 확인

  1. 첫 호출의 주소와 둘째 호출의 주소는 같은 버퍼를 가리킵니다.

  2. 두 번째 호출 뒤 버퍼 값은 4라 저장한 주소를 두 번 읽으면 [4,4]처럼 보일 수 있습니다.

  3. 각 호출 동안 값을 복사해 소유하면 [2,4]를 보존합니다.

빌린 주소는 결과 소유를 뜻하지 않습니다. 이 버퍼 규약에서는 유효 기간 안에 복사하거나 소유권 이전 계약을 따로 받아야 합니다.

흔한 오답에서 다시 생각하기

두 번 받은 주소니까 두 독립 행이 영구 보존됩니다.

호출 횟수와 저장 공간의 수명은 다릅니다. 주소가 같으면 나중에 덮어쓴 값을 읽습니다.

마지막 배치에 남은 빈칸도 자료라고 읽으면 어떤 결과가 생길까요?

배치에는 저장 공간의 최대 용량과 실제 유효 행 수가 따로 있습니다. 필터의 선택 위치는 현재 배치의 유효 범위 안에 있어야 합니다. 이전 배치의 남은 값이나 다음 호출에 덮어쓰인 값은 현재 결과가 아닙니다.

이 단원은 빈 RowBatch도 전달하고 종료는 별도의 Done으로 전하는 자체 규약입니다. 실제 실행기는 빈 출력을 건너뛰거나 다시 채울 수 있습니다. 배치 처리·SIMD 명령 사용·여러 worker 실행은 각각 다른 주장으로 확인해야 합니다.

먼저 확인할 개념
  • 인코딩·압축·late materialization

    선택 위치로 필요한 행을 뒤에서 가져올 때 대응을 보존합니다.

  • 집합·중복·NULL 처리

    유효한 숫자 0과 NULL의 필터 의미를 구별합니다.

묶음이 바꾸는 호출 단위

vectorization은 연산자 사이에 한 행 대신 작은 batch를 넘기는 실행 모델이다. 한 번 호출로 여러 행을 처리해 호출 비용을 줄이고 같은 열을 반복 처리하는 루프에 유리할 수 있다. batch 크기는 하드웨어·행 크기·질의에 따라 조절한다.

벡터화했다고 반드시 SIMD 명령을 쓰거나 여러 CPU에서 동시 실행하는 것은 아니다. SIMD를 활용하기 쉬운 배치와 실제 생성된 명령·병렬 스레드는 각각 확인할 주장이다. 이 강의에서는 실행하지 않는다.

행의 위치를 잃지 않는 필터

필터는 batch의 살아남은 행을 모으거나 선택 위치 배열로 가리킬 수 있다. 값 자체가0이어도 선택된 유효 행일 수 있다. 빈 결과 batch와 전체 입력 종료도 구별해야 한다.

이 예는 입력 batch를 최대4개씩 읽고 각 batch 통과 행을 즉시 넘기며, 빈 batch 뒤에도 자식 종료 전까지 계속 읽는 교육 계약이다. 출력이 꽉 찰 때까지 재충전하는 구현이면 호출 경계는 달라질 수 있다.

파이프라인과 중간 결과

scan→filter→projection처럼 batch를 다음 단계로 바로 넘길 수 있으면 전체 중간 결과를 저장하지 않는 pipeline을 구성한다. 전체 정렬이나 어떤 집계·join 단계는 정보를 모아야 해 경계를 끊을 수 있다.

batch가 크면 호출이 줄지만 작업 버퍼와 캐시 부담이 늘고 작은 LIMIT의 불필요한 읽기가 생길 수 있다. 빠른지는 데이터와 계획을 실제 측정해야 하며 아래 호출 수 차이를 속도 배수로 간주하지 않는다.

조건을 바꾸어 비교하기

호출 감소와 속도 주장을 구별합니다

11행 전체 입력을 종료까지 읽습니다. 호출당 고정 비용은 10ns, 실제 행 처리당 추가 비용은 3ns로 정합니다. 스칼라·최대 배치 4·최대 배치 8의 자체 합산 비용을 구하세요. 종료 호출도 고정 비용을 부담합니다.

  1. 스칼라는 데이터 11회와 Done 1회로 12회입니다. 비용은 12×10+11×3=153ns입니다.

  2. 최대 배치 4는 데이터 세 번과 Done 한 번으로 4회입니다. 비용은 40+33=73ns입니다.

  3. 최대 배치 8은 데이터 두 번과 Done 한 번으로 3회입니다. 비용은 30+33=63ns입니다.

스칼라 모형의 비용은 153 ns, 최대 배치 4는 73 ns, 최대 배치 8은 63 ns입니다. 실제 CPU·캐시·SIMD·복사 비용을 측정한 수치가 아닙니다.

비교할 점

호출 수의 비율 12/4=3과 합산 비용 비율 153/73은 같지 않습니다. 배치를 더 키웠을 때의 다른 비용도 이 단순 식에는 없습니다.

선택 배열을 합성할 때 원래 행 위치를 유지합니다

값 [0,NULL,4,5]와 유효 표시 [참,거짓,참,참]이 있습니다. 첫 필터는 유효한 짝수만 고르고 다음 필터는 x>1입니다. 값 복사 없이 원래 배치를 가리킬 때 최종 선택 위치를 구하세요.

  1. 첫 필터는 원래 위치 0과 2를 고릅니다. 값 0은 유효하고 NULL은 제외됩니다.

  2. 두 번째 필터가 보는 두 값은 0과 4입니다. 두 후보 중 뒤의 4만 통과합니다.

  3. 뒤의 후보가 첫 선택 배열의 위치 1이라는 이유로 원래 배치 위치 1을 가리키면 NULL을 선택합니다. 선택 배열을 합성해 원래 위치 2를 유지합니다.

최종 선택은 원래 배치 위치 [2]이며 값은 [4]입니다.

비교할 점

후보 목록에서의 위치와 원래 배치에서의 위치를 구별합니다. 숫자 0을 무효 표시로 사용하는 것은 이 자료 계약과 맞지 않습니다.

연습 1 · 값과 상태 예측

표의 11행을 최대 배치 5로 바꾸어 x>7 필터의 배치별 결과와 종료 포함 자식 호출 수를 구하세요.

힌트 1

배치는 [0..4],[5..9],[10]입니다.

힌트 2

빈 결과와 마지막 짧은 배치도 진행 상태입니다.

풀이와 답 확인

  1. 첫 배치는 빈 결과입니다.

  2. 두 번째 배치에서 8과 9가 통과하고 마지막에서 10이 통과합니다.

  3. 데이터 세 번과 Done 한 번으로 네 호출입니다.

결과 배치는 [],[8,9],[10]이고 호출은 4회입니다. 전체 논리 결과 [8,9,10]은 배치 4와 같습니다.

흔한 오답에서 다시 생각하기

배치를 4에서 5로 키우면 반드시 호출 한 번이 줄어듭니다.

ceil(11/4)와 ceil(11/5)는 모두 3입니다. 배치 수는 올림의 경계를 따라 변합니다.

연습 2 · 오류 찾아 고치기

세 번째 배치의 네 칸 저장 공간에는 [8,9,10,99]가 남아 있고 유효 행 수는 3입니다. 필터가 용량 4를 순회해 99까지 반환합니다. 오류를 고치세요.

힌트 1

99는 현재 입력 행인지 확인합니다.

힌트 2

선택 위치에도 유효 범위 검사가 필요합니다.

풀이와 답 확인

  1. 현재 유효 행은 위치 0,1,2뿐입니다.

  2. 이전 사용의 잔여값 99가 있는 위치 3은 읽지 않습니다.

  3. 유효 행 수까지만 평가하고 모든 선택 위치가 그 범위 안에 있는지 검사합니다.

현재 출력은 [8,9,10]입니다. 잔여값 99를 반환하면 없는 입력 행을 만들어 낸 오류입니다.

흔한 오답에서 다시 생각하기

칸이 할당되어 있으니 그 값은 전부 현재 자료입니다.

용량과 실제 입력 길이가 다릅니다. 초기화 여부도 현재 행의 존재를 보장하지 않습니다.

연습 3 · 직접 만들어 보기

첫 값 0도 통과하는 짝수 필터와 LIMIT 1을 둡니다. 최대 배치 4의 Scan은 [0,1,2,3]을 한 번에 읽습니다. 스칼라 방식과 비교해 읽은 행 수와 자식 호출 수를 구하세요. 종료까지 추가 호출하지 않습니다.

힌트 1

스칼라는 첫 Row(0) 뒤 멈춥니다.

힌트 2

배치는 LIMIT을 하위 scan에 전달하지 않는 규약입니다.

풀이와 답 확인

  1. 스칼라는 첫 행만 읽어 한 자식 호출로 결과 0을 얻습니다.

  2. 배치는 네 행을 한 번에 받아 한 자식 호출로 필터 결과 [0,2]를 얻습니다.

  3. LIMIT은 첫 결과 0만 사용하고 나머지 입력은 이 계약에서 불필요하게 읽었습니다.

자식 호출은 둘 다 1회지만 읽은 행은 스칼라 1행, 배치 4행입니다. 결과는 동일한 한 행 0입니다.

흔한 오답에서 다시 생각하기

배치의 호출 수가 적으므로 작은 LIMIT에서도 추가 읽기는 없습니다.

묶음 단위의 선행 읽기로 필요 없는 행이 생길 수 있습니다. 요청 전달과 배치 크기 조건을 확인합니다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

생산 단계는 배치당 4 ms, 다음 소비 단계는 배치당 6 ms입니다. 배치 세 개를 처리하며 각 단계는 한 번에 하나를 실행합니다. 동시에 실행할 자원이 충분하고 준비된 배치 보관 공간도 충분합니다. 겹침 실행 시간을 그리세요.

힌트 1

소비 단계는 해당 배치가 생산된 뒤에 시작합니다.

힌트 2

소비 단계의 이전 배치가 끝나야 다음 배치를 시작합니다.

풀이와 답 확인

  1. 첫째 배치 생산은 0–4 ms, 둘째는 4–8 ms, 셋째는 8–12 ms입니다.

  2. 첫째 배치 소비는 4–10 ms, 둘째는 10–16 ms, 셋째는 16–22 ms입니다.

  3. 전체 마지막 완료는 22 ms이며 각 배치를 생산·소비 순서로 직렬 처리하면 30 ms입니다.

겹친 모형의 완료는 22 ms입니다. 단순히 생산 합 12와 소비 합 18의 최댓값 18로 끝나지 않고 시작 지연이 있습니다.

흔한 오답에서 다시 생각하기

느린 단계의 합만 보면 18 ms에 모두 끝납니다.

첫 배치가 생산되기 전에는 소비를 시작할 수 없습니다. 파이프라인의 처음 채우는 시간을 포함합니다.

취소를 요청한 시각과 마지막 자원을 정리한 시각이 같을까요?

질의 내 병렬 scan은 서로 겹치지 않는 범위가 전체 입력을 덮어야 합니다. gather로 결과를 모은 도착 순서는 입력 순서나 ORDER BY 순서를 자동으로 보장하지 않습니다. 다음 예는 읽기 전용 고정 입력과 동일한 자료 의미를 유지합니다.

취소 요청은 실행 종료의 증거가 아닙니다. 자체 협력 모형에서는 worker가 점검 지점에서 요청을 보고 멈춘 뒤 소유 자원을 정리하고 종료를 알립니다. 실제 PostgreSQL에서는 취소를 별도 연결로 보내지만 취소 요청 자체의 성공 응답은 없으므로 원래 질의의 응답을 계속 확인해야 합니다.

먼저 확인할 개념
  • 생산자·소비자·독자쓰기

    버퍼가 가득 찬 대기와 소비자 중단을 함께 추적합니다.

  • pin·dirty·eviction

    사용 중인 자원을 완료 확인 전에 해제하면 안 되는 이유를 연결합니다.

서로 다른 질의와 한 질의의 병렬성

질의 간 병렬은 여러 사용자의 요청을 동시에 실행하는 것이다. 질의 내 병렬은 한 질의의 scan·join 등의 일을 여러 worker에 나눈다. 연산자 내부 분할, 서로 다른 단계 겹침, 여러 가지 계획 분기를 병렬화할 수 있다.

scan 범위가 겹치면 중복 집계, 빠지면 누락이 생긴다. gather는 여러 흐름을 모으고 repartition은 목적별로 다시 나눈다. worker 결과 도착 순서는 SQL의 ORDER BY가 지정한 최종 순서를 자동 보장하지 않는다.

작업 분량과 가장 늦은 worker

병렬 시간은 단순히 전체 시간을 worker 수로 나눈 값과 같지 않다. 불균형한 분할, 공유 I/O, 통신·병합과 시작 비용이 남는다. 아래는 동시에 시작하고 각 행 비용이 같은 독립 작업이며 마지막 worker 뒤 고정 gather비용을더하는 모델이다.

작업을 늘렸다고 공유 디스크 병목을 넘어 무한 속도를 얻지 않는다. 집계에서는 각 worker의 부분 합을 합쳐야 하며 평균은 단순 worker 평균이 아니라 건수도 함께 고려해야 한다.

취소는 협력과 정리의 프로토콜

취소 flag를 관측하는 지점마다 작업을 멈추는 교육 모델에서는 다음 점검까지 계산이 진행될 수 있다. 실제 DB는 인터럽트·I/O 대기·잠금·정리 절차를 사용하고 응답으로 결과를 알려야 한다.

PostgreSQL 취소 요청은 별도 연결에서 보내며 직접 성공 응답을 받지 않는다. 원래 질의 응답을 기다려야 하며 이미 작업이 끝난 뒤 도착하면 효과가 없을 수 있다. 취소가 이미 commit된 과거 거래까지 되돌린다는 뜻은 아니다. 이 절은 실제 프로세스를 종료하지 않는다.

표의 병렬 계획과 한 worker가 12행을 처리하는 순차 계획에 모두 마지막 gather 3 ms를 적용합니다. 별도 불균형 계획은 worker별 2,3,7행입니다. 계산 시간을 비교하세요.

  1. 순차는 12×2+3=27 ms입니다. 균등 병렬은 8+3=11 ms입니다.

  2. 동일한 마지막 비용의 속도비는 27/11, 약 2.45입니다.

  3. 불균형 계획에서 W0의 계산 시간은 4 ms, W1은 6 ms, W2는 14 ms입니다. 마지막 worker가 끝난 뒤 gather 비용 3 ms를 더하므로 전체 완료 시각은 17 ms입니다.

순차 27 ms, 균등 병렬 11 ms, 불균등 병렬 17 ms입니다. 기본 원고의 순차 행 처리 24 ms와는 gather 포함 범위가 다릅니다.

비교할 점

worker 수로 27을 단순히 나누면 9 ms지만 직렬 gather와 분할 불균형은 그렇게 나뉘지 않습니다. 실제 공유 I/O 비용도 이 모형에 없습니다.

취소 관찰 뒤에도 정리가 남습니다

별도 두 worker 모형에서 시각 5 ms에 취소를 요청했습니다. W0는 다음 점검 8 ms에 보고 정리 2 ms를 수행합니다. W1은 점검 12 ms에 보고 정리 3 ms를 수행합니다. 조정자는 두 종료 확인 뒤 최종 취소 완료를 알립니다. 통신 지연은 0입니다.

  1. W0의 정리 종료는 8+2=10 ms입니다.

  2. W1의 정리 종료는 12+3=15 ms입니다.

  3. 마지막 종료 확인은 15 ms이므로 요청부터 완료까지는 15−5=10 ms입니다.

요청은 5 ms, 최종 완료는 15 ms입니다. 조정자는 5 ms에 worker가 쓰는 버퍼를 먼저 해제하지 않습니다.

비교할 점

이는 명시한 협력 모형의 값입니다. 실제 DB·OS의 취소 지연을 10 ms로 보장하거나 이미 commit된 거래를 취소하는 뜻이 아닙니다.

연습 1 · 값과 상태 예측

범위를 [0,5),[4,8),[8,12)로 잘못 나누었습니다. 행 값은 위치와 같고 각 worker가 자기 범위를 모두 더한 뒤 합을 모읍니다. 오류와 최종 합을 구하세요.

힌트 1

힌트 2

풀이와 답 확인

  1. 첫 구간은 0..4, 둘째는 4..7이므로 4가 중복입니다.

  2. 누락 위치는 없지만 자료 4를 한 번 더 더합니다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

① 값 0도 결과입니다. ② 후보 배열 위치와 원래 배치 위치를 구별합니다.

힌트 2

③ 점검 시각 뒤 정리 시간을 더하고 마지막 종료를 기다립니다.

풀이와 답 확인

  1. ① 첫 호출은 0을 받고 다음 필터 호출은 1을 거절한 뒤 2를 받습니다. 자식 호출은 합계 세 번입니다.

  2. ② 후보 값 0과 4 중 4만 통과하므로 원래 위치 [2]입니다.

  3. ③ 종료 시각은 10 ms와 15 ms입니다. 최종 완료는 15 ms이고 요청 이후 지연은 10 ms입니다.

  4. 조기 중단과 실패 경로에서도 자원 수명 계약을 보존합니다. 계산은 자체 호출·시간 모형이며 실제 엔진·SIMD·취소·학생 실험은 미수행입니다.

① Scan.Next는 3회입니다. ② 원래 선택 위치는 [2]이고 값은 [4]입니다. ③ 최종 완료는 15 ms, 요청 이후 지연은 10 ms입니다.

해결한 뒤 점검할 것

  • 자료 값 0·NULL과 Done·Failure·취소 요청 상태를 구별합니다.

  • 배치 유효 행 수와 선택 위치의 대응·수명을 보존합니다.

  • 호출 횟수와 실제 읽은 행 수·실행 시간을 같은 양으로 취급하지 않습니다.

  • 반열린 범위의 전체 포함·무중복과 출력 순서를 따로 확인합니다.

  • 조기 중단 뒤 대기 깨우기·종료·정리·자원 해제를 확인합니다.

보강 자료의 출처와 확인 범위
  • CMU 15-445/645 — Query Processing I

    공식 7쪽 PDF 전체를 실제 읽었다. 단일 tuple·별도 종료 표시·materialization·batch·pull/push·pipeline breaker와 LIMIT을 확인했다. 세 갈래 제어 상태·빌린 버퍼·가상 ns 비용·선택 합성은 명시한 자체 계약이다. 순차 scan의 광범위 우열 표현은 모든 질의의 보장으로 채택하지 않았다.

  • CMU 15-445/645 — Query Execution II

    공식 6쪽 PDF 전체를 실제 읽었다. 질의 간/내 병렬성·서로 겹치지 않는 입력·exchange의 gather/distribute/repartition·단계 겹침·I/O 병목을 확인했다. 모든 exchange가 전체 입력 전에 반드시 blocking한다거나 worker 프로세스 오류가 전체 상태에 영향을 주지 않는다는 광범위 보장으로 확장하지 않는다. 자체 시간표는 실제 성능 측정이 아니다.

  • PostgreSQL 18 — Canceling Requests in Progress

    공식 54.2.8의 줄325–333을 실제 읽었다. 별도 연결·키 확인·직접 취소 응답 부재·이미 완료한 질의의 늦은 취소·원래 응답 대기를 확인했다. 두 worker 정리와 큐 종료 모형은 실제 PostgreSQL 전체 취소 구현이라고 주장하지 않는다.

입력 0부터 5까지의 짝수 필터에서 LIMIT 2는 Scan.Next 3회입니다. 정상 종료까지는 Scan.Next 7회와 Filter.Next 4회입니다. 전부 거절되면 필터 첫 호출 안에 자식 7회가 필요합니다. 정렬 입력 9,4,1은 첫 결과 1 전에 자식 4회가 필요합니다. 빌린 한 칸 버퍼의 두 주소는 둘째 호출 뒤 같은 값 4를 가리키고, 즉시 복사는 2와 4를 보존합니다. 11행의 스칼라·배치 4·배치 8은 종료 포함 12회·4회·3회이며 가상 비용은 153 ns·73 ns·63 ns입니다. 배치 5도 종료 포함 4회입니다. NULL을 제외한 짝수 선택은 원래 위치 0과 2이며 후속 조건 x>1은 위치 2입니다. 마지막 배치의 용량 4와 유효 길이 3을 구별했습니다. LIMIT 1에서는 스칼라와 배치가 모두 한 호출이지만 읽은 행은 1과 4입니다. 생산 4 ms와 소비 6 ms의 세 배치는 전체 22 ms이고 직렬은 30 ms입니다. 12행에 동일 gather 3 ms를 포함한 순차는 27 ms, 균등 병렬은 11 ms, 불균등 2·3·7행은 17 ms입니다. 올바른 위치 합은 66이며 위치 4를 중복하면 70입니다. 취소 요청 5 ms 뒤 각 종료는 10 ms와 15 ms이며 전체 지연은 10 ms입니다. 도착 순서 gather가 정렬 순서와 다른 목록을 만듦을 확인했습니다. 모든 결과는 손검산이며 실제 엔진·SIMD·worker·취소 코드·학생 실험은 수행하지 않았습니다.
