소단원 5.1

B+트리·해시

정확히 한 학생을 찾는 조회와 번호 구간을 찾는 조회에 같은 인덱스가 유리할까?

준비 개념과 학습 목표

준비 개념

  • 인덱스는 검색 키에서 데이터 위치로 가는 보조 구조다. 페이지는 저장·읽기의 묶음이며 leaf는 트리의 맨 아래 노드다.

  • B+트리 내부 키는 자식 선택을 위한 경계이며 실제 레코드 또는 위치 정보는 잎에 있다. 중복 없는 정수 키 예제로 시작한다.

학습 목표

  • 정렬 트리의 분기와 잎 범위 검색을 추적한다.

  • 해시 충돌과 동등·범위 검색의 차이를 설명한다.

인덱스 잎에 도착하면 데이터도 이미 읽은 것일까요?

책의 색인이 본문 쪽을 가리키듯 인덱스의 잎도 데이터가 있는 위치를 가리킬 수 있습니다. 잎에 실제 값을 모두 담는 형식도 있지만 이 예제는 키와 레코드 위치만 담습니다. 따라서 잎을 읽은 뒤 데이터 페이지에 가는 비용이 남습니다.

정렬된 트리는 시작 경계를 찾고 오른쪽 잎을 이어 읽어 범위를 처리할 수 있습니다. 해시는 동등한 키의 버킷을 고르는 데 쓰지만 보통 키의 대소 순서를 보존하지 않습니다. 어느 경우든 실제 키와 조건을 다시 확인해야 합니다.

먼저 확인할 개념
  • 슬롯 페이지·튜플 식별자

    잎의 레코드 위치가 데이터 페이지의 식별자로 이어지는 구조를 연결합니다.

  • 역색인·포스팅 리스트

    키에 연결된 여러 레코드 위치를 별도로 보존하는 이유를 비교합니다.

한 페이지에서 여러 자식을 고른다

트리의 내부 페이지는 정렬된 분리 키와 자식 포인터를 가진다. 분리 키 25가 있다면 이 예제는 왼쪽이25보다 작고 오른쪽이25 이상이라는 규칙이다. 잎들은 같은 깊이에 있어 검색 경로가 한쪽만 길게 늘어나는 것을 방지한다.

큰 fanout은 한 페이지에서 많은 자식을 구별하는 정도다. 실제 페이지 용량은 바이트 수·키 길이·포인터 크기에 달린다. 여기서는 키 개수로 용량을 정한 종이 모형이며 모든 DB에서 최대 키 수가 동일한 상수라고 말하지 않는다.

잎의 순서를 범위 조회에 사용한다

잎의 키들은 정렬되어 있고 오른쪽 잎으로 이어지는 링크를 사용할 수 있다. 시작 키를 찾은 뒤 다음 잎들을 순서대로 읽으며 종료 경계를 확인한다. 내부 분리 키를 찾았다고 실제 레코드 조회를 끝내지 않고 알맞은 잎까지 내려간다.

범위에 맞는 많은 결과를 내보내면 결과 수만큼의 비용도 필요하다. 인덱스가 있다는 이유로 모든 조회가 한 번의 페이지 읽기로 끝나거나 출력 비용이0이 되는 것은 아니다. 캐시 상태와 데이터 페이지 방문도 실제 비용에 포함한다.

해시는 같은 위치와 같은 키를 구별한다

h(k)=k mod4의 버킷에서는 키2,6,10이 모두2번으로 간다. 이것은 충돌이지 세 키가 같다는 뜻이 아니다. 해당 버킷 안에서 원래 키의 동등 여부를 다시 검사하고 모든 항목을 보존하는 충돌 처리가 필요하다.

해시는 키 순서를 일반적으로 보존하지 않는다. 등호 검색에 맞는 버킷을 빠르게 고를 수 있어도 범위 2..10을 찾는 데 버킷 2만 보면3이나8을 놓친다. 실제 인덱스 선택은 조회 형태·분포·갱신 비용과 함께 판단하며 여기서는 실행 시간을 측정하지 않았다.

루트 분리 키는 20과 40입니다. 왼쪽은 20 미만, 가운데는 20 이상 40 미만, 오른쪽은 40 이상입니다.

중간 과정을 따라가는 예제

내부 분리 키 25, 왼 잎 [10,20], 오른 잎 [25,30]의 트리에서 키 25와 범위 18..28을 찾으라. 별도 해시 h=k mod4에2,6,10을 넣고6을 찾아라.

  1. 25는 경계 이상이므로 오른 잎에서 25의 레코드 위치를 얻는다. 내부 25는 라우팅 사본이다.

  2. 18은 왼 잎에서 찾기 시작하고20을 얻는다. 오른 잎으로 이동하여25를 얻고30>28에서 멈춘다.

  3. 범위 결과는 20,25다. 트리의 잎 정렬과 링크를 함께 사용했다.

  4. 해시2/6/10은 모두 버킷 2다. 그 안에서 원래 키를 비교하여 6을 고르며 2나 10을 6으로 바꾸지 않는다.

트리 점조회25, 범위 20/25, 해시6은 충돌 버킷의 원래 키 비교로 얻는다.

조건을 바꾸어 비교하기

범위 결과와 데이터 페이지를 따로 셉니다

범위 12..43을 찾습니다. 결과 키의 데이터 페이지는 15→P0, 20→P1, 25→P1, 30→P2, 40→P2입니다. 읽는 인덱스·데이터 페이지 수를 구하세요.

  1. 12는 L0에서 시작합니다. 15를 고르고 오른쪽 L1의 20·25·30을 고릅니다. L2에서 40을 고르고 45가 종료값 43보다 커서 멈춥니다.

  2. 루트와 L0·L1·L2를 읽으므로 인덱스 페이지는 네 개입니다.

  3. 데이터 페이지 P0·P1·P2는 각각 한 번 읽습니다. 같은 P1과 P2를 다시 요청해도 이 모형에서는 캐시에 남아 있습니다.

결과 키는 15·20·25·30·40이고 인덱스 읽기 4회, 데이터 읽기 3회로 총 7회입니다. 반환 결과는 다섯 개지만 데이터 읽기도 반드시 다섯 회가 되는 것은 아닙니다.

비교할 점

인덱스 네 페이지가 답 전체를 담았다고 세면 데이터 읽기를 빠뜨립니다. 반대로 결과마다 새 데이터 읽기로 세면 이미 읽은 페이지의 재사용을 놓칩니다.

해시 충돌은 키의 동등함이 아닙니다

h(k)=k mod 5인 모형에 2·7·12·3·8을 넣습니다. 키 7의 동등 검색과 범위 2..8을 버킷 2만으로 처리하려는 검색을 비교하세요.

  1. 버킷 2에는 2·7·12, 버킷 3에는 3·8이 들어갑니다.

  2. 키 7의 동등 검색은 버킷 2 안에서 원래 키가 7인 항목을 고릅니다.

  3. 범위 2..8의 결과는 2·3·7·8입니다. 버킷 2만 보면 3과 8을 놓치며 12는 범위 밖입니다.

동등 검색 결과는 7입니다. 범위 검색은 버킷 2만으로 완료할 수 없습니다. 이 모형에서는 필요한 전체 버킷을 확인하고 실제 범위 조건을 적용해야 합니다.

비교할 점

같은 해시값인 2·7·12를 같은 레코드로 덮어쓰면 충돌 처리부터 잘못됩니다. mod 5는 실제 PostgreSQL의 해시 함수가 아닌 교육 모형입니다.

종이와 본문으로 직접 해보기

키1,5,9와2,6을 h=k mod4로 배정하라. 범위 1..6을 버킷 1만 읽으면 무엇을 놓치는가?

힌트 보기

같은 나머지끼리 모으고 실제 범위 조건을 다시 검사한다.

풀이 보기

버킷 1에1,5,9, 버킷 2에2,6이다. 범위 1..6의 결과 1,2,5,6 중 버킷 1만 보면2와6을 놓치고 9는 범위 밖이라 버려야 한다.

오해와 반례

해시가 같으면 같은 레코드이고 B+트리 내부 키에도 실제 레코드가 항상 있다.

2,6,10의 나머지는 같지만 키는 다르다. B+트리 내부 25는 탐색 경계이며 잎 25의 레코드를 대신하지 않는다. 각 구조의 저장 역할을 구분한다.

스스로 풀어보기

먼저 답과 이유를 적고, 필요한 만큼 힌트를 한 단계씩 열어 보세요.

연습 1 · 값과 상태 예측

기본 트리에서 키 40을 찾고 실제 데이터까지 읽습니다. 루트가 처음부터 캐시에 있는 경우와 없는 경우를 비교하세요. 잎과 데이터 페이지는 처음 캐시에 없습니다.

힌트 1

40과 같은 분리 키에서 어느 자식으로 가는지 봅니다.

힌트 2

루트가 캐시되었다면 방문은 해도 장치 읽기는 추가하지 않습니다.

풀이와 답 확인

  1. 40은 오른쪽 범위이므로 L2로 내려갑니다.

  2. 루트가 없으면 루트·L2·해당 데이터 페이지로 세 번 읽습니다.

  3. 루트가 있으면 L2·데이터 페이지만 두 번 읽습니다.

루트가 차가우면 3회, 이미 캐시되었으면 2회입니다. 검색 경로의 단계 수와 실제 페이지 읽기 수를 구별합니다.

흔한 오답에서 다시 생각하기

분리 키 40이 루트에 있으니 잎은 읽지 않습니다.

루트의 40은 자식 선택 경계입니다. 실제 레코드 위치를 얻으려면 이 모형에서는 L2까지 내려갑니다.

연습 2 · 오류 찾아 고치기

범위 12..43 검색 코드가 시작 잎 L0에서 15를 얻은 뒤 잎을 더 읽지 않고 완료합니다. 오류와 수정 종료 조건을 설명하세요.

힌트 1

시작 잎 다음에도 범위 안의 키가 있는지 확인합니다.

힌트 2

실제 키가 종료 경계를 넘거나 잎이 끝나야 종료할 수 있습니다.

풀이와 답 확인

  1. L1의 20·25·30과 L2의 40을 빠뜨렸습니다.

  2. 오른쪽 잎으로 이동하며 범위 안의 키를 계속 모읍니다.

  3. L2의 45를 확인하면 43보다 크므로 이 정렬 모형에서는 뒤의 키도 범위 밖이라 멈춥니다.

반환해야 할 결과는 15·20·25·30·40입니다. 시작 위치를 찾는 일과 범위 전체를 끝내는 일은 별개입니다.

흔한 오답에서 다시 생각하기

트리 검색은 잎 하나에서 끝나므로 15만 반환해도 됩니다.

점조회와 범위 조회를 섞었습니다. 범위 결과는 여러 잎에 걸칠 수 있습니다.

연습 3 · 직접 만들어 보기

비고유 인덱스의 키 25에 레코드 ID r1·r2·r3이 연결됩니다. 각 레코드는 서로 다릅니다. 하나의 키에 ID 목록을 두는 잎 표현과 키 25 동등 검색 결과를 구성하세요. 이 질의에서 세 레코드는 모두 보인다고 정합니다.

힌트 1

키가 같은 것과 레코드가 같은 것은 구별합니다.

힌트 2

세 위치를 모두 보존하는 표현이 필요합니다.

풀이와 답 확인

  1. 잎 항목을 (25,[r1,r2,r3])으로 구성합니다.

  2. 동등 검색에서 목록의 세 위치를 모두 얻습니다.

  3. 데이터의 추가 조건이나 가시성 검사는 별도로 적용합니다. 이 문제에는 세 레코드가 모두 보인다고 정합니다.

한 키 항목에 세 ID를 보관하고 동등 검색 결과는 세 레코드입니다. 최신 한 ID로 덮어쓰면 다른 두 레코드를 잃습니다.

흔한 오답에서 다시 생각하기

키 25는 하나이므로 어떤 레코드 한 개만 있으면 충분합니다.

키의 고유 여부를 확인하지 않았습니다. 비고유 인덱스는 같은 키의 여러 레코드를 표현해야 합니다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

첫 범위 예제와 키 결과는 같지만 다섯 결과가 각각 다른 데이터 페이지 P0..P4에 있습니다. 루트도 처음 캐시에 없습니다. 총 읽기 수와 앞 예제의 차이를 구하세요.

힌트 1

인덱스 경로는 그대로입니다.

힌트 2

서로 다른 데이터 페이지 수만 바뀝니다.

풀이와 답 확인

  1. 루트와 세 잎의 인덱스 읽기는 네 번입니다.

  2. 데이터 읽기는 서로 다른 다섯 페이지라 다섯 번입니다.

  3. 합계는 아홉 번으로 앞의 일곱 번보다 두 번 많습니다.

총 읽기는 9회입니다. 결과 수와 인덱스 구조가 같아도 데이터의 물리 배치가 비용을 바꿉니다.

흔한 오답에서 다시 생각하기

반환 키가 같으므로 총 읽기도 반드시 7회입니다.

레코드가 어떤 페이지를 공유하는지가 달라졌습니다. 결과 동일성과 물리 읽기량 동일성은 다른 조건입니다.

준비 개념과 학습 목표

준비 개념

  • 이 단원의 자체 B+트리 잎은 최대 3키, 비루트 최소 2키다. 루트 하나만 남으면 최소 2 예외를 허용한다.

  • 분할은 두 페이지로 나누는 일, 병합은 이웃을 합치는 일이다. WAL은 페이지 변경 전에 복구용 기록을 영구 저장하는 규칙이다.

학습 목표

  • 잎 분할과 삭제 후 병합에서 키와 경계를 보존한다.

  • 동시성 보호와 충돌 후 복구를 별도 문제로 설명한다.

삭제로 빈자리가 생겼을 때 어느 경계까지 고쳐야 할까요?

분할은 새 잎 하나를 만드는 일로 끝나지 않습니다. 키가 어느 잎에 남는지와 부모 경계·잎 링크가 맞아야 다음 검색이 올바릅니다. 잎의 경계 키를 부모에 복사해도 실제 레코드 키는 잎에 남겨 둡니다.

아래는 비루트 잎 최소 두 키·최대 세 키인 자체 모형입니다. 삭제 뒤 부족하면 여유 있는 형제에서 빌리고, 빌릴 수 없으면 합칠 수 있는 크기인지 확인합니다. 이 즉시 복구 정책을 모든 실제 DB의 삭제 정책으로 일반화하지 않습니다.

공간 부족은 부모까지 전파될 수 있다

잎 [10,20,30]에 25를 넣으면 정렬한 [10,20,25,30]이 최대 3을 넘는다. 이 모형은 왼 [10,20]과 오른 [25,30]으로 나누고 부모에 오른 첫 키 25를 복사한다. 25는 잎에서 사라지지 않는다. 자식 포인터와 잎 링크도 새 구조에 맞춰 바꾼다.

부모도 꽉 차면 내부 분할이 위로 전파될 수 있고 루트 분할은 새 루트로 높이를 늘린다. 내부 분할은 탐색 경계를 위로 이동하는 규칙이어서 잎 레코드 복사와 구별한다. 구체 분할 위치·최소 개수는 구현마다 다르므로 종이 모형의 3을 실제 DB 페이지 한계로 쓰지 않는다.

점유율 복구와 실제 삭제 정책

위 두 잎에서 10을 지우면 왼 [20]은 최소 2보다 작다. 오른[25,30]도 최소 2라 하나를 빌리면 오른이 부족해진다. 이 모형에서는 [20,25,30]으로 병합하고 부모의 분리 키 25와 한 자식 포인터를 없앤다. 부모가 자식 하나의 루트이면 그 잎을 새 루트로 삼는다.

일반 교재는 빌리기·병합으로 최소 점유율을 유지할 수 있지만 실제 시스템은 다른 정책도 사용한다. Berkeley의 해당 입문 자료는 삭제 후 부족한 잎을 그대로 둘 수 있다고 설명하며 PostgreSQL은 별도 동시 삭제 절차를 쓴다. 여기서 선택한 즉시 병합을 그 시스템들의 실제 동작이라고 바꾸지 않는다.

정상 구조와 충돌 복구는 다른 보장이다

WAL은 데이터 페이지의 변경을 저장하기 전에 그 변경의 로그를 영구 저장한다. 충돌 때 페이지에 아직 반영하지 못한 변경을 REDO할 근거가 생긴다. 메모리 페이지의 latch는 동시 접근을 조절하지만 전원이 꺼진 뒤의 복구 기록을 대신하지 못한다.

실제 분할은 잎·링크·부모 등 여러 변경으로 나뉠 수 있다. PostgreSQL의 문서는 분할과 상위 포인터 삽입을 별도 WAL 단계로 기록하며 복구 중 상위 경로가 덜 갱신된 경우도 다룬다. 로그와 페이지 번호·적용 상태를 확인하는 실제 복구 프로토콜을 생략하고 모든 페이지가 한순간에 저장된다고 가정하지 않는다.

키 이동만 하고 부모 경계를 21로 두면 새 오른쪽의 18을 왼쪽으로 잘못 안내하게 됩니다. 점유율과 라우팅 경계를 함께 갱신해야 합니다.

로그가 메모리에 있는 것과 영구 저장된 것은 다릅니다

구조 변경에 필요한 로그의 끝이 LSN 300이고 안정적 WAL 끝은 290입니다. 변경 데이터 페이지를 저장하려 합니다. WAL 저장이 실패하거나 데이터 페이지 쓰기가 실패하는 경우를 구별하세요.

  1. 먼저 복구에 필요한 로그를 최소 LSN 300까지 안정적으로 저장해야 합니다. 메모리에서 생성한 것만으로 조건을 만족하지 않습니다.

  2. WAL 저장이 실패하면 변경 페이지를 새로 저장하지 않고 실패를 전달합니다.

  3. WAL 저장은 성공했지만 페이지 쓰기가 실패하면 저장되지 않은 변경을 복구할 기록은 남습니다. 다만 실제 복구는 해당 로그의 정의와 적용 프로토콜을 따라야 합니다.

성공 순서는 필요한 WAL의 안정적 저장 다음 데이터 페이지 저장입니다. WAL 실패 경로는 페이지 저장을 진행하지 않습니다. 페이지 실패 경로는 성공으로 보고하지 않고 복구·재시도 조건을 유지합니다.

비교할 점

로그가 있다는 이유로 임의의 여러 페이지 변경이 자동으로 일괄 원자적이라고 말할 수 없습니다. 어떤 변경을 어떤 로그로 다시 적용하는지까지 정해져 있어야 합니다.

오해와 반례

latch로 분할을 보호하면 로그 없이도 충돌 복구가 되고 삭제는 모든 DB가 바로 병합한다.

latch는 살아 있는 실행의 동시 접근 보호다. 영구 로그 없이 충돌하면 잎·부모 일부만 남을 수 있다. 즉시 병합은 이 교육 모형의 정책이며 실제 DB의 삭제 조건은 별도다.

소단원 5.3

페이지 latch와 구조 변경

부모가 가리킨 잎이 검색 도중 둘로 나뉘면 키가 없다고 결론 내도 될까?

준비 개념과 학습 목표

준비 개념

  • latch는 공유 메모리 페이지의 짧은 물리적 접근을 보호한다. 트랜잭션 lock의 논리적 데이터 격리와 목적·유지 시간이 다를 수 있다.

  • high key는 페이지 담당 범위의 상한, right-link는 오른쪽 형제 포인터다. pin은 버퍼 페이지의 교체를 제한하는 수명 관리이며 latch와 구별한다.

학습 목표

  • 중간 분할 상태의 잘못된 검색을 추적한다.

  • 짧은 페이지 보호와 범위 재검사의 역할을 나눈다.

안정된 한 페이지를 읽어도 검색 결과가 틀릴 수 있을까요?

페이지 latch는 읽는 동안 그 페이지의 키와 포인터가 반쯤 바뀐 상태를 보지 않도록 합니다. 그렇지만 도착한 페이지가 오래된 부모 경로가 안내한 페이지일 수 있습니다. 그 페이지의 범위를 검사하고 필요하면 유효한 오른쪽 링크로 이동해야 합니다.

점조회와 범위 스캔의 링크 사용도 같은 문제는 아닙니다. 이미 복사한 결과가 새 분할 페이지에 다시 나타날 수 있어 범위 스캔은 당시의 진행 위치를 기억해야 합니다. 아래는 삭제·재사용·추가 삽입 없이 기존 키만 분할되는 작은 안정 상태 모형입니다.

먼저 확인할 개념
  • 세마포어·조건변수·모니터

    여러 자원의 보호와 획득 순서가 진행 가능성에 미치는 영향을 연결합니다.

  • 캐시·직접 I/O·동시성

    프레임 참조의 수명과 상태 변경 보호를 구별하는 조건을 사용합니다.

안정된 페이지 한 장을 읽는다

공유 버퍼에서 키 배열과 포인터를 읽는 동안 다른 쓰기가 반만 반영되면 일관된 구조를 해석할 수 없다. read/write latch는 읽기 동안 페이지가 중간 상태로 바뀌지 않도록 보호하는 도구다. 실제 모드와 범위는 구현의 규칙으로 확인한다.

latch를 잡았다고 트랜잭션 전체의 격리가 자동 완성되지는 않는다. 읽은 레코드의 가시성·논리적 잠금은 다른 층의 문제다. 또한 pin이 있어 페이지 교체를 막아도 구조 쓰기를 막는 latch가 없으면 같은 보호라고 할 수 없다.

부모 경로가 오래되면 범위를 재검사한다

분할 후 부모가 아직 새 자식 포인터를 받지 못했다면 기존 왼 잎에 도착할 수 있다. B-link 방식은 페이지 high key를 검사하고 검색키가 담당 범위보다 크면 right-link를 따라 새 오른쪽으로 이동한다. 여러 분할이면 같은 검사를 반복할 수 있다.

이 단원의 단순 정수 모형은 왼 잎 [10,20]의 high key 20, right-link→오른[25,30]으로 정한다. 실제 PostgreSQL의 pivot·중복 정렬·경계 규칙은 더 복잡하다. 여기서는 30 검색이 20보다 커서 오른쪽으로 이동한다는 작은 예만 계산한다.

여러 페이지의 보호 순서도 설계한다

한 작업이 왼 페이지를 잡고 오른쪽을 기다리는 동안 다른 작업이 오른쪽을 잡고 왼쪽을 기다리면 순환 대기가 생긴다. latch가 존재한다는 사실만으로 진행이 보장되지 않는다. 페이지 획득 순서·재시도·해제 조건을 알고리즘에 맞춰 정해야 한다.

초보용 전역 latch로 모든 트리 변경과 검색을 직렬화하는 모형도 구조 중간 관찰을 막을 수 있지만 동시성이 줄어든다. 페이지별 보호나 right-link 설계는 성능과 복잡성의 절충이다. 실제 PostgreSQL을 전역 latch 모형이라고 부르거나 종이 증명으로 DB 부하 측정까지 완료했다고 표시하지 않는다.

  2. 새 현재 링크를 따라 S로 가면 25를 다시 복사하고 뒤에 Q의 35·45도 읽습니다.

  3. 당시에 기억한 Q로 가면 새 S의 25를 다시 읽지 않고 35·45를 이어 읽습니다.

현재 링크를 새로 따라가면 25를 중복 반환할 수 있습니다. 이 조건에서는 당시 다음 잎 Q를 기억한 진행이 기존 결과를 한 번씩 유지합니다.

같음은 이 모형에서 오른쪽 이동 조건이 아닙니다.

풀이와 답 확인

  1. 45>25이므로 P에서 Q로 이동합니다.

  2. 45는 Q의 high 45와 같으므로 Q의 키를 확인합니다.

  3. Q에 실제 45가 있으므로 반환합니다.

P→Q 경로에서 45를 찾습니다. R까지 이동할 필요는 없습니다.

연습 2 · 오류 찾아 고치기

작업 A는 페이지 번호 1의 latch를 잡고 번호 2를 기다립니다. 작업 B는 번호 2를 잡고 번호 1을 기다립니다. 각 latch는 배타적입니다. 대기 그래프와 원인을 구하세요.

힌트 1

누가 어떤 자원을 가진 상대를 기다리는지 표시합니다.

힌트 2

대기 방향이 원으로 이어지는지 확인합니다.

풀이와 답 확인

  1. A는 B가 가진 번호 2를 기다려 A→B입니다.

  2. B는 A가 가진 번호 1을 기다려 B→A입니다.

  3. 두 작업이 보유한 채 서로 기다리므로 A→B→A의 순환 대기가 생깁니다.

이 상태는 교착입니다. 페이지 내용을 보호하는 latch가 있어도 획득 순서가 반대이면 진행하지 못할 수 있습니다.

흔한 오답에서 다시 생각하기

두 페이지 모두 보호되니 작업도 반드시 끝납니다.

내용의 안전성과 작업이 진행하는 성질은 다릅니다. 보호된 채 영원히 기다리는 상태가 반례입니다.

연습 3 · 직접 만들어 보기

앞의 교착 모형에서 모든 작업이 번호가 작은 latch부터 얻도록 합니다. B는 아직 다른 작업에 보이지 않는 준비 단계에서 번호 2만 잡고 있습니다. 번호 1도 필요하다는 것을 알았을 때 안전한 재시도 순서를 구성하세요. 변경 데이터는 아직 없습니다.

힌트 1

큰 번호를 유지한 채 작은 번호를 기다리지 않습니다.

힌트 2

이미 변경한 자료가 없다는 조건을 사용합니다.

풀이와 답 확인

  1. B는 번호 2를 놓고 준비 상태를 취소합니다.

  2. B는 번호 1을 먼저 얻습니다. A가 번호 1을 가지고 있다면 다른 latch를 보유하지 않고 기다립니다.

  3. 번호 1을 얻은 뒤 번호 2를 얻고 필요한 상태를 다시 확인해 작업합니다.

B는 2를 놓고 1→2 순서로 다시 획득합니다. 이 단순 두 자원 모형에서는 순서 반전으로 생긴 순환 대기를 없앱니다. 실제 트리 알고리즘에 무조건 이 번호 순서를 적용한다는 뜻은 아닙니다.

흔한 오답에서 다시 생각하기

번호 2를 잡은 채 번호 1을 기다려도 나중에 순서를 기록하면 됩니다.

그 순간 이미 순서 규칙을 어겨 앞 교착을 다시 만들 수 있습니다. 실제 보유와 대기 순서가 규칙을 지켜야 합니다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

P의 pin만 얻고 latch 없이 키 배열과 high key를 읽습니다. 쓰기 작업이 두 필드를 각각 갱신하는 중입니다. pin이 1이라는 이유로 일관된 페이지와 올바른 트랜잭션 가시성을 모두 보장한다고 주장합니다. 빠진 보호를 설명하세요.

힌트 1

pin은 교체 수명을 보호하는 표시입니다.

힌트 2

페이지 구조와 논리적 레코드 가시성을 따로 봅니다.

풀이와 답 확인

  1. pin이 남았다는 사실은 해당 프레임을 교체하지 않는 조건이지 키 배열 수정 금지가 아닙니다.

  2. 페이지의 일관된 내용을 읽기 위해 정해진 latch 또는 다른 동등한 구조 보호가 필요합니다.

  3. 트랜잭션이 어떤 레코드 버전을 볼 수 있는지는 별도의 가시성·격리 규칙을 따라야 합니다.

pin만으로 구조 읽기나 트랜잭션 가시성까지 보장할 수 없습니다. 프레임 수명·페이지 내용·논리적 가시성을 분리해야 합니다.

흔한 오답에서 다시 생각하기

버퍼에 남아 있으므로 읽는 모든 값은 같은 시점의 확정 데이터입니다.

버퍼 수명은 데이터 버전과 같은 표시가 아닙니다. 동시에 수정되는 내용과 트랜잭션 규칙을 별도로 보호해야 합니다.
