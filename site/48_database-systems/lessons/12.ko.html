소단원 12.1

optimistic control

친구와 같은 값을 수정하되 끝에서만 충돌을 검사하면 어떻게 될까?

준비 개념과 학습 목표

준비 개념

  • 트랜잭션과 commit

  • 읽기-계산-쓰기

  • 값과 버전

학습 목표

  • private 작업과 공개 commit을 구별한다.

  • 읽은 버전의 검증 실패와 재시도를 추적한다.

  • 검증과 설치를 원자적으로 묶어야 하는 이유를 설명한다.

값이 원래 숫자로 돌아왔어도 읽은 버전은 여전히 유효한가요?

고정된 점 key만 사용하는 자체 낙관적 모형입니다. 모든 writer는 기존 값과 단조 증가 버전을 함께 읽고 변경 결과는 private에 둡니다. 성공 commit은 하나의 공통 임계구역에서 모든 읽기 버전을 검사하고 값 설치·버전 증가까지 마칩니다. 값과 버전은 원자적으로 함께 읽습니다. 쓰기 대상 key의 기존 버전도 읽기 집합에 포함하며, 같은 key를 다시 읽을 때 버전이 달라지면 즉시 실패 처리합니다.

키 추가·삭제·범위 검색·외부 효과는 제외합니다. 버전 검사 없이 값만 비교하거나 검사와 설치를 분리하면 이 계약이 깨집니다. 실패 뒤에는 새 값을 읽고 계산부터 다시 합니다. 아래 수치는 실제 동시 DB 실행 로그가 아닙니다.

먼저 확인할 개념
  • 직렬가능성·복구가능성

    성공 commit 순서의 직렬화와 실패 결과의 공개 여부를 구별합니다.

  • 병렬 실행·취소

    실패한 private 작업을 완료 결과로 공개하지 않습니다.

먼저 계산하고 끝에서 검사한다

낙관적 제어는 충돌이 적을 수 있다는 기대 아래 작업을 진행하고 공개 전에 유효성을 검사한다. 읽은 항목의 read set과 바꿀 항목의 write set을 기록하고 쓰기 결과를 private 영역에 둔다. 충돌이 발견되면 결과를 공개하지 않고 abort하거나 다시 계산한다.

검사 자체와 버전 기록도 비용이다. 충돌이 잦으면 오래 계산한 작업을 버려야 하므로 낙관적이라는 이름이 항상 빠르다는 결론을 주지 않는다. CMU 강의는 read·validation·write 단계와 직렬 검증의 critical section을 설명한다.

점 key만 다루는 자체 버전 모형

이 모형은 미리 존재하는 key만 읽고 쓰며 모든 writer가 같은 규칙을 따른다. 값과 단조 증가 버전을 원자적으로 읽고 각 읽은 key의 버전을 기록한다. 같은 key를 다시 읽어 버전이 달라졌거나 commit 검사에서 다르면 abort한다. 모든 write key도 기존 버전을 먼저 읽도록 제한한다. 범위 검색·새 key·삭제·외부 효과는 제외한다.

commit은 하나의 직렬 critical section에서 모든 read key의 현재 버전을 비교하고 모두 같을 때만 private 값을 설치하며 버전을 증가시킨다. 검사와 설치 사이에 다른 commit을 허용하지 않는다. 이 제한 아래 성공한 작업의 읽기 상태는 설치 직전의 상태와 일치하므로 commit 순서로 직렬화할 수 있다.

실패 뒤에는 옛 결과를 재사용하지 않는다

충돌 뒤 같은 업무를 다시 수행하려면 새로운 값을 읽고 판단·계산부터 다시 한다. 옛 값으로 만든 결과를 새 버전 번호만 붙여 쓰면 잃어버린 갱신을 다시 만들 수 있다. 업무 밖의 메일 같은 효과는 이 private/commit 모형에 들어 있지 않다.

범위의 빈 결과를 읽었는데 다른 작업이 새 행을 삽입하는 phantom은 기존 key 버전 표만으로 검출하지 못한다. 범위·predicate 기록이나 다른 검증 방식이 필요하다. 교육용 점 key 모형을 실제 DB 전체의 serializable 구현과 같다고 부르지 않는다.

공개 값과 버전은 같은 사건 경계에서 갱신합니다. private 12를 공개된 성공 결과와 혼동하지 않습니다.

중간 과정을 따라가는 예제

x=(값 10, 버전 1), y=(20,1)이다. A와 B는 각각 x를 읽고 +1 결과를 private에 둔다. A가 먼저 commit하고 B가 뒤에 검사한다. 그 뒤 B가 업무 전체를 재시도한다.

  1. A와 B의 읽기 버전은 모두 1이고 private 결과는 11이다. A 검사에서 현재 x 버전 1이 같아 x=(11,2)를 설치한다.

  2. B 검사에서는 기록 1과 현재 2가 달라 abort한다. private 11은 공개되지 않는다. 이때 x는 여전히 (11,2)다.

  3. B가 새 x=(11,2)를 읽어 +1을 재계산한다. 다른 commit이 없으면 검사 통과 후 x=(12,3)를 설치한다.

첫 B 시도는 실패하며 재시도 뒤 값은 12, 버전은 3이다. 버전 검사와 설치가 원자적이고 모든 writer가 참여한다는 자체 가정이 필요하다.

조건을 바꾸어 비교하기

실패 재시도는 값을 다시 읽습니다

표의 B가 실패 뒤 같은 +2 업무를 다시 수행합니다. 다른 commit은 없다고 정합니다. 최종 상태를 구하세요.

  1. B의 첫 private 12는 버립니다.

  2. 새 값 12·버전 5를 읽고 private 14를 계산합니다.

  3. 검사와 설치를 같은 임계구역에서 마쳐 값 14·버전 6으로 갱신합니다.

두 성공 증가 뒤 값은 14이고 버전은 6입니다.

비교할 점

버전 5만 읽고 옛 private 12를 다시 설치하면 증가 하나를 잃습니다.

같은 값으로 돌아온 변경도 검출합니다

별도 T가 값 10·버전 4를 읽었습니다. 그 뒤 다른 두 성공 writer가 값 20·버전 5, 이어 값 10·버전 6을 설치합니다. T의 commit 검사는?

  1. 현재 값 10은 옛 값 10과 같습니다.

  2. 현재 버전 6은 읽기 버전 4와 다릅니다.

  3. 명시한 검사는 T를 abort합니다.

이 모형은 값이 같아도 읽기 이후에 발생한 중간 변경을 버전 차이로 검출하고 T를 abort합니다.

비교할 점

이를 유한 폭 버전이 무한 시간 동안 재사용되지 않는다는 실제 보장으로 바꾸지 않습니다.

종이와 본문으로 직접 해보기

C는 y=(20,1)만 읽어 +2 결과를 준비했다. A의 x 갱신 뒤 C는 통과하는가? 별도 반례에서 A/B가 모두 검사만 먼저 통과하고 나중에 각각 옛 결과 11을 설치하면 최종 값은?

힌트 보기

C의 read set에 x가 없다. 둘째 질문에서는 critical section 가정을 제거했다.

풀이 보기

y 버전이 그대로라면 C는 통과하여 y=(22,2)가 된다. 검사와 설치를 분리한 반례에서는 A/B가 모두 11을 써 최종 11이 될 수 있다. 읽기 검사를 했다는 사실만으로 두 증가를 보존하지 못했다.

오해와 반례

commit 직전에 한번 버전을 확인하기만 하면 그 뒤 쓰기는 따로 해도 안전하다.

검사 후 설치 전 다른 commit이 끼면 판단 근거가 바뀐다. 검증과 공개 설치의 원자적 경계, read/write 기록의 범위가 함께 필요하다.

연습 1 · 값과 상태 예측

x를 읽은 A가 commit한 뒤, C는 y의 값 20·버전 8만 읽어 +3을 계산했습니다. y에는 다른 변경이 없고 C의 read set은 {y}입니다. C가 설치하는 상태는?

힌트 1

x는 C의 검사 집합에 없습니다.

힌트 2

해당 key의 버전만 올립니다.

풀이와 답 확인

  1. y의 현재 버전 8이 기록과 같습니다.

  2. C는 값 23·버전 9를 설치합니다.

정의한 모형에서 C는 성공하여 y가 23·버전 9가 됩니다.

연습 2 · 오류 찾아 고치기

A와 B가 모두 x=10을 읽고 private 12를 계산했습니다. 검사만 각각 버전 4에서 통과한 뒤 공통 임계구역 밖에서 두 설치를 허용합니다. +2 두 번의 값이 보존되나요?

힌트 1

둘은 모두 같은 옛 private 값을 씁니다.

힌트 2

버전을 올려도 옛 계산이 새 계산으로 바뀌지 않습니다.

풀이와 답 확인

  1. 두 설치 모두 값 12를 쓰므로 최종 값이 12일 수 있습니다.

  2. 정상 두 성공 증가의 기대 값 14와 다릅니다.

  3. 검사와 설치를 공통 임계구역에서 묶어야 합니다.

검사만 통과했다는 사실로 안전하지 않습니다. 버전 증가의 세부 경쟁과 별개로 값 갱신을 잃을 수 있습니다.

버전 검사는 설치 전에 한 번만 하면 충분합니다.

검사 근거가 설치까지 유지되도록 원자적 경계를 보장합니다.

힌트 1

한 항목만 통과하면 충분한지 봅니다.

힌트 2

모든 read key를 검사합니다.

풀이와 답 확인

  1. x의 현재 버전은 R이 기록한 것과 다릅니다.

  2. R의 전체 read set 검사 중 하나라도 다르면 private 결과를 공개하지 않고 실패합니다.

R은 실패하고 새 읽기와 판단으로 재시도합니다.

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

힌트 1

모든 중간 변경을 보려면 번호 재사용을 생각합니다.

힌트 2

시간 범위와 살아 있는 관찰자를 확인합니다.

풀이와 답 확인

  1. 단순 비교는 옛 0과 새 0을 같다고 보아 변경을 놓칩니다.

  2. 원래 단조 증가·읽기 수명 동안 재사용 없음 가정을 위반했습니다.

  3. 세대의 폭만 늘리는 것과 재사용 수명 계약을 보장하는 것은 구별합니다.

유한 버전 순환에서는 이 원래 증명을 그대로 사용할 수 없습니다. 실제 구현의 재사용 보호가 필요합니다.

범위의 빈 결과도 점 key 검사로 검출하나요?

설명 기준 확인

없는 key와 조건 집합이 기록 범위 밖이면 삽입을 놓칩니다. 범위 검증을 추가해야 합니다.

한 단계 더

x/y 두 key에서 read set {x}, {y}, {x,y}를 가진 세 작업을 표로 만들고 앞 작업의 write set과 만나는 경우를 표시하자. 교집합이 있다는 이유만으로 모든 알고리즘이 같은 시점에 반드시 abort한다고 일반화하지 말고 이 모형의 현재 버전 검사 결과를 계산하자.

옛 거래를 보던 화면이 새 commit 뒤에도 같은 값을 보여 주어야 할까?

고정된 스냅샷과 자신의 private 쓰기는 같은 가시성 규칙인가요?

자체 committed 버전은 [시작,끝)의 반열린 구간으로 표시합니다. snapshot s에 시작≤s<끝인 버전을 고릅니다. 다른 트랜잭션의 미커밋 값은 보이지 않으며 자신의 쓰기는 별도 규칙으로 읽습니다. 이 숫자는 실제 PostgreSQL XID 인코딩이 아닙니다.

PostgreSQL의 일반 Read Committed SELECT는 문장별 스냅샷, Repeatable Read는 첫 비제어 문장이 정한 스냅샷을 유지하면서 자기 쓰기도 봅니다. 다른 행 쓰기가 동시에 성공할 수 있는 자체 SI 모형은 직렬가능성을 자동 보장하지 않습니다.

    일관된 가시성만으로 직렬 동치가 되는지 따로 검사합니다.

  • predicate·range lock

값 하나 대신 버전 여러 개

MVCC는 이전 읽기와 새 쓰기를 함께 지원하려고 여러 버전을 관리한다. 자체 단순 모형은 성공한 commit에 증가하는 시점을 부여하고 committed 버전의 유효 구간을 [시작,끝)으로 적는다. snapshot s에서는 시작≤s<끝인 버전을 읽는다. 실제 DB의 transaction ID와 가시성 판단은 더 복잡하다.

미완료 writer의 private 값은 다른 reader에게 공개하지 않는다. 자신의 이전 쓰기는 자기 읽기에 보이도록 별도 규칙을 둘 수 있다. PostgreSQL은 이 규칙과 격리 수준에 따른 snapshot을 문서화한다. MVCC라고 모든 잠금과 쓰기 충돌이 사라지는 것은 아니다.

어떤 시점의 snapshot인가

PostgreSQL Read Committed의 일반 SELECT는 문장이 시작될 때의 committed 상태를 본다. 같은 transaction의 두 문장 사이 다른 commit이 있으면 결과가 달라질 수 있다. Repeatable Read는 첫 비제어 문장이 정한 transaction snapshot을 이후에도 유지하며 자신의 변경도 본다.

고정 snapshot에서 읽은 옛 버전을 기반으로 이미 다른 transaction이 바꾼 행을 갱신하려면 충돌로 실패할 수 있다. 성공 조건과 재시도 정책은 DB 격리 계약에 따라 확인한다. transaction을 다시 시도할 때는 의사결정에 사용한 읽기도 다시 해야 한다.

같은 화면을 보는 것과 직렬 실행은 다르다

자체 snapshot isolation 모형은 모두 같은 committed snapshot을 읽되 동일 행의 동시 쓰기는 충돌시키고 다른 행 쓰기는 허용한다. 두 작업이 서로의 다른 행을 읽고 각자 자기 행을 바꾸면 write skew가 가능하다. 행별 쓰기 충돌이 없다는 이유로 업무 불변식이 유지되지는 않는다.

PostgreSQL Serializable은 snapshot 위의 serialization 이상을 검출하는 추가 제어를 사용하며 실패한 전체 transaction의 재시도를 준비해야 한다. 아래 반례는 제한한 SI 모형의 분석이고 실제 DB의 관찰 실험은 아니다.

중간 과정을 따라가는 예제

x의 committed 버전은 값 5의 [2,7), 값 9의 [7,∞)이다. snapshot 6과 7에서 값을 고르자. 별도 두 담당자 A/B는 당직 값 (a,b)=(1,1)을 snapshot으로 읽고 적어도 하나는 1이어야 한다는 규칙 아래 상대가 1이면 자기 값을 0으로 바꾼다.

  1. snapshot 6은 2≤6<7이므로 5다. snapshot 7은 옛 끝 7을 포함하지 않고 새 시작 7을 포함하므로 9다. private 값 13이 있어도 다른 reader는 이를 고르지 않는다.

  2. SI 반례에서 A는 b=1을 보고 a=0을 쓰고 B는 a=1을 보고 b=0을 쓴다. 서로 다른 행 쓰기이므로 이 모형의 동일 행 충돌 규칙은 두 commit을 허용한다.

  3. 최종 (0,0)은 a+b≥1을 위반한다. A 뒤 B를 실제 직렬 실행하면 B는 a=0을 읽어 자기 b=1을 유지하므로 (0,1)이 된다.

가시 값은 5와 9다. 별도 SI 반례는 (0,0)을 만들 수 있지만 해당 업무의 직렬 결과와 다르다.

조건을 바꾸어 비교하기

문장별과 고정된 읽기를 비교합니다

자기 쓰기가 없는 reader의 첫 SELECT는 s=4, 두 번째는 s=10입니다. 문장별 모형과 고정 snapshot 4 모형을 비교하세요.

  1. 문장별 첫 읽기는 값 4이고 두 번째는 값 12입니다.

  2. 고정 snapshot 4에서는 두 읽기 모두 값 4입니다.

  3. 다른 writer의 private 99는 어느 committed 선택에도 사용하지 않습니다.

문장별 snapshot에서는 첫 SELECT가 값 4를 읽고 두 번째 SELECT가 값 12를 읽습니다. snapshot 4를 고정하면 두 SELECT가 모두 값 4를 읽습니다.

비교할 점

고정 읽기에서 자기 쓰기가 있는 경우도 옛 값만 읽는다고 일반화하지 않습니다.

같은 두 상태를 읽어도 업무 규칙이 깨집니다

두 담당자의 당직 값은 a=1,b=1이고 a+b≥1이어야 합니다. A와 B는 같은 snapshot을 읽고 상대가 1이면 자기 행을 0으로 바꿉니다. 자체 SI는 같은 행의 동시 쓰기만 충돌시킵니다.

  1. A는 b=1을 보고 a=0을 씁니다. B는 a=1을 보고 b=0을 씁니다.

  2. 서로 다른 행이라 모형은 두 성공 commit을 허용하여 (0,0)이 됩니다.

  3. A 다음 B의 직렬 실행에서는 B가 a=0을 보고 b=1을 유지합니다. B 다음 A에서는 a=1을 유지합니다.

동시 결과 (0,0)은 두 직렬 결과 (0,1)과 (1,0) 중 어느 것과도 같지 않습니다.

비교할 점

PostgreSQL Serializable의 추가 탐지와 실제 실패자를 이 자체 SI 모형의 성공 기록으로 대신하지 않습니다.

오해와 반례

모든 읽기가 같은 snapshot을 사용하면 서로 다른 행에 쓴 결과도 항상 serializable이다.

당직 반례는 같은 (1,1)을 읽고 다른 행을 바꿔 (0,0)이 된다. 업무의 읽기-쓰기 의존성과 추가 충돌 제어가 필요하다.

학습 목표

  • 오래 읽는 snapshot이 요구하는 버전을 찾는다.

  • 보수적인 회수 경계와 실제 가시성을 구별한다.

  • 공간 회수·물리 해제·동시 충돌의 범위를 설명한다.

현재 아무도 읽지 않는 버전도 보수적 경계에서는 남을 수 있나요?

자체 회수 모형은 모든 활성 reader의 snapshot을 안정적으로 등록하고 새 reader는 현재 이후의 snapshot만 사용합니다. 과거 조회·backup·replica·추가 retention은 제외합니다. 구간 끝 e≤활성 최솟값 H이면 논리 회수 후보로 표시합니다.

후보 표시는 물리 해제 완료가 아닙니다. reader가 기존 포인터·페이지 참조를 유지하는 수명 계약도 지켜야 합니다. PostgreSQL 표준 VACUUM의 내부 재사용과 OS 파일 반환도 구별합니다. 회수는 업무 충돌 검증을 대신하지 않습니다.

먼저 확인할 개념
  • Bloom filter와 선택성

    버전이 다른 저장 내용과 요약·참조 수명 조건을 혼동하지 않습니다.

  • 병렬 실행·취소

    참조를 가진 작업의 실제 종료 뒤 물리 자원을 반환하는 조건을 이어 봅니다.

옛 버전도 현재 reader에게 필요하다

MVCC의 이전 버전은 최신 값이 아니어도 활성 transaction의 snapshot에 보일 수 있다. reader가 필요한 버전을 지우면 그 reader의 격리 계약을 깨뜨린다. 오래 유지되는 snapshot은 필요한 이전 버전과 공간의 수명을 늘릴 수 있다.

자체 모형은 모든 활성 reader의 snapshot을 안정적으로 등록하고 앞으로 시작할 reader는 현재 이후 시점만 사용한다. 과거 조회·backup·replica·추가 retention은 제외한다. 실제 DB는 이런 추가 보존 조건도 확인해야 한다.

보수적인 경계로 회수 후보 고르기

활성 snapshot의 최솟값을 H라고 하자. committed 버전의 끝 e가 e≤H이면 모든 활성 snapshot은 그 버전의 [시작,e)에 들어가지 않는다. 이 모형에서는 해당 버전을 논리적 회수 후보로 표시할 수 있다. 최신 끝 ∞인 버전은 이 규칙으로 제거하지 않는다.

끝이 H보다 크다고 반드시 어떤 reader가 현재 사용한다는 뜻은 아니다. 이 검사는 안전한 후보만 쉽게 찾는 보수적 규칙이다. 등록·회수 경계가 서로 경쟁하면 새 reader를 놓칠 수 있으므로 안정된 snapshot 등록 가정이 중요하다.

후보 삭제와 물리 공간 반환의 차이

논리적으로 불필요한 버전이어도 동시 reader가 보유한 pointer나 page 참조를 안전하게 처리한 뒤 물리 해제를 해야 한다. timestamp 비교만으로 메모리 해제의 race까지 해결했다고 할 수 없다. 실제 storage 관리·latch·reader 보호 조건을 따로 확인한다.

PostgreSQL 표준 VACUUM은 사용하지 않는 버전 공간을 내부 재사용 가능하게 만드는 것이 기본이며 보통 파일을 줄여 OS로 모두 반환하지 않는다. 일부 끝 페이지 반환 조건과 VACUUM FULL의 복사·추가 공간·강한 잠금은 구별한다. GC가 write skew 검출이나 transaction serializability를 대신하는 것도 아니다.

    실제 표시 줄62–66과 별도 재조회 줄90–104, 줄109–144의 문장/transaction snapshot·자기 쓰기·동시 갱신 실패·SI 이상·SSI와 재시도를 읽었다. 숫자 시점 구간과 당직 모형은 자체 설명이며 내부 XID 인코딩 또는 실행 로그가 아니다.

  • PostgreSQL 18 — Routine Vacuuming

    실제 표시 본문 줄28–52의 오래된 버전 보존·표준 내부 재사용·끝 페이지 조건·FULL의 복사와 공간·강한 잠금을 읽었다. 단순 e≤H와 포인터 수명은 자체 회수 모형이며 실제 VACUUM을 수행하지 않았다.

초기 x 값 10·버전 4에서 A가 +2를 설치하면 값 12·버전 5입니다. B 첫 검사는 기록 4와 현재 5가 달라 실패하고 새 읽기·재계산 뒤 값 14·버전 6을 설치합니다. 값이 10으로 돌아와도 버전 6은 옛 4와 다릅니다. y 값 20·버전 8만 읽은 독립 C의 +3은 값 23·버전 9가 됩니다. 검사와 설치를 분리하면 두 private 12 설치가 값 14를 보존하지 못합니다. 두 비트 버전 네 번 순환은 옛 0과 새 0의 식별 실패를 만듭니다. committed x의 snapshot 4는 값 4, snapshot 5와 8은 값 8, snapshot 9와 10은 값 12입니다. 문장별 읽기 시점 4와 10은 값 4 뒤 12, 고정 snapshot 4는 값 4 뒤 4입니다. 자기 private 쓰기 6은 명시한 자기 읽기 규칙에서 6으로 보입니다. 당직 자체 SI 동시 결과는 (0,0)이고 직렬 두 순서는 (0,1)과 (1,0)입니다. 회수 표의 snapshot 6은 값 5, snapshot 11은 값 9입니다.
