소단원 12.1

optimistic control

친구와 같은 값을 수정하되 끝에서만 충돌을 검사하면 어떻게 될까?

준비 개념과 학습 목표

준비 개념

  • 트랜잭션과 commit

  • 읽기-계산-쓰기

  • 값과 버전

학습 목표

  • private 작업과 공개 commit을 구별한다.

  • 읽은 버전의 검증 실패와 재시도를 추적한다.

  • 검증과 설치를 원자적으로 묶어야 하는 이유를 설명한다.

먼저 계산하고 끝에서 검사한다

낙관적 제어는 충돌이 적을 수 있다는 기대 아래 작업을 진행하고 공개 전에 유효성을 검사한다. 읽은 항목의 read set과 바꿀 항목의 write set을 기록하고 쓰기 결과를 private 영역에 둔다. 충돌이 발견되면 결과를 공개하지 않고 abort하거나 다시 계산한다.

검사 자체와 버전 기록도 비용이다. 충돌이 잦으면 오래 계산한 작업을 버려야 하므로 낙관적이라는 이름이 항상 빠르다는 결론을 주지 않는다. CMU 강의는 read·validation·write 단계와 직렬 검증의 critical section을 설명한다.

점 key만 다루는 자체 버전 모형

이 모형은 미리 존재하는 key만 읽고 쓰며 모든 writer가 같은 규칙을 따른다. 값과 단조 증가 버전을 원자적으로 읽고 각 읽은 key의 버전을 기록한다. 같은 key를 다시 읽어 버전이 달라졌거나 commit 검사에서 다르면 abort한다. 모든 write key도 기존 버전을 먼저 읽도록 제한한다. 범위 검색·새 key·삭제·외부 효과는 제외한다.

commit은 하나의 직렬 critical section에서 모든 read key의 현재 버전을 비교하고 모두 같을 때만 private 값을 설치하며 버전을 증가시킨다. 검사와 설치 사이에 다른 commit을 허용하지 않는다. 이 제한 아래 성공한 작업의 읽기 상태는 설치 직전의 상태와 일치하므로 commit 순서로 직렬화할 수 있다.

실패 뒤에는 옛 결과를 재사용하지 않는다

충돌 뒤 같은 업무를 다시 수행하려면 새로운 값을 읽고 판단·계산부터 다시 한다. 옛 값으로 만든 결과를 새 버전 번호만 붙여 쓰면 잃어버린 갱신을 다시 만들 수 있다. 업무 밖의 메일 같은 효과는 이 private/commit 모형에 들어 있지 않다.

범위의 빈 결과를 읽었는데 다른 작업이 새 행을 삽입하는 phantom은 기존 key 버전 표만으로 검출하지 못한다. 범위·predicate 기록이나 다른 검증 방식이 필요하다. 교육용 점 key 모형을 실제 DB 전체의 serializable 구현과 같다고 부르지 않는다.

중간 과정을 따라가는 예제

x=(값 10, 버전 1), y=(20,1)이다. A와 B는 각각 x를 읽고 +1 결과를 private에 둔다. A가 먼저 commit하고 B가 뒤에 검사한다. 그 뒤 B가 업무 전체를 재시도한다.

  1. A와 B의 읽기 버전은 모두 1이고 private 결과는 11이다. A 검사에서 현재 x 버전 1이 같아 x=(11,2)를 설치한다.

  2. B 검사에서는 기록 1과 현재 2가 달라 abort한다. private 11은 공개되지 않는다. 이때 x는 여전히 (11,2)다.

  3. B가 새 x=(11,2)를 읽어 +1을 재계산한다. 다른 commit이 없으면 검사 통과 후 x=(12,3)를 설치한다.

첫 B 시도는 실패하며 재시도 뒤 값은 12, 버전은 3이다. 버전 검사와 설치가 원자적이고 모든 writer가 참여한다는 자체 가정이 필요하다.

종이와 본문으로 직접 해보기

C는 y=(20,1)만 읽어 +2 결과를 준비했다. A의 x 갱신 뒤 C는 통과하는가? 별도 반례에서 A/B가 모두 검사만 먼저 통과하고 나중에 각각 옛 결과 11을 설치하면 최종 값은?

힌트 보기

C의 read set에 x가 없다. 둘째 질문에서는 critical section 가정을 제거했다.

풀이 보기

y 버전이 그대로라면 C는 통과하여 y=(22,2)가 된다. 검사와 설치를 분리한 반례에서는 A/B가 모두 11을 써 최종 11이 될 수 있다. 읽기 검사를 했다는 사실만으로 두 증가를 보존하지 못했다.

오해와 반례

commit 직전에 한번 버전을 확인하기만 하면 그 뒤 쓰기는 따로 해도 안전하다.

검사 후 설치 전 다른 commit이 끼면 판단 근거가 바뀐다. 검증과 공개 설치의 원자적 경계, read/write 기록의 범위가 함께 필요하다.

존재하지 않았던 key와 predicate는 기록 범위 밖이다.

한 단계 더

x/y 두 key에서 read set {x}, {y}, {x,y}를 가진 세 작업을 표로 만들고 앞 작업의 write set과 만나는 경우를 표시하자. 교집합이 있다는 이유만으로 모든 알고리즘이 같은 시점에 반드시 abort한다고 일반화하지 말고 이 모형의 현재 버전 검사 결과를 계산하자.

소단원 12.2

버전 가시성·snapshot

옛 거래를 보던 화면이 새 commit 뒤에도 같은 값을 보여 주어야 할까?

준비 개념과 학습 목표

준비 개념

  • commit과 미완료 쓰기

  • 시점과 반열린 구간

  • 격리 수준

학습 목표

  • snapshot 시점에 따른 가시 버전을 고른다.

  • 문장 snapshot과 고정 transaction snapshot을 구별한다.

  • snapshot isolation과 serializable의 차이를 반례로 설명한다.

값 하나 대신 버전 여러 개

MVCC는 이전 읽기와 새 쓰기를 함께 지원하려고 여러 버전을 관리한다. 자체 단순 모형은 성공한 commit에 증가하는 시점을 부여하고 committed 버전의 유효 구간을 [시작,끝)으로 적는다. snapshot s에서는 시작≤s<끝인 버전을 읽는다. 실제 DB의 transaction ID와 가시성 판단은 더 복잡하다.

미완료 writer의 private 값은 다른 reader에게 공개하지 않는다. 자신의 이전 쓰기는 자기 읽기에 보이도록 별도 규칙을 둘 수 있다. PostgreSQL은 이 규칙과 격리 수준에 따른 snapshot을 문서화한다. MVCC라고 모든 잠금과 쓰기 충돌이 사라지는 것은 아니다.

어떤 시점의 snapshot인가

PostgreSQL Read Committed의 일반 SELECT는 문장이 시작될 때의 committed 상태를 본다. 같은 transaction의 두 문장 사이 다른 commit이 있으면 결과가 달라질 수 있다. Repeatable Read는 첫 비제어 문장이 정한 transaction snapshot을 이후에도 유지하며 자신의 변경도 본다.

고정 snapshot에서 읽은 옛 버전을 기반으로 이미 다른 transaction이 바꾼 행을 갱신하려면 충돌로 실패할 수 있다. 성공 조건과 재시도 정책은 DB 격리 계약에 따라 확인한다. transaction을 다시 시도할 때는 의사결정에 사용한 읽기도 다시 해야 한다.

같은 화면을 보는 것과 직렬 실행은 다르다

자체 snapshot isolation 모형은 모두 같은 committed snapshot을 읽되 동일 행의 동시 쓰기는 충돌시키고 다른 행 쓰기는 허용한다. 두 작업이 서로의 다른 행을 읽고 각자 자기 행을 바꾸면 write skew가 가능하다. 행별 쓰기 충돌이 없다는 이유로 업무 불변식이 유지되지는 않는다.

PostgreSQL Serializable은 snapshot 위의 serialization 이상을 검출하는 추가 제어를 사용하며 실패한 전체 transaction의 재시도를 준비해야 한다. 아래 반례는 제한한 SI 모형의 분석이고 실제 DB의 관찰 실험은 아니다.

중간 과정을 따라가는 예제

x의 committed 버전은 값 5의 [2,7), 값 9의 [7,∞)이다. snapshot 6과 7에서 값을 고르자. 별도 두 담당자 A/B는 당직 값 (a,b)=(1,1)을 snapshot으로 읽고 적어도 하나는 1이어야 한다는 규칙 아래 상대가 1이면 자기 값을 0으로 바꾼다.

  1. snapshot 6은 2≤6<7이므로 5다. snapshot 7은 옛 끝 7을 포함하지 않고 새 시작 7을 포함하므로 9다. private 값 13이 있어도 다른 reader는 이를 고르지 않는다.

  2. SI 반례에서 A는 b=1을 보고 a=0을 쓰고 B는 a=1을 보고 b=0을 쓴다. 서로 다른 행 쓰기이므로 이 모형의 동일 행 충돌 규칙은 두 commit을 허용한다.

  3. 최종 (0,0)은 a+b≥1을 위반한다. A 뒤 B를 실제 직렬 실행하면 B는 a=0을 읽어 자기 b=1을 유지하므로 (0,1)이 된다.

가시 값은 5와 9다. 별도 SI 반례는 (0,0)을 만들 수 있지만 해당 업무의 직렬 결과와 다르다.

종이와 본문으로 직접 해보기

문장 snapshot 모형에서 첫 SELECT가 시점 6, 다른 commit이 7, 둘째 SELECT가 시점 8이면 두 값은? 고정 snapshot 6이면? 당직 모형에서 B가 A commit 후의 새 snapshot을 읽으면?

힌트 보기

자신의 쓰기는 없다고 가정한다. B는 상대 a가 1일 때만 떠난다.

풀이 보기

문장별로는 5 뒤 9, 고정 snapshot 6이면 5 뒤 5다. B가 새 a=0을 보면 떠나지 않아 b=1을 유지한다. 이는 snapshot을 언제 잡는지 바꾼 별도 이력이다.

오해와 반례

모든 읽기가 같은 snapshot을 사용하면 서로 다른 행에 쓴 결과도 항상 serializable이다.

당직 반례는 같은 (1,1)을 읽고 다른 행을 바꿔 (0,0)이 된다. 업무의 읽기-쓰기 의존성과 추가 충돌 제어가 필요하다.

소단원 12.3

garbage collection·충돌

가장 최신 값만 남기면 저장 공간을 바로 비워도 될까?

준비 개념과 학습 목표

준비 개념

  • 버전 구간

  • 활성 snapshot

  • 논리 삭제와 메모리 해제

학습 목표

  • 오래 읽는 snapshot이 요구하는 버전을 찾는다.

  • 보수적인 회수 경계와 실제 가시성을 구별한다.

  • 공간 회수·물리 해제·동시 충돌의 범위를 설명한다.

옛 버전도 현재 reader에게 필요하다

MVCC의 이전 버전은 최신 값이 아니어도 활성 transaction의 snapshot에 보일 수 있다. reader가 필요한 버전을 지우면 그 reader의 격리 계약을 깨뜨린다. 오래 유지되는 snapshot은 필요한 이전 버전과 공간의 수명을 늘릴 수 있다.

자체 모형은 모든 활성 reader의 snapshot을 안정적으로 등록하고 앞으로 시작할 reader는 현재 이후 시점만 사용한다. 과거 조회·backup·replica·추가 retention은 제외한다. 실제 DB는 이런 추가 보존 조건도 확인해야 한다.

보수적인 경계로 회수 후보 고르기

활성 snapshot의 최솟값을 H라고 하자. committed 버전의 끝 e가 e≤H이면 모든 활성 snapshot은 그 버전의 [시작,e)에 들어가지 않는다. 이 모형에서는 해당 버전을 논리적 회수 후보로 표시할 수 있다. 최신 끝 ∞인 버전은 이 규칙으로 제거하지 않는다.

끝이 H보다 크다고 반드시 어떤 reader가 현재 사용한다는 뜻은 아니다. 이 검사는 안전한 후보만 쉽게 찾는 보수적 규칙이다. 등록·회수 경계가 서로 경쟁하면 새 reader를 놓칠 수 있으므로 안정된 snapshot 등록 가정이 중요하다.

후보 삭제와 물리 공간 반환의 차이

논리적으로 불필요한 버전이어도 동시 reader가 보유한 pointer나 page 참조를 안전하게 처리한 뒤 물리 해제를 해야 한다. timestamp 비교만으로 메모리 해제의 race까지 해결했다고 할 수 없다. 실제 storage 관리·latch·reader 보호 조건을 따로 확인한다.

PostgreSQL 표준 VACUUM은 사용하지 않는 버전 공간을 내부 재사용 가능하게 만드는 것이 기본이며 보통 파일을 줄여 OS로 모두 반환하지 않는다. 일부 끝 페이지 반환 조건과 VACUUM FULL의 복사·추가 공간·강한 잠금은 구별한다. GC가 write skew 검출이나 transaction serializability를 대신하는 것도 아니다.

중간 과정을 따라가는 예제

x 버전은 3@[1,4), 5@[4,8), 7@[8,12), 9@[12,∞)이다. 활성 snapshot은 6과 10이다. 현재 시점은 12 이상이며 reader 등록이 안정적이다. 필요한 버전과 H 규칙의 회수 후보를 찾자.

  1. snapshot 6은 값 5, snapshot 10은 값 7을 본다. 최신 값 9도 새 reader를 위해 남긴다. 가장 오래된 값 3은 두 활성 snapshot에 보이지 않는다.

  2. H=min(6,10)=6이다. 끝 4≤6인 값 3만 이 규칙으로 회수 후보다. 값 5의 끝 8은 H보다 크므로 아직 후보가 아니다.

  3. snapshot 6이 종료되고 10만 남으면 H=10이다. 끝 8≤10인 값 5도 후보가 된다. 값 7은 snapshot 10에 필요하여 남고 최신 9도 남는다.

처음 필요한 값은 5·7·9, H 후보는 3이다. 6 종료 뒤 후보는 3·5이고 7·9는 보존한다. 실제 물리 해제의 동시 안전성은 별도다.

힌트 보기

실제로 보이는 값은 5와 9지만 보수적인 경계는 H=6이다.

풀이 보기

처음 H=6이라 후보는 값 3뿐이다. 값 7도 현재 두 snapshot에 보이지 않지만 끝 12>6이므로 이 간단한 규칙은 후보로 잡지 않는다. 6 종료 뒤 H=13이면 끝 4·8·12가 모두 ≤13이므로 3·5·7이 후보이고 최신 9는 남는다.

오해와 반례

최신 아닌 버전을 모두 지우면 MVCC의 공간도 줄고 모든 충돌 문제도 해결된다.

snapshot 6은 이전 값 5를 필요로 한다. 공간 회수와 업무 읽기-쓰기 충돌 제어는 다른 기능이며 실제 파일 축소·pointer 안전성도 추가 조건이다.

한 단계 더

오래된 reader 하나를 6에 둔 채 새 commit으로 버전이 늘어나는 그림을 그리자. 최솟값 규칙이 어디까지 공간을 보존하는지 표시하고 timeout으로 reader를 끝내는 정책이 업무 실패·재시도와 어떤 관계인지 토론하자. 실제 DB를 강제로 종료하거나 운영 VACUUM을 실행하지 않는다.
