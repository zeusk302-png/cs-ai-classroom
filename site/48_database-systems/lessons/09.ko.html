소단원 9.1

선택도·히스토그램

백만 행을 읽기 전에 조건에 맞는 행이 몇 개인지 어떻게 짐작할까?

준비 개념과 학습 목표

준비 개념

  • 조건을 만족한 행의 개수와 전체 행의 개수는 다르다.
  • 실행 계획은 같은 결과를 얻기 위한 처리 경로다.

학습 목표

  • 선택도와 결과 행 수의 관계를 계산한다.
  • 균등 분포·히스토그램·빈도 정보의 한계를 구분한다.

선택도는 통과하는 비율

선택도는 조건을 통과하는 행의 비율이다. 전체 행 수 N과 선택도 s가 있으면 출력 행 수를 N×s로 추정할 수 있다. 이는 모든 행을 실제로 검사해서 얻은 정답과 구별되며 통계가 오래되거나 표본이 불완전하면 틀릴 수 있다.

서로 다른 값이 D개라는 정보만으로 특정 값이 N/D번 나온다고 단정할 수는 없다. 균등 분포라는 가정이 추가되어야 한다. 인기 강의 하나에 대부분의 수강 기록이 몰리는 예를 생각하면 값 개수만으로 빈도를 알아내기 어렵다.

히스토그램은 분포를 요약

구간별 분포를 요약하면 단순 전체 균등 가정보다 범위 조건을 세밀하게 추정할 수 있다. PostgreSQL의 해당 예제는 같은 빈도의 bucket을 두고 bucket 내부에서는 선형 분포를 가정해 일부 비율을 계산한다. 같은 너비의 bucket과 같은 빈도의 bucket을 혼동하지 않는다.

경계 두 개 사이의 모든 실제 값을 저장한 것은 아니므로 작은 구간 안의 쏠림은 놓칠 수 있다. 아래는 NULL과 별도 인기값이 없고 연속 분포로 보간하는 축소 히스토그램이다. 정수의 경계 등호를 정확히 세는 표와는 다르다.

인기값과 나머지 집단

자주 나타나는 값 목록은 equality 조건을 추정하는 데 도움을 준다. 알려진 인기값은 그 빈도를 사용하고 그 외 값은 남은 비중을 나누는 가정을 할 수 있다. NULL 비중이 있으면 같은 질량을 중복해서 나누지 않는다.

PostgreSQL은 인기값에 해당하는 집단을 제외한 나머지에 히스토그램을 둘 수 있다. 두 부분을 다시 합칠 때에는 각 집단의 비중을 곱해야 한다. 통계 구조 이름보다 어떤 행을 대표하고 어떤 가정을 사용했는지 이해하는 것이 먼저다.

중간 과정을 따라가는 예제

전체 1000행, NULL과 별도 인기값 없음, 같은 빈도의 bucket 4개가 각각 250행을 대표한다. 경계는 0·10·20·50·100이고 내부는 연속 균등 보간한다고 가정한다. x<35의 추정 행 수와 선택도를 구하자.

  1. 0에서20까지 첫 두 bucket은 총500행이다.
  2. 20–50 bucket에서35까지의 비율은 (35−20)/(50−20)=1/2이므로125행을 더한다.
  3. 추정은625행이고 선택도625/1000=0.625다. 전체0–100 균등 가정으로 얻은350행과 다르다.

히스토그램 축소 모형의 추정은625행·선택도0.625다. 실제 데이터를 센 결과라는 의미는 아니다.

종이와 본문으로 직접 해보기

같은 모형에서 x<75를 추정하자. 별도의 범주형 열에서는 전체1000행 중 인기값A가400행이고, NULL은0이며 그 외 값이60개라고 하자. 나머지가 균등하면 인기값이 아닌 B의 추정은?

힌트 보기

세 bucket 전체와 마지막 bucket 일부를 더하고, 범주형 문제는 남은 행만 나누자.

풀이 보기

x<75는750+250×(75−50)/(100−50)=875행이다. B는(1000−400)/60=10행이다. A와 B의 빈도를 똑같이 놓으면 주어진 인기값 정보를 버리는 셈이다.

오해와 반례

히스토그램 경계가 있으면 모든 조건의 정확한 행 수를 안다.

bucket 내부 보간과 통계 표본 때문에 추정 오차가 남는다. 같은 bucket 안에 값이 한쪽으로 몰리는 분포는 같은 경계 요약과 다른 실제 범위 결과를 낼 수 있다.

자기점검

625행/1000행의 선택도는?

답과 이유 보기

0.625다.

통과 행의 비율이다.

경계 간격이10·10·30·50이면 각 bucket 빈도도 같은 비율로 늘어나는가?

답과 이유 보기

이 예제에서는 아니다.

같은 빈도250행을 명시했고 너비는 서로 다르다.

인기값A400행을 뺀 나머지는?

답과 이유 보기

600행이다.

남은60개 값에만 균등 배분한다.

한 단계 더

같은 20–50 bucket이 대표하는 250행을 모두 21 근처에 모은 모형과 모두 49 근처에 모은 모형을 그려 보자. 첫 모형에서 이 bucket의 x<35 행은 250이고 둘째에서는 0이다. 다른 bucket은 동일하게 유지한다. 동일한 bucket 질량만 알아서는 35보다 작은 실제 행 수를 정확히 결정할 수 없다는 점을 확인하자. 이는 내부 균등 가정을 깨는 분포 반례이며 히스토그램 보간 추정 125행과 구별한다.

소단원 9.2

카디널리티 추정 오류

각 조건의 추정이 맞아도 두 조건을 합친 추정은 틀릴 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 조건을 만족한 행의 개수와 전체 행의 개수는 다르다.
  • 실행 계획은 같은 결과를 얻기 위한 처리 경로다.

학습 목표

  • 독립 가정과 상관된 조건을 구분한다.
  • 초기 추정 오차가 후속 연산에 미치는 영향을 추적한다.

행 수는 계획 선택의 입력

카디널리티는 여기서 연산이 내보내는 행의 개수다. 필터 결과가 작다고 추정하면 반복해서 탐색하는 방법을 선택할 수 있지만 실제로 크면 반복 횟수가 많이 늘어날 수 있다. 출력 행 수와 내부에서 검사한 행 수를 구별해야 한다.

정확한 전체 행 수만 있으면 모든 조건의 결과도 정확하다는 뜻은 아니다. 조건별 분포, 여러 열의 관계, 시간에 따른 변경을 알아야 한다. 표본 통계를 늘려도 잘못된 독립 가정 자체는 해결되지 않을 수 있다.

곱셈에는 독립이라는 전제

두 조건의 선택도를 곱하면 각 조건이 서로 독립이라는 가정을 사용한 것이다. 성적 열두 개가 복사본처럼 항상 같으면 첫 열의 특정 값과 둘째 열의 같은 값은 독립 사건이 아니다. 첫 조건을 통과한 행에서 둘째 조건도 반드시 참이 될 수 있다.

반대로 서로 모순되는 두 값은 실제 결과가0일 수 있다. 단순한 열별 빈도만 곱하면 양수 추정이 나온다. PostgreSQL의 다변량 통계에는 dependency, 여러 열의 distinct 수, MCV 정보 등 서로 다른 보완 수단이 있으나 모든 쿼리를 완벽하게 예측한다는 보장은 아니다.

오차를 비교할 때 단위를 유지

추정20행과 실제200행의 비는10배다. 이를10행 차이라고 말하면 안 된다. 비율 비교는0일 때 나눗셈이 정의되지 않으므로 실제0인 예는 따로 보고한다. 어떤 노드에서 처음 오차가 커졌는지도 살펴야 한다.

종이 위 후속 비용을 늘리는 모형과 실제 DB 결과는 구분한다. EXPLAIN ANALYZE는 쿼리를 실제 실행하는 관찰 도구이므로 여기서는 실행하지 않는다. 문서의 actual 값과 우리의 가상 행 수를 같은 실험의 결과처럼 표시하지 않는다.

중간 과정을 따라가는 예제

1000행에서 두 열 a,b가 항상 같으며 값0–9가 각각100행에 나타난다. a=2 AND b=2의 독립 추정을 구하고 실제 논리적 개수와 비교하자. 가상 후속 작업은 출력 행마다7단위 비용을 사용한다.

  1. 각 조건 선택도는100/1000=0.1이다. 독립 곱은0.1×0.1=0.01이고 추정은10행이다.
  2. a=b이므로 a=2를 통과한100행이 모두 b=2도 만족한다. 실제 정의된 데이터의 결과는100행이다.
  3. 실제/추정은100/10=10배, 차이는90행이다. 후속 축소 비용은70단위로 추정하지만700단위가 필요하다.

개별 선택도가 정확해도 독립 가정 때문에10배 과소 추정한다. 후속 비용도 이 가상 선형 모형에서는70→700으로 달라진다.

종이와 본문으로 직접 해보기

같은 데이터에서 a=2 AND b=3의 독립 추정과 실제 개수를 구하자. 실제/추정 비율과 추정/실제 비율을 모두 정의할 수 있는가?

힌트 보기

a=b와 두 equality가 동시에 가능한지 확인하자.

풀이 보기

독립 추정은10행 그대로지만 실제는0이다. 실제/추정은0/10=0이지만 추정/실제는10/0이라 정의되지 않는다. 이 경우는 비율 하나로 숨기지 말고 추정10·실제0이라고 기록한다.

오해와 반례

ANALYZE를 한 번 했으면 모든 결합 조건의 추정이 정확하다.

최신 표본도 여러 열의 상관이나 실제 값 조합을 완전히 표현하지 못할 수 있다. 목적에 맞는 다변량 통계와 노드별 추정 비교가 필요하며 특정 예의 개선을 모든 조건에 일반화하지 않는다.

자기점검

각 조건0.1을 곱한 선택도는?

답과 이유 보기

0.01이다.

독립이라는 추가 가정을 사용한 계산이다.

100행과10행의 차이와 배수는?

답과 이유 보기

90행 차이·10배다.

뺄셈과 나눗셈은 다른 지표다.

실제0이면 추정/실제 배수를 바로 계산하는가?

답과 이유 보기

계산할 수 없다.

분모0의 나눗셈이기 때문이다.

한 단계 더

실제 데이터 정의, 통계가 표현하는 관계, 독립 추정, 결과 개수 네 열의 표를 만들자. 이어 조인 입력이100 대신10으로 추정되었다고 가정하고, 반복 횟수와 메모리 예상이 어디서 달라질지 설명하자. 실제 계획 선택 결과는 미상으로 남긴다.

소단원 9.3

CPU·I/O·메모리 비용

디스크를 덜 읽는 계획이면 언제나 더 빠를까?

준비 개념과 학습 목표

준비 개념

  • 조건을 만족한 행의 개수와 전체 행의 개수는 다르다.
  • 실행 계획은 같은 결과를 얻기 위한 처리 경로다.

학습 목표

  • 서로 다른 비용 요소를 같은 비교 모형으로 합친다.
  • 메모리 초과와 실제 시간 측정의 차이를 설명한다.

비용은 서로 다른 작업의 요약

계획에는 page 읽기, 행 처리, 연산자 평가, 메모리 사용 같은 요소가 있다. PostgreSQL의 planner cost는 상대적인 척도이며 기본 설정은 sequential page 비용을 기준으로 한다. cost 숫자를 그대로 밀리초라고 읽어서는 안 된다.

임의로 순차1·임의4·행0.01 같은 계수를 정하면 비교 모형을 만들 수 있다. 계수는 캐시와 장치 환경에 영향을 받는다. 물리적인 임의 읽기의 지연이 언제나 순차의 정확히4배라는 법칙으로 이해하지 않는다.

덜 읽고 더 계산하는 교환

작은 후보만 index로 찾으면 page 읽기를 줄일 수 있지만 많은 후보를 흩어 읽으면 다른 비용이 늘 수 있다. 반대로 전체 순차 탐색은 후보가 많을 때 단순하게 비교할 수 있다. 출력 결과가 같아도 실행 경로의 작업량은 다르다.

아래 두 계획은 비용 비교를 위한 자체 숫자 모형이다. 실제 PostgreSQL planner의 모든 항목을 구현한 식이 아니다. 실제 시간에는 출력 변환과 전달 등 이 단순 모형에 넣지 않은 비용도 있을 수 있다.

메모리는 성능의 조건

정렬이나 hash 작업이 메모리에 맞는지에 따라 disk 사용과 batch 수가 달라질 수 있다. 필요한 바이트를 행 수×가정한 저장 폭으로 계산하되 실제 구조의 header, pointer, allocator 비용은 별도임을 밝힌다.

메모리 예산만 늘리면 모든 계획이 좋아진다는 결론도 조심해야 한다. 동시 작업이 여러 개이면 전체 사용량이 커질 수 있고 데이터 분포가 바뀌면 계획도 달라진다. 문서의 sort method·memory/disk·hash batch 정보는 이런 판단을 위한 관찰 항목이다.

중간 과정을 따라가는 예제

가상 단위로 순차 page=1, 임의 page=4, 처리 행=0.01이다. 계획A는 순차100page·10000행, B는 임의20page·1000행만 처리하며 다른 비용은0이다. 별도 hash 자료는1000행×64바이트로 가정하고 예산은48KiB다. 구조 overhead는 제외한다.

  1. A는100×1+10000×.01=200단위다. B는20×4+1000×.01=90단위다. 이 모형은B를 선호한다.
  2. 임의 page 비용만12로 바꾸면B는240+10=250단위로A200보다 커져 선호가 바뀐다.
  3. 자료 크기는64000바이트다.48KiB는49152바이트로14848바이트 부족하다. 이 가정에서는 모두 메모리에 담을 수 없지만 실제 spill량이나 시간은 이 차이만으로 확정하지 않는다.

가상 비용은 계수4일 때B90<A200, 계수12일 때A200<B250이다. 메모리 자료64000바이트는48KiB 예산을 넘는다.

종이와 본문으로 직접 해보기

임의 page 비용이8이면 어느 계획이 유리한가? 예산을64KiB로 바꾸면 가상 자료는 들어가는가? 세 작업이 각각64KiB를 전부 쓰면 합은?

힌트 보기

1KiB=1024바이트이며 비용과 메모리를 따로 계산하자.

풀이 보기

B는 160+10=170단위로 A200보다 작다. 64KiB=65536바이트여서 가상 64000바이트는 1536바이트 여유로 들어간다. 세 작업의 예산 합은 192KiB=196608바이트다. 실제 구조 overhead를 더하면 들어간다는 판단이 바뀔 수 있다.

오해와 반례

EXPLAIN cost가200이면 실제 실행 시간도200ms다.

cost는 설정된 상대 척도이며 실제 시간과 다르다. 위 200은 자체 계수의 계산값이다. actual 시간은 실제 실행 관찰이고 여기서는 측정하지 않았다.
