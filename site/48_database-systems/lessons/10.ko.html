소단원 10.1

논리 변환과 탐색

같은 두 결과 행을 얻으면서 중간에 비교하는 행 쌍은 줄일 수 있을까?

준비 개념과 학습 목표

준비 개념

  • inner join은 조건에 맞는 행 쌍을 만든다.

  • WHERE는 조건이 참인 행을 남긴다.

학습 목표

  • 결과를 보존하는 변환과 결과를 바꾸는 변환을 구별한다.

  • 논리 변환·비용 추정·탐색의 역할을 설명한다.

논리 계획은 무엇을 구할지 적는다

질의 최적화의 출발점은 정답의 의미다. 필터로 행을 고르고 조인으로 관계를 연결하고 투영으로 열을 고르는 구조를 논리 계획이라고 생각하자. 논리 계획을 바꿀 때에는 같은 입력에서 같은 결과를 내야 한다. 비용이 싸더라도 점수나 행 개수가 바뀌면 잘못된 변환이다.

SQL에서 중복 행의 개수도 결과의 일부다. SELECT id가 같은 id를 두 번 내는 질의에 DISTINCT를 몰래 붙여 한 번만 내면 동치가 아니다. ORDER BY가 없는 결과 행의 나열 순서를 최적화의 정답으로 고정하지도 않는다. 집합 관계대수의 직관을 SQL에 옮길 때에는 중복과 NULL을 별도로 살펴야 한다.

조건과 필요한 열을 일찍 줄인다

한 테이블의 열만 참조하는 결정적인 조건은 적절한 inner join 아래로 이동하여 조인 입력을 줄일 수 있다. 예를 들어 학생의 지역 조건은 학생 행에, 점수 조건은 성적 행에 먼저 적용한다. 남은 행끼리 연결해도 같은 학생·점수 쌍을 얻는지 작은 표로 확인하면 변환 이유가 보인다.

열을 줄이는 투영은 행 수를 줄이는 필터와 다르다. 최종 출력에 없는 연결용 id도 조인할 때까지 보존해야 하며 아직 적용하지 않은 조건에 쓰는 열도 필요하다. outer join, 집계, LIMIT, 부작용이나 평가 횟수에 민감한 표현식을 이 단순 규칙으로 무조건 이동시키면 안 된다.

동치 후보를 찾고 비용으로 비교한다

변환 규칙은 후보 계획을 만들고 비용 모형은 후보를 비교한다. 논리적으로 같은 조인도 index lookup이나 hash join처럼 여러 물리 구현을 가질 수 있다. 예상 행 수와 메모리·입출력 비용을 이용해 좋은 후보를 찾지만 예상 비용은 실제 초 단위 측정값과 같지 않다.

모든 후보를 끝없이 탐색하는 것도 비용이다. 구현은 시간이나 탐색 범위에 한계를 둘 수 있고 큰 조인 질의에는 휴리스틱을 사용할 수 있다. 따라서 선택된 계획이 모든 가능한 계획 중 실제 실행 시간이 가장 짧다고 보장되지는 않는다. 결과 의미 보존과 실행 효율 개선은 서로 다른 검증 항목이다.

중간 과정을 따라가는 예제

R(id,city)는 (1,A),(2,B),(3,A), S(rid,score)는 (1,80),(1,90),(2,70),(3,50)이다. id=rid인 inner join에서 city=A이고 score>=80인 id·score를 구하자. 모든 입력 행 쌍을 한 번씩 비교하는 종이 모형을 쓴다.

  1. 원래 입력의 후보 행 쌍은 3×4=12개다. id 연결과 두 조건을 모두 통과하는 쌍은 (1,80),(1,90)이다.

  2. R을 city=A로 먼저 거르면 id 1과 3의 2행이 남는다. S를 score>=80으로 거르면 rid 1의 점수 80과 90, 2행이 남는다.

  3. 필터 후 후보 비교는 2×2=4개이며 id가 같은 두 쌍만 출력한다. 필터 자체의 비용은 이 후보 쌍 수에 포함하지 않았다.

두 계획의 결과는 (1,80),(1,90)로 같다. 종이 모형의 후보 비교는 12개에서 4개로 줄지만 실제 DBMS의 속도 개선 배수라는 뜻은 아니다.

종이와 본문으로 직접 해보기

R은 id 1·2, S는 (rid=1,score=50) 한 행이다. LEFT JOIN의 ON에는 id=rid만 있고 WHERE에는 score>=80이 있다. 점수 조건을 WHERE에서 지우고 ON에만 넣으면 결과가 같은가?

힌트 보기

LEFT JOIN의 연결 실패는 오른쪽 열이 NULL인 행을 만든다. WHERE는 NULL인 비교 결과도 참으로 취급하지 않는다.

풀이 보기

원래 질의는 id 1의 50점 행과 id 2의 NULL 행이 모두 WHERE에서 제거되어 0행이다. 조건을 ON에만 넣으면 두 id 모두 연결에 실패하지만 왼쪽 행을 보존하므로 (1,NULL),(2,NULL) 2행이다. 같은 변환이 아니다.

오해와 반례

필터를 아래로 내리면 항상 정답이 같고 실행도 빨라진다.

위 LEFT JOIN 반례는 정답부터 달라진다. 의미가 같은 inner join 변환이라도 필터 계산 비용·통계 오차·다른 접근 경로 때문에 실제 속도는 달라질 수 있으므로 동치 조건과 성능 증거를 각각 확인한다.

답과 이유 보기

DISTINCT 등 원래 의미가 요구하지 않으면 안 된다.

중복 개수를 임의로 바꾸면 SQL 결과가 바뀐다.

추정 비용이 가장 낮은 후보가 실제로도 언제나 가장 빠른가?

한 단계 더

S의 점수 90을 80으로 바꾸면 결과 (1,80)이 두 번 나온다. 두 행을 종이에 각각 적어 보고 DISTINCT를 명시한 경우와 명시하지 않은 경우의 개수를 비교하자. 이어 최종 출력에는 id만 있어도 필터 적용 전 score를 제거할 수 없는 이유를 설명해 보자.

소단원 10.2

join order·dynamic programming

세 테이블을 연결할 때 첫 번째 두 테이블의 선택이 왜 마지막 비용까지 바꿀까?

준비 개념과 학습 목표

준비 개념

  • 조인의 중간 결과도 다음 조인의 입력이 된다.

  • 예상 행 수는 실제 행 수와 구별한다.

학습 목표

  • 부분 집합별 최선 후보를 이용해 작은 조인 순서를 계산한다.

  • 순서·출력 속성이 다른 후보를 섣불리 버리지 않는다.

먼저 만드는 중간 결과를 비교한다

A·B·C를 inner join으로 연결할 때 (A join B) join C와 A join (B join C)는 적절히 전체 연결 조건을 유지하면 같은 결과를 낼 수 있다. 그러나 처음 만들어 내는 AB와 BC의 행 수가 다르면 다음 단계에 보내는 양도 달라진다. 연결 조건이 없는 A·C부터 만나면 큰 Cartesian product가 생길 수도 있다.

교환·결합 직관은 inner join의 적절한 의미 조건에서 사용한다. LEFT JOIN의 보존 행은 마음대로 순서를 바꾸어서는 안 된다. 또한 SQL 작성 순서가 DBMS가 실제 실행하는 순서로 그대로 고정된다고 생각하지 않는다. 최적화기는 허용되는 여러 순서를 검토할 수 있다.

작은 부분 문제의 답을 재사용한다

dynamic programming, 동적 계획법은 작은 문제의 최선 후보를 저장하고 더 큰 문제를 만들 때 재사용하는 방법이다. 여기서는 한 테이블의 비용을 0으로 정한 축소 모형을 쓰고, 두 테이블 부분 집합 AB·BC·AC의 비용을 먼저 계산한다. 이어 세 테이블을 만들 수 있는 세 가지 분할을 비교한다.

예를 들어 DP[S]를 S에 들어 있는 테이블을 모두 연결하는 최소 추정 비용이라고 하자. 분할 X와 S−X의 출력 속성이 같고 이후 비용에 충분한 정보가 보존된 모형에서는 DP[X]+DP[S−X]+해당 연결 비용을 비교할 수 있다. 실제 최적화기는 scan 비용, 여러 조인 구현, 정렬·메모리 등의 항목을 추가한다. 이 단순 표를 실제 DBMS의 완전한 알고리즘으로 보지는 않는다.

싼 부분 결과 하나만 남기면 놓칠 수 있다

같은 AB 결과라도 id로 정렬된 출력과 정렬되지 않은 출력은 이후 연산에 서로 다른 가치를 가진다. 정렬되지 않은 AB가 만드는 비용 10, 정렬된 AB가 20이라고 해서 20을 즉시 버리면, 다음 단계가 정렬을 요구할 때 전체 비용이 더 커질 수 있다.

자체 모형에서 정렬되지 않은 후보는 나중에 정렬 비용 100과 후속 처리 5를 더해 총 115, 이미 정렬된 후보는 후속 처리 5만 더해 총 25라고 하자. 같은 부분 집합이라도 필요한 출력 속성별로 후보를 구분할 이유다. 시간 한도나 탐색 제한이 있으면 동적 계획법을 사용해도 고려한 공간 밖의 더 좋은 계획은 놓칠 수 있다.

중간 과정을 따라가는 예제

자체 비용 모형에서 각 단일 테이블 비용은 0이다. 첫 연결의 예상 출력 행 수를 비용으로 세며 AB=10, BC=1000, AC=100000이다. 세 테이블 연결의 최종 출력은 어떤 순서에서도 20행으로 추정하고 두 번째 연결 비용을 20으로 센다. 이 모형에서 첫 연결을 고르자.

  1. 크기 2의 부분 문제는 DP[AB]=10, DP[BC]=1000, DP[AC]=100000이다. AC는 연결 조건이 없어 큰 중간 곱을 만드는 후보로 두었다.

  2. AB부터 만들면 총 10+20=30, BC부터면 1000+20=1020, AC부터면 100000+20=100020이다.

  3. 세 후보에서 30이 가장 작으므로 AB부터 연결하는 계획을 저장한다. 실제 시간을 재지 않았고 이 비용 모형에는 scan·정렬·메모리 비용이 없다.

주어진 축소 모형에서는 AB를 먼저 연결하는 비용 30의 계획이 최선이다. 예상 출력 수가 틀리거나 비용 항목이 추가되면 선택이 바뀔 수 있다.

종이와 본문으로 직접 해보기

새 통계에서 AB=200, BC=5, AC=100000, 최종 연결 비용=30이라고 하자. 같은 표의 선택을 바꾸자. 별도로 AB의 두 물리 후보 U는 제작 10·후속 정렬 100·후속 처리 5, O는 제작 20·후속 정렬 0·후속 처리 5다. 전체 비용은?

힌트 보기

먼저 세 부분 비용 각각에 30을 더한다. 물리 후보는 후속 비용도 끝까지 더한다.

풀이 보기

AB부터 230, BC부터 35, AC부터 100030이므로 BC부터 선택한다. U는 115, O는 25이므로 제작 비용은 더 비싸도 이미 정렬된 O가 전체에서는 유리하다.

오해와 반례

중간 행이 가장 적은 후보 하나만 기억하면 모든 질의의 최적 계획을 보장한다.

출력 순서·조인 구현·메모리 등의 물리 속성을 무시하면 전체 비용이 싼 후보를 잃는다. 위 U/O 반례에서 제작 비용 10만 보고 U를 남기면 총 25의 O를 놓친다. 전역 최적성은 정확한 상태·비용 모형·탐색 범위 등의 조건에 달려 있다.

자기점검

답과 이유 보기

정렬된 후보를 보존하는 이유는?

답과 이유 보기

후속 연산에 필요한 정렬 비용을 줄일 수 있기 때문이다.

부분 제작 비용과 끝까지의 비용은 다르다.

한 단계 더

종이에 테이블 이름 A·B·C 세 장을 놓고 나열 순서 6가지를 써 보자. 이것은 이름의 순열 개수이며 가능한 모든 조인 트리·물리 구현 수와 같지 않다. 그중 같은 부분 집합 AB를 반복해서 계산하는 경우를 표시하면 부분 결과 재사용의 의미를 볼 수 있다.

소단원 10.3

물리 계획 선택·캐시

인덱스가 있어도 전체를 읽는 계획이 더 쌀 수 있고, 계획을 저장해도 결과는 다시 구해야 할까?

준비 개념과 학습 목표

준비 개념

  • 인덱스는 원하는 행 위치를 찾는 접근 경로다.

  • 같은 질의 형태에 들어가는 입력값은 달라질 수 있다.

학습 목표

  • 물리 접근 경로를 같은 비용 단위로 비교한다.

  • 계획 재사용과 질의 결과 재사용을 구별한다.

논리적 연결을 실제 작업으로 구현한다

물리 계획은 어떤 scan으로 행을 읽고 어떤 구현으로 조인하고 정렬할지 정한다. 순차 scan은 많은 페이지를 연속해서 읽을 수 있고 index scan은 위치를 찾은 뒤 필요한 행에 접근한다. 조건에 맞는 행이 적을 때 인덱스가 유리할 수 있지만 대부분의 행을 읽으면 흩어진 접근 비용이 커질 수 있다.

비용 비교에는 같은 단위를 사용한다. 아래 예제의 100·4·2는 실제 밀리초나 PostgreSQL 설정값이 아니라 자체 비용 점수다. 실제 선택은 통계·캐시·저장장치·행 배치·index-only scan 가능성 등의 영향을 받는다. 인덱스 존재만으로 특정 계획을 강제로 정답 처리하지 않는다.

입력값에 맞춘 계획과 재사용 계획

준비된 질의는 질의 형태의 분석 결과 등을 재사용할 수 있다. PostgreSQL은 입력 파라미터를 반영한 custom plan과 여러 입력에 사용할 generic plan을 구분한다. 매번 입력에 맞추어 계획하면 선택적인 조건에 유리한 접근 경로를 찾을 수 있지만 계획 만드는 비용이 반복될 수 있다.

generic plan은 계획 재사용으로 이 비용을 아끼는 대신 입력값에 따라 크게 달라지는 선택도를 충분히 활용하지 못할 수 있다. 인기값과 드문 값의 분포가 다른 열에서 두 계획의 장단점을 생각해 보자. 실제 PostgreSQL의 선택 규칙을 아래 고정 비용 장난감 모형과 동일하다고 단정하지 않는다.

계획 캐시는 정답 저장소와 다르다

저장한 계획은 데이터를 어떻게 읽을지에 대한 작업 지시다. 이전 결과 행 자체를 자동으로 저장해 다음 실행에 그대로 돌려주는 것과는 다르다. 테이블 값이 달라지면 재사용 계획으로 실행해도 그 실행의 가시성 규칙에 맞는 데이터를 다시 읽어 결과를 만든다.

DDL 변경이나 통계 갱신 등은 계획을 다시 만들 필요를 일으킬 수 있다. 캐시된 계획의 수명과 범위도 구현에 달린다. PostgreSQL PREPARE의 준비된 문장은 세션 범위다. 서로 다른 연결에서 똑같은 이름을 쓴다고 한 세션의 준비된 문장이 그대로 공유된다고 가정하지 않는다.

중간 과정을 따라가는 예제

자체 비용에서 순차 scan은 항상 100점, index scan은 시작 4점+일치 행 수 r×2점이다. r=5와 r=80을 비교하자. 이어 generic plan은 순차 scan 100점을 재사용하고, custom 계획 비용은 매번 3점이며 그 입력에 싼 scan을 고른다고 하자. 같은 입력으로 두 번 실행할 비용을 비교한다. generic의 초기 준비 비용은 이미 지불해 두 방식 비교에서 제외한다.

  1. r=5이면 index 비용 4+2×5=14이므로 100보다 싸다. r=80이면 4+2×80=164여서 순차 scan 100이 싸다.

  2. 두 번 모두 r=5라면 generic 실행 총 비용은 200, custom은 2×(3+14)=34다.

  3. 두 번 모두 r=80이라면 generic은 200, custom은 2×(3+100)=206이다. 선택 비용의 이득이 없으면 반복 계획 비용만 추가된다.

이 자체 모형에서는 적은 행에 인덱스, 많은 행에 순차 scan이 유리하다. custom/generic의 우열도 입력 분포와 계획 비용에 따라 바뀐다.

종이와 본문으로 직접 해보기

같은 scan 비용에서 r=20과 r=60의 싼 경로를 고르자. 두 입력을 각각 한 번 처리하면 위 generic과 custom의 합계는? 별도로 SELECT score의 이전 결과가 80이었다고 하자. 다음 실행에서 보이는 테이블 값이 90으로 갱신되면 계획 재사용만으로 80을 다시 반환해야 하는가?

힌트 보기

index 비용은 4+2r, custom에는 실행마다 계획 비용 3을 더한다. 결과의 재사용과 계획의 재사용은 다르다.

풀이 보기

r=20이면 index 44, r=60이면 index 124보다 순차 100이 싸다. generic 합계 200, custom은 (3+44)+(3+100)=150이다. 다음 실행에서 값 90이 보인다는 가정에서는 새 결과 90을 읽는다. 계획 캐시 자체는 옛 결과 80을 반환하는 결과 캐시가 아니다.

오해와 반례

계획이 캐시되면 실행할 때 데이터를 읽지 않으며 항상 같은 결과가 나온다.

계획은 작업 경로를 재사용한다. 같은 경로로 읽어도 가시성 규칙에 맞는 데이터가 바뀌면 결과는 바뀐다. 별도 결과 캐시를 설계했다면 갱신·무효화 규칙을 따로 검토해야 하며 PREPARE만으로 그 기능을 추정해서는 안 된다.

한 단계 더

자체 모형의 두 scan 비용이 같아지는 행 수는 4+2r=100에서 r=48이다. r=47·48·49에서 경로 선택을 계산해 보자. 각각 index 98, 두 경로 모두 100, index 102로 순차 scan 100이 유리하다. 이 경계가 실제 DBMS의 선택 행 수라는 주장과는 구별한다.
