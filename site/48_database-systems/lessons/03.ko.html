소단원 3.1

pin·dirty·eviction

지금 누군가 읽고 있는 페이지를 다른 페이지로 바꾸어도 될까?

준비 개념과 학습 목표

준비 개념

  • page는 DB 파일의 자료 단위, frame은 그 page를 담는 메모리 칸이다. page ID와 frame ID를 구별한다.

  • pin count는 frame의 페이지를 현재 사용하는 요청자 수다. acquire/release를 짝지으며 누적 인기 점수가 아니다.

  • dirty는 메모리 복사본의 변경이 저장장치의 대응 상태에 아직 반영되지 않았다는 상태다. 인기·사용 중 여부와 별개다.

학습 목표

  • pin·dirty·page table의 역할을 나눈다.

  • 교체 가능한 후보와 안전한 쓰기 순서를 추적한다.

  • pin과 내용 latch 및 transaction lock을 구별한다.

페이지를 바꿔도 되는 때와 저장해도 되는 때는 같을까요?

책상 세 자리에 책이 놓여 있다고 생각해 봅시다. 누군가 지금 펼쳐 읽는 책은 다른 책으로 바꿀 수 없습니다. pin 수는 그 페이지를 사용 중인 참조의 수입니다. 오래 인기 있었는지를 세는 수가 아니며, pin이 남은 페이지를 교체 후보에서 제외하는 이유는 현재 사용자의 참조를 보호하기 위해서입니다.

dirty는 메모리의 변경이 저장 장치의 페이지에 아직 반영되지 않았다는 표시입니다. 커밋 여부와 같은 표시가 아닙니다. 또한 pin만으로 두 사용자가 내용을 동시에 고치는 일을 막지는 못합니다. 내용을 보호하는 latch와 페이지를 교체하지 않도록 붙잡는 pin을 구별해야 합니다.

먼저 확인할 개념
  • 시스템 호출과 페이지 자원

    페이지를 담는 메모리와 실제 읽기 결과를 구별하는 출발점입니다.

  • 가변길이·압축·삭제

    페이지 안의 내용이 바뀌는 경우와 참조의 수명 문제를 연결합니다.

메모리 칸과 페이지의 대응을 기록한다

buffer pool은 파일의 일부 페이지를 고정 크기 frame에 담고 page ID→frame 매핑을 유지한다. 요청 페이지가 있으면 hit로 그 frame을 재사용하고 pin을 증가시킨다. 없으면 miss이며 빈 frame이나 교체 가능한 frame을 확보해 페이지를 읽는다. page table은 현재 메모리 위치, 디스크 page directory는 파일 위치를 찾는 자료로 역할이 다르다.

pin>0은 사용 중인 페이지를 다른 것으로 바꾸지 말라는 수명 보호다. 요청자는 사용을 끝낸 뒤 unpin을 요청하며 count가 감소한다. 복수 요청자가 있으면 하나가 release해도 남은 pin이0이 아닐 수 있다. pin은 page 내용을 읽거나 쓰는 여러 thread를 서로 배제하지 않으므로 별도 latch가 필요하다.

dirty와 후보 선택은 다른 차원이다

pin=0인 페이지가 보통 eviction 후보가 된다. dirty=0이면 저장장치에 같은 내용을 다시 쓸 필요 없이 frame을 재사용할 수 있다. dirty=1이면 변경을 잃지 않도록 쓰기·복구 순서를 지켜야 한다. 어느 후보를 택할지는 LRU·CLOCK·clean 우선 등의 정책에 따라 다르며 dirty라고 영원히 교체 불가한 것은 아니다.

모든 frame이 pin되어 있으면 정책이 아무 페이지나 골라 쫓아낼 수 없다. 기다리거나 요청 실패를 반환하거나 자원을 다른 방식으로 확보하는 경로가 필요하다. 잘못된 unpin 누락은 메모리가 남아 보이는데도 교체 후보가 사라지는 원인이 된다. 실제 구현의 guard나 오류 경로도 pin을 정확히 release해야 한다.

쓰기 완료와 재변경을 구별한다

WAL을 쓰는 DB에서 변경 기록은 대응 데이터 페이지가 안정 저장에 기록되기 전에 먼저 안정 저장되어야 한다. dirty eviction 전에 log flush가 필요한 경우가 있고, background writer로 미리 페이지를 쓰는 선택도 있다. dirty flag를0으로 만들었다는 사실만으로 transaction commit·논리 lock 해제가 완료됐다는 뜻은 아니다.

flush가 진행되는 동안 페이지를 다른 thread가 다시 바꾸면 이전 내용을 쓴 완료만으로 현재 dirty를 지울 수 없다. 복사본·version·latch 등의 기법으로 쓰기 대상 버전과 현재 버전을 구별해야 한다. 단원 예제는 동시 변경이 없는 안전한 순서 모형이며 실제 디스크의 전원 장애 내구성까지 실험하지 않았다.

중간 과정을 따라가는 예제

frame3개에 A(pin2,dirty1,last1),B(pin0,dirty1,last2),C(pin0,dirty0,last3)가 있다. 정책은 unpinned clean 우선, 없으면 unpinned 중 last가 가장 작은 것이다. 새 D를 요청해 pin1로 사용한다. A를 두 번 순차 unpin한 뒤 E를 요청한다. A의 page LSN40,stable WAL LSN35이며 새 읽기 성공·동시변경 없음이다.

  1. 첫 D miss에서 A는 pin2라 제외된다. B/C 중 clean C를 골라 쓰기 없이 교체한다. D를 읽어 pin1/dirty0으로 만든다.

  2. A의 첫 unpin은2→1로 아직 후보가 아니다. 두 번째 unpin 뒤0이 된다. B도0이며 D는1이라 후보가 아니다.

  3. E miss에서 unpinned clean이 없으므로 last1인 A를 선택한다. page LSN40>stable35여서 먼저 WAL을 최소40까지 안정 저장한다.

  4. 그 뒤 A의 변경 페이지를 안전하게 쓰고 E를 읽어 frame을 재배정한다. 두 miss의 페이지 읽기2회, 데이터 페이지 쓰기1회다. WAL flush는 별도 작업이며 페이지 쓰기 횟수에 합치지 않는다.

D는 C를 교체하고 E는 WAL 순서 뒤 A를 교체한다. pin·dirty·최근성은 각각 다른 판단을 한다.

조건을 바꾸어 비교하기

깨끗한 후보가 먼저 선택됩니다

표의 상태에서 D를 한 번 읽고 pin을 1로 유지합니다. 이어 A의 참조 두 개를 각각 해제한 뒤 E를 읽어 pin을 1로 유지합니다. A의 페이지 LSN은 40이고 안정적으로 저장된 WAL 끝은 35입니다. 교체 과정의 페이지 읽기·쓰기를 세어 봅시다. 필요한 WAL 저장과 페이지 쓰기 및 새 페이지 읽기는 모두 성공하며, 설명한 동작 이외의 접근은 없다고 가정합니다.

  1. D를 읽을 때 A는 사용 중입니다. B와 C는 사용하지 않지만 C만 깨끗하므로 C를 D로 바꿉니다. D는 pin 1, dirty 없음이 됩니다.

  2. A를 두 번 해제하면 pin은 2에서 1을 거쳐 0이 됩니다. E를 읽을 때 D는 제외되고, A와 B 모두 dirty입니다. 마지막 접근 1인 A가 후보입니다.

  3. A의 변경을 페이지에 쓰기 전에 그 변경을 복구할 WAL이 안정적으로 저장되어 있어야 합니다. 주어진 모형에서는 WAL 끝을 최소 40까지 저장한 뒤 A의 페이지를 쓰고 E를 읽습니다.

페이지 읽기는 D와 E의 2회이고 페이지 쓰기는 A의 1회입니다. WAL 저장 작업은 페이지 쓰기 횟수에 섞지 않습니다. 마지막 상태는 E와 B와 D이며, E와 D는 pin 1입니다.

비교할 점

dirty 페이지라고 바로 교체할 수 있는 것이 아닙니다. pin이 0인지와 WAL 순서가 맞는지를 모두 확인해야 합니다.

쓰기 완료가 오래된 버전일 수 있습니다

페이지의 버전 5를 저장하는 작업을 시작했습니다. 저장 작업 중 다른 사용자가 페이지를 버전 6으로 바꾸었습니다. 버전 5의 저장이 성공하면 dirty를 지워도 될까요?

  1. 저장 작업이 대상으로 삼은 버전은 5입니다. 현재 메모리의 버전은 6입니다.

  2. 버전 5가 저장되었다는 사실은 버전 6의 변경까지 저장되었다는 뜻이 아닙니다.

  3. 완료 처리에서는 저장한 버전과 현재 버전을 보호된 상태에서 비교해야 합니다. 두 버전이 다르면 새 변경의 dirty를 유지합니다.

현재 페이지는 dirty로 남겨야 합니다. 그 뒤 버전 6을 대상으로 하는 저장이 성공하고 그동안 새 변경이 없었을 때 dirty를 지울 수 있습니다.

비교할 점

저장 성공이라는 한 가지 신호로 현재 페이지의 모든 변경이 반영되었다고 판단하면 새 변경을 놓칩니다.

오해와 반례

연습 1 · 값과 상태 예측

D가 C를 교체한 뒤 A를 한 번만 해제하고, B를 새로 pin한 상태에서 E를 요청합니다. 교체 후보와 즉시 처리 가능 여부를 구하세요.

힌트 1

A의 참조는 처음 두 개였습니다.

힌트 2

B의 pin을 새로 얻으면 0에서 1이 됩니다.

풀이와 답 확인

  1. A는 pin 1, B는 pin 1, D는 pin 1입니다.

  2. 사용하지 않는 프레임이 없으므로 어느 페이지도 교체하지 않습니다.

즉시 교체할 후보가 없습니다. 대기하거나 정해진 자원 부족 처리로 넘어가야 합니다.

흔한 오답에서 다시 생각하기

dirty인 B를 쓰고 교체하면 됩니다.

B는 사용 중입니다. 페이지 쓰기가 끝나도 현재 참조가 자동으로 없어지지는 않습니다.

연습 2 · 오류 찾아 고치기

pin이 0인 페이지에서 참조를 세 번 얻고 두 번 해제했습니다. 프로그램은 그 뒤 네 번 더 해제해 pin을 −3으로 만들고 교체 가능하다고 판단했습니다. 오류와 처리 경계를 설명하세요.

힌트 1

먼저 합법적인 다섯 동작의 결과를 계산합니다.

힌트 2

해제할 참조가 실제로 남아 있는지 확인해야 합니다.

풀이와 답 확인

  1. 세 번 얻고 두 번 해제하면 pin은 1입니다.

  2. 남은 참조 하나를 해제하면 0이지만 그 이후 해제는 유효한 참조가 없습니다.

  3. 잘못된 중복 해제를 검출하고 수를 음수로 내려 교체 판단에 쓰지 않아야 합니다.

합법적인 앞부분의 pin은 1입니다. 추가 해제는 실제로 소유한 참조에 한해 한 번만 허용되며, 나머지 중복 해제는 오류입니다.

흔한 오답에서 다시 생각하기

음수도 0보다 작으므로 더 안전한 교체 상태입니다.

pin 수는 현재 유효한 참조의 개수를 나타내야 합니다. 음수는 안전성의 증거가 아니라 참조 관리 오류입니다.

연습 3 · 직접 만들어 보기

pin 0, dirty인 F의 페이지 LSN이 52이고 안정적 WAL 끝이 48입니다. WAL 저장이 실패하는 경우까지 포함해 F를 다른 페이지로 바꾸는 절차를 구성하세요.

힌트 1

복구 기록과 데이터 페이지의 저장 순서를 정합니다.

힌트 2

실패 뒤 원래 프레임을 덮어써도 되는지 묻습니다.

풀이와 답 확인

  1. 후보 선정 뒤 페이지의 변경 상태와 버전을 보호합니다.

  2. 필요한 WAL을 최소 52까지 저장합니다. 실패하면 데이터 페이지 쓰기와 새 페이지 덮어쓰기를 진행하지 않습니다.

  3. WAL 저장이 성공한 뒤 F의 해당 버전을 저장합니다. 페이지 쓰기도 실패하면 원래 내용을 보존하고 실패를 전달합니다.

  4. 필요한 저장이 성공했음을 확인한 뒤에만 프레임을 새 페이지로 전환합니다.

WAL 실패 또는 페이지 쓰기 실패에서는 F를 새 페이지로 덮어쓰지 않습니다. 성공 경로는 WAL 저장, 데이터 페이지 저장, 프레임 전환 순서입니다.

pin 0은 사용자 참조 조건입니다. 복구에 필요한 dirty 내용을 잃어도 된다는 허가가 아닙니다.

소단원 3.2

교체정책·prefetch

최근 읽은 페이지를 남기고 다음 페이지를 먼저 읽으면 언제 유리할까?

준비 개념과 학습 목표

준비 개념

  • hit는 요청 페이지가 buffer에 있는 경우다. miss의 읽기 비용과 dirty 피해자의 쓰기 비용은 별도로 센다.

  • LRU는 가장 오래 최근 사용된 후보를, CLOCK은 reference bit와 hand를 사용해 근사 선택한다.

  • prefetch는 앞으로 쓸 것으로 예상한 페이지를 먼저 가져온다. 실제 사용될 때까지 기다리거나 필요 없으면 낭비될 수 있다.

학습 목표

  • 명시한 LRU/CLOCK 계약으로 상태를 추적한다.

  • scan flooding과 정책 선택의 한계를 설명한다.

  • prefetch의 겹침과 추가 I/O 비용을 계산한다.

미리 읽기는 언제 빨라지고 언제 자리가 모자랄까요?

교체 정책은 다음에 필요한 페이지를 모르는 상태에서 자리를 비우는 규칙입니다. 이 단원에서는 LRU의 순서를 모든 접근 때 갱신한다고 정합니다. pin 해제 시각을 기준으로 삼는 다른 구현과 섞으면 같은 접근열에서도 다른 답이 나옵니다.

미리 읽기는 다음 페이지의 읽기를 현재 페이지의 계산과 겹치는 방법입니다. 읽기 횟수가 반드시 줄어드는 것은 아닙니다. 아직 계산하지 않은 페이지를 담을 공간과 읽기·계산이 실제로 겹칠 조건이 있어야 합니다.

먼저 확인할 개념
  • 요구 페이징·교체 정책

    최근 사용과 교체 후보의 차이를 먼저 확인합니다.

  • 파서·최적화·실행·저장 계층

    실행기의 순차 요청이 저장 계층의 읽기 일정과 연결됨을 확인합니다.

정책은 상태와 갱신 시점을 정해야 재현된다

LRU는 후보 중 마지막 사용이 가장 오래된 것을 택한다. last를 읽기·unpin 중 언제 갱신하는지는 구현 계약에 따라 다르므로 trace에서는 규칙을 명시한다. 본문 LRU 모형은 각 접근에서 최근 순서를 갱신하고 접근 즉시 unpin하는 단일 요청자다. dirty는 모두0이며 동시 요청이 없다.

CLOCK은 frame들을 원으로 놓고 접근 시 ref=1로 만든다. 교체 시 hand에서 pin된 것을 건너뛰고, unpinned ref1은0으로 지우며 다음으로 간다. unpinned ref0에서 교체하고 새 ref1을 주고 hand를 다음 frame으로 옮긴다. 이 계약에서 pin된 페이지의 ref를 건드리지 않기로 한다. CLOCK의1비트는 정확한 모든 최근 순서를 저장하지 않는다.

최근성만으로 모든 패턴을 예측하지 못한다

buffer보다 큰 테이블을 순차로 여러 번 훑으면 LRU가 다음 회차에 재사용할 페이지를 계속 교체하는 sequential flooding이 생길 수 있다. 중요한 소수 페이지를 반복 사용하다 큰 일회성 scan을 섞어도 scan이 cache를 오염시킬 수 있다. 각 query의 작은 ring·scan bypass·반복 접근 이력·priority hint는 이런 상황을 완화하는 선택이다.

미래 참조를 아는 최적 교체는 비교 기준으로 유용하지만 실제로 일반 미래를 알 수는 없다. MRU나 LRU-K가 특정 pattern에서 유리할 수 있어도 모든 trace에서 최적은 아니다. policy overhead·pin 후보 제한·dirty write·I/O 지연을 함께 평가하고 hit율 한 숫자를 전체 경과시간과 같다고 취급하지 않는다.

미리 읽기는 일을 없애기보다 기다림을 옮긴다

query plan이 다음 scan page를 알려 주면 현재 page를 계산하는 동안 다음 I/O를 시작할 수 있다. I/O와 계산의 겹침이 가능하고 준비 frame과 backend 자원이 있어야 한다. 첫 page의 초기 대기는 남고 다음 page가 소비 시점까지 완료되지 않으면 여전히 기다린다.

prefetch한 page를 실제로 쓰지 않으면 I/O·memory를 낭비하며 유용한 page를 밀어낼 수도 있다. 과도한 prefetch가 demand 요청과 대역폭을 경쟁하면 응답이 늦어질 수 있다. 평가에서 demand miss와 실제 storage read, 미사용 prefetch, 준비 지연을 나누며 OS의 다른 cache가 있는지도 확인한다.

시계 방향으로 A, B, C가 놓이고 바늘은 A를 가리킵니다. 참조 비트는 A=1, B=0, C=0이고 pin은 A=0, B=1, C=0입니다. 새 D가 필요합니다. pin 페이지는 비트도 건드리지 않고 지나가며, 비트 1은 0으로 바꾸고 지나가고, 사용하지 않는 비트 0을 교체합니다. 새 페이지 비트는 1이고 바늘은 다음 자리로 이동합니다.

힌트 1

바늘이 보는 순서대로 한 자리씩 처리합니다.

힌트 2

B의 비트가 0이어도 pin 조건이 먼저 적용됩니다.

풀이와 답 확인

  1. A의 참조 비트를 0으로 바꾸고 지나갑니다.

  2. B는 사용 중이라 그대로 지나갑니다.

  3. C는 사용하지 않고 비트가 0이므로 D로 바꿉니다. 다음 자리는 A입니다.

C가 교체됩니다. A의 비트는 0, B의 비트는 0 그대로, D의 비트는 1이며 바늘은 A를 가리킵니다.

흔한 오답에서 다시 생각하기

비트 0인 B를 먼저 교체합니다.

사용 중인 페이지를 제외하는 조건을 빠뜨렸습니다. 최근 접근 비트가 낮아도 pin은 별도로 보호합니다.

연습 2 · 오류 찾아 고치기

두 프레임뿐인 구현이 예제의 세 번째 읽기를 시각 6에 시작하려고 둘째 페이지가 든 프레임을 덮어씁니다. 둘째 페이지는 아직 계산하지 않았습니다. 오류와 두 프레임으로 가능한 수정 일정을 구하세요.

힌트 1

첫 계산이 끝나는 시각은 8입니다.

힌트 2

계산하지 않은 둘째 페이지는 보존해야 합니다.

풀이와 답 확인

  1. 둘째 프레임의 미처리 페이지를 덮어쓰는 동작을 금지합니다.

  2. 첫 페이지 계산이 시각 8에 끝나면 그 자리에 셋째 페이지를 [8,11)에 읽습니다.

  3. 둘째 계산은 [8,13), 셋째 계산은 [13,18)로 유지합니다.

셋째 읽기를 [8,11)로 늦추면 두 프레임으로도 이 사례의 종료 시각 18ms를 유지할 수 있습니다. 시각 6의 원래 일정은 불가능하지만 최종 시간까지 반드시 늘어난다는 뜻은 아닙니다.

흔한 오답에서 다시 생각하기

프레임이 부족하니 종료 시각도 무조건 21ms가 됩니다.

자원 부족은 해당 시작 시각을 막습니다. 수정한 읽기가 다음 계산 시작 전 끝나는지 확인하면 이 경우의 추가 지연은 없습니다.

읽기 6ms, 계산 4ms인 세 페이지를 세 프레임으로 처리합니다. 두 담당은 각각 하나이고 독립적으로 겹칠 수 있습니다. 읽기와 계산 구간을 구성하고 직렬 시간과 비교하세요.

힌트 1

읽기 담당은 세 페이지를 순서대로 읽습니다.

힌트 2

풀이와 답 확인

  2. 계산은 [6,10), [12,16), [18,22)입니다.

겹친 일정은 22ms이며 직렬보다 8ms 짧습니다. 계산 담당은 읽기를 기다리는 구간이 생깁니다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

실제로 사용할 페이지는 A, B 두 개이고 C는 사용하지 않습니다. 읽기 담당 하나가 A, C, B 순서로 미리 읽습니다. 읽기 6ms, 계산 4ms이며 세 프레임입니다. 필요한 두 페이지만 A, B 순서로 읽는 경우와 종료 시각·읽기 수를 비교하세요.

힌트 1

쓰지 않는 C도 읽기 담당의 시간을 차지합니다.

힌트 2

B를 계산할 수 있는 가장 이른 시각을 각각 구합니다.

풀이와 답 확인

  1. A, B만 읽으면 A 읽기 [0,6), 계산 [6,10), B 읽기 [6,12), 계산 [12,16)입니다.

  2. A, C, B를 읽으면 B 읽기는 [12,18)로 늦고 B 계산은 [18,22)입니다.

소단원 3.3

캐시·직접 I/O·동시성

DB buffer에 없다는 것이 저장장치에서도 읽어야 한다는 뜻일까?

준비 개념과 학습 목표

준비 개념

  • DB buffer와 OS page cache는 서로 다른 층이다. 같은 페이지가 여러 곳에 복사될 수 있다.

  • direct I/O는 특정 OS cache 경로를 줄이는 선택이며 buffer 관리·WAL·내구성을 대신하지 않는다.

  • latch는 내부 자료구조의 짧은 동시 접근을 보호한다. transaction lock의 논리 격리와 pin 수명 보호를 구별한다.

학습 목표

  • 두 cache 층의 조건부 miss를 계산한다.

  • 직접 I/O의 정렬·지원·내구성 한계를 설명한다.

  • 동일 miss 동시 처리와 flush 버전 문제를 추적한다.

캐시가 두 층이면 두 히트율을 그냥 곱해도 될까요?

데이터베이스 버퍼에서 찾은 페이지는 운영체제 캐시를 확인하지 않을 수 있습니다. 운영체제 캐시에 도달하는 요청은 앞 단계에서 놓친 요청뿐입니다. 따라서 단계마다 어떤 요청을 분모로 삼는지 먼저 적어야 합니다.

직접 I/O도 자동으로 모든 문제를 해결하지 않습니다. 정렬 조건은 파일시스템과 구현 조건에 따라 달라질 수 있고, 운영체제 캐시를 우회하려는 선택과 저장 완료를 보장하는 동기화는 별개의 문제입니다. 아래 주소와 비용은 공식 제품의 성능 측정이 아니라 이해를 위한 모형입니다.

먼저 확인할 개념
  • 세마포어·조건변수·모니터

    동일 페이지의 중복 읽기를 막고 대기자를 깨우는 상태 전이를 연결합니다.

  • append-only와 정리

    저장과 정리가 참조의 수명·실패 처리에 미치는 영향을 연결합니다.

miss에는 어떤 cache의 miss인지 붙인다

DB buffer miss라도 OS page cache가 같은 자료를 갖고 있으면 장치에서 새로 읽지 않고 복사하는 경로가 가능하다. DB hit율, OS hit율, 실제 장치 읽기 횟수를 구별한다. 중복 복사에 메모리가 들고 서로 다른 교체정책이 정보를 따로 관리하므로 두 층을 두었다는 것만으로 항상 더 효율적이지 않다.

일부 DBMS는 직접 I/O를 사용해 OS page cache를 우회하고 자신이 재사용·prefetch·쓰기 순서를 관리한다. 다른 시스템은 OS cache를 활용한다. DBMS별·파일 종류별 설정이 다르고 장치/서버 cache가 남을 수도 있어 direct라는 단어를 저장장치의 모든 cache 제거로 읽지 않는다.

직접 읽기와 안정 저장은 별개다

Linux O_DIRECT는 buffer 주소·I/O 길이·파일 offset에 정렬 제한이 있을 수 있고 지원 여부·오정렬 처리도 filesystem과 kernel에 따라 다르다. 이 단원은 선택된4096B 정렬 모형으로 계산하며 모든 Linux 파일에 같은 제약이 있다고 주장하지 않는다. 반환 오류나 fallback 경로를 실제 환경에서 확인해야 한다.

O_DIRECT 자체는 O_SYNC와 같은 내구성 보장이 아니다. DB가 요구하는 WAL 순서·flush·오류 처리는 남는다. buffered/direct/mmap 접근을 같은 파일의 겹치는 영역에 섞으면 coherency와 성능 문제가 생길 수 있다. 작업 파일을 실제로 열지 않고 규칙과 상태만 종이로 판단한다.

동시 miss는 같은 frame의 수명과 내용을 연결한다

두 thread가 같은 페이지를 동시에 miss로 발견하면 아무 보호 없이 각각 load를 시작해 복사본이 두 개 생길 수 있다. page table에 LOADING 상태를 예약하고 나머지는 기다리거나 기존 load에 참여하도록 구성하는 방법이 있다. 예약·frame 확보·pin·I/O완료·오류 정리·READY 공개의 순서를 서로 일관되게 보호해야 한다. 긴 I/O 동안 전역 latch를 계속 잡는 구현은 다른 요청을 막을 수 있어 latch 범위를 설계한다.

pin은 사용 중 frame을 바꾸지 못하게 하고 latch는 metadata/content의 원자적 변경을 보호한다. flush가 version5 복사본을 쓰는 동안 writer가 version6을 만들면5의 완료로6의 dirty를 제거하면 안 된다. frame generation과 page ID도 확인해 늦은 완료가 이미 재배정된 frame을 수정하지 않게 한다. pool을 나누어 경합을 줄일 때는 한 pool이 꽉 차고 다른 pool이 남는 불균형도 생길 수 있다.

조건부 히트율과 전체 평균

표의 요청에서 OS 캐시 조건부 히트율, 장치에 도달할 전체 비율, 요청당 평균 비용을 구하세요.

  1. DB 버퍼에서 놓친 요청은 200개입니다. OS 캐시는 그중 150개를 처리하므로 조건부 히트율은 150/200=75%입니다.

  2. 장치까지 간 것은 50/1000=5%입니다. 같은 사실을 DB 미스 비율 20%와 그 이후 OS 미스 비율 25%의 곱으로 구할 수 있습니다.

  3. 전체 비용은 800×1+150×10+50×100=7300U입니다.

같은 페이지를 동시에 요청합니다

빈 버퍼에서 T1과 T2가 동시에 P를 요청합니다. 상태는 ABSENT, LOADING, READY 중 하나이며 LOADING을 등록하는 검사는 하나의 보호된 동작입니다. 읽기는 성공하고 두 요청은 모두 참조를 얻습니다.

  1. T1이 P가 없음을 확인하고 LOADING을 등록합니다. 이 동작과 등록 사이에 T2가 끼어들어 별도 읽기를 시작할 수 없어야 합니다.

  2. T2는 LOADING을 보고 대기합니다. T1의 읽기가 성공하면 보호된 상태에서 READY로 바꾸고 T1의 참조를 확보한 뒤 대기자를 깨웁니다. T2도 참조를 얻기 전까지 프레임이 교체되지 않도록 대기 중인 요청의 예약을 유지하거나 보호된 상태에서 다시 확인하는 절차가 필요합니다.

  3. 두 요청이 각각 pin을 얻으면 pin은 2입니다. 한 요청만 해제하면 pin은 1입니다.

장치 읽기는 한 번이며 두 요청이 참조를 얻은 뒤 pin은 2입니다. 한 번 해제한 뒤에도 사용자가 남으므로 교체할 수 없습니다.

    공개 원문 실제 줄 382–414와 1739–1905를 읽었다. 직접 I/O와 동기화 저장의 구별, 주소·길이·오프셋 정렬 조건 및 파일시스템별 차이를 대조했다. 이 원문의 역사적 설명을 현재 모든 Linux의 동일한 계약으로 일반화하지 않으며 4096 배수 규칙은 별도로 정의한 손모형이다.

새 페이지 D는 깨끗한 프레임 C를 교체합니다. A의 두 참조를 모두 해제한 뒤 새 페이지 E는 오래된 dirty 프레임 A를 교체합니다. 이 과정의 페이지 읽기는 2회, 페이지 쓰기는 1회이며 WAL 저장은 별도입니다. 세 참조를 획득하고 두 참조를 해제하면 pin 카운트는 1입니다. LRU의 접근 순서가 A, B, A, C, B, A이면 히트는 1회, 미스는 5회입니다. CLOCK은 A의 참조 비트를 지우고 사용 중인 B를 건너 C를 교체하며 다음 바늘은 A입니다. 페이지마다 읽기 3 ms와 계산 5 ms가 필요한 세 프레임 일정은 18 ms에 끝납니다. 두 프레임 수정 일정에서도 셋째 페이지를 8 ms부터 11 ms까지 읽으므로 전체는 18 ms에 끝납니다. 페이지마다 읽기 6 ms와 계산 4 ms가 필요한 세 페이지 일정은 22 ms에 끝납니다. 필요한 A와 B만 읽으면 16 ms에 끝나지만 불필요한 C를 사이에 넣으면 22 ms에 끝납니다. 요청 1000개 중 DB 히트 800개, DB 미스 뒤 OS 히트 150개, 장치 읽기 50개의 전체 경로 비용은 7300U이고 평균은 7.3U입니다. 같은 경로 비용에서 DB 히트 900개, OS 히트 60개, 장치 읽기 40개이면 총비용은 5500U이고 평균은 5.5U입니다. 주소 8193을 4096으로 나눈 나머지는 1입니다. 전이 문제의 200개 요청은 총비용 1460U, 평균 비용 7.3U입니다. 모두 손검산이며 실제 DB, 장치, 동시성, 전원 차단 실험은 수행하지 않았습니다.
