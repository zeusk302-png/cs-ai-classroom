두 복제본의 확인을 기다려도 세 번째 복제본은 아직 옛 값을 읽을 수 있을까요?

한 거래의 commit에 대해 primary의 영속화는 시각 2 ms에 끝납니다. 직접 연결되어 선택 가능한 세 standby R1, R2, R3의 확인 시각을 아래 표에 지정합니다. 시각은 primary가 해당 확인을 받은 시점으로 통신 지연까지 포함하며 실제 측정은 아닙니다. 운영체제 기록, 영속 flush, 읽기에 가시인 적용 확인은 서로 다릅니다.

ANY 2는 후보 세 개 중 조건을 먼저 만족한 두 개의 확인을 기다립니다. FIRST 2는 연결된 R1과 R2를 우선 대상으로 선택한다고 정합니다. 다른 변경과 연결 끊김은 없습니다. 어느 두 개를 기다리는지와 어떤 완료 단계를 기다리는지 모두 적어야 성공 응답의 의미를 읽을 수 있습니다. 이는 복제 확인이며 여러 참가자의 2PC 결정과 별개입니다.

복제본은 같은 시각에 같은 위치에 있지 않을 수 있다

복제는 자료 사본을 여러 위치에 유지하는 방법이다. 비동기 복제에서는 주 서버가 성공을 응답한 뒤 복제 서버가 변경을 받을 수 있다. 그러므로 복제 서버에서 읽은 옛 값은 복제 지연으로 설명될 수 있으며, 복제본 존재만으로 최신 읽기를 보장하지 않는다. 장애로 주 서버를 잃으면 아직 전달되지 않은 성공 변경도 잃을 수 있다.

동기 복제는 어느 서버의 어떤 확인을 기다리는지 계약을 지정한다. PostgreSQL의 remote_write는 대기 서버 운영체제에 기록된 확인이고 remote_apply는 적용되어 읽기에 보이는 확인까지 기다린다. 영속 저장 확인과 운영체제 기록 확인은 다르다. 지정된 대기 서버를 기다린 성공이 모든 서버의 즉시 최신화를 뜻하지 않으며, 기다리는 대상이 응답하지 않으면 가용성에 영향을 준다.

여러 참가자가 하나의 결정을 공유한다

두 계좌가 서로 다른 참가자에 있으면 한 계좌 차감만 commit하고 다른 계좌 입금을 취소하는 결과를 막아야 한다. 2PC의 첫 단계에서 조정자는 각 참가자에게 준비를 요청한다. 참가자는 필요한 상태를 영속적으로 남기고 준비 가능 여부를 답한다. 전원 준비가 확인된 뒤 조정자는 commit 결정을 영속적으로 기록하고 전달한다. 참가자 거절이 있으면 commit 조건을 충족하지 못한다.

준비 완료는 전체 commit 완료와 다르다. 준비한 참가자가 결정 메시지를 받지 못했다면 타임아웃만으로 마음대로 abort하면 안 된다. 조정자가 이미 commit을 결정했을 수 있기 때문이다. 2PC는 일부 장애에서 결정 확인을 기다리며 막힐 수 있다. 복구 가능한 로그·참가자 식별·결정 전달과 복구 절차가 필요하며, 단지 메시지 두 번을 보내는 코드가 아니다.

복제·원자성·격리는 다른 질문이다

복제는 사본의 유지와 장애 대응을 다루고 원자적 commit은 여러 참가자의 전체 결정 일치를 다룬다. 격리는 여러 동시 트랜잭션이 어떤 값을 보고 어떤 결과를 만들 수 있는지를 다룬다. 2PC만 사용했다고 직렬가능성이나 최신 복제 읽기까지 자동으로 얻지는 않는다.

PostgreSQL의 PREPARE TRANSACTION은 외부 트랜잭션 관리자가 사용하는 2PC 인터페이스다. 준비 상태는 잠금 등을 계속 보유하며 오래 남으면 유지 관리에 영향을 준다. 이 단원은 명령 실행을 요구하지 않고 종이 참가자 표만 만든다. 제품 문서와 자체 상태표를 동일한 실제 실행 증거로 취급하지 않는다.

중간 과정을 따라가는 예제

자체 계좌 A 80과 B 20을 참가자 P와 Q에 나누어 두고 10을 A에서 B로 옮긴다. P·Q는 각각 70·30 변경을 준비했다. 조정자는 commit 결정을 영속화했지만 Q에 보낸 결정이 유실되었다. Q는 준비 상태에서 타임아웃을 관찰한다. Q가 abort하면 되는가?

  1. 준비한 후보 값의 합은 70+30=100이고 초기 합도 80+20=100이다. 합 보존은 이 거래의 필요한 조건 중 하나다.

  2. 조정자의 영속 결정은 commit이다. P가 이를 적용해 A 70을 확정했다고 하자. Q가 독자적으로 abort하여 B 20을 유지하면 전체 합은 90이 되어 거래가 찢어진다.

  3. Q는 준비 상태와 로그를 보존하고 결정 확인·복구 절차를 따라야 한다. 타임아웃은 응답 부재의 관찰이며 조정자의 abort 결정을 증명하지 않는다.

독자적 abort는 정당화되지 않는다. 결정 확인 뒤 양쪽 commit 결과는 70·30이다. 복구가 언제 끝나는지는 별도 장애·통신 조건에 달린다.

조건을 바꾸어 비교하기

확인 단계에 따라 둘째 도착이 달라집니다

ANY 2에서 remote_write, 영속 flush를 기다리는 on, remote_apply의 가장 이른 성공 응답 시각을 구하세요. 다른 처리 비용은 없습니다.

  1. 운영체제 기록 확인은 R3가 3 ms, R1이 4 ms에 도착하므로 두 확인은 4 ms에 모입니다.

  2. 영속 flush 확인은 R1이 6 ms, R2가 7 ms에 도착하므로 두 확인은 7 ms에 모입니다.

  3. 적용 확인은 R1이 9 ms, R2가 12 ms에 도착하므로 두 확인은 12 ms에 모입니다.

ANY 2의 지정 성공 응답 시각은 remote_write에서 4 ms, on에서 7 ms, remote_apply에서 12 ms입니다.

비교할 점

서로 다른 단계의 가장 빠른 서버를 같은 확인 집합으로 고정하지 않습니다.

한 참가자가 결정을 못 받았습니다

별도 2PC 모형에서 A=80, B=20, C=50이고 A에서 B로 10을 옮깁니다. 세 참가자는 모두 준비 YES이며 조정자는 commit 결정을 영속화했습니다. A 담당자는 commit했지만 B 담당자는 결정을 못 받아 준비 상태입니다. B 담당자가 독자 abort하면 각 값과 합은 어떻게 되나요? C는 변경하지 않습니다.

  1. 전체 commit 기대는 A=70, B=30, C=50이며 합은 150입니다.

  2. B 담당자가 독자 abort하면 개별 확정값은 A=70, B=20, C=50으로 합이 140이 됩니다.

  3. 준비한 참가자의 응답 부재만으로 이미 영속화된 commit 결정을 바꾸지 않습니다.

독자 abort는 전체 원자성 계약을 깨뜨립니다. B 담당자는 준비 상태를 유지하고 영속 결정을 확인하는 복구 절차를 따릅니다.

비교할 점

이 표는 각 참가자의 상태 비교이며 준비 거래를 모두 읽을 수 있는 하나의 정상 읽기 snapshot이라고 주장하지 않습니다.

종이와 본문으로 직접 해보기

주 서버의 완료 변경 표지는 10·20·30이고 비동기 복제본은 10·20까지만 받았다. 주 서버의 표지 30 성공 응답 뒤 복제본을 읽을 때의 한계와, 주 서버 전체 손실 때 빠질 수 있는 변경 수를 적자.

연습 1 · 값과 상태 예측

같은 확인 표에서 FIRST 2의 현재 선택은 R1과 R2입니다. remote_write 성공 시각과 ANY 2의 remote_write 성공 시각을 비교하세요.

힌트 1

R3는 FIRST의 현재 선택 밖입니다.

힌트 2

선택한 두 확인 중 더 늦은 시각을 기다립니다.

풀이와 답 확인

  1. FIRST 2는 R1의 4 ms와 R2의 5 ms를 모두 기다려 5 ms입니다.

  2. ANY 2는 R3와 R1의 확인이 모이는 4 ms입니다.

FIRST 2는 5 ms, ANY 2는 4 ms입니다. 지정된 후보와 선택 정책이 달라 대기 시각도 달라집니다.

연습 2 · 오류 찾아 고치기

ANY 2 remote_apply 응답을 12 ms에 받았으니 R3의 새 snapshot 읽기도 이 거래를 반드시 본다고 썼습니다. 표를 이용해 고치세요.

힌트 1

R3의 적용 확인은 14 ms입니다.

힌트 2

이미 시작한 snapshot과 적용 뒤 새 읽기도 구분합니다.

풀이와 답 확인

  1. 12 ms의 응답은 R1과 R2의 적용 확인을 근거로 합니다.

  2. R3의 적용은 아직 확인되지 않았으므로 R3의 새 읽기가 이 거래를 반드시 본다고 보장하지 않습니다.

  3. 과거 snapshot을 유지하는 읽기는 적용 뒤에도 별도 가시성 조건이 필요합니다.

대기한 두 standby의 확인을 모든 standby의 즉시 최신화로 확대하지 않습니다.

quorum을 채우면 모든 복제본의 적용도 동시 완료다.

확인 집합 밖의 서버는 같은 시각에 같은 단계에 도달하지 않을 수 있습니다.

연습 3 · 직접 만들어 보기

2PC 준비 단계에서 P와 Q는 YES, R은 NO를 보냈습니다. 조정자가 전원 YES일 때만 commit하는 계약입니다. 결정을 영속적으로 남기고 참가자에게 전달하는 안을 쓰세요.

힌트 1

복제 quorum의 두 확인 규칙을 적용하지 않습니다.

힌트 2

준비한 참가자도 알려진 최종 결정을 따라야 합니다.

풀이와 답 확인

  1. 전원 YES 조건을 만족하지 못하므로 commit하지 않습니다.

  2. 조정자는 abort 결정을 기록하고 참가자에게 전달합니다.

  3. YES였던 참가자도 이 abort 결정을 확인하여 준비 변경을 종료합니다.

이 2PC 계약의 최종 결정은 abort입니다. 세 개 중 YES 두 개를 복제 quorum처럼 세지 않습니다.

흔한 오답에서 다시 생각하기

두 YES가 과반수라 전체 commit한다.

이 프로토콜의 commit 조건은 전원 준비이며 다른 프로토콜의 투표 수를 대입하지 않습니다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

ANY 2 remote_apply에서 R2는 연결되어 후보로 남지만 적용 확인을 보내지 못합니다. R1과 R3의 지정 적용 확인 시각은 그대로입니다. FIRST 2의 현재 선택도 R1과 R2로 고정하며 후보 교체는 없다고 정합니다. 두 정책의 완료를 비교하세요.

힌트 1

R2의 뒤늦은 확인 시각을 임의로 만들지 않습니다.

힌트 2

정상 응답만 골라 계산한 p95가 모든 요청의 지연을 대표할까요?

같은 20초의 가상 측정 구간에서 시도, 응답 완료, 정확 완료를 나눕니다. A는 시도 1800건, 응답 완료 1700건, 정확 완료 1600건입니다. B는 시도 2600건, 응답 완료 2500건, 정확 완료 1500건입니다. 정확 완료는 응답 완료의 부분집합이며 실패에는 오답·거절·타임아웃 등이 있습니다.

지연 예제의 1000개 정상 완료 응답과 별도 타임아웃 100개는 다른 모집단입니다. 정상 완료 응답의 p95를 전체 시도의 p95로 바꾸지 않습니다. nearest-rank는 정렬한 N개 표본의 ceil(pN)번째입니다. 여기에 나오는 숫자는 TPC-C 실행이나 실제 제품 순위가 아닌 자체 보고 연습입니다.

작은 엔진도 경계 계약이 필요하다

파서가 만든 질의가 실행기를 거쳐 저장 계층을 읽고 결과를 돌려주는 흐름에서 각 경계의 자료 형태·오류·소유권·트랜잭션 상태를 연결한다. 개별 정렬기가 맞아도 취소된 거래의 변경을 저장 계층이 노출하면 전체 엔진은 틀릴 수 있다. 통합 시험은 전체 입력과 기대 자료 상태를 함께 고정한다.

작은 범위부터 시작하면 실패 원인을 찾기 쉽다. 고정 레코드 두 개를 읽고 변경·commit·재시작까지 사건을 확장한다. 실제 저장하지 않는 메모리 엔진의 시험을 디스크 내구성 시험이라고 부르지 않는다. 제품 간 비교에서는 지원하지 않는 기능과 사용한 설정도 함께 적는다.

부하 조건과 결과 정의를 먼저 쓴다

benchmark는 정해 둔 작업을 반복하여 성능을 측정하는 절차다. 자료량·질의 조합·읽기/쓰기 비율·동시 고객 수·하드웨어·초기 상태·예열·측정 구간·타임아웃을 명시해야 숫자의 의미를 비교할 수 있다. 자료가 모두 메모리에 들어가는 실험을 더 큰 디스크 작업으로 그대로 외삽하지 않는다.

시도 처리율과 정확한 완료 처리율을 구별한다. 초당 많은 요청을 거절하거나 잘못 답해도 시도 수는 높을 수 있다. 지연은 어떤 모집단의 응답을 측정했는지와 실패·타임아웃 처리를 적는다. 평균 하나는 긴 꼬리를 숨길 수 있으므로 실제 표본 수와 백분위 계산 규칙을 함께 보여 준다.

표준 이름에는 표준 조건이 붙는다

TPC-C는 여러 거래 유형의 혼합과 응답 조건 등을 지정하고 그 안에서 New-Order 처리 지표 tpmC를 정의한다. 임의의 SELECT 반복이나 자체 잔액 표를 TPC-C 점수라고 부르지 않는다. 공인 결과를 주장하려면 그 규약·공개 조건을 충족해야 하고 서로 다른 TPC 시험의 지표도 그대로 비교하지 않는다.

이 단원의 표는 계산 연습용 가상 자료이며 공인 benchmark나 실제 실행 측정이 아니다. 실제 측정에는 동일 조건 반복과 변동 설명이 필요하다. 비용 비교도 어떤 장비·저장·운영 범위를 포함했는지 적고 보편적인 제품 순위를 가상 숫자로 만들지 않는다.

  2. B의 시도 처리율은 1,500/10=150회/s이고 정확 완료 처리율은 800/10=80건/s다. 정확 완료율은 800/1,500≈53.3%다.

  3. 이 표에서는 B가 더 많은 요청을 시도했으나 정확히 완료한 건수는 A보다 작다. 단위와 분모를 생략한 숫자 150만으로 B의 품질이 낫다고 판단하지 않는다.

A 100회/s·90건/s·90%, B 150회/s·80건/s·약 53.3%다. 가상 결과이며 실제 엔진 비교가 아니다.

  2. p95의 순위는 950번째라 45 ms입니다.

  3. p99의 순위는 990번째라 500 ms입니다.

정상 완료 표본의 평균은 67.75 ms, p95는 45 ms, p99는 500 ms입니다.

답의 정확성에는 개별 조건도 있다

거래 전후 잔액 합이 같다는 것은 합 보존 조건의 검사다. 금액을 잘못된 상대에게 옮기거나 두 계좌를 그대로 두어도 합은 맞을 수 있다. 따라서 입력 거래와 각 계좌의 기대 값·성공/실패 판정·중복 요청 처리까지 비교한다. 불변식 하나가 모든 결과 계약을 대신하지 않는다.

정확성 보고는 어떤 입력을 어떤 기준 답과 대조했는지 명시한다. 자체 작은 모형의 계산 확인과 실제 엔진 관찰을 분리한다. 기대 답을 만든 계산도 틀릴 수 있어 독립 추적과 반례가 필요하다. 학습자 실험은 학습자가 실제 수행하기 전에는 미수행으로 남긴다.

동시성은 사건 순서로 조사한다

동시에 실행했다는 사실만으로 격리 수준을 검증하지 못한다. 누가 언제 무엇을 읽고 썼는지, commit·abort·재시도가 어떻게 끝났는지 기록한다. 두 증가 요청이 모두 성공했는데 최종 값이 한 번만 증가하면 lost update 의심을 조사한다. 모든 동시 시험을 통과해도 조사하지 않은 이력을 증명하지는 않는다.

직렬가능성을 주장할 때는 어떤 직렬 결과와 대응하는지, 범위 읽기·삽입·삭제까지 포함했는지 조건을 적는다. 분산 환경에서는 여러 참가자의 결정 일치와 복제 읽기 시점도 별도로 기록한다. 단일 스레드 모형의 계산을 실제 경쟁 시험으로 보고하지 않는다.

내구성은 성공 응답과 장애 경계를 연결한다

내구성 보고는 성공 응답 전에 무엇을 영속화하는 계약인지와 어떤 장애를 실제 시험했는지 함께 적는다. 프로세스 종료·운영체제 장애·서버 전체 손실은 남는 자료가 다르다. 주 서버 WAL에 남은 변경이 비동기 복제본에도 이미 존재한다고 가정하면 장애 범위를 과장한다.

보고에는 버전·설정·초기 자료·사건 로그·기대/관찰·실패·남은 제약을 담는다. 시험 계획과 실제 수행 개수, 수행 중 통과 개수의 분모를 구별한다. 미수행 복구·동시성 항목을 파일 존재나 재시작 화면만으로 통과로 표시하지 않는다. 이 단원은 이러한 보고 양식을 종이로 채우는 연습이다.

  1. 세 결과 모두 합은 100이다. 합 검사만 쓰면 X·Y·Z 모두 통과한다.

  3. X의 값 일치는 이 사례의 결과 검사다. 경쟁 이력이나 영속 상태·장애 복구를 관찰한 근거가 없으므로 동시성·내구성 전체 통과로 확대하지 않는다.
