소단원 1.1

파서·최적화·실행·저장 계층

한 줄의 SELECT 뒤에는 왜 여러 종류의 일이 있을까?

준비 개념과 학습 목표

준비 개념

  • 레코드는 한 대상의 필드 묶음이고 표는 레코드의 모음이다. 페이지는 저장 계층이 다루는 고정 크기 데이터 조각이다.
  • SQL은 원하는 결과를 기술하는 언어다. 여기서는 정수 id·score, NULL 없음, 중복 없는 id와 변하지 않는 표를 가정한다.
  • 연산자는 입력에서 결과를 만드는 절차다. 필터는 조건에 맞는 행을 남기고 투영은 선택한 열을 남긴다.

학습 목표

  • 구문·이름 해석·계획·실행·저장의 역할을 구분한다.
  • 결과 의미를 유지한 두 접근 방법의 가상 페이지 비용을 비교한다.

문자열을 의미 있는 요청으로 만든다

토큰화는 문자열을 SELECT·이름·연산자 등으로 나누고 파싱은 문법에 맞는 구조를 만든다. 이름 해석은 T와 score가 실제 스키마에 있는지 확인한다. 문법이 맞아도 없는 열을 읽는 요청은 유효하지 않다. 구현에서는 이 단계가 합쳐질 수도 있지만 책임은 구분할 수 있다.

SELECT id FROM T WHERE score >= 70은 필터 뒤 id를 투영하라는 뜻이다. ORDER BY가 없으므로 행 순서를 계약으로 삼지 않는다. 일반 SQL에는 NULL·중복·자료형 변환 등이 있으므로 여기의 단순 집합 설명을 모든 SQL로 확대하지 않는다.

계획을 바꿔도 답의 의미는 유지한다

논리 계획은 무엇을 계산할지, 물리 계획은 스캔·인덱스 등 어떻게 계산할지 정한다. 최적화는 허용된 의미를 보존하면서 비용이 낮을 것으로 추정한 계획을 고른다. 추정에는 통계와 비용 모형의 오차가 있으므로 이름이 최적화라고 실제 최저 시간을 보장하지 않는다.

가상 표 T={(1,60),(2,80),(3,70),(4,50)}의 첫 두 행은 P0, 나머지는 P1에 있다. 캐시가 처음 비어 있고 각 페이지 접근 비용이 1이며 다른 비용을 무시하면 스캔은 2이다. 인덱스 경로가 인덱스 페이지 2개와 데이터 페이지 2개를 읽는다고 정하면 비용 4이다. 이 작은 모형에서는 인덱스가 더 비싸다.

실행과 저장을 연결한다

iterator 모형에서는 상위 연산자가 하위 연산자의 Next를 호출해 행을 요청한다. 필터는 불합격 행을 건너뛰며 합격 행이나 정상 끝을 반환한다. 실제 오류는 정상 끝과 다른 상태로 전달해야 한다. batch 모형은 여러 행을 한 번에 보내고 materialization은 결과 묶음을 만든다.

저장 계층은 레코드 위치와 페이지를 다루고 버퍼는 이미 읽은 페이지를 재사용한다. DBMS 페이지 미스가 반드시 장치의 물리 읽기 한 번은 아니다. OS 캐시가 데이터를 줄 수 있다. SQLite는 SQL을 바이트코드로 만들고 VM·B-tree·pager·VFS로 이어지는 실제 설계를 제공한다. 이 모형은 특정 엔진의 모든 내부 절차를 복제한 것이 아니다.

중간 과정을 따라가는 예제

위의 T와 P0·P1에 대해 SELECT id FROM T WHERE score >= 70을 스캔하라. 순서는 설명용 스캔 순서다.

  1. 파싱·이름 해석을 통과한 후 scan → filter(score >= 70) → project(id)를 정한다.
  2. P0을 읽고 (1,60)을 거절한다. (2,80)은 합격해 id 2를 낸다.
  3. P1을 읽고 (3,70)은 경계값을 포함하므로 id 3을 낸다. (4,50)은 거절한다.
  4. 다음 요청은 정상 끝이다. 네 행을 검사하고 두 페이지를 가져왔으며 합격 행은 두 개다.

결과는 id 2와 3의 모음이다. 가상 냉간 페이지 비용은 2이며 SQL 자체는 이 출력 순서를 보장하지 않는다.

힌트 보기

>=와 >가 점수 70에 주는 차이를 먼저 표시한다.

풀이 보기

id 2만 남는다. 네 행·두 페이지 스캔은 그대로이므로 정한 비용 모형에서 비용 2다. 결과 수가 줄어도 이 스캔의 페이지 수는 줄지 않는다.

오해와 반례

인덱스가 있으면 항상 더 빠르고, 물리 계획이 다르면 다른 답을 내도 된다.

가정한 인덱스 비용 4는 스캔 2보다 크다. 계획 차이는 실행 방법의 차이지 허용된 결과 의미를 바꿀 허가가 아니다.

답과 이유 보기

한 단계 더

필터를 저장소 가까이 내려 처리량을 줄이는 predicate pushdown을 생각해 보라. 변환은 NULL 의미·부작용·오류·자료형 등의 언어 계약을 보존해야 한다. 비용은 페이지 읽기 외에도 CPU·메모리·정렬·통신을 포함할 수 있으므로 한 지표의 감소가 전체 시간 감소와 같지 않다.

소단원 1.2

시스템 호출과 자원

페이지를 읽어 달라는 요청과 실제 디스크 동작은 같은 사건일까?

준비 개념과 학습 목표

준비 개념

  • 시스템 호출은 프로그램이 OS에 서비스를 요청하는 경계다. 라이브러리 API 한 호출이 시스템 호출 여러 개나 0개로 이어질 수 있다.
  • 파일 기술자 fd는 열린 파일 등을 가리키는 OS의 정수 손잡이다. 버퍼는 바이트를 담는 메모리이고 1 KiB=1024바이트다.
  • 캐시는 다시 쓰기 위한 사본이다. dirty는 메모리의 변경을 저장 상태에 반영해야 함을 뜻하며 전원 장애 뒤 지속을 뜻하지 않는다.

학습 목표

  • 짧은 읽기·EOF·오류를 구분하며 페이지 읽기를 추적한다.
  • 자원 수명·캐시·동기화와 내구성 주장 사이의 조건을 설명한다.

계층마다 다른 사건을 센다

DBMS는 페이지를 요청하고 VFS 같은 추상층은 OS에 맞는 읽기·쓰기·잠금 기능을 제공한다. 여기서는 일반 파일에 양의 count로 읽기를 요청한다. Linux의 read(fd,buf,count)는 최대 count바이트를 요청한다. 성공 반환 n은 실제 읽은 바이트 수이며 n<count 자체는 오류가 아니다. 0은 EOF, -1은 실패이고 errno로 이유를 구분한다.

OS가 캐시에서 읽기를 처리할 수 있으므로 API 호출 수·시스템 호출 수·물리 I/O 수를 같은 수로 세지 않는다. 이 절은 Linux 문서의 의미를 종이로 해석한다. Windows에서는 다른 구현 경로가 쓰일 수 있으며 여기서 Unix 호출을 실행하지 않았다.

페이지는 완성되었을 때만 해석한다

가상 페이지 로더는 필요한 4096바이트가 모일 때까지 남은 길이로 요청한다. 양의 n이 돌아오면 채운 길이를 n만큼 증가시킨다. 목표 전의 EOF는 정상적인 완성 페이지가 아니므로 불완전 페이지 오류로 반환한다. 실패를 빈 페이지로 바꾸면 데이터 없음과 장치 실패를 구분하지 못한다.

이 종이 모형은 다른 스레드가 fd의 위치를 바꾸지 않으며 적절한 메모리를 확보했다고 가정한다. 실제 구현은 offset 지정 읽기·EINTR 처리·취소·반복 상한·비동기 완료 등을 계약에 맞게 정한다. 오류 뒤 진행과 파일 위치는 반환 규칙을 읽고 판단해야 하며 모든 실패를 무조건 재시도하지 않는다.

수명과 동기화에는 별도 계약이 있다

페이지 프레임 4개를 각 4096바이트로 두면 데이터 공간은 16384바이트=16 KiB다. 이것은 메타데이터·쿼리 결과·인덱스·프로세스 전체 메모리를 포함하지 않는다. pin은 사용 중인 프레임의 축출을 막는 모형의 참조 표시다. 사용하는 동안 참조를 유지하고 완료 뒤 해제해야 하며 용량 부족도 오류나 대기를 설계해야 한다.

쓰기 성공만으로 여러 페이지 트랜잭션의 원자성·내구성을 증명하지 않는다. Linux fsync는 파일 데이터와 필요한 메타데이터 동기화를 요청하지만 새 파일명의 디렉터리 항목에는 별도 디렉터리 fsync가 필요할 수 있다. DBMS 로그·순서·복구와 파일시스템·장치 보장이 함께 맞아야 한다. 단일 함수 이름만으로 전원 장애 시험을 대체할 수 없다.

중간 과정을 따라가는 예제

독점적으로 사용하는 fd에서 4096바이트 페이지를 읽는다. 연속 성공 반환이 1024, 2048, 1024바이트라고 가정하고 요청 길이를 추적하라.

  1. 채운 길이 0, 요청 4096. 반환 1024를 기록하면 채운 길이 1024다.
  2. 남은 3072를 요청한다. 반환 2048 뒤 채운 길이는 3072다.
  3. 남은 1024를 요청한다. 반환 1024 뒤 길이는 4096이다.
  4. 완성 페이지가 되었으므로 해석할 수 있다. 양의 반환마다 파일 위치도 그 수만큼 이동하는 일반 읽기 모형이다.

요청은 4096 → 3072 → 1024, 누적 길이는 1024 → 3072 → 4096이다. 세 번의 read 성공을 실제 장치 읽기 세 번이라고 결론 내릴 수 없다.

종이와 본문으로 직접 해보기

힌트 보기

오해와 반례

write가 성공하거나 메모리 페이지가 dirty이면 트랜잭션이 전원 장애에도 보존된다.

dirty는 미반영 변경의 표시다. write·동기화·복구 프로토콜과 장치 조건을 따로 확인해야 하며 여러 변경의 원자성은 추가 계약이다.

메타데이터·다른 버퍼·코드 등은 포함되지 않았다.

한 단계 더

pin 수가 1 이상인 모든 프레임을 축출 금지하면 네 프레임이 모두 사용 중일 때 다섯 번째 페이지 요청을 어떻게 처리할까? 기다림·오류·명시적 자원 예약 같은 정책이 필요하다. 기다림은 다른 실행자가 결국 해제한다는 활성 가정 없이는 완료를 보장하지 않는다. 실제 동시 접근에서는 pin의 원자적 변경과 별도 내용 보호도 검토한다.

출처와 확인 범위

    공식 프로젝트 문서의 count 이하 반환·짧은 읽기·EOF 0·실패 -1 및 errno를 실제 확인했다. Linux 인터페이스 설명이며 Windows에서 실행한 기록이 아니다.

  • Linux man-pages: fsync(2)

소단원 1.3

엔진 API·테스트 기반

빈 결과와 고장 때문에 결과가 없는 상황을 어떻게 구별할까?

준비 개념과 학습 목표

준비 개념

  • API는 호출자와 구현 사이의 입력·출력·오류·수명 계약이다. 연결은 DB를 사용하는 맥락, 준비문은 준비된 한 SQL 실행 객체다.
  • 테스트 fixture는 매 테스트의 초기 데이터를 정하는 장치다. 오라클은 예상 결과를 판단하는 기준이며 오류 주입은 정한 위치에서 실패를 흉내 낸다.
  • ROW는 현재 행, DONE은 정상 끝, ERROR는 실패를 뜻하는 서로 다른 상태다. 종이 모형에서는 이 이름을 추상 상태로 쓰고 실제 SQLite는 구체 반환 코드를 쓴다.

학습 목표

  • 연결·준비문·결과 값의 수명과 오류를 분리한다.
  • 정상·경계·실패 테스트의 기대값을 계약에 맞게 정한다.

API를 상태 전이로 읽는다

SQLite 입문 경로는 open → prepare_v2 → 필요하면 bind → 반복 step → 현재 행의 column 함수군 → finalize → close다. prepare는 실행 준비이며 결과 행을 모두 읽었다는 뜻이 아니다. 모든 호출의 반환을 확인하고 오류 경로에서도 생성된 자원을 정리해야 한다.

step이 SQLITE_ROW를 반환한 뒤에만 유효 열을 읽는다. sqlite3_column은 입문 문서에서 함수군을 가리키는 이름이고 실제 코드는 column_int·column_text 등 구체 함수를 쓴다. TEXT/BLOB 포인터는 SQLite 소유이며 형 변환이나 step/reset/finalize가 수명을 끝낼 수 있다. 나중에 사용할 값은 유효할 때 자기 저장소에 복사하고 반환 포인터를 임의로 free하지 않는다.

정상 끝을 실패와 구별한다

순차 읽기 전용 종이 엔진을 정하자. T={(1,60),(2,80),(3,70),(4,50)}, 두 행씩 P0·P1, NULL 없음과 유일 id를 다시 가정한다. 호출자는 ROW에서 얻은 id를 복사해 후보 목록에 넣고 DONE을 만났을 때만 complete로 게시한다. ERROR라면 후보를 버리고 failed를 게시하는 자체 소비자 정책이다.

실제 스트리밍 API는 실패 전 일부 행을 이미 줄 수 있다. 따라서 ROW 몇 개를 받았다고 전체 쿼리 성공을 주장하지 않는다. 자체 후보 버리기 정책은 SQLite의 모든 결과가 자동 원자 게시된다는 뜻이 아니다. 이 읽기 모형은 트랜잭션 커밋·동시 갱신·디스크 내구성도 증명하지 않는다.

테스트의 초기 조건과 관측을 적는다

각 테스트를 같은 fixture로 시작하고 입력·가상 실패 위치·기대 상태·기대 행·자원 해제를 적는다. 순서 없는 SQL에는 행 모음을 비교하고 순서가 필요하면 ORDER BY 계약을 추가한다. 정상 빈 결과 complete([])는 실패와 별개다. 구문 오류, 없는 열, 페이지 읽기 실패, 메모리 부족도 정상 끝으로 둔갑하면 안 된다.

SQLite의 공식 테스트 설명에는 메모리 및 VFS I/O 실패 주입과 crash testing이 있다. 이를 읽었다는 사실은 이 교재가 그 테스트를 수행했다는 증거가 아니다. 작은 모형이 맞아도 실제 ABI·컴파일·버전·파일시스템·복구·동시성은 별도 시험 대상이다.

중간 과정을 따라가는 예제

위의 T를 초기화하고 SELECT id FROM T WHERE score >= 70을 실행하는 종이 소비자의 상태를 추적하라. P1 요청에서만 오류를 주입한 경우도 비교하라.

  1. 정상 실행에서 ROW(2)를 복사한다. 후보는 [2]이며 아직 complete가 아니다.
  2. ROW(3)를 복사하면 후보는 [2,3]이다. DONE에서 complete({2,3})를 게시한다.
  3. 실패 실행은 P0에서 ROW(2)까지 같지만 P1 요청에서 ERROR다. 후보 [2]를 버리고 failed를 게시한다.
  4. 두 경로 모두 준비문과 연결의 정리 책임을 수행하도록 계약한다. 이는 실제 API 호출 로그가 아닌 종이 상태 전이이다.

정상은 complete({2,3}), 주입 오류는 failed이며 complete({2})가 아니다. 부분 행 수신과 전체 성공을 구별했다.

종이와 본문으로 직접 해보기

힌트 보기

행 없음의 이유가 정상 검색 완료인지 실패인지 확인한다.

풀이 보기

정상은 DONE 뒤 complete([])다. 첫 페이지 오류는 ERROR 뒤 failed다. 빈 목록과 오류는 같은 결과가 아니다.

오해와 반례

정상 예제 하나가 통과하면 엔진 전체가 안전하고 디스크 복구도 검증됐다.

파싱 오류·경계값·메모리/I/O 실패·동시성·크래시 등은 다른 관측이다. 특정 fixture의 종이 성공은 구현과 복구의 시험을 대신하지 않는다.

같은 의미의 질의를 스캔과 다른 계획으로 실행해 결과 모음을 비교하는 differential testing을 생각해 보라. 둘이 같아도 같은 버그를 공유할 수 있으므로 독립 오라클·경계 fixture·실패 주입을 함께 사용한다. 실제 테스트에서는 버전·컴파일 옵션·입력 seed·환경을 고정하고 자원 누수도 관측해야 한다. 이는 선택 구현이며 본문 학습에 설치가 필요하지 않다.
