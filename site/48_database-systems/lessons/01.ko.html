소단원 1.1

파서·최적화·실행·저장 계층

한 줄의 SELECT 뒤에는 왜 여러 종류의 일이 있을까?

준비 개념과 학습 목표

준비 개념

  • 레코드는 한 대상의 필드 묶음이고 표는 레코드의 모음이다. 페이지는 저장 계층이 다루는 고정 크기 데이터 조각이다.

  • SQL은 원하는 결과를 기술하는 언어다. 여기서는 정수 id·score, NULL 없음, 중복 없는 id와 변하지 않는 표를 가정한다.

  • 연산자는 입력에서 결과를 만드는 절차다. 필터는 조건에 맞는 행을 남기고 투영은 선택한 열을 남긴다.

학습 목표

  • 구문·이름 해석·계획·실행·저장의 역할을 구분한다.

  • 결과 의미를 유지한 두 접근 방법의 가상 페이지 비용을 비교한다.

같은 정답을 내는 두 경로 중 어느 쪽이 더 적은 페이지를 가져올까요?

사서에게 책 제목을 요청하면 질문을 이해하고, 찾는 경로를 고르고, 서가에서 자료를 꺼내는 일이 이어집니다. DBMS에서도 문법 확인, 이름 해석, 계획 선택, 실제 행 생산과 페이지 접근을 구분합니다. SQLite의 공식 구조는 SQL을 바이트코드로 만들고 실행하는 경로를 보여 줍니다. 이 비유의 비용은 실제 SQLite 성능이 아닙니다.

아래 자체 표는 정수 id와 score를 가진 여섯 행이고 id가 유일하며 NULL과 동시 변경은 없습니다. P0에는 (1,40), (2,90), P1에는 (3,70), (4,90), P2에는 (5,60), (6,70)이 있습니다. 점수 조건을 통과한 id의 모음을 비교하며 ORDER BY가 없으면 순서를 정답 조건으로 사용하지 않습니다. 비용은 처음 비어 있는 캐시에서 가져온 서로 다른 페이지 하나당 1로 정합니다.

먼저 확인할 개념
  • 관계형 DBMS의 계층

    요청 의미와 저장 방법을 분리하는 이유를 먼저 확인합니다.

  • 시스템 호출과 페이지 자원

    DBMS의 페이지 요청이 OS와 장치에서 같은 수의 사건을 뜻하지 않는다는 조건을 연결합니다.

문자열을 의미 있는 요청으로 만든다

토큰화는 문자열을 SELECT·이름·연산자 등으로 나누고 파싱은 문법에 맞는 구조를 만든다. 이름 해석은 T와 score가 실제 스키마에 있는지 확인한다. 문법이 맞아도 없는 열을 읽는 요청은 유효하지 않다. 구현에서는 이 단계가 합쳐질 수도 있지만 책임은 구분할 수 있다.

SELECT id FROM T WHERE score >= 70은 필터 뒤 id를 투영하라는 뜻이다. ORDER BY가 없으므로 행 순서를 계약으로 삼지 않는다. 일반 SQL에는 NULL·중복·자료형 변환 등이 있으므로 여기의 단순 집합 설명을 모든 SQL로 확대하지 않는다.

계획을 바꿔도 답의 의미는 유지한다

논리 계획은 무엇을 계산할지, 물리 계획은 스캔·인덱스 등 어떻게 계산할지 정한다. 최적화는 허용된 의미를 보존하면서 비용이 낮을 것으로 추정한 계획을 고른다. 추정에는 통계와 비용 모형의 오차가 있으므로 이름이 최적화라고 실제 최저 시간을 보장하지 않는다.

가상 표 T={(1,60),(2,80),(3,70),(4,50)}의 첫 두 행은 P0, 나머지는 P1에 있다. 캐시가 처음 비어 있고 각 페이지 접근 비용이 1이며 다른 비용을 무시하면 스캔은 2이다. 인덱스 경로가 인덱스 페이지 2개와 데이터 페이지 2개를 읽는다고 정하면 비용 4이다. 이 작은 모형에서는 인덱스가 더 비싸다.

실행과 저장을 연결한다

iterator 모형에서는 상위 연산자가 하위 연산자의 Next를 호출해 행을 요청한다. 필터는 불합격 행을 건너뛰며 합격 행이나 정상 끝을 반환한다. 실제 오류는 정상 끝과 다른 상태로 전달해야 한다. batch 모형은 여러 행을 한 번에 보내고 materialization은 결과 묶음을 만든다.

저장 계층은 레코드 위치와 페이지를 다루고 버퍼는 이미 읽은 페이지를 재사용한다. DBMS 페이지 미스가 반드시 장치의 물리 읽기 한 번은 아니다. OS 캐시가 데이터를 줄 수 있다. SQLite는 SQL을 바이트코드로 만들고 VM·B-tree·pager·VFS로 이어지는 실제 설계를 제공한다. 이 모형은 특정 엔진의 모든 내부 절차를 복제한 것이 아니다.

여섯 행을 가진 자체 표에서 질문과 실행 경로를 구별합니다.
계층입력 또는 결정이 모형에서 확인할 것

이름 해석

T와 score의 존재를 확인합니다.

score 대신 scroe를 쓰면 존재하지 않는 열로 거절합니다.

논리 의미

score >= 70 뒤 id를 남깁니다.

결과 모음은 {2,3,4,6}입니다.

스캔 경로

데이터 페이지 P0, P1, P2를 가져옵니다.

서로 다른 데이터 페이지는 세 개입니다.

인덱스 경로

별도 인덱스 페이지 두 개와 합격 행의 데이터 페이지를 가져옵니다.

이 조건의 데이터 페이지도 세 개여서 총 다섯 개입니다.

결과 계약

두 경로 모두 같은 id 모음을 냅니다.

ORDER BY가 없으므로 출력 순서만 바뀐 것은 실패가 아닙니다.

위에서 아래로 요청 의미를 먼저 확정한 뒤 접근 경로를 읽습니다. 인덱스 페이지와 데이터 페이지는 서로 다른 페이지이며 캐시에 없다고 가정합니다. 비용 단위 1은 페이지 획득 횟수의 자체 모형이고 초나 실제 장치 읽기 횟수가 아닙니다.

중간 과정을 따라가는 예제

위의 T와 P0·P1에 대해 SELECT id FROM T WHERE score >= 70을 스캔하라. 순서는 설명용 스캔 순서다.

  1. 파싱·이름 해석을 통과한 후 scan → filter(score >= 70) → project(id)를 정한다.

  2. P0을 읽고 (1,60)을 거절한다. (2,80)은 합격해 id 2를 낸다.

  3. P1을 읽고 (3,70)은 경계값을 포함하므로 id 3을 낸다. (4,50)은 거절한다.

  4. 다음 요청은 정상 끝이다. 네 행을 검사하고 두 페이지를 가져왔으며 합격 행은 두 개다.

결과는 id 2와 3의 모음이다. 가상 냉간 페이지 비용은 2이며 SQL 자체는 이 출력 순서를 보장하지 않는다.

조건을 바꾸어 비교하기

합격 행이 여러 페이지에 흩어진 경우

위 표에서 score >= 70을 스캔과 인덱스로 계산하세요. 인덱스는 별도 페이지 두 개를 먼저 가져오고 합격 행의 데이터 페이지는 한 번씩만 가져옵니다.

  1. 합격 행은 id 2, 3, 4, 6입니다.

  2. id 2는 P0, id 3과 4는 P1, id 6은 P2에 있으므로 합격 행의 데이터 페이지는 세 개입니다.

  3. 스캔 비용은 3이고 인덱스 경로 비용은 2+3=5입니다.

두 경로의 결과 모음은 같지만 정한 냉간 비용은 스캔이 3, 인덱스가 5입니다.

비교할 점

기본의 네 행·두 페이지에서 여섯 행·세 페이지로 늘려 결과 수와 서로 다른 페이지 수를 별도로 셉니다.

소수의 합격 행도 배치에 따라 비용이 달라집니다.

별도 표에는 100행이 열 페이지에 열 행씩 있습니다. 다섯 행만 합격하며 인덱스 페이지 두 개가 필요합니다. 다섯 합격 행이 한 페이지에 모인 경우와 서로 다른 다섯 페이지에 흩어진 경우를 비교하세요.

  1. 전체 스캔은 어느 경우든 열 페이지를 가져와 비용이 10입니다.

  2. 한 페이지에 모이면 인덱스 비용은 2+1=3입니다.

  3. 다섯 페이지에 흩어지면 인덱스 비용은 2+5=7입니다.

합격 수는 다섯 행으로 같지만 인덱스 비용은 배치에 따라 3 또는 7입니다. 둘 다 이 표의 스캔 비용 10보다 작습니다.

비교할 점

합격 수만으로 페이지 비용을 확정할 수 없다는 점을 데이터 배치로 확인합니다.

종이와 본문으로 직접 해보기

같은 T에서 조건을 score > 70으로 바꿔 결과와 냉간 스캔 비용을 써 보라.

힌트 보기

>=와 >가 점수 70에 주는 차이를 먼저 표시한다.

풀이 보기

id 2만 남는다. 네 행·두 페이지 스캔은 그대로이므로 정한 비용 모형에서 비용 2다. 결과 수가 줄어도 이 스캔의 페이지 수는 줄지 않는다.

오해와 반례

인덱스가 있으면 항상 더 빠르고, 물리 계획이 다르면 다른 답을 내도 된다.

가정한 인덱스 비용 4는 스캔 2보다 크다. 계획 차이는 실행 방법의 차이지 허용된 결과 의미를 바꿀 허가가 아니다.

스스로 풀어보기

먼저 답과 이유를 적고, 필요한 만큼 힌트를 한 단계씩 열어 보세요.

연습 1 · 값과 상태 예측

여섯 행의 표에서 조건을 score >= 90으로 바꾸세요. 결과 모음과 스캔·인덱스 비용을 구하세요. 인덱스의 별도 페이지 수는 두 개로 유지합니다.

힌트 1

90인 행의 id와 페이지를 먼저 찾습니다.

힌트 2

결과에 포함되지 않는 페이지도 전체 스캔에서는 읽습니다.

풀이와 답 확인

  1. 합격 id는 2와 4이고 각각 P0와 P1에 있습니다.

  2. 스캔은 세 페이지라 비용이 3입니다.

  3. 인덱스는 별도 두 페이지와 데이터 두 페이지라 비용이 4입니다.

결과는 {2,4}이며 스캔 비용은 3, 인덱스 비용은 4입니다.

흔한 오답에서 다시 생각하기

합격 행이 두 개니까 두 경로 비용도 모두 2입니다.

전체 스캔 페이지와 합격 행 수는 다른 값입니다. 인덱스의 자체 페이지 비용도 포함해야 합니다.

연습 2 · 오류 찾아 고치기

검사기가 스캔 결과 [2,3,4,6]과 인덱스 결과 [6,4,3,2]를 다르다고 거절했습니다. 지금의 SQL 계약에서 검사를 고치고, 순서 검사를 하고 싶을 때 필요한 질의 조건을 쓰세요.

힌트 1

id가 유일하고 ORDER BY가 없다는 가정을 확인합니다.

힌트 2

원하는 순서를 SQL에 명시하는 경우와 명시하지 않은 경우를 나눕니다.

풀이와 답 확인

  1. 현재 계약에서는 두 결과를 순서 없는 id 모음으로 비교합니다.

  2. 둘 다 {2,3,4,6}이므로 이 결과 차이만으로 실패 처리하지 않습니다.

  3. 오름차순 목록을 요구하려면 ORDER BY id를 추가하고 그 계약에 맞게 검사합니다.

현재 두 결과는 같은 정답입니다. 명시적 ORDER BY id가 있으면 오름차순 결과를 따로 검사합니다.

흔한 오답에서 다시 생각하기

모든 SQL 결과는 삽입한 순서대로 나옵니다.

정한 질의에는 순서 조건이 없습니다. 관찰된 한 번의 순서를 언어 계약으로 확대하지 않습니다.

연습 3 · 직접 만들어 보기

인덱스가 있어도 전체 스캔이 더 싼 작은 반례를 직접 구성하세요. 두 데이터 페이지에 합격 행을 나누고 인덱스는 별도 두 페이지를 읽도록 정하세요.

힌트 1

각 데이터 페이지에 합격 행을 하나 이상 둡니다.

힌트 2

결과 의미는 같게 유지하고 읽는 서로 다른 페이지를 셉니다.

풀이와 답 확인

  1. 예를 들어 P0에 (1,80), (2,40), P1에 (3,90), (4,50)을 둡니다.

  2. score >= 70의 결과 모음은 {1,3}입니다.

  3. 스캔 비용은 2이고 인덱스는 별도 두 페이지와 데이터 두 페이지를 읽어 비용이 4입니다.

제시한 반례에서 두 경로의 정답은 같고 스캔 비용 2가 인덱스 비용 4보다 작습니다. 같은 조건을 만족하는 다른 표도 가능합니다.

흔한 오답에서 다시 생각하기

인덱스가 있다는 사실만으로 더 작은 비용이 증명됩니다.

찾기 구조 자체를 가져오는 비용과 합격 행의 데이터 페이지 비용을 함께 비교합니다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

여섯 행 모형의 score >= 70에서 페이지 획득마다 2 U, 스캔의 행 조건 검사마다 0.5 U가 든다고 정하세요. 인덱스는 같은 두 인덱스 페이지와 세 데이터 페이지를 읽으며 합격 후보 네 행만 0.5 U씩 검사합니다. 다른 비용은 없을 때 전체를 비교하세요.

페이지를 읽어 달라는 요청과 실제 디스크 동작은 같은 사건일까?

준비 개념과 학습 목표

준비 개념

  • 시스템 호출은 프로그램이 OS에 서비스를 요청하는 경계다. 라이브러리 API 한 호출이 시스템 호출 여러 개나 0개로 이어질 수 있다.

  • 파일 기술자 fd는 열린 파일 등을 가리키는 OS의 정수 손잡이다. 버퍼는 바이트를 담는 메모리이고 1 KiB=1024바이트다.

  • 캐시는 다시 쓰기 위한 사본이다. dirty는 메모리의 변경을 저장 상태에 반영해야 함을 뜻하며 전원 장애 뒤 지속을 뜻하지 않는다.

학습 목표

  • 짧은 읽기·EOF·오류를 구분하며 페이지 읽기를 추적한다.

  • 자원 수명·캐시·동기화와 내구성 주장 사이의 조건을 설명한다.

짧게 읽힌 페이지의 나머지를 0으로 채우면 원래 자료를 읽은 것일까요?

파일을 봉투에 담긴 자료라고 생각하면 한 번의 요청이 필요한 모든 내용을 주리라는 가정부터 확인해야 합니다. Linux read의 반환 규칙은 양의 짧은 반환을 성공으로 다루며 EOF와 실패를 구분합니다. 상위 페이지 로더는 이 반환 상태를 필요한 전체 길이와 함께 판단합니다.

아래 자체 로더는 일반 파일에서 4096바이트를 모은 뒤에만 페이지를 해석합니다. 버퍼 용량은 충분하고 한 작업만 읽기를 수행한다고 가정합니다. 채운 길이는 성공한 양의 반환만큼 증가합니다. 이 종이 모형에서는 EINTR가 들어오면 읽기 위치와 기존 버퍼 내용이 유지된다는 조건을 추가하고 남은 길이를 다시 요청합니다. 이 추가 조건을 모든 실제 오류 반환의 보장으로 사용하지 않습니다. 다른 오류를 무조건 재시도하지 않으며, 실제 구현의 오류 뒤 파일 위치는 해당 인터페이스와 환경에서 별도로 확인해야 합니다.

먼저 확인할 개념
  • SSD 페이지와 지우기 단위

    저장 장치의 페이지 단위와 DBMS가 필요한 페이지의 의미를 구별합니다.

  • 참조계수와 자원 수명

    사용 중인 프레임을 언제 재사용할 수 있는지 참조 수로 추적합니다.

계층마다 다른 사건을 센다

DBMS는 페이지를 요청하고 VFS 같은 추상층은 OS에 맞는 읽기·쓰기·잠금 기능을 제공한다. 여기서는 일반 파일에 양의 count로 읽기를 요청한다. Linux의 read(fd,buf,count)는 최대 count바이트를 요청한다. 성공 반환 n은 실제 읽은 바이트 수이며 n<count 자체는 오류가 아니다. 0은 EOF, -1은 실패이고 errno로 이유를 구분한다.

OS가 캐시에서 읽기를 처리할 수 있으므로 API 호출 수·시스템 호출 수·물리 I/O 수를 같은 수로 세지 않는다. 이 절은 Linux 문서의 의미를 종이로 해석한다. Windows에서는 다른 구현 경로가 쓰일 수 있으며 여기서 Unix 호출을 실행하지 않았다.

페이지는 완성되었을 때만 해석한다

가상 페이지 로더는 필요한 4096바이트가 모일 때까지 남은 길이로 요청한다. 양의 n이 돌아오면 채운 길이를 n만큼 증가시킨다. 목표 전의 EOF는 정상적인 완성 페이지가 아니므로 불완전 페이지 오류로 반환한다. 실패를 빈 페이지로 바꾸면 데이터 없음과 장치 실패를 구분하지 못한다.

이 종이 모형은 다른 스레드가 fd의 위치를 바꾸지 않으며 적절한 메모리를 확보했다고 가정한다. 실제 구현은 offset 지정 읽기·EINTR 처리·취소·반복 상한·비동기 완료 등을 계약에 맞게 정한다. 오류 뒤 진행과 파일 위치는 반환 규칙을 읽고 판단해야 하며 모든 실패를 무조건 재시도하지 않는다.

수명과 동기화에는 별도 계약이 있다

페이지 프레임 4개를 각 4096바이트로 두면 데이터 공간은 16384바이트=16 KiB다. 이것은 메타데이터·쿼리 결과·인덱스·프로세스 전체 메모리를 포함하지 않는다. pin은 사용 중인 프레임의 축출을 막는 모형의 참조 표시다. 사용하는 동안 참조를 유지하고 완료 뒤 해제해야 하며 용량 부족도 오류나 대기를 설계해야 한다.

쓰기 성공만으로 여러 페이지 트랜잭션의 원자성·내구성을 증명하지 않는다. Linux fsync는 파일 데이터와 필요한 메타데이터 동기화를 요청하지만 새 파일명의 디렉터리 항목에는 별도 디렉터리 fsync가 필요할 수 있다. DBMS 로그·순서·복구와 파일시스템·장치 보장이 함께 맞아야 한다. 단일 함수 이름만으로 전원 장애 시험을 대체할 수 없다.

풀이와 답 확인

  1. 받은 길이는 1536+1024=2560바이트이므로 부족한 길이는 4096−2560=1536바이트입니다.

  2. 프레임 데이터는 3×4096=12288바이트로 12 KiB입니다.

  3. 메타데이터는 3×64=192바이트이며 두 부분 합은 12480바이트입니다.

불완전 페이지이며 부족한 길이는 1536바이트입니다. 명시한 데이터와 메타데이터의 합은 12480바이트로 프로세스 전체 메모리는 아닙니다.

흔한 오답에서 다시 생각하기

EINTR의 -1을 더하면 받은 길이는 2559바이트입니다.

-1은 실패 상태를 나타내며 음수 길이의 자료를 받았다는 뜻이 아닙니다.

연습 2 · 오류 찾아 고치기

로더가 2048바이트 성공 뒤 EOF를 만나 나머지를 0으로 채우고 정상 페이지로 반환했습니다. 정한 완성 페이지 계약에 맞게 고치세요.

힌트 1

EOF는 0바이트를 받았다는 뜻입니다.

힌트 2

필요한 바이트를 실제로 받았는지 검사합니다.

풀이와 답 확인

  1. 2048바이트만 확인되었고 목표 4096바이트보다 부족합니다.

  2. 남은 공간의 0은 파일에서 읽은 자료가 아니므로 정상 완성으로 게시하지 않습니다.

  3. 불완전 페이지 오류를 반환하고 이 실패 경로의 버퍼와 참조 정리 책임을 따로 지킵니다.

이 로더는 불완전 페이지 오류를 반환해야 합니다. 파일 형식이 별도 빈 공간 규칙을 허용하는 다른 계약은 여기서 가정하지 않았습니다.

흔한 오답에서 다시 생각하기

버퍼가 4096바이트이므로 그 안의 모든 바이트가 파일에서 왔습니다.

공간의 크기와 유효하게 받은 길이는 다릅니다. 0으로 채우는 동작이 읽지 못한 파일 내용을 복구하지 않습니다.

힌트 1

힌트 2

각 해제 뒤 B의 pin 수를 기록합니다.

풀이와 답 확인

  1. 초기에는 A의 pin이 1이고 B의 pin이 2여서 후보가 없습니다.

  2. B 사용자 한 명이 해제하면 B의 pin은 1이고 후보는 여전히 없습니다.

  3. 다른 B 사용자가 해제하면 B의 pin은 0이므로 B만 축출 가능합니다.

소단원 1.3

엔진 API·테스트 기반

빈 결과와 고장 때문에 결과가 없는 상황을 어떻게 구별할까?

준비 개념과 학습 목표

준비 개념

  • API는 호출자와 구현 사이의 입력·출력·오류·수명 계약이다. 연결은 DB를 사용하는 맥락, 준비문은 준비된 한 SQL 실행 객체다.

  • 테스트 fixture는 매 테스트의 초기 데이터를 정하는 장치다. 오라클은 예상 결과를 판단하는 기준이며 오류 주입은 정한 위치에서 실패를 흉내 낸다.

  • ROW는 현재 행, DONE은 정상 끝, ERROR는 실패를 뜻하는 서로 다른 상태다. 종이 모형에서는 이 이름을 추상 상태로 쓰고 실제 SQLite는 구체 반환 코드를 쓴다.

학습 목표

  • 연결·준비문·결과 값의 수명과 오류를 분리한다.

  • 정상·경계·실패 테스트의 기대값을 계약에 맞게 정한다.

목록에 행이 몇 개 들어왔다면 질의 전체가 성공한 것일까요?

받은 행을 봉투에 모으는 것과 봉투에 최종 확인 도장을 찍는 일을 나누어 생각해 봅니다. 아래 소비자는 ROW에서 받은 값을 자기 목록으로 복사하고 DONE을 만난 뒤에만 complete로 게시합니다. ERROR가 나오면 후보 목록을 버리고 failed를 게시합니다. 이것은 이 교재의 명시적 소비자 정책이며 모든 SQLite 결과가 자동으로 같은 방식으로 게시된다는 뜻은 아닙니다.

첫 소단원의 여섯 행 표를 그대로 사용합니다. 행 값 복사는 유효한 현재 행에서 해야 합니다. SQLite의 TEXT/BLOB 포인터는 엔진 소유이고 다음 step이나 reset, finalize 또는 특정 형 변환으로 무효화될 수 있습니다. 종이에 문자열을 복사해 추적하는 연습은 실제 포인터 안전성 시험이 아닙니다. 결과 검사와 자원 정리 검사도 따로 기록합니다.

먼저 확인할 개념
  • 검증과 확인

    명세에 맞는 결과와 학습자가 이해할 수 있는 설명을 구별하며 기대값을 만듭니다.

  • 파서부터 저장 계층까지

    정상 경로의 행 모음과 페이지 배치를 오류 주입의 기준으로 사용합니다.

API를 상태 전이로 읽는다

SQLite 입문 경로는 open → prepare_v2 → 필요하면 bind → 반복 step → 현재 행의 column 함수군 → finalize → close다. prepare는 실행 준비이며 결과 행을 모두 읽었다는 뜻이 아니다. 모든 호출의 반환을 확인하고 오류 경로에서도 생성된 자원을 정리해야 한다.

step이 SQLITE_ROW를 반환한 뒤에만 유효 열을 읽는다. sqlite3_column은 입문 문서에서 함수군을 가리키는 이름이고 실제 코드는 column_int·column_text 등 구체 함수를 쓴다. TEXT/BLOB 포인터는 SQLite 소유이며 형 변환이나 step/reset/finalize가 수명을 끝낼 수 있다. 나중에 사용할 값은 유효할 때 자기 저장소에 복사하고 반환 포인터를 임의로 free하지 않는다.

정상 끝을 실패와 구별한다

순차 읽기 전용 종이 엔진을 정하자. T={(1,60),(2,80),(3,70),(4,50)}, 두 행씩 P0·P1, NULL 없음과 유일 id를 다시 가정한다. 호출자는 ROW에서 얻은 id를 복사해 후보 목록에 넣고 DONE을 만났을 때만 complete로 게시한다. ERROR라면 후보를 버리고 failed를 게시하는 자체 소비자 정책이다.

실제 스트리밍 API는 실패 전 일부 행을 이미 줄 수 있다. 따라서 ROW 몇 개를 받았다고 전체 쿼리 성공을 주장하지 않는다. 자체 후보 버리기 정책은 SQLite의 모든 결과가 자동 원자 게시된다는 뜻이 아니다. 이 읽기 모형은 트랜잭션 커밋·동시 갱신·디스크 내구성도 증명하지 않는다.

테스트의 초기 조건과 관측을 적는다

각 테스트를 같은 fixture로 시작하고 입력·가상 실패 위치·기대 상태·기대 행·자원 해제를 적는다. 순서 없는 SQL에는 행 모음을 비교하고 순서가 필요하면 ORDER BY 계약을 추가한다. 정상 빈 결과 complete([])는 실패와 별개다. 구문 오류, 없는 열, 페이지 읽기 실패, 메모리 부족도 정상 끝으로 둔갑하면 안 된다.

SQLite의 공식 테스트 설명에는 메모리 및 VFS I/O 실패 주입과 crash testing이 있다. 이를 읽었다는 사실은 이 교재가 그 테스트를 수행했다는 증거가 아니다. 작은 모형이 맞아도 실제 ABI·컴파일·버전·파일시스템·복구·동시성은 별도 시험 대상이다.

중간 과정을 따라가는 예제

위의 T를 초기화하고 SELECT id FROM T WHERE score >= 70을 실행하는 종이 소비자의 상태를 추적하라. P1 요청에서만 오류를 주입한 경우도 비교하라.

  1. 정상 실행에서 ROW(2)를 복사한다. 후보는 [2]이며 아직 complete가 아니다.

  2. ROW(3)를 복사하면 후보는 [2,3]이다. DONE에서 complete({2,3})를 게시한다.

  3. 실패 실행은 P0에서 ROW(2)까지 같지만 P1 요청에서 ERROR다. 후보 [2]를 버리고 failed를 게시한다.

  4. 두 경로 모두 준비문과 연결의 정리 책임을 수행하도록 계약한다. 이는 실제 API 호출 로그가 아닌 종이 상태 전이이다.

정상은 complete({2,3}), 주입 오류는 failed이며 complete({2})가 아니다. 부분 행 수신과 전체 성공을 구별했다.

세 행을 받은 뒤 실패하는 경우

  1. 정상 실행에서는 id 2, 3, 4, 6을 후보로 복사한 뒤 DONE에서 complete({2,3,4,6})를 게시합니다.

  2. P2 오류 경로에서는 P0에서 id 2, P1에서 id 3과 4를 얻어 후보가 {2,3,4}입니다.

  3. P2 요청의 ERROR에서 후보를 버리고 failed를 게시합니다.

  4. 두 경로 모두 생성된 준비문을 정리하고 연결 정리 책임을 지킵니다.

정상은 complete({2,3,4,6})이고 주입 오류는 failed입니다. 이미 세 행을 받았어도 complete({2,3,4})로 바꾸지 않습니다.

  3. 자기 문자열 s가 유지되는 동안 s의 값 AA를 사용합니다.
