소단원 4.1

객체수명

화면에서 몬스터를 지웠는데 이전에 예약한 공격이 계속된다면 무엇을 확인해야 할까?

준비 개념과 학습 목표

준비 개념

  • 객체는 정체성과 상태를 가지며 생성·사용·종료 시점이 있다.

  • 참조를 가지고 있다는 사실과 대상이 아직 유효하다는 사실은 다르다.

  • 이 단원의 상태표는 직접 만든 종이 모형이며 특정 엔진의 실행 결과가 아니다.

학습 목표

  • 생성·준비·활성·삭제 예약·삭제를 구별한다.

  • 삭제 예약 시점과 실제 해제 시점을 분리한다.

  • 오래된 식별자와 남은 이벤트가 만드는 수명 오류를 추적한다.

등장과 준비를 나누기

몬스터를 만든다고 곧바로 모든 기능이 준비되는 것은 아니다. 위치·체력 데이터를 만들고 다른 객체와 연결한 뒤 게임 세계에 넣고 사용할 수 있다. 생성 중인 객체를 다른 시스템에 너무 일찍 공개하면 아직 설정하지 않은 체력을 읽거나 무기가 없는 상태에서 공격할 수 있다. 어느 시점부터 외부에서 사용 가능한지 규칙을 정해야 한다.

Godot의 장면 트리 진입은 부모가 먼저이고 준비 콜백은 자식이 먼저다. 부모의 준비 단계에서 자식의 준비 결과를 이용할 수 있는 구조다. 이 순서를 모든 게임 엔진에 그대로 적용하지 않는다. 우리 종이 모형에서는 준비가 끝난 뒤 Alive가 된다고 정하고 그 전에는 업데이트 대상에 넣지 않는다.

삭제를 요청하는 순간과 끝나는 순간

수명 상태를 Alive, PendingDelete, Deleted로 나누자. PendingDelete는 삭제 요청을 받았지만 저장 공간을 아직 해제하지 않은 상태다. Godot의 queue_free도 즉시 삭제가 아니라 현재 프레임 끝에 삭제를 예약한다. 실제 삭제 후에는 해당 노드와 자식에 대한 참조가 무효가 되므로 사용을 계속할 수 없다.

이 강의의 게임 규칙은 PendingDelete가 된 순간부터 피해·공격·점수 이벤트를 새로 처리하지 않고 프레임 끝에 실제 삭제하는 것이다. 이는 우리가 선택한 규칙이며 queue_free가 모든 사용자 게임 이벤트를 자동 차단한다는 뜻이 아니다. 같은 프레임에 두 충돌이 와도 보상을 두 번 지급하지 않도록 상태 전이를 검사한다.

참조와 소유·연결의 정리

트리에서 노드를 떼는 일과 객체를 삭제하는 일은 다르다. Godot remove_child는 부모 관계를 제거하지만 노드 자체를 삭제하지 않는다. 반대로 부모 노드를 해제하면 자식도 해제된다. 따라서 장면 밖으로 옮겨 보관할 객체와 장면 종료 때 함께 끝낼 객체를 구별해야 한다.

예약한 이벤트가 오래된 객체를 가리킬 수도 있다. 자체 식별자를 슬롯 번호와 세대 번호의 쌍으로 만들면 슬롯을 재사용해도 이전 세대와 구별할 수 있다. 세대를 확인하는 조회 정책과 남은 예약 이벤트의 취소·무시 정책을 함께 정하자. 식별자를 정수로 만들었다는 이유만으로 유효성 검사가 저절로 생기는 것은 아니다.

중간 과정을 따라가는 예제

Alive 몬스터 M의 체력은 3이다. 같은 프레임에서 피해 3, 피해 2, 공격 예약 이벤트가 순서대로 온다. 체력이 0 이하가 되면 PendingDelete로 바꾸고 이후 이벤트를 무시한다. 첫 전이 때만 점수 10을 준다. 프레임 끝에 Deleted가 된다. 상태·체력·점수를 추적하라.

  1. 시작은 Alive, 체력 3, 이번 프레임 획득 점수 0이다.

  2. 첫 피해 3을 처리하면 3−3=0이며 PendingDelete로 전이하고 점수 10을 준다.

  3. 둘째 피해 2는 이미 PendingDelete이므로 무시한다. 체력은 −2가 아니라 0으로 남는다.

  4. 공격 예약 이벤트도 상태 검사에서 무시한다. 삭제가 미뤄졌다고 공격을 허용하지 않는다.

  5. 프레임 끝에 실제 삭제되어 Deleted가 된다. 총 획득 점수는 10이며 20이 아니다. 이 추적은 정한 게임 정책의 종이 결과다.

첫 피해 뒤 체력 0·PendingDelete·점수 10, 프레임 끝에 Deleted다. 후속 피해와 공격은 무시한다.

종이와 본문으로 직접 해보기

오해와 반례

삭제 예약 호출이 끝났으므로 모든 참조가 즉시 없어지고 후속 이벤트도 자동 무시된다.

예약과 실제 삭제는 다를 수 있다. 종이 사례에서는 둘째 피해가 도착할 때 저장된 객체는 남아 있지만 PendingDelete 검사로 무시한다. 엔진 해제 시점과 게임 이벤트 정책을 별도로 확인해야 한다.

소단원 4.2

scene graph·ECS 비교

장면 트리에서 부모를 바꾸는 일과 객체에 속도 데이터를 붙이는 일은 같은 변화일까?

준비 개념과 학습 목표

준비 개념

  • 트리는 부모와 자식의 계층 관계를 표현한다.

  • 컴포넌트는 기능이나 데이터를 나눈 조각이며 ECS에서는 식별자·데이터·처리 역할을 구별한다.

  • 위치는 회전과 크기 변환이 없는 평행이동만 먼저 계산한다.

학습 목표

  • 장면 그래프가 표현하는 계층과 ECS의 데이터 선택을 구별한다.

  • 지역 위치와 전역 위치를 조건에 맞게 계산한다.

  • 상속·부모 관계·컴포넌트 포함 관계를 혼동하지 않는다.

장면 그래프의 질문

장면 그래프는 화면이나 세계의 객체 사이 계층을 표현한다. 캐릭터에 붙인 모자는 캐릭터의 움직임을 따르고 메뉴의 글자는 패널 안에 배치된다. 각 노드의 지역 변환을 부모 변환과 합성하면 전역 변환을 얻는다. 계층은 편집·변환·수명 관리에 유용하지만 어떤 책임을 전달하는지는 엔진과 설계에 따라 다르다.

평행이동만 있고 같은 좌표축을 사용하면 전역 위치는 부모 전역 위치와 자식 지역 위치의 벡터 합이다. 회전이나 배율이 있으면 단순히 두 좌표를 더해서 끝낼 수 없으며 변환 합성이 필요하다. 부모의 위치가 (10,0)이고 자식 지역 위치가 (2,3)이면 이 제한된 모형의 전역 위치는 (12,3)이다.

ECS의 질문

ECS는 어떤 엔티티가 필요한 데이터를 가지고 있으며 어느 시스템이 처리할지를 조직한다. Unity Entities의 엔티티는 식별자이고 컴포넌트는 데이터를 담으며 시스템이 데이터를 처리한다. 위치와 속도가 모두 있는 엔티티만 이동 시스템이 선택한다고 정하면 체력만 있는 객체는 그 순회에 들어오지 않는다.

씬 노드에 스크립트나 여러 기능을 붙이는 모든 구조를 곧바로 Unity식 ECS라고 부르지 않는다. 컴포넌트 기반 설계라는 넓은 아이디어와 특정 ECS의 저장·쿼리·스케줄링 규칙은 구별한다. ECS에서도 부모 식별자 등의 데이터로 계층을 표현할 수 있어 트리와 ECS가 반드시 서로를 배제하지 않는다.

무엇이 같고 무엇이 다른가

장면 트리의 부모 관계는 클래스 상속 관계가 아니다. 모자가 캐릭터의 자식이라는 사실은 모자가 캐릭터 종류라는 뜻이 아니다. 마찬가지로 Position을 가진 엔티티가 Position의 하위 클래스라는 뜻도 아니다. 각 관계가 표현하는 질문을 말로 풀어 보면 잘못된 설계를 줄일 수 있다.

부모 변경 시 지역 위치를 유지할지 전역 위치를 유지할지 명시하자. Godot reparent의 전역 변환 보존은 지원하는 노드 형식에서 적용되며 Control은 위치만 보존한다. ECS 선택 조건 변경도 수명이나 수직 계층과 동일하지 않다. 어떤 시스템이 읽고 쓰는 데이터와 어떤 부모가 영향을 주는지 각각 적는다.

중간 과정을 따라가는 예제

평행이동 모형에서 P의 전역 위치는 (10,0), C의 지역 위치는 (2,3)이다. C를 전역 위치 (20,0)인 Q의 자식으로 바꾸면서 전역 위치를 유지한다. 또 e1은 Position·Velocity, e2는 Position, e3는 Velocity·Health를 가진다. 새 지역 위치와 Position·Velocity 둘 다 필요한 이동 쿼리의 대상을 구하라.

  1. 처음 C의 전역 위치는 (10,0)+(2,3)=(12,3)이다.

  2. 새 부모 Q를 기준으로 같은 전역 위치를 유지하려면 새 지역 위치는 (12,3)−(20,0)=(-8,3)이다.

  3. 검산하면 (20,0)+(-8,3)=(12,3)으로 처음 전역 위치가 보존된다.

  4. e1은 Position과 Velocity가 모두 있으므로 선택된다. e2는 Velocity가 없고 e3는 Position이 없으므로 제외된다.

  5. 부모 변경 계산과 컴포넌트 쿼리는 서로 다른 관계를 다룬다. 여기서는 한쪽 변화가 다른 쪽 데이터를 자동 변경한다고 가정하지 않는다.

새 지역 위치는 (-8,3), 이동 쿼리는 e1만 선택한다.

종이와 본문으로 직접 해보기

이번에는 부모를 Q로 바꾸면서 지역 위치 (2,3)을 그대로 유지한다. 새 전역 위치를 계산하라. 다음 순회 전에 e2에 Velocity를 추가하고 e1에서 Velocity를 제거하면 같은 쿼리의 대상은 누구인가?

힌트 보기

지역 유지와 전역 유지를 바꾸어 읽지 말자. 쿼리는 변화 이후의 포함 관계를 다시 판정한다.

풀이 보기

새 전역 위치는 (20,0)+(2,3)=(22,3)이다. 다음 쿼리는 e2만 선택한다. e1은 Velocity가 없어 제외되고 e3는 여전히 Position이 없다. 실제 엔진에서는 컴포넌트 추가·제거를 안전하게 적용하는 시점도 지켜야 한다.

오해와 반례

부모 자식 관계가 있으면 자식은 부모의 하위 클래스이고 ECS에는 계층을 표현할 수 없다.

소단원 4.3

상태와 데이터배치

같은 네 캐릭터의 x값을 읽는데 저장 순서가 달라지면 어떤 차이를 예상할 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 상태는 현재 값이며 그 값을 바꾸는 규칙과 저장 위치는 구별한다.

  • 연속 메모리의 주소는 바이트 단위로 센다.

  • 이 단원의 16바이트 줄은 계산용 가정이며 실제 CPU 캐시 규격이나 측정값이 아니다.

학습 목표

  • 객체별 묶음과 필드별 묶음의 주소를 비교한다.

  • 상태 갱신과 데이터 구조 변경을 구별한다.

  • 줄 수 계산으로 실행 시간이나 실제 캐시 미스를 단정하지 않는다.

상태의 의미와 놓는 위치

캐릭터의 x·y·체력은 게임 상태다. 피해를 받으면 체력이 감소하고 이동하면 위치가 바뀌는 것은 의미상의 규칙이다. 이 규칙을 정하는 일과 각 값을 메모리에 놓는 일은 별개의 설계다. 같은 상태와 규칙을 객체별 묶음이나 필드별 배열로 저장할 수 있다.

객체별 묶음 AoS는 [x,y,h]를 한 객체 단위로 반복한다. 필드별 묶음 SoA는 모든 x를 모으고 모든 y를 모으는 방식이다. 한 캐릭터의 여러 필드를 함께 읽을지, 여러 캐릭터의 한 필드만 순회할지에 따라 접근 패턴이 다르므로 항상 한 방식이 우월하다고 말하지 않는다.

주소표로 제한된 비용 보기

계산 모형에서 각 필드는 4바이트, 객체당 세 필드는 12바이트이며 숨은 간격이나 메타데이터가 없다고 정한다. 주소 0부터 네 객체의 x만 읽으면 시작 주소는 0,12,24,36이다. 16바이트 줄의 번호는 주소를 16으로 나눈 몫이다. 각 x의 4바이트 범위가 줄을 넘는지도 확인한다.

실제 자료형에는 정렬과 패딩, 포인터, 메타데이터가 있을 수 있다. 캐시 줄 크기·기존 캐시 상태·교체·프리페치·다른 데이터 접근도 영향을 준다. 종이에서 몇 개의 서로 다른 줄에 접근하는지 계산했다고 실제 미스 수나 실행 시간을 측정한 것은 아니다. 최적화 판단에는 대상 환경의 프로파일링이 필요하다.

값 변경과 구조 변경의 안전

체력 값을 3에서 2로 바꾸는 일과 Health 컴포넌트를 제거하는 일은 다르다. Unity Entities에서는 컴포넌트 추가·제거나 엔티티 생성·삭제 등이 저장 구조를 재조직할 수 있다. 마지막 엔티티를 빈 곳으로 옮기면 이전에 기억한 배열 위치가 다른 대상을 가리킬 수도 있다.

순회 도중 저장 구조를 바꾸어 기존 참조나 반복자의 유효성을 깨지 않도록 규칙을 정한다. 명령을 모았다가 안전한 시점에 적용하거나 엔진의 허용 API를 따른다. 연속 배열만 만든다고 식별자의 수명·동시 접근·구조 변경 문제까지 해결되는 것은 아니다. 필드별 배열도 같은 엔티티의 필드가 올바르게 대응해야 한다.

중간 과정을 따라가는 예제

네 객체의 x,y,h는 각각 4바이트이고 AoS는 객체당 12바이트, 시작 주소 0, 패딩 없음이다. SoA의 x 배열도 주소 0에서 시작해 4바이트씩 연속이다. 16바이트 줄 모형에서 x만 읽을 때 서로 다른 줄 번호를 구하라. 캐시는 측정하지 않는다.

  1. AoS x의 범위는 0–3,12–15,24–27,36–39다. 각 값이 한 줄 안에 들어간다.

  2. 시작 주소의 몫은 0//16=0,12//16=0,24//16=1,36//16=2다.

  3. AoS가 닿는 서로 다른 줄 번호 집합은 {0,1,2}로 3개다.

  4. SoA x의 범위는 0–3,4–7,8–11,12–15여서 모두 줄 0에 들어간다. 서로 다른 줄은 1개다.

  5. 양쪽 상태 데이터 전체 크기는 4×12=48바이트로 같다. 줄 수 3 대 1은 이 접근과 정렬 가정의 결과이며 3배 속도를 뜻하지 않는다.

AoS는 줄 {0,1,2} 세 개, SoA x는 줄 {0} 한 개다. 전체 상태 크기는 둘 다 48바이트다.

종이와 본문으로 직접 해보기

SoA x 배열의 시작 주소를 4로 옮기면 네 x의 바이트 범위와 줄 수는 어떻게 바뀌는가? 또 밀집 배열 [e1,e2,e3]에서 e2를 지우고 마지막 e3로 빈 자리를 채우면 위치 1을 기억한 참조는 누구를 가리키는가?

힌트 보기

주소 4,8,12,16의 범위를 확인하고 배열 위치와 엔티티 정체성을 구별하라.

풀이 보기

범위는 4–7,8–11,12–15,16–19라서 줄 {0,1} 두 개다. 삭제 후 배열은 [e1,e3]이며 위치 1은 e3를 가리킨다. 이전 e2 참조를 위치 1로 계속 해석하면 잘못된 대상이다. 식별자 조회와 구조 변경 시점 규칙이 필요하다.

오해와 반례

SoA로 바꾸면 데이터가 작아지고 모든 게임에서 반드시 빨라진다.

이 모형의 전체 상태 크기는 양쪽 모두 48바이트다. x만 읽을 때 정렬된 SoA의 줄 수가 적지만 시작 주소 4에서는 두 줄을 읽는다. 모든 필드를 한 객체씩 읽거나 구조 변경이 잦은 작업의 비용은 다를 수 있어 실제 속도는 별도로 측정해야 한다.
