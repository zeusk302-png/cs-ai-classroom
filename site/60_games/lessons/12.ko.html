소단원 12.1

빌드·리소스 검증

편집기에서 보이던 캐릭터가 친구의 실행 파일에서는 사라질 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 장면은 게임 객체와 상태를 묶는다.

  • 이미지·소리·글꼴은 코드가 참조하는 자원이다.

학습 목표

  • 프로젝트와 실행 배포물을 구별한다.

  • 장면의 종속 자원과 실제 패키지 목록을 대조한다.

실행할 대상과 데이터를 함께 준비한다

게임 프로젝트는 편집기에서 작업하는 자료이고 배포물은 사용자가 실행할 대상이다. 엔진·플랫폼·내보내기 설정에 따라 준비 과정이 달라진다. 파일 압축이 성공했다는 사실만으로 사용 가능한 실행 파일이 만들어진 것은 아니다.

Godot의 Export Project는 실행 가능한 build를 만드는 흐름이고 Export PCK/ZIP은 프로젝트 데이터만 내보내는 흐름이다. preset과 export template 및 플랫폼에 필요한 도구가 준비되어야 한다. 아래 종이 모형은 이 구별을 연습하며 실제 Godot 내보내기를 수행한 것은 아니다.

참조를 따라 누락을 찾는다

장면 S가 캐릭터 그림 T와 효과음 A를 사용하고, 화면 U가 글꼴 F를 사용한다면 S→T, S→A, U→F의 화살표를 그린다. 참조된 자원이 묶음에 없으면 그 장면을 표시하거나 재생하는 데 문제가 생길 수 있다. 디버그 빌드와 release 빌드의 자원 목록도 확인한다.

코드가 문자열로 읽는 별도 JSON 같은 파일은 선택 자원만 내보내는 규칙에서 추가 필터가 필요할 수 있다. 에디터 캐시에 있던 데이터가 깨끗한 실행 환경에도 있다고 가정하지 않는다. 같은 자원을 여러 곳에서 사용한다고 패키지 파일을 무조건 중복 개수로 세지는 않는다.

목록 검증과 사용자 실행을 연결한다

종속 목록 비교는 누락 후보를 찾는 정적 점검이다. 존재하는 파일도 형식·지원 기능·사용 경로가 다르면 실행 중 실패할 수 있다. 실제 배포물의 시작 장면·장면 전환·소리·글꼴·저장 경로를 목표 환경에서 확인하고 로그에 버전과 조건을 남긴다.

공개 패키지에는 비밀 인증키나 내보내기 credentials를 넣지 않는다. 데이터가 압축되어 있어도 수신한 사용자가 절대 읽을 수 없다고 가정할 수 없다. 이 단원에서는 공개 파일 목록 설계만 하고 실제 비밀값이나 공개 배포를 다루지 않는다.

중간 과정을 따라가는 예제

자체 모형에서 시작 장면 S는 T·A, 메뉴 U는 F, 설정은 C.json을 요구한다. 필요한 서로 다른 파일은 S,U,T,A,F,C.json이다. 패키지에는 S,U,T,A,F만 있다. 누락과 포함 비율을 구하자.

  1. 필수 파일은 6개다. T를 여러 장면이 사용해도 같은 파일은 한 번 센다.

  2. 패키지에 필요한 파일 5개가 있어 5/6×100≈83.3%다.

  3. C.json이 누락됐다. 파일 포함 비율은 실행 성공률이 아니며 설정 읽기 실패 가능성을 별도 확인해야 한다.

C.json 1개 누락이다. 포함 비율 약 83.3%는 목록 대조 수치이며 실제 게임 실행을 증명하지 않는다.

소단원 12.2

난이도·접근성·피드백

어떤 사람에게 쉬운 게임이 다른 사람에게는 조작조차 어려울 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 규칙의 성공 조건과 조작 방법은 구별된다.

  • 성공률의 분모는 관찰한 시도 수다.

학습 목표

  • 도전과 접근 장벽을 나누어 설명한다.

  • 보조 설정과 피드백의 효과를 검증할 계획을 세운다.

장벽의 종류를 먼저 찾는다

게임의 어려움은 플레이어 능력과 게임이 요구하는 행동의 관계에서 생긴다. 빠른 반복 입력, 작은 목표 조준, 짧은 제한 시간, 복잡한 기억 과제는 다른 종류의 도전이다. 한 가지 쉬움/어려움 설정만으로 모두의 필요를 충족한다고 단정하지 않는다.

예를 들어 퍼즐 생각은 즐기지만 손을 빠르게 움직이기 어려운 사람에게 퍼즐 답을 알려 주는 대신 시간 제한을 조절할 수 있다. 지원 설정은 어떤 행동을 바꾸는지 설명한다. 플레이어를 비하하는 모드 이름보다 제한 시간·적 공격·힌트 같은 변화 내용을 알려 준다.

설정과 진행 및 피드백을 연결한다

난이도를 바꿀 때 이미 쌓은 진행을 어떻게 보존할지 정한다. 저장 지점·일시정지·설정 복원이 있으면 반복 실패 후 다시 접근하기 쉽다. 다만 온라인 다인 게임의 공정성이나 서버 상태처럼 추가 조건이 있는 경우도 있어 모든 게임이 같은 처리 정책을 쓰지는 않는다.

피드백은 성공/실패와 다음 행동을 알아볼 수 있게 돕는다. 실패 원인이 시간 부족인지 잘못된 선택인지 표시하고, 색 하나나 소리 하나만으로 중요한 정보를 전달하지 않는 방안을 생각한다. 그림을 바꾼 설계 의도와 실제 플레이어가 정보를 이해했는지는 별도 확인한다.

평균만 보고 장벽을 숨기지 않는다

관찰할 때 도움 제공·기기·설정·이전 경험과 목표 과제를 기록한다. 전체 성공률이 올라도 특정 입력 방식의 실패가 남을 수 있다. 따라서 접근성 옵션 존재와 실제로 이용 가능한 상태, 플레이어가 이해하고 사용하는 상태를 나누어 확인한다.

종이 예제의 실패율 감소는 기술 통계다. 실제 플레이 실험이 없으므로 보조 모드의 효능이나 재미를 검증한 수치가 아니다. 차이가 난 이유를 확인하려면 같은 과제·성공 기준과 연구 절차를 설계하고 실제 관찰을 별도로 해야 한다.

중간 과정을 따라가는 예제

가상 10회 표에서 기본 시간 제한은 성공6·실패4다. 시간을 늘린 설정은 성공8·실패2다. 성공률 차이와 실패 수 상대 감소를 계산하자.

  1. 기본 성공률 6/10=60%, 수정 성공률 8/10=80%다.

  2. 성공률 차이는 20퍼센트포인트다. 실패 수는 4→2로 2회 줄었다.

  3. 실패 수 상대 감소는 (4−2)/4=50%다. 서로 다른 척도이며 가상 표만으로 실제 설정 효과를 증명하지 않는다.

성공률 60→80%, 차이20퍼센트포인트, 실패 수 상대 감소50%다. 재미·실사용 효과는 미검증이다.

종이와 본문으로 직접 해보기

수정 표 성공8은 일반 조작7/8과 보조 입력1/2의 합이다. 집단별 성공률을 구하고 “모두에게 충분하다”는 문장을 점검하자.

힌트 보기

분모 8과2를 나누고 작은 표본 한계를 적는다.

풀이 보기

일반 조작87.5%, 보조 입력50%다. 전체80%가 보조 입력80%는 아니다. 각 표본이 작고 한 실패가 남아 모두에게 충분하다고 보장할 수 없다.

오해와 반례

쉬운 모드가 있으면 접근성은 완성되고 모든 사람이 같은 난이도를 느낀다.

조작·표시·이해·시간 등 장벽이 다르고 옵션이 발견·사용 가능한지도 확인해야 한다. 같은 게임 조건이 사람별 같은 경험을 만들지는 않는다.

소단원 12.3

릴리스와 개선보고

버전 이름을 붙였다고 친구가 받은 파일도 검증한 게임과 같을까?

준비 개념과 학습 목표

준비 개념

  • 릴리스는 사용자가 받을 특정 배포물을 가리킨다.

  • 검토 기록은 확인한 버전과 환경에 연결한다.

학습 목표

  • 소스 버전·빌드·공개 파일의 연결을 기록한다.

  • 재현 가능한 문제와 개선 이력을 보고한다.

소스와 산출물의 연결을 남긴다

릴리스에는 소스 식별자, 빌드 설정, 패키지 식별자와 변경 설명을 연결한다. Git tag는 저장소 이력의 한 지점을 표시하고 GitHub release는 설명과 배포 파일을 묶어 제공할 수 있다. 자동 제공되는 소스 압축 파일이 모든 플랫폼의 실행 빌드라고 가정하지 않는다.

버전 이름이 같아도 다시 빌드한 패키지의 내용이 달라질 수 있다. 검증한 파일 H와 공개한 파일 G의 식별 정보가 다른 경우 H 결과를 G에 적용하지 않는다. 내용 해시 일치는 파일 바이트 일치 확인에 도움이 되지만 코드가 올바르거나 모든 기기에서 실행된다는 보장은 아니다.

실패 보고는 다음 사람이 따라갈 수 있게 쓴다

“안 됨” 대신 게임 버전·기기/운영체제·설정·시작 상태·재현 순서·예상·실제를 적는다. 저장 자료가 관련되면 필요한 최소 사례를 만들고 개인 정보나 인증 정보를 제거한다. 발생 빈도와 화면·로그의 수집 방법도 표시한다.

개선 보고에는 수정한 문제, 영향을 받은 규칙, 재검사한 입력과 남은 환경을 연결한다. 옛 버전의 통과 기록을 새 파일에 복사하지 않는다. 전체 실패 목록에서 닫힌 항목과 미해결·미재현 항목을 구별하면 다음 릴리스의 작업을 정할 수 있다.

되돌림과 개선의 한계를 적는다

문제가 생겼을 때 이전 실행 파일로 돌아가는 것은 저장 데이터 형식이나 서버 상태까지 자동으로 복원하는 일이 아니다. 새 저장 형식 v2를 옛 실행 파일이 읽지 못한다면 이전 패키지 보존만으로 충분하지 않을 수 있다. 호환 조건과 데이터 보존 경로를 별도로 설계한다.

문서의 완료율은 정의한 확인 목록의 완료 수다. 실제 사용자 수·평가 만족도·모든 결함 제거율로 바꾸어 표현하지 않는다. 실제 배포·다운로드·목표 환경 실행을 하지 않았다면 계획과 손계산만 기록한다.

중간 과정을 따라가는 예제

가상 release v1.2의 필수 확인 8개 중7개가 H 패키지에서 통과했다. 한 개는 아직 미수행이다. 공개 후보 G는 H와 내용 식별자가 다르다. 확인 완료율과 공개 후보 판정을 적자.

  1. H에서 통과한 확인 비율은7/8=87.5%다. 나머지는 실패가 아니라 미수행이라는 상태를 보존한다.

  2. G는 다른 패키지이므로 H의7개 통과 기록을 G의 통과 기록으로 세지 않는다.

  3. G를 공개하려면 정의한 필수 기준에 따라 같은 산출물을 검사하고 결과와 식별자를 연결한다. 이 시나리오는 공개를 실행한 것이 아니다.

H 확인 비율87.5%, 미수행1개다. G는 해당 검사 결과가 아직 없으며 배포 적합성을 별도 확인해야 한다.

종이와 본문으로 직접 해보기

H에서 마지막 검사를 통과한 뒤 동일 바이트의 파일을 제공하면 비율은? 사용자가 실제 다운로드·실행한 기록이 없다면 어디까지 완료라고 말할 수 있나?

힌트 보기

검사 완료와 전달 및 실행을 나눈다.

풀이 보기

정의한 H 검사8/8=100%다. 동일 파일 전달 여부를 확인할 수 있어도 사용자 다운로드·목표 환경 실행·즐거움까지 검증했다고 말할 수 없다.

오해와 반례

태그와 검사가100%면 배포·저장 호환·사용자 실행도 모두 끝났다.

태그는 소스 지점이며 확인 목록은 지정된 범위다. 공개 산출물·저장 호환·사용자 환경은 각각 다른 증거가 필요하다.
