소단원 12.1

빌드·리소스 검증

편집기에서 보이던 캐릭터가 친구의 실행 파일에서는 사라질 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 장면은 게임 객체와 상태를 묶는다.

  • 이미지·소리·글꼴은 코드가 참조하는 자원이다.

학습 목표

  • 프로젝트와 실행 배포물을 구별한다.

  • 장면의 종속 자원과 실제 패키지 목록을 대조한다.

같은 개수의 파일을 넣으면 같은 게임을 배포한 것일까요?

앞 본문은 실행 배포물과 자원 묶음을 구별하고 필요한 파일의 이름을 실제 패키지 목록과 대조했습니다. 새 자체 의존 그래프의 시작 장면은 S입니다. S는 A와 B를 요구하고, A는 T를 요구합니다. B는 T와 F를 요구하며 F는 다시 B를 요구합니다. 같은 자원을 두 경로에서 요구하거나 순환이 있어도 파일을 무한히 세지 않습니다. 이미 방문한 이름을 다시 확장하지 않는 집합으로 필요한 이름을 모으면 S, A, B, T, F의 다섯 개입니다.

추가 계약에서 실행 중 문자열 경로로 읽는 C.json이 반드시 필요하고 선택 언어의 시작 자원 J는 글꼴 JF를 요구합니다. C.json과 J를 추가 시작점으로 삼으면 필요한 서로 다른 이름은 S, A, B, T, F, C.json, J, JF의 여덟 개입니다. 패키지에 JF만 빠지면 일곱 개가 존재하여 이름 기준 충족률은 7/8입니다. 정적 장면 참조에서 찾지 못한 동적 파일도 업무 계약에 따라 별도로 포함해야 합니다. 이 그래프는 Godot의 실제 장면을 읽어 추출한 결과가 아닙니다.

이름 존재와 내용 판본 일치도 따로 확인합니다. 여덟 이름을 모두 넣어도 T가 기대 판본 2가 아니라 옛 판본 1이면 이름 충족률은 100%이지만 명시한 판본 충족률은 7/8입니다. 파일 하나를 추가해도 실제 실행·선택 언어 표시·입력 동작을 확인한 것은 아닙니다. Godot의 Export Project는 실행 배포를 만들고 Export PCK/ZIP은 자원 데이터를 내보내는 범위이므로, 자원 묶음만으로 독립 실행을 확인했다고 쓰지 않습니다.

먼저 확인할 개념
  • 빌드·리소스 검증

    실행물과 자원 목록의 기본 구분을 참조 순환·동적 파일·판본 대조에 연결합니다.

  • 릴리스와 개선보고

    시험한 배포물의 식별 정보와 미수행 검사를 보존하는 기본 설명을 이어갑니다.

실행할 대상과 데이터를 함께 준비한다

게임 프로젝트는 편집기에서 작업하는 자료이고 배포물은 사용자가 실행할 대상이다. 엔진·플랫폼·내보내기 설정에 따라 준비 과정이 달라진다. 파일 압축이 성공했다는 사실만으로 사용 가능한 실행 파일이 만들어진 것은 아니다.

Godot의 Export Project는 실행 가능한 build를 만드는 흐름이고 Export PCK/ZIP은 프로젝트 데이터만 내보내는 흐름이다. preset과 export template 및 플랫폼에 필요한 도구가 준비되어야 한다. 아래 종이 모형은 이 구별을 연습하며 실제 Godot 내보내기를 수행한 것은 아니다.

참조를 따라 누락을 찾는다

장면 S가 캐릭터 그림 T와 효과음 A를 사용하고, 화면 U가 글꼴 F를 사용한다면 S→T, S→A, U→F의 화살표를 그린다. 참조된 자원이 묶음에 없으면 그 장면을 표시하거나 재생하는 데 문제가 생길 수 있다. 디버그 빌드와 release 빌드의 자원 목록도 확인한다.

코드가 문자열로 읽는 별도 JSON 같은 파일은 선택 자원만 내보내는 규칙에서 추가 필터가 필요할 수 있다. 에디터 캐시에 있던 데이터가 깨끗한 실행 환경에도 있다고 가정하지 않는다. 같은 자원을 여러 곳에서 사용한다고 패키지 파일을 무조건 중복 개수로 세지는 않는다.

목록 검증과 사용자 실행을 연결한다

종속 목록 비교는 누락 후보를 찾는 정적 점검이다. 존재하는 파일도 형식·지원 기능·사용 경로가 다르면 실행 중 실패할 수 있다. 실제 배포물의 시작 장면·장면 전환·소리·글꼴·저장 경로를 목표 환경에서 확인하고 로그에 버전과 조건을 남긴다.

공개 패키지에는 비밀 인증키나 내보내기 credentials를 넣지 않는다. 데이터가 압축되어 있어도 수신한 사용자가 절대 읽을 수 없다고 가정할 수 없다. 이 단원에서는 공개 파일 목록 설계만 하고 실제 비밀값이나 공개 배포를 다루지 않는다.

중간 과정을 따라가는 예제

자체 모형에서 시작 장면 S는 T·A, 메뉴 U는 F, 설정은 C.json을 요구한다. 필요한 서로 다른 파일은 S,U,T,A,F,C.json이다. 패키지에는 S,U,T,A,F만 있다. 누락과 포함 비율을 구하자.

  1. 필수 파일은 6개다. T를 여러 장면이 사용해도 같은 파일은 한 번 센다.

  2. 패키지에 필요한 파일 5개가 있어 5/6×100≈83.3%다.

  3. C.json이 누락됐다. 파일 포함 비율은 실행 성공률이 아니며 설정 읽기 실패 가능성을 별도 확인해야 한다.

C.json 1개 누락이다. 포함 비율 약 83.3%는 목록 대조 수치이며 실제 게임 실행을 증명하지 않는다.

  1. S에서의 닫힘은 S, A, B, T, F입니다. 추가 시작점 C.json과 J, 그리고 J의 참조 JF를 합치면 여덟 이름입니다.

이름은 같고 판본은 다른 파일

  1. 필요한 여덟 이름이 모두 존재하므로 이름 충족률은 8/8 = 100%입니다.

연습 1 · 값과 상태 예측

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

여덟 자원의 크기는 S가 1 MiB, A가 2 MiB, B가 2 MiB, T가 4 MiB, F가 1 MiB, C.json이 1 MiB, J가 1 MiB, JF가 3 MiB입니다. 같은 이름은 한 번 저장하고 압축·관리 비용은 없다고 가정합니다. 전체 크기와 JF 누락 패키지 크기를 구하세요.

힌트 1

A와 B가 요구하는 T를 중복 저장하지 않습니다.

힌트 2

준비 개념과 학습 목표

준비 개념

  • 규칙의 성공 조건과 조작 방법은 구별된다.

  • 성공률의 분모는 관찰한 시도 수다.

학습 목표

  • 도전과 접근 장벽을 나누어 설명한다.

  • 보조 설정과 피드백의 효과를 검증할 계획을 세운다.

모든 사용자 집단의 성공률이 높아져도 전체 성공률은 낮아질 수 있을까요?

앞 본문은 가상 시도에서 성공률과 실패율을 비교하고 도움 모드의 결과를 따로 보았습니다. 새 두 집단의 가상 장부에서 변경 전 일반 집단은 10번 중 8번 성공하고 도움 집단은 2번 중 1번 성공합니다. 변경 후 일반 집단은 2번 중 2번 성공하고 도움 집단은 10번 중 6번 성공합니다. 일반 집단은 80%에서 100%로, 도움 집단은 50%에서 60%로 높아졌지만 전체는 9/12에서 8/12로 낮아집니다. 집단 구성의 비중이 바뀌었기 때문입니다.

비교의 질문을 적어야 합니다. 각 장부의 실제 구성으로 계산한 전체 비율과 두 집단을 각각 절반으로 고정한 가상 가중 비율은 다릅니다. 고정 비중에서는 변경 전 (0.8+0.5)/2 = 65%, 변경 후 (1+0.6)/2 = 80%입니다. 이는 정해 둔 비중에 대한 산술 비교이며 실제 설정 변경의 인과 효과나 실제 사용자의 만족을 입증하지 않습니다. 작은 가상 표본의 수치로 누구나 사용할 수 있다고 주장하지 않습니다.

별도 자체 시간 조절 모형은 게임 진행 시간만 소비합니다. 총 허용 시간 10초 중 5초가 경과한 상태에서 허용 시간을 20초로 바꾸면 이미 소비한 5초를 보존하여 남은 시간은 15초입니다. 일시 정지의 벽시계 30초를 게임 시간에서 제외한 뒤 4초를 더 진행하면 누적 게임 시간은 9초이고 남은 시간은 11초입니다. Microsoft의 난이도 지침은 시간을 조절하고 진행을 잃지 않는 선택의 필요성을 설명하지만 이 계산식과 정지 계약은 새 종이 모형의 추가 조건입니다.

먼저 확인할 개념
  • 난이도·접근성·피드백

    집단별 성공과 시간·입력·피드백 조절을 구별한 기본 설명을 이어갑니다.

  • 릴리스와 개선보고

    시험한 대상과 미확인 항목을 기록하는 기본 릴리스 설명을 집단별 증거에 연결합니다.

장벽의 종류를 먼저 찾는다

게임의 어려움은 플레이어 능력과 게임이 요구하는 행동의 관계에서 생긴다. 빠른 반복 입력, 작은 목표 조준, 짧은 제한 시간, 복잡한 기억 과제는 다른 종류의 도전이다. 한 가지 쉬움/어려움 설정만으로 모두의 필요를 충족한다고 단정하지 않는다.

예를 들어 퍼즐 생각은 즐기지만 손을 빠르게 움직이기 어려운 사람에게 퍼즐 답을 알려 주는 대신 시간 제한을 조절할 수 있다. 지원 설정은 어떤 행동을 바꾸는지 설명한다. 플레이어를 비하하는 모드 이름보다 제한 시간·적 공격·힌트 같은 변화 내용을 알려 준다.

설정과 진행 및 피드백을 연결한다

난이도를 바꿀 때 이미 쌓은 진행을 어떻게 보존할지 정한다. 저장 지점·일시정지·설정 복원이 있으면 반복 실패 후 다시 접근하기 쉽다. 다만 온라인 다인 게임의 공정성이나 서버 상태처럼 추가 조건이 있는 경우도 있어 모든 게임이 같은 처리 정책을 쓰지는 않는다.

피드백은 성공/실패와 다음 행동을 알아볼 수 있게 돕는다. 실패 원인이 시간 부족인지 잘못된 선택인지 표시하고, 색 하나나 소리 하나만으로 중요한 정보를 전달하지 않는 방안을 생각한다. 그림을 바꾼 설계 의도와 실제 플레이어가 정보를 이해했는지는 별도 확인한다.

평균만 보고 장벽을 숨기지 않는다

관찰할 때 도움 제공·기기·설정·이전 경험과 목표 과제를 기록한다. 전체 성공률이 올라도 특정 입력 방식의 실패가 남을 수 있다. 따라서 접근성 옵션 존재와 실제로 이용 가능한 상태, 플레이어가 이해하고 사용하는 상태를 나누어 확인한다.

종이 예제의 실패율 감소는 기술 통계다. 실제 플레이 실험이 없으므로 보조 모드의 효능이나 재미를 검증한 수치가 아니다. 차이가 난 이유를 확인하려면 같은 과제·성공 기준과 연구 절차를 설계하고 실제 관찰을 별도로 해야 한다.
