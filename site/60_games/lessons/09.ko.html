소단원 9.1

비동기로드와 cache

화면을 넘겼는데 늦게 도착한 그림이 이전 장면에 붙으면 어떻게 될까?

준비 개념과 학습 목표

준비 개념

  • 게임 프레임

  • 리소스와 참조

학습 목표

  • 요청 반환과 결과 준비를 구별한다.

  • cache 소유권과 오래된 결과를 추적한다.

요청 둘이 같은 로드를 기다릴 때 한 요청의 취소가 다른 요청도 취소해야 할까요?

앞 본문은 늦게 돌아온 결과의 세대와 handle의 책임을 구별했습니다. 새 자체 wrapper는 cache 키를 (자산 이름, 자료 버전)으로 두고 같은 키의 진행 중 엔진 로드를 하나만 공유합니다. 엔진 handle H를 wrapper 하나가 소유합니다. 소비자 요청 A와 B는 별도의 요청 ID와 장면 세대를 가지고 기다립니다. A가 취소되어도 B의 대기는 유지하며, 이것을 엔진 I/O 취소 성공이라고 보고하지 않습니다.

여기서 논리 lease는 wrapper 내부의 사용 권한 장부이며 엔진 reference count와 같은 수치가 아닙니다. 로드가 성공하고 살아 있는 소비자가 있을 때 cache의 lease 하나와 소비자마다 lease 하나를 기록합니다. 마지막 논리 lease가 사라지면 wrapper가 H를 한 번 release합니다. cache 퇴출은 cache의 lease만 없애며 소비자가 가진 lease는 유지합니다. 기다리는 소비자는 완료 전에는 결과 lease를 갖지 않습니다. 실패나 살아 있는 소비자가 없는 완료는 cache에 게시하지 않고 H를 한 번 정리하는 자체 정책입니다.

세대 검사는 화면 적용을 막는 조건이고 자료 버전 검사는 올바른 cache 항목을 고르는 조건입니다. 같은 세대에서도 v1 자료를 v2 요청의 답으로 붙이면 틀립니다. 또한 작업 수 기준 진행과 바이트 기준 진행은 다른 분모입니다. 별도 가상 두 작업이 1 B와 100 B이고 작은 작업만 완료했다면 완료 작업은 1/2이지만 완료 바이트는 1/101입니다. 실제 Addressables 진행값이나 파일 전송 속도를 이 가상 비율로 측정했다고 하지 않습니다.

준비 중에도 게임은 계속한다

비동기 로드는 요청의 제어를 빨리 돌려주지만 결과가 준비되었다는 뜻은 아니다. 완료 handle·callback 등으로 성공/실패를 확인하고 준비 전에는 loading 표시나 대체 리소스를 쓴다.

현재 thread를 막아 완료를 기다리면 프레임이 멈출 수 있다. 비동기라는 이름도 모든 decode·GPU 작업이 무조건 프레임 예산 안에서 끝난다는 보장은 아니므로 실제 프로파일링은 별도다.

같은 리소스의 소유권을 관리한다

cache는 준비된 값을 재사용하는 정책이다. 키에는 자산 ID와 버전처럼 결과를 식별할 정보를 포함하고, 재사용 중인 값을 eviction할 때 살아 있는 소비자의 소유권을 확인한다.

Unity Addressables의 load/release는 참조 수를 관리하며 load와 정리가 대응해야 한다. 참조가 0이어도 같은 bundle의 다른 자산 때문에 즉시 메모리에서 사라지지 않을 수 있다. 아래 cache 정책을 엔진 내부와 동일하다고 가정하지 않는다.

오래된 완료는 현재 장면에 적용하지 않는다

요청에 장면 generation을 붙이면 완료 시 현재 값과 비교할 수 있다. 값이 다르면 새 장면 UI에 붙이지 않고 얻은 handle의 정리 책임을 수행한다. 화면을 떠났다는 이유만으로 실제 I/O가 취소되었다고 생각하지 않는다.

실패도 handle·대기자 정리가 필요하다. in-flight 요청을 한 개로 합치는 정책이라면 여러 소비자에게 완료를 전달하되 개별 취소와 마지막 참조의 해제를 따로 처리한다.

중간 과정을 따라가는 예제

자체 로더의 장면 generation은 7이다. 요청 R에 7을 붙이고 로딩 중 장면이 8로 바뀐다. R 완료 후 자산 handle H가 생긴다. 별도 정상 cache 소비자 A/B가 각각 참조 하나를 갖는 모형도 추적하자.

  1. R의 7과 현재 8이 다르므로 새 장면에는 결과를 적용하지 않는다. H를 얻었으므로 정리 책임을 수행한다.

  2. 정상 cache의 A/B 참조 수는 2이고 A 종료 후 1이라 B는 계속 사용한다.

  3. B 종료 후 0이면 이 자체 정책의 eviction 후보지만 실제 Addressables bundle 메모리 해제 시점은 별도다.

오래된 결과는 적용하지 않고 handle을 정리한다. 참조 2→1→0과 실제 물리 해제는 구별한다.

조건을 바꾸어 비교하기

한 소비자를 취소해도 공유 로드를 유지하기

A는 세대 7, B는 세대 8입니다. 같은 (hero,v2)를 기다리다가 A가 취소됩니다. 완료 때 B는 살아 있습니다. cache 퇴출과 B 종료까지 책임을 추적하세요.

  1. 완료 전 A와 B의 결과 lease는 없습니다. A 취소는 A의 대기 등록만 제거합니다.

  2. 완료 때 cache와 B에 각각 lease 하나를 주어 논리 합계가 2개입니다. A에는 적용하지 않습니다.

  3. cache 퇴출 뒤 합계는 1개입니다. B 종료 뒤 0개가 되어 wrapper가 H를 한 번 release합니다.

B는 결과를 사용할 수 있고 H 정리는 마지막 lease 뒤 한 번입니다.

비교할 점

A 취소 때 H를 무조건 정리하면 B의 사용 계약을 훼손할 수 있습니다.

lease가 사라져도 bundle 전체 해제와는 다른 경우

별도 가상 bundle 크기는 192 KiB이며 자산 A의 자료는 120 KiB, B의 자료는 40 KiB입니다. A 참조는 0, B 참조는 1입니다. A 정리만으로 120 KiB의 실제 메모리가 즉시 돌아왔다고 말할 수 있나요?

  1. 자료 크기 두 개의 합은 160 KiB이며 bundle 크기와도 다릅니다.

  2. B의 참조가 남은 bundle에서는 A 참조 0만으로 부분 unload를 보장하지 않습니다.

  3. 192 KiB를 실제 프로세스 상주 크기라고 가정하지도 않습니다.

즉시 120 KiB 회수나 bundle 전체 회수를 보장할 수 없습니다.

비교할 점

논리 장부·bundle 수명·측정된 실제 메모리 크기를 따로 기록합니다.

연습 1 · 값과 상태 예측

표의 순서에서 B가 cache 퇴출보다 먼저 사용을 끝냅니다. 완료 직후부터 H 정리까지 논리 lease 수를 구하세요.

힌트 1

완료 직후 cache와 B가 각각 하나입니다.

힌트 2

cache 자체도 소유자입니다.

풀이와 답 확인

  1. 완료 직후 합계는 2개입니다. B 종료 뒤 cache만 남아 1개입니다.

  2. cache 퇴출 뒤 0개가 되어 H를 한 번 release합니다.

논리 합계는 2개, 1개, 0개 순서입니다.

흔한 오답에서 다시 생각하기

B가 끝나면 cache 존재와 무관하게 H를 정리한다.

cache의 결과 유지 책임이 남아 있으므로 이 정책에서는 마지막 lease까지 기다립니다.

연습 2 · 오류 찾아 고치기

현재 장면 세대는 8입니다. (hero,v1)의 성공 응답과 (hero,v2)의 요청이 모두 세대 8이라는 이유로 v1 결과를 v2 요청에 적용했습니다. 어느 검사가 빠졌나요?

힌트 1

세대와 자료 버전의 목적을 나눕니다.

힌트 2

공유 키의 두 좌표를 확인합니다.

풀이와 답 확인

  1. 세대 검사는 통과하지만 자산 이름과 자료 버전의 요청 키가 일치하지 않습니다.

  2. v1은 해당 키의 대기자에게만 전달하고 v2의 로드는 별도 키로 유지합니다.

세대가 같아도 자료 버전이 다른 응답을 적용하면 안 됩니다.

흔한 오답에서 다시 생각하기

같은 장면 세대이면 모든 자료 버전이 호환된다.

장면의 생존과 자료 호환성은 별도 조건입니다.

연습 3 · 직접 만들어 보기

A와 B가 기다리다가 둘 다 완료 전에 취소되었습니다. 뒤늦게 H가 성공 완료합니다. 이 wrapper의 cache 게시·결과 적용·정리 횟수를 설계하세요.

힌트 1

살아 있는 소비자가 없는 완료 정책을 사용합니다.

힌트 2

성공 결과와 게시 여부는 다릅니다.

풀이와 답 확인

  1. cache에 게시하지 않고 A와 B에 적용하지 않습니다.

  2. wrapper가 H를 한 번 release하고 진행 중 항목을 제거합니다. 각 요청 취소 때 같은 H를 중복 release하지 않습니다.

게시 0회, 적용 0회, H release 1회입니다.

흔한 오답에서 다시 생각하기

성공 완료했으므로 무조건 cache lease를 만든다.

이번 자체 정책은 살아 있는 소비자가 없는 완료를 cache에 남기지 않습니다. 다른 정책은 명시적으로 따로 설계해야 합니다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

별도 가상 작업 두 개의 크기는 1 B와 100 B입니다. 작은 작업만 완료했을 때 작업 완료 비율과 바이트 완료 비율을 구하고 어느 비율도 남은 시간을 바로 정하지 못하는 이유를 쓰세요.

힌트 1

각 비율의 분모를 먼저 씁니다.

힌트 2

처리 속도와 의존 관계는 주어지지 않았습니다.

풀이와 답 확인

  1. 작업 완료 비율은 1/2 = 50%입니다. 바이트 완료 비율은 1/101로 약 0.99%입니다.

  2. 속도와 남은 단계의 비용을 모르므로 두 값만으로 완료 시각을 결정하지 못합니다.

작업 수와 바이트 수의 분모가 다르고 시간 예측 정보도 부족합니다.

흔한 오답에서 다시 생각하기

작업 절반이 완료했으므로 남은 시간도 정확히 절반이다.

작업 크기와 비용이 같다는 조건이 없으며 실제 API 진행의 의미도 별도 확인해야 합니다.

소단원 9.2

오디오이벤트

동전을 얻을 때 한 번만 소리가 나야 하는데 매 프레임 울린다면?

준비 개념과 학습 목표

준비 개념

  • 상태 변화와 프레임

  • 이벤트

학습 목표

  • 이벤트 발생과 재생 상태를 구별한다.

  • 동시 재생·bus·정리 정책을 추적한다.

소리 세 개만 남길 때 가장 오래된 소리와 가장 낮은 우선순위 소리 중 무엇을 끊을까요?

앞 본문은 Godot의 max_polyphony가 넘으면 오래된 소리를 차단하는 규칙을 읽었습니다. 새 자체 이벤트 관리자는 최대 활성 소리 3개, 정수 우선순위가 클수록 중요하다는 별도 규칙을 둡니다. 공간이 없으면 가장 낮은 활성 우선순위를 찾습니다. 새 우선순위가 그보다 낮으면 새 요청을 버립니다. 같거나 높으면 가장 낮은 우선순위 중 가장 먼저 시작한 소리를 끊고 새 소리를 시작합니다. 이 우선순위 정책은 Godot 기본 oldest 규칙이라고 주장하지 않습니다.

이벤트 ID 장부는 ID와 내용 및 채택/거절 결과를 함께 기록하는 자체 설계입니다. 같은 ID와 같은 내용의 재전달은 기존 결과를 돌려주고 다시 재생하지 않습니다. 같은 ID의 다른 내용은 충돌로 거절합니다. 재생 요청을 채택했다는 장부는 스피커에서 실제로 들렸다는 증거가 아닙니다. 재생 완료 전에 프로그램이 중단되는 실패와 장부/재생 호출의 원자성은 별도 설계 문제로 남습니다.

수명 정리도 자연 종료만 기다릴 수 없습니다. Godot finished는 stop 호출이나 트리 이탈에 나오지 않는 조건을 확인했습니다. 이 자체 관리자는 자연 종료·명시 중지·대상 제거를 각각 종료 경로로 연결하고 동일 소리의 정리를 멱등하게 처리합니다. 버스 경로는 Master, Music, Sfx의 순서에서 Sfx→Music→Master처럼 왼쪽으로 보냅니다. 효과 순서와 stream 교체의 중지를 숨기지 않으며 청감·출력 장치는 측정하지 않습니다.

먼저 확인할 개념
  • 오디오이벤트

    기본 oldest 차단·finished 조건·버스 routing을 자체 우선순위 정책과 비교합니다.

  • 비동기로드와 cache

    장면 세대와 대상 생존 및 handle 정리 책임을 구별합니다. 요청 ID 장부는 이 보강의 자체 확장입니다.

게임 변화가 소리 요청을 만든다

코인 획득 같은 한 번의 상태 변화에서 오디오 이벤트를 만든다. 매 프레임 코인을 보유하는 조건을 검사해 재생하면 지속 상태를 사건으로 잘못 해석한 것이다.

이벤트 ID·클립 ID·목적 bus·필요한 위치를 정하고 같은 사건의 중복 요청을 어떻게 처리할지 정책을 둔다. UI나 배경음의 비위치 재생과 세계 위치에 따른 2D/3D 재생도 구별한다.

동시에 들리는 수와 경로를 정한다

player의 동시 재생 한도는 새 요청을 처리하는 정책과 연결된다. Godot AudioStreamPlayer의 max_polyphony를 넘는 play는 가장 오래된 소리를 잘라내므로 모든 엔진이 같은 정책이라고 일반화하지 않는다.

효과음·음악 등을 bus로 나누면 볼륨과 효과를 그룹별로 관리하고 Master로 보낼 수 있다. clip, player, bus는 각각 자료·재생 상태·혼합 경로라 하나로 섞지 않는다.

종료 사건과 강제 중지를 구분한다

자연스럽게 끝남과 stop 호출·장면 이탈의 정리 경로가 다를 수 있다. Godot finished는 중단 없이 완료될 때 발생하며 stop이나 재생 중 tree 이탈에는 발생하지 않는다.

따라서 finished만 기다려 모든 정리를 처리하면 강제 중지 때 남는 상태가 생긴다. 완료·취소·이탈에서 공통 정리 함수를 쓰는 등 정책을 설계하고 실제 듣기·장치 검사는 별도로 수행한다.

중간 과정을 따라가는 예제

Godot 문서의 oldest 차단 정책을 쓰는 가상 player에서 max_polyphony=2다. A,B,C를 순서대로 play하고, 그동안 자연 종료는 없다.

  1. A 뒤 재생 목록은 [A], B 뒤 [A,B]다.

  2. C 요청은 한도를 넘으므로 가장 오래된 A를 차단하고 [B,C]가 된다.

  3. stop으로 재생을 강제 중지했다면 finished를 자연 완료 통보처럼 기다리지 말고 별도 정리 경로를 수행한다.

C 뒤 두 소리 B/C가 남고 A는 차단된다. 실제 오디오 재생 결과는 아니다.

조건을 바꾸어 비교하기

우선순위와 오래된 순서의 두 단계 선택

표의 A부터 E까지 처리할 때 중지한 소리와 거절한 요청, 활성 소리를 구하세요.

  1. A, B, C가 세 칸을 채웁니다.

  2. D의 우선순위 0은 최저 1보다 낮아 거절합니다.

  3. E의 우선순위 1은 최저와 같아 A와 B 중 먼저 시작한 A를 중지합니다.

중지한 소리는 A이고 거절한 요청은 D입니다. 활성 순서는 B, C, E입니다.

비교할 점

단순히 모든 새 요청마다 가장 오래된 소리를 끊는 정책과 다릅니다.

자연 종료 신호만으로는 정리 수를 셀 수 없는 경우

서로 다른 소리 P, Q, R 세 개를 시작합니다. P는 자연 종료, Q는 stop으로 중지, R은 트리에서 제거합니다. 각 소리의 정리는 한 번입니다. finished 수와 정리 수를 구하세요.

  1. 자연 종료 P에서만 finished가 나오는 주어진 조건입니다.

  2. Q와 R도 별도 종료 경로에서 소유 장부를 정리합니다.

  3. 같은 대상의 뒤늦은 종료 알림이 다시 와도 멱등 정리합니다.

finished는 1회이고 소리 정리는 총 3회입니다.

비교할 점

finished 수를 총 종료 수로 해석하면 Q와 R의 책임이 남습니다.

연습 1 · 값과 상태 예측

표의 마지막 B, C, E 상태에 F 우선순위 2를 새 ID로 전달합니다. 중간 자연 종료는 없습니다. 어느 소리를 끊고 무엇이 남나요?

힌트 1

최저 우선순위는 여전히 1입니다.

힌트 2

B와 E의 시작 순서를 비교합니다.

풀이와 답 확인

연습 2 · 오류 찾아 고치기

E의 채택 결과를 ID 41과 내용 (click,우선순위 1)로 저장했습니다. 같은 ID와 내용이 재전달된 뒤 같은 ID의 (alarm,우선순위 2)가 옵니다. 두 경우를 모두 새 재생으로 처리하는 오류를 고치세요.

힌트 1

동일 재전달과 충돌을 나눕니다.

힌트 2

현재 활성 여부만으로 과거 요청 ID를 잊지 않습니다.

풀이와 답 확인

  1. 첫 재전달은 기존 채택 결과만 돌려주며 새 재생은 없습니다.

  2. 다른 내용의 두 번째 요청은 ID 충돌로 거절합니다.

동일 재전달의 추가 재생은 0회이고 다른 내용은 충돌입니다.

흔한 오답에서 다시 생각하기

같은 ID이면 새 내용으로 과거 장부를 덮어쓴다.

과거 ID의 의미를 바꾸면 재전달 판정과 호출자에게 돌려주는 결과가 달라집니다.

연습 3 · 직접 만들어 보기

버스 순서는 Master가 0, Music이 1, Sfx가 2입니다. Sfx를 Music으로, Music을 Master로 보내려 합니다. Music을 Sfx로 되돌리는 제안과 비교하고, 별도 선형 배율 0.5를 두 단계 적용한 신호 비율을 구하세요.

힌트 1

경로는 왼쪽으로 보내는 규칙입니다.

힌트 2

선형 배율은 이 문제의 자체 산술이며 dB나 청감이 아닙니다.

풀이와 답 확인

  1. 2→1→0은 왼쪽 routing입니다. 1→2를 추가하면 방향 규칙에 어긋나며 Sfx와 Music의 순환을 만듭니다.

  2. 자체 선형 신호 비율은 0.5×0.5 = 0.25입니다.

정상 경로는 Sfx→Music→Master이고 별도 신호 비율은 1/4입니다.

흔한 오답에서 다시 생각하기

버스 두 단계를 지나면 사람이 느끼는 크기도 반드시 1/4이다.

여기서는 선형 신호 산술만 정했습니다. dB와 사람의 청감 및 효과 처리는 별도입니다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

P가 자연 종료된 뒤 대상 제거 알림도 들어옵니다. 두 경로가 같은 lease를 각각 반환하면 어떤 오류이며 정리 장부에는 어떤 상태 전이가 필요한가요?

힌트 1

종료 알림 수와 소유 책임 수를 나눕니다.

힌트 2

활성에서 정리됨으로 한 번 이동합니다.

풀이와 답 확인

  1. 첫 종료에서 활성 책임을 정리됨 상태로 바꾸고 lease를 한 번 반환합니다.

  2. 뒤 알림은 정리됨 상태를 보고 추가 반환하지 않습니다.

두 알림이어도 같은 책임 반환은 1회입니다.

흔한 오답에서 다시 생각하기

모든 종료 알림마다 release해야 누수가 없다.

이미 반환한 책임을 다시 반환하면 중복 정리입니다. 다른 실제 소유자가 있다면 각각 별도로 장부에 있어야 합니다.

앞 본문은 v1 coin을 v2 cents로 변환하고 검증 뒤 적용하는 자체 정책을 추가했습니다. 새 자체 저장 계약은 v1 coin 정수, v2 cents 정수, v3 wallet.cents 정수입니다. 허용 잔액은 0부터 100000 cents입니다. v1은 coin이 0부터 1000까지인 것을 먼저 확인한 뒤 100을 곱합니다. v2는 이미 cents이므로 다시 100을 곱하지 않습니다. v3로의 변경은 같은 금액을 wallet 필드에 넣는 구조 변경입니다. 미래 버전은 현재 상태를 보존하며 거절합니다.

별도 객체 저장은 지속 ID와 parent ID를 사용합니다. 전체 자료에서 ID 중복과 누락된 부모를 먼저 검사하고, 모든 후보 객체를 만든 뒤 ID 맵으로 부모를 연결합니다. 연결 전에는 자기 자신을 부모로 삼거나 A의 부모가 B이고 B의 부모가 A인 순환도 거절합니다. ID가 유일하고 부모가 모두 존재해도 트리 관계가 유효한 것은 아닙니다. 배열에서 자식이 먼저 나온다고 부모가 없는 것은 아닙니다. 모든 검사·연결이 성공한 후보만 현재 장면과 교체한다는 자체 정책이며 Godot 안내 예제의 기존 노드 삭제 순서를 그대로 보장한다고 하지 않습니다. 엔진의 실행 중 객체 식별값을 재실행 후에도 같은 지속 ID라고 가정하지 않습니다.

금액과 항목의 관계도 한 시점의 snapshot이어야 합니다. 자체 불변식은 wallet.cents = 100×항목 coin 합입니다. 처음 항목 [7,3]과 wallet 1000이 있다가 [7,5]와 wallet 1200으로 갱신됩니다. 옛 wallet과 새 항목을 섞으면 각각의 자료형·범위는 정상이어도 관계가 깨집니다. 후보 파일 완성과 논리 공개를 구별하고, 저장 snapshot의 판본이 최신 공개 판본보다 큰 경우에만 원자적으로 교체하는 자체 정책을 둡니다. 파일 이름 바꾸기만으로 전원 장애 내구성이나 실제 다중 writer의 원자성을 검증했다고 하지 않습니다.

먼저 확인할 개념
  • 세이브와 데이터버전

    JSON 구문과 업무 범위·migration 및 후보 검증 뒤 적용의 자체 계약을 이어 사용합니다.

  • 비동기로드와 cache

    장면 세대와 응답을 적용할 대상의 현재 생존 상태를 구별합니다. 저장 판본 비교는 이 보강에서 추가하는 자체 정책입니다.

다시 만들 수 있는 상태를 고른다

저장에는 점수·진행 단계·객체 ID처럼 다음 실행에서 의미를 복원할 값을 담는다. 메모리 주소·열린 handle·현재 callback은 다음 프로세스에서 그대로 유효한 값이 아니다.

Godot 예시는 Persist 그룹의 객체가 dictionary를 만들고 JSON으로 user:// 파일에 저장한다. JSON은 엔진의 모든 자료형을 자동 보존하지 않으므로 좌표를 수치 필드로 분리하는 등 표현 계약을 정한다.

버전은 데이터 해석 규약이다

version 필드를 두고 지원 가능한 과거 버전에서 현재 schema로 변환한다. 이름·단위가 바뀌면 단순 복사 대신 명시적 변환이 필요하며 이미 현재 버전인 값에 같은 변환을 또 적용하지 않는다.

아래 coin→coin_cents 변환은 자체 게임의 가상 규약이다. 알 수 없는 미래 버전은 근거 없이 추측 변환하지 않고 읽기 실패를 알려 원본을 보존한다.

검증한 상태를 한 번 적용한다

parse 성공은 자료형·범위·객체 ID·데이터 일관성이 맞다는 뜻이 아니다. 임시 상태에서 검사와 migration을 마친 뒤 현재 세계에 적용하면 손상된 입력이 진행 중 게임을 부분 변경하는 위험을 줄일 수 있다.

파일 쓰기도 중단·용량 부족·손상에 대한 정책이 필요하다. 임시 파일·백업·교체·동기화는 플랫폼별 보장이 달라 실제 저장 내구성 실험 없이는 항상 원자적·전원 손실 안전하다고 선언하지 않는다.

중간 과정을 따라가는 예제

자체 schema v1은 {version:1, coin:12}, v2는 {version:2, coin_cents:정수}다. 변환은 coin_cents=100×coin이며 허용 범위는 0..100000이다. 현재 게임 값은 500이다.

  1. v1의 coin 12 를 정수·범위로 확인한 뒤 100×12=1200 인 v2 임시 상태를 만든다.

  2. 1200은 범위 안이라 검증 완료 후 현재 값을 1200으로 한 번 적용한다.

  3. 이미 v2 인 1200 은 그대로 해석한다. 다시 100 을 곱해 120000 으로 만들면 규약과 범위를 위반한다.

정상 migration 후 version 2/coin_cents 1200 이며 현재 상태 적용은 검증 뒤 한 번이다.

조건을 바꾸어 비교하기

단위 변환을 한 번만 적용하기

v1 coin 12와 별도 v2 cents 1200을 각각 v3로 변환합니다. 현재 wallet.cents는 500이며 실패 때 보존합니다.

  1. v1 coin 12는 0부터 1000 범위 안이므로 100을 곱해 1200 cents입니다.

  2. v2의 1200은 이미 cents이므로 그대로 1200입니다.

  3. 두 후보 모두 허용 범위 안이며 v3 wallet.cents에 1200을 저장합니다.

두 독립 입력의 후보 금액은 모두 1200 cents입니다.

비교할 점

v2에도 100을 곱하면 120000 cents로 범위를 벗어나며 단위도 틀립니다.

자식 행이 먼저 있어도 전체 맵으로 연결하기

객체 행 순서는 B(parent=A), A(parent 없음)입니다. 각 ID는 유일합니다. 두 단계 후보 생성과 연결을 쓰세요.

  1. 첫 단계에서 B와 A를 만들고 ID 맵에 각각 등록합니다.

  2. 둘째 단계에서 B의 parent ID A를 맵으로 찾아 연결합니다.

  3. 전체 연결 성공 뒤 현재 장면을 후보와 교체합니다.

행 순서와 무관하게 B의 부모를 A로 연결할 수 있습니다.

비교할 점

첫 행만 보고 부모가 누락되었다고 단정하면 전체 자료에 있는 A를 놓칩니다.

풀이와 답 확인

  1. 완료 때 cache와 B의 lease로 합계는 2개입니다. cache 퇴출 뒤 1개, B 종료 뒤 0개이며 wrapper가 H를 한 번 release합니다.

  2. D는 거절합니다. E는 최저 동률 중 먼저 시작한 A를 중지합니다. 활성 소리는 B, C, E입니다.

  3. coin 12는 1200 cents이며 v3 wallet.cents에 넣습니다. B와 A를 모두 후보로 만든 뒤 ID 맵에서 B의 부모 A를 연결합니다.

  4. 다른 후보의 항목 합은 12여서 요구 금액은 1200입니다. 옛 wallet 1000과 불일치하므로 공개하지 않습니다.

논리 lease 합계는 2개, 1개, 0개로 줄며 H는 마지막에 한 번 정리합니다. D는 거절하고 A를 중지하여 B, C, E가 남습니다. v3 금액은 1200 cents이며 전체 ID 맵으로 B를 A에 연결합니다. 옛 금액과 새 항목을 섞은 후보는 거절합니다.

해결한 뒤 점검할 것

  • 취소한 대기자와 살아 있는 소비자의 수명을 분리한다.

  • cache 퇴출과 마지막 책임 정리 및 bundle 메모리 회수를 구별한다.

  • 자체 소리 우선순위를 Godot 기본 oldest 정책과 구별한다.

  • 금액 단위 변환·전체 ID 연결·한 시점 관계 검증 뒤 후보를 공개한다.

  • 새 엔진·오디오·파일·학생 실행을 미수행으로 기록한다.
