평균 시간이 같으면 같은 수의 프레임이 마감을 지킬까요?

앞 본문은 60 fps 목표의 프레임 예산을 1000/60 ms로 계산하고 각 프레임의 시간을 확인했습니다. 새 가상 기록 A는 12, 12, 12, 12, 32 ms이고 B는 16, 16, 16, 16, 16 ms입니다. 두 기록은 각각 총 80 ms로 평균 16 ms이며 총 프레임 수를 총 시간으로 나눈 처리율도 62.5 fps입니다. 하지만 A는 프레임 하나가 예산을 넘고 B는 하나도 넘지 않습니다. 평균만으로 각 프레임의 마감 충족을 결정할 수 없습니다.

별도 자체 파이프라인은 CPU 한 개와 GPU 한 개가 서로 다른 프레임의 일을 겹쳐 처리할 수 있다고 가정합니다. 각 프레임은 CPU 6 ms를 먼저 끝낸 뒤 GPU 10 ms를 실행합니다. 각 장치는 한 번에 한 작업만 실행하고 선점·추가 대기·동기화 비용은 없습니다. 프레임 세 개를 시각 0부터 CPU 순서대로 공급하면 GPU 완료 시각은 16, 26, 36 ms입니다. 첫 결과 지연은 16 ms이고 이후 완료 간격은 10 ms입니다. 세 프레임 구간의 처리율 3/0.036 fps와 긴 정상 구간의 처리율 100 fps는 서로 다른 관찰 구간입니다.

프로파일러에서 어느 구간을 측정했는지 먼저 적습니다. 실제 장치의 실행, Editor의 실행, 시작 준비를 포함한 구간은 같은 관찰 조건이 아닙니다. 새 파이프라인의 병목 계산은 명시한 장치·의존 관계의 종이 모형이며 실제 Unity의 CPU/GPU 겹침을 측정한 값이 아닙니다. 계측 자체의 비용도 조건에 포함해야 하며, 프레임 시간의 역수를 각각 평균한 값은 총 프레임 수를 총 시간으로 나눈 처리율과 일반적으로 다릅니다.

목표 빈도를 한 프레임 시간으로 바꾼다

60프레임/초의 목표 간격은 1000/60≈16.667ms다. 30프레임/초는 약33.333ms,120프레임/초는 약8.333ms다. 이는 목표 간격이며 화면 출력과 입력 지연 등 모든 품질 지표를 같은 숫자로 표현하지 않는다.

예산 안에 들어가려면 실제 병목 경로의 작업을 관측한다. CPU와 GPU가 겹쳐 일할 수 있으므로 각각의 수치를 무조건 더하지 않는다. 아래 종이 예제는 한 프레임 안 작업이 직렬이며 겹치지 않는다고 명시한 단순 모형이다.

어디서 시간이 쓰였는지 관측한다

profiling은 함수·메모리·렌더링 등 성능 정보를 수집해 비용의 원인을 찾는 과정이다. 먼저 반복 가능한 장면과 입력,빌드·품질 설정·장치를 기록한다. 가장 큰 구간을 바꾼 뒤 같은 조건에서 다시 비교하되 기능 결과가 같아야 한다.

Editor 관측은 개발 중 원인을 찾는 데 유용하지만 출시 장치 결과를 대신하지 않는다. 관측 도구 자체의 비용도 생각해야 한다. 이 교재는 가상 시간표만 계산하며 Profiler 스크린샷이나 실제 장치 FPS를 만들어 내지 않는다.

평균만으로 순간 지연을 숨기지 않는다

프레임 시간의 합을 프레임 수로 나누면 평균 시간이다. 그 역수로 얻은 전체 처리율은 개별 프레임 FPS의 평균과 다를 수 있다. 적은 수의 긴 프레임도 체감 끊김에 영향을 줄 수 있어 최댓값과 예산 초과 횟수를 함께 본다.

초기 로딩이나 새 자원 적재가 포함된 구간과 이미 준비된 구간을 구별한다. 예산 초과가 관측되면 원인별 추적을 하고 표본 길이·장면 범위를 보고한다. 짧은 가상 표가 모든 플레이 장면의 성능을 인증하지 않는다.

중간 과정을 따라가는 예제

직렬 프레임의 입력1ms·게임 논리5ms·렌더 준비6ms·기타2ms를 합하고 60fps 예산과 비교하라.

  1. 합은1+5+6+2=14ms다.

  2. 60fps 예산1000/60≈16.667ms보다 약2.667ms 여유가 있다.

  3. 추가 작업4ms가 생기면18ms로 예산을 약1.333ms 넘는다.

기본14ms는 이 직렬 모형 예산 안이고 추가 후18ms는 초과다. 실제 출력 fps 측정값은 아니다.

조건을 바꾸어 비교하기

평균 16 ms의 두 기록을 비교하기

A와 B의 평균, 총 구간 처리율, 60 fps 예산 초과 비율을 계산하세요.

  1. 두 기록의 시간 합은 각각 80 ms이고 평균은 80/5 = 16 ms입니다.

  2. 각 처리율은 5/0.08 = 62.5 fps입니다. A의 32 ms 프레임만 1000/60 ms를 넘습니다.

  3. A의 초과 비율은 1/5 = 20%이고 B의 초과 비율은 0/5 = 0%입니다.

평균과 처리율은 같지만 A는 마감 초과가 1개이고 B는 0개입니다.

비교할 점

가상 기록의 결과를 실제 화면의 지연이나 사용자의 불편 정도를 측정한 결과로 쓰지 않습니다.

CPU만 줄이는 경우와 GPU만 줄이는 경우

세 프레임 파이프라인에서 CPU만 3 ms로 줄이는 경우와 GPU만 7 ms로 줄이는 경우를 각각 원래 모형에서 독립적으로 계산하세요.

  1. CPU 3 ms / GPU 10 ms에서는 CPU 종료가 3, 6, 9 ms입니다. GPU 완료는 13, 23, 33 ms이고 이후 간격은 10 ms입니다.

  2. CPU 6 ms / GPU 7 ms에서는 CPU 종료가 6, 12, 18 ms입니다. GPU 완료는 13, 20, 27 ms이고 이후 간격은 7 ms입니다.

  3. 두 경우의 첫 결과 지연은 모두 13 ms이지만 긴 정상 구간의 처리율은 각각 100 fps와 1000/7 fps입니다.

CPU만 줄이면 세 프레임 완료 시각은 33 ms이고 GPU만 줄이면 27 ms입니다. 첫 결과 지연만 같다고 전체 성능이 같은 것은 아닙니다.

비교할 점

이번 이상 모형에서 GPU가 병목이라는 판단은 실제 장치의 병목을 확인했다는 뜻이 아닙니다.

연습 1 · 값과 상태 예측

원래 CPU 6 ms / GPU 10 ms 파이프라인에서 두 장치를 겹치지 않고 프레임 하나의 CPU와 GPU를 끝낸 뒤 다음 프레임을 시작합니다. 세 완료 시각과 전체 시간을 구하세요.

힌트 1

프레임 하나의 두 작업 시간은 합산합니다.

힌트 2

다음 CPU는 앞 프레임 GPU 완료 뒤 시작합니다.

풀이와 답 확인

  1. 한 프레임은 6+10 = 16 ms입니다.

  2. 완료 시각은 16, 32, 48 ms이고 전체 구간은 48 ms입니다. 원래 겹친 모형은 36 ms입니다.

겹치지 않는 모형은 세 프레임에 48 ms가 걸립니다.

흔한 오답에서 다시 생각하기

겹침 여부와 무관하게 전체 시간은 max(6,10)×3 = 30 ms다.

첫 프레임의 선행 의존과 겹침 허용 여부를 빠뜨렸습니다.

연습 2 · 오류 찾아 고치기

A의 각 프레임에 1000/시간을 계산한 뒤 그 다섯 값을 평균하여 전체 처리율이라고 보고했습니다. 계산값과 올바른 전체 처리율을 비교하세요.

힌트 1

12 ms 프레임은 1000/12 fps이고 32 ms는 1000/32 fps입니다.

힌트 2

전체 처리율의 분모는 합산한 시간입니다.

풀이와 답 확인

  1. 개별 역수의 평균은 (4×1000/12+1000/32)/5 = 875/12 fps, 약 72.92 fps입니다.

  2. 전체 구간 처리율은 5000/80 = 62.5 fps입니다. 평균하는 대상이 다릅니다.

전체 구간 처리율 보고는 62.5 fps로 고칩니다.

흔한 오답에서 다시 생각하기

각 프레임의 fps를 평균하면 항상 총 프레임 수/총 시간과 같다.

역수와 평균의 순서를 바꾸면 값이 달라집니다.

연습 3 · 직접 만들어 보기

별도 가상 측정에서 준비가 20 ms이고 실제 프레임 5개의 합이 80 ms입니다. 프레임 구간 처리율과 준비 포함 전체 처리율을 이름·분모와 함께 설계하세요.

힌트 1

프레임 구간은 80 ms입니다.

힌트 2

준비 포함 전체 구간은 100 ms입니다.

풀이와 답 확인

  1. 프레임 구간 처리율은 5/0.08 = 62.5 fps입니다.

  2. 준비 포함 처리율은 5/0.1 = 50 fps입니다. 입력·장치·준비 포함 여부와 표본 수 5를 함께 기록합니다.

두 처리율은 각각 62.5 fps와 50 fps이며 분모를 분명히 보고합니다.

흔한 오답에서 다시 생각하기

50 fps는 틀린 값이므로 버린다.

준비 포함이라는 질문에는 유효한 값입니다. 서로 다른 구간의 수치를 같은 이름으로 합치지 않습니다.

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

별도 가상 작업의 계측 없는 시간은 15 ms이고 계측 호출 한 번마다 0.5 ms가 직렬로 더해집니다. 세 번 계측한 시간과 네 번 계측한 시간을 구하고 60 fps 예산을 비교하세요.

힌트 1

추가 비용은 호출 수에 비례한다고 이 문제에서 가정합니다.

힌트 2

시간을 1000/60 ms와 비교합니다.

풀이와 답 확인

  1. 세 번이면 15+3×0.5 = 16.5 ms여서 예산 이내입니다.

  2. 네 번이면 17 ms여서 예산을 1/3 ms 넘습니다. 이는 가정한 추가 비용의 손계산입니다.

세 번은 16.5 ms이고 네 번은 17 ms입니다. 계측 조건만 달라도 이번 예산 판정이 바뀝니다.

흔한 오답에서 다시 생각하기

프로파일러로 보았으므로 계측 추가 비용은 항상 0이다.

도구를 실제 실행하지 않았으며 여기의 호출 비용은 자체 가정입니다. 실제 비용은 별도 확인이 필요합니다.

설명 기준 확인

첫 결과 지연과 정상 구간 처리율은 같은 지표인가요?

설명 기준 확인

첫 결과는 CPU와 GPU 선행 의존을 모두 기다리고 이후 결과 간격은 명시한 모형의 병목에 영향을 받습니다.

게임 상태를 되돌리면 이미 지급한 외부 보상도 함께 되돌아갈까요?

앞 본문의 정수 규칙을 이어 사용합니다. 매 tick마다 x에 입력 u를 더한 뒤 새 x가 2 이상이면 score를 1 증가시킵니다. 초기 x는 0이고 score는 0입니다. 입력 1, 1, 0을 처리하면 x는 1, 2, 2이고 score는 0, 1, 2입니다. 매 tick의 규칙 순서, 입력과 상태 좌표는 재생 계약의 일부입니다. 값을 갱신하기 전에 조건을 검사하는 다른 구현은 같은 입력에도 score가 달라질 수 있습니다.

새 자체 난수 상태는 r←(5r+1) mod 16이며 매 tick 한 번 갱신하여 출력합니다. seed 1에서 첫 세 출력은 6, 15, 12입니다. 첫 tick 직후 checkpoint는 x=1, score=0, r=6, 다음 tick 번호 2와 규칙 판본을 보관합니다. 이를 복원해 입력 1, 0을 재생하면 출력 15, 12와 score 1, 2를 얻습니다. r을 저장하지 않고 seed 1로 다시 시작하면 출력은 6, 15로 바뀝니다. 이 16상태 식은 Godot의 구현이나 보안 난수가 아닙니다.

별도 외부 보상 모형은 score가 증가하는 각 tick에 동전 1개를 지급하며 처음 동전은 0개입니다. 원래 세 tick이 끝나면 동전은 2개입니다. 게임 checkpoint만 첫 tick 직후로 복원하고 외부 동전은 되돌리지 않은 채 둘째·셋째 tick을 다시 지급하면 동전은 4개가 됩니다. 외부 장부에 (실행 세대, tick 번호)의 처리 결과를 남기고 같은 키·내용은 재지급하지 않는 자체 정책을 쓰면 동전은 2개로 유지됩니다. 장부 확인과 지급을 원자적으로 함께 적용한다는 추가 가정이 필요하며 실제 저장소나 엔진에서 그 성질을 시험한 것은 아닙니다.

같은 전이 규칙의 조건을 정한다

재생은 기록한 입력으로 상태의 변화를 다시 계산하는 과정이다. 초기 상태,규칙 버전,입력의 tick과 순서,난수 상태 등 결과에 영향을 주는 조건을 보존해야 한다. 같은 키를 눌렀다는 요약만으로 정확한 적용 순서를 알 수 없는 경우가 있다.

자체 모형은 정수 위치 x=0에서 tick마다 u∈{−1,0,1}을 받아 x←x+u로 갱신한다. 각 tick 후 x가2 이상일 때 점수를1 더한다. 위치 갱신 뒤 점수 판정을 하는 순서로 고정한다. 입력도 정수이며 부동소수점 물리나 네트워크 경쟁은 없다.

난수도 상태를 가진다

PRNG는 현재 상태에서 다음 값과 상태를 계산한다. 고정 seed는 초기화를 재현하는 데 도움이 되지만 중간의 호출 수와 순서가 달라지면 다음 결과가 달라진다. 화면 장식과 게임 규칙이 같은 생성기를 공유하면 장식의 추가 호출이 게임 결과에 영향을 줄 수 있다.

자체 생성기 r←(5r+1) mod16을 초기 r=1에서 사용한다. 이는 학습용 작은 수열이며 안전한 난수나 Godot의 실제 출력이 아니다. 실제 RNG API의 하부 알고리즘은 구현 세부사항일 수 있어 규칙/엔진 버전까지 보존하고 장기 재생 조건을 검토한다.

검증 대상의 상태를 비교한다

tick별 위치·점수·RNG 상태를 같은 순서로 비교하면 처음 달라진 지점을 찾기 쉽다. 단순 요약값은 서로 다른 상태를 같은 값으로 만들 수 있다. 정한 필드를 빠뜨리지 않고 비교하며 저장 방식과 정렬 규칙도 고정한다.

프레임 간격을 곱해 이동하면 시간 차이를 반영할 수 있지만 그것만으로 모든 플랫폼의 물리 계산이 동일해지는 것은 아니다. 이 절은 명시한 작은 정수 모형의 결정성만 손으로 확인한다. 실제 엔진 재생이나 장치 간 동기화 시험은 수행하지 않는다.

자동검사 100%와 도움 없이 완료한 사용자 비율을 합칠 수 있을까요?

앞 본문은 하한 점수 규칙과 사용자 과제 관찰을 구별했습니다. 새 자체 규칙은 점수를 0 이상 10 이하로 제한하여 next = min(10,max(0,S+Δ))로 만듭니다. 잘못된 구현은 min(10,S+Δ)만 적용합니다. 독립 명세에서 S=3, Δ=−5의 정답은 0이지만 잘못된 구현은 −2입니다. 구현과 예상값 생성기가 같은 잘못된 식을 공유하면 둘 다 −2를 내어 검사가 통과할 수 있습니다.

새 가상 자동검사 장부에는 요구사항 R1 하한, R2 상한, R3 실패 시 상태 보존의 세 항목이 있습니다. 선택한 네 검사는 모두 R2만 확인하며 네 개 모두 통과했다고 가정합니다. 시험 통과율은 4/4 = 100%입니다. 실제 확인한 요구사항 종류는 1/3이고 R1·R3는 아직 확인하지 않았습니다. 조건이 다른 분모를 합쳐 하나의 성공률로 쓰지 않습니다. 이 장부는 Unity Test Framework를 실제 실행한 결과가 아닙니다.

별도 가상 사용자 과제는 초대한 6명 중 5명이 시작했고 시작한 5명 중 3명은 도움 없이 완료, 1명은 도움을 받아 완료, 1명은 미완료입니다. 시작한 사람을 분모로 한 독립 완료율은 3/5 = 60%이고 도움 포함 완료율은 4/5 = 80%입니다. 초대한 사람 대비 시작률은 5/6입니다. 참여하지 않은 한 명의 과제 결과는 관찰하지 않았습니다. 과제 문구·도움 제공 시점·목표 사용자 조건을 기록하고 실제 학습자나 사용자의 시험 결과로 주장하지 않습니다.

playtest는 사람의 행동을 관찰한다

playtest에서는 실제 사람이 목표를 이해하고 조작하며 선택하는 모습을 본다. 예를 들어 도움 없이 첫 임무를 찾는 과업을 주고 안내를 놓치는 장면을 기록한다. 사용성 성공과 재미·몰입·균형은 관련 있지만 하나의 성공률로 모두 증명하지 않는다.

목표와 관찰 질문,대상 사용자,진행자의 도움 규칙을 먼저 정한다. 정답 버튼을 미리 알려 주는 과업은 발견 문제를 숨길 수 있다. 행동·발언·진행자 개입을 구별하고 참가자의 동의와 필요한 최소 기록 범위를 정한다. 본 활동은 실제 사람에게 수행하지 않는다.

풀이와 답 확인

  2. 재생 첫 입력 1 뒤 x는 2, score는 1, r은 15입니다. 입력 0 뒤 x는 2, score는 2, r은 12입니다. 난수 출력은 15와 12입니다.

  3. 두 지급 키의 동일 내용 완료 기록이 있으므로 추가 지급은 0개입니다. 외부 동전은 2개로 유지됩니다. 장부 없이 재지급하는 별도 경우에는 4개가 됩니다.

  4. 자동검사 통과율은 4/4 = 100%이고 확인한 요구사항 종류 비율은 1/3입니다. 시작률은 5/6이고 시작자 독립 완료율은 3/5 = 60%, 도움 포함 완료율은 4/5 = 80%입니다. 미참여자 한 명의 과제 결과와 R1·R3는 미확인입니다.
