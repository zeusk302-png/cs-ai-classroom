소단원 11.1

profiling과 frame budget

평균 프레임이 빠른데도 게임이 가끔 끊겨 보이는 이유는 무엇일까?

준비 개념과 학습 목표

준비 개념

  • 초와 밀리초

  • 평균과 최댓값

학습 목표

  • 프레임 예산을 시간으로 계산한다.

  • 측정 환경과 비용 경계를 밝힌다.

  • 평균과 느린 프레임을 함께 검토한다.

목표 빈도를 한 프레임 시간으로 바꾼다

60프레임/초의 목표 간격은 1000/60≈16.667ms다. 30프레임/초는 약33.333ms,120프레임/초는 약8.333ms다. 이는 목표 간격이며 화면 출력과 입력 지연 등 모든 품질 지표를 같은 숫자로 표현하지 않는다.

예산 안에 들어가려면 실제 병목 경로의 작업을 관측한다. CPU와 GPU가 겹쳐 일할 수 있으므로 각각의 수치를 무조건 더하지 않는다. 아래 종이 예제는 한 프레임 안 작업이 직렬이며 겹치지 않는다고 명시한 단순 모형이다.

어디서 시간이 쓰였는지 관측한다

profiling은 함수·메모리·렌더링 등 성능 정보를 수집해 비용의 원인을 찾는 과정이다. 먼저 반복 가능한 장면과 입력,빌드·품질 설정·장치를 기록한다. 가장 큰 구간을 바꾼 뒤 같은 조건에서 다시 비교하되 기능 결과가 같아야 한다.

Editor 관측은 개발 중 원인을 찾는 데 유용하지만 출시 장치 결과를 대신하지 않는다. 관측 도구 자체의 비용도 생각해야 한다. 이 교재는 가상 시간표만 계산하며 Profiler 스크린샷이나 실제 장치 FPS를 만들어 내지 않는다.

평균만으로 순간 지연을 숨기지 않는다

프레임 시간의 합을 프레임 수로 나누면 평균 시간이다. 그 역수로 얻은 전체 처리율은 개별 프레임 FPS의 평균과 다를 수 있다. 적은 수의 긴 프레임도 체감 끊김에 영향을 줄 수 있어 최댓값과 예산 초과 횟수를 함께 본다.

초기 로딩이나 새 자원 적재가 포함된 구간과 이미 준비된 구간을 구별한다. 예산 초과가 관측되면 원인별 추적을 하고 표본 길이·장면 범위를 보고한다. 짧은 가상 표가 모든 플레이 장면의 성능을 인증하지 않는다.

중간 과정을 따라가는 예제

직렬 프레임의 입력1ms·게임 논리5ms·렌더 준비6ms·기타2ms를 합하고 60fps 예산과 비교하라.

  1. 합은1+5+6+2=14ms다.

  2. 60fps 예산1000/60≈16.667ms보다 약2.667ms 여유가 있다.

  3. 추가 작업4ms가 생기면18ms로 예산을 약1.333ms 넘는다.

기본14ms는 이 직렬 모형 예산 안이고 추가 후18ms는 초과다. 실제 출력 fps 측정값은 아니다.

종이와 본문으로 직접 해보기

가상 프레임 시간10,10,10,30ms의 평균·최댓값·60fps 예산 초과 횟수와 전체 처리율을 구하라.

힌트 보기

총 시간60ms에 프레임4개다. 각 프레임을16.667ms와 비교한다.

풀이 보기

평균15ms,최댓값30ms,초과1/4=25%다. 전체 처리율은4/.06≈66.667fps지만 한 프레임이 예산을 넘었다.

오해와 반례

평균이60fps보다 빠르면 모든 프레임이 예산을 만족한다.

평균15ms인 활동에도30ms 프레임이 있다. 평균 처리율과 매 프레임의 지연은 다른 관측이다.

답과 이유 보기

한 단계 더

겹치는 CPU12ms·GPU14ms라면 합26ms를 프레임 지연으로 곧장 쓰지 말라. 파이프라인과 동기화 의존성을 먼저 정해야 새 비용을 계산할 수 있다.

출처와 확인 범위
  • Unity — Unity Profiler

    실제 본문에서 응용의 성능 정보, Editor 자원 관측과 의도한 출시 플랫폼 장치 연결의 차이를 읽었다. 도구를 실제 실행하지 않았다.

  • Unity — Per-frame updates

    실제 본문에서 Update 간격이 프레임률에 따라 변함과 프레임당 고정 이동의 속도 변화, deltaTime으로 시간 단위 이동을 계산하는 설명을 읽었다. 자체 정수 tick 모형은 Unity 물리 결정성 보증이 아니다.

소단원 11.2

재생·결정성

입력 기록을 다시 읽었는데 다른 결과가 나오면 무엇을 빠뜨린 것일까?

준비 개념과 학습 목표

준비 개념

  • 상태 전이

  • 정수와 나머지

학습 목표

  • 재생에 필요한 초기 상태와 입력 순서를 기록한다.

  • seed와 RNG 호출 순서를 구별한다.

  • 자체 결정성과 엔진 전체의 결정성을 분리한다.

같은 전이 규칙의 조건을 정한다

재생은 기록한 입력으로 상태의 변화를 다시 계산하는 과정이다. 초기 상태,규칙 버전,입력의 tick과 순서,난수 상태 등 결과에 영향을 주는 조건을 보존해야 한다. 같은 키를 눌렀다는 요약만으로 정확한 적용 순서를 알 수 없는 경우가 있다.

자체 모형은 정수 위치 x=0에서 tick마다 u∈{−1,0,1}을 받아 x←x+u로 갱신한다. 각 tick 후 x가2 이상일 때 점수를1 더한다. 위치 갱신 뒤 점수 판정을 하는 순서로 고정한다. 입력도 정수이며 부동소수점 물리나 네트워크 경쟁은 없다.

난수도 상태를 가진다

PRNG는 현재 상태에서 다음 값과 상태를 계산한다. 고정 seed는 초기화를 재현하는 데 도움이 되지만 중간의 호출 수와 순서가 달라지면 다음 결과가 달라진다. 화면 장식과 게임 규칙이 같은 생성기를 공유하면 장식의 추가 호출이 게임 결과에 영향을 줄 수 있다.

자체 생성기 r←(5r+1) mod16을 초기 r=1에서 사용한다. 이는 학습용 작은 수열이며 안전한 난수나 Godot의 실제 출력이 아니다. 실제 RNG API의 하부 알고리즘은 구현 세부사항일 수 있어 규칙/엔진 버전까지 보존하고 장기 재생 조건을 검토한다.

검증 대상의 상태를 비교한다

tick별 위치·점수·RNG 상태를 같은 순서로 비교하면 처음 달라진 지점을 찾기 쉽다. 단순 요약값은 서로 다른 상태를 같은 값으로 만들 수 있다. 정한 필드를 빠뜨리지 않고 비교하며 저장 방식과 정렬 규칙도 고정한다.

프레임 간격을 곱해 이동하면 시간 차이를 반영할 수 있지만 그것만으로 모든 플랫폼의 물리 계산이 동일해지는 것은 아니다. 이 절은 명시한 작은 정수 모형의 결정성만 손으로 확인한다. 실제 엔진 재생이나 장치 간 동기화 시험은 수행하지 않는다.

중간 과정을 따라가는 예제

입력 u=1,1,0,−1을 초기 위치 x=0, 점수 0에 적용하여 각 tick 뒤 위치와 점수를 구하라.

  1. tick1 위치1·점수0이다.

  2. tick2 위치2·점수1,tick3 위치2·점수2다.

  3. tick4 위치1·점수2다. 같은 초기값과 순서로 다시 계산하면 같은 열이다.

위치1/2/2/1,누적 점수0/1/2/2다. 위치 갱신 후 판정 규칙의 종이 재생이다.

종이와 본문으로 직접 해보기

r1에서 자체 생성기의 다음 세 값을 구하라. 첫 값 뒤 장식이 두 번째 값을 소비하면 게임의 다음 값은?

힌트 보기

5r+1을16으로 나눈 나머지를 반복한다.

풀이 보기

값은6,15,12다. 장식이15를 먼저 소비하면 게임의 다음 값은12로 원래 두 번째15와 다르다. 같은 seed만으로 호출 변화까지 상쇄하지 않는다.

오해와 반례

seed만 같으면 초기 상태나 호출 순서와 관계없이 게임 전체가 같다.

seed는 난수 초기화의 일부 조건이다. 입력 순서·규칙·게임 상태와 RNG 소비가 다르면 결과가 바뀐다.

한 단계 더

생성기 상태를 첫 호출 뒤6으로 저장했다면 다음 값15를 얻은 후 저장 상태6을 복원해 다시15를 얻는다. 이는 자체 모형 계산이며 실제 API state에는 저장했던 유효 상태만 복원한다.

출처와 확인 범위
  • Godot — Random number generation

    실제 본문에서 고정 seed의 수열, 호출마다 내부 상태 갱신, 별도 RNG 인스턴스와 상태 저장/복원의 재생 용도를 읽었다. 아래 작은 생성기는 자체 산술 모형이다.

  • Godot — RandomNumberGenerator

    실제 API 본문 seed 초기화의 state 변경·저장한 state 복원·임의 state 금지·하부 알고리즘이 구현 세부사항임을 읽었다. 자체 모형을 이 API 출력값으로 표시하지 않는다.

  • Unity — Per-frame updates

    실제 본문에서 Update 간격이 프레임률에 따라 변함과 프레임당 고정 이동의 속도 변화, deltaTime으로 시간 단위 이동을 계산하는 설명을 읽었다. 자체 정수 tick 모형은 Unity 물리 결정성 보증이 아니다.

소단원 11.3

자동검사와 playtest

점수 계산 테스트가 모두 통과하면 처음 하는 사람도 게임을 이해할까?

준비 개념과 학습 목표

준비 개념

  • 기대값과 관측

  • 과업 성공

학습 목표

  • 규칙 검사와 실제 플레이 관찰의 범위를 구별한다.

  • 성공 조건과 실패 기록을 설계한다.

  • 미수행을 예상표와 분리한다.

반복 가능한 규칙을 검사한다

자동검사는 입력과 기대값을 정하고 코드 결과를 반복 비교한다. 점수 하한,승패 조건,저장/불러오기 같은 규칙과 연결을 확인할 수 있다. 테스트 환경과 어떤 경로를 실행했는지 기록해야 통과의 의미를 판단할 수 있다.

게임 엔진의 Edit Mode·Play Mode·대상 플랫폼 검사는 실행 범위가 다르다. 순수 규칙 통과가 실제 화면 입력,오디오,장치 저장까지 확인했다는 뜻은 아니다. 실제 실행한 테스트 수와 아직 설계한 사례 수를 구별한다.

playtest는 사람의 행동을 관찰한다

playtest에서는 실제 사람이 목표를 이해하고 조작하며 선택하는 모습을 본다. 예를 들어 도움 없이 첫 임무를 찾는 과업을 주고 안내를 놓치는 장면을 기록한다. 사용성 성공과 재미·몰입·균형은 관련 있지만 하나의 성공률로 모두 증명하지 않는다.

목표와 관찰 질문,대상 사용자,진행자의 도움 규칙을 먼저 정한다. 정답 버튼을 미리 알려 주는 과업은 발견 문제를 숨길 수 있다. 행동·발언·진행자 개입을 구별하고 참가자의 동의와 필요한 최소 기록 범위를 정한다. 본 활동은 실제 사람에게 수행하지 않는다.

서로 다른 근거를 한 숫자로 합치지 않는다

규칙 테스트8개 중8개 통과와 플레이 과업5명 중3명 성공은 서로 다른 분모다. 이를11/13으로 합친 게임 성공률은 의미가 없다. 각 결과는 실제 실행 범위와 관찰 조건에 따라 따로 보고한다.

실패는 재현 입력·기대 결과·실제 관측·환경을 기록해 개선하고 다시 확인한다. 아직 실행하지 않았다면 예상이나 계획으로 남긴다. 가상의 관찰 표는 분석 연습일 뿐 학습자나 장치가 통과했다는 증거가 아니다.

중간 과정을 따라가는 예제

가상 규칙 점수 S의 갱신은 max(0,S+Δ)다. 초기 S3에 Δ−5,+2를 주는 두 기대값과, 이를 S+Δ로 잘못 구현한 결과를 비교하라.

  1. 정상 첫 갱신은max(0,3−5)=0이다.

  2. 다음 정상 값은max(0,0+2)=2다.

  3. 잘못된 구현은−2 뒤0으로 정상0/2와 다르다.

기대열0/2,결함열−2/0이다. 하한 경계를 잡는 예상 검사이며 코드 실행 결과는 아니다.

종이와 본문으로 직접 해보기

가상 5명 중3명이 도움 없이 완료하고1명은 도움 후 완료,1명은 미완료다. 도움 없는 성공률과 도움 포함 완료율을 구하라.

힌트 보기

두 지표의 성공 정의를 분리하되 전체 분모5는 유지한다.

풀이 보기

도움 없는 성공은3/5=60%,도움 포함 완료는4/5=80%다. 한 사람이 도움을 받았다는 기록을 보존하며 둘을 같은 성공률로 부르지 않는다.

자동검사가 통과하면 재미와 초심자 이해도도 검증된다.

자동검사는 지정 입력의 결과를 확인한다. 행동 이해·조작 발견·재미는 실제 사용자 관찰과 별도의 질문이 필요하다.
