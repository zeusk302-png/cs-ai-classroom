소단원 3.1

키보드·포인터·controller

스페이스를 누르는 일과 한글 한 글자를 입력하는 일은 같은 이벤트일까?

준비 개념과 학습 목표

준비 개념

  • 장치는 물리 상태를 보내고 게임은 이를 의미 있는 행동으로 변환한다. 키·문자·버튼·축은 다른 자료다.
  • 미니복습: 좌표를 두 배 크기 화면으로 옮기면 같은 지점의 수치도 두 배가 될 수 있다.
  • 자가진단: 축 값0.02를 사람이 의도한 이동으로 반드시 해석해야 하는가?

학습 목표

  • 물리 키 사건과 텍스트 입력을 구분한다.
  • 포인터의 화면/가상 좌표와 viewport 여백을 계산한다.
  • 아날로그 축의 범위와 자체 dead zone 정책을 설명한다.

같은 키에도 뜻은 여러 가지

게임 이동에는 물리 키의 누름·뗌이 필요하고 이름 입력에는 문자 입력이 필요하다. 한 키에서 Shift나 입력기 조합에 따라 다른 문자가 나오거나 한 문자를 여러 키로 만들 수 있다. 따라서 키 코드를 그대로 문자로 저장해 전 세계 키보드와 한글 입력을 처리했다고 말하지 않는다. 키에 대응하는 게임 행동과 텍스트 입력 경로를 구분한다.

포인터는 위치 변화, 버튼 전환, 스크롤처럼 서로 다른 데이터를 준다. 컨트롤러도 디지털 버튼과 연속 축이 있다. GLFW의 joystick 축은 −1..1 범위를 쓰고 gamepad 매핑으로 위치의 의미를 통일할 수 있지만 모든 장치가 같은 원시 인덱스라는 뜻은 아니다. 장치의 존재·매핑 성공·연결 해제를 확인할 계획이 필요하며 번호만 영구 신원으로 저장하지 않는다.

화면에서 게임 영역으로

가상 화면 크기와 창 크기는 다를 수 있다. 포인터가 창 왼쪽 위 기준이라고 할 때 게임 viewport의 왼쪽 위 (a,b)와 배율 s를 알면 가상 좌표는 ((X−a)/s,(Y−b)/s)다. 여기서는 위쪽 원점의 좌표를 끝까지 사용한다. 게임 영역 바깥 여백은 메뉴 선택으로 보내지 않는 등 정책을 정한다.

고해상도 화면에서는 논리 창 좌표와 framebuffer 픽셀이 다를 수 있다. 두 값의 단위를 맞춘 뒤 viewport 변환을 해야 한다. 화면을 늘리거나 검은 여백을 넣었는데 실제 창 크기를 가상 좌표처럼 쓰면 클릭 대상이 어긋난다. 예제는 균일 배율2와 정해진 여백만 계산하며 실제 DPI나 터치 기기 보정 결과는 아니다.

미세한 축 흔들림을 처리하는 규칙

아날로그 스틱은 손을 떼어도 정확히0이 아닐 수 있다. dead zone은 작은 변화에 반응하지 않도록 정한 정책이다. 이 예제는 한 축 u에 대해 δ=0.2, |u|≤δ이면0, 아니면 sign(u)(|u|−δ)/(1−δ)로 재조정한다. 이는 자체 축별 모형이며 모든 엔진의 기본 구현이나 원형 dead zone과 같지 않다.

u=0.6은 (0.6−0.2)/0.8=0.5로 변환되고 u=−0.6은−0.5다. 연속성을 위해 경계에서도0이 되며 끝 u=1은1이다. δ가 너무 크면 작은 의도 입력이 사라지고 너무 작으면 노이즈 이동이 남는다. 실제 장치별 범위·보정·접근성을 조사해야 하므로 한 숫자가 모두에게 적절하다고 주장하지 않는다.

중간 과정을 따라가는 예제

가상 게임500×250을1000×600 창에 비율을 유지해 표시한다. 게임 viewport는 위쪽 원점(0,50),크기1000×500이고 여백 클릭은 제외한다. 포인터(200,150)과(200,25), 축u0.6과u0.1을 위 정책으로 변환하라.

  1. viewport 배율은1000/500=500/250=2다. (200,150)은 게임 영역 안이다.
  2. 가상 위치는((200−0)/2,(150−50)/2)=(100,50)다. 창 y150을 그대로 게임 y150으로 쓰지 않는다.
  3. (200,25)는 viewport의 위쪽 경계50보다 위라 게임 영역 밖이다. 제외 정책에 따라 게임 좌표 선택을 생성하지 않는다.
  4. δ0.2에서u0.6은0.5이고u0.1은|u|≤0.2라0이다.

유효 가상 포인터(100,50), 여백 클릭 제외, 축 결과0.5와0이다. 실제 장치와 창을 열어 얻은 결과가 아닌 단위·정책 계산이다.

풀이 보기

오해와 반례

컨트롤러 버튼0은 모든 장치에서 점프이고 포인터 좌표는 언제나 실제 픽셀이다.

원시 버튼 순서는 장치·플랫폼마다 다를 수 있어 매핑이 필요하다. GLFW 포인터는 창 내용 영역의 screen coordinates이므로 framebuffer 픽셀과 같다는 보장이 없다. 여백과 배율도 반례이며 API가 반환한 좌표의 원점·단위를 먼저 읽어야 한다.

소단원 3.2

edge·level 입력

점프를 눌러 둔 채로 다섯 번 갱신하면 점프 명령도 다섯 번이어야 할까?

준비 개념과 학습 목표

준비 개념

  • level은 현재 눌린 상태, edge는 눌림이나 뗌의 전환이다. 초기 이전 상태도 정한다.
  • 미니복습: Boolean 참/거짓과 AND/NOT을 사용해 두 상태를 비교한다.
  • 자가진단: 두 관측 시각 사이에 누르고 뗀 변화는 마지막 상태 하나에 남는가?

학습 목표

  • pressed/released/held를 상태 표로 계산한다.
  • 짧은 입력과 반복 키 이벤트의 차이를 설명한다.
  • 여러 고정 갱신에서 한 명령을 한 번만 소비하는 정책을 세운다.

상태와 변화가 맡는 역할

이전 상태 p와 현재 상태 c가0/1일 때 pressed=(NOT p) AND c, released=p AND (NOT c), held=c로 정의한다. pressed는0→1 전환, released는1→0 전환이고 held는 계속 누른 동안에도1이다. 이동을 유지하는 입력과 메뉴를 한 번 확인하는 입력에 같은 규칙을 쓰면 의도와 다른 반복이 생길 수 있다.

이 정의는 두 관측 상태의 차이다. 관측 사이에0→1→0이 일어나면 양끝은0이라 pressed를 찾지 못한다. 실제 이벤트 큐에서 순서 있는 press/release를 받으면 짧은 누름을 기록할 수 있다. GLFW cached state와 SDL 키 스냅샷의 누락 조건이 이런 차이를 설명한다. API를 자주 조회했다는 말만으로 모든 변화를 보았다고 주장하지 않는다.

반복 이벤트를 새 누름과 구별하기

운영체제의 키 반복은 문자를 반복 입력할 때 유용하다. GLFW의 REPEAT 빈도는 사용자 설정의 영향을 받으며 이것을 계속 눌린 키 상태나 애니메이션 시간의 대용으로 쓰지 말라고 설명한다. 점프 요청을 실제0→1 PRESS에서 한 번 기록한다면 REPEAT를 새 점프로 세지 않는 정책을 명시한다. 연속 발사를 원하는 게임은 발사 주기를 게임 시간으로 따로 설계할 수 있다.

여러 물리 입력을 하나의 행동으로 합칠 때 행동 edge와 각 키의 edge는 다를 수 있다. 스페이스를 계속 누른 상태에서 컨트롤러 점프 버튼을 추가로 누르면 OR로 합친 행동 level은 여전히1이다. 각 장치 누름마다 명령을 만들 것인지 합친 행동0→1만 명령으로 만들 것인지 선택한다. 아래 예제는 하나의 입력원과 한 번 누름당 요청 하나만 사용한다.

한 입력을 한 갱신에 배정하기

렌더 프레임 하나 사이에 고정 simulation tick이 두 번 실행될 수 있다. 프레임 pressed=true를 두 tick에 그대로 읽게 하면 한 누름이 두 요청으로 복제된다. 순서 있는 명령을 특정 tick에 배정하고 그 tick에서 소비한 뒤 지우는 모형을 쓰면 복제를 피할 수 있다. 이동 held는 매 tick에 같은 상태를 읽을 수 있지만 점프 edge는 소비 횟수 정책이 다르다.

프레임 사이에 tick이 하나도 없다면 처리할 edge를 바로 지우는 정책은 입력을 잃을 수 있다. 보류 큐를 다음 tick까지 유지하거나 목표 tick을 정한다. focus가 사라져 release를 못 받을 때 상태를 초기화하는 정책도 필요하다. 초기화는 실제 물리 release 사건을 관측한 것과 다르므로 재생 기록에서도 구분한다. 명령 요청 수와 실제로 가능한 점프 수는 게임 상태기계의 조건으로 다시 판단한다.

중간 과정을 따라가는 예제

초기 이전 상태p=0, 다섯 관측의 c는0,1,1,0,1이다. 각 관측 후 p=c로 갱신한다. held/pressed/released를 계산하고 한 pressed당 JumpRequest 하나일 때 요청 수를 구하라.

  1. 첫 c0은p0이므로 held0,pressed0,released0이다. 이후p0이다.
  2. 둘째c1은p0이라 held1,pressed1,released0이고p1로 바뀐다. 셋째c1은 held1이지만 pressed0,released0이다.
  3. 넷째c0은p1이라 held0,pressed0,released1이다. 다섯째c1은p0이라 held1,pressed1,released0이다.
  4. held 배열은0/1/1/0/1, pressed는0/1/0/0/1, released는0/0/0/1/0이다. 요청은 둘째와 다섯째의2개다.

JumpRequest는2개이며 held 참의3회와 다르다. 실제 점프가 공중에서도 허용되는지 같은 규칙은 이 입력 표에서 아직 결정하지 않았다.

종이와 본문으로 직접 해보기

힌트 보기

관측 끝점0과0만 보았을 때와 두 사건을 순서대로 받았을 때를 나눈다. 소비한 명령은 다음 tick에 남겨 두지 않는다.

풀이 보기

스냅샷은0→0이라 pressed0으로 짧은 누름을 놓친다. 두 이벤트를 순서대로 처리한 큐는 pressed 요청1개와 최종level0을 얻는다. tick16에 배정한 요청을 tick16에서 한 번 소비하고 tick24에는0개여야 한다. 프레임 true를 두번 읽어2개를 만드는 것은 명시한 한누름 한요청 계약 위반이다.

오해와 반례

held가 참인 모든 tick은 새로운 누름이며 REPEAT도 항상 새 점프다.

상태0/1/1 예제에서 세 번째 held1은 유지이고 새 전환이 아니다. 운영체제 REPEAT 또한 물리 키가 계속 눌린 동안의 별도 반복이다. 점프·메뉴·문자·연속발사는 요구가 다르므로 상태, 전환, 반복 사건과 게임 시간 기반 반복 정책을 구분한다.

한 단계 더

심화: OR로 합친 점프 행동에서 스페이스0→1,컨트롤러0→1,스페이스1→0,컨트롤러1→0 순서를 추적하라. 행동 level은1,1,1,0이고 행동 pressed는 첫 사건에서만 생긴다. 두 입력원의 개별 눌림2개를 별도 요청으로 만들고 싶은 설계는 다른 계약이다. 보류 명령에는 순서·목표 tick·소비 여부를 기록하고 focus 초기화 사건도 별도 표기하는 재생 형식을 제안하라.

소단원 3.3

매핑과 입력지연

키를 누르는 순간부터 화면이 변할 때까지 어디에서 기다릴까?

준비 개념과 학습 목표

준비 개념

  • 물리 입력과 게임 행동 이름을 분리한다. MoveRight와 Jump는 특정 키 코드가 아니다.
  • 미니복습: 끝 시각에서 시작 시각을 빼면 경과시간이다. ms와초를 섞지 않는다.
  • 자가진단: 화면 FPS가 높다는 사실만으로 물리 입력부터 표시까지 지연을 알 수 있는가?

학습 목표

  • 장치 입력을 행동으로 변환하는 계층과 충돌 정책을 설계한다.
  • 입력→수집→갱신→렌더→표시의 지연을 시간표로 분해한다.
  • 예상 스케줄 계산과 실제 지연 측정을 구분한다.

키 이름보다 행동 의미를 보관하기

게임 코드가 특정 스페이스 키를 직접 검사하는 곳이 많으면 키 재설정과 컨트롤러 지원을 바꾸기 어렵다. 장치 사건을 Jump 같은 행동으로 매핑하고 simulation은 행동 명령을 읽는 모형을 쓴다. 메뉴 확인과 게임 점프에 같은 버튼을 배정해도 현재 입력 맥락에 따라 어느 행동을 받을지 정해야 한다.

여러 입력원이 같은 행동을 만들 때 합산·최댓값·최근 사용 장치 선택 등 정책이 가능하다. 디지털 오른쪽1과 스틱 오른쪽0.5를 더하면1.5가 되어 지정 최대 속도를 넘길 수 있다. 예제는 이동 요청을[−1,1]로 제한하고 메뉴가 열린 동안 게임 점프를 전달하지 않는 자체 정책을 쓴다. 이것이 모든 게임의 최선 정책이라는 뜻은 아니다.

언제 읽고 언제 반영하는가

물리 변화가 장치/OS에서 전달되고 프로그램이 이벤트를 수집하며 다음 simulation tick이 적용하고 렌더가 결과를 그린 뒤 디스플레이가 보여 준다. 각 단계 사이의 기다림이 누적된다. 프레임 시작에 입력 큐를 처리하면 같은 프레임 갱신에 들어갈 기회를 줄 수 있지만 무조건 최저 지연이라는 보장은 아니다. 이벤트 도착 시각과 갱신 스케줄이 중요하다.

주기T마다 상태를 보는 이상 모형에서 입력 시각이 관측 사이 어디에 있는지에 따라 수집 대기는0부터T보다 작은 값까지 달라진다. 평균T/2는 위상이 균등하다는 추가 가정이 있어야 한다. OS가 늦게 전달하거나 큐가 쌓이고 창 이동이 main loop를 막으면 이 단순 경계만으로 전체 지연을 제한하지 못한다. SDL 공식 문서도 일부 플랫폼 창 이동/크기 변경의 block 예외를 설명한다.

FPS와 반응 시간은 다른 측정

렌더 프레임이 자주 만들어져도 오래된 상태를 표시하거나 표시 큐가 길면 입력 반응은 느릴 수 있다. 수집 대기·simulation 대기·렌더/제출·표시 대기·실제 발광을 구분해 어느 끝점의 지연인지 기록한다. CPU가 frame을 제출한 시각을 사람에게 빛이 도착한 시각으로 바꿔 쓰지 않는다.

실제 입력 지연을 검증하려면 같은 사건의 시간표와 시계 기준, 반복 표본, 부하·디스플레이 조건을 명시해야 한다. timestamp의 발생 위치나 서로 다른 시계의 오차를 무시하면 잘못된 지연 차이를 만들 수 있다. 아래 숫자는 이상 순차 스케줄의 가상 값이다. 하드웨어를 측정하거나 네트워크 게임의 예측/롤백 성능을 시험한 결과로 보고하지 않는다.

중간 과정을 따라가는 예제

가상 사건의 시각(ms): 물리누름5, OS전달7, 수집8, simulation 적용10, 렌더완료12, 화면표시16, 발광18이다. 단계별 차이와 물리→발광 총지연을 계산하라. 모든 시각은 동일 시계의 순차 가정이다.

  1. 물리5→전달7은2ms, 전달7→수집8은1ms다. 수집 이전 대기 합은3ms다.
  2. 수집8→simulation10은2ms, simulation10→렌더12는2ms다. 렌더까지 물리 기준7ms다.
  3. 렌더12→표시16은4ms, 표시16→발광18은2ms다. 제출/표시를 발광 시각과 같은 것으로 쓰지 않는다.
  4. 총합2+1+2+2+4+2=13ms이며18−5=13ms로 재확인한다.

지정한 물리→발광 끝점의 가상 총지연은13ms다. FPS 수치나 실제 측정치가 아닌 주어진 사건 시간표의 산술이다.

종이와 본문으로 직접 해보기

수집을16ms로 늦춰 simulation18,렌더20,표시24,발광26이 되었다고 가정한다. 물리5/OS7은 그대로다. 지연 증가와, 메뉴가 열린 상태에서 Jump버튼 하나를 눌렀을 때 정책상 게임 Jump전달 수를 구하라.

힌트 보기

새 수집 대기는16−7이다. 최종26−5와 이전13을 비교한다. 행동 전달은 현재 맥락 정책을 따른다.

풀이 보기

전달→수집 대기는9ms로 이전1ms보다8ms 커졌다. 새 총지연21ms=26−5이고 이전13ms에서8ms 증가한다. 메뉴가 열려 게임 점프를 차단하는 정책이면 게임 Jump전달은0개다. 버튼 사건이 없었다는 뜻이 아니라 다른 맥락에서 처리한 것이다.

오해와 반례

입력 API를 쓰고 FPS가60이면 반응 지연도 항상1/60초다.

같은 물리 사건이13ms 또는21ms로 달라지는 두 가상 스케줄이 반례다. FPS는 프레임 생성 빈도이며 이벤트 전달·적용·표시의 여러 대기를 모두 정하지 않는다. 매핑도 같은 버튼이 메뉴와 게임에서 다르게 처리될 수 있어 이벤트와 행동을 구분해야 한다.
