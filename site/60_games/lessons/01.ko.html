소단원 1.1

규칙·상태·상호작용

같은 오른쪽 입력도 이미 이긴 뒤에는 왜 이동하지 않을 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 상태는 다음 행동을 결정하는 데 필요한 현재 정보다. 변수는 그 정보의 이름이다. 입력은 규칙에 전달되는 사건이며 반복은 갱신을 여러 번 수행하는 것이다. 한 번의 갱신을 tick이라 부른다.

학습 목표

  • 상태·입력·전이·표시를 구별한다

  • 작은 보드 규칙을 순서대로 추적한다

  • 프레임 수와 경과시간의 조건을 설명한다

같은 위치를 보여 주는 두 상태가 다음 입력에도 같을까요?

앞 본문은 네 유효 상태의 보드다. 새 별도 규칙 K에서는 상태를 (위치, 열쇠 보유)로 정하고 위치는 0부터 3, 보유 값은 참 또는 거짓이다. 초기 상태는 (0,거짓)이다. 위치 1에 도착하면 열쇠를 얻고, 한 번 얻은 열쇠는 RESET 전까지 유지한다. RIGHT는 한 칸 오른쪽으로 가지만 위치 2에서 열쇠가 없으면 그대로다. LEFT는 한 칸 왼쪽으로 가되 0 아래로 가지 않는다. 위치 3에서는 RESET 이외의 모든 입력을 무시한다. WAIT는 그대로이며 RESET은 언제나 (0,거짓)을 만든다.

이 규칙은 열쇠를 이미 가진 상태를 포함한 계약을 설명하기 위해 유효 상태를 (0,거짓),(0,참),(1,참),(2,거짓),(2,참),(3,참)의 여섯 개로 정의한다. 초기 상태에서 실제로 도달 가능한 것은 (2,거짓)을 제외한 다섯 개다. 위치 1에 도착하면 얻는 규칙 때문에 초기 상태에서 열쇠 없이 위치 2에 갈 수 없다. 유효하다고 정한 상태와 초기 상태에서 도달 가능한 상태는 다른 집합이다.

표시는 위치만 보여 주는 G라고 하자. G가 같아도 숨은 열쇠 값이 다르면 다음 전이가 달라질 수 있다. 열쇠가 있는지에 따라 달라지는 규칙을 위치만 저장한 구현으로 바꾸면 필요한 정보를 잃는다. 아래 계산은 자체 종이 규칙이며 실제 엔진이나 키 이벤트를 실행하지 않는다.

먼저 확인할 개념
  • 상태와 순서의 역할

    기본 네 상태 모형과 불변조건을 새 열쇠 상태의 전제로 삼는다.

  • 상태 확장과 범위

    기본 확장의 열쇠 보유 예시를 별도 완전한 계약으로 정의한다.

게임 규칙은 상태 전이로 적을 수 있다

보드 위치는 정수 0부터 3, 상태는 (위치, PLAYING 또는 WON)이다. 처음은 (0,PLAYING). 한 tick에 RIGHT/LEFT/WAIT/RESET 중 하나만 전달한다. RESET은 언제나 처음으로 돌아간다. WON에서는 나머지 입력을 무시한다. PLAYING에서 RIGHT는 1 증가하되 3을 넘지 않고 LEFT는 1 감소하되 0 아래로 가지 않으며 WAIT는 그대로다. 새 위치가 3이면 WON으로 바꾼다.

이 전이 함수 F는 유효 상태와 정해진 입력에서 다음 상태를 하나로 정한다. 현실 게임의 확률·동시 입력은 이 모형에서 제외했다. 키를 누르고 있는 동안 입력을 몇 번 만드는지는 별도 입력 정책이다. “오른쪽 키를 누른다”만 쓰면 tick 수가 정해지지 않는다.

def step(state, event):
    x, phase = state
    if event == 'RESET':
        return (0, 'PLAYING')
    if phase == 'WON':
        return state
    if event == 'RIGHT':
        x = min(3, x + 1)
    elif event == 'LEFT':
        x = max(0, x - 1)
    elif event != 'WAIT':
        raise ValueError('unknown event')
    return (x, 'WON' if x == 3 else 'PLAYING')

입력 순서와 규칙의 불변조건

유효 상태는 0≤위치≤3이고 WON과 위치 3이 동치인 네 상태다. 처음에 조건이 맞고 이동을 양끝에서 제한하며 3에서 승리로 바꾸고 RESET이 처음으로 돌아가므로 모든 유효 전이 후에도 조건이 유지된다. 임의의 잘못된 초기 상태까지 복구한다는 주장은 아니다.

위치 2에서 RIGHT 다음 LEFT는 먼저 승리하여 LEFT를 무시하고 3에 남는다. LEFT 다음 RIGHT는 1을 거쳐 2에 남는다. 같은 입력 개수라도 순서가 결과를 바꾼다. 화면 표시 G(상태)는 위치와 승리를 보여줄 뿐 이 모형에서는 상태를 바꾸지 않는다.

시간을 쓰는 게임에서는 tick 수와 초를 구별한다

여기서는 이동 1칸이 입력 사건 한 개의 결과다. 연속 운동으로 바꾸면 속도는 칸/초, delta는 직전 갱신 이후 경과초이며 일정 속도v에서 이동량은v×delta다. 매 프레임 1칸이면 1초에 30프레임인 경우 30칸,60프레임이면 60칸이라 기기별 차이가 생긴다.

일정 속도 6칸/초를 각각 30회×1/30초,60회×1/60초로 나누면 총 이동은 모두 6칸이다. 이 계산은 일정 속도의 단순 운동에 대한 것이다. 충돌·가속도·부동소수 오차·불규칙 단계까지 완전히 동일한 결과를 보장하는 증명은 아니다.

소단원 1.2

엔진과 게임코드

화면에 캐릭터를 그려주는 엔진은 우리 보드의 승리 규칙도 자동으로 알고 있을까?

준비 개념과 학습 목표

준비 개념

  • 함수는 입력을 받아 정해진 처리를 수행하는 단위다. 호출은 그 처리를 요청하는 일이다. callback은 제공해 둔 함수를 실행 환경이 정해진 시점에 호출하는 방식이다. 상태는 현재 위치·진행 여부 같은 정보다.

학습 목표

  • 엔진 서비스와 게임 규칙의 책임을 구별한다

  • 입력→규칙→표시의 계약을 적는다

  • 명시된 엔진 판본의 갱신 방식과 검증 범위를 구별한다

최종 위치가 같으면 중복 소비도 없었다고 말할 수 있을까요?

이 소단원은 열쇠 규칙 K를 사용하지 않고 앞 본문의 네 상태 보드를 독립 사용한다. 별도 입력 장부의 사건은 (세대, 번호, 종류)다. 같은 세대 안에서 같은 번호/종류를 다시 받으면 저장된 사건으로 보고 규칙을 다시 실행하지 않는다. 같은 세대/번호인데 종류가 다르면 충돌로 거절한다. 새 사건을 수용하면 보드 전이와 번호 기록을 함께 반영한다. 이것은 자체 종이 계약이며 엔진이 자동 제공하는 기능이라는 주장이 아니다. 사건 장부는 현재 세대의 사건만 수용하고, 과거 또는 아직 시작하지 않은 세대는 거절한다.

초기 세대는 1이다. RESET 사건을 수용하면 보드는 초기로 돌아가고 세대가 1 증가하며 이전 세대의 재전송은 거절한다. 새 세대의 번호는 다시 1부터 사용할 수 있다. 이전 사건 장부를 무조건 지우고 세대도 저장하지 않으면 늦은 옛 RIGHT가 새 게임에서 다시 이동할 수 있다. 새 세대가 실제 장치에서 생성/전달되는 방법은 제외한다.

최종 위치만 보면 같은 RIGHT를 두 번 소비한 오류가 승리의 이동 무시 규칙에 가려질 수 있다. 따라서 수용된 사건 수, 규칙 호출 수, 최종 상태를 각각 관찰한다. 표시 G는 읽기만 하므로 여러 번 표시해도 상태가 변하지 않는다. 원자 반영은 여기서 주어진 순차 계약이고 실제 스레드 경쟁/저장 실패는 검증하지 않는다.

먼저 확인할 개념
  • 입력·규칙·표시 경계

    기본 F/G 책임과 콜백 중복 소비를 새 사건 장부로 확장한다.

  • 승리 뒤 이동 무시

    기본 보드의 네 상태 전이를 그대로 사용한다.

엔진은 재사용할 실행 기반을 제공한다

게임 엔진은 창·입력·그림·소리·자원·물리 같은 실행 기반과 구성 도구를 제공한다. 게임코드는 어떤 입력이 어떤 행동이고 언제 승리하며 무엇을 표시할지 결정한다. 엔진이 충돌 정보를 줄 수 있어도 그 충돌이 점수인지 실패인지는 게임 규칙이다.

Godot4.3 문서의 노드와 씬은 게임 요소를 조직하는 한 방식이다. 씬에 노드를 묶고 스크립트로 동작을 정한다. 이는 고정 판본의 설명 예시이며 엔진 설치나 최신 지원 버전 선택을 이론 학습의 필수로 삼지 않는다.

입력·규칙·표시는 경계에서 만난다

종이 모형에서는 입력 변환기가 한 사건을 RIGHT 등으로 바꾸고 규칙 함수 F가 새 상태를 만들며 표시 함수 G가 그 상태를 그림이나 문자열로 바꾼다. 엔진을 바꾸어도 F의 계약을 유지하면 규칙을 따로 검토하기 쉽다. 표시 함수가 위치를 몰래 증가시키면 그림을 두 번 그렸을 때 두 칸 이동하는 결함이 생길 수 있다.

예를 들어 상태(2,PLAYING)에 RIGHT 한 개가 들어오면 F의 결과는(3,WON), G는 “3: 승리”를 만든다. 이후 G만 다시 호출해도 상태는 그대로여야 한다. 입력 장치에서 키 반복을 여러 사건으로 만드는 부분은 이 종이 함수 검증이 보장하지 않는다.

실행 환경이 callback을 호출한다

Godot4.3의 _process(delta)는 프레임에 따라 호출되고 delta는 경과초다. _physics_process는 가능한 고정 간격으로 물리 단계 전에 호출하며 기본 설정은 60Hz다. 이 값은 문서의 기본값이고 프로젝트 설정으로 바뀔 수 있다. 표시 프레임과 물리 단계가 항상 일대일인 것은 아니다.

규칙 업데이트가 두 callback에 중복 배치되면 입력 하나를 두 번 처리할 수 있다. 어느 단계에서 입력을 소비하고 상태를 바꿀지 정하고 표시가 그 상태를 읽도록 구성해야 한다. 이 단원은 Godot callback을 실제 실행하지 않았으며 Python 전이 함수의 결과만 확인한다.

소단원 1.3

프로토타입 범위

종이 게임이 규칙대로 끝났다는 사실만으로 재미와 네트워크 성능까지 알 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 요구는 달성해야 할 조건이다. 근거는 그 조건을 판단할 자료다. 프로토타입은 질문을 확인하려는 제한된 모형이다. 범위는 포함한 기능과 제외한 기능을 정한다.

학습 목표

  • 검토 질문에 맞는 프로토타입을 고른다

  • 규칙 통과와 사용자 경험·기술 성능 증거를 구별한다

  • 작은 완료 기준과 제외 범위를 기록한다

시험 다섯 개가 통과하면 여섯 번째 요구도 확인되었을까요?

자체 종이 요구 장부는 R1 목표 도달, R2 승리 후 이동 무시, R3 초기화, R4 위치 0의 하한, R5 동일 사건 중복 소비 방지, R6 대상 플레이어의 안내 이해다. 앞 본문의 규칙 함수 시험은 R1부터 R4까지 다룬다. R5는 둘째 소단원의 사건 장부 계약을 관찰해야 한다. R6는 실제 대상 플레이어의 관찰이 필요하며 이 원고에서는 수행하지 않는다.

가상 시험 T1은 RIGHT 세 번, T2는 WON에서 LEFT, T3는 WON에서 RESET, T4는 초기 LEFT, T5는 초기 WAIT라고 하자. 모두 계획만 있고 실제 새 시험은 실행하지 않았다. 요구에 연결된 시험은 R1부터 R4까지며 T5가 성공해도 새 요구 R5/R6를 다루지 않는다. 중복 소비 변형은 위치 2에서 RIGHT 뒤 최종 상태만 확인하는 시험을 통과할 수 있다.

별도 합성 플레이 장부에서 전체 대상 다섯 회 중 안내 없이 성공 세 회, 안내를 받아 완료 한 회, 중단 한 회라고 제공한다. 사전 성공 조건을 안내 없이 완료로 두면 성공률은 3/5다. 완료 네 회만 남긴 3/4는 다른 분모다. 이 수치는 실제 사람이 플레이한 자료가 아니고 재미·학습 효과·제품 준비를 입증하지 않는다.

먼저 확인할 개념
  • 질문과 증거 범위

    기본 프로토타입 완료 기준과 실제 플레이 관찰의 구별을 유지한다.

  • 규칙과 연결 검증

    규칙 단독 표가 사건 소비 경계를 검증하지 못하는 이유를 연결한다.

모형을 만들기 전에 질문을 정한다

프로토타입은 완제품의 작은 복사일 필요가 없다. 종이 보드로 목표 도달·승리 후 입력·재시작 규칙을 확인할 수 있다. 동작하는 작은 프로그램으로 입력 처리나 프레임 시간을 확인할 수 있다. 플레이어 경험 질문은 실제 사람이 과업과 플레이를 하는 관찰이 필요하다.

보드 0..3, 초기(0,PLAYING), RIGHT로 한 칸, LEFT로 한 칸, WAIT 유지,3에서 WON, WON에서 이동 무시, RESET으로 초기화한다고 이 소단원의 모형을 독립 정의한다. 그래픽·소리·물리·네트워크·저장 기능은 포함하지 않는다.

범위와 통과 기준을 연결한다

이번 질문은 “세 번 이동하여 승리하고 재시작할 수 있는가?”다. 기준은 RIGHT 세 번 뒤(3,WON), 이어 LEFT에도 그대로, RESET 뒤(0,PLAYING)이다. 여기에 0에서 LEFT의 경계 사례를 추가하면 의도한 규칙을 더 분명하게 확인할 수 있다.

이 기준을 통과해도 화면이 읽기 쉽거나 사용자가 재미있어하거나 서버가 많은 접속을 처리한다는 근거는 없다. 통과 기준은 확인한 질문의 범위 안에서 해석한다. 코드가 완성되지 않았다는 이유로 종이 모형의 규칙 검토가 무의미해지는 것도 아니다.

반복에서 버전과 미확인 질문을 남긴다

규칙을 바꾼 뒤에는 같은 초기 상태·입력 순서·예상 결과를 기록해 비교한다. 승리 후에도 LEFT를 허용하는 버전이라면 승리 상태의 의미와 목표 3이라는 조건을 다시 설계해야 한다. 변경 이유 없이 결과표만 달리 쓰면 무엇을 검토했는지 모른다.

재미를 검토하려면 대상 플레이어·과업·관찰 지표를 정하고 실제 플레이 관찰을 수행해야 한다. 이 원고의 표는 사람이 플레이한 자료가 아니라 종이 상태 추적이다. 실제 엔진·GPU·네트워크 성능은 미확인 질문으로 남긴다.

세 독립 장부를 검토하라. ① K 초기에서 RIGHT,LEFT,RIGHT,RIGHT,RIGHT를 처리하고 위치 0으로 돌아왔을 때 초기 상태와 같은지 판정하라. ② 원래 보드 초기/세대 1에서 번호 1 RIGHT, 같은 사건 재전송, 번호 2 RESET, 늦은 세대 1 번호 1 RIGHT, 세대 2 번호 1 RIGHT를 처리하라. ③ T1부터 T5에 R5의 호출 수를 검사하는 T6을 추가한 요구 연결 비율과 합성 다섯 플레이의 전체 성공률을 구하라. 실제 엔진·장치·플레이 시험은 요구하지 않는다.

힌트 1

①은 열쇠가 유지되는 별도 규칙 K다. ②는 앞 본문의 열쇠 없는 보드와 사건 장부다.

힌트 2

계획된 요구 연결 분모 여섯 개와 합성 플레이 대상 다섯 회를 서로 바꾸지 않는다.

풀이와 답 확인

  1. ① 상태는 (1,참),(0,참),(1,참),(2,참),(3,참)이다. 위치 0으로 돌아온 (0,참)은 초기 (0,거짓)과 다르다.

  2. ② 첫 RIGHT를 수용하고 재전송은 중복이다. RESET을 수용하여 세대 2/초기 보드로 만든다. 늦은 세대 1 사건은 거절하고 새 세대 사건을 수용한다. 규칙 호출은 세 번, 최종 (1,PLAYING)이다.

  3. ③ 요구 연결은 다섯 개/전체 여섯 개로 약 83.33%다. 합성 전체 대상 성공률은 세 회/다섯 회로 60%다. 계획 연결과 실제 수행·재미는 별도다.

K의 최종 상태는 (3,참)이며 도중 위치 0에서 열쇠는 유지된다. 사건 장부에서는 규칙 호출 세 번과 최종 (1,PLAYING), 세대 2다. 요구 연결은 약 83.33%, 합성 전체 성공률은 60%다. 모든 새 엔진·플레이·학생 시험은 미수행이다.

해결한 뒤 점검할 것

  • 열쇠 규칙과 원래 보드의 별도 초기 조건을 유지한다.

  • 위치 표시와 전체 상태, 중복 소비와 승리 뒤 무효 이동을 구별한다.

  • 세대와 번호/내용을 함께 비교한다.

  • 요구 연결과 실제 수행, 전체 대상과 완료 대상의 분모를 구별한다.
