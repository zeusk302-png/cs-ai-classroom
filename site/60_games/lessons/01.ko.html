소단원 1.1

규칙·상태·상호작용

같은 오른쪽 입력도 이미 이긴 뒤에는 왜 이동하지 않을 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 상태는 다음 행동을 결정하는 데 필요한 현재 정보다. 변수는 그 정보의 이름이다. 입력은 규칙에 전달되는 사건이며 반복은 갱신을 여러 번 수행하는 것이다. 한 번의 갱신을 tick이라 부른다.

학습 목표

  • 상태·입력·전이·표시를 구별한다
  • 작은 보드 규칙을 순서대로 추적한다
  • 프레임 수와 경과시간의 조건을 설명한다

게임 규칙은 상태 전이로 적을 수 있다

보드 위치는 정수 0부터 3, 상태는 (위치, PLAYING 또는 WON)이다. 처음은 (0,PLAYING). 한 tick에 RIGHT/LEFT/WAIT/RESET 중 하나만 전달한다. RESET은 언제나 처음으로 돌아간다. WON에서는 나머지 입력을 무시한다. PLAYING에서 RIGHT는 1 증가하되 3을 넘지 않고 LEFT는 1 감소하되 0 아래로 가지 않으며 WAIT는 그대로다. 새 위치가 3이면 WON으로 바꾼다.

이 전이 함수 F는 유효 상태와 정해진 입력에서 다음 상태를 하나로 정한다. 현실 게임의 확률·동시 입력은 이 모형에서 제외했다. 키를 누르고 있는 동안 입력을 몇 번 만드는지는 별도 입력 정책이다. “오른쪽 키를 누른다”만 쓰면 tick 수가 정해지지 않는다.

def step(state, event):
    x, phase = state
    if event == 'RESET':
        return (0, 'PLAYING')
    if phase == 'WON':
        return state
    if event == 'RIGHT':
        x = min(3, x + 1)
    elif event == 'LEFT':
        x = max(0, x - 1)
    elif event != 'WAIT':
        raise ValueError('unknown event')
    return (x, 'WON' if x == 3 else 'PLAYING')

입력 순서와 규칙의 불변조건

유효 상태는 0≤위치≤3이고 WON과 위치 3이 동치인 네 상태다. 처음에 조건이 맞고 이동을 양끝에서 제한하며 3에서 승리로 바꾸고 RESET이 처음으로 돌아가므로 모든 유효 전이 후에도 조건이 유지된다. 임의의 잘못된 초기 상태까지 복구한다는 주장은 아니다.

위치 2에서 RIGHT 다음 LEFT는 먼저 승리하여 LEFT를 무시하고 3에 남는다. LEFT 다음 RIGHT는 1을 거쳐 2에 남는다. 같은 입력 개수라도 순서가 결과를 바꾼다. 화면 표시 G(상태)는 위치와 승리를 보여줄 뿐 이 모형에서는 상태를 바꾸지 않는다.

시간을 쓰는 게임에서는 tick 수와 초를 구별한다

여기서는 이동 1칸이 입력 사건 한 개의 결과다. 연속 운동으로 바꾸면 속도는 칸/초, delta는 직전 갱신 이후 경과초이며 일정 속도v에서 이동량은v×delta다. 매 프레임 1칸이면 1초에 30프레임인 경우 30칸,60프레임이면 60칸이라 기기별 차이가 생긴다.

일정 속도 6칸/초를 각각 30회×1/30초,60회×1/60초로 나누면 총 이동은 모두 6칸이다. 이 계산은 일정 속도의 단순 운동에 대한 것이다. 충돌·가속도·부동소수 오차·불규칙 단계까지 완전히 동일한 결과를 보장하는 증명은 아니다.

소단원 1.2

엔진과 게임코드

화면에 캐릭터를 그려주는 엔진은 우리 보드의 승리 규칙도 자동으로 알고 있을까?

준비 개념과 학습 목표

준비 개념

  • 함수는 입력을 받아 정해진 처리를 수행하는 단위다. 호출은 그 처리를 요청하는 일이다. callback은 제공해 둔 함수를 실행 환경이 정해진 시점에 호출하는 방식이다. 상태는 현재 위치·진행 여부 같은 정보다.

학습 목표

  • 엔진 서비스와 게임 규칙의 책임을 구별한다
  • 입력→규칙→표시의 계약을 적는다
  • 명시된 엔진 판본의 갱신 방식과 검증 범위를 구별한다

엔진은 재사용할 실행 기반을 제공한다

게임 엔진은 창·입력·그림·소리·자원·물리 같은 실행 기반과 구성 도구를 제공한다. 게임코드는 어떤 입력이 어떤 행동이고 언제 승리하며 무엇을 표시할지 결정한다. 엔진이 충돌 정보를 줄 수 있어도 그 충돌이 점수인지 실패인지는 게임 규칙이다.

Godot4.3 문서의 노드와 씬은 게임 요소를 조직하는 한 방식이다. 씬에 노드를 묶고 스크립트로 동작을 정한다. 이는 고정 판본의 설명 예시이며 엔진 설치나 최신 지원 버전 선택을 이론 학습의 필수로 삼지 않는다.

입력·규칙·표시는 경계에서 만난다

종이 모형에서는 입력 변환기가 한 사건을 RIGHT 등으로 바꾸고 규칙 함수 F가 새 상태를 만들며 표시 함수 G가 그 상태를 그림이나 문자열로 바꾼다. 엔진을 바꾸어도 F의 계약을 유지하면 규칙을 따로 검토하기 쉽다. 표시 함수가 위치를 몰래 증가시키면 그림을 두 번 그렸을 때 두 칸 이동하는 결함이 생길 수 있다.

예를 들어 상태(2,PLAYING)에 RIGHT 한 개가 들어오면 F의 결과는(3,WON), G는 “3: 승리”를 만든다. 이후 G만 다시 호출해도 상태는 그대로여야 한다. 입력 장치에서 키 반복을 여러 사건으로 만드는 부분은 이 종이 함수 검증이 보장하지 않는다.

실행 환경이 callback을 호출한다

Godot4.3의 _process(delta)는 프레임에 따라 호출되고 delta는 경과초다. _physics_process는 가능한 고정 간격으로 물리 단계 전에 호출하며 기본 설정은 60Hz다. 이 값은 문서의 기본값이고 프로젝트 설정으로 바뀔 수 있다. 표시 프레임과 물리 단계가 항상 일대일인 것은 아니다.

규칙 업데이트가 두 callback에 중복 배치되면 입력 하나를 두 번 처리할 수 있다. 어느 단계에서 입력을 소비하고 상태를 바꿀지 정하고 표시가 그 상태를 읽도록 구성해야 한다. 이 단원은 Godot callback을 실제 실행하지 않았으며 Python 전이 함수의 결과만 확인한다.

중간 과정을 따라가는 예제

가상 입력 변환기가 RIGHT 한 개를 만들었다. 상태는(2,PLAYING). 규칙 한 번과 표시 두 번의 결과를 추적하라.

  1. 입력 변환 출력은 RIGHT 한 개다.
  2. F는 2를 3으로 바꾸고 WON을 만든다.
  3. G는 “3: 승리”를 출력한다고 정한다.
  4. G를 두 번 호출해도 읽기만 하므로 상태는(3,WON)이다.

규칙 갱신 1회, 표시 2회, 위치 3이다. 표시 횟수와 이동 횟수의 관계를 분리했다.

엔진의 물리 기능을 쓰면 게임 규칙도 자동으로 검증된다.

소단원 1.3

프로토타입 범위

종이 게임이 규칙대로 끝났다는 사실만으로 재미와 네트워크 성능까지 알 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 요구는 달성해야 할 조건이다. 근거는 그 조건을 판단할 자료다. 프로토타입은 질문을 확인하려는 제한된 모형이다. 범위는 포함한 기능과 제외한 기능을 정한다.

학습 목표

  • 검토 질문에 맞는 프로토타입을 고른다
  • 규칙 통과와 사용자 경험·기술 성능 증거를 구별한다
  • 작은 완료 기준과 제외 범위를 기록한다

모형을 만들기 전에 질문을 정한다

프로토타입은 완제품의 작은 복사일 필요가 없다. 종이 보드로 목표 도달·승리 후 입력·재시작 규칙을 확인할 수 있다. 동작하는 작은 프로그램으로 입력 처리나 프레임 시간을 확인할 수 있다. 플레이어 경험 질문은 실제 사람이 과업과 플레이를 하는 관찰이 필요하다.

보드 0..3, 초기(0,PLAYING), RIGHT로 한 칸, LEFT로 한 칸, WAIT 유지,3에서 WON, WON에서 이동 무시, RESET으로 초기화한다고 이 소단원의 모형을 독립 정의한다. 그래픽·소리·물리·네트워크·저장 기능은 포함하지 않는다.

범위와 통과 기준을 연결한다

이번 질문은 “세 번 이동하여 승리하고 재시작할 수 있는가?”다. 기준은 RIGHT 세 번 뒤(3,WON), 이어 LEFT에도 그대로, RESET 뒤(0,PLAYING)이다. 여기에 0에서 LEFT의 경계 사례를 추가하면 의도한 규칙을 더 분명하게 확인할 수 있다.

이 기준을 통과해도 화면이 읽기 쉽거나 사용자가 재미있어하거나 서버가 많은 접속을 처리한다는 근거는 없다. 통과 기준은 확인한 질문의 범위 안에서 해석한다. 코드가 완성되지 않았다는 이유로 종이 모형의 규칙 검토가 무의미해지는 것도 아니다.

반복에서 버전과 미확인 질문을 남긴다

규칙을 바꾼 뒤에는 같은 초기 상태·입력 순서·예상 결과를 기록해 비교한다. 승리 후에도 LEFT를 허용하는 버전이라면 승리 상태의 의미와 목표 3이라는 조건을 다시 설계해야 한다. 변경 이유 없이 결과표만 달리 쓰면 무엇을 검토했는지 모른다.

재미를 검토하려면 대상 플레이어·과업·관찰 지표를 정하고 실제 플레이 관찰을 수행해야 한다. 이 원고의 표는 사람이 플레이한 자료가 아니라 종이 상태 추적이다. 실제 엔진·GPU·네트워크 성능은 미확인 질문으로 남긴다.

중간 과정을 따라가는 예제

네 입력 시험 RIGHT×3, 이후 LEFT, RESET, 초기 LEFT를 계획하라. 각 시험의 초기 상태와 기대값·검증 범위를 적어라.

  1. 초기(0,PLAYING)에서 RIGHT 세 번:1,2,3으로 이동하고 WON.
  2. 그 결과 상태에서 LEFT:승리 후 무시되어(3,WON).
  3. 그 상태에서 RESET:(0,PLAYING).
  4. 초기 상태에서 LEFT:(0,PLAYING). 이는 규칙과 경계 검토이며 재미 측정이 아니다.

목표 도달·승리 후 흡수·재시작·하한을 확인하는 규칙 표다. 플레이어 반응이나 엔진 성능 결론은 포함하지 않는다.

즐거움은 대상 사람의 실제 플레이·질문·관찰이 필요하고, 초기화는 유효 상태별 RESET 전이 표로 검토할 수 있다. 종이 표만으로 사람의 즐거움 값을 만들어 넣지 않는다.
