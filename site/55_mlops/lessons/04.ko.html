소단원 4.1

환경·의존성 고정

어제 설치한 이름만 적으면 다음 달에도 같은 도구를 얻을까?

준비 개념과 학습 목표

준비 개념

  • 패키지 버전

  • 직접 의존과 전이 의존

  • 내용 식별자와 파일 이름

학습 목표

  • 패키지 분리와 전체 실행 환경 고정을 구별한다

  • 의존성 제약을 만족하는 고정 목록과 hash의 범위를 설명한다

분리한 상자와 고정된 재료

Python 가상 환경은 프로젝트별 패키지를 분리하는 도구다. 빈 가상 환경을 만들었다고 라이브러리 버전이나 학습 결과가 고정되는 것은 아니다. base Python과 실제 설치 목록을 함께 기록해야 한다.

실행 환경에는 Python·패키지뿐 아니라 OS·CPU/GPU·driver·런타임·수치 dtype와 외부 도구도 포함된다. 이 단원에서는 이름이 가상의 A/B/C인 작은 의존성 표를 비교한다. 실제 설치를 권장하거나 특정 버전 조합의 호환성을 인증하는 표가 아니다.

꼬리를 따라 의존까지 확인하기

A를 고정해도 A가 허용하는 B의 범위가 넓으면 재설치 시 B가 달라질 수 있다. B가 다시 C를 부르면 C도 전이 의존이다. 모든 선택 버전이 각 패키지의 제약을 함께 만족하는지 확인한다.

정확 버전 목록과 내려받은 파일의 hash는 다른 정보를 담는다. 버전은 선택 제약, hash는 기대한 바이트와의 일치 검사다. hash 일치는 패키지가 안전하거나 올바른 예측을 한다는 증명이 아니며 기대hash의 출처 자체도 신뢰해야 한다.

재생성과 플랫폼 조건

Wheel 묶음을 보관하면 원격 index가 없어도 같은 파일 재료를 사용할 수 있다. 그러나 compiled wheel의 OS·architecture·Python ABI 조건이 맞아야 한다. 파일을 갖고 있다고 아무 기계에서 사용할 수 있는 것은 아니다.

가상 환경 폴더는 interpreter와 scripts의 경로를 포함할 수 있어 다른 경로로 통째로 복사하는 것보다 기록한 조건으로 재생성하는 정책이 필요하다. 고정 목록·hash·플랫폼·코드·자료 버전을 묶어 기록하고 설치 성공과 결과 재현 성공도 별도로 확인한다.

중간 과정을 따라가는 예제

가상 의존성: A1은 B2 또는 B3, B2는 C1, B3는 C2를 요구한다. C1/C2는 서로 다른 버전이다. 목록[A1,B3,C1]과[A1,B2,C1]을 비교하고 A1만 고정했을 때 가능한 두 환경을 적어라.

  1. A1,B3 조합에서는 B3의 제약이 C2이므로 C1 목록은 불일치다.

  2. A1,B2,C1은 A의 B2 허용과 B2의 C1 요구를 모두 만족한다.

  3. A1만 고정하면 조건상[A1,B2,C1] 또는[A1,B3,C2]가 가능하다.

  4. 각 환경은 문법상 의존 제약을 만족하지만 실행 성공·모델 출력 동일성은 검사하지 않았다. 이 예의 제약을 실제 package resolver 실험으로 소개하지 않는다.

첫 목록 불일치, 둘째 일치. A1의 동일성만으로 B/C까지 고정되지 않는다. 의존 만족과 실제 실행 검증은 다른 단계다.

종이와 본문으로 직접 해보기

가상 Windows x64용 파일 W와 Linux x64용 파일 L을 적고, 다른 OS에서 W를 복사해도 호환이 보장되는지 설명하라. 기대 내용 D1인데 이름 같은 파일 내용 D2를 받은 상황에서 버전명과 hash 검사를 구별하라.

힌트 보기

compiled 파일의 대상 조건을 적는다. D1/D2는 hash 자체가 아닌 서로 다른 내용의 기호다.

풀이 보기

W는 해당 OS/ABI/architecture 조건의 파일이므로 Linux 호환을 보장하지 않는다. 같은 버전 문자열만 확인하면 D2 변경을 놓칠 수 있지만 신뢰한 D1의hash와 실제 파일hash를 비교하면 바이트 불일치를 발견하는 정책을 만들 수 있다. 실제 hash를 계산한 예는 아니다.

오해와 반례

venv를 만들고 최상위 package 하나를 고정하면 모든 기계에서 같은 학습 결과다.

전이 의존과 base interpreter·플랫폼·자료·코드·난수/알고리즘 조건이 남는다. 자체 A1 예는 두 다른 합법 의존 환경을 허용하며 같은 환경도 학습 결과 동일성의 충분조건으로 주장하지 않는다.

소단원 4.2

작업 DAG와 재시도

다시 시도한 작업이 같은 결과를 두 번 더해 버리면 어떻게 될까?

준비 개념과 학습 목표

준비 개념

  • 방향 있는 의존 간선

  • 작업 성공과 결과 게시

  • 동일한 요청 식별자

학습 목표

  • DAG의 선행 조건과 병렬 가능 작업을 찾는다

  • 재시도에서 입력 고정·중복 방지·완성 결과 게시를 구별한다

화살표가 약속하는 순서

DAG는 방향이 있고 순환이 없는 의존 그래프다. A→B이면 이 원고에서는 A의 성공 결과가 B의 입력으로 필요하다는 뜻이다. B는 A의 조건이 충족되어야 시작하며 서로 간선이 없는 작업도 자원 제한 때문에 반드시 동시에 실행되지는 않는다.

모든 선행 성공을 기다리는 정책과 하나만 성공해도 시작하는 정책은 다르다. 실제 Airflow의 trigger rule이 실행 조건을 바꾸므로 그래프만 보고 무조건 all-success라고 가정하지 않는다. 아래 예는 모든 선행 성공·무제한 worker·통신0인 자체 모형이다.

실패 지점과 남은 효과

작업이 파일 일부를 쓰고 실패하면 다음 작업이 그 일부를 완성 자료로 읽지 않게 해야 한다. 임시 결과를 검증한 뒤 완성 이름이나 완료 manifest로 게시하는 정책과, 작업 시작부터 최종 결과로 보이는 정책은 다르다. 게시의 원자성과 저장소 조건을 따로 확인한다.

외부 효과를 완료한 뒤 성공 응답만 잃으면 재시도가 같은 효과를 또 만들 수 있다. 동일 작업 키에 대해 결과를 한 번만 확정하는 멱등 정책이 필요하다. 단순히 retries 숫자를 늘리는 것이 exactly-once 실행 보장은 아니다.

같은 입력을 다시 읽기

재시도마다 latest 자료나 현재시간 now로 입력을 고르면 같은 작업 이름인데 다른 데이터를 처리할 수 있다. 고정 partition·자료 내용 ID·설정·코드 버전을 입력에 포함한다. 고정한 데이터가 실제로 변경되지 않게 보관하는 정책도 필요하다.

서로 다른 worker에서 실행되는 작업은 앞 worker의 로컬 파일을 못 볼 수 있다. 결과가 있는 공용 저장소 위치와 내용 ID를 전달한다. 경로 전달 자체만으로 완료 여부·접근권한·내용 동일성이 확인되는 것은 아니다. 이 원고는 실제 orchestration을 실행하지 않았다.

중간 과정을 따라가는 예제

가상 DAG에서 A(2분)→B(3분), A→C(4분), B와C→D(1분)이다. 모두 성공하고 무제한worker/통신0이면 종료 시각은? 별도로 작업K가 결과행 하나를 INSERT한 뒤 응답을 잃고 재시도하면 무조건 INSERT 정책의 행수는?

  1. A는0→2에 끝나고 B는2→5, C는2→6에 끝난다.

  2. D는 두 선행의 최대 종료6에 시작해7에 끝난다.

  3. 모든 작업을 직렬로 하면2+3+4+1=10분이다. 의존 임계경로 A→C→D는7분이다.

  4. K의 최초 INSERT가 실제 확정되고 재시도에서도 새 행을 INSERT하면 두 행이다. 성공 응답을 잃었어도 첫 효과는 남아 있다.

이상 병렬 종료7분 대 직렬10분이며 중복 INSERT는 2행이다. 같은 K에 고유 키·조건부 확정/UPSERT 정책을 올바르게 적용하면 한 논리 결과를 유지할 수 있지만 실제 저장소 검증은 하지 않았다.

종이와 본문으로 직접 해보기

C가 시작 2부터 2분 진행한 뒤 실패하고 2분 대기 후 전체 4분을 다시 실행한다. B는 성공 유지하며 D는 all-success일 때 언제 끝나는가? 재시도마다 입력 latest가 D1→D2로 바뀌면 같은 입력의 재현인가?

힌트 보기

C의 실패 시각 4, 재시작 6을 표에 적는다. 성공한 B를 다시 시작하지 않는 정책이다.

풀이 보기

C는 4에 실패하고 6→10에 재시도 성공한다. D10→11, 전체 11분이다. D1/D2가 다른 내용이면 같은 입력을 다시 실행한 것이 아니다. 고정 내용 ID와 partition을 입력으로 사용해야 한다.

오해와 반례

DAG가 순환이 없고 재시도를 하면 결과가 항상 한 번만 생긴다.

DAG는 선행 관계를 정한다. 최초 효과 확정 뒤 응답 손실이면 중복이 생길 수 있다. 입력 고정·멱등 키·완료 게시·실패 상태는 별도로 설계하고 정확한 실행/효과 보장 범위를 밝힌다.

seed와 지금 상태는 다르다

seed는 특정 생성기의 시작 상태를 설정하는 재료다. 그 뒤 난수를 몇 번 어떤 순서로 썼는지가 지금 상태를 바꾼다. 같은 시작 seed라도 입력 처리 순서가 바뀌거나 중간에 다른 난수 호출이 끼면 작업별로 받는 값이 달라질 수 있다.

Python·NumPy·PyTorch와 별도 generator 객체는 각각의 난수원을 가질 수 있다. 한 라이브러리 seed만 다루면 다른 원의 상태가 남는다. PyTorch 공식 문서는 release/플랫폼/CPU 대 GPU까지 완전 동일을 보장하지 않으며 알고리즘 결정성과 난수 통제도 구별한다.

다시 시작하기와 이어서 하기

처음부터 같이 실행하는 것과 checkpoint부터 같이 이어 실행하는 것은 다르다. 모델 가중치만 저장하면 optimizer의 상태·학습률 스케줄·진행 epoch/step·자료 순서·난수 상태가 빠질 수 있다. 재개 후 같은 다음 단계를 원하면 필요한 상태와 실행 조건을 함께 보관한다.

동일 seed로 초기화하면 이미 소비한 난수도 다시 처음부터 나올 수 있다. 여기서는 실제 library와 무관한 가상 난수 테이프를 쓴다. 물리 난수나 보안용 난수의 예가 아니며 수치열은 학습자 종이 활동용으로 직접 정했다.

산출물의 이름과 근거 연결

artifact는 학습 가중치·변환기·평가표·로그 같은 산출물이다. 어느 자료 내용·코드 버전·환경·설정·seed/상태에서 만들었는지 manifest로 연결하면 같은 이름의 서로 다른 모델을 구별할 수 있다. 설정은 기본값까지 실제 사용한 값을 기록한다.

내용 hash는 파일 내용의 식별에 도움이 되지만 그 파일의 정확성이나 학습 성능을 보장하지 않는다. 재현성 비교도 비트 동일·수치 허용 오차·통계적 반복 결과 중 무엇인지 정한다. 이 원고는 실제 학습/복구/성능 측정을 실행하지 않았고 다음 예는 가상 상태 장부다.

중간 과정을 따라가는 예제

가상 seed S의 테이프가 .2,.7,.4,.9 순서다. A가 첫 값, B가 다음 값을 쓰고 직후 checkpoint한다. 상태를 저장해 C가 다음 값을 쓸 때와 seed S만 다시 설정할 때의 C 값을 비교하라. 입력 순서 B→A라면 각 값도 적어라.

  1. 정상 A→B 순서에서 A=.2,B=.7이며 소비 위치는 2다.

  2. checkpoint가 다음 위치 2를 보존하면 C는 세 번째 값 .4를 쓴다.

  3. seed S만 다시 설정하면 테이프 시작으로 돌아가 C=.2다. 이어가기와 처음부터 재시작이 다르다.

  4. 순서를 B→A로 바꾸면 B=.2,A=.7이다. 동일 seed가 작업 A의 동일 값을 보장하려면 호출 순서도 조건에 넣는다.

상태 복구 C=.4, seed 재설정 C=.2다. 순서 변경으로 A/B에 배정되는 값도 바뀐다. 이 테이프는 실제 RNG 출력이 아니다.

종이와 본문으로 직접 해보기

설정 η=.1, 자료 D1, 코드 C1로 만든 모델 M1의 manifest를 종이에 쓰고 η=.2 또는 자료 D2로 바뀔 때 무엇을 새로 기록할지 적어라. checkpoint에 가중치만 있을 때 다음 학습 단계 동일성을 단정할 수 있는가?

풀이 보기

M1에 D1/C1/η.1/환경 버전/난수원과 상태/진행 위치/출력 내용 ID/비교 정책을 연결한다. η.2 또는 D2는 실제 사용 설정과 새 입력/출력 ID를 기록한다. 가중치만으로 optimizer·스케줄·난수/자료 위치를 알 수 없으므로 동일 다음 단계를 보장하지 못한다.

오해와 반례

seed 하나와 모델 파일 이름만 같으면 모든 기계와 재개 시점에서 같은 결과다.

가상 테이프도 호출 순서와 복구 위치에 따라 다르다. 실제 library는 독립 난수원·알고리즘·dtype·플랫폼 차이가 남고 같은 파일 이름이 같은 내용이라는 보장도 없다.
