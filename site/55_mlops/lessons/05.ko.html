소단원 5.1

파라미터·지표·로그

정확도 .92만 남겨 두면 어떤 자료와 설정으로 그 숫자가 나왔는지 다시 알 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 파라미터는 학습률처럼 실행에 준 설정, 지표는 정확도처럼 측정해 기록하는 값이다.

  • run은 한 실행의 식별 단위, artifact는 모델·그림 같은 결과 파일이다. 로그는 사건과 맥락을 남기는 기록이다.

학습 목표

  • 실행 ID로 설정·자료·평가·결과를 연결한다.

  • 동일 조건의 지표만 비교하고 미실행 기록을 구분한다.

숫자에 출처를 붙인다

한 실험 run에는 파라미터와 지표뿐 아니라 코드 버전, 데이터 버전, 평가 분할, 난수 seed, 환경 정보를 연결한다. seed는 무작위 선택의 시작값이며 같은 seed 하나만으로 모든 장치에서 완전 재현된다고 보장하지 않는다. 정확도 .92가 훈련 자료인지 검증 자료인지도 별도 필드다.

지표의 이름·단위·분모를 함께 적는다. latency=12만 적으면 밀리초인지 초인지, 평균인지 95백분위인지 알 수 없다. 학습 중 loss는 step 또는 epoch와 함께 시계열로 남겨 마지막 값과 최소값을 혼동하지 않는다.

실험을 묶되 실행은 분리한다

experiment는 같은 과제의 여러 run을 모으는 이름이다. 두 설정을 시험했다면 서로 다른 run ID로 남겨 좋은 지표만 한 실행에 섞지 않는다. 모델 파일도 어느 run에서 생성되었는지 연결해야 지표와 결과물의 짝을 다시 찾는다.

실패한 실행은 실패 시점과 오류를 남기고 완성 모델의 평가값으로 표시하지 않는다. 교육용 가상 기록은 paper_example 같은 표식으로 실제 train.py 실행 기록과 구분한다. 기록 파일이 존재한다는 사실은 실제 실행이나 성능 검증을 뜻하지 않는다.

비교의 분모와 조건을 맞춘다

모형 표의 A와 B가 같은 검증 집합 100개를 평가했다면 맞은 수 90과 92로 정확도 .90과 .92를 계산한다. 다른 집합 10개에서 맞은 10개는 정확도 1이어도 같은 어려움과 표본 규모가 아니다. 수치만 정렬하기 전 자료의 ID와 평가 규칙을 확인한다.

반복 실행 평균은 각 표본의 값과 집계 방법을 보존해야 의미가 있다. 여러 seed의 차이와 평가 자료의 불확실성은 다른 분석이다. 추적 도구가 그래프를 그렸다고 목표가 공정하거나 배포가 승인되었다는 뜻은 아니다.

중간 과정을 따라가는 예제

자체 기록 A:학습률 .01,평가 집합 D1 100개 중 90정답, B:.02/D1/92정답, C:.02/D2 10개 중 10정답이다. 정확도와 같은 집합 비교를 하라.

  1. A=90/100=.90, B=92/100=.92다. D1이라는 같은 분모를 확인했다.

  2. C=10/10=1이지만 D2이며 표본 수도 다르다. A/B보다 우수하다고 이 표만으로 단정하지 않는다.

  3. B−A는 .02, 즉 2퍼센트포인트다. 상대 증가율은 .02/.90≈2.22%로 다른 값이다.

  4. 각 설정·지표·데이터를 별도 run A/B/C에 연결한다. 이 표는 실제 모델 학습 기록이 아니다.

같은 D1에서 B가 A보다 2퍼센트포인트 높다. C는 조건을 맞춰 재평가해야 한다.

종이와 본문으로 직접 해보기

한 run의 loss가 step1:.8, step2:.5, step3:.6이다. 최소값과 마지막값을 나누어 적어라.

힌트 보기

시간 위치와 값의 크기를 따로 본다.

풀이 보기

최소 .5는 step2, 마지막 .6은 step3이다. 모델 파일이 어느 checkpoint인지도 연결해야 최소 loss와 마지막 파일을 자동 같은 결과라고 하지 않는다.

오해와 반례

가장 큰 정확도와 가장 작은 loss를 어디서든 모아 한 run의 결과라고 쓰면 된다.

A/B/C의 자료·설정이 달라 그런 결합은 존재하지 않은 실험을 만든다. step2 최소 loss와 step3 파일도 구별한다.

한 단계 더

A를 세 seed에서 .90/.92/.91로 얻었다는 가상 추가 조건이면 평균(.90+.92+.91)/3=.91이다. 실제 반복을 하지 않은 표이므로 재현성 측정이라고 기록하지 않는다.

소단원 5.2

model registry

최신 모델 파일이라는 이름이 바뀌었을 때 어제 서비스한 정확한 모델을 다시 찾을 수 있을까?

준비 개념과 학습 목표

준비 개념

  • registry는 모델 이름 아래 버전과 출처·설명을 관리하는 저장소다.

  • lineage는 결과가 어떤 run·자료·코드에서 왔는지 연결한 계보, alias는 특정 버전을 가리키는 바꿀 수 있는 별명이다.

학습 목표

  • 모델 이름·버전·별명·실행 출처를 구별한다.

  • 서비스와 rollback에서 실제 사용 버전을 기록한다.

등록과 학습은 다른 사건이다

모델을 학습해 로그에 남기는 일과 그 결과를 registry의 이름 아래 새 버전으로 등록하는 일은 다르다. 등록 항목에는 결과물 위치와 생성 run을 연결한다. 버전 번호 3이 버전 2보다 성능이 좋다는 뜻은 아니며 단지 등록 순서를 나타낼 수 있다.

실제 재현에는 모델 가중치 외 전처리·입출력 규격·의존 환경도 필요하다. 파일 이름만 같거나 버전 숫자만 같다는 이유로 결과 바이트와 평가 조건이 같다고 결론 내리지 않는다. 별도 hash로 결과물을 확인할 수 있지만 hash 역시 학습 성능의 증거는 아니다.

버전 참조와 별명 참조

MLflow의 models:/Study/2는 특정 등록 버전, models:/Study@champion은 그 별명이 현재 가리키는 버전이다. champion을 2에서 3으로 바꾸면 이름은 같아도 다음에 별명을 해석한 대상이 달라질 수 있다. 이것이 mutable reference의 뜻이다.

실행 당시 별명을 어떤 버전과 결과물로 해석했는지 남겨야 과거를 복원할 수 있다. 이미 메모리에 모델을 로드한 서버가 별명 변경만으로 즉시 새 모델을 받는다고 가정하지 않는다. 로드·캐시·재시작과 배포 방식은 별도 정책이다.

분류 표식은 승인 증거와 연결한다

버전에 validation_status:approved 같은 tag를 붙일 수 있지만 문자열 하나가 독립 평가와 승인 과정을 자동 증명하지는 않는다. 누가 어떤 결과물과 기준을 확인했는지 증거 ID를 연결한다. OSS와 관리형 환경의 권한·governance 기능도 같은 것으로 단정하지 않는다.

rollback은 이전에 확인한 버전으로 참조나 배포를 되돌리는 선택이다. 그 버전이 현재 입력 규격·자료와 호환되는지 검토해야 한다. registry 기록과 실제 서버의 수신/추론 결과를 별도 확인하는 이유다.

중간 과정을 따라가는 예제

가상 Study 버전 1→run R1/hash H1, 버전 2→R2/H2, 버전 3→R3/H3다. champion이 2일 때 실행 S가 로드하고, 그 뒤 champion을 3으로 바꿨다. S의 과거 출처와 새 조회 대상을 적어라.

  1. S의 로드 기록에는 당시 resolved_version=2,run R2,H2를 적는다.

  2. 별명 재배정 뒤 새 alias 조회는 3/R3/H3를 가리킨다.

  3. 고정 models:/Study/2는 계속 버전 2를 가리키는 참조다. 등록 결과 자체가 삭제되지 않았다고 정한다.

  4. S가 자동 갱신된다는 결론은 없다. 이 예제는 참조표이며 실제 서버를 실행하지 않았다.

S의 과거는 2/R2/H2, 새 별명 해석은 3/R3/H3다.

종이와 본문으로 직접 해보기

champion을 3에서 2로 되돌리고 서버가 다음 로드 때만 alias를 해석한다면 언제 버전 2를 받는가?

힌트 보기

별명 변경과 모델 로드 사건을 분리한다.

풀이 보기

변경 뒤 다음 로드에서 2를 해석한다. 이미 로드한 3은 그 정책에 따라 새 로드 전까지 남을 수 있다. 버전 2의 호환성·승인 증거도 따로 확인한다.

오해와 반례

버전 숫자가 크거나 approved tag가 있으면 최신 서버에서 검증된 최상 모델이다.

버전 3은 등록 순서일 뿐이고 tag는 기록이다. 서버 S가 2를 이미 로드했다는 반례와 증거 없는 approved 표식을 구별한다.

소단원 5.3

승격조건과 승인기록

정확도가 조금 높아졌지만 응답시간이 길어졌다면 새 모델로 바꿀 조건을 누가 어떻게 남겨야 할까?

준비 개념과 학습 목표

준비 개념

  • 승격은 후보 모델을 정한 다음 사용 단계로 옮기는 결정이다. 배포 실행과 구별한다.

  • 승인 기록은 대상 버전·증거·기준·검토자·결정 시각·이유를 연결한다. 미확인은 통과와 다르다.

학습 목표

  • 여러 수치와 증거 조건을 모두 검사한다.

  • 승인 대상 변경 시 이전 승인의 효력을 재검토한다.

조건은 비교 전에 정한다

자체 정책은 같은 D1의 정확도≥.92, p95 응답시간≤50ms, 입력 규격 검사 PASS, 독립 검토 완료를 모두 만족해야 승격 후보가 된다고 정한다. p95는 정한 측정 집합에서 95백분위 지연이며 평균과 다르다. 여기서는 숫자가 주어진 종이 표다.

조건의 AND는 하나라도 실패 또는 미확인이면 자동 통과시키지 않는다는 뜻이다. 지표가 반올림된 표시값이라면 경계 판정에는 원값과 반올림 규칙을 확인한다. 예제에서는 표시 소수를 정확한 입력값으로 정한다.

결정은 특정 결과물에 귀속된다

승인자는 기준 버전과 모델 버전/hash, 평가 데이터·코드의 ID, 검토 결과, 결정 이유를 묶는다. 평가 뒤 파일이 바뀌면 같은 파일명이어도 과거 증거가 현재 바이트를 검토했다고 보장하지 못한다. 변경된 대상은 새 평가/검토가 필요할 수 있다.

tag를 approved로 적거나 registry에 등록하는 API 자체가 이 자체 정책을 강제한다고 주장하지 않는다. 실제 권한 제어·감사·승인 절차는 사용 환경별로 구현하고 확인해야 한다. 개인이 자기 지표를 적는 것과 독립 검토를 수행한 것은 구별한다.

승인과 배포후 확인을 분리한다

기준 통과와 승인 기록완료는 배포해도 되는지 판단할 근거다. 실제 배포 성공·서버 버전 확인·장애 없는 실행은 이후 다른 증거다. 실패 시 되돌릴 버전과 입력 호환성·중지 조건도 함께 정한다.

실제로 측정하지 않은 p95나 실행하지 않은 규격 검사를 PASS로 만들지 않는다. 미수행/실패/통과의 구별을 남기면 다음 담당자가 필요한 작업을 알 수 있다. 이 단원은 가상 결정표이며 프로젝트의 실제 배포 승인이나 측정 로그가 아니다.

중간 과정을 따라가는 예제

후보 A:정확도 .93/p95 55ms/규격 PASS/검토 완료, B:.92/45/PASS/완료, C:.94/40/미수행/완료다. 위 모든 조건을 적용하라.

  1. A는 정확도 통과지만 55>50이라 지연 조건 실패다.

  2. B는 .92≥.92/45≤50이며 두 증거 조건도 통과라 기준상 승격 후보다.

  3. C의 좋은 두 수치가 미수행 규격 검사를 대신하지 않는다. 아직 통과 아님으로 남긴다.

  4. B도 대상 버전/hash와 승인자/기준/시각/이유를 기록하고 실제 배포 성공은 별도 확인한다.

기준상 후보는 B뿐이다. A실패/C미확인과 B의 실제 배포 미수행을 구별한다.

한 단계 더

성능을 올리되 p95가 증가하는 후보와 정확도가 조금 낮고 빠른 후보의 trade-off표를 그리자. 필요시 기준을 바꿀 수 있지만 후보를 본 뒤 기준을 몰래 바꾸지 말고 기준 버전/이유를 남긴다. 실제 조직 승인은 미수행이다.
