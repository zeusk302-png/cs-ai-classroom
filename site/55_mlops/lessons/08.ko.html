shadow·canary

전체 오류율이 높은 버전이 모든 집단에서도 더 나쁠까?

아래 수치는 실제 트래픽이 아닌 자체 요청 장부다. 기존 버전 O는 쉬운 요청 90개에서 오류 1개, 어려운 요청 10개에서 오류 3개다. 새 버전 N은 쉬운 요청 10개에서 오류 0개, 어려운 요청 90개에서 오류 18개다. O의 전체 오류율은 4%, N은 18%다. 그러나 쉬운 집단에서는 N의 0%가 O의 1/90보다 낮고, 어려운 집단에서도 N의 20%가 O의 30%보다 낮다. 전체 비교에는 버전과 요청 난이도 비중이 함께 바뀌었다.

공통 목표를 쉬움과 어려움 각각 절반으로 정하면 O의 오류율은 (1/90+3/10)/2=7/45이고 N은 (0+18/90)/2=1/10이다. 이 목표 아래 N이 낮다. 이 표만으로 무작위 배정이나 인과 효과가 증명되지는 않는다. 관측한 두 집단의 비율을 같은 목표로 다시 가중한 결과다. Google SRE의 대표성·귀속과 공유 실패 영역 설명을 읽고 이 별도 모형을 구성했다.

별도 shadow 장부는 원래 요청 100개를 O가 모두 응답하고 44개를 N에 복제한다. 짝이 완성된 40개 중 출력이 같은 ID는 32개, 다른 ID는 8개이며 나머지 4개는 새 결과가 누락됐다. 완성 짝의 일치율은 32/40=80%다. 복제한 전체 44개의 일치율은 미확인 네 결과를 모두 불일치로 두면 8/11, 모두 일치로 두면 9/11이다. 사용자 응답은 100개, 추론 실행은 144회다. 응답을 폐기해도 공유 저장소 쓰기를 금지하지 않으면 부작용이 남는다.

복제해서 보는 shadow

shadow는 기존 버전이 응답하는 동안 새 버전에도 요청을 복제해 계산을 관찰한다. 여기서 새 응답은 사용자에게 전달하지 않는다. Istio의 mirroring은 복제 응답을 폐기하므로 결과 비교를 하려면 별도 기록과 요청 식별자가 필요하다. 새 서비스가 메일 발송이나 결제 같은 부작용을 일으키면 응답만 버려도 영향은 남는다. 복제 입력은 권한·개인정보 조건을 지키고, 쓰기 작업을 격리한 뒤 사용해야 한다.

일부가 실제로 받는 canary

canary는 일정 기간 일부 실제 트래픽을 새 버전에 보내 평가한다. 나머지 기존 버전은 control이다. 새 버전의 응답이 실제 사용자에게 가므로 소수에게도 실패가 발생할 수 있다. 5% 분배는 일반적으로 긴 시간의 비율 목표이지 매 20개 요청마다 반드시 한 개라는 약속이 아니다. 사용자 식별자의 일정한 해시로 라우팅하면 같은 사용자가 버전을 계속 오가는 문제를 줄일 수 있다.

분모를 함께 읽기

전체 오류율만 보면 작은 canary의 문제는 숨을 수 있다. 버전별 오류 건수와 요청 수, 지연, 입력 조건을 함께 기록하고 증설·중단 기준을 미리 정한다. 관측 창이 짧거나 특정 사용자만 포함되면 희귀 실패와 공정성 문제를 놓친다. shadow의 응답 일치율은 실제 사용자의 클릭이나 학습 효과를 측정하지 못하므로 온라인 품질 검증과 구별한다.

전체 오류율이 높은 버전이 모든 집단에서도 더 나쁠까?
대상 또는 조건장부와 결과

O의 관측 혼합

쉬움 90개와 어려움 10개, 오류 4개로 전체 4%다.

N의 관측 혼합

쉬움 10개와 어려움 90개, 오류 18개로 전체 18%다.

공통 절반 목표

O는 7/45, N은 1/10의 가중 오류율이다.

shadow의 완성 짝

40개 중 32개가 같아 일치율은 80%다.

첫 두 행은 서로 다른 집단 비중을 사용한다. 셋째 행은 같은 목표 비중을 사용한다. 마지막 행의 분모는 전체 사용자 요청이나 전체 복제 수가 아닌 비교 결과가 완성된 ID 수다.

중간 과정을 따라가는 예제

가상으로 정확히 1000개 요청을 기존 900개·새 버전 100개로 배정했다. 기존 오류9개, 새 오류8개다. 전체와 버전별 오류율을 구하라.

  1. 기존 9/900=1%, 새 8/100=8%이다.

  2. 전체 (9+8)/1000=1.7%이다.

  3. 새 버전은 control보다 7%p 높다. 1.7%만 보면 새 버전의 8% 문제가 작게 보인다.

기존1%, 새8%, 전체1.7%. 교육용 표이며 실제 서비스 측정은 아니다.

조건을 바꾸어 비교하기

집단 비중을 고정해 비교하기

위 O/N 표를 관측 혼합과 공통 절반 목표로 각각 비교하라.

  1. O의 오류 합은 4개이고 N의 오류 합은 18개다. 각 버전 요청 수는 100개다.

  2. O의 목표 오류율은 7/45로 약 15.56%, N은 10%다.

  3. 집단 비중 변경으로 전체 순위가 뒤집혔으므로 관측 혼합 비교를 그대로 버전 효과로 해석하지 않는다.

관측 혼합에서는 O가 낮고, 공통 절반 목표에서는 N이 낮다.

비교할 점

기본의 단일 버전 분모 비교에 요청 구성이라는 조건을 추가한다.

누락을 일치로 세지 않는 shadow

44개 복제에서 40개만 짝이 완성됐다. 이 중 32개가 일치한다. 미완성 4개를 제거한 비율과 전체 범위를 구하라.

  1. 완성 짝의 비율은 32/40=4/5다.

  2. 전체 일치 수는 32개부터 36개까지 가능하므로 전체 비율은 [8/11,9/11]이다.

  3. 새 결과가 없다는 사실을 기존 결과와 일치한다고 대입하지 않는다.

완성 짝은 80%, 전체 복제 기준 범위는 [8/11,9/11]이다.

비교할 점

같은 값의 비율도 누락 처리와 분모에 따라 의미가 다르다.

종이와 본문으로 직접 해보기

같은 1000개를 전부 기존 버전으로 응답하고 200개만 shadow에 복제하면 각 실행 수와 사용자 응답 수는?

힌트 보기

복제 실행은 원래 실행을 대체하지 않는다.

풀이 보기

오해와 반례

shadow는 사용자 응답을 안 바꾸므로 아무 위험이 없다.

추가 부하·정보 전달·쓰기 부작용은 남는다. 응답 경로만 격리했다고 입력과 외부 효과까지 안전해진 것은 아니다.

연습 1 · 값과 상태 예측

공통 목표에서 쉬운 요청 비중을 w, 어려운 비중을 1−w로 둔다. 0≤w≤1에서 N의 오류율이 O보다 낮은가?

힌트 1

집단별 차이를 가중한다.

힌트 2

O−N=w/90+(1−w)/10이다.

풀이와 답 확인

  1. 두 집단의 차이는 각각 1/90과 1/10으로 양수다.

  2. 비중이 어느 끝점이어도 가중 차이는 양수다.

모든 w에서 N이 엄격히 낮다. 관측한 집단별 오류율을 고정한다는 전제가 필요하다.

흔한 오답에서 다시 생각하기

전체 18%이므로 N이 항상 높다.

18%는 N의 관측 비중이며 공통 목표 비중과 다르다.

연습 2 · 오류 찾아 고치기

분석자가 누락 4개를 일치로 채워 전체 shadow 일치율을 36/44로 확정했다. 무엇을 고쳐야 하는가?

힌트 1

미확인 결과는 관측 일치가 아니다.

힌트 2

36은 가능한 최대 일치 수다.

풀이와 답 확인

  1. 관측한 일치는 32개뿐이다.

  2. 36/44는 상한으로 표시하고 하한 32/44도 함께 기록한다.

확정값을 범위 [8/11,9/11]로 고친다.

흔한 오답에서 다시 생각하기

누락은 오류가 아니므로 모두 일치다.

HTTP 오류가 없다는 사실과 출력 비교 완료는 서로 다르다.

연습 3 · 직접 만들어 보기

100개 원래 요청 중 44개를 shadow로 복제하되 후속 원장 효과를 원래 경로만 한 번 수행하도록 역할 표를 작성하라.

힌트 1

사용자 응답 경로와 쓰기 경로를 따로 적는다.

힌트 2

복제 추론에는 원장 쓰기 권한을 주지 않는 별도 모형이다.

풀이와 답 확인

  1. O는 100개 사용자 응답과 고유 요청별 원장 쓰기를 맡는다.

  2. N은 44개 계산과 ID별 비교 기록만 남기며 원장에는 쓰지 않는다.

O의 응답은 100개, 전체 추론은 144회다. 원장 효과 수는 각 고유 요청이 정확히 한 번 쓰인다는 별도 전제 아래 100개다.

흔한 오답에서 다시 생각하기

복제 응답만 폐기하면 쓰기 효과도 없어진다.

응답 폐기와 저장소 권한 차단은 별도 조건이다.

자체 실수 파이프라인에서 구 구성 A는 전처리 P_A(x)=2x, 모델 M_A(z)=3z, 후처리 H_A(y)=y−1이다. 전체 함수는 F_A(x)=6x−1이다. 새 구성 B는 P_B(x)=x+1, M_B(z)=4z, H_B(y)=y+2로 F_B(x)=4x+6이다. x=2에서 A의 출력은 11, B는 14다. 모델만 A로 복귀하고 나머지는 B로 유지한 혼합 C는 F_C(x)=3x+5다.

혼합 C도 x=2에서 11을 내므로 이 한 검사점에서는 A와 같다. 그러나 x=1에서는 A가 5, C가 8이다. 차이 F_C−F_A=6−3x는 x=2에서만 0이다. 올바른 복귀 대상은 세 구성 ID와 입력·출력 계약을 묶은 A다. 같은 shape나 한 표본 출력 일치로 전체 계약의 동등성을 주장하지 않는다.

이 문단의 시각 단위는 초다. 별도 논리 라우터는 요청 접수 때 구성 묶음 ID를 한 번 정하고 끝까지 유지한다. 시각 10에 stable이 A에서 B로 바뀌어도 시각 9에 A로 접수한 요청은 A를 사용한다. 시각 11에 새로 접수한 요청은 B를 사용한다. 단계마다 현재 stable을 다시 조회하면 전처리는 A, 모델·후처리는 B가 될 수 있다. 이것은 자체 라우터 전제이며 TensorFlow Serving의 라벨 기능이 세 구성의 원자 묶음을 자동 제공한다고 주장하지 않는다.

함께 움직이는 추론 계약

서비스 결과는 모델 가중치만으로 정해지지 않는다. 전처리·특징 순서·토큰 사전·출력 단위·후처리가 함께 계약을 이룬다. 입력 차원이 같아도 [나이,소득]을 [소득,나이]로 바꾸면 의미가 달라진다. 어떤 버전이 어떤 스키마를 받아 어떤 형식과 단위를 반환하는지 기록하고, 기존 호출자와 새 호출자의 호환 여부를 따로 확인한다.

버전과 별칭

명시 버전42는 특정 모델을 가리키고 stable이라는 라벨은 운영자가 바꿀 수 있는 별칭이다. TensorFlow Serving은 specific 정책으로 여러 버전을 동시에 유지하고 라벨을 배정할 수 있다. 라벨이 있는 것만으로5% 분배가 생기지는 않는다. 클라이언트나 앞단 라우터가 각 요청의 라벨을 선택해야 한다. 사용자별 일정한 배정과 요청 로그의 실제 버전 기록이 원인 분석을 돕는다.

로드·준비·전환·보존

새 버전을 먼저 로드하고 정상 추론과 자원 준비를 확인한 뒤 라벨을 전환한다. 기존 라벨을 새 버전에 재배정할 때 문서는 이미 로드되어 제공 가능한 버전을 요구한다. 구 버전을 너무 일찍 내리면 즉시 복귀가 어렵다. 라벨 변경은 이미 끝난 요청 결과나 외부 쓰기를 되돌리는 트랜잭션이 아니다. 전처리까지 버전별로 짝지어 보존해야 재현 가능한 복귀가 된다.

접수 시 묶음 고정

진행 중 요청은 접수 때 정한 구성을 유지한다.

함수의 적용 순서는 전처리→모델→후처리다. 각 행의 이름은 모델 파일 하나가 아닌 세 구성의 조합이다. 마지막 행은 이 예제에서 명시한 요청 수명 규칙이다.

중간 과정을 따라가는 예제

모델42의 가상 점수는 w·x, w=(2,1), 계약 x=[나이/10,소득/100]이다. 나이20·소득300에서 계약을 지킨 경우와 순서만 뒤집은 경우를 구하라.

  1. 정상 특징은 (2,3)이고 점수2×2+1×3=7이다.

  2. 잘못된 순서 (3,2)의 점수는2×3+1×2=8이다.

  3. 차원2가 같아도 의미가 달라 모델42로 라벨만 돌리면 오류가 남는다.

정상7, 뒤집힌 특징8. 모델·전처리 조합으로 복귀해야 한다.

진행 중 요청과 별칭 전환

두 요청 R과 S는 모두 입력 x=2이며 시각 단위는 초다. R은 시각 9에 A로 접수됐고 S는 시각 11에 B로 접수됐다. stable 전환 시각은 10이다. 접수 시 묶음 고정 규칙으로 출력하라.

  1. R은 A 전체를 사용해 11을 낸다.

  2. S는 B 전체를 사용해 14를 낸다.

  3. R이 P_A 이후 전환을 따라 M_B/H_B를 쓰면 4×4+2=18이 되어 별도 혼합 결과다.

정상 출력은 R이 11, S가 14다. 단계별 별칭 재조회 사례는 R을 18로 바꾼다.

표본이 부족한 창을 건너뛰면 연속 실패가 될까?

아래는 제품 경보 구현과 별개인 자체 종이 정책이다. 1분 단위로 종료된 창의 새 버전 요청 수가 20개 이상이면 유효하다. 유효 창에서 오류율이 엄격히 10%를 넘으면 초과다. 시간상 인접한 두 창이 모두 유효 초과일 때 중단한다. 요청 수 미달이나 누락 창은 연속성을 끊고 승격은 보류한다. 관측되지 않은 창을 정상으로 단정하지도, 건너뛰어 두 창을 붙이지도 않는다. 첫 창은 시각 0초에 시작하고 60초에 끝난다.

네 창의 (요청 수,오류 수)는 (100,11),(10,2),(100,12),(100,13)이다. 첫 창은 11%로 초과다. 둘째의 비율은 20%지만 요청 수 10개여서 무효다. 셋째는 12%로 초과이고 넷째는 13%로 초과다. 최초 중단 판단은 넷째 종료 시각 240초다. 유효 세 창의 통합 오류율은 36/300=12%지만 이 통합값이 시간상 인접 규칙을 대신하지 않는다.

판단 후 미래 경로 복귀가 정확히 30초 걸리고 그 사이 새 버전에 매초 3개가 계속 접수된다고 정하면 추가 노출은 90개다. 각 요청 결과가 없으면 추가 오류 수는 0개부터 90개까지 가능하다. 별도 품질 장부는 새 요청 100개 중 라벨이 도착한 50개에서 좋은 결과 40개와 나쁜 결과 10개다. 도착 라벨 기준 좋은 비율은 80%지만 미도착 50개를 포함한 전체 비율은 [40%,90%]다. 라벨 지연과 HTTP 오류 경보를 구분한다.

  • 실패감지와 복구

    기본의 엄격한 임계값과 데이터 부족 사례를 최소 표본·시간 인접 규칙의 상태 판정에 사용한다.

  • shadow·canary

    canary와 control의 분모 및 사용자 노출을 구분해 판단 장부를 읽는다.

관측 창과 판단 규칙

판단 정책은 지표·분모·관측 기간·최소 요청 수·임계값을 함께 정한다. 이 단원의 종이 정책은 완료된 연속 두1분 창에서 새 버전 오류율이 엄격히5%를 넘으면 중단한다. 실제 제품의 경보 설정과 같다고 주장하지 않는다. 오류율0%여도 요청0개라면 성공 증거가 아니라 데이터 부족이다. 평균 지연은 긴 꼬리를 숨길 수 있어 백분위와 timeout도 함께 본다.

복귀할 수 있는 준비

SageMaker의 배포 guardrails 자동 롤백에는 CloudWatch 경보 설정이 전제이고, 경보 조회 권한도 필요하다. 두 fleet을 묶어 관측하면 구 버전 오류 때문에 배포가 중단될 수도 있다. 문서는 새 구성만의 지표로 구분하는 방법도 보여 준다. 운영 계약은 검증된 구 버전과 전처리를 유지하고, 분배 중지·복귀·정상 지표 확인·사건 기록 순서를 갖춘다.

요청 경로와 실제 영향

라우팅 복귀는 미래 요청의 경로를 바꾼다. 잘못 저장된 결과·이미 보낸 알림·캐시에 남은 응답은 별도 수정 대상이다. 감지 전 피해를 줄이는 것과 피해를 되돌리는 것을 구분한다. 새 버전에서만 문제가 났다는 가정도 데이터나 외부 서비스의 공통 장애가 있으면 틀릴 수 있다. 복귀 후 지표가 회복하지 않으면 원인 가정을 재검토한다.

표본이 부족한 창을 건너뛰면 연속 실패가 될까?
대상 또는 조건장부와 결과

첫 창

100개 중 오류 11개로 유효 초과다.

둘째 창

10개 중 오류 2개지만 최소 20개에 못 미쳐 무효다.

셋째 창

100개 중 오류 12개로 유효 초과다.

넷째 창

100개 중 오류 13개로 유효 초과이며 인접 셋째와 함께 중단 조건이다.

유효 여부를 먼저 확인하고 엄격한 비율 비교를 한다. 무효는 비율 0%와 다르다. 두 창이라는 표현은 유효 창 목록의 인접이 아닌 실제 시간 창의 인접이다.

중간 과정을 따라가는 예제

가상 새 버전의1분 창 요청이 각100개이고 오류가 순서대로4,7,8개다. 연속 두 창의 오류율이 엄격히5% 초과일 때 중단한다. 복귀까지 추가30초 동안 매초2개가 새 버전에 간다고 가정하라.

  1. 오류율4%,7%,8%이다.

  2. 첫 창은 미초과, 둘째와 셋째가 연속 초과이므로 셋째 종료 시 중단 판단이다.

  3. 복귀 전 추가 노출 요청은30×2=60개이다. 오류 건수는 그60개의 실패 여부를 모르므로 구할 수 없다.

셋째 창 종료에 판단, 추가 노출60개. 실제 감지·복구 측정이 아니다.

조건을 바꾸어 비교하기

무효 창을 끼운 네 창

위 네 창에 정책을 적용하고 최초 판단 시각을 구하라.

  1. 둘째 창은 20%여도 무효라 첫째의 연속성을 끊는다.

  2. 셋째와 넷째가 시간상 인접한 유효 초과 쌍이다.

  3. 각 창이 60초이므로 넷째 종료는 240초다.

최초 판단은 240초다.

비교할 점

기본의 연속 비율 규칙에 최소 표본과 무효 창 처리 계약을 추가한다.

도착한 라벨만 좋은 비율

100개 중 라벨이 온 50개에서 40개가 좋다. 전체 좋은 비율과 추가 노출을 혼동하지 말고 범위를 구하라.

  1. 완료 라벨 기준 비율은 40/50=80%다.

  2. 미도착 50개가 모두 나쁘면 전체 40%, 모두 좋으면 90%다.

  3. 라벨 도착이 대표 표본이라는 가정이 없으므로 완료 비율을 전체 확정값으로 쓰지 않는다.

전체 좋은 비율은 [40%,90%]다.
