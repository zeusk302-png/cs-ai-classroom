소단원 3.1

lineage와 snapshot

모델 파일 하나만 남기면 그 모델이 어떤 자료를 보고 배웠는지 다시 알 수 있을까?

준비 개념과 학습 목표

준비 개념

  • artifact는 데이터·특징표·모델 등 보존할 산출물이다. execution은 그 입력으로 변환이나 학습을 수행한 한 실행이다.

  • 유향 간선 A→E→B는 실행 E가 A를 입력으로 받아 B를 냈음을 뜻한다. 이 단원은 순환 없는 기록 그래프를 쓴다.

  • snapshot은 특정 시점/버전의 내용과 읽기 경계를 고정한 자료다. 같은 이름의 가변 파일 경로만으로 내용은 고정되지 않는다.

학습 목표

  • 입출력 lineage에서 오염된 자료의 영향을 받는 모델을 추적한다.

  • 내용 고정·시점·환경·난수 기록과 재현성의 한계를 구별한다.

각 표를 정상적으로 읽었는데도 합계가 틀릴 수 있을까요?

새 종이 계좌 표에서 시점 0의 A와 B 잔액은 각각 6과 4다. 시점 1에 A에서 B로 2를 옮기는 원자적 거래가 완료되어 각각 4와 6이 된다. 다른 거래는 없고 각 시점의 합계는 10이다. 실제 금융 계좌나 데이터베이스가 아닌 일관된 읽기 경계의 작은 모형이다.

A를 시점 0에 읽고 B를 시점 1에 읽으면 합계는 12다. 반대로 A를 시점 1, B를 시점 0에서 읽으면 합계는 8이다. 네 개별 읽기 값은 모두 실제로 있었지만 두 혼합 쌍은 어떤 명시 시점의 상태도 아니다. 각 파일의 내용 ID를 고정하는 것과 두 표가 같은 논리 시점이라는 조건은 별개다.

기록 그래프에 원본 A0와 B1을 입력으로 한 실행 E_mix와 출력 F_mix를 정확히 적어도 결과 12의 입력 일관성 오류가 사라지지는 않는다. lineage는 사용한 입력을 추적하게 해 주며 입력 계약을 자동 승인하지 않는다. A0의 영향을 앞으로 찾을 때 B1은 E_mix의 다른 입력이므로 오염이 역방향으로 전파된다고 판단하지 않는다.

별도 캐시 모형은 입력 x=3, 코드 y=ax+b, 상태 (a,b)를 사용한다. 상태 (2,1)에서는 출력 7이고 (3,1)에서는 출력 10이다. 입력 ID와 코드 ID만 같은 키는 이 두 실행을 구별하지 못한다. 결과에 영향을 주는 상태와 외부 조회 판본을 키에 포함하거나 캐시 재사용을 거부해야 한다. 완전한 키의 기록과 실제 재실행 일치의 증거도 구별한다.

레시피와 재료의 실제 기록

요리 이름만 있어서는 어떤 재료를 썼는지 모르는 것처럼 모델 이름만으로는 원본을 추적할 수 없다. 실제 기록에서는 원시 자료 D, 특징표 F, 모델 M 각각에 안정적인 식별자를 주고 실행 E의 입력·출력 관계를 남긴다. 비유의 레시피와 달리 실행은 프로그램 버전·매개변수·환경 및 성공/실패 상태도 필요하다.

lineage는 산출물의 계보이며 파일을 한 디렉터리에 넣는 것과 다르다. MLMD의 Event가 artifact와 execution을 연결하듯, 자체 표에서도 입력 ID·출력 ID·실행 ID를 따로 둔다. 실험 이름이라는 Context는 묶는 이름이지 데이터 내용 자체나 완료 상태를 대체하지 않는다.

같은 경로와 같은 내용은 다르다

어제의 data.csv와 오늘의 data.csv에 행이 추가되었다면 경로는 같아도 학습 입력이 달라졌다. snapshot은 변경 없이 보존된 바이트, schema·행 선택 규칙·분할 기준·조회 시각 등을 명시한다. 데이터베이스의 일관된 읽기 경계 없이 파일들을 하나씩 복사하면 서로 다른 시점의 표가 섞일 수 있다.

내용 digest는 바이트 변화 탐지에 도움을 주지만 여기서는 실제 해시를 계산하지 않는다. 해시가 같다는 근거를 의미 동일성·출처 신뢰·완전 재현성으로 확대하지 않는다. 행 순서·실수 형식·외부 조회·권한·난수·하드웨어 차이가 결과를 바꾸므로 동일 내용의 정의와 실행 조건을 각각 기록한다.

문제가 생겼을 때 그래프를 따라간다

어떤 입력 D가 잘못되었다면 D에서 앞으로 도달하는 execution과 artifact를 찾는다. 모델에서 뒤로 따라가면 원본·변환·분할·학습 환경을 확인할 수 있다. 그래프에 간선이 누락되면 영향 목록도 누락되므로 기록 완전성은 별도 확인 대상이다.

같은 입력 ID와 코드 ID로 캐시를 재사용할 때 변환 매개변수·학습 상태·환경이 결과에 영향을 준다면 캐시 키에 포함해야 한다. 난수만 같게 설정해도 병렬 연산이나 비결정적 장치까지 자동 고정되지 않는다. 이 단원의 간선 탐색은 종이 기록이며 실제 데이터 관리 서비스나 모델 재훈련을 실행한 것이 아니다.

중간 과정을 따라가는 예제

기록 그래프 D1→E1→F1→E2→M1, D2→E3→F2→E4→M2, F1과 F2→E5→M3가 있다. 모든 간선은 명시된 입력 관계이고 다른 입력은 없다고 가정한다. D1이 잘못되었다면 영향을 받는 산출물과 실행을 찾고 M3의 상류 원시 자료를 구하라.

  1. D1의 직접 후속 실행은 E1, 그 출력은 F1이다. 아직 다른 입력 D2까지 오염되었다고 판단하지 않는다.

  2. F1에서 E2와 E5를 방문하므로 출력 M1과 M3를 찾는다. D1 영향 실행 집합은 E1/E2/E5다.

  3. F2는 E5의 다른 입력이지만 간선 방향은 F2→E5다. 오염의 전방 도달성만으로 F2·M2를 포함하지 않는다.

  4. M3를 뒤로 추적하면 E5의 F1/F2, 각 E1/E3의 D1/D2가 원시 상류다. 영향 탐색과 원인 탐색의 방향이 다르다.

D1 영향 산출물 F1/M1/M3, 실행 E1/E2/E5, M3의 원시 상류 D1/D2다. 이는 주어진 완전 기록의 도달성 결과다.

준비 개념과 학습 목표

준비 개념

  • 특징 벡터의 각 열에는 순서·단위·자료형·결측 규칙이 있다. 길이가 같아도 뜻이 다르면 같은 입력이 아니다.

  • fit은 훈련 자료에서 평균·분산·어휘 등을 추정한다. transform은 고정된 그 상태로 입력을 바꾼다.

  • 여기서는 표준화 z=(x−μ)/σ, σ>0이며 σ는 훈련 집합의 모집단 표준편차로 정한다.

학습 목표

  • 훈련에서 추정한 변환 상태를 평가·서빙에 그대로 적용한다.

  • 공유 코드·버전·열 순서·단위와 허용 오차를 입력 계약으로 정한다.

변환 상태를 바꾸어도 같은 예측을 유지할 수 있을까요?

새 한 차원 입력의 기존 특징은 z=(x−12)/2이고 기존 모델은 y=3z+1이다. 새 특징 좌표를 z′=2z+1로 정의한다. 같은 원본 x라도 z와 z′의 수치가 다르다. 그러나 모델 계수까지 함께 바꾸면 같은 원본의 y를 유지할 수 있다.

z=(z′−1)/2를 기존 모델에 넣으면 y=(3/2)z′−1/2다. 따라서 새 모델은 기울기 3/2와 절편 −1/2로 정한다. x=18에서는 기존 z=3과 새 z′=7이며 두 올바른 짝의 예측은 모두 10이다. 기존 모델에 새 z′를 넣으면 22, 새 모델에 기존 z를 넣으면 4다. 변환과 모델의 판본을 하나의 짝으로 선택해야 한다.

이 일치는 명시한 가역 affine 변환의 정확 대수식이며 어느 실제 라이브러리를 변환하거나 모델을 다시 학습한 결과가 아니다. 일반식 z′=αz+β에서 α≠0이면 새 계수는 w′=w/α, b′=b−wβ/α다. α=0에서는 원래 z 정보를 잃으므로 같은 역식으로 복구할 수 없다.

별도 두 특징 모형은 점수 s=2x1−3x2이며 입력 오차는 |δ1|≤1/10, |δ2|≤1/5다. 점수 오차의 절댓값은 2/10+3/5=4/5 이하이고 δ=(1/10,−1/5)에서 상계가 달성된다. 또 별도 점수 r=2x1−x2의 열 교환 오류는 (0,0)과 (1,1) 검사에서 숨지만 (1,0)에서는 정상 2와 교환 뒤 −1로 드러난다. 유한 검사의 일치와 전체 입력의 동등성은 다르다.

코드뿐 아니라 배운 상태도 전달한다

원본 x가 모델 입력 z로 바뀌는 함수는 Tθ(x)다. θ에는 훈련 평균·표준편차·범주 어휘·결측 대체값이 들어갈 수 있다. 같은 transform 코드라도 θ가 다르면 다른 함수다. 모델 M은 자신이 학습한 Tθ와 짝지어 보관하고 서빙에서도 그 상태를 사용한다.

예컨대 범주 red/blue를 0/1로 정한 어휘와 blue/red를 0/1로 정한 어휘는 정수 길이가 같아도 의미가 반대다. 새 범주는 미리 정한 unknown 처리·오류 정책에 따라 다룬다. 모든 새 문자열을 제멋대로 다음 번호로 배정하면 모델이 배운 열의 의미와 달라진다.

자료 분할을 먼저 한다

평가 자료에서 fit을 하면 평균·특징 선택을 통해 평가 정보가 훈련에 들어간다. train에서만 상태를 구하고 train/test/live 모두 그 상태로 transform한다. cross-validation에서는 각 fold의 훈련 부분 안에서 fit해야 하므로 전체 자료에서 전처리를 미리 fit한 뒤 fold를 나누는 것도 누출이다.

scikit-learn Pipeline은 변환과 예측기를 연결하고 적절한 평가 절차 안에서 훈련 부분의 fit을 수행하는 데 도움을 준다. pipeline이라는 객체 이름만으로 시간 누출이나 잘못된 join까지 해결하지는 않는다. 원본 분할 기준·시간·레이블 수집을 함께 검사한다.

일치 확인의 입력을 정한다

같은 고정 원본 사례와 변환 상태를 오프라인·온라인 경로에 넣어 중간 특징을 비교한다. 열 이름뿐 아니라 단위·순서·결측·자료형·unknown·반올림 규칙을 기록한다. 정확 정수 결과는 같음을 검사할 수 있지만 실수 연산은 사전에 정한 절대/상대 오차와 유한성 조건을 적용할 수 있다.

작은 golden 사례 몇 개의 일치는 모든 입력에 대한 동등성 증명이 아니다. 경계값·음수·결측·새 범주·σ0 같은 조건도 점검한다. 이 단원은 σ>0 모형을 계산하며 σ0을 처리하는 라이브러리 정책을 임의로 나눗셈0으로 구현하지 않는다. 실제 시스템에서 테스트를 실행하지 않은 상태를 유지한다.

나중에 도착한 수정값을 과거 요청에 적용해도 될까요?

새 특징 이력은 각 행에 적용 시작 시각 e, 사용 가능 시각 a, 값 v를 기록한다. H1은 적용 시작 5초, 가용 시각 6초, 값 2다. H2는 적용 시작 5초, 가용 시각 12초, 값 4다. H3는 적용 시작 9초, 가용 시각 9초, 값 3이다. 시각은 공통 시계의 초이고 H2는 적용 시작 5초의 값을 나중에 수정한 행이다. H3는 적용 시작 9초의 새 값이다. 자료는 모순 없는 자체 장부이며 실제 feature store 실행이 아니다.

당시 요청 시각 t에 e≤t와 a≤t를 모두 만족한 행만 후보로 둔다. 후보에서 e가 가장 큰 행을 고르고 같은 e이면 a가 큰 행을 고른다. 이 장부에는 같은 e/a의 충돌이 없다. t=8에서는 H1만 후보여서 값 2다. t=10에서는 H1/H3가 후보이고 적용 시작이 더 늦은 H3의 값 3을 선택한다. 요청 이후 도착한 H2를 당시 알고 있었다고 취급하지 않는다.

시각 13에 과거를 재구성하면서 가용 시각 조건을 빼면 t=8에는 H1/H2 중 최신 수정 H2를 골라 값 4를 낼 수 있다. t=10에는 적용 시작 9의 H3가 여전히 우선하여 값 3이다. 그래서 일부 요청의 일치는 가용 시각을 누락한 재구성이 올바르다는 증거가 아니다. 당시 입력 재현과 나중에 수정된 사실을 반영한 재산정은 별도 목적이다.

별도 네 요청 점수 차이 장부에서 알려진 첫 두 절대차는 2와 0이다. 나머지 두 요청의 기록은 없지만 각 절대차가 2 이하라는 추가 인증 가정을 둔다. 네 요청 전체 평균 절대차는 [1/2,3/2] 범위다. 알려진 두 요청만의 평균 1은 전체 평균의 확인값이 아니다. 또 별도 두 요청의 부호 있는 차이 +2와 −2는 평균 0이지만 절대차 평균 2다.

불일치의 원인을 나눈다

훈련과 서빙은 배치/온라인 처리 방식이 다를 수 있다. 변환 생략·어휘 버전·열 순서·조회 테이블 변경은 같은 요청에서도 입력을 바꾼다. 반면 새 시점에 원본 분포가 변한 경우에는 동일 함수를 적용해도 다른 사례 분포를 보게 된다. 두 현상은 함께 일어날 수 있어 한 수치만으로 원인을 단정하지 않는다.

Google Rules of ML은 같은 사례의 훈련/서빙 점수 일치, 서빙 특징 기록, 변하는 테이블 join, 공유 코드를 강조한다. 실제 부동소수 구현은 합리적인 허용 오차가 필요할 수 있고 확률적 생성 경로는 난수 조건도 통제해야 한다. 여기의 점수는 결정적인 작은 정확 수식이다.

미래 정보를 과거에 섞지 않는다

예측 t=10시에 9:50에 발생했지만10:05에 도착한 사건은 10시에 운영 시스템이 알지 못했을 수 있다. 당시 이용 가능성을 재현하려면 발생 시각 cutoff만으로 충분하지 않고 도착·적재·snapshot 경계도 점검한다. 나중에 수정된 고객 속성을 과거 요청에 join하면 당시 특징이 바뀐다.

시간창은 시작/끝 포함 규칙과 시간대까지 고정한다. point-in-time join은 해당 요청 시각의 사용 가능한 버전을 고르는 계약이다. snapshot을 한 번 만들었다는 사실만으로 모든 과거 요청의 당시 테이블 상태를 복원한 것은 아니다. 수집되지 않은 과거 값은 알 수 없다고 남긴다.

대조 기록과 성능 측정을 연결한다

동일 요청 ID·고정 모델·변환 버전·당시 원본에 대해 offline/live 특징을 짝지어 비교하면 어떤 열이 달랐는지 찾을 수 있다. 특징이 같아도 모델 파일·계산 정밀도·후처리 규칙이 다르면 최종 점수가 달라질 수 있다. 어느 단계의 차이인지 순서대로 좁힌다.

train/holdout/다음날/live의 성능 차이는 일반화·시간 변화·구현 오류를 모두 포함할 수 있다. 짝 비교로 구현 일치를 확인한 뒤 시간 분할 평가와 데이터 품질·레이블 성숙도를 따로 본다. 서빙 로그는 필요한 정보만 적절히 관리해야 하며 전 기록 보관이 자동 정당화되지는 않는다. 실제 로그 수집·서비스 배포·품질 실험은 이 단원에서 수행하지 않는다.
