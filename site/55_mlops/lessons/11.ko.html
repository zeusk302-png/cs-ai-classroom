소단원 11.1

자원과 비용측정

추론 한 번을 싸게 만들었는데 왜 한 달 요금은 늘었을까?

준비 개념과 학습 목표

준비 개념

  • 시간과 비율
  • 학습·추론 구별
  • 처리량과 지연

학습 목표

  • 측정 구간과 분모를 정해 자원·품질을 비교한다.
  • 가상 단가로 총비용과 성공 요청당 비용을 계산한다.
  • 평균 지연과 꼬리 지연, 측정값과 추정값을 구분한다.

비교의 단위를 먼저 고정한다

학습 한 번, 추론 요청 한 번, 성공 응답 천 번, 한 달 운영은 서로 다른 비용 단위다. 모델 버전과 입력 크기, 배치 크기, 하드웨어, 관측 기간, 준비 실행 포함 여부를 함께 적는다. 같은 요청 수라도 더 긴 입력이나 재시도가 많으면 처리량과 자원이 달라진다.

시간은 벽시계 실행 시간과 장치별 사용 시간을 나눌 수 있다. 장치 두 개를 한 시간 빌리면 병렬 작업의 벽시계는 한 시간이지만 장치 시간은 두 시간이다. 지연을 줄이는 선택이 총 장치 시간까지 줄인다고 할 수 없다. CPU·GPU·메모리·저장·네트워크의 관측 범위를 쓰고 없는 측정은 미측정으로 표시한다.

숫자의 분모와 분포를 함께 기록한다

온라인 서비스에는 시도 수, 오류 수, 지연과 진행 중 요청 수가 중요하다. 성공당 비용은 성공 수, 오류율은 전체 시도 수를 분모로 쓴다. 실패 요청도 계산 자원을 사용하므로 비용에서 빼버리지 않는다. 모델 정확도와 유효 응답률을 함께 봐야 단지 답을 덜 내서 빨라진 경우를 가려낼 수 있다.

평균만 보면 드문 긴 요청을 놓칠 수 있다. 정렬한 작은 표에서 p95를 구할 때는 여기서 채택한 nearest-rank 규칙 ceil(.95n)의 위치를 명시한다. 실제 도구는 다른 보간이나 집계 방식을 쓸 수 있다. 메모리 같은 현재 값은 올라가고 내려가는 gauge, 요청 누계는 재시작 때 초기화될 수 있는 counter로 관측하는 식으로 의미를 맞춘다.

비용표는 가정과 실제 청구를 분리한다

총비용을 계산 자원 요금, 저장 요금, 전송 요금, 기타 항목의 합으로 만든다. 이 단원의 단가는 산술 연습용 가상 수치이며 특정 업체의 현재 가격이 아니다. 예약·할인·최소 청구 단위·세금·실패와 유휴 시간에 따라 실제 청구가 달라질 수 있다.

최적화 전후는 같은 품질과 입력 조건에서 비교한다. 한 번 빠른 결과가 나왔다면 반복 측정과 변동 범위를 확인할 근거가 아직 부족하다. 메트릭 라벨에 요청 ID나 모든 사용자 ID를 넣으면 경우의 수가 커져 관측 시스템 자체의 비용이 늘 수 있다. 집계 메트릭과 제한된 상세 조사 기록의 역할을 나눈다.

중간 과정을 따라가는 예제

가상 A는 장치 2개를 1.5시간, B는 1개를 2시간 사용했다. 둘 다 장치 시간당 400원, 저장 100원, 전송 200원이다. 시도는 각각 1,000회, 성공은 A 900회/B 800회다. 품질은 별도 미측정이다. 총비용과 성공당 비용을 비교하라.

  1. A의 장치 시간은 2×1.5=3시간이므로 계산 비용 1,200원, 총 1,500원이다. B는 1×2=2시간으로 계산 800원, 총 1,100원이다.
  2. A는 성공당 1,500/900=약 1.667원, B는 1,100/800=1.375원이다. 시도당 비용은 A1.5원/B1.1원으로 다른 분모다.
  3. 오류율은 A100/1,000=10%, B200/1,000=20%다. B가 성공당 싸더라도 오류를 두 배 비율로 낸다.
  4. 벽시계는 A1.5시간/B2시간이므로 A가 더 빨리 끝나지만 장치 시간과 총비용은 높다. 품질 미측정 상태에서는 더 좋은 모델을 결정하지 않는다.

가상 총비용 A1,500원/B1,100원, 성공당 약1.667원/1.375원이다. 시간·오류·품질을 함께 비교해야 한다.

종이와 본문으로 직접 해보기

지연 표 10,10,10,10,10,10,10,10,10,100 ms의 평균과 nearest-rank p95를 구하라. 총100회 중 오류5회인 표의 오류율도 구하라.

힌트 보기

평균은 합190/10이다. p95 위치는 ceil(.95×10)=10이며 1부터 세는 정렬 위치다.

풀이 보기

평균은19 ms지만 p95는10번째 값100 ms다. 이 작은 표에서 평균만 보면 긴 요청을 놓친다. 오류율은5/100=5%다. 이 표는 실제 부하 측정이 아니며 모집단의 안정된 p95 추정이라고 주장하지 않는다.

오해와 반례

GPU 사용률이 높으면 모델이 정확하고 경제적이다.

장치가 바쁘다는 것과 유용한 성공 결과를 얻는 것은 다르다. 실패한 재시도나 불필요한 계산도 높은 사용률을 만들 수 있다. 품질·유효 응답·지연·성공당 비용을 별도로 측정해야 한다.

소단원 11.2

접근통제·모델위험

예측 API를 호출할 수 있다는 것이 학습 데이터도 받을 수 있다는 뜻일까?

준비 개념과 학습 목표

준비 개념

  • 인증과 권한
  • 모델 평가
  • 데이터와 모델 산출물

학습 목표

  • 역할·동작·대상·조건으로 최소 권한을 설계한다.
  • 접근 허가와 모델 사용 적합성을 다른 판단으로 본다.
  • 전체 정확도와 집단별 실패를 함께 읽는다.

인증과 허가는 다른 단계다

인증은 요청자가 누구인지 확인하고 권한 검사는 그 사람이 해당 대상에 해당 동작을 해도 되는지 확인한다. 학습자는 공개 모델의 예측 요청만, 학습 작업은 정해진 데이터 읽기와 후보 모델 기록만, 배포 작업은 승인된 모델 읽기와 서비스 버전 전환만 맡게 설계할 수 있다. 역할 이름보다 허용 동작과 자원 범위가 중요하다.

최소 권한은 일을 수행하는 데 필요한 범위와 조건만 주는 원칙이다. 임시 자격과 정기적인 권한 검토는 탈취되거나 남은 권한의 노출을 줄이는 수단이다. 자격이 잠깐 유효해도 그 동안 너무 넓은 권한이면 위험은 남는다. 이 설명은 특정 IAM JSON의 검증된 배포 정책이 아니라 종이 설계 활동이다.

모델 산출물도 보호 대상이다

데이터 원본뿐 아니라 모델 파일·평가 자료·설정·접속 비밀과 로그를 보호한다. 누구나 모델 파일을 바꿀 수 있다면 승인한 평가와 실제 서비스 모델이 달라진다. 읽기 권한과 수정 권한, 후보 제출과 실제 배포 권한을 나누면 이 경로를 더 잘 점검할 수 있다.

권한을 가진 사용자라도 의도한 사용 범위를 넘어 모델을 쓰는 문제는 남는다. 개발용 분류기를 중요한 결정의 단독 근거로 옮기는 것, 학습 분포와 다른 입력, 편향된 오류, 민감 정보 노출을 위험 목록에 적는다. 높은 정확도 하나가 위험을 모두 제거하지 않는다. 위험 판단은 대상 사용자·영향·실패 비용과 검토 근거를 함께 요구한다.

위험 기준과 대응자를 사전에 정한다

사용 목적과 금지 사용, 평가 집합의 범위, 집단별 오류와 미평가 조건을 기록한다. 정한 기준을 넘으면 누구에게 알리고 언제 배포를 보류·복구할지 역할을 정한다. NIST AI RMF 1.0의 위험 관리 맥락과 책임 구분을 참고하지만 문서를 썼다는 것만으로 법적 적합성이나 안전 인증을 얻는 것은 아니다.

전체 점수가 상승해도 작은 집단의 실패가 커질 수 있다. 따라서 같은 시험표에서 전체와 구간별 결과를 함께 비교한다. 표본 수가 적거나 신뢰구간을 계산하지 않았다면 그 한계를 남긴다. 평가 수치는 접근통제 설정의 정상 동작을 증명하지 않으므로 권한 검사와 모델 평가를 각각 확인해야 한다.

중간 과정을 따라가는 예제

자체 역할표에서 학습자 L은 predict:public-v1만, 학습 작업 T는 read:dataset-d1와 write:candidate만, 배포 작업 D는 read:approved와 switch:service만 허용한다. 다른 허가는 없고 나머지는 거부한다. 요청 L/read:d1, T/write:candidate, T/switch:service, D/read:approved를 판정하라.

  1. L의 허가 집합에 read:d1은 없으므로 거부한다. 예측 호출 허가가 원본 데이터 읽기로 확대되지 않는다.
  2. T의 후보 쓰기는 허용한다. 하지만 T의 서비스 전환 요청은 허가 집합에 없어 거부한다.
  3. D의 승인 모델 읽기는 허용한다. 이름이 후보인 모델을 approved로 잘못 연결하면 이 단순 표만으로 이를 자동 탐지하지 못하므로 승인 대상 식별을 별도로 검증해야 한다.
  4. 이 표의 결과는 거부·허용·거부·허용이다. 실제 클라우드에서는 상위 정책·명시적 거부·조건 등 추가 규칙을 검증해야 한다.

자체 기본 거부 모형의 요청 네 개는 순서대로 거부, 허용, 거부, 허용이다. 실제 IAM 적용 결과가 아니다.

종이와 본문으로 직접 해보기

가상 시험은 집단A80명/B20명이다. 이전 모델은 A72명/B18명, 새 모델은 A78명/B12명을 맞혔다. 전체와 두 집단의 정확도를 계산하라. B정확도85% 이상이라는 자체 배포 기준을 새 모델이 만족하나?

힌트 보기

각 집단의 분모80과20, 전체 분모100을 구별한다.

풀이 보기

이전은 A90%,B90%,전체90/100=90%다. 새 모델은 A97.5%,B60%,전체90/100=90%다. 전체는 같지만 B는30%포인트 떨어져 자체85% 기준을 만족하지 않는다. 이 가상 표로 실제 공정성이나 통계적 확실성을 인증하지 않는다.

오해와 반례

전체 정확도가 같으면 모델 위험도 같다.

활동에서 전체90%는 같지만 작은 집단B 정확도가90%에서60%로 떨어졌다. 영향과 실패 분포가 다르다. 표본·사용 맥락·실패 비용까지 검토해야 하며 하나의 전체 값만으로 위험을 판단하지 않는다.

소단원 11.3

감사기록과 책임

모델이 잘못된 답을 냈을 때 지금 파일 이름만으로 그 당시 모델을 알 수 있을까?

준비 개념과 학습 목표

준비 개념

  • 모델 버전
  • 로그와 시각
  • 접근 권한

학습 목표

  • 실행·평가·승인·배포의 연결된 근거를 설계한다.
  • 로그의 민감 정보·변조·누락 위험을 구별한다.
  • 실패 대응 책임과 증거의 한계를 기록한다.

파일 이름 대신 실행의 연결을 남긴다

같은 model.bin 이름을 계속 덮어쓰면 어느 평가 결과가 어느 모델에 해당했는지 잃을 수 있다. 실행 ID, 코드·환경·데이터 버전, 인자, 수행자, 산출물 식별, 평가표와 승인 근거를 연결한다. 해시는 바이트 식별에 도움을 주지만 파일 내용이 올바르거나 실제 평가를 거쳤다는 보증은 아니다.

배포 기록에는 요청 시각, 실제 완료 시각, 대상 서비스, 이전·새 버전, 요청자, 승인자, 결과와 실패 이유를 남긴다. 배포 요청을 했다는 기록과 실제 서비스 전환이 성공했다는 기록을 구분한다. 조사자는 사고 시각에 서비스가 가리키던 버전과 입력·특징 처리 버전까지 추적해야 한다. 이 연결이 있어도 환경과 데이터 보존이 부족하면 완전 재현은 어려울 수 있다.

기록은 필요한 만큼 남기고 보호한다

누가 언제 무엇을 어디에 했고 결과가 무엇인지 감사 목적에 맞게 기록한다. 비밀번호·접속 토큰·민감한 원문 입력을 무조건 넣지 않는다. 식별자를 줄이거나 별도 접근 제한 자료로 연결하고 보관 목적과 기간을 정한다. 상세 데이터 없이도 모델·요청 유형·오류 코드로 조사할 수 있는지 먼저 설계한다.

로그를 수정·삭제할 수 있는 사람, 열람 권한, 전송과 보관 보호 및 변조·누락 탐지를 정한다. 단순히 로그 파일을 만든 것으로 완전성과 신뢰성을 보장하지 못한다. 기록 실패 자체도 운영자가 알 수 있어야 한다. 보관 종료 시 자료를 정리하되 승인 근거나 필요한 사고 증거를 실수로 없애지 않도록 정한 규칙을 적용한다.

책임은 조사할 사람과 결정할 사람까지 정한다

모델 작성자, 독립 평가자, 배포 승인자, 운영 대응자와 사용자의 역할을 적는다. 실패를 발견한 사람이 대응 담당에게 알리는 경로, 서비스 중지나 롤백을 결정할 권한, 후속 검토와 종료 기준을 정한다. NIST의 역할·책임과 지속 검토 관점을 참고하여 변경 때마다 근거를 갱신한다.

감사는 잘못한 사람을 즉시 단정하는 일이 아니라 당시의 권한·정보·판단·실행을 근거로 복원하는 일이다. 로그에 사용자가 적혀 있어도 탈취 자격이나 기록 오류 가능성을 배제할 수 없다. 관찰과 추정, 미확인 내용을 나눠 기록하고 재발 방지를 위한 변경과 실제 검증 결과를 연결한다.

중간 과정을 따라가는 예제

자체 기록에 E17은 data:d3/code:c8로 모델 해시 hA를 생성하고 평가90%를 기록했다. 승인 A4는 hA를 허가했다. 배포 B9는 14:00 요청 후14:02 서비스 s를 hA로 전환 완료했다. 14:03 추론 R6은 hB라고 기록됐다. 이 자료로 무엇을 확인하고 무엇이 미확인인가?

  1. E17→hA→A4→B9는 학습·평가·승인·배포 근거가 연결된다. 14:00은 요청이고 실제 전환 완료 기록은14:02다.
  2. 14:03의 R6에는 hA가 아니라 hB가 적혀 있다. 같은 서비스·실제 모델 식별을 뜻한다는 가정 아래 승인·배포 연결과 불일치한다.
  3. 서비스 라우팅·모델 로딩·로그 필드 의미와 시각 정렬을 확인해야 한다. 로그가 잘못됐거나 다른 인스턴스가 남았을 수도 있어 hB가 악성 모델이었다고 즉시 결론내리지 않는다.
  4. 담당자는 R6의 대상 인스턴스와 실제 로딩 버전을 확인하고 기준에 따라 보류·복구를 결정한다. 이 예제는 기록 설계의 반례이며 실제 사고 조사 결과가 아니다.

hA의 평가·승인·배포 기록은 연결되지만 R6의 hB는 불일치다. 원인과 실제 서비스 상태는 추가 확인 대상이다.

풀이 보기

시각·서비스·요청 ID·모델 해시·역할·결과는 목적에 맞춰 제한된 기본 메타데이터로 검토한다. 접근 토큰은 기록하지 않는다. 상담 원문은 기본 로그에서 제외하고 필요성·권한·보관 조건을 별도로 심사한다. 요청 ID나 역할도 익명성을 자동 보장하지 않으므로 열람과 연결 자료를 제한한다.

오해와 반례

해시와 로그가 있으면 모델 성능과 무결성, 모든 행위의 책임까지 증명된다.

해시는 같은 바이트인지 확인하는 식별 근거다. 실제로 무엇을 평가했고 승인·서비스와 연결됐는지는 별도 기록과 검증이 필요하다. 로그는 누락·변조·자격 탈취·시각 오류 가능성이 있어 단독으로 모든 사실이나 책임을 확정하지 않는다.
