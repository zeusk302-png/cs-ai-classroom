소단원 12.1

부하·장애주입

예측 하나가 빨리 끝나는 서비스는 백 명이 동시에 쓰더라도 빠를까?

준비 개념과 학습 목표

준비 개념

  • 요청·응답과 대기열

  • 처리량과 지연

  • 가상 모형과 실제 관측

학습 목표

  • 입력 부하·처리 능력·대기열을 구별한다.

  • 제한된 장애 모형의 결과를 계산한다.

  • 시험 범위·중단 조건·미수행 상태를 명시한다.

무엇을 요청하고 무엇을 성공으로 셀까

ML 서비스의 부하는 요청 수만으로 같아지지 않는다. 입력 크기·batch·동시성·cache·모델/전처리 버전·의존 서비스도 정한다. 성공은 HTTP 응답뿐 아니라 제한 시간·출력 형식·업무 조건을 포함해 정의할 수 있다.

모델 정확성 시험과 처리 성능 시험은 다른 관찰이다. 지연 평균 하나가 실패 요청과 긴 꼬리를 숨길 수 있으므로 분모·기간·실패·분포를 함께 적는다. 실제 측정 자료가 없으면 예상 계산이라고 표시한다.

손으로 추적하는 한 서버 모형

아래 모델은 하나의 FIFO 서버가 요청 하나를 100 ms에 처리하고 초기 큐가 비어 있다. 요청들은 가상 시각에 정해진 순서로 도착하고 overhead·batch·네트워크는 없다. 처리 시작=max(도착,직전 완료), 완료=시작+100으로 계산한다.

이 모델의 최대 지속 처리량은 10개/s다. 처리율을 넘는 입력이 계속 오면 대기열이 늘지만 실제 GPU나 서버의 한계를 측정한 것이 아니다. 큐 제한·거절·timeout·취소가 있는 다른 정책은 새 가정을 요구한다.

장애 가설과 관찰을 함께 정한다

의존 서비스 timeout·process 재시작·응답 유실·용량 감소 같은 장애를 시험할 때 기대하는 상태와 중단 기준을 적는다. 격리된 시험 대상과 복구 계획을 정하고 운영 접근 권한이 있는 실제 시험과 종이 계획을 구별한다.

한 장애 주입 시험이 통과해도 다른 입력·동시 장애·자료 손상까지 검증하지는 않는다. Google SRE는 mock·system·production 시험의 경계와 재현 어려움을 구별한다. 이 활동은 종이 시나리오이며 외부 시스템을 느리게 만들거나 종료하지 않는다.

중간 과정을 따라가는 예제

자체 FIFO 모형에 네 요청이 0,50,100,150 ms에 도착한다. 처리 시간은 각각 100 ms이며 timeout/취소는 없다. 완료·대기·응답 시간을 구하자. 별도 장애 이력에서는 둘째 처리만 200 ms다.

  1. 정상 시작은 0/100/200/300, 완료는 100/200/300/400 ms다. 대기는 0/50/100/150, 응답 시간은 100/150/200/250 ms다.

  2. 정상 평균 응답은 (100+150+200+250)/4=175 ms다. 첫 도착 0부터 마지막 완료 400까지 네 완료의 이 구간 처리량은 10개/s다. 짧은 이 구간을 실제 지속 부하 측정이라고 하지 않는다.

  3. 둘째만 200 ms이면 시작은 0/100/300/400, 완료는 100/300/400/500이다. 응답 시간은 100/250/300/350, 평균 250 ms다. 한 느린 요청이 뒤의 대기에도 영향을 준다.

정상 평균 175 ms, 별도 장애 모델 평균 250 ms다. 실제 서버 성능과 장애 주입 결과는 미수행이다.

종이와 본문으로 직접 해보기

정상 모형의 성공 기준을 응답 시간 200 ms 이하로 정하면 네 요청 중 몇 개가 성공인가? 장애 이력에서는? 200 ms를 넘은 요청을 실제 서버가 취소한다고 새로 가정하면 같은 완료 표를 그대로 쓸 수 있는가?

힌트 보기

등호를 포함한다. 원래 표에는 timeout/취소가 없었다.

풀이 보기

정상은 첫 세 요청으로 3/4=75%, 장애 이력은 첫 요청만으로 1/4=25%다. 취소를 추가하면 작업이 언제·어디서 멈추는지 정해야 하므로 원래 완료 표를 자동 적용하지 않는다.

오해와 반례

단일 요청이 100 ms면 모든 요청의 응답도 100 ms다.

응답에는 대기가 포함된다. 자체 네 요청은 100/150/200/250 ms이고 느린 의존 효과는 뒤 요청에도 퍼진다.

재현·배포·롤백 실습

모델 파일만 예전 것으로 바꾸면 서비스 전체가 예전처럼 돌아갈까?

준비 개념과 학습 목표

준비 개념

  • artifact와 버전

  • 입력/출력 schema

  • 릴리스와 상태

학습 목표

  • 재현에 필요한 코드·자료·환경·설정을 묶는다.

  • 버전 호환 표로 배포/롤백 조건을 확인한다.

  • 종이 실습과 실제 배포 검증을 구별한다.

실행 기록은 재현을 돕는 자료다

ML 실험 기록에는 code revision·데이터 snapshot·split·전처리·모델 artifact·환경과 의존 버전·seed·설정·metric 정의를 함께 남긴다. MLflow는 run의 parameters·metrics·artifact와 metadata를 기록하는 도구다. 기록이 있다는 사실이 동일 출력 재현 성공을 자동 증명하지는 않는다.

seed가 같아도 병렬 실행·비결정적 연산·환경·자료 순서가 달라 결과가 달라질 수 있다. 정확한 동일성이 필요한지 허용 오차 내 재현이 필요한지 먼저 정한다. 비밀·개인정보가 든 자료를 기록에 그대로 넣지 않는다.

릴리스는 여러 호환 요소를 가진다

자체 서비스 릴리스는 모델 M, 전처리 P, schema S, serving 설정 C의 묶음이다. 각 파일의 식별과 실제 제공하는 묶음을 확인한다. 새 모델만 바꾸고 옛 전처리를 남기면 입력 의미가 달라질 수 있다.

배포 전 검증한 묶음과 운영에서 관찰한 묶음을 구별한다. 점진 배포에서는 동시에 여러 버전이 존재할 수 있으므로 단일 이름만 보고 전체 서비스가 새 버전이라고 결론 내리지 않는다. 성공 요청과 모델 품질의 확인도 서로 다르다.

되돌리는 범위를 먼저 명시한다

Kubernetes Deployment의 revision rollback은 Pod template를 되돌리는 범위다. 외부 DB migration·모델 registry의 변경·mutable 설정·이미 발생한 업무 효과까지 과거로 자동 복구하지 않는다. 이력 보존과 실제 호환 자원의 가용성도 필요하다.

이 종이 실습에서는 변경할 요소를 체크하고 보존된 artifact·호환 schema·재검증 조건을 만족할 때 롤백 계획을 승인한다. 실제 명령을 입력하지 않고 미수행으로 남긴다. 모델만 되돌리는 선택과 전체 상태 복구를 구별한다.

중간 과정을 따라가는 예제

자체 R1=(M1,P1,S1,C1), R2=(M2,P2,S2,C2)다. 허용된 (M,P,S) 조합은 (1,1,1)과 (2,2,2)뿐이다. 현재는 R2이며 DB는 S2를 요구한다. 저장된 R1 파일은 있다. 모델 M1만 바꾸는 A, Pod 묶음 R1을 되돌리고 DB는 S2로 남기는 B, 검증된 schema 호환 복구까지 R1 상태를 만드는 C를 비교하자.

  1. A는 (M1,P2,S2)가 되어 허용 조합 밖이다. 모델 파일 보존은 전처리/입력 호환을 증명하지 않는다.

  2. B는 서비스 묶음 (1,1,1) 자체는 허용되지만 DB가 S2라 서비스 S1과 계약이 어긋난다. Pod rollback만으로 DB가 S1이 되지는 않는다.

  3. C는 별도로 검증한 DB 호환 복구가 가능하고 자료 보존 조건을 지킨다는 가정 아래 묶음과 DB를 S1로 맞춘다. 이는 계획의 조건 통과이며 실제 복구 완료가 아니다.

A는 묶음 호환 실패, B는 외부 schema 호환 실패, C만 명시된 계획 조건을 통과한다. 실제 배포·자료 복구·재현 실행은 하지 않았다.

종이와 본문으로 직접 해보기

풀이 보기

seed와 모델 버전 이름만 기록하면 재현도 롤백도 검증된 것이다.

  • 미수행과 미확인 한계를 보존한다.

문서는 운영자가 행동할 근거다

runbook에는 목적·대상·사용 버전·징후·진단·권한·중단 조건·복구/되돌림·확인 방법·연락 경로를 적는다. 설명만 있고 적용 대상 버전이 없으면 다른 서비스에 잘못 적용할 수 있다. 실제 비밀은 문서에 넣지 않고 필요한 안전한 참조를 쓴다.

보고는 실제 관측과 해석을 구별한다. 요청 실패가 늘어난 사실과 그 원인이 모델 변경이라는 가설은 서로 다른 자료다. 특정 입력에서만 시험했으면 그 범위를 쓰고 학생·장치·운영 실험을 하지 않은 상태를 그대로 남긴다.

성공률은 분모를 바꾸면 다른 뜻이다

계획한 시험, 수행한 시험, 수행하여 통과한 시험을 각각 센다. 수행한 시험 중 통과 비율과 계획 대비 실행 완료율은 다르다. 미수행을 통과로 간주하거나 실패와 한 칸에 섞으면 필요한 다음 행동을 알기 어렵다.

검증 기준을 결과를 본 뒤 유리하게 바꾸면 원래 계획을 만족했는지 평가하지 못한다. 기준을 변경해야 한다면 이유와 새 버전 기준을 기록하고 이전 결과와 분리한다. 일부 지표의 통과가 전체 사용 준비 완료를 뜻하지 않는다.

사건 뒤에는 재발을 줄일 조치를 적는다

Google SRE의 postmortem은 사건·영향·완화·원인과 후속 조치를 남긴다. 사람 한 명을 탓하는 설명보다 당시 정보·도구·설계·검증에서 어떤 조건이 문제를 만들었는지 증거로 다룬다. 원인 미확인이면 미확인이라고 적는다.

후속 조치는 담당자·완료 기준·검증 방법을 가진다. 문서에 추가할 예정과 실제 수정/시험 완료를 구별한다. 운영자는 보고에서 남은 위험·복구의 한계·다음 확인 조건을 찾아야 한다.

중간 과정을 따라가는 예제

자체 시험 계획은 Q1 정상 입력, Q2 큰 입력, Q3 의존 지연, Q4 재시작, Q5 rollback이다. 가상 결과는 Q1 통과, Q2 실패, Q3 통과, Q4/Q5 미수행이다. 별도 가상 사건은 시각 2분에 오류 증가 시작, 5분에 탐지, 8분에 완화 행동 시작, 11분에 정상 조건 회복이다.

  1. 실행은 3/5=60%, 실행한 시험 중 통과는 2/3≈66.7%다. 계획 중 확인된 통과는 2/5=40%다. 실패 하나와 미수행 둘은 같은 상태가 아니다.

  2. 가상 영향 시간은 11−2=9분, 탐지 지연은 5−2=3분, 탐지 후 회복은 11−5=6분이다. 행동 시작 후 회복 3분과도 구별한다. 단일 사건을 장기 평균 MTTR 측정으로 부르지 않는다.

  3. Q2 원인은 아직 조사 중이라고 적고 Q4/Q5는 다음 수행 대상이라고 남긴다. 오류 증가 시점과 배포 시점이 가까웠다는 사실만으로 모델 원인 확정이라고 적지 않는다.

완료율 60%·실행 중 통과 약 66.7%·계획 중 확인 통과 40%를 각각 적는다. 가상 영향 9분·탐지 3분·탐지 후 회복 6분이며 실제 사건 측정이 아니다.

종이와 본문으로 직접 해보기

Q4를 뒤에 실제로 수행했다고 가정한 종이 결과에서 통과로 추가하고 Q5는 계속 미수행이면 세 비율은? 정상 회복 확인이 시각 13분으로 정정되면 가상 영향 시간과 탐지 후 회복은?

힌트 보기

새로는 실행 4·통과 3·계획 5다. 탐지는 여전히 5분이다.

풀이 보기

종이 표의 완료율 4/5=80%, 실행 중 통과 3/4=75%, 계획 중 확인 통과 3/5=60%다. 회복 시각 13분이면 영향 11분·탐지 후 회복 8분이다. 정정 근거와 이전 시간선 변경을 함께 남긴다. 실제 Q4 실행 증거가 생겼다는 주장은 하지 않는다.

오해와 반례

통과한 시험만 모으면 검증 보고의 성공률을 100%로 쓰고 미수행은 지워도 된다.

실패·미수행을 빼면 어떤 범위를 확인했는지 사라진다. 계획·실행·통과를 다른 칸에 기록하고 분모를 고정한다.
