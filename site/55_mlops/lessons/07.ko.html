소단원 7.1

batch·online 추론

밤에 한꺼번에 계산하는 예측과 버튼을 누른 순간 필요한 예측은 어떻게 다를까?

준비 개념과 학습 목표

준비 개념

  • 학습과 예측

  • 시간 단위

학습 목표

  • 업무의 batch 처리와 모델의 배치 차원을 구별한다.

  • 처리량과 응답 시간의 조건을 비교한다.

상태가 없는 계산도 묶는 방법에 따라 값이 바뀔 수 있을까?

아래는 서버를 실행한 결과가 아닌 자체 실수 계산 모형이다. 요청 A, B, C의 입력은 각각 2, 6, 10이다. 계산 F는 묶음의 각 원소 x에 2x+1을 적용한다. 세 요청을 따로 계산해도 출력은 5, 13, 21이며 한 묶음으로 계산해도 같은 순서의 값이다. 이는 F가 각 요청의 값만 사용하기 때문이다. 요청 순서를 바꾸면 출력 순서도 함께 바뀌므로 ID로 원래 요청과 다시 연결해야 한다.

별도 계산 G는 묶음 안 평균을 각 입력에서 뺀다. 세 요청을 함께 넣으면 평균이 6이므로 출력은 −4, 0, 4다. A/B를 먼저 묶고 C를 단독 처리하면 앞 묶음의 평균은 4여서 출력은 −2, 2이고 C의 출력은 0이다. 세 요청을 각각 처리하면 모든 출력이 0이다. G는 요청 사이에 저장 상태를 남기지 않지만 현재 묶음의 다른 원소를 사용한다. 따라서 상태가 없다는 사실만으로 어떤 묶음에서도 개별 의미가 같다고 인증하지 않는다.

별도 준비된 7개 입력의 시간 모형은 한 실행기에서 순차 처리하며 입출력과 대기를 제외한다. 크기가 양의 정수 b인 묶음의 비용은 C(b)=4+2b ms다. 한 건씩 처리하면 7×6=42 ms다. 최대 크기 3으로 앞에서부터 묶으면 크기 3, 3, 1이며 비용은 10, 10, 6 ms로 총 26 ms다. 준비된 마지막 부분 묶음도 실제 크기 1로 계산한다. 완료 시각은 첫 세 건이 10 ms, 다음 세 건이 20 ms, 마지막 한 건이 26 ms이므로 평균 완료 지연은 116/7 ms다. 전체 처리량 7/0.026 건/초의 역수는 개별 요청 지연이 아니다.

  • 입출력 계약

예측을 언제 쓰는지 먼저 정한다

추론은 학습된 모형을 입력에 적용해 결과를 얻는 작업이다. batch 업무는 정해진 시각이나 모인 자료 묶음에 대해 계산하고 online 업무는 도착하는 요청에 응답한다. 다음 날 보고서와 지금 보여 줄 검색 결과는 기한이 다르다.

batch 추론에도 완료 시한과 실패 처리가 필요하다. online 도 여러 요청을 짧게 모아 모델 한 번에 넣을 수 있다. 따라서 업무 방식과 텐서의 배치 크기는 다른 구분이다.

전체 응답 경로를 센다

응답에는 입력 검증·전처리·대기·모델 계산·후처리·전송이 들어갈 수 있다. 모델 계산 시간만으로 사용자가 기다린 시간을 대신할 수 없다.

처리량은 단위 시간당 완료 건수이며 개별 요청의 지연과 다르다. 모형 크기·입력 길이·장치와 동시 부하를 명시하지 않은 속도 비교는 판단 근거가 부족하다.

같은 결과를 재현할 조건을 남긴다

묶음 업무는 어떤 입력 집합과 모형 버전으로 계산했는지 남겨 누락·중복·재처리 범위를 확인한다. online 결과도 요청 식별자와 버전을 연결하면 오류를 추적하기 쉽다.

예측 계산이 같아도 후속 업무 효과가 중복되면 안 되는 경우가 있다. 추론을 재시도하는 것과 결제 같은 업무를 재실행하는 것을 한꺼번에 안전하다고 가정하지 않는다.

첫 세 행의 출력값은 시간과 무관한 별도 실수 모형이다. 마지막 행은 준비 시각을 모두 0 ms로 둔 순차 시간 모형이며 제품 실측이 아니다.

중간 과정을 따라가는 예제

자체 단일 실행기 모델에서 100 개를 한 건씩 처리하면 건당 모델 비용 10 ms 다. batch 크기 10 의 모델 비용은 묶음당 40 ms 다. 준비된 입력만 처리하고 입출력·대기 비용은 제외한다. 별도 online 경로는 검증 2+대기 5+계산 10+후처리 3 ms 다.

  1. 개별 모델 계산은 100×10=1000 ms 로 초당 100 건 상당이다.

  2. 열 묶음의 계산은 10×40=400 ms 로 초당 250 건 상당이다. 각 묶음 안 결과는 계산 40 ms 가 지나야 나오며 모으는 대기는 계산에 포함하지 않았다.

  3. online 전체는 2+5+10+3=20 ms 다. 모델 계산 10 ms 만을 전체 응답으로 보고하면 절반이 누락된다.

자체 모델의 계산 처리량은 각각 100 건/초와 250 건/초, online 전체 경로는 20 ms 다. 특정 서빙 제품의 실측 성능이 아니다.

조건을 바꾸어 비교하기

저장 상태와 묶음 내부 의존성

F와 G에 대해 전체 묶음과 개별 처리의 A 출력을 비교하라.

  1. F의 A 출력은 어느 묶음에서도 2×2+1=5다.

  2. G의 전체 묶음에서 A 출력은 2−6=−4다. 단독 A의 평균은 2여서 출력은 0이다.

F는 이 사례에서 개별 의미를 보존하고 G는 보존하지 않는다.

비교할 점

상태 유무와 묶음 내부 의존성을 구별한다.

부분 묶음의 실제 비용

준비된 7개 입력을 최대 3개씩 처리하는 전체 시간과 평균 완료 지연을 구하라.

  1. 세 묶음의 비용 합은 10+10+6=26 ms다.

  2. 완료 지연 합은 3×10+3×20+26=116 ms다.

  3. 평균은 116/7 ms이며 처리량은 3500/13 건/초다.

총 시간은 26 ms, 평균 완료 지연은 116/7 ms다.

비교할 점

묶음 수를 올림하더라도 마지막 묶음 비용을 최대 크기 비용으로 자동 대체하지 않는다.

풀이 보기

오해와 반례

online 추론은 반드시 한 요청씩 모델을 실행한다.

상태 없는 호환 입력은 서버가 동적 배치로 묶을 수 있다. 다만 모으는 지연이 업무의 응답 예산에 들어가야 한다.

연습 1 · 값과 상태 예측

G에서 A를 단독으로, B/C를 함께 처리하면 ID별 출력은?

힌트 1

각 묶음의 평균을 별도로 계산한다.

힌트 2

B/C 평균은 8이다.

풀이와 답 확인

  1. 단독 A 출력은 0이다.

  2. B의 출력은 6−8=−2, C의 출력은 10−8=2다.

ID A/B/C의 출력은 각각 0, −2, 2다.

흔한 오답에서 다시 생각하기

전체 평균 6을 계속 사용한다.

G의 정의는 현재 묶음 평균이므로 분할마다 평균이 달라진다.

연습 2 · 오류 찾아 고치기

F에 입력 순서 C,A,B를 넣은 출력 [21,5,13]을 A,B,C 순서로 보고했다. 고쳐라.

힌트 1

출력 위치와 요청 ID를 연결한다.

힌트 2

호출 순서와 보고 순서가 다르다.

풀이와 답 확인

  1. 계산 위치별 ID는 C, A, B다.

  2. ID로 재배치하면 A=5, B=13, C=21이다.

ID 대응을 보존해 [5,13,21]로 보고한다.

흔한 오답에서 다시 생각하기

연습 4 · 선택 심화

선택 심화는 기본 연습 뒤 더 탐구하고 싶을 때 풀어 보세요.

같은 시간 모형에서 7건 모두를 한 묶음으로 처리할 수 있다면 총 시간과 평균 지연은? 한 건씩 처리할 때 평균도 비교하라.

힌트 1

C(7)=18 ms다.

힌트 2

개별 완료 시각은 6,12,18,24,30,36,42 ms다.

풀이와 답 확인

  1. 한 묶음은 18 ms에 모두 끝나므로 총 시간과 평균 지연이 모두 18 ms다.

  2. 개별 처리의 평균은 168/7=24 ms다.

  3. 최대 3개 정책의 평균 116/7 ms는 18 ms보다 작지만 총 시간은 26 ms로 더 길다.

전체 처리 시간과 평균 요청 지연의 우선순위가 다를 수 있다.

앞 묶음의 일부 요청이 먼저 끝나는 시각을 함께 세어야 한다.

자체 계약의 요청은 B=1이고 입력 이름 image, FP32, 전체 shape [1,2,1,2]다. 채널 앞 순서로 R의 두 값과 G의 두 값을 저장한다. 각 값은 유한한 0..1 실수이고 원래 8비트 픽셀을 255로 나눈다. 원래 R=(255,0), G=(0,255)이므로 논리 입력은 R=(1,0), G=(0,1), 평탄 저장은 [1,0,0,1]이다. 계산 점수 s는 R의 두 값 합에 G의 두 값 합의 2배를 더한 값으로, 여기서는 3이다.

별도 원래 R=(255,255), G=(0,0)의 올바른 채널 앞 저장은 [1,1,0,0]이고 s=2다. 이를 채널 뒤 형식 [R0,G0,R1,G1]=[1,0,1,0]으로 저장한 뒤 shape만 채널 앞이라고 붙이면 해석된 R=(1,0), G=(1,0)이어서 s=3이다. 원소 수와 자료형만 확인한 검사는 이 의미 오류를 찾지 못한다. 메타데이터를 고치는 것과 실제 원소 순서를 바꾸는 것은 다른 행동이다.

출력은 두 점수 [s,4−s]이며 확률이라고 약속하지 않는다. 판본 V의 범주 순서는 [고양이,강아지]다. 첫 입력의 출력 [3,1]은 고양이를 선택하지만 판본 W가 같은 숫자에 [강아지,고양이]를 붙이면 강아지를 선택한다. 동률이면 첫 범주를 고른다는 자체 규칙도 명시한다. 입력 계약, 출력 범주 순서, 모형 판본을 묶어 검사해야 한다. max_batch_size=4인 Triton 설정에서 이 입력의 dims는 [2,1,2]이며 전체 shape에 배치 축이 추가된다. 실제 API나 모델을 호출하지 않았다.

서빙 인터페이스는 입력 이름, 자료형, 차원 순서와 허용 크기를 약속한다. 출력도 점수 벡터인지 라벨인지 이름과 크기를 정해야 호출하는 프로그램이 해석할 수 있다.

Triton 의 배치 지원 설정에서는 max_batch_size 와 dims 를 합쳐 전체 shape 를 정의한다. 제품별 규약을 먼저 읽어 배치 축을 두 번 넣거나 빠뜨리는 일을 막는다.

소단원 7.3

동시성·timeout·batching

요청을 모으면 빨라지는데 왜 첫 요청은 더 오래 기다릴까?

준비 개념과 학습 목표

준비 개념

  • 큐

  • 벽시계시간

  • 상태 없는 함수

학습 목표

  • 호환 요청의 배치 대기와 계산을 합친다.

  • 큐 timeout 과 전체 deadline·실행 취소를 구분한다.

배치가 준비됐어도 실행기가 바쁘면 언제 끝날까?

자체 단일 실행기의 FIFO 모형이며 제품 스케줄러의 모든 규칙을 대신하지 않는다. 실행기는 10 ms까지 기존 작업으로 바쁘다. 호환 요청 A, B, C가 각각 0, 2, 4 ms에 온다. 도착순으로 최대 두 건을 묶고, 첫 요청 뒤 3 ms 또는 두 건 충족 중 먼저 온 사건에서 묶음을 준비 상태로 확정한다. 확정된 묶음은 새 요청과 합치지 않는다. 실행은 비선점이며 실제 묶음 크기에 관계없이 5 ms 걸린다. 전송 등 다른 비용은 0이다.

A/B 묶음은 2 ms에 준비되지만 실행기가 비는 10 ms까지 기다린다. 실행은 10–15 ms이고 두 요청 모두 15 ms에 끝나므로 A의 지연은 15 ms, B의 지연은 13 ms다. C는 7 ms에 단독 묶음으로 준비되고 앞 묶음이 끝난 15 ms에 실행해 20 ms에 끝나므로 지연은 16 ms다. C의 모으기 대기는 3 ms, 준비 뒤 실행기 대기는 8 ms, 실행 시간은 5 ms다.

별도 응답 판정은 도착부터 12 ms 이내 완료하면 성공으로 보고 등호를 포함한다. 세 요청 모두 이 응답 목표를 놓친다. 호출자가 기다리기를 끝내도 위 모형에는 실행 중단 규칙이 없으므로 서버는 예정대로 끝난다. 성공 0건과 서버 완료 3건을 구분한다. 재시도가 후속 업무 효과를 발생시키는 경우에는 별도 원자 ID 원장이 필요하다. 같은 ID·같은 내용은 기존 결과를 돌려주고 같은 ID·다른 내용은 충돌로 거절한다는 자체 정책은 추론 계산의 무상태성과 다른 계약이다.

먼저 확인할 개념
  • 동시성·timeout·batching

    모으기 지연·실행기 대기·deadline을 서로 다른 구간으로 센다.

  • 입출력 계약

    호환 입력과 요청 ID의 대응을 유지한 채 시간표를 구성한다.

동시에 받는 것과 동시에 실행하는 것은 다르다

서버는 여러 요청을 받아도 실행기가 부족하면 큐에 보관한다. 실행 인스턴스를 늘리는 선택은 메모리·장치 경쟁과 함께 평가해야 한다. 동시 연결 수가 바로 계산 처리량은 아니다.

상태 없는 모델의 호환 요청은 묶어 실행할 수 있다. 상태가 이어지는 시퀀스는 같은 상태 소유자에게 전달하는 등 추가 규칙이 필요하므로 아무 요청이나 섞는다고 가정하지 않는다.

모으는 시간을 지연 예산에 넣는다

dynamic batching 은 도착한 호환 요청을 서버가 묶는 방식이다. 꽉 찬 묶음을 기다리는 지연 제한과 최대 크기를 정하면 처리 효율과 응답 시간을 교환할 수 있다.

설정의 배치 모으기 지연은 전체 응답의 절대 상한이 아니다. 실행기 경쟁·실행·전송 시간이 더해질 수 있다. 아래는 특정 제품 스케줄러의 모든 세부 규칙이 아닌 단순 시간표다.

timeout 은 어느 단계인지 밝힌다

큐에서 오래 기다린 요청을 거절하는 정책과 호출자의 전체 deadline 은 다른 경계다. 호출자가 기다리기를 끝냈다고 실행이 반드시 중단되거나 결과가 없어진다고 단정하지 않는다.

취소 전파·재시도·중복 식별 정책을 설계하고 실패율·큐 길이·지연 분포를 본다. 평균 시간 하나만 맞아도 일부 요청은 기한을 놓칠 수 있다.

중간 과정을 따라가는 예제

한 실행기가 비어 있고 호환 요청 A/B 가 0/2 ms 에 온다. 교육용 정책은 최대 2 개, 첫 요청 뒤 최대 3 ms 까지 모으고 2 개가 되면 즉시 시작한다. 묶음 실행 5 ms, 다른 비용 0 이다. 둘의 지연과 A 의 전체 deadline 6 ms 충족을 판단하자.

  1. t=0 에 A 를 모으고 t=2 에 B 가 와 2 개가 되면 t=2 에 실행한다.

  2. t=7 에 모두 완료하므로 A 는 7 ms, B 는 5 ms 를 기다린다. A 의 모으기 대기는 2 ms 지만 전체는 7 ms 다.

  3. A 의 deadline 은 t=6 이므로 결과가 1 ms 늦다. 모으기 지연이 3 ms 이하인 사실만으로 deadline 6 ms 를 보장하지 못한다.

A/B 지연은 7/5 ms 이며 A 는 deadline 을 놓친다. 배치 대기와 전체 응답을 따로 계산해야 한다.
